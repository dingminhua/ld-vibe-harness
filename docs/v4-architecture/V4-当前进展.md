## 2. 当前推进方式：多模型并行与主任务复核

本节记录 Human 当前确认的 V4 推进偏好，不是正式 Specs，不定义 LDVH 架构概念，也不使用“Agent”作为构成要素或产品术语。后续 V4 工作在任务能够安全拆分时采用以下方式，Human 另行调整或工具能力不支持时据实报告：

1. 主任务使用 `gpt-5.6-sol` 和 `high` 推理强度，承担 00 对齐、Specs 前置判断、任务拆分、共享接口收敛、集成、完整验证与最终结论；不使用 `xhigh` 或 `pro` 推理档位。
2. 边界清晰的独立实现优先交给其它模型的独立 Codex 任务：一般实现与聚焦测试默认使用 `gpt-5.6-terra` + `high`；低风险、机械性强且验收条件确定的实现或检查可以使用 `gpt-5.6-luna` + `high`。模型不可用或当次工具不能指定模型时，不冒充已经按该分工执行，并由主任务说明实际安排。
3. 需要不同模型时使用独立 Codex 任务和独立 Git worktree/分支；普通内部并行如果不能选择模型，只用于不要求模型分工的只读调查、独立复核或边界明确的子任务。
4. 并行开始前必须先在适用 Specs 中固定语义、范围和结果边界，并在相应工作规划中明确责任、接口、文件所有权、验证风险和集成顺序。并行任务不得自行补造或改变 Specs。
5. 并行任务不得修改同一生产文件或共同编排位置。共享接口、公共 Schema、服务注册、冲突处理和跨范围集成由主任务单线完成；无法形成互斥所有权时不并行修改。
6. 每个并行结果必须提供提交、聚焦验证、已知缺口和来源回指。主任务逐项检查 diff 与适用契约，按明确顺序集成，再运行受影响验证、完整回归、静态检查和必要的真实环境验证；分支模型的完成声明不能替代主任务复核。
7. 多模型并行只用于缩短等待时间，不降低 00、当前有效 Specs、Human Gate、Stop Conditions、术语审计和未覆盖范围如实声明的要求。架构不确定、来源冲突或需要 Human 选择时，受影响范围返回主任务处理，不由并行任务自行决定。

是否采用并行由任务结构决定：可独立验证且文件所有权互斥时并行；强顺序依赖、共同接口尚未收敛或会并发修改核心文件时保持单线。该方式适用于 V4 的 Specs 准备、Code、tests、Web 和独立复核，但只约束当前推进过程，不反向成为 Helper 服务或五类构成要素的产品定义。

2026-07-13 Human 将后续推理强度从 `xhigh` 调整为 `high`。§3.4 已经启动的批次保留启动时的真实模型与强度记录；后续新建任务或继续任务按本节使用 `high`，不得把历史执行参数改写为当前偏好。

## 3. V4 全局推进路线与并行边界

V4 不是把 V3 文件和实现复制到新目录，而是按照 00 重新建立规则、事实、行动、确定性能力和 Human 呈现之间的完整工作链路。V3 资产逐项作为历史问题、实践证据和实现参考接受保留、重写、合并、取消或延后判断；只有进入当前规则源、实现、验证和实际接入的范围，才能形成 V4 能力声明。

目标工作链路为：

```text
当前任务与工作对象
→ 解析管辖范围
→ 定位相关规则、事实、状态和能力
→ 展开足够的规则上下文
→ 判断适用要求、Human Gate 和 Stop Conditions
→ 使用适用行动结构和 Code 能力
→ 执行、验证、回写事实源
→ Web 向 Human 呈现状态、风险和证据
→ 后续 AI 从事实源恢复并接续
```
