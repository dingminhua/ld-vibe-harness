# LD Vibe Harness 的管理分层思想借鉴评估

> 创建日期：2026-05-30
> 状态：内部调研
> 编号归属：70-89 内部调研
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs/01-specs文档结构规范.md`、`specs/02-LDVH文件夹说明.md`、`specs/03-事实源边界与承载规范.md`

---

## 一、本文解决的问题

本文评估 LD Vibe Harness 应如何借鉴 PM Kit 的"七层管理分层"思想（规范 → 决策 → 需求 → 实践 → 对象 → 记录 → 审查），并结合 LD Vibe Harness 的五类构成要素和 AI 行动模型进行适配。本文是内部调研，不直接构成强制规则；调研结论进入 01-69 正式规范区间或 ADR 后才成为稳定规则。

---

## 二、PM Kit 七层模型原文要点

PM Kit 的七层理解模型如下：

```text
规范 → 决策 → 需求 → 实践 → 对象 → 记录 → 审查
```

| 层级 | 回答的问题 | 常见位置 |
|---|---|---|
| 规范 | 长期必须遵守什么 | specs、rules |
| 决策 | 为什么这样做 | ADR |
| 需求 | 本阶段要达成什么 | docs/20-89 |
| 实践 | 实际怎么做 | Skill、help、tools |
| 对象 | 管理的实体是什么，处于什么状态 | 对象规范定义，实例化于项目事实源 |
| 记录 | 实际发生了什么，有什么证据 | 更新日志、ADR、审计报告 |
| 审查 | 是否符合规范，发现如何闭环 | 审计入口、Human Gate |

核心流转链路：

```text
规范约束需求
需求产生实践
实践创建或更新对象
对象变化形成记录
审查检查记录和对象
审查发现回流为对象
对象闭环后可能反向修正规范或形成 ADR
```

---

## 三、结论

PM Kit 的七层管理分层对 LD Vibe Harness 有重要借鉴价值，但不应直接照搬。

更准确的判断是：

> LD Vibe Harness 可以吸收七层模型的分类思维和管理闭环逻辑，但应映射到自身的五类构成要素和 AI 行动模型中，而不是复制 PM Kit 的文档编号或对象体系。

LD Vibe Harness 最值得借鉴的是：

1. 把不同性质的内容分层管理，避免混在一起
2. 建立从规范到审查的完整闭环
3. 明确每一层回答什么问题、承载在哪里、如何检查
4. 防止"把任务写进规范"、"把工具当事实源"等常见误区

---

## 四、LD Vibe Harness 与 PM Kit 七层模型的关系判断

| 维度 | PM Kit 七层模型 | LD Vibe Harness 适配方向 |
|---|---|---|
| 产品定位 | 通用产品管理套件 | Vibe Coding 工程驾驭框架 |
| 第一服务对象 | 人和 AI 并重 | AI 执行者为第一服务对象 |
| 分层目的 | 帮助阅读和理解文档体系 | 帮助 AI 识别场景、加载上下文、判断门禁 |
| 架构基础 | 文档编号模型 + 管理对象 | 五类构成要素 + 生产对象 + 行动模型 |
| 事实源 | Git 文件（specs、docs、pm-kit-base） | Git 文件（specs、docs、ldvh-base） |
| 审查机制 | 98/99 审计、Human Gate | 行动模型 Gate、Human Gate、证据回写 |

LD Vibe Harness 不应成为 PM Kit clone。LD Vibe Harness 可以吸收七层模型的分类思维，但必须保持自身边界：

```text
LD Vibe Harness 的分层服务于 AI 行动模型
LD Vibe Harness 的规范体系围绕五类构成要素展开
LD Vibe Harness 的对象体系由 10-39 生产对象规范定义
LD Vibe Harness 的审查由行动模型 Gate 和 Human Gate 承载
```

## 五、可借鉴方向

### 5.1 分层管理思维

PM Kit 七层模型的核心价值是：不同性质的内容应该放在不同的位置，避免混在一起。

LD Vibe Harness 应借鉴这种思维，但映射到自身的架构中：

| PM Kit 七层 | LD Vibe Harness 对应 | 说明 |
|---|---|---|
| 规范 | specs/01-69 正式规范 | 长期必须遵守的规则，由 specs 承载 |
| 决策 | ldvh-base/adrs/ + specs/70-89 内部调研结论升级 | ADR 记录长期决策原因 |
| 需求 | Intent + TaskSet + Task | 本阶段要达成的目标，由生产对象承载 |
| 实践 | Trae Solo Skill + tools/ + docs/ 操作说明 | 实际怎么做，由 Skill 和工具承载 |
| 对象 | 10-39 Harness 生产对象规范 + ldvh-base/ 实例 | 管理的实体及其状态 |
| 记录 | ldvh-base/changes/ + ldvh-base/pitfalls/ + 更新日志 | 实际发生的事实和证据 |
| 审查 | 行动模型 Gate + Human Gate + 审计流程 | 是否符合规范，发现如何闭环 |

这七层不是互相替代关系，而是互相支撑关系。AI 行动模型可以根据当前任务场景，判断需要读取哪一层的内容。

### 5.2 管理闭环逻辑

PM Kit 的流转链路体现了完整的管理闭环：

```text
规范约束需求 → 需求产生实践 → 实践创建或更新对象 → 对象变化形成记录 → 审查检查记录和对象 → 审查发现回流为对象 → 对象闭环后可能反向修正规范或形成 ADR
```

LD Vibe Harness 可以映射到自身的 AI 行动闭环：

```text
人表达意图、约束或确认
  ↓
AI 依据 Harness 行动模型识别场景、事实源边界和 Human Gate
  ↓
AI 读取事实源（规范 + 决策 + 需求 + 对象），并判断是否需要工具、Skill 或子 Agent
  ↓
AI 按生产对象和行动模型拆解、执行、检查任务
  ↓
工具辅助解析、校验、聚合和受控写入
  ↓
执行证据、检查结果或决策回到 Git 文件事实源（记录层）
  ↓
Web Tools 展示状态、待确认事项和检查结果（审查层）
  ↓
人基于事实源追踪、确认、验收或调整方向
  ↓
失败、不确定性或人类纠偏回到 Pitfall、规则或行动模型（反向修正）
```

这与 LD Vibe Harness 00 总纲中定义的事实源闭环、AI 行动闭环和人类确认闭环一致。

### 5.3 常见误区防范

PM Kit 总结的常见误区对 LD Vibe Harness 同样适用：

| PM Kit 误区 | LD Vibe Harness 适配 |
|---|---|
| 把任务写进规范 | Task 实例应放在 ldvh-base/，不应写入 specs/ 正文 |
| 把操作步骤写成正式规则 | 操作步骤应放在 Skill、tools/ 或 docs/，不应写入 specs/ |
| 把审计发现直接变 TODO | 审计发现必须先分类（Task / Risk / Memo / 暂不处理），不能无脑任务化 |
| 把工具视图当事实源 | Web Tools 只能读取和展示 Git 文件事实源，不能成为最终事实源 |
| 把 help 当正式规范 | docs/ 操作说明和学习材料只帮助理解，正式规则以 specs/ 为准 |

这些误区应纳入 LD Vibe Harness 的事实源边界规范和 AI 行动模型的 Gate 判断中。

### 5.4 文档归属判断方法

PM Kit 提供的阅读方法（判断内容归属哪一层）对 LD Vibe Harness 同样有价值。

AI 读取一段内容时，可以按以下问题判断它的归属：

1. 它是不是长期规则？如果是，可能属于 specs/01-69
2. 它是不是长期决策原因？如果是，可能属于 ldvh-base/adrs/ 或 specs/70-89 升级后
3. 它是不是本阶段要完成的目标？如果是，可能属于 Intent / TaskSet / Task
4. 它是不是具体操作方法？如果是，可能属于 Skill、docs/ 或 tools/
5. 它是不是某个生产对象？如果是，应按 10-39 对象模型判断生命周期和状态
6. 它是不是已经发生的事实？如果是，可能属于 ldvh-base/changes/、pitfalls/ 或 ADR
7. 它是不是检查结果？如果是，应该进入审计流程，并继续分流
8. 它有没有唯一事实源？如果没有，应先确定权威位置，再写内容

这可以作为 LD Vibe Harness AI 行动模型中"场景识别"的一部分。

## 六、不应照搬的地方

| PM Kit 能力 | LD Vibe Harness 是否应照搬 | 原因 |
|---|---|---|
| 七层编号模型 | 不建议直接复制编号 | LD Vibe Harness 的编号体系围绕五类构成要素展开（00、01-07、10-39、40-69、70-89） |
| docs/20-89 需求编号 | 不适用 | LD Vibe Harness 的需求由 Intent / TaskSet 承载，不由 specs 编号承载 |
| 98/99 审计入口 | 谨慎借鉴 | LD Vibe Harness 的审查应由行动模型 Gate 和 Human Gate 承载，具体审计流程待 40-69 行动模型规范定义 |
| 文档编号模型 v3 | 不适用 | LD Vibe Harness 有自己的 specs 文档结构规范（specs/01） |

## 七、对 LD Vibe Harness 的启发

### 7.1 对 specs 文档体系的启发

LD Vibe Harness 的 specs 文档体系已经通过编号分区体现了分层思维：

| 编号段 | 类型 | 对应的管理分层 |
|---|---|---|
| 00 | 理念与纲要 | 规范层的顶层定义 |
| 01-07 | 基础规范 | 规范层的核心规则 |
| 10-39 | 生产对象规范 | 对象层的定义 |
| 40-69 | 行动模型规范 | 实践层 + 审查层的定义 |
| 70-89 | 内部调研 | 决策层的前置材料 |

PM Kit 的七层模型启发 LD Vibe Harness 应在 specs 文档中更明确地声明每一层的作用和边界，这正是 specs/01 已做的文档类型区分（正式规范、子文档、实践文档、内部调研、索引文档）。

### 7.2 对 AI 行动模型的启发

七层模型可以作为 AI 行动模型中"Context 加载"的参考：

| 场景 | AI 应读取的层级 | 目标 |
|---|---|---|
| 进入新项目 | 规范层（specs/00-07） + 对象层（ldvh-base/ 索引） | 了解项目规则和当前状态 |
| 执行具体任务 | 需求层（Task YAML） + 决策层（相关 ADR） + 规范层（相关 specs） | 了解任务目标、决策背景和约束 |
| 需要操作方法 | 实践层（Skill / tools/ / docs/） | 了解具体怎么做 |
| 任务完成 | 记录层（changes/ / pitfalls/） | 留下变更和踩坑记录 |
| 触发审查 | 审查层（Gate / Human Gate / 审计） | 判断是否符合规范、是否需要人确认 |

这能让 AI 的上下文加载更有针对性，而不是盲目读取所有文档。

### 7.3 对事实源边界规范的启发

七层模型中的"工具不是事实源"、"help 不是正式规范"等判断，与 LD Vibe Harness specs/03 的事实源边界规范高度一致。

PM Kit 的启发是：应在事实源边界规范中更明确地列出常见误区，帮助 AI 和人快速判断内容归属。

### 7.4 对生产对象规范的启发

七层模型中的"对象"层对应 LD Vibe Harness 的 10-39 生产对象规范。

PM Kit 的启发是：生产对象规范应明确每一类对象回答什么问题、承载在哪里、状态如何流转、如何与记录层和审查层联动。

## 八、风险评估

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 过度照搬 PMKit 编号 | LD Vibe Harness 复制 docs/20-89、98/99 等编号 | 坚持 specs/01 的编号分区规则 |
| 分层过于复杂 | 七层变成教条，增加 AI 和人的理解成本 | 分层只作为理解工具，不作为强制规则 |
| 与五类构成要素冲突 | 七层模型与介质、Trae Solo、工具、对象、行动模型的分类产生矛盾 | 明确七层是内容分类视角，五类是架构构成视角，两者互补而非替代 |
| 审查机制不明确 | Gate / Human Gate 的触发条件和分流规则不清晰 | 由 40-69 行动模型规范定义具体审查流程 |

## 九、评估结论

PM Kit 七层管理分层对 LD Vibe Harness 的核心启发可以浓缩为一句话：

> 把不同性质的内容分层管理，建立从规范到审查的完整闭环，防止内容混杂和事实源漂移。

LD Vibe Harness 应吸收这一思想，但走自己的路径：

```text
PM Kit：七层模型帮助人和 AI 理解文档体系
LD Vibe Harness：分层思维服务 AI 行动模型，让 AI 知道读什么、做什么、何时停下
```

因此，LD Vibe Harness 后续最优先的借鉴方向不是复制七层编号，而是：

1. 在 specs 文档中更明确地声明每一层的作用和边界
2. 在 AI 行动模型中融入分层加载上下文的逻辑
3. 在事实源边界规范中列出常见误区
4. 在生产对象规范中明确对象与记录层、审查层的联动关系
5. 在审查机制中明确 Gate / Human Gate 的触发条件和分流规则

| 检查项 | 标准 |
