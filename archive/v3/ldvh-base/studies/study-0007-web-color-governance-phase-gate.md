# Web 颜色体系治理专项（规范10）

## 研究问题

在不打断 Web 第一阶段功能交付的前提下，如何建立颜色体系治理顺序，使颜色语义可追溯、可审计，并避免组件层继续扩散硬编码业务颜色。

## 输入与边界

- 输入来自 `spark-0019`、`web/docs/01-全局设计约束.md` 和 `web/docs/11-Web测试实现规范.md`。
- 本 Study 只整理颜色治理阶段、约束和后续分流，不直接执行全量颜色重构。
- 第一阶段以功能交付为优先，颜色问题只记录偏差和新增约束，不做大规模迁移。
- 后续阶段应回到 Web 文档、主题 token、语义映射和测试入口落地，不把本 Study 作为长期执行清单。

## 关键发现

- 主题层已存在 ldvh 系列 light/dark token，具备集中治理基础。
- 分类、生命周期状态、执行流程和信号语义已经有集中映射入口。
- 当前仍存在少量 hardcoded 例外；这些例外不阻塞第一阶段交付，但应进入专项治理。
- 颜色治理需要分为冻结、语义审计、硬编码清单收敛和 token 健康回归四个阶段，避免一次性大改干扰功能线。

## 建议

- 阶段一：第一阶段执行冻结。继续功能推进，不做大规模颜色迁移，不在组件层新增硬编码业务语义颜色。
- 阶段二：语义审计与统一。核对 category、status、executionFlow 和 signals 的语义边界，确保新增颜色不在组件层新增业务语义类。
- 阶段三：硬编码与例外清单收敛。汇总 bg-white、text-white 和特殊色示例，建立用途、范围、审批理由和复检日期。
- 阶段四：token 健康与质量门。处理悬空 token，补齐 light/dark 一致性与可读性回归检查，并建立颜色审查规则。
- 执行时遵守规范10：新增颜色只能来源于 ldvh 主题 token 或已存在语义映射 key；禁止新增裸露十六进制色值；禁止新增 tailwind 语义色类直接表达业务语义；同一语义必须单点定义。

## 后续分流

- 阶段一冻结结果应回写到 Web 阶段性交付记录或相关 WorkCase，不在本 Study 内持续维护执行状态。
- 语义审计应分流到 Web 设计文档或后续 Web 治理 WorkCase。
- 硬编码清单和受控例外应分流到 Web 文档或专项事实源，明确理由、影响范围和复检时间。
- token 健康与质量门应分流到 Code/Web 测试或 CI 接入计划，避免只停留在研究结论。
