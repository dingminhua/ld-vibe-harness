## 1. 本文定位

本文是 `specs/27-Task-任务.md` 的历史机制文件（编号 27.01），承接 Rules 入口实践。本文不是独立工作模型，不得重新定义 Task 的对象定位、准入条件、对象关系、字段契约、事实源回写或证据留存。发生冲突时，以 27 主文档和上位基础规范为准。

---

## 2. 实践目标

让 AI 在执行 Task 生命周期时，自动遵守状态变更规则、关闭条件和 Human Gate 场景约束。在编辑 `ldvh-base/tasks/` 下 YAML 文件时，遵守状态流转约束和字段契约。

Rules 入口是安全带和高频提醒，不是 Task 完整流程。Task 的创建、执行、审计、关闭流程由 ldvh-intake Skill 和 ldvh-close Skill 承接，Task Tools 契约式校验由 27.04-Tools.md 和 27.06-Contract.md 承接。

---

## 3. 适用场景

1. AI 准备执行 `planned` 状态的 Task 时；
2. AI 完成执行，准备启动独立 agent 审计时；
3. AI 审计完成，准备关闭 Task 时；
4. AI 编辑 Task YAML 实例的状态字段时；
5. AI 创建子任务或修改 `sub_tasks` 字段时；
6. AI 修改 `blocked_by` 字段或执行存在前置依赖的 Task 时。

---

## 4. 实践边界

1. 本实践只约束 Rules 层对 Task 的状态变更规则、关闭条件、Human Gate 场景和禁止承载内容；
2. Task 的完整准入条件、状态机语义、对象关系和字段契约由 27 主文档定义；
3. Task 的创建、执行、审计、关闭流程由 ldvh-intake Skill 和 ldvh-close Skill 承接；
4. Task Tools 契约式校验和 Fact Validator 由 27.04-Tools.md 和 27.06-Contract.md 承接；
5. 本实践不替代 27 主文档的任何章节。

---

## 5. 实践内容

### 5.1 状态变更规则

1. AI 开始执行 `planned` 状态的 Task 前，必须先将状态变更为 `executing` 并更新 `updated` 日期，不得在 `planned` 状态下直接执行任务；
2. **前置任务强制阻塞**：Task 的 `blocked_by` 列表非空时，所有前置 Task 必须为 `closed`，当前 Task 才允许从 `planned` 进入 `executing`；
3. **创建后立即执行**：创建 Task 后，如当前会话可立即执行，必须立即将状态变更为 `executing` 并开始执行，不得停留在 `planned` 状态等待下次会话；Task 是追踪机制，不是停止点；
4. AI 完成执行后启动独立 agent 审计前，必须先将状态变更为 `verifying`；
5. 独立 agent 审计 acceptance 全部通过后，状态从 `verifying` 变更为 `review_needed`；
6. 审计发现 bug 需要修复时，状态从 `verifying` 退回 `executing`，应记录退回原因；
7. `review_needed` 状态的 Task 退回 `executing` 时，应记录退回原因并更新 `updated` 字段；
8. `closed` 是稳定终态，终态 Task 不得重开；如需重新执行，必须新建 Task 并引用原 Task。

### 5.2 关闭条件

Task 从 `review_needed` → `closed` 必须同时满足：

1. `acceptance` 字段中所有检查项已标记为 `- [x]`（未勾选的 `- [ ]` 项存在时，必须启动独立 agent 重新审计，不得直接关闭）；
2. 所有子任务（`sub_tasks`）已关闭（`status: closed`）；
3. `closure_evidence` 字段已填写。

以上条件全部满足时，AI 直接将 Task 状态变更为 `closed`，不需要 Human Gate 确认。

### 5.3 Human Gate 场景

以下场景必须触发 Human Gate：

1. 状态从 `verifying` → `review_needed` 时确认；
2. 高风险操作前确认（修改 specs、Rules、ADR、ldvh-base/ 等事实源）；
3. 创建子任务时确认（AI 自动创建子任务时应通知用户）。

Human Gate 在 Trae 中通过 AskUserQuestion 承载（依据 `specs/05-Trae-Solo环境规范.md` §9）。

### 5.4 子任务规则

1. 子任务不能再有子任务，即 `parent_task` 不为空的 Task 不得被其他 Task 的 `parent_task` 引用；
2. 子任务默认关联父任务的 `source_intent`；
3. 父任务关闭前，所有子任务必须已关闭（`status: closed`）；
4. AI 执行 Task 时发现 bug、缺口或规范遗漏，应自动创建子任务并关联到当前 Task；
5. 独立 agent 验证 acceptance 列表时发现未通过项，应为每个 bug 创建子任务；子任务修复完成后重新验证主任务 acceptance 列表；如重新验证仍发现新 bug，停止自动循环并通过 AskUserQuestion 向用户报告。

### 5.5 禁止承载内容

Rules 入口不得承载以下内容：

1. Task 完整准入条件列表；
2. Task 状态机完整定义；
3. Task 字段契约；
4. Task 对象关系转化规则；
5. Task 创建、执行、审计、关闭完整流程；
6. Task Tools 命令清单和参数说明；
7. Task 事实源回写规则；
8. Task 证据留存要求。

以上内容分别由 27 主文档、ldvh-intake Skill、ldvh-close Skill、27.04-Tools.md 和 27.06-Contract.md 承载。

---

## 6. Human Gate

1. 将 Task 相关状态变更规则、关闭条件或 Human Gate 场景从 Rules 中移除时，应经 Human Gate 确认；
2. Task 状态机或关闭条件变更影响 Rules 入口时，应经 Human Gate 确认；
3. 本子文档从 active 变更为 active-prep 或 not-created 时，应经 Human Gate 确认。

---

## 7. 检查项

检查 Task Rules 入口是否合规时，应确认：

1. Rules 是否只保留 Task 状态变更规则、关闭条件、Human Gate 场景和子任务规则；
2. Rules 是否未复制 27 主文档的完整准入条件、状态机语义或字段契约；
3. Rules 是否未复制 ldvh-intake Skill 或 ldvh-close Skill 的完整流程；
4. Rules 是否未复制 27.04-Tools.md 的命令清单和参数说明；
5. AI 执行 Task 前是否先将状态从 `planned` 变更为 `executing`；
6. AI 审计前是否先将状态变更为 `verifying`；
7. AI 关闭 Task 前是否确认关闭条件全部满足；
8. AI 是否未在关闭 Task 时要求 Human Gate 确认；
9. AI 创建子任务前是否触发 Human Gate 通知用户。
