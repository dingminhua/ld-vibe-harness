## 1. 本文解决的问题

本文解决 LD Vibe Harness 中 LDVH 工具是什么、承担什么职责、与 Git 文件事实源是什么关系，以及 Tools 辅助层和 Web 信息同步层应如何分工的问题。

12 系列只治理 LDVH 当前可定义、可实现、可检查、可治理的工具能力边界，不定义具体产品功能、页面设计、API 契约或代码实现细节。

## 2. 与 00 总纲的关系

00 定义 LDVH 工具是 LD Vibe Harness 的五类构成要素之一，并明确工具负责读取事实源、聚合事实源、校验事实源、提供受控写入入口，降低人和 AI 维护结构化文件的成本。

本文承接 00 的该判断，将 LDVH 工具拆分为 Tools 辅助层和 Web 信息同步层两类可治理工具能力：Tools 辅助层面向确定性解析、校验、聚合和受控写入；Web 信息同步层面向人可读、可确认、可操作的派生视图和受控编辑入口。

## 3. 权威领域与子文档分工

本文是 LDVH 工具体系总边界、Tools 辅助层与 Web 信息同步层分工、工具事实源边界和工具 Human Gate 总规则的事实源。12.01、12.02 分别展开两类工具能力内部设计细则，不重复维护工具总边界。

12 系列子文档分工如下：

| 文档 | 类型 | 权威领域 |
|---|---|---|
| `12-LDVH工具基础规范.md` | 主文档 | LDVH 工具总体边界、tools/web 分工、工具事实源边界、Human Gate 总规则 |
| `12.01-Tools辅助规范.md` | 子文档 | `tools/` Tools 辅助层的解析、校验、聚合、上下文包、受控写入和输出边界 |
| `12.02-Web信息同步规范.md` | 子文档 | `web/` Web 信息同步层的派生视图、信息同步原则、Human Gate UI、受控编辑入口和缓存边界 |

子文档不得另建 Tools 辅助层与 Web 信息同步层的职责分工表。需要判断某项工具能力应进入 Tools 辅助层还是 Web 信息同步层时，以本文第五节为准。

## 4. LDVH 与工具的关系

LDVH 工具是 LDVH 提供的辅助执行手段，用于降低读取、解析、校验、聚合、信息同步和受控写入 Git 文件事实源的成本。

LDVH 对工具的治理原则如下：

1. **工具不等于事实源**：工具实现、工具输出、工具缓存、数据库派生视图和 UI 状态都不能成为最终事实源。
2. **输入来自事实源**：工具读取、解析、校验和信息同步的稳定事实必须来自 Git 文件事实源。
3. **稳定事实必须回写**：工具运行中产生的稳定结论、证据、决策或变更，必须写入对应 Git 文件事实源后才成为 LDVH 稳定事实。
4. **写入必须受控**：工具可以提供受控写入入口，但不得绕过事实源边界、对象规范、行动模型或 Human Gate。
5. **实现不替代规范**：`web/` 和 `tools/` 中的代码实现不能替代 specs/、ldvh-base/或 docs/ 中的权威事实。

## 5. Tools 辅助层 / Web 信息同步层选择边界

本节是 AI 判断"这项工具能力应该进入 Tools 辅助层还是 Web 信息同步层"的唯一对比事实源，也是 12 系列工具分工的最后决策点。12.01、12.02 可引用本节，但不得复制维护另一套选择规则。

12 系列的分工原则是：本文负责“工具能力放在哪一层”，12.01、12.02 负责“选定之后如何设计、治理和检查”。当子文档中的内部检查项与本节发生冲突时，以本节为准，并应修正子文档。

| 层级 | 适合承载 | 不适合承载 | 进入条件 |
|---|---|---|---|
| Tools 辅助层 | 解析、校验、聚合、上下文包生成、派生数据生成、受控写入执行、命令行辅助 | 页面交互设计、人工确认体验、可视化布局、产品功能叙事 | 能由确定性处理逻辑描述，且主要面向机器读取、校验或执行 |
| Web 信息同步层 | 派生视图同步、状态和缺口呈现、Human Gate UI、受控编辑入口、人类确认工作台 | 事实源权威定义、对象状态机、底层校验算法、AI 决策 | 需要面向人同步、确认、操作或协同，且数据可追溯到 Git 文件事实源 |

选择顺序：

1. 能由确定性处理逻辑完成的解析、校验、聚合和写入执行，优先进入 Tools 辅助层；
2. 需要人查看、筛选、确认、编辑或验收的能力，进入 Web 信息同步层；
3. Web 信息同步层需要的派生数据应由 Tools 辅助层或后端聚合产生，不得在 UI 中另建权威事实；
4. Tools 辅助层不得因为需要被人触发就承担信息同步体验职责；
5. Web 信息同步层不得因为同步了某项状态就成为该状态的事实源；
6. 具体工具功能清单和页面设计不进入 12 正式规范，应进入 docs/、模型实践子文档或实现目录。

## 6. 工具与事实源关系

工具可以读取、解析、校验、聚合、信息同步和受控写入 Git 文件事实源。工具的价值是降低人和 AI 操作事实源的成本，而不是替代事实源。

工具输出只有满足以下条件后，才成为 LDVH 稳定事实：

1. 已写入对应权威事实源文件；
2. 写入位置符合 `specs/10-事实源边界与承载规范.md` 和对应对象规范；
3. 必要时通过 Human Gate；
4. 可以被 Git 追溯；
5. 不与已有权威事实冲突。

工具缓存、数据库派生视图、运行时索引和页面状态不得成为任务状态、证据、决策、规则或审计结果的唯一来源。

## 7. 工具与 AI 协作关系

工具可以辅助 AI 读取事实源、获得结构化上下文、执行确定性校验和准备受控写入，但工具不得替代 AI 的场景判断，也不得直接调用或模拟 AI 决策。

协作边界如下：

1. Rules 可约束 AI 使用工具的方式；
2. Skill 可在授权流程中调用工具执行确定性解析、校验、聚合、上下文准备或受控写入；
3. Agent 可调用工具获取结构化上下文或验证输入；
4. 工具不得直接调用 AI、Skill 或 Agent；
5. 工具可执行已授权、可机械化、可校验的受控写入，但不得产生授权本身、替代流程性判断或绕过 Human Gate；
6. 当前 AI 运行环境提供的 Task、Search、Agent 调用等系统能力不自动归入 LDVH Tools 辅助层，不得据此放宽 LDVH Tools 不调用 AI、Skill 或 Agent 的边界；
7. 工具输出与 AI 判断冲突时，以 Git 文件事实源和对应规范为准。

本文是工具基础规范，不是具体事实模型或行动模型。本文通过以下机制关系说明相关机制实体的落地、同步、检查或审计触发条件。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| Rules | `../.trae/rules/ldvh-l0-rules.md`、`../.trae/rules/ldvh-l1-rules.md` | L0/L1 规则入口 | 本文的工具分工、受控写入规则或事实源边界适配变化时 |
| Tools | 12.01-Tools辅助规范.md | 子文档 | Tools 辅助层能力、校验规则或写入链路变化时 |

12 系列子文档的机制关系不使用本文的普通机制落地关系，通过 NN.01-NN.06 模型实践子文档承接。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变 12 系列规范编号和职责分工；
2. 改变 `web/` 或 `tools/` 的目录定位、事实源性质或工具分工；
3. 工具写入或覆盖 Git 文件事实源；
4. 工具改变事实源归属；
5. 工具将派生数据、缓存、数据库视图或 UI 状态提升为稳定事实；
6. 工具绕过 Rules、对象状态机、行动模型或 Human Gate；
7. 工具引入持久化数据库作为派生层并影响事实源读取、信息同步或写入链路。

12 系列一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| 工具范围 | 12 系列只治理 Tools 辅助层和 Web 信息同步层两类工具能力 |
| 分工边界 | Tools 辅助层与 Web 信息同步层分工只在本文维护 |
| 子文档分工 | Tools 辅助和 Web 信息同步分别进入对应子文档 |
| 事实源边界 | 工具输出、缓存、数据库和 UI 状态未替代 Git 文件事实源 |
| 受控写入 | 写入目标、写入前校验、写入后验证和 Human Gate 已识别 |
| AI 协作边界 | 工具未直接调用 AI、Skill 或 Agent |
| Change 记录 | 工具规范或工具写入类高影响变更已记录（依据 specs/22-Change-变更记录.md） |
