> 创建日期：2026-06-06
> 更新日期：2026-06-08

## 1. 本文解决的问题

本文回答 LDVH 工作模型事实对象中的字段内容，尤其是长文本字段，应采用什么格式书写、被 Web 如何语义化渲染、被 Code 如何校验。本文不定义字段契约、对象状态机或工作模型准入条件，这些仍由 `specs-v2/05-工作模型基础规范.md` 和后续 21-39 具体工作模型规范负责。

---

## 2. 与 00、05 和 09 的关系

00 将工作模型定义为 LDVH 五类构成要素之一。`specs-v2/05-工作模型基础规范.md` 定义工作模型字段契约和事实实例边界。`specs-v2/09-事实源边界与承载规范.md` 定义 Markdown 和 YAML 的承载分工原则：

- Markdown 更适合承载背景、原因、解释、设计语境、长文本内容；
- YAML 更适合承载任务、状态、结构化关系、审计字段和需要工具解析的事实。

本文承接这一分工，进一步规定：YAML 工作模型事实对象中的长文本字段，其内容可以使用 Markdown 语义书写。Markdown 是字段内容格式，不是新事实源。YAML 仍是权威事实源，Web 和 Code 是派生视图。

---

## 3. 内容格式类型

LDVH 工作模型字段内容分为以下六种格式类型。格式类型不是独立工作模型，不具备独立生命周期、状态机或关闭条件，而是字段内容的书写和消费契约。

### 3.1 Narrative / 叙述说明

适合字段：`description`、`notes`、`context`、`success_criteria`、`constraints`、`rationale`

用途：说明背景、问题、目标、范围、约束。

书写规则：

1. 允许使用 Markdown 标题、段落、列表、引用、代码块、表格、链接；
2. 不强制 checklist；
3. 推荐使用 `## 背景`、`## 目标`、`## 边界` 等标题结构提升可读性；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
description: |
  ## 背景

  当前 Web 呈现中长文本字段缺少统一格式规范。

  ## 目标

  建立工作字段内容格式规范，统一 AI 写入、Web 渲染和 Code 校验。
```

### 3.2 Checklist / 检查清单

适合字段：`acceptance`

用途：任务验收标准、关闭检查项、质量门禁。

书写规则：

1. 必须使用 `- [ ]`（未完成）或 `- [x]`（已完成）格式；
2. 每项必须是可独立验证的原子条件；
3. 不应包含非 checklist 内容；如需补充说明，放在 checklist 项的文本中；
4. YAML 中应使用块标量 `|` 承载；
5. Task 关闭前所有检查项必须标记为 `- [x]`。

示例：

```yaml
acceptance: |
  - [ ] 创建 specs-v2/05.01-工作字段内容格式规范.md
  - [ ] 定义六种内容格式的边界和书写规则
  - [ ] 明确 Code 校验消费规则
  - [ ] 运行事实源校验通过
```

### 3.3 Evidence / 验证证据

适合字段：`verification`、`closure_evidence`

用途：记录验证过程、命令、结果和结论。

书写规则：

1. 应包含验证结果和结论；
2. 可包含验证命令、关键输出、文件路径；
3. 不建议贴超长日志，应摘要关键信息；
4. YAML 中应使用块标量 `|` 承载；
5. closed 状态 Task 的 `closure_evidence` 不得为空。

示例：

```yaml
closure_evidence: |
  ## 验证结果

  通过。

  ## 验证命令

  ```bash
  python3 tools/fact_validate.py ldvh-base/
  ```

  ## 结论

  任务满足验收条件。
```

### 3.4 Decision / 决策记录

适合字段：`decision`、`consequences`

用途：记录决策选择、理由和影响。

书写规则：

1. 应明确"选择了什么"和"为什么"；
2. 应区分已决策和未决策内容；
3. 如决策会改变事实源边界，应进入 ADR；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
decision: |
  采用 YAML 字段内 Markdown 作为内容格式方案。

  ## 理由

  - 不改变事实源边界
  - 兼容现有 Validator
  - Web 改造成本较低
```

### 3.5 Reference / 引用索引

适合字段：`related_docs`、`deliverables`、`affected_docs`

用途：记录引用路径、关联对象和外部资料。

书写规则：

1. 列表元素应为字符串路径或对象 ID；
2. 内部路径应可被 Code 校验存在性；
3. 外部链接使用完整 URL；
4. 这些字段通常是 list 类型，不是 Markdown 文本。

示例：

```yaml
related_docs:
- specs-v2/03-文档基础规范.md
- specs-v2/09-事实源边界与承载规范.md
deliverables:
- specs-v2/05.01-工作字段内容格式规范.md
```

### 3.6 Log / 过程记录

适合字段：`transition_reasons`、执行过程摘要

用途：追踪过程、记录关键节点和后续观察。

书写规则：

1. 适合时间线或过程记录；
2. 不一定是最终结论；
3. 应避免变成无结构流水账；
4. YAML 中应使用块标量 `|` 承载。

## 4. 字段到内容格式的映射

### 4.1 Intent

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `description` | Narrative | 意图背景和目标 |
| `success_criteria` | Narrative / Checklist | 成功标准，可使用 checklist |
| `constraints` | Narrative / Checklist | 约束条件 |
| `related_docs` | Reference | 引用文档路径 |
| `completion_evidence` | Evidence | 完成证据，completed / closed 时必填 |
| `status_history` | Log | 状态变化记录 |

### 4.2 Task

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `description` | Narrative | 任务背景和目标 |
| `acceptance` | Checklist | 验收标准，必须使用 `- [ ]` / `- [x]` |
| `verification` | Evidence / Checklist | 验证方式 |
| `risk_assessment` | Narrative / Checklist | 风险判断、已知不确定性和降级方式 |
| `closure_evidence` | Evidence | 关闭证据，closed 时必填 |
| `deliverables` | Reference | 交付物路径 |
| `related_docs` | Reference | 引用文档路径 |
| `affected_docs` | Reference | 受影响文档路径 |
| `status_history` | Log | 状态变化记录 |

### 4.3 ADR

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `context` | Narrative | 决策背景 |
| `decision` | Decision | 决策选择和理由 |
| `consequences` | Decision / Narrative | 决策影响 |
| `alternatives` | Narrative / Decision | 替代方案和取舍 |
| `affects` | Reference | 受影响范围、文件、规范或机制 |
| `related_tasks` | Reference | 关联任务 ID |
| `related_intents` | Reference | 关联 Intent ID |
| `related_changes` | Reference | 关联 Change commit |
| `related_rules` | Reference | 决策已升级或承接的规范、Rules 路径 |
| `superseded_by` | Reference | 替代本决策的新 ADR ID |
| `status_history` | Log | 状态变化记录 |

### 4.4 Memo

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `description` | Narrative / Decision / Reference / Log | Memo 内容灵活，按实际需要选择格式 |

### 4.5 Pitfall

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `symptoms` | Narrative | 症状描述 |
| `trigger_conditions` | Narrative / Checklist | 触发条件 |
| `root_cause` | Narrative | 根因分析 |
| `resolution` | Narrative / Evidence | 解决方案 |
| `verification` | Evidence | 验证方式 |
| `avoidance` | Narrative / Checklist | 避免方法 |
| `applicability` | Narrative | 适用范围 |

### 4.6 Profile

| 字段 | 内容格式 | 说明 |
|---|---|---|
| `description` | Narrative | 项目描述 |
| `notes` | Narrative / Reference | 备注 |

## 5. Web 语义化渲染消费规则

Web 端应根据字段内容格式选择渲染组件，而不是一律按普通 Markdown 渲染。Web 渲染是派生视图，不得回写事实源。

### 5.1 渲染映射

| 内容格式 | Web 渲染组件 | 说明 |
|---|---|---|
| Narrative | SummaryText | Markdown 正文，支持摘要/展开 |
| Checklist | ChecklistCard | 检查清单，显示完成比例和每项状态 |
| Evidence | EvidenceBlock | 验证证据区，突出命令、路径和结果 |
| Decision | SummaryText / Decision block | 决策内容，按 Markdown 渲染 |
| Reference | ReferenceCard / DocPreviewLink | 引用卡片或文档预览链接 |
| Log | SummaryText / Timeline | 过程记录，按 Markdown 或时间线渲染 |

### 5.2 当前 Web 字段分类

当前 ObjectDetail.tsx 中的字段分类与本文映射关系：

```text
SUMMARY_TEXT_FIELDS → Narrative / Decision / Log
  description, context, consequences, success_criteria, constraints,
  rationale, observation, analysis, mitigation, resolution, verification, notes

REFERENCE_FIELDS → Reference
  blocked_by, source_intent, parent_task, related_tasks, related_adrs

特殊字段：
  acceptance → Checklist（ChecklistCard）
  closure_evidence → Evidence（EvidenceBlock）
  related_docs / deliverables → Reference（DocPreviewLink）
```

Task v2 新增或明确的 `risk_assessment`、`status_history`、`related_changes` 字段，Intent v2 新增或明确的 `completion_evidence`、`status_history`、`related_memos` 字段，以及 ADR v2 新增或明确的 `alternatives`、`affects`、`related_intents`、`related_changes`、`related_rules`、`superseded_by`、`status_history` 字段，当前 Web 实现尚未完成字段分类同步。后续 Web 同步时，`risk_assessment` 应按 Narrative / Checklist 渲染，`completion_evidence` 应按 Evidence 渲染，`alternatives` 应按 Narrative / Decision 渲染，`status_history` 应按 Log 渲染，`affects`、`related_changes`、`related_memos`、`related_intents`、`related_rules`、`superseded_by` 应按 Reference 渲染；未完成同步前，不得把 Web 展示状态表述为已覆盖这些字段。

### 5.3 Web 边界约束

1. Web 展示的事实以 Git 文件事实源为准；
2. 摘要、折叠、渐进展开只能是展示层派生结果，不得回写到 YAML；
3. YAML 原文折叠区作为事实完整性兜底展示；
4. Web 不得在 UI 中另建权威事实；
5. 如需长期保存 Web 生成的总结，应创建 Memo 或更新规范允许的字段。

## 6. Code 校验消费规则

Code 应根据字段内容格式执行不同级别的校验。本文只定义校验方向，具体校验逻辑由 `tools/fact_validate.py` 实现。

### 6.1 必须校验（error）

| 对象 | 字段 | 校验规则 |
|---|---|---|
| Task | `acceptance` | 非空；如包含文本但不符合 `- [ ]` / `- [x]` 格式，报 warning |
| Task（closed） | `closure_evidence` | 不得为空 |
| Task（closed） | `closed_at` | 不得为空 |
| Memo（resolved） | `resolved_to`、`resolved_at` | 不得为空 |

### 6.2 建议校验（warning）

| 对象 | 字段 | 校验规则 |
|---|---|---|
| Task | `acceptance` | 包含文本但不符合 checklist 格式时提示 |
| 所有 | 长文本字段 | 包含冒号、换行但未使用 YAML 块标量 `|` 时提示 |

### 6.3 暂不校验

| 对象 | 字段 | 说明 |
|---|---|---|
| 所有 | Narrative 字段 | Markdown 语法正确性暂不校验 |
| 所有 | 内部路径 | 路径存在性校验待后续增强 |
| 所有 | 外部链接 | URL 可达性不校验 |
| 所有 | HTML 内容 | 危险 HTML 暂不拦截，待后续增强 |

### 6.4 当前 Validator 现状

`tools/fact_validate.py` 当前已实现：

- Task `acceptance` checklist 格式校验（warning 级别）；
- Task closed 状态 `closure_evidence` 和 `closed_at` 必填校验（error 级别）；
- Memo resolved 状态 `resolved_to` 和 `resolved_at` 必填校验（error 级别）；
- 长文本 YAML 块标量提示（YAML 解析失败时的建议信息）。

暂未实现：

- Narrative 字段 Markdown 语法校验；
- 内部路径存在性校验；
- 危险 HTML 拦截；
- Evidence 字段格式校验；
- Decision 字段结构校验。
- Task `risk_assessment`、`status_history` 和 `related_changes` 字段的专门校验。

## 7. AI 写入规则

AI 创建或更新事实对象时，应遵守以下写入规则：

### 7.1 长文本字段优先使用 YAML 块标量

以下字段如包含中文标点、英文冒号、换行、命令、列表式说明或超过一短句，应优先使用 YAML 块标量 `|`：

- Intent：`description`、`success_criteria`、`constraints`
- Task：`description`、`acceptance`、`verification`、`risk_assessment`、`closure_evidence`
- ADR：`context`、`decision`、`consequences`
- Memo：`description`
- Profile：`description`、`notes`
- Pitfall：`symptoms`、`trigger_conditions`、`root_cause`、`resolution`、`verification`、`avoidance`、`applicability`

不得把包含冒号的长文本直接写成未加引号的普通单行字符串。

### 7.2 Checklist 字段必须使用检查列表格式

Task `acceptance` 必须使用 `- [ ]` 检查列表格式，将验收标准拆解为可独立验证的原子检查项。

### 7.3 Evidence 字段应包含验证结果和结论

`verification` 和 `closure_evidence` 应包含验证结果和结论，可包含验证命令和关键输出。

### 7.4 不自行添加未定义字段

AI 不得在事实对象中添加对象规范未定义的字段。如需新增字段，应先更新对应对象规范。

## 8. 事实源边界

1. YAML 事实对象仍是权威事实源，Markdown 只是字段内容格式；
2. Web 渲染、摘要、折叠、预览都是派生视图，不得替代事实源；
3. 不引入外部 `.md` 正文文件作为事实对象内容引用机制；
4. 如未来需支持外部 Markdown 正文引用，应另建 ADR 决策，不得在本文中预设；
5. 格式类型（Narrative / Checklist / Evidence / Decision / Reference / Log）不是独立工作模型，不具备独立生命周期、状态机或关闭条件。

## 10. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 工作字段内容格式不得替代工作模型字段契约、状态机或事实源边界 | `specs-v2/05-工作模型基础规范.md`、`specs-v2/09-事实源边界与承载规范.md`、具体工作模型规范 | 工作模型治理 | 新增、删除或改变内容格式类型、字段映射或事实源边界时 |
| 确定性执行要求 | Code 应能按本文检查可机械化的字段内容格式要求 | `specs-v2/07-Code实现规范.md`、`tools/fact_validate.py` 或后续 Code 实现、正反样例 | 校验实现 | Checklist、Evidence、Reference、YAML 块标量或字段映射规则变化时 |
| Human 交互要求 | Web 按字段内容格式进行语义化渲染，但不得把渲染状态提升为事实源 | `specs-v2/08-Web信息同步规范.md`、Web 派生视图、Human Gate | Web 信息同步 | Web 渲染映射、受控编辑入口或展示字段变化时 |
| 生命周期触发要求 | 字段契约、Code 校验或 Web 渲染变化后，应检查本文是否需要同步 | 工作模型规范检查、Code 测试、Web 联动检查 | 触发保障 | 具体工作模型字段、Code 校验、Web 渲染或事实源格式变化时 |

## 11. Human Gate 与检查要求

本文变更属于规范体系变更，应评估 Human Gate。以下变更需要 Human Gate：

1. 新增或删除内容格式类型；
2. 改变字段到内容格式的映射；
3. 改变 Code 校验级别（error / warning / 不校验）；
4. 改变 Web 渲染映射；
5. 改变事实源边界声明。
