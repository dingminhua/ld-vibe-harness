## 1. 行动定位与适用场景

安装与接入初始化是把 LDVH 从规范仓库转化为用户可实际使用的管理链路的落地行动。

本文定义 AI 如何确认当前 LDVH 管理实例、确认或适配当前 AI 开发环境、引导或协助生成管辖项目配置、识别目标管辖项目、检查或建立项目文档工作区、工作对象事实源目录、AI 入口、Code / Web / 运行投影基础，并把初始化结果、缺口和降级方式回写到正确事实源。

本文把用户首次接入 LDVH 的链路划分为相邻阶段：环境确认与运行投影应用、管辖项目配置发现与确认、管辖项目产品初始化、缺口分流和产品审计输入。环境初始化记录、管辖项目配置和项目初始化结果分别保留各自事实源边界；本文只定义它们在同一接入流程中的执行顺序、Gate 和交接关系。

本文不要求创建独立环境检测器。AI 应优先基于当前会话、平台上下文、已生效入口和自身工具能力判断当前环境；判断不清时，应请求 Human 从平台适配清单或待填平台中选择；仍无法确认时，进入未知环境适配向导。项目中存在 `.trae/`、AGENTS.md、`.cursor/` 或其他平台投影痕迹，只能作为辅助线索，不得单独作为当前运行环境的唯一判据。

本文不直接绑定 Trae Solo 或任何单一平台。安装与接入初始化必须围绕当前平台适配清单执行和验证。当前优先做实的清单是 `docs/specs/04.09-Trae-Solo适配清单.md`；其他平台没有补齐清单、证据和审计结论前，不得声明完整支持，也不得作为完整初始化通过依据。

本文不定义产品审计。初始化完成后是否持续有效、是否漂移、是否真实可用，由 `docs/specs/43-product-audit-产品审计.md` 承接；本文只提供产品审计输入，不得把初始化结果冒充为产品审计结论。

本文适用于以下场景：

1. 用户要求安装、接入、初始化或启用 LDVH；
2. 用户首次在某个 AI 开发环境中使用 LDVH，需要确认环境适配、入口投影和降级方式；
3. `LDVH-GOVERNED-PROJECTS.yaml` 尚不存在、需要生成草案，或新增、删除、修改管辖项目条目后，需要确认项目是否可用；
4. AI 进入管辖项目后发现 `docs/`、`ldvh-base/`、工作区级薄入口、初始化结果或基础校验缺失；
5. 需要把 LDVH 自身 dogfood 项目校准为可被 LDVH 管辖的项目；
6. 产品审计、规范落地统筹或用户反馈发现初始化缺口，需要补齐初始化动作；
7. 当前环境、入口或项目路径变化后，需要重新确认初始化基础是否仍可用。

本文不适用于以下场景：

1. 只阅读 LDVH 规范或解释某个术语；
2. 只更新已完成初始化后的环境适配映射或运行投影漂移记录，且不影响用户接入链路；
3. 已初始化项目中的普通 Task 执行、验证、关闭或变更提交；
4. 对已完成初始化状态进行全面持续性审查；
5. 为单个工作模型创建具体事实实例，除非该实例本身是初始化目标并已通过对应 Human Gate。

## 2. 准入条件

进入安装与接入初始化前，应至少满足以下准入条件：

1. 能定位 LDVH 自身项目根目录；
2. 能读取 LDVH-AI-ENTRY.md、`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/01-目录说明.md`、`docs/specs/02-术语规范.md` 和本文；
3. 能确认当前 AI 开发环境，并能定位当前平台适配清单；无法定位时，能请求 Human 从已有清单或待填平台中选择；
4. 能读取或创建 `LDVH-GOVERNED-PROJECTS.yaml`，并确认 Human 授权范围；
5. 能明确目标管辖项目的 `id` 和 `path`，能从候选项目生成配置草案，或能暂停向 Human 请求填写；
6. 能判断当前动作是只做分析、生成初始化计划，还是允许写入环境初始化记录、管辖项目配置或管辖项目；
7. 若需要创建目录、写入初始化结果、修改配置或修改工作区级入口，已获得 Human 明确授权；
8. 若目标项目路径不存在、权限不足或可能影响用户现有项目入口，已触发 Human Gate。

以下任一条件不满足时，不得宣称安装与接入初始化完成：

1. 目标项目未登记到 `LDVH-GOVERNED-PROJECTS.yaml`，且 Human 未授权新增；
2. 目标项目 `path` 无法定位或无法判断是否为用户指定项目；
3. AI 无权检查或写入目标项目；
4. `docs/`、`ldvh-base/`、初始化结果、工作区级薄入口或必要 Code 校验缺失且未记录降级方式；
5. active 工作模型或 active 工作流程无法从 `docs/specs/20-工作模型集合索引.md`、`docs/specs/40-工作流程集合索引.md` 定位；
6. 高影响写入、入口修改或长期降级未通过 Human Gate。

## 3. 事实源边界

安装与接入初始化涉及多个事实源，必须按以下边界处理：

| 事实 | 权威位置 |
|---|---|
| LDVH 正式规范 | `docs/specs/` |
| 当前 LDVH 管理实例和管辖项目清单 | `LDVH-GOVERNED-PROJECTS.yaml` |
| AI 统一入口运行投影 | LDVH-AI-ENTRY.md |
| LDVH 自身环境初始化记录 | `LDVH-ENVIRONMENT-INITIALIZATION.md` |
| 管辖项目文档事实 | `{project.path}/docs/` |
| 管辖项目内部分析 | `{project.path}/docs/evals/` |
| 管辖项目外部引用 | `{project.path}/docs/refs/` |
| 管辖项目工作对象实例 | `{project.path}/ldvh-base/` |
| Change 事实实例 | Git commit 记录 |
| Code 实现 | `tools/` |
| Web 实现 | `web/` |

环境初始化结果应写入 LDVH 自身项目根目录的：

```text
LDVH-ENVIRONMENT-INITIALIZATION.md
```

该文件记录当前 LDVH 自身项目与当前 AI 开发环境的适配结果、运行投影状态、降级方式和 Human 确认状态。它不是 docs/specs 正式规范，不是管辖项目默认安装文件，也不替代管辖项目配置或项目初始化结果。

管辖项目配置结果应写入 LDVH 自身项目根目录的：

```text
LDVH-GOVERNED-PROJECTS.yaml
```

该文件只登记当前 LDVH 管理实例和管辖项目清单，不承载初始化状态、审计状态、环境适配正文或运行投影正文。

管辖项目产品初始化结果应写入目标管辖项目的 `docs/` 正文区，默认文件为：

```text
{project.path}/docs/ldvh-product-initialization.md
```

若管辖项目已有等价初始化说明、接入说明或项目约定文件，可以在 Human 确认后使用已有文件，但必须在初始化输出中记录实际路径。初始化结果文档不是工作对象，不具备状态机，不替代 Task、Intent、ADR、Memo、Change 或 Pitfall 的权威字段。

安装与接入初始化不得把以下内容写入错误位置：

1. 不得把产品初始化状态、初始化结果或缺口清单写入 `LDVH-GOVERNED-PROJECTS.yaml`；
2. 不得把管辖项目环境能力核验写成 LDVH 自身环境初始化记录；
3. 不得在管辖项目中默认创建 `docs/specs/` 或 `specs/`；
4. 不得在管辖项目中默认创建平台规则文件、项目指令或 AI 统一入口；
5. 不得为 removed、deferred-field、deferred-doc 或 reserved 工作模型创建默认事实源目录；
6. 不得把初始化报告、聊天记录、工具输出或 Web 状态当成最终事实源。

## 5. Scenario 识别

安装与接入初始化 Scenario 应按以下条件识别：

| Scenario | 进入条件 | 不进入条件 |
|---|---|---|
| 环境确认与运行投影应用 | 用户首次使用 LDVH、当前 AI 环境变化、缺少 `LDVH-ENVIRONMENT-INITIALIZATION.md`，或需要确认平台入口和降级方式 | 只审查已存在运行投影漂移且不影响接入链路 |
| 管辖项目配置发现与确认 | `LDVH-GOVERNED-PROJECTS.yaml` 不存在、需要新增/删除/修改项目，或需要从候选目录生成配置草案 | 已有条目且本次不改变项目身份 |
| 管辖项目产品初始化 | 用户要求接入 LDVH，或目标项目尚无初始化结果 | 只是解释 LDVH 概念或阅读规范 |
| 目录承载确认 | 需要检查或创建 `{path}/docs`、`{path}/docs/evals`、`{path}/docs/refs` 或 `{path}/ldvh-base` | 只做规范文档修改 |
| 工作模型承载确认 | 需要确认 active 工作模型实例目录、命名规则或 removed/deferred 边界 | 只创建某个具体工作对象实例 |
| 工作流程入口确认 | 需要确认 active 工作流程是否可被 AI 定位和执行 | 只执行某个已明确流程 |
| 运行投影确认 | 需要确认工作区级薄入口、AI 统一入口、平台入口或环境适配映射 | 只做普通 Task 执行 |
| 初始化缺口补齐 | 审计或执行发现初始化基础缺失 | 缺口属于普通 Task、ADR 或规范变更且不影响初始化基础 |

多个 Scenario 同时匹配时，应按环境确认、管辖项目配置、目标项目身份、目录和事实源、工作模型、工作流程、Code/Web、初始化结果的顺序处理；若某一步触发 Human Gate，应先暂停确认，不得跳到后续阶段宣称完成。

若 Scenario 不清，应先说明可能进入安装与接入初始化的原因，并请求 Human 确认当前环境、目标项目和授权范围。

## 6. 执行流程

安装与接入初始化按以下步骤执行。

### 6.1 确认初始化范围

AI 应先确认：

1. 当前 LDVH 自身项目根目录；
2. 当前 AI 开发环境是否可由 AI 基于当前会话、平台上下文、已生效入口或自身工具能力明确判断；
3. 判断不清时，Human 选择的平台适配清单、待填平台或未知环境适配路径；
4. 目标管辖项目 `id`；
5. 目标管辖项目 `path`；
6. 本次是首次安装、首次接入、补齐缺口、重新初始化还是只生成计划；
7. 是否允许写入 `LDVH-ENVIRONMENT-INITIALIZATION.md`；
8. 是否允许写入 `LDVH-GOVERNED-PROJECTS.yaml`；
9. 是否允许写入目标项目 `docs/`、`ldvh-base/` 或工作区级入口；
10. 是否存在影响用户原有项目入口的风险。

范围不清时，应暂停并请求 Human 明确当前环境、目标项目和授权范围，不得默认初始化所有登记项目。

### 6.2 确认环境与运行投影

AI 应按以下顺序确认当前环境：

1. 先基于当前会话、平台上下文、已生效入口和自身工具能力判断当前 AI 开发环境；
2. 若能明确判断，定位并读取对应平台适配清单；当前平台为 Trae Solo 时读取 `docs/specs/04.09-Trae-Solo适配清单.md`；
3. 若不能明确判断，请求 Human 从已有平台清单或待填平台中选择；
4. 若 Human 选择其他或不确定，进入未知环境适配向导，并按 04.08 待填模板记录需要补齐的清单项；
5. 不得仅凭项目中存在某个平台投影文件断言当前运行环境；
6. 不得跳过平台适配清单直接套用平台预设；
7. 不要求创建独立环境检测器；未来如需自动化，应优先作为环境投影检查或审计辅助，而不是替代 AI 判断、Human 选择和清单审计。

环境确认后，AI 应读取平台清单中的 AI-S1 至 AI-S15 和 LR-1 至 LR-7 要求响应矩阵，再读取或准备更新 `LDVH-ENVIRONMENT-INITIALIZATION.md`。初始化应先判断本次依赖哪些 AI 支持要求和规范落地要求，并逐项读取 `platform_method`、`platform_entities`、`refs_evidence`、`status`、`degradation`、`audit_evidence` 和 `open_items`。若关键要求为 supported 或 ready-for-audit，可以按清单范围自动应用安全的读取、检查、草案生成和降级判断；若关键要求为 partial，只能执行该要求已覆盖的承接方法并记录降级；若关键要求缺失、not-started、draft 或 deprecated，不得宣称完整安装与接入初始化完成。创建、修改、删除持久入口、平台规则、Hook、自动化或工作区级配置前必须触发 Human Gate。

未知环境适配向导至少应确认：

1. AI-S1 至 AI-S15 中哪些 AI 支持要求可以被该环境承接；
2. LR-1 至 LR-7 中哪些规范落地要求可以被该环境承接；
3. 每项可承接要求对应的平台方法、平台实体、refs 或实测证据；
4. 每项无法完整承接要求的会话级降级方式和残留风险；
5. 哪些要求缺少审计证据、Open Items 或 Human Gate 结论；
6. 是否允许创建工作区级薄入口、规则、Skill、Command、Hook、自动化或等价平台机制；
7. 应按 04.08 形成哪些待填要求响应矩阵行。

### 6.3 读取统一入口和管辖项目配置

AI 应读取：

1. LDVH-AI-ENTRY.md；
2. `LDVH-GOVERNED-PROJECTS.yaml`；
3. `docs/specs/03.06-管辖项目配置规范.md`。

若管辖项目配置不存在或目标项目未登记，应按 03.06 引导用户填写最小字段，或由 AI 先扫描用户指定目录、当前工作区相邻目录和当前仓库上下文，生成候选项目配置草案。AI 可以根据目录名生成候选 `id`、`path` 和可选 `name`，但不得臆测 `description`，不得静默决定哪些候选项目纳入管辖，也不得自动写入配置。修改配置前必须触发 Human Gate。配置文件只能登记 `product_name`、`product_description` 和项目的 `id`、`path`、可选 `name`、可选 `description`，不得新增初始化状态字段。

候选项目发现应遵守以下边界：

1. 可把 `.git`、`README`、`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`pom.xml`、`build.gradle`、`docs/`、`ldvh-base/` 或等价项目根信号作为候选线索；
2. 应排除 `node_modules/`、`.venv/`、`venv/`、`dist/`、`build/`、`.cache/` 和明显生成目录；
3. 自动发现结果只是候选清单，不是管辖项目事实；
4. 若找不到候选，应回退到最小手填模板；
5. Human 确认后才能写入或修改 `LDVH-GOVERNED-PROJECTS.yaml`。

### 6.4 检查目标项目路径

AI 应检查目标项目 `path` 是否：

1. 可定位；
2. 与用户意图匹配；
3. 不指向 LDVH 自身项目以外的意外目录；
4. 不会因写入影响用户其他项目；
5. 具备本次授权范围内的读取或写入权限。

路径不存在、路径含义不清、权限不足或可能写错项目时，应暂停并请求 Human 确认。

### 6.5 检查或建立文档工作区

目标管辖项目默认文档工作区为：

```text
{project.path}/docs
{project.path}/docs/evals
{project.path}/docs/refs
```

AI 应按 `docs/specs/03.02-管辖项目文档规范.md` 检查这些目录是否存在、是否与用户项目已有文档结构冲突、是否需要创建。

若目录缺失且 Human 授权写入，可以创建目录或生成待创建清单；若项目已有等价文档结构，应先说明差异并请求 Human 决定是否映射、迁移或保留降级。不得在管辖项目中创建 `docs/specs/` 或 `specs/` 作为 LDVH 规范区。

### 6.6 检查或建立工作对象事实源承载

目标管辖项目默认工作对象事实源根目录为：

```text
{project.path}/ldvh-base
```

AI 应先读取 `docs/specs/20-工作模型集合索引.md`，确认 active 工作模型，再读取对应工作模型规范中的事实源位置。当前 active 工作模型包括 ADR、Change、Pitfall、Intent、Memo 和 Task；其中 Change 由 Git commit 记录承载，不创建 `ldvh-base/changes/`。

AI 只应为 active 且具体工作模型规范明确要求文件目录的工作模型检查或创建事实源目录。removed、deferred-field、deferred-doc 和 reserved 项不得被初始化为默认事实源目录。若旧目录或旧事实实例已经存在但对应模型已 removed，应记录为审计输入或待清理缺口，不得在初始化中擅自删除。

### 6.7 检查工作流程入口

AI 应读取 `docs/specs/40-工作流程集合索引.md`，确认 active 工作流程，并保证入口文件或初始化结果能指向 active 工作流程。

安装与接入初始化应确认至少以下 active 流程可被定位：

1. `docs/specs/41-landing-orchestration-规范落地统筹.md`；
2. 本文；
3. `docs/specs/44-multi-role-thinking-多角色思考.md`。

planned、candidate 或 reserved 工作流程只能作为后续讨论输入，不得被初始化结果写成已生效流程。

### 6.8 检查 AI 入口和运行投影

AI 应检查：

1. LDVH 自身项目根目录 LDVH-AI-ENTRY.md 是否存在；
2. 当前平台是否有工作区级薄入口或会话级降级入口能把 AI 引向 LDVH；
3. 是否需要为工作区级入口添加单句薄引用；
4. 是否有人明确要求在管辖项目创建项目级入口。

工作区级入口属于用户工作区，不随 LDVH 项目提交；AI 只能在 Human 授权下提示或协助写入。管辖项目一般不创建项目级平台入口。确需例外时，必须触发 Human Gate，说明与用户项目原有入口的关系、影响范围和退出方式。

### 6.9 检查 Code 和 Web 基础

AI 应检查当前 LDVH Code 是否能支持本次初始化至少以下能力：

1. 校验 `LDVH-GOVERNED-PROJECTS.yaml`；
2. 检查 docs/specs 正式规范结构；
3. 检查已存在工作对象实例的基础字段和事实源位置；
4. 记录不能机械验证的初始化缺口。

若 Code 能力不足，应按 `docs/specs/07-Code实现规范.md` 记录 Code 缺口，不得声称初始化已被完整机械验证。

Web 不是安装与接入初始化的必需前提。若 Web 已存在，应只作为 Human-facing 展示、确认或受控轻写入入口；Web 页面状态不得替代初始化结果文档、工作对象事实源或 Code 校验结果。

### 6.10 分流缺口并调用 41

初始化过程中发现以下问题时，应进入 `docs/specs/41-landing-orchestration-规范落地统筹.md` 或按其分流规则记录缺口：

1. 正式规范缺口；
2. 运行投影缺口；
3. Code 校验缺口；
4. Web 展示或受控写入缺口；
5. Human Gate 缺口；
6. 工作模型或工作流程索引不一致；
7. 事实源边界不清；
8. 需要长期降级的初始化事项。

缺口不得停留在聊天中。能立即修复且已授权的，可以在本流程中修复；不能立即修复的，应写入初始化结果，并按性质分流为 Task、Memo、ADR、规范待补齐事项或后续审计输入。

### 6.11 写入初始化结果

产品初始化阶段完成或降级结束时，应写入或更新项目初始化结果文档，默认位置为：

```text
{project.path}/docs/ldvh-product-initialization.md
```

初始化结果至少包含：

1. 初始化日期；
2. 当前 AI 环境确认方式、已应用环境适配方案和运行投影状态；
3. `LDVH-ENVIRONMENT-INITIALIZATION.md` 状态和残留缺口；
4. LDVH 管理实例和目标项目 `id`、`path`；
5. 本次授权范围；
6. 已检查或创建的目录；
7. 已确认的 active 工作模型和工作流程；
8. AI 入口、工作区级入口或降级入口状态；
9. Code / Web / 运行投影状态；
10. 已执行验证命令或人工检查；
11. open / degraded / done 缺口清单；
12. Human Gate 结果；
13. 后续产品审计输入。

若本次只允许分析、不允许写入，应在对话中给出安装与接入初始化计划和缺口清单，但不得宣称安装与接入初始化完成。

## 7. Gate 触发条件

以下情况必须触发 Human Gate：

1. AI 无法明确判断当前环境且需要 Human 从已有平台适配清单、待填平台或未知环境适配路径中选择；
2. 新增、删除或修改 `LDVH-GOVERNED-PROJECTS.yaml` 项目条目；
3. 在目标项目中创建、删除、重命名 `docs/`、`ldvh-base/` 或其关键子目录；
4. 在用户工作区级入口、平台配置、项目规则或等价入口中写入内容；
5. 在管辖项目中例外创建项目级入口、平台规则文件或 AI 统一入口；
6. 初始化目标项目路径不清、可能误写其他项目或权限边界不明；
7. 为 removed、deferred-field、deferred-doc 或 reserved 工作模型创建目录或实例；
8. 接受长期降级或关闭关键初始化缺口；
9. 将初始化结果写入非默认位置；
10. 修改 Code、Web、运行投影或事实源边界以支持初始化；
11. 宣称安装与接入初始化完成但缺少必要环境确认、配置、目录、入口、验证或回写证据。

Gate 触发时，AI 应说明触发原因、影响范围、建议动作、可选降级方式和需要 Human 确认的具体问题。

## 8. Skill 和 Agent 调度

安装与接入初始化默认由主控 AI 执行，不要求创建专用 Skill。

当初始化步骤稳定、可复用且不会替代主控判断时，可以评估是否创建 LDVH 自建 Skill。Skill 只能承接读取清单、目录检查、结果模板生成、缺口聚合等稳定子步骤，不得决定目标项目、绕过 Human Gate、写入平台入口或宣称初始化完成。

以下情况可以按 `docs/specs/44-multi-role-thinking-多角色思考.md` 调用独立、专项或并行 Agent：

1. 目标项目路径、入口写入或事实源边界存在争议；
2. 是否创建项目级入口、目录结构或运行投影存在风险；
3. 工作模型、工作流程、Code、Web 和运行投影缺口需要多视角判断；
4. 初始化缺口是否可以长期降级不清；
5. 需要审查初始化方案是否会影响用户原有项目。

Agent 输出必须回到主控汇总。稳定结论只有写入初始化结果、工作对象、规范或其他 Git 文件事实源后才生效。

## 9. 工具协作适配

安装与接入初始化可以使用 Code、命令、Web、搜索和文件检查协作，但必须遵守以下边界：

1. Code 可以校验 `LDVH-GOVERNED-PROJECTS.yaml`、docs/specs 结构、工作对象字段、路径存在性和引用关系；
2. Code 可以生成初始化检查报告或缺口清单，但输出不是最终事实源；
3. Code 不得自行新增管辖项目条目、创建工作对象实例、关闭缺口或修改平台入口；
4. Web 可以展示初始化状态、缺口、Gate 和待确认事项，但 Web 状态不替代 Git 文件事实源；
5. 搜索和文件读取用于定位现有项目文档、目录和事实实例，不得把搜索结果直接写成稳定事实；
6. 工具无法覆盖的判断，应记录人工降级检查和残留风险。

若初始化发现缺少必要工具，应按 `docs/specs/07-Code实现规范.md` 判断是否形成 Code 需求；Code 自身规范或测试缺失时，应先建立最小可验证能力，再声明机械验证完成。

## 10. 事实源回写与证据留存

安装与接入初始化应按以下规则回写事实和证据：

| 输出 | 回写位置 |
|---|---|
| 管辖项目清单变化 | `LDVH-GOVERNED-PROJECTS.yaml` |
| 初始化结果 | {project.path}/docs/ldvh-product-initialization.md 或 Human 确认的等价项目正文文档 |
| 初始化缺口 | 初始化结果文档；必要时分流为 Task、Memo、ADR 或规范待补齐事项 |
| 目录创建或事实源写入 | Git 文件事实源和后续 Change commit |
| Code 校验结果 | 初始化结果文档中的摘要和可追溯命令；完整输出按需进入结果物 |
| Human Gate 结果 | 初始化结果文档、相关工作对象或 commit 记录 |
| 长期决策 | ADR |
| 可执行后续工作 | Task |
| 暂存发现或提醒 | Memo |

初始化证据至少应保留：

1. 读取的关键规范和配置；
2. 目标项目 `id`、`path` 和 Human 授权范围；
3. 已检查路径、目录和入口；
4. 已执行命令或人工检查；
5. 写入文件清单；
6. 缺口状态和降级方式；
7. Gate 结果和后续审计输入。

聊天记录、临时命令输出、Agent 输出和 Web 页面状态不得单独作为初始化完成证据。

安装与接入初始化的机制适配边界如下：

## 14. 检查要求

检查一次安装与接入初始化是否符合本流程时，应确认：

| 检查项 | 标准 |
|---|---|
| 目标明确 | 已明确 LDVH 管理实例、目标项目 `id` 和 `path` |
| 授权清晰 | 已说明只分析、可写配置、可写项目目录或可写入口的范围 |
| 配置有效 | `LDVH-GOVERNED-PROJECTS.yaml` 符合 03.06，未承载初始化状态 |
