# 机制落地关系与运行投影同步机制评估

> 创建日期：2026-06-07
> 定位：LD Vibe Harness 关于机制落地关系、环境初始化和规范变更后运行投影同步的项目内部评估
> 调研边界：不直接构成强制规则
> 执行效力：无，结论需进入 00-79 正式规范区间或 ADR 后才成为稳定规则
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs/03-文档规范.md`、`specs/05-Trae-Solo环境规范.md`、`specs/07-工作模型基础规范.md`、`specs/08-工作流程基础规范.md`、`specs/10-工作流测试.md`、`specs/14-Code实现与工具规范.md`

## 1. 本文解决的问题

本文记录一次关于 LDVH 安装、初始化和后续规范变更同步机制的设计讨论，用于评估是否应将 `specs/03-文档规范.md` 中的机制落地关系升级为更明确的运行投影同步契约。

讨论的起点是：用户在不同 AI 开发环境中安装 LDVH 后，AI 应能根据当前工作环境自动生成或检查相应运行配置，例如 Rules、AGENTS、Skill、hooks、MCP、权限策略、校验工具入口和 Human Gate 提示。进一步的问题是：规范后续发生变化时，AI 也应知道哪些环境配置需要同步更新，而不是只在首次初始化时使用。

本文不修改正式规范，不定义新的工作流程，不要求其他文档立即增加章节。本文仅沉淀设计判断，供后续决定是否修改 03、07、08、14，是否新增初始化工作流程，或是否创建工具和 Task。

---

## 2. 结论

建议将机制落地关系理解为：

```text
specs 正式规范 = 权威源
运行环境设置 / Rules / AGENTS / Skill / hooks / MCP config / Tools / Web = 运行投影
机制落地关系 = 从权威源到运行投影的同步契约
```

初始化只是第一次运行投影同步。规范变更、规则漂移审计、Skill 更新、工具契约变化和环境迁移，都应走同一套机制落地关系。

更合适的正式落地路径不是让初始化工作流程反过来规定其他规范如何写，而是：

1. 由 `specs/03-文档规范.md` 定义机制落地关系的同步语义、字段、消费规则和文档治理要求；
2. 由 `specs/07-工作模型基础规范.md` 继续定义 20-39 工作模型主规范中的机制适配边界；
3. 由 `specs/08-工作流程基础规范.md` 继续定义 40-59 工作流程主规范中的机制适配边界；
4. 后续如新增初始化工作流程，该流程只消费 03、07、08 已授权的声明位置，不新增对其他文档的骨架要求；
5. 后续如新增工具，应让工具扫描机制落地关系和机制适配边界，检查运行投影是否缺失、过期或漂移。

## 3. 核心概念

### 3.1 权威源

权威源是 specs 正式规范、工作模型主规范、工作流程主规范、结构化契约章节和 Git 文件事实源。权威源定义稳定规则、对象边界、字段契约、状态机、Context、Scenario、Gate、Human Gate、校验要求和事实源边界。

权威源不应被运行环境设置反向替代。AGENTS、Rules、Skill、hooks、MCP config、Web 页面和工具输出都不应成为规范本身。

### 3.2 运行投影

运行投影是为了让 AI 在具体开发环境中实际遵守权威源而生成或维护的机制实体。运行投影包括但不限于：

1. 项目规则入口；
2. 目录规则入口；
3. 可复用 Skill；
4. 命令权限策略；
5. 生命周期 hooks；
6. MCP server 配置；
7. 工具校验入口；
8. Web 信息同步入口；
9. Human Gate 提示或审批策略；
10. 自动化或定时审计入口。

运行投影的价值是让规范可执行、可提示、可检查和可同步。运行投影不是新的事实源。

### 3.3 机制落地关系

机制落地关系应从普通“有关联”的说明，升级为“何处消费、何时同步、如何验证”的同步契约。

一个有效的机制落地关系至少应回答：

1. 哪段规范被哪个机制实体消费；
2. 该消费属于入口摘要、流程编排、校验实现、展示视图、命令权限还是审批提示；
3. 哪些规范变化会触发同步；
4. 当前环境中应落到哪个具体文件或设置；
5. 同步后如何验证没有漂移；
6. 无法同步时是否应创建 Task、Memo、ADR 或阻塞说明。

## 4. 与 03、07、08 的分工

### 4.1 03 负责文档声明规则

`specs/03-文档规范.md` 更适合定义机制落地关系的通用语义，因为它已经负责文档骨架、引用纪律、机制落地关系和文档治理检查。

建议后续在 03 中明确：

1. 机制落地关系是产品初始化、规范变更同步、审计和漂移诊断的输入；
2. 普通 specs 文档可通过机制落地关系声明自身稳定规则被哪些机制实体消费；
3. 机制落地关系应包含来源章节、同步触发条件和验证方式；
4. 初始化流程不得从聊天记录、evals 或工具输出中直接推断长期机制要求；
5. 初始化流程不得要求其他规范临时增加非 03、07、08 定义的章节。

### 4.2 07 负责工作模型机制适配边界

20-39 工作模型主规范不使用普通机制落地关系，而应依据 07 在主规范中声明机制适配边界。

这意味着 Task、ADR、Intent、Memo、Pitfall、Profile 等对象的字段契约、状态机、关闭条件、Human Gate 和工具消费关系，仍应由各对象主规范承载。初始化或同步流程只读取这些主规范中已经按 07 授权的机制适配边界，不发明新的对象规则。

### 4.3 08 负责工作流程机制适配边界

40-59 工作流程主规范不应要求其他文档增加初始化声明。工作流程只能定义自身行动如何读取、判断、执行、暂停、回写、验证和调用机制。

如果后续新增 LDVH 初始化工作流程，它应只定义：

```text
识别环境
→ 读取 03/07/08 授权的机制声明
→ 生成运行投影计划
→ Human Gate
→ 写入或更新运行投影
→ 验证并记录证据
```

它不应定义其他规范必须增加什么章节。

## 5. 建议的机制落地关系字段

当前 03 中机制落地关系表的最小字段是“关联机制、关联实体、关系类型、触发条件”。后续可评估扩展为：

| 字段 | 含义 |
|---|---|
| 关联机制 | Rules、Skill、Agent、Tools、Web、Contract、MCP、Hooks、Automation 等 |
| 抽象落地能力 | project_rules、directory_rules、skill、validator、command_policy、hook、mcp_server、web_view、human_gate_prompt、automation 等 |
| 关联实体 | 当前项目中的具体文件、目录、工具、Skill、配置或待生成实体 |
| 关系类型 | 入口摘要、流程编排、校验实现、受控写入、展示视图、审批提示、命令权限等 |
| 来源章节 | 被消费的规范章节，例如某规范中的具体章节编号 |
| 同步触发条件 | 初始化、来源章节变化、字段契约变化、状态机变化、Human Gate 变化、审计或规则漂移诊断 |
| 验证方式 | 文件包含来源引用、Skill 不复制正文、pytest、fact_validate、specs_validate、手工审计等 |
| 降级处理 | 当前环境不支持该抽象能力时如何退化或记录阻塞 |

示例：

```markdown
| 关联机制 | 抽象落地能力 | 关联实体 | 关系类型 | 来源章节 | 同步触发条件 | 验证方式 |
|---|---|---|---|---|---|---|
| Rules | project_rules | 项目规则入口 | Task 关闭入口摘要 | §关闭条件 | 初始化、关闭条件变化、审计 | 检查项目规则包含来源引用且不复制完整正文 |
| Skill | skill | ldvh-close | Task 关闭流程编排 | §关闭条件、§Human Gate | 初始化、关闭流程变化 | Skill 引用来源章节且 STOP 点覆盖 Human Gate |
| Tools | validator | tools/fact_validate.py | 事实实例校验 | §字段契约、§状态机 | 字段或状态机变化 | pytest + fact_validate 目标样例 |
```

## 6. 抽象落地能力与环境映射

机制落地关系不宜直接写死所有 AI 开发环境的文件路径，否则 Codex、Trae、Claude Code、Cursor 或未来环境会让规范快速膨胀。

更合适的方式是先声明抽象落地能力，再由环境适配层映射到具体实现。

| 抽象落地能力 | 含义 |
|---|---|
| project_rules | 项目级持续指令或项目规则入口 |
| directory_rules | 目录级或文件范围规则入口 |
| skill | 可复用工作流入口 |
| validator | 确定性校验工具入口 |
| command_policy | 命令权限、沙箱外执行或高风险命令策略 |
| hook | 生命周期自动检查或提醒 |
| mcp_server | 外部工具和上下文协议服务配置 |
| web_view | Web 展示、同步或 Human Gate 辅助界面 |
| human_gate_prompt | 人工确认、审批或暂停提示 |
| automation | 定时审计、周期检查或自动化任务 |

不同环境中的映射示例：

| 抽象能力 | Codex 可能实现 | Trae 可能实现 |
|---|---|---|
| project_rules | 根 `AGENTS.md` | `.trae/rules/ldvh-project-rules.md` |
| directory_rules | 子目录 `AGENTS.md` | 项目规则摘要或平台 Rules 能力 |
| skill | `.agents/skills/{name}/SKILL.md` | `.trae/skills/{name}/SKILL.md` |
| validator | `tools/` 命令、hooks、Skill 调用 | `tools/` 命令、Skill 调用 |
| command_policy | `.codex/rules/*.rules`、approval policy | 平台自动运行与安全设置 |
| hook | `.codex/hooks.json` 或 config hooks | 平台支持的自动检查入口或降级为 Skill 检查 |
| human_gate_prompt | approval/on-request、对话暂停确认 | AskUserQuestion |

环境适配表属于初始化/同步流程或环境规范的输入，不应复制到每个对象规范中。

## 7. 初始化同步流程

初始化同步是运行投影同步的首次执行。

建议流程：

1. 识别当前 AI 开发环境和项目根目录；
2. 识别环境支持的抽象落地能力；
3. 读取 03 的机制落地关系规则；
4. 读取 07 和 20，确认 active 工作模型及其机制适配边界；
5. 读取 08，确认工作流程区段、初始化类行动和机制适配边界；
6. 扫描普通 specs 文档的机制落地关系；
7. 生成当前环境的运行投影计划；
8. 展示将创建或修改的配置文件、Skill、hooks、Rules、工具入口和降级项；
9. 触发 Human Gate，由用户确认初始化范围；
10. 写入运行投影；
11. 运行验证；
12. 将初始化结果、验证证据和未同步项记录到 Task、Memo 或初始化报告中。

初始化同步的输出不应只是一批文件，还应包含可审计说明：

1. 当前识别到的环境；
2. 支持和不支持的抽象能力；
3. 已生成或更新的运行投影；
4. 降级处理项；
5. 验证结果；
6. 后续需要人工确认或补齐的事项。

## 8. 规范变更同步流程

规范变更同步是初始化之后的增量投影同步。

建议流程：

```text
发现 specs 变更
→ 定位变更文件和章节
→ 匹配机制落地关系中的来源章节
→ 判断同步触发条件是否命中
→ 列出受影响运行投影
→ 更新或提示更新运行投影
→ 执行验证方式
→ 记录同步证据或阻塞原因
```

示例：

如果修改 `specs/27-Task-任务.md` 的关闭条件，则应检查：

1. 项目规则或 AGENTS 中的 Task 关闭入口摘要是否需要同步；
2. `ldvh-close` Skill 的 STOP 点和关闭流程是否需要同步；
3. `tools/fact_validate.py` 是否需要增加或修改 acceptance、closure_evidence、blocked_by 校验；
4. `tests/tools/` 是否需要新增或调整测试；
5. Web Task 详情页或关闭操作入口是否消费了该关闭条件；
6. 同步后是否运行 fact_validate、pytest 或 Web 检查。

如果无法同步，应明确记录原因：

1. 当前环境不支持对应抽象能力；
2. 目标运行投影不存在；
3. 规范变化需要先补工具能力；
4. 变更触发 Human Gate 但尚未确认；
5. 需要创建后续 Task 或 ADR。

## 9. 漂移审计

运行投影可能出现漂移：

1. specs 已变更，但 AGENTS、Rules、Skill、hooks 或工具未同步；
2. 运行投影复制了旧正文，与权威规范冲突；
3. 工具校验逻辑与字段契约或状态机不一致；
4. Web 展示或受控写入逻辑与事实源边界不一致；
5. 不同环境的投影文件表达不一致；
6. 运行投影中残留历史场景规则、旧路径或旧对象状态。

后续可考虑提供漂移审计工具。工具输入应来自 Git 文件事实源，包括：

1. specs 机制落地关系；
2. 工作模型和工作流程机制适配边界；
3. 环境适配表；
4. 实际运行投影文件；
5. 工具和测试结果。

工具输出应包含：

1. 缺失投影；
2. 过期投影；
3. 未验证投影；
4. 无法映射的抽象能力；
5. 需要 Human Gate 的高影响同步；
6. 建议的修正路径。

工具输出不是稳定事实。需要保留的漂移结论应回写 Task、Memo、Pitfall 或审计报告。

## 10. 与既有评估的关系

本文与 `specs/evals/11-LDVH规范即机制-Rules与Skill自动生成评估.md` 方向一致，但范围更宽。

evals/11 主要关注 Rules 与 Skill 从 specs 自动生成；本文将问题扩展为运行投影同步，覆盖初始化、规范变更、Tools、Web、hooks、MCP、权限策略和环境差异。

两者可以形成递进关系：

1. evals/11 关注“规范即机制”的生成可行性；
2. 本文关注“规范到运行投影”的同步契约；
3. 后续正式规范可以先吸收本文中较小的 03 机制落地关系字段增强，再评估是否做自动生成工具。

## 11. 可能落地路径

建议按低风险顺序推进：

| 阶段 | 目标 | 输出 |
|---|---|---|
| 阶段一 | 在 03 中增强机制落地关系语义 | 明确机制落地关系用于初始化、规范变更同步、审计和漂移诊断 |
| 阶段二 | 在 03 中补充字段建议 | 增加来源章节、同步触发条件、验证方式、降级处理等字段 |
| 阶段三 | 在 07、08 中确认工作模型和工作流程的机制适配边界消费方式 | 明确初始化流程只能读取既有机制适配边界，不新增骨架要求 |
| 阶段四 | 新增初始化/同步工作流程 | 只定义如何消费 03/07/08 声明、生成投影计划、Human Gate、验证和回写 |
| 阶段五 | 新增漂移审计工具 | 读取 specs 与运行投影，输出缺失、过期和未验证项 |
| 阶段六 | 评估自动生成 | 在投影声明足够结构化后，再决定是否生成 AGENTS、Rules、Skill、hooks 或环境配置 |

## 12. 开放问题

1. 机制落地关系字段是否应先只增加“来源章节、同步触发条件、验证方式”，还是一次性引入“抽象落地能力”和“降级处理”？
2. 抽象落地能力清单应由 03 维护，还是由后续初始化工作流程或环境规范维护？
3. Codex、Trae、Claude Code 等环境映射表应作为 refs、正式规范、Profile 字段，还是工具内置配置？
4. 20-39 和 40-59 的机制适配边界是否需要统一表格格式，以便工具扫描？
5. 运行投影同步失败时，应默认创建 Task，还是只在用户确认后创建？
6. 投影文件是否允许自动覆盖，还是必须先生成 diff 并 Human Gate？
7. 是否需要为每个运行投影记录来源规范 commit hash，以支持漂移审计？
8. 运行投影中的摘要应允许多长，如何防止摘要变成第二份规范正文？
9. 如果某环境没有对应机制能力，降级投影应写到哪里才不制造第二事实源？
10. 初始化完成证据应作为 Task closure_evidence、Memo、Change 说明，还是单独初始化报告？
