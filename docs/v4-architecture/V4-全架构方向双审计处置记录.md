# V4 全架构方向双审计处置记录

> 处置日期：2026-07-14。输入为仓库根目录的 `V4-Audit-Report-GLM5.2-2026-07-14-1524.md` 与 `V4-Audit-Report-GPT-5.6-SOL-极高-2026-07-14-1533.md`。本文只记录审计事实核对、意见处置和后续顺序，不是规则源，不授权新字段、新操作、事实写入或 Human Gate 结论。两份原始审计保持不改。

## 1. 总结论

两份审计提供了有价值的实际消费视角，但严重度和部分事实判断不能原样接受。处置后没有保留 P0；当前最高为 P1，且集中在三个产品事实：

1. V4 还没有用自己的能力完成一次“实时管辖解析 → 真实事实创建/读取 → 中断恢复 → 受控更新”纵向闭环；
2. Helper 的渐进式披露和共同响应契约虽按当前规则正确实现，但在真实调用中产生了明显的固定输出成本；
3. 工作推进总纲同时记录了“外部配置已失效”和曾经成立的“已成功解析”，容易使后续 AI 将瞬时外部状态误当当前事实。

WorkCase 不是两份审计全部意见的主体。GPT 报告将 WorkCase 视为普通跨会话任务的默认编排器，这与当前类型边界不符：WorkCase 只用于高风险、长周期、确需 Human 审批或必须稳定记录为项目责任的工作。Human 先确认工作意图，AI 才准备并审核执行计划；Human 再判断该计划是否值得执行，并可取消工作。这是对“是否做”和“怎么做”的两次不同判断，不是 AI 可自行扩张的强制流程。该语义已由提交 `a8d83570` 在 21 中澄清。

## 5. 合并后的执行顺序

本次审计不导向立即精简 WorkCase，也不导向立即开建首个正式行动模板。合并后的顺序是：

1. 已修复当前外部管辖配置，并将总纲中的环境状态改为带时点、可过期的观察；
2. 已修正 `docs/code/README.md` 中对单操作 `capabilities` 的误导示例；
3. Human 后续校正：内部建设阶段直接通过 Specs、Code 和 tests 解决问题，不为了验证流程创建 Pitfall、Spark 或其它事实对象；
4. 已按该边界完成单对象 update/CAS/status 契约、实现、转换验证和关系校验修正；
5. 当实践中自然出现满足类型准入的事实时，再经 Human 对具体对象确认后使用创建、读取、更新和跨会话恢复链路；
6. 当实际出现符合颗粒度的高风险、长周期、确需 Human 审批或项目记录工作时，再完成首个 WorkCase dogfood；
7. 只在真实行动出现稳定重复后，再定义首个正式行动模板。

Helper 包络、L3 精准读取、F1 规模、错误恢复和字段准入成本作为纵切面过程中的实测项，不在没有消费证据时并行扩展契约。

## 6. Gate 与不改变的边界

- 一般事实对象创建前的 Human 确认，不等于 WorkCase 执行计划的 Human 确认；
- 本记录不代替对具体事实对象内容的创建确认；
- 本记录不代替对具体 WorkCase 执行计划的 Human 批准；
- 单对象受控更新已成立仍只证明一个文件的 CAS、转换检查和回读，不证明真实跨会话接续、Human 决定或项目事实已经发生；
- 在真实 V4 对象被 Web 正确只读展示且 V3 写入被隔离前，不宣称 Web 已取得 V4 事实交互身份；
- 测试通过只证明当次实现边界，真实 AI 场景消费证据才用于判断 V1–V8 净价值。
