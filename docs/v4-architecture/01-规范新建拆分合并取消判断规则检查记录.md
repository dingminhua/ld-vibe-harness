# 01 新建、拆分、合并与取消规范判断规则检查记录

> 记录性质：本文为拟新增到 `specification-model-foundation` 的判断规则准备，并按拟议检查字段组织。其成立依据仍是 00、修改前 01 和独立复核；本文不是规则源，不替代 `specs/01-规范模型基础规范.md` 正文。

## 1. 准备解决的问题

修改前 01 已要求每份规范承担一项明确且稳定的规范责任，禁止两份当前规范重复承担同一责任，但没有给出可重复执行的判断顺序和成立条件。

缺失的规则对象是：准备新建、拆分、合并或取消的 LDVH 规范文档，以及这些文档准备承担的规则责任。

预期作用是：在候选标题、编号和 `spec_key` 形成前，先使用同一顺序判断是否真有独有稳定规则、是否已由现有位置承接，以及独立文档是否对 AI 具有净价值。

## 2. 准备唯一定义的规则

1. 判断必须从 00、不使用候选名称的规则对象描述和具体候选规则清单开始；
2. 必须移除现有来源已承担的规则、实现与测试细节、一次性步骤、没有跨消费方稳定契约价值的内部状态和未经证明的未来设想；
3. 独立普通规范必须同时满足明确对象、独有稳定规则、唯一定义位置、可分开判断的适用或变化原因、自然完整的规范内容、独立失败与验证边界和文档净价值；
4. 必须比较现有规范章节、授权附件、独立规范、事实模型、行动模板、Code 与 tests、实现说明、`docs/` 与归档等位置；
5. 拆分后的每一份规范都必须独立满足准入条件；重复、从属、摘要或无剩余规则的候选必须合并或取消；
6. 新建或实质改变责任前必须形成检查记录并完成独立复核；
7. 仅就责任是否应独立存在的未决问题，只有按固定顺序仍无法收敛或涉及重大价值取舍时，才由本次规则新增 Human Gate；已由 00、01 或其它来源规则触发的 Gate 仍然适用。

## 3. 与现有规则的对照

| 现有位置 | 已有内容 | 本次剩余需求 |
|---|---|---|
| 00 | 五类构成要素、V1–V8、Human Gate、Stop Conditions 和上位边界 | 不定义规范文档的准入、拆分、合并和取消规则 |
| 01 对规范文档的定义 | 每份规范承担一项明确且稳定责任 | 没有说明什么条件下算明确、稳定且值得独立 |
| 01 的当前规则源条件 | 禁止两份当前规范重复承担同一责任 | 没有定义如何发现重复，也没有要求在候选阶段比较其它承载位置 |
| 01 的模板 | 要求说明为什么需要独立存在 | 没有成立条件、反例、净价值或独立复核要求 |
| 01 的 Human Gate | 无法区分两份当前规范是否重复时交由 Human | 对责任判断没有先要求执行者完成候选规则对照、承载位置比较、净价值判断和独立复核 |

移除已有规则的重复转述后，仍剩下一组未被定义的稳定判断规则，需要进入当前规则源。

### 3.1 逐条映射

| 拟新增规则 | 修改前已有承接 | 真正新增的部分 |
|---|---|---|
| 从 00、无候选名称的对象描述和具体规则清单开始 | 00 已有上位判断顺序；01 模板要求说明价值和责任 | 禁止用候选名称、编号和 key 反证必要性，并要求先列具体规则 |
| 移除重复、实现细节、一次性步骤和无稳定契约的内部状态 | 01 已禁止重复当前责任，并排除 Code、tests 和低频迁移步骤 | 在候选阶段按单条规则移除错误承载内容，而不等到两份 active 规范冲突 |
| 独立普通规范的全部成立条件 | 01 只有“明确且稳定的责任”和“为什么需要独立存在” | 明确对象、独有规则、唯一定义位置、可分开判断的变化原因、非填充式完整、独立失败与验证和文档净价值 |
| 比较其它承载位置 | 01 已分开规范、附件、Code、tests 和历史材料 | 在新建规范前必须系统比较现有章节、附件、事实模型、行动模板、实现和工作记录 |
| 拆分、合并和取消条件 | 01 已规定不得丢失仍适用规则，不得重复保留当前责任，并定义替代关系 | 要求拆分后每组分别成立，对同对象和强同步规则保持同篇，对无剩余规则候选直接取消 |
| 检查记录和独立复核 | 01 已为术语检查定义类似机制，但不适用于整份规范责任 | 对规范数量和责任边界单独要求记录、更小方案检查和独立复核 |
| 责任判断的 Human Gate 边界 | 01 已在无法区分两份当前责任时进入 Human Gate | 只限定本节对“责任是否独立”新增的 Gate；不覆盖 00、01 或其它来源规则已有的 Gate |

## 4. 承载位置比较

| 位置 | 结论 | 理由 |
|---|---|---|
| 01 正文 | 推荐 | 该规则直接约束规范文档的身份、数量、责任边界和生命周期，与 01 现有规则对象一致 |
| 新的独立规范 | 不推荐 | 会为“是否应新建规范”再建一份规范，增加启动、定位、关系和同步成本；新文档的规则对象仍是 01 已有的规范文档 |
| 授权附件 | 不推荐 | 候选内容是叙事性核心规则，不是已定义的字段表、枚举或矩阵 |
| `docs/` | 仅作检查记录 | 可以保留判断过程，但不能让规则对 AI 和 Code 生效 |
| 事实模型、行动模板、Code、tests 或 Web | 不适用 | 它们均不承担规范模型的核心规则定义 |

## 5. 相邻责任、正反例和独立失败

相邻责任是双语术语治理、规范身份、规范关系和附件授权。它们分别检查名称、文件身份、关系和附件；本次规则检查整份规范是否有必要作为独立规则来源存在。

本次责任可以在不改变相邻责任的情况下独立变化：新的重复规范、无剩余规则的候选文档或跨文档拼接负担可以要求调整判断条件，却不改变术语含义、YAML 身份字段、规范关系类型或附件授权边界。反过来，术语改名、YAML 字段校准或附件字段表调整，也不必然改变本次判断规则。

正例：

1. 候选规范删除现有来源已承担的内容后，仍有独有、稳定、可独立验证的规则；
2. 两组规则有不同的对象、适用边界和变化原因，拆分后能减少无关读取；
3. 两份当前规范实际定义同一责任，按本次规则合并为唯一来源。

反例：

1. 为“验证”、“声明”或“内部能力状态”建立横跨所有来源的总规范，但删除各来源规范、Code/tests、Helper、Web 和环境已承担的内容后没有剩余规则；
2. 为已由工作对象、管辖范围、规则来源和 Helper 承接的判断再建一份抽象中间规范；
3. 为了保留 V3 的名称、顺序或实现模块，在没有独有稳定规则时仍建立文件。

独立失败场景是：没有这些判断规则时，同一候选责任会因执行者当次偏好被反复建立、改名、合并或取消，即使术语和模板都符合 01，Specs 数量和责任边界仍无法收敛。

## 6. V1–V8 净价值

1. V1：减少空壳和重复规范，使 AI 更快定位唯一规则来源；
2. V2：要求先理解候选规则、现有来源和其它承载位置；
3. V3：使规范责任和相邻承载位置有可执行边界；
4. V6：不再依赖当次执行者的隐含判断标准；
5. V8：将本次反复暴露的问题收敛为可复用规则。

新增成本是 01 正文增长、候选检查记录和独立复核。该成本低于继续反复改变 Specs 数量、名称、依据和建设顺序所带来的架构偏移、Human 审核负担和后续 Code 返工。

## 7. 建议与影响范围

建议将这组规则作为 `specification-model-foundation` 的正文章节，不建立新的普通规范、授权附件或正式术语。

直接影响：

1. 01 的 `positioning`、职责边界、当前规则源成立条件、验证要求、Human Gate 和 Stop Conditions；
2. 所有后续候选 Specs 的新建、拆分、合并和取消判断；
3. 现有 Specs 责任受到实质质疑时的重新审核。

本次不修改 00、02、03、双语术语表、Code、tests、Web 或归档资产。等独立复核收敛后，再判断 01 修改是否可保留并向 Human 报告。
