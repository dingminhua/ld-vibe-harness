## 1. 本文解决的问题

本文解决 LDVH 中术语应如何命名、解释、引用和变更的问题。

术语规范的目标不是复制各专项规范的规则正文，而是让 AI 和 Human 在阅读、编写和执行 LDVH 文档时，能够稳定区分项目、工作区、规范、索引文档、规范落地、环境适配、运行投影、构成要素、环境能力、初始化、审计和检查等概念。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 的产品定位、五类构成要素、事实源原则、运行闭环标准和 Human Gate 原则，是本文的上位概念来源。本文承接 00，将后续正式规范、工作模型、工作流程、Code、Web 和环境适配需要复用的概念整理为统一术语边界。

本文不得反向改写 00 的产品定位和上位概念。若术语治理发现需要调整 00 中的上位概念，应单独触发 Human Gate，而不是在本文或其他规范中隐式覆盖。

除 00 的上位概念表达外，本文是 LDVH 术语定义和术语变更治理的权威位置。01、03、04、05、06、07、08、09、10、11、12 以及后续工作模型和工作流程规范可以说明术语在本规范中的应用规则，但不得并行维护同一术语的权威定义。

## 4. 项目、工作区与文档分区术语

| 术语 | 定义 | 边界 |
|---|---|---|
| LDVH 自身项目 | 承载和维护 LDVH 规范体系、Code、Web 和 dogfood 事实实例的项目 | 当前项目使用 `docs/specs/` 作为正式规范事实源 |
| 管辖项目 | 安装并使用 LDVH 进行需求、任务、证据、变更、审计或交付治理的用户项目 | 管辖项目不默认创建 `docs/specs/` 或 `specs/`，使用 `docs/` 承载项目文档 |
| 管辖项目配置 | LDVH 自身项目根目录 `LDVH-GOVERNED-PROJECTS.yaml`，用于说明当前 LDVH 管理实例并登记管辖项目最小清单 | 根字段只包含 `product_name`、`product_description`、`projects`；每个项目只强制 `id` 和 `path`，可选 `name` 和 `description`；不承载项目状态、项目类型、环境适配、运行投影或工作对象关系 |
| LDVH 文档工作区 | 承载 LDVH 规范正文、内部评估和外部引用的文档工作区 | 在 LDVH 自身项目中为 `docs/`，其下并列设置 `docs/specs/`、`docs/evals/` 和 `docs/refs/` |
| 规范正文区 | 承载 LDVH 正式规范正文的文档分区 | 在 LDVH 自身项目中为 `docs/specs/`；管辖项目不默认创建 |
| 管辖项目文档工作区 | 承载管辖项目正文、内部分析和外部引用的文档工作区 | 在管辖项目中为 `docs/` |
| 正文区 | 文档工作区中承载稳定正文的根层级 | `evals/` 和 `refs/` 不属于正文区 |
| evals | 内部评估、方案分析或内部调研区 | 不直接构成正式规范，结论需要吸收到正文区或工作对象后生效 |
| refs | 外部引用、第三方资料、官方文档摘录或引用副本区 | 不直接构成正式规范，不反向维护正文区规则 |
| 吸收 | 将 evals、refs 或临时分析中的结论转入正文区、工作对象、ADR、Task、Memo 或其他权威位置的治理动作 | 只引用 evals、refs 或临时材料路径，不构成吸收 |

## 5. 规范体系术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 正式规范 | `docs/specs/` 正文区中定义稳定规则、对象边界、流程要求、Code 要求、Web 要求、环境适配要求或检查要求的规范文档 | 正式规范应遵守 03 的文档骨架，并按 04.01 判断规范落地要求 |
| 候选事项 | 尚未创建、尚未生效或需要后续讨论、吸收、废止、保留的事项 | 候选事项不得被当作已经生效的规则执行 |

## 6. 索引文档术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 索引文档 | 用于定位编号区段、文档集合、状态清单或输入清单的文档 | 不替代对应基础规范或具体规范 |
| 说明性索引 | 只帮助查找文档、章节或资料，不定义稳定治理规则的索引文档 | 不默认属于正式规范 |
| 规范型集合索引 | 维护正式编号区段或规范集合的清单、状态、编号占用、关系、初始化输入、审计输入或 Human Gate 规则的索引文档 | 属于正式规范，规则由 `docs/specs/03.03-索引文档规范.md` 规定 |

## 7. 规范落地与环境适配术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 规范落地要求 | 一条稳定规范要落地需要满足的要求 | 不等于 Rules、Skill、Agent、Hook、CI、命令、工具文件或 Web 页面 |
| 保障机制 | 保障某项规范落地要求被执行、检查、复用、触发或确认的规则、流程、Code、Human Gate、子 Agent 思考、生命周期触发或审计动作 | 必须与规范落地要求绑定；无法保障时应记录降级方式 |
| 环境适配映射 | 某项规范落地要求和保障机制在特定开发环境中如何实现、验证和降级的映射关系 | 不得反向改写正式规范；LDVH 自身项目维护该映射，管辖项目不默认维护独立环境适配记录 |
| 运行投影 | 环境适配映射后实际存在、维护或调用的入口、文件、命令、配置、工具、页面、Skill、Agent、Hook、CI 检查、摘要或降级记录 | 不是最终事实源 |
| 运行投影状态 | 某个运行投影实体在当前环境中的存在、可用或维护状态，例如已存在、计划创建、缺失、部分可用、已废止或不适用 | 不是运行投影本体，只用于登记、检查和漂移判断 |
| 环境 | AI 和 Human 实际执行工作的工具、平台或运行面 | 可以包括 Codex、Trae、Claude Code、Cursor、CI、Web 工作台、命令行等 |
| 环境实体 | 具体环境中可被定位、配置、调用或维护的文件、规则、Skill、Agent、Hook、命令、页面、CI 配置或平台入口 | 只能作为环境适配映射或运行投影的一部分 |
| 环境能力 | 具体环境中可被 LDVH 用来承接规范落地要求的入口、机制、工具或运行面 | 能力边界由 `docs/specs/04.04-环境能力承接边界规范.md` 规定 |
| 承接边界 | 某类环境能力适合承接什么、不适合承接什么，以及何时需要组合其他能力或降级处理的边界 | 具体规则由 `docs/specs/04.04-环境能力承接边界规范.md` 规定 |
| 工作区级入口 | 用户当前开发环境或工作区配置中用于引导 AI 进入 LDVH 管理入口、管辖项目配置或 LDVH 事实源的薄引用 | 属于用户工作区，不随 LDVH 项目提交；初始化时只应写入醒目的单句引用或等价薄入口 |
| 项目级入口 | LDVH 自身项目仓库内用于说明本项目如何被当前环境治理的薄入口、平台规则文件、项目指令或等价入口 | 默认只用于 LDVH 自身项目；管辖项目一般不创建项目级入口，避免和用户项目原有入口冲突 |
| AI 统一入口 | LDVH 自身项目根目录 LDVH-AI-ENTRY.md，用于向 AI 提供最小读取顺序、场景路由、STOP 点和权威路径提示的运行投影 | 不是 docs/specs 正式规范，不替代管辖项目配置、当前环境初始化记录、工作对象事实源或 Code 验证；具体规则由 `docs/specs/04.02-环境适配与运行投影规范.md` 规定 |
| LDVH 项目事实源 | 管辖项目中由 LDVH 创建、维护或消费的命名空间事实源、工作对象实例或受控记录 | 可以在管辖项目内创建；不得伪装成用户项目原有入口或替代用户项目业务文件 |
| 项目接入说明 | 解释某个管辖项目如何通过工作区级入口、管辖项目配置、`ldvh-base/`、`docs/` 或产品初始化结果进入 LDVH 治理的叙述性说明 | 不是根目录管辖项目清单；不得承载环境能力核验、运行投影正文或平台入口正文 |
| 能力缺口 | 当前环境没有能力完整承接某项规范落地要求，或能力存在但缺少必要配置、入口、Code、测试、权限或 Human Gate | 不得通过改低正式规范要求解决 |
| 漂移 | 运行投影、环境适配映射或自动触发方式与 docs/specs 正式规范不一致，或规范已变更但运行投影未同步 | 漂移检查结果不是最终事实源，稳定结论需要回写 |
| 降级方式 | 环境能力不足、运行投影缺失或稳定触发无法保证时，记录的替代检查、人工确认、后续任务或残留风险处理方式 | 不得用于降低正式规范要求 |
| LDVH 落地特别要求 | LDVH 自行设定、跨环境落地时需要遵守的特殊运行纪律，例如薄入口、LDVH 自建 Skill 命名和 Skill 触发边界 | 由 `docs/specs/04.05-LDVH落地特别要求规范.md` 规定 |
| 个人落地特别要求 | 当前个人、维护者或当前执行环境中的特殊命令、路径或平台约定 | 由 `docs/specs/04.06-个人落地特别要求规范.md` 登记；不自动推广为 LDVH 通用规则 |
| 启用 | 将已登记的 LDVH 落地特别要求或个人落地特别要求应用到特定环境、项目、运行投影、Code 配置或 Human 选择中的动作 | 未启用事项不得被 AI 当成当前项目规则执行 |
| 薄入口 | 运行投影中的入口内容只承担发现、触发、导航、提醒和交还职责，不复制完整规范正文，不维护第二事实源 | 不等于信息不足；细则应回到正式规范、LDVH 自身环境初始化记录、管辖项目配置、Code 实现或其他权威位置读取 |

规范落地要求类型包括上位约束承接要求、入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求和生命周期触发要求。各类型的规则以 `docs/specs/04.01-规范落地声明规范.md` 为准。

## 8. 构成要素与环境能力术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 开发环境 | LDVH 五类构成要素之一，提供 AI 与 Human 实际执行工作的环境能力 | 不是最终事实源 |
| 工作模型 | LDVH 五类构成要素之一，用于承载项目工作事实、对象字段、状态和验收规则 | 通用规则由 `docs/specs/05-工作模型基础规范.md` 承载 |
| 工作对象 | 依据工作模型创建、维护和检查的具体事实实例，例如 Intent、Task、ADR、Memo、Change 或 Pitfall | 不等同于普通 Markdown 文档；具体对象字段和状态由对应工作模型规范定义；管辖项目配置不是工作对象 |
| 工作字段 | 工作模型或工作对象中用于承载特定事实、关系、状态、证据或引用的字段 | 字段命名、类型和内容格式由工作模型规范和 `docs/specs/05.01-工作字段内容格式规范.md` 定义 |
| 工作流程 | LDVH 五类构成要素之一，用于约束 AI 如何识别场景、读取事实、执行、验证、回写和暂停 | 通用规则由 `docs/specs/06-工作流程基础规范.md` 承载 |
| Code | LDVH 五类构成要素之一，用于确定性执行、解析、校验、聚合、测试、上下文压缩和受控写入 | 工具、脚本、校验器和命令入口都是 Code 的实现形态 |
| Web | LDVH 五类构成要素之一，用于 Human-facing 展示、确认、授权、验收和受控轻写入 | Web 页面状态不是最终事实源 |
| 受控轻写入 | Web 在规范授权范围内，对已定义字段、状态或人工标记执行的有限写入 | 不是开放式事实源编辑；写入入口、校验规则和事实源回写仍必须由对应 Code 能力或正式规范约束 |
| Rules / Instructions | 环境中用于入口可见、硬约束摘要、事实源边界提示或项目入口提示的能力或实体 | 只是运行投影，不是最终规范事实源 |
| Skill | 环境中用于复用多步骤流程、标准化输入输出或受控检查步骤的能力或实体 | 不负责调度子 Agent；需要稳定触发时应组合 Hook、CI、自动运行或降级检查 |
| LDVH 自建 Skill | 由 LDVH 为承接自身工作流程、治理动作、检查步骤或运行投影而创建或要求维护的 Skill | 不等于管辖项目业务 Skill、第三方平台 Skill 或一次性实验 Skill |
| LDVH 包装 Skill | LDVH 为封装、调用或约束第三方能力、项目能力或既有流程而维护的 Skill | 不改变被包装能力的事实源边界，也不得绕过 LDVH 自建 Skill 的正文边界要求 |
| Agent | 环境中用于独立上下文、专项视角、并行审查或权限边界差异的能力或实体 | Agent 输出必须回到主控或 Human，稳定结论回写后才生效 |
| Hook / 自动触发 | 环境中用于生命周期事件触发、提醒、阻断、记录或自动检查的能力或实体 | 不定义规范正文或工作流程本身 |

Tools 和 PyTools 不作为核心构成要素或独立机制术语。需要指向具体实现时，优先使用 Code、工具、脚本、校验器、命令入口或 `tools/` 目录实现。

## 9. 工作流程、运行闭环、初始化、审计与检查术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 运行闭环 | LDVH 从 Intent、Plan、Execute、Verify、Record 到 Learn 的端到端质量闭环 | 不等同于单个工作流程 |
| 具体工作流程 | 40-59 区段中单一行动或行动族的执行规范，约束 Context、Scenario、Gate、执行、验证、回写和暂停 | 具体工作流程是工作流程构成要素在运行闭环中的组成单元 |
| Scenario 识别条件 | 工作流程用于判断某个行动是否进入的场景条件 | 不应由 Rules / Instructions 维护完整正文 |
| Gate | 工作流程中的暂停、进入、退出、确认或授权条件 | Human Gate 是高影响场景中的人类确认机制 |
| 产品初始化 | 将 LDVH 规范体系真正转化为项目可用实践的落地环节 | 详细流程由具体工作流程定义；不得被环境初始化替代 |
| 环境初始化 | 为 LDVH 自身项目和当前开发环境完成环境能力核验、环境适配映射、运行投影准备和降级记录的初始化准备 | 只是产品初始化的前置准备或组成部分，不等同于产品初始化；不作为管辖项目默认初始化动作 |
| 当前环境初始化记录 | LDVH 自身项目根目录 LDVH-ENVIRONMENT-INITIALIZATION.md，记录 LDVH 自身项目的环境适配、运行投影、能力核验和降级方式 | 不是 docs/specs 正式规范，不替代产品初始化，不作为管辖项目默认文件 |
| 产品审计 | 对已经完成或声称完成的产品初始化结果进行审查，确认实践是否真实存在、持续有效、未漂移且未绕过 Human Gate | 可以使用检查作为手段，但不等同于检查 |
| 检查 | 依据规范、工作对象、工作流程或 Code 契约，对文档、实例、行动、输出或运行投影进行符合性判断 | 检查结果不是最终事实源，稳定结论需要回写 |

“工作闭环”不作为推荐术语；优先使用“运行闭环”。

## 10. 非 LDVH 来源内容与最佳实践术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 非 LDVH 来源内容 | 不是由 LDVH 正式规范、LDVH 自建 Code、LDVH 自建 Skill、LDVH 初始化产物或已被 LDVH 接管的事实源直接提供的内容、能力、资产或产物 | 可被读取、参考、调用或转换，但不能未经接管直接生效 |
| 已接管 | 非 LDVH 来源内容已经完成来源识别、用途判断、影响范围判断、主控审查、必要验证、事实源归属和必要 Human Gate | 已接管不等于成为强制规则；是否生效取决于写入的权威位置 |
| 未接管 | 非 LDVH 来源内容尚未完成接管要求，只能作为候选输入、参考材料、临时能力或待验证产物 | 不得直接作为 LDVH 规则、事实、状态、证据或验收结果 |
| 主控接管 | LDVH 主控对外部输入或外部能力输出进行审查、筛选、验证、归属、回写、降级或废弃的治理动作 | 外部能力不得替代主控进行事实源归属、最终验收、跨流程调度或 Human Gate 决策 |
| 信任等级 | 非 LDVH 来源内容在当前接管状态下可被如何使用的分级判断 | 具体等级和准入规则由 `docs/specs/11-非LDVH来源内容治理规范.md` 承载 |
| 最佳实践 | 经过实践验证、可复用但不直接产生强制规则的最佳做法、案例或经验入口 | 不能定义新的工作模型、工作流程、字段、状态机、事实源、Human Gate 或 Code 硬规则 |
| 实践升级 | 将最佳实践中反复稳定出现的经验，按内容性质吸收到正式规范、工作对象、Code、Web、测试或其他权威位置的治理动作 | 升级后是否具备强制效力，取决于被吸收的权威位置 |
| 第三方 Skill 接管落地选项 | 第三方 Skill、平台 Skill、外部 Skill 或类似外部可复用 AI 能力作为默认可用接管路径时的启用、取消、降级和重新启用选项 | 默认启用，但用户可以通过 AI 请求取消；取消不影响 11 的非 LDVH 来源内容治理规则 |

## 11. 中文术语定语规则

中文“规则”“技能”“代理”“智能体”“工具”“程序”“展示”“机制”等词不得裸用，除非上下文已经通过标题、表格字段或段落首句明确限定其语义。

推荐用法如下：

| 场景 | 推荐用语 | 避免裸用 |
|---|---|---|
| docs/specs 中的稳定条款 | 正式规范、规范规则、规范要求 | 规则 |
| 工作模型字段、状态、验收、检查 | 字段规则、状态规则、验收规则、对象检查 | 规则 |
| 工作流程 Context、Scenario、Gate、执行、回写、证据 | 行动规则、Scenario 识别条件、Gate 条件、回写要求 | 规则、触发规则 |
| 环境入口约束 | Rules / Instructions 入口、入口摘要、硬约束摘要 | 规则 |
| 普通能力说明 | 能力、功能、流程、方法 | 技能 |
| AI 泛称 | AI 执行者、AI 代理能力、子 Agent | 代理、智能体 |
| 确定性实现 | Code 实现、工具、脚本、校验器、命令入口 | 程序 |
| Web 能力 | Web、Human-facing 页面、信息同步、受控交互 | 展示 |
| 环境适配 | 环境能力、环境实体、运行投影 | 机制 |

## 13. 固定机制子文档边界

固定机制子文档指围绕工作模型或工作流程默认拆出的 `NN.01` 至 `NN.06` 文件，例如 Rules、Skill、Agent、Tools、Web 和 Contract 文件。

固定机制子文档不构成工作模型或工作流程的默认完整性要求。机制相关内容应按内容性质进入主规范、规范落地要求、环境适配映射、Code 规范、Web 规范、工作流程规范、结构化契约或待补齐事项。

## 16. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变五类构成要素的术语边界；
2. 将环境能力、环境实体或运行投影提升为最终事实源；
3. 将环境初始化等同于产品初始化；
4. 改变规范落地要求、保障机制、环境适配映射、运行投影或 AI 统一入口之间的术语关系；
5. 改变 Code、工具、脚本、校验器或 `tools/` 目录实现之间的术语边界；
6. 将固定机制子文档恢复为默认完整性要求；
7. 长期保留不推荐表达对照而不安排收敛；
8. 允许其他规范并行维护本文已定义术语的权威定义。

术语检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位来源 | 00 是本文的上位概念来源，本文未反向改写 00，00 未以本文作为自身规范依据 |
| 术语归口 | 术语定义归口本文，其他规范只说明应用规则 |
| 产品初始化 | 产品初始化未被环境初始化替代 |
| 环境适配 | 环境能力、环境实体和运行投影未混同 |
| AI 统一入口 | AI 统一入口被视为运行投影，不是正式规范或最终事实源 |
| 构成要素 | 开发环境、工作模型、工作流程、Code、Web 未互相替代 |
| 中文定语 | 高风险中文裸词已有上下文限定或改为推荐用语 |
| 不推荐表达 | 不推荐表达已有替代写法 |
