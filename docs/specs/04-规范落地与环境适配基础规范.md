## 1. 本文解决的问题

本文解决 LDVH 正式规范如何进入具体 AI 开发环境和运行环境的问题。

04 系列不以某个环境已有能力为起点，也不把环境视为主动承接方。04 系列的基本链路是：

```text
正式规范声明落地要求
  ↓
LDVH 提供能力保障
  ↓
LDVH 读取环境能力清单
  ↓
LDVH 完成该环境中的环境适配、能力输出、适配降级和缺口记录
```

环境只提供客观能力清单、约束、证据和当前可用性边界。环境不决定 LDVH 的能力保障，也不能降低 LDVH 的规范要求。环境能力不足只能形成环境缺口和适配降级，不能阻止 LDVH 为其他环境、Code、CI、Web 或后续演进提供更完整的能力保障。例如 Trae 暂无稳定 Hook 能力时，只能在 Trae 环境适配中降级；如果 Codex 或其他环境具备更稳定的 Hook / lifecycle 能力，LDVH 仍应保留并建设该能力路径。

---
## 2. 与 00 总纲的关系

00 将开发环境列为 LDVH 构成要素之一，同时要求 Code、Web、工作模型、工作流程和事实源协同运行。本文承接 00 的治理边界：

1. 正式规范仍是规则事实源；
2. Git 文件仍是稳定事实源的默认承载；
3. Code 提供确定性执行、校验和受控写入；
4. Web 提供 Human-facing 派生视图和受控交互；
5. AI 环境入口、Skill、Agent、Hook、Command、配置和缓存都只是能力输出或环境适配表达；
6. Human Gate 负责授权、暂停、确认和高影响决策。

04 系列只定义规范落地、能力保障和环境适配的基础规则，不替代 00 的理念、事实源边界、工作对象规范、Code 规范、Web 规范或 42 检查流程。

## 5. 基础原则

1. **规范先行**：只有正式规范声明落地要求后，才进入能力保障和环境适配判断；
2. **LDVH 提供**：能力保障由 LDVH 提供，不由环境替 LDVH 选择；
3. **环境客观**：环境只提供能力清单、限制、证据状态和当前可用性；
4. **能力不降级**：弱环境只能在自身适配中降级，不能降低 LDVH 对强环境、Code、CI 或 Web 的能力建设；
5. **薄入口**：环境入口只保留摘要、路径、触发、STOP 点和交还方式，不复制正式规范正文；
6. **事实源回写**：环境工具输出、能力输出、Web 视图和对话结论不是最终事实源；
7. **显式降级**：无法完整适配时，应写明适配降级、残留风险和后续补齐事项；
8. **Human Gate**：高影响写入、长期配置、权限扩大、完整支持声明和删除历史清单前必须暂停确认。

## 6. 环境扩展规则

本文当前只要求 `04.03` 写 Trae Work CN 与 Codex App。若后续需要新增其他环境，应按以下顺序处理：

1. AI 读取该环境官方资料、项目 refs 和当前环境证据；
2. AI 形成环境客观能力清单，区分已验证、refs-only、待确认、不可用；
3. AI 按 `04.03` 的环境适配字段补齐适配方式和能力输出；
4. AI 写明来源、适配检查、适配降级和待补齐事项；
5. 完整支持声明、新增环境列或长期能力输出创建前触发 Human Gate。

不得因为某个环境未写入当前环境范围，就把该环境视为不支持；也不得因为某个环境有候选能力，就声明 LDVH 已在该环境完整落地。

## 7. Human Gate 与检查要求

以下情况必须评估 Human Gate：

1. 改变 04 系列三层主轴；
2. 将环境能力反向提升为 LDVH 全局能力要求；
3. 声明某环境完整支持 LDVH；
4. 新增、删除或长期维护环境适配文件；
5. 恢复旧 04.06 / 04.07 / 04.08 为当前环境适配事实源；
6. 允许能力输出替代正式规范或 Git 文件事实源；
7. 允许弱环境降级结果影响强环境能力建设。

检查 04 系列时，应确认：

| 检查项 | 标准 |
|---|---|
| 三层方向 | 规范声明要求、LDVH 提供能力保障、LDVH 基于环境能力清单完成环境适配 |
| 术语一致 | 使用能力保障、环境适配、环境能力清单、能力输出、适配降级，不把环境写成主动承接方 |
| 文件边界 | 04.01、04.02、04.03、04.04 职责未混同 |
| 事实源边界 | 环境适配、能力输出、入口、工具输出、Web 视图未成为最终事实源 |
| 环境扩展 | 新环境通过调研和卡片追加，不凭记忆补写 |
| 降级处理 | 环境不足只影响本环境适配，保留强环境高质量路径 |
