## 1. 目的

本提案在继续编号或起草正式规范之前，回答五个问题：

1. V4 还必须承担哪些长期且独立的规范职责；
2. 哪些职责需要独立标准规范，哪些应合并、延后或交给附件、Schema、Code 和行动模板；
3. 每项职责负责什么、明确不负责什么；
4. 规范依据、结构归属、建设顺序和编号顺序如何分开；
5. 哪些真正是需要 Human 决定的架构选择。

本文不起草具体规则，不为未来全部规范预分配编号，不新建 Code 或 tests，也不改变 Web 和 `icons/` 的冻结边界。

## 2. 职责划分与完整性检查原则

候选职责只在同时满足以下条件时建议由独立标准规范承担：

1. 能用一个长期成立的问题表达其唯一职责；
2. 与相邻职责存在独立失败场景，不能由其他职责自动推出；
3. 变化原因、消费方式或验证入口足以独立；
4. 拆分能降低 AI 的定位、理解、边界或维护负担，没有只为目录整齐制造额外流程；
5. 能明确归入 00 定义的五类构成要素，没有形成第六类构成要素。

低频迁移、内部维护、特定厂商事件、具体命令和单一实现细节，默认不单独建立标准规范。

01 的适用范围覆盖所有标准规范，统一规定文档身份、结构、关系、规则表达和规则源资格。这不表示每份规范都必须把 `specification-model-foundation` 机械写入 `basis`；`basis` 只保留理解、判断或维护当前职责直接且必要的规范依据。

本提案中的独立标准规范都是直接细化 `ldvh-root` 下不同职责的同级候选，不根据编号、建设先后或消费方向构造人为的多层规范树。实际起草时，结构归属使用 `parent_spec` 与 `relation` 表达；规范依据使用 `basis` 独立表达，两者不得互相替代。

## 6. 三组关键边界

### 6.1 不建立广义 AI 行为总规范

Human 于 2026-07-12 确认，V4 不为了保留 V3 名称而建立独立《AI 行为规范》，也不建立《AI 规则履行规范》。原候选内容都有更准确的职责承担位置：

1. 规则是否适用、命中后产生什么义务，由《规则适用与效力规范》及相应具体规则的来源规范承担；
2. 事实、推测、证据和如实声明的边界，由事实源与信息溯源、验证与声明及相应具体规则的来源规范承担；
3. Human Gate、暂停、交还和缺少所需能力时的处理，由 00、相应具体规则的来源规范和 Helper 服务契约承担；
4. 重复场景的行动结构由行动模板承担，未命中规则或模板的普通求解继续保持自主。

“矩阵型答复是否使用 SVG”等可随时调整的输出、交互或协作偏好，不默认提升为 LDVH 永久规则：

1. 只在当前交互需要时，直接使用作用范围清楚的 Human 当前指令，不必持久化；
2. 需要跨会话、按项目或按工作对象保留时，按事实模型的准入条件论证是否建立候选 AI 协作偏好记录，由相应事实记录承载当前作用范围和启用状态；
3. ADR 可以记录为什么选择某种偏好或提供、检查机制，但不承载当前启用状态，也不因决策记录自动产生规则效力；
4. 如果某项可变配置需要“必须执行”的效力，正式来源规范必须先定义参数含义、适用范围、优先级，以及参数值如何影响规则效力；事实记录只提供当前值，不因提供参数而变成第二规则源。

Human 当前指令和已启用协作偏好只在其作用范围内影响可自主决定的表达或协作方式，不得覆盖已适用来源规则的强制要求、Human Gate 或 Stop Conditions；发生冲突时必须如实报告并按来源规则处理。

当前不再单独建立“AI 行为机制规范”。Helper 可以在未来服务契约中区分来源规则、Human 当前指令和已启用协作偏好，向 AI 提供时保留来源回指；Code 和环境机制只在已规划、已实现、已接入且可验证的范围内提供、检查或反馈。

### 6.2 事实源、事实模型和验证声明分开

三项责任分别回答：

1. 事实源与信息溯源：信息是什么角色，来自哪里，能否进入稳定事实；
2. 事实模型：稳定内容如何对象化保存；
3. 验证与声明：现有依据能够支持多大范围的结论。

三者的变化原因、消费方和验证方式不同，任意两者都不能推出第三者。合并会重现 V3 对信息权威、持久结构和证据支持范围的混用。

### 6.3 Helper 服务、Code 工程实践要求与真实实现分开

《LDVH Helper CLI 服务契约规范》定义面向 AI 的外部服务语义，不定义内部模块和算法。

《Code 系统规划与工程实践规范》定义 Code 构成要素内的系统规划与工程实践要求，当前不再拆成“Code 架构规范”和“Code 实践规范”两份独立标准规范，也不建立“Code 实现规范”。真实实现只位于 Code 和 tests。

未来系统规划可以考虑使用候选 `attachment_key: code-system-plan` 的授权附件，承载模块职责表、模块之间允许的引用与调用关系、公共接口登记、Schema 的唯一定义和维护责任、测试映射，以及可度量的规模、复杂度、测试和可维护性约束。核心规则、适用范围、准入、验证、Human Gate 和 Stop Conditions 必须由父规范正文先定义；授权附件只能承载正文已授权的结构化细节，带有独立叙事和决策理由的完整规划不得整体放入附件。调查材料仍是 `docs/` 或未来 Study 输入，只有被当前规则源正式吸收的要求才有规则效力。

## 8. 规范依据、结构归属和实现消费关系

本节分别记录三类不同关系。它们不得因为都能画成箭头而混为一种“依赖”：

1. 结构归属：由 `parent_spec` 与 `relation` 表示当前规范在规范结构中直接属于或细化谁；
2. 规范依据：由 `basis` 表示理解、判断或维护当前规范所必需的直接上位规范；
3. 实现或消费关系：描述 Helper、Code、环境适配器和 Web 如何使用规范、事实或服务，不是规范依据，也不建立结构归属。

| 事实模型基础 | `work-object-governance-scope`、`fact-source-traceability`、`verification-claims` | 稳定事实对象必须具有对象边界、事实源位置和证据边界 |
| 行动模板基础 | `rule-applicability-effect`、`verification-claims`、`fact-model-foundation` | 行动结构需要引用适用规则、验证条件和事实回写边界 |
| LDVH Helper CLI 服务契约 | `specification-model-foundation`、`work-object-governance-scope`、`fact-source-traceability`、`rule-applicability-effect`、`verification-claims`、`fact-model-foundation`、`action-template-foundation` | Helper 需要统一组织这些已经定义的语义，但不创造新语义 |
| Code 系统规划与工程实践 | `helper-cli-service-contract` | Code 需要实现已定义的 Helper 外部服务，并保持内部职责与外部契约分离 |
| 环境接入 | `work-object-governance-scope`、`verification-claims`、`helper-cli-service-contract` | 环境适配器需要传递对象信息、调用 Helper 并验证真实接入 |
| Web 信息呈现与交互 | `fact-source-traceability`、`verification-claims`、`fact-model-foundation` | Web 从相应 Source of Truth 独立读取，并呈现事实、证据和声明边界 |

### 8.3 实现与消费关系

以下关系不写入 `basis` 或 `parent_spec`：

1. 规范模型、事实模型、行动模板和 Code 能力由 Helper 组织后服务 AI；
2. Code 实现 Helper CLI，但 Code 的实现关系不赋予 Code 重新定义 Helper 外部语义的权力；
3. 环境适配器转换目标环境协议并调用 Helper，不自行实现另一套规则或管辖判断；
4. Web 从相应 Source of Truth 独立读取并服务 Human，不通过 Helper；
5. Code/tests 的实现和真实环境接入属于建设活动，其先后关系只在 §9 记录。

## 10. Code 启动条件

V4 Code 和 tests 继续暂停。首批实现开始前，至少必须同时满足：

2. 《Code 系统规划与工程实践规范》已吸收经可靠来源和适用性核验、符合 00 和 V1-V8 的外部工程实践要求；
3. 当前 V4 系统规划已明确模块职责、模块之间允许的引用与调用方向、公共接口、Schema 的唯一定义和维护责任、测试层次与映射、可度量的质量约束和必须重构的条件；
4. 首个可端到端验证的最小实现增量，其可证明范围、未实现范围和验证入口已明确；
