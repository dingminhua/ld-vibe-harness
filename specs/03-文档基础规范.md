## 1. 本文解决的问题

本文定义 LD Vibe Harness 中不同文档工作区共享的基础规则：文档工作区如何划分正文、studies 和 sources，文件如何命名，章节和段落如何组织，文档之间如何引用，调研或分析结论如何吸收，以及 AI 修改文档时应如何检查。

本文不直接定义 LDVH 正式规范编号、规范落地要求字段、README 写作规则、需求文档模板、技术文档模板或根目录 YAML 配置字段。这些特例由应用剖面或专题子文档定义：规范文档剖面依据 `specs/03.01-规范文档规范.md`，管辖项目配置依据 `specs/03.04-管辖项目配置规范.md`。

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 依赖 Git 可追踪文件作为稳定事实源，并要求 AI、人、Code 和 Web 围绕同一组事实协作。本文承接该要求，为 Markdown 文档类事实源提供统一的文档工作区、文档结构、引用和吸收规则。

本文是文档基础规则的权威位置。应用剖面文档只能声明某个文档工作区的特有规则，不得复制或改写本文的通用规则。

## 3. 文档工作区三分契约

### 3.1 文档工作区

文档工作区是一个 Git 可追踪目录，用于承载一组具有共同事实源边界的 Markdown 文档。LDVH 当前正式识别的文档工作区如下：

| 文档工作区 | 根目录 | 正文区 | 应用剖面 | 说明 |
|---|---|---|---|---|
| LDVH 文档工作区 | `docs/` | `specs/` 和 `docs/` 根目录 Markdown 文档 | `specs/03.01-规范文档规范.md` | `specs/` 承载 LDVH 正式规范资产；`docs/` 根目录 Markdown 文档承载用户资产或项目文档资产；`docs/studies/` 和 `docs/sources/` 承载可变资料 |

管辖项目不默认创建 `specs/`，也不因登记为管辖项目而形成 LDVH 管理的 `docs/` 文档工作区。LDVH 自身作为被 LDVH 管辖的项目时，正式规范以 `specs/` 承载，以根 README 文档和必要的 `docs/` 根目录正文文件承载项目入口文档或项目资料。

### 3.2 三分契约

每个文档工作区使用同一套三分契约，但正文区路径可以由应用剖面指定：

```text
<B>/        正文区
<W>/studies/  内部研究、内部分析和吸收候选
<W>/sources/  外部信源、外部资料和第三方资料
```

其中 `<W>` 是文档工作区根目录，`<B>` 是正文区目录。LDVH 文档工作区中规范正文区为 `specs/`，用户资产或项目文档资产正文区为 `docs/` 根目录 Markdown 文档。管辖项目文档由项目自身约定管理，LDVH 仅在具体任务、用户明确指令、项目约定或 Human Gate 触发时读取、引用或受控修改。

### 3.3 正文区

正文区承载已经被采纳、可以作为该文档工作区稳定事实源的文档。

正文区规则：

1. 正文区承载该文档工作区的权威文档；
2. specs 正文区不得把 `docs/`、`studies/`、`sources/`、外部 URL、外部项目资料或非 LDVH 资产作为权威依据；
3. 正文区可以记录已经吸收的结论，但结论正文必须写入正文区自身或对应工作对象；
4. 正文区文档如需稳定关联工作对象，应使用对象 ID、文件路径或应用剖面定义的字段承载。

### 3.4 studies 区

`studies/` 承载内部研究、内部分析、方案比较、实践复盘、设计探索和吸收候选。

studies 区规则：

1. studies 文档不直接构成正文区稳定事实；
2. studies 文档可以引用正文区作为评估依据；
3. studies 结论必须吸收到 specs、正文区、ADR、WorkPlan、Memo、Pitfall、WorkArea 或其他权威位置后才生效；
4. studies 文档必须声明来源，来源应明确指向被评估材料、用户输入、调研对象、会议记录、外部资料或其他真实输入，不得只指向关联对象；
5. studies 文档可以通过头部 `关联对象` 字段登记相关 WorkArea、WorkPlan、ADR、Memo、Pitfall 或其他工作对象；该字段可以为空，且不得替代来源字段；
6. studies 编号只用于排序和引用便利，不占用正文区编号体系。

### 3.5 sources 区

`sources/` 承载外部信源、外部资料和第三方资料。

sources 区规则：

1. sources 文档不直接构成正文区稳定事实；
2. sources 文档不得反向维护正文区规则、正文区结论或工作对象状态；
3. sources 文档不得包含对正文区文件的路径引用、关联规范声明或依据引用；
4. 外部资料中的结论必须先被分析、判断并吸收到 specs、正文区或工作对象后，才可成为稳定事实；
5. sources 文档必须声明来源，来源应明确指向外部资料、引用副本、网页、论文、仓库、产品文档、访谈记录或其他真实来源，不得只指向关联对象；
6. sources 文档可以通过头部 `关联对象` 字段登记相关 WorkArea、WorkPlan、ADR、Memo、Pitfall 或其他工作对象；该字段可以为空，且不得替代来源字段；
7. sources 编号只用于排序和引用便利，不占用正文区编号体系。

### 3.6 吸收规则

按术语规范的术语边界，吸收要求 studies 或 sources 中的结论转入某个权威位置。吸收后，权威位置承载结论本身，原 studies 或 sources 只保留背景、来源或分析过程。

常见吸收出口如下：

| 输入位置 | 结论性质 | 吸收出口 |
|---|---|---|
| `studies/` | 稳定文档规则 | specs 或正文区 |
| `studies/` | 长期决策 | ADR |
| `studies/` | 可执行工作 | WorkPlan |
| `studies/` | 暂存发现或待观察信息 | Memo |
| `studies/` | 已解决且可复用的踩坑经验 | Pitfall |
| `sources/` | 被采纳的外部事实或方法 | specs、正文区、ADR 或 WorkPlan |
| `sources/` | 仅供背景阅读 | 保留在 sources，不升级 |

吸收不得只通过“引用 studies 或 sources 路径”完成。specs 正文区不得出现指向 docs、studies、sources、外部 URL、外部项目资料或非 LDVH 资产的依据性引用。被采纳的权威结论必须在吸收出口中明确写出。

## 4. 命名与路径规则

### 4.1 文件命名

文档文件名应表达文档身份和主题。文档工作区应用剖面可以为正文区、studies 区和 sources 区定义更具体的编号或命名规则。

通用命名规则：

1. 正文区文件名应稳定、可读、避免临时词；
2. studies 和 sources 文件可使用自然序号作为排序前缀；
3. 文件名变更必须同步检查所有路径引用；
4. 文件名不得只依赖日期、聊天轮次或临时任务名表达长期身份；
5. 同一文档工作区内不得出现两个表达同一权威领域的正文文件。

### 4.2 章节编号

Markdown 正文章节标题统一使用阿拉伯数字层级编号。一级章节使用 `## N. 标题`，二级章节使用 `### N.N 标题`，三级章节按需使用 `#### N.N.N 标题`。

同一文档内不得混用中文大写章节编号、罗马数字编号和阿拉伯数字章节编号。正文有序列表可以在章节内从 `1.` 重新开始，不属于章节编号。

### 4.3 应用剖面与专题子文档

子文档用于承接同一父规范下的应用剖面或专题分工。子文档不是父规范正文的任意拆分，也不是父规范规则的复制位置；子文档只有在存在独立、稳定、可命名、可检查或可消费的子归口时才应存在。子文档不得成为每个工作模型或工作流程的默认拆分结构。

父规范与子文档职责边界如下：

1. 父规范负责本规范域的定位、上位依据承接、归口边界、分类原则、准入条件、通用原则、子文档清单和适用边界；
2. 子文档负责明确子领域的应用规则、格式规则、检查规则、消费规则、适配规则或对象化写作骨架；
3. 子文档不得重新定义父规范已经定义的通用规则，不得反向改写父规范原则，不得并行维护父规范已经归口的分类、准入、状态机、字段契约、流程骨架或事实源边界；
4. 父规范不得因为被子文档引用、消费或登记，就反向补写子文档的消费细节、实现路径、同级关系或下游同步义务；
5. 父规范和子文档均不得重新定义 `specs/02-术语规范.md` 已归口术语；需要说明术语在当前规范域中的用法时，应使用术语应用关系。

允许创建或保留子文档的条件：

1. 父规范已经存在可复用通用规则；
2. 存在需要共享通用规则但边界不同的应用剖面或专题问题；
3. 子领域具有独立、稳定、可命名的归口，且放入父规范会显著削弱父规范的可读性或维护性；
4. 子文档只定义应用剖面特例、专题细则、格式规则、检查规则、消费规则或适配规则，不复制父规范通用规则；
5. 子文档规则存在明确消费方、检查方式、适配入口、写作骨架或稳定引用需求；
6. 父规范维护子文档清单和适用边界；
7. 新增、删除或重命名子文档应评估 Human Gate。

父子文档引用关系应遵守本文 §6.4-§6.7：子文档通常以上位依据引用父规范；父规范只有在维护本规范域的子文档清单、适用边界或真实消费关系时，才登记子文档；同级子文档不得仅因主题相关互相列为相关规范。若某段内容回答“本规范域是什么、为什么存在、谁有权定义、如何分类、如何准入”，应放入父规范；若回答“某个子领域怎么写、怎么检查、怎么消费、怎么适配”，应放入子文档；若回答“术语是什么意思”，应放入 `specs/02-术语规范.md`；若回答具体对象字段、状态机、流程步骤、Code 或 Web 实现契约，应放入对应权威归口。

当前应用剖面子文档入口如下：

| 子文档 | 类型 | 说明 |
|---|---|---|
| `specs/03.01-规范文档规范.md` | 应用剖面 | `specs/`、`docs/`、`docs/studies/`、`docs/sources/`，LDVH 规范资产、用户资产和可变资料区 |
| `specs/03.02-工作模型文档规范.md` | 专题子文档 | 20-39 具体工作模型规范文档的写作骨架、成员自描述契约和检查要求 |
| `specs/03.03-工作流程文档规范.md` | 专题子文档 | 40-59 具体工作流程规范文档的写作骨架、成员自描述契约、行动特有可测试性锚点和检查要求 |
| `specs/03.04-管辖项目配置规范.md` | 专题子文档 | 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 的字段、注释示例、使用边界和 Code 校验要求 |

03 相关专题父规范入口如下：

| 专题父规范 | 说明 |
|---|---|
| `specs/04-规范落地与环境适配基础规范.md` | 04 系列专题子文档入口；具体清单由 04 §4 维护 |

为每个工作模型或工作流程默认创建 Rules、Skill、Agent、Code、Web 子文档不属于本节允许的子文档，不得作为默认结构新增。

子文档检查需求按三层处理：

| 检查层级 | 检查需求 | 处理方式 |
|---|---|---|
| 当前机械校验 | 识别 `NN.SS` 子文档类型，检查 `创建日期`、`所属主文档`、`关系`、`适用范围`、`上位依据` 等头部字段，检查 Markdown 路径和章节引用是否存在，并检查子文档是否疑似二次定义 02 已归口术语；二次定义检查覆盖正文段落、列表项、头部元信息、表格单元格和脚注中的定义句式 | 由 `code/specs_validate.py index --fail-on-diagnostics`、文档结构校验和章节引用校验子命令承接；修改子文档相关规范后应运行 `python3 code/specs_validate.py all --fail-on-diagnostics` |
| 后续 Code 候选 | 检查子文档编号是否以前缀隶属于父文档编号，`所属主文档` 是否存在，`上位依据` 是否包含父规范，`关系` 字段是否属于稳定枚举，父规范子文档清单是否与实际文件同步，新增、删除、重命名和回并是否留下待处理引用 | 只有在父子关系字段、关系枚举和清单维护方式稳定后，才按本文 §9.1 扩展 `code/specs_validate.py` 并补正反样例 |
| Human Gate | 新增、删除、重命名子文档，改变子文档父规范归口，扩大子文档适用范围，允许子文档承载父规范通用规则或 02 已归口术语定义 | 先说明父子职责边界、影响文件、引用同步和现有 Code 覆盖情况，再由 Human 判断是否生效 |

当前 Code 能检查子文档的基础结构、引用存在性和疑似术语二次定义句式，但不能替代对子文档职责边界、父子归口和适用范围是否越界的人工判断。若本节新增更细的机械检查需求，应按 §9.1 形成 Code 缺口、实现最小校验并补充正反验证样例。

### 4.4 子文档与术语引用规则

子文档继承父规范的文档边界，也继承 `specs/02-术语规范.md` 的术语归口规则。子文档可以引用 02 已定义术语并说明该术语在当前子领域中的应用关系，但不得把子领域应用关系写成新的术语定义。

子文档使用术语时应遵守：

1. 若只是使用 02 已定义术语，应直接使用推荐术语，不重新解释术语本体；
2. 若需要说明术语在子文档中的用途，应使用“术语 / 子文档应用关系”或等价表格，说明列使用“在本文中用于……”“由……消费”“与……区分”“不得用于……”等应用句式；
3. 子文档不得设置“术语定义”“概念定义”“名词解释”等章节来定义 02 已归口术语；
4. 子文档不得在正文段落、头部元信息、表格单元格、脚注或示例中使用“X 是……”“X 指……”“X 是指……”“X 定义为……”“X 包括且仅包括……”等句式定义 02 已归口术语；
5. 子文档发现术语缺失、术语边界不足或替代写法不清晰时，应先回到 02 增补或调整术语，再在子文档中引用该术语并说明应用关系；
6. 子文档头部 `相关规范` 只有在当前子文档正文直接消费 02 的术语口径、不推荐表达处理或术语变更治理时才登记 02；不得仅因父规范引用 02 而机械反向补写；
7. 子文档头部 `所属主文档` 和 `上位依据` 应指向父规范；术语依据不替代父规范依据，父规范依据也不替代术语归口。

AI 修改子文档时，应按以下顺序执行：

1. 先确认该文件是否为 `NN.SS` 子文档，并读取 `所属主文档`、`上位依据` 和 02；
2. 判断拟新增内容是在定义术语、说明父规范通用规则，还是说明子领域应用关系；
3. 若内容是在回答“术语是什么意思”，写入 02；
4. 若内容是在回答“父规范域的通用分类、准入或边界是什么”，写入父规范；
5. 若内容是在回答“该子领域如何使用某术语、如何写、如何检查、如何消费或如何适配”，写入子文档；
6. 修改后运行 `python3 code/specs_validate.py all --fail-on-diagnostics`，若触发术语二次定义诊断，应优先改写为应用关系或回写 02。

## 5. 文档结构与段落规则

### 5.1 头部元信息

正式纳入文档工作区治理的 Markdown 文档应通过头部元信息说明定位和边界。头部元信息不是普通装饰文本，而是人、AI、Code 和 Web 可共同消费的稳定机器接口。

头部元信息继续使用 Markdown 引用行格式：

```markdown
> 字段：值
```

不得把头部改成 YAML frontmatter，除非对应应用剖面、Code 解析、Web 消费和迁移收益已通过 Human Gate 明确确认。当前 `> 字段：值` 格式已被 Code 解析并用于派生索引、文档类型推断、引用关系、父子文档关系和诊断；AI 和 Web 读取头部时应把这些字段视为稳定契约字段，而不是正文段落。

头部元信息契约遵守以下规则：

1. 字段名应稳定，字段语义由本文和应用剖面定义；
2. 字段值应是短文本、路径引用、对象引用或应用剖面定义的简单值，不承载完整 schema、状态机、长规则正文或执行过程；
3. 同一事实不得同时由普通头部和其他机器契约重复维护；若存在成员自描述、工作对象 YAML、项目配置或 Code 派生索引，应按各自事实源边界分工；
4. Code 可以消费头部字段生成派生索引和诊断，但 Code 输出不是最终事实源；
5. Web 可以展示或链接头部字段，但不得把展示需要反向扩展为新的必填字段；
6. 需要新增、重命名或废弃头部字段时，应先明确字段语义、适用文档类型、内容格式、Code / Web 消费边界和迁移策略。

通用头部字段包括：

| 字段 | 含义 |
|---|---|
| 创建日期 / 更新日期 | 文档创建或最近更新日期 |
| 定位 | 文档回答什么问题，属于什么事实源边界 |
| 适用范围 | 文档适用的项目、场景或文档工作区 |
| 来源 | studies 或 sources 的真实输入、外部资料或触发材料；不得只写关联对象 |
| 上位依据 | 本文依赖的上位规范或权威文档 |
| 相关规范 | 与本文相关但不替代本文权威领域的规范文档 |
| 关联对象 | 与本文相关的 WorkArea、WorkPlan、ADR、Memo、Pitfall 或其他工作对象；可为空，不得替代来源 |

头部不得承载正文才应展开的规则，不得用“本文不做什么”的反向清单替代正向职责表达。

### 5.2 段落与列表

段落应围绕一个明确判断或规则展开，避免把多个事实、判断和行动塞入同一长段。

列表用于表达并列规则、步骤、检查项或选项。列表项应互相独立，避免一个列表同时混合定义、例外、检查和执行步骤。

00 总纲作为顶层纲要文档，可以在 §1 使用产品存在理由或总纲叙事标题，不强制命名为“本文解决的问题”。该例外只适用于 00，不改变其他正式规范文档的标准骨架要求。

### 5.3 表格

表格用于表达稳定对照关系。表格列名应清楚，行内容应能被 AI 和工具稳定解析。

表格不得用于隐藏长篇说明。需要解释的内容应放在表格前后正文中。

### 5.4 代码块

代码块用于承载示例、模板、命令、结构化片段或流程图。代码块中的示例不得被误读为真实事实源，必要时应在代码块前说明其示例性质。

## 6. 引用与关联规则

### 6.1 路径引用

引用 Git 文件事实源时，应使用明确路径。Markdown 正文中的路径引用应可被 AI 搜索和工具检查。

当引用目标文件发生重命名、搬移或删除时，必须同步检查所有路径引用。

### 6.2 章节引用

引用章节时统一使用 `§N`、`§N.N` 或 `§N.N.N`。章节引用必须指向真实存在的标题编号。

应用剖面可以定义编号速记规则，但速记规则不得替代真实路径和章节存在性检查。

### 6.3 对象引用

引用工作对象时，应使用对应工作模型定义的对象 ID 或文件路径。文档引用对象不改变对象状态；对象状态、负责人、验收和关闭证据仍由工作对象事实源承载。

### 6.4 引用方向

文档引用必须遵循事实源边界。正文区不得通过引用 studies 或 sources 来绕过吸收；studies 和 sources 也不得反向定义正文区规则。

引用关系只表达当前文档为了理解、继承、消费、同步或检查而需要读取的事实源，不表达被引用文档的重要程度、被引用次数、被下游依赖情况或补齐对称关系的需要。判断是否写入引用字段时，应先判断当前文档自身是否存在真实读取、约束、字段消费、状态消费、同步或检查义务，再选择引用类型；不得因为两个文档主题相近、文件互相提到、下游已经引用上游、或希望提升可发现性而补写引用。

头部元信息中的引用方向应遵守以下规则：

1. `上位依据` 只登记当前文档直接承接的上位规范或权威文档；
2. `相关规范` 只登记当前文档定义自身边界、消费字段契约、同步要求或执行检查时必须读取的规范；
3. `来源` 只登记 studies 或 sources 的真实输入、外部资料或触发材料，不得只登记关联对象；
4. `关联对象` 只登记与当前文档相关的工作对象，可为空，不得替代来源、上位依据或相关规范；
5. 被引用文档不得仅因为被下游文档引用，就在自己的 `相关规范` 中反向登记该下游文档；
6. 允许双向引用的前提是两个文档都对彼此存在真实约束、字段契约消费或同步义务，且这种义务能从正文中读出；
7. 成员自描述主文件可以登记自身集合事实，Code 派生索引可以聚合成员清单和状态；派生索引不是普通 `相关规范` 的反向登记理由；
8. 如果只是“谁引用了我”的追溯需求，应通过全文搜索、Code 索引或审计结果获得，不写入被引用文档的 `相关规范`。

### 6.5 定义归口判定

定义归口用于判断某个规则、字段、状态、术语、流程或目录事实应由哪个文档维护。归口判断先看内容性质和权威领域，再看引用关系；引用某个文档不改变定义归口，被引用文档也不因此获得维护引用方规则的职责。

定义归口判定顺序如下：

1. 术语名称、术语边界、推荐用语、不推荐表达处理和术语变更治理归口 `specs/02-术语规范.md`；
2. 目录、编号分区、文件归属和工作区映射归口 `specs/01-目录说明.md`；
3. 文档工作区、正文区、studies、sources、文档结构、引用、吸收和文档治理检查归口本文；
4. specs 正式规范骨架、LDVH 自身 `specs/` 应用剖面、规范落地要求段落和 specs 修改执行顺序归口 `specs/03.01-规范文档规范.md`；
5. 工作模型成员自描述契约归口 `specs/03.02-工作模型文档规范.md`，工作流程成员自描述契约归口 `specs/03.03-工作流程文档规范.md`；
6. 工作模型通用规则归口 `specs/05-工作模型基础规范.md`，具体工作模型字段、状态机和实例规则归口对应 20-39 工作模型规范；
7. 工作流程通用规则归口 `specs/06-工作流程基础规范.md`，具体工作流程 Context、Scenario、Gate、执行、回写和证据规则归口对应 40-59 active 工作流程规范；
8. 规范落地要求、LDVH 能力保障、环境适配、环境能力、适配措施和入口部署归口 04 系列对应规范；
9. Git 文件事实源、单一事实源、事实承载介质和回写边界归口 `specs/09-事实源边界与承载规范.md`；
10. Code 和 Web 的实现边界、验证、同步和消费规则分别归口 `specs/07-Code确定性执行实现规范.md` 与 `specs/08-Web信息同步实现规范.md`。

当一个内容同时涉及多个归口时，应把定义写入最小权威归口文档，并在其他文档只保留必要入口、引用或消费规则。若当前归口文档尚未创建、尚未生效，或成员自描述 / Code 派生集合索引显示为 candidate、planned、reserved、removed 或其他非 active 状态，只能把内容记录为候选事项、待补齐事项、工作对象或 studies 输入，不得把未生效文档当作权威归口。

### 6.6 引用类型分级

引用类型按约束强度分级。选择引用字段时，应使用满足当前文档实际依赖的最低充分级别，不得把普通导航、追溯或主题相关提升为上位依据或相关规范。

| 引用类型 | 约束强度 | 写入位置 | 判定标准 |
|---|---|---|---|
| 上位依据 | 最高 | 头部 `上位依据` | 当前文档直接承接其原则、分类、状态机、字段契约、流程骨架或权威边界；删除该依据会导致当前文档失去定义基础 |
| 相关规范 | 高 | 头部 `相关规范` | 当前文档定义自身边界、消费字段契约、同步要求或执行检查时必须读取；不是被谁引用的反向清单 |
| 正文依据引用 | 高 | 正文段落 | 当前规则需要指向另一权威事实源才能说明继承、约束、例外或同步来源，且被引用对象已经是有效权威事实源 |
| 消费引用 | 中 | 正文段落、表格或字段说明 | 当前文档、Code、Web、Rules、Skill、Agent、Hook 或工作对象需要读取另一事实源的字段、状态、清单或输出，但不重定义对方规则 |
| 关联引用 | 中低 | 头部 `关联对象`、对象字段或正文说明 | 仅说明相关工作对象、任务、ADR、Memo、Pitfall 或材料与当前文档有关，不替代来源、上位依据、相关规范或状态事实 |
| 来源引用 | 中低 | studies 或 sources 头部 `来源` | 只登记真实输入、外部资料、触发材料或被评估对象；来源本身不自动成为正文区稳定事实 |
| 导航引用 | 低 | README、入口摘要、索引说明或正文入口句 | 只帮助读者找到材料，不表达定义权威、同步义务、字段消费或检查依赖 |
| 审计追溯 | 最低 | Code 输出、搜索结果、任务证据或审计报告 | 只回答“谁引用了我”“哪里出现了某路径”等追溯问题，不写入被引用文档头部字段 |

引用分级不改变事实源边界。正文区引用 studies、sources、外部 URL、外部项目资料或非 LDVH 资产时，只能作为背景、来源或候选输入，不能作为正式规范依据；稳定结论必须先吸收到对应权威归口后，才能被正文区以依据性方式消费。

### 6.7 禁止反向补全

反向补全是指仅因为 A 文档引用、消费、登记或提到 B 文档，就在 B 文档中补写 A 文档路径、相关规范、上位依据、关联对象、来源、同步义务或正文规则。反向补全会制造虚假的双向约束，破坏定义归口和单一事实源原则，文档治理中不得使用。

禁止反向补全规则如下：

1. 被下游规范引用，不构成上游规范把下游规范写入 `相关规范` 的理由；
2. 被 Code 派生集合索引列入成员清单，不构成成员文档把派生索引或其他成员反向登记为相关规范的理由；
3. 被工作对象、ADR、Memo、Git 提交记录或审计报告引用，不构成文档头部补写该对象为来源、上位依据或相关规范的理由；
4. Code、Web、Rules、Skill、Agent、Hook 或环境入口消费某规范，不构成该规范反向登记具体环境实体、能力资产实例或消费方实现路径的理由；
5. 只有当被引用文档自身正文已经定义对引用方的真实字段消费、状态消费、同步义务、检查义务或双向约束时，才可以写入相应引用；
6. 为可发现性、导航、审计、影响面分析或“谁依赖我”建立的关系，应通过 Code 派生索引、全文搜索、任务证据或审计输出承接，不写入被引用文档头部元信息；
7. 已发现的反向补全应按定义归口和引用类型分级移除、降级为导航引用，或转入对应工作对象、审计结果、待补齐事项。

## 7. 文档与工作对象关系

文档和工作对象是不同事实源形态。

文档适合承载：

1. 背景、解释、设计语境和报告；
2. 需求、技术说明、操作说明和外部资料；
3. 不需要状态机和高频结构化解析的长文本事实。

工作对象适合承载：

1. 状态、负责人、验收、关闭证据和关系字段；
2. 需要 Code 实现校验、聚合或受控写入的事实；
3. 需要跨会话追踪的 WorkArea、WorkPlan、ADR、Memo、Pitfall、Study 等实例，或需要通过 Git 提交记录追溯的事实源修改。

当一个文档需要生命周期治理时，不应直接把文档升级成工作对象；应创建或更新相应 WorkArea、WorkPlan、ADR 或 Memo，并在对象中引用文档路径。

## 8. 规范落地要求

规范落地要求的术语定义按 `specs/02-术语规范.md`，声明字段和类型按 `specs/04.01-规范落地声明规范.md`。本文只说明文档工作区中哪些文档需要设置该段落，以及文档检查如何发现对应 Code 缺口。

规范落地要求段落只适用于 specs 正式规范文档，不是所有 Markdown 文档的通用要求。目录说明、索引说明、studies、sources、README、项目文档和其他非正式规范文档，不默认要求设置规范落地要求段落；只有被应用剖面明确纳入正式规范治理的文档，才适用该段落要求。

按 `specs/02-术语规范.md` 的术语，规范落地要求到具体环境实体的转换应纳入环境适配。规范落地与环境适配的父规范入口由 `specs/04-规范落地与环境适配基础规范.md` 承接；环境适配应说明同一落地要求在当前环境中通过哪些机制、文件、配置、命令、入口、降级方式和验证方式满足，通用规则由 `specs/04.02-LDVH能力资产与落地保障规范.md` 和 `specs/04.03-环境入口适配与部署规范.md` 规定。

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | 文档工作区入口摘要 | 文档工作区入口摘要、应用剖面引用、专题子文档引用、`specs/04.02-LDVH能力资产与落地保障规范.md` | AI 执行入口提示 | 本文的文档工作区三分契约、命名规则、引用规则、子文档规则或文档与工作对象关系变化时 |
| 确定性执行要求 | 文档章节和引用校验 | `code/specs_validate.py` 或后续文档校验 Code、正反样例验证、降级风险记录 | 校验实现 | 本文的章节编号、章节引用、路径引用、studies/sources 边界或文档治理检查变化时 |

具体环境实体不在本文表格中声明，应由后续环境适配规则解释。遇到“机制落地关系”或“机制承接关系”等不推荐表达时，应按 `specs/02-术语规范.md` 处理，将其拆分为“规范落地要求”“LDVH 能力保障”和“环境适配”后再吸收到当前正式规范或候选事项中。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变文档工作区三分契约；
2. 改变正文区、studies 区或 sources 区的事实源性质；
3. 新增、删除或重命名应用剖面或专题子文档；
4. 允许正文区直接以 studies 或 sources 作为权威依据；
5. 改变文档与工作对象之间的权威边界；
6. 新增、替换或扩大文档检查 Code 实现的判定范围，并可能影响规范结论、吸收结论或文档治理通过条件。

文档基础检查至少包括：

| 检查项 | 标准 |
|---|---|
| 文档工作区 | 文档位于正确工作区和正确分区 |
| 命名 | 文件名表达稳定主题，重命名后引用已同步 |
| 章节编号 | 正文章节使用阿拉伯数字层级编号 |
| 章节引用 | `§` 引用目标真实存在 |
| 定义归口 | 规则、字段、状态、术语、流程或目录事实写入最小权威归口文档；未生效文档未被当作权威归口 |
| 引用类型 | 上位依据、相关规范、正文依据引用、消费引用、关联引用、来源引用、导航引用和审计追溯按最低充分级别使用，未把导航、追溯或主题相关提升为强约束引用 |
| 引用边界 | 正文区未以 studies/sources 作为权威依据；引用字段基于当前文档真实读取、约束、消费、同步或检查义务设置 |
| 反向补全 | `相关规范`、上位依据、关联对象、来源、同步义务或正文规则未仅因被下游引用、消费、登记或提到而反向补写 |
| 来源与关联 | studies/sources 已声明真实来源；关联工作对象只写入 `关联对象`，不得替代来源 |
| 吸收关系 | studies/sources 结论已写入权威吸收出口后才生效 |
| 对象边界 | 文档未替代工作对象状态、验收或关闭证据 |
| 子文档结构 | 子文档头部字段、父规范路径、父子引用和章节引用可解析；未被误识别为普通正式规范 |
| 子文档归口 | 子文档只承载应用剖面特例、专题细则、格式规则、检查规则、消费规则或适配规则，未复制父规范通用规则 |

### 9.1 文档检查 Code 缺口处理

当某项文档检查已经被规范要求，但现有 Code 实现无法覆盖该检查时，AI 不得直接沿用不适配的实现得出通过结论，也不得仅以人工阅读替代确定性检查结论。

AI 应按以下顺序处理文档检查 Code 缺口：

1. 明确检查需求：说明要检查的对象、规则来源、输入范围、预期失败条件和输出格式；
2. 判断是否已有适配 Code 实现：若已有实现只需小范围扩展，应先扩展既有实现；若现有实现假设与当前文档工作区冲突，应视为 Code 缺口；
3. 按 `specs/07-Code确定性执行实现规范.md` 判断 Code 需求准入，需求成立时实现覆盖当前检查需求的最小确定性校验；
4. 按 `specs/07-Code确定性执行实现规范.md` 验证 Code 实现本身，至少使用一个应通过样例和一个应失败样例，或使用等价的正反验证方式，证明实现能识别目标规则；
5. 运行 Code 实现检查目标文档；
6. 将 Code 需求、实现位置、验证方式和检查结果写入本次任务记录或相关工作对象；
7. 若当前任务不能实现对应 Code，应记录缺口、降级检查方式和残留风险；该降级不得被表述为完整通过。

文档检查实现满足确定性执行要求，也属于 Code 构成要素。新增、扩展、测试、修改、维护或删除文档检查 Code 实现时，应同时遵守 `specs/07-Code确定性执行实现规范.md`；若该 Code 实现需要在不同开发环境中暴露为命令、脚本入口或自动化检查，还应由 `specs/04.02-LDVH能力资产与落地保障规范.md` 解释具体能力资产关系。
