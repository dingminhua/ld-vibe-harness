# V4 环境接入规范与安装验证行动模板准入调查

> 记录性质：本文依据 `specification-model-foundation` §13 与 `action-template-foundation` §5，汇总环境接入规则责任和安装验证行动结构的既有调查、承载比较与准入边界。本文不是规则源，不授予规范、模板、adapter、安装或环境接入效力。

## 1. 调查结论

V4 需要两项互相分离但前后衔接的当前来源：

1. 一份普通规范，唯一定义外部环境连接同一 Helper 时的协议映射、能力不足交还、静态安装与真实触发区分、安装生命周期及回滚成立条件；
2. 一份具体行动模板，组织一次 LDVH 环境接入的现状发现、方案形成、授权、安装、真实验证、失败回滚与交还。

第一项使用既有审定身份 `spec_id: "09"`、`spec_key: "environment-integration"` 和名称《环境接入规范》。第二项不得占用已经 active 的 30–32；其最终编号只承担路径排序，不改变模板责任或稳定 `template_key`。

`LDVH-GOVERNED-PROJECTS.yaml` 的位置、字段、发现、有效性和管辖判定继续由 02 唯一定义，不从 02 移入 09。安装行动可以在 Human 明确授权时调用 02 已定义的配置能力，但安装 LDVH 不自动登记或修改管辖项目。

## 2. 不使用候选名称表达规则对象

准备约束的对象是：外部 AI/开发环境中的事件、工具调用、工作对象上下文和环境能力，如何经单一薄接入单元转换为 Helper 请求；Helper 结果如何忠实返回环境；这种连接如何被安装、检查、真实触发、升级、禁用、卸载和证明回滚。

准备组织的重复行动是：围绕一个明确目标环境和作用范围，发现当前状态，确认 Helper 与规则源前置，形成可检查方案，取得副作用授权，执行安装或变更，分别完成静态回读、Helper 直调和环境真实触发验证，在失败时恢复原状，并交还已验证、未验证和残留范围。

| 候选规则 | 已有来源 | 处置 |

| Helper 请求、响应、部分结果和能力声明 | 04 已完整承担 | 09 定义协议转换必须忠实，不复制字段闭集 |

移除已有来源后，仍有一组独立适用、独立失败且需要长期稳定位置的环境连接规则，不能无损放入 02、04、07、具体 adapter 或行动模板。

## 4. 承载位置比较

| 位置 | 适合承载 | 不适合承载 | 结论 |
|---|---|---|---|
| 02 正文 | 管辖配置和工作对象解析 | 环境协议、安装生命周期和真实触发 | 不扩张 02 |
| 04 正文 | Helper 外部服务契约 | 厂商环境如何连接、安装与卸载 | 不让 Helper 反向知道环境 |
| 07 正文 | Code 与 tests 的共同工程要求 | 环境接入的产品和外部契约 | 实现消费规则，不定义规则 |
| 授权附件 | 已由父规范定义的字段表或矩阵 | 尚未成立的核心环境规则 | 不用附件建立责任 |
| 具体 adapter 来源 | 一个厂商的稳定协议与安装接口 | 跨环境共同边界 | 仅在具体环境需要时另审 |
| 行动模板 | 重复安装、验证和回滚步骤 | 接入成立条件和规则权威 | 另建配套模板 |
| 独立普通规范 | 跨环境稳定连接、生命周期和证据规则 | 厂商实现细节 | 建立 09 |

## 5. 正例、反例、独立失败与变化原因

正例：

1. adapter 收到环境事件后保留目标对象和缺失字段，调用同一 Helper，并把 `partial` 或拒绝忠实返回；
2. 安装文件可见但尚未取得真实自动触发证据时，只声明静态安装已观察，不声明环境已经接入；
3. 卸载后真实确认环境不再自动触发 LDVH，同时保留安装前未知用户配置；
4. 目标环境不支持阻断能力时如实降级为提示或不可承接，不伪造强制执行。

反例：

1. 修改 `LDVH-GOVERNED-PROJECTS.yaml` 字段或管辖判定；该责任属于 02；
2. 在 09 中列出 Codex、WorkBuddy 或其它厂商事件闭集和固定路径；这些属于具体环境来源；
3. 在行动模板中发明“安装成功”条件；成立条件必须来自 09 和具体环境来源；
4. 因包、文件、Hook 或 manifest 存在就声明 `integrated`；静态存在不能证明真实连接。

独立失败场景：Helper 本身正确且可直接调用，但 adapter 错映射工作对象、吞掉拒绝、未被环境自动触发、卸载后仍残留触发，或破坏用户既有 Hook。上述失败不能由 02、04 或 07 的通过结果解释或排除。

独立变化原因：Helper 契约和管辖配置不变时，目标环境协议、权限、事件、安装接口及真实触发能力仍会变化；某一 adapter 变化不应迫使跨环境共同规则复制到其它 adapter。

## 6. V1–V8 净价值

09 主要提升 V1、V3、V4、V5 和 V7：AI 能找到唯一接入入口，识别环境能力和授权边界，按真实证据推进安装与验证，并向 Human 清楚交还断点、失败和回滚。真实触发和恢复证据也为 V6 提供环境前置。

新增一份规范会增加一次来源发现和跨文件读取成本。该成本通过以下边界控制：09 不复制 02 配置、04 服务字段、06 模板共同结构、07 实现细节或厂商协议；具体安装时由配套模板精确回指 09 的必要章节。相对于每个 adapter 自建安装与“已接入”语义，单一规范的净价值成立。

## 7. 历史资产处置

V3 `10-安装与配置规范` 中的管辖项目配置、target-first、Git worktree 身份已经由 V4 02 承接，不进入 09。V3 的固定 `check -> plan -> apply -> verify` 状态机、环境策略枚举、runtime receipt、固定 lifecycle 事件、安装路径和命令不直接恢复。

V3 `30-安装配置与验证行动模板` 证明安装、验证、断点恢复和失败回滚具有重复价值，但其中固定阶段、厂商事件、用户提示格式和 V3 状态分类不取得 V4 效力。V4 模板只保留稳定关系：发现现状、形成方案、取得授权、执行、静态回读、真实触发、失败回滚和如实交还。

V3 环境安装回滚检查表只作为失败模式输入。若未来多个具体 adapter 需要同一稳定机器字段表，再按 01 判断是否为 09 建立授权附件；当前不为迁移历史附件而预建字段闭集。
