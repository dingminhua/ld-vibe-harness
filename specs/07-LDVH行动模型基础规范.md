## 三、行动模型的定义与定位

### 3.1 行动模型的定义

LDVH 行动模型是 LDVH 对 AI 在项目中如何行动的执行控制建模，通过定义 Context（AI 行动前应获得的最小可行动上下文）、Scenario（AI 如何识别当前任务场景）、Gate（AI 何时必须暂停并请求人确认）、规则适用、Skill 进入、Agent 调度、事实源回写和证据留存等内容，约束 AI 的执行行为，确保 AI 稳定、可控地工作。

### 3.2 行动模型的核心特征

行动模型必须具备以下核心特征：

1. **以 AI 为中心**：行动模型以 AI 执行者为第一服务对象，信息组织方式、事实源读取、场景识别、工具选择等首先满足 AI 的需求；
2. **基于事实源**：行动模型依赖 Git 文件事实源，不依赖聊天记忆、工具缓存或数据库派生视图；
3. **场景可识别**：行动必须有明确 Scenario 识别条件，使 AI 能判断何时进入该行动；
4. **Context 最小可行动**：行动必须定义执行前需要读取的最小上下文，避免过载或缺失关键依据；
5. **Human Gate 优先**：关键行动必须触发 Human Gate，等待人类确认后方可继续；
6. **证据留存**：AI 执行的关键步骤必须留下可追溯的证据；
7. **事实回写**：AI 完成执行后必须按事实源边界把稳定事实写回项目；
8. **机制可适配**：行动可以说明 Rules、Skill、Agent 和工具如何参与，但不得替代 04、05、06 中对应机制、工具和对象规则。

### 3.3 行动模型与自由执行的区别

| 维度 | 自由执行 | 行动模型约束下的执行 |
|---|---|---|
| 上下文来源 | 聊天记忆、临时信息 | Git 文件事实源、结构化 Context |
| 场景识别 | 凭感觉、无明确规则 | 按 Scenario 规则明确识别 |
| 约束机制 | 无明确约束 | 规则、Gate、状态机多重约束 |
| Skill / Agent | 随意调用或混用 | 按行动模型和 04 系列机制边界选择 |
| 人类确认 | 随意、无明确触发点 | Human Gate 明确触发条件 |
| 证据留存 | 无强制要求、仅聊天记录 | 必须按规范留存可追溯证据 |
| 事实回写 | 随意、可能不回写 | 必须按事实源边界回写 |
| 可追溯性 | 弱、仅聊天历史 | 强、Git 文件事实源 + 结构化证据 |

## 四、行动模型模型

### 4.1 行动模型模型定义

行动模型模型是 LDVH 对某一类 AI 行动控制事实的标准化建模结构，用于统一描述该行动的行动定位、适用场景、准入条件、事实源边界、Context 要求、Scenario 识别、执行流程、Gate 触发条件、Skill 和 Agent 调度、工具协作、事实源回写、证据留存、Human Gate、落地初始化、落地审计、合规检查和待补齐事项。

每个 41-69 具体行动规范，都是一个具体行动模型模型的定义文档。

### 4.2 行动模型模型的标准组成

一个行动模型模型应包含以下内容：

1. 行动定位与适用场景；
2. 准入条件；
3. 事实源边界；
4. Context 要求；
5. Scenario 识别；
6. 执行流程；
7. Gate 触发条件；
8. Skill 和 Agent 调度；
9. 工具协作适配；
10. 事实源回写要求；
11. 证据留存要求；
12. Human Gate；
13. 附件型实践子文档按需拆分规则；
14. 落地初始化；
15. 落地审计；
16. 合规检查；
17. 待补齐事项。

### 4.3 行动模型模型与行动执行

行动模型模型定义行动类别的规则，行动执行是项目或会话中按模型完成的具体过程。

行动模型模型承载于 `specs/40-69`。行动执行过程中产生的稳定事实不得停留在聊天、Skill 输出、Agent 输出或工具缓存中，必须依据 `specs/03-事实源边界与承载规范.md` 和对应生产对象规范写回 `ldvh-base/`、`docs/`、`specs/` 或其他权威位置。

### 4.4 行动模型模型与生产对象

行动模型控制 AI 如何行动，生产对象承载工程生产事实。两者关系如下：

| 维度 | 行动模型 | 生产对象 |
|---|---|---|
| 核心问题 | AI 如何读取、判断、执行、停下和回写 | 项目事实如何结构化、流转和沉淀 |
| 规范区段 | `specs/40-69` | `specs/10-39` |
| 实例事实 | 行动执行结果按事实类型回写 | 对象实例承载于 `ldvh-base/` |
| 关键约束 | Context、Scenario、Gate、回写、证据 | 准入、字段、状态机、验收和对象关系 |

行动模型可以创建、更新、检查或引用生产对象，但不得重新定义生产对象字段、状态机、验收标准或对象实例事实源边界。

### 4.5 行动模型模型与工具实现

工具可以依据行动模型模型开发上下文包生成、Scenario 辅助识别、Gate 提示、证据聚合、回写校验和受控写入能力。工具实现不得替代行动模型模型本身，也不得绕过行动模型定义的事实源边界和 Human Gate。

### 4.6 行动模型文件命名与附件型实践子文档

41-69 主文件均为具体行动规范，文件名不重复“行动模型规范”字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

行动模型主文档必须完整定义行动模型。行动模型附件型实践子文档用于在主模型完整定义后，按需承接某个行动模型围绕 Rules、Skill、Agent、Tools 和 Web 的机制实践内容。附件型实践子文档不重新定义行动模型，不是模型完整性的默认要求，不得为空占位。

具体行动规范应在主文档中定义 Context、Scenario、Gate、执行流程、回写要求、证据要求、Skill 和 Agent 调度、工具协作、落地初始化、落地审计和合规检查。若某类 Rules、Skill、Agent、Tools 或 Web 实践内容复杂、需要独立维护，且经 Human Gate 确认，可创建对应附件型实践子文档。主文档应保留摘要、适用条件和引用，不得把行动核心规则迁移到子文档中。

附件型实践子文档统一命名如下：

| 编号 | 文件名 | 内容 |
|---|---|---|
| `NN.01` | `NN.01-Rules.md` | Rules 实践内容 |
| `NN.02` | `NN.02-Skill.md` | Skill 实践内容 |
| `NN.03` | `NN.03-Agent.md` | Agent 实践内容 |
| `NN.04` | `NN.04-Tools.md` | Tools 实践内容 |
| `NN.05` | `NN.05-Web.md` | Web 实践内容 |

`NN.01-Rules.md`、`NN.02-Skill.md`、`NN.03-Agent.md`、`NN.04-Tools.md`、`NN.05-Web.md` 均为附件型实践子文档。行动自身的 Context、Scenario、Gate、执行流程、回写要求和证据要求应留在 `NN` 主文件，不应转移到附件型实践子文档。

### 4.7 落地初始化、落地审计与合规检查

行动模型规范应按需要定义落地初始化、落地审计和合规检查要求。三者术语边界依据 `specs/01-specs文档结构与术语规范.md` §7.6；本文只规定行动模型在这些章节中应覆盖的行动模型相关内容。

落地初始化应说明该行动模型进入项目实践时需要创建或确认的 Rules 摘要、Skill、Agent 可用性清单、Tools 校验能力、Web 展示入口、索引引用、初始化产物、暂缓项和 Human Gate。

落地审计应说明如何审查该行动模型的实践是否真实落地、持续有效、与 Git 文件事实源一致、未绕过 Human Gate，并识别初始化缺口、过期实践和需要整改的附件型实践子文档。

合规检查应说明行动规范写作、Scenario 识别、Context 读取、Gate 触发、Skill 和 Agent 调度、工具协作、事实源回写、证据留存和 Human Gate 是否符合本行动模型和上位规范。

### 4.8 完整方案形成流程

行动模型完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义行动模型；
2. 定义 Context、Scenario、Gate、执行流程、Skill 和 Agent 调度、工具协作、回写要求和证据要求；
3. 定义落地初始化计划、落地审计要求和合规检查标准；
4. 判断 Rules、Skill、Agent、Tools 或 Web 实践是否复杂到需要独立维护；
5. 仅在按需且经 Human Gate 确认时创建附件型实践子文档；
6. 修改规范、附件型实践子文档、协作机制或事实源时记录 Change。

## 五、行动模型准入与分类原则

### 5.1 行动分类原则

LDVH 行动模型可按治理用途分为以下几类：

1. **初始化行动**：建立项目可被 LDVH 管辖的基础上下文、目录、规则和对象实例承载能力；
2. **需求规划行动**：将人的输入、意图和资料转化为可追踪、可执行、可验证的事实源；
3. **任务执行行动**：推动最小执行对象流转，记录证据、阻塞、风险、变更和关闭条件；
4. **Review 行动**：检查执行结果、证据、关闭条件和 Human Gate；
5. **审计行动**：检查项目状态、事实源、规则、对象、工具和行动模型是否持续合规；
6. **协作增强行动**：通过 Skill、Agent、工具或多角色分析增强 AI 的判断质量，但不替代事实源和 Human Gate；
7. **管理行动**：管理生产对象、规则、协作机制和事实源边界的受控变更。

### 5.2 行动清单归属

具体行动清单、编号归属、维护状态和区段关系由 `specs/40-行动模型集合索引.md` 维护。本文只定义行动模型的通用分类和准入原则。

### 5.3 预留编号区段

编号区段 51-69 预留用于未来新增行动，不得未经 Human Gate 确认提前占用。

### 5.4 准入条件原则

一个流程需要满足以下条件之一，才应成为行动模型：

1. **需要稳定控制 AI 行动**：该流程需要约束 AI 读取、判断、执行、停止和回写方式；
2. **需要明确 Scenario 识别**：该流程存在可识别的任务场景，且错误进入或漏进入会影响执行质量；
3. **需要明确 Context 要求**：该流程依赖一组稳定的最小可行动上下文；
4. **需要 Gate 控制**：该流程包含必须等待人确认或条件满足后才能继续的节点；
5. **需要跨机制协作**：该流程需要协调 Rules、Skill、Agent、工具和生产对象；
6. **需要事实源回写和证据留存**：该流程产出稳定事实、证据、决策、任务、变更或审计结果；
7. **不成为行动模型就会导致 AI 行动边界漂移**：该流程如果不结构化，就会导致 AI 凭聊天记忆执行、绕过 Human Gate 或无法追溯。

不满足以上条件的内容，应按其性质分流：
- 一次性局部执行策略 → 留在当前执行上下文；
- 可复用但可在主上下文完成的轻量流程 → 评估是否作为 Skill；
- 只需独立上下文或专业审查 → 评估是否调用 Agent；
- 长期硬约束 → 写入 specs/ 或 `.trae/rules/`；
- 稳定生产事实 → 按 10-39 对象规范写入 `ldvh-base/`；
- 外部参考资料 → 写入 `specs/refs/`。

## 六、行动模型的通用规范

### 6.1 Context（上下文）原则

Context 是由事实源组织出的 AI 执行输入、任务背景和行动依据。

Context 的目标是给 AI 提供足够但不过载的最小可行动上下文，让 AI 能够：

1. 理解当前项目的身份和边界；
2. 理解当前任务的背景和目标；
3. 知道可用的规则、Skill、Agent 和工具；
4. 知道事实源的边界和回写位置；
5. 知道何时触发 Human Gate。

Context 的组织遵循以下原则：

1. **最小化原则**：只包含 AI 执行当前行动所需的最小信息；
2. **结构化原则**：以结构化方式组织，便于 AI 理解和处理；
3. **事实源原则**：所有稳定信息都来自 Git 文件事实源；
4. **动态原则**：根据当前 Scenario 动态调整 Context 内容；
5. **可追溯原则**：Context 应能回溯到原始事实源文件。

### 6.2 Scenario（场景）原则

Scenario 是 AI 当前所处的任务类型、协作模式和执行入口。

Scenario 的目标是让 AI 能够：

1. 识别当前任务属于什么行动类型；
2. 选择合适的执行入口；
3. 加载对应的规则和 Context；
4. 判断是否进入 Skill、调用 Agent 或使用工具；
5. 判断是否应触发 Human Gate。

Scenario 的识别遵循以下原则：

1. **基于事实源**：根据 Git 文件事实源和用户当前输入识别当前场景；
2. **明确规则**：每个具体行动规范都应定义识别规则；
3. **优先级**：多个场景同时匹配时，按具体行动规范或 40 索引中的关系说明选择；
4. **Human Gate**：高影响场景切换可能触发 Human Gate；
5. **可降级**：条件不足时应降级为主上下文分析或询问用户，而不是强行进入行动。

### 6.3 Gate（门禁）原则

Gate 是需要人确认或满足条件后才允许继续的控制点。

Gate 分为以下类型：

1. **Human Gate**：必须由人类确认后方可继续；
2. **条件 Gate**：满足特定条件后方可继续；
3. **审批 Gate**：必须由特定角色审批后方可继续。

Gate 的执行遵循以下原则：

1. **先停再问**：识别到 Gate 时，AI 必须先暂停执行，再请求人类确认；
2. **明确说明**：AI 必须明确说明触发 Gate 的原因、影响范围和建议确认事项；
3. **不可绕过**：AI 不得绕过 Gate 继续执行；
4. **证据留存**：Gate 的确认过程必须留下可追溯的证据；
5. **回写联动**：Gate 结果形成稳定事实时，应按事实源边界回写。

### 6.4 规则适用原则

规则是 AI、人和工具必须遵守的行为边界。

规则的加载遵循以下原则：

1. **优先级**：项目规则优先于 LDVH 基础规则；
2. **不冲突**：规则之间不得冲突，冲突时按优先级处理，并评估是否需要修正规则；
3. **可追溯**：规则必须有明确的来源和版本；
4. **机制回指**：Rules 机制设计和治理以 `specs/04-LDVH-AI协作规范.md` 和 `specs/04.01-Rules机制规范.md` 为准；
5. **Human Gate**：规则变更必须触发 Human Gate。

### 6.5 Skill 进入原则

Skill 是 AI 可使用的可复用流程。行动模型可以在具体场景中说明何时建议进入 Skill，但 Skill 的准入、命名、部署、输出和事实源回写边界由 `specs/04-LDVH-AI协作规范.md` 和 `specs/04.02-Skill机制规范.md` 定义。

Skill 进入在行动模型中的通用原则：

1. **场景匹配**：根据当前 Scenario 判断是否需要可复用流程；
2. **机制回指**：Skill 准入和边界必须回指 04 系列规范；
3. **规则约束**：Skill 的执行必须遵守规则、事实源边界和行动模型；
4. **不得越权**：Skill 不得自行调度 Agent，不得替代 Human Gate；
5. **证据留存**：Skill 产生的稳定事实必须回写到 Git 文件事实源后才成为稳定事实。

### 6.6 Agent 调度原则

Agent 是 AI 代理执行能力。行动模型可以在具体场景中说明何时建议调度 Agent，但 Agent 的创建、调用、定义摘要、生命周期、权限边界和事实源回写边界由 `specs/04-LDVH-AI协作规范.md` 和 `specs/04.03-Agent机制规范.md` 定义。

Agent 调度在行动模型中的通用原则：

1. **场景匹配**：根据当前 Scenario 判断是否需要独立上下文、结论隔离、并行委派或不同权限边界；
2. **机制回指**：Agent 创建或调用治理条件必须回指 04 系列规范；
3. **规则约束**：Agent 的执行必须遵守规则、事实源边界和行动模型；
4. **Human Gate**：关键 Agent 的创建、调度、权限调整或写入动作必须按对应规范评估 Human Gate；
5. **不替代事实源**：Agent 不得成为事实源，只能读取、分析和建议；
6. **能力前提可检查**：具体行动可以声明某类 Agent 能力为增强模式前提；前提不满足时，应降级、暂停或提示用户，而不是假装已具备能力。

### 6.7 工具协作原则

工具可以辅助 AI 读取事实源、获得结构化上下文、执行确定性校验、准备受控写入、展示 Gate 和证据，但工具不得替代 AI 的场景判断，也不得直接调用或模拟 AI 决策。

工具协作遵循以下原则：

1. Tools 辅助和 Web 展示的分工以 `specs/05-LDVH工具基础规范.md` 为准；
2. 工具输出不是最终事实源；
3. 工具写入必须受控，且不得绕过事实源边界、对象规范、行动模型或 Human Gate；
4. 工具能力不足时，行动模型不得假定工具已完成校验或回写；
5. 工具运行中产生的稳定事实必须回写 Git 文件事实源后才成立。

### 6.8 事实源回写原则

事实源回写是 AI 完成执行后把稳定事实写回项目的过程。

AI 完成执行后的事实源回写，依据 `specs/03-事实源边界与承载规范.md` §七定义的回写条件执行，本文不重复维护。行动模型的适配说明如下：

1. **行动模型回写触发**：AI 按 Scenario 执行完毕后，应判断执行结果是否包含稳定事实；若包含，必须按 03 §七回写；
2. **回写与 Gate 联动**：关键事实的回写应评估 Human Gate，依据本文、具体行动规范和相关基础规范判断；
3. **对象回写回指**：任务、证据、变更、风险、决策等对象实例回写必须遵守 10-39 具体生产对象规范；
4. **机制输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实；
5. **报告回写分流**：审计报告、分析报告或管辖项目资料应按 02、03 和具体行动规范判断进入 docs/、ldvh-base/ 或 specs/。

### 6.9 证据留存原则

行动模型的证据留存遵循以下原则：

1. **关键步骤留证**：Context 读取、Scenario 判断、Gate 触发、Skill / Agent 调度、工具校验、事实源回写等关键步骤应留下可追溯证据；
2. **证据归属明确**：证据属于生产对象实例时，按 Evidence 或相关对象规范写入 `ldvh-base/`；属于报告时，按 docs/ 边界写入；属于规范变更时，记录 Change；
3. **证据可验证**：证据应说明来源、时间、执行者、结果和影响范围；
4. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
5. **关闭前可追溯**：涉及任务、审计或 Review 的行动，在关闭前应能追溯关键证据。

## 七、与 40-69 具体行动规范的关系

### 7.1 40 行动模型集合索引

40 是行动模型集合索引，不定义具体行动流程，只提供该区段内文档的清单、关系映射、状态和维护信息。

### 7.2 41-69 具体行动规范

41-69 是具体行动规范，每个规范定义一个具体行动模型。具体行动规范应依据 §4.2 定义的行动模型模型标准组成展开，并在具体行动语境下定义更具体的行动规则。

具体行动规范不得在缺少说明的情况下省略 §4.2 中的标准组成；如某一组成项暂不适用或待补齐，应在对应章节说明原因或进入待补齐事项。

### 7.3 关系原则

本文与 40-69 具体行动规范的关系遵循以下原则：

1. 本文定义行动模型的通用规则和行动模型模型的标准组成，40-69 定义具体行动模型；
2. 具体行动规范不得与本文的通用规则矛盾；
3. 具体行动规范可以在本文的通用规则基础上，定义更具体的规则；
4. 发生冲突时，以本文的通用规则为准，除非具体行动规范明确说明例外情况并经 Human Gate 确认。

## 八、Human Gate 与检查要求

### 8.1 Human Gate 触发条件

以下情况应评估 Human Gate：

1. 新增行动；
2. 删除行动；
3. 重命名行动；
4. 重排行动编号区段；
5. 改变行动模型的通用规则；
6. 改变行动模型模型的标准组成；
7. 改变 Context、Scenario、Gate 的定义；
8. 改变事实源回写的原则；
9. 改变 Human Gate 的触发条件；
10. 新增、删除、重命名或改变行动模型附件型实践子文档；
11. 改变 Skill、Agent 或工具在行动模型中的调度边界；
12. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 8.2 检查要求

行动模型规范写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 行动定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、生产对象、行动模型、Context、Scenario 和 Gate 术语一致 |
| 模型组成 | 具体行动规范覆盖行动模型模型的标准组成，缺项已说明原因 |
| 附件型实践子文档 | 已说明是否需要附件型实践子文档；如创建，已确认按需、非空、不替代主模型且经 Human Gate |
| 落地初始化 | 已按需要定义设计进入实践的初始化计划、初始化产物和暂缓项 |
| 落地审计 | 已按需要定义实践是否真实落地并持续有效的审计要求 |
| Context | Context 来源明确且符合事实源边界 |
| Scenario | Scenario 识别规则明确，避免凭感觉进入行动 |
| Gate | Gate 触发条件明确，确保关键步骤必须等待人类确认 |
| Skill / Agent | 机制使用符合 04 系列规范，不由 Skill 调度 Agent |
| 工具协作 | 工具边界符合 05 系列规范，未让工具替代事实源或 AI 判断 |
| 事实源回写 | 符合 `specs/03-事实源边界与承载规范.md` 的事实源边界原则 |
| 证据留存 | 关键步骤有可追溯证据要求 |
| 合规检查 | 已定义行动规范写作、Scenario、Context、Gate、回写、证据和 Human Gate 的符合性检查标准 |
| 文件命名 | 主文件和附件型实践子文档命名符合 §4.6，未重复维护区段性质或行动归属 |
