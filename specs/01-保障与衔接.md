## 1. 价值判断

本文存在的价值，是把 00 的理念、构成要素和 V1-V10 从“应该如此”推进到“可以被保障并接入协作环境”。没有保障与衔接，规则只能停留在规范正文、聊天提醒或 AI 自觉，无法稳定形成入口提示、执行拦截、验证证据、事实源回写和缺口分流。

本文服务 00 的 AI 第一目标：让 AI 在读取、判断、执行、验证、回写和交还时，知道每条关键规则如何被保障、由谁承接、缺口在哪里、何时必须暂停。本文不新增构成要素，而是定义五类构成要素、事实源和协作环境之间的保障与衔接层。

## 2. 权威依据

本文承接 `specs/00-理念与构成.md`。

本文不得重定义 00 的存在理由、AI 第一服务对象、五类构成要素、事实源边界、保障与衔接层或 V1-V10。若本文与 00 冲突，以 00 为准。

`specs/04-Specs基础规范.md` 定义 specs 正文结构、附件边界和 Code 解析入口。本文定义保障需求和衔接链路；04 定义这些内容在 spec 中如何被稳定写入、引用和检查。

`specs/02-AI行为规范.md` 定义 AI 执行者如何遵守价值门、主控责任、诊断分流、Human Gate 和停止条件。02 的行为规则必须通过本文的保障需求与衔接规则说明其落地边界。

## 3. 归口边界

本文归口定义保障与衔接基础规则：

1. 规则要求如何形成保障需求；
2. LDVH 能力、能力组合和能力缺口的共同口径；
3. 保障需求最小字段；
4. 保障需求的消费时机；
5. 承接归口、承接机制的类型和边界；
6. 环境入口、Runtime Protocol、canonical event 和 trigger source 的上位语义；
7. 行动指南的输入、输出、边界和缺口暴露要求；
8. receipt、evidence 和 diagnostic 的基础语义；
9. 承接缺口如何分流；
10. 什么情况下不得声称保障已经生效。

本文不归口定义具体流程、具体字段模型、具体命令输出、具体页面、具体环境入口 registry、具体 Git message、具体测试用例或具体环境安装方式。相邻内容需要规则时，应进入行动模板、事实模型、Code、Web、本文外部衔接规则、事实源与 Git 溯源或测试规范承接。

## 4. 适用范围

本文适用于 LDVH 中所有需要说明“规则如何不落空”的内容，包括 specs 规则、AI 行为要求、事实对象状态要求、行动模板 Gate、Code 诊断、Web 展示、环境入口、Hook、Rules、Skill、Agent、Git 溯源、测试验证和 Human Gate。

凡是正式 spec 提出“必须、不得、应当、需要验证、需要回写、需要停止、需要 Human 确认、需要 Code 检查、需要 Web 展示或需要环境入口”的规则，均应判断是否形成保障需求，并说明其内部保障、外部衔接、行动指南承接方式或缺口。

## 5. 内部保障

内部保障回答：LDVH 凭什么让规则不落空。它关注规则要求如何形成保障需求，保障需求需要哪些能力或能力组合，由哪个承接机制接住，输出什么证据，并在缺口出现时如何分流。

### 5.1 保障、能力、承接与衔接定义

规则说明“应该怎样”。保障说明“如何防止规则落空”。能力说明“LDVH 凭什么提供保障”。承接是保障链路内部的动作，说明“由哪个构成要素、保障衔接位置、环境入口机制或 Human Gate 接住保障”。衔接说明 LDVH 如何进入具体协作环境，使保障能够被读取、触发、执行、验证、留证、回写和分流。

保障链路如下：

```text
规则要求
  -> 保障需求
  -> LDVH 能力 / 能力组合
  -> 承接机制
  -> 执行 / 提示 / 拦截
  -> receipt / evidence
  -> 验证 / diagnostic
  -> 事实源回写 / 缺口分流
```

保障需求不是规则本体之外的新价值来源，也不是事实源。它是规则进入技术环节的可消费表达。承接机制不是事实源；承接机制输出只有按事实源边界受控回写到 Git 可追踪文件事实源后，才可能成为稳定事实；Git 提交记录只作为溯源证据，不成为独立事实源。

### 5.2 LDVH 能力与能力缺口

LDVH 能力不是单个工具、Hook、Skill、页面或脚本，而是 LDVH 为减少 AI 负担、保障构成要素应用而形成的能力面。能力可以由规范体系、事实模型、行动模板、Code、Web、环境入口、测试、Git 和 Human Gate 共同形成。

能力资产或承载物只是能力的具体承载，例如 Rules 薄引用、Skill、Agent、Hook、Code、Web、命令、测试或页面。本文只定义能力、能力组合和能力缺口的共同口径；具体资产登记、安装、schema、页面和环境适配由后续归口规范承接。

环境能力是 Codex、Claude Code、IDE、Shell、CI 或其它协作环境提供的入口和机制。环境能力可以被 LDVH 使用，但不自动成为 LDVH 能力本体；只有回到本文定义的保障需求、承接机制、证据边界和缺口分流后，才能声称被 LDVH 保障链路消费。

能力缺口必须显式暴露。若某项保障需求缺少所需能力、能力组合、环境支持或承接机制，AI、Code、Web、行动模板或环境入口不得静默跳过，也不得把必要保障缺失降级为普通待补齐事项。

### 5.3 保障需求最小字段

正式 spec 提出保障需求时，至少应说明：

| 字段 | 要求 |
|---|---|
| 需求ID | 稳定标识，用于 Code、行动模板、环境入口、Web、测试和过程输出回指。 |
| 保障需求 | 要防止哪条规则落空，减少哪类 AI 负担。 |
| 来源依据 | 保障需求来自哪篇 spec、章节、附件、事实对象或证据。 |
| 所需能力 | 需要哪些 LDVH 能力、能力组合或环境能力；当前缺失时必须说明能力缺口。 |
| 消费时机 | 在什么行动时机必须被读取、检查、提示、拦截、验证或交还。 |
| 承接归口 | 由规范体系、事实模型、行动模板、Code、Web、保障与衔接层、环境入口、Git 溯源、测试或 Human Gate 中哪个主位置接住。 |
| 承接机制 | 具体通过规则入口、行动模板、Code、Web、Hook、Rules、Skill、Agent、测试、Git 或 Human Gate 中的哪些机制承接。 |
| 完成证据 | 什么 receipt、evidence、命令结果、Web 呈现、测试结果、Human 决策或 Git 记录可证明本次保障发生过。 |
| 阻断条件 | 哪些缺失、失败、冲突、不可验证或 Human Gate 未决会阻断当前行动或完成声明。 |
| 缺口分流 | 不能承接时回到哪个构成要素缺口、事实对象、行动模板候选、Human Gate 或待补齐事项。 |

字段可以由正文表格、授权附件、Code 派生结构或后续成员规范承载，但不得只存在聊天过程或一次性工具输出中。

### 5.4 消费时机

消费时机用于回答保障需求何时被 AI、Code、Web、环境入口、行动模板或 Human Gate 使用。

当前消费时机闭集由 `specs/attachments/01.Att.01-保障消费时机表.md` 承载。正式 spec 不得私自新增同义时机；需要新增、删除、重命名或改变消费时机含义时，必须修改本文或授权附件，并评估 Human Gate。

### 5.5 承接机制边界

承接机制可以包括：

| 承接机制 | 作用 | 边界 |
|---|---|---|
| Specs 正文 | 定义规则、保障需求和权威边界。 | 不替代执行、验证或事实源回写。 |
| 行动模板 | 将保障需求组织为 Context、Scenario、Gate、执行、验证、回写和分流。 | 不重写来源规则，不维护第二事实源。 |
| Code | 解析、校验、诊断、生成 read_plan、聚合和受控写入前检查。 | 不替代 AI 判断或 Human Gate。 |
| Web | 展示状态、风险、证据、验证结果和待确认事项。 | 不维护事实源，不替代行动判断。 |
| 环境入口 | 提供 Rules 薄引用、Hook、插件、入口可见和环境适配能力。 | 不证明当前环境已经完整支持 LDVH。 |
| 测试 | 提供可复现验证、回归检查和失败阻断依据。 | 不把测试通过升级为 Human 授权。 |
| Git | 记录 Git 文件事实源变更的溯源证据和提交说明。 | 不替代 Git 文件事实源、规则正文或对象状态。 |
| Human Gate | 完成授权、方向校正、风险接受或验收确认。 | 只能由 Human 完成，AI 和 Code 不得代替。 |

承接机制可以组合使用，但必须说明主承接位置和输出回指关系。多个机制共同承接同一保障需求时，不得形成互相竞争的权威副本。

### 5.6 Receipt、Evidence 与 Diagnostic

`receipt` 是某个保障消费、执行、确认或写入动作已经发生的回执。`evidence` 是用于支持判断、验证、关闭或溯源的证据。`diagnostic` 是对缺失、失败、风险、不可验证或不一致的结构化判断。

receipt、evidence 和 diagnostic 默认是过程输出，不自动成为事实源。需要长期溯源时，必须按事实源边界受控回写到 Git 可追踪文件事实源；Git 提交记录只用于证明文件变更和提交语义，不承载独立事实源。

AI 不得把 receipt 等同于规则满足，不得把 evidence 等同于 Human 授权，不得把 diagnostic 等同于最终结论。它们都必须回到主控 AI、事实源规则和必要的 Human Gate。

### 5.7 缺口分流

保障需求无法被承接时，必须区分：

| 类型 | 判断 | 处理 |
|---|---|---|
| `blocking` | 阻断当前行动、规则成立、完成声明、事实源回写或 Human Gate。 | 停止当前完成声明，修复、分流或交还 Human。 |
| `warning` | 不阻断当前行动，但影响风险、证据完整性或判断可信度。 | 明示风险和承接位置，不得静默。 |
| `follow_up` | 不阻断当前行动，但需要后续补齐。 | 写入对应事实源、待补齐事项或工作对象。 |
| `unverifiable` | 当前无法验证、验证范围不足或证据不可复现。 | 说明原因、影响范围和后续承接，不得声明已验证。 |

必要保障缺失不得降级为普通待补齐事项。若缺失支撑当前规则成立、关键行动、Human Gate、Stop Conditions 或完成声明，必须作为 blocker、Human Gate 或 Stop Condition 处理。

### 5.8 不得声称生效边界

出现以下情况时，不得声称保障已完整生效：

1. 只有规范正文要求，没有消费时机、承接机制或完成证据；
2. 只有 Code、Hook、Web、Skill、Agent 或测试输出，没有回指来源保障需求；
3. 只有环境入口资产文件存在，没有证明当前环境已接入；
4. 只有 receipt 或工具成功输出，但缺少主控 AI 判断、验证证据或 Human Gate；
5. 缺口、warning、blocker、unverifiable 没有分流位置；
6. 稳定事实停留在聊天、缓存、环境索引、Web 状态或工具输出中。

## 6. 外部衔接

外部衔接回答：LDVH 如何进入具体协作环境，使内部保障能力能够被读取、触发、执行、验证、留证、回写和分流。

### 6.1 环境入口边界

环境入口是 LDVH 面向外部协作环境暴露的入口层，可以包括 Rules 薄引用、Hook、插件、命令入口、环境说明或其它入口可见机制。环境入口的职责是让协作环境能够进入同一套保障消费语义，不是复制 specs 规则，也不是证明当前环境已经完整支持 LDVH。

支持 Hook 或插件的环境，可以通过环境事件触发保障消费。缺少 Hook 或插件的环境，可以通过 Rules 薄引用或等价入口让 AI 自觉进入保障消费。两条路径都必须回到同一套保障需求、消费时机、证据边界和缺口分流，不得形成两套互相竞争的规则体系。

### 6.2 Runtime Protocol 最小语义

Runtime Protocol 是 LDVH 暴露给协作环境的统一生命周期协议。不同环境可以有不同触发方式，但必须归一到同一套保障消费语义。

本文只定义 Runtime Protocol 的最小语义：

1. 识别当前事件属于哪个消费时机；
2. 标明触发来源，例如 Hook、Rules 薄引用、插件、手动等价入口或其它环境入口；
3. 携带足够上下文以判断目标、管辖范围、读写性质和已有 receipt；
4. 消费对应保障需求，输出 read_plan、检查结果、阻断、receipt、evidence、diagnostic 或行动指南输入；
5. 暴露能力缺口、环境缺口、不可验证范围和 Human Gate 未决事项。

本文不定义完整 payload schema、dispatcher 文件路径、命令参数、receipt 存储路径或环境安装方式。这些内容由 Code、本文授权附件、测试、事实源与 Git 溯源等承接。

### 6.3 Canonical Event 与 Trigger Source

`canonical event` 是 LDVH 内部消费保障需求的统一事件语义。`trigger source` 是同一事件来自哪个外部入口的来源说明。

当前可用的消费时机闭集仍以 `01.Att.01` 为准。若后续需要把用户输入、外部页面操作、自动任务或其它入口提升为新的消费时机，必须修改本文或授权附件，并评估 Human Gate。

canonical event 不得反向定义消费时机闭集。trigger source 不得改变规则权威，也不得让 Hook 路径、Rules 路径、插件路径或手动等价路径各自形成不同规则。

### 6.4 外部衔接不得固化的内容

本文不应固化具体 Hook 安装方式、插件目录结构、adapter 文件名、dispatcher CLI、payload 完整字段、receipt 文件路径、环境专属配置、Web 页面、测试用例或 Git commit-msg 细节。

这些内容应由 Code、本文授权附件、行动模板、测试、Web、Git 和事实源规范承接。本文只定义它们必须回到同一套保障消费语义，并说明不得声称生效的边界。

### 6.5 环境入口类型

环境入口必须先归入 `specs/attachments/01.Att.03-环境入口类型表.md` 的类型闭集，再声明接入状态。

`automated_hook` 是当前环境能自动触发、能阻断失败、能被安装状态检查复现的入口。入口是否满足该条件必须由状态检查、安装证据和失败处理共同证明。

`manual_entrypoint` 是 Code CLI、README 命令或外部调用方可以手动触发的入口。manual-ready 只能证明入口可用，不证明协作环境会自动触发，也不证明写入、完成声明或 Human Gate 已被拦截。

`external_adapter_candidate` 是后续外部环境、插件或 runtime adapter 可以接入的候选。候选必须等真实触发、稳定 payload、失败处理、安装状态、回滚方式和测试证据齐备后，才能升级为自动入口。

`removed_top_level` 用于 Rules / Skill 这类 V3 已取消的顶层机制。它们不是待启用入口；若后续需要入口可见能力，必须转为 repo instruction、外部包装、manual entrypoint 或正式环境 adapter，而不是恢复顶层目录机制。

### 6.6 接入状态声明

环境接入状态必须使用 `specs/attachments/01.Att.04-环境接入状态表.md` 的状态闭集。

状态声明必须区分：

1. `available`：文件、脚本或候选入口存在；
2. `manual_ready`：可手动或外部调用，但没有自动触发；
3. `integrated`：当前环境真实自动触发，失败可阻断，安装状态可复现；
4. `deferred`：后置，不阻断当前主线；
5. `removed_top_level`：V3 顶层机制已取消，不作为后置入口；
6. `absent`：没有可识别入口。

`environment_integrated=partial` 只能在至少一个真实自动入口 integrated，且其它入口边界如实声明时使用。具体当前环境状态应由环境状态检查命令、README 或实现域文档报告，不得手写成不可复核的长期规则。

Code、README、测试、迁移记录和 AI 完成声明不得把 `available`、`manual_ready`、`deferred` 或 `removed_top_level` 写成 `integrated`。

### 6.7 Runtime payload 与 receipt

runtime payload 字段由 `specs/attachments/01.Att.05-runtime-payload字段表.md` 承接。payload 至少应能表达 event、trigger_source、target_path、operation、task、acknowledged_paths、verification_evidence 和 session_id 等信息。

receipt 是过程输出和证据候选，不是事实源、授权、放行或 Human Gate 完成。receipt 可以帮助 AI 定性入口是否被调用、读取计划是否覆盖、诊断是否产生和缺口如何分流，但必须回到 03 的事实源边界和 09 的验证声明边界。

stdout-only receipt 只能作为当次过程输出。若后续需要稳定 receipt 存储，必须先补事实源回写规则、字段 schema、清理策略和测试，不得把临时 stdout 输出升级为事实源。

### 6.8 Rules 与 Skill legacy 边界

V3 不保留 `rules/` 或 `skills/` 顶层目录机制。Rules 和 Skill 只作为历史术语、来源材料或外部包装候选存在。

V2 Rules 的入口可见能力可以被转写为 repo instruction、环境薄引用、manual entrypoint 或外部 adapter 候选，但不得恢复 Rules 顶层规则源、Rules registry 或与 specs 并列的权威入口。

V2 Skill 的可复用工作流能力可以被吸收为行动模板步骤、Action Guide 提示、Code CLI 或外部包装候选，但不得恢复 Skill 顶层机制、Skill registry、Skill 执行闭环或用 Skill 输出替代主控 AI 判断。

若环境本身提供名为 Rules 或 Skill 的机制，V3 仍必须按本文重新分类其入口类型和状态；名称相同不等于 V3 顶层机制恢复。

### 6.9 安装、回滚与受管项目边界

安装、覆盖或卸载真实环境入口必须有安装目标、回滚方式、状态检查和验证命令。最小检查项由 `specs/attachments/01.Att.06-环境安装回滚检查表.md` 承接。

worktree-local Git Hook 只声明对应 Git 仓库的 commit message 校验入口已自动触发，不声明外部受管项目、其它 worktree、session start、pre tool use 或 completion claim 已接入。具体 Hook path、安装命令和回滚命令由实现域文档承接。

后续将环境入口接入受管项目时，必须复用 10 的 target-first、Git common-dir 和多目标边界。不得用当前 cwd、路径相似、repo 名称或用户意图替代受管项目解析。

## 7. 行动指南

行动指南回答：AI 每次行动前最终拿到什么。它是保障与衔接层面向 AI 当前行动的承接包，不是第三套规则体系。

### 7.1 行动指南定位

行动指南可以由 Code、环境入口、行动模板、AI 主控或后续专门机制共同生成或组织。它的职责是帮助 AI 快速判断当前行动应该读取什么、先做什么、何时停止、如何验证、如何分流。

行动指南不是规则源、授权器、事实源、测试结论或 Human Gate。行动指南输出必须回指来源依据和保障需求；无法回指时，只能作为过程建议或 diagnostic，不得作为完成证明。

### 7.2 行动指南输入

行动指南输入可以包括：

1. active specs 和授权附件；
2. 当前用户目标、raw input、cwd、target、session_id 和 trigger source；
3. 已有 read_plan、read_plan_consumed receipt、运行时 receipt 或 diagnostic；
4. 当前保障需求、消费时机、承接机制和阻断条件；
5. Code 关系定位输出、事实对象状态、Git 溯源信息或测试结果；
6. 能力缺口、环境缺口、Human Gate 状态和不可验证范围。

输入不足时，行动指南必须暴露 `missing_fields`、`capability_gap`、`unverifiable` 或 Stop Conditions，不得生成看似完整但不可验证的行动约束。

### 7.3 行动指南输出

行动指南至少应能表达：

| 输出 | 用途 |
|---|---|
| `task_read_plan` | 当前行动需要优先读取的事实源、规范、对象或证据。 |
| `next_queries` | 需要继续定位或展开时的后续查询。 |
| `stop_conditions` | AI 必须暂停、分流或进入 Human Gate 的条件。 |
| `validation_guard` | 完成声明、写入、提交或交还前需要验证的内容。 |
| `next_action` | 当前建议的下一步行动、暂停、追问或分流。 |
| `missing_fields` | 当前缺失但影响行动判断的信息。 |
| `capability_gap` | 当前保障能力、环境能力或承接机制缺口。 |
| `impact_summary` | 受影响的规范、事实对象、行动模板、Code、Web、测试或环境入口。 |
| `source_refs` | 输出依据回指到的 specs、附件、事实源、对象或证据。 |

这些字段是行动指南的语义契约，不要求当前阶段已经存在完整 Code schema。具体字段 schema、生成方式和测试由后续 Code、行动模板或本文外部衔接规则承接。

### 7.4 Fallback 与不可验证

若关系定位能力、Code 输出、环境入口或其它行动指南输入不可用，行动指南必须使用 fallback read_plan 或显式 diagnostic，并说明 fallback 的来源、覆盖范围和不足。

AI 不得确认空 read_plan 后进入写入、提交或完成声明。若当前无法形成足够行动指南，必须按 blocking、warning、follow_up、unverifiable 或 Human Gate 分流。

### 7.5 行动指南边界

行动指南不得替代 AI 主控判断、Human Gate、事实源、Hook 实际拦截、测试验证、Code 校验或具体行动模板。AI 按行动指南行动时，仍必须保留价值判断、归口判断、风险判断、验证声明和 Human Gate 交还责任。

后续 specs 可以配置行动指南应引用哪些规则、行动模板、事实源和验证方式，但不得另建与本文并列的行动入口机制。

## 8. 保障措施

本文通过以下机制保障自身规则被后续 specs 和技术环节消费：

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 三层职责承接要求 | 后续规范和机制必须区分内部保障、外部衔接和行动指南，不得把三者混成一个实现清单 | 本文 §5、§6、§7，00 上位定位，review | 架构治理 | 新增或修改保障与衔接规则时 |
| 保障需求入口要求 | 后续正式 spec 提出必须、验证、回写、停止或 Human Gate 规则时，应说明保障需求或不可承接原因 | 本文 §5.3、02 结构规则、Code 解析、review | 保障需求治理 | 新增、修改或迁移规则时 |
| 能力缺口暴露要求 | 保障需求必须说明所需能力或能力缺口，不得让资产存在等同于能力生效 | 本文 §5.2、§5.3、§5.7 | 能力治理 | 新增保障需求、环境入口或承接机制时 |
| 消费时机闭集要求 | 保障需求使用统一消费时机，不得私设同义入口 | `01.Att.01`、Code 解析、行动模板 | 入口治理 | 新增或修改消费时机时 |
| 承接边界要求 | 保障需求必须说明承接归口和机制，不得让 Code、Web、环境入口或行动模板互相反向定义 | 本文 §5.5、后续构成要素规范 | 跨构成要素治理 | 新增承接机制或改动承接边界时 |
| 外部衔接边界要求 | 环境入口、Hook、Rules、插件和 Runtime Protocol 必须回到同一保障消费语义，不得形成第二规则源 | 本文 §6、01.Att.03-06、Code 解析 | 环境入口治理 | 新增环境入口、Hook、插件或 Runtime Protocol 时 |
| 环境状态声明要求 | available、manual_ready、integrated、deferred、removed_top_level 和 absent 不得混写 | 本文 §6.5-6.9、01.Att.03-06、environment_status、environment_entry_audit | 状态治理 | 声称环境已接管、阻断或后置时 |
| 行动指南边界要求 | 行动指南必须回指来源和缺口，不得替代 AI 判断、事实源或 Human Gate | 本文 §7、02 AI 行为规则、Code 解析 | 行动承接治理 | 生成 read_plan、next_action、completion claim 或 human-facing output 时 |

| 缺口分流要求 | 承接缺口必须分级并进入对应承接位置 | 本文 §5.7、事实模型、行动模板、Human Gate | 缺口治理 | 出现 blocker、warning、follow-up 或 unverifiable 时 |

`specs/attachments/01.Att.02-保障机制承接矩阵.md` 只维护最小承接映射，不替代本文正文规则，也不替代后续具体实现。

## 9. 验证方法

本文验证口径如下：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 价值衔接检查 | 本文是否只承接 00 的保障与衔接层，没有新增构成要素或新价值门 | 回到 00 和 Human Gate |
| 三层职责检查 | 主体规则区是否清楚区分内部保障、外部衔接和行动指南 | 回到本文 §5、§6、§7 重排 |
| 保障需求结构检查 | 保障需求是否具备来源、所需能力、消费时机、承接机制、完成证据、阻断条件和缺口分流 | 记录为规范结构缺口或 Code 解析缺口 |
| 承接边界检查 | 后续 specs 是否把具体实现交给对应构成要素，没有在本文或附件中提前吞并 | 回到对应构成要素规范或 Human Gate |
| 外部衔接检查 | 环境入口、Hook、Rules、插件和 Runtime Protocol 是否只提供入口与触发语义，没有形成第二规则源 | 回到本文 §6、01.Att.03-06 或 Human Gate |
| 环境状态检查 | 自动入口、manual-ready、候选、removed_top_level 和 absent 是否按闭集区分，没有把文件存在或手动命令写成自动集成 | 回到本文 §6.5-6.9、Code 状态检查或 Human Gate |
| 行动指南检查 | 行动指南是否有来源回指、缺口暴露和 Stop Conditions，没有替代 AI 判断、事实源或 Human Gate | 按本文 §7 和 03 处理 |
| 证据边界检查 | receipt、evidence、diagnostic 是否未被当作事实源或 Human 授权 | 停止完成声明，回到事实源边界或 Human Gate |
| 缺口处理检查 | blocking、warning、follow-up、unverifiable 是否被正确分流 | 按 §5.7 处理，不得静默或降级 |

Code 可以检查 identity block、附件路径、消费时机闭集和保障需求字段是否可解析；AI 必须判断价值、归口、承接边界和风险；上位冲突、风险接受和不可自动判断事项必须进入 Human Gate。

## 10. Human Gate

以下情况必须进入 Human Gate：

1. 改变保障与衔接层在 00 中的上位定位；
2. 将保障与衔接层改为构成要素；
3. 改变内部保障、外部衔接和行动指南三层职责的关系；
4. 新增、删除、重命名或改变消费时机闭集含义；
5. 改变 Runtime Protocol、canonical event 或 trigger source 的基础语义，导致环境入口和运行时判断边界变化；
6. 改变 receipt、evidence、diagnostic 的基础语义，导致后续机制判断边界变化；
7. 允许行动指南、Code、Hook、Web、Skill、Agent、测试或环境入口跳过 Human Gate、事实源边界或验证证据；
8. 接受关键保障不可验证、不可回写、无法分流或无行动指南缺口暴露的风险。
9. 新增、删除、改名或重排环境入口类型、接入状态闭集或 removed_top_level 口径；
10. 将 manual-ready、available、deferred 或 absent 入口升级为 integrated；
11. 安装、覆盖、卸载或扩大真实自动 Hook、插件、runtime adapter 或 repo instruction 的影响范围；
12. 恢复 Rules / Skill 顶层机制，或把 legacy 资产重新写成 V3 顶层入口；
13. 接受环境入口无法回滚、无法验证、无法定位 target 或无法说明失败处理的风险；
14. 声称环境入口已经完成授权、放行、验收或 Human Gate。

AI 可以准备影响范围、选项和建议，但不得替 Human 完成 Gate。

## 11. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 本文与 00 的价值门、五类构成要素、事实源边界或保障与衔接层冲突；
2. 下位规范绕过本文各自定义互相竞争的保障与衔接基础规则；
3. 新增规则提出强制要求，但没有保障需求、承接机制、验证方法或缺口分流；
4. 保障需求缺少所需能力或能力缺口说明，却被声称已经完整生效；
5. 环境入口、Hook、Rules、插件或 Runtime Protocol 正在替代 specs、事实源或 Human Gate；
6. 行动指南正在替代 AI 主控判断、Human Gate、事实源、测试验证或完成证明；
7. Code、Hook、Web、Skill、Agent、测试或 receipt 正在替代 Human Gate 或事实源；
8. 必要保障缺失被降级为普通待补齐事项；
9. 无法判断某个承接缺口是否阻断当前行动或完成声明。
10. 无法区分入口是 automated、manual-ready、candidate、removed_top_level 还是 absent；
11. 文件存在、脚本存在、README 命令存在或测试通过被写成自动触发证据；
12. runtime receipt、Hook 输出、Code 输出或 Web 展示正在替代事实源、Human Gate 或完成验收；
13. Rules / Skill 目录、注册表或执行闭环被恢复为 V3 顶层机制；
14. 安装或卸载真实入口前没有回滚方式、状态检查和 Human 确认；
15. 受管项目环境入口未通过 target-first 和 Git common-dir 边界确认。

暂停后，AI 只能交还触发条件、涉及事实源、影响范围、建议归口和是否需要 Human Gate，不得继续声明保障生效。
