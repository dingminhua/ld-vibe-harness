## 一、对象定位与准入

### 1.1 ADR 定义

ADR 是已确认、后续应遵守的决策记录。ADR 应记录决策内容、背景、原因、选择、影响范围和后续约束（依据 14 §八）。

ADR 不是所有判断的默认归宿。AI 可以做出临时判断、记录分析结论、在当前任务中做局部选择，但只有满足准入条件、影响长期执行方式的决策，才应进入 ADR 事实源。

### 1.2 ADR 与临时判断

临时判断是 AI 或人在执行过程中做出的局部选择，不默认成为 ADR。临时判断可以记录在 Memo、Task evidence 或讨论材料中。

ADR 是满足准入条件、进入 PM Kit 管理系统的决策。所有 ADR 都是判断，但不是所有判断都是 ADR（依据 14 §七.3）。

一个 ADR 至少应具备：

1. 明确的决策内容；
2. 决策背景和原因；
3. 决策后果；
4. 影响范围；
5. 可追溯的状态。

### 1.3 ADR 准入条件

当一个判断满足以下条件之一时，应考虑形成 ADR（依据 14 §七.3）：

1. 影响多个对象；
2. 改变长期执行方式；
3. 改变事实源归属；
4. 形成长期行为边界；
5. 反复出现且需要稳定约束。

不满足 ADR 准入条件的临时判断，可以先作为 Memo、Task evidence 或讨论材料保留。

以下内容通常不应单独形成 ADR：

1. 当前 Task 内的局部技术选择；
2. 一次性执行方式调整；
3. 不影响其他对象的临时方案；
4. 尚未稳定的讨论或想法；
5. 已由 specs 或 Rules 明确约束的重复判断；
6. 仅涉及当前会话的执行策略。

AI 不得因为某个判断"看起来重要"就自动创建 ADR。只有满足准入条件的判断，才应写入 ADR 事实源。

### 1.4 ADR 与 specs / Rules 的边界

ADR 记录为什么这样决定，specs 或 Rules 记录以后必须怎么做。两者不得互相替代（依据 10 §九.4）。

当 ADR 中的决策升级为长期基础规范时，应将规则正文写入 specs 或 Rules，ADR 保留原因和背景。ADR 不替代 specs 规范正文，不替代 Rules 执行入口，不替代 Kit Base 中的其他对象状态。

## 三、状态机

### 3.1 标准状态

ADR 标准状态如下：

| 标准状态 | 含义 |
|---|---|
| proposed | 已提出，尚未确认 |
| accepted | 已确认，后续应遵守 |
| deprecated | 已废弃，不再建议遵守，但保留历史 |
| superseded | 已被新 ADR 替代 |
| rejected | 已否决，不采纳 |

### 3.2 合法状态流转

```text
proposed → accepted, rejected
accepted → deprecated, superseded
deprecated → 无
superseded → 无
rejected → 无
```

未在上述规则中列出的流转为非法流转，工具应拒绝执行。

`deprecated`、`superseded` 和 `rejected` 是稳定终态。终态 ADR 不得重开；如需重新决策，必须新建 ADR 承接，并在新 ADR 中引用原 ADR。

`proposed` 状态的 ADR 不应作为执行依据。只有 `accepted` 状态的 ADR 才表示已确认、后续应遵守的决策。

## 四、字段契约

### 4.1 基础字段

ADR 基础字段对齐 10 §12.2：`id`、`type`、`title`、`status`、`created`、`updated`。

### 4.2 ADR 扩展字段

ADR 扩展字段对齐 10 §12.5，字段名称与简要说明如下：

| 字段名 | 简要说明 |
|---|---|
| `date` | 决策日期 |
| `context` | 决策背景 |
| `decision` | 决策内容 |
| `consequences` | 决策后果 |
| `alternatives` | 考虑过但未采纳的替代方案（可选） |
| `affects` | 影响范围列表（可选） |
| `related_objects` | 关联的管理对象 ID 列表（可选） |
| `related_rules` | 关联的规则文件列表（可选） |
| `superseded_by` | 仅当 status 为 superseded 时必须填写，指向替代本决策的新 ADR ID |

### 4.3 文件命名

文件命名格式对齐 10 §12.5：

```text
pm-kit-base/adrs/adr-{NNNN}-short-title.yaml
```

编号从 `0001` 开始递增，固定 4 位；英文标题使用小写短横线；每个项目独立编号，不使用跨项目全局编号。

## 五、与其他对象的关系

### 5.1 转化关系

#### 5.1.1 Memo → ADR

当 Memo 中的输入涉及需要长期追溯的判断或选择，且满足 ADR 准入条件时，Memo 可转化为 ADR。

转化条件：

1. Memo 内容满足 ADR 准入条件（§1.3）；
2. 决策内容已明确，不再是未任务化输入；
3. 已获得人类确认。

转化后 Memo 状态应变为 `converted`，并记录 `linked_adr_id`。

#### 5.1.2 Task evidence → ADR

当 Task 执行过程中产生的判断满足 ADR 准入条件时，可将判断从 Task evidence 升级为 ADR。

转化条件：

1. 判断满足 ADR 准入条件（§1.3）；
2. 判断影响范围超出当前 Task；
3. 已获得人类确认。

转化后应在 ADR 的 `related_objects` 字段记录来源 Task ID，在 Task 的 evidence 中记录 ADR ID。

#### 5.1.3 ADR → Task

当 ADR 的决策需要具体执行时，应创建 Task 承接执行工作，ADR 保留决策记录。

创建 Task 后应在 ADR 的 `related_objects` 字段记录 Task ID。

#### 5.1.4 ADR → specs / Rules

当 ADR 满足升级条件时，决策应升级为规则或规范正文。升级路径与条件见 §5.2。

#### 5.1.5 不满足准入的判断

不满足 ADR 准入条件的判断，应按其性质分流（依据 14 §七.3）：

1. 有保留价值但暂不任务化 → Memo；
2. 已有明确目标和完成标准 → Task；
3. 已确认的风险 → Risk；
4. 已确认的依赖 → Dependency；
5. 一次性执行策略 → 留在当前执行上下文。

### 5.2 升级路径

当某个 ADR 满足以下条件之一时，应考虑升级为规则或规范正文（依据 10 §九.4）：

1. 影响多个项目或所有接入项目；
2. 改变 AI、人或工具的长期行为；
3. 改变事实源归属；
4. 改变 Human Gate 判断；
5. 多次重复出现且需要稳定约束；
6. 影响初始化、工具写入或对象关闭方式。

升级后应保持：

```text
ADR 记录为什么这样决定
specs 或 Rules 记录以后必须怎么做
```

两者不得互相替代。

升级操作必须：

1. 将规则正文写入 specs 或 Rules；
2. ADR 保留原因和背景，不删除；
3. 在 ADR 的 `related_rules` 字段记录升级后的规则文件；
4. 升级操作须经 Human Gate 确认。

### 5.3 推翻与废弃规则

1. **ADR 不得删除**。推翻旧决策时，不得删除旧 ADR 文件，应通过状态变更表达。

2. **推翻旧决策时**，将旧 ADR 的 `status` 标记为 `superseded`，并在 `superseded_by` 字段引用新 ADR 的 ID。新 ADR 的 `context` 中应说明推翻旧决策的原因。

3. **废弃决策时**，将 ADR 的 `status` 标记为 `deprecated`，表示不再建议遵守但保留历史。废弃应在 `consequences` 或 `context` 中补充废弃原因。

4. **ADR 文件名可因标题修正而调整**，但重命名时必须同步更新所有引用该 ADR 的 `related_objects`、`superseded_by` 和其他关联字段。

5. **终态 ADR 不得重开**。如需对已终态的决策重新判断，必须新建 ADR，并在新 ADR 中引用原 ADR。

6. **推翻或废弃操作须经 Human Gate 确认**（见 §九）。

## 八、AI 协作适配

本节声明 ADR 对象如何适配 AI 协作层（11），不重新定义 11 的总原则。

### 8.1 AI 读取 ADR

1. AI 读取 ADR 时应优先读取 `accepted` 状态的 ADR，作为已确认决策的执行依据。
2. AI 不得将 `proposed` 状态的 ADR 作为执行依据。
3. AI 读取 `deprecated` 或 `superseded` 状态的 ADR 时，应识别其历史语境，不作为当前执行依据。

### 8.2 AI 创建 ADR

1. AI 不得因为某个判断"看起来重要"就自动创建 ADR，必须先判断是否满足 ADR 准入条件（§1.3）。
2. AI 创建 ADR 时，初始状态应为 `proposed`，不得直接创建为 `accepted`。
3. AI 将 `proposed` 状态推进为 `accepted` 时，必须经 Human Gate 确认。

### 8.3 AI 推翻或废弃 ADR

1. AI 不得自行推翻或废弃 `accepted` 状态的 ADR，必须经 Human Gate 确认。
2. AI 发现需要推翻或废弃 ADR 时，应向用户说明原因、影响范围和替代方案。

### 8.4 AI 升级 ADR

1. AI 识别到 ADR 满足升级条件（§5.2）时，应建议升级为 specs 或 Rules。
2. 升级操作须经 Human Gate 确认，AI 不得自行执行升级。

### 8.5 AI 与 ADR 转化

1. AI 在对话中识别到 Memo 或 Task evidence 满足 ADR 准入条件时，应建议转化为 ADR。
2. 转化操作须经 Human Gate 确认。
3. AI 识别到 ADR 决策需要执行时，应建议创建 Task 承接。

## 九、Human Gate

### 9.1 必须触发 Human Gate 的操作

| 操作 | 需要确认的内容 |
|---|---|
| proposed → accepted | 决策确认与影响范围认可 |
| accepted → deprecated | 废弃原因与后续处理 |
| accepted → superseded | 替代决策与新 ADR 关联 |
| ADR 升级为 specs 或 Rules | 升级内容与规则归属 |
| ADR 文件重命名 | 引用同步更新 |

### 9.2 应评估 Human Gate 的情况

1. 新增影响多个项目、规则、Skill、Agent 或工具边界的 ADR；
2. 将原本只是 Memo、Intent 或临时判断的内容升级为 ADR；
3. 推翻或废弃已长期执行的 ADR；
4. 修改 ADR 的核心决策内容（`decision` 字段）；
5. 改变 ADR 的事实源载体、状态机或升级路径语义。

## 十、程序辅助适配

本节声明 ADR 对象如何适配程序辅助层（12），不重新定义 12 的总原则。

### 10.1 解析

1. 程序解析 ADR 时应依据 10 §12.5 定义的格式契约。
2. 解析失败时应报告具体的失败位置、期望格式和实际内容，不得静默跳过。

### 10.2 校验

程序校验 ADR 时应覆盖：

| 校验类型 | 校验对象 |
|---|---|
| 字段完整性 | ADR 必填字段（id、title、status、date、context、decision、consequences）是否齐全 |
| 状态合法性 | 状态值是否属于标准状态，状态流转是否属于合法流转 |
| 条件必填 | superseded 状态是否具备 superseded_by 字段 |
| 引用有效性 | superseded_by、related_objects、related_rules 引用的对象是否存在 |
| 格式合规性 | 文件命名、编号和 YAML 格式是否符合 10 §12.5 |

### 10.3 聚合

1. 程序可聚合 ADR 列表、状态分布、升级路径和推翻历史，供工具展示或 AI 上下文使用。
2. 聚合输出属于派生视图数据，不替代 ADR 事实源。

### 10.4 受控写入

1. 程序写入 ADR 时应校验字段完整性和状态合法性。
2. 写入前应判断是否触发 Human Gate（§九）。
3. 程序不得自动执行 ADR 状态流转中需要 Human Gate 确认的操作。

## 十一、工具展示适配

本节声明 ADR 对象如何适配工具展示层（13），不重新定义 13 的总原则。

### 11.1 展示范围

工具可以展示 ADR 的以下信息：

1. ADR 列表与状态分布；
2. ADR 的影响范围和关联对象；
3. ADR 的升级路径和推翻历史；
4. 待确认的 ADR（proposed 状态）；
5. 已终态的 ADR（deprecated、superseded、rejected 状态）。

### 11.2 展示约束

1. 工具展示的 ADR 信息必须可追溯到 Git 文件事实源。
2. 工具不得维护与 ADR 事实源不一致的权威状态。
3. 工具展示 ADR 状态变更时，应提示 Human Gate 要求。

### 11.3 受控写入

1. 工具可通过受控写入入口修改 ADR，写入目标必须是项目的 Git 文件事实源。
2. ADR 状态变更写入前应评估 Human Gate。
3. 写入后工具视图应从事实源重新读取或刷新。
