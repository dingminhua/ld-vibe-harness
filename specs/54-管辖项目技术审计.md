# 管辖项目技术审计

> 创建日期：2026-05-28
> 定位：PM Kit 管辖项目技术层面的合规审计流程
> 适用范围：PM Kit 管辖项目（Python 程序、PM Web Tools、配置文件、规则文件）
> 上位依据：`specs-v2/00-PMKit理念与纲要.md`、`specs-v2/10-事实源规范.md`、`specs-v2/11-AI协作规范.md`、`specs-v2/12-程序辅助规范.md`、`specs-v2/13-工具展示规范.md`

---

## 一、本文解决的问题

本文解决的问题是：PM Kit 管辖项目的技术实现——Python 程序、PM Web Tools、配置文件和规则文件——是否遵守 specs-v2/12 程序辅助规范和 specs-v2/13 工具展示规范定义的技术合规要求，以及如何检查、记录和处理违规发现。

管辖项目技术审计与管理审计（53）互补：

| 维度 | 管辖项目管理审计（53） | 管辖项目技术审计（本文） |
|---|---|---|
| 审计对象 | 规范体系的管理合规性 | 工具代码和程序实现的技术合规性 |
| 检查焦点 | 对象落实、禁止扩张、适配一致 | 程序辅助和工具展示是否遵守 12/13 规范 |
| 违规性质 | 规范体系治理问题 | 代码实现技术问题 |
| 产出分流 | 规范调整、对象补齐、扩张回退 | 程序修正、工具修正、代码质量修复 |

本文约束对象为 PM Kit 管辖项目的技术实现层。规范体系自身的合规性由管理审计负责，不在本文范围内。

---

## 二、与 00 总纲的关系

00 §四 定义事实源原则：事实必须能被 AI 读取、被人审查、被工具解析或聚合、通过 Git 追溯变化、同一事实只能有一个权威位置。程序和工具的技术实现必须遵守这些原则。

00 §五 定义协作闭环：工具辅助解析、校验、聚合和受控写入，执行证据回到 Git 文件事实源。程序和工具的技术实现必须确保闭环不被破坏。

00 §六 定义价值实现原则：PM Kit 的建设成效以 AI 是否能稳定理解、受控执行、识别门禁、留下证据并支持人类确认来衡量。技术审计检查程序和工具是否在技术层面支撑这些价值。

本文将 00 的价值要求转化为技术合规检查流程：检查程序辅助是否遵守 12 的行为约束，检查工具展示是否遵守 13 的行为约束，检查代码质量是否满足 L1 硬约束，检查配置与规则文件是否格式合规。

## 三、事实源边界声明

本文的权威领域是管辖项目技术审计的流程定义、检查项、分流规则和 Human Gate 触发条件。本文不定义程序辅助的行为约束（见 12）、工具展示的行为约束（见 13）、AI 协作的 Human Gate 总清单（见 11）、事实源的载体规则和格式契约（见 10）、管理对象的语义和状态机（见 14 及 20-49）。

## 四、流程定义与触发条件

### 4.1 审计对象

管辖项目技术审计的审计对象为 PM Kit 管辖项目中涉及程序辅助和工具展示的技术实现，包括：

| 审计对象 | 审计依据 | 说明 |
|---|---|---|
| Python 程序代码 | specs-v2/12 | 解析、校验、聚合、受控写入的实现 |
| PM Web Tools 代码 | specs-v2/13 | 展示、受控编辑、Human Gate 提示的实现 |
| 配置文件 | specs-v2/10、specs-v2/11 | Kit Base YAML、规则文件、product.yaml |
| 规则文件 | specs-v2/11 | L0/L1/L2 规则文件格式与引用 |

### 4.2 触发条件

满足以下任一条件时，应执行管辖项目技术审计：

1. Python 程序或 PM Web Tools 代码修改后
2. specs-v2/12 或 specs-v2/13 修改后
3. PM Kit 版本发布前
4. 新增程序辅助功能或工具展示功能后
5. 定期技术巡检

触发条件 1 和 4 为即时触发，审计范围限定为变更涉及的功能模块。触发条件 2 为规范变更触发，审计范围限定为规范变更涉及的合规检查项。触发条件 3 和 5 为全量触发，审计范围覆盖全部检查项。

## 五、执行步骤

### 5.1 程序辅助合规检查（对齐 specs-v2/12）

#### 5.1.1 事实源读取合规

| 检查项 | 依据 | 合规标准 | 违规等级 |
|---|---|---|---|
| 程序输入是否来自 Git 文件事实源 | 12 §5.1 | 程序解析的输入必须来自 Git 文件事实源，不得将缓存、数据库、UI 状态或对话内容作为解析输入的权威来源 | 高 |
| 程序是否未将缓存/数据库/UI 状态作为权威来源 | 12 §3.2 | 缓存和数据库只能是派生层，必须可由 Git 文件事实源重新生成 | 高 |
| 程序输出是否可追溯到 Git 文件 | 12 §4 | 程序输出中需要长期保留的信息，必须回写到 Git 文件事实源 | 中 |

#### 5.1.2 禁止职责合规

| 检查项 | 依据 | 合规标准 | 违规等级 |
|---|---|---|---|
| 程序是否未保存第二套事实 | 12 §3.2 | 程序不得维护与 Git 文件事实源不一致的权威状态 | 高 |
| 程序是否未绕过对象状态机 | 12 §3.2 | 程序不得绕过管理对象规范定义的状态机进行状态流转 | 高 |
| 程序是否未直接调用 AI/Skill/Agent | 12 §3.2 | 程序不得调用 AI、Skill 或 Agent | 高 |
| 程序是否未自动修改业务事实 | 12 §3.2 | 程序不得自动修改任务状态、关闭任务或修改规则 | 高 |
| 程序是否未生成索引文件 | 12 §7.4、§11.7 | 索引类信息只返回结果，不得持久化为独立文件 | 中 |

#### 5.1.3 受控写入合规

| 检查项 | 依据 | 合规标准 | 违规等级 |
|---|---|---|---|
| 程序写入是否遵守受控写入原则 | 12 §8 | 写入目标必须是项目的 Git 文件事实源，写入前必须校验 | 高 |
| 程序是否未绕过 Human Gate 自动写入 | 12 §8.4 | 程序不得绕过 Human Gate 自动写入 | 高 |
| 程序写入后是否记录变更 | 12 §8.3 | 写入后必须记录变更记录 | 中 |
| 程序是否未修改规范文档或规则文件 | 12 §8.5 | specs 和 Rules 不得通过程序直接修改 | 高 |

#### 5.1.4 解析与校验合规

| 检查项 | 依据 | 合规标准 | 违规等级 |
|---|---|---|---|
| 解析失败时是否报告具体位置 | 12 §5.3 | 解析失败应报告失败位置、期望格式和实际内容，不得静默跳过 | 中 |
| 解析失败是否未修改原始文件 | 12 §5.3 | 解析失败不得导致程序修改或覆盖原始事实源文件 | 高 |
| 校验失败是否未自动修改事实源 | 12 §6.4 | 校验失败不得导致程序自动修改事实源 | 高 |
| 写入前校验失败是否阻止写入 | 12 §6.4 | 写入前校验失败应阻止写入操作 | 高 |

### 5.2 工具展示合规检查（对齐 specs-v2/13）

#### 5.2.1 事实源边界合规

| 检查项 | 依据 | 合规标准 | 违规等级 |
|---|---|---|---|
| 工具是否未维护第二事实源 | 13 §3.3、§4.1 | 工具不得维护与 Git 文件不一致的权威状态 | 高 |
| 工具展示数据是否从 Git 文件事实源聚合 | 13 §4.2 | 展示内容必须可追溯到 Git 文件事实源 | 高 |
| 工具是否未将缓存或数据库作为权威状态 | 13 §5.3 | 缓存和数据库只能是派生层 | 高 |
| 工具是否未将自身项目误作为被管理项目事实源 | 13 §3.3 | 工具写入必须回到被管理项目自身 | 高 |

## 六、产出与分流

### 6.1 审计发现分流规则

审计发现按性质分流为以下类型：

| 发现类型 | 分流目标 | 说明 |
|---|---|---|
| 程序辅助违规 | Task | 需修正程序实现，使其遵守 12 规范 |
| 工具展示违规 | Task | 需修正工具实现，使其遵守 13 规范 |
| 代码质量问题 | Task | 需修正代码，消除硬编码、违规依赖或禁止事项违反 |
| 配置/规则格式问题 | Task 或 Memo | 格式不合规需修正时创建 Task；仅需提醒或记录时创建 Memo |
| 规范缺口 | Memo 或 ADR | 审计中发现规范未覆盖的技术场景，记录为 Memo 或形成 ADR |

分流后的对象事实归属依据 10 §八.5 审计发现分流规则处理。审计快照可以记录发现摘要，但不得替代分流对象的事实源。

### 6.2 技术审计报告

每次技术审计应产出审计报告，报告内容包括：

1. 审计触发条件与审计范围
2. 各检查项的检查结果（通过 / 不合规 / 缺失）
3. 不合规发现的详情：违规代码位置、违反的规范条款、违规等级、建议修复方式
4. 分流结果：每条发现已分流为 Task、Memo 或 ADR 的 ID
5. 审计结论：合规 / 部分合规 / 不合规

审计报告不是事实源。审计报告中需要长期保留的发现，必须分流为对应管理对象并写入 Git 文件事实源。

## 七、Human Gate

以下情况必须暂停并等待用户确认：

1. 发现程序绕过 Human Gate 自动写入
2. 发现工具维护第二事实源
3. 需要新增依赖或修改技术栈
4. 审计发现涉及跨项目技术影响
5. 修正违规需要修改规范文档或规则文件
6. 审计发现需要改变程序与工具的接口边界

Human Gate 的执行规则依据 11 §十二。

## 八、检查要求

技术审计检查至少包括：

| # | 检查项 | 标准 |
|---|---|---|
| 1 | 程序未保存第二套事实 | 程序未维护与 Git 文件事实源不一致的权威状态 |
| 2 | 程序未生成索引文件 | 索引类信息只返回结果，未持久化为独立文件 |
| 3 | 工具未维护第二事实源 | 工具未维护与 Git 文件不一致的权威状态 |
| 4 | 代码未硬编码产品专属路径 | 程序中不存在特定产品的路径、项目名或业务概念硬编码 |
| 5 | 规则文件引用路径有效 | 规则文件中的引用路径可追踪、可检查 |
| 6 | 审计发现已按分流规则处理 | 每条审计发现已分流为 Task、Memo 或 ADR 并写入事实源 |

## 十、待补齐事项

1. 程序辅助合规的自动化检测规则待展开——当前检查项为人工审计标准，尚未转化为可程序化执行的检测规则
2. 工具展示合规的前端验证标准待细化——API 返回结构与前端渲染契约的一致性检查标准需随 PM Web Tools 实现进展补充
3. 管辖项目技术审计与受管理项目技术审计的交叉场景待补充——当管辖项目的程序或工具同时服务多个受管理项目时，审计范围和分流规则的交叉处理方式待明确
4. 审计快照的格式和存储位置待确认——审计报告是否需要结构化存储到 pm-kit-base，还是仅作为过程文档保留在 docs，待实践验证后决定
5. CI/CD 集成的自动审计检查项待实践验证——哪些检查项可以自动化、自动化检查的触发方式和失败处理策略待程序辅助能力建设后补充
6. 违规等级与修复优先级的映射关系待细化——当前违规等级为高/中二级，是否需要增加低级、是否需要与 Task 优先级字段建立映射待实践验证
