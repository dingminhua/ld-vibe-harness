## 1. 本文解决的问题

本文解决 LDVH v2 中工作模型区段如何登记、迁移、检查和被初始化或审计流程消费的问题。

本文是 20-39 工作模型区段的规范型集合索引。AI 和 Human 在进入具体工作模型前，应先通过本文确认：

1. 哪些编号已经占用；
2. 哪些工作模型是 active、removed、deferred-field、deferred-doc 或 reserved；
3. 哪些旧规范可以迁入 v2，哪些旧规范不得误恢复为独立工作模型；
4. 产品初始化和审计应读取哪些 active 工作模型；
5. 后续迁移优先级如何表达。

本文不定义具体工作模型的字段契约、状态机、实例验收规则、对象特有 Human Gate 或行动流程。这些内容由 21-39 具体工作模型规范承载。

---
## 2. 与 00 和 05 的关系

00 定义 LDVH 工作模型是五类构成要素之一，用于承载工程生产事实。05 定义工作模型的基础规则、准入条件、通用规范和与 20-39 具体规范的关系。

本文承接 05，只维护工作模型集合的清单、状态、关系、迁移闸门和产品级初始化/审计输入。本文不得反向改写 05 的通用规则，也不得替代 21-39 具体工作模型规范。

## 5. 工作模型迁移闸门

工作模型迁移必须先通过本文判断集合状态，再决定是否创建或修改 21-39 文档。

迁移闸门规则如下：

1. `active` 项可以迁入 v2 具体工作模型规范；
2. `next` 只是迁移优先级，不改变编号、对象定义或集合状态；
3. `removed` 项不得在没有 Human Gate 的情况下恢复为独立工作模型；
4. `deferred-field` 项不得因为旧文档存在、术语重要或字段常用而自动对象化；
5. `deferred-doc` 项不得在没有独立状态机、字段契约和验收需求前升级为 YAML 工作模型；
6. `reserved` 编号不得绕过 Human Gate 占用；
7. 旧 `specs/` 中尚未迁入 v2 的内容只能作为迁移素材，不自动成为 v2 权威规范。

当前迁移顺序建议：

| 顺序 | 对象 | 原因 |
|---|---|---|
| 已完成 | Task / 任务(27) | Task 已迁入 v2，承接 AI 执行、验收、验证证据、风险判断、依赖关系、产物引用和检查结果 |
| 1 | Intent / 意图(24) | Intent 承接人的目标、约束和任务集合职责 |
| 2 | ADR / Change / Pitfall / Memo / Profile | 依据后续迁移需要逐步补齐 |

## 6. 集合关系

当前工作模型按治理用途分为以下关系组：

| 关系组 | 对象 | 说明 |
|---|---|---|
| 核心执行实体 | Task(27) | 最小可执行、可追踪、可验证、可关闭的工作单元 |
| 意图和入口 | Intent(24)、Memo(25)、Profile(26) | Intent 承载正式目标和约束；Memo 承载未任务化但有价值的信息；Profile 承载项目身份和接入配置 |
| 决策和经验 | ADR(21)、Pitfall(23) | ADR 承载已确认决策；Pitfall 承载可复用经验 |
| 变更记录 | Change(22) | 承载事实源变更记录，优先与 Git commit 事实对齐 |
| 字段或模板承载概念 | Dependency(30)、Risk(31)、Artifact(32)、Checklist(33) | 暂不作为独立工作模型，先由现有对象字段、模板、内容格式或产物路径承接 |
| 文档承载概念 | Roadmap(34) | 暂不作为 YAML 工作模型，先由 Markdown 文档或规划入口承接 |

集合关系只说明对象在集合中的定位，不替代具体对象关系规则。具体对象之间可引用、可阻塞、可关闭或可验收的规则，应由对应具体工作模型规范定义。

## 7. 初始化与审计输入

产品初始化和产品审计读取本文时，应至少确认：

1. active 工作模型是否均有 v2 主规范或明确迁移状态；
2. active 工作模型的事实实例目录、命名、基础字段、状态机和验收规则是否能从对应主规范读取；
3. removed、deferred-field、deferred-doc 和 reserved 项未被误创建为默认事实源目录；
4. 验证证据、风险判断、依赖关系、产物引用和检查结果应按 Task 字段、内容格式、模板或结果物路径处理；
5. 旧 `specs/` 的旧工作模型文档未被直接当成 v2 权威规范；
6. Code、Web、Skill、Agent 或运行投影消费工作模型时，引用的是 05、本文和已迁入的具体工作模型规范，而不是旧子文档结构。

本文只提供初始化和审计输入，不定义初始化或审计工作流程。

## 8. 集合一致性检查

集合一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| 编号一致性 | 20-39 编号未重复、未越界，35-39 未绕过 Human Gate 占用 |
| 清单一致性 | 本文登记的文档名、状态和迁移动作与 `specs-v2/` 实际文件一致 |
| 状态一致性 | active、removed、deferred-field、deferred-doc、reserved 的含义未混用 |
| 迁移闸门 | removed 或 deferred 项未被自动迁入为独立工作模型 |
| 引用一致性 | 01、03.03、03.04、05 和具体工作模型规范对 20 的引用一致 |
| 边界一致性 | 本文未定义具体字段契约、状态机、实例验收规则或对象特有 Human Gate |
| 初始化输入 | 产品初始化和审计只把 active 工作模型作为默认独立对象输入 |
| 旧规范边界 | 旧 `specs/` 只作为迁移素材，未直接覆盖 v2 正文区结论 |

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或重排 20-39 编号；
2. 改变某个编号对应的工作模型归属；
3. 将 removed 项恢复为独立工作模型；
4. 将 deferred-field 或 deferred-doc 项升级为独立工作模型；
5. 占用 35-39 保留编号；
6. 改变集合状态或迁移动作的含义；
7. 让本文定义具体字段契约、状态机、实例验收规则或对象特有 Human Gate；
8. 恢复固定机制子文档作为工作模型完整性要求；
9. 将旧 `specs/` 中未迁入的内容直接视为 v2 权威规范。

工作模型集合索引检查至少包括：

| 检查项 | 标准 |
|---|---|
| 索引范围 | 已声明 20-39 编号范围 |
| 文档清单 | 每个编号的文档名、类型、集合状态、迁移动作和定位清晰 |
| 状态边界 | removed、deferred-field、deferred-doc 和 reserved 未被误当成 active 工作模型 |
| 迁移优先级 | 迁移优先级不改变编号 |
| 规则边界 | 未承载具体对象字段、状态机或行动流程 |
| 初始化与审计输入 | 已说明产品初始化和审计如何消费本文 |
| Human Gate | 编号、状态、升级、降级和旧规范恢复场景已声明 Human Gate |
