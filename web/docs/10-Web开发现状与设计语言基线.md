# Web 开发现状与设计语言基线

> 更新：2026-07-25
> 范围：`web/` 当前参考实现、页面开发文档和后续 Web 修改入口
> 上位文档：[`01-全局设计约束.md`](./01-全局设计约束.md)

## 1. 文档定位

本文用于把 Web 当前开发现状、页面文档职责和已经稳定的设计语言收敛到一个入口。后续修改 Web 页面时，应先按本文判断目标页面属于哪一类，再回到对应页面文档和源码实现。

本文不替代 `specs/05-Web信息同步规范.md`、`specs/08-测试基础规范.md`、事实模型规范或 Git 文件事实源。本文只说明当前 `web/` 参考实现如何把这些规则呈现给 Human。

当前 V4 事实读取器读取 WorkCase、ADR、Pitfall、Spark 和 Study 的 V4 原生载体；不读取 V2/V3 资产或旧字段。详情、对象预览、源路径复制和正文阅读必须先取得精确读取，并把 `canonical_path`、`carrier` 和 `check_status` 从读取结果传到消费面；候选列表不承诺这些元数据。Study 定位为“外部内容调研报告”，不提供兼容双读。

## 1.1 已确认与待确认边界

当前 Web 设计沉淀采用“已确认先固化、待确认不写死”的原则。最前面三个产品入口 / tab 的最终名称、顺序和信息架构仍未完全确定，因此本文只沉淀它们必须遵守的视觉、i18n、复制、阅读面板和事实源边界，不把临时入口文案写成最终产品结构。

已确认并可进入实现收敛的内容：

1. App Shell 采用左侧主导航、中间主内容和右侧扩展阅读区；移动端右侧扩展阅读切换为底部阅读抽屉。
2. 对象列表使用卡片网格和统一状态筛选 tab，不回退到表格或顶部对象类型 tab。
3. 对象详情是语义阅读器，不是载体文件查看器；YAML 载体可有折叠源码兜底，Markdown Study 的完整阅读只进入同一份正文的扩展阅读。
4. 提交、研究、决策、火花、经验五个基准模块已经形成稳定阅读语言。
5. ObjectDetail 和 ReadingPanel 必须复用同一套身份头部、节点顺序、折叠行为、关联行和复制语义。
6. 所有用户可见 UI 文案必须走 i18n；事实正文、Git message、Markdown 正文、路径、命令、ID 和 hash 不翻译。
7. 复制入口必须按对象路径、文档路径、链接、引用、提交上下文和提交 hash 区分，不使用泛化“复制完整路径”覆盖所有场景。
8. Web 只做 Human-facing 派生展示和受控轻写入，不成为第二事实源。

待确认且不得写死为最终设计的内容：

1. 最前面三个入口 / tab 的最终名称、顺序和信息架构。
2. 这些入口是否最终对应 Dashboard、当前工作、项目文件或其他更准确的产品入口。
3. 未确认入口不得反向影响已确认的对象页、提交页、ProjectFiles、扩展阅读、复制语义和 i18n 规则。

## 2. 五个基准模块

当前 Web 的设计语言以五个已经完善的阅读模块为中心：

| 模块 | 路由 | 当前定位 | 作为基线的内容 |
|---|---|---|---|
| 提交 | `/changelog`、`/changelog/:hash` | Git commit records 证据追溯 | 筛选 tab、提交卡片、提交详情、复制提交上下文、右侧快速阅读 |
| 外部调研 | `/objects/study`、`/objects/study/:id` | 外部调研报告阅读界面 | 研究意图、摘要、建议、唯一 Markdown 正文入口和关联资料；终态只在事实存在时显示处置 |
| 决策 | `/objects/adr`、`/objects/adr/:id` | 决策阅读页 | 对象卡片、标准身份头部、问题/决策/范围/理由/影响节点；retired 以处置收束 |
| 火花 | `/objects/spark`、`/objects/spark/:id` | 待分流信息阅读页 | 对象卡片、标准身份头部、意图/摘要/演变节点；routed、implemented、discarded 才显示对应终态处置 |
| 经验 | `/objects/pitfall`、`/objects/pitfall/:id` | 可复用经验阅读页 | 对象卡片、标准身份头部、现象/触发/范围/验证/根因/方案/规避节点；retired 以处置收束 |

这五个模块不是孤立样板，而是后续 Web 页面继续收敛的中心。新页面或旧页面改造如涉及列表、详情、右侧扩展阅读、复制入口、关联行、节点折叠或提交证据，应优先复用这五个模块已经形成的语言。

## 4. 统一设计语言

五个基准模块共享以下语言：

1. 顶部切换区使用 `ldvh-tab-list` / `ldvh-tab-button`，滚动时固定在主滚动容器顶部。
2. 列表主体使用 `ldvh-section-grid`；卡片宽度不足时换行，不用表格或营销式大留白替代。
3. 精确可读详情、预览和已解析引用的右上可放复制入口；候选卡不复制源路径。状态、类型和标题各在自己的层级，不互相挤占。
4. 标题带使用弱背景、内圈边框、左侧语义短线、对象类型图标或提交图标和完整标题。
5. 更新时间统一在卡片底部右侧，使用 `formatDateTime()`。
6. 详情页和右侧扩展阅读复用同一身份头部、节点顺序、折叠行为和关联行。
7. 正文节点使用小圆点标题、整行点击折叠、`ChevronDown` / `ChevronUp` 和统一 Markdown 阅读样式。
8. 已精确读取且有来源路径的关联行使用左侧语义图标和标题，右侧提供复制入口与扩展阅读入口；其余关联行保留扩展阅读入口但不伪造路径。操作图标必须垂直居中。
9. 复制入口必须按内容语义命名和复制：对象复制对象路径，文档复制文档路径，URL 复制链接，普通引用复制引用，提交卡片复制提交定位上下文，提交详情复制 hash。

### 4.1 四类事实对象的共同阅读基线

Study、ADR、Spark 与 Pitfall 已经形成 WorkCase 必须继承的阅读秩序。它们不是字段数相同的模板，而是在不同事实任务下共同遵守以下分层：

1. **先身份，后判断。** 统一身份头部先说明类型、状态、稳定 ID、标题、创建/更新时间与可用复制动作；不把状态、时间或复制混入正文节点。
2. **详情按阅读问题组织。** 每个对象以少量固定语义节点承接当前最需要理解的事实，而不是逐字段铺开。节点默认展开，使用同一圆点、整行折叠和 Markdown 正文。
3. **终态是处置，不是另一套时间线。** 只有终态对象才出现 `disposition_summary`；它与对象的 `updated_at` 共同构成最后一次有效记录，不新增关闭、退出或分流时间字段，也不把处置做成强警报模块。
4. **列表只帮助定位。** 卡片保留身份、状态、标题、必要优先级和更新时间；ADR/Pitfall retired、Spark terminal 才补一段弱处置正文，Study 不在列表复述报告摘要。
5. **关联在主阅读之后。** 关联区只呈现来源已有的正式关系或外部资料。可读对象先解析标题、状态与可复制路径；未解析或跨项目引用如实保留其稳定身份，不把导航信息写成新的事实判断。
6. **详情与扩展阅读同源。** ReadingPanel 复用同一身份头部和阅读布局；Study 正文是同一 Markdown carrier 的进入入口，不在主详情复制第二份全文。

WorkCase 后续可以增加进度、执行态势和关闭材料等专属内容，但必须先落在这六项共同秩序中：专属派生信息回答推进问题，不能替代身份、事实正文、终态处置或关联来源。

### 4.2 WorkCase 人的阅读视角

WorkCase / 工作项是工作主线对象，可以拥有不同于研究、决策、火花、经验和提交的专用阅读形态；但它仍必须继承同一套身份头部、卡片框架、复制语义、右侧阅读和弱装饰语言。WorkCase 的设计语言必须先继承五个成熟模块的基线，新的专用表达只能围绕“工作项对象更复杂”来增加，不能另起一套视觉和信息秩序。专用形态只服务人的阅读任务，不允许把执行项提升为一级对象或另起一套状态事实。

工作项列表优先回答 Human 的四个问题：

1. 我现在最该看哪个工作项；
2. 这个工作项是否需要我处理或确认；
3. 这个工作项当前卡在哪里；
4. 这个工作项是否已经具备关闭判断材料。

在呈现这四个问题以前，WorkCase 卡片先按“方案待确认 / 推进中 / 关闭待确认 / 已关闭”四个进展分组帮助 Human 定位。该分类轴只叫“进展分组”，不是 WorkCase 生命周期或正式状态。只有“推进中”继续显示工作项执行、主控自检、独立复核、主控收敛四个推进环节；创建前方案审核尚无 WorkCase，不形成 Card 或分组。推进中可以以轻微且尊重减弱动态偏好的动效提示当前位置，其它三组不得借动效或推进轨迹暗示仍在自动推进。执行项态势条仍可如实显示其各项状态，但不代替进展分组、正式 phase、授权或完成判断。

“方案待确认”Card 的正文固定为目标、成功标准两个计划判断区，分别直接读取 `goal` 与当前 profile 的标准陈述集合。两项完整显示，不截断、不折叠、不限制标准条数，也不在 Web 重新摘要。覆盖、排除和其它 `scope` 技术边界，以及执行步骤、工作项、验证安排和创建审核详情留在同源详情页。该简化只改变列表信息选择，不缩减 21 对完整计划批准材料的要求。

该 Card 的排版固定为“16px/600 对象标题 → 13px/600 判断区标题 → 12px/20px 事实正文 → 11–12px 元信息”。标题、判断项标题、判断项正文和元信息必须分别使用共享语义类，不在业务组件内临时指定字号；成功标准陈述即使使用紧凑字号也仍属于事实正文，不能使用弱色、mono 或辅助标签语义。

成功标准是并列集合，统一使用圆点；只有来源已明确表达步骤、优先级、排名或依赖顺序时才使用数字序号。不得把数组位置、criterion ID 或显示排序视觉化为先后关系。

内部 `closure_preparing` 投影为“推进中 / 主控收敛”；直到 Controller 形成完整关闭材料并实际进入 `human_closure_confirming`，进展分组才切换为“关闭待确认”。不得在 Human Gate 尚未成立时提前提示 Human 处理。

因此 WorkCase 列表卡片的信息层级应为：

```text
工作项身份 / 优先级 / 进展分组
推进中时的推进环节
需要 Human 处理的关闭或异常信号
执行态势条
少量执行项队列
更新时间
```

WorkCase 详情页优先回答“是否能继续推进或关闭”，信息层级应为：

```text
身份头部
工作项进度 / 成功标准进度 / 关闭材料
执行态势总览和执行项队列
成功标准
验证证据
关闭证据
检查安排
目标 / 所属工作项 / 来源
关联材料
```

执行项只表达 WorkCase 内部恢复、角色分工、阻塞和证据线索。执行项状态显示必须回到 `pending / in_progress / blocked / done / skipped`，UI 文案对应“待执行 / 执行中 / 已阻塞 / 已完成 / 已跳过”。旧的 `planned / executing / verifying / absorbing / ready` 只可作为兼容读取输入，不作为新的图例、文案或页面设计语言。

### 4.3 组件契约沉淀

以下组件契约属于已确认的跨页面设计语言。最前面三个入口 / tab 的信息架构未定时，仍必须遵守这些组件契约，但不得把临时入口名称写入最终结构。

| 组件族 | 统一契约 | 不得出现 |
|---|---|---|
| Tab / 筛选 | 使用 `ldvh-tab-list`、`ldvh-tab-button`、`ldvh-tab-button-active`、`ldvh-tab-button-idle`、`ldvh-tab-count`；同层 tab 数字与文字同字体、同字号、同字重 | 单页自定义胶囊、加粗数字、营销式分段控件、顶部对象类型 tab 替代左侧导航 |
| Card | 使用 `ldvh-section-grid` 和 `ldvh-panel`；标题完整换行；右上只放复制入口；更新时间固定在底部右侧 | 表格化对象列表、标题截断、右上堆叠多个强按钮、卡片内大面积装饰色 |
| Identity Header | 顺序固定为 `类型标签 + 状态标签 + object-id`、标题、标签、创建/更新时间、右上复制对象路径；详情页和右侧预览同源 | 状态漂移到右上操作区、对象详情和 ReadingPanel 两套头部、ID 做大号标题 |
| Reading Node | 小圆点标题、整行点击、`ChevronDown` / `ChevronUp`、Markdown 内容区、默认展开 | 每个对象类型自定义折叠样式、正文节点内放额外“展开/收起”文字按钮 |
| Reference Row | 左侧语义图标 + 标题/路径/URL，右侧复制入口 + 扩展阅读入口；整行打开扩展阅读，复制不触发展开 | 对象、文档、URL 各自使用不同卡片、文字按钮或操作尺寸 |
| ReadingPanel / 移动抽屉 | 顶部控制区固定，正文独立滚动；桌面右侧面板，Compact 切换为底部抽屉 | 右侧对象列表导航、只开不关的单向入口、移动端另做独立站或底部主导航 |

## 5. 复制语义

复制按钮不是泛化“复制”动作，必须让 Human 和 AI 都知道复制结果是什么。

| 场景 | Tooltip | 复制内容来源 |
|---|---|---|
| 精确可读的对象详情头部、对象引用、右侧对象预览 | 复制对象路径 | 精确读取返回的 `canonical_path`；缺失、无效或候选列表时不显示复制入口 |
| 本地 Markdown 文档、Study 正文入口 | 复制文档路径 | 文档绝对路径或规范化后的 Markdown 文件路径 |
| 外部 URL | 复制链接 | URL `ref` |
| 非对象、非文档、非 URL 的普通引用 | 复制引用 | 原始引用文本 |
| 提交卡片 | 复制提交上下文 | 面向 AI 定位的稳定多行提交上下文 |
| 提交详情 | 复制提交 hash | 完整 commit hash |
| ProjectFiles 工具页 | 复制路径 | 项目路径、文件路径或 diff 文件路径 |

对象路径复制不得依赖可能只是对象 ID 的 `target`、列表 `path` 或导航键作为来源。`canonical_path` 只是预期位置，仍须与精确读取的 `check_status: readable` 一起成立；否则页面显示实际读取状态、问题和未读取范围，而不复制路径。

## 6. 后续开发顺序

后续继续推进 Web 时，推荐按以下顺序做判断：

1. 目标是否影响五个基准模块；如果影响，先保证五个模块一起变化。
2. 目标是否影响详情页和右侧扩展阅读；如果影响，两处必须复用同一布局或同一字段组件。
3. 目标是否影响列表卡片；如果影响，先对齐研究、决策、火花、经验对象卡片和提交卡片。
4. 目标是否新增复制、图标、状态、时间或 tab；如果新增，先检查全局设计、图标语义和 i18n。
5. 目标是否改变 API、事实源读取或状态派生；如果改变，补充或说明对应测试验证。
6. 目标是否读取 Git commit records；如果读取，必须复用 `web/api/services/git.ts` 的 commit message 拆分和 Conventional Commits 解析，不在页面 API 中维护第二套 parser。

## 7. 不再采用的方向

1. 不把对象详情退回 YAML 字段平铺。
2. 不让每个对象类型各自发明卡片、节点标题、复制按钮、关联行或时间位置。
3. 不把提交页当成独立视觉系统；提交是五个基准模块之一。
4. 不在右侧扩展阅读区维护第二套对象摘要。
5. 不用“复制完整路径”作为通用文案覆盖对象、文档、链接、引用和提交这些不同动作。
