# 开发实践规范

> 创建日期：2026-05-28
> 定位：接入 PM Kit 的项目必须具备的开发实践事实源规范，确保 AI 知道项目怎么跑、怎么检查、怎么验证
> 适用范围：所有接入 PM Kit 且包含代码或配置修改的项目
> 上位依据：specs-v2/00、specs-v2/10

---

## 一、本文解决的问题

本文解决的问题是：AI 进入一个项目后，如何知道这个项目怎么跑、怎么检查、怎么验证、怎么汇报开发完成。

PM Kit 中 AI 不得凭惯例推断检查命令。每个项目的开发实践事实源必须由项目自身维护，AI 只能依据该事实源执行检查和验证。本文定义的是"项目必须具备什么开发实践事实源、AI 必须依据什么执行"，不是"怎么开发软件"。

本文不重新定义管理对象总表，不定义具体技术栈、具体命令或具体验证步骤，不定义 PM Web Tools 页面或 API。

---

## 二、与 00 总纲的关系

00 定义 PM Kit 的核心问题是：AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。

本文对该问题的回应是：用开发实践事实源让 AI 能够判断：

1. 这个项目用什么技术栈；
2. 改完代码后怎么检查；
3. 改完代码后怎么验证；
4. 开发完成后怎么汇报；
5. 哪些验证是必须的，不能跳过。

---

## 三、开发实践事实源的定位

开发实践事实源回答"如何开发并完成开发阶段验证"。

它不是：
- 开发方法论或开发流程指南；
- 发布交付实践（归 56-交付实践规范）；
- 任务对象状态、关闭字段或 Review Gate（归 specs-v2/14）；
- AI 协作语义、Human Gate 或 Rule / Skill / Agent 边界（归 specs-v2/11）；
- 踩坑记录（归 `pm-kit-base/pitfalls/`）；
- 审计发现（归 specs-v2/51 或 pm-kit-base 分流对象）。

---

## 四、开发实践事实源必须包含

接入 PM Kit 的项目，其开发实践事实源必须包含以下内容：

### 4.1 项目技术栈

项目使用的技术栈，至少说明各层级的技术和位置。

### 4.2 本地启动与运行

项目如何在本地启动和运行。

### 4.3 开发检查命令

不同类型修改对应的检查命令。AI 不得凭惯例推断检查命令，必须以开发实践事实源或项目文件为依据。

若项目暂未定义统一检查命令，应在事实源中明确声明。

### 4.4 修改类型与局部验证要求

不同修改类型对应的必须执行项和通过标准。至少覆盖：

| 修改类型 | 必须执行 | 通过标准 |
|---|---|---|
| 前端显示或交互修改 | 语法检查、浏览器验证、控制台检查 | 页面正常加载，目标 UI 符合需求，控制台无相关错误 |
| 前端数据渲染修改 | 语法检查、浏览器验证、必要时核对 API 返回 | 页面展示与数据结构一致 |
| 服务端修改 | 语法检查、服务启动或重载验证、相关 API 验证 | 服务可启动，API 行为符合预期 |
| API 协议或数据结构修改 | 服务端检查、前端验证、API 返回核对 | 前后端字段一致 |
| 文档修改 | 链接、编号、事实源归属检查 | 链接有效，归属合规 |
| 配置修改 | 配置读取或启动验证 | 配置可被正常读取 |
| 结构化对象 YAML 修改 | YAML 结构检查、字段归属检查 | YAML 可解析，字段合规 |

### 4.5 开发完成汇报要求

AI 汇报开发任务完成前，必须说明：

1. 修改了什么；
2. 涉及哪些文件；
3. 执行过哪些检查命令；
4. 做过哪些浏览器、API 或配置验证；
5. 是否存在未验证项及原因。

若只完成代码修改但尚未验证，应汇报"代码修改完成，验证未完成"，不得汇报"任务完成"。

### 4.6 技术红线

开发实践中必须遵守的技术红线：

1. 不得提交密钥、令牌、Cookie 或其他敏感凭据；
2. 新增依赖、新框架或新运行时前必须先确认；
3. 不得绕过 pm-kit-base 和 docs 的事实源分工；
4. 不得把当前任务状态、负责人、处理进度写入需求文档；
5. 不得仅凭惯例推断检查命令，必须以开发实践事实源或项目文件为依据。

---

## 五、开发实践事实源不得包含

1. 发布步骤、发布记录、线上回滚（归 56-交付实践规范）；
2. 任务状态、具体业务需求（归 pm-kit-base 或需求文档）；
3. AI 协作语义、Human Gate、Rule / Skill / Agent 边界（归 specs-v2/11）；
4. 踩坑记录（归 `pm-kit-base/pitfalls/`）；
5. 审计发现列表（归 specs-v2/51 或 pm-kit-base 分流对象）。

---

## 六、AI 执行规则

### 6.1 修改代码前必须读取

AI 修改代码前，必须先读取当前项目的开发实践事实源，确认当前项目的开发检查和局部验证要求。

### 6.2 不得凭惯例推断

AI 不得凭惯例推断检查命令。若开发实践事实源中未定义某类修改的检查命令，AI 应先询问用户是否补充，而不是自行推断。

### 6.3 验证是开发完成的必要条件

开发完成汇报必须包含验证结果。未验证的修改不得汇报为"任务完成"。

### 6.4 前端修改必须浏览器验证

仅通过语法检查不能作为前端显示或交互修改完成依据。前端修改必须经过浏览器验证和控制台检查。

---

## 七、实践沉淀规则

当用户指出 AI 在开发、检查、调试或局部验证中遗漏必要步骤时，AI 必须判断该遗漏是否暴露开发实践事实源缺口。若是，应询问用户是否将该实践补充到开发实践事实源；用户确认后，应更新开发实践事实源并记录 Change 记录。

---

## 八、开发验证与 Evidence 的关系

开发验证是 Evidence 的重要来源，但开发实践规范不定义 Evidence 对象本身。

- **"怎么验"** → 本规范（开发实践事实源）
- **"验完的结果归哪"** → specs-v2/21（Task 关闭证据）和 specs-v2/10（记录事实源边界）

开发验证结果应作为 Task 关闭证据的一部分，但开发实践规范不重复定义 Evidence 字段。

---

## 九、无代码项目

无代码项目（纯文档、纯配置、纯规则项目）仍应保留开发实践事实源文件，但内容可以为空或只声明"本项目无代码修改，开发检查和验证要求不适用"。

不得因为项目无代码就删除开发实践事实源文件。

---

## 十、初始化与审计

开发实践事实源由 AI 在项目初始化时根据项目实际技术栈、运行方式、检查命令和验证路径生成。初始化时若开发实践事实源已存在则跳过不改动，但应在审计时检查其是否与当前项目实际一致。初始化流程见 specs-v2/50，审计流程见 specs-v2/51。

---

## 十一、与 56-交付实践规范 的边界

| | 55 开发实践规范 | 56 交付实践规范 |
|---|---|---|
| 阶段 | 开发阶段 | 发布阶段 |
| 核心问题 | 怎么跑、怎么检查、怎么验证 | 怎么发布、怎么验证发布、怎么回滚 |
| 事实源 | specs-v2/55 | specs-v2/56 |
| Evidence 来源 | Check、Run、本地验证 | Approval、发布确认、发布后验证 |
| 可以为空吗 | 不可以 | 可以，无发布流程时声明为空 |
| AI 误判风险 | 凭惯例推断检查命令 | 凭惯例推断发布步骤 |

发布前可以引用 55 的开发检查结果，但不得重复维护 55 中的局部开发验证细节。

---

## 十二、不进入本文的内容

以下内容不进入本文，由其他规范或后续实践承载：

1. 具体项目的技术栈、启动命令、检查命令和验证步骤；
2. PM Web Tools 的开发相关页面或 API；
3. 发布交付实践（归 56-交付实践规范）；
4. Evidence 对象的完整定义（归 specs-v2/21 和 specs-v2/10）；
5. AI 协作语义和 Human Gate（归 specs-v2/11）；
6. 初始化流程的完整定义（归 specs-v2/50）。
