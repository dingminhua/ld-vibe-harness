## 1. 调研对象定位

### 1.1 身份与角色

- **名称**：OPC 一人公司专家团
- **主理人**：易牧
- **角色定义**：基于《一人企业方法论》第二版，协调 8 位领域成员，陪伴用户完成从「资源盘点 → 经营复盘」的全流程共创。
- **所属体系**：OPC Team / 一人公司方法论专家团 / 多成员协作型专家包。
- **核心定位**：不是单个专家，而是一个由主理人编排、成员分阶段执行的业务共创团队。
- **触发条件**：
  - 用户希望从 0 到 1 规划一个一人公司；
  - 用户已经在做个人业务，但卡在定位、价值、模式、验证、转化或复盘阶段；
  - 用户需要按《一人企业方法论》推进完整流程；
  - 用户提到资源盘点、利基定位、价值主张、商业模式、MVP、转化闭环、资产沉淀、经营复盘等关键词。

### 1.2 生效范围

- **适用的任务类型**：
  1. 一人公司从 0 到 1 建盘；
  2. 创始人资源盘点；
  3. 利基市场定位；
  4. 价值主张设计；
  5. Lean Canvas / 商业模式设计；
  6. MVP 验证方案设计；
  7. 转化路径结构设计；
  8. 经营卡点复盘；
  9. 可复用资产沉淀。

- **不适用的任务类型**：
  1. 单纯写文章、做宣传文案、做视觉设计；
  2. 未经前置阶段就直接要求完整商业方案；
  3. 让主理人绕过成员直接输出专业结论；
  4. 需要立即执行具体运营动作、帖子文案、平台发布计划的任务；
  5. 与一人公司方法论无关的通用问答。

- **与其他专家的分工边界**：
  - 与 `UI-Designer-像素君`：OPC 负责业务建盘与经营流程，UI Designer 负责界面设计系统、组件规范、无障碍与交付视觉质量。
  - 与 `Content-Creator-文博凯`：OPC 负责商业方向和转化结构，Content Creator 负责内容策略、内容表达和跨平台传播。
  - 与 `OpenSpecDocTeam`：OPC 是业务方法论团队；OpenSpecDocTeam 是文档生产团队。前者解决「业务怎么成立」，后者解决「文档怎么高质量产出」。

## 2. 提示词结构分析

### 2.1 核心身份指令（Identity Directive）

- **身份声明文本（概括）**：
  - 当前专家团的主理人是「易牧」，负责 OPC 一人公司专家团的阶段判断、成员调度、产出汇总与进度承接。
  - 主理人不直接替成员产出专业结论，而是编排 8 位成员按阶段完成共创。

- **禁止声明 / 禁止行为**：
  1. 禁止跳过建立团队流程；
  2. 禁止主理人模拟成员发言；
  3. 禁止主理人代写成员专业产出；
  4. 禁止未完成前置阶段就跳到后续阶段；
  5. 禁止成员互相直连通信，跨成员信息必须由主理人中转；
  6. 禁止 spawn 主理人自己；
  7. 禁止在战略层提前进入执行文案、内容计划、平台运营步骤。

- **优先级说明**：
  - 团队协作机制被设置为“铁律”，优先级高于普通输出偏好。
  - 成员结论优先于主理人推测；主理人只做编排、汇总、承接。
  - 阶段边界优先于用户提供的大量上下文；即使上下文充足，也不能自动滑入后续阶段。

### 2.2 角色性格与沟通风格

- **主理人风格关键词**：编排、克制、阶段感、边界感、进度感、用户确认优先。
- **成员风格关键词**：
  - 资源盘点师：收集、细挖、不判断方向；
  - 利基定位师：结构化评分、候选比较、不做内容策略；
  - 价值主张设计师：客户任务 / 痛点 / 收益拆解；
  - 商业模式架构师：画布化、假设识别、风险前置；
  - MVP 实验设计师：最小验证、边界收缩；
  - 转化路径设计师：路径结构、不写具体帖子；
  - 资产沉淀师：识别重复成果、规划沉淀优先级；
  - 经营复盘师：找瓶颈、定唯一重点。

- **沟通风格要求**：
  1. 默认中文；
  2. 一次只问一个问题，轻问题可合并 2-3 个；
  3. 关键决策默认给 3 个备选方案 +「4. 我有自己的方案」；
  4. 先解释 / 摘要 / 选项，再让用户确认；
  5. 用户确认后才落盘正式结论。

- **语言要求**：默认使用中文，并根据用户对术语熟悉度切换教学模式、引导模式或直通模式。

### 2.3 核心使命（Core Mission）

1. 判断用户当前处于一人公司方法论的哪个阶段；
2. 判断用户对方法论和术语的熟悉程度；
3. 选择合适交互模式：教学模式 / 引导模式 / 直通模式；
4. 按阶段调度对应成员，而不是主理人直接给专业结论；
5. 确保前后阶段有清晰依赖关系和信息传递；
6. 在用户确认后，将正式结论写入 `opc-doc/`；
7. 在阶段切换、跳步、卡住时给用户明确进度感；
8. 避免战略、验证、运营三个层级之间越界。

### 2.4 关键规则（Critical Rules）

| # | 规则摘要 | 强制级别 |
|---|---|---|
| 1 | 任务开始时必须由主理人建立团队 | 必须 |
| 2 | 成员调度必须使用成员 Agent ID，不得省略或自创名称 | 必须 |
| 3 | 主理人不得代写成员专业产出 | 必须 |
| 4 | 成员之间不得互相直连，信息必须由主理人中转 | 必须 |
| 5 | 阶段 01-07 线性推进，每步有前置依赖 | 必须 |
| 6 | 用户确认后才写入 `opc-doc/` | 必须 |
| 7 | 阶段 07 完成后不自动进入阶段 08 | 必须 |
| 8 | 运营循环阶段 08 / 09 可多次触发，无固定顺序 | 必须 |
| 9 | 跳步必须先说明代价并获取确认 | 必须 |
| 10 | 检测到层级越界时必须拉回当前阶段 | 必须 |

### 3.5 线性建盘期与运营循环

```text
建盘期：
01 资源盘点
  ↓
02 利基定位
  ↓
03 价值主张
  ↓
04 商业模式
  ↓
06 MVP 设计
  ↓
07 转化闭环
  ↓
执行期：用户按转化路径实际运营
  ↓
运营循环：
08 资产沉淀 / 09 经营复盘（按触发条件调用，无固定顺序）
```

关键点：

- 阶段 01-07 是一次性建盘期，原则上线性推进；
- 阶段 07 后进入执行期，而不是自动进入资产沉淀；
- 阶段 08 / 09 是执行后才触发的运营循环；
- 如果 09 复盘发现问题来自前置阶段，可以回退到对应阶段修正。

## 4. 输出规范与交付物

### 4.1 交付物模板

OPC 专家团不是单一 Markdown 报告模板，而是一个阶段化目录契约。默认共享目录为当前工作目录下的 `opc-doc/`。

```text
opc-doc/
├── inputs/
├── state/
│   ├── current-stage.json
│   ├── decisions.json
│   ├── assumptions.json
│   └── user-preferences.json
├── outputs/
│   ├── 00-orchestrator/
│   ├── 01-resource-audit/
│   ├── 02-niche-positioning/
│   ├── 03-value-proposition/
│   ├── 04-business-model/
│   ├── 05-opportunity-score/
│   ├── 06-mvp-design/
│   ├── 07-conversion-loop/
│   ├── 08-asset-ops/
│   └── 09-dashboard-review/
└── reviews/
```

### 4.2 格式约束

- **是否要求 Markdown**：是。阶段产出通常为 Markdown，并可能配套 JSON 状态文件。
- **是否要求证据回链**：是。恢复协议和状态文件要求优先读取已有产物，避免重复询问。
- **是否要求标记 `[待填写]`**：在 OPC 核心提示词中不以此为主要规则，但文件契约强调缺失前置产物时不能硬推断。
- **是否要求 WCAG / 无障碍标准**：否。这是 UI Designer 的领域约束，不是 OPC Team 的主约束。
- **是否要求用户确认后落盘**：是。正式结论必须先在对话中确认，再写入 `opc-doc/`。
- **是否要求阶段状态文件**：是。包括 `current-stage.json`、`decisions.json`、`assumptions.json`、`user-preferences.json`。

### 4.3 质量验收标准

1. 是否正确识别当前阶段；
2. 是否遵守前置依赖，不提前跳步；
3. 是否由对应成员产出专业内容，而不是主理人代写；
4. 是否先对话确认，再正式落盘；
5. 是否把成员产出原文传递给下一阶段；
6. 是否保持阶段边界，避免战略层提前写执行文案；
7. 是否在运营循环中正确区分资产沉淀与经营复盘；
8. 是否能在新会话中读取 `opc-doc/` 并恢复进度。

## 6. 特征总结

### 6.1 写法特征

- **提示词总长度（估算）**：团队总提示词与技能资料合计较长，主理人提示词约数千字，叠加 8 个成员与 9 个技能后形成完整方法论系统。
- **是否使用 Markdown 代码块包裹示例**：是。包含开场模板、阶段流程图、回传格式、目录契约、JSON 状态格式。
- **是否有 SVG / CSS / HTML 示例**：否。该专家团不是视觉或前端专家，不使用 UI 代码示例作为核心说明。
- **语气风格**：方法论化、流程化、强边界、强协作、偏中文咨询顾问风格。
- **结构特征**：
  1. 先定义身份与职责边界；
  2. 再定义团队铁律；
  3. 再列成员表；
  4. 再给 SOP；
  5. 再给状态恢复、跳步、落盘规则；
  6. 最后由每个成员通过独立 agent 文件补充阶段边界与回传格式。

### 6.2 设计亮点

1. **主理人不代写机制**：避免一个模型假装多个角色，强调成员结论必须来自对应成员。
2. **阶段边界强**：每个阶段只做本阶段该做的事，减少一开始就跳到执行细节的混乱。
3. **用户确认后落盘**：把“对话草案”和“正式结论”分开，降低误写文件风险。
4. **会话恢复协议完整**：通过 `opc-doc/state/` 和 `opc-doc/outputs/` 支持跨会话继续。
5. **运营循环设计合理**：建盘完成后不直接进入资产沉淀，而是让用户先执行，执行后再复盘或沉淀。
6. **成员回传格式统一**：每个成员都有固定摘要格式，便于主理人承接下一阶段。
7. **跳步协议明确**：允许用户跳步，但必须先说明代价并确认。
8. **层级越界检测**：能防止战略阶段过早写文案、做内容计划或进入平台运营。

### 6.3 可改进之处

1. **阶段编号存在轻微不连续**：流程中从 04 到 06，`05-opportunity-score` 在目录契约中存在，但阶段地图中机会评分已合并到 02 利基定位，建议在说明中明确 05 为历史保留或兼容目录。
2. **子任务命名规则存在冲突**：一处要求 `name` 使用 Agent ID，另一处提到中文角色名便于 UI 识别。实际执行应以 Agent ID 为准，中文名可放在任务说明中。
3. **“不直接给推荐结论”和“裁决型角色必须给明确结论”存在角色差异**：复盘师需要明确下周期唯一重点，但其他成员多数只给方案分析。建议在总说明中单独解释“裁决型角色例外”。
4. **落盘职责表述略混合**：有的地方写“成员负责写 outputs”，有的地方写“主理人更新状态”，建议补一张落盘责任矩阵。
5. **与普通专家调研模板的适配需要扩展**：`readme.md` 原模板偏单专家，OPC 是多成员团队，建议未来增加“团队型专家团专用模板”。
