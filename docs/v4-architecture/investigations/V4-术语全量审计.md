> 审计范围：`specs/attachments/01.Att.01-LDVH双语术语表.md` 当前登记的 38 个 `current` 术语和 5 个 `proposed` 术语，共 43 个。

## 1. 审计目的

本次审计不是检查术语表字段是否齐全，而是检查每个正式名称是否确实对应一个必要、稳定、边界清楚的概念，并检查中文、英文、定义来源和实际使用是否一致。

审计依据是 `specification-model-foundation` §§12.2–12.7，重点回答：

1. 不使用现有名称时，预期概念能否用普通语言说清楚；
2. 该概念是否需要成为跨规范正式术语；
3. 名称属于行业标准术语、常见描述性表达还是 LDVH 特定术语；
4. 中英文是否指向同一范围，是否存在逐字翻译造成的错误暗示；
5. 正例、反例和相邻概念是否能把边界说清楚；
6. 取消该正式名称、改用普通语言或已有术语后，是否仍能无歧义表达规则；
7. 名称或定义变化是否影响原架构判断，还是只影响表达准确性。

## 2. 方法与外部依据

[ISO 704:2022](https://www.iso.org/standard/79077.html)区分对象、概念、定义和名称，并把术语形成与定义编写作为不同工作；[W3C SKOS Primer](https://www.w3.org/TR/skos-primer/)同样区分概念和用于标记概念的自然语言标签。本文只采用“概念不能由名称反向证明”的原则，不声称 LDVH 已实现 ISO 术语数据库或 SKOS 数据模型。

行业来源只用于判断某个名称是否已有稳定含义，不能替代 LDVH 自身定义。没有足够一手来源的名称一律不标成“行业标准术语”。本轮没有发现必须以行业标准身份保留的 LDVH 术语；大部分名称是常见描述性表达或 LDVH 特定术语。

`Standard Specification` 的歧义判断参考 [IETF RFC 2026](https://datatracker.ietf.org/doc/rfc2026/) 中该表达与标准化状态的实际用法。`Information Traceability` 的边界检查参考 [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 对来源与形成过程的建模范围，但 LDVH 不采用完整 PROV 模型。Working Tree、Index、commit 和历史的技术边界继续以 [Git 官方对象说明](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)为技术参考；它们不负责定义 LDVH 的事实语义。

来源分类含义：

| 分类 | 本文用法 |
|---|---|
| 行业标准术语 | 有直接一手标准或正式规范来源，并且 LDVH 用法没有扩张或改义 |
| 常见描述性表达 | 在相关语境中自然可理解，但本文不主张存在统一行业定义 |
| LDVH 特定术语 | 为 LDVH 内部稳定概念或专名建立的规范名称，含义只由 LDVH 定义来源确定 |

## 9. 与原架构判断的关系

### 11.4 聚焦复核对三个名称分歧的结论

主执行者在汇总阶段提出 `工作对象管辖判定（Work Object Governance Determination）` 新候选。由于该名称不在第一轮独立复核范围内，Human 已给出的独立复核授权继续用于一次只读聚焦检查。独立审查者同时重新核对另外两个替代名称分歧，结论如下：

1. `非根规范（Non-root Specification）` 优于 `统一结构规范（Common-Format Specification）`。当前 01 是根规范与非根规范的闭合分类；后者还容易把固定头尾承担的语义职责误读成纯格式要求。

## 15. 2026-07-18 根规范概念重构后的术语检查增补

00 后续完成概念重构，废除把规范模型、事实模型、行动模板、Code、Web 并列为五类构成要素的旧分类，并将 V1-V8 的正式中文名称改为“V1-V8 价值评判标准”。因此，本文 §§4、12 对旧分类和旧中文名称的判断只保留为当时审计记录，不再证明当前名称与范围；当前定义以 `ldvh-root` §§3、6 为准。本节按 `specification-model-foundation` §12.4 补充两项变更的检查记录，不成为平行定义点，也不改变 00 已定案语义。

### 15.1 语义构成要素（Semantic Component）

1. **预期含义**：按照内容承担的主要语义责任，把 LDVH 稳定组织的规范、事实和可复用行动流程分为三类；该分类不按载体、实现、入口、触发方式或交互方式划分。
2. **必要性**：旧“构成要素”曾同时涵盖三类内容、Code 和 Web，无法继续表达当前仅对语义内容归类的闭集；若不收窄名称，读者会继续把确定性能力或交互职责误列为第四、第五类。
3. **来源分类**：LDVH 特定术语。`semantic component` 在普通技术语境可作描述性组合，但本文不主张其具有统一行业定义。
4. **中英文候选**：采用“语义构成要素 / Semantic Component”；“构成要素”仅作为当前上下文中的中文简写；不采用“语义要素 / Semantic Element”（过宽，不能自然体现组成与归口）、“架构构成要素 / Architectural Component”（会再次自然包含 Code 和 Web）或 `Building Block`（容易暗示实现模块）。
5. **定义核对**：唯一定义来源 `ldvh-root` §3 已直接说明，它是按照主要语义责任对规范、事实和可复用行动流程进行的归类，且不按载体位置、文件类型、运行层级或使用方式划分。
6. **正例与反例**：规范模型、事实模型、行动模板是正例；Code、Web、Helper、Helper CLI、Hook、Gate、页面状态和实现模块不是语义构成要素。
7. **相邻概念**：Code 是确定性执行能力的上位概念；Web 承担面向 Human 的独立交互职责；三种价值交付方式说明能力与内容如何交付价值。三者都与语义内容归类正交，不构成本术语的上位或下位类型。
8. **替换检查**：把定义替入“行动模板是三类语义构成要素之一”和“渐进式披露不属于三类语义构成要素”后，前者仍表示可复用行动流程的内容归口，后者仍排除消费方式；把 Code 或 Web 代入则不满足“按主要语义责任组织规范、事实或流程”的定义。
9. **使用扫描**：当前 Specs 中，完整名称只用于三类闭集、其成员资格及反例边界；00 中无修饰“构成要素”仅出现在“构成要素职责边界”“构成要素章节”等已由 §3 限定的简写上下文。历史 `docs/` 仍保留旧五类分类的形成过程，但不属于当前规则源；本节明确其旧结论不再作为当前术语证据。
10. **影响范围**：00 已先行完成定义变更；下属 Specs 已按三类语义构成要素、Code、Web 和价值交付方式分别对齐。本次只同步术语表首选名称、英文名、中文有效表达和定义来源，不改变字段、Schema、Code、事实对象或文件身份。
11. **检查结论**：语义与名称检查支持将旧登记“构成要素 / Component”改名并收窄为“语义构成要素 / Semantic Component”，保留“构成要素”为受 §3 上下文限定的中文有效表达，且不保留英文 `Component` 为独立有效表达。但 00 §3 首次定义处尚未按 §12.7 同时写出 Canonical English Term，本阶段又禁止修改 00，因此该条先登记为 `proposed`；只有定义来源完成经授权的双语同步并经独立回读后，才能转为 `current`。

### 15.2 V1-V8 价值评判标准（V1-V8 Value Criteria）

1. **预期含义**：00 表格列出的八项价值维度，用于判断 LDVH 的内容、能力、交付方式及其实践是否帮助 AI 获得可辨认的净收益。
2. **必要性**：旧“价值标准”容易被理解为价值观或正式合规标准，“行动标尺”又容易被理解为直接决定行动允许；当前名称需要明确它承担价值评判依据，而不替代规则适用、授权、验证或 Human 决定。
3. **来源分类**：V1-V8 的闭集与编号是 LDVH 特定概念；`value criteria` 是自然的描述性英文，不主张为行业统一模型。
4. **中英文候选**：采用“V1-V8 价值评判标准 / V1-V8 Value Criteria”；不采用“V1-V8 价值标准 / Value Standards”（容易指向价值观或正式标准）、“V1-V8 价值判断 / Value Judgment”（与依据这些标准作出的判断行为混淆）或“行动标尺”（错误暗示直接行动授权效力）。
5. **定义核对**：唯一定义来源 `ldvh-root` §6 已区分“V1-V8 价值评判标准”与“V1-V8 价值判断”，并明确这些标准对设计、纳入和使用发挥指导作用，不替代 AI 普通求解路径。
6. **正例与反例**：V1 定位到 V8 积累的八项维度是正例；行动允许公式、Human Gate 条件、验证要求、具体测试结果和一般道德价值观不是本术语所指标准。
7. **相邻概念**：“V1-V8 价值判断”是依据这些标准对具体实践作出的判断；规范效力、规则适用和行动允许分别回答规则能否作为依据、是否约束当前事项和行动能否推进，不由价值标准单独决定。
8. **替换检查**：把定义替入“新增机制必须接受 V1-V8 价值评判标准审核”后，仍表示用八项价值维度评估净收益；若替入“行动允许”或“Human Gate”，则会错误改变原句的授权或决定语义，证明这些相邻概念不可互换。
9. **使用扫描**：当前 Specs 中，正式名称只见于 00、01 与术语表，均指向同一八项维度；`V1-V8 Value Criteria` 与 00 正文一致。旧中文名称和“行动标尺”仅保留在历史调查、提案或执行计划的旧称说明中，不作为当前规范表达。
10. **影响范围**：00 已先行完成中文名称与定义边界变更；01 及下属 Specs 已同步当前称谓。本次只更新术语表中文首选名和 §6 回指，不改变 V1-V8 的数量、判断问题、机器表示、Code、Schema 或事实记录。
11. **检查结论**：把中文首选名称从“V1-V8 价值标准”改为“V1-V8 价值评判标准”，沿用已审定的英文 `V1-V8 Value Criteria` 和缩写 `V1-V8`；旧中文名称与“行动标尺”不作为其他有效表达继续登记。
