## 1. 价值判断

本文的价值，是把五类事实对象创建后反复出现的“读取当前快照与关系、区分更正/普通更新/生命周期变化/多对象承接、核对具体类型规则与授权、形成目标快照、选择原子能力、回读验证和交还”组织为稳定行动结构。它减少用内容修改偷渡状态推进、用状态变化覆盖事实更正、以旧指纹覆盖并发变化、把替代拆成不一致的多次写入，以及关闭旧对象却丢失剩余事实与关系的风险。

普通更新、WorkCase phase/status 推进、Spark 路由、五类关闭或退出、ADR/Pitfall/Study 整体替代虽然领域条件不同，但共享同一变更边界；差异由 20–24 定义，不为每个动作词复制模板。单纯读取、创建全新且无承接关系的对象、Git 提交或一次性文件编辑不适用。

## 2. 规范依据

本文直接依据：

1. `action-template-foundation`：规定模板共同结构、授权、能力、失败分流、验证和交还；
2. `fact-model-foundation`：规定事实对象共同更新边界、单对象 CAS 操作、多对象变更的原子性要求和具体类型权威分工；
3. `spark-fact-type`、`workcase-fact-type`、`adr-fact-type`、`pitfall-fact-type`、`study-fact-type`：分别唯一规定内容更正、状态/阶段转换、字段失效、关系、关闭、替代、退出、证据和 Human Gate。

本文不得把上述来源的转换表、字段清单或证据条件复制为模板规则。04、07、Human 指令、项目规则和实际能力按当次对象提供服务、实现、授权和验证输入。

## 3. 职责边界

本文负责定义：

1. 既有对象变更候选的进入、排除、不确定和作用范围；
2. 当前对象、关系闭包、来源、证据、授权与并发基线的读取顺序；
3. `fact_correction`、`content_update`、`single_object_lifecycle` 和 `multi_object_disposition` 四类当次变化闭集，以及按完整写集合和共同不变量分类的边界；
4. 完整目标快照、单对象 CAS、多对象原子能力、回读验证和失败交还的稳定关系；
5. 合法多步序列与多对象原子事务的区别；
6. 新对象创建、Git 提交、能力缺口和残留责任的分流。

本文不负责定义：

1. 各类型合法状态、阶段、转换边、进入条件、关闭分类、关系或字段失效；
2. 自然语言事实是否真实、证据是否充分、审核是否独立或 Human 决定是否成立；
3. Helper 请求响应字段、CAS 算法、事务、锁、文件替换、回滚、错误码或测试实现；
4. 删除、迁移、批量修复或 Git 历史操作的实现；
5. 无承接关系的新对象是否应创建；
6. commit、push、PR、发布或上层工作完成。

20–24 定义“什么变化合法”；本文定义“如何组织一次变化”；05/04 定义可调用的领域/共同服务契约；Code 只执行已实现的确定性检查和状态变更。任何一层不得代替另一层。

## 4. 适用范围

当目标明确指向至少一个当前事实对象，并准备改变其内容、状态、阶段、关系、终态或承接位置时，本模板产生候选。执行状态变更前必须能够：定位唯一管辖项目和实际 worktree；以稳定引用读取当前对象与必要关系闭包；确认具体类型来源和当次授权；取得支持并发检测的当前内容基线；判断变更属于单对象还是必须多对象共同成立。

只读消费、候选对象化判断、无承接关系的新对象创建、普通文件编辑、Git 提交或类型来源本身修改不适用。目标、当前对象、来源、授权、关系闭包或原子范围不确定时，只继续只读核对或交还，不猜测变更。

## 5. 事实对象生命周期变更与承接处置行动模板定义

### 行动模板声明

| template_key | summary | definition_ref |
|---|---|---|
| `fact-object-lifecycle-change` | 对既有事实对象区分更正、普通更新、单对象生命周期变化与多对象承接，按当前类型规则和可用原子能力执行、回读和交还 | `fact-object-lifecycle-change-action-template::5. 事实对象生命周期变更与承接处置行动模板定义` |

### 5.1 输入与前置条件

执行者必须取得：Human 当前目标与授权；唯一项目/worktree；目标稳定引用；当前完整对象、内容指纹与必要关系闭包；具体类型来源；支持变更声明的来源、证据、审核和 Human 决定；实际可用的读取、单对象 CAS 或多对象原子能力。旧摘要、路径猜测、Web 卡片、缓存指纹或模板中的状态词不能替代当前对象回读。

### 5.2 参与者、能力与授权

AI 负责分类变更、解释类型规则、核对来源证据、确定原子范围、形成完整目标快照、处理并发与验证结果。Human 只承担类型来源和当前指令保留的方向、批准、关闭、风险或承接决定。Helper/Code 只对已声明且实现的稳定引用、机械校验、CAS、原子变更、关系图和回读提供能力；单对象能力存在不表示多对象能力已经存在。

### 5.3 行动步骤与分支

#### A. 建立当前对象和影响闭包

1. 定位唯一项目/worktree，以稳定引用精确读取目标对象并保留 `content_fingerprint`；
2. 按具体类型来源展开会影响合法性、基数、DAG、依赖、替代、路由或承接的目标与反向关系；
3. 核对当前状态/阶段、来源、证据、版本、审核、批准、阻塞和未完成读取范围；
4. 读取当次授权，区分“允许修改内容”“允许推进状态”“允许关闭/替代/承接”等不同作用范围。

#### B. 分类变化并确定原子范围

当次变化必须且只能归入以下一类。分类依据是变化完整成立所需的写集合、关系和共同不变量，不是用户使用了“修正”“更新”“关闭”“路由”或“替代”等动作词：

1. `fact_correction`：修复同一对象中的错误事实，对象身份及 status/phase 保持不变；WorkCase v1→v2 是本分类内一次性语义迁移，以 profile 与结构迁移为主，并可同时执行获得明确授权的当前语义修正，但不得偷渡生命周期推进；其它更正若同时需要生命周期变化，整体改按 `single_object_lifecycle` 分类；
2. `content_update`：补强或更新仍属于同一对象的当前内容，对象身份及 status/phase 保持不变；与事实更正的差异由 AI 根据来源和实际含义判断，Code 不裁决二者；
3. `single_object_lifecycle`：完整成立只需要修改一个既有对象，并且具体类型来源明确允许由一个完整目标快照完成；所需批准、版本、结果、条件字段和关系变化必须在同一对象快照中共同成立；
4. `multi_object_disposition`：完整成立要求创建或修改两个以上对象，或者多个对象、关系和状态必须共同生效；全部写目标、前置指纹和共同不变量属于同一原子范围；
5. 关闭、路由、直接落实或关系变化不因名称自动成为多对象处置。若目标对象已存在且无需修改、反向关系只由 Code 派生，或直接落实只改变一个对象且无需建立事实承接关系，则仍可按类型来源判断为 `single_object_lifecycle`；若必须新建或更新承接目标，或同时改变多个对象、关系或状态才能完整成立，则属于 `multi_object_disposition`；
6. 若变化实质上是无承接关系的新对象创建，转交 `fact-object-controlled-creation`；若只是 Git 提交，另按 `git-commit` 判断。

#### C. 执行单对象分支

1. 依据具体类型来源形成排除 Code 托管字段后的完整目标快照，或在类型来源已经定义专属确定性 delta 时形成其要求的显式顶层变化与托管记录输入；两种路径都必须由 AI 显式处理条件字段、版本、审核与批准失效。类型来源要求直接落实判断时，AI 先 F3 读取对象并按需 F4 核对必要依据，再取得相应 Human 当前授权；F4 不写入对象、关系或 CAS 请求；
2. 使用最近回读的指纹调用范围匹配的单对象操作。其它事实类型和 legacy WorkCase 使用 `update-fact-object`。v1 WorkCase 不得普通推进；只有一次性 v1→v2 `fact_correction` 可以使用 generic `update-fact-object` 提交完整 after snapshot。v2 正常变化需要形成、替换当前 review、Controller 当前处置或 Human approval 时必须使用 `update-workcase`；其它完整目标可使用 `update-fact-object`。v2 已托管 review/approval 事实的更正也必须按获得明确授权的 `fact_correction` 走 generic `update-fact-object` 完整 after，不得冒充普通更新或绕过 Human/Reviewer 字段所有权。Code 对托管事件的防绕过检查以 after 进入 v2 为边界，不能因 before 的 profile 缺失、未知或机械无效而跳过；合法 v1→v2 迁移仍由本节迁移不变量单独约束。对 valid-before v2，普通 generic `fact_correction` 必须保持 review 成员数量、身份与顺序不变；只有来源定义的 plan/result 升版 reset 或 v1→v2 迁移才可移除被替代 review。Reviewer 同事件更正改变 `scope`、`conclusion` 或 `feedback`，并使 creation review 或已经离开 `independent_reviewing` 的 result review 按最终条件必须具有 `controller_resolution` 时，可以在 status/phase 不变的同一更正中原子补入该必需处置；其它新处置仍走 `update-workcase`。invalid-before 托管记录窄修复只允许在审核事件身份完整且原样保留、status/phase 不变，且对象仅因一个且仅一个 review 成员缺少必需的 `controller_resolution` 而无效时，补入该处置；除 Code 写入新的 `updated_at` 和仅在该 review 成员中补入缺失处置外，after 必须与 before 完全一致，并在补入后全机械有效，不得借修复更正其它内容、形成新 review/approval 或改变事件时点、版本、身份和生命周期位置。其它由来源允许的 invalid-before 普通字段修复，必须使 `creation_reviews`、`result_reviews`、`execution_approval` 与 `closure_approval` 分别和 before 完全一致，不得借对象的机械错误改写同一事件内容。指纹变化时拒绝覆盖，重新读取并由 AI 判断目标是否仍成立；
3. `no_change` 不制造时间或成功变更；拒绝、失败、回滚、部分结果和不可观察结果按实际结果交还；
4. 写入后精确回读当前对象及必要关系闭包，分别验证机械成立与类型语义成立范围。

WorkCase v1→v2 迁移只能在 Human 明确授权的完整事实更正中执行。after 必须移除 `audit_summary`、`progress_history`、`improvement_observations`、`nonbinding_followups` 和每个 `review_basis`，可收敛冗余或错误表达，并删除经语义判断已被替代的 review。对 before 已存在的每一类 creation/result reviews，after 必须至少保留一项；保留的 review 成员按原顺序形成非空子序列，且每个成员的 reviewer、reviewed_at、subject_version、scope、conclusion 与 feedback 保持不变。before 为空或字段未形成时 after 不得新增，最终 presence 由 phase/Schema 决定。一般语义清理不得改写 Reviewer 话语；确需纠正 Reviewer 自有字段时，必须先完成不改变这些字段的迁移，再依据字段所有者或原始来源授权，以独立的同事件 `fact_correction` 处理。`controller_resolution` 是 Controller 当前处置，只有 Human 明确授权覆盖这项托管内容时才可按最终 v2 条件校准；Code 不判断其语义。Code 只锁定对象身份、status/phase、plan/result version、approval `subject_version`/`approved_at`、Reviewer 自有字段及顺序；closed 迁移还必须锁定 `closure_outcome`，不得重开或改关闭分类。Code 不判断哪些表达修正、review 删除、处置校准或 Human 决定语义成立；机械通过不等于语义授权或正确。closed v1 默认只读，只在有明确统一结构消费需要时执行一次迁移；完整 after 可修正 validation/disposition/approval summary 的表达精度与一致性，但不得伪造 Human 决定。

`fact_correction`、`content_update` 和 `single_object_lifecycle` 可以复用同一共享单对象 CAS 事务，但调用前的语义分类、授权、来源与证据判断保持不同。专属 delta 只把 AI/Controller 已经决定的变化确定性形成完整 after，不得提供复制类型状态机的 `advance`、`pass`、`close` 等语义命令，不得从 Reviewer conclusion 或普通字段差异决定 phase、版本、复审或 Human Gate。CAS 请求不增加由 Code 判断的自然语言分类字段；指纹冲突后不得把旧目标静默重试到新快照。

#### D. 组织合法多步序列

1. 只有每一步都能独立形成具体类型允许的完整有效对象、具有该步实际授权与 Gate，并且中间状态能够保存和恢复时，才可把多个单对象 CAS 组织为合法序列；
2. 每一步写后必须回读，并使用该次回读的新 `content_fingerprint` 形成下一步；不得复用序列起点指纹、把多个预计算目标连续写入或跳过中间语义复核；
3. 同一转换要求共同成立的字段必须放入一个完整目标快照，不能拆成多个暂时无效的对象。例如 21 已规定 WorkCase 的 phase 推进必须与当次适用的批准、版本、当前 review/处置、报告或终态字段共同满足相应转换条件；模板只回指该规则，不复制其状态机；
4. 合法序列只能确认每个已完成单对象步骤分别成立，不表示整段序列具有事务原子性。后续步骤被拒绝、失败、等待 Human 或尚未授权时，必须保留并交还最后一个已回读的合法状态；
5. 只要完整责任要求多个对象共同生效，就不得使用合法单对象序列代替 `multi_object_disposition` 的原子能力。

#### E. 执行多对象分支

1. 同时形成所有受影响对象的变更前基线、完整目标快照、关系变化、来源证据、授权与不变量；
2. 只有当前规则源已经定义多对象公开操作，且 Code 对全部目标、关系、CAS 基线、原子写入、失败回滚和回读具有范围匹配实现时才执行；
3. 任一对象、关系、指纹、来源、授权或能力缺失都不得先写其余对象；预先创建孤立新对象、多个单对象成功、补偿更新或后续补关系都不能拼接成多对象原子成功；
4. 当前多对象公开能力未成立、范围不匹配或结果不可观察时，必须零写入；交还完整拟变更范围、各基线指纹、共同不变量和能力缺口，保持全部对象原状，不把计划、部分准备或单对象结果当作整体结果。

### 5.4 输出、验证、回写与交还

交还至少区分：目标对象与影响闭包；四类闭集中的当次分类和所依据的类型来源；完整写集合；单对象 CAS、合法多步序列或多对象原子范围；授权、来源、证据、审核和 Human Gate；每个已执行步骤变更前后的稳定引用、指纹、状态/阶段与关系；实际写入、拒绝、无变化、回滚、残留和副作用；机械验证与 AI 语义审核覆盖；未执行、未验证和后续承接；Git 提交及其它排除行动未被自动执行。分类和序列信息默认只作为当次交还，不自动成为 Helper 请求字段或事实对象字段。

长期回写只进入具体类型来源允许的事实对象和关系位置。模板不保存运行阶段、事务 receipt 或执行日志；多对象能力缺失时的拟变更默认只作当次交还，除非其它稳定来源另行准入。

### 5.5 组合、变更与退出

替代或承接可能在一个原子行动中包含“创建新对象 + 更新旧对象 + 建立关系”，整体由本模板多对象分支承担，并复用 31 的对象化/类型判断成果，但不得调用 31 的单对象创建后再宣称整体完成。Human 另行授权 commit 时，变更回读完成后可串联 30；事实对象变化不自动产生提交授权。

模板稳定结构、原子边界或失败分流改变时按 06 重审。若未来多对象能力拆成独立、稳定且具有不同失败闭环的行动，需重新比较是否拆模板；不能仅因新增 API 就拆分。

## 7. Human Gate

本文不新增统一 Human Gate。必须执行 20–24 和 Human 当前指令保留的计划批准、关闭确认、方向、证据争议、替代、退出、删除、风险接受或其它决定。已有决定只覆盖其明确对象和范围；不能用一次“更新”授权推定关闭、替代、创建新对象或 Git 提交授权。

## 8. Stop Conditions

出现以下任一情况时，暂停受影响的对象、原子范围、状态变更或相应声明：

1. 项目/worktree、稳定引用、当前对象、指纹或影响闭包无法确定；
2. 使用缓存、卡片或旧摘要替代当前完整对象和关系回读；
3. 无法区分事实更正、普通更新、单对象生命周期变化和多对象承接；
4. 模板正在自行定义或改写类型状态、阶段、转换、字段失效、关系或证据条件；
5. 当次授权、来源、证据、审核或 Human Gate 不覆盖实际变化；
6. 完整目标快照不成立、CAS 指纹过期或准备覆盖并发变化；
7. 需要多对象共同成立但公开契约、实现、原子性、回滚或回读能力缺失；
8. 准备用多个单对象写入拼接替代、路由、关闭或承接成功；
9. 多步序列中的某一步尚未回读或仍使用旧指纹，耦合字段被拆成无效中间快照，或者准备把逐步成功冒充事务原子性；
10. 多对象能力未成立时准备预写新对象、先改一个目标、依赖补偿或随后补关系，而不是保持零写入；
11. 写入失败、拒绝、部分成立、回滚或结果不可观察，却准备声明完成；
12. 写后未回读对象和必要关系闭包，或承接仍有缺口；
13. 准备把事实对象变化扩张为事实真实、审核通过、工作完成、Git 已提交、push 或发布；
14. 声明无效、来源冲突或模板不适用，却准备以模板阻止普通求解。
15. v1 WorkCase 未先完成获授权的语义迁移就普通推进，或迁移未走 generic `update-fact-object` 完整 after、未移除全部 v1-only 内容、改变锁定不可变项、改写/重排保留 review 的 Reviewer 自有字段、从空数组新增 review、未获覆盖托管内容的 Human 授权就校准 Controller 处置，或准备以机械通过代替语义授权。
16. closed v1 没有明确统一结构消费需要却被迁移，或迁移重开对象、改变关闭分类/版本/批准时间，或伪造 Human 决定。

暂停期间允许的行动与恢复按 00 §11 执行。
