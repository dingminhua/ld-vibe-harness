## 1. 推导方法

目标 Specs 不从当前编号和文件名推导，而按以下顺序形成：

1. 从 00 的存在理由、五点设计理念和 V1-V8 推导 LDVH 必须解决的问题；
2. 把现有 19 篇 Specs 与 19 个附件拆成原子规则资产；
3. 按共同变化、共同消费、共同验证和相同权威方向组合职责；
4. 只有具备独立适用条件、独立变化原因或独立消费入口的职责，才形成独立规范；
5. 用逐篇和逐附件迁移映射检查现有内容是否全部获得归属；
6. 职责和依赖稳定后，最后决定编号与文件路径。

## 2. 从 00 推导的必要规则能力

LDVH 要实现 00 的理念与价值，必须形成以下闭环。这里先定义能力，不预设文档边界。

| 价值问题 | 规则体系必须回答 | 主要输出 |
|---|---|---|
| V1 快速定位 | 当前任务相关的规则、事实、状态、对象和能力在哪里 | 来源索引、职责定位、读取入口 |
| V2 充分理解 | 这些来源之间是什么关系，当前上下文应读到什么粒度 | 关系投影、上下文组织、渐进读取 |
| V3 边界识别 | 当前工作对象是什么，哪些规则适用，产生什么义务，何时必须暂停 | 工作对象解析、规则适用结果、Gate/Stop |
| V4 稳定推进 | 当前场景有哪些可复用行动结构和确定性能力 | 行动模板、Helper 能力、Code 反馈 |
| V5 据实判断 | 判断与声明由哪些事实、验证结果和当次可观察依据支持 | 来源回指、验证要求、证明范围、残留风险 |
| V6 工作接续 | 哪些结果必须稳定回写，如何跨会话恢复 | 事实源、事实模型、Git 溯源、接续入口 |
| V7 清晰沟通 | Human 需要决定什么，作用范围和后续方向是什么 | Human Gate 交还、Helper/Web 呈现 |
| V8 持续积累 | 经验、反复问题、规则缺口和能力缺口进入哪里 | 事实对象、规则修订、能力缺口分流 |

上述闭环还必须共同守住四项边界：

1. 具体规则命中时产生效力，未命中时不限制 AI 普通求解路径；
2. Human Gate 和 Stop Conditions 只作用于来源规则命中的范围；
3. 未实现、未接入或未验证的能力不得声明为已保障、integrated 或完成；
4. 规则源、事实源、过程输出、证据和派生视图各自承担不同职责。

### 4.1 构成要素与治理规范是两个维度

五类构成要素回答“LDVH 由什么构成”；目标规范清单回答“这些构成要素及其共同边界由哪些规则治理”。两者不是同一种分类。

每篇正式 Spec 和授权附件都具有规范体系内的规则载体身份；同时，它可以治理某个构成要素、某项跨要素共同边界，或直接承载行动模板等功能资产。因此：

- “事实模型规范”是规则载体，其治理对象是事实模型；
- 正式行动模板既属于规则源，又是行动模板构成要素的功能资产；
- Code 和 Web 规范属于规范体系，受其治理的可执行资产分别属于 Code 和 Web 构成要素。

五类构成要素与目标规范的主要承接关系如下：

| 构成要素 | 该要素的功能资产 | 主要治理规范或规范族 |
|---|---|---|
| 规范体系 | 全部正式 Specs 和授权附件构成的规则源 | 规范体系基础规范、规则适用与效力规范 |
| 事实模型 | 对象类型、字段、状态、关系及其事实实例 | 事实模型基础规范及 Spark、WorkCase、ADR、Pitfall、Study 成员规范 |
| 行动模板 | 可被 AI 和 Helper 消费的正式行动结构 | 行动模板基础规范、具体行动模板及其引用的来源规则 |
| Code | parser、resolver、validator、Helper backend、runtime facade 等确定性实现 | Code 基础规范及相关跨要素规范 |
| Web | 来源呈现、Confirm UI 和受控交互实现 | Web 基础规范及相关信息来源、事实模型和验证规范 |

这一关系不表示规范体系在构成关系上是其他四类要素的上级，而是区分“规则由什么承载”、“要素由什么实现”与“规则治理什么”。

Helper 位于与五类构成要素不同的分类轴上：架构上，它是面向 AI 的跨要素统一服务入口，组织并消费适用的规范体系、事实模型、行动模板和 Code 能力；实现上，Helper CLI 的程序、命令、解析、校验和受控操作由 Code 实现。因此，Helper 既不是第六类构成要素，也不能被缩减为 Code 的一个普通能力。关系可简写为：`规范体系、事实模型、行动模板、Code → Helper → AI`、`Code → 实现 Helper CLI`、`Web → Human`。

### 4.2 为什么新增“规则适用与效力规范”

当前 01 试图用“保障需求”表达规则如何进入技术链路，但同时混入能力、环境和 Action Guide，导致它成为总容器。新规范只回答：

1. 哪些规则需要稳定 ID；
2. 规则针对什么对象、动作和上下文；
3. 命中后是必须、不得、暂停、验证、回写还是交还；
4. 谁在什么时机消费；
5. 需要哪些能力，缺失时如何处理；
6. 如何证明规则被满足；
7. 本篇新增哪些 Gate/Stop，哪些继承 00。

它不决定具体规则内容，也不禁止未命中规则的普通 AI 行动。

### 4.3 为什么建立“信息源”上位角色

信息源与 Git 溯源规范不是把规则源和事实源合并成同一种权威，而是统一定义来源角色和共同溯源要求：

- 规则源回答“应该怎样”；
- 事实源回答“当前是什么、发生过什么”；
- 过程输出回答“本次执行观察到什么”；
- 证据回答“哪些记录支持某个判断”；
- 派生视图回答“如何方便消费已有来源”。

各角色仍由不同规范治理，不能互相替代。

## 5. 事实对象规范形态

Spark、WorkCase、ADR、Pitfall、Study 暂保持五篇独立成员规范，不是因为当前已有五个文件，而是因为：

1. 五类对象具有独立准入条件和生命周期；
2. AI 通常只需要读取当前对象类型，分篇能降低上下文负担；
3. 单个类型的字段和状态可以独立变化；
4. Code、Web 和 Helper 可以按对象类型定向消费。

共同内容全部上收事实模型基础规范：事实源位置、实例不得反向定义模型、Git 溯源、状态和证据共同要求、通用 Gate/Stop。成员规范只保留：

- 类型定位与相邻类型分流；
- 类型特有准入条件；
- 类型特有字段与状态；
- 类型特有验证、Human Gate 和 Stop 增量。

目标成员规范：

1. Spark（火花）规范；
2. WorkCase（工作项）规范；
3. ADR（决策）规范；
4. Pitfall（踩坑经验）规范；
5. Study（研究报告）规范。

## 6. 目标行动模板

现有三篇行动模板不足以承接已经存在的规则资产。目标暂定六篇：

| 目标模板 | 来源与必要性 |
|---|---|
| LDVH 启用与项目登记行动模板 | 从当前 10/30 拆出工作区确认、管辖项目登记、事实源入口初始化；它不依赖环境 Hook 一定可安装 |
| 环境接入与验收行动模板 | 从当前 01/10/30 拆出插件/Hook 安装、升级、回滚、断点后 lifecycle 验收和 integrated 判读 |
| 事实对象创建与回写行动模板 | 承接正式 Spark/WorkCase/ADR/Pitfall/Study 的类型判断、受控创建、字段验证、回读和 Git 溯源，防止模型规则散落到 CLI |
| Git 提交行动模板 | 承接本地提交范围、commit message、验证和交还，保留当前 31 |
| Git 远端变更行动模板 | 承接当前散落在 01/03/09/10 的 push、force/delete/mirror/tag/protected-like ref 目标、Human Gate 和验证规则 |
| 环境插件编写与更新行动模板 | 承接目标环境能力分析、薄入口实现、本地验证和安装验收交还，重构当前 33 |

行动模板只组织来源规则和当前上下文，不复制字段闭集、target resolver、integrated 判定或验证声明契约。

## 7. 不单独形成规范的概念

| 概念 | 归属 |
|---|---|
| 保障与衔接 | 拆入规则适用与效力、Helper、环境、验证、AI 和 Code，不再保留总容器 |
| Action Guide | 成为 Helper 响应中的任务导航和关系投影，不形成独立概念规范 |
| 能力匹配模型 | 规则适用与效力规范定义所需能力，Helper 汇总可用能力和缺口，环境/Code/测试提供实际 provider |
| Diagnostic 分类 | 规则适用与效力规范定义通用缺口语义，AI 定义处理责任，Code 定义结构化输出 |
| Repair lane | 规则适用与效力规范限定适用条件，AI 定义行为，Code 实现，验证规范定义恢复证明 |
| Human Gate | 00 定义上位语义，各来源规范只定义本篇增量 |
| Stop Conditions | 00 定义上位语义，AI 定义通用执行行为，各来源规范定义本篇增量 |
| 安装与配置总规范 | 项目配置归工作对象规范，环境能力归环境规范，交互步骤归两个行动模板 |
| 测试基础规范 | 归“验证与声明”；tests 是实现域，不成为构成要素 |
| Runtime Protocol 独立文件 | 语义归环境接入、Helper 和 Code，不恢复独立顶层协议 |

## 10. 迁移前必须重新裁决的现有规则

“现有内容不得遗漏”表示必须获得处理结论，不表示全部原样保留。以下规则需要在目标职责中重新判断：

| 现有规则 | 风险 | 重新判断方向 |
|---|---|---|
| 所有 LDVH 行动前都必须调用价值门并输出 3-5 行轻量判断 | 容易把价值标准变成 AI 全局过程管制 | 只在修改 LDVH 实践、形成重要声明或来源规则明确要求时消费对应判断 |
| 写入或提交前固定要求读取并确认 00/01/02 | 固定路径替代任务相关规则定位，也会在 01/02 重组后失效 | 由 Helper 根据工作对象和适用规则生成目标相关读取要求，不维护固定三文件白名单 |
| 创建、修改或分流任何事实对象都默认进入 Human Gate | 可能让受控创建入口失去自动服务价值，并把普通事实维护全部升级为人工门禁 | 按对象类型、字段影响、状态变化和来源规则定义 Gate；受控、可验证、低风险写入不自动要求 Human 决定 |
| WorkCase 将 subagent review、Human plan confirm 等过程阶段全部写成稳定业务状态 | 把协作实现方式固化为事实模型，限制不同 AI 和环境组合 | 区分稳定工作状态与当次编排/receipt；只保留跨会话真正需要恢复的业务状态 |
| 只有具备可阻断 lifecycle Hook 的环境才属于 LDVH 支持范围 | 可能把“完整自动保障”和“可使用 Helper 的环境”混成一个支持结论 | 区分 Helper 可用、环境可接入、自动提示、软阻断、硬阻断和 integrated，不用单一布尔支持口径覆盖全部能力 |
| Action Guide 维护大量固定输出字段和验收清单 | 容易把当前 builder schema 固化成产品概念，增加上下文负担 | 提炼 Helper Response 的最小语义契约；展示字段和具体 schema 由 Code/接口版本承接 |
| 行动模板不是规则源 | 与 00“正式 specs 及授权附件构成规则源”冲突 | 正式行动模板是行动结构的规则来源，但不得重定义领域规则、字段闭集或授权 |
| Web 不得依赖任何 Code 输出或共享实现 | “过程输出不是主数据”被扩大为实现必须完全分离 | Web 必须从正式来源独立判断事实，但可以复用不改变语义的共享解析库；不得把临时 diagnostic/receipt 当主数据 |
| Linux 路径建议统一转小写 | 会破坏大小写敏感文件系统的真实路径语义 | 路径规范必须服从目标文件系统，跨平台比较不能通过无条件 lower-case 实现 |
| 每篇固定保留保障措施、验证方法和待补齐事项 | 产生大量重复、形式化章节，并把实现缺口混入规则正文 | 由规则适用与效力、验证要求和继承机制决定本篇需要的增量；待办进入工作对象或迁移计划，不作为所有规范固定正文 |

上述规则只有完成“保留、改写、拆分或删除”的明确判断后，才算被完整迁移。

## 12. 架构呈现顺序与语义依赖

### 12.1 核心规范的架构呈现顺序

1. 理念与构成；
2. 规范体系基础规范；
3. 规则适用与效力规范；
4. 信息源与 Git 溯源规范；
5. 验证与声明规范；
6. 工作对象与管辖规范；
7. LDVH Helper CLI 服务规范；
8. AI 规则履行规范；
9. 环境接入规范；
10. 事实模型基础规范；
11. 行动模板基础规范；
12. Code 基础规范；
13. Web 基础规范。

事实模型放在行动模板之前，使“稳定对象如何表达”先于“重复行动如何组织”。该清单暂只确定架构呈现顺序，不预先锁定最终文件编号。

### 12.2 呈现顺序不等于依赖顺序

一张平铺清单无法同时表达根语义、构成要素、治理对象和规则依赖。例如，Helper 在架构上是 LDVH 的基础服务形式，因此在事实模型之前呈现；但 Helper 的具体投影和受控操作仍可以依赖事实模型规则。

正式规范之间的语义依赖将由 `basis` 单独表达，并遵守以下原则：

1. `basis` 只表示理解或判定本规范所必需的上位语义，不因编号相邻而建立；
2. 依赖图必须无环，不用反向引用表示“实现了我”或“由我消费”；
3. 下游消费者、实现位置和派生导航由职责索引或 Code 生成，不写入上游规范的语义依赖。

因此，后续编写不按 1–13 机械串行。每篇规范定稿时，再根据它实际需要的上位语义确定 `basis`，并由 validator 检查无环和可解析性。

## 13. 迁移方式

不整体移动或复制当前 `specs/`。Git history 已提供历史追溯，完整临时副本会形成第二候选规则源。

每次迁移一个完整职责切片：

1. 明确来源章节、目标职责和退出条件；
2. 新建或修改目标规范；
3. 同步迁移附件、`basis`、`parent_spec` 和引用；
4. 验证目标规范已经完整承接；
5. 在同一迁移切片中删除旧位置重复规则；
6. 单独提交，保证可以按 Git commit 回查。

01、10 和 30 只有在迁移映射中的全部内容完成承接后才删除。迁移期间同一规则不得长期在两个 active 位置维护。
