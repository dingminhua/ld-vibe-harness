> 创建日期：2026-06-09

> 定位：内部评估与行动参考，不直接成为 LDVH 强制规则；后续如需生效，应吸收到 docs/specs 正文区、ADR、Task、Memo、Code、Web 或其他权威事实源
> 执行效力：无；本文结论需进入 docs/specs 正文区、工作对象、Code、Web、测试、运行投影或最佳实践后才具备对应效力

## 1. 核心判断

LDVH 当前整体推进方向符合 AI 执行者的真实需求。

LDVH 的价值不在于让 AI 记住更多规则，而在于用稳定事实源、明确入口、工作模型、工作流程、Code、Web 和 Human Gate 托住 AI 的概率性、上下文依赖和无状态问题，使 AI 能更稳定地读取、判断、执行、验证、回写和学习。

当前方向可以概括为：

```text
从“AI 能读懂规范”
推进到“AI 能基于最小上下文快速判断”
再推进到“AI 能通过 Code 和流程稳定执行、验证、停顿和回写”
```

因此，LDVH 当前方向是正确的；但当前还不能说已经完全满足 AI 需求。更准确的判断是：理念层和规范层较好符合 AI 需求，工具层和执行层仍需继续补齐。

围绕“规范落地要求”的进一步判断是：这套机制本身符合 AI 需求，因为它把正式规范从“可读文本”推进到“可执行、可验证、可回写、可审计”的机制链路。它要求稳定规范说明自己如何被看见、复用、确定性执行、Human 交互、生命周期触发或被后续规范承接，能够显著降低 AI 在执行时的猜测成本。

但规范落地要求不能演化为形式化填表或抽象堆叠。它必须持续服务以下目标：让 AI 少读、少猜、停得准、做完后能证明。凡是不能帮助 AI 更快定位事实源、判断边界、获得验证反馈或完成事实源回写的落地要求，都不应进入核心机制。

规范落地要求的价值边界可以概括为：

```text
规范服务 AI
机制托住 AI
Code 减轻 AI
Web 协调 Human
事实源沉淀闭环
```

## 2. AI 执行者的关键需求

### 2.1 明确边界

AI 需要知道：

1. 当前任务属于什么场景；
2. 应读取哪些事实源；
3. 哪些文件、对象、状态或规则可以修改；
4. 哪些内容只能参考，不能直接生效；
5. 什么时候必须暂停并请求 Human 确认。

边界模糊时，AI 容易扩大任务范围、遗漏关键约束、误改事实源或绕过 Human Gate。

### 2.2 稳定事实

AI 不天然保留跨会话状态。对 AI 来说，稳定事实必须能回到 Git 可追踪文件，而不是停留在聊天记录、模型记忆、工具缓存、Web 状态或临时输出中。

AI 最需要回答的问题是：

```text
我现在能读取哪个文件，并据此行动？
```

### 2.3 关联信息

AI 需要知道当前任务关联哪些规范、Task、ADR、Memo、Pitfall、Change、Intent、Code、Web 或运行投影。缺少关联信息时，AI 容易孤立理解任务，误判影响范围。

### 2.4 可见状态

AI 需要看到任务、决策、缺口、初始化、审计和验证的当前状态。状态不可见时，AI 无法判断下一步是执行、验证、回写、暂停、分流还是关闭。

### 2.5 可用工具

AI 可以阅读文档，但不能长期依赖手工跨文档聚合。可机械化的检查、索引、聚合、验证和受控写入，应尽量交给 Code 承接。

对 AI 友好的工具输出应能回答：

1. 当前有哪些事实源；
2. 哪些引用失效；
3. 哪些状态非法；
4. 哪些规范落地要求未承接；
5. 哪些 Human Gate 缺少证据；
6. 哪些验证未通过；
7. 哪些缺口需要分流。

### 2.6 停顿机制

AI 需要明确知道何时不能自行继续。Human Gate 对 AI 的意义不是增加审批负担，而是防止 AI 在高影响变更、事实源边界不清、授权不明、长期降级或关闭判断时越权推进。

### 2.7 验证反馈

AI 需要可复现反馈，而不是依赖“看起来可以”“逻辑上应该没问题”等自述。关键行动、状态变更、事实回写和交付结论，应通过 Code、测试、审查证据、Web 呈现或 Human 确认验证。

### 2.8 经验回流

AI 需要把重复错误、规范缺口、事实源漂移、工具不足和踩坑经验回流到 Pitfall、Memo、ADR、Task、规范、Code、Web 或运行投影中，避免同类问题反复出现。

## 3. 当前 LDVH 已符合 AI 需求的部分

### 3.1 AI 入口方向正确

LDVH-AI-ENTRY.md 为 AI 提供了最小读取顺序和场景路由，降低了 AI 不知道从哪里开始的风险。

这符合 AI 的快速定位需求。

### 3.2 五类构成要素分工清晰

00 总纲把 LDVH 拆成开发环境、工作模型、工作流程、Code 和 Web，并明确事实源原则贯穿其中。这有助于 AI 判断：

1. 什么是环境机制；
2. 什么是工作事实；
3. 什么是行动流程；
4. 什么应由 Code 确定性执行；
5. 什么应由 Web 面向 Human 呈现。

这符合 AI 的边界判断需求。

### 3.3 工作流程正在回答 AI 的行动问题

41 规范落地统筹、42 安装与接入初始化、43 产品审计、44 多角色思考等流程，开始系统回答 AI 执行时最需要的问题：

```text
当前场景是什么？
需要哪些 Context？
如何分流？
什么时候 Gate？
怎么验证？
结果写回哪里？
```

这符合 AI 的稳定执行需求。

### 3.4 工作模型正在承载可追踪事实

ADR、Task、Intent、Memo、Pitfall 等工作模型，使 AI 可以围绕同一组事实追踪任务、决策、意图、经验和缺口，而不是依赖聊天记忆。

这符合 AI 的无状态补偿需求。

### 3.5 Code 方向正确

现有 Code 能力已经开始承接结构校验、事实对象校验、commit 校验等确定性反馈。Code 规范也明确 Code 不得替代规范判断、Human Gate 或最终事实源。

这符合 AI 对确定性反馈和上下文压缩的需求。

### 3.6 Human Gate 规则逐步成型

多个规范已经明确高影响写入、入口变更、状态关闭、长期降级、ADR 状态流转、Code 受控写入等场景需要 Human Gate。

这符合 AI 对停顿机制和授权边界的需求。

### 3.7 规范落地要求机制方向正确

04 系列已经把正式规范进入运行环境的链路拆为“正式规范 → 规范落地要求 → 保障机制 → 环境适配映射 → 运行投影 → 漂移检查与事实源回写”。这对 AI 是友好的，因为 AI 可以据此判断一条规范究竟只是上位原则，还是需要进入入口摘要、工作流程、Skill、Agent、Code、Web、Human Gate 或生命周期触发。

规范落地要求能够回答 AI 执行时最容易缺失的几个问题：

1. 这条规范是否需要被 AI 入口看见；
2. 是否需要被流程复用；
3. 是否需要确定性检查、聚合、校验或受控写入；
4. 是否需要 Human 看见、确认、授权或验收；
5. 是否需要在提交、写入、审计、初始化、停止等生命周期事件中触发；
6. 是否需要被后续规范、Code、Web、工作对象或运行投影承接。

这符合 AI 对边界、稳定事实、关联信息、可见状态、工具反馈和停顿机制的综合需求。

## 4. 当前仍不够符合 AI 需求的部分

### 4.1 AI 仍需要读太多

虽然入口已经存在，但复杂任务仍可能要求 AI 同时读取 00、01、02、03、04、05、06、07、09、20、40、具体工作模型、具体工作流程、相关 Task、ADR、Memo 和 evals。

这会带来上下文过载风险。

下一步应加强最小可行动上下文生成，而不是继续要求 AI 每次手动全量阅读。

### 4.2 规范落地要求缺少全局聚合视图

各规范已经声明规范落地要求，但 AI 判断“哪些要求已经承接、哪些仍 open、哪些 degraded”时，仍需手工跨文件聚合。

这会削弱快速定位、正确判断和强制验证。

应优先形成 landing report 或等价 Code 输出。

landing report 不应只是把表格内容重新罗列一遍，而应回答每项落地要求是否已经实例化：由什么机制执行、何时执行、输入输出是什么、失败如何降级、验证方式是什么、稳定事实写回哪里、是否触发 Human Gate。

建议至少支持以下状态：

```text
closed
open
degraded
needs_human_gate
not_required
```

### 4.3 工作对象事实源存在历史漂移风险

如果 Task、ADR、Memo 等对象引用旧路径、不存在的 deliverables 或已迁移的 docs，AI 会被错误事实干扰。

对 AI 来说，事实源不健康比没有事实源更危险，因为它会制造看似稳定但实际失效的依据。

### 4.4 Human Gate 证据机制不足

当前 Gate 触发条件较多，但 Gate 证据的统一结构仍不足。AI 需要知道：

1. 应问什么；
2. 影响范围是什么；
3. 用户确认了什么；
4. 确认后写回哪里；
5. 后续如何证明该确认发生过；
6. 该确认是否足以关闭任务、接受降级或推进高影响变更。

Human Gate 应从“触发规则”继续推进到“证据结构”。

### 4.5 Web 尚未充分承担 AI-Human 桥接

Web 的价值不是简单展示页面，而是帮助 Human 看见 AI 的方向、风险、状态、证据和待确认事项，并给出高质量反馈。

后续 Web 应更多呈现：

1. open / degraded 缺口；
2. Human Gate 待确认项；
3. 校验失败摘要；
4. Task 关闭证据；
5. ADR 决策影响范围；
6. 事实源漂移；
7. 初始化和审计状态。

### 4.6 继续抽象存在负担风险

继续新增大量工作流程、对象或规则，未必更符合 AI 需求。过多抽象会增加 AI 的流程选择负担和上下文负担。

当前更应优先让已有 41、42、43、26、07 跑通闭环，而不是继续大规模扩写新流程。

### 4.7 规范落地要求存在形式化风险

规范落地要求本身是必要机制，但存在被误用为形式化填表的风险。需要避免以下倾向：

1. 不应要求目录说明、索引、evals、refs、README 和说明性文档默认声明规范落地要求；
2. 不应把具体环境实体、工具文件、平台配置、Web 页面或 Skill 实体直接写入普通规范落地要求表；
3. 不应把“有保障机制描述”视为已经落地，仍需判断是否存在可定位实体、触发方式、验证方式和回写出口；
4. 不应通过复制规范正文、增加入口摘要或堆叠流程来替代 Code 聚合、校验和 Web 呈现；
5. 不应把 00 总纲改写为执行手册，具体字段、状态、环境适配和工具细节应留在专项规范中。

如果规范落地要求不能帮助 AI 更少读取、更少猜测、更准确停顿或更可靠证明完成，它就不应进入核心机制。

## 5. specs 文档体系重构的补充判断

### 5.1 不建议为了编号完美而大规模重排 specs

基于 00 总纲和多角度分析，当前 `docs/specs/` 主干不宜为了编号看起来更完美而整体推翻重排。

当前主干已经形成相对稳定的 AI 入口和规范定位：

```text
00    总纲
01    目录说明
02    术语规范
03    文档基础规范
04    规范落地与环境适配
05    工作模型基础规范
06    工作流程基础规范
07    Code 实现规范
08    Web 信息同步规范
09    事实源边界与承载规范
10    运行闭环测试规范
11    非 LDVH 来源内容治理规范
12    最佳实践
20    工作模型集合索引
21-39 具体工作模型
40    工作流程集合索引
41-59 具体工作流程
```

这个结构虽然不是完全按抽象层级排序，但已经服务了 AI 的快速定位、集合索引、工作模型/工作流程分区和 Code/Web/事实源边界判断。若仅为追求编号顺序上的理论完整而重编号，会带来路径引用漂移、AI 入口漂移、Web 预览失效、Code 校验断裂和历史工作对象引用失效等风险。

更符合 AI 需求的方向是：保持当前主干稳定，强化边界说明、入口路由、Code 聚合、Human Gate 证据和局部重组，而不是一次性全局迁移。

### 5.2 文档治理与事实源的关系

文档治理和事实源不是简单并列关系，也不是谁替代谁的关系。

更准确的关系是：

```text
01 负责目录与编号映射
03 负责 Markdown 文档工作区治理
09 负责跨 Markdown、YAML、Code、Web、运行投影和工具输出的最终事实源权威原则
```

事实源不是文档治理的前置章节，也不是 LDVH 的第六类构成要素。00 总纲已经明确：事实源不是并列构成要素，而是贯穿开发环境、工作模型、工作流程、Code 和 Web 的底层权威原则。

因此：

1. `03-文档基础规范.md` 应聚焦 Markdown 文档工作区，回答 docs/specs、docs/evals、docs/refs 如何分区、命名、引用、吸收和表达；
2. `09-事实源边界与承载规范.md` 应聚焦最终事实源、单一事实源、承载介质、工具输出回写和事实归属；
3. `01-目录说明.md` 应负责目录、编号和内容归属导航，不应重新定义事实源原则或文档写作细则；
4. 其他规范可以声明自身事实源边界，但不应重复维护 09 的通用事实源原则。

这意味着不应简单把 `09` 前移成 `03`，也不应把 `03` 扩张为所有事实源治理。更稳妥的方式是保留编号稳定，同时在 01、03、09 中把上述层级关系讲清楚。

### 5.3 当前主干应保持稳定，重点做结构澄清和局部重组

当前 specs 的主要问题不是主干错误，而是部分边界和子体系需要澄清：

1. 04 系列需要整理为更清晰的“规范落地与环境适配链路”；
2. 03 与 09 的职责需要避免混淆；
3. 01 需要更明确展示五类构成要素与当前编号区段的映射；
4. 20 和 40 应继续作为集合索引，不应被改成基础规范编号；
5. candidate、planned、reserved 项不应被 AI 当成已创建正式 Markdown 路径；
6. evals/refs 的结论不应被直接当作 specs 正文事实消费；
7. Code/Web/运行投影不应被误升格为最终事实源。

其中 04 的合理定位不是“开发环境本身”，而是正式规范进入开发环境和运行投影的桥梁：

```text
正式规范
→ 规范落地要求
→ 保障机制
→ 环境能力
→ 运行投影
→ 适配映射记录
→ 漂移检查
→ 事实源回写
```

因此，04 可局部重组和澄清，但不宜简单改名为开发环境基础规范，也不宜把平台实例清单、个人环境要求、入口投影和规范落地要求继续混成同一层次。

### 5.4 后续扩展区规划

为更好承接 00 总纲的五类构成要素，可以在不破坏当前主干的前提下规划未来扩展区：

| 构成要素 | 当前基础规范 | 当前集合索引 | 未来扩展区 |
|---|---|---|---|
| 开发环境 | 04 | 暂无 | 60-69 |
| 工作模型 | 05 | 20 | 21-39 |
| 工作流程 | 06 | 40 | 41-59 |
| Code | 07 | 暂无 | 70-79 |
| Web | 08 | 暂无 | 80-89 |

这种方式比全局重编号更稳：既保留现有 AI 入口和路径稳定性，又让开发环境、Code、Web 在未来具备与工作模型、工作流程相似的集合扩展空间。

未来如需真正启用 60-89，应先经过 Human Gate，明确编号区段定位、集合索引职责、是否创建正式 Markdown 文件、是否影响 Code/Web/入口/运行投影，并通过校验确认不会造成事实源漂移。

### 5.5 specs 重构的优先级

当前 specs 体系重构的优先级应是：

```text
先澄清边界
再整理 04
再强化 01/03/09 的关系
再补 Code 聚合和入口漂移检查
再规划 60-89 扩展区
最后才考虑正式迁移或重编号
```

不建议优先执行全局重编号。更重要的是让 AI 在现有结构下更少读取、更少猜测、更准确停顿、更稳定验证、更可靠回写。

## 6. 面向 AI 需求的推进原则

### 6.1 让 AI 少读

优先建设聚合、索引、摘要和最小上下文能力。目标不是减少事实源，而是让 AI 在具体任务中只读取必要事实源。

建议优先产出：

1. 当前任务最小读取集；
2. active 工作模型和工作流程摘要；
3. open / degraded 缺口摘要；
4. Human Gate 待确认项摘要；
5. 校验失败摘要；
6. 相关 Task / ADR / Memo / Pitfall 关联摘要。

### 6.2 让 AI 少猜

能机械检查的内容应交给 Code：

1. 路径是否存在；
2. 引用是否有效；
3. 状态是否合法；
4. 关闭条件是否满足；
5. 规范落地要求是否具备承接机制；
6. 运行投影是否漂移；
7. Human Gate 是否有证据；
8. Web 与 Git 文件事实源是否一致。

### 6.3 让 AI 停得准

Human Gate 不应泛化成“遇事都问”。应按类型分层：

| Gate 类型 | 用途 |
|---|---|
| 澄清 Gate | 意图、目标、范围或验收标准不清 |
| 授权 Gate | 写入、删除、迁移、创建长期运行投影或修改配置 |
| 风险 Gate | 影响范围大、事实源边界不清或存在不可逆风险 |
| 验收 Gate | 关闭 Task、接受长期降级或确认交付结果 |
| 决策 Gate | ADR、规范方向或长期机制取舍 |

### 6.4 让 AI 做完后能证明

Task、ADR、审计结果和初始化结果应能回答：

1. 做了什么；
2. 为什么做；
3. 依据是什么；
4. 验证命令或验证方式是什么；
5. 验证结果是什么；
6. 结果写回哪里；
7. 谁确认了；
8. 还有什么残留风险。

### 6.5 少新增抽象，多跑闭环

当前阶段应避免为了未来假想能力继续堆叠流程、对象或机制。每新增一层抽象后，应优先安排一次实例化验证。

更符合 AI 需求的路线是：

```text
少新增抽象
多跑现有闭环
多补 Code 聚合
多清事实源漂移
多沉淀验证证据
```

### 6.6 让规范落地要求少形式、多实例

规范落地要求应优先服务可执行性，而不是服务文档形式完整。每项落地要求都应尽量能被进一步追问：

1. 这项要求是否真的降低 AI 读取、判断、验证或回写负担；
2. 是否有明确保障机制，而不只是愿望式表述；
3. 是否已经映射到可定位的流程、Code、Web、Human Gate、运行投影或后续 Task；
4. 是否有验证方式或可接受的降级说明；
5. 是否避免把环境实体混入正式规范，造成规范与平台绑定；
6. 是否避免把运行投影、工具输出、Web 状态或聊天结论当成最终事实源。

更合理的方向不是让 AI 阅读更多落地要求表，而是让 Code、Web 和工作流程把这些要求聚合成 AI 可行动的最小上下文。

## 7. 建议优先行动

### 7.1 修复或分流工作对象事实源漂移

优先处理 ldvh-base 中的历史路径、缺失引用、deliverables 不存在、closure_evidence 格式不足等问题。

目标不是让校验结果表面变绿，而是恢复工作对象事实源对 AI 的可信度。

### 7.2 扩展规范落地要求聚合报告

建议扩展 `tools/specs_validate.py` 或等价 Code 能力，生成 landing report：

```text
扫描 docs/specs
→ 聚合所有规范落地要求
→ 按类型分组
→ 标记已承接、open、degraded、needs_human_gate
→ 输出可读报告或 JSON
```

该能力将显著降低 AI 的跨文档聚合负担。

landing report 的输出重点应是行动判断，而不是文档复述。优先输出：

1. 每项规范落地要求的来源文件和类型；
2. 是否存在保障机制；
3. 是否已实例化到流程、Code、Web、Human Gate、运行投影或后续 Task；
4. 当前状态是 closed、open、degraded、needs_human_gate 还是 not_required；
5. 缺口归属和建议回写位置；
6. 可复现验证方式或降级说明。

### 7.3 Dogfood 42 和 43

使用 LDVH 审计 LDVH 自身，检查：

1. AI 入口是否有效；
2. 管辖项目配置是否有效；
3. 环境初始化记录是否有效；
4. docs/specs 是否通过校验；
5. ldvh-base 是否通过校验；
6. active 工作模型和工作流程是否可定位；
7. Code / Web 是否支撑当前闭环；
8. open / degraded 缺口是否已分流。

### 7.4 建立 Human Gate 最小证据结构

先不追求复杂 Web UI，优先让 Gate 证据进入 Git 文件事实源。

建议最小字段包括：

1. 确认事项；
2. 影响范围；
3. 确认人；
4. 确认时间；
5. 确认上下文；
6. 确认后的执行动作；
7. 验证结果；
8. 回写位置。

### 7.5 增强 Web 的 Human-facing 审计面

Web 后续应优先服务 Human 对 AI 的高质量确认，而不只是展示对象详情。

优先展示：

1. 当前风险；
2. 待确认事项；
3. 验证证据；
4. 缺口状态；
5. 事实源漂移；
6. Task 关闭条件；
7. ADR 决策影响。

## 9. 一句话参考

LDVH 的下一阶段，不应只是让 AI 读到更多规范，而应让 AI 更少依赖记忆、更少手工聚合、更少猜测、更准确停顿、更稳定验证、更可靠回写。

```text
规范服务 AI，机制托住 AI，Code 减轻 AI，Web 协调 Human，事实源沉淀闭环。
```
