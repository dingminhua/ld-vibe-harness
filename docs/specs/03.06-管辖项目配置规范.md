# 管辖项目配置规范

> 创建日期：2026-06-09
> 定位：定义 LDVH 根目录管辖项目配置文件的事实源边界、字段规则、填写方式和 Code 校验要求
> 适用范围：LDVH 自身项目根目录 `LDVH-GOVERNED-PROJECTS.yaml`，以及 AI、Human 和 Code 读取管辖项目清单的场景
> 上位依据：`docs/specs/03-文档基础规范.md`
> 相关规范：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/01-目录说明.md`、`docs/specs/02-术语规范.md`、`docs/specs/03.02-管辖项目文档规范.md`、`docs/specs/04.02-环境适配与运行投影规范.md`、`docs/specs/07-Code实现规范.md`、`docs/specs/09-事实源边界与承载规范.md`

---
## 1. 本文解决的问题

本文解决 LDVH 如何说明当前管理实例，并登记管辖项目清单的问题。

管辖项目配置是 LDVH 自身项目根目录下的 YAML 文件：

```text
LDVH-GOVERNED-PROJECTS.yaml
```

该文件登记两类最小信息：当前 LDVH 管理实例的产品名称与产品说明，以及被 LDVH 管辖项目的 `id` 和 `path`。项目 `name` 与 `description` 只是可读性补充，允许省略。该文件不是工作对象，不进入 `ldvh-base/`，不具备状态机、对象关系或关闭条件，也不替代 Intent、Task、ADR、Memo、Change、Pitfall 等工作对象。

---
## 2. 与 00 和 03 的关系

00 要求稳定事实回到 Git 可追踪文件。本文将“哪些项目被当前 LDVH 管辖”定义为 LDVH 自身项目根目录的 Git 文件事实。

03 定义文档工作区和根目录文件治理边界。本文作为 03 的专题子文档，只规定管辖项目配置文件，不定义管辖项目 `docs/` 文档写作规则；管辖项目文档规则仍由 `docs/specs/03.02-管辖项目文档规范.md` 承接。

---
## 3. 文件位置与事实源边界

管辖项目配置文件固定放在 LDVH 自身项目根目录：

```text
LDVH-GOVERNED-PROJECTS.yaml
```

边界如下：

| 内容 | 权威位置 | 说明 |
|---|---|---|
| 产品级说明 | `LDVH-GOVERNED-PROJECTS.yaml` | 登记当前 LDVH 管理实例的名称和说明 |
| 管辖项目清单 | `LDVH-GOVERNED-PROJECTS.yaml` | 只登记项目 id、路径，以及可选名称、说明 |
| 管辖项目文档 | `{path}/docs` | 由 `path` 固定推导 |
| 管辖项目工作对象 | `{path}/ldvh-base` | 由 `path` 固定推导 |
| LDVH 环境适配 | `LDVH-ENVIRONMENT-INITIALIZATION.md` | 只属于 LDVH 自身项目 |
| 工作对象事实 | `ldvh-base/` 下对应目录 | 不由本文定义字段或状态 |

管辖项目配置不得承载以下内容：

1. 项目类型字段；
2. 项目状态字段；
3. docs 路径字段；
4. ldvh-base 路径字段；
5. 环境适配、运行投影、平台规则或入口正文；
6. 工作对象状态、验收、关闭证据或对象关系。

---
## 4. 字段规则

根对象只允许三个字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `product_name` | string | 是 | 当前 LDVH 管理实例或产品名称 |
| `product_description` | string | 是 | 当前 LDVH 管理实例或产品说明 |
| `projects` | list[object] | 是 | 管辖项目列表；没有项目时使用空列表 |

每个项目只允许四个字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 项目稳定 ID；同一文件内不得重复 |
| `path` | string | 是 | 项目根目录路径 |
| `name` | string | 否 | 项目名称；省略时 AI 可使用 `id` 作为显示名 |
| `description` | string | 否 | 项目说明；省略时 AI 不得臆测项目性质 |

固定推导规则如下：

| 推导项 | 规则 |
|---|---|
| 项目类型 | 所有条目都是管辖项目 |
| 文档工作区 | `{path}/docs` |
| 工作对象事实源 | `{path}/ldvh-base` |

LDVH 自身源码仓库可以把 LDVH 自己登记为 dogfood 管辖项目。这是当前仓库开发 LDVH 时的自我治理事实，不是用户安装 LDVH 后必须继承的管辖项目默认值。用户安装后的管辖项目清单应由用户实际项目决定。

AI 不得因为需要更多信息就在本文件中新增字段。若确实出现新信息需求，应先判断是否进入管辖项目文档、工作对象、LDVH 自身环境初始化记录、正式规范或后续 Human Gate。

---
## 5. YAML 注释填写规则

`LDVH-GOVERNED-PROJECTS.yaml` 应在文件注释中直接说明填写方法和多项目示例，不再创建单独的说明文档。

注释至少应说明：

1. 这个文件用于说明当前 LDVH 管理实例，并登记 LDVH 管辖项目；
2. 根字段只允许 `product_name`、`product_description`、`projects`；
3. 每个项目只要求填写 `id` 和 `path`；
4. 每个项目可选填写 `name` 和 `description`；
5. `id` 不能重复；
6. `docs` 和 `ldvh-base` 路径由 `path` 固定推导；
7. LDVH 自身 dogfood 条目的边界；
8. 单项目和多项目填写示例。

注释是用户填写帮助，不是结构化事实；Code 校验以 YAML 有效内容为准。

---
## 6. AI 使用规则

AI 需要识别管辖项目时，应读取 `LDVH-GOVERNED-PROJECTS.yaml`。

读取后应按以下方式使用：

1. 用 `product_name` 和 `product_description` 理解当前 LDVH 管理实例的用途；
2. 通过项目 `id` 稳定引用项目；
3. 用项目 `name` 和 `description` 辅助理解项目性质；若缺失，不得臆测；
4. 用 `path` 定位项目根目录；
5. 需要管辖项目文档时，进入 `{path}/docs`；
6. 需要管辖项目工作对象时，进入 `{path}/ldvh-base`。

AI 不得把本文件解释为产品初始化完成、环境适配完成或运行投影已建立。项目是否已完成产品初始化，应由后续产品初始化或产品审计工作流程判断。

## 7. Code 校验规则

Code 应至少检查：

| 检查项 | 标准 |
|---|---|
| 文件存在 | LDVH 自身项目根目录存在 `LDVH-GOVERNED-PROJECTS.yaml` |
| 根结构 | 根对象是 mapping，且只包含 `product_name`、`product_description`、`projects` |
| 产品字段 | `product_name` 和 `product_description` 是非空字符串 |
| 列表结构 | `projects` 是 list |
| 字段边界 | 每个项目只包含 `id`、`path`、`name`、`description` 四个字段 |
| 必填字段 | 每个项目必须包含 `id` 和 `path` |
| 可选字段 | `name` 和 `description` 可省略；出现时必须是非空字符串 |
| ID 唯一性 | 同一文件内 `id` 不重复 |

Code 不应在本阶段检查路径是否真实存在。路径存在性可能受挂载、权限、工作区布局和用户当前环境影响，应由产品初始化或产品审计流程判断。

## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 管辖项目配置必须遵守本文定义的文件位置、产品字段、项目字段边界和固定推导规则 | 本文、01 目录说明、03 文档基础规范、Human Gate | 项目接入治理 | 新增、修改或审计管辖项目配置时 |
| 入口可见要求 | AI 需要识别管辖项目时，应能定位 `LDVH-GOVERNED-PROJECTS.yaml` | 01 目录说明、03 系列子文档入口、运行入口摘要 | AI 执行入口提示 | 根目录文件名、字段规则或入口引用变化时 |
| 确定性执行要求 | 管辖项目配置的结构、产品必填字段、项目必填字段、项目可选字段和 `id` 唯一性应由 Code 校验 | `tools/specs_validate.py governed-projects`、正反样例 | 校验实现 | 字段集合、根结构、唯一性规则或文件名变化时 |
| Human 交互要求 | 新增、删除或修改管辖项目条目时，应评估 Human Gate | Human Gate、影响范围说明、人工确认 | 项目接入治理 | 管辖项目清单变化时 |
| 生命周期触发要求 | 管辖项目配置变化后，应检查 01、02、03.02、产品初始化、产品审计、Code 和 Web 是否需要同步 | 文档检查、项目配置校验、人工降级检查 | 触发保障 | 文件位置、字段规则、推导规则或项目清单变化时 |

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除或修改管辖项目条目；
2. 改变 `LDVH-GOVERNED-PROJECTS.yaml` 文件名或位置；
3. 新增 `product_name`、`product_description`、`projects`、项目 `id`、`path`、`name`、`description` 之外的字段；
4. 允许 `id` 重复；
5. 将本文件改为工作对象、环境初始化记录或运行投影；
6. 让本文件替代产品初始化或产品审计结论。

管辖项目配置检查至少包括：

| 检查项 | 标准 |
|---|---|
| 文件边界 | 文件位于 LDVH 自身项目根目录 |
| 产品字段 | `product_name`、`product_description` 已填写 |
| 字段边界 | 项目只强制使用 `id` 和 `path`，只允许选填 `name` 和 `description` |
| ID 唯一 | `id` 不重复 |
| 固定推导 | docs 和 ldvh-base 路径未单独填写 |
| Dogfood 边界 | LDVH 自身条目只作为源码仓库自我治理事实，不被解释为用户安装默认管辖项目 |
| 非工作对象 | 文件未进入 `ldvh-base/`，未使用工作对象状态机 |
| 非环境适配 | 文件未承载运行投影或平台入口正文 |
