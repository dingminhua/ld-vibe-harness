> 创建日期：2026-06-09

## 1. 核心判断

LDVH 当前整体推进方向符合 AI 执行者的真实需求。

LDVH 的价值不在于让 AI 记住更多规则，而在于用稳定事实源、明确入口、工作模型、工作流程、Code、Web 和 Human Gate 托住 AI 的概率性、上下文依赖和无状态问题，使 AI 能更稳定地读取、判断、执行、验证、回写和学习。

当前方向可以概括为：

```text
从“AI 能读懂规范”
推进到“AI 能基于最小上下文快速判断”
再推进到“AI 能通过 Code 和流程稳定执行、验证、停顿和回写”
```

因此，LDVH 当前方向是正确的；但当前还不能说已经完全满足 AI 需求。更准确的判断是：理念层和规范层较好符合 AI 需求，工具层和执行层仍需继续补齐。

## 2. AI 执行者的关键需求

### 2.1 明确边界

AI 需要知道：

1. 当前任务属于什么场景；
2. 应读取哪些事实源；
3. 哪些文件、对象、状态或规则可以修改；
4. 哪些内容只能参考，不能直接生效；
5. 什么时候必须暂停并请求 Human 确认。

边界模糊时，AI 容易扩大任务范围、遗漏关键约束、误改事实源或绕过 Human Gate。

### 2.2 稳定事实

AI 不天然保留跨会话状态。对 AI 来说，稳定事实必须能回到 Git 可追踪文件，而不是停留在聊天记录、模型记忆、工具缓存、Web 状态或临时输出中。

AI 最需要回答的问题是：

```text
我现在能读取哪个文件，并据此行动？
```

### 2.3 关联信息

AI 需要知道当前任务关联哪些规范、Task、ADR、Memo、Pitfall、Change、Intent、Code、Web 或运行投影。缺少关联信息时，AI 容易孤立理解任务，误判影响范围。

### 2.4 可见状态

AI 需要看到任务、决策、缺口、初始化、审计和验证的当前状态。状态不可见时，AI 无法判断下一步是执行、验证、回写、暂停、分流还是关闭。

### 2.5 可用工具

AI 可以阅读文档，但不能长期依赖手工跨文档聚合。可机械化的检查、索引、聚合、验证和受控写入，应尽量交给 Code 承接。

对 AI 友好的工具输出应能回答：

1. 当前有哪些事实源；
2. 哪些引用失效；
3. 哪些状态非法；
4. 哪些规范落地要求未承接；
5. 哪些 Human Gate 缺少证据；
6. 哪些验证未通过；
7. 哪些缺口需要分流。

### 2.6 停顿机制

AI 需要明确知道何时不能自行继续。Human Gate 对 AI 的意义不是增加审批负担，而是防止 AI 在高影响变更、事实源边界不清、授权不明、长期降级或关闭判断时越权推进。

### 2.7 验证反馈

AI 需要可复现反馈，而不是依赖“看起来可以”“逻辑上应该没问题”等自述。关键行动、状态变更、事实回写和交付结论，应通过 Code、测试、审查证据、Web 呈现或 Human 确认验证。

### 2.8 经验回流

AI 需要把重复错误、规范缺口、事实源漂移、工具不足和踩坑经验回流到 Pitfall、Memo、ADR、Task、规范、Code、Web 或运行投影中，避免同类问题反复出现。

## 3. 当前 LDVH 已符合 AI 需求的部分

### 3.1 AI 入口方向正确

LDVH-AI-ENTRY.md 为 AI 提供了最小读取顺序和场景路由，降低了 AI 不知道从哪里开始的风险。

这符合 AI 的快速定位需求。

### 3.2 五类构成要素分工清晰

00 总纲把 LDVH 拆成开发环境、工作模型、工作流程、Code 和 Web，并明确事实源原则贯穿其中。这有助于 AI 判断：

1. 什么是环境机制；
2. 什么是工作事实；
3. 什么是行动流程；
4. 什么应由 Code 确定性执行；
5. 什么应由 Web 面向 Human 呈现。

这符合 AI 的边界判断需求。

### 3.3 工作流程正在回答 AI 的行动问题

41 规范落地统筹、42 安装与接入初始化、43 产品审计、44 多角色思考等流程，开始系统回答 AI 执行时最需要的问题：

```text
当前场景是什么？
需要哪些 Context？
如何分流？
什么时候 Gate？
怎么验证？
结果写回哪里？
```

这符合 AI 的稳定执行需求。

### 3.4 工作模型正在承载可追踪事实

ADR、Task、Intent、Memo、Pitfall 等工作模型，使 AI 可以围绕同一组事实追踪任务、决策、意图、经验和缺口，而不是依赖聊天记忆。

这符合 AI 的无状态补偿需求。

### 3.5 Code 方向正确

现有 Code 能力已经开始承接结构校验、事实对象校验、commit 校验等确定性反馈。Code 规范也明确 Code 不得替代规范判断、Human Gate 或最终事实源。

这符合 AI 对确定性反馈和上下文压缩的需求。

### 3.6 Human Gate 规则逐步成型

多个规范已经明确高影响写入、入口变更、状态关闭、长期降级、ADR 状态流转、Code 受控写入等场景需要 Human Gate。

这符合 AI 对停顿机制和授权边界的需求。

## 4. 当前仍不够符合 AI 需求的部分

### 4.1 AI 仍需要读太多

虽然入口已经存在，但复杂任务仍可能要求 AI 同时读取 00、01、02、03、04、05、06、07、09、20、40、具体工作模型、具体工作流程、相关 Task、ADR、Memo 和 evals。

这会带来上下文过载风险。

下一步应加强最小可行动上下文生成，而不是继续要求 AI 每次手动全量阅读。

### 4.2 规范落地要求缺少全局聚合视图

各规范已经声明规范落地要求，但 AI 判断“哪些要求已经承接、哪些仍 open、哪些 degraded”时，仍需手工跨文件聚合。

这会削弱快速定位、正确判断和强制验证。

应优先形成 landing report 或等价 Code 输出。

### 4.3 工作对象事实源存在历史漂移风险

如果 Task、ADR、Memo 等对象引用旧路径、不存在的 deliverables 或已迁移的 docs，AI 会被错误事实干扰。

对 AI 来说，事实源不健康比没有事实源更危险，因为它会制造看似稳定但实际失效的依据。

### 4.4 Human Gate 证据机制不足

当前 Gate 触发条件较多，但 Gate 证据的统一结构仍不足。AI 需要知道：

1. 应问什么；
2. 影响范围是什么；
3. 用户确认了什么；
4. 确认后写回哪里；
5. 后续如何证明该确认发生过；
6. 该确认是否足以关闭任务、接受降级或推进高影响变更。

Human Gate 应从“触发规则”继续推进到“证据结构”。

### 4.5 Web 尚未充分承担 AI-Human 桥接

Web 的价值不是简单展示页面，而是帮助 Human 看见 AI 的方向、风险、状态、证据和待确认事项，并给出高质量反馈。

后续 Web 应更多呈现：

1. open / degraded 缺口；
2. Human Gate 待确认项；
3. 校验失败摘要；
4. Task 关闭证据；
5. ADR 决策影响范围；
6. 事实源漂移；
7. 初始化和审计状态。

### 4.6 继续抽象存在负担风险

继续新增大量工作流程、对象或规则，未必更符合 AI 需求。过多抽象会增加 AI 的流程选择负担和上下文负担。

当前更应优先让已有 41、42、43、26、07 跑通闭环，而不是继续大规模扩写新流程。

## 5. 面向 AI 需求的推进原则

### 5.1 让 AI 少读

优先建设聚合、索引、摘要和最小上下文能力。目标不是减少事实源，而是让 AI 在具体任务中只读取必要事实源。

建议优先产出：

1. 当前任务最小读取集；
2. active 工作模型和工作流程摘要；
3. open / degraded 缺口摘要；
4. Human Gate 待确认项摘要；
5. 校验失败摘要；
6. 相关 Task / ADR / Memo / Pitfall 关联摘要。

### 5.2 让 AI 少猜

能机械检查的内容应交给 Code：

1. 路径是否存在；
2. 引用是否有效；
3. 状态是否合法；
4. 关闭条件是否满足；
5. 规范落地要求是否具备承接机制；
6. 运行投影是否漂移；
7. Human Gate 是否有证据；
8. Web 与 Git 文件事实源是否一致。

### 5.3 让 AI 停得准

Human Gate 不应泛化成“遇事都问”。应按类型分层：

| Gate 类型 | 用途 |
|---|---|
| 澄清 Gate | 意图、目标、范围或验收标准不清 |
| 授权 Gate | 写入、删除、迁移、创建长期运行投影或修改配置 |
| 风险 Gate | 影响范围大、事实源边界不清或存在不可逆风险 |
| 验收 Gate | 关闭 Task、接受长期降级或确认交付结果 |
| 决策 Gate | ADR、规范方向或长期机制取舍 |

### 5.4 让 AI 做完后能证明

Task、ADR、审计结果和初始化结果应能回答：

1. 做了什么；
2. 为什么做；
3. 依据是什么；
4. 验证命令或验证方式是什么；
5. 验证结果是什么；
6. 结果写回哪里；
7. 谁确认了；
8. 还有什么残留风险。

### 5.5 少新增抽象，多跑闭环

当前阶段应避免为了未来假想能力继续堆叠流程、对象或机制。每新增一层抽象后，应优先安排一次实例化验证。

更符合 AI 需求的路线是：

```text
少新增抽象
多跑现有闭环
多补 Code 聚合
多清事实源漂移
多沉淀验证证据
```

## 6. 建议优先行动

### 6.1 修复或分流工作对象事实源漂移

优先处理 ldvh-base 中的历史路径、缺失引用、deliverables 不存在、closure_evidence 格式不足等问题。

目标不是让校验结果表面变绿，而是恢复工作对象事实源对 AI 的可信度。

### 6.2 扩展规范落地要求聚合报告

建议扩展 `tools/specs_validate.py` 或等价 Code 能力，生成 landing report：

```text
扫描 docs/specs
→ 聚合所有规范落地要求
→ 按类型分组
→ 标记已承接、open、degraded、needs_human_gate
→ 输出可读报告或 JSON
```

该能力将显著降低 AI 的跨文档聚合负担。

### 6.3 Dogfood 42 和 43

使用 LDVH 审计 LDVH 自身，检查：

1. AI 入口是否有效；
2. 管辖项目配置是否有效；
3. 环境初始化记录是否有效；
4. docs/specs 是否通过校验；
5. ldvh-base 是否通过校验；
6. active 工作模型和工作流程是否可定位；
7. Code / Web 是否支撑当前闭环；
8. open / degraded 缺口是否已分流。

### 6.4 建立 Human Gate 最小证据结构

先不追求复杂 Web UI，优先让 Gate 证据进入 Git 文件事实源。

建议最小字段包括：

1. 确认事项；
2. 影响范围；
3. 确认人；
4. 确认时间；
5. 确认上下文；
6. 确认后的执行动作；
7. 验证结果；
8. 回写位置。

### 6.5 增强 Web 的 Human-facing 审计面

Web 后续应优先服务 Human 对 AI 的高质量确认，而不只是展示对象详情。

优先展示：

1. 当前风险；
2. 待确认事项；
3. 验证证据；
4. 缺口状态；
5. 事实源漂移；
6. Task 关闭条件；
7. ADR 决策影响。

## 8. 一句话参考

LDVH 的下一阶段，不应只是让 AI 读到更多规范，而应让 AI 更少依赖记忆、更少手工聚合、更少猜测、更准确停顿、更稳定验证、更可靠回写。

```text
规范服务 AI，机制托住 AI，Code 减轻 AI，Web 协调 Human，事实源沉淀闭环。
```
