1. ECC 式完整安装器；

## 7. 新增讨论：以部署入口作为 04 落地起点

用户补充了当前重要判断：LDVH 目前还不存在“让用户配置功能”的正式说法。当前 LDVH 的能力不是可选安装项，而是应安装、应准备、应可检查的必备内容。未来可以提供配置能力，例如在 Web 中列出大量 Skill 并让用户勾选，再由 AI 按配置措施安装和验证；但当前阶段即使做 Web 页面，也只能作为清单展示，不能表达为用户可选择启用或禁用。

当前更适合作为起点的问题是“部署入口”。用户认为当前最缺的是入口：既没有明确要求，也没有明确安装适配内容。

用户提出当前需要部署的入口能力可先收敛为四类：

1. Rules；
2. Skill；
3. Agent；
4. Hook。

用户倾向认为其它内容不属于部署入口。例如 CLI、Code、Web 等更像 LDVH 自身需要准备的能力资产或执行能力，不应与环境入口部署混在一起。

当前疑点：

1. Trae 似乎可以通过 Skill 兼容出类似 Hook 的效果；
2. Codex App 若要 Hook，可能需要使用其自身 Hook 能力；
3. Hook 在不同环境下是否属于真实 Hook、Skill 模拟、Command 触发、人工降级或 CLI 侧能力，目前边界混乱；
4. 对纯 CLI 环境不熟悉，需要进一步判断只用 CLI 时 Rules、Skill、Agent、Hook 分别如何表达。

该讨论对 04 的启发：

1. 当前不应把 LDVH 能力表达为用户可选功能配置；
2. 可以先定义“部署入口清单”或“环境入口适配清单”，但其语义应是必备项检查，不是用户选择项；
3. 入口部署对象先聚焦 Rules、Skill、Agent、Hook；
4. Code、Web、CLI 更适合作为 LDVH 能力保障或检查执行能力，不一定属于环境入口部署对象；
5. Hook 需要单独澄清真实 Hook、模拟 Hook、生命周期触发、人工降级之间的边界。

四类必备入口的边界补充：

1. Rules、Skill、Agent、Hook 是当前 LDVH 面向 AI 开发环境的必备入口能力，不是用户可选功能配置；
2. 四类必备入口不等于把所有相关资产都复制到每个管辖项目，也不等于每个环境都必须具备同名原生能力；
3. Rules 的边界是让 AI 稳定看到 LDVH 入口、规则约束、STOP 点和目标项目识别要求；
4. Skill 的边界是承载可复用 SOP 或操作能力，原生 Skill 不存在时可以转译为指令化流程、命令模板或人工步骤，但仍需可检查；
5. Agent 的边界是承载独立上下文、专项审查或分角色执行能力，原生 Agent 不存在时可以由主控 AI 顺序模拟，但必须显式记录目标、输入和输出；
6. Hook 的边界是生命周期触发和检查入口，可能由原生 Hook、Skill 模拟、命令触发或人工检查清单降级实现，不能把降级实现误写成原生支持；
7. Code、Web、CLI、MCP 和文档不是同一层级的部署入口；它们可以是能力保障、检查执行、展示入口、连接器或事实承载位置，但不应混入四类入口清单；
8. 四类入口的部署与检查必须保留现有 specs 中的边界：事实源边界、Human Gate、环境适配状态查询、管辖项目目标边界和降级证据边界都不能遗漏。

## 8. 新增讨论：管辖项目概念必须纳入部署入口

用户指出需要叉开讨论“管辖项目”概念。部署入口如果不区分 LDVH 自身项目、管辖项目和 AI 开发环境入口，会导致入口部署语义混乱。

当前临时判断：部署入口不是单纯部署到 LDVH 仓库，也不是单纯部署到某个业务项目，而是部署到 AI 执行时能够识别当前管辖项目，并按 LDVH 规则治理它的入口链路里。

需要区分至少三层：

1. LDVH 自身项目：承载 specs、Code、Web、规则、能力保障和 LDVH 自身工作对象规范；
2. 管辖项目：被 LDVH 管理、检查、落地和记录工作对象的目标项目；
3. AI 开发环境入口：Trae、Codex、Claude Code、CLI 等环境中承载 Rules、Skill、Agent、Hook 的入口。

该概念对部署入口的影响：

1. 不应把 LDVH 的 Rules、Skill、Agent、Hook 错装成每个管辖项目的一套完整副本；
2. 不应在每个管辖项目复制 specs 正文形成第二事实源；
3. Skill 应优先被理解为 LDVH 通用能力，执行时根据当前管辖项目 id/path 读取对应项目事实源；
4. Agent 输入必须包含管辖项目边界，避免跨项目误读事实源；
5. Hook 触发时必须知道作用对象是 LDVH 自身、工作区入口，还是某个管辖项目；
6. 管辖项目入口应尽量薄，只用于识别受 LDVH 管辖、定位管辖项目配置和指向 LDVH 统一入口。

后续需要读取 specs 中关于管辖项目的正式定义，尤其是目录说明和管辖项目配置规范，再判断部署入口规则应如何接入。

已读取的正式规范包括：

1. `specs/00-LD-Vibe-Harness理念与纲要.md`；
2. `specs/01-目录说明.md`；
3. `specs/03.05-管辖项目配置规范.md`。

从 specs 得到的正式边界：

1. LDVH 需要区分 LDVH 自身项目和管辖项目；
2. LDVH 自身项目承载和维护 `specs/`、Code、Web、文本能力资产和 dogfood 事实实例；
3. 管辖项目是安装并使用 LDVH 进行工程治理的用户项目；
4. 管辖项目不默认创建 `specs/` 或等价规范工作区；
5. 管辖项目的项目文档位置由项目自身约定决定，工作对象事实源是 `{path}/ldvh-base`；
6. 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 只登记当前 LDVH 管理实例，以及管辖项目的 `id`、`path`、可选 `name`、可选 `description`；
7. `LDVH-GOVERNED-PROJECTS.yaml` 不记录初始化状态、落地状态、检查状态、环境能力、适配措施或缺口处理状态；
8. 管辖项目接入后，应优先检查工作区根目录配置是否登记该项目，并检查对应项目的 `ldvh-base/` 和必要的工作区级薄入口；
9. 管辖项目不默认创建环境规则文件、项目指令或等价项目级入口；确需例外时，必须 Human 明确授权并记录影响范围；
10. 项目入口文档可以是 README，但不得承载 LDVH 稳定规范规则、工作对象状态机、字段契约或验收事实；
11. 管辖项目 `docs/studies` 和 `docs/sources` 结论必须吸收后才成为项目稳定事实；
12. 工作模型实例由项目拥有，存放在项目结构化事实源目录中。

对部署入口讨论的修正：

1. 部署入口首先应面向工作区级 / 环境级入口，让 AI 能识别 LDVH 管理实例和管辖项目清单；
2. 不应默认在每个管辖项目创建项目级 Rules、Skill、Agent、Hook 入口；
3. 若某个管辖项目确需项目级入口，应作为例外适配措施处理，并触发 Human Gate；
4. Rules / Skill / Agent / Hook 的部署状态应区分“LDVH 通用入口已部署”和“某管辖项目例外入口已部署”；
5. 管辖项目配置文件不是部署状态事实源，部署状态、缺口和检查结论应由当前检查报告、Task、适配卡片、Code 输出或其他对应事实源承载。

多管辖项目带来的新增判断：

1. 多个管辖项目是 LDVH 管理实例的必然场景，不应为了降低复杂度而假设只有一个管辖项目；
2. 多项目本身不是问题，默认选择才是问题；
3. 管辖项目配置只回答“当前工作区中的 LDVH 管哪些项目”，不回答“本次任务要处理哪个项目”；
4. 凡是动作会读取、检查、修改或回写管辖项目事实源，AI 必须先确定目标管辖项目；
5. 目标管辖项目可以来自用户明确指定的 `project_id`、明确路径、当前工作目录唯一匹配、或当前流程上下文中的唯一项目；
6. 如果当前路径匹配多个嵌套项目，应优先使用最长路径匹配，但高影响写入前仍应 Human Gate；
7. 如果当前路径不在任何登记项目下，或用户说“当前项目”但无法唯一匹配，AI 不得默认选择第一个项目，应暂停并询问 Human；
8. 如果用户要求处理所有项目，可以遍历检查，但写入和缺口关闭仍应明确授权范围，并按项目隔离输出；
9. 多项目检查报告必须逐项目标注 `project_id`、`project_path`、检查范围、缺口和降级，不得混成一个整体结论；
10. Code 命令和部署入口应支持 `project_id` / `project_path` / `all projects` 等目标模式；没有目标参数时，只应做项目清单检查或要求确认，不应直接检查或修改某个项目；
11. LDVH 自身 dogfood 项目不得被解释为用户安装后的默认管辖项目；
12. Rules、Skill、Agent、Hook 在多项目场景下必须携带或解析目标项目边界，避免跨项目误读、误写和事实源污染。

管辖项目设置后的行为调整：

1. 设置管辖项目后，用户需要通过 Web 或等价 Human-facing 入口知道发生了什么变化；
2. 设置管辖项目可以建立或检查 LDVH 需要的数据文件夹或结构化事实源目录，用于承载 LDVH 工作对象实例；
