## 1. 本文解决的问题

本文解决 LD Vibe Harness specs 中术语边界如何定义、机制英文专名如何使用、中文术语如何加定语、管辖项目如何定义、模型实践子文档如何命名，以及术语变更如何治理的问题。

术语边界的目标是避免同一词语在 specs 中同时指代 Trae 机制、规范条款、对象规则、行动条件或普通能力，导致事实源和执行边界混淆。

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 的产品理念、价值实现标准、五类构成要素和基础规范索引。本文承接 00 中关于术语一致性和事实源单一性的要求，专门定义术语边界、机制英文专名、中文术语定语、模型实践子文档命名和术语变更治理。

本文是 LDVH 术语边界和术语变更治理的权威位置。00 只保留术语一致性的顶层要求；03 定义 specs 文档结构和引用纪律，不重复维护术语边界。

## 3. 术语边界职责

本文的权威领域是 LDVH 机制英文专名、中文术语定语、管辖项目定义、模型实践子文档命名、Scenario 与 Rules 的术语边界、落地初始化/落地审计/合规检查术语边界和术语变更治理。

术语边界用于约束 specs 写作中的命名一致性。涉及具体机制细节时，仍以对应机制规范为准；本文只定义机制名、中文术语和文档标题中的命名纪律。

## 4. 机制英文专名

LDVH specs 中，英文机制名 Rules、Skill、Agent、Tools、Web 专指 Trae 或 LDVH 工具体系中的机制层：

| 术语 | 含义 | 机制规范 |
|---|---|---|---|
| Rules | Trae Rules 机制 | `specs/11.01-Rules机制规范.md` |
| Skill | Trae Skill 机制 | `specs/11.02-Skill机制规范.md` |
| Agent | Trae Agent 机制 | `specs/11.03-Agent机制规范.md` |
| Tools | LDVH `tools/` Tools 辅助机制 | `specs/12.01-Tools辅助规范.md` |
| Web | LDVH `web/` Web 信息同步机制 | `specs/12.02-Web信息同步规范.md` |
| PyTools | LDVH `tools/` 下由 Python 构建的确定性辅助程序 | `specs/12.01-Tools辅助规范.md` |

提到上述机制时，应使用英文专名 Rules、Skill、Agent、Tools、Web、PyTools，不使用裸中文"规则""技能""代理""智能体""程序""展示"替代。

Tools 与 PyTools 的区分：Tools 指 Tools 辅助机制层（概念、原则、职责边界），PyTools 指 `tools/` 下具体的 Python 程序实现。避免"工具"一词同时指向机制和实现，造成泛化指向。

## 5. 中文术语必须加定语

中文"规则""技能""代理""智能体""程序""展示"等词不得裸用，除非上下文已经通过标题、表格字段或段落首句明确限定其语义。

推荐用法如下：

| 场景 | 推荐术语 | 不推荐裸用 |
|---|---|---|
| specs 中定义的稳定条款 | specs 规范 | 规则 |
| 事实模型字段、状态、验收、检查 | 对象规则、字段规则、状态规则、验收规则、检查规则 | 规则 |
| 行动模型的 Context、Scenario、Gate、流程、回写、证据 | 行动规则、Scenario 识别条件、行动进入条件、Gate 条件、回写要求 | 规则、触发规则 |
| 普通能力说明 | 能力、功能、流程、方法 | 技能 |
| AI 泛称 | AI 执行者、AI 代理能力、子代理能力 | Agent、代理、智能体 |
| 确定性工具辅助 | Tools 辅助、Tools 适配、Tools 能力 | 程序、程序辅助 |
| Python 确定性辅助程序 | PyTools 实现、PyTools 脚本 | 工具程序、Python 工具 |
| Web 信息同步能力 | Web 信息同步、Web 适配、Web 信息同步层 | 展示 |
| Trae / LDVH 机制适配 | Rules 适配、Skill 适配、Agent 适配、Tools 适配、Web 适配 | 规则适配、技能适配、代理适配、程序适配、展示适配 |

## 6. LDVH 与 Harness 的关系及构成要素全称与短称

LD Vibe Harness 是 Harness 思想的实践，简称为LDVH。Harness 不是独立对象域，不作为工具、事实模型或行动模型的归属前缀。

在 00 总纲等理念层文档中，当 LD Vibe Harness 语境已经由标题、段落或章节明确限定时，可以使用"工具""事实模型""行动模型"作为构成要素短称。

在编号分区、文档标题、跨文档引用、对象规范和行动规范中，应使用"LDVH 工具""LDVH 事实模型""LDVH 行动模型"等正式全称。

不得使用"Harness 工具""Harness 事实模型""Harness 行动模型"作为正式术语。

## 7. 管辖项目

管辖项目是指接入并使用 LD Vibe Harness 进行需求、任务、证据、变更、审计或交付治理的实际项目。

管辖项目与 LDVH 项目（ld-vibe-harness）的关系：

| 维度 | LDVH 项目 | 管辖项目 |
|---|---|---|
| 定位 | LDVH 规范体系的承载和维护项目 | 接入 LDVH 进行工程治理的实际业务项目 |
| 规范来源 | specs/ 定义规范 | 遵循 LDVH specs 定义的规范 |
| ldvh-base/ | 承载 LDVH 项目自身的事实实例 | 承载该管辖项目的事实实例 |
| Rules | L1 声明项目定位和专属硬约束 | L1 声明项目定位和专属硬约束 |
| 事实模型规则 | L0 事实模型规则适用于所有管辖项目 | L0 事实模型规则适用于所有管辖项目 |

管辖项目目录由 L0 工作区规则中的管辖项目配置定义。L0 管辖项目配置是管辖项目目录列表的权威位置，决定了 `ldvh-base/` 目录应出现在哪些项目目录下。

每个管辖项目应各自拥有 `ldvh-base/` 目录，由该项目自身管理（依据 `specs/01-LDVH目录说明.md` §3.5）。管辖项目之间不共享 `ldvh-base/` 目录。

管辖项目必须遵守 LDVH 事实模型基础规范（`specs/13-LDVH事实模型基础规范.md`）和 L0 事实模型规则。事实模型规则定位于 L0 层级，因为事实模型的字段契约、状态机、Human Gate 和引用完整性规则由 LDVH specs 统一定义，对所有管辖项目通用，不属于单个项目的场景规则。

## 8. 模型实践子文档命名中的机制名

事实模型和行动模型的 `NN.01` 至 `NN.05` 模型实践子文档必须使用机制英文专名：

| 模型实践子文档 | 机制含义 | 不承载内容 |
|---|---|---|
| `NN.01-Rules.md` | Rules 入口约束实践子文档 | 不承载对象规则、行动规则、Scenario 完整识别条件或完整 SOP |
| `NN.02-Skill.md` | Skill 契约式行动实践子文档 | 不承载普通能力说明，不替代行动流程或对象规范 |
| `NN.03-Agent.md` | Agent 独立上下文并行实践子文档 | 不承载泛化 AI 代理说明，不替代 Agent 定义摘要或 Trae 平台实体 |
| `NN.04-Tools.md` | Tools 契约式校验与执行实践子文档 | 不承载业务事实，不替代 Tools 实现或事实源 |
| `NN.05-Web.md` | Web 信息同步实践子文档 | 不承载 UI 状态作为事实源，不替代 Web 实现 |
| `NN.06-Contract.md` | 契约子文档 | 不承载主模型规则，只定义结构化契约、字段 schema、接口契约和数据结构 |

模型实践子文档的内容边界依据 `specs/03-Specs文档规范.md` §4.3，主模型核心内容应留在 `NN` 主文件。Tools 适配和 Web 适配只说明机制接入边界，不承载具体实现代码。

模型实践子文档属于附件型实践承接文档。主文档应保证模型定义完整可读，子文档只在实践内容复杂或需要独立维护时按需创建。子文档可以承接 Rules 入口约束示例、Skill 契约式行动输入输出、Agent 上下文隔离映射、Tools 契约式校验字段、Web 信息同步字段等实践展开，但不得把主模型核心规则迁移到子文档中维护。

NN.01-NN.05 为机制实践子文档，NN.06 为契约子文档。两者都是附件型子文档，都按需创建，都不重新定义主模型，但性质不同：机制实践子文档回答"这个模型如何实践某个机制"，契约子文档回答"这个模型的结构化接口、schema 和数据契约是什么"。契约子文档不得承载主模型的对象定位、状态机、Scenario、Gate、执行流程或 Human Gate；这些内容应留在主文档。

### 8.1 模型实践子文档标题命名维度规则

附件型实践子文档标题格式为：`{主模型名} — {机制名}{实践类型}`。契约子文档标题格式为：`{主模型名} — 契约`。

标题命名遵循以下维度规则：

1. **机制名必须使用 LDVH 标准术语**：机制名必须使用 Rules / Skill / Agent / Tools / Web，不得使用功能替代词（如"常驻上下文"替代 Rules）、承载方式（如"预制脚本程序"替代 Tools）或实现形式（如"网页信息呈现"替代 Web）替代；
2. **实践类型使用固定标准名称**：`NN.01-Rules.md` 固定为 Rules 入口约束实践，`NN.02-Skill.md` 固定为 Skill 契约式行动实践，`NN.03-Agent.md` 固定为 Agent 独立上下文并行实践，`NN.04-Tools.md` 固定为 Tools 契约式校验与执行实践，`NN.05-Web.md` 固定为 Web 信息同步实践；具体模型不得自行替换为流程实践、上下文隔离实践、能力实践、展示实践等其他实践类型名称；
3. **实践类型命名不设置局部选项**：模型实践子文档不得按局部实现方式选择其他实践类型名称；如某机制在特定模型中不创建实体或暂缓实现，应通过子文档状态和正文说明表达，不得通过改变标题实践类型表达；
4. **语义定义由区间基础规范补充**：NN.01-NN.06 各编号的语义定义由 13 §4.6（事实模型）和 14 §4.6（行动模型）在各自附件型实践子文档表格中补充，通用规则依据 `specs/04-LDVH模型子文档规范.md`。本文不重复维护。

本规则是模型实践子文档标题命名的权威位置。13 §4.6 和 14 §4.6 的标题格式规则应引用本规则，不得并行维护同一命名维度约束。

## 9. Scenario 与 Rules 的边界

行动模型判断何时进入某行动时，应使用"Scenario 识别条件"或"行动进入条件"。

Rules 可以通过短摘要提醒 AI 评估某个 Scenario，但不应在 Rules 模型实践子文档中维护完整 Scenario 识别条件、角色矩阵、报告模板、执行流程或对象规则。

## 10. 落地初始化、落地审计与合规检查

落地初始化是指将规范中已经设计或规划的内容转化为项目实际可用实践的初始化计划和首次执行动作。它关注"设计如何进入实践"，例如：创建必要目录、创建或更新 Rules 摘要、创建 Skill 实体、确认 Agent 可用清单、准备 Tools 校验能力、配置信息同步型 Web 入口、建立索引引用和记录暂缓项。落地初始化不是合规检查，不以逐条审查既有内容是否符合规范为主要目标。

落地审计是指对已经完成或声称完成的落地初始化结果进行审查，确认对应实践是否真实存在、持续有效、与 Git 文件事实源一致、未绕过 Human Gate，且未与上位规范或权威事实源冲突。落地审计关注"实践是否按设计落地并持续有效"。

合规检查是指依据 specs、Rules、对象规范、行动模型或工具规范中的明确条款，对某份文档、对象实例、行动执行、工具输出或机制实践进行符合性检查。合规检查关注"对象是否符合既有规范要求"。

三者关系如下：

| 概念 | 核心问题 | 典型对象 | 输出 |
|---|---|---|---|
| 落地初始化 | 设计如何进入实践 | 目录、Rules、Skill、Agent、Tools、Web、索引、初始化记录 | 初始化计划、初始化产物、暂缓项 |
| 落地审计 | 实践是否真实落地并持续有效 | 已初始化的实践内容和事实源 | 审计结论、缺口、整改建议 |
| 合规检查 | 是否符合规范条款 | 文档、对象实例、行动输出、工具输出、机制实践 | 检查结果、违规项、修正建议 |

落地初始化、落地审计和合规检查是不同层级的治理概念。落地审计可以使用合规检查作为检查手段，但不得把合规检查等同于落地审计；落地初始化可以产生后续合规检查所需的事实源或对象，但不得被写成合规检查清单。

落地初始化、落地审计和合规检查是独立于具体行动模型或事实模型的规范性工作，应在对应基础规范中定义概念和边界，在具体行动或对象文档中按需定义落地初始化计划、落地审计要求和合规检查标准。

## 11. 术语变更治理

术语变更治理用于确保术语边界、机制名含义和附件型实践子文档命名不会被局部文档隐式改写。涉及术语边界、机制含义、模型实践子文档机制含义或契约子文档承载边界的变更，应统一按本文 Human Gate 与检查要求执行。

## 13. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变本文定义的术语边界或 Rules、Skill、Agent、Tools、Web 的机制名含义；
2. 改变 LDVH 与 Harness 的关系定义，或将 Harness 前缀作为工具、事实模型、行动模型的正式术语；
3. 将中文"规则""技能""代理""智能体""程序""展示"等裸用词提升为正式术语；
4. 改变管辖项目的定义或管辖项目目录配置的权威位置；
5. 改变 `NN.01` 至 `NN.05` 模型实践子文档的机制含义或命名维度规则；
6. 改变 `NN.06` 契约子文档的定位或承载边界；
7. 将 Scenario 识别条件、行动流程或对象规则转移到 Rules 模型实践子文档；
8. 让 Skill 适配文件承载 Agent 调度；
9. 让 Agent 适配文件替代 Trae Agent 实体定义；
10. 让 Tools 适配文件承载具体实现代码或替代事实源；
11. 让 Web 适配文件承载 UI 状态作为稳定事实；
12. 让契约子文档承载主模型的对象定位、状态机、Scenario、Gate、执行流程或 Human Gate。

当 AI 识别到上述情况时，依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §7 Human Gate 与检查要求执行。

术语规范检查至少包括：

| 检查项 | 标准 |
|---|---|
| 机制英文专名 | Rules、Skill、Agent、Tools、Web 使用英文机制名 |
| 中文术语定语 | 中文"规则""技能""代理""智能体""程序""展示"等词已加定语或上下文限定 |
| LDVH 与 Harness 关系 | LD Vibe Harness 是 Harness 思想的实践，简称为LDVH；Harness 不作为构成要素归属前缀 |
| 管辖项目定义 | 管辖项目定义与 L0 管辖项目配置一致，ldvh-base/ 目录位置与配置匹配 |
| 模型实践子文档命名 | NN.01-NN.05 使用机制英文专名，NN.06 为契约子文档 |
| 术语变更治理 | 术语变更已评估 Human Gate |
| 架构术语一致性 | 与五类构成要素、事实模型和行动模型术语一致 |
