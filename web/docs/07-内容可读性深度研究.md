# 内容可读性深度研究

> 关联工作项：workcase-0029
> 范围：LDVH Web 展示层对象详情、列表、仪表盘和文档阅读体验
> 结论：优先采用“字段语义化渲染 + 长文本渐进展开 + 右侧扩展阅读区”的组合方案。

## 1. 当前痛点

### 1.1 长文本字段缺少结构层次

LDVH 事实对象中常见 `description`、`success_criteria`、`constraints`、`context`、`consequences`、`resolution` 等字段。这些字段在 YAML 中通常以整段文本承载，在页面中直接展示时会出现三个问题：

- 用户需要通读整段内容才能识别关键结论；
- 多个长字段连续出现时，页面纵向滚动成本高；
- 字段间的重要性差异不明显，验收标准、约束、来源、证据等关键事实容易被淹没。

### 1.2 Checklist 与普通 Markdown 的阅读目标不同

`success_criteria` 不是普通说明文本，而是 WorkCase 执行和关闭审查的检查清单。当前若只把它当作 Markdown 渲染，会弱化以下信息：

- 已完成项与未完成项的进度差异；
- 每个检查项是否足够原子；
- 成功标准与验证证据之间的对应关系。

### 1.3 引用字段缺少上下文预览

`related_workcases`、`related_adrs`、`related_docs`、`orchestration.execution_items.input_refs` 等字段承担追溯关系，但只展示 ID 或路径时，用户还需要跳转后才能判断是否值得阅读。大量跳转会打断主线阅读。

### 1.4 页面缺少“主线/辅助信息”分层

对象详情页把字段逐块平铺，适合完整审计，但不适合快速理解。新用户需要先知道“这是什么、现在处于什么状态、下一步是什么”；维护者则需要快速看依赖、验收和证据。

## 2. 改善方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| 字段语义化渲染 | 按字段类型使用不同组件：checklist、引用卡片、证据块、长文本摘要 | 直接提升关键字段可读性；与事实模型字段契约一致 | 需要维护字段到组件的映射 | ObjectDetail |
| 渐进展开 | 每个长文本字段默认显示摘要，支持展开全文 | 降低首屏信息密度；保留完整事实 | 摘要生成规则需要谨慎，不能丢失事实 | description、context、consequences |
| 右侧扩展阅读区 | 点击关联文档或引用对象时，在右侧面板展开预览 | 不打断主内容阅读；适合桌面深度阅读 | 移动端需要降级为抽屉或单页跳转 | related_docs、related_workcases、ADR 引用 |
| 结构化摘要卡 | 对 WorkCase、ADR 生成顶部摘要：状态、来源、执行项、下一步 | 快速建立对象认知；适合新用户 | 需要避免与事实源形成第二事实源 | 对象详情页顶部 |
| 关键项高亮 | 对未完成 execution_items、缺失证据、review_needed 等状态加视觉提示 | 强化行动导向 | 过度高亮会造成噪音 | Dashboard、ObjectDetail |

## 3. 推荐组合

### 3.1 对象详情页采用三层阅读结构

1. 顶部摘要层：对象类型、标题、状态、更新时间、来源对象、下一步信号；
2. 主内容层：description、success_criteria、decision、context 等核心字段；
3. 扩展阅读层：related_docs、related_workcases、related_adrs、原始 YAML。

这样可以保留事实完整性，同时让不同角色按需要阅读。

### 3.2 字段组件按语义渲染

建议建立字段渲染优先级：

| 字段类别 | 字段示例 | 推荐组件 |
|---|---|---|
| 检查清单 | success_criteria、orchestration.execution_items | ChecklistCard 或结构化执行项视图，显示完成比例和每项状态 |
| 依赖关系 | workcase、related_workcases、related_adrs | ReferenceCard，显示对象 ID、标题、状态 |
| 长文本说明 | description、context、consequences | SummaryText，默认展示前几行并可展开 |
| 文档引用 | related_docs | DocPreviewLink，点击后在右侧阅读区打开 |
| 关闭证据 | closure_evidence | EvidenceBlock，突出验证命令、文件路径和结果 |
| 原始事实 | YAML source | 折叠代码块，默认收起 |

### 3.3 长文本不要自动改写事实

摘要只能作为展示层派生结果，不应回写到 YAML。若需要长期保存总结，应创建 Spark 或更新规范允许的字段，避免 Web 展示层形成第二事实源。

### 3.4 Checklist 应服务 WorkCase 关闭流程

`success_criteria` 建议渲染为可审计列表：

- 已完成项使用弱化样式；
- 未完成项保持高可见度；
- 若 WorkCase 处于 review_needed，显示关闭审查提示；
- 后续可将 closure_evidence 与 success_criteria 项建立视觉对应，但不改变 WorkCase 字段契约。

## 4. 可执行设计建议

1. ObjectDetail 顶部增加摘要卡，突出状态、来源、依赖和下一步；
2. 将 `success_criteria` 从普通 Markdown 升级为 ChecklistCard；
3. 将 `related_docs`、`related_workcases`、`related_adrs` 统一渲染为引用卡片；
4. 桌面端引入右侧扩展阅读区，用于预览关联文档和引用对象；
5. 移动端将扩展阅读区降级为底部抽屉或跳转详情；
6. 保留 YAML 原文折叠区，作为事实完整性兜底；
7. 所有展示增强只消费事实源，不新增未定义事实字段。

## 5. 后续实现优先级

1. 先改 ObjectDetail 的字段渲染，让 WorkCase、执行项、ADR 的详情页更容易读；
2. 再改 Dashboard 的行动信号，让待推进事项与最近动态更清晰；
3. 最后实现右侧扩展阅读区，承接多角色审视中提出的桌面深度阅读模式。
