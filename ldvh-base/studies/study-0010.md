## 研究问题

### 项目问题

LDVH 未来会同时遇到资料阅读、规则核对、代码实现和验证等工作。问题并不是是否"应该使用更多代理"，而是：一项工作何时真的可以拆开，拆开后谁对共享改动、交接信息和最终判断负责。

这关系到项目推进的节奏。若把工具提供的并行能力直接当成流程，读者会看见许多局部产出，却无法知道哪一个结论进入了项目、哪一处改动由谁汇总；反过来，若把一切都留给单一执行者，独立的阅读与核验又会不必要地串行。本研究为后续具体任务提供判断框架，不设定长期流程。

### 外部问题

Codex 的子代理和 Git worktree 能如何帮助 LDVH 处理可并行的研究、核验与实现工作，同时避免把产品能力误写为固定流程？

### 本次边界

本报告于 2026-07-23 重新阅读上述资料，只讨论 Codex 的子代理、worktree 与运行时配置对协作方式的启发。它不比较其它 agent 产品，不测量并行的实际收益，也不声称任何当前项目已采用、验证或授权这些做法。

特别地，worktree 是否需要环境准备、哪些文件可以并发修改、何时汇总结果，取决于未来具体任务和当前工作树；这些都不能从产品文档自动得出。本报告也不把 v3 的历史结论当作本次来源。

## 关键发现

### 发现一：可并行的是有独立交付面的阅读与核验

Subagents 文档把代码库探索、测试、分诊和资料汇总这类任务列为适合并行的场景。它们的共同点不是任务名称，而是可以先说明输入问题、预期输出和不碰触的范围：一份资料比较、一个只读代码定位或一项测试观察，都能由主线程在随后统一吸收。

这对 LDVH 的启发是，先问"结果交回后能否由一个人清楚比较和采用"，再决定是否拆分。一个可用的最小交接是：要回答的问题、输出形式、允许读取的范围、不得修改的范围，以及谁负责汇总。这样并行服务于推进判断，而不是制造更多过程记录。

它不等于代理越多越好。多个任务若争夺同一份事实对象、同一个 Schema 或同一处代码设计，表面上可以分派，实质上仍要共享判断；这类工作过早并行，往往只是把冲突从开始时移到汇总时。

**对后续项目工作的直接影响**：本发现应影响 `specs/03-行动编排规范.md`（如已存在）或 WorkCase 中主控-角色调度机制的设计。当前不需要创建新对象，但后续在开发主控调度机制时应引用本发现作为"什么可以并行"的判断标准。

### 发现二：Worktree 解决的是检出隔离，不是交接和可交付性

Local environments 文档说明 worktree 可把并发改动放在独立目录中。这使两个确实需要不同改动面的任务可以减少直接覆盖，也让主工作目录不必承担所有实验性改动。

对 LDVH 而言，真正需要保留的是"实际在哪个工作树写入"和"谁负责把结果带回主线"两件事。独立目录仍可能缺依赖、生成文件、环境变量或本地准备；即使测试在一个目录通过，也不自动说明结果适合另一个目录，更不说明可以合并。

因此，worktree 是在具体 WorkCase 中可验证的手段，而不是 Study 可以提前宣布的默认流程。若任务没有真实的并行写入需求，额外建 worktree 反而增加准备与交接成本。

**对后续项目工作的直接影响**：本发现应影响 WorkCase 的执行实践——当 Human 要求试行并行实现时，应在 WorkCase 执行记录中明确 worktree 准备状态、交接方式和合并顺序。当前不需要创建新对象，但后续与 worktree 相关的 WorkCase 应引用本发现作为准备清单的依据。

### 发现三：运行时权限和项目责任是两层不同的东西

Configuration Reference 说明子代理会继承父任务的沙箱与权限上下文，并允许以配置控制并发或专用角色。这解释了运行时能做什么、会受到什么限制。

但项目责任仍需在任务语境里明确：谁能修改共享文件、谁吸收多路发现、何时需要 Human 判断方向或接受风险。运行时允许一次写入，不表示这次写入已经有项目层面的理由；运行时能同时启动多个角色，也不表示结果之间已经一致。

这一区分让 LDVH 不必把产品配置抄成规范。配置是当次执行条件，项目责任则由目标、规则与 Human 决定共同限定；两者都应在需要时被看见，但不应互相替代。

**对后续项目工作的直接影响**：本发现应影响 00 文档中关于"以规范源为边界系统"章节和 05 事实模型中"来源"定义的引用。如果后续发现 Web 或 Helper 的响应将运行时权限展示为项目结论，应创建 Pitfall 记录该误用模式。当前不需要创建新对象。

## 建议

### 建议一：创建 ADR 讨论"主控-角色调度机制"的设计归属

本研究三个发现都指向同一个问题：LDVH 需要一个清晰的"主控-角色调度机制"来确定何时并行、谁负责汇总、什么可以委托给子代理。当前 03 行动编排规范和 05 事实模型基础规范都没有定义这一机制。

建议创建 ADR，记录以下选项及其取舍：
- 选项 A：在 03 行动编排规范中定义主控-角色调度机制，05 只记录执行事实
- 选项 B：在 05 事实模型中定义角色契约作为事实对象，03 引用它
- 选项 C：不定义通用机制，在每个具体 WorkCase 中临机决定

验收条件：ADR 完成后，后续 Study 或 WorkCase 在涉及并行拆分时能直接引用 ADR 的结论，而不会重复本研究的问题。

**承接目标**：ADR，`object_id` 由创建时分配
**判断标准**：当本研究的三条发现已在至少两次后续工作中被引用，并且 AI 仍然需要重复讨论"是否可以并行"时，即满足创建 ADR 的条件。

### 建议二：当 Human 要求试行并行实现时，创建 WorkCase 记录实际交接

本研究不预设 worktree 或子代理作为默认流程，但在 Human 明确要求试行的场景下，建议创建有界 WorkCase，其执行项至少包括：
- worktree 准备状态检查（依赖、环境变量、本地配置）
- 各工作树写入范围（文件路径白名单）
- 合并顺序和冲突处理方案
- 汇总结论与残留风险记录

该 WorkCase 的产出不是证明"并行天然正确"，而是收集实际成本和净收益，供 Human 决定是否固化为长期默认。

**承接目标**：WorkCase
**判断标准**：Human 明确说出类似"用两个工作树同时改 X 和 Y"或"你拆成子代理并行做"的指令，且目标改动面可独立重叠验证时，创建 WorkCase。

### 建议三：研究结论直接作为判断线索，不单独创建治理对象

本研究的三个发现目前都不需要单独创建 Spark、Pitfall 或 WorkCase。它们可以直接在后续工作中作为判断线索——当 AI 遇到"是否可以并行"的问题时，引用本研究的三条发现作为判断框架。

**判断标准**：当后续工作中 AI 或 Human 提到"是否可以拆开做""是否需要建 worktree""子代理能否写文件"这类问题时，直接引用本研究的相关发现，而不是另建对象。只有出现"多次并行产出的结果难以汇总"或"共享写入责任不清"的具体症状时，才创建 Spark 记录该症状。
