## 1. 本文定位

本文定义多角色思考工作流程使用的结构化契约。本文解决角色定义放哪里、角色如何被选择、主控如何构造多角色子 Agent 调用参数、子 Agent 如何返回角色分析结果、主控如何汇总为多角色报告，以及回写建议如何表达的问题。

本文是 `specs/41-multi-role-thinking-多角色思考.md` 的历史机制文件，不是独立工作流程。本文不得重新定义多角色思考的行动定位、准入条件、Scenario、执行流程、Gate、事实源回写或 Human Gate。发生冲突时，以 41 主文档和上位基础规范为准。

---

## 2. 事实源边界

1. 角色定义和默认角色集合的权威位置是本文；
2. 角色不是 `ldvh-base/`工作模型，不创建 Role 事实实例；
3. 不创建"角色应用场景"工作模型；不同用途下的输出结构由本文契约字段表达；
4. Skill、Agent Prompt、Tools、Web 和工具缓存不得复制维护角色定义第二事实源；
5. Tools 可以从本文派生索引、校验 schema 或展示数据，但派生物不是事实源；
6. Web 可以展示角色、报告和 Human Gate 待确认项，但 UI 状态不是事实源；
7. 修改本文角色定义、默认角色集合或契约字段属于规范变更，应评估 Human Gate 并记录 Change（依据 specs/22-Change-变更.md）

角色独立性原则：

1. 默认角色集合必须能够脱离当前环境预装系统 Agent 独立使用；
2. 当前环境系统 Agent、自定义 Agent 文件或 PMKit 推荐自建 Agent 清单只能作为角色视角、触发场景和审查维度的抽象素材；
3. 本文不复制和维护任何外部 Agent 的完整 Prompt，不把外部 Agent 名称作为运行前提；
4. 删除、禁用或未安装外部 Agent 不影响主上下文轻量模式使用本文角色；
5. 多角色子 Agent 模式只依赖主控当前能启动的可调用 Agent 容器，角色能力来自本文契约和本次运行时注入参数。

## 3. RoleDefinition 契约

RoleDefinition 表示一个稳定角色定义。

```yaml
id: 稳定英文标识，必填，全局唯一
name: 中文角色名，必填
dimension: 角色维度，必填
focus: 关注点列表，必填
triggers: 适用触发场景，必填
output_formats:
  multi_role_thinking: 多角色思考场景输出字段，必填
prompt_template: 可注入主上下文或可调用 Agent 容器的角色提示模板，必填
notes: 补充说明，选填
```

字段约束：

1. `id` 应使用小写英文和连字符，不使用项目私有业务名；
2. `name` 应表达角色职责，不绑定具体平台或技术栈品牌；
3. `dimension` 用于分组和精简角色；
4. `focus` 用于指导角色分析关注点；
5. `triggers` 用于辅助主控选择角色；
6. `output_formats.multi_role_thinking` 默认应包含适用性、影响范围、分析结论、风险和建议动作；
7. `prompt_template` 是角色提示模板，不等于可调用 Agent；
8. 角色定义不得包含密钥、凭据、生产环境权限或不可公开的内部敏感信息。

## 6. RoleSelectionOutput 契约

RoleSelectionOutput 表示主控选择角色后的输出。

```yaml
selected_roles:
  - role_id: 稳定角色 ID；role_origin 为 runtime 时可为空
    role_name: 角色或临时职能名称，必填
    role_origin: preset | runtime
    reason: 选择理由，必填
    temporary_scope: 临时职能适用边界；role_origin 为 runtime 时必填
    preset_gap: 默认角色不足以覆盖的原因；role_origin 为 runtime 时必填
    promotion_candidate: 是否建议后续评估沉淀，必填
excluded_roles:
  - role_id: 角色 ID
    reason: 排除理由
mode_recommendation: 主上下文轻量模式 / 多角色子 Agent 模式
mode_reason: 模式选择理由
human_gate_required: true / false
human_gate_reason: 触发原因，选填
```

字段规则：

1. `role_origin: preset` 表示来自默认角色集合；
2. `role_origin: runtime` 表示本次临时职能，不属于稳定角色定义；
3. `role_origin: runtime` 时，必须填写 `temporary_scope` 和 `preset_gap`；
4. `promotion_candidate: true` 只表示建议后续评估，不等于已批准沉淀；
5. 将 runtime 临时职能升级为 preset 默认角色，必须触发 Human Gate 并修改默认角色集合。

选择规则：

1. 优先选择与变更类型直接相关的角色；
2. 涉及事实源、规则、编号、对象、工作流程时必须包含 `governance-reviewer`；
3. 涉及 Human Gate、权限、删除、远程操作、Agent 或工具写入时必须包含 `risk-permission-reviewer`；
4. 涉及完成标准、关闭、Review 或审计时必须包含 `verification-evidence-reviewer`；
5. 涉及 Skill、Agent、MCP 或 Tools 时必须包含 `ai-collaboration-architect` 或 `tooling-architect`；
6. 涉及 Web 信息同步、受控编辑或 Human Gate 工作台时应包含 `webtools-product-reviewer`；
7. 涉及落地审计或合规检查时应包含 `audit-reviewer`；
8. 涉及核心价值审查、V1 稳定理解、上下文获取问题、AI 依赖聊天记忆或 Context 定义审查时应包含 `context-precision-reviewer`；
9. 单次分析选中角色数超过 4 个时，应精简、合并同维度角色或拆分分析批次；
10. 多角色子 Agent 模式下，同一轮并行启动的子 Agent 实例不得超过 4 个。

## 7. AgentRoleInvocation 契约

AgentRoleInvocation 表示主控在多角色子 Agent 模式下给可调用 Agent 容器注入的角色参数。

```yaml
role_id: 角色 ID，必填
role_name: 角色名，必填
role_prompt: 由 prompt_template 和本次主题合成的角色提示，必填
topic: 分析主题，必填
context_pack: 本角色可读取或已提供的事实源摘要，必填
output_format: 本角色应返回的结构，必填
boundary_rules:
  - 不直接写入事实源
  - 不替代 Human Gate
  - 不把工具缓存或派生视图作为事实源
human_gate_rules: 本次需要特别关注的 Human Gate 条件，选填
```

约束：

1. 每个 AgentRoleInvocation 只注入一个主要角色；
2. 同一可调用 Agent 容器可以并行启动多个实例，但同一轮多角色子 Agent 模式并行启动的子 Agent 实例不得超过 4 个；
3. 不依赖 `.trae/agents/` 自定义 Agent 文件；多角色子 Agent 模式由 Rules 入口触发后，由主控使用当前运行环境提供的可调用 Agent 容器并注入角色参数实现，详见 `specs/41.03-Agent.md`；
4. AgentRoleInvocation 只能作为主控编排子 Agent 的运行时参数契约，不得被 Skill、Tools、MCP 或脚本作为直接调度 Agent 的接口契约；
5. 当前运行环境提供的可调用 Agent 容器不是 LDVH Tools 辅助层；
6. 子 Agent 输出必须返回主控汇总，不得直接成为事实源；
7. 子 Agent 不得自行执行高影响写入。

## 10. WriteBackSuggestion 契约

WriteBackSuggestion 表示事实源回写建议。

```yaml
should_write_back:
  - target: 目标文件或对象
    reason: 回写原因
    type: Task / Memo / ADR / Risk / Evidence / Change / docs / specs / rules
should_not_write_back:
  - content: 不应回写的过程信息
    reason: 不回写原因
human_gate_required: true / false
change_required: true / false
notes: 补充说明
```

约束：

1. 仅服务当前对话的过程分析不回写；
2. 需要执行的明确动作应进入 Task；
3. 有保留价值但暂不任务化的信息应进入 Memo；
4. 长期有效决策应进入 ADR 或 specs；
5. 不确定因素应进入 Risk；
6. 验证结果或关闭证据应进入 Evidence；
7. 实际修改应记录 Change（依据 specs/22-Change-变更.md）
8. 规范或规则正文写入前应评估 Human Gate。

## 11. 工具和 Web 消费要求

Tools 和 Web 消费本文契约时应遵守：

1. 可以读取本文生成角色索引、报告 schema、字段校验规则和展示模型；
2. 不得修改本文定义的角色语义；
3. 不得把工具缓存、数据库派生视图或 UI 状态作为事实源；
4. 不得直接决定角色结论；
5. 不得替代 Human Gate；
6. 不得把 AgentRoleInvocation 契约作为直接调度 Agent 的接口契约；
7. 输出的结构化结果必须能追溯到本文字段和 Git 文件事实源。

## 12. 检查项

检查本文是否被正确使用时，应确认：

1. 角色定义是否从本文读取，而不是从 Skill、Agent Prompt、工具缓存或 Web 状态读取；
2. 角色选择是否说明选择理由；
3. RoleSelectionOutput 是否标注每个 selected role 的 `role_origin`；
4. runtime 临时职能是否包含 `temporary_scope`、`preset_gap` 和 `promotion_candidate`；
5. 是否避免把 runtime 临时职能当作稳定角色事实引用；
6. 多角色子 Agent 调用参数是否包含角色、主题、上下文、输出格式和边界规则；
7. AgentRoleInvocation 是否只作为主控编排子 Agent 的运行时参数契约使用；
8. 角色分析结果是否包含适用性、影响范围、结论、风险和建议动作；
9. 多角色报告是否包含一致结论、分歧点、风险汇总、执行顺序、回写建议和 Human Gate；
10. 回写建议是否遵守事实源边界；
11. 修改本文是否记录 Change，并在必要时触发 Human Gate（依据 specs/22-Change-变更.md）
