## 1. 本文解决的问题

本文解决 LDVH 中测试要求如何跨 Code、Web、工作流程和后续构成要素保持一致的问题。

本文定义测试治理的稳定上层规则，包括验证声明、测试实现归属、测试证据边界、无法自动化时的等价验证、失败处理和同步触发。具体实现域的测试命令、测试文件映射、夹具结构、API contract、页面测试、组件测试、构建入口和迁移计划由对应实现文档承载。

---
## 2. 与 00 总纲的关系

00 要求 LDVH 形成可读取、可执行、可验证、可回写的运行闭环。测试是验证闭环的确定性反馈方式之一，服务于 AI 执行、Human 判断、Code 稳定反馈、Web 信息同步和事实源回写前后的风险控制。

本文承接 00 的运行闭环要求，定义测试与 Git 文件事实源、规范正文、Code、Web、Human Gate 和工作流程之间的治理关系。测试结果、测试缓存、测试夹具和测试报告只提供验证证据或诊断输入，不替代 Git 文件事实源、specs 正文、工作对象或 Human Gate 记录；事实源边界应遵守 `specs/09-事实源边界与承载规范.md`。

---
## 3. 测试治理分层

LDVH 的测试治理按三层分工：

| 层级 | 承载位置 | 职责 |
|---|---|---|
| 上层测试要求 | `specs/11-测试基础规范.md`、对应构成要素 specs | 定义验证纪律、事实源边界、测试归属、验证声明、失败处理和同步触发 |
| 实现测试细则 | `code/docs/`、`web/docs/` 或对应实现域文档 | 定义当前参考实现的测试入口、命令、文件映射、夹具组织和执行细节 |
| 测试实现 | `tests/` 下按构成要素分区的测试目录 | 承载可执行测试代码、最小夹具、正反样例和回归样例 |

测试要求应进入 specs 或对应构成要素规范。测试实现细则应进入对应实现域文档。测试代码、测试夹具和回归样例应进入 `tests/`。同一规则不得在 specs、实现文档和测试代码中复制维护为多个权威来源。

---
## 4. 测试实现归属

`tests/` 是测试实现集合目录，只承载按构成要素分区的测试代码、最小夹具、正反样例和回归样例，不承载规范正文、测试策略、长期规则、对象契约、状态机或 Human Gate 条件。

测试实现归属规则如下：

1. Code 工具、脚本、校验器、受控写入和其它确定性实现的测试放入 `tests/code/`；
2. Web API、Web 组件、Web 页面、Human-facing 交互和 Web 写入边界的测试放入 `tests/web/`；
3. 工作流程的可测试性锚点由 40-59 成员主文件按 `specs/03.03-工作流程文档规范.md` 声明，具体测试实现归属应由 active 工作流程主文件、对应实现域文档和工作计划共同确定；
4. 新增构成要素或实现域需要长期测试分区时，应先回到 `specs/01-目录说明.md` 和本文判断目录归属，再按需触发 Human Gate；
5. 实现框架生成的临时缓存、覆盖率、截图、浏览器 trace、构建产物和运行报告不得进入测试事实源。

Code 当前参考实现的测试映射由 `code/docs/` 承载，并受 `specs/07-Code确定性执行实现规范.md` 的测试边界约束。Web 当前参考实现的测试入口、测试类型、API contract、页面验证和夹具约定由 `web/docs/` 承载，并受 `specs/08-Web信息同步实现规范.md` 的测试边界约束。实现域文档不得通过测试细节反向改写 specs 稳定规则。

---
## 5. 验证方式与声明

LDVH 认可以下验证方式：

| 验证方式 | 适用场景 | 声明要求 |
|---|---|---|
| 自动化测试 | 成功条件、失败条件和输入输出可机械复现 | 说明测试入口、关键覆盖点和结果 |
| 命令校验 | 文档结构、引用、构建、格式、类型或 CLI 行为可由命令稳定反馈 | 说明命令、退出状态和关键输出 |
| 等价验证 | 自动化测试暂不可行，但可通过最小样例、人工检查或现有工具复现关键风险 | 说明原因、替代步骤和残留风险 |
| Human 验收 | 涉及授权、确认、体验判断或高影响选择 | 说明确认对象、影响范围、用户选择和证据位置 |
| 回归验证 | 修复 bug、迁移结构或改变输入输出后防止复发 | 说明复现样例、失败前表现和通过条件 |

AI 只能在验证方式、关键输出和残留风险可复现时，把变更表述为已验证。无法建立完整测试时，应说明原因、采用的等价验证方式和残留风险，不得表述为完整验证。测试失败、关键校验未运行或验证证据无法追溯时，不得关闭相关任务、提交验收结论或声明变更完成。

---
## 6. 事实源与证据边界

测试证据用于支持判断，不成为最终事实源。测试证据应能回指测试入口、输入范围、关键样例、命令输出或 Human 验收记录。

测试相关内容的事实源边界如下：

1. 测试代码和测试夹具只服务验证，不定义规范规则、字段契约、状态机、流程步骤或事实实例；
2. 测试结果、覆盖率、截图、缓存、Mock 数据和浏览器 trace 不替代 Git 文件事实源；
3. 测试夹具应保持最小化，只表达被验证行为所需的输入；
4. 当测试暴露规范缺口、对象契约缺口或实现文档缺口时，应回到对应 specs、工作对象或实现文档处理；
5. 当测试样例形成长期可复用经验、风险、后续工作或决策时，应按工作模型归入 Pitfall、ADR、WorkPlan 或 Memo。

---
## 7. 同步触发规则

以下变化应同步检查测试要求、实现测试细则和测试实现是否需要更新：

1. specs 正式规范新增、删除、重命名、编号占用、引用关系、章节结构或规范落地要求变化；
2. 工作模型字段契约、状态机、对象关系、事实源边界、Human Gate 条件或受控写入规则变化；
3. 工作流程的 Context、Scenario、Gate、执行流程、回写、证据或行动特有可测试性锚点变化；
4. Code CLI、输入输出、错误码、诊断格式、写入行为、目录假设、下游消费合同或模块结构变化；
5. Web API、页面、组件、派生视图、缓存策略、写入白名单、Confirm UI、i18n 或来源呈现变化；
6. 测试目录、测试命令、测试夹具、Mock 数据、构建入口或验证入口变化；
7. 工作计划关闭、验收、发布、迁移或删除实现前需要确认验证证据是否仍可复现。

触发后应优先判断变化属于上层测试要求、实现测试细则还是测试实现。上层规则进入 specs；当前参考实现细节进入对应 `code/docs/` 或 `web/docs/`；可执行测试进入 `tests/`。

---
## 8. Code、Web 与工作流程测试协作

Code 与 Web 分属不同构成要素，测试也应按构成要素分区承接。Code 测试不得混入 Web 测试目录，Web 测试不得混入 Code 测试目录。二者可以基于同一 Git 文件事实源和同一 specs 契约分别实现读取、解析、聚合和展示验证。

Code 测试应优先验证确定性输入输出、错误处理、诊断结构、exit code、受控写入边界和回归样例。Code 当前参考实现的测试映射、命令入口和拆分策略由 `code/docs/` 承载。

Code 测试不得只停留在入口加载、字段存在或输出非空等烟雾断言。对被 AI 入口、Human 操作、CI、发布或验收声明依赖的关键 CLI 聚合入口，应提供端到端自动化测试或命令校验，并同时覆盖成功路径和可复现失败路径。LDVH 当前 Code 参考实现中，`npm run test:code` 应作为 Code 完整测试入口，至少包含 `tests/code` 自动化测试和 `python3 code/specs_validate.py all --fail-on-diagnostics` 综合检查；只运行局部单元测试时，应在验证声明中说明未覆盖综合入口的残留风险。

Web 测试应优先验证 Human-facing 读取、呈现、交互、空态、错误态、只读边界、写入边界、来源呈现、i18n 和敏感信息边界。Web 当前参考实现的测试入口、API contract、页面验证、构建检查和夹具约定由 `web/docs/` 承载。

工作流程测试机制应先由 40-59 active 成员主文件提供行动特有可测试性锚点。具体测试用例、预期行为矩阵、失败诊断和回归用例是否形成统一实现入口，应在对应流程主文件、实现域文档和工作计划中逐步稳定，不得用测试实现反向恢复未 active 的工作流程。

## 9. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | Code、Web、工作流程和后续实现域的测试治理应遵守本文定义的验证声明、事实源边界和测试归属 | `specs/07-Code确定性执行实现规范.md`、`specs/08-Web信息同步实现规范.md`、`specs/09-事实源边界与承载规范.md`、`specs/03.03-工作流程文档规范.md`、实现域文档、测试实现 | 测试治理 | 测试归属、验证声明或测试证据边界变化时 |
| 入口可见要求 | AI 执行 Code、Web、工作流程或验收相关任务时应能定位本文作为测试基础规范 | AI 入口分层、目录说明、Code/Web 实现文档入口摘要 | AI 执行入口提示 | 测试基础规范文件名、定位、适用范围或入口引用变化时 |
| 确定性执行要求 | 可机械化的测试目录、测试归属、文档引用和验证入口应由 Code 校验或记录缺口 | Code 检查、测试、人工降级检查 | 校验实现 | 测试目录规则、测试命令、测试文件映射或验证入口规则变化时 |
| Human 交互要求 | 改变测试归属、验证声明标准、测试结果事实源性质或验收证据边界前应评估 Human Gate | Human Gate、影响范围说明、确认记录 | 测试治理确认 | 测试结果可能影响任务关闭、验收、事实源回写或高影响发布时 |
| 生命周期触发要求 | 规范、Code、Web、工作流程或测试实现变化后，应检查本文和对应实现文档是否需要同步 | 规范修改执行顺序、实现文档联动检查、测试回归、人工降级检查 | 触发保障 | §7 任一同步触发场景发生时 |

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变 `tests/`、`tests/code/`、`tests/web/` 的目录定位或事实源性质；
2. 将测试结果、测试缓存、覆盖率、截图、Mock 数据或测试报告提升为稳定事实；
3. 改变“已验证”“等价验证”“完整验证”的声明标准；
4. 删除高价值测试、回归样例或验收证据且缺少替代验证方式；
5. 用测试实现反向定义 specs 规则、对象字段契约、状态机、Human Gate 或工作流程；
6. 新增长期测试分区、改变构成要素测试归属或扩大测试对任务关闭和验收的判定范围。

测试治理检查至少包括：

| 检查项 | 标准 |
|---|---|
| 分层归属 | 上层要求在 specs，当前参考实现细则在实现域文档，可执行测试在 `tests/` |
| 目录归属 | Code 测试、Web 测试和后续实现域测试按构成要素分区 |
| 验证声明 | 已验证、等价验证、残留风险和未验证状态表达准确 |
| 事实源边界 | 测试输出、缓存、夹具和报告未替代 Git 文件事实源 |
| 同步联动 | 规范、实现、文档和测试变更后已检查对应联动 |
| 失败处理 | 测试失败或关键验证未运行时未关闭任务、验收或提交完成结论 |
