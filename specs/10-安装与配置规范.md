## 1. 价值判断

本文存在的价值，是让 V3 能确定当前工作对象是否属于 LDVH 管辖项目，并把安装、初始化、项目归属、事实源入口、Git Hook 接入、环境承接策略、验证和回滚边界交给 Code 做确定性判断，减少 AI 依赖当前目录、路径相似、对话记忆、长流程模板或主观意图判断项目归属与安装步骤的负担。

安装与配置规范主要服务 V1、V3、V4 和 V7：它让 AI 与 Code 快速定位 LDVH root、目标工作区、管辖项目配置、项目事实源入口和安装检测入口，正确判断 target 是否受管、是否 unknown 或跨项目，稳定执行 target-first 解析、install plan 生成、受控 apply 和 verify，并在涉及写入、提交、事实源回写或环境入口承接时保留可检查证据。它回答“这个工作对象归哪个项目管辖”“安装将改变什么”“哪些动作必须 Human Gate”“如何验证和回滚”，不替代事实对象实例、环境 integrated 证明或 Human 风险接受。

## 2. 权威依据

本文承接 `specs/03-事实源与Git溯源规范.md` 的 Git 文件事实源边界，承接 `specs/01-保障与衔接.md` 的环境入口、Hook 分类、插件 / 扩展包安装口径和 integrated 声明边界，承接 `specs/02-AI行为规范.md` 的主控判断责任，承接 `specs/04-Specs基础规范.md` 的正式规范结构，并与 `specs/05-事实模型基础规范.md`、`specs/07-Code确定性执行规范.md`、`specs/09-测试与验证规范.md` 配合。

若安装计划、管辖项目配置与事实对象实例冲突，先以 Git 可追踪事实源和 Human Gate 处理冲突。若 Code 解析结果与本文正文冲突，以本文正文和 Human Gate 为准。

## 3. 归口边界

本文归口定义 LDVH 安装与初始化中的机器可消费规则：LDVH root、目标工作区根目录、管辖项目登记、工作对象归属、target-first 判定、多目标边界、Git worktree 身份匹配、项目事实源入口、install_plan、environment_strategy、apply 写入边界、验证和回滚。

本文不归口定义事实对象完整字段、真实实例内容、Web 页面/API 数据路径、具体插件 manifest schema、commit message 契约、行动模板实例或环境 integrated 判定。事实对象规则归 05 和 20-24，Code 实现边界归 07，Web 同源独立读取归 08，验证归 09，环境入口分类、安装回滚上位边界和 integrated 声明归 01 §6。安装或环境入口动作必须引用本文做 target/project 解析和 install plan 约束，但不得把本文写成 Human Gate 已完成或环境已 integrated 的证明。

## 4. 适用范围

本文适用于：

1. 目标工作区根目录中的 `LDVH-GOVERNED-PROJECTS.yaml`；
2. 安装、接入、初始化、配置、检查安装是否生效、修复旧插件 / 旧路径或 stale V2 path；
3. AI、Code、测试、preflight、runtime facade、Hook 或环境入口动作对工作对象的管辖项目归属判断；
4. target path、cwd fallback、Git common-dir、worktree、staged paths 和多 target 场景；
5. 事实对象真实实例、Web 同源独立读取和后续环境入口动作前后的项目边界判断；
6. 安装向导 CLI 或等价 Code facade 的 `check`、`plan`、`apply` 和 `verify`。

## 5. 管辖项目配置契约

管辖项目配置事实源是 `LDVH-GOVERNED-PROJECTS.yaml`。该文件只能位于目标工作区根目录，使用 YAML mapping 表达产品说明和项目列表。项目根目录、用户级目录、LDVH 本体目录或事实源目录下的同名文件都不是 V3 支持的配置位置。

配置根字段必须包含 `product_name`、`product_description` 和 `projects`。每个项目必须包含稳定 `id` 和 `path`；`name`、`description` 和 `git` 是可选说明或身份线索。字段闭集、必填性和 resolution 输出字段由 `specs/attachments/10.Att.01-管辖项目配置字段表.md` 承接。

`LDVH-GOVERNED-PROJECTS.yaml` 是项目登记事实源，只登记管辖项目入口和身份线索，不得替代事实对象实例、项目索引、知识地图、Web 缓存或 runtime receipt。项目列表不得反向定义 20-24 的字段、状态、关闭条件或 Human Gate。

配置中的 `path` 可以是相对目标工作区根目录的路径，也可以是绝对路径。使用相对 path 时，目标工作区根目录是 path 的基准目录，配置中所有管辖项目的相对 path 都应以工作区根目录为起点解析。目标工作区根目录必须是这些管辖项目的有效父目录或独立于项目目录的位置，不应与 LDVH 本体路径或某个管辖项目的根路径等同——除非该工作区确只管理一个项目且 LDVH 本体即为该项目。

管辖项目必须是 Git 管理的项目；`git` 字段可以由 Code 从项目根 Git worktree 推导，但项目本身不能是非 Git 目录。`git.common_dir` 如存在，必须作为 Git worktree / Codex worktree 的确定性身份线索；`git.remote_url` 只能作为证据线索，不得单独决定管辖项目命中。

### 5.1 配置层级冲突

同一路径链上只能存在一个 active `LDVH-GOVERNED-PROJECTS.yaml`。当 Human 或 Code 明确选择目标工作区根目录时，解析必须从根目录向深层路径检查目标项目；如果目标工作区根目录和目标项目或其中间目录同时存在多个 active `LDVH-GOVERNED-PROJECTS.yaml`，AI 和 Code 必须阻断，不得静默选择最近配置、不得自动合并、不得自动覆盖。

用户要求安装或初始化某个目标工作区，但目标项目内已经存在 `LDVH-GOVERNED-PROJECTS.yaml` 时，该项目内配置只能视为 legacy / conflict，不能作为可选主位置。AI 必须提示 Human 先删除、迁移或明确保留其中一个配置文件。删除、迁移、合并或覆盖配置都属于 Human Gate；未确认前不得继续声明工作区配置完成。

当 explicit target 指向工作区根目录时，应按该 target 的路径链解析；当 cwd 位于项目内但 explicit target 指向工作区根目录时，项目内配置不得覆盖 explicit target。只有缺少 explicit target 时，才允许使用 cwd fallback。

## 6. 工作对象与判定顺序

工作对象是本次操作实际影响的目录、文件、仓库、staged paths 或项目。V3 判定管辖项目必须采用 target-first；只有缺少明确 target 时，才允许使用 cwd fallback。

Code 判定顺序为：

1. target path 命中项目 `path`；
2. target Git common-dir 命中项目 `git.common_dir` 或项目根 Git common-dir；
3. explicit project 仅用于校验、消歧或 Human 确认，不得覆盖真实 target；
4. cwd path 作为 fallback；
5. cwd Git common-dir 作为 fallback；
6. 未命中时 no-op。

AI 不得依据路径相似、对话记忆、目录名称或用户意图自行判定管辖项目归属。Code 必须输出 `target_resolutions`，逐 target 记录 `normalized_path`、`source`、`status`、`governed_project_id`、`governed_project_path`、`governed_via`、`git_common_dir` 和 `unknown_reason` 等证据。

路径归一化原则、比较规则和规范化函数契约遵循 `specs/attachments/10.Att.02-路径语义与规范化规则.md`。

## 7. 多目标与 no-op 边界

同一管辖项目内的多个 target 可以形成同一 `governed_subject`。跨管辖项目 target、Git identity 多项目歧义、或写操作中管辖/非管辖混合 target，必须阻断、拆分或进入 Human Gate，不得静默合并。

非管辖 target 应 no-op，不触发 LDVH 管辖项目机制，也不得把非管辖项目写入 `LDVH-GOVERNED-PROJECTS.yaml`。环境 Hook 或外部 adapter 已确认 target/cwd 不属于管辖项目时，no-op 必须静默，不输出 runtime guidance、read_plan、completion warning、additionalContext 或 deny 决策。只读操作遇到不确定 target 时可以输出 warning 或 unverifiable；写入、提交或事实源回写遇到 unknown target 时必须阻断或要求显式 target。

`git.commit-msg` 的工作对象是 repo root、repo common-dir 和 staged paths；message file 只作为提交消息输入，不得被误当作项目 target。

## 8. 事实源入口与环境引用边界

管辖项目的事实对象实例默认位于项目根下的 `ldvh-base/`。V3 自身的真实事实对象实例位于该路径；Web API 按 08 从同一 Git 文件事实源独立读取这些实例。管辖项目配置仍只建立项目登记、项目归属解析和边界校验，不建立通用 Web 写入，不恢复知识地图，也不替代事实对象字段 schema。

首次启用管辖项目时，应检查项目根下是否存在以下事实源目录，并向 Human 说明用途。创建这些目录属于项目级事实源初始化，必须进入 Human Gate；目录存在只表示事实源入口具备，不表示已有事实实例、Web 写入已启用、Hook 已安装或环境入口已 integrated。

| 目录 | 用途 | 不得替代 |
|---|---|---|
| `ldvh-base/workcases/` | 承载 WorkCase 工作项实例，记录目标、推进状态、验证证据、关闭证据和后续分流。 | 不替代行动模板、Human Gate 或项目管理工具。 |
| `ldvh-base/adrs/` | 承载 ADR 决策实例，记录已确认决策、取舍依据、影响和吸收/归档状态。 | 不替代 specs 正文、未确认讨论或一次性执行策略。 |
| `ldvh-base/pitfalls/` | 承载 Pitfall 踩坑经验实例，记录已验证的问题、根因、解决方式和规避策略。 | 不替代未解决问题、规范规则或测试失败缓存。 |
| `ldvh-base/sparks/` | 承载 Spark 火花实例，记录待分流想法、候选发现、问题线索和后续归口。 | 不替代 WorkCase、ADR、Study 或当前对话临时记忆。 |
| `ldvh-base/studies/` | 承载 Study 稳定研究报告实例，使用 Markdown frontmatter 和正文沉淀研究结论。 | 不替代外部原文、临时调研材料或未经吸收的研究过程。 |

临时调研材料、外部资料或第三方参考不得被写成本规范的固定目录要求；只有被提升为稳定事实的研究报告进入 `ldvh-base/studies/`。

项目索引不得替代事实源。Code 可以实时读取 `LDVH-GOVERNED-PROJECTS.yaml` 和项目根路径，生成当次解析结果、diagnostic、source_refs 或 preflight 辅助信息；这些输出都是过程输出，不是项目索引事实源、授权、放行或 Human Gate 完成。

Hook、adapter、commit gate 或环境入口的安装、回滚和 integrated 状态归 01 §6。它们可以引用本文 resolver 判断目标是否处于管辖范围、作用域是否单一、是否跨项目或混合非管辖 target；本文不得被写成安装授权、部署完成或环境生效证明。

### 8.1 安装计划与执行契约

安装与配置的确定性入口应按 `check -> plan -> apply -> verify` 组织。`check` 和 `plan` 必须只读；`apply` 是唯一可以写入配置、目录、Git Hook、thin reference 或其它安装对象的阶段；`verify` 必须复用可复跑的验证入口。

`install_plan` 是安装执行前的机器契约，至少包含：

| 字段 | 要求 |
|---|---|
| `ldvh_root` | LDVH 本体绝对路径，必须能找到 specs、Code 和 Runtime Protocol |
| `workspace_root` | 目标工作区根目录，配置文件以此为基准 |
| `governed_config` | 目标工作区根目录下的 `LDVH-GOVERNED-PROJECTS.yaml` |
| `target_projects` | 已选择或已解析的管辖项目列表，包含路径、Git worktree 和 Git common-dir 线索 |
| `environment_strategy` | `plugin_hook`、`thin_reference`、`manual_entrypoint`、`external_adapter_candidate` 或 `unsupported` |
| `checks` | 只读检查事实，不得混入 Human 选项 |
| `planned_writes` | 将写入、修改、升级或删除的对象及位置 |
| `skipped_writes` | 本次不会执行的对象及原因 |
| `human_gate_required` | 是否需要 Human Gate 以及触发原因 |
| `rollback` | 每个写入动作的回滚或卸载入口 |
| `verification` | 写入后必须运行的验证命令、预期输出和不可验证范围 |
| `source_refs` | 10、01、07、09、Code 后端和相关附件 |

参数齐全、无配置层级冲突、目标项目已受管且是有效 Git worktree、环境策略明确、没有旧 Hook / 旧插件覆盖风险且 `--confirm-human-gate` 已显式提供时，CLI 可以把 `check -> plan -> apply -> verify` 压缩为 direct path 执行。任一候选不唯一、冲突存在、覆盖风险存在、目标环境不明、跨项目或混合非管辖 target、缺少 Human Gate 时，CLI 必须停止在 `plan` 或 `check`，输出诊断和待 Human 选择项，不得自行推断。

`apply` 第一优先级复用已有 Code 后端：管辖项目解析和配置校验、环境入口审计、Git Hook 状态/安装/卸载/verify、统一验收和 runtime 可见性探针分别使用对应 Code 模块。CLI 不得复制第二套 target resolver、Hook installer、环境入口分类或 integrated 判断。具体 Code 入口、模块职责和测试映射由 Code 实现域文档与可执行测试承接。

### 8.2 环境承接策略

环境是否支持 Hook 不形成两套安装规则，只决定 `environment_strategy` 和写入对象：

| `environment_strategy` | 使用场景 | 写入或承接对象 | 验证边界 |
|---|---|---|---|
| `plugin_hook` | 目标环境支持插件、扩展包或 package 形态 Hook | 目标环境插件 / 扩展包 / package 方案；不得直接写用户环境 Hook 系统文件 | 安装检测可验证插件可见、manifest、V3 shim、旧路径和 repo-local shim 正反输入；真实 lifecycle 仍需断点后验证 |
| `thin_reference` | 目标环境没有自动 Hook，但能读取 repo instruction 或等价薄引用 | 指向 `hooks/LDVH-RUNTIME-PROTOCOL.md` 的薄引用文本 | 验证薄引用可读、manual entrypoint 可运行、runtime adapter 产出 receipt |
| `manual_entrypoint` | 目标环境只能手动调用 runtime adapter | manual `runtime_adapter.py` 命令和恢复入口语 | 验证 `status=ok`、`event=session_start`、`receipt_id` 和 `Diagnostics: none` |
| `external_adapter_candidate` | 目标环境需要外部 adapter，但尚未成为正式入口 | adapter 候选说明和后续 Gate | 不声明 installed 或 integrated，只输出候选和缺口 |
| `unsupported` | 目标环境能力不明或没有可承接入口 | 不写环境入口 | 输出阻断或待确认项 |

文件存在、插件缓存、薄引用文本、历史 trust、shim 直测或 manual receipt 都不得单独写成 integrated。integrated 仍由 01 的环境入口规则判断，必须具备真实自动触发、稳定 payload、失败处理、安装接入证据、回滚方式和测试证据。

## 9. 保障措施

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 配置契约要求 | 管辖项目配置必须可解析、字段闭集、项目 ID 唯一 | 10.Att.01、Code validator、tests | 项目治理 | 新增或修改 `LDVH-GOVERNED-PROJECTS.yaml` 时 |
| 配置层级要求 | 配置只能位于目标工作区根目录；同一路径链只能存在一个 active 配置；遇到项目内配置必须阻断 | 本文、Code hierarchy check、tests | 配置治理 | 选择目标工作区、安装或迁移配置时 |
| target-first 要求 | 判定必须优先使用实际工作对象，cwd 只能 fallback | 本文、07、preflight、tests | 工作对象治理 | 写入、提交、Hook payload 或显式 target 出现时 |
| Git identity 要求 | worktree 必须通过 Git common-dir 等确定性身份匹配 | Code resolver、Git 命令、tests | Worktree 治理 | target path 与登记 path 不同但 Git 身份相同时 |
| 多目标边界要求 | 跨项目或管辖/非管辖混合写入必须阻断或分流 | Code diagnostic、09 测试 | 边界治理 | 一次操作含多个 target 时 |
| 环境引用边界要求 | 安装或环境入口动作只能引用本文解析目标，不得把本文写成安装授权或环境生效证明 | 01、07、09、迁移记录 | 环境治理 | 安装 Hook、声明接管或运行时阻断时 |
| 安装计划要求 | 安装必须先形成可复跑 `install_plan`，分离检查事实、计划写入、Human Gate、回滚和验证 | 本文、07、09、Code facade、tests | 安装治理 | 安装、初始化、配置或修复旧入口时 |
| apply Gate 要求 | 写入只能发生在 `apply`，且必须显式提供 Human Gate；`check` 和 `plan` 必须只读 | 本文、Code CLI、tests | 写入治理 | 修改配置、目录、Git Hook、薄引用或插件承接时 |
| 环境策略要求 | 支持 Hook 与不支持 Hook 只改变 `environment_strategy`，不得拆成两套规则或声明未验证 integrated | 01、本文、Code audit、tests | 环境治理 | 生成安装计划或交还验证时 |

## 10. 验证方法

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 配置检查 | `LDVH-GOVERNED-PROJECTS.yaml` 是否存在、可解析、字段闭集、项目 ID 唯一 | 修正配置或记录不可验证缺口 |
| 配置层级检查 | 从目标工作区根目录向目标项目深层路径是否只存在一个 active `LDVH-GOVERNED-PROJECTS.yaml`，且该配置是否位于目标工作区根目录 | 暂停，要求删除、迁移或明确保留其中一个配置 |
| Git 项目检查 | 已选择管辖项目是否为有效 Git worktree；非 Git 目录不得作为可安装管辖项目继续执行 | 暂停安装，并说明管辖项目必须是 Git 仓库 |
| 归属检查 | target path、cwd fallback 和 Git common-dir 是否能稳定解析项目归属 | 补 target、修配置或输出 no-op/unknown |
| 多目标检查 | 同项目、多项目、管辖/非管辖混合 target 是否按边界处理 | 阻断、拆分或进入 Human Gate |
| 事实源检查 | 项目配置是否没有替代事实对象实例或项目索引事实源；首次启用时是否说明 `ldvh-base/` 及五个子目录用途 | 回到 03/05/10 修正边界 |
| 环境引用检查 | 输出是否没有把管辖项目配置写成 Hook 安装授权、部署完成或环境入口已经生效 | 回到 01/07/09 或环境适配缺口 |
| 安装计划检查 | `install_plan` 是否包含 root、workspace、配置、项目、环境策略、检查事实、计划写入、回滚、验证和 source_refs | 补齐 plan 或停止 apply |
| apply Gate 检查 | 写入命令是否只在 `apply` 执行，且是否显式带 Human Gate | 拒绝写入 |
| 环境策略检查 | `plugin_hook`、`thin_reference`、`manual_entrypoint` 等策略是否都回到 runtime adapter receipt 和统一安装验证 | 修正策略或写为不可验证 |

## 11. Human Gate

以下情况必须进入 Human Gate：

1. 新增、删除、重命名或批量迁移管辖项目登记；
2. 接受路径、Git identity 或项目 ID 歧义；
3. 一次写入跨多个管辖项目或混合管辖/非管辖 target；
4. 删除、迁移、合并或覆盖同一路径链上的多个 `LDVH-GOVERNED-PROJECTS.yaml`；
5. 创建、删除、迁移或重命名管辖项目根下的 `ldvh-base/` 或事实对象子目录；
6. 将项目配置、Code 输出、Web 缓存或运行时 receipt 升级为事实对象实例或项目索引事实源；
7. 把管辖项目配置或解析结果写成 Hook 安装授权、部署完成、通用 Web 写入授权或环境入口生效证明。
8. 执行 `install_plan` 中任何 `planned_writes`；
9. 选择或改变 `environment_strategy`，或接受 `plugin_hook`、`thin_reference`、`manual_entrypoint`、`external_adapter_candidate` 的风险与限制；
10. 覆盖、升级、禁用或卸载既有 Git Hook、插件、扩展包、thin reference 或旧路径。

## 12. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 缺少明确 target，但当前行动涉及写入、提交或事实源回写；
2. `LDVH-GOVERNED-PROJECTS.yaml` 缺失、不可解析、字段越界或项目 ID 冲突；
3. `LDVH-GOVERNED-PROJECTS.yaml` 位于项目根目录、用户级目录、LDVH 本体目录或事实源目录，或同一路径链上存在多个 active 配置，但尚未由 Human 删除、迁移或明确保留其中一个；
4. Git common-dir 命中多个项目，或 remote_url 被单独用于决定归属；
5. 已选择管辖项目不是有效 Git worktree，却准备继续安装、初始化或接入 Git Hook；
6. 跨管辖项目或管辖/非管辖混合写入未拆分；
7. Code、Web、Hook、Rules 或项目索引正在替代事实源、Human Gate 或事实对象实例；
8. `ldvh-base/` 目录用途、写入影响或 Human Gate 状态未说明，却准备创建、删除或迁移事实源目录；
9. 管辖项目配置或静态解析结果被写成 Hook 安装授权、部署完成或运行时拦截已启用。
10. `apply` 未显式带 Human Gate，却准备写入配置、目录、Git Hook、thin reference、插件或外部 adapter；
11. `install_plan` 缺少回滚、验证、source_refs 或不可验证范围；
12. 环境策略只证明文件存在、插件可见、薄引用存在或 shim 直测，却准备声明 integrated。
