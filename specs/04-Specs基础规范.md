## 1. 价值判断

本文存在的价值，是让 specs 成为 AI 可快速定位、充分理解、正确判断、稳定执行，并能被 Code 稳定解析、被 Human 确认审核的规则承载层。

本文承接 `specs/00-理念与构成.md` 的 V1-V9 价值门和 `specs/01-保障与衔接.md` 的保障与衔接规则，按以下顺序服务：

| 服务对象 | 本文如何服务 |
|---|---|
| AI 第一 | 固定头部、主体规则区、固定尾部共同明确权威、归口、范围、规则、保障、验证和停止条件，服务 V1、V2、V3 和 V4，减少 AI 猜测。 |
| Code 第二 | 通过 identity block、固定头尾、信息角色索引、显式路径和附件字段表提供可解析入口，支撑 V1、V6 和 V7。 |
| Human 第三 | 价值冲突、Human Gate 和不可自动判断事项不得由 AI 或 Code 代替确认，支撑 V5 门禁确认和 V8 范式交互。 |
| 体系迭代 | 结构、附件、Code 派生、review、迁移或验证缺口必须回到对应承接位置，支撑 V9。 |

本文不以“写得完整”为目标，而以“能被 AI 正确使用、能被 Code 支撑定位、能被 Human 审核”为目标。

正式 spec 必须说明自身为什么存在、减少 AI 哪类负担、如何承接 00 的价值门。不能说明价值的内容，不应进入正式 spec。

价值判断只说明本文服务哪些 00 价值、减少哪类 AI 负担、为什么值得成为规范；不得重写 00 的价值门，不得把本地价值判断升级为新的上位价值。

## 2. 权威依据

本文的上位依据是 `specs/00-理念与构成.md` 和 `specs/01-保障与衔接.md`。

本文不得重定义 00 的存在理由、AI 第一服务对象、构成要素、价值门或最高 Human Gate 口径。若本文与 00 冲突，以 00 为准。

本文不得重定义 01 的保障需求、消费时机、承接机制、receipt、evidence、diagnostic 或缺口分流基础语义。若本文结构规则与 01 的保障与衔接规则冲突，应回到 00、01 和 Human Gate。

00 作为根规范，不受本文固定头尾和主体规则区要求的反向约束。00 应尽量遵循本文的可定位、可解析、可验证原则，但可以因其根规范性质豁免固定头尾顺序和完整性要求。

正式 spec 必须声明自身权威依据。权威依据用于回答：

1. 本文承接哪些上位规范；
2. 本文不能重定义哪些上位判断；
3. 冲突时应回到哪一层处理。

Code 可以读取 `basis` 字段和正文路径，但不能替规范作者判断权威承接是否合理。权威判断必须在正文中成立。

## 3. 归口边界

本文归口定义 specs 的写作、引用、附件、迁移、修改、审核和 Code 解析入口规则。

归口边界用于回答：本文有权定义什么，不能把什么内容反向定义成上位规则。

正式 spec 必须声明自身归口边界。归口边界应使用正向定义，不使用无限排除清单。

推荐表达方式：

```text
本文归口定义 X。
Y 若需要规则，应回到对应规范承接。
下游材料不得反向定义本文规则。
```

附件、Code、行动指南、测试、review、迁移材料和对话记录不得反向定义 specs 正文规则。若下游材料发现规则缺口，应回到对应 spec 正文吸收。

Code、review、迁移材料、测试输出、行动指南和对话记录不得输出或暗示 `approved`、`allowed`、`unblocked`、`accepted risk` 等授权语义。授权、放行和风险接受只能来自正文规则允许的 Human Gate 或明确的上位规范。

## 4. 适用范围

本文适用于：

1. `specs/` 中的正式规范正文；
2. 被正式规范正文授权的附件；
3. 正式规范的新增、迁移、修改、审核和解析；
4. Code 对 specs 的结构读取、诊断、索引和行动指南输入生成。

正式 spec 必须声明自身适用范围。适用范围用于回答：本文规则用在哪些对象、行动或文档上。

适用范围不负责声明关系索引、附件清单、目录、读取计划或 Code 覆盖状态。这些内容能由 Code 从 identity block、路径、显式引用和 Markdown 结构派生时，不应在正文中手写罗列。

## 5. Specs正文结构

### 5.1 固定头部

除 00 外，正式 spec 必须具备固定头部、主体规则区和固定尾部。

固定头部必须按以下顺序出现：

| 顺序 | 固定头部 | 职责 |
|---|---|---|
| 1 | 价值判断 | 说明本文为什么存在，是否服务 00 的价值门，减少 AI 哪类负担。 |
| 2 | 权威依据 | 说明本文依据哪些上位规范，冲突时回到哪里。 |
| 3 | 归口边界 | 说明本文有权定义什么，不能反向定义什么。 |
| 4 | 适用范围 | 说明本文规则适用于哪些对象、行动或文档。 |

固定头部是 AI 快速定位和 Code 稳定解析的入口。章节内部可以使用自然语言、表格、列表或专题小节自由展开。

### 5.2 主体规则区

主体规则区位于固定头部和固定尾部之间。单篇 spec 可以根据自身归口自定义主体规则区的章节标题、章节数量和组织方式，不要求所有正式 spec 使用同一个主体章节标题。

主体规则区是规则本体。主体规则区应写本篇 spec 相对上位规范新增、细化或例外的规则，不重复上位规范全文；标题应表达本篇 spec 的归口对象、机制、字段、边界或规则簇。

主体规则区不得承载过程输出、Code 派生目录、读取计划、关系图、一次性检查结果、review 结果、测试输出或迁移证据。主体规则区也不得绕过固定尾部中的保障措施、验证方法、Human Gate、Stop Conditions 和待补齐事项。

主体规则区存在多个规则簇、表格、附件边界、Code 派生边界或角色索引边界时，应使用专题小节区分。专题小节标题应表达规则职责，不得使用目录式、过程式或证据式标题。

### 5.3 实现域实践边界

Specs 正文只定义需求、规则、契约、边界、Human Gate、Stop Conditions 和验证要求。实现域实践细节由对应实现域承接，包括 `code/`、`code/docs/`、`web/`、`web/docs/`、`tests/`、`hooks/`、实现域文档和可执行测试。

实践细节包括具体实现语言、框架、模块拆分、内部目录组织、页面组件、API 路由、测试文件清单、fixtures 组织、性能实践、安装脚本和执行命令细节。上述内容可以被 specs 要求满足某个契约或边界，但不得在 specs 正文中作为实现方案锁死，也不得由实现域文档、代码、测试、review 或迁移材料反向改写 specs。

当实践经验暴露稳定规则缺口时，应先回到对应 spec 正文、附件契约或 Human Gate 承接；未承接前只能作为实现说明、诊断、测试样例或迁移证据存在。

### 5.4 固定尾部

固定尾部必须包含以下章节。固定尾部的标题应保持稳定；章节序号可以随主体规则区长度变化。

| 固定尾部 | 职责 |
|---|---|
| 保障措施 | 说明为了让规则被遵守，需要哪些机制。 |
| 验证方法 | 说明如何检查规则是否被满足。 |
| Human Gate | 说明哪些事项必须由 Human 确认、授权或接受风险。 |
| Stop Conditions | 说明 AI 必须暂停的触发条件。 |
| 待补齐事项 | 收束未闭合问题、后续规范和 Code 缺口。 |

固定尾部不得被主体规则区替代。需要扩展保障、验证、门禁或停止规则时，应进入对应固定尾部章节。

### 5.5 章节职责边界

信息角色职责由本文定义。下位规范可以自定义主体规则区标题，但不得通过主体规则区、保障措施、验证方法、附件或 Code 输出改变信息角色职责。

信息角色职责闭集：

| 信息角色 | 只负责 | 不负责 |
|---|---|---|
| 价值判断 | 说明本文为什么存在、服务哪些 00 价值、减少 AI 哪类负担。 | 不重写 00 价值门，不写具体规则细节。 |
| 权威依据 | 说明本文承接哪些上位规范、冲突时回到哪里。 | 不定义本文管什么，不处理具体规则内容。 |
| 归口边界 | 说明本文有权定义什么、相邻高风险归口在哪里。 | 不写无限排除清单，不替相邻规范定义规则。 |
| 适用范围 | 说明本文规则适用于哪些对象、行动或文档。 | 不手写目录、关系索引、读取计划或 Code 覆盖状态。 |
| 主体规则区 | 写本文新增、细化、例外的规则。 | 不重复上位规范全文，不承载过程输出、Code 派生目录、读取计划、关系图或一次性检查结果。 |
| 保障措施 | 说明为了让规则被遵守需要哪些机制。 | 不记录一次性执行结果，不写全量审计清单。 |
| 验证方法 | 说明如何检查规则是否被满足。 | 不声明当前已经通过，不把 Code 诊断升级为授权。 |
| Human Gate | 说明必须由 Human 确认、授权或接受风险的事项。 | 不写 AI 自行放行条件。 |
| Stop Conditions | 说明 AI 必须暂停的触发条件。 | 不替 Human 完成暂停后的确认。 |
| 待补齐事项 | 收束影响后续规范、Code、对象、验证或迁移的未闭合事项。 | 不写泛泛优化愿望，不隐藏新规则。 |

主体规则区不得替代固定头部或固定尾部。需要扩展保障、验证、门禁或停止规则时，应进入对应固定尾部章节，不得藏在主体规则区。

### 5.6 Specs 编号分层

specs 编号段表示规范归口和层级承接，不表示五类构成要素的排序，也不把编号本身升级为构成要素。

| 编号段 | 层级 | 性质 |
|---|---|---|
| 00 | 根锚点 | 最高价值锚点，不展开具体规则 |
| 01-03 | 横切基础规范 | 保障衔接、AI 行为、事实源，非构成要素 |
| 04 | 规范体系要素基础规范 | 承接规范体系构成要素，治理 specs 结构 |
| 05-08 | 其余四类构成要素基础规范 | 事实模型、行动模板、Code、Web |
| 09-10 | 跨要素治理规范 | 测试验证、安装配置，非构成要素 |
| 20-24 | 事实对象成员规范 | 承接 05 的事实对象具体成员 |
| 30+ | 行动模板实例 | 承接 06 的具体行动模板 |

04-08 对应 00 §5 定义的五类构成要素基础规范。规范体系要素由本文（04）承接：定义 specs 编号分层、正文结构、身份索引、附件授权、状态归口、Code 派生边界和修改审核，使 specs 结构稳定、可被 Code 消费，并支撑行动指南输入与 read_plan 派生。

编号分层只说明规范归口和承接层级，不改变 parent_spec、basis、related_specs 或正文显式引用所表达的规范关系。新增 spec 时必须按归口选择对应编号段；编号段已满、需要新增编号段或需要改变编号段含义时，必须修改本文并评估 Human Gate。

### 5.7 固定尾部跨篇一致性

固定尾部各章节必须遵守跨篇一致性，通用条件在上位定义一次，各篇只写本篇归口特定的部分。

**Human Gate**：
- 00 §8 是 Human Gate 的上位定义点，定义 Human Gate 上位边界和"AI 不得替代 Human 完成 Gate"声明；
- 01-10 的 Human Gate 只写改变本篇归口核心内容的 Gate，不重复"改变上位规则需 Gate""下位反向定义上位需 Gate"或"AI 不得替代 Human"声明。

**Stop Conditions**：
- 02 §9 是 Stop Conditions 的上位定义点，定义 AI 通用停止条件（如过程输出替代正文、必要保障缺失、Human Gate 触发未决、规则冲突无法确认权威）；
- 01/03-10 的 Stop Conditions 只写本篇归口特定的停止条件，不重复 02 §9 的通用条件。

**待补齐事项**：
- 待补齐事项只收纳当前仍未承接的体系缺口；
- 后续规范已承接的条目，必须更新为"已由 XX 承接"或删除；
- 只剩实现细节的条目不进入待补齐事项，移到实现域待办。

新增 spec 或修改固定尾部章节时，必须按本节检查跨篇一致性。

### 5.8 跨规范职责边界总览

跨规范职责边界总览用于帮助 AI 在修改、审计或生成行动指南前快速判断应回到哪篇正式 spec。它是路由表和防越界检查，不是第二规则源，不替代单篇 spec 的归口边界、主体规则、Human Gate、Stop Conditions 或附件授权。

当总览与单篇 spec 正文冲突时，以单篇 spec 正文、上位规范和 Human Gate 为准；当单篇 spec 边界不清时，必须回到对应正文补强，不得由 docs、Code、测试、review 收据或行动指南长期补位。

当前高风险交叉边界如下：

| Spec | 主职责 | 不应承担 |
|---|---|---|
| `00` | 定义 LDVH 存在理由、AI 第一服务对象、事实源边界、保障与衔接层、五类构成要素和 V1-V9。 | 具体流程、runtime 细节、环境插件细节、测试命令、字段 schema。 |
| `01` | 定义保障需求、消费时机、能力 / 能力缺口、环境入口上位语义、canonical event、receipt / evidence / diagnostic 和 repair lane。 | 具体 Code 模块、具体测试文件、插件 manifest、安装步骤、事实对象字段。 |
| `07` | 定义 Code 能力边界、结构化输出、diagnostic、Action Guide 输出、preflight 和 runtime facade 实现边界。 | 授权、Human Gate、事实源、Web 数据契约、安装验收、环境 integrated 声明。 |
| `09` | 定义验证方式分层、验证声明、失败阻断、测试证据边界和验证入口选择。 | 具体测试框架、每个测试文件职责、Code 输出 schema、行动步骤、事实对象字段。 |
| `10` | 定义管辖项目配置、target-first、scope_status、多目标 / no-op、install_plan 机器契约和环境策略。 | 环境 integrated 判定、插件要求全文、Human-facing 安装流程、事实对象字段。 |
| `30` | 组织安装、配置、验证、断点恢复和 Human-facing 交还的行动模板。 | 机器核心安装规则、target resolver、环境 integrated 判定、插件编写要求、Code 输出字段。 |
| `33` | 定义环境插件必须满足的要求，以及编写 / 更新插件或 adapter 的行动模板。 | 安装验收闭环、真实 integrated 声明、共享分类逻辑、target 归口逻辑、diagnostic 分流。 |

使用该总览时必须遵守：

1. 需要新增或改变规则语义时，先回到主职责所在 spec；若主职责不明，进入 Human Gate 或在本文补归口规则；
2. docs、Code、tests、环境插件、行动模板和 review 只能作为实现域、验证域或过程材料，不得反向扩大自身主职责；
3. 能力缺口、不可验证、环境差异、安装差异和测试未覆盖范围必须按 01、09、10、30 或 33 分流，不得被写成已经 integrated、已授权或已完成；
4. 该总览只覆盖当前高风险交叉边界；新增高风险 spec 或交叉职责时，应更新本文，并检查对应单篇 spec 的归口边界是否同步。

## 6. Specs身份与索引

### 6.1 `ldvh_spec` identity block

正式 spec 必须包含 `ldvh_spec` identity block。字段闭集见 `specs/attachments/04.Att.01-规范身份字段表.md`。

`ldvh_spec` 是 Code 读取规范身份、路径、权威承接、显式关系和消费入口的稳定结构。字段不得替代正文判断；字段内容与正文冲突时，必须回到正文和 Human Gate。

### 6.2 `role_sections` 过渡索引

`role_sections` 是信息角色到正文章节标题的索引投影，不是第二规则源，也不是事实源或绕过正文的例外机制。当前 active 主线仍保留人工声明 `role_sections`，作为 Code 尚未稳定推导前的过渡索引；人工声明不得与正文冲突，不得新增信息角色职责，不得覆盖正文标题。Code 能稳定推导后，`role_sections` 应由 Code 生成或诊断，不再作为人工必填规则字段。

`role_sections.rule_body` 可以是单个章节标题，也可以是多个章节标题列表，用于指向主体规则区。主体规则区的标题由单篇 spec 自定义，Code 不得因为主体标题不同而判定结构失败。

`role_sections`、identity block、canonical path、code_consumption、显式引用和附件 relation 产生的结构性诊断属于 specs 结构治理问题。若这些诊断发生在当前 primary spec / attachment 上，并导致 Hook 或 validator 在写入前自锁，AI 和 Code 应按 01 的 specs structural repair lane 分流：普通写入停止，`operation=repair` 只允许修复当前 primary 文件的结构映射或字段一致性，修复后用本文验证方法复跑结构检查。该通道不得用于重写规则语义、接受风险、跨 spec 批量迁移或替代 Human Gate。

### 6.3 `code_consumption`

`code_consumption` 只声明本文提供哪些可被 Code 消费的结构入口。它不得承诺 Code 已经实现，不得把 Code 输出升级为授权、放行、验收或事实源。

### 6.4 显式路径与引用

引用关系必须显式写在 identity block、正文路径或正文引用中。关系类型见 `specs/attachments/04.Att.03-引用关系类型表.md`。

## 7. 附件授权

### 7.1 `ldvh_attachment` identity block

附件必须包含 `ldvh_attachment` identity block。字段闭集见 `specs/attachments/04.Att.05-附件身份字段表.md`。

### 7.2 附件允许承载内容

附件只是正文授权的附属内容。允许进入附件的内容包括字段闭集、枚举、术语表、纯表、数据矩阵和正文明确授权的机器契约。

### 7.3 附件禁止承载内容

附件不得承载上位原则、核心规则、行动流程、Human Gate、大段解释、迁移过程、可由 Code 生成的目录、关系图、检查清单或读取路线。

### 7.4 附件与正文关系

附件不得反向定义正文规则。若附件发现字段、枚举、矩阵或机器契约无法表达正文要求，应回到正文修改或进入 Human Gate，不得在附件中扩写核心规则。

## 8. 状态归口原则

V3 中只有两类对象可以拥有可记录、可迁移、可校验的状态：

1. specs / attachments 自身的生命周期状态；
2. 事实源对象的业务状态。

Specs / attachments 自身的生命周期状态由 `specs/attachments/04.Att.01-规范身份字段表.md` 和 `specs/attachments/04.Att.05-附件身份字段表.md` 承接。事实源对象的业务状态必须由对应事实对象规范定义状态闭集，并落在 03 允许的 Git 可追踪事实源中。

除此之外，所有 `status`、`state`、`状态` 都只能作为当前运行、验证、审计、交互、交还或展示输出。运行时输出、Code 诊断、环境审计、安装检测、验收结果、状态卡片、状态列、Web 展示、测试结果和 CLI summary 不得作为长期事实，不得形成独立状态闭集，不得被 specs 当作事实状态消费。

Specs 可以定义判定分类、验证输出分类、诊断级别、检查结果、展示标签或交互阶段，但必须明确它们不是可记录状态。附件也不得绕过本文把分类表、检查表、交互表或输出字段写成第三类状态闭集。

下位规范发现需要长期记录的状态时，必须回到 facts 归口：要么由事实对象规范定义业务状态并进入事实源，要么保留为过程输出、验证证据或展示输出。不得因为某个输出字段名叫 `status`，就把它升级为事实状态。

## 9. Code派生边界

不得手写全量目录作为规范结构层。目录、关系图、读取计划、覆盖诊断和索引应由 Code 从 Markdown 文件、identity block 和显式引用生成。

正文只写需要规范作者判断的规则、边界、方法和门禁。Code 可以稳定派生的内容，不应作为固定头部、固定尾部或正文清单手写罗列。

| 内容 | 是否应固定成章节 | 处理方式 |
|---|---|---|
| 关系索引 | 否 | 由 Code 从 `parent_spec`、`basis`、`related_specs`、路径引用和 Markdown 结构生成。 |
| Code 覆盖 | 否 | 作为验证诊断、review 收据或待补齐事项处理，不成为独立规则章节。 |
| 规则来源 | 否 | 正式 spec 正文本身就是规则本体；附件、Code、review、迁移材料和对话记录不得反向改写正文。 |
| 附件清单 | 否 | 由 Code 从附件 identity block、`parent_spec`、`related_specs` 和正文引用生成。 |
| 目录 | 否 | 由 Code 从文件路径、标题和 Markdown 结构生成。 |
| 关系图 | 否 | 由 Code 从显式引用和 identity block 生成。 |
| 读取计划 | 否 | 由 Code 从固定头部、固定尾部、`role_sections`、上位依据和显式引用生成。 |
| 覆盖诊断 | 否 | 由 Code 或 review 输出，不进入正文冒充规则。 |

## 10. 规范修改与审核

### 10.1 修改顺序

修改正式 spec 时，应先判断价值门、权威依据、归口边界和适用范围，再修改主体规则区，最后同步保障措施、验证方法、Human Gate、Stop Conditions 和待补齐事项。

### 10.2 review 收据边界

review 收据只能证明某次审核或检查发生过，不能授权、放行、接受风险或改变正文规则。

### 10.3 Human Gate 触发

修改 00、01 或 02 的上位结构规则、附件边界、事实源边界、Human Gate 语义、Stop Conditions 或不可自动判断事项时，必须进入 Human Gate。

### 10.4 缺口回写

发现结构、附件、Code 派生、review、迁移或验证缺口时，必须回写到对应规范的待补齐事项、过程记录或后续承接位置，不得停留在聊天、一次性输出或临时检查结果中。

## 11. 保障措施

保障措施用于回答：为了让本文规则被遵守，需要哪些机制。

正式 spec 必须说明自身规则依赖哪些保障措施。保障措施可以包括：

1. 固定头部入口；
2. 主体规则区角色索引；
3. identity block 字段闭集；
4. 附件授权边界；
5. 显式路径和引用；
6. AI 修改顺序；
7. Code 结构诊断；
8. Human Gate；
9. review 收据证据；
10. 待补齐事项回写；
11. 状态归口诊断。

保障措施必须遵守 01 的保障与衔接边界。保障措施不记录某一次执行结果。一次性检查结果、测试输出、review 记录和迁移证据应留在对应过程材料中，不进入正文冒充规则。review 收据只能证明某次审核或检查发生过，不能授权、放行、接受风险或改变正文规则。

状态归口原则必须由 03、05、01 附件和 Code validator 同步承接。下位规范若定义分类、检查结果、诊断级别或交互阶段，必须能被检查出其不是第三类可记录状态。

若某个规则提出了新的保障需求，而当前没有机制支撑，正式 spec 必须按 01 判断 blocker、warning、follow-up 或 unverifiable，并写入对应承接位置；不得只写入待补齐事项后声称已经落地。

## 12. 验证方法

验证方法用于回答：如何检查本文规则是否被满足。

正式 spec 必须说明自身规则的验证方法。验证方法应区分：

| 验证主体 | 职责 |
|---|---|
| AI | 判断价值、权威、归口、适用范围、主体规则区和停止条件是否自洽。 |
| Code | 检查 identity block、固定头尾、角色索引、路径、显式引用、附件字段和可解析结构。 |
| Human | 通过 Human Gate 确认价值冲突、边界争议、风险接受和无法自动判断的问题。 |

验证方法只定义检查口径，不承诺当前已经通过。

Code 可检查项不应被手写成固定正文清单。Code 覆盖状态应由 Code 诊断、review 收据或待补齐事项承接。正文只定义哪些检查有意义、检查失败时如何处理。

当验证无法稳定完成时，AI 必须说明不可验证原因，并把缺口回写到待补齐事项或对应过程记录。

本文自身的最小自检口径：

| 检查对象 | 方法 |
|---|---|
| 固定头部 | 本文必须具备价值判断、权威依据、归口边界和适用范围，且顺序一致。 |
| 主体规则区 | 本文必须在固定头部和固定尾部之间提供主体规则区，并使用专题小节区分规则簇。 |
| 固定尾部 | 本文必须具备保障措施、验证方法、Human Gate、Stop Conditions 和待补齐事项。 |
| 信息角色职责 | 本文每个信息角色不得承载职责闭集之外的核心规则。 |
| specs structural repair | 当前 primary spec / attachment 的 `role_sections`、identity block、canonical path、code_consumption、显式引用或附件 relation 结构性诊断进入 repair 时，只验证该 primary 结构诊断是否被清除；无关全局诊断只能进入 residual risk，不得让 repair 永久自锁。 |
| 00 豁免 | 本文只能豁免 00，不能让其他正式规范逃离固定头尾和主体规则区要求。 |
| 编号分层 | 本文是否声明 specs 编号分层，新增 spec 是否按归口选择编号段。 |
| 固定尾部跨篇一致性 | 本文固定尾部是否只写本篇归口特定内容，Human Gate/Stop Conditions/待补齐事项是否未重复上位通用条件。 |
| 跨规范职责边界 | 本文总览是否只作为路由表和防越界检查，且不替代单篇 spec 正文、Human Gate 或附件授权。 |
| 状态归口原则 | 本文和下位规范是否只把 specs / attachments 生命周期状态和事实对象业务状态写成可记录状态，其它 status/state 是否仅作为过程输出、验证证据或展示输出。 |
| Code 派生边界 | 本文不得把目录、关系图、读取计划、覆盖诊断或索引作为手写事实层。 |
| 规范修改与审核 | 本文修改顺序、review 收据边界、Human Gate 触发和缺口回写是否自洽。 |
| 保障措施 | 本文提出的结构规则必须有对应保障措施或进入待补齐事项。 |
| 验证方法 | 本文提出的结构规则必须说明 AI、Code 或 Human 如何检查。 |
| Human Gate | 本文涉及上位价值、结构硬门或风险接受时必须交还 Human。 |
| Stop Conditions | 本文发现自身不满足固定头尾、主体规则区或职责闭集时，AI 必须先暂停修正本文。 |

## 13. Human Gate

Human Gate 用于回答：哪些事项必须由 Human 确认、授权或接受风险。

以下情况必须进入 Human Gate：

1. AI 无法判断价值冲突、归口冲突或适用范围冲突；
2. Code 诊断结果与正文判断冲突；
3. 需要接受不可验证、不可回滚或影响后续体系结构的风险。

Human Gate 的输出必须回指到正文规则、Human 明示决定或待补齐事项。review 收据、Code 诊断、测试结果和行动指南不能替代 Human 的授权、放行或风险接受。

## 14. Stop Conditions

Stop Conditions 用于回答：AI 什么时候必须暂停，不能继续按惯性修改。

出现以下情况时，AI 必须暂停并报告：

1. 发现固定头部或固定尾部缺失、改名，或主体规则区替代固定尾部；
2. 发现 Code 可派生内容被正文手写罗列，并产生维护分叉风险；
3. 发现新增规则没有对应保障措施、承接机制或验证方法；
4. 发现运行、验证、审计、交互或展示输出被下位规范写成第三类可记录状态。

暂停后，AI 应说明触发条件、涉及文件、可选处理方案和建议归口，不得直接越过停止条件继续修改。

Stop Conditions 触发后，AI 不得自行恢复推进，除非本文或上位规范已经定义了非 Human 的分流路径。每次暂停至少应说明：

1. 触发条件；
2. 停止范围；
3. 是否进入 Human Gate；
4. 需要交还的证据；
5. 后续承接位置。

## 15. 待补齐事项

待补齐事项用于承接未闭合问题，避免缺口留在对话、临时 review 或迁移过程里消失。

待补齐事项必须是影响后续规范、Code、对象、验证或迁移的体系缺口；不得写成当前任务清单、泛泛优化愿望或隐藏的新规则。

当前体系缺口：

1. 将现有正式 specs 按本文固定头部、主体规则区和固定尾部重排；
2. 调整附件字段表，使其服务信息角色和 Code 索引，不替代正文规则；
3. 实现 Code 对 `ldvh_spec`、`ldvh_attachment`、固定头尾、主体规则区、附件边界和显式引用的检查；
4. 明确 review 收据与保障措施之间的关系。
