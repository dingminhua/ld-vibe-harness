# 规范落地与环境适配基础规范

> 创建日期：2026-06-08
> 定位：定义 LDVH v2 中正式规范如何从权威文本转化为规范落地要求、保障机制、环境适配映射和运行投影
> 适用范围：LDVH `specs-v2/` 正式规范、规范落地要求声明、环境适配、运行投影、环境能力承接边界和特别说明或豁免管理
> 上位依据：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs-v2/02-术语规范.md`、`specs-v2/03-文档基础规范.md`、`specs-v2/03.01-规范文档规范.md`、`specs-v2/04.01-规范落地要求规范.md`、`specs-v2/04.02-环境适配与运行投影规范.md`、`specs-v2/04.03-环境适配映射与运行投影记录模板.md`、`specs-v2/04.04-环境能力承接边界.md`、`specs-v2/04.05-特别说明与豁免.md`、`specs-v2/14-Code实现规范.md`

## 1. 本文解决的问题

本文解决 LDVH v2 正式规范如何进入运行环境的问题。

正式规范不能只停留在正文中，也不能直接跳到某个环境的 Rules、Skill、Agent、Hook、命令、CI 或 Web 页面。规范应先说明自己要落地需要满足哪些要求，再说明由什么保障机制执行，之后才进入具体环境适配和运行投影。

本文是 04 系列的父规范，只定义分层链路、子文档边界和适用顺序。各层细则由 04.01 至 04.05 承接。当前项目的具体环境适配结果不进入 specs-v2 编号体系，应作为环境初始化记录进入项目根目录的 `LDVH-ENVIRONMENT-INITIALIZATION.md`。

本文使用的规范落地要求、保障机制、环境适配映射、运行投影、环境能力、环境实体、漂移、产品初始化和环境初始化等术语，按 `specs-v2/02-术语规范.md` 定义。本文只规定这些术语在 04 系列中的应用关系和执行边界。

---
## 2. 与 00 总纲的关系

00 定义开发环境、工作模型、工作流程、Code 和 Web 是 LDVH 的五类构成要素，并要求 LDVH 形成可规划、可执行、可验证、可沉淀、可演进的 AI 工程闭环。

本文承接 00 的上位原则，把正式规范进入运行环境的链路拆成以下层次：

```text
正式规范
→ 规范落地要求
→ 保障机制
→ 环境适配映射
→ 运行投影
→ 漂移检查与事实源回写
```

其中，正式规范是权威文本；规范落地要求、保障机制、环境适配映射和运行投影的术语定义按 `specs-v2/02-术语规范.md` 执行。本文在此说明它们在规范进入运行环境时的先后关系。

运行投影不是最终事实源。运行投影、环境工具输出、Skill 输出、Agent 输出、Web 状态或缓存与 specs-v2 正式规范冲突时，以 specs-v2 正式规范为准。

## 3. 分层规则

### 3.1 正式规范

正式规范位于 `specs-v2/` 正文区，定义 LDVH v2 的稳定规则、对象边界、流程要求、Code 要求、Web 要求、环境适配要求或检查要求。

只有 `specs-v2/` 下的正式规范文档默认需要声明“规范落地要求”段落。目录说明、索引说明、evals、refs、README、项目资料文档和其他非正式规范文档，不默认需要声明规范落地要求；若其中内容被升级为稳定规则，应先吸收到正式规范，再由正式规范声明规范落地要求。

### 3.2 规范落地要求

规范落地要求用于回答：这条规范要落地，需要被看见、复用、独立思考、确定性执行、Human 交互、生命周期触发或被后续规范承接吗。

规范落地要求不是环境实体，不得直接写成 Rules、Instructions、Skill、Agent、Hook、CI、命令、工具文件、Web 页面或平台配置。

### 3.3 保障机制

保障机制用于回答：某项规范落地要求由什么规则、检查、流程、Code、Human Gate、子 Agent 思考、生命周期触发或审计动作保障执行。

规范落地要求必须绑定保障机制。没有保障机制的落地声明，只是愿望，不构成完整落地声明。

### 3.4 环境适配映射

环境适配映射用于回答：某项规范落地要求和保障机制，在 Codex、Trae、Claude Code、Cursor、CI、Web、命令行或其他环境中如何实现、如何验证、如何降级。

环境适配映射以规范落地要求为输入，不得因为某个环境已有或缺少某项能力而反向改变正式规范本身。

### 3.5 运行投影

运行投影是环境适配映射后实际存在或被调用的入口、文件、配置、命令、Skill、Agent、Hook、CI 检查、Web 页面、摘要或降级记录。

运行投影必须能追溯到正式规范、规范落地要求和环境适配映射。运行投影不得承载未被正式规范吸收的 evals、refs 或临时判断。

## 4. 04 系列子文档边界

04 系列使用子文档，是因为规范落地、环境适配、记录模板、环境能力边界和特别说明分别回答不同问题。子文档不得复制父规范通用链路，也不得重新定义 00 的五类构成要素。

| 文档 | 回答的问题 | 边界 |
|---|---|---|
| `specs-v2/04.01-规范落地要求规范.md` | 正式规范如何声明规范落地要求和保障机制 | 不维护具体环境实体 |
| `specs-v2/04.02-环境适配与运行投影规范.md` | 规范落地要求如何映射到具体环境并形成运行投影 | 不重新定义平台能力，不反向改写正式规范 |
| `specs-v2/04.03-环境适配映射与运行投影记录模板.md` | 环境适配映射、运行投影和当前环境初始化记录如何登记、验证和降级 | 不维护具体环境能力清单，不替代产品初始化流程 |
| `specs-v2/04.04-环境能力承接边界.md` | Rules / Instructions、Skill、Agent、Hook、Code、Web 等能力各自适合承接什么 | 不替代各环境官方文档，不维护平台能力清单 |
| `specs-v2/04.05-特别说明与豁免.md` | 哪些特别说明或豁免需要单独登记、如何启用和限制 | 不作为绕开正式规范、Human Gate 或事实源边界的口袋 |

04.03 至 04.05 文件名不包含“规范”，是因为它们主要维护模板、边界和登记事项；但只要位于 `specs-v2/` 正文区并定义稳定规则，就仍属于正式规范文档，必须声明规范落地要求。当前环境初始化记录不属于 specs-v2 正式规范，不要求声明规范落地要求。

## 5. 使用顺序

AI 创建、修改或审计 specs-v2 正式规范时，应按以下顺序处理：

1. 先读取 `specs-v2/00-LD-Vibe-Harness理念与纲要.md` 中与本次变更相关的上位原则；
2. 按 `specs-v2/03-文档基础规范.md` 和 `specs-v2/03.01-规范文档规范.md` 判断文档工作区、正式规范身份、引用方向和文档骨架；
3. 按 `specs-v2/04.01-规范落地要求规范.md` 判断目标规范是否需要声明或更新规范落地要求；
4. 若某项落地要求需要进入运行环境，按 `specs-v2/04.02-环境适配与运行投影规范.md` 判断环境适配映射和运行投影；
5. 若需要登记环境适配映射、运行投影、验证方式或降级方式，按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 处理；
6. 若需要选择 Rules / Instructions、Skill、Agent、Hook、Code、Web 或其他能力承接，按 `specs-v2/04.04-环境能力承接边界.md` 判断能力边界；
7. 若涉及不适合放入通用规范正文、但需要单独登记的特别说明或豁免，按 `specs-v2/04.05-特别说明与豁免.md` 处理；
8. 若当前项目缺少环境初始化记录，或根目录 `LDVH-ENVIRONMENT-INITIALIZATION.md` 尚未适配当前项目和当前开发平台，应先按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 创建、确认或更新该文件，并持续提醒用户完成适配；在完成前不得创建、修改或删除持久运行投影；
9. 若发现需要确定性工具、校验、解析、受控写入、测试或上下文压缩，按 `specs-v2/14-Code实现规范.md` 形成 Code 需求、实现最小能力并验证。

## 6. 不得省略的边界

正式规范进入运行时不得省略以下边界：

1. **要求先于环境**：先判断 LDVH 需要什么规范落地要求，再判断某个环境如何适配；
2. **规范不替代平台文档**：平台能力、参数契约和客观限制以官方文档、当前环境配置或 refs 为准；
3. **适配不绑定**：Codex、Trae、Claude Code、Cursor 或其他环境都只是适配对象，不成为 LDVH 唯一底座；
4. **投影不是事实源**：运行投影只能承载入口、摘要、触发、流程或降级记录，不能替代 specs-v2 正式规范；
5. **缺口要回到正确层级**：规范缺口回规范，环境缺口回环境适配映射，Code 缺口回 Code 需求，特殊例外回特别说明与豁免；
6. **稳定事实必须回写**：Agent、Skill、工具、Web、CI 或 Hook 输出中的稳定结论，必须写入 Git 文件事实源后才生效。

## 7. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续正式规范涉及规范落地、环境适配、运行投影、环境能力或特别说明时，应遵守本文定义的分层链路和子文档边界 | `specs-v2/03.01-规范文档规范.md` 正式规范骨架、04 系列子文档引用、总纲一致性检查 | 文档治理 | 新增、修改或审计 specs-v2 正式规范时 |
| 入口可见要求 | AI 进行规范文档修改或环境适配时应能定位本文作为 04 系列父规范入口 | 规范文档入口摘要、相关规范引用、环境适配映射入口 | AI 执行入口提示 | 本文定位、04 系列子文档边界或使用顺序变化时 |
| 确定性执行要求 | 文档检查 Code 应能检查 04 系列正式规范是否具备规范落地要求段落和必填字段 | `tools/specs_validate.py` 或后续文档校验 Code、正反样例验证 | 校验实现 | 04 系列新增、重命名、删除或规范落地要求字段变化时 |
| 生命周期触发要求 | 正式规范变更后应检查是否影响规范落地要求、环境适配映射、运行投影、环境能力边界或特别说明 | `specs-v2/03.01-规范文档规范.md` 修改执行顺序、04 系列子文档、人工降级检查 | 触发保障 | 正式规范新增、重命名、删除、规范落地要求变化或环境迁移时 |

## 8. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变规范落地要求、保障机制、环境适配映射和运行投影之间的分层关系；
2. 新增、删除、重命名或改变 04 系列子文档职责；
3. 允许正式规范直接把环境实体写成规范落地要求；
4. 允许运行投影替代 specs-v2 正式规范；
5. 将某个具体环境能力提升为 LDVH 全局唯一底座；
6. 新增或扩大特别说明、豁免规则，并可能削弱 Human Gate、事实源边界或 Code 验证纪律。

04 系列检查至少包括：

| 检查项 | 标准 |
|---|---|
| 分层链路 | 正式规范、规范落地要求、保障机制、环境适配映射和运行投影未混淆 |
| 子文档边界 | 04.01 至 04.05 各自回答不同问题，未互相复制正文 |
| 环境边界 | 平台能力由官方文档、refs 或当前配置核验，正式规范未重写平台手册 |
| 事实源边界 | 运行投影、工具输出、Skill 输出、Agent 输出和 Web 状态未成为最终事实源 |
| Code 适配 | 需要确定性执行时已按 `specs-v2/14-Code实现规范.md` 判断 Code 需求并验证 |
| 特别说明 | 特别说明或豁免已声明适用范围、默认效力、承接位置和退出条件 |
