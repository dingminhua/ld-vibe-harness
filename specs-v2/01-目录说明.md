> 适用范围：LDVH 自身项目、安装 LDVH 的管辖项目，以及 AI 在上述项目中判断文件归属、编号占用和目录事实源性质的场景

## 1. 本文解决的问题

本文解决 LDVH v2 中内容应放在哪个目录、不同项目中的文档工作区如何映射、根目录初始化产物如何识别、specs-v2 编号如何分区，以及目录说明与文档规范、索引文档、环境适配和 Code 实现之间如何分工的问题。

本文只规定目录与编号边界，不直接定义文档写作细则、事实源权威性原则、工作模型字段契约、工作流程行动规则或 Code 实现细则。文档工作区规则由 `specs-v2/03-文档基础规范.md` 承接；规范落地与环境适配由 `specs-v2/04-规范落地与环境适配基础规范.md` 承接；Code 实现边界由 `specs-v2/07-Code实现规范.md` 承接。

## 2. 与 00 总纲的关系

00 定义 LDVH 由开发环境、工作模型、工作流程、Code 和 Web 五类构成要素共同形成 AI 工程驾驭体系，并要求稳定事实回到 Git 可追踪文件。

本文承接 00 的事实源和构成要素分工，把这些内容落实到项目目录和编号分区上，使 AI 能快速判断：

1. 哪个目录承载 LDVH 规范；
2. 哪个目录承载管辖项目文档；
3. 哪个目录承载结构化事实实例；
4. 哪个目录承载 Code、Web 和测试实现；
5. 哪些根目录文件属于项目入口或初始化结果物；
6. 哪些编号区段属于基础规范、工作模型、工作流程或其他构成要素。

## 3. 项目类型与工作区映射

LDVH 需要区分两类项目：

| 项目类型 | 定位 | 规范工作区 | 文档工作区 | 说明 |
|---|---|---|---|---|
| LDVH 自身项目 | 承载和维护 LDVH 规范体系、Code、Web 和 dogfood 事实实例 | `specs-v2/` | 根 README.md、必要的 `docs/` 或项目资料 | 当前 v2 基线只以 `specs-v2/` 作为规范事实源 |
| 管辖项目 | 安装并使用 LDVH 进行工程治理的用户项目 | 不默认创建 `specs-v2/` 或 `specs/` | `docs/` | 用户项目通过 `docs/` 承载项目文档、内部分析和外部引用 |

旧 `specs/` 在 v2 重建期间只作为迁移素材库。旧 `specs/` 中尚未迁入 `specs-v2/` 的内容，不自动构成 v2 权威规范。

首次阅读或安装 LDVH 时，AI 应根据目标选择最小入口：

1. 理解 LDVH v2 基线：先读 `specs-v2/00-LD-Vibe-Harness理念与纲要.md`，再读本文和 `specs-v2/02-术语规范.md`；
2. 判断目录、编号或内容归属：先读本文，再按内容进入 03、04、05-12 或待迁移的后续基础规范；
3. 完成当前环境初始化准备：先检查根目录 LDVH-ENVIRONMENT-INITIALIZATION.md，再按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 创建、确认或更新记录，并按 `specs-v2/04.02-环境适配与运行投影规范.md`、`specs-v2/04.04-环境能力承接边界.md` 判断环境能力和降级方式；
4. 创建、修改或审计 specs-v2 正式规范：先读 `specs-v2/03-文档基础规范.md`、`specs-v2/03.01-规范文档规范.md`，再读 `specs-v2/04.01-规范落地要求规范.md` 和必要的 04 系列、07-12 规范。

管辖项目安装 LDVH 后，应优先检查根目录 LDVH-ENVIRONMENT-INITIALIZATION.md 是否存在并已适配当前项目、当前开发平台、权限边界和 Human 授权状态。该文件不存在或未适配时，按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 处理，不得继续创建持久运行投影。

## 4. 目录与根文件规划

LDVH v2 当前识别以下目录和根文件：

| 路径 | 定位 | 主要内容 | 边界 |
|---|---|---|---|
| `specs-v2/` | LDVH v2 规范文档工作区 | 正式规范正文区、`evals/`、`refs/` | 只属于 LDVH 自身项目；用户管辖项目不默认创建 |
| `specs-v2/evals/` | LDVH v2 内部评估区 | 方案分析、迁移评估、内部调研 | 不直接构成正式规范；结论需吸收到正文区或工作对象 |
| `specs-v2/refs/` | LDVH v2 外部引用区 | 外部资料引用、副本或摘要 | 不直接构成正式规范；不得反向维护正文区规则 |
| `docs/` | 管辖项目文档工作区 | 项目正文文档、内部分析、外部引用、说明和报告 | 用户项目使用；LDVH 自身项目仅按需要创建 |
| `docs/evals/` | 管辖项目内部分析区 | 方案比较、项目复盘、内部调研 | 结论需吸收到 docs 正文、工作对象或决策后生效 |
| `docs/refs/` | 管辖项目外部引用区 | 外部资料、第三方文档、引用材料 | 不直接构成项目稳定结论 |
| `ldvh-base/` | 结构化事实实例目录 | Task、ADR、Change、Pitfall、Intent、Memo、Profile 等实例 | 事实实例目录；具体实例规则由工作模型规范定义 |
| `tools/` | Code 实现目录 | 校验器、脚本、上下文生成、受控写入和其他确定性实现 | Code 输出不是最终事实源 |
| `tests/` | 自动化测试目录 | Code、Web 和其他实现的测试与夹具 | 测试结果不替代 Git 文件事实 |
| `web/` | Web 实现目录 | Human-facing 页面、后端、API、交互与呈现实现 | Web 状态不替代 Git 文件事实源 |
| LDVH-ENVIRONMENT-INITIALIZATION.md | 根目录环境初始化记录 | 当前项目环境适配、运行投影、能力核验和降级方式 | 不是规范文档；结构由 04.03 模板约束 |
| README.md | 项目入口说明 | 项目简介、安装、使用入口和导航 | 项目文档入口；具体规范不在 README 中定义 |

目录名称和内容归属本身不自动决定最终事实源权威性。最终事实源边界由 `specs-v2/09-事实源边界与承载规范.md` 定义；所有稳定事实仍应遵守 00 和 09 中 Git 可追踪文件和单一事实源原则。

## 6. 索引文档与编号区段

20 和 40 是规范型集合索引，应按 `specs-v2/03.03-索引文档规范.md` 编写和维护。当前 20 工作模型集合索引已迁入 v2；40 工作流程集合索引尚未迁入。AI 处理工作模型集合时，应读取 `specs-v2/20-工作模型集合索引.md`；处理工作流程集合时，应先确认 40 是否已经迁入。

集合索引只维护清单、状态、编号范围、关系、初始化输入和审计输入，不定义具体对象字段、状态机、工作流程 Context、Scenario、Gate 或行动流程。

工作模型和工作流程的分工如下：

| 区段 | 基础规范 | 集合索引 | 具体规范 |
|---|---|---|---|
| 工作模型 | 05 工作模型基础规范 | 20 工作模型集合索引 | 21-39 具体工作模型规范 |
| 工作流程 | 06 工作流程基础规范 | 40 工作流程集合索引 | 41-59 具体工作流程规范 |

新增或修改 20、40、21-39、41-59 文档时，应同步检查 01 的编号分区、03.03 的索引规则、对应基础规范和对应集合索引。若对应文件尚未迁入，只能记录为待迁移事项或迁移计划，不能引用不存在的索引作为事实源入口。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除或重命名本文定义的一级目录；
2. 改变 `specs-v2/`、`docs/`、`ldvh-base/`、`tools/`、`web/` 或 `tests/` 的定位；
3. 将用户管辖项目改为默认创建 `specs-v2/` 或 `specs/`；
4. 改变 LDVH-ENVIRONMENT-INITIALIZATION.md 的根目录定位；
5. 改变 specs-v2 编号分区；
6. 将 20 或 40 改为基础规范编号；
7. 将索引文档扩张为具体工作模型或工作流程规则；
8. 将旧 `specs/` 中尚未迁入的内容直接视为 v2 权威规范。

目录和编号检查至少包括：

| 检查项 | 标准 |
|---|---|
| 工作区映射 | LDVH 自身使用 `specs-v2/`；用户管辖项目使用 `docs/` |
| 根目录初始化记录 | LDVH-ENVIRONMENT-INITIALIZATION.md 位于根目录，缺失或未适配时按 04.03 处理 |
| 编号分区 | 文档编号符合本文 §5 |
| 索引边界 | 20/40 是集合索引，05/06 是基础规范 |
| 内容归属 | 内容进入权威归属文档，不重复多处维护 |
| 旧规范迁移 | 旧 `specs/` 只作为迁移素材，不直接成为 v2 依据 |
| Code 适配 | 可机械检查内容已评估是否需要 Code 支撑 |
