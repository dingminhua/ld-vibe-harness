## 1. 目的与边界

本矩阵从 V3 资产实际承担的责任、实现和验证状态出发，判断其在 V4 中应当保留、重写、拆分、合并、迁移、延后或删除。

本矩阵不按 V3 编号推导 V4 编号，也不把旧文件作为 V4 成员预设。候选职责名称只用于检查职责划分是否完整，不代表已经决定建立同名规范。

本矩阵保留“规范体系”一词描述 V3 原有资产和历史设计；描述 V4 目标架构时使用当前 00 已定义的“规范模型（Specification Model）”。规范模型约束正式规范资产并组织规则源，但不单独形成第二规则源。Helper CLI 继续是基础服务形式；Helper 只表示架构层统一跨要素服务入口，本矩阵不引入独立“Helper 服务体系”或把 CLI 降为访问形式。

事实实例按对象类型全量计数并按类型处置；92 个实例继续完整保存在归档中，不逐个继承其状态。只有在 V4 事实模型确定后，才有必要逐实例判断其中哪些内容值得吸收为新的 V4 事实。

## 3. 处置术语

| 处置 | 含义 |
| --- | --- |
| 保留 | 00 的上位语义或问题仍成立，可以成为 V4 设计依据；仍需用 V4 资产重新表达 |
| 重写 | 问题仍成立，但 V3 的结构、字段或规则负担不适合直接沿用 |
| 拆分 | 一个 V3 资产承担多个独立职责，需要分别确定承担位置 |
| 合并 | 多个 V3 资产重复表达同一责任，应形成一个来源或机器契约 |
| 移入 Code/Schema | 属于确定性实现或数据契约，不应由叙述性规范承载全部细节 |
| 移入行动模板 | 属于重复行动的执行结构，不应成为所有任务的通用规则 |
| 移入事实模型 | 属于需跨会话保存的稳定状态、证据或经验 |
| 降为记录 | 只描述阶段调查、迁移或维护过程，不应成为长期规则 |
| 延后 | 问题可能存在，但建设顺序中在先的规范或契约尚未稳定，当前不设计 |
| 删除 | V4 不再保留该机制；历史仍保留在归档中 |

## 4. 临时分析代号

以下大写英文代号只用于压缩本矩阵中的重复文字，不是正式架构概念、术语、`spec_key` 或 V4 规范成员。正式设计不得引用这些代号代替已确认的中英文术语。

| `SPEC_MODEL` | 正式规范资产的类型、身份、结构、关系、规则表达和机器消费；组织规则源但不形成第二规则源 |

| `FACT_MODEL` | 事实对象准入、字段、状态、证据、关系和实例边界 |

## 11. 从矩阵暴露出的系统性问题

### 11.1 Helper CLI 的上位定位与实际入口不一致

V3 虽已把 Helper CLI 定义为基础服务形式，并把 Helper 定义为架构层统一跨要素入口，但实际能力分散在 Action Guide、多个 CLI facade、Hook 和 runtime adapter 中，没有形成稳定统一的 Helper CLI 服务契约。V4 必须保留 00 的这一定位，先定义 Helper CLI 对 AI 提供什么，再决定 Code 模块和环境入口；不得未经 00 层面的决定引入独立 Helper 服务实体或把 CLI 降为普通访问形式。

### 11.2 来源责任与执行机制纠缠

规则效力、AI 行为、事实源、验证声明、Hook、安装和 runtime payload 在多个规范之间相互重复。V4 需要让权威方向保持单向：规范模型约束正式规范资产，取得正式效力的 Specs 正文及授权附件构成规则源；来源规范定义语义，Schema 表达机器契约，Code 实现确定能力，Helper 组织服务，环境 adapter 只负责协议衔接。模型、索引、Helper 输出和 Code 派生结果都不得形成第二规则源。

### 11.3 固定读取和全局门禁负担过高

固定读取 00/01/02、read-plan acknowledgment、pre-tool-use cache 和完成门禁形成一整套环境相关机制。它试图解决 AI 未读规则的问题，但成本高且限制普通求解。V4 应通过 Helper 的任务相关规则解析解决定位和消费问题，不预设所有环境都支持同一生命周期。

### 11.4 正文、机器契约和实现硬编码

V3 的 YAML 有机器价值，但 Code 和 tests 同时依赖编号、路径、章节和正文措辞。V4 应保留明确机器身份，减少重复字段，并让 Schema/Code 消费稳定语义而非具体文案。

### 11.5 事实状态与过程编排混合

WorkCase orchestration、runtime receipt、诊断和环境事件中有大量短期状态。V4 需要坚持只有跨会话稳定、需要追溯和复用的内容才进入事实源；临时状态默认属于 Helper session 或其它当次运行信息。

### 11.6 设计状态超过真实接入状态

V3 对环境 Hook、安装和保障定义广泛，但实际接入只是部分成立。V4 必须从一开始区分设计、实现、接入、验证和可用状态，并让 Helper 如实返回缺口。

### 11.7 Code 缺少先行系统规划

V3 `code/ldvh_specs.py` 达到 7,817 行，包含 181 个顶层函数或类（计入嵌套定义共 184 个），同时承担规范、事实、项目、Action Guide、runtime、commit gate 和演练等职责；对应的 `tests/code/test_ldvh_specs_validate.py` 也达到 7,310 行。这不只是单文件行数问题，而是系统分解、模块职责、模块引用与调用方向和持续重构机制没有先于能力累加成立的风险信号。V4 应先为 Code 构成要素完成系统规划，并核验、选择适用的外部工程实践要求，再开始 Code 和 tests 实现。具体规则不应只依赖统一行数上限，而应结合职责、复杂度、模块关系、测试性和可导航性定义可执行边界。

## 12. 当前候选结论

1. V3 00 的上位语义构成 V4 00 的基线；V4 已经 Human 明确决定，以规范模型替代规范体系作为构成要素，同时保留 Helper CLI、事实源、V1–V8、Web、验证和 Gate/Stop 的既有边界。
2. V3 01 不应成为 V4 01 的母版；它应被拆分为规则效力、Helper CLI 服务契约、验证声明和环境集成等责任。
3. V3 04 中“机器可消费的正式规范资产”问题仍成立；V4 01 已经 Human 确认，并在提交 `065ce954` 中以规范模型基础规范承担这一职责，未继承迁移、双读、旧路径和大量反向关系。
4. V4 已在其余规范成员编号前完成候选职责划分与完整性检查；本矩阵临时记作 `RULE_EFFECT`、`HELPER_CLI`、`VERIFY_CLAIM` 和 `CODE_SYSTEM` 的职责保持独立，不再设置独立的 AI 规则履行或 AI 行为规范职责。
5. V4 Code 和 tests 必须从零建立；V3 模块和测试只提供场景，不提供兼容契约。在 Code 构成要素的系统规划、经核验选定的外部工程实践要求和正式承载边界得到确认前，暂不启动新实现。
6. V3 事实实例不自动成为 V4 当前事实；是否吸收必须等 V4 事实模型确定后逐项裁决。
7. Web 和 icons 继续冻结，不参与当前责任重建。
