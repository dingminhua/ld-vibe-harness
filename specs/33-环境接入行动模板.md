## 1. 价值判断

本文的价值，是把环境接入中反复出现且容易漏失的四项工作——环境接入、管辖配置、Git Hook 部署与验证——组织成一条稳定行动结构，并串联目标与现状确认、用户资产保护、副作用授权、写后回读、真实事件验证、断点恢复、失败回滚和如实交还。

没有本模板时，AI 容易把源码或 Skill 文件存在写成环境接入完成，把未配置或未解析的项目写成已受管辖，把手工直调写成真实递达或触发，或者漏装承接最终 Git Gate 的 Git Hook。模板通过精确回指 02、09 和具体环境来源减少这些遗漏，不复制管辖字段、厂商事件、命令、路径、UI 或步骤数量。

只询问接入概念、只诊断 Helper CLI 或 Git Gate 核心、编写新的薄 Skill 文本、修改厂商机制配置，或者当前事项不产生环境部署副作用时，继续使用相应来源和普通求解，不因本模板存在而强制进入部署流程。

## 2. 规范依据

本文直接依据：

1. `action-template-foundation`：规定具体模板的准入、适用、授权、共同结构、验证、回写和交还边界；
2. `environment-integration`：唯一规定源码仓库能力本体、唯一 AI 接入单元薄 Skill、SKILL.md 内容合同、必部署的 Git Hook、其承接的 Git Gate、common-dir 覆盖边界、生命周期、静态观察、真实递达与触发、环境证据和回滚成立条件。
3. `work-object-governance-scope`：唯一规定管辖配置的位置、字段、发现、有效性、工作对象与管辖解析结果。

03 的信息作用与来源回指、04 的 Helper 服务契约、07 的 Code/tests 要求、Human 当前指令、具体环境当前资料及实际部署能力按当次目标提供输入。本文只组织消费，不复制其字段、协议、算法或成立条件。

## 3. 职责边界

本文负责定义：

1. 一次环境接入、管辖配置、Git Hook 部署与验证行动的适用与排除边界，以及检查、升级、修复、禁用、卸载或回滚分支；
2. 目标环境、工作对象、源码仓库、管辖配置、用户资产、Helper CLI、Git common-dir、Git Hook、Git Gate、薄 Skill 部署件、授权和验证入口之间的稳定行动关系；
3. 只读发现、方案形成、写入授权、执行、静态回读、实际适用入口直调、真实环境触发和回滚的步骤依赖；
4. 需要 Human 操作目标环境时的断点恢复和最小观察交还；
5. 成功、部分完成、失败、不可验证、回滚和残留的分流及最终交还。

本文不负责定义：

1. 环境接入成立条件、管辖项目配置、Helper 字段、厂商事件、manifest、payload、权限或部署接口；
2. 薄 Skill 文本内容（由 09 §5.2 内容合同定义）或 Git Gate 检查实现的设计、编写、重构、发布或平台兼容策略；
3. 具体命令、文件路径、UI 操作、部署能力参数、日志格式或测试实现；
4. 自动发现工作区、自动登记项目、初始化事实源或修改事实对象；
5. Human 是否已经授权部署、平台信任、重启、覆盖、卸载或风险接受；
6. 环境接入运行状态、永久 receipt、事实对象或另一套环境状态机；
7. Git commit、push、发布、marketplace 提交或其它后续行动。

具体环境来源定义“如何连接”；02 定义“如何配置并判定管辖”；09 定义“什么条件下完整接入声明成立”；本文只定义“如何组织这四项工作”。

## 4. 适用范围

当 Human 目标涉及以下一项，并且已经能够识别具体目标环境与候选接入单元时，本模板进入候选：

1. 首次部署或启用 LDVH 环境接入；
2. 配置或核验目标项目的管辖配置与当次管辖解析；
3. 检查既有接入是否仍能连接当前源码仓库、薄 Skill、管辖配置、承接 Git Gate 的 Git Hook 与 Git Gate 核心；
4. 升级、修复或迁移环境接入、管辖配置或 Git Hook 部署；
5. 禁用、卸载或回滚环境接入或 Git Hook 部署；
6. 继续一次因重启、新窗口、新任务、信任或 Human UI 操作而中断的验证。

目标环境的技能机制或原生 Git `commit-msg` 接入不成立、部署接口不清楚、只诊断 Helper CLI 或 Git Gate 核心、不涉及环境部署，或没有写入/部署授权时，不执行部署分支。可以继续只读调查、形成方案或准备 Human Gate。目标环境没有技能机制时，按 09 §5.1 不得改投环境 Hook、插件或 adapter；不能部署承接 Git Gate 的 Git Hook 时，也不得把 Skill 单独部署写成完整接入。需要新增环境侧脚本或配置对象时，按 09 §8 如实交还能力缺口；本模板不得在部署步骤中顺带设计或生成并行接入层。

### 5.1 输入与前置条件

执行者必须取得并区分：Human 当前目标与副作用授权；目标环境名称、版本和实际运行位置；技能部署位置及其可触发会话范围；目标环境当前官方或实际权威资料及观察时间；能够把 SKILL.md 文本递达给 AI 的技能机制、必需输入与反馈能力；LDVH 源码仓库绝对路径、Git identity/revision、工作区根、实际工作对象和 02 管辖解析输入；09.Att.01 中源码 Helper launcher、Git Hook 管理入口、Git Gate 核心入口与源码模式 doctor 的当前交付状态；canonical SKILL.md 当前来源与部署对象；目标 actual worktree、由它解析并验证的 common-dir、共享该 common-dir 的主/linked worktree；现有 Skill 部署件、Git Hook、配置、权限、信任和用户资产；计划使用的部署/卸载能力；静态、直接调用、真实递达与逐事件触发和回滚验证入口。

除非 Human 明确指定不同的目标环境或工作区，执行者应先把当前可观察的运行环境和工作区作为候选目标，并优先通过只读观察、当前环境资料和实际部署/配置对象取得上述信息；不得把可观察的信息先要求 Human 转述。进入方案、逐事件验证矩阵或最终交还前，必须分别锁定并报告：执行环境的产品/运行器、版本、平台、实际运行位置和识别依据；目标环境的产品/运行器、版本、平台、目标位置和识别依据；以及两者为同一环境、不同但可访问、不同且当前不可访问或尚未确认的关系。候选不是目标；不得以多个厂商名称、历史环境或“未配置”替代这一锁定。只有目标不可观察或无法识别、Human 指定不同目标，或者需要选择部署范围、授权写入、接受权限或信任、处理冲突时，才向 Human 请求相应信息或决定。

只读调查还必须针对已声明的候选接入范围，分开确认技能机制的加载、启用、信任、权限、用户级配置限制，以及登记一项技能时环境要求提供的字段与输入（LDVH 一侧各字段值的权威来源见 09.Att.01「技能登记字段值」）。若具体环境来源或当前可观察事实不能确认某项限制，保持相应范围 `unverified`；不得从其它环境、历史记录或名称猜测开关、菜单、manifest、目录、字段或权限模型。

历史部署记录、聊天记忆、包管理器状态、文件存在、旧截图、fixture 或模板命中不能替代当前输入。LDVH wheel、sdist、editable distribution、pip 状态或 console entry point 都不是默认接入前提。缺少具体环境来源、源码仓库、canonical SKILL.md、可用的管辖配置、common-dir 身份或实际执行能力时，只能形成缺口和方案，不能用模板补造。

执行者按 09 §8 形成能力状态，保存当次具体环境来源并交还输入或证据缺口；本模板不替执行者研究全部厂商，也不把模拟 fixture 当作真实环境证据。

### 5.2 参与者、能力与授权

AI 负责回读来源、识别适用范围、核对现状和用户资产、形成四项工作方案、判断授权覆盖、调用实际能力、解释验证结果和交还未验证范围。Human 只承担当前来源或环境保留的部署/删除与管辖配置写入授权、平台信任、权限、重启、UI 操作、冲突取舍和风险接受。

Helper/Code/实际部署或配置能力只执行其当前声明且实际可用的机械检查、配置写入、部署对象变更、调用和回读。具体环境只提供其真实支持的事件与反馈；环境能力不足不能由模板伪造成已保障。委派执行或观察时，主控 AI 仍负责来源、授权、证据和最终结论。

Human 已明确授权为某一项目的 Git common-dir 部署承接 Git Gate 的 Git Hook 时，该授权可覆盖共享该 common-dir 的主 worktree、现有 linked worktree 与后续 linked worktree；AI 必须先从显式 actual worktree 解析 common-dir、核对 09 所要求的管辖、用户资产和实际写入，并展示覆盖影响。独立 clone 具有不同 common-dir，不在该授权或部署范围内；这只是当次行动范围，不建立长期授权状态或项目登记。

### 5.3 行动步骤与分支

#### A. 建立目标与当前基线

1. 明确当次是首次完成、检查、升级、修复、禁用、卸载还是恢复验证，并对环境接入、管辖配置、Git Hook 部署与验证分别记录当前状态；固定目标环境、版本、部署位置、可触发会话范围、工作区与工作对象，不相互推定；
2. 回读 09、LDVH 当前接入面说明（`specs/attachments/09.Att.01-环境接入面.md`）、具体环境来源及实际部署/配置能力，不沿用历史命令或路径；
3. 只读检查当前规则源、源码仓库身份与修订、09.Att.01 中各必需源码入口的交付状态、显式工作区根、02 配置存在性、目标 actual worktree 与 common-dir、当前接入对象、权限、信任、用户资产、旧版本和冲突；任一必需源码入口或 common-dir 级 Git Hook 管理能力未交付时，只记录迁移缺口，不形成可执行完整接入方案；
4. 把 LDVH 管理对象、确认保留的用户对象、身份未知对象和当前不可观察范围分开；
5. 研究目标环境当前官方或实际权威资料，确认是否存在能够把 SKILL.md 文本递达给 AI 的技能机制，以及原生 Git 事件能否承接 Git Gate；按功能判断，不只看“Skill”这个名称。记录资料 URL 或稳定定位、观察时间、产品版本和平台；
6. 对照 09.Att.01 判断候选机制与接入范围是否同某个既有 LDVH 入口语义对应，列出实际输入、输出、partial/error、超时、权限、用户资产和回滚；
7. 按 09 §8 形成能力状态：
   - 尚未调查、资料未找到、版本不明、权限不足或不可观察 → `unverified`
   - 找到候选自动机制但尚未部署或真实递达或触发 → `unverified`
   - 肯定依据证明不存在能承接必需输入与反馈的自动机制 → `unsupported`
   - 静态部署或核心直调通过，但没有真实递达或触发 → 对应子范围已观察，完整接入仍为 `unverified`
   - `partial` 只能说明已完成的子范围，不能覆盖 `unsupported` 或 `unverified`；
8. 只有目标环境可直接部署 canonical SKILL.md、目标项目能按 02 建立或核验有效管辖配置，且目标 Git common-dir 可部署承接 Git Gate 的 Git Hook 时，才继续形成四项工作完整方案；
9. 若环境接入或 Git Hook 部署必须新增环境侧脚本或未知配置对象，记录缺口并分流到独立 Code 计划，按具体环境资料和 07 建立独立 Code 计划，不继续副作用执行；
10. 管辖配置作为四项工作之一留在本模板中，但其字段、写入、解析与验证完全回到 02；若目标实质是编写薄 Skill 新文本或其它独立行动，分流而不由本模板补造。

若执行者无法仅凭当前可观察信息和具体环境来源锁定目标环境身份、版本、位置或它与执行环境的关系，且该信息只能由 Human 选择、暴露或确认，AI 必须在形成四项工作方案、Skill 部署判断或验收交还前先交还一条最小 **Human 目标确认请求**。该请求不是对 Human 的默认指令，也不构成部署或配置授权；它只包含：当前执行环境及识别依据；待确认目标和已有候选依据；无法由 AI 只读确认的具体事实；Human 需要返回的原始 UI 文本、截图、日志或配置结果；确认后的 AI 复跑入口；以及当前仍为 `unverified` 的事件。Human 确认目标本身不等于部署成功或真实事件已触发。

若权威来源或当前观察证明某个已声明事件必须先由 Human 启用、信任、授予权限、重启或完成其它受限环境操作，AI 必须在形成可执行四项工作方案前交还一条最小 **Human 受限操作请求**。该请求不是对 Human 的默认指令，也不构成授权；它只包含：目标环境和版本及依据；来源明确的设置位置与 Human 动作（未知则明确未知）；受影响事件或缺失能力；用户、工作区、项目、会话和用户资产的影响范围；操作后应出现的可观察状态；Human 需返回的原始 UI 文本、截图、日志或配置结果；以及 AI 的复跑入口和当前仍为 `unverified` 的范围。Human 返回原始结果后，AI 必须重新读取当前状态，再进入方案或真实验证；Human 完成该操作本身不等于部署成功或真实事件已触发。

#### B. 形成方案并取得授权

1. 列出将创建、修改、替换、禁用或删除的对象，以及明确不改变的对象；
2. 对每项变化给出来源、实际能力、预期结果、静态/真实验证入口和失败回滚方向；
3. 分开列出环境接入（源码取得/更新与 Skill 部署）、02 管辖配置的核验或写入、承接 Git Gate 的 common-dir 级 Git Hook 部署、验证，以及环境信任/权限、重启和真实触发；不把它们捆绑为一次默认授权，也不得把四项工作中任一项降为可选项；当次已有有效管辖配置时执行核验而非无效重写；
4. 对未知用户资产、覆盖/合并、不可完整回滚、所需能力无法成立且可能需要接受受影响保障或残留风险，或跨用户/工作区扩大进入 Human Gate；
5. Human 未授权时停在只读方案；授权只覆盖明确环境、对象和副作用。

#### C. 执行并完成静态回读

1. 在执行前重新检查方案依赖、目标对象和当前基线；变化使方案过期时停止并重做差异；
2. 调用实际部署或配置能力，只改变授权范围；管辖配置只按 B 中单列且已获授权的计划项依 02 写入，不隐式登记项目或初始化事实源；不构建或安装 LDVH wheel、sdist、editable distribution，不以 pip 安装 LDVH 本体，不提交 Git 或安装其它工具；
3. 每项写入后回读实际文件、管辖配置、Skill 部署件、common-dir 级 Git Hook、权限或管理入口结果，重新执行当次管辖解析，并记录与方案的净差异；同时回读技能的可触发会话范围和 Git Hook 覆盖的主/linked worktree，确认 Git Hook 路径与配置属于目标 common-dir，未覆盖未知用户 Git Hook，也未影响独立 clone 或其它 common-dir；
4. 执行 Helper CLI 直接可调用检查、Git Gate 核心直调和 fixture 检查时，明确它们分别只证明对应入口，不能替代 Skill 真实递达或 Git Gate 真实事件触发；skill 或环境接入面版本变化后，可先经只读公开操作 `git-hooks-status`（09 §5.9）取得 Git Hook 部署状态、bundle 版本、worktree 覆盖、项目 `skill/SKILL.md` 与当次显式 `skill_path` 目标副本对齐、Stop gate 一致性的结构化观察，作为静态回读的补充入口，但不替代本步其它回读与后续真实触发验证；调用 `git-hooks-status` 时必须显式传 `arguments.platform`(仅报告) 与绝对 `arguments.skill_path`(实际目标)，`skill_path` 缺省/空/相对路径或 `platform` 缺省/空一律 `invalid_request`，且结果只覆盖传入 `skill_path` 这一个目标；也可用已交付的 `ldvh environment-sync inspect` 做只读复核，它不写任何厂商目录、不猜测路径；
5. 静态失败、部分写入、结果不可观察或与方案不一致时，不进入成功分支，转入失败与回滚。

#### D. 完成真实环境触发或建立恢复断点

1. 先按 02 对当次显式工作对象重新执行管辖解析并确认结果范围；再按具体环境来源选择代表性真实会话，检查目标环境是否真实加载薄 Skill、AI 是否经路由真实取得规则引导与当次行动模板；同时在共享目标 common-dir 的主 worktree 与至少一个可用 linked worktree（存在时）执行代表性真实 Git 事件，确认 Git Gate 按各自 actual worktree、当次 Index 与 commit message 调用唯一核心并忠实返回 allow/block；独立 clone 只有纳入本次目标时才作为另一 common-dir 单独验证，不为验收专门创建；
2. 同时覆盖至少一个主要成功路径和一个与当前接入风险匹配的输入缺失、能力缺口、失败、映射拒绝或未验证范围；
3. 需要 Human 信任、权限、重启、新窗口、新任务或 UI 观察时，交还最小验收说明：目标环境、动作、正常表现、应返回的原始结果、复跑入口和未验证范围；
4. 恢复后先重新检查四项工作的当前状态与来源，再消费 Human 原始观察；不把断点前计划当作当前结果；
5. 当前执行环境不能触发目标环境时，只交还目标特定的真实验证恢复包，保持相应范围未验证。恢复包至少包含：已锁定的执行环境与目标环境及二者关系；受影响事件；不能触发的事实与依据；下一责任方；最小动作和需要返回的原始观察；AI 复跑入口；以及仍未覆盖的风险路径。不能以"目标 AI 未配置"或候选环境名称代替该恢复包。

#### D2. Skill 部署后 Human 操作引导

薄 Skill 部署到目标环境技能位置后，仅完成文件复制与部署不等于环境已加载技能或 AI 已取得引导。执行者必须在部署后的输出或交还中包含以下引导：

1. 提示 Human 确认技能已启用或加载——说明需要去目标 AI 环境设置中确认技能已启用、其可见会话范围覆盖目标会话。仅凭文件存在、部署日志或手工 CLI 调用不能证明环境已真实加载技能。
2. 提供面向 Human 的生效验证方法——建议 Human 启动一次新会话，观察 AI 是否实际经路由取得规则引导与当次行动模板（存在可回指的 CLI 请求与结果、取得内容与当次规则源对应）；任一项缺失时说明真实递达未成立，需要排查启用或加载配置。
3. 说明 hydrate 风险——会话中出现的上下文内容可能来自历史恢复（hydrate），不能单独作为真实递达证据。只有同一轮新会话中同时存在可回指的路由取得记录和预期结果，才能确认 Skill 接入已生效。

本节的引导职责不替代 5.3.D 中真实递达与触发的验证要求。Human 完成后重新检查当前状态方可进入真实验证；Human 完成操作本身不等于部署成功或真实递达已成立。

#### E. 失败、禁用、卸载与回滚

1. 根据实际变化和变更前基线选择停止、修复、禁用、卸载或回滚，不对未改变对象执行恢复；
2. 只处理可证明由 LDVH 管理或 Human 明确授权处理的对象，保留未知用户资产；
3. 回滚后重新检查部署对象和目标环境，证明接入不再自动触发或已恢复变更前连接；承接 Git Gate 的 Git Hook 的禁用、卸载与回滚以 common-dir 为单位，并重新观察共享它的代表性 worktree。删除某个 linked worktree 不构成 Git Hook 卸载；独立 clone 的 Git Hook 状态不随另一 clone 改变；
4. 无法恢复原内容、权限、信任、运行环境或用户配置时，明确残留和影响范围，不能把命令成功写成回滚完成；
5. 修复后需要重新执行静态与真实验证，不能沿用失败前证据。

### 5.4 输出、验证、回写与交还

目标尚未锁定而交还 **Human 目标确认请求** 时，该交还属于预方案恢复断点，不形成逐事件验证矩阵。它必须记录执行环境及识别依据、目标未知或候选及依据、未锁定的具体事实、Human 需要返回的原始信息、AI 复跑入口和当前未验证范围；目标锁定后，才进入逐事件验证矩阵。

除此例外，每次行动的交还必须先声明执行环境与目标环境的身份、版本、平台、位置、识别依据和二者关系，并记录 LDVH 源码仓库身份与修订。交还先对**环境接入、管辖配置、Git Hook 部署、验证**四项工作分别给出当次结果；随后必须为具体环境来源已经声明、且本接入单元本次承接的每个接入范围形成一行**逐事件验证矩阵**。它是本次行动的交还材料，不是永久环境状态、事实对象或跨厂商事件登记。每行至少记录：环境、版本和接入单元；来源声明的接入范围；Skill 静态部署与真实递达；管辖配置来源、当次解析输入、结果与范围；common-dir、Git Hook 静态部署、actual worktree、Index/message 绑定与 Git Gate 真实触发；Helper CLI 与 Git Gate 核心直调；主要风险路径；证据及观察时间；`verified`、`unverified`、`unsupported` 或 `not_applicable` 状态；回滚或不适用依据。阻塞本次接入或验收的每个 `unverified` 还必须记录目标特定的阻塞事实和来源、下一责任方、最小恢复动作、所需原始观察、AI 复跑入口及仍未覆盖的范围。薄 Skill 的静态部署观察还须指明实际技能位置、可见会话范围（如用户级范围、工作区级或项目级范围）、启用/信任与加载来源；缓存、hydrate 或历史记录均不能单独证明本轮真实递达。

同一接入单元的静态部署观察可以被多行引用，但不得伪装成每个接入范围均有独立部署事实。没有真实递达或触发证据时，该范围必须为 `unverified`；只有肯定依据证明该环境无法承接所需机制、输入或反馈时才能为 `unsupported`。只有四项工作的当次必需结果、主要成功路径与风险路径证据完整，才可写 `verified`。`not_applicable` 必须写明其来源依据，不能用于跳过环境接入、管辖配置、Git Hook 部署或真实验证。

交还至少区分：目标环境、版本、Skill 部署位置、可触发会话范围及其与工作对象范围的区别；源码仓库身份与修订；管辖配置来源、当次解析输入、结果与范围；目标 common-dir 及共享/不共享它的 worktree；模板适用理由；当前基线和用户资产；四项工作的方案、授权和实际变化；明确未变化对象；静态部署观察；Helper CLI 与 Git Gate 核心直调；Skill 真实递达与 Git Gate 真实触发及结果；成功、失败、部分结果、输入或能力缺口、映射拒绝或 no-op 的原因；Human 断点及恢复入口；回滚/卸载入口和实际结果；已验证、未验证、残留风险和后续行动。

环境部署配置只写入具体环境来源和实际能力允许的位置；管辖配置只写入 02 授权的位置与字段。模板不另建永久 receipt 或环境状态对象；需要长期保留的稳定事实必须重新按事实模型判断。Git commit、发布和 marketplace 提交不因四项工作完成而自动执行。

### 5.5 组合、变更与退出

本模板可以消费已经完成的薄 Skill 文本或环境侧对象编写结果，但不把编写与环境接入合成一个成功声明。管辖配置是本模板四项工作之一；配置已有效时只做当次核验，需要写入时必须作为独立计划项取得 Human 授权，再按 02 执行、回读和验证。四项工作分别成立、不互相替代，但完整接入结论必须同时覆盖四项。

模板稳定步骤关系、适用或失败边界改变时按 06 重审。若未来四项工作不再共享稳定结构，或确定性部署与配置服务能够在不损失 Human Gate、真实触发和失败交还的前提下更低成本承接，应缩减、拆分或退出本模板。

### 5.6 薄 Skill 的部署边界

薄 Skill 以 canonical SKILL.md 为唯一内容来源，部署到目标环境的技能位置。目标环境技能机制支持用户级范围时，默认按 09 §5.2 的用户级部署（跨多个工作区或项目可见），仅当 Human 明确要求限制可见范围时才部署到项目级或工作区级。一次行动必须确认当次实际部署件身份、部署位置、可见会话范围（默认用户级、仅按 Human 明确要求才限制到项目级或工作区级）、启用/信任状态和加载来源；这些静态观察只证明部署，不能替代真实递达。

部署件必须与当前 canonical 模板逐字节一致（09 §5.3）；具体环境来源负责定义该环境的技能目录、加载时机与启用机制。本文不得列举厂商、技能文件名、manifest 字段、图标资产或构建命令，也不得把某一环境的技能结构当作新环境的接入前提。薄 Skill 是唯一 AI 路由形式，但完整接入还必须按 02 建立或核验管辖配置，并按 09 §5.7 部署承接 Git Gate 的 common-dir 级 Git Hook；Skill 真实递达、管辖解析、Git Hook 部署和 Git Gate 真实触发分别验证，不得互相替代。

同步或复核 Skill 部署件优先使用已交付的 `ldvh environment-sync`（09.Att.01）：`inspect` 子命令只读复核 canonical 模板、当次显式 `skill_path` 目标副本与目标 common-dir 的 Hook 状态，不写任何厂商目录、不猜测路径；`update` 子命令产生实际写入，必须按 09 §11 取得覆盖显式 `skill_path`/common-dir 的 Human Gate 授权，且只同步调用方显式确认的 Skill 目标、复用 `git-hook-manager` 检查/升级 common-dir Hook，未知资产冲突或不明写路径时零写入、冲突停止。静态 `aligned` 不等于 Skill 已递达或 Git Hook 已真实触发，真实递达与逐事件触发仍须按 09 §6.2.1 各自验证。

## 7. Human Gate

本文不新增脱离 09 的统一 Human Gate；环境接入的 Human Gate 按 09 §11 及当前实际适用的其它来源执行。

Human 决定的复用按 00 §10 执行；Human 当前指令已经授权某一对象和副作用，且适用于该行动的全部来源规则许可条件已经成立时不重复索取同一决定，但该授权不替代静态回读、Helper CLI 与 Git Gate 核心直调、Skill 真实递达、逐 worktree Git Gate 真实触发或回滚验证，也不自动包含 Git commit、发布和其它环境或独立 clone。

## 8. Stop Conditions

09 §12 的环境接入停止条件全部适用于本模板；此外，出现以下任一模板特有情况时，暂停能够包含风险的最小环境、配置/部署对象、事件或声明：

1. 目标环境技能机制或接入路径无法确定，或者事项实质是编写薄 Skill 新文本、修改厂商机制配置或其它独立行动，却准备由本模板补造；
2. 当前环境接入、管辖配置、Git Hook 部署、用户资产、权限、信任、冲突或未知范围未检查；
3. 方案没有分开环境接入、管辖配置的核验或写入、Git Hook 部署、验证、权限/信任、重启、明确不变对象和回滚，或把其中一项授权扩大到其它项、Git commit 或发布；
4. 静态写入失败、部分成立、不可观察或与方案不一致，却准备继续真实环境验证；
5. 需要 Human 断点，但恢复入口、原始观察要求或未验证范围不清楚；
6. 实际失败、部分结果、输入或能力缺口、映射拒绝或 no-op 的原因、回滚或未验证范围没有进入最终交还；
7. 薄 Skill 的实际部署件、启用/信任、加载来源或可见会话范围无法确认，或者准备把缓存、hydrate 或历史记录写成当前真实递达。
8. 完整接入方案或结论缺少环境接入、当次有效管辖配置与解析、承接 Git Gate 的 common-dir 级 Git Hook 部署或完整验证任一项，或者把这些组成写成可选分支；
9. Git Hook 目标 common-dir、共享它的 worktree 或独立 clone 边界未解析，或者准备合并不同 worktree 的 Index、message、未提交内容或候选身份。
