# 平台适配清单规范

> 创建日期：2026-06-09
> 定位：定义平台适配清单如何把 LDVH 对 AI 的支持要求和规范落地要求，逐项映射为具体 AI 开发平台上的承接方法、证据、降级和待补齐事项
> 适用范围：Trae Solo、Codex、Cursor、Claude Code、CI、Web 工作台、命令行或其他 AI 开发平台的 LDVH 适配清单
> 上位依据：`docs/specs/04-规范落地与环境适配基础规范.md`
> 相关规范：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/04.01-规范落地声明规范.md`、`docs/specs/04.02-环境适配与运行投影规范.md`、`docs/specs/04.03-环境能力承接边界规范.md`、`docs/specs/42-product-initialization-产品初始化.md`、`docs/specs/43-product-audit-产品审计.md`

---
## 1. 本文解决的问题

本文定义平台适配清单机制。

平台适配清单不是平台能力说明书，也不是平台官方文档摘要。它的主轴是 LDVH 对 AI 执行者提出的支持要求和正式规范提出的落地要求；平台只是在每项要求下回答“在这个平台上用什么方法承接、证据是什么、不能完整承接时如何降级”。

普通用户或新平台适配者只需要先做一件事：按本文创建当前平台的“平台适配清单”。清单可以是 draft 或 partial，不要求一次证明完整支持。42 会只按清单中已有证据执行初始化；43 会按清单审计并指出 blocked、degraded 或可补齐项。

LDVH 的安装与接入初始化、产品审计和环境适配不直接绑定某个 AI 开发平台，而是读取当前平台适配清单中的要求响应矩阵。42 安装与接入初始化按矩阵执行；43 产品审计按矩阵逐项审计。

当前已有 Trae Solo 和 Codex 清单。二者均需按真实证据和审计结论维护状态；其他平台不预设完整支持，只保留同构响应矩阵；对应平台用户补齐清单、提供证据并通过审计前，不得声明完整支持。

平台能力如 Rules、Skill、Agent、Command、MCP、Hook、CI、Code、Web 只是承接方法候选，不是清单主轴。清单不得因为某个平台有某项能力，就反向改变 LDVH 的要求。

平台适配清单记录平台承接方法、证据成熟度、降级方式和待补齐事项，不记录某个用户当前环境的实际状态。实际文件、入口、权限、工具或运行投影是否存在，应由 42 初始化和 43 审计现场检查。

## 2. 清单状态

平台适配清单必须声明支持状态。这里的状态表示平台清单或要求响应项的成熟度，不表示某个用户当前环境已经完成初始化。

| 状态 | 含义 | 是否可作为 42 完整执行依据 | 是否可作为 43 pass 依据 |
|---|---|---|---|
| not-started | 尚未填写清单 | 否 | 否 |
| draft | 已草拟但缺少证据或关键字段 | 否 | 否 |
| partial | 部分能力已确认，但存在关键缺口或长期降级 | 只能局部执行 | 不能全链路 pass |
| ready-for-audit | 清单字段和证据已补齐，等待 43 审计 | 可以按范围执行 | 只能审计，不能自动 pass |
| supported | 已通过 43 审计，可作为当前支持平台 | 可以 | 可以 |
| deprecated | 曾经支持但已不推荐或已失效 | 否 | 否 |

除已经通过 43 审计的清单外，任何平台默认不得被写成 supported。没有真实平台上下文、维护者、证据和审计结论的平台，只能是 not-started、draft 或 partial。

## 3. 清单事实源边界

平台适配清单应写入 `docs/specs/04.xx` 正式规范区，作为平台适配规则和待办清单的稳定事实源。

| 内容 | 权威位置 |
|---|---|
| 平台适配清单字段和状态规则 | 本文 |
| Trae Solo 当前适配清单 | `docs/specs/04.07-Trae-Solo适配清单.md` |
| Codex 当前适配清单 | `docs/specs/04.08-Codex适配清单.md` |
| 其他平台待填要求 | 本文或后续对应平台清单 |
| 初始化执行结果 | 42 初始化输出或目标项目中 Human 确认的等价文档 |
| 审计执行结果 | 43 审计输出、Task、Memo、ADR 或对应 Git 文件事实源 |
| 实际运行投影入口 | LDVH-AI-ENTRY.md、平台规则、平台 Skill、平台 Agent、Hook、CI、Web 或命令 |
| 安装与接入初始化执行规则 | `docs/specs/42-product-initialization-产品初始化.md` |
| 产品审计执行规则 | `docs/specs/43-product-audit-产品审计.md` |

清单不得复制平台官方文档全文，不得把聊天判断当作平台事实，不得把尚未验证的能力写成 supported，不得替代 42 或 43 的流程判断。

## 4. LDVH 对 AI 的支持要求

平台适配清单必须先响应 00 总纲中 LDVH 为 AI 执行者提供稳定支撑的要求。

| 要求 ID | AI 支持要求 | 来源 | 平台需要回答的问题 |
|---|---|---|---|
| AI-S1 | 明确边界 | 00 §2、00 §4.1 V2/V3/V4 | 平台如何让 AI 看见任务范围、事实源边界、权限边界、环境边界和禁止事项 |
| AI-S2 | 稳定事实 | 00 §2、00 §3、00 §5.1 | 平台如何帮助 AI 回到 Git 文件事实源，而不是依赖聊天记忆、工具缓存或平台临时状态 |
| AI-S3 | 关联信息 | 00 §2、00 §4.1 V1/V2/V3 | 平台如何让 AI 快速获得相关规范、项目配置、工作对象、refs、上下游关系和历史证据 |
| AI-S4 | 可见状态 | 00 §2、00 §4.1 V7/V9 | 平台如何让 AI 和 Human 看见任务状态、初始化状态、审计状态、阻塞、风险和待确认事项 |
| AI-S5 | 可用工具 | 00 §2、00 §3.2、00 §3.5 | 平台如何提供或调用规则加载、工具运行、文件读写、搜索、命令、Skill、Agent、MCP、Web 或等价能力 |
| AI-S6 | 快速定位 | 00 §4.1 V1 | 平台如何帮助 AI 快速定位入口、规范、事实源、任务状态和工具入口 |
| AI-S7 | 完整理解 | 00 §4.1 V2 | 平台如何给 AI 足够但不过载的上下文，避免遗漏、误读和反复询问已有信息 |
| AI-S8 | 正确判断 | 00 §4.1 V3 | 平台如何帮助 AI 判断事实源边界、风险、阻塞、工具需求、Skill 进入和子 Agent 调度 |
| AI-S9 | 稳定执行 | 00 §4.1 V4 | 平台如何约束 AI 按规范、工作模型、工作流程和受控工具执行，而不是自由发挥 |
| AI-S10 | 门禁识别 | 00 §4.1 V5 | 平台如何让 AI 识别 Human Gate，暂停并等待确认 |
| AI-S11 | 强制验证 | 00 §4.1 V6 | 平台如何支持测试、校验、运行结果、审查证据、预览或 Human 确认 |
| AI-S12 | 证据沉淀 | 00 §4.1 V7 | 平台如何让执行结果、证据、决策和变更可追溯 |
| AI-S13 | 可靠回写 | 00 §4.1 V8 | 平台如何保证稳定事实回写到 Git 文件事实源 |
| AI-S14 | 人类确认质量 | 00 §4.1 V9 | 平台如何让 Human 基于状态、风险、影响和证据做出高质量确认 |
| AI-S15 | 持续完善 | 00 §4.1 V10、00 §5 | 平台如何帮助 AI 把问题、踩坑、缺口和改进机会回流为规范、工作模型、工作流程、Code、Web 或环境适配改进 |

## 5. 规范落地要求响应类型

平台适配清单还必须响应 04.01 定义的规范落地要求类型。

| 要求 ID | 规范落地要求 | 来源 | 平台需要回答的问题 |
|---|---|---|---|
| LR-1 | 上位约束承接要求 | 04.01 §4 | 平台如何让 AI 持续承接 LDVH 上位规范、专项规范和约束链路 |
| LR-2 | 入口可见要求 | 04.01 §4、04.02 §5、04.04 §4-§5 | 平台如何让 AI 在进入项目、流程或任务时看见清单、入口、边界和摘要；平台入口在哪里，是否只做薄引用，是否能定位 LDVH-AI-ENTRY.md 或等价入口 |
| LR-3 | 流程复用要求 | 04.01 §4 | 平台如何把重复流程承接为 Skill、Command、工作流程或操作清单 |
| LR-4 | 子 Agent 思考要求 | 04.01 §4 | 平台如何支持独立、专项或并行视角，或无法支持时如何降级 |
| LR-5 | 确定性执行要求 | 04.01 §4 | 平台如何稳定运行 Code、测试、校验、解析、聚合、上下文压缩或受控写入 |
| LR-6 | Human 交互要求 | 04.01 §4 | 平台如何让 Human 看见、确认、授权、验收或受控轻写入 |
| LR-7 | 生命周期触发要求 | 04.01 §4 | 平台如何在规范、配置、入口、事实源、任务、提交或会话事件上触发检查或降级提醒 |

## 6. 要求响应矩阵字段

每个平台适配清单必须以“要求响应矩阵”为主体。每一行至少包含以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| requirement_id | 是 | 采用 AI-S1 至 AI-S15 或 LR-1 至 LR-7 |
| requirement_name | 是 | 要求名称 |
| requirement_source | 是 | 来源规范和章节 |
| platform_method | 是 | 该平台用什么具体方法承接该要求 |
| platform_entities | 是 | 具体机制、文件、命令、规则、Skill、Agent、MCP、Web、Code 或人工流程 |
| refs_evidence | 是 | 平台 refs、官方资料、现有文件或实测证据 |
| status | 是 | not-started、draft、partial、ready-for-audit、supported、deprecated |
| degradation | 是 | 无法完整承接时的降级方式和残留风险 |
| audit_evidence | 是 | 43 审计时应检查的证据 |
| open_items | 是 | 后续要补齐的事项 |

平台能力索引可以作为辅助章节存在，但不得替代要求响应矩阵。

## 7. 42 使用清单的规则

42 安装与接入初始化必须围绕当前平台适配清单中的要求响应矩阵执行和验证，而不是围绕某个平台名称或平台能力清单硬编码执行。

AI 应按以下顺序处理：

1. 确认当前平台；
2. 定位对应平台适配清单；
3. 读取 AI-S1 至 AI-S15 和 LR-1 至 LR-7 的要求响应矩阵；
4. 判断本次安装与接入初始化依赖哪些要求；
5. 对每项依赖要求读取 platform_method、status、degradation、audit_evidence 和 open_items；
6. 若关键要求只有 partial 或 degraded 响应，42 只能按降级路径执行并记录残留风险；
7. 若关键要求 not-started、draft、deprecated 或缺失，不得宣称完整安装与接入初始化完成；
8. Trae Solo 和 Codex 清单是当前已存在的要求响应清单，但 42 不得把任一平台名写成唯一执行逻辑。

---
## 8. 43 使用清单的规则

43 产品审计必须审计当前平台适配清单中的要求响应矩阵，以及矩阵声明与实际环境、运行投影、初始化结果之间的一致性。

产品审计至少应检查：

1. 当前平台是否有清单；
2. 清单状态是否允许本次审计范围；
3. AI-S1 至 AI-S15 和 LR-1 至 LR-7 是否被逐项响应；
4. 每项响应是否说明 platform_method、platform_entities、refs_evidence、status、degradation、audit_evidence 和 open_items；
5. audit_evidence 是否存在且可追溯；
6. 降级项是否被 42 初始化结果正确记录；
7. 清单是否把未经验证的承接方法写成 supported；
8. 清单是否需要回退为 partial、draft 或 deprecated。

没有完整清单或没有证据的平台，43 只能输出 blocked、degraded、partial 或 out-of-scope，不得输出全链路 pass。

## 10. Human Gate 与检查要求

以下情况必须触发 Human Gate：

1. 将任一平台清单状态改为 supported；
2. 将未经审计的要求响应矩阵作为完整初始化依据；
3. 删除、重命名或改变 Trae Solo、Codex 等既有平台清单职责；
4. 把某个平台能力提升为 LDVH 全局唯一底座；
5. 允许缺少 audit_evidence 的平台通过 43；
6. 改变本文字段、状态机或 42/43 依赖要求响应矩阵的规则。

检查平台适配清单时，应确认：

1. 要求响应矩阵覆盖 AI-S1 至 AI-S15 和 LR-1 至 LR-7；
2. 状态与证据匹配；
3. 未把平台官方文档、聊天判断或工具缓存当成最终事实；
4. degradation、audit_evidence 和 open_items 没有被隐藏；
5. Trae Solo 和 Codex 是当前已有清单实例，不是写死在 42 或 43 中的平台逻辑。

## 11. 规范落地要求

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 平台差异应由平台适配清单中的要求响应矩阵承接，42 和 43 不得直接绑定某个平台名称作为唯一执行逻辑 | 本文、00、04.01、04.02、42、43、Human Gate | 环境适配治理 | 新增、修改或审计平台适配规则时 |
| 入口可见要求 | AI 进入环境确认、初始化或审计时，应能定位平台适配清单机制、当前平台清单和要求响应矩阵 | 04 父规范、04.02、42、43、运行入口摘要 | AI 执行入口提示 | 当前平台、清单状态或入口投影变化时 |
| 确定性执行要求 | 后续 Code 应能检查要求响应矩阵字段、状态、证据和 42/43 引用一致性 | `tools/specs_validate.py` 扩展、正反样例 | 校验实现 | 清单字段、状态或平台清单文件变化时 |
| Human 交互要求 | 平台清单声明 supported、删除 Trae Solo 清单或改变清单字段规则前必须 Human Gate | Human Gate、审计证据、影响说明 | 平台适配确认 | §8 中任一 Gate 条件发生时 |
| 生命周期触发要求 | 平台清单、运行投影、42 初始化结果或 43 审计证据变化后，应检查清单状态和审计证据是否仍一致 | 43 产品审计、人工降级检查、Code 缺口 | 触发保障 | 平台能力、入口、清单字段、审计证据或初始化流程变化时 |

## 12. 待补齐事项

1. 平台适配清单要求响应矩阵的结构化 Code 校验待 Trae Solo 清单稳定后补齐；
2. 其他平台是否单独建 `04.xx` 清单文件，待对应平台用户提供真实填写内容后决定；
3. supported 状态是否需要更严格的证据格式，待 43 首次审计 Trae Solo 清单后评估。
