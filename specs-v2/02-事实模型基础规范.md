## 1. 本文解决的问题

本文定义 LDVH 如何把工程工作事实建模为稳定、可追溯、可校验、可被 AI 读取和可被 Human 审查的事实模型，并统一承接字段契约、字段内容格式和字段注册治理。

本文解决：

1. 什么内容可以成为事实模型，什么内容只能留在当前上下文、已有对象字段、规范、文档或研究材料中；
2. 事实模型、事实实例、字段契约、字段内容格式和字段注册表之间如何分工；
3. 具体事实模型规范最低必须定义哪些对象规则、状态规则、字段规则、证据规则和消费边界；
4. 公共字段如何保持语义稳定，同时不反向推导每个模型都采用该字段；
5. 字段注册表如何作为附件被 Code、Web 和知识地图消费，但不成为具体模型完整 schema 的权威来源；
6. 事实模型与行动编排、Code、Web、运行时扩展和全局事实源规则之间如何避免互相越界；
7. 事实模型相关规范变化时，哪些内容必须进入 Human Gate、保障要求或后续行动编排接管。

本文不定义具体事实模型的完整字段表、状态枚举、实例文件内容、关闭条件或对象特有验收标准。这些规则由 20-29 具体事实模型规范在自身主文件中定义。本文不把 `specs/09-事实源边界与承载规范.md` 的全局事实源原则整体迁入 02；02 只定义事实模型和事实实例如何承接全局事实源原则。

## 5. 事实模型定义与准入

事实模型是 LDVH 对某一类工程生产事实的标准化建模结构。它定义该类事实的对象定位、准入条件、事实源边界、状态机、对象关系、Human Gate、字段契约、证据要求、实例检查和消费边界。

事实实例是项目中按事实模型创建的具体事实。事实模型定义规则，事实实例承载项目事实；模型不得承载具体实例状态，实例不得重新定义模型规则。

一个内容必须满足以下条件之一，才应成为事实模型或进入既有事实模型实例：

1. 需要独立追踪状态；
2. 需要可验证的完成标准；
3. 需要关闭证据、验证证据或 Human Gate 证据；
4. 需要被其它对象稳定引用，或需要引用其它对象；
5. 需要被 Code 排序、过滤、聚合、校验，或被 Web 呈现给 Human；
6. 不结构化会导致进度、责任、完成标准、决策依据或验证结果不可追踪。

不满足以上条件的内容应按性质分流：

| 内容性质 | 分流位置 |
|---|---|
| 只服务当前对话的临时判断 | 当前上下文，不写入事实源 |
| 已有目标但不需要独立状态 | 作为 WorkCase 内部执行项或当前行动编排上下文处理 |
| 现有对象的属性、关系、证据或输出路径 | 写入现有事实实例字段 |
| 长期规则、字段规则、状态规则或流程规则 | 写入对应规范 |
| 长期决策 | ADR 或对应事实源 |
| 暂存想法、候选发现或待分流问题 | Spark 或对应待补齐事项 |
| 研究报告或外部资料吸收候选 | Study、docs/studies 或 docs/sources，按 active 规则判断 |

不得因为内容重要、页面需要展示、工具容易解析或 AI 想减少记忆负担，就绕过准入条件创建新的事实模型。

已清退对象类型不得重新成为当前事实模型入口。旧 `TaskPlan`、`Task` 和 `SubTask` 不再是当前 active 事实模型，也不得作为 Code 或 Web 的兼容读取、校验、迁移、直达展示或测试夹具维护对象。历史事实由 Git 历史、相关 Spark 或已迁移后的 WorkCase 承载；当前事实源、Code 入口、Web 入口和字段注册只面向 active 事实模型。

清退对象的详细目录、旧对象类型和旧字段清单由 `02.Att.07-清退对象与废弃字段登记表.md` 承载。该附件只能登记已清退对象、旧入口和废弃字段，不得单独扩大或缩小本文定义的清退边界。

## 6. 事实模型标准组成与成员规则

具体事实模型规范必须在自身主文件中定义完整对象规则。成员主文件既是该事实模型规则事实源，也是事实模型集合事实源；手写目录、派生索引、Code 输出和知识地图不得替代成员主文件。

v2 具体事实模型成员默认位于 `specs-v2/20-29-事实模型/`，文件名采用：

```text
NN-{英文名}-{中文名}.md
```

文件名不得重复“事实模型规范”字样。成员编号、文件名编号、一级标题、`v2_spec.spec_id` 和成员身份块 `spec_id` 必须一致。编号冲突、编号越界、路径漂移、身份块缺失、集合状态非法或锚点不可回指时，必须报告为事实模型成员一致性缺口。

具体事实模型成员必须同时具备：

1. `v2_spec`，承载规范写作身份、写作状态、迁移来源、active 事实源和 Code/知识地图消费类别；
2. `v2_fact_model_member`，承载事实模型集合成员身份、集合状态、实例事实源、规则锚点和成员级 Code 消费入口。

`v2_spec.status` / `v2_spec.authority` 描述规范写作状态和 v2 写作区权威状态；`v2_fact_model_member.collection_status` 描述该事实模型在事实模型集合中的治理状态。两者不得混用。`specs-v2/` 中的成员身份块不得把 v2 草稿升级为 active 权威；active 事实仍以 `active_fact_source` 指向的 v1 成员主文件为准，直到 Human 单篇确认并完成切换。

`v2_fact_model_member` 至少必须包含以下字段：

| 字段 | 最低要求 |
|---|---|
| `spec_id` | 必须与文件名编号和 `v2_spec.spec_id` 一致 |
| `kind` | 固定为 `fact_model` |
| `name_en` / `name_zh` | 必须与文件名英文段和中文段一致 |
| `collection_status` | 必须使用本文定义的集合状态闭集 |
| `canonical_path` | 必须与成员主文件真实路径一致 |
| `instance_root` / `instance_carrier` | 必须说明实例事实源入口和承载方式；无实例时必须说明原因 |
| `fact_source_anchor` / `schema_anchor` / `state_machine_anchor` / `human_gate_anchor` | 必须回指成员主文件中的对应章节 |
| `code_consumption` | 必须说明 Code 应读取的字段、章节、锚点或检查入口 |

事实模型成员集合状态闭集如下：

| 集合状态 | 含义 |
|---|---|
| `active` | 已是当前 active 事实模型集合成员；v2 未切换前必须能回指 active v1 成员主文件 |
| `candidate` | 候选事实模型；不得进入 active 实例入口、默认 Dashboard、CLI 新建入口或 Web 新建入口 |
| `reserved` | 编号预留；不得被解释为已存在事实模型 |
| `removed` | 已移除或清退；不得作为新写入入口 |

实例承载方式闭集如下：

| 承载方式 | 含义 |
|---|---|
| `yaml` | 事实实例以 YAML 文件或 YAML frontmatter 为主要结构化承载 |
| `markdown` | 事实实例以 Markdown frontmatter 和正文承载 |
| `external` | 使用外部事实源；成员主文件必须说明原因、位置和同步边界 |
| `none` | 无事实实例目录；必须说明为什么不产生实例 |

`v2_fact_model_member` 的详细字段说明由 `02.Att.02-事实模型成员身份字段表.md` 承载；成员规范骨架模板由 `02.Att.03-事实模型成员规范骨架模板.md` 承载；成员一致性辅助核对表由 `02.Att.04-事实模型成员一致性辅助核对表.md` 承载；v1-v2 双读映射矩阵由 `02.Att.05-事实模型成员双读映射矩阵.md` 承载。附件只承载各自授权的信息对象，不得单独改变本文定义的成员主文件权威边界、成员身份原则、集合状态闭集、事实源边界或 Human Gate。

具体事实模型成员主文件必须采用 `02.Att.03` 授权的专属骨架，并同时满足 01 的正式规范必要章节。骨架章节均为强制要求；某章节暂不适用时，必须保留章节并说明不适用原因、替代承载位置或待补齐事项，不得无说明删除。成员规范可以在专属骨架内增加对象特有子章节，但不得改变上位章节含义。

具体事实模型主文件至少应覆盖：

1. 对象定位与准入条件；
2. 事实源边界；
3. 状态机；
4. 对象关系；
5. Human Gate；
6. 字段契约；
7. 事实实例写入、回写、验证和证据留存；
8. Code、Web、知识地图和运行时扩展消费边界；
9. 规范保障要求；
10. 对象特有实例检查；
11. 待补齐事项。

具体事实模型不得把字段契约、状态机、关闭条件、Human Gate 或事实源边界拆到未授权附件、Code 实现、Web 页面、Rules、Skill、Agent 或过程输出中独立维护。长示例、字段注册长表、正反样例、迁移矩阵或对象检查辅助表可以在主规范明确授权后作为附件存在；附件不得成为对象规则入口。

active v1 的 20-29 具体事实模型规范通过 `ldvh_doc` 和 `ldvh_member` 声明成员身份。v2 切换前，Code 默认仍以 active `ldvh_doc` / `ldvh_member` 为集合索引入口；v2 `v2_fact_model_member` 只能作为迁移诊断和双读验证输入。切换 active 前，必须定义并验证 Code 双读策略，至少确认：

1. active `ldvh_member` 与 v2 `v2_fact_model_member` 的编号、路径、集合状态、实例目录和锚点一致；
2. `collection_status=active` 的 v2 成员能回指一个 active v1 事实源，或有 Human Gate 记录说明新增 active 的授权；
3. `collection_status=candidate`、`reserved` 或 `removed` 不进入 active 实例入口、默认 Dashboard、CLI 新建入口或 Web 新建入口；
4. 25-29 未占用编号不得因目录存在、计划存在或知识地图派生而被解释为已登记成员；
5. 派生集合索引必须回指成员主文件，不能成为成员集合事实源。

具体事实模型成员清单不由手写集合索引维护。成员主文件身份块是集合事实源，Code 和知识地图只能派生集合视图、读取建议和诊断结果。

## 7. 字段契约规则

字段契约是事实模型的一部分，不是独立构成要素。字段契约用于说明一个事实模型中每个字段回答什么问题、采用什么值形态、是否必填、何时条件必填、内容如何表达、由谁消费、由谁拥有 schema 和约束。

具体事实模型字段契约至少应说明：

| 字段契约项 | 含义 |
|---|---|
| 字段名或路径 | 字段名称或重要嵌套字段路径 |
| 字段来源 | 公共基线字段、公共字段、模型特有字段或历史兼容字段 |
| 字段含义 | 字段回答什么问题，不应承载什么内容 |
| 值形态 | string、datetime、markdown、object、list_object、list_string 等 |
| 是否必填 | 必填、可选或条件必填 |
| 状态条件 | 哪些状态下必须存在、必须为空或必须满足额外约束 |
| 内容格式 | narrative、checklist、evidence、decision、reference、log 或 structured |
| schema 归口 | 具体模型、公共字段规则或其它非附件权威位置 |
| 消费方 | AI、Code、Web、知识地图、运行时扩展或具体行动编排 |

所有事实模型必须具备模型身份基线字段：

| 字段 | 公共语义 |
|---|---|
| `id` | 事实实例唯一标识 |
| `type` | 事实实例所属模型类型 |
| `title` | 一句话概括 |
| `status` | 当前对象状态 |
| `created` | 创建时间，使用 datetime |
| `updated` | 最近更新时间，使用 datetime |

`datetime` 字段必须使用 ISO 8601 时间戳，至少包含日期、小时和分钟，例如 `2026-06-18T17:10:00+08:00` 或 `2026-06-18T17:10:00`。仅包含日期的 `YYYY-MM-DD` 属于 `date`，不得写入 `created`、`updated`、`closed_at`、`review_requested_at`、`evolution.at` 等 `datetime` 字段；只有字段契约明确为 `date` 时，才允许使用纯日期。

以下公共字段在被具体事实模型采用时，必须遵守统一语义。本文只定义公共语义和内容格式，不规定具体事实模型是否必须采用这些字段：

| 字段 | 回答什么问题 | 不应该写什么 | 内容格式 |
|---|---|---|---|
| `description` | 对象背景、目标、范围和存在理由 | 验证方法、风险说明、约束条件、验收标准、状态变化 | narrative |
| `source` | 对象的输入来源 | 一般关联、验证结论 | reference / narrative |
| `source_detail` | 输入来源说明、触发问题或原始输入摘要 | 一般关联清单、状态变化历史 | narrative / reference |
| `acceptance` | 完成判断条件 | 验证方法、风险说明、背景 | checklist |
| `verification` | 怎么验证完成 | 风险说明、约束条件、背景说明、验收标准 | evidence |
| `verification_evidence` | 成功标准如何被检查 | 验收标准、背景说明 | evidence |
| `closure_evidence` | 为什么可以关闭、关闭结果、残留风险和 Human Gate 结果 | 验收标准、背景说明 | evidence |
| `closed_at` | 关闭时间 | 创建时间、更新时间 | datetime |
| `archive_reason` | 为什么归档 | 归档后的内容、验证 | narrative |
| `deprecated_reason` | 为什么废弃 | 归档原因、状态流水、替代关系 | narrative |
| `discard_reason` | 为什么废弃 | 废弃后的说明、验证 | narrative |
| `notes` | 其他字段无法承载的补充说明 | 核心信息、验证方法、决策 | narrative |

具体事实模型只要定义 `archived`、`deprecated`、`discarded` 等非活跃终态，就必须为该终态定义并填写对应原因字段：`archived` 使用 `archive_reason`，`deprecated` 使用 `deprecated_reason`，`discarded` 使用 `discard_reason`。原因字段必须说明为什么对象不再处于活跃入口，以及后续 AI / Human 应如何理解该对象；不得只写“已归档”“已废弃”等重复状态本身的空泛文本。

工作对象不得手写维护 `status_history`。状态变化历史、前后状态、修改原因和执行者由 Git 提交记录派生；需要长期保留的语义转折应写入对象专用字段、证据字段或相关工作对象，不得用手写状态历史形成第二事实源。

引用字段分为来源引用和关联引用：

| 字段或字段族 | 用途 | 边界 |
|---|---|---|
| `source_*` | 本对象的直接输入来源 | 不承载一般关联 |
| `related_*` | 与本对象有关联的其它对象、文档或规则 | 不承载直接输入来源 |
| `related_docs` | 后续引用或承接的文档路径 | 不承载对象 ID |
| `related_rules` | 规范、Rules、Skill、Agent、Code 或 Web 路径 | 不承载一般项目文档 |
| `urls` | Study 等报告正文提炼出的外部 `http(s)` URL 及用途摘要 | 不承载项目内文档、规范路径、代码位置或纯说明文本 |
| `superseded_by` | 替代本对象的新对象、规范或实现引用 | 不作为一般关联字段使用 |

如果引用是本对象的直接输入来源，应放入 `source_*`；如果只是一般关联，应放入 `related_*`。如果引用是文档路径，使用 `related_docs`；如果是规范、Rules、Skill、Agent、Code 或 Web 路径，使用 `related_rules`。如果引用是 Study 报告正文中的外部网页资料，使用 `urls`；`urls` 只承载完整 `http(s)` URL 及中文用途摘要。

`priority` 用于执行调度顺序、价值判断和保留意义判断，回答“哪个工作项或火花应先处理”。`priority` 只适用于 WorkCase 和 Spark，枚举如下：

| 值 | 判断标准 |
|---|---|
| `P0` | 不立即处理会阻塞当前主线、导致事实源漂移、使关键能力不可用、破坏验证闭环、造成重大返工或扩散明显错误 |
| `P1` | 应优先处理，明确影响当前目标推进、关键闭环、近期交付、长期事实源稳定性或关键治理边界，但不覆盖全部 P0 工作 |
| `P2` | 有明确价值，可在 P0 和 P1 工作之后按正常节奏处理 |
| `P3` | 可延后、候选、优化、补充、可替代、可丢弃，或不影响当前主线关闭 |

`priority` 适用边界如下：

1. WorkCase 必须维护 `priority`，不得维护 `importance`；
2. Spark 必须维护 `priority`，不得维护 `importance`；
3. ADR、Study 和 Pitfall 不得直接维护 `priority` 或 `importance`；
4. ExecutionItem 不得独立维护 `priority` 或 `importance`，其调度顺序由 WorkCase 的执行编排承载；
5. Pitfall 不得使用 `severity` 字段，影响和后果应写入 `symptoms`、`applicability`、`avoidance` 或 `notes`。

公共字段语义由本文和 `02.Att.01-字段注册表.md` 授权表共同服务，但公共字段不是默认可写字段池。具体模型采用公共字段时，必须在自身字段契约中显式声明采用、必填性、状态条件和模型内约束。

字段治理遵循以下规则：

1. 新增字段前，必须检查公共字段语义和字段注册表，避免同义异名；
2. 相同字段名在不同对象中的公共语义应保持一致；需要差异化时，具体模型必须说明差异，不得静默漂移；
3. 字段是否存在、是否必填、状态条件、关闭条件和对象内完整 schema 只由具体事实模型规范定义；
4. 字段注册项只说明字段若被采用应如何理解、消费和检查，不得反向证明具体模型已经采用该字段；
5. 废弃字段不得作为新写入入口；历史兼容读取、迁移提示和替代关系由字段注册附件、Code/Web 实现和具体模型共同承接。

## 8. 字段内容格式

字段内容格式定义字段内部文本或结构如何表达。内容格式不是事实模型，不具备独立生命周期、状态机或关闭条件。

LDVH 事实模型字段内容至少使用以下格式类型：

| 格式类型 | 用途 | 边界 |
|---|---|---|
| `narrative` | 背景、目标、范围、约束、说明和补充信息 | 不承载 checklist、状态流转或完整证据闭环 |
| `checklist` | 验收标准、关闭检查项和质量门禁 | 检查项必须可独立验证 |
| `evidence` | 验证计划、验证命令、验证结果、结论、关闭判断和 Human Gate 记录 | 不得只写“已验证”“通过”等无法复查的短句 |
| `decision` | 决策选择、理由、影响和后续注意事项 | 若形成长期架构决策，应进入 ADR 或对应事实源 |
| `reference` | 对象 ID、文档路径、规范路径、Commit、URL 或其它引用 | 不承载一般说明文本 |
| `log` | 过程摘要、语义转折、修订记录和观察时间线 | 不得变成无结构流水账或第二事实源 |
| `structured` | 对象内部结构化子对象或列表 | 完整 schema 由具体模型定义 |

字段内容写入遵循以下规则：

1. `value_shape=markdown`、`checklist_markdown` 或 `evidence_markdown` 的字段，如包含中文标点、英文冒号、换行、命令、列表式说明或超过一短句，应优先使用 YAML 块标量 `|`；
2. 不得把包含冒号的长文本直接写成未加引号的普通单行字符串；
3. `format_kind=checklist` 的字段必须使用 `- [ ]` 或 `- [x]` 检查列表格式，每项必须是可独立验证的原子条件；
4. 具体模型若把 Checklist 字段声明为关闭条件，关闭前所有检查项必须标记为 `- [x]`，或在对应证据字段说明不能完成的降级结论和 Human Gate 结果；
5. `format_kind=evidence` 的字段应使用 `## 验证计划`、`## 验证命令`、`## 验证结果`、`## 结论` 四段式结构；
6. `## 验证计划` 回答要验证什么、依据什么判断通过；
7. `## 验证命令` 记录实际运行的命令、脚本、检查入口、人工检查动作或“不适用”的理由；
8. `## 验证结果` 记录检查结果摘要、关键输出、路径或观察结论，不粘贴超长日志；
9. `## 结论` 给出明确验证结论，并说明残留风险、关闭判断或后续分流；
10. `urls` 字段必须使用结构化网址对象，至少包含 `ref` 和 `summary`；`ref` 保存完整 `http(s)` URL，`summary` 用中文说明该网址支撑当前报告中的什么判断；
11. `format_kind=structured` 的字段必须使用 YAML object 或 list[object]，不得写成 Markdown 字符串；完整 schema、字段是否必填、状态条件和关闭条件由具体事实模型规范定义。

新写入或重写验证证据字段时，应使用可复查结构，至少说明验证计划、验证命令或动作、验证结果和结论。具体模型若把某证据字段声明为关闭条件，进入关闭状态前不得为空，也不得只写“已验证”“见上文”“通过”等无法复查的短句。

涉及 Human Gate 的验证证据字段，可以嵌入 `Human Gate 记录：` 文本块。该记录应至少说明确认时间、确认主体、确认事项、确认结论、确认范围、约束条件和后续责任。Human Gate 记录进入 `closure_evidence`、ADR 字段、行动编排结果、Spark 或其它事实源字段时，只作为对应字段中的证据片段，不创建独立验证证据对象，也不得替代对象状态机、决策正文、验证结论或 Git 提交记录追溯。

YAML 工作对象中的长文本字段可以使用 Markdown 语义书写。Markdown 在此处只是字段内容格式，不改变对象事实源位置，也不创建第二事实源。

AI 不得在事实实例中添加字段注册表未登记、且具体事实模型规范未定义的字段。如需新增字段，应先回到本文、`02.Att.01` 和对应具体事实模型主文件判断最小权威归口；字段注册项仍不得反向证明具体模型已经采用该字段。

## 9. 字段注册与消费边界

`02.Att.01-字段注册表.md` 是本文授权附件，只承载字段注册表、注册列闭集、字段生命周期、废弃/别名/替代关系和 AI/Code/Web 可消费元数据。字段矩阵诊断由 `02.Att.06-字段矩阵诊断表.md` 承载；清退对象和废弃字段登记由 `02.Att.07-清退对象与废弃字段登记表.md` 承载。

字段注册表负责：

1. 登记字段名或重要嵌套字段路径；
2. 登记字段语义、内容格式、值形态、引用类型和消费元数据；
3. 登记枚举归口、schema 归口和可机械检查维度；
4. 登记 Web 派生展示语义；
5. 登记字段生命周期、废弃字段、别名字段和替代字段；
6. 为字段矩阵诊断提供注册来源，支持 Code 发现同义字段、值形态冲突和废弃字段复用。

字段注册表不负责：

1. 定义具体事实模型是否采用某字段；
2. 定义字段是否必填、条件必填或可为空；
3. 定义对象状态机、合法流转或关闭条件；
4. 定义对象内完整 schema、跨字段约束或实例写入授权；
5. 定义 Code 输出 Schema、Web 组件、API 路由、页面布局或运行时扩展适配方式。

Code、Web 和知识地图可以消费字段注册表和具体模型字段契约。消费结果只能作为诊断、索引、展示、受控交互或最小读取建议，不得替代字段注册表、具体模型规范或事实实例。

凡本文直接命名并给出写入、禁用、替代或消费规则的字段，例如 `priority`、`importance`、`severity`、`status_history`、`archive_reason`、`deprecated_reason`、`discard_reason`，必须能回指字段注册表、具体事实模型字段契约或清退对象与废弃字段登记表。不得在主文、附件、Code 或 Web 中形成无法回指的隐性字段规则。

## 10. 事实实例写入、证据与回写边界

事实实例写入必须遵守全局事实源原则和具体事实模型规范。AI、Code、Web、Skill、Agent 或运行时扩展输出只有写入对应 Git 文件事实源，并满足对象规范、必要 Human Gate 和 Git 可追溯要求后，才成为稳定事实实例或稳定事实更新。

事实实例写入和回写遵循以下规则：

1. 创建实例前必须判断准入条件，不得因内容重要就自动建模；
2. 更新实例前必须读取对应事实源，按状态机判断操作是否允许；
3. 涉及状态流转、关闭、删除、降级、归档、废弃或高影响字段变更时，必须评估 Human Gate；
4. 字段写入必须符合具体模型字段契约、公共字段语义、内容格式和字段注册边界；
5. 验证证据、关闭证据和 Human Gate 记录必须能回指事实源、验证动作、结论和残留风险；
6. Git 提交记录用于追溯事实源修改，不作为工作对象手写字段维护；
7. Code/Web/知识地图派生状态不得作为对象状态、验证结论或关闭判断的唯一依据。

事实实例证据生命周期至少包括：

| 证据节点 | 最低要求 |
|---|---|
| 对象创建 | 记录创建原因、创建依据和来源；可由创建字段、来源字段、首个提交或对应 WorkCase/Spark 承载 |
| 状态变更 | 能追溯变更时间、变更主体、变更原因、变更前后状态和相关字段变化；Git 提交记录可作为追溯来源，但不得手写维护提交清单 |
| 验收检查 | 记录检查对象、检查标准、检查动作、结果摘要和结论；自动检查和人工检查都必须能复查 |
| Human Gate | 记录确认事项、确认主体、确认结论、范围、约束和后续责任；不得用“已确认”替代具体确认记录 |
| 关闭判断 | 关闭前必须能追溯验收证据、关闭证据、残留风险、后续分流和必要 Human Gate 结果 |

聊天、临时分析、命令输出、Agent 输出、Web 页面状态和工具报告不得直接冒充稳定证据。它们只有按事实类型写入对应事实实例、规范、ADR、Study、Spark、Pitfall、Git 提交记录或其它明确事实源后，才形成可复查证据。

事实模型规范可以定义对象特有证据字段、回写条件和实例检查要求，但不得重定义全局最终事实源、单一事实源或工具输出回写原则。若对象特有规则与全局事实源规范冲突，必须暂停并进入 Human Gate。

## 11. 与行动编排、Code、Web 和运行时扩展的边界

事实模型承载工程工作事实；行动编排约束 AI 如何读取、判断、执行、暂停、验证、交还和回写。行动编排可以创建、更新、检查或引用事实实例，但不得重新定义事实模型字段、状态机、验收标准或事实实例事实源边界。

Code 可以依据事实模型开发解析、校验、聚合、测试、受控写入、字段矩阵和派生索引能力。Code 不得自行判断对象准入、替代 Human Gate、把派生索引写成事实源，或用实现逻辑反向改变字段契约。

工作对象接口用于把事实模型契约转换为 AI、Rules、Skill、Code 和 Web 可共同消费的结构化边界。接口原语不替代事实模型规范，不形成第二套字段事实源，只描述对象在不同机制中的可消费面。

工作对象接口至少包括：

| 接口层次 | 说明 | 权威来源 |
|---|---|---|
| 对象接口摘要 | 对象 ID、事实源目录、文件命名、默认状态、终态、主要读取场景和主要写入场景 | 具体事实模型主规范与字段契约 |
| Raw Object 接口 | YAML、Markdown frontmatter 或其它事实实例载体的字段、类型、必填性、条件必填、枚举、列表字段和示例 | 字段契约或对应权威位置 |
| 引用关系接口 | 本对象可引用哪些对象、哪些对象可引用本对象、引用字段、引用有效性和缺失引用处理方式 | 具体事实模型主规范与字段契约 |
| 消费者接口 | AI、Rules、Skill、Code、Web 分别消费哪些字段、在哪些场景消费、消费失败如何报告缺口 | 字段契约或对应权威位置 |

Code 的对象能力至少区分读取、校验、状态流转、创建、删除和缺口报告。读取接口不得改变事实源；校验接口依据字段契约校验字段完整性、状态合法性、条件必填、引用关系和文件命名；状态流转接口必须依据状态枚举和流转矩阵执行，并在写入前检查 Human Gate；创建接口必须检查编号、命名、必填字段和初始状态；删除接口必须依据对象规范判断是否允许删除并保留 Git 可追溯性；缺口报告接口必须在字段契约、Code 实现和测试不同步时输出结构化缺口，不得静默通过。

Web 可以展示事实实例、字段证据、状态信号、风险、待确认事项和受控交互入口。Web 页面状态不是事实源；受控轻写入必须回到具体事实模型、Code 校验和 Human Gate 边界。

运行时扩展可以提供入口可见、读取顺序、流程复用、Agent 调度、工具调用和环境适配能力保障。运行时扩展承载物不得复制事实模型完整字段契约、状态机、关闭条件或 Human Gate 细则；需要摘要时必须回指本文和具体模型规范。

## 14. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 新增、删除、重命名、合并、拆分、降级或废弃事实模型；
2. 改变事实模型准入条件、标准组成、成员身份块、专属骨架、集合状态闭集或具体模型主文件权威边界；
3. 改变模型身份基线字段 `id`、`type`、`title`、`status`、`created`、`updated` 的存在性或公共语义；
4. 改变字段契约原则、公共字段语义、`priority` 统一标准、引用字段边界、字段注册表边界、注册列闭集或字段生命周期状态；
5. 新增、删除或改变字段内容格式类型，或改变验证证据、Checklist、Structured 等可机械校验格式；
6. 将字段注册表解释为具体模型字段存在性、必填性、状态条件、关闭条件或完整 schema 的依据；
7. 将 Code、Web、知识地图、运行时索引、工具输出或聊天过程升级为事实实例事实源；
8. 将行动编排、Rules、Skill、Agent、Code、Web 或运行时扩展内容写成事实模型完整规则入口；
9. 将 `specs/09-事实源边界与承载规范.md` 的全局事实源原则整体迁入本文或本文附件；
10. 重新启用已清退的 TaskPlan、Task、SubTask 对象类型或旧字段入口；
11. 接受事实模型相关 Code 检查缺口、长期降级或无验证迁移。

以下情况应评估 Human Gate，并在影响模型集合、字段契约、事实源边界、状态机、Human Gate、字段注册、Code/Web 消费或 active 事实源时暂停确认：

1. 修改本文待补齐事项、规范保障要求或附件授权；
2. 调整 20-29 具体事实模型骨架、成员身份字段、实例目录或字段契约表达方式；
3. 新增、删除、重命名或改变 `02.Att.01` 中注册列、字段生命周期状态或 `code_consumption` 内容；
4. 新增、删除、重命名或改变 `02.Att.02`、`02.Att.03`、`02.Att.04`、`02.Att.05` 中成员身份字段、成员骨架模板、一致性核对项、双读映射或 `code_consumption` 内容；
5. 新增、删除、重命名或改变 `02.Att.06` 中字段矩阵核对项，或改变 `02.Att.07` 中清退对象、旧入口、废弃字段登记和 `code_consumption` 内容；
6. 发现本文与 active v1 05 系列、09、具体事实模型规范、Code 校验结果或 Web 消费入口冲突；
7. 后续构成要素实践试图重新定义本文已定义的事实模型、字段契约或事实实例边界。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 结论、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。
