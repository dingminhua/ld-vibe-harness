# 程序辅助规范

> 创建日期：2026-05-28
> 定位：PM Kit 程序辅助层的定位、职责边界、解析、校验、聚合、受控写入与协作规则
> 适用范围：所有接入 PM Kit 的项目
> 上位依据：`specs-v2/00-PMKit理念与纲要.md`

---

## 一、本文解决的问题

本文解决的问题是：程序在 PM Kit 中承担什么角色、能做什么、不能做什么，以及程序如何与 Git 文件事实源交互、如何辅助 AI 和工具、如何受控写入。

程序负责确定性解析、校验、聚合和受控写入，Rule / Skill / Agent 负责协作约束和流程入口。程序不保存第二套事实、不修改业务事实、不替代对象状态机、不直接调用 AI。

---

## 二、与 00 总纲的关系

00 §二 定义工具负责读取事实源、聚合事实源、校验事实源、提供受控写入入口、降低人和 AI 维护结构化文件的成本。00 §五 要求协作闭环中工具辅助解析、校验、聚合和受控写入，执行证据回到 Git 文件事实源。

本文将 00 的工具职责要求转化为程序辅助层的行为约束：程序可以读取、解析、校验、聚合和受控写入 Git 文件事实源，但不能成为最终事实源。本文约束对象为程序。

---

## 三、程序辅助的定位与职责边界

> 事实源边界声明：本文的权威领域是程序辅助层的行为约束和职责边界。程序输出不是事实源；对象语义、状态机和事实源格式契约由 14-管理对象规范和 10-事实源层规范定义，本文不重新定义。

程序在 PM Kit 中的定位是确定性辅助层：程序处理的是可由规则完全确定的解析、校验、聚合和写入操作，不处理需要判断、决策或创造性的工作。

### 3.1 允许的职责

| 职责 | 说明 |
|---|---|
| 读取 | 从 Git 文件事实源读取结构化对象 |
| 解析 | 解析结构化格式文件 |
| 校验 | 校验字段完整性、状态合法性、引用有效性和格式合规性 |
| 聚合 | 聚合项目上下文、任务状态、审计结果 |
| 受控写入 | 按授权写入目标项目事实源，写入后记录变更 |
| 报告缺口 | 报告初始化缺口、合规缺口和结构缺口 |
| 生成派生视图数据 | 生成供工具展示层使用的聚合数据 |
| 生成上下文包 | 生成 AI 执行上下文包 |

### 3.2 禁止的职责

1. 保存第二套事实：程序不得维护与 Git 文件事实源不一致的权威状态。
2. 修改业务事实：程序不得自动修改任务状态、关闭任务或修改规则。
3. 替代对象状态机：程序不得绕过管理对象规范定义的状态机进行状态流转。
4. 直接调用 AI：程序不得调用 AI、Skill 或 Agent。
5. 成为事实源：程序输出不得成为任务状态、证据、决策、规则或审计的唯一来源。

---

## 四、程序与事实源的关系

1. 程序的输入来源是 Git 文件事实源，程序不维护独立的数据存储。
2. 程序的输出不是事实源。程序输出中出现的校验结果、聚合数据、上下文包和派生视图数据，均属于派生层，不替代 Git 文件事实源的权威地位。
3. 程序输出中需要长期保留的信息，必须回写到 Git 文件事实源，并重新判断其对象类型和事实源载体。
4. 程序可以使用缓存或数据库提高性能，但缓存和数据库只能是派生层，必须可由 Git 文件事实源重新生成，失效或重建后不影响事实源完整性。

---

## 五、解析原则

### 5.1 输入来源

1. 程序解析的输入必须来自 Git 文件事实源。
2. 程序不得将缓存、数据库、UI 状态或对话内容作为解析输入的权威来源。

### 5.2 格式依赖

1. 程序解析依赖事实源层（10）定义的格式契约。
2. 当格式契约变更时，程序解析逻辑应同步更新；程序不得自行定义或扩张格式契约。

### 5.3 错误处理

1. 解析失败时，程序应报告具体的失败位置、期望格式和实际内容，不得静默跳过。
2. 解析失败不得导致程序修改或覆盖原始事实源文件。
3. 解析失败应作为缺口报告处理，由 AI 或人判断后续操作。

---

## 六、校验原则

### 6.1 校验范围

校验范围由管理对象规范（14）和各对象实践定义，程序不自行扩张校验范围。

校验至少覆盖：

| 校验类型 | 校验对象 | 校验依据 |
|---|---|---|
| 字段完整性 | 对象必填字段 | 管理对象规范 |
| 状态合法性 | 对象状态流转路径 | 对象状态机 |
| 引用有效性 | 对象间引用关系 | 项目文件存在性 |
| 格式合规性 | 文件命名、编号、头部声明 | 事实源层规范 |
| 规则引用合法性 | 规则文件引用路径 | AI 协作层规范 |

### 6.2 校验时机

1. 对象写入前必须校验。
2. 项目初始化或接入时应执行全量校验。
3. 事实源变更后，相关校验应重新执行。

### 6.3 校验结果

1. 校验结果应结构化输出，包含校验类型、校验对象、校验结果（通过 / 不合规 / 缺失）、不合规详情和建议修复方式。
2. 校验结果不是事实源。校验发现的修复应按审计发现分流规则处理。

### 6.4 校验失败处理

1. 校验失败不得导致程序自动修改事实源。
2. 校验失败应报告给 AI 或人，由其判断是否修复及修复方式。
3. 写入前校验失败应阻止写入操作。

---

## 七、聚合原则

### 7.1 聚合范围

1. 聚合范围由使用场景决定：项目上下文、任务状态、审计结果、初始化缺口等。
2. 聚合输入必须来自 Git 文件事实源，不得混入缓存、数据库或 UI 状态中的派生数据。

### 7.2 聚合输出

1. 聚合输出属于派生视图数据，不是事实源。
2. 聚合输出必须包含来源引用：每个数据项必须能追溯到 Git 文件事实源。
3. 聚合输出不得缓存后漂移：如果事实源已变更，聚合输出必须重新生成。

### 7.3 聚合与事实源的关系

1. 聚合不改变事实源内容。
2. 聚合结果中需要长期保留的信息，必须回写到 Git 文件事实源。
3. 聚合不得维护与 Git 文件事实源不一致的权威状态。

### 7.4 索引类信息

索引类信息是程序从 Git 文件事实源聚合得出的对象列表、交叉引用、状态汇总和搜索过滤结果。索引类信息属于派生视图数据，不是事实源。

1. 索引类信息不生成文件，只返回结果。程序不得将索引类信息持久化为独立文件。
2. 索引类信息按需计算，直接返回给调用方（AI、工具或人）。
3. 目录结构本身提供自然索引（如 `pm-kit-base/tasks/` 按文件名列出所有任务），程序不需要额外生成索引文件。
4. 如果索引类信息中的某项内容需要长期保留，应判断其对象类型，按对应对象的事实源载体写入 Git 文件，不得将索引本身作为事实源。

---

## 八、受控写入原则

### 8.1 写入目标

1. 程序的任何写入操作，实际写入目标必须是项目的 Git 文件事实源。
2. 写入不得只停留在程序内部存储、数据库或 UI 状态。
3. 程序不得维护自己的数据存储。

### 8.2 写入前检查

写入前必须校验：

1. 目标事实源归属正确；
2. 写入内容符合对象格式规范；
3. 状态流转合法；
4. 是否触发 Human Gate；
5. 是否已有权威事实（避免覆盖）。

### 8.3 写入后验证

1. 写入后必须记录变更记录。
2. 写入后工具视图应从事实源重新读取或刷新。
3. 写入后可通过 Git 追溯。

### 8.4 写入与 Human Gate

1. 程序写入或覆盖 Git 文件事实源，必须评估 Human Gate。
2. 程序不得绕过 Human Gate 自动写入。
3. Human Gate 的完整定义见 AI 协作层规范（11）。

### 8.5 禁止通过程序修改的内容

1. 规范文档（specs）不得通过程序直接修改。
2. 规则文件（Rules）不得通过程序直接修改。
3. 程序不得自动修改任务状态、关闭任务或修改规则。

---

## 九、程序与 AI 协作的关系

### 9.1 程序如何辅助 AI 读取事实源

1. 程序可以为 AI 生成上下文包，降低 AI 进入项目时的上下文组装成本。
2. 上下文包必须从 Git 文件事实源实时生成或按需生成。
3. 上下文包不是事实源。上下文包中出现的新信息，如果需要长期保留，应重新判断其对象类型和事实源载体。
4. AI 不得因为某项内容进入本次上下文，就认为它已经进入项目事实源。

### 9.2 程序如何辅助 AI 回写事实源

1. 程序可以为 AI 提供受控写入入口，按授权写入目标项目事实源。
2. AI 通过程序写入事实源时，必须遵守受控写入原则（第八节）。
3. AI 不得绕过程序的写入校验直接修改事实源。

### 9.3 程序与 Rule / Skill / Agent 的关系

1. Rule 可以依据本文约束 AI 使用程序的行为。
2. Skill 可以调用程序执行确定性校验和聚合。
3. Agent 可以调用程序获取结构化上下文。
4. 程序不得调用 AI、Skill 或 Agent。

---

## 十、程序与工具展示层的关系

### 10.1 程序如何为工具提供数据

1. 程序可以为工具展示层生成派生视图数据。
2. 派生视图数据必须从 Git 文件事实源聚合生成，可追溯到事实源。
3. 工具展示层不得将程序提供的派生视图数据作为权威事实源。

### 10.2 工具展示层如何使用程序

1. 工具展示层可以调用程序获取聚合数据。
2. 工具展示层写入时，必须通过程序的受控写入入口，遵守受控写入原则。
3. 工具展示层不得绕过程序的写入校验。

---

## 十一、程序禁止事项

1. 不得绕过事实源：程序不得将缓存、数据库或 UI 状态作为权威事实源。
2. 不得绕过 Human Gate：程序不得在需要人确认的节点自动执行。
3. 不得改变项目归属：程序写入必须回到被管理项目自身的 Git 文件事实源。
4. 不得将派生数据升级为权威事实：程序输出不得成为任务状态、证据、决策、规则或审计的唯一来源。
5. 不得引入持久化数据库作为事实源替代：程序可以使用数据库作为派生层，但不得将其作为权威事实源。
6. 不得自动修改业务事实：程序不得自动修改任务状态、关闭任务或修改规则。
7. 不得生成索引文件：程序不得将索引类信息持久化为独立文件，索引类信息只返回结果（见 §7.4）。

---

## 十二、Human Gate 与检查要求

以下情况必须暂停并等待用户确认：

1. 程序写入或覆盖 Git 文件事实源；
2. 程序改变事实源归属；
3. 程序将派生数据升级为权威事实；
4. 程序绕过规则、决策或证据门禁；
5. 程序引入持久化数据库作为派生层。

检查至少包括：

| 检查项 | 标准 |
|---|---|
| 来源可追溯 | 程序输出可追溯到 Git 文件 |
| 写入可追溯 | 程序写入落到 Git 文件 |
| 缓存非权威 | 缓存可重建且非唯一事实源 |
| 项目归属 | 程序写入被管理项目自身 |
| Gate 判断 | 高影响写入已评估 Human Gate |
| 校验覆盖 | 写入前校验已执行且通过 |

---

## 十三、不进入本文的内容

以下内容不进入本文：

1. 程序的具体模块设计和代码实现；
2. 具体编程语言的选择、模块结构和命令说明；
3. API 契约和数据库 schema；
4. 具体缓存策略和部署方式；
5. 具体校验器、聚合器、解析器的实现逻辑；
6. PM Web Tools 页面设计、交互和数据库设计（见 13-工具展示层规范）；
7. AI 协作语义和 Human Gate 总清单（见 11-AI 协作层规范）；
8. 管理对象实践细则（见 20-49 管理对象实践）；
9. 操作步骤、案例和工具使用手册。

---

## 十四、待补齐事项

1. 上下文包的字段定义是否需要在本文或对象实践中补齐；
2. 校验结果是否需要标准化输出格式；
3. 受控写入的具体校验流程是否需要与事实源层规范对齐；
4. 程序是否需要支持两种接入形态（单项目产品 vs 多项目产品）；
5. 程序与工具展示层的接口边界是否需要进一步细化。
