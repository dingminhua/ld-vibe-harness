# Trae Rules、Skills 与 Agent 使用规则调研

> 创建日期：2026-05-26
> 来源：Trae 官方文档
> 定位：外部资料引用，不直接成为 LDVH 强制规则

## 一、结论摘要

截至 2026-05-26，Trae 官方文档中与 AI 协作资产相关的核心机制可概括为：

| 机制 | 官方定位 | 主要作用 | 加载/触发方式 | 适合承载 |
|---|---|---|---|---|
| Rules | 规范 AI 在 TRAE 内的行为 | 长期约束、项目/个人偏好、代码风格、架构边界 | 规则注入；项目规则支持 4 种生效方式 | 底线规则、硬约束、风格规范、目录/模块约束 |
| Skills | 面向特定场景的专业能力说明书 | 复用 SOP、操作流程、输出结构、专业知识 | 动态按需加载，也可手动调用 | 可复用流程、复杂步骤、模板、脚本说明 |
| Agent | 面向特定任务的智能体 | 通过 Prompt、MCP Server、内置工具组合完成专业任务 | 用户通过 @ 选择；SOLO Agent 可调用自定义 Agent | 专业角色、工具组合、复杂任务分工 |
| SOLO Agent | 面向复杂项目开发的主控智能体 | 任务规划、执行推进、多 Agent 编排 | SOLO 模式下通过 @ 选择 | 中大型开发、重构、Plan/Spec 流程、多角色协作 |

推荐理解：

```text
Rules 决定 AI 必须遵守什么边界；
Skills 告诉 AI 遇到某类任务时如何稳定执行；
Agent 定义由哪个专业角色、带哪些工具来执行；
SOLO Agent 负责复杂任务中的规划、推进和多 Agent 编排。
```

## 三、Rules 使用规则

### 3.1 官方定位

Rules 用于规范 AI 在 TRAE 内的行为，包括代码风格、语言与框架、交互方式等，使 AI 输出更符合个人偏好和项目要求。

官方列出的核心价值包括：

1. 提升效率：把反复沟通的偏好和要求转化为可复用规则。
2. 统一标准：把团队规范、项目标准结构化，使输出保持一致。
3. 保障质量：让 AI 明确架构设计、命名规范、代码风格等核心约束，减少常见错误。

### 3.2 规则类型

Trae 支持两类规则：

| 类型 | 作用域 | 适合内容 |
|---|---|---|
| 全局规则 | 所有项目 | 个人语言风格、操作系统偏好、回答深度、交互方式 |
| 项目规则 | 当前项目 | 代码风格、技术栈、框架约束、API 限制、项目架构边界 |

项目规则使用 Markdown 编写，系统会在当前项目中创建 `.trae/rules/` 文件夹并保存规则文件。

### 3.3 项目规则的 4 种生效方式

| 生效方式 | 官方说明 | 需要配置 | 使用建议 |
|---|---|---|---|
| 始终生效 | 当前项目下所有 AI 对话中生效 | `alwaysApply: true` | 只放核心硬约束，避免上下文膨胀 |
| 指定文件生效 | 匹配 `globs` 字段指定文件时生效 | `alwaysApply: false` + `globs` | 适合前端、后端、测试、文档等文件类型规则 |
| 智能生效 | AI 根据 `description` 判断相关性后决定是否使用 | `alwaysApply: false` + `description` | 适合场景规则，但描述必须清晰 |
| 手动触发生效 | 仅当对话中用 `#Rule` 提及时生效 | `alwaysApply: false` | 适合低频、特殊、成本较高的规则 |

注意：`#Rule` 引用优先级最高。即使某条规则原本是指定文件生效或智能生效，只要用户在对话中通过 `#Rule` 提及，AI 也会在本次对话中使用。

### 3.4 多层规则嵌套

Trae 支持在 `.trae/rules/` 下创建子文件夹归类规则，系统自动递归读取，最多支持 3 层嵌套。

示例：

```text
.trae/rules/
├── general-rules.md
├── frontend/
│   ├── react-best-practices.md
│   └── testing/
│       └── unit-test-rules.md
├── backend/
│   └── api-design.md
└── devops/
    └── ci-rules.md
```

超出第 3 层的规则不会被识别，因此规则目录应控制深度。

### 3.5 子目录规则

Trae 支持在项目任意子目录下创建 `.trae/rules/` 文件夹，为特定模块配置专属规则。

当对话中提及该目录下文件，或 AI 执行任务时读取了该目录下文件，系统会自动携带并应用该目录规则。

这对大型项目很重要：

1. 可以避免根目录规则过大。
2. 可以减少模块规则互相干扰。
3. 可以按技术栈或业务模块设置局部约束。

### 3.6 AGENTS.md、CLAUDE.md 与 CLAUDE.local.md

Trae 支持将项目根目录中的 `AGENTS.md`、`CLAUDE.md`、`CLAUDE.local.md` 加入上下文。

启用方式：前往设置中的规则导入设置，打开对应开关。

官方说明中：

1. `AGENTS.md` 是项目级轻量 Markdown 指引，仅在当前项目生效，可在其他支持 `AGENTS.md` 的 IDE 中复用。
2. Trae 兼容 `CLAUDE.md` 和 `CLAUDE.local.md`，从 Claude Code 导入项目时可复用已有文件。
3. 开启后，智能体会读取这些文件并添加到上下文中。

LDVH 视角下，这类文件可视为跨工具兼容的规则入口，但需要避免与 `.trae/rules/` 形成冲突事实源。

### 3.7 Git Commit Message 规则

Trae 支持通过规则文件中的 `scene: git_message` 字段，为 AI 生成提交内容设置规则。

示例：

```markdown
---
scene: git_message
---
正文：生成提交内容时应遵守的规范
```

只要规则文件包含 `scene: git_message`，AI 生成提交内容时都会遵循其中定义的规则，不受 `alwaysApply`、`description`、`globs` 等字段影响。若多个规则文件都包含该字段，AI 会同时遵循。

### 3.8 Rules 最佳实践

官方最佳实践可整理为：

1. 控制单条规则的内容粒度，避免一条规则包含过多信息。
2. 各条规则之间不得彼此冲突或互相覆盖。
3. 指定文件路径时使用相对于项目根目录的相对路径。
4. 引用规则时优先选择与当前对话或任务强相关的规则。
5. 新建或修改规则后，建议开启新对话，避免历史上下文与新规则冲突。
6. 若项目已有大量不符合规范的代码，应明确告诉 AI 当前任务是重构，并在特定场景中强制要求严格遵循新规则。

## 四、Skills 使用规则

### 4.1 官方定位

Trae 中的 Skill 通过 `SKILL.md` 文件定义和管理。

官方定义：每个 Skill 封装指令、脚本及相关资源，用于为智能体提供可复用、面向特定场景的专业能力。

一个 Skill 可以被理解为智能体的“专业能力说明书”，在执行任务时，智能体按需加载相应 Skill，以增强对任务的理解和执行能力。

### 4.2 Skill 的关键特征

| 特征 | 说明 |
|---|---|
| 结构化 | 一个 Skill 对应一个 `SKILL.md`，以结构化方式描述任务目标、适用场景、约束、步骤、示例、脚本等 |
| 动态按需加载 | 智能体不会在任务开始时读取所有 Skill 全文，而是先扫描简要描述，判断相关后再加载详细内容 |
| 可复用 | 可将 SOP、规范、模板、专业经验沉淀为长期复用能力 |
| 可共享 | 可在团队、项目或社区间共享 |

### 4.3 Skill 与 Rules、MCP Server 的区别

| 对比项 | 区别 |
|---|---|
| Skill vs Rules | Rules 采用全量加载机制，一旦开启对话会注入并占用上下文；Skill 按需加载，仅在需要时进入上下文 |
| Skill vs MCP Server | Skill 描述如何完成任务；MCP Server 提供可调用工具 |

例子：Playwright MCP Server 提供浏览器自动化能力；对应 Skill 可以约定测试工程结构、POM 设计规范、测试用例编写和执行流程。

### 4.4 Skill 类型与目录

| 类型 | 目录 | 用途 |
|---|---|---|
| 项目技能 | 当前项目 `.trae/skills/` | 项目专属业务知识、技术方案、内部工具协作、项目维护流程 |
| 全局技能 | macOS/Linux：`~/.trae/skills`；Windows：`%userprofile%/.trae/skills` | 跨项目通用开发范式、通用工具链、个人或组织长期偏好 |

Trae 也支持 `.agents/skills/` 目录。若 `.trae/skills/` 与 `.agents/skills/` 中的 Skill 重名，系统优先调用 `.trae/skills/` 中的 Skill。

### 4.5 Skill 结构

一个 Skill 必须包含 `SKILL.md`，也可以包含示例、模板、资源、脚本等。

```text
skill-name/
├── SKILL.md
├── examples/
│   ├── input.md
│   └── output.md
├── templates/
│   └── component.tsx
└── resources/
    └── style-guide.md
```

官方给出的 `SKILL.md` 基本格式：

```markdown
---
name: 技能名称
description: 简要描述这个技能的功能和使用场景
---

# 技能名称

## 描述
描述这个技能的作用。

## 使用场景
描述触发这个技能的条件。

## 指令
清晰的分步说明，告诉智能体具体怎么做。

## 示例（可选）
输入/输出示例，展示预期效果。
```

### 4.6 创建、启用和使用 Skill

Trae 支持三种创建方式：

1. 通过对话由 AI 自动创建 Skill。
2. 在设置中的“技能与命令”手动创建全局或项目 Skill。
3. 手动导入外部 `SKILL.md` 或包含 `SKILL.md` 的 zip 文件。

创建后可通过开关启用或禁用 Skill。项目 Skill 被禁用时，Trae 会在项目 `.trae/` 目录下创建 `skill-config.json`，记录被禁用的项目技能。

使用方式包括：

1. 手动调用：用户明确要求使用某个 Skill。
2. 自动调用：AI 根据任务内容与 Skill 的适用场景描述判断是否加载。

### 4.7 写好 Skill 的官方标准

官方最佳实践强调：Skill 不是一次性 Prompt，也不是写给人看的说明文档，而是可长期复用、输入输出明确、强调稳定性和工程化维护的能力模块。

核心标准如下：

| 标准 | 含义 |
|---|---|
| 元数据精准 | `name` 简洁唯一，使用小写字母、数字、连字符，建议动名词，不超过 64 字符；`description` 从模型视角描述能力与触发时机，不超过 1024 字符 |
| 边界明确 | 明确何时使用、何时不要使用，降低误触发 |
| 输入输出结构化 | 用模型可解析的输入输出定义减少歧义 |
| 步骤明确可执行 | 用指令式步骤描述，而非泛泛描述 |
| 失败策略完备 | 对校验失败、执行失败、外部服务不可用等场景给出处理策略 |
| 职责单一 | 每个 Skill 只做一件事，对应一个核心动作 |
| 渐进式披露 | `SKILL.md` 作为入口和导航，详细示例、模板、脚本拆分为独立文件 |
| 评测驱动 | 先建立无 Skill 基线，识别失败点，再设计评测用例和最小化 Skill |

### 4.8 Skill 的构建流程

官方推荐流程可归纳为：

1. 建立无 Skill 基线，观察模型在哪些场景不稳定。
2. 以失败优先原则定义 3-5 个可复现评测用例。
3. 编写最小化 Skill，只覆盖当前评测所需的最短成功路径。
4. 补充边界条件、输入输出结构和示例。
5. 每次修改 Skill 后进行评测回归。
6. 在真实使用中继续观察误触发、遗漏上下文、反复读取等信号，作为新评测输入。

## 五、Agent 使用规则

### 5.1 官方定位

Trae 支持创建自定义 Agent，并为其配置 Prompt、MCP Server 与内置工具，使其协助完成特定任务。

自定义 Agent 可以修改、分享、删除，也可以通过链接导入他人分享的 Agent。

### 5.2 创建方式

Trae 支持两种创建方式：

| 方式 | 官方建议 | 说明 |
|---|---|---|
| 智能生成 | 推荐 | 描述 Agent 功能、场景、使用时机，由系统生成初稿后再修改 |
| 手动创建 | 可选 | 逐项配置头像、名称、Prompt、是否可被其他 Agent 调用、工具等 |

### 5.3 Agent 配置项

| 配置项 | 说明 |
|---|---|
| 头像 | 可选，用于标识 Agent |
| 名称 | Agent 名称 |
| Prompt | 规定 Agent 人设、回答口吻、工作流程、工具使用时机、需要遵守的规范 |
| 可被其他智能体调用 | 开启后可被其他 Agent 调用，被调用时拥有独立上下文 |
| 英文标识名 | 被其他 Agent 调用时使用的唯一英文标识，例如 `project-analyzer` |
| 何时调用 | 描述其他 Agent 适合调用该 Agent 的场景和时机 |
| 工具 | 可配置 MCP Server 和内置工具 |

目前官方说明中，只有 SOLO Agent 可以调用自定义 Agent。

### 5.4 Agent 可用工具

自定义 Agent 可配置：

1. MCP Server：添加后可调用 MCP Server 提供的工具。
2. 内置工具：
   - 阅读：检索和查看文件。
   - 文件系统：增删改查文件。
   - 终端：运行命令并获取状态和结果。
   - 联网搜索：搜索与用户任务相关的网页内容。
   - 预览：生成可预览前端结果后提供预览入口。

工具配置决定 Agent 能做什么，因此应遵循最小授权原则：只给该 Agent 完成任务真正需要的工具。

### 5.5 使用、分享与导入

使用 Agent：在 AI 对话输入框输入 `@` 或点击 `@智能体`，从列表中选择。

分享 Agent 前，官方提示应对 Agent Prompt 和 MCP Server 配置中的信息进行脱敏。

导入 Agent：点击他人分享链接，按浏览器引导打开 Trae，在信息展示窗口点击“立即获取”。

### 5.6 官方一键导入 Agent 类型

Trae 官方提供若干可一键导入的自定义 Agent 示例，包括：

| Agent | 使用场景 |
|---|---|
| UI Designer | UI/UX、组件设计、设计系统、视觉优化 |
| Frontend Architect | 前端界面、组件架构、状态管理、性能优化 |
| Backend Architect | API、业务逻辑、数据库架构、服务端系统 |
| API Test Pro | API 功能、契约、性能、负载、安全测试 |
| AI Integration Engineer | 大模型、推荐系统、智能自动化、AI 部署 |
| DevOps Architect | CI/CD、云基础设施、监控、部署自动化 |
| Performance Expert | 性能测试、瓶颈分析、系统优化 |
| Compliance Checker | 法律文档、隐私政策、服务条款、合规风险 |

这些 Agent 可以单独调用，也可以由 SOLO Agent 在开发流程相应阶段自动调用。

## 六、SOLO Agent 使用规则

### 6.1 官方定位

SOLO Agent 是面向复杂项目开发的智能体，支持从需求迭代到架构重构的全流程开发。

其核心能力包括：

1. 智能任务规划。
2. 精准执行机制。
3. 确认计划后自动推进开发进度。
4. 编排多个智能体组成 AI 团队。

启用前提：通过界面左上角模式切换按钮，将 Trae 切换至 SOLO 模式。

### 6.2 调用自定义 Agent

SOLO Agent 支持调用自定义 Agent 完成模块化任务。

官方说明：

1. SOLO Agent 默认内置 Search Agent，用于检索和查看文件。
2. 配置可调用 Agent 后，SOLO Agent 作为主控 Agent，可在复杂任务中自动调用相应 Agent。
3. 被调用 Agent 在独立上下文中专注处理各自任务。
4. 用户也可以在 Prompt 中明确指定需要调用的 Agent。

这说明 Agent 更适合做“角色化分工”，而不是承载基础硬约束。

### 6.3 Plan 模式

Plan 模式适用于中小型功能开发和模块级重构。

流程：

1. SOLO Agent 收到需求。
2. 分析需求并规划任务。
3. 生成规划文档。
4. 等待用户确认。
5. 确认后一一执行。

如果计划不符合预期，用户可以直接编辑计划，或发送修改需求让 SOLO Agent 调整。

启用方式：输入 `/`，在模式选择列表中选择 `/ Plan`。

### 6.4 Spec 模式

Spec 模式面向更复杂的系统级任务。

SOLO Agent 会生成三阶段文档组：

1. 大纲：`spec.md`。
2. 任务列表：`tasks.md`。
3. 验收清单：`checklist.md`。

这些文件存储在项目根目录 `.trae/specs/` 下，按任务名称分组为独立文件夹，可纳入版本控制作为长期项目知识资产。

首次创建后，SOLO Agent 会暂停并等待用户确认。确认执行后，任务列表和验收清单状态会随执行进度自动更新。

适用场景包括：

1. 新系统 / 新模块 0 到 1 搭建。
2. 大规模重构。
3. 多人协作项目。
4. 高质量 / 高稳定性项目开发。
5. 需长期维护的成熟项目。

启用方式：输入 `/`，在模式选择列表中选择 `/ Spec`。

## 七、Rules、Skills、Agent 的分工建议

### 7.1 决策矩阵

| 需要沉淀的内容 | 优先载体 | 原因 |
|---|---|---|
| 所有任务都必须遵守的硬约束 | Rules | 始终生效，适合底线要求 |
| 只对某类文件或目录生效的约束 | 指定文件/子目录 Rules | 可按路径触发，减少干扰 |
| 需要按步骤执行的 SOP | Skills | 按需加载，适合流程和模板 |
| 低频但复杂的操作手册 | Skills | 避免长期占用上下文 |
| 专业角色执行复杂任务 | Agent | 可配置 Prompt、工具和 MCP |
| 多角色协作或复杂开发推进 | SOLO Agent + 自定义 Agent | 主控 Agent 负责任务拆分和调度 |
| 提交信息规范 | `scene: git_message` Rules | 官方提供专门场景字段 |
| 跨工具兼容的轻量规则 | AGENTS.md / CLAUDE.md | 便于在其他 AI IDE 复用，但需避免冲突 |

### 7.2 载体选择口诀

```text
必须永远遵守 → Rule
遇到场景才执行 → Skill
需要专业角色和工具组合 → Agent
需要规划、拆解、调度多个角色 → SOLO Agent
需要跨工具兼容 → AGENTS.md / CLAUDE.md，但要控制事实源冲突
```

### 7.3 LDVH 借鉴建议

1. LDVH 的 L0/L1 规则应保持短小、稳定、硬约束化，避免写成百科手册。
2. L2 场景规则可借鉴 Trae 的智能生效、指定文件生效和子目录规则机制。
3. 对话整理、任务验收、备忘写入等流程型能力更适合 Skill，而不是一直放在 Rules 中。
4. 多角色分析、前后端专项审查、性能测试等角色型能力更适合 Agent。
5. 复杂功能开发可借鉴 SOLO Agent 的 Plan/Spec 模式，但 LDVH 应明确自己的事实源边界，避免 `.trae/specs/` 与项目 `specs/`、`docs/`、`ldvh-base/`混淆。
6. Agent 或 Skill 分享前必须脱敏，尤其是 Prompt、MCP Server 配置、内部路径、密钥、Token、业务数据。
7. 新增规则或 Skill 后建议开启新对话验证，避免旧上下文覆盖新配置。
