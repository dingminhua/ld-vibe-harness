## 1. 本文解决的问题

本文解决 LDVH 中工作模型区段如何登记、检查和被后续重新设计的落地检查流程或审计流程消费的问题。

本文是 20-39 工作模型区段的规范型集合索引。AI 和 Human 在进入具体工作模型前，应先通过本文确认：

1. 哪些编号已经占用；
2. 哪些工作模型是 active、removed、deferred-field、deferred-doc 或 reserved；
3. 哪些生产概念不得误恢复为独立工作模型；
4. 后续重新设计的落地检查流程应读取哪些 active 工作模型；
5. 候选事项和保留编号如何表达。

本文不定义具体工作模型的字段契约、状态机、实例验收规则、对象特有 Human Gate 或行动流程。这些内容由 21-39 具体工作模型规范承载。

## 2. 与 00 和 05 的关系

00 定义 LDVH 工作模型是五类构成要素之一，用于承载工程生产事实。05 定义工作模型的基础规则、准入条件、通用规范和与 20-39 具体规范的关系。

本文承接 05，只维护工作模型集合的清单、状态、关系和后续重新设计的落地检查输入。本文不得反向改写 05 的通用规则，也不得替代 21-39 具体工作模型规范。

## 5. 工作模型集合闸门

创建、删除、恢复或调整工作模型前，必须先通过本文判断集合状态，再决定是否创建或修改 21-39 文档。

集合闸门规则如下：

1. `active` 项可以作为当前具体工作模型规范；
2. `removed` 项不得在没有 Human Gate 的情况下恢复为独立工作模型；
3. `deferred-field` 项不得因为术语重要或字段常用而自动对象化；
4. `deferred-doc` 项不得在没有独立状态机、字段契约和验收需求前升级为 YAML 工作模型；
5. `reserved` 编号不得绕过 Human Gate 占用；
6. 参考与研究材料或临时参考不得自动成为当前正式规范。

当前 active 工作模型：

| 顺序 | 对象 | 原因 |
|---|---|---|
| active | WorkArea / 工作域(24) | 承接长期工作范围、上下文和治理范围 |
| active | TaskPlan / 任务计划(27) | 承接一次目标的执行契约、任务列表、Human 确认点和关闭审查 |
| active | Task / 任务(26) | 承接 AI 执行、验收、验证证据、风险判断、依赖关系、产物引用和检查结果 |
| active | SubTask / 子任务(28) | 承接 Task 下最小可并行执行单元 |
| active | Change / 变更(22) | 承接事实源变更追溯和 commit message 契约 |
| active | ADR / 决策(21) | 承接长期决策和高影响规范判断 |
| active | Memo / 备忘(25) | 承接未任务化但有保留价值的输入，是 ADR、WorkArea、TaskPlan、Task 的前置蓄水区 |
| active | Pitfall / 踩坑(23) | 承接已解决、已验证且具有复用价值的踩坑经验 |

## 6. 集合关系

当前工作模型按治理用途分为以下关系组：

| 关系组 | 对象 | 说明 |
|---|---|---|
| 工作主链路 | WorkArea(24)、TaskPlan(27)、Task(26)、SubTask(28) | 工作域承接长期范围；任务计划承接一次目标和人类确认；Task 和 SubTask 承接 AI 执行 |
| 输入和分流 | Memo(25) | Memo 承载未任务化但有价值的信息；项目身份和管辖清单不作为工作对象，由 `LDVH-GOVERNED-PROJECTS.yaml`、项目文档或相关事实源承接 |
| 决策和经验 | ADR(21)、Pitfall(23) | ADR 承载已确认决策；Pitfall 承载可复用经验 |
| 变更记录 | Change(22) | 承载事实源变更记录，优先与 Git commit 事实对齐 |
| 字段或模板承载概念 | Dependency(33)、Risk(34)、Artifact(35)、Checklist(36) | 暂不作为独立工作模型，先由现有对象字段、模板、内容格式或产物路径承接 |
| 文档承载概念 | Roadmap(37) | 暂不作为 YAML 工作模型，先由 Markdown 文档或规划入口承接 |

集合关系只说明对象在集合中的定位，不替代具体对象关系规则。具体对象之间可引用、可阻塞、可关闭或可验收的规则，应由对应具体工作模型规范定义。

## 7. 落地检查输入

后续重新设计的落地检查流程读取本文时，应至少确认：

1. active 工作模型是否均有当前主规范或明确集合状态；
2. active 工作模型的事实实例目录、命名、基础字段、状态机和验收规则是否能从对应主规范读取；
3. removed、deferred-field、deferred-doc 和 reserved 项未被误创建为默认事实源目录；
4. 验证证据、风险判断、依赖关系、产物引用和检查结果应按 Task 字段、内容格式、模板或结果物路径处理；
5. 参考与研究材料或临时参考未被直接当成当前权威规范；
6. Code、Web、Skill、Agent 或适配措施消费工作模型时，引用的是 05、本文和具体工作模型规范，而不是固定机制子文档结构。

本文只提供落地检查输入，不定义初始化、落地检查或审计工作流程；落地检查流程是否存在 active 入口，应查询 40 工作流程集合索引。

集合一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| 编号一致性 | 20-39 编号未重复、未越界，38-39 未绕过 Human Gate 占用 |
| 清单一致性 | 本文登记的文档名和集合状态与 `specs/` 实际文件一致 |

| 集合闸门 | removed 或 deferred 项未被自动创建为独立工作模型 |
| 引用一致性 | 01、03.02、03.03、05 和具体工作模型规范对 20 的引用一致 |
| 边界一致性 | 本文未定义具体字段契约、状态机、实例验收规则或对象特有 Human Gate |
| 落地检查输入 | 后续重新设计的落地检查流程只把 active 工作模型作为默认独立对象输入 |
| 参考与研究材料边界 | 参考与研究材料未直接覆盖 `specs/` 正文区结论 |

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或重排 20-39 编号；
2. 改变某个编号对应的工作模型归属；
3. 将 removed 项恢复为独立工作模型；
4. 将 deferred-field 或 deferred-doc 项升级为独立工作模型；
5. 占用 38-39 保留编号；
6. 改变集合状态的含义；
7. 让本文定义具体字段契约、状态机、实例验收规则或对象特有 Human Gate；
8. 恢复固定机制子文档作为工作模型完整性要求；
9. 将参考与研究材料直接视为当前权威规范。

工作模型集合索引检查至少包括：

| 检查项 | 标准 |
|---|---|
| 索引范围 | 已声明 20-39 编号范围 |
| 文档清单 | 每个编号的文档名、类型、集合状态和定位清晰 |
| 状态边界 | removed、deferred-field、deferred-doc 和 reserved 未被误当成 active 工作模型 |
| 编号稳定性 | 处理顺序不改变编号 |
| 规则边界 | 未承载具体对象字段、状态机或行动流程 |
| 落地检查输入 | 已说明后续重新设计的落地检查流程如何消费本文 |
| Human Gate | 编号、状态、升级、降级和恢复场景已声明 Human Gate |
