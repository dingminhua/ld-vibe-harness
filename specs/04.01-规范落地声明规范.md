# 规范落地声明规范

> 创建日期：2026-06-13
> 所属主文档：`specs/04-规范落地与环境适配基础规范.md`
> 关系：专题子文档
> 定位：定义正式规范如何声明自己的落地要求
> 适用范围：规范落地要求类型、声明字段、触发条件、后续消费关系
> 上位依据：`specs/04-规范落地与环境适配基础规范.md`、`specs/02-术语规范.md`、`specs/03.01-规范文档规范.md`
> 相关规范：`specs/04.02-LDVH能力资产与落地保障规范.md`、`specs/04.03-环境入口适配与部署规范.md`

本文定义 specs 如何声明“我需要被怎样落地”。本文不决定具体能力资产、不定义环境入口、不记录部署结果。

---

## 1. 本文解决的问题

正式规范不能只描述规则本身，还应在需要时声明这些规则如何被 AI、Code、Web、Human Gate、环境适配和部署检查看见和消费。

04.01 解决的问题是：规范作者如何表达落地要求，使 04.02 能判断需要哪些 LDVH 能力资产和能力组合来保障落地。

---

## 2. 声明边界

规范落地声明只回答：

1. 当前规范有哪些落地要求；
2. 这些要求属于哪种类型；
3. 哪些后续能力或流程需要消费这些要求；
4. 这些要求变化时应触发哪些同步检查。

规范落地声明不得直接声明某个环境入口已经部署完成，不得记录用户本地状态，不得把候选保障机制写成已实现能力。

---

## 3. 落地要求类型

| 类型 | 含义 | 后续消费 |
|---|---|---|
| 上位约束承接要求 | 本规范需要被其它规范、流程或实现遵守 | 04.02、目录索引、Code 引用检查 |
| 入口可见要求 | AI 或 Human 必须能在执行时定位本规范 | Rules 资产、薄引用、Web 展示 |
| 流程复用要求 | 本规范需要形成可复用 SOP 或检查流程 | Skill 资产、工作流程、Command 包装 |
| 子 Agent 思考要求 | 本规范涉及独立审查、分角色判断或复杂争议 | Agent 资产、主控多视角审查 |
| 确定性执行要求 | 本规范存在可机械检查、解析、聚合或验证的规则 | Code、测试、CI、命令验证 |
| Human 交互要求 | 本规范涉及确认、授权、验收或高风险选择 | Human Gate、Web、对话确认 |
| 生命周期触发要求 | 本规范变化后或相关事件发生时需要触发检查 | Hook 资产、CI、手动检查 |

---

## 4. 声明字段

规范落地要求应使用稳定表格或等价结构表达，至少包含：

| 字段 | 必填 | 含义 |
|---|---|---|
| 落地要求 | 是 | 要求类型 |
| 要求内容 | 是 | 需要被落地的具体内容 |
| 保障机制 | 是 | 候选保障方向，不等于最终实现或已部署状态 |
| 同步类型 | 是 | 文档、Code、Web、流程、Human Gate 或环境部署同步 |
| 触发条件 | 是 | 何时需要复检或同步 |

保障机制字段只表达后续应考虑的保障方向。具体能力资产和能力组合由 04.02 判断；具体环境入口适配、部署和适配检查由 04.03 定义。

---

## 5. 类型选择规则

1. 如果规范必须被 AI 首轮读取或执行前定位，应声明入口可见要求；
2. 如果规范中存在重复执行步骤，应声明流程复用要求；
3. 如果规范需要独立视角、争议审查或并行分析，应声明子 Agent 思考要求；
4. 如果规范可被解析、校验或测试，应声明确定性执行要求；
5. 如果规范涉及授权、确认、验收或高风险选择，应声明 Human 交互要求；
6. 如果规范变化后必须触发检查，应声明生命周期触发要求；
7. 如果规范是其它规范或实现的上位约束，应声明上位约束承接要求。

---

## 6. 后续消费关系

| 后续位置 | 消费本文的方式 |
|---|---|
| 04.02 | 根据落地要求类型选择 LDVH 能力资产和能力组合 |
| 04.03 | 在环境入口中部署和检查 04.02 选定的能力资产 |
| 07 Code | 将可机械检查的落地要求实现为确定性检查 |
| 08 Web | 将 Human 需要看见的要求展示为派生视图 |

---

## 7. 规范落地要求

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 正式规范声明落地要求时应使用本文定义的类型和字段 | 本文、04.02、Code 检查 | 规范治理 | 落地要求类型或字段变化时 |
| 入口可见要求 | AI 修改或阅读正式规范时应能定位本文 | Rules 资产、04 父规范、目录索引 | AI 执行入口提示 | 04.01 文件名、定位或字段变化时 |
| 确定性执行要求 | Code 应能检查落地要求表的基本结构和引用关系 | Code、测试、人工检查 | 校验实现 | 字段稳定后 |
| Human 交互要求 | 新增落地要求类型或改变现有类型语义前应暂停确认 | Human Gate | 规范治理确认 | 要求类型、字段或适用边界变化时 |

---

## 8. Human Gate 与检查要求

以下情况必须评估 Human Gate：

1. 新增或删除落地要求类型；
2. 改变落地要求字段含义；
3. 将保障机制字段解释为已部署状态；
4. 将环境适配或个人环境要求写入本文。

检查要求：

| 检查项 | 标准 |
|---|---|
| 字段完整 | 落地要求表包含要求内容、保障机制、同步类型和触发条件 |
| 类型准确 | 落地要求类型属于本文定义范围 |
| 不越界 | 未声明环境部署完成或用户本地状态 |
| 可追溯 | 保障机制能由 04.02、04.03、07、08 或 Human Gate 承接 |
