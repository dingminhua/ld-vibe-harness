## 1. 价值判断

本文存在的价值，是让 specs 成为 AI 可快速定位、Code 可稳定解析、Human 可裁决审核的规则事实层。

本文承接 `specs/00-理念与构成.md` 的价值门和 `specs/01-保障与承接.md` 的保障承接链路，按以下顺序服务：

| 服务对象 | 本文如何服务 |
|---|---|
| AI 第一 | 固定正文入口、明确权威、归口、范围、规则、保障、验证和停止条件，减少 AI 猜测。 |
| Code 第二 | 通过 identity block、固定章节、显式路径和附件字段表提供可解析入口。 |
| Human 第三 | 把价值判断、Human Gate 和不可自动判断事项留给 Human 裁决。 |

本文不以“写得完整”为目标，而以“能被 AI 正确使用、能被 Code 支撑定位、能被 Human 审核”为目标。

正式 spec 必须说明自身为什么存在、减少 AI 哪类负担、如何承接 00 的价值门。不能说明价值的内容，不应进入正式 spec。

价值判断只说明本文服务哪些 00 价值、减少哪类 AI 负担、为什么值得成为规范；不得重写 00 的价值门，不得把本地价值判断升级为新的上位价值。

## 2. 权威依据

本文的上位依据是 `specs/00-理念与构成.md` 和 `specs/01-保障与承接.md`。

本文不得重定义 00 的存在理由、AI 第一服务对象、构成要素、价值门或最高裁决口径。若本文与 00 冲突，以 00 为准。

本文不得重定义 01 的保障需求、消费时机、承接机制、receipt、evidence、diagnostic 或缺口分流基础语义。若本文结构规则与 01 的保障承接规则冲突，应回到 00、01 和 Human Gate 判断。

00 作为根规范，不受本文固定章节的反向约束。00 应尽量遵循本文的可定位、可解析、可验证原则，但可以因其根规范性质豁免固定章节顺序和完整章节清单。

正式 spec 必须声明自身权威依据。权威依据用于回答：

1. 本文承接哪些上位规范；
2. 本文不能重定义哪些上位判断；
3. 冲突时应回到哪一层处理。

Code 可以读取 `basis` 字段和正文路径，但不能替规范作者判断权威承接是否合理。权威判断必须在正文中成立。

## 3. 归口边界

本文归口定义 specs 的写作、引用、附件、迁移、修改、审核和 Code 解析入口规则。

归口边界用于回答：本文有权定义什么，不能把什么内容反向定义成上位规则。

正式 spec 必须声明自身归口边界。归口边界应使用正向定义，不使用无限排除清单。

推荐表达方式：

```text
本文归口定义 X。
Y 若需要规则，应回到对应规范承接。
下游材料不得反向定义本文规则。
```

附件、Code、行动指南、测试、review、迁移材料和对话记录不得反向定义 specs 正文规则。若下游材料发现规则缺口，应回到对应 spec 正文吸收。

Code、review、迁移材料、测试输出、行动指南和对话记录不得输出或暗示 `approved`、`allowed`、`unblocked`、`accepted risk` 等授权语义。授权、放行和风险接受只能来自正文规则允许的 Human Gate 或明确的上位规范。

## 4. 适用范围

本文适用于：

1. `specs/` 中的正式规范正文；
2. 被正式规范正文授权的附件；
3. 正式规范的新增、迁移、修改、审核和解析；
4. Code 对 specs 的结构读取、诊断、索引和行动指南输入生成。

正式 spec 必须声明自身适用范围。适用范围用于回答：本文规则用在哪些对象、行动或文档上。

适用范围不负责声明关系索引、附件清单、目录、读取计划或 Code 覆盖状态。这些内容能由 Code 从 identity block、路径、显式引用和 Markdown 结构派生时，不应在正文中手写罗列。

## 5. 本地规则

### 5.1 本地规则职责

正式 spec 的正文必须包含本地规则。

本地规则只写本文相对上位规范新增、细化或例外的内容，不重复上位规范全文。

正式 spec 的 `5. 本地规则` 必须使用 `### 5.x` 专题小节区分规则簇。第 5 章存在多个规则簇、表格、附件边界、Code 派生边界或角色索引边界时，不得只堆叠在 `## 5. 本地规则` 下。

`5.x` 小节标题应表达规则职责，不得使用目录式、过程式或证据式标题。`5.x` 小节只服务第 5 章的可读性和可定位性，不新增固定章节，不改变 10 个固定章节闭集。

### 5.2 固定章节入口

所有正式 spec 必须具备以下固定正文入口：

| 顺序 | 固定章节 | 职责 |
|---|---|---|
| 1 | 价值判断 | 说明本文为什么存在，是否服务 00 的价值门，减少 AI 哪类负担。 |
| 2 | 权威依据 | 说明本文依据哪些上位规范，冲突时回到哪里。 |
| 3 | 归口边界 | 说明本文有权定义什么，不能反向定义什么。 |
| 4 | 适用范围 | 说明本文规则适用于哪些对象、行动或文档。 |
| 5 | 本地规则 | 写本文新增、细化、例外的规则。 |
| 6 | 保障措施 | 说明为了让规则被遵守，需要哪些机制。 |
| 7 | 验证方法 | 说明如何检查规则是否被满足。 |
| 8 | Human Gate | 说明哪些事项必须由 Human 判断、授权或接受风险。 |
| 9 | Stop Conditions | 说明 AI 必须暂停的触发条件。 |
| 10 | 待补齐事项 | 收束未闭合问题、后续规范和 Code 缺口。 |

固定章节是 AI 快速定位和 Code 稳定解析的入口。章节标题应保持一致；章节内部可以使用自然语言、表格、列表或专题小节自由展开。

除 00 外，正式 spec 必须遵守本文固定章节要求。若 00 的结构无法支撑 AI 快速定位、Code 基础解析或 Human 价值裁决，应优先修改 00 本身，而不是用下位规范反向解释 00。

### 5.3 固定章节职责闭集

固定章节职责由本文定义。下位规范只能实例化固定章节，不得通过本地规则、保障措施、验证方法、附件或 Code 输出改变固定章节职责。

固定章节职责闭集：

| 固定章节 | 只负责 | 不负责 |
|---|---|---|
| 价值判断 | 说明本文为什么存在、服务哪些 00 价值、减少 AI 哪类负担。 | 不重写 00 价值门，不写具体规则细节。 |
| 权威依据 | 说明本文承接哪些上位规范、冲突时回到哪里。 | 不定义本文管什么，不处理具体规则内容。 |
| 归口边界 | 说明本文有权定义什么、相邻高风险归口在哪里。 | 不写无限排除清单，不替相邻规范定义规则。 |
| 适用范围 | 说明本文规则适用于哪些对象、行动或文档。 | 不手写目录、关系索引、读取计划或 Code 覆盖状态。 |
| 本地规则 | 写本文新增、细化、例外的规则。 | 不重复上位规范全文，不承载过程证据。 |
| 保障措施 | 说明为了让规则被遵守需要哪些机制。 | 不记录一次性执行结果，不写全量审计清单。 |
| 验证方法 | 说明如何检查规则是否被满足。 | 不声明当前已经通过，不把 Code 诊断升级为授权。 |
| Human Gate | 说明必须由 Human 判断、授权或接受风险的事项。 | 不写 AI 自行放行条件。 |
| Stop Conditions | 说明 AI 必须暂停的触发条件。 | 不替 Human 作出暂停后的裁决。 |
| 待补齐事项 | 收束影响后续规范、Code、对象、验证或迁移的未闭合事项。 | 不写泛泛优化愿望，不隐藏新规则。 |

自由章节不得替代固定章节。需要扩展专题时，应放入对应固定章节内部，优先放入 `5. 本地规则`、`6. 保障措施`、`7. 验证方法` 或 `10. 待补齐事项`。

### 5.4 附件与显式引用边界

正式 spec 必须包含 `ldvh_spec` identity block。字段闭集见 `specs/attachments/02.Att.01-规范身份字段表.md`。

附件必须包含 `ldvh_attachment` identity block。字段闭集见 `specs/attachments/02.Att.05-附件身份字段表.md`。

附件只是正文授权的附属内容。允许进入附件的内容包括字段闭集、枚举、纯表、数据矩阵和正文明确授权的机器契约。附件不得承载上位原则、核心规则、行动流程、Human Gate、大段解释、迁移过程、可由 Code 生成的目录、关系图、检查清单或读取路线。

引用关系必须显式写在 identity block、正文路径或正文引用中。关系类型见 `specs/attachments/02.Att.03-引用关系类型表.md`。

### 5.5 角色索引与 Code 派生边界

`role_sections` 是固定章节的索引投影，不是第二规则事实源，也不是绕过固定章节的例外机制。当前 candidate 阶段允许人工声明 `role_sections`，只作为 Code 尚未稳定推导前的过渡索引；人工声明不得与固定章节冲突，不得新增固定章节之外的规则职责，不得覆盖正文标题。Code 能稳定推导后，`role_sections` 应由 Code 生成或诊断，不再作为人工必填规则字段。

不得手写全量目录作为规范事实层。目录、关系图、读取计划、覆盖诊断和索引应由 Code 从 Markdown 文件、identity block 和显式引用生成。

正文只写需要规范作者判断的规则、边界、方法和门禁。Code 可以稳定派生的内容，不应作为固定章节或正文清单手写罗列。

| 内容 | 是否应固定成章节 | 处理方式 |
|---|---|---|
| 关系索引 | 否 | 由 Code 从 `parent_spec`、`basis`、`related_specs`、路径引用和 Markdown 结构生成。 |
| Code 覆盖 | 否 | 作为验证诊断、review 收据或待补齐事项处理，不成为独立规则章节。 |
| 规则来源 | 否 | 正式 spec 正文本身就是规则本体；附件、Code、review、迁移材料和对话记录不得反向改写正文。 |
| 附件清单 | 否 | 由 Code 从附件 identity block、`parent_spec`、`related_specs` 和正文引用生成。 |
| 目录 | 否 | 由 Code 从文件路径、标题和 Markdown 结构生成。 |
| 关系图 | 否 | 由 Code 从显式引用和 identity block 生成。 |
| 读取计划 | 否 | 由 Code 从固定章节、`role_sections`、上位依据和显式引用生成。 |
| 覆盖诊断 | 否 | 由 Code 或 review 输出，不进入正文冒充规则。 |

## 6. 保障措施

保障措施用于回答：为了让本文规则被遵守，需要哪些机制。

正式 spec 必须说明自身规则依赖哪些保障措施。保障措施可以包括：

1. 固定章节入口；
2. 第 5 章 `5.x` 专题小节入口；
3. identity block 字段闭集；
4. 附件授权边界；
5. 显式路径和引用；
6. AI 修改顺序；
7. Code 结构诊断；
8. Human Gate；
9. review 收据证据；
10. 待补齐事项回写。

保障措施必须遵守 01 的保障与承接边界。保障措施不记录某一次执行结果。一次性检查结果、测试输出、review 记录和迁移证据应留在对应过程材料中，不进入正文冒充规则。review 收据只能证明某次审核或检查发生过，不能授权、放行、接受风险或改变正文规则。

若某个规则提出了新的保障需求，而当前没有机制支撑，正式 spec 必须按 01 判断 blocker、warning、follow-up 或 unverifiable，并写入对应承接位置；不得只写入 `10. 待补齐事项` 后声称已经落地。

## 7. 验证方法

验证方法用于回答：如何检查本文规则是否被满足。

正式 spec 必须说明自身规则的验证方法。验证方法应区分：

| 验证主体 | 职责 |
|---|---|
| AI | 判断价值、权威、归口、适用范围、本地规则和停止条件是否自洽。 |
| Code | 检查 identity block、固定章节、路径、显式引用、附件字段和可解析结构。 |
| Human | 裁决价值冲突、边界争议、风险接受和无法自动判断的问题。 |

验证方法只定义检查口径，不承诺当前已经通过。

Code 可检查项不应被手写成固定正文清单。Code 覆盖状态应由 Code 诊断、review 收据或待补齐事项承接。正文只定义哪些检查有意义、检查失败时如何处理。

当验证无法稳定完成时，AI 必须说明不可验证原因，并把缺口回写到 `10. 待补齐事项` 或对应过程记录。

本文自身的最小自检口径：

| 检查对象 | 方法 |
|---|---|
| 固定章节 | 本文必须具备 10 个固定章节，且顺序一致。 |
| 第 5 章小节 | 本文第 5 章必须使用 `### 5.x` 专题小节区分规则簇；下位正式 spec 的第 5 章也应按本文要求可定位。 |
| 章节职责 | 本文每章不得承载职责闭集之外的核心规则。 |
| 00 豁免 | 本文只能豁免 00，不能让其他正式规范逃离固定章节。 |
| Code 派生边界 | 本文不得把目录、关系图、读取计划、覆盖诊断或索引作为手写事实层。 |
| 保障措施 | 本文提出的结构规则必须有对应保障措施或进入待补齐事项。 |
| 验证方法 | 本文提出的结构规则必须说明 AI、Code 或 Human 如何检查。 |
| Human Gate | 本文涉及上位价值、结构硬门或风险接受时必须交还 Human。 |
| Stop Conditions | 本文发现自身不满足固定章节或职责闭集时，AI 必须先暂停修正本文。 |

## 8. Human Gate

Human Gate 用于回答：哪些事项必须由 Human 判断、授权或接受风险。

以下情况必须进入 Human Gate：

1. 修改 00 的价值门、AI 第一对象或构成要素；
2. 修改 01 的保障承接基础规则；
3. 修改 02 的固定章节、权威规则、归口规则或附件边界；
4. 下位规范试图反向定义上位规范；
5. AI 无法判断价值冲突、归口冲突或适用范围冲突；
6. Code 诊断结果与正文判断冲突；
7. 需要接受不可验证、不可回滚或影响后续体系结构的风险。

Human Gate 不是 AI 自行通过的条件。AI 可以提出判断、证据和建议，但不得替 Human 完成裁决。

Human Gate 的输出必须回指到正文规则、Human 明示决定或待补齐事项。review 收据、Code 诊断、测试结果和行动指南不能替代 Human 的授权、放行或风险接受。

## 9. Stop Conditions

Stop Conditions 用于回答：AI 什么时候必须暂停，不能继续按惯性修改。

出现以下情况时，AI 必须暂停并报告：

1. 发现本文或下位规范与 00 价值门冲突；
2. 发现本文或下位规范与 01 保障承接基础规则冲突；
3. 发现固定章节缺失、改名或被自由章节替代；
4. 发现规则被附件、Code、review、迁移材料或对话记录反向改写；
5. 发现 Code 可派生内容被正文手写罗列，并产生维护分叉风险；
6. 发现新增规则没有对应保障措施、承接机制或验证方法；
7. 发现需要 Human Gate 的事项被 AI 当作普通编辑继续推进；
8. 发现同一规则在多个位置重复定义且无法判断权威来源。

暂停后，AI 应说明触发条件、涉及文件、可选处理方案和建议归口，不得直接越过停止条件继续修改。

Stop Conditions 触发后，AI 不得自行恢复推进，除非本文或上位规范已经定义了非 Human 的分流路径。每次暂停至少应说明：

1. 触发条件；
2. 停止范围；
3. 是否进入 Human Gate；
4. 需要交还的证据；
5. 后续承接位置。

## 10. 待补齐事项

待补齐事项用于承接未闭合问题，避免缺口留在对话、临时 review 或迁移过程里消失。

待补齐事项必须是影响后续规范、Code、对象、验证或迁移的体系缺口；不得写成当前任务清单、泛泛优化愿望或隐藏的新规则。
