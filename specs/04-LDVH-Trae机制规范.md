## 一、本文解决的问题

本文解决 LD Vibe Harness 如何使用 Trae Rules、Skill、Agent、MCP、Tool Calling、斜杠命令和上下文工具等 Trae 原生机制，以及这些机制在 LDVH 中如何命名、分层、触发、受 Human Gate 约束并按事实源边界回写的问题。

Trae 原生机制提供 AI 协作入口和工具能力，但机制本身不自动保证项目工程可控。LDVH 的职责，是把这些原生机制纳入 Git 文件事实源、Harness 生产对象和 Harness 行动模型的治理闭环。

## 二、与 00 总纲的关系

00 定义 Trae Solo 环境机制是 LD Vibe Harness 的五类构成要素之一，并明确 LDVH 对 Trae Solo 环境机制的态度是利用、不重新定义、规范不替代和适配不绑定。

本文承接 00 的该判断，专门定义 Trae 原生机制在 LDVH 中的使用边界、事实源边界、Human Gate 和子文档分工。00 只保留五类构成要素和基础规范索引，不重复维护 Rules、Skill、Agent、MCP、Tool Calling、斜杠命令或上下文工具的具体治理规则。

## 四、LDVH 与 Trae 原生机制的关系

Trae 原生机制是 LDVH 可利用的协作底座。LDVH 不重新定义 Trae 官方能力，不替代 Trae 的产品说明，也不保证 Trae 机制的运行行为始终稳定不变。

LDVH 对 Trae 原生机制的治理原则如下：

1. **利用不重新定义**：LDVH 定义如何使用 Trae 原生机制，不重新定义 Trae 官方机制本身。
2. **规范不替代**：LDVH 的机制规范是 Trae 使用约束和最佳实践，不替代 Trae 官方文档。
3. **适配不绑定**：LDVH 适配 Trae Solo 的能力模型，但不假设 Trae 是唯一可用 AI 编程环境。
4. **机制不等于事实源**：Rules、Skill、Agent、MCP、Tool Calling、斜杠命令、上下文工具和 Trae `.trae/specs/` 都是执行机制、过程资产或协作入口，不能直接成为最终事实源。
5. **稳定事实必须回写**：上述机制产生的稳定结论、规则、任务、证据、决策或变更，必须写入 specs/、ldvh-base/、docs/ 或其他对应 Git 文件事实源后才成为 LDVH 稳定事实。

| 机制 | Trae 侧定位 | LDVH 使用方式 | 权威规则 |

| Skill | 可复用专业能力说明书 | 承载可复用 SOP、标准化输入输出和轻量写入流程 | `04.02-Skill机制规范.md` |
| Agent | 专业智能体和工具组合 | 承载独立上下文、结论隔离、并行委派或不同工具权限场景 | `04.03-Agent机制规范.md` |
| MCP | 外部工具和服务协议层 | 为 Agent 或主流程提供可调用工具能力 | `04.04-MCP与工具调用机制规范.md` |

| 斜杠命令 | Trae 对话中的过程控制命令 | 可作为计划、调试、解释、继续和清理上下文的过程入口 | `04.04-MCP与工具调用机制规范.md` |

| Trae `.trae/specs/` | Trae Plan/Spec 过程资产 | 可作为过程输入和任务清单，不自动替代 LDVH 正式事实源 | `04.04-MCP与工具调用机制规范.md` |

## 六、参考资料处理原则

本次 04 系列建设使用以下资料作为对照输入：

1. `trae-pm-kit/specs/08` 系列：作为 PM Kit AI 协作体系来源参考，只迁移通用机制判断，不迁移 PM Kit 专属对象、路径、标准技能清单或推荐 Agent 清单。
2. `ld-vibe-harness/specs-v2/11` 系列：作为 LDVH 迁移参考，只吸收适配 LDVH 五类构成要素和事实源边界的内容。
3. `references/01`、`02`、`04`、`05`、`06`、`07`：作为 Trae 官方机制和外部工具用法参考，不直接成为强制规则。

多角色讨论资料和自建 Agent 清单资料在 04 正式规范中只作为参考依据，不创建具体多角色矩阵、不创建 LDVH 推荐自建 Agent 清单，也不表示已创建任何 Trae Agent。

## 七、事实源回写原则

Trae 机制运行过程中产生的信息按以下规则处理：

1. 临时计划、命令输出、工具结果、Agent 分析、MCP 返回、上下文工具注入和 Trae `.trae/specs/` 内容，默认都是过程信息。
2. 过程信息只有满足 `specs/03-事实源边界与承载规范.md` 的回写要求，并写入对应 Git 文件事实源后，才成为稳定事实。
3. 规则类事实应写入 specs/ 或 `.trae/rules/` 对应规则文件。
4. 结构化生产对象事实应写入 `ldvh-base/` 对应对象目录。
5. 管辖项目资料、报告或审计结果应写入 docs/。
6. 外部资料和第三方参考应写入 references/，不得直接作为 LDVH 强制规则。
7. 工具、Skill 或 Agent 的输出不得与 Git 文件事实源并行维护同一稳定事实。

## 八、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变 04 系列规范编号和职责分工；
2. 创建、修改、删除或启用/禁用规则、Skill、Agent 或项目级 MCP 配置；
3. 调整 Agent 工具权限、MCP Server 权限、可写文件范围或网络访问范围；
4. 将外部参考、Trae 过程资产、MCP 输出、Agent 输出或工具缓存提升为稳定事实；
5. 在 04 正式规范中新增具体 LDVH 标准 Skill 清单、自建 Agent 推荐清单或多角色矩阵；
6. 改变 Trae 机制与 LDVH 事实源边界、生产对象或行动模型之间的职责关系。

04 系列一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| 机制边界 | 未重新定义 Trae 官方能力 |
| 子文档分工 | Rules、Skill、Agent、MCP 与工具调用分别进入对应子文档 |
| 事实源回写 | 稳定事实必须回写 Git 文件事实源 |
| 参考边界 | 外部参考和 PM Kit 资料未直接成为 LDVH 强制规则 |
| PM Kit 去专属化 | 未迁移 PM Kit 专属路径、标准 Skill 清单或推荐 Agent 清单 |
| Human Gate | 高影响机制变更已识别并说明确认要求 |
