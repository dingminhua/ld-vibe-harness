## 1. 本文解决的问题

本文定义多角色思考工作流程。多角色思考是 AI 在面对复杂变更、复杂决策、跨模块影响、规范治理、协作机制调整或高风险操作前，按多个专业视角分别分析、汇总分歧、识别风险、提出建议动作和 Human Gate 判断的行动。

多角色思考工作流程统一定义何时进入、读什么、如何选择轻量模式或多角色子 Agent 模式、如何使用可调用 Agent 容器注入角色参数、如何输出、如何回写稳定事实和如何审计。

本文是多角色思考工作流程的完整主文档。Rules、Skill、Agent、Tools、Web 和 Contract 相关历史机制文件仅作为迁移前过渡资料，按需承接对应机制实践，不重新定义多角色思考工作流程。

## 3. 行动定位与适用场景

### 3.1 行动定义

多角色思考是面向复杂问题的分析增强行动。它通过多个专业视角分别分析同一输入，降低单一视角遗漏风险，帮助 AI 和人识别影响范围、风险等级、分歧点、建议执行顺序、需要同步的事实源和 Human Gate。

多角色思考不是独立事实源，不替代 ADR、Task、Memo、Risk、Evidence、Change 或规范正文。它的输出默认是过程分析；只有按事实源边界写回对应 Git 文件后，才成为稳定事实。

### 3.2 适用场景

出现以下情况之一时，应考虑进入多角色思考：

1. 用户明确要求从不同角色、不同专业视角或多角色角度分析；
2. 规范、规则、Skill、Agent、工具或工作流程变更需要评估跨模块影响；
3. 技术选型、架构调整或工具设计需要同时评估性能、安全、可维护性、验证和治理边界；
4. 需求变更会影响产品、前端、后端、数据、测试、发布、治理或 AI 协作多个维度；
5. 需要判断某个输出应分流为 Task、Memo、ADR、Risk、Evidence、Change 或 docs 报告；
6. 需要在执行高影响变更前识别 Human Gate 和证据要求；
7. 主上下文判断存在明显不确定性，且单一视角可能遗漏重要风险。

### 3.3 不适用场景

以下情况通常不应进入多角色思考：

1. 简单问答或单文件小改，单一主上下文即可处理；
2. 用户已经明确给出决策并只要求执行低风险操作；
3. 问题已满足 Task 准入条件且不需要多视角分析，应直接进入对应 Task 行动；
4. 只需要确定性字段校验，应使用Tools 辅助或对象审计；
5. 已经由具体工作流程定义了更直接的执行流程，且没有复杂分歧或跨角色影响；
6. 用户明确要求不要进行额外分析。

## 4. 准入条件

多角色思考行动的准入条件如下：

1. 存在一个需要分析的明确主题、变更、决策、风险或问题；
2. 至少存在两个以上有意义的分析视角；
3. 分析结论可能影响后续执行、规范、对象、工具、协作机制或 Human Gate；
4. 输入材料能够追溯到用户输入或 Git 文件事实源；
5. AI 能够明确说明本次分析是过程分析，还是需要回写为稳定事实。

不满足准入条件时，应退回主上下文直接回答、询问用户补充输入，或分流到更合适的行动、Skill、Agent 或Tools 辅助。

## 6. Context 要求

### 6.1 最小 Context

执行多角色思考前，AI 应获得以下最小 Context：

1. 用户提出的分析主题、目标、约束和期望输出；
2. 当前项目 L1 规则和相关工作区规则；
3. 与本次主题直接相关的 specs、ldvh-base、docs、tools、web 或代码文件；
4. `specs/08-工作流程基础规范.md`；
5. `specs/05-Trae-Solo环境规范.md`；
6. 需要判断事实源回写时读取 `specs/04-事实源边界与承载规范.md` 和对应工作模型规范；
7. 需要判断工具协作时读取 `specs/06-Python与Web工具规范.md`。

### 6.2 可选 Context

根据主题复杂度，可增加以下 Context：

1. `specs/evals/` 中与本次主题相关的内部评估文档；
2. 已存在的 Task、ADR、Memo、Risk、Evidence 或 Change 实例；
3. 当前环境中可调用 Agent 容器的能力说明。

可选 Context 只能作为输入材料，不能覆盖当前 specs/ 正式规范，也不能被当作当前项目已经存在对应 Skill、Agent、Tools 或 Web 实体的证据。

## 7. Scenario 识别

### 7.1 进入条件

当用户输入、任务背景或事实源状态满足以下条件之一时，AI 应识别为多角色思考 Scenario：

1. 出现"多角色""不同角色""不同视角""从多个专业角度""多角度""各自说一遍"等明确触发语，或语义等价表述（如"全面分析""各个角度看""换位思考""分别从不同立场"）；
2. 当前变更影响两个以上规范、对象、行动、工具、项目模块或协作机制；
3. 当前任务涉及 Rules、Skill、Agent、MCP、工具、事实源边界或 Human Gate 的职责划分；
4. 当前判断存在高影响风险，且需要安全、治理、验证或架构视角共同审查；
5. 用户要求先分析影响、风险、分歧或执行顺序，再决定是否修改；
6. AI 对执行路径不确定，并判断单一视角不足以安全推进。

触发语匹配原则：本条使用"等"表示非穷举。当用户表述与已列触发语语义等价时，AI 应同样触发多角色思考，不得仅因字面不匹配而跳过。L0 / L1 / L2 Rules 入口摘要受篇幅限制可能只列部分触发语，执行时应以本条完整条件为准。

### 7.2 优先级

多角色思考与其他行动同时匹配时，按以下原则处理：

1. 若用户明确要求多角色分析，优先进入多角色思考；
2. 若已有明确 Task 且只需执行，优先进入 Task 执行行动；
3. 若正在创建或更新对象实例，优先遵守对应对象创建或对象状态更新行动；
4. 若涉及规范、规则、Skill、Agent 或工具变更，先进行多角色思考或治理审查，再执行写入；
5. 若触发 Human Gate，先暂停并请求确认。

### 7.3 降级条件

以下情况应降级为主上下文直接分析或询问用户：

1. 主题不明确，无法选择角色；
2. 没有足够事实源支持分析；
3. 用户只需要简短回答；
4. 分析可能引入无关复杂度；
5. 多角色子 Agent 模式不适用，但轻量模式足以完成。

## 8. 执行流程

### 8.1 选择分析模式

多角色思考分为两种模式：

| 模式 | 说明 | 行为 |
|---|---|---|---|
| 主上下文轻量模式 | 无需独立上下文，AI 在主上下文中依次分析各角色 | AI 在主上下文中按角色分别分析并汇总 |
| 多角色子 Agent 模式 | 需要独立上下文、结论隔离或并行委派 | 主控为每个角色构造独立参数，启动可调用 Agent 容器的多个实例，各实例输出回到主控后统一汇总 |

主控识别到多角色思考场景时，除非对话中已明确要求使用某种模式，否则都必须先说明两种模式的差异，通过 AskUserQuestion 机制向用户呈现选项供其选择启动的模式。两种模式都由主控负责最终汇总。

模式选择属于 AskUserQuestion 承载范围。模式选择完成前，不得启动对应模式的分角色分析；不得先输出完整多角色报告，再在报告末尾用自由文本询问模式选择。

### 8.2 识别变更类型

AI 应先判断分析主题属于哪些类型：

1. 需求 / 产品变更；
2. UI / 前端体验变更；
3. 服务端 / API / 数据变更；
4. 数据 / 模型相关变更；
5. 安全 / 合规变更；
6. 规则 / 规范 / 文档变更；
7. Skill / Agent / AI 协作变更；
8. MCP / 工具链 / 自动化变更；
9. 发布 / 部署 / 关闭变更；
10. 审计 / 复盘 / 流程改进；
11. 通用架构 / 大型重构。

### 8.3 角色定义

角色定义是多角色思考的稳定规范内容，不创建 Role 工作模型，不创建"角色应用场景"工作模型。角色定义应作为 AI、Rules、Agent、Tools 和 Web 可共同引用的结构化契约使用，不应在 Skill、Agent Prompt、工具缓存或 Web 状态中复制维护第二事实源。

本文只定义角色定义的事实源边界和使用原则。角色字段契约、默认角色集合、角色选择输入输出、角色调用参数、角色分析结果和多角色报告结构由 `specs/41.06-Contract.md` 承接。

角色定义使用应遵循以下原则：

1. 角色定义属于 specs 稳定规范，不属于 `ldvh-base/`事实实例；
2. 默认角色集合由 41.06 统一维护，主控按主题和变更类型选择角色；
3. 不为每个角色创建自定义 Agent；角色内容作为运行时参数注入主上下文或可调用 Agent 容器；
4. 不创建独立"角色应用场景"对象；不同用途下的输出结构由 41.06 的契约字段表达。

默认角色集合是稳定基线，不是封闭枚举。AI 应优先从 41.06 默认角色集合中选择角色；当默认角色不足以覆盖本次关键风险、边界或专项问题时，可以声明本次临时职能视角。临时职能仅作为本次运行时分析参数，不创建 Role 事实实例，不自动写入默认角色集合，也不得被后续 AI 当作稳定角色引用。

临时职能如需沉淀为默认角色，必须说明复用价值、触发场景、与既有角色差异和契约字段影响，并经 Human Gate 确认后修改 41.06。

角色定义的事实源边界、角色独立性原则和 Tools / Web 消费约束详见 `specs/41.06-Contract.md` §2。

### 8.4 选择角色

角色选择规则由 `specs/41.06-Contract.md` §6 统一定义，包括选择优先级、必选角色触发条件和角色数精简规则。主控按 41.06 §5 RoleSelectionInput 构造输入，按 §6 RoleSelectionOutput 输出选择结果。

主控应在启动子 Agent 前输出 RoleSelectionOutput，让用户确认角色选择是否合理。RoleSelectionOutput 属于自由 Markdown 或结构化报告输出；若只是说明已选角色及理由，可以自由 Markdown 输出。若存在多个角色组合方案、需要用户确认角色范围、需要确认是否补充临时职能或是否接受子 Agent 角色分配，应使用 AskUserQuestion。

### 8.5 分角色分析

每个角色至少输出：

1. 适用性：相关 / 无关；
2. 影响范围：具体模块、文件、接口、对象、行动或流程；
3. 分析结论：该角色视角下的判断；
4. 风险：高 / 中 / 低，并说明原因；
5. 建议动作：需要执行、暂停、确认、回写或补充的具体事项。

### 8.6 汇总对比

AI 应汇总各角色分析，至少包含：

1. 一致结论；
2. 分歧点；
3. 风险汇总；
4. 建议执行顺序；
5. 需要同步的文档、对象、规则、Skill、Agent 或工具；
6. 事实源回写建议；
7. Human Gate 判断。

### 8.7 输出格式

多角色思考输出建议采用以下结构：

```markdown
# 多角色思考报告

## 适用性判断
- 是否进入多角色思考：是 / 否
- 分析模式：主上下文轻量模式 / 多角色子 Agent 模式
- 涉及角色：{角色列表}

## 变更或问题概述
- 主题：{一句话描述}
- 影响范围：{模块 / 文件 / 对象 / 行动 / 项目}

## 各角色分析

### {角色名}
- 适用性：相关 / 无关
- 影响范围：{描述}
- 分析结论：{结论}
- 风险：高 / 中 / 低 — {描述}
- 建议动作：{列表}

## 角色间一致与分歧
- 一致结论：{列表}
- 分歧点：{列表}

## 风险汇总
- 高风险：{列表}
- 中风险：{列表}
- 低风险：{列表}

## 建议执行顺序
1. {第一步}
2. {第二步}

## 事实源回写建议
- 应写回：{文件或对象}
- 不应写回：{过程信息}

## Human Gate
- 是否触发：是 / 否
- 触发原因：{原因}
- 建议确认事项：{列表}
```

## 9. Gate 触发条件

### 9.1 条件 Gate

以下情况触发条件 Gate：

1. 缺少分析主题或输入材料；
2. 需要读取的事实源不存在或无法确认；
3. 角色选择依据不足；
4. 角色参数构造依据不足，无法为多角色子 Agent 模式提供清晰角色边界；
5. 输出需要回写但目标事实源不明确。

条件 Gate 未满足时，AI 应降级、询问用户或暂停，不得继续执行高影响分析或写入。

### 9.2 Human Gate

Human Gate 触发条件统一由 §14 定义。本节不重复列举 Human Gate 条件，避免与 §14 并行维护导致不一致。

## 10. Rules 和 Agent 调度

> 本节对应 08 §4.2 第 8 项"Skill 和 Agent 调度"。因多角色思考不创建 LDVH 版 Skill（见 §10.1），改为 Rules 触发 + Agent 调度。

### 10.1 Rules 触发

多角色思考不需要创建 LDVH 版 Skill。进入多角色思考的触发判断应由 Rules 承接，执行流程由本文承接。

Rules 只做入口提醒：当用户要求多角色、多视角、跨模块影响评估、复杂变更风险审查，或 AI 判断单一主上下文可能遗漏风险时，应进入本文定义的多角色思考工作流程。

Rules 不得复制本文的完整 Scenario、角色定义、执行流程、输出格式或 Human Gate 条款。需要执行时，AI 应读取本文并按本文执行。

### 10.2 多角色子 Agent 模式

多角色子 Agent 模式用于需要独立上下文、结论隔离、并行委派、不同权限边界或大量事实源读取的多角色分析。

多角色子 Agent 模式遵循以下规则：

1. 多角色子 Agent 模式只能在 Rules 入口触发多角色思考后，由主控依据本文和 41.06 契约编排；
2. 主控根据本文角色定义和当前主题选择角色；
3. 主控为每个角色构造独立调用参数，参数应包含角色名、关注点、触发背景、输入事实源、输出格式和边界要求；
4. 主控可使用当前运行环境提供的可调用 Agent 容器启动一个或多个子 Agent 实例，每个实例只承担被注入的角色视角；
5. 当前运行环境提供的可调用 Agent 容器不是 LDVH Tools 辅助层，Tools、Skill、MCP 或脚本不得直接作为多角色子 Agent 流程入口；
6. 同一可调用 Agent 容器可以被并行启动多个实例，每个实例使用不同角色参数；同一轮多角色子 Agent 模式并行启动的子 Agent 实例不得超过 4 个；
7. 多角色子 Agent 输出必须回到主控汇总，不得直接成为事实源；
8. 子 Agent 发现 Human Gate 场景时必须标注，不得自行执行高影响写入；
9. 不为每个角色创建自定义 Agent；角色定义来自本文，作为运行时参数注入；
10. 多角色子 Agent 模式不依赖 `.trae/agents/` 自定义 Agent 文件；角色参数注入规则见 `specs/41.03-Agent.md`；
11. 需要创建、导入、启用、修改或删除 Agent 时，必须按 05 §8 触发 Human Gate。

可调用 Agent 容器是指当前主控能够通过工具接口实际启动的 Agent 类型。本文不维护可调用 Agent 容器清单，不在稳定规范中核验特定 Agent 可用状态，也不把某个环境中的可用 Agent 列表写成稳定规则。

---

## 11. 工具协作适配

多角色思考可使用工具辅助以下工作：

1. 搜索和读取相关事实源；
2. 生成或校验 Context 包；
3. 检查 Markdown 链接、编号、引用和 YAML 语法；
4. 聚合变更影响文件；
5. 准备受控写入候选内容；
6. 展示分歧、风险和 Human Gate 待确认项。

工具不得直接决定角色结论，不得直接调用 AI、Skill 或 Agent，不得将工具缓存或派生视图作为最终事实源。

MCP Server 在多角色思考中的定位：MCP 结果可作为输入材料，但不得直接决定角色结论；提供 AI 推理能力的 MCP Server 返回结果应与工具缓存同等对待，不作为事实源。

---

## 12. 事实源回写要求

多角色思考完成后，应按以下规则判断是否回写：

| 输出类型 | 回写位置 |
|---|---|
| 仅服务当前对话的分析 | 不回写，保留在当前上下文 |
| 需要执行的明确动作 | 创建或更新 Task，位置由 Task 对象规范定义 |
| 有保留价值但暂不任务化的信息 | 创建或更新 Memo，位置由 Memo 对象规范定义 |
| 已确认且长期有效的决策 | 创建或更新 ADR，位置由 ADR 对象规范定义 |
| 已识别的不确定因素 | 创建或更新 Risk，位置由 Risk 对象规范定义 |
| 验证结果或关闭证据 | 创建或更新 Evidence，位置由 Evidence 对象规范定义 |
| 对事实源产生影响的实际修改 | 记录变更（依据 specs/22-Change-变更记录.md） |
| 管辖项目报告或审计结果 | 写入 docs/ 对应报告 |
| 规范或规则正文 | 写入 specs/ 或 `.trae/rules/`，并评估 Human Gate |

未写入权威事实源前，多角色思考报告不能被后续 AI 当作稳定事实引用。

---

## 13. 证据留存要求

多角色思考的证据至少包括：

1. 分析主题和输入来源；
2. 读取的关键事实源；
3. 选择的分析模式及原因；
4. 多角色子 Agent 模式的调用参数、角色边界和隔离说明；
5. 选用角色及选择理由；
6. 各角色结论、风险和建议动作；
7. 汇总结论、分歧和 Human Gate 判断；
8. 若发生写入，记录写入文件、写入原因、验证结果和 Change ID。

---

## 14. Human Gate

### 14.1 必须暂停确认的情况

以下情况必须暂停并请求人类确认：

1. 将多角色思考结论升级为规范、规则、ADR 或长期行动边界；
2. 创建、导入、启用、修改或删除 Agent；
3. 允许多角色子 Agent 模式访问更高权限或写入文件；
4. 依据多角色思考结论修改事实源权威位置；
5. 依据多角色思考结论执行跨项目、高风险或不可自动确认的变更；
6. 创建 LDVH 正式 Skill、Agent、机制实体、实现入口或契约能力；
7. 将运行时临时职能升级为默认角色、修改默认角色集合、修改角色选择契约或改变角色选择规则。

### 14.2 用户确认后的处理

用户确认后，AI 应：

1. 明确记录确认事项；
2. 按对应规范执行写入或创建；
3. 写入后补充 Change 记录（依据 specs/22-Change-变更记录.md）
4. 执行可用检查；
5. 汇报哪些内容已成为稳定事实，哪些仍是建议。

发生冲突时，以本文和上位基础规范为准，历史机制文件应修正为引用或适配本文规则。

## 16. 行动特有检查

检查一次多角色思考执行是否符合本流程时，应确认：

| # | 检查项 | 通过条件 |
|---|---|---|
| 1 | 是否说明进入多角色思考的触发原因 | 输出中包含明确的触发原因描述，且可追溯到 §7 Scenario 识别条件之一 |
| 2 | 是否声明分析模式 | 输出中明确声明"主上下文轻量模式"或"多角色子 Agent 模式" |
| 3 | 是否说明选择该模式的原因 | 轻量模式和子 Agent 模式均需说明选择原因；子 Agent 模式还需说明角色参数和隔离方式；需要用户决策的模式选择通过 AskUserQuestion 承载 |
| 4 | 是否列出读取的关键事实源 | 输出中列出本次分析读取的 specs、ldvh-base、docs 或代码文件 |
| 5 | 是否按角色输出适用性、影响范围、结论、风险和建议动作 | 每个角色输出包含 41.06 RoleAnalysisResult 契约的必填字段 |
| 6 | 是否区分默认角色和临时职能 | RoleSelectionOutput 标注 preset 默认角色和 runtime 临时职能；runtime 临时职能说明边界、默认角色不足原因和是否建议后续沉淀 |
| 7 | 是否汇总一致结论和分歧点 | 汇总中明确区分一致结论和分歧点，不混淆 |
| 8 | 是否给出风险等级和建议执行顺序 | 风险按高/中/低分级，执行顺序有明确步骤编号 |
| 9 | 是否判断事实源回写目标 | 按 §12 回写要求判断每类输出的回写位置 |
| 10 | 是否判断 Human Gate | 按 §14 判断是否触发 Human Gate，触发时暂停请求确认 |
| 11 | 是否避免把过程分析、Agent 输出、工具缓存、临时职能或 Web 状态直接作为稳定事实引用 | 输出中明确标注"本分析为过程分析，未写入权威事实源前不得作为稳定事实引用" |
| 12 | 如发生写入，是否记录写入文件、写入原因、验证结果和 Change ID | 写入后创建 Change YAML，记录写入文件、原因、验证结果和 Change ID |

检查多角色思考工作流程文档是否符合本流程时，应确认本文覆盖 08 §4.2 定义的工作流程标准组成；缺项应说明不适用原因或进入待补齐事项。
