## 1. 价值判断

环境插件是 LDVH 最外层入口，也是多环境架构中唯一需要"每个环境单独写"的部分。如果没有明确的编写行动模板，AI 容易走两个极端：要么把所有逻辑塞进一个巨无霸 shim，要么把 manifest、hooks 配置和 shim 拆得支离破碎，导致后续维护和升级无法追溯。

本文的价值在于：

1. **把"写一个环境插件"从玄学变成可执行步骤**：分析 Hook API → 写三个文件 → 验证触发 → 交还。每一步都有明确的最小产出和检查标准。
2. **把存量升级统一为同一套流程**：stale path 修复、缺失事件补齐、V1→V3 迁移，都走同一套分析→编写→验证→交还的四阶段流程，不另起分支。
3. **明确薄 shim 边界**：所有核心逻辑留在 `code/runtime_adapter.py`，shim 只做 payload 格式翻译。避免每个环境插件各自维护一份规则逻辑。
4. **让安装流程（spec 30）有东西可装**：30 只管"把这个插件装上去并验证触发"，33 管"这个插件怎么写出来的"。两者协作形成完整闭环。

环境插件编写行动主要服务 V1、V2、V3、V4、V6：它让 AI 在动手写文件前先分析目标环境 Hook API 能力，按固定三层结构（manifest + hooks.json + shim）组织产出，在 Gate 处暂停等待 Human 确认，执行本地验证，并在交还时明确文件和下一步。多环境差异数据由附件承接，不在模板正文中重复。

## 3. 归口边界

本文归口定义环境插件编写和更新的步骤组织、四阶段行动、三层文件结构的最小要求和交还边界。

本文不归口定义：
- 具体环境 Hook API 的完整文档（应在目标环境官方文档中查找，差异数据由 `33.Att.01` 承接）
- `runtime_adapter.py` 内部逻辑（归 code 域）
- 插件安装后的验证闭环（归 30）
- Git commit-msg Hook 的编写（Git Hook 是独立层级，与环境插件无关）
- 管辖项目配置契约（归 10）
- 插件市场发布、版本管理和签名流程

本文可以组织"环境分析→编写→验证→交还"的行动顺序，也可以把 Codex 参考标本作为编写时的对照起点；但不得把命令样例、字段定义或 API 参数写成模板规则，不得把标本复制后不改当成新插件，不得把本地语法验证通过写成真实环境触发已验证。

## 4. 适用范围

本文适用于：

1. 为一个尚未有 LDVH 插件的 AI 环境编写新插件；
2. 更新已有插件：修正 stale path（如旧版 `ld-vibe-harness` → 新版 `ld-vibe-harness-v3`）、补齐缺失事件（如只注册了 SessionStart 和 PreToolUse，缺 Stop）、修正 matcher 规则或 shim 逻辑；
3. 审查现有插件是否满足薄 shim 边界（不复制规则、不独立维护校验逻辑）。

用户只是询问概念或边界时，只回答本文和 01 的相关边界，不写入文件、不修改插件。

## 5. 模板定位与来源

本文是 06 之后的正式行动模板，编号为 `33`。它与 30 平行：30 管安装、验证、交还已存在的插件；33 管插件的编写和更新本身。两模板协作但不互相包含。

因此，33 的成败不取决于是否亲自运行每个 Hook 事件，而取决于是否能按 06 的七结构稳定组织编写行动：场景识别、Context 收集、Gate 与 Human Gate、四阶段执行、本地验证、回写和交还。底层 Hook API 细节由目标环境官方文档和 `33.Att.01` 承接；33 必须消费其输出并交还主控 AI 与 Human 判断。

当前最小闭环包括：分析目标环境 Hook API → 按三层结构编写三个文件（manifest、hooks.json、shim）→ 本地静态验证 → 交还给 30 的安装流程。插件市场发布、跨环境批量迁移、插件包签名等需求仍需按来源规则进入 Human Gate。

## 6. 环境插件编写行动边界

### 6.1 插件包三层结构

每个环境插件是一个独立子目录，放在 `hooks/environment-plugins/` 下。每个插件包至少包含三个文件：

| 文件 | 职责 | 规模 |
|---|---|---|
| manifest（`plugin.json` 或等价） | 声明插件元数据、Hook 入口指向 | ~30 行 |
| Hook 事件路由（`hooks/hooks.json` 或等价） | 声明事件列表、matcher、shim 命令路径 | ~70 行 |
| 薄 shim（`.py` 或等价脚本） | payload 格式翻译 → 调 `runtime_adapter.py` → 输出翻译 | ~200–700 行 |

Manifest 必须声明指向包内 `hooks/hooks.json` 的路径字段。Manifest 不得声明 Rules、Skills 或其它非 Hook 能力。

Hook 事件路由必须注册 LDVH 核心三事件：`session_start`（映射到目标环境 SessionStart）、`pre_tool_use`（映射到目标环境 PreToolUse，matcher 覆盖 Write/Edit/Bash）、`completion_claim`（映射到目标环境 Stop）。所有事件的 `command` 字段必须指向包内 shim 脚本。不得添加 LDVH 暂未映射到稳定 runtime 事件的环境事件；matcher 不得覆盖用户非 LDVH 管辖的工具调用。

薄 shim 的唯一职责是 payload 格式翻译：读取目标环境 Hook 载荷 → 解析事件名并映射到 V3 runtime event → 定位 LDVH root → 提取 target_path、tool_name、command_text、cwd → 构造 runtime_adapter 能吃的 payload → 调子进程 → 把输出翻译回目标环境协议。shim 必须指向 `code/runtime_adapter.py`，不得在 shim 内实现校验逻辑。找不到 LDVH root 时必须降级通过（输出 warning 并 exit 0）。只读工具操作（Read、Grep、Glob）默认静默跳过。未映射事件默认静默返回。默认不写事实源。

参考标本：`hooks/environment-plugins/codex-ldvh-v3/`。所有新环境插件以它为范本，但必须按目标环境差异调整 manifest 格式、Hook 事件名、payload 字段提取逻辑和输出协议。

### 6.2 场景分类

| 场景 | 触发条件 | 走向 |
|---|---|---|
| **新增** | 目标环境尚无 `hooks/environment-plugins/<env>-ldvh-v3/` 目录 | 完整四阶段 |
| **更新（stale path）** | 已有目录但 shim/hooks.json 指向旧路径（如 V1→V3） | 轻量四阶段：分析差异 → 只改路径/事件 → 验证 → 交还 |
| **更新（补齐事件）** | 已有目录但 hooks.json 缺少核心事件（如缺 Stop） | 轻量四阶段：分析差异 → 补 hooks.json + shim → 验证 → 交还 |
| **审查** | 用户询问"这个插件怎么写才对" | 只读分析，不写文件 |

### 6.3 四阶段行动

无论新增还是更新，统一使用四阶段行动：

| 阶段 | 名称 | 说明 | 写入边界 |
|---|---|---|---|
| 1/4 | 环境分析 | 查阅目标环境 Hook API 文档，确认支持的事件、payload 格式、插件安装位置、路径解析方式 | 不写入 |
| 2/4 | 编写/更新 | 按三层结构编写或修改文件；更新场景必须先明确差异再动手 | 可写入（经 Human Gate 确认后） |
| 3/4 | 本地验证 | 语法检查、shim 干跑、payload fixture 测试、静态路径检查 | 不写入 |
| 4/4 | 交还 | 输出文件清单、关键决策记录、与标本的差异说明、下一步（进入 30 安装流程） | 不写入 |

### 6.4 环境分析阶段必须确认的问题

在动手写之前，必须先回答：

1. 目标环境支持哪些 lifecycle Hook 事件？至少要有 SessionStart + PreToolUse + Stop 三个才能完整接入。缺事件时必须在交还中标注缺口。
2. 每个事件的 payload 格式（stdin JSON？环境变量？文件路径？命令行参数？）
3. Hook 配置文件的格式（JSON？TOML？YAML？独立文件还是嵌入全局 settings？）
4. Hook 命令中的路径解析方式（`$PLUGIN_ROOT`？`${CODEBUDDY_PLUGIN_ROOT}`？绝对路径？）
5. PreToolUse 是否可阻断？不可阻断时只能 diagnostic-only。
6. 插件/扩展的安装目标位置和激活方式。

目标环境 Hook API 文档不可用时，暂停并交还缺口。

### 6.5 更新场景的增量要求

存量更新时，2/4 编写阶段必须：
- 先列出差异：哪一行要改、改前是什么、改后是什么
- 不改的部分明确声明"保持不变"
- 更新完成后运行本地验证（3/4）确保未引入回归

更新前必须读取目标环境当前已安装的插件，确认需要同步更新的实际安装位置。repo-local 样例包和实际安装位置是两份独立文件，更新 repo 样例包后，实际安装位置需要经 30 的安装流程再次部署。

### 6.6 编写/更新产出边界

Manifest、hooks.json 和 shim 的内容只能包含入口声明、Hook 配置、payload 翻译和资产引用。不得在插件包中写入 specs 规则正文、事实源内容、校验逻辑、Human Gate 判断、commit message 契约、安装配置契约或 runtime adapter 逻辑。

环境差异速查数据（Codex、WorkBuddy 等环境的具体 Hook API 字段和配置契约）回指 `specs/attachments/33.Att.01-环境插件差异速查.md`。编写时以目标环境官方文档为准，`33.Att.01` 仅作速查入口。

## 7. Context、Scenario、Gate 与交还

| 结构 | 最小要求 |
|---|---|
| Context | 读取用户目标（新增还是更新）、目标环境名称、目标环境 Hook API 官方文档（或 `33.Att.01` 速查）、Codex 参考标本、当前 `hooks/environment-plugins/` 目录状态、目标环境已安装插件状态（更新场景），并回指 `specs/01-保障与衔接.md`、`specs/06-行动模板基础规范.md`、`specs/30-安装配置与验证行动模板.md`、`specs/07-Code确定性执行规范.md` 和 `specs/09-测试与验证规范.md`。 |
| Scenario | 用户要求为一个新目标环境编写 LDVH 插件、更新已有插件（修正 stale path、补齐缺失事件、修正 matcher/shim 逻辑）、或审查现有插件是否符合薄 shim 边界时适用；用户只是询问概念或边界时，只回答 01 和本文边界，不写入文件、不修改插件。 |
| Gate | 目标环境 Hook API 文档不可用、不支持至少 SessionStart + PreToolUse、2/4 编写阶段写入前未经 Human Gate 确认、本地验证未通过、发现 shim 中复制了 specs 规则或校验逻辑、路径指向 stale V1/V2 产物但未确认正确 V3 路径、缺少 1/4 环境分析或 4/4 交还阶段时，必须暂停或进入 Human Gate。 |
| 执行 | 先用有限、只读、有证据的环境分析确认目标环境 Hook API 能力；再按四阶段组织环境分析→编写/更新→本地验证→交还。执行阶段只编排来源规则和 Codex 参考标本：环境入口边界按 01，Hook 配置和路径解析按目标环境官方文档，验证按 09，具体命令和输出字段按 Code 实现域文档。新增场景走完整四阶段，更新场景先在 1/4 输出差异清单再进入 2/4。 |
| 验证 | 验证覆盖本地静态验证：JSON 语法检查、Python 语法编译检查、shim 干跑（用 fixture payload 模拟三个核心事件）、静态路径检查（确认所有路径指向 V3 产物）、降级检查（LDVH root 找不到时输出 warning + exit 0）。真实环境触发验证由 30 的安装流程和断点后 lifecycle 验证承接，不属本文范围。本文只列验证入口、不可验证范围和 09.Att.01 字段名；具体验证命令、输出字段和通过标准由 09 和实现域测试承接。 |
| 回写 | 插件编写过程的代码和配置输出落在 `hooks/environment-plugins/<env>-ldvh-v3/` 目录内。环境分析输出（支持事件清单、payload schema、与标本差异点）、编写决策记录（事件映射、matcher 策略、路径解析方式）、验证摘要和残留风险按 03/05/09 分流，不得把过程输出写成事实源或事实对象。更新场景的差异清单是轻量回写，只记录改动行和不变部分，不重写完整文件内容。 |
| 交还 | 交还插件文件清单（哪些文件被创建/修改）、关键决策记录（事件映射选择、matcher 策略、路径解析方式）、与 Codex 标本的差异说明、本地验证结果摘要、不可验证范围（本地验证能覆盖的 vs 真实环境才能验证的）、残留风险、下一步（进入 30 安装流程）、source_refs 和未完成分流。更新场景额外标注实际安装位置是否需要同步更新。阻断时交还阻断原因、缺口证据和建议的下一步。 |

## 8. 保障措施

| 要求 | 机制 | 触发 | 证据 | 缺口处理 |
|---|---|---|---|---|
| 四阶段行动要求 | 编写和更新必须使用四阶段组织当前阶段、已确认决策和未发生事项；由本文、04、06 保障，2/4 写入前必须经 Human Gate 确认 | 编写或更新环境插件时 | §6.3 四阶段记录、Human Gate 确认记录、§7 交还 | 缺少阶段或 Human Gate 时停止写入，回到对应阶段重做 |
| 薄 shim 边界 | shim 只能做 payload 翻译 + 调 runtime_adapter，不得含校验逻辑；由本文 §6.1 和 Code review 保障 | 编写/更新 shim 时 | shim 源码审查、无独立规则逻辑 | 发现复制规则逻辑时重写为 shim-only |
| 三事件最小集 | 每个环境插件必须注册 SessionStart + PreToolUse + Stop；由本文 §6.1 保障 | 编写/审查 hooks.json 时 | hooks.json 事件清单、本地验证通过 | 缺事件时在交还中标注、不声明完整 |
| stale path 检测 | 更新场景必须先读实际安装位置和 repo sample，确认所有 path 引用；由本文 §6.5 保障 | 存量更新时 | 差异清单、路径验证通过 | path 不明确时暂停 |
| 读操作跳过 | PreToolUse shim 必须检查是否为只读操作（Read/Grep/Glob），只读操作静默跳过；由本文 §6.1 和 Codex 标本保障 | PreToolUse 触发时 | shim 中读操作判断逻辑 | 写操作误判为只读时修复 shim |
| 降级通过 | 找不到 LDVH root 时 shim 必须输出 warning 并 exit 0，不阻断；由本文 §6.1 保障 | LDVH root 解析失败时 | warning diagnostic + exit 0 | 反向：root 存在却降级时修复 shim |
| 环境文档优先 | 编写前必须以目标环境官方文档为准；`33.Att.01` 只作速查，不是完整 API 文档；由本文 §6.6 保障 | 编写新环境插件时 | 环境分析阶段引用的官方文档链接 | 跳过文档直接抄 Codex 标本时暂停 |
| 验证交还要求 | 完成声明前必须交还文件清单、本地验证结果、不可验证范围和下一步；由本文、09 保障 | 声称插件编写完成时 | §7 交还摘要、验证结果、source_refs | 缺少交还时写为未完成，补齐后再声明完成 |

## 9. 验证方法

验证本文规则时应检查：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 结构检查 | 是否具备 Context、Scenario、Gate、执行、验证、回写和交还七结构 | 保持为候选，不作为正式编写行动模板 |
| 来源检查 | 是否回指 01、06、30、07、09 和实现域文档，不复制来源规则的字段闭集、枚举、判定顺序或命令样例 | 回到来源规范或模板重写 |
| 插件结构检查 | 插件包是否包含 manifest + hooks.json + shim 三个文件 | 不得声明插件编写完成 |
| 事件检查 | hooks.json 是否注册了至少 SessionStart + PreToolUse + Stop | 交还中标注缺失事件 |
| shim 边界检查 | shim 是否只做 payload 翻译 + 调 runtime_adapter，不含独立规则逻辑 | 重写 shim |
| 路径检查 | hooks.json 和 shim 中所有文件路径是否指向 V3 产物（非 V1/V2 stale path） | 修正路径 |
| 语法检查 | manifest JSON 是否可解析、hooks.json JSON 是否可解析、shim 是否通过 `py_compile` | 修复语法错误 |
| 干跑检查 | shim 能否用 fixture payload（模拟 SessionStart / PreToolUse / Stop）成功调用 runtime_adapter.py | 修复 shim 逻辑 |
| 降级检查 | 故意让 LDVH root 找不到时，shim 是否输出 warning 并 exit 0 | 修复降级逻辑 |
| Gate 检查 | 是否覆盖目标环境 API 不可用、事件不足、写入前未经 Human Gate、验证未通过、stale path 和缺少环境分析/交还的暂停条件 | 暂停并交还 Human |
| 交还检查 | 编写完成或阻断时是否交还文件清单、决策记录、验证摘要、不可验证范围、下一步和 source_refs | 补交交还摘要，不声明闭环 |

## 10. Human Gate

以下情况必须进入 Human Gate：

1. 为新增目标环境编写插件包——环境分析完成后、动手写文件前；
2. 更新已有插件的 hooks.json 或 shim——差异清单展示后、修改前；
3. 修改 manifest 中的事件注册或路径引用；
4. 将插件包部署到实际安装位置（经 30 安装流程）；
5. 声称插件编写完成——必须经 4/4 交还阶段 Human 确认；
6. 编写过程中发现目标环境 Hook API 文档不足、事件不支持或 payload 格式不明确；
7. 接受残留风险、未验证范围或环境差异缺口。

## 11. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 目标环境 Hook API 文档不可用，无法确认支持的事件和 payload 格式；
2. 目标环境不支持至少 SessionStart + PreToolUse 两个核心事件；
3. 发现 shim 中复制了 specs 规则、校验逻辑或 Human Gate 判断；
4. 路径指向 stale V1/V2 产物但未确认正确的 V3 路径；
5. 本地验证（语法、干跑、降级）未通过；
6. 缺少 1/4 环境分析或 4/4 交还阶段；
7. Codex 标本被直接复制后不改，当作新环境插件；
8. 将本地语法验证通过写成真实环境触发已验证。
