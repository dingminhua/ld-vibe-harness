## 3. 工作模型的定义与定位

### 3.1 工作模型的定义

LDVH 工作模型是 LDVH 对工程生产事实的自定义建模，将项目中的工作域、任务计划、任务、子任务、决策、变更和经验等工作事实抽象为具有明确字段契约、状态流转和验收标准的结构化对象，并通过字段内容格式承载风险判断、依赖关系、验证证据、产物引用、检查结果等结构化内容。

### 3.2 工作模型的核心特征

工作模型必须具备以下核心特征：

1. **规范由 LDVH 定义**：对象的准入条件、字段契约、状态流转、事实源边界和验收规则由 LDVH 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的事实实例属于项目，存放在该项目自身的 ldvh-base/ 目录中；每个接入 LDVH 的管辖项目应各自拥有 ldvh-base/ 目录，由该项目自身管理（依据 `docs/specs/01-目录说明.md` §4）；
3. **服务工程生产**：对象用于让 AI、人和工具围绕同一组项目事实协作，支持任务拆解、状态追踪、证据回写、决策追溯和变更审计；
4. **Git 可追溯**：事实实例必须以 Git 可追踪文件的形式承载，优先使用 YAML 格式（适合结构化字段）或 Markdown 格式（适合说明性内容）；
5. **单一事实源**：每个事实实例只能有一个权威承载位置，其他位置只能引用或聚合，不得复制并维护独立事实。

### 3.3 工作模型与临时信息的区别

| 维度 | 临时信息 | 工作模型 |
|---|---|---|
| 性质 | 执行过程中的局部选择、临时判断、聊天内容 | 结构化、可追溯、可验证的工程事实 |
| 持续时间 | 一次性，仅在当前执行上下文中有效 | 长期，可跨会话、跨执行轮次追踪 |
| 复用价值 | 无，仅服务当前执行 | 有，可被其他对象引用、可被 AI 后续执行参考 |
| 追踪需求 | 不需要独立追踪 | 需要独立追踪、状态流转和验收标准 |
| 承载位置 | 聊天记忆、工具缓存、命令输出等临时位置 | Git 文件事实源（docs/specs/、ldvh-base/、docs/ 等） |

## 4. 工作模型

### 4.1 工作模型定义

工作模型是 LDVH 对某一类工程生产事实的标准化建模结构，用于统一描述该对象的对象定位与准入条件（含范围声明）、事实源边界、状态机、对象关系、Human Gate、字段契约、事实源回写与证据留存、适配规则和待补齐事项。

每个 21-39 具体工作模型规范，都是一个具体工作模型的定义文档。

### 4.2 工作模型的标准组成

一个工作模型应包含以下内容：

1. 对象定位与准入条件（含范围声明）；
2. 事实源边界；
3. 状态机；
4. 与其他对象的关系；
5. Human Gate；
6. 字段契约；
7. 事实源回写与证据留存；
8. 适配规则（AI 协作、Code 辅助、Web 信息同步）；
9. 待补齐事项。

工作模型规范的范围声明合并到 §1 对象定位与准入条件的头部；与上位基础规范的关系通过头部元信息的上位依据字段声明，不再独立成章。通用回写与证据规则、AI 协作规则、Code 辅助规则和 Web 同步规则由本文 §7 定义，具体工作模型规范只声明对象特有差异。

### 4.3 工作模型与事实实例

工作模型定义事实类别的规则，事实实例是项目中按工作模型创建的具体事实。

工作模型承载于 `docs/specs/20-39`。除具体工作模型规范明确声明的事实源例外外，事实实例默认承载于 `ldvh-base/`；例如 Change 以 Git commit 作为事实实例的权威事实源，由 `docs/specs/22-Change-变更.md` 单独定义。模型不得承载具体实例状态，实例不得重新定义模型规则。

### 4.4 工作模型与工作流程

工作模型承载工程生产事实，工作流程控制 AI 如何行动。两者关系如下：

| 维度 | 工作模型 | 工作流程 |
|---|---|---|
| 核心问题 | 项目事实如何结构化、流转和沉淀 | AI 如何读取、判断、执行、停下和回写 |
| 规范区段 | `docs/specs/20-39` | `docs/specs/40-59` |
| 实例事实 | 事实实例承载于 `ldvh-base/` | 行动执行结果按事实类型回写 |
| 关键约束 | 准入、字段、状态机、验收和对象关系 | Context、Scenario、Gate、回写、证据 |

工作流程可以创建、更新、检查或引用工作模型，但不得重新定义工作模型字段、状态机、验收标准或事实实例事实源边界。工作模型可以被工作流程创建、更新、检查或引用，但工作模型规范不得定义工作流程的 Context、Scenario、Gate、执行流程或事实源回写规则。

### 4.5 工作模型与工具实现

工具可以依据工作模型开发解析、校验、聚合、展示和受控写入能力。工具实现不得替代工作模型本身，也不得绕过模型定义的事实源边界和 Human Gate。

### 4.6 工作模型文件命名与适配规则

适用区段：工作模型（docs/specs/20-39）。

21-39 主文件均为工作模型规范，文件名不重复"工作模型规范"字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

工作模型主规范是具体工作模型规则的唯一规范入口。21-39 工作模型不默认拆分 NN.01-NN.06 固定机制子文档，新增工作模型时默认只创建 NN 主规范。机制适配内容应回并到主规范对应章节，或按机制归属进入对应权威位置。

具体工作模型规范应在主规范中定义字段规则、状态规则、验收规则和适配规则，不得把模型核心规则拆到分散文件中。

Rules、Skill、Agent、Code、Web、Contract 等机制或实现内容不得作为每个工作模型的固定子文档结构重复维护。确需承接时，应按机制归属进入 04、06、07、08、运行 Rules、Skill 文件、Agent 定义摘要、Code 实现、Web 实现，或在工作模型主规范适配规则章节中保留摘要和引用。

Contract 可以作为字段契约、机器消费契约或校验接口继续存在，但其权威性来自工作模型主规范中的字段规则、状态机和事实源边界。新增或稳定后的 Contract 能力不得依赖 NN.06 固定编号结构成立。

### 4.7 LDVH 级初始化、审计与检查边界

工作模型规范不定义逐对象落地前决策、价值与要素审查、落地初始化、落地审计或泛化合规检查。工作模型是否新增、升级、降级、停用或重排编号，由本文的准入条件、Human Gate 要求和 `docs/specs/20-工作模型集合索引.md` 的集合登记规则共同约束。

LDVH 初始化是 LDVH 级初始化，不是每个工作模型各自选择初始化内容。LDVH落地应依据 20 中 active 工作模型清单，统一确认规范、事实源目录、实例命名、Rules、Skill、Agent、Code、Web 和契约能力是否具备最低可用入口。具体工作模型主规范只声明自身实例目录、文件命名、字段规则、状态规则、关系规则和对象特有实例检查，不重复 LDVH 级初始化流程。

LDVH 审计是 LDVH 级审计，主要检查LDVH落地是否完成、active 工作模型是否与 20 索引一致、事实源目录和实例是否符合对应主规范、固定机制子文档边界是否清晰、机制引用是否存在断裂。具体工作模型主规范只定义对象特有实例检查，不重复 LDVH 级审计流程。

合规检查不作为工作模型主规范的独立泛化章节。工作模型相关检查拆分为：生产对象规范写作检查、实例数据检查、集合一致性检查和LDVH落地完整性检查。本文维护生产对象规范写作检查和实例数据检查通用原则；20 维护集合一致性检查和落地与检查输入清单；42 LDVH落地与检查负责执行LDVH 级落地完整性检查。

### 4.8 完整方案形成流程

工作模型完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义工作模型；
2. 定义实例事实源位置、字段契约、状态机、关系规则、Human Gate、事实源回写与证据留存和适配规则；
3. 定义对象特有实例检查；
4. 判断 Rules、Skill、Agent、Code、Web 或 Contract 实践是否需要进入对应机制事实源或实现层；
5. 涉及 Skill、Code、Web 或 Contract 的，完成联动检查；
6. 修改规范、协作机制或实例事实源时，应按 `docs/specs/22-Change-变更.md` 记录可追溯变更。

## 5. 运行入口边界

工作模型对象规则的权威位置是 docs/specs 对应主规范及其已回并结构化契约章节。运行投影只能承接入口摘要、检查提示、能力调用和降级方式，不得替代工作模型主规范。

Rules / Instructions、Skill、Agent、Code、Web 或其他环境实体只保留必要入口摘要、压缩保护、规范引用、消费字段和检查入口，不得复制字段契约、状态机、关闭条件或 Human Gate 细则。具体环境如何承接这些入口，由 04 系列环境适配映射和运行投影记录处理。

## 6. 工作模型准入与分类原则

### 6.1 对象分类原则

LDVH 工作模型可按治理用途分为以下几类：

1. **工作范围和计划入口**：承载长期工作域、一次目标的任务计划、人类确认点和关闭审查；
2. **核心执行实体**：承载 AI 可执行、可追踪、可验证、可关闭的任务和子任务；
3. **决策和风险**：已确认的决策记录、已识别的风险、前置条件或外部约束；
4. **支撑和记录**：执行摘要、验证结果、关闭证据、验收记录、可引用产物、检查项、变更记录和踩坑经验。

### 6.2 对象清单归属

具体工作模型清单、编号归属、维护状态和区段关系由 `docs/specs/20-工作模型集合索引.md` 维护。本文只定义工作模型的通用分类和准入原则。

### 6.3 预留编号区段

编号区段 38-39 预留用于未来新增工作模型，不得未经 Human Gate 确认提前占用。

### 6.4 准入条件原则

一个内容需要满足以下条件之一，才应成为工作模型：

1. **需要独立追踪状态**：该内容有明确的状态流转，需要跨会话或跨执行轮次追踪；
2. **需要可验证的完成标准**：该内容有明确的验收条件，需要验证是否完成；
3. **需要关闭证据**：该内容完成后需要记录证据，供后续追溯或审计；
4. **需要关联其他对象**：该内容需要被其他对象引用，或引用其他对象；
5. **需要被 Web 信息同步，或被 Code 排序、过滤、聚合或审计**：该内容需要被 Web 或 Code 处理，以降低人和 AI 的维护成本；
6. **不成为工作模型就会导致进度、责任、完成标准或验证结果不可追踪**：该内容如果不结构化，就会导致项目事实漂移或不可追溯。

不满足以上条件的内容，应按其性质分流：
- 可以在当前对话中直接回答或处理的信息 → 留在聊天记忆中，不写入事实源；
- 已有明确目标和完成标准，但不需要独立追踪 → 作为现有 Task 或 SubTask 的执行步骤，不单独创建对象；
- 属于现有对象的属性、关系、检查项或输出路径 → 写入现有对象字段或模板，不单独创建工作模型；
- 属于长期规则或决策，但不需要独立状态机 → 写入 docs/specs/，必要时由当前项目的运行投影入口保留薄入口摘要；
- 属于项目背景或参考资料 → 写入 docs/ 或 docs/refs/；
- 属于路线规划、阶段说明或产品方向共识 → 优先写入 Markdown 文档或 research 入口；
- 属于临时执行策略 → 留在当前执行上下文中。

## 7. 工作模型的通用规范

### 7.1 事实源边界原则

工作模型的事实源边界依据 `docs/specs/09-事实源边界与承载规范.md` 定义的原则执行，本文不重复维护。工作模型的适配说明如下：

1. **介质选择适配**：依据 `docs/specs/09-事实源边界与承载规范.md` §6，事实实例优先使用 YAML 格式承载（适合任务、状态、结构化关系和审计字段），说明性内容可使用 Markdown 格式；
2. **目录归属适配**：依据 `docs/specs/09-事实源边界与承载规范.md` §8 和 `docs/specs/01-目录说明.md`，工作模型规范承载于 docs/specs/20-39，事实实例承载于 ldvh-base/，管辖项目资料承载于 docs/，外部资料承载于 docs/refs/。

### 7.2 状态流转原则

工作模型的状态流转遵循以下原则：

1. **状态变更先于执行**：执行者在执行对象相关操作时，必须同步更新事实源中的对象状态；
2. **终态不可重开**：对象进入终态后，不得直接重开；如需重新处理，必须新建对象承接；
3. **状态流转可追溯**：状态变更必须留下可追溯的记录，包括变更时间、变更人和变更原因；
4. **Human Gate 触发原则**：关键状态流转必须触发 Human Gate，等待人类确认后方可继续。

### 7.3 字段契约原则

工作模型的字段契约遵循以下原则：

1. **基础字段对齐**：所有工作模型应包含基础字段（id、type、title、status、created、updated）；其中 `created` 和 `updated` 使用 ISO 8601 时间戳格式，类型为 `datetime`；
2. **扩展字段明确**：具体工作模型的扩展字段由该工作模型的规范明确定义，包括字段名、类型、是否必填、约束条件；
3. **字段语义一致**：相同字段名在不同对象中的语义应保持一致；
4. **引用完整性**：引用其他对象的字段应确保引用的对象存在且有效。

#### 7.3.1 事实对象接口公共原语

事实对象接口用于把工作模型契约转换为 AI、Rules、Skill、Code 和 Web 可共同消费的结构化边界。接口原语不替代工作模型规范，不形成第二套字段事实源，只描述对象在不同机制中的可消费面。

事实对象接口至少包括以下层次：

| 接口层次 | 说明 | 权威来源 |
|---|---|---|
| 对象接口摘要 | 说明对象 ID、事实源目录、文件命名、默认状态、终态、主要读取场景和主要写入场景 | 具体工作模型主规范与字段契约 |
| Raw Object 接口 | 说明 YAML 或其他事实实例载体的字段、类型、必填性、条件必填、枚举、列表字段和示例 | 字段契约或对应机制事实源 |
| 引用关系接口 | 说明本对象可引用哪些对象、哪些对象可引用本对象、引用字段、引用有效性和缺失引用处理方式 | 具体工作模型主规范与字段契约 |
| 消费者接口 | 说明 AI、Rules、Skill、Code、Web 分别消费哪些字段、在哪些场景消费、消费失败如何报告缺口 | 字段契约、Contract 能力或对应机制事实源 |

事实对象接口应遵守以下规则：

1. 字段契约或 Contract 能力是结构化字段契约和机器消费接口的权威位置；
2. Code、Web 或 Skill 不得在字段契约或 Contract 能力外自行定义字段名、字段类型、状态枚举或状态流转矩阵；
3. 字段契约或 Contract 能力变更必须同步检查消费该契约的 Code 实现、测试、Rules、Skill 和 Web 入口；
4. 暂未被 Code 或 Web 消费的接口层次可以标记为待补齐，但不得把未实现能力表述为已落地；
5. 接口消费关系应说明消费方式、消费字段、验证命令或替代检查方式、同步触发条件。

#### 7.3.2 Code 消费事实对象接口原则

Code 消费事实对象接口时，应以字段契约或 Contract 能力为输入契约，以 Git 文件事实源为唯一权威输入输出边界。Code 的对象能力至少区分以下接口：

| 接口 | 说明 |
|---|---|
| 读取接口 | 从事实源读取对象并解析为结构化数据，不改变事实源 |
| 校验接口 | 依据字段契约或 Contract 能力校验字段完整性、状态合法性、条件必填、引用关系和文件命名 |
| 状态流转接口 | 依据字段契约或 Contract 能力的状态枚举和流转矩阵执行受控状态变更，并在写入前检查 Human Gate |
| 创建接口 | 依据字段契约或 Contract 能力生成新对象实例，检查编号、命名、必填字段和初始状态 |
| 删除接口 | 依据对象规范判断是否允许删除，并保留 Git 可追溯性 |
| 缺口报告接口 | 当字段契约或 Contract 能力、Code 实现和测试不同步时，输出结构化缺口，不得静默通过 |

Code 消费规则：

1. 字段契约或 Contract 能力已定义但 Code 未覆盖的字段或状态，应报告能力缺口或校验缺口；
2. Code 实现新增或修改对象接口能力时，必须同步更新对应测试；
3. Code 输出为派生结果，不替代事实源，也不替代 Human Gate；
4. 受控写入必须执行写入前校验，写入后重新校验目标事实源；
5. 字段契约或 Contract 能力变更后，如 Code 实现和测试未同步完成，相关 Code 输出不得作为最终验收依据。

### 7.4 事实源回写与证据留存通用规则

工作模型的事实源回写与证据留存遵循以下通用规则，具体工作模型规范只声明对象特有差异：

1. **回写时序**：状态变更先于执行（依据本文 §7.2）；
2. **回写不绕过 HG**：涉及 Human Gate 的回写操作必须经确认后执行；
3. **记录变更**：创建、更新或删除对象时应按 `docs/specs/22-Change-变更.md` 记录可追溯变更；
4. **证据可追溯**：证据应可追溯到 Git 文件事实源，不得仅存在于对话记录、工具缓存或 Web 派生状态中；
5. **证据完整性**：对象状态变更时应留存足以支持后续追溯和审计的证据摘要。

### 7.5 AI 协作通用规则

工作模型的 AI 协作遵循以下通用规则，具体工作模型规范只声明对象特有差异：

1. **事实源优先**：AI 读取对象时应从 Git 文件事实源或本文声明的只读 Code 派生结果获取信息，不得依赖聊天记忆、工具缓存或 Web 派生状态作为最终依据；
2. **状态适用性**：AI 应根据对象状态判断读取结果适用性；
3. **准入判断**：AI 不得因判断重要就自动创建对象，必须先判断是否满足准入条件；
4. **Human Gate 评估**：AI 创建、更新、删除或流转对象前，必须先按本文、具体工作模型规范和相关基础规范评估是否触发 Human Gate；具体模型列明的高影响场景必须暂停并请求 Human 确认。

### 7.6 Code 辅助通用规则

工作模型的 Code 辅助遵循以下通用规则，具体工作模型规范只声明对象特有差异：

1. **解析依据**：Code 实现解析对象时应依据对应工作模型规范定义的字段契约和文件命名规则；
2. **只读不自动成为依据**：Code 只读查询结果不自动成为执行依据；AI 或 Skill 必须按对应工作模型规范的状态语义判断读取结果适用性；
3. **派生不替代事实源**：聚合输出属于派生视图数据，不替代 Git 文件事实源；
4. **不得自行判断准入**：Code 实现不得自行判断对象准入、生成授权、替代流程性判断或自动执行需要 Human Gate 确认的操作；
5. **不得绕过 HG**：Code 实现不得绕过被修改对象的 Human Gate 要求。

### 7.7 Web 信息同步通用规则

工作模型的 Web 信息同步遵循以下通用规则，具体工作模型规范只声明对象特有差异：

1. **可追溯**：Web 信息同步的对象信息必须可追溯到 Git 文件事实源；
2. **不得维护不一致权威状态**：Web 不得维护与 Git 文件事实源不一致的权威状态；
3. **不得绕过格式规范**：Web 不得绕过对应工作模型规范的字段契约直接展示或编辑派生状态。

### 7.8 检查标准原则

工作模型的检查标准遵循以下原则：

1. **可验证**：检查标准必须是可验证的，不能是模糊的主观判断；
2. **明确**：检查标准必须明确，不能有歧义；
3. **可追溯**：检查完成后必须记录检查证据，包括检查时间、检查人和检查结果；
4. **按对象性质选择检查类型**：以完成为目标的对象应定义验收标准；不以完成为目标的对象应定义检查要求；
5. **对象特有检查进入主文件**：具体工作模型主文件只定义本对象特有的实例检查、验收或证据要求。LDVH 级初始化、LDVH 级审计、集合一致性检查和通用规范写作检查不得在每个对象主文件中重复维护。

### 7.9 AI 协作适配原则

AI 协作适配定义 AI 如何读取、创建、更新和检查工作模型。AI 协作适配遵循以下原则：

1. **按事实源读取**：AI 读取事实实例时必须按事实源边界读取，不依赖聊天记忆、工具缓存或数据库派生视图；
2. **按规范创建**：AI 创建事实实例时必须按工作模型规范的字段契约创建，不得自行添加、省略或修改字段；
3. **按状态机更新**：AI 更新事实实例时必须按工作模型规范的状态机流转，状态变更先于执行；
4. **按验收标准检查**：AI 检查事实实例时必须按工作模型规范的验收标准检查，检查结果留存证据；
5. **不得绕过规范**：AI 不得绕过工作模型规范定义的字段契约、状态机、验收标准或事实源边界；
6. **Human Gate 评估**：AI 创建、更新或删除关键事实实例时，应评估是否需要触发 Human Gate；
7. **机制回指**：AI 协作适配中涉及 Rules、Skill、Agent 的使用边界，必须回指 `docs/specs/04.03-环境能力清单与环境适配规范.md`。

### 7.10 事实源回写适配原则

AI 完成执行后的事实源回写，依据 `docs/specs/09-事实源边界与承载规范.md` §7定义的回写条件执行，本文不重复维护。工作模型的适配说明如下：

1. **事实实例回写触发**：AI 按工作流程执行完毕后，应判断执行结果是否需要创建或更新事实实例；若需要，必须按 `docs/specs/09-事实源边界与承载规范.md` §7 回写；
2. **回写与 Gate 联动**：关键事实实例的创建和更新应评估 Human Gate，依据本文、具体工作模型规范和相关基础规范判断；
3. **回写验证**：事实实例回写后应验证字段完整性、状态合法性和引用完整性；
4. **机制输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实实例；
5. **报告回写分流**：检查报告、分析报告或管辖项目资料应按 02、03 和具体工作模型规范判断进入 docs/、ldvh-base/或 docs/specs/。

### 7.11 证据留存适配原则

工作模型的证据留存遵循以下原则：

1. **对象创建留证**：对象创建时应记录创建原因、创建者和创建依据；
2. **状态变更留证**：状态变更时应记录变更时间、变更人、变更原因和变更前状态；
3. **验收检查留证**：验收检查时应记录检查时间、检查人、检查结果和检查证据；
4. **Human Gate 确认留证**：Human Gate 确认时应记录确认事项、确认人和确认结果；
5. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
6. **关闭前可追溯**：涉及任务、审计或 Review 的对象，在关闭前应能追溯关键证据。

## 8. 与 20-39 具体工作模型规范的关系

### 8.1 20 工作模型集合索引

20 是工作模型集合索引，不定义工作模型字段、状态机、机制承接内容或行动流程，只提供该区段内主规范的清单、关系映射、状态、升级结论、降级结论和维护信息。

### 8.2 21-39 具体工作模型规范

21-39 是具体工作模型规范，每个规范定义一个具体工作模型。具体工作模型规范应依据 §4.2 定义的工作模型标准组成展开，并在具体工作模型语境下定义更具体的工作模型规则。

具体工作模型规范不得在缺少说明的情况下省略 §4.2 中的标准组成；如某一组成项暂不适用或待补齐，应在对应章节说明原因或进入待补齐事项。具体工作模型规范不重复LDVH 级初始化、LDVH 级审计、集合一致性检查或通用规范写作检查。

### 8.3 关系原则

本文与 20-39 具体工作模型规范的关系遵循以下原则：
1. 本文定义工作模型的通用规则和工作模型的标准组成，20-39 定义具体工作模型；
2. 具体工作模型规范不得与本文的通用规则矛盾；
3. 具体工作模型规范可以在本文的通用规则基础上，定义更具体的规则；
4. 发生冲突时，以本文的通用规则为准，除非具体工作模型规范明确说明例外情况并经 Human Gate 确认。

## 10. Human Gate 与检查要求

### 10.1 Human Gate 触发条件

以下情况应评估 Human Gate：
1. 新增工作模型；
2. 删除工作模型；
3. 重命名工作模型；
4. 重排工作模型编号区段；
5. 改变工作模型的通用规则；
6. 改变工作模型的事实源边界原则；
7. 将原本不属于工作模型的内容升级为工作模型；
8. 将原本属于工作模型的内容降级为非工作模型；
9. 改变工作模型的标准组成；
10. 恢复或新增固定子文档结构；
11. 改变 AI 协作适配边界（AI 如何创建、更新、检查工作模型）；
12. 改变工作模型与工作流程的交互边界；
13. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 10.2 检查要求

工作模型规范写作检查至少包括：
| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 对象定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、工作模型和工作流程术语一致 |
| 模型组成 | 具体工作模型规范覆盖工作模型的标准组成，缺项已说明原因 |
| 适配规则 | 已说明 Rules、Skill、Agent、Code、Web、Contract 等机制内容的归属和引用方式 |
| 对象特有实例检查 | 已定义本对象特有的实例字段、状态流转、关系引用、事实源回写、证据留存和事实源边界检查规则 |
| 文件命名 | 主文件命名符合 §4.6，未重复维护区段性质或对象归属 |
| 事实源边界 | 符合 `docs/specs/09-事实源边界与承载规范.md` 的事实源边界原则 |
| 目录归属 | 符合 `docs/specs/01-目录说明.md` 的目录规划 |
| AI 协作适配 | AI 读取、创建、更新和检查事实实例的规则符合 04 环境适配边界和本文 §7.9 |
| 事实源回写 | AI 创建或更新事实实例后的回写符合 09 事实源边界原则和本文 §7.10 |
| 证据留存 | 对象创建、状态变更、验收检查和 Human Gate 确认有可追溯证据要求，符合本文 §7.11 |
