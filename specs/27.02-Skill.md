## 1. 已落地 Skill 决策

### 1.1 ldvh-close 内部调用 ldvh-commit

**决策日期**：2026-06-04

**问题**：ldvh-close 关闭 Task 后，如何触发 ldvh-commit / Change 流程？

**决策**：ldvh-close 在关闭流程中必然修改事实源（status → closed、closed_at、closure_evidence），属于准入变更，因此必须内部调用 ldvh-commit Skill 编排提交。

**理由**：
- L0 Rules 虽已规定"准入变更发生后立即调用 ldvh-commit"，但实际执行中 AI 容易遗漏或延迟；
- ldvh-close 是关闭流程的编排者，它最清楚是否产生了事实源修改；
- 内部调用确保 Change 与 Task 关闭同步完成，避免"Task 已关闭但变更未提交"的不一致状态。

**实现位置**：`.trae/skills/ldvh-close/SKILL.md` §6

### 1.2 Record 阶段完成判断条件

**决策日期**：2026-06-04

**问题**：Record 阶段"完成"的判断条件是什么？

**决策**：Task + Change 两要素。一个 Task 的 Record 阶段视为完成，当且仅当：
1. Task 已关闭（status=closed，closure_evidence 已填写）；
2. 对应 Change 已提交（存在符合 22 §8 格式的 commit，Refs 引用该 Task ID）。

**理由**：
- Task 关闭但无 Change → 变更未沉淀到事实源；
- 有 Change 但 Task 未关闭 → 变更未经过关闭审查。

注：Evidence 独立事实模型已取消，验证和关闭证据由 Task 的 `closure_evidence` 字段和引用结果物承接。

**实现位置**：`specs/22-Change-变更记录.md` §6.4

### 1.3 Task 的 related_changes 字段暂不回写

**决策日期**：2026-06-04

**问题**：Task 的 related_changes 字段是否需要自动回写？

**决策**：暂不回写。靠 commit message 中的 `Refs: task-XXXX` 实现反向追溯。

**理由**：
- Change 当前没有独立 ID（权威事实源是 Git commit hash），related_changes 无法引用 Change 实例 ID；
- commit message 的 Refs 已能实现反向追溯（从 Change 找 Task）；
- 正向追溯（从 Task 找 Change）的紧迫性较低，可通过 `git log --grep` 补偿；
- 后续如 Web Dogfood 暴露正向追溯需求，可通过 ADR 决策是否回写。

## 2. 检查项

1. ldvh-plan、ldvh-execute、ldvh-review、ldvh-close Skill 是否覆盖 Task 全生命周期；
2. Task 特有的 Skill 步骤是否需要独立记录；
3. ldvh-close 是否在事实源修改时内部调用 ldvh-commit；
4. Record 完成判断是否满足两要素条件。
