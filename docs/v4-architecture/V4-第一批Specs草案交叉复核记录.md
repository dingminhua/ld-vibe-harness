## 2. 共同起草边界

五份规范在共同起草阶段遵守：

3. 使用 01 的固定头部、自由规则主体和固定尾部，H2 连续；
4. 不把 V3 Code、tests、字段、状态、命令、目录或 Web DTO 作为 V4 权威；
5. 具体领域语义必须等待相应正式来源，Code 和 Web 不得反向定义；
6. 术语和机器表示先登记为 `proposed`，定义来源草案进入当前规则源时再同步判断是否可转为 `current`。

## 3. 分项复核与修正

### 3.1 04 Helper

初稿覆盖公开入口、请求、能力发现、机器响应、读取与状态变更、规则判断和环境一致性。独立复核发现并修正：

1. 补回当前任务相关信息和关联视图，要求保留对象身份、关系来源、遗漏分支、派生边界和过期状态；
2. 未跟踪实现细节不进入公开能力身份；
3. 第一版 `availability` 设计曾把未知操作、来源/实现缺失和请求范围放进同一能力发现结果；第二轮审核已将其拆开，当前 `availability` 只在已有当前来源的操作与有效请求下，按零、部分、全部可调用范围形成互斥结果；未知 key 返回 `invalid_request`，无契约实现只作诊断；
4. `outcome` Helper 服务结果按请求无效、部分完成、拒绝、不可用、错误、全部完成和无需变化形成互斥决策；
5. 规则结果收窄为 `规则适用判断结果 / Rule Applicability Evaluation Result`，使用 `applicability` 与 `insufficient_information`，不复用 01 的 `basis`；
6. Stop Conditions 补齐恢复条件和对应验证行。

第一轮独立复查曾确认当时文本为 0 blocker、0 major、0 minor。Human 集中审阅开始后，主执行者与新的独立复核进一步发现四项激活前问题：`operation_key` 定义条件与“已定义未实现”循环、通用发现和请求级检查混合、共同请求与响应类型不足以形成机器契约，以及 00 要求的接续信息没有进入共同响应。

Human 同意后，第二轮修正：

1. 允许当前来源先定义全局唯一且不可改派的 `operation_key`，实现和能力依据只决定能否调用；
2. 将 `capabilities` 拆为不带 key 的通用发现和带 key 的当次请求可用性检查；通用发现不把尚未提供的参数写成不可用；
3. 无当前来源的内部实现退出公开操作清单，只能作为契约缺口诊断；
4. 新增 `04.Att.01-Helper CLI 请求与响应字段表.md`，只承载标准输入、共同 JSON 字段、类型、必填性、空值、闭集和 capabilities 结果结构；
5. 共同响应新增 `request_kind` 和 `follow_up`，分别消除 capabilities 响应身份歧义并承接 00 的结果接续要求；
6. 第一版“能力发现结果”候选取消，改为范围更准确的“当次操作可用性 / Request-specific Operation Availability”；第二轮独立术语复核确认概念必要、中英文自然且边界完整；
7. 为避免 Code 从任意正文猜测领域公开操作，具体操作来源在固定 `Helper 公开操作` H3 下使用 Markdown 表格声明操作和输入/结果契约位置；没有修改 01 的 YAML 身份块解析边界，也没有建立第二操作注册表。
8. Human 确认标题和文件名省略项目语境中重复的 `LDVH`，改为 `04-Helper CLI 服务契约规范.md`；`spec_key: helper-cli-service-contract` 和规范责任保持不变。

第二轮最终复核结果：

1. 服务契约闭环复核为 0 blocker、0 major、0 minor；确认 `follow_up` 逐项来源和范围、未知 key、可选诊断 code、外层 `outcome` 与内层 `availability` 均已闭合；
2. 完整术语独立复核保留公开操作标识、当次操作可用性和规则适用判断结果；第一版“服务结果 / Service Outcome”因名称范围比 Helper 专属定义更宽，改为“Helper 服务结果 / Helper Service Outcome”；04 正文已补四项正式双语定义来源，最终复核为 0 blocker、0 major、0 minor；
3. 附件授权边界复核最初发现正文 YAML 会越过 01 的解析边界，改用固定 Markdown 表格并同步 YAML 身份摘要后，最终为 0 blocker、0 major、0 minor；
4. YAML 身份、父侧授权、H2 连续性、术语数量、旧候选残留、差异空白和 Web/icons/Code/tests 不变边界检查通过。

Human 随后确认上述设计决定。04 与附件已经同步转为 `active`，四个机器接口术语同步转为 `current`；它们在 01 的其余有效性条件同时满足时进入当前规则源。该激活不表示任何 Helper/Code/tests 已实现、可用或通过验证。

### 3.2 05 事实模型

初稿覆盖事实类型准入、事实对象身份、来源、证据、关系、状态、变更和类型取消。独立复核发现并修正：

1. 消除“先成为稳定事实才能准入事实模型”的循环：候选内容是否已经是稳定事实继续由 03 判断；类型只决定事实对象身份和类型规则；
2. 建立“候选定义来源拟准入无效力 → 准入条件和独立复核通过 → 唯一定义来源进入当前规则源时同时生效”的两阶段边界；
3. 区分事实对象稳定身份与当前内容有效性；无效内容仍可被定位修复，但不得作为有效稳定事实消费；
4. 统一使用“唯一定义来源”，避免与事实内容的来源回指混淆；
5. 分开关闭、归档、合并、替代、删除和类型取消，不建立统一“退出”状态或机器动作；
6. 区分工作对象与事实对象：前者绑定当前事项，后者是已准入类型下的稳定单位。

Human 确认只在确实优于 V3 时采用改进方案后，05 增加最小分布式类型身份：`事实类型标识 / Fact Type Identifier` 使用 `fact_type_key`，由各具体类型的当前定义来源在固定 Markdown 表格中声明；Code 只能扫描当前来源生成派生视图，不建立中央类型清单。事实对象稳定引用至少保留当前配置中的项目 `id`、`fact_type_key` 和类型定义的对象身份；派生 Schema 只保留实现、生成和一致性验证责任，不再使用“Schema 权威位置”表述。该修改不准入任何具体事实类型，也不声明 Helper 已提供事实类型发现能力。

三项术语的独立复核结论为保留：`事实类型 / Fact Type` 以“事实对象类型”为中文别名；`事实对象 / Fact Object` 以“事实实例 / Fact Instance”为中英文别名；`事实类型标识 / Fact Type Identifier` 使用机器字段 `fact_type_key`。初次复核发现术语审计记录的使用扫描、影响范围、总览和“事实类型”来源分类不完整或不准确，已完成修正。边界复核提出的声明表解析 Major 也已补齐，最终为 0 blocker、0 major、0 minor。Human 已授权确认优于 V3 后推进，05、active 03 首选表达和术语表状态已同步激活；这不准入任何具体事实类型或声明实现能力。

### 3.3 06 行动模板

初稿覆盖准入、适用、共同结构、验证、回写、交还、参与者、能力、授权和委派。独立复核发现并修正：

1. 具体模板核心行动结构必须由当前规则源正文作为唯一定义来源；现有规范自然承接或经 01 §13 建立普通规范，附件不得承载完整流程；
2. `template_key` 在全部当前具体模板中唯一，改名或移动保持，不得改派；拆分、合并、替代和取消必须保留旧身份的承接位置；
3. 发现入口把 `template_key` 映射到当前定义来源 `spec_key` 与正文位置，不维护第二份手工目录；
4. 01 的规范文件 `draft/active/retired` 不被误作模板生命周期状态；
5. “执行资源”改为含义明确的“参与者、能力与授权”；
6. Human 可以作出来源保留的授权、方向、风险接受和验收决定，但不能补造定义来源、能力、事实或技术验证。

本轮集中审核补齐 `行动模板标识 / Action Template Identifier` 的正式定义、`template_key` 精确格式、分布式 `行动模板声明` 表、唯一解析算法和故障隔离。Code 只扫描当前规则源形成派生视图，不建立中央模板清单；模板声明也不自动成为 Helper 公开能力。术语独立复核提出的两项 major 和旧总览 minor 均已修正，最终为 0 blocker、0 major、0 minor。随 06 激活，该术语已同步为 `current`；这不准入任何具体行动模板或声明实现能力。

### 3.4 07 Code 与测试

07 在外部资料核验基础上覆盖 Code 实现规划、模块与依赖、接口与 Schema 维护、诊断、重构、设计偏移、风险驱动测试和证据边界。独立复核发现并修正：

1. 第一版 `Code 规划 / Code Planning` 与其“版本化实现说明”定义不完全一致，经独立术语复核改为 `Code 实现规划 / Code Implementation Plan`；完整审计与最终状态随 07 集中审核同步；
2. 区分领域/公开接口语义与纯内部技术接口、内部数据结构的 Code 设计责任；
3. 取消把 `Focused/Component`、`Contract/Boundary`、`System/Public-capability` 当成近义词的错误分组，改用四种 LDVH 本地检查范围；
4. 重构评估增加“结构仍合适，记录依据后保持现状”的合法结果；
5. 共享实现从绝对要求改为优先方向，允许跨语言、跨进程或安全隔离下的独立实现并要求一致性措施；
6. 接口删除证明限定在声明支持范围和已识别消费者集合，保留不可观察风险；
7. ISO 42010 和 ISO 29119 的支持明确为间接参考或有限范围，NIST SSDF 使用已发布 v1.1 而不吸收观察日的 v1.2 draft；
8. 单文件 5000 行只作为重构评估信号，不作为无上下文失败线。

Human 在 04 集中审核期间进一步要求防止 V3 式测试冗长。07 已先补入待审核规则：共同请求、响应或 Schema 契约由共享 validator、生成结果或公共契约测试统一验证，具体操作测试只补自身字段、结果和风险，不复制全部共同断言。该补充尚未因写入而自动通过 07 集中审核，后续审核时必须判断其是否充分、是否过度约束实现以及能否避免测试辅助设施成为第二规则源。

集中审核进一步补齐当前规划入口、覆盖范围、实现起点、多份规划组合和替代关系，并使必要 Code tests、未验证隔离、验证表和 Stop Conditions 完全一致；`basis` 同步增加实际直接使用的 `source-of-truth-traceability`。外部资料表只保留一手页面能够直接支持的有限结论。修正后架构边界与术语独立复核均为 0 blocker、0 major、0 minor。07 与 `Code 实现规划` 已同步激活，不表示 Code/tests 已开始。

最终独立复查：0 blocker、0 major、0 minor。08 保持 `draft`，当前 `web/` 和 `icons/` 未被修改，也未声明已符合 V4。
