## 1. 价值判断

LDVH 以规范体系组织规则和边界。本文通过稳定的规则载体、职责标识、上位语义依赖和解析入口，帮助 AI：

1. 快速定位当前事项需要的规范及其上位语义依据，主要服务 V1；
2. 区分正文结构、结构归属、功能归属，以及 Spec 与附件的载体身份，主要服务 V2 和 V3；
3. 在文件改名、编号调整、规范拆分或跨会话修改时稳定识别同一职责，主要服务 V6；
4. 让 Code 能从受治理 Spec 和附件派生导航、关系和诊断，减少 AI 全文读取、手工维护索引和猜测权威关系的负担，服务 V1、V2 和 V8。

本文的价值不在于让所有 Spec 拥有相同内容，而在于让不同职责的规范使用可定位、可理解、可追溯、可解析的共同载体。

## 2. 规范依据

本文直接依据 `specs/00-理念与构成.md`，具体承接其对 Specs 共同结构、职责标识、正向依赖、派生导航、解析入口和承接规则的授权。00 所称“正向依赖”，在本文中具体表示由下位 Spec 主动声明并指向直接上位 Spec 的语义依赖；后文统一称为“上位语义依赖”。

00 是根规范，不反向依赖本文。本文可以定义 00 如何被识别和解析，但不得要求 00 采用与下位规范相同的正文结构，也不得重新解释 00 定义的理念、构成要素、价值标准、验证要求、Human Gate 或 Stop Conditions。

本文授权的附件只能承载本文明确授权的字段闭集、枚举、关系类型和登记信息，不得借附件新增或扩大正文职责。

## 3. 职责边界

本文归口定义：

1. 哪些载体构成 LDVH 规则源；
2. 根规范与下位正式规范的共同结构；
3. 规范和附件的稳定职责标识、当前编号和路径身份；
4. `basis`、`parent_spec`、正文引用和派生反向关系的职责区分；
5. 附件如何获得唯一父规范授权；
6. Code 可以从受治理 Spec 和附件派生什么，派生结果不得承担什么；
7. 规范改名、改号、拆分、合并、替代和退出时如何保持职责可追溯。

本文不定义具体规则的适用条件和效力，不定义 Helper CLI 服务、领域业务规则、事实对象字段、行动步骤、Code 内部实现或 Web 交互。本文也不根据规范编号或文件相邻关系推断架构层级。

## 4. 适用范围

本文适用于：

1. `specs/` 根目录中纳入规范身份和生命周期治理的 Spec；
2. 由受治理 Spec 明确声明的附件；
3. 受治理 Spec 和附件的新建、修改、引用、拆分、合并、迁移、替代和退出；
4. Code 对上述载体的身份解析、结构识别、依赖检查、导航派生和诊断。

本文不将 `docs/`、对话、评审结果、测试输出、Code 生成索引或迁移计划转化为规则源。它们可以帮助发现和说明问题，但只有被当前有效 Spec 正文或其当前有效授权附件吸收后，才能成为 LDVH 当前规则源的一部分。

## 5. 规则源构成

LDVH 的规范体系管理受治理 Spec 及其附件。满足本节条件的当前有效 Spec 正文及其当前有效授权附件共同构成 LDVH 当前规则源，这就是 00 所称“正式 specs 正文及其授权附件”。本文将具有规范身份并进入生命周期管理的 Spec 统称为“受治理 Spec”；将能够作为当前规则依据的 Spec 称为“当前有效 Spec”或“正式 Spec”。一篇 Spec 可以治理规范体系自身、其他构成要素或跨要素共同边界；这不改变该 Spec 作为规范体系规则载体的身份。

载体进入当前规则源必须同时满足：

1. 位于 `specs/` 的受治理路径中；
2. 具有 `ldvh_spec` 或 `ldvh_attachment` 身份块（identity block），并且能够按当前身份字段或 §6.3 的基线过渡规则解析；
3. Spec 的 `status=active`，或附件的 `status=active` 且唯一父 Spec 当前有效；
4. 当前有效 Spec 声明的 `basis` 和 `parent_spec`（如有）均指向其他当前有效 Spec；附件的唯一父 Spec 当前有效，并且附件授权的双向确认成立，或其旧授权方式符合 §6.3 的基线过渡规则；
5. Spec 正文结构符合本文允许的当前结构状态：根规范采用根规范结构，已完成迁移的 Spec 采用标准规范结构，尚未迁移的基线 Spec 符合 §6.3 的过渡条件。

`candidate`、`deprecated` 和 `archived` 载体仍可以被导航、评审和追溯，但不得作为当前规则依据。一次性过程输出即使位于 Git 中，也不因路径或格式自动获得规则源身份。

## 6. 规范类型与正文结构

### 6.1 正文结构类型

`spec_kind` 只表示正文结构类型，不同时表示结构归属、功能归属或五类构成要素归属。

| `spec_kind` | 含义 | 结构要求 |
|---|---|---|
| `root` | 根规范 | 使用根规范结构；当前 LDVH 中仅 00 属于根规范 |
| `standard` | 根规范之外的受治理 Spec | 使用标准规范结构 |

成员规范由 `parent_spec` 和 `relation=member_of` 表示；正式行动模板由 `parent_spec` 和 `relation=instance_of` 表示。两者的 `spec_kind` 均为 `standard`。正式行动模板作为文件载体属于规则源，同时按功能职责属于行动模板构成要素。

规范的上位语义依赖由 `basis` 表达，结构归属由 `parent_spec` 和 `relation` 共同表达，不由编号段、目录顺序或 `spec_kind` 推断。

### 6.2 根规范结构

根规范保留自身的上位叙事结构，不使用下位规范固定头部。其文末必须依次保留：

1. 验证要求；
2. Human Gate；
3. Stop Conditions。

### 6.3 标准规范结构

除根规范外，新建或已完成结构迁移的受治理 Spec 必须由固定头部、自由主体和固定尾部构成。

固定头部依次为：

1. 价值判断；
2. 规范依据；
3. 职责边界；
4. 适用范围。

自由主体只承载本规范归口的具体规则，章节名称和数量由本规范的职责决定。

固定尾部依次为：

1. 验证要求；
2. Human Gate；
3. Stop Conditions。

“保障措施”不再是所有 Spec 的固定章节。具体规则需要声明的作用方式、所需能力和缺口处理，由承担规则适用与效力职责的规范统一定义；单篇 Spec 只写自身需要的增量。“待补齐事项”也不再是固定章节；未完成工作应进入可接续的工作对象或迁移计划，不与已生效规则混合维护。

本文的迁移基线，是 Git 历史中本文首次同时具有 `ldvh_spec.spec_key=normative-system-foundation` 和 `status=active` 的 commit 及其完整树。该树中已存在的 Spec 和附件，可以在迁移期间暂时沿用基线树已经记录的旧正文结构、旧身份块字段与枚举、旧关系值、旧父侧附件授权方式和尚未去重的 `basis`；其中 `active` 载体的当前规则源资格不因尚未迁移而自动失效。Code 必须以该 commit 的树为基线清单和旧结构上限，不另行维护人工遗留清单。

迁移中的载体只有完整满足当前身份字段、关系和正文结构要求时，才能声明完成目标结构迁移；部分迁移仍按过渡载体处理。过渡载体可以删除旧结构、增加当前目标字段并逐步收敛，但不得在某个过渡载体中新增该载体基线版本未使用的旧字段、旧枚举、旧关系或旧父侧授权，也不得扩大其既有旧用法。需要替代尚无稳定 key 的旧职责时，必须在切换前或同一切换切片中先为旧载体分配只代表该旧职责的 `spec_key` 或 `attachment_key`，再由新载体的 `supersedes` 指向该 key。

### 6.4 信息角色

固定章节和自由主体的信息角色由 `specs/attachments/04.Att.02-规范信息角色表.md` 定义。每个信息角色对应的章节只承担该角色的主责；必要的跨章引用不改变信息归口，也不得借引用隐藏规则、验证缺口、Human Gate 或 Stop Conditions。

标准规范在某项职责上确实没有新增 Human Gate 或 Stop Conditions 时，仍保留对应章节，并明确写明“本文不新增相应条件，沿用 00 及实际适用的来源规则”；不得为填充固定结构而制造无实际边界的条件。

“验证要求”必须使用 00 已定义的七个字段：验证对象、验证时机、成立条件、可接受依据、验证入口、可证明范围和未满足时的处理。没有真实验证内容时，应先重新判断该规则是否需要进入正式 Spec，不得用“AI 语义审核”等无成立条件的空泛表述占位。

## 7. 规范职责与稳定标识

### 7.1 规范职责的稳定标识

每篇迁入目标结构的 Spec 必须使用 `spec_key` 作为其规范职责的稳定标识。`spec_key` 不包含编号、路径、状态或版本；同一职责改名、移动或改号时保持 `spec_key` 不变。

`spec_id` 是当前规范集合中的唯一编号标识，可以随整体编号迁移而变化；`canonical_path` 是当前文件位置，可以随改名或目录迁移而变化。两者都不得代替 `spec_key` 表示稳定职责。

当前规范集合中，`spec_key`、`spec_id` 和 `canonical_path` 必须分别唯一。`spec_key` 一经赋予某项规范职责，不得在该规范退出后重新分配给其他职责。附件的 `attachment_key` 遵守同样的唯一与不可复用原则；当前附件集合中，`attachment_key`、`attachment_id` 和 `canonical_path` 必须分别唯一。

### 7.2 身份块与启动识别边界

为避免本文与身份字段附件互相等待授权的启动验证环，本节直接定义首次识别所需的最小字段和唯一启动发现约定：

1. Spec 最小身份字段为 `spec_key`、`spec_id`、`spec_kind`、`title`、`status`、`canonical_path`、`basis` 和 `authorized_attachments`；
2. 附件最小身份字段为 `attachment_key`、`attachment_id`、`title`、`status`、`canonical_path`、`parent_spec` 和 `relation`；
3. Code 启动时，只在 `specs/` 的 Markdown YAML 块中搜索 `ldvh_spec.spec_key=normative-system-foundation`，以此发现承担 00 所授权 Specs 共同结构治理职责的规范；该约定不依赖 `spec_id`、文件名或路径；
4. 搜索结果必须且只能有一个，并且该受治理 Spec 的 `status` 必须为 `active`；缺失、重复或无法解析时，停止依赖规范结构契约的解析，不得猜测承担者；
5. 发现本文后，先按本节的 Spec 最小字段识别本文，再读取本文的 `authorized_attachments`，根据附件最小字段识别 `attachment_key=spec-identity-fields` 和 `attachment_key=attachment-identity-fields` 两张身份字段表，最后使用字段表校验完整身份。

受治理 Spec 的完整身份字段闭集见 `specs/attachments/04.Att.01-规范身份字段表.md`，附件的完整身份字段闭集见 `specs/attachments/04.Att.05-附件身份字段表.md`。字段表在本文授权的身份治理范围内定义完整字段与枚举，但不得删除、改写或绕过本节规定的最小识别边界。

身份块（identity block）用于识别和解析，不得代替正文中的价值、依据、职责、范围和规则判断。身份块与正文冲突时，应暂停依赖冲突字段的解析或变更，并修正不一致；不得选择便利的一方继续。

### 7.3 `role_sections`

`role_sections` 是信息角色到当前 H2 章节标题的解析索引，不是第二规则源。目标结构中的标准规范必须恰好声明 `value_judgment`、`normative_basis`、`responsibility_boundary`、`scope`、`rule_body`、`verification_requirements`、`human_gate` 和 `stop_conditions` 八个键，不得缺少或增加其他键。

除 `rule_body` 外，每个键的值必须是一个非空 H2 标题字符串；`rule_body` 必须是至少包含一个非空 H2 标题的列表。全部标题必须存在且互不重复，每个 H2 必须恰好由一个信息角色索引。`role_sections` 不得新增正文未承载的信息角色或改变章节职责。当前契约要求在身份块中人工声明并与正文同步；未来只有先修改本文和规范身份字段表，才能将其改为由 Code 派生并从身份块删除，不得因 Code 已具备派生能力而自动改变必填性。

### 7.4 `code_consumption`

`code_consumption` 声明本规范提供的稳定解析入口，不列举 Code 模块，也不承诺相应能力已实现或可用。Code 是否已消费、如何实现和当次是否可用，应由 Code 和验证结果说明。

## 8. 上位语义依赖与其他引用

### 8.1 `basis`

`basis` 只记录理解、判定或维护本规范必不可少的直接上位语义依赖。下位规范指向上位规范，上位规范不反向列举所有消费者。

`basis` 必须满足：

1. 当前有效 Spec 只引用其他当前有效 Spec；
2. 只保留直接依赖，不重复列举可通过上位依赖到达的间接依赖；
3. 不因文件编号相邻、实现了本规范、消费了本规范或出现在同一流程中而建立；
4. 全部当前有效 Spec 的 `basis` 共同形成无环有向图。

`basis` 不负责表示 Code 实现、测试覆盖、下游消费者、导航顺序或当次读取计划。

### 8.2 `parent_spec`

`parent_spec` 表示直接结构归属：成员规范属于哪个规范族，行动模板受哪个基础规范治理，附件由哪个父规范授权。当前有效的子 Spec 必须指向当前有效的父 Spec。`parent_spec` 不自动表示全部语义依赖；理解本规范确实必需的上位语义仍应进入 `basis`。

一篇 Spec 最多只有一个直接父规范。根规范没有父规范。标准规范只在存在真实结构归属时声明父规范，不为了形成表面层级而强制挂载。Spec 不得以自身为父；全部当前有效 Spec 的 `parent_spec` 共同形成无环有向图。

### 8.3 其他引用

正文对其他规范、附件、事实或实现的引用，只表示引用所在语句明示的关系。附件授权、上位语义依赖、替代关系和结构归属不得仅靠普通正文链接暗示，必须使用本文定义的结构字段。

`supersedes` 用于由新 Spec 或新附件主动指向被替代职责的 `spec_key` 或 `attachment_key`。同一职责只发生改名、改号或移动时继续使用原 key，不声明 `supersedes`；只有职责实质拆分、合并或替代时，新载体才使用 `supersedes` 保留可派生的替代链。

`supersedes` 中的 key 必须存在、类型一致、互不重复，不得指向当前载体自身；全部 Spec 替代关系和全部附件替代关系分别形成无环有向图。新载体为 `candidate` 时，被替代载体可以继续为 `active`；新载体转为 `active` 时，被替代载体必须在同一切换切片中转为 `deprecated` 或 `archived`，不得与新载体同时作为当前规则依据。

主动声明的关系类型及其承载位置见 `specs/attachments/04.Att.03-规范关系类型表.md`。下游消费、实现、验证和受影响关系应由 Code 从上位语义依赖、其他主动声明关系和实际资产派生，不在上位规范中手工维护反向清单。

## 9. 附件授权

附件是受治理 Spec 明确授权的结构化规则载体，可用于承载字段闭集、枚举、矩阵、术语登记和其他由父规范正文已明确授权的稳定表格。

附件获得授权必须形成双向确认：

1. 附件的 `parent_spec` 指向唯一父 Spec，`relation` 为 `authorized_by`；
2. 父 Spec 的 `authorized_attachments` 明确列出该附件；
3. 父规范正文说明附件被授权承载的对象。

附件不得承载根理念、未经正文授权的核心规则、行动流程、Human Gate、Stop Conditions、长篇解释、迁移过程或可由 Code 派生的目录和反向关系。附件不得通过表格新增父规范未定义的职责。

附件身份块字段闭集见 `specs/attachments/04.Att.05-附件身份字段表.md`。完成目标结构迁移的当前有效附件，只有在唯一父 Spec 当前有效且双向确认成立时，才进入当前规则源；尚未完成目标结构迁移的基线附件，可以按 §6.3 记录的旧授权方式确认过渡资格。附件与父规范冲突时，受影响的解析和行动必须暂停；应回到父规范确认意图并同步修正附件，不得将冲突表格作为便利例外。

## 10. 继承与作用边界

上位语义依赖表示语义依据，不表示上位规范的每条具体规则都无条件作用于下位规范所处理的每个事项。具体规则的适用范围和效力仍由来源规范定义。

下位规范必须遵守它已声明依据中对当前职责和事项适用的上位规则，不得重新解释、覆盖或弱化上位定义。需要细化时，只写在自身职责和适用范围内的增量；需要改变上位定义时，必须回到上位规范。

标准规范的 Human Gate 和 Stop Conditions 只写本职责相对 00 新增或细化的条件，不复制 00 的全部通用条件。未命中来源规范适用条件的普通 AI 求解路径，不因未出现在规范正文、身份块、关系图或 Code 派生导航中而被禁止。

## 11. 派生导航与 Code 解析

Code 可以从受治理 Spec、授权附件、身份块、H2 结构和主动声明的关系派生：

1. 当前规范和附件目录；
2. `spec_key`、`spec_id` 和路径映射；
3. `basis` 依赖图、无环检查和上位语义依据链；
4. 父子关系、附件双向确认、替代链和反向消费导航；
5. 章节角色导航和按职责生成的读取候选；
6. 结构、引用、重复职责和迁移残留诊断。

可稳定派生的目录、反向关系、依赖图、读取候选和覆盖诊断不在正文中手工维护。派生结果是导航、压缩上下文和诊断入口，不是第二规则源，不得改变规则的适用范围和效力，也不得声称未实现或未验证的解析能力已可用。

Code 实现可以发现结构缺口，但不得为了符合当前解析器而反向固化不必要的正文结构。本文修改解析契约后，Code 应在对应实现阶段跟随校准；校准完成前，必须如实说明尚未支持的范围。

## 12. 规范修改与迁移

### 12.1 修改顺序

修改受治理 Spec 时，应依次确认：

1. 本次修改是否仍服务本规范的价值和稳定职责；
2. 规范依据、职责边界和适用范围是否变化；
3. 自由主体中哪些规则需要修改；
4. 验证要求、Human Gate 和 Stop Conditions 是否需要增量调整；
5. 身份块、附件、主动声明的关系和 Code 解析入口是否需要同步。

修改不得只更新 YAML 或附件而不更新正文规则，也不得只修改正文而留下已失效的身份和引用。

### 12.2 改名、移动与改号

同一职责只发生改名、移动或改号时：

1. Spec 保持 `spec_key` 不变，附件保持 `attachment_key` 不变；
2. 更新 `spec_id`、`title` 或 `canonical_path` 中实际变化的字段；
3. 在同一迁移切片中更新附件父路径、上位语义依赖和显式引用；
4. 由 Git 保留旧路径和方案的历史追溯，不保留第二份 active 规则作为兼容副本。

### 12.3 拆分、合并与替代

Spec 或附件职责发生实质拆分、合并或替代时，必须先明确：

1. 每个目标载体的稳定职责及其 `spec_key` 或 `attachment_key`；
2. 原规则逐项迁入的目标位置；
3. 哪些内容被删除，以及删除是因为过期、重复、可派生还是不再成立；
4. 新载体的 `supersedes` 如何指向被替代职责的同类型 key；
5. 原载体何时转为 `deprecated` 或 `archived`；
6. 附件、引用、Code 解析和下游消费如何接续。

新旧内容必须同时存在时，新载体在完成前保持 `candidate`，原载体继续作为当前有效规则；在同一切换切片中，新载体转为 `active`，原载体同时转为 `deprecated` 或 `archived`。不得同时保留两份表达同一职责的当前有效规则。迁移工作记录在工作对象或迁移计划中，不在受治理 Spec 中建立固定待办区。

### 12.4 生命周期转换

Spec 与附件使用相同的单向生命周期：`candidate` 可以转为 `active` 或 `archived`，`active` 可以转为 `deprecated` 或 `archived`，`deprecated` 只能转为 `archived`，`archived` 是终态。状态未变化不属于转换；其他反向或跨级转换均不允许。

新载体通常先以 `candidate` 完成结构和关系验证；在同一变更切片中已经完整满足启用条件并完成验证时，也可以初始即为 `active`。职责被替代时使用 `active → deprecated`；职责直接退出且已确认不需要保留过渡期时，可以使用 `active → archived`。已经归档的职责需要重新建立时，应创建新的稳定职责标识，并在确属实质承接时通过 `supersedes` 保留关系，不得重新启用或复用已归档载体的 key。

## 13. 术语归口

需要跨规范稳定使用，并会影响规则理解、解析、判断或兼容迁移的术语，应纳入术语登记。每个已登记的 active 术语必须有且只有一个定义来源。术语的含义和边界由对该概念负责的规范正文决定；其他规范可以引用和细化自身适用范围内的增量，不建立平行定义。只在单篇 Spec 内使用且不影响跨规范理解的局部表达，不强制登记。

`specs/attachments/04.Att.06-LDVH术语登记表.md` 是 LDVH 的全局术语登记入口。它只登记推荐术语、用于检索的类别、唯一定义来源、其他有效表达、历史名称和状态，不复制来源规范的定义全文，也不反向改变来源语义。类别只用于检索和归组，不承担新的概念定义。只有来源已明确且当前仍成立的术语才登记为 active；来源尚未定稿的术语不得由术语登记表提前代定义。

术语改名时，应在来源规范中完成语义变更，并同步更新引用和术语登记。历史名称只用于迁移定位，不与当前推荐术语共同承担规则语义。

## 15. Human Gate

以下事项必须进入 Human Gate：

1. 改变根规范与标准规范的基本结构关系，或改变 00 授予本文的 Specs 共同结构治理范围；
2. 新增、删除或改变所有目标结构 Spec 共同必需的身份字段、信息角色或上位语义依赖语义；
3. 无法确认某次拆分、合并或替代是同一职责迁移，还是形成了新的稳定职责；
4. 准备删除、废弃或迁移当前有效规则载体，但无法确认其规则是否已被完整承接或确实不再成立；
5. 出现依赖环、重复当前有效职责、孤立附件或规则来源不明时，需要由 Human 决定是否修改上位结构规则，或选择何种修正与迁移方案。

Human Gate 只完成结构取舍、职责判断、迁移方向或是否修改规则的决定，不能代替结构、引用、依赖和附件授权的实际修正与验证。现行规则未修改、结构未修复之前，Human 回应不得将不符合本文的状态转化为已成立。

## 16. Stop Conditions

出现以下任一情况时，AI 必须暂停受影响的规范修改、迁移、解析或声明：

1. 当前 Spec 的稳定职责、上位语义依据、职责边界或适用范围无法确认；
2. `spec_key`、`attachment_key`、ID 或 `canonical_path` 冲突，启动发现标识缺失或重复，`basis` 或 `parent_spec` 引用不存在、指向非当前有效 Spec 或形成环依赖；
3. 附件缺少唯一父规范授权、与父规范冲突，或承载了未经正文授权的核心规则；
4. 准备声明某篇 Spec 已完成目标结构迁移，但固定头尾、信息角色或解析结果不一致；
5. 无法取得唯一迁移基线却仍需依赖过渡资格，出现基线之外的旧结构扩张，发生 §12.4 未允许的状态转换，迁移会删除尚未承接的规则，实质替代未记录有效的 `supersedes`，替代目标悬空、类型错误、自指、重复或成环，或切换后仍保留两份重复的当前有效规则；
6. Code、附件、索引、评审、测试或迁移材料正在反向定义当前有效 Spec 的规则、权威、适用范围或效力。

暂停只影响与触发条件相关的 Spec、附件、依赖关系、迁移切片或声明。暂停期间可以继续定位来源、比对差异、修正结构、补齐引用、准备迁移映射或 Human Gate 交还内容；未受影响的普通求解路径不因本节被禁止。
