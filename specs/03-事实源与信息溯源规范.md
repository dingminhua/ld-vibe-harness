## 1. 价值判断

本文的价值，是让 AI 在当前工作中直接使用真实存在的最新内容，同时能区分哪些内容已经位于事实源，哪些是当次观察、聊天、工具输出、缓存、索引或其它派生信息，以及这些信息如何回到来源和后续历史。这样可以避免 AI 因只读取 `HEAD` 而忽略进行中的事实内容和未提交事实，也可以避免把聊天、工具成功、缓存、索引或 Git commit 误当成事实正确、验证通过或工作完成。

本文主要服务以下 V1–V8 价值：

1. V1 快速定位：定位当前事实所在文件及其来源；
2. V2 充分理解：把当前内容、来源、形成过程和派生关系联系起来；
3. V3 边界识别：区分规则源、事实源、当次观察、各类输出和派生信息；
4. V5 据实判断：让判断不超出当前事实和当次可观察依据；
5. V6 工作接续：使进行中而非只有已完成、已提交的工作能够被后续 AI 恢复；
6. V8 持续积累：把确有长期价值的信息按明确位置纳入事实源，并保留变化历史。

## 2. 规范依据

本文直接依据 `ldvh-root` 对事实源、事实源边界和事实模型职责的定义，细化以下已确定原则：

1. 事实源以 Git 可追踪文件为唯一有效承载形态；
2. 事实源必须有组织、可消费；
3. 聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图不能自行替代事实源；
4. 稳定事实、状态、证据、决策和经验可以由事实模型在事实源边界内组织。

本文同时依据 `specification-model-foundation` 区分规则源与其它信息，并沿用其当前工作树边界：当前内容以 Working Tree 中的实际文件为默认读取视图，Index 和 `HEAD` 不得覆盖当前内容或成为规则生效开关。

本文依据 `work-object-governance-scope` 取得工作对象实际所在 Git worktree 与配置登记路径的边界。该依据只用于确定当前事实应当绑定哪一个实际 worktree，不使管辖项目配置成为事实源，也不使管辖判定替代事实内容和来源规则。

本文不得重新定义 00 的事实源，也不得把信息分类、Git 状态、索引、缓存、Code 输出或本文自身变成第二事实源。[W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 对 provenance 的定义可用于理解“来源及形成过程”与“质量、可靠性或可信度判断”之间的区别，但本文不采用完整 W3C PROV 数据模型，也不据此新增实体、活动或参与者 Schema。

## 3. 职责边界

本文负责：

1. 稳定事实、当次可观察信息、聊天、AI 推理、工具输出、缓存和派生信息之间的边界；
2. 事实源与某项信息原始出处之间的区别；
3. 来源回指和信息溯源的基本要求；
4. 信息纳入或更新事实源时的共同边界；
5. Working Tree、Index、`HEAD` 和 Git history 在当前读取与历史溯源中的不同作用；
6. Git 记录能够支持和不能支持的结论。

本文不负责：

1. 重新定义 01 的规则源资格、规范身份或规范关系；
2. 定义具体事实类型、字段、状态闭集、关系、Schema 或目录；
3. 判断证据是否充分，或者定义完成、通过、可用、接入和关闭等声明；
4. 定义 Git 暂存、拆分、提交、push、remote/ref 写入、commit message 或 Hook 流程；
5. 定义 Helper 请求与响应字段、Code 模块、算法、诊断码或缓存实现；
6. 定义 Web 页面、API 或交互方式。

上述内容分别由以下位置承担：

1. 规范身份和当前规则源资格由规范模型承担；
2. 关于结论不得超出事实、验证结果或当次可观察依据所支持范围的上位边界由 00 承担；
3. 各领域的成立条件、可接受依据和可证明范围由相应来源规范承担；
4. 事实对象结构由事实模型承担，可复用行动结构由行动模板承担；
5. Helper 的公开服务请求与结果语义由 Helper 服务契约承担；
6. Code 实现规划、内部模块、算法、诊断、缓存和测试工程由 Code 工程实践及 Code/tests 实现承担；
7. 环境连接、安装、真实触发和回滚由环境接入职责承担；
8. Web 的读取、呈现和受控交互由 Web 相关职责承担。

本文只定义这些职责共同使用的事实源和溯源边界。

## 4. 适用范围

本文适用于管辖项目中以下事项：

1. AI、Helper、Code 或 Web 读取项目当前事实；
2. Human 指令、文件观察、外部资料、命令、测试、Code、评审或其它工具产生当前信息；
3. 当前信息需要跨行动、会话、执行者或阶段继续保留；
4. 事实被新建、更新、推进状态、关闭、更正、移动或删除；
5. 缓存、索引、摘要、聚合或视图从规则源或事实源派生；
6. 需要说明当前 Working Tree 内容与 Index、`HEAD` 或 Git history 的关系。

本文不要求与项目事实无关的一般知识问答或普通求解先建立事实源记录，也不要求聊天、命令输出、测试结果、诊断、临时报告、缓存、索引、摘要或 Web 展示都长期保存。

## 5. 核心术语与边界

### 5.1 稳定事实（Stable Fact）

稳定事实是在管辖项目中需要跨行动、会话、执行者或阶段继续保留，并且已经位于符合 00 事实源边界的当前文件位置、满足适用来源规则、能够被后续消费的事实内容。需要对象化、状态化或证据化管理的内容，还必须满足适用事实模型；不需要上述管理的稳定内容，不因缺少事实模型而自动失去稳定事实资格。

“稳定”表示它具有明确、可持续读取的当前承载位置，不表示内容已经完成、关闭、不可修改、已经提交或天然可信。内容处于来源规则允许的进行中状态时，只要其当前文件与状态有效，同样可以承载稳定事实并支持后续接续。稳定事实仍必须按来源、状态和适用验证要求判断，不能仅凭名称取得正确性或可信度。

未提交不排除稳定事实。当前文件位于 Git worktree，已经被 Git 跟踪，或者尚未跟踪但未被 ignore 规则排除、能够后续纳入 Git，并满足适用来源规则与验证要求时，其当前内容可以作为稳定事实被读取；需要事实模型管理的内容还必须满足相应事实模型。commit 只在之后补充历史锚点。

### 5.2 当次产生与派生的信息

聊天与 AI 推理、命令和测试输出、Code 诊断、评审结果、临时报告、缓存、索引、摘要、聚合结果和 Web 展示，都可能在当前行动、观察、计算、验证、展示或协作过程中产生。它们的形成方式、生命周期和消费边界不同，本文不把它们合并定义为一个正式信息类型。

这些信息可以在各自来源和实际范围内支持当次判断，也可以成为后续写入或更新事实源的输入，但不会因为重要、格式结构化、工具成功或被重复显示而自行成为稳定事实。是否需要长期保留，必须回到适用来源规则和实际接续价值判断；需要对象化、状态化或证据化管理时，还必须回到相应事实模型。

### 5.3 来源回指（Source Reference）与信息溯源（Information Traceability）

来源回指是能够以当前判断所需精度重新定位某项信息的原始出处、当次观察、输入文件、命令或其它形成依据的可复核引用。具体表示可以是文件与对象定位、规范 key 与章节、外部来源地址、命令与输入范围、Git ref 或由相应来源规范定义的其它结构。

一个位置、URL、分支名、Git ref 或命令名称不一定单独构成充分的来源回指。来源会变化且当前结论依赖特定版本或观察时点时，回指必须按需要同时保留仓库或系统身份、路径或对象、commit 或版本、观察时间、命令输入范围和执行上下文中的必要部分；多个引用可以组合满足重新定位要求。本文不要求所有来源使用同一字段闭集，但不得用无法回到实际出处的模糊说明冒充来源回指。

信息溯源是从当前信息回到其来源、关键形成或转换过程以及当前承载位置的能力。它帮助 AI 判断信息从哪里来、经过什么变化、现在在哪里，但不单独证明内容正确、证据充分、Human 已确认或工作完成。

来源回指不要求所有信息采用同一种字段，也不要求本文预先建立全局 `source_refs` Schema。具体事实对象、Helper 响应和 Code 输出需要哪些字段，由承担相应职责的规范定义。

### 5.4 写入或更新事实源

把确需长期保留的当前信息写入或更新到适用来源规则定义的事实源位置时，必须按适用规则保留来源、当前状态和必要关系，并随后回读实际 Working Tree 内容。需要对象化、状态化或证据化管理的内容，还必须写入相应事实模型允许的位置和结构。本文将这些要求作为一组共同规则，不把该动作提前建立为独立正式术语。

写入动作本身不自动证明事实成立。只有目标位置、适用来源规则、来源和验证要求成立，并且需要事实模型管理时相应对象类型、字段、状态和关系也成立，写入后的当前内容才能按相应范围作为稳定事实消费；是否已经 commit 不属于这一成立条件。

## 6. 信息作用与消费边界

同一段内容可以随着处理发生作用变化，但作用变化必须有明确依据和承载位置，不能由文件名、工具类型或显示位置自动推断。

| 当前信息 | 可以承担的作用 | 不得自动承担的作用 |
|---|---|---|
| 当前规则源中的规范正文与授权附件 | 提供规则含义、适用边界和机器契约 | 不作为项目事实对象或证明具体工作已经完成 |
| 当前事实源文件中的有效内容 | 提供项目当前稳定事实、状态、证据、决策或经验 | 不重新定义事实模型、规则或 Human Gate |
| Human 当前指令 | 约束或授权当次明确范围内的行动和决定 | 不自动成为跨会话项目事实，不替代事实源文件写入、回读与技术验证 |
| 当前文件、环境或外部来源的可观察信息 | 支持当次判断，并作为事实源写入或更新的候选输入 | 不因被观察到就取得长期稳定性或事实源身份 |
| AI、命令、测试、Code、评审和其它工具产生的信息 | 提供候选结论、诊断、验证输入或当前反馈 | 不替代事实源、规则源、Human Gate 或完成声明 |
| 缓存、索引、摘要、聚合和 Web 视图 | 加速定位、压缩上下文或辅助展示 | 不成为第二事实源，不覆盖其输入来源 |
| `LDVH-GOVERNED-PROJECTS.yaml` 和其它明确配置 | 按来源规范作为直接配置输入 | 不因可被 Code 读取而变成项目事实源或规则源 |
| Working Tree、Index、`HEAD` 和 Git history 信息 | 分别说明当前内容、待提交内容和历史版本关系 | 不单独证明语义正确、验证通过、风险已接受或工作完成 |

外部文档、网页、API 或第三方仓库可以是某项信息的来源，也可以在其自身领域具有权威性；但它们不会因此成为 00 定义的 LDVH 项目事实源。需要跨会话消费的项目结论必须按适用来源规则写入项目事实源并保留适当来源回指；需要对象化、状态化或证据化管理时，还必须符合相应事实模型。

## 7. 当前工作树读取规则

1. 判断项目当前事实时，AI、Helper 和 Code 默认读取当前 Working Tree 中实际存在的文件内容，不以 Index、`HEAD`、远端分支或缓存替代当前文件；
2. 当工作对象或 Human 目标明确指定 commit、Git ref、历史时间点或当前版本与历史版本的比较时，可以读取对应历史对象；结果必须保留版本定位并明确标记为历史内容或比较结果，不得将其冒充为项目当前事实；
3. 已被 Git 跟踪的修改和尚未跟踪但未被 ignore 规则排除的新文件都可以承载当前事实；“dirty”或“untracked”只描述 Git 状态，不等于内容无效；已跟踪文件不因路径后来命中 ignore 规则而自动失去 Git 跟踪身份；
4. 当前文件中的进行中状态必须按适用来源规则和需要时事实模型消费，不能因为尚未完成或提交而回退读取旧状态；
5. 当前工作树已经删除、移动或重命名的文件，不得因旧路径仍存在于 `HEAD` 而继续作为当前事实读取；相应变化是否合法由来源规则、需要时适用的事实模型和当次验证判断，但显式历史读取仍可按第 2 项进行；
6. Working Tree 与 Index 或 `HEAD` 不同时，判断当前事实必须使用当前内容，同时把差异作为溯源上下文；显式历史读取或版本比较按第 2 项保持各版本身份；
7. 当前文件无法解析、违反适用 Schema、状态或关系规则时，必须报告当前不一致，不能静默使用旧提交掩盖问题；
8. 未提交状态本身不造成全局停止。只有具体来源规则要求提交、当前内容不成立、事实冲突无法判断，或者相应行动需要历史锚点时，才暂停受影响范围或进入 Human Gate。

工作对象明确位于某个 Git worktree 时，当前事实的读取、写入、回读和验证必须绑定该对象实际所在的 worktree。管辖项目配置中的登记路径、Helper 或 Code 所在 worktree，以及共享同一 Git common-dir 的其它 worktree 都不得替代目标 worktree；同一管辖项目的多个 worktree 中存在的当前事实和进行中变化不得静默合并。

缓存、索引和派生视图检测到 Working Tree 变化后应重新生成或明确标记过期；它们不得反向要求 AI 忽略更新后的当前文件。

## 8. 稳定事实形成与事实源更新规则

当前信息进入或更新事实源时，必须依次确认：

1. 该信息确实需要跨行动、会话、执行者或阶段继续保留，而不是只服务当前推理；
2. 已有适用来源规则定义相应内容的承载位置、边界和消费方式；内容需要对象化、状态化或证据化管理时，已有事实模型定义相应对象、结构和当前状态要求；
3. 目标文件位于对应管辖项目的 Git worktree 内，已经被 Git 跟踪，或者尚未跟踪但未被 ignore 规则排除、能够后续纳入 Git，并处于适用来源规则及需要时事实模型允许的位置；
4. 需要保留的来源回指、形成依据和关系按适用来源规则及需要时事实模型写入或关联，未把推测写成已证实事实；
5. 当前 Working Tree 内容满足适用来源规则，以及需要时相应对象、字段、状态、关系和验证要求；
6. 写入后已经回读实际目标文件，确认当前内容而不是只依赖写入命令成功输出。

本文不授权任何具体事实类型。历史实例、名称、目录或 Schema 不自动取得当前事实类型身份；没有当前有效具体事实类型定义的对象只能保持候选，不得由本文直接创建为正式事实对象。

事实源写入或更新并完成回读后，当前内容可以在其实际成立范围内立即支持后续工作。尚未提交时，应在需要判断历史状态、交还提交准备度或比较版本时如实说明；不得把“尚未提交”改写成“事实不存在”，也不得把“当前有效”改写成“已经形成 Git 历史记录”。

## 9. Git 溯源边界

[Git 官方对象模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)说明了 Working Tree 内容进入 tree 与 commit 历史时的基本关系；[git status](https://git-scm.com/docs/git-status)区分 Index 与 `HEAD`、Working Tree 与 Index，以及尚未跟踪且未被忽略的文件；[gitignore](https://git-scm.com/docs/gitignore)明确已被跟踪的文件不受 ignore 规则影响；[gitrevisions](https://git-scm.com/docs/gitrevisions)定义了 revision 与路径对历史对象的定位方式。本文据此区分当前、待提交和历史内容，但不把 Git 技术模型提升为 LDVH 的事实语义来源。

Git 为当前内容和历史变化提供三个不同观察层次：

| Git 层次 | 主要作用 | 不得覆盖的内容 |
|---|---|---|
| Working Tree | 当前实际文件和进行中变化，是 AI 与 Code 的默认读取视图 | 不被 Index 或 `HEAD` 中旧内容覆盖 |
| Index | 下一次 commit 的候选快照，用于提交范围和提交前验证 | 不代表全部当前变化，也不决定当前事实或规则是否生效 |
| 可解析的 `HEAD` 与 Git history | 已提交快照、父提交关系、作者与提交者信息及 message 等历史锚点 | 不替代 Working Tree，不自动证明事实正确、验证通过或任务完成 |

Git 可追踪要求当前事实位于 Git worktree 中已经被 Git 跟踪，或者尚未跟踪但未被 ignore 规则排除、能够后续纳入 Git 的文件位置；不要求每次事实写入后立即 commit。未提交的新文件和修改可以支持当前接续；在创建 commit 后，才能进一步声明相应版本已经获得提交标识和可回查的历史关系。

有效 Git worktree 可能尚未创建第一个 commit。此时 Working Tree 中满足其它条件的内容仍可支持当前工作，但不得声称 `HEAD` 已解析到提交、已有 commit 标识或已经形成 Git history；需要历史锚点的行动必须等待相应 commit 实际创建。

commit message 可以说明变更意图、范围或验证情况，但这些说明必须由实际文件、来源规则和验证依据支持。commit 创建成功只证明 Git 接受了该快照和 metadata，不证明 message 中的语义真实，也不完成 Human Gate、事实验证、发布、部署、PR、merge 或远端同步。

具体提交时机、暂存范围、提交拆分、message 格式、Hook、push 和远端 ref 写入不由本文规定。只有在后续证明存在稳定重复价值时，才由行动模板或项目策略承接。

## 10. 代表性判断场景

| 场景 | 当前判断 |
|---|---|
| 已跟踪事实文件在 Working Tree 中修改但未提交 | 读取当前文件；在 §§5.1、8 的其余条件同时成立，包括需要时适用事实模型时，可以作为当前稳定事实，Git 差异作为溯源上下文 |
| 新事实文件尚未跟踪且未被 ignore 规则排除 | 在 §§5.1、8 的其余条件同时成立，包括需要时适用事实模型时，可以作为当前稳定事实；不得声称已经存在 commit 历史 |
| 新文件被 ignore 规则排除且尚未被 Git 跟踪 | 不满足当前 Git 可追踪承载条件；不得作为稳定事实消费 |
| 已跟踪文件的路径后来命中 ignore 规则 | ignore 不自动取消已有跟踪身份；仍按当前文件、来源规则、验证要求和需要时适用事实模型判断 |
| 当前文件已删除，但旧路径仍存在于 `HEAD` | 不把 `HEAD` 中旧文件作为当前事实；显式历史审查可以读取并标明版本 |
| Human 明确要求检查某个 commit、Git ref 或版本差异 | 读取指定历史对象或参与比较的各版本，保留版本定位，不把历史内容改写成当前事实 |
| Index、`HEAD`、缓存或 Web 视图与 Working Tree 不同 | 判断当前事实时使用 Working Tree；其它内容只承担待提交、历史或派生视图作用，并报告相关差异或过期状态 |
| Git worktree 尚无第一个 commit | 当前文件仍可在其它条件成立时支持当前工作；不得声明已有 `HEAD` 提交或 Git 历史锚点 |

## 12. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 的事实源定位、事实源边界，或者允许 Git 可追踪文件以外的内容成为 LDVH 稳定事实承载；
2. 改变 Working Tree 作为当前默认读取视图的边界，或者重新要求只有 commit 后的内容才算当前事实；
3. 为同一稳定事实建立多个需要分别维护的权威位置，或者在冲突位置之间选择新的唯一位置；
4. 决定当前事实冲突、来源无法回指或 Git 无法识别目标文件时的修复方向、唯一位置选择、受影响范围或是否放弃将相关内容作为稳定事实消费。

Human 当次已经明确决定相应事项时，不重复请求同一决定；但 Human 回应不能替代事实源文件写入与回读、来源规则或事实模型校验、技术验证或 Git 历史形成，也不能使不满足事实源边界的内容取得稳定事实身份。

## 13. Stop Conditions

出现以下任一情况时，必须暂停依赖受影响事实或溯源结论的最小行动、对象或声明范围：

1. 判断项目当前事实时，AI、Helper 或 Code 正在用 Index、`HEAD`、远端分支、缓存、索引或 Web 视图覆盖当前 Working Tree 内容；
2. 显式历史对象或版本比较没有保留版本身份，或者历史内容正在被冒充为项目当前事实；
3. 当前文件无法解析或违反适用来源规则、需要时事实模型，却准备静默回退到旧提交继续；
4. 聊天、AI 推理、命令或测试输出、Human 当前指令、工具成功、配置、缓存、派生结果或 Git commit 正在被直接冒充为稳定事实、规则、验证通过或完成证明；
5. 同一稳定事实存在相互冲突的权威位置，且无法按来源规则确定当前应消费哪一处；
6. 准备写入或更新稳定事实，但没有已定义的来源规则或目标位置；内容需要对象化、状态化或证据化管理时，没有适用事实模型或当前状态要求；
7. 来源规则要求保留来源回指，但当前信息无法以所需精度回到其出处或形成依据；
8. 正在声明某个版本已有 Git 历史锚点，但对应修改尚未 commit、`HEAD` 尚不可解析，或提交标识与目标内容不匹配。

未提交、dirty、untracked、进行中状态或缺少远端同步本身不构成停止条件。暂停期间可以继续只读核对当前文件、Git 状态与差异，修正事实结构或来源回指，补充验证，拆分冲突对象，准备 Human Gate，并继续不依赖受影响结论的普通工作。

受影响范围只能在当前读取视图或历史对象身份已经纠正、事实结构与来源要求已经满足、冲突位置已经处理、需要时相应事实模型已经存在、历史声明已经缩小到实际提交范围，或者 Human 已对其保留事项作出作用范围清楚的决定后恢复。
