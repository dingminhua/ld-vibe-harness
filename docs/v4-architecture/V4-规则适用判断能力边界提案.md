# V4 规则适用判断能力边界提案

> 记录性质：本文是正式 Specs 和 Code 启动前的架构调查与候选方案，不是规则源，不定义公开操作，不声明 Helper 已能自动判断自然语言规则。
> 核验日期：2026-07-13。

## 1. 本次要回答的问题

L3/L4 规范内容读取已经实现。下一步原计划是建立“规则适用判断”能力。本次先回答：

1. Helper 现在是否已经能定位由来源规范定义的一条具体规则，并对其执行可重复的判断；
2. 现有规范内容、工作对象和当次信息是否足以作为可复核的机器输入；
3. 判断语义应由哪个来源定义，Helper 是否会因执行通用判断而反向创造规则含义；
4. 如果当前条件不足，什么应继续由 AI Agent 负责，什么条件成立后才能重启 Helper 公开操作设计。

## 2. 当前规则源已经确定的边界

### 2.1 00 的上位边界

`ldvh-root` 已经要求：

1. 命中来源规范声明的适用范围时，其规则必须执行；
2. 未命中具体规则时，不限制 AI 的普通求解路径；
3. Human Gate 和 Stop Conditions 与一般的规则命中不能合并成一个“允许/禁止”结果；
4. 规则适用条件、效力或权威关系无法确认，且继续可能违反要求时，必须暂停受影响范围；
5. 未实现、未接入或未验证的范围，不得被声明为已保障或已可用。

因此，任何候选的通用规则适用判断模型都不得引入“未命中即禁止”的默认授权语义，也不得把规则适用、Human Gate 决定、Stop Conditions 触发和行动已完成折叠为同一状态。

### 2.2 01、02 与具体来源的责任

`specification-model-foundation` 定义当前规则源、规范身份、规范依据、结构归属、附件授权、替代关系和渐进式披露，但明确不定义每条具体规则的适用判断与效力。`work-object-governance-scope` 定义工作对象及管辖范围，但管辖成立不等于其中每条规则都已命中。

每条规则的语义、适用对象、条件、效力，以及其适用范围内相关的 Human Gate 和 Stop Conditions，必须由相应来源定义。规范依据、结构归属或建设顺序不自动产生规则优先级。

### 2.3 04 已有的规则适用判断结果定义与报告要求

`helper-cli-service-contract` §9 已定义“规则适用判断结果 / Rule Applicability Evaluation Result”。当 Helper 报告对某条已定位规则的判断时，必须保留具体规则的来源位置、对象与范围、实际输入、来源条件、判断结果、缺口，以及相关 Human Gate 和 Stop Conditions 范围。

但是：

1. 04 没有声明对应的 Helper 公开操作；
2. 04 明确不定义哪条来源规则已命中；
3. 04 没有授予 Helper 创造通用效力或优先级的权限；
4. 因此，现有 `applicability` 字段定义不能被解释为执行通用规则适用判断的程序已经存在。

这与已通过的责任审计一致：不建立统一定义全部规则命中和效力的模型；Helper 只在具体来源语义已经成立时组织和报告结果。

## 3. 当前无法建立通用公开操作的缺口

### 3.1 来源尚未定义可唯一定位的一条具体规则

当前可稳定定位规范及其标题路径，但一个 Markdown 章节可以包含多条要求、例外、Human Gate 和 Stop Conditions。`spec_key + heading_path` 可以定位来源内容，不一定能唯一标识要执行适用判断的一条具体规则。

如果没有由来源规范定义且可唯一定位的一条具体规则，Helper 选择某一句或某一项执行判断，就会变成由 Code 决定什么是规则。

### 3.2 来源尚未定义可由 Code 确定判断的通用适用条件

当前规则主体是自然语言 Markdown。各来源可以表达适用对象、条件、例外、义务、Human Gate 和 Stop Conditions，但尚未定义通用条件 Schema、类型系统、运算符或判断执行失败的语义。

如果 Code 将自然语言自行翻译为布尔条件，就会取得本应属于来源规范的含义定义权。如果调用未定义的模型对自然语言作判断，则会把非确定性推理写成 Helper 确定性能力，且当前没有模型提供者、提示、版本、失败或证据契约支持这个声明。

### 3.3 规则所需的输入尚未被完整定义

04 的共同请求允许 `task`、`work_object_locators`、`arguments` 和 `observed_context`，但这些通用容器不会自动提供明确且足以完成判断的输入集合，也不会说明哪个来源对每个值负责、值在什么时间和对象范围内有效，以及未经验证的调用方观察如何与稳定事实区分。

尚未建立具体事实类型并不意味着所有规则都必须等待事实服务才能由 AI 理解，但它意味着现在不能声明已有一个通用、可验证的 Helper 输入契约。

### 3.4 判断不能形成结论的不同原因尚未完整区分

04 当前的 `applicability` 使用：

```text
applies
does_not_apply
insufficient_information
not_evaluated
```

它已经区分“依据不足”与“尚未检查”，但尚未单独表达“已尝试判断，但因来源冲突、要判断的具体规则无法唯一定位、条件不受支持或判断执行失败而不能形成适用结论”。

这个问题不应现在直接通过新增枚举修复。需要先出现第一类满足 §6.2 条件的具体规则，再判断哪些属于具体操作结果，哪些应由 Helper 外层 `outcome`、`gaps` 或 `diagnostics` 承接。

### 3.5 V3 没有提供可继承的通用规则适用判断模型

V3 只读调查没有发现独立、可审计的规则适用判断器。实际实现主要是：

1. 规范正文使用自然语言说明适用范围；
2. Action Guide 按 `consumption_timing` 的字符串相等筛选要求，`task` 并不参与命中判断；
3. 以路径前缀、扩展名、规范编号和固定名单对目标分类，然后附加固定读取清单；
4. `action_classifier` 判断工具或命令的读写副作用，不判断来源规则对当次事项是否适用；
5. Pitfall 的 `applicability` 只是自然语言经验边界，Code 只检查字段存在，没有使用该内容得出规则适用判断结果。

V3 的主要失败模式是：用全局消费时机代替具体规则命中；使用默认固定读取造成信息过载；新资产必须同步 Code/tests 中的路径白名单；将服务范围与单条规则范围混合；将规则、导航、验证、Human Gate 和 Stop Conditions 候选、行动建议混入同一个大结果；以及对具体中文文本、编号和路径形成大量测试耦合。

可保留的 V3 经验只是边界性经验：来源规范负责适用范围和效力；管辖、规范依据、结构归属、附件授权、替代关系、读取候选和导航不产生适用结论；`does_not_apply` 必须有明确不命中依据；未知、缺失和冲突必须如实保留；多对象应逐项判断；未提交的 Working Tree 也属于当前信息。这些经验支持本文不开发通用判断操作的结论，不支持恢复 V3 的字段、状态、固定事件闭集、路径分类器或 Action Guide 结果。

## 4. 候选方案比较

| 候选方案 | 实际做法 | 主要问题 | 结论 |
|---|---|---|---|
| 现在建立处理任意自然语言规则的判断程序 | Helper 自行理解任意 Specs 文本并输出适用结论 | 来源尚未定义可唯一定位的一条具体规则、条件语义、结构化输入或可复核判断契约；这会让 Code 或模型创造规则含义 | 不采用 |
| 让调用方提供结论，Helper 只包装返回 | AI 在 `arguments` 中提供 `applies` 等结果，Helper 校验字段后按服务契约返回 | 会把调用方主张冒充为“Helper 判断结果”，Helper 没有执行新的可重复检查 | 不采用 |
| 建立只返回 `not_evaluated` 的公开操作 | 保留公开操作形式，对自然语言规则不实际判断 | 调用不会产生规则是否适用的新信息，只增加调用和维护负担 | 不采用 |
| AI 当前依来源内容和当次可回指信息作语义判断，Helper 只提供已实现并验证的操作 | AI 使用 `read-specification-content` 取得可回指的 L3/L4 当前内容，结合工作对象和当次可回指信息判断；无法确认且继续受影响行动可能违反来源要求时，按 00 暂停该范围 | 尚未把语义判断自动化，但不会让 Helper 过度声明其实际没有执行的判断 | **当前推荐** |
| 一组具体规则共享同一来源定义的输入与判断契约后，建立只处理该组规则的公开操作 | 只对来源已经定义可唯一定位的一条具体规则、所需输入和条件语义的范围执行判断 | 需要后续具体来源与 Code/tests，且可能形成多个领域操作而不是一个通用操作 | **未来可采用** |

## 5. 对行业模型的核验结论

本次只从官方或一手资料核对 OPA、Cedar、XACML/ABAC 与 DMN。它们对结构化输入、判断逻辑、执行分工和诊断提供了不同的成熟实践，但不共同保证同一组结果语义或字段。跨模型比较支持 LDVH 作出以下自身设计判断：

1. 对于拟由 Code 自动判断的范围，来源必须提供可唯一定位的具体规则，所需输入和判断条件必须具有明确、可供 Code 消费的结构；
2. 判断逻辑必须有明确的策略或决策定义；
3. 判断与实际执行分离；
4. LDVH 需要主动区分“不适用”、“输入不足”、“尚未检查”和“判断执行失败”；现有模型有的明确区分，有的会合并，不能直接继承其结果语义；
5. 不同模型分别提供策略标识、输入、诊断或决策日志机制，支持 LDVH 将来源回指与可复核依据作为自身契约要求，但这不是全部模型共同保证的字段集合。

可以借鉴的是：请求提供结构化输入，判断使用已定义逻辑，结果保留实际依据，执行由相应调用方负责，四者不相互替代。这不意味着将 LDVH 改造为授权引擎：

- OPA 的结构化输入、判断与执行分离及决策日志可用于借鉴输入审计、决策关联和策略版本记录；LDVH 所需的精确来源回指仍须由自身契约定义，且 OPA 的 `undefined` 不能直接成为 LDVH 的统一含义；
- Cedar 的明确请求角色、决定性策略和错误诊断值得借鉴；但 `Allow/Deny`、default deny 和 forbid-overrides 属于授权领域，与 00 的普通求解自主边界不同；
- XACML 对 `NotApplicable` 与 `Indeterminate` 的区分支持对不同原因分别处理；但 Permit/Deny、通用规则组合算法和 XML 契约不应直接引入 LDVH；
- DMN 的决策、输入数据和决策依据分离支持“先定义需要什么输入”；但 DMN 1.5 的 FEEL `null` 可能同时承载缺失值和错误，不能直接作为 LDVH 的缺口语义，自然语言 Specs 也不能因此被当成已定义的决策表。

主要依据：[OPA 官方文档](https://www.openpolicyagent.org/docs)、[OPA Decision Logs](https://www.openpolicyagent.org/docs/management-decision-logs)、[Cedar Authorization](https://docs.cedarpolicy.com/auth/authorization.html)、[Cedar Policy Validation](https://docs.cedarpolicy.com/policies/validation.html)、[XACML 3.0 Core](https://docs.oasis-open.org/xacml/3.0/xacml-3.0-core-spec-os-en.html)、[NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)和 [OMG DMN 1.5](https://www.omg.org/spec/DMN/1.5/About-DMN)。

## 6. 推荐的当前边界

### 6.1 当前应当做什么

1. 不定义通用 `evaluate-rule-applicability` 公开操作；
2. 不让 Code 或模型自行将全部自然语言 Specs 翻译为通用条件系统；
3. 不让 Helper 将 AI 或其它调用方提供的结论冒充为 Helper 的确定性判断；
4. AI Agent 当前通过 Helper 读取可回指的 L3/L4 内容，结合当次工作对象和当次可回指信息作语义判断；
5. AI 无法确认规则适用条件、效力或权威关系，并且继续受影响行动可能违反来源要求时，按 00 暂停该受影响范围；可以安全补充的只读依据继续补充，确实需要 Human 判断时再进入 Human Gate。对 Human Gate 或 Stop Conditions 是否存在的普通怀疑不自动创造 Human Gate 或 Stop Conditions；
6. 04 §9 已有的规则适用判断结果定义与报告要求暂时保留，但不因此声明公开判断能力已可用。

### 6.2 何时可以重启公开操作设计

只有候选规则范围同时满足以下条件，才重新评估对应公开操作：

1. 来源规范定义可稳定、唯一定位的一条具体规则；
2. 来源自己定义可由 Code 按已定义条件确定判断的适用条件和结果语义；
3. 工作对象、行动或声明对象及所需事实输入有明确 Schema；
4. 每项输入都能保留来源回指、观察时点、对象与有效范围；
5. 不适用、信息不足、尚未检查、来源冲突、条件不受支持和判断执行失败能被分别处理；
6. 结果不会被误解为行动已授权、Human Gate 已通过、Stop Conditions 已解除、规则已履行或工作已完成；
7. Code/tests 能独立复现判断结果及失败路径，并且能回指实际使用的当前规则和输入。

满足条件的实现可能是只处理一组共享同一来源定义的输入与判断契约的具体规则的独立操作，不预设必须有一个处理全部 Specs 的通用操作。

## 7. 对全局建设顺序的影响

原路线中“L3/L4 读取 → 规则适用判断 → 具体事实类型”默认了当前会出现由来源规范定义且可唯一定位的一条具体规则，并且其条件已可由 Code 确定判断。本次调查表明，该前提尚未成立，当前不应开发这个通用操作。

推荐调整为：

```text
L3/L4 当前规范内容读取（已实现）
→ AI 依来源内容继续承担当前语义判断
→ 逐类审核具体事实类型，并明确其事实源和结构化契约
→ 建立事实读取与受控回写
→ 在一组具体规则共享同一来源定义的输入与判断契约时，按具体范围重新评估规则适用公开操作
```

这不是降低 V3 “边界识别”目标，而是避免在缺少可证明条件时过度声明 Helper 能力。当前 AI 仍必须读取足以包含适用范围、必要定义、验证要求、Human Gate 和 Stop Conditions 的 L3 内容；无法保证完整性时展开到 L4，并履行已经命中的规则。变化的只是“Helper 已可通用自动判断”的建设假设。

## 8. 需要 Human 确认的边界

1. 当前不新增通用规则适用判断公开操作，也不启动对应 Code；
2. 当前仍由 AI Agent 根据自然语言规则的含义、当次实际输入及其来源回指，判断规则是否适用；无法确认且继续受影响行动可能违反来源要求时，才按 00 暂停该范围，确需 Human 判断时再进入 Human Gate；
3. 不为了这个候选能力，现在向所有 Specs 强行加入统一规则 ID 和通用条件语言；
4. 04 §9 的规则适用判断结果定义与报告要求暂时保留，四值结果对不同失败原因的处理等待首类满足 §6.2 条件的具体规则出现时再审核；
5. 下一主线转入具体事实类型的逐项准入审核，同时保留未来对一组共享同一来源定义的输入与判断契约的具体规则建立独立公开操作的可能性。
