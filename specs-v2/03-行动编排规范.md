## 1. 本文解决的问题

本文定义 LDVH 如何把 AI 行动从自由执行收束为可识别、可暂停、可验证、可交还、可分流和可回写的行动编排。

本文解决：

1. AI 执行前应如何获得最小可行动 Context；
2. AI 如何识别当前任务是否命中某个 Scenario；
3. AI 何时必须触发 Gate 或 Human Gate；
4. 主控 AI 如何调度 Skill、Agent、Code、Web 和运行时扩展，并回收它们的输出；
5. AI 执行中发现问题时如何分流、暂停、降级或继续；
6. 行动过程中的过程输出、证据触发和事实源回写应如何交给 07 判断；
7. 30-59 行动编排成员如何声明身份、状态、锚点、可测试性和能力资产；
8. 普通规范保障要求何时应由行动编排接管为执行闭环。

本文不定义具体事实模型字段、全局事实源规则、Git commit message 契约、Code 输出 Schema、Web 页面契约、运行时扩展资产登记或测试治理本体。上述内容分别由 02、07、04、05、06 和 08 承接。

## 4. 行动编排定义、定位与分层

行动编排是 LDVH 对某一类 AI 行动控制事实的标准化建模结构。它定义 Context、Scenario、Gate、执行流程、执行中问题分流、反合理化暂停、主控调度、Skill 和 Agent 调度、Code 与命令协作、过程输出、证据触发、事实源回写触发、环境适配边界、可测试性锚点、保障要求接管和失败降级。

行动编排分三层：

| 层 | 职责 |
|---|---|
| 03 主规范 | 定义行动编排通用规则、成员机制、接管原则和跨构成要素边界 |
| 30-59 成员主文件 | 定义具体行动流程的准入、Context、Scenario、Gate、执行、证据、回写、可测试性和能力资产 |
| Skill/Agent/Hook/Code/Web 等能力 | 提供执行外壳、专项分析、事件触发、确定性诊断或展示入口，输出必须交还主控 |

30、41、42、43、44 等具体流程不得被 03 合并成一个总流程。03 只定义所有成员必须遵守的通用结构和治理边界。

## 5. 行动编排准入与新增依据

只有当某类 AI 行动具备可重复的场景、稳定的 Context、明确 Gate、可验证结果、事实源回写或缺口分流需求时，才应建立行动编排。

以下情况可以触发行动编排新增或升级判断：

1. 同类 AI 行动反复出现，且依赖固定读取顺序、判断步骤或停止点；
2. 多个规范保障要求需要组织成跨步骤执行闭环；
3. 行动涉及 Human Gate、长期证据、事实源回写、能力资产调度或失败分流；
4. 仅靠规范散文和聊天提醒无法稳定避免重复误判；
5. 需要 Code、Skill、Agent、Hook、Web 或 CI 提供协作保障。

不得为了包装普通建议、一次性讨论、单个命令或纯展示入口而新增行动编排。

## 6. Context、Scenario、Gate 与 Human Gate

Context 定义行动开始前 AI 必须读取或查询的最小可行动上下文。Context 应优先指向事实源、章节锚点、对象 ID、Code 查询入口或明确命令输出，不得要求 AI 无条件全文读取大量文档。

Scenario 定义行动进入信号。Scenario 必须能被 AI 从用户目标、文件状态、事实对象状态、Code 诊断、错误输出或 Human 指令中识别，不得只写抽象愿景。

Gate 定义行动必须暂停、降级、分流或等待 Human 的条件。Human Gate 只能由 Human 完成确认、授权、方向校正或验收。Code、Skill、Agent、Hook、Web、测试或聊天判断不得替代 Human Gate。

行动中的 Human Gate 记录必须遵守 01 定义的最小记录契约，至少包含时间、决策、范围和约束。具体行动成员可以增加触发原因、确认事项、验证要求、回写位置、残留风险和后续动作，但不得只用“已确认”“用户同意”或按钮点击替代可追溯记录。

具体行动成员必须在自身主文件中声明 Context、Scenario、Gate 和 Human Gate 锚点；03 只维护通用原则。

## 7. 主控调度与能力协作边界

行动编排默认由主控 AI 负责最终判断。Skill、Agent、Code、Web、Hook、CI 和环境工具只能提供执行能力、专项视角、确定性诊断、事件触发或展示入口。

| 能力 | 在行动中的职责 | 不负责 |
|---|---|---|
| Skill | 封装稳定流程步骤、输入输出、失败处理和交还格式 | 不新增规则、不替代主控判断、不替代事实源 |
| Agent | 在隔离上下文中做专项审查、争议分析或并行探索 | 不直接写入事实源、不独立决定状态流转 |
| Code | 解析、校验、聚合、诊断、受控写入前检查 | 不替代 Human Gate、不反向定义规范规则 |
| Web | 展示 Human-facing 状态、风险、证据和待确认事项 | 不维护第二事实源、不替代行动判断 |
| Hook | 在生命周期事件点触发检查、提示、阻断或记录 | 不证明当前环境完整支持 LDVH |
| Rules | 提供入口路由、最小读取顺序和 STOP 点 | 不复制 specs 正文、不成为第二规范 |

所有能力输出均为过程输出，必须交还主控。主控应判断是否继续执行、触发 Gate、回写事实源、分流缺口或结束流程。

## 8. 过程输出、证据与事实源回写触发

行动执行会产生聊天答复、Skill 输出、Agent 输出、命令输出、诊断报告、Web 展示、候选草案和风险提示。这些默认不是最终事实源。

03 只定义行动中何时需要触发事实源判断：

1. 行动形成任务、决策、经验、风险、缺口、验收或关闭判断；
2. 行动改变规范、事实模型、行动流程、Code、Web、运行时扩展或测试规则；
3. 行动产生需要长期追溯的验证结论、失败诊断、降级说明或 Human Gate 记录；
4. 行动完成事实源修改，需要 Git commit records 追溯。

具体回写位置、Git 追溯、过程输出回写条件和不得回写内容由 07 定义。事实模型实例如何承载证据由 02 和具体模型成员定义。测试验证声明由 08 定义。

## 9. 执行中问题分流与失败暂停

AI 在行动执行中发现新问题时，必须按闭集判断问题性质并采取对应行动，不得跳过分流，也不得把所有问题统一处理为阻塞或忽略。

| 分流类型 | 判断条件 | 处理方式 |
|---|---|---|
| `blocking` | 直接阻塞当前行动成功标准、Gate 条件、事实源回写或验收判断 | 回到当前行动内部处理，修复后重新验证 |
| `follow_up` | 不阻塞当前行动，但需要后续跟进 | 记录为 Spark、新 WorkCase 或待接管缺口候选，当前行动不等待 |
| `opportunistic_fix` | 与当前行动直接相关，修复成本极低，且不引入新风险 | 在当前行动范围内修复，并在验证或关闭材料中记录 |
| `adr_candidate` | 涉及架构决策、技术选型、规范方向或高影响取舍 | 分流为 ADR proposed 或 Spark 候选，必要时触发 Human Gate |
| `pitfall_candidate` | 具有可复用教训价值，后续项目或场景可能重复遇到 | 分流为 Pitfall 候选，并回指当前行动证据 |
| `spark_candidate` | 有保留价值但尚未达到 ADR、Pitfall 或 WorkCase 条件 | 分流为 Spark 候选 |
| `study_candidate` | 需要后续研究、外部资料整理或来源材料吸收 | 分流为 Study 候选、研究材料或来源材料吸收路径 |

分流必须遵守以下约束：

1. `blocking` 不得降级为 `follow_up`、候选对象或忽略项；
2. `opportunistic_fix` 的成本或风险不清楚时，必须降级为 `follow_up`；
3. ADR、Pitfall、Spark、Study 候选默认不阻塞当前行动，除非它们影响当前成功标准、Gate 或事实源回写；
4. 每个分流决定必须能回指问题来源、当前行动、判断理由、处理方式和后续事实源位置；
5. 具体事实模型实例如何记录候选、证据和关联对象，由 02 与 20-29 成员主文件定义。

AI 不得用“应该通过”“看起来没问题”“逻辑上可行”“按理说已完成”等推测性表述替代验证证据。出现以下任一情况时，必须暂停继续宣称完成，并按问题性质进入 `blocking`、`follow_up`、Human Gate、专项审查、事实对象分流或具体行动编排：

1. 验证命令失败、缺少验证命令、验证范围不足或验证结果不可复现；
2. Gate 条件、事实源回写、状态流转、证据留存或验收材料存在未满足项；
3. 同一问题连续修复后仍失败，或失败原因不能明确归属；
4. 工具输出、Web 状态、Agent 输出、测试结果或聊天结论与 Git 文件事实源不一致；
5. 需要接受长期降级、关闭 open/degraded 缺口或跳过部分验证。

修复后必须重新执行相关验证，或明确记录无法验证的原因、残留风险和后续分流。不得只说明“已修复”或“已调整”后直接关闭。

## 10. 30-59 成员关系、成员身份与 active 判定

30-59 是具体行动编排成员编号段。成员主文件放在 `specs-v2/` 根目录；成员集合事实源来自成员主文件自描述，而不是手写目录清单。

具体行动编排成员必须同时具备：

1. `v2_spec`，承载规范写作身份、写作状态、迁移来源、active 事实源和 Code/知识地图消费类别；
2. `v2_action_member`，承载行动编排集合成员身份、集合状态、规则锚点、接管关系、能力保障映射和成员级 Code 消费入口。

`v2_spec.status` / `v2_spec.authority` 描述规范写作状态和 v2 写作区权威状态；`v2_action_member.collection_status` 描述该行动编排在行动编排成员集合中的治理状态。两者不得混用。

所有状态的 `v2_action_member` 都必须声明成员身份字段：

1. 成员身份、编号、英文名、中文名和 canonical path；
2. 集合状态；
3. Code 消费入口。

active 成员还必须声明可执行锚点和接管映射：

1. Context、Scenario、Gate、执行、问题分流、回写、证据和可测试性锚点；
2. `assurance_takeover`；
3. `capability_assets`。

planned、candidate、reserved、removed 或 deprecated 成员可以缺少 active 可执行锚点，但必须在成员主文件中说明不可执行原因、后续条件、替代入口或清退原因；不得因为锚点缺失而被解释为 active 流程。

行动编排成员集合状态闭集如下：

| 状态 | 含义 | 执行边界 |
|---|---|---|
| `active` | 已是当前 active 行动编排集合成员；v2 未切换前必须能回指 active v1 成员主文件 | 可以作为可执行流程，但仍受 active 事实源和 Human Gate 约束 |
| `planned` | 已有明确规划和编号意向，但尚未形成可执行成员主文件 | 不得执行，不得被 Rules/Skill/Agent/Hook 默认调用 |
| `candidate` | 候选行动编排，概念或草案仍需论证 | 不得执行，不得进入默认读取顺序或能力资产硬依赖 |
| `reserved` | 编号预留 | 不得被解释为已存在行动编排 |
| `removed` | 已移除或清退 | 不得作为当前流程入口 |
| `deprecated` | 已废弃或被替代，必须说明替代入口或关闭理由 | 不得作为新行动入口，只能用于追溯 |

只有成员自描述为 active、存在主文件、锚点完整且通过必要检查的成员，才构成当前可执行的行动编排。planned、candidate、reserved、removed 或其它非 active 状态不得被当作已生效流程执行。

Code 和知识地图可以派生成员集合索引、读取建议和诊断结果，但不得替代成员主文件。

`v2_action_member` 的详细字段说明由 `03.Att.01-成员身份字段表.md` 承载；成员主文件骨架模板由 `03.Att.02-成员主文件骨架模板.md` 承载；成员一致性辅助核对表由 `03.Att.03-成员一致性辅助核对表.md` 承载。附件只承载各自授权的信息对象，不得单独改变本文定义的成员主文件权威边界、成员身份原则、集合状态闭集、行动流程边界或 Human Gate。

## 11. 成员主文件骨架与可测试性锚点

具体行动编排成员主文件必须采用 `03.Att.02` 授权的专属骨架，并至少包含：

1. 行动定位与适用场景；
2. 准入条件；
3. 事实源边界；
4. Context 要求；
5. Scenario 识别；
6. 执行流程；
7. 执行中问题分流与失败暂停；
8. Gate 触发条件；
9. Skill 和 Agent 调度；
10. Code 与命令入口协作适配；
11. 事实源回写与证据留存；
12. 环境适配边界；
13. 行动特有可测试性锚点；
14. 规范保障要求；
15. 检查要求；
16. 待补齐事项。

行动特有可测试性锚点用于说明该流程应如何被验证和反例检查。测试治理、测试实现归属和验证声明归 08，成员主文件只维护行动本体的可测试条件。

## 12. 保障要求接管与能力保障闭环

行动编排可以接管规范保障要求，但接管必须显式、可追溯、可验证。

接管必须说明：

1. 来源规范和保障要求；
2. 接管范围；
3. 输入来源和事实源边界；
4. 执行流程、验证方式和证据位置；
5. Human Gate 条件；
6. 失败降级和缺口分流方式；
7. 所需 Skill、Agent、Hook、Code、Web、CI 或运行时扩展能力。

行动编排接管的是执行责任，不是来源规范的规则权威。接管流程降级、移除、重命名、编号变化或失去 active 状态时，必须触发来源规范和相关能力资产同步检查。

`capability_assets` 只登记“本行动编排需要哪些能力保障及其当前映射”，不替代 06 定义的运行时扩展承载物自描述，也不声明 Rules、Skill、Agent、Hook、Code、Web、CI 或环境入口已经部署完成。固定 Rules、Skill、Agent 或 Hook 的资产身份、来源规范、消费场景、输入输出、验证方式、同步触发和废弃规则由 06 及对应承载物自描述承接。

当行动编排需要某类能力但承载物尚不存在、不可发现、未验证或权限不足时，成员主文件必须记录缺口、降级方式、验证要求和后续分流，不得用 `capability_assets` 的计划项替代能力保障闭环。

## 14. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 新增、删除、重命名、合并、拆分或降级行动编排成员；
2. 将非 active 成员解释为可执行流程；
3. 改变 Context、Scenario、Gate、Human Gate、回写触发或证据要求；
4. 改变保障要求接管范围、接管状态或接管流程编号；
5. 允许 Skill、Agent、Code、Web、Hook 或 Rules 替代主控判断、事实源或 Human Gate；
6. 接受行动编排、能力保障、验证或事实源回写长期降级；
7. 发现本文与 active 06、03.03、30-59 成员、07 事实源规则或 01 治理规则冲突。
