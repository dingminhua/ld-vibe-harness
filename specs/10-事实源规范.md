# 事实源规范

> 创建日期：2026-05-28
> 定位：PM Kit 事实源层基础规范，定义事实放在哪、边界是什么、如何组织
> 适用范围：所有接入 PM Kit 的项目
> 上位依据：`specs-v2/00-PMKit理念与纲要.md`
> 约束对象：事实源载体和文档治理行为

---

## 一、本文解决的问题

本文解决 PM Kit 中项目事实应该由哪些 Git 文件事实源承载、不同事实源载体如何分工、AI 和工具如何避免制造第二事实源的问题。

PM Kit 的目标不是让所有信息都进入同一个目录，也不是让工具界面成为项目事实的权威位置。PM Kit 需要让 AI 在进入项目后，能够稳定判断一个事实应从哪里读取、应写回哪里、哪些位置只能作为索引或派生视图，以及哪些写入行为需要等待人确认。

本文将旧版 specs/03 系列中属于事实源层的稳定规则整合为单一基础规范，不创建子文档。

---

## 二、与 00 总纲的关系

00 定义 PM Kit 的核心问题是：AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。

本文对该问题的回应是：定义项目事实进入 Git 文件事实源时的治理方式。

1. AI 通过事实源载体边界知道该读什么；
2. AI 通过事实源选择流程知道应写回哪里；
3. AI 通过单一事实源原则知道不能重复维护同一事实；
4. AI 通过 Kit Base、docs、ADR、Rules、派生视图等载体边界知道哪些事实应结构化，哪些事实应说明化，哪些事实只能派生展示；
5. AI 通过 Human Gate 判断知道何时停下等待人确认。

00 §四定义了事实源的五条基础原则，本文将其展开为完整的治理规则体系。00 §七.2定义事实源层（编号 10）回答"事实放在哪、边界是什么、如何组织"，本文是该层的权威规范。

## 三、事实源边界声明与治理总原则

**事实源边界声明：** 本文是 PM Kit 事实源层基础规范的权威事实源。本文定义事实源治理总原则、载体边界、选择流程、文档角色与结构治理、结构化对象事实源治理、记录与证据事实源治理、决策与规则事实源边界、派生视图与工具边界、文档命名与入口规则和格式契约。本文不定义管理对象语义、对象状态机、对象字段定义和对象转化关系（见 14-管理对象规范和 20-49 管理对象实践）；不定义 AI 如何执行 Rule、Skill 或 Agent（见 11）；不定义 Python 程序具体实现（见 12）；不定义 PM Web Tools 具体实现（见 13）。

### 3.1 Git 文件事实源原则

需要长期追踪、AI 读取、人审查、工具解析或 Git 追溯的事实，最终必须落到 Git 可追踪文件。

聊天记录、工具缓存、临时 UI 状态、数据库派生视图、运行时索引和模型上下文都不能成为 PM Kit 的最终事实源。

### 3.2 单一事实源原则

同一事实只能有一个权威位置。其他位置只能引用、摘要、索引、聚合或派生展示，不得独立维护同一事实。

当一个事实已经有权威位置时，AI 和工具不得为了便利复制一份可变事实到其他文档、缓存、视图或配置中。

### 3.3 先判对象再判载体

新增事实进入 PM Kit 前，应先判断它属于什么对象、对象关系或执行事实，再依据本文判断进入哪个载体。

对象类型不清楚时，不应直接创建文档、目录或结构化文件。

### 3.4 结构化优先原则

当事实需要高频被 AI 读取、程序校验、工具聚合、状态流转、关系追踪或证据回写时，应优先进入结构化事实源。

Markdown 更适合背景、原因、解释、需求语境、规范说明和人类可读材料。结构化文件更适合状态、关系、检查项、审计字段、证据摘要和可解析对象事实。

### 3.5 被管理项目归属原则

无论 PM Kit 作为原项目子目录接入，还是与原项目并行存在，项目事实都应归属到被管理项目自身。

被管理项目的结构化对象事实源进入该项目的 Kit Base，默认目录名为 `pm-kit-base/`。多个被管理项目分别维护各自的 `pm-kit-base/`，PM Kit Tools 自身作为被管理项目时也遵守同一原则。

### 3.6 工具不是最终事实源

PM Web Tools、Python 程序、缓存、数据库和运行时索引只能作为解析、校验、聚合、展示或受控写入入口。工具产生的稳定事实必须回写到 Git 文件事实源。

## 四、事实源载体边界

### 4.1 specs

specs 是 PM Kit 跨项目基础规范的权威事实源。

specs 承载所有接入 PM Kit 的项目都应继承的基础规范、管理思想、对象规范、事实源治理、AI 协作、工具辅助、初始化和审计规则。

specs 不承载 PM Kit Tools 自身需求、当前进度、项目日志、踩坑记录、工具实现代码或临时迁移计划。

### 4.2 docs

docs 承载 PM Kit Tools 自身项目事实、产品需求、实践、日志、审计、帮助材料和历史素材。

docs 不承载 PM Kit 基础规范。docs 可以承载人类可读说明，但不得重复维护 Kit Base 中的动态对象状态，也不得替代 Kit Base adrs 中的 ADR 记录长期决策原因。

### 4.3 Kit Base

Kit Base 是接入 PM Kit 的项目必须具备的结构化对象事实源基础层，默认目录名为 `pm-kit-base/`。

Kit Base 承载需要结构化、可解析、可流转、可回写和可被工具聚合的项目对象事实。

Kit Base 不以任务为唯一中心。它可以承载多类结构化对象事实，但不承载规范正文、需求长文、帮助材料、代码、工具缓存、UI 状态或聊天记录全文。

### 4.4 ADR

ADR 是已确认、后续应遵守的决策记录，承载于 Kit Base `adrs/` 子目录。

ADR 不替代 specs 正文、Rules 入口或 Change 记录。长期决策升级为规则时，规则正文应进入对应规范或规则入口，ADR 保留为什么这样做的原因。

### 4.5 Rules

Rules 是 AI 执行时的规则入口、约束摘要或项目专属规则承载位置。

Rules 不应复制 specs 大段正文形成第二事实源。Rules 可以索引、摘要或桥接 specs，也可以承载项目专属硬约束，但不得与 specs 基础规范冲突。

### 4.6 Skill 与 Agent

Skill 是可复用执行流程入口，Agent 是独立上下文执行者或专业分工机制。它们可以帮助 AI 执行、分析、整理和回写事实，但不成为项目事实最终事实源。

Skill 或 Agent 产生的稳定事实，应回写到被管理项目对应 Git 文件事实源。

### 4.7 PM Web Tools 与 Python 程序

PM Web Tools 和 Python 程序可以读取、解析、校验、聚合和受控写入 Git 文件事实源。

工具缓存、数据库派生视图、运行时索引和页面状态都不能成为最终事实源。工具展示必须能追溯到 Git 文件事实源。

### 4.8 Context

Context 是由事实源动态组织出的 AI 执行输入、任务背景和行动依据。

Context 不默认成为独立事实源。只有当动态上下文中的内容稳定为对象事实、决策、证据、规则或记录时，才应写入对应载体。

## 五、事实源选择流程

AI 或工具处理新增事实时，应按以下顺序判断：

1. 判断事实所属对象、对象关系或执行事实；
2. 判断该事实是否需要长期保存、审查、校验或追溯；
3. 判断该事实属于规范正文、人类可读文档、结构化对象、决策原因、记录证据、规则入口、工具派生视图还是动态上下文；
4. 检查是否已经存在权威事实源；
5. 若已有权威事实源，只能引用、摘要、聚合或受控更新，不得复制维护；
6. 若尚无权威事实源，依据本文载体边界选择载体；
7. 判断是否涉及事实源边界变更、长期规则变更、对象关闭、证据覆盖或其他 Human Gate；
8. 写入后应留下可追溯的变更记录、证据、决策或检查结果。

## 六、文档角色与结构治理

### 6.1 文档角色

文档类载体至少应能归入以下角色之一：

| 角色 | 含义 |
|---|---|
| 基础规范 | 可跨项目继承、约束 AI、人或工具长期行为的规范正文 |
| 项目事实 | PM Kit Tools 或被管理项目自身的需求、实践、帮助、日志和审计材料 |
| 输入池 | 尚未任务化或未稳定归属的临时输入 |
| 记录类事实源 | Change 记录、踩坑、发布记录、执行记录等实际发生过的记录 |
| 决策材料 | 决策原因、背景和影响说明，长期决策应进入 ADR |
| 审计/归档 | 审计快照、历史材料和不再作为当前事实源但有追溯价值的内容 |
| 帮助材料 | 示例、说明、使用指南和教程 |
| 索引 | 指向详情事实源的轻量入口，不维护详情正文或可变状态 |

一个文档可以服务多个阅读目的，但不能同时维护多个权威事实源。

### 6.2 specs 与 docs 的结构边界

specs 承载 PM Kit 基础规范。进入 specs 的内容必须具有跨项目复用价值、概念边界稳定、能约束长期行为。

docs 承载 PM Kit Tools 自身项目文档、产品需求、实践、日志、审计、帮助资料和历史素材。docs 不承载 PM Kit 基础规范。

接入项目可以由初始化依据项目实际生成适合的文档结构，但必须满足：事实源角色清晰、AI 可读取、人可审查、工具可解析或聚合、Git 可追溯、不重复维护同一事实。

### 6.3 拆分治理

文档满足以下任一条件时，应评估拆分必要性，并判断是否触发 Human Gate：

1. 同一文档承载多个生命周期明显不同的事实；
2. 同一文档同时维护规范、需求、任务状态、审计和日志；
3. 文档过长导致 AI 或人难以定位权威事实；
4. 文档中的某部分已具备独立跨项目复用价值；
5. 子主题需要独立 Human Gate 或独立审核。

拆分后的每个文档必须明确自身角色、权威边界和与原文档的关系。不得通过拆分制造第二事实源。

### 6.4 合并治理

文档满足以下任一条件时，应评估合并必要性，并确认合并后唯一权威事实源：

1. 多个文档维护同一事实；
2. 文档只是另一事实源的重复摘要；
3. 文档长期不被引用且无独立事实源价值；
4. 拆分导致 AI 需要跨多个文件才能理解同一规则完整语义。

合并不等于丢弃历史。被合并文档如仍有追溯价值，应保留引用、迁移说明或归档记录。

### 6.5 归档治理

文档不再作为当前事实源但仍有历史价值时，应标记为历史素材或迁入合适归档位置。

归档内容不得继续作为当前执行依据。AI 可以读取归档材料作为背景，但不能把归档材料当作当前规则事实源。

### 6.6 删除治理

没有事实源价值、历史价值或引用价值的文档可以删除。删除普通 Git 文件本身不必因文件操作触发 Human Gate，但删除规则入口、Skill、Agent、产品身份或关键事实源等例外对象时应按相关规范评估 Human Gate。

删除前应判断该文档是否仍被 specs、docs、Rules、ADR、Kit Base 或工具索引引用。若存在引用关系，应先处理引用迁移或说明引用失效原因。

### 6.7 索引与详情

索引文档只记录轻量入口，不维护详情正文、动态状态、关闭原因、证据正文或可变字段。

当一个事实采用索引 + 详情模式时，详情文件是事实正文，索引只作为人类和 AI 的定位入口。

索引不得因便利复制详情中的可变事实，否则会形成第二事实源。

## 七、结构化对象事实源治理

### 7.1 Kit Base 定位

Kit Base 是接入 PM Kit 的项目必须具备的结构化对象事实源基础层，默认目录名为 `pm-kit-base/`。

Kit Base 用于承载需要被 AI 高频读取、程序解析、工具聚合、状态流转、关系追踪和证据回写的项目对象事实。

Kit Base 不以任务为唯一中心。它可以承载多类结构化对象事实，但不承载规范正文、需求长文、帮助材料、代码、工具缓存、UI 状态或聊天记录全文。

Kit Base 内部采用子目录分域，每个子目录承载一类结构化对象事实。

### 7.2 目录结构原则

Kit Base 根目录 `pm-kit-base/` 是强制基础设施。子目录应按项目对象需要渐进生成。

当某类对象事实尚未出现、尚无工具解析需求或尚无状态流转需求时，可不创建对应子目录。

不得为"模板完整"一次性创建所有子目录。

若 Memo、Pitfall、Evidence、Audit、Checklist 等事实已经进入 Kit Base 对应子目录，docs 只能提供说明、链接、历史材料或工具生成视图，不得重复维护其正文、状态或关闭结果。

### 7.3 文件命名原则

Kit Base 子目录下的结构化文件采用统一命名格式：`{对象类型}-{语义标识}.yaml`。对象类型为子目录对应的对象英文类型，全小写；语义标识为该对象的唯一标识或语义标题，英文小写、单词间用中划线。

禁止将动态状态字段写入文件名。文件名只承载静态类型与标识。

### 7.4 YAML 字段原则

Kit Base 结构化 YAML 文件应至少包含基础字段：`id`（对象唯一标识，全局唯一）、`type`（对象类型，与子目录语义一致）、`title`（对象标题，人类可读）、`status`（当前状态，结构化流转对象必须）、`created`（创建时间，格式 YYYY-MM-DD）、`updated`（更新时间，格式 YYYY-MM-DD）。

状态值应使用英文，不使用中文。具体对象的合法状态值由对象实践文档定义。

每个 YAML 文件承载一个对象实例。不得在一个 YAML 文件中写入多个不同 ID 的对象实例。对象之间通过 `id` 字段建立引用关系，不得通过 YAML 文件合并来表达多对象关系。

### 7.5 禁止内容

以下内容不得写入 Kit Base 结构化 YAML 文件：

1. 完整的需求语境、背景说明或设计讨论（写入 docs）；
2. 工具缓存或 UI 状态；
3. 临时调试字段；
4. 凭证、密钥或敏感信息；
5. 超过 1000 字符的单字段内容。

## 八、记录与证据事实源治理

### 8.1 记录类型

记录与证据类事实至少包括：

| 类型 | 回答的问题 |
|---|---|
| Change 记录 | 本次实际改了什么 |
| 验证证据 | 某项工作如何被验证或关闭 |
| 审计记录 | 检查发现了什么、如何分流 |
| 检查结果 | 某个 Checklist 的执行结果是什么 |
| 踩坑记录 | 哪个可复用问题以后要避免 |
| 发布记录 | 发布或交付时实际执行和验证了什么 |
| 变更说明 | 事实源、范围、规则或边界发生了什么变化 |

### 8.2 事实源形态

记录类事实不应一律采用同一种文件形态。AI 或工具应先判断记录的主要用途、主要消费者和读取方式，再确定其事实源形态。

踩坑记录的主要消费者是 AI。踩坑记录不应优先作为人类阅读型长文维护；当某个问题具有复用价值、需要 AI 在后续执行前识别和规避时，应作为可解析的结构化事实源维护。

开发备忘属于 Memo 类事实。若项目已经存在 Memo 结构化事实源，docs 中的开发备忘文档不得重复维护备忘正文、动态状态或关闭结果，只能作为使用说明、历史材料、轻量入口或工具生成视图。

Change 记录采用结构化 YAML 文件模式，通过 `pm-kit-base/changes/` 记录，所有项目均可产生 Change 记录。Change 记录通常不作为 AI 每次执行前默认必读事实源，而是服务追溯、审计、发布记录和工具聚合。

### 8.3 索引与详情模式

记录类事实可以采用索引 + 详情模式，也可以采用结构化详情 + 工具派生视图模式。

索引用于定位，详情或结构化记录用于承载权威事实。索引不得维护详情正文、动态状态、关闭原因、完整验证结果或可变字段。

当记录需要被工具解析、状态流转、与对象建立关系、被 AI 高频匹配或转化为检查动作时，应进入 Kit Base 或其他结构化事实源；当记录主要用于人类追溯和解释时，可以进入 docs 记录目录。

### 8.4 记录与结构化证据边界

Change 记录、验证证据、审计记录和任务关闭证据可以互相引用，但不得互相替代：

1. Change 记录回答实际改了什么；
2. 验证证据回答如何证明某项工作满足要求；
3. 审计记录回答检查发现了什么；
4. 结构化对象状态回答当前对象处于什么状态；
5. ADR 回答为什么做出长期决策。

同一事实如果需要同时被人阅读和工具解析，应明确哪一处是权威事实源，另一处只能引用或摘要。

当证据内容较短、只服务单个对象关闭时，可以留在对象事实源字段中。当证据内容需要跨任务复用、被审计引用、作为发布或验收记录长期追溯，或需要工具独立解析时，应考虑进入独立 Evidence、Checklist 结果、审计记录或发布记录事实源，并由原对象字段引用。

Review Gate 结果不得只停留在聊天记录、Agent 输出、工具界面或命令行输出中。若 Review Gate 发现需要继续处理的问题，应分流为 Task、ADR、Risk、Dependency、Memo 或审计记录。

Review Gate 通过不等于 Human Gate 已授权。对象关闭仍需要人类验收确认与关闭授权。

当前阶段不把 Run、Check、Approval 独立对象化。它们作为证据来源理解。只有当 Run、Check、Approval 需要跨任务独立追踪、被工具解析、被审计复用或形成稳定状态机时，才评估是否拆分为独立对象。

### 8.5 审计发现分流

审计发现不应成为问题的最终归宿。审计发现应根据性质分流为：

1. 可执行工作；
2. 未任务化 Memo；
3. 决策或 ADR；
4. 规则或规范调整；
5. 风险或依赖；
6. 关闭记录。

分流后的对象事实归属应依据对象判断和载体边界判断。审计快照可以记录发现摘要，但不得替代分流对象的事实源。

## 九、决策与规则事实源边界

### 9.1 ADR 定位

ADR 是管理对象，承载于 Kit Base `adrs/` 子目录，以 YAML 结构化记录决策内容、背景、原因、选择、影响范围和后续约束。

ADR 不替代 specs 规范正文，不替代 Rules 执行入口，不替代 Kit Base 中的其他对象状态。

ADR 应优先保留完整决策信息。文件命名宜采用稳定编号 + 语义标题，便于长期引用和完整阅读；不应仅为便于工具解析而牺牲决策背景和原因的可理解性。

临时判断可以先作为 Memo、Task evidence 或讨论材料保留；当判断影响多个对象、长期执行方式、事实源归属、规则边界或反复讨论的问题时，应考虑形成 ADR。

ADR 生命周期规则：

1. ADR 不得删除；
2. 推翻旧决策时，将旧 ADR 状态标记为 `superseded`，并引用新 ADR 编号；
3. ADR 文件名可因标题修正而调整，但重命名时必须同步更新引用。

若工具或文档生成决策列表，该列表只能作为派生视图或轻量入口，不得替代 ADR 记录。

### 9.2 specs 与规则正文

specs 承载 PM Kit 跨项目基础规范正文。凡是所有接入 PM Kit 的项目都应继承的长期规则，应进入 specs。

specs 不记录具体项目当前任务状态、工具实现细节、临时计划或 PM Kit Tools 自身迁移任务。

当 ADR 中的决策升级为长期基础规范时，应将规则正文写入 specs，ADR 保留原因和背景。

### 9.3 Rules 与规则入口

Rules 是 AI 执行时的规则入口、约束摘要或项目专属规则承载位置。

Rules 可以索引、摘要或桥接 specs，但不得复制 specs 大段正文形成第二事实源。

项目专属规则可以在项目规则入口中权威维护，但不得与 specs 基础规范冲突。

### 9.4 决策升级为规则

当某个 ADR 满足以下条件之一时，应考虑升级为规则或规范正文：

1. 影响多个项目或所有接入项目；
2. 改变 AI、人或工具的长期行为；
3. 改变事实源归属；
4. 改变 Human Gate 判断；
5. 多次重复出现且需要稳定约束；
6. 影响初始化、工具写入或对象关闭方式。

升级后应保持：ADR 记录为什么这样决定，specs 或 Rules 记录以后必须怎么做。两者不得互相替代。

## 十、派生视图与工具边界

### 10.1 工具角色

PM Kit 中的工具可以承担以下角色：

1. 读取 Git 文件事实源；
2. 解析结构化对象；
3. 校验字段、关系和状态；
4. 聚合项目上下文；
5. 展示状态和缺口；
6. 提示 Human Gate；
7. 提供受控写入入口；
8. 生成审计或检查结果。

工具不得承担以下角色：

1. 成为最终事实源；
2. 绕过 Git 文件写入；
3. 绕过 Human Gate；
4. 将缓存或数据库作为权威状态；
5. 将 PM Kit Tools 自身项目误作为被管理项目事实源。

### 10.2 派生视图边界

派生视图是从 Git 文件事实源读取、解析、聚合后生成的展示结果。

派生视图可以展示：对象状态、对象关系、初始化缺口、审计结果、检查清单、待确认事项、动态上下文。

派生视图不得维护：与 Git 文件不一致的权威状态、无法追溯来源的事实、只存在于 UI 中的关闭证据、只存在于缓存中的决策或规则、绕过被管理项目事实源的项目记录。

### 10.3 缓存和数据库边界

工具可以使用缓存或数据库提高性能，但缓存和数据库只能是派生层。

缓存或数据库中的内容必须满足：

1. 可由 Git 文件事实源重新生成，或明确标记为运行时临时状态；
2. 不作为任务状态、证据、决策、规则或审计的唯一来源；
3. 失效、删除或重建后不影响事实源完整性；
4. 不保存敏感凭据或不应持久化的信息；
5. 不改变被管理项目事实归属。

### 10.4 受控写入边界

工具可以提供受控写入入口，但写入目标必须是被管理项目自身的 Git 文件事实源。

受控写入至少应满足：

1. 写入前明确目标事实源；
2. 写入前判断是否已有权威事实；
3. 写入前判断是否触发 Human Gate；
4. 写入后可通过 Git 追溯；
5. 写入后工具视图应从事实源重新读取或刷新；
6. 写入不得只停留在工具数据库或 UI 状态。

### 10.5 Context 边界

Context 是由事实源组织出的 AI 执行输入、任务背景和行动依据。

Context 通常不作为独立事实源。Context 中出现的新信息，如果需要长期保留，应重新判断其对象类型和事实源载体。

AI 不得因为某项内容进入本次上下文，就认为它已经进入项目事实源。

## 十一、文档命名与入口规则

### 11.1 文件命名格式

接入 PM Kit 的项目文档文件命名采用编号加语义标题：`NN-标题.md`，其中 `NN` 为两位数字，标题必须简短表达文档主题。

命名约束：

1. 文件名应表达稳定主题，不表达临时状态、当前进度、短期优先级或未确认方案；
2. 标题、文件名和定位应保持一致；
3. 编号只表达体系位置或阅读顺序，不表达当前优先级、任务状态或完成状态；
4. 同一层级下命名风格应一致；
5. 重命名应同步检查引用、入口、规则索引和日志；
6. 历史素材应在定位或归档状态中显式标记，不应伪装为当前执行依据。

### 11.2 编号段设计原则

编号段用于帮助 AI 和人从编号判断文档角色。编号段划分应遵循以下原则：

1. 低编号段用于必备记录文档；
2. 中编号段用于项目规则和通用模型；
3. 高编号段用于需求与专题；
4. 审计快照使用固定编号；
5. ADR 使用独立目录；
6. 规则与需求分离：规则编号段和需求编号段不得交叉；
7. 治理规则与客观规则分离：项目约定和通用模型使用不同编号段。

具体编号段分配由项目实践决定。

### 11.3 编号选择与重排

编号选择流程：

1. 先判断文档承载的管理对象和治理角色；
2. 再选择最合适的编号段；
3. 编号冲突时优先评估是否需要有序重排；若暂不重排，顺延到下一个可用编号；
4. 禁止无理由跳号，但允许为对象驱动重构进行有记录的编号调整；
5. 编号调整必须同步更新引用、项目规则必读索引和 Change 记录。

编号重排要求：

1. 先有 ADR 或明确决策依据；
2. 保留迁移说明或 Change 记录；
3. 同步修正所有相对链接和必读索引；
4. 原文档如需保留历史价值，按归档规则处理；
5. 工具、规则、技能中引用旧路径的，必须同步检查。

旧编号引用处理：

| 场景 | 处理规则 |
|---|---|
| Change 记录、ADR 背景、历史输入归档中的旧编号 | 可保留，但必须能看出是历史语境 |
| 当前规范正文、必读索引、Skill、Rule、工具配置中的旧编号 | 必须更新为当前编号或当前权威路径 |
| 其他文档引用已迁移文档但尚未修正 | 必须加过渡说明，标明旧编号对应的新编号 |
| 无法判断是历史引用还是当前引用 | 按当前引用处理，优先修正或进入审计发现 |

### 11.4 README 入口

README 是项目稳定门面和第一入口。

README 必须包含：

| 顺序 | 段落 | 必须 | 内容 |
|---|---|---|---|
| 1 | 项目目标 | 是 | 一段话概述 + 职责列表 |
| 2 | 技术栈 | 是 | 语言、框架、关键依赖 |
| 3 | 快速上手 | 视项目 | 环境要求、运行命令、测试命令 |
| 4 | 项目集关系 | 是 | 上游、下游、接口契约、依赖关系与维护关系 |

README 禁止放当前状态、详细计划、完整文件索引、变更历史和临时备忘。

### 11.5 项目必须具备的信息

接入 PM Kit 的项目必须能以 Git 文件事实源回答以下问题：

| # | AI 必须能回答的问题 | 最低要求 |
|---|---|---|
| 1 | 项目是什么、职责边界在哪 | 有稳定的项目身份入口 |
| 2 | 每次改了什么、为什么改 | 有可追溯的变更记录，至少包含变更内容、原因、影响范围、验证方式 |
| 3 | 有哪些已知的复用性陷阱 | 已解决的可复用问题可被检索 |
| 4 | 怎么开发、怎么检查 | AI 执行前有可读取的实践说明 |
| 5 | 怎么发布、怎么验证 | 如有发布流程，有书面依据 |
| 6 | 为什么做某个长期决策 | 影响后续行为的决策有可追溯记录 |
| 7 | AI 必须遵守什么项目约束 | 项目硬约束和必读入口存在 |

项目的具体文件名、目录结构、编号方式可与 PM Kit 推荐方式不同，但必须满足"AI 可读取、人可审查、Git 可追溯"三项约束。无代码项目 #4 和 #5 可简化。

### 11.6 项目规则入口

有独立项目事实源、文档、任务或代码边界的接入项目，应通过项目规则提供 AI 执行入口。

项目规则入口应指向：项目定位、必读事实源、项目专属硬约束、场景规则入口、常用检查要求、压缩后仍需保留的关键词。

项目规则入口不应变成完整文档目录索引，也不应复制 specs、docs 或 ADR 的正文。入口应服务 AI 快速建立上下文，而不是替代事实源。

项目规则中应维护"必读文档索引"。新增事实源文件或关键文档时，应同步更新该项目规则。必读文档索引列核心文档，不追求全量；非核心文档通过目录自发现。

### 11.7 索引与详情边界

索引用于定位，详情用于承载权威事实。索引可以维护：编号、标题、类型或适用范围、稳定链接、极简摘要。

索引不得维护：详情正文、动态状态、关闭原因、完整验证结果、根因分析全文、可变决策原因、可由结构化事实源派生的统计。

当索引和详情发生冲突时，以详情事实源或结构化事实源为准。索引应被修复，不应反向覆盖详情事实。

### 11.8 跨项目归属判断

文档归属判断流程：

1. 是否只有一个项目会读/改？是 → 放该项目 docs/；否 → 继续；
2. 是否被 2 个以上项目引用，或描述整体架构、治理、接口？是 → 放管理项目 docs/；否 → 继续；
3. 是否是长期决策，回答"为什么这样做"？是 → 放 pm-kit-base/adrs/；否 → 继续；
4. 是否只是临时想法、待办、未确认问题？是 → 放对应项目开发备忘；否 → 作为正式编号文档进入合适编号段。

跨项目引用应显式体现项目归属。禁止通过模糊表述掩盖路径归属，例如只写"当前项目文档""管理项目文档"而不说明事实源所属项目或入口位置。

### 11.9 历史素材与归档入口

历史素材、归档文档和旧规范材料可以保留，但必须满足：

1. 明确标记其历史或素材状态；
2. 不作为当前执行依据；
3. 不出现在项目规则的当前必读入口中，除非明确说明只作为背景材料；
4. 不与当前 specs、docs、Rules 或 Kit Base 重复维护权威事实；
5. 被重新启用为当前规则或规范前，应评估 Human Gate。

AI 可以读取历史素材辅助理解背景，但不得仅依据历史素材执行当前规则、创建对象或覆盖事实源。

### 11.10 引用路径规则

文档引用应优先使用稳定、可审查、可被工具检查的路径。

引用应满足：

1. 同一项目内文档优先使用相对路径；
2. 跨项目引用应显式体现项目归属；
3. 索引引用详情，详情不应依赖索引才能成立；
4. 工具视图可以链接事实源，但不得让事实源反向依赖工具视图。

### 11.11 重命名与移动流程

文档重命名或移动前，AI 应判断：

1. 文件是否是规则入口、项目身份、ADR、关键事实源或普通文档；
2. 是否改变文档角色或权威事实源归属；
3. 是否影响项目规则、README、索引、其他文档引用、工具配置或测试资料；
4. 是否需要 Human Gate；
5. 是否需要形成 ADR、Change、Evidence 或 Audit 记录。

重命名或移动后，至少应检查：

1. 文件标题和定位是否与新文件名一致；
2. 上级索引或地图是否更新；
3. 项目规则入口是否仍可读取；
4. 相对链接是否有效；
5. 历史引用是否需要保留为历史语境；
6. Change 记录是否完成。

### 11.12 文档入口缺口处理

当 AI 发现无法判断应读取哪个入口时，不应直接猜测。应先识别缺口类型：

| 缺口类型 | 处理方式 |
|---|---|
| 缺少项目身份入口 | 记录 Identity 缺口，必要时请求人确认 |
| 缺少项目规则入口 | 记录 Rules 缺口，提示需要项目规则 |
| 缺少必备文档 | 依据 §11.5 判断缺失要素，记录缺口 |
| 缺少事实源索引 | 依据事实源角色判断是否创建索引或仅记录缺口 |
| 索引与详情冲突 | 以详情或结构化事实源为准，记录修复 Work 或 Audit |
| 历史材料被当前入口引用 | 评估是否归档、替换引用或触发 Human Gate |
| 引用路径失效 | 修复引用或记录文档治理缺口 |

缺口不等于立即创建完整目录或重构文档体系。AI 应按影响范围和门禁要求渐进处理。

## 十二、格式契约

本节集中承载程序依赖的固定格式契约。程序工具以本节为格式依据，AI 在写入被管理项目事实源时必须遵守本节约定，不得根据项目情况自行调整。

### 12.1 Kit Base 目录与文件命名契约

Kit Base 根目录名为 `pm-kit-base/`，位于被管理项目根目录下。

子目录按对象分域：

| 子目录 | 承载对象 | 说明 |
|---|---|---|
| `tasks/` | Task | 符合准入条件、进入管理系统的可执行、可流转、可验收对象 |
| `memos/` | Memo | 尚未任务化但有保留价值的输入、发现和提醒 |
| `evidences/` | Evidence | 执行摘要、验证结果、关闭证据和验收记录 |
| `checks/` | Checklist / Audit | 检查事项及检查结果 |
| `risks/` | Risk | 已识别的不确定因素 |
| `deps/` | Dependency | 依赖的前置条件或外部约束 |
| `adrs/` | ADR | 已确认、后续应遵守的决策记录 |
| `changes/` | Change | 变更记录（时间戳命名，记录即终态） |

子目录按项目对象需要渐进生成。当某类对象事实尚未出现时，可不创建对应子目录。

文件命名格式：`{对象类型}-{语义标识}.yaml`。对象类型为子目录对应的对象英文类型（`task`、`memo`、`evidence` 等），全小写；语义标识为该对象的唯一标识或语义标题，英文小写、单词间用中划线。

文件名只承载静态类型与标识，禁止将动态状态字段写入文件名。

### 12.2 YAML 字段契约

Kit Base 下的 YAML 文件必须包含以下基础字段：

| 字段名 | 含义 | 约束 |
|---|---|---|
| `id` | 对象唯一标识 | 必须，全局唯一 |
| `type` | 对象类型 | 必须，与子目录语义一致 |
| `title` | 对象标题 | 必须，人类可读 |
| `status` | 当前状态 | 结构化流转对象必须 |
| `created` | 创建时间 | 必须，格式 YYYY-MM-DD |
| `updated` | 更新时间 | 必须，格式 YYYY-MM-DD |

结构化流转对象的状态值必须使用英文值。具体对象的合法状态值由对象实践文档定义。

每个 YAML 文件承载一个对象实例。不得在一个 YAML 文件中写入多个不同 ID 的对象实例。对象之间通过 `id` 字段建立引用关系，不得通过 YAML 文件合并来表达多对象关系。

### 12.3 Change 记录格式契约

Change 记录采用结构化 YAML 文件模式，存放在 `pm-kit-base/changes/` 目录。所有项目均可产生 Change 记录。

文件组织：

- 文件名使用时间戳：`{YYYYMMDDHHmmss}.yaml`
- 不维护索引文件，目录本身提供索引
- 文件创建后不可修改

YAML 字段：

```yaml
id: CHG-{YYYYMMDDHHmmss}
title: 变更标题
date: YYYY-MM-DD
changes: |
  变更内容
reason: |
  变更原因
impact: |
  影响范围
validation: |
  验证方式
project: 项目标识（可选）
tags: []（可选）
```

字段约束：

1. `id` 与文件名中的时间戳一致；
2. `date` 格式 YYYY-MM-DD；
3. `validation` 不可省略，无具体验证内容时标记为 `—`；
4. `changes` 记录实际变更内容，`reason` 记录为什么变更。

记录粒度：

1. 一次逻辑变更批次记一条 Change；
2. 同一原因、同一目标的多文件修改记一条 Change；
3. 不同原因的修改分开记录；
4. 跨项目影响写入 `impact` 字段，不拆成多条。

### 12.4 踩坑记录格式契约

踩坑记录采用结构化 YAML 文件模式，存放在 `pm-kit-base/pitfalls/` 目录。不使用索引 + 详情二层模式，YAML 自身提供索引功能。

文件命名：`pitfall-{NNNN}-short-title.yaml`。编号从 `0001` 开始递增，固定 4 位；英文标题使用小写短横线；每个项目独立编号。

YAML 字段：

| 字段 | 必须 | 约束 |
|---|---|---|
| `id` | 是 | 格式 PF-{NNNN}，与文件名中的编号一致 |
| `title` | 是 | 人类可读的踩坑标题 |
| `status` | 是 | 合法值：open、resolved、deprecated |
| `date` | 是 | 记录日期，格式 YYYY-MM-DD |
| `scenario` | 是 | 触发场景 |
| `trigger` | 是 | 触发条件 |
| `symptom` | 是 | 错误表现 |
| `root_cause` | 是 | 根因 |
| `workaround` | 是 | 规避或修复方式 |
| `scope` | 否 | 适用范围列表（用于 AI 快速筛选） |
| `tags` | 否 | 标签列表 |
| `related_objects` | 否 | 关联的管理对象 ID 列表 |

踩坑记录触发级别：

| 级别 | 触发场景 | 要求 |
|---|---|---|
| 必须 | 修复非显而易见 bug | 修复完成时创建 |
| 必须 | 发现违反直觉约束 | 修复完成时创建 |
| 建议 | 长时间排查的问题 | 梳理时补充 |

非显而易见判定：

| 类型 | 是否记录 |
|---|---|
| 拼写错误、缺 import、缩进错误 | 不记录 |
| 报错直接定位的一行空指针或越界 | 不记录 |
| 状态机、时序、竞态、边界条件 | 记录 |
| 环境依赖、平台差异、路径权限 | 记录 |
| 字段名、键名、跨端格式不匹配 | 记录 |
| 框架或语言的违反直觉行为 | 记录 |

### 12.5 ADR 格式契约

ADR 采用结构化 YAML 文件模式，存放在 `pm-kit-base/adrs/` 目录。

文件命名：`adr-{NNNN}-short-title.yaml`。编号从 `0001` 开始递增，固定 4 位；英文标题使用小写短横线；每个项目独立编号，不使用跨项目全局编号。

YAML 字段：

```yaml
id: adr-{NNNN}
title: 决策标题
status: proposed | accepted | deprecated | superseded | rejected
date: YYYY-MM-DD
context: |
  背景说明
decision: |
  决策内容
consequences: |
  后果
alternatives: |
  考虑过的替代方案
affects:
  - 影响范围
related_objects:
  - 关联对象
related_rules:
  - 关联规则
superseded_by: adr-{NNNN}
```

字段约束：

| 字段 | 必须 | 说明 |
|---|---|---|
| `id` | 是 | 与文件名中的编号一致 |
| `title` | 是 | 人类可读的决策标题 |
| `status` | 是 | 合法值：proposed、accepted、deprecated、superseded、rejected |
| `date` | 是 | 决策日期，格式 YYYY-MM-DD |
| `context` | 是 | 决策背景 |
| `decision` | 是 | 决策内容 |
| `consequences` | 是 | 决策后果 |
| `alternatives` | 否 | 考虑过但未采纳的替代方案 |
| `affects` | 否 | 影响范围列表 |
| `related_objects` | 否 | 关联的管理对象 ID 列表 |
| `related_rules` | 否 | 关联的规则文件列表 |
| `superseded_by` | 否 | 仅当 status 为 superseded 时必须填写，指向替代本决策的新 ADR ID |

## 十三、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变事实源载体边界；
2. 改变 specs、docs、Kit Base、ADR、Rules 的权威关系；
3. 将工具缓存、派生视图或聊天记录升级为事实源；
4. 覆盖已有证据、审计结果或决策记录；
5. 改变被管理项目的事实归属；
6. 将旧事实源迁移到新载体；
7. 改变 Kit Base 根目录或结构化事实源基本约定；
8. 修改本文定义的目录名、文件名格式或字段名；
9. 修改 YAML 基础字段约定或状态值的合法枚举；
10. 将项目文档升级为跨项目基础规范；
11. 改变文档的权威事实源角色；
12. 删除或覆盖关键事实源文档；
13. 将归档材料重新作为当前规则；
14. 新增或修改长期基础规范；
15. 将决策升级为规则；
16. 改变 Rules 与 specs 的边界；
17. 建立新的长期文档命名体系或入口体系；
18. 重命名或移动 Rules、ADR、项目身份文件或关键事实源；
19. 工具写入或覆盖 Git 文件事实源；
20. 工具将派生数据升级为权威事实。

检查至少包括：

| 检查项 | 标准 |
|---|---|
| 对象依据 | 新增事实已判断对象类型或对象关系 |
| 载体清晰 | 已判断权威事实源载体 |
| 单一事实源 | 未重复维护同一可变事实 |
| 项目归属 | 事实写入被管理项目自身 |
| 工具边界 | 工具输出未成为最终事实源 |
| 可追溯 | 变更、证据或决策可通过 Git 文件追溯 |
| 文档角色 | 文档角色明确 |
| 索引边界 | 索引不维护详情正文或动态状态 |
| 归档状态 | 历史材料不作为当前执行依据 |
| 命名一致 | 文件名、标题和定位一致 |
| 信息完备 | §11.5 信息完备要求被满足 |
| 格式合规 | Kit Base 目录、文件命名、YAML 字段、Change 记录、踩坑记录、ADR 格式符合本文定义 |
| 引用有效 | 关键引用路径可追踪、可检查 |
| 来源可追溯 | 视图数据可追溯到 Git 文件 |
| 缓存非权威 | 缓存可重建且非唯一事实源 |
