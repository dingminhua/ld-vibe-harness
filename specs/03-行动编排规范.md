## 1. 本文解决的问题

本文定义 AI 做 LDVH 工作时如何调用 00 的价值门、遵守 01 的正式变更门，并把一次行动编排为可识别、可验证、可分流、可交还的闭环。

本文解决：

1. 做任何 LDVH 工作前，行动编排如何调用 00 的价值门；
2. 修改涉及 specs、Code 和实例时，行动编排应该按什么顺序推进；
3. Code 验证和子 agent 审核如何进入正式变更编排；
4. warning 不阻断行动时，AI 如何在完成时向 Human 报告并分流；
5. AI 何时必须停止并触发 Human Gate。

本文不定义规范文件结构、附件字段、Code 输出 schema、事实模型字段、Git 追溯细则、Web 展示或 Runtime 入口。这些内容由 01、04、02、07、05 和 06 承接。

## 2. 上位依据

本文承接 `specs/00-LDVH-v3理念与价值标准.md` 的 AI 第一服务对象、价值门和 Stop Conditions。

本文承接 `specs/01-规范体系基础规范.md` 的单一 Markdown 事实源、正式变更准入硬门、review 收据边界和 warning 处理规则。

若本文与 00 或 01 冲突，以 00 和 01 为准。本文只规定行动编排顺序，不反向定义规范体系、Code、事实模型或事实源规则。

## 3. 构成要素归属与价值判断

本文属于六类构成要素中的行动编排。

| 价值 | 本文如何服务 | 减少的 AI 负担 |
|---|---|---|
| V1 快速定位 | 让 AI 先判断当前 LDVH 工作属于 specs、Code、实例还是回写 | 定位负担 |
| V2 可行动理解 | 用固定行动顺序减少“先写哪里”的判断 | 理解负担 |
| V3 正确判断 | 用价值门和权威顺序防止 Code、实例或 review 反向定义规则 | 判断负担 |
| V4 稳定执行 | 用 specs -> Code -> 实例 -> 验证 -> 回报的顺序约束执行 | 执行负担 |
| V5 门禁识别 | 明确触发 Human Gate、blocker 和 warning 的处理差异 | 停止负担 |
| V6 强制验证 | 要求正式变更完成前有 Code 验证和审核证据 | 验证负担 |
| V8 可靠回写 | 要求 warning、缺口和完成证据在收尾时回报和分流 | 回写负担 |

本文不要求每次行动都修改文件。本文要求每次行动都能说明自己为什么行动、按什么顺序行动、如何确认行动结果。

## 4. 适用范围与事实源边界

本文适用于 AI 执行 LDVH 相关行动编排，包括：

1. 新增、迁移、修改或审计 specs；
2. 实现或修改 LDVH Code；
3. 修改 LDVH 事实实例；
4. 处理 Code 诊断、warning、blocker、缺口和完成回报；
5. 调用子 agent、工具或测试协助判断。

本文的规则事实源是本文 Markdown 正文。Code 输出、review 收据、子 agent 审核、测试结果和聊天结论都只是证据或过程输出。

review 收据只能证明某次正式变更经过了指定动作；它不得替代本文规则，也不得记录迁移后的规则解释。

## 5. Context、Scenario、Gate

Context 是行动编排开始前必须读取或确认的最小上下文。LDVH 自身行动的默认 Context 为：00、01、本文、目标规范或对象、相关 Code 验证入口和本次任务目标。

Scenario 是行动编排进入信号。以下情况命中本文：

1. Human 要求新增、迁移、修改或审计 LDVH specs；
2. Human 要求实现或修改 LDVH Code；
3. Human 要求修改 LDVH 事实实例；
4. Code、测试或子 agent 输出 blocker、warning、缺口或归口不清；
5. 一次行动同时影响 specs、Code、实例、验证或回写。

Gate 是行动必须暂停、分流或确认的条件。本文的 Gate 见 Human Gate / Stop Conditions；01 的 formal review gate 仍由 01 定义。

## 6. 本地规则

任何 LDVH 行动编排开始前，必须先调用 00 的价值门，并在本次回复或过程证据中留下最小判断结果。

03 不重新定义价值门问题。价值门的正式来源是 `specs/00-LDVH-v3理念与价值标准.md`。03 只规定：价值门没有通过时，行动编排不得进入方案写作、文件修改、Code 实现或实例变更。

AI 记录价值门结果时，只保留足够行动的判断：本次行动服务什么目标、减少哪类 AI 负担、是否保持单一 Markdown 事实源、是否触发 Human Gate、完成时如何验证和回报。不得把价值门记录扩写成第二份 00。

涉及规则、实现和实例的行动编排，默认顺序为：

1. 先改 specs，明确规则、边界、价值和验证要求；
2. 再改 Code，让 Code 确定性解析、检查或生成派生结果；
3. 再改实例，让事实对象遵守已经成立的 specs 和 Code；
4. 再运行验证，记录 Code 结果、测试结果和不可验证缺口；
5. 最后回报 Human，说明完成项、验证项、warning、blocker 处理和后续分流。

只有在修复显然属于实现缺陷、且不改变规则含义时，才可以先改 Code；若 Code 修复暴露规则缺口，必须回到 specs。

正式 specs 或附件新增、迁移和修改，必须遵守 01 的 formal review gate。03 不重复定义 review 字段、hash 门禁或测试细节，只规定行动编排必须先满足 01 gate，再声明结构完整。

子 agent、Code、测试和工具输出必须交还主控 AI。主控 AI 负责综合判断、触发 Human Gate、报告 warning 和保留后续分流，不得把外部输出直接当作最终结论。

## 8. 验证与证据

AI 声称 LDVH 工作完成前，至少提供：

1. 本次行动调用 00 价值门后的判断；
2. 实际修改对象和修改顺序；
3. Code 验证或测试命令结果；
4. 子 agent 审核结果，若本次涉及 01 要求 formal review 的正式变更；
5. warning、blocker、缺口和后续分流；
6. 需要 Human 知道的残留风险。

无法验证时，不得说“完成且无问题”。只能说明已完成的部分、未验证原因、风险和后续处理位置。

## 9. Human Gate / Stop Conditions

以下情况必须暂停并等待 Human：

1. 价值门无法回答或目标价值不清；
2. 需要改变 00 或 01 的上位规则；
3. 需要改变 specs -> Code -> 实例的默认顺序；
4. Code、实例或 review 收据正在反向定义规范规则；
5. warning 被判断为可接受长期风险；
6. blocker 无法在当前行动内解决；
7. 子 agent 审核与主控判断冲突，且影响正式变更是否成立。

AI 可以准备选项、影响范围和证据，但不得替 Human 完成 Gate。
