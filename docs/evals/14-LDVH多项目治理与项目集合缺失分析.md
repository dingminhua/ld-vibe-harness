# LDVH 多项目治理与项目集合缺失分析

> 创建日期：2026-06-05
> 定位：分析 LDVH 多项目管理场景下项目定义清晰度和项目集合对象缺失问题，提出方案建议
> 触发：用户提出"存在多个项目需要管理的情况，项目的定义要清晰，生产对象只有项目没有项目集合如何处理"
> 来源：LDVH 多项目治理实践与项目集合分析

---

## 1. 本文解决的问题

当前 LDVH 面临两个相关但不同的问题：

1. **项目定义不够清晰**：术语规范中"管辖项目"的定义偏功能描述，缺少明确的边界判定标准，导致"什么算一个项目"存在模糊空间
2. **缺少项目集合对象**：工作模型中只有 Profile（项目画像）代表单个项目，没有项目集合（Project Group/Collection）对象，多项目分组和聚合治理缺少结构化承载

---

## 2. 现状分析

### 2.1 项目定义现状

术语规范（02 §7）定义管辖项目为"接入并使用 LD Vibe Harness 进行需求、任务、证据、变更、审计或交付治理的实际项目"。当前判定要素：

- 有独立的 `ldvh-base/` 目录
- 有项目规则（`.trae/rules/ldvh-project-rules.md`）
- 有 Profile 实例

但以下边界场景不够清晰：

| 场景 | 当前是否明确 |
|---|---|
| 单仓库多模块，每个模块是否算独立项目 | 不明确 |
| 仓库级项目 vs 产品级项目 | 不明确 |
| 临时实验性代码是否需要接入 LDVH | 不明确 |
| ld-vibe-harness 自身是否同时是管辖项目 | 实际是，但术语中区分了"LDVH 项目"和"管辖项目" |

### 2.2 项目集合缺失现状

当前多项目治理依赖的机制：

| 需求 | 当前承载位置 | 是否结构化 |
|---|---|---|
| 项目名册 | 工作区规则中的管辖项目配置 | 半结构化（文本声明） |
| 单项目身份 | Profile 对象 | 结构化 |
| 跨项目任务追踪 | Intent 可跨项目引用 | 依赖人工关联 |
| 项目分组 | 无 | 无 |
| 跨项目聚合视图 | 无 | 无 |

---

## 3. 方案分析

### 方案 A：不新增对象，强化现有机制

**做法**：
- 明确项目定义的边界判定标准（补充到术语规范）
- 工作区规则继续承担项目名册角色
- 跨项目协调通过 Intent 跨项目引用实现
- 项目分组通过工作区规则中的分类注释实现

**优点**：
- 不增加抽象层，符合"服务最近可运行闭环"原则
- 改动最小，风险最低
- 工作区规则作为项目名册已可满足基本需求

**缺点**：
- 项目分组逻辑散落在工作区规则文本中，非结构化
- 跨项目查询和聚合依赖人工维护
- 随项目增多，工作区规则膨胀

### 方案 B：为 Profile 增加分组标签

**做法**：
- 在 Profile 扩展字段中增加 `tags` 字段（列表类型）
- 通过标签实现逻辑分组（如按业务域、技术栈、团队等维度）
- 不引入新对象类型，仅扩展现有对象

**优点**：
- 轻量扩展，不引入新对象
- 标签天然支持多维度分组
- 可渐进引入，不需要一次性设计完整分组体系

**缺点**：
- 分组逻辑分散在各 Profile 中，无集中视图
- 标签缺乏治理（谁定义标签、标签含义如何统一）
- 无法承载分组级别的配置或规则

### 方案 C：新增项目集合对象

**做法**：
- 创建新的工作模型 ProjectGroup（项目集合）
- 承载项目分组、分组级配置和聚合治理
- Profile 通过 `group` 字段引用 ProjectGroup

**优点**：
- 结构化程度高，支持复杂分组场景
- 可承载分组级规则和配置
- 集中视图，便于管理和查询

**缺点**：
- 增加抽象层，可能过度设计
- 需要完整的工作模型规范（准入条件、状态机、字段契约等）
- 当前场景可能不足以支撑完整对象的投入

---

## 4. 建议方案

**推荐：方案 A 为主 + 方案 B 为补充，暂不引入方案 C**

理由：

1. **项目定义清晰化是当务之急**：无论是否引入项目集合，项目定义的边界判定标准都需要明确。这是方案 A 的核心内容，也是所有方案的前提。

2. **当前场景不需要项目集合对象**：LDVH 原则"服务最近可运行闭环"——当前管辖项目数量有限，工作区规则作为名册已可满足。引入完整对象需要足够的实例验证。

3. **标签是低成本渐进方案**：Profile 增加 `tags` 字段几乎零成本，可按需引入，不需要完整规范。当标签实践积累到一定程度，再评估是否升级为方案 C。

4. **Dogfood 驱动**：先在实际多项目场景中使用方案 A+B，发现真正的分组需求后再决定是否引入方案 C。避免"连续新增抽象而未 Dogfood"。

### 4.1 项目定义清晰化建议

建议在术语规范中补充项目边界判定标准：

**一个项目应满足以下全部条件**：

1. 有独立的 Git 仓库或仓库内独立管理的顶层目录
2. 有独立的构建/部署单元或发布节奏
3. 需要独立的需求、任务或变更治理
4. 接入 LDVH 后有独立的 `ldvh-base/` 目录和项目规则

**以下情况不算独立项目**：

1. 同仓库内的子模块，共享构建和发布节奏 → 作为项目的组成部分
2. 临时实验性代码，不需要治理 → 不接入 LDVH
3. 纯配置或文档仓库，无独立治理需求 → 不接入 LDVH 或以轻量方式管理

### 4.2 Profile 标签扩展建议

在 Profile 扩展字段中增加可选的 `tags` 字段：

```yaml
tags:
  - domain:web
  - stack:python
  - team:core
```

标签格式为 `{维度}:{值}`，维度和值由项目自行定义，LDVH 不预设标签体系。标签的治理（统一维度、冲突处理）留待实践积累后通过 ADR 决策。

### 4.3 方案 C 的引入时机

当以下条件之一满足时，应重新评估是否引入项目集合对象：

1. 管辖项目超过 5 个，且存在明确的分组治理需求
2. 标签实践暴露出分组级配置或规则的需求
3. 跨项目聚合视图成为日常必需而非偶尔使用

---

## 5. 与 LDVH 原则的一致性

| 原则 | 本方案如何遵循 |
|---|---|
| 服务最近可运行闭环 | 不引入未经验证的抽象，先解决定义清晰化 |
| Dogfood | 方案 A+B 可立即实践，积累经验后再升级 |
| 不新增抽象而未实例验证 | 方案 C 暂缓，等实例需求驱动 |
| Human Gate | 项目定义变更和 Profile 字段扩展需 Human Gate |
