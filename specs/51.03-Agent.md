## 1. 本文定位

本文是 `specs/51-multi-role-thinking-多角色思考.md` 的附件型实践子文档（编号 51.03），承接多角色子 Agent 模式实践。本文不是独立行动模型，不得重新定义多角色思考的行动定位、准入条件、Context、Scenario、Gate、执行流程、事实源回写、证据留存或 Human Gate。发生冲突时，以 51 主文档和上位基础规范为准。

---

## 2. 调用机制

多角色子 Agent 模式的调用机制如下：

1. 多角色子 Agent 模式只能在 Rules 入口触发多角色思考后，由主控依据 51 主文档和 51.06 契约编排；
2. 主控可使用当前运行环境提供的可调用 Agent 容器启动子 Agent 实例，为每个角色注入独立参数；
3. 当前运行环境提供的可调用 Agent 容器不是 LDVH Tools 辅助层，Tools、Skill、MCP 或脚本不得直接作为多角色子 Agent 流程入口；
4. 主控可在同一消息中并行启动多个子 Agent 实例，每个实例使用不同角色参数；
5. 不为每个角色创建自定义 Agent 文件；角色定义来自 51.06-Contract.md，作为运行时参数注入；
6. 子 Agent 实例获得独立上下文，不继承主控对话历史。

---

## 3. 角色-可调用 Agent 容器映射原则

主控应根据当前运行环境实际可用的可调用 Agent 容器、角色关注点和任务边界，在运行时选择合适的容器类型。本文不维护具体可调用 Agent 类型清单，不把某个环境中的可用 Agent 列表写成稳定规范。

映射原则：

1. 优先选择与角色关注点直接匹配的可调用 Agent 容器；
2. 没有匹配容器时，选择可承载通用分析任务的容器并完整注入角色参数；
3. 容器选择不得改变 51.06-Contract.md 中的角色定义、角色选择规则或输出契约；
4. 容器选择不得使 Tools、Skill、MCP 或脚本成为多角色子 Agent 流程入口；
5. 每次调用都必须在参数中注入本次分析主题、角色关注点、输出格式和边界规则；
6. 当前环境可用容器发生变化时，主控应在运行时调整选择，不修改本文维护环境清单。

---

## 4. 参数注入

主控为每个角色构造可调用 Agent 容器参数时，应遵循 51.06-Contract.md 的 AgentRoleInvocation 契约：

```yaml
role_id: 角色 ID
role_name: 角色名
role_prompt: 由 prompt_template 和本次主题合成的角色提示
topic: 分析主题
context_pack: 本角色可读取或已提供的事实源摘要
output_format: 本角色应返回的结构
boundary_rules:
  - 不直接写入事实源
  - 不替代 Human Gate
  - 不把工具缓存或派生视图作为事实源
human_gate_rules: 本次需要特别关注的 Human Gate 条件（选填）
```

参数注入规则：

1. 每个可调用 Agent 容器调用只注入一个主要角色；
2. `role_prompt` 应包含角色关注点、触发背景和输出要求；
3. `context_pack` 应包含本次分析所需的最小事实源摘要，按角色关注点裁剪，避免子 Agent 读取过多无关信息；
4. `output_format` 应明确要求子 Agent 返回 RoleAnalysisResult 契约结构，并提供输出模板；
5. `boundary_rules` 必须包含不直接写入事实源、不替代 Human Gate、不把工具缓存或派生视图作为事实源三条底线规则。

### 4.1 执行前输出

主控在启动子 Agent 前，应先输出 51.06 §6 RoleSelectionOutput，包含：

1. 选中的角色及选择理由；
2. 排除的角色及排除理由；
3. 推荐的分析模式及理由；
4. 是否触发 Human Gate。

用户确认角色选择后，主控再启动子 Agent 实例。

---

## 5. 上下文分发

1. 主控在启动子 Agent 前应完成 Context 读取和角色选择；
2. 每个子 Agent 实例获得独立的 `context_pack`，只包含与该角色相关的事实源摘要；
3. 主控不应把全部事实源原样传递给每个子 Agent，应按角色关注点裁剪；裁剪示例：
   - governance-reviewer：§5 事实源边界、§9/§14 Human Gate、§8 角色定义
   - ai-collaboration-architect：§10 调度、51.03 全文、51.06 全文
   - audit-reviewer：§18/§19/§13
   - documentation-engineer：全文结构、编号、引用路径
   - verification-evidence-reviewer：§18/§19/§13、落地产物文件
4. 子 Agent 如需读取额外事实源，应在输出中说明读取了哪些文件，主控据此判断是否需要补充 Context。

---

## 6. 汇总规则

1. 所有子 Agent 输出必须回到主控汇总，不得直接成为事实源；
2. 主控按 51 主文档 §8.6 汇总对比，至少包含一致结论、分歧点、风险汇总、建议执行顺序、需要同步的事项、事实源回写建议和 Human Gate 判断；
3. 主控汇总后的多角色报告按 51.06-Contract.md 的 MultiRoleReport 契约结构输出；
4. 子 Agent 发现 Human Gate 场景时必须标注，主控在汇总时统一判断是否触发 Human Gate。

---

## 7. 检查项

检查 Agent 调度是否合规时，应确认：

1. 是否先由 Rules 入口触发多角色思考，再由主控依据 51 主文档和 51.06 契约编排；
2. 是否使用当前运行环境提供的可调用 Agent 容器，而非依赖 `.trae/agents/` 自定义 Agent 文件；
3. 是否未把可调用 Agent 容器归入 LDVH Tools 辅助层；
4. 是否为每个角色注入了完整的 AgentRoleInvocation 参数；
5. 是否按运行时映射原则选择可调用 Agent 容器；
6. 子 Agent 输出是否回到主控汇总；
7. 子 Agent 是否未直接写入事实源；
8. 子 Agent 是否未替代 Human Gate；
9. 主控汇总是否包含一致结论、分歧点、风险汇总、执行顺序、回写建议和 Human Gate 判断。

---

## 8. Human Gate

1. 角色选择结果应经用户确认后再启动子 Agent 实例（51.06 §6 RoleSelectionOutput）；
2. 子 Agent 输出涉及事实源回写时，必须经 Human Gate 确认后才能写入；
3. 模式选择（主上下文轻量 vs 多角色子 Agent）难以取舍时，应交由用户选择；
4. 子 Agent 发现需要触发 Human Gate 的场景时必须标注，主控在汇总时统一判断。
