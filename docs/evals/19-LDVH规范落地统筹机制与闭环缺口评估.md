## 1. 本文解决的问题

本文分析三个相互关联的问题：

1. **03 与 14 的职责边界问题**：`03` 提出文档规范和落地要求，但如果 `03` 直接按 `docs/evals/14-LDVH多项目治理与项目集合缺失分析.md` 的要求去修改，`03` 并不知道 `14` 整体有哪些需要规范和统筹安排的内容，也不知道全局还有多少落地要求待执行；
2. **内部闭环问题**：当前规范体系在文档层基本自洽，但执行层是否真正闭环；
3. **AI 自身需求匹配问题**：当前规范体系是否符合 AI 作为执行者的理解需求、执行需求和自我约束需求。

本文不替代任何正式规范。稳定结论应吸收到对应正式规范、工作流程、Code、Web 或工作对象后才生效。

## 2. 与 00 总纲的关系

00 定义 LDVH 由开发环境、工作模型、工作流程、Code 和 Web 五类构成要素共同形成 AI 工程驾驭体系，并要求规范驱动的 AI 工作 Harness 能够可规划、可执行、可验证、可沉淀、可演进。

本文以 00 的治理边界为评估依据，只分析"规范落地要求从声明到执行的链路是否存在缺口，以及如何补齐"。

## 3. 核心问题分析

### 3.1 03 不能直接按 14 改

`docs/evals/14-LDVH多项目治理与项目集合缺失分析.md` 位于 `docs/evals/`，按 `03` 的三分契约，它只是输入分析，不是正式规范。

按 `03.01` 的吸收规则：

1. evals 文档不直接构成正文区稳定事实；
2. evals 结论必须吸收到正文区、ADR、Task、Memo 或其他权威位置后才生效；
3. 吸收不得只通过"引用 evals 路径"完成，权威结论必须在吸收出口中明确写出。

因此，`03` 不能直接按 `14` 的要求修改。`14` 中的稳定结论应先判断归属：

| 14 中的结论 | 建议吸收出口 |
|---|---|
| 项目定义边界判定标准 | `02-术语规范.md` 或 `26-Profile-项目画像.md` |
| Profile 标签扩展 | `26-Profile-项目画像.md` 字段契约 |
| 项目集合对象暂不引入 | ADR 或 Memo |
| 方案 C 引入时机 | Memo 或 Task |

### 3.2 核心缺口：缺少落地要求执行统筹机制

当前 `04.01` 定义了规范落地要求的类型和字段，`04.02` 定义了环境适配映射和运行投影规则，`04.04` 定义了环境能力承接边界。但缺少一个关键中间层：

```text
每个规范都能提出落地要求，
但不能要求每个规范自己知道全局；
必须有一个统一机制收集、分类、分派、验证和回写。
```

这个缺口导致：

1. AI 不知道所有规范一共提出了哪些待落地要求；
2. 每类落地要求没有统一队列、统一状态、统一关闭标准；
3. 规范变更后，无法自动检查哪些运行投影需要同步；
4. 运行投影漂移只能靠人工发现。

#### 已闭环部分

| 模块 | 判断 |
|---|---|
| 文档工作区边界 | 基本闭环 |
| evals/refs 吸收规则 | 基本闭环 |
| 正式规范骨架 | 基本闭环 |
| 规范落地要求类型 | 基本闭环 |
| 规范落地要求字段 | 基本闭环 |
| 环境适配与运行投影分层 | 基本闭环 |
| 环境能力承接边界 | 基本闭环 |
| Code 需求准入 | 基本闭环 |
| 多角色思考流程 | 基本闭环 |
| 当前 Codex 环境初始化记录 | 文档层闭环 |

#### 未闭环部分

| 缺口 | 影响 |
|---|---|
| 缺少落地要求全局聚合机制 | AI 不知道所有规范一共提出了哪些待落地要求 |
| 缺少按类型执行统筹 | 每类要求没有统一队列、统一状态、统一关闭标准 |
| 缺少运行投影漂移检查 Code | 规范改了以后，不知道入口/Skill/Hook/Web/Code 是否过期 |

| 缺少生命周期自动触发 | 很多触发要求只能人工降级检查 |
| 缺少 Human Gate 项目级证据机制 | 当前多靠对话确认 |
| 42/43 等产品初始化/审计流程未稳定 | 产品级落地和审计执行入口不足 |

### 3.4 AI 自身需求匹配

| AI 需求维度 | 当前匹配状态 | 缺口 |
|---|---|---|
| 理解需求：边界清晰、事实源层级清楚 | 基本满足 | 无重大缺口 |
| 执行需求：能按流程稳定执行落地要求 | 部分满足 | 缺少统筹流程，AI 仍要手工跨文档追踪 |
| 自我约束需求：机制而非自觉保障执行 | 未满足 | 缺少聚合检查、漂移检查、测试用例事实源 |

## 4. 规范落地执行闭环 10 步流程

### 4.1 总流程

```text
1. 规范产生
→ 2. 判断规范身份
→ 3. 声明规范落地要求
→ 4. 按落地要求类型分流
→ 5. 绑定保障机制
→ 6. 建立环境适配映射
→ 7. 生成或登记运行投影
→ 8. 执行验证 / 漂移检查
→ 9. 问题分流回写
→ 10. 关闭或进入后续 Task
```

### 4.2 第 1 步：规范产生

**输入来源**

- 用户提出的新规则
- `docs/evals/` 的分析结论
- `docs/refs/` 的外部资料
- 已发生的 Pitfall
- ADR 决策
- Task 执行中发现的缺口
- Code/Web/运行投影漂移检查结果

**处理规则**

| 输入 | 是否直接生效 | 正确出口 |
|---|---:|---|
| `docs/evals/14...` | 否 | 吸收到正式规范、ADR、Task、Memo |
| 用户临时判断 | 否 | 需要确认是否成为规则 |
| Pitfall 经验 | 否 | 可吸收到规范或最佳实践 |
| ADR 决策 | 是决策事实，不自动等于规范 | 必要时吸收到 specs |
| Task 发现 | 否 | 需要回写为 Task 证据、Memo 或规范 |

**闭环状态**：已闭环——`03` 已定义 evals/refs 不能直接成为正式规则。

### 4.3 第 2 步：判断规范身份

当某个结论准备进入 `docs/specs/` 时，先判断它属于哪类规范：

1. 文档结构规则 → `03` / `03.01` / `03.02` / `03.03`
2. 规范落地、环境适配、运行投影规则 → `04` 系列
3. 工作模型字段、状态、对象规则 → `20-39`
4. 工作流程、AI 行动规则 → `40-59`
5. Code 实现、校验、工具规则 → `07`
6. Web/Human-facing 同步规则 → `08`
7. 事实源边界、回写规则 → `09`
8. 运行闭环测试规则 → `10`

**闭环状态**：编号区段基本明确，但缺少"规范主题归属判定表/工具"。

### 4.4 第 3 步：声明规范落地要求

正式规范不能只写规则，还要说明这条规则如何被执行。当前 `04.01` 已定义落地要求类型：

| 类型 | 说明 |
|---|---|
| 上位约束承接要求 | 后续规范、流程或检查要承接它 |
| 入口可见要求 | AI 进入场景时要能看到它 |
| 流程复用要求 | 重复步骤应变成流程或 Skill |
| 子 Agent 思考要求 | 需要独立、专项、并行视角 |
| 确定性执行要求 | 需要 Code、测试、校验 |
| Human 交互要求 | 需要用户确认、授权、验收 |
| 生命周期触发要求 | 需要在变更、提交、停止等事件触发 |

每条要求至少要有：落地要求、要求内容、保障机制、同步类型、触发条件。

**闭环状态**：字段和类型已闭环，但缺少全局聚合视图。

### 4.5 第 4 步：按落地要求类型分流

这是核心缺口。应建立"规范落地要求执行统筹机制"，职责是：

```text
扫描所有正式规范
→ 提取规范落地要求表
→ 按类型分组
→ 判断每组应该由什么机制承接
→ 检查是否已有环境适配映射
→ 检查是否已有运行投影
→ 检查是否已有验证方式
→ 输出缺口清单
```

#### 4.5.1 上位约束承接要求

**执行机制**

```text
规范 A 声明自己是上位约束
→ 检查哪些规范引用它
→ 检查相关规范是否真的承接了它
→ 没承接则生成规范缺口
```

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| 有上位依据字段 | 基本有 |
| 有相关规范引用 | 基本有 |
| 能检查字段是否符合 | 部分有 |
| 能检查"语义承接是否完整" | 未闭环 |

#### 4.5.2 入口可见要求

**执行机制**

```text
规范声明入口可见
→ 判断入口场景
→ 生成入口摘要
→ 映射到 Rules / Instructions / README / Skill 描述 / 环境初始化记录
→ 检查入口是否存在
→ 检查入口是否过期
```

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| specs 中声明入口可见 | 已有 |
| 环境初始化记录有映射 | 已有 |
| 项目级入口投影存在 | 未闭环 |
| 漂移检查存在 | 未闭环 |

#### 4.5.3 流程复用要求

**执行机制**

```text
规范声明流程复用
→ 判断是否已有工作流程规范
→ 判断是否需要 Skill / 命令 / 操作清单
→ 若流程不稳定，只记录候选
→ 若流程稳定，建立运行投影
→ 用运行闭环测试验证触发和降级
```

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| 流程复用类型已定义 | 已闭环 |
| 工作流程区段已建立 | 部分闭环 |
| 41 多角色思考已存在 | 已有 |
| 42/43 产品初始化/审计等关键流程 | 从 ADR 看仍缺 |
| Skill 投影 | 未闭环 |
| 测试用例事实源 | 未闭环 |

#### 4.5.4 子 Agent 思考要求

**执行机制**

```text
规范声明子 Agent 思考
→ 判断是否真的需要独立上下文/并行/专项视角
→ 选择角色
→ 主控构造输入
→ 子 Agent 输出
→ 主控汇总
→ 稳定结论回写事实源
```

`41-multi-role-thinking` 已把这条流程写得比较完整。

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| 多角色流程规范 | 已闭环 |
| 角色选择规则 | 已闭环 |
| 主控汇总规则 | 已闭环 |
| 子 Agent 项目级投影 | 未闭环 |
| 多角色运行闭环测试 | 未闭环 |
| 稳定结论回写检查 | 部分闭环 |

#### 4.5.5 确定性执行要求

**执行机制**

```text
规范声明确定性执行
→ 判断是否存在机械化规则
→ 形成 Code 需求
→ 实现最小工具/校验器
→ 加正反样例或测试
→ 输出诊断
→ 问题回写 Task / Memo / 规范
```

当前已有 `tools/specs_validate.py`、`tools/fact_validate.py`、`tools/fact_cli.py`，但覆盖范围主要是文档标题编号、引用完整性、部分规范落地要求字段、环境初始化结构、fact YAML 校验。

还没覆盖：全量规范落地要求聚合、按类型分流、运行投影漂移、生命周期触发缺失、测试用例事实源完整性。

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| Code 规范 | 已闭环 |
| Code 需求准入 | 已闭环 |
| 部分校验器 | 已有 |
| specs 结构校验 | 部分闭环 |
| 落地要求聚合校验 | 未闭环 |
| 运行投影漂移校验 | 未闭环 |

#### 4.5.6 Human 交互要求

**执行机制**

```text
规范声明 Human 交互
→ 判断是否需要确认/授权/验收
→ 映射到对话确认、AskUserQuestion、审批、Web 工作台
→ 保存证据
→ 未确认不得继续执行高影响动作
```

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| Human Gate 条件已有 | 已有 |
| 规范中反复声明 | 已有 |
| 当前会话可通过对话执行 | 部分闭环 |
| 项目级 Human Gate 投影 | 未闭环 |
| Web 受控写入闭环 | 部分/待确认 |
| Human Gate 证据事实源 | 未完全闭环 |

#### 4.5.7 生命周期触发要求

**执行机制**

```text
规范声明生命周期触发
→ 判断触发事件
→ 映射到 Hook / CI / 自动化 / Skill 流程 / 人工降级检查
→ 运行检查
→ 发现漂移
→ 回写缺口
```

典型触发事件：docs/specs 正式规范新增、正式规范修改、规范落地要求变化、Code 校验规则变化、运行投影变化、环境能力变化、会话停止前、commit 前、Task 关闭前。

**闭环检查**

| 检查点 | 当前状态 |
|---|---|
| 生命周期触发类型已定义 | 已闭环 |
| 规范中声明较多 | 已有 |
| Hook/CI 自动触发 | 未闭环 |
| 人工降级检查 | 有 |
| 漂移检查 Code | 未闭环 |

### 4.6 第 5 步：绑定保障机制

每个落地要求都必须有保障机制。保障机制来源：

1. 规范结构保障
2. Code 保障
3. 流程保障
4. 子 Agent 保障
5. Human Gate 保障
6. 生命周期触发保障
7. 环境适配保障

闭环标准：每条落地要求必须能回答——谁/什么机制执行？何时执行？失败怎么办？证据在哪里？是否需要回写？

**当前问题**：很多规范表格里写了保障机制，但颗粒度偏"声明式"，没有统一检查保障机制是否真正实例化。

**闭环状态**：文本声明已闭环，保障机制实例化未闭环。

### 4.7 第 6 步：建立环境适配映射

`04.02` 已规定分层链路。当前 `LDVH-ENVIRONMENT-INITIALIZATION.md` 已做了 Codex 环境映射，但明确承认项目级持久运行投影缺失、漂移检查 Code 缺失。

**闭环状态**

| 层级 | 状态 |
|---|---|
| 环境适配规范 | 已闭环 |
| Codex 初始化记录 | 已有 |
| 当前环境能力核验 | 已有 |
| 持久运行投影 | 未闭环 |
| 漂移检查 | 未闭环 |

### 4.8 第 7 步：生成或登记运行投影

运行投影包括：Rules/Instructions、Skill、Agent、Hook、CI、命令、Code 校验器、Web 页面、Human Gate 提示、环境初始化记录、降级记录。

关键原则：运行投影不是事实源，只是执行入口。

**当前状态**

| 投影类型 | 当前状态 |

| Code 命令 | 部分存在 |
| Web 页面 | 部分存在 |
| 环境初始化记录 | 存在 |
| Rules/Instructions | 项目级缺失或不完整 |
| Skill | 项目级缺失 |
| Agent 模板 | 项目级缺失 |
| Hook | 缺失 |
| CI | 未确认 |
| 漂移检查 | 缺失 |

### 4.9 第 8 步：执行验证 / 漂移检查

由 `10-运行闭环测试规范` 承接。验证分四层：

| 验证层 | 应检查什么 | 当前状态 |
|---|---|---|
| 结构检查 | 文档章节、表格字段、引用路径 | 部分闭环 |
| 规则检查 | 落地要求是否合法、有无保障机制 | 部分闭环 |
| 场景检查 | AI 是否按场景触发流程/暂停/Human Gate | 未闭环 |
| 回写检查 | 稳定事实是否写到正确事实源 | 未完全闭环 |
| 漂移检查 | 规范变了，投影是否同步 | 未闭环 |

最大缺口：`10` 已定义"测试用例事实源边界"，但承载位置还没有稳定。

### 4.10 第 9 步：问题分流回写

| 问题类型 | 回写出口 |
|---|---|
| 规范缺失 | `docs/specs/` 对应正式规范 |
| 规范冲突 | ADR 或规范修正 |
| 环境适配缺口 | `LDVH-ENVIRONMENT-INITIALIZATION.md` / Task |
| 运行投影缺失 | Task / 环境初始化记录 |
| Code 缺口 | Task + `07` 规则下的 Code 需求 |
| 测试用例缺失 | 运行闭环测试用例事实源，当前未稳定 |
| Human Gate 不足 | 对应规范 / Web / Human Gate 机制 |
| 经验教训 | Pitfall / Memo / 最佳实践 |
| 长期决策 | ADR |

**闭环状态**：理论分流规则已存在，工具化分流和测试用例事实源未闭环。

### 4.11 第 10 步：关闭或进入后续 Task

建议关闭标准——一条规范落地要求只有满足以下条件才算闭环：

1. 已声明落地要求类型
2. 已声明保障机制
3. 已判断是否需要环境适配
4. 若需要，已有环境适配映射
5. 若需要，已有运行投影或降级记录
6. 已有验证方式
7. 已执行验证或说明无法验证原因
8. 发现的问题已回写到正确事实源
9. 若仍未完成，已有 Task 承接
10. Human Gate 已处理高影响决策

### 5.1 建立"规范落地统筹"工作流程

#### 42 启动场景

## 7. 最终判断

### 是否都闭环？

还没有。更准确地说：

```text
文档规范闭环：基本成立
落地要求声明闭环：基本成立
环境适配规则闭环：基本成立
执行统筹闭环：未成立
运行投影闭环：未成立
漂移检查闭环：未成立
运行闭环测试事实源：未成立
AI 自我执行需求：部分满足
```

### 当前最该补什么？

不是 `03`，也不是直接按 `14` 改，而是补一个"规范落地要求执行统筹流程"。

它要解决的核心问题：

```text
每个规范都能提出落地要求，
但不能要求每个规范自己知道全局；
必须有一个统一机制收集、分流、验证和回写。
```

如果这个机制补上，规范体系才能从"规范体系自洽"升级为"AI 可稳定执行的运行闭环"。
