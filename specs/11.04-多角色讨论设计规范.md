## 一、角色矩阵

### 1.1 角色全景

角色分为六大维度，共 20 个通用核心角色。角色名称不得绑定具体业务产品、历史项目或特定技术栈：

| 序号 | 维度 | 角色名 | 核心关注点 | 来源 |
|---|---|---|---|---|
| 1 | 产品/需求 | 产品价值审视 | 需求是否值得做、是否偏离目标、成功标准可验证性 | 通用产品评审 |
| 2 | 产品/需求 | 用户体验审视 | 用户路径、交互清晰度、操作摩擦、信息架构 | 通用设计评审 |
| 3 | 产品/需求 | 需求规范审视 | 需求文档完整性、目标边界、验收标准、事实源归属 | PM Kit 规范 |
| 4 | 技术架构 | 客户端架构审视 | 客户端结构、状态管理、渲染边界、平台兼容 | 通用技术评审 |
| 5 | 技术架构 | 服务端架构审视 | 服务端结构、API 契约、数据流、运行边界 | 通用技术评审 |
| 6 | 技术架构 | 数据与模型审视 | 数据结构、模型产物、标注/训练/推理边界、版本管理 | 通用技术评审 |
| 7 | 技术架构 | 数据架构审视 | 数据流、存储方案、结构化对象、序列化与迁移 | 通用技术评审 |
| 8 | 技术架构 | 接口契约审视 | 跨模块/跨项目接口、协议版本、兼容性、契约文档 | 通用技术评审 |
| 9 | 质量/QA | 验证证据审视 | 完成标准、验证方式、关闭证据、可关闭判断 | 通用质量评审 |
| 10 | 质量/QA | QA 工程审视 | 功能测试、回归测试、自动化覆盖、测试策略 | 通用质量评审 |
| 11 | 质量/QA | 性能工程审视 | 性能瓶颈、资源消耗、优化方案、基准测试 | 通用质量评审 |
| 12 | 安全/治理 | 安全工程审视 | 密钥、权限、破坏性操作、依赖安全、数据保护 | 通用安全评审 |
| 13 | 安全/治理 | 风险与权限审视 | 跨项目影响、Human Gate 触发、审计、状态机合规 | PM Kit 规范 |
| 14 | 安全/治理 | 治理审视 | 规则变更、文档治理、编号规范、索引更新 | PM Kit 规范 |
| 15 | AI/工具链 | AI 协作审视 | Skill/Agent/MCP 边界、SOLO 调度、上下文隔离、权限 | PM Kit 规范 |
| 16 | AI/工具链 | 工具链审视 | MCP 配置、工具链、自动化脚本、诊断读取 | 通用工具评审 |
| 17 | AI/工具链 | 文档工程审视 | 文档结构、Change 记录、ADR、索引、可读性 | PM Kit 规范 |
| 18 | 工程流程 | 规范与架构审视 | 状态机正确性、事实源边界、接口边界、ADR | PM Kit 规范 |
| 19 | 工程流程 | 发布与关闭审视 | 可关闭判断、Change 记录、ADR、发布流程、部署边界 | 通用发布评审 |
| 20 | 工程流程 | 复盘改进审视 | 经验沉淀、踩坑记录、流程改进、周期性回顾 | 通用复盘评审 |

### 1.2 角色关注点模板

每个角色分析时应覆盖以下维度：

```text
- 适用性：相关 / 无关
- 影响范围：具体模块 / 文件 / 接口 / 流程
- 分析结论：该角色视角下的判断
- 风险：高 / 中 / 低 — 具体描述
- 建议动作：需要执行的具体事项
```

## 二、变更类型-角色映射

| 变更类型 | 默认角色组合 |
|---|---|
| 需求/产品变更 | 产品价值审视、需求规范审视、用户体验审视 |
| 客户端相关 | 客户端架构审视、数据架构审视、QA 工程审视 |
| 服务端相关 | 服务端架构审视、接口契约审视、性能工程审视 |
| 数据/模型相关 | 数据与模型审视、数据架构审视、验证证据审视 |
| UI/前端变更 | 用户体验审视、客户端架构审视、QA 工程审视 |
| 安全/合规变更 | 安全工程审视、风险与权限审视、治理审视 |
| 跨项目接口/契约 | 接口契约审视、客户端架构审视、服务端架构审视、风险与权限审视 |
| 规则/规范/文档 | 治理审视、文档工程审视、规范与架构审视 |
| Skill/Agent/AI 协作 | AI 协作审视、工具链审视、规范与架构审视 |
| MCP/工具链/自动化 | 工具链审视、性能工程审视、安全工程审视 |
| 发布/部署/关闭 | 发布与关闭审视、验证证据审视、文档工程审视 |
| 复盘/流程改进 | 复盘改进审视、治理审视、规范与架构审视 |
| 通用架构/大型重构 | 全部角色，或按影响面精选 8-12 个核心角色 |

## 三、角色筛选与精简

当匹配角色超过 8 个时，按以下优先级精选：

1. 保留与变更类型直接相关的技术或治理角色。
2. 保留风险与权限审视。
3. 保留验证证据审视。
4. 同维度角色可合并分析。
5. 发布与关闭审视、复盘工程师仅在涉及发布、关闭或复盘时保留。

精简后建议角色数控制在 5-8 个。被精简角色可在报告中标注，如需深入分析可补充。

## 四、分析模式

### 4.1 轻量模式

适用于只读讨论、文件读取少、不需要独立上下文、隔离执行或并行分析的场景。

执行步骤：

1. 识别变更类型。
2. 从角色映射表获取默认角色组合。
3. 根据项目实际情况增删角色。
4. 按角色关注点分别分析。
5. 汇总各角色分析，产出结构化对比报告。

### 4.2 建议升级模式

适用于分析中发现需要独立上下文、结论隔离、并行委派、大量事实源读取或不同工具权限的场景。

执行步骤：

1. 先产出轻量分析报告。
2. 在报告中说明为什么轻量模式不足。
3. 提示用户建议调用 SOLO Agent 进行多 Agent 分析。
4. 不直接调度 Agent。

## 五、输出格式

```markdown
# 多角色视角分析报告

## 适用性判断
- 是否属于多角色分析场景：是/否
- 分析模式：轻量模式 / 建议 SOLO Agent 模式
- 涉及角色：{角色列表}

## 变更概述
- 变更内容：{一句话描述}
- 影响范围：{模块/项目列表}

## 各角色分析

### {角色名}
- 适用性：相关 / 无关
- 影响范围：{描述}
- 分析结论：{结论}
- 风险：{高/中/低} — {描述}
- 建议动作：{列表}

## 角色间分歧
- {分歧点}：{角色 A 观点} vs {角色 B 观点}

## 风险汇总
- 高风险：{列表}
- 中风险：{列表}
- 低风险：{列表}

## 建议执行顺序
1. {第一步}
2. {第二步}

## 需要同步的文档/规则
- {文档/规则列表}

## Human Gate
- 是否建议 SOLO Agent 深入分析：是/否
- 其他需要用户确认的事项：{列表}
```

## 六、多角色讨论检查项

| 检查项 | 标准 |
|---|---|
| 角色匹配 | 已根据变更类型选择角色 |
| 角色精简 | 超过 8 个角色时已精简 |
| 影响范围 | 明确模块、文件、接口或流程 |
| 风险分级 | 高/中/低风险表达清楚 |
| Human Gate | 引用 11-AI协作规范 §十二，不维护第二套清单 |
| Agent 边界 | 只建议用户调用 SOLO Agent，不直接调度 Agent |
| 输出格式 | 包含结论、风险、建议动作和确认项 |
