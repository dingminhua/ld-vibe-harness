## 1. 价值判断

本文的价值，是把五类事实对象创建后反复出现的“读取当前快照与关系、区分更正/普通更新/生命周期变化/多对象承接、核对具体类型规则与授权、形成完整 after、选择原子能力、回读验证和交还”组织为稳定行动结构。它减少用内容修改偷渡状态推进、用状态变化覆盖事实更正、以旧指纹覆盖并发变化、把替代拆成不一致的多次写入，以及关闭旧对象却丢失剩余事实与关系的风险。


对 Human 而言，本文只直接支持 HV3「入档闭环节点可验」中的既有对象变化节点：内容、状态、阶段、关闭、分流或替代必须经具体类型规则允许的完整 after、CAS 和写后回读，才能在相应范围内表达为已经发生。本文不替具体类型定义闭环，也不因单个节点机械有效就宣称事项整体已经完成或获得 Human 接受。

## 2. 规范依据

本文直接依据：

1. `action-template-foundation`：规定模板共同结构、授权、能力、失败分流、验证和交还；
2. `fact-model-foundation`：规定事实对象共同更新边界、单对象 CAS 操作、多对象变更的原子性要求和具体类型权威分工；

本文不得另行定义或改变上述来源的转换表、字段清单或证据条件。行动中为防止错误路由、非原子写入或 Human Gate 绕过而复述的高风险约束必须显式回指原来源，发生冲突时以 20–25 的唯一类型来源为准。04、07、Human 指令、项目规则和实际能力按当次对象提供服务、实现、授权和验证输入。

## 3. 职责边界

本文负责定义：

1. 既有对象变更候选的进入、排除、不确定和作用范围；
2. 当前对象、关系闭包、来源、证据、授权与并发基线的读取顺序；
3. `fact_correction`、`content_update`、`single_object_lifecycle` 和 `multi_object_disposition` 四类当次变化闭集，以及按完整写集合和共同不变量分类的边界；
4. 完整 after、单对象 CAS、多对象原子能力、回读验证和失败交还的稳定关系；
5. 合法多步序列与多对象原子事务的区别；
6. 新对象创建、Git 提交、能力缺口和残留责任的分流。

本文不负责定义：

1. 各类型合法状态、阶段、转换边、进入条件、关闭分类、关系或字段失效；
2. 自然语言事实是否真实、证据是否充分、审核是否独立或 Human 决定是否成立；
3. Helper 请求响应字段、CAS 算法、事务、锁、文件替换、回滚、错误码或测试实现；
4. 删除、批量修复或 Git 历史操作的实现；
5. 无承接关系的新对象是否应创建；
6. commit、push、PR、发布或上层工作完成。

20–25 定义“什么变化合法”；本文定义“如何组织一次变化”；05/04 定义可调用的领域/共同服务契约；Code 只执行已实现的确定性检查和状态变更。任何一层不得代替另一层。

## 4. 适用范围

当目标明确指向至少一个当前事实对象，并准备改变其内容、状态、阶段、关系、终态或承接位置时，本模板产生候选。执行状态变更前必须能够：定位唯一管辖项目和实际 worktree；以稳定引用读取当前对象与必要关系闭包；确认具体类型来源和当次授权；取得支持并发检测的当前内容基线；判断变更属于单对象还是必须多对象共同成立。

只读消费、候选对象化判断、无承接关系的新对象创建、普通文件编辑、Git 提交或类型来源本身修改不适用。目标、当前对象、来源、授权、关系闭包或原子范围不确定时，只继续只读核对或交还，不猜测变更。

## 5. 事实对象生命周期变更与承接处置行动模板定义

### 行动模板声明

| template_key | summary | definition_ref |
|---|---|---|
| `fact-object-lifecycle-change` | 对既有事实对象区分更正、普通更新、单对象生命周期变化与多对象承接，按当前类型规则和可用原子能力执行、回读和交还 | `fact-object-lifecycle-change-action-template::5. 事实对象生命周期变更与承接处置行动模板定义` |

### 5.1 输入与前置条件

执行者必须取得：Human 当前目标与授权；属于已获 Gate 1 批准的 WorkCase 时，还必须取得当前 `execution_authorization`、与其准确绑定的 `execution_approval` 及实际 Human 来源回指；唯一项目/worktree；目标稳定引用；当前完整对象、内容指纹与必要关系闭包；具体类型来源；支持变更声明的来源、证据、审核和 Human 决定；实际可用的读取、单对象 CAS 或多对象原子能力。旧摘要、路径猜测、Web 卡片、缓存指纹、模板中的状态词或 approval 字段单独存在不能替代当前对象与授权包回读。

### 5.2 参与者、能力与授权

AI 负责分类变更、解释类型规则、核对来源证据、确定原子范围、形成完整 after、处理并发与验证结果。Human 只作出类型来源和当前指令保留给 Human 的方向选择、批准、关闭、风险接受或承接决定；当前 WorkCase Gate 1 已把事实变更及其目标、范围、副作用和风险逐项列入 `execution_authorization` 并形成有效 `execution_approval` 时，相应决定已经存在，不因进入本模板、切换执行者或准备调用 Helper 再次请求。Helper/Code 只对已声明且实现的稳定引用、机械校验、CAS、原子变更、关系图和回读提供能力；单对象能力存在不表示多对象能力已经存在。

### 5.3 行动步骤与分支

#### A. 建立当前对象和影响闭包

1. 定位唯一项目/worktree，以稳定引用精确读取目标对象并保留 `content_fingerprint`；
2. 按具体类型来源展开会影响合法性、基数、DAG、依赖、替代、路由或承接的目标与反向关系；
3. 核对当前状态/阶段、来源、证据、版本、审核、批准、阻塞和未完成读取范围；
4. 读取当次授权，区分“允许修改内容”“允许推进状态”“允许关闭/替代/承接”等不同作用范围。获批 WorkCase 中以当前 `execution_authorization`、`execution_approval` 和 Human 来源回指共同证明已批准范围；不得只读 approval 摘要、模板 key 或 item 名称后推定授权。

#### B. 分类变化并确定原子范围

当次变化必须且只能归入以下一类。分类依据是变化完整成立所需的写集合、关系和共同不变量，不是用户使用了“修正”“更新”“关闭”“路由”或“替代”等动作词：

1. `fact_correction`：修复同一对象中已记错或遗漏的事实，对象身份及 status/phase 保持不变；其它更正若同时需要生命周期变化，整体改按 `single_object_lifecycle` 分类；
2. `content_update`：补强或更新仍属于同一对象的当前内容，对象身份及 status/phase 保持不变；与事实更正的差异由 AI 根据来源和实际含义判断，Code 不裁决二者；
3. `single_object_lifecycle`：完整成立只需要修改一个既有对象，并且具体类型来源明确允许由一个完整 after 完成；所需批准、版本、结果、条件字段和关系变化必须在同一 after 中共同成立；
4. `multi_object_disposition`：完整成立要求创建或修改两个以上对象，或者多个对象、关系和状态必须共同生效；全部写目标、前置指纹和共同不变量属于同一原子范围；
5. 关闭、路由、直接落实或关系变化不因名称自动成为多对象处置。若目标对象已存在且无需修改、反向关系只由 Code 派生，或直接落实只改变一个对象且无需建立事实承接关系，则仍可按类型来源判断为 `single_object_lifecycle`；若必须新建或更新承接目标，或同时改变多个对象、关系或状态才能完整成立，则属于 `multi_object_disposition`；
6. Spark 不再支持 partial-successor routing 或 Spark-owned `routed-to`。Spark 只按其自身三状态完成单对象生命周期变化；“交给 WorkCase”写入 Spark 的处置说明，不创建 successor、不改变 Spark 承接关系。WorkCase 的 `multi_object_disposition` 语义仍保留，但本 WC 不新增、不改写、不执行它；若未来其它类型需要多个对象共同生效，仍按本模板的多对象边界处理；
7. WorkCase 的操作路由不取代本节语义分类：必须同时根据当前 before 和实际变更意图选择 21 唯一允许的专属操作，不得因为自称“更正”“笔误”或“无状态变化”改走通用写入；
8. 若变化实质上是无承接关系的新对象创建，转交 `fact-object-controlled-creation`；若只是 Git 提交，另按 `git-commit` 判断。

#### C. 执行单对象分支

1. `ldvh-base/` 中的 canonical 事实载体只允许由当前来源定义且与对象类型、carrier 和变化分类匹配的 Helper 受控操作写入；不得用普通文件工具、脚本、重定向、补丁或其它绕过 Helper 的方式直接修改。依据具体类型来源形成排除 Code 托管字段后的完整目标 after；未提交的字段表示 after 中不存在，不实施字段级 merge。AI 必须显式处理条件字段、版本、审核、批准和失效集。类型来源要求直接落实判断时，AI 先 F3 读取对象并按需 F4 核对必要依据，再消费已经覆盖准确对象、变化、影响和风险的 Human 当前授权；获批 WorkCase 可以消费 Gate 1 授权包，不得因进入该判断步骤再索取同一授权。F4 不写入对象、关系或 CAS 请求；

当 mechanically valid 遗留对象完全缺少 `change_log` 时，只能按 05 §11.7 在原本合法的同一次真实更新中建立第一条当前三字段流水；`workcase-0100` Gate 1 已明确批准该专用方案。执行者必须取得当前完整 Working Tree before 与 fingerprint；Code 还必须在同一受控事务确认 HEAD 同路径普通文件机械有效且同样完全缺少流水。HEAD 已有流水但 Working Tree 删除、HEAD 不存在/不可读/无效、after 不是原本合法的业务变化、首写不是恰好一条或含旧署名时零写入拒绝。第一条只记录本次变化并说明此前历史未恢复，不表示对象创建或完整历史；不得调用退休迁移入口、独立补写基线或推断旧署名。

若 HEAD 或未提交候选含旧签名形状，当前入口不得改名归一或重签名；旧候选不能通过当前 Git Gate，须由 Human 决定舍弃、回退或另行建立范围更窄的当前三字段更正方案。已批准的首次流水方案只适用于 HEAD 与 Working Tree 都完全没有流水的 before，不修复任何已有旧形状记录。

| WorkCase before | 当次意图与 after | 唯一操作 |
|---|---|---|
| 机械有效的 `status=open|blocked` 活动期对象 | 事实更正、内容更新、item 或 phase/status 的合法推进、关系变化、审核/批准/关闭提案形成，after 仍为活动期 | `update-workcase` |
| 机械有效的 `status=open|blocked` 且 `phase=human_closure_confirming` 对象 | Human 已对当前完整 before 作出关闭决定，after 为由当前 proposal 唯一形成的 `closed` | `close-workcase` |
| 机械有效的 `status=closed` 对象 | 只更正原关闭时已成立但被记错或遗漏的事实，after 仍为 `closed` | `correct-closed-workcase` |

`update-workcase` 不得形成 closed，也不得进入或离开 `termination_preparing`；`begin-workcase-termination` 只开始 Human 主动终止，`complete-workcase-termination` 只完成该专属善后并形成 closed；`close-workcase` 不得更正已 closed 对象，`correct-closed-workcase` 不得重开对象。重复关闭不是 `no_change`，必须拒绝。

3. WorkCase 三个操作都复用 05 §11.7 的 `workspace_root`、`fact_ref`、`expected_content_fingerprint`、`fact_object`、共同请求包装与结果形状，并复用 §11.8 的共享事务。`fact_object` 必须是排除 Code 托管身份和时间字段后的完整 after，不接受 patch、顶层差量或由 Code 猜测目标状态。`expected_content_fingerprint` 必须精确绑定当次实际参与判断的 AI、Reviewer 或 Human 所使用的完整 source before；
4. `update-workcase` 中，Reviewer 可以新增一次实际发生的 `creation_reviews` / `result_reviews` 事件，并只填写该事件的 Reviewer 自有字段；Controller 只形成本次当前处置及其它 Controller 所有字段。普通更新不得改写已有 review 事件的 Reviewer 自有字段；获授权的事实更正也必须保留同事件身份与被审对象。Reviewer conclusion 不自动选择 phase 或代替 Human 决定；`execution_approval` 只能对应 Human 在 Gate 1 对当时 `plan_version` 与冻结 `execution_authorization` 基线的实际批准，`baseline_fingerprint` 必须继续匹配当前冻结基线；包内 PlanΔ 只更新 current plan review 与 `plan_version`，不改写或补造 approval。当次变化消费 Human 实际决定时，共同 `authorization_reference` 只回指该 Human 输入；同一获批 WorkCase 的计划内后续步骤可以继续回指该 Gate 1 来源，不因步骤或执行者变化要求新的 Human 输入。Reviewer 输入不写入该引用；
5. `close-workcase` 的 before 必须完整机械有效，且为 `phase=human_closure_confirming`；共同 `authorization_reference` 必须回指 Human 针对当前 before 与 proposal 的实际关闭决定。Human 只决定是否停止、是否按当前结果与验证所支持的分类接受相应风险，以及每项剩余责任是 route_existing、suggest_spark 还是 accept_stop；Human 可在建议的 Spark 尚未建立时关闭，不为技术结果真实性背书；Reviewer 不做关闭决定；
7. `close-workcase` 不接受脱离 before proposal 的第二份目标或 suggestion 清单。Code 必须在同一 source 事务中重新读取 proposal 中全部 route_existing targets，逐个精确比较已保存指纹，并检查同项目、WorkCase open/blocked 或 Spark open 状态、引用、去重和关系图约束；Code 还必须对 source 完整检查入向 `depends-on`。任一 target 变化、缺失、不可读或不再合法，或 source 入向依赖检查未通过时，source 零写入，Controller 重建 proposal 并重新取得 Human 决定；
8. `correct-closed-workcase` 除完整 closed after 外，必须提交 `route_target_fingerprints` array 与 `independent_review_reference` object-or-null。指纹数组必须按目标去重，与 after 全部 `routed-to` targets 精确相等；无 target 时是空数组。每个成员的 `target` 使用 05 稳定三元组，`content_fingerprint` 原样复用当次精确读取的完整载体指纹；Code 在同一 source 事务中回读全部 after targets。before 已有且 after 未改变的 target 可按自身生命周期处于后续状态；after 新增 target 只能是同项目、机械有效的 `open|blocked` WorkCase 或 open Spark；
10. `correct-closed-workcase` 只能修复原关闭时已成立的记录错误或遗漏，不得因后来事实、target 后续进展、新责任、新建 Spark 或新验收边界回溯改写历史；后来的新 Spark 从自身写 `related-to → 原 WC`，不回写 closed source，不要求 residual/suggestion ID。after 仍必须满足 21 的 outcome 一致性与剩余责任完整处置；任一标准为 `not_satisfied` 或 `not_verified` 时，至少存在一项 `residual_responsibilities`、`routed-to` 或 constrained `spark_suggestions`，语义全覆盖由 Controller、Reviewer 和 Human 确认，Code 不猜测文本对应；
11. `update-workcase`、`begin-workcase-termination`、`complete-workcase-termination`、`close-workcase` 与 `correct-closed-workcase` 都只接受 mechanically valid 的当前 before；invalid、unavailable、not-found 或只能解析部分字段的 WorkCase 必须零写入拒绝，并交还实际问题与继续只读诊断入口。五个专属操作不提供旧形状转换或 invalid 记录修复；不得把 05 为其它类型来源明确允许的修复例外扩张到 WorkCase。唯一例外是 21 的固定清单 `recover-invalid-workcase`：它只读取已绑定的历史 Git carrier，要求目标 `status=closed` 且 `check_status=invalid`，在 0092 的固定恢复标记、当前 fingerprint 和完整性审计证明成立后才可恢复 0093，不承诺跨对象原子性或通用 invalid 修复；已带恢复标记的目标不得再次恢复；
12. `fact_correction`、`content_update` 和 `single_object_lifecycle` 可以复用同一共享单对象 CAS 事务，但调用前的语义分类、授权、来源与证据判断保持不同。Code 只验证完整 after 与来源定义的确定性转换边界，不得提供通过 `advance`、`pass`、裸 `close` 等动作词自行推导 after 或 phase 的语义命令；正式 `close-workcase` 仍只消费调用方已经形成的完整 after。Code 不得从 Reviewer conclusion 或普通字段差异决定 phase、版本、复审或 Human Gate。指纹变化时拒绝覆盖，必须重新读取并由 AI 判断目标是否仍成立；
13. `no_change` 不制造时间或成功变更；拒绝、失败、回滚、部分结果和不可观察结果按实际结果交还；
14. 每次 Helper 受控操作返回后，只要共同 `changes`、领域结果、`final_observation` 或来源要求的重新观察表明已发生、仍残留或无法排除任何事实源写入（无论 Helper 外层 `outcome` 为何），就必须按响应中的实际 locator 或 attempt identity，从同一实际 Working Tree 分别尝试精确回读当前对象及必要关系闭包，并检查写入口返回的独立完整性审计 `verification`；需要当前重新观察时再调用公开 `check-fact-integrity`。locator 或 attempt identity 不足、回读无法完成、事实源写入无法排除，或完整性检查为 `result.status=partial`、外层 `outcome=unavailable` 或其它非 `ok`、调用失败、已因事实集合、规则源、worktree 变化而失效时，都必须保留最近已回读状态以及实际或可能残留，停止后续事实写入、提交与成功声明，不得直接修补 canonical 载体。只有精确回读成立，且完整性检查外层 `outcome=ok`、`result.status=complete` 时，才可继续下一次事实写入或形成成功声明。Code 验证回读对象的机械成立范围，AI 再依据类型来源审核其类型语义是否成立；精确回读与整库机械审计互不替代，后者是写后过程检查，不进入普通提交候选校验链。

#### D. 组织合法多步序列

1. 只有每一步都能独立形成具体类型允许的完整有效对象、由现有且当前有效的授权覆盖相应对象、变化与风险，并且中间状态能够保存和恢复时，才可把多个单对象 CAS 组织为合法序列；“每步有授权”不表示每步重新进入 Human Gate，获批 WorkCase 中逐项列明的步骤直接消费同一 Gate 1 授权包；
2. 每一步写后必须完成 §C.14 的精确回读与 `check-fact-integrity`，并仅在两者成立后使用该次回读的新 `content_fingerprint` 形成下一步；不得复用序列起点指纹、把多个预计算目标连续写入、跳过整库机械审计或跳过中间语义复核；
3. 同一转换要求共同成立的字段必须放入一个完整 after，不能拆成多个暂时无效的对象。例如 21 已规定 WorkCase 的活动期推进必须与当次适用的字段、版本、review/处置、批准和失效集共同满足转换条件；从 `human_closure_confirming` 形成 closed 不是普通 phase 边，必须单独调用 `close-workcase`；模板只回指该规则，不复制其状态机；
4. 合法序列只能确认每个已完成单对象步骤分别成立，不表示整段序列具有事务原子性。后续步骤被拒绝、失败、等待 Human 或尚未授权时，必须保留并交还最后一个已回读的合法状态；
5. 只要完整责任要求多个对象共同生效，就不得使用合法单对象序列代替 `multi_object_disposition` 的原子能力。唯一来源明示允许的例外是完整 WC 现场 draft Pitfall 与 source `contributed-to`：两步本来就被定义为各自独立成立的非原子序列，后一步失败时保留 draft 并如实交还，不声称关系已成立。

#### E. 执行多对象分支

1. 同时形成所有受影响对象的变更前基线、各自完整 after、关系变化、来源证据、授权与不变量；
2. 只有当前规则源已经定义多对象公开操作，且 Code 对全部目标、关系、CAS 基线、原子写入、失败回滚和回读具有范围匹配实现时才执行；
3. 任一对象、关系、指纹、来源、授权或能力缺失都不得先写其余对象；预先创建孤立新对象、多个单对象成功、补偿更新或后续补关系都不能拼接成多对象原子成功；
4. 当前多对象公开能力未成立、范围不匹配或结果不可观察时，必须零写入；交还完整拟变更范围、各基线指纹、共同不变量和能力缺口，保持全部对象原状，不把计划、部分准备或单对象结果当作整体结果；
5. 未来范围匹配的多对象公开操作返回后，只要共同 `changes`、领域结果、`final_observation` 或来源要求的重新观察表明任一目标已发生、仍残留或无法排除事实源写入（无论 Helper 外层 `outcome` 为何），就必须按每一已知 locator 或 attempt identity 分别尝试精确回读受影响目标，并立即对同一 worktree 调用 `check-fact-integrity`，不得等待或假定其它目标回读全部完成。只有全部实际受影响目标的精确回读成立，且完整性检查外层 `outcome=ok`、`result.status=complete` 时，才可声明该多对象写入通过写后机械审计；无法定位、回读、审计或排除残留时，保留实际结果并按 §C.14 停止。

21 没有声明 WorkCase 多对象原子写操作，本模板不得补造一个。`close-workcase` 和 `correct-closed-workcase` 只原子修改 source WorkCase；route_existing targets 只在同一 source 事务中重读、校验和比较指纹，不被该事务修改。Spark 不创建 successor、不建立 Spark-owned `routed-to`，也不以多次单对象写入拼接承接结果。`suggest_spark` 无 target 对象，Human 可先关闭 source；后续新 Spark 由 Human 独立创建并从自身关联 closed WC。已存量 target 需更新才能覆盖 route_existing 责任时，只有该 target 行动本身可以独立成立且 Human 允许非原子序列时，才可先按其自身来源完成并回读，再使用当前 target 快照重建 proposal 或更正目标集；该序列不得表述为跨对象原子成功。若单步不能独立成立，或 Human 目标要求 source 与 target 必须共同原子生效，当前能力缺失并停止，不改写任一对象。

### 5.4 输出、验证、回写与交还

交还至少区分：目标对象与影响闭包；四类闭集中的当次分类和所依据的类型来源；完整写集合；单对象 CAS、合法多步序列或多对象原子范围；授权、来源、证据、审核和 Human Gate；每个已执行步骤变更前后的稳定引用、指纹、状态/阶段与关系；逐写 `check-fact-integrity` 的外层结果、`result.status`、问题与失效边界；实际写入、拒绝、无变化、回滚、残留和副作用；机械验证与 AI 语义审核覆盖；未执行、未验证和后续承接；Git 提交及其它排除行动是否已由 Human 直接授权或 WorkCase Gate 1 逐项列明，以及实际执行或未执行结果。WorkCase 还必须交还由 before/意图选中的专属操作、完整 after 回读、当次实际消费的 Human / Reviewer 输入边界、已校验与未校验的 route targets，以及 closed 保留集或终态更正范围。分类、序列和引用信息默认只作为当次交还，不自动成为 Helper 请求字段或事实对象字段。

长期回写只进入具体类型来源允许的事实对象和关系位置。模板不保存运行阶段、事务 receipt 或执行日志；多对象能力缺失时的拟变更默认只作当次交还，除非其它稳定来源另行准入。

### 5.5 组合、变更与退出

替代或承接可能在一个原子行动中包含“创建新对象 + 更新旧对象 + 建立关系”，整体由本模板多对象分支承担，并复用 31 的对象化/类型判断成果，但只有来源已声明范围匹配的公开原子操作时才可执行，不得调用 31 的单对象创建后再宣称整体完成。Spark 简化模型不产生 successor 或 Spark-owned route；WorkCase 只执行 21 已声明的三个单 source 专属操作，不因需要承接目标就推导或新增多对象操作。Human 已直接授权本地 commit，或当前 WorkCase `execution_authorization` 已逐项列明该 commit 且 `execution_approval` 准确覆盖时，变更回读完成后可串联 30；事实对象变化本身不自动产生提交授权。串联时，逐写 `check-fact-integrity` 不能替代提交预检，只有 `precheck-git-commit` 外层 `outcome=ok` 且 `result.mechanical_outcome=passed` 才进入 30 的机械合规路径。

模板稳定结构、原子边界或失败分流改变时按 06 重审。若未来多对象能力拆成独立、稳定且具有不同失败闭环的行动，需重新比较是否拆模板；不能仅因新增 API 就拆分。

## 7. Human Gate

本文不新增统一 Human Gate。凡 20–25 或 Human 当前指令保留给 Human 的计划批准、关闭确认、方向、证据争议、替代、退出、删除、风险接受或其它决定，都必须先由 Human 实际作出，再由相应行动在其明确对象和范围内消费。已有决定只覆盖其明确对象和范围；不能用一次一般“更新”授权推定关闭、替代、创建新对象或 Git 提交授权。当前 WorkCase Gate 1 的 `execution_authorization` 已逐项列明这些动作、准确对象、允许影响与风险边界，并由 `execution_approval` 实际批准时，不属于一般更新授权，相应计划内行动直接消费该批准，不重复进入 Human Gate。

WorkCase 中，Human 的 Gate 1 当前计划与授权包批准、Gate 2 最终关闭决定和 closed 实质更正决定彼此不可替代，也不由 Reviewer conclusion 或 Code 机械通过推定。当前计划批准和活动期 review 按 21 写入当前活动对象，关闭时随活动期过程字段移除。最终关闭决定不另存终态收据。除只更正原关闭 `related-to` 记录的明示例外外，实质 closed 更正还必须有当次实际独立复核与 Controller 处置；related-to 例外仍必须有 Human 新决定。当次终态更正的复核与 Human 决定引用只作为操作输入被消费，不保存为终态证明或过程收据。Pitfall 的 promote/discard 或其它对象变化只有在 Gate 1 已针对准确对象、目标动作和风险逐项授权时才可在当前 WorkCase 中直接消费；执行中形成、Gate 1 无法绑定最终快照的变化不得反向推定授权。

已获 Gate 1 批准的 WorkCase 发现动作未列明、对象或影响范围扩大、需要接受新风险，或实际能力只能执行更高影响副作用时，不得在执行期进入追加 Human Gate，也不得先写入再补授权。受影响变化保持零写入，按 21 与 34 据实取消或收敛相应 item，并继续 Controller 自检、独立结果复核和 Gate 2。Human 主动撤回或改变目标仍按其新指令处理，但不把系统主动索取扩权加入正常两次确认流程。

## 8. Stop Conditions

出现以下任一情况时，暂停受影响的对象、原子范围、状态变更或相应声明：

1. 项目/worktree、稳定引用、当前对象、指纹或影响闭包无法确定；
2. 使用缓存、卡片或旧摘要替代当前完整对象和关系回读；
3. 无法区分事实更正、普通更新、单对象生命周期变化和多对象承接；
4. 模板正在自行定义或改写类型状态、阶段、转换、字段失效、关系或证据条件；
5. 当次授权、来源、证据、审核或 Human Gate 不覆盖实际变化；
6. 完整 after 不成立、CAS 指纹过期或准备覆盖并发变化；
7. 需要多对象共同成立但公开契约、实现、原子性、回滚或回读能力缺失；
8. 准备用多个单对象写入拼接替代、路由、关闭或承接成功；
9. 多步序列中的某一步尚未回读或仍使用旧指纹，耦合字段被拆成无效中间快照，或者准备把逐步成功冒充事务原子性；
10. 多对象能力未成立时准备预写新对象、先改一个目标、依赖补偿或随后补关系，而不是保持零写入；
11. 写入失败、拒绝、部分成立、回滚或结果不可观察，却准备声明完成；
12. 写后未回读对象和必要关系闭包，或承接仍有缺口；
13. 准备把事实对象变化扩张为事实真实、审核通过、工作完成、Git 已提交、push 或发布；
14. 声明无效、来源冲突或模板不适用，却准备以模板阻止普通求解；
15. 准备用 `update-fact-object` 写 WorkCase，按字段差量选择操作，或将活动期更新、专属关闭、closed 更正路由到错误的 WorkCase 操作；
16. WorkCase 请求未提交完整 after，准备做 patch/merge，或让 Code 从 Reviewer conclusion、Human 回应或普通字段差异猜测 phase、版本、复审或 Human Gate；
17. 任一 WorkCase 专属操作收到 invalid、unavailable、not-found 或只能解析部分字段的 before，却准备继续形成 after、删除旧字段、改换形状、推进 lifecycle 或声明已修复；
18. `close-workcase` 的 before 不是机械有效的 `human_closure_confirming`，Human 决定与当前 before/proposal 不匹配，route target 指纹或图约束失效，closed after 未精确保留应保留事实、未严格映射 proposal、保存了活动期过程字段，或夹带事实更正；
19. `correct-closed-workcase` 准备根据后来事实、target 进展或新责任回溯改写原关闭历史，after target 指纹数组与实际 `routed-to` 不等，目标未全部回读或状态不合法，实质更正缺少实际独立复核、Controller 处置或 Human 新决定，或终态剩余责任没有完整承接；
20. 准备为 WorkCase 补造多对象原子操作，在 close/correct 事务中修改 route target，或把独立创建/更新 target 后再关闭 source 表述为跨对象原子成功。
21. Pitfall promote 中夹带任何正文、关系或处置变化，discard 删改原正文/关系或缺少处置，审核绑定非最终 draft 快照，或准备批量原子处理多个 draft。
22. WorkCase suggest_spark 被要求先创建 target 才能关闭，建议中保存未来 Spark ID，或后续 Spark 被要求引用 residual/suggestion ID。
23. 准备向 closed WC 追加后来新建对象的 `related-to`，把后来事实冒充原关闭记录更正，或对只更正原关闭 related-to 强制要求独立 result review；
24. 准备用普通文件能力直接写入 `ldvh-base/`，或者任一次实际 Helper 写入后尚未完成精确回读与外层 `outcome=ok`、`result.status=complete` 的 `check-fact-integrity`，却准备继续下一次事实写入、提交或声明变化成立。
