## 一、本文解决的问题

本文定义多角色思考行动模型。多角色思考是 AI 在面对复杂变更、复杂决策、跨模块影响、规范治理、协作机制调整或高风险操作前，按多个专业视角分别分析、汇总分歧、识别风险、提出建议动作和 Human Gate 判断的行动。

多角色思考行动模型统一定义何时进入、读什么、如何选择轻量模式或多角色子 Agent 模式、如何使用可调用 Agent 容器注入角色参数、如何输出、如何回写稳定事实和如何审计。

本文是多角色思考行动模型的完整主文档。Rules、Skill、Agent、Tools、Web 相关子文档仅作为附件型实践承接文档，按需展开对应机制实践，不重新定义多角色思考行动模型。

## 三、行动定位与适用场景

### 3.1 行动定义

多角色思考是面向复杂问题的分析增强行动。它通过多个专业视角分别分析同一输入，降低单一视角遗漏风险，帮助 AI 和人识别影响范围、风险等级、分歧点、建议执行顺序、需要同步的事实源和 Human Gate。

多角色思考不是独立事实源，不替代 ADR、Task、Memo、Risk、Evidence、Change 或规范正文。它的输出默认是过程分析；只有按事实源边界写回对应 Git 文件后，才成为稳定事实。

### 3.2 适用场景

出现以下情况之一时，应考虑进入多角色思考：

1. 用户明确要求从不同角色、不同专业视角或多角色角度分析；
2. 规范、规则、Skill、Agent、工具或行动模型变更需要评估跨模块影响；
3. 技术选型、架构调整或工具设计需要同时评估性能、安全、可维护性、验证和治理边界；
4. 需求变更会影响产品、前端、后端、数据、测试、发布、治理或 AI 协作多个维度；
5. 需要判断某个输出应分流为 Task、Memo、ADR、Risk、Evidence、Change 或 docs 报告；
6. 需要在执行高影响变更前识别 Human Gate 和证据要求；
7. 主上下文判断存在明显不确定性，且单一视角可能遗漏重要风险。

### 3.3 不适用场景

以下情况通常不应进入多角色思考：

1. 简单问答或单文件小改，单一主上下文即可处理；
2. 用户已经明确给出决策并只要求执行低风险操作；
3. 问题已满足 Task 准入条件且不需要多视角分析，应直接进入对应 Task 行动；
4. 只需要确定性字段校验，应使用Tools 辅助或对象审计；
5. 已经由具体行动模型定义了更直接的执行流程，且没有复杂分歧或跨角色影响；
6. 用户明确要求不要进行额外分析。

## 四、准入条件

多角色思考行动的准入条件如下：

1. 存在一个需要分析的明确主题、变更、决策、风险或问题；
2. 至少存在两个以上有意义的分析视角；
3. 分析结论可能影响后续执行、规范、对象、工具、协作机制或 Human Gate；
4. 输入材料能够追溯到用户输入或 Git 文件事实源；
5. AI 能够明确说明本次分析是过程分析，还是需要回写为稳定事实。

不满足准入条件时，应退回主上下文直接回答、询问用户补充输入，或分流到更合适的行动、Skill、Agent 或Tools 辅助。

## 六、Context 要求

### 6.1 最小 Context

执行多角色思考前，AI 应获得以下最小 Context：

1. 用户提出的分析主题、目标、约束和期望输出；
2. 当前项目 L1 规则和相关工作区规则；
3. 与本次主题直接相关的 specs、ldvh-base、docs、tools、web 或代码文件；
4. `specs/14-LDVH行动模型基础规范.md`；
5. `specs/11-LDVH-AI协作规范.md`、`specs/11.02-Skill机制规范.md`、`specs/11.03-Agent机制规范.md`；
6. 需要判断事实源回写时读取 `specs/10-事实源边界与承载规范.md` 和对应生产对象规范；
7. 需要判断工具协作时读取 `specs/12-LDVH工具基础规范.md`。

### 6.2 可选 Context

根据主题复杂度，可增加以下 Context：

1. `specs/evals/` 中与本次主题相关的内部评估文档；
2. 已存在的 Task、ADR、Memo、Risk、Evidence 或 Change 实例；
3. 当前环境中可调用 Agent 容器的能力说明。

可选 Context 只能作为输入材料，不能覆盖当前 specs/ 正式规范，也不能被当作当前项目已经存在对应 Skill、Agent、Tools 或 Web 实体的证据。

## 七、Scenario 识别

### 7.1 进入条件

当用户输入、任务背景或事实源状态满足以下条件之一时，AI 应识别为多角色思考 Scenario：

1. 出现"多角色""不同角色""不同视角""从多个专业角度""各自说一遍"等明确触发语；
2. 当前变更影响两个以上规范、对象、行动、工具、项目模块或协作机制；
3. 当前任务涉及 Rules、Skill、Agent、MCP、工具、事实源边界或 Human Gate 的职责划分；
4. 当前判断存在高影响风险，且需要安全、治理、验证或架构视角共同审查；
5. 用户要求先分析影响、风险、分歧或执行顺序，再决定是否修改；
6. AI 对执行路径不确定，并判断单一视角不足以安全推进。

### 7.2 优先级

多角色思考与其他行动同时匹配时，按以下原则处理：

1. 若用户明确要求多角色分析，优先进入多角色思考；
2. 若已有明确 Task 且只需执行，优先进入 Task 执行行动；
3. 若正在创建或更新对象实例，优先遵守对应对象创建或对象状态更新行动；
4. 若涉及规范、规则、Skill、Agent 或工具变更，先进行多角色思考或治理审查，再执行写入；
5. 若触发 Human Gate，先暂停并请求确认。

### 7.3 降级条件

以下情况应降级为主上下文直接分析或询问用户：

1. 主题不明确，无法选择角色；
2. 没有足够事实源支持分析；
3. 用户只需要简短回答；
4. 分析可能引入无关复杂度；
5. 多角色子 Agent 模式不适用，但轻量模式足以完成。

## 八、执行流程

### 8.1 选择分析模式

多角色思考分为两种模式：

| 模式 | 说明 | 行为 |
|---|---|---|---|
| 主上下文轻量模式 | 无需独立上下文，AI 在主上下文中依次分析各角色 | AI 在主上下文中按角色分别分析并汇总 |
| 多角色子 Agent 模式 | 需要独立上下文、结论隔离或并行委派 | 主控为每个角色构造独立参数，启动可调用 Agent 容器的多个实例，各实例输出回到主控后统一汇总 |

主控识别到多角色思考场景时，除非对话中已明确要求使用某种模式，否则都必须先说明两种模式的差异，通过 AskUserQuestion 机制向用户呈现选项供其选择启动的模式。两种模式都由主控负责最终汇总。

### 8.2 识别变更类型

AI 应先判断分析主题属于哪些类型：

1. 需求 / 产品变更；
2. UI / 前端体验变更；
3. 服务端 / API / 数据变更；
4. 数据 / 模型相关变更；
5. 安全 / 合规变更；
6. 规则 / 规范 / 文档变更；
7. Skill / Agent / AI 协作变更；
8. MCP / 工具链 / 自动化变更；
9. 发布 / 部署 / 关闭变更；
10. 审计 / 复盘 / 流程改进；
11. 通用架构 / 大型重构。

### 8.3 角色定义

角色定义是多角色思考的稳定规范内容，不创建 Role 生产对象，不创建"角色应用场景"生产对象。角色定义应作为 AI、Rules、Agent、Tools 和 Web 可共同引用的结构化契约使用，不应在 Skill、Agent Prompt、工具缓存或 Web 状态中复制维护第二事实源。

本文只定义角色定义的事实源边界和使用原则。角色字段契约、默认角色集合、角色选择输入输出、角色调用参数、角色分析结果和多角色报告结构由 `specs/51.06-Contract.md` 承接。

角色定义使用应遵循以下原则：

1. 角色定义属于 specs 稳定规范，不属于 `ldvh-base/` 生产对象实例；
2. 默认角色集合由 51.06 统一维护，主控按主题和变更类型选择角色；
3. 不为每个角色创建自定义 Agent；角色内容作为运行时参数注入主上下文或可调用 Agent 容器；
4. 不创建独立"角色应用场景"对象；不同用途下的输出结构由 51.06 的契约字段表达。

角色定义的事实源边界、角色独立性原则和 Tools / Web 消费约束详见 `specs/51.06-Contract.md` §二。

### 8.4 选择角色

角色选择规则由 `specs/51.06-Contract.md` §六统一定义，包括选择优先级、必选角色触发条件和角色数精简规则。主控按 41.13 §五 RoleSelectionInput 构造输入，按 §六 RoleSelectionOutput 输出选择结果。

主控应在启动子 Agent 前输出 RoleSelectionOutput，让用户确认角色选择是否合理。

### 8.5 分角色分析

每个角色至少输出：

1. 适用性：相关 / 无关；
2. 影响范围：具体模块、文件、接口、对象、行动或流程；
3. 分析结论：该角色视角下的判断；
4. 风险：高 / 中 / 低，并说明原因；
5. 建议动作：需要执行、暂停、确认、回写或补充的具体事项。

### 8.6 汇总对比

AI 应汇总各角色分析，至少包含：

1. 一致结论；
2. 分歧点；
3. 风险汇总；
4. 建议执行顺序；
5. 需要同步的文档、对象、规则、Skill、Agent 或工具；
6. 事实源回写建议；
7. Human Gate 判断。

### 8.7 输出格式

多角色思考输出建议采用以下结构：

```markdown
# 多角色思考报告

## 适用性判断
- 是否进入多角色思考：是 / 否
- 分析模式：主上下文轻量模式 / 多角色子 Agent 模式
- 涉及角色：{角色列表}

## 变更或问题概述
- 主题：{一句话描述}
- 影响范围：{模块 / 文件 / 对象 / 行动 / 项目}

## 各角色分析

### {角色名}
- 适用性：相关 / 无关
- 影响范围：{描述}
- 分析结论：{结论}
- 风险：高 / 中 / 低 — {描述}
- 建议动作：{列表}

## 角色间一致与分歧
- 一致结论：{列表}
- 分歧点：{列表}

## 风险汇总
- 高风险：{列表}
- 中风险：{列表}
- 低风险：{列表}

## 建议执行顺序
1. {第一步}
2. {第二步}

## 事实源回写建议
- 应写回：{文件或对象}
- 不应写回：{过程信息}

## Human Gate
- 是否触发：是 / 否
- 触发原因：{原因}
- 建议确认事项：{列表}
```

## 九、Gate 触发条件

### 9.1 条件 Gate

以下情况触发条件 Gate：

1. 缺少分析主题或输入材料；
2. 需要读取的事实源不存在或无法确认；
3. 角色选择依据不足；
4. 角色参数构造依据不足，无法为多角色子 Agent 模式提供清晰角色边界；
5. 输出需要回写但目标事实源不明确。

条件 Gate 未满足时，AI 应降级、询问用户或暂停，不得继续执行高影响分析或写入。

### 9.2 Human Gate

Human Gate 触发条件统一由 §十四 定义。本节不重复列举 Human Gate 条件，避免与 §十四 并行维护导致不一致。

## 十、Rules 和 Agent 调度

> 本节对应 14 §4.2 第 8 项"Skill 和 Agent 调度"。因多角色思考不创建 LDVH 版 Skill（见 §10.1），改为 Rules 触发 + Agent 调度。

### 10.1 Rules 触发

多角色思考不需要创建 LDVH 版 Skill。进入多角色思考的触发判断应由 Rules 承接，执行流程由本文承接。

Rules 只做入口提醒：当用户要求多角色、多视角、跨模块影响评估、复杂变更风险审查，或 AI 判断单一主上下文可能遗漏风险时，应进入本文定义的多角色思考行动模型。

Rules 不得复制本文的完整 Scenario、角色定义、执行流程、输出格式或 Human Gate 条款。需要执行时，AI 应读取本文并按本文执行。

### 10.2 多角色子 Agent 模式

多角色子 Agent 模式用于需要独立上下文、结论隔离、并行委派、不同权限边界或大量事实源读取的多角色分析。

多角色子 Agent 模式遵循以下规则：

1. 主控根据本文角色定义和当前主题选择角色；
2. 主控为每个角色构造独立调用参数，参数应包含角色名、关注点、触发背景、输入事实源、输出格式和边界要求；
3. 主控启动可调用 Agent 容器的一个或多个实例，每个实例只承担被注入的角色视角；
4. 同一可调用 Agent 容器可以被并行启动多个实例，每个实例使用不同角色参数；
5. 多角色子 Agent 输出必须回到主控汇总，不得直接成为事实源；
6. 子 Agent 发现 Human Gate 场景时必须标注，不得自行执行高影响写入；
7. 不为每个角色创建自定义 Agent；角色定义来自本文，作为运行时参数注入；
8. 多角色子 Agent 模式通过 Task 工具系统子 Agent + 角色参数注入实现，不依赖 `.trae/agents/` 自定义 Agent 文件；角色-子 Agent 类型映射和参数注入规则见 `specs/51.03-Agent.md`；
9. 需要创建、导入、启用、修改或删除 Agent 时，必须按 11.03 触发 Human Gate。

可调用 Agent 容器是指当前主控能够通过工具接口实际启动的 Agent 类型。本文不维护可调用 Agent 容器清单，不在稳定规范中核验特定 Agent 可用状态，也不把某个环境中的可用 Agent 列表写成稳定规则。

## 十一、工具协作适配

多角色思考可使用工具辅助以下工作：

1. 搜索和读取相关事实源；
2. 生成或校验 Context 包；
3. 检查 Markdown 链接、编号、引用和 YAML 语法；
4. 聚合变更影响文件；
5. 准备受控写入候选内容；
6. 展示分歧、风险和 Human Gate 待确认项。

工具不得直接决定角色结论，不得直接调用 AI、Skill 或 Agent，不得将工具缓存或派生视图作为最终事实源。

MCP Server 在多角色思考中的定位：MCP 结果可作为输入材料，但不得直接决定角色结论；提供 AI 推理能力的 MCP Server 返回结果应与工具缓存同等对待，不作为事实源。

---

## 十二、事实源回写要求

多角色思考完成后，应按以下规则判断是否回写：

| 输出类型 | 回写位置 |
|---|---|
| 仅服务当前对话的分析 | 不回写，保留在当前上下文 |
| 需要执行的明确动作 | 创建或更新 Task，位置由 Task 对象规范定义 |
| 有保留价值但暂不任务化的信息 | 创建或更新 Memo，位置由 Memo 对象规范定义 |
| 已确认且长期有效的决策 | 创建或更新 ADR，位置由 ADR 对象规范定义 |
| 已识别的不确定因素 | 创建或更新 Risk，位置由 Risk 对象规范定义 |
| 验证结果或关闭证据 | 创建或更新 Evidence，位置由 Evidence 对象规范定义 |
| 对事实源产生影响的实际修改 | 创建 Change YAML 到 `ldvh-base/changes/` |
| 管辖项目报告或审计结果 | 写入 docs/ 对应报告 |
| 规范或规则正文 | 写入 specs/ 或 `.trae/rules/`，并评估 Human Gate |

未写入权威事实源前，多角色思考报告不能被后续 AI 当作稳定事实引用。

---

## 十三、证据留存要求

多角色思考的证据至少包括：

1. 分析主题和输入来源；
2. 读取的关键事实源；
3. 选择的分析模式及原因；
4. 多角色子 Agent 模式的调用参数、角色边界和隔离说明；
5. 选用角色及选择理由；
6. 各角色结论、风险和建议动作；
7. 汇总结论、分歧和 Human Gate 判断；
8. 若发生写入，记录写入文件、写入原因、验证结果和 Change ID。

---

## 十四、Human Gate

### 14.1 必须暂停确认的情况

以下情况必须暂停并请求人类确认：

1. 将多角色思考结论升级为规范、规则、ADR 或长期行动边界；
2. 创建、导入、启用、修改或删除 Agent；
3. 允许多角色子 Agent 模式访问更高权限或写入文件；
4. 依据多角色思考结论修改事实源权威位置；
5. 依据多角色思考结论执行跨项目、高风险或不可自动确认的变更；
6. 创建 LDVH 正式 Skill、Agent 或附件型实践子文档。

### 14.2 用户确认后的处理

用户确认后，AI 应：

1. 明确记录确认事项；
2. 按对应规范执行写入或创建；
3. 写入后补充 Change 记录；
4. 执行可用检查；
5. 汇报哪些内容已成为稳定事实，哪些仍是建议。

发生冲突时，以本文和上位基础规范为准，附件型实践子文档应修正为引用或适配本文规则。

## 十六、落地前决策

落地前决策用于判断多角色思考行动模型在具体项目中需要落地哪些实践子项。落地前决策发生在实际初始化之前，不等同于落地初始化，也不表示对应 Rules、Agent、Tools、Web 或 Contract 实践已经存在。

落地前决策应确认以下事项：

1. 是否需要在 L0、L1 或 L2 Rules 中增加多角色思考入口摘要；
2. 是否需要启用多角色子 Agent 模式，以及是否涉及创建、导入、启用或修改 Agent；
3. 是否需要 Tools 校验能力，例如报告结构校验、角色字段校验、角色参数校验和回写候选检查；
4. 是否需要使用或扩展 `51.06-Contract.md` 中的结构化契约；
5. 哪些事项立即落地，哪些事项暂缓，暂缓原因和后续评估方式是什么；
6. 哪些事项触发 Human Gate，是否已获得确认。

落地前决策的输出是决策清单，不是初始化产物。未完成落地前决策前，不应声称已经完成落地初始化。

## 十七、价值与要素审查

落地前决策完成后、实际落地初始化开始前，必须基于 `specs/00-LD-Vibe-Harness理念与纲要.md` 执行价值与要素审查。

价值与要素审查至少应覆盖：

1. 拟落地的 Rules 入口摘要、Agent 调度、Tools 校验和契约子文档是否有助于 V1 稳定理解、V2 受控执行、V3 门禁识别、V4 证据沉淀、V5 事实回写、V6 人类确认质量或 V7 持续改进中的一项或多项；
2. 各实践子项是否明确归属于介质、Trae Solo 环境机制、Harness 工具、Harness 生产对象或 Harness 行动模型之一，且未混淆五类构成要素边界；
3. 多角色思考行动模型是否仍以 AI 执行者为第一服务对象，帮助 AI 识别场景、读取事实源、选择工具 / Skill / Agent、触发 Human Gate 和回写事实；
4. 是否避免把 Agent 输出、工具缓存、Web 状态或 Skill 输出当作最终事实源；
5. 是否避免创建无必要的 Rules、Skill、Agent、工具或对象，导致体系膨胀但不提升可控性；
6. 是否明确需要 Human Gate 的事项，并在确认后再进入落地初始化。

审查不通过时，应回到落地前决策修正方案、标记暂缓或停止落地；不得直接进入初始化。

## 十八、落地初始化与审计边界

> 本节合并覆盖 14 §4.2 第 16 项"落地初始化"和第 17 项"落地审计"。

落地初始化应在落地前决策完成后执行。落地初始化关注已经明确要建立的内容和步骤，包括写入 Rules 摘要、创建或更新附件型实践子文档、启用必要工具校验、记录 Change 和验证实际产物。

落地初始化的具体步骤不在本文展开，应由对应附件型实践子文档承接：

1. Rules 入口摘要由 `51.01-Rules.md` 承接；
2. Skill 不创建理由由 `51.02-Skill.md` 承接；
3. 多角色子 Agent 模式由 `51.03-Agent.md` 承接；
4. 工具校验和结构化检查由 `51.04-Tools.md` 承接；
5. Web 不创建理由由 `51.05-Web.md` 承接；
6. 角色定义、角色选择、Agent 调用参数、多角色报告和回写建议契约由 `51.06-Contract.md` 承接。

### 18.1 落地审计

落地审计应基于已经完成或声称完成的落地项进行，不应审计尚未决策或已标记暂缓的事项是否实现。对于暂缓项，审计只检查是否有暂缓原因、前提条件和重新评估方式。

落地审计检查清单：

| 检查项 | 通过条件 |
|---|---|
| Rules 入口摘要是否仍存在且内容一致 | L0/L1/L2 中对应入口摘要与 51.01 定义一致 |
| 附件型实践子文档是否与主文档对齐 | 51.01-51.06 内容未与 51 主文档产生矛盾 |
| Change 记录是否覆盖所有落地项 | 每个落地项在 `ldvh-base/changes/` 中有对应 Change YAML |
| Human Gate 是否被绕过 | 所有触发 Human Gate 的落地项均有用户确认记录 |
| active-prep 子文档状态是否需要更新 | 51.04 的基础设施是否已建立，是否应升级为 active |
| 落地项是否持续有效 | 已落地的 Rules 入口、Agent 调度、契约使用在实际执行中可正常工作 |

落地初始化和落地审计都不是一次多角色思考执行的合规检查。一次执行是否合规，应按第十九章检查。

## 十九、合规检查

检查一次多角色思考执行是否合规时，应确认：

| # | 检查项 | 通过条件 |
|---|---|---|
| 1 | 是否说明进入多角色思考的触发原因 | 输出中包含明确的触发原因描述，且可追溯到 §七 Scenario 识别条件之一 |
| 2 | 是否声明分析模式 | 输出中明确声明"主上下文轻量模式"或"多角色子 Agent 模式" |
| 3 | 是否说明选择该模式的原因 | 轻量模式和子 Agent 模式均需说明选择原因；子 Agent 模式还需说明角色参数和隔离方式 |
| 4 | 是否列出读取的关键事实源 | 输出中列出本次分析读取的 specs、ldvh-base、docs 或代码文件 |
| 5 | 是否按角色输出适用性、影响范围、结论、风险和建议动作 | 每个角色输出包含 51.06 RoleAnalysisResult 契约的必填字段 |
| 6 | 是否汇总一致结论和分歧点 | 汇总中明确区分一致结论和分歧点，不混淆 |
| 7 | 是否给出风险等级和建议执行顺序 | 风险按高/中/低分级，执行顺序有明确步骤编号 |
| 8 | 是否判断事实源回写目标 | 按 §十二回写要求判断每类输出的回写位置 |
| 9 | 是否判断 Human Gate | 按 §十四判断是否触发 Human Gate，触发时暂停请求确认 |
| 10 | 是否避免把过程分析、Agent 输出、工具缓存或 Web 状态直接作为稳定事实引用 | 输出中明确标注"本分析为过程分析，未写入权威事实源前不得作为稳定事实引用" |
| 11 | 如发生写入，是否记录写入文件、写入原因、验证结果和 Change ID | 写入后创建 Change YAML，记录写入文件、原因、验证结果和 Change ID |

检查多角色思考行动模型文档是否合规时，应确认本文覆盖 14 §4.2 定义的行动模型标准组成；缺项应说明不适用原因或进入待补齐事项。
