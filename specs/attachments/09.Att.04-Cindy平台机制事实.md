## 1. 平台机制事实

| 机制 | Cindy 实际承载 |
|---|---|
| 协作 Worker | Orca Worker；session 级、持久、UI 可见，与一次性 subagent 不是同一执行渠道 |
| Worker agent | 当前宿主支持的 `codex`、`claude-code` 或 `pi`；实际可用范围以当次 Orca 目录为准 |
| Worker 模型 | 按 agent 分组的当次 Orca 可用模型目录；不在本卡写死模型名或跨 agent 推导兼容性 |
| Worker 建立 | 当前 session 需处于 Orca team；单个 Worker 与多个 Worker 分别使用平台当次提供的单建立与批量建立能力 |
| Worker 权限 | Orca team 的 Worker 默认采用 `bypassPermissions`（Full access／完全访问）；该选择是 Worker 建立偏好，不改变 Lead 权限 |
| Worker 消息 | 已有 Worker 可继续接收任务，忙时消息可排队；Worker 结果由平台异步回送 Lead，不以轮询作为正常等待方式 |

## 2. 执行注意事项

1. **创建前模型选择：** 确认 Orca Worker 能力实际可用后，在创建 WorkCase 前向 Human 发出一次自由文本询问：“当前环境支持协作模式，本次独立复核使用什么模型？”默认不展开 Orca 模型目录；Human 可直接指定模型，也可明确委托 AI 选择。
2. **按需取得目录：** 只有 Human 主动要求查看可用模型，或所填模型无法唯一解析、与 Orca Worker 不兼容或当前不可用时，才读取当次 Orca 模型目录并给出必要说明或候选。模型必须映射到当次目录中的精确 agent 与 model 路由；只在无法唯一、安全映射时追问最小澄清。
3. **Gate 1 冻结与执行期复用：** 选定结果写入 `execution_authorization.reviewer_policy`并随完整授权包提交 Gate 1 冻结。Gate 1 后的新建、恢复、压缩后继续或接管执行上下文只重检当前权限、能力与冻结 policy 的有效性，不因每次创建、复用或分派 Orca Worker 重复询问模型。
4. **权限默认：** 开启或更新 Orca team 时显式采用 `bypassPermissions`，使 UI 与后续 Worker 建立沿用完全访问偏好，不在 Worker 执行中逐次申请权限。宿主要求 Human 确认升级时，取消或超时不得记为完全访问已生效。
5. **实际记录：** `actual_agent` / `actual_model` 按 Orca Worker 的实际路由据实记录，并与 Gate 1 冻结的 reviewer policy 一致。
6. **规则语义回指：** Worker 使用、复核、降级、轮次与 WorkCase 收敛的规则语义一律见 21 §4.5、31 §5.2.1 与 34 §5，本文不复述。

## 3. Orca Worker 对 WorkCase 控制点的承接映射

本节只把 LDVH 已定义的控制点映射为 Cindy 平台动作，不定义控制点的进入条件、完成条件、阶段转换、复核轮次、降级顺序或 Human Gate。是否应执行某个控制点、Worker 输出是否合格、WorkCase 下一步是什么，均以所列权威来源和 Helper 对当前对象形成的结果为准。

| LDVH 控制点 | Cindy / Orca 承接动作 | 单一事实来源 |
|---|---|---|
| 创建前 Reviewer 能力预检与模型选择 | Lead 先读取当前 Orca workspace/team 与已有 Worker 的可观察状态；确认协作 Worker 实际可用后，按第 2 节完成一次模型选择和精确 agent/model 映射。已有匹配 Worker 可以复用；需要新建时，必须由当次 Human 指令明确覆盖创建只读 Reviewer，不能从“创建/继续 WC”自行推导。 | 31 §5.2.1；可用性与方法边界见 21 §4.5 |
| 创建方案复核 | Lead 把当前被审计划版本交给匹配的 Orca Worker。分派消息携带 `Intent`、`Decisions`、`Boundaries`、`Task`，并明确只读、被审版本及预期返回内容；Worker 不修改文件、事实对象或状态。 | 21 §4.5、§6；31 §5 |
| Gate 1 后恢复或接管 | Lead 精确读取当前 WorkCase、投影与冻结 reviewer policy，再读取当前 Orca workspace 信息核对既有 Worker 和实际能力；平台观察只供选择执行通道，不替代 WorkCase 当前事实或 Helper 投影。 | 34 §5.1；对象与投影语义见 21 |
| 执行期需要 collaboration Worker review | Lead 依据冻结 policy 选择匹配的现有 Worker；确需建立新 Worker 时只消费已经明确覆盖该建立动作的 Human 指令。单个已解析目标用单次建立或发送，多目标全部解析后使用批量建立/并行发送；每个任务仍携带独立的 `Intent`、`Decisions`、`Boundaries`、`Task` 与被审版本。 | 21 §4.5；34 §5.1、§5.2 |
| Worker 已成功受理任务 | Cindy 以实际 dispatch 回执判断任务是否已调度。成功调度后 Lead 结束当前回合，不轮询、不保持连接；由 Orca 异步完成并把报告回送 Lead。没有成功调度回执时如实报告失败或未调度，不等待不存在的结果。 | Cindy 当次平台机制；WC 是否继续或退出仍见 34 §5.2、§5.4 |
| 收到 Worker 报告 | Lead 核对报告的实际执行渠道、agent/model、被审版本、只读边界和结论，再由 Lead 按 Helper 契约完成需要的 WorkCase 写回、重新读取、投影与后续控制；Worker 报告本身不写入或推进 WorkCase。 | 21 §4.5、§7；34 §5.2、§5.3 |
| Worker 返回后的继续与 Human 交还 | Lead 继续消费当前 WorkCase 的 Controller-owned 控制链；是否允许交还 Human 只读取当前 Helper handoff 结果和 21/34 的权威规则。Orca 的建立、分派、返回或单项完成不由本卡解释为新的 Gate 或合法退出。 | 21 §9.3.1、§11；34 §5.2、§5.4、§7 |

### 3.1 单一事实保护

1. 本映射不保存 WorkCase 实例状态、当前 Worker 状态、模型目录、review 结论、dispatch receipt 或下一控制步骤；这些内容分别来自当前事实对象、Helper 结果和 Orca 当次回执。
2. 本映射与 21、31、34 或 Helper 当前结果不一致时，不以本卡解释或修补规则；停止使用冲突行，回到对应权威来源重新读取并更新平台映射。
3. Orca 平台机制变化只更新 Cindy 动作一列及其观察依据，不把平台变化反写成 WorkCase 生命周期规则。
