## 1. 价值判断

本文的价值，是让 AI 在当前工作中直接使用真实存在的最新内容，同时能区分哪些内容已经位于事实源，哪些是当次观察、聊天、工具输出、缓存、索引或其它派生信息，以及这些信息如何回到来源和后续历史。这样可以避免 AI 因只读取 `HEAD` 而忽略进行中的事实内容和未提交事实，也可以避免把聊天、工具成功、缓存、索引或 Git commit 误当成事实正确、验证通过或工作完成。

本文主要服务以下 V1-V8 价值：

1. V1 快速定位：定位当前事实所在文件及其来源；
2. V2 充分理解：把当前内容、来源、形成过程和派生关系联系起来；
3. V3 边界识别：区分规则源、事实源、当次观察、各类输出和派生信息；
4. V5 据实判断：让判断不超出当前事实和当次可观察依据；
5. V6 工作接续：使进行中而非只有已完成、已提交的工作能够被后续 AI 恢复；
6. V8 持续积累：把确有长期价值的信息按明确位置纳入事实源，并保留变化历史。

## 2. 规范依据

本文直接依据 `ldvh-root` 对事实源作为信息锚点与判断依据、事实源边界和事实模型职责的定义，细化以下已确定原则：

1. 事实源以管辖项目实际 Git Working Tree 中符合适用来源规则的当前文件为唯一有效承载形态；
2. 事实源必须有组织、可消费；
3. 聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图不能自行替代事实源；
4. 稳定事实、状态、证据、决策和经验可以由事实模型在事实源边界内组织。

本文同时依据 `specification-model-foundation` 区分规则源与其它信息，并沿用其当前工作树边界：当前内容以 Working Tree 中的实际文件为默认读取视图，Index 和 `HEAD` 不得覆盖当前内容或成为规则生效开关。

本文依据 `work-object-governance-scope` 取得工作对象实际所在 Git worktree 与配置登记路径的边界。该依据只用于确定当前事实应当绑定哪一个实际 worktree，不使管辖项目配置成为事实源，也不使管辖判定替代事实内容和来源规则。

本文不得重新定义 00 的事实源，也不得把信息分类、Git 状态、索引、缓存、Code 输出或本文自身变成第二事实源。[W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 对 provenance 的定义可用于理解“来源及形成过程”与“质量、可靠性或可信度判断”之间的区别，但本文不采用完整 W3C PROV 数据模型，也不据此新增实体、活动或参与者 Schema。

## 3. 职责边界

本文负责：

1. 稳定事实、当次可观察信息、聊天、AI 推理、工具输出、缓存和派生信息之间的边界；
2. 事实源与某项信息原始出处之间的区别；
3. 来源回指和信息溯源的基本要求；
4. 信息纳入或更新事实源时的共同边界；
5. Working Tree、Index、`HEAD` 和 Git history 在当前读取与历史溯源中的不同作用；
6. Git 记录能够支持和不能支持的结论；
7. 全部受 LDVH 管辖项目的新 commit 在证据粒度、完整 message、验证分层、非合规处置和历史比较上的共同契约；
8. 面向 AI 的 Git commit 候选机械预检公开操作及其领域输入、结果和失效边界。

本文不负责：

1. 重新定义 01 的规则源资格、规范身份或规范关系；
2. 定义具体事实类型、字段、状态闭集、关系、Schema 或目录；
3. 判断证据是否充分，或者定义完成、通过、可用、接入和关闭等声明；
4. 定义 Git 暂存算法、用户既有 Index 隔离、commit 创建步骤、push、remote/ref 写入或 Git Hook 安装流程；
5. 定义 Helper 共同请求与响应字段、Code 模块、算法、诊断码或缓存实现；
6. 定义 Web 页面、API 或交互方式。

上述内容分别由以下位置承担：

1. 规范身份和当前规则源资格由规范模型承担；
2. 关于结论不得超出事实、验证结果或当次可观察依据所支持范围的上位边界由 00 承担；
3. 各领域的成立条件、可接受依据和可证明范围由相应来源规范承担；
4. 事实对象结构由事实模型承担，可复用行动结构由行动模板承担；
5. Helper 的公开服务请求与结果语义由 Helper 服务契约承担；
6. Code 实现规划、内部模块、算法、诊断、缓存和测试工程由 Code 工程实践及 Code/tests 实现承担；
7. 环境连接、安装、真实触发和回滚由环境接入职责承担；
8. Web 的读取、呈现和受控交互由 Web 相关职责承担；
9. Human 已授权后的本地 commit 候选形成、Index 保护、创建和写后回读由行动模板承担；项目特有测试、branch 和其它附加政策由项目正式来源承担。

本文只定义这些职责共同使用的事实源和溯源边界。

## 4. 适用范围

本文适用于管辖项目中以下事项：

1. AI、Helper、Code 或 Web 读取项目当前事实；
2. Human 指令、文件观察、外部资料、命令、测试、Code、评审或其它工具产生当前信息；
3. 当前信息需要跨行动、会话、执行者或阶段继续保留；
4. 事实被新建、更新、推进状态、关闭、更正、移动或删除；
5. 缓存、索引、摘要、聚合或视图从规则源或事实源派生；
6. 需要说明当前 Working Tree 内容与 Index、`HEAD` 或 Git history 的关系；
7. 在单一受管辖项目的单一实际 Git worktree 中形成、重写、审查、验证或呈现新 commit 及其完整 message。

本文不要求与项目事实无关的一般知识问答或普通求解先建立事实源记录，也不要求聊天、命令输出、测试结果、诊断、临时报告、缓存、索引、摘要或 Web 展示都长期保存。

## 5. 核心术语与边界

### 5.1 稳定事实（Stable Fact）

稳定事实是在管辖项目中需要跨行动、会话、执行者或阶段继续保留，并且已经位于符合 00 事实源边界的当前文件位置、满足适用来源规则、能够被后续消费的事实内容。需要对象化、状态化或证据化管理的内容，还必须满足适用事实模型；不需要上述管理的稳定内容，不因缺少事实模型而自动失去稳定事实资格。

“稳定”表示它具有明确、可持续读取的当前承载位置，不表示内容已经完成、关闭、不可修改、已经提交或天然可信。内容处于来源规则允许的进行中状态时，只要其当前文件与状态有效，同样可以承载稳定事实并支持后续接续。稳定事实仍必须按来源、状态和适用验证要求判断，不能仅凭名称取得正确性或可信度。

未提交不排除稳定事实。当前文件位于管辖项目实际 Git worktree，并满足适用来源规则与验证要求时，其当前内容可以作为稳定事实被读取；单个文件的 Git 状态不决定这一资格。需要事实模型管理的内容还必须满足相应事实模型。commit 实际创建后，只为其中记录的内容提供 Git 历史依据。

### 5.2 当次产生与派生的信息

聊天与 AI 推理、命令和测试输出、Code 诊断、评审结果、临时报告、缓存、索引、摘要、聚合结果和 Web 展示，都可能在当前行动、观察、计算、验证、展示或协作过程中产生。它们的形成方式、生命周期和消费边界不同，本文不把它们合并定义为一个正式信息类型。

这些信息可以在各自来源和实际范围内支持当次判断，也可以成为后续写入或更新事实源的输入，但不会因为重要、格式结构化、工具成功或被重复显示而自行成为稳定事实。是否需要长期保留，必须回到适用来源规则和实际接续价值判断；需要对象化、状态化或证据化管理时，还必须回到相应事实模型。

### 5.3 来源回指（Source Reference）与信息溯源（Information Traceability）

来源回指是能够以当前判断所需精度重新定位某项信息的原始出处、当次观察、输入文件、命令或其它形成依据的可复核引用。具体表示可以是文件与对象定位、规范 key 与章节、外部来源地址、命令与输入范围、Git ref 或由相应来源规范定义的其它结构。

一个位置、URL、分支名、Git ref 或命令名称不一定单独构成充分的来源回指。来源会变化且当前结论依赖特定版本或观察时点时，回指必须按需要同时保留仓库或系统身份、路径或对象、commit 或版本、观察时间、命令输入范围和执行上下文中的必要部分；多个引用可以组合满足重新定位要求。本文不要求所有来源使用同一字段闭集，但不得用无法回到实际出处的模糊说明冒充来源回指。

信息溯源是从当前信息回到其来源、关键形成或转换过程以及当前承载位置的能力。它帮助 AI 判断信息从哪里来、经过什么变化、现在在哪里，但不单独证明内容正确、证据充分、Human 已确认或工作完成。

来源回指不要求所有信息采用同一种字段，也不要求本文预先建立全局 `source_refs` Schema。具体事实对象、Helper 响应和 Code 输出需要哪些字段，由承担相应职责的规范定义。

### 5.4 写入或更新事实源

把确需长期保留的当前信息写入或更新到适用来源规则定义的事实源位置时，必须按适用规则保留来源、当前状态和必要关系，并随后回读实际 Working Tree 内容。需要对象化、状态化或证据化管理的内容，还必须写入相应事实模型允许的位置和结构。本文将这些要求作为一组共同规则，不把该动作提前建立为独立正式术语。

写入动作本身不自动证明事实成立。只有目标位置、适用来源规则、来源和验证要求成立，并且需要事实模型管理时相应对象类型、字段、状态和关系也成立，写入后的当前内容才能按相应范围作为稳定事实消费；是否已经 commit 不属于这一成立条件。

## 6. 信息作用与消费边界

同一段内容可以随着处理发生作用变化，但作用变化必须有明确依据和承载位置，不能由文件名、工具类型或显示位置自动推断。

信息作用与消费边界表见 [03.Att.01-来源参考枚举闭集.md](attachments/03.Att.01-来源参考枚举闭集.md)。

外部文档、网页、API 或第三方仓库可以是某项信息的来源，也可以在其自身领域具有权威性；但它们不会因此成为 00 定义的 LDVH 项目事实源。需要跨会话消费的项目结论必须按适用来源规则写入项目事实源并保留适当来源回指；需要对象化、状态化或证据化管理时，还必须符合相应事实模型。

## 7. 当前工作树读取规则

1. 判断项目当前事实时，AI、Helper 和 Code 默认读取当前 Working Tree 中实际存在的文件内容，不以 Index、`HEAD`、远端分支或缓存替代当前文件；
2. 当工作对象或 Human 目标明确指定 commit、Git ref、历史时间点或当前版本与历史版本的比较时，可以读取对应历史对象；结果必须保留版本定位并明确标记为历史内容或比较结果，不得将其冒充为项目当前事实；
3. 当前文件只要满足事实源边界和适用来源规则即可承载当前事实；dirty、untracked、ignored、staged 或 committed 只描述 Git 状态，不决定当前事实资格；
4. 当前文件中的进行中状态必须按适用来源规则和需要时事实模型消费，不能因为尚未完成或提交而回退读取旧状态；
5. 当前工作树已经删除、移动或重命名的文件，不得因旧路径仍存在于 `HEAD` 而继续作为当前事实读取；相应变化是否合法由来源规则、需要时适用的事实模型和当次验证判断，但显式历史读取仍可按第 2 项进行；
6. Working Tree 与 Index 或 `HEAD` 不同时，判断当前事实必须使用当前内容，同时把差异作为溯源上下文；显式历史读取或版本比较按第 2 项保持各版本身份；
7. 当前文件无法解析、违反适用 Schema、状态或关系规则时，必须报告当前不一致，不能静默使用旧提交掩盖问题；写入与 AI 精确读取场景按适用来源规则标记、拒绝或分流，Web 阅读场景的报告落实为逐字段、逐结构的问题呈现（00 §8.3、08 §5.3），不得仅因此将整个可解析对象呈现为读取失败；
8. 未提交状态本身不造成全局停止。只有具体来源规则要求提交、当前内容不成立、事实冲突无法判断，或者相应行动需要历史锚点时，才暂停受影响范围或进入 Human Gate。

工作对象明确位于某个 Git worktree 时，当前事实的读取、写入、回读和验证必须绑定该对象实际所在的 worktree。管辖项目配置中的登记路径、Helper 或 Code 所在 worktree，以及共享同一 Git common-dir 的其它 worktree 都不得替代目标 worktree；同一管辖项目的多个 worktree 中存在的当前事实和进行中变化不得静默合并。

缓存、索引和派生视图检测到 Working Tree 变化后应重新生成或明确标记过期；它们不得反向要求 AI 忽略更新后的当前文件。

## 8. 稳定事实形成与事实源更新规则

当前信息进入或更新事实源时，写入行动必须先按 00 §4 确认 Human 当前指令已经授权，且适用于该行动的全部来源规则许可条件已经成立；行动获准后，还必须依次确认：

1. 该信息确实需要跨行动、会话、执行者或阶段继续保留，而不是只服务当前推理；
2. 已有适用来源规则定义相应内容的承载位置、边界和消费方式；内容需要对象化、状态化或证据化管理时，已有事实模型定义相应对象、结构和当前状态要求；
3. 目标文件位于对应管辖项目的实际 Git worktree 内，并处于适用来源规则及需要时事实模型允许的位置；单个文件的 Git 状态不构成写入或更新资格条件；
4. 需要保留的来源回指、形成依据和关系按适用来源规则及需要时事实模型写入或关联，未把推测写成已证实事实；
5. 当前 Working Tree 内容满足适用来源规则，以及需要时相应对象、字段、状态、关系和验证要求；
6. 写入后已经回读实际目标文件，确认当前内容而不是只依赖写入命令成功输出。

本文不授权任何具体事实类型。历史实例、名称、目录或 Schema 不自动取得当前事实类型身份；没有当前有效具体事实类型定义的对象只能保持候选，不得由本文直接创建为正式事实对象。

事实源写入或更新并完成回读后，当前内容可以在其实际成立范围内立即支持后续工作。尚未提交时，应在需要判断历史状态、交还提交准备度或比较版本时如实说明；不得把“尚未提交”改写成“事实不存在”，也不得把“当前有效”改写成“已经形成 Git 历史记录”。

## 9. Git 溯源边界

[Git 官方对象模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)说明了 Working Tree 内容进入 tree 与 commit 历史时的基本关系；[git status](https://git-scm.com/docs/git-status)区分 Index 与 `HEAD`、Working Tree 与 Index，以及尚未跟踪且未被忽略的文件；[gitignore](https://git-scm.com/docs/gitignore)明确已被跟踪的文件不受 ignore 规则影响；[gitrevisions](https://git-scm.com/docs/gitrevisions)定义了 revision 与路径对历史对象的定位方式。本文据此区分当前、待提交和历史内容，但不把 Git 技术模型提升为 LDVH 的事实语义来源。

Git 为当前内容和历史变化提供三个不同观察层次：

| Git 层次 | 主要作用 | 不得覆盖的内容 |
|---|---|---|
| Working Tree | 当前实际文件和进行中变化，是 AI 与 Code 的默认读取视图 | 不被 Index 或 `HEAD` 中旧内容覆盖 |
| Index | 下一次 commit 的候选快照，用于提交范围和提交前验证 | 不代表全部当前变化，也不决定当前事实或规则是否生效 |
| 可解析的 `HEAD` 与 Git history | 已提交快照、父提交关系、作者与提交者信息及 message 等历史锚点 | 不替代 Working Tree，不自动证明事实正确、验证通过或任务完成 |

当前事实资格绑定管辖项目实际 Git worktree 中的当前文件，不绑定单个文件的 Git 状态，也不要求每次写入后立即 commit。未提交的新文件和修改可以支持当前接续；在创建 commit 后，才能进一步声明相应版本已经获得提交标识和可回查的历史关系。

有效 Git worktree 可能尚未创建第一个 commit。此时 Working Tree 中满足其它条件的内容仍可支持当前工作，但不得声称 `HEAD` 已解析到提交、已有 commit 标识或已经形成 Git history；需要历史锚点的行动必须等待相应 commit 实际创建。

commit message 可以说明变更意图、范围或验证情况，但这些说明必须由实际文件、来源规则和验证依据支持。commit 创建成功只证明 Git 接受了该快照和 metadata，不证明 message 中的语义真实，也不完成 Human Gate、事实验证、发布、部署、PR、merge 或远端同步。

### 9.1 提交契约的适用与时间边界

以下共同契约只适用于当次管辖解析能够确定为一个 `governed_single` 项目中的一个实际 Git worktree，且正在形成新 commit 或经 Human 另行授权重写后的新 commit。明确 `non_governed` 时不适用本契约，也不阻止普通求解；`scope_unknown`、`mixed_scope`、跨项目或 worktree 不唯一时，不得声明 LDVH 提交合规，应先解析、拆分或停止交还。

当前 Working Tree 中取得规则源资格的本文版本，对其生效后形成的候选前瞻适用。修改本文自身的候选按当次实际读取的当前来源审核。既有 commit 不因后续规则变化自动成为创建时违规；只有能恢复当时实际适用的来源身份和内容时，历史审计才能声明“创建时合规”，否则只能声明“与当前契约一致或存在差异”。

验证或审计至少应识别 `source-of-truth-traceability`、实际来源路径、观察时间，以及按原始规范内容计算的确定性内容指纹；来源已进入 Git 时可以追加可解析的 blob 或 commit 身份。`spec_id`、自然语言摘要、Git commit 时间或当前 `HEAD` 不能单独证明当时实际读取的 Working Tree 版本。本文不要求另建长期 receipt。

### 9.2 Commit 证据粒度与拆分基线

一个 commit 只承载一个可以共同说明、共同验证并共同回退的主要目的。文件、目录或 type 数量不能单独证明目的相同或不同。存在以下任一情况时应拆分，除非拆分会破坏同一目的的最小可验证性，并能在 body 中明确说明关系：

1. 变化具有彼此独立的目的、验证方式或回退条件；
2. 无关清理、格式化、生成物或用户既有变化被混入目标；
3. 不同变化需要不同授权、风险决定或 Human Gate；
4. 任一部分失败后，其它部分仍可独立成立并应独立保留；
5. 候选跨越多个管辖项目或多个实际 worktree。

项目来源可以要求更细拆分，但不得允许多个独立目的仅凭宽泛 description 合并。AI 负责目的、共同验证与可回退性的语义判断；Code 只能报告路径、数量和其它已结构化信号。

### 9.3 Header 契约

机械检查把 CRLF 或 CR 统一为 LF，忽略开头空行和以 `#` 起始的完整注释行，但不删除正文中的 `#` 内容，也不得依赖 Git cleanup 隐式改变待验证 message。第一条有效行必须使用：

```text
type[(scope)][!]: 简体中文描述
```

其中：

1. `type` 必填，只能取下表所列 token；
2. `scope` 可省略；存在准确匹配时只能取 `specs`、`docs`、`rules`、`runtime`、`code`、`web`、`tests`、`config`、`workcase`、`adr`、`spark`、`study`、`pitfall`；没有准确匹配时省略，不得临时发明 token；
3. `!` 可省略；只有变化破坏已经承诺的公开契约、格式、兼容性或迁移路径时使用；
4. 冒号后必须有一个空格；description 必须是简洁、真实、可区分主要目的的简体中文短句，不使用句号结尾；
5. `revert` 仍需简体中文 description，并在 body 说明被撤销对象与原因；该 type 不授权历史写入。

type 与 scope 枚举闭集见 [03.Att.01-来源参考枚举闭集.md](attachments/03.Att.01-来源参考枚举闭集.md)。

scope 闭集不承担任意业务架构分区；业务项目没有准确匹配时省略 scope，以 description 和 body 表达具体影响面。项目不得私设 token；若省略频率实际损害定位价值，应统一修订本文。

type 和 scope 都不能替代 description、body、实际 diff 或项目验证。Code 可以检查 token 闭集和至少存在 CJK 字符，但不得据此声明已证明简体中文语义、真实性或表达质量。

### 9.4 Body 与 Footer 契约

所有受本契约约束的新 commit 都必须具有 body，不因候选只有一个路径、type 不是 `revert` 或未使用 `!` 而省略。每个 body 的最低结构是唯一一个 `关键变更:`，其下至少一个从行首开始的 `- ` 列表项，且 `- ` 后必须含非空白内容。该最低结构只证明正文存在且可机械解析，不证明列表内容真实、充分或与 diff 一致。

trigger 只声明普遍最低结构之上的机械追加要求，或提示 AI 按实际情况补足语义上下文；`mechanical` 只表示 Code 能否仅凭 §9.5 的结构化输入确定 trigger，不表示其它语义条件可以忽略：

trigger 枚举闭集见 [03.Att.01-来源参考枚举闭集.md](attachments/03.Att.01-来源参考枚举闭集.md)。

body 小标题闭集为 `动机:`、`关键变更:`、`影响边界:`、`验证结论:`、`风险与后续:`。每个实际出现的小标题必须唯一，其标题至下一个小标题或 footer 之前至少有一个非空白内容行；`关键变更:` 和使用 `!` 时必需的 `影响边界:` 还必须分别具有至少一个符合前述格式的非空列表项。独占一行、无前导空白且以 `:` 结尾的其它文本视为未知小标题并机械拒绝；因此一个列表项不得跨越未知小标题、其它固定小标题或末尾 trailer 块归属于前一节。按实际需要增加最低结构以外的固定小标题；`验证结论:` 只记录实际执行及其结果，不把计划或未运行检查写成已验证。`revert` 的 body 仍按 §9.3 由 AI 审核是否据实说明被撤销对象与原因，不能用机械列表存在替代该语义判断。

footer 必须在末尾使用连续的 Git trailer 块，且每次提交必须恰好含一个非空 `Session-ID:`、一个非空 `Model-ID:` 与一个非空 `Workbench-Name:`。三者共同声明实际执行当次 `git commit` 的唯一当前执行会话：`Session-ID` 填该提交会话的定位符；`Model-ID` 填该会话实际驱动模型本身的可观察标识，例如 `gpt-5`、`k3-256k`、`hy3`，不得拼接宿主产品名（如 `workbuddy-hy3`）并归一为小写；`Workbench-Name` 填当次实际发起提交的宿主软件/产品显示名，例如 `Cindy`、`WorkBuddy`、`Trae`、`Claude Code`，不是机器主机名（如 `LaoDings-MacBook-Pro`），去除系统名称与括号系统后缀，不执行小写归一化。裸产品别名黑名单只约束 `Model-ID`；`Workbench-Name` 不受该黑名单约束，宿主产品名即使命中黑名单词（如 `WorkBuddy`）也应填写在 `Workbench-Name` 中。该提交签名与事实对象 `change_log` 的流水签名是两个独立责任边界：流水保留形成对象变化时的实际写入会话、模型与宿主，footer 只声明实际执行当次提交的会话、模型与宿主；两者不要求相等，不得为了通过提交而改写流水签名，也不得把最后修改内容或最后写入流水的 AI 冒充为当次提交执行者。三类 trailer 由当次提交执行会话自报并由机械校验排雷，当前架构不支持模型id的平台可验证注入；它们是执行会话声明（attestation），不是已验证身份。当调用环境（如宿主产品）提供了 `LDVH_MODEL_ID`、`LDVH_WORKBENCH_NAME` 与 `LDVH_SESSION_ID` 环境变量时，`prepare-commit-msg` Git Hook 会剥离 AI 自报的三类 trailer 并改用环境变量值，使 footer 署名由可信环境注入而非模型自报；未设置环境变量时仍由 AI 自报并由 `commit-msg` Hook 机械校验。旧写入路径已取消（2026-08-09 Human 决定）：新提交只接受 `Session-ID` / `Model-ID` / `Workbench-Name`；旧 `Agent-ID` / `Host-Environment` trailer 仅供读取历史，不作为任何新提交形状。`Signer-Type:` 已退役，出现即为机械不合格，不得作为兼容 trailer 保留。它们不代表 Git author、Human 授权、模型能力、身份真实性或提交内容已获认可。footer 还可以保留 `BREAKING CHANGE:`、`Refs:`、`Co-authored-by:` 等兼容 trailer，但不得替代 LDVH body。`BREAKING CHANGE:` 不单独证明 breaking 语义成立。

过渡期已经进入 HEAD 的 `model_id` / `host_name` 流水与更早的旧形状一样只读保留，不因后续提交回写。相对 HEAD 新增的流水必须使用当前 `model_id` / `agent_workbench` 形状；若未提交后缀仍为 `model_id` / `host_name`，只能先使用 05 §11.7.2 的双指纹受控归一入口改正键名，commit Hook 本身只拒绝不合格候选，不代替该写入。

### 9.5 验证输入与结论分层

提交前合规判断必须绑定同一观察时点和同一候选快照，并取得：

1. 完整 message；
2. 相对于唯一实际 worktree 根、使用 `/` 分隔且不含空项、`.`、`..`、绝对路径、重复项或越界项的完整候选路径集合；rename/copy 按新旧两个可观察路径计入，删除按原路径计入，submodule 变化按其 worktree 中的单一路径计入；
3. 当次管辖解析结果和实际 worktree 身份；
4. 本文实际来源路径、观察时间和确定性内容指纹；
5. 可唯一识别候选内容的快照身份；
6. 事实布局内候选存在时，按 §9.9 形成的暂存内容观察；
7. 项目来源要求的其它验证结果。

AI 语义审核还必须取得 Human 目标、实际候选 diff 或等价完整快照内容、项目规则和实际验证结果。message、候选路径、候选内容、worktree、管辖结果、本文内容或项目验证任一变化，先前结论立即失效；具体 Git 提交行动必须在写入前重新核对同一组绑定输入。

候选路径缺失、读取失败、重复、越出 worktree、来源身份不完整或管辖结果不确定时，validator 必须返回不可验证或失败，不得把空路径降级为 warning 后声明合规。Code 可以机械检查规范化后的 header 语法、枚举、空格、CJK 字符存在、description 句末句号、所有提交的最低 body、小标题唯一性与闭集、非空内容、必需列表结构、由 `!` 追加的 `影响边界:`，以及事实布局内候选按 §9.9 的同核机械校验。AI 负责主要目的、拆分、简体中文语义、description 真实性、高影响分类、breaking 必要性、`revert` 说明、body 充分性、验证与风险是否据实。

任一层通过都不得替代另一层，也不得证明 Human 授权、Git 写入或项目验证成立。项目、行动模板、validator、Git Hook 和 Web 可以生成或缓存受本文内容指纹和同步测试约束的 Code 表示、本地化标签与 DTO，但不得维护第二语义权威或静默扩展闭集。

### 9.6 非合规与历史处置

创建前发现候选不合规时，停止创建并修正候选或 message，不依赖 Git Hook 以后兜底。Git 返回后发现新 commit 的实际 message 或内容不合规时，不得声明提交闭环成功，也不得继续 push、PR 或把上层工作标记完成；保留实际状态和证据。amend、reset、rebase、再次提交或远端改写均需相应 Human 授权和其它来源支持。

审计既有历史时默认只读报告，不自动改写。无法恢复创建时本文来源时，只能标记为“按当前契约比较”，不得断言历史行为当时违规。已发布、共享或位于远端的历史还受协作与远端风险约束，本文不提供改写授权。

具体提交时机、暂存范围、用户既有 Index 隔离、Git 命令、commit 创建与写后回读步骤、Git Hook 安装、push 和远端 ref 写入不由本文规定。具体创建行动由行动模板承接；项目来源只增加领域验证、branch 等不冲突的更严格要求，不得削弱或改写本节共同契约。

|---|---|---|---|---|
| `precheck-git-commit` | 对一个受管辖 Git worktree 当前真实 Index 与完整 message 执行提交契约机械预检 | `read` | `source-of-truth-traceability::9.7 Git commit 候选机械预检输入字段` | `source-of-truth-traceability::9.8 Git commit 候选机械预检结果字段` |

### 9.7 Git commit 候选机械预检输入字段

本操作使用 04 定义的共同请求对象。`work_object_locators` 必填且必须恰有一个非空路径 string，定位一个实际 Git worktree 或其中对象；相对路径以 Helper 进程实际 `cwd` 为基准。领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `message` | string | 必填；允许空字符串 | 当次准备检查的完整 commit message；空值仍交由机械校验形成 `failed`，不因内容不合格改写为请求结构无效 |
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 明确选择本次管辖配置的工作区根；不表示目标已经受管辖 |

本操作不接受 `candidate_paths`、`snapshot_identity`、来源路径、来源指纹或 `index_file`。候选路径与快照必须从目标 worktree 当前真实 Index 只读观察，来源身份必须从确认本操作公开身份的同一当前规则源形成。`task` 不参与机械结论；`observed_context` 与 `authorization_reference` 必须为空，`requested_disclosure` 必须省略或为 `null`。本操作是只读检查，不要求 Git 写入授权，也不得从调用方环境变量接受另一 Index 或 worktree 身份。

### 9.8 Git commit 候选机械预检结果字段

提交机械预检结果（Git Commit Mechanical Precheck Outcome）是按照本文提交契约，对一次已经绑定 worktree、Index、message、管辖和来源身份的提交候选执行可机械检查条件后形成的三值结果，机器表示为 `mechanical_outcome`。它只使用 `passed`、`failed` 或 `unverifiable`，不同于 Helper 外层服务结果、原生 Git Gate 的 allow/block 作用和 AI 语义审核结论。

当管辖、来源投影、实际候选观察和机械校验均已执行时，Helper 外层使用 `outcome: ok`；机械是否通过只由提交机械预检结果表达。领域 `result` 使用以下字段闭集：

| 字段 | JSON 类型 | 空值规则 | 含义与边界 |
|---|---|---|---|
| `mechanical_outcome` | string | `passed`、`failed` 或 `unverifiable` | 只表示本文可机械检查范围的结果 |
| `candidate` | object | 不允许 `null` | 使用下述候选字段，绑定实际 worktree、完整候选路径与 Index 快照 |
| `message` | object | 不允许 `null` | 使用下述 message 字段，保留规范化结果 |
| `contract` | object | 不允许 `null` | 使用下述契约字段，标识实际使用的本文来源投影 |
| `issues` | array | 没有问题时为空 | 每项只含非空 string `code` 与 `message`，机器语义只在本操作和本文范围内成立 |
| `semantic_checks_required` | array | 不允许 `null`；成员为非空 string | 机械检查后仍须由 AI 完成的语义审核范围 |

`candidate` 只含 `git_worktree_root`：非空绝对路径 string、`paths`：完整的规范化 worktree 相对路径 array（空候选使用空 array 并形成 `unverifiable`）、`snapshot_identity`：非空 string。`message` 只含 `normalized_message`、`header`、`body`，三者均为 string 或 `null`。`contract` 只含 `source_key`、`source_path`、`source_fingerprint` 三个非空 string，以及 string 或 `null` 的 `observed_at`。完整管辖结果进入共同 `scope.governance_resolution`，不在领域结果复制第二份。事实候选校验层的结果按 §9.9 并入 `mechanical_outcome` 与 `issues`，不新增顶层结果字段。

机械不合格仍表示本次读取操作已经完成，Helper 不得将 `mechanical_outcome: failed` 改写为外层 `rejected`。空候选等已经由同一 validator 可信形成的不可验证结果可以使用外层 `ok` 与 `mechanical_outcome: unverifiable`；规则源、契约投影、管辖解析、Git 观察或候选漂移没有形成可信校验输入时，外层使用 `unavailable` 并保留未完成范围、来源和诊断。`passed` 不证明主要目的、拆分、自然语言真实性、授权、项目验证、Git 写入或最终 Git Gate 通过；message、Index、worktree、管辖结果或本文来源任一变化，先前结果立即失效。

### 9.9 事实候选机械校验

当提交候选包含事实布局内路径时，提交契约机械校验在 message 与候选路径检查之外增加事实候选校验层。本层只校验当次 Index 候选中的事实文件，不做全库或全量扫描；全库完整性检查只能由 05 登记的独立公开操作提供，不得进入提交链路。

触发与跳过按路径与暂存内容机械判定：

1. 候选路径位于 05 及相应事实类型来源定义的对象布局内，且当次 Index 在该路径有暂存内容时，进入本层；路径文件名不能解析为合法 object_id、文件内 object_id 与文件名身份不一致、或载体、派生 Schema、内容指纹、大小预算任一机械检查不成立，均为本层校验失败，不作为跳过条件；
2. 布局内路径在当次 Index 无暂存内容（删除）时跳过本层，不形成事实问题；改名出布局的新路径不属于布局，不进入本层；改名入布局的新路径有暂存内容时按普通候选进入本层并接受身份核对；
3. 布局外候选路径不参与本层，也不因本层产生额外开销。



暂存内容只能由候选观察层按当次绑定真实 Index 中该路径的 blob 身份只读取得：原生 Git Gate 使用事件自身提供的 Index 观察，Helper 预检对当前真实 Index 重新观察；两者都不得接受调用方提供的候选内容、来源路径或另一 Index 身份。validator 保持纯函数，不读取 Git 或文件系统；暂存内容由观察层作为校验输入提供。不存在事实候选时，双入口不得形成事实 Schema 投影，也不得读取任何暂存 blob。

本层必须调用与 05 事实读取相同的载体解析、派生 Schema 校验、object_id 与文件名身份核对、内容指纹与大小预算机械实现，不得复制第二份解析或校验逻辑；以 Working Tree 为读取视图的事实读取入口不得整体搬入提交链路。事实 Schema 投影从确认本操作公开身份的同一当前规则源派生，并按来源内容与指纹绑定；来源或投影无法形成时按 §9.8 既有分层处理，不得降级为跳过。

### 9.10 发布与版本公共契约

发布指以对外可见的版本身份（版本号与 tag）标记一组已受控提交并同步对外声明。本文只定义发布在提交契约内的共同规则与授权边界，不定义 tag、push、remote/ref 写入或平台 Release 的具体操作步骤（分别由行动模板、项目正式来源与远端平台承担）。

1. **版本号**：遵循语义化版本（SemVer）；pre-release 阶段使用 `-alpha`、`-beta` 或 `-rc.N` 后缀，正式版本不带后缀。
2. **tag 一致性**：对外发布必须使用 tag 标记；tag 采用 `v` 前缀且必须与当前发布版本号严格一致。版本号、tag 与全部版本声明点（`CHANGELOG.md`、`README.md` 版本行、`web/package.json` 及其 lockfile 等）不得相互矛盾；发现漂移必须先修正声明，再标记发布。
3. **变更日志**：每个对外发布版本必须在 `CHANGELOG.md` 记录一条 `## [版本] - YYYY-MM-DD` 条目，使用 `Added`、`Changed`、`Fixed`、`Removed`、`Known` 分区；条目内容必须由实际已提交变更支撑，发布时集中编写，不得为未提交内容作记录。
4. **发布提交类型**：`release` type 用于标记发布、更新版本号与变更日志、同步版本声明与打 tag；`release` 提交不得携带发布范围外的混合变更，仍受本契约全部 message、验证与 Git Gate 约束。
5. **授权边界**：发布是 Human 决定。AI 可以起草版本与变更日志内容并形成发布候选提交，但打 tag、`git push`（含 `--tags`）或任何将版本暴露给远端的动作，只在 Human 明确授权后执行。远端 PR/merge 与平台 Release 操作不经过本地 `commit-msg` Git Gate，其合规性以本地受控创建与提交时为准；GitHub 等平台的 Release 页只是对外展示层，不构成版本权威。
6. **部署件变更标注**：发布触及需要用户在已接入环境重放部署的部署件（如 `skill/SKILL.md`、承接 Git Gate 的 Git Hook 部署件）时，`CHANGELOG.md` 对应条目必须在 `Added` 等分区之前增加醒目分区（如 `### ⚠️ 需要更新 Skill`，按实际部署件命名），说明本次更新需重新部署的部署件并提供简单更新方式（方式细节按 README「更新」小节与环境接入规则，如告知已接入环境的 AI「LDVH 更新了」由 AI 重放受影响部署件）；发布未触及任何部署件时不得生造该分区。发布前必须核对本次变更是否触及部署件，并据此决定该分区是否出现。


## 10. 代表性判断场景

| 场景 | 当前判断 |
|---|---|
| 已跟踪事实文件在 Working Tree 中修改但未提交 | 读取当前文件；在 §§5.1、8 的其余条件同时成立，包括需要时适用事实模型时，可以作为当前稳定事实，Git 差异作为溯源上下文 |
| 新事实文件尚未被 Git 跟踪 | 在 §§5.1、8 的其余条件同时成立，包括需要时适用事实模型时，可以作为当前稳定事实；不得声称已经存在 commit 历史 |
| 新文件被 ignore 规则排除且尚未被 Git 跟踪 | ignore 状态不改变当前事实资格；仍按当前文件、来源规则、验证要求和需要时适用事实模型判断，不得声称已经存在 commit 历史 |
| 已跟踪文件的路径后来命中 ignore 规则 | ignore 状态不改变当前事实资格；仍按当前文件、来源规则、验证要求和需要时适用事实模型判断 |
| 当前文件已删除，但旧路径仍存在于 `HEAD` | 不把 `HEAD` 中旧文件作为当前事实；显式历史审查可以读取并标明版本 |
| Human 明确要求检查某个 commit、Git ref 或版本差异 | 读取指定历史对象或参与比较的各版本，保留版本定位，不把历史内容改写成当前事实 |
| Index、`HEAD`、缓存或 Web 视图与 Working Tree 不同 | 判断当前事实时使用 Working Tree；其它内容只承担待提交、历史或派生视图作用，并报告相关差异或过期状态 |
| Git worktree 尚无第一个 commit | 当前文件仍可在其它条件成立时支持当前工作；不得声明已有 `HEAD` 提交或 Git 历史锚点 |
| 受管辖项目准备创建新 commit | 按 §9.1 确认管辖与实际 worktree，按 §§9.2–9.5 审核同一候选快照、完整 message 和验证输入；本文不产生 Git 写入授权 |
| AI 在创建前主动预检当前候选 | 调用 `precheck-git-commit` 读取当前真实 Index 并取得机械结果；仍须完成 AI 语义审核，创建前对同一组绑定输入重新核对 |
| 原生 `commit-msg` Git Gate 检查真实提交事件 | 不经过 Helper 服务链；以事件实际 message 与 Index 使用同一提交契约投影和候选观察实现并调用唯一 validator，非 `passed` 时阻断 |
| 审计旧 commit 但无法恢复创建时规则内容 | 只报告与当前 §9 契约的一致或差异，不断言创建时违规，不自动改写历史 |
| 非受管辖项目准备普通 Git commit | §9.1 的 LDVH 提交契约不适用，不据此阻断普通求解或项目自身规则 |

## 11. 时间表示与溯源边界

所有带时刻语义的来源字段必须按同一瞬时解释：Code 新生成的时间统一写为 RFC 3339 UTC `Z` 形式；旧对象中带明确非零偏移的表示继续作为历史输入兼容读取，不要求迁移或重写历史事实。时间表示的变化不得被解释为事实内容或来源已经更正。

`created_at`、`updated_at`、`change_log.at`、演变时间、审核/批准时间、`observed_at`、事件时间以及 Git/API 返回的 commit 时间均适用上述边界。纯日期字段没有时区转换语义。无法解析或只有不明确本地时区的值必须暴露为未知/原文，不得静默猜测。

## 13. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 的事实源定位、事实源边界，或者允许管辖项目实际 Git Working Tree 当前文件以外的内容成为 LDVH 稳定事实承载；
2. 改变 Working Tree 作为当前默认读取视图的边界，或者重新要求只有 commit 后的内容才算当前事实；
3. 为同一稳定事实建立多个需要分别维护的权威位置，或者在冲突位置之间选择新的唯一位置；
4. 决定当前事实冲突、来源无法回指或 Git 无法识别目标文件时的修复方向、唯一位置选择、受影响范围或是否放弃将相关内容作为稳定事实消费。
5. 是否创建、amend、rebase、reset、push 或以其它方式改写 Git 状态与历史；
6. 多个合理拆分或 breaking 方案会改变 Human 目标、公开承诺、不可逆历史或重大风险，且当前来源无法决定时采用哪一方案；普通拆分和分类仍由 AI 依据来源判断；
7. 是否接受无法恢复创建时规则来源的历史差异，或者另行启动历史治理；
8. 是否安装、替换、合并或移除 Git Hook 与 `core.hooksPath`。

9. 受管辖提交若新增 `specs/<id>-*.md` 独立规范文档，或将其 `status` 转为 active，须携带 Human Gate 授权记录：提交消息 footer 须含非空 `Human-Gate:` trailer，指向本次 Human 决定（如授权说明或决策提请标识）；无该记录时 Git Gate 机械阻断，提交不得通过。上述两项同时依 00 §10.1 第 12 条为确定的 Human Gate 事件。既有可强制执行规则的实质性改写同样依 00 §10.1 第 12 条为确定的 Human Gate 事件，AI 不得自行判定是否触发；但该事项的 `Human-Gate:` trailer 按 03.Att.01 的 footer trailer 枚举为条件性要求——仅当本次提交同时新增或激活 spec 文档时强制，否则可选——其 Human Gate 性质由 00 §10.1 第 12 条而非机械 trailer 保证。`Human-Gate` trailer 的合法 token 与取值要求见 03.Att.01。

Human 决定的复用按 00 §10 执行；Human 回应不能替代事实源文件写入与回读、来源规则或事实模型校验、技术验证或 Git 历史形成，也不能使不满足事实源边界的内容取得稳定事实身份。

## 14. Stop Conditions

出现以下任一情况时，必须暂停依赖受影响事实或溯源结论的最小行动、对象或声明范围：

1. 判断项目当前事实时，AI、Helper 或 Code 正在用 Index、`HEAD`、远端分支、缓存、索引或 Web 视图覆盖当前 Working Tree 内容；
2. 显式历史对象或版本比较没有保留版本身份，或者历史内容正在被冒充为项目当前事实；
3. 当前文件无法解析或违反适用来源规则、需要时事实模型，却准备静默回退到旧提交继续；
4. 聊天、AI 推理、命令或测试输出、Human 当前指令、工具成功、配置、缓存、派生结果或 Git commit 正在被直接冒充为稳定事实、规则、验证通过或完成证明；
5. 同一稳定事实存在相互冲突的权威位置，且无法按来源规则确定当前应消费哪一处；
6. 准备写入或更新稳定事实，但没有已定义的来源规则或目标位置；内容需要对象化、状态化或证据化管理时，没有适用事实模型或当前状态要求；
7. 来源规则要求保留来源回指，但当前信息无法以所需精度回到其出处或形成依据；
8. 正在声明某个版本已有 Git 历史锚点，但对应修改尚未 commit、`HEAD` 尚不可解析，或提交标识与目标内容不匹配。
9. 准备声明受管辖提交合规，但管辖结果不是单一受管辖项目、实际 worktree 不唯一，或完整 message、候选路径、候选快照和本文内容指纹无法取得；
10. 受管辖提交候选混入无关变化、不能形成一个共同说明/验证/回退的主要目的、机械检查失败，或 AI 无法确认 description、拆分、breaking、body、验证与风险据实；
11. 新 commit 已产生但回读不符合 §9，且没有相应历史修改授权；
12. 消费者维护了与 §9 不一致的 type、scope、body 或时间规则；只暂停该消费者及依赖它的声明，不自动阻断可信当前来源和其它入口。

未提交、dirty、untracked、进行中状态或缺少远端同步本身不构成停止条件。暂停范围与可继续行动按 00 §11 执行；对本文而言，只读核对当前文件、Git 状态与差异，修正事实结构或来源回指，补充验证、拆分冲突对象和准备 Human Gate，可以在不越过受影响边界时继续。

受影响范围只能在当前读取视图或历史对象身份已经纠正、事实结构与来源要求已经满足、冲突位置已经处理、需要时相应事实模型已经存在、历史声明已经缩小到实际提交范围，或者 Human 已对其保留事项作出作用范围清楚的决定后恢复。
