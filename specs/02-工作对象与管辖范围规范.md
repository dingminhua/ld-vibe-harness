## 1. 价值判断

本文的价值，是让 AI 能把 Human 当前目标、实际工作对象和工作区级管辖项目配置联系起来，确定每个已识别对象与 LDVH 管辖项目的关系，并把配置缺失、身份歧义、多项目和混合范围如实保留下来。这样可以减少 AI 依赖当前目录、名称相似、对话记忆或单一工具输出猜测项目归属的负担。

本文主要服务：

1. V1 快速定位：定位当前事项实际涉及的工作对象及其管辖项目；
2. V2 充分理解：联系 Human 目标、显式对象定位符、路径、Git 身份和管辖配置；
3. V3 边界识别：区分已管辖、非管辖、无法确认、多管辖项目和混合范围；
4. V5 据实判断：使管辖结论只覆盖当次输入和可回指依据实际支持的对象；
5. V7 清晰沟通：在对象或配置歧义时，清楚交还对象、依据、缺口和影响范围。

本文不把管辖解析变成所有 AI 行动必须经过的全局流程。只有当前事项需要对象专属的 LDVH 规则、事实、行动模板或 Code 能力时，才需要取得能够支持相应对象范围的管辖解析结果。

## 2. 规范依据

本文直接依据 `ldvh-root`，细化 00 中“Helper CLI 围绕当前任务和工作对象提供服务”以及“Helper CLI 的服务范围与具体规则的适用范围分属不同层次”的上位定义。

本文不得改变或重新解释以下边界：

1. AI 是 LDVH 的第一服务对象；
2. LDVH Helper CLI 是基础服务形式；
3. 管辖命中只进入后续对象专属服务和规则判断，不等于任何具体规则已经适用；
4. 未命中具体规则时，AI 的普通求解路径保持自主；
5. 项目中的稳定事实仍必须回到 00 定义的事实源边界；
6. 设计、实现、环境接入和验证状态必须如实区分。

本文作为普通规范，按 `specification-model-foundation` 的形成与治理约束组织；01 不因提供形成与治理约束而被机械写入 `basis`。历史规范、Code、tests 和配置只作为问题与成熟场景参考，不因被参考而自动取得当前规则效力。

## 3. 职责边界

本文负责定义：

1. 工作对象、工作对象定位符、工作对象身份依据、管辖项目、管辖范围、工作对象管辖判定和管辖范围解析的含义与差异；
2. `LDVH-GOVERNED-PROJECTS.yaml` 的定位、工作区根位置、配置发现边界和规则权威边界；
3. 管辖项目配置的语义、字段契约授权、有效性和冲突处理；
4. 显式工作对象、当前操作实际涉及对象、`cwd`、路径和 Git 身份各自承担的作用；
5. 逐工作对象的 `governed`、`not_governed` 和 `unknown` 关系，以及单一、多项目、非管辖、未知和混合聚合结果；
6. 哪些结果可以交给后续 LDVH 职责继续判断，哪些对象范围需要补充依据、拆分或交由 Human 决定。

本文不定义：

1. 具体来源规则是否适用、命中后产生什么义务，或多条规则如何处理冲突；
2. Helper CLI 的命令、请求与响应 envelope、错误码、静默输出或受控副作用；
3. 管辖配置的安装向导、写入步骤、备份、恢复、迁移或回滚流程；
4. 路径规范化、符号链接、大小写、worktree、submodule 或 Git 命令的具体算法；
5. Hook、插件、adapter、环境事件和环境 `integrated` 判定；
6. 项目事实对象、行动模板、Code 模块、tests 或 Web 展示；
7. 写入、提交、远端变更或其它行动本身是否获准执行。

## 4. 适用范围

本文适用于以下场景中的工作对象管辖判定和管辖范围解析：

1. AI 或 Helper 需要围绕当前事项定位对象专属的规则、事实、行动模板或 Code 能力；
2. Human 目标、显式对象定位符、当前操作实际涉及对象、`cwd`、路径或 Git 身份之间可能不一致；
3. 当前事项涉及一个或多个工作对象、一个或多个管辖项目，或者混合管辖与非管辖对象；
4. 安装、环境入口或 Helper 需要读取和验证工作区级管辖项目配置；
5. 下游职责需要获得对象、管辖项目、来源回指和未解决缺口。

本文不要求一般知识问答、明确不依赖 LDVH 工作对象的普通求解，或者已经能够确认不受本文规则影响的事项先运行固定 Helper、Hook 或 preflight。

## 5. 核心概念

本节中的中英文名称及其登记必须符合 `specification-model-foundation` 和当前双语术语表；其含义和边界以本节对应定义为唯一来源。

### 5.1 工作对象（Work Object）

工作对象是当前事项实际读取、修改、比较、验证或作出声明所指向的可识别资源或项目内信息对象。文件、目录、Git 仓库、worktree、Git ref，以及由正式规范定义的项目内对象都可以成为工作对象。

工作对象绑定当次事项。除非后续适用的事实模型和事实源规则另有定义，并按规则写入或更新事实源，它本身不是跨会话稳定事实。

### 5.2 工作对象定位符（Work Object Locator）

工作对象定位符是 Human、当前操作或环境入口提供的结构化定位输入，用于指向一个或多个候选工作对象。路径、带仓库依据的 Git ref、稳定对象引用或等价结构化输入都可以成为工作对象定位符。

自然语言目标可以由 AI 用于识别候选工作对象，但 Code 只消费结构化定位符和可观察依据，不通过猜测自然语言、目录名称或路径相似性自行确定项目归属。

### 5.3 工作对象身份依据（Work Object Identity Evidence）

工作对象身份依据是用于复核工作对象类型、实际身份、边界或与项目关系，并能回指当次观察来源的信息。路径存在性、真实路径关系、Git worktree 根和 Git common-dir 都可以在各自范围内提供身份依据；remote URL、名称相似或对话记忆不能单独形成确定的工作对象管辖判定。Git worktree 根说明当次对象实际位于哪份工作树，Git common-dir 说明哪些 worktree 共享同一本地 Git 仓库；二者不得互相替代。

### 5.4 管辖项目（Governed Project）与管辖范围（Governance Scope）

管辖项目是当前选定且有效的 `LDVH-GOVERNED-PROJECTS.yaml` 中登记，并能从其项目路径复核为有效 Git worktree 的项目。每个管辖项目具有稳定项目 ID、作为本地登记入口的项目路径，以及可选的名称和说明。Code 从该路径现场读取 Git common-dir，不要求 Human 在配置中复制 Git 元数据。

同一 Git common-dir 只对应当前配置中的一个管辖项目。该仓库的主 worktree 和 linked worktree 均可以通过当次可观察的 Git common-dir 命中该项目；新增、移除、移动或切换其它 linked worktree 不要求修改管辖项目配置。分支名、当前 `HEAD` 和 remote URL 不定义管辖项目身份；配置登记路径失效时配置仍然无效。

项目路径只承担配置登记、配置验证和直接路径命中的入口作用。工作对象位于该项目的其它 worktree 时，实际 worktree 根决定当次读取、修改和验证的内容；项目路径、Helper 进程所在 worktree 或共享同一 Git common-dir 的其它 worktree 都不得替代它。不同 worktree 中的当前规则源、事实源和进行中变化不得因命中同一管辖项目而合并。

管辖范围是该项目登记和可复核项目身份共同界定的对象范围。一个对象进入管辖范围，只表示可以围绕该对象继续提供 LDVH 对象专属服务并判断候选规则；它不表示全部 LDVH 规则生效，不表示行动获准，也不证明能力可用、环境已接入或工作已完成。

Human 当前指令可以指定本次意图对象，但不能只凭当次指令把未登记项目判定为 `governed`，也不能覆盖按当前配置和依据形成的工作对象管辖判定。新增、移除或修改管辖项目必须修改工作区配置并完成相应验证。

### 5.5 工作对象管辖判定（Work Object Governance Determination）与管辖范围解析（Governance Scope Resolution）

工作对象管辖判定表示依据当次定位符、身份依据和当前有效管辖项目配置，对一个已识别工作对象形成的原子结论：

| 机器表示 | 含义 |
|---|---|
| `governed` | 对象身份足以复核，并且唯一命中一个管辖项目 |
| `not_governed` | 已选定有效配置，对象身份足以复核，且没有命中其中任何管辖项目 |
| `unknown` | 配置、对象身份或匹配关系不足、无效、冲突或不唯一，无法支持前两种结论 |

管辖范围解析是根据工作对象定位符、对象身份依据和当前选定管辖配置，形成逐对象管辖判定及聚合结果的过程。结果绑定当次输入、配置内容和观察时间，不是规则源、事实源、行动授权、规则命中结果或验证通过声明。

## 6. 管辖项目配置（Governed Projects Configuration）

### 6.1 文件定位与权威边界

管辖项目配置的文件名为 `LDVH-GOVERNED-PROJECTS.yaml`。该文件位于 Human 选择或安装配置明确指定的工作区根目录：

```text
<workspace_root>/LDVH-GOVERNED-PROJECTS.yaml
```

工作区根目录可以同时管理一个或多个项目，也可以位于所有项目仓库之外。该目录不要求自身是 Git worktree，因此管辖项目配置可以不被项目 Git 跟踪。

管辖项目配置是 Helper/Code 在当前工作区形成工作对象管辖判定的直接配置输入，但它不是项目事实对象，不属于事实模型，不是 00 定义的事实源，也不取得规则权威。项目中的稳定事实、状态、证据和决策仍必须保存在相应项目中由 Git 可追踪文件承载的事实源内。

配置文件只登记项目 ID、本地项目入口和 Human 可读说明，不复制 Git common-dir、remote URL、默认分支或当前分支，也不记录初始化状态、执行状态、环境接入状态、验证结论、Human Gate 完成状态或项目事实内容。

### 6.2 配置发现

1. 已有 Human 选择、安装记录或环境入口明确提供 `workspace_root` 时，只以该根目录下的配置作为本次候选主配置；
2. 没有显式工作区根时，有显式工作对象定位符就从各定位符可复核的路径边界向上查找同名文件；没有显式定位符时才从进程实际 `cwd` 向上查找。候选对象位于有效 Git worktree 时，还必须从现场解析的 Git common-dir 的父目录开始向上查找，使位于工作区目录之外的 linked worktree 可以发现共享仓库所在工作区的配置；不得把 Git common-dir 或其它 Git 元数据目录内部的同名文件作为工作区配置。Code 必须返回每条发现路径和查找依据，不得从 `task` 猜测工作区根；
3. 自动发现到的配置按真实绝对路径去重，同一路径的多条发现依据全部保留且不构成冲突。不同工作对象或同一相关路径链发现两个或以上不同真实配置路径时，不得按内容是否有效、最近目录、修改时间或任意固定优先级静默选择；本次配置选择和相关对象关系为 `unknown`；
4. Git worktree 根目录中的同名文件只有在该目录本身被明确选为工作区根时才可以作为本次配置。自动向上发现时必须跳过该文件并继续检查上层目录，不能因为距离对象更近而停止查找、制造冲突或覆盖外部工作区配置；
5. Git worktree 不在登记项目路径之下时，Code 必须分别从登记项目路径和当次对象实际所在 worktree 现场读取 Git common-dir；二者唯一一致时可以匹配原管辖项目，remote URL 不能单独决定命中。

### 6.3 配置字段与有效性

本文授权 `governed-projects-config-fields` 附件承载配置根字段、项目字段和管辖解析结果字段。核心边界如下：

1. 根字段为 `product_name`、`product_description` 和 `projects`；
2. 每个项目必须有全配置唯一的 `id` 和非空 `path`；`name` 和 `description` 可选；
3. 相对 `path` 以配置所在工作区根目录为解析基准，绝对路径保持其实际含义；
4. 每个项目路径在配置验证和实际消费时必须能够复核为有效 Git worktree；Code 必须从该路径现场读取 Git common-dir，不得通过隐式 `git init` 使错误配置成立；
5. 同一配置中的项目 ID、规范化项目路径和现场读取的 Git common-dir 均不得造成重复或不唯一命中；同一 Git common-dir 不得登记为两个管辖项目；
6. 分支、`HEAD`、remote URL、目录名称或路径相似性都不得代替项目 ID、有效项目路径和当次 Git common-dir 依据；
7. 配置不接受附件字段表以外的状态、运行或安装字段；
8. YAML 无法解析、字段不完整、项目不是有效 Git worktree、项目身份重复或同一对象唯一命中多个项目时，不得输出确定的 `governed` 或 `not_governed`。

具体字段类型、条件和机器表示只在授权附件中定义一次；Code 常量、Helper 输出和 tests 必须从该来源契约推导，不得形成第二套字段定义。

## 7. 工作对象解析规则

1. 显式工作对象定位符和当前操作可以确定的实际涉及对象必须保留；二者不一致时记录差异，不得用 `cwd` 静默覆盖；
2. 只有缺少显式定位符和可确定的实际涉及对象时，`cwd` 才作为工作对象回退输入；
3. 相对定位符必须保留其解析基准和来源回指；
4. 多个定位符解析到同一身份时可以形成一个工作对象，但必须保留原始定位符；一个定位符确定性展开为多个对象时必须保留多个工作对象；
5. 路径包含判断必须保持真实路径和路径段边界，不得使用裸字符串前缀，也不得穿透 submodule 或其它嵌套 Git worktree 的仓库边界；具体跨平台算法由 Code 和 tests 证明；
6. worktree 路径和 Git common-dir 分别提供当次内容位置和共享本地 Git 仓库依据，层次不同不构成冲突；命中管辖项目后仍必须保留对象实际 worktree 根，不得使用登记项目路径或其它 worktree 替代；
7. 尚未创建的文件只要预期路径、解析基准和已存在的项目边界可以复核，也可以作为候选工作对象；不存在本身不决定工作对象管辖判定。

## 8. 解析结果与消费边界

### 8.1 聚合结果

逐对象管辖判定可以确定性聚合为：

| 聚合状态 | 成立条件 |
|---|---|
| `governed_single` | 全部已解析对象均为 `governed`，并且唯一命中同一个管辖项目 |
| `multiple_governed_projects` | 全部已解析对象均为 `governed`，并且命中两个或以上管辖项目 |
| `non_governed` | 已选定有效配置，全部已解析对象均为 `not_governed` |
| `scope_unknown` | 没有可用配置、配置选择冲突、没有可用工作对象，或者全部对象均为 `unknown` |
| `mixed_scope` | 已解析对象中出现两种或以上工作对象管辖判定 |

聚合状态只描述输入对象集合，不得扩张到当次没有提供或无法从当前操作确定的其它对象。多个对象分别命中不同管辖项目属于 `multiple_governed_projects`；同一对象命中多个不等价项目属于 `unknown`。

### 8.2 最小结果信息

管辖范围解析结果至少保留：选定工作区根、配置路径与配置读取状态、原始定位符、解析基准、逐对象身份依据、能够复核时对象实际 Git worktree 根、逐对象管辖判定、命中项目及匹配方式、聚合状态、来源回指和未解决缺口。

具体响应 envelope、错误码、摘要方式和自动展开策略由后续 Helper 服务契约定义。Helper 可以压缩展示，但不得丢失返回完整对象分组、来源依据和缺口所需的回指。

### 8.3 消费边界

1. `governed_single` 可以把逐对象上下文交给后续职责定位候选规则、项目事实、行动模板和能力；
2. `multiple_governed_projects` 必须保留每个对象与项目的映射，是否组合行动由后续来源规则判断；
3. `non_governed` 只证明本次输入对象未命中选定配置，不要求 AI 停止普通求解；
4. `scope_unknown` 应补充配置、工作区根、定位符或身份依据，不得被当作已管辖或非管辖；
5. `mixed_scope` 必须保持对象分组，不得用一个总结果覆盖全部对象；
6. 任何结果都不得单独推出具体规则命中、行动授权、Human Gate 完成、能力可用、环境已接入或工作完成。
7. `registered_project_path` 只回指配置登记入口；下游读取、修改或验证对象内容时必须使用该对象实际 worktree 根。同一项目的多个 worktree 即使聚合为 `governed_single`，当前规则源、事实源和进行中变化仍按对象分别消费。

## 9. 代表性判定场景

以下场景用于约束语义，不固定实现算法：

| 场景 | 预期结果 |
|---|---|
| 明确工作区根且其中配置有效 | 使用该配置并返回其绝对路径和来源 |
| 工作区根位于多个项目仓库之外 | 配置仍可作为本机工作区输入，不要求工作区根进入 Git |
| 外部工作区配置与 Git worktree 根内同名文件同时存在 | 未明确选择 Git worktree 根为工作区根时，跳过仓库内文件并继续使用唯一外部配置；不得由最近文件覆盖 |
| 显式对象与 `cwd` 指向不同项目 | 保留显式对象；`cwd` 只作解析上下文 |
| 没有显式对象，`cwd` 唯一命中配置项目 | 可以通过 `cwd` 回退形成工作对象 |
| `cwd` 是位于项目之外的工作区根且没有其它对象，配置有效 | `cwd` 形成唯一工作对象；不得枚举或猜测子项目；逐对象为 `not_governed`，聚合为 `non_governed` |
| `cwd` 是工作区根，同时提供 linked worktree 内的显式定位符 | 只把显式定位符作为对象；`cwd` 只承担相对路径基准，不形成第二对象 |
| linked worktree 位于工作区目录之外，沿其路径无法发现配置，但从实际 Git common-dir 向上唯一发现配置 | 使用该配置继续解析，并保留 common-dir 配置发现依据 |
| main worktree、长期 linked worktree 或临时 linked worktree 的 Git common-dir 唯一匹配 | 对象命中同一管辖项目，同时分别保留各自实际 worktree 根 |
| worktree 切换、重命名分支或处于 detached HEAD | 不改变管辖项目命中；当次内容仍由实际 worktree 决定 |
| 同一管辖项目的多个 worktree 同时作为对象 | 聚合可以是 `governed_single`，但逐对象结果和当前内容不得合并 |
| 相同 remote URL 的独立 clone 已取得完整本地路径和 Git 依据，但未由项目路径或 Git common-dir 命中 | 逐对象为 `not_governed`；不因 remote 相同而命中已登记项目 |
| 只有 remote URL、名称或分支而没有可复核本地对象身份 | 相关对象为 `unknown` |
| 对象位于未独立登记的 submodule | 以 submodule 自身 Git common-dir 判断；父项目路径不得穿透该 Git 仓库边界；本地身份充分时为 `not_governed` |
| submodule 作为独立项目登记 | 对象命中该 submodule 对应的管辖项目 |
| 两个配置项目路径现场解析到同一 Git common-dir | 配置无效，不能把同一共享仓库登记成两个管辖项目 |
| 配置登记的项目路径不是有效 Git worktree | 配置验证失败，相关工作对象管辖判定为 `unknown`；不得隐式执行 `git init` |
| 有效配置存在且全部输入对象均未命中 | 逐对象为 `not_governed`，聚合结果为 `non_governed` |
| 配置缺失或 YAML 无法解析 | `scope_unknown`，不得通过“没有找到”推出非管辖 |
| 多个对象分别命中不同管辖项目 | `multiple_governed_projects`，保持对象与项目映射 |
| 管辖与非管辖对象同时存在 | `mixed_scope`，保持分组 |
| Human 只说“这次把未登记项目也当作管辖项目” | 不据此将未登记项目判定为 `governed`；需要修改配置并完成验证 |

## 10. Helper CLI 公开操作

### Helper 公开操作

| `operation_key` | `summary` | `effect` | `arguments_contract` | `result_contract` |
|---|---|---|---|---|
| `resolve-governance-scope` | 读取当前管辖项目配置和工作对象的当次路径与 Git 依据，形成逐对象管辖判定及聚合结果 | `read` | `work-object-governance-scope::10.1 管辖范围解析输入字段` | `governed-projects-config-fields::管辖范围解析结果字段` |

本操作只读取配置、路径和 Git 信息，不修改配置、工作对象、Git worktree、分支、`HEAD` 或其它状态。它不从 `task` 推断工作对象或管辖项目，不判断具体规则是否适用，不产生行动授权，也不读取配置登记路径或其它 worktree 中的项目内容来替代目标 worktree。

Helper 先依据自身已经建立的当前规则源发现本操作及其契约，再读取请求指定对象的配置、路径和 Git 依据。目标 worktree 中的 Specs 不参与本操作的身份、契约或启动判断，也不能在管辖结果形成前反向改写 Helper 可以执行的操作；本操作完成后，其它确需读取对象专属规范、事实源或项目内容的职责才按各自来源规则绑定目标对象实际 worktree。

### 10.1 管辖范围解析输入字段

本操作使用 04 定义的共同请求对象。`work_object_locators` 可以为空；非空时只接受非空路径 string，每个成员按输入顺序形成一个待解析范围，object 成员和空字符串按 `invalid_request` 处理。绝对路径保持其含义；相对路径以 Helper 进程实际 `cwd` 为解析基准，并在来源回指中保留该基准。提供显式定位符后，进程 `cwd` 不再形成替代对象。定位符为空时，Helper 把进程实际 `cwd` 作为唯一回退定位输入，并在逐对象结果中记录 `source: cwd`。进程实际 `cwd` 是 Helper 当次观察，不由调用方在 `observed_context` 中声明或覆盖。

领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 明确选择本次唯一工作区根；只在该目录下读取 `LDVH-GOVERNED-PROJECTS.yaml`，不表示该目录自身或任一子目录已经成为工作对象或管辖项目 |

提供 `workspace_root` 时，不再从定位符、Git common-dir 或 `cwd` 向上发现其它候选配置；路径不存在、不是目录或配置不存在时，仍按结果契约报告实际配置状态和缺口，不因路径字符串格式正确而伪造有效配置。配置存在但必需读取因权限或 I/O 失败而未完成时，按 §10.2 使用服务级未完成结果。未提供时，有显式定位符就分别从其可复核的路径边界，以及能够现场解析时从其 Git common-dir 的父目录向上发现配置；没有显式定位符时才对进程实际 `cwd` 使用相同发现方式。自动发现遇到 Git worktree 根内的同名文件时按 §6.2 跳过并继续向上；发现结果按真实绝对路径去重并保留全部依据，两个或以上不同配置路径使用 `config_status: conflict`，不得通过解析内容筛除竞争配置，也不得静默选取最近或首个结果。

本操作要求 `observed_context` 为空 object；其中出现任何成员都属于本操作未知字段。非空 `observed_context`、未知 `arguments` 字段、非绝对 `workspace_root`、共同字段类型错误或不成立的定位符结构按 04 使用 `invalid_request`。`task` 即使出现也不参与工作区根、对象或项目匹配。`requested_disclosure` 不改变本操作的选择和结果范围，共同响应 `disclosure` 固定为 `null`。

### 10.2 管辖范围解析结果边界

领域 `result` 直接使用 `governed-projects-config-fields` 附件的“管辖范围解析结果字段”单一对象，不建立第二份字段定义。由于本操作的领域结果本身就是完整管辖范围解析，共同响应中的 `scope.governance_resolution` 固定为 `null`，不得复制一份可能与 `result` 分叉的结果；其它操作需要携带本操作已经形成的解析结果时，仍按 04 使用 `scope.governance_resolution`。

每个输入范围使用 `locator_index`、`locator` 和 `source` 三个字段形成共同 `scope.requested` 的 object 成员；显式定位符按原始输入顺序从 `0` 编号，`cwd` 回退固定使用序号 `0`。已经形成对应 `object_resolutions[]` 条目的范围原样进入 `scope.completed`，未形成条目的范围原样进入 `scope.not_completed`。三份范围成员与逐对象结果通过 `locator_index` 一一对应，重复定位符不得合并。`outcome: ok` 时全部请求范围必须进入 `completed`；`partial` 时 `scope_status` 只聚合已经完成的 `object_resolutions`，不得用于覆盖 `not_completed`。

只要有效请求的全部输入对象都已经按本操作契约形成 `governed`、`not_governed` 或 `unknown` 逐对象结果，并形成相应聚合结果，外层使用 `outcome: ok`。`config_status` 为 `missing`、`invalid` 或 `conflict`，逐对象为 `unknown`，或者聚合为 `scope_unknown`、`multiple_governed_projects` 或 `mixed_scope`，都属于可以如实完成的领域结果，不自动改写为 Helper 执行失败。

只有请求结构或字段不成立时使用 `invalid_request`；至少一个独立输入范围已经完成、至少一个因实现或环境错误未能按契约形成任何逐对象结果时使用 `partial`；没有输入范围能够完成时，再按 04 区分 `unavailable` 或 `error`。配置不存在、YAML 或字段无效、多个不同真实配置路径冲突、对象确定性位于非 Git 目录、符号链接循环或已经成功观察到的身份依据不足，可以按领域契约形成相应状态。配置文件存在但必需读取因权限或 I/O 失败而没有执行、Git 可执行能力不存在、Git 进程无法运行，或者必需的路径观察因权限失败而没有完成时，不能通过创建 `unknown` 规避服务级未完成结果；按受影响范围使用 `partial`、`unavailable` 或 `error`。

配置、路径、Git common-dir 和实际 worktree 都是可变化的当次来源。响应必须在共同 `sources`、逐对象 `source_refs` 和适用的 `identity_evidence` 中保留实际定位依据；结论依赖观察时点时，来源回指必须按 04 使用 RFC 3339 `observed_at`。结果按 `locator_index` 保持原始定位符顺序；多个定位符即使指向同一对象也分别保留，不进行丢失来源差异的自动去重。

配置、对象身份和项目匹配的未解决缺口统一进入共同响应 `gaps`，不在领域 `result` 中复制第二份。共同 `gaps` 还可以按 04 承载 Helper 服务或实现缺口，但必须通过 `scope` 和来源回指区分受影响范围。

## 12. Human Gate

以下事项必须进入 Human Gate：

1. 选择或改变主工作区根和 `LDVH-GOVERNED-PROJECTS.yaml` 的实际位置；
2. 新增、移除、重命名或修改管辖项目登记，或者接受项目 ID、路径、现场 Git common-dir 的歧义；
3. 发现多份相互竞争的配置，需要删除、迁移、合并或明确保留其中一份；
4. 多个同样合理的意图对象会导致不同外部影响或长期事实变化，现有依据不能替 Human 选择。

Human 已在当前指令中清楚给出相应决定时，不重复索取同一决定；但该回应不能替代配置写入、对象身份核对、配置验证、Code 验证或环境接入证明。

## 13. Stop Conditions

出现以下任一情况时，必须暂停依赖相应管辖结论的最小行动、对象或声明范围：

1. 主工作区根或配置路径无法确认，且当前判断需要管辖配置；
2. 配置缺失、不可读、YAML 无效、字段不成立、登记项目不是有效 Git worktree，或存在相互竞争的配置，却准备输出确定的工作对象管辖判定；
3. 工作对象身份冲突、一个对象唯一命中多个项目，或者 remote URL、名称相似或对话记忆正在被单独用于决定管辖；
4. 多项目或混合范围被折叠，已经无法确认每项依据或结论属于哪个对象；
5. Human 当次指令正在被用于绕过配置变更，把未登记项目判定为 `governed`，或者覆盖按当前配置和依据形成的工作对象管辖判定；
6. 管辖配置正在被表述为项目事实对象、事实源、规则源、行动授权或完成证明；
7. 尚未实现、接入或验证的 resolver、Helper、Code、tests 或环境能力正在被声明为已可用或已自动保障。

配置缺失、`scope_unknown`、`multiple_governed_projects` 或 `mixed_scope` 本身不造成全局停止。暂停期间可以继续只读核对、补充工作对象定位符、检查配置和身份依据、拆分对象、准备 Human Gate，并继续明确不依赖受影响管辖结论的普通工作。

受影响范围只能在与具体触发原因对应的条件满足后恢复：工作区根和配置路径已经确认，配置错误或冲突已经修正，对象身份或项目匹配歧义已经消除，对象已经拆分，配置变更已经完成并验证，或者声明已经缩小到现有依据实际支持的范围。恢复不得自动扩张到其它对象或行动。
