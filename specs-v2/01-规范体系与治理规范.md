## 1. 本文解决的问题

本文定义 v2 规范体系如何成立，以及单篇规范如何成为可读取、可判断、可检查、可派生知识地图的稳定规范结构。它回答的核心问题是：一篇规范最低必须具备哪些结构，才能让 AI 在有限上下文中判断它的位置、权威边界、依赖关系、检查入口和待补齐风险。

本文解决：

1. 规范如何声明身份、状态、权威边界、迁移来源和 active 事实源；
2. 正式规范最低需要哪些必要章节；
3. 规范如何表达上位依据、相关关系、消费关系、附件授权和迁移来源；
4. 规范结构如何形成知识地图所需的节点、边、来源回指和最小读取依据；
5. 附件如何命名、授权、受父规范约束，并避免变成隐性主规范；
6. 专题规范如何声明成员集合、专属骨架、锚点和 Code 消费入口；
7. Code 检查缺口、Human Gate 和待补齐事项如何暴露给 AI 与 Human。

本文只定义上述共同治理规则。事实模型字段、状态机、行动流程、Code 输出 Schema、Web 页面契约、Git 提交格式、事实源细则、运行时扩展类型和具体环境适配规则，由对应构成要素实践在自身规范中声明。本文不预设这些专题的最终编号、拆分方式或迁入结论。

## 2. 上位依据

本文承接 `00-LDVH理念与价值标准.md` 的已确认基线：

1. v2 规范治理必须以“LDVH 为什么存在”和“AI 执行者为第一服务对象”为最高校验锚点；
2. 每篇规范必须归属到六类构成要素之一，或说明自己如何服务这些构成要素；
3. 事实源是底层原则，不得被规范结构、附件、工具输出、派生投影或页面状态替代；
4. 知识地图是规范结构的派生机制和实现方法，不是独立事实源、独立构成要素或工作对象；
5. 每篇规范及其下属机制必须接受 V1-V10 准入判断。

01 只定义规范体系共同遵守的治理规则。知识地图输入契约由规范身份、章节、引用、附件授权和消费关系派生，不构成 01 的并列主题。各规范的存在性、职责、拆分方式、附件需求和迁移归口，必须回到原文逐篇核对后由对应规范自行声明。

## 3. 适用范围与事实源边界

本文适用于三类对象：

1. v2 写作区中的规范；
2. 经 Human 单篇确认后进入 active 的 LDVH 正式规范；
3. 被主规范授权的附件、注册表、矩阵、模板、示例和长清单。

`specs-v2/` 是 v2 写作区。切换 active 前，其中的规范用于方案核对、迁移计划、结构试写和知识地图解析，但不得替代当前 active `specs/`。AI 执行 active 规则、Code 默认校验、Rules 入口加载和事实源回写判断时，仍应以当前 active `specs/` 为准。

迁移来源、研究材料、审计追溯、工具输出、环境观察和聊天过程都不能直接成为正式规范依据。稳定结论必须吸收到 active 规范、对应事实模型、行动编排、ADR、WorkCase、Spark、Pitfall 或其他明确事实源后，才形成可执行事实。

## 4. 规范身份与元信息契约

### 4.1 规范文件命名与编号

v2 规范文件名必须让 AI 在目录视图中先判断文件性质，再决定是否读取正文。

根规范命名采用：

```text
{两位编号}-{规范名称}.md
```

附件命名采用本文 §9 的 `{父编号}.Att.{两位序号}-{名称}.md`。专题成员规范是否使用独立区段、独立编号或专属成员身份块，由所属构成要素实践在自身规范中声明；01 不预设专题成员的最终编号段。

规范编号用于表达规范在规范体系中的读取入口、权威归口和体系位置，不用于表达文件创建时间。新增、删除、重命名、合并、拆分或重排规范编号前，必须先判断：

1. 是否符合 00 的存在理由、AI 第一服务对象和 V1-V10；
2. 是否改变某个构成要素实践的权威归口；
3. 是否需要读取 active 原文确认旧规则边界；
4. 是否会破坏 Code、Web、运行时扩展或知识地图的既有消费入口；
5. 是否触发 Human Gate。

编号计划、迁移计划、目录草案和知识地图派生结果不能替代 active 原文。对现有规范做迁移、改名、改号或改归口判断时，必须逐篇读取原文，确认其真实职责、事实源边界、引用关系和 Code 消费入口。

### 4.2 v2 规范身份块

每篇 v2 规范必须在一级标题之后、正文第一章之前提供 `v2_spec`。该身份块用于让 AI、Code 和知识地图在不阅读全文时先判断规范身份、状态、范围、关系和迁移风险。

`v2_spec` 字段契约如下：

| 字段 | 出现要求 | 含义 |
|---|---|---|
| `spec_id` | 必须出现 | 规范编号，必须与文件名编号一致 |
| `spec_kind` | 必须出现 | 规范类型，例如 `spec`、`member_spec` |
| `title` | 必须出现 | 规范标题，必须与一级标题一致 |
| `status` | 必须出现 | 状态，例如 `draft`、`notes`、`stub`、`active` |
| `authority` | 必须出现 | 权威状态；v2 切换前应为 `not_active_until_human_approved` |
| `canonical_path` | 必须出现 | 当前文件路径，必须与真实路径一致 |
| `created` | 必须出现 | 创建日期，格式为 `YYYY-MM-DD` |
| `updated` | 必须出现 | 最近正文变更日期，格式为 `YYYY-MM-DD`，不得早于 `created` |
| `parent_spec` | 必须出现 | 父规范路径；无父规范时使用空字符串 |
| `relation` | 必须出现 | 与父规范的关系；无父规范时使用空字符串 |
| `positioning` | 必须出现 | 本规范定位 |
| `scope` | 必须出现 | 本规范适用范围 |
| `basis` | 必须出现 | 上位依据；无上位依据时使用空列表 |
| `related_specs` | 必须出现 | 相关规范；无相关规范时使用空列表 |
| `migration_sources` | 必须出现 | 迁入、吸收或参考的来源；无来源时使用空列表 |
| `active_fact_source` | 必须出现 | 当前 active 事实源；无 active 对应物时使用空列表并在待补齐事项说明 |
| `code_consumption` | 必须出现 | Code 或知识地图消费的字段、关系、结构或诊断入口 |
| `migration_status` | 必须出现 | 迁移状态，例如 `not_migrated`、`partially_migrated`、`ready_for_review` |

普通正文头部不得重复维护 `v2_spec` 已承载的身份事实。若 v2 规范身份块与文件名、标题、路径或正文范围冲突，应先修正身份块或文件结构，再继续讨论正文内容。

### 4.3 active 身份块

v2 未切换为 active 前，当前正式规范仍使用 active `specs/` 中的 `ldvh_doc`。v2 规范进入 active 时，应保留一个稳定的 active 身份块，用于承载编号、类型、标题、状态、路径、定位、范围、依据、相关规范和 Code 消费入口。

active 身份块至少需要保持以下能力：

1. 编号、标题、路径和状态可被 Code 确定性校验；
2. 上位依据、相关规范、父规范和附件授权可派生为知识地图边；
3. `positioning` 与 `scope` 能让 AI 判断读取价值和权威范围；
4. `code_consumption` 能说明 Code、Web、运行时扩展或知识地图读取哪些结构；
5. 迁移到 active 时，能追溯来源、active 事实源和 Human 确认记录。

现有 `ldvh_doc` 字段名和枚举在迁移前仍是 Code 默认入口。v2 如果调整 active 身份块字段，应先定义双读兼容、迁移策略、正反样例和降级诊断，不得让 Code 只能把 v2 规范当作解析失败处理。

## 5. 正式规范必要章节

除 00 总纲外，正式规范必须至少具备以下结构：

1. 一级标题；
2. 规范身份块；
3. `## 1. 本文解决的问题`；
4. 与 00 的关系、上位依据或等价承接章节；
5. 核心规则章节；
6. `规范保障要求`；
7. `Human Gate`；
8. `AI 检查要求`；
9. `待补齐事项`。

00 是顶层总纲，可以使用产品存在理由或总纲叙事标题，不强制把第一章命名为 `本文解决的问题`。其他正式规范不得借 00 例外省略自身的必要章节。

正式规范正文采用当前有效规则态写法。正文只定义当前生效的规则、契约、流程、边界和状态判定方法；历史迁移、旧编号、旧文件名、执行结果、环境观察和过程状态应进入 Git history、ADR、WorkCase、Spark、Pitfall、研究材料或对应事实源。

章节标题应使用可解析的阿拉伯数字层级编号。正文对章节的引用应使用 `§N`、`§N.N` 或等价稳定锚点；正文路径引用应指向真实存在的文件。

职责边界应通过定位、适用范围、上位依据、相关规范、权威归口和正向规则表达。正式规范不设置专门的反向边界章节；需要说明不承载的内容时，应同时指明由哪个权威归口或待补齐事项承接。

## 6. 权威域、定义归口与吸收规则

一条稳定规则只能有一个最小权威归口。AI 新增或修改规范内容时，应先判断该内容回答的问题，再写入最小权威归口：

| 问题类型 | 最小权威归口 |
|---|---|
| LDVH 为什么存在、AI 第一服务对象、价值判断 | 00 总纲 |
| 规范体系、规范身份、必要章节、附件、知识地图输入、引用纪律 | 01 |
| 术语、推荐表达、不推荐表达处理 | 01 正文和 `01.Att.02-术语表与表达清单.md` |
| 事实源、证据、回写边界 | 事实源规则的 active 归口；本文不预设编号 |
| 保障要求、能力保障、环境适配 | 对应构成要素实践或保障机制的 active 归口；本文不预设编号 |
| 事实模型、字段契约、状态机、对象关系 | 事实模型的 active 归口；本文不预设成员编号 |
| 行动编排、Context、Scenario、Gate、执行、暂停、交还 | 行动编排的 active 归口；本文不预设成员编号 |
| Code 解析、校验、聚合、诊断和反馈 | Code 的 active 归口；本文不预设实现入口 |
| Web 展示、Human 可见状态、确认入口 | Web 的 active 归口；本文不预设实施阶段 |
| Git 提交、变更追溯、历史证据 | 事实源、行动编排或 Git 追溯规则的 active 归口；本文不预设编号 |
| 测试、验证、回归和验收证据 | 对应构成要素实践或验证规则的 active 归口；本文不预设编号 |

引用另一个规范不自动改变权威归口。被引用、被消费、被展示、被工具读取或被附件登记的规范，不因为下游使用而反向承担下游规则、同步义务或实现细节。

迁移来源、研究材料、外部资料和工具输出中的稳定结论，必须吸收到最小权威归口后才生效。吸收不得只通过引用路径完成；被采纳的规则、字段、状态、流程、保障要求或检查要求必须在权威归口正文中明确写出。

## 7. 术语治理与表达纪律

术语治理属于规范体系治理。01 正文定义术语归口、变更边界和表达纪律；`01.Att.02-术语表与表达清单.md` 承载术语条目、推荐表达、不推荐表达和替代写法。

术语本体定义与对象规则定义应区分处理：

1. 术语本体定义回答“这个名称在 LDVH 中是什么意思、边界是什么、推荐怎么称呼”，归口 01 和术语表附件；
2. 对象规则定义回答“某个事实模型、行动编排、字段、状态、流程、Code、Web 或运行时扩展在自身规范中如何构成、如何约束、如何执行”，归口对应构成要素实践；
3. 非术语归口规范可以说明某个术语在本规范中的应用关系，但不得重新定义术语本体、同义词、包含关系或替代表达；
4. 若发现术语缺失、术语边界不足、不推荐表达残留或术语需要改名，应先回到 01 和 `01.Att.02` 处理，再同步相关规范或 Code 检查；
5. 术语表附件中的条目不得把字段契约、状态机、流程 Gate、事实源边界或环境适配细则写成术语定义。

术语应用关系应使用“术语 / 本规范应用关系”或等价表格，说明该术语在当前规范中的承载、消费、约束或检查方式。说明句式应使用“在本规范中用于……”“由……消费”“与……区分”“不得用于……”等应用口径，不得写成“X 是……”“X 指……”“X 定义为……”等二次定义。

术语新增、改名、废止或改变边界前，应检查：

1. 是否影响 00 的存在理由、AI 第一服务对象、六类构成要素、事实源底层原则或 V1-V10；
2. 是否影响规范身份、附件授权、知识地图关系、引用纪律或 Code 消费入口；
3. 是否影响事实模型、行动编排、Code、Web、运行时扩展、事实源、Git 追溯或测试验证规则；
4. 是否需要同步 `01.Att.02`、相关规范、Code 术语检查、知识地图关系和 Web 展示；
5. 是否触发 Human Gate。

## 8. 引用关系与知识地图输入

知识地图与规范强耦合。v2 不把知识地图放在规范体系之外维护，也不为目录说明另设独立上位规范。知识地图由规范身份、章节锚点、权威归口、迁移来源、引用关系、附件授权、消费关系、Code 校验结果和 Git 可追踪事实源实时派生。

知识地图的基本输入如下：

| 输入 | 派生结果 | 要求 |
|---|---|---|
| `v2_spec` 或 active 身份块 | 规范节点 | 必须能回指路径、标题、编号、状态和事实源 |
| H2-H4 章节标题 | 章节节点或章节锚点 | 必须可解析、可引用、可定位行号 |
| `basis` | 上位依据边 | 只能指向真实承接的上位原则 |
| `related_specs` | 相关规范边 | 只登记读取依赖、同步依赖、字段依赖或检查依赖 |
| `migration_sources` | 迁移来源边 | 只说明迁入、吸收或参考来源，不授予 active 权威 |
| `active_fact_source` | active 事实源边 | 用于避免写作区内容替代当前正式规则 |
| `parent_spec` / `relation` | 父子或附件授权边 | 必须能判断从属关系和授权范围 |
| 正文路径引用 | 路径引用边 | 不得把导航引用升级为上位依据 |
| 正文 `§` 引用 | 章节引用边 | 必须能回指目标章节 |
| `code_consumption` | 消费边 | 说明 Code、Web、运行时扩展或知识地图读取目的 |

关系类型的详细表放入 `01.Att.01-知识地图关系类型表.md`。01 正文定义最小闭集：`basis`、`related`、`parent`、`derives_from`、`consumes`、`validates`、`renders`、`writes_to`、`owns_attachment`、`gated_by`、`impacts`。附件可以扩展示例和判定口径，但不得单独改变关系原则。

知识地图输出只用于定位、最小读取、影响判断、诊断回指和派生展示。它不得替代规范正文、成员主文件、附件授权、Code 校验原始结果或 Git 文件事实源。

## 9. 附件规则

附件是主规范授权的附属文件，不是常规子规范体系。附件只承载主规范授权的注册表、矩阵、模板、示例、长清单或其它不适合放入主文的辅助材料。

术语表、表达清单、字段注册表和关系类型表可以作为附件存在。此类附件承载条目、清单和判定辅助信息；条目治理规则、字段存在性、关系原则和权威边界仍必须留在授权主规范正文中。

附件命名采用：

```text
{父编号}.Att.{两位序号}-{名称}.md
```

附件应与父规范位于同一层级，不默认放入子文件夹。附件在结构上必须由父规范授权，在生效上必须随父规范经过 Human 单篇确认；父规范未确认时，附件不得独立成为 active 规范依据。

附件必须提供 `v2_attachment` 或等价身份块：

| 字段 | 出现要求 | 含义 |
|---|---|---|
| `attachment_id` | 必须出现 | 附件编号，必须与文件名一致 |
| `title` | 必须出现 | 附件标题，必须与一级标题一致 |
| `status` | 必须出现 | 状态 |
| `authority` | 必须出现 | 权威状态；v2 切换前应为 `not_active_until_parent_and_human_approved` |
| `parent_spec` | 必须出现 | 授权父规范路径 |
| `canonical_path` | 必须出现 | 附件真实路径 |
| `purpose` | 必须出现 | 附件用途 |
| `migration_sources` | 必须出现 | 迁移来源；无来源时使用空列表 |
| `code_consumption` | 必须出现 | Code 或知识地图消费该附件的方式 |

附件不得承载需要主规范确认的核心原则、权威域、状态机、字段存在性、流程 Gate、资产登记机制或事实源边界。若附件内容开始承担这些职责，应回到父规范正文处理。

## 10. 专题成员与专属骨架规则

某些规范域可以拥有成员集合或专属骨架。成员集合不是目录清单，也不是派生索引本身；成员主文件必须声明自己的成员身份、状态、路径、锚点和 Code 消费入口，Code 与知识地图只能消费这些事实并生成派生视图。

专题规范可以定义本专题成员文件的专属骨架、成员自描述字段、状态判定、章节锚点和 Code 消费入口，但必须在所属主规范或成员主文件中显式声明。

01 只定义声明方法和治理边界，不预设任何专题的必需章节、字段、状态机、流程 Gate、实例目录或执行步骤。专题专属骨架必须说明：

1. 适用范围；
2. 必需章节；
3. 可不适用章节的说明方式；
4. 成员自描述字段；
5. 派生索引回指方式；
6. Human Gate；
7. 检查入口。

成员自描述属于成员主文件事实源，不得放入附件、派生索引、普通头部或 Code 输出中独立维护。Code、Web 和知识地图可以消费这些结构，但输出只能作为导航、诊断或展示，不能替代成员主文件。

## 11. 规范保障要求

正式规范必须设置 `规范保障要求` 章节。该章节用于说明当前规范中哪些要求需要被入口、流程、Code、Web、运行时扩展、环境适配或人工降级检查保障。

规范保障要求表采用以下最小结构；保障类型枚举和接管机制由经单篇核对确认的 active 归口承接：

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 规范结构可解析要求 | 规范应声明身份、必要章节、引用关系、附件授权和待补齐事项 | 01、Code 解析、人工降级检查 | 规范治理 | 新增、修改、拆分、合并、重命名或迁移 v2 规范时 |
| 术语治理要求 | 术语定义、推荐表达、不推荐表达和替代写法应由 01 与术语表附件统一承接 | 01、术语表与表达清单、Code 术语检查、人工降级检查 | 术语治理 | 术语新增、改名、废止、边界变化或不推荐表达处理变化时 |
| 知识地图回指要求 | 知识地图节点、边和诊断必须回指规范、章节、附件或事实源 | 01、知识地图关系类型表、Code 解析 | 派生机制 | 关系类型、身份块字段、附件规则或 Code 派生输出变化时 |
| 迁移兼容要求 | v2 未切换前不得破坏 active `ldvh_doc`、成员自描述和现有 Code 默认入口 | active v1 校验、v2 解析、双读兼容计划 | 迁移治理 | v2 身份块、章节骨架、成员机制或 Code 校验入口变化时 |

保障要求的类型枚举、环境适配、能力保障和接管机制由后续经单篇核对确认的 active 归口承接。01 只要求正式规范具备该章节和最小可解析结构，不预设这些机制归入哪个编号。

## 12. Human Gate

以下情况应评估 Human Gate：

1. 将任一 v2 规范切换为 active；
2. 改变正式规范必要章节；
3. 改变身份块字段、状态枚举、路径规则或 Code 消费入口；
4. 新增、删除、重命名、合并或拆分规范；
5. 改变附件命名、附件授权或附件权威边界；
6. 改变术语归口、核心术语边界、推荐表达或不推荐表达处理；
7. 改变知识地图关系类型、派生规则或回指规则；
8. 改变专题成员自描述、成员状态判定、专属骨架或派生索引边界；
9. 将 active 规范迁移、改名、改号、合并、拆分或改变归口；
10. 将迁移来源、研究材料、工具输出、环境观察或聊天过程升级为正式规范依据；
11. 接受 Code 检查缺口、长期降级或无验证迁移。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 自检、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。

## 13. AI 检查要求

规范治理检查至少包括：

| 检查项 | 标准 |
|---|---|
| 身份块 | 字段完整，编号、标题、路径、状态和日期一致 |
| 上位依据 | 上位依据真实承接，不把导航引用写成依据 |
| 事实源边界 | v2 写作区、active 事实源、研究材料和工具输出边界清晰 |
| 必要章节 | 正式规范具备本文 §5 的必要章节 |
| 权威归口 | 稳定规则写入最小权威归口 |
| 术语治理 | 术语定义、推荐表达和不推荐表达进入 01 与术语表附件；其他规范只说明应用关系 |
| 引用关系 | 关系类型按最低充分级别使用，未反向补全下游义务 |
| 附件授权 | 附件由父规范授权，不承载主原则 |
| 专题骨架 | 成员集合和专属骨架由所属主规范或成员主文件声明 |
| 规范保障要求 | 章节存在，表头和保障内容可解析 |
| Code 适配 | 现有检查能力、缺口、降级方式和残留风险已说明 |

AI 检查要求用于发现结构缺口、事实源风险、引用错误、术语漂移和 Code 覆盖不足。检查结论只能作为诊断、待确认事项或 Human Gate 输入，不能替代 Human 确认。

### 13.1 Code 覆盖、缺口与降级

Code 检查是 AI 检查要求中的确定性检查方式，不是 Human Gate，也不是每篇规范的独立必备章节。01 因定义规范身份、章节锚点、引用关系、附件身份和知识地图输入，需要说明 Code 可以消费哪些结构，以及没有 Code 覆盖时如何处理缺口。

Code 应优先消费规范中的结构化身份块、章节锚点、引用关系、附件身份、成员自描述和保障要求表，生成派生索引、知识地图、诊断和最小读取建议。

v2 解析至少应输出：

1. 规范节点；
2. 章节节点或章节锚点；
3. 关系边；
4. 附件授权边；
5. 迁移来源和 active 事实源回指；
6. `content_hash`；
7. `line_start` / `line_end`；
8. `parse_status`；
9. `diagnostics`；
10. `review_hints`。

v2 未切换前，Code 默认校验仍以 active `specs/` 的 `ldvh_doc`、`ldvh_member`、固定章节、保障表和现有派生索引结构为准。v2 解析在切换前只能作为诊断和迁移辅助，不得替代 active 校验。v2 解析输出的最终 Schema 由后续 Code 规范单篇确认；01 只定义规范结构需要被 Code 读取和回指的最小方向。

当规范提出的检查要求尚无 Code 覆盖时，应记录 Code 缺口、人工降级方式、正反样例需求和残留风险。缺口未处理前，不得声称该结构已被完整确定性校验。
