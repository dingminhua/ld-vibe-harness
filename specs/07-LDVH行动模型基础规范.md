## 三、行动模型的定义与定位

### 3.1 行动模型的定义

LDVH 行动模型是 LDVH 对 AI 在项目中如何行动的执行控制建模，通过定义 Context（AI 行动前应获得的最小可行动上下文）、Scenario（AI 如何识别当前任务场景）、Gate（AI 何时必须暂停并请求人确认）、规则适用、Skill 进入、Agent 调度和事实源回写等内容，约束 AI 的执行行为，确保 AI 稳定、可控地工作。

### 3.2 行动模型的核心特征

行动模型必须具备以下核心特征：

1. **以 AI 为中心**：行动模型以 AI 执行者为第一服务对象，信息组织方式、事实源读取、场景识别、工具选择等首先满足 AI 的需求；
2. **基于事实源**：行动模型依赖 Git 文件事实源，不依赖聊天记忆、工具缓存或数据库派生视图；
3. **Human Gate 优先**：关键行动必须触发 Human Gate，等待人类确认后方可继续；
4. **证据留存**：AI 执行的每个关键步骤都必须留下可追溯的证据；
5. **事实回写**：AI 完成执行后必须按事实源边界把稳定事实写回项目。

### 3.3 行动模型与自由执行的区别

| 维度 | 自由执行 | 行动模型约束下的执行 |
|---|---|---|
| 上下文来源 | 聊天记忆、临时信息 | Git 文件事实源、结构化 Context |
| 场景识别 | 凭感觉、无明确规则 | 按 Scenario 规则明确识别 |
| 约束机制 | 无明确约束 | 规则、Gate、状态机多重约束 |
| 人类确认 | 随意、无明确触发点 | Human Gate 明确触发条件 |
| 证据留存 | 无强制要求、仅聊天记录 | 必须按规范留存可追溯证据 |
| 事实回写 | 随意、可能不回写 | 必须按事实源边界回写 |
| 可追溯性 | 弱、仅聊天历史 | 强、Git 文件事实源 + 结构化证据 |

## 四、行动模型的核心组件

### 4.1 Context（上下文）

Context 是由事实源组织出的 AI 执行输入、任务背景和行动依据。

#### 4.1.1 Context 的目标

Context 的目标是给 AI 提供足够但不过载的最小可行动上下文，让 AI 能够：
1. 理解当前项目的身份和边界；
2. 理解当前任务的背景和目标；
3. 知道可用的规则、Skill 和 Agent；
4. 知道事实源的边界和回写位置；
5. 知道何时触发 Human Gate。

#### 4.1.2 Context 的类型

Context 分为以下类型：
1. **项目初始化 Context**：AI 进入项目时首先读取的上下文；
2. **任务执行 Context**：AI 执行任务时读取的上下文；
3. **需求规划 Context**：AI 进行需求规划时读取的上下文；
4. **Review Context**：AI 进行 Review 时读取的上下文；
5. **审计 Context**：AI 进行审计时读取的上下文。

#### 4.1.3 Context 的组织原则

Context 的组织遵循以下原则：
1. **最小化原则**：只包含 AI 执行当前任务所需的最小信息，避免信息过载；
2. **结构化原则**：以结构化方式组织，便于 AI 理解和处理；
3. **事实源原则**：所有信息都来自 Git 文件事实源，不依赖聊天记忆；
4. **动态原则**：根据当前 Scenario 动态调整 Context 内容。

### 4.2 Scenario（场景）

Scenario 是 AI 当前所处的任务类型、协作模式和执行入口。

#### 4.2.1 Scenario 的目标

Scenario 的目标是让 AI 能够：
1. 识别当前任务属于什么类型；
2. 选择合适的执行入口；
3. 加载对应的规则和 Context；
4. 调用合适的 Skill 和 Agent。

#### 4.2.2 Scenario 的类型

Scenario 分为以下类型：
1. **初始化场景**：AI 进入项目，初始化 LDVH；
2. **需求规划场景**：AI 理解需求，规划任务；
3. **任务执行场景**：AI 执行具体任务；
4. **Review 场景**：AI 审查执行结果；
5. **审计场景**：AI 审计项目状态；
6. **修复场景**：AI 修复问题或错误。

#### 4.2.3 Scenario 的识别原则

Scenario 的识别遵循以下原则：
1. **基于事实源**：根据 Git 文件事实源中的内容识别当前场景；
2. **明确规则**：每个场景都有明确的识别规则；
3. **优先级**：多个场景同时匹配时，按优先级选择；
4. **Human Gate**：场景切换可能触发 Human Gate。

### 4.3 Gate（门禁）

Gate 是需要人确认或满足条件后才允许继续的控制点。

#### 4.3.1 Gate 的类型

Gate 分为以下类型：
1. **Human Gate**：必须由人类确认后方可继续；
2. **条件 Gate**：满足特定条件后方可继续；
3. **审批 Gate**：必须由特定角色审批后方可继续。

#### 4.3.2 Human Gate 的触发条件

以下情况必须触发 Human Gate：

**通用 Human Gate**：依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §七、`specs/01-specs文档结构规范.md` §八、`specs/02-LDVH目录说明.md` §五、`specs/03-事实源边界与承载规范.md` §九、`specs/04-LDVH-AI协作规范.md` §八 及 L1 项目规则中定义的 Human Gate 条件执行，本文不重复维护。

**行动模型 Human Gate**：以下情况由行动模型定义，是本文对 Human Gate 触发条件的补充：

1. **关键状态流转**：如 Task 从 Review Needed 到 Closed；
2. **高风险操作**：如删除重要文件、修改核心规范；
3. **跨项目影响**：影响多个项目的操作；
4. **AI 不确定**：AI 不确定该如何操作时。

#### 4.3.3 Gate 的执行原则

Gate 的执行遵循以下原则：
1. **先停再问**：识别到 Gate 时，AI 必须先暂停执行，再请求人类确认；
2. **明确说明**：AI 必须明确说明触发 Gate 的原因、影响范围和建议确认事项；
3. **不可绕过**：AI 不得绕过 Gate 继续执行；
4. **证据留存**：Gate 的确认过程必须留下可追溯的证据。

### 4.4 规则适用

规则是 AI、人和工具必须遵守的行为边界。

#### 4.4.1 规则的类型

规则分为以下类型：
1. **LDVH 基础规则**：由 specs/01-07 定义，适用于所有接入 LDVH 的项目；
2. **项目规则**：由项目的 .trae/rules/ 定义，仅适用于该项目；
3. **对象规则**：由生产对象规范定义，适用于该对象的操作。

#### 4.4.2 规则的加载原则

规则的加载遵循以下原则：
1. **优先级**：项目规则优先于 LDVH 基础规则；
2. **不冲突**：规则之间不得冲突，冲突时按优先级处理；
3. **可追溯**：规则必须有明确的来源和版本；
4. **Human Gate**：规则变更必须触发 Human Gate。

### 4.5 Skill 进入

Skill 是 AI 可使用的可复用流程。行动模型可以在具体场景中说明何时建议进入 Skill，但 Skill 的准入、命名、部署、输出和事实源回写边界由 `specs/04-LDVH-AI协作规范.md` 和 `specs/04.02-Skill机制规范.md` 定义。

Skill 进入在行动模型中的通用原则：
1. **场景匹配**：根据当前 Scenario 判断是否需要可复用流程；
2. **机制回指**：Skill 准入和边界必须回指 04 系列规范；
3. **规则约束**：Skill 的执行必须遵守规则、事实源边界和行动模型；
4. **Human Gate**：关键 Skill 的进入或写入动作必须按对应规范评估 Human Gate；
5. **证据留存**：Skill 产生的稳定事实必须回写到 Git 文件事实源后才成为稳定事实。

### 4.6 Agent 调度

Agent 是 AI 代理执行能力。行动模型可以在具体场景中说明何时建议调度 Agent，但 Agent 的创建、调用、定义摘要、生命周期、权限边界和事实源回写边界由 `specs/04-LDVH-AI协作规范.md` 和 `specs/04.03-Agent机制规范.md` 定义。

Agent 调度在行动模型中的通用原则：
1. **场景匹配**：根据当前 Scenario 判断是否需要独立上下文、结论隔离、并行委派或不同权限边界；
2. **机制回指**：Agent 创建或调用治理条件必须回指 04 系列规范；
3. **规则约束**：Agent 的执行必须遵守规则、事实源边界和行动模型；
4. **Human Gate**：关键 Agent 的创建、调度、权限调整或写入动作必须按对应规范评估 Human Gate；
5. **不替代事实源**：Agent 不得成为事实源，只能读取、分析和建议。

### 4.7 事实源回写

事实源回写是 AI 完成执行后把稳定事实写回项目的过程。

#### 4.7.1 事实源回写的原则

AI 完成执行后的事实源回写，依据 `specs/03-事实源边界与承载规范.md` §七定义的回写条件执行，本文不重复维护。行动模型的适配说明如下：

1. **行动模型回写触发**：AI 按 Scenario 执行完毕后，应判断执行结果是否包含稳定事实；若包含，必须按 03 §七回写；
2. **回写与 Gate 联动**：关键事实的回写应评估 Human Gate，依据本文 §4.3.2 行动模型 Human Gate 条件判断。

#### 4.7.2 事实源回写的内容

事实源回写的内容包括：
1. **Task 状态更新**：更新 Task 的状态、完成摘要、验证结果、关闭证据等；
2. **新对象创建**：创建新的生产对象实例（如 Memo、ADR、Change 等）；
3. **规则更新**：更新规则（如需要）；
4. **文档更新**：更新项目文档（如需要）。

## 七、Human Gate 与检查要求

### 7.1 Human Gate 触发条件

以下情况应评估 Human Gate：
1. 新增行动；
2. 删除行动；
3. 重命名行动；
4. 重排行动编号区段；
5. 改变行动模型的通用规则；
6. 改变 Context、Scenario、Gate 的定义；
7. 改变事实源回写的原则；
8. 改变 Human Gate 的触发条件。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 7.2 检查要求

行动模型规范写作检查至少包括：
| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 行动定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、生产对象和行动模型术语一致 |
| 事实源边界 | 符合 `specs/03-事实源边界与承载规范.md` 的事实源边界原则 |
| Human Gate | 明确触发条件，确保关键步骤必须等待人类确认 |
