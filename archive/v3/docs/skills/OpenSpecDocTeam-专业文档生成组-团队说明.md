## 1. 先定边界（关键）

你现在遇到的“团队化”场景其实不是换了新模型，而是命中 **OpenSpecDocTeam** 的标准工作流。

### 1.1 团队身份判断

- **是否是独立专家**：否（这是一个团队/方法）
- **是否有固定角色分工**：是
- **是否可并行替代个人创作**：否。它本质是“主理人 + 3 名成员”协同闭环

### 1.2 产出目标

- 快速把“写作型任务”切成可复用阶段
- 保证每章可追溯（有检索→生成→审核）
- 通过一致性约束降低手工返工

## 2. 团队结构与角色

### 2.1 角色清单

| 角色 | Agent ID | 定位 | 典型职责 |
|---|---|---|---|
| 主理人（总编辑） | `doc-team-lead` | 项目统筹与编排 | 需求分析、流程选型、参数卡维护、最终汇编 |
| 检索员 | `doc-researcher` | 证据聚合 | 生成检索报告、来源与相关度标注、缺口说明 |
| 生成员 | `doc-generator` | 章节写作 | 按模板/要求输出正文、并回传可审核稿 |
| 审核员 | `doc-auditor` | 质量控制 | 6 维度审稿、问题清单、PASS/REVISE |

### 2.2 与 UI/Content 专家的关系

- `OpenSpecDocTeam` 专注 **流程正确性** 与 **协作一致性**。
- `UI Designer` / `Content Creator` 等独立专家提供内容知识结构与领域风格。
- 可理解为：
  - 团队给出“怎么产出”；
  - 专家给出“按其能力输出什么”。

## 3. 触发条件与执行模式（路由）

### 3.1 触发条件

- 用户要求“写文档/生成说明书/补写章节/按模板写”
- 用户要求“审稿/查缺口/分析当前专家团队”
- 用户提到要按“固定流程”完成文档任务

### 3.2 A-F 流程映射

| 用户意图 | 推荐流程 | 核心动作 |
|---|---|---|
| 单一维度“帮我写一篇…” | Workflow A（完整长文档） | 主理人拆分章节并驱动检索→生成→审核 |
| 按模板填充 | Workflow B | 保留模板结构，逐项检索/生成/审核 |
| 补写某一章/重写章节 | Workflow C | 仅该章节走闭环 |
| 只审稿 | Workflow D | 只调用审核员 |
| 要求草稿、不要审核 | Workflow E | 跳过审核，附风险提示 |
| 文档章节多、要求加速 | Workflow F | 并行检索/生成后统一汇总 |

## 4. 工作流闭环（最小可执行版）

### 4.1 阶段总览（Phase 1-6）

1. **需求分析**：定义目标、范围、质量要求、参数约束
2. **知识检索**：按章检索来源、关联、规范和案例
3. **内容生成**：按检索输入生成章节草稿
4. **质量审核**：逻辑、完整性、参数、格式、跨章一致性
5. **整合汇编**：统一目录、术语、编号、待完善事项
6. **交付输出**：含待确认项与风险边界说明

### 4.2 统一硬性规则

- 无来源不得硬写；信息缺口统一写 `[待填写]`
- 规范引用需统一引用格式（避免虚构）
- 每轮不通过允许最多 2 次修订，第三轮可进入“强制通过 + 警告”
- 角色不越界：主理人不代写正文，审核员不直接重写正文
