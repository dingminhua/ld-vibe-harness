## 1. 本文解决的问题

本文用于把 v2 00 的上位原则锚定到两个问题：LDVH 为什么存在，以及为什么 AI 执行者是第一服务对象。后续章节只围绕这两个问题展开，不新增与其并列的价值来源。

本文解决：

1. LDVH 要解决的 Vibe Coding 持续演进失控问题；
2. AI 执行者的依赖、能力与本质如何决定 LDVH 的设计重点；
3. 六类构成要素如何共同支撑 AI 启动有序少读、推理有据少猜、行止有规可依、结果有证可验；
4. 事实源为什么是贯穿六类构成要素的底层权威原则，而不是第七类构成要素；
5. V1-V10 如何判断新增机制是否真正减少 AI 的定位、理解、判断、执行、验证和回写负担；
6. 什么样的规则、对象、字段、附件、工具、资产承载物或派生机制不应成为构成要素实践。

本文只定义上位原则和价值判断，不定义规范结构、字段契约、行动流程、Code 输出 Schema、Web 页面规则、Git 提交格式或具体环境适配规则。

## 2. LDVH 为什么存在

Vibe Coding 让人用自然语言表达目标，AI 推理生成实现——门槛低，反馈快，产出多，但 AI 生成代码的本质不是确定性编译，而是基于开发环境组织的上下文、结合模型训练经验和参数进行的概率性推理——因此天生带有概率性推理、上下文依赖和无状态三大硬伤。

虽然目前，Vibe Coding 已经能够较好完成单个功能、局部修复，也能在明确测试目标和验收反馈下承担较长时间的连续工作。但是，真实开发往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是如何在项目持续演进中，避免项目从“开始还不错”逐渐变成“难以继续做”的问题。

它的方法，是以规范文档定义产品、明确要求，以 AI 推理生成实现、实现回流，以事实模型承载工作事实、沉淀记忆，以行动编排驱动执行、监督闭环，以 Code 提供确定性执行、稳定结果，以 Web 桥接 Human 与 AI、协调认知——进而让 Vibe Coding 更高效、更稳定、更可控。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于实践沉淀而来，简称为 LDVH。

## 3. 以 AI 执行者为第一服务对象

LD Vibe Harness 以 AI 执行者为第一服务对象，通过深入理解 AI 执行者的依赖、能力与本质，依托开发环境构建可实现的方法与机制，为 AI 提供有力支撑，推动 AI 更稳定地输出，最终形成可持续的产品闭环。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——没有可用工具时，AI 只能停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的环境工具、Code、Skill 或 Agent，并把工具反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

基于这些依赖、能力与本质，LD Vibe Harness 的设计重点，不是要求 AI 自发变得可靠，而是：

1. 用规范体系，组织稳定事实、关联信息、明确边界和可见状态，为 AI 的目标推导、场景识别、行动判断与验收标准生成提供依据，减少 AI 对聊天记忆、隐含上下文和主观猜测的依赖；

2. 用事实模型，为 AI 的目标、工作项、决策、经验、必要执行状态和证据沉淀建立对象化承载、字段契约与状态秩序，使 AI 做出的稳定结论、验证依据、关闭判断和经验分流能够被追溯；事实源修改追溯由 Git 提交记录承接；

3. 用行动编排，为 AI 的上下文读取、工作规划、执行推进、验证关闭、风险暂停和事实回写提供行动路径、约束和停顿机制，使 AI 知道该读什么、怎么做、何时停下、完成后写回哪里；

4. 用 Code，为 AI 的解析、索引、聚合、校验、测试、上下文压缩和受控写入提供确定性反馈，减少 AI 的跨文档读取负担、判断负担和验证成本；

5. 用 Web，为 AI 与 Human 之间的状态可见、风险呈现、待确认事项、验收判断和方向校正提供 Human-facing 桥接，使 Human 能及时看见 AI 的方向、风险和待决策点，并给出明确修正与决策；

6. 用运行时扩展，对接上述规范、模型、流程、Code 和 Web 的内部运行需求，为入口可见、规则加载、流程复用、Agent 调度和工具调用提供能力保障，并提供面向不同 AI 协作环境的适配措施，使 LDVH 能被看见、被触发和被执行。

通过这些支撑，让 AI 启动有序少读、推理有据少猜、行止有规可依、结果有证可验，使 AI 的概率性、上下文依赖和无状态风险被结构化约束。

## 4. 六类构成要素

LDVH 由六类构成要素共同形成 AI 工程驾驭体系。六类构成要素不是第 2 节和第 3 节之外的新体系，而是第 3 节六个支撑方向的归口化表达：

| 构成要素 | 定位 | 回答的问题 |
|---|---|---|
| 规范体系 | 上位原则、边界和价值判断 | 如何组织稳定事实、关联信息、明确边界和可见状态，支撑 AI 的目标推导、场景识别、行动判断和验收标准生成 |
| 事实模型 | 工程工作事实建模 | 如何为目标、工作项、决策、经验、必要执行状态和证据沉淀建立对象化承载与状态秩序 |
| 行动编排 | AI 执行控制建模 | 如何约束 AI 的上下文读取、工作规划、执行推进、验证关闭、风险暂停和事实回写 |
| Code | 确定性执行、校验和上下文压缩 | 哪些稳定解析、聚合、校验、反馈和上下文压缩可由确定性工具承接 |
| Web | Human-facing 信息桥接和受控交互 | 如何让 Human 看见状态、风险、证据、待确认事项和 AI 行动方向，并完成验收判断与方向校正 |
| 运行时扩展 | 运行需求能力保障与环境适配 | 如何对接规范、模型、流程、Code 和 Web 的内部运行需求，提供入口可见、能力调用、流程复用和环境适配 |

六类构成要素不是上下层级，也不是六种同质能力。它们性质不同、归口不同，共同服务第 2 节和第 3 节定义的 LDVH 目标。

六类构成要素不是资产分类。构成要素回答 LDVH 由哪些能力面组成；资产回答这些能力面由哪些可维护承载物实现、登记、验证和适配。一个构成要素可以由多种资产共同承载，一个资产也可能服务多个构成要素。

开发环境本身不是 LDVH 构成要素，而是运行时扩展的接入与适配对象。运行时扩展的具体承载物、资产登记、验证方式和环境适配规则由后续保障机制与环境适配相关规范承接，00 不定义具体资产类型。

本文后续统一使用“运行时扩展”指代 LDVH 面向运行环境的能力保障归口；具体承载物、命名、登记和适配规则不在 00 定义。

## 5. 事实源底层原则

事实源不是第七类构成要素，而是贯穿六类构成要素的底层权威原则。它服务第 3 节中“稳定结论、验证依据、关闭判断和经验分流能够被追溯”的要求。

LDVH 中稳定事实必须回到 Git 可追踪文件。聊天过程、AI 推理过程、工具输出、运行时索引、Web 页面状态、缓存、数据库派生视图或运行时扩展输出，都不能自动成为最终事实源。

事实源原则至少包括：

1. 稳定事实必须有明确承载位置；
2. 同一事实不应长期存在多个互相竞争的权威副本；
3. 工具输出只有在写入对应权威事实源后，才可能成为稳定事实；
4. 验证证据、关闭证据、决策依据和经验沉淀必须能回指事实源；
5. 事实源修改追溯由 Git commit records 承接。

具体事实源、证据、回写、吸收和 Git 追溯规则由后续相关规范承接。本文只定义上位原则。

## 6. V1-V10 价值判断

LDVH 的六类构成要素及其下属机制，都必须服务以下价值判断中的一项或多项。V1-V10 不是独立于第 2 节和第 3 节的新目标，而是用于判断某项机制是否真的能缓解 AI 的概率性推理、上下文依赖和无状态风险。

字段、附件、资产承载物、工具、派生关系、Code 输出和 Web 展示等都不是与六类构成要素并列的准入主体。它们必须先归属到规范体系、事实模型、行动编排、Code、Web 或运行时扩展之一，再接受 V1-V10 判断。

派生机制只能作为六类构成要素的实现方法之一。它服务哪些 V 项取决于自身归属和用途，但不得成为独立价值标准、独立构成要素、事实源或工作对象；具体结构、生成、展示和消费边界由后续对应实践定义。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | AI 能否根据当前目标和场景快速定位应读取的事实源、规范入口、工作状态和工具入口 | AI 盲目全文阅读、找不到入口、遗漏关键事实或规范规则 |
| V2 | 可行动理解 | AI 能否在足够但不过载的上下文中形成可执行的目标、边界、事实、状态和验收标准理解 | AI 反复询问已有事实、误读项目边界、遗漏关键约束，或读了很多仍不能行动 |
| V3 | 正确判断 | AI 能否判断事实源边界、风险、阻塞、工具需求、流程复用需求和专项协作调度需求 | AI 误判工作性质、错过风险或阻塞、错误选择工具、流程或专项协作方式 |
| V4 | 稳定执行 | AI 能否依据规范体系、事实模型和行动编排形成可执行路径、拆解步骤并稳定推进工作，而不是凭聊天记忆自由发挥 | AI 绕过规范规则、跳过工作状态、无法形成稳定路径或直接修改不该修改的事实 |
| V5 | 门禁识别 | AI 能否识别 Human Gate，知道何时必须暂停并等待人确认 | AI 擅自执行高影响变更、跳过确认、误关闭工作对象 |
| V6 | 强制验证 | AI 的关键行动、状态变更、事实回写和交付结论能否通过 Code 校验、检查结果、审查证据、Web 呈现或 Human 确认验证；没有验证证据的完成不视为真正完成 | AI 只凭自述判断完成、用推测性表述替代验证，或验证结果缺失、不可复现 |
| V7 | 证据沉淀 | AI 的验证结果、执行证据、决策依据或 Git 提交记录能否在需要追溯时被稳定找到 | 完成了但无法证明、结果只存在聊天里、后续无法追溯 |
| V8 | 可靠回写 | 稳定事实能否按事实源边界回写到 Git 文件事实源 | 事实漂移在聊天、缓存、Web 页面状态、工具输出或派生数据中 |
| V9 | 人类确认质量 | AI 能否向 Human 提供足够的事实源、证据、项目态势、风险、影响和待确认事项，使 Human 给出可被 AI 消费的高质量确认 | Human 只能凭感觉验收，AI 无法获得明确、可追溯、可执行的确认 |
| V10 | 持续完善 | AI 能否识别可复用经验、反复问题和体系缺口，并推动其回到规范体系、事实模型、行动编排、Code、Web 或运行时扩展中 | 同类错误反复发生，可复用经验、规范规则缺口和工具能力不足没有沉淀 |

## 7. 构成要素实践准入判断

后续任何规则、对象、字段、附件、工具、资产承载物、Code 输出、Web 展示、运行时扩展或派生机制，作为六类构成要素的实践纳入 LDVH 前，必须同时满足：能归属六类构成要素之一；至少服务 V1-V10 中一项；说明减少哪类 AI 负担以及新增维护成本；具备事实源边界和验证方式；不触发本文列出的反向排除项。

在此基础上，还应回答：

1. 它属于六类构成要素中的哪一类；如果涉及事实源，它如何遵守事实源底层原则；
2. 它服务 V1-V10 中哪些价值；
3. 它是否仍以 AI 执行者为第一服务对象；
4. 它是否减少 AI 的定位、理解、判断、执行、验证或回写负担；
5. 它是否有明确事实源边界和验证方式；
6. 它是否会制造第二事实源；
7. 它是否会让下属机制、规则、对象、附件、工具或资产承载物为存在而存在；
8. 它是否绕过 Human Gate 或压缩 Human 的关键判断；
9. 它是否能被 Code、Web、测试、审计或人工检查稳定消费；
10. 它是否有退出、废弃、迁移或降级边界。

以下情况不应作为构成要素实践纳入 LDVH：

1. 不能归属六类构成要素，或不能说明服务 V1-V10 的规则、对象、字段、附件、工具或资产承载物；
2. 只是复制已有规则、制造新入口或增加阅读负担的内容；
3. 把 AI 的语义理解、规范权衡、风险判断或 Human Gate 压缩为不可审查的自动结论；
4. 把工具缓存、Web 页面状态、运行时索引、派生投影或聊天过程当作最终事实源；
5. 创建新的规则、附件、对象、运行时扩展承载物或 Code/Web 能力，却不能说明归属关系和真实执行成本下降；
6. 因未来想象能力而阻塞当前可验证实践。

## 8. v2 写作基线已确认事项

以下事项已经 Human 确认，作为 v2 写作区后续文档编写、单篇核对和机制归口判断的基线。该确认只表示写作和迁移判断基线已经成立，不表示本文已经 active 生效；正式规则仍以当前 active 事实源为准。

1. v2 00 把“LDVH 为什么存在”和“AI 执行者为第一服务对象”作为最高校验锚点；
2. 六类构成要素采用“规范体系、事实模型、行动编排、Code、Web、运行时扩展”；
3. 事实源继续只作为底层原则，而不是第七类构成要素；
4. 派生机制只作为六类构成要素的实现方法，并由后续对应构成要素实践承接；
5. V1-V10 作为所有 v2 内容的准入门槛。

## 9. 规范保障要求

00 是 v2 的最高价值锚点。后续规范、附件、构成要素实践和派生机制不得削弱本文定义的存在理由、AI 第一服务对象、六类构成要素、事实源底层原则和 V1-V10。

## 10. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 改变第 2 节“LDVH 为什么存在”的表述、定位或方法；
2. 改变第 3 节“以 AI 执行者为第一服务对象”的依赖、能力、本质或六个支撑方向；
3. 新增、删除、改名或重排六类构成要素；
4. 将事实源改为第七类构成要素，或将派生机制、附件、工具输出、Web 页面状态、运行时索引升级为最终事实源；
5. 改变 V1-V10 的编号、含义、准入作用或反向判断；
6. 将运行闭环、事实对象生命周期、具体流程步骤或具体环境适配细则写入 00，导致 00 替代后续构成要素实践；
7. 用对象数量、页面数量、工具数量、附件数量或资产数量替代 V1-V10 价值判断。

以下情况应评估 Human Gate，并在影响 00 最高锚点、六类构成要素、事实源底层原则或 V1-V10 时暂停确认：

1. 调整本文待补齐事项的归口、范围或关闭条件；
2. 新增可能影响后续构成要素实践准入的价值判断、反向排除项或检查标准；
3. 后续规范、附件、Code、Web 或运行时扩展试图把本文原则解释为自身执行豁免；
4. 规范核对发现本文与 01、active v1 原文或后续单篇规范存在上位冲突。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 结论、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。
