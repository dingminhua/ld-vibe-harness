## 一、本文解决的问题

本文定义多角色思考行动模型。多角色思考是 AI 在面对复杂变更、复杂决策、跨模块影响、规范治理、协作机制调整或高风险操作前，按多个专业视角分别分析、汇总分歧、识别风险、提出建议动作和 Human Gate 判断的行动。

本文将早期 `pm-kit-multi-role-analysis` Skill 原型升级为 LDVH 行动模型。Skill 可以作为本行动的轻量执行入口，但不再承载本行动的完整治理方案。多角色思考行动模型统一定义何时进入、读什么、如何选择轻量模式或 Agent 增强模式、如何处理 Trae 预制 Agent 前提、如何输出、如何回写稳定事实和如何审计。

## 三、行动定位与适用场景

### 3.1 行动定义

多角色思考是面向复杂问题的分析增强行动。它通过多个专业视角分别分析同一输入，降低单一视角遗漏风险，帮助 AI 和人识别影响范围、风险等级、分歧点、建议执行顺序、需要同步的事实源和 Human Gate。

多角色思考不是独立事实源，不替代 ADR、Task、Memo、Risk、Evidence、Change 或规范正文。它的输出默认是过程分析；只有按事实源边界写回对应 Git 文件后，才成为稳定事实。

### 3.2 适用场景

出现以下情况之一时，应考虑进入多角色思考：

1. 用户明确要求从不同角色、不同专业视角或多角色角度分析；
2. 规范、规则、Skill、Agent、工具或行动模型变更需要评估跨模块影响；
3. 技术选型、架构调整或工具设计需要同时评估性能、安全、可维护性、验证和治理边界；
4. 需求变更会影响产品、前端、后端、数据、测试、发布、治理或 AI 协作多个维度；
5. 需要判断某个输出应分流为 Task、Memo、ADR、Risk、Evidence、Change 或 docs 报告；
6. 需要在执行高影响变更前识别 Human Gate 和证据要求；
7. 主上下文判断存在明显不确定性，且单一视角可能遗漏重要风险。

### 3.3 不适用场景

以下情况通常不应进入多角色思考：

1. 简单问答或单文件小改，单一主上下文即可处理；
2. 用户已经明确给出决策并只要求执行低风险操作；
3. 问题已满足 Task 准入条件且不需要多视角分析，应直接进入对应 Task 行动；
4. 只需要确定性字段校验，应使用Tools 辅助或对象审计；
5. 已经由具体行动模型定义了更直接的执行流程，且没有复杂分歧或跨角色影响；
6. 用户明确要求不要进行额外分析。

## 四、准入条件

多角色思考行动的准入条件如下：

1. 存在一个需要分析的明确主题、变更、决策、风险或问题；
2. 至少存在两个以上有意义的分析视角；
3. 分析结论可能影响后续执行、规范、对象、工具、协作机制或 Human Gate；
4. 输入材料能够追溯到用户输入或 Git 文件事实源；
5. AI 能够明确说明本次分析是过程分析，还是需要回写为稳定事实。

不满足准入条件时，应退回主上下文直接回答、询问用户补充输入，或分流到更合适的行动、Skill、Agent 或Tools 辅助。

## 六、Context 要求

### 6.1 最小 Context

执行多角色思考前，AI 应获得以下最小 Context：

1. 用户提出的分析主题、目标、约束和期望输出；
2. 当前项目 L1 规则和相关工作区规则；
3. 与本次主题直接相关的 specs、ldvh-base、docs、tools、web 或代码文件；
4. `specs/07-LDVH行动模型基础规范.md`；
5. `specs/04-LDVH-AI协作规范.md`、`specs/04.02-Skill机制规范.md`、`specs/04.03-Agent机制规范.md`；
6. 需要判断事实源回写时读取 `specs/03-事实源边界与承载规范.md` 和对应生产对象规范；
7. 需要判断工具协作时读取 `specs/05-LDVH工具基础规范.md`。

### 6.2 可选 Context

根据主题复杂度，可增加以下 Context：

1. `specs-v2/11.04-多角色讨论设计规范.md`，作为早期角色矩阵和输出格式参考；
2. `specs-v2/11.05-推荐自建Agent清单.md`，作为早期 Agent 思路参考；
3. `specs/evals/` 中与本次主题相关的内部评估文档；
4. 已存在的 Task、ADR、Memo、Risk、Evidence 或 Change 实例；
5. Trae 预制 Agent 可用性说明或当前环境中可调用 Agent 列表。

可选 Context 只能作为参考输入。旧版 specs-v2 和早期 Skill 原型不能直接覆盖当前 specs/ 正式规范。

## 七、Scenario 识别

### 7.1 进入条件

当用户输入、任务背景或事实源状态满足以下条件之一时，AI 应识别为多角色思考 Scenario：

1. 出现“多角色”“不同角色”“不同视角”“从多个专业角度”“各自说一遍”等明确触发语；
2. 当前变更影响两个以上规范、对象、行动、工具、项目模块或协作机制；
3. 当前任务涉及 Rules、Skill、Agent、MCP、工具、事实源边界或 Human Gate 的职责划分；
4. 当前判断存在高影响风险，且需要安全、治理、验证或架构视角共同审查；
5. 用户要求先分析影响、风险、分歧或执行顺序，再决定是否修改；
6. AI 对执行路径不确定，并判断单一视角不足以安全推进。

### 7.2 优先级

多角色思考与其他行动同时匹配时，按以下原则处理：

1. 若用户明确要求多角色分析，优先进入多角色思考；
2. 若已有明确 Task 且只需执行，优先进入 Task 执行行动；
3. 若正在创建或更新对象实例，优先遵守对应对象创建或对象状态更新行动；
4. 若涉及规范、规则、Skill、Agent 或工具变更，先进行多角色思考或治理审查，再执行写入；
5. 若触发 Human Gate，先暂停并请求确认。

### 7.3 降级条件

以下情况应降级为主上下文直接分析或询问用户：

1. 主题不明确，无法选择角色；
2. 没有足够事实源支持分析；
3. 用户只需要简短回答；
4. 分析可能引入无关复杂度；
5. Agent 增强模式前提不满足，但轻量模式足以完成。

## 八、执行流程

### 8.1 选择分析模式

多角色思考分为三种模式：

| 模式 | 条件 | 行为 |
|---|---|---|
| 主上下文轻量模式 | 只读讨论、事实源读取少、不需要独立上下文、结论隔离或并行委派 | AI 在主上下文中按角色分别分析并汇总 |
| Skill 辅助模式 | 流程可复用、输入输出稳定、可在主上下文执行 | 可进入符合 04.02 的 Skill 承接结构化输出 |
| Agent 增强模式 | 需要独立上下文、结论隔离、并行委派、不同权限边界或大量事实源读取 | 由用户显式调用或主控编排已安装的 Trae 预制 Agent，汇总各 Agent 结果 |

默认优先主上下文轻量模式。只有当主上下文或 Skill 不足时，才进入 Agent 增强模式判断。

### 8.2 检查 Agent 前提

Agent 增强模式的默认前提是：当前 Trae 环境已安装并可调用相关 Trae 预制 Agent。

本行动支持以下降级规则：

1. 已安装并可调用相关 Trae 预制 Agent时，可进入 Agent 增强模式；
2. 未安装或不可确认时，不得假装已执行 Agent 增强分析；
3. 未安装时仍可执行主上下文轻量模式或 Skill 辅助模式；
4. 若用户明确要求 Agent 增强模式但前提不满足，AI 应暂停并提示需要先初始化或安装相关 Agent；
5. 创建、导入、启用或修改 Agent 调度边界必须按 04.03 触发 Human Gate。

### 8.3 识别变更类型

AI 应先判断分析主题属于哪些类型：

1. 需求 / 产品变更；
2. UI / 前端变更；
3. 服务端 / API / 数据变更；
4. 数据 / 模型相关变更；
5. 安全 / 合规变更；
6. 规则 / 规范 / 文档变更；
7. Skill / Agent / AI 协作变更；
8. MCP / 工具链 / 自动化变更；
9. 发布 / 部署 / 关闭变更；
10. 复盘 / 流程改进；
11. 通用架构 / 大型重构。

### 8.4 选择角色

角色选择应遵循以下原则：

1. 优先选择与变更类型直接相关的角色；
2. 涉及事实源、规则、编号、对象、行动模型时必须包含治理或规范视角；
3. 涉及 Human Gate、权限、删除、远程操作、Agent 或工具写入时必须包含风险与权限视角；
4. 涉及完成标准、关闭、Review 或审计时必须包含验证证据视角；
5. 涉及 Skill、Agent、MCP 或工具时必须包含 AI 协作或工具链视角；
6. 角色数超过 8 个时应精简或合并同维度角色；
7. 旧版角色矩阵可作为参考，但不得成为 LDVH 当前正式规范的唯一事实源。

### 8.5 分角色分析

每个角色至少输出：

1. 适用性：相关 / 无关；
2. 影响范围：具体模块、文件、接口、对象、行动或流程；
3. 分析结论：该角色视角下的判断；
4. 风险：高 / 中 / 低，并说明原因；
5. 建议动作：需要执行、暂停、确认、回写或补充的具体事项。

### 8.6 汇总对比

AI 应汇总各角色分析，至少包含：

1. 一致结论；
2. 分歧点；
3. 风险汇总；
4. 建议执行顺序；
5. 需要同步的文档、对象、规则、Skill、Agent 或工具；
6. 事实源回写建议；
7. Human Gate 判断。

### 8.7 输出格式

多角色思考输出建议采用以下结构：

```markdown
# 多角色思考报告

## 适用性判断
- 是否进入多角色思考：是 / 否
- 分析模式：主上下文轻量模式 / Skill 辅助模式 / Agent 增强模式
- Agent 前提：已满足 / 未满足但已降级 / 不适用
- 涉及角色：{角色列表}

## 变更或问题概述
- 主题：{一句话描述}
- 影响范围：{模块 / 文件 / 对象 / 行动 / 项目}

## 各角色分析

### {角色名}
- 适用性：相关 / 无关
- 影响范围：{描述}
- 分析结论：{结论}
- 风险：高 / 中 / 低 — {描述}
- 建议动作：{列表}

## 角色间一致与分歧
- 一致结论：{列表}
- 分歧点：{列表}

## 风险汇总
- 高风险：{列表}
- 中风险：{列表}
- 低风险：{列表}

## 建议执行顺序
1. {第一步}

## 事实源回写建议
- 应写回：{文件或对象}
- 不应写回：{过程信息}

- 建议确认事项：{列表}
```

## 九、Gate 触发条件

### 9.1 条件 Gate

以下情况触发条件 Gate：

1. 缺少分析主题或输入材料；
2. 需要读取的事实源不存在或无法确认；
3. 角色选择依据不足；
4. Agent 增强模式所需 Trae 预制 Agent 未安装或不可确认；
5. 输出需要回写但目标事实源不明确。

条件 Gate 未满足时，AI 应降级、询问用户或暂停，不得继续执行高影响分析或写入。

### 9.2 Human Gate

以下情况必须评估 Human Gate：

1. 多角色思考结论建议修改 specs、Rules、Skill、Agent、工具或行动模型；
2. 多角色思考结论建议创建、导入、启用、修改或删除 Agent；
3. 多角色思考结论建议改变事实源权威位置；
4. 多角色思考结论建议将过程分析升级为 ADR、规则、规范或长期行动边界；
5. 多角色思考结论涉及跨项目影响、高风险权限、删除重要资产或远程 Git 操作；
6. 用户要求从轻量模式升级到 Agent 增强模式，但需要先安装或启用 Agent。

## 十、Skill 和 Agent 调度

### 10.1 Skill 辅助

多角色思考可以由 Skill 辅助完成，但 Skill 必须符合以下边界：

1. Skill 只承接可复用流程、标准化输入输出和轻量分析；
2. Skill 不得调度 Agent；
3. Skill 不得替代 Human Gate；
4. Skill 输出不是最终事实源；
5. Skill 若发现需要 Agent 增强，应向用户或主控建议升级，而不是自行调度。

早期 `pm-kit-multi-role-analysis` Skill 可作为迁移参考。未来如创建 LDVH 版 Skill，应按 41.02 模型实践子文档规划，并使用 LDVH 命名和部署规则。

### 10.2 Agent 增强

Agent 增强模式用于需要独立上下文、结论隔离、并行委派、不同权限边界或大量事实源读取的多角色分析。

Agent 增强调度遵循以下规则：

1. 默认前提是 Trae 预制 Agent 已安装并可调用；
2. 未安装时，本行动不能执行 Agent 增强模式，但仍可执行主上下文轻量模式或 Skill 辅助模式；
3. Agent 只能由用户显式调用或主控编排；
4. Agent 输出必须回到主控或用户汇总，不得直接成为事实源；
5. Agent 发现 Human Gate 场景时必须标注并停止相关修改；
6. 不为每个角色自动创建自定义 Agent；
7. 需要创建、导入或修改 Agent 时，必须按 04.03 触发 Human Gate。

### 10.3 推荐使用的 Trae 预制 Agent 类型

在已安装 Trae 预制 Agent 的前提下，可按主题选择相关 Agent 参与增强分析，例如：

| 主题 | 可考虑的 Agent 类型 |
|---|---|
| UI / 前端体验 | UI 设计、前端架构 |
| 后端 / API / 数据 | 后端架构、API 测试 |
| 性能问题 | 性能优化 |
| 部署 / CI / 监控 | DevOps 架构 |
| AI / 模型 / 智能自动化 | AI 集成 |
| 安全风险 | 安全审查或主上下文安全视角 |

上述类型是调度建议，不表示 LDVH 已创建或维护对应 Agent 定义摘要，也不替代 Trae 平台实际可用 Agent 列表。

## 十一、工具协作适配

多角色思考可使用工具辅助以下工作：

1. 搜索和读取相关事实源；
2. 生成或校验 Context 包；
3. 检查 Markdown 链接、编号、引用和 YAML 语法；
4. 聚合变更影响文件；
5. 准备受控写入候选内容；
6. 展示分歧、风险和 Human Gate 待确认项。

工具不得直接决定角色结论，不得直接调用 AI、Skill 或 Agent，不得将工具缓存或派生视图作为最终事实源。

---

## 十二、事实源回写要求

多角色思考完成后，应按以下规则判断是否回写：

| 输出类型 | 回写位置 |
|---|---|
| 仅服务当前对话的分析 | 不回写，保留在当前上下文 |
| 需要执行的明确动作 | 创建或更新 Task，位置由 Task 对象规范定义 |
| 有保留价值但暂不任务化的信息 | 创建或更新 Memo，位置由 Memo 对象规范定义 |
| 已确认且长期有效的决策 | 创建或更新 ADR，位置由 ADR 对象规范定义 |
| 已识别的不确定因素 | 创建或更新 Risk，位置由 Risk 对象规范定义 |
| 验证结果或关闭证据 | 创建或更新 Evidence，位置由 Evidence 对象规范定义 |
| 对事实源产生影响的实际修改 | 创建 Change YAML 到 `ldvh-base/changes/` |
| 管辖项目报告或审计结果 | 写入 docs/ 对应报告 |
| 规范或规则正文 | 写入 specs/ 或 `.trae/rules/`，并评估 Human Gate |

未写入权威事实源前，多角色思考报告不能被后续 AI 当作稳定事实引用。

---

## 十三、证据留存要求

多角色思考的证据至少包括：

1. 分析主题和输入来源；
2. 读取的关键事实源；
3. 选择的分析模式及原因；
4. Agent 前提是否满足及降级说明；
5. 选用角色及选择理由；
6. 各角色结论、风险和建议动作；
7. 汇总结论、分歧和 Human Gate 判断；
8. 若发生写入，记录写入文件、写入原因、验证结果和 Change ID。

---

## 十四、Human Gate

### 14.1 必须暂停确认的情况

以下情况必须暂停并请求人类确认：

1. 将多角色思考结论升级为规范、规则、ADR 或长期行动边界；
2. 创建、导入、启用、修改或删除 Agent；
3. 允许 Agent 增强模式访问更高权限或写入文件；
4. 依据多角色思考结论修改事实源权威位置；
5. 依据多角色思考结论执行跨项目、高风险或不可自动确认的变更；
6. 将旧版 Skill 原型迁移、重命名或替换为 LDVH 正式 Skill。

### 14.2 用户确认后的处理

用户确认后，AI 应：

1. 明确记录确认事项；
2. 按对应规范执行写入或创建；
3. 写入后补充 Change 记录；
4. 执行可用检查；
5. 汇报哪些内容已成为稳定事实，哪些仍是建议。
