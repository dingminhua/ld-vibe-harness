## 1. 价值判断

本文存在的价值，是把 LDVH 安装、初始化和管辖项目配置这类高影响行动沉淀成可复用模板，让 AI 在执行前能稳定说明写入位置、影响范围、验证方式和回滚路径，减少遗漏告知、误装入口、误判 integrated 或绕过 Human Gate 的风险。

该模板主要服务 V1、V2、V3、V4、V5、V6、V7 和 V8：它让 AI 快速定位安装与配置入口，理解写入对象和环境边界，正确判断受管项目、环境入口和 integrated 状态，按固定 Gate 稳定执行，在高影响写入、配置位置确认或风险接受前等待 Human 确认，执行指定验证，按格式回写配置和残留风险，并用范式交互向 Human 呈现待确认事项。安装和初始化会改变环境入口、配置位置或受管项目边界；如果没有模板，AI 容易把“方案存在”“样例包存在”“旧插件存在”误写成“已部署”或“已接管”，也容易把系统检查结果当成用户决策、把后置缺口放进主选项，或在最终确认前边问边写。

## 2. 权威依据

本文承接 `specs/06-行动模板基础规范.md` 的 Context、Scenario、Gate、执行、验证、回写和交还结构。

本文承接 `specs/01-保障与衔接.md` 的环境入口、Hook 分类、插件 / 扩展包安装口径和 integrated 声明边界；承接 `specs/10-管辖项目配置规范.md` 的配置事实源和 target-first 解析边界；承接 `specs/07-Code确定性执行规范.md` 和 `specs/09-测试与验证规范.md` 的实现域与验证边界。

本文受 V3 01 的环境入口边界约束，也受 V3 01、06、10 的共同约束：01 管环境入口、06 管行动模板结构、10 管管辖项目配置契约。本文不声明 integrated；只有真实自动触发、失败可阻断、安装与接入证据可复核、回滚方式明确且验证证据齐备时，才可由对应环境入口规则判断是否 integrated。

若本文与 01、06、10 或 Human Gate 冲突，应回到上位规范和 Human Gate，不得由本模板自行覆盖。

## 3. 归口边界

本文归口定义 LDVH 安装、初始化和管辖项目配置行动的步骤组织、用户告知清单、Gate、验证和交还。

本文不归口定义环境入口判定分类、Hook 安装实现、插件 manifest schema、管辖项目配置字段、Code 命令细节、Web 页面、测试框架或真实用户环境配置。环境入口边界归 01，状态归口原则归 04，Code 实现实践归 07 和 `code/docs/`，管辖项目配置契约归 10，验证声明归 09。

本文可以组织“先告知、再确认、再执行、再验证、再交还”的行动顺序，但不得把行动步骤写成环境入口安装授权、配置事实源契约、Code 实现细节或 integrated 状态证明。

本文不得登记 Git 提交、WorkCase 推进或其它 31+ 行动模板候选的迁入判断；跨模板候选筛选统一回到 `specs/06-行动模板基础规范.md`。

## 4. 适用范围

本文适用于：

1. 用户要求安装 LDVH、接入 LDVH 或初始化 LDVH；
2. 用户要求配置、生成或迁移 `LDVH-GOVERNED-PROJECTS.yaml`；
3. 用户要求把项目登记为管辖项目，或检查某项目是否已被 LDVH 管辖；
4. 用户要求检查安装是否生效、修复旧插件、旧路径或 stale V2 path；
5. 后续真实安装、升级、禁用、卸载环境插件或 Git hook shim 前的 Human Gate 准备。

用户只是询问概念、职责或边界时，只回答 01、06、10 和本文边界，不写入配置、不安装插件、不修改 Hook。

## 5. 模板定位与来源

本文是 06 之后的第一个独立正式行动模板，编号为 `30`。它不是 06 父规范的正文示范，也不是 Code 实现域文档；它是可被 AI 直接引用的行动模板成员。

本文吸收 V2 `33-ldvh-install-action` 的安装、初始化、首次管辖项目配置和验收交还能力。V2 `32-environment-entry-adaptation` 的动态投影、部署检查和插件边界只能作为后续增强输入，不能让本文复制 32 全文、恢复 Rules/Skill 顶层机制或越过 Human Gate。

当前只迁入最小闭环：安装入口发现、安装方式判断、初始化检查、目标工作区确认、管辖项目登记、环境插件安装 / 升级方案判断、每个已选择管辖项目的 Git Hook 安装 / 升级方案判断、用户告知清单、验证、回写和交还。真实环境插件写入、管辖项目 Git Hook 写入、完整部署自动化、用户级配置解析、项目内配置迁移和批量项目接入仍需 Human Gate 与最终确认。

## 6. 用户告知清单

安装、部署、初始化、配置或卸载前，本模板必须先形成用户告知清单，并把清单交给 Human 确认。

告知清单至少包括：

1. 要安装、生成、修改、覆盖、禁用、卸载或删除的对象；
2. 写入位置及其级别：用户级、工作区级、项目级、Git 本地目录、插件 cache、仓库内样例或只读检查；
3. 受影响项目、不受影响项目、跨项目范围和混合非管辖 target 风险；
4. 会接入哪些 Git hook shim、环境 Hook、plugin lifecycle event、manual entrypoint 或 repo instruction；
5. 是否需要创建或检查管辖项目根下的 `ldvh-base/` 事实源目录，以及每个子目录的用途；
6. 哪些事件可能阻断，哪些只是 diagnostic，哪些仍是 `manual_ready` 或 `deferred`；
7. 旧插件、旧路径、旧配置、stale V2 path、历史 trust 或旧 Hook 的处理方式；
8. 验证命令、预期结果、不可验证范围和失败处理；
9. 回滚或卸载入口，以及卸载后如何确认环境不再自动触发 LDVH；
10. 当前仍未 integrated 的能力；
11. 残留风险、source_refs 和下一步 Human Gate。

管辖项目事实源目录告知必须说明：

| 目录 | 用途 | 创建边界 |
|---|---|---|
| `ldvh-base/workcases/` | 存放 WorkCase 工作项实例，用来追踪目标、推进状态、验证证据和关闭证据。 | 只创建目录不创建工作项，不替代行动模板或 Human Gate。 |
| `ldvh-base/adrs/` | 存放 ADR 决策实例，用来记录已确认决策、取舍依据和影响。 | 只创建目录不表示已有决策，不替代 specs 正文。 |
| `ldvh-base/pitfalls/` | 存放 Pitfall 踩坑经验实例，用来沉淀已验证的问题、根因、解决方式和规避策略。 | 只创建目录不替代未解决问题或测试失败记录。 |
| `ldvh-base/sparks/` | 存放 Spark 火花实例，用来记录待分流想法、候选发现和问题线索。 | 只创建目录不替代 WorkCase、ADR、Study 或聊天上下文。 |
| `ldvh-base/studies/` | 存放 Study 稳定研究报告实例，用来沉淀被提升后的研究结论。 | 只创建目录不替代临时调研材料、外部资料原文或未经吸收的研究过程。 |

临时调研材料、外部资料或第三方参考不是本模板要求创建的固定目录；只有被提升为稳定事实的研究报告进入 `ldvh-base/studies/`。

缺少用户告知清单时，不得安装、部署、初始化、写入配置、声明接入或要求 Human 验收。告知清单不是授权本身；授权只能来自 Human Gate。

## 7. 安装行动阶段与 Human Gate

### 7.1 行动阶段与交互边界

安装、接入、初始化或配置管辖项目时，AI 必须使用安装行动阶段组织 Human-facing 交互。安装行动不是测试模式；它是正常安装流程。是否执行只由最终确认决定。

安装行动固定为五个阶段：

| 阶段 | 名称 | 说明 | 写入边界 |
|---|---|---|---|
| 1/5 | 路径确认 | 展示完整流程，确认 LDVH 本体路径和目标工作区路径 | 不写入 |
| 2/5 | 安装前检查 | 只读检查当前项目、目标工作区配置、事实源目录、环境入口、旧插件和旧路径证据 | 不写入 |
| 3/5 | 安装选项 | 只收集真正需要 Human 决定的安装选项；配置位置不作为选项 | 不写入 |
| 4/5 | 安装方案预览 | 汇总用户告知清单、检查结果、Human 选择、将执行动作、后置项、验证方式和回滚方式 | 不写入 |
| 5/5 | 最终确认 | Human 选择执行或不执行；只有选择执行后才可写入 | 确认执行后才可写入 |

每次向 Human 展示安装行动时，交互输出应表达当前阶段、已确认决策 / 结果和未发生事项。已完成事项应写入简短结果，尚未发生事项应保持空白或不展示噪音占位，不写“待进行 / 待选择 / 待确认”等无效占位。本文不得新增安装运行时状态闭集，不得把交互展示项写成环境入口判定事实、事实对象状态或安装事实记录。具体图标、表格、展示列和交还摘要模板归 `code/docs/03-LDVH-Install-Wizard-Practice.md` 或运行时输出。

每一步开头前，AI 必须先完成内部摘要检查，确认本步目的、不会做什么、需要 Human 决定什么。内部摘要检查默认不在用户主界面逐字展示；用户主界面优先展示流程表、关键路径表、检查结果表或选项表。只有存在风险、授权、阻断、容易误解的写入边界，或 Human 要求说明时，才把内部摘要压缩成一句提示，例如“当前只读检查，不会写入”。内部摘要检查不得替代用户告知清单、Human Gate 或验证结论。

每个需要 Human 判断的步骤必须使用简洁确认块，而不是专业字段解释、固定五问式卡片或默认三行摘要。确认块最多三行，只保留 `确认项`、`选择影响` 和 `异常反馈`；低风险路径确认可以只给表格和选项，不额外展示确认块。不需要 Human 判断的步骤只说明正常标准和失败时应交回的路径、错误文本、截图或命令输出。AI 可以在技术明细中保留 raw diagnostic，但主界面不得裸露 raw diagnostic。

需要 Human 作出选择时，若当前界面支持选择框 / 单选控件，必须优先使用选择框 / 单选控件；界面不支持时，使用等价编号选项。每次只问一个问题，不把检查事实、后置项或返回修改混入主选项。选项表必须给出选项、说明和结果；最终确认只允许两个主选项，路径候选、工作区候选或项目编号候选按实际候选数量编号展示，但不得把“返回修改”写成第三个主选项。

安装行动必须区分方案确认和执行确认。4/5 安装方案预览只能询问“是否进入最终确认”，该选择不是执行授权，不得用“执行方案”或其它会让 Human 误以为已经授权写入的措辞。5/5 最终确认必须直接询问“执行方案”或“不执行，停止安装”，不得再次要求 Human 确认只读检查、重复展示安装前检查事实，或把执行后验证包装成新的只读验证选项。Human 在 5/5 选择 `1 执行方案` 后，AI 必须立即执行已确认写入并进入执行后验证，不得继续解释流程或再次索要同一授权。

安装行动的关键表格必须使用稳定、可扫描的视觉标记帮助 Human 区分路径项、检查项、风险等级和下一步处理；具体图标、展示列和示例形态归实现域。路径确认表格正文只展示说明和建议，不单列限制列，不重复展示绝对路径；安装前检查结果表必须包含“下一步处理”列；图标只用于提高可读性，不得替代结论文字、说明、Human Gate 或验证结论。安装前检查必须区分检查结论分类和是否阻断；注意类结论只表示需知情或需关注，不自动阻断；需安装和需升级类结论必须进入安装方案预览；阻断类结论必须停止执行并说明解除阻断条件。

### 7.2 用户告知、用户选择与检查事实

用户告知清单必须作为 4/5 安装方案预览的必含内容交给 Human 确认；若 2/5 安装前检查发现 blocking，AI 也必须在暂停交还时同步列出已能确认的告知清单项、缺失项和解除条件。告知清单不得替代 5/5 最终确认。

安装前检查只能输出系统已检查事实，不得把事实伪装成 Human 选项。目录已存在、配置已存在、项目内配置不受支持、当前实现不支持用户级配置目录、旧插件和旧路径状态、外部 Hook 状态等，都应写入检查结果、需授权动作或后置项；不得继续询问 Human 是否创建已存在目录，或把项目内配置、用户级配置目录放进主选项。环境插件未安装时必须记录为需安装类结论并安排安装方案；环境插件已安装但指向旧路径、旧版本或 stale V2 path 时必须记录为需升级类结论并安排升级方案；每个已选择管辖项目都必须先确认是有效 Git worktree，非 Git 目录必须记录为阻断类结论并说明管辖项目必须是 Git 仓库；每个已选择管辖项目都必须检查 Git `commit-msg` Hook 状态，未安装时必须记录为需安装类结论并安排安装方案，已安装但不是当前 V3 managed hook 或指向旧路径时必须记录为需升级类结论并安排升级方案；不得把这类情况表达成“不安装插件”“不处理插件”或“Git Hook 后置可不做”。

### 7.3 路径发现、配置位置与管辖项目清单

目标工作区配置已存在且方案倾向保留时，安装前检查必须读取并展示当前配置项目清单，不得只写“保留工作区配置”。配置清单必须用表格列出 `product_name`、`product_description` 摘要、每个候选项目的编号、项目 ID、名称、项目路径、Git common-dir、是否已设置为管辖项目和检查结论；不得展示“当前目标”列。AI 必须在清单后询问 Human：`1 不改管辖项目配置` 或 `2 按编号设置管辖项目`；选择 2 时再要求 Human 提供要设置为管辖项目的编号列表。配置正确性结论至少覆盖字段闭集、必填字段、项目 ID 唯一、路径可解析、target-first 解析结论和配置层级冲突。新建或重写配置时，安装方案预览必须用同等表格展示拟写入项目清单，让 Human 能比较“当前配置”和“拟写入配置”。

安装入口发现必须先从 LDVH 本体读取本文。目标工作区没有 LDVH 文件时，AI 可以执行有限、只读、有证据的 bootstrap discovery：依次检查当前对话或进程已知 LDVH root、`LDVH_ROOT` / `LDVH_HOME` 环境变量、已安装插件 / Hook / wrapper 中记录的 LDVH root、当前 cwd 向上的 `specs/30-LDVH安装初始化管辖项目配置行动模板.md` 与 `code/specs_validate.py` 组合、常见工作区父目录的有限深度搜索；找到候选后必须展示候选路径和证据，多个候选必须让 Human 选择，找不到时必须要求 Human 提供 LDVH 本体路径，不得要求目标工作区已经存在 `specs/30`。

安装选项只包含当前可执行且需要 Human 取舍的决策。`LDVH-GOVERNED-PROJECTS.yaml` 的配置位置不是选项，只能是目标工作区根目录；项目根目录、用户级目录和 LDVH 本体目录都不是支持位置。AI 必须用路径确认表解释 LDVH 本体路径、目标工作区根目录和配置文件完整路径分别代表什么、为什么建议这样选择；表格列为 `项目`、`说明`、`建议`，不得把绝对路径作为单独列重复展示，也不得单列限制列。路径确认后还必须提供可复制路径块，至少包含 `LDVH_ROOT=<ldvh-root>`、`WORKSPACE_ROOT=<workspace-root>` 和 `GOVERNED_CONFIG=<workspace-root>/LDVH-GOVERNED-PROJECTS.yaml`。可复制路径块是绝对路径的主展示位置，不得替代表格中的说明、建议、配置层级检查或 Human Gate。项目内已存在 `LDVH-GOVERNED-PROJECTS.yaml` 时，只能记录为 legacy / conflict，并要求 Human 先删除、迁移或明确保留其中一个；不得把它作为主选项。

### 7.4 安装方案预览与最终确认

安装方案预览必须合并所有 Human Gate。主界面只展示普通用户作出下一步判断所需的信息：会改变什么、不会改变什么、执行后还需要验证什么、是否存在阻断；技术明细可以附后或折叠展示，但不得丢失。技术明细必须按净变化分组展示：将新增、将修改或升级、将保持不变、不会执行、需后置确认、验证、不可验证范围、回滚。写入对象、写入位置、将执行动作、不会执行的事项、后置项、验证命令、失败处理和回滚方式都必须在此步可见或可展开。若环境插件未安装，方案预览必须安排安装；若环境插件已安装但过时或指向 stale V2 path，方案预览必须安排升级；插件安装或升级的写入对象、影响范围、验证和回滚入口必须明确。完整安装方案必须同时覆盖 AI 环境 Hook 和管辖项目 Git Hook；每个已选择管辖项目都必须列出 repo 路径、`core.hooksPath` / active hook 状态、将执行的 install / upgrade / no-op 动作、验证命令和卸载 / rollback 命令。若已选择管辖项目不是有效 Git worktree，安装方案预览必须停止为 blocking，不得继续进入最终执行，并必须说明管辖项目必须是 Git 仓库。若 Git Hook 因目标不明确、非管辖、混合 target 或 Human 未确认而不能执行，安装不得声明完成，只能记录为 gated / blocking。若目标工作区根目录到目标项目路径链上已经存在项目内 `LDVH-GOVERNED-PROJECTS.yaml`，安装方案预览必须报告配置层级冲突，并要求先删除、迁移或明确保留其中一个配置文件；不得继续进入执行。真实 lifecycle、外部环境触发或卸载后自动触发状态无法在当前回合验证时，必须写入不可验证范围，不得混入“验证通过”；但只读安装检测已证明插件可见、指向 V3 shim、shim 直测通过且无阻断诊断时，不得仅因当前回合无法证明真实 lifecycle 而阻断安装完成。最终确认前，AI 只能只读检查、展示结果和收集选择，不得写入配置、创建目录、安装插件、修改 Hook、修改用户环境或声明 integrated。

### 7.5 环境入口判定结果的安装交还

用户主界面必须把 01、`01.Att.03`、`01.Att.04` 和环境审计结果翻译为可行动语言，不得要求 Human 理解内部字段。`environment_hook_integrated=false` 在 01 判定为支持 Hook 且安装检测已通过时，应写成 `自动接入待验收`；在 01 判定为无自动环境 Hook 或仅手动入口可用时，应写成 `手动可用` 或 `可用但不自动拦截`。`target_environment_supported=false` 和 `unsupported_target_environment` 应写成“当前目标环境没有可用 Hook 接入”。`PreToolUse` 应写成“写入前检查”；`completion_claim_direct_nonblocking` 应写成“完成声明检查只提示问题，不阻断环境关闭”。这些 raw diagnostic 只能出现在技术明细、命令输出或诊断附录中。

30 不判定目标环境是否支持 Hook，不新增环境入口判定分类，也不得把承接形态写成状态闭集。30 必须读取 01、`01.Att.03`、`01.Att.04` 和环境审计结果；当这些结果确认目标环境没有可用环境 Hook / 插件入口时，30 只组织手动可用安装交还。该交还不是降级，不单独开 32，也不得交给 31。AI 必须说明目标环境无法自动触发 LDVH 环境 Hook，不能声明 `environment_hook_integrated=true`，也不能安排插件页面、重启 App、写入前检查阻断等 31 验收测试。30 只能在安装方案预览和交还中列出可用承接形态：`repo instruction`、`manual entrypoint`、`thin reference` 或 `external_adapter_candidate` 类型候选；验证标准是薄引用或手动入口可找到 V3 specs、读取顺序正确、manual CLI 可运行、Git Hook 正反例通过，以及 Human 已理解不会自动阻断写入或完成声明。手动可用安装交还可以和管辖项目 Git Hook、工作区配置、事实源目录初始化一起完成 30 安装闭环，但环境入口判定分类只能使用 `01.Att.04` 的 `manual_ready`、`available`、`deferred`、`removed_top_level` 或 `absent` 等分类，不得写 integrated，也不得把 repo instruction、thin reference 或外部 adapter 候选写成环境接入事实状态。

手动可用安装交还的用户表达必须避免“降级”“不能安装”“不安装插件”等容易误解的说法。主界面应写：AI 可以读取 LDVH 规则；你或 AI 可以手动运行检查命令；Git Hook 仍可在每个管辖项目内阻断提交；当前目标环境不会在写入前自动拦截，也不会进入 31。当 01 判定结果需要 Human 决策时只给两个主选项：`1 按手动可用方式完成安装交还` 或 `2 暂停，等目标环境 Hook 支持`。

环境 Hook 或插件提示必须按当前目标环境命名。AI 能从当前运行上下文识别当前 AI 运行环境名称时，必须优先使用该环境名称，不得沿用示例环境名称；只有当前运行环境、环境审计或 Human 明确目标环境为 Codex 时，才可在用户主界面写 `Codex/工具入口插件`。目标环境不是当前运行环境，或换成 Trae、IDE、Agent runner、CI、repo instruction、未知环境时，必须改写为对应的目标环境名称，或使用环境无关的 `目标环境插件 / 工具入口插件`。AI 提示用户安装、升级、授权或验收环境插件时，必须说明目标环境、插件页面 / 扩展页面或插件管理器入口、用户需要执行的授权 / trust 动作、重启 App 或重载插件宿主的要求、新开窗口或新会话后应看到的预期现象、失败后应返回给 AI 的信息，以及 AI 后续诊断命令。未真实写入插件包、未进入插件页面或未获得授权证据前，不得写成“插件已安装”；只能使用 `待用户安装`、`需授权`、`可见 / 需验证` 或 `已写入但待用户授权` 等用户提示语或当前证据说明。

### 7.6 环境插件安装检测与 lifecycle 验收

环境插件安装、升级或复核必须给出安装检测标准、用户侧冒烟检查顺序和正常判断标准；具体检查项由第 10 章验证方法承接。安装检测通过即可作为安装完成条件；用户侧冒烟检查不是安装完成阻断项，不阻断安装完成。缺少真实 lifecycle、授权 / trust、payload 或失败处理证据时，安装检测仍可通过并完成安装交还，但不得声明 integrated；用户侧冒烟检查失败时进入诊断或修复流程，不得直接回写安装检测失败；只有复跑安装检测发现插件缺失、插件未启用、必需 Hook manifest 不完整、旧路径、stale V2 path、shim 直测失败或 Git Hook 正反例失败时，才应返回 `review_required` 或 `blocked`。

当 `integrated` 结论会影响后续逻辑时，必须存在当次可执行的 lifecycle 验收机制，不得让 `environment_hook_integrated=false` 成为无法判断的死循环。安装检测已通过但真实 lifecycle 尚未在当前回合验证时，30 只负责交还用户侧冒烟检查要求，并提示 Human 可进入 `specs/31-环境Hook接入后验收行动模板.md` 的逐项验收；31 负责重启目标 App、新会话只读可见性探针、插件页面授权、受控写入负例阻断、受控正例放行、复跑统一安装验证入口并交还本次验收总结。本次验收总结不得写成长效状态，也不得被后续对话消费为 integrated 依据；后续需要判断时必须重新运行当前检测。

### 7.7 安装完成交还与失败信息包

安装完成交还必须给出用户能直接理解的结论句。支持 Hook 且安装检测通过但尚未 lifecycle 验收时，写 `安装完成；自动接入待验收，可进入 31`。目标环境确认无 Hook 时，写 `安装完成；当前环境为手动可用，不会自动拦截`。这两种结论都不得写成 integrated，也不得让 Human 误以为安装失败。

安装完成交还必须先给交还摘要，再给技术明细。交还摘要至少覆盖安装完成判断、01.Att.04 环境接入判定分类及证据、环境自动拦截结论、每个管辖项目 Git `commit-msg` Hook 验证摘要、下一步 Human Gate 和不可验证范围；不得在交还摘要中形成新的安装状态闭集。交还摘要之后必须把 Hook 验证分成两个块：`环境自动拦截` 和 `提交消息检查`，不得把环境 Hook 和 Git commit-msg Hook 混成一个“Hook 已通过”。

安装交还必须单列用户下一步待办。支持 Hook 时待办最多五项：打开目标环境插件页面、重启 App 或重载插件宿主、完成授权 / trust、进入 31 后在新窗口或新会话运行只读可见性探针、决定是否继续 31 受控正反例验收。手动可用安装交还待办最多五项：确认 repo instruction 或 thin reference 入口、运行 manual CLI 或等价检查、复核每个管辖项目 Git Hook、理解不会自动拦截、以后目标环境支持 Hook 时再升级为环境插件。

失败或暂停时必须提供可复制失败信息包，不得只要求“截图给我”。失败信息包至少列出：目标环境名称和版本、插件页面结果截图或文字、`install_verification.py --format json` 完整输出、`environment_entry_audit.py --format text` 输出、失败步骤编号、是否发生实际写入、scratch target 路径和文件状态、相关错误文本。若某项拿不到，写“未取得”并说明原因。

最终确认只展示两个主选项：`1 执行方案` 和 `2 不执行，停止安装`。最终确认前必须明确提示选择执行后才会开始写入；最终确认摘要只列出将写入对象和不写入对象，不得重复安装前检查表或把已完成的只读检查再次作为待确认事项。Human 选择不执行时，AI 必须停止在方案预览或最终确认状态，不得写入；Human 要求调整方案时，AI 必须回到对应前一步，但不得把返回修改作为第三个主选项；只有 Human 选择执行后，AI 才能按方案执行已确认的仓库内动作，并在写入后执行验证、回滚说明和残留风险交还。

安装执行完成后必须输出安装完成交还总结，不得只给零散验证结果。交还总结必须单列实际写入、明确未写入对象、验证摘要、Hook 接入后测试、不可验证范围、撤销 / 恢复入口和残留边界。Hook 接入后测试必须优先使用统一安装验证入口或等价入口形成可复现验收结果，并单列每个已选择管辖项目的 Git 提交消息检查结果、managed hook 证据、正例提交消息放行结果和反例提交消息阻断结果；若本次包含 AI 环境 Hook 插件安装、升级或复核，也必须单列插件证据、转接脚本 / runtime 直测结果、真实自动触发是否已验证和不能声明 integrated 的原因。缺少 Hook 接入后测试总结或统一安装验证入口等价验收结果时，不得声明安装完成；只能声明写入已执行但安装交还未完成。

## 11. Human Gate

以下情况必须进入 Human Gate：

1. 安装、升级、禁用、卸载或迁移 LDVH 插件 / 扩展包 / package；
2. 写入、覆盖、删除或迁移环境入口、Hook、plugin lifecycle event 或 repo instruction；
3. 创建、修改、迁移目标工作区根目录下的 `LDVH-GOVERNED-PROJECTS.yaml`，或确认 LDVH 本体路径 / 目标工作区根目录；
4. 创建、删除、迁移或重命名管辖项目 `ldvh-base/` 及事实源子目录；
5. 删除、迁移、合并、覆盖或保留同一路径链上的多个 `LDVH-GOVERNED-PROJECTS.yaml`；
6. 接受用户级配置目录后置缺口或其它当前 Code 不支持的配置候选；
7. 声称环境入口 integrated、接受阻断行为、接受残留风险、确认安装方案预览、选择执行或不执行、要求调整方案或要求 Human 验收；
8. 多项目、跨项目或混合非管辖 target 的安装、配置或验证范围不清。

## 12. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 目标环境、写入对象、写入位置级别或影响范围不清；
2. 缺少安装行动阶段展示、用户告知清单、安装方案预览或最终确认，或这些内容未交给 Human 确认；
3. 插件、Hook、repo instruction、旧路径或历史 trust 被写成 integrated 证明；
4. LDVH 本体路径、目标工作区根目录或目标工作区配置文件完整路径不清；
5. 目标项目内已有 `LDVH-GOVERNED-PROJECTS.yaml` 尚未删除、迁移或明确保留；
6. 管辖项目 `ldvh-base/` 目录用途、写入影响或 Human Gate 状态未说明，或系统已检查事实被重新包装成 Human 选项；
7. Code、环境审计或工具输出正在替代 Human Gate、事实源或完成判断；
8. 验证、回滚或卸载路径不可复现，却要求声明安装部署完成。

## 13. 待补齐事项

1. 本模板用于真实安装、升级、禁用、卸载或迁移 LDVH 插件 / 扩展包 / package 前，必须重新生成用户告知清单并进入 Human Gate；
2. 用户级配置目录和项目内配置不是本模板支持的主位置；如已存在，只能作为 legacy / conflict 或后置缺口处理；
3. 本模板当前只承接最小安装、初始化、管辖项目配置和事实源目录初始化闭环；若要扩展到批量管辖项目配置、跨项目安装或完整卸载记录，必须先修订本文并重新进入 Human Gate；
4. 本模板声明安装、升级或卸载完成前，需要 Code 实现域提供可复现的 status、正反例和 rollback 证据；
