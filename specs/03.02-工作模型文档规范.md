# 工作模型文档规范

> 创建日期：2026-06-08

> 关系：专题子文档

> 适用范围：`specs/20-39` 具体工作模型规范文档
> 上位依据：`specs/03-文档基础规范.md`

## 1. 本文解决的问题

本文解决具体工作模型规范文档应如何书写的问题，包括文档骨架、成员自描述契约、章节边界、字段契约表达、事实源边界表达、适配边界摘要、规范落地要求和检查要求。

本文只规定工作模型规范文档的写作方式。工作模型的定义、准入、通用规则、状态流转原则和实例边界由 `specs/05-工作模型基础规范.md` 定义；字段内容格式由 `specs/05.01-工作字段内容格式规范.md` 定义。

---
## 2. 与 00 和 05 的关系

00 定义工作模型是 LDVH 五类构成要素之一。05 定义工作模型基础规则和具体工作模型的标准组成。本文承接 03 的文档治理规则和 05 的模型组成要求，把具体工作模型应包含的规则转换为可写、可审、可校验的文档骨架。

具体工作模型规范不得通过文档结构反向改变 05 的通用规则；如具体模型确需例外，应在对应章节说明例外原因，并按 05 的 Human Gate 要求处理。

---
## 3. 适用文件

20-39 是具体工作模型规范区段，均按本文编写。工作模型集合不再通过独立手写集合索引文档维护成员清单；每个具体工作模型主文件必须通过头部元信息和成员自描述字段声明自身集合事实，Code 依据这些字段生成派生集合索引。

具体工作模型规范文件名采用：

```text
NN-{英文名}-{中文名}.md
```

文件名不得重复“工作模型规范”字样。

具体工作模型主文件的编号、文件名编号、标题编号和成员自描述 `spec_id` 必须一致。编号冲突、编号越界、文件缺失、状态非法或自描述字段缺失时，由 `code/spec_checks/index.py` 诊断识别。

---
## 4. 成员自描述契约

具体工作模型主文件必须在头部元信息之后、正文第一章之前提供机器可读成员自描述块。成员自描述块用于 Code 生成派生工作模型集合索引、状态清单、冲突诊断和 AI Context Pack；它是成员主文件的一部分，不是派生索引。Code 已依据成员自描述生成派生集合索引。

成员自描述块建议使用 YAML 代码块，字段至少包括：

| 字段 | 含义 | 要求 |
|---|---|---|
| `spec_id` | specs 编号 | 必填，必须为 20-39 内两位编号，并与文件名一致 |
| `kind` | 成员类型 | 必填，固定为 `work_model` |
| `name_en` | 英文名 | 必填，与文件名英文段保持一致 |
| `name_zh` | 中文名 | 必填，与文件名中文段保持一致 |
| `collection_status` | 集合状态 | 必填，建议使用 `active`、`candidate`、`reserved`、`removed`；状态语义由 05 和本文约束 |
| `canonical_path` | 主文件路径 | 必填，指向当前文件 |
| `instance_root` | 默认事实实例目录 | 条件必填；无实例目录或使用外部事实源时必须说明 |
| `schema_anchor` | 字段契约章节锚点 | 必填，指向本文档字段契约章节 |
| `state_machine_anchor` | 状态机章节锚点 | 必填；不适用时指向说明不适用的章节 |
| `human_gate_anchor` | Human Gate 章节锚点 | 必填 |
| `code_consumption` | Code 消费说明 | 必填，列出 Code 应读取的字段、章节或校验入口 |
| `supersedes` / `superseded_by` | 替代关系 | 可选，用于重命名、迁移或废弃后的追溯 |

示例：

```yaml
ldvh_member:
  spec_id: "21"
  kind: work_model
  name_en: WorkPlan
  name_zh: 工作计划
  collection_status: active
  canonical_path: specs/21-WorkPlan-工作计划.md
  instance_root: ldvh-base/workplans/
  schema_anchor: "§6"
  state_machine_anchor: "§3"
  human_gate_anchor: "§5"
  code_consumption:
    - fields
    - state_machine
    - instance_checks
```

成员自描述中的集合状态只描述该规范成员在 20-39 区段中的治理状态，不承载项目运行状态、实例状态或检查过程状态。后续 Code 派生输出必须回指成员主文件，不得把派生索引作为最终事实源。

## 6. 字段契约表达

字段契约应使用稳定表格或结构化代码块表达，至少说明字段名、含义、类型、是否必填、默认值或状态约束、内容格式和消费方。

字段契约不得把字段内容格式、Web 渲染组件或 Code 校验实现写成字段定义本身。字段内容格式应引用 `specs/05.01-工作字段内容格式规范.md`；Code 和 Web 只作为消费方或实现方。

---
## 7. 适配边界表达

适配边界用于说明 AI、Rules / Instructions、Skill、Agent、Code、Web 或结构化契约如何消费该工作模型。

适配边界应只保留摘要和引用关系，不得复制完整适配措施、Skill 正文、Code 实现说明或 Web 设计稿。需要实现或适配时，应回到 04 系列、07、08 或对应环境实体处理。

---
## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 具体工作模型规范文档应按 05 的标准组成、本文骨架和成员自描述契约编写 | 03.01、本文、05、Human Gate | 文档治理 | 新增、修改、重命名或审计 20-39 工作模型规范时 |
| 确定性执行要求 | Code 应能检查具体工作模型规范是否覆盖成员自描述、必要章节、字段契约和事实源边界，并生成派生工作模型集合索引 | `code/spec_checks/index.py`、正反样例 | 校验实现 | 工作模型文档骨架、成员自描述字段、字段契约表或检查项变化时 |
| 生命周期触发要求 | 具体工作模型规范变化后，应检查成员自描述、Web 和相关流程是否需要同步 | 成员自描述校验、Code 派生索引、联动检查、人工降级检查 | 触发保障 | 字段契约、状态机、对象关系、事实源边界、成员自描述或适配边界变化时 |

---
## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变具体工作模型规范的标准骨架；
2. 允许具体工作模型规范省略标准组成且无说明；
3. 将 Code、Web、Skill 或 Agent 实现说明提升为字段契约权威来源；
4. 改变字段契约、状态机、事实源边界或对象关系表达方式；
5. 改变成员自描述字段、集合状态语义或 Code 派生集合索引消费方式。

工作模型文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 骨架 | 覆盖本文 §5 标准章节，缺项已说明 |
| 上位依据 | 上位依据指向 05，相关规范按内容引用 02、03、05.01、09、07、08 |
| 成员自描述 | 自描述字段完整，编号、文件名、路径、集合状态和锚点可被 Code 校验 |
| 字段契约 | 字段名、类型、必填性、内容格式和消费方清晰 |
| 事实源边界 | 实例位置、权威字段和派生视图边界清晰 |
| 适配边界 | 只保留摘要和引用，不复制实现正文 |

---
## 10. 待补齐事项

1. 后续新增、升级或降级 20-39 具体工作模型时，应按本文检查并修正骨架和成员自描述；
2. 工作模型字段契约的机器可校验格式待 05、05.01 和具体模型稳定后补齐；
3. 现有 20-27 工作模型主文件已提供成员自描述字段，后续新增或调整工作模型时应同步维护；
4. 工作模型派生集合索引、编号冲突检查和状态诊断已由 `code/spec_checks/index.py` 承接。
