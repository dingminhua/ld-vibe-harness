# V4 LDVH 管辖项目统一 Git 提交契约承载与闭环调查

> 记录性质：本文是 `specification-model-foundation` §13.5 要求的规范责任调整判断记录，不是规则源，不使任何 commit 合规，也不授权 amend、push 或其它 Git 写入。初始判断者为 GPT SOL；初稿形成时间为 2026-07-15 04:13:22 +08:00，结构重审时间为 2026-07-15（Asia/Shanghai）。Human 已明确：LDVH 统一提交契约适用于全部受 LDVH 管辖的项目，不只用于 LDVH V4 仓库。当前建议是扩充 30 的既有具体行动责任，不新增 09；独立复核尚未完成。

## 1. 不使用候选名称表达规则对象

需要补齐的规则对象是：**在任何受 LDVH 管辖的实际 Git worktree 中准备创建新本地 commit 时，候选变化、提交拆分、完整 message、验证声明以及创建前后回读结果之间必须满足的统一关系**。

具体需要回答：

1. 一个 commit 应覆盖什么样的主要目的，何时必须拆分；
2. header 使用什么结构，允许哪些 type/scope；
3. 什么情况下 body 必填，至少保留什么内容；
4. 格式机械校验、AI 语义审核和 Git 写后回读分别负责什么；
5. 已创建的不合规 commit 如何停止扩散，何时必须交还 Human。

这些要求不能藏在 Code、Hook、提示词或归档中，但“必须有正式来源”不等于“必须建立独立普通规范”。承载位置还要继续比较它们能否脱离 Git 提交行动独立消费、独立变化，以及拆分后的读取成本。

## 2. 实际暴露的问题

2026-07-15 创建的 `a82b00feeabf94851ea2e10671a433d8a01d106d` 使用 `feat: add Git commit action template mechanism`。该 message 能描述大意，但没有遵循 V3 历史提交契约体现的 LDVH 习惯：description 不是简体中文，八个文件和高影响范围也没有 body。

直接根因是：

1. 03 §9 有意不定义提交拆分、message 格式、Hook 和 push；
2. 30 初版有意只组织项目规则发现、候选、验证、创建和回读，并明确不定义项目政策；
3. 当前 V4 没有正式来源定义全部受管辖项目共同遵守的 LDVH 提交契约；
4. 因而 30 的“读取项目提交政策”把 LDVH 应当提供的共同基线错误地下放给各项目，执行者只能临场选择格式；
5. V3 validator 可以证明历史机制存在，但 `archive/`、Code 和 tests 不能自行恢复规则效力。

因此，先 amend 只能修复一个历史锚点，不能消除下一次重复失败。

## 3. 移除重复和实现细节后的规则

03 已经定义 Working Tree、Index、`HEAD`、history 和 message 的一般证明边界；06 已经定义行动模板共同准入与消费规则；30 已经定义本地 commit 的目标隔离、候选、验证、创建和回读关系。去掉这些重复内容，以及 `git add`、CLI、锁、Hook 安装和测试实现后，仍需补充：

1. 对全部受 LDVH 管辖项目统一适用的 header、type/scope、简体中文 description 和 body 契约；
2. 一个 commit 的主要目的与拆分条件；
3. 使用实际候选路径和完整 message 的提交前机械校验；
4. AI 对目的、真实性、验证覆盖和风险的语义审核；
5. 已创建不合规 commit 的报告、停止和历史改写 Human Gate。

这些是稳定规则，不应留在当次对话或实现中；但它们只在 Git 提交行动进入候选形成、message 生成、创建前校验和写后处置时被消费。

## 4. 结构性判断：是否需要独立普通规范

### 4.1 独立对象不足

这组规则没有脱离 Git 提交行动的独立操作对象。message、body 和拆分都只存在于“准备或检查 commit”这一场景；没有另一个业务过程需要单独消费所谓“提交政策对象”。

### 4.2 触发与生命周期高度一致

规则的触发点与 30 完全重叠：形成候选、生成 message、提交前校验、创建后回读和发现不合规历史。格式变化也会直接改变 30 的输入、分支、验证和交还；两份规范必须同步修改。

### 4.3 独立失败不等于必须拆文档

message 格式可以在 Git 能力正常时独立失败，但 01 §13.2 还要求独立适用、自然承载困难和正净价值。仅有独立失败场景不足以抵消每次提交都要拼接 03、09、30 三份来源的成本。

### 4.4 09 的净价值结论

单独建立 09 会产生：

1. 30 必须永久引用一个只服务自身输出契约的并列规范；
2. message、验证、Stop Conditions 和 Human Gate 在 09 与 30 之间容易重复；
3. 后续执行者必须先判断“行动规则”和“项目规则”两份文件的组合关系；
4. Code validator 的来源回指和测试同步也被人为拆成两层。

因此 09 不满足 01 §13.2(3)、(4) 和 (7) 的正净价值要求，取消候选，不占用规范编号。

## 5. 承载位置比较

### 5.1 03 正文或 03 附件

不采用。03 管辖 Git 与信息溯源的一般语义，而 LDVH header/type/scope 是 LDVH 执行 Git 提交这一具体行动的统一契约。加入 03 会把行动约束伪装成 Git 通用语义；附件也不得承担父规范没有先定义的核心规则和 Human Gate。

### 5.2 独立 09

不采用。它只有规则形式上的独立性，没有消费和变化上的独立性，增加一次行动的跨文档拼接与同步成本。

### 5.3 30 正文

建议采用。30 已经是 LDVH Git 提交这一具体、重复行动的正式来源，message 形成、拆分、校验和不合规处置都是该行动的输入、步骤分支、验证或交还条件。将统一契约放入 30，不会让 06 或 03 取得具体行动政策，也不会把实现提升为权威。

30 应明确分成两层：

1. **LDVH 统一提交契约**：对全部受管辖项目定义 header、type/scope、body、主要目的、校验和不合规历史处置；
2. **通用行动结构**：目标 worktree、授权、用户既有 Index 保护、领域/项目附加规则发现、候选、验证、创建、回读和交还。

项目自己的正式来源可以追加领域验证、分支保护或其它不冲突的更严格要求，但不得替换、削弱或静默扩展 30 的统一 header/type/scope/body 和拆分契约。确需改变共同契约时，应修改 30，而不是在单个项目形成方言。

### 5.4 `30.Att.01` 授权附件

当前不建立。type/scope 和 body 条件虽适合结构化表格，但数量和复用范围尚不足以证明新增附件的净价值。先在 30 正文中由同一来源定义核心规则与表格；只有表格规模、独立机器消费或维护负担实际增加，并且 30 已先定义相应核心语义和授权边界时，才重新判断附件。

### 5.5 Code、Hook、tests 或配置

只实现，不定义。validator 可以解析 30 中的结构化表格或由 Code 规划定义内部表示；Hook 和环境接入可以调用 validator；tests 证明机械范围。任一实现都不得维护第二份 type/scope 或 body 规则。

## 6. 与 06“模板不得定义领域或项目规则”的关系

06 禁止行动模板通过引用或复制其它领域来源而覆盖事实语义、状态、授权和项目领域要求。它不禁止具体模板定义 LDVH 为该行动统一提供的稳定输入、输出和验证契约，否则具体模板无法形成一致能力。

本次调整需要同步澄清 30 初版中过度绝对的边界：

1. 30 直接定义全部受管辖项目的 LDVH 提交共同基线，不再把格式责任下放给各项目；
2. 项目和领域来源仍定义其特有测试、分支保护和其它附加条件，30 组织实际发现和执行；
3. 附加条件不得与共同 message 和拆分契约冲突，也不得形成项目方言；
4. Code、Hook、Skill 和环境接入继续不得复制契约正文。

这不是让所有行动模板任意吸收领域规则，而是让具体模板对 LDVH 自身提供的具体行动一致性负责；仍按“规则是否只随该行动消费和变化”决定最小承载位置。

## 7. 正例、反例和失败边界

正例：在任一受 LDVH 管辖项目中提交同一主要目的的规范、实现和测试变化。30 统一要求简体中文 header、必要 body 和实际候选校验；项目来源另行补充对应领域测试要求。

反例：某个受管辖业务仓库通过自己的说明文件改用另一套 type 或允许多文件高影响提交省略 body。该说明不能削弱 30 的共同契约；若业务需要确实证明共同契约不足，应回到 30 统一修改。

失败边界：目标、授权、候选和 Git 能力都成立，但任一受管辖项目的 message 使用未知 type、全英文 description 或多文件无 body。30 在创建前停止；该失败属于具体 Git 提交行动，不需要另建规范才能解释。

## 8. 对 V1–V8 的净价值

将统一契约合入 30：

1. V1：一次定位即可找到 Git 提交完整行动规则；
2. V2/V3：03、06、30 分别保持“溯源语义、模板共同规则、具体行动”的三层边界；
3. V4/V5：提交前校验和写后回读进入同一因果链，且机械与语义结论分开；
4. V6/V7：后续执行者和 Human 从同一来源恢复 message、验证和风险要求；
5. V8：规则、validator 和环境接入都回指 30，避免第二权威。

代价是 30 正文变长，并同时包含共同契约和执行步骤；通过明确小节和机器可解析表格可以控制。相比新增 09、各项目重复规则和永久跨文档拼接，该成本更低。

## 9. 建议与 Gate

建议按以下顺序推进：

1. 取消 09 候选，不建立独立普通规范或附件；
2. 对“30 是否可以在不侵入领域规则的情况下承载全部受管辖项目统一提交契约”做独立复核；
3. 复核通过后，在 30 内增加统一契约，并同步修改其 positioning、scope、职责边界、行动步骤、验证、Human Gate 和 Stop Conditions；
4. 形成 07 要求的 Code 实现规划，实现只读、无 Git 写副作用的 message + candidate paths validator 和风险 tests；
5. validator 成立后，再由 Human 决定是否 amend `a82b00fe`，并用同一 30 流程完成重校验和写后回读。

独立复核必须主动挑战：

1. 统一契约是否真的与 30 同触发、同变化，还是仍有独立消费者；
2. 30 的共同契约、行动步骤与项目领域附加要求是否能明确分层；
3. type/scope/body 表是否需要附件，还是正文最小充分；
4. 是否存在把领域测试要求、项目特有约束或实现细节误吸入 30 的内容；
5. 扩充 30 后的读取成本是否仍低于新增规范。

复核与主执行者处置完成前，不修改 active 30 的责任边界，不实现 validator，也不改写现有 commit。
