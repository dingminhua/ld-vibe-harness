> 适用范围：LDVH 自身项目、安装 LDVH 的管辖项目，以及 AI 在上述项目中判断文件归属、编号占用和目录事实源性质的场景

> 相关规范：`specs/02-术语规范.md`、`specs/03-文档基础规范.md`、`specs/03.01-规范文档规范.md`、`specs/03.02-索引文档规范.md`、`specs/03.05-管辖项目配置规范.md`、`specs/04-规范落地与环境适配基础规范.md`、`specs/07-Code确定性执行实现规范.md`

## 1. 本文解决的问题

本文解决 LDVH 中内容应放在哪个目录、不同项目中的文档工作区如何映射、specs 编号如何分区，以及目录说明与文档规范、索引文档、环境适配和 Code 实现之间如何分工的问题。

本文只规定目录与编号边界，不直接定义文档写作细则、事实源权威性原则、工作模型字段契约、工作流程行动规则或 Code 实现细则。文档工作区规则由 `specs/03-文档基础规范.md` 承接；规范落地与环境适配由 `specs/04-规范落地与环境适配基础规范.md` 承接；Code 实现边界由 `specs/07-Code确定性执行实现规范.md` 承接。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 由开发环境、工作模型、工作流程、Code 和 Web 五类构成要素共同形成 AI 工程驾驭体系，并要求稳定事实回到 Git 可追踪文件。

本文承接 00 的事实源和构成要素分工，把这些内容落实到项目目录和编号分区上，使 AI 能快速判断：

1. 哪个目录承载 LDVH 规范；
2. 哪个目录承载管辖项目文档；
3. 哪个目录承载结构化事实实例；
4. 哪个目录承载 Code、Web 和测试实现；
5. 哪些根目录文件属于 LDVH 自身项目入口；
6. 哪些编号区段属于基础规范、工作模型、工作流程或其他构成要素。

## 3. 项目类型与工作区映射

LDVH 需要区分两类项目：

| 项目类型 | 定位 | 规范工作区 | 文档工作区 | 说明 |
|---|---|---|---|---|
| LDVH 自身项目 | 承载和维护 LDVH 规范体系、Code、Web、文本能力资产和 dogfood 事实实例 | `specs/` | `docs/` 根目录项目文档资产、`docs/studies/` 和 `docs/sources/` | 目标正式基线以 `specs/` 作为规范资产和规范事实源，`docs/studies/` 和 `docs/sources/` 只作为可变资料区 |
| 管辖项目 | 安装并使用 LDVH 进行工程治理的用户项目 | 不默认创建 `specs/` | 项目自有文档位置，常见为 `docs/` 或 README | 用户项目文档由项目自身约定管理；LDVH 不默认接管、初始化、重排或强制校验用户 docs |

首次阅读或安装 LDVH 时，AI 应根据目标选择最小入口：

1. 理解 LDVH 正式基线：迁移完成后先读 00 总纲，再读本文和术语规范；迁移完成前按当前仓库实际路径读取对应规范；
2. 判断目录、编号或内容归属：先读本文，再按内容进入 03、04、05、05.01、06、07、08、09、20、40 或已登记的候选区段；
3. 进入 LDVH 运行入口：先检查 `../rules/LDVH-AI-ENTRY.md`，再按场景进入正式规范、管辖项目配置、环境能力清单或工作流程入口；
4. 完成环境确认或环境适配判断：按 `specs/04.03-环境入口适配与部署规范.md` 读取环境入口适配、部署和适配检查规则，并通过当前任务的具体检查结果或后续重新设计的落地检查流程确认真实入口、权限、工具和适配降级；
5. 创建、修改或审计 specs 正式规范：先读文档基础规范、规范文档规范和规范落地声明规范，再读必要的 04 系列、07、08、09 规范；未进入 specs 正文区的候选材料不得作为正式规范依据。

管辖项目接入 LDVH 后，应优先检查工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 是否登记该项目，并检查对应项目的 `ldvh-base/` 和必要的工作区级环境入口是否能通过薄引用让 AI 稳定进入 LDVH 管理链路。LDVH 不因项目被登记为管辖项目而默认接管、创建、迁移或校验用户 docs；需要读取或修改项目文档时，应由具体任务、用户指令、项目约定或 Human Gate 明确触发。管辖项目不默认创建环境规则文件、项目指令或等价项目级入口；确需例外时，必须由 Human 明确授权并记录影响范围。

## 4. 目录与根文件规划

LDVH 当前识别以下目录和根文件：

| 路径 | 定位 | 主要内容 | 边界 |
|---|---|---|---|
| `specs/` | LDVH 规范资产目录 | 正式规范正文 | 只属于 LDVH 自身项目；用户管辖项目不默认创建；同时是规范资产和规范事实源 |
| `docs/` | 用户文档资产与资料工作区根目录 | 根目录 Markdown 文档、内部研究资料和外部信源资料 | 在 LDVH 自身项目中按本文识别为项目文档资产与资料区；在管辖项目中只按项目自身约定读取，不由 LDVH 默认接管、初始化、重排或强制校验 |
| `docs/studies/` | 内部研究资料区 | LDVH 内部研究、方案分析、吸收候选；管辖项目中仅在项目自身采用该目录时作为内部资料读取 | 可整理、归档或删除；不直接构成正式规范或项目稳定结论；管辖项目中的吸收动作必须由具体任务、用户指令或 Human Gate 触发 |
| `docs/sources/` | 外部信源资料区 | 外部资料、客观信源、引用副本、摘要和第三方文档；管辖项目中仅在项目自身采用该目录时作为外部资料读取 | 可整理、归档或删除；不直接构成正式规范或项目稳定结论；不得反向维护 specs 规则 |
| `ldvh-base/` | 结构化事实实例目录 | WorkArea、TaskPlan、Task、SubTask、ADR、Change、Pitfall、Memo 等实例 | 工作对象事实源目录，不是能力资产；具体实例规则由工作模型规范定义 |
| `rules/` | 文本能力资产目录 | AI-facing 规则、入口摘要和约束提示 | 只承载可复用文本能力资产，不替代 `specs/` 正式规范正文，不保存运行状态 |
| `skills/` | 文本能力资产目录 | AI-facing 任务能力、流程复用说明和标准化操作入口 | 只承载可复用文本能力资产，不替代工作流程、Code 或事实源 |
| `hooks/` | 文本能力资产目录 | 生命周期触发提示、检查策略、Hook 说明或跨环境 Hook 候选资产 | 不默认启用自动写入；实际环境 Hook 仍需 04 和 Human Gate 约束 |
| `agents/` | 文本能力资产目录 | 角色、子 Agent、多角色模板或专项审查能力说明 | Agent 输出必须回到主控或 Human，稳定结论回写后才生效 |
| `code/` | Code 参考实现目录 | LDVH 提供的校验器、脚本、上下文生成、受控写入和其他确定性参考实现 | LDVH 核心是规范系统，用户可根据07约束自行实现 Code；只放实现，不放测试；Code 输出不是最终事实源 |
| `tests/` | 自动化测试集合目录 | Code、Web 和其他实现的测试与夹具 | 测试按构成要素分区，Code 测试放入 `tests/code/`，Web 测试放入 `tests/web/`；测试结果不替代 Git 文件事实 |
| `web/` | Web 参考实现目录 | LDVH 提供的 Human-facing 页面、后端、API、交互与呈现参考实现 | LDVH 核心是规范系统，用户可根据08约束自行实现 Web；Web 状态不替代 Git 文件事实源 |
| LDVH-GOVERNED-PROJECTS.yaml | 工作区根目录管辖项目配置 | 当前工作区 LDVH 管理实例的产品名称、产品说明，以及管辖项目 `id`、根路径、可选名称和可选说明 | 不是工作对象；不承载初始化状态、落地状态、检查状态、项目类型、docs 路径、ldvh-base 路径、环境适配或适配措施正文 |
| `../rules/LDVH-AI-ENTRY.md` | LDVH AI 统一入口 Rules 资产 | AI 进入 LDVH 时的最小读取顺序、场景路由、STOP 点和权威路径提示 | 不是规范文档；不属于管辖项目默认文件；结构由 04.02 和 04.03 约束，不替代正式规范、管辖项目配置、环境能力清单、具体检查结果或后续重新设计的落地检查过程输出 |
| README.md | 项目入口说明 | 项目简介、安装、使用入口和导航 | 项目文档入口；具体规范不在 README 中定义 |

目录名称和内容归属本身不自动决定最终事实源权威性。`specs/` 是规范资产和规范事实源；`rules/`、`skills/`、`hooks/`、`agents/`、`code/` 和 `web/` 是能力资产目录；`ldvh-base/` 是工作对象事实源目录；`docs/` 根目录 Markdown 文档是用户资产或项目文档资产；`docs/studies/` 和 `docs/sources/` 是可变资料区。管辖项目中的用户文档由项目自身约定管理，LDVH 只在任务需要时读取、引用或按授权修改，不把设置管辖项目解释为接管用户 docs。最终事实源边界由事实源边界规范定义；所有稳定事实仍应遵守 00 和 09 中 Git 可追踪文件和单一事实源原则。

## 6. 索引文档与编号区段

20 和 40 是规范型集合索引，应按 `specs/03.02-索引文档规范.md` 编写和维护。当前 20 工作模型集合索引和 40 工作流程集合索引均已在 `specs/` 生效。AI 处理工作模型集合时，应读取 `specs/20-工作模型集合索引.md`；处理工作流程集合时，应读取 `specs/40-工作流程集合索引.md`。

集合索引只维护清单、状态、编号范围、关系、落地与检查输入，不定义具体对象字段、状态机、工作流程 Context、Scenario、Gate 或行动流程。

工作模型和工作流程的分工如下：

| 区段 | 基础规范 | 集合索引 | 具体规范 |
|---|---|---|---|
| 工作模型 | 05 工作模型基础规范 | 20 工作模型集合索引 | 21-39 具体工作模型规范 |
| 工作流程 | 06 工作流程基础规范 | 40 工作流程集合索引 | 41-59 具体工作流程规范 |

新增或修改 20、40、21-39、41-59 文档时，应同步检查 01 的编号分区、03.02 的索引规则、对应基础规范和对应集合索引。若对应文件尚未创建或尚未生效，只能记录为候选事项、计划或待补齐事项，不能引用不存在的索引作为事实源入口。

## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除或重命名本文定义的一级目录；
2. 改变 `specs/`、`docs/`、`ldvh-base/`、`rules/`、`skills/`、`hooks/`、`agents/`、`code/`、`web/` 或 `tests/` 的定位；
3. 将用户管辖项目改为默认创建 `specs/` 或默认接管用户 docs；
4. 改变 specs 编号分区；
5. 将 20 或 40 改为基础规范编号；
6. 将索引文档扩张为具体工作模型或工作流程规则；
7. 将 docs 子目录资料、外部信源、内部研究或临时参考内容直接视为正式规范；
8. 删除、重命名或移动 `../rules/LDVH-AI-ENTRY.md`。

目录和编号检查至少包括：

| 检查项 | 标准 |
|---|---|
| 工作区映射 | LDVH 自身使用 `specs/`；用户管辖项目不默认创建 `specs/`，项目文档按项目自身约定管理 |
| AI 统一入口 | LDVH 自身项目存在 `../rules/LDVH-AI-ENTRY.md`；管辖项目不默认要求该文件 |
| 编号分区 | 文档编号符合本文 §5 |
| 索引边界 | 20/40 是集合索引，05/06 是基础规范 |
| 内容归属 | 内容进入权威归属文档，不重复多处维护 |
| 资料边界 | docs/studies、docs/sources、临时参考内容不直接成为正式依据 |
| Code 适配 | 可机械检查内容已评估是否需要 Code 支撑 |
