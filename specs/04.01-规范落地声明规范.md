# 规范落地要求与类型规范

> 创建日期：2026-06-11
> 定位：定义 LDVH 正式规范可以提出哪些落地要求，以及这些要求如何声明、检查和进入后续能力保障
> 适用范围：LDVH `specs/` 正式规范、规范落地要求声明、要求类型、保障机制提示、同步触发和后续 04.02 / 04.03 消费
> 上位依据：`specs/04-规范落地与环境适配基础规范.md`

---
## 1. 本文解决的问题

本文解决正式规范如何表达“我需要被怎样落地”的问题。

规范落地要求只描述正式规范为了进入运行环境需要被看见、复用、校验、触发、确认或被后续规范继续约束。它不指定环境能力，不直接创建适配措施，也不把某个环境的现有能力写成规范需求。

本文是 04 系列第一层：规范声明要求。后续由 `specs/04.02-LDVH能力保障规范.md` 判断 LDVH 应提供什么能力保障这些要求，再由 `specs/04.03-环境适配规范.md` 基于环境能力清单完成环境适配。

---
## 2. 基本边界

规范落地要求必须遵守以下边界：

1. 要求来自正式规范自身的治理需要；
2. 要求不得来自某个环境当前是否支持；
3. 要求不得把 Skill、Hook、Agent、Command、Code、Web 等机制写成唯一实现方式；
4. 要求可以提示候选保障机制，但最终能力组合由 04.02 判断；
5. 要求可以在环境适配中降级执行，但不得被环境能力不足改低；
6. 要求稳定后应能被 Code、Web、入口摘要、工作对象或可查询的落地检查流程消费。

规范文档可以在自身“规范落地要求”章节声明要求，也可以由 04 系列、Code 或可查询的落地检查流程在检查时识别缺失要求并形成修改建议。未经正式规范吸收的 studies、sources、对话判断或环境输出，不得直接成为正式落地要求。

---
## 3. 落地要求类型

LDVH 当前使用七类规范落地要求。

| 类型 | 含义 | 常见触发 | 后续保障方向 |
|---|---|---|---|
| 上位约束承接要求 | 本规范是其他规范、流程、对象或检查的上位依据，需要后续持续遵守 | 总纲、基础规范、字段契约、状态机、边界规则变化 | 规范引用、索引、Code 检查、人工降级检查、Human Gate |
| 入口可见要求 | AI 进入项目、场景或流程时需要看见本规范的入口、摘要或 STOP 点 | 新增入口、规则边界、场景路由、事实源提示 | Rules / Instructions、AI 统一入口、薄引用、目录索引 |
| 流程复用要求 | 本规范包含重复、多步骤、可标准化执行的流程 | 频繁执行的检查、创建、迁移、收口、回写流程 | Skill、Command、工作流程、操作清单、Code wrapper |
| 子 Agent 思考要求 | 本规范需要独立上下文、专项视角、并行审查或权限隔离 | 架构争议、跨环境比较、复杂审阅、多角色判断 | Agent / subagent、主控多视角审阅、Human Gate；具体流程可执行性应查询 40 工作流程集合索引 |
| 确定性执行要求 | 本规范包含可机械检查、解析、聚合、测试或受控写入的规则 | 字段、编号、引用、矩阵、状态、路径、命令、测试 | Code、命令入口、CI、测试、校验器、结构化输出 |
| Human 交互要求 | 本规范要求 Human 看见、确认、授权、验收或选择 | 高影响写入、状态流转、删除、权限、长期配置、完整支持声明 | Human Gate、Web、对话确认、结构化问询、审批提示 |
| 生命周期触发要求 | 本规范要求在提交、写入、变更、停止、审阅或对象状态变化时触发检查 | 规范变更、适配措施变化、Task 状态变化、Code/Web/Skill 边界变化 | Hook、CI、自动运行、命令检查、人工降级检查 |

七类要求可以组合出现。同一规范不需要机械覆盖所有类型，只声明真实需要进入运行环境的要求。

---
## 4. 声明字段

正式规范声明落地要求时，建议使用以下字段：

| 字段 | 必填 | 含义 |
|---|---|---|
| 落地要求 | 是 | 使用本文 §3 的要求类型 |
| 要求内容 | 是 | 本规范希望被怎样看见、执行、确认、校验或触发 |
| 保障机制 | 是 | 候选保障机制，可以是 Rules、Skill、Agent、Hook、Code、Web、Human Gate、Command、CI 或人工降级 |
| 同步类型 | 是 | 入口提示、流程复用、检查输入、校验实现、环境治理、触发保障等同步方向 |
| 触发条件 | 是 | 何时需要检查该要求是否同步到能力保障和环境适配 |

字段中的“保障机制”只表示候选方向，不代表某个环境已经具备能力，也不代表适配措施已经存在。是否进入 Rules、Skill、Agent、Hook 四类必备部署入口，由 04.02 基于能力保障规则判断；规范落地要求不得直接指定必须由某个环境的某项原生能力实现。

---
## 5. 类型选择规则

选择落地要求类型时，应按以下规则判断：

1. 如果规范变化会影响后续规范、流程或对象，应声明上位约束承接要求；
2. 如果 AI 执行任务前必须知道某个边界，应声明入口可见要求；
3. 如果某段操作会反复执行且步骤稳定，应声明流程复用要求；
4. 如果判断需要独立视角或并行审查，应声明子 Agent 思考要求；
5. 如果可以机械检查、解析、测试或受控写入，应声明确定性执行要求；
6. 如果需要 Human 选择、授权、验收或承担风险，应声明 Human 交互要求；
7. 如果需要在事件发生时稳定触发，应声明生命周期触发要求。

不得因为某个机制存在就反推要求。例如环境有 Skill 并不意味着规范必须声明流程复用要求；环境有 Hook 也不意味着规范必须声明生命周期触发要求。要求必须来自规范本身。

## 6. 与 04.02 / 04.03 的关系

本文只输出规范落地要求。后续消费关系如下：

| 消费方 | 消费方式 |
|---|---|
| `specs/04.02-LDVH能力保障规范.md` | 将要求转换为 LDVH 能力保障组合、能力缺口和建设优先级 |
| `specs/04.03-环境适配规范.md` | 将能力保障组合基于环境能力清单适配为环境入口、流程、校验、降级和缺口 |
| 可查询的落地检查流程 | 读取要求、能力保障和环境适配，现场检查环境能否执行；流程可执行性应查询 40 工作流程集合索引 |
| Code | 对可机械化要求执行文档、字段、引用、路径、矩阵或状态校验 |
| Web | 把需要 Human 看见和确认的要求形成派生视图或受控轻写入入口 |

如果 04.02 或 04.03 发现某项要求无法保障或无法适配，应记录缺口和降级，而不是回头降低本文中的要求类型。

---
## 7. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增或删除七类落地要求类型；
2. 将某个环境能力写成规范落地要求；
3. 删除某项已被 04.02、04.03、Code、Web 或可查询的落地检查流程消费的要求；
4. 允许没有落地要求的规范直接创建长期适配措施；
5. 允许 studies、sources 或对话判断绕过正式规范直接成为落地要求。

检查规范落地要求时，应确认：

| 检查项 | 标准 |
|---|---|
| 要求来源 | 来自正式规范自身治理需要 |
| 类型有效 | 使用本文七类要求或经 Human Gate 扩展的新类型 |
| 字段完整 | 包含要求内容、保障机制、同步类型和触发条件 |
| 环境中立 | 未把 Trae、Codex 或其他环境能力写成要求来源 |
| 后续可消费 | 能被 04.02、04.03、Code、Web 或可查询的落地检查流程继续处理 |

## 8. 规范落地要求

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 正式规范声明落地要求时应遵守本文类型和字段规则 | 本文、04 父文档、Human Gate | 规范治理 | 落地要求类型、字段或声明边界变化时 |
| 入口可见要求 | AI 处理规范落地要求时应能定位本文 | 04 父文档、入口摘要、40 索引、人工降级检查 | AI 执行入口提示 | 本文标题、定位、类型表或字段表变化时 |
| 流程复用要求 | 落地要求识别和检查应形成可复用步骤 | 04.02 能力保障、Skill、Command、Code 检查 | 流程复用 | 新增规范或批量检查规范落地要求时 |
| 确定性执行要求 | 后续 Code 应能检查规范落地要求章节、类型和必要字段 | `code/specs_validate.py` 扩展、正反样例 | 校验实现 | 字段契约稳定时 |
| 生命周期触发要求 | 正式规范变化后应检查落地要求是否需要同步 | Code、人工降级检查、可查询的落地检查流程 | 触发保障 | specs 新增、重命名、删除或要求章节变化时 |

## 9. 待补齐事项

1. 需要确认 Code 校验是否要求每篇正式规范都必须有“规范落地要求”章节；
2. 需要通过可查询的落地检查流程确认如何展示缺失、过期或不可适配的落地要求；
3. 需要继续补齐字段校验、正反样例和检查口径。
