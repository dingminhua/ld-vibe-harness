# LDVH 基础设施工具层设计

> 创建日期：2026-06-03
> 定位：LDVH 基础设施工具层的项目内部设计评估，描述规则上下文路由器、Context Pack 生成器和通用对象校验框架的最小连续链路
> 调研边界：不直接构成强制规则
> 执行效力：无，结论需进入 specs 正文区或 ADR 后才成为稳定规则
> 上位依据：`specs/14-Code实现与工具规范.md`
> 相关规范：`specs/03-文档基础规范.md`、`specs/03.01-规范文档规范.md`、`specs/07-工作模型基础规范.md`、`specs/20-工作模型集合索引.md`

---

## 1. 文档定位

本文只描述三个基础设施工具的连续链路，不展开每个工具的完整产品能力。三个工具均为只读 Tools，不写入任何事实源。

本文位于 `specs/evals/`，不进入 specs 正文编号体系，不替代 `specs/14-Code实现与工具规范.md` 的原则定义。

---

## 2. 最小连续链路

```
Task Intent
  → 规则上下文路由器（识别场景，确定读取范围）
  → Context Pack 生成器（按范围聚合 Git 事实源，生成结构化上下文）
  → 通用对象校验框架（消费上下文，输出校验报告）
```

三者可独立使用，也可串联。串联时后一节点只消费前一节点的结构化输出。

---

## 3. 三个节点的最小职责

### 3.1 规则上下文路由器

- 输入：项目路径、任务意图描述、目标文件路径
- 输出：上下文路由报告（需读取的 specs 章节、场景规则路径、Human Gate 风险、Change 记录提醒）
- 不负责：直接执行校验、写入事实源、调用 AI/Skill/Agent

### 3.2 Context Pack 生成器

- 输入：路由报告（或其他指定的文件/章节列表）
- 输出：结构化上下文包（每个数据项带 Git 文件路径和行号，来源可追溯）
- 不负责：判断任务是否合规、修改事实源、生成长期事实

### 3.3 通用对象校验框架

- 输入：对象类型 + 对象路径（或 Context Pack）
- 输出：结构化校验报告（字段完整性、状态合法性、引用有效性、格式合规性）
- 不负责：替代 Human Gate、自动修复、自动状态流转

---

## 4. 连续性规则

- 每个节点输出必须可追溯到 Git 文件事实源（`specs/14-Code实现与工具规范.md` §4）
- 任一节点不得把工具输出升级为事实源（`specs/14-Code实现与工具规范.md` §4）
- 任一节点不得绕过 Human Gate（`specs/14-Code实现与工具规范.md` §5.2）
- 任一节点不得调用 AI、Skill 或 Agent（`specs/14-Code实现与工具规范.md` §5.2）

---

## 5. 现有资源如何配合

三个基础设施工具不独立存在，需要以下现有资源提供输入和约束。

### 5.1 specs/ 规范文档

**路由器需要的：**

- `specs/01` §4 编号分区表 → 路由器据此将任务类型映射到 specs 编号段
- `specs/03-文档基础规范.md` §3 文档工作区三分契约 → 路由器据此区分正文、evals 和 refs
- `specs/03.01-规范文档规范.md` §2 正文区规则 → 路由器据此区分正式规范和应用剖面子文档
- 各对象规范（20-39）的字段契约和状态机 → 校验框架据此校验对象实例

**当前状态：** 编号分区（01 §4）、文档工作区三分契约（03 §3）和规范文档剖面（03.01）已就绪，可直接被路由器消费。对象规范（20-39）中的 active 工作模型可按成熟度逐步接入校验框架。

### 5.2 .trae/rules/ 规则文件

**路由器需要的：**

- 项目规则（`ldvh-project-rules.md`）中的任务类型 → 读取映射 → 路由器据此生成 specs 读取清单
- 场景规则（`ldvh-specs-rules.md`）中的场景约束 → 路由器据此判断是否需要进入场景规则
- 事实模型规则（`ldvh-fact-model-rules.md`）→ 路由器据此判断是否进入事实实例编辑场景

**当前状态：** 项目规则中的"入口"段落已包含任务类型到 specs 的映射，但格式是自然语言摘要。路由器需要能解析这段映射，或项目规则需要补充结构化映射表。

### 5.3 tools/ 现有工具

**校验框架需要消费的：**

- `fact_cli.py` 的 ADR 索引和查询能力 → 校验框架可调用其 ADR 引用完整性检查
- `specs_validate.py refs` 的引用检查 → 校验框架可调用其跨文档引用校验
- `commit_validate.py` 的格式检查 → 校验框架可调用其 Change 格式校验

**当前状态：** 现有工具各自独立，输出格式不统一。校验框架需要定义统一的校验结果格式，现有工具逐步适配或替换。

### 5.4 ldvh-base/ 事实实例

**校验框架需要的：**

- ADR YAML 实例（`ldvh-base/adrs/`）→ 校验框架按 21.06 Contract 校验字段
- Change YAML 实例（`ldvh-base/changes/`）→ 校验框架按 22 规范校验字段

**当前状态：** ADR 实例已就绪，Change 尚未创建 YAML 实例（当前以 Git commit message 为事实实例）。校验框架先覆盖 ADR 校验。

### 5.5 Skills

**不直接配合：** 三个工具均为只读 Tools，不调用 Skill（依据 `specs/14-Code实现与工具规范.md` §5.2）。AI 或 Skill 可选择调用工具，但工具不反向编排 Skill 流程。

## 6. 测试方式

依据 `specs/14-Code实现与工具规范.md` §8：

- 每个工具在 `tools/` 下新增 Python 文件，对应 `tests/tools/` 下 pytest 测试文件
- 测试输入使用测试夹具或最小样例文件，不依赖聊天记忆或运行时缓存
- 测试覆盖该工具实际承担的职责：读取、解析、校验、聚合、上下文包生成
- 校验框架必须测试：写入前校验失败会阻止写入
- 无法自动化覆盖的行为，记录原因和替代检查方式

- 本文在基础设施工具设计变更时更新
- `specs/14-Code实现与工具规范.md` 原则变更时，评估本文是否需要同步
- 本文不维护工具 CLI 详细命令、JSON/YAML schema 或实现细节 — 这些跟随 `tools/` 代码和 `tests/` 测试
