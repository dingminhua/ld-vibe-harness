## 一、评估背景

specs-v2 是 PM Kit 规范体系的早期设计稿，采用与当前 specs/ 不同的术语体系（PM Kit vs LDVH、pm-kit-base vs ldvh-base）和文档组织方式。当前 specs/ 已形成成熟的规范体系，包含 60+ 文件。本评估旨在识别 specs-v2 中 specs/ 尚未覆盖的独特内容，为删除 specs-v2 前的吸收决策提供依据。

### 1.1 术语映射

| specs-v2 术语 | specs/ 对应术语 |
|---|---|
| PM Kit | LDVH |
| pm-kit-base | ldvh-base |
| specs-v2/ | specs/ |
| 管理对象 | 事实模型对象 |
| 对象实践 | 对象主文档 + NN.01-NN.06 子文档 |
| 程序辅助 | Tools (PyTools) |
| 工具展示 | Web |

### 1.2 结构差异

| 维度 | specs-v2 | specs/ |
|---|---|---|
| 对象文档结构 | 单文件"对象实践" | 主文档 + 6 子文档 (Rules/Skill/Agent/Tools/Web/Contract) |
| 基础规范层 | 10-13 四层载体 + 14 管理对象 | 10 事实源 + 11 AI协作 + 12 工具 + 13 事实模型 + 14 行动模型 |
| 流程文档 | 50-56 独立编号 | 无独立流程文档 |

## 二、高价值内容（specs/ 缺失，建议吸收）

### 2.1 Memo 备忘对象

- **来源**：22-Memo-备忘对象实践.md
- **specs/ 现状**：无 Memo 对象
- **独特价值**：Memo 填补了"尚未任务化但有保留价值的输入、发现和提醒"这一对象空白。当前 specs/ 中，这类信息缺乏正式承载对象，容易丢失或被误创建为 Task/ADR。
- **核心内容**：
  - 准入条件：有保留价值但当前无法/不应直接任务化
  - 状态机：open → converted / closed
  - 转化关系：Memo → Task / ADR / Risk / Pitfall
  - 不应创建 Memo 的 9 类场景（防止过度 Memo 化）
- **吸收建议**：在 specs/ 中新增 Memo 事实模型对象，遵循 specs/ 的主文档+6子文档结构
- **适配工作**：术语替换、路径替换（pm-kit-base → ldvh-base）、子文档拆分

### 2.2 Profile 项目档案对象

- **来源**：26-Profile-项目档案对象实践.md
- **specs/ 现状**：无 Profile 对象
- **独特价值**：Profile 提供项目身份登记、路径映射和项目名册（roster），是多项目产品管理的基础。当前 specs/ 缺乏项目身份和路径映射的正式对象。
- **核心内容**：
  - product.yaml 结构定义（product 段 + roster 段）
  - 单项目产品 vs 多项目产品的判定方式
  - Profile 是 AI 进入项目时首先读取的事实源
  - 修改 Profile 必须触发 Human Gate
- **吸收建议**：在 specs/ 中新增 Profile 事实模型对象
- **适配工作**：需要评估 LDVH 是否需要多项目产品支持；如果不需要，Profile 可简化为单项目版本

### 2.3 开发实践规范

- **来源**：55-开发实践规范.md
- **specs/ 现状**：无开发实践规范
- **独特价值**：定义项目必须具备的开发实践事实源（技术栈、启动运行、检查命令、修改类型与局部验证要求、开发完成汇报要求、技术红线）。当前 specs/ 缺乏对"AI 进入项目后如何知道怎么跑、怎么检查、怎么验证"的规范。
- **核心内容**：
  - 7 类修改类型的必须执行项和通过标准表
  - AI 不得凭惯例推断检查命令
  - 开发完成汇报必须包含验证结果
  - 前端修改必须浏览器验证
  - 实践沉淀规则（遗漏步骤时补充事实源）
- **吸收建议**：在 specs/ 中新增开发实践规范，或在行动模型中增加开发实践场景
- **适配工作**：需要与 LDVH 的对象模型对齐，确定存放位置（docs/04 或 specs/ 新编号）

### 2.4 交付实践规范

- **来源**：56-交付实践规范.md
- **specs/ 现状**：无交付实践规范
- **独特价值**：定义项目必须具备的交付实践事实源（发布状态声明、发布形态、发布前检查、构建部署步骤、发布后验证、回滚方案、发布记录要求）。与 55 开发实践规范互补。
- **核心内容**：
  - AI 不得凭惯例推断发布步骤
  - 发布前检查不可跳过
  - 发布后验证不可省略
  - 无发布流程项目仍需保留声明文件
- **吸收建议**：与 55 开发实践规范一同吸收
- **适配工作**：同 55

### 2.5 初始化流程

- **来源**：50-PMKit初始化流程.md
- **specs/ 现状**：无初始化流程规范
- **独特价值**：定义项目接入 LDVH 时的结构化初始化流程，包括产品/项目类型判定、L0/L1 规则评估、Skill/Agent 评估、事实源目录评估、自动创建/Human Gate/禁止创建的内容分类。
- **核心内容**：
  - 产品形态判定（单项目/多项目治理/多项目子项目）
  - 项目性质判定（业务代码/工具/规范文档/混合）
  - 允许自动创建的内容清单
  - Human Gate 后创建的内容
  - 不得自动创建的内容
  - 初始化报告格式
- **吸收建议**：在 specs/ 中新增初始化流程规范
- **适配工作**：术语和路径替换

### 2.6 审计流程

- **来源**：51-PMKit审计流程.md
- **specs/ 现状**：无审计流程规范
- **独特价值**：定义受管理项目的合规审计流程，包括规范审计、技术审计、全量审计三种类型，以及审计发现分流规则和快照规则。
- **核心内容**：
  - 审计类型：规范审计 / 技术审计 / 全量审计
  - 审计发现分流：Task / 待决策 Task / Memo
  - 回链要求：每条发现必须记录 linked_task_id / linked_memo_id
  - 快照规则：98-技术审计.md / 99-规范审计.md，只追加不修改
  - 审计报告格式
- **吸收建议**：在 specs/ 中新增审计流程规范
- **适配工作**：术语和路径替换

### 2.7 推荐自建 Agent 清单

- **来源**：11.05-推荐自建Agent清单.md
- **specs/ 现状**：无推荐 Agent 清单
- **独特价值**：提供了 6 个推荐自建 Agent 的详细定义（规范治理审查员、审计员、AI 协作架构师、WebTools 产品审视员、工具链架构师、文档工程师），以及不建议自建的场景。对 LDVH 的 Agent 规划有直接参考价值。
- **核心内容**：
  - 6 个推荐 Agent 的英文标识、模式、调度方式、适用场景、核心职责、职责边界
  - 不建议自建 Agent 的 3 类场景
  - 首批建设建议（3 个以内 / 5 个以内）
  - 8 条落地约束
- **吸收建议**：吸收到 specs/11.03-Agent机制规范 或作为独立评估文档存入 specs/evals/
- **适配工作**：Agent 名称从 pmkit-* 改为 ldvh-*，职责描述适配 LDVH 体系

## 三、中价值内容（specs/ 部分覆盖，建议选择性吸收）

### 3.1 管理对象规范与载体映射

- **来源**：14-管理对象规范.md + 14.01-管理对象落地载体映射.md
- **specs/ 现状**：specs/13 定义事实模型基础，specs/14 定义行动模型基础，specs/20 定义事实模型集合索引
- **独特价值**：
  - specs-v2/14 提供了 11 个核心管理对象的分类体系（核心执行实体/意图和入口/决策和风险/支撑和记录），比 specs/20 的索引更结构化
  - specs-v2/14.01 提供了每个对象到 6 种载体（事实源/Rule/Skill/Agent/程序/工具）的完整映射，specs/ 无此映射
  - specs-v2/14 定义了对象实践文档的章节骨架标准（§9.6），specs/ 的子文档结构（NN.01-NN.06）是另一种组织方式
- **吸收建议**：
  - 载体映射概念值得吸收到 specs/20-事实模型集合索引 中
  - 对象分类体系可参考但需适配 LDVH 的对象集（LDVH 有 Intent/Evidence/Task 等，但无 Risk/Dependency/Artifact/Checklist）
  - 对象实践文档骨架标准不需要吸收（specs/ 已有自己的 NN.01-NN.06 结构）

### 3.2 框架对象

- **来源**：15-框架对象.md
- **specs/ 现状**：无"框架对象"概念
- **独特价值**：区分"核心管理对象"（业务实体）和"框架对象"（基础设施：Rules/Skill/Agent/Profile/Context/Scenario/Gate），明确框架对象无独立状态机、不被管理对象直接引用。
- **吸收建议**：概念值得吸收到 specs/13 或 specs/00 中，作为对象分类的补充说明。但文档本身较浅，只需吸收概念而非全文。
- **适配工作**：LDVH 已有 Rules/Skill/Agent 的机制规范，Context/Scenario/Gate 需评估是否需要独立定义

### 3.3 多角色讨论设计规范

- **来源**：11.04-多角色讨论设计规范.md
- **specs/ 现状**：specs/51-multi-role-thinking-多角色思考.md
- **独特价值**：
  - specs-v2/11.04 提供了 20 个角色的详细矩阵（6 维度：产品/需求、技术架构、质量/QA、安全/治理、AI/工具链、工程流程）
  - 变更类型-角色映射表（12 种变更类型的默认角色组合）
  - 角色筛选与精简规则（超过 8 个时精选到 5-8 个）
  - 轻量模式 vs 建议升级模式的区分
  - 结构化输出格式
- **吸收建议**：角色矩阵和变更类型-角色映射可补充到 specs/51 中。但需注意 specs/51 已有自己的多角色思考方法，应评估是否兼容。
- **适配工作**：角色矩阵中的"PM Kit 规范"来源需替换为 LDVH 规范

### 3.4 工具展示规范

## 六、风险与注意事项

1. **术语冲突**：specs-v2 使用 PM Kit 术语体系，直接复制会导致术语不一致。所有吸收内容必须完成术语适配。
2. **结构冲突**：specs-v2 的对象实践是单文件结构，specs/ 是主文档+6子文档结构。吸收新对象时必须遵循 specs/ 的结构。
3. **对象集差异**：specs-v2 定义了 11 个核心管理对象（含 Risk、Dependency、Artifact、Checklist），LDVH 当前只有 ADR/Change/Pitfall/Intent/Evidence/Task/multi-role-thinking。吸收时需评估 LDVH 是否需要 Risk/Dependency 等对象。
4. **路径差异**：specs-v2 使用 pm-kit-base，LDVH 使用 ldvh-base。所有路径引用必须替换。
5. **编号冲突**：specs-v2 和 specs/ 的编号体系不同（如 specs-v2/14 是管理对象规范，specs/14 是行动模型基础规范）。吸收新内容时需分配新的 specs/ 编号。
6. **Brief/TaskSet 二选一**：specs-v2 中 Brief 和 TaskSet 是同一概念的两次命名，吸收时只需选一个。

## 七、总结

specs-v2 共 28 个文件，评估结果：

| 价值等级 | 文件数 | 说明 |
|---|---|---|
| 高价值（建议吸收） | 7 | Memo、Profile、开发实践、交付实践、初始化流程、审计流程、推荐Agent清单 |
| 中价值（建议选择性吸收） | 7 | 管理对象规范+载体映射、框架对象、多角色讨论、工具展示、程序辅助、事实源增强、管辖项目流程 |
| 低价值（建议不吸收） | 14 | 已有等价对象实践(4)、已有等价基础规范(3)、Brief/TaskSet重复(2)、总纲(1)、ADR/Task/Pitfall/Change对象实践(4) |

**核心结论**：specs-v2 中最有价值的是 specs/ 完全缺失的新对象（Memo、Profile）和新流程（初始化、审计、开发实践、交付实践），以及推荐 Agent 清单。这些内容填补了 LDVH 规范体系的真实空白。其余内容要么已被 specs/ 覆盖，要么可通过增强现有 specs/ 文档获得。
