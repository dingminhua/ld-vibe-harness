# V4 V3 事实对象全量逐条迁移决定

> 记录性质：本文记录 Human 对 V3 事实实例进入 V4 的明确范围决定及后续实施边界。它不是规则源，不自行授权迁移写入，也不证明迁移规范、行动模板、Code、清单或任何对象迁移已经完成。
> 决定日期：2026-07-15
> 当前状态：不可变基线、decision-independent source characterization、正式 successor 契约与 34 行动模板已建立；语义审核和生产实例尚未开始

## 1. Human 决定

V3 的全部事实对象都必须依据 V4 当前事实对象模型逐条迁移，包括已经关闭、完成、解决、丢弃或处于其它终态的对象。不得因为对象已关闭、内容较旧、状态不再使用、历史实现已经归档或当前默认召回不包含终态，就把它排除在迁移范围之外。

2026-07-16，Human 对正式契约前的两项全局策略明确决定“两个都按推荐”：

1. 全部 V4 target 都是当前新建 successor，使用 Code 分配的新 V4 身份和实际迁移创建时间；V3 ID、原始时间及缺时区情况只保留在 immutable ledger/source refs，不猜测时区，不冒充 V4 托管时间或历史领域事件时间；
2. 严格使用当前五种 V4 事实类型，不新增“历史记录”伪类型或迁移专用终态；一项仍无法合法承接时，只暂停该项并逐项交还 Human。

该决定改变的是 V3 实例收口范围，不恢复 V3 Schema、字段、状态、路径、orchestration、关系或实现效力。V3 内容必须按 05 与 20–24 的当前语义重新审核和承载，不能把旧文件改名后直接放入 V4 当前位置。

## 3. “逐条迁移”的完成含义

未来迁移必须建立 92 项闭集清单，每个 V3 源对象各有且只有一个主清单项，并至少记录：

1. V3 类型、ID、规范化源路径、内容指纹、Git 版本和原状态；
2. 当前语义审核、仍有价值的内容、应退出的旧实现细节和证据缺口；
3. V4 目标类型、稳定引用和实际承载路径；
4. 发生拆分或合并时，全部 V3 source 与全部 V4 target 的双向可追溯映射；
5. 未迁内容及理由、来源/时间/关系/证据修复、机械和语义验证结果；
6. 实际写入、回读、Git 历史锚点和失败/残留状态。

逐条审核不强制旧对象与 V4 对象机械 1:1。根据当前语义可以 1:1 重建、拆分为多个 V4 对象、多个来源合并为一个不丢失来源的 V4 对象，或重新判断应由另一 V4 事实类型承载。但每个 V3 对象都必须能从清单回指至少一个实际 V4 承接结果；单纯标记 `history-only`、留在 archive、不再适用或“不准入”默认不算完成迁移。某一对象确实无法由任何 V4 类型合法承接时必须暂停该项并交还 Human，不能静默豁免。

## 4. 终态和历史边界

旧状态不得按名称机械映射。特别是：

- V3 Spark `resolved` 不自动等于 V4 `routed`；
- V3 WorkCase `closed` 不自动满足 V4 的结果包、验证、独立审核、Human 关闭确认和剩余责任承接；
- V3 `active` Study/Pitfall 不自动成为 V4 `active` 当前入口；
- 旧对象缺少时区、关闭时间、来源版本、适用边界、证据或当前关系时，必须补充可验证依据、缩小声明或进入 Human Gate，不得编造历史决定。

已经关闭的 V3 对象仍然必须迁移，但迁移不得伪造 V4 当时实际发生过的审核、批准或验证。05 §7.4 已经闭合该 blocker：旧终态只是源观察，每个 successor 都是一个新 V4 对象，只能从目标类型当前合法初态创建；历史终态内容如何进入该新对象仍必须逐项语义审核。

## 5. 当前能力缺口

当前 `create-fact-object` 只允许具体类型的合法新建初态，并由 Code 分配当前 ID 和时间；`update-fact-object` 只更新已经存在的 V4 对象。05 §7.4 和 34 现已定义正式 successor 契约与行动结构，但当前仍没有 semantic ledger Schema、拆分/合并映射 verifier、可恢复批处理、durable journal 或逐项 receipt 能力。31 和 32 仍不因 34 成立而扩张为迁移实现。

因此，在 semantic ledger、92 项逐源审核、全量 dry-run、可恢复写入和完整回读成立前，不创建或改写任何 V4 迁移对象。库存完成、字段转换草案、dry-run 或部分批次成功都不得声明为 V3 事实迁移完成。

## 6. 当前实施顺序

2026-07-15 Human 调整当前目标：立即暂停 Web V4 bridge 和原生 Windows 验证，把两者列为发布前后续事项；先完成 92 项迁移与验证，再建立 bootstrap/resume，并完成真实跨会话 dogfood。此前 Web bridge 工作只停放在独立本地分支，不合入 `dev-v4`、不推送。当前按以下顺序实施：

1. 建立迁移专项调查、92 项不可变机器基线、decision-independent source characterization 和只读验证器；该阶段零 V4 实例；
2. 取得历史身份/时间及无法归类对象的 Human 全局决定，完成正式迁移契约和 34 行动模板准入；已完成；
3. 建立 ledger Schema、全量双向映射校验、无写 dry-run、可恢复/幂等写入与完整回读；
4. 完成 92 项逐源语义审核，再用同时覆盖非终态、终态、拆分、合并、时间缺失和关系修复的 pilot 验证；
5. 按 target 依赖拓扑分批迁移全部 92 项，每批实施前 subagent 审核，完成后独立提交；
6. 在 92 项均有实际 V4 承接、验证和 Git 锚点后关闭 V3 实例迁移 Gate；
7. 使用迁移后的真实事实建立 bootstrap/resume 并完成真实跨会话 dogfood；
8. 发布前恢复 Web V4 bridge、原生 Windows、CI、开源资料和最终验收。

## 7. 完成边界

V3 事实迁移完成必须同时满足：92 个源对象无遗漏；每项有可回指清单、实际 V4 承接、来源与证据处置、机械与语义验证及 Git 锚点；全部拆分/合并关系闭合；终态对象没有被跳过或冒充 V4 原生历史；没有未交还的失败、残留或无法承接对象。

本文、05 §7.4 与 34 共同证明 successor 身份/时间、旧终态边界和行动承载已经建立；它们不证明任何 V4 实例、完整 semantic ledger/映射、92 项逐源审核、executor 或迁移 Gate 已经完成。
