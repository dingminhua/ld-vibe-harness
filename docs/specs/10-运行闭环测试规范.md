## 1. 本文解决的问题

本文解决 LDVH 如何把运行闭环、工作流程、环境能力承接、Code / Web 实现和 AI 行动控制转化为可验证测试的问题，包括：

1. 运行闭环测试的定义、目标和事实源边界；
2. 如何把工作流程场景、Skill 使用场景、Human Gate 场景、Code 校验和事实源回写建模为测试用例；
3. 自动化测试如何辅助 AI 发现规范、测试用例、运行投影、Code、Web 或事实源中的问题；
4. AI 发现问题后应按什么顺序自修正规范、测试用例、运行投影或实现实体；
5. 如何检查完成判断是否具备外部验证、可复现证据、失败暂停和事实源回写；
6. 运行闭环测试与 04、06、07、08 及 40-59 工作流程规范的关系。

本文不直接定义具体 Skill，不直接修改既有 Skill 实体，不替代具体工作流程规范，也不替代 Code 或 Web 实现规范。

## 2. 与 00 总纲的关系

00 定义 LDVH 通过理念、规范、事实源和工作流程约束 AI 稳定工作，并要求结果有证可验。运行闭环测试承接这一目标，把“AI 应如何行动”和“AI 完成后如何证明”进一步转化为可复现、可检查、可迭代的测试用例，使 AI 不只依赖会话经验发现问题，而能依据规范化测试发现问题、定位原因并提出修正。

06 定义工作流程的 Context、Scenario、Gate、证据留存、执行中问题分流、反合理化和失败暂停规则。本文不重复定义这些行动规则，而是规定如何把 06 的行动规则转化为测试输入、预期行为、停止条件、证据检查、失败诊断和修正顺序。

本文是 LDVH 运行闭环测试的权威位置。工作流程基础规则由 `docs/specs/06-工作流程基础规范.md` 定义；具体工作流程的行动特有可测试性锚点由 `docs/specs/03.05-工作流程文档规范.md` 要求嵌入对应流程主文档；Skill、Agent、Rules 等开发环境能力由 `docs/specs/04.03-环境能力清单与环境适配规范.md` 定义；Code 与 Web 边界由 `docs/specs/07-Code确定性执行实现规范.md`、`docs/specs/08-Web信息同步实现规范.md` 定义。本文只定义跨流程、跨机制、跨事实源的测试建模和测试反馈闭环。

## 3. 权威领域

本文的权威领域包括：

1. 运行闭环测试的定义和目标；
2. 运行闭环测试用例的最小组成；
3. 测试对象、测试类型和测试覆盖要求；
4. 自动化测试的输入、输出和事实源边界；

8. 运行闭环测试的 Human Gate 与检查要求。

## 4. 运行闭环测试定义

### 4.1 运行闭环测试

运行闭环测试是 LDVH 对运行闭环和 AI 行动控制规则的测试建模方法，用于将规范中的工作流程、环境能力承接、Human Gate、事实源读取、事实源回写、失败降级、Code / Web 行为和机制边界转化为可复现测试用例。

运行闭环测试的目标不是证明 AI 永远正确，而是让 AI 在执行前、执行中或机制升级前，能够依据测试用例发现以下问题：

1. 规范缺失、冲突或表述不可执行；
2. 工作流程的 Context、Scenario、Gate 或回写边界不完整；
3. Skill 触发条件、不适用场景、输入输出、交还主控或失败处理不稳定；
4. Rules、Skill、Agent、Code、Web 或 Contract 的机制边界不一致；
5. 自动化工具无法检查关键约束或检查结果无法回写为事实；
6. 完成判断缺少外部验证、证据不可复现，或 AI 用推测性表述替代验证证据；
7. 失败后未按规范暂停、分流和重新验证，而是直接宣称完成或直接修改实现实体。

### 4.2 运行闭环测试与普通软件测试

运行闭环测试可以使用软件测试工具实现，但测试对象不是普通函数行为，而是 AI 行动控制行为。它测试的是 AI 是否按规范读取、判断、暂停、执行、回写和修正。

运行闭环测试不得把一次会话的临时成功视为稳定通过，也不得把 AI 自述、主观判断或不可复现截图作为稳定通过依据。只有测试用例、输入条件、预期行为、检查方式、验证证据、失败处理和回归结果均可复现时，才可作为稳定测试依据。

### 4.3 运行闭环测试与评估文档

项目评估文档可以提出测试建议，但测试建议只有进入正式规范或测试用例事实源后，才成为稳定测试依据。Code 实现和测试夹具只能承接或验证已归属的规范与测试用例事实源，不作为测试依据的权威来源。运行闭环测试应优先从正式规范和事实源生成，不得直接以聊天结论、临时评估结论、Code 夹具或一次性脚本作为长期测试规则。

## 5. 测试对象

运行闭环测试至少覆盖以下对象：

1. **工作流程规范**：测试 Context、Scenario、Gate、执行流程、回写要求和证据留存是否可执行；
2. **Skill 或运行投影调整**：测试某类流程是否具备创建或修改 Skill、Rules 摘要、Agent 定义摘要或运行入口的规范依据、测试用例和失败处理；
3. **Skill 实体**：测试 Skill 是否遵守上位规范、触发边界、输入输出和回写规则；
4. **Rules 投影**：测试 Rules 是否只承载入口摘要、压缩保护和运行时硬约束，不替代 specs；
5. **工具实现**：测试工具是否按规范读取、校验、生成、回写和报错；
6. **Human Gate**：测试需要人确认的场景是否暂停，且用户取消、暂缓或调整时不会继续执行；
7. **事实源回写**：测试稳定事实是否写入对应 Git 文件事实源，而不是停留在聊天、Skill 输出、Agent 输出或工具缓存；
8. **完成证据与关闭判断**：测试 acceptance、验证结果、Gate 条件、证据留存、状态流转和 closure 判断是否满足对应工作模型和工作流程要求；
9. **失败暂停与反合理化**：测试失败、证据不足、验证范围不足或长期降级场景中，AI 是否按 06 §6.10.1 暂停、分流并重新验证。

## 6. 测试用例建模

### 6.1 测试用例最小组成

一个运行闭环测试用例至少应包含：

1. `id`：稳定测试用例标识；
2. `title`：测试用例标题；
3. `target`：被测试的规范、流程、Skill、Rules、工具或事实源；
4. `scenario`：触发场景；
5. `given`：执行前事实源、上下文和前置条件；
6. `input`：用户输入、工具输入或模拟事件；
7. `expected_behavior`：AI 或工具应表现出的行为；
8. `expected_stop`：是否必须停止、暂停或触发 Human Gate；
9. `expected_evidence`：应产生或检查的证据；
10. `expected_writeback`：是否应写回事实源以及写回位置；
11. `failure_diagnosis`：失败后应优先判断的问题归属；
12. `repair_policy`：失败后允许的修正方向和禁止动作；
13. `expected_verification`：应执行或检查的验证方式、关键输出和可复现条件；
14. `expected_failure_handling`：验证失败、证据不足或无法复现时应暂停、分流、降级或触发 Human Gate 的规则。

### 6.2 测试用例来源

运行闭环测试用例应从以下来源生成：

1. 正式规范中的 Context、Scenario、Gate、执行流程和检查要求；
2. 工作模型中的准入条件、状态机、字段契约、验收和 closure 条件；
3. 环境能力在 LDVH 中的使用边界；
4. Human Gate、高风险变更和事实源回写要求；
5. 已发生的失败案例、误触发案例、漏触发案例和规范冲突案例；
6. 06 中的证据留存、执行中问题分流、反合理化和失败暂停规则；
7. Task、审计、Review 或具体工作流程中反复出现的证据不足、验证不可复现或关闭判断争议。

### 6.3 测试用例类型

运行闭环测试应覆盖以下类型：

1. **正向路径**：输入满足触发条件，AI 应进入对应流程或 Skill；
2. **负向路径**：输入不满足触发条件，AI 不应进入对应流程或 Skill；
3. **边界路径**：输入同时接近多个机制边界，AI 应按规范选择 Rules、Skill、Agent 或主控执行；
4. **缺失上下文路径**：事实源、规范或实例缺失时，AI 应停止并说明缺口；
5. **Human Gate 路径**：涉及写入、删除、状态流转、规范升级或高风险变更时，AI 应暂停确认；
6. **失败降级路径**：工具失败、权限不足、验证失败或规范冲突时，AI 应交还主控，不得强行继续；
7. **回写路径**：稳定事实产生后，AI 应写回正确事实源或说明尚未获得写入授权；
8. **完成证据路径**：AI 宣称完成、关闭 Task、确认审计结论或结束流程前，应能提供外部验证和可追溯证据；
9. **反合理化路径**：AI 使用“应该通过”“看起来没问题”等推测性表述替代验证时，测试应判定为失败或要求暂停分流；
10. **回归路径**：修正一个问题后，不得破坏既有正向、负向、Human Gate、失败降级和完成证据用例。

## 7. 自动化测试

### 7.1 自动化测试定位

自动化测试用于提高运行闭环测试的可复现性和检查效率。自动化测试可以检查文件结构、字段、路径、章节、引用、测试用例格式、工具输出和部分行为约束，但不得替代 Human Gate，也不得替代人对规范方向、风险级别和产品取舍的判断。

### 7.2 自动化测试输入

自动化测试的输入应来自 Git 文件事实源，包括：

1. docs/specs 正式规范；
2. 工作模型实例；
3. 运行闭环测试用例；
4. Rules、Skill、Agent 定义摘要或实体文件；
5. 工具实现与测试夹具；
6. 受控样例输入和预期输出。

自动化测试不得依赖不可复现的聊天记忆作为唯一输入。

### 7.3 自动化测试输出

自动化测试输出至少应包含：

1. 通过或失败结果；
2. 失败用例标识；
3. 失败位置；
4. 失败原因分类；
5. 建议修正方向；
6. 是否需要 Human Gate；
7. 是否可由 AI 继续提出补丁；
8. 验证证据是否存在、可复现、可回写；
9. 失败是否触发暂停、分流、降级或重新验证。

测试输出本身不是稳定事实。需要长期保留的测试结论、变更记录、风险、任务或决策必须写回对应事实源。

#### 7.3.1 过程输出验证边界

运行闭环测试可以验证过程输出是否按 06 §6.8.1、07、08 和 09 满足边界明示、来源追溯、回写分流、Human Gate 联动、主控交还和降级说明要求。测试目标是验证过程输出行为是否可复现，不是把测试输出本身变成稳定事实。

过程输出相关测试应覆盖：

1. 输出是否明确标注过程输出、候选建议、检查摘要、临时诊断或已回写事实；
2. 输出引用的事实、命令、测试、Human Gate 记录或 Web / Code 派生数据是否可追溯；
3. 产生稳定事实时是否写入正确权威位置，未回写时是否说明原因和残留风险；
4. 需要 Human 授权、接受长期降级、确认关键风险、批准写入或关闭任务时是否触发或引用 Human Gate；
5. Web 展示是否区分临时、候选、已回写、验证失败、降级和待确认状态；
6. Code 输出是否区分候选生成、确定性诊断、受控写入和写入后验证；
7. 验证失败、证据不足或无法复现时是否暂停、分流并避免宣称完成。

过程输出验证可以通过自动化测试、命令输出断言、结构检查、Web 交互测试、人工降级检查或审查清单实现。若当前环境无法自动化验证，应记录等价验证方式、未覆盖范围和后续分流，不得把一次性人工观察表述为稳定通过。

### 7.4 自动化测试分层

运行闭环测试自动化应分层实现：

1. **结构检查**：检查文件存在、命名、章节、字段和引用；
2. **规则检查**：检查禁止事项、必填项、状态流转和引用完整性；
3. **场景检查**：以测试用例模拟输入，检查应触发的流程、Skill、Gate 或停止条件；
4. **回写检查**：检查稳定事实是否写入允许位置，是否越权修改；
5. **证据检查**：检查完成判断是否具备验证方式、关键输出、回写位置和残留风险说明；
6. **失败处理检查**：检查失败后是否暂停、分流、降级、触发 Human Gate 或重新验证；
7. **回归检查**：检查新增或修改规则是否破坏既有用例。

## 8. AI 自发现与自修正

### 8.1 自发现

AI 可以依据运行闭环测试结果发现问题。发现问题时，AI 应先输出问题归属判断，而不是直接修改文件。

问题归属分为：

1. 规范缺失；
2. 规范冲突；
3. 测试用例缺失或错误；
4. Skill 或运行投影承接缺口；
5. Skill 实体实现偏差；
6. Rules 投影偏差；
7. 工具实现缺陷；
8. 事实源实例错误；
9. Human Gate 未确认或权限不足；
10. 验证证据不足或不可复现；
11. AI 反合理化、跳过失败暂停或错误宣称完成。

### 8.2 自修正顺序

AI 自修正应按以下顺序执行：

1. 若正式规范缺失或冲突，先提出规范修正；
2. 若测试用例不能覆盖问题，先提出测试用例修正；
3. 若规范不能指导运行投影或实现实体生成，先修正规范或运行投影记录；
4. 若实现实体未遵守已稳定规范，才修改实现实体；
5. 若工具实现不符合规范，才修改工具实现；
6. 若事实源实例不符合契约，按对象规范和 Human Gate 修正实例；
7. 若失败原因是验证证据不足、验证不可复现或 AI 跳过暂停，应先补齐验证方式、证据或分流记录，不得直接修改 Skill、Rules、Code、Web 或对象状态来掩盖失败；
8. 每次修正后运行相关验证和回归测试。

### 8.3 禁止直接修 Skill

Skill 失败不得直接推导为“修改 Skill”。在 LDVH 中，Skill 是规范和工作流程的运行入口，不是规则本身。任何 Skill 修改前，都应先检查对应规范、测试用例和环境适配映射是否已经稳定。

只有满足以下条件时，才允许修改 Skill 实体：

1. 上位正式规范已定义该行为；
2. 运行闭环测试用例已定义预期行为；
3. 失败原因已定位为 Skill 实体未遵守规范或测试用例；
4. 修改范围不新增规范未定义的规则、字段、状态或 Human Gate 条件；
5. 修改后能回跑相关测试。

### 8.4 失败暂停与反合理化处理

运行闭环测试发现验证失败、证据不足、结果不可复现或 AI 使用推测性表述替代验证证据时，应先判定为行动控制失败，而不是直接判定为实现缺陷。

处理顺序如下：

1. 确认失败是否来自正式规范、测试用例、运行投影、环境能力、工具实现、事实源实例或 Human Gate；
2. 检查 AI 是否按 06 §6.10.1 暂停继续宣称完成，并说明失败、证据不足或无法复现的原因；
3. 检查是否已按问题性质分流到 blocking、follow-up、Human Gate、Memo、Pitfall、ADR、独立审阅或具体工作流程；
4. 检查修复后是否重新执行相关验证，或记录无法验证的原因、残留风险和后续分流；
5. 只有失败归属明确为实现实体偏差时，才进入对应实现实体修改。

## 9. 与 Skill 和运行投影的关系

运行闭环测试是创建或修改 Skill、Rules 摘要、Agent 定义摘要、Hook、CI、Code 入口、Web 入口等运行投影前的前置约束。创建或修改这类实体前，应先完成以下检查：

1. 该能力是否应由 Skill 承载；
2. 上位规范是否已经定义流程边界；
3. 是否已有测试用例覆盖正常触发、负向触发、Human Gate、失败降级和事实源回写；
4. 测试失败时是否能判断修正规范、测试用例、环境适配映射还是实现实体；
5. 是否存在足够证据证明实现实体修改不是临时修补。

运行投影的质量，不以入口文本长度或实体数量衡量，而以触发稳定性、边界清晰度、输入输出可执行性、失败处理完整性、事实源回写正确性和测试可复现性衡量。

## 10. 与工作流程规范的关系

工作流程规范定义 AI 应如何行动，运行闭环测试定义这些行动如何被验证。具体关系如下：

| 维度 | 工作流程规范 | 运行闭环测试 |
|---|---|---|
| 关注点 | 行动规则 | 行动规则是否可复现验证 |
| 核心内容 | Context、Scenario、Gate、执行流程、回写、证据 | 用例、输入、预期行为、检查、失败诊断、修正策略 |
| 事实源 | docs/specs/40-59 具体流程规范 | 正式规范和测试用例事实源 |
| 验证实现 | 运行入口、Skill、Agent、Code 或 Web 的实际执行能力 | Code 测试、测试夹具、脚本、CI 或人工降级检查 |
| 失败处理 | 规定 AI 应如何停下或回写 | 判断失败属于规范、用例、运行投影、实现实体还是 Code |

具体工作流程规范应能派生出测试用例。行动特有可测试性锚点应写入对应工作流程主文档，按 `docs/specs/03.05-工作流程文档规范.md` 执行；具体测试用例、预期行为矩阵、失败诊断和回归用例应进入本文定义的测试用例事实源或 Code 测试实现。本文不为每个工作流程创建独立测试章节或测试子文档。若某个工作流程无法生成可复现测试用例，应优先检查该工作流程的 Context、Scenario、Gate 或回写要求是否过于模糊。

## 11. 测试用例事实源边界

运行闭环测试用例应作为稳定事实源维护。具体承载位置由后续 Code 规范、目录规范或运行闭环测试实现方案确定。

在承载位置稳定前，测试用例不得散落在聊天记录、临时脚本输出或 Skill 文档正文中。若必须临时记录，应回写到受控文档或任务证据中，并标注待归属位置。

测试用例事实源不得重新定义规范正文。测试用例只能表达“在某输入和前置条件下，应如何验证规范行为”。若测试用例发现规范未定义预期行为，应回到正式规范修正。

## 13. Human Gate 与检查要求

以下运行闭环测试相关行为必须触发 Human Gate：

1. 新增、修改或删除正式规范中的测试规则；
2. 创建、修改或删除稳定测试用例事实源；
3. 将测试失败结论用于修改 Skill、Rules、Agent、Code、Web 或 Contract 实体；
4. 自动化测试建议执行高风险变更、删除事实源或修改对象状态；
5. 测试结果显示规范冲突，需要选择修正规范方向；
6. AI 自修正将影响多个工作流程、多个工作模型或跨项目规则入口。

检查运行闭环测试时，应确认：

1. 测试用例是否有明确目标、输入、预期行为和失败诊断；
2. 测试是否能区分规范缺失、测试缺失、运行投影缺口和实体实现偏差；
3. 自动化测试是否只辅助检查，不绕过 Human Gate；
4. AI 是否先修正规范、测试用例或环境适配映射，再修改 Skill 或其他实现实体；
5. 测试输出中的稳定结论是否已按事实源边界回写；
6. 完成判断是否有外部验证、关键输出、证据归属和可复现路径；
7. 失败、证据不足、无法复现或长期降级时，AI 是否暂停并按 06 §6.10.1 分流；
8. 回归测试是否覆盖既有正向、负向、Human Gate、失败降级、完成证据和反合理化路径。
