## 1. LDVH 为什么存在

Vibe Coding 使 Human 能够用自然语言表达目标，由 AI 推理生成实现，门槛低、反馈快、产出多。但 AI 生成代码的本质不是确定性编译，而是基于开发环境上下文、模型训练经验和参数形成的概率性推理，因此天然存在上下文依赖、概率性输出和无状态等问题。

虽然目前 Vibe Coding 已经能够较好地完成单个功能、局部修复，也能在明确的测试目标和验收反馈下承担较长时间的连续工作。但真实开发不是单点工作的叠加，它往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是项目在持续演进中，如何避免从“开始还不错”逐渐变成“难以继续做”的问题。概括如下：

设计理念：

1. 以 AI 执行者为第一服务对象；
2. 以 LDVH Helper CLI 为基础服务形式；
3. 以事实源为信息锚点；
4. 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素；
5. 以 V1-V8 价值标准为行动标尺。

构成要素：

1. 用规范体系定义规则、边界和保障要求；
2. 用事实模型组织事实、状态、证据和经验；
3. 用行动模板沉淀可复用行动结构；
4. 用 Code 提供确定性解析、校验、受控操作和反馈；
5. 用 Web 桥接 Human 与 AI，呈现状态、风险和证据。

最终目标：

1. 让 AI、Human、Code 可以各展所长，使 Vibe Coding 推理更稳定、结果更可控、产出更高效；
2. 进而让环境、模型、使用者可以自由组合，使 Vibe Coding 使用更方便、选择更丰富、协同更顺畅。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于经验沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

LDVH 以 AI 执行者为第一服务对象。要说明这一点，需要先理解 AI 执行者的依赖、能力与本质。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——缺少可用工具或环境能力时，AI 容易停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的工具或环境能力，并把反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

这些依赖、能力与本质共同决定了 LDVH 的支撑方向：为 AI 提供可消费、可验证、可接续的稳定依据与协作条件，使其能够充分发挥自身能力，让长期项目中的判断有据、行动可续、结果可验。

## 3. 以 LDVH Helper CLI 为基础服务形式

LDVH 以 Helper CLI 为基础服务形式。AI 可以直接调用，环境 Hook、插件和 adapter 也可以在相应生命周期中调用同一服务能力，并将结果交给 AI。

Helper CLI 围绕当前任务和工作对象提供服务，帮助 AI 定位事实与规则、了解当前状态、调用 LDVH 已有能力、识别当前行动适用的要求，并明确结果如何验证、回写和接续。

Helper CLI 只在当前事项落入来源规范的适用范围时产生强制作用。命中具体规则时，AI 必须执行该规则规定的要求；未命中具体规则时，LDVH 不对 AI 的普通求解路径产生影响。

Helper CLI 的具体命令、响应格式、环境衔接和实现方式由后续相关规范承接；本文只定义其基础服务形式、作用和边界。

## 4. 以事实源为信息锚点

LDVH 以事实源为信息锚点，并提出两项要求：

1. 有 Git，可溯源。事实源以 Git 可追踪文件为唯一有效承载形态，稳定事实的形成、修改、验证和关闭都能回到明确的 Git 文件位置和 Git 溯源记录；聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图等只有回写到 Git 文件事实源并完成验证后，才可能成为稳定事实。

2. 有组织，可消费。事实源不是材料堆积，而是要形成清晰的事实组织：事实放在哪里，边界是什么，引用关系如何建立，状态如何变化，结果回写到哪里。组织清晰的事实源才能被 Code 消费，进而放大事实源的价值——让 AI 少读、少猜、少漂移，让验证、回写和接续有稳定入口，而不只是人能看懂的材料。

上述两项要求共同构成本文所称的事实源边界：符合两项要求，才是 LDVH 认可的事实源；不符合的，不得作为稳定事实的承载位置。后续本文中“事实源边界”均指这两项要求。

事实源承载管辖项目中需要稳定保留的事实、状态、证据、决策和经验，为 AI 理解项目现状、追溯既有依据、回写验证结果和接续后续工作提供稳定位置。

事实模型、Code 和 Web 可以承接、消费、展示或辅助回写事实，但不得替代事实源整体。具体事实源类型、证据规则、回写规则、吸收规则、Code 消费规则和 Git 溯源等规则，由后续相关规范承接；本文只定义上位原则。

## 5. 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素

LDVH 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素。这五类构成要素把规则、事实、行动、确定性反馈和 Human-facing 呈现分开归口，形成 AI 可定位、可行动、可验证、可交还的结构。

LDVH 的五类构成要素包括：

1. 规范体系。以 Code 可消费的 Markdown 组织 LDVH 的规则、边界、价值标准和保障要求，由正式 specs 正文及其授权附件共同构成 LDVH 规则源，为 AI 以及包括 Helper CLI 在内的 Code 能力提供可定位、可解析、可引用的规则依据，使 AI 能据此理解目标边界、识别适用场景并判断行动约束；
2. 事实模型。在事实源边界内组织需要对象化、状态化或证据化管理的事实，使结论、状态、证据和经验能够在事实源中稳定记录、关联、更新和消费；
3. 行动模板。沉淀重复场景中的可复用行动结构，明确适用条件、关键步骤、验证入口和交还方式，使 AI 在命中相应场景时能够稳定行动；
4. Code。提供解析、索引、聚合、校验、测试、上下文压缩和受控写入等确定性能力与反馈，并以 Helper CLI 作为面向 AI 执行者的基础服务形式，降低 AI 的读取、判断和验证成本；
5. Web。从事实源独立读取并呈现状态、风险、证据、待确认事项和验收信息，帮助 Human 理解项目情况、进行方向校正与决策。

五类构成要素用于确定 LDVH 内容的职责归口，不形成上下层级，也不直接决定具体实践是否准入。规则、对象、字段、附件、工具、Code 输出、Web 展示和派生机制等构成要素实践纳入 LDVH 前，必须归属于规范体系、事实模型、行动模板、Code 或 Web，并接受 V1-V9 价值判断；涉及稳定事实承载时，还必须符合事实源边界。

## 6. 以 V1-V8 价值标准为行动标尺

LDVH 以 V1-V8 价值标准为行动标尺。五类构成要素及其具体实践，都必须帮助 AI 获得以下一种或多种价值。

V1-V8 分别从定位、理解、边界、推进、判断、接续、沟通和积累八个方面进行判断。每项实践按照自身职责服务其中一项或多项价值；新增机制只有在为 AI 带来可辨认的净收益时，才具有纳入 LDVH 的价值。

本文所称“V1-V8 价值标准”，是表格列出的八项价值维度；“V1-V8 价值判断”是依据这些标准判断构成要素及其具体实践能否为 AI 带来相应价值；“行动标尺”表示这些标准对 LDVH 设计、纳入和使用的指导作用。表格中的“不满足时的表现”用于识别相应负担和风险。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | 能否帮助 AI 根据当前目标和工作对象，快速定位相关且来源明确的规则、事实和状态，以及可用能力的入口 | 信息存在但 AI 找不到；盲目搜索或全文读取；误用来源；遗漏关键规则、事实、状态或能力入口 |
| V2 | 充分理解 | 能否帮助 AI 将当前相关的目标、工作对象、规则、事实、状态、依赖关系和验收要求联系起来，形成充分、连贯且不过载的整体理解 | AI 找到了相关信息，但仍无法形成整体理解；关系、冲突或关键上下文被遗漏；上下文不足或过载造成误解 |
| V3 | 边界识别 | 能否帮助 AI 依据来源明确且可回指的规则、事实和当前状态，识别当前事项适用哪些要求、什么必须遵守、什么可以自主决定、什么情况必须暂停、暂停影响什么，以及哪些决定应交由 Human | AI 已理解当前事项，但仍发生规则适用误判、要求遗漏、作用外溢、越权推进、应停未停或错误恢复 |
| V4 | 稳定推进 | 能否帮助 AI 在 LDVH 已明确承接的事项中，复用适用的行动结构和可用能力，并及时获得能够支持后续调整或分流的确定性反馈 | AI 已明确目标和边界，但仍反复重建已有处理方式、遗漏关键要求、无效试错，或在缺少反馈时发生执行漂移 |
| V5 | 据实判断 | 能否帮助 AI 使受 LDVH 规则或项目事实约束的重要判断，以及关于状态变化、能力状态、环境接入和完成情况的结论与声明，保持在验证结果或当次可观察依据实际支持的范围内，并清楚区分已经证实、尚未证实和残留风险 | AI 将事实与推测混淆；以自述、工具成功、局部结果或静态存在代替范围匹配的依据；判断或声明超出实际证据范围 |
| V6 | 工作接续 | 能否帮助 AI 把当前项目后续工作需要的事实、状态、证据和决策稳定保留下来，使不同会话、执行者和阶段都能恢复这些信息、追溯其来源和变化并接续工作 | 当次工作已有可信结果，但后续执行者无法恢复依据、状态和决定，只能重复调查、重建状态或中断接续 |
| V7 | 清晰沟通 | 能否帮助 AI 在需要 Human 判断、授权、确认或验收时，清楚交还当前状态、依据、影响、风险和待决定事项，使 Human 能够作出对象与作用范围明确的回应，并使 AI 能够据此继续、调整或保持暂停 | AI 已识别需要 Human 参与，但交还内容仍然含混；Human 无法明确回应，或 AI 无法确定回应约束的对象、范围和后续行动 |
| V8 | 持续积累 | 能否帮助 AI 使当前工作中形成的可复用经验、反复问题以及规则或能力缺口，在后续事项中能够被复用或继续处理 | 当前项目可以接续，但相似事项仍然重复分析和试错；同类问题反复发生；已经发现的经验和体系缺口长期悬置 |

## 7. 规范保障要求

00 是 LDVH 的最高价值锚点。后续规范、附件、构成要素实践和派生机制不得削弱本文定义的存在理由、AI 第一服务对象、事实源边界、保障与衔接层、五类构成要素和 V1-V9。

00 不重复每篇规范都应具备的入口可见、结构校验、生命周期同步和 Code 消费等基础治理要求；保障与衔接由 01 统一定义，Specs 结构治理由 04 统一定义。本文只声明 00 作为最高价值锚点特有的上位约束承接要求。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续规范、附件、构成要素实践和派生机制必须承接本文定义的存在理由、AI 第一服务对象、事实源边界、保障与衔接层、五类构成要素、V1-V9 和 Human Gate 边界，不得改写、绕开或弱化为普通建议 | 00、01、02、04、Human Gate、后续规范创建/审核行动模板或一致性核对；具体执行闭环不在 00 定义 | 价值治理 | 新增、修改、合并、拆分、重命名或迁移规范，或后续机制试图重新解释本文最高锚点时 |

## 8. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 改变第 1 节“LDVH 为什么存在”的表述、定位或方法；
2. 改变第 2 节“以 AI 执行者为第一服务对象”的依赖、能力、本质或支撑方向；
3. 新增、删除、改名或重排五类构成要素；
4. 将事实源改为构成要素，或将派生机制、附件、工具输出、Web 页面状态、运行时索引升级为事实源；
5. 改变 V1-V9 的编号、含义、准入作用或反向判断；
6. 将运行闭环、事实对象生命周期、具体流程步骤或具体环境适配细则写入 00，导致 00 替代后续构成要素实践；
7. 将保障与衔接层改为构成要素，或绕过 01 直接在下位规范各自发明互相竞争的保障衔接基础规则；
8. 用对象数量、页面数量、工具数量、附件数量或资产数量替代 V1-V9 价值判断。

以下情况必须评估 Human Gate；确认影响 00 最高锚点、事实源边界、保障与衔接层、五类构成要素或 V1-V9 时，必须暂停确认：

1. 调整本文待补齐事项的归口、范围或关闭条件；
2. 新增可能影响后续构成要素实践纳入边界的价值判断、风险边界或检查标准；
3. 后续规范、附件、Code、Web 或保障与衔接承载物试图把本文原则解释为自身执行豁免；
4. 规范核对发现本文与 01、02、04 或后续单篇规范存在上位冲突。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 结论、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。

## 9. 待补齐事项

1. 保障与衔接层的具体承载物、资产登记和环境适配规则，应由后续对应规范承接；
2. V1-V9 的后续消费、检查、映射和展示方式，应在 01、Code、Web 和保障与衔接相关规范单篇确认后继续补齐，并回指本文价值锚点。
