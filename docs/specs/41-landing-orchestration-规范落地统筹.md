## 1. 行动定位与适用场景

规范落地统筹是 LDVH 的基础落地工作流程，用于把正式规范中的规范落地要求转化为可执行、可检查、可降级和可回写的行动判断。

本文不重新定义规范落地要求、环境适配映射、运行投影、环境能力、Code、Web、事实源或运行闭环测试规则。本文只定义 AI 面对一批落地要求时，如何统筹读取、提取、分流、验证、发现缺口和回写。

出现以下情况之一时，应考虑进入规范落地统筹：

1. 新增、修改、重命名或删除 `docs/specs/` 正式规范；
2. 某个正式规范的规范落地要求、保障机制、同步类型或触发条件发生变化；
3. 04 系列的规范落地、环境适配、运行投影或环境能力承接规则发生变化；
4. 具体工作模型、工作流程、Code、Web、运行投影、Skill、Agent、Hook、CI 或 Rules / Instructions 的承接边界发生变化；
5. LDVH落地与检查或集合一致性检查需要确认当前规范是否已经能被执行；
6. 用户明确询问“哪些要求还没落地”“规范改了要同步什么”“现在是否闭环”等问题；
7. AI 在执行规范、工作对象或工作流程时发现缺少工具、测试、运行投影、Human Gate 或事实源回写位置。

41 触发保障采用分层抽象机制，不依赖单一 AI 记忆、单一入口或固定实体清单。各层职责如下：

| 层级 | 抽象机制 | 保障职责 | 缺口处理 |
|---|---|---|---|
| 入口路由层 | AI 统一入口、平台薄入口或人工降级提示 | 让 AI 在正式规范变更、落地要求变化、运行投影漂移、Code/Web/Skill/Agent/Hook/CI 边界变化或 LDVH落地与检查时看见 41 | 入口不可见或过期时，记录运行投影漂移或入口可见缺口 |
| 规范 Scenario 层 | 本文 Scenario、04 系列落地要求、具体规范触发条件 | 从正式规范和落地要求中判断是否应进入 41，而不是从环境实体名称反推 | Scenario 不完整时，回写正式规范缺口或 Task |
| 集合索引层 | 40 active 工作流程索引 | 确认 41 是 active 工作流程，并为 42、入口和 Code 查询提供定位 | 索引缺失或状态不一致时，记录集合一致性缺口 |
| Code 检查层 | 规范索引、落地要求聚合、结构校验、漂移检查或人工降级检查 | 提供可复现的定位、聚合和缺口诊断；能力不足时显式输出 open / degraded | 工具不能判断触发、消费、证据或漂移时，形成 Code / 41 联动缺口 |
| 42 消费层 | LDVH落地与检查读取 41 聚合结果和缺口状态 | 检查 41 输出是否覆盖当前范围，且未把 active 状态误判为闭环 | 无法消费 41 输出时，42 报告 41/42 联动缺口 |
| 运行投影层 | Rules / Instructions、Skill、Agent、Hook、CI、Web、Code 或命令入口 | 只承接被正式规范声明的抽象能力，不维护固定实体名单 | 投影缺失、复制正文或路径漂移时，进入 04.02、平台清单、Task 或 41 |
| Human Gate 层 | Human Gate、影响说明、降级接受和回写证据 | 在高影响写入、长期降级、关键缺口关闭或通过声明前提供人工确认 | 证据不足时保持 needs_human_gate、open 或 degraded |

上述层级只描述能力类型和职责边界，不登记具体 Skill 名称、平台入口路径、Hook 名称、CI job、Web 页面或 Code 命令清单。新增、重命名或删除某个实体时，41 只判断相关正式规范是否声明了该类抽象能力、现有承接是否可定位和可验证、缺口应分流到哪里；不得为了维护实体名单而修改本文。

以下情况通常不应进入完整规范落地统筹：

1. 简单问答或不影响正式规范、运行投影和事实源的低风险解释；
2. 只需按已有工具运行确定性校验，且不需要判断承接缺口；
3. 用户明确只要求阅读或总结某个非正式输入材料，且不要求吸收为正式规则；
4. 当前事项已经由更具体工作流程处理，且不涉及新的规范落地要求。

## 2. 准入条件

进入规范落地统筹前，应满足以下条件：

1. 存在明确的统筹范围，例如某个规范文件、编号区段、变更集合、运行投影、Code/Web/Skill/Agent/Hook/CI 承接事项或审计目标；
2. 能定位至少一个正式规范、工作流程、工作模型、运行投影或缺口来源；
3. 需要判断规范落地要求是否已经具备保障机制、环境适配、运行投影、验证方式或回写出口；
4. AI 能区分正式规范、research/refs 输入、运行投影、Code 输出、Web 状态和聊天过程信息；
5. 统筹结果可能影响后续规范修改、工作流程创建、Code 需求、Web 同步、Task、Memo、ADR、Pitfall、Change 或 Human Gate。

不满足准入条件时，应退回主上下文直接回答、先补充事实源、运行已有校验，或进入更具体的工作流程。

## 4. Context 要求

执行规范落地统筹前，AI 应获得以下最小 Context：

1. 本次统筹范围和触发原因；
2. `docs/specs/06-工作流程基础规范.md`；
3. `docs/specs/40-工作流程集合索引.md`；
4. `docs/specs/04.01-规范落地声明规范.md`；
5. `docs/specs/04.02-环境适配与运行投影规范.md`；
6. `docs/specs/04.03-环境能力承接边界规范.md`；
7. 涉及平台差异、LDVH落地与检查、运行投影状态或环境支持判断时，读取 `docs/specs/04.06-平台适配清单规范.md`；当前平台为 Trae Solo 时，同时读取 `docs/specs/04.07-Trae-Solo适配清单.md`；当前平台为 Codex CLI 时，同时读取 `docs/specs/04.08-Codex适配清单.md`；
8. 本次涉及的正式规范原文；
9. 需要判断回写时，读取 `docs/specs/09-事实源边界与承载规范.md` 和对应工作模型或文档规范；
10. 需要判断 Code、Web 或测试时，读取 `docs/specs/07-Code实现规范.md`、`docs/specs/08-Web信息同步规范.md` 或 `docs/specs/10-运行闭环测试规范.md`。

根据主题复杂度，可增加以下 Context：

1. 当前运行投影、平台适配清单、42 落地与检查报告、管辖项目配置或平台 refs；
2. 与本次缺口相关的 `docs/research/` 输入材料；
3. 相关工作模型实例、Task、ADR、Memo、Pitfall 或 Change；
4. 已存在的 Code 命令、测试、Web 实现、Rules / Instructions 摘要、Skill、Agent、Hook 或 CI 配置；
5. 需要独立、并行或专项判断时，读取 `docs/specs/44-multi-role-thinking-多角色思考.md`。

可选 Context 只能作为输入材料或运行投影证据，不得覆盖正式规范，也不得把环境实体误当成权威事实源。

## 5. Scenario 识别

当用户输入、文件变化或事实源状态满足以下条件之一时，AI 应识别为规范落地统筹 Scenario：

1. 用户要求创建、修改、审计、吸收或迁移正式规范；
2. 用户提出会影响 LDVH 长期执行方式、规范落地链路、Code / Web / Skill / Agent / Hook / CI / Rules / Instructions 承接边界或验收口径的稳定思想、需求或治理原则；
3. 用户要求判断某个规范是否能落地、是否闭环、是否还有缺口；
4. 正式规范中的“规范落地要求”章节新增、修改、删除或字段变化；
5. 新增或修改 Code、Web、Skill、Agent、Hook、CI、Rules / Instructions 等运行投影；
6. 运行投影、环境适配映射或工具校验结果与正式规范不一致；
7. LDVH落地与检查需要确认 active 工作模型、工作流程、Code、Web 和运行投影是否具备最低可用承接；
8. AI 判断某项规范执行需要工具、测试、Human Gate、事实源回写或运行投影，但当前项目尚未明确承接位置。

多个 Scenario 同时匹配时，应优先处理会影响事实源写入、运行投影、Human Gate、Code/Web 实现或编号状态的事项。若判断边界不清，应先调用多角色思考或请求 Human 确认。

## 6. 执行流程

### 6.1 确定统筹范围

AI 应先明确本次统筹的范围：

1. 单个正式规范；
2. 一个编号区段；
3. 一组文件变更；
4. 某类落地要求；
5. 某个运行投影或环境适配映射；
6. LDVH落地与检查输入；
7. 用户指定的缺口问题。

范围不明确时，应先询问用户或降级为局部分析，不得假装已完成全局统筹。

当统筹范围来自 Human 提出的稳定思想、需求或治理原则，且该内容会改变 LDVH 长期行动方式、验收口径或运行投影承接时，AI 应先判断其应写入哪个正式规范。需要成为稳定规则的内容必须先进入 `docs/specs/` 或对应权威事实源，再由本流程提取落地要求、分流承接机制、判断验证方式和回写出口。规范修订完成前，不得先用 Code、Rules / Instructions、Skill、Agent、Web、Hook、CI 或其他运行投影反向制造规则事实。

### 6.2 提取规范落地要求

AI 应从范围内正式规范提取“规范落地要求”表，至少记录：

1. 来源文件；
2. 落地要求类型；
3. 要求内容；
4. 保障机制；
5. 同步类型；
6. 触发条件；
7. 是否涉及环境适配映射；
8. 是否涉及运行投影；
9. 是否涉及 Code、Web、Skill、Agent、Hook、CI、Rules / Instructions 或 Human Gate。

规范落地统筹不维护具体 Skill、具体平台入口、具体 Agent、具体 Hook、具体 CI、具体 Web 页面或具体 Code 命令的固定枚举清单。统筹的职责是从正式规范中动态提取抽象落地要求，判断这些要求需要哪类承接机制，并检查是否已有可定位实体、可执行方式、验证证据、降级方式和回写出口。具体实体名称、路径、模板、安装位置和 open_items 应留在对应规范、平台适配清单、Task、Code、Web 或实际运行投影中维护。

当本流程作为 42 LDVH落地与检查的输入时，AI 应覆盖本次 42 范围内需要读取的所有正式规范、平台适配清单、工作模型集合、工作流程集合和实际运行投影；若当前 Code 只能抽取部分规范落地要求，或不能判断承接机制是否实例化，应把“41 聚合/判断能力不足”作为 open / degraded 缺口输出，而不得把 active 状态误判为闭环完成。

若正式规范缺少规范落地要求章节，应按 `03.01`、`04.01` 和对应文档规范判断是否属于例外；非例外缺失应记录为规范缺口。

### 6.3 按落地要求类型分流

AI 应按 `04.01` 的落地要求类型分流处理：

| 落地要求类型 | 统筹判断 |
|---|---|
| 上位约束承接要求 | 哪些下游规范、索引、工作模型、工作流程、Code、Web 或运行投影应承接它 |
| 入口可见要求 | 是否需要 Rules / Instructions、目录入口、运行入口摘要、Web 入口或人工降级提醒 |
| 流程复用要求 | 是否应进入工作流程、Skill、命令流程、操作清单或仅保留主上下文执行 |
| 子 Agent 思考要求 | 是否需要独立、专项、并行视角，并按 44 调用多角色思考或 Agent |
| 确定性执行要求 | 是否形成 Code 需求、工具扩展、测试、CI 或校验器缺口 |
| Human 交互要求 | 是否需要 Human Gate、Web / Human 入口、对话确认、审批或验收证据 |
| 生命周期触发要求 | 是否需要 Hook、CI、自动运行、提交前后检查、会话停止检查或人工降级检查 |

分流判断只处理抽象机制类型，不在本文维护具体实体清单。新增一个 Skill、入口、Hook、CI、Web 页面或 Code 命令，不应自动导致修改本文；只有抽象机制边界、分流规则、验证要求或回写边界变化时，才需要修改本文。

### 6.4 判断保障机制是否实例化

每条落地要求都应回答：

1. 由什么机制执行；
2. 何时执行；
3. 输入是什么；
4. 输出是什么；
5. 失败或能力缺口时如何降级；
6. 验证方式是什么；
7. 稳定事实写回哪里；
8. 是否触发 Human Gate。

只写“Code 检查”“运行入口摘要”“Human Gate”但没有可定位实体、执行方式、降级方式或后续 Task 的，应记录为未完全实例化。

若落地要求本身声明需要 Code 承接，而现有 Code 缺失、只能生成启发式报告、不能消费 Human Gate 证据、不能检查运行投影漂移或不能把结果回指事实源，应记录为 Code / 41 联动缺口，并建议进入 Task 或 Code 需求；不得通过人工罗列具体清单来替代缺失工具。

### 6.5 判断环境适配和运行投影

涉及环境能力时，AI 应按 `04.02`、`04.03` 和必要的平台适配清单判断：

1. 是否需要环境适配映射；
2. 当前环境是否具备对应能力；
3. 是否已有运行投影；
4. 运行投影是否只做入口、提醒、调用或降级，不复制权威规范正文；
5. 运行投影是否与正式规范一致；
6. 当前平台适配清单是否已按 `04.06` 声明承接方法、证据、降级和 open_items；当前平台为 Trae Solo 时，是否与 `04.07` 的响应矩阵一致；
7. 缺口应进入 Task、Memo、ADR、Code 需求、Web 需求、平台适配清单 open_items 或人工降级说明；若本次处于 42 LDVH落地与检查，只能在当前过程报告中说明缺口分流结果，不得把 42 报告作为状态事实源。

运行投影不是最终事实源。运行投影输出中的稳定事实必须按 `09` 回写后才生效。

运行投影检查应回答“某类规范落地要求是否已有抽象承接”，而不是回答“本文固定清单中的某个实体是否存在”。如果平台适配清单、04.04 或其他正式规范要求某类入口、Skill 或工具存在，41 应据该规范提取需求并判断现状；若规范未声明该实体，41 不得为了补清单而凭经验新增要求。

### 6.6 判断验证与测试

AI 应按 `10` 判断每项要求是否有验证方式：

1. 结构和字段可由文档校验或 Code 校验；
2. 行为和触发可由运行闭环测试、正反样例、人工降级检查或审计验证；
3. 回写和证据可由事实源检查、工作对象校验或 Change 记录验证；
4. 运行投影漂移可由 Code、CI、Hook 或人工降级检查发现；
5. 测试用例事实源尚未稳定时，应记录缺口，不得把聊天结论或临时脚本作为长期测试依据。

验证不足、证据不可复现、只凭 AI 自述、工具输出无法回指事实源、或跳过应执行检查时，对应落地要求不得标记为 `closed`。AI 应按 06 §6.10.1 和 10 §8.4 判断是否记录为 `open`、`degraded`、`needs_human_gate`，或分流到 Task、Memo、ADR、Pitfall、Code 需求、测试用例缺口或运行投影缺口。

### 6.7 输出统筹结果

规范落地统筹应输出结构化结果，建议包含：

```yaml
landing_orchestration_result:
  scope:
    reason: 本次触发原因
    files:
      - docs/specs/example.md
  requirements:
    - source: docs/specs/example.md
      type: 确定性执行要求
      content: 要求内容
      guarantee: 保障机制
      environment_mapping: exists | missing | not_required | degraded
      runtime_projection: exists | missing | not_required | degraded
      verification: exists | missing | degraded
      evidence:
        sources:
          - docs/specs/example.md
        summary: 证据摘要
      residual_risk: none | 风险说明
      failure_handling: none | open | degraded | needs_human_gate | follow_up
      writeback: specs | Task | Memo | ADR | Pitfall | Change | platform_checklist | none
      status: closed | open | degraded | needs_human_gate
      notes: 说明
  gaps:
    - gap: 缺口描述
      owner_area: specs | code | web | workflow | work_model | runtime_projection | human_gate | test
      suggested_writeback: 建议回写位置
      source_requirement: 来源规范和落地要求
      missing_capability: 缺失的抽象能力，不填写固定实体清单
  human_gate:
    required: true
    reason: 触发原因
```

当结果供 42 消费时，应额外说明：本次是否覆盖了 42 声明的检查范围；是否存在 41 自身无法完成的聚合、实例化判断、验证证据消费或运行投影漂移检查缺口；这些缺口不得被 42 解释为已通过。

`landing-plan` 合同由本文（41）定义，为唯一权威结构。`landing-plan` 是 41 的只读过程输出合同，用于把 `landing-report`、运行投影检查、Human Gate 检查、事实源检查、LDVH落地与检查和验证状态聚合成 AI / Human 可消费的计划视图。`landing-plan` 不是稳定事实源，不得直接写入规范状态、工作对象状态、平台适配清单、Code/Web 状态或 Human Gate 结论；其中形成的任务、决策、缺口、降级接受、验证结论或回写目标，必须按 `09`、相关工作模型和本文 §10 分流回写后才成为稳定事实。

`landing-plan` 至少应满足以下合同：

1. `metadata.report` 固定为 `landing-plan`，`metadata.read_only` 为 `true`，`metadata.source_of_truth` 为 `false`，并说明状态来源是派生启发式或等价降级口径；
2. `scope` 说明项目根、工作区根、读取的规范来源数量和规范落地要求数量；
3. `facts_read` 列出本次聚合读取的报告、事实源、运行投影、Human Gate、LDVH落地与检查或其他输入来源；
4. `capabilities` 说明当前 Code、运行投影、Human Gate、事实源、验证或回写消费能力的状态、证据和缺口；
5. `requirements` 汇总规范落地要求总量、状态分布、未关闭缺口数量和 owner_area 分布；
6. `gaps` 按 owner_area、子类、状态、建议回写位置和缺失能力组织缺口，不维护固定实体清单；
7. `proposed_actions` 给出候选行动、owner_area、优先级、缺口数量、建议回写位置和必要的运行投影 remediation 分类；其中的运行投影类行动对应 `docs/specs/04.02-环境适配与运行投影规范.md` §3.3 定义的"候选运行投影"，仅属过程输出，不代表已落地；
8. `test_design` 必须在授权和执行前说明测试先行要求，包括成功条件、失败条件、正例、反例和边界样例；无法先写自动化测试时，应说明等价验证方式和残留风险；
9. `writes_required` 和 `write_targets` 分别说明是否需要事实源写入以及候选写入目标；写入目标只能作为授权前候选，不得自动执行；
10. `human_gate` 说明 Human Gate 子类、触发原因和待确认事项；涉及写入、长期降级、关键缺口关闭或通过声明时，必须在执行前确认；
11. `validation_plan` 和 `verify_commands` 分别说明验证状态、验证命令和复检方式；验证失败、不可复现或缺少命令时，不得进入 `closed`；
12. `review_targets` 说明后续审核承接位置，至少应能表达 `review_needed`、Web / Human-facing 审核面或 Human Gate 记录；
13. `writeback_targets` 说明稳定结论应回写到哪些权威事实源，不能回写时必须保持 open、degraded 或 needs_human_gate。

当 Code 提供 `tools/specs_validate.py landing-plan` 或等价实现时，其输出必须符合上述合同。42 消费 landing-plan 时应以本文合同为准校验输入结构，格式不符时降级为人工检查并报告 41/42 联动缺口。

## 7. Gate 触发条件

以下情况触发条件 Gate：

1. 统筹范围不明确；
2. 需要读取的正式规范、索引、平台适配清单或运行投影不存在；
3. 落地要求类型、保障机制或回写出口无法判断；
4. 当前环境能力不足且没有可靠降级方式；
5. 运行投影可能过期，但缺少漂移检查；
6. 需要修改 Code、Web、Skill、Agent、Hook、CI 或 Rules / Instructions，但缺少对应规范依据或验证方式。

以下情况必须暂停并请求 Human 确认：

1. 新增、删除、重命名或重排正式规范编号；
2. 改变某项规范落地要求的类型、保障机制或触发条件；
3. 将候选缺口升级为正式规范、工作流程、工作模型或长期运行投影；
4. 创建、启用、删除或改变 Skill、Agent、Hook、CI、Web 受控写入或高影响 Code 工具；
5. 接受能力缺口的长期降级方式；
6. 关闭仍有 open 或 degraded 状态的关键落地要求；
7. 跳过验证、只凭 AI 自述关闭要求、或把不可复现证据视为通过；
8. Human 明确提出的稳定需求、治理思想或验收口径已被实现，且 AI 准备声明完成、闭环或关闭相关关键缺口；
9. LDVH落地与检查要把当前状态判定为已闭环。

Human Gate 触发后，应按 `docs/specs/06-工作流程基础规范.md` §6.3.1 记录轻量人类决策。规范落地统筹语境下，最小记录应包含时间、Human 决策、影响范围以及决策成立所依赖的依据、限制、验证、后续分流或回写约束。Human Gate 不强制关联 Task；只有决策需要形成后续执行对象、缺口分流或关闭证据时，才按对应工作模型关联 Task、ADR、Change、Memo 或其他事实对象。

## 8. Skill 和 Agent 调度

规范落地统筹不默认创建专用 Skill。理由如下：

1. 本流程需要读取正式规范并进行主控判断；
2. 它经常涉及 Human Gate、回写分流和跨机制协调；
3. Skill 可以辅助固定检查步骤，但不得替代主控判断；
4. 若未来形成稳定、低风险、输入输出明确的子步骤，可按 `04.03` 判断是否创建 Skill 或命令流程。

规范落地统筹可调用 Agent 或多角色思考，但只在以下情况使用：

1. 规范边界、机制选择或编号调整存在高影响分歧；
2. 需要独立、专项或并行视角审查；
3. 涉及 Rules / Instructions、Skill、Agent、Code、Web、Hook、CI 或 Human Gate 的职责冲突；
4. 需要确认某项缺口应进入规范、工作流程、Code、Web、Task、Memo、ADR、Pitfall 或最佳实践。

Agent 输出必须回到主控汇总。稳定结论只有写回事实源后才生效。

## 9. 工具协作适配

规范落地统筹可使用 Code、命令、校验器、搜索工具或测试辅助以下工作：

1. 搜索和读取正式规范；
2. 提取规范落地要求表；
3. 检查章节、字段、引用、编号和路径；
4. 聚合 Code、Web、运行投影或事实源缺口；
5. 生成缺口清单、验证报告或受控写入候选；
6. 执行运行闭环测试或正反样例。

工具不得替代 AI 判断，不得直接决定 Human Gate，不得把工具输出作为最终事实源。工具报告中的 closed/open/degraded 状态只有能回指正式规范、事实源、测试或工作对象证据时，才可作为统筹证据使用。

若 AI 发现现有工具不足，应按 `07` 形成最小 Code 需求、实现或扩展工具并验证；工具规范缺失时，应先补齐必要规范或测试要求。`tools/specs_validate.py landing-report` 已形成规范落地要求全局聚合报告的基础 Code 实现，`tools/specs_validate.py human-gate` 已形成 Human Gate 轻量人类决策记录结构的基础检查；这些工具输出属于派生检查结果，AI 仍必须按本文流程验证、回写缺口，不得把工具输出当作唯一事实源或最终关闭证据。

## 10. 事实源回写与证据留存

规范落地统筹完成后，应按以下规则判断回写：

| 输出类型 | 回写位置 |
|---|---|
| 正式规范缺口或冲突 | 对应 `docs/specs/` 正式规范，或先形成 Task / Memo / ADR |
| 需要执行的修复动作 | Task |
| 有保留价值但暂不执行的信息 | Memo |
| 长期决策、取舍或降级接受 | ADR |
| 可复用教训或反复踩坑 | Pitfall |
| 实际文件修改 | Change / Git commit |
| Code 工具或校验缺口 | Task，并按 `07` 形成 Code 需求 |
| Web 同步或 Human 入口缺口 | Task / Web 文档 / 对应规范 |
| 运行投影或环境适配缺口 | 平台适配清单 open_items、Task 或 Memo；42 当前落地与检查报告只说明分流结果 |
| 测试用例缺口 | 10 定义的测试用例事实源待稳定；稳定前记录为 Task 或待补齐事项 |

证据至少包括：

1. 本次统筹范围和触发原因；
2. 读取的关键事实源；
3. 提取的落地要求清单；
4. 分流判断和依据；
5. 保障机制、环境适配、运行投影和验证状态；
6. 缺口清单、降级方式和残留风险；
7. Human Gate 判断；如已触发，应包含或引用符合 06 §6.3.1 的轻量人类决策记录；
8. open、degraded 或 needs_human_gate 状态的原因和后续分流；
9. Human 明确提出的稳定需求、治理思想或验收口径在关闭前的验收结论、授权代表、降级说明或残留风险；
10. 若发生写入，记录写入文件、验证结果和 Change / commit 关联。

统筹结果不得用“看起来已闭环”“应该已经承接”“工具会检查”等推测性表述替代证据。需要关闭关键缺口时，应能说明关闭依据、验证方式、回写位置、残留风险和 Human Gate 状态；不能说明时，应保持 open、degraded 或 needs_human_gate。

## 11. 机制适配边界

规范落地统筹的机制适配边界如下：

| 能力 | 当前结论 | 边界 |
|---|---|---|
| Rules / Instructions | 需要薄入口 | 只提醒规范变更、闭环检查或落地缺口场景应定位本文，不复制完整流程 |
| Skill | 默认不创建 | 可承接稳定子步骤，但不得替代主控判断、Human Gate 或跨机制分流 |
| Agent | 可作为增强模式 | 用于独立、专项、并行审查，输出回到主控 |
| Code / 工具 | 需要逐步补齐 | 优先承接确定性提取、校验、聚合、漂移检查和测试；不得判断规范价值 |
| Web | 不默认创建专用页面 | 可在产品化后展示缺口、Gate 和落地与检查报告，但不得成为第二事实源 |
| Hook / CI | 后续评估 | 适合承接生命周期触发和漂移检查；触发时机必须先由规范或工作流程定义 |

本文不创建固定机制子文档。机制实体、实现入口和运行投影应按 04、07、08、10 和当前平台适配清单处理。

## 12. 行动特有可测试性锚点

规范落地统筹至少应能派生以下测试锚点：

| 类型 | 可测试性锚点 |
|---|---|
| 正向场景 | 新增或修改正式规范、规范落地要求或运行投影时，AI 应进入规范落地统筹或说明为何降级 |
| 负向场景 | 简单问答、低风险解释或不影响正式规范和运行投影的事项，不应强行进入完整统筹 |
| Gate 场景 | 编号重排、保障机制变化、长期降级、运行投影创建、Code/Web/Skill/Agent/Hook/CI 高影响变更应暂停确认 |
| 回写场景 | 缺口应按性质分流到 specs、Task、Memo、ADR、Pitfall、Change、Code、Web、平台清单 open_items 或待补齐事项；42 当前落地与检查报告只能说明分流结果 |
| 失败降级 | 缺少事实源、工具失败、环境能力不足或测试事实源未稳定时，应记录 degraded 或 open 状态 |
| 反合理化 | 统筹结论只凭 AI 自述、不可复现证据或未实现工具能力时，应保持 open/degraded 或触发 Human Gate |
| 回归风险 | 修改本文后，应检查 40 索引、04 系列、07、08、09、10、运行投影和相关工作流程是否需要同步 |

具体测试用例、预期行为矩阵、失败诊断和回归用例不写入本文，应按 `docs/specs/10-运行闭环测试规范.md` 进入测试用例事实源或 Code 测试实现。

## 13. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |

## 14. 检查要求

检查一次规范落地统筹执行是否符合本流程时，应确认：

| 检查项 | 标准 |
|---|---|
| 触发原因 | 明确说明进入或不进入本流程的原因 |
| 统筹范围 | 范围清晰，未把局部分析冒充全局统筹 |
| 事实源读取 | 已读取 04.01、04.02、04.03、06、40 和受影响正式规范 |
| 要求提取 | 已提取规范落地要求类型、要求内容、保障机制、同步类型和触发条件 |
| 分流判断 | 每条要求已判断 Code、Web、Skill、Agent、Hook、CI、Rules / Instructions、Human Gate 或人工降级关系 |
| 抽象机制边界 | 未把具体 Skill、入口、Hook、CI、Web 页面或 Code 命令清单写入本文作为固定要求 |
| 环境适配 | 需要环境能力时，已判断环境适配映射和运行投影状态 |
| 验证方式 | 已判断验证、测试、Code 校验、人工降级或缺口状态 |
| 证据质量 | closed 状态有可追溯证据，open/degraded/needs_human_gate 有原因、风险和后续分流 |
| 回写建议 | 缺口按 09 和相关工作模型/文档规范分流 |
| Human Gate | 高影响写入、降级、编号、运行投影和闭环判断已暂停确认，并按 06 §6.3.1 留下轻量人类决策记录或降级说明 |
| 事实源边界 | 未把聊天、research/refs、工具输出、Web 状态或运行投影当成最终事实源 |
| 机制边界 | 未用 Skill、Agent、Hook、Code 或 Web 替代主控判断 |

检查本文是否作为具体工作流程规范完成时，应确认：

1. 覆盖 03.05 要求的标准章节；
2. 与 06 的通用规则不冲突；
3. 在 40 中登记为 active；
4. 未重新定义 04.01、04.02、04.03、07、08、09 或 10 的权威规则；
5. 当前权威路径为 `docs/specs/41-landing-orchestration-规范落地统筹.md`；
6. 行动特有可测试性锚点已写入本文；
7. 多角色思考仅作为辅助工作流程或 Agent 承接方式，不替代本文的统筹判断。
