## 1. 本文解决的问题

本文解决 LD Vibe Harness 中 Code 构成要素如何承载确定性工具、测试、实现文档、更新维护和事实源受控写入的问题。

Code 的目标不是替代 specs、Rules、Skill、Agent、Web 或事实实例，而是用可执行、可测试、可复现的实现降低 AI 和人读取、解析、校验、聚合、上下文准备和受控写入 Git 文件事实源的成本。

本文从原 06 二合一工具规范中拆出 Code 与 Tools 辅助层相关内容。Web 信息同步层由 `specs/15-Web信息同步规范.md` 独立承载。

## 2. 与 00 总纲的关系

00 定义 Code 是 LD Vibe Harness 的五类构成要素之一。Code 负责承载可执行实现、确定性工具、测试、自动化检查和实现级维护纪律。

本文承接 00 对 Code 的定位，定义 Code 与 Git 文件事实源、Specs、Tools、Web、测试和文档的边界。稳定规则仍由 specs 定义，稳定事实仍由 Git 文件事实源承载，Code 实现不得反向替代规范正文或事实实例。

## 3. Code 权威领域

本文是 LDVH Code 构成要素、`tools/` 确定性实现、PyTools 辅助层、工具生命周期、工具测试、代码文档边界、工具与事实源关系、工具与 AI 协作关系以及工具 Human Gate 检查要求的权威规范。

本文不定义 Web 页面、Web 信息同步、人类确认工作台、Web API 产品设计或 UI 交互细节；这些内容由 `specs/15-Web信息同步规范.md`、`web/` 实现目录或 Web 相关设计文档承载。

## 4. Code 与事实源边界

Code 可以读取、解析、校验、聚合、信息同步准备和受控写入 Git 文件事实源。Code 的价值是降低人和 AI 操作事实源的成本，而不是替代事实源。

Code 治理原则如下：

1. **Code 不等于事实源**：工具实现、工具输出、测试缓存、运行时索引和诊断结果都不能成为最终事实源。
2. **输入来自事实源**：工具读取、解析、校验和聚合的稳定事实必须来自 Git 文件事实源。
3. **稳定事实必须回写**：工具运行中产生的稳定结论、证据、决策或变更，必须写入对应 Git 文件事实源后才成为 LDVH 稳定事实。
4. **写入必须受控**：工具可以提供受控写入入口，但不得绕过事实源边界、对象规范、工作流程或 Human Gate。
5. **实现不替代规范**：`tools/`、`tests/` 和代码文档不能替代 specs/、ldvh-base/ 或 docs/ 中的权威事实。

## 5. PyTools 辅助层规则

PyTools 辅助层面向机器可执行、可重复、可校验的确定性工作，包括解析、校验、聚合、上下文包生成、派生数据生成和受控写入。

### 5.1 允许职责

1. 读取和解析 specs 文档、ldvh-base 事实实例、docs 资料和其他 Git 文件事实源；
2. 校验文件格式、字段完整性、状态连通性、章节编号和引用完整性；
3. 生成上下文包、派生数据、聚合报告和诊断结果；
4. 执行已授权的受控写入；
5. 支持命令行调用，暴露确定性输入输出接口。

### 5.2 禁止职责

1. 将派生数据、索引、诊断或缓存持久化为独立事实源；
2. 将 Tools 输出作为 specs 规范、Rules、审计或决策的唯一来源；
3. 自动修改 specs 原文、Rules 或事实实例；
4. 绕过 Human Gate 自动写入；
5. 直接调用 AI、Skill 或 Agent；
6. 用 LLM 摘要、向量化结果或语义推断替代确定性结果。

### 5.3 命名与 CLI 规则

PyTools 文件统一放置于 `tools/`，命名格式为 `<domain>_<capability>.py`。

CLI 至少支持 `--help`。输入路径参数应区分文件、目录和项目根目录。写入类命令必须显式表达目标对象、目标状态或目标路径。

### 5.4 输出规则

输出应能被 AI、Rules、Skill、Web 或其他工具稳定消费。结构化输出应包含 `ok`、`command`、`target`、`summary`、`issues` 等语义字段。

exit code 约定如下：

| exit code | 含义 |
|---|---|
| 0 | 成功且无 error |
| 1 | 存在 error |
| 2 | 参数错误 |
| 3 | 环境不可用 |

## 6. 工具制作要求

新增 PyTools 前，必须明确以下内容：

| 项目 | 要求 |
|---|---|
| 工具名称 | 使用 `<domain>_<capability>.py` 命名 |
| 所属层级 | 明确属于 Code / PyTools，不得混入 Web 信息同步职责 |
| 消费事实源 | 声明读取的 specs、ldvh-base、docs 或其他 Git 文件事实源 |
| 消费规范 | 声明依赖的 specs 章节、字段契约或状态机 |
| 输入 | 明确文件、目录、项目根目录、参数和默认值 |
| 输出 | 明确文本输出、结构化输出、exit code 和错误信息 |
| 写入行为 | 明确是否写入、写入目标、写入前校验和写入后验证 |
| Human Gate | 写入类或高影响命令必须声明 Human Gate 来源，不得生成授权本身 |
| 降级方式 | 工具不可用时说明人工检查或停止执行条件 |
| 测试入口 | 新增对应 `tests/tools/test_<name>.py` |
| Code 文档 | 复杂工具应提供使用、维护或故障排查说明 |

工具功能清单、参数设计和实现细节进入 `tools/` 实现、测试或代码文档；稳定规则进入 specs；事实实例进入 ldvh-base。

## 7. 工具使用场景

工具使用场景必须由对应规范、Rules、Skill 或工作流程声明。未声明场景时，AI 应根据本文判断工具是否适合执行确定性解析、校验、聚合或受控写入。

当前通用场景如下：

| 场景 | 工具层级 | 使用要求 |
|---|---|---|
| 修改 specs 章节编号 | PyTools | 应运行文档结构检查 |
| 修改 specs 文件名、章节引用、上位依据或相关规范 | PyTools | 应运行引用完整性检查 |
| 创建或修改事实实例 YAML | PyTools | 应运行事实实例校验 |
| 创建事实对象 | PyTools | 优先使用受控创建命令，不得手工绕过编号和骨架规则 |
| 状态流转 | PyTools | 必须校验合法状态和合法流转 |
| 准备提交 | PyTools | 应校验提交信息格式和变更范围 |
| Web 派生视图需要数据 | PyTools / Web | PyTools 提供确定性派生数据，Web 负责展示和确认体验 |

工具不可用时，不得直接视为检查通过。AI 应人工检查并说明降级原因；写入类工具不可用且无法保证受控写入时，应暂停。

---

## 8. 工具测试要求

新增 PyTools 必须新增对应 `tests/tools/test_<name>.py`。修改输入、输出、错误码、写入行为、字段消费、状态机消费或校验规则时，必须同步更新测试。

测试至少覆盖：

1. `--help` 或基础 CLI 可用性；
2. 参数错误和路径不存在；
3. 成功路径；
4. 失败路径；
5. 输出结构和 exit code；
6. 写入类命令的写入前阻断；
7. 写入类命令的写入后验证；
8. 状态流转类命令的合法和非法流转；
9. 引用或契约消费类命令的正例、反例和边界样例。

测试夹具必须最小化，不得演化为第二事实源。测试缓存和测试结果不得替代 Git 文件事实源。测试不通过时不得提交相关 Code 变更。

## 9. 工具更新、维护与删除

### 9.1 更新触发条件

以下规格变更会影响 tools/ 下代码实现，AI 必须同步检查工具代码和测试：

1. 对象类型新增、删除或重命名；
2. 字段契约新增、删除、重命名或格式变更；
3. 状态机新增、删除或流转变更；
4. 事实源目录结构变更；
5. 术语统一、文件命名或目录命名变更；
6. 章节编号、引用规则或文档骨架变更；
7. Human Gate、受控写入或验证要求变更。

### 9.2 联动检查内容

规格变更后，AI 应检查：

1. `tools/` 中是否存在受影响的硬编码引用；
2. 元数据映射、校验规则、写入逻辑是否需要同步；
3. 测试用例是否需要同步；
4. Web 是否消费该工具输出；
5. Rules、Skill 或 Agent 是否调用该工具；
6. 工具文档是否需要同步。

如果 tools/ 代码不满足新规范要求，必须在同一变更中完成同步，或明确记录阻塞原因，不得声称规范已完整落地。

### 9.3 删除工具

删除工具前必须确认：

1. 没有 Rules、Skill、Agent、Web 或其他工具继续调用；
2. 没有 specs、docs 或测试继续引用；
3. 替代工具或人工降级路径已明确；
4. 对应测试已删除、迁移或改写；
5. 如影响工作流程、受控写入或 Human Gate，应触发 Human Gate。

## 10. Code 文档边界

Code 可以拥有自己的文档，但 Code 文档不替代 specs。

Code 文档可以承载：

1. 工具使用说明；
2. 命令示例；
3. 开发者维护说明；
4. 故障排查；
5. fixtures 说明；
6. 版本兼容说明；
7. 实现细节和已知限制。

Code 文档不得承载：

1. LDVH 稳定规范规则；
2. 对象字段契约；
3. 状态机权威定义；
4. Human Gate 权威条件；
5. 事实源最终结论；
6. 与 specs 冲突的行为定义。

复杂工具的 Code 文档可放入 `docs/`、`tools/` 附近的实现说明或项目约定的代码文档位置。若 Code 文档中的内容具有长期规范效力，应回写 specs；若形成事实实例、决策或任务，应回写 ldvh-base。

## 11. Code 与 AI 协作关系

工具可以辅助 AI 读取事实源、获得结构化上下文、执行确定性校验和准备受控写入，但工具不得替代 AI 的场景判断，也不得直接调用或模拟 AI 决策。

协作边界如下：

1. Rules 可约束 AI 使用工具的方式；
2. Skill 可在授权流程中调用工具执行确定性解析、校验、聚合、上下文准备或受控写入；
3. Agent 可调用工具获取结构化上下文或验证输入；
4. 工具不得直接调用 AI、Skill 或 Agent；
5. 工具可执行已授权、可机械化、可校验的受控写入，但不得产生授权本身、替代流程性判断或绕过 Human Gate；
6. 当前 AI 运行环境提供的 Task、Search、Agent 调用等系统能力不自动归入 LDVH Code 或 PyTools，不得据此放宽工具不调用 AI、Skill 或 Agent 的边界；
7. 工具输出与 AI 判断冲突时，以 Git 文件事实源和对应规范为准。

---

## 12. Code 与 Web 的关系

Code 和 Web 是独立构成要素，但允许协作。

| 事项 | Code / PyTools | Web |
|---|---|---|
| 确定性解析 | 负责 | 可调用结果 |
| 校验算法 | 负责 | 展示结果 |
| 受控写入执行 | 负责已授权写入 | 负责人工确认入口 |
| 派生视图 | 可生成数据 | 负责呈现 |
| Human Gate UI | 不负责 | 负责展示和确认体验 |
| 权威事实 | 不承载 | 不承载 |
| 页面交互 | 不负责 | 负责 |

Web 需要确定性数据时，应优先调用 Code / PyTools 或后端聚合逻辑。Web 不得在 UI 中另建权威事实，不得绕过 Code 的校验和受控写入边界直接修改 Git 文件事实源。

## 13. 机制落地关系

本文通过以下机制关系说明相关机制实体的落地、同步、检查或审计触发条件。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| Rules | `../.trae/rules/ldvh-workspace-rules.md`、`../.trae/rules/ldvh-project-rules.md` | 工具使用、校验、受控写入和提交前检查入口 | 本文的 Code 边界、工具使用要求、测试要求或受控写入规则变化时 |
| Tools | `tools/` | 确定性实现 | 本文的工具制作、使用、测试、维护或删除规则变化时 |
| Tests | `tests/tools/` | 工具行为验证 | 工具输入、输出、错误码、写入行为或消费契约变化时 |
| Web | `specs/15-Web信息同步规范.md`、`web/` | 派生视图与人类确认入口 | Web 消费工具输出、触发受控写入或展示工具诊断结果时 |

具体工作模型或工作流程如需工具能力，应在对应主规范中说明 Tools 适配边界、消费契约、验证入口和降级方式。

## 14. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变本文定义的 Code / PyTools 职责分工；
2. 改变 `tools/`、`tests/` 或 Code 文档的目录定位、事实源性质或工具分工；
3. 工具写入或覆盖 Git 文件事实源；
4. 工具改变事实源归属；
5. 工具将派生数据、缓存、运行时索引或测试结果提升为稳定事实；
6. 工具绕过 Rules、对象状态机、工作流程或 Human Gate；
7. 删除被 Rules、Skill、Agent、Web 或其他工具消费的工具。

Code 一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| Code 边界 | Code 只承载实现、工具、测试、自动化检查和代码文档，不替代 specs 或事实实例 |
| 工具制作 | 新工具已声明输入、输出、事实源、规范来源、写入行为、Human Gate 和测试入口 |
| 工具使用 | 使用场景、降级方式和必须检查条件已明确 |
| 工具测试 | 新增或修改工具已同步测试，测试不通过不得提交 |
| 工具维护 | 规格变更已同步检查工具、测试、文档和下游消费方 |
| 事实源边界 | 工具输出、缓存、索引和测试结果未替代 Git 文件事实源 |
| AI 协作边界 | 工具未直接调用 AI、Skill 或 Agent |
| Web 边界 | Web 展示和确认体验未进入 Code，Code 未承担 UI 产品设计 |
