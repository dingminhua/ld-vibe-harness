## 2. 04 Helper 公共接口

### 2.1 公开操作标识 / Public Operation Identifier

预期含义：稳定识别 Helper CLI 某一项已经由当前来源定义的公开操作，使 AI、Code、tests 和环境入口引用同一服务行为，而不依赖内部函数、文件路径、实现存在性或展示名称。04 当前由 `operation_key` 承载。

- 来源分类：LDVH Helper 服务特定的接口概念；不是行业标准术语。
- 现有术语不足：`spec_key`、`attachment_key` 是规范模型身份；命令名可能包含通用 `call`，都不能稳定识别被调用的具体服务行为。
- 中文候选：`公开操作标识`。
- 英文候选：`Public Operation Identifier`。
- 替代名称：`Operation Key` 适合作为机器字段俗称，但不能完整表达“公开、稳定且不依赖实现”的概念；`Public Capability Identifier` 会把操作身份与当次能力可用性混在一起，因此不采用。
- 定义：由具体公开操作的当前来源赋予，在全部当前公开操作中唯一、改名或移动时保持、取消后不得改派，用于跨 AI、Code、tests 和环境入口稳定引用同一 Helper 服务行为的标识。
- 机器表示：字段 `operation_key`；具体值由定义该公开操作的当前来源确定。
- 发现结构：第二轮修订要求具体操作来源在固定 `Helper 公开操作` H3 下使用固定 Markdown 表格声明 key、摘要、读取/状态变更边界和输入/结果契约位置。表格只是当前来源中的机器读取入口，不另建正式架构术语，也不成为平行注册表；采用表格而非正文 YAML，避免越过 01 已定义的 YAML 解析边界。
- 正例：规则读取、管辖解析或未来事实读取能力分别具有稳定且来源明确的操作 key。
- 反例：Python 函数名、CLI 别名、厂商 Hook 事件、尚未实现的路线图名称。
- 相邻概念：公开 CLI 命令负责路由；能力发现报告当次可调用性；操作标识不证明实现、授权或调用成功。
- 替换检查：若去掉该概念，环境入口和 tests 只能依赖命令文本或内部函数，无法稳定引用同一公开服务行为。
- 代表性代入：把定义代入“`call` 通过稳定的公开操作标识调用某项操作”和“Code 不得反向创造公开操作标识”，仍分别表示跨入口稳定引用和来源先于实现，没有扩大为能力可用或调用成功。
- 使用扫描：当前命中 04、04.Att.01、术语表和本审计记录；active 00–03 没有同名异义，`spec_key`、`attachment_key` 和未来 `template_key` 均有各自对象边界。
- 影响范围：接受该术语会约束未来操作来源表格、Helper 实现注册、Code/tests 和环境映射；改名必须同步 04、附件、术语表和消费者；取消则必须提供另一种不依赖命令文本或内部函数的稳定身份机制。
- 唯一定义来源：`helper-cli-service-contract` §「5.1 入口与输出形式」。
- Human 确认：不单独新增 Human Gate；随 04 激活决定一并确认，Human 确认不能替代语义与机器契约检查。
- 独立复核结论：概念必要、名称自然、边界明确。已以 `proposed` 登记双语术语表；`operation_key` 只作为该概念的机器表示，不扩张为所有 LDVH 对象的通用 key。04 进入当前规则源时才可同步转为 `current`。

### 2.2 当次操作可用性 / Request-specific Operation Availability

预期含义：说明一个已经由当前规则源定义的公开操作，在给定请求内容、对象范围和观察时点下，实际可以调用到什么范围。04 当前使用：

```text
unavailable_for_request
partially_available
available_for_request
```

- 来源分类：LDVH Helper 服务特定的请求级接口概念；不是长期状态模型，也不是行业标准枚举。
- 现有术语不足：00 只禁止把未实现、未接入和未验证冒充为可用，没有提供机器响应区分零个、部分和全部请求范围的字段。
- 中文候选：`当次操作可用性`。
- 英文候选：`Request-specific Operation Availability`。
- 替代名称：`操作可用性 / Operation Availability` 容易被理解为长期能力状态；`请求可用性 / Request Availability` 没有指出被判断的是公开操作，因此不采用。
- 定义：一个已有当前来源的公开操作，在给定请求内容、对象范围和观察时点下，零个、部分或全部请求范围实际可以调用的程度。
- 机器表示：字段 `availability`；通用发现未获得具体请求时为 `null`，针对单项操作的检查只使用上述三个值。
- 正例：公开操作已经定义，但没有实现或能力依据，因此当次零范围可调用；多对象请求只有部分对象可调用；全部请求范围可调用。
- 反例：是否发现实现、项目长期“能力状态”、环境 `integrated`、功能路线图阶段、调用执行结果或上层工作完成状态。
- 相邻概念：通用发现分别报告公开来源、实现存在性和所需输入，但不判断尚未提供的请求；Helper 服务结果描述发现或调用过程是否完成；本概念只绑定某一公开操作和给定请求。
- 替换检查：若只返回布尔 `available`，无法表达多对象请求中的部分范围；若继续把实现是否存在、无契约实现和请求级可用性放进一个枚举，则没有具体请求时会被迫把“尚未检查”误写成“不可用”。
- 代表性代入：把定义代入“判断该公开操作对当次请求范围的可用性”和“通用发现不计算当次操作可用性”，分别仍表示给定请求下零/部分/全部范围和未提供请求时不作判断。
- 决策顺序：当前来源不存在的名称为无效请求；已有来源但没有实现、缺少可复核能力依据或零个独立范围可调用时为 `unavailable_for_request`；至少一个独立范围可调用且至少一个不可调用时为 `partially_available`；全部请求范围可调用时为 `available_for_request`。
- 使用扫描与影响范围：取代第一版草案登记的“能力发现结果 / Capability Discovery Result”；`defined_not_implemented` 改由 `implementation.present: false` 表达，`implementation_without_contract` 退出公开清单并只作为契约缺口诊断。影响 04、其授权附件、术语表及未来 Helper/Code/tests/环境映射，不影响 active 00–03。
- 唯一定义来源：`helper-cli-service-contract` §「6.2 当次操作可用性」。
- Human 确认：不单独新增 Human Gate；随 04 激活决定一并确认。
- 独立复核结论：概念必要，中英文自然且范围一致；`availability` 只回答零、部分或全部请求范围是否可调用。通用发现时为 `null`、未知 key 为 `invalid_request`、无契约实现只作诊断，已经完整替代旧候选而没有遗漏必要分流。建议保留并继续以 `proposed` 登记。

### 2.3 Helper 服务结果 / Helper Service Outcome

预期含义：一次公开 Helper 发现或调用请求在其请求范围内形成的外层结果，用于机器调用方先分流，再读取范围、来源、变化、验证和缺口。04 当前使用：

```text
ok
no_change
partial
rejected
unavailable
invalid_request
error
```

- 来源分类：LDVH Helper 服务特定的接口概念；中英文名称是 LDVH 特定限定表达，不声称为行业标准术语或枚举。
- 现有术语不足：进程退出码只能快速分流，`result` 是领域结果内容，`success` 布尔值会折叠拒绝、不可用、部分完成和无变化；三者都不能承担共同外层结果语义。
- 中文候选：`Helper 服务结果`。
- 英文候选：`Helper Service Outcome`。
- 替代名称：第一版 `服务结果 / Service Outcome` 比 Helper 专属定义范围更宽，独立复核后取消；`调用结果 / Call Result` 容易与 `result` 内容混淆；`执行结果 / Execution Result` 无法自然包含尚未执行即被拒绝或请求无效的情况。
- 定义：Helper 已开始处理一次公开发现或调用请求后，对该请求在当次范围内是否全部完成、无需变化、部分完成、被拒绝、不可用、无效或发生实现错误所作的唯一外层分类。
- 机器表示：字段 `outcome`，使用本节七个互斥值；退出码只是其快速分流镜像。
- 正例：结构有效但授权不足为 `rejected`；只有部分对象完成为 `partial`；请求完成但没有变化为 `no_change`。
- 反例：事实对象状态、测试结论、Human Gate 结果、环境集成状态、项目完成状态。
- 相邻概念：进程退出码只是快速分流镜像；`outcome` 是共同外层分类，具体操作 `result` 是由操作来源定义的领域内容；当次操作可用性检查成功完成时，即使内部 `availability` 为部分或不可用，外层 Helper 服务结果仍可为 `ok`。完整语义还包括 `scope`、`sources`、`gaps`、`changes` 和 `verification`。
- 替换检查：只使用 exit code 或 `success: true/false` 会折叠拒绝、不可用、部分结果和无变化，导致调用方扩大解释。
- 代表性代入：把定义代入“`outcome` 返回一次 Helper 服务结果”和“当次检查的 Helper 服务结果可以为 `ok`”，都只指发现或调用请求的共同外层分类，不会覆盖领域 `result` 或其它服务的普通结果。
- 使用扫描：当前命中 04、04.Att.01、术语表、责任审计和本批复核记录；active 00–03 使用“实际调用结果”等普通表达，但没有定义本七值分类。增加 `Helper` 限定后不会把这些普通结果自动纳入 `outcome`。
- 影响范围：接受或改名会影响 04、附件字段说明、术语表以及未来 Helper/Code/tests/环境入口对 `outcome` 的引用；取消则必须改用另一种能够保留七类分流的共同外层结果表达。
- 唯一定义来源：`helper-cli-service-contract` §「7.2 Helper 服务结果与退出码」。
- Human 确认：不单独新增 Human Gate；随 04 激活决定一并确认。
- 互斥顺序：先判断请求结构，不成立为 `invalid_request`；至少一个独立子范围完成且至少一个未完成时为 `partial`；没有子范围完成时，规则/授权拒绝为 `rejected`，实现、可复核能力依据、配置、依赖或环境不足为 `unavailable`，实现异常或结果不可信为 `error`；全部范围执行并形成结果为 `ok`；只有允许执行且检查完成的状态变更请求在目标已满足或无需变化时使用 `no_change`。
- 独立复核结论：概念及七值区分必要，互斥顺序成立；第一版无修饰名称范围过宽，改为 `Helper 服务结果 / Helper Service Outcome` 后与定义一致。退出码映射和 `outcome` 字段属于同一公开契约；不得把 `ok` 或 `no_change` 解释为上层工作完成。

### 2.4 规则适用判断结果 / Rule Applicability Evaluation Result

预期含义：Helper 针对一条已定位来源规则、一个明确对象范围和当次输入，报告是否已经完成适用判断及其结果。04 当前使用：

```text
applies
does_not_apply
insufficient_information
not_evaluated
```

- 来源分类：LDVH Helper 服务对来源规则判断的接口概念；不是新的规则效力模型。
- 现有术语不足：具体来源规则定义适用条件，但没有提供 Helper 区分“适用、不适用、依据不足和尚未检查”的共同机器结果；布尔值会把后两类误写成不适用。
- 中文候选：`规则适用判断结果`。
- 英文候选：`Rule Applicability Evaluation Result`。
- 替代名称：`Rule Applicability Result` 更短，但容易把 `not_evaluated` 误读成已经形成适用性结果；`Rule Effect Result` 会错误扩大到规则效力和履行状态，因此不采用。
- 定义：Helper 针对一条已定位的当前来源规则、一个明确对象范围和当次输入，报告是否已经完成适用判断，以及判断为适用、不适用、依据不足或尚未检查的结果。
- 机器表示：字段 `applicability`；不复用 01 已用于规范依据的 `basis`。
- 正例：依据足以判断命中；依据足以判断不命中；依据不足；尚未执行检查。
- 反例：规则优先级、规则有效/无效、规则已自动保障、AI 是否遵守、行动是否完成。
- 相邻概念：01 定义当前规则源和披露层级；具体来源定义适用条件和效力；02 提供对象范围；本概念只报告某次判断。
- 替换检查：如果把依据不足和尚未检查都写成“不适用”，AI 会把未知范围误当成已排除规则。
- 代表性代入：把定义代入“通过 `applicability` 返回一项规则适用判断结果”和“该规则适用判断结果绑定对象与当次输入”，仍分别表达四值判断状态和当次范围，不会变成规则效力或行动完成结果。
- 使用扫描：当前命中 04、术语表和本批审核记录；active 01 的 `basis` 只表示规范依据，02 的管辖判定只表示工作对象范围，均不承担规则适用判断结果。
- 影响范围：接受该术语会约束未来 Helper 规则服务、Code/tests 和环境入口对 `applicability` 的解释；改名须同步 04、术语表和消费者；取消则会失去区分依据不足与尚未检查的共同接口。
- 唯一定义来源：`helper-cli-service-contract` §「9. 规则信息与判断报告」。
- Human 确认：不单独新增 Human Gate；随 04 激活决定一并确认。
- 独立复核结论：收窄后的名称准确表达规则对对象和当次输入的适用判断；`insufficient_information` 与规范 `basis` 不再混淆。四分结果具有明确净价值，但必须维持“来源规则语义不变、结果绑定当次对象和输入”的边界。04 转为 `active` 前登记概念。

### 2.5 04 的其它字段

`task`、`arguments`、`scope`、`sources`、`gaps`、`changes`、`verification`、`diagnostics` 等在 04 中是普通接口字段，并已由表格直接限定语义；当前没有证据要求把每个字段分别提升为双语架构术语。若未来字段被跨多个规范作为独立概念复用、出现名称歧义或形成机器枚举，必须重新执行 01 §12，而不能凭本记录自动取得 `current`。

## 3. 05 事实模型候选术语

### 3.1 事实类型 / Fact Type

预期含义：对一类准备在项目中稳定保留、具有相同事实语义和实例边界，并需要按共同规则接受对象化、状态化或证据化管理的事实内容所作的语义分类。

- 必要性：`事实模型` 是 00 定义的构成要素，`稳定事实` 是 03 定义的内容性质；二者都不能表达一类对象共同接受何种准入、身份和更新规则。不建立本概念时，具体对象只能依赖目录、Schema 或历史名称被归类，Code 容易反向决定类型语义。
- 来源分类：常见描述性表达，LDVH 对其准入范围和语义边界作特定定义；不声称行业标准。
- 中英文候选：首选 `事实类型 / Fact Type`；`事实对象类型` 只作为 active 03 已使用的中文别名，不另建英文别名。
- 定义：对一类准备在项目中稳定保留、具有相同事实语义和实例边界，并需要按共同规则接受对象化、状态化或证据化管理的事实内容所作的语义分类；每类由当前有效的唯一定义来源定义。
- 正例：经准入后具有共同对象语义、身份和状态要求的一类决策记录。
- 反例：文件扩展名、目录、Schema 名、前端筛选项、Code 类名和 V3 遗留类型名称。
- 相邻概念：`事实模型` 是构成要素；`事实对象` 是类型下的具体单位；`稳定事实` 还包括不需要对象化的普通内容。类型成立不等于其中每个对象的当前内容有效。
- 替换检查：把定义代入“该事实类型需要独立证明准入条件”和“Code 不得创造事实类型”，分别仍表示语义分类需要准入、实现不能反向决定分类，没有扩大为具体对象或整个事实模型。
- 代表性代入：把定义代入“一个历史名称不证明该事实类型已经在 V4 准入”，仍然表示历史名称不能证明对应语义分类及其共同规则成立。
- 使用扫描：激活同步后，首选名称命中 00、03–06、08；中文别名“事实对象类型”只保留在 05 的别名说明、术语表和架构记录中。07 正文没有命中。00 同时使用上位概念“事实模型”和本概念；没有发现同名异义。
- 影响范围：接受该术语会影响 00、03–06、08、术语表、事实类型声明及未来 Helper/Code/tests/Web 消费；改名必须同步这些位置；取消则无法准确表达类型级准入和共同规则。
- 唯一定义来源：`fact-model-foundation` §「5.1 事实类型（Fact Type）」。
- Human 边界：Human 已同意采用比 V3 更清楚的分布式类型身份方案；该决定不豁免语义检查。术语本身不新增 Human Gate。
- 检查结论：保留。概念必要，中英文范围一致；独立复核和 active 03 首选表达同步已经完成。

### 3.2 事实对象 / Fact Object 与事实实例 / Fact Instance

预期含义：已准入事实类型之下，按该类型唯一定义来源规定的身份、结构和位置承载、可跨行动与会话独立定位和更新的一项稳定事实单位。

- 必要性：只称“对象”会与 02 的工作对象混淆，只称“稳定事实”无法表达已准入类型下的独立身份、当前权威位置、关系和变更边界。
- 来源分类：LDVH 特定术语；不声称行业标准。
- 中英文候选：首选 `事实对象 / Fact Object`；保留 `事实实例 / Fact Instance` 为中英文别名，用于承接 active 03 已有的 type/instance 表达，不作为另一概念。
- 定义：在已准入事实类型之下，由该类型的定义来源赋予稳定身份和当前权威位置、用于独立定位、验证、关联和更新事实内容的单位。
- 正例：已准入类型下、位于唯一当前权威位置、可通过项目、类型和对象身份稳定引用的一项记录。
- 反例：任意文件或 YAML 映射、命令输出、缓存、Web 视图、未准入的 V3 实例，以及仅因当前事项指向而成为工作对象的普通资源。
- 相邻概念：`事实类型` 约束一类对象；`稳定事实` 不一定需要成为事实对象；`工作对象` 绑定当前事项。同一资源在当前事项指向时可以同时是工作对象和事实对象，但成立条件不同。
- 替换检查：把定义代入“更新事实对象前必须定位当前权威位置”和“缓存不得成为事实对象”，分别仍表示稳定单位的更新目标与排除派生内容，不会误指当前事项中的任意资源。
- 代表性代入：把定义代入“事实对象身份可以在当前内容无效时继续用于定位修复目标”，仍能区分稳定单位身份与当前内容有效性。
- 使用扫描：激活同步后，首选名称命中 00–03、05、06；别名“事实实例 / Fact Instance”只保留在 05 的别名说明、术语表和架构记录中。未发现另一独立实例概念；02 的工作对象边界已经在 05 明确区分。
- 影响范围：接受该术语会影响 00–03、05、06、术语表、具体事实类型及未来 Helper/Code/tests/Web；改名必须同步首选名称和别名；取消会重新造成工作对象、稳定事实和类型实例之间的歧义。
- 唯一定义来源：`fact-model-foundation` §「5.2 事实对象（Fact Object）」。
- Human 边界：随 05 是否激活一并确认，不新增独立 Human Gate；Human 确认不能替代独立语义复核。
- 检查结论：保留首选 `事实对象 / Fact Object`，并把 `事实实例 / Fact Instance` 作为同一概念的别名；active 03 和其它直接引用已经同步。

### 3.3 事实类型标识 / Fact Type Identifier

预期含义：为每个已经准入的具体事实语义分类提供一个不依赖标题、路径、Schema、目录或实现模块的稳定机器身份，使分布在不同当前规则源中的类型可以被唯一引用和确定性发现。

- 必要性：`spec_key` 识别规范责任，一份规范可以定义多个事实类型，不能替代类型身份；类型名称、标题、目录和 Code 注册名都可能变化或产生歧义。若不在 05 统一最小身份规则，第一个具体类型或实现会自行决定 key、唯一范围和发现位置，后续跨类型消费需要迁移。
- 来源分类：LDVH 事实模型特定的机器接口概念；不声称行业标准。
- 中英文候选：`事实类型标识 / Fact Type Identifier`。`Fact Type Key` 只适合作为机器字段俗称；`Fact Type ID` 容易与具体对象 ID 或运行时数据库 ID 混淆，因此不作为规范英文名。
- 定义：具体事实类型的唯一定义来源赋予、用于跨规范、Helper、Code、tests 和 Web 稳定引用同一事实类型的机器可读标识。
- 机器表示：`fact_type_key`，使用小写 ASCII kebab-case，匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`；在全部当前事实类型中唯一，类型改名或移动时保持，取消后不得改派。
- 正例：两个不同当前来源分别定义的具体事实类型使用不同稳定 key；同一类型的定义章节移动后继续使用原 key。
- 反例：规范 `spec_key`、具体事实对象 ID、目录名、Schema `$id`、Python 类名、V3 历史类型名称和尚未准入的路线图名称。
- 相邻概念：`职责标识符` 识别规范或附件责任；`事实类型` 是被识别的语义分类；事实对象身份在同一管辖项目和事实类型内唯一。类型 key 不证明实现存在、对象有效或 Helper 操作可用。
- 替换检查：把定义代入“`fact_type_key` 在全部当前事实类型中唯一”和“Code 不得改派事实类型标识”，仍分别表示类型级稳定机器身份的唯一性与来源先于实现，不会覆盖规范或对象身份。
- 代表性代入：把定义代入“跨类型稳定引用必须保留事实类型标识”，可以准确说明引用为何不能只保存对象局部 ID。
- 使用扫描：当前命中 05、术语表和本记录；active 00–04 没有同名异义。04 的 `operation_key` 识别 Helper 公开操作，01 的 `spec_key` / `attachment_key` 识别规范职责，边界不同。
- 影响范围：接受该术语会约束具体事实类型声明、对象跨类型引用及未来 Helper/Code/tests/Web；改名必须同步 05、术语表、声明表和消费者；取消会使类型身份回退到名称、路径或实现注册。
- 唯一定义来源：`fact-model-foundation` §「5.3 事实类型标识（Fact Type Identifier）」。
- Human 边界：Human 已同意在确实优于 V3 的前提下采用本最小设计；该决定不豁免独立复核，也不授权中央类型清单、具体类型或实现。
- 检查结论：保留。概念只承担类型级稳定机器身份；分布式声明表仍位于各类型唯一定义来源，不建立中央白名单；独立复核已经完成。

## 4. 06–08 标题和重复表达

### 4.1 06

“参与者、能力与授权”分别指谁承担行动、需要什么实际能力、允许影响什么范围，替代了过于宽泛的“执行资源”。它们都是当前语境中的普通名词，不需要合成新的正式术语。具体行动模板的“唯一定义来源、稳定身份和发现入口”复用 01 的定义来源与身份治理，不建立新的模板状态模型。

06 为具体行动模板提出 `template_key`，用于在当前规则源中稳定识别模板，并把它映射到当前定义来源 `spec_key` 与正文位置。它是行动模板特定的机器身份，不是规范职责标识符，也不证明模板适用、已执行或已验证。

- 候选中文：`行动模板标识`。
- 候选英文：`Action Template Identifier`。
- 来源分类：LDVH 行动模板特定接口概念，不声称行业标准。
- 正例：模板改名或移动时 key 保持，拆分、合并、替代时旧 key 能回到承接说明。
- 反例：规范 `spec_key`、文件名、标题、编号、某次模板运行 ID。
- 初步结论：稳定身份概念必要；具体正文承载格式尚未成立。第一份具体模板准入前必须完成机器格式和独立复核，若该名称需要跨 Helper、Code 和模板定义来源复用，则同步登记双语术语表。

### 4.2 07

Human 确认中文标题为 `Code 实践与测试规范`，英文采用 `Code Practices and Testing Specification`。`code-engineering-practices` 保持表示已审定的统一 Code 工程责任；测试从一开始就是该责任的一部分，标题显式化不构成职责拆分。

07 的“Code 规划、模块责任、依赖方向、接口与 Schema 维护、诊断、重构评估、风险驱动测试、测试检查范围”是正文直接说明的工程表达。除下述 `Code 规划` 外，当前没有把这些表达登记为 LDVH 架构构成要素、机器状态或行业标准术语。

独立复核确认 `Code 规划 / Code Planning` 已经承担稳定形成时机、最小内容、同步、偏移、验证与停止条件，因此不能继续只作为普通短语。候选审查如下：

- 准确定义：面向一个实际准备实现或变更范围的版本化实现说明，在编码前记录来源、模块责任、依赖与调用方向、接口与 Schema 维护责任、错误与诊断、风险、测试和已知缺口，并在这些内容变化时同步更新。
- 来源分类：LDVH Code 实践中的特定描述性术语；不声称是行业标准。
- 中文候选：`Code 规划`。
- 英文候选：`Code Planning`。
- 替代名称：`Implementation Plan` 容易落入任务步骤和排期；`Code Design Description` 弱化先于实现、持续同步和测试映射；`Code Engineering Plan` 容易被理解为项目级工程计划，因此均不采用。
- 现有术语不足：单次实施计划关注本次步骤和进度；架构描述可能覆盖更广产品或系统；实现说明没有自动包含“先于相应实现并与边界变化同步”的责任。
- 正例：首个 Helper 增量开始前，对实际准备实现的模块、依赖、接口、Schema、诊断和测试形成版本化说明。
- 反例：任务排期、当前进度、未来路线图、源码文件列表、事后为既成实现补写的合理化说明。
- 相邻概念：它不是规则源、产品契约、具体事实类型或项目排期；可以使用架构图等表达形式，但不因此等同完整架构描述标准。
- 替换检查：取消该概念而只要求“先想清楚”无法稳定定位实现前输入、维护责任和设计偏移；拆成多项零散记录会增加同步遗漏。
- 唯一定义来源：候选 07 §5；在 07 为 `draft` 时只具有 proposed 状态。
- 使用扫描与影响范围：当前只命中 07、07 调查记录、本记录和关系/建设记录，没有与当前规则源既有术语冲突；未来会影响版本化 Code 规划文件、Helper 实现前置和 Code/tests 交付检查。

- 独立复核：一名未参与 07 起草的执行者确认概念必要、中英文范围一致，并确认上述三个替代名称均不如当前名称准确；候选可以登记为 `proposed`，但只有 07 进入当前规则源且术语表同步满足 `current` 条件后才能生效。
