## 1. 本文解决的问题

本文定义 v3 spec 应如何写，才能同时满足 Human 可读、Code 可解析、AI 可行动。

本文解决：

1. Markdown 正文如何作为唯一规范事实源；
2. v3 spec 的身份块、章节、父子关系和来源回指如何稳定表达；
3. 附件如何只承载被父规范授权的机器可读契约、闭集、表格和模板；
4. 如何避免 v2 中通用治理语言、Human Gate、事实源边界、Code 消费和检查清单在每篇正文中重复膨胀；
5. Code 如何从 spec 结构生成 Action Guide 所需的关系、读取计划、影响判断、停止条件和下一步查询。

本文不定义事实模型字段、行动流程、Code 实现结构、Web 展示、Runtime 入口或 Git 提交规则。

## 2. 上位依据

本文承接 `specs/00-LDVH-v3理念与价值标准.md`。

若本文与 00 冲突，以 00 为准。若本文与 v2 01 冲突，v3 内以本文为候选方向；但不得反向改变 v2 active 规范。

## 3. 规范事实源和机器契约

v3 spec 正文使用 Markdown。Markdown 正文是规范事实源，必须保留足够的自然语言说明，使 Human 和 AI 能理解规则背景、边界和 Human Gate。

机器契约分三层：

| 层级 | 承载 | 作用 | 事实源地位 |
|---|---|---|---|
| Markdown 正文 | `specs/*.md` | 规则权威、边界、价值判断和本地 delta | 规范事实源 |
| 授权附件 | `specs/attachments/*.md` | 字段表、闭集、章节角色、关系类型、判定矩阵 | 由父规范授权 |
| schema | `specs/schemas/*.yaml` | Code 校验的机器结构 | 机器契约，不是上位规范 |

不得为普通 spec 长期维护人工 YAML 孪生文件。YAML 可以用于 schema、fixture、临时迁移证据和生成调试输出。

## 4. v3 spec 必要结构

v3 spec 至少包含：

| 结构 | 作用 |
|---|---|
| H1 标题 | Human 入口和 Code 标题 |
| `v3_spec` identity block | Code 解析身份、状态、父子关系、来源和消费类别 |
| 本文解决的问题 | 本地问题和 AI 负担说明 |
| 上位依据 | 父层规则和来源回指 |
| 构成要素归属与价值判断 | 说明服务哪些 V 项和减少哪类 AI 负担 |
| 本地规则 | 只写本 spec 特有规则和 delta |
| Code / Action Guide 消费边界 | 说明可解析字段和生成导航责任 |
| Human Gate | 只写本 spec 特有暂停条件，通用 doctrine 继承父层 |
| 待补齐事项 | 可生成 next_queries 的未决项 |

章节名称可以按语义调整，但必须能被 Code 映射到 `specs/attachments/01.Att.02-规范章节角色表.md` 的章节角色。

## 5. 父子规则和去冗余

v3 使用父层规范减少重复。父层规范定义通用 doctrine；子规范只写本地 delta。

子规范不得重复大段父层通用规则。需要承接父层规则时，使用以下方式之一：

1. 在 `v3_spec.parent_spec` 声明父规范；
2. 在“上位依据”中说明继承关系；
3. 在本地规则中只写差异、例外、扩展或更严格约束；
4. 让 Code 从父层和子层共同生成检查项或 Action Guide。

去冗余不得删除以下内容：

1. 本地 Human Gate；
2. 本地事实源边界；
3. 行动特有场景、准入条件和执行差异；
4. 本地回写、验证和证据要求；
5. Code 稳定解析所需的 identity block、章节角色、source refs 和本地 delta。

## 6. 附件规则

01 的附件只承载 v3 spec 体系的最小机器契约：

| 附件 | 作用 |
|---|---|
| `01.Att.01-规范身份字段表.md` | 定义 `v3_spec` identity block 字段 |
| `01.Att.02-规范章节角色表.md` | 定义章节角色及其 Action Guide 消费方式 |
| `01.Att.03-行动指南关系类型表.md` | 定义 Code 可输出的关系类型闭集 |
| `01.Att.04-去冗余判定表.md` | 定义重复内容的处理分类 |

v3 01 不手写当前全量目录登记。目录、附件清单、关系图和一致性诊断应由 Code 从 Markdown 文件生成，避免手写目录成为第二事实源。

v3 01 不建立独立术语大表，除非术语差异已经阻塞 Code 解析或 AI 行动。表达建议、长检查清单、迁移日志和过程审查不应放入 01 附件。

## 7. Action Guide 输入责任

每篇 v3 spec 必须为 Action Guide 提供足够输入：

| Action Guide 要素 | spec 来源 |
|---|---|
| relationships | `parent_spec`、`basis`、`related_specs`、附件引用和显式关系 |
| read_plan | 上位依据、章节角色、附件角色和本地规则 |
| impact_judgment | 构成要素归属、消费类别、相关规范和本地变更边界 |
| stop_conditions | Human Gate、本地禁止项、状态/authority 和待澄清项 |
| next_queries | 待补齐事项、缺失 source refs、无法解析章节或未确认迁移项 |
| verification | Code 消费类别、schema、测试入口或等价验证说明 |
| source_refs | canonical path、父规范、附件和来源文件 |

Code 可以生成这些导航输出，但不得把输出写成权威事实源。

## 8. Human Gate

以下情况必须暂停确认：

1. 将 YAML 或 schema 作为普通 spec 的上位权威；
2. 新增 01 附件但不能说明减少 AI 哪类负担；
3. 手写全量目录、全量关系图或全量检查清单，导致第二事实源；
4. 去冗余方案删除本地 Human Gate、事实源边界或行动特有 delta；
5. Code 输出 `allowed`、`approved`、`unblocked` 等授权语义；
6. 修改 Runtime、hook、dispatcher、rules、skills 或 Web 策略。
