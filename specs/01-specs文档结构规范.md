## 一、本文解决的问题

本文解决 LD Vibe Harness specs 文档如何编号、如何分区、如何区分正式规范文档、子文档、实践文档和内部调研文档，以及如何通过引用纪律避免多个事实源的问题。

LD Vibe Harness 的 specs 文档治理目标，不是让所有内容都进入同一种文档格式，而是让 AI、人和工具能稳定判断一份文档在规范体系中的位置、权威范围、上位依据、引用方式和 Human Gate 要求。

## 二、与 00 总纲的关系

00 定义 LD Vibe Harness 的产品理念、价值实现标准、五类构成要素和基础规范索引。本文承接 00 中关于规范体系结构和事实源单一性的要求，专门定义 specs 文档结构、编号分区、文档类型、引用纪律和治理检查。

本文是 specs 文档结构和文档治理规则的权威位置。00 只保留基础规范索引和对本文的引用，不重复维护编号分区、子文档、实践文档、引用纪律和写作检查细则。

## 四、编号分区

LD Vibe Harness specs 采用分区编号，编号本身必须表达文档在规范体系中的位置。编号分区围绕五类构成要素展开，而不是围绕文档形态展开。

| 编号段 | 类型 | 说明 |
|---|---|---|
| 00 | 理念与纲要 | 定义 LD Vibe Harness 的存在理由、第一服务对象、价值实现标准、五类构成要素和顶层治理原则 |
| 01-07 | 基础规范 | 定义 specs 文档结构、文件夹说明、事实源、Trae Solo 环境机制、LDVH 工具、LDVH 生产对象和 LDVH 行动模型的基础规则 |
| 08-09 | 保留基础规范扩展 | 保留给后续基础规范扩展 |
| 10-39 | LDVH 生产对象规范 | 10 可作为生产对象集合索引，11 起为具体生产对象规范 |
| 40-69 | LDVH 行动模型规范 | 40 可作为行动模型集合索引，41 起为具体行动规范 |
| 70-89 | 内部调研 | 承载 LD Vibe Harness 内部调研、设计探索、方案比较和经验分析 |
| 90-99 | 保留 | 保留给后续扩展，不得未经确认提前占用 |

新增、调整或占用编号段属于规范体系变更，应评估 Human Gate。

## 五、文档类型

### 5.1 正式规范文档

正式规范文档使用两位编号，格式为 NN。正式规范文档可以定义稳定规则，适用于 00-69 区间。

示例：

```text
01-specs文档结构规范.md
02-LDVH文件夹说明.md
03-事实源边界与承载规范.md
04-Trae-Solo环境机制规范.md
05-LDVH工具基础规范.md
06-LDVH生产对象基础规范.md
07-LDVH行动模型基础规范.md
10-生产对象集合索引.md
40-行动模型集合索引.md
```

正式规范文档必须声明上位依据、解决问题、与 00 总纲的关系、事实源边界、不进入本文的内容和待补齐事项。

### 5.2 子文档

正式规范文档因内容超出单文档承载能力时，可以创建子文档。子文档编号格式为 NN.SS，其中 NN 为父文档编号，SS 为子文档序号。

子文档不是独立规范，而是父文档的扩展。子文档的权威来源是父文档，子文档不得与父文档矛盾。

示例：

```text
04.01-Rules机制规范.md
04.02-Skill机制规范.md
04.03-Agent机制规范.md
```

子文档不强制采用正式规范文档的完整骨架，但必须遵守父文档定义的子文档格式，并保留父文档引用、所属范围、章节归属和待补齐标记等最小治理信息。

### 5.3 实践文档

子文档下需要承载具体实践说明时，可以创建实践文档。实践文档编号格式为 NN.SS.PP，其中 NN 为父规范编号，SS 为子文档序号，PP 为实践序号。

实践文档不是独立规范，不得定义新的基础规则，只能记录对父规范或子文档的具体落地方式、实例说明、适用场景、输入输出、实体入口和维护状态。

示例：

```text
04.02.01-对话转任务技能实践.md
04.02.02-备忘写入技能实践.md
04.03.01-搜索Agent实践.md
```

具体 Skill / Agent 的实践文档只说明落地方式和使用边界，不替代 Trae Solo 实体定义文件，也不承载运行结果事实。运行结果形成稳定事实时，应按事实源边界写回 specs/、docs/ 或 ldvh-base/。

### 5.4 内部调研文档

70-89 内部调研承载 LD Vibe Harness 自身的研究、设计探索和方案比较。内部调研可以成为规范、ADR 或行动模型调整的依据，但其内容不直接构成强制执行规则。

内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

```markdown
> 适用范围：...

## N-2、Human Gate 与检查要求

## N-1、不进入本文的内容

## N、待补齐事项
```

头部字段规则：以上字段为必填字段。新增头部字段不得与已有字段语义重叠，不得在头部承载正文才应展开的规范内容。

子文档建议采用以下骨架：

```markdown

> 所属主文档：`specs/NN-xxx.md`
```

父文档可以为其子文档定义更具体的格式。子文档格式不得弱化本文定义的最小治理信息。

## 七、引用纪律

引用纪律的本质是事实源单一性在文档体系中的体现——同一个规则只能在一份文档中定义，其他文档只能指向它，不能复制它。

1. 权威唯一：每项稳定规则只能有一个权威定义位置。其他文档需要使用该规则时，只能写“依据 XX §Y”，不得复制、改写或另行定义同义规则；
2. 边界优先：判断规则权威位置时，优先依据事实源边界，而不是依据文档出现顺序、引用次数或描述详细程度；
3. 上位约束：00 定义体系理念、价值标准、构成要素和顶层治理原则；01 定义 specs 文档结构和治理规则；02 定义项目文件夹规划；03 定义事实源边界与承载规则；04 定义 Trae Solo 环境机制基础规则；05 定义 LDVH 工具基础规则；06 定义 LDVH 生产对象基础规则；07 定义 LDVH 行动模型基础规则；10-39 定义具体生产对象规则；40-69 定义具体行动模型规则；70-89 只提供内部调研，不直接构成强制规则；
4. 适配不重写：生产对象、行动模型、场景实践或工具说明引用基础规范时，只能说明如何适配，不能重新定义基础规则；
5. 冲突处理：当两个文档对同一规则给出不同表述时，应先判断该规则的权威领域；非权威文档应改为引用权威文档，不能保留并列规则；
6. 调研升级：70-89 内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

## 八、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增 specs 编号段或改变编号体系；
2. 重命名或重排 specs 文档；
3. 改变子文档或实践文档层级关系；
4. 子文档或实践文档重新定义父规范已有原则；
5. specs 文档引用 specs 外部文档作为规范依据；
6. 实践文档新增或扩张基础规范；
7. 将 70-89 内部调研结论直接作为强制规则使用。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

specs 文档写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 事实源边界 | 核心规则章节开头已声明本文权威领域和边界 |
| 文档类型 | 文档编号和骨架符合正式规范、子文档或实践文档类型 |
| 不写内容 | 已列出不进入本文的内容 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、生产对象和行动模型术语一致 |
| 文件夹规划一致性 | 与 `specs/02-LDVH文件夹说明.md` 的文件夹规划一致 |
| 事实源边界一致性 | 与 `specs/03-事实源边界与承载规范.md` 的事实源边界一致 |
