# 平台适配清单规范

> 创建日期：2026-06-09
> 定位：定义平台适配清单如何把 LDVH 对 AI 的支持要求和规范落地要求，逐项映射为具体 AI 开发平台上的承接方法、证据、降级和待补齐事项
> 适用范围：Trae Solo 桌面形态、Codex CLI、本地命令行、CI 或其他可在本地工作区内读取、验证和回写事实源的 AI 开发环境适配清单
> 上位依据：`docs/specs/04-规范落地与环境适配基础规范.md`
> 相关规范：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/04.01-规范落地声明规范.md`、`docs/specs/04.02-环境适配与运行投影规范.md`、`docs/specs/04.03-环境能力承接边界规范.md`、`docs/specs/42-ldvh-landing-check-LDVH落地与检查.md`

## 1. 本文解决的问题

本文定义平台适配清单机制。

平台适配清单不是平台能力说明书，也不是平台官方文档摘要。它的主轴是 LDVH 对 AI 执行者提出的支持要求和正式规范提出的落地要求；平台只是在每项要求下回答“在这个平台上用什么方法承接、证据是什么、不能完整承接时如何降级”。

本文当前不处理网页端、云端托管形态或移动端形态。上述形态不得通过本文的降级项被默认为已承接，后续若需要纳入，应先经 Human Gate 判断是否新增独立平台清单或专项规范。

普通用户或新平台适配者只需要先做一件事：按本文创建当前平台的“平台适配清单”。清单可以先不完整，不要求一次证明完整支持。42 会按清单中已有证据执行只读检查、授权落地、复检，并指出 blocked、degraded 或可补齐项。

LDVH 的安装接入、LDVH落地与检查和环境适配不直接绑定某个 AI 开发平台，而是读取当前平台适配清单中的要求响应矩阵。42 LDVH落地与检查按矩阵执行现场检查、授权落地、复检和缺口分流。

当前已有 Trae Solo 和 Codex 清单。二者均需按真实证据维护承接方法、证据、降级方式和待补齐事项；其他平台不预设完整支持，只保留同构响应矩阵；对应平台用户补齐清单、提供证据并通过 42 LDVH落地与检查前，不得声明完整支持。

平台能力如 Rules、Skill、Agent、Command、MCP、Hook、CI、Code、命令或本地预览只是承接方法候选，不是清单主轴。清单不得因为某个平台有某项能力，就反向改变 LDVH 的要求。

平台适配清单记录平台承接方法、证据来源、降级方式和待补齐事项，不记录某个用户当前环境的实际状态，也不记录清单成熟度状态。实际文件、入口、权限、工具或运行投影是否存在，应由 42 LDVH落地与检查现场检查。

---
## 2. 清单不维护状态

平台适配清单不得声明顶层支持状态、成熟度状态或逐项状态。清单只记录稳定的要求响应内容：平台如何承接、证据来自哪里、无法完整承接时如何降级、还有哪些 open items。

42 LDVH落地与检查读取清单后，在当前报告中派生 done、todo、needs_human_gate、degraded、blocked、out-of-scope、pass 或 pass-with-warnings 等结论。这些结论属于本次过程报告，不得回写为平台清单状态。需要长期保留的稳定事实，应按内容性质分流到平台清单 open_items、Task、Memo、ADR、Pitfall、正式规范、Code 或其他 Git 文件事实源。

没有真实平台上下文、维护者、证据和检查结论的平台，不得声明完整支持；只能保留待填写或待验证的要求响应内容，并由 42 在现场说明缺口和降级路径。

---
## 3. 清单事实源边界

平台适配清单应写入 `docs/specs/04.xx` 正式规范区，作为平台适配规则和待办清单的稳定事实源。

| 内容 | 权威位置 |
|---|---|
| 平台适配清单字段规则 | 本文 |
| Trae Solo 当前适配清单 | `docs/specs/04.07-Trae-Solo适配清单.md` |
| Codex 当前适配清单 | `docs/specs/04.08-Codex适配清单.md` |
| 其他平台待填要求 | 本文或后续对应平台清单 |
| LDVH落地与检查过程结果 | 当前对话或调用结果中的 42 落地与检查报告；默认不创建状态或报告文档 |
| 需要长期保留的检查结论 | Task、Memo、ADR、Pitfall、正式规范、平台清单 open_items 或对应 Git 文件事实源 |
| 实际运行投影入口 | LDVH-AI-ENTRY.md、平台规则、平台 Skill、平台 Agent、Hook、CI、命令或本地预览 |
| LDVH落地与检查执行规则 | `docs/specs/42-ldvh-landing-check-LDVH落地与检查.md` |

清单不得复制平台官方文档全文，不得把聊天判断当作平台事实，不得把尚未验证的能力写成完整支持结论，不得替代 42 LDVH落地与检查的现场判断。

| AI-S2 | 稳定事实 | 00 §2、00 §3、00 §5.1 | 平台如何帮助 AI 回到 Git 文件事实源，而不是依赖聊天记忆、工具缓存或平台临时状态 |

| AI-S9 | 稳定执行 | 00 §4.1 V4 | 平台如何约束 AI 按规范、工作模型、工作流程和受控工具执行，而不是自由发挥 |

## 5. 规范落地要求响应类型

平台适配清单还必须响应 04.01 定义的规范落地要求类型。

| 要求 ID | 规范落地要求 | 来源 | 平台需要回答的问题 |
|---|---|---|---|
| LR-1 | 上位约束承接要求 | 04.01 §4 | 平台如何让 AI 持续承接 LDVH 上位规范、专项规范和约束链路 |
| LR-2 | 入口可见要求 | 04.01 §4、04.02 §5、04.04 §4-§5 | 平台如何让 AI 在进入项目、流程或任务时看见清单、入口、边界和摘要；平台入口在哪里，是否只做薄引用，是否能定位 LDVH-AI-ENTRY.md 或等价入口 |
| LR-3 | 流程复用要求 | 04.01 §4 | 平台如何把重复流程承接为 Skill、Command、工作流程或操作清单 |
| LR-4 | 子 Agent 思考要求 | 04.01 §4 | 平台如何支持独立、专项或并行视角，或无法支持时如何降级 |
| LR-5 | 确定性执行要求 | 04.01 §4 | 平台如何稳定运行 Code、测试、校验、解析、聚合、上下文压缩或受控写入 |
| LR-6 | Human 交互要求 | 04.01 §4 | 平台如何让 Human 看见、确认、授权、验收或受控轻写入 |
| LR-7 | 生命周期触发要求 | 04.01 §4 | 平台如何在规范、配置、入口、事实源、任务、提交或会话事件上触发检查或降级提醒 |

## 6. 要求响应矩阵字段

每个平台适配清单必须以“要求响应矩阵”为主体。每一行至少包含以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| requirement_id | 是 | 采用 AI-S1 至 AI-S15 或 LR-1 至 LR-7 |
| requirement_name | 是 | 要求名称 |
| requirement_source | 是 | 来源规范和章节 |
| platform_method | 是 | 该平台用什么具体方法承接该要求 |
| platform_entities | 是 | 具体机制、文件、命令、规则、Skill、Agent、MCP、Code 或人工流程 |
| refs_evidence | 是 | 平台 refs、官方资料、现有文件或实测证据 |
| degradation | 是 | 无法完整承接时的降级方式和残留风险 |
| check_evidence | 是 | 42 LDVH落地与检查时应检查的证据 |
| open_items | 是 | 后续要补齐的事项 |

平台能力索引可以作为辅助章节存在，但不得替代要求响应矩阵。

## 7. 42 使用清单的规则

42 LDVH落地与检查必须围绕当前平台适配清单中的要求响应矩阵执行和验证，而不是围绕某个平台名称或平台能力清单硬编码执行。

AI 应按以下顺序处理：

1. 确认当前平台；
2. 定位对应平台适配清单；
3. 读取 AI-S1 至 AI-S15 和 LR-1 至 LR-7 的要求响应矩阵；
4. 判断本次LDVH落地与检查依赖哪些要求；
5. 对每项依赖要求读取 platform_method、platform_entities、refs_evidence、degradation、check_evidence 和 open_items；
6. 若关键要求只有降级承接或缺少现场证据，42 只能按降级路径执行并记录残留风险；
7. 若关键要求缺失、证据缺失或 open_items 仍阻断当前目标，不得宣称完整 LDVH落地与检查通过；
8. Trae Solo 和 Codex 清单是当前已存在的要求响应清单，但 42 不得把任一平台名写成唯一执行逻辑。

---
## 8. 42 检查清单的规则

42 LDVH落地与检查必须检查当前平台适配清单中的要求响应矩阵，以及矩阵声明与实际环境、运行投影和本次 42 落地与检查报告之间的一致性。

LDVH落地与检查至少应检查：

1. 当前平台是否有清单；
2. AI-S1 至 AI-S15 和 LR-1 至 LR-7 是否被逐项响应；
3. 每项响应是否说明 platform_method、platform_entities、refs_evidence、degradation、check_evidence 和 open_items；
4. check_evidence 是否存在且可追溯；
5. 降级项是否在 42 落地与检查报告中被正确说明；
6. 清单是否把未经验证的承接方法写成完整支持结论；
7. 清单是否有阻断本次目标的缺失字段、缺失证据或未处理 open_items。

没有完整清单或没有证据的平台，42 只能输出 blocked、degraded 或 out-of-scope，不得输出全链路 pass。

## 10. 规范落地要求

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 平台差异应由平台适配清单中的要求响应矩阵承接，42 不得直接绑定某个平台名称作为唯一执行逻辑 | 本文、00、04.01、04.02、42、Human Gate | 环境适配治理 | 新增、修改或检查平台适配规则时 |
| 入口可见要求 | AI 进入环境确认或 LDVH落地与检查时，应能定位平台适配清单机制、当前平台清单和要求响应矩阵 | 04 父规范、04.02、42、运行入口摘要 | AI 执行入口提示 | 当前平台、清单内容或入口投影变化时 |
| 确定性执行要求 | 后续 Code 应能检查要求响应矩阵字段、证据和 42 引用一致性 | `tools/specs_validate.py` 扩展、正反样例 | 校验实现 | 清单字段、证据或平台清单文件变化时 |

## 11. Human Gate 与检查要求

以下情况必须触发 Human Gate：

1. 将任一平台声明为完整支持或作为完整通过依据；
2. 将未经 42 检查的要求响应矩阵作为完整落地依据；
3. 删除、重命名或改变 Trae Solo、Codex 等既有平台清单职责；
4. 把某个平台能力提升为 LDVH 全局唯一底座；
5. 允许缺少 check_evidence 的平台通过 42；
6. 改变本文字段或 42 依赖要求响应矩阵的规则。

检查平台适配清单时，应确认：

1. 要求响应矩阵覆盖 AI-S1 至 AI-S15 和 LR-1 至 LR-7；
2. 承接方法、证据、降级方式和 open_items 相互匹配；
3. 未把平台官方文档、聊天判断或工具缓存当成最终事实；
4. degradation、check_evidence 和 open_items 没有被隐藏；
5. Trae Solo 和 Codex 是当前已有清单实例，不是写死在 42 中的平台逻辑。

---
## 12. 待补齐事项

1. 平台适配清单要求响应矩阵的结构化 Code 校验待 Trae Solo 清单稳定后补齐；
2. 其他平台是否单独建 `04.xx` 清单文件，待对应平台用户提供真实填写内容后决定；
3. 完整支持结论是否需要更严格的证据格式，待 42 首次检查 Trae Solo 清单后评估。
