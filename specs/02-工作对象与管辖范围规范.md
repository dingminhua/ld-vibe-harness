## 1. 价值判断

本文的价值，是让 AI 能把 Human 当前目标、实际工作对象和工作区级管辖项目配置联系起来，确定每个已识别对象与 LDVH 管辖项目的关系，并把配置缺失、身份歧义、多项目和混合范围如实保留下来。这样可以减少 AI 依赖当前目录、名称相似、对话记忆或单一工具输出猜测项目归属的负担。

本文主要服务：

1. V1 快速定位：定位当前事项实际涉及的工作对象及其管辖项目；
2. V2 充分理解：联系 Human 目标、显式对象定位符、路径、Git 身份和管辖配置；
3. V3 边界识别：区分已管辖、非管辖、无法确认、多管辖项目和混合范围；
4. V5 据实判断：使管辖结论只覆盖当次输入和可回指依据实际支持的对象；
5. V7 清晰沟通：在对象或配置歧义时，清楚交还对象、依据、缺口和影响范围。

本文不把管辖解析变成所有 AI 行动必须经过的全局流程。只有当前事项需要对象专属的 LDVH 规则、事实、行动模板或 Code 能力时，才需要取得能够支持相应对象范围的管辖解析结果。

## 2. 规范依据

本文直接依据 `ldvh-root`，细化 00 中“Helper CLI 围绕当前任务和工作对象提供服务”以及“Helper CLI 的服务范围与具体规则的适用范围分属不同层次”的上位定义。

本文不得改变或重新解释以下边界：

1. AI 是 LDVH 的第一服务对象；
2. LDVH Helper CLI 是基础服务形式；
3. 管辖命中只进入后续对象专属服务和规则判断，不等于任何具体规则已经适用；
4. 未命中具体规则时，AI 的普通求解路径保持自主；
5. 项目中的稳定事实仍必须回到 00 定义的事实源边界；
6. 设计、实现、环境接入和验证状态必须如实区分。

本文作为普通规范，按 `specification-model-foundation` 的形成与治理约束组织；01 不因提供形成与治理约束而被机械写入 `basis`。V3 规范、Code、tests 和现有配置只作为问题与成熟场景参考，不因被参考而自动取得 V4 规则效力。

## 3. 职责边界

本文负责定义：

1. 工作对象、工作对象定位符、工作对象身份依据、管辖项目、管辖范围、工作对象管辖判定和管辖范围解析的含义与差异；
2. `LDVH-GOVERNED-PROJECTS.yaml` 的定位、工作区根位置、配置发现边界和规则权威边界；
3. 管辖项目配置的语义、字段契约授权、有效性和冲突处理；
4. 显式工作对象、当前操作实际涉及对象、`cwd`、路径和 Git 身份各自承担的作用；
5. 逐工作对象的 `governed`、`not_governed` 和 `unknown` 关系，以及单一、多项目、非管辖、未知和混合聚合结果；
6. 哪些结果可以交给后续 LDVH 职责继续判断，哪些对象范围需要补充依据、拆分或交由 Human 决定。

本文不定义：

1. 具体来源规则是否适用、命中后产生什么义务，或多条规则如何处理冲突；
2. Helper CLI 的命令、请求与响应 envelope、错误码、静默输出或受控副作用；
3. 管辖配置的安装向导、写入步骤、备份、恢复、迁移或回滚流程；
4. 路径规范化、符号链接、大小写、worktree、submodule 或 Git 命令的具体算法；
5. Hook、插件、adapter、环境事件和环境 `integrated` 判定；
6. 项目事实对象、行动模板、Code 模块、tests 或 Web 展示；
7. 写入、提交、远端变更或其它行动本身是否获准执行。

## 4. 适用范围

本文适用于以下场景中的工作对象管辖判定和管辖范围解析：

1. AI 或未来 Helper 需要围绕当前事项定位对象专属的规则、事实、行动模板或 Code 能力；
2. Human 目标、显式对象定位符、当前操作实际涉及对象、`cwd`、路径或 Git 身份之间可能不一致；
3. 当前事项涉及一个或多个工作对象、一个或多个管辖项目，或者混合管辖与非管辖对象；
4. 安装、环境入口或 Helper 需要读取和验证工作区级管辖项目配置；
5. 下游职责需要获得对象、管辖项目、来源回指和未解决缺口。

本文不要求一般知识问答、明确不依赖 LDVH 工作对象的普通求解，或者已经能够确认不受本文规则影响的事项先运行固定 Helper、Hook 或 preflight。

## 5. 核心概念

本节中的中英文名称已经 Human 于 2026-07-12 确认，并在双语术语表中登记为 `current`；其含义和边界以本节对应定义为唯一来源。

### 5.1 工作对象（Work Object）

工作对象是当前事项实际读取、修改、比较、验证或作出声明所指向的可识别资源或项目内信息对象。文件、目录、Git 仓库、worktree、Git ref，以及由正式规范定义的项目内对象都可以成为工作对象。

工作对象绑定当次事项。除非后续适用的事实模型和事实源规则另有定义，并按规则写入或更新事实源，它本身不是跨会话稳定事实。

### 5.2 工作对象定位符（Work Object Locator）

工作对象定位符是 Human、当前操作或环境入口提供的结构化定位输入，用于指向一个或多个候选工作对象。路径、带仓库依据的 Git ref、稳定对象引用或等价结构化输入都可以成为工作对象定位符。

自然语言目标可以由 AI 用于识别候选工作对象，但 Code 只消费结构化定位符和可观察依据，不通过猜测自然语言、目录名称或路径相似性自行确定项目归属。

### 5.3 工作对象身份依据（Work Object Identity Evidence）

工作对象身份依据是用于复核工作对象类型、实际身份、边界或与项目关系，并能回指当次观察来源的信息。路径存在性、真实路径关系、Git 仓库根和 Git common-dir 都可以在各自范围内提供身份依据；remote URL、名称相似或对话记忆不能单独形成确定的工作对象管辖判定。

### 5.4 管辖项目（Governed Project）与管辖范围（Governance Scope）

管辖项目是当前选定且有效的 `LDVH-GOVERNED-PROJECTS.yaml` 中登记、并能复核为有效 Git worktree 的项目。每个管辖项目具有稳定项目 ID、项目路径，以及可选的名称、说明和 Git 身份线索。配置文件本身可以位于 Git 之外，但非 Git 目录不能取得管辖项目身份。

管辖范围是该项目登记和可复核项目身份共同界定的对象范围。一个对象进入管辖范围，只表示可以围绕该对象继续提供 LDVH 对象专属服务并判断候选规则；它不表示全部 LDVH 规则生效，不表示行动获准，也不证明能力可用、环境已接入或工作已完成。

Human 当前指令可以指定本次意图对象，但不能只凭当次指令把未登记项目判定为 `governed`，也不能覆盖按当前配置和依据形成的工作对象管辖判定。新增、移除或修改管辖项目必须修改工作区配置并完成相应验证。

### 5.5 工作对象管辖判定（Work Object Governance Determination）与管辖范围解析（Governance Scope Resolution）

工作对象管辖判定表示依据当次定位符、身份依据和当前有效管辖项目配置，对一个已识别工作对象形成的原子结论：

| 机器表示 | 含义 |
|---|---|
| `governed` | 对象身份足以复核，并且唯一命中一个管辖项目 |
| `not_governed` | 已选定有效配置，对象身份足以复核，且没有命中其中任何管辖项目 |
| `unknown` | 配置、对象身份或匹配关系不足、无效、冲突或不唯一，无法支持前两种结论 |

管辖范围解析是根据工作对象定位符、对象身份依据和当前选定管辖配置，形成逐对象管辖判定及聚合结果的过程。结果绑定当次输入、配置内容和观察时间，不是规则源、事实源、行动授权、规则命中结果或验证通过声明。

## 6. 管辖项目配置（Governed Projects Configuration）

### 6.1 文件定位与权威边界

V4 保留 V3 已验证使用的文件名 `LDVH-GOVERNED-PROJECTS.yaml`。该文件位于 Human 选择或安装配置明确指定的工作区根目录：

```text
<workspace_root>/LDVH-GOVERNED-PROJECTS.yaml
```

工作区根目录可以同时管理一个或多个项目，也可以位于所有项目仓库之外。该目录不要求自身是 Git worktree，因此管辖项目配置可以不被项目 Git 跟踪。

管辖项目配置是 Helper/Code 在当前工作区形成工作对象管辖判定的直接配置输入，但它不是项目事实对象，不属于事实模型，不是 00 定义的事实源，也不取得规则权威。项目中的稳定事实、状态、证据和决策仍必须保存在相应项目中由 Git 可追踪文件承载的事实源内。

配置文件只登记项目入口和身份线索，不记录初始化状态、执行状态、环境接入状态、验证结论、Human Gate 完成状态或项目事实内容。

### 6.2 配置发现

1. 已有 Human 选择、安装记录或环境入口明确提供 `workspace_root` 时，只以该根目录下的配置作为本次候选主配置；
2. 没有显式工作区根时，未来 Code 可以从显式工作对象定位符和 `cwd` 向上查找同名文件，但必须返回发现路径和查找依据；
3. 不同工作对象发现不同配置，或同一相关路径链发现多份配置时，不得按最近目录、修改时间或任意固定优先级静默选择；本次配置选择和相关对象关系为 `unknown`；
4. 仓库根目录中的同名文件只有在该目录本身被明确选为工作区根时才是主配置，不能因为距离对象更近而覆盖已选定的外部工作区配置；
5. Git worktree 不在登记项目路径之下时，可以通过配置中的 `git.common_dir` 和当次 Git 身份依据匹配原管辖项目；`git.remote_url` 只能辅助核对，不能单独决定命中。

### 6.3 配置字段与有效性

本文授权 `governed-projects-config-fields` 附件承载配置根字段、项目字段、Git 身份字段和管辖解析结果字段。核心边界如下：

1. 根字段保持 V3 的最小结构：`product_name`、`product_description` 和 `projects`；
2. 每个项目必须有全配置唯一的 `id` 和非空 `path`；`name`、`description` 和 `git` 可选；
3. 相对 `path` 以配置所在工作区根目录为解析基准，绝对路径保持其实际含义；
4. 每个项目路径在配置验证和实际消费时必须能够复核为有效 Git worktree；配置未填写 `git` 时，Code 可以从项目路径读取 Git 身份，但不得通过隐式 `git init` 使错误配置成立；
5. 同一配置中的项目 ID、规范化项目路径和能够确定的 Git common-dir 组合不得造成重复或不唯一命中；
6. `git.common_dir` 可以作为 worktree 身份依据，`git.remote_url` 和 `git.default_branch` 只作辅助说明；
7. 配置不接受附件字段表以外的状态、运行或安装字段；
8. YAML 无法解析、字段不完整、项目不是有效 Git worktree、项目身份重复或同一对象唯一命中多个项目时，不得输出确定的 `governed` 或 `non_governed`。

具体字段类型、条件和机器表示只在授权附件中定义一次；Code 常量、Helper 输出和 tests 必须从该来源契约推导，不得形成第二套字段定义。

## 7. 工作对象解析规则

1. 显式工作对象定位符和当前操作可以确定的实际涉及对象必须保留；二者不一致时记录差异，不得用 `cwd` 静默覆盖；
2. 只有缺少显式定位符和可确定的实际涉及对象时，`cwd` 才作为工作对象回退输入；
3. 相对定位符必须保留其解析基准和来源回指；
4. 多个定位符解析到同一身份时可以形成一个工作对象，但必须保留原始定位符；一个定位符确定性展开为多个对象时必须保留多个工作对象；
5. 路径包含判断必须保持真实路径和路径段边界，不得使用裸字符串前缀；具体跨平台算法由 Code 和 tests 证明；
6. worktree 路径和 Git common-dir 分别提供路径位置和仓库身份依据，层次不同不构成冲突；
7. 尚未创建的文件只要预期路径、解析基准和已存在的项目边界可以复核，也可以作为候选工作对象；不存在本身不决定工作对象管辖判定。

## 8. 解析结果与消费边界

### 8.1 聚合结果

逐对象管辖判定可以确定性聚合为：

| 聚合状态 | 成立条件 |
|---|---|
| `governed_single` | 全部已解析对象均为 `governed`，并且唯一命中同一个管辖项目 |
| `multiple_governed_projects` | 全部已解析对象均为 `governed`，并且命中两个或以上管辖项目 |
| `non_governed` | 已选定有效配置，全部已解析对象均为 `not_governed` |
| `scope_unknown` | 没有可用配置、配置选择冲突、没有可用工作对象，或者全部对象均为 `unknown` |
| `mixed_scope` | 已解析对象中出现两种或以上工作对象管辖判定 |

聚合状态只描述输入对象集合，不得扩张到当次没有提供或无法从当前操作确定的其它对象。多个对象分别命中不同管辖项目属于 `multiple_governed_projects`；同一对象命中多个不等价项目属于 `unknown`。

### 8.2 最小结果信息

管辖范围解析结果至少保留：选定工作区根、配置路径与配置读取状态、原始定位符、解析基准、逐对象身份依据、逐对象管辖判定、命中项目及匹配方式、聚合状态、来源回指和未解决缺口。

具体响应 envelope、错误码、摘要方式和自动展开策略由后续 Helper 服务契约定义。Helper 可以压缩展示，但不得丢失返回完整对象分组、来源依据和缺口所需的回指。

### 8.3 消费边界

1. `governed_single` 可以把逐对象上下文交给后续职责定位候选规则、项目事实、行动模板和能力；
2. `multiple_governed_projects` 必须保留每个对象与项目的映射，是否组合行动由后续来源规则判断；
3. `non_governed` 只证明本次输入对象未命中选定配置，不要求 AI 停止普通求解；
4. `scope_unknown` 应补充配置、工作区根、定位符或身份依据，不得被当作已管辖或非管辖；
5. `mixed_scope` 必须保持对象分组，不得用一个总结果覆盖全部对象；
6. 任何结果都不得单独推出具体规则命中、行动授权、Human Gate 完成、能力可用、环境已接入或工作完成。

## 9. 代表性判定场景

以下场景用于约束语义，不固定实现算法：

| 场景 | 预期结果 |
|---|---|
| 明确工作区根且其中配置有效 | 使用该配置并返回其绝对路径和来源 |
| 工作区根位于多个项目仓库之外 | 配置仍可作为本机工作区输入，不要求工作区根进入 Git |
| 外部工作区配置与项目仓库内同名文件同时存在 | 已明确外部工作区根时不得由仓库内文件覆盖；未明确时报告配置冲突 |
| 显式对象与 `cwd` 指向不同项目 | 保留显式对象；`cwd` 只作解析上下文 |
| 没有显式对象，`cwd` 唯一命中配置项目 | 可以通过 `cwd` 回退形成工作对象 |
| worktree 路径不同但 Git common-dir 唯一匹配 | 对象可以命中对应管辖项目 |
| 配置登记的项目路径不是有效 Git worktree | 配置验证失败，相关工作对象管辖判定为 `unknown`；不得隐式执行 `git init` |
| 只有 remote URL 或项目名称相似 | 依据不足，相关对象为 `unknown` |
| 有效配置存在且全部输入对象均未命中 | 逐对象为 `not_governed`，聚合结果为 `non_governed` |
| 配置缺失或 YAML 无法解析 | `scope_unknown`，不得通过“没有找到”推出非管辖 |
| 多个对象分别命中不同管辖项目 | `multiple_governed_projects`，保持对象与项目映射 |
| 管辖与非管辖对象同时存在 | `mixed_scope`，保持分组 |
| Human 只说“这次把未登记项目也当作管辖项目” | 不据此将未登记项目判定为 `governed`；需要修改配置并完成验证 |

## 11. Human Gate

以下事项必须进入 Human Gate：

1. 选择或改变主工作区根和 `LDVH-GOVERNED-PROJECTS.yaml` 的实际位置；
2. 新增、移除、重命名或修改管辖项目登记，或者接受项目 ID、路径、Git common-dir 的歧义；
3. 发现多份相互竞争的配置，需要删除、迁移、合并或明确保留其中一份；
4. 多个同样合理的意图对象会导致不同外部影响或长期事实变化，现有依据不能替 Human 选择。

Human 已在当前指令中清楚给出相应决定时，不重复索取同一决定；但该回应不能替代配置写入、对象身份核对、配置验证、Code 验证或环境接入证明。

## 12. Stop Conditions

出现以下任一情况时，必须暂停依赖相应管辖结论的最小行动、对象或声明范围：

1. 主工作区根或配置路径无法确认，且当前判断需要管辖配置；
2. 配置缺失、不可读、YAML 无效、字段不成立、登记项目不是有效 Git worktree，或存在相互竞争的配置，却准备输出确定的工作对象管辖判定；
3. 工作对象身份冲突、一个对象唯一命中多个项目，或者 remote URL、名称相似或对话记忆正在被单独用于决定管辖；
4. 多项目或混合范围被折叠，已经无法确认每项依据或结论属于哪个对象；
5. Human 当次指令正在被用于绕过配置变更，把未登记项目判定为 `governed`，或者覆盖按当前配置和依据形成的工作对象管辖判定；
6. 管辖配置正在被表述为项目事实对象、事实源、规则源、行动授权或完成证明；
7. 尚未实现、接入或验证的 resolver、Helper、Code、tests 或环境能力正在被声明为已可用或已自动保障。

配置缺失、`scope_unknown`、`multiple_governed_projects` 或 `mixed_scope` 本身不造成全局停止。暂停期间可以继续只读核对、补充工作对象定位符、检查配置和身份依据、拆分对象、准备 Human Gate，并继续明确不依赖受影响管辖结论的普通工作。

受影响范围只能在与具体触发原因对应的条件满足后恢复：工作区根和配置路径已经确认，配置错误或冲突已经修正，对象身份或项目匹配歧义已经消除，对象已经拆分，配置变更已经完成并验证，或者声明已经缩小到现有依据实际支持的范围。恢复不得自动扩张到其它对象或行动。
