# 工具展示规范

> 创建日期：2026-05-28
> 定位：PM Kit 工具展示层基础规范，定义工具的定位、展示原则、受控写入、人类确认入口和协作边界
> 适用范围：所有接入 PM Kit 的项目
> 上位依据：`specs-v2/00-PMKit理念与纲要.md`
> 约束对象：工具展示行为和受控写入行为

---

## 一、本文解决的问题

本文解决的问题是：工具在 PM Kit 中承担什么角色、展示什么、能写入什么、如何与事实源交互、如何与 AI 和程序辅助协作，以及工具不得做什么。

工具是执行型工作台，核心交互模式为"看见 → 操作 → 协同"。工具不是事实源，是各产品项目 `docs/` 和 `pm-kit-base/` 的聚合视图和受控编辑入口。

---

## 二、与 00 总纲的关系

00 §二 定义了工具的职责：读取事实源、聚合事实源、校验事实源、提供受控写入入口，降低人和 AI 维护结构化文件的成本。

00 §五 定义了协作闭环：工具辅助解析、校验、聚合和受控写入；PM Web Tools 展示状态、待确认事项和检查结果；人基于事实源追踪、确认、验收或调整方向。

00 §四 定义了事实源原则：工具缓存、数据库派生视图都不能成为最终事实源。

本文将上述要求转化为工具展示层的行为约束：工具可以展示、校验、聚合和受控写入，但不能成为最终事实源。

---

## 三、工具定位与职责边界

> 事实源边界声明：本文权威领域为工具展示层的行为约束和协作边界。工具的事实源语义由 10 定义，对象语义由 14 定义，AI 协作语义由 11 定义，程序辅助语义由 12 定义。本文不重新定义上述领域的规则，只定义工具展示层如何依据这些规则行动。

### 3.1 定位

工具是执行型工作台，核心交互模式为"看见 → 操作 → 协同"：

1. 看见：从各项目事实源聚合呈现产品状态；
2. 操作：通过受控编辑入口修改项目事实源；
3. 协同：为 AI 对话层提供结构化上下文。

### 3.2 工具可以承担的角色

1. 读取 Git 文件事实源；
2. 解析结构化对象；
3. 校验字段、关系和状态；
4. 聚合项目上下文；
5. 展示状态和缺口；
6. 提示 Human Gate；
7. 提供受控写入入口；
8. 生成审计或检查结果。

### 3.3 工具不得承担的角色

1. 成为最终事实源；
2. 绕过 Git 文件写入；
3. 绕过 Human Gate；
4. 将缓存或数据库作为权威状态；
5. 将 PM Kit Tools 自身项目误作为被管理项目事实源。

---

## 四、工具与事实源的关系

### 4.1 核心约束

1. 工具不是事实源。事实源在各项目的 `docs/`、`pm-kit-base/` 和 `.trae/rules/` 中。
2. 工具不生产内容，不存储内容。所有数据来自项目内的事实源。
3. 工具不制造第二套事实。展示的内容必须与事实源一致，不得缓存后漂移。
4. `pm-kit-base/` 与 `docs/` 是同级事实源。工具读取和展示时，两类事实源同等重要，不得偏废。

### 4.2 展示与事实源一致性

工具展示的内容必须可追溯到 Git 文件事实源。当工具展示与事实源不一致时，以 Git 文件事实源为准。

工具不得维护与 Git 文件不一致的权威状态。

---

## 五、展示原则与派生视图边界

### 5.1 展示范围

工具可以展示：

1. 对象状态；
2. 对象关系；
3. 初始化缺口；
4. 审计结果；
5. 检查清单；
6. 待确认事项；
7. 动态上下文。

### 5.2 派生视图边界

派生视图是从 Git 文件事实源读取、解析、聚合后生成的展示结果。

派生视图不得维护：

1. 与 Git 文件不一致的权威状态；
2. 无法追溯来源的事实；
3. 只存在于 UI 中的关闭证据；
4. 只存在于缓存中的决策或规则；
5. 绕过被管理项目事实源的项目记录。

### 5.3 缓存和数据库边界

工具可以使用缓存或数据库提高性能，但缓存和数据库只能是派生层。

缓存或数据库中的内容必须满足：

1. 可由 Git 文件事实源重新生成，或明确标记为运行时临时状态；
2. 不作为任务状态、证据、决策、规则或审计的唯一来源；
3. 失效、删除或重建后不影响事实源完整性；
4. 不保存敏感凭据或不应持久化的信息；
5. 不改变被管理项目事实归属。

### 5.4 Context 边界

Context 作为工具派生视图时，通常不作为独立事实源。Context 中出现的新信息，如果需要长期保留，应重新判断其对象类型和事实源载体。

AI 不得因为某项内容进入本次上下文，就认为它已经进入项目事实源。

---

## 六、人类确认入口

### 6.1 Human Gate 在工具中的体现

工具必须在以下情况暂停并等待用户确认：

1. 工具写入或覆盖 Git 文件事实源；
2. 工具改变事实源归属；
3. 工具将派生数据升级为权威事实；
4. 工具绕过规则、决策或证据门禁；
5. 工具迁移旧结构化事实源；
6. 修改 specs 规范文档。

### 6.2 确认流程原则

1. 工具不得绕过 Human Gate 自动完成高影响写入；
2. 工具应明确提示用户需要确认的操作和影响范围；
3. 确认结果应可追溯。

### 6.3 确认记录回写

工具执行人类确认后的写入，必须回到被管理项目自身的 Git 文件事实源，不得只停留在工具数据库或 UI 状态。

---

## 七、受控写入入口

### 7.1 写入原则

1. 工具的任何写入操作，实际写入目标项目的事实源文件；
2. 写入后必须触发该项目的 Change 记录（写入 `pm-kit-base/changes/`）；
3. 工具不得维护自己的数据存储。

### 7.2 写入前检查

受控写入至少应满足：

1. 写入前明确目标事实源；
2. 写入前判断是否已有权威事实；
3. 写入前判断是否触发 Human Gate。

### 7.3 写入后验证

1. 写入后可通过 Git 追溯；
2. 写入后工具视图应从事实源重新读取或刷新；
3. 写入不得只停留在工具数据库或 UI 状态。

### 7.4 写入与 Human Gate

1. 高影响写入必须经过 Human Gate；
2. 写入目标必须是被管理项目自身的 Git 文件事实源；
3. 禁止通过工具直接修改 specs 规范文档。

---

## 八、工具与 AI 协作

### 8.1 协作原则

1. 工具不直接调用 AI、Skill 或 Agent；
2. 工具只提供结构化上下文、受控编辑入口、Human Gate 提示和可投递的执行请求；
3. AI 能力由 Trae 对话层提供，工具只提供结构化数据和受控编辑入口。

### 8.2 工具如何辅助 AI 展示状态和缺口

1. 工具可以聚合项目状态供 AI 读取；
2. 工具可以展示初始化缺口、审计发现和待确认事项；
3. 工具可以提供结构化上下文给 AI 对话层。

### 8.3 Rule / Skill / Agent 用法

1. Rule：L0/L1/L2 约束，工具不得违反任何层级规则；
2. Skill：工具提供结构化上下文和执行请求，由 Trae 对话层或人类确认后触发；
3. Agent：工具提供结构化上下文和任务边界，由 Trae 对话层或人类确认后调度。

---

## 九、工具与程序辅助

### 9.1 工具如何消费程序输出

1. 工具后端可调用程序辅助获取聚合数据；
2. 程序辅助的解析、校验和聚合结果可作为工具展示的数据来源；
3. 程序辅助的受控写入能力可被工具调用。

### 9.2 边界

1. 工具和程序辅助各自遵守自身载体规范；
2. 工具不得因调用程序辅助而绕过事实源原则和 Human Gate；
3. 程序辅助的缓存和数据库边界同样适用于工具。

---

## 十、工具禁止事项

1. 不得替代事实源：工具展示不是事实源，不得将工具视图当作权威事实源；
2. 不得绕过 Human Gate：工具不得自动完成需要人类确认的操作；
3. 不得改变项目归属：工具写入必须回到被管理项目自身，不得将 PM Kit Tools 自身项目作为写入目标；
4. 不得维护第二事实源：工具不得维护与 Git 文件不一致的权威状态；
5. 缓存和数据库只能作为派生层：不得将缓存或数据库作为任务状态、证据、决策、规则或审计的唯一来源；
6. 不得直接调用 AI：AI 能力由 Trae 对话层提供，工具不得直接调用 AI、Skill 或 Agent。

---

## 十一、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 工具写入或覆盖 Git 文件事实源；
2. 工具改变事实源归属；
3. 工具将派生数据升级为权威事实；
4. 工具绕过规则、决策或证据门禁；
5. 工具迁移旧结构化事实源；
6. 工具引入持久化数据库作为派生层。

检查至少包括：

| 检查项 | 标准 |
|---|---|
| 来源可追溯 | 视图数据可追溯到 Git 文件 |
| 写入可追溯 | 工具写入落到 Git 文件 |
| 缓存非权威 | 缓存可重建且非唯一事实源 |
| 项目归属 | 工具写入被管理项目自身 |
| Gate 判断 | 高影响写入已评估 Human Gate |

---

## 十二、不进入本文的内容

以下内容不进入本文：

1. PM Web Tools 页面设计、UI 交互和前端实现；
2. API 契约和数据库 schema；
3. 具体缓存策略和部署方式；
4. 功能域模型和功能域边界（属于工具产品需求，见 docs）；
5. 程序辅助的具体模块设计和代码实现（见 12）；
6. AI 协作语义和 Human Gate 总清单（见 11）；
7. 管理对象的完整实践细则（见 20-49）；
8. 工具读取优先级和具体读取策略（属于工具实现细节）。
