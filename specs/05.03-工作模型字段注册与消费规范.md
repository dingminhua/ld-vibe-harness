## 1. 本文解决的问题

本文维护 LDVH 工作模型字段注册表和消费语义。注册表登记字段名、重要嵌套字段路径、字段含义、内容格式、值形态、引用类型、枚举归属、schema 归属、Code 可校验维度、Web 派生视图语义、字段生命周期和替代关系。

本文不定义具体工作模型是否采用某字段、字段是否必填、状态条件必填、状态机、关闭条件或对象内完整 schema；这些规则由 20-39 具体工作模型规范负责。本文也不定义字段内容格式本身；格式类型由 `specs/05.02-工作模型字段内容与格式规范.md` 负责。公共字段语义和字段治理规则由 `specs/05.01-工作模型字段定义与语义规范.md` 负责。

## 2. 与 05、05.01、05.02、07、08 和 20-39 的关系

`specs/05-工作模型基础规范.md` 是工作模型总纲。`specs/05.01-工作模型字段定义与语义规范.md` 定义字段层语义和治理规则；`specs/05.02-工作模型字段内容与格式规范.md` 定义字段内容写法；本文把字段语义和内容格式登记为 AI、Code 和 Web 可共同消费的注册表。

07 和 08 定义 Code/Web 实现如何消费字段注册语义；本文只定义可消费元数据和消费边界，不规定 Python 模块名、CLI 输出格式、React 组件名、页面布局、API 路由或测试文件组织。

## 3. 字段注册表

本节是 AI、Code 和 Web 共同消费字段语义的权威注册入口。注册表服务 `specs/00-LD-Vibe-Harness理念与纲要.md` 的 AI 第一原则：让 AI 快速定位字段语义、减少猜测、避免跨对象同义字段漂移，并让 Code/Web 从同一字段契约派生校验和呈现。

`id`、`type`、`title`、`status`、`created`、`updated` 等基础字段也应进入注册表，登记其通用语义和消费元数据；这些基础字段在具体工作模型中的取值规则、枚举值、必填性和状态条件，以 20-39 具体工作模型规范为准。05.03 只说明“字段若被具体工作模型采用，应按什么语义、内容格式和消费元数据理解”。

### 3.1 注册边界

字段注册表负责：

1. 登记字段名或重要嵌套字段路径；
2. 登记字段回答的问题和不得承载的内容；
3. 登记字段内容格式和稳定消费枚举；
4. 登记 Code 可机械消费的值形态、引用种类、枚举归属、schema 归属和可校验维度；
5. 登记 Web 可消费的派生视图语义，不规定组件名、页面布局或交互方案；
6. 登记废弃字段、别名字段、替代字段和迁移指向；
7. 暴露跨对象重复字段风险：同义字段应复用已有注册项，或在本文登记别名、废弃、替代或差异关系。

字段注册表不负责：

1. 具体工作模型是否采用该字段；
2. 具体工作模型字段是否必填；
3. 状态条件必填；
4. 状态机和合法状态流转；
5. 关闭条件；
6. 对象内完整 schema 和跨字段约束。

以上内容必须回到 20-39 具体工作模型规范。若字段注册与具体工作模型规范冲突，以具体工作模型规范的字段采用、必填性、状态条件和关闭条件为准；以本文的字段语义、内容格式和消费元数据为准。

Code / Web 消费元数据只表达字段契约如何被机器检查和人机界面理解，不规定具体实现文件、函数名、组件名、页面布局或交互方案。具体实现结构由 `specs/07-Code确定性执行实现规范.md`、`specs/08-Web信息同步实现规范.md` 和对应实现负责。

### 3.2 字段路径写法

字段路径使用点号表示重要嵌套字段：

```text
orchestration.execution_items.status
orchestration.plan_review.review_policy.required_perspectives
orchestration.plan_review.review_items.agent_name
orchestration.plan_review.controller_resolution.summary
orchestration.result_review.controller_self_check.attestation.statement
```

数组元素不写 `[]`；注册项默认适用于该数组内每个对象。字段路径只用于登记内容/消费规则，不代表该路径在所有对象中存在。

### 3.3 注册枚举

注册表字段应使用稳定枚举，避免把自然语言描述当成机器契约。

| 注册列 | 允许值或写法 | 含义 |
|---|---|---|
| `field_path` | 字段名或点号路径 | 字段或重要嵌套字段路径 |
| `scope` | `common` / `workcase` / 具体工作模型名 | 注册项适用范围 |
| `format_kind` | `narrative` / `checklist` / `evidence` / `decision` / `reference` / `log` / `structured` | 05.02 定义的内容格式类型 |
| `value_shape` | `string` / `markdown` / `checklist_markdown` / `evidence_markdown` / `boolean` / `date` / `datetime` / `object` / `list_object` / `list_string` / `list_mixed` | Code 可判断的值形态 |
| `ref_kind` | `none` / `object_ref` / `workarea_ref` / `workcase_ref` / `commit_ref` / `doc_path` / `mixed_ref` / `local_id` / `enum` / `url_ref` | 引用或标识类型 |
| `enum_owner` | `none` / `05.01` / `05.02` / `05.03` / 具体工作模型编号 | 枚举值归属；本文不拥有对象状态枚举 |
| `schema_owner` | `none` / `05.01` / `05.02` / `05.03` / 20-39 具体工作模型编号 | 对象内结构约束归属 |
| `code_check_kind` | `none` / `format` / `ref` / `enum` / `structured` / `deprecated` / `owner_state` | Code 可消费的校验维度；`owner_state` 表示状态条件由具体对象规范决定 |
| `web_render_kind` | `summary` / `checklist` / `evidence` / `object_ref` / `doc_link` / `commit_ref` / `mixed_ref` / `structured_area` / `status_signal` / `enum_signal` / `metadata` / `deprecated` / `url_ref` | Web 派生视图语义 |
| `status` | `active` / `deprecated` / `removed` / `alias` | 注册项生命周期状态 |
| `replacement` | 字段路径、对象名或 `none` | 废弃、别名或替代关系 |

`value_shape` 只登记字段在有值时的稳定值形态，不表达字段必填性、条件必填或是否允许为空/null；这些对象内约束由 `schema_owner` 指向的具体工作模型规范定义。

### 3.6 已清退工作对象边界

旧 `TaskPlan`、`Task` 和 `SubTask` 不再是当前 active 工作模型，也不再作为 Code 或 Web 的兼容读取、校验、迁移、直达展示或测试夹具维护对象。历史事实由 Git 历史、相关 Spark 或已迁移后的 WorkCase 承载；当前事实源、Code 入口、Web 入口和注册表只面向 active 工作模型。

清退后的边界要求：

1. `ldvh-base/taskplans/`、`ldvh-base/tasks/` 和 `ldvh-base/subtasks/` 不得作为当前事实源目录存在；
2. `taskplan`、`task`、`subtask` 不得作为 CLI、Validator、Web API 或 Web 路由的对象类型；
3. `taskplans`、`related_taskplans`、`related_tasks`、`source_tasks`、`tasks`、`completion_evidence`、`deliverables`、`affected_docs` 等旧字段不得作为 active 对象字段扩展；
4. 需要表达执行拆分时使用 `WorkCase.orchestration.execution_items`；需要表达关联关系时使用当前对象字段或文档/Git 引用；
5. 如果在历史文档、commit message 或研究材料中出现旧名称，Web 和 Code 不得把它们自动提升为当前对象入口。

## 4. Web 语义化渲染消费规则

Web 应消费 §3 注册表中的 `format_kind`、`ref_kind`、`web_render_kind`、`status` 和 `replacement`，从同一字段契约派生 Human-facing 视图。本文只定义字段到派生视图语义的契约，不规定具体组件名称、文件结构、页面布局或交互实现。Web 渲染是派生视图，不得回写事实源。

### 4.1 `web_render_kind` 枚举

| `web_render_kind` | 派生视图语义 | 必须保持的契约 |
|---|---|---|
| `summary` | 摘要或正文区域 | 按 Markdown 字段内容展示；不得把摘要派生结果回写为事实 |
| `checklist` | 检查清单区域 | 保留每项检查状态和完成比例语义 |
| `evidence` | 证据区域 | 突出验证命令、路径、结果、结论、关闭判断和 Human Gate 结果 |
| `object_ref` | 对象引用 | 仅对可识别对象 ID 执行对象跳转；不可识别引用按普通引用显示 |
| `doc_link` | 文档或路径引用 | 按文件路径、规范路径或 URL 引用显示 |
| `commit_ref` | Git 提交引用 | 作为 Git commit 引用显示，不得误当工作对象 ID |
| `mixed_ref` | 混合引用列表或混合引用值 | 分类型识别对象 ID、路径、URL、命令和说明性文本；不可识别项按普通引用显示，不得强行跳转 |
| `structured_area` | 结构化区域 | 结构化对象或列表不得裸渲染为普通 Markdown 文本 |
| `status_signal` | 状态信号 | 用于对象状态、优先级和内部执行状态等带进展或风险含义的稳定枚举展示 |
| `enum_signal` | 普通枚举信号 | 用于编排模式、类型等不直接表示进展或风险的稳定枚举展示 |
| `metadata` | 元信息 | 用于时间、布尔、局部 ID 等不构成正文的字段 |
| `deprecated` | 废弃字段提示 | 读取历史字段时应提示替代关系，不应鼓励新写入 |

`mixed_ref` 字段可以同时包含路径、对象 ID、URL、命令、Git 变更引用或说明性文本。Code 只应对可判定为项目内文件或目录路径的项做存在性检查；不可判定为路径的项应保留为普通混合引用，由 Web 按类型识别或降级展示。

### 4.2 Web 消费顺序

Web 视图应优先消费 `structured_area`、`checklist`、`evidence`、`object_ref`、`commit_ref`、`doc_link` 和 `mixed_ref` 等强语义字段，再消费 `summary`、`status_signal`、`enum_signal` 和 `metadata`。当同一字段同时具备引用和叙述含义时，以 `ref_kind` 决定是否可跳转，以 `web_render_kind` 决定展示语义。

`related_workcases` 必须作为 WorkCase 对象引用消费；对象相关提交必须由 Git 历史、文件路径、对象 ID 和提交正文自然文本派生，不得依赖对象字段手写维护；`orchestration`、`orchestration.execution_items`、`orchestration.plan_review`、`orchestration.result_review` 和 `revision_history` 必须作为结构化区域消费；`success_criteria`、`verification_evidence`、`closure_evidence`、`plan_confirmed_at`、`closure_requested_at` 和 `closed_at` 必须作为方案确认、结果复核和关闭确认的核心信号消费。

### 4.3 Web 边界约束

1. Web 展示的事实以 Git 文件事实源为准；
2. 摘要、折叠、渐进展开只能是展示层派生结果，不得回写到 YAML；
3. YAML 原文折叠区作为事实完整性兜底展示；
4. Web 不得在 UI 中另建权威事实；
5. Web 对 `status=deprecated`、`status=removed` 或 `status=alias` 的旧对象和旧字段只能作为历史兼容视图消费；除受控迁移或历史详情直达外，不得进入主导航、Dashboard、默认关注队列或新建入口；
6. 如需长期保存 Web 生成的总结，应创建 Spark；除 `specs/08-Web信息同步实现规范.md` §8.2 明确白名单外，Web 不得更新其他对象字段。

## 5. Code 校验消费规则

Code 应消费 §3 注册表中的 `field_path`、`format_kind`、`value_shape`、`ref_kind`、`enum_owner`、`schema_owner`、`code_check_kind`、`status` 和 `replacement`。本文只定义可机械消费维度和字段契约，具体校验逻辑、文件位置、命令名称、测试组织和错误输出格式由 Code 实现规范与对应实现负责。

### 5.1 `code_check_kind` 枚举

| `code_check_kind` | 可机械消费维度 | 边界 |
|---|---|---|
| `none` | 不从本文派生校验 | 仍可由具体对象规范或实现自行校验 |
| `format` | 字段内容格式、YAML 块标量、Markdown/checklist/evidence 基础形态 | 不决定字段是否必填 |
| `ref` | 引用类型、引用前缀、路径或 commit 形态 | 引用存在性是否强制由具体对象规范或 Code 实现决定 |
| `enum` | 枚举值集合 | 枚举值以 `enum_owner` 指向的规范为准 |
| `structured` | object / list[object] 形态和已注册嵌套路径 | 不替代 `schema_owner` 定义的完整对象内 schema |
| `deprecated` | 废弃字段、别名、替代字段、迁移提示 | 不自动执行迁移，迁移策略由工作对象或流程承接 |
| `owner_state` | 状态条件必填、关闭条件、对象内跨字段约束 | 05.03 只登记字段可被消费；具体诊断级别归属对象规范和 Code 实现 |

### 5.2 Code 消费边界

1. Code 不应从 05.03 推导具体工作模型采用字段、必填性、状态机、关闭条件或对象内完整 schema；
2. Code 应使用 `schema_owner` 和 `enum_owner` 回到对应 20-39 具体工作模型规范读取完整约束；
3. Code 应将 `status=deprecated`、`status=removed` 和 `replacement` 作为兼容读取、迁移提示和新写入拦截的输入；
4. Code 对 `removed work model` 和 `deprecated alias` 的新建写入必须拦截；历史对象只保留读取、校验、迁移提示、受控清理和兼容展示能力；
5. Code 应优先让 Web 复用同一字段注册结果，避免 Code/Web 分别维护字段分类；
6. 当前 Markdown 注册表是权威规范表达；后续可派生或迁移为机器可读 YAML/JSON registry，但不得产生第二事实源。

## 6. 工作对象接口公共原语

工作对象接口用于把工作模型契约转换为 AI、Rules、Skill、Code 和 Web 可共同消费的结构化边界。接口原语不替代工作模型规范，不形成第二套字段事实源，只描述对象在不同机制中的可消费面。

工作对象接口至少包括以下层次：

| 接口层次 | 说明 | 权威来源 |
|---|---|---|
| 对象接口摘要 | 说明对象 ID、事实源目录、文件命名、默认状态、终态、主要读取场景和主要写入场景 | 具体工作模型主规范与字段契约 |
| Raw Object 接口 | 说明 YAML 或其他事实实例载体的字段、类型、必填性、条件必填、枚举、列表字段和示例 | 字段契约或对应权威位置 |
| 引用关系接口 | 说明本对象可引用哪些对象、哪些对象可引用本对象、引用字段、引用有效性和缺失引用处理方式 | 具体工作模型主规范与字段契约 |
| 消费者接口 | 说明 AI、Rules、Skill、Code、Web 分别消费哪些字段、在哪些场景消费、消费失败如何报告缺口 | 字段契约或对应权威位置 |

工作对象接口应遵守以下规则：

1. 字段契约是结构化字段契约和机器消费接口的权威位置；
2. Code、Web 或 Skill 不得在字段契约外自行定义字段名、字段类型、状态枚举或状态流转矩阵；
3. 字段契约变更必须同步检查消费该契约的 Code 实现、测试、Rules、Skill 和 Web 入口；
4. 暂未被 Code 或 Web 消费的接口层次可以标记为待补齐，但不得把未实现能力表述为已落地；
5. 接口消费关系应说明消费方式、消费字段、验证命令或替代检查方式、同步触发条件。

### 6.1 Code 消费工作对象接口原则

Code 消费工作对象接口时，应以字段契约为输入契约，以 Git 文件事实源为唯一权威输入输出边界。Code 的对象能力至少区分以下接口：

| 接口 | 说明 |
|---|---|
| 读取接口 | 从事实源读取对象并解析为结构化数据，不改变事实源 |
| 校验接口 | 依据字段契约校验字段完整性、状态合法性、条件必填、引用关系和文件命名 |
| 状态流转接口 | 依据字段契约的状态枚举和流转矩阵执行受控状态变更，并在写入前检查 Human Gate |
| 创建接口 | 依据字段契约生成新对象实例，检查编号、命名、必填字段和初始状态 |
| 删除接口 | 依据对象规范判断是否允许删除，并保留 Git 可追溯性 |
| 缺口报告接口 | 当字段契约、Code 实现和测试不同步时，输出结构化缺口，不得静默通过 |

Code 消费规则：

1. 字段契约已定义但 Code 未覆盖的字段或状态，应报告能力缺口或校验缺口；
2. Code 实现新增或修改对象接口能力时，必须同步更新对应测试；
3. Code 输出为派生结果，不替代事实源，也不替代 Human Gate；
4. 受控写入必须执行写入前校验，写入后重新校验目标事实源；
5. 字段契约变更后，如 Code 实现和测试未同步完成，相关 Code 输出不得作为最终验收依据。

## 8. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除或重命名字段注册表子文档；
2. 改变注册列或稳定枚举；
3. 改变字段到内容格式、Code 校验维度或 Web 渲染语义的映射；
4. 将本文注册表解释为具体工作模型完整 schema；
5. 将 Code/Web 具体实现规则写入本文，造成 07、08 或实现文档的权威边界漂移。

检查至少确认：注册表列完整；字段路径不重复；枚举值稳定；owner 归属与 active 工作模型编号一致；废弃/别名/替代关系清晰；本文没有定义具体对象必填性、状态机或关闭条件。
