# 事实源边界与承载规范

> 创建日期：2026-05-29
> 定位：LD Vibe Harness 最终事实源、单一事实源、事实承载和回写边界规范
> 适用范围：LD Vibe Harness 项目及所有接入 LD Vibe Harness 的管辖项目
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs/01-目录说明.md`、`specs/02-术语规范.md`、`specs/03-文档规范.md`

---

---
## 1. 本文解决的问题

本文解决 LD Vibe Harness 中哪些内容可以成为最终事实源、同一事实只能由哪里权威承载、聊天、工具缓存、数据库派生视图和 UI 状态为什么不能替代 Git 文件事实源，以及事实应如何选择 Markdown、YAML 或其他介质承载的问题。

LD Vibe Harness 的核心目标之一，是让 AI 不依赖聊天记忆持续推进项目，而是围绕 Git 可追踪文件读取、执行、检查和回写。本文为这一目标定义事实源边界和承载原则。

各目录在事实源体系中的性质声明，由 `specs/01-目录说明.md` 依据本文原则承载。

---

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 的价值实现标准和四类构成要素，并要求 AI 的执行结果能留下可追溯证据、稳定事实能按边界回写到 Git 文件事实源。本文承接该要求，专门定义最终事实源、非事实源边界、单一事实源原则、事实承载方式和工具输出回写规则。

本文是 LD Vibe Harness 事实源权威性判断原则的权威位置。00 只保留事实源闭环的顶层价值要求；01 依据本文原则声明各目录在事实源体系中的性质，但不定义判断原则本身。

---

## 3. 事实源边界职责

本文的权威领域是最终事实源定义、单一事实源原则、非事实源边界、事实承载介质选择、工具输出回写和事实归属判断。

---

## 4. 最终事实源原则

LD Vibe Harness 的最终事实源必须是 Git 可追踪文件。一个事实只有写入其对应权威文件位置后，才成为可追溯、可审查、可被 AI 稳定读取和可被工具解析的 LD Vibe Harness 事实。

基础原则：

1. 事实必须能被 AI 读取；
2. 事实必须能被人审查；
3. 事实必须能被工具解析或聚合；
4. 事实必须能通过 Git 追溯变化；
5. 同一事实只能有一个权威位置，原则上不能出现多个事实源。

聊天记录、临时 UI 状态、工具缓存、数据库派生视图、运行时索引、命令输出和模型临时上下文都不能成为 LD Vibe Harness 的最终事实源。

---

## 5. 单一事实源规则

同一事实只能有一个权威定义位置。其他文件、工具页面、缓存、报告或实践说明需要使用该事实时，只能引用或聚合权威位置，不得复制并维护一份独立事实。

典型规则：

1. specs/ 定义规范，不承载具体事实实例；
2. ldvh-base/承载结构化对象实例，不承载规范正文；
3. docs/ 承载管辖项目资料和报告，不替代 ldvh-base/中的动态对象状态；
4. specs/refs/ 承载外部资料，不直接成为 LD Vibe Harness 强制规则；
5. web/ 和 tools/ 可以实现工具能力，但不能独立维护与 Git 文件事实源冲突的状态。

当两个位置出现同一事实的不同表述时，应依据本文和对应对象规范判断权威位置，非权威位置应改为引用、摘要或删除重复事实。

## 6. 事实承载介质选择

YAML、Markdown、Python、JavaScript 等文件格式和编程语言是 LD Vibe Harness 使用的行业标准承载形式。LD Vibe Harness 不重新定义这些介质本身的语法，只定义事实承载选择原则。

### 6.1 Markdown

Markdown 更适合承载：

1. 背景、原因、解释和设计语境；
2. 理念、规范说明、调研和报告；
3. 人类需要阅读、审查和理解的长文本内容；
4. 不需要高频程序解析的说明性事实。

### 6.2 YAML

YAML 更适合承载：

1. 任务、状态、结构化关系和审计字段；
2. 可解析决策、证据摘要、变更记录和对象实例；
3. 需要被工具校验、聚合、筛选或受控写入的事实；
4. 高频被 AI 读取且需要稳定字段契约的事实。

### 6.3 Python 与 JavaScript

Python 和 JavaScript 主要用于工具实现、校验器、聚合器、Web Tools 前后端和辅助脚本。代码文件可以是工具实现事实，但不能替代规范、对象实例、证据、决策或任务状态的权威事实源。

### 6.4 派生数据

JSON、数据库表、运行时索引、页面状态、缓存文件和命令输出可以作为工具运行过程中的派生数据或中间结果，但不得成为唯一事实源。派生数据必须能从 Git 文件事实源重新生成，或在形成稳定事实后回写到对应权威位置。

### 6.5 事实源读取策略

AI 读取事实源时，应遵循读取精准原则（依据 `specs/08-工作流程基础规范.md` §6.1.1），避免上下文过载。

1. **定位优先于全文**：AI 应先使用搜索工具定位目标段落，再按行范围读取；不得在未定位的情况下全文读取超过 200 行的规范文档；
2. **章节锚点**：LDVH 规范文档使用 `§` 编号体系，章节标题可作为精准读取入口；AI 应先搜索章节标题（如 `^## `、`^### `），再读取目标段落；
3. **工具辅助章节定位**：AI 可通过 Tools 辅助工具生成章节索引辅助定位，但规范文档正文不得依赖固定章节索引作为骨架（依据 `specs/03-文档规范.md` §4.1）；
4. **事实源读取粒度**：AI 应根据任务复杂度选择读取粒度——简单事实查询使用搜索定位 + 行范围读取；跨章节理解任务可逐步扩展读取范围；完整上下文构建任务才考虑全文读取。

## 7. 工具输出回写规则

工具可以读取、解析、校验、聚合、展示和受控写入 Git 文件事实源。工具的价值是降低人和 AI 操作事实源的成本，而不是替代事实源。

工具输出只有满足以下条件后，才成为 LD Vibe Harness 稳定事实：

1. 已写入对应权威事实源文件；
2. 写入位置符合本文和对应对象规范的事实源边界；
3. 必要时通过对应 Human Gate；
4. 可以被 Git 追溯；
5. 不与已有权威事实冲突。

工具缓存、数据库派生视图、运行时索引和页面状态不得成为任务状态、证据、决策、规则或审计结果的唯一来源。

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变某类事实的权威位置；
2. 改变目录是否为最终事实源的判断原则；
3. 将原本属于 ldvh-base/的对象实例事实改放到 specs/、docs/、web/ 或 tools/；
4. 将工具缓存、数据库派生视图、运行时索引或 UI 状态提升为唯一事实源；
5. 将 specs/refs/ 外部资料直接作为强制规范依据；
6. 在多个位置并行维护同一稳定事实。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的目录、事实源、影响范围和建议确认事项。

事实源检查至少包括：

| 检查项 | 标准 |
|---|---|
| 最终事实源 | 稳定事实已写入 Git 可追踪文件 |
| 单一事实源 | 同一事实只有一个权威位置 |
| 目录事实源性质 | 写入位置符合 01 目录事实源性质声明 |
| 承载介质 | Markdown、YAML 或代码文件选择符合事实类型 |
| 工具边界 | 工具缓存和派生视图未成为最终事实源 |
| references 边界 | 外部资料未直接成为强制规则 |
