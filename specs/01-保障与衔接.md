## 1. 价值判断

本文存在的价值，是把 00 的理念、构成要素和 V1-V10 从“应该如此”推进到“可以被保障并接入协作环境”。没有保障与衔接，规则只能停留在规范正文、聊天提醒或 AI 自觉，无法稳定形成入口提示、执行拦截、验证证据、事实源回写和缺口分流。

本文服务 00 的 AI 第一目标：让 AI 在读取、判断、执行、验证、回写和交还时，知道每条关键规则如何被保障、由谁承接、缺口在哪里、何时必须暂停。本文不新增构成要素，而是定义五类构成要素、用户事实源和协作环境之间的保障与衔接层。

## 2. 权威依据

本文承接 `specs/00-理念与构成.md`。

本文不得重定义 00 的存在理由、AI 第一服务对象、五类构成要素、用户事实源底层原则、保障与衔接层或 V1-V10。若本文与 00 冲突，以 00 为准。

`specs/02-Specs基础规范.md` 定义 specs 正文结构、附件边界和 Code 解析入口。本文定义保障需求和衔接链路；02 定义这些内容在 spec 中如何被稳定写入、引用和检查。

`specs/03-AI行为规范.md` 定义 AI 执行者如何遵守价值门、主控责任、诊断分流、Human Gate 和停止条件。03 的行为规则必须通过本文的保障需求与衔接规则说明其落地边界。

## 3. 归口边界

本文归口定义保障与衔接基础规则：

1. 规则要求如何形成保障需求；
2. 保障需求最小字段；
3. 保障需求的消费时机；
4. 承接机制的类型和边界；

## 4. 适用范围

本文适用于 LDVH 中所有需要说明“规则如何不落空”的内容，包括 specs 规则、AI 行为要求、事实对象状态要求、行动编排 Gate、Code 诊断、Web 展示、运行时入口、Hook、Rules、Skill、Agent、Git 追溯、测试验证和 Human Gate。

凡是正式 spec 提出“必须、不得、应当、需要验证、需要回写、需要停止、需要 Human 确认、需要 Code 检查、需要 Web 展示或需要运行时入口”的规则，均应判断是否形成保障需求，并说明其承接方式或缺口。

## 5. 保障需求

### 5.1 保障、承接与衔接定义

规则说明“应该怎样”。保障说明“如何防止规则落空”。承接是保障链路内部的动作，说明“由哪个构成要素、技术机制或人工门禁接住保障”。衔接说明 LDVH 如何进入具体协作环境，使保障能够被读取、触发、执行、验证、留证、回写和分流。

保障链路如下：

```text
规则要求
  -> 保障需求
  -> 承接机制
  -> 执行 / 提示 / 拦截
  -> receipt / evidence
  -> 验证 / diagnostic
  -> 事实源回写 / 缺口分流
```

保障需求不是规则本体之外的新价值来源，也不是事实源。它是规则进入技术环节的可消费表达。承接机制不是最终事实源；承接机制输出只有按事实源边界写入 Git 可追踪文件或形成 Git commit records 后，才可能成为稳定事实。

### 5.2 保障需求最小字段

正式 spec 提出保障需求时，至少应说明：

| 字段 | 要求 |
|---|---|
| 需求ID | 稳定标识，用于 Code、行动编排、Runtime、Web、测试和过程输出回指。 |
| 保障需求 | 要防止哪条规则落空，减少哪类 AI 负担。 |
| 来源事实源 | 保障需求来自哪篇 spec、章节、附件或事实对象。 |
| 消费时机 | 在什么行动时机必须被读取、检查、提示、拦截、验证或交还。 |
| 承接构成要素 | 由规范体系、事实模型、行动模板、Code、Web 或保障与衔接层中的哪一类接住。 |
| 承接机制 | 具体通过规则入口、行动编排、Code、Web、Hook、Rules、Skill、Agent、测试、Git 或 Human Gate 中的哪些机制承接。 |
| 完成证据 | 什么 receipt、evidence、命令结果、Web 呈现、测试结果、Human 决策或 Git 记录可证明本次保障发生过。 |
| 阻断条件 | 哪些缺失、失败、冲突、不可验证或 Human Gate 未决会阻断当前行动或完成声明。 |
| 缺口分流 | 不能承接时回到哪个构成要素缺口、事实对象、行动编排候选、Human Gate 或待补齐事项。 |

字段可以由正文表格、授权附件、Code 派生结构或后续成员规范承载，但不得只存在聊天过程或一次性工具输出中。

### 5.3 消费时机

消费时机用于回答保障需求何时被 AI、Code、Web、Runtime、行动编排或 Human Gate 使用。

当前消费时机闭集由 `specs/attachments/01.Att.01-保障消费时机表.md` 承载。正式 spec 不得私自新增同义时机；需要新增、删除、重命名或改变消费时机含义时，必须修改本文或授权附件，并评估 Human Gate。

## 6. 承接机制

### 6.1 承接机制边界

承接机制可以包括：

| 承接机制 | 作用 | 边界 |
|---|---|---|
| Specs 正文 | 定义规则、保障需求和权威边界。 | 不替代执行、验证或事实源回写。 |
| 行动编排 | 将保障需求组织为 Context、Scenario、Gate、执行、验证、回写和分流。 | 不重写来源规则，不维护第二事实源。 |
| Code | 解析、校验、诊断、生成 read_plan、聚合和受控写入前检查。 | 不替代 AI 判断或 Human Gate。 |
| Web | 展示状态、风险、证据、验证结果和待确认事项。 | 不维护最终事实源，不替代行动判断。 |
| 环境入口 | 提供 Rules 薄引用、Hook、插件、入口可见和环境适配能力。 | 不证明当前环境已经完整支持 LDVH。 |
| 测试 | 提供可复现验证、回归检查和失败阻断依据。 | 不把测试通过升级为 Human 授权。 |
| Git | 承接事实源修改追溯和提交记录。 | 不替代规则正文或对象状态。 |
| Human Gate | 完成授权、方向校正、风险接受或验收判断。 | 只能由 Human 完成，AI 和 Code 不得代替。 |

承接机制可以组合使用，但必须说明主承接位置和输出回指关系。多个机制共同承接同一保障需求时，不得形成互相竞争的权威副本。

### 6.2 Receipt、Evidence 与 Diagnostic

`receipt` 是某个保障消费、执行、确认或写入动作已经发生的回执。`evidence` 是用于支持判断、验证、关闭或追溯的证据。`diagnostic` 是对缺失、失败、风险、不可验证或不一致的结构化判断。

receipt、evidence 和 diagnostic 默认是过程输出，不自动成为最终事实源。需要长期追溯时，必须按事实源边界回写或通过 Git commit records 承接。

AI 不得把 receipt 等同于规则满足，不得把 evidence 等同于 Human 授权，不得把 diagnostic 等同于最终裁决。它们都必须回到主控 AI、事实源规则和必要的 Human Gate 判断。

### 6.3 缺口分流

保障需求无法被承接时，必须区分：

| 类型 | 判断 | 处理 |
|---|---|---|
| `blocking` | 阻断当前行动、规则成立、完成声明、事实源回写或 Human Gate。 | 停止当前完成声明，修复、分流或交还 Human。 |
| `warning` | 不阻断当前行动，但影响风险、证据完整性或判断可信度。 | 明示风险和承接位置，不得静默。 |
| `follow_up` | 不阻断当前行动，但需要后续补齐。 | 写入对应事实源、待补齐事项或工作对象。 |
| `unverifiable` | 当前无法验证、验证范围不足或证据不可复现。 | 说明原因、影响范围和后续承接，不得声明已验证。 |

必要保障缺失不得降级为普通待补齐事项。若缺失支撑当前规则成立、关键行动、Human Gate、Stop Conditions 或完成声明，必须作为 blocker、Human Gate 或 Stop Condition 处理。

### 6.4 不得声称生效边界

出现以下情况时，不得声称保障已完整生效：

1. 只有规范正文要求，没有消费时机、承接机制或完成证据；
2. 只有 Code、Hook、Web、Skill、Agent 或测试输出，没有回指来源保障需求；
3. 只有运行时资产文件存在，没有证明当前环境已接入；
4. 只有 receipt 或工具成功输出，但缺少主控 AI 判断、验证证据或 Human Gate；
5. 缺口、warning、blocker、unverifiable 没有分流位置；
6. 稳定事实停留在聊天、缓存、运行时索引、Web 状态或工具输出中。

## 7. 保障措施

本文通过以下机制保障自身规则被后续 specs 和技术环节消费：

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 保障需求入口要求 | 后续正式 spec 提出必须、验证、回写、停止或 Human Gate 规则时，应说明保障需求或不可承接原因 | 本文 §5.2、02 结构规则、Code 解析、review | 保障需求治理 | 新增、修改或迁移规则时 |
| 消费时机闭集要求 | 保障需求使用统一消费时机，不得私设同义入口 | `01.Att.01`、Code 解析、行动编排 | 入口治理 | 新增或修改消费时机时 |
| 承接边界要求 | 保障需求必须说明主承接构成要素和机制，不得让 Code、Web、Runtime 或行动编排互相反向定义 | 本文 §6.1、后续构成要素规范 | 跨构成要素治理 | 新增承接机制或改动承接边界时 |
| 证据回指要求 | receipt、evidence 和 diagnostic 必须能回指来源需求和事实源边界 | 本文 §6.2、事实源规范、Git 追溯、测试规范 | 证据治理 | 形成验证、关闭、提交或交还结论时 |
| 缺口分流要求 | 承接缺口必须分级并进入对应承接位置 | 本文 §6.3、事实模型、行动编排、Human Gate | 缺口治理 | 出现 blocker、warning、follow-up 或 unverifiable 时 |

`specs/attachments/01.Att.06-保障机制承接矩阵.md` 只维护最小承接映射，不替代本文正文规则，也不替代后续具体实现。

## 8. 验证方法

本文验证口径如下：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 价值衔接检查 | 本文是否只承接 00 的保障与衔接层，没有新增构成要素或新价值门 | 回到 00 和 Human Gate |
| 保障需求结构检查 | 保障需求是否具备来源、消费时机、承接机制、完成证据、阻断条件和缺口分流 | 记录为规范结构缺口或 Code 解析缺口 |
| 承接边界检查 | 后续 specs 是否把具体实现交给对应构成要素，没有在本文或附件中提前吞并 | 回到对应构成要素规范或 Human Gate |
| 证据边界检查 | receipt、evidence、diagnostic 是否未被当作最终事实源或 Human 授权 | 停止完成声明，回到事实源边界或 Human Gate |
| 缺口处理检查 | blocking、warning、follow-up、unverifiable 是否被正确分流 | 按 §6.3 处理，不得静默或降级 |

Code 可以检查 identity block、附件路径、消费时机闭集和保障需求字段是否可解析；AI 必须判断价值、归口、承接边界和风险；Human 负责裁决上位冲突、风险接受和不可自动判断事项。

## 9. Human Gate

以下情况必须进入 Human Gate：

1. 改变保障与衔接层在 00 中的上位定位；
2. 将保障与衔接层改为构成要素；
3. 新增、删除、重命名或改变消费时机闭集含义；
4. 改变 receipt、evidence、diagnostic 的基础语义，导致后续机制判断边界变化；
5. 允许某类机制跳过 Human Gate、事实源边界或验证证据；
6. 接受关键保障不可验证、不可回写或无法分流的风险。

AI 可以准备影响范围、选项和建议，但不得替 Human 完成 Gate。

## 10. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 本文与 00 的价值门、五类构成要素、用户事实源底层原则或保障与衔接层冲突；
2. 下位规范绕过本文各自定义互相竞争的保障与衔接基础规则；
3. 新增规则提出强制要求，但没有保障需求、承接机制、验证方法或缺口分流；
4. Code、Hook、Web、Skill、Agent、测试或 receipt 正在替代 Human Gate 或最终事实源；
5. 必要保障缺失被降级为普通待补齐事项；
6. 无法判断某个承接缺口是否阻断当前行动或完成声明。

暂停后，AI 只能交还触发条件、涉及事实源、影响范围、建议归口和是否需要 Human Gate，不得继续声明保障生效。
