## 1. 本文定位

本文是 `specs/22-Change-变更记录.md` 的附件型实践子文档（编号 22.02），承接 Skill 编排实践。本文定义 ldvh-commit Skill 的编排流程、输入输出、Human Gate 触发点和 PyTools 调用方式。

本文不是独立事实模型，不得重新定义 Change 的对象定位、准入条件、状态机、Human Gate、字段契约、事实源回写或证据留存。发生冲突时，以 22 主文档和上位基础规范为准。

## 2. 实践目标

让 AI 在准备提交代码变更时，通过 ldvh-commit Skill 统一编排提交流程，确保每次 commit 都经过 diff 展示、message 起草、格式预检和用户确认，替代当前 L0、22.01 多处重复维护的提交步骤。

## 3. 适用场景

1. AI 完成代码修改，准备执行 `git commit` 时；
2. AI 跨多个 Git 仓库提交时；
3. 用户在对话中要求提交变更时。

## 4. 实践边界

1. ldvh-commit Skill 只编排提交流程，不执行 commit（由 AI 执行命令）；
2. commit message 格式规范由 22 §8 和 22.06-Contract.md 定义；
3. 格式校验由 PyTools `check_22_commit_format.py` 执行；
4. Skill 不替代 Rules 的入口提醒，Rules 只保留 Skill 引用。

## 5. 编排流程

### 5.1 主流程

1. **检查变更**：AI 执行 `git status`，Skill 确认有变更文件
2. **展示 diff**：AI 执行 `git diff --stat` 和 `git diff`，Skill 确认用户已查看
3. **起草 message**：Skill 按 22 §8 格式引导 AI 起草 commit message（type、scope、subject、body、Refs）
4. **格式预检**：AI 调用 `python3 tools/check_22_commit_format.py --check-message "<message>"`，exit code ≠ 0 时修正后重新预检
5. **Human Gate 确认**：Skill 触发 AskUserQuestion，展示 diff 摘要和完整 message，用户确认后继续
6. **逐文件 add**：AI 执行 `git add <file>`（不可 `git add -A` 或 `git add .`）
7. **执行 commit**：AI 执行 `git commit -m "<message>"`
8. **验证**：AI 执行 `git status` 确认提交成功

### 5.2 跨仓库流程

跨仓库变更时，对每个有 `.git` 的仓库重复主流程。无 `.git` 的目录报告 `未发现 Git 仓库，跳过`。

### 5.3 异常处理

- 格式预检不通过：展示不合规项，修正 message 后重新预检
- 用户取消确认：停止提交流程，不执行 commit
- 无变更文件：报告 `无变更，跳过提交`

## 6. Human Gate

以下节点触发 Human Gate（AskUserQuestion）：

1. 步骤 5：展示 diff 和 message 后，用户确认是否继续提交
2. 涉及 `ldvh-base/` 事实实例修改时，额外提醒用户确认修改内容

## 7. 检查项

- [ ] Skill 是否在 diff 展示后才进入 message 起草
- [ ] 格式预检未通过时是否阻止继续
- [ ] 用户确认前是否展示了完整 diff 和 message
- [ ] commit message 是否包含 type、scope、subject、body、Refs
- [ ] 是否逐文件 add，未使用 `git add -A` 或 `git add .`
- [ ] 跨仓库变更是否逐仓库独立提交

## 8. 待补齐事项

1. 如后续支持自动生成 commit message，Skill 增加 message 生成步骤；
2. 如后续支持 pre-commit hook，评估是否将格式预检集成到 hook 中。
