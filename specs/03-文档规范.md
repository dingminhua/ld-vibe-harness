## 1. 本文解决的问题

本文解决 LD Vibe Harness specs 文档如何区分正式规范文档、子文档、历史机制文件和项目评估文档，如何编写文档骨架，以及如何通过引用纪律避免多个事实源的问题。

LD Vibe Harness 的文档治理目标，不是让所有内容都进入同一种文档格式，而是让 AI、人和工具能稳定判断一份文档在规范体系中的位置、权威范围、上位依据、术语含义、引用方式和 Human Gate 要求。

specs 编号分区由 `specs/01-目录说明.md` 定义，本文不重复维护。术语边界、机制英文专名、中文术语定语和历史机制文件命名维度规则由 `specs/02-术语规范.md` 定义，本文不重复维护。

## 4. 文档类型

### 4.1 正式规范文档

正式规范文档使用两位编号，格式为 NN。正式规范文档可以定义稳定规则，适用于 00-79 区间。

示例：

```text
01-目录说明.md
02-术语规范.md
03-文档规范.md
04-事实源边界与承载规范.md
05-Trae-Solo环境规范.md
06-Python与Web工具规范.md
07-工作模型基础规范.md
08-工作流程基础规范.md
20-工作模型集合索引.md
```

正式规范文档必须通过头部元信息声明定位、适用范围、上位依据和相关规范；正文必须包含解决问题、与 00 总纲的关系、核心规则、Human Gate 与检查要求和待补齐事项。00 总纲作为顶层文档，不要求声明上位依据。正式规范文档不得设置"不进入本文""边界说明"等反向边界章节。

specs/ 目录内所有 Markdown 文档的正文章节标题应统一使用阿拉伯数字层级编号。一级章节使用 `## N. 标题`，二级章节使用 `### N.N 标题`，三级章节按需使用 `#### N.N.N 标题`。正文引用章节时统一使用 `§N`、`§N.N` 或 `§N.N.N`。正式规范文档、子文档、历史机制文件、结构化契约文件、索引文档、`specs/evals/` 项目评估文档和 `specs/refs/` 外部资料引用文档均适用该编号规则。同一文档内不得混用中文大写章节编号、罗马数字编号和阿拉伯数字章节编号。章节编号统一只约束文档结构和引用定位，不改变 `specs/evals/` 与 `specs/refs/` 的执行效力和事实源性质。

正文章节标题编号与正文有序列表编号应区分处理。`## N. 标题`、`### N.N 标题`、`#### N.N.N 标题` 属于章节编号，应随文档层级连续展开；章节内部的普通枚举、步骤、检查项和规则清单可以使用 Markdown 有序列表，并可在每个章节内从 `1.` 重新开始。只有需要稳定引用或被 Rules、Skill、Agent、Tools、Web 或 Contract 实体消费的内容，才应升级为 `N.N` 或 `N.N.N` 子章节。

正式规范文档不得依赖文档内章节索引作为固定骨架。AI 与 Tools 的章节定位应依据 Markdown 标题搜索、机器生成章节索引和原文行范围读取；文档正文如需稳定引用，依靠阿拉伯数字章节编号和原文标题。

### 4.2 子文档

正式规范文档因内容超出单文档承载能力，或某个编号区间的上位基础规范明确要求通过附属文件承接特定内容时，可以创建子文档。子文档编号格式为 NN.SS，其中 NN 为父文档编号，SS 为子文档序号。

子文档不是独立规范，而是父文档的扩展或指定区间内的历史机制承接。子文档的权威来源是父文档，子文档不得与父文档矛盾，不得重新定义父文档、基础规范或机制规范已有规则。

示例：

```text
05-Trae-Solo环境规范.md
```

子文档不强制采用正式规范文档的完整骨架，但必须遵守父文档定义的子文档格式，并保留父文档引用、所属范围、章节归属和待补齐标记等最小治理信息。历史机制文件应说明自身只是工作模型或工作流程在某个机制或主题下的历史实践承接，不替代主文档。

### 4.3 历史机制文件

历史机制文件是指定编号区间内曾按 NN.SS 形式创建的机制承接文件。当前适用于 `20-39` 工作模型规范区和 `40-59` 工作流程规范区，用于在迁移完成前承接某个工作模型或工作流程围绕 Rules、Skill、Agent、Tools、Web、Contract 等机制的历史实践内容。LDVH 当前不设置三段式实践文档层级。

历史机制文件不是独立规范，也不是工作模型或工作流程完整性的默认要求。历史机制文件只能作为迁移前过渡资料保留，用于说明对应工作模型或工作流程在某个机制下曾如何实践。新增或稳定后的机制内容应按机制归属进入主规范机制适配边界、05、06、08、运行 Rules、Skill 实体、Agent 定义摘要、Tools 实现、Web 实现或契约能力，不得继续依赖固定 NN.01-NN.06 结构成立。历史机制文件不得定义新的基础规则，不得替代主文档，不得重新定义主模型的对象定位、字段契约、状态机、Context、Scenario、Gate、执行流程、事实源边界或 Human Gate。

历史机制文件的具体迁移、保留和删除规则由对应区间的上位基础规范定义：工作模型依据 `specs/07-工作模型基础规范.md` 和 `specs/20-工作模型集合索引.md`，工作流程依据 `specs/08-工作流程基础规范.md`。

示例：

```text
21.01-Rules.md
21.04-Tools.md
41.01-Rules.md
41.02-Skill.md
41.05-Web.md
```

04、05、06、07、08 等基础规范区的机制内容不是历史机制文件。机制规范定义机制本身的治理规则；历史机制文件只说明某个工作模型或工作流程曾如何实践这些机制，不替代 Trae 实体定义文件、工具实现、机制规范或主模型。运行结果形成稳定事实时，应按事实源边界写回 specs/、docs/ 或 ldvh-base/。

### 4.4 索引文档

正式规范区间中，20 或 08 等编号可作为区段入口的索引文档。索引文档使用两位编号。

索引文档不定义对象字段、状态机或行动流程，只提供该区段内文档的清单、关系映射、状态和维护信息。索引文档服务于 AI 和人在进入一个区段前快速了解该区段的文档组织和现状。

示例：

```text
20-工作模型集合索引.md
08-工作流程基础规范.md
```

索引文档的权威来源是其上位规范（如 20 依据 07、08 依据自身工作流程基础规范职责维护 40-59 区段索引），索引文档不得在清单之外定义新的对象或行动规则。

### 4.5 项目评估文档（evals/）

specs/evals/ 承载因 LD Vibe Harness 项目实际情况而生成的评估文档和内部参考文档，包括对外部工具、方法、框架或概念的项目级评估，以及项目内部临时参考。

项目评估文档的编号组织和效力声明依据 `specs/01-目录说明.md` §3.3.2。

项目评估文档应通过头部元信息声明创建日期、定位、编号归属、调研边界、执行效力、上位依据和相关规范。项目评估文档不需要 Human Gate 与检查要求章节。

项目评估文档的章节结构应符合 §5.7 项目评估文档骨架，必须包含"本文解决的问题"和"结论"两个核心章节，正文章节按评估逻辑组织并保持阿拉伯数字编号一致性。

specs/evals/ 与 specs/ 根目录正式规范文档之间的引用方向如下：

1. specs/evals/ 可以引用 specs/ 根目录正式规范文档（00-79 编号区间）作为评估依据和上位规范；
2. specs/ 根目录正式规范文档（00-79 编号区间）不得引用 specs/evals/ 中的任何文件，包括路径引用、关联规范声明和依据引用；
3. specs/evals/ 的评估结论必须进入 00-79 正式规范区间或 ADR 后，才能被正式规范文档消费。

引用方向规则依据 `specs/01-目录说明.md` §3.3.2。

### 4.6 外部资料引用文档（refs/）

specs/refs/ 承载与 LD Vibe Harness 规范体系相关的外部资料引用，用于在规范编写和内部调研时快速查阅。

外部资料引用文档的编号组织和效力声明依据 `specs/01-目录说明.md` §3.3.1。外部资料引用文档是外部资料的引用副本，不改变其非规范事实源的性质。

外部资料引用文档应通过头部元信息声明创建日期、来源和定位。

外部资料引用文档的章节结构应符合 §5.8 外部资料引用文档骨架，必须包含"结论摘要"章节，正文章节按资料来源性质组织并保持阿拉伯数字编号一致性。外部资料引用文档不得包含对 specs/ 目录内文件的路径引用、关联规范声明或依据引用。

specs/refs/ 与 specs/ 规范体系之间的引用方向如下：

1. specs/ 根目录正式规范文档（00-79 编号区间）不得引用 specs/refs/ 中的任何文件，包括路径引用、关联规范声明和依据引用；
2. refs/ 不得反向引用 specs/ 目录内的任何文件，包括路径引用、关联规范声明和依据引用；
3. refs/ 下的文档不得包含对 specs/ 目录内文件的路径引用、关联规范声明或依据引用。

引用方向规则依据 `specs/01-目录说明.md` §3.3.1。

## 5. 文档骨架

### 5.1 正式规范文档骨架

正式规范文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---

---
## 1. 本文解决的问题

## 2. 与 00 总纲的关系

## 3～N-2. 核心规则
（具体章节按主题组织）

## N-1. Human Gate 与检查要求

## N. 待补齐事项
```

普通 specs 文档如存在机制落地关系，机制落地关系章节应放在 Human Gate 与检查要求之前；不涉及机制落地关系的文档不得为了模板完整性占位声明。

机制落地关系是 specs 文档与 Trae 环境机制实体或 LDVH 可执行机制实体之间的关系声明，用于记录该规范内容落地到 Rules、Skill、Agent、Tools、Web、MCP 或其他机制实体时的实体路径、关系类型、同步触发条件和审计入口。机制落地关系不是普通规范引用、上位依据关系、相关规范清单或文档内容一致性检查；文档之间的规范依据、引用方向和一致性要求应通过头部元信息、正文引用纪律、Human Gate 与检查要求承载，不应混入机制落地关系表。

注：20-39 和 40-59 区段的正式规范，可用"与直接上位基础规范的关系"替代"与 00 总纲的关系"章节标题，直接上位基础规范分别为 `specs/07-工作模型基础规范.md` 和 `specs/08-工作流程基础规范.md`。00 总纲作为顶层文档，不要求包含"与 00 总纲的关系"章节。`20-工作模型集合索引.md` 是区段入口索引文档，按本文 §5.4 索引文档骨架检查，不按 §5.1 正式规范文档完整骨架要求补齐"本文解决的问题"、关系章节或"Human Gate 与检查要求"章节；其头部字段按索引文档骨架中的定位、上位依据和索引范围执行。`08-工作流程基础规范.md` 同时承担工作流程基础规范与 40-59 区段索引职责，按 §5.1 正式规范文档完整骨架要求执行。

头部字段规则：以上字段为正式规范文档必填字段，00 总纲作为顶层文档可不声明上位依据。新增头部字段不得与已有字段语义重叠，不得在头部承载正文才应展开的规范内容。历史机制文件可在"适用范围"之后增加"定位"字段，用于说明该文件在主规范机制适配边界中的角色，但"定位"不得与"适用范围"语义重叠。正文不得通过"不进入本文""边界说明"等反向清单表达职责边界；职责边界应由头部定位、适用范围、上位依据、相关规范和正文正向规则共同表达。

### 5.2 子文档骨架

子文档建议采用以下骨架：

```markdown
# {子文档标题}

> 创建日期：YYYY-MM-DD
> 所属主文档：`specs/NN-xxx.md`
> 关系：父规范扩展
> 适用范围：...
> 上位依据：`specs/NN-xxx.md`

---

## 1. 本文定位

## 2. 父规范关系

## 3. 核心规则

## 4. Human Gate 与检查要求

## 5. 待补齐事项
```

父文档可以为其子文档定义更具体的格式。子文档格式不得弱化本文定义的最小治理信息，也不得设置"不进入本文""边界说明"等反向边界章节。

### 5.3 历史机制文件骨架

历史机制文件建议采用以下骨架，具体工作模型或工作流程可在 07、08 约束下按机制承接重点调整章节：

```markdown
# {历史机制文件标题}

> 创建日期：YYYY-MM-DD
> 所属主文档：`specs/NN-xxx.md`
> 关系：工作模型历史机制文件 / 工作流程历史机制文件
> 适用范围：...
> 上位依据：`specs/NN-xxx.md`
> 相关规范：...（可选）

---

## 1. 本文定位

## 2. 实践目标

## 3. 适用场景

## 4. 实践边界

## 5. 实践内容

## 6. Human Gate

## 7. 检查要求

## 8. 待补齐事项
```

历史机制文件不得复制父规范、主模型、主流程或机制规范的规则正文，只能引用其规则并说明该模型或流程在对应机制下的历史实践内容、迁移状态和检查要求。

### 5.4 索引文档骨架

索引文档建议采用以下骨架：

```markdown
# {区段名称}索引

> 创建日期：YYYY-MM-DD
> 定位：...
> 上位依据：`specs/07-工作模型基础规范.md` 或 `specs/08-工作流程基础规范.md`
> 索引范围：20-39 / 40-59

---

## 1. 定位

说明本索引服务的区段、索引目标和阅读指引。

## 2. 索引范围

说明本索引覆盖的编号区间及其边界。

## 3. 文档清单

| 编号 | 文档 | 类型 | 定位 | 状态 | 说明 |
|---|---|---|---|---|---|
| 21 | xxx | 正式规范 | ... | stable | ... |
| 22 | yyy | 正式规范 | ... | planned | ... |

## 4. 对象/模型关系

说明文档之间的引用关系、依赖关系和事实源边界。

## 5. Human Gate

列出索引范围变更的相关 Human Gate 要求。

## 6. 维护说明

说明索引更新时机、同步要求和待补齐标记。
```

索引文档不得复制上位基础规范或具体对象/行动规范的规则正文。

### 5.5 结构化契约文件骨架

结构化契约文件建议采用以下骨架：

```markdown
# {结构化契约文件标题}

> 创建日期：YYYY-MM-DD
> 所属主文档：`specs/NN-xxx.md`
> 关系：工作模型结构化契约文件 / 工作流程结构化契约文件
> 适用范围：...
> 上位依据：`specs/NN-xxx.md`
> 相关规范：...（可选）

---

## 1. 本文定位

## 2. 事实源边界

## 3. 契约定义

（按实际契约类型组织，如字段 schema、接口契约、数据结构等）

## 4. 工具和 Web 消费要求

## 5. 检查项

## 6. 待补齐事项
```

结构化契约文件不得复制主文档的对象定位、状态机、Scenario、Gate、执行流程或 Human Gate 规则。结构化契约文件只定义结构化契约，供 Tools 校验、Web 信息同步和 Agent 调度消费；它属于历史机制文件或契约能力承接，不构成固定 NN.06 子文档要求。

### 5.6 机制落地关系骨架

普通 specs 文档存在机制落地关系时，建议采用以下最小骨架：

```markdown
## 6. 机制落地关系

本文通过以下机制关系说明相关机制实体的落地、同步、检查或审计触发条件。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
```

## 6. 机制落地关系

机制落地关系用于说明普通 specs 文档中的稳定规则是否被 Rules、Skill、Agent、Tools、Web 或 Contract 实体稳定消费，以及文档变更、产品初始化、同步检查、审计或规则漂移诊断时需要检查或更新哪些实体。

机制落地关系遵循最小声明原则：只有当本文规则被某个机制实体稳定消费，且本文变更、产品初始化、同步检查、审计或规则漂移诊断会导致该实体需要检查或更新时，才声明该机制关系。不涉及的机制不声明。

20-39 工作模型和 40-59 工作流程不使用普通机制落地关系，依据 `specs/07-工作模型基础规范.md` 和 `specs/08-工作流程基础规范.md`，在主规范中声明机制适配边界。历史 NN.01-NN.06 机制文件只作为迁移前资料或过渡契约保留，不作为机制关系成立的默认结构。

机制落地关系至少包含：关联机制、关联实体、关系类型和触发条件。必要时可补充维护边界和检查要求。

判断普通 specs 文档是否需要声明某类机制落地关系时，应依据以下标准：

| 关联机制 | 声明条件 |
|---|---|
| Rules | 本文规则被 `.trae/rules/*.md` 摘要、触发或作为运行时约束，且本文变化需要同步检查 Rules 文件 |
| Skill | 本文规则被可复用 Skill 流程消费，影响触发条件、输入输出、执行流程、回写边界或降级路径 |
| Agent | 本文规则被 Agent Prompt、角色参数、权限边界、上下文隔离或调度条件消费 |
| Tools | 本文规则被 Tools 用于解析、校验、聚合、上下文包生成、派生数据生成或受控写入 |
| Web | 本文规则被 Web 页面、Human Gate UI、受控编辑入口、派生视图或信息同步流程消费 |
| Contract | 本文规则被结构化字段、schema、接口契约或数据结构消费，且变化会触发契约同步 |

普通 specs 文档新增、修改或删除机制落地关系时，应同步检查对应机制实体的头部来源、维护边界和引用纪律。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| Rules | `ld-vibe-harness/.trae/rules/ldvh-specs-rules.md` | specs 编辑入口摘要 | 本文的文档骨架、引用纪律、机制落地关系、反向边界或文档治理检查变化时 |

| Tools | `ld-vibe-harness/tools/specs_refs_validate.py` | 03 文档引用机械化检查工具 | 本文的章节引用、引用纪律、refs 反向引用、机制落地关系或文档治理检查变化时 |

## 7. 引用纪律

引用纪律的本质是事实源单一性在文档体系中的体现——同一个 specs 规范只能在一份文档中定义，其他文档只能指向它，不能复制它。

1. 权威唯一：每项稳定 specs 规范只能有一个权威定义位置。其他文档需要使用该 specs 规范时，只能写"依据权威文档 §Y"，不得复制、改写或另行定义同义 specs 规范；
2. 职责表达：判断 specs 规范权威位置时，优先依据文档头部定位、适用范围、上位依据、相关规范和正文正向规则，而不是依据反向边界清单、文档出现顺序、引用次数或描述详细程度；
3. 上位约束：00 定义体系理念、价值标准、构成要素和顶层治理原则；01 定义项目目录规划和 specs 编号分区；02 定义术语边界和术语变更治理；03 定义文档类型、文档骨架、引用纪律和文档治理规则；04 定义事实源边界与承载规则；05 定义 LDVH Trae Solo 环境规范基础规则；06 定义 LDVH 辅助工具基础规则；07 定义 LDVH 工作模型基础规则；08 定义 LDVH 工作流程基础规则；20-39 定义具体工作模型规则；40-59 定义具体工作流程规则；specs/evals/ 只提供项目评估，不直接构成强制规则；specs/refs/ 只提供外部资料引用，不直接成为强制规则；
4. 适配不重写：工作模型、工作流程、场景实践或工具说明引用基础规范时，只能说明如何适配，不能重新定义基础规则；
5. 冲突处理：当两个文档对同一 specs 规范给出不同表述时，应先判断该 specs 规范的权威领域；非权威文档应改为引用权威文档，不能保留并列 specs 规范；
6. 调研升级：specs/evals/ 项目评估中的结论需要进入 00-79 正式规范区间或 ADR 后，才成为稳定规则；
7. 引用方向：specs/ 根目录正式规范文档（00-79 编号区间）不得引用 specs/evals/ 和 specs/refs/ 中的任何文件，包括路径引用、关联规范声明和依据引用；specs/evals/ 可以引用 specs/ 根目录正式规范文档作为评估依据；specs/refs/ 不得引用 specs/ 目录内的任何文件。引用方向规则依据 `specs/01-目录说明.md` §3.3.1 和 `specs/01-目录说明.md` §3.3.2。

## 8. Specs 文档索引

Specs 文档索引是从 specs Markdown 原文中确定性提取的派生导航信息，用于帮助 AI、人和 Tools 定位文档、章节、头部元信息、引用关系、机制落地关系和文档治理缺口。

### 8.1 索引定位

Specs 文档索引的定位如下：

1. 索引是派生数据，必须能回溯到 specs 原文路径、行号和文件内容状态；
2. 索引不得替代 specs 原文，不得维护独立规则解释，不得作为工作模型、工作流程、Rules、Tools 或 Web 的权威规则来源；
3. 索引与原文冲突时，以原文为准；
4. 索引缺失、过期或解析失败时，不得作为规范判断依据；
5. 索引生成不得调用 AI、Skill 或 Agent。

### 8.2 输入范围

第一阶段 specs 文档索引默认只覆盖 `specs/*.md`（含正式规范文档、子文档、历史机制文件、结构化契约文件和区段集合索引），默认不覆盖 `specs/evals/*.md`、`specs/refs/*.md` 及其他非 specs 根目录文档。`specs/evals/` 和 `specs/refs/` 只有在用户明确指定时，才可按原文读取。

### 8.3 索引类型

Specs 文档索引包括以下类型：

1. 文档清单索引：记录每份 specs 文档的基本信息；
2. 章节索引：记录 Markdown 标题树、标题层级、章节编号和起止行号；
3. 头部元信息索引：记录文档头部字段；
4. 引用关系索引：记录路径引用、章节引用和头部依据引用；
5. 机制落地关系索引：记录机制落地关系表格；
6. 文档治理诊断索引：记录可机械化发现的问题。

### 8.4 AI 消费规则

AI 使用 specs 文档索引时应遵循以下顺序：

1. 根据任务识别需要查询的 specs 根目录规范文档或主题；
2. 使用文档清单索引或章节索引定位候选文档和章节；
3. 按索引中的路径和行号读取 specs 原文片段；
4. 以读取到的原文作为规范判断依据；
5. 索引缺失、过期、冲突或无法定位时，回退到搜索定位和行范围读取。

AI 不得只读索引而不读原文就执行高影响规范变更、Rules 修改、Tools 写入、Human Gate 判断或事实源回写。

### 8.5 Tools 辅助程序边界

Specs 文档索引程序属于 Tools 辅助层能力。Tools 辅助程序可以扫描、解析、校验、聚合和输出派生数据，但不得：

1. 将索引类信息持久化为独立事实源；
2. 将 Tools 输出作为 specs 规范、Rules、审计或决策的唯一来源；
3. 自动修改 specs 原文、Rules 或事实实例；
4. 绕过 Human Gate 自动写入；
5. 直接调用 AI、Skill 或 Agent；
6. 用 LLM 摘要、向量化结果或语义推断替代确定性解析结果。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 重命名或重排 specs 文档；
2. 改变子文档或历史机制文件层级关系；
3. 子文档或历史机制文件重新定义父规范已有原则；
4. specs 文档引用 specs 外部文档作为规范依据；
5. 历史机制文件新增或扩张基础规范；
6. 将 specs/evals/ 项目评估结论直接作为强制规则使用；
7. 新增或重排索引文档，改变索引范围或文档归属；
8. 索引文档定义新的对象字段、状态机或行动规则；
9. 改变机制落地关系规则，或新增、修改、删除会影响 Rules、Skill、Agent、Tools、Web 或 Contract 实体同步检查、产品初始化、审计或规则漂移诊断的机制落地关系；
10. 改变 specs/ 根目录正式规范文档与 specs/evals/、specs/refs/ 之间的引用方向规则。

当 AI 识别到上述情况时，依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §7 Human Gate 与检查要求执行。

项目应提供 `tools/specs_doc_validate.py`，作为本文的机械化检查工具，用于辅助检查 specs/ 目录内 Markdown 文档的章节标题编号。工具至少应检查：一级章节是否连续；二级、三级章节是否与父章节编号一致；同级章节是否掉号、跳号或重复；标题编号层级是否与 Markdown 标题层级一致；是否存在中文大写或罗马数字章节标题残留。工具应忽略 fenced code block 内的示例标题和正文 Markdown 有序列表。

AI 在新增、迁移或批量修改 specs/ 下 Markdown 文档章节标题编号后，应优先调用 `tools/specs_doc_validate.py`；工具不可用时，应人工检查并说明降级原因（依据 specs/22-Change-变更记录.md）工具测试用例应放置于 `tests/tools/test_specs_doc_validate.py`，并通过项目当前测试入口执行。

项目应提供 `tools/specs_refs_validate.py`，作为本文的机械化检查工具，用于辅助检查 specs/ 目录内 Markdown 文档的章节引用。工具至少应检查：显式 `specs/*.md` 路径引用的目标文件是否存在；显式路径后的 `§N`、`§N.N` 或 `§N.N.N` 目标章节是否存在；同文档内部章节引用是否存在；`NN §N` 或 `NN.SS §N` 速记引用是否能解析到目标文档和章节；正文是否残留中文大写章节引用。工具应忽略 fenced code block 内的示例引用。

AI 在新增、迁移、重命名或批量修改 specs/ 下 Markdown 文档文件名、章节编号、章节引用、上位依据、相关规范、机制落地关系、索引清单或引用纪律相关内容后，应优先调用 `tools/specs_refs_validate.py`；工具不可用时，应人工检查并说明降级原因（依据 specs/22-Change-变更记录.md）工具默认检查 specs/ 根目录正式规范文档；需要专项审计 `specs/evals/` 或 `specs/refs/` 时，应显式传入目标目录或文件。工具测试用例应放置于 `tests/tools/test_specs_refs_validate.py`，并通过项目当前测试入口执行。

工具使用建议：

1. 批量修改前先运行工具获取全量基线，避免仅凭正则脚本匹配特定模式而遗漏边缘情况（如脚本只匹配了"一～十"而漏掉"十一～二十"，或只处理了 `##` 层级而遗漏 `####` 无编号子标题）；
2. 不要仅依赖正则脚本的自我验证——脚本匹配的是预设模式，工具检查的是编号连续性、父级一致性和层级对应关系，两者覆盖的维度不同。脚本执行后必须再用工具做权威验证；
3. 工具输出的告警需要区分真实违规与有意例外：如 refs/ 下的模板类文件可能使用非编号的模板式标题（"模板1：""基本用法"等），这些标题虽然被工具标记为"缺少阿拉伯数字编号"，但属于文档性质决定的合理差异，不应强制编号化。AI 应对工具输出逐条判断，不能盲目清零；
4. 迭代工作流程建议：`工具基线 → 分析告警分类 → 批量修复 → 工具验证 → 逐条处理残留 → 工具复验`。每轮修复后都应重新运行工具，确保上一轮的修复没有引入新的编号跳跃或父级不一致。
