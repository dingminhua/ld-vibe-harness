## 1. 本文解决的问题

本文记录 LDVH 工作流程集合从原 45-58 执行阶段候选转向底层治理流程候选的设计评估。

本次评估解决：

1. 为什么当前 40 工作流程集合需要推倒重排；
2. 哪些旧候选适合保留、合并、降级或迁移为后续候选；
3. 哪些底层工作流程应优先进入 41-59；
4. 哪些流程适合配套 Skill、Agent、Code 或人工降级检查；
5. 后续创建 active 主流程前需要确认哪些 Human Gate 和测试边界。

---
## 2. 结论

当前 40 的主要缺口不是缺少任务执行阶段拆分，而是缺少对 LDVH 自身最底层资产的持续审查流程。若 specs、Code、Rules 入口和能力资产本身无法被稳定审查，后续 Input、Plan、Execute、Verify、Record、Learn 阶段流程会反复依赖聊天提醒和临时判断。

重建后的 40 应优先登记以下底层治理流程候选：

1. specs 审核；
2. Code 审核；
3. Rules 入口审核；
4. 能力资产审核；
5. 事实源与回写审核；
6. 变更影响审核；
7. 工作流程设计审核；
8. Dogfood 闭环；
9. 上下文准备；
10. 任务执行与验证闭环。

这些流程应先作为工作流程候选进入 40。高频可复用步骤可以再封装为 Skill，复杂语义判断可以由 Agent 辅助，可机械化检查应进入 Code 或测试。

## 3. 评估正文

### 3.1 重建原因

原 45-58 候选主要来自标准运行流程的执行阶段拆分，覆盖输入接入、计划规划、任务执行、验证关闭、ADR、Change、对象状态、管辖项目配置、经验沉淀、Review、上下文准备、流程测试、非 LDVH 内容接管和实践升级。

这组候选有实践价值，但存在三个问题：

1. 它们更像执行阶段流程，不能优先回答 specs、Code、Rules 入口是否可信；
2. Review、流程测试、实践升级等候选过于泛化，容易在没有底层审查流程时反复扩张；
3. 旧候选没有把 00 的 V1-V10 价值标准转化为 LDVH 自身资产审查的稳定入口。

因此，40 应先把底层治理流程排在前面，再把原执行阶段候选迁移为后续候选或合并项。

### 3.2 首批底层流程判断

specs 审核应检查 specs 是否内部逻辑自洽、定义归口正确、编号和引用一致、符合 00 价值标准、符合 AI 第一服务对象、符合文档治理和规范落地要求。它应成为工作流程，并可配套 `ldvh-spec-audit` Skill、语义审查 Agent 和 specs 校验 Code。

Code 审核应检查 Code 是否好用、是否降低 AI 上下文消耗、是否符合 07 的需求准入、验证先行、测试边界、输出边界和事实源边界。它应成为工作流程，重点依赖测试、命令验证和等价验证记录；Skill 可选。

Rules 入口审核应检查 `rules/LDVH-AI-ENTRY.md` 是否保持薄入口、是否正确路由场景、是否未复制 specs 正文、是否没有保存长期状态、是否与 04.02、04.03、01、40 和相关适配措施同步。它应成为工作流程，并适合配套固定检查 Skill 和部分 Code 检查。

能力资产审核应覆盖 Rules、Skill、Agent、Hook、Code、Web 的边界，防止 Skill 新增稳定规则、Agent 输出直接生效、Hook 触发被写成检查通过、Code 输出冒充事实源或 Web 维护第二事实源。

事实源与回写审核应专门检查稳定事实是否进入 Git 文件事实源，过程输出、工具输出、Skill 输出、Agent 输出和 Web 状态是否没有成为最终事实源。

变更影响审核应作为横切流程，检查 specs、Code、Rules、Skill、Agent、Hook、Web、目录、编号和集合状态变化后的同步、Human Gate、测试和入口更新。

工作流程设计审核应反过来审查 41-59 流程自身，确认具体流程符合 06 和 03.04，不把流程写成泛化说明、Skill 正文或索引规则。

Dogfood 闭环应落实 00 的防递归建设原则。每新增一层抽象后，应用 LDVH 自己跑一次最小闭环，而不是继续补更多抽象。

上下文准备可从原 55 保留，但定位应从泛化候选收敛为最小可行动 Context Pack 生成与检查。

任务执行与验证闭环可合并原 47 和 48，避免执行与验证分裂导致证据、关闭和失败分流脱节。

### 3.3 旧候选迁移判断

原输入接入和计划规划保留为后续候选，等待底层审查流程稳定后再创建。

原任务执行和任务验证与关闭建议合并为任务执行与验证闭环。

原 ADR decision、change commit、object state update 和 governed project config 适合作为后续管理行动候选，不进入首批底层治理流程。

原 learning capture 和 practice upgrade 建议合并为经验回流与实践升级候选。

原 review 不宜保留为泛化 Review，应拆入 specs 审核、Code 审核、Rules 入口审核、能力资产审核和工作流程设计审核。

原 workflow test design 不宜过早独立成流程，应先由 03.04 的行动特有可测试性锚点和 Code 测试需求承接。

原 non-LDVH content handover 可作为后续接管行动候选保留。

### 3.4 工作流程与 Skill 的关系

工作流程承载权威的 Scenario、Context、Gate、执行流程、回写、证据、Human Gate、失败降级和能力协作边界。

Skill 承载可复用 SOP、固定检查步骤、输出格式、失败处理和交还主控方式。

Agent 承载独立上下文、复杂语义审查、争议分析和多视角判断。

Code 承载文件存在、编号、章节、引用、落地要求表、测试命令、路径、输出格式等可机械化检查。

因此本次重建不应先创建 Skill 来定义流程，而应先在 40 登记候选，再创建具体主流程，最后按高频程度和可机械化程度分别建设 Skill、Agent 和 Code。

## 4. 后续建议

1. 先将 40 的 41-50 重排为底层治理候选；
2. 将原 45-58 执行阶段候选改写为后续候选、合并项或待重评项；
3. 优先创建 41 specs audit、42 code audit、43 rules entry audit 三个主流程；
4. 为 specs audit 评估配套 Skill、Agent 和 Code 检查；
5. 为 Code audit 先明确测试和等价验证边界，再判断是否需要 Skill；
6. 为 Rules entry audit 评估固定检查 Skill 和路径/薄入口 Code 检查；
7. 每创建一个 active 主流程后，同步检查 01、03.04、06、07、04.02、04.03 和 40 是否需要更新。
