# V4 规范成员发现与术语方案评估

> 记录性质：V4 架构设计记录，不是规则源。
> 决策状态：01 草案建议；Human 已确认 YAML 使用代码围栏、术语采用中英双语、基础规范避免治理过度。
> 评估日期：2026-07-11

## 1. 需要解决的问题

V4 需要用尽量少的共同规则回答三个问题：

1. 哪些 Markdown 文件可能成为规则；
2. Human、AI 和 Code 如何识别它们；
3. 跨规范名词如何同时保持中文可读、英文可检索和机器可解析。

## 2. 已确认约束

1. 当前规则源由正式规范正文及其授权附件构成。
2. YAML 身份必须以带 `yaml` 语言标识的代码围栏展示，不能只依赖普通文本式 Front Matter。
3. Code 可以消费身份和关系，但未实现的解析器、校验器或 Helper 不能被声明为可用。
4. V4 不继承 V3 迁移基线、双读和旧 validator。
5. 只有长期稳定、日常识别和消费真正需要的约束进入 01；低频内部维护不提前制度化。
6. 进入全局术语表、机器接口或存在跨语言歧义风险的核心术语，使用“中文规范术语 + English Canonical Term + 机器表示”，三者表达同一概念。

## 3. 推荐方案

采用“受限目录检查 + H1 后固定 YAML 身份块 + Code 派生导航”。

1. Code 只检查已提交 Git 版本中的 `specs/*.md` 和 `specs/attachments/*.md`。
2. 每个候选文件以唯一 H1 开始，随后使用带 `yaml` 标识的代码围栏承载 `ldvh` 身份字段。
3. 身份块保存稳定职责标识、编号、状态和必要的主动声明关系；标题、路径、职责和范围从文件本身取得。
4. 不维护人工成员清单；Code 从当前文件派生目录和关系。
5. `status: "active"` 只是必要条件；身份无法确定、结构错误、职责重复、关系错误或附件授权失败时必须报告，不能静默忽略。
6. 默认只有当前 `HEAD` 的已提交内容构成当前规则源；面向提交的校验以暂存区实际将提交的完整内容为对象。

完整载体示例：

````markdown
# 规范体系基础规范

```yaml
ldvh:
  schema: "ldvh-spec/v1"
  kind: "spec"
  key: "normative-system-foundation"
  spec_id: "01"
  status: "draft"
  structure: "standard"
  basis:
    - "ldvh-root"
```

## 1. 价值判断
````

## 4. 为什么不用其他方案

### 4.1 不使用人工成员清单

人工成员清单会重复维护文件身份和路径，并形成第二个同步点。当前目录和关系可以由 Code 从自描述文件派生，不需要新的权威文件。

### 4.2 不使用无代码围栏的 Front Matter

Front Matter 可以确定机器边界，但普通 Markdown 展示不一定清楚。LDVH 同时服务 Human、AI 和 Code，因此采用 H1 后固定位置的 YAML 代码围栏：Human 可直接阅读，Code 仍可按固定位置解析。

### 4.3 不依赖纯目录扫描

目录只能确定候选范围，不能表达草案、当前状态、稳定身份、依赖和附件授权。因此仍需要最小 YAML 身份块。

## 5. 核心规范与低频维护的边界

| 内容 | 01 是否规定 | 承接位置 |
| --- | --- | --- |
| 当前规则源、身份块、共同正文结构 | 是 | 01 |
| 稳定职责标识、基础关系、附件授权 | 是 | 01 |
| 三态生命周期和提交后生效 | 是，只规定结果边界 | 01 |
| YAML 字段类型和安全子集 | 是，只规定实现无关的最小数据契约 | 01 |
| YAML 加载器、字节级错误码 | 否 | Schema、Code、tests |
| 提交前校验暂存区完整内容 | 是，只规定校验对象 | 01 |
| Git 双树算法和对象 ID | 否 | Code 或维护工具 |
| 五状态生命周期、永久墓碑、持续历史扫描 | 否 | 当前不采用；新 `key` 分配时只检查仍保留的 V4 历史 |
| 批量重编号、迁移、拆分合并的详细步骤 | 否 | 维护指南或行动模板 |
| 每次 active 修改都写 Human 决议元数据 | 否 | 由实际命中的 Human Gate 和事实记录规则决定 |
| 一次性 00/01 启用步骤 | 否 | 本设计记录和当次执行计划 |

这些内容未进入 01 不表示禁止实现；只表示它们不能在尚无稳定重复需求时增加所有 AI 的日常规则负担。

## 6. 双语术语构造

一个需要双语治理的核心概念使用三层表达：

```text
中文规范术语 ↔ English Canonical Term ↔ 机器表示
```

例如：

```text
稳定职责标识 ↔ Stable Responsibility Identifier ↔ key
身份块       ↔ Identity Block                    ↔ H1 后的 yaml 围栏
当前规则源   ↔ Current Rule Source               ↔ —
```

未来术语表只记录名称、机器表示和定义来源，不复制定义。建议最小结构：

| 中文规范术语 | English Canonical Term | 机器表示 | 唯一定义来源 | 其他有效表达 | 历史名称 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |

机器表示只填写精确字段、枚举或对象名称；没有直接表示时填写 `—`。状态只使用 `current` 或 `historical`。定义仍位于承担该概念职责的规范正文；术语表只负责检索和映射，不能成为第二定义点。

## 7. 与 V3 04 的关系

继续保留：

- 带 YAML 代码围栏的机器身份；
- 稳定职责标识与编号、标题、路径分离；
- 根规范与标准规范；
- 上位语义依赖、结构归属、附件授权和替代关系；
- Code 派生导航但不形成第二规则源；
- 验证要求、Human Gate 和 Stop Conditions。

明确改变：

- 规范编号从 04 调整为 01；
- Spec 与附件统一使用 `key`，关系值使用稳定 key，不使用路径；
- `kind` 与 `structure` 分开表达载体类型和正文结构；
- `parent_spec` 和 `authorized_attachments` 保留清楚字段名，但值改为稳定 key；
- 生命周期简化为 `draft`、`active`、`retired`；
- 不继承 V3 迁移基线、旧结构双读和兼容校验。

明确不采用：

- 无围栏 Front Matter；
- `canonical_path`、`title`、`role_sections` 等可直接取得或稳定派生的重复字段；
- 五状态生命周期、永久终态身份记录和双 Git 树治理算法；
- 强制 `resolution` / Human 决议身份字段。

仍需单独确认：

- V3 的 `code_consumption` 当前未进入 01 最小字段。它是否仍有不可替代的稳定接口声明价值，应在设计 V4 Code 解析契约时单独评估；如果不能证明移除后更契合 V1–V8，就恢复该字段。

## 8. 后续启用边界

01 仍是草案。正式启用前至少需要：

1. 对照 00 和 V3 04 完成语义复核；
2. Human 明确接受 01 的字段、术语和精简边界；
3. 在 00 的 H1 后增加根规范 YAML 身份块，不改变 00 规则正文；
4. 将 01 状态改为 `active`；
5. 验证 00 和 01 可以按同一身份规则读取。

V4 parser、validator 和 Helper 尚未实现时，只能声明规范设计已确认，不能声明机器能力已经 available、integrated 或 completed。
