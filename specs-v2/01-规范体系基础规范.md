## 1. 本文解决的问题

本文定义 v2 规范体系如何成立，以及单篇规范如何成为可读取、可判断、可校验、可派生知识地图的稳定规范结构。它回答的核心问题是：一篇规范最低必须具备哪些结构，才能让 AI 在有限上下文中判断它的位置、权威边界、依赖关系、校验入口和待补齐风险。

本文解决：

1. 规范如何声明身份、状态、权威边界、迁移来源和 active 事实源；
2. 当前 v2 目录如何只登记已经单篇处理的规范和附件；
3. 正式规范最低需要哪些必要章节；
4. 规范如何表达上位依据、构成要素归属、正向价值判断和逆向价值判断；
5. 规范如何表达相关关系、消费关系、附件授权和迁移来源；
6. 规范结构如何形成知识地图所需的节点、边、来源回指和最小读取依据；
7. 附件如何命名、授权、受父规范约束，并避免变成隐性主规范；
8. v1 子文档迁移时如何判断回并主规范、拆为附件、升为根规范或暂不迁移；
9. 规范保障要求、Human Gate、规范写作执行顺序和 Code 缺口如何以统一结构暴露给 AI 与 Human。

本文只定义上述共同治理规则。事实模型字段、状态机、行动流程、Code 输出 Schema、Web 页面契约、Git 提交格式、事实源细则、运行时扩展类型和具体环境适配规则，由对应构成要素实践在自身规范中声明。本文不预设这些专题的最终编号、拆分方式或迁入结论。

## 2. 上位依据

本文承接 `00-LDVH理念与价值标准.md` 的 v2 写作基线已确认事项：

1. v2 规范治理必须以“LDVH 为什么存在”和“AI 执行者为第一服务对象”为最高校验锚点；
2. 每篇规范必须归属到六类构成要素之一，或说明自己如何服务这些构成要素；
3. 事实源是底层原则，不得被规范结构、附件、工具输出、派生投影或页面状态替代；
4. 知识地图是规范结构的派生机制和实现方法，不是独立事实源、独立构成要素或工作对象；
5. 每篇规范及其下属机制必须接受 V1-V10 准入判断。

本文不得重定义 00 的存在理由、AI 第一服务对象、六类构成要素、事实源底层原则或 V1-V10。本文只定义这些上位原则在正式规范中如何被声明、承接、核对和治理；若本文与 00 冲突，以 00 为准。

01 只定义规范体系共同遵守的治理规则。知识地图输入契约由规范身份、章节、引用、附件授权和消费关系派生，不构成 01 的并列主题。各规范的存在性、职责、拆分方式、附件需求和迁移归口，必须回到原文逐篇核对后由对应规范自行声明。

## 3. 构成要素归属与价值判断

### 3.1 构成要素归属

本文属于六类构成要素中的 `规范体系`。

| 项目 | 判断 |
|---|---|
| 主归属 | 规范体系 |
| 辅助服务对象 | 事实模型、行动编排、Code、Web 和运行时扩展都可消费本文定义的规范身份、章节结构、附件授权、引用关系、保障声明和 Human Gate 规则 |
| 不归属边界 | 本文不定义事实模型字段、对象状态机、行动流程、Code 输出 Schema、Web 页面契约、事实源细则或运行时扩展适配规则 |

### 3.2 正向价值判断

本文至少服务以下价值标准：

| 价值标准 | 本文如何服务 |
|---|---|
| V1 快速定位 | 通过目录登记、规范身份、附件授权和知识地图输入，让 AI 快速判断应读哪篇规范、附件或 active 事实源 |
| V2 可行动理解 | 通过必要章节、上位依据、权威归口和事实源边界，让 AI 在有限上下文中形成可执行理解 |
| V3 正确判断 | 通过权威域、吸收规则、附件规则和旧子文档迁移规则，降低 AI 误判归口、重复维护或制造第二事实源的风险 |
| V4 稳定执行 | 通过规范写作与修改执行顺序，约束 AI 创建、迁移、修改和审计规范时的最低动作 |
| V5 门禁识别 | 通过 Human Gate 规则，让 AI 在高影响规范治理变更前暂停并等待 Human 确认 |
| V6 强制验证 | 通过 Code 覆盖、缺口与降级规则，为规范身份、章节、引用、附件和保障要求提供确定性诊断方向 |
| V10 持续完善 | 通过待补齐事项、附件边界和迁移治理规则，把规范缺口、迁移缺口和 Code 覆盖缺口保留为后续改进入口 |

本文不要求每篇规范服务 V1-V10 全部十项。除 00 外，每篇正式规范必须列出自己真实服务的 V 项；不得为了填满表格而虚构价值。

### 3.3 逆向价值判断

本文必须避免以下反向风险：

| 反向风险 | 本文如何避免 |
|---|---|
| 用目录草案替代规范事实 | 当前目录只登记已进入单篇核对范围的规范和附件，未来编号和占位文件不得写成事实 |
| 用附件制造隐性主规范 | 附件只能承载父规范授权的表、矩阵、模板、示例和清单，不得定义核心原则或新规则入口 |
| 用知识地图替代事实源 | 知识地图只用于定位、影响判断、诊断回指和派生展示，不替代规范正文、附件授权或 Git 文件事实源 |
| 用 Code 输出替代 Human Gate | Code 只提供确定性诊断，不能替代 Human 的确认、授权、方向校正或验收 |
| 凭旧编号或主题相近迁移规则 | 迁移 v1 原文时必须逐篇读取 active 事实源，确认真实职责、事实源边界、引用关系和 Code 消费入口 |
| 反向补全下游义务 | 被引用、被消费、被展示或被工具读取的规范，不因下游使用而承担下游实现细节或同步义务 |

## 4. 适用范围与事实源边界

本文适用于三类对象：

1. v2 写作区中的规范；
2. 经 Human 单篇确认后进入 active 的 LDVH 正式规范；
3. 被主规范授权的附件、注册表、矩阵、模板、示例和长清单。

`specs-v2/` 是 v2 写作区。切换 active 前，其中的规范用于方案核对、迁移计划、结构试写和知识地图解析，但不得替代当前 active `specs/`。AI 执行 active 规则、Code 默认校验、Rules 入口加载和事实源回写判断时，仍应以当前 active `specs/` 为准。

迁移来源、研究材料、审计追溯、工具输出、环境观察和聊天过程都不能直接成为正式规范依据。稳定结论必须吸收到 active 规范、对应事实模型、行动编排、ADR、WorkCase、Spark、Pitfall 或其他明确事实源后，才形成可执行事实。

### 5.1.1 项目目录与管辖项目配置职责归口

v2 不保留独立“目录说明”根规范。v1 `01-目录说明.md` 和 `03.04-管辖项目配置规范.md` 的职责在 v2 中按最小权威归口拆分承接：

| 内容 | v2 归口 | 边界 |

| v2 规范写作区、已处理范围、规范编号、附件命名和专题成员声明方法 | 01 | 不定义事实模型字段、行动流程、事实源细则或环境适配实现 |
| 稳定事实源、单一事实源、Git 可追溯、过程输出回写、事实承载介质和文档工作区事实源边界 | 07 | 不维护规范目录登记或成员骨架 |
| 事实模型实例目录、实例承载方式、字段契约和工作对象写入边界 | 02 与 20-29 成员主文件 | 不定义全局事实源原则 |

`LDVH-GOVERNED-PROJECTS.yaml` 是工作区根目录的管辖项目配置事实源，用于登记当前 LDVH 管理实例和管辖项目清单。该配置不是工作对象，不进入 `ldvh-base/`，不承载初始化状态、部署适配结果、检查状态、环境能力、适配措施、缺口处理状态或项目文档接管状态。

管辖项目配置只允许表达当前管理实例和管辖项目最小清单。其 v1 字段规则在 v2 切换前仍以 active `specs/03.04-管辖项目配置规范.md` 为准；v2 后续若调整字段、文件位置或入口，应回到本文、06、07 和对应 Code 检查共同确认，不得由 README、Rules 入口、Web 页面或过程输出直接扩展字段。

用户管辖项目不因被登记而默认创建 `specs/`，也不因被登记而默认接管、初始化、重排或强制校验用户 docs。管辖项目文档位置由项目自身约定、README、用户指令、任务上下文或 Human Gate 决定；管辖项目工作对象事实源默认按项目根目录下 `ldvh-base/` 定位，具体对象规则由 02 和 20-29 成员主文件定义。

项目正文区、研究区和来源区的事实源边界不由 01 直接定义。01 只说明目录职责归口；正文区、`studies/`、`sources/`、Markdown/YAML/代码文件/派生输出等承载介质选择和吸收边界由 07 承接。

### 5.2 规范文件命名与编号

v2 规范文件名必须让 AI 在目录视图中先判断文件性质，再决定是否读取正文。

根规范命名采用：

```text
{两位编号}-{规范名称}.md
```

附件命名采用本文 §10 的 `{父编号}.Att.{两位序号}-{名称}.md`。专题成员规范是否使用独立区段、独立编号或专属成员身份块，由所属构成要素实践在自身规范中声明；01 不预设专题成员的最终编号段。

后续编号不得提前写成既成事实。除 §5.1 已登记的规范和附件外，其它编号、文件名、顺序和归口，都必须在读取 active 原文、确认真实职责并完成 Human 单篇核对后再登记。

规范编号用于表达规范在规范体系中的读取入口、权威归口和体系位置，不用于表达文件创建时间。新增、删除、重命名、合并、拆分或重排规范编号前，必须先判断：

1. 是否符合 00 的存在理由、AI 第一服务对象和 V1-V10；
2. 是否改变某个构成要素实践的权威归口；
3. 是否需要读取 active 原文确认旧规则边界；
4. 是否会破坏 Code、Web、运行时扩展或知识地图的既有消费入口；
5. 是否触发 Human Gate。

编号计划、迁移计划、目录草案和知识地图派生结果不能替代 active 原文。对现有规范做迁移、改名、改号或改归口判断时，必须逐篇读取原文，确认其真实职责、事实源边界、引用关系和 Code 消费入口。

### 5.3 v2 规范身份块

每篇 v2 规范必须在一级标题之后、正文第一章之前提供 `v2_spec`。该身份块用于让 AI、Code 和知识地图在不阅读全文时先判断规范身份、状态、范围、关系和迁移风险。

`v2_spec` 字段契约和状态闭集由 `01.Att.04-规范身份字段表.md` 承载。01 正文只定义身份块必须存在、必须可解析、必须与文件名和正文范围一致、不得被正文重复维护。

普通正文头部不得重复维护 `v2_spec` 已承载的身份事实。若 v2 规范身份块与文件名、标题、路径或正文范围冲突，应先修正身份块或文件结构，再继续讨论正文内容。

新增、删除、重命名或改变 `v2_spec` 字段、状态闭集或状态含义前，必须进入 Human Gate。未进入 `01.Att.04` 闭集的状态值不得在 v2 规范身份块中使用；仅用于计划、占位或笔记的文件不应伪装成 v2 规范。

### 5.4 active 身份块

v2 未切换为 active 前，当前正式规范仍使用 active `specs/` 中的 `ldvh_doc`。v2 规范进入 active 时，应保留一个稳定的 active 身份块，用于承载编号、类型、标题、状态、路径、定位、范围、依据、相关规范和 Code 消费入口。

active 身份块能力提示由 `01.Att.04` 承载。该提示只说明身份块必须保持的可解析、可回指和可迁移能力，不直接改变当前 active `ldvh_doc` 字段。

现有 `ldvh_doc` 字段名和枚举在迁移前仍是 Code 默认入口。v2 如果调整 active 身份块字段，应先定义双读兼容、迁移策略、正反样例和降级诊断，不得让 Code 只能把 v2 规范当作解析失败处理。

## 6. 正式规范必要章节

除 00 总纲外，正式规范必须至少具备以下结构：

1. 一级标题；
2. 规范身份块；
3. `## 1. 本文解决的问题`；
4. `## 2. 上位依据`；
5. `## 3. 构成要素归属与价值判断`；
6. 核心规则章节；
7. `规范保障要求`；
8. `Human Gate`；
9. `待补齐事项`。

00 是顶层总纲，可以使用产品存在理由或总纲叙事标题，不强制把第一章命名为 `本文解决的问题`，也不要求设置 `上位依据` 或 `构成要素归属与价值判断` 章节。其他正式规范不得借 00 例外省略自身的必要章节。

`上位依据` 章节必须说明直接承接哪些上位规范、这些上位规范分别约束本文什么、本文不得重定义哪些上位规则，以及与上位依据冲突时以哪个事实源为准。`v2_spec.basis` 是结构化字段，`上位依据` 章节是 AI 和 Human 可读的解释，两者必须一致。

`构成要素归属与价值判断` 章节必须说明本规范的主归属、辅助服务对象、不归属边界、正向服务的 V1-V10 项和需要避免的逆向风险。正向价值只列真实服务的 V 项，不要求十项全部出现；逆向价值判断必须明确说明本规范如何避免制造第二事实源、增加 AI 阅读负担、绕过 Human Gate、替代上位规范或压缩 Human 判断。

正式规范正文采用当前有效规则态写法。正文只定义当前生效的规则、契约、流程、边界和状态判定方法；历史迁移、旧编号、旧文件名、执行结果、环境观察和过程状态应进入 Git history、ADR、WorkCase、Spark、Pitfall、研究材料或对应事实源。

章节标题应使用可解析的阿拉伯数字层级编号。正文对章节的引用应使用 `§N`、`§N.N` 或等价稳定锚点；正文路径引用应指向真实存在的文件。

职责边界应通过定位、适用范围、上位依据、相关规范、权威归口和正向规则表达。正式规范不设置专门的反向边界章节；需要说明不承载的内容时，应同时指明由哪个权威归口或待补齐事项承接。

## 7. 权威域、定义归口与吸收规则

一条稳定规则只能有一个最小权威归口。AI 新增或修改规范内容时，应先判断该内容回答的问题，再写入最小权威归口：

| 问题类型 | 最小权威归口 |
|---|---|
| LDVH 为什么存在、AI 第一服务对象、价值判断 | 00 总纲 |
| 规范体系、规范身份、必要章节、附件、知识地图输入、引用纪律 | 01 |
| 术语与推荐表达 | 01 正文和 `01.Att.02-术语表.md` |
| 不推荐表达、替代写法和中文定语规则 | 01 正文和 `01.Att.08-规范表达清单.md` |
| 事实源、证据、回写边界 | 事实源规则的 active 归口；本文不预设编号 |
| 保障要求、能力保障、环境适配 | 对应构成要素实践或保障机制的 active 归口；本文不预设编号 |
| 事实模型、字段契约、状态机、对象关系 | 事实模型的 active 归口；本文不预设成员编号 |
| 行动编排、Context、Scenario、Gate、执行、暂停、交还 | 行动编排的 active 归口；本文不预设成员编号 |
| Code 解析、校验、聚合、诊断和反馈 | Code 的 active 归口；本文不预设实现入口 |
| Web 展示、Human 可见状态、确认入口 | Web 的 active 归口；本文不预设实施阶段 |
| Git 提交、变更追溯、历史证据 | 事实源、行动编排或 Git 追溯规则的 active 归口；本文不预设编号 |
| 测试、验证、回归和验收证据 | 对应构成要素实践或验证规则的 active 归口；本文不预设编号 |

引用另一个规范不自动改变权威归口。被引用、被消费、被展示、被工具读取或被附件登记的规范，不因为下游使用而反向承担下游规则、同步义务或实现细节。

迁移来源、研究材料、外部资料和工具输出中的稳定结论，必须吸收到最小权威归口后才生效。吸收不得只通过引用路径完成；被采纳的规则、字段、状态、流程、保障要求或校验规则必须在权威归口正文中明确写出。

## 8. 术语治理与表达纪律

术语治理属于规范体系治理。01 正文定义术语归口、变更边界和表达纪律；`01.Att.02-术语表.md` 承载术语条目、推荐表达和术语边界，`01.Att.08-规范表达清单.md` 承载不推荐表达、替代写法和中文定语规则。

术语本体定义与对象规则定义应区分处理：

1. 术语本体定义回答“这个名称在 LDVH 中是什么意思、边界是什么、推荐怎么称呼”，归口 01 和术语表附件；
2. 对象规则定义回答“某个事实模型、行动编排、字段、状态、流程、Code、Web 或运行时扩展在自身规范中如何构成、如何约束、如何执行”，归口对应构成要素实践；
3. 非术语归口规范可以说明某个术语在本规范中的应用关系，但不得重新定义术语本体、同义词、包含关系或替代表达；
4. 若发现术语缺失、术语边界不足或术语需要改名，应先回到 01 和 `01.Att.02` 处理；若发现不推荐表达残留、替代写法或中文定语问题，应回到 `01.Att.08` 处理；随后再同步相关规范或 Code 检查；
5. 术语表附件中的条目不得把字段契约、状态机、流程 Gate、事实源边界或环境适配细则写成术语定义。

术语应用关系应使用“术语 / 本规范应用关系”或等价表格，说明该术语在当前规范中的承载、消费、约束或检查方式。说明句式应使用“在本规范中用于……”“由……消费”“与……区分”“不得用于……”等应用口径，不得写成“X 是……”“X 指……”“X 定义为……”等二次定义。

术语新增、改名、废止或改变边界前，应检查：

1. 是否影响 00 的存在理由、AI 第一服务对象、六类构成要素、事实源底层原则或 V1-V10；
2. 是否影响规范身份、附件授权、知识地图关系、引用纪律或 Code 消费入口；
3. 是否影响事实模型、行动编排、Code、Web、运行时扩展、事实源、Git 追溯或测试验证规则；
4. 是否需要同步 `01.Att.02`、`01.Att.08`、相关规范、Code 术语检查、知识地图关系和 Web 展示；
5. 是否触发 Human Gate。

## 9. 引用关系与知识地图输入

知识地图与规范强耦合。v2 不把知识地图放在规范体系之外维护，也不为目录说明另设独立上位规范。知识地图由规范身份、章节锚点、权威归口、迁移来源、引用关系、附件授权、消费关系、Code 校验结果和 Git 可追踪事实源实时派生。

知识地图的统一原则如下：

1. 知识地图只能作为只读派生投影，用于定位、最小读取、影响判断、诊断回指和派生展示，不得替代规范正文、附件授权、成员主文件、事实对象、管辖项目配置或 Git commit records；
2. 知识地图必须由 Code 按请求从当前事实源实时生成，不得落盘维护 `entities.json`、`edges.json`、`graph-metadata.json`，不得引入外部图数据库作为事实缓存，也不得依赖长期缓存或派生索引作为事实源；
3. 知识地图必须支持渐进式获取信息，默认只提供入口摘要和一跳关系；二跳、多跳、原文、表格明细、事实对象全文、Git diff 或提交历史只能按当前任务需要展开；
4. 每次展开必须能说明展开理由、输入范围和来源回指；不得因为存在图关系就默认读取全量规范、全量事实对象、全量 Git history 或全量管辖项目文档；
5. 每个节点和关系边必须能回指路径、字段、章节、表格行、对象 ID、commit hash 或其它明确事实源位置；无法回指来源的内容只能作为诊断或排除项，不得输出为可信节点或边；
6. 知识地图可以覆盖 LDVH 自身项目和已登记管辖项目，但必须以工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 为入口，按项目命名空间隔离节点、边和诊断；
7. 知识地图不得反向维护管辖项目清单，不得默认接管、创建、迁移、重排或强制校验用户项目 docs，不得把 LDVH dogfood 条目解释为用户安装后的默认管辖项目；
8. Git history 在知识地图中只作为时间、变更和证据层输入；知识地图可以展示变更事件和影响关系，但不得替代 Git commit records 或提交契约。

知识地图渐进读取分层如下：

| 层级 | 默认输出 | 展开条件 |
|---|---|---|
| 入口层 | 节点摘要、编号、标题、状态、路径、构成要素归属、上位依据、附件和 Code 消费类别 | AI 需要判断先读哪几个节点时 |
| 邻接层 | 当前节点的一跳 `basis`、`related`、`parent`、`derives_from`、`consumes`、`gated_by`、`impacts` 等关系 | AI 需要判断依赖、影响、消费或 Gate 时 |
| 展开层 | 二跳、多跳、影响面、阻塞链、证据链、收敛链和跨项目边 | 规范修改、事实源回写、关闭判断、迁移核对或审计需要时 |
| 原文层 | 规范正文、附件表格、事实对象全文、Git diff、commit body 或测试输出 | 关系视图不足以作出判断或需要验证证据时 |

知识地图的基本输入如下：

| 输入 | 派生结果 | 要求 |
|---|---|---|
| `v2_spec` 或 active 身份块 | 规范节点 | 必须能回指路径、标题、编号、状态和事实源 |
| H2-H4 章节标题 | 章节节点或章节锚点 | 必须可解析、可引用、可定位行号 |
| `basis` | 上位依据边 | 只能指向真实承接的上位原则 |
| `related_specs` | 相关规范边 | 只登记读取依赖、同步依赖、字段依赖或检查依赖 |
| `migration_sources` | 迁移来源边 | 只说明迁入、吸收或参考来源，不授予 active 权威 |
| `active_fact_source` | active 事实源边 | 用于避免写作区内容替代当前正式规则 |
| `parent_spec` / `relation` | 父子或附件授权边 | 必须能判断从属关系和授权范围 |
| 正文路径引用 | 路径引用边 | 不得把导航引用升级为上位依据 |
| 正文 `§` 引用 | 章节引用边 | 必须能回指目标章节 |
| `code_consumption` | 消费边 | 说明 Code、Web、运行时扩展或知识地图读取目的 |

`active_fact_source` 在知识地图中映射为 `derives_from` 关系的一种来源结构，含义是“写作区规范从当前 active 事实源取得对照和迁移依据”。该关系不得被解释为 v2 写作区已经具备 active 权威，也不得新增独立的 `active_fact_source` 边类型。

关系类型的详细表放入 `01.Att.01-知识地图关系类型表.md`。01 正文定义最小闭集：`basis`、`related`、`parent`、`derives_from`、`consumes`、`validates`、`renders`、`writes_to`、`owns_attachment`、`gated_by`、`impacts`。附件可以扩展示例和判定口径，但不得单独改变关系原则。

AI 或 Code 生成关系边时，应按以下顺序判断：

1. 先判断是否存在父规范授权；存在时使用 `parent` 或 `owns_attachment`；
2. 再判断是否存在上位原则承接；存在时使用 `basis`；
3. 再判断是否存在真实读取、同步、字段或检查依赖；存在时使用 `related`；
4. 再判断是否只是迁移、active 事实源对照、吸收、解析或派生来源；存在时使用 `derives_from`；
5. 再判断是否是消费、校验、展示或写入行为；分别使用 `consumes`、`validates`、`renders`、`writes_to`；
6. 再判断是否存在 Human Gate、授权或暂停条件；使用 `gated_by`；
7. 只需要影响面提示但不构成以上关系时，使用 `impacts`。

同一对节点可以存在多条不同类型关系，但每条关系必须能回指具体字段、章节、表格行、Code 输出或事实源路径。

以下关系升级被禁止：

1. 不得把 `related` 升级为 `basis`；
2. 不得把 `derives_from` 升级为 active 事实源；
3. 不得把 `consumes` 升级为被消费方对消费方的同步义务；
4. 不得把 `renders` 升级为最终事实源；
5. 不得把 `validates` 的一次输出升级为长期状态；
6. 不得把 `impacts` 升级为父子关系或执行责任；
7. 不得把路径同目录、编号相邻或主题相近写成强关系。

知识地图输出只用于定位、最小读取、影响判断、诊断回指和派生展示。它不得替代规范正文、成员主文件、附件授权、Code 校验原始结果或 Git 文件事实源。

## 10. 附件规则

附件是主规范授权的附属文件，不是常规子规范体系。附件只承载主规范授权的注册表、矩阵、模板、示例、长清单或其它不适合放入主文的辅助材料。

附件必须围绕一个主要信息对象建立。主要信息对象可以是一个注册表、关系类型表、字段表、状态闭集、矩阵、模板、示例集、长清单或辅助核对表；附件可以包含服务该对象的字段说明、值域、正反例和核对项，但不得同时维护两个可以独立变化、独立授权或独立被 Code 消费的信息对象。

当一个附件同时承载多个主要信息对象时，必须拆分为多个附件，并由父规范逐项授权。不得使用“附录”“补充说明”“综合表”“治理清单”等宽泛名称把多个对象混在一个附件中。附件名称必须直接命名它承载的主要信息对象。

附件名称中的大主语由父规范编号提供，默认不得重复父规范标题中的核心主题词。例如 02 的附件不应反复写“事实模型”，03 的附件不应反复写“行动编排”，除非不写会导致跨父规范歧义。附件名称必须保留足以识别主要信息对象的小主语；若名称只剩“表达清单”“模板”“矩阵”等泛名，应补足小主语。

同一信息对象类型在不同父规范下重复出现时，应优先保持同构小主语和同构尾部类型，由 `{父编号}.Att.{两位序号}` 区分归属。例如 02 和 03 都可以使用“成员身份字段表”“成员主文件骨架模板”“成员一致性辅助核对表”；不得为了显式归属而写成“事实模型成员身份字段表”或“行动编排成员身份字段表”。

附件名称的信息对象类型必须使用以下闭集之一：`表`、`清单`、`矩阵`、`模板`、`核对表`、`登记表`、`样例集`。附件名称不得以 `规则`、`规范`、`机制`、`治理` 作为文件名尾部类型；这些词容易把附件误写成独立规则入口。若这些词属于稳定术语或必要限定语，例如“规范保障要求”，可以作为小主语的一部分使用，但不得作为附件承载类型。

附件名称不得使用 `与` 打包两个并列对象。若两个对象可以独立变化、独立授权或独立消费，应拆成两个附件；若确实属于同一登记对象，应使用上位对象命名，例如“清退登记表”，而不是“清退对象与废弃字段登记表”。

术语表、规范表达清单、字段注册表、字段矩阵、关系类型表、规范保障要求类型表和行动编排接管建议矩阵可以作为附件存在。此类附件承载条目、清单、矩阵、正反例和判定辅助信息；条目治理规则、字段存在性、关系原则、保障声明原则、行动编排接管边界和权威边界仍必须留在授权主规范正文中。

附件可以声明维护自身条目、矩阵或清单所需的表格字段、值域、状态闭集、推荐写法、禁止写法和辅助核对表。此类声明只约束该附件内部登记和诊断，不得扩展为其它规范的必要字段、状态机、流程 Gate、事实源边界、Code 消费要求或跨规范治理原则。

附件与 v1 子文档的最大区别是约束强度。v1 子文档可以在父文档下较自由地展开一个专题；v2 附件不得自由扩展父规范，也不得形成新的规则入口。附件只能回答父规范已经授权它回答的问题；一旦附件开始定义新的核心原则、流程 Gate、事实源边界、字段存在性、状态机、保障声明原则或接管责任，应立即回到父规范正文处理，不能继续在附件中扩写。

附件命名采用：

```text
{父编号}.Att.{两位序号}-{名称}.md
```

附件文件名中的 `{名称}`、一级标题和 `v2_attachment.title` 必须完全一致；`v2_attachment.canonical_path` 必须与真实文件路径完全一致；`v2_attachment.parent_spec` 必须指向授权父规范。名称、标题、身份块或路径任一不一致，均应视为附件命名与身份漂移缺口。

附件应与父规范位于同一层级，不默认放入子文件夹。附件在结构上必须由父规范授权，在生效上必须随父规范经过 Human 单篇确认；父规范未确认时，附件不得独立成为 active 规范依据。

附件必须提供 `v2_attachment` 或等价身份块。附件身份字段契约和状态闭集由 `01.Att.05` 承载；附件正文不得自行增删身份字段或状态值。

附件不得承载需要主规范确认的核心原则、权威域、状态机、字段存在性、流程 Gate、资产登记机制或事实源边界。若附件内容开始承担这些职责，应回到父规范正文处理。若主规范因为表格、模板、矩阵、示例或清单过长而影响 AI 快速定位和判断，应优先拆为父规范授权附件，而不是继续膨胀主文档。

附件不得设置 `AI 检查要求`、`Human Gate` 或 `Code 消费要求` 作为独立章节。附件需要提供核对信息时，应使用“关系辅助核对表”“术语与表达辅助核对表”“保障声明辅助核对表”或等价标题，且只能作为附件内容的诊断辅助，不能形成正式规范必要章节。

附件身份块中的 `code_consumption` 只说明附件可能被 Code 或知识地图消费的内容类别，不定义消费字段、输出 Schema、诊断字段、命令入口或覆盖要求。附件的 Code 消费边界、缺口记录和降级方式必须由本文 §14.1 或后续 Code 规范统一承接。

v2 不保留常规 `NN.xx` 子文档体系。迁移 v1 子文档或专题补充文件时，应按以下顺序判断：

1. 子文档中的主体规则、边界、状态机、流程 Gate、权威归口、字段存在性或事实源规则，应回并到所属主规范或新的最小权威归口正文；
2. 子文档中的长表、注册表、矩阵、模板、示例、正反样例、清单和判定辅助信息，可以在父规范明确授权后拆为附件；
3. 子文档职责已经独立服务六类构成要素之一，且无法由父规范正文或附件清晰承载时，才可申请升为根规范；
4. 子文档只承载历史讨论、方案草稿、迁移中间态或未确认材料时，应暂不迁移，保留为来源或待补齐事项；
5. 不得为了保留旧编号、减少改写或方便引用而把 v1 子文档机械迁移为 v2 子文档。

旧子文档迁移结论必须回指 active v1 原文，并说明主体规则回并位置、附件授权位置、暂不迁移理由或升为根规范的 Human Gate 结果。

## 11. 专题成员与专属骨架规则

某些规范域可以拥有成员集合或专属骨架。成员集合不是目录清单，也不是派生索引本身；成员主文件必须声明自己的成员身份、状态、路径、锚点和 Code 消费入口，Code 与知识地图只能消费这些事实并生成派生视图。

专题规范可以定义本专题成员文件的专属骨架、成员自描述字段、状态判定、章节锚点和 Code 消费入口，但必须在所属主规范或成员主文件中显式声明。

01 只定义声明方法和治理边界，不预设任何专题的必需章节、字段、状态机、流程 Gate、实例目录或执行步骤。专题专属骨架必须说明：

1. 适用范围；
2. 必需章节；
3. 可不适用章节的说明方式；
4. 成员自描述字段；
5. 派生索引回指方式；
6. Human Gate；
7. 检查入口。

成员自描述属于成员主文件事实源，不得放入附件、派生索引、普通头部或 Code 输出中独立维护。Code、Web 和知识地图可以消费这些结构，但输出只能作为导航、诊断或展示，不能替代成员主文件。

## 12. 规范保障要求

正式规范必须设置 `规范保障要求` 章节。该章节用于说明当前规范中哪些要求需要被入口、流程、Code、Web、运行时扩展、环境适配或人工降级检查保障。

规范保障要求表采用以下统一结构，沿用 v1 保障声明的五字段契约：

| 字段 | 出现要求 | 含义 |
|---|---|---|
| `保障要求` | 必须出现 | 保障要求类型；必须使用 `01.Att.03` 定义的闭集 |
| `要求内容` | 必须出现 | 需要被看见、执行、复用、检查、触发、确认或实现的具体内容 |
| `保障机制` | 必须出现 | 已声明保障方向、现有临时保障、人工降级检查或建议接管的行动编排；不等于已实现或已部署状态 |
| `同步类型` | 必须出现 | 文档、Code、Web、流程、Human Gate、运行时扩展、环境适配或迁移治理同步 |
| `触发条件` | 必须出现 | 何时需要复检、同步、接管、降级或 Human Gate |

`01.Att.03-规范保障要求类型表.md` 承载保障要求类型闭集、类型说明、声明写法和保障声明辅助核对表。`01.Att.07-行动编排接管建议矩阵.md` 承载行动编排接管建议矩阵和接管建议辅助核对表。两个附件只能维护各自主信息对象的表格、矩阵、正反例和判定辅助信息，不得改变本文定义的保障声明字段、接管边界或事实源原则。

普通保障要求描述“需要保障什么”。当一个或多个普通保障要求需要跨步骤、跨资产、Human Gate、证据留存、事实源回写、缺口分流或后续同步时，应在 `保障机制` 中建议由某个行动编排接管，或建议建立对应行动编排实例。行动编排接管不是普通检查项，而是把相关保障要求组织成执行闭环。

行动编排接管后，来源规范只保留规则来源、保障要求来源和接管引用；执行步骤、检查清单、验证责任、证据组织、Human Gate、缺口分流、关闭判断和后续同步责任转移到接管行动编排。无 active 行动编排可定位时，不得声称该保障要求已经被接管，只能写为“建议由某行动编排接管”“待接管缺口”或“人工降级检查”。

## 13. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 将任一 v2 规范切换为 active；
2. 改变正式规范必要章节；
3. 改变 `上位依据` 或 `构成要素归属与价值判断` 章节的必要性、字段口径或判断边界；
4. 改变身份块字段、状态枚举、路径规则或 Code 消费入口；
5. 新增、删除、重命名、合并或拆分规范；
6. 改变附件命名、附件授权、附件主要信息对象或附件权威边界；
7. 改变术语归口、核心术语边界、推荐表达或不推荐表达处理；
8. 改变知识地图关系类型、派生规则或回指规则；
9. 改变专题成员自描述、成员状态判定、专属骨架或派生索引边界；
10. 将 active 规范迁移、改名、改号、合并、拆分或改变归口；
11. 将迁移来源、研究材料、工具输出、环境观察或聊天过程升级为正式规范依据；
12. 接受 Code 检查缺口、长期降级或无验证迁移。

以下情况应评估 Human Gate，并在影响目录登记、编号、权威归口、构成要素归属、价值判断、附件授权、状态闭集、保障要求类型、行动编排接管边界或 active 事实源时暂停确认：

1. 修改本文待补齐事项、保障要求或规范写作执行顺序；
2. 调整旧子文档迁移结论、附件拆分方式或暂不迁移理由；
3. 发现 v2 写作区内容与 active v1 原文、README 写作区入口或 Code 校验结果冲突；
4. 新增知识地图输入字段、诊断字段、关系来源结构、价值判断消费字段、保障声明辅助字段、行动编排接管建议字段或 Code 消费入口；
5. 新增、删除、重命名或改变任一附件中的关系类型、术语状态、表达处理方式、保障要求类型、建议接管矩阵、身份字段、身份状态闭集、辅助核对字段或 `code_consumption` 内容；
6. 后续构成要素实践试图重新定义 01 已定义的规范身份、附件、术语归口、保障声明或 Human Gate 基础规则。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 结论、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。

Human Gate 记录是人类对关键行动作出的轻量决策记录，不是独立事实模型。只有当决策本身形成后续执行对象、缺口分流、长期决策或关闭证据时，才按内容性质进入 WorkCase、ADR、Spark、Pitfall、Study、事实模型字段或其它事实源。

Human Gate 最小记录必须包含：

| 字段 | 含义 |
|---|---|
| 时间 | Human 作出决策或确认记录形成的时间；环境无法提供稳定身份时，可与“当前 Human 确认”共同记录 |
| 决策 | Human 的选择、授权、取消、暂缓、拒绝或修改反馈 |
| 范围 | 决策影响的事实源、规范、工作对象、Code、Web、运行入口、环境能力或后续流程 |
| 约束 | 决策成立所依赖的依据、限制、风险、验证要求、后续分流或回写要求 |

具体事实模型、行动编排、Web 或运行时扩展可以在上述结构上增加字段，但不得省略时间、决策、范围和约束四类最小可追溯信息。

## 14. 规范写作与修改执行顺序

AI 修改、迁移或新增 v2 规范前，必须按以下最低执行顺序处理：

1. 读取 active 工作入口、`specs-v2/README.md`、v2 00、本文和相关附件；
2. 读取目标 active v1 原文，确认真实职责、事实源边界、引用关系、保障要求、Human Gate 和 Code 消费入口；
3. 判断拟写内容的最小权威归口，不得仅凭文件名、旧编号、目录相邻或主题相近决定归口；
4. 判断是否涉及目录登记、编号、身份块、状态闭集、上位依据、构成要素归属、价值判断、附件授权、术语归口、知识地图关系、保障要求类型、行动编排接管边界或 Human Gate；
5. 涉及必须暂停事项时，先停止写入并等待 Human 确认；
6. 写入时把主体规则放入主规范正文，把长表、注册表、矩阵、模板、示例或清单放入父规范授权附件，并确保每个附件只承载一个主要信息对象；
7. 写入后核对必要章节、身份块、状态闭集、上位依据、构成要素归属与价值判断、附件授权、引用关系、保障要求、Human Gate 和待补齐事项；
8. 记录仍未迁入、未确认、无 Code 覆盖或需后续单篇核对的内容，不得宣称迁移完成。

规范治理核对至少包括：

| 检查项 | 标准 |
|---|---|
| 当前目录 | 只登记已经单篇处理的规范和附件，未把未来编号或占位文件写成事实 |
| 身份块 | 字段完整，编号、标题、路径、状态和日期一致 |
| 状态闭集 | `spec_kind`、规范 `status`、规范 `authority`、`migration_status` 属于 `01.Att.04` 闭集；附件状态属于 `01.Att.05` 闭集 |
| 上位依据 | 章节存在，与 `v2_spec.basis` 一致，真实承接上位规范，不把导航引用写成依据 |
| 构成要素归属与价值判断 | 章节存在，主归属明确，正向价值不虚构，逆向风险有边界说明 |
| 事实源边界 | v2 写作区、active 事实源、研究材料和工具输出边界清晰 |
| 必要章节 | 正式规范具备本文 §6 的必要章节 |
| 权威归口 | 稳定规则写入最小权威归口 |
| 术语与表达治理 | 术语定义和推荐表达进入 01 与术语表附件，不推荐表达和中文定语规则进入规范表达清单附件；其他规范只说明应用关系 |
| 引用关系 | 关系类型按最低充分级别使用，未反向补全下游义务 |
| 附件授权 | 附件由父规范授权，围绕单一主要信息对象，不承载主原则 |
| 子文档迁移 | v1 子文档主体规则回并主规范，长表、注册表、矩阵、模板、示例或清单才拆为附件 |
| 专题骨架 | 成员集合和专属骨架由所属主规范或成员主文件声明 |
| 规范保障要求 | 章节存在，五字段完整，保障要求类型属于 `01.Att.03` 闭集，保障机制没有把建议接管写成 active 接管事实 |
| Code 适配 | 现有检查能力、缺口、降级方式和残留风险已说明 |

规范治理核对用于发现结构缺口、事实源风险、引用错误、术语漂移和 Code 覆盖不足。核对结论只能作为诊断、待确认事项或 Human Gate 输入，不能替代 Human 确认。

### 14.1 Code 覆盖、缺口与降级

Code 是规范治理中的确定性诊断方式，不是 Human Gate，也不是每篇规范的独立必备章节。01 因定义规范身份、章节锚点、引用关系、附件身份和知识地图输入，需要说明 Code 可以消费哪些结构，以及没有 Code 覆盖时如何处理缺口。

Code 应优先消费规范中的结构化身份块、章节锚点、引用关系、附件身份、附件授权表、成员自描述和保障要求表，生成派生索引、知识地图、诊断和最小读取建议。

附件正文不得定义 Code 输出 Schema、诊断字段、命令入口、覆盖要求或降级方式。附件身份块中的 `code_consumption` 只提供消费类别提示；具体如何解析附件条目、矩阵、状态闭集、辅助核对表和正反样例，必须由本文、附件授权关系和后续 Code 规范统一定义。

v2 解析为了支持 01 的规范治理，至少应能回指以下信息；字段名、数据类型和最终输出 Schema 由后续 Code 规范单篇确认：

1. 规范节点；
2. 章节节点或章节锚点；
3. 关系边；
4. 构成要素归属和价值判断摘要；
5. 附件授权边；
6. 附件 `code_consumption` 类别提示；
7. 迁移来源和 active 事实源回指；
8. `content_hash`；
9. `line_start` / `line_end`；
10. `parse_status`；
11. `diagnostics`；
12. `review_hints`。

v2 未切换前，Code 默认校验仍以 active `specs/` 的 `ldvh_doc`、`ldvh_member`、固定章节、保障表和现有派生索引结构为准。v2 解析在切换前只能作为诊断和迁移辅助，不得替代 active 校验。01 只定义规范结构需要被 Code 读取和回指的最小方向。

当规范保障要求需要 Code 覆盖但尚未实现时，应记录 Code 缺口、人工降级方式、正反样例需求和残留风险。缺口未处理前，不得声称该结构已被完整确定性校验。
