## 1. 价值判断

本文的价值，是在具体事实类型形成前先确定共同准入、公共字段和消费边界，使 AI 能区分“需要长期保留的稳定事实”与“确实需要事实模型管理的结构化事实”，并通过一套统一的对象身份、类型、标题、时间、来源、证据和关系入口可靠地定位、关联、更新和处置事实对象，而不让各具体类型、Code 或 Web 分别创造同义字段。

本文主要服务：

1. V1 快速定位：让 AI 能从具体事实类型的定义来源定位允许的对象、位置和当前权威实例；
2. V2 充分理解：把事实对象、来源回指、证据、状态和关系放回同一类型语义中理解；
3. V3 边界识别：区分稳定事实、事实模型管理对象、具体类型规则和实现派生结构；
4. V5 据实判断：使状态、结论和更新声明不超出来源与证据实际支持的范围；
5. V6 工作接续：使需要结构化管理的事实可以跨行动、会话、执行者和阶段恢复与继续更新；
6. V8 持续积累：只把具有持续净价值的事实类型纳入模型，并在类型停止使用或对象被关闭、归档、合并、替代或删除时保留仍适用的事实。

独立建立本文，是因为事实类型是否准入、准入后共同遵守什么，以及具体事实类型的定义来源和消费实现分别负责什么，具有独立于任何单一事实类型的规则对象和失败边界。没有这层共同规则时，各类型容易重复或冲突地定义事实身份、权威位置、状态与更新边界；把这些规则交给某一具体类型、Code 或 Web，又会使局部实现反向定义整个事实模型。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：定义事实模型作为三类语义构成要素之一，在事实源边界内组织需要对象化、状态化或证据化管理的事实，并要求具体实践接受 V1–V8 价值判断；
2. `work-object-governance-scope`：定义事实所属管辖项目、工作对象和管辖范围的判断边界；
3. `source-of-truth-traceability`：定义稳定事实、来源回指、事实源写入与更新、当前 Working Tree 读取和 Git 溯源边界。

本文不得重新定义上述规范的事实源、管辖范围、稳定事实、来源回指或 Git 语义。本文作为普通规范，仍按 `specification-model-foundation` 的普遍结构和治理规则形成；该普遍约束不是本文的事实模型语义依据，因此不写入 `basis`。

历史规范、附件、实例、Code、tests 和 Web 只可作为问题与设计输入。历史名称、字段、状态、目录与对象实例不因曾经存在，就取得当前事实类型身份或规则效力。

## 3. 职责边界

本文负责定义：

1. 稳定事实进入事实模型管理的共同准入条件，以及不应对象化时的分流边界；
2. 管辖项目拥有自身 `ldvh-base/` 的唯一事实载体拓扑，以及具体事实类型及其事实对象共同遵守的身份、权威位置、来源、证据、状态、关系、发现、召回、消费、变更与处置边界；
3. 全部事实对象字段的统一登记、字段新增准入、唯一身份和适用范围，以及跨类型字段与类型专属字段的定义、引用、提升和组合规则；
4. 具体事实类型的唯一定义来源必须承担的规则范围；
5. 事实模型领域的 Helper 公开操作及其领域 `arguments`、`result`、机械校验边界和部分失败语义；
6. 规范正文、授权附件、Helper、Code、tests 和 Web 在事实模型中的权威边界；
7. 事实类型和事实对象在不成立、冲突、停止使用、关闭、归档、合并、替代或删除时的验证、Human Gate 与 Stop Conditions。

本文不负责定义：

1. 任何具体事实类型是否成立，或具体类型的目的、对象范围、增量字段、合法初态、状态值、阶段、转换边、关系类型、Schema 和文件格式；本文定义的 `ldvh-base/` 共同拓扑不构成类型准入或类型语义；
2. 某项证据是否足以证明具体领域结论、完成、通过、关闭或验收；
3. 04 统一定义的 Helper 共同请求与响应字段、Code 模块与算法、诊断码、缓存、测试文件或 Web DTO、路由和页面交互；本文只可在自身领域责任内定义事实服务公开操作的 `arguments` 与 `result`；
4. 事实源之外的信息分类、Working Tree 与 Git history 的一般边界；
5. 创建、修改、删除、提交、push 或其它外部行动的通用授权；
6. 可复用行动步骤、环境接入或项目特定强制规则。

具体事实类型的定义来源负责类型语义；相应领域来源负责成立条件与证据充分性；03 负责事实源与信息溯源；04 负责 Helper 共同请求与响应语义，本文负责事实模型领域操作语义；Code 和 tests 负责实现与确定性验证；Web 负责读取、呈现和受控交互。任何消费方都不得因实现方便而取得事实类型定义权。本文后续定义的 Helper 操作只能规定跨类型调用协议、作用范围、原子性和结果语义；当操作需要检查合法初态、状态、阶段、转换、关系或字段条件时，必须读取或忠实派生相应具体类型来源，不得在本文再建立一份类型规则枚举。

## 4. 适用范围

本文适用于管辖项目中以下场景：

1. 判断一类稳定事实是否需要由事实模型对象化、状态化或证据化管理；
2. 新建或实质修改具体事实类型的定义来源；
3. 创建、读取、关联、更新、更正、推进、关闭、归档、移动或删除事实对象；
4. Helper、Code、tests 或 Web 发现、召回、读取、解析、校验、索引、聚合、展示、消费或请求受控修改事实对象；
5. 具体事实类型准备停止新增、合并、替代或取消当前使用；
6. 当前事实对象、具体事实类型的定义来源、Schema 或派生结果之间出现冲突。

本文不要求所有稳定事实都成为事实对象。普通 Markdown 或其它符合来源规则、位于管辖项目实际 Git Working Tree 的当前文件已经能自然、清楚地保存和消费内容，且不需要对象化、状态化或证据化管理时，该内容继续按 03 作为稳定事实处理，不因缺少具体事实类型而失效。

## 5. 草案概念边界

本节定义三个双语术语；其名称和登记必须符合 `specification-model-foundation` 和当前双语术语表。

### 5.1 事实类型（Fact Type）

事实类型是对一类准备在项目中稳定保留、具有相同事实语义和实例边界，并需要按共同规则接受对象化、状态化或证据化管理的事实内容所作的语义分类。每个事实类型由当前有效的唯一定义来源定义；类型本身不是承担规范责任的文件或实现模块。类型及其定义来源成立前，候选内容是否已经是稳定事实仍按 03 判断；仅凭候选类型名称不得取得事实对象身份或类型规则效力。

事实类型不是文件扩展名、目录名、Schema 名称、前端筛选项或 Code 类名。两个对象使用相似字段不证明它们属于同一事实类型；一个历史名称或现存目录也不证明该类型已经在 V4 准入。

`事实对象类型` 与本概念指向同一语义，只作为术语表登记的中文别名；当前规则源使用首选名称“事实类型”，不得让两个名称看似承担不同概念。

### 5.2 事实对象（Fact Object）

事实对象是在已准入事实类型之下，由该类型的定义来源赋予稳定身份和当前权威位置、用于独立定位、验证、关联和更新事实内容的单位。对象身份可以在当前内容无效时继续用于定位冲突和修复目标；不满足定义来源或事实源条件的当前内容不得作为有效稳定事实消费。

事实对象必须位于 00 和 03 定义的事实源边界内。文件、YAML 映射、Markdown 区块或其它结构只有在具体事实类型的定义来源允许并满足共同规则时，才可能承载事实对象；结构化文件、对象 ID、Code 输出或 Web 记录本身不自动成为事实对象。

“事实类型”约束一类对象的共同语义，“事实对象”是该类型下的具体稳定事实单位，“稳定事实”则还包括不需要事实模型管理的内容。三者不得互相替代。

“工作对象”绑定当前事项，范围包括文件、目录、仓库、Git ref 和其它被当前行动指向的资源；“事实对象”是已经准入事实类型下可以跨行动和会话稳定定位的事实单位。当前事项指向某个事实对象时，同一资源可以同时作为工作对象和事实对象，但两种身份的成立条件与作用不同。

`事实实例 / Fact Instance` 与本概念指向同一语义，只作为术语表登记的中英文别名；当前规则源使用首选名称“事实对象 / Fact Object”。

### 5.3 事实类型标识（Fact Type Identifier）

事实类型标识是具体事实类型的唯一定义来源赋予、用于跨规范、Helper、Code、tests 和 Web 稳定引用同一事实类型的机器可读标识，机器字段为 `fact_type_key`。它只识别事实类型，不识别承担定义责任的规范、具体事实对象、目录、Schema 或实现模块，也不证明该类型已经实现或某个事实对象有效。

`fact_type_key` 使用小写 ASCII kebab-case，必须匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`。它在全部当前事实类型中唯一；类型名称、标题、路径或承载规范发生不改变类型语义的调整时保持不变，类型取消后的 key 不得改派给其它事实类型。

事实类型标识不是所有事实内容共用的全局对象 ID。每个事实对象必须按本文授权的统一字段登记保存 `fact_type_key`，其值必须与对象所属具体事实类型的当前声明完全一致；具体类型不得改用 `type`、文件目录、Schema 名称或 Code 类名表达同一公共语义。跨类型或跨消费方形成稳定引用时同样必须保留该标识。

## 6. 事实类型准入与承载位置

### 6.1 准入条件

一项候选事实类型只有同时满足以下条件，才可以完成准入。起草中的候选定义来源可以声明“拟准入”，但该声明没有当前规则效力；只有全部准入条件和独立复核通过，并且唯一定义来源进入当前规则源时，类型准入与其类型规则才同时生效：

1. 候选内容准备在管辖项目中跨行动、会话、执行者或阶段继续保留，而不是只服务当次推理、展示、缓存或执行过程；候选内容是否已经是稳定事实按 03 判断，仅凭拟准入声明不得取得事实对象身份或类型规则效力；
2. 该类内容确实需要对象化、状态化或证据化管理中的至少一种，并能说明缺少相应管理会造成的定位、理解、判断、接续或积累失败；
3. 该类内容具有可重复使用的稳定语义和对象边界；即使只有一个高价值对象，也必须存在独立身份、关系、更新或生命周期需要，而不能只因内容重要就建立类型；
4. 由普通 Markdown 或其它符合来源规则的文件承载的稳定内容、现有事实类型或其它正确承载位置不能在不混淆责任的情况下自然承担；
5. 在准入生效时具有唯一且当前有效的定义来源，能够完整定义 §10 要求的类型责任；起草阶段的候选来源只用于证明这一条件可以成立；
6. 纳入后为 AI 带来的 V1–V8 净价值，高于新增类型发现、跨来源读取、Schema 维护、迁移和实现成本；
7. 类型名称、跨规范术语和机器表示在需要时满足 01 的术语与规范责任治理要求。

文件已经结构化、历史中存在同名规范或实例、Web 已有页面、Code 已有解析器或可能实现自动化，均不能单独证明类型应当准入。

### 6.2 唯一定义来源与结构承载

具体事实类型的核心语义必须由符合 01 的当前规则源正文作为唯一定义来源承担。已有规范能够在自身责任内自然定义该类型时，可以在该规范正文中承担；确有独立规范责任时，才按 01 §13 建立新的普通规范。

授权附件只可承载父规范正文已经定义并授权的字段表、枚举或关系矩阵，不能独自定义类型目的、准入、对象边界、状态含义、证据要求、Human Gate 或 Stop Conditions。Schema、Code 常量、tests、Helper 响应和 Web DTO 必须从唯一定义来源推导，不能成为第二定义来源。

定义一个或多个具体事实类型的当前来源，必须在正文中使用唯一一个标题文本完全为 `事实类型声明` 的 H3，并使用以下真实表头逐行声明：

| fact_type_key | summary | definition_ref |
|---|---|---|

三个字段分别表示：`fact_type_key` 是符合 §5.3 的稳定事实类型标识；`summary` 是不替代正式定义的一句话类型摘要；`definition_ref` 使用 `<spec_key>::<exact-heading-text>` 指向同一当前来源正文中承担该类型完整语义的唯一 H2。类型定义统一使用 H2，使其内部可以按统一字段登记设置“准入审计引用”“类型字段使用绑定”和“类型专属字段定义”等 H3，不允许用 H3 定义类型后再制造同级伪嵌套。

Code 按以下闭集规则解析声明：

1. 每份当前规则源至多出现一个标题文本为 `事实类型声明` 的 H3；该 H3 所属章节除空白行外必须直接以声明表开始，并在下一个 H2 或 H3 前只包含这一张表；
2. 声明表必须恰有 `fact_type_key`、`summary`、`definition_ref` 三列，顺序与上述真实表头一致，不接受附加列、缺列、重复列或替代表头；
3. 每个数据行必须按 GFM 表格规则解析为恰好三个非空单元格；表格至少包含一个数据行，同一来源内不得重复 `fact_type_key`；
4. `definition_ref` 在第一个 `::` 处分为两段；前段必须与声明所在规范的 `spec_key` 完全相同，后段必须非空且不得再包含 `::`；
5. 后段按去除 Markdown 标题标记和首尾空白后的完整标题文本，在声明所在规范全文中唯一匹配一个 H2；不得指向 H3 或 `事实类型声明` 自身；
6. 被引用定义章节的范围从匹配 H2 开始，到下一个 H2 前结束。

声明表只是各类型唯一定义来源中的机器读取入口，不是平行登记表。只有声明所在规范进入当前规则源、`definition_ref` 目标存在且 §6.1 全部准入条件成立时，相应事实类型才进入当前事实类型集合。草案中的声明没有规则效力。声明 H3 后缺表、重复声明 H3、多表、空表、表头或数据行畸形时，该来源中的全部声明都不得进入派生视图；某一行的 key 格式错误、`definition_ref` 格式错误、越源、目标缺失、目标歧义或指向声明表自身时，只暂停该行对应类型；当前来源之间或同一来源内出现重复 `fact_type_key` 时，所有重复项都暂停发现和消费。Code 可以扫描全部当前规则源中的声明表形成派生视图，但不得让实现注册表、缓存或生成文件反向成为类型来源。

本文通过 `fact-object-field-registry` 附件建立全部正式事实对象字段的统一登记表。登记表是结构与字段稳定身份、当前定义位置和适用类型范围的唯一索引权威，不复制类型归口字段的完整语义；定义归口为 `foundation` 的字段由附件唯一定义，定义归口为 `type` 的字段仍由相应具体类型的唯一定义来源承担，并由登记表中的 `definition_ref` 精确回指。Code 可以从登记表和各定义来源派生 Schema、适用矩阵和检索视图，但派生结果不得成为第二字段权威。本文不建立中央事实类型清单；04 的 `capabilities` 也只发现已有当前来源的 Helper 公开操作。除非未来当前来源另行定义事实类型或字段发现操作及其契约，事实类型声明和字段登记不得被冒充为已经可通过 Helper 调用的能力。

## 7. 事实对象共同边界

### 7.1 统一字段登记与类型字段组合

本文授权 `specs/attachments/05.Att.01-事实对象统一字段登记.md` 承载结构与字段统一登记表、`foundation` 字段、来源与证据引用、关系目标、类型字段引用表和类型归口字段定义表的结构化契约。附件只展开本节已经定义的以下边界，不取得具体事实类型定义权：

1. 每个正式字段必须先取得全局唯一且不得改派的 `field_key`，并在附件统一字段登记表中登记所属结构、canonical `field_path`、JSON 类型、字段角色、值结构、定义归口、适用事实类型、唯一定义来源和状态；未登记字段不得进入类型定义、Schema、对象、Code、tests 或 Web DTO；
2. `object_id`、`fact_type_key`、`title`、`created_at`、`updated_at` 和 `source_refs` 是所有事实对象必需的公共字段；`status`、`evidence_refs` 和 `relations` 按附件及具体类型规则条件出现；
3. 字段的定义归口与适用类型是两个独立维度。`foundation` 表示字段由附件唯一定义，可以通过 `applies_to` 对全部类型保留或只供多个明确类型复用；`type` 表示字段只由一个具体类型来源唯一定义，并且 `applies_to` 恰为该类型。字段不会因为当前已完成类型数量变化而自动改变定义归口；
4. `foundation` 字段的路径、共同语义、JSON 类型和基础约束只由附件定义；具体类型只通过“类型字段使用绑定表”声明适用于本类型的 `field_key` 与 `presence`，没有差异时直接继承，确有单调收紧时用 `constraint_ref` 回指本类型唯一正文归口；绑定表不得复制路径或自然语言规则，也不得改名、放宽或改变共同语义；
5. `type` 字段的完整语义只在相应具体类型的“类型专属字段定义表”中定义，同时必须在统一登记表中保留相同 `field_key`、所属结构、字段路径、JSON 类型、唯一 `definition_ref` 和唯一适用类型。类型来源不得定义未完成统一登记的字段；
6. 类型来源可以收紧 `object_id` 格式，定义 `status` 的值与状态机，规定 `source_refs` 和 `evidence_refs` 的充分性，定义 `relations[].relation_key` 的语义、目标类型、基数和完整性，但不得改变公共入口的名称、JSON 类型或共同边界；“收紧”只允许增加本类型成立条件，不得否定共同语义或使同一字段在不同类型回答不同问题；
7. 派生 Schema 必须从附件登记的结构身份开始，由结构成员、适用于该类型的事实对象直接字段、每个字段的唯一语义定义和类型使用绑定单向组合；结构成员随容器引用继承，不得在各类型重复绑定；不得把五份复制后的完整 Schema 当作五个互相独立的字段权威；
8. 修改 `applies_to: *` 的基础字段必须评估全部当前事实类型；修改只供部分类型复用的 `foundation` 字段必须评估全部适用类型；修改 `type` 字段必须评估其唯一类型及消费者。任何变更都必须先更新统一登记及唯一来源，再评估对象、Helper、Code、tests 和 Web 的同步或迁移范围，不得用局部兼容字段规避共同变更；

### 7.2 字段新增准入与提升

任何具体类型提出正式字段或 JSON object 结构前，必须检索附件登记的全部 `current` 与 `retired` 字段和结构，并比较字段或结构回答的问题、不承载的语义、JSON 值形态、成员闭集、生命周期、来源与证据、出现条件、未知值和更新规则；只比较名称、路径或实现 shape 不成立。聊天、记忆或尚未回写的 agent 输出不能作为查重全集。

字段提案只能得到以下四种结论之一：

1. 现有字段能够无损承接时，复用现有 `field_key`；不得因命名偏好、类型归属或实现方便创建别名；
2. 现有 `definition_scope: type` 字段被第二个类型需要时，先在同一变更中将其定义归口提升为 `foundation`、把唯一共同定义迁入附件并更新 `applies_to` 与全部使用绑定，再由新类型引用；不得先复制后整理；
3. 相似字段实际语义不同且不能形成共同基线时，保留或建立不同字段，但必须记录差异边界，避免同名异义；
4. 全部现有字段都不能无损承接时，才可以创建新的类型归口字段，并在同一变更中完成唯一 `field_key`、类型来源定义、统一登记和使用绑定。

字段提升到 `foundation` 后不得因为后续新增类型不使用而降回类型来源；`applies_to` 只按实际复用范围扩展或经显式退出决定收缩。字段从适用范围退出、拆分、合并、改名或改变身份语义时，必须显式处理已有对象和引用。`retired` 登记行是永久 tombstone，不得删除；字段查重始终包含它，旧 `field_key` 及其“所属结构 + canonical 路径”均不得改派。重新需要 retired 语义时必须形成显式恢复或替代决定。异名同义字段不得并存；同名异义字段不得在同一所属结构中共用 canonical 路径。

结构使用同一四结论准入和提升规则：首次只服务一个类型时由该类型唯一定义；第二个类型需要复用时先提升到附件 `foundation` 定义，再更新适用范围和全部成员字段。结构只表示 JSON object 成员闭集，array 字段通过 `value_structure` 引用 item object 结构。结构提升、拆分、合并、改名、retired tombstone、身份不得改派和 current/retired 全量查重要求与字段相同；不得创建同义 `structure_key` 绕过字段查重。

Code 负责枚举完整登记、检查 `field_key`、`structure_key` 和定义唯一性、精确名称或路径冲突、引用、类型、适用范围、成员出现规则与 Schema 组合；AI 负责比较字段与结构的自然语言语义，并形成复用、提升、区分或新增判断。Code 不得根据关键词、相似度、embedding 或其它启发式自动裁决语义等价。语义仍有歧义、涉及破坏性迁移或改变全部类型共同边界时进入 Human Gate。

具体类型的当前推进顺序属于架构推进计划，不属于本文的长期事实模型语义。无论采用何种推进顺序，一个类型只有在自身语义、对象边界、全部字段与结构准入、状态、来源、证据、关系、验证和独立复核完整形成后，才能作为后续类型查重的已完成输入。

### 7.3 对象成立与稳定引用

每个事实对象必须同时满足：

1. 所属具体事实类型已经准入，能够通过 `fact_type_key` 唯一回到其当前有效的定义来源；
2. 对象位于对应管辖项目的 Git worktree 和该类型允许的事实源位置；
3. 对象通过公共字段 `object_id` 具有在同一管辖项目和同一事实类型范围内唯一且稳定的身份；具体类型可以收紧格式，但不得改用标题、路径、`fact_type_key` 或其它字段替代对象身份；
4. 对象的当前权威位置唯一；副本、索引、缓存、摘要、聚合和 Web 视图不得与当前对象形成并行权威；
5. 当前 Working Tree 内容可以按该类型的定义来源解析，并满足适用字段、状态、关系和验证要求；
6. 对象能够回指理解其当前内容所需的来源和形成依据；发生更新后必须回读实际 Working Tree 内容，是否长期保存更新历史由该类型的定义来源决定；
7. 对象的结论、状态与声明没有超出当前来源和证据实际支持的范围。

### 7.1 管辖项目的 canonical 事实载体拓扑

每个管辖项目在自身仓库根目录拥有唯一的 `ldvh-base/`；LDVH V4 作为一个管辖项目也遵守同一拓扑。当前五类 V4 事实对象的唯一 canonical 相对路径为：`ldvh-base/sparks/<object_id>.yaml`、`ldvh-base/workcases/<object_id>.yaml`、`ldvh-base/adrs/<object_id>.yaml`、`ldvh-base/pitfalls/<object_id>.yaml` 与 `ldvh-base/studies/<object_id>.md`。`ldvh-base/` 不是跨项目共享仓库、缓存、导入区或历史兼容层；项目 A 的对象不得以项目 B 的 `ldvh-base/` 作为权威载体。

此共同拓扑只规定存储归属和路径根，不继承或恢复任何历史字段、状态、文件命名、目录附加层级或实现。具体类型仍由其唯一定义来源决定对象语义、字段、状态、文件后缀及其目录中的合法对象。仓库根级 `facts/` 不是 V4 事实对象的 canonical 路径，不得被读取器、写入器、校验器、Web、测试或迁移兼容逻辑作为第二来源。

具体事实类型的定义来源必须确定对象粒度、身份稳定边界、允许位置以及一文件一对象、多对象同文件或其它承载方式。本文不预设文件与对象的数量关系，也不规定 YAML、Markdown 或其它格式。

事实对象的稳定引用至少必须能还原为“当前选定管辖项目配置中的项目 `id` + `fact_type_key` + `object_id`”。项目 `id` 只在其所属配置内唯一；引用需要跨工作区配置解释时，还必须按附件保留配置来源以及 02 要求的项目身份依据，不能假定不同配置中的同名项目 `id` 指向同一项目。该引用规则用于消除跨项目和跨类型歧义，不要求把三部分写进同一个字符串。

重命名、移动或结构迁移不得无意改变对象身份。多个当前位置声称承载同一对象、多个对象重复使用同一身份，或者对象身份只能靠标题、路径相似与 Code 猜测时，不能选择较新、较近或较方便的一份静默继续。

## 8. 来源、证据与关系

1. 事实对象必须遵守 03 的来源回指和信息溯源规则；具体事实类型的定义来源负责定义对象需要保留哪些来源、在什么条件下必须包含版本、观察时间、输入范围或其它上下文；
2. 来源回指只证明能够回到形成依据，不单独证明内容正确或证据充分；具体领域成立条件和该类型的定义来源共同决定可接受依据与可证明范围；
3. 当次观察、Human 指令、聊天、AI 推理、命令或测试输出可以成为事实对象写入或更新的输入，但必须按 03 和具体事实类型的定义来源完成写入、校验与回读后，才能在实际成立范围内作为稳定事实消费；
4. 对象形成依据统一通过公共字段 `source_refs` 保留；需要把特定依据明确标记为支持结论、验证或状态的证据时，统一通过 `evidence_refs` 关联。两者成员使用附件定义的同一引用结构，但字段作用不得互换；具体类型负责定义哪些来源和证据在何种条件下必须出现及何时充分；
5. 事实对象之间的关系统一通过公共字段 `relations` 表达，每项保留关系方向、类型和可稳定定位的目标；关系类型、基数、跨项目边界、目标缺失与循环是否合法，由定义该关系语义的具体事实类型定义来源负责，并且不得与目标类型的定义来源冲突；不得重新建立 `related_sparks`、`related_workcases` 或其它按目标类型分裂的同义公共字段；
6. 索引、反向关系和聚合可以由 Code 派生，但必须回指当前对象和来源规则，不得反向增加事实关系或改变事实语义。

来源存在、证据数量、Human 验收、测试通过或 Git commit 均不能脱离具体成立条件单独证明对象结论或状态成立。

### 8.1 事实对象发现、召回、展开与语义消费

事实对象被创建后，只有在后续行动中能够于正确时机被重新发现、读取和语义消费，才实际形成跨行动价值。该链路必须区分四个不可互相替代的结论：

1. **发现**：在已确定的管辖项目和实际 Working Tree 中，枚举符合当次结构化条件的对象引用和最小候选信息；
2. **召回**：在当前行动、对象、主题或 lifecycle 时机下，把少量可能相关的候选提供给 AI，并保留候选命中依据与未检查范围；
3. **展开**：对 AI 选中或当前输入精确引用的对象，从唯一当前权威位置读取完整内容并完成已实现的机械检查；
4. **语义消费**：AI 依据具体类型来源、当前目标、对象内容、状态、来源、证据、适用边界和现时环境，判断该事实能否以多大范围影响当前行动。

精确事实引用、当前工作对象、来源 locator、对象关系、类型、状态、标题与当前来源已明确交给 Code 的可检索文本，可以作为确定性发现或候选缩小依据。Code 必须返回实际命中依据，不得根据关键词权重、相似度、embedding、LLM 输出或其它启发式自动裁决两段自然语言是否语义相关、对象是否适用或结论是否仍当前。AI 也不得因为候选被返回、文件机械有效、文本相似或对象状态非终态，就把它宣称为当次适用事实。

事实信息的渐进式披露使用以下五层。层级只表示 AI 当次获得的信息深度，不新增事实对象字段，也不预先定义 Helper API：

| 层级 | 内容 | 直接用途 | 不能单独证明 |
|---|---|---|---|
| F0 恢复清单 | 当次管辖项目、实际 worktree/common-dir、各类型/状态数量、Schema 与对象集指纹、当前工作对象引用、已选对象、coverage 和未完成 cursor | 确认恢复边界、过期与未检查范围 | 任何具体对象相关、适用或内容未变 |
| F1 基础卡片 | 具体类型来源要求在会话建立或恢复时完整审阅的全部最小权威字段投影 | 建立当前决策约束和未关闭责任全貌 | 对象全文已读、已适用或已授权行动 |
| F2 候选卡片 | 按类型、状态、引用、关系、locator 或允许字段精确文本命中的少量对象、最小权威字段、命中依据，以及具体类型确有需要时从完整文本形成的有界确定性摘录 | 让 AI 在不读取全部正文时筛选可能相关对象并决定是否进入 F3 | 语义相关、现时适用、结论当前、被摘录字段已经完整读取或事实源内容应保持短小 |
| F3 完整对象 | 对象当前权威文件的全部内容与已实现机械检查 | 完成对象语义、状态、适用与限制判断 | 来源真实、证据充分、外部事实当前或行动获授权 |
| F4 来源证据 | 只对影响当次适用、决定、验证或当前性的必要 source/evidence locator 进行展开 | 核对具体声明及其来源、版本、观察时点和范围 | 未展开引用也已核对，或对象全部声明都当前 |

召回是候选与基础上下文的提供机会，不是把当前项目全部事实对象正文永久注入 AI 上下文。消费方应先取得 F0，再按类型来源完成当次必需的 F1，其它对象先进入 F2，只对 AI 选中对象按需展开 F3 和 F4。F1 可以要求“全部对象的最小卡片”，与不全量注入正文不冲突。任何分层结果的数量、排序、分页、截断、指纹、无效/不可读对象和未检查范围都必须可观察；超过资源或上下文边界时应分页、继续缩小或报告 partial，不得静默截断后声称已全量召回。F2 的确定性摘录只属于 Helper 派生输出，必须保留原字段路径、固定预算、是否完整和 F3 稳定引用；它不得写回事实对象、由 AI 重写、替代 F3，或反向要求事实源把完整内容压缩到卡片预算内。

在管辖项目和实际 Working Tree 成立后，新会话开始、会话恢复和上下文压缩后恢复都必须重建 F0，并完整审阅当前项目全部 `active` ADR 与全部 `open`/`blocked` WorkCase 的 F1。若当前工作对象精确绑定一个 WorkCase，还必须展开该对象及其直接 `open`/`blocked` 依赖到 F3。压缩恢复还必须重新回读当次已判断适用的 ADR、仍影响行动的 Pitfall、已引用 Study 结论的版本/观察/限制边界、相关 `open` Spark，以及未完成分页与未检查范围。旧摘要、缓存或压缩前文本只能用于恢复精确引用，不替代当前 Working Tree 回读。

环境共享恢复消费 F1 时必须继续全部 `next_cursor`，并在每页之间保持同一查询、Schema 指纹和对象集指纹；任一 `partial`、cursor 失效、无效或不可读对象、资源/时间预算中断都使当前 coverage 保持未完成。未完成时不得把已返回的零张、一张或多张卡片解释为当前全部责任。Helper 仍按 §11.5–11.6 接收并回显精确恢复引用；WorkCase 当前绑定、唯一机械候选的非绑定展开及 `active_items[]` 字段唯一按 21 §7 解释，环境交付投影和 adapter 映射唯一按 09 §5.1 解释，Code 不成为第二份合同权威。

完整 Helper coverage 不等于必需 F1 已全部交付给 AI。受环境上下文或交付投影预算限制时，无法容纳的必需 F1 卡片必须使 `delivery_coverage` 保持 `incomplete`，并显式返回总数、已交付数、省略数、来源和继续展开入口。不得静默截断后声称已完整审阅 F1，也不得用 byte 预算改写 Helper 实际 coverage。

新的独立 AI 执行上下文如尚未对同一管辖项目和实际 Working Tree 按本节重建 F0、完成必需 F1 审阅，也按新会话处理；父执行者摘要、任务描述或环境继承标记不能单独证明恢复完成。

目标环境明确提供 startup、resume、compact 或等价 lifecycle 事件时，薄环境入口可调用同一 Helper 恢复链路；环境没有相应事件时，必须由 AI 在开始或发现上下文缺口后重新调用。任何一种环境的 Hook 事件名都不得反向定义上述恢复语义，环境缺少 compact 事件时也不得声称已普遍自动恢复。

具体类型的唯一定义来源必须定义：哪些当前目标、语义情形、显式引用、关系或 lifecycle 时机应产生本类型的召回机会；各状态对象何时进入默认候选、仅作历史或仅在精确引用下展开；展开后必须核对哪些适用、时效、证据或安全边界。本文不建立所有类型共用的触发词、时间间隔、相关性分数、默认数量或状态排序闭集。终态对象不得一律丢弃，非终态对象也不得无差别注入；其实际作用由对象类型、状态语义、当前场景和精确来源共同决定。

被当前对象的 `source_refs`、`evidence_refs` 或 `relations` 精确指向的其它事实对象，无论是否终态，都进入按需引用闭包；这只使其可按支持当次理解所需层级展开，不使终态内容恢复当前效力。

当前 `read-fact-objects` 只对已知稳定引用执行展开和机械检查，不实现发现或召回。本节不因定义语义模型而使新的 Helper 公开操作、候选索引、环境触发或上下文注入能力自动成立；这些能力必须在后续增量中另行定义预算、请求结果契约、失败语义、实现与范围匹配测试。

## 9. 状态与事实对象变更

### 9.1 状态边界

事实类型只有在其对象确实存在需要跨行动接续、影响消费或约束更新的语义阶段时，才定义状态。并非每个事实类型都必须有状态字段或状态机。

需要状态时，具体事实类型的定义来源必须定义：

1. 状态集合及每个状态的语义；
2. 初始状态如何成立；
3. 允许和禁止的转换；
4. 每次转换所需的来源、证据、验证和必要授权；
5. 转换失败、部分写入和当前状态无法判断时的处理；
6. 终止、关闭、归档或其它处理方式是否存在及其语义。

本文不规定任何通用状态名称、机器值、顺序或终态。文件存在、Git tracked/untracked/dirty、commit 创建、命令成功、测试通过、Human 回应或 Web 展示状态，不自动等于事实对象的领域状态或状态转换。

### 9.2 更新规则

新建、修改、更正、关系变更或状态转换必须依次确认：

1. 目标事实类型已准入，唯一定义来源和对象当前权威位置明确；
2. Human 当前指令已经授权，且适用于该行动的全部来源规则许可条件已经成立；
3. 输入信息的作用、来源回指和证据范围清楚，没有把推测改写成已证实事实；
4. 更新后的身份、字段、状态和关系满足该类型的定义来源；
5. 写入使用实际可用的入口完成，没有用计划、请求或工具成功替代实际结果；
6. 写入后回读当前 Working Tree 中的目标内容，并按该类型的定义来源完成验证；
7. 失败、部分成立、未验证范围和残留风险按实际结果保留，没有扩大成功声明。

更正事实内容与推进对象状态可能具有不同成立条件；具体类型需要区分时必须分别定义，不能把任意内容修改自动解释为状态推进。本文也不因定义更新规则而授予任何消费方通用写入或删除权限。

### 9.3 关闭、归档、合并、替代与删除

具体事实类型的定义来源必须分别定义是否允许关闭、归档、合并、替代或删除，以及每种实际存在的行为如何成立、处理后是否仍可作为历史或参考信息消费、仍适用事实的承接位置和恢复边界。本文不把这些性质不同的行为合并为统一状态或统一机器动作。

关闭或归档不等于文件必须删除，也不等于其历史内容失效。删除、合并或替代不得丢失仍需接续的事实、来源、证据和关系；没有来源规则明确允许时，不得用“已完成”“已过时”或实现清理需要推定对象可以删除。

## 10. 具体事实类型的责任边界

每个具体事实类型的唯一定义来源至少必须定义：

1. 类型目的、准入理由、V1–V8 净价值和与由普通文件承载的稳定内容、相邻类型的边界；
2. `fact_type_key`、适用的管辖项目或工作对象范围，以及来源如何被定位；
3. 事实对象表达什么、对象粒度、稳定身份、允许位置和当前权威位置；
4. 回指本文统一字段登记，先通过准入审计引用所指的结构化证据证明每项信息需求已经全局查重，再通过类型字段使用绑定引用现有字段，并只在确实新增 `definition_scope: type` 字段时建立类型专属字段定义；必须说明未知内容处理、Schema 组合位置、生成方式和一致性验证，不得复制 `foundation` 字段定义；
5. 是否需要状态；需要时的状态集合、语义、转换、验证以及关闭或归档方式；
6. 来源回指、证据、关系、可接受依据和可证明范围；
7. 发现、召回、展开与语义消费时机，各状态的候选边界，以及创建、读取、更新、更正、关联、合并、移动、归档和删除中实际适用的行动边界；
8. 验证要求、Human Gate、Stop Conditions，以及失败和部分成立时的最小影响范围；
9. 类型停止新增、合并、替代或取消时，现有对象与仍适用事实的处置方式。

上述清单规定必须回答的语义问题。字段身份和跨类型结构只由本文及其附件统一规定；具体事实类型的定义来源只有在本类型语义确实需要、完成全局字段检索且不能复用时才建立类型专属字段、状态值、关系类型或行动边界，不得为了填满模板制造结构，也不得重新定义公共入口。

具体类型来源是其合法初态、状态与阶段闭集、转换边、转换成立条件、字段失效、关系语义和召回投影的唯一语义权威。本文、附件、行动模板、Helper、Code、tests 和 Web 可以回指、投影或机械执行这些规则，但不得复制后形成可独立修改的第二权威；跨类型 Helper 契约需要描述能力边界时，应引用对应类型章节，并只补充该操作特有的单对象、多对象、CAS、原子性、失败和结果语义。实现确需使用派生常量时，必须明确其来源归属并以范围匹配测试防止与具体类型来源漂移。

事实模型基础只定义共同准入和共同边界，不代替具体类型的唯一定义来源。Human 已确认当前 V4 需要 Spark、WorkCase、ADR、Pitfall 和 Study 五个类型，不再重复审核这五个类型是否建立；它们仍必须分别明确领域语义、对象边界、字段、状态、来源、证据和验证规则。未来提出这五类以外的新事实类型时，仍须与普通 Markdown 和现有类型比较并按 §6.1 完成准入。

### 11.1 事实对象读取输入字段

本操作使用 04 定义的共同请求对象，并复用 02 `resolve-governance-scope` 对 `work_object_locators`、`arguments.workspace_root`、配置、路径和 Git 身份的解释。`work_object_locators` 缺省或为空时使用 Helper 进程实际 `cwd`；非空时每项必须是非空路径 string。每个定位输入都必须完成并形成 `governed` 结果，且全部结果必须属于同一 `governed_project_id` 和同一实际 `git_worktree_root`；任一定位输入未完成、不是 `governed`、形成混合或多项目范围，或者同一项目落在不同 worktree 时，都不读取任何事实文件。同一项目的不同 worktree 不得合并或由登记项目路径替代。不能形成唯一读取边界时，按 04 报告全部事实引用未完成范围和实际管辖结果。

领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全使用 02 §10.1 的配置选择语义，不表示该目录本身是事实对象位置 |
| `fact_refs` | array | 必填且 1–128 项；成员使用下表闭集 | 按稳定三元组精确选择对象；保持输入顺序，重复项不合并，不接受路径、标题、关键词或相似性回退 |

`fact_refs[]` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `governed_project_id` | string | 必填非空 | 目标在本次所选配置中的项目 `id`；必须与实际管辖解析结果核对 |
| `fact_type_key` | string | 必填；必须精确匹配当次当前来源中已准入的一类 | 决定 20–24 中的载体、目录、扩展名、对象 ID 和机械约束，不做别名或大小写修正 |
| `object_id` | string | 必填非空 | 目标类型范围内的稳定对象身份；必须满足该类型来源定义的格式 |

每个输入成员按原始顺序取得从零开始的 `fact_ref_index`，并以该序号区分重复三元组。未知共同或领域字段、空 `fact_refs`、成员字段闭集或 JSON 类型错误、未知 `fact_type_key`、不符合相应类型格式的 `object_id`、非绝对 `workspace_root`、非空 `observed_context`、非空 `authorization_reference`，或者非 `null` 的 `requested_disclosure`，均使用 `invalid_request`；不得通过尝试路径或猜测类型修正请求。`task` 可以出现但不参与项目、Working Tree、类型或对象选择。

共同 `scope.requested`、`scope.completed` 和 `scope.not_completed` 对每个事实引用使用相同 object 成员闭集：`fact_ref_index` 为原始非负 integer 序号，`requested_ref` 为字段闭集与 `fact_refs[]` 相同的 object。每个输入成员先进入 `requested`，再按其逐项结果进入 `completed` 或 `not_completed`；不得只写 integer、合并重复引用或用路径替代原始稳定三元组。

### 11.2 事实对象读取结果字段

领域 `result` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `items` | array | 已形成唯一读取边界时必填且与 `fact_refs` 等长；按 `fact_ref_index` 排序 | 每个请求引用恰有一项；局部坏文件、缺失对象或技术未完成不得吞掉其它项 |

`items[]` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `fact_ref_index` | integer | 必填且不小于零 | 对应原始 `fact_refs[]` 序号 |
| `requested_ref` | object | 必填；字段闭集与 `fact_refs[]` 相同 | 原样回显精确三元组，不提升未知身份 |
| `canonical_path` | string 或 null | 必填；能够从当前类型与合法身份确定时为 Git 相对 POSIX 路径 | 只表示类型来源定义的唯一预期位置，不证明文件存在、可追踪或有效 |
| `carrier` | string 或 null | 必填；只允许 `yaml`、`markdown` 或 `null` | 回显类型来源定义的载体；无法安全确定时为 `null` |
| `check_status` | string | 必填；只允许 `mechanically_valid`、`invalid`、`not_found` 或 `unavailable` | 分别表示已通过全部当次已实现且适用的机械检查、已完成检查但对象不成立、预期位置不存在，或技术条件使检查未完成 |
| `fact_object` | object 或 null | 必填；只在 `mechanically_valid` 时非空 | YAML 类型返回对象映射；Study 返回字段闭集为 `frontmatter` object 与 `body` string；不得把正文并入 frontmatter 或把本结果当作第二 Schema |
| `content_fingerprint` | string 或 null | 必填；只在 `mechanically_valid` 时为 64 位小写十六进制 string | 对当次安全读取的完整 UTF-8 载体 bytes 计算 SHA-256，仅作为后续单对象 CAS 的过期检测条件；不是对象身份、Git 版本或内容语义等价证明 |
| `issues` | array | 必填；无问题时为空 | 成员使用下述机械问题字段；只陈述已观察的失败或未完成，不作自然语言领域裁决 |
| `source_refs` | array | 必填且至少一项；成员直接复用 04 授权附件的“来源回指字段”闭集 | 回指类型来源、实际 Working Tree 文件或支持本项结果的路径/Git 观察；不得用 `HEAD` 或其它 worktree 替代当前内容 |

`issues[]` 使用字段闭集：`category` 为 `location`、`git-traceability`、`parse`、`schema`、`identity`、`reference` 或 `relation` 之一；`field_path` 为能够定位字段时的非空 string，否则为 `null`；`summary` 为非空 string；`source_refs` 为至少一项且成员直接复用 04 授权附件的“来源回指字段”闭集。分类只稳定区分机械责任，不形成自然语言事实错误的通用闭集。

对象文件必须位于目标实际 worktree 中；从 worktree 根到 canonical path 的任何现有路径组件及叶节点都不得是符号链接。单个文件的 Git 状态不决定其进入当次机械检查或成为稳定事实的资格。读取不得回退 `HEAD`、Index、登记项目路径、同仓库其它 worktree 或缓存。

首个实现增量的确定性资源边界为：单次最多 128 个 `fact_refs`，单个事实载体最多 4 MiB，单次关系图遍历或单类型全集扫描最多 10,000 个对象。超出请求项数按 `invalid_request`；已经形成读取边界后遇到载体或关系图预算上限时，相应对象使用 `unavailable` 并进入共同未完成范围，不得截断后按已完成或有效报告。该边界只限制 Helper 调用资源，不改变事实对象或类型语义。

`mechanically_valid` 要求：预期位置与文件身份成立，载体可解析，字段和递归结构闭集、JSON 类型、必填/禁止/非空、明确枚举、时间不等式、引用 shape 以及当前来源明确交给 Code 的类型条件全部通过；需要对象全集才能判断的目标存在、重复身份、基数和 DAG 只在实际完成对应全集检查时进入该结论。尚未实现或本次不能完成的适用机械检查必须使受影响项成为 `unavailable`，不得降级为通过。单个对象的失败不使其它已完成项失效。

读取边界未形成时 `result` 固定为 `null`，全部事实引用 scope member 进入 `not_completed`。读取边界已经形成后，`invalid` 和 `not_found` 是检查已经完成的领域结果，相应 scope member 进入共同 `scope.completed`；只要全部项均形成 `mechanically_valid`、`invalid` 或 `not_found`，外层使用 `outcome: ok`。`unavailable` 进入 `scope.not_completed`；同时存在已完成项时使用 `partial`，没有任何项完成时再按 04 区分 `unavailable` 或 `error`。共同 `scope.governance_resolution` 必须承载当次完整管辖解析结果；`changes` 固定为空。共同 `verification` 只列实际执行并有依据的机械检查，`gaps` 和 `diagnostics` 保留技术未完成与未证明范围，不得用 `outcome: ok` 或本操作结果冒充事实语义已经由 Code 确认。

### 11.3 事实对象草案准备输入与结果

`prepare-fact-object-draft` 是无事实源副作用的读取操作。它只在一个已解析的管辖项目和一个实际 Git Working Tree 中，为 AI 已经选择的事实类型返回当前派生字段契约、载体、候选身份和草案依据；不创建 canonical 文件、不预留身份、不写 allocator、Git ref、配置、缓存或其它持久状态。AI 仍负责依据具体类型来源判断是否值得对象化、类型是否正确、自然语言字段如何填写、来源和证据是否充分。

领域 `arguments` 只允许：可选绝对路径 `workspace_root`、必填非空 `governed_project_id`、必填且精确匹配当前五类之一的 `fact_type_key`。`work_object_locators` 与唯一读取边界沿用 §11.1；`observed_context`、`authorization_reference` 必须为空，`requested_disclosure` 必须为 `null`。结果字段闭集为：`governed_project_id`、`fact_type_key`、`candidate_object_id`、`candidate_canonical_path`、`carrier`、`schema_fingerprint`、`worktree_fingerprint`、`managed_fields` 和 `field_contracts`。`managed_fields` 固定为 `object_id`、`fact_type_key`、`created_at`、`updated_at`；AI 不填写这些字段。`field_contracts[]` 只投影当前来源派生字段的 `field_path`、`json_type`、`presence` 和 `constraint_ref`，不复制字段语义。`constraint_ref` 精确回显类型绑定中的 `inherit` 或同一类型正文 H2 回指，使 AI 能够回到条件来源；Code 不解析该自然语言正文，也不得把 `presence: conditional` 解释为“任意省略均合法”。

候选身份只表示准备时观察到的下一顺序编号，不形成预留、稳定引用或成功承诺。多个调用可以得到同一候选身份；正式创建必须重新分配并返回实际身份。草案依据必须同时绑定当次 `governed_project_id`、实际 `git_worktree_root`、`git_common_dir`、事实类型和派生 Schema；创建时任一绑定变化都必须拒绝旧草案，不得静默移植到另一 worktree 或旧 Schema。

### 11.4 事实对象受控创建输入与结果

`create-fact-object` 是一次只创建一个对象的状态变更操作。领域 `arguments` 只允许：可选绝对路径 `workspace_root`；必填 `draft_basis` object；必填 `fact_object` object。`draft_basis` 必须精确包含 `governed_project_id`、`fact_type_key`、`candidate_object_id`、`schema_fingerprint` 和 `worktree_fingerprint`，并来自 §11.3 的实际结果。YAML 类型的 `fact_object` 是待创建字段 object；Study 的 `fact_object` 精确包含 `frontmatter` object 与非空 `body` string。AI 提供的字段中禁止 `object_id`、`fact_type_key`、`created_at` 和 `updated_at`；Code 在最终分配身份时写入这四项，其中两个时间使用同一个带时区 RFC 3339 创建时点。AI 必须提供其余当前必填字段、来源、证据和自然语言内容，不得提交空值或占位内容。

本操作只接受相应具体类型来源在其生命周期章节明示的合法创建初态，并机械检查该初态的全部条件；05 不另行枚举各类型初态。当前来源分别为 20 §6、21 §6、22 §6、23 §6 和 24 §6，其中 WorkCase 来源明确允许在附加阻塞条件成立时以 `blocked` 创建；WorkCase 的最终 Code 托管 `created_at` 还必须按 21 的精确兼容边界选择对应 profile，等于或晚于边界的新对象不得借 legacy 读取兼容创建。首版受控创建不接受 `supersedes`，因为该关系要求目标状态与多个对象在同一获准变更中共同成立；它必须由后续多对象原子变更能力承接。其它创建时允许的关系仍须完成目标、状态、时间、自指和 DAG 检查。Code 不得根据正文推断类型、状态、来源充分性或字段语义，也不得因 Schema 通过而宣称对象值得创建。

full-v4 Working Tree 测试证据 DTO 的唯一字段与比较契约属于 07 及其授权附件，不是事实对象共同字段、类型专属字段或本登记的结构。05 只约束承载该 DTO 的事实读写边界，不复制或另行授权其字段。

最终身份由 Code 在创建临界区分配。顺序编号在同一管辖项目的同一 `git_common_dir` 内使用“项目 + 类型”共享排他锁和单调 allocator；allocator 必须先对全部可见 linked worktree 的既有身份取上界，分配后的编号永久不复用并允许因失败或崩溃产生跳号。目标文件必须使用原子 no-overwrite 创建；已存在的文件、符号链接、手工并发写入或候选身份过期均不得被覆盖。不同 clone 或不同机器不共享本地锁，首版只在后续合并前通过全局身份扫描拒绝冲突，不声明跨 clone 唯一分配已经解决。

正式写入前必须重新确认管辖、worktree/common-dir、Schema fingerprint、初始状态、完整载体、字段、时间、引用、关系和目标路径；写入后必须使用 `read-fact-objects` 的同一机械边界回读实际 Working Tree。写后回读失败时只可在确认目标仍是本次原子创建内容时尝试删除回滚；回滚成功报告未创建，回滚失败则报告实际残留文件和未完成验证，不得返回 `ok`。

成功结果字段闭集为：`requested_candidate_id`、`actual_ref`、`canonical_path`、`carrier` 和 `fact_object`；`actual_ref` 使用 §11.1 的稳定三元组。创建调用的 `scope.requested`、`scope.completed` 与 `scope.not_completed` 均以原始 `draft_basis` 作为同一范围成员；成功时该成员进入 `completed`，最终身份只进入 `result.actual_ref`、`changes.target` 与 `verification.scope`，不得用新身份替换请求范围。共同 `changes` 使用 `status: created` 回指实际路径；共同 `verification` 回指写后读取结果。草案过期、Schema 或 worktree 变化、初始状态或语义字段机械不成立、`supersedes` 出现、授权或来源规则不允许时不得写入，并按 04 区分 `invalid_request`、`rejected` 或 `unavailable`。请求成功只证明一个新文件已经原子创建并通过当次机械回读，不证明自然语言事实真实、证据充分、Human Gate 已完成、Git 已提交或上层工作完成。

### 11.5 事实对象候选发现输入字段

本操作复用 §11.1 的 `work_object_locators`、`arguments.workspace_root`、管辖解析和唯一实际 worktree/common-dir 边界。领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全复用 02 的配置选择语义 |
| `governed_project_id` | string | 必填非空 | 必须与实际管辖项目精确一致 |
| `card_layer` | string | 必填；只允许 `F1` 或 `F2` | `F1` 固定形成恢复基线；`F2` 按确定性条件缩小候选 |
| `fact_type_keys` | array | `F2` 必填且 1–5 个互异当前类型；`F1` 禁止 | F2 扫描类型范围，不改变类型语义 |
| `statuses` | array | F2 可选；出现时 1–9 个互异非空 string | 只保留其实际状态精确命中的对象；省略时按 20–24 使用 Spark `open`、WorkCase `open/blocked`、其它三类 `active` |
| `exact_refs` | array | F2 可选；最多 128 个互异成员 | 成员使用 §11.1 稳定三元组；出现时只保留精确对象，且可使显式选择的终态进入候选 |

| `current_workcase_ref` | object | 可选；使用 §11.1 稳定三元组且类型必须为 `workcase` | 回显 AI 或上层入口已知的当前工作责任，供 F0 恢复和后续 F3 精确展开；不由 Code 猜测绑定 |
| `selected_fact_refs` | array | 可选；1–128 个互异稳定三元组 | 回显压缩前或上层入口已明确选择的事实引用，供恢复后重新读取；不证明仍相关或适用 |

`F1` 不接受任何 F2 过滤条件，固定扫描全部 `active` ADR 和全部 `open`/`blocked` WorkCase，并按 `(fact_type_key, object_id)` 升序分页。F2 各过滤类别之间为 AND，同一类别多个成员为 OR；`exact_refs`、`relation_targets` 中的项目必须等于 `governed_project_id`，`exact_refs` 的类型必须位于 `fact_type_keys`，关系目标可以是任一当前事实类型。显式 `statuses` 与 `exact_refs` 同时出现时仍必须同时满足；终态不会因精确引用自动绕过显式状态过滤。

### 11.6 事实对象候选发现结果字段

领域 `result` 使用字段闭集：`recovery_manifest`、`cards`、`coverage`。`recovery_manifest` 是 F0，字段闭集为：

| 字段 | JSON 类型 | 含义 |
|---|---|---|
| `governed_project_id` | string | 当次实际管辖项目 |
| `git_worktree_root`、`git_common_dir` | string | 当次实际 Git 身份的绝对路径 |
| `schema_fingerprint`、`object_set_fingerprint` | string | 当前五类型派生 Schema 与被扫描对象集合的 SHA-256 指纹；只用于过期检测，不成为事实身份 |
| `counts` | array | 按类型和状态升序列出机械有效对象数量；每项字段闭集为 `fact_type_key`、`status`、`count` |
| `current_workcase_ref`、`selected_fact_refs` | object 或 null；array | 原样回显请求中的恢复指针；前者未提供时为 `null`，后者未提供时为空数组；不提升为候选命中或事实适用结论 |
| `invalid_objects`、`unavailable_objects` | array | 列出未进入卡片集合的 canonical path、`check_status` 和机械问题；对象身份可安全确定时包含稳定 `fact_ref`，目录或预算范围失败时改含 `fact_type_key`；不可静默忽略 |

`cards[]` 按 `(fact_type_key, object_id)` 升序，字段闭集为 `fact_ref`、`card_layer`、`fields`、`excerpts`、`match_reasons`、`source_refs`。`fact_ref` 使用稳定三元组；`fields` 直接投影对象当前权威值，条件字段不适用时省略；不得在 `fields` 中生成摘要、标签、权重或推断值。`excerpts` 是数组，没有类型化摘录时为空；每项字段闭集为 `field_path`、`text`、`complete`，其中 `field_path` 必须是下表明确允许的完整对象直接 string 字段，`text` 必须从该字段起点开始原样保留最多 512 个 Unicode scalar values，不 trim、不拼接省略号、不重写 Markdown，`complete` 只在 `text` 已包含该字段全部值时为 `true`。摘录的固定预算是 Helper 传输边界，不是事实写作长度、字段值或验证阈值；`complete: false` 时调用方必须使用同卡 `fact_ref` 进入 F3 才能取得完整内容。

F1 投影必须忠实承接具体类型来源：ADR 按 22 §7 的 `object_id/title/decision_question/decision/applicability/updated_at`；WorkCase 按 21 §7 的 `object_id/title/status/phase/goal/scope/summary/priority/blocking_summary/updated_at`，并附加从当前 `work_items` 确定性派生、不得写回对象的 `work_item_counts`。F1 的 `excerpts` 固定为空。F2 按 20–24 只允许：

| 类型 | F2 `fields` 投影 |
|---|---|
| Spark | `fields` 只含 `object_id`、`title`、`status`、`priority`、`updated_at`；`intent` 存在时，`excerpts` 按 `intent`、`summary` 的固定顺序各包含一项对应 `field_path` 的有界摘录，旧对象缺失 `intent` 时只包含 `summary`；两个字段都是 F2 `text_match.field_paths` 允许的完整检索来源，但都不直接进入 `fields`，也不得在旧对象上生成伪 `intent` 摘录 |
| WorkCase | `object_id`、`title`、`status`、`phase`、`goal`、`scope`、`summary`、`priority`、`blocking_summary`、`updated_at`；`work_item_counts` 只作为当前 `work_items` 的确定性派生结果附加 |
| ADR | `object_id`、`title`、`status`、`decision_question`、`decision`、`applicability`、`updated_at` |
| Pitfall | `object_id`、`title`、`status`、`symptoms`、`trigger_conditions`、`applicability`、`validation_summary`、`updated_at` |
| Study | `object_id`、`title`、`status`、`research_question`、`abstract`、`applicability`、`validation_summary`、`updated_at` |

`match_reasons[]` 只允许字段闭集 `kind`、`field_path`、`matched_text`；`kind` 为 `recovery-baseline`、`default-status`、`status`、`exact-ref`、`relation-target`、`locator` 或 `field-text`。`matched_text` 只在 locator 或字段文本命中时出现，并且必须是对象完整当前字段中实际命中的原文字面内容；命中位置可以位于返回摘录之外，这不允许扩大摘录预算或暗示摘录已覆盖命中上下文。不得返回相关性说明或语义分数。Study 卡片不解释当前性；版本与观察边界只能通过精确读取和必要 F4 来源核对。

`coverage` 字段闭集为：`status`（`complete` 或 `partial`）、`total_matching`、`returned`、`offset`、`next_cursor`、`object_set_fingerprint`。`total_matching` 是同一对象集合与查询下的完整机械有效匹配数；`next_cursor` 只在尚有下一页时为非空 string，否则为 `null`。存在 invalid 或 unavailable 对象时 coverage 为 `partial`，并进入共同 `scope.not_completed` 与 `gaps`；F1 此时不得宣称恢复基线完整。没有这些对象且本页形成时为 `complete`，即使仍有下一页也只表示扫描集合完整，AI 仍须继续分页才能声称全部卡片已读。

首版单次最多扫描五类合计 10,000 个 canonical 身份文件；目录、Git 身份、Schema 或必需机械检查不能完成时相应范围为 unavailable。操作不返回 F3 正文；AI 选中对象后必须使用 `read-fact-objects` 精确展开。共同 `changes` 固定为空；共同 `verification` 只证明当次直接扫描、机械检查、确定性过滤、投影、排序和分页实际完成的范围。

### 11.7 事实对象单对象 CAS 更新输入与结果

`update-fact-object` 是一次只修改一个已存在对象的状态变更操作。它不实现 JSON Patch、字段级 merge、删除、创建、迁移、合并、多对象事务或 Git 提交。调用前 AI 必须使用 `read-fact-objects` 精确读取当前对象，核对具体类型来源、当次授权、来源与证据，并把读取返回的 `content_fingerprint` 原样用于当次比较与交换（compare-and-swap，CAS）。

领域 `arguments` 只允许：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全复用 02 §10.1 的配置选择语义 |
| `fact_ref` | object | 必填；精确使用 §11.1 `fact_refs[]` 的稳定三元组字段闭集 | 选择唯一目标；不接受路径、标题、别名或搜索回退 |
| `expected_content_fingerprint` | string | 必填 64 位小写十六进制 string | 必须精确匹配同一 worktree 当前载体再次安全读取的 SHA-256；不匹配时使用 `rejected` 且不写入 |
| `fact_object` | object | 必填 | YAML 类型提交排除 Code 托管字段后的完整目标字段映射；Study 精确包含 `frontmatter` object 与非空 `body` string；未提交字段表示目标状态中不存在，不实施部分 merge |

`work_object_locators` 与唯一实际 worktree/common-dir 边界复用 §11.1；`observed_context` 必须为空，`requested_disclosure` 必须为 `null`。`authorization_reference` 可以回指当次已经存在的 Human 决定或授权来源，但 Code 不根据自然语言自动判断授权语义或作用范围。Code 托管 `object_id`、`fact_type_key`、`created_at` 和 `updated_at`：前三项从当前对象原样保留，最后一项在实际变更时写为当次带时区 RFC 3339 时点且必须晚于当前 `updated_at`；本地时钟无法形成后继时点时拒绝写入，AI 不得提交这四项。

Code 必须在同一类型受控写入锁内重新确认管辖、Git 身份、目标普通文件、当前对象机械有效性和完整内容指纹。输入内容与当前对象除 `updated_at` 外完全相同时返回 `no_change`，不重写文件或制造新时间。确有变化时，必须对完整目标快照执行载体、Schema、身份、引用、关系和具体类型条件检查，并对变更前后执行以下机械转换边界：

1. status 不变时只可作具体类型来源允许的原地更正或内容更新；status 或 phase 变化只允许该类型来源明示可以由单对象快照完成的转换，终态能否重开、何时退回及字段如何失效均以该来源为准；
2. 任何新增、移除或改写 `supersedes` 边，以及任何进入 `superseded` 的转换，都要求两个或更多对象同时成立，本操作使用 `rejected` 且不写入；这是本操作的单对象能力边界，不改变 20–24 对相应关系和状态的语义；
3. WorkCase 的 status/phase 组合、计划与结果版本单调性、内容变化时的版本递增、审核和批准失效以及退回条件必须完整满足 21 §6；本文不再复述这些类型规则，Code 只对 21 明确交给机械检查的快照差异执行保守校验。

计划或结果的“实质改变”、Human 表达的含义、审核是否真正独立、证据是否足够和更正是否仍为同一事实，仍由 AI 依据当前来源判断。Code 只对已结构化的值变化作保守过期与失效检查，不为绕过重审而解释自然语言是否“只是文案”。

受支持的 Helper 写入在类型锁内串行，并在原子替换前再次比较旧载体完整 bytes。这一保证覆盖共享同一 `git_common_dir` 且通过当前受控入口的并发进程；不使用该锁的外部手工进程或工具只能在替换前后尽可能检出，不声称对这些外部写入或跨 clone 写入提供线性化 CAS。原子替换后必须使用 `read-fact-objects` 的同一机械边界回读。写后回读不成立时，只可在目标仍精确等于本次新载体时 CAS 回滚原文；冲突或回滚失败必须报告实际残留和未完成验证，不得返回 `ok`。

成功与 `no_change` 的领域 `result` 字段闭集为：`actual_ref`、`canonical_path`、`carrier`、`previous_content_fingerprint`、`content_fingerprint` 和 `fact_object`。`actual_ref` 使用 §11.1 稳定三元组；两个指纹都是 64 位小写十六进制 SHA-256，`no_change` 时两者相同。`fact_object` 返回回读后实际对象。共同 scope 的三个数组都使用原始 `fact_ref` 作为同一范围成员；成功更新时 `changes.status` 为 `updated`，并回指实际对象和 Working Tree 路径。请求成功只证明该单文件已在当次 CAS 边界内替换并通过机械回读，不证明自然语言事实、证据、Human Gate、Git 提交或上层工作已完成。

### 11.8 共享单对象受控写事务

`create-fact-object`、`update-fact-object` 和具体类型来源声明的受控写操作共同使用同一 `git_common_dir/ldvh` 持久协调根。创建使用“项目 + 类型”单调 allocator；对既有对象的更新使用同一“项目 + 类型”排他域串行当前受控入口。linked worktree 不得各自建立 allocator 或锁，不得在权限不足时回退 worktree-local、进程临时目录、仅内存锁或无锁扫描；这些替代会分裂可见对象集合、复用已消耗编号或削弱已声明的并发边界。

单对象更新事务按以下顺序执行：

1. 在进入锁前完成有效请求、唯一项目/worktree/common-dir 与派生 Schema 的只读确认；
2. 进入共同类型锁后重新安全读取目标载体、机械校验当前对象，并精确比较 expected content fingerprint；
3. 请求表达的完整 after 与当前对象相同时先返回 `no_change`，不得为了更新时间而重写；
4. 确有变化时使用 Helper 服务边界提供的唯一带时区 RFC 3339 `event_at` 写 `updated_at`；该值不能严格晚于当前值时拒绝且零写入；类型专属托管记录只能按其来源把同一值用于本事件的其它时间字段；
5. 对完整候选执行载体 parse、派生 Schema、身份、引用、关系、项目级约束和变更前后 transition 检查；
6. 在替换前再次比较当前完整 bytes，原子写入后按 `read-fact-objects` 的同一边界回读；回读失败时只可在目标仍精确等于本次新 bytes 时条件回滚。

共享事务接收调用方或类型适配层已经确定的完整语义 after，不解释事实正文、审核结论、授权含义、实质变化或流程推进，也不反向调用 Helper。类型适配层可以确定性填入来源明示的托管字段和固定失效集合，但不得复制状态机或从普通字段差异选择 phase、版本、复审或 Human Gate。通用 `update-fact-object` 的既有请求与完整结果保持兼容。

Helper 在有效服务请求边界只观察一次 `event_at`；实际受控记录时间和该受控写操作生成的 Working Tree observation 应复用该值，不得在 operation、候选和该对象写入来源回指中各自重新读取时钟。管辖、配置或其它只读观察仍按其自身实际观察边界记录。`no_change` 的领域结果不得把该边界观察冒充对象事件；具体操作需要返回事件字段时使用 `null`。

进入共同锁前，锁目录或锁文件因权限、只读文件系统或等价的预期访问限制无法创建或取得时，必须在 target、allocator 和 counter 均未改变的情况下返回 `unavailable`，使用稳定 code `controlled_write_lock_unavailable`，并在 compact 中保留摘要与恢复条件、在 diagnostic 中安全增加 `stage`、协调根角色、所需访问和系统错误类别。不得返回原始异常正文或把目标读写阶段的其它异常误分类为锁问题。`capabilities` 是读取入口，不得以创建目录或锁文件作为写探针；没有观察到确定性缺口只表示可以尝试调用，不保证未来动态锁获取成功。

所有 YAML 事实载体序列化后必须满足：重新解析所得结构与目标字段语义等价；任何物理行不得以 ASCII space 或 tab 结束；最终文本使用 UTF-8 和单个结尾换行。实现必须通过 emitter 配置避免自动折行制造尾随空白，不得对已生成文本逐行 `rstrip`，因为字符串值中的空白可能具有领域语义。Study 的 frontmatter 服从同一规则，正文继续按其类型来源和 carrier 契约处理。

## 12. 事实类型停止新增、合并、替代或取消

事实类型准备停止新增、合并、替代或取消当前使用时，必须先：

1. 确认其唯一定义来源的责任将保留、转移还是退出，并按 01 处理相应规范或附件关系；
2. 停止创建无法由当前有效来源验证的新对象；
3. 逐类确定现有对象继续保持、迁移、合并、归档或删除的条件；
4. 为仍适用的事实、来源、证据和关系确定唯一当前承接位置；
5. 处理引用该类型的其它事实对象、Helper、Code、tests 和 Web 契约，避免悬空引用或并行权威；
6. 验证迁移、替代或取消后的当前 Working Tree，并如实标记未处理对象、未验证范围和残留风险。

上述处理不建立本文统一的类型状态字段，也不能只通过删除 Schema、隐藏页面或停止 Code 支持完成。唯一定义来源仍为 `active` 时，实现不得自行宣布该类型已经取消；定义来源退出或被替代时，也不得遗失仍然适用的事实或让两个来源同时承担当前语义。

## 14. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 对事实模型的定义，或准备让不满足事实源边界的内容取得事实对象身份；
2. 已完成 §6.1、承载位置比较和独立复核，仍无法判断候选事实类型的净价值，或者需要接受明显的长期迁移与维护负担；
3. 同一事实对象或同一类事实存在多个相互冲突的权威位置，来源规则无法确定保留、合并或放弃哪一处；
4. 事实类型或大批事实对象的合并、迁移、归档或删除可能造成仍适用事实、来源、证据或关系的实质损失；
5. 需要处理具体事实类型定义来源规定必须由 Human 决定的证据例外、状态转换、风险、关闭、归档、合并、替代或删除方向。
6. 新增、删除、改名、拆分、合并或改变字段的 JSON 类型、稳定身份或共同语义，并且语义复核仍有歧义，或会对多个当前类型产生破坏性迁移负担。

Human 决定的复用按 00 §9 执行；Human 只能决定是否停止、改向、取舍承接位置或接受清楚标明的未验证风险，不能替代类型准入、定义来源、事实源写入与回读、对象校验、证据充分性或技术验证，也不能使无效对象、状态或关系自动成立。

## 15. Stop Conditions

出现以下任一情况时，必须暂停依赖受影响事实类型、事实对象或声明的最小范围：

1. 候选类型尚未满足准入条件或没有当前有效的唯一定义来源，却准备创建、更新或消费正式事实对象；
2. 正在仅凭历史名称、规范、字段、状态、目录、现存实例、Code 或 Web 实现恢复具体事实类型；
3. 事实类型标识重复、格式错误、被改派或无法回到同一当前定义来源，或者对象不在允许的事实源位置、稳定引用有歧义、身份或当前权威位置不唯一，或者当前 Working Tree 内容无法按具体事实类型的定义来源解析；
4. 状态、字段、证据或关系违反具体事实类型的定义来源，却准备静默修复、回退旧提交或继续作出成立声明；
5. 正在创建或使用未登记字段或结构，字段或结构没有覆盖全部 `current`、`retired` 登记及本类型完整提案的全局查重与独立语义复核，多个类型或草案出现未消歧的同名异义或异名同义身份，第二个类型准备复制现有专属字段或结构而未先提升，或者登记、唯一定义、适用范围、成员出现规则和类型绑定不一致；
6. 来源无法按所需精度回指，证据范围不能支持当前结论或转换，或者关系目标无法通过稳定身份定位；
7. Helper、Code、tests、Schema、缓存、索引、聚合或 Web 正在新增、改变或覆盖事实类型语义，或把确定性命中、候选返回、机械有效或非终态自动解释为语义相关、当次适用或应全量注入；
8. 写入、更新、转换、关闭、归档、合并、替代、删除或类型变更没有实际完成并回读，却准备声明对象或类型已改变；
9. 类型或对象的变更会遗失仍适用事实、来源、证据或关系，留下悬空引用，或形成多个当前承接位置；
10. 无法确认停止影响哪些对象、类型、消费方或声明，继续推进可能扩大不一致。

类型未准入、对象无效、状态无法判断或关系缺失本身不造成全局停止。暂停范围与允许继续的行动按 00 §10 执行；可以继续只读核对当前来源和对象、比较承载位置、补充来源与证据、修正草案或对象结构、拆分冲突、准备 Human Gate，并继续明确不依赖受影响事实的普通工作。

恢复按 00 §10 执行；与触发原因对应的条件必须满足：类型准入和唯一定义来源成立；字段与结构已经完成全局查重、唯一登记、定义、适用绑定和独立复核；对象身份、位置、结构、状态、来源、证据或关系已经修正并回读；冲突权威位置已经处理；声明已经缩小到现有依据实际支持的范围；类型或对象变更已经保留仍适用事实；或者 Human 已对其保留事项作出作用范围清楚的决定。
