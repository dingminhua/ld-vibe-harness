## 1. 行动定位与适用场景

规范审核是 LDVH 对 `specs/00-19` 基础规范区正式规范文档进行质量审查的工作流程。它回答：一份不涉及具体工作模型或工作流程定义的 `specs/` 文档，是否能够被 AI 稳定理解、能否支撑 AI 的执行、验证与回写、是否仍符合 00 的价值实现标准、是否避免了事实源漂移或重复维护。

本流程只审查 `specs/00-19` 基础规范文档中写的规范要求是否合理、完整、一致、可执行；不深入 20-39 工作模型的字段契约、状态机或对象关系细节（由 41 承接），不深入 40-59 工作流程的 Scenario、Context、Gate、执行流程或能力协作细节（由 40 承接），不审核 Code 实现、Web 展示或具体工作对象实例的运行状态，不把 Code 输出视为"项目已满足规范要求"的证据。

以下场景应进入本流程：

1. 新增或修改 `specs/00-19` 中的正式规范文档；
2. 修改已有正式规范文档的定位、上位依据、相关规范、正文规则、规范落地要求或检查要求后；
3. 发现某规范文档存在引用缺失、锚点漂移、事实源重复维护、与 00 价值标准偏离或与 03 文档治理冲突的线索；
4. Code 派生索引、文档结构检查、引用检查、落地要求检查或综合校验报告 specs 相关诊断；
5. AI 执行时反复依赖聊天记忆、临时提示或外部资料才能理解某个规范；
6. 把 `docs/studies/`、`docs/sources/`、Web 页面状态、工具输出或外部 URL 直接当作规范依据时；
7. 新增或变更工作模型、工作流程、Code、Web、Rules 入口或能力资产，需要回溯检查上位规范是否仍然自洽。

以下场景不应由本流程直接承接：

1. 只查询当前有哪些成员或集合；该事项由成员主文件自描述和 Code 派生索引承接；
2. 审核 20-39 工作模型的字段契约、状态机、对象关系或实例边界；该事项由 41 承接；
3. 审核 40-59 工作流程的 Scenario、Context、Gate、执行流程、能力协作或可测试性锚点；该事项由 40 承接；
4. 管理工作对象实例状态或执行进度；
5. 替代 Code 校验、测试或 Human Gate。

## 2. 准入条件

进入本流程前，应满足以下条件之一：

1. 已存在目标 specs 文档或明确的候选标题、编号意向；
2. 已有 Code 诊断、入口漂移、引用缺失、锚点缺失、骨架缺失或重复维护线索；
3. 已有与 00 价值标准、03 文档治理或 09 事实源边界相关的争议或改进诉求；
4. 已有工作流程、工作模型、Code、Web、Rules 入口或能力资产准备消费或引用该规范；
5. AI 执行时反复出现同类型误判或依赖聊天记忆。

不满足以上条件时，不应为了维持编号顺序或制造"看起来完整"的体系而触发审核。只有当文档真正承担稳定规则、支撑 AI 执行或被其他能力资产引用时，才触发本流程。

## 4. Context 要求

执行本流程前，AI 应按最小可行动原则准备以下 Context：

1. `../rules/LDVH-MAINTAINER-ENTRY.md` 中与 specs 场景路由、Code 查询入口、STOP 点和维护规则相关的段落；
2. `specs/00-LD-Vibe-Harness理念与纲要.md` 中产品定位、价值实现标准（V1-V10）、事实源原则、运行闭环标准和总纲一致性检查相关段落；
3. `specs/03-文档基础规范.md` 中工作区契约、命名、引用纪律、studies/sources 边界、引用类型与方向和文档治理相关段落；
4. `specs/03.01-规范文档规范.md` 中正式规范骨架、编号、相关规范规则、规范落地要求段落和检查要求；
5. `specs/01-目录说明.md` 中 specs 编号分区、成员自描述与 Code 派生索引边界；
6. `specs/09-事实源边界与承载规范.md` 中单一事实源原则、权威位置判断、工具输出边界与 Web 状态边界；
7. `specs/10-测试基础规范.md` 中验证声明、等价验证与测试治理边界；
8. 目标 specs 文档全文或关键段落；
9. 必要时运行 `python3 code/specs_validate.py index`、`python3 code/specs_validate.py doc specs`、`python3 code/specs_validate.py refs specs`、`python3 code/specs_validate.py landing specs` 或 `python3 code/specs_validate.py all` 获取导航与诊断。

若目标文档尚未创建，AI 只能审核候选草案和创建方案，不得声称该文档已经生效。若无法定位目标文档、上位规范或必要诊断来源，应暂停并说明缺口。

当 01 或 02 作为被审核对象时，它们不再充当审核依据，应以 00 为核心依据，其他 00-19 文档作为交叉参照。具体降级规则如下：

1. 审核 01 时，§4 第 5 条（01 中 specs 编号分区、成员自描述与 Code 派生索引边界）不作为审核依据，改由 00 的事实源原则和 03/03.01 的文档治理规则替代；编号分区完整性检查以 00 的构成要素分工和当前 specs 实际文件为交叉参照；
2. 审核 02 时，§4 第 3 条（03 中引用纪律相关段落）和 §4 第 4 条（03.01 中正式规范骨架）仍可作为审核依据，但 02 自身的术语归口规则不作为自我审核依据，改由 00 的上位概念来源和 03 的文档治理规则替代；术语缺口检查以当前 specs 全文实际使用的概念为交叉参照。

## 5. Scenario 识别

AI 遇到以下信号时，应识别为规范审核场景：

1. 用户要求创建、修改、审查或重写某个 `specs/` 正式规范文档；
2. 用户提到 V1-V10、价值标准、AI 第一服务对象、单一事实源、引用纪律、规范落地要求、检查要求或文档治理；
3. Code 派生索引、结构检查、引用检查或落地要求检查报告 specs 相关诊断；
4. 某个 specs 文档出现指向 `docs/`、外部 URL、外部项目资料或非 LDVH 资产的依据性引用；
5. 某个 specs 文档同时承担规范、历史记录、研究材料或工具使用说明等多种角色；
6. AI 执行时反复需要"先读完整个 specs 才能判断"或依赖聊天中的口头解释；
7. 工作流程、工作模型、Code、Web、Rules 入口或能力资产引用了某个 specs，但该规范自身无法独立支撑该引用。

多个场景同时命中时，应先判断是否存在更具体的 active 工作流程。若没有更具体的 active 工作流程，或目标就是审核 specs 规范文档质量，则进入本流程。

## 6. 执行流程

规范审核按以下步骤执行：

1. **确认目标**：确认被审核对象是已存在的正式规范文档、候选草案、子文档、迁移计划或能力消费请求；如被审核对象实际是 `specs/20-39` 工作模型或 `specs/40-59` 工作流程成员主文件，应按需要切换到 41（工作模型审核）或 40（工作流程设计审核），而非继续以本流程深入；若被审核对象为 01 或 02，应按 §4 末尾的依据降级规则调整审核依据，并在审核结论中说明依据降级范围；
2. **确认权威依据**：读取或定位 00、03、03.01、01、09、10 和目标文档；若目标文档为 01 或 02，按 §4 末尾的依据降级规则跳过目标文档自身作为依据的条目，改由 00 和其他 00-19 文档替代；
3. **运行确定性诊断**：优先运行或参考 `python3 code/specs_validate.py index`、`python3 code/specs_validate.py doc specs`、`python3 code/specs_validate.py refs specs`、`python3 code/specs_validate.py landing specs`、`python3 code/specs_validate.py all` 获取目标文档的机械属性导航与诊断（文件存在与命名一致性、文档结构与骨架章节齐全性、引用有效性与锚点有效性、规范落地要求表结构、派生集合索引与冲突诊断）；
4. **审核定位与上位依据**：检查创建日期、定位、适用范围、上位依据是否明确，是否与 00 和当前编号分区一致；
4a. **审核 01 特有项（若目标为 01）**：①编号分区是否覆盖当前 specs 实际存在的所有编号段，是否存在已占用但未声明的编号或已声明但无对应文件的编号；②目录映射是否与项目实际目录结构一致；③内容归属判断是否与当前 specs 全文的实际职责分工一致；④成员自描述与 Code 派生索引的边界声明是否仍准确；
4b. **审核 02 特有项（若目标为 02）**：①术语表是否覆盖当前 specs 全文中实际使用的核心概念，是否存在高频使用但未归口定义的术语缺口；②不推荐表达对照是否随规范稳定逐步收敛，是否存在长期停滞的待收敛项；③术语归口规则是否被其他规范实际遵守，是否存在非归口文档重复定义已归口术语的迹象；④术语变更治理清单是否与当前规范体系实际变化同步；
5. **审核文档骨架**：按 03.01 的正式规范骨架检查：①是否包含创建日期、定位、适用范围、上位依据等头部声明；②是否包含问题定义（或 00 级总纲叙事）、核心规则段、规范落地要求、检查要求等必填段落；③是否按正向规则表达（即明确"应做什么"，而非集中表达"禁止什么"）；④是否避免把 docs/studies/历史记录或工具使用说明写进 specs 正文；
6. **审核子文档（若适用）**：若目标是子文档（如 03.01、03.03、03.04、05.01 等 NN.SS 格式），检查：①是否声明了所属主文档、与主文档的关系、适用范围与上位依据；②是否避免复制父规范的通用规则，只表达子领域差异；③是否有独立的成员自描述 YAML 或等效声明；④是否在父规范的相关规范或引用段中被正确指向；⑤是否避免与父规范冲突（如重新定义已有状态、字段或校验方式）；
7. **审核相关规范**：检查 `相关规范` 是否为真实读取/同步/检查依赖，是否避免反向清单、是否引用 docs、外部 URL 或非 LDVH 资产作为依据；
8. **审核引用纪律**：检查引用方向是否由粗到精、引用类型是否正确、是否存在把导航/追溯/被引用提升为上位依据或相关规范；
9. **审核事实源单一性**：检查是否在 specs 与 docs、Web、工具输出或数据库之间重复维护同一事实；是否存在"两条同样规则分别写在两个地方"的迹象；
10. **审核价值一致性**：判断文档是否服务 V1-V10；是否出现"为机制而机制""制造第二事实源""绕过 Human Gate"或"偏离 AI 第一服务对象"的表述；
11. **审核规范落地要求**：检查规范落地要求表是否声明要求内容、保障机制、同步类型和触发条件，是否把具体环境实体写成要求本身，是否制造无法保障的落地承诺；
12. **审核检查要求**：检查文档是否明确 AI 应如何判断规则成立、失败或需要 Human Gate；是否存在"只要求但不说明判定方法"；
13. **审核与 docs 和 studies 的边界**：检查是否把历史迁移、来源演化、研究材料或工具使用说明直接写进 specs 正文；
14. **审核可执行性**：检查规范是否能被 AI 直接消费并产生动作，而不是只陈述理念；是否缺少必要锚点、字段或判定方法；
15. **形成审核结论**：按 §10 输出过程结论，必要时触发 Human Gate、创建后续 WorkPlan/Memo/ADR/Pitfall 或修订目标文件；
16. **复跑验证**：目标文档被修改后，应重新运行相关校验命令，并记录结果、残留风险和下一步分流；验证命令输出仅用于判断目标规范文档的机械属性是否自洽，不代表该规范在项目中已被满足。

## 7. Gate 触发条件

出现以下情况时，AI 必须暂停继续宣称审核通过，并按影响范围触发 Human Gate、降级检查或后续分流：

1. 新增或删除 `specs/00-19` 下正式规范文档；
2. 重命名、移动、改变编号或改变子文档归属；
3. 改变 00 总纲相关的产品定位、价值实现标准、五类构成要素、事实源原则或运行闭环标准；
4. 让 specs 文档承担历史记录、研究材料、工具使用说明或 Web 状态维护职责；
5. 目标文档与 00、01、03、03.01、09 或 10 冲突；
6. 目标文档缺少问题定义、规范落地要求或检查要求，却被要求作为正式规范执行；
7. 审核需要接受长期降级、跳过验证、关闭 open/degraded 缺口或绕过 Code 诊断；
8. Code 诊断、Git 文件事实源、入口资产或目标文档正文之间存在冲突；
9. 审核结论会影响工作模型、工作流程、Code、Web、Rules 入口或能力资产的长期行为边界。

Gate 触发时，AI 应说明触发原因、影响范围、可选处理方式、推荐分流和需要 Human 确认的具体事项。Human 确认形成稳定事实时，应按 06 的 Human Gate 最小字段记录时间、决策、范围和约束。

## 8. Skill 与 Agent 调度

本流程默认由主控 AI 执行。只有当审核任务可复用、复杂、争议大或需要独立上下文时，才考虑 Skill 或 Agent 辅助。

Skill 适合承接：

1. 固定审核清单；
2. 标准化输出格式；
3. 常见失败分类（如引用缺失、事实源重复、价值指标替代）；
4. 交还主控的修订建议；
5. 重复执行的 specs 审核 SOP。

Agent 适合承接：

1. 跨文档语义自洽审查；
2. 价值一致性判断与替代指标识别；
3. 多个规范之间职责冲突分析；
4. 高影响规范变更的并行审阅；
5. 长期降级或缺口关闭的争议分析。

Skill 和 Agent 输出均为过程输出，必须交还主控。Skill 不得自行调度 Agent，Agent 输出不得直接生效，不得绕过 Human Gate、Code 诊断、事实源回写或主控判断。

---
## 9. Code 与命令入口协作适配

本流程优先使用 Code 完成可机械化检查。Code 适合承接：

1. specs 文件存在与命名一致性检查；
2. 文档结构和章节骨架检查；
3. specs 引用检查与锚点有效性；
4. 规范落地要求表结构检查；
5. Code 派生集合索引、状态清单和冲突诊断；
6. 与工作模型/工作流程成员自描述的一致性提示。

常用命令包括：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

Code 输出只作为导航、聚合和诊断结果。Code 不判断规范是否符合价值标准、是否语义自洽、是否真的让 AI 更好用，也不生成授权。Code 不可用、诊断不完整或输出无法回指事实源时，应退回人工检查并记录残留风险。

**审查边界声明**：本流程只审查目标规范文档中写的规范要求是否合理、完整、一致、可执行；不审查项目中是否已实际满足这些要求。Code 的作用仅限于帮助 AI 检查目标文档的机械属性（文件存在、命名、骨架、引用、锚点、落地要求表结构），Code 输出不构成"该规范在项目中已被满足"的证据。

## 10. 事实源回写与证据留存

本流程执行后的过程输出应至少说明：

1. 审核对象；
2. 读取的权威依据；
3. 运行的 Code 命令或人工降级检查；
4. 发现的问题（引用、事实源、价值标准、文档治理或落地要求层面）；
5. 价值一致性结论，说明目标文档主要服务的 V1-V10 项、未发现的价值偏离和残留风险；
6. 审核结论；
7. 是否触发 Human Gate；
8. 是否修改目标文档或生成后续工作对象；
9. 残留风险和下一步分流。

审核结论分为：

| 结论 | 含义 |
|---|---|
| `pass` | 未发现阻塞问题，且必要验证通过 |
| `pass_with_followups` | 可继续使用，但存在不阻塞的后续改进项 |
| `blocked` | 存在阻塞问题，不得作为正式规范依据继续消费 |
| `needs_human_gate` | 需要 Human 确认后才能继续或升级/修改 |
| `not_applicable` | 当前对象不属于 specs 规范审核范围（如纯 studies、纯工具说明） |

稳定事实回写规则如下：

1. 目标规范正文需要调整时，回写对应 `specs/` 主文件；
2. 审核形成缺口、后续工作线索或后续行动时，回写 Memo 或 WorkPlan；
3. 审核形成长期决策或架构判断时，回写 ADR；
4. 审核形成可复用踩坑经验时，回写 Pitfall；
5. 审核形成研究报告或迁移说明时，回写 docs；
6. 发生事实源修改时，按 25-Change 的 Git、commit message 和 Refs 追溯规则处理。

凡回写为 WorkPlan 的后续行动，必须按 `specs/21-WorkPlan-工作计划.md` 和 `specs/05.01-工作字段内容格式规范.md` 填写 `success_criteria`、`orchestration.execution_items`、`verification_evidence` 与 `closure_evidence` 等字段；流程步骤不得新建 TaskPlan、Task 或 SubTask，执行期拆分只能作为 WorkPlan 内部 `execution_items`。

不得把聊天中的"看起来合格""逻辑没问题""应该符合 Vx"当作完成证据。关键结论必须能回指规范、目标文件、命令输出、Human Gate 或事实源差异。

## 11. 环境适配边界

本流程可以被 Rules 入口提示、Skill SOP、Agent 审查、Code 校验、Web 展示、Hook 提醒或 CI 检查辅助，但这些能力不得替代本流程正文。

环境适配边界如下：

1. Rules 入口只提示何时读取本流程和相关规范，不复制流程全文；
2. Skill 可以封装固定审核清单，但不新增稳定规则；
3. Agent 可以提供独立语义审查和价值一致性判断，但不直接生效；
4. Code 可以提供确定性诊断，但不替代 AI 语义判断和 Human Gate；
5. Web 可以展示审核状态、诊断和 Human Gate 入口，但不维护第二事实源；
6. Hook 或 CI 可以提醒或阻断高风险变更，但触发不等于检查通过；
7. CI 属于保障机制，不是固定文本能力资产类型；
8. 环境能力缺失时，应降级为人工检查并记录残留风险。

## 12. 行动特有可测试性锚点

本流程的关键行为应能通过正例、反例、Gate 场景、回写场景和命令验证进行检查。

正向场景：

1. 目标规范有清晰定位、适用范围和上位依据；
2. 目标规范遵循 03.01 的正式规范骨架；
3. 引用遵守引用方向和引用类型规则，不把 docs 或外部 URL 作为依据；
4. 规范落地要求声明要求内容、保障机制、同步类型和触发条件；
5. 检查要求说明如何判定通过/失败；
6. 不出现重复维护同一事实的迹象；
7. Code 校验无阻塞诊断；
8. 审核结论能回指事实源和验证结果。

负向场景：

1. 缺少问题定义或规范落地要求；
2. 把 docs/studies、外部 URL 或 Web 页面状态当作规范依据；
3. 把历史迁移、来源演化或工具使用说明写进 specs 正文；
4. 引用方向或引用类型混乱，相关规范像反向清单；
5. 规范落地要求只写"符合规范"或空泛陈述，没有判定方法；
6. 规范正文同时承担研究材料、历史记录或执行说明等多重角色；
7. 用页面数量、文档数量或引用数量等替代 V1-V10 的价值指标。

Gate 场景：

1. 新增或删除正式规范文档；
2. 修改 00 总纲相关的价值标准或事实源原则；
3. 让 specs 承担历史记录或 Web 状态维护职责；
4. 接受长期降级或跳过关键验证；
5. 改变引用纪律或事实源边界。

回写场景：

1. 审核发现正文缺陷，应回写目标规范主文件；
2. 审核发现后续改进项，应回写工作对象或 docs；
3. 审核发现长期决策，应回写 ADR；
4. 审核发现可复用误判，应回写 Pitfall；
5. 审核只产生临时建议时，应明确其为过程输出。

修改本流程或目标规范后，至少应运行：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

无法运行自动化校验时，应说明原因、采用的人工检查方式和残留风险，不得声称完整验证。Code 命令输出仅辅助机械属性检查，不替代 AI 对价值与规范的判断。

## 14. 检查要求

规范审核至少包括：

| 检查项 | 标准 |
|---|---|
| 对象归属 | 被审核对象属于 `specs/00-19` 基础规范区正式规范文档、候选草案或能力消费请求；若为 20-39 工作模型或 40-59 工作流程成员主文件，应切换到 41 或 40 |
| 定位与上位依据 | 创建日期、定位、适用范围、上位依据明确且与 00 保持一致；00 顶层可不声明上位依据 |
| 文档骨架 | 包含问题定义（或总纲叙事）、核心规则、规范落地要求、检查要求等必填段落 |
| 子文档边界 | 若目标为子文档（NN.SS），须声明所属主文档、与主文档的关系、适用范围与上位依据；不复制父规范通用规则；不与父规范冲突； |
| 相关规范 | `相关规范` 是真实读取/同步/检查依赖；未出现反向清单、docs 引用或外部 URL 依据 |
| 引用纪律 | 引用方向由粗到精，引用类型区分导航/追溯/主题相关/上位依据/相关规范，未混淆 |
| 事实源单一性 | 同一事实未同时出现在 specs、docs、Web、工具输出或数据库中；权威位置唯一 |
| 价值一致性 | 文档能解释主要服务哪些 V1-V10 项；未出现替代指标、空泛理念、为机制而机制、制造第二事实源、绕过 Human Gate、机制膨胀或偏离 AI 第一服务对象 |
| 规范落地要求 | 每项落地要求声明要求内容、保障机制、同步类型和触发条件，未把环境实体写成要求本身 |
| 检查要求 | 说明如何判定规则成立、失败或需要 Human Gate，未出现"只要求不判定" |
| 正向表达 | 职责边界通过定位、适用范围、上位依据、相关规范和正文正向规则表达，未出现反向说明章节 |
| docs/studies 边界 | 未把历史迁移、来源演化、研究材料或工具使用说明写进 specs 正文 |
| 可执行性 | 规范可被 AI 直接消费并产生动作；必要锚点、字段或判定方法完整 |
| 01 编号分区完整性（若目标为 01） | 编号分区覆盖当前 specs 实际存在的所有编号段；已占用编号均已声明；已声明编号均有对应文件或保留说明；目录映射与项目实际目录结构一致；内容归属判断与当前 specs 全文实际职责分工一致 |
| 02 术语覆盖与收敛（若目标为 02） | 术语表覆盖当前 specs 全文中实际使用的核心概念，无高频未归口术语缺口；不推荐表达对照随规范稳定逐步收敛，无长期停滞项；术语归口规则被其他规范实际遵守，无非归口文档重复定义已归口术语；术语变更治理清单与当前规范体系实际变化同步 |
| Code 诊断 | 相关 Code 校验命令已运行或已说明无法运行的原因、采用的人工检查方式和残留风险；Code 诊断仅辅助机械属性检查，不替代 AI 对价值与规范的判断 |
| 审核结论 | 结论按 `pass / pass_with_followups / blocked / needs_human_gate / not_applicable` 分类，且能回指事实源；Code 输出不替代 AI 判断 |
