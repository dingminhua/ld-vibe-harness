## 1. 本文解决的问题

本文定义 LDVH 工作模型字段内容如何书写和被读取，包括 Narrative、Checklist、验证证据、Decision、Reference、Log 和 Structured 等内容格式。内容格式是字段内部文本或结构的表达规则，不是独立工作模型，不具备独立生命周期、状态机或关闭条件。

字段名、公共字段语义和字段治理规则由 `specs/05.01-工作模型字段定义与语义规范.md` 定义；字段注册表、内容格式映射、Code/Web 消费元数据由 `specs/05.03-工作模型字段注册与消费规范.md` 定义；具体工作模型字段采用、必填性、状态条件和关闭条件由 20-39 具体工作模型规范定义。

---

## 2. 与 05、05.01、05.03 和 09 的关系

`specs/05-工作模型基础规范.md` 定义工作模型总纲，本文只定义字段内容格式。`specs/05.01-工作模型字段定义与语义规范.md` 回答字段承载什么语义；本文回答这些语义在字段内容中如何表达。

`specs/05.03-工作模型字段注册与消费规范.md` 登记每个字段或重要路径采用哪种 `format_kind`、`value_shape` 和消费语义。本文只定义格式类型和写入规则，不维护字段注册表。

`specs/09-事实源边界与承载规范.md` 定义 Markdown 和 YAML 的事实源承载分工。本文在字段内容格式范围内承接该分工：YAML 工作对象中的长文本字段可以使用 Markdown 语义书写，Markdown 是字段内容格式，不因此形成第二事实源。

## 3. 内容格式类型

LDVH 工作模型字段内容分为以下七种格式类型。格式类型不是独立工作模型，不具备独立生命周期、状态机或关闭条件，而是字段内容的书写和消费规则。

### 3.1 Narrative / 叙述说明

适合字段：`description`、`notes`、`context`、`success_criteria`、`constraints`、`rationale`

用途：说明背景、问题、目标、范围、约束。

书写规则：

1. 允许使用 Markdown 标题、段落、列表、引用、代码块、表格、链接；
2. 不强制 checklist；
3. 推荐使用 `## 背景`、`## 目标`、`## 边界` 等标题结构提升可读性；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
description: |
  ## 背景

  当前 Web 呈现中长文本字段缺少统一格式规范。

  ## 目标

  建立工作模型字段内容与格式规范，统一 AI 写入、Web 渲染和 Code 校验。
```

### 3.2 Checklist / 检查清单

适合字段：`acceptance`

用途：完成标准、关闭检查项、质量门禁。

书写规则：

1. 必须使用 `- [ ]`（未完成）或 `- [x]`（已完成）格式；
2. 每项必须是可独立验证的原子条件；
3. 不应包含非 checklist 内容；如需补充说明，放在 checklist 项的文本中；
4. YAML 中应使用块标量 `|` 承载；
5. 具体工作模型若把 Checklist 字段声明为关闭条件，关闭前所有检查项必须标记为 `- [x]`。

示例：

```yaml
acceptance: |
  - [ ] 建立字段内容格式规则
  - [ ] 定义七种内容格式的边界和书写规则
  - [ ] 明确 Code 校验消费规则
  - [ ] 运行事实源校验通过
```

### 3.3 验证证据

适合字段：`verification`、`verification_evidence`、`closure_evidence`

用途：记录验证过程、命令、结果、结论，以及关闭判断所需的证据摘要。

书写规则：

1. 应使用稳定 Markdown 骨架表达验证，不得写成无结构长段落；
2. 新写入或重写 `verification`、`verification_evidence`、`closure_evidence` 时，应按顺序包含以下二级标题：`## 验证计划`、`## 验证命令`、`## 验证结果`、`## 结论`；
3. `## 验证计划` 回答“要验证什么、依据什么判断通过”，应列出验证对象、判断条件、人工检查或自动检查范围；
4. `## 验证命令` 记录实际运行的命令、脚本、检查入口、人工检查动作或“不适用”的理由；命令应使用 fenced code block 或行内代码；
5. `## 验证结果` 记录每项检查的结果摘要、关键输出、路径或观察结论；不得粘贴超长日志，必要时引用日志、截图、报告或 commit；
6. `## 结论` 给出明确验证结论，例如“通过”“未通过”“部分通过/降级接受”“未运行”，并说明残留风险、关闭判断或后续分流；
7. YAML 中应使用块标量 `|` 承载；
8. 具体工作模型若把验证证据字段声明为关闭条件，进入关闭状态前对应字段不得为空，且不得只写“已验证”“见上文”“通过”等无法复查的短句。

存量对象可兼容读取旧格式；新增、重写或进入关闭审查的对象应使用上述四段式结构。Web 可以据此把验证证据渲染为分段阅读区，Code 可以据此检查关键二级标题是否存在。

#### 3.3.1 Human Gate 记录承载

涉及 Human Gate 的验证证据字段，可以嵌入 `Human Gate 记录：` 文本块。该记录应符合 `specs/06-工作流程基础规范.md` §6.3.1 的最小证据结构，并可被 `code/specs_validate.py human-gate` 检查。

Human Gate 记录进入 `closure_evidence`、ADR `context` / `consequences`、工作流程结果、Spark 或其他事实源字段时，只作为对应字段中的证据片段，不创建独立验证证据对象，也不得替代对象状态机、决策正文、验证结论或 Git 提交记录追溯。

示例：

````yaml
closure_evidence: |
  ## 验证计划

  检查字段内容格式规范、Web 字段渲染和对应测试是否一致。

  ## 验证命令

  ```bash
  python3 code/specs_validate.py doc specs
  npm run check --workspace web
  ```

  ## 验证结果

  两项检查均通过，未发现结构错误或类型错误。

  ## 结论

  工作满足验收条件。
````

### 3.4 Decision / 决策记录

适合字段：`decision`、`consequences`

用途：记录决策选择、理由和影响。

书写规则：

1. 应明确"选择了什么"和"为什么"；
2. 应区分已决策和未决策内容；
3. 如决策会改变事实源边界，应进入 ADR；
4. YAML 中应使用块标量 `|` 承载。

Decision 格式只定义决策类字段的通用写法：应表达选择、理由、影响和后续注意事项。具体对象可在自身工作模型规范中进一步固定章节结构、必填段落和校验规则；例如 ADR `consequences` 的五段式影响闭环由 `specs/22-ADR-决策.md` 负责，本文不重复定义对象特有强约束。

示例：

```yaml
decision: |
  采用 YAML 字段内 Markdown 作为内容格式方案。

  ## 理由

  - 不改变事实源边界
  - 兼容现有 Validator
  - Web 改造成本较低
consequences: |
  ## 影响

  - 字段内容仍在 YAML 事实源中，Markdown 只是内容格式。

  ## 代价

  - Web 和 Code 需要统一消费 Markdown 字段。

  ## 风险

  - 如果缺少字段注册，Markdown 内容可能被不同入口解释为不同语义。

  ## 后续

  - 通过 05.03 字段注册表、Code 校验和 Web 统一渲染规则约束消费方式。
```

### 3.5 Reference / 引用索引

适合字段：`related_docs`、`related_rules`、`urls`、`source_docs`

用途：记录引用路径、关联对象和外部资料。

书写规则：

1. 列表元素应为字符串路径或对象 ID；
2. 内部路径应可被 Code 校验存在性；
3. 外部链接使用完整 URL；
4. 这些字段通常是 list 类型，不是 Markdown 文本；
5. `urls` 只保存外部 `http(s)` 网址。每个条目必须使用结构化网址对象，至少包含 `ref` 和 `summary`：`ref` 必填并保存完整 `http(s)` URL，`summary` 必填并用中文说明该网址在当前报告中支撑什么判断，`title` 是可选展示标题。不得写裸 URL 字符串，也不得用英文或空泛文本替代中文简介。

示例：

```yaml
related_docs:
- specs/03-文档基础规范.md
- specs/09-事实源边界与承载规范.md
related_rules:
- specs/05.02-工作模型字段内容与格式规范.md
urls:
- ref: https://example.com/reference
  title: 外部参考资料标题
  summary: 说明该网址支撑报告中的哪个判断，而不是复制外部资料正文。
```

### 3.6 Log / 过程记录

适合字段：`transition_reasons`、执行过程摘要

用途：追踪过程、记录关键节点和后续观察。

书写规则：

1. 适合时间线或过程记录；
2. 不一定是最终结论；
3. 应避免变成无结构流水账；
4. YAML 中应使用块标量 `|` 承载。

### 3.7 Structured / 结构化对象

适合字段：`orchestration`、`orchestration.execution_items`、`orchestration.review`

用途：承载对象内部的结构化子对象或列表，使 Code 能按路径校验、Web 能按结构化语义呈现。

书写规则：

1. 使用 YAML object 或 list[object]，不得写成 Markdown 字符串；
2. 重要嵌套字段路径应在 `specs/05.03-工作模型字段注册与消费规范.md` §3 注册；
3. 完整对象内 schema、字段是否必填、状态条件和关闭条件由具体工作模型规范定义；
4. Web 应按结构化区域语义消费，不得只作为普通 JSON/YAML 文本展示；
5. Code 可依据注册路径做基础类型、枚举、引用和废弃字段检查，但不得用本文替代具体工作模型规范中的对象内约束。

## 4. AI 写入规则

AI 创建或更新工作对象时，应遵守以下写入规则：

### 4.1 长文本字段优先使用 YAML 块标量

注册表中 `value_shape=markdown`、`value_shape=checklist_markdown` 或 `value_shape=evidence_markdown` 的字段，如包含中文标点、英文冒号、换行、命令、列表式说明或超过一短句，应优先使用 YAML 块标量 `|`。

不得把包含冒号的长文本直接写成未加引号的普通单行字符串。

### 4.2 Checklist 字段必须使用检查列表格式

注册表中 `format_kind=checklist` 的字段必须使用 `- [ ]` 检查列表格式，将验收标准拆解为可独立验证的原子检查项。

### 4.3 验证证据字段应使用四段式结构

注册表中 `format_kind=evidence` 的字段应使用 `## 验证计划`、`## 验证命令`、`## 验证结果`、`## 结论` 四段式结构；可在对应段落中包含关键输出、关闭判断、残留风险或 Human Gate 结果。存量旧格式可兼容读取，但新增、重写和进入关闭审查的事实源不得继续写成无结构段落。

### 4.4 不自行添加未注册或未定义字段

AI 不得在工作对象中添加 05.03 未注册、且对象规范未定义的字段。如需新增字段，应先在 `specs/05.03-工作模型字段注册与消费规范.md` 登记字段名或重要嵌套字段路径，再更新对应对象规范；字段是否被具体对象采用仍由 20-39 具体工作模型规范决定。

## 5. 事实源边界

1. 工作对象文件仍是权威事实源；多数对象为 YAML，Study 为 Markdown frontmatter 和正文承载报告实例；
2. 字段内容格式只规定字段内部文本或结构如何书写，不改变对象事实源位置；
3. Git 提交记录不是工作对象字段，由 `specs/10-Git提交规范.md` 承接；
4. Web 和 Code 可以按 05.03 注册表消费本文格式类型，但不得把派生展示、摘要、校验结果回写为第二事实源；
5. 具体工作模型若把某个字段声明为关闭条件，应在 20-39 对应规范中定义条件，本文只提供内容格式。

## 6. 规范保障要求

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 字段内容格式不得替代字段语义、字段注册表或具体工作模型字段契约 | 05.01、05.03、20-39 具体工作模型规范 | 工作模型治理 | 新增、删除或改变内容格式类型时 |

## 7. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增或删除内容格式类型；
2. 改变 Checklist 或验证证据等可机械校验格式；
3. 改变 Decision、Reference、Structured 等格式与具体工作模型规范的分工；
4. 允许本文替代 05.01 字段语义、05.03 注册表或 20-39 具体字段契约。

检查至少确认：内容格式类型边界清晰；示例不与事实源边界冲突；引用到 05.01、05.03、07、08 和 20-39 的职责分工正确。

## 8. 待补齐事项

1. 若后续引入新的内容格式类型，应先确认是否已有格式可复用，避免把对象特有写法提升为全局格式；
2. 具体工作模型字段契约变化时，应同步检查 05.03 注册表中的 `format_kind` 和 `value_shape` 是否需要调整；
3. Code 与 Web 对四段式证据、Checklist 和 Structured 字段的消费能力应持续通过 07、08 和对应测试补齐。
