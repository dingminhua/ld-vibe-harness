# 规范落地要求规范

> 创建日期：2026-06-08
> 定位：定义 LDVH v2 正式规范如何声明规范落地要求、绑定保障机制，并在规范变更时检查落地要求是否需要同步
> 适用范围：LDVH `specs-v2/` 正式规范、规范落地要求声明、保障机制声明、规范变更审计和规范文档检查
> 上位依据：`specs-v2/04-规范落地与环境适配基础规范.md`
> 相关规范：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`、`specs-v2/03-文档基础规范.md`、`specs-v2/03.01-规范文档规范.md`、`specs-v2/04.02-环境适配与运行投影规范.md`、`specs-v2/04.03-环境适配映射与运行投影记录模板.md`、`specs-v2/04.04-环境能力承接边界.md`、`specs-v2/14-Code实现规范.md`

---
## 1. 本文解决的问题

本文解决 LDVH v2 正式规范如何声明自身规则要落地需要满足哪些要求。

正式规范不能只停留在正文中。凡是需要被 AI、Human、Code、Web、子 Agent、流程入口、生命周期触发或其他运行能力持续消费的稳定规则，都应说明该规范要落地需要满足哪些要求，以及这些要求由什么保障机制执行。

本文不直接维护 Codex、Trae、Claude Code、Cursor、CI、Web 或其他环境中的具体文件、配置、命令、Hook、Skill、Agent 或页面。具体环境实体、运行投影和漂移检查由 `specs-v2/04.02-环境适配与运行投影规范.md` 定义。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 由开发环境、工作模型、工作流程、Code 和 Web 五类构成要素共同形成 AI 工程驾驭体系，并要求规范驱动的 AI 工作 Harness 能够可规划、可执行、可验证、可沉淀、可演进。

`specs-v2/04-规范落地与环境适配基础规范.md` 定义正式规范进入运行环境的完整链路：

```text
正式规范
→ 规范落地要求
→ 保障机制
→ 环境适配映射
→ 运行投影
```

本文只定义“规范落地要求”和“保障机制”。“环境适配映射”和“运行投影”由 `specs-v2/04.02-环境适配与运行投影规范.md` 定义。

00 自身的原则不直接写成具体 Rules、Skill、Hook、Code 或 Web 页面。00 的原则如需运行，应先被对应专项规范吸收为可执行规则，再由专项规范按本文声明规范落地要求和保障机制。

---
## 3. 基本概念

### 3.1 规范落地要求

规范落地要求用于说明一条稳定规范要落地，需要满足哪些要求。

规范落地要求回答：

1. 这条规范要被 AI 看见吗；
2. 这条规范需要被流程复用吗；
3. 这条规范需要子 Agent 独立、专项或并行思考吗；
4. 这条规范需要确定性执行或校验吗；
5. 这条规范需要 Human 交互、确认或展示吗；
6. 这条规范需要在某个生命周期事件上稳定触发吗；
7. 这条规范是否是上位约束，需要后续规范承接。

规范落地要求不是环境实体，不应直接写成 Rules、Skill、Agent、Hook、CI、命令、Web 页面或工具文件。

### 3.2 保障机制

保障机制用于说明规范落地要求由什么规则、检查、流程、Code、Human Gate、子 Agent 思考、生命周期触发或审计动作保障执行。

规范落地要求必须绑定保障机制。只写“需要上位约束承接”“需要生命周期触发”“需要确定性执行”，但没有说明由什么保障执行，不构成完整落地声明。

保障机制可以是单一机制，也可以是组合机制。例如“规范变更后必须校验”通常需要入口提示、Code 校验、生命周期触发和降级记录共同保障。

### 3.3 环境适配映射

环境适配映射用于说明某项规范落地要求和保障机制在特定开发环境中如何实现。环境适配映射由 `specs-v2/04.02-环境适配与运行投影规范.md` 定义。

正式规范声明规范落地要求时，可以说明某项要求需要环境适配，但不得在普通规范落地要求表中直接维护具体环境实体。

---
## 4. 规范落地要求类型

正式规范可以声明以下规范落地要求：

| 落地要求 | 含义 | 常见保障机制 |
|---|---|---|
| 上位约束承接要求 | 该规范作为上位依据，需要后续正式规范、检查流程或 Human Gate 持续承接 | 上位依据字段、总纲一致性检查、专项规范转化、Human Gate |
| 入口可见要求 | AI 进入项目、文档工作区或任务场景时需要看见该规范摘要、边界或入口 | 入口摘要、项目说明、规则入口映射、目录入口 |
| 流程复用要求 | 该规范中的重复步骤需要被封装成可复用流程 | Skill、命令、工作流程、操作清单 |
| 子 Agent 思考要求 | 需要脱离主上下文、使用特定专业视角、或并行展开多个视角 | 子 Agent、独立审阅、并行审查、专项检查 |
| 确定性执行要求 | 该规范需要稳定的解析、校验、聚合、测试、上下文压缩或受控写入 | Code、测试、校验命令、CI、脚本 |
| Human 交互要求 | 该规范需要 Human 看见、确认、授权、验收或轻写入 | Human Gate、Web、对话确认、审批提示 |
| 生命周期触发要求 | 该规范需要在提交、写入、修改、停止、子 Agent 完成等事件上稳定触发 | 触发映射、CI、自动运行、定时任务、降级检查 |

子 Agent 思考要求中的独立、专项、并行是可组合维度。一个场景可以要求多个独立 Agent 分别从文档一致性、Code 可验证性和环境适配风险等视角并行审查后汇总。

---
## 5. 规范落地要求声明规则

正式规范文档应在“规范落地要求”段落中声明自身稳定规则的落地要求。

规范落地要求至少包含：

| 字段 | 含义 |
|---|---|
| 落地要求 | 采用 §4 中的类型 |
| 要求内容 | 该要求具体要保障什么 |
| 保障机制 | 由什么规则、检查、流程、Code、Human Gate、子 Agent 思考或生命周期触发保障执行 |
| 同步类型 | 初始化、入口摘要、校验实现、流程复用、展示同步、审计输入等 |
| 触发条件 | 规范变更、字段契约变化、Human Gate 变化、环境适配映射变化、运行投影漂移等 |

必要时可以补充来源章节、验证方式、降级处理和是否需要环境适配映射。

不直接定义稳定规范规则的说明性文档不默认需要声明规范落地要求。目录说明、编号索引、迁移状态索引、evals、refs、README 和项目资料文档，应先把稳定结论吸收到正式规范后，再由正式规范声明规范落地要求。

规范落地要求表不得直接维护具体环境实体。具体环境实体只应进入环境适配映射或运行投影。

---
## 6. 保障机制规则

规范落地要求必须说明保障机制。保障机制可以来自以下来源：

1. **规范结构保障**：上位依据、相关规范、正式规范骨架、章节要求、检查清单；
2. **Code 保障**：确定性校验、测试、解析、聚合、上下文压缩、受控写入；
3. **流程保障**：可复用步骤、Skill、工作流程、命令入口；
4. **子 Agent 保障**：独立审阅、专项视角、并行检查、汇总报告；
5. **Human Gate 保障**：人工确认、授权、验收、暂停和风险判断；
6. **生命周期触发保障**：触发时机、自动运行、定时检查、会话停止检查或降级检查；
7. **环境适配保障**：某项要求需要进入环境适配映射，并由 `specs-v2/04.02-环境适配与运行投影规范.md` 解释具体实体。

保障机制不得绕过事实源边界、Human Gate 或 Code 验证纪律。保障机制无法完整实现时，应记录降级方式和残留风险，不得表述为完整落地。

---
## 7. 与环境适配的边界

规范落地要求和环境适配映射必须分层维护。

规范落地要求声明：

1. 哪条稳定规范需要落地；
2. 落地需要满足什么要求；
3. 由什么保障机制保障执行；
4. 什么变化会触发同步或检查。

环境适配映射声明：

1. 某项规范落地要求在具体环境中是否支持；
2. 支持时映射到哪些环境机制、文件、配置、工具、入口或页面；
3. 不支持时如何降级；
4. 如何验证运行投影未漂移。

正式规范不得因为某个环境已有能力而反向改变规范落地要求。环境不支持某项要求时，应进入环境适配映射的降级记录，不得改写规范本身。

---
## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续正式规范声明规范落地要求时，应遵守本文定义的字段、类型和边界 | `specs-v2/03.01-规范文档规范.md` 正式规范骨架、规范文档检查 | 文档治理 | 本文 §4-§7 变化时 |
| 入口可见要求 | AI 修改 specs-v2 正式规范时应能定位本文作为规范落地要求权威入口 | 规范文档入口摘要、相关规范引用 | AI 执行入口提示 | 本文定位、适用范围或关键术语变化时 |
| 确定性执行要求 | 文档检查 Code 应能识别“规范落地要求”章节、必填字段和合法落地要求类型 | `tools/specs_validate.py` 或后续文档校验 Code | 校验实现 | 规范落地要求章节名、表格字段、类型清单或正式规范骨架变化时 |
| 生命周期触发要求 | 正式规范变更后应检查是否影响规范落地要求声明和后续环境适配映射 | `specs-v2/03.01-规范文档规范.md` 修改执行顺序、`specs-v2/04.02-环境适配与运行投影规范.md`、人工降级检查 | 触发保障 | 正式规范新增、重命名、删除、规范落地要求变化或环境迁移时 |

具体环境实体不在本文中声明，应由 `specs-v2/04.02-环境适配与运行投影规范.md` 解释。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变规范落地要求类型；
2. 改变保障机制字段或声明规则；
3. 允许正式规范直接把环境实体写成落地要求；
4. 改变规范落地要求与环境适配映射之间的权威边界；
5. 删除某项已被正式规范消费的保障机制；
6. 将不能机械验证的语义判断表述为完整 Code 校验通过。

规范落地要求检查至少包括：

| 检查项 | 标准 |
|---|---|
| 落地要求 | 正式规范声明的是要求，不是环境实体 |
| 类型 | 落地要求类型来自本文 §4 |
| 保障机制 | 每项落地要求都有保障机制 |
| 字段 | 表格包含落地要求、要求内容、保障机制、同步类型、触发条件 |
| 环境边界 | 具体环境实体未混入普通规范落地要求表 |
| Code 适配 | 可机械化检查已按 `specs-v2/14-Code实现规范.md` 判断和验证 |
| 降级处理 | 保障机制无法完整实现时已记录降级方式和残留风险 |
