## 1. 本文解决的问题

本文解决 LD Vibe Harness specs 中术语边界如何定义、机制英文专名如何使用、中文术语如何加定语、管辖项目如何定义、历史机制文件如何命名，以及术语变更如何治理的问题。

术语边界的目标是避免同一词语在 specs 中同时指代 Trae 机制、规范条款、对象规则、行动条件或普通能力，导致事实源和执行边界混淆。

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 的产品理念、价值实现标准、四类构成要素和基础规范索引。本文承接 00 中关于术语一致性和事实源单一性的要求，专门定义术语边界、机制英文专名、中文术语定语、历史机制文件命名和术语变更治理。

## 3. 术语边界职责

本文的权威领域是 LDVH 机制英文专名、中文术语定语、管辖项目定义、历史机制文件命名、Scenario 与 Rules 的术语边界、产品初始化/产品审计/检查术语边界和术语变更治理。

术语边界用于约束 specs 写作中的命名一致性。涉及具体机制细节时，仍以对应机制规范为准；本文只定义机制名、中文术语和文档标题中的命名纪律。

### 3.1 工作流程与工作闭环

工作流程与工作闭环是两个不同层级的概念，不得混用：

| 维度 | 工作流程 / Workflow | 工作闭环 / Closed Loop |
|---|---|---|
| 定义 | 具体行动规范，约束 AI 如何读取、判断、执行、停下和回写 | 端到端完成性概念，强调从意图到验证到沉淀形成完整回路 |
| 规范区段 | `specs/40-59` | 跨区段概念，不独占编号 |
| 核心关注 | 单一行动的控制规则（Context、Scenario、Gate、回写、证据） | 多行动串联后的完整性（是否形成回路、是否有反馈、是否可追溯） |
| 典型实例 | 44-任务执行、45-决策记录、46-变更记录 | Core Loop（Intent→Plan→Execute→Verify→Record→Learn→回到 Intent） |
| 关系 | 工作流程是工作闭环的组成单元 | 工作闭环由多个工作流程串联形成 |

不得将"工作闭环"用于指代单个工作流程，也不得将"工作流程"用于指代端到端回路。

## 4. 机制英文专名

LDVH specs 中，英文机制名 Rules、Skill、Agent、Tools、Web 专指 Trae 或 LDVH 辅助工具体系中的机制层：

| 术语 | 含义 | 机制规范 |
|---|---|---|---|
| Rules | Trae Rules 机制 | `specs/05-Trae-Solo环境规范.md` §6 |
| Skill | Trae Skill 机制 | `specs/05-Trae-Solo环境规范.md` §7 |
| Agent | Trae Agent 机制 | `specs/05-Trae-Solo环境规范.md` §8 |
| Tools | LDVH `tools/` Tools 辅助机制 | `specs/06-Python与Web工具规范.md §4` |
| Web | LDVH `web/` Web 信息同步机制 | `specs/06-Python与Web工具规范.md §5` |
| PyTools | LDVH `tools/` 下由 Python 构建的确定性辅助程序 | `specs/06-Python与Web工具规范.md §4` |

提到上述机制时，应使用英文专名 Rules、Skill、Agent、Tools、Web、PyTools，不使用裸中文"规则""技能""代理""智能体""程序""展示"替代。

Tools 与 PyTools 的区分：Tools 指 Tools 辅助机制层（概念、原则、职责边界），PyTools 指 `tools/` 下具体的 Python 程序实现。避免"工具"一词同时指向机制和实现，造成泛化指向。

## 5. 中文术语必须加定语

中文"规则""技能""代理""智能体""程序""展示"等词不得裸用，除非上下文已经通过标题、表格字段或段落首句明确限定其语义。

推荐用法如下：

| 场景 | 推荐术语 | 不推荐裸用 |
|---|---|---|
| specs 中定义的稳定条款 | specs 规范 | 规则 |
| 工作模型字段、状态、验收、检查 | 对象规则、字段规则、状态规则、验收规则、检查规则 | 规则 |
| 工作流程的 Context、Scenario、Gate、流程、回写、证据 | 行动规则、Scenario 识别条件、行动进入条件、Gate 条件、回写要求 | 规则、触发规则 |
| 普通能力说明 | 能力、功能、流程、方法 | 技能 |
| AI 泛称 | AI 执行者、AI 代理能力、子代理能力 | Agent、代理、智能体 |
| 确定性工具辅助 | Tools 辅助、Tools 适配、Tools 能力 | 程序、程序辅助 |
| Python 确定性辅助程序 | PyTools 实现、PyTools 脚本 | 工具程序、Python 工具 |
| Web 信息同步能力 | Web 信息同步、Web 适配、Web 信息同步层 | 展示 |
| Trae / LDVH 机制适配 | Rules 适配、Skill 适配、Agent 适配、Tools 适配、Web 适配 | 规则适配、技能适配、代理适配、程序适配、展示适配 |

## 6. LDVH 与 Harness 的关系及构成要素全称与短称

LD Vibe Harness 是 Harness 思想的实践，简称为LDVH。Harness 不是独立对象域，不作为工具、工作模型或工作流程的归属前缀。

在 00 总纲等理念层文档中，当 LD Vibe Harness 语境已经由标题、段落或章节明确限定时，可以使用"工具""工作模型""工作流程"作为构成要素短称。

在编号分区、文档标题、跨文档引用、对象规范和行动规范中，应使用"LDVH 辅助工具""LDVH 工作模型""LDVH 工作流程"等正式全称。

不得使用"Harness 工具""Harness 工作模型""Harness 工作流程"作为正式术语。

## 7. 管辖项目

管辖项目是指接入并使用 LD Vibe Harness 进行需求、任务、证据、变更、审计或交付治理的实际项目。

管辖项目与 LDVH 项目（ld-vibe-harness）的关系：

| 维度 | LDVH 项目 | 管辖项目 |
|---|---|---|
| 定位 | LDVH 规范体系的承载和维护项目 | 接入 LDVH 进行工程治理的实际业务项目 |
| 规范来源 | specs/ 定义规范 | 遵循 LDVH specs 定义的规范 |
| ldvh-base/ | 承载 LDVH 项目自身的事实实例 | 承载该管辖项目的事实实例 |
| Rules | 项目规则声明项目定位和专属硬约束 | 项目规则声明项目定位和专属硬约束 |
| 工作模型规则 | 工作模型对象在运行时需要遵守的入口约束，默认由项目规则中的事实实例硬约束、工作区规则的项目识别入口和 specs 对象规范原文共同承接 | 对所有管辖项目通用，LDVH 不使用场景规则承载工作模型规则 |

管辖项目目录由工作区规则中的管辖项目配置定义。工作区管辖项目配置是管辖项目目录列表的权威位置，决定了 `ldvh-base/` 目录应出现在哪些项目目录下。

每个管辖项目应各自拥有 `ldvh-base/` 目录，由该项目自身管理（依据 `specs/01-目录说明.md` §3.5）。管辖项目之间不共享 `ldvh-base/` 目录。

管辖项目必须遵守 LDVH 工作模型基础规范（`specs/07-工作模型基础规范.md`）和工作区规则中的管辖项目配置、项目识别入口及项目规则中的事实实例硬约束。工作模型的字段契约、状态机、Human Gate 和引用完整性规则由 LDVH specs 统一定义，对所有管辖项目通用；其运行时入口约束由工作区规则、项目规则和 specs 原文共同承接，不使用场景规则承载。

## 8. 历史机制文件命名中的机制名

工作模型和工作流程的 `NN.01` 至 `NN.06` 历史机制文件使用机制英文专名：

| 历史机制文件 | 机制含义 | 不承载内容 |
|---|---|---|
| `NN.01-Rules.md` | Rules 入口约束实践子文档 | 不承载对象规则、行动规则、Scenario 完整识别条件或完整 SOP |
| `NN.02-Skill.md` | Skill 契约式行动实践子文档 | 不承载普通能力说明，不替代行动流程或对象规范 |
| `NN.03-Agent.md` | Agent 独立上下文并行实践子文档 | 不承载泛化 AI 代理说明，不替代 Agent 定义摘要或 Trae 平台实体 |
| `NN.04-Tools.md` | Tools 契约式校验与执行实践子文档 | 不承载业务事实，不替代 Tools 实现或事实源 |
| `NN.05-Web.md` | Web 信息同步实践子文档 | 不承载 UI 状态作为事实源，不替代 Web 实现 |
| `NN.06-Contract.md` | 结构化契约文件 | 不承载主模型规则，只定义结构化契约、字段 schema、接口契约和数据结构 |

历史机制文件的内容边界依据 `specs/03-文档规范.md` §4.3，主模型或主流程核心内容应留在 `NN` 主文件。机制适配只说明边界，不承载具体实现代码。

历史机制文件属于迁移前过渡资料。主文档应保证模型或流程定义完整可读，机制文件只在实践内容复杂或需要独立维护时按需保留。机制文件可以承接 Rules 入口约束示例、Skill 契约式行动输入输出、Agent 上下文隔离映射、Tools 契约式校验字段、Web 信息同步字段等历史实践内容，但不得把主模型核心规则迁移到机制文件中维护。

NN.01-NN.06 为历史机制文件。它们都不重新定义主模型或主流程，但性质不同：NN.01-NN.05 回答"这个模型或流程曾如何实践某个机制"，NN.06 回答"这个模型或流程的结构化接口、schema 和数据契约是什么"。结构化契约文件不得承载主模型的对象定位、状态机、Scenario、Gate、执行流程或 Human Gate；这些内容应留在主文档。

### 8.1 历史机制文件标题命名维度规则

历史机制文件标题格式为：`{主模型名} — {机制名}{实践类型}`。结构化契约文件标题格式为：`{主模型名} — 契约`。

标题命名遵循以下维度规则：

1. **机制名必须使用 LDVH 标准术语**：机制名必须使用 Rules / Skill / Agent / Tools / Web，不得使用功能替代词（如"常驻上下文"替代 Rules）、承载方式（如"预制脚本程序"替代 Tools）或实现形式（如"网页信息呈现"替代 Web）替代；
2. **实践类型使用历史标准名称**：历史机制文件中，`NN.01-Rules.md` 对应 Rules 入口约束实践，`NN.02-Skill.md` 对应 Skill 契约式行动实践，`NN.03-Agent.md` 对应 Agent 独立上下文并行实践，`NN.04-Tools.md` 对应 Tools 契约式校验与执行实践，`NN.05-Web.md` 对应 Web 信息同步实践；该命名仅用于解释迁移前文件和仍保留的过渡资料，不构成新增工作模型或工作流程的完整性要求；具体模型不得自行替换为流程实践、上下文隔离实践、能力实践、展示实践等其他实践类型名称；
3. **实践类型命名不设置局部选项**：历史机制文件不得按局部实现方式选择其他实践类型名称；如某机制在特定模型中不创建实体或暂缓实现，应通过文件状态和正文说明表达，不得通过改变标题实践类型表达；
4. **语义定义由区间基础规范补充**：NN.01-NN.06 各编号的语义定义由 07 §4.6（工作模型）和 08 §4.6（工作流程）在各自机制适配边界表格中补充。本文不重复维护。

本规则是历史机制文件标题命名的权威位置。07 §4.6 和 08 §4.6 的标题格式规则应引用本规则，不得并行维护同一命名维度约束。

## 9. Scenario 与 Rules 的边界

工作流程判断何时进入某行动时，应使用"Scenario 识别条件"或"行动进入条件"。

Rules 可以通过短摘要提醒 AI 评估某个 Scenario，但不应在 Rules 历史机制文件中维护完整 Scenario 识别条件、角色矩阵、报告模板、执行流程或对象规则。

## 10. 产品初始化、产品审计与检查

产品初始化是指将 LDVH 规范体系整体转化为项目实际可用实践的初始化计划和首次执行动作。它关注"设计如何进入实践"，例如：创建必要目录、创建或更新 Rules 摘要、创建 Skill 实体、确认 Agent 可用清单、准备 Tools 校验能力、配置信息同步型 Web 入口、建立索引引用和记录暂缓项。产品初始化是产品级操作，不是每个工作模型或工作流程各自选择初始化内容。

产品审计是指对已经完成或声称完成的产品初始化结果进行审查，确认对应实践是否真实存在、持续有效、与 Git 文件事实源一致、未绕过 Human Gate，且未与上位规范或权威事实源冲突。产品审计关注"实践是否按设计落地并持续有效"。

检查是指依据 specs、Rules、对象规范、工作流程或工具规范中的明确条款，对某份文档、对象实例、行动执行、工具输出或机制实践进行符合性检查。检查关注"对象是否符合既有规范要求"。具体检查类型包括：生产对象规范写作检查、实例数据检查、集合一致性检查、产品初始化完整性检查和行动特有检查。

三者关系如下：

| 概念 | 核心问题 | 典型对象 | 输出 |
|---|---|---|---|
| 产品初始化 | 设计如何进入实践 | 目录、Rules、Skill、Agent、Tools、Web、索引、初始化记录 | 初始化计划、初始化产物、暂缓项 |
| 产品审计 | 实践是否真实落地并持续有效 | 已初始化的实践内容和事实源 | 审计结论、缺口、整改建议 |
| 检查 | 是否符合规范条款 | 文档、对象实例、行动输出、工具输出、机制实践 | 检查结果、违规项、修正建议 |

产品初始化、产品审计和检查是不同层级的治理概念。产品审计可以使用检查作为检查手段，但不得把检查等同于产品审计；产品初始化可以产生后续检查所需的事实源或对象，但不得被写成检查清单。

产品初始化、产品审计和检查是产品级治理概念，应在对应基础规范中定义概念和边界。具体工作模型主规范只定义对象特有实例检查；具体工作流程主规范只定义行动特有检查。产品初始化和产品审计由工作流程区段中对应工作流程负责执行。

## 11. 术语变更治理

## 13. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变本文定义的术语边界或 Rules、Skill、Agent、Tools、Web 的机制名含义；
2. 改变 LDVH 与 Harness 的关系定义，或将 Harness 前缀作为工具、工作模型、工作流程的正式术语；
3. 将中文"规则""技能""代理""智能体""程序""展示"等裸用词提升为正式术语；
4. 改变管辖项目的定义或管辖项目目录配置的权威位置；
5. 改变 `NN.01` 至 `NN.05` 历史机制文件的机制含义或命名维度规则；
6. 改变 `NN.06` 结构化契约文件的定位或承载边界；
7. 将 Scenario 识别条件、行动流程或对象规则转移到 Rules 历史机制文件；
8. 让 Skill 适配文件承载 Agent 调度；
9. 让 Agent 适配文件替代 Trae Agent 实体定义；
10. 让 Tools 适配文件承载具体实现代码或替代事实源；
11. 让 Web 适配文件承载 UI 状态作为稳定事实；
12. 让结构化契约文件承载主模型的对象定位、状态机、Scenario、Gate、执行流程或 Human Gate。

当 AI 识别到上述情况时，依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §5.3 Human Gate 闭环执行。

术语规范检查至少包括：

| 检查项 | 标准 |
|---|---|
| 机制英文专名 | Rules、Skill、Agent、Tools、Web 使用英文机制名 |
| 中文术语定语 | 中文"规则""技能""代理""智能体""程序""展示"等词已加定语或上下文限定 |
| LDVH 与 Harness 关系 | LD Vibe Harness 是 Harness 思想的实践，简称为LDVH；Harness 不作为构成要素归属前缀 |
| 管辖项目定义 | 管辖项目定义与工作区规则管辖项目配置一致，ldvh-base/ 目录位置与配置匹配 |
| 历史机制文件命名 | NN.01-NN.05 使用机制英文专名，NN.06 为结构化契约文件 |
| 术语变更治理 | 术语变更已评估 Human Gate |
| 架构术语一致性 | 与四类构成要素、工作模型和工作流程术语一致 |
