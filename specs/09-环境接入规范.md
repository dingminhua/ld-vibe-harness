## 1. 价值判断

本文的价值，是让 AI 和 Human 能分别判断四项工作：环境接入是否已取得源码仓库、部署薄 Skill 并真实递达；管辖配置是否经 02 建立或核验；承接 Git Gate 的 Git Hook 是否已部署到目标 Git common-dir；验证是否对前三项及 Git Gate 真实事件取得范围匹配证据。每项的权威仍由对应当前规则源与实际结果提供，环境侧文本不得复制规则、模板清单、事实 Schema 或判断逻辑。

本文主要服务：

1. V1 快速定位：每个环境只有一个 LDVH 薄 Skill，能够回指当前源码仓库、其实际 Helper 和目标工作对象；
2. V2 充分理解：接入结果保留 Helper 的来源、范围、部分结果、失败和未证明条件；
3. V3 边界识别：区分厂商技能机制、Skill 文本合同、Helper 契约、管辖配置和真实递达；
4. V4 稳定推进：环境接入、管辖配置、Git Hook 部署、升级、禁用、卸载和失败回滚具有清楚边界；
5. V5 据实判断：接入声明绑定目标环境、版本、部署件、会话和当次实际证据；
6. V6 工作接续：Skill 在其真实被加载的时机把同一路由纪律交给后续 AI；
7. V7 清晰沟通：能力不足、授权、断点、失败、回滚和未验证范围能够如实交还。

环境接入的价值来自消除环境侧规则副本与错误宣称，不来自要求所有环境具有相同技能机制、加载时机或表现。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：规定环境接入以薄 Skill 承载路由纪律，规则与能力由 CLI 从当前规则源现取，所需的确定性程序由 Code 实现，并保留 AI、Code、Web、Human 与三类语义构成要素的上位边界；
2. `work-object-governance-scope`：规定接入行动必须使用的工作对象、工作区根、管辖项目配置和解析结果；
3. `source-of-truth-traceability`：规定环境观察、部署结果、递达结果、诊断和回滚结果的信息作用、当前性及来源回指；
4. `helper-cli-service-contract`：规定 Helper 公开请求、响应、能力、部分结果和错误边界。

`code-engineering-practices` 约束 CLI 与 Git Gate 的 Code 和 tests，但不定义环境接入语义。`action-template-foundation` 及具体模板可以组织重复行动，但不反向定义本文的成立条件。厂商资料只定义对应环境的技能机制事实，不定义跨环境共同规则。

## 3. 职责边界

本文负责定义：

1. 薄 Skill 接入单元的内容合同：职责闭集、禁止项、环境中性、模板唯一来源、分发与新鲜度判据；
2. 规则引导与行动模板的路由纪律、降级路径与路由不可用时的交还；
3. 源码仓库能力本体、仓库入口与诊断性 CLI 直调的边界；
4. 承接原生阻断型机械 Git Gate 的 Git Hook 的必部署要求、Git common-dir 覆盖边界与逐事件绑定；
5. 环境接入、管辖配置、Git Hook 部署与验证四项工作及其升级、禁用、卸载、共存和回滚的共同成立条件；
6. 接入声明所需的证据边界与能力判定（`unsupported` 与 `unverified`）；
7. 跨环境共同规则与单一环境机制事实的分界。

本文不负责定义：

1. `LDVH-GOVERNED-PROJECTS.yaml` 的位置、字段、发现、有效性或管辖判定；
2. Helper 命令、请求/响应字段、退出码、领域操作、规则或事实语义；
3. 规则引导的内容与行动模板的内容；
4. Git Gate 的封闭纯机械合格条件；
5. 某厂商的技能目录、加载时机、权限、manifest 或 UI；
6. 环境 Hook、插件或 adapter 接入形态——本规范不定义该形态，LDVH 接入面无此层；
7. 某次部署、配置、修改、卸载或外部环境操作已经获得 Human 授权；
8. 所有环境必须具有技能机制、阻断能力或相同结果表现。

02 唯一定义管辖配置；04 唯一定义 Helper 外部服务；07 定义 Code/tests 共同工程要求；00 与 01 定义规则引导内容；30–34 定义行动模板；Git Gate 合格条件由其定义来源唯一承载。本文不改变这些责任。

## 4. 适用范围

本文适用于：

1. 准备在目标环境部署、检查、升级、禁用、卸载或回滚薄 Skill 接入单元；
2. 准备声明 Skill 已部署、已递达，或 AI 已真实取得规则引导与当次行动模板；
3. 取得、更新、检查或直接诊断源码仓库及其 CLI 入口；
4. 准备为受管辖 Git common-dir 部署、检查、卸载或回滚承接原生 Git Gate 的 Git Hook；
5. 在同一接入行动中配置或核验目标项目的管辖配置与当次管辖解析；
6. 目标环境无技能机制、递达失败、部署冲突或卸载残留需要分流。

直接调用 Helper 或其它源码入口可以按 04 与具体领域来源执行当前已定义的正式能力；它不构成另一种 AI 环境路由形式，也不能替代薄 Skill 的部署与真实递达。环境机制说明只有在说明具体环境时受本文约束，不因记录现状而成为规则源。

## 5. 唯一接入单元：薄 Skill

### 5.1 单一单元与权威边界

一个目标环境只应部署一个承接 LDVH 的 Skill，不得按行动模板、事实类型或项目分别部署多份规则副本。接入链路必须区分三个层次：厂商技能机制（只提供加载时机与文本递达，不定义语义）；薄 Skill 文本（本文 §5.2 的内容合同，只承载路由纪律）；CLI 交付（04 定义的 Helper 公开操作、01 定义的规范读取、30–34 定义的行动模板，是唯一权威）。Skill 不取得 Helper 之外的语义权威。

LDVH 提供环境无关的接入方法，不负责预先调查或维护全部 AI 开发环境的厂商步骤。处理目标环境的 AI 依据该环境当前官方或实际权威资料，识别其技能机制的技能位置、加载时机、可见会话范围和权限，再对照本文形成当次方案。厂商是否使用 `Skill` 这一名称不决定机制是否存在；判断对象是该机制能否把 SKILL.md 文本递达给 AI。

目标环境没有技能机制时，完整接入不成立：CLI 仍可按其来源执行当前已定义的正式能力，但不得把直调表述为 AI 环境路由或 Skill 接入，也不得为该环境改投环境 Hook、插件或 adapter——接入面无此层。能力缺口按 §8 判定并如实交还。

### 5.2 SKILL.md 内容合同

SKILL.md 是环境侧唯一的 LDVH 文本，只承担下列职责闭集：

1. 身份告知：声明当前项目可能受 LDVH 管辖、LDVH 是什么、权威在 CLI；
2. 规则引导路由：会话开始、恢复或上下文压缩后继续时，按 §5.4 取得当次规则引导；
3. 行动模板路由：动手落入 LDVH 领域（事实写入、规范修订、提交、接入动作或任何 30–34 模板覆盖的行动）前，按 §5.5 现取当次行动模板并照其执行。

下列固定表述只如实声明上述三项职责所处的能力边界，不增加第四项职责，也不把 SKILL.md 变成第二规则源：

薄 Skill 对事实写入的保护仅为劝告级：它只能将 AI 路由到 Helper 与行动模板，不能在模型之外机械阻断对 `ldvh-base/` 的直写。

承接 Git Gate 的 Git Hook 以 Git common-dir 为部署边界：一次部署覆盖共享该 common-dir 的主 worktree、现有 linked worktree 与后续新建 linked worktree；纳入当次完整接入目标的独立 clone 具有不同 common-dir，必须单独部署，未纳入目标时不为验收创建或部署。每个真实 Git 事件仍只绑定 actual worktree、当次 Index 与 commit message；未触发承接 Git Gate 的 Git Hook，或绕过 Git Gate 检查的行动不在覆盖范围。

机械检查能够发现来源已定义的机械不合格，不能据此判断事实内容的语义真实性；即使 Schema 合法，语义污染风险仍然存在，未提交污染窗口只能压缩、不能消除。

薄 Skill 的默认部署范围为用户级（跨多个工作区或项目可见）：它只负责把落入 LDVH 领域的会话路由到 Helper CLI，不承担管辖判断，管辖边界由 `resolve-governance-scope` 按 02 单独保障。因此在目标环境技能机制支持用户级范围时，除非 Human 明确要求限制可见范围，否则按用户级部署；仅当 Human 明确要求时，才部署到项目级或工作区级。该默认值只说明技能可能在哪些会话被加载，不等同于项目已纳入管辖，也不改变本文 §6.3 要求按当次计划单独确认实际部署位置与可见会话范围的义务。

禁止项：

1. 不得复制规则正文、规范章节、行动模板正文或事实 Schema；
2. 不得写死行动模板清单、Helper 操作清单、信封字段或调用参数——一律现取；
3. 不得写死机器绝对路径或未交付的相对路径：只使用 09.Att.01 标记为已交付、且已解析到当次确认源码仓库的入口；未交付或不可得时如实交还迁移缺口；
4. 不得出现特定环境名称，不得断言任何环境的自动加载、触发或递达状态；
5. 不得把 `partial`、`unavailable`、未验证写成成功、生效或已保障。

### 5.2a Helper 调用参数纪律

SKILL.md 必须含有一条固定的 Helper 调用参数纪律，内容如下：

> 调用任何 LDVH Helper 公开操作（`resolve-governance-scope`、`prepare-fact-object-draft`、
> `create-fact-object`、`read-fact-objects`、`update-workcase` 等）时，**一律不提供
> `arguments.workspace_root`**。依赖规范 02 §6.2 与 §10.1 定义的自动发现机制：
> 不传时，CLI 以 cwd（应在实际 Git worktree 内）作为定位符，从该 worktree 根沿父
> 目录链向上查找 `LDVH-GOVERNED-PROJECTS.yaml`，跳过仓库内同名文件，遇第一个
> 候选即停；不从定位符子路径、`cwd`、Git common-dir 或平行目录另开查找路径。
>
> 下列情形才可传 `workspace_root`：
> - Human 在当次会话中明确指定了一个工作区根路径；
> - 传值时只在该路径下读取配置，不向上查找，也不从其它来源增加发现路径。
>
> AI 不得自行猜测或传递路径。若自动发现返回 `missing`，如实报告给 Human，由 Human
> 决定是否显式指定工作区根，AI 不得另猜路径重试。
>
> 此纪律不改变 Code 行为，只约束 AI 调用方式。违反纪律会关闭自动发现并造成
> 配置 miss，其故障根因在调用方而非 Code；审计追溯由 02 §6.2-5 强制返回实际
> 选定配置与依据兜底。

本文该条文只固定在 SKILL.md 内容合同中；它在任何环境进程的 SKILL.md 文本里都必须保持同文，不得因环境、项目、`cwd` 或任务文字而改写。Helper 操作信封与参数仍以 capabilities 与 04 的当次内容为准，本文不复制或新增参数，也不新增 `workspace_root="auto"` 或任何新参数。

### 5.3 模板唯一来源与分发

SKILL.md 的唯一定义来源是 LDVH 源码仓库中的 canonical 模板 `skill/SKILL.md`。任何环境的部署件必须与当前仓库模板逐字节一致；模板不含任何逐环境值，部署即复制文件。部署件与当前模板不一致即过期，处理为重新部署并重新验证受影响范围。模板内容只能随本文修订变化；canonical Skill 的具体修改治理（逐段对比、独立审核、Human Gate、独立 commit 等）由 00 §10.1 第 13 项定义。不得手工修改部署件，也不得为某一环境单独改进。

图标资产的唯一来源是 LDVH 源码仓库根目录 `icons/`（多尺寸 PNG 与源图，内容只能随本文修订变化）。图标配置属于厂商技能机制的可选外观能力，不构成接入成立条件：处理方必须依据目标环境当前官方或实际权威资料，先判定该环境是否支持技能图标及其配置方式，再使用该目录素材执行配置；目标环境无此机制或其机制无法确认时如实交还，不得伪造配置路径、不得静默跳过、不得把图标配置写成真实递达或接入成功的证据。图标配置不进入 SKILL.md 文本，部署件逐字节一致要求不因图标配置变化。

当前源码仓库必须提供可检查的接入面说明或唯一发现入口，使目标环境 AI 能够取得当前实际存在的源码入口、Skill 模板位置、图标资产位置、Git Hook 管理入口与 Git Gate 核心入口，以及每项入口的适用来源、输入、输出、`partial`/错误和反馈边界。未实现的目标入口必须明确标记为缺口，不得登记成当前已交付能力。该说明只投影既有来源与实现，不建立第二份权威、登记或新的 Helper 操作。

上述接入面说明由授权附件 09.Att.01（`specs/attachments/09.Att.01-环境接入面.md`）承载；附件登记源码模式要求的入口、资产、当前实际交付状态与迁移缺口，并对已交付入口展开输入、输出与失败边界。它不定义厂商事件、部署路径或接入结论，也不新增入口、Helper 操作或权威来源。

### 5.4 规则引导路由

AI 经已交付的源码 Helper `read-specification-content` 精确读取 00 §8.1 与 §8.2 的 L3 原文，并把实际使用路径与取得范围如实报告。该读取按照 01 §9.10 `work-context-rule-orientation` profile 定义的内容选择，只交付规则引导原文、来源、已完成范围和缺口，事实侧状态恒为 `not_requested`，不做管辖解析、项目候选、事实发现或事实恢复。读取只帮助 AI 定位和理解规则，不形成环境层的适用判断、Human Gate 判断、Human 决定证据、行动允许或完成裁决。

在宿主原生提供匹配 09.Att.01 `work-context-core` 合同的生命周期事件对象，且该源码入口可用的环境中，AI 也可以经 `ldvh work-context` 入口取得相同规则引导；该入口不可用时不经此路径，不新增环境 Hook 或 adapter。

某次会话没有取得规则引导，只能据实形成读取缺口；除非另一项当前来源已经对同一原生事件封闭定义了机械 Git Gate 及失败方式，不得仅因缺少规则引导而阻断普通求解。

AI 已依据当前目标明确进入 05 §8.1 的事实消费分支，且 09.Att.01 将 `context-recovery` 源码入口标记为已交付时，事实恢复投影必须把 Helper 实际 coverage 与交付的 `delivery_coverage` 分开报告；入口未交付时如实交还迁移缺口。项目候选、binding、事实 coverage、WorkCase 候选和按需展开由共享 Code 按 02、05 与 21 唯一解释；缩减不得吞掉 `partial`、未读 cursor、无效/不可读对象、输入不足或来源缺口，也不得把候选写成当前任务绑定。

### 5.5 行动模板路由

动手落入 LDVH 领域前，AI 必须经 `read-action-template-candidates` 定位、经 `read-action-template-content` 读取当次适用的行动模板，并照模板执行其中的机械检查与强制项。模板清单、版本或内容不得凭记忆、旧副本或 Skill 文本假设；模板不可得或读取为 `partial` 时如实交还缺口，不得以“知道流程”为由继续受控写入或其它高影响行动。

### 5.6 CLI 核心接口与直接调用边界

任何环境都可以从 shell 直接调用源码仓库提供的 Helper 与其它 CLI 入口；直调受 04 与具体领域来源约束，可以执行其当前已定义的正式能力，但只证明当次 CLI 调用范围，不形成与薄 Skill 并列的 AI 环境路由，也不能把未部署或未递达的 Skill 补写成完整接入。受控写入只能经 05 §11 定义的受控操作；直写受管事实载体是 05 与 31 定义的禁令，本文不重复其条件。

### 5.7 原生阻断型机械 Git Gate

完整 LDVH 接入必须部署一个原生 Git Hook bundle：`prepare-commit-msg` 只在存在有效 `LDVH_SIGNATURE` 快照时写入三字段 trailer，`commit-msg` 承接最终 Git Gate；后者是整套 LDVH 的最终闸门，不是可选分支。两个按 Git 事件名固定的入口只可转交同一受控源码实现，不得各自复制规则或形成第二套逻辑。只有其它当前正式来源已经独立定义封闭的纯机械合格条件，且原生事件确实只能就地允许或阻断时，`commit-msg` Hook 才可直接调用该条件的唯一核心 Code 实现。Git Gate 只接收实际事件提供的输入，必须在同一实际候选、来源、管辖和 Index 身份上得到可验证绑定；输出只限 allow/block 与可回查诊断。任一绑定缺失、读取失败或漂移均阻断。Git Gate 本身不得写入 message、Index 或历史；`prepare-commit-msg` 以外的 Hook 不得借此写入 message；任何 Hook 都不得判断本地最小增量、自然语言语义、行动授权、验证充分性或完成，也不得建立第二份 Schema、规则源、状态、登记或语义权威。过程中的行动模板路由、受控写入、写后回读、事实完整性审计和 Human Gate 等机械检查与纪律仍分别按其来源执行；Git Gate 不替代它们。

同一机械检查另有 Helper 公开操作（`precheck-git-commit`）供 AI 主动预检时，不表示 Git Gate 改为调用 Helper，也不允许形成两套检查。两个入口必须按照同一当前来源形成检查输入，观察各自当次绑定候选并调用同一份确定性检查实现；Helper 以结构化结果支持 AI，Git Gate 以真实环境事件输入重新检查并只映射 allow/block。任一入口的旧结果不得替代另一入口对其当次实际输入的检查。

本文的 Git Gate 是由 Code 实现、按来源已定义闭集条件自动执行的机械检查；Human Gate 是来源规范保留给 Human 的判断、授权、方向校正、风险接受或验收节点；二者互不替代。

Git Gate 的闭集只属于其来源明确指定的同一原生事件，不是目标环境内 AI 行动的许可白名单。不得维护“允许的全部工具/命令/动作”登记，也不得把未映射、未识别或新增的名称默认判为 block。未进入来源定义的 Git Gate 的其它行动是否允许，按 Human 当前指令和各自适用来源判断。

承接原生 Git `commit-msg` Git Gate 的 Git Hook bundle 以 Git common-dir 为唯一部署边界。部署前必须由一个显式 actual worktree 解析并验证其 common-dir，且既有管辖解析针对该 worktree 返回 `governed_single`；不得从任意或隐式 cwd、相邻 worktree 或历史路径猜测部署目标。管理器必须把 `prepare-commit-msg` 与 `commit-msg` 作为同一版本的完整 bundle 预检、安装、升级、检查、卸载与回滚：任一成员未知、绑定不符或写入失败时不得留下半部署状态。一次部署必须使共享该 common-dir 的主 worktree、全部现有 linked worktree 以及后续新建 linked worktree 在其真实 `prepare-commit-msg` 与 `commit-msg` 事件中分别触发受控注入与同一 Git Gate；新建 linked worktree 不要求重复部署。纳入完整接入目标的独立 clone 具有不同 common-dir，必须作为独立部署边界另行部署、验证和回滚。

common-dir 级共享只共享 Git Hook 部署，不合并工作事件。每次真实事件必须由 Git Hook 取得并由 Git Gate 核心重新验证实际触发事件的 worktree、该 worktree 当次 Index 与 commit message；不同 worktree 的工作区内容、Index、未提交内容、候选身份与结果不得相互推断、替代或合并。未触发承接 Git Gate 的 Git Hook、使用 `--no-verify` 或其它方式绕过 Git Gate 检查的行动不在 Git Gate 覆盖范围；不得据此宣称全局阻断。

## 6. 环境接入、管辖配置、Git Hook 部署与验证边界

### 6.1 四项工作与执行/目标环境区分

一次完整环境行动必须把以下四项工作分别说明，不能以其中任一项的完成替代另一项：

1. **环境接入**：取得并锁定 LDVH 源码仓库、实际修订和仓库入口，将 canonical SKILL.md 部署到目标环境技能位置，并确认目标环境真实加载 Skill、AI 经路由取得规则引导与行动模板；默认流程不构建或安装 LDVH wheel、sdist、editable distribution，也不以 pip 安装 LDVH 本体作为成立条件；
2. **管辖配置**：按 02 对目标项目的工作区、工作对象与管辖配置进行建立或核验，并以当次实际管辖解析结果确认范围；已有有效配置不需重写，需要新增、删除或修改时必须作为独立计划项取得授权；
3. **Git Hook 部署**：从一个经管辖解析确认的 actual worktree 解析目标 Git common-dir，并把承接 Git Gate 的 Git Hook 部署到该 common-dir；此项是完整 LDVH 接入的必需工作，不得降为可选；
4. **验证**：对环境接入、管辖配置与 Git Hook 部署分别取得静态、直调、真实递达/触发、主要风险和回滚或不适用范围的相称证据，并如实交还未验证范围。

四项工作全部成立，才能声明当次范围的完整 LDVH 接入成立；缺少任一项都只能交还已完成的子范围与缺口。

在形成方案、逐事件交还或验收结论前，执行者还必须区分并锁定**执行环境**与**目标环境**：前者是 AI 当次实际运行并进行观察的产品/运行器、版本、平台和可观察运行位置；后者是本次拟部署、检查或验证接入单元的环境、版本、平台和目标位置。交还必须说明两者是同一环境、不同但可访问、不同且当前不可访问，还是尚未确认，并回指当次识别依据。目标尚未锁定时，只能继续无副作用调查，或按 33 交还目标确认请求；不得把候选环境列表写成接入结论。

### 6.2 静态观察、可调用与真实递达

下列观察互不替代：

1. 源码仓库、文件或配置存在，只证明当次静态对象被观察到；
2. 源码入口中的 Helper 可以从 shell 或测试入口直接调用，只证明当次 CLI 调用能力与实际结果范围；
3. SKILL.md 已复制到目标环境技能位置，只证明部署件存在且可与当前模板比对，不证明环境已加载或 AI 已取得引导；
4. 管辖配置存在、可读或写入成功，只证明对应静态对象或当次变化；只有按 02 对显式工作对象形成当次解析结果，才证明该结果声明的管辖范围；
5. Git Gate 核心可以从测试入口直接调用，只证明当次机械检查入口，不证明真实事件已产生 allow/block；
6. 目标环境在代表性真实会话中由 AI 经路由取得规则引导与当次行动模板，只证明 Skill 链路当次真实递达；Git Gate 对 actual worktree、其当次 Index 与 commit message 形成可回指的 allow/block 与诊断，只证明 Git Gate 链路当次真实触发；
7. 只有源码仓库与入口、Skill 静态部署与真实递达、管辖配置与当次解析、common-dir 级 Git Hook 静态部署与逐 worktree Git Gate 真实触发，以及来源要求的成功、失败、能力差异和回滚检查均取得范围匹配证据，才能声明完整接入已经验证。

任何一项通过都不得自动扩张到后续项目、会话、环境版本、其它事件、阻断能力或永久接入状态。环境或部署件变化后，原证据只能作为历史输入，必须重新检查受影响范围。

环境无关 doctor 只允许读取当前 LDVH 源码仓库身份与核心入口、显式提供的工作对象和管辖解析、LDVH 自有配置可读性、已交付接入面静态存在及当前调用或验证缺口。根级 `docs/` 是临时说明材料；其存在、缺失、文件名、内容、新旧程度或是否进入任何发行包不得成为 doctor、环境接入、能力可用性、`ready` 状态、Git Gate 或实现验证的输入或成立条件。它不得扫描、猜测或修改未显式提供的目标环境配置，不得把历史真实递达解释为当前仍已接入，也不得写用户或全局配置、安装外部工具、登录、接受信任或触发重启。doctor 成功完成只证明诊断本身可用，不证明任何目标环境已经接入。

源码模式 doctor 的输出合同保持为 `ldvh-doctor/1`。调用方必须显式提供绝对 `workspace_root`、非空 `work_object_locator` 和已交付的绝对源码 Helper launcher；runner 使用最多 20 秒的单次 Helper 调用边界，先读取 Helper capabilities，再调用 04 已定义的 `resolve-governance-scope`，不新增 Helper 操作。输出至少包含合同、总体 `status`、当前源码仓库身份与修订、Helper 调用观察、配置与管辖结果、接入面交付状态、逐项 checks、limitations 和 diagnostics；接入面成员只投影当前源码仓库已有入口、角色与来源，不复制其输入输出协议。

doctor 的 `status` 只使用 `ready`、`attention`、`unavailable`：Helper 和显式配置/管辖均可用且已交付接入面静态存在时为 `ready`；诊断完成但配置、管辖或静态入口存在缺口时为 `attention`；输入无效、Helper 无法形成合同响应或诊断本身无法完成时为 `unavailable`。`ready` 与 `attention` 进程退出 0，`unavailable` 退出 1；三者均不表示目标环境已经部署、真实递达或通过真实验证。

### 6.3 四项工作与变更计划

首次完成、升级、修复、禁用、卸载或迁移前，必须先只读确认：四项工作的当前状态；目标环境及版本；工作区和工作对象范围；当前规则源与当次实际适用的 CLI 入口可达性；现有 Skill、管辖配置与 Git Hook 部署件；用户既有配置、权限要求、冲突、计划写入或删除、明确不变范围、验证入口及回滚方式。

Skill 部署位置及其可见会话范围（例如目标环境实际支持的用户级、工作区级或项目级范围）必须在计划中单独确认。目标环境技能机制支持用户级范围时，默认按 §5.2 的用户级部署，仅在 Human 明确要求限制可见范围时才部署到项目级或工作区级。该范围只说明技能可能在哪些会话被加载，不等同于项目已纳入管辖、当前任务相关、规则已经适用或项目事实已经读取。范围覆盖多个工作区或项目时，范围内 Skill 仍只交付同一路由纪律；不得依据项目路径、名称、`cwd` 或任务文字筛选、改变或停止该交付。是否继续取得项目事实，仍由 AI 依当前目标和来源规则决定。

环境变更计划必须将 LDVH 管理对象与未知或用户管理对象分开。不得覆盖、截断或删除无法证明由 LDVH 管理的技能、配置或脚本；需要替换、合并或放弃既有用户配置时，进入 Human Gate。

执行只能覆盖 Human 当前指令已授权，且适用于该行动的全部来源规则许可条件已经成立的目标、环境和写入范围。Skill 或 Git Hook 部署授权不自动包含管辖配置写入；管辖配置是四项工作之一，但它的写入必须在方案中单列并取得覆盖该对象与副作用的 Human 授权。事实源初始化、Git commit、重启环境、接受平台信任提示、删除旧资产或安装其它工具仍分别依据实际适用的来源规则和 Human 当前指令判断。

LDVH 核心的默认载体唯一为源码仓库。默认接入不得构建或安装 LDVH wheel、sdist、editable distribution，不得要求 pip 安装 LDVH 本体，也不得把 Python distribution metadata 或 console entry point 作为核心可用或完整接入的成立条件。运行依赖的准备与 LDVH 本体打包是两个问题：如仓库入口依赖外部运行时或第三方库，只能按仓库当前声明准备并验证该运行条件，不得借此把 LDVH 本体改成默认安装包。

判定“已有可用核心”必须完成源码身份确认，而非只看命令存在：①显式取得源码仓库绝对路径；②记录其 Git remote（存在时）、当前 revision 与工作树状态；③09.Att.01 已将稳定源码 Helper launcher 标记为交付，且该入口确实解析到当前源码而非其它安装副本；④该源码 Helper launcher 的 capabilities 返回当前公开能力。四项不全按迁移缺口、修复或重新取得源码处理，不得把“命令存在”写成版本正确。

当前已验证平台为 macOS 与 Windows（受控写入，`file_only` 耐久，仅限 NTFS fixed drive）。Windows 受控事实写入已按 05 §11.8 条件 (a)–(c) 获准：仅限 NTFS fixed drive，耐久等级为 `file_only`，残留风险（断电后目录项可能回退至替换前完整旧文件，不会产生损坏文件）已由 Human 于 2026-08-07 经 Human Gate 接受；其仓库入口、运行依赖、路径写法与 Git Hook 执行能力已在目标平台（win32 / NTFS fixed drive / Python 3.13.14）实测通过（证据见 study-0025），环境接入一致证据已具备，故 Windows 声明为已验证平台，完整接入成立的声明门槛已满足。其它平台按未验证范围处理；未在目标平台实测前，不得声明该平台受支持，如实交还缺口。

#### 6.3.1 平台声明的变更触发与失效

当受管辖 worktree 的 Git Index 包含平台相关面清单（按 07 相应条款界定）内文件的改动时，该 worktree 的「已验证平台」声明中受影响平台侧自动失效，回退 `unverified`；未受影响平台侧的已验证声明不受本次触发影响。

失效的平台侧只有满足以下任一条件后方可恢复 `verified`：

1. 在目标平台实际执行范围匹配的测试并全部通过，且测试结果绑定到当前 worktree；或
2. AI/Human 判断改动不影响目标平台运行时语义，并在 commit message 中以 `Platform-Affected: unaffected` 声明。

平台相关面清单随多个平台陆续声称已验证而可能不断演变；机械扫描能够发现来源已定义的清单内路径匹配，不能据此判断改动是否真的改变了另一侧平台的运行时语义，该语义判断归 AI/Human。恢复验证的测试结果或判断依据须保留在对应 WorkCase 或 Study 中，作为 07 相应条款要求维护清单的依据之一；机械 glob 清单随代码演进而同步更新，语义级「擅入」由 AI 在 Code review 中识别并建议补充清单条目。

### 6.4 管辖配置边界

管辖配置是完整接入的四项工作之一。接入流程必须读取 02 定义的 `workspace_root` 和 `LDVH-GOVERNED-PROJECTS.yaml`，并调用实际可用的管辖解析能力验证目标范围；不得在本文、Skill 或行动模板中复制字段和解析算法。

取得 LDVH 源码或部署 Skill 不自动新增、删除或修改管辖项目。已有配置必须按 02 回读并以当次解析核验；需要新增、删除或修改时，必须把该变化作为四项工作方案中的独立计划项，使用 02 的当前字段与验证规则，展示实际写入、回读与解析结果。环境接入不能证明管辖配置成立，管辖配置成立也不能证明 Skill 已真实递达或 Git Hook 已部署。

### 6.5 升级、禁用、卸载与回滚

升级必须以当前 canonical 模板重放部署，并重新检查 CLI 入口兼容性、用户配置冲突和受影响范围，不能仅替换文件后沿用旧验证结论。禁用必须证明目标环境不再加载该 Skill；卸载还必须处理 LDVH 管理的部署对象和短期过程数据，并保留或恢复部署前未知用户资产。

每项可能写入或删除的对象都必须在执行前具有可理解的回滚或恢复方向。失败后只能恢复当次实际改变且有基线依据的对象；缺少原始内容、权限或可验证恢复入口时，不得承诺完整回滚，并应在写入前交还风险。

回滚完成必须通过目标环境和实际部署对象重新观察：接入不再自动发生或已经恢复到变更前状态，同时无关用户配置未被破坏。运行命令成功、备份文件存在或部署能力返回成功不能单独证明回滚成立。

升级承接 Git Gate 的 Git Hook 必须以目标 common-dir 为单位，并在共享它的代表性实际 worktree 中重新验证 Git Gate 的真实事件绑定；不能只替换 Git Hook 文件后沿用旧验证结论。禁用或卸载 common-dir 级 Git Hook 会同时影响共享该 common-dir 的主 worktree、现有 linked worktree 与后续 linked worktree；执行前必须展示这一影响并取得相应授权。删除某个 linked worktree 不会卸载 common-dir 级 Git Hook；独立 clone 的 Git Hook 也不会因另一 clone 的卸载而消失。回滚必须重新观察目标 common-dir 及代表性 worktree，证明目标 Git Hook 状态与 Git Gate 逐事件绑定已恢复或移除。

## 7. 真实环境验证与证据边界

### 7.1 最小证据

准备声明某一接入范围已经真实递达、真实触发或通过验证时，至少必须回指：

1. 目标环境名称、版本和实际运行位置；
2. 接入单元身份、部署位置与当前内容回读，及部署件与 canonical 模板的一致性结果；
3. 管辖配置的当前来源、显式工作对象、当次解析结果与范围；
4. 被验证的会话、生命周期或 Git 原生事件范围；
5. AI 经路由取得规则引导与当次行动模板的实际 CLI 请求与结果，以及 Git Gate 的当前来源、Git Hook 所在 common-dir、实际触发 worktree、当次 Index、commit message、核心入口、同一候选绑定与 allow/block 诊断；
6. 至少一个代表性成功路径，以及一个与主要风险匹配的输入缺失、拒绝、能力缺口、失败或未验证范围；
7. 实际副作用、未发生副作用、未覆盖事件和环境能力缺口；
8. 环境接入、管辖配置和 Git Hook 部署前后或回滚前后的真实对象回读。

上述链路只要求当次证据可以相互核对，不因此建立统一追踪契约或持久状态；Helper 的部分结果、不可用和未证明范围仍按 04 保留。

证据只覆盖当次目标环境、版本、入口、会话或事件、工作对象和实际路径。截图、日志、诊断、测试和 Human 观察只在其真实产生范围内作为当次依据，不自动成为稳定事实；需要跨会话保留时必须进入适用事实类型或稳定项目文档，而不是由环境侧建立永久状态。


### 7.2 断点与 Human 观察

真实验证需要重启、打开新会话、接受平台信任、在目标 UI 操作或观察只有 Human 可见的结果时，AI 必须把断点组织为可恢复的最小验收说明：目标环境、Human 必须执行的动作、正常可观察表现、需要返回的原始结果、复跑入口和当前未验证范围。

Human 只承担环境强制保留给 Human 的授权、信任、重启、界面操作和观察，不负责解释 Helper 契约或判断技术验证是否通过。AI 在恢复后必须重新读取四项工作的当前状态和来源，不依赖聊天记忆把断点前计划当作当前结果。

当目标环境身份、版本、位置或与执行环境的关系只能由 Human 确认或暴露时，AI 必须先交还最小目标确认请求，而不是要求 Human 猜测技术路径。该请求至少说明当前执行环境和识别依据、待确认目标及候选依据、为何无法由 AI 只读确认、Human 需要返回的原始信息，以及确认后的复跑入口和仍未验证的范围；Human 的确认本身不等于安装、部署、接入或真实触发。

手工 CLI 调用或 shell 直调可以用于诊断，但不能替代目标环境真实加载与真实递达。目标环境无法在当前执行环境中验证时，应保持相应范围未验证，并交还取得真实证据的入口，不得伪造跨环境结论。

## 8. 环境机制核验与能力判定

每个目标环境的技能机制都必须依据当前官方或实际权威资料核验其技能位置、加载时机、可见会话范围、权限、可观察入口，以及登记或部署一项技能时该环境要求提供的字段与输入（名称、描述、指令正文、图标或厂商私有扩展等）；不得凭其它环境、历史记录或名称猜测这些要求。厂商机制变化快的内容留在当次调查记录；只有形成稳定外部契约且满足 01 §13 时，才建立普通规范或授权附件。

这项核验由处理该目标环境的 AI 在用户当前任务中完成；LDVH 只提供调查输入、接入面说明、状态判定、验证与回滚方法，不承诺预制每个厂商的配置步骤或兼容矩阵。这是 LDVH 的设计原则而非临时状态。AI 必须保留所用资料的 URL 或稳定定位、观察时间、目标产品版本与平台，并把“未找到”与“肯定不存在”分开。

完整接入的能力状态必须区分 `unsupported` 与 `unverified`。只有当前官方或实际权威资料，或者对实际环境的范围匹配观察，肯定证明不存在能够把 SKILL.md 文本递达给 AI 的机制，或不存在可承接必需原生 Git `commit-msg` Gate 的机制时，才能把相应完整接入判为 `unsupported`。尚未调查、没有找到资料、权限不足、版本不明或当前不可观察均为 `unverified`；发现候选机制也只表示可以继续调查，不能替代部署、真实递达和真实 Git 事件证据。`partial` 只描述已经完成的实际子范围，不得掩盖 `unsupported` 或 `unverified`。

`unverified` 只表示当次证据不足，不表示以完成接入或验收为目标的行动已经闭合。阻塞该目标的 `unverified` 必须保留目标特定的原因、当前责任方、最小恢复动作、需要返回的原始观察和复跑入口；只有目标明确排除、Human 明确拒绝/未授权，或当前来源已定义的停止依据成立时，才可把该阻塞作为当次停止依据。不得用并列厂商名称、历史环境或泛化的“未配置”替代实际目标与恢复交还。

## 9. 代表性场景

| 场景 | 处理 |
|---|---|
| SKILL.md 已部署，但当前会话未取得规则引导 | 只报告部署观察；真实递达保持未验证，按 §5.4 现取引导或交还缺口 |
| CLI 入口不在 PATH | 从已确认的 LDVH 源码仓库使用仓库入口；入口仍不可得时如实交还缺口，不猜绝对路径或改投安装副本 |
| `ldvh work-context` 不可用或返回 `unavailable` | 直接使用精确读取路径（§5.4），报告所用路径与取得范围；`work-context` 不可用不是接入失败 |
| 凭记忆写死模板清单、操作清单或信封字段 | 禁止；经 candidates/content 现取；旧文本一律不作权威 |
| 环境无技能机制但可 shell 直调 | 完整接入不成立；直调仍可按 04 与领域来源执行已定义的正式能力，但不是 AI 环境路由；不得改投环境 Hook、插件或 adapter |
| 同一环境存在多份 LDVH 技能文本 | 违反单一单元；先确认各份管理归属，用户资产进入 Human Gate 后清理 |
| Git Gate 在真实提交中返回 block | 只证明当次事件、候选与诊断；不得扩张为语义审核或授权结论 |
| 新建 linked worktree | 若共享已部署 Git Hook 的同一 common-dir，无需重复部署；仍须在该 worktree 的真实事件中验证 Git Gate 对 actual worktree、Index 与 message 的绑定 |
| 纳入当次完整接入目标的独立 clone | 因 common-dir 不同，作为独立部署边界重新部署、验证和回滚，不继承其它 clone 的结论；未纳入目标时不为验收创建或部署 |
| 部署件与当前 canonical 模板不一致 | 部署件过期；重新部署并重新验证受影响范围 |
| 环境界面显示“技能已启用”但无真实取得证据 | 只证明静态配置；真实递达未验证 |
| 卸载命令成功但环境仍加载旧技能文本 | 回滚未成立，继续定位残留，不声明卸载完成 |
| 目标环境无法从当前执行环境观察 | 完成静态检查与可行诊断，交还真实环境验收入口，保持接入未成立 |

## 10. 验证要求

环境接入、管辖配置、Git Hook 部署和验证是四项相互独立的工作；其中验证必须分别覆盖源码仓库与入口、Skill 文本合同与真实路由、管辖配置与当次解析、common-dir 级 Git Hook 部署和逐 worktree Git Gate 真实触发。任一项通过均不得替代或倒推其它项，且完整 LDVH 接入要求四项全部成立。

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 规范身份与责任 | 新建、修改或准备启用本文时 | YAML、直接依据、结构和职责边界符合 00、01、02、03、04；没有复制配置、服务字段、实现或厂商机制 | 当前规则源、准入记录与本文 | 规范回读、机械解析、责任和引用检查 | 当次规范身份与正文 | 保持草案或停止依赖，修正重复、遗漏和错误归口后复核 |
| 单一单元与内容合同 | 部署、修改或核对 SKILL.md 时 | 每个环境只有一个接入单元；职责闭集与禁止项成立；部署件与 canonical 模板逐字节一致；无规则正文、写死清单、写死路径或环境名 | 当前模板、部署件回读与文本比对 | 模板逐字节比对、AI 对照 §5.2 审核 | 当次部署件与模板 | 停止消费过期部署件；重新部署或回指模板修正 |
| 规则引导路由 | 修改路由或声明递达时 | 精确读取路径回指 01 §9.10 与 00 §8.1/§8.2；事实侧 `not_requested` 语义保留；取得范围如实报告；未因缺引导阻断普通求解 | 当前来源、实际请求与结果、交付范围 | 直调精确读取路径、结果审查 | 当次引导取得范围与路径 | 报告读取缺口；不把缺失写成无规则或已保障 |
| 行动模板路由 | 受控行动与高影响行动前 | 当次模板经 `read-action-template-candidates`/`read-action-template-content` 现取并照其执行；无凭记忆或旧副本行动 | 当次调用记录、模板原文与执行对照 | 现取调用与模板回读 | 当次行动与所取模板 | 停止受控写入；现取后重审行动 |
| 结果映射忠实 | CLI 结果返回环境或写入交还时 | 成功、部分、拒绝、不可用、来源、范围和能力差异保留；`partial` 未映射为完整成功 | 原始 CLI 请求与结果、交还文本 | AI 对照 04 审核 | 当次结果与映射 | 修正交还；补充缺口与未证明条件 |
| Git Gate 双入口一致性 | 同一机械检查同时提供预检和原生阻断时 | 两入口按同一当前来源形成检查输入，调用同一份确定性检查实现；Helper 返回结构化结果，Git Gate 以真实事件输入重新检查且只映射 allow/block；入口代码未复制规则或校验逻辑 | 当前来源、Helper 请求与响应、Git Gate 实际输入与诊断、同一绑定候选一致性 tests | Helper 直调、Git Gate 直调、真实 Git 事件和 Code review | 当次来源、机械检查、候选及两个受测入口 | 停止接入或能力声明；删除重复逻辑并回到同一来源和检查实现 |
| Git Gate 与 AI 行动边界 | 新增或修改阻断条件或事件绑定时 | allow/block 只作用于来源绑定的同一原生事件与实际候选；不存在全局工具、命令或动作白名单；未登记名称和无关行动不被外推阻断 | 00、07、Git Gate 来源、原始事件、实际候选、已知与未知名称样例 | shared core tests、negative tests 与代表性真实事件 | 当次 Git Gate、原生事件、候选和受测无关行动 | 停止阻断声明；删除默认拒绝与名称白名单，按来源、事件、目标和副作用重新限定 |

| 禁用、卸载与回滚 | 准备声明已移除或恢复时 | 目标环境不再加载或已恢复基线；LDVH 管理对象已处理；无关用户资产未受损 | 前后基线、部署对象、环境观察和残留检查 | 卸载/回滚后回读与真实加载反例 | 当次目标和可观察范围 | 不声明回滚完成；继续修复或交还不可恢复范围 |

## 11. Human Gate

以下事项必须进入 Human Gate：

1. 部署、升级、禁用、卸载或迁移 Skill 接入单元、承接 Git Gate 的 common-dir 级 Git Hook 或相关配置，并明确其对共享该 common-dir 的主/linked worktree 的影响；
2. 接受平台信任、权限、登录、重启或其它只能由 Human 完成的环境动作；
3. 覆盖、合并、删除或放弃无法证明由 LDVH 管理的既有用户资产；
4. 修改管辖项目配置、初始化项目事实源或扩大部署到其它工作区、项目、用户或环境；
5. 在目标环境不具备所需能力时，决定是否接受已说明的能力缺口、受影响保障和残留风险；
6. 无法完整回滚、恢复基线或确认无关用户配置不受影响时仍决定执行；
7. 让 Skill 复制规则/模板、写死清单或路径、部署多份副本，或把某厂商机制事实提升为通用规则。

Human 决定的复用按 00 §10 执行；部署授权不能替代技术验证，风险接受不能把未验证写成通过，当前环境授权也不能扩张到其它环境。

## 12. Stop Conditions

出现以下任一情况时，暂停受影响的部署、递达或接入声明：

1. 目标环境、版本、工作区、工作对象、当前规则源或实际适用的 CLI 入口无法确定；
2. Skill 文本正在复制规则、写死模板/操作清单、写死机器路径或断言环境触发状态；
3. 凭记忆或旧副本行动，而未现取当次行动模板；
4. CLI 的部分、失败、拒绝、不可用、来源或能力缺口被交还吞掉或改写；
5. 计划写入、删除、权限、用户既有资产、验证入口或回滚方式不清楚；
6. 缺少覆盖实际副作用的 Human 授权；
7. 准备把文件存在、“技能已启用”或 shell 直调声明为真实递达、真实触发或接入；
8. Git Gate 没有在同一候选、来源、管辖和 Index 身份上得到可验证绑定，或其 allow/block 结果被改写；
9. 禁用、卸载或回滚后仍存在自动加载、未知残留或无关用户配置损坏；
10. 当前环境无法验证目标环境，却准备作出跨环境通过结论；
11. 厂商机制事实、实现、Code/tests 或行动模板正在反向定义本文规则；
12. 结果失败、部分成立、不可观察或未验证，却准备声明接入完成；
13. 准备为任何环境新建环境 Hook、插件或 adapter 接入层——LDVH 接入面无此层；
14. 执行环境或目标环境身份、二者关系或目标特定的阻塞依据尚未锁定，却准备以泛化 `unverified`、候选厂商名称或“未配置”形成接入或验收结论，或交还中缺少责任方、恢复动作、原始观察要求或复跑入口。
15. 环境接入、当次有效管辖配置与解析、承接 Git Gate 的 common-dir 级 Git Hook 部署或完整验证中任一缺失，或者准备把四项工作中任一项写成可选分支；
16. Git Hook 的目标 common-dir、共享它的 worktree 或独立 clone 边界无法验证，或者不同 worktree 的 Index、message、未提交内容或候选身份正在被合并或相互推断。

暂停范围与可继续行动按 00 §11 执行；对本文而言，只读核对来源和现状、形成方案、运行无副作用诊断、缩小范围、准备 Human Gate 或修正部署件可以在不越过受影响边界时继续。

受影响范围只能在目标和来源重新明确、映射恢复忠实、授权覆盖实际变化、用户资产得到保护、部署对象完成回读、真实递达或真实事件取得范围匹配证据、回滚残留消除，或者声明缩小到现有证据实际支持的范围后恢复。
