## 1. 定位

本文承载 21 授权的 WorkCase `orchestration` 长字段表、枚举和条件。

本文不定义 WorkCase 状态机、Human Gate、行动编排流程、Agent 能力或测试治理；这些内容仍归 21 主文、03、06 和 08。

## 2. 通用枚举

| 字段 | 允许值 |
|---|---|
| `orchestration.mode` | `single`、`sequential`、`parallel`、`mixed` |
| `execution_items[].mode` | `single`、`sequential`、`parallel` |
| `execution_items[].status` | `pending`、`in_progress`、`blocked`、`done`、`skipped` |
| `orchestration_owner` | `main_controller`、`workflow` |
| `result.status` | `pass`、`pass_with_followups`、`fail`、`needs_human_gate` |
| `human_confirmation.decision` | `execute`、`revise_plan`、`close` |
| `human_closure_confirmation.decision` | `close`、`continue_execution`、`revise_plan`、`request_result_review`、`request_self_check` |

## 3. review_policy字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `selection_reason` | 是 | 说明为什么本轮需要这些审核视角或角色 |
| `required_perspectives` | 是 | 必须列出本轮要求的审核视角或角色 |
| `optional_perspectives` | 否 | 可为空列表；只记录本轮允许补充但不强制要求的审核视角 |
| `tool_method_requirements` | 否 | 写能力类型或方法要求，不绑定具体工具名、语言、框架或实现 |
| `aggregation_rule` | 是 | 说明 `pass`、`fail`、`needs_human_gate` 如何聚合 |

新建 WorkCase 草案的 `result_review.review_policy` 应预置默认结果复核视角，至少覆盖规范一致性与事实源边界、实现与验证证据、WorkCase 治理和关闭材料。该默认策略必须说明：execution_items 全部 `done` 后应先进入 `result_self_checking` 完成主控自检，再进入 `subagents_result_reviewing` 完成独立结果复核；主控自检不得替代子 Agent、第三方审核 Agent 或可辨识独立视角的 `result_review.review_items`。

## 4. review_items字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `id` | 是 | 当前 WorkCase 内唯一 |
| `role` | 是 | 审核角色或专业视角 |
| `agent_name` | 是 | 必须指向独立子 Agent、第三方审核 Agent 或可辨识专业审核主体 |
| `requested_at` | 是 | ISO 8601 时间戳 |
| `prompt_context.objective` | 是 | 说明本次审核要判断什么 |
| `prompt_context.input_refs` | 是 | 列出方案、规范、事实源、上下文入口或其它输入 |
| `prompt_context.constraints` | 否 | 可为空列表；记录只读、禁止修改、重点检查等约束 |
| `context_digest` | 否 | 可使用 hash 或说明性摘要；不替代输入引用 |
| `prompt_context.prompt_digest` | 否 | 记录关键提示摘要，不要求保存完整提示全文 |
| `result.status` | 是 | 必须属于通用枚举 |
| `result.summary` | 是 | 说明通过、条件通过或不通过的理由 |
| `result.key_findings` | 否 | 只记录影响 Human 或主控决策的发现 |
| `result.recommendations` | 否 | 只记录需要主控处理或 Human 知道的建议 |
| `result.required_changes` | 否 | 为空表示没有强制修改要求 |
| `result.evidence_refs` | 否 | 可包含路径、命令、对象 ID、报告或说明性引用 |
| `raw_output_ref` | 否 | 常规审核为空；高风险或争议审核才引用外部稳定位置 |
| `attested_at` | 是 | 审核结论完成时间 |
| `attestation.signer` | 是 | 通常等于 `agent_name` |
| `attestation.statement` | 是 | 声明基于 prompt context 和 input refs 完成审核并对结论负责 |

主控不得改写 `review_items` 原始审核结论。`agent_name` 不得填写主控自身标识来冒充子 Agent；若由 workflow 接管审核，应使用 `orchestration_owner: workflow` 并填写 `workflow_ref`。

## 5. controller_resolution字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `resolved_at` | 是 | ISO 8601 时间戳 |
| `resolver` | 是 | 通常为主控 AI 标识 |
| `source_review_item_ids` | 是 | 覆盖本轮已完成审核条目 |
| `accepted_findings` | 否 | 可为空列表 |
| `rejected_findings` | 否 | 有拒绝时必须说明理由 |
| `required_changes_applied` | 否 | 修改 WorkCase 字段时必须与 `revision_history` 对齐 |
| `unresolved_items` | 否 | 非空时 Human 确认必须覆盖；`executing` 及后续状态不得仍保留行动前未确认事项 |
| `changed_fields` | 否 | 改字段时必须填写，并回指 `revision_history` |
| `revision_history_refs` | 否 | 可使用 `revision_history` 局部引用或说明性引用 |
| `summary` | 是 | 说明如何处理审核意见以及是否需要重审或 Human 裁决 |

凡主控根据审核意见修改 WorkCase 字段，必须追加 `revision_history`；若修改影响本轮审核对象本身，必须回到对应审核状态重新审核。

## 6. human_confirmation字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `decision` | 条件必填 | `executing` 及后续状态必须填写；值为 `execute`、`revise_plan` 或 `close` |
| `scope` | 条件必填 | 说明授权覆盖的目标、范围和执行边界 |
| `constraints` | 条件必填 | 可为空列表；有约束时必须写清 |
| `confirmed_at` | 条件必填 | Human 确认方案时间 |
| `summary` | 条件必填 | 说明确认依据、是否有条件通过和执行边界 |

## 7. controller_self_check字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `controller` | 是 | 主控 AI 或执行控制者标识 |
| `checked_at` | 是 | ISO 8601 时间戳 |
| `prompt_context.objective` | 是 | 应说明检查成功标准、验证证据、关闭证据和残留风险 |
| `prompt_context.input_refs` | 是 | 列出 WorkCase、产物、验证命令、相关对象或上下文入口 |
| `result.status` | 是 | 必须属于通用枚举 |
| `result.summary` | 是 | 必须说明是否可提交第三方复核及理由 |
| `result.key_findings` | 是 | 必须非空；无发现时写明未发现范围内问题 |
| `result.required_changes` | 是 | 没有必须修改项时为空列表；非空时不得进入结果复核 |
| `result.evidence_refs` | 否 | 可为空列表 |
| `attested_at` | 是 | 自检结论完成时间 |
| `attestation.signer` | 是 | 通常为主控标识 |
| `attestation.statement` | 是 | 声明基于上下文完成自检并对结论负责 |

主控自检发现范围内必须修改项时，必须先修复、补充证据、复跑相关验证，并把修复写入执行项、`verification_evidence`、`closure_evidence` 或 `revision_history` 后，才能提交结果复核。

## 8. human_closure_confirmation字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `decision` | 条件必填 | `closed` 时必须填写；值为 `close`、`continue_execution`、`revise_plan`、`request_result_review` 或 `request_self_check` |
| `scope` | 条件必填 | 说明关闭或退回覆盖的范围 |
| `constraints` | 条件必填 | 可为空列表；有约束时必须写清 |
| `confirmed_at` | 条件必填 | Human 确认关闭时间 |
| `summary` | 条件必填 | 说明关闭依据、残留风险接受或退回判断 |

关闭确认前的 `closure_evidence` 必须包含与 `WorkCase` 主规范一致的 `后续分流 / 收口结果` 结论：收口干净时明确写无后续分流、无残留尾巴；收口不干净时必须明确承接对象、责任人与继续处理方向。该要求不改变 `human_closure_confirmation` 字段本身，但改变其必须引用的关闭证据内容。

## 9. revision_history字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `at` | 是 | ISO 8601 时间戳 |
| `from_status` | 是 | 必须属于 WorkCase 状态枚举 |
| `to_status` | 是 | 必须属于 WorkCase 状态枚举 |
| `actor` | 是 | Human、主控 AI、审核 Agent 或其他明确主体 |
| `reason` | 是 | 说明为什么退回或修改 |
| `changed_fields` | 是 | 例如 `success_criteria`、`orchestration.execution_items` |
| `summary` | 是 | 说明改了什么以及后续应如何执行、审核或确认 |
