# 环境能力承接边界

> 创建日期：2026-06-08
> 定位：定义 LDVH 中环境能力如何承接规范落地要求，以及 Rules / Instructions、Skill、Agent、Hook、Code、Web 等能力的选择边界
> 适用范围：LDVH 环境能力承接判断、运行投影设计、环境适配映射、能力缺口判断、Code 需求识别和环境能力漂移审计
> 上位依据：`docs/specs/04-规范落地与环境适配基础规范.md`
> 相关规范：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/02-术语规范.md`、`docs/specs/04.01-规范落地要求规范.md`、`docs/specs/04.02-环境适配与运行投影规范.md`、`docs/specs/04.03-环境适配映射与运行投影记录模板.md`、`docs/specs/04.05-LDVH落地特别要求.md`、`docs/specs/04.06-个人落地特别要求.md`、`docs/specs/07-Code实现规范.md`

---
## 1. 本文解决的问题

本文解决 LDVH 在环境适配时如何选择环境能力的问题。

LDVH 先根据自身规范判断需要哪些规范落地要求和保障机制，再判断某个环境可以用哪些能力承接。Rules / Instructions、Skill、Agent、Hook、Code、Web 等能力不是规范落地要求本身，而是环境适配映射中的承接方式或运行投影。

本文不重新定义 Codex、Trae、Claude Code、Cursor 或其他平台的客观能力、参数契约和限制。具体平台能力以官方文档、refs 或当前环境配置为准。

---
## 2. 与 00 总纲的关系

00 定义开发环境是 LDVH 五类构成要素之一，Code 和 Web 也是独立构成要素。本文承接 00 的分工：开发环境提供 Rules / Instructions、Skill、Agent、Hook、命令、工具等运行能力；Code 提供确定性执行；Web 提供 Human-facing 桥接和受控交互。

本文的重点不是按环境罗列能力，而是按 LDVH 的落地需要定义能力承接边界。不同环境可以用不同方式承接同一规范落地要求。

---
## 3. 术语应用关系

本文使用的环境能力、环境实体、承接边界、能力缺口、Code、Web、Rules / Instructions、Skill、Agent、Hook 等术语，按 `docs/specs/02-术语规范.md` 定义。以下小节只说明这些术语在环境能力承接判断中的应用关系，不另行维护术语权威定义。

### 3.1 环境能力

本文只在承接判断场景中使用环境能力：判断具体环境中哪些入口、机制、工具或运行面可被 LDVH 用来承接规范落地要求。

环境能力可以由平台提供，例如 Rules、Instructions、Skill、Agent、Hook、命令、自动运行或提问工具；也可以由 LDVH 自行提供或约束，例如 Code 校验、Web 工作台、CI 检查或受控写入入口。

### 3.2 承接边界

本文对承接边界的应用规则是：说明某类环境能力适合承接什么、不能承接什么，以及何时需要组合其他能力或降级处理。

承接边界只回答“用什么能力更适合实现这个要求”，不回答“规范是否需要这个要求”。规范是否需要某项要求，应先按 `docs/specs/04.01-规范落地要求规范.md` 判断。

### 3.3 能力缺口

本文将当前环境没有能力完整承接某项规范落地要求，或能力存在但缺少必要配置、入口、Code、测试、权限或 Human Gate 的情况，按能力缺口处理。

能力缺口不得通过改低规范要求解决。应按缺口性质回到环境适配映射、Code 需求、Human Gate、LDVH 落地特别要求、个人落地特别要求或后续 Task。

---
## 4. 通用承接原则

环境能力承接应遵守以下原则：

1. **要求先行**：先判断规范要落地有哪些要求，再选择环境能力；
2. **能力核验**：能力客观行为以官方文档、refs、当前配置和实际运行投影为准；
3. **利用不重写**：LDVH 定义如何使用环境能力，不复制平台教程、参数手册或完整功能清单；
4. **适配不绑定**：同一规范落地要求可以在不同环境中映射为不同能力组合；
5. **组合承接**：一个要求可以由多个能力共同承接，例如 Skill 复用流程、Code 执行校验、Hook 或 CI 保障触发；
6. **投影回写**：运行投影输出不是事实源，稳定事实必须回写 Git 文件事实源；
7. **缺口留痕**：环境不支持或能力不足时，应记录降级方式和残留风险。

## 5. 能力承接边界

| 环境能力 | 适合承接 | 不适合承接 | 边界要求 |
|---|---|---|---|
| Rules / Instructions | 入口可见要求、硬约束摘要、事实源边界提示、项目入口提示 | 大段教程、完整 SOP、对象字段契约全文、低频流程、临时判断 | 只是运行投影，不是最终规范事实源；应引用权威规范，不复制长正文 |
| Skill | 流程复用要求、可复用多步骤流程、标准化输入输出、受控检查步骤 | 稳定规则正文、Human Gate 判断本身、独立上下文或并行委派 | Skill 不能调度子 Agent；需要稳定事件触发时必须组合生命周期触发能力或降级检查 |
| Agent | 子 Agent 思考要求、独立上下文、专项视角、并行审查、权限边界差异 | 简单问答、单文件小改、只包装角色名称、稳定事实源正文 | Agent 输出必须返回主控或用户，稳定结论回写事实源后才生效 |
| Hook / 自动触发 | 生命周期触发要求、提交前后检查、会话停止检查、工具调用前后检查、自动提醒或阻断 | 规范正文、工作流程本身、不能机械判断的语义结论 | 工作流程或规范定义触发时机；Hook、CI 或自动运行只负责在环境中实现触发 |
| Code / 命令 / CI | 确定性执行要求、解析、校验、测试、聚合、上下文压缩、受控写入、漂移检查 | 规范判断、Human Gate 授权、AI 语义结论 | Code 受 `docs/specs/07-Code实现规范.md` 约束；命令和 CI 是 Code 或环境入口，不是独立事实源 |
| Web / Human 入口 | Human 交互要求、态势呈现、确认、授权、验收、受控轻写入 | 开放式事实源后台、绕过 Code 校验的写入、替代 Human 判断 | Web 应围绕 Git 文件事实源和 Code 契约工作，不得维护第二套对象事实 |

MCP、Connector、Commands、Context Loading 和 Human Gate 不默认作为 LDVH 的独立核心机制。MCP 和 Connector 可以作为某个环境的工具来源；Commands 可以作为命令入口；Context Loading 是工作流程或入口可见要求的一部分；Human Gate 是治理条件，可以由 Web、对话确认、提问工具、Hook 阻断或 Rules 提示承接。

## 6. Rules / Skill / Agent 选择边界

环境适配需要在 Rules / Instructions、Skill 和 Agent 之间选择时，应按以下顺序判断：

1. 如果内容是长期稳定硬约束、事实源边界、禁止事项或入口提示，优先承接到 Rules / Instructions 类入口；
2. 如果内容是可复用、多步骤、输入输出稳定、可在主上下文中执行的流程，优先承接到 Skill 或命令流程；
3. 如果内容需要独立上下文、结论隔离、专项视角、并行委派或权限边界差异，才承接到 Agent；
4. 如果内容需要在某个事件上稳定发生，不能只依赖 Skill 的模型判断，应声明生命周期触发要求，并映射到 Hook、CI、自动运行、规则条件或人工降级检查；
5. 如果内容需要确定性解析、校验、聚合、测试或受控写入，应先按 `docs/specs/07-Code实现规范.md` 判断 Code 需求，现有 Code 不足时先形成最小 Code 实现和验证。

不得因为某项内容“重要”就写入 Rules，不得因为某个步骤“多”就创建 Skill，不得因为某个视角“专业”就创建 Agent。环境能力承接判断必须服务规范落地要求，而不是为机制本身扩张。

---
## 7. 工具缺口处理

当 AI 在规范创建、文档检查、事实源维护或执行验证中发现“有一个工具会更可靠、更省上下文或更容易验证”时，应先判断该工具是否属于 Code 需求。

处理顺序：

1. 检查当前项目是否已有适配的 Code、命令、脚本、测试、CI 或校验入口；
2. 若已有实现只需小范围扩展，应按 `docs/specs/07-Code实现规范.md` 扩展并验证；
3. 若不存在适配实现，应先形成 Code 需求，说明规则来源、输入范围、失败条件、输出形式和验证方式；
4. 若 Code 本身的规范、测试或维护规则缺失，应先补齐必要的 Code 规范或最小测试要求，再实现工具；
5. 工具实现后必须运行正反验证或等价验证，并记录降级方式和残留风险。

工具不是与 Code 并列的新构成要素。工具、脚本、校验器和命令入口都是 Code 的具体实现或运行投影。

## 8. 事实源回写边界

环境能力产生的过程信息默认不是稳定事实。

以下内容只有写入对应 Git 文件事实源后才生效：

1. Skill 输出中的稳定结论、任务、证据、决策或变更；
2. Agent 输出中的分析、建议、风险、审阅意见或任务拆分；
3. Hook、CI、命令或 Code 输出中的检查结果、失败诊断或漂移发现；
4. Web 页面状态、表单输入、人工修改标记或确认结果；
5. 平台计划、平台缓存、对话摘要或环境自动生成的过程文档。

涉及机制、工作模型、状态机、部署边界、目录边界或规则归属判断时，AI 应先定位并读取对应正式规范原文，不得只凭聊天记忆、目录现状、工具输出或平台经验作出规范判断。

## 9. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 环境适配映射选择 Rules / Instructions、Skill、Agent、Hook、Code、Web 或其他能力时，应遵守本文定义的承接边界 | `docs/specs/04.02-环境适配与运行投影规范.md`、环境能力核验、Human Gate | 环境治理 | 本文 §4-§8 的能力边界、选择顺序或工具缺口处理规则变化时 |
| 入口可见要求 | AI 进行环境适配或运行投影设计时应能定位本文作为能力承接边界入口 | 规范文档入口摘要、相关规范引用、环境适配映射引用 | AI 执行入口提示 | 本文定位、适用范围或能力表变化时 |
| 流程复用要求 | 环境能力承接判断和工具缺口处理应形成可复用检查步骤 | 环境适配流程、Code 需求准入流程、人工降级检查 | 流程复用 | 新增环境能力类型、改变 Rules / Skill / Agent 边界或工具缺口处理顺序时 |
| 子 Agent 思考要求 | 复杂环境能力接入或跨环境能力冲突应使用独立、专项或并行视角审查 | 子 Agent 审阅、主控汇总、Human Gate | 审计输入 | 引入新环境、能力边界不清、平台能力与 LDVH 使用边界冲突时 |
| 确定性执行要求 | 能机械检查的能力映射、运行投影路径和 Code 入口应由 Code 校验或记录缺口 | `tools/specs_validate.py` 扩展、漂移检查 Code、正反样例 | 校验实现 | 环境适配映射字段、运行投影路径、Code 入口或能力承接表变化时 |

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 将某项环境能力提升为 LDVH 全局必须能力；
2. 允许 Skill 调度 Agent；
3. 允许 Agent 输出、Skill 输出、Hook 输出、Web 状态或工具输出成为最终事实源；
4. 改变 Rules / Instructions、Skill、Agent、Hook、Code 或 Web 的承接边界；
5. 在没有 Code 需求准入和验证的情况下新增稳定工具或校验器；
6. 允许环境能力不足时不记录降级方式；
7. 将平台能力说明写成 LDVH 正式规范的客观事实源。

环境能力承接检查至少包括：

| 检查项 | 标准 |
|---|---|
| 要求先行 | 能力选择来自规范落地要求，而不是环境偏好 |
| 平台核验 | 平台能力以官方文档、refs 或当前配置核验 |
| 能力边界 | Rules / Instructions、Skill、Agent、Hook、Code、Web 未互相替代 |
| Skill 边界 | Skill 未调度子 Agent，稳定触发未只依赖 Skill 自动调用 |
| Agent 边界 | Agent 使用满足独立、专项、并行或权限边界需求 |
| Code 边界 | 工具和命令按 Code 需求准入、最小实现和验证处理 |
| 回写边界 | 过程输出中的稳定事实已回写 Git 文件事实源 |
| 降级处理 | 环境不支持时已记录降级方式和残留风险 |

## 11. 待补齐事项

1. 当前环境初始化记录稳定或更新后，应将 Codex、Trae、Claude Code、Cursor 等环境的能力核验结果写入环境适配映射、当前环境初始化记录、Task、Memo、ADR 或 refs，不在本文复制平台手册；
2. 运行投影漂移检查 Code 待后续按最小样例实现；
3. 工作流程基础规范后续变化时，应进一步校准生命周期触发要求与 Hook、CI、自动运行之间的边界；
4. Web 信息同步规范后续变化时，应进一步校准 Web / Human 入口的受控轻写入边界。
