## 1. 本文解决的问题

本文定义 LDVH 事实模型的字段层规则：字段是什么、公共字段回答什么问题、字段新增/复用/废弃如何治理，以及字段层与内容格式、注册消费、20-39 具体事实模型字段契约之间如何分工。

本文不定义具体事实模型是否采用某字段、字段是否必填、状态条件必填、状态机、关闭条件或对象内完整 schema。这些规则由 20-39 具体事实模型规范负责。本文也不定义字段内容的 Markdown/checklist/evidence 写法，内容格式由 `specs/05.02-事实模型字段内容与格式规范.md` 负责；字段注册表和 Code/Web 可消费元数据由 `specs/05.03-事实模型字段注册与消费规范.md` 负责。

---

## 2. 与 05、05.02、05.03 和 20-39 的关系

`specs/05-事实模型基础规范.md` 是事实模型总纲，定义事实模型定位、准入、通用原则和与 20-39 的关系。本文是字段层子文档，只承接字段契约通用原则和公共字段语义。

`specs/05.02-事实模型字段内容与格式规范.md` 定义字段内容如何书写。本文中的字段语义只回答“字段承载什么”，05.02 回答“字段内容以什么格式表达”。

`specs/05.03-事实模型字段注册与消费规范.md` 维护字段名、重要嵌套路径、内容格式映射、Code/Web 消费元数据、废弃字段和别名关系。本文中的公共字段语义应被 05.03 注册表消费，但注册表不得反向定义具体对象字段是否存在或是否必填。

20-39 具体事实模型规范定义具体对象采用哪些字段、字段类型、必填性、状态条件、状态机、关闭条件和对象内结构约束。若字段语义与具体对象采用规则发生冲突，应区分两个层面处理：字段公共语义归本文，字段采用和约束归具体对象规范。

## 3. 字段契约通用原则

事实模型的字段契约遵循以下原则：

1. **基础字段对齐**：所有事实模型应包含基础字段（id、type、title、status、created、updated）；其中 `created` 和 `updated` 使用 ISO 8601 时间戳格式，类型为 `datetime`；
2. **扩展字段明确**：具体事实模型的扩展字段由该事实模型的规范明确定义，包括字段名、类型、是否必填、约束条件；
3. **字段语义一致**：相同字段名在不同对象中的语义应保持一致；
4. **引用完整性**：引用其他对象的字段应确保引用的对象存在且有效。

### 3.1 priority 统一标准

`priority`（优先级）用于执行调度顺序、价值判断和保留意义判断，回答“哪个工作项或火花应先处理”。工作对象不再维护独立的 `importance`（重要程度）字段，避免优先级与重要程度形成两套近似体系并增加理解负担。

`priority` 只适用于 WorkCase（工作项）和 Spark（火花），枚举如下：

| 值 | 判断标准 |
|---|---|
| `P0` | 不立即处理会阻塞当前主线、导致事实源漂移、使关键能力不可用、破坏验证闭环、造成重大返工或扩散明显错误 |
| `P1` | 应优先处理，明确影响当前目标推进、关键闭环、近期交付、长期事实源稳定性或关键治理边界，但不覆盖全部 P0 工作 |
| `P2` | 有明确价值，可在 P0 和 P1 工作之后按正常节奏处理 |
| `P3` | 可延后、候选、优化、补充、可替代、可丢弃，或不影响当前主线关闭 |

字段适用边界如下：

1. WorkCase 必须维护 `priority`，不得维护 `importance`；
2. Spark 必须维护 `priority`，不得维护 `importance`；
3. ADR、Study 和 Pitfall 不得直接维护 `priority` 或 `importance`；
4. ExecutionItem 不得独立维护 `priority` 或 `importance`，其调度顺序由 WorkCase 的执行编排承载；
5. Pitfall 不得使用 `severity` 字段，影响和后果应写入 `symptoms`、`applicability`、`avoidance` 或 `notes`。

## 4. 公共字段语义定义

本节定义跨工作对象共享的公共字段语义边界。每个公共字段明确：回答什么问题、不应该写什么、适用方式和内容格式。各具体事实模型规范定义对象特有字段契约，公共字段引用本节。

### 4.1 全局公共字段

以下字段所有工作对象在采用时 SHALL 遵循统一语义：

| 字段 | 回答什么问题 | 不应该写什么 | 内容格式 |
|------|------------|------------|---------|
| `id` | 唯一标识 | 描述性内容 | string |
| `type` | 对象类型 | 描述性内容 | enum |
| `title` | 一句话概括 | 详细说明、验证方法、状态变化 | string |
| `status` | 当前状态 | 状态变化历史、变更原因 | enum |
| `created` | 创建时间 | 修改时间 | datetime |
| `updated` | 最后更新时间 | 创建时间 | datetime |
| `description` | 这个对象是什么、为什么存在 | 验证方法、风险说明、约束条件、验收标准、状态变化 | Narrative |

`datetime` 字段必须写为 ISO 8601 时间戳，至少包含日期、小时和分钟，例如 `2026-06-18T17:10:00+08:00` 或 `2026-06-18T17:10:00`。仅包含日期的 `YYYY-MM-DD` 属于 `date`，不得写入 `created`、`updated`、`closed_at`、`review_requested_at`、`evolution.at` 等 `datetime` 字段。只有字段契约明确为 `date` 时，才允许使用纯日期，例如 ADR 的 `date` 或 Spark 的 `resolved_at`。

`description`（描述）是所有对象的核心叙述字段，只承载对象的背景、目标和范围说明。以下内容不应写入 `description`，应写入对应字段：

- 验证方法 → `verification`（验证）或 `acceptance`（验收标准）
- 风险说明、约束条件、降级方式 → `constraints`（约束）或 `notes`（备注）
- 验收标准 → `acceptance`（验收标准）
- 状态变化历史、前后状态、修改原因和执行者 → Git 提交记录派生信息

### 4.2 部分公共字段

以下字段在被具体事实模型采用时 SHALL 遵循统一语义。本文只定义公共语义和内容格式，不规定具体事实模型是否必须采用这些字段。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `source` | 这个对象的输入来源 | 一般关联、验证结论 | 需要记录输入来源的对象 | Reference / Narrative |
| `source_detail` | 输入来源的说明、触发问题或原始输入摘要 | 一般关联清单、状态变化历史 | 需要补充来源上下文的对象 | Narrative / Reference |
| `acceptance` | 完成的判断条件 | 验证方法、风险说明、背景 | 需要验收检查的对象或执行项 | Checklist |
| `verification` | 怎么验证完成 | 风险说明、约束条件、背景说明 | 需要记录验证方式或验证结果的对象 | 验证证据 |
| `verification_evidence` | 成功标准如何被检查 | 验收标准、背景说明 | 需要记录验证证据的对象 | 验证证据 |
| `closure_evidence` | 为什么可以关闭、关闭结果、残留风险和 Human Gate 结果 | 验收标准、背景说明 | 需要关闭证据的对象 | 验证证据 |
| `closed_at` | 关闭时间 | 创建时间、更新时间 | 需要关闭时间的对象 | datetime |
| `archive_reason` | 为什么归档 | 归档后的内容、验证 | 需要归档原因的对象 | Narrative |
| `deprecated_reason` | 为什么废弃 | 归档原因、状态流水、替代关系 | 需要表达废弃原因的对象 | Narrative |
| `discard_reason` | 为什么废弃 | 废弃后的说明、验证 | 需要废弃原因的对象 | Narrative |
| `notes` | 其他字段无法承载的补充说明 | 核心信息、验证方法、决策 | 需要补充说明的对象 | Narrative |

具体事实模型只要定义 `archived`、`deprecated`、`discarded` 等非活跃终态，就必须为该终态定义并填写对应原因字段：`archived` 使用 `archive_reason`，`deprecated` 使用 `deprecated_reason`，`discarded` 使用 `discard_reason`。原因字段必须说明为什么对象不再处于活跃入口，以及后续 AI / Human 应如何理解该对象；不得只写“已归档”“已废弃”等重复状态本身的空泛文本。

工作对象不得手写维护 `status_history`。状态变化历史、前后状态、修改原因和执行者由 Git 提交记录派生；需要长期保留的语义转折应写入对象专用字段、证据字段或相关工作对象，不得用手写状态历史形成第二事实源。

`verification`（验证）只承载验证计划、验证命令、验证结果和验证结论。以下内容不应写入 `verification`，应写入对应字段：

- 风险说明、约束条件、降级方式 → `description`（描述）或 `notes`（备注）
- 背景说明 → `description`（描述）
- 验收标准 → `acceptance`（验收标准）

### 4.3 引用字段语义边界

引用字段分为两类：来源引用（`source_*`）和关联引用（`related_*`）。

**来源引用 `source_*`**：本对象的输入来源。如果某个对象是创建本对象的直接原因或输入，应放入 `source_*`。

**关联引用 `related_*`**：与本对象有关联的其他对象。如果某个对象只是与本对象有关联但不是直接输入来源，应放入 `related_*`。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `related_docs` | 引用的文档路径 | 对象 ID 引用 | 需要关联文档的对象 | Reference |
| `urls` | 报告正文提炼出的外部网址及用途摘要 | 项目内文档、规范路径、代码位置或纯说明文本 | Study 等需要提炼外部网址依据的对象 | Reference |
| `related_adrs` | 关联的决策记录 | 来源决策（用 source_*） | 需要关联 ADR 的对象 | Reference |
| `related_sparks` | 关联的火花 | 来源火花（用 source_sparks） | 需要关联 Spark 的对象 | Reference |
| `related_studies` | 关联的研究报告 | 报告正文或研究过程 | 需要关联 Study 的对象 | Reference |
| `related_workcases` | 关联的工作项 | 所属工作项（用归属字段） | 需要关联 WorkCase 的对象 | Reference |
| `related_pitfalls` | 关联的踩坑经验 | 来源踩坑经验 | 需要关联 Pitfall 的对象 | Reference |
| `related_rules` | 关联的规范路径 | 一般文档引用（用 related_docs） | 需要关联规范或能力路径的对象 | Reference |
| `superseded_by` | 替代本对象的新对象 | 一般关联 | 需要替代关系的对象 | Reference |
| `source_objects` | 本对象的来源对象 | 一般关联（用 related_*） | 需要记录对象来源的对象 | Reference |
| `source_sparks` | 本对象的来源火花 | 一般火花关联（用 related_sparks） | 需要记录火花来源的对象 | Reference |
| `source_docs` | 本对象的输入资料或来源文档路径 | 后续引用文档（用 related_docs） | 需要记录来源资料路径的对象 | Reference |

判断规则：

1. 如果引用是本对象的直接输入来源，放入 `source_*`；如果只是一般关联，放入 `related_*`。
3. 如果具体事实模型仍保留替代关系字段，使用 `superseded_by`，不放入 `related_*`；未保留该字段的对象不得自行引入替代状态或替代字段。
4. 如果引用是文档路径，使用 `related_docs`；如果是规范、Rules、Skill、Code 或 Web 路径，使用 `related_rules`。
5. 如果引用是 Study 报告正文中的外部网页资料，使用 `urls`；`urls` 只承载 `http(s)` URL 及用途摘要，不表达项目文档关系、规范路径、代码位置或纯说明文本。

## 5. 字段治理规则

字段新增、复用、废弃和别名治理遵循以下规则：

1. 新增字段前，应先检查本文公共字段语义和 `specs/05.03-事实模型字段注册与消费规范.md` 的注册表，避免创建同义异名字段；
2. 若新字段承载已有字段语义，应复用已有字段名，或在 05.03 登记别名/废弃/替代关系；
3. 若同名字段在不同对象中的语义需要差异化，具体事实模型规范必须说明差异，不得让同名字段静默漂移；
4. 具体事实模型新增、删除、重命名字段时，应同步检查 05.01 公共语义、05.02 内容格式、05.03 注册表、Code、Web 和测试；
5. 废弃字段不得作为新写入入口；历史兼容读取、迁移提示和替代关系由 05.03 与 Code/Web 实现承接；
6. 字段层规则不得替代 20-39 具体事实模型字段契约，05.03 注册项也不得被解释为具体对象已采用该字段。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 具体事实模型字段契约应遵守本文公共字段语义和字段治理规则 | 05、05.01、20-39 具体事实模型规范 | 事实模型治理 | 新增、删除、重命名或改变字段语义时 |

## 7. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除或重命名 05 系列字段层子文档；
2. 改变公共字段语义；
3. 改变 `priority` 等跨对象字段治理规则；
4. 允许 05.01 反向定义具体事实模型的完整字段 schema、必填性、状态机或关闭条件；
5. 改变字段层与 20-39、05.02、05.03、07 或 08 的职责边界。

检查至少确认：公共字段语义未复制具体对象 schema；字段治理规则可被 20-39、05.02、05.03、Code 和 Web 稳定消费；引用路径真实存在。
