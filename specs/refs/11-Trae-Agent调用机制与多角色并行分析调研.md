# Trae 子 Agent 调用机制、上下文传递与多角色并行分析调研

> 创建日期：2026-05-31
> 来源：基于 Trae 官方文档、社区资料和平台实际验证的独立调研
> 定位：外部资料引用与平台机制调研，不直接成为 LDVH 强制规则
> 关联规范：specs/51-multi-role-thinking-多角色思考.md

---

## 一、结论摘要

截至 2026-05-31，Trae 平台子 Agent 的调用机制、上下文传递和多角色并行分析的核心发现如下：

| 维度 | 核心结论 |
|---|---|
| 调用机制 | 存在两种子 Agent 调用机制：Task 工具（主控 AI 调用内置子 Agent）和自定义 Agent（SOLO 编排调用），两者上下文均独立、不继承对话历史 |
| 上下文构建 | 三层模型：平台自动注入（不可控）→ 父 Agent 手动构建（可控）→ 子 Agent 自行读取（间接传递） |
| 自定义 Agent 边界 | `.trae/agents/` 下的自定义 Agent 可被读取但不可被主控 AI 通过 Task 工具直接调用；主控只能读取其 Prompt 后通过 `general_purpose_task` 间接注入 |
| 多角色并行 | `general_purpose_task` 可作为可调用 Agent 容器，通过参数注入角色实现并行隔离分析；Skill 无独立上下文，不能替代 |
| 模式选择 | 默认 Skill 轻量模式（串行、共享上下文）；需要结论隔离时升级为多角色子 Agent 模式（并行、独立上下文）；难以取舍时 Human Gate |

## 二、Trae 子 Agent 的两种调用机制

### 2.1 机制对比

| 维度 | Task 工具（内置子 Agent） | 自定义 Agent（SOLO 编排） |
|---|---|---|
| 调用方 | 主控 AI 通过 Task 工具调用 | SOLO Agent 通过平台编排调用 |
| 可用类型 | 固定列表：search、general_purpose_task、ui-designer、frontend-architect、backend-architect、api-test-pro、ai-integration-engineer、devops-architect、performance-expert | 用户自定义，通过 Trae UI 创建 |
| 上下文 | 独立上下文，不继承对话历史 | 独立上下文，不继承对话历史 |
| Prompt 来源 | 系统内置，不可修改 | 用户自定义，可配置 Prompt、工具、MCP Server |
| 配置入口 | Task 工具的 query/description 参数 | Trae UI 的 Agent 创建面板 |
| 可被其他 Agent 调用 | 不可（只能被主控 AI 调用） | 可配置"可被其他智能体调用"（目前仅 SOLO 可调用） |
| 模型选择 | 系统分配，不可指定 | 可在 Trae UI 中配置 |

### 2.2 内置子 Agent 类型与能力

| subagent_type | 专长 | 工具权限 |
|---|---|---|
| `search` | 搜索/调研 | 搜索相关工具 |
| `general_purpose_task` | 通用编码任务，行为完全由传入的任务描述决定 | 完整工具集（Skill、Search、Grep、Read、Write、RunCommand 等） |
| `ui-designer` | UI 设计 | 设计相关工具 |
| `frontend-architect` | 前端 UI、状态管理、性能优化 | 前端相关工具 |
| `backend-architect` | 后端/API、数据库、服务端逻辑 | 后端相关工具 |
| `api-test-pro` | API 测试、性能测试、负载测试 | 测试相关工具 |
| `ai-integration-engineer` | AI/ML 集成、语言模型、推荐系统 | AI 相关工具 |
| `devops-architect` | CI/CD、云基础设施、监控、部署自动化 | DevOps 相关工具 |
| `performance-expert` | 性能测试、瓶颈分析、优化 | 性能相关工具 |

`general_purpose_task` 没有预设的专业倾向，是最通用的隔离执行容器：

- 传入"你是安全审查员"→ 做安全审查
- 传入"你是架构师"→ 做架构分析
- 传入"你是运维专家"→ 做运维评估

### 2.3 自定义 Agent 文件的调用边界

`.trae/agents/` 下的自定义 Agent 文件：

- ✅ 可以被主控 AI 读取和理解
- ✅ 其 Prompt 可以被提取后注入 `general_purpose_task`
- ❌ 不能被主控 AI 通过 Task 工具直接注册为新的 `subagent_type`
- ❌ 不能被主控 AI 一键调用

**关键结论**：自定义 Agent 文件是可读取的角色定义参考，不是可调度的 Agent 实例。主控 AI 只能读取其 Prompt 内容，然后通过 `general_purpose_task` 的 query 参数注入角色，间接模拟自定义 Agent 的效果。

## 三、上下文构建的三层模型

### 3.1 第一层：平台自动注入（不可控）

以下上下文由 Trae 平台在子 Agent 启动时自动注入，父 Agent 和用户均无法控制：

| 自动注入项 | 机制 | 说明 |
|---|---|---|
| L0 工作区规则 | `workspace_rules.md` 在会话初始化时注入 | 所有 Agent 均可看到 |
| L1 项目规则 | `project_rules.md` 在会话初始化时注入 | 所有 Agent 均可看到 |
| L2 场景规则 | `*-rules.md` 按 globs 或 description 条件注入 | 按条件生效 |
| 工具描述 | 根据 subagent_type 自动注入可用工具的 schema 和使用说明 | 决定子 Agent 能做什么 |
| 代码索引 | 工作区代码索引对子 Agent 可用 | 子 Agent 可通过 SearchCodebase、Grep 等工具检索 |
| Skill 描述 | 智能体先扫描 Skill 简要描述，判断相关后再加载详细内容 | 按需加载 |

**关键结论**：子 Agent 天然就能看到项目的 L0/L1 规则，不需要父 Agent 在 query 中重复传递。

### 3.2 第二层：父 Agent 手动构建（可控）

以下上下文由父 Agent 通过 Task 工具参数传递：

| 控制项 | 传递方式 | 限制 |
|---|---|---|
| 任务描述 | `query` 参数 | 形式限制 ≤30 词，实际可更长 |
| 任务标签 | `description` 参数 | 3-5 词 |
| Agent 类型 | `subagent_type` 参数 | 固定列表，不可扩展 |
| 业务上下文 | 只能写在 query 中 | 受 query 长度约束 |

Task 工具的 usage notes 要求：

> "Include all necessary context from the user's message and prior assistant steps, as well as a detailed plan for the task, in the task description."

**关键结论**：业务上下文（任务目标、变更概述、约束条件、输出格式要求）必须由父 Agent 在 query 中显式构建，子 Agent 拿不到对话历史。

### 3.3 第三层：子 Agent 自行读取（间接传递）

子 Agent 启动后，可以通过工具自行读取文件系统中的事实源：

| 读取方式 | 工具 | 说明 |
|---|---|---|
| 文件读取 | Read | 读取指定文件内容 |
| 代码搜索 | SearchCodebase、Grep | 检索代码库 |
| 目录浏览 | LS、Glob | 浏览文件结构 |
| 网络搜索 | WebSearch、WebFetch | 搜索外部资料 |

间接引用模式的工作方式：

```text
父 Agent query 中写：
"执行前必须读取 specs/51-multi-role-thinking-多角色思考.md，按该文档定义的角色定位和职责边界执行"

子 Agent 启动后：
1. 读取角色定义文件 → 获取完整角色、约束、输出格式
2. 读取 L1 规则（平台自动注入）→ 获取项目硬约束
3. 读取必读文档清单中的事实源 → 获取业务上下文
```

## 四、自定义 Agent 的上下文与调用机制

### 4.1 创建配置

根据 Trae 官方文档，自定义 Agent 可配置以下参数：

| 参数 | 说明 | 对上下文的影响 |
|---|---|---|
| 名称 | Agent 显示名称 | 无 |
| 提示词 | 规范和指导 Agent 完成任务的方式 | **核心上下文**：定义角色、流程、约束、输出格式 |
| 可被其他智能体调用 | 开启后 SOLO 可调用 | 调用时获得独立上下文 |
| 英文标识名 | 被调用时的唯一标识 | SOLO 用于路由 |
| 何时调用 | 描述调用场景和时机 | SOLO 用于调度决策 |
| MCP Server | 外部工具能力 | 扩展 Agent 工具集 |
| 内置工具 | Read、Edit、Terminal、Web search、Preview | 决定 Agent 能做什么 |

### 4.2 SOLO 调用时的上下文构建

官方文档原文：

> "开启后，该智能体可被其他智能体调用，以完成模块化任务。被调用时，该智能体拥有独立的上下文。"

这意味着：

1. 自定义 Agent 被 SOLO 调用时，获得**独立的对话上下文**（不共享 SOLO 的对话历史）
2. 项目的 Rules（L0/L1）仍然会被自动注入
3. Agent 的 Prompt 自身就是上下文的一部分
4. SOLO 通过"何时调用"描述和英文标识名来决定调度哪个 Agent

### 4.3 自定义 Agent 文件与 Task 工具的边界

| 维度 | `.trae/agents/` 自定义 Agent | Task 工具内置子 Agent |
|---|---|---|
| 可被主控 AI 直接调用 | ❌ 不能注册为新的 subagent_type | ✅ 通过 Task 工具调用 |
| 可被 SOLO 调用 | ✅ 配置"可被其他智能体调用"后 | ❌ 不适用 |
| Prompt 可自定义 | ✅ 用户完全控制 | ❌ 系统内置 |
| 工具可自定义 | ✅ 可配置 MCP Server 和内置工具 | ❌ 由 subagent_type 决定 |
| 模型可指定 | ✅ 可在 Trae UI 中配置 | ❌ 系统分配 |

## 五、上下文传递模式对比

### 5.1 直接传递 vs 间接引用

| 模式 | 机制 | 优势 | 劣势 |
|---|---|---|---|
| 直接传递 | 父 Agent 在 query 中写明所有上下文 | 简单直接 | 受 query 长度限制；上下文可能过时；维护成本高 |
| 间接引用 | 父 Agent 传递路径，子 Agent 自行读取 | 不受长度限制；事实源始终最新；单一事实源 | 子 Agent 需要额外读取步骤；依赖文件系统可达性 |

### 5.2 间接引用模式的平台适配性

| 设计假设 | 平台实际情况 | 是否匹配 |
|---|---|---|
| Agent Prompt 中引用路径，Agent 自行读取 | ✅ 子 Agent 有 Read 工具，可读取文件 | 匹配 |
| Agent 不需要对话历史 | ✅ 子 Agent 本就没有对话历史 | 匹配 |
| L0/L1 规则自动注入 | ✅ 平台自动注入，不需要在 Prompt 中重复 | 匹配 |
| 上下文包由 SOLO 传递 | ⚠️ SOLO 调用时如何传递上下文包未定义 | 缺口 |

## 六、多角色并行分析的实现模式

### 6.1 核心概念

| 概念 | 定义 | 说明 |
|---|---|---|
| Agent Prompt 模板 | 可读取的角色定义、触发时机、关注点、输出格式和边界约束 | 来源：`.trae/agents/*.md`、specs 角色定义、docs 摘要、对话临时要求 |
| 可调用 Agent 容器 | 主控能够通过工具接口实际启动的 Agent 类型 | 当前可用：系统内置子 Agent，尤其是 `general_purpose_task` |
| 主控 AI | 负责判断、选择、构造、启动、收集、汇总 | 多角色讨论的协调者和最终汇总者 |

### 6.2 并行隔离分析的实现方式

通过 `general_purpose_task` 作为可调用 Agent 容器，为每个角色构造独立参数，并行启动多个实例：

```text
┌──────────────────────────────────────────────┐
│              主控 AI（协调者）                   │
│                                              │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │
│  │ 子代理 A │ │ 子代理 B │ │ 子代理 C │ │ 子代理 D │ │
│  │安全专家 │ │ 架构师  │ │运维专家 │ │产品经理 │ │
│  │隔离上下文│ │隔离上下文│ │隔离上下文│ │隔离上下文│ │
│  └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ │
│      │          │          │          │       │
│      └──────────┴─────┬────┴──────────┘       │
│                       ▼                        │
│              结构化对比报告                      │
└──────────────────────────────────────────────┘
```

具体做法：在一条消息中同时发起多个 Task 调用，每个子代理扮演不同角色：

| 调用 | subagent_type | 角色提示词 |
|---|---|---|
| 1 | `general_purpose_task` | "你是安全审查员，从安全角度分析..." |
| 2 | `general_purpose_task` | "你是架构师，从设计角度分析..." |
| 3 | `general_purpose_task` | "你是运维专家，从运维角度分析..." |

每个子代理：
- ✅ **独立上下文** — 互不干扰
- ✅ **并行执行** — 同时启动
- ✅ **只返回结论** — 不污染主对话

### 6.3 Skill 与多角色子 Agent 在多角色分析中的区别

| 维度 | Skill | 多角色子 Agent（Task 工具） |
|---|---|---|
| 上下文 | 共享主上下文，无隔离 | 每个实例独立上下文 |
| 执行方式 | 串行 | 并行 |
| 角色间影响 | 角色间互相可见、可能趋同 | 角色结论先隔离形成，互不影响 |
| 成本 | 低 | 较高 |
| 汇总方式 | 主控直接汇总 | 子 Agent 输出回主控，主控统一汇总 |
| 适用场景 | 普通讨论、事实源读取较少、不要求角色间隔离 | 复杂话题、需要结论隔离、用户明确要求并行 |

**关键结论**：Skill 本质是可复用流程和提示词的展开，不具备独立上下文和并行隔离能力。多角色讨论需要角色间隔离时，必须使用 Task 工具 + `general_purpose_task` 子 Agent。

### 6.4 实际验证效果

通过 3 个并行 `general_purpose_task` 子代理对 LDVH 理念与纲要进行多角色分析，验证了以下效果：

- ✅ 三个角色同时启动、独立分析，互不干扰
- ✅ 每个角色有独立上下文，不会因看到其他角色结论而趋同
- ✅ 三方结论自然交叉验证——共识点可信度高，独特点补充了视角盲区
- ✅ 总耗时 ≈ 单个角色耗时（并行），而非 3 倍

## 七、Skill 模式与多角色子 Agent 模式的决策关系

### 7.1 Skill / 主上下文轻量模式

适合：

- 普通讨论
- 事实源读取较少
- 不要求角色间结论隔离
- 允许多个视角在同一上下文中串行分析
- 用户希望快速得到结构化分析

特点：

- 串行
- 共用主上下文
- 成本低
- 角色间可能互相影响
- 最终由主控直接汇总

### 7.2 多角色子 Agent 模式

适合：

- 用户明确要求多 Agent、并行、独立上下文或结论隔离
- 话题复杂，单一上下文容易污染判断
- 需要多个角色独立形成结论
- 需要并行读取或分析较多事实源
- 分析结果将影响规范、规则、Agent、Skill、工具或事实源边界

特点：

- 并行
- 每个角色独立上下文
- 角色结论先隔离形成
- 成本更高
- 子 Agent 输出回主控
- 主控统一汇总

### 7.3 模式选择规则

当 Skill 轻量模式和多角色子 Agent 模式都可行，但难以判断是否需要升级时，应由主控说明差异并交给人选择。

核心决策规则：

> 默认轻量；需要隔离则 Agent；难以取舍则 Human Gate；所有结果回主控汇总；稳定事实按事实源边界回写。

## 八、角色定义形态与设计方向

### 8.1 角色是否应成为生产对象的准入分析

按生产对象准入条件检查：

| 准入条件 | 角色是否满足 | 说明 |
|---|---|---|
| 需要独立追踪状态 | 弱 | 角色定义是相对稳定的配置，状态流转需求弱 |
| 需要可验证的完成标准 | 不满足 | 角色定义没有"完成"概念 |
| 需要关闭证据 | 不满足 | 角色不会被"关闭" |
| 需要关联其他对象 | 满足 | 角色需要被 Skill、Agent、行动模型引用 |
| 需要被工具展示、排序、过滤、聚合或审计 | 满足 | 角色索引需要被工具读取和聚合 |
| 不成为生产对象就会导致不可追踪 | 中等 | 角色定义散落各处会导致不一致 |

**结论**：角色不完全满足生产对象核心准入条件，更像配置型参考数据。但角色定义需要跨 Skill、Agent、行动模型和工具共享，如果散落各处会违反单一事实源原则。

### 8.2 "角色应用场景"是否应成为独立生产对象

角色应用场景本质上是"同一角色定义 + 不同输出结构约束"，更像是角色定义的一个字段维度，而非独立实体。拆成独立对象会导致：

1. 对象数量膨胀
2. 角色和角色应用场景之间是强 1:N 关系，每次读取角色都要额外读取应用场景
3. 角色应用场景没有独立状态流转和关闭条件
4. 角色应用场景的生命周期完全依附于角色

**结论**：不建议创建独立的"角色应用场景"生产对象，输出格式差异应作为角色定义的字段维度解决。

### 8.3 角色定义形态的三种选项

| 形态 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| specs 规范中的结构化章节 | 权威、稳定、符合事实源边界 | 不可被工具直接解析、项目级扩展困难 | 角色高度稳定、跨项目通用 |
| Role 生产对象（ldvh-base/roles/） | 结构化 YAML、可索引、可扩展、可被工具解析 | 需要定义新生产对象、增加维护成本 | 角色需要项目级自定义 |
| specs 定义通用角色 + ldvh-base/roles/ 承载项目扩展 | 兼顾稳定性和扩展性 | 两层结构，需要明确边界 | 通用角色稳定 + 项目角色可扩展 |

### 8.4 推荐设计方向

角色定义放在 specs 稳定规范中，不需要创建 Role 生产对象：

1. 角色定义是跨项目通用的稳定规则，不是项目级可自定义的动态实例
2. 角色定义的权威位置在 specs 规范中（51 主文档或其附件型实践子文档）
3. 不需要为角色创建独立的生产对象编号
4. 角色的输出格式差异作为规范中的字段定义，不单独创建"角色应用场景"对象
5. 工具可以从 specs 规范中解析角色定义，提供索引和聚合能力

角色定义应包含：角色名、维度、关注点、触发条件、输出格式（按场景区分）、Prompt 模板。

### 8.5 PM Kit 多角色讨论 Skill 的问题分析

PM Kit 把多角色讨论设计成 Skill（`pm-kit-multi-role-analysis`），存在以下问题，LDVH 应避免：

| 问题 | 说明 | LDVH 应对 |
|---|---|---|
| Skill 无独立上下文 | 轻量模式所有角色共享主上下文，角色间互相可见、互相影响 | 区分 Skill 轻量模式和子 Agent 隔离模式，不混为一谈 |
| 角色矩阵硬编码在 Markdown 表格 | 不可被工具解析、不可被项目扩展、不可被 Skill 和 Agent 以结构化方式共享 | 使用结构化字段定义角色，不使用 Markdown 表格 |
| 流程和角色定义耦合 | Skill 同时承载执行流程、角色矩阵引用、输出格式定义和模式升级判断 | 角色定义在 specs，执行流程在行动模型，两者分离 |
| SOLO Agent 模式只是建议 | Skill 不能调度 Agent，用户需要手动切换 | 主控应能直接启动多角色子 Agent |

### 9.4 51 多角色思考行动模型的设计方向

基于全部调研，51 的设计方向如下：

**角色定义**：

- 放在 specs 稳定规范中，使用结构化字段定义
- 包含：角色名、维度、关注点、触发条件、输出格式（按场景区分）、Prompt 模板
- 不创建独立生产对象，不需要 ldvh-base/roles/ 目录

**执行模式**：

- 默认 Skill / 主上下文轻量模式：串行、共用上下文、成本低
- 多角色子 Agent 模式：并行、独立上下文、结论隔离、通过可调用 Agent 容器实现
- 模式选择由主控判断，难以取舍时 Human Gate 交用户选择
- 所有模式最终由主控汇总

**可调用 Agent 容器**：

- 当前可用容器为系统内置子 Agent，尤其是 `general_purpose_task`
- 主控根据角色定义构造参数，注入可调用 Agent 容器
- 每个角色启动一个独立实例，实现结论隔离
- 未来如果平台支持主控调用自定义 Agent，可扩展容器类型

**Agent Prompt 模板**：

- 角色定义中的 Prompt 模板可作为调用参数注入容器
- `.trae/agents/` 中的自定义 Agent 文件可作为 Prompt 模板参考
- 存在自定义 Agent 文件不等于主控可调用，不得假设其已成为可调度 Agent

**汇总与回写**：

- 无论 Skill 还是多角色子 Agent，最终汇总者都是主控 AI
- 汇总包含：一致结论、分歧点、风险、执行顺序、事实源回写建议、Human Gate 判断
- 稳定事实按事实源边界回写，过程分析不回写

**核心决策规则**：

> 默认轻量；需要隔离则 Agent；难以取舍则 Human Gate；所有结果回主控汇总；稳定事实按事实源边界回写。
