## 3. 核心命题

### 3.1 目标：最适合 AI 工作的 Vibe Coding Harness

LDVH 的目标不是复刻某个外部产品，也不是交付某个固定工具，而是构建最适合 AI 稳定工作的 Vibe Coding Harness。

它要解决的是：

```text
AI 如何在真实项目中持续、正确、可验证、可沉淀地工作。
```

因此，Gstack、Superpowers、BMAD、Linear、Shrimp、Trae Solo、MCP 等参考对象都只是机制来源，不是 LDVH 的目标本身。

### 3.2 DNA：规范定义产品，AI 推理实现

LDVH 的核心不是某一套当前实现，而是 specs 定义的产品 DNA。

specs 应定义：

1. 事实源；
2. 工作对象；
3. 状态；
4. 流程；
5. Human Gate；
6. 验证；
7. 回写；
8. 扩展；
9. 宿主适配；
10. 实现生成依据。

AI 根据 specs 推理并生成：

1. tools；
2. web；
3. rules；
4. skills；
5. agents；
6. code；
7. validators；
8. templates；
9. adapters。

因此，LDVH 不是“规范替代实现”，而是：

```text
规范定义产品，AI 推理实现。
```

### 3.3 落地：能力不可缺席，载体可以替换

LDVH 不是只有 specs 就能运行。要真正使用 LDVH，必须有能力实现层。

也就是某种形式的：

1. 规则入口；
2. 流程入口；
3. 工具能力；
4. 展示界面；
5. 验证机制；
6. 代码实现；
7. Agent 或审查能力。

但这些能力不必固定为当前仓库里的 Python tools、React Web、Trae Rules、Trae Skills 或现有代码结构。

它们可以换成不同语言、不同数据库或文件形态、不同 IDE、不同 AI 编程环境、不同 Web / CLI / MCP / CI 载体。

核心原则是：

```text
能力不可缺席，载体可以替换。
```

这修正了“当前仓库中的 tools、web、rules、skills 不是 LDVH 必要边界”这一表述可能带来的歧义。更准确的说法是：

```text
tools / web / rules / skills / agents / code 是 LDVH 应用时不可缺少的能力形态，
但它们的具体载体、技术路径、宿主环境和实现方式不是固定边界。
```

### 3.4 闭环：规范 → 实现 → 验证 → 回流

LDVH 的演进不是：

```text
写规范 → 写实现 → 结束
```

而是：

```text
规范迭代
→ AI 推理实现
→ 能力落地使用
→ 事实源与测试验证
→ 实践经验回流规范
```

这一闭环保证：

1. 规范不空转；
2. 实现不漂移；
3. AI 生成不失控；
4. 经验不丢失；
5. 产品能持续演进。

本次沟通特别强调：

```text
先迭代规范，再推理实现，再事实源测试验证，最后回流规范。
```

这是新版 00 文档需要吸收的关键机制。

### 3.5 体验：AI 需要什么，什么就是第一体验

LDVH 的第一体验不是某个页面、某个命令、某个 Skill，也不只是 Core Loop。

真正的第一体验是：

```text
AI 进入项目后，能获得、生成或调用最小可行动环境。
```

AI 的能力结构可以从需要、害怕和擅长三个方面展开。

#### AI 需要什么

1. 目标清晰：AI 需要知道用户到底要达成什么，不只是当前要执行什么。目标不清时，AI 容易围绕最近一句话工作，把局部动作误当成整体目标。
2. 边界明确：AI 需要知道哪些能改、哪些不能改，哪些只是讨论、哪些进入执行，哪些是参考材料、哪些是权威事实源。边界不清时，AI 容易过度执行或跳过确认。
3. 事实可信：AI 需要知道哪些信息是真的、稳定的、可以作为判断依据。没有可信事实时，AI 会根据上下文残影做判断，形成看似合理但缺少依据的结论。
4. 状态可见：AI 需要知道当前对象、任务和流程处于什么状态。状态不可见时，AI 不知道下一步动作是否合法，也不知道是否需要 Human Gate。
5. 规则可用：AI 需要在正确时机拿到当前场景必须遵守的规则。规则太少会越界，规则太多会过载，真正有用的是场景化、可触发、能指导下一步的规则。
6. 验收具体：AI 需要知道做到什么程度才算完成。没有验收标准时，AI 容易用“已经做了”替代“已经满足要求”。
7. 反馈及时：AI 需要在行动后尽快知道结果是否正确。反馈滞后时，AI 容易继续在错误方向上叠加工作。
8. 工具可用：AI 需要有稳定工具去读取、验证、执行、写回，而不是只靠自然语言推理。工具不可用时，AI 难以形成可靠闭环。
9. 记忆可回：AI 需要把已经确认过的事实、决策、坑、经验和状态重新找回来。没有外部化记忆时，AI 会反复问、反复错、反复推翻前面的判断。
10. 停点明确：AI 需要知道什么时候必须停下来问人。停点不明确时，AI 可能过度自主，越过人的确认权。

压缩为 00 文档可用表达：

```text
AI 需要：目标清晰、边界明确、事实可信、状态可见、规则可用、验收具体、反馈及时、工具可用、记忆可回、停点明确。
```

#### AI 害怕什么

1. 目标含混：AI 容易把最近指令当成真实目标，导致局部执行偏离整体方向。
2. 边界失守：AI 容易在讨论、规划、执行、写入和提交之间混淆，提前进入不该进入的动作。
3. 事实混乱：AI 容易把聊天记忆、工具输出、缓存视图和正式事实源混在一起，导致判断失据。
4. 上下过载：AI 容易在过多规范、文件和历史信息中丢失重点，或者在信息不足时凭猜测补全。
5. 规则漂移：AI 容易在长任务中忘记入口规则、状态机、Human Gate 和验证要求。
6. 状态不明：AI 容易不知道当前对象能否流转、当前任务是否可执行、当前决策是否已生效。
7. 反馈缺失：AI 容易在没有验证结果的情况下继续推进，把未验证产出当成已完成结果。
8. 工具失控：AI 容易误用工具、过度写入、跳过受控入口，甚至让派生输出污染事实源。
9. 记忆断裂：AI 容易重复犯同类错误，无法把过去的坑、决策和经验自然带入当前任务。
10. 停点不明：AI 容易越过需要人确认的关键节点，把应由人判断的价值、风险和授权问题自行决定。

压缩为 00 文档可用表达：

```text
AI 害怕：目标含混、边界失守、事实混乱、上下过载、规则漂移、状态不明、反馈缺失、工具失控、记忆断裂、停点不明。
```

#### AI 擅长什么

1. 意图理解：AI 擅长从自然语言中识别用户目标、约束和隐含诉求。
2. 归纳拆解：AI 擅长把复杂问题拆成阶段、步骤、对象和检查项。
3. 方案生成：AI 擅长基于上下文提出实现方案、替代路径和取舍建议。
4. 结构处理：AI 擅长处理 Markdown、YAML、JSON、代码、表格和状态字段等结构化对象。
5. 规范推理：AI 擅长在给定规范、规则和事实源后，推理下一步应如何执行、如何生成实现、如何验证结果。
6. 工具调用：AI 擅长把读取、搜索、验证、执行、预览、写回等动作交给工具完成。
7. 模式迁移：AI 擅长把一个场景中形成的模式迁移到相似场景，复用经验和结构。
8. 反馈迭代：AI 擅长根据测试结果、验证失败、用户反馈和事实源变化持续调整方案。
9. 文档生成：AI 擅长把过程、决策、证据和经验整理成可复用文档。
10. 缺口发现：AI 擅长在执行中发现规则缺口、事实源缺口、工具缺口和流程缺口。

压缩为 00 文档可用表达：

```text
AI 擅长：意图理解、归纳拆解、方案生成、结构处理、规范推理、工具调用、模式迁移、反馈迭代、文档生成、缺口发现。
```

LDVH 应围绕这一能力结构组织 specs、rules、skills、tools、web、agents 和 code：需要的就充分保障，害怕的就充分避免，擅长的就充分发挥。

Core Loop 仍然重要，但它是第一体验中的行动主线：

```text
Intent → Plan → Execute → Verify → Record → Learn
```

## 5. 事实源测试验证的含义

本次沟通中的“事实源测试验证”不是普通软件测试，而是 LDVH 的真实性检验机制。

它至少包括三层。

### 5.1 事实源一致性验证

检查实现是否遵守 specs 和事实源边界：

1. 字段是否符合规范；
2. 状态机是否符合规范；
3. 引用是否完整；
4. Human Gate 是否被识别；
5. 变更是否回写；
6. 证据是否沉淀；
7. 工具输出是否没有成为第二事实源。

### 5.2 能力实现验证

检查生成出来的 tools、rules、skills、web、agents、code 是否真的能工作：

1. Skill 是否能引导 AI 正确进入流程；
2. Rule 是否能在正确场景触发；
3. Tool 是否能解析和校验事实源；
4. Web 是否能展示正确状态；
5. Agent 是否能完成独立审查；
6. code 是否能通过 lint、test、build。

### 5.3 真实使用验证

通过 Dogfood 或用户实践检查：

1. AI 是否更少迷路；
2. 人是否更容易确认；
3. Task 是否更容易关闭；
4. 验证是否更可靠；
5. Change 是否更可追溯；
6. 同类错误是否减少；
7. 新环境是否更容易适配。

## 6. 外部参考产品进入 LDVH DNA 的方式

本次沟通确认：外部产品不应作为 LDVH 的目标边界，而应作为机制基因来源。

LDVH 应吸收参考产品的精华进入自身 DNA，而不是复制它们的外形。

### 6.1 Gstack：流程产品化与阶段交接

Gstack 可借鉴的精华包括：

1. 工作流必须产品化；
2. 阶段要有输入、输出和停止条件；
3. 产物应连续交接；
4. Human Gate 应结构化；
5. 真实环境验证应进入验证链。

转译到 LDVH DNA：

```text
LDVH 必须把 AI 工作组织为可阶段化、可交接、可验证、可回写的流程。
```

### 6.2 Superpowers：工程纪律与反合理化

Superpowers 可借鉴的精华包括：

1. AI 容易合理化跳过测试；
2. 验证纪律必须前置和强制；
3. 不能相信 AI 自述完成；
4. 失败要进入调试流程，而不是猜测修复；
5. Skill 和流程要阻止 AI 自欺。

转译到 LDVH DNA：

```text
LDVH 必须默认 AI 会漂移、会自信、会合理化跳过验证，
因此验证、证据和反合理化必须成为流程内建机制。
```

### 6.3 BMAD：方法论分层与微文件架构

BMAD 可借鉴的精华包括：

1. 复杂工作需要阶段化方法论；
2. 不同角色或视角服务于不同阶段质量；
3. 微文件架构降低上下文负担；
4. 状态和产物应该可追踪；
5. 模板和完成定义能提高一致性。

转译到 LDVH DNA：

```text
LDVH 应用微文件和工作对象降低 AI 上下文负担，
用阶段产物、状态字段和定义清晰的完成条件支持复杂任务推进。
```

### 6.4 Linear：对象状态、优先级和工作流秩序

Linear 可借鉴的精华包括：

1. 工作对象必须有清楚状态；
2. 状态流转比自由文本更可靠；
3. 任务、负责人、优先级、关系、完成条件需要可追踪；
4. 产品体验要降低维护任务系统的成本。

转译到 LDVH DNA：

```text
LDVH 的工作对象必须具备状态、关系、优先级、验收和关闭纪律，
让 AI 和人围绕同一组事实协作。
```

### 6.5 Shrimp Task Manager：任务分解与 AI 可操作任务管理

Shrimp Task Manager 可借鉴的精华包括：

1. 任务拆解和任务链对 AI 很重要；
2. AI 需要可操作的任务列表，而不只是文字计划；
3. 任务关系、依赖、完成标准需要结构化。

转译到 LDVH DNA：

```text
LDVH 的 Task 不是普通 todo，
而是 AI 可执行、可验证、可关闭、可追溯的工作单元。
```

### 6.6 Trae Solo：原生 AI 环境机制

Trae Solo 可借鉴的精华包括：

1. Rules 可以作为场景入口；
2. Skills 可以作为复用流程；
3. Agents 可以作为隔离视角或独立审计；
4. AskUserQuestion 可以承载 Human Gate；
5. RunCommand 和 Preview 可以支持真实验证；
6. Spec / Plan 可以作为原生规划资产；
7. Schedule 可以支持周期任务；
8. 工具调用是 AI 行动的一部分。

转译到 LDVH DNA：

```text
LDVH 应定义如何利用 AI 编程环境的原生机制，
但不绑定某一个宿主。
不同宿主应依据 specs 生成自己的 Rules、Skills、Agents、Tools 和交互门禁。
```

### 6.7 MCP / OpenAPI / Terraform 类体系：协议与实现分离

MCP、OpenAPI、Terraform 类体系可借鉴的精华包括：

1. 规范可以先于实现存在；
2. 多个实现可以消费同一规范；
3. 一致性靠契约、验证和兼容性测试保障；
4. 生态扩展依赖稳定协议，而非单一实现。

转译到 LDVH DNA：

```text
LDVH 的 specs 应成为可被不同实现消费的稳定契约；
实现可多样，但必须通过一致性验证。
```

本次沟通后，建议新版 00 从以下主线重新组织。

### 7.1 为什么需要 LDVH

Vibe Coding 的问题不是 AI 不够强，而是 AI 缺少可持续工作的环境。

### 7.2 LDVH 的目标

LDVH 的目标是做最适合 AI 工作的 Vibe Coding Harness。

### 7.3 LDVH 的产品本质

LDVH 是规范驱动、AI 生成实现、事实源验证回流的自演进产品系统。

### 7.4 规范 DNA

specs 是 LDVH 的 DNA，定义对象、流程、边界、门禁、验证、演进和实现生成依据。

### 7.5 AI 的双重角色

AI 既是 LDVH 的第一服务对象，也是依据规范生成和改进 LDVH 实现的引擎。

### 7.6 能力实现层

tools、web、rules、skills、agents、code 是 LDVH 应用所必需的能力形态，但具体载体、技术路径和宿主环境可替换。

### 7.7 事实源与验证

Git 文件事实源、结构化对象、测试、Validator、Change、ADR、Pitfall、Dogfood 构成验证锚点。

### 7.8 第一体验

AI 需要什么，什么就是第一体验；第一体验是 AI 获得、生成或调用最小可行动环境。

### 7.9 Core Loop

Intent → Plan → Execute → Verify → Record → Learn 是 AI 工作的主流程骨架。

### 7.10 参考产品吸收原则

Gstack、Superpowers、BMAD、Linear、Shrimp、Trae Solo、MCP 等提供机制基因，不提供目标边界。

### 7.11 价值实现标准

判断一切规范和实现是否让 AI 更好工作、更少漂移、更易验证、更能回流。

### 7.12 可扩展与自演进

扩展不是预置一切，而是让新能力能从规范推理生成、事实源验证、经验回流。

### 7.13 防递归与 Dogfood

防止只扩规范不跑闭环；每次抽象都必须落地验证。

### 7.14 机制落地与检查

00 应约束后续 specs、rules、skills、tools、web、agents 和事实源。

## 8. 第 2 节重梳草稿：AI 能力结构与三方配合

### 8.1 设计逻辑

第 2 节的核心逻辑从"AI 需要/害怕/擅长"三段式，调整为：

```text
充分利用 AI 擅长的，针对 AI 害怕的，设计 Human、AI、Code 组合配合。
```

需要和害怕是一体两面——需要"目标清晰"就是害怕"目标含混"，拆成两组只是同一件事的正反说。真正的结构应该是：

- AI 擅长的 → 充分发挥
- AI 不擅长的（即害怕的）→ 设计 Human、Code、流程、规范来配合

配合不是一一对应，而是三方能力的组合。三方的本质区别：

```text
Human → 判断力（价值、意图、优先级、授权）
AI    → 推理力（概率性：理解、生成、迭代、发现）
Code  → 执行力（确定性：读取、校验、写入、反馈）
```

这与第 1 节形成对照：AI 生成代码的本质不是确定性编译，而是概率性推理——因此需要 Human 的判断力锚定方向，需要 Code 的确定性执行力验证和落地。

### 8.2 三方擅长清单

#### Human 擅长什么

1. 价值判断——什么重要、什么该做、什么不该做
2. 意图表达——用户真正想要什么
3. 优先级排序——先做什么后做什么
4. 风险评估——哪些变更可能出大问题
5. 授权决策——能不能做、要不要继续
6. 经验直觉——从历史和常识中快速判断
7. 质量验收——结果是否满足真实需求

压缩表达：

```text
Human 擅长：价值判断、意图表达、优先排序、风险评估、授权决策、经验直觉、质量验收。
```

#### AI 擅长什么

1. 意图理解——从自然语言识别目标和约束
2. 归纳拆解——把复杂问题拆成阶段和步骤
3. 方案生成——提出实现方案和替代路径
4. 结构处理——处理 Markdown、YAML、代码等结构化对象
5. 规范推理——依据规范推理下一步如何执行
6. Code 调用——把动作交给 Code 完成
7. 模式迁移——把一个场景的模式复用到相似场景
8. 反馈迭代——根据结果持续调整
9. 文档生成——整理过程、决策和证据
10. 缺口发现——发现规则、事实源、Code 和流程缺口

压缩表达：

```text
AI 擅长：意图理解、归纳拆解、方案生成、结构处理、规范推理、Code调用、模式迁移、反馈迭代、文档生成、缺口发现。
```

#### Code 擅长什么

1. 精确读取——从文件中提取结构化数据，不遗漏不臆造
2. 快速索引——在大量文件中定位目标内容
3. 一致性校验——检查字段、状态、引用是否符合规范
4. 受控写入——通过入口写入，不绕过规则
5. 状态聚合——把分散对象的状态汇总成全局视图
6. 持久记忆——事实一旦写入就稳定存在，不遗忘不篡改
7. 实时反馈——命令执行后立刻给出结果

压缩表达：

```text
Code 擅长：精确读取、快速索引、一致性校验、受控写入、状态聚合、持久记忆、实时反馈。
```

### 8.3 AI 害怕什么与三方配合矩阵

| AI 害怕 | Human 擅长 | AI 擅长 | Code 擅长 | 配合方式 |
|---|---|---|---|---|
| 目标含混 | 价值判断、意图表达、优先排序 | 意图理解、归纳拆解 | 精确读取 | Human 表达意图，AI 理解和拆解，Code 读取事实源对齐 |
| 边界失守 | 风险评估、授权决策 | 规范推理 | 一致性校验、受控写入 | 规则定义边界，AI 推理判断，Code 校验写入是否越界，Human 做关键授权 |
| 事实混乱 | 经验直觉 | 缺口发现 | 精确读取、持久记忆 | 事实源边界隔离可信与不可信，Code 精确读取和持久记忆，AI 发现事实缺口 |
| 上下过载 | 优先排序 | 归纳拆解 | 快速索引 | Human 排优先级，AI 拆解重点，Code 索引定位，避免全量加载 |
| 规则漂移 | 价值判断 | 规范推理 | 一致性校验 | 规则入口场景化触发，AI 推理当前适用规则，Code 校验是否遵守 |
| 状态不明 | 质量验收 | 结构处理 | 状态聚合 | Code 聚合全局状态，AI 处理状态字段判断合法性，Human 验收关键状态 |
| 反馈缺失 | 质量验收 | 反馈迭代 | 实时反馈 | Code 实时反馈执行结果，AI 据此迭代，Human 验收最终结果 |
| Code 失控 | 授权决策、风险评估 | Code 调用 | 受控写入 | Code 提供受控入口，AI 通过入口调用，Human 审批高风险操作 |
| 记忆断裂 | 经验直觉 | 文档生成、模式迁移 | 持久记忆 | AI 生成文档沉淀经验，Code 持久存储，AI 迁移复用，Human 补充直觉经验 |
| 停点不明 | 价值判断、授权决策 | 规范推理 | 一致性校验 | Human Gate 定义停点，AI 推理识别停点，Code 校验是否跳过 |

```text

LD Vibe Harness 以 AI 执行者为第一服务对象。

这里的"第一服务对象"不是价值排序，而是设计顺序：先按照 AI 执行者的能力结构设计产品框架，再通过 Human、AI 和 Code 的分工实现产品闭环。

AI 执行者的能力结构可以从擅长和害怕两个方面理解。

AI 擅长：意图理解、归纳拆解、方案生成、结构处理、规范推理、Code调用、模式迁移、反馈迭代、文档生成、缺口发现。

AI 害怕：目标含混、边界失守、事实混乱、上下过载、规则漂移、状态不明、反馈缺失、Code失控、记忆断裂、停点不明。

LD Vibe Harness 的工作流程设计遵循一个核心原则：充分利用 AI 擅长的，针对 AI 害怕的，设计 Human、Code、流程、规范组合配合。

三方的本质区别：Human 提供判断力，AI 提供推理力，Code 提供执行力。配合不是一一对应，而是三方能力的组合。以"事实混乱"为例：AI 概率性推理容易混淆可信与不可信，因此需要事实源边界隔离可信与不可信，Code 确定性读取和持久记忆，AI 在可信事实上推理，Human 补充直觉经验——四者组合才能让 AI 在可信基础上高效产出。

它要充分发挥 AI 理解力强、知识面广的优势，有效补足前说后忘、行动漂移的短板，更通过规范驱动实现闭环，让 AI 的推理生成能力服务产品持续演进。

因此，LD Vibe Harness 不只是为 AI 提供上下文，而是为 AI 提供可行动的项目环境：让 AI 知道在什么情况下去哪里读取什么、依据什么判断、如何拆解任务、何时调用 Code、什么情况下需要等待 Human 确认，以及完成后如何形成从证据沉淀到事实回写的闭环。

LD Vibe Harness 同时在工作流程中设计反馈机制：AI 在执行中发现规则缺口、事实源混乱、Code 不足和重复失败时，应通过 Memo、Pitfall、Task 或 ADR 将发现回流到规范体系、工作模型或工作流程中，使体系在执行中持续完善。

在这个前提下，LD Vibe Harness 从 Human、AI、Code 三个视角进行架构，由开发环境、辅助工具、工作模型和工作流程四类构成要素共同组成，并以 Git 文件事实源作为底层权威原则。

Human 在 LD Vibe Harness 中负责：

1. 表达意图；
2. 补充约束；
3. 排定优先级；
4. 确认关键节点；
5. 做出关键决策和授权；
6. 校正 AI 判断；
7. 验收结果。

AI 负责：

1. 读取项目上下文；
2. 识别当前任务场景和事实源边界；
3. 拆解任务并提出执行计划；
4. 依据规范推理生成 rules、skills、Code 等能力实现；
5. 判断需要调用的 Code、Skill 或子 Agent；
6. 识别风险、阻塞和需要 Human 确认的节点；
7. 执行任务并记录执行证据；
8. 按事实源边界写回项目；
9. 发现问题和改进机会，通过 Memo、Pitfall、Task 或 ADR 回流规范。

Code 负责：

1. 读取、索引和聚合事实源；
2. 生成 AI 可行动的最小上下文；
3. 校验事实源、规范、引用、状态和执行结果；
4. 提供受控写入入口；
5. 通过网页视图呈现项目态势、证据、风险和待确认事项；
6. 降低 Human 和 AI 维护结构化文件的成本。
```
