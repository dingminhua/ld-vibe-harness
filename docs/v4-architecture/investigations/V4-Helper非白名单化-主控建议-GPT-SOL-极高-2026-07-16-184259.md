## 1. 给主控的直接结论

V4 应继续采用 Helper，不应恢复 V3 的中央 Action Classifier。

正确目标不是“取消所有闭集”，而是严格区分三个边界：

1. **Helper 公开服务能力可以是闭集**：机器接口必须具有稳定 `operation_key`、输入、输出和实现边界；
2. **原生机械 Gate 的合格条件可以是闭集**：例如同一 Git `commit-msg` 事件中，对实际 message、Index、worktree 和当前规则契约做 allow/block；
3. **AI 的普通行动空间必须保持开放**：用户目标、新工具、新任务类型和普通求解不得因为不在 Helper `capabilities`、行动模板或 adapter 映射中而被判定为禁止。

建议主控采用以下架构口令，并把它转化为规范约束和自动化测试：

> **服务能力闭集，机械条件闭集，AI 行动开放；所有阻断必须来源绑定、对象绑定、效果绑定并限制在最小范围。**

在恢复一般 `PreToolUse`、完成检查或更多环境生命周期之前，应先建立本文第 8 节的反白名单验收测试。否则 V4 最容易在“补回 V3 功能”的过程中重新引入 V3 的根本问题。

## 2. 什么是本次所说的“行动白名单”

行动白名单不只指一个名为 `ALLOWED_ACTIONS` 的数组。只要系统满足下列特征，就已经形成事实上的行动白名单：

1. 必须先把用户任务或工具调用归入中央动作类型，系统才允许继续；
2. 中央代码枚举已知工具、命令、用户意图或工作阶段；
3. 新工具、新命令或新任务必须修改中央分类器；
4. 未匹配的动作默认等价于“不支持”“不允许”或全局阻断；
5. 行动模板、Helper `operation_key` 或环境事件映射被解释为全部合法行动的集合；
6. Code 取代 AI 判断自然语言任务、规则适用性、授权或完成语义。

反之，Helper 的机器接口使用闭集不等于行动白名单。闭集只说明“LDVH 能直接提供或机械验证什么”，不说明“AI 只能做什么”。

| 边界 | 是否允许闭集 | 闭集的合法含义 | 不得被解释为 |
|---|---:|---|---|
| Helper `operation_key` | 是 | 当前规则源定义且已有实现的服务能力 | AI 允许执行的全部行动 |
| 某个原生机械 Gate | 是 | 对明确事件、对象和机械条件的 allow/block | 所有工具和所有任务的总许可器 |
| 行动模板 | 否，不形成中央许可表 | 可复用行动知识和验证结构 | 未命中就不得行动 |
| AI 普通求解 | 否 | 依据用户目标、当前事实、适用规则和实际授权自主规划 | 必须先映射为 Helper 操作或模板 |

### 3.2 未知动作默认进入写类 preflight

V3 的核心分类入口位于 [`action_classifier.py:1035`](../../../../ld-vibe-harness-v3/code/action_classifier.py#L1035)。无法命中已有分类时，最终分支返回：

对应代码见 [`action_classifier.py:1111`](../../../../ld-vibe-harness-v3/code/action_classifier.py#L1111)。这就是白名单机制的直接证据：未知项并非保持为普通求解或只报告能力缺口，而是被中央分类器收敛成需要 preflight 的写动作。

### 3.3 通用 Hook 把分类器放到所有工具调用前

V3 Codex 插件把 `PreToolUse` 配置为 `matcher: "*"`，见 [`hooks.json:14`](../../../../ld-vibe-harness-v3/hooks/environment-plugins/codex-ldvh-v3/hooks/hooks.json#L14)。同一插件还统一接入 `PostToolUse`、`UserPromptSubmit`、`Stop` 和 `Notification`。

问题不在于 Hook 数量本身，而在于“所有工具调用 → 中央分类器 → 默认未知写动作”的组合。该组合迫使系统持续穷举工具协议和 Shell 语义。

在本次基线中：

```text

```

行数不能单独证明设计错误，但结合上述枚举、Shell 解析和默认分支，可以证明 V3 把环境协议识别、动作分类、目标推断、读写判断、任务导航和规则消费持续集中到了中央实现。

## 4. 可查证的 V4 正确方向

### 4.1 根规范已经定义开放普通求解边界

V4 根规范明确规定：命中具体规则时执行该规则；未命中具体规则时，Helper 仍可提供服务，但 AI 普通求解路径保持自主。见 [`specs/00-理念与构成.md:99`](../../../specs/00-理念与构成.md#L99)。

这条规则已经足以否定“Helper 能力列表就是行动许可列表”。本建议不要求改变根规范语义。

### 4.2 `capabilities` 当前只定义服务发现

04 将 `capabilities` 定义为当前规则源公开操作、实现和输入的发现入口，见 [`specs/04-Helper CLI 服务规范.md:102`](../../../specs/04-Helper%20CLI%20服务规范.md#L102)。公开操作由来源定义，Code、tests 和环境不能反向创造，见 [`specs/04-Helper CLI 服务规范.md:104`](../../../specs/04-Helper%20CLI%20服务规范.md#L104)。

在本次观察基线，真实命令：

```bash
.venv/bin/ldvh capabilities | jq -r '.result.operations[].operation_key'
```

返回 10 项：

```text
create-fact-object
find-fact-object-candidates
prepare-fact-object-draft
read-action-template-candidates
read-action-template-content
read-fact-objects
read-specification-candidates
read-specification-content
resolve-governance-scope

```

这些操作描述 V4 当前可以直接提供的服务，并未枚举 `research`、`refactor`、`fix-bug`、`run-tests`、`edit-code` 或环境工具名。这是正确方向。

### 4.3 行动模板规范已经否定模板许可化

06 明确规定：

- 模板适用不等于行动获授权：[`specs/06-行动模板基础规范.md:176`](../../../specs/06-行动模板基础规范.md#L176)
- 选择、执行、验证与完成不是同一结论：[`specs/06-行动模板基础规范.md:180`](../../../specs/06-行动模板基础规范.md#L180)
- 模板是内部行动知识，不要求用户逐个安装或选择：[`specs/06-行动模板基础规范.md:193`](../../../specs/06-行动模板基础规范.md#L193)
- 模板未命中时 AI 继续普通求解：[`specs/06-行动模板基础规范.md:197`](../../../specs/06-行动模板基础规范.md#L197)

因此 V4 不应建立 `approved_template_keys`、`required_action_template` 或“无模板则阻断”的中央逻辑。

### 4.4 环境规范已经把机械 Gate 限定为窄例外

09 规定环境原生事件、共享 Hook 行为和 Helper 操作分层，见 [`specs/09-环境接入规范.md:92`](../../../specs/09-环境接入规范.md#L92)。只有其它当前来源已经定义封闭纯机械合格条件，且原生事件只能就地允许或阻断时，才允许直接调用唯一核心 Gate，见 [`specs/09-环境接入规范.md:94`](../../../specs/09-环境接入规范.md#L94)。

09 同时明确不建立共享 Hook 行为固定闭集或中央登记，见 [`specs/09-环境接入规范.md:98`](../../../specs/09-环境接入规范.md#L98)。

### 4.5 当前 `commit-msg` 是正确的窄 Gate 样板

最新 V4 已在 `93ae8411` 合入原生 `commit-msg` Gate。共享实现只应用 03 的机械契约：[`code/ldvh/hooks/commit_msg.py:108`](../../../code/ldvh/hooks/commit_msg.py#L108)。它绑定实际 worktree、message、governance 和 Index，然后调用 commit candidate observation 与 validation。

原生 adapter 只投影 Git 能提供的参数，不复制规则：[`code/ldvh/git_hooks/commit_msg.py:250`](../../../code/ldvh/git_hooks/commit_msg.py#L250)。安装还要求 Human Gate 且不覆盖非 LDVH Hook：[`code/ldvh/git_hooks/commit_msg.py:307`](../../../code/ldvh/git_hooks/commit_msg.py#L307)。

对应真实 Git 生命周期测试验证了：

- 非法消息阻断、合法消息通过；
- 实际临时 Index 被观察；
- 无法绑定管辖时 fail closed；
- 不覆盖用户 Hook 或修改 `core.hooksPath`。

测试见 [`code/tests/git_hooks/test_commit_msg.py:142`](../../../code/tests/git_hooks/test_commit_msg.py#L142)。

这个实现可以作为“封闭机械 Gate”的样板，但不得推广为“所有未知工具调用默认阻断”的依据。Git `commit-msg` 可以 fail closed，是因为该原生事件、候选对象、实际 Index 和机械合格条件都是封闭且可观察的；一般用户任务和任意 `PreToolUse` 不具备这个条件。

## 5. 当前仍存在的重新白名单化风险

### R1：把 `operation_key` 误当成许可标识

04 的公开操作集合必须是闭集，但未来 adapter 可能错误实现为：

```text
工具调用无法映射到 operation_key -> deny
```

正确结果应是：Helper 没有对应服务能力，或当前不需要 Helper；这本身不决定普通行动是否合法。

### R2：恢复一个“大一统 PreToolUse 分类器”

若主控为了补回 V3 写前治理，重新建立工具名、Shell 命令、任务意图和操作类型的中央枚举，即使模块改名为 `helper_action_router`，本质仍是 V3。

### R3：把行动模板变成必选路由

如果未来要求每项任务先选一个 `template_key`，或没有匹配模板就停止，06 的内部知识边界将被实现反向改写。

### R4：把 Helper 不可用扩大成全任务停止

某项 Helper 能力不可用，只能暂停依赖该能力或具体来源规则的最小行动范围。它不能自动阻断不依赖该 Helper 能力的普通读取、分析、代码修改或沟通。

### R5：用环境事件映射建立第二套动作注册表

环境 adapter 如果维护 `event/tool -> LDVH action type -> operation_key` 的全量中央表，就会同时复制厂商协议、动作语义和 Helper 服务路由。09 已经要求 adapter 只做薄投影，不得取得 Helper 之外的语义权威。

### R6：把 fail-closed 从窄 Gate 扩张为全局策略

“无法证明 Git 当前 Index 合格，所以阻断这次 commit”是正确的。

“无法理解一个新 Bash 命令，所以阻断整个任务或把它认定为未授权写入”是白名单化。

二者必须在规范、代码接口和测试中分开。

## 6. 建议写入下位规范的反白名单不变量

00 §3 已经提供上位依据。建议不要为了本建议改变 00 的语义，而是在 04 和 09 中增加由 00 §3 派生的明确约束，并补 contract tests。若主控判断拟议文字改变而不是澄清 00 的上位边界，则应按 00 进入相应 Human Gate。

### AWI-01：能力发现不构成行动许可

建议在 04 `capabilities` 章节加入：

> `capabilities` 及其公开 `operation_key` 集合只表示 Helper 当前能够直接提供、检查或执行的服务能力，不构成 AI、Human、环境工具或普通求解行动的许可清单。某项行动没有对应公开操作，只能证明 Helper 没有以公开操作直接承担该行动；不得据此形成行动禁止、授权缺失、规则适用或任务停止结论。

### AWI-02：阻断必须具有四项绑定

建议在 04 状态变更边界或 09 原生机械 Gate 章节加入：

> 任何自动阻断必须同时绑定：定义阻断条件的当前来源、受保护的具体对象或状态转换、当次可观察的实际效果或候选，以及能够覆盖风险的最小受影响范围。缺少任一绑定时，不得用中央动作类型、工具名称、模板缺失或 Helper 能力缺失补造阻断依据。

### AWI-03：未知行动不等于禁止行动

建议在 09 输入投影章节加入：

> 未知工具名、未知自然语言任务、未登记命令形态和未映射环境事件不得仅因“未知”而被解释为禁止行动。能够证明未命中任何适用受保护边界时应 no-op 或只报告接入缺口；已经命中来源定义的受保护边界但缺少该 Gate 必需输入时，只暂停受影响的最小行动，并以“对象或效果不可验证”而不是“动作不在白名单”作为原因。

### AWI-04：Helper 不可用只缩小能力声明

> Helper 进程、单项操作、环境映射或某项验证不可用时，只暂停实际依赖该能力且由来源要求暂停的范围。未依赖受影响能力的普通求解路径继续；不得把 `unavailable`、未知 `operation_key` 或 adapter 缺口提升为全局拒绝。

### AWI-05：行动模板缺失保持普通求解

06 已经具备该语义，建议只补自动化测试，不新增中央模板选择状态机。

### AWI-06：不得建立通用行动类型权威

> LDVH 核心不得建立要求所有用户任务、工具调用、Shell 命令或环境事件先归类后才能继续的中央 Action Type、Allowed Actions、Supported Tools 或固定工作阶段。来源已经定义的对象类型、事实状态、机械效果类别或单一 Gate 结果闭集不受此限制，但不得扩张为普通行动许可模型。

## 7. 推荐的运行时恢复架构

### 7.1 正确数据流

```text
原生环境事件
  -> 薄 adapter：只投影环境实际提供的字段
  -> 可观察上下文：event / tool identifier / cwd / targets / effect evidence
  -> resolve-governance-scope
  -> 检查是否命中“当前来源已经定义”的受保护边界
       -> 未命中：no-op、提示或普通 Helper 信息服务；AI 继续求解
       -> 命中封闭机械 Gate：调用唯一核心，返回最小范围 allow/block
       -> 需要语义或 Human 决定：把来源、输入和缺口交给 AI/Human
```

这条链中不应出现：

```text
所有工具调用 -> 中央 action classifier -> allowed action/template/operation 列表 -> allow/deny
```

### 7.2 adapter 只记录事实，不定义语义

建议未来共享观察结构只包含环境实际可观察字段，例如：

- 原始事件名称，使用开放字符串；
- 原始工具标识，使用开放字符串，不建立全部支持工具枚举；
- 环境明确提供的目标路径或对象；
- 环境或确定性解析实际证明的效果证据；
- cwd、时间、环境来源和原始 payload 回查引用；
- 未提供或无法确认的字段。

小型机械效果类别可以存在，例如 `read_only`、`state_change`、`external_side_effect`、`unknown`，但必须满足：

1. 它只描述当次可观察效果，不是行动许可；
2. 不从自然语言任务猜测；
3. `unknown` 不自动等于全局拒绝；
4. Gate 是否适用仍须回到具体来源和受保护对象。

### 7.3 不要把 Shell 解析器当安全边界

不要恢复 V3 对管道、重定向、`find`、`xargs`、Git 全部子命令和 Python 脚本的持续穷举。

应优先使用更接近真实对象的边界：

- Git 提交：读取原生 Git 事件和实际 Index；
- 事实创建/更新：使用 Helper 受控事务、CAS、原子写入和写后回读；
- 规范与事实一致性：使用 validator、post-change 检查和 CI；
- 环境安装：使用明确安装 action、Human Gate、状态检查和真实触发证据；
- 无法机械观察的普通任务语义：由 AI 对照来源判断，不伪装成 Code 已保障。

一般 `Bash` 不能仅因无法证明只读就被全局禁止。若 Bash 实际命中某个来源定义的受保护对象，应由该对象的专属边界处理；若目标和效果均无法绑定，则只按适用来源暂停能够覆盖风险的最小范围。

### 7.4 Completion 不应由通用 Stop 事件自动定义

环境 `Stop` 可能只表示一次模型输出结束，不等价于工作完成声明。未来恢复完成验证时，应由明确的“准备声明完成”输入或来源定义的 WorkCase/行动模板完成条件触发；原生 Stop 只有在厂商事件语义和当前来源共同证明等价时才能映射。

完成检查可以机械验证已有证据、测试结果引用、未完成范围和事实状态，但不得由 Code 判断自然语言目标已经充分满足。

## 8. 必须建立的反白名单验收矩阵

建议在任何一般 `PreToolUse`、动作观察器、完成 Hook 或新环境 adapter 合入前，先建立专门测试文件，例如：

```text
code/tests/architecture/test_open_action_boundary.py
code/tests/environment/test_runtime_open_action_boundary.py
```

建议的最低测试矩阵如下：

| ID | 场景 | 必须结果 | 失败说明 |
|---|---|---|---|
| AW-01 | 调用未知 Helper `operation_key` | Helper 只报告无该服务/请求不可用；环境不得据此生成普通行动 deny | 把服务闭集当成许可闭集 |
| AW-02 | 当前任务没有匹配行动模板 | AI 普通求解继续；不要求用户选择模板 | 模板许可化 |
| AW-03 | 新增从未登记的只读工具，目标不受 LDVH 管辖 | no-op 或提供普通信息，不阻断 | 工具名白名单 |
| AW-04 | 新工具修改管辖项目中的普通代码，但未命中来源定义的专属 Gate | 不得仅因工具未知而阻断 | 通用工具白名单 |
| AW-05 | 新工具尝试改变受保护事实源 | 根据事实源路径、对象和实际效果命中专属 Gate；不依赖工具名称 | Gate 未对象绑定 |
| AW-06 | Helper 某项服务不可用 | 只暂停依赖该服务的最小范围；其它普通工作继续 | 不可用被提升为全局停止 |
| AW-07 | 新增一个由现有事实模型支持的事实类型 | 继续使用通用事实发现/创建/更新操作，不增加 `create-<type>` | 领域动词白名单膨胀 |
| AW-08 | 新增环境事件但没有成立的共享行为映射 | 安全场景 no-op；需要语义时报告缺口，不猜“最近动作” | 事件映射白名单 |
| AW-09 | 某个机械 Gate 返回 block | 响应包含来源、对象、实际候选/效果和最小阻断范围 | 无来源全局阻断 |
| AW-10 | 同一效果由两个不同工具名产生 | 命中结果由对象和效果决定，而不是工具别名决定 | 工具枚举耦合 |
| AW-11 | 无法解析复杂 Shell 命令 | 不伪造只读/写入结论；改用专属真实边界或明确不可验证范围 | 恢复 Shell 语义猜测器 |
| AW-12 | 环境 Stop 发生但没有完成声明输入 | 不生成“任务完成”或完成阻断结论 | 生命周期事件语义越权 |

### 8.1 建议增加的结构性断言

1. 一般 runtime package 中不存在要求所有调用先通过的 `ALLOWED_ACTIONS`、`SUPPORTED_TOOLS`、`READ_ONLY_TOOLS`、`WRITE_TOOLS` 中央许可表；
2. adapter 源码不包含事实 Schema、行动模板正文、规则判断或完成规则副本；
3. 通用 Helper 响应不产生 `action_allowed`、`task_authorized`、`task_completed` 等超出具体来源和调用范围的结论；
4. 阻断型接口必须是具体 Gate 类型，不能复用一个接受任意自然语言任务并返回 allow/deny 的通用 `assess-action`；
5. 新工具别名或新任务动词不要求修改 Helper 核心。

这些断言应以 AST/模块依赖、响应契约和行为测试为主；简单关键词扫描只能作为审计提示，不能单独作为通过证据。

## 9. Helper 公开操作的准入判据

主控可以用以下问题判断是否应该新增 `operation_key`：

### 应新增或复用公开操作的情况

1. AI 需要稳定调用一项 LDVH 自身拥有的服务；
2. 服务具有明确来源、对象、输入、输出和读取/状态变更边界；
3. Code 能机械执行或验证，不需要替代 AI 的自然语言语义判断；
4. 操作能够跨任务、工具和环境复用；
5. 没有公开入口会迫使 AI 了解内部 Python 模块或绕过受控事务。

当前 `create-fact-object`、`update-fact-object`、`resolve-governance-scope` 都符合这种形态。

### 不应新增公开操作的情况

不要仅因为出现以下内容就新增操作：

- 新用户意图：`research`、`fix-bug`、`refactor`；
- 新工具：`bash`、`apply_patch`、某个 MCP tool；
- 新行动模板；
- 新环境 Hook 名；
- 现有通用事实操作已经能通过 `fact_type_key` 承载的新事实类型；
- 一次性工作计划步骤。

否则 `operation_key` 会从服务接口退化为行动白名单。

## 11. 推荐实施顺序

### 第一步：先固定规范推论，不改根语义

1. 主控确认“Helper 能力闭集不等于行动许可闭集”；
2. 在 04/09 增加 AWI-01 至 AWI-04 的明确下位约束；
3. 由独立审核确认新增文字只是落实 00 §3，没有改变根规范语义。

### 第二步：先写反白名单测试

至少建立 AW-01、AW-02、AW-03、AW-04、AW-06、AW-09、AW-12。测试未建立前，不应合入通用动作观察器或所有工具共用的阻断路径。

### 第三步：按受保护对象逐项恢复运行时治理

推荐顺序：

1. 保持已经形成的 Git `commit-msg` 窄 Gate；
2. 事实写入继续以 Helper 受控事务和写后回读为主；
3. 对确有来源定义的规范、配置或安装变化建立专属检查；
4. 再考虑一般 `PreToolUse` 的只读观察与提示能力；
5. 不建设覆盖全部工具和 Shell 的中央 Action Classifier。

### 第四步：恢复完成验证，但不把 Stop 当完成

先定义明确完成声明输入、证据结构、未完成范围和 AI/Human 分工，再决定哪些环境事件能够真实映射；没有映射证据的 Stop 保持 no-op 或仅提供提示。

### 第五步：执行三层验证

1. contract tests：Helper 服务闭集和普通行动开放边界；
2. behavior tests：未知工具、未知事件、能力不可用和专属 Gate；
3. real trigger：目标环境真实触发，保存原始事件、转换请求、Helper/Gate 结果和环境反馈。

## 12. 主控决策清单

建议主控明确接受以下决定：

- [ ] V4 继续使用 Helper，不恢复 V3 `action_classifier.py` 或等价中央动作分类器；
- [ ] `capabilities` 只表示服务发现，不表示行动许可；
- [ ] 新工具、新任务动词、新模板和新环境事件不自动要求新增 `operation_key`；
- [ ] 一般 PreToolUse 不以工具名称或 Shell 白名单作为阻断依据；
- [ ] 自动阻断必须回指当前来源、明确对象、实际效果/候选和最小范围；
- [ ] `unavailable`、未知操作和模板未命中不形成全局停止；
- [ ] Git `commit-msg` 作为窄机械 Gate 样板，不扩张为所有工具调用的 fail-closed 先例；
- [ ] 在恢复一般运行时治理前先建立 AW-01 至 AW-12 的反白名单验收矩阵；
- [ ] 任何把 Helper 能力集合改为 AI 行动许可集合的提议，都视为改变 00 §3 上位边界，先暂停并进入对应 Human Gate/独立审核。

## 13. 最终建议

V4 从 V3 的行动白名单转向 Helper 是正确且必要的架构修正。当前 00、04、06、09 已经分别提供了普通求解自主、服务能力发现、模板非授权和窄机械 Gate 的正确基础；当前通用事实操作和最新 Git `commit-msg` Gate 也提供了正向实现样本。

真正的风险不在现有 Helper，而在未来补回 PreToolUse、完成检查和更多环境事件时，把下列三件事重新混为一体：

```text
Helper 能做什么
来源规则要求什么
AI 可以做什么
```

主控应把三者永久分层：Helper 公开它能可靠提供的服务；来源规则定义具体对象和场景的要求；AI 在用户授权与适用规则内保持开放求解。只有来源已经定义、对象和效果能够真实绑定的封闭机械条件，才进入自动阻断。

据此，本建议对 V4 Helper 方向给出：**附条件通过**。条件不是增加更多行动目录，而是先建立并持续验证“能力闭集不等于行动白名单”的架构不变量。
