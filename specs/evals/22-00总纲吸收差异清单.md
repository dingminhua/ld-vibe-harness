## 1. 本文解决的问题

本文承接 `specs/evals/21-LDVH全盘确认与核心吸收建议.md` 对 LDVH 当前项目方向的全盘确认结论，用于跟踪 00 总纲是否已经吸收其中需要正式确认的核心命题。

本文的主要目标是：

1. 将 00 总纲吸收事项整理为可勾选清单，避免梳理过程中遗忘进度；
2. 区分已覆盖、部分覆盖、未覆盖和需决策内容；
3. 标注后续可能影响的正式规范、Rules、Skill、Tools、Web 或 Task；
4. 在正式修改 00 总纲前，先形成可讨论、可分批推进的内部参考。

本文不是正式规范，不直接修改 00 总纲，不替代 ADR、Task 或 Change。涉及 00 总纲、工作流程、工作模型、Rules、Skill 或 Tools 的正式变更时，应回到对应正式规范、Human Gate、Task 和 Change 流程。

---

## 2. 结论

首轮梳理建议以 00 总纲为入口，优先确认 `specs/evals/21-LDVH全盘确认与核心吸收建议.md` 中 P0 级内容是否已经稳定进入总纲。

当前初步判断是：00 总纲已经覆盖 LDVH 存在理由、AI 第一体验、四类构成要素、Git 文件事实源原则、价值实现标准、Human Gate 与防递归建设原则，但以下内容仍需要重点确认：

1. 产品定义是否需要以更凝练的总纲句式固定；
2. Core Loop 六阶段是否需要作为运行闭环标准显式写入；
3. Task 治理锚点是否需要提升为总纲级原则；
4. “未验证不完成”是否需要成为总纲级工程纪律；
5. Human Gate 是否需要从高影响变更确认进一步表述为判断权、授权权和责任边界；
6. Skill 生命周期化、独立审计 Agent、工具权限面和第三方 Skill 治理接管是否仅在后续规范承接，还是需要在 00 中保留顶层原则。

## 7. 暂缓与不吸收清单

| 状态 | 内容 | 当前建议 | 理由 |
|---|---|---|---|
| [ ] | 自建 MCP | 暂缓 | PyTools、Validator、Web 态势入口与受控轻写入边界尚未完全稳定 |
| [ ] | ProjectGroup 工作模型 | 暂缓 | 可先用 Profile tags 和项目身份轻量承接 |
| [ ] | Automation / Cron 工作模型 | 暂缓 | 先把 Task / Change / Verify / Web / Validator 闭环跑稳 |
| [ ] | Web 开放式写入后台 | 暂缓 | 不做开放式 YAML 编辑或任意字段修改；但保留受控轻写入路线：Memo 可创建，生产对象无删除，其他对象仅允许修改名称、调整优先级、安排前置任务、修改目标等有限操作，并可增加人工修改标记供 AI 识别 |
| [ ] | 大规模生成 Rules、Skill、Validators 或 Web schema | 暂缓 | specs 结构化程度和契约消费路线仍需整理 |
| [ ] | 隐藏本地状态目录作为事实源 | 不吸收 | 会制造第二事实源 |
| [ ] | 自动 push、release、merge | 不吸收 | 属于 Human 权限边界 |
| [ ] | 分数式完成标准 | 不吸收 | LDVH 完成标准应基于 acceptance、验证、evidence、Human Gate、Change 和状态机 |
| [ ] | 人格化 Agent 系统 | 不吸收 | Agent 应作为独立上下文、专业审计或隔离评估能力 |
| [ ] | AI 自审即完成 | 不吸收 | Verify 应具备外部性和可追溯证据 |
| [ ] | 平台能力替代 LDVH 内核 | 不吸收 | 平台能力只能增强承载底座，不能替代事实模型和治理闭环 |
