## 1. 本文解决的问题

本文解决 LD Vibe Harness 中 Web 构成要素如何承载信息同步、派生视图、状态和缺口呈现、Confirm UI、受控轻写入白名单和 Web 实现文档的问题。

Web 的目标不是替代 specs、Code、Rules、Skill、Agent 或事实实例，而是把 Git 文件事实源及其派生状态以人可读、可确认、可操作的方式同步给人，并仅在规范白名单允许时提供受控写入和确认入口。

LDVH 整体以 AI 执行者为第一服务对象；Web 的直接服务对象是 Human。Web 设计必须立足人的理解、判断、确认、验收和方向校正需求，同时服务 AI 执行闭环的可见性与可控性。Web 不应按传统项目管理看板优先设计后再要求 AI 适配，而应在事实源、事实模型、行动编排、Code、Rules、Skill 和 Agent 已经服务 AI 执行的基础上，为 Human 提供看见 AI 状态、理解风险、介入关键判断和完成受控授权的界面。

本文只定义 Web 信息同步实现相关内容。Code 辅助、确定性校验、受控写入和测试实现由 `specs/07-Code确定性执行实现规范.md` 独立承载。LDVH 在 `web/` 下提供了一套参考实现，用户可根据本文约束自行实现 Web。

## 2. 与 00 总纲的关系

00 定义 Web 是 LD Vibe Harness 的五类构成要素之一。Web 负责面向人同步事实源状态、缺口、验证结果和确认项，并提供 Confirm UI 与受控轻写入白名单约束下的交互。

本文承接 00 对 Web 的定位，定义 Web 与 Git 文件事实源、Specs、Code、测试、缓存、数据库、Human Gate 和实现文档的边界。稳定规则仍由 specs 定义，稳定事实仍由 Git 文件事实源承载，Web 页面状态、缓存和数据库派生视图不得反向替代规范正文或事实实例。

### 2.1 服务对象分工

LDVH 的服务对象分工如下：

| 层面 | 第一服务对象 | 主要需求 | Web 参与方式 |
|---|---|---|---|
| LDVH 整体框架 | AI 执行者 | 快速定位事实、理解约束、选择工具、执行工作流、验证并回写 | Web 提供 Human-facing 桥接，帮助人看见和校正 AI 执行态势 |
| Web 信息同步层 | Human | 理解项目态势、判断风险、确认授权、验收结果、在白名单内进行受控轻写入 | 展示事实源和派生状态，提供 Confirm UI 与受控交互 |

因此，Web 的设计判断应优先回答：

1. Human 当前需要理解什么项目态势、风险、阻塞、证据或待决策点；
2. Human 需要在哪里介入 AI 执行闭环、给出确认、取消、暂缓或修改反馈；
3. Human 的判断如何通过受控链路回到事实源、工作对象、验证结果或 Git 提交记录；
4. 哪些信息应保留为 AI 可执行的结构化事实，哪些信息只需要面向 Human 页面呈现；
5. 哪些交互会让 Web 越界成为事实源、绕过 Code 或弱化 AI 第一服务对象定位。

## 3. Web 权威领域

本文是 LDVH Web 信息同步构成要素、Web 信息同步层、派生视图、状态和缺口呈现、Confirm UI、受控轻写入白名单、缓存和数据库边界、Web 与 Code 协作关系、Web 实现文档边界以及 Web Human Gate 检查要求的权威规范。

本文不定义 Code 命名、CLI、输出结构、更新维护或确定性校验算法；这些内容由 `specs/07-Code确定性执行实现规范.md` 承载。跨构成要素的测试治理、验证声明和测试证据边界由 `specs/11-测试基础规范.md` 承载。

## 4. Web 与事实源边界

Web 可以展示、同步、筛选和解释 Git 文件事实源及其派生状态。Web 只有在本文和对应对象规范明确列入白名单时，才可以辅助写入 Git 文件事实源。Web 的价值是降低人理解、确认和操作事实源的成本，而不是替代事实源。

Web 治理原则如下：

1. **Web 不等于事实源**：页面状态、缓存、数据库派生视图、运行时索引和 UI 页面呈现都不能成为最终事实源。
2. **Web 展示来自事实源**：Web 展示的稳定事实必须可追溯到 Git 文件事实源。
3. **派生状态必须可识别**：Web 展示的派生视图必须标注数据来源、同步时间或可追溯依据。
4. **写入必须受控**：Web 只有在本文白名单和对应对象规范同时授权时，才能提供受控写入入口，且不得绕过事实源边界、对象规范、Code 校验、行动编排或 Human Gate。
5. **实现不替代规范**：`web/`、`web/docs/`、缓存和数据库不能替代 specs/、ldvh-base/ 或 docs/ 中的权威事实。
6. **事实源同源实现**：Web 与 Code 都可以直接读取、解析和聚合 Git 文件事实源，但必须遵守同一套 specs、对象契约、事实源目录、状态定义和写入边界。Web 独立实现面向 Human 的读取、筛选、呈现、缓存、API 聚合或轻写入校验，不等于创建第二事实源；禁止的是脱离 Git 文件事实源和 specs 另建权威数据、字段契约、状态机或验收规则。

## 5. Web 信息同步层规则

Web 信息同步层面向人可读、可确认、可操作的界面，包括派生视图、状态和缺口呈现、Confirm UI 和白名单内受控轻写入入口。

### 5.1 允许职责

1. Web 展示事实实例、规范状态、引用关系、验证结果、缺口和待确认项；
2. Web 展示 Code 生成的确定性诊断、`ldvh_doc` 文档元信息、聚合结果和派生数据；
3. Web 展示规范保障、能力保障、LDVH 能力资产和环境适配缺口的 Human-facing 派生态势；
4. 提供 Confirm UI，承载人类确认、取消、暂缓或修改反馈；
5. 提供白名单内受控轻写入入口，并把写入交给受控写入链路执行；
6. Web 展示同步延迟、数据来源、最近更新时间和错误状态；
7. 提供面向人的筛选、导航、对比和审查体验；
8. 围绕 Human 的理解、判断、确认、验收和方向校正需求组织信息架构与交互优先级。

### 5.2 禁止职责

1. 定义事实源权威规则、对象字段契约或状态机；
2. 在白名单之外或绕过校验修改 Git 文件事实源；
3. 将页面状态、缓存或数据库派生视图提升为稳定事实；
4. 直接调用 AI、Skill 或 Agent；
5. 用 UI 展示替代验证证据或事实源回写；
6. 在 Web 中维护独立于 Git 文件事实源的权威状态；
7. 以 Web 页面表单、看板或人类项目管理习惯反向定义 AI 执行流程、对象契约或闭环规则；
8. 通过 Web 页面反向新增、补写或迁移 `ldvh_doc` 字段；Web 如发现文档元信息缺失或冲突，只能展示诊断、引导回到 Code / specs 修复流程或在白名单允许时触发受控轻写入。

### 5.3 Web AI 承接边界

并行 AI 或 Web AI 承接 Web 工作时，应先按本文做只读差距审计，再进入实现。只读差距审计至少按页面或 API 列出事实源来源、派生状态、Human Gate 状态、写入白名单状态、测试归属、错误态和需要 Human 决策的事项。

Web AI 不得自行决定以下事项：

1. 扩大 Web 写入白名单；
2. 将 Gate 页面升级为审批系统；
3. 通过 Web 页面反向定义 WorkCase、ADR、Pitfall 或行动编排状态；
4. 绕过 40-59 成员主文件自描述和 Code 派生行动编排集合索引恢复未标记为 active 的行动编排测试机制；
5. 把 `web/docs/`、页面文案、按钮状态、缓存或临时诊断当作 specs 权威来源；
6. 在未补齐来源追溯、错误态和测试归属前，把派生聚合结果呈现为完整事实。

Web AI 如发现上述事项需要推进，应先输出 owner 决策项或 specs 修改建议，不得直接实现。

### 5.4 项目当前事实态势呈现

Web 必须把项目的当前状态以事实可追溯的方式呈现给 Human，使 Human 即使不直接参与 AI 执行，也能清楚看见 AI 正在做什么、将要做什么、哪些事项并行推进、哪些事项等待前置条件、哪些事项需要 Human 配合或决策。

项目当前事实态势呈现应至少回答：

1. 当前有哪些 WorkCase 处于活跃、待审查、已闭合或异常状态；
2. 每个活跃 WorkCase 下有哪些执行项正在执行、验证、已验证、等待前置、待执行或已关闭；
3. 每个 WorkCase 的执行项如存在并行关系，应能看见并行执行、局部等待、验证和关闭状态；
4. 哪些阻塞来自事实源中的 `blocked_by`，哪些等待状态是 Web 基于未关闭前置项派生的展示结果；
5. 哪些事项已经进入 Human Gate、计划关闭判断、验证证据补齐或其他需要 Human 配合的节点；
6. 下一步最可能推进的对象、验证入口、风险或缺口在哪里；
7. 所有状态、数量、关系和提示均能追溯到 Git 文件事实源、Code 确定性输出、Web 后端确定性聚合或明确 Human 输入。

该能力的设计目标是“事实态势同步”，不是恢复独立工作台、项目管理看板或 Web 权威状态。Web 可以用态势条、状态图标、层级卡片、筛选、关联跳转和只读摘要帮助 Human 扫描全局，但不得把页面排序、临时筛选、UI 展开状态或缓存结果解释为 AI 执行事实、任务完成事实或 Human 已授权事实。

执行项的呈现应服务“人看见并行执行和局部进展”的需求。执行项不作为一级导航 tab；当它作为 WorkCase 的内部编排层出现时，应弱于 WorkCase 主线，避免让 Human 误以为每个执行项都需要人工介入。只有进入等待、验证、已验证、异常、Human Gate 或影响计划关闭判断时，执行项才应显著进入 Human 的注意力。

### 5.5 派生态势原因语义规则

Web 呈现派生态势时，不得只使用不能回答原因的泛化状态词。凡是 Web 根据事实源字段、关系、状态机或后端聚合生成的 Human-facing 态势，都应同时具备原因语义和可追溯依据，使 Human 能判断“当前是什么状态”以及“为什么被归入该状态”。

派生态势原因语义规则如下：

1. Web 可以把事实源状态、关系和校验结果聚合为面向 Human 的态势标签，但标签不得反向定义事实源状态机；
2. 同一个事实源状态在不同原因下需要拆分为不同 Human-facing 态势时，Web 应拆分为不同 Human-facing 态势呈现，不得用一个泛化词覆盖多个原因；
3. 呈现“等待”“阻塞”“风险”“需要确认”“验证失败”“待执行”等态势时，应能追溯到 Git 文件事实源字段、Web 后端确定性聚合、Code 输出或明确 Human 输入；
4. 等待类态势必须区分等待原因。没有未关闭前置项的 `planned` WorkCase 或执行项应表达为待执行或计划中；存在未关闭前置关系时，才可表达为等待前置；
5. Human Gate、验证、关闭判断、证据缺失、同步失败、降级和异常等态势也应使用能表达原因的标签或辅助说明，不得仅使用“等待中”“处理中”“异常”等无法定位原因的泛词；
6. 态势条、状态图标、列表卡片、对象详情和右侧扩展阅读区消费同一派生态势语义，不得在不同页面维护彼此冲突的标签、颜色、图标或排序；
7. 新增或修改派生态势原因语义时，应同步检查 Web API 聚合字段、前端映射、i18n 文案、页面文档、图标语义文档和 `tests/web/` 覆盖。

以 WorkCase 或执行项为例，`planned` 只是事实源状态；Web 不得直接把所有 `planned` 都表达为等待前置。Web 只有在确定性聚合出未关闭前置对象或前置执行项时，才可把它表达为等待前置；否则应表达为待执行。该表达仍是 Web 派生态势，不改变 WorkCase 或执行项的事实源状态。

## 6. 信息同步原则

1. Web 页面展示的事实以 Git 文件事实源为准，同步延迟应可识别和可追溯；
2. 派生视图必须明确标注数据来源和同步时间；
3. 派生视图不得维护独立于 Git 文件事实源的权威状态；
4. Web 与 Code 可以各自读取、解析和聚合 Git 文件事实源，但必须基于同一事实源目录、同一 specs 契约和同一对象状态定义；
5. Web 展示的错误、缺口和建议必须能追溯到 Git 文件事实源、规范规则、Web 确定性实现、Code 工具输出或明确的人工输入；
6. Web、Code 或事实源之间发生冲突时，以 Git 文件事实源和对应 specs 为准。

### 6.1 过程输出展示边界

Web 可以展示行动编排过程输出，包括工具报告、检查摘要、候选草案、风险提示、Human Gate 待确认项、验证摘要、下一步建议和临时分析结论。Web 展示过程输出的目标是帮助 Human 和 AI 理解当前流程状态，不是为过程输出建立新的权威事实源。

LDVH 能力资产、规范保障要求摘要、assurance-plan、assurance-report、Validate 结果和 Code 检查输出在 Web 中均属于派生展示或过程输出。Web 可以展示 `specs/04.02-LDVH能力资产与保障机制规范.md` 定义的 Rules、Skill、Agent、Hook、Code、Web 等能力资产及其 Code 检查状态，用于帮助 Human 定位能力资产、理解当前仓库的能力建设状态和识别缺口；该展示不得表达用户可自由启用或禁用能力资产，不得把 Code、Web、CLI、MCP、Command、CI 或文档展示为与 Rules、Skill、Agent、Hook 同级的文本能力资产类型，也不得声明任何外部 AI 开发环境或用户本地实例已经安装、启用或原生完整支持这些能力资产。

过程输出展示应满足：

1. 明确区分已回写事实、待确认候选、临时诊断、验证摘要、风险提示和降级说明；
2. 显示来源路径、命令、测试、Human 输入、同步时间或可追溯依据；
3. 对未回写、未验证、验证失败、同步过期或需要 Human Gate 的内容提供可见状态；
4. 对候选草案、建议动作和风险判断提供回到受控写入链路、工作对象或对应事实源的入口或说明；
5. 不得把页面排序、筛选、勾选、临时编辑、缓存状态或数据库记录解释为流程完成、任务关闭、验收通过或事实源已回写；
6. 过程输出被 Web 展示后若形成稳定事实，仍必须按 `specs/09-事实源边界与承载规范.md` 和对应事实模型、行动编排规范回写 Git 文件事实源。

Web 展示过程输出时，应优先消费 Code 或后端确定性输出；需要 AI 语义判断的内容只能作为候选说明展示，不得在 Web 中自动升级为权威结论。

### 6.2 Web 自主读取与热路径实现纪律

Web 面向 Human 的高频页面、列表、筛选、导航、对象详情和轻量派生聚合，可以由 Web 自主实现 Git 文件事实源读取、YAML 解析、对象摘要、状态统计和关系聚合。此类实现不要求经由 Code CLI 或 Code 输出；只要读取对象仍来自 Git 文件事实源，契约仍遵守 specs，派生结果仍可追溯，就不构成第二事实源。

Web 自主实现应遵守以下纪律：

1. 高频读取路径优先使用 Web 原生确定性实现，避免每次页面加载都启动 Code 子进程、全量校验或重型报告生成；
2. Web 原生实现只能读取、解析、筛选、排序、聚合和展示事实源，不得新增事实源字段契约、状态机、验收规则或写入能力；
3. 对象列表、状态筛选、对象详情和关联摘要应尽量复用同一次事实源读取结果，避免为了 UI 数字、标签或卡片重复触发全量扫描；
4. 页面内可以使用请求合并、进程内临时索引或短生命周期内存缓存改善体验，但缓存必须可失效、可降级，且不得作为事实源、决策或审计依据；
5. Web 消费 Code 输出应限于确定性校验、报告、受控写入或已有输出契约明确更合适的场景，不得因实现便利把普通页面热路径绑定到 Code CLI；
6. Web 原生读取与 Code 输出结果冲突时，以 Git 文件事实源和对应 specs 为准，并应暴露错误态、降级说明或待修复事项。

Web AI 修改上述读取路径时，必须同步检查测试归属和验证方式。新增或重写 Web 原生事实源读取、对象聚合、状态统计、关系索引或请求合并逻辑时，应补充 `tests/web/` 下的 API、服务或组件测试，或在变更说明中记录等价验证命令和无法自动化的原因。

## 7. 缓存和数据库边界

Web 可以使用缓存或数据库改善同步效率和交互体验，但缓存和数据库只能承载派生数据。

缓存和数据库规则如下：

1. 缓存和数据库不得作为事实实例、决策、状态或审计的唯一来源；
2. 缓存和数据库数据必须能追溯到 Git 文件事实源、Code 输出或明确的人工输入；
3. 缓存和数据库内容与事实源冲突时，以事实源为准；
4. 缓存失效、同步失败或派生数据过期时，Web 必须可识别地呈现状态；
5. 引入持久化数据库并影响事实源读取、信息同步或写入链路时，应评估 Human Gate。

## 8. Confirm UI 与 Web 写入白名单

Confirm UI 可用于展示事实实例状态、缺口、风险和待确认项，供人类确认后触发受控写入。

Confirm UI 规则如下：

1. UI 必须清楚展示确认对象、影响范围、风险和可选操作；
2. UI 必须区分确认、取消、暂缓和修改反馈；
3. UI 只能承载人的确认结果，不得自动生成授权；
4. 受控写入入口必须先进入 §8.2 白名单，并提供基于字段契约或对象规范的字段校验；
5. 受控写入入口不得绕过 Code 受控写入层或后端薄封装的确定性校验直接修改事实源；
6. 写入入口应区分可写字段和只读字段；未列入 §8.2 白名单的对象和字段一律只读；
7. 写入后应能展示验证结果、错误状态或回写证据。

### 8.1 Confirm UI 最小字段

Confirm UI 的展示、输入、导出或受控写入结果应能承接 `specs/06-工作流程基础规范.md` §6.3.1 的最小证据结构。

Web 侧至少应支持以下信息被 Human 看见或被确认结果记录：

1. Gate 触发原因；
2. 确认对象或确认事项；
3. 影响范围；
4. 确认依据、风险和可替代方案；
5. 用户选择，至少区分确认、取消、暂缓和修改反馈；
6. 确认人和时间，或环境可提供的等价确认来源；
7. 确认后的执行动作；
8. 验证结果、错误状态或降级说明；
9. 回写位置和残留风险。

Web 可以展示或收集 Human Gate 结果，但不得把 UI 状态、缓存或数据库记录提升为最终事实源。需要长期追溯的确认结果，应通过受控写入链路回写到工作对象、结果文件、Git commit 记录或对应事实源。

### 8.2 Web 事实源写入白名单

当前唯一允许 Web 直接写入 Git 文件事实源的能力是 Spark 快速创建。除下表外，Web 对 WorkCase、ADR、Pitfall、Study、specs、Rules、Skill、Agent、Code 和其它 Git 文件事实源均只能读取、展示、筛选、复制路径或提供跳转，不得修改字段、状态、关系、内容或文件。

| 能力 | API | 写入目标 | 允许字段 | 约束 |
|---|---|---|---|---|
| Spark 快速创建 | `POST /api/sparks` | `ldvh-base/sparks/spark-{NNNN}-{slug}.yaml` | `title`、`description`、`priority` | 只能创建 `status: pending` 的新 Spark；必须校验必填字段和优先级；`source` 固定写入 `web`；不得写入 `status_history`；不得在创建后通过 Web 编辑 Spark 字段或状态 |

白名单规则如下：

1. Web 不得提供对象字段通用 `PATCH`、`PUT`、`DELETE` 或任意 YAML 写回接口；
2. WorkCase 的 `status`、`workcase`、`success_criteria`、`verification_evidence`、`closure_evidence`、`orchestration` 等字段在 Web 中均为只读展示；
3. WorkCase、ADR、Pitfall 和 Study 在 Web 中均为只读展示；
4. Spark 快速创建只用于捕获尚未计划化但值得保留的信息，不得用来绕过 WorkCase、ADR 或 Pitfall 的准入规则；
5. 短期不扩展 Web 写入白名单；Gate、Validate、ProjectFiles、ObjectDetail 和 Dashboard 均不得据页面需要新增写入入口；
6. 未来如需新增 Web 写入能力，必须先修改本文白名单和对应对象规范，补齐校验、测试、Human Gate 影响评估和降级路径，再实现代码。

Spark 快速创建作为当前唯一 Web 写入样例，应满足：

1. 写入前校验 `title`、`description` 和 `priority` 最小字段；
2. 文件名、ID 和 slug 生成必须避免覆盖既有 Spark，冲突时返回明确错误；
3. 写入后必须能重新读取目标文件并确认最小字段、`source: web` 和 `status: pending` 存在，且不得出现手写 `status_history`；
4. API 响应必须区分成功、字段错误、冲突、写入失败和写后验证失败；
5. 必须在 `tests/web/api/` 或等价 Web API 测试分区中覆盖成功、字段错误、冲突和写后验证路径；
6. 不得扩展为通用 YAML 编辑器，不得修改既有 Spark 字段或状态。

### 8.3 Gate / Validate 阶段边界

在对应回写合同、对象规范和 Human Gate 证据落点明确前，Gate 和 Validate 的阶段边界如下：

1. Gate 可以展示待确认项、确认对象、影响范围、风险和可选操作，但确认、取消、暂缓和修改反馈动作只可作为占位或候选过程输出，不得直接回写事实源；
2. Validate 只展示验证结果、错误态、降级说明、来源命令和修复线索，不得自动修复、自动关闭任务或自动写入验证结论；
3. 二者如需从只读展示升级为受控写入，必须先补齐 §8.2 白名单、对应对象规范、Human Gate 最小证据结构、回写位置和 Web 测试要求。

## 9. Web 与 Code 的关系

Web 和 Code 是独立构成要素，二者基于同一个 Git 文件事实源和同一套 specs 契约协作。Code 优先服务 AI 的确定性执行、校验、上下文压缩和受控写入；Web 优先服务 Human 的理解、筛选、确认、验收、方向校正和交互效率。二者可以各自实现读取、解析、聚合、缓存和展示所需的确定性逻辑，不要求 Web 必须经由 Code 才能访问事实源。

| 事项 | Web | Code |
|---|---|---|
| 人可读展示 | 负责 | 不负责 |
| Confirm UI | 负责 | 不负责 |
| 白名单内受控轻写入体验 | 仅负责白名单内表单与反馈 | 执行或约束已授权写入 |
| 确定性解析 | 可为 Human-facing 场景独立实现读取、解析、聚合和 API 适配 | 可为 AI-facing 场景独立实现读取、解析、聚合和上下文压缩 |
| 校验算法 | 可实现 Web 交互、展示、输入和白名单写入前校验 | 负责 Code 工具、命令行、测试和规范保障检查 |
| 派生数据 | 面向 Human 生成、缓存、展示和同步 | 面向 AI 或自动检查生成、聚合和输出 |
| 权威事实 | 不承载 | 不承载 |
| 测试算法行为 | 不负责 | 负责 |

Web 需要事实源数据或确定性派生数据时，可以直接读取 Git 文件事实源，也可以调用 Code 输出或后端聚合入口。选择哪种实现方式，应以服务对象、响应效率、交互复杂度、测试成本和维护成本为依据；不得因为 Code 已有实现而禁止 Web 做更适合 Human-facing 场景的独立实现，也不得因为 Web 已有实现而削弱 Code 面向 AI 和自动验证的确定性职责。Web 与 Code 的实现允许重复读取同一事实源，但不得重复定义权威事实源、对象字段契约、状态机、验收规则或 Human Gate 条件。

## 10. Web 使用场景

Web 使用场景必须由对应规范、产品设计、行动编排或实现文档声明。未声明场景时，AI 应根据本文判断能力是否属于面向人同步、确认、编辑或协同。

当前通用场景如下：

| 场景 | Web 职责 | Code 职责 |
|---|---|---|
| 展示事实实例状态 | 展示、筛选、导航，可直接读取或通过 API 聚合事实实例 | 解析、聚合并为 AI 提供事实实例上下文 |
| 展示校验结果 | 呈现问题、严重级别和修复入口 | 执行确定性校验 |
| Human Gate | 展示确认项并收集人类选择 | 执行已授权写入或验证 |
| Spark 快速创建 | 提供速记表单和创建结果反馈 | 校验并写入 Spark 事实源 |
| 缺口审查 | 展示缺口和关联对象 | 生成缺口诊断 |
| 运行态监控 | 展示同步状态和错误 | 提供可追溯输出 |
| 项目当前事实态势 | 聚合展示 WorkCase、执行项、阻塞、验证、Human Gate 和下一步信号，帮助 Human 看见 AI 正在做什么、将要做什么、需要配合什么 | 提供结构化事实、确定性校验、执行报告、状态回写和可追溯输出 |
| AI 执行态势理解 | 展示 AI 当前依据、风险、阻塞、验证证据和待 Human 决策点 | 提供结构化状态、报告和可追溯输出 |
| LDVH 能力资产 | 只读展示 04.02 定义的 Rules、Skill、Agent、Hook、Code、Web 等能力资产、来源边界、使用场景、降级方式和 Code 检查状态 | 检查 04.02 能力资产定义、必备资产路径、支撑能力误列和 Rules 引用关系 |

Web 不可用时，不得视为事实源缺失或检查通过。AI 应回到 Git 文件事实源、Code 工具和对象规范执行人工或命令行检查。

## 11. Web 文档边界

Web 可以拥有自己的实现文档，但 Web 文档不替代 specs。

Web 文档可以承载：

1. 页面信息架构；
2. API 使用说明；
3. 同步策略；
4. 组件说明；
5. 部署和运行说明；
6. 故障排查；
7. UI 状态和交互设计；
8. Backlog 和产品设计草案。

Web 文档不得承载：

1. LDVH 稳定规范规则；
2. 对象字段契约；
3. 状态机权威定义；
4. Human Gate 权威条件；
5. 事实源最终结论；
6. 与 specs 冲突的行为定义。

Web 实现文档应进入项目文档工作区或项目约定的实现文档位置，并遵守 03 系列文档规范。`web/` 目录优先承载 Web 实现本身；`web/docs/` 只作为实现说明识别，不得替代 specs、docs 正文或工作对象。若 Web 文档中的内容具有长期规范效力，应回写 specs；若形成工作对象事实、决策、任务或经验，应按 20-39 对应事实模型回写到 `ldvh-base/`；若形成事实源修改追溯，应按 `specs/10-Git提交规范.md` 回到 Git commit 记录。

LDVH 在 `web/` 下提供了一套参考实现和 `web/docs/` 下的参考实现文档，不作为权威规范；用户可根据本文约束自行选择实现方式。

Web 文档吸收规则如下：

1. `web/docs/` 可以记录页面结构、组件说明、API 使用、交互草案和实现限制；
2. 涉及 Web 职责边界、写入权限、Human Gate 条件、测试归属、事实源边界、缓存数据库边界或长期页面约束的内容，应吸收到本文或对应正式规范后才具备规范效力；
3. Web AI 可以审计 `web/docs/` 与本文的差异并提出吸收建议，但不得把 `web/docs/` 中的实现描述直接作为修改事实源、扩大权限或定义流程的依据；
4. `web/docs/` 与 specs 冲突时，以 specs 为准，并应记录待吸收、待降级或待删除建议。

## 12. Web 测试与验证要求

Web 变更应根据影响范围执行测试和验证。Code 与 Web 已分属不同构成要素，因此测试也必须按构成要素分区承接；Web 测试不得混入 Code 工具测试目录，Code 工具测试也不得混入 Web 测试目录。对应风险层级的测试或等价验证不通过时，不得提交相关 Web 变更。Web 测试治理、验证声明、测试实现归属和测试证据事实源边界应同时遵守 `specs/11-测试基础规范.md`。

Web 测试目录规则如下：

1. Web 信息同步、Web API、Web 组件、Web 页面、Confirm UI、白名单轻写入体验、文件浏览、diff 展示和 Validate 页面相关测试应放在 `tests/web/` 下；
2. `tests/web/` 可按实现需要继续分为 `api/`、`components/`、`pages/`、`fixtures/` 或等价子目录；
3. Web 测试可以调用 Web 自身的 TypeScript、Node、Playwright、构建检查或等价验证入口，但测试文件和长期测试夹具的归属仍以 `tests/web/` 为准，具体测试入口、命令、夹具组织和页面/API 映射由 `web/docs/` 承载；
4. Web 测试只验证 Web 面向 Human 的读取、呈现、交互、错误态、写入边界和敏感信息边界，不承载 Code 工具测试；
5. 与 Web 测试对应的 npm script、Playwright 配置或测试运行入口可以保留在 `web/` 中，但不得把 `web/` 下的缓存、截图、覆盖率或测试产物提升为稳定事实。

Web 测试至少关注：

1. 页面或组件是否正确展示数据来源；
2. 派生视图是否正确处理同步延迟、错误和空状态；
3. Confirm UI 是否区分确认、取消、暂缓和修改反馈；
4. 白名单外对象和字段是否保持只读；
5. Spark 快速创建是否调用校验和受控写入链路；
6. 缓存或数据库派生视图是否不替代事实源；
7. Web 独立实现事实源读取、对象解析、派生聚合、缓存策略或 API 聚合时，应同步检查其是否仍基于同一 Git 文件事实源、同一 specs 契约和同一对象状态定义。

Web 测试优先级如下：

1. API contract 测试优先于页面测试；
2. 高风险 API 优先覆盖 `POST /api/sparks`、ProjectFiles、Validate 和 Objects；
3. 页面测试优先覆盖 Gate、Validate、ProjectFiles 和 ObjectDetail 的空态、错误态、降级态、只读边界和来源呈现；
4. E2E、视觉回归和复杂浏览器流程后置，不作为当前 Web API contract 测试的前置条件；
5. Web AI 新增或修改高风险 API 时，应同步补齐 `tests/web/api/` 下的最小测试或说明等价验证方式。

Web 测试夹具、Mock 数据、缓存和截图不得成为稳定事实源。

## 13. Web 更新、维护与删除

### 13.1 更新触发条件

以下变更会影响 Web 实现或 Web 文档，AI 必须同步检查 Web：

1. 事实源目录结构变更；
2. 对象字段契约或状态机变更；
3. Human Gate 条件、确认内容或确认流程变更；
4. Code 输出结构变化且 Web 选择消费该输出；
5. Web 直接消费的事实源目录、字段契约、状态定义或同步策略变更；
6. Web 写入白名单、只读字段或写入链路变更；
7. 页面信息架构、API 或后端聚合方式变更。

### 13.2 联动检查内容

Web 相关规格变更后，AI 应检查：

1. `web/` 中是否存在受影响的页面、组件、API 或状态逻辑；
2. Web 是否继续正确展示数据来源、同步时间和错误状态；
3. Web 是否继续基于同一 Git 文件事实源、同一 specs 契约和同一对象状态定义；
4. Web 测试是否需要同步；
5. Web 文档是否需要同步；
6. Rules、Skill 或行动编排是否依赖该 Web 能力。

### 13.3 删除 Web 能力

删除 Web 页面、接口或能力前必须确认：

1. 没有行动编排、Rules、Skill 或用户操作路径继续依赖；
2. 替代入口或命令行降级路径已明确；
3. 对应测试已删除、搬移或改写；
4. Web 文档和引用已同步；
5. 如影响 Human Gate、Web 写入白名单或事实源同步，应触发 Human Gate。

## 14. 规范保障要求

本文通过以下规范保障要求说明相关要求的同步、检查或审计触发条件。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| Human 交互要求 | LDVH 整体以 AI 执行者为第一服务对象；Web 的直接服务对象是 Human，Web 信息架构和交互必须服务人的理解、判断、确认、验收和方向校正需求 | 00 总纲、06 行动编排、07 Code、09 事实源边界、Human Gate | 设计治理 | Web 信息架构、页面优先级、导航、确认入口或白名单写入体验变化时 |
| Human 交互要求 | Web 必须能以事实可追溯方式呈现项目当前态势，使 Human 清楚看见 AI 正在做什么、将要做什么、哪些 WorkCase 或执行项并行推进或等待前置、哪些事项需要 Human 配合或决策 | WorkCase 事实源、Human Gate、Validate、Changelog、Web 对象聚合 API | 信息同步 | Dashboard、ObjectList、ObjectDetail、计划卡片、执行项层级、Human Gate 或验证呈现变化时 |
| Human 交互要求 | Web 展示派生态势时应能表达原因语义和可追溯依据，等待、阻塞、风险、待执行、Human Gate、验证失败和证据缺失等态势不得被泛化为无法判断原因的标签 | Web API 聚合、前端态势映射、i18n、页面文档、图标语义文档、Web 测试 | 信息同步 | 派生态势标签、状态映射、颜色图标、排序、tooltip、文案或聚合依据变化时 |
| 上位约束承接要求 | Web 只能承接 Human-facing 信息同步、确认、验收和白名单内受控轻写入，不得替代事实源或规范正文 | 09 事实源边界、07 Code、事实模型与行动编排规范、Human Gate | Web 治理 | Web 边界、信息同步、缓存数据库或 Web 写入规则变化时 |
| 确定性执行要求 | Web 与 Code 可以各自实现事实源读取、对象解析、状态聚合、缓存和派生视图，但必须基于同一 Git 文件事实源、同一 specs 契约、同一对象字段契约和同一状态定义，不得创建第二事实源或第二规范 | 07 Code、09 事实源边界、对象规范、Web 测试、Code 测试 | 实现承接 | Web 或 Code 新增、修改事实源读取、对象展示、校验展示、聚合统计、状态派生、缓存策略或白名单写入入口时 |
| 确定性执行要求 | Web 可以消费 Code 输出，也可以直接读取事实源；当 Web 消费 Code 输出时，应遵守输出契约，当 Web 独立实现时，应提供等价的来源追溯、错误处理和测试验证 | `specs/07-Code确定性执行实现规范.md`、测试或等价验证、输出契约、Web 实现文档 | 实现承接 | Web 消费 Code 输出、独立实现事实源读取、展示工具诊断或触发受控写入时 |
| Human 交互要求 | Confirm UI 应清楚展示确认对象、影响范围、风险和用户选择，并能承接 06 §6.3.1 的最小证据结构 | Web / Human 入口、Human Gate、受控写入链路 | Human 协同 | Confirm UI、确认流程、白名单写入入口或验收入口变化时 |
| 入口可见要求 | Web 可以只读展示 LDVH 能力资产，帮助 Human 看见 Rules、Skill、Agent、Hook、Code、Web 等能力资产的固定路径、来源边界、降级方式和 Code 检查状态，但不得把该展示写成用户可选配置、环境安装状态或环境完整支持声明 | 04.02、04.03、Rules 入口分层、Code 能力资产检查 | 信息同步 | LDVH 能力资产定义、Rules 入口分层、Dashboard、Validate 或 Web 入口展示变化时 |
| 生命周期触发要求 | Web 页面、API、缓存、`ldvh_doc` 展示边界、写入白名单或 Code 输出消费变化后，应检查 Web 测试和文档是否同步 | Web 测试、Code 回归、文档联动检查 | 触发保障 | Web 页面、API、状态呈现、文档元信息展示、写入白名单或 Code 输出消费变化时 |

具体事实模型或行动编排如需 Web 能力，应在对应主规范中说明 Web 适配边界、字段契约、验证入口和降级方式。

## 15. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变本文定义的 Web 信息同步职责分工；
2. 改变 `web/`、`web/docs/`、缓存或数据库的目录定位、事实源性质或同步分工；
3. 新增、扩大、删除或改变 §8.2 Web 写入白名单；
4. Web 改变事实源归属；
5. Web 将派生数据、缓存、数据库视图或 UI 状态提升为稳定事实；
6. Web 绕过 Rules、对象状态机、写入校验、行动编排或 Human Gate；
7. Web 引入持久化数据库作为派生层并影响事实源读取、信息同步或写入链路；
8. 删除被行动编排、Human Gate 或白名单写入依赖的 Web 能力。

Web 一致性检查至少包括：

| 检查项 | 标准 |
|---|---|
| 服务对象分工 | LDVH 整体仍以 AI 执行者为第一服务对象；Web 设计明确服务 Human 的理解、判断、确认、验收和方向校正 |
| Web 边界 | Web 只承载信息同步、派生视图、Confirm UI 和白名单内受控轻写入 |
| 事实源边界 | 页面状态、缓存、数据库和 UI 展示未替代 Git 文件事实源 |
| Code / Web 同源协作 | Web 与 Code 均基于同一 Git 文件事实源和同一 specs 契约；允许各自实现读取、解析、聚合和校验；未创建第二事实源、第二字段契约、第二状态机或第二验收规则 |
| 数据来源 | 派生视图标注数据来源、同步时间或可追溯依据 |
| 派生态势原因语义 | 等待、阻塞、风险、待执行、Human Gate、验证失败和证据缺失等态势能说明原因；同一事实源状态在原因不同时未被泛化为单一标签 |
| 过程输出展示 | 过程输出已区分临时、候选、已回写、验证失败、降级和待 Human Gate 状态 |
| Web 写入白名单 | 当前仅 Spark 快速创建可写入；白名单外对象和字段保持只读；写入目标、字段校验、写入前校验和写入后验证已识别 |
| Human Gate | UI 明确确认对象、影响范围、风险和用户选择，并能形成或导出 06 §6.3.1 所需的最小证据 |
| Code 协作 | Web 选择消费 Code 输出或触发受控写入时遵守输出契约、写入校验和事实源边界；Web 独立实现时具备来源追溯、错误处理和测试验证 |
| AI 协作边界 | Web 未直接调用 AI、Skill 或 Agent |
| Web 文档 | Web 文档未替代 specs、事实实例或对象契约 |
