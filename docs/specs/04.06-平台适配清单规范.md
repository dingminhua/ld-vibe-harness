> 创建日期：2026-06-09

## 1. 本文解决的问题

本文定义平台适配清单机制。

平台适配清单不是平台能力说明书，也不是平台官方文档摘要。它的主轴是 LDVH 对 AI 执行者提出的支持要求和正式规范提出的落地要求；平台只是在每项要求下回答“在这个平台上用什么方法承接、证据是什么、不能完整承接时如何降级”。

本文当前不处理网页端、云端托管形态或移动端形态。上述形态不得通过本文的降级项被默认为已承接，后续若需要纳入，应先经 Human Gate 判断是否新增独立平台清单或专项规范。

普通用户或新平台适配者只需要先做一件事：按本文创建当前平台的“平台适配清单”。清单可以先不完整，不要求一次证明完整支持。42 会按清单中已有证据执行只读检查、授权落地、复检，并指出 blocked、degraded 或可补齐项。

LDVH 的安装接入、LDVH落地与检查和环境适配不直接绑定某个 AI 开发平台，而是读取当前平台适配清单中的要求响应矩阵。当前已有 Trae Solo 和 Codex 清单；其他平台不预设完整支持。

平台能力如 Rules、Skill、Agent、Command、MCP、Hook、CI、Code、命令或本地预览只是承接方法候选，不是清单主轴。清单不得因为某个平台有某项能力，就反向改变 LDVH 的要求。

平台适配清单记录平台承接方法、平台实体映射规则、证据来源、降级方式和待补齐事项，不记录某个用户当前环境的实际状态，也不记录清单成熟度状态。实际文件、入口、权限、工具或运行投影是否存在，应由 42 LDVH落地与检查现场检查。

## 2. 清单不维护状态

平台适配清单不得声明顶层支持状态、成熟度状态或逐项状态。清单只记录稳定的要求响应内容：平台如何承接、证据来自哪里、无法完整承接时如何降级、还有哪些 open items。清单元数据可以登记 `verification_scope`，用于说明资料整理、refs 证据或真实环境实测的覆盖范围；该字段不是通过状态，也不得替代 42 现场结论。

42 LDVH落地与检查读取清单后，在当前报告中派生 done、todo、needs_human_gate、degraded、blocked、out-of-scope、pass 或 pass-with-warnings 等结论。这些结论属于本次过程报告，不得回写为平台清单状态。需要长期保留的稳定事实，应按内容性质分流到平台清单 open_items、Task、Memo、ADR、Pitfall、正式规范、Code 或其他 Git 文件事实源。

没有真实平台上下文、维护者、证据和检查结论的平台，不得声明完整支持；只能保留待填写或待验证的要求响应内容，并由 42 在现场说明缺口和降级路径。

## 3. 清单事实源边界

平台适配清单应写入 `docs/specs/04.xx` 正式规范区，作为平台适配规则和待办清单的稳定事实源。

| 内容 | 权威位置 |
|---|---|
| 平台适配清单字段规则 | 本文 |
| Trae Solo 当前适配清单 | `docs/specs/04.07-Trae-Solo适配清单.md` |
| Codex 当前适配清单 | `docs/specs/04.08-Codex适配清单.md` |
| 其他平台待填要求 | 本文或后续对应平台清单 |
| LDVH落地与检查过程结果 | 当前对话或调用结果中的 42 落地与检查报告；具体状态文档边界按本文 §2 执行 |
| 需要长期保留的检查结论 | Task、Memo、ADR、Pitfall、正式规范、平台清单 open_items 或对应 Git 文件事实源 |
| 实际运行投影入口 | LDVH-AI-ENTRY.md、平台规则、平台 Skill、平台 Agent、Hook、CI、命令或本地预览 |
| LDVH落地与检查执行规则 | `docs/specs/42-ldvh-landing-check-LDVH落地与检查.md` |

清单不得复制平台官方文档全文，不得把聊天判断当作平台事实，不得把尚未验证的能力写成完整支持结论，不得替代 42 LDVH落地与检查的现场判断。

## 6. 平台实体映射规则

平台实体映射规则用于回答：某个平台的 Rules 在哪里、Skill 在哪里、Agent 在哪里、Hook 在哪里、Command 在哪里、入口文件在哪里、哪些实体禁止项目级创建、哪些只能薄引用、哪些能力只能降级。

平台实体映射规则借鉴 ECC target adapter 的分层思想：每个平台知道自己的实体在哪里、如何访问、有什么约束。但 LDVH 不创建安装器、不保存安装状态、不把平台名称硬编码为 42 的通过依据。

### 6.1 实体映射维度

每个平台清单必须声明以下实体映射维度。维度声明的是路径、规则和约束，不是安装状态或当前环境观察结果。

| 映射维度 | 平台需要声明的内容 |
|---|---|
| Rules / Instructions | 用户级规则路径、项目级规则路径、是否允许项目级创建、是否支持压缩规则 |
| Skill | Skill 存储路径、命名规则、是否支持项目级 Skill、Skill 进入方式 |
| Agent | Agent 存储路径、调度方式、是否支持子 Agent、并行 Agent 限制 |
| Hook / Command | Hook / Command 存储路径、触发方式、是否允许项目级 Hook |
| 入口文件 | AI 入口文件路径、是否只做薄引用、薄引用目标路径 |
| MCP / 工具连接 | MCP 配置路径、可用工具列表、工具权限边界 |
| CI / 自动化 | CI 配置路径、触发方式、可用检查类型 |
| Web / 预览 | Web 预览方式、本地预览能力 |

### 6.2 映射约束规则

1. 禁止项目级创建的实体必须在映射中标注 `project_level: forbidden`，并说明原因；
2. 只允许薄引用的实体必须标注 `thin_ref_only: true`，并说明引用目标路径和引用内容约束；
3. 只能降级的能力必须标注 `degraded_only: true`，并说明降级方式和残留风险；
4. 映射规则不保存安装状态、初始化状态或环境观察状态；这些只能由 42 现场读取为当前检查结果；
5. 映射规则不替代 42 的现场检查；映射声明的是路径和规则，实际是否存在由 42 验证；
6. 映射规则不得因为某个平台缺少某项能力而反向改变 LDVH 的要求；
7. 同一维度在不同平台上的映射可以不同，但必须能追溯到同一项 LDVH 要求。

### 6.3 映射与要求响应矩阵的关系

平台实体映射规则是要求响应矩阵的前置规则。要求响应矩阵中的 `platform_entities` 字段应按本节映射维度声明，确保每项承接方法都能定位到具体的平台实体路径和约束。

42 读取平台清单时，应先读取平台实体映射规则，再按映射规则定位要求响应矩阵中声明的具体实体。

## 7. 要求响应矩阵字段

每个平台适配清单必须以“要求响应矩阵”为主体。每一行至少包含以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| requirement_id | 是 | 采用 AI-S1 至 AI-S15 或 LR-1 至 LR-7 |
| requirement_name | 是 | 要求名称 |
| requirement_source | 是 | 来源规范和章节 |
| platform_method | 是 | 该平台用什么具体方法承接该要求 |
| platform_entities | 是 | 按 §6 平台实体映射规则声明具体机制、文件、命令、规则、Skill、Agent、MCP、Code 或人工流程 |
| refs_evidence | 是 | 平台 refs、官方资料、现有文件或实测证据 |
| degradation | 是 | 无法完整承接时的降级方式和残留风险 |
| check_evidence | 是 | 42 LDVH落地与检查时应检查的证据 |
| open_items | 是 | 后续要补齐的事项 |

平台能力索引可以作为辅助章节存在，但不得替代要求响应矩阵。

Markdown 清单可以使用中文表头，但必须能等价映射到上述字段：`要求 ID` 对应 `requirement_id`，`要求名称` 对应 `requirement_name`，章节标题或清单说明对应 `requirement_source`，`平台承接方法` 对应 `platform_method`，`平台实体` 对应 `platform_entities`，`refs 依据` 对应 `refs_evidence`，`降级方式` 对应 `degradation`，`42 检查证据` 对应 `check_evidence`，`Open Items` 对应 `open_items`。若使用中文表头且未设置独立来源列，必须在清单章节或行内确保来源可追溯。

## 8. 42 使用清单的规则

42 LDVH落地与检查必须围绕当前平台适配清单中的要求响应矩阵执行和验证，而不是围绕某个平台名称或平台能力清单硬编码执行。

AI 应按以下顺序处理：

1. 确认当前平台；
2. 定位对应平台适配清单；
3. 读取 §6 平台实体映射规则，了解该平台的实体路径、约束和降级标注；
4. 读取 AI-S1 至 AI-S15 和 LR-1 至 LR-7 的要求响应矩阵；
5. 判断本次LDVH落地与检查依赖哪些要求；
6. 对每项依赖要求读取 platform_method、platform_entities（按 §6 映射规则定位）、refs_evidence、degradation、check_evidence 和 open_items；
7. 若关键要求只有降级承接或缺少现场证据，42 只能按降级路径执行并记录残留风险；
8. 若关键要求缺失、证据缺失或 open_items 仍阻断当前目标，不得宣称完整 LDVH落地与检查通过；
9. Trae Solo 和 Codex 清单是当前已存在的要求响应清单，但 42 不得把任一平台名写成唯一执行逻辑。

---
## 9. 42 检查清单的规则

42 LDVH落地与检查必须检查当前平台适配清单中的要求响应矩阵，以及矩阵声明与实际环境、运行投影和本次 42 落地与检查报告之间的一致性。

LDVH落地与检查至少应检查：

1. 当前平台是否有清单；
2. 平台实体映射规则（§6）是否声明所有映射维度；
3. 映射约束标注（project_level: forbidden、thin_ref_only、degraded_only）是否与实际平台能力一致；
4. AI-S1 至 AI-S15 和 LR-1 至 LR-7 是否被逐项响应；
5. 每项响应是否说明 platform_method、platform_entities（按 §6 映射规则定位）、refs_evidence、degradation、check_evidence 和 open_items；
6. check_evidence 是否存在且可追溯；
7. 降级项是否在 42 落地与检查报告中被正确说明；
8. 清单是否把未经验证的承接方法写成完整支持结论；
9. 清单是否有阻断本次目标的缺失字段、缺失证据或未处理 open_items。

没有完整清单或没有证据的平台，42 只能输出 blocked、degraded 或 out-of-scope，不得输出全链路 pass。

## 11. 规范落地要求

## 12. Human Gate 与检查要求

以下情况必须触发 Human Gate：

1. 将任一平台声明为完整支持或作为完整通过依据；
2. 将未经 42 检查的要求响应矩阵作为完整落地依据；
3. 删除、重命名或改变 Trae Solo、Codex 等既有平台清单职责；
4. 把某个平台能力提升为 LDVH 全局唯一底座；
5. 允许缺少 check_evidence 的平台通过 42；
6. 改变本文字段或 42 依赖要求响应矩阵的规则。

检查平台适配清单时，应确认：

1. 要求响应矩阵覆盖 AI-S1 至 AI-S15 和 LR-1 至 LR-7；
2. 平台实体映射规则（§6）声明了所有映射维度，约束标注与实际平台能力一致；
3. 承接方法、证据、降级方式和 open_items 相互匹配；
4. 未把平台官方文档、聊天判断或工具缓存当成最终事实；
5. degradation、check_evidence 和 open_items 没有被隐藏；
6. Trae Solo 和 Codex 是当前已有清单实例，不是写死在 42 中的平台逻辑。
