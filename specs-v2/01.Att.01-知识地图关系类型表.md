## 1. 定位

本文承载知识地图关系类型清单。01 正文定义知识地图的治理原则、回指要求和事实源边界；本文只定义可被 Code、Web、运行时扩展和 AI 读取的关系类型表。

知识地图关系只用于定位、最小读取、影响判断、诊断回指和派生展示。关系边不得替代规范正文、附件授权、成员主文件、Code 校验原始结果或 Git 文件事实源。

## 2. 关系类型表

| 边类型 | 方向 | 来源结构 | A 端允许主体 | B 端允许客体 | 含义 | 禁止误用 |
|---|---|---|---|---|---|---|
| `basis` | A -> B | `basis` | 规范、附件、成员规范 | 上位规范或授权父规范 | A 直接承接 B 的上位原则、权威边界或基础契约 | 不得把导航入口、主题相关或被频繁引用对象写成上位依据 |
| `related` | A -> B | `related_specs`、正文强依赖引用 | 规范、附件、成员规范 | 规范、附件、成员规范 | A 定义自身边界、消费字段、同步要求或检查要求时需要读取 B | 不得因为 B 引用了 A、主题相近或为了可发现性而反向补写 |
| `parent` | A -> B | `parent_spec` / `relation` | 附件、成员规范、专题成员 | 授权父规范或所属主规范 | A 从属于 B，且 A 的边界由 B 授权或约束 | 不得把普通相关规范、迁移来源或目录相邻关系写成父子关系 |
| `derives_from` | A -> B | `migration_sources`、派生输出声明 | 写作区规范、附件、Code 派生输出、知识地图节点 | active 规范、来源规范、事实源、成员主文件 | A 从 B 迁入、吸收、解析或派生 | 不得把来源关系升级为 active 权威或执行依据 |
| `consumes` | A -> B | `code_consumption`、正文消费声明、保障要求表 | Code、Web、运行时扩展、知识地图、规范、行动编排 | 规范结构、字段、事实源、附件、成员自描述 | A 读取或消费 B 的结构、字段、状态或输出 | 不得把消费关系写成 B 对 A 的同步义务 |
| `validates` | A -> B | Code 检查声明、测试声明、保障要求表 | Code、测试、CI、人工降级检查、行动编排 | 规范、事实源、字段、附件、资产承载物 | A 对 B 执行校验、检查、验证或回归判断 | 不得把一次检查输出替代 B 的权威事实源 |
| `renders` | A -> B | Web/知识地图展示声明 | Web、知识地图、报告、派生视图 | 规范、事实源、字段、状态、证据 | A 展示 B 的派生视图或 Human-facing 状态 | 不得把展示状态升级为最终事实源 |
| `writes_to` | A -> B | 受控写入声明、事实源回写声明、行动编排回写规则 | Code、行动编排、受控 Web 写入、AI 执行过程 | Git 文件事实源、规范、事实模型实例、Git 提交记录 | A 在授权条件下把稳定事实写入 B | 不得把工具输出、缓存、页面状态或聊天过程视为已回写 |
| `owns_attachment` | A -> B | 父规范正文附件授权、附件 `parent_spec` | 主规范 | 附件 | A 授权 B 承载注册表、矩阵、模板、示例或长清单 | 不得让附件承载父规范未授权的核心原则、状态机、事实源边界或流程 Gate |
| `gated_by` | A -> B | Human Gate 章节、保障要求表、行动编排 Gate | 规范变更、行动、写入、迁移、适配措施 | Human Gate、授权要求、暂停条件 | A 受 B 的暂停、确认、授权或验收约束 | 不得用普通确认或工具成功结果替代 Human Gate |
| `impacts` | A -> B | 影响分析、同步触发、Code 诊断 | 规范、附件、字段、资产、Code、Web、运行时扩展 | 受影响规范、附件、字段、资产、检查或展示 | A 变化可能影响 B，需要检查或同步 | 不得把影响关系写成上位依据、父子关系或执行责任转移 |

## 3. 关系判定顺序

AI 或 Code 生成关系边时，应按以下顺序判断：

1. 先判断是否存在父规范授权；存在时使用 `parent` 或 `owns_attachment`；
2. 再判断是否存在上位原则承接；存在时使用 `basis`；
3. 再判断是否存在真实读取、同步、字段或检查依赖；存在时使用 `related`；
4. 再判断是否只是迁移、吸收、解析或派生来源；存在时使用 `derives_from`；
5. 再判断是否是消费、校验、展示或写入行为；分别使用 `consumes`、`validates`、`renders`、`writes_to`；
6. 再判断是否存在 Human Gate、授权或暂停条件；使用 `gated_by`；
7. 只需要影响面提示但不构成以上关系时，使用 `impacts`。

同一对节点可以存在多条不同类型关系，但每条关系必须能回指具体字段、章节、表格行、Code 输出或事实源路径。

## 4. 禁止升级规则

以下关系升级被禁止：

1. 不得把 `related` 升级为 `basis`；
2. 不得把 `derives_from` 升级为 active 事实源；
3. 不得把 `consumes` 升级为被消费方对消费方的同步义务；
4. 不得把 `renders` 升级为最终事实源；
5. 不得把 `validates` 的一次输出升级为长期状态；
6. 不得把 `impacts` 升级为父子关系或执行责任；
7. 不得把路径同目录、编号相邻或主题相近写成强关系。

## 5. Code 消费要求

Code 解析关系类型时，至少应保留：

| 字段 | 含义 |
|---|---|
| `edge_type` | 本文定义的关系类型 |
| `source_node` | A 端节点 ID、路径或锚点 |
| `target_node` | B 端节点 ID、路径或锚点 |
| `source_path` | 关系来源文件 |
| `source_anchor` | 关系来源章节、字段或表格行 |
| `direction` | 固定为 A -> B |
| `parse_status` | parsed、partial、missing_target、invalid_direction 或 equivalent |
| `diagnostics` | 关系缺失、目标不存在、方向错误、升级误用或反向补全诊断 |

Code 输出只作为派生索引、诊断和最小读取建议，不替代关系来源文件。

## 6. Human Gate

以下情况应评估 Human Gate：

1. 新增、删除或重命名关系类型；
2. 改变任一关系类型的方向、来源结构或禁止误用；
3. 允许知识地图关系替代规范正文、附件授权、成员主文件或 Git 文件事实源；
4. 将派生关系边写回为 active 规范事实。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备关系影响范围、误用风险和待确认事项，但不得把关系检查结果替代 Human Gate。

## 7. AI 检查要求

检查至少包括：

| 检查项 | 标准 |
|---|---|
| 类型闭集 | 关系类型属于本文定义范围 |
| 方向一致 | 关系方向符合本文表格 |
| 来源可回指 | 每条边能回指字段、章节、表格行、Code 输出或事实源路径 |
| 目标存在 | 目标节点、路径或锚点真实存在，或被诊断为缺失 |
| 未误升级 | 未把导航、来源、展示、影响或消费关系升级为上位依据、父子关系或事实源 |

AI 检查要求用于发现关系方向错误、目标缺失、误升级和反向补全风险；检查结论不能替代 Human 对关系类型变更的确认。
