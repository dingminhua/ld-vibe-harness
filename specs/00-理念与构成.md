## 1. LDVH 为什么存在

Vibe Coding 使 Human 能够用自然语言表达目标，由 AI 理解意图、推理方案并生成实现，门槛低、反馈快、产出多。但 AI 生成代码的本质不是确定性编译，而是基于开发环境上下文、模型训练经验和参数形成的概率性推理，因此天然存在上下文依赖、概率性输出和无状态等问题。

Vibe Coding 能够较好地完成单个功能、局部修复，也能在明确的测试目标和验收反馈下承担较长时间的连续工作。但真实开发不是单点工作的叠加，它往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是项目在持续演进中，如何避免从“开始还不错”逐渐变成“难以继续做”的问题。概括如下：

设计理念：

1. 以 AI 执行者为第一服务对象；
2. 以 LDVH Helper CLI 为基础服务形式；
3. 以事实源为信息锚点；
4. 以规范模型、事实模型、行动模板、Code 和 Web 为构成要素；
5. 以 V1-V8 价值标准为行动标尺。

构成要素：

1. 用规范模型组织规范及其规则和边界；
2. 用事实模型组织事实、状态、证据和经验；
3. 用行动模板沉淀可复用行动结构；
4. 用 Code 提供确定性解析、校验、受控操作和反馈；
5. 用 Web 桥接 Human 与 AI，呈现状态、风险和证据。

最终目标：

1. 让 AI、Human、Code 可以各展所长，使 Vibe Coding 推理更稳定、结果更可控、产出更高效；
2. 进而让环境、模型、使用者可以自由组合，使 Vibe Coding 使用更方便、选择更丰富、协同更顺畅。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于经验沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

AI 执行者（AI Agent）是承担当前事项的理解、判断、行动和结果交付责任，并消费 LDVH 信息与能力服务的 AI 角色。模型文件、被调用工具或单次 AI 输出本身不是本文所称的 AI 执行者。

LDVH 以 AI 执行者为第一服务对象。要说明这一点，需要先理解 AI 执行者的依赖、能力与本质。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——缺少可用工具或环境能力时，AI 容易停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的工具或环境能力，并把反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

这些依赖、能力与本质共同决定了 LDVH 的支撑方向：为 AI 提供可消费、可验证、可接续的稳定依据与协作条件，使其能够充分发挥自身能力，让长期项目中的判断有据、行动可续、结果可验。本文定义的 V1-V8 价值标准，将这些依赖、能力与本质形成的支撑需求，归纳为 AI 在长期项目中需要获得的八类价值。

## 3. 以 LDVH Helper CLI 为基础服务形式

LDVH 以 Helper CLI 为基础服务形式。AI 可以直接调用，环境 Hook、插件和 adapter 也可以在相应生命周期中调用同一服务能力，并将结果交给 AI。

Helper CLI 围绕当前任务和工作对象提供服务，帮助 AI 定位事实与规则、了解当前状态、调用 LDVH 已有能力、识别当前行动适用的要求，并明确结果如何验证、回写和接续。

Helper CLI 的服务范围与具体规则的适用范围分属不同层次。Helper CLI 的服务范围由负责定义 Helper 服务契约、工作对象管辖判定和管辖范围解析规则的规范确定；具体规则的适用范围和效力由相应规则的来源规范决定。当前事项命中具体规则时，AI 必须执行该规则规定的要求；未命中具体规则时，Helper CLI 仍可提供信息和能力服务，AI 的普通求解路径保持自主。

Helper CLI 的具体命令、响应格式、环境衔接和实现方式，由承担相应职责的后续规范承接；本文只定义其基础服务形式、作用和边界。

Helper CLI 的实现层与架构层必须区分：

```text
规范模型、事实模型、行动模板、Code → Helper → AI
Code → 实现 Helper CLI
Web → Human
```

实现层上，Helper CLI 的程序、命令、解析、校验和受控操作由 Code 实现；架构层上，Helper 是面向 AI 的统一跨要素服务入口，组织并消费当前事项适用的规范模型、事实模型、行动模板和 Code 能力。因此，Helper 不是第六类构成要素，也不能被缩减为 Code 的一个普通能力。

## 4. 以事实源为信息锚点

LDVH 以事实源为信息锚点，并提出两项要求：

1. 有 Git，可溯源。事实源以 Git 可追踪文件为唯一有效承载形态，稳定事实的形成、修改、验证和关闭都能回到明确的 Git 文件位置和 Git 溯源记录；聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图等只有回写到 Git 文件事实源并完成验证后，才可能成为稳定事实。

2. 有组织，可消费。事实源不是材料堆积，而是要形成清晰的事实组织：事实放在哪里，边界是什么，引用关系如何建立，状态如何变化，结果回写到哪里。组织清晰的事实源才能被 Code 消费，进而放大事实源的价值——让 AI 少读、少猜、少漂移，让验证、回写和接续有稳定入口，而不只是人能看懂的材料。

上述两项要求共同构成本文所称的事实源边界：符合两项要求，才是 LDVH 认可的事实源；不符合的，不得作为稳定事实的承载位置。后续本文中“事实源边界”均指这两项要求。

事实源承载管辖项目中需要稳定保留的事实、状态、证据、决策和经验，为 AI 理解项目现状、追溯既有依据、回写验证结果和接续后续工作提供稳定位置。

事实模型、Code 和 Web 可以承接、消费、展示或辅助回写事实，但不得替代事实源整体。具体事实源类型、证据规则、回写规则、吸收规则、Code 消费规则和 Git 溯源等规则，由后续相关规范承接；本文只定义上位原则。

## 5. 以规范模型、事实模型、行动模板、Code 和 Web 为构成要素

LDVH 以规范模型、事实模型、行动模板、Code 和 Web 为构成要素。这五类构成要素把规则、事实、行动、确定性反馈和面向 Human 的呈现分开归口，形成 AI 可定位、可行动、可验证、可交还的结构。

LDVH 的五类构成要素包括：

1. 规范模型（Specification Model）。定义 LDVH 正式规范文档（Specs）及其授权附件的类型、身份、结构、关系和规则表达方式，使规范及其规则、边界和价值标准能够以 Code 可消费的 Markdown 组织。正式 Specs 及其授权附件是受规范模型约束的规范资产；其中取得正式效力的正文与授权附件共同构成 LDVH 规则源。规范模型用于组织规则源，不单独形成第二规则源。规则源为 AI 以及包括 Helper CLI 在内的 Code 能力提供可定位、可解析、可引用的规则依据，使 AI 能据此理解目标边界、识别适用场景并判断行动约束；
2. 事实模型。在事实源边界内组织需要对象化、状态化或证据化管理的事实，使结论、状态、证据和经验能够在事实源中稳定记录、关联、更新和消费；
3. 行动模板。沉淀重复场景中的可复用行动结构，明确适用条件、关键步骤、验证入口和交还方式，使 AI 在命中相应场景时能够稳定行动；
4. Code。提供解析、索引、聚合、校验、测试、上下文压缩和受控写入等确定性能力与反馈，并以 Helper CLI 作为面向 AI 执行者的基础服务形式，降低 AI 的读取、判断和验证成本。Code 不得自行补充或重新解释来源规则的含义，也不得以确定性处理结果替代仍需由 AI 完成的语义判断；凡判断依赖 Code 的实际执行结果，AI 必须以相应调用、回读或验证结果为依据，不得编造执行结果，也不得将推测表述为实际结果；
5. Web。从事实源独立读取并呈现状态、风险、证据、待确认事项和验收信息，帮助 Human 理解项目情况、进行方向校正与决策。

五类构成要素用于确定 LDVH 内容的职责归口，不形成上下层级，也不直接决定具体实践是否准入。规则、对象、字段、附件、工具、Code 输出、Web 展示和派生机制等构成要素实践纳入 LDVH 前，必须归属于规范模型、事实模型、行动模板、Code 或 Web，并接受 V1-V8 价值判断；涉及稳定事实承载时，其承载位置还必须符合事实源边界。

LDVH 规范模型中的文档类型、共同结构、职责标识符、规范依据、结构归属、附件授权、替代关系、其它正文引用的效力边界和解析入口，由承担规范模型定义职责的规范统一定义；Code 根据这些关系生成导航、索引或汇总时，不得形成新的规范关系或规则权威。该规范应区分本文采用的根规范结构与下位正式规范采用的普通规范结构，但不得改变或重新解释本文的上位定义。本文只授权该职责，不绑定承担该职责的具体编号或文件。

## 6. 以 V1-V8 价值标准为行动标尺

LDVH 以 V1-V8 价值标准（V1-V8 Value Criteria）为行动标尺。五类构成要素及其具体实践，都必须帮助 AI 获得以下一种或多种价值。

V1-V8 分别从定位、理解、边界、推进、判断、接续、沟通和积累八个方面衡量 LDVH 为 AI 提供的价值。每项实践按照自身职责服务其中一项或多项价值；新增机制只有在为 AI 带来可辨认的净收益时，才具备纳入 LDVH 的价值基础。

本文所称“V1-V8 价值标准”，是表格列出的八项价值维度；“V1-V8 价值判断”是依据这些标准判断构成要素及其具体实践能否为 AI 带来相应价值；“行动标尺”表示这些标准对 LDVH 构成要素及其具体实践的设计、纳入和使用发挥指导作用；AI 的普通求解路径仍按照本文定义的 Helper CLI 作用边界保持自主。表格中的“不满足时的表现”用于识别相应负担和风险。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | 能否帮助 AI 根据当前目标和工作对象，快速定位相关且来源明确的规则、事实和状态，以及可用能力的入口 | 信息存在但 AI 找不到；盲目搜索或全文读取；误用来源；遗漏关键规则、事实、状态或能力入口 |
| V2 | 充分理解 | 能否帮助 AI 将当前相关的目标、工作对象、规则、事实、状态、依赖关系和验收要求联系起来，形成充分、连贯且不过载的整体理解 | AI 找到了相关信息，但仍无法形成整体理解；关系、冲突或关键上下文被遗漏；上下文不足或过载造成误解 |
| V3 | 边界识别 | 能否帮助 AI 依据来源明确且可回指的规则、事实和当前状态，识别当前事项适用哪些要求、什么必须遵守、什么可以自主决定、什么情况必须暂停、暂停影响什么，以及哪些决定应交由 Human | AI 已理解当前事项，但仍发生规则适用误判、要求遗漏、作用外溢、越权推进、应停未停或错误恢复 |
| V4 | 稳定推进 | 能否帮助 AI 在 LDVH 已明确支持的场景中，复用适用的行动结构、调用可用能力，并及时获得能够支持后续调整或分流的确定性反馈 | AI 已明确目标和边界，但仍反复重建已有处理方式、遗漏关键要求、无效试错，或在缺少反馈时发生执行漂移 |
| V5 | 据实判断 | 能否帮助 AI 对受 LDVH 规则约束或者需要由项目事实和当次可观察依据支持的重要判断形成可回指依据，并使关于状态变化、能力状态、环境接入和完成情况的结论与声明，保持在相关事实、验证结果或当次可观察依据实际支持的范围内，并清楚区分已证实范围、未证实范围和残留风险 | AI 将事实与推测混淆；以自述、工具成功、局部结果或静态存在代替范围匹配的依据；判断或声明超出实际证据范围 |
| V6 | 工作接续 | 能否帮助 AI 把当前项目后续工作需要的事实、状态、证据和决策稳定保留下来，使不同会话、执行者和阶段都能恢复这些信息、追溯其来源和变化并接续工作 | 当次工作已有可信结果，但后续执行者无法恢复依据、状态和决定，只能重复调查、重建状态或中断接续 |
| V7 | 清晰沟通 | 能否帮助 AI 在需要 Human 判断、授权、确认或验收时，清楚交还当前状态、依据、影响、风险和待决定事项，使 Human 的回应能够明确待决定对象的处理结论、作用范围和后续方向，并使 AI 能够据此继续、调整或保持暂停 | AI 已识别需要 Human 参与，但交还内容仍然含混；Human 无法明确回应，或 AI 无法确定回应约束的对象、范围和后续行动 |
| V8 | 持续积累 | 能否帮助 AI 在后续事项中复用当前工作形成的经验，并继续处理已经发现的反复问题以及规则或能力缺口 | 当前项目可以接续，但相似事项仍然重复分析和试错；同类问题反复发生；已经发现的经验和体系缺口长期悬置 |

## 7. 验证要求

验证要求用于判断本文定义的上位原则是否在具体变更、机制和声明中成立。验证结论只覆盖当次检查的对象、环境和范围；未检查、不可观察或缺少依据的部分仍属于未验证范围。

Human 作出的判断、授权、方向选择、风险接受或验收决定及其记录，只能证明相应决定及其作用范围；技术状态、能力可用性、环境接入和完成范围仍须由对应事实、实际调用、测试、环境触发或回读结果证明。只有来源规则明确将 Human 验收本身作为成立条件时，验收记录才可证明对应验收对象成立，并且不得扩张到技术状态或未验证范围。Human Gate 只承接必须由 Human 作出的判断和决定，不作为技术验证入口。

表中列出的验证入口只在相应能力实际可用、需要环境接入时已完成接入，并且能够产生当次可观察结果时成立；入口名称或静态存在不构成验证。

本文所称“环境 integrated”沿用承担环境接入判定职责的规范所定义的当次判定，不表示长期状态；能力可用、状态成立和工作完成分别由对应来源规范及当次验证范围判断，本文不另行建立状态闭集。

## 8. Human Gate

Human Gate 用于将上位判断和决定保留给 Human，包括授权、方向选择、风险接受和验收。Human Gate 触发后，受其影响的行动、对象或声明必须优先暂停；未受影响的工作可以在来源规则和作用范围清楚时继续。

### 8.1 触发条件

以下事项只能由 Human 决定：

1. 改变 LDVH 的存在理由、核心问题或最终目标；
2. 改变 AI 执行者作为第一服务对象的定位，或者改变 Human、AI 和 Code 的基本职责关系；
3. 改变 Helper CLI 的基础服务形式，或者改变“命中具体规则时落实规则要求、未命中具体规则时保持普通求解路径自主”的作用边界；
4. 改变事实源作为信息锚点的定位、事实源边界，或者将事实源改为构成要素；
5. 新增、删除、改名或重排规范模型、事实模型、行动模板、Code 和 Web 五类构成要素；
6. 改变 V1-V8 的数量、名称、判断问题、价值边界或净价值成立原则；
7. 改变本文对规范模型定义职责的授权范围，或者改变根规范结构与普通规范结构的基本关系；
8. 改变本文验证要求、Human Gate 或 Stop Conditions 的上位语义；
9. 改变本文对下位规范、附件、事实对象、Code、Web、工具输出和环境入口的效力约束，即其不得重新解释、覆盖或弱化本文的上位定义；
10. 决定是否接受来源规则要求交由 Human 处理的重大取舍，或者是否在明确未验证范围和残留风险后继续。

不改变规则含义的错别字修正、格式调整、措辞澄清和等义表达优化，不单独触发 Human Gate。无法确认修改是否改变上位语义时，应当先暂停受影响的修改并交由 Human 判断。

### 8.2 交还要求

进入 Human Gate 时，AI 应当向 Human 清楚交还：

1. 待决定的对象和问题；
2. 触发 Human Gate 的来源规则；
3. 当前事实、验证依据和未验证范围；
4. 受影响的行动、对象和声明；
5. 可选处理方式及各自影响；
6. 已知风险和残留风险；
7. Human 回应后可以继续、调整、分流或保持暂停的范围。

### 8.3 Human 回应与效力边界

Human 回应应明确待决定对象的处理结论、作用范围和后续方向。无法判断 Human 回应约束哪些对象或行动时，受影响范围继续保持暂停，并请求补充确认。

Human Gate 只能完成 Human 判断、授权、方向校正、风险接受或验收决定，不能把未验证内容转化为已验证，也不能替代事实源、测试结果、环境触发依据或完成声明所需的验证。

AI 可以准备事实、影响范围、风险、选项和建议，但不得替代 Human 作出决定；Code、tests、Hook、Helper 响应、工具成功输出和 Web 展示结果，也不得替代 Human 作出 Human Gate 所保留的决定。

## 9. Stop Conditions

Stop Conditions 用于在继续推进将违反已经生效的规则、背离稳定事实、超出验证依据或越过 Human 决定边界时，优先暂停受影响范围。停止效力只作用于来源规则定义的停止条件所命中的行动、对象或声明；未命中具体停止条件的普通求解路径保持自主。

### 9.1 停止条件

出现以下任一情况时，AI 必须暂停受影响的行动、对象或声明：

1. 已经触发 Human Gate，但尚未取得对象、作用范围和后续方向清楚的 Human 回应；
2. 已经发现与当前行动、对象或声明相关的具体来源规则，但无法确认其适用条件、效力，或者无法判断多条规则之间的权威关系，继续推进可能违反其中的强制要求；
3. 具体规则已经适用，但其要求的行动、受控入口、验证或回写无法满足，并且来源规则没有提供可以继续的分流方式；
4. 准备创建、修改或回写正式事实对象或事实源，但无法满足适用的事实模型、字段、状态、验证或 Git 溯源要求；
5. 准备将新的规则、对象、能力或机制纳入 LDVH，但无法归入五类构成要素，或者无法确认其能够为 AI 带来 V1-V8 中可辨认的净价值；
6. 准备声明状态成立、能力可用、环境 integrated 或工作完成，但现有验证结果或当次可观察依据不能支持声明范围；
7. 下位规范、附件、事实对象、Code、Web、工具输出或环境入口的内容或输出重新解释、覆盖或弱化本文的上位定义，或者承担规范模型定义职责的规范超出本文授权范围；
8. 无法确认停止影响哪些行动、对象或声明，或者已经取得 Human 回应但无法确认恢复条件及该回应的作用范围。

无法确定精确影响范围时，应暂停能够完整包含潜在影响的最小当前行动或工作对象；只有能够确认不受该来源规则影响的工作才可继续，暂停不得自动扩张到无关任务或普通求解路径。

### 9.2 暂停期间允许的行动

Stop Conditions 与 Human Gate 承担不同职责：Stop Conditions 决定何时暂停，Human Gate 决定哪些事项必须由 Human 作出判断。未触发 Human Gate 的停止，可以在来源规则定义的核对、修复、验证或分流条件满足后恢复；已经触发 Human Gate 的，必须取得作用范围清楚的 Human 回应。

暂停期间，AI 可以开展不越过停止边界的规则定位、事实核对、验证、证据收集、修复准备和分流准备，也可以准备 Human Gate 的交还内容，并继续未受影响的工作。

### 9.3 恢复条件

受影响范围只能在与触发原因对应的以下恢复条件满足后恢复：

1. 规则适用条件、效力或权威关系已经确认；
2. 强制要求已经满足，或者已经进入来源规则明确允许的分流方式；
3. 缺少的事实、验证或环境依据已经取得，或者相关声明已经缩小到现有依据实际支持的范围；
4. 已经取得对象、作用范围和后续方向清楚的 Human 回应；
5. 违反本文上位定义或超出结构治理授权的冲突已经修正并完成相应验证。

恢复只覆盖现有依据能够支持的范围，不自动恢复其它受影响事项。

### 9.4 能力边界

Helper CLI、Code、Hook、validator 和环境入口可以在各自已实现、已接入且当次可验证的能力范围内，识别、报告来源规则已经定义的停止条件，或执行相应停止要求。其停止效力必须回指具体来源规则、触发条件和受影响范围；未命中具体停止条件时，AI 的普通求解路径保持自主。
