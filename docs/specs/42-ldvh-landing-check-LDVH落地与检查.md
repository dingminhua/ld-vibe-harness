## 1. 行动定位与适用场景

LDVH落地与检查是把 LDVH 从规范仓库转化为用户可实际使用的管理链路，并持续确认该链路是否仍然可用的同一工作流程。

本文合并旧的 LDVH 落地动作和后置检查职责。AI 不应把初始化和检查理解为两个长期状态，也不应维护初始化状态文档或检查状态文档。正确动作是：先检查当前事实源和环境，输出当前缺口；经 Human 授权后逐项落地；完成后复检；最后在当前对话或调用结果中输出本次落地与检查报告。

本文适用于以下场景：

1. 用户要求安装、接入、初始化、启用或检查 LDVH；
2. 用户询问“现在能不能用”“还差什么”“有没有漂移”“下一步做什么”；
3. `LDVH-GOVERNED-PROJECTS.yaml` 缺失、需要生成草案，或需要新增、删除、修改管辖项目条目；
4. AI 进入管辖项目后发现 `docs/`、`ldvh-base/`、工作区级薄入口、平台清单或基础校验缺失；
5. 平台适配清单、入口、项目路径、目录、Code、Web、工作模型或工作流程发生变化，需要复检；
6. LDVH 自身源码仓库作为 dogfood 管辖项目时，需要检查或补齐自身落地链路；
7. 用户授权 AI 逐项修复检查报告中的缺口。

本文不适用于以下场景：

1. 只阅读 LDVH 规范或解释某个术语；
2. 普通 Task 执行、验证、关闭或变更提交；
3. 只审查某个 ADR、Task、Memo、Pitfall 或 Change 的对象状态；
4. 只做变更影响识别、联动编排或规范落地要求分流且不检查 LDVH 接入链路，应进入变更联动统筹流程；
5. 为单个工作模型创建具体事实实例，除非该实例本身是本次落地目标并已通过对应 Human Gate。

## 2. 准入条件

进入 LDVH落地与检查前，应至少满足以下条件：

1. 能定位 LDVH 自身项目根目录；
2. 能读取 LDVH-AI-ENTRY.md、`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/01-目录说明.md`、`docs/specs/02-术语规范.md`、`docs/specs/03.06-管辖项目配置规范.md` 和本文；
3. 能读取或确认缺失工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml`；
4. 能确认当前 AI 开发环境，并能定位当前平台适配清单；无法定位时，能请求 Human 从已有清单或待填平台中选择；
5. 能明确本次范围是只检查、首次落地、缺口补齐、复检，还是多项目检查；
6. 若涉及目标管辖项目，能明确目标项目 `id`、`path` 和访问权限；
7. 能区分检查发现、稳定事实、缺口分流和受控写入；
8. 若需要修改配置、目录、入口、平台清单、Code 或 Web，已触发 Human Gate。

### 2.1 Bootstrap 最低路径

当本文用于首次安装、接入、初始化或启用 LDVH 时，LDVH落地与检查必须具备不依赖高级统筹流程的最低路径。

最低路径应满足：

1. 能读取 LDVH 自身正式规范、目录说明、术语、管辖项目配置规则和本文；
2. 能定位工作区根目录和 `LDVH-GOVERNED-PROJECTS.yaml`，或把缺失记录为 blocked / needs_human_gate；
3. 能检查 `docs/specs/`、`tools/`、`tests/`、`web/`、`ldvh-base/`、入口文件和 active 索引的基础存在性与一致性；
4. 能识别当前 AI 开发环境和环境承接矩阵是否可定位；
5. 能输出本次 LDVH落地与检查报告；
6. 能把缺口分流为规范缺口、Code 缺口、Web 缺口、Task 缺口、事实源缺口、环境承接缺口或 Human Gate；
7. 能明确哪些检查由 Code 基线能力完成，哪些检查只能人工降级。

最低路径不得要求以下内容已经可用：

1. 41 规范落地统筹流程已经完整闭环；
2. 规范落地统筹 Skill 已经存在；
3. `landing-plan`、`change-plan` 或等价变更联动计划已经生成；
4. Web 运行态已经启动；
5. 外部 AI 开发环境提供额外支援能力。

这些能力可以作为检查对象、可选输入或缺口分流目标，但不得成为本文启动的前置条件。

以下任一条件不满足时，不得宣称 LDVH落地与检查通过：

1. 检查范围不明确；
2. 无法读取或确认管辖项目配置；
3. 目标项目路径无法定位且未记录为 blocked；
4. 无法区分落地缺口、检查发现和普通任务缺口；
5. 需要 Human Gate 的修改尚未确认；
6. 结论没有证据、缺口状态或分流建议。

## 3. 事实源边界

LDVH落地与检查涉及多个事实源，必须按以下边界处理：

| 事实 | 权威位置 |
|---|---|
| LDVH 正式规范 | `docs/specs/` |
| 当前 LDVH 管理实例和管辖项目清单 | 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` |
| AI 统一入口运行投影 | LDVH-AI-ENTRY.md |
| 平台适配清单与要求响应矩阵 | `docs/specs/04.06-平台适配清单规范.md` 和当前平台清单 |
| 管辖项目文档事实 | `{project.path}/docs/` |
| 管辖项目内部分析 | `{project.path}/docs/research/` |
| 管辖项目外部引用 | `{project.path}/docs/refs/` |
| 管辖项目工作对象实例 | `{project.path}/ldvh-base/` |
| Code 实现和校验命令 | `tools/` |
| Web 实现和 Human-facing 展示 | `web/` |
| 实际变更 | Git diff 和后续 Change / commit 证据 |

当前环境确认、检查发现、缺口清单和复检结论默认只进入当前落地与检查报告。报告不是长期状态事实源。需要长期保留的稳定事实，必须按内容性质另行进入管辖项目配置、平台适配清单、Task、Memo、ADR、Pitfall、正式规范、Code、Web 或其他 Git 文件事实源，并满足对应准入条件和 Human Gate。

42 只聚合本次检查状态，不拥有安装、初始化、环境观察或运行投影现场状态的长期状态机。Task、ADR 等具备证据生命周期的工作对象可以按对应规范保存状态；安装 / 初始化 / 环境观察只能即时读取为当前检查结果。若检查结果形成后续执行、长期决策、风险经验、提醒或正式规则，应按 §6.6 分流并通过对应对象或规范保存，而不得保存为“已安装”“已初始化”“环境已确认”“运行投影已完成”等长期状态。

LDVH落地与检查不得把以下内容写入错误位置：

1. 不得把初始化状态、落地状态、检查状态、检查报告或缺口清单写入 `LDVH-GOVERNED-PROJECTS.yaml`；
2. 不得默认创建初始化状态文档、检查报告文档或其他状态记录文档；
3. 不得把聊天记录、工具输出、Web 页面状态或报告结论当成最终事实源；
4. 不得在管辖项目中默认创建 `docs/specs/`、`specs/`、平台规则文件、项目级 AI 指令或 AI 统一入口；
5. 不得为 removed、deferred-field、deferred-doc 或 reserved 工作模型创建默认事实源目录；
6. 不得把未经检查的平台名称、入口存在、工具可用或历史会话判断写成完整支持或通过结论。

## 5. Scenario 识别

LDVH落地与检查 Scenario 应按以下条件识别：

| Scenario | 进入条件 | 不进入条件 |
|---|---|---|
| 只读检查 | 用户要求知道现状、缺口、可用性、漂移或下一步行动，且未授权写入 | 用户只要求解释概念 |
| 首次落地 | 用户首次安装、接入、初始化或启用 LDVH | 普通 Task 执行 |
| 缺口补齐 | 当前检查报告发现可修复缺口，且用户授权逐项处理 | 缺口已属于明确 Task 且不影响落地链路 |
| 复检 | 已完成一组落地动作，需要确认缺口是否关闭 | 只运行单个命令且不判断链路 |
| 环境与入口检查 | 当前平台、入口、运行投影或权限边界变化 | 只做会话级临时说明 |
| 管辖项目配置检查 | `LDVH-GOVERNED-PROJECTS.yaml` 缺失、异常、需要新增/删除/修改项目，或项目路径可能漂移 | 只是阅读已有配置 |
| 管辖项目承载检查 | 需要检查项目 `docs/`、`ldvh-base/`、active 模型/流程、Code/Web 和入口承载 | 只阅读单个项目文档 |
| 缺口分流 | 发现无法立即修复的规范、Code、Web、运行投影、Human Gate 或事实源缺口 | 已有明确事实源和执行流程 |

多个 Scenario 同时匹配时，应按只读检查、缺口报告、Human Gate、授权落地、复检、分流的顺序处理。任何一步触发 Human Gate 时，应先暂停确认，不得跳到后续阶段宣称通过。

## 6. 执行流程

LDVH落地与检查按以下步骤执行。

### 6.1 确认范围和模式

AI 应先确认：

1. 当前 LDVH 自身项目根目录；
2. 当前工作区根目录和管辖项目配置位置；
3. 本次目标是只读检查、首次落地、缺口补齐、复检还是多项目检查；
4. 当前 AI 开发环境是否可由当前会话、平台上下文、已生效入口或自身工具能力明确判断；
5. 目标管辖项目 `id` 和 `path`；
6. 是否允许修改 `LDVH-GOVERNED-PROJECTS.yaml`；
7. 是否允许写入目标项目 `docs/`、`ldvh-base/` 或工作区级入口；
8. 是否允许修改平台适配清单、Code、Web 或运行投影；
9. 本次报告是否只保留在当前对话或调用结果中；
10. 是否存在影响用户原有项目入口的风险。

范围不清时，应暂停并请求 Human 明确当前环境、目标项目和授权范围，不得默认检查或修改所有登记项目。

### 6.2 执行只读检查

AI 应先执行只读检查，并在写入前输出当前检查结果。只读检查至少包括：

1. 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 是否存在、结构是否符合 03.06、是否错误承载状态；
2. 目标项目 `path` 是否可定位、是否与用户意图匹配、是否有读取权限；
3. 当前平台是否能定位到平台适配清单，清单是否覆盖 AI-S1 至 AI-S15 和 LR-1 至 LR-7；
4. LDVH-AI-ENTRY.md 是否存在，平台用户级 / 系统级薄入口、项目级例外入口或降级入口是否能引导 AI 进入 LDVH；
5. 目标项目 `docs/`、`docs/research/`、`docs/refs/` 是否存在或有合理降级；
6. 目标项目 `ldvh-base/` 是否存在，且只为 active 或已授权例外模型创建事实源承载；
7. 20 active 工作模型和 40 active 工作流程是否可定位；
8. Bootstrap Code 基线能力是否具备，非基线 Code 校验、Web 展示或 Human-facing 入口是否满足本次目标，或是否可降级；
9. 是否存在不应默认创建的 `docs/specs/`、项目级入口、初始化状态文档、检查状态文档或过期运行投影；
10. 当前 41 或后续更名流程是否可作为变更联动统筹能力被定位；不可定位时记录为能力缺口，不阻塞 bootstrap 最低路径；
11. 上次报告、当前现场检查、变更联动统筹输出或 Human 明确说明中的 open / degraded / needs_human_gate 缺口是否仍未处理。

检查当前 41 或后续更名流程时，42 只确认该变更联动统筹能力是否可定位、是否 active、是否能提供可追溯过程输出、是否存在 open / degraded 缺口。任一层不可定位、不可验证或不可消费时，42 应把它报告为变更联动统筹能力缺口，不得把该缺口作为 bootstrap 最低路径失败的唯一原因，也不得用 42 自身固定清单替代变更联动统筹结果。

42 不维护具体平台入口、具体 Skill、具体 Agent、具体 Hook、具体 CI、具体 Web 页面或具体 Code 命令的固定枚举清单。新增、删除或重命名某个运行投影实体时，不应为了把实体名称加入本文而修改 42。42 只定义抽象检查算法：先从正式规范、平台适配清单和工作流程中提取落地要求，再检查这些要求是否已有可定位的承接机制、运行投影、验证方式、降级方式和回写出口。具体实体名称、路径、模板、open_items 和证据应由对应规范、平台适配清单、Task、Code、Web 或实际运行投影承载。

当抽象检查算法发现“需要某类非基线 Code / Skill / 运行投影 / Human Gate / Web / Hook / CI 承接”，但当前没有可用工具、实体或验证方式时，42 应把它报告为缺口，并按 §6.6 分流给变更联动统筹流程、Task、平台适配清单 open_items、Code 需求、Web 需求或 Human Gate，而不是在本文中直接新增固定清单项。

只读检查结果应先告诉 Human：已满足什么、缺什么、哪些可自动补齐、哪些必须 Human Gate、哪些只能降级。

### 6.3 生成缺口清单和行动建议

检查结果至少应把每项发现归为：

| 状态 | 含义 |
|---|---|
| done | 当前范围内已满足，有可追溯证据 |
| todo | 未满足，但可在本流程中经授权补齐 |
| needs_human_gate | 需要 Human 确认范围、写入、降级或风险接受 |
| degraded | 可用但依赖降级方式，必须说明残留风险 |
| blocked | 缺少关键事实源、权限、路径、入口或确认，不能继续宣称通过 |
| out-of-scope | 本次不覆盖，不能据此判断通过或失败 |

AI 应给出逐项行动建议。建议可以包括：更新管辖项目配置、创建目录、补平台薄入口、补平台清单 open item、记录 Task、形成 ADR、补 Code 校验、进入变更联动统筹流程或保持降级。行动建议必须对应抽象缺口类型，不得把本文改造成具体实体维护清单。

### 6.4 Human Gate 和逐项落地

以下动作必须先 Human Gate（触发条件见 §7）：

Human 授权后，AI 只能执行授权范围内的落地动作。未授权事项继续保留为 todo、needs_human_gate、degraded 或 blocked，不得静默写入。

### 6.5 复检

完成一组授权动作后，AI 应复检对应项：

1. 被修改的配置、目录、入口、Code、Web 或平台清单是否真实存在；
2. 修改是否符合对应规范；
3. 是否引入新的事实源边界、入口冲突、目录冲突或 Human Gate 缺口；
4. 原 todo / blocked 项是否变为 done、degraded 或仍 blocked；
5. 仍需长期保留的发现是否已按准入条件分流。

复检失败时，不得宣称完成。AI 应说明失败原因、影响范围和下一步建议。

### 6.6 分流缺口

无法在本流程中立即修复的缺口，应按以下规则分流：

| 缺口类型 | 分流去向 |
|---|---|
| 正式规范缺口或落地要求冲突 | 变更联动统筹流程、Task 或正式规范修改 |
| 管辖项目配置漂移 | 03.06 受控修改；后续可由 52 candidate 承接 |
| 平台适配、运行投影或入口缺口 | 平台适配清单 open_items、Task、Memo、ADR 或变更联动统筹流程 |
| 可执行修复项 | Task |
| 长期决策、边界变更或降级接受 | ADR |
| 暂不执行但有保留价值的信息 | Memo |
| 可复用风险或经验 | Pitfall 或最佳实践候选 |
| 已实际修改事实源 | Change / Git commit 记录 |
| Code 或 Web 能力缺口 | Code/Web 需求、Task 或变更联动统筹流程 |
| 变更联动统筹能力、实例化判断或当前 41 自身闭环缺口 | 变更联动统筹流程、Task 或正式规范修改；42 当前报告只说明发现和分流建议 |

缺口分流建议不是写入授权。实际写入仍需满足对应工作模型、文档规范和 Human Gate。

### 6.7 输出落地与检查报告

本流程结束、降级或阻塞时，AI 应在当前对话或调用结果中输出落地与检查报告。报告至少包含：

1. 日期和触发原因；
2. 检查范围和模式；
3. 读取的关键事实源；
4. 当前 AI 环境确认方式、平台清单和运行投影状态；
5. LDVH 管理实例和目标项目 `id`、`path`；
6. 本次授权范围；
7. 每项检查状态：done / todo / needs_human_gate / degraded / blocked / out-of-scope；
8. 已执行的落地动作；
9. 已执行验证命令或人工检查；
10. Human Gate 结果；
11. 仍未处理的缺口和分流建议；
12. 本次结论：pass / pass-with-warnings / degraded / blocked / out-of-scope；
13. 下一步行动建议。

报告不得只写"正常""已完成"或"没问题"。必须说明证据、范围、状态、缺口和分流去向。报告默认不写入文档事实源。

当当前 41 或后续更名流程已提供 `landing-plan`、`change-plan` 或等价变更联动过程输出时，42 应把它作为只读可选输入消费，而不是把它当成事实源状态、落地完成证明或 bootstrap 前置条件。消费过程应满足以下边界：

1. 先确认 `metadata.report`、`metadata.read_only`、`metadata.source_of_truth`、`scope` 和 `facts_read`，确保输入确实来自变更联动统筹过程输出合同或等价降级报告；
2. 从 `capabilities`、`requirements`、`gaps`、`proposed_actions`、`writes_required`、`writeback_targets`、`human_gate` 和 `validation_plan` 中提取本次检查范围内的变更影响、缺口、候选行动、Human Gate 和验证计划；
3. 将变更联动过程输出中的 open / degraded / needs_human_gate / follow_up 项映射为 42 报告中的 todo / degraded / needs_human_gate / blocked / out-of-scope 状态，并保留来源字段或来源摘要；
4. 当变更联动过程输出标明统筹能力、实例化判断、验证证据消费、运行投影漂移检查或 Human Gate 回写消费不足时，42 应报告为变更联动统筹能力缺口，不得把缺口吞并为 42 已处理；
5. 当变更联动过程输出缺失、字段不完整、来源不可追溯或覆盖范围不足时，42 应显式标注“变更联动输出缺失/不足”，将变更联动统筹能力列为 todo 或 out-of-scope 缺口项，并以 42 bootstrap 最低路径继续；不得在该输出缺失时宣称变更影响聚合已覆盖；
6. 42 不得因为 `landing-plan`、`change-plan` 或等价变更联动过程输出生成成功而宣称 LDVH落地与检查通过；通过结论仍必须由 42 结合当前现场检查、证据、授权范围、复检结果和 Human Gate 状态给出。

42 自身产生的检查报告、检查结果聚合和缺口诊断均属于过程输出。它们的输出边界如下：

| 过程输出 | 内容边界 | 不得表达为 | 稳定化路径 |
|---|---|---|---|
| 检查报告 | 本次范围、读取事实源、现场检查、授权范围、验证、Gate、缺口和结论 | 初始化状态、检查状态、长期报告事实源或项目配置状态 | 当前对话或调用结果；需要沉淀时经 Human Gate 后按 09 分流 |
| 检查结果聚合 | 将变更联动统筹输出、Code、配置、目录、运行投影、Human Gate、验证和人工检查结果汇总为 done / todo / needs_human_gate / degraded / blocked / out-of-scope 等本次检查标签 | 工作对象状态流转、规范闭环状态、平台支持状态、安装状态、初始化状态、环境状态或缺口关闭事实 | 回写到对应 Task、ADR、Memo、Pitfall、Change、平台适配清单、Code/Web 或正式规范后才稳定 |
| 缺口诊断 | 描述缺失能力、证据不足、覆盖范围不足、降级原因、残留风险和建议分流 | 自动创建任务、自动接受降级、自动关闭缺口或授权写入 | 按缺口性质进入变更联动统筹流程、Task、Memo、ADR、Pitfall、平台适配清单 open_items、Code/Web 需求或规范修改 |

42 输出过程报告时，应显式区分“已检查到的事实”“从变更联动统筹流程或 Code 派生的检查结果”“候选建议”“需要 Human Gate 的写入或关闭动作”和“已回写的稳定事实”。若报告中包含候选任务、候选决策、候选缺口关闭、降级接受、验证结论或回写目标，AI 必须说明它们尚未稳定化，除非已按对应事实源完成受控写入、复检并记录证据。

42 的检查结果聚合只服务于本次落地与检查结论，不拥有其他事实源的状态机。聚合时应遵循以下优先级：blocked 高于 needs_human_gate，needs_human_gate 高于 todo，todo 高于 degraded，degraded 高于 done；out-of-scope 不参与通过判断。任一关键范围存在 blocked、needs_human_gate 或未解释的 degraded 时，42 不得输出 pass，只能输出 blocked、degraded 或 pass-with-warnings，并说明原因。

## 7. Gate 触发条件

以下动作必须触发 Human Gate：

1. 新增、删除或修改 `LDVH-GOVERNED-PROJECTS.yaml` 项目条目；
2. 创建、删除、重命名项目 `docs/`、`ldvh-base/` 或关键子目录；
3. 写入平台用户级 / 系统级入口、平台配置、项目规则或等价入口；
4. 在管辖项目中例外创建项目级入口、平台规则文件或 AI 统一入口；
5. 修改平台适配清单、正式规范、Code、Web、Skill、Agent、Hook、CI 或运行投影；
6. 为 removed、deferred-field、deferred-doc 或 reserved 工作模型创建目录或实例；
7. 接受长期降级、关闭关键缺口或宣称 blocked 转为 pass；
8. 将落地与检查报告沉淀为文档、工作对象或其他持久事实源。

## 8. Skill 和 Agent 调度

LDVH落地与检查默认由主控 AI 执行，不要求创建专用 Skill，也不在本文枚举应存在的具体 Skill。

当检查步骤稳定、可复用且不会替代主控判断时，可以评估是否创建 LDVH 自建 Skill。Skill 只能承接读取清单、目录检查、结果模板生成、缺口聚合等稳定子步骤，不得决定目标项目、绕过 Human Gate、写入平台入口或宣称检查通过。42 检查 Skill 时，只检查“规范落地要求是否需要 Skill 承接、已有 Skill 是否符合 04.04 的命名和正文边界、Skill 是否路径漂移或复制事实源正文、缺口是否已分流”，不得维护具体 Skill 名称清单。

以下情况可以按 `docs/specs/44-multi-role-thinking-多角色思考.md` 调用独立、专项或并行 Agent：

1. 目标项目路径、入口写入或事实源边界存在争议；
2. 是否创建项目级入口、目录结构或运行投影存在风险；
3. 工作模型、工作流程、Code、Web 和运行投影缺口需要多视角判断；
4. 长期降级是否可接受不清；
5. 需要并行检查多个项目且结果必须由主控统一汇总。

Agent 输出必须回到主控汇总。落地与检查报告不是长期状态事实源；需要形成稳定结论时，应按内容性质另行进入配置、工作对象、规范或其他 Git 文件事实源，并满足对应准入和 Gate。

## 9. 工具协作适配

LDVH落地与检查可以使用 Code、命令、Web、搜索和文件检查协作，但必须遵守以下边界：

1. Code 可以校验 `LDVH-GOVERNED-PROJECTS.yaml`、docs/specs 结构、工作对象字段、路径存在性、目录结构和入口引用；
2. Code 可以生成检查报告或缺口清单，但输出不是最终事实源；
3. Code 不得自行新增管辖项目条目、创建工作对象实例、关闭缺口或修改平台入口；
4. Web 可以展示本次检查过程、缺口、Gate 和待确认事项，但 Web 状态不替代 Git 文件事实源；
5. 搜索和文件读取用于定位现有项目文档、目录和事实实例，不得把搜索结果直接写成稳定事实；
6. 工具无法覆盖的判断，应记录人工降级检查和残留风险。

若发现缺少非基线工具，应按 `docs/specs/07-Code实现规范.md` 判断是否形成 Code 需求；Code 自身规范或测试缺失时，应先建立最小可验证能力，再声明机械验证完成。

42 使用工具时，可以消费变更联动统筹流程的过程输出或等价 Code 输出。若当前工具只能抽取变更影响或落地要求，但不能判断承接机制是否实例化、验证证据是否存在、运行投影是否漂移或 Human Gate 是否可回写，42 应把这些能力差距作为 Code / 变更联动统筹能力缺口报告给 Human，而不是把临时人工判断写成已闭环。

### 9.1 Bootstrap Code 基线能力

Bootstrap Code 基线能力是 LDVH落地与检查在没有外部环境支援时必须预先具备的 Code 能力。它们由本文定义需求边界，由 07 约束实现方式，由 10 约束可测试性，由 `tools/` 实现，由 `tests/` 证明。

这些能力不是运行时发现缺失后再临时定义的需求。若以下能力在 `tools/` 或 `tests/` 中缺失，应视为 LDVH 自身 Code 能力资产未完成，而不是普通环境承接降级。

Bootstrap Code 基线能力至少包括：

| 能力 | 最低作用 | 输出边界 |
|---|---|---|
| specs 完整性检查 | 检查 `docs/specs/` 基础结构、标题、引用和 active 索引是否可读取 | 诊断结果和 exit code，不写入事实源 |
| 资产目录检查 | 检查 `docs/specs/`、`tools/`、`tests/`、`web/`、`ldvh-base/`、入口文件是否存在或记录缺口 | 当前检查报告输入，不创建目录 |
| 管辖项目配置检查 | 检查 `LDVH-GOVERNED-PROJECTS.yaml` 是否存在、可读取、结构符合 03.06 | 诊断结果；写入草案必须 Human Gate |
| 工作模型和工作流程索引检查 | 检查 20 / 40 active 项是否可定位，planned / candidate / reserved 未被误执行 | 诊断结果和缺口分类 |
| 环境承接矩阵检查 | 检查当前环境和 04.06 承接矩阵是否可定位，必要时记录待补齐事项 | 当前检查报告输入，不宣称环境完整支持 |
| 运行投影入口检查 | 检查 LDVH-AI-ENTRY.md 和环境薄入口是否可定位、是否存在路径漂移 | 诊断结果；入口写入必须 Human Gate |
| Code 自检 | 检查 Bootstrap Code 自身命令、测试入口和最小样例是否可运行 | 命令结果和失败诊断 |
| Web 资产检查 | 检查 `web/` 作为资产是否存在、关键入口是否可定位 | 资产检查结果；不得要求 Web 运行态作为 bootstrap 前置条件 |
| 42 报告结构输出 | 生成或校验本次 LDVH落地与检查报告所需字段 | 当前对话或调用结果，不默认写入文档 |
| 缺口分类与分流 | 将发现分类为规范、Code、Web、Task、事实源、环境承接或 Human Gate 缺口 | 分流建议；不自动创建 Task 或关闭缺口 |

Bootstrap Code 基线能力不得直接执行以下动作：

1. 自动新增、删除或修改管辖项目配置；
2. 自动创建 `docs/`、`ldvh-base/`、入口文件、平台清单或运行投影；
3. 自动创建 Task、ADR、Memo、Pitfall 或 Change；
4. 自动接受长期承接降级；
5. 自动宣称 LDVH落地与检查通过。

当 Bootstrap Code 基线能力未实现或测试不能证明时，42 应输出 Code 能力资产未完成的缺口，并建议创建或使用 Task 补齐 `tools/` 实现和 `tests/` 证明。该缺口关闭前，不得宣称 LDVH 已具备完整 bootstrap 能力。

## 10. 事实源回写与证据留存

LDVH落地与检查应按以下规则处理事实和证据：

| 输出 | 回写位置 |
|---|---|
| 管辖项目清单变化 | 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` |
| 落地与检查报告 | 当前对话或调用结果；默认不写入文档事实源 |
| 缺口清单 | 当前报告；必要时经准入判断和 Human 授权后分流为 Task、Memo、ADR、Pitfall 或规范待补齐事项 |
| 安装 / 初始化 / 环境观察状态 | 不回写；每次执行时即时读取为当前检查结果 |
| 目录创建或事实源写入 | Git 文件事实源和后续 Change / commit 证据 |
| Code 校验结果 | 当前报告中的摘要和可追溯命令；完整输出按需保留在当前执行上下文 |
| Human Gate 结果 | 当前报告、相关工作对象或 commit 记录 |
| 长期决策 | ADR |
| 可执行后续工作 | Task |
| 暂存发现或提醒 | Memo |

证据至少应保留：

1. 读取的关键规范和配置；
2. 目标项目 `id`、`path` 和 Human 授权范围；
3. 已检查路径、目录和入口；
4. 已执行命令或人工检查；
5. 写入文件清单；
6. 缺口状态和降级方式；
7. Gate 结果和后续分流建议。

聊天记录、临时命令输出、Agent 输出和 Web 页面状态不得单独作为完成或通过证据。

## 11. 机制适配边界

LDVH落地与检查的机制适配边界如下：

| 能力 | 当前结论 | 边界 |
|---|---|---|
| Rules / Instructions | 按落地要求判断是否需要薄入口 | 平台入口只指向 LDVH 管理入口或 LDVH-AI-ENTRY.md，不复制流程全文；具体路径和模板由 04.04、平台适配清单和实际运行投影承载 |
| Skill | 默认不创建，不枚举具体 Skill | 可承接稳定子步骤，不替代目标项目判断、Human Gate 或最终通过判断；具体 Skill 是否需要存在由相关规范的落地要求和 41 统筹结果决定 |
| Agent | 可作为增强模式 | 用于独立、专项、并行审查，输出回到主控 |
| Code / 工具 | 按落地要求动态判断缺口 | 优先承接管辖项目配置、路径、目录、工作对象、入口漂移、运行投影漂移和 41 聚合结果消费；缺工具时报告 Code 缺口并分流 |
| Web | 可选 | 可展示本次检查过程和 Gate，不作为最终事实源 |
| Hook / CI | 后续评估 | 适合在配置、入口或规范变更后触发一致性检查提醒 |

本文不创建固定机制子文档。机制实体、实现入口和运行投影应按 04、07、08、10 和当前平台适配清单处理。

## 12. 行动特有可测试性锚点

LDVH落地与检查至少应能派生以下测试锚点：

| 类型 | 可测试性锚点 |
|---|---|
| 正向场景 | 用户要求安装、接入、检查可用性、检查漂移或询问缺口时，AI 应进入本文或说明缺少的准入条件 |
| 负向场景 | 简单规范解释、普通 Task 执行或单个对象状态审查，不应被误判为完整 LDVH落地与检查 |
| 只读场景 | 未授权写入时，只输出检查结果、缺口和建议，不修改事实源 |
| Gate 场景 | 修改配置、创建目录、写入入口、接受长期降级、沉淀报告或宣称通过时，应触发 Human Gate |
| 输出场景 | 落地与检查报告只在当前对话或调用结果中输出；不得默认创建初始化状态文档、检查报告文档或其他状态记录文档 |
| 复检场景 | 授权落地动作完成后，应复检对应项，不得跳过验证宣称通过 |
| 失败降级 | 缺少项目路径、权限、入口、Code 校验或 active 索引时，应记录 degraded 或 blocked，不得宣称 pass |
| 回归风险 | 修改本文后，应检查 01、02、03.02、03.06、04、05、06、07、08、09、20、40、41、44、Code、Web 和运行投影是否需要同步 |

具体测试用例、预期行为矩阵、失败诊断和回归用例不写入本文，应按 `docs/specs/10-运行闭环测试规范.md` 进入测试用例事实源或 Code 测试实现。

## 14. 检查要求

检查一次 LDVH落地与检查是否符合本流程时，应确认：

| 检查项 | 标准 |
|---|---|
| 范围明确 | 已明确检查范围、模式、目标项目和授权边界 |
| 先检后做 | 写入前已先输出当前检查结果和缺口 |
| 配置有效 | `LDVH-GOVERNED-PROJECTS.yaml` 符合 03.06，未承载状态或报告正文 |
| 路径确认 | 目标项目路径存在或缺失已触发 Gate，未误写其他项目 |
| 文档工作区 | `docs/`、`docs/research/`、`docs/refs/` 已检查或记录缺口 |
| 工作对象承载 | `ldvh-base/` 和 active 工作模型事实源目录按 20 和具体模型规范检查，未创建 removed/deferred/reserved 默认目录 |
| 工作流程入口 | active 工作流程按 40 定位，planned/candidate 未被当作已生效 |
| 落地需求来源 | 已从正式规范、平台适配清单和 41 聚合结果中提取本次范围内的落地要求，未用 42 自身固定清单替代 |
| 入口投影 | AI 统一入口、平台用户级 / 系统级薄入口、项目级例外入口或降级入口状态清晰，具体路径来自 04.04、平台适配清单或实际运行投影 |
| 平台清单 | 已读取当前平台适配清单中的要求响应矩阵，且未把平台名称或平台能力清单硬编码为通过依据 |
| 运行投影抽象检查 | 已按落地要求类型判断是否需要 Rules / Instructions、Skill、Agent、Hook、CI、Web、Code 或人工降级；未在本文枚举具体实体 |
| Code / Web | Code 校验和 Web 可用性已检查或记录缺口 |
| 授权落地 | 实际写入均在 Human 授权范围内 |
| 复检 | 授权动作完成后已复检对应项 |
| 报告输出 | 已在当前对话或调用结果中输出落地与检查报告，未默认创建状态文档 |
| 缺口分流 | todo / needs_human_gate / degraded / blocked 缺口按 41 和事实源边界分流 |
| Human Gate | 高影响写入、入口、路径、降级、沉淀报告和通过声明已暂停确认 |

检查本文是否作为具体工作流程规范完成时，应确认：

1. 覆盖 03.05 要求的标准章节；
2. 与 06 的通用规则不冲突；
3. 在 `docs/specs/40-工作流程集合索引.md` 中登记为 active；
4. 未重新定义 03.06、04.02、04.06、09、20、40 或 41 的权威规则；
5. 当前权威路径为 `docs/specs/42-ldvh-landing-check-LDVH落地与检查.md`；
6. 行动特有可测试性锚点已写入本文；
7. 未恢复独立后置检查流程或初始化状态记录。
