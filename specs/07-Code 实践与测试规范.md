## 1. 价值判断

Code 实践与测试规范（Code Practices and Testing Specification）的价值，是让 AI 在开始实现前先形成可检查的 Code 整体规划，在持续变化中保持模块、依赖、接口、Schema 维护和测试责任一致，并用与风险相匹配的测试取得范围清楚的确定性反馈。

本文主要服务：

1. V2 充分理解：把来源契约、模块责任、依赖、接口、Schema、失败路径和测试联系成一个可以共同检查的实现视图；
2. V3 边界识别：区分来源规范定义的语义、Code 的实现责任、tests 的验证作用和外部环境的真实结果；
3. V4 稳定推进：在实现、修复和重构前明确工程边界，并及时获得能够支持调整或分流的测试与诊断反馈；
4. V5 据实判断：使测试通过、覆盖率、静态检查和诊断输出只支持其实际检查范围内的结论；
5. V6 工作接续：让后续 AI 能恢复当前模块设计、维护责任、已知风险、测试映射和设计偏移；
6. V8 持续积累：把重复出现的耦合、Schema 漂移、诊断缺口和测试缺口转化为可持续修正的工程要求。

首次实现前设计与持续工程要求约束同一份 Code，并且必须持续同步；测试又直接验证这些边界，因此本文不把 Code 实现规划、工程实践和测试拆成多份普通规范。本文也不建立一份横跨所有来源规范的“测试与验证总规范”：具体规则的成立条件和可证明范围仍由各自来源规范定义。

## 2. 规范依据

本文直接依据 `ldvh-root`，细化 00 对 Code 作为确定性执行能力上位概念及其实现关系的定义：

1. Code 提供解析、索引、聚合、校验、测试、上下文压缩和受控写入等确定性能力与反馈；
2. 在实现层，Helper CLI、Git Hook、环境 Hook、Git Gate 和 Hook Gate 所需的确定性程序由 Code 实现；该关系不建立架构层隶属、并列语义构成要素或固定模块层级；
3. Web 是面向 Human 的交互呈现职责，不属于 Code；为 Web 服务的脚本与配置归入 Web 实现，不因具有可执行形态而归入 `code/`；
4. Code 和 tests 不得重新解释规范模型、事实模型、行动模板、Helper、Web 或环境的来源语义；
5. 能力可用、状态成立和工作完成的声明不得超出当次实现、测试和可观察依据实际支持的范围。

本文同时依据 `source-of-truth-traceability` 对 Working Tree 当前内容、未提交或未跟踪文件、`HEAD` 和 Git history 的边界，判断当前 Code 实现规划及其实现起点。Git 提交不是当前规划生效或被消费的前置条件，历史锚点也不能覆盖 Working Tree 中实际存在的当前内容。

本文作为普通规范，接受 `specification-model-foundation` 的文件形成与治理约束；该普遍结构约束不是本文 Code 工程语义的直接依据，因此不写入 `basis`。Helper 契约、领域规范、具体 Schema 来源和环境契约是相应 Code 增量开始规划和实现时必须读取的输入，不反向成为本文共同工程要求的规范依据。

本文采用 `code-engineering-practices` 作为职责标识符。Code tests 及可被其它职责规范直接引用的共同测试工程要求属于本文责任，而不是第二项横向责任；这不把其它职责域的测试资产物理归入 Code。职责标识符不需要逐字镜像标题。

## 3. 职责边界

本文负责定义：

1. 首次实现及会实质改变 Code 结构的增量开始前，必须形成哪些 Code 实现规划内容；
2. 模块责任、允许的依赖与调用方向以及共享能力的维护边界；
3. 公共接口、内部接口和 Code 侧 Schema 表示的维护责任与同步要求；
4. 内部错误传播、诊断、必要可观察信息和敏感信息保护的共同边界；
5. 依据责任、耦合、复杂度、变更频率、可测试性和可导航性进行重构评估的条件；
6. Code 实现规划与真实实现偏移时的发现、修正和声明边界；
7. 风险驱动的测试选择、检查范围、正反例与失败覆盖、测试同步和测试证据边界；
8. AI 如何审核 Code 是否把机械结果提升为正式来源未定义的语义结论；
9. 外部工程资料如何经过来源与适用性核验，才能候选进入 LDVH 当前规则源；
10. Code 与 Code tests 在 LDVH 仓库中的顶层资产归属，以及统一测试执行入口不得改变资产归属和结论范围的边界。
11. full-v4 Working Tree 证据 DTO 的唯一结构、固定覆盖政策、内容指纹、前后比较状态及生产与消费边界。
12. Code 实现确定性检查、行动分类或环境中的 Hook Gate 时，不得把局部来源闭集扩张为全局 AI 行动白名单的共同边界。

本文不负责定义：

1. Helper CLI 的公开命令、请求与响应字段、结果语义、能力清单或服务状态；
2. 规范、事实、行动模板、管辖配置或其它领域 Schema 的业务含义、字段闭集和状态；
3. 某一环境的事件、payload、manifest、安装接口、真实触发或回滚契约；
4. 除本文明确的 Code 与 Code tests 顶层资产归属及授权附件定义的 full-v4 Working Tree 证据契约外，具体算法、编程语言、框架、包管理器、内部目录结构、runner、profile、fixture、命令或覆盖率工具；
5. 单次实施计划、任务排期、当前实现进度或某次重构的逐步操作说明；
6. 全局行数上限、统一复杂度阈值、固定测试金字塔或对所有 Code 一体适用的测试数量；
7. 具体功能是否满足其来源规则、环境是否接入、Human 是否验收或项目是否完成。

真实源码、测试文件、实现说明和单次执行输出是本文约束或检查的对象，不因实现存在而成为本文的替代规则来源。

## 4. 适用范围

本文适用于 LDVH Code 与 Code tests 的以下场景；其它职责规范把本文列为直接依据时，本文共同测试工程要求同时适用于该职责域 tests，但不改变其资产归属：

1. 首次开始实现 Helper CLI 或其它确定性能力；
2. 新增会跨越现有模块、接口、Schema 或副作用边界的能力；
3. 修改模块责任、依赖方向、公共或内部接口、Schema 维护方式、错误传播或诊断路径；
4. 修复缺陷、进行行为保持型重构，或者处理重复回归和测试不稳定；
5. 评估过大文件、复杂模块、重复实现、循环依赖、难以隔离测试或 AI 难以导航的 Code；
6. 准备使用测试、静态检查、覆盖率或诊断结果支持实现、可用性或完成声明；
7. 准备把外部工程建议转化为 LDVH 稳定工程要求。

完全局部且不改变现有模块、依赖、接口、Schema、诊断或测试策略的修改，可以复用当前有效的 Code 实现规划，只需核对该规划仍覆盖本次变更并设计与风险匹配的测试；本文不要求为每个微小修改重新建立完整规划。

正文中的 module responsibility、dependency direction、interface ownership、Schema maintenance、diagnostics、refactoring assessment 和 risk-driven testing 只是中英文自然工程表达，不在本文中建立新的 LDVH 核心术语、机器枚举或跨规范状态模型。`Code 实现规划 / Code Implementation Plan` 承担稳定形成时机、内容、同步和偏移规则，必须按 01 的术语规则使用当前登记名称与定义。

### 4.1 Code 与 Code tests 的仓库位置

在 LDVH 仓库中，承载 00 所定义确定性执行能力的 Code 实现统一位于根级 `code/`。不得另用根级 `src/`、`lib/` 或其它并列目录承载同等 Code 实现责任；`code/` 内部如何按语言、包、模块或能力继续组织，由当前 Code 实现规划依据实际责任决定。

Code tests 统一位于 `code/tests/`，与被验证的 Code 实现共同归入 `code/`；仓库根目录不得另设 `tests/`。Web tests 的顶层资产归属和文件位置由 08 唯一定义；07 只在 08 将本文列为直接依据后，为其提供共同测试工程要求。以后可以提供统一测试执行入口依次调用 Code 与其它职责域测试，但统一执行不得改变各自来源定义的实现归属、依赖、配置或文件位置，也不得把一方测试结果扩大为另一方已经通过。

## 5. Code 实现规划（Code Implementation Plan）

Code 实现规划是面向一个实际准备实现或变更范围的版本化说明，用于在编码前记录来源、模块责任、依赖与调用方向、接口与 Schema 维护责任、错误与诊断、风险、测试和已知缺口，并在这些内容变化时同步更新。

它不是单次实施计划：不记录任务排期、临时步骤或运行进度；也不是独立规则源或产品契约，不能定义 Helper、领域或环境语义；它与架构描述可能使用相同图表或视图，但只覆盖 LDVH Code 当前准备实现和维护的范围。`Code Implementation Plan` 是 LDVH 对这一内部工程对象采用的描述性英文名称，不声称是行业标准术语，必须按 01 完成必要的术语审核和登记。

### 5.1 规划先于相应实现

任何准备进入实现的 Code/tests 范围，必须先有能够覆盖该增量的 Code 实现规划。后续变更出现以下任一情况时，必须在开始相应实现前建立或更新受影响部分，不得等实现完成后补写：

1. 新增、拆分、合并或实质改变模块责任；
2. 新增或改变模块间允许的依赖与调用方向；
3. 新增或改变公共接口、跨模块内部接口或其维护责任；
4. 新增或改变 Schema 的 Code 侧表示、生成关系或维护责任；
5. 改变副作用、权限、外部进程、文件写入或其它资源边界；
6. 改变错误传播、诊断信息或关键可观察位置；
7. 改变主要风险、测试检查范围或测试证据取得方式；
8. 进行跨越多个既有责任边界的重构。
9. 新发现的问题需要修正规则、字段、生命周期、接口、可观察结果、授权或验证边界的来源规范或授权附件；此时先按 `specification-model-foundation` §13.6 完成来源修正和独立复核，才形成或更新本规划并开始实现。

规划只约束实际准备实现的范围。未来设想不得为了显得完整而提前固化为模块、接口或兼容义务；未解决问题必须明确保留为未决定项，不得由 Code 猜测补齐。

已确认当前来源完整而问题仅为实现偏差时，不要求为了流程新增或改写 Specs；规划必须回指该确认过的来源、说明其覆盖本次预期行为，并把实现与测试限制在该来源已经规定的边界内。实现、测试或现有页面不得反向证明来源已经完整，也不得以实现先行迫使事后修改规则来迁就既有行为。

### 5.2 最小规划内容

Code 实现规划至少应当使下列信息可定位、可共同检查：

| 规划内容 | 必须说明 | 不得代替 |
|---|---|---|
| 实现目标与来源 | 本增量准备实现什么能力、直接消费哪些当前有效来源、明确不实现什么 | 不得由规划自创外部产品或领域语义 |
| 模块责任 | 每个受影响模块承担的内聚责任、输入、输出、副作用和不承担的内容 | 不得用当前文件名列表代替责任说明 |
| 依赖与调用方向 | 允许的模块依赖、调用入口、禁止的绕行以及需要隔离的外部依赖 | 不得用偶然 import 现状反向证明设计合理 |
| 接口维护 | 公共和跨模块内部接口的语义来源、Code 维护者、消费者及变更影响 | 不得取得 Helper 或领域契约定义权 |
| Schema 维护 | 每个 Code 侧 Schema 表示的语义来源、唯一维护位置、生成或同步方式及消费者 | 不得复制出多个相互独立的语义权威 |
| 错误与诊断 | 失败如何跨边界传播、在哪里补充诊断上下文、哪些信息必须避免泄露 | 不得用日志存在代替失败处理 |
| 风险与测试 | 关键成功、失败和边界风险对应哪些测试检查范围、真实依赖或 test double，以及哪些范围暂未验证 | 不得用单一测试命令或覆盖率数字代替风险分析 |
| 演进与缺口 | 已知偏移、待决定事项、允许的临时边界、重新评估条件和残留风险 | 不得把有期限的实现取舍写成永久架构事实 |

本文不指定规划文件的名称、目录、图示方法或工具。规划可以位于能够被当前实现者和后续 AI 稳定定位、与 Code 变化同步维护的版本化实现说明中；它不是规则源，不得覆盖当前有效规范或外部契约。

### 5.3 规划深度

规划深度必须与变更影响匹配：

| 变更类型 | 最小处理 |
|---|---|
| 首次实现或新的跨模块能力 | 覆盖 §5.2 的完整相关内容，并建立初始风险与测试映射 |
| 模块、依赖、接口或 Schema 变化 | 更新受影响责任、消费者、依赖和测试映射，检查相邻模块 |
| 局部行为变化 | 确认现有规划仍成立，补充本次行为和失败风险对应的测试 |
| 缺陷修复 | 定位缺陷穿过的责任边界，优先形成能够暴露该缺陷的回归测试，并检查同类风险 |
| 行为保持型重构 | 先确认预期保持的行为和现有证据，标明结构变化及其验证范围 |

规划规模本身不是目标。能够清楚支持实现与复核的最小充分内容优于大量复制源码、目录或未来设想的文档。

### 5.4 当前规划的定位与替代

Code 实现规划必须位于符合 `source-of-truth-traceability` 的管辖项目实际 Git Working Tree 当前文件中，并通过一个稳定的当前规划入口，使当前实现者和后续 AI 能够直接定位。尚未提交或尚未跟踪不使当前规划失效；规划及其入口应与对应 Code 一同进入后续版本历史。当前规划入口可以直接承载一份规划，也可以只列出当前适用的多份规划及其覆盖范围；它不得重新定义来源语义、复制规划正文或演变为模块与接口白名单。

每份当前适用的规划必须说明：

1. 覆盖的 Code 对象或范围，包括适用的模块、公共或跨模块接口、Schema 表示和副作用边界；
2. 开始形成该规划时所依据的实现起点：有可解析的 `HEAD` 时记录起点 commit；尚无历史锚点时明确说明，并记录作为起点的实际文件及范围；同时说明规划是否覆盖当前 Working Tree 中尚未提交或尚未跟踪的实现变化；
3. 与其它同时适用规划的共同部分、细化部分和明确不覆盖内容；存在重叠时，必须说明如何共同读取以及哪个文件负责更具体的内容，不得让两份规划对同一责任给出冲突要求；
4. 替代旧规划时，旧文件指向新的当前位置并明确不再承担当前规划责任；旧规划可以保留为历史，但不得与替代文件并行证明当前设计；
5. 当前规划入口、规划正文和真实实现发生影响定位、覆盖或组合关系的变化时，必须在同一实现增量中同步更新。

本文不固定当前规划入口或规划文件的目录和名称。每份当前适用的 Code 实现规划必须能够通过稳定入口定位；改变该位置时，旧入口必须留下能够定位新入口的信息。

## 6. 模块责任与依赖方向（Module Responsibilities and Dependency Direction）

1. 每个模块必须有可说明的内聚责任和维护边界。一个模块可以承担彼此紧密相关的一组行为，但不得只因调用方便持续吸收无关解析、业务判断、I/O、环境适配和输出包装；
2. 模块边界应使变更原因、失败范围和测试入口能够被隔离。新增能力需要修改一个中心模块中的多个无关分支时，必须检查该模块是否已经成为过度聚合入口；
3. 规划必须明确模块间允许的依赖和调用方向。实现不得通过访问内部文件、全局状态、隐式注册或跨层回调绕过已声明边界；
4. 模块依赖不得形成无人承担的循环。发现新循环时，必须先明确逻辑所有者和边界，再选择消除循环、引入明确接口，或记录平台约束下无法消除的最小循环及其测试；不得让偶然 import 顺序成为正确性条件；
5. 多个入口消费同一稳定语义时，应优先由一个共享维护位置提供确定性实现或生成结果。跨语言、跨进程、安全隔离或其它实际边界确实需要独立实现时，必须共同回到同一语义来源，并通过单向生成、同步检查或一致性测试防止漂移；只有输入协议或输出能力不同的部分留在各自边界层；
6. 外部依赖、文件系统、网络、进程和其它副作用应在可识别边界中调用，使核心判断可以测试，并使失败、超时、部分结果和回滚能力不被隐藏；
7. 公共 facade 或统一入口可以存在，但它只组织调用和结果，不得成为所有领域行为、Schema、环境协议和诊断的第二维护位置；
8. 模块粒度不由行数单独决定。拆分后如果只增加跨模块跳转、重复上下文和同步维护，而没有改善责任、依赖、测试或导航，则不因“文件必须小”而拆分。

## 7. 接口与 Schema 维护责任（Interface and Schema Maintenance）

### 7.1 语义来源与实现维护分开

来源规范或外部契约定义领域接口、公开接口及其 Schema 的业务语义；Code 实现规划分配相应实现、转换、生成、校验和兼容处理的维护责任。纯内部技术接口和只服务实现的数据结构可以由 Code 实现规划定义技术语义，但不得改变、缩窄或扩大其承接的外部和领域语义。Code 类型定义、常量、测试数据和 validator 都不得因更容易修改而取得外部或领域语义权威。

Code 可以检查正式来源已经定义的精确身份、规范化值、结构、关系和确定性条件；自然语言是否语义等价、规则责任是否重复、适用范围如何解释以及内容应否合并，仍由 AI 判断。涉及规则选择、授权、状态推断、语义汇总、完成声明、回退或跨来源聚合的 Code 增量，AI 必须把实现的每项结论回指正式来源，审核 Code 是否把候选、缺失、未知或机械差异越权提升为来源未定义的语义结论。

上述审核要求用于阻止 Code 越权，不构成建设语义审计 Code 的需求。本文所称 AI 判断或复核，是 AI 执行者在 Code 之外直接回读正式来源作出的判断，不得由 Code 调用、封装或编排模型执行或模拟。AI 复核只能识别并阻止越权，不能授权 Code 生成正式来源未以确定性规则定义的语义结论、候选、诊断或建议。

准备实现一个外部或领域接口时，对应来源必须当前有效且足以支持本增量。来源缺失、仍为草案或存在冲突时，可以继续调查、制作不承诺语义的原型或准备测试框架，但不得把推测字段和行为实现成已支持契约。

### 7.2 唯一维护责任

1. 每个公共接口和跨模块内部接口必须有一个可定位的 Code 维护责任，能够说明谁负责其实现定义、消费者影响和变更同步；
2. 每一种 Schema 语义在 Code 内应有一个明确的主要表示或生成入口。其它类型、常量、文档片段、test fixture 或传输结构如果由它派生，必须能回到该入口和语义来源；
3. 无法生成而必须手工维护多份表示时，规划必须明确唯一编辑位置、同步方向和能够发现漂移的检查；不得让多份表示互相循环证明正确；
4. Schema 转换必须保留来源允许的未知、缺失、无效和部分信息边界，不得为了适配内部类型而虚构默认值或缩窄外部语义；
5. 改变接口或 Schema 表示前，必须识别当前消费者、兼容影响、迁移或同时切换边界以及对应测试。本文不要求固定版本策略，但不允许静默破坏已声明支持的消费者；
6. 删除接口、字段或兼容分支前，必须在已声明支持范围和已识别消费者集合内取得退出依据，或由相应来源允许删除；“搜索不到直接调用”不能单独排除动态、生成或环境消费者，无法观察的消费者风险必须如实保留。
7. 安全或信任边界相关的环境构造（包括 Git 子进程环境隔离）必须由一个共享实现负责；不同调用方的差异只能通过显式参数化表达，不得复制后各自增补或遗漏隔离规则。无法共享而确需独立实现时，必须按 §6 第 5 项回到同一来源，并以一致性测试覆盖受保护输入及其阻断结果。

### 7.3 接口验证边界

接口与 Schema tests 可以证明当次生产者、消费者、转换和校验满足被测试的来源样例与约束；它们不能反向定义来源语义，也不能单独证明真实环境已经触发、所有未来消费者兼容或整个能力可用。

### 7.4 确定性检查与 AI 行动边界

Code 不得建立穷举 AI 全部行动、工具名、命令名或厂商事件名的许可白名单，也不得以“未分类”“未知工具”或“未登记动作”作为全局默认拒绝理由。Helper 公开操作、行动模板、事实状态、接口字段和某项机械 Git Gate 或 Hook Gate 的闭集，只能在其正式来源定义的局部契约内实现。

来源已经把某一原生事件的机械合格条件封闭定义时，Code 可以对该事件的实际候选执行确定性 allow/block；分类必须绑定来源规则、原生事件、真实目标、候选将产生的副作用和本次候选输入。工具名、命令名或事件名可以作为解析输入，但不能单独证明行动语义、授权、风险或阻断条件成立。无法取得来源要求的候选输入时，只能按该来源对同一事件规定的失败方式处理，包括来源明确要求时对该次事件 fail-closed；不得把阻断扩张到其它工具调用、只读调查、推理、沟通或普通求解。

规范候选、原文、组合上下文、来源指纹和内容摘要可以由 Code 按 01 与 04 确定性形成，用于帮助 AI 读取和发现规则源漂移；Code 不得据此自动决定自然语言规则与当前任务相关、当次全部适用来源已经找全、Human Gate 或 Stop Conditions 是否命中、Human 回应是否构成具体授权、验证是否充分或行动是否允许。AI 对这些问题的判断记录属于当次语义判断，不能仅因具有固定字段、摘要或实现可解析形式而被 Code 提升为机械真值。

本文不定义全部行动共用的 action envelope、preflight receipt、授权 token、统一允许状态或运行时状态机。某项来源已封闭定义的机械 Git Gate 或 Hook Gate 确需候选输入 DTO 时，该结构由相应来源在同一事件边界内定义，只承载确定性检查所需的瞬时输入；它不得成为事实对象、Human 决定证据、跨工具通行证或其它行动的默认前置条件。缺少通用 receipt、未登记工具名或没有匹配行动模板，本身均不构成 Code 阻断普通求解的来源。

### 7.5 工作上下文交付的核心与环境入口边界

LDVH 核心依照当前规则源已定义的信息交付规则组织规则引导与事实读取。尚未进入规则源定义的事实分支时，核心不得读取、恢复、聚合或推断项目事实；进入事实分支后，核心只调用该分支允许的事实读取能力，并如实保留已交付范围、未交付范围和来源所定义的 coverage。规则或事实已经取得，不构成相关性、规则适用、授权、完成或事实充分性的结论。

环境 Hook、承担环境接入的插件和 adapter 是核心的稳定薄引用：它们只传递原生事件实际提供的输入、调用其稳定引用的核心，并如实映射核心结果。它们不得自行读取规则或事实、恢复或补造事实、从任务文字、路径、缓存或父上下文推断事实、选择信息分支，或作出相关性、规则适用、授权、充分性及完成判断。

核心不能承接的输入、能力或环境范围，应由结果如实呈现未交付或不兼容范围；环境入口不得另行调用其它读取、恢复或旧行为以制造表面可用。

## 8. 错误、诊断与可观察性（Errors, Diagnostics, and Observability）

1. 错误必须在最接近其确定来源的位置保留原始原因，并在跨越模块边界时补充当前操作、受影响对象或范围以及必要的调用上下文；不得只留下无法定位的通用失败文本；
2. 模块只能在能够恢复、转换为来源契约允许的结果，或补充上下文后继续传播时捕获错误。静默吞掉、返回虚假成功、用空值掩盖未知或无条件回退旧路径均不成立；
3. 诊断应能区分输入无效、能力不支持、依赖不可用、内部错误、部分成功和取消等实际不同的失败原因，但本文不建立通用错误码或状态闭集；
4. 诊断至少应使复核者能够定位发生失败的能力或边界、实际输入范围、受影响对象、已完成与未完成部分以及可以继续核对的来源位置；具体字段和展示方式由对应接口及实现决定；
5. 可观察信息必须与风险和排障需要匹配。不得为了“可观察”记录完整敏感输入、凭据、私密路径内容或不必要的个人信息；必要信息应经过最小化、脱敏或安全引用；
6. 日志、trace、异常、诊断文件和测试输出只是其实际产生范围内的当次信息，不因格式结构化或长期保存而自动成为规则、稳定事实、验证通过或完成证明；
7. 事实未请求、读取范围不足、来源不可读、事实冲突、能力不支持、输入不足或环境不兼容，均应按相应来源定义的实际原因、范围和可继续核对入口呈现；不得统称为“降级”，不得由此虚报成功、掩盖未交付范围或改走其它旧行为。
8. 诊断路径本身必须测试。只测试成功返回、不测试错误传播、上下文保留和敏感信息边界，不能证明诊断设计成立。

## 9. 复杂度、重构与设计偏移（Complexity, Refactoring, and Design Drift）

### 9.1 重构评估触发

出现以下任一信号时，必须对受影响 Code 进行重构评估，而不是继续无条件叠加：

1. 一个文件或模块承担多个无关责任，或者因不同来源、接口和副作用频繁以不同原因变化；
2. 新增普通能力仍需修改同一个巨型 facade、长条件链、全局注册表或共享可变状态；
3. 出现循环依赖、跨边界绕行、内部结构被远端模块直接访问，或依赖方向与规划相反；
4. 同一解析、Schema、错误映射、权限判断或受控操作在多个位置重复维护；
5. 单元或组件行为无法隔离测试，任何局部变化都必须搭建大量无关依赖或运行全系统；
6. 缺陷、回归、失败诊断或合并冲突反复集中在同一边界；
7. 文件、函数或依赖图的规模与复杂度已经使 Human 或 AI 难以在合理上下文内理解影响范围；
8. 项目已有经证据支持的局部度量阈值被触发，或者当前对象显著偏离同类模块；
9. Code 实现规划、真实依赖、接口、Schema 维护位置或测试映射已经不一致。

行数、圈复杂度、依赖数量、变更频率和覆盖率都可以作为发现风险的信号，但任何单一数字都不能自动证明设计错误或健康。本文不设置“超过 5000 行即失败”等无上下文全局阈值；即使未触发数字阈值，只要责任、耦合、测试或导航已经失控，仍必须评估。

### 9.2 评估结果

重构评估必须形成以下一种可解释结果：

1. 在当前增量前或当前增量中先完成必要重构；
2. 先补充能够保护预期行为的特征测试、接口契约测试或回归测试，再重构；
3. 把行为变化和结构变化保持为可分别理解、可分别验证的范围；
4. 有边界地暂缓，并记录暂缓原因、受影响范围、残留风险、不得继续扩大的边界和重新评估条件；
5. 证据表明当前结构仍然合适，记录检查范围、成立理由和重新评估信号后保持现状。

不能只写“技术债以后处理”而不说明范围与触发条件。重构不得把当前偶然行为自动固化为正确契约；预期保持的行为必须回到对应来源和当次事实核对。

### 9.3 设计偏移

改变模块责任、依赖、接口、Schema 维护、诊断或测试策略的实现变更，必须在完成声明前与当前 Code 实现规划比较。出现偏移时只能：

1. 修正实现回到已经确认的规划；或
2. 在继续相应实现前更新规划，说明改变原因、消费者影响、新风险和测试变化。

未经处理的偏移只影响依赖该设计结论的最小实现与声明范围，不自动阻止无关工作；但不得用“Code 已经这样写了”反向证明规划应当如此。

## 10. 风险驱动测试与测试检查范围

### 10.1 风险决定测试选择

每个实现增量必须在编码或重构前识别可能失败的行为和边界，并据此选择测试。风险分析至少考虑适用项：

1. 失败影响，包括规则误判、数据损坏、越权副作用、信息泄露、不可逆变化和错误完成声明；
2. 发生可能性，包括新代码、复杂分支、外部依赖、并发、平台差异、模糊输入和历史回归；
3. 变化范围，包括受影响模块、接口、Schema、消费者、环境边界和兼容路径；
4. 可检测性，包括错误是否容易被局部测试发现、是否只能在真实组合或目标环境暴露；
5. 恢复难度，包括是否可以安全重试、回滚、隔离或缩小影响范围。

测试投入、检查范围、数据、技术和覆盖深度应由这些风险决定，不按文件数量或固定比例平均分配。风险低且已有稳定覆盖的局部修改可以使用较小测试集合；高影响、跨边界或不可逆能力必须取得与其风险相匹配的多范围证据，或者明确保持未验证。

每次运行 Code tests 前，主控 AI 必须按 00 §9 先记录实际变更对象、可能破坏的规则/结构/契约/消费者、所选检查及理由、未检查范围和全量回归触发判断。修改 Code 时必须运行与风险匹配的相关 Code tests；只有修改共享的机器消费 Schema、接口或契约，变化跨越多个实现边界，影响范围无法可靠收窄，§10.1 风险分析认定风险高，或者当前适用来源明确要求时，才为相应完成声明取得或复用全量回归结果。全量回归不替代对聚焦风险场景的选择；未命中时不得仅以“更保险”为由扩大到全量回归或无关 Helper tests。同一 Working Tree 快照上仍覆盖当前差异的有效结果必须复用；Code 和测试 runner 不得代替 AI 判断测试充分性。

### 10.2 测试检查范围

本文使用以下 LDVH 本地检查范围帮助选择证据边界，不把它们声称为行业标准中的 test levels，也不规定目录、runner、框架或固定比例：

| 检查范围 | 主要检查对象 | 证据边界 |
|---|---|---|
| 局部组件行为 | 单个函数、类或内聚模块在受控依赖下的行为、边界和失败 | 只证明该组件与 test double 假设下的行为 |
| 接口契约 | 生产者与消费者之间的接口、Schema、转换、错误和兼容约束 | 证明被测双方与样例范围，不证明全部真实依赖可用 |
| 真实组合 | 两个或以上真实模块、存储、进程或依赖的协同 | 只覆盖实际接入的组合、配置和环境 |
| 公开入口贯通 | 从真实公开入口穿过主要内部路径得到的整体结果 | 证明受控实现边界内的当次能力，不自动证明外部环境真实触发，也不表示覆盖全部执行分支 |

外部运行环境的真实事件、安装和自动触发可以成为某项能力所需的更外层验证，但其成立条件和结论属于对应环境或来源契约，不由本文的 Code 测试检查范围替代。

根级 `docs/` 是临时说明材料，不属于 LDVH 能力、环境接入、发行或实现验证的测试输入；tests 不得以其存在、缺失、文件名、内容、打包状态或新旧程度断言能力可用、`ready`、已接入、已发布或实现通过。Human 明确要求处理某份临时材料时，可以只检查该材料自身，但该结果不构成上述任何结论的证据。

回归测试（regression tests）、特征测试（characterization tests）、基于性质的测试（property-based tests）、模糊测试（fuzz tests）、性能测试、安全测试、并发测试和兼容性测试描述测试目的或技术，可以出现在不同检查范围。本文不要求每个增量全部使用，而要求风险与所选检查范围、目的和真实依赖范围能够对应。

### 10.3 测试用例边界

1. 准备让新增或修改逻辑通过当前公开入口正常调用、执行高影响副作用，或把相应实现增量视为完成前，必须覆盖主要成功路径，以及与风险相关的反例、边界、缺失或未知输入、依赖失败、部分结果和错误传播；
2. 缺陷修复应在可行时先形成能够暴露原缺陷的测试，并检查相邻输入或同类路径；无法稳定复现时必须说明替代依据和残留范围；
3. 测试断言只能固定当前有效的正式来源已经定义的可观察行为和边界。评审意见、现有实现、fixture、快照或测试断言本身都不是规则来源；除非内部结构本身是本次工程风险，不应让测试过度绑定偶然调用顺序、私有字段或当前文件布局；
4. 测试必须具有缺陷敏感性：如果被保护的行为被破坏，测试应当失败。只执行代码而没有有效断言、只确认命令退出成功或只生成快照，不能自动证明风险已覆盖；
5. 使用 mock、stub、fake 或其它 test double 时，必须明确替代了什么真实依赖。仅有 test double 的通过结果不得表述为真实集成、真实文件系统、真实进程、网络或环境已经验证；
6. 测试应可重复运行并隔离无关状态。flaky、依赖执行顺序或偶然外部状态的测试是测试缺陷；在修复或明确隔离前，不得用其偶然通过支持稳定结论；
7. 静态类型、lint、格式化、Schema 校验和覆盖率可以补充测试，但不能替代实际行为、失败路径和集成边界检查；
8. 多个公开操作共用同一请求、响应或 Schema 契约时，共同字段与共同规则必须由一个共享 validator、生成结果或公共契约测试入口验证。具体操作测试复用该入口，只补充自身 `arguments`、`result`、特殊结果和风险场景；不得在每个操作测试中复制全部共同字段与断言。共享测试辅助设施只承接来源契约，不得成为第二套接口语义或业务逻辑；
9. 正式来源定义的确定性入口存在把机械结果越权提升为语义结论的回归风险时，tests 必须选择能够暴露该越权的最小反例。不得为测试 AI 的语义判断新增 Code 路径，也不得按固定输入类别重复建测；正式来源未定义的语义等价、规则适用、授权、完成或责任归口不得成为测试预期。
10. 实现涉及行动分类、Git Hook、环境 Hook、Git Gate、Hook Gate、adapter 或权限判断时，tests 必须证明局部 Gate 只影响来源绑定的同一事件与候选，并成对覆盖两类反例：实际 payload、权威环境语义或可观察副作用能够证明为无关只读的行动，即使工具或命令名称未登记，也不会仅因名称未知被全局阻断；已经进入来源定义的 Gate，但候选绑定、必需输入不可验证或发生来源定义的身份漂移时，仍按该来源只对同一事件 fail-closed。测试不得通过不断扩充允许名称列表来满足前一反例，也不得为避免全局阻断而取消后一反例的局部 Gate。
11. 实现工作上下文规则引导、事实读取或环境接入入口时，tests 必须证明：
   （1）核心的默认入口只执行当前规则源定义的规则引导，并明确事实为 `not_requested`；不得调用事实读取或恢复能力，规则选择不得随任务文字、cwd、工作对象、缓存或父上下文变化；
   （2）只有核心进入当前规则源定义的事实分支后，才可以调用事实读取能力；tests 必须覆盖其实际读取范围、coverage 与 `partial` 等来源状态，并证明规则交付或部分事实读取未被提升为事实完整、规则适用、授权或完成；
   （3）环境 Hook、环境接入插件和 adapter 只传递原生事件实际输入、调用稳定核心引用并如实映射结果；以依赖隔离或调用记录证明其没有读取规则或事实、没有恢复事实、没有选择事实分支，也没有在核心未承接时调用其它策略；
   （4）输入不足、能力不支持、事实范围不足、事实冲突、来源不可读或环境不兼容，必须分别保留其实际原因和未交付范围；不得建立或测试名为“降级”的通用状态、路径或结果。

## 11. 测试同步与证据边界（Test Synchronization and Evidence Boundary）

### 11.1 测试映射与同步

Code 实现规划必须把关键模块、接口、Schema 和风险映射到主要测试检查范围，并说明哪些依赖真实运行、哪些被替代。发生下列变化时，相关 tests 必须在同一实现增量中更新或明确证明无需变化：

1. 来源要求或可观察行为变化；
2. 模块责任、依赖方向或副作用边界变化；
3. 公共或跨模块接口、Schema 表示或生成关系变化；
4. 错误传播、诊断或敏感信息处理变化；
5. 修复缺陷、移除兼容行为或完成重构；
6. 发现现有测试错误、过时、重复、flaky 或无法暴露被保护缺陷。

Code tests 自身属于 Code，必须遵守适用的责任、依赖、可维护性和敏感信息边界。其它职责域 tests 的物理归属由相应职责规范定义；其规范把本文列为直接依据时，共同遵守本节适用的测试工程要求。测试辅助设施不得成为另一套业务逻辑或 Schema 权威。

“明确未验证”只用于缩小证据和能力声明，不能替代本节要求的 Code tests。必要 tests 尚未补齐时，相关实现只能保留为与当前公开入口和高影响副作用隔离的原型或明确未完成内容；不得把它接入正常调用路径、用于执行高影响副作用或视为该实现增量已经完成。真实外部环境暂时不可验证时，可以继续标明相应环境范围未验证，但仍须完成不依赖该环境即可成立的 Code tests，并且不得把 Code tests 冒充为真实环境验证。

### 11.2 测试证据

准备使用测试结果支持结论时，至少必须能够回答：

1. 测试了哪个 Code 对象、Working Tree 内容、版本或构建；
2. 选择了哪些测试检查范围、用例和风险，为什么足够支持当前声明；
3. 使用了什么关键环境、配置、真实依赖和 test double；
4. 哪些测试通过、失败、跳过、隔离或未运行；
5. 结果覆盖哪些行为、接口、Schema、失败路径和平台；
6. 哪些范围仍未测试、不可观察或存在残留风险。

对于“全量测试”或任何准备支持全范围通过、可用或完成声明的测试会话，以上信息必须由可回读的单一运行记录承载。记录至少包含稳定 `run_id`、启动时间、原始合并输出的固定位置、每个检查步骤及其 argv/工作目录、最终 exit code、结束时间和最终状态；状态只能是 `running`、`passed`、`failed` 或 `unknown`。启动端、终端会话、UI 回传或日志流中途断开时，不得根据已见输出推断通过；若不能通过 `run_id` 回读带最终 exit code 的终态，结果必须是 `unknown` 且 `evidence incomplete`，不得用于声明全量通过。原始输出因截断、缺失或无法读取而不能复核时，同样必须缩小为 `unknown`。

准备用 full-v4 结果说明“当前 Working Tree 已通过”时，单一运行记录还必须原样携带 `working-tree-test-evidence-fields` 定义的 Working Tree 证据 DTO。它以实际 worktree 中受固定政策覆盖的当前普通文件 bytes 为输入，不以 tracked、staged、committed、ignored、`HEAD` 或单一 `dirty` 标志替代。只有原始输出及终态证据完整，且该 DTO 的 `status` 为 `complete`，全量运行才能使用 `passed` 或 `failed`；DTO 为 `stale` 或 `incomplete` 时，必须保留已执行步骤与诊断，但全量运行最终状态为 `unknown`，不得把局部失败或已见通过扩大为当前 Working Tree 结论。旧运行记录没有该 DTO 时，可继续在原有边界内回读其步骤与输出，但不得追溯性补造或声称已完成当前 Working Tree 内容绑定。

LDVH 当前工作树的全量验证唯一规范入口是 `tools/run_full_tests.py start --plan full-v4`，并以 `tools/run_full_tests.py status --run-id <run_id>` 回读。该入口以脱离启动终端的 worker 执行固定检查计划，并将记录与原始输出存入被忽略的 `.ldvh-test-runs/<run_id>/`；直接执行局部 runner 可以用于开发诊断，但没有该记录时不得充当全量通过证据。`probe` 计划仅用于验证回读机制，不得充当产品测试结果。

本次 A 增量只冻结附件的结构、政策、指纹和纯比较责任；它不表示当前 runner 已实现文件遍历、安全读取、before/after 采集、运行记录接入或过期状态的识别与处置。这些生产责任属于后续 Working Tree 证据实现；Human、Helper、Web 和 Codex 的投影只能消费该 DTO，不得重算指纹、改写状态或建立第二 Schema，相应展示和交互不属于本次 A 增量。

具体命令、报告格式和保存位置由真实实现与适用来源决定。只有测试名称、测试文件静态存在、runner 返回成功、覆盖率数字或 Human 认可，均不能单独回答上述问题。

### 11.3 可证明范围

1. 聚焦测试通过只证明受控依赖下的局部行为；契约测试通过只证明被测接口组合；集成或系统测试通过也只覆盖当次配置、环境和路径；
2. 覆盖率只说明某种度量下代码被执行或条件被观察的比例，不证明断言有效、需求完整、边界正确或不存在缺陷；
3. 没有失败不等于所有风险已测试；跳过、隔离、flaky 和未运行必须从通过范围中排除；
4. Code tests 不能单独证明 Helper 外部契约已经生效、环境已经 integrated、Human Gate 已完成、事实已经正确写入或整个工作已经完成；
5. 测试结果需要跨行动或会话长期保留时，必须按相应来源规则进入允许的稳定位置；测试输出本身不因被保存而扩大证明范围。

## 12. 外部工程资料的选择与吸收

外部标准、官方工程指南、论文、书籍或厂商实践可以帮助发现候选要求，但不得直接成为 LDVH 规则。准备以外部资料支持新增或改变稳定工程要求时，必须：

1. 优先定位标准组织、规范维护者、研究发布方或实践发布方的一手来源；
2. 记录来源身份、版本或发布日期、观察时间、适用对象和来源自身的限定；
3. 区分国际标准、共识性知识、组织内部实践、培训材料、研究结论和个人意见，不把它们统一称为“行业标准”或“最佳实践”；
4. 对照 LDVH 的 Code 角色、AI 第一服务对象、来源权威和当前实现约束，说明适用、不适用和需要调整的部分；
5. 检查是否会引入固定技术栈、过度流程、无上下文阈值、第二规则源或与当前来源冲突；
6. 只有候选要求被正式规范正文或其已授权附件明确吸收并完成相应审核后，才取得 LDVH 规则效力。

调查记录、链接、外部文档、Code review 意见或 tests 不能替代正式吸收。没有可靠一手来源时，不得声称某项要求是行业最佳实践；仍可基于 LDVH 自身问题和 V1-V8 净价值提出内部规则，但必须如实说明其内部来源。

## 13. 代表性工程场景

| 场景 | 本文要求 |
|---|---|
| 一个 Code 文件已经超过 5000 行 | 行数触发重构评估，但不自动决定按文件、类或固定层拆分；先识别责任、依赖、接口、Schema、失败和测试边界，再确定拆分或有边界暂缓 |
| 新 Helper 字段尚无当前有效来源 | 可以调查影响和准备非承诺原型，不得由 Code 或 tests 把猜测字段实现成外部契约 |
| 同一 Schema 在三个模块分别手写 | 明确语义来源和唯一 Code 维护入口；其它表示改为生成或建立单向同步检查 |
| 每个 Helper 操作测试都复制完整共同响应断言 | 由共享 validator、生成结果或公共契约测试统一覆盖共同字段；操作测试只保留操作专属 Schema、结果和风险，避免复制后漂移或形成冗长测试 |
| facade 只转发调用但文件较大 | 检查导航、变更和测试负担；若责任仍单一、依赖清楚且拆分净收益不足，不因行数单独拆分 |
| facade 同时解析规范、写事实、安装环境并包装诊断 | 属于多责任与跨边界聚合，必须在继续扩展前评估模块拆分和依赖方向 |
| 全部测试使用 mock 且通过 | 只能证明 mock 假设下的局部行为；若风险涉及真实解析、文件、进程或环境，必须增加相应检查范围或真实依赖覆盖，否则标记未验证 |
| 重构同时改变行为 | 必须让行为变化和结构变化可分别理解与验证；无法区分时不得声称只是行为保持型重构 |
| 外部指南推荐固定测试比例 | 先记录来源和适用性；本文不因外部比例存在而建立统一测试金字塔或覆盖率门槛 |
| 新增一个只读工具后 Git Gate 或 Hook Gate 因名称未登记而阻断 | 这是全局行动白名单回归；删除默认拒绝与按名称外推，改为只检查来源明确绑定的原生事件、实际候选、目标和副作用，并用未知名称反例防止复发 |
| 某一 Git Gate 对 commit 事件执行闭集检查 | 只对该次 commit 的实际候选按来源输出 allow/block；该闭集不授予或禁止 AI 的其它工具调用、调查、编辑或沟通 |

| 接口与 Schema 维护 | 新增或改变接口、Schema 表示、生成或兼容处理时 | 语义来源有效，Code 维护责任唯一，消费者和同步方向清楚，未知与失败边界未被改写 | 来源契约、维护映射、生成或同步结果、contract tests | 来源回读、Schema/contract tests 和消费者检查 | 当次接口、表示与已识别消费者 | 不实现未定义语义；修正重复维护、漂移或兼容缺口 |
| 确定性 Gate 与 AI 行动边界 | 新增或修改行动分类、Git Hook、环境 Hook、Git Gate、Hook Gate、adapter 或权限判断时 | Code 未建立全局 AI 行动、工具或命令白名单；机械判断绑定来源定义的同一事件、实际候选、目标和副作用；未知名称及无关行动不会被外推阻断 | 00、实际来源、实现与配置、已知/未知工具或命令样例、allow/block 与诊断 | Code review、negative tests、同一事件测试及需要时真实环境触发 | 当次机制、来源、原生事件、候选和受测无关行动 | 隔离受影响实现，删除默认拒绝和名称白名单，按事件与实际副作用重新限定并测试 |
| 工作上下文交付与环境薄引用 | 新增或修改工作上下文核心、事实读取分支、环境 Hook、接入插件或 adapter 时 | 默认核心路径仅交付规则，事实读取仅在规则源定义的核心事实分支发生；环境 Hook、接入插件与 adapter 只作原生输入和核心结果映射 | 当前规则源、核心调用记录、原生输入、核心结果、环境映射与来源状态 | 默认路径调用记录、事实分支测试、环境入口 negative tests 与来源回读 | 当次核心、事实分支、环境入口与已交付范围 | 默认路径出现事实读取、环境入口读取规则或事实、选择分支、作语义判断，或核心不能承接时隐去未交付或不兼容范围、改走旧策略或虚报成功的，停止受影响交付并修正 |
| Code 来源语义边界 | 新增或修改规则选择、授权、状态推断、语义汇总、完成声明、回退或跨来源聚合时 | 每项语义结论都能回指正式来源；AI 已在 Code 之外审核机械结果没有被提升为来源未定义的结论；存在回归风险时，最小负向 tests 只固定来源已定义的可观察边界 | 当前规则源或适用外部契约、Code 实现规划、源码差异、AI 复核记录和必要的最小负向 tests | 来源回读、AI 设计与 Code review，以及必要的 contract tests 或 negative tests | 当次检查的实现结论、来源和反例；AI 复核记录只证明已执行边界审核，不授权 Code 语义结论，也不证明未检查 Code 均未越权 | 暂停受影响实现或声明；把结果恢复为来源允许的非结论边界，或者先修正正式来源、实现和 tests |
| 错误与诊断 | 新增失败路径、捕获、回退、诊断或可观察信息时 | 原始原因和必要上下文可定位，部分结果未被虚报成功，敏感信息未被不必要暴露 | 失败输入、诊断输出、错误链、脱敏检查和 negative tests | 组件、contract、integration tests 及安全复核 | 当次被触发的失败路径和输出范围 | 不用错误结果支持能力声明；修正吞错、误映射或泄露 |
| 重构评估与设计偏移 | 命中 §9.1 信号或实现改变规划时 | 已形成 §9.2 的明确结果；预期行为和结构变化可验证；规划与实现已重新一致 | 度量和变更历史、依赖与责任分析、规划差异、特征测试与回归测试 | Code review、依赖检查、测试和规划回读 | 当次重构对象与检查过的相邻边界 | 暂停继续叠加或完成声明；先测试、重构、更新规划或有边界暂缓 |
| 风险驱动测试设计 | 实现、修复或重构前选择 tests 时 | 主要成功、失败、边界和高影响风险已经映射到适当检查范围，真实依赖与 test double 范围清楚 | 风险清单、测试映射、来源要求、历史缺陷和变更影响 | 测试设计复核及对应 test collection | 当次识别的风险与选择的测试范围 | 补充必要 Code tests；未补齐时隔离相应实现，只有真实外部环境范围可以继续明确标记为未验证 |
| Tests 质量与同步 | Code、接口、Schema、诊断或测试自身变化时 | 相关 tests 同步更新，断言能暴露目标缺陷，结果可重复，flaky/skip 未被算作通过；共同契约断言由共享入口承接，具体操作测试没有复制全部共同字段形成第二维护点 | test diff、共享契约测试、故障注入或反例、重复运行结果和测试报告 | 实际 runner、变异或故障检查、Code review | 当次运行的 tests、共享契约和环境 | 修复或隔离测试缺陷，合并重复共同断言；必要 tests 缺失或陈旧时隔离相应实现，不接入正常调用路径，并从证明范围中排除不可靠结果 |
| 测试证据与声明 | 使用 tests 支持实现、可用或完成结论时 | 对象、版本、检查范围、环境、真实依赖、结果、跳过和未验证范围可回指，声明未超出证据 | Working Tree/版本、调用与报告、环境信息、失败和残留风险 | 实际 tests、回读和 AI 对照声明审核 | 当次对象、版本、环境和被执行路径 | 缩小或撤回声明；补充实际测试或标记未验证 |
| 外部资料吸收 | 声称行业标准、最佳实践，或准备新增稳定工程要求时 | 一手来源、版本、观察时间、适用性和冲突已经核验；要求已由正式规则源吸收 | 调查记录、原始来源、适用性比较和规范变更 | 来源回读、语义审核和需要时独立复核 | 当次候选要求及其明确采用范围 | 保持为调查输入，不作 LDVH 规则或行业结论 |

本文所涉 Code 实现规划、模块边界、tests、runner 与自动化检查的能力声明，按 00 §9 及上表对应验证对象判断。

## 15. Human Gate

本文不要求 Human 逐项批准普通模块拆分、内部接口设计、测试用例或重构方案；这些属于 AI 与实现维护者在当前规则和授权范围内的工程判断。

本文不新增独立于 00 和实际来源规则的 Human Gate。出现以下情况时，分别按已有来源进入 Human Gate：

1. 准备改变 Code 作为确定性执行能力的上位概念、Helper CLI、Git Hook、环境 Hook、Git Gate 与 Hook Gate 的实现层关系，或测试证据边界等 00 上位语义；
2. 多个实现方向会改变 Human 已确认的外部产品范围、不可逆技术承诺或受控副作用，而当前来源不能替 Human 选择；
3. 准备接受高影响残留风险、长期保留已确认的严重设计偏移，或在验证范围不足时继续作出相应声明；
4. 实际来源规则明确把某项接口、风险接受、兼容退出或验收决定保留给 Human。

Human 回应可以决定方向和风险取舍，但不能使缺少来源的接口或 Schema 取得语义，不能替代 Code 实现规划、实现修正和测试，也不能扩大测试证据的可证明范围。

## 16. Stop Conditions

出现以下任一情况时，必须暂停受影响的最小 Code 实现、变更或声明范围：

1. 首次实现或命中 §5.1 的变化尚无相应 Code 实现规划，或者准备在实现完成后再补写规划；
2. 准备实现的 Helper、领域、事实、行动或环境语义没有当前有效来源，存在冲突，或 Code 正在自行补造契约；
3. 模块责任、依赖方向、公共接口或 Schema 维护责任不唯一，存在无人承担的循环或跨边界绕行，却准备继续叠加功能；
4. 真实实现与当前 Code 实现规划已经偏移，且尚未修正实现或先更新规划；
5. 错误被静默吞掉、部分失败被返回为成功、未知输入被猜测，或诊断正在泄露不必要的敏感信息；
6. 已命中重构评估条件，但没有形成 §9.2 的任何明确结果，或者使用单一行数、复杂度或覆盖率数字替代责任与风险判断；
7. §10.3 或 §11.1 要求的 Code tests 缺失、陈旧或不能暴露被保护缺陷，却准备把相应实现接入当前公开入口或正常调用路径、用于执行高影响副作用，或把相应实现增量视为完成；
8. test double、静态检查、覆盖率、flaky、skip 或局部测试结果正在被冒充为真实集成、真实环境、全范围通过或完成证明；
9. 外部建议尚未核验来源和适用性，或者只存在于调查记录、Code 或 tests 中，却正在被表述为 LDVH 规则、行业标准或最佳实践；
10. 无法确认测试结果对应哪个 Code 对象、版本、环境或未验证范围，却准备使用该结果支持结论。
11. Code、tests 或配置把 Helper 操作、行动模板、工具名、命令名、事件名或其它局部闭集扩张为 AI 全部行动白名单，或仅因名称未知、未分类、未登记而阻断来源没有约束的普通求解。
12. Code、tests 或配置正在建立全部行动共用的 envelope、receipt、授权 token、允许状态或运行时状态机，或者把 AI 自述、规则读取摘要、上下文 coverage、Human 回应的 AI 转述或未漂移状态提升为自然语言适用判断、Human 决定证据或行动允许。

暂停范围与可继续行动按 00 §11 执行；对本文而言，只读调查、来源核对、规划补充、依赖分析、测试设计、最小复现和诊断修复可以在不越过受影响边界时继续。

只有与触发原因对应的来源已经成立、规划已经先行补齐、责任与依赖已经明确、设计偏移已经处理、诊断或测试缺口已经修复，或者声明已经缩小到现有证据实际支持的范围后，受影响工作才能恢复。
