# V4 Git 提交行动模板准入与 V3 边界调查

> 记录性质：本文是 `specification-model-foundation` §13.5 要求的新规范责任判断记录，不是规则源，不授予 Git 提交权限，也不表示 Helper、Git 写入、Hook、Skill 或环境接入已经成立。初始判断者为 GPT SOL；记录形成时间为 2026-07-15（Asia/Shanghai）。两轮独立复核、定点小修、Code 规划、通用声明解析、风险匹配 tests 和激活检查均已完成；30 已转为 `active`，其效力仍以 01 的其余当前规则源资格条件同时成立为前提。

## 1. 调查目标

本次不先假定需要名为“Git 提交行动模板”的独立规范，而审核以下规则对象是否具有独立承载价值：

> 当 Human 已明确要求在一个可确定的 Git worktree 中创建本地新 commit 时，AI 如何在不复制 Git、项目、测试和授权规则的前提下，重复组织目标范围确认、当前状态读取、适用规则定位、验证、目标提交快照形成、commit 创建、写后回读和结果交还。

本次重点回答：

1. 上述行动结构是否在移除领域规则、项目策略、实现命令和单次目标后仍然成立；
2. 应由现有 02、03、06、07，项目规则、Code/tests、Skill 或独立普通规范中的哪一处承载；
3. V3 的 Git 提交行动资产中哪些边界可保留，哪些不得恢复；
4. 首个 V4 具体行动模板能否用该场景验证 06 的“基础规范 → 具体模板”机制。

## 3. V3 的实际处理方式

V3 已经尝试把 Git 提交拆成五类责任：

| V3 位置 | 实际责任 |
|---|---|
| 03 与 `03.Att.01` | Git 溯源和全局 commit message 字段、type/scope、body 条件 |
| 31 | Git 状态读取、范围判断、拆分、验证、message 形成、提交和交还的薄行动入口 |
| Skill | 将 31 转成环境中可触发的执行步骤，并重复部分 message 与 validator 细节 |
| Code/Hook | commit message 机械校验和 commit-msg 触发 |
| WorkCase 0004 | 记录 31 落地、资产同步、独立复核和 Human 关闭过程 |

V3 的明确设计意图是：31 只接管行动执行责任，不复制 commit message 本体规则。WorkCase 0004 的多路复核也确认了这一分工。

但 V3 最终仍产生以下耦合：

1. 把 Conventional Commit 风格、中文 description、type/scope 闭集和 body 小标题提升为 LDVH 全局契约；
2. 31 把“单一主意图”“必须运行 validator”“多类文件必须写 body”等项目或契约政策当作通用提交行动要求；
3. Skill 再次展开 type/scope、body、命令和 validator 规则，形成从规范到模板到 Skill 的同步链；
4. Hook、Skill runtime、validator 和行动模板的存在容易被误读为环境已经接入或提交已经获权；
5. 固定 Context、Scenario、Gate、执行、验证、回写、交还七结构造成模板形态重于当前 V4 06 所需的语义结构；
6. 对修改 specs、Code、tests、Web 等普通提交普遍增加 Human Gate，超出“只有真实保留决定才交给 Human”的当前边界。

## 4. V3 内容的 V4 处置

| V3 内容 | V4 处置 | 理由 |
|---|---|---|
| 31 是薄行动入口，不定义 message 契约 | 保留 | 准确区分规则与行动组织 |
| 提交前读取目标 repo、Working Tree、Index 和必要 diff | 保留 | 是稳定行动输入和范围判断，不是项目政策 |
| 区分 staged、unstaged、untracked 和用户已有变更 | 保留 | 防止把无关变化混入提交或破坏用户状态 |
| 定位并消费实际适用的项目、测试和 message 规则 | 保留 | 模板负责组织读取，不复制规则 |
| 提交前形成并核对实际目标快照 | 保留 | 防止计划范围和实际提交范围漂移 |
| 提交后回读 commit 和剩余 Working Tree | 保留 | 区分命令成功、实际历史锚点和剩余变化 |
| commit 不等于验证、工作完成、push 或 PR | 保留并回指 03 | 防止扩大结果声明 |
| 全局 Conventional Commit/type/scope/body 契约 | 不恢复 | 属于项目策略或另行证明的正式规则，不是所有 V4 项目的普遍要求 |
| 一次 commit 必须只有单一主意图 | 不作为全局闭集恢复 | 提交拆分是项目策略和当次判断；模板只在范围无法由当前目标和来源确定时暂停 |
| 固定七结构 | 不恢复 | 当前 06 只要求语义内容可定位，不要求固定阶段或表形 |
| 强制 `commit_validate.py`、Hook 或固定命令 | 不恢复 | 当前 V4 没有相应公开契约和能力证明；工具入口只能按实际来源与可用性消费 |
| 修改 specs/Code/tests/Web 一律进入 Human Gate | 不恢复 | 文件类别不自动产生 Human 保留决定；以实际授权、风险和来源 Gate 为准 |
| AI 完成修改后自动提交 | 不恢复 | 修改授权不自动包含创建 commit；模板适用不扩张授权 |
| Skill 中复制 message 和 validator 细节 | 不恢复 | 环境入口不得形成第二模板或第二规则源 |
| push、PR、amend、rebase、merge、tag、Hook 安装 | 排除 | 副作用、授权和失败边界不同，应普通求解或另行审核模板责任 |

## 5. 扣除现有来源后的候选规则

首轮独立复核指出，初稿把 01 和 03 已经定义的提交前 Index 检查、提交后 `HEAD` 回读和证明边界也计入了 30 的独有价值。按 01 §13.1 重新扣除后的结果如下：

| 候选内容 | 已有来源承担 | 30 的剩余责任 |
|---|---|---|
| 当前 Working Tree、Index、`HEAD`、history 和 commit message 的作用与证明边界 | 01 §6.3、03 §§7–9 | 不重定义；只把这些视图组织为当次提交行动输入和回读依据 |
| 模板适用不等于授权、步骤成功不等于完成、Human 不能替代技术验证 | 06 §§6–8 | 不重定义；只说明它们在本地新 commit 场景中的具体停止和交还位置 |
| Human 对当次本地新 commit 的授权 | 06 §6.2 与 Human 当前指令 | 30 只要求明确取得，不允许项目规则、模板命中或修改完成替代授权 |
| repo/worktree 身份与管辖解析 | 02 | 30 只消费能够唯一绑定的结果，不重定义解析规则 |
| message、branch、签名、拆分、Hook 和测试门禁政策 | 项目或领域正式来源 | 30 负责定位、记录实际检查范围并消费，不补造政策 |
| Human 目标变化与既有 staged、unstaged、untracked 变化的归属组合 | 尚无来源完整承担 | 30 唯一定义：在提交行动中区分目标、既有和来源不明变化 |
| 在不改写用户既有 Index 的前提下形成目标候选快照 | 尚无来源完整承担 | 30 唯一定义：隔离条件、无法隔离时停止、只撤销本次可归属临时变化 |
| 项目规则、目标候选快照和范围匹配验证的组合关系 | 尚无来源完整承担 | 30 唯一定义：三者必须共同覆盖同一提交候选，不能各自成立却对象错位 |
| commit 后目标相关残留、无关变化和实际历史结果的分别交还 | 01/03 定义视图与证明边界，06 定义一般交还 | 30 唯一定义 Git 特有的残留分类和继续入口 |
| 既有 Hook 随 Git 自动触发后的拒绝、修改或部分结果 | Git 环境事实与项目来源 | 30 唯一定义在本行动中的回读和分流；不安装、修改、禁用或绕过 Hook |

扣除后，30 的独有规则只包括：

1. 在 Human 已明确授权本地新 commit 后，把当次目标变化与既有或来源不明的 staged、unstaged、untracked 变化分别归属；
2. 在不丢弃、覆盖或静默改写用户既有 Index 和 Working Tree 变化的前提下形成只覆盖已授权目标的候选快照；无法安全隔离时停止；
3. 使候选快照、实际检查到的项目/领域规则和范围匹配验证指向同一对象与版本；
4. 把既有 Hook 的实际触发结果作为 Git 执行条件回读，不把“模板未主动调用”解释为“Hook 未执行”；
5. commit 后分别交还实际历史结果、目标相关残留、既有无关变化、验证缺口和未执行的远端或历史改写行动。

这些剩余规则具有 Git 提交行动特有的组合关系和失败分流；01、03、06 单独存在都不能自然替代该组合，但它们继续分别承担底层事实、证明和共同模板规则。

| 位置 | 比较结果 |

| 01 正文章节 | 01 已定义规范候选的 Working Tree/Index/`HEAD` 边界及规范提交前后检查；它不适用于任意项目变化，也不承担目标变化归属、用户既有 Index 保护或提交行动分流 |

| 06 正文章节 | 06 只定义全部模板的共同规则；放入 Git 步骤会使基础规范夹带具体实例 |

| 项目正式规则 | 适合承载 message、branch、签名、Hook、测试门禁和拆分政策；不适合反复复制通用读取、执行、回读与交还结构 |

| 独立普通规范中的具体行动模板 | 能以稳定 `template_key` 定义独立适用、失败、验证和交还边界，并只引用其它规则；当前为净负担最低的候选位置 |

## 7. 正反例与独立失败场景

### 7.1 正例

1. Human 明确要求提交本轮修改，目标 repo 和文件范围清楚；AI 使用模板读取规则、核对差异、执行验证、创建本地 commit 并回读交还。
2. 工作树同时包含本轮目标变化和用户既有无关变化；模板要求隔离目标范围并保留剩余状态，不把无关变化静默提交或丢弃。
3. 项目具有自己的 message 或 branch 规则；模板定位并消费该来源，但正文不复制具体格式。
4. 项目没有额外 message 规则；模板只要求 message 对实际快照和验证据实，不自行恢复 V3 全局 Conventional Commit 契约。

### 7.2 反例

1. 用户只询问 Git 状态、message 规则或提交建议，不要求创建 commit；不进入状态变更步骤。
2. 用户要求 push、创建 PR、amend 或 rebase；这些行为不因命中本模板自动获权。
3. 目标不是 Git worktree，或目标 repo、worktree、提交范围无法唯一确定；模板不能猜测。
4. 一次性紧急操作不满足模板的身份、授权、范围或能力条件；不因名称相似强制套用模板。

### 7.3 独立失败场景

1. 01/03 的视图规则都正确，但 AI 漏读用户已有 staged 变化，把无关修改提交；
2. 各项目规则和验证都正确，但对应的是 Working Tree 或旧版本，没有共同覆盖实际候选快照；
3. AI 为隔离本次目标改写了用户既有 Index，失败后又以“恢复”为名重置或覆盖原有 staged 内容；
4. 既有 Hook 拒绝或修改了提交，AI 却按原计划 message 或预期结果交还；
5. commit 实际形成，但目标相关变化仍残留，AI 只报告新历史锚点而遗漏剩余工作；
6. commit 没有形成或结果不可观察，AI 却把 Git 调用、模板命中或 Hook 存在当成成功。

这些错误发生在已有视图、项目规则和 Git 能力均可能正确的情况下，失败点是目标、Index、候选快照、验证、环境结果和交还之间的行动组合，因而不能仅靠 01、03、06 或 Git 命令自然消除。

## 8. V1–V8 与净价值

1. V1：稳定定位本次需要读取的工作对象、Git 状态、项目规则和验证入口；
2. V2：把 Human 目标、实际差异、暂存快照、验证和历史锚点联系起来；
3. V3：区分规则、授权、Working Tree、Index、commit、push、PR 和完成声明；
4. V4：减少把目标、用户既有 Index、项目规则和验证对象错配的推进错误；
5. V5：在 03 的证明边界之上，防止对实际候选、Hook 结果和目标残留作超范围声明；
6. V6：补充 Git 特有的 commit 身份、目标残留、既有无关变化和可继续入口；
7. V7：清楚区分实际提交、未提交目标、既有变化、已验证和未验证范围；
8. V8：将高频提交行动的稳定组织方式维护在单一来源，而不是复制到 Skill、Agent 或项目说明。

新增成本包括一份普通规范、模板发现、跨 02/03/06 与项目来源的读取和后续维护。扣除已有来源后，主要收益只来自避免误纳既有 Index、验证对象错位、忽略既有 Hook 实际结果和遗漏目标残留。若正文能够收缩到这些组合关系，其收益高于重复提交场景中每次重新建立关系的成本，正净价值暂时成立；若第二轮复核仍发现这些规则可以由现有来源自然承接，则应取消候选，而不是为保留编号继续扩写。

## 9. 首轮独立复核与主执行者处置

首轮复核由独立于初始判断的 GPT SOL subagent `review_spec30` 于 2026-07-15（Asia/Shanghai）完成。复核主动尝试由 01、03、06、项目规则、Code 和普通求解承接候选，并给出“修改后再审，当前不得转为 `active`”的结论。本次复核只形成分析，不修改文件。

| 复核意见 | 主执行者裁决 | 本次处置 |
|---|---|---|
| 未扣除 01 已定义的提交前 Index 和提交后 `HEAD` 规则 | 接受 | 重写 §5、§6、§7.3 和 §8，只把 Git 特有组合计为独有价值 |
| Human 授权与“其它来源授权”矛盾 | 接受 | 统一为 Human 当前明确授权；项目规则只提供限制和允许条件 |
| Human Gate 可能绕过强制门禁 | 接受 | 明确只有来源保留风险接受权时才可决定，不可绕过规则只能补验、改目标、取消或修改权威来源 |
| 未处理既有 Hook 自动触发 | 接受 | 区分“不得安装/修改/禁用/绕过”和“Git 可能自动执行既有 Hook”，增加回读与分流 |
| “恢复原有状态”可能改写用户 Index | 接受 | 收紧为只撤销本次可归属且可验证的临时变化，恢复后必须回读；否则不动 Index 并停止 |
| “没有项目规则”缺少发现范围 | 接受 | 要求保留已检查来源、作用范围、不可读取范围和缺口，只能声明有限搜索结果 |
| 正文偏厚，重复 03/06 | 接受 | 将共同证明、授权和能力边界缩减为来源回指，仅保留 Git 特有进入、组合、分流和交还 |
| 未覆盖 detached、unborn 或无首个 commit | 接受 | 输入和分流改为 branch/`HEAD` 状态，显式覆盖这些场景 |
| “普通求解成本更低”作为单次排除条件过于主观 | 接受 | 从单次不适用条件移除，只保留在模板维护和退出判断中 |
| 缺少成功、失败、部分结果走查 | 接受 | 在 §10 增加代表性语义走查，不把它们写入规范正文成为一次性实例 |

主执行者未拒绝任何实质意见。首轮复核证明独立规范仍有较高可能，但没有证明准入已经完成；所有修改必须经第二轮独立复核重新挑战。

## 10. 代表性场景走查

以下走查只验证候选结构，不授予真实 Git 操作权限，也不声称实际命令已执行。

### 10.1 成功结果

Human 明确要求把当前任务变化创建为本地 commit。目标 worktree 唯一；初始观察确认 Index 无既有无关变化，Working Tree 中目标与无关变化可区分；已检查项目规则来源和验证入口均可读取。执行者形成只含目标的候选快照，验证覆盖该快照，既有 Hook 没有拒绝或修改结果；commit 后回读到新的实际历史锚点，目标相关变化无残留，无关 Working Tree 变化仍保留。模板可以报告本地 commit 成功，同时明确没有执行 push 或 PR。

### 10.2 失败并保持无状态变更

Human 已授权本地 commit，但初始观察发现用户既有 staged 内容与本次目标在同一文件中交叠，当前能力不能在不改写既有 Index 的情况下形成可验证候选。模板在创建 commit 前停止，不通过 reset、清理、隐藏或猜测范围继续；交还冲突范围、未创建 commit、未改变既有 Index，以及需要 Human 调整目标或提供安全能力的入口。这一失败发生在 Git 和项目规则本身均可用时，证明隔离关系具有独立失败边界。

### 10.3 部分结果

Human 已授权且候选快照形成，Git 创建了本地 commit；既有 Hook 在执行中修改了实际 message，提交后回读还发现一部分目标相关 Working Tree 变化未进入 commit。模板保留实际 commit 身份和实际 message，明确交还已提交范围、目标残留、既有无关变化与验证覆盖，不把原计划 message 或“任务全部完成”当成事实。不得自动 amend、再次提交或 push；后续行动需要按当前授权和来源重新判断。

### 10.4 既有 Hook 拒绝

候选和验证已经形成，但 Git 自动执行的既有 Hook 拒绝 commit。模板不禁用、绕过或修改 Hook，不把命令调用解释为 commit 已形成；回读确认没有新历史锚点，交还 Hook 的实际可观察诊断、候选仍处位置和可以修正规则要求或保持暂停的入口。

### 10.5 detached、unborn 与无首个 commit

detached `HEAD`、unborn branch 或尚无首个 commit 不自动适用或排除。模板必须先读取实际 branch/`HEAD` 状态；项目规则若禁止相应状态则停止，允许且其它条件成立时按实际不存在的旧历史锚点形成候选和回读。不得为满足“当前 branch”或“前一个 commit”字段而伪造值。
