## 1. 本文解决的问题

本文只解决 LDVH 如何使用 开发环境的问题，包括：

1. Rules、Skill、Agent 在 LDVH 中分别承载什么；
2. AI 在 LDVH 场景下如何选择 Rules、Skill、Agent；
3. LDVH 如何用 AskUserQuestion 承载 Human Gate；
4. LDVH 如何处理 RunCommand、Schedule、MCP 等 Trae 工具的事实源边界；
5. Trae 机制产生的过程信息如何回写为 LDVH 稳定事实。

本文不解决以下问题：

1. Trae 平台能力的完整说明；
2. Trae 工具参数契约的完整手册；
3. Trae 官方最佳实践或教程复述；
4. 直接修改既有 Skill 实体以修补单次执行问题；
5. 其他项目的 Skill、Agent、Rules 清单迁移；
6. 外部参考资料向 LDVH 强制规则的直接提升。

## 2. 与 00 总纲的关系

00 定义开发环境是 LD Vibe Harness 的四类构成要素之一，并明确 LDVH 对开发环境的态度是利用、不重新定义、规范不替代和适配不绑定。

本文承接该判断，将 开发环境视为 LDVH 的执行底座和协作入口。LDVH 只定义自身如何治理、调用和回写这些机制，不替代 Trae 平台本身。

## 3. 权威领域

本文是以下 LDVH 特殊约定的唯一事实源：

1. Rules / Skill / Agent 的 LDVH 选择边界；
2. Rules、Skill、Agent 在 LDVH 中的事实源边界和治理要求；
3. AskUserQuestion 在 LDVH 中实现 Human Gate 的触发和问询设计要求；
4. RunCommand、Schedule、MCP 等 Trae 工具在 LDVH 中的回写约束；
5. Trae 机制输出进入 Git 文件事实源的规则。

Trae 平台能力、参数契约和平台限制不属于本文权威领域，应引用 `specs/refs/trae/`。

## 4. LDVH 与开发环境的关系

LDVH 对开发环境遵循以下原则：

1. **利用不重新定义**：LDVH 定义如何使用 Trae 能力，不重写 Trae 能力定义；
2. **规范不替代**：LDVH 规范是使用约定，不替代 Trae 官方文档和 refs；
3. **适配不绑定**：LDVH 可适配 Trae Solo，但不把 Trae 设为唯一 AI 编程环境；
4. **机制不等于事实源**：Rules、Skill、Agent、工具调用和对话输出都是运行机制或过程信息，不自动成为稳定事实；
5. **稳定事实必须回写**：稳定结论、规则、任务、证据、决策或变更必须写入 specs/、ldvh-base/、docs/ 或其他对应 Git 文件事实源。

## 5. Rules / Skill / Agent 选择边界

本节是 AI 判断“这件事应该放入 Rules、Skill 还是 Agent”的 LDVH 唯一对比事实源。Trae 对 Rules、Skills、Agent 的平台定义见 refs：

- Rules：`specs/refs/trae/01-Rules规则机制.md`
- Skills：`specs/refs/trae/02-Skills技能机制.md`
- Agent：`specs/refs/trae/03-Agent智能体机制.md`

LDVH 分工原则：本节负责“选谁”，各机制章节只定义“选定之后如何治理和检查”。

| 机制 | 适合承载 | 不适合承载 | LDVH 进入条件 |
|---|---|---|---|
| Rules | 必须遵守、绝对禁止、事实源边界、Human Gate 入口、工作区规则/项目规则入口、具体对象规则入口指引 | 大段教程、完整 SOP、低频流程、角色隔离分析、外部资料全文、对象字段契约正文、状态机正文 | 需要长期稳定约束 AI 或人；LDVH 只维护工作区规则和项目规则两类 Rules 入口，不使用场景规则 |
| Skill | 可复用多步骤流程、标准化输入输出、轻量评估、受控写入流程 | Human Gate 判断本身、稳定规则正文、独立上下文或并行委派 | 流程可复用、可在主上下文执行、边界和输出稳定 |
| Agent | 独立上下文、结论隔离、并行委派、不同权限边界、长期专业入口 | 简单问答、单文件小改、可由 Skill 完成的流程、仅包装角色名称 | 主上下文或 Skill 不足，且存在隔离、并行或权限差异需求 |

选择顺序：

1. 能通过稳定约束解决的问题，优先进入 Rules；
2. 需要可复用流程但可在主上下文完成的问题，进入 Skill；
3. 需要独立上下文、结论隔离、并行委派或不同权限边界的问题，才考虑 Agent；
4. 不能因为某个流程“看起来专业”就升级为 Agent；
5. 不能因为某个步骤“经常出现”就写入 Rules，若它是流程，应优先判断 Skill；
6. 不能在正式规范中提前创建具体 Skill 清单或 Agent 清单，除非对应工作模型主规范、工作流程主规范或机制实体定义已稳定支撑。

### 5.1 选择判断流程

判断某项内容应由哪类机制承载时，应按以下流程处理：

1. 先判断它是否是长期稳定硬约束；若是，优先进入 Rules 或 specs 正式规范；若不是，不得仅因高频出现就写入 Rules；
2. 再判断它是否是可复用流程；若流程多步骤、输入输出稳定且可在主上下文执行，优先进入 Skill；若只是一次性操作，不应创建 Skill；
3. 再判断它是否需要独立上下文、结论隔离、并行委派或不同权限边界；只有主上下文或 Skill 不足时，才考虑 Agent；
4. 最后判断是否需要创建新的机制资产；若现有 Rules、Skill、Agent 已能覆盖，应优先引用或复用。

### 5.2 常见误判纠偏

以下判断不得作为进入某类机制的充分理由：

1. 高频出现不等于应写入 Rules；若本质是流程，应优先判断是否进入 Skill；
2. 多步骤不等于必须创建 Skill；若流程不可复用、输入输出不稳定或只服务单次任务，不应创建 Skill；
3. 专业名称不等于应创建 Agent；只有存在独立上下文、结论隔离、并行委派或权限差异时，才考虑 Agent；
4. 重要信息不等于可以停留在 Skill 或 Agent 输出；稳定事实必须回写 Git 文件事实源；
5. 机制入口不等于最终事实源；Rules、Skill、Agent 是执行机制或协作入口，不替代 specs/、ldvh-base/、docs/ 等事实源。

### 5.3 机制章节引用纪律

本文各机制章节可以描述各自机制内部的设计条件、文件结构、命名规则、生命周期、权限边界和检查项，但不得维护另一套跨机制选择规则。

涉及机制边界时，应遵守：

1. 可以写“已拟使用本机制后如何设计、治理和检查”；
2. 必须引用本文 §5 作为跨机制选择依据；
3. 不得复制本文 §5 的三机制对比表；
4. 不得新增与本文 §5 不同的选择顺序；
5. 不得用章节局部检查项覆盖本文 §5 的跨机制判断；
6. 如发现章节边界描述与本文 §5 不一致，应修改对应章节，使其回到引用关系。

## 6. Rules 机制 LDVH 特殊约定

Trae Rules 的平台定义、生效方式、子目录规则、AGENTS.md 兼容性和 Git Commit Message 规则见 `specs/refs/trae/01-Rules规则机制.md`。本文只定义 LDVH 如何使用 Rules。

### 6.1 规则分层

LDVH 的规则体系由规范层和通道层共同构成：

```text
规范层：LDVH specs
  ├─ 00 理念与纲要
  ├─ 01-03、10-14 基础规范
  ├─ 20-39 工作模型规范
  └─ 40-59 工作流程规范

通道层：工作区规则 → 项目规则 → specs 原文
  工作区规则：跨项目桥接 —— 声明基础规范来源、项目识别机制、项目规则读取机制、管辖项目配置和压缩保护
  项目规则：声明项目定位、必读入口、目录事实源边界、项目专属硬约束和对象规范入口
  specs 原文：承载对象字段契约、状态机、工作流程、Human Gate 规则和结构化契约章节
```

LDVH 不使用场景规则作为规则层或例外机制。任何长期稳定约束必须归入 specs 正式规范、工作区规则或项目规则；局部、临时或外部平台适配约束不得在 LDVH 中新增 `.trae/rules/` 场景规则文件承载，应转为项目规则摘要、工作区规则摘要、Skill 流程、refs 参考或当前任务的一次性执行条件。

各层职责：

| 层级 | 典型位置 | 职责 | 禁止 |
|---|---|---|---|
| 规范层 | `specs/` | 定义 LDVH 通用规范、对象规则和工作流程 | 绑定单一管辖项目的临时事实 |
| 工作区规则 | 工作区根 `.trae/rules/ldvh-workspace-rules.md` | 跨项目桥接、项目上下文识别、项目规则读取机制、管辖项目配置和压缩保护 | 展开完整规范正文、承载单项目约束或复制对象契约 |
| 项目规则 | 项目 `.trae/rules/ldvh-project-rules.md` | 项目定位、必读入口、项目专属硬约束、对象规范入口和事实实例编辑硬约束 | 重复规范层或工作区规则已定义内容、复制对象规范正文 |
| specs 原文 | `specs/` 对应主规范及结构化契约章节 | 字段契约、状态机、关闭条件、Human Gate 细则和工作流程正文 | 被 Rules 摘要替代或在 Rules 中二次维护 |

### 6.2 Trae Rules 生效方式映射

LDVH 规则只分为工作区规则和项目规则，同时必须映射 Trae Rules 的真实生效方式。Trae 的 globs、description 或手动触发能力是平台能力，不构成 LDVH 场景规则层；LDVH 不使用这些能力新增场景规则文件。具体 Trae 生效方式以 `specs/refs/trae/01-Rules规则机制.md` 为准。

| LDVH 规则类型 | 推荐 Trae 生效方式 | LDVH 用途 |
|---|---|---|
| 工作区规则 | 始终生效 | 跨项目桥接、项目识别、基础规范入口和压缩保护 |
| 项目规则 | 始终生效 | 项目定位、项目专属硬约束、事实源边界、必读入口和对象规范入口 |
| Git 提交规则 | Git 提交消息场景 | 仅用于提交消息生成 |

`#Rule` 手动触发优先于自动匹配。Git 提交消息规则不得由普通 alwaysApply、globs 或 description 替代。

### 6.3 项目规则读取机制

AI 读取某个项目目录下的文档或代码文件时，应先识别项目上下文并读取该项目规则。会话期间同一项目规则已读取过的，可以不重复读取。

执行顺序：

1. 从文件路径判断所属项目；
2. 检查会话中是否已读取该项目规则；
3. 未读取时，先依据工作区规则识别规则入口，再读取项目 `.trae/rules/ldvh-project-rules.md`；
4. 根据项目规则必读入口读取必要核心文档和对象规范；
5. 编辑 `ldvh-base/` 事实实例时，必须按项目规则中的事实实例硬约束回到对应 specs 原文和结构化契约章节。

项目规则必读入口应区分读取粒度，不得因“必读”而默认全文读取所有文档。规范文档和工作模型规范应先搜索章节标题定位，再按行范围读取目标段落。

### 6.4 规则唯一事实源

同一规则只能有一个权威位置。其他规则文件或文档需要使用该规则时，只能引用权威位置或保留压缩摘要，不得复制维护完整规则正文。

Rules 是 specs 正式规范的运行时投影，可以承载入口摘要、压缩保护和项目专属硬约束。Rules 不得长期承载具有跨环境复用价值的框架级原则正文；当工作区规则或项目规则中出现新的长期原则、框架级约束、机制边界判断或跨环境复用规则时，应先回流到对应 specs 正式规范，再由 Rules 保留摘要和规范引用。

典型归属：

| 规则类型 | 权威位置 |
|---|---|
| LDVH 理念、构成要素和基础规范索引 | `specs/00` |
| specs 编号、文档类型和引用纪律 | `specs/03` |
| 目录事实源性质声明 | `specs/01` |
| 事实源边界和回写原则 | `specs/04` |
| Trae 机制总体边界 | `specs/05` |
| Rules 机制规则 | `specs/05` §6 |
| 管辖项目定义和术语边界 | `specs/02` |
| 工作区桥接规则 | 工作区规则 |
| 管辖项目配置 | 工作区规则 |
| 对象规范入口和事实实例编辑硬约束 | 项目规则 |
| 项目专属硬约束 | 项目规则 |
| 字段契约、状态机和工作模型细则 | specs 对应主规范及结构化契约章节 |
| 局部文件类型或执行条件约束 | specs、项目规则、工作区规则、Skill、refs 或当前任务一次性执行条件，按内容性质归位；不得新增场景规则承载 |

### 6.5 Rules 与机制落地关系

普通 specs 文档与 Rules 实体的关联关系，应由对应 specs 文档依据 `specs/03-文档规范.md` §6 的机制落地关系维护。

Rules 文件头部应声明规范来源和维护边界。规范来源用于说明该 Rules 文件摘要、触发或约束的权威 specs；维护边界用于说明该 Rules 文件只作为运行时入口或压缩摘要，不替代 specs 正式规范。

20-39 工作模型和 40-59 工作流程与 Rules 的关系，不再通过固定 NN.01-Rules.md 或场景规则结构承接。具体工作模型或工作流程如需运行时入口，应在对应主规范中说明入口摘要、触发条件和权威引用，并同步到项目规则或工作区规则；不得同步到 `.trae/rules/` 的场景规则。

审计现有工作区规则或项目规则时，不得只检查已有 Rules 文件本身，还必须从 specs 根目录正式文档反向发现 Rules 需求。需要修改 Rules 文件时，只能加入必要入口摘要和权威 specs 引用，不得复制 specs 正文或把 Rules 文件变成第二事实源。

### 6.6 规则设计约束

已拟使用 Rules 时，规则正文应短小、稳定、可检查、可引用、可执行。Rules 的写法必须吸收 Trae 官方最佳实践：单条规则保持聚焦，规则之间不得冲突或相互覆盖，路径引用优先使用项目根目录相对路径，规则内容应清楚描述 AI 需要执行的具体行为。

单个 Rules 文档正文有效内容不得超过 1000 字符；正文有效内容只统计承载行为约束、入口摘要、触发条件、压缩保护和权威引用的有意义文本，不统计标题、头部元数据、空行、表格分隔符、列表编号、Markdown 标记和纯格式字符。

规则正文不应包含：

1. 大段教程；
2. 完整 SOP；
3. 低频知识；
4. 长篇背景材料；
5. 工具使用手册全文；
6. 可由 Skill 按需加载的流程细节；
7. 可由 specs 正式规范承载的稳定规则正文；
8. 可由 refs 承载的外部资料；
9. 只表达理念但不能映射到具体 AI 行为的抽象口号；
10. 与同层或上层规则重复、覆盖或冲突的条目；
11. evals 文档的硬约束、必读入口或路由规则；
12. 尚未回流到正式规范且仅存在于 evals 中的原则或约束。

项目规则不得引用 evals 内容作为硬约束或必读入口。evals 中的有效原则应先回流到 specs 正式规范，再由项目规则保留摘要和规范引用。

AI 处理任务时，应先读取与任务主题相关的参考文档（`specs/evals/`、`specs/refs/`），包括产品方向、外部借鉴、技术评估等。参考文档读取是通用原则，不需要在项目规则中特别指向某个 evals 文件。

新增或修改 Rules 时，应优先判断内容是否可写成一句明确的运行时指令；若不能，应回到 specs、Skill 或 refs 重新归位。涉及事实实例、对象字段、状态机或工作流程的规则，应通过项目规则入口指向 specs 原文，不得新建场景规则。

新增或修改 docs/、specs/、ldvh-base/ 关键入口时，应同步检查项目规则必读入口是否需要更新。

### 6.7 规则变更流程

规则变更执行时应按以下流程处理：

1. 判断变更对象属于规范层、工作区规则、项目规则还是 Git 提交规则；
2. 判断是否触发 Human Gate；
3. 说明变更原因、影响范围和待修改文件；
4. 用户已批准的情况下修改对应规范或规则文件；
5. 同步检查引用、必读入口、对象规范入口和压缩保护；
6. 检查修改后的规则是否仍满足聚焦、无冲突、无重复覆盖、可执行和路径清晰要求；
7. 追加 Change 记录；
8. 执行一致性检查。

涉及规则文件删除时，不得仅按文件扩展名判断是否需要 Human Gate；凡删除 specs、Rules、ldvh-base 或其他事实源入口，应按高风险变更评估并执行 Human Gate。

## 7. Skill 机制 LDVH 特殊约定

Trae Skills 的平台定义、文件结构、动态加载、启用禁用、最佳实践等客观事实见 `specs/refs/trae/02-Skills技能机制.md`。本文只定义 LDVH 如何使用 Skill，以及 LDVH 如何生产、测试和修正 Skill。

LDVH 对 Skill 的治理原则是：先修正规范和生产方法，再修改 Skill 实体。Skill 执行中暴露的问题，不得直接通过临时改写 Skill 文档修补；应先判断问题属于规范缺口、工作流程缺口、工作模型缺口、测试用例缺口还是 Skill 实体实现偏差，再按对应事实源修正。

### 7.1 Skill 内部设计检查

跨机制选择依据本文 §5，本节不另行判断某项内容是否应优先进入 Rules、Skill 或 Agent。已拟使用 Skill 时，应检查该 Skill 是否满足以下内部设计条件：

1. 可复用，不是一次性临时操作；
2. 存在多步骤流程或稳定分支判断；
3. 需要标准化输入、输出或写入格式；
4. 可在主上下文中执行；
5. 有明确事实源读取和回写边界；
6. 不承载 Human Gate 判断本身；
7. 不承载稳定规则正文；
8. 不承载完整教程或外部工具手册；
9. 具体对象流程已有工作模型主规范、工作流程主规范或机制实体定义支撑；
10. 涉及既有 Rules、specs、工作模型、工作流程或 Human Gate 规范时，只列出适用入口、关键检查项或 STOP 点，不复制完整规范正文。

### 7.2 命名与部署边界

LDVH 提供的通用 Skill 应使用 `ldvh-` 前缀，避免与管辖项目业务 Skill 或外部 Skill 混淆。

| 项目 | LDVH 约定 |
|---|---|
| 目录名 | `.trae/skills/ldvh-{skill-name}/` |
| YAML `name` | 使用与目录一致的 `ldvh-{skill-name}` |
| 命名风格 | 小写字母、数字和连字符 |
| 禁止 | 不得使用其他项目前缀，不得绑定具体业务项目名 |

部署边界：

1. LDVH 通用 Skill 应部署在管辖项目 `.trae/skills/` 目录下，使用 `ldvh-` 前缀声明为全局可用，随项目一起版本管理；
2. 管辖项目业务 Skill 应部署在对应项目 `.trae/skills/` 位置，并不得使用 `ldvh-` 前缀；
3. Skill 实体文件是 Trae 执行入口，不替代 specs/、ldvh-base/ 或 docs/ 的事实源；
4. Skill 创建、修改、删除或迁移部署位置应评估 Human Gate；
5. 规范、工作模型主规范、工作流程主规范或机制实体定义引用 Skill 实体路径时，应明确该路径归属哪个管辖项目。

判断某个 `ldvh-*` Skill 是否已部署或可调用时，AI 必须检查部署边界、目录、`SKILL.md` 元数据、最小段落和 Human Gate 记录，不得只凭聊天记忆或其他项目目录判断。

### 7.3 Skill 文件结构要求

LDVH Skill 文件除满足 Trae 平台结构外，还应至少包含：定位、触发条件、不适用场景、输入、输出、必读文件、执行流程、失败处理、规则强调、输出格式、交还主控、Human Gate、事实源回写和 Agent 边界。

Skill 必读文件中的路径必须区分 LDVH 项目规范、工作区规则和管辖项目事实源，不得用“当前项目”等模糊表述掩盖路径归属。

Skill 的 `description` 应面向 AI 执行者说明能力和触发时机，不应只写角色名称、愿景口号或人类读者说明。触发条件与不适用场景应成对出现，避免 Skill 误触发、漏触发或覆盖其他机制。

Skill 提示词、Skill 文档和面向 AI 的 Skill 编排说明应使用中文，除非外部平台字段或技术标识必须使用英文。

### 7.4 Skill 内容引用原则

Skill 主体内容必须引用 specs 对应章节，不得在 Skill 文档中自成一派。具体要求：

1. 流程细节涉及规则、字段契约、状态机、Human Gate 条件和事实源回写要求时，必须引用对应 specs 章节；
2. Skill 只写触发条件、必读文件、关键检查项和 STOP 点，不写完整规范正文；
3. 当 Skill 文档与 specs 规范对同一事项有不同表述时，以 specs 规范为准；
4. specs 规范变更后，引用该规范的 Skill 应同步更新引用位置，但不需要同步复制变更内容；
5. Skill 不得在引用之外新增规则、字段、状态或约束；如需新增，应先在 specs 中定义，再在 Skill 中引用。

### 7.5 Skill 生产方法

创建或修改 Skill 前，应先确认 Skill 的上位依据已经稳定。Skill 生产方法按以下顺序执行：

1. 确认目标能力属于可复用流程，并通过本文 §5 判断不应进入 Rules 或 Agent；
2. 确认对应工作模型、工作流程、事实源边界、Human Gate 和回写要求已在 specs 中定义；
3. 将使用场景整理为工作流测试用例，覆盖正常路径、误触发路径、缺失上下文路径、Human Gate 路径和失败降级路径；
4. 依据测试用例提炼 Skill 的触发条件、不适用场景、输入、输出、执行步骤和失败处理；
5. 编写或更新 Skill 实体，仅保留入口、流程编排、关键检查和 STOP 点；
6. 运行工作流测试，检查 Skill 是否能稳定引导 AI 发现问题、停止越界动作并提出修正方向；
7. 测试失败时先判断是否需要修正规范、测试用例或生产方法，只有确认 Skill 实体与已稳定规范不一致时，才修改 Skill 实体。

### 7.6 Skill 测试准入

Skill 不应在缺少测试用例的情况下进入稳定使用。每个稳定 Skill 至少应具备以下测试覆盖：

1. 正常触发：用户输入符合触发条件时，AI 能进入正确 Skill；
2. 负例触发：用户输入属于不适用场景时，AI 不进入该 Skill；
3. 上下文读取：AI 能按规范读取最小必要事实源，不全文读取大型规范文档；
4. Human Gate：涉及写入、状态流转、删除、高风险变更或关键决策时，AI 能暂停并请求确认；
5. 事实源回写：Skill 输出中的稳定事实不会停留在聊天或工具缓存中；
6. 失败降级：缺少事实源、规范冲突、工具失败或权限不足时，AI 能停止、说明原因并交还主控。

工作流测试的定义、测试用例组织、自动化测试、AI 自发现和自修正边界由 `specs/10-工作流测试.md` 定义。本文只定义 Skill 机制自身的测试准入要求。

### 7.7 输出与事实源回写

Skill 输出不是最终事实源。Skill 产生的稳定结论、任务、备忘、证据、决策或变更，必须写入对应 Git 文件事实源后才成为稳定事实。

Skill 只完成一个受控流程，不负责全局调度。每个 Skill 在流程结束、暂停、失败、需要 Human Gate、需要 Agent 或建议进入下一个 Skill 时，必须显式交还主控。

### 7.8 Skill 与 Agent 边界

Skill 不得调度 Agent。Skill 发现以下情况时，应停止升级动作并提示用户或主控判断是否使用 Agent：

1. 主上下文难以承载所需事实源；
2. 需要不同角色独立形成结论；
3. 需要并行委派多个专业角色；
4. 需要与主上下文不同的权限边界；
5. 需要长期维护 Agent Prompt 或权限配置。

### 7.9 具体 Skill 清单原则

本文不维护 LDVH 标准 Skill 清单。具体 Skill 只有在满足对应工作模型主规范、工作流程主规范或工具实践已稳定，且输入、输出、事实源回写边界明确，并通过工作流测试准入后，才可进入 Skill 实体定义；对应主规范只保留触发摘要、适用条件和权威引用。

### 7.10 Skill 修正规则

当 Skill 使用中出现误触发、漏触发、越权写入、上下文过载、事实源遗漏、Human Gate 缺失或失败处理不清时，应按以下顺序修正：

1. 判断是否是 specs 正式规范缺失或冲突；若是，先修正规范；
2. 判断是否是工作流测试用例缺失；若是，先补测试用例；
3. 判断是否是 Skill 生产方法未覆盖该类问题；若是，先修正本文或 `specs/10-工作流测试.md` 中的方法规则；
4. 判断是否是 Skill 实体未遵守已稳定规范；若是，才修改 Skill 实体；
5. 修改 Skill 实体后必须回跑相关工作流测试，防止修复单点问题却破坏其他路径。

不得把 Skill 失败直接等同于“需要改 Skill”。Skill 失败首先是规范、测试、生产方法和实体实现之间的一致性问题。

## 8. Agent 机制 LDVH 特殊约定

Trae Agent 的平台定义、内置智能体、自定义智能体配置、SOLO Agent、Plan / Spec 模式等客观事实见 `specs/refs/trae/03-Agent智能体机制.md`、`specs/refs/trae/06-Spec与Plan工作流程.md` 和 `specs/refs/trae/09-SOLO模式.md`。本文只定义 LDVH 如何治理 Agent。

### 8.1 Agent 创建或调用治理检查

跨机制选择依据本文 §5，本节不另行判断某项内容是否应优先进入 Rules、Skill 或 Agent。已拟使用 Agent 时，应检查是否满足以下治理条件：

1. 需要独立上下文；
2. 需要结论隔离；
3. 需要并行委派；
4. 需要不同权限边界；
5. 需要长期专业入口。

Agent 治理检查还应确认：

1. 不是仅为单次简单问答或单文件小改创建 Agent；
2. 不用 Agent 承载稳定规范正文、项目事实源正文或完整教程；
3. 不是仅为了包装角色名称；
4. Agent 创建、修改、删除或权限调整已按 Human Gate 处理。

### 8.2 调度规则

Agent 应被动响应用户显式调用或主控编排，不得自行触发。

LDVH 调度规则：

1. 用户可通过 Trae `@Agent` 显式调用已存在的 Agent；
2. SOLO Agent 或主控流程可在复杂任务中编排子 Agent；
3. 子 Agent 调度权只属于用户显式调用或主控编排，Skill、Tools、MCP、脚本或工具缓存不得直接发起子 Agent 调度；
4. 若某一工作流程已经定义子 Agent 流程入口，主控编排子 Agent 必须从该工作流程的 Rules 入口和主文档进入；
5. Skill 不得调度 Agent；
6. Agent 默认不调度其他 Agent，除非其定义和主控授权明确允许；
7. Agent 默认只读分析，除非输入上下文明确授权写入；
8. Agent 发现 Human Gate 场景时必须标注并停止相关修改；
9. Agent 输出应返回主控或用户，由主控决定是否写回事实源、是否进入下一个 Skill、是否触发 Human Gate 或是否结束流程。

### 8.3 Agent 定义摘要单一事实源

Trae 平台中的 Agent Prompt 是运行入口。LDVH 中已确认创建或导入的 Agent，应在项目 Git 文件事实源中维护定义摘要，避免关键行为只存在于平台配置中。

Agent 定义摘要应至少包含：Agent 名称、英文标识、角色定位、触发场景、分析关注点、职责边界、必读文档、输入输出、权限范围、Prompt 来源和维护状态。

Agent 定义摘要和 Trae 平台 Prompt 不得形成两个互相冲突的事实源。Prompt 应尽量引用定义摘要作为权威来源，只保留角色入口、执行约束和输出格式等必要内容。

### 8.4 生命周期

创建 Agent 时应检查治理条件、说明为什么 Rules、Skill 或主上下文不足、说明角色和权限边界、触发 Human Gate、在 Trae 中创建或导入 Agent、在 Git 文件事实源中维护定义摘要并记录变更。

修改 Agent 时应判断是否影响职责边界、触发条件、权限边界或 Prompt；涉及高影响变更时触发 Human Gate，并同步修改 Trae 平台配置和 Git 文件定义摘要。

删除或停用 Agent 时应确认不再被流程、规则、Skill 或文档引用，触发 Human Gate，并归档或更新 Git 文件定义摘要。

### 8.5 Agent 输出与事实源回写

Agent 输出不是最终事实源。Agent 输出中的分析、建议、证据、风险、任务拆分、决策建议或变更说明，只有写入对应 Git 文件事实源后才成为稳定事实。

回写规则：

1. specs 规范或 Rules 写入 specs/ 或 `.trae/rules/` 对应位置；
2. 任务、证据、变更、风险等结构化对象写入 `ldvh-base/`；
3. 管辖项目报告或审计结果写入 docs/；
4. 外部资料或 Agent 模板参考写入 specs/refs/；
5. Agent 输出与事实源冲突时，以 Git 文件事实源为准；
6. Agent 不得自行宣称任务完成，必须由主控或用户依据事实源和证据判断。

### 8.6 推荐清单处理原则

其他项目的推荐自建 Agent 清单、Trae 官方一键导入 Agent 示例和社区 Agent 模板，只能作为参考输入。LDVH 正式规范不得直接维护推荐自建 Agent 清单。

## 9. AskUserQuestion 使用 LDVH 特殊约定

AskUserQuestion 的平台定义和参数契约见 `specs/refs/trae/08-内置AI工具.md`。本文只定义 AskUserQuestion 在 LDVH 中何时触发、如何设计、如何降级和如何传递给 AI。

在 LDVH 中，AskUserQuestion 是实现 Human Gate 的首选技术方式。

### 9.1 触发场景

当工作流程规范、工作模型规范、项目 Rules 或当前任务语境定义 Human Gate 触发条件时，应通过 AskUserQuestion 实现用户确认。

当用户请求创建或修改事实源、执行 ADR 写入、事实对象状态流转、规范升级、高风险变更，或需要在 2-4 个互斥或可多选方案中选择时，AI 必须暂停拟执行动作并调用 AskUserQuestion；用户选择确认后才可继续执行，用户选择暂停、暂缓或取消后必须停止执行并等待后续指示。

### 9.2 问询设计规范

LDVH 问询应满足：

1. `question` 以 `?` 或 `？` 结尾；
2. 问题描述明确指向需要用户做的决策；
3. `header` 用 2-4 词概括问题类型；
4. 选项之间互斥，或在多选场景中清楚说明可组合；
5. 每个选项说明选择后果；
6. 选项覆盖所有合理选择，不遗漏取消、暂缓或暂停选项；
7. 需要推荐时，将推荐选项放在第一项，并在 label 末尾添加“(推荐)”；
8. 当问题可表达为 2-4 个互斥或可多选选项时，应使用 AskUserQuestion，不得以自由文本问句替代；
9. `question` 超过 60 字符时，必须拆分：将简要摘要放入 `question`，详细背景或理由放入选项的 `description`；`question` 本身应控制在 60 字符以内，确保用户一眼可读。

### 9.3 输出与问询边界

以下内容应使用自由 Markdown 输出：分析报告、审计报告、整改建议表、风险汇总、事实源回写建议、已完成执行结果、证据说明和检查结果。

以下内容必须使用 AskUserQuestion 承载：Human Gate 暂停确认、模式选择、范围确认或范围修正、整改优先级或执行批次确认，以及其他 2-4 个互斥或可多选选项中的用户决策。

### 9.4 取消与降级处理

用户明确表示“取消”“暂停”“暂缓”“先别做”“以后再说”或选择等效选项时，AI 必须停止当前需确认动作，等待用户后续主动指示。

取消后不得通过改写同义问题反复追问。若取消导致任务无法继续，应记录阻塞原因到对应 Task 或当前输出中。

## 10. 其他 Trae Solo 工具 LDVH 特殊约定

Trae 内置工具的客观能力和参数契约见 `specs/refs/trae/08-内置AI工具.md`；MCP 机制见 `specs/refs/trae/04-MCP模型上下文协议.md`；Commands 见 `specs/refs/trae/05-Commands斜杠命令.md`；自动运行与安全性见 `specs/refs/trae/07-自动运行与安全性.md`。本文只定义 LDVH 使用边界。

### 10.1 RunCommand

1. RunCommand 用于终端操作，不用于替代专用文件读写工具；
2. 长时间运行的服务器进程应使用非阻塞模式启动；
3. 高风险命令应触发确认或遵守当前环境工具约束；
4. RunCommand 输出不是事实源；稳定结论必须回写 Git 文件事实源。

### 10.2 Schedule

1. Schedule 只用于明确的周期性任务；
2. 周期任务的消息应包含足够上下文，使新会话无需追问即可执行；
3. Schedule 触发的执行结果不是事实源；稳定结论必须回写 Git 文件事实源。

### 10.3 MCP

1. MCP 工具的使用边界由对应管辖项目规则定义；
2. MCP 工具输出不是事实源；稳定结论必须回写 Git 文件事实源；
3. 涉及认证或私有服务的 MCP 调用，应检查是否有专用 Skill 或 MCP 工具提供认证访问，不得绕过认证。

### 10.4 Commands、Plan 与 Spec

1. Commands 是 Trae 的快捷执行入口，不是 LDVH 稳定事实源；
2. Plan / Spec 模式生成的过程文档，只有按 LDVH 事实源规则写入对应 Git 文件事实源后，才成为 LDVH 稳定事实；
3. LDVH 的 Task、Intent、ADR、Change 等事实对象不由 Trae Plan / Spec 文档替代。

## 11. 事实源回写原则

Rules、Skill、Agent、AskUserQuestion 和其他 Trae 工具运行过程中产生的信息按以下规则处理。

### 11.1 通用回写规则

1. Skill 输出、Agent 分析、工具输出和临时计划默认都是过程信息；
2. 过程信息只有满足 `specs/04-事实源边界与承载规范.md` 的回写要求，并写入对应 Git 文件事实源后，才成为稳定事实；
3. 规则类事实应写入 specs/ 或 `.trae/rules/` 对应规则文件；
4. 结构化工作模型事实应写入 `ldvh-base/` 对应对象目录；
5. 管辖项目资料、报告或审计结果应写入 docs/；
6. 外部资料和第三方参考应写入 specs/refs/，不得直接作为 LDVH 强制规则；
7. Skill、Agent 或工具输出不得与 Git 文件事实源并行维护同一稳定事实。

### 11.2 规范判断必须回原文

AI 涉及机制、工作模型、状态机、部署边界、目录边界或规则归属判断时，必须先定位并读取对应正式规范原文，再结合当前实例状态判断。

1. 不得只凭聊天记忆、目录现状、工具输出或经验作出规范判断；
2. Rules、Skill、Agent 是运行时机制入口，不是稳定事实源；
3. 当发现依赖错误记忆、跳过规范原文、混淆层级或误判部署边界时，应将错误模式转化为可执行检查项；
4. 检查项未满足、必读原文未定位或当前实例状态无法确认时，必须停止规范判断，并转入补读、核查或 Human Gate。

### 11.3 Rules 特有回写

Rules 是 specs 正式规范的运行时投影。当工作区规则或项目规则中出现新的长期原则、框架级约束、机制边界判断或跨环境复用规则时，应先回流到对应 specs 正式规范，再由 Rules 保留摘要和规范引用。

### 11.4 Skill 特有回写

Skill 输出不是最终事实源。Skill 产生的稳定结论、任务、备忘、证据、决策或变更，必须写入对应 Git 文件事实源后才成为稳定事实。涉及写入时应列出待写入文件、写入原因和影响范围。

### 11.5 Agent 特有回写

Agent 输出不是最终事实源。Agent 输出中的分析、建议、证据、风险、任务拆分、决策建议或变更说明，只有写入对应 Git 文件事实源后才成为稳定事实。Agent 输出与事实源冲突时，以 Git 文件事实源为准。

## 12. 机制落地关系

本文是 Trae Solo 环境规范基础规范，不是具体工作模型或工作流程。本文通过以下机制关系说明相关机制实体的落地、同步、检查或审计触发条件。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| Rules | `../.trae/rules/ldvh-workspace-rules.md`、项目 `.trae/rules/ldvh-project-rules.md` | 工作区规则/项目规则入口 | 本文的机制选择规则、事实源回写适配变化时 |
| Skill | 本文 §7 | Skill 机制规范 | Skill 准入、边界或输出规则变化时 |
| Agent | 本文 §8 | Agent 机制规范 | Agent 准入、边界或权限规则变化时 |
| AskUserQuestion | `../.trae/rules/ldvh-workspace-rules.md` | 工作区规则引用 | 本文的 AskUserQuestion 触发场景、设计规范或降级策略变化时 |

20-39 工作模型和 40-59 工作流程与 Rules 的关系，不再通过固定 NN.01-Rules.md 或场景规则结构承接。对应主规范负责声明对象规范入口和运行时摘要，项目规则或工作区规则负责承载必要入口摘要、触发条件和权威引用；LDVH 不使用场景规则承载工作模型或工作流程入口。

### 12.1 工作模型历史机制文件迁移原则

20-39 工作模型历史 NN.01 Rules、NN.02 Skill、NN.03 Agent 文件不再作为工作模型完整性的固定组成。迁移时应按以下归属处理：

1. 对象字段、状态机、准入条件、关系规则、关闭条件和事实源回写要求回到对应工作模型主规范；
2. Rules 文件只保留运行时入口摘要、触发条件、Human Gate 提醒和权威规范引用，不维护完整字段契约、状态机或流程 SOP；
3. Skill 文件承载可复用多步骤编排和 Human Gate 编排提示，但不替代对象主规范、Contract、Rules 或 Tools；
4. Agent 文件只保留是否需要独立上下文、并行委派或权限隔离的判断摘要，不用相似的“不创建理由”维持独立子文档；
5. 历史机制文件迁移完成后，应在对应主规范、运行 Rules、Skill 实体或 Agent 定义摘要中保留权威入口，并停止把 `NN.01-NN.03` 当作第二事实源。

## 13. Human Gate 与检查要求

### 13.1 通用 Human Gate 触发场景

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变 05 开发环境规范编号和职责分工；
2. 创建、修改、删除或启用/禁用规则、Skill 或 Agent；
3. 调整 Agent 权限、可写文件范围、网络访问范围或可调用范围；
4. 将外部参考、Agent 输出、Skill 输出或工具缓存提升为稳定事实；
5. 在正式规范中新增具体 LDVH 标准 Skill 清单、自建 Agent 推荐清单或多角色矩阵；
6. 改变 Rules、Skill、Agent 与 LDVH 事实源边界、工作模型或工作流程之间的职责关系。

### 13.2 Rules 特有 Human Gate

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变工作区规则或项目规则文件；
2. 改变项目上下文识别、项目规则读取机制、事实实例编辑硬约束或对象规范入口机制；
3. 改变规则唯一事实源归属；
4. 将教程、SOP、外部参考或工具输出提升为规则正文；
5. 改变 Git 提交规则、规则生效方式或高风险操作门禁；
6. 改变 Rules 与普通 specs 文档机制落地关系的维护方式。

### 13.3 Skill 特有 Human Gate

以下情况应评估 Human Gate：

1. 创建、修改、删除、重命名或启用/禁用 Skill；
2. 改变 Skill 部署位置、命名前缀或触发条件；
3. 将 Skill 输出提升为稳定事实但未回写 Git 文件事实源；
4. 允许 Skill 修改 Rules、specs 规范、Agent、跨项目契约或其他高影响资产；
5. 允许 Skill 调度 Agent；
6. 在正式规范中新增具体 LDVH 标准 Skill 清单。

### 13.4 Agent 特有 Human Gate

以下情况应评估 Human Gate：

1. 创建、导入、启用、停用、删除或重命名 Agent；
2. 修改 Agent Prompt、职责边界、触发方式或定义摘要；
3. 调整 Agent 权限边界、写入权限、网络权限或可调用范围；
4. 允许 Agent 调度其他 Agent；
5. 将 Agent 输出提升为稳定事实但未回写 Git 文件事实源；
6. 将推荐 Agent 清单正式化；
7. 删除或改变 Agent 定义摘要的权威位置。

### 13.5 AskUserQuestion 特有 Human Gate

新增或修改以下事项时，应评估 Human Gate：

1. 新增 AskUserQuestion 触发场景；
2. 修改降级策略或取消处理规则；
3. 在工作区规则中新增、修改或移除 AskUserQuestion 通用运行时入口摘要。
