## 1. 本文定位

本文定义 Task 事实模型使用的结构化数据契约。本文解决 Task YAML 实例应包含哪些字段、字段类型和约束是什么、文件命名规则是什么、状态流转契约是什么，以及工具实现应如何消费本契约的问题。

本文是 Task 事实模型契约字段的权威位置。本文是 `specs/27-Task-任务.md` 的附件型契约子文档，不是独立事实模型。本文不得重新定义 Task 的对象定位、准入条件、状态机语义、Human Gate、事实源回写或证据留存要求。发生冲突时，以 27 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款（依据 `specs/04-LDVH模型子文档规范.md` §7.1）。

## 2. Task YAML Schema

### 2.1 基础字段

Task 基础字段遵循 `specs/13-LDVH事实模型基础规范.md` §7.3 的字段契约原则，所有事实模型应包含基础字段。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | Task 对象 ID，格式为 `task-{NNNN}` |
| `type` | string | 是 | 固定为 `task` |
| `title` | string | 是 | 任务标题 |
| `status` | string | 是 | Task 状态，必须属于标准状态枚举 |
| `created` | date | 是 | 对象创建日期 |
| `updated` | date | 是 | 最近更新日期 |

### 2.2 扩展字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `description` | string | 是 | 任务详细描述 |
| `source_intent` | string | 否 | 关联 Intent ID |
| `source` | string | 是 | 来源（Intent ID 或用户直接指示） |
| `acceptance` | string | 是 | 验收标准 |
| `verification` | string | 否 | 验证方式 |
| `assignee` | string | 否 | 执行者 |
| `related_adrs` | list of string | 否 | 关联 ADR ID 列表 |
| `related_evidence` | list of string | 否 | 关联 Evidence ID 列表 |
| `related_changes` | list of string | 否 | 关联 Change ID 列表 |
| `closed_at` | date | 条件必填 | 仅当 `status` 为 `closed` 时必须填写 |
| `closure_evidence` | string | 条件必填 | 仅当 `status` 为 `closed` 时必须填写，关闭证据摘要 |

### 2.3 完整 YAML 示例

```yaml
id: task-0001
type: task
title: 创建 Intent 事实模型精简版规范
status: closed
created: 2026-06-03
updated: 2026-06-03
description: 按 21 ADR 结构创建 Intent 精简版规范，包含 7 个核心章节和 Contract 子文档
source_intent: intent-0001
source: intent-0001
acceptance: 24-Intent-意图.md 和 24.06-Contract.md 文件存在且包含 7 个核心章节
verification: 文件存在性检查 + 章节完整性检查
assignee:
related_adrs: []
related_evidence:
  - ev-0001
related_changes: []
closed_at: 2026-06-03
closure_evidence: 24-Intent-意图.md 和 24.06-Contract.md 已创建，包含全部 7 个核心章节
```

## 3. 字段约束

1. `status` 必须属于 Task 标准状态枚举：`planned`、`executing`、`review_needed`、`closed`；
2. `type` 必须固定为 `task`；
3. `closed_at` 仅在 `status: closed` 时必填，其他状态下不得填写；
4. `closure_evidence` 仅在 `status: closed` 时必填，其他状态下不得填写；
5. `source_intent` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
6. `related_adrs` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
7. `related_evidence` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
8. `related_changes` 应引用已存在的 Change ID，引用无效时应标记为校验警告；
9. `id` 格式必须为 `task-{NNNN}`，编号固定 4 位，从 `0001` 起递增；
10. `created` 和 `updated` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
11. `closed_at` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
12. `related_adrs`、`related_evidence`、`related_changes` 为列表类型，可为空列表，不得省略字段后以 null 替代空列表。

## 4. 文件命名契约

Task 实例文件命名规则：

```text
task-{NNNN}-short-title.yaml
```

约束：

1. 编号从 `0001` 起递增，固定 4 位；
2. 英文短标题使用小写短横线命名；
3. 每个项目独立编号，不使用跨项目全局编号；
4. 文件存放位置为 `ldvh-base/tasks/`；
5. 文件名变化必须同步检查所有引用该 Task 的 `related_tasks`、`source_intent` 和其他关联字段。

## 5. 状态流转契约

Task 状态语义和流转规则由 `specs/27-Task-任务.md` §5 定义，本文只提供结构化枚举和流转矩阵供 Tools 校验消费。

### 5.1 标准状态枚举

| 标准状态 |
|---|
| `planned` |
| `executing` |
| `review_needed` |
| `closed` |

状态含义依据 `specs/27-Task-任务.md` §5.1。

### 5.2 合法状态流转

| 当前状态 | 可流转至 |
|---|---|
| `planned` | `executing` |
| `executing` | `review_needed` |
| `review_needed` | `closed`, `executing` |
| `closed` | 无 |

`review_needed` → `executing` 为退回流转，应记录退回原因。

流转语义和约束依据 `specs/27-Task-任务.md` §5.2。

## 6. 契约消费声明

1. Tools 辅助程序解析 Task 时应依据本文定义的 YAML schema 和字段约束，不得自行扩张格式契约（依据 `specs/12.01-Tools辅助规范.md` §6.1）；
2. Tools 辅助程序校验 Task 时应覆盖字段完整性、状态合法性、条件必填和引用有效性；
3. Tools 辅助程序读取 Task 时可依据本文状态枚举和字段契约执行状态筛选、详情解析和关联字段解析，但 Task 读取结果是否可作为当前执行依据由 27 主文档和 Skill 流程判断；
4. 实践子文档和工具可以消费本文契约，但不得复制维护契约字段第二事实源（依据 `specs/04-LDVH模型子文档规范.md` §7.2）；
5. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 `specs/04-LDVH模型子文档规范.md` §7.3）（依据 specs/22-Change-变更记录.md）；
6. 契约子文档应先于工具实现创建，工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束（依据 `specs/04-LDVH模型子文档规范.md` §7.4）；
7. 本文契约变更时，消费本文的 Tools 实现和对应测试必须同步更新（依据 `specs/04-LDVH模型子文档规范.md` §7.4、§8）。

## 7. 检查项

检查本文是否被正确使用时，应确认：

1. Task YAML 实例字段是否完整，必填字段是否齐全；
2. `status` 是否属于标准状态枚举；
3. `type` 是否固定为 `task`；
4. `closed` 状态的 Task 是否已填写 `closed_at` 和 `closure_evidence`；
5. `source_intent` 引用的事实模型 ID 是否有效；
6. `related_adrs` 引用的事实模型 ID 是否有效；
7. `related_evidence` 引用的事实模型 ID 是否有效；
8. `related_changes` 引用的事实模型 ID 是否有效；
9. 文件命名是否符合 `task-{NNNN}-short-title.yaml` 格式；
10. 状态流转是否合法，是否存在非法流转；
11. 终态 Task 是否存在重开情况；
12. 退回流转是否记录了退回原因；
13. 工具实现是否依据本文 schema 解析和校验，未自行扩张格式契约；
14. 修改本文是否记录 Change，并在必要时触发 Human Gate（依据 specs/22-Change-变更记录.md）
