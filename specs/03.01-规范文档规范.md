# 规范文档规范

> 创建日期：2026-06-08
> 定位：定义 LDVH `specs/` 规范文档工作区的正式规范、evals、refs、历史机制文件、运行投影同步契约和规范文档治理规则
> 适用范围：LD Vibe Harness 自身 `specs/` 文档工作区
> 上位依据：`specs/03-文档基础规范.md`
> 相关规范：`specs/01-目录说明.md`、`specs/02-术语规范.md`、`specs/04-事实源边界与承载规范.md`

---
## 1. 本文定位

本文是 `specs/` 规范文档工作区的应用剖面规范。`specs/` 继承 `specs/03-文档基础规范.md` 的文档工作区三分契约、命名、结构、引用和吸收规则；本文只定义 `<W>=specs` 时的特有规则。

LDVH 自身规范工作区的三分映射如下：

```text
specs/        LDVH 正式规范正文区
specs/evals/  LDVH 内部评估和设计分析
specs/refs/   LDVH 外部资料引用
```

---

## 2. specs 正文区

### 2.1 正文区定位

`specs/` 根目录正文区承载 LDVH 正式规范。正式规范可以定义稳定规则、对象边界、字段契约、状态机、工作流程、Human Gate、机制落地关系和检查要求。

正式规范正文区不得引用 `specs/evals/` 或 `specs/refs/` 作为规范依据。evals 或 refs 中的稳定规范规则必须吸收到 specs 正文区；长期决策可以进入 ADR；可执行工作或暂存发现可以进入 Task、Memo 等工作对象，但这些对象不因此成为规范规则。

### 2.2 编号分区

specs 正文区使用编号分区。编号分区、编号占用和新增编号判断由 `specs/01-目录说明.md` §4 定义，本文不重复维护。

正式规范文档使用两位编号，格式为 `NN-标题.md`。应用剖面子文档使用 `NN.SS-标题.md`。历史机制文件和结构化契约文件沿用既有编号时，必须遵守本文 §6。

### 2.3 正式规范文档骨架

正式规范文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---
## 1. 本文解决的问题

## 2. 与 00 总纲的关系

## 3～N-2. 核心规则

## N-1. Human Gate 与检查要求

## N. 待补齐事项
```

20-39 区段的具体工作模型规范采用 `specs/07-工作模型基础规范.md` 定义的专用骨架；40-59 区段的具体工作流程规范采用 `specs/08-工作流程基础规范.md` 定义的专用骨架。00 总纲作为顶层文档，可不声明上位依据。

正式规范文档不得设置“本文不做什么”“边界说明”等反向边界章节。职责边界应通过定位、适用范围、上位依据、相关规范和正文正向规则表达。

## 3. specs/evals

`specs/evals/` 继承 `specs/03-文档基础规范.md` §3.4 和 §3.6 的 evals 与吸收规则。本文只定义 `<W>=specs` 时的特例。

specs/evals 文档特例：

1. `specs/evals/` 承载 LDVH 内部评估、设计探索、方案比较、外部项目借鉴分析和项目内部临时参考；
2. specs/evals 可以引用 specs 正文区作为评估依据和上位规范；
3. 稳定规范规则必须吸收到 specs 正文区后，才能被正式规范文档作为规则消费；
4. 长期决策可以吸收到 ADR，可执行工作或暂存发现可以吸收到 Task、Memo 等工作对象，但不得被正式规范直接当成规则引用；
5. specs/evals 不需要 Human Gate 与检查要求章节。

specs/evals 文档建议采用以下骨架：

```markdown
# {评估标题}

> 创建日期：YYYY-MM-DD
> 定位：LD Vibe Harness 对 {评估对象} 的项目级借鉴评估
> 调研边界：不直接构成强制规则
> 执行效力：无；规范规则需进入 specs 正文区，决策或工作事实需进入对应工作对象后才生效
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---
## 1. 本文解决的问题

## 2. 结论

## 3. 评估正文

## N. 待补齐事项
```

## 4. specs/refs

`specs/refs/` 继承 `specs/03-文档基础规范.md` §3.5 和 §3.6 的 refs 与吸收规则。本文只定义 `<W>=specs` 时的特例。

specs/refs 文档特例：

1. `specs/refs/` 承载与 LDVH 规范体系相关的外部资料引用副本；
2. specs/refs 文档头部必须声明外部资料来源；
3. 被采纳的外部资料结论必须吸收到 specs 正文区、ADR、Task 或其他权威出口后才生效；
4. specs/refs 文档不得包含对 specs 正文区文件的路径引用、关联规范声明或依据引用。

specs/refs 文档建议采用以下骨架：

```markdown
# {引用标题}

> 创建日期：YYYY-MM-DD
> 来源：{外部资料来源}
> 定位：外部资料引用，不直接成为 LDVH 强制规则

---
## 1. 外部材料摘要

## 2. 引用正文

## N. 待进一步调研
```

## 6. 历史机制文件与结构化契约

### 6.1 固定机制子文档取消

LDVH 不再要求每个工作模型或工作流程默认拆分固定 `NN.01` 至 `NN.06` 机制子文档。历史上存在的 Rules、Skill、Agent、Tools、Web、Contract 文件只作为迁移前过渡资料或遗留契约保留。

新增或稳定后的机制内容应按机制归属进入：

1. 主规范机制适配边界；
2. `specs/05-Trae-Solo环境规范.md`；
3. `specs/08-工作流程基础规范.md`；
4. `specs/14-Code实现与工具规范.md` 与 `tools/` 实现；
5. `specs/15-Web信息同步规范.md` 与 `web/` 实现；
6. 运行 Rules / Skill 实体、Agent 定义摘要或契约能力。

### 6.2 历史机制文件

历史机制文件不是独立规范，也不是工作模型或工作流程完整性的默认要求。历史机制文件只能说明对应模型或流程在某个机制下曾如何实践，不得重新定义主模型、主流程、字段契约、状态机、Context、Scenario、Gate、事实源边界或 Human Gate。

历史机制文件的迁移、保留和删除规则由对应区间的上位基础规范定义：工作模型依据 `specs/07-工作模型基础规范.md` 和 `specs/20-工作模型集合索引.md`，工作流程依据 `specs/08-工作流程基础规范.md`。

### 6.3 结构化契约

结构化契约可以作为字段契约、schema、接口契约或机器消费契约存在，但不构成固定 `NN.06` 子文档要求。新增或稳定后的契约优先回并到主规范契约章节，或由 Code（含 Tools / PyTools 实现）和 Web 实现消费主规范契约。

## 7. 运行投影同步契约

机制落地关系是 specs 正式规范到运行投影的同步契约。它用于说明某段稳定规范被 Rules、Skill、Agent、Tools、Web、Contract、MCP、Hooks、Automation 或其他机制实体消费时，何处消费、何时同步、如何验证。

机制落地关系不是普通引用、文档重要性声明或上位依据声明。只有当某个机制实体直接消费本文中的可执行规则、字段契约、状态机、流程步骤、触发条件、权限边界或校验要求，并且本文变化会导致该实体需要同步检查或更新时，才声明机制落地关系。

机制落地关系至少包含：

| 字段 | 含义 |
|---|---|
| 关联机制 | Rules、Skill、Agent、Tools、Web、Contract、MCP、Hooks、Automation 等 |
| 关联实体 | 当前项目中的具体文件、目录、工具、Skill、配置或待生成实体 |
| 关系类型 | 入口摘要、流程编排、校验实现、受控写入、展示视图、审批提示、命令权限等 |
| 触发条件 | 初始化、来源章节变化、字段契约变化、状态机变化、Human Gate 变化、审计或规则漂移诊断 |

必要时可补充来源章节、抽象落地能力、验证方式和降级处理。

20-39 工作模型和 40-59 工作流程不使用普通机制落地关系，依据 `specs/07-工作模型基础规范.md` 和 `specs/08-工作流程基础规范.md`，在主规范中声明机制适配边界。

## 8. Specs 修改执行顺序

AI 新增、修改或审计 specs 正式规范文档时，应按以下顺序执行：

1. 根据任务场景确定基础入口：文档工作区、命名、引用、evals/refs 或应用剖面边界读取 `specs/03-文档基础规范.md`；specs 正式规范、机制落地关系或历史机制文件读取本文；目录归属和编号分区读取 `specs/01-目录说明.md`；术语读取 `specs/02-术语规范.md`；
2. 判断拟修改内容属于哪个规范权威领域；
3. 读取目标规范及其上位依据、相关规范；
4. 按需读取 00 中与本次变更相关的产品定位、五类构成要素、价值实现标准、运行闭环标准和 Human Gate 要求；
5. 判断变更是否符合 00 上位原则，是否弱化事实源边界、Human Gate、验证纪律或五类构成要素分工；
6. 若涉及高影响变更，触发 Human Gate；
7. 修改目标规范；
8. 运行文档结构校验和引用校验；
9. 检查是否需要更新机制落地关系；
10. 若变更影响运行投影，按机制落地关系同步检查对应实体。

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 重命名或重排 specs 正式规范文档；
2. 改变 specs 正文区、specs/evals 或 specs/refs 的引用方向规则；
3. 将 specs/evals 或 specs/refs 结论直接作为强制规则使用；
4. 新增、删除或重命名应用剖面子文档；
5. 恢复或新增固定机制子文档结构；
6. 改变机制落地关系规则，或新增、修改、删除会影响运行投影同步检查、产品初始化、审计或规则漂移诊断的机制落地关系；
7. 历史机制文件新增或扩张基础规范。

规范文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 正式规范文档已声明上位依据，00 除外 |
| 编号分区 | 文档编号符合 `specs/01-目录说明.md` |
| 文档结构 | 文档骨架符合正式规范、工作模型、工作流程、evals、refs 或应用剖面要求 |
| 应用剖面 | 子文档只定义特例，未复制父规范通用规则 |
| 历史机制文件 | 未恢复固定机制子文档结构 |
| 引用方向 | specs 正文区未引用 specs/evals 或 specs/refs 作为规范依据 |
| 机制落地关系 | 仅声明实际消费的运行投影同步契约 |
| 校验 | specs 修改后已运行文档结构和引用校验，或记录降级原因 |

## 11. 待补齐事项

1. 机制落地关系字段是否扩展来源章节、抽象落地能力、验证方式和降级处理，待运行投影同步工具设计稳定后确认；
2. 历史机制文件的逐项迁移状态待随工作模型和工作流程规范继续收敛；
3. specs/evals 与 specs/refs 的历史文档结构统一性待后续持续审计和修正。
