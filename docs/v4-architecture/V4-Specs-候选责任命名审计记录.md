# V4 Specs 候选责任命名审计记录

> 记录性质：本文依据 `specification-model-foundation` §§12–13，对《V4 Specs 责任重新审计记录》已经证明成立的六项通用或基础候选责任审核中英文规范名称和 `spec_key`。本文不是规则源，不授予候选名称、职责标识符、编号、路径或规范状态，也不把六项解释为所有未来具体规范的封闭清单。

## 1. 审核边界

本轮只回答两个问题：

1. 哪个中英文名称能够准确指向已经成立的责任；
2. 哪个 `spec_key` 能作为该责任不随标题、编号或路径变化的稳定身份。

本轮不决定：

1. `spec_id`、文件编号、文件路径；
2. `parent_spec`、`relation`、`basis` 或 `related_specs`；
3. 六项规范的建设顺序或并行关系；
4. 规范正文、附件或 Code 的具体设计；
5. 候选名称是否立即进入双语术语表；
6. Spark、WorkCase、ADR、Pitfall、Study 等具体事实类型是否建立及其名称；
7. 具体行动模板、项目适用的正式规则来源或单一环境 adapter 契约是否形成新的普通规范责任。

规范标题首先是规范文档的身份表达，不因出现在标题中就自动成为需要单独登记的架构术语。只有标题中的表达还要作为跨规范稳定概念独立复用，并满足 01 §12.3 时，才另行进入双语术语治理。本轮优先复用 00 和当前术语表已经定义的 `LDVH Helper CLI`、事实模型（Fact Model）、行动模板（Action Template）、Code、Web 等名称，不为标题完整而创造新概念。

## 2. 共同判断标准

每个名称和 `spec_key` 必须同时满足：

1. 名称以已经成立的规则对象为主语，不用建设阶段、内部简称或历史编号代替责任；
2. 中文和英文指向同一责任，英文优先自然表达，不逐字硬译；
3. 标题可以概括正文，但不能把责任缩窄为其中一项实现，也不能暗示未成立的额外权威；
4. 优先复用当前术语；新增普通描述必须能直接理解，不包装成行业标准或新架构概念；
5. `spec_key` 使用小写英文与连字符，只表达稳定责任，不编码版本、编号、状态、结构父级或建设顺序；
6. 标题变化不必导致 `spec_key` 变化；两个不同责任不得共享或交换 `spec_key`；
7. 把名称替换为其责任说明后，代表性语句含义仍成立；
8. 名称和 `spec_key` 不得恢复已取消的横向验证或规则效力责任。

来源分类采用 01 §12.4 的口径：本轮名称均为“现有 LDVH 术语加普通描述性表达”的组合，不声称是行业标准术语。英文自然性只作为名称质量判断，不赋予其外部标准权威。

## 3. 六项候选责任

### 3.1 候选责任 A

不使用候选名称的预期含义：一份规范负责定义 AI 和环境入口共同使用的 Helper CLI 公开服务边界，包括请求、响应、公开命令、能力发现、来源与对象范围保留、部分结果、受控操作结果以及规则判断报告；它不定义内部模块或环境协议。

候选比较：

| 候选名称 | 判断 |
|---|---|
| Helper CLI 服务契约规范 / Helper CLI Service Contract Specification | 推荐。保留 00 已定义的 Helper CLI 服务形式，并用“服务契约”准确限定公开接口与结果语义；标题省略已由项目语境明确的 `LDVH`，避免文件名过长 |
| Helper 基础服务规范 / Helper Foundation Service Specification | 不推荐。“基础服务”重复 00 的上位定位，但没有清楚表达公开接口契约 |
| LDVH Helper 服务规范 / LDVH Helper Service Specification | 不推荐。省略 CLI 后弱化当前唯一已确定的基础服务形式，“服务规范”也容易同时指向内部实现 |

推荐定义：该规范定义 LDVH Helper CLI 面向 AI 及环境入口的稳定公开服务契约，以及实际服务结果能够支持的范围；不定义规则、事实、模板的领域语义，不定义 Code 内部结构或厂商环境协议。

- 正例：公开命令、参数语义、响应字段、来源保留、部分成功和退出语义。
- 反例：parser 库选择、缓存算法、某厂商 Hook payload、事实类型字段。
- 相邻责任：Code 实现该契约；环境接入映射该契约；具体来源规范定义被报告规则的效力。
- 替换检查：“修改该规范时必须检查公开 CLI 与机器响应是否仍保持来源、对象范围和部分结果”能够准确替换为上述责任说明。
- 推荐中文：`Helper CLI 服务契约规范`。
- 推荐英文：`Helper CLI Service Contract Specification`。
- 推荐 `spec_key`：`helper-cli-service-contract`。
- 术语处理：“LDVH Helper CLI”已经是 `current`；“服务契约”在标题中是普通描述，不在本轮新增独立术语。

### 3.2 候选责任 B

不使用候选名称的预期含义：一份规范负责定义需要结构化管理的事实类型及其实例所共同遵守的准入、身份、Schema 权威方向、字段、状态、关系和实例操作边界；它不重新定义事实源，也不直接定义每一种具体事实类型。

候选比较：

| 候选名称 | 判断 |
|---|---|
| 事实模型基础规范 / Fact Model Foundation Specification | 推荐。直接复用 00 已定义的构成要素名称，“基础”表示共同规则而非具体事实类型 |
| 结构化事实规范 / Structured Facts Specification | 不推荐。只描述处理后的形态，没有表达事实类型准入、模型共同规则和实例治理的完整责任 |
| 事实对象规范 / Fact Object Specification | 不推荐。把责任缩窄为实例对象，容易遗漏类型准入、Schema 权威方向及共同状态关系规则 |

推荐定义：该规范定义事实模型纳入事实类型及组织其实例时共同适用的基础规则；具体事实类型的核心语义仍由各自正式来源定义。

- 正例：事实类型准入、实例身份、Schema 权威方向、状态转换和关系目标。
- 反例：重新定义 Git 事实源、规定某个 WorkCase 的领域字段、保存 Helper 会话缓存。
- 相邻责任：03 定义事实源与信息溯源；具体事实类型来源定义领域语义；Code/tests 实现结构校验。
- 替换检查：“修改该规范时必须检查不同事实类型是否仍共享明确的身份和 Schema 权威方向”能够准确替换为上述责任说明。
- 推荐中文：`事实模型基础规范`。
- 推荐英文：`Fact Model Foundation Specification`。
- 推荐 `spec_key`：`fact-model-foundation`。
- 术语处理：“事实模型”已经是 `current`；“基础规范”沿用 01 已有标题构造，不新增独立术语。

### 3.3 候选责任 C

不使用候选名称的预期含义：一份规范负责定义重复场景中可复用行动结构的准入、稳定身份、共同内容、来源引用、更新退出以及模板身份与实际授权、执行和完成之间的边界。

候选比较：

| 候选名称 | 判断 |
|---|---|
| 行动模板基础规范 / Action Template Foundation Specification | 推荐。直接复用 00 已定义的构成要素名称，并准确表达对所有具体模板共同规则的责任 |
| 可复用行动规范 / Reusable Action Specification | 不推荐。容易把一次实际行动与用于组织行动的模板混为一体 |
| 行动流程规范 / Action Workflow Specification | 不推荐。“流程”容易暗示固定执行顺序和运行状态，超出行动模板的权威边界 |

推荐定义：该规范定义行动模板的准入、身份和共同结构，以及模板对来源规则、事实和能力的引用边界；模板存在或被选择不等于行动获授权、已执行、验证通过或完成。

- 正例：模板进入条件、输入、失败分流、验证入口、回写和交还的共同语义。
- 反例：把单次计划登记成模板、用模板改变 Human Gate、在模板中保存一次运行状态。
- 相邻责任：具体来源规范定义行动义务；事实模型管理需要稳定保存的事实；Helper 发现和提供模板；Code 执行确定性能力。
- 替换检查：“修改该规范时必须检查模板共同结构是否仍回指来源且不冒充执行结果”能够准确替换为上述责任说明。
- 推荐中文：`行动模板基础规范`。
- 推荐英文：`Action Template Foundation Specification`。
- 推荐 `spec_key`：`action-template-foundation`。
- 术语处理：“行动模板”已经是 `current`；不新增“行动流程”等相邻术语。

### 3.4 候选责任 D

不使用候选名称的预期含义：一份规范负责约束实现 Helper CLI 及其它确定性能力的 Code，在首次实现前明确模块责任、依赖与调用方向、接口与 Schema 维护责任和测试策略，并在持续变化中管理错误与诊断、可观察性、复杂度、重构条件、外部工程实践吸收以及设计与实现偏移。这里没有建立一个独立于 Helper CLI 的“Code 系统”。

候选比较：

| 候选名称 | 判断 |
|---|---|
| Code 实践与测试规范 / Code Practices and Testing Specification | 推荐。以 Code 构成要素为主语，并把测试责任明确写入标题；正文仍覆盖实现前规划、诊断、重构和持续演进，不暗示存在独立于 Helper CLI 的另一套系统 |
| Code 系统设计与工程实践规范 / Code System Design and Engineering Practices Specification | 不推荐。内容本身可成立，但“Code 系统设计”容易让人误解为 Code 是与 Helper CLI 并列的另一套系统 |
| Code 系统规划与工程实践规范 / Code System Planning and Engineering Practices Specification | 不推荐。“系统规划”还容易被理解为建设计划或排期，不能稳定指向模块、依赖、接口与 Schema 责任设计 |
| Code 工程治理规范 / Code Engineering Governance Specification | 不推荐。“治理”过于抽象，无法从名称直接判断它同时承担首次系统设计和持续工程要求 |

推荐定义：该规范定义 Code 实现 Helper CLI 及其它确定性能力时共同遵守的工程实践要求，包括首次实现前必须明确的模块、依赖、接口、Schema 维护责任和测试策略；真实源码、测试文件和单次实施计划不成为该规范的替代来源。

- 正例：模块责任、允许依赖、公共接口维护者、风险驱动测试策略、诊断和重构条件。
- 反例：固定当前文件清单、规定单次重构步骤、用全局 5000 行阈值替代设计判断、重新定义 Helper 外部契约。
- 相邻责任：Helper 规范定义外部服务；领域规范定义 Schema 语义；Code/tests 实现并验证；环境接入定义 adapter 边界。
- 替换检查：“修改该规范时必须检查实现 Helper CLI 的 Code 是否仍在首次实现前明确模块与接口，并持续满足测试、诊断和重构要求”能够准确替换为上述责任说明。
- 推荐中文：`Code 实践与测试规范`。
- 推荐英文：`Code Practices and Testing Specification`。
- 推荐 `spec_key`：`code-engineering-practices`。
- 术语处理：“Code”已经是 `current`；“实践与测试”只作普通描述，不声称为 LDVH 新模型或行业标准。标题变化只把同一责任中已经存在的测试显式化，因此稳定 `spec_key` 不随标题逐字变化。

### 3.5 候选责任 E

不使用候选名称的预期含义：一份规范负责定义 Web 如何从允许的信息源独立读取、形成和标明派生信息、向 Human 呈现来源与判断边界，并在适用授权和 Code 能力成立时请求受控交互；它不取得事实定义、写入或 Human 决策权威。

候选比较：

| 候选名称 | 判断 |
|---|---|
| Web 呈现与交互规范 / Web Presentation and Interaction Specification | 推荐。以 Web 的两个 Human-facing 主动作概括产品责任；独立读取是形成可信呈现的内部规则，由定位、范围和正文明确，不需要全部写入标题 |
| Web 信息访问、呈现与交互规范 / Web Information Access, Presentation, and Interaction Specification | 可表达完整责任，但标题过长，并且容易把读取这一内部边界误解为与 Human-facing 呈现、交互并列的产品目的 |
| Web 信息产品规范 / Web Information Product Specification | 不推荐。“信息产品”是审计记录中的概括，不是 00 术语，且无法直接看出读取、来源呈现和受控交互边界 |

推荐定义：该规范定义 Web 面向 Human 的信息呈现及受控交互边界；为了使呈现可信，正文同时约束 Web 从允许范围独立读取、标明派生信息和回指来源。标题省略读取，不授予 Web 事实写入权威，写入只能作为有来源授权且有实际 Code 能力承接的交互请求。

- 正例：读取范围、派生值过期提示、来源导航、多语言和视口下的可识别性、受控写入请求及结果回读。
- 反例：由页面创建事实字段、把页面成功当作 Human Gate、通过 Helper 中转 Web 读取、把旧缓存显示成当前事实。
- 相邻责任：03 定义信息和事实源共同边界；事实模型定义结构化事实；Code 提供确定性能力；Web 不经过 Helper 服务 Human。
- 替换检查：“修改该规范时必须检查 Web 是否仍从允许来源读取、清楚呈现来源并只请求已授权交互”能够准确替换为上述责任说明。
- 推荐中文：`Web 呈现与交互规范`。
- 推荐英文：`Web Presentation and Interaction Specification`。
- 推荐 `spec_key`：`web-presentation-interaction`。
- 术语处理：“Web”已经是 `current`；“呈现与交互”只是一组普通动作，不建立“信息产品”等新架构术语。读取仍是该责任必须遵守的内部规则。

### 3.6 候选责任 F

不使用候选名称的预期含义：一份规范负责定义外部环境事件、工具调用和上下文到 Helper 请求的转换、结果映射、能力不足交还，以及环境连接的安装、检查、真实触发、升级、禁用、卸载和回滚边界；它不把厂商协议提升为通用规则。

候选比较：

| 候选名称 | 判断 |
|---|---|
| 环境接入规范 / Environment Integration Specification | 推荐。复用 00 已经反复使用的“环境接入”表达，能够概括 adapter 映射、真实触发及安装和回滚边界 |
| 外部运行环境连接规范 / External Runtime Environment Connection Specification | 不推荐。接近审计对象的逐字描述，但中文和英文都生硬，且“运行环境”容易被误解为仅指进程 runtime |
| 环境适配器规范 / Environment Adapter Specification | 不推荐。把责任缩窄为 adapter 实现，遗漏安装、真实触发、卸载和回滚的接入成立条件 |

推荐定义：该规范定义外部环境连接 LDVH Helper CLI 时共同适用的转换、结果映射、真实触发、安装与回滚边界；具体厂商协议与实现只有形成稳定外部契约并另经审核时，才进入相应正式来源。

- 正例：未知事件交还、Helper 结果忠实映射、静态安装与真实触发区分、卸载后不再自动触发的证明。
- 反例：把某厂商事件闭集写成所有环境通用枚举、复制事实或规则判断、以文件存在声明已经 integrated。
- 相邻责任：Helper 规范定义被调用服务；02 提供工作对象；Code/tests 实现 adapter；行动模板可以组织重复安装步骤。
- 替换检查：“修改该规范时必须检查环境映射、真实触发和回滚是否仍在不改写 Helper 语义的前提下成立”能够准确替换为上述责任说明。
- 推荐中文：`环境接入规范`。
- 推荐英文：`Environment Integration Specification`。
- 推荐 `spec_key`：`environment-integration`。
- 术语处理：“环境接入”已经在 00 中作为普通表达稳定使用；本轮不把它提升为脱离该规范责任的独立架构概念。

## 4. 汇总建议

| 候选责任 | 推荐中文名称 | 推荐英文名称 | 推荐 `spec_key` | 相对旧提案 |
|---|---|---|---|---|
| A | Helper CLI 服务契约规范 | Helper CLI Service Contract Specification | `helper-cli-service-contract` | 保留；标题缩短不改变职责 |
| B | 事实模型基础规范 | Fact Model Foundation Specification | `fact-model-foundation` | 保留 |
| C | 行动模板基础规范 | Action Template Foundation Specification | `action-template-foundation` | 保留 |
| D | Code 实践与测试规范 | Code Practices and Testing Specification | `code-engineering-practices` | Human 将测试显式写入标题；职责仍是同一 Code 工程责任，正文保留首次实现前规划要求 |
| E | Web 呈现与交互规范 | Web Presentation and Interaction Specification | `web-presentation-interaction` | Human 决定读取作为正文内部规则，不进入标题；定位和范围仍明确独立读取、来源与派生边界 |
| F | 环境接入规范 | Environment Integration Specification | `environment-integration` | 保留 |

旧提案中的名称和 `spec_key` 均未取得正式规范身份，因此本轮比较不构成已生效职责标识符的改名或替代。推荐项只有在独立复核完成、异议关闭并进入相应规范草案后，才成为该草案的正式身份候选。

## 5. 术语影响

本轮不建议立即修改双语术语表：

1. `LDVH Helper CLI`、事实模型、行动模板、Code、Web 已登记为 `current`；
