## 1. 行动定位与适用场景

多角色思考是面向复杂问题的分析增强行动。它通过多个专业视角分别分析同一输入，帮助 AI 和 Human 识别影响范围、风险判断、分歧点、建议执行顺序、需要同步的事实源和 Human Gate。

多角色思考不是独立事实源，不替代 ADR、Task、Memo、Change、Pitfall、管辖项目配置、规范正文、Code 实现或 Web 实现。它的输出默认是过程分析；只有按事实源边界写回对应 Git 文件后，才成为稳定事实。

出现以下情况之一时，应考虑进入多角色思考：

1. 用户明确要求从不同角色、不同专业视角或多角色角度分析；
2. 规范、Rules / Instructions、Skill、Agent、Code、Web、工具或工作流程变更需要评估跨模块影响；
3. 技术选型、架构调整或工具设计需要同时评估安全、治理、可维护性、验证和落地边界；
4. 需求变更会影响产品、前端、后端、数据、测试、发布、治理或 AI 协作多个维度；
5. 需要判断某个输出应分流为 Task、Memo、ADR、Pitfall、Change、管辖项目配置更新或 docs 报告；
6. 需要在执行高影响变更前识别 Human Gate 和证据要求；
7. 主上下文判断存在明显不确定性，且单一视角可能遗漏重要风险。

以下情况通常不应进入多角色思考：

1. 简单问答或单文件小改，单一主上下文即可处理；
2. 用户已经明确给出决策并只要求执行低风险操作；
3. 问题已满足更具体工作流程的准入条件，且不需要多视角分析；
4. 只需要确定性字段、路径或格式校验，应优先使用 Code、工具或对象审计；
5. 用户明确要求不要进行额外分析。

## 2. 准入条件

多角色思考行动的准入条件如下：

1. 存在一个需要分析的明确主题、变更、决策、风险或问题；
2. 至少存在两个以上有意义的分析视角；
3. 分析结论可能影响后续执行、规范、工作对象、工具、协作机制或 Human Gate；
4. 输入材料能够追溯到用户输入或 Git 文件事实源；
5. AI 能够明确说明本次分析是过程分析，还是需要回写为稳定事实。

不满足准入条件时，应退回主上下文直接回答、询问用户补充输入，或分流到更合适的工作流程、Skill、Agent、Code 或工具辅助。

## 3. 事实源边界

本文是多角色思考工作流程的权威事实源。本文定义多角色思考的准入条件、Context、Scenario、执行流程、Gate、Skill 和 Agent 调度、工具协作、事实源回写、证据留存、机制适配边界和检查要求。

| 内容 | 权威位置 |

| 工作流程集合状态 | `docs/specs/40-工作流程集合索引.md` |
| Skill、Agent、Rules / Instructions、Code、Web 等能力承接边界 | `docs/specs/04.03-环境能力承接边界规范.md` |

## 4. Context 要求

执行多角色思考前，AI 应获得以下最小 Context：

1. 用户提出的分析主题、目标、约束和期望输出；
2. 当前项目的目录、规范入口、事实源边界和相关工作区规则；
3. 与本次主题直接相关的 `docs/specs/`、`ldvh-base/`、`docs/`、`tools/`、`web/` 或代码文件；
4. `docs/specs/06-工作流程基础规范.md`；
5. `docs/specs/40-工作流程集合索引.md`；
6. 需要判断事实源回写时，读取 `docs/specs/09-事实源边界与承载规范.md` 和对应工作模型规范；
7. 需要判断能力承接时，读取 `docs/specs/04.03-环境能力承接边界规范.md`、`docs/specs/07-Code实现规范.md` 或 `docs/specs/08-Web信息同步规范.md`。

根据主题复杂度，可增加以下 Context：

1. `docs/evals/` 中与本次主题相关的内部评估文档；
2. `docs/refs/` 中与平台、第三方能力或外部资料相关的引用文档；
3. 已存在的 Task、ADR、Memo、Pitfall、Change、Intent 实例，或管辖项目配置；
4. 当前平台适配清单、42 落地与检查报告，以及当前环境中可调用 Agent、结构化问询、Hook、CI、Code 或 Web 能力的现场证据；若主题属于管辖项目，还应读取工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 和对应项目事实源。

可选 Context 只能作为输入材料，不能覆盖 `docs/specs/` 正式规范，也不能被当作当前项目已经存在对应 Skill、Agent、工具或 Web 实体的证据。

## 5. Scenario 识别

当用户输入、任务背景或事实源状态满足以下条件之一时，AI 应识别为多角色思考 Scenario：

1. 出现“多角色”“不同角色”“不同视角”“从多个专业角度”“多角度”“各自说一遍”等明确触发语，或语义等价表述；
2. 当前变更影响两个以上规范、工作对象、工作流程、工具、项目模块或协作机制；
3. 当前任务涉及 Rules / Instructions、Skill、Agent、Code、Web、工具、事实源边界或 Human Gate 的职责划分；
4. 当前判断存在高影响风险，且需要安全、治理、验证、架构或产品视角共同审查；
5. 用户要求先分析影响、风险、分歧或执行顺序，再决定是否修改；
6. AI 对执行路径不确定，并判断单一视角不足以安全推进。

触发语匹配原则：本条使用“等”表示非穷举。当用户表述与已列触发语语义等价时，AI 应同样触发多角色思考，不得仅因字面不匹配而跳过。

多角色思考与其他行动同时匹配时，按以下原则处理：

1. 若用户明确要求多角色分析，优先进入多角色思考；
2. 若已有明确 Task 且只需执行，优先进入 Task 执行相关工作流程；
3. 若正在创建或更新对象实例，优先遵守对应对象创建或对象状态更新流程；
4. 若涉及规范、规则、Skill、Agent、Code、Web 或工具变更，先进行多角色思考或治理审查，再执行写入；
5. 若触发 Human Gate，先暂停并请求确认。

以下情况应降级为主上下文直接分析或询问用户：

1. 主题不明确，无法选择角色；
2. 没有足够事实源支持分析；
3. 用户只需要简短回答；
4. 分析会引入无关复杂度；
5. 多角色子 Agent 模式不适用，但轻量模式足以完成。

## 6. 执行流程

### 6.1 选择分析模式

多角色思考分为两种模式：

| 模式 | 说明 | 行为 |
|---|---|---|
| 主上下文轻量模式 | 无需独立上下文，AI 在主上下文中依次分析各角色 | AI 在主上下文中按角色分别分析并汇总 |
| 多角色子 Agent 模式 | 需要独立上下文、结论隔离、并行委派或不同权限边界 | 主控为每个角色构造独立参数，启动可调用 Agent 容器，各实例输出回到主控后统一汇总 |

主控识别到多角色思考场景时，除非用户已明确指定模式，否则应先判断是否需要用户选择。存在两种模式都可行、取舍影响执行成本或需要用户确认分析强度时，应通过结构化问询或当前环境等价 Human 交互能力让用户选择。模式选择完成前，不得启动对应模式的分角色分析；不得先输出完整多角色报告，再在报告末尾用自由文本询问模式选择。

### 6.2 识别变更类型

AI 应先判断分析主题属于哪些类型：

1. 需求 / 产品变更；
2. UI / 前端体验变更；
3. 服务端 / API / 数据变更；
4. 数据 / 模型相关变更；
5. 安全 / 合规变更；
6. 规则 / 规范 / 文档变更；
7. Skill / Agent / AI 协作变更；
8. Code / 工具链 / 自动化变更；
9. Web / Human-facing 入口变更；
10. 发布 / 部署 / 关闭变更；
11. 审计 / 复盘 / 流程改进；
12. 通用架构 / 大型重构。

### 6.3 选择角色

角色是多角色思考的运行时分析视角，不是工作模型，不创建 Role 工作对象。默认角色集合见本文 §6.4。

角色选择规则：

1. 优先选择与变更类型直接相关的角色；
2. 涉及事实源、规则、编号、对象或工作流程时，必须包含治理规范审视；
3. 涉及 Human Gate、权限、删除、远程操作、Agent 或工具写入时，必须包含风险与权限审视；
4. 涉及完成标准、关闭、Review 或审计时，必须包含验证证据审视；
5. 涉及 Skill、Agent、MCP、Code 或工具链时，必须包含 AI 协作架构审视或工具链架构审视；
6. 涉及 Web 信息同步、受控编辑或 Human Gate 工作台时，应包含 Web 信息同步产品审视；
7. 涉及落地检查或合规检查时，应包含治理审视；
8. 涉及上下文获取问题、AI 依赖聊天记忆或 Context 定义审查时，应包含上下文精准性审视；
9. 单次分析选中角色数超过 4 个时，应精简、合并同维度角色或拆分分析批次；
10. 多角色子 Agent 模式下，同一轮并行启动的子 Agent 实例不得超过 4 个。

默认角色集合是稳定基线，不是封闭枚举。当默认角色不足以覆盖本次关键风险、边界或专项问题时，可以声明本次临时职能视角。临时职能仅作为本次运行时分析参数，不创建 Role 事实实例，不自动写入默认角色集合，也不得被后续 AI 当作稳定角色引用。临时职能如需沉淀为默认角色，必须说明复用价值、触发场景、与既有角色差异和契约字段影响，并经 Human Gate 确认后修改本文。

RoleSelectionOutput 应包含：

```yaml
selected_roles:
  - role_id: 稳定角色 ID；role_origin 为 runtime 时可为空
    role_name: 角色或临时职能名称，必填
    role_origin: preset | runtime
    reason: 选择理由，必填
    temporary_scope: 临时职能适用边界；role_origin 为 runtime 时必填
    preset_gap: 默认角色不足以覆盖的原因；role_origin 为 runtime 时必填
    promotion_candidate: 是否建议后续评估沉淀，必填
excluded_roles:
  - role_id: 角色 ID
    reason: 排除理由
mode_recommendation: 主上下文轻量模式 / 多角色子 Agent 模式
mode_reason: 模式选择理由
human_gate_required: true / false
human_gate_reason: 触发原因，选填
```

### 6.5 分角色分析

每个角色至少输出：

1. 适用性：相关 / 无关 / 部分相关；
2. 影响范围：具体模块、文件、接口、对象、行动或流程；
3. 分析结论：该角色视角下的判断；
4. 风险：高 / 中 / 低，并说明原因；
5. 建议动作：执行 / 暂停 / 确认 / 回写 / 补充，并标注优先级；
6. 依据：引用的事实源或观察，选填；
7. Human Gate：是否触发及原因，选填。

### 6.6 汇总对比

AI 应汇总各角色分析，至少包含：

1. 一致结论；
2. 分歧点；
3. 风险汇总；
4. 建议执行顺序；
5. 需要同步的文档、对象、规则、Skill、Agent、Code、Web 或工具；
6. 事实源回写建议；
7. Human Gate 判断。

### 6.7 报告结构

多角色思考报告建议采用以下结构：

```markdown
# 多角色思考报告

## 适用性判断
- 是否进入多角色思考：是 / 否
- 分析模式：主上下文轻量模式 / 多角色子 Agent 模式
- 涉及角色：{角色列表}

## 变更或问题概述
- 主题：{一句话描述}
- 影响范围：{模块 / 文件 / 对象 / 行动 / 项目}

## 各角色分析

### {角色名}
- 适用性：相关 / 无关 / 部分相关
- 影响范围：{描述}
- 分析结论：{结论}
- 风险：高 / 中 / 低 — {描述}
- 建议动作：{列表}

## 角色间一致与分歧
- 一致结论：{列表}
- 分歧点：{列表}

## 风险汇总
- 高风险：{列表}
- 中风险：{列表}
- 低风险：{列表}

## 建议执行顺序
1. {第一步}
2. {第二步}

## 事实源回写建议
- 应写回：{文件或对象}
- 不应回写：{过程信息}

## Human Gate
- 是否触发：是 / 否
- 触发原因：{原因}
- 建议确认事项：{列表}
```

## 7. Gate 触发条件

以下情况触发条件 Gate：

1. 缺少分析主题或输入材料；
2. 需要读取的事实源不存在或无法确认；
3. 角色选择依据不足；
4. 角色参数构造依据不足，无法为多角色子 Agent 模式提供清晰角色边界；
5. 输出需要回写但目标事实源不明确；
6. 当前环境无法承接所需结构化问询或可调用 Agent 能力，且无法形成可靠降级方式。

条件 Gate 未满足时，AI 应降级、询问用户或暂停，不得继续执行高影响分析或写入。

以下情况必须暂停并请求 Human 确认：

1. 将多角色思考结论升级为规范、Rules / Instructions、ADR 或长期行动边界；
2. 创建、导入、启用、修改或删除 Agent；
3. 允许多角色子 Agent 模式访问更高权限或写入文件；
4. 依据多角色思考结论修改事实源权威位置；
5. 依据多角色思考结论执行跨项目、高风险或不可自动确认的变更；
6. 创建 LDVH 正式 Skill、Agent、Code、Web、运行投影或契约能力；
7. 将运行时临时职能升级为默认角色、修改默认角色集合、修改角色选择契约或改变角色选择规则。

用户确认后，AI 应明确记录确认事项，按对应规范执行写入或创建，执行可用检查，并汇报哪些内容已成为稳定事实、哪些仍是建议。

## 8. Skill 和 Agent 调度

多角色思考不创建默认 LDVH Skill。理由如下：

1. 触发判断适合由 Rules / Instructions 类入口摘要承接；
2. 执行流程、角色选择、输出格式和 Human Gate 判断由本文承载；
3. 主上下文轻量模式和多角色子 Agent 模式均不依赖 Skill；
4. 创建专用 Skill 会增加维护成本，但不提升可控性。

Rules / Instructions 入口只做薄入口提醒：当用户要求多角色、多视角、跨模块影响评估、复杂变更风险审查，或 AI 判断单一主上下文可能遗漏风险时，应进入本文定义的多角色思考工作流程。入口不得复制本文完整 Scenario、角色定义、执行流程、输出模板或 Human Gate 条款。

多角色子 Agent 模式用于需要独立上下文、结论隔离、并行委派、不同权限边界或大量事实源读取的多角色分析。它遵循以下规则：

1. 多角色子 Agent 模式只能由主控依据本文编排，不得由 Skill、Code、工具、MCP 或脚本直接触发；
2. 主控根据本文角色定义和当前主题选择角色；
3. 主控为每个角色构造独立调用参数，参数应包含角色名、关注点、触发背景、输入事实源、输出格式和边界要求；
4. 主控可使用当前运行环境提供的可调用 Agent 容器启动一个或多个子 Agent 实例，每个实例只承担被注入的角色视角；
5. 同一轮多角色子 Agent 模式并行启动的子 Agent 实例不得超过 4 个；
6. 多角色子 Agent 输出必须回到主控汇总，不得直接成为事实源；
7. 子 Agent 发现 Human Gate 场景时必须标注，不得自行执行高影响写入；
8. 不为每个角色创建自定义 Agent；角色定义作为运行时参数注入；
9. 需要创建、导入、启用、修改或删除 Agent 时，必须触发 Human Gate。

AgentRoleInvocation 建议结构：

```yaml
role_id: 角色 ID，必填
role_name: 角色名，必填
role_prompt: 由角色关注点和本次主题合成的角色提示，必填
topic: 分析主题，必填
context_pack: 本角色可读取或已提供的事实源摘要，必填
output_format: 本角色应返回的结构，必填
boundary_rules:
  - 不直接写入事实源
  - 不替代 Human Gate
  - 不把工具缓存或派生视图作为事实源
human_gate_rules: 本次需要特别关注的 Human Gate 条件，选填
```

## 9. 工具协作适配

多角色思考可使用 Code、命令或通用工具辅助以下工作：

1. 搜索和读取相关事实源；
2. 生成或校验 Context 包；
3. 检查 Markdown 链接、编号、引用和 YAML 语法；
4. 聚合变更影响文件；
5. 准备受控写入候选内容；
6. 展示分歧、风险和 Human Gate 待确认项。

工具不得直接决定角色结论，不得直接调用 AI、Skill 或 Agent，不得将工具缓存、命令输出或派生视图作为最终事实源。

多角色思考当前不创建专用 Code、工具、MCP Server 或工具校验 schema。若未来确需专用实现，应先评估价值、事实源边界、工作流程关系、运行闭环测试和 Human Gate。

## 10. 事实源回写与证据留存

多角色思考完成后，应按以下规则判断是否回写：

| 输出类型 | 回写位置 |
|---|---|
| 仅服务当前对话的分析 | 不回写，保留在当前上下文 |
| 需要执行的明确动作 | 创建或更新 Task |
| 有保留价值但暂不任务化的信息 | 创建或更新 Memo |
| 已确认且长期有效的决策 | 创建或更新 ADR，或在 Human Gate 后升级为正式规范 |
| 风险判断 | 写入 Task、Memo、ADR、Pitfall 或 docs 报告中的对应字段或段落，不创建独立 Risk 对象 |
| 验证证据、检查结果或关闭依据 | 写入 Task 的验证/关闭字段、被引用结果物、Change、Pitfall 或 docs 报告，不创建独立 Evidence 对象 |
| 对事实源产生影响的实际修改 | 按 Change 规范通过 Git commit 记录 |
| 管辖项目正式报告或经授权的报告正文 | Human Gate 后写入 docs/ 对应正文或报告；42 产品落地与检查默认只输出当前过程报告，不自行创建文档 |
| 规范或规则正文 | 写入 `docs/specs/` 或运行投影入口，并评估 Human Gate |

未写入权威事实源前，多角色思考报告不能被后续 AI 当作稳定事实引用。

多角色思考的证据至少包括：

1. 分析主题和输入来源；
2. 读取的关键事实源；
3. 选择的分析模式及原因；
4. 多角色子 Agent 模式的调用参数、角色边界和隔离说明；
5. 选用角色及选择理由；
6. 各角色结论、风险和建议动作；
7. 汇总结论、分歧和 Human Gate 判断；
8. 若发生写入，记录写入文件、写入原因、验证结果和 Change 关联。

## 11. 机制适配边界

多角色思考的机制适配边界如下：

| 能力 | 当前结论 | 边界 |
|---|---|---|
| Rules / Instructions | 需要薄入口 | 只做触发摘要和权威文档导航，不复制完整流程 |
| Skill | 默认不创建 | 本流程由主控读取本文执行；Skill 不得直接调度子 Agent |
| Agent | 可作为增强模式 | 由主控注入角色参数，输出回到主控；稳定结论回写后才生效 |
| Code / 工具 | 默认不创建专用实现 | 可使用通用读取、校验、聚合工具；不得决定角色结论或替代 Human Gate |
| Web | 默认不创建专用页面 | 报告和 Human Gate 可在对话中完成；若未来进入 Web，应遵守 08 的受控交互边界 |
| Hook / CI | 默认不要求 | 若未来需要稳定触发多角色审查，应先定义触发时机、测试用例和降级方式 |

多角色思考相关输入材料中的有效内容已按性质并入本文。本流程不恢复固定 `NN.01` 至 `NN.06` 子文档机制，也不要求 AI 回读输入材料。

## 12. 行动特有可测试性锚点

多角色思考至少应能派生以下测试锚点：

| 类型 | 可测试性锚点 |
|---|---|
| 正向场景 | 用户明确要求多角色、多视角或跨模块影响评估时，AI 应进入多角色思考 |
| 负向场景 | 简单问答、低风险单文件小改或用户明确拒绝额外分析时，AI 不应强行进入多角色思考 |
| Gate 场景 | 模式选择、事实源写入、Agent 权限变化、临时职能升级或规范修改应暂停确认 |
| 回写场景 | 报告中的稳定动作、决策、经验、风险判断或验证证据应按 20-39、03 和 09 分流 |
| 失败降级 | 缺少事实源、角色依据不足、当前环境无可调用 Agent 或结构化问询不可用时，应降级为轻量模式、询问用户或停止 |
| 回归风险 | 修改角色集合、模式选择、Agent 调度或回写规则后，应重新检查 Rules 薄入口、40 索引、10 运行闭环测试和相关工作模型规范 |

具体测试用例、预期行为矩阵、失败诊断和回归用例不写入本文，应按 `docs/specs/10-运行闭环测试规范.md` 进入测试用例事实源或 Code 测试实现。

## 14. 检查要求

检查一次多角色思考执行是否符合本流程时，应确认：

| 检查项 | 标准 |
|---|---|
| 触发原因 | 输出中包含明确触发原因，且可追溯到本文 Scenario 条件之一 |
| 分析模式 | 明确声明主上下文轻量模式或多角色子 Agent 模式，并说明原因 |
| 角色选择 | 说明 selected_roles、excluded_roles、role_origin 和选择理由 |
| 临时职能 | runtime 临时职能已说明 temporary_scope、preset_gap 和 promotion_candidate |
| 事实源读取 | 列出本次分析读取的关键规范、工作对象、docs 或代码文件 |
| 分角色输出 | 每个角色包含适用性、影响范围、结论、风险和建议动作 |
| 汇总输出 | 汇总一致结论、分歧点、风险等级、执行顺序、回写建议和 Human Gate |
| 回写判断 | 按本文 §10 判断稳定事实应写入哪里，未恢复 Risk / Evidence 独立对象 |
| Human Gate | 按本文 §7 判断是否暂停确认 |
| 事实源边界 | 未把过程分析、Agent 输出、工具缓存、临时职能或 Web 状态直接作为稳定事实 |
| 机制边界 | 未创建固定机制子文档，未让 Skill、Code 或工具直接调度子 Agent |

检查本文是否作为具体工作流程规范完成时，应确认：

1. 覆盖 03.05 要求的标准章节；
2. 与 06 的通用规则不冲突；
3. 在 40 中登记为 active；
4. 多角色思考相关输入材料的有效内容已吸收、分流或明确不采用；
5. 当前权威路径为 `docs/specs/44-multi-role-thinking-多角色思考.md`；
6. 不再把 Risk / Evidence 作为独立工作模型恢复；
7. 行动特有可测试性锚点已写入本文。
