## 1. 目标

v2 的目标不是复制一套新规范，而是把现有 specs 的权威归口、读取路径和知识地图结构构件重整为更服务 AI 的体系。

目标判断以 00 的 AI 第一服务对象和 V1-V10 为准：

1. 服务 V1：AI 能快速定位该读什么；
2. 服务 V2：AI 获得足够但不过载的可行动理解；
3. 服务 V3：AI 能判断定义归口、消费关系、事实源边界和风险；
4. 服务 V4：AI 能稳定执行，而不是依赖聊天记忆；
5. 服务 V5：AI 能识别 Human Gate；
6. 服务 V6：关键结论能验证；
7. 服务 V7：证据能沉淀；
8. 服务 V8：稳定事实可靠回写；
9. 服务 V9：Human 能看见态势、风险和证据；
10. 服务 V10：可复用经验、反复问题和体系缺口能回流。

## 2. 基本原则

1. `specs/` 在切换前仍是唯一 active 正式规范事实源。
2. `specs-v2/` 只承载未 active 的计划、结构和占位。
3. 不批量迁入正式规范正文；每篇规范必须单独和 Human 核对后再迁入。
4. 知识地图是实现 V1/V2/V3/V9/V10 的方法之一，不是 00 中的独立价值判断。
5. 知识地图不是新事实源、不是工作对象、不是第七类构成要素，也不是资产分类。
6. 知识地图由规范结构构件、工作对象字段、管辖项目配置和 Git 提交记录经 Code 实时解析生成。
7. Web 暂不实施；v2 先完成规范结构和 Code v2 只读解析能力。
8. v1 子规范形式和成员文件中的机制性契约不得因 v2 减少文件数量而消失。
9. 逐篇迁入前必须先通过 `V1-UNDERSTANDING-GATE.md` 中的机制理解门禁。
10. v1 03/03.01 中的正式规范必要章节、`ldvh_doc` 机器身份、保障要求、Human Gate、引用纪律、吸收规则和 Code 缺口处理必须由 v2 01 承接。
11. `specs-v2/` 的未 active 状态只由文件状态、身份块和计划文件表达；单篇规范正文必须按目标正式规范口径书写，不使用讨论性、试探性或长期候选口吻。

编号调整理由：

1. 01 是规范体系与治理的结构元规范；规范身份、必要章节、权威归口、引用关系、附件授权、Code 消费入口、入口定位和最小读取路径应先由 01 定义，知识地图结构构件由这些规范结构派生。
2. 原计划中独立的系统地图规范不再保留；目录说明、入口定位和编号关系由 01 的规范结构与知识地图派生机制承接。
3. 术语不再占主干编号；术语治理归入 01 正文，术语表归入 `01.Att.02-术语表.md`，规范表达清单归入 `01.Att.06-规范表达清单.md`。
4. 主干 02-06 按六类构成要素中除 01 已承接的“规范体系”外的五项排序：事实模型、行动编排、Code、Web、运行时扩展。
5. 07 和 08 是跨构成要素的底层基础规范，不是第七类或第八类构成要素。事实源、Git 追溯和测试验证服务六类构成要素，但不得被任何单一构成要素静默吞并。
6. Git 提交本体规则不得并入行动编排；Git 提交编排流程归 03，commit message 契约、Git commit records 追溯和派生展示规则归 07，并由 04、05 分别承接实现校验和展示消费。

依赖顺序约束：

1. v2 01 是规范体系与治理规范，不是 v1 04 保障机制的前移。
2. v2 02 承接事实模型、字段契约和事实实例对全局事实源原则的适配；v1 09 全局事实源规则由 v2 07 单篇承接，未核对前不得视为完成迁移。
3. v2 03 承接行动编排通用规则、03.03 成员机制和 30-59 具体流程迁移判断；v1 44 Git 提交编排作为具体行动编排成员迁移判断进入 03，v1 10 Git 提交规范本体不得作为 03 附件承接。
4. v2 04 承接 Code 确定性执行、只读解析、校验、知识地图投影和受控写入边界；测试治理由 v2 08 承接，04 只说明自身实现测试入口和 Code 诊断可验证性。
5. v2 07 承接 v1 09 和 v1 10 的事实源、Git 追溯和提交消息契约，不承接 AI 提交流程；v1 44 的提交流程仍归 03。
6. v2 08 承接 v1 11 测试基础规范，定义跨构成要素的测试治理、验证声明和测试证据边界；具体 Code/Web 测试实现仍由对应实现域承接。
7. v2 06 若合并 v1 04 系列，必须显式保留 v1 04、04.01、04.02、04.03 的声明、资产登记机制、环境适配和检查链路，并保留 v1 对 Code/Web、运行时扩展和其它可维护承载物的消费边界映射。

## 4. 附件与成员区

附件不是常规子规范体系。附件只承载主规范授权的注册表、矩阵、模板、示例或长清单。

附件不得承载 `ldvh_doc`、`ldvh_member`、保障要求类型、成员锚点、资产登记机制、环境适配状态或其他机制性事实；这些必须由主规范、成员主文件或正式资产自描述承载。

| 区域 | 用途 | 边界 |
|---|---|---|
| 根目录 `{父编号}.Att.{两位序号}-{名称}.md` | 术语表、字段注册表、知识地图关系类型、迁移承接清单、环境矩阵、模板、示例 | 不定义主规范原则 |
| `20-29-事实模型/` | 具体事实模型迁移写作区 | 每篇单独核对 |
| `30-59-行动编排/` | 具体行动编排迁移写作区 | 每篇单独核对 |

## 5. 知识地图结构构件

v2 主规范应天然支持 Code 抽取知识地图，但不得要求 AI 读取全量文件。知识地图依赖规范结构、字段契约、管辖项目配置和 Git 记录等结构构件，由 Code 实时解析生成，只读派生，不落盘为新的事实源。

结构构件包括：

1. 规范身份；
2. 权威域；
3. 定义项；
4. 消费项；
5. 被检查项；
6. 回写目标；
7. Human Gate 关系；
8. 附件授权；
9. 成员集合；
10. 管辖项目命名空间。

边类型先放入 `01.Att.01-知识地图关系类型表.md`，随 01 单篇核对确认。

## 6. 已记录判断

以下判断只作为 v2 计划记录，不构成正式迁入：

1. 00 从“理念与纲要”收敛为“理念与价值标准”，作为所有 v2 内容的最高判断基准。
2. V1-V10 不只是评价标准，而是六类构成要素及其下属机制成为构成要素实践的准入门槛。
3. 字段、附件、资产承载物、工具、知识地图关系、Code 输出和 Web 展示都必须先归属六类构成要素之一，不得在 00 中被写成并列准入主体。
4. 知识地图是服务 V1/V2/V3/V9/V10 的方法之一，不在 00 中作为独立章节维护。
5. 运行闭环不在 00 中作为独立章节维护；00 只保留闭环相关价值判断，具体事实对象生命周期、AI 行动生命周期、证据回写、Git 追溯和持续回流分别由 02、03、04 及相关事实模型或行动编排规范承接。
6. 01 定义所有 v2 规范共同遵守的规范身份、必要章节、权威归口、引用纪律、附件规则、知识地图输入、规范保障要求锚点、Human Gate 锚点和 Code 缺口处理；后续专题规范若需要专属结构，应由自身在单篇核对时声明。
7. 独立的系统地图规范不再保留；目录说明、入口定位、编号关系和最小读取路径由 01 的规范结构与知识地图派生机制承接。
8. 字段契约属于事实模型，但 02 只能成为统一治理入口，不得成为所有具体模型 schema 的单一权威。
9. 公共字段稳定性由 02 中央定义、20-29 具体模型声明采用、Code 生成字段矩阵校验共同保障；注册表不得反向定义字段存在性、必填性或状态条件。
10. 30-59 行动编排不能简单合并；03 承接通用规则和成员结构，30/41/42/43/44 等具体流程仍需保留各自职责。
11. Web 暂不实施不等于 Web 契约可忽略；事实对象 DTO、状态字段和 Spark 创建白名单仍是迁移回归线。
