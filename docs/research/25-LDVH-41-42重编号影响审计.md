### 3.1 40 当前登记

### 3.2 当前 42 更像 bootstrap 流程

当前 42 的正文定位是：检查当前事实源和环境，输出当前缺口，经 Human 授权后逐项落地，完成后复检，最后输出本次落地与检查报告。

当前 42 处理的问题包括：

1. 首次安装、接入、初始化或启用 LDVH；
2. 当前环境确认；
3. 管辖项目配置发现与确认；
4. 项目落地；
5. 缺口补齐；
6. 漂移检查；
7. 可用性检查；
8. LDVH 自身 dogfood 管辖和落地与检查报告。

这些职责更接近所有后续工作流程的基础可用性检查，因此存在“当前 42 更适合作为未来 41”的候选判断。

### 3.3 当前 41 更像高级联动统筹流程

当前 41 的正文定位是：AI 在新增、修改、检查或执行正式规范时，收集规范落地要求、分流承接机制、判断环境适配和运行投影缺口、安排验证并回写结果。

当前 41 处理的问题包括：

1. 正式规范新增、修改、重命名或删除；
2. 规范落地要求变化；
3. Code / Web / Skill / Agent / Hook / CI / Rules / Instructions 承接边界变化；
4. 运行投影漂移；
5. 规范落地要求是否具备保障机制、环境适配、运行投影、验证方式和回写出口；
6. landing-plan 或等价统筹输出。

这些职责默认 LDVH 基础入口、事实源、工作流程集合、Code/Web/运行投影检查链路已经具备最低可用性，因此更像在基础落地之后运行的高级联动统筹流程。

### 4.4 landing-plan 与 plan 类输出问题

最新讨论进一步修正：`landing-plan` 这个名称不再准确。

原因是该过程输出当前实际表达的不是“落地”，而是一次受控变更发生后，LDVH 如何识别影响面、拆分执行、协调 Agent / Task / Code / Web / tests / 规范同步、安排验证并形成关闭证据。

但后续讨论又进一步修正：问题不只是把 `landing-plan` 改名为 `change-plan`。如果正式工作流中的工作安排、执行拆分、验收标准和关闭证据都应布置在 Task 中，那么独立的 plan 类过程输出可能不应成为正式机制。

因此，`change-plan / 变更联动计划` 只能作为候选概念保留，不应立即实体化：

```text
change-plan = 变更联动计划，候选概念，是否需要独立存在待定
```

其候选定义为：

```text
变更联动计划用于描述一次 LDVH 受控变更的影响面、联动对象、执行拆分、Agent 调用建议、Task 创建建议、验证要求和关闭证据要求。
```

它不是：

1. LDVH 落地与检查流程的 bootstrap 报告；
2. Task；
3. 正式事实源；
4. 环境承接矩阵；
5. Bootstrap Code 基线需求定义；
6. 规范本体。

当前更稳的判断是：暂不推进 `landing-plan` → `change-plan` 改名，也不急于创建独立 change-plan 工作流。应先确认正式工作安排是否统一由 Task 承载。

如果后续确认仍需要 plan 类输出，则再讨论其名称、字段、归属和与 Task 的关系；如果确认 Task 足以承载正式安排，则当前 41 或后续更名流程应转为“识别影响并建议创建 / 更新 Task”，而不是生成独立 plan。

无论最终是否保留 plan 类输出，已有 `landing-plan` 命名已进入 Code、tests、Web API、Web 页面、正式规范和工作对象。任何迁移都不应作为零散文本替换处理，应由独立 Task 承载。

## 5. 循环依赖风险

### 5.1 当前 42 对当前 41 的依赖较深

当前 42 明确把当前 41 纳入相关规范、Context、只读检查、缺口分流、landing-plan 消费和工具协作中。

典型依赖包括：

1. Context 要求中读取 `docs/specs/41-landing-orchestration-规范落地统筹.md`；
2. 只读检查要求当前 41 能提供或生成本次范围内的落地要求聚合结果；
3. 检查 41 时，42 应按 41 的分层抽象机制消费触发保障状态；
4. 当 41 已提供 `landing-plan` 或等价过程输出时，42 应把它作为只读输入消费；
5. landing-plan 缺失、不完整或来源不可追溯时，42 报告为 41 输出缺失或不足。

这些逻辑适合“基础落地已完成后的高级检查”，但不适合作为 bootstrap 的执行前提。

### 5.2 bootstrap 阶段不能要求 41 已可用

如果当前 42 用于首次安装、接入、初始化或启用 LDVH，那么它不能要求当前 41、41 Skill 或 landing-plan 先可用。

原因是当前 41 的可用性本身属于 LDVH 工作流程能力、运行投影和 Code/Web 辅助能力的一部分，应该由基础落地检查发现、记录和分流，而不是作为基础落地检查的先决条件。

更安全的边界应是：

```text
基础落地与检查流程可以检查规范落地统筹流程是否存在、是否 active、是否有缺口。
基础落地与检查流程不得要求规范落地统筹 Skill 或 landing-plan 已经可用才能启动。
```

### 5.3 04.03 也绑定了当前 41 生成、42 消费

`docs/specs/04.03-环境能力清单与环境适配规范.md` 当前写明：承接单元字段由 41 规范落地统筹流程生成，42 只消费不生成，04.03 只定义字段结构和选择原则。

这一关系在“当前编号不变”时是清晰的，但如果当前 42 调整为未来 41、当前 41 调整为未来 42，则该句必须同步，否则会变成编号错位。

更稳的表述候选是：

```text
承接单元字段由规范落地统筹流程生成；LDVH 落地与检查流程只消费不生成。
```

也就是先用流程名降低编号耦合。

## 6. 重编号候选方案

### 6.1 方案 A：不重编号，只修边界

保留当前：

```text
41 = 规范落地统筹
42 = LDVH 落地与检查
```

只修正：

1. 当前 42 不得在 bootstrap 前提中强依赖当前 41；
2. 当前 42 对当前 41 的依赖改为“可选输入 / 缺口检查”；
3. 当前 41 增加 Skill 化、00 价值判断、Agent 调度建议和 Task 先行候选；
4. 04.03、42 等位置尽量用流程名而不是编号描述关系。

优点：改动小，避免大范围重命名和引用迁移。

缺点：编号顺序仍然不符合执行依赖直觉，后续讨论中容易继续误解“41 是基础流程”。

### 6.2 方案 B：正式重编号

调整为：

```text
未来 41 = LDVH 落地与检查
未来 42 = 规范落地统筹
```

需要同步：

1. 文件名；
2. 文档标题；
3. 40 工作流程集合索引；
4. 01 目录说明；
5. 04、04.02、04.03、04.06 等正式规范引用；
6. 当前 42 内部对当前 41 的依赖关系；
7. tools、tests、Web API、Web 页面和 i18n 文案；
8. `task-0061-landing-orchestration-closure-loop.yaml` 等工作对象；
9. research / refs 中仍有后续指导价值的引用；
10. 24 文档关于 41 Skill 的命名。

优点：编号顺序和执行依赖更自然，bootstrap 流程先于高级统筹流程。

缺点：影响面大，必须 Human Gate，且需要专门 Task 承载执行、校验和回滚判断。

### 6.3 方案 C：暂不重编号，先去编号化

短期保留当前文件和编号，但在正式规范中尽量用流程名表达关系：

```text
LDVH 落地与检查流程
规范落地统筹流程
```

而不是在关键边界中写死：

```text
41 生成，42 消费
42 依赖 41
41 Skill
```

优点：降低后续重编号成本，也能先解决循环依赖和命名漂移。

缺点：不能完全解决编号顺序不自然的问题。

## 7. Bootstrap Code 基线需求归属

### 7.1 Code 需求不是运行时发现项

最新讨论修正了一个关键判断：LDVH 落地与检查所需的 Bootstrap Code 能力，不应在执行检查时“发现缺失后再确定需求”。

更准确的边界是：

```text
LDVH 落地与检查需要哪些 Bootstrap Code 能力，应由 LDVH 落地与检查流程预先定义。
这些能力是基础检查的前置设计内容，不是运行时临时缺口发现内容。
```

原因是 LDVH 落地与检查需要在没有外部环境支援的条件下完成基础检查。如果执行时才临时发现“还需要某个 Code 能力”，再临时定义需求、实现工具、补测试、回到检查流程，就会让 bootstrap 变成边检查边构建，无法形成稳定、可复现的初始化能力。

因此，Bootstrap Code 能力应作为 LDVH 落地与检查流程的基线需求先被定义、实现和验证。执行 LDVH 落地与检查时，这些能力应作为已具备能力被调用。

### 7.2 需求归 LDVH 落地与检查流程，不归 07

Bootstrap Code 基线需求应归属于 LDVH 落地与检查流程，也就是当前 42 或未来编号调整后的对应流程。

`docs/specs/07-Code确定性执行实现规范.md` 不应定义 LDVH 落地与检查到底需要哪些 Code 能力。07 的职责是定义 Code 实现边界、实现规则、验证规则、受控写入和维护规则。它可以约束这些 Code 能力如何实现和验证，但不决定 LDVH 落地与检查需要哪些能力。

更清晰的职责边界是：

| 层 | 职责 |
|---|---|
| LDVH 落地与检查流程 | 定义 bootstrap / 初始化检查必须具备哪些基线 Code 能力 |
| 07 Code 实现规范 | 定义这些 Code 能力如何实现、验证、维护和避免越界 |
| 10 运行闭环测试规范 | 定义这些能力如何建模为可复现测试和闭环验证 |
| Task | 承载具体 Code 能力补齐工作的目标、范围、验收和关闭证据 |
| `tools/` | 实现 Code 能力 |
| `tests/` | 证明 Code 能力 |

因此，07 参与的是实现约束，不参与需求定义。

### 7.3 Bootstrap Code 能力缺失的性质

如果 LDVH 落地与检查流程已定义某项 Bootstrap Code 基线能力，但 `tools/` 和 `tests/` 未实现或无法验证该能力，这不应被视为普通环境降级项。

这类问题应被视为 LDVH 自身 Code 能力资产未完成或不完整。

对应处理方式应是：

1. 不宣称 LDVH 落地与检查流程已经具备完整 bootstrap 能力；
2. 不把该缺失归因于外部 AI 开发环境；
3. 不通过规范落地统筹 Skill 临时弥补；
4. 创建或使用已有 Task 承载具体 Code 能力补齐；
5. 完成 tools 实现、tests 验证和必要规范同步后，再宣称该基线能力具备。

## 8. 推荐判断

当前不建议立刻执行正式重编号。

推荐先采用方案 C：暂不重编号，先去编号化并修正 bootstrap 边界。

理由：

1. 当前 42 引用面较大，直接重编号风险高；
2. landing-plan 已进入 Code、tests、Web API 和 Web 页面，且 plan 类输出是否继续存在仍待判断，不能只改 specs；
3. 当前 42 对当前 41 的依赖需要先拆成“可选输入 / 缺口检查”，否则重编号后仍可能保留循环依赖；
4. 规范落地统筹 Skill 的命名应等编号关系确认后再定，当前宜称为“规范落地统筹 Skill”；
5. 真正重编号应作为独立高影响 Task 执行，并触发 Human Gate。

建议下一步：

1. 先在当前 42 或未来对应的 LDVH 落地与检查流程中定义 Bootstrap Code 基线能力；
2. 明确 bootstrap 最低路径不能依赖当前 41、规范落地统筹 Skill 或 landing-plan；
3. 明确 Bootstrap Code 基线需求不是运行时发现项，而是 LDVH 落地与检查流程的前置设计内容；
4. 把当前 42 中“必须消费 41”的表达改成“如存在则消费；不存在则记录为规范落地统筹能力缺口”；
5. 把 04.03 中“41 生成、42 消费”改成“规范落地统筹流程生成，LDVH 落地与检查流程消费”；
6. 暂不改文件名；
7. 暂不创建规范落地统筹 Skill；
8. 暂不直接批量替换 landing-plan；
9. 先确认正式工作安排是否统一由 Task 承载；
10. 后续如要重编号、保留 plan 类输出或执行 `landing-plan` 改名，先创建 Task 承载完整迁移。
