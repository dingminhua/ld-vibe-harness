# 网站整体性多角色审视研究

> 关联任务：task-0030
> 范围：LDVH Web 展示层整体信息架构、导航逻辑、页面关系和信息密度
> 结论：桌面端应从“页面平铺浏览”升级为“左侧导航 + 中间主内容 + 右侧扩展阅读区”的三段式阅读体验。

## 1. 角色视角与核心诉求

| 角色 | 核心诉求 | 主要问题 |
|---|---|---|
| 新用户 | 快速理解 LDVH 有哪些对象、当前项目处于什么状态、下一步该看哪里 | 页面术语密度高，缺少引导路径和对象关系解释 |
| 项目管理者 | 快速判断哪些任务在推进、哪些依赖阻塞、变更是否可追溯 | Dashboard 信号分散，待推进、最近活动、校验、变更之间缺少优先级 |
| 开发者 | 从任务进入相关代码、文档、验收标准和验证命令 | 对象详情页字段平铺，关联文档需要跳转，容易打断上下文 |
| AI 协作者 | 精确读取事实源、状态、依赖、验收项和引用关系 | 页面展示还不能充分表达状态机、Human Gate、blocked_by 等执行约束 |

## 2. 当前网站整体性观察

### 2.1 信息架构已经具备基础闭环

现有页面覆盖了 Dashboard、ObjectList、ObjectDetail、Validate 和 Changelog，已经能完成“看全局状态 → 找对象 → 看详情 → 校验 → 看变更”的基础路径。

### 2.2 页面之间的主次关系还不够明确

Dashboard 同时展示统计、最近活动、最近变更、校验状态和待推进事项，但用户不一定能判断哪个区域代表“现在最应该处理的工作”。后续应在 Dashboard 和对象详情内强化行动信号，不再新增并行执行入口。

### 2.3 对象详情页更像事实平铺页，而不是工作阅读页

ObjectDetail 能展示完整 YAML 派生内容，但没有区分主线事实和辅助事实。对于 Task，用户最关心的是状态、验收、依赖、证据；对于 ADR，用户最关心的是决策、状态、影响和关联对象。不同对象需要差异化阅读重点。

### 2.4 关联文档的跳转成本偏高

Web 设计文档、Task、ADR、Intent 之间存在大量引用。当前跳转会替换主页面，用户读完关联内容后需要返回，深度阅读体验不连续。

## 3. 三段式布局方案

### 3.1 布局定义

```text
┌──────────────┬──────────────────────────────┬──────────────────────┐
│ 左侧导航     │ 中间主内容                   │ 右侧扩展阅读区       │
│              │                              │                      │
│ 对象类型     │ 当前对象详情 / 任务主线      │ 关联文档预览         │
│ 页面入口     │ 验收、状态、证据、关系       │ 关联对象摘要         │
│ 校验/变更    │                              │ YAML / Markdown      │
└──────────────┴──────────────────────────────┴──────────────────────┘
```

### 3.2 左侧导航

左侧导航继续承担全局定位：Dashboard、对象类型、Validate、Changelog。它不应该承载过多动态内容，避免与 Dashboard 重复。

### 3.3 中间主内容

中间区域展示当前任务或对象的主阅读路径：

- Dashboard：展示全局信号；
- ObjectDetail：展示对象摘要、核心字段、验收和证据；
- ObjectList：展示对象集合与筛选。

### 3.4 右侧扩展阅读区

右侧区域用于承接“相关但不应该打断主线”的内容：

- 点击 related_docs 时预览 Markdown；
- 点击 related_tasks 或 related_adrs 时展示对象摘要；
- 查看 YAML 原文；
- 展示当前对象的引用关系和追溯链。

右侧区域不应成为新的事实源，只读取 API 或已有文件内容。

## 4. 多角色问题与改进建议

### 4.1 新用户视角

问题：对象类型、状态和工作流术语密集，缺少渐进解释。

建议：

- Dashboard 顶部增加一句项目态势摘要；
- 对象详情页顶部展示“这是什么”和“下一步是什么”；
- 对象详情页作为新用户理解执行闭环的入口。

### 4.2 项目管理者视角

问题：最近活动、待推进、校验和变更都是重要信号，但优先级不够明确。

建议：

- Dashboard 保持最近活动在待推进上方，优先呈现动态；
- 待推进区域突出 executing、verifying、review_needed；
- 校验失败时在 Dashboard 形成强提示；
- Changelog 与任务详情形成互链，显示任务完成证据。

### 4.3 开发者视角

问题：从任务到实现文件、文档依据、验收项之间缺少一屏联动。

建议：

- ObjectDetail 的 Task 视图优先展示 acceptance、blocked_by、related_docs；
- related_docs 在右侧扩展区打开；
- closure_evidence 中的文件路径和命令未来可渲染为可点击引用或命令块。

### 4.4 AI 协作者视角

问题：AI 需要准确理解状态机和执行约束，普通 UI 不能弱化这些事实。

建议：

- Task 页面明确展示 blocked_by 是否已满足；
- planned、executing、verifying、review_needed 使用一致的状态说明；
- Human Gate 相关状态在 UI 中保留提示，但不在 Web 端绕过执行规则；
- Validate 页面继续作为事实契约检查入口。

## 5. 整体性改进方案

### 5.1 信息架构

采用“全局态势 → 对象详情 → 校验与变更追溯”的主路径：

1. Dashboard 负责项目态势；
2. ObjectDetail 负责事实阅读与引用追溯；
3. Validate 和 Changelog 负责可信度与证据。

### 5.2 交互模式

- 普通导航仍使用路由跳转；
- 关联阅读使用右侧扩展区；
- 移动端保留单列布局，右侧扩展区降级为抽屉；
- 原始 YAML 默认收起，需要审计时展开。

### 5.3 视觉密度

- Dashboard 高密度但分层明确；
- ObjectDetail 中等密度，优先阅读核心事实；
- Validate 和 Changelog 保持工具型页面的信息密度。

## 6. 建议落地顺序

1. 先完善 ObjectDetail 字段语义化渲染；
2. 再实现右侧扩展阅读区基础能力；
3. 然后调整 Dashboard 与对象详情的行动信号边界；
4. 最后补充面向新用户的解释性微文案。

## 7. 设计原则

- 不引入新的 UI 框架；
- 不新增第二事实源；
- 不为了移动端牺牲桌面深度阅读；
- 不让右侧扩展区替代主内容，只承接上下文；
- 所有交互增强必须服务事实源读取、状态判断和执行闭环。
