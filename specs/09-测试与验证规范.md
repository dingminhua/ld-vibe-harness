## 1. 价值判断

本文存在的价值，是让 AI 的完成声明、写入、提交、关闭和交还有可复现证据，而不是只凭自述、印象或局部观察。

本文主要服务 00 的 V6 强制验证、V7 格式回写和 V8 范式交互：测试与验证规定哪些关键结论必须验证、验证证据如何回指和回写、未验证范围和残留风险如何向 Human 呈现。测试与验证不是第六类构成要素，而是跨五类构成要素和保障与衔接层的验证治理。

## 2. 权威依据

本文承接 `specs/00-理念与构成.md` 的强制验证价值、`specs/01-保障与衔接.md` 的 evidence 和 diagnostic 边界、`specs/02-AI行为规范.md` 的不得虚假完成规则、`specs/03-事实源与Git溯源规范.md` 的证据事实源边界，以及 `specs/04-Specs基础规范.md` 的结构规则。

若测试结果与事实源或 specs 冲突，应回到事实源和 specs；测试不得反向定义规则。

## 3. 归口边界

本文归口定义测试治理、验证声明、失败阻断、测试证据边界、等价验证和同步触发。

本文不归口定义具体测试框架、测试文件清单、Web 页面测试、Code 输出 schema、行动模板流程或事实对象字段。实现细节由对应实现域和 `tests/` 承接。

本文只定义验证要求、测试治理、证据边界、失败阻断、Human 验收和同步触发，不定义具体测试框架、目录拆分、fixtures 组织、mock 策略、性能调优或每个测试文件的职责。测试实践由 `tests/`、对应实现域测试和实现域文档承接；`tests/` 可以保存可执行测试、fixtures、正反例、回归样例和测试工具，但不得反向改写 specs、事实源、Human Gate、Code/Web 契约或完成声明。

V3 不强制要求 `tests/docs/` 作为固定目录。只有当测试实现实践形成稳定维护需求，且不替代 specs 规则或验证声明时，才可由实现域自行建立测试文档。

## 4. 适用范围

本文适用于：

1. AI 声称完成、通过、关闭、可交付或可提交前的验证判断；
2. Code、Web、行动模板、事实模型、事实源和环境入口相关测试；
3. 自动化测试、命令校验、等价验证、Human 验收和回归验证；
4. V2 `08-测试基础规范.md` 与 `08.Att.*` 的迁移判断。

## 5. 验证方式分层

V3 认可以下验证方式：

| 验证方式 | 适用场景 | 要求 |
|---|---|---|
| 自动化测试 | 可机械复现的行为、结构、正反例和回归 | 说明命令、范围和结果 |
| 命令校验 | 文档结构、CLI 输出、格式、引用或构建可稳定反馈 | 说明命令和关键输出 |
| 等价验证 | 自动化测试暂不可行但可用最小样例、回读或手动命令覆盖关键风险 | 说明原因、步骤和残留风险 |
| Human 验收 | 涉及授权、体验、方向确认或风险接受 | 说明确认对象、影响范围和证据 |
| 回归验证 | 修复、迁移或行为变更后防止复发 | 说明失败前表现和通过条件 |

未执行、失败、不可复现或无法回指来源的验证，不得写成“已验证”。

验证入口应按风险和影响范围选择，不能把最慢的全量测试当作所有改动的默认要求，也不能为了节省时间跳过关键风险。AI 应优先选择能覆盖本次变更风险的最小稳定验证入口，并在完成声明中说明未运行范围和残留风险。

### 5.1 `verification_plan` 输出契约

`verification_plan` 是测试选择说明，用于在执行验证前回答“为什么选择这些入口、覆盖哪些层、排除哪些层、剩余风险是什么”。它不是测试结果、事实源、授权、Human Gate 或完成证明；即使 `verification_plan` 生成成功，也不能据此声明验证通过。

当 AI 选择自动化测试、命令校验、等价验证或组合验证时，应先形成 `verification_plan` 或等价说明。该说明至少包含：

| 字段 / 信息 | 要求 | 边界 |
|---|---|---|
| `profile` / 验证入口类型 | 说明本次使用快速层、目标层、runtime / 慢速层、全量层或等价组合 | 具体 profile 名称、CLI 参数和命令由 tests 实现域定义 |
| `changed_paths` / 输入范围 | 说明本次选择所依据的 changed paths、target 或风险对象 | 不得把空 changed paths 写成全项目已覆盖 |
| `selected_layers` | 列出实际会运行或已经运行的验证层 | 只表示覆盖范围，不表示结果已通过 |
| `excluded_layers` | 列出本次没有覆盖的层级 | 被排除层必须进入未验证范围或残留风险判断 |
| `selection_reasons` | 说明为什么当前入口足以覆盖本次风险，或为什么需要升级 | 不得用“节省时间”替代风险判断 |
| `unverified_scope` | 说明未运行、不可复现、不能自动验证或需要 Human 验收的范围 | 不得在完成声明中隐藏 |
| `residual_risk` | 说明未覆盖范围可能留下的风险和后续处理 | 不得被测试通过自动清零 |
| `matrix_refs` / source_refs | 回指本文 §5 验证入口选择矩阵、相关 specs 或实现域测试文档 | 回指不是授权或事实源提升 |

`verification_plan` 的选择流程如下：

1. 先按 changed paths、target、语义影响和用户目标判断风险范围；
2. 再选择能覆盖本次风险的最小稳定验证入口；
3. 若跳过 runtime、慢速、Web、环境入口或其它高成本层，必须在 `excluded_layers`、`unverified_scope` 和 `residual_risk` 中说明；
4. 若局部验证不足以覆盖跨域风险，应升级到更完整的组合验证或明确等价验证；
5. 验证执行后，完成声明仍必须按 §6 和 `09.Att.01` 单独说明验证对象、入口、结果、未验证范围、残留风险和证据回指。

Action Guide 可以输出 `verification_outline` 或等价验证前视图，用于组织 validation guard、Stop Conditions、fallback、capability gap、unverifiable 和残留风险。该输出只回答“接下来需要验证什么、验证不了如何交还”，不替代 `verification_plan` 的测试入口选择，不替代测试结果、验证声明、Human 验收或完成证明。

快速层、目标层、runtime / 慢速层和全量层是覆盖范围分类，不是质量评价。快速层适合开发中的结构检查和低风险变更；目标层适合影响边界清楚的 Code、specs、事实实例或 Web/API 变更；runtime / 慢速层适合 runtime facade、preflight、completion、环境入口、安装验收等行为链路；全量层适合阶段收口、跨域迁移、发布前验证或局部测试无法界定风险的高影响变更。任何层级通过都不能替代 Human Gate、事实源判断或完成声明。

`tests/` 可以定义 runner profile、stage 名称、slow policy、命令参数和维护实践，但不得改变本文的验证声明标准、失败阻断标准或 Human Gate 条件。若 tests 实现域发现本文选择矩阵不足，应回到本文或附件补规则，而不是由 runner 输出反向定义验证规则。

验证入口选择矩阵如下：

| 变更类型 | 默认验证入口 | 升级条件 | 边界 |
|---|---|---|---|
| 单个事实实例新增或改写，且不改变成员规范、字段 schema、状态闭集、validator、测试基础设施或跨域消费逻辑 | 事实实例结构、字段、状态、关系和事实源边界的 validator 或等价命令校验 | 同时修改成员规范、字段 schema、状态闭集、validator、测试基础设施、Web/API 消费、行动模板或环境入口 | 不默认要求全量测试；validator 通过不替代 Human Gate、事实源判断或验证声明 |
| 单篇 spec 文本澄清，且不改变规则语义、字段契约、状态闭集、Human Gate 或 Stop Conditions | specs 结构、identity、引用和章节角色校验，或等价回读检查 | 改变规则语义、保障需求、Human Gate、状态闭集、字段 schema、Code 消费契约或测试口径 | 不用全量测试替代规则审核；不可验证范围必须说明 |
| 事实模型、行动模板、验证规则、字段 schema 或状态闭集变化 | specs validator、相关事实实例校验和对应目标测试 | 影响 Code、Web、tests、Hook、环境入口或多个构成要素 | 需要检查测试同步；局部测试不能覆盖跨域风险时升级全量 |
| Code validator、runtime facade、payload、诊断、测试基础设施或验证入口实现变化 | 覆盖该实现正例、反例和失败条件的目标自动化测试 | 涉及跨域行为、环境入口、提交门禁、Web/API 或发布前收口 | Code 输出不得反向定义 specs、事实源或 Human Gate |
| Git remote ref target、`git push` gate、远端同步诊断或外部状态变更分类变化 | 覆盖普通分支 push target 识别、非只读分类、缺 remote/ref 负例、force/delete/mirror/tag/protected-like ref 强 gate 的目标自动化测试 | 涉及环境 shim、runtime facade、真实远端写入或跨环境插件分类 | 测试不得真实更新远端；repo-local 解析通过不等于 push 已成功或已授权 |
| 外部入口薄引用、真实安装包 / cache、marketplace package、环境插件 shim 或 adapter 边界变化 | 覆盖 repo-local 样例静态检查、真实安装件 / cache / marketplace package 审计、shared classifier / runtime adapter 委托、stale path / 旧 shim 负例和核心三事件 manifest 检查的目标自动化测试 | 涉及真实 lifecycle、安装 / 升级、trust、回滚、payload 或跨环境插件 | repo-local 直测、插件文件存在或 cache 存在不等于 integrated；真实 integrated 必须按 01/30 的 lifecycle 当次依据另行判读 |
| 跨 Code、Web、specs、事实源、测试或环境入口的联动变更，或阶段收口 / 发布前验证 | 全量层或明确等价的组合验证 | 无法用目标测试界定影响范围、存在高风险回归或需要提交前完整信心 | 必须说明全量范围、失败处理和未覆盖范围 |

全量测试适用于：

1. 主线切换、阶段收口、发布前验证或大范围迁移；
2. 跨 Code、Web、specs、事实源、测试或环境入口的联动变更；
3. validator、formal specs 结构检查、字段 schema、事实实例校验实现或测试基础设施本身变化；
4. 修复已知高风险回归，且局部测试无法覆盖影响面；
5. 提交前存在多处高影响文件变更，且无法用目标测试和等价验证充分界定风险。

目标测试、单面 validator、Web API/TypeScript check、构建检查或等价验证适用于：

1. 单一 spec 文本澄清，且不改变规则语义、字段 schema 或 validator 逻辑；
2. 单一 Web/API/Code 模块变更，影响边界可由对应测试直接覆盖；
3. 文档、迁移记录或历史审查材料整理；
4. 已知全量测试成本过高，且本次变更风险可由更小入口稳定覆盖。

分层测试入口应满足：

1. 快速层只覆盖结构验证、formal specs 结构检查或等价轻量门禁；
2. 目标层根据变更路径选择目标测试，并允许在明确说明未验证范围时跳过慢速 runtime/e2e 层；
3. runtime 或等价慢速层专门覆盖 runtime facade、manual adapter、preflight、completion claim、环境入口和静态 e2e 演练；
4. 全量层用于阶段收口、跨域迁移、发布前验证或高风险回归，必须包含 slow 层和 Web 构建/类型/API 检查；
5. slow 层不得被默认并行化；具体 runner profile 名称、命令和 slow policy 由 tests 实现域文档与可执行 runner 承接。

## 6. 验证声明与失败阻断

AI 完成声明至少应说明：

1. 验证对象；
2. 验证入口；
3. 关键覆盖点；
4. 结果；
5. 未验证范围；
6. 残留风险；
7. 证据回指。

验证声明字段闭集和完整验证条件由 `specs/attachments/09.Att.01-验证声明字段表.md` 承接；该附件不得改变失败阻断、Human Gate、测试证据边界或等价验证口径。

出现以下情况时，不得声明完成或关闭：

1. 必须运行的测试失败；
2. 关键验证未运行且没有等价验证；
3. 证据无法回指命令、样例、事实源或 Human 确认；
4. 验证结果与事实源、specs 或实现观察冲突；
5. Human 验收尚未发生却被写成已确认；
6. 仅有工具成功输出，但没有 AI 对范围和风险的判断。

Repair lane 的验证声明必须单独处理。`operation=repair` 或 `mode=repair` 写入后，最终验证只判断 primary target 及必要直接 dependent 的结构性诊断是否被清除，不要求无关全局诊断同时清空；但无关全局诊断必须作为 diagnostic、未验证范围或 residual risk 暴露。若 repair 写入后 primary target 或必要 direct dependent 仍有未清除的结构性诊断，验证声明必须写为失败、未通过或不可完成，不得声明 repair 完成、对象关闭或验收通过。

## 7. 测试证据与同步触发

测试证据用于支持判断，不成为事实源。测试输出、覆盖率、截图、trace、缓存、Mock 数据和临时报告不得替代 specs、事实对象、Git 记录或 Human Gate。

稳定验证结论、失败诊断、残留风险或验收记录需要长期溯源时，应按 03 分流到对应事实源；Git commit records 只溯源相关文件修改和提交说明，不替代验证事实源。

以下变化应检查测试同步：

1. specs 编号、结构、保障需求、Human Gate 或事实源边界变化；
2. 事实模型字段、状态、对象关系或证据规则变化；
3. 行动模板 Context、Scenario、Gate、验证或回写变化；
4. Code CLI、parser、diagnostic、runtime facade 或输出字段变化；
5. Web API、页面、Confirm UI、展示来源或缓存边界变化；
6. Hook、环境入口、安装、payload 或 adapter 行为变化；
7. Git remote ref target、`git push` gate、远端同步诊断或外部状态变更分类变化；
8. 外部入口薄引用边界、真实安装包 / cache / marketplace package 审计、repo-local 样例与真实 integrated 区分变化；
9. 测试目录、fixture、命令或验证入口变化。

### 7.1 LDVH 影响验证证据边界

安装、接入或断点恢复后的环境验收应称为 `LDVH 影响验证`。Tests 不得把它窄化为“Hook 文件是否存在”，也不得把插件文件存在、配置存在或 shim 直测写成 integrated。验证证据必须证明真实 AI lifecycle Hook 的触发时机、预期结果、实际观察、失败阻断能力、是否写入和未验证范围；缺少可阻断 lifecycle Hook 时，不得通过正式 LDVH 影响验证。

LDVH 影响验证默认只读。自动化测试、命令校验和 Human 验收不得为了证明 Hook 或 LDVH 可用而写入 `spark-0046`、`ldvh-base/sparks/`、specs、事实对象实例或其它正式事实源。需要覆盖写入前阻断行为时，应优先使用 payload fixture、shim 直测、runtime adapter dry-run 或只读可见性探针；确需真实 scratch 写入时，必须显式声明 scratch target、写入原因、清理命令和删除确认，且验证声明必须说明该写入不是事实源。

测试输出、采样日志或 lifecycle 过程记录只代表本次验证观察。它们不得作为长期事实状态写入正式事实源；需要长期沉淀时，必须按 03 分流，并由 Human Gate 判断是否提升为对应事实对象。

Tests 是 LDVH 的测试与验证实现域，承接本文验证规则，为 Code、Hook、安装、Web 和事实源回写提供可复跑证据。Tests 不是第六类构成要素；文件路径、命令和工具链仍使用小写目录 `tests/`。

### 7.2 自锁事故验收矩阵

自锁事故验收矩阵用于验证 01 的 Hook 行动边界、07 的 Code repair 契约、10 的管辖解析和本文验证声明是否共同防止 LDVH 因自身事实源或保障机制异常而全局锁死。该矩阵只定义验收口径，不新增 runtime event、bypass、自动恢复路径或长期状态。

| 事故 / 场景 | 验收输入 | 通过条件 | 不得通过的表现 |
|---|---|---|---|
| 坏事实对象在场，当前写入 target 与其无关 | 当前 target 可明确归口，坏对象只形成 `unrelated_global` 或 residual risk | 当前普通写入只受自身 read_plan、`target_primary`、`runtime_blocker` 和 Human Gate 约束；坏对象作为 residual risk 暴露 | 因无关坏对象阻断当前普通写入，或把全局诊断注入当前 target |
| 当前 target 自身是坏事实对象的普通写入 | 当前 target 归口为该事实对象，存在结构、字段、引用或状态诊断 | normal preflight 必须暴露 `target_primary` blocker，并要求 repair、拆分或 Human Gate | 普通写入绕过 `target_primary` blocker，或把修复写成已完成 |
| repair mode 修复当前 primary fact target | 单一事实对象 target、`mode=repair` / `operation=repair`、07 闭集内可修复 diagnostic、read_plan 消费依据 | 允许进入 repair preflight；final validation 只看 primary target 和必要 direct dependent；`unrelated_global` 保留为 residual risk | 要求清空无关全局诊断才算 repair 通过，或把 repair 当作 bypass |
| specs structural repair 修复当前 primary spec / attachment | 单一 spec / attachment target、`mode=repair` / `operation=repair`、07 闭集内可修复 specs structural diagnostic（如 `ROLE_SECTION_NOT_FOUND`）、read_plan 消费依据 | 允许进入 repair preflight；final validation 只看当前 primary spec / attachment 的结构诊断是否清除；`unrelated_global` 保留为 residual risk | 因当前 spec 结构诊断导致无法修复自身，或借 repair 改写规则语义、接受 Human Gate 风险、跨 spec 批量迁移 |
| repair 写入后 final validation 仍失败 | repair 已发生，但 primary target 或必要 direct dependent 仍有结构诊断 | 验证声明必须写为失败、未通过或“已写未通过”；不得关闭对象 | 声称完成、关闭、状态推进、验收通过或 Human Gate 已完成 |
| repair 目标越界 | 非事实对象 / spec / attachment target、非闭集 diagnostic、状态推进、关闭、风险接受、跨对象迁移、规则语义改写或业务语义判断 | 必须阻断或进入 Human Gate；不得使用 repair lane 放行 | 自动修改业务语义、推进状态、关闭对象、改写规则语义或接受风险 |
| `scope_unknown` | 缺少足够路径、cwd、payload、管辖配置或 target 依据，无法判断是否受管 | 输出 degraded、`capability_gap`、`missing_fields` 或 `unverifiable`；不得生成项目事实源 read_plan 或全局 deny | 把 unknown 当作管辖对象扩大阻断，或静默生成看似完整的行动指南 |
| `declared_multi_governed` / `mixed_scope` | Human 明确声明多管辖对象读取，或写入/提交/迁移同时涉及多管辖、非管辖混合 target | 只读审计可保留多对象独立归口；写入、提交、迁移和事实源回写必须拆分、阻断或进入 Human Gate | 合并生成一个不可拆的行动指南，或用其中一个项目的 read_plan 覆盖全部 target |
| read_plan receipt bootstrap | `ldvh.session_start`、`ldvh.acknowledge_read_plan`、`ldvh.pre_tool_use` 之间需要传递当次 read_plan 消费依据 | receipt 只能作为 stdout-only 或短期 runtime cache；pre_tool_use 只采信同 session、同 workspace、未过期且覆盖目标 `required_read_plan` 的依据 | receipt 变成任意命令 bypass、写入授权、事实源、Human Gate，或生成 receipt 的动作被同一 read_plan 检查自锁 |
| completion claim 仅存在无关全局诊断 | 当前完成 target 自身无 blocker，存在 `unrelated_global` residual risk | `ldvh.completion_claim` 不因无关全局诊断阻断当前完成声明，但必须暴露未验证范围和 residual risk；环境 Stop / 关闭不得被误阻断 | 把无关全局诊断写成当前 target 完成 blocker，或误阻断环境正常停止 |
| completion claim 存在当前 blocker | 当前完成 target 缺验证证据、有 `target_primary` blocker、`runtime_blocker` 或 target / scope 未决 | 必须阻断完成声明，并说明验证缺口、诊断和需要的下一步 | 工具成功、测试通过或 receipt 单独被写成完成 |
| 保障机制自身失败 | Hook、runtime cache、target resolver、validator 或诊断分流无法可信工作 | 必须暴露机制失败、影响范围和需要 Human 介入的位置；允许 Human 授权一次受控处理或完善机制 | 自动恢复、自动接受风险、静默放行、扩大作用域或写成长期健康状态 |

本文的自锁事故验收不要求每次修改都运行全量测试。AI 应按 §5 的验证入口选择矩阵选择最小稳定验证入口；当变更涉及 preflight、repair、completion、read_plan receipt、target resolver 或环境入口时，必须至少覆盖本矩阵中对应正反例，或明确说明等价验证和未覆盖风险。

## 9. 验证方法

验证本文规则时应检查：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 声明检查 | 完成声明是否说明验证对象、入口、范围、结果和风险 | 补充声明或标为未验证 |
| 失败检查 | 是否存在失败、未运行或不可复现的关键验证 | 阻断完成声明 |
| 证据检查 | 测试证据是否没有替代事实源或 Human Gate | 回到 03 或 Human Gate |
| 成本检查 | 验证入口是否匹配风险范围，是否说明未运行的慢速全量测试或残留风险 | 补充目标测试、等价验证或运行全量测试 |
| 同步检查 | 相关规则或实现变化后是否同步 tests 或等价验证 | 记录测试缺口 |
| LDVH 影响检查 | 是否按接入方式说明触发、结果、副作用和未验证范围；是否避免正式事实源写入 | 修正验证设计；发生越界写入时清理并把本次验证写为失败或未验证 |
| 管辖分流检查 | 是否覆盖 `governed_single`、`non_governed`、`scope_unknown`、`governed_target_unknown`、`declared_multi_governed` 和 `mixed_scope` 的正反例 | 补目标测试或记录不可验证缺口 |
| 自锁事故检查 | 是否覆盖 §7.2 中与本次变更相关的无关坏事实对象、repair、read_plan receipt、completion 和保障机制失败场景 | 补目标测试、等价验证或记录未覆盖风险 |

## 10. Human Gate

以下情况必须进入 Human Gate：

1. 改变“已验证”“未验证”“等价验证”“完整验证”的声明标准；
2. 删除高价值测试、回归样例或验收证据且无替代方式；
3. 接受关键验证长期缺失、失败或不可复现；
4. 将测试输出、覆盖率、截图、trace 或报告提升为稳定事实；
5. 用测试通过替代 Human 授权、风险接受或验收。

## 11. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 声称完成但无验证证据；
2. 关键测试失败或未运行却继续关闭；
3. 测试结果与事实源或 specs 冲突；
4. 测试代码反向定义规则、字段、状态或 Human Gate；
5. 无法说明未验证范围和残留风险。
