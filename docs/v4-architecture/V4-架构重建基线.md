## 1. 记录目的

本记录用于约束 V4 架构重建阶段的起点、资产身份、声明边界和完成条件，防止 V3 的规则、实现和验证结论在未经重新裁决时被默认带入 V4。

本记录位于 `docs/` 而非 `specs/`，不定义 LDVH 的持久产品规则、Schema、接口契约或验收契约。需要长期生效的规则，必须经过 V4 裁决并写入当前 V4 规则源。

## 2. V4 的非继承起点

V4 是全新的架构与规范起点，不是 V3 的兼容迁移、原地修补或继续演进。因此：

1. V3 的规则、字段、附件关系、状态、路径和解析约定不自动在 V4 中生效。
2. V4 不承担旧字段、旧附件授权、旧 validator、双读、Git 迁移基线或其他 V3 过渡机制的兼容义务。
3. V3 资产可以作为问题样本、历史经验和实现参考，但必须逐项得到“采纳、改写、拆分或淘汰”的 V4 处置结论。
4. 任何被采纳的内容都必须在 V4 当前规则源、模型或实现中重新明确表达；不得仅以 V3 中已存在为由主张其对 V4 有效。

### 4.1 V4 00 的根级校准要求

V4 00 最初以归档 V3 00 为恢复依据，并以其上位定义一致作为默认边界。V4 不得在未告知 Human 并取得明确决定的情况下，删除、弱化、扩大或改变 V3 00 已定义的上位语义；文件修改、下游使用或实现存在都不能使差异自动获得接受。

2026-07-11，Human 在明确比较当前五类构成和替代方案后，确认一项对 V4 00 的调整：取消“规范体系”作为正式构成要素，以“规范模型（Specification Model）”承担正式 Specs、授权附件及规则表达的结构化组织职责。该决定只改变构成要素的名称、定义和规范模型职责归属，不改变规则源由取得正式效力的 Specs 正文及其授权附件构成，也不赋予模型、索引、Helper 或 Code 新的规则权威。

本次调整同时明确保留：

1. “以 LDVH Helper CLI 为基础服务形式”的根级表述；
2. Helper 在架构层作为面向 AI 的统一跨要素服务入口；
3. Code 实现 Helper CLI，Helper 不是第六类构成要素；
4. Web 独立服务 Human，不经过 Helper CLI；
5. 事实源信息锚点、V1–V8、验证真实性、Human Gate 和 Stop Conditions 的既有上位语义。

当前 V4 00 相对归档 V3 00 获得接受的根级差异限定为：版本身份由 V3 更新为 V4；增加不冲突的 Helper 架构层/实现层澄清；以规范模型替代规范体系作为五类构成要素之一。其它根级差异仍必须先说明原因、影响和替代方案，并由 Human 明确决定。

### 4.2 当前工作树与 Git 溯源边界

2026-07-12，Human 明确确认：Git 提交不是当前内容存在、事实可接续或规则生效的前置条件。AI 和 Code 默认读取当前工作树中的实际内容；未提交的 WorkCase、事实记录和 active 规范变化不能因为尚未进入 `HEAD` 而被忽略，否则会使进行中的工作无法恢复和接续。暂存区只表示准备提交的内容，`HEAD` 只提供最近已提交历史版本，二者都不得覆盖当前工作树。

Git 继续承担溯源职责：提交形成可回查的历史锚点，但不自动证明内容正确、验证通过或工作完成。当前工作树内容必须按适用的结构、规则、事实模型和验证要求判断；内容不一致时应报告当前不一致，不得静默回退到旧提交。01 的当前规则源成立条件已经按该决定修正，当前《事实源与信息溯源规范》草案对事实内容采用同一边界。

正式接受和后续修改时至少必须逐项复核：

1. 存在理由、最终目标以及 AI、Human、Code 的基本职责关系；
2. AI 第一服务对象和 Helper CLI 基础服务形式；
3. 事实源以 Git 可追踪文件为唯一有效承载的边界，以及有组织、可消费要求；
4. 规范模型、事实模型、行动模板、Code 和 Web 五类构成要素分别承担的主要职责，以及 Web 的上位职责；
5. V1–V8 的名称、完整判断问题、价值边界和净价值原则；
6. 根级验证边界，包括 Human 决定不能替代技术验证、静态存在不能证明可用、`integrated` 只按当次依据成立；
7. Human Gate 的触发、交还、回应和效力边界；
8. Stop Conditions 的来源规则驱动、最小暂停范围、暂停期间允许行动和按触发原因恢复；
9. 下位规范、事实模型、行动模板、Code、Helper、Web 和工具输出不得反向解释、覆盖或弱化根规范。

如果 V4 设计还需改变其中任何一项，应先向 Human 明确说明差异、原因、影响和替代方案；在 Human 明确改变本校准基线前，该差异阻断 V4 00 的正式接受。

## 5. Web 冻结边界

本轮重建不修改 Git 跟踪的 `web/` 内容，不对其进行架构调整、接口迁移、数据适配或风格修改。

Web 仍作为既有产品资产保留。未来只有在 V4 规则、Source of Truth 和实现边界已稳定，且另行明确纳入范围后，才能开始其 V4 校准。

## 6. 旧测试结果的处置

V3 定向测试曾得到 `245 passed, 37 failed`。这一结果描述的是 V3 旧 validator 与当时规范变动之间的冲突，不是 V4 的失败清单、验收基线或修复 backlog。

V4 测试必须从已接受的 V4 规则、Schema、服务契约和实现边界重新推导。旧测试只能用来发现候选场景、边界条件和历史风险；采纳某个场景时，仍需要为它建立 V4 的独立验证依据。

## 7. 重建阶段的声明约束

在 V4 对应资产完成设计、实现、接入和验证之前：

- 不得因为归档的旧 Code、tests、hooks、事实对象，或冻结的 Web、icons 仍存在，就声明对应 V4 能力已实现、available、integrated、已保障或 completed。
- 不得用 V3 测试通过数量或 Hook 执行成功来证明 V4 合规。
- 不得将未经接受的草案、讨论记录或历史文件表述为已生效的 V4 规则。
- 未被 V4 覆盖、未实现、未接入或未验证的范围，必须在当次工作中如实降级声明。

## 9. 后续裁决方式

对 V3 资产的后续处理应以职责和 V4 实际需求为单位，而不是按旧编号或旧文件整体搬运。每项采纳应至少能说明：

1. 它解决的 V4 问题和对 AI 的净价值；
2. 它在 V4 中的职责归属和权威来源；
3. 它的适用、效力、验证和声明边界；
4. 它是采纳、改写、拆分还是淘汰，以及为何。

当此类结论需要形成持久规则时，应进入 V4 `specs/`；只描述重建过程、阶段状态或资产处置的内容，应继续保留在工作记录中。
