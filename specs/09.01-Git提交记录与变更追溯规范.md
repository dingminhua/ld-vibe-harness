# Git 提交记录与变更追溯规范

> 创建日期：2026-06-19
> 所属主文档：`specs/09-事实源边界与承载规范.md`
> 关系：专题子文档
> 定位：定义 Git 提交记录、commit message 契约、追溯字段、派生关联和 Code/Web 消费规则
> 适用范围：LDVH 自身项目及所有接入 LDVH 且需要追踪 Git 文件事实源修改的管辖项目
> 上位依据：`specs/09-事实源边界与承载规范.md`

---
## 1. 本文解决的问题

本文解决 Git 提交记录如何成为事实源修改的追溯证据、commit message 应如何书写、AI 和 Human 如何利用提交历史理解变更、Code 如何校验提交记录、Web 如何展示提交记录派生视图，以及工作对象是否需要手写关联提交字段的问题。

Git 提交记录不是 LDVH 工作对象，不进入 20-39 工作模型集合，不创建 `ldvh-base/changes/`，也不具备 YAML 状态机。它是事实源修改的 Git 层追溯证据，服务 `specs/09-事实源边界与承载规范.md` 定义的 Git 可追踪原则。

---
## 2. 与 09 和工作模型的关系

09 定义最终事实源必须是 Git 可追踪文件。本文承接 09，专门定义修改这些文件时如何通过 Git commit records 留下可读取、可审查、可校验、可被 Web 派生展示的追溯证据。

Git 提交记录与工作模型的边界如下：

| 内容 | 权威位置 |
|---|---|
| 工作对象状态、字段、验收和关闭判断 | 对应 `ldvh-base/` YAML 或 Study Markdown 实例 |
| 工作对象字段契约和状态机 | 20-39 具体工作模型规范 |
| 事实源修改的提交证据 | Git commit records |
| 提交记录格式与追溯规则 | 本文 |
| 提交记录的列表、筛选、关联和详情展示 | Code/Web 派生视图，不替代 Git |

工作对象不得手写维护 `related_changes` 这类提交清单字段。需要查看某个对象相关提交时，应由 Code 或 Web 根据 Git 历史、commit message `Refs:`、文件路径、对象 ID 和必要索引实时派生。派生结果可以展示为“关联提交”或“提交记录”，但不得回写为新的对象事实字段。

---
## 3. 适用范围

以下修改应通过符合本文契约的 Git commit 留痕：

1. 修改 specs 正式规范、规则入口、能力资产、Code、Web、测试或配置；
2. 修改 `ldvh-base/` 下的工作对象事实源；
3. 修改 Study Markdown、docs 正文、docs/studies、docs/sources 或经授权沉淀的项目文档；
4. 修改会影响 Human Gate、状态流转、事实源边界、校验逻辑、Web 呈现或 AI 入口的文件；
5. 完成 WorkPlan、ADR、Memo、Study、Pitfall、WorkArea 等对象的创建、关键字段改写、状态变化、归档或删除；
6. 回退、修正或补充之前已提交的事实源修改。

未进入 Git 的临时实验、构建产物、缓存或本地草稿不形成正式提交记录；一旦提交，就应尽量符合本文格式。

---
## 4. commit message 格式

LDVH 推荐使用以下格式：

```text
<type>(<scope>): <subject>

<body>

Refs: <object-refs>
Human-Gate: <summary>
Verification: <commands-or-result>
Risk: <risk-summary>
```

| 字段 | 要求 | 说明 |
|---|---|---|
| `type` | 必填 | 提交类型，使用本文 §5 枚举 |
| `scope` | 可选 | 影响范围，使用本文 §6 推荐值或项目扩展值 |
| `subject` | 必填 | 简短说明，推荐不超过 72 字符 |
| `body` | 推荐 | 说明变更原因、影响范围、关键取舍和上下文 |
| `Refs` | 推荐 | 关联对象 ID、规范编号、路径或 commit hash |
| `Human-Gate` | 条件必填 | 涉及 Human Gate 时记录确认摘要；不涉及时可写 `不适用：...` |
| `Verification` | 推荐 | 记录验证命令、人工检查或未运行原因 |
| `Risk` | 推荐 | 记录残留风险；无风险时可写 `无已知残留风险` |

`Refs`、`Human-Gate`、`Verification`、`Risk` 是机器可识别 trailer。Code 应尽量解析并给出缺失 warning；是否将缺失升级为 error 由当前项目的提交门禁策略决定。

---
## 5. type 枚举

| type | 含义 |
|---|---|
| `feat` | 新增功能、能力或对象 |
| `fix` | 修复缺陷 |
| `docs` | 文档修改 |
| `spec` | specs 规范修改 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 测试相关 |
| `chore` | 构建、配置或辅助维护 |
| `rule` | Rules / Instructions 修改 |
| `adr` | ADR 实例创建或状态变化 |
| `revert` | 回退之前的提交 |

---
## 6. scope 推荐值

| scope | 含义 |
|---|---|
| `specs` | specs 规范文档 |
| `docs` | docs 正文或项目文档 |
| `rules` | Rules / Instructions |
| `code` | Code / 工具实现 |
| `web` | Web 实现 |
| `tests` | 测试代码 |
| `config` | 项目配置 |
| `workarea` | WorkArea 实例 |
| `workplan` | WorkPlan 实例 |
| `adr` | ADR 实例 |
| `memo` | Memo 实例 |
| `study` | Study 实例 |
| `pitfall` | Pitfall 实例 |
| `studies` | docs/studies 相关修改 |
| `sources` | docs/sources 相关修改 |

scope 为推荐值。项目可以在不破坏解析的前提下扩展，但不应用 scope 创造新的工作对象类别。

## 7. Refs 与派生关联

`Refs:` 用于让提交记录可被对象、规范、路径或其他 commit 追溯。推荐格式如下：

| 引用类型 | 示例 |
|---|---|
| WorkArea | `workarea-0001` |
| WorkPlan | `workplan-0001` |
| ADR | `adr-0001` |
| Memo | `memo-0001` |
| Study | `study-0001` |
| Pitfall | `pitfall-0001` |
| 规范 | `specs/09.01-Git提交记录与变更追溯规范.md` 或 `09.01` |
| 文件路径 | `web/src/pages/Changelog.tsx` |
| commit hash | `abc1234` |

`Refs` 不改变被引用对象的事实源归属，不等于对象状态流转，不等于验收通过，也不替代 WorkPlan 关闭证据。它只为 Git 提交和对象事实源之间建立追溯入口。

工作对象、规范、Code 和 Web 需要“关联提交”时，应按以下优先级派生：

1. commit message `Refs:` 中的对象 ID、规范编号和路径；
2. commit touched files 与对象事实源路径、规范路径、Code/Web 文件路径的匹配；
3. commit body 中明确出现的对象 ID 或规范路径；
4. 必要时由用户或 AI 在当前分析中临时筛选，但不得回写为手填提交字段。

---
## 8. 提交语言要求

LDVH 自身项目的提交说明必须使用简体中文表达主要人类可读内容。`type`、`scope`、trailer key、路径、命令、对象 ID、英文专名和代码标识可以保留英文或原文。

Code 可机械检查 commit message 是否包含中文字符、是否符合首行格式、是否包含推荐 trailer；简体中文与繁体中文的细分判断若无法可靠机械化，应由 Human 审查兜底。

---
## 9. Human Gate 与风险

Git 提交记录本身不额外触发 Human Gate。Human Gate 由被修改的事实源、对象、规范、Code、Web、工作流程或破坏性 Git 操作触发。

以下场景应记录 `Human-Gate:` trailer 或在 body 中说明确认情况：

1. 修改事实源边界、对象状态机、字段契约、规范编号、目录归属或 AI 入口；
2. 删除、迁移或重命名工作对象事实源；
3. 执行破坏性 Git 操作，例如改写已共享历史、强推、删除分支或批量回退；
4. 修改受控写入、校验、Human Gate、Web 编辑或安全相关能力；
5. 用户明确确认某个高影响方向、迁移策略或验收结论。

`Risk:` 应说明残留风险、未验证内容、兼容性影响或 `无已知残留风险`。不得用“应该没问题”替代风险说明。

---
## 10. Code 消费规则

Code 可以实现以下能力：

1. 校验 commit message 首行格式、type 枚举、subject 长度和中文要求；
2. 解析 `Refs:`、`Human-Gate:`、`Verification:`、`Risk:` trailer；
3. 基于 Git 历史和 touched files 派生对象关联提交；
4. 为 Web 提供提交列表、提交详情、文件统计、追溯 trailer 和关联引用；
5. 对缺少推荐 trailer、缺少 Refs 或格式不稳定的提交给出 warning；
6. 检查对象事实源中是否仍出现需要清理的手写提交字段。

Code 输出只是派生诊断、导航或展示数据，不替代 Git commit records。commit message 契约变化后，应同步更新 `code/commit_validate.py`、相关测试和 Web API 解析契约。

---
## 11. Web 呈现规则

Web 可以展示 Git 提交记录列表、最近提交、提交详情、关联引用、验证摘要、风险摘要、文件统计和对象相关提交。

Web 呈现必须遵守：

1. 页面和导航表达为“提交记录”“最近提交”或“Git 提交记录”，不得把它表达为独立工作对象；
2. `/changelog` 可作为路由名保留，但页面文案应表达为提交记录派生视图；
3. Dashboard、ProjectFiles 和 Changelog 应尽量共享同一 commit DTO 或解析契约；
4. 对象详情中的关联提交应由 Git 派生，不从对象 YAML 手写字段读取为权威事实；
5. Web 缓存、页面状态、筛选状态和派生索引不得替代 Git commit records。

## 12. 示例

```text
spec(specs): 建立 Git 提交记录追溯规范

将变更追溯从工作对象迁出，改由 09.01 定义 Git 提交记录契约。
工作对象不再手写 related_changes，关联提交由 Refs 和 Git 历史派生。

Refs: workplan-0074, specs/09.01-Git提交记录与变更追溯规范.md
Human-Gate: 用户确认提交记录不作为工作对象，并要求提交语言使用简体中文
Verification: python3 code/specs_validate.py all
Risk: 需要同步 Code/Web 旧文案和测试夹具
```

```text
fix(web): 统一提交记录详情展示

让 Changelog、Dashboard 和 ProjectFiles 共享 commit 解析结果，
避免同一提交在不同页面出现字段漂移。

Refs: web/src/pages/Changelog.tsx, web/api/routes/changelog.ts
Human-Gate: 不适用：仅修复派生展示，不改变事实源
Verification: npm run check --workspace web
Risk: 无已知残留风险
```

## 13. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 事实源修改应通过 Git 提交记录留下可追溯证据，不再把提交记录建模为工作对象 | 09、本文、06、Human Gate | 事实源治理 | 修改 Git 文件事实源、工作对象状态、规范、Code、Web 或入口资产时 |
| 入口可见要求 | AI 准备提交、审计提交历史或追溯对象相关提交时应能定位本文 | Rules 入口摘要、commit_validate 帮助、Web 提交记录页 | AI 执行入口提示 | 提交、回退、审计、关闭 WorkPlan 或查询关联提交时 |
| 确定性执行要求 | commit message 可机械校验的部分由 Code 检查，关联提交由 Git 派生 | `code/commit_validate.py`、Git 查询、测试夹具 | 校验实现 | 提交契约、trailer、Refs 或关联派生规则变化时 |
| 确定性执行要求 | LDVH 自身仓库应提供或启用提交前 message 校验入口；未启用 Git hook 时，AI 提交前必须手动运行等价预检 | `commit-msg` hook、`code/commit_validate.py --check-message`、CI 或人工降级检查 | 触发保障 | 创建 Git commit、修改提交契约、调整 hook/CI 或迁移仓库入口时 |
| Human 交互要求 | 高影响事实源修改和破坏性 Git 操作必须记录或触发 Human Gate | Human Gate、提交 body、`Human-Gate:` trailer | 人工确认 | 修改事实源边界、状态机、字段契约、入口资产或执行破坏性 Git 操作时 |
| 生命周期触发要求 | 本规范变化后，应同步检查 01、05、05.01、06、07、08、Code、Web 和测试 | specs 检查、Code 测试、Web 类型检查、残留搜索 | 触发保障 | 提交格式、追溯字段、关联派生或 Web 展示规则变化时 |

## 14. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变 Git 提交记录的事实源定位；
2. 改变 commit message 必填字段、提交语言、提交门禁或破坏性 Git 操作边界；
3. 把提交记录重新建模为工作对象或创建 `ldvh-base/changes/`；
4. 把 Web 缓存、数据库索引或对象 YAML 字段提升为提交记录事实源；
5. 删除 Code 校验或降低高影响事实源修改的追溯要求。

检查至少包括：

| 检查项 | 标准 |
|---|---|
| 事实源边界 | 提交记录由 Git commit records 承载，不创建工作对象实例 |
| 格式契约 | commit message 首行、type、scope、Refs 和推荐 trailer 可被解析 |
| 语言要求 | LDVH 自身提交主要人类可读内容使用简体中文 |
| 提交门禁 | LDVH 自身仓库存在 `commit-msg` hook、CI 或等价预检入口；未启用时提交执行者必须在提交前运行 `code/commit_validate.py --check-message` |
| 派生关联 | 对象关联提交由 Git 历史和 `Refs:` 派生，不手写维护 |
| Code 边界 | Code 只校验、解析和聚合，不替代 Git |
| Web 边界 | Web 只展示派生视图，不替代 Git |

---
## 15. 待补齐事项

1. 应补齐 LDVH 自身仓库的 `commit-msg` hook 或 CI 提交信息检查，并明确哪些 warning 升级为 error；
2. 若未来支持多仓库管辖项目，应补齐跨仓库提交记录查询和 Web 聚合边界；
3. 若未来需要自动派生对象关联提交，应优先基于 `Refs:` 和 touched files 实现，不恢复手写字段。
