## 1. 价值判断

环境插件是 LDVH 最外层入口，也是多环境架构中唯一需要按环境能力分别承接的部分。如果没有明确的插件要求和编写行动模板，AI 容易走两个极端：要么把所有逻辑塞进一个巨无霸 shim，要么把 manifest、hooks 配置和 shim 拆得支离破碎，导致后续维护和升级无法追溯。

本文的价值在于：

1. **先定义要求，再决定是否写插件**：分析 Hook API → 明确目标环境能承接哪些 LDVH canonical event、payload、阻断和回滚能力 → 再决定是否编写 repo-local 样例、目标环境 package、settings adapter 或只交还能力缺口。
2. **把"写一个环境插件"从玄学变成可执行步骤**：分析 Hook API → 写等价入口资产 → 本地一致性验证 → 交还。每一步都有明确的最小产出和检查标准。
3. **把存量升级统一为同一套流程**：stale path 修复、缺失事件补齐、V1→V3 迁移，都走同一套分析→编写→验证→交还的四阶段流程，不另起分支。
4. **明确薄引用边界**：所有核心逻辑留在共享 LDVH Code，thin reference shim / adapter 或目标环境等价入口资产只做入口声明、payload 翻译、adapter 引用和输出协议翻译，不承载规则逻辑、复杂命令分类、target 归口、diagnostic 分流或状态推进。
5. **让安装流程（spec 30）有可验收对象**：30 只管"把目标环境真实入口装上去并验证触发"，33 管"这个入口必须满足什么要求、如何编写或更新"。两者协作形成完整闭环。

环境插件编写行动主要服务 V1、V2、V3、V4、V6：它让 AI 在动手写文件前先分析目标环境 Hook API 能力，按要求优先的方式组织产出，在 Gate 处暂停等待 Human 确认，执行本地一致性验证，并在交还时明确要求 / 入口资产清单、未写入项、不可验证范围和下一步。多环境差异数据由附件承接，不在模板正文中重复。

## 2. 权威依据

本文承接 `specs/06-行动模板基础规范.md` 的 Context、Scenario、Gate、执行、验证、回写和交还结构。行动模板不是规则源，也不是授权器；本文的职责是把环境插件编写/更新的行动路径组织为可复用模板。

本文承接 `specs/01-保障与衔接.md` 的环境入口分类、Hook 边界和 integrated 声明约束——环境插件编写时必须遵守：目标环境入口资产只能作为薄引用，承载入口声明、Hook 配置、payload 翻译 / adapter 引用、输出协议翻译和必要资产引用；不得复制 specs 规则、事实源、行动模板、校验逻辑、命令分类逻辑、target 归口逻辑、diagnostic 分流逻辑或 Human Gate 判断。

本文可以引用 `hooks/environment-plugins/codex-ldvh-v3/` 和 `hooks/environment-plugins/workbuddy-ldvh-v3/` 作为 repo-local 参考标本，但不得复制其命令、字段或逻辑形成第二规则源。参考标本只能证明本仓库样例包的结构和 shim 行为，不证明当前 Codex、WorkBuddy 或其它目标环境已经安装、启用或 integrated。具体环境的 Hook API 差异和配置契约回指对应环境的官方文档和 `specs/attachments/33.Att.01-环境插件差异速查.md`。

若本文与 01、06、10、30 或 Human Gate 冲突，应回到上位规范和 Human Gate，不得由本模板自行覆盖。

## 3. 归口边界

本文归口定义环境插件编写和更新的步骤组织、四阶段行动、插件要求、等价入口结构和交还边界。

本文同时归口定义目标环境插件的要求契约：任何目标环境入口，无论表现为插件包、扩展包、settings hook、marketplace package、adapter 脚本或其它等价机制，都必须能说明它如何满足本文的事件映射、payload 转译、target-first、薄引用、失败处理、安装位置、回滚和验证交还要求。

本文不归口定义：
- 具体环境 Hook API 的完整文档（应在目标环境官方文档中查找，差异数据由 `33.Att.01` 承接）
- `runtime_adapter.py` 内部逻辑（归 code 域）
- 插件安装后的验证闭环（归 30）
- Git commit-msg Hook 的编写（Git Hook 是独立层级，与环境插件无关）
- 管辖项目配置契约（归 10）
- 插件市场发布、版本管理和签名流程

本文可以组织"环境分析→要求确认→编写/更新→验证→交还"的行动顺序，也可以把 Codex / WorkBuddy 参考标本作为编写时的对照起点；但不得把命令样例、字段定义或 API 参数写成模板规则，不得把标本复制后不改当成新插件，不得把本地语法验证通过写成真实环境触发已验证。

## 4. 适用范围

本文适用于：

1. 为一个尚未有 LDVH 插件的 AI 环境编写新插件；
2. 更新已有插件：修正 stale path（如旧版 `ld-vibe-harness` → 新版 `ld-vibe-harness-v3`）、补齐缺失事件（如只覆盖 `ldvh.session_start` 和 `ldvh.pre_tool_use`，缺 `ldvh.completion_claim`）、修正 matcher 规则或 shim 逻辑；
3. 审查现有插件是否满足薄引用边界（不复制规则、不独立维护校验逻辑或环境专属复杂判断）。
4. 目标环境机制尚不清楚或无法在当前 AI 环境中验证时，只定义插件要求、差异清单、不可验证范围和交还给 30 的验收入口。

用户只是询问概念或边界时，只回答本文和 01 的相关边界，不写入文件、不修改插件。

## 5. 模板定位与来源

本文是 06 之后的正式行动模板，编号为 `33`。它与 30 平行：30 管安装、验证、交还已存在的插件；33 管插件的编写和更新本身。两模板协作但不互相包含。

因此，33 的成败不取决于是否亲自运行每个 Hook 事件，也不取决于 repo 中是否预置了某个环境的完整插件，而取决于是否能按 06 的七结构稳定组织插件要求和编写行动：场景识别、Context 收集、Gate 与 Human Gate、四阶段执行、本地一致性验证、回写和交还。底层 Hook API 细节由目标环境官方文档和 `33.Att.01` 承接；33 必须消费其输出并交还主控 AI 与 Human 判断。

当前最小闭环包括：分析目标环境 Hook API → 明确本文要求如何在该环境中投影 → 按目标环境等价结构编写或更新入口资产 → 本地静态 / fixture 一致性验证 → 交还 30 安装 / 验收入口、目标环境回传证据要求或 capability_gap 分流。插件市场发布、跨环境批量迁移、插件包签名等需求仍需按来源规则进入 Human Gate。

## 6. 环境插件编写行动边界

### 6.1 插件要求与等价结构

目标环境插件首先必须满足本文的要求契约，然后才按环境能力选择等价实现形态。repo-local 样例包可以放在 `hooks/environment-plugins/` 下，但真实目标环境可能使用插件包、扩展包、settings hook、marketplace package、adapter 脚本或其它机制；这些形态不要求文件名相同，只要求职责等价、可审计、可回滚。

环境插件必须是薄引用，不是环境专属实现层。允许留在插件或等价入口资产中的内容只包括：入口声明、环境原生事件到 LDVH canonical event 的映射、payload 字段投影、LDVH root / adapter 引用、目标环境输出协议翻译、必要资产引用和按目标环境协议的不阻断降级提示。凡是会影响阻断、no-op、diagnostic、read_plan、repair、bypass、completion、验证声明、事实源回写或状态推进的判断，都必须由共享 LDVH Code 承接，不得在 Codex、WorkBuddy 或其它环境插件中各自维护一份复杂逻辑。真实安装包、插件 cache、marketplace package、扩展包和 repo-local 样例包适用同一薄引用检查；不能因为入口资产已经被目标环境复制到 cache 或 marketplace 目录，就允许其保留旧 target 解析、命令分类、diagnostic 分流或事实源写入逻辑。

repo-local 样例包的推荐三层结构如下；目标环境若使用不同结构，必须在环境分析中说明等价关系：

| 等价层 | repo-local 推荐文件 | 职责 | 规模 |
|---|---|---|
| manifest / package declaration | `plugin.json` 或等价 | 声明插件元数据、Hook 入口指向 | ~30 行 |
| Hook event routing | `hooks/hooks.json` 或等价 | 声明事件列表、matcher、shim 命令或等价入口路径 | ~70 行 |
| thin reference shim / adapter | `.py` 或等价脚本 | payload 格式翻译 → 引用 / 调用 `runtime_adapter.py` → 输出协议翻译 | ~200–700 行 |

Manifest 或等价声明必须能定位 Hook event routing；目标环境没有 manifest 时，必须说明其 settings、marketplace package 或扩展配置如何承担同等职责。Manifest 不得声明 Rules、Skills 或其它非 Hook 能力。

Hook 事件路由必须把目标环境 lifecycle event 映射到 LDVH canonical event。完整环境入口至少覆盖：目标环境 SessionStart 或等价事件映射到 `ldvh.session_start`，目标环境 PreToolUse 或等价写前事件映射到 `ldvh.pre_tool_use`（matcher 覆盖 Write/Edit/Bash 或目标环境等价写入工具），目标环境 Stop 或等价完成邻近事件映射到 `ldvh.completion_claim`。目标环境事件名可以不同，也可以由多个原生事件组合成一个 LDVH canonical event；必须以 LDVH canonical event 作为对外语义，不得把环境原生事件名写成 LDVH 事件。缺少任一核心事件或缺少阻断能力时，只能声明 partial capability / capability_gap，不能声明完整 integrated。所有事件的 command 或等价入口必须指向 thin reference shim / adapter。不得添加 LDVH 暂未映射到稳定 canonical event 的环境事件；matcher 不得覆盖用户非 LDVH 管辖的工具调用。

薄引用 shim / adapter 的唯一职责是入口投影：读取目标环境 Hook 载荷 → 解析环境原生事件名并映射到 LDVH canonical event → 定位 LDVH root → 提取 target_path、target_paths、tool_name、command_text、cwd、session_id、operation、verification_evidence 等可用字段 → 构造 runtime_adapter 能吃的 payload → 调用 LDVH runtime adapter → 把输出翻译回目标环境协议。shim / adapter 或目标环境等价入口资产必须指向 `code/runtime_adapter.py` 或等价 LDVH runtime adapter 入口，不得在入口资产内实现校验逻辑、命令分类逻辑、target 归口逻辑、diagnostic 分流逻辑或状态推进逻辑。找不到 LDVH root 时，目标环境入口必须按目标环境协议降级为不阻断，并产生 warning、diagnostic 或等价提示；repo-local 命令式 shim 可以表现为 warning + exit 0。只读工具操作（Read、Grep、Glob 或目标环境等价只读操作）只能由共享 LDVH Code 或共享分类器判断；环境插件不得各自维护独立分类规则。target / target_paths、Git remote ref target、patch path 和嵌套 payload 的投影必须委托共享 classifier / runtime helper；入口资产不得复制一套环境专属解析器。未映射事件默认静默返回。默认不写事实源。

研究采样、调试日志或 lifecycle 观察只能作为显式 opt-in 的临时过程输出。环境插件不得默认写 `ldvh-base/`、specs、事实对象或受管项目；即使通过环境变量启用研究采样，也必须写入明确的 scratch / temp 目录或由共享 Code 的受控命令承接，并在交还中说明其不是事实源、evidence、授权或 integrated 依据。

参考标本：`hooks/environment-plugins/codex-ldvh-v3/` 与 `hooks/environment-plugins/workbuddy-ldvh-v3/`。所有新环境插件可以参考它们的职责划分，但必须按目标环境差异调整 manifest / settings 格式、Hook 事件名、payload 字段提取逻辑和输出协议。参考标本的存在不等于当前 AI 环境插件开启；当前 Codex hook 关闭时，Codex 会话只能做 repo-local 代码和样例 shim 验证，不能声明 Codex lifecycle integrated。WorkBuddy hook 开启与否只能由 WorkBuddy 当前环境的真实 lifecycle 输出和 30 验收判断，Codex 会话不能替代。

### 6.2 场景分类

| 场景 | 触发条件 | 走向 |
|---|---|---|
| **新增** | 目标环境尚无已知 LDVH 入口资产、repo-local 样例、adapter 或插件要求记录 | 完整四阶段 |
| **更新（stale path）** | 已有 repo-local 样例包、目标环境等价配置或 shim / adapter 指向旧路径（如 V1→V3） | 轻量四阶段：分析差异 → 只改路径/事件 → 验证 → 交还 |
| **更新（补齐事件）** | 已有入口资产缺少核心 LDVH canonical event（如缺 `ldvh.completion_claim`） | 轻量四阶段：分析差异 → 补 Hook event routing 或目标环境等价配置 + shim / adapter → 验证 → 交还 |
| **要求定义** | 目标环境机制尚未调查清楚，或当前 AI 环境无法触发目标环境 lifecycle | 只定义插件要求、capability_gap、不可验证范围和 30 验收入口 |
| **审查** | 用户询问"这个插件怎么写才对" | 只读分析，不写文件 |

### 6.3 四阶段行动

无论新增还是更新，统一使用四阶段行动：

| 阶段 | 名称 | 说明 | 写入边界 |
|---|---|---|---|
| 1/4 | 环境分析 | 查阅目标环境 Hook API 文档，确认支持的事件、payload 格式、插件安装位置、路径解析方式和当前 AI 环境是否能实际触发目标环境 lifecycle | 不写入 |
| 2/4 | 编写/更新 | 按目标环境等价结构编写或修改文件；更新场景必须先明确差异再动手 | 可写入（经 Human Gate 确认后） |
| 3/4 | 本地验证 | 等价配置解析检查、shim / adapter 语法检查、canonical event fixture 干跑、静态路径检查 | 不写入 |
| 4/4 | 交还 | 输出要求 / 入口资产清单、未写入项、关键决策记录、与标本的差异说明、当前环境不可验证范围、下一步（30 安装 / 验收入口、目标环境回传证据或 capability_gap 分流） | 不写入 |

### 6.4 环境分析阶段必须确认的问题

在动手写之前，必须先回答：

1. 目标环境支持哪些 lifecycle Hook 事件？至少要能映射出 `ldvh.session_start`、`ldvh.pre_tool_use`、`ldvh.completion_claim` 三个 LDVH canonical event 才能完整接入。缺原生事件、缺 completion-adjacent 事件或缺写前阻断能力时必须在交还中标注缺口。
2. 每个事件的 payload 格式（stdin JSON？环境变量？文件路径？命令行参数？）
3. Hook 配置文件的格式（JSON？TOML？YAML？独立文件还是嵌入全局 settings？）
4. Hook 命令中的路径解析方式（`$PLUGIN_ROOT`？`${CODEBUDDY_PLUGIN_ROOT}`？绝对路径？）
5. 映射到 `ldvh.pre_tool_use` 的目标环境原生事件是否可阻断？不可阻断时只能 diagnostic-only。
6. 插件/扩展的安装目标位置和激活方式。
7. 当前 AI 会话是否就是目标环境；若不是，只能做样例包/adapter 代码审计，不能声明目标环境 lifecycle 已触发。

目标环境 Hook API 文档不可用时，暂停并交还缺口。

### 6.5 更新场景的增量要求

存量更新时，2/4 编写阶段必须：
- 先列出差异：哪一行要改、改前是什么、改后是什么
- 不改的部分明确声明"保持不变"
- 更新完成后运行本地验证（3/4）确保未引入回归

更新前必须读取目标环境当前已安装或启用的入口资产，确认需要同步更新的实际安装位置、配置位置或 package 位置。repo-local 样例和目标环境真实入口是两类独立资产 / 位置；更新 repo-local 样例后，不等于真实入口已同步，真实入口需要经 30 的安装 / 验收流程再次部署或验证。

### 6.6 编写/更新产出边界

repo-local manifest / hooks / shim 或目标环境等价入口资产只能包含入口声明、Hook 配置、环境原生事件映射、payload 字段投影、LDVH root / adapter 引用、输出协议翻译、必要资产引用和按目标环境协议的不阻断降级提示。不得在插件包、settings hook、marketplace package、adapter 脚本或其它等价入口资产中写入 specs 规则正文、事实源内容、校验逻辑、命令分类逻辑、target 归口逻辑、diagnostic 分流逻辑、状态推进逻辑、Human Gate 判断、commit message 契约、安装配置契约或 runtime adapter 逻辑。

环境差异速查数据（Codex、WorkBuddy 等环境的具体 Hook API 字段和配置契约）回指 `specs/attachments/33.Att.01-环境插件差异速查.md`。编写时以目标环境官方文档为准，`33.Att.01` 仅作速查入口。

## 8. 保障措施

| 要求 | 机制 | 触发 | 证据 | 缺口处理 |
|---|---|---|---|---|
| 四阶段行动要求 | 编写和更新必须使用四阶段组织当前阶段、已确认决策和未发生事项；由本文、04、06 保障，2/4 写入前必须经 Human Gate 确认 | 编写或更新环境插件时 | §6.3 四阶段记录、Human Gate 确认记录、§7 交还 | 缺少阶段或 Human Gate 时停止写入，回到对应阶段重做 |
| 薄引用边界 | shim / adapter 或目标环境等价入口资产只能做入口声明、payload 翻译、adapter 引用和输出协议翻译，不得含校验逻辑、命令分类逻辑、target 归口逻辑、diagnostic 分流逻辑或状态推进逻辑；由本文 §6.1 和 Code review 保障 | 编写/更新 shim / adapter 或目标环境等价入口资产时 | 入口资产审查、无独立规则逻辑或环境专属复杂判断 | 发现复制规则逻辑或环境专属复杂判断时，重写为 thin reference shim / adapter 或等价入口资产，并把判断迁回共享 LDVH Code |
| 三事件最小集 | 目标环境入口或等价配置必须覆盖 `ldvh.session_start`、`ldvh.pre_tool_use`、`ldvh.completion_claim`；由本文 §6.1 保障 | 编写/审查 Hook event routing 或目标环境等价配置时 | canonical event 覆盖清单、本地 fixture 验证和 capability_gap 说明 | 缺原生事件、缺阻断能力或缺 completion-adjacent 事件时在交还中标注 partial capability，不声明完整 |
| stale path 检测 | 更新场景必须先读实际安装位置和 repo sample，确认所有 path 引用；由本文 §6.5 保障 | 存量更新时 | 差异清单、路径验证通过 | path 不明确时暂停 |
| 要求优先边界 | 先声明目标环境插件必须满足的 canonical event、payload、target-first、阻断、降级、回滚和验证要求，再决定是否写 repo-local 样例或真实入口资产 | 新增、更新或审查插件时 | 要求覆盖清单、capability_gap、与目标环境 API 的映射 | 只找到样例包但缺目标环境能力依据时，不声明支持或 integrated |
| 读操作跳过 | `ldvh.pre_tool_use` 对应 shim / adapter 只投影 tool_name、operation、command_text 和 payload 字段并调用共享 LDVH runtime / classifier；只读跳过由共享 Code 判断，环境入口只翻译 no-op / allow 输出；由本文 §6.1 和共享 Code 保障 | `ldvh.pre_tool_use` 映射触发时 | 入口资产无独立分类规则、共享 runtime / classifier 判断结果、目标环境 no-op / allow 输出翻译 | 写操作误判为只读时修复共享 classifier / runtime，并同步入口 fixture |
| 降级通过 | 找不到 LDVH root 时，目标环境入口必须按目标环境协议降级为不阻断，并产生 warning、diagnostic 或等价提示；repo-local 命令式 shim 可表现为 warning + exit 0 | LDVH root 解析失败时 | 目标环境协议下的不阻断降级证据、warning / diagnostic 等价输出，或 repo-local shim 的 warning + exit 0 | 反向：root 存在却降级时修复入口资产 |
| 环境文档优先 | 编写前必须以目标环境官方文档为准；`33.Att.01` 只作速查，不是完整 API 文档；由本文 §6.6 保障 | 编写新环境插件时 | 环境分析阶段引用的官方文档链接 | 跳过文档直接抄 Codex 标本时暂停 |
| 当前环境边界 | 当前 AI 环境只能验收本环境真实 lifecycle；不能替代另一个目标环境的真实触发、阻断或 completion 检查 | 跨 Codex / WorkBuddy / 其它环境审计时 | 当前环境名称、目标环境名称、目标环境当次原始输出或不可验证声明 | Codex 中只能审计 WorkBuddy 样例包或回传证据；WorkBuddy 中也不能替代 Codex integrated 判断 |
| 验证交还要求 | 完成声明前必须交还要求 / 入口资产清单、未写入项、本地验证结果、不可验证范围和下一步；由本文、09 保障 | 声称插件编写完成时 | §7 交还摘要、验证结果、source_refs | 缺少交还时写为未完成，补齐后再声明完成 |

## 9. 验证方法

验证本文规则时应检查：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 结构检查 | 是否具备 Context、Scenario、Gate、执行、验证、回写和交还七结构 | 保持为候选，不作为正式编写行动模板 |
| 来源检查 | 是否回指 01、06、30、07、09 和实现域文档，不复制来源规则的字段闭集、枚举、判定顺序或命令样例 | 回到来源规范或模板重写 |
| 插件结构检查 | repo-local 样例包若采用三层结构，是否包含 manifest + hooks.json + shim；目标环境使用 settings hook、marketplace package、adapter 脚本或其它结构时，是否说明与三层职责的等价关系 | 补齐样例包结构或等价关系，不得把单一文件结构当成所有环境完成条件 |
| 事件检查 | Hook event routing 或目标环境等价配置是否覆盖 `ldvh.session_start`、`ldvh.pre_tool_use`、`ldvh.completion_claim`；缺少原生事件或阻断能力时是否标注 partial capability / capability_gap | 交还中标注缺失事件、缺失阻断能力或 partial capability |
| 薄引用检查 | shim / adapter 或目标环境等价入口资产是否只做入口声明、payload 翻译、adapter 引用和输出协议翻译，不含独立规则逻辑、命令分类逻辑、target 归口逻辑、diagnostic 分流逻辑或状态推进逻辑 | 重写 shim / adapter 或等价入口资产，并把判断迁回共享 LDVH Code |
| 路径检查 | repo-local 样例包、目标环境等价配置和 shim / adapter 中所有文件路径是否指向 V3 产物（非 V1/V2 stale path） | 修正路径 |
| 语法检查 | repo-local manifest / hooks JSON 或目标环境等价配置是否可解析，shim / adapter 是否通过对应语法检查 | 修复语法错误 |
| 干跑检查 | shim / adapter 能否用 fixture payload（模拟 `ldvh.session_start`、`ldvh.pre_tool_use`、`ldvh.completion_claim`）成功调用 runtime_adapter.py | 修复 shim / adapter 逻辑 |
| 降级检查 | 故意让 LDVH root 找不到时，目标环境入口是否按目标环境协议不阻断并产生 warning、diagnostic 或等价提示；repo-local 命令式 shim 是否 warning + exit 0 | 修复降级逻辑 |
| 要求覆盖检查 | 是否逐项说明 canonical event 映射、payload 字段、target-first、阻断能力、降级、回滚、当前环境边界和 30 验收入口 | 补要求覆盖清单，不写成支持或 integrated |
| 跨环境检查 | 当前 AI 环境是否与目标环境一致；若不一致，是否只做样例包/adapter 审计或判读目标环境回传原始输出 | 删除跨环境 integrated 判断，改为不可验证范围或 30 验收任务 |
| Gate 检查 | 是否覆盖目标环境 API 不可用、事件不足、写入前未经 Human Gate、验证未通过、stale path 和缺少环境分析/交还的暂停条件 | 暂停并交还 Human |
| 交还检查 | 编写完成或阻断时是否交还要求 / 入口资产清单、未写入项、决策记录、验证摘要、不可验证范围、下一步和 source_refs | 补交交还摘要，不声明闭环 |

## 10. Human Gate

以下情况必须进入 Human Gate：

1. 为新增目标环境编写插件要求、repo-local 样例包或目标环境等价入口资产——环境分析完成后、动手写文件前；
2. 更新已有插件的 Hook event routing、目标环境等价配置或 shim / adapter——差异清单展示后、修改前；
3. 修改 manifest / package declaration / settings hook 中的事件注册或路径引用；
4. 将目标环境真实入口资产部署到实际安装位置（经 30 安装 / 验收流程）；
5. 声称插件编写完成——必须经 4/4 交还阶段 Human 确认；
6. 编写过程中发现目标环境 Hook API 文档不足、事件不支持或 payload 格式不明确；
7. 接受残留风险、未验证范围或环境差异缺口。
8. 在当前 AI 环境中声明另一个目标环境的 lifecycle integrated、阻断已生效或 completion_claim 已接入。

## 11. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 目标环境 Hook API 文档不可用，无法确认支持的事件和 payload 格式；
2. 目标环境无法映射 `ldvh.session_start` 或 `ldvh.pre_tool_use` 两个核心 LDVH canonical event；
3. 发现 shim 中复制了 specs 规则、校验逻辑或 Human Gate 判断；
4. 路径指向 stale V1/V2 产物但未确认正确的 V3 路径；
5. 本地验证（语法、干跑、降级）未通过；
6. 缺少 1/4 环境分析或 4/4 交还阶段；
7. Codex 标本被直接复制后不改，当作新环境插件；
8. 将本地语法验证通过写成真实环境触发已验证。
9. 当前在 Codex 却声明 WorkBuddy lifecycle 已通过，或当前在 WorkBuddy 却声明 Codex lifecycle 已通过；除非有目标环境当次原始输出并按 30 完成判读。
