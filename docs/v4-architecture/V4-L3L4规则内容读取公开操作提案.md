# V4 L3/L4 规则内容读取公开操作提案

> 记录性质：当前主任务对并行调查结果的收敛提案，不是规则源，不授予 Helper 公开操作身份，不授权 Code 实现。
> 形成时间：2026-07-13

## 1. 提案目标

当前 `read-specification-candidates` 只提供 L0–L2 的规范发现、概览和关系，`resolve-governance-scope` 只解析工作对象管辖范围。AI 仍不能通过 Helper 取得 01 定义的 L3 规则内容或 L4 完整来源，因此无法在不自行全文搜索的情况下获得具体规则、适用范围、必要定义、验证、Human Gate 和 Stop Conditions。

本提案只解决“按精确来源读取当前 L3/L4 内容”。任务相关性、规则适用判断、事实读取、行动模板选择和状态变更不属于本操作。

## 2. 00 对齐判断

该能力直接服务 00 的：

1. V1：从稳定职责标识符和当前来源位置精确取得规则；
2. V2：使规则正文与理解它所需的范围、定义和验证上下文保持在同一结果中；
3. V3：为后续规则适用判断提供充分来源，但不自行创造适用结论；
4. V5：使 AI 的判断可以回到当前 Working Tree 中的具体来源；
5. Helper CLI 边界：Helper 组织并提供当前规则信息，具体规则效力仍来自来源规范，未命中规则时不限制 AI 的普通求解路径。

如果读取操作根据自然语言自行筛选“相关规则”、输出 `applies`、建立规则优先级或把读取成功解释为规则已经履行，就会偏离 00。本提案明确排除这些行为。

## 3. 并行调查的共同结论

V3 经验审核与当前 Code/tests 影响分析形成以下一致结论：

1. 保留精确来源、渐进式披露、关系检查、缺口、部分结果和来源回指；
2. 不继承固定读取 `00/01/02`、read-plan acknowledgement、receipt/cache、静态章节映射或全局写前门禁；
3. 不扩大现有 L0–L2 操作，也不把 L3/L4 逻辑加入 `helper.service`、现有投影模型或 governance 状态；
4. L3/L4 需要独立的精确选择、正文范围定位、上下文组成和全文读取责任；
5. 默认读取当前 Working Tree，不以 Index、`HEAD`、缓存或同一 Git 仓库的其它 worktree 替代当前来源；
6. 读取只提供按精确输入选择的规则内容，不执行任务相关性或规则适用判断。

## 4. 建议的公开操作边界

### 4.1 新建操作，不扩展现有操作

建议在 01 中新建独立 Helper 公开操作。候选 `operation_key` 为 `read-specification-content`；该 key 在 Human 确认并进入当前规则源前只是提案，不具备公开身份。

不建议扩展 `read-specification-candidates`，原因是其当前责任和输入已经明确限定为 L0–L2，且明确拒绝 L3/L4、任务相关性和管辖解析。把两类读取合并会使发现与正文消费的输入、结果和失败语义重新耦合。

### 4.2 当次调用只使用确认操作身份的当前规则源

处理当次调用时，当前操作只从用于确认 `read-specification-content` 公开身份的当前规则源中读取内容；仅允许读取其中声明为 `active` 且通过全部适用已实现机械检查的规范载体，不沿 `work_object_locators` 到管辖项目中寻找另一套 `specs/`。尚未由 Code 实现、无法机械证明的完整规则源资格条件继续进入缺口；读取结果不因此宣称载体已经证明满足全部当前规则源资格。

依据是 00 和 01 当前定义的规范模型对象是 LDVH 正式 Specs；02 定义工作对象及其实际 worktree，不表示每个管辖项目都具有可被当作 LDVH 当前规则源的同名目录。允许目标项目自行提供规则源需要独立定义身份、资格、冲突和安装关系，不能由本操作推断。

因此当前不消费 `task`、`work_object_locators` 或 `scope.governance_resolution` 来选择来源，响应中的管辖解析保持为空。未来确有项目专属正式规则源需求时，必须先由 Specs 另行定义。

### 4.3 当前内容，不支持历史版本

当前只读取规则源检查所对应的实际 Working Tree，包括未提交和未跟踪但符合 01 候选规则的当前文件；不支持 Git ref、commit、Index 或历史比较输入。

历史内容仍可通过普通 Git 工具调查，但不得混入当前规则结果。未来若需要 Helper 历史读取，应另行定义版本定位、历史身份和当前/历史区分，不在当前契约预建兼容机制。

## 5. 建议的输入边界

### 5.1 共同字段

沿用 04 的共同请求。`requested_disclosure` 对本操作只接受 `L3` 或 `L4`，不允许 `null`、L0–L2 或其它值，也不静默改写请求层级。

### 5.2 精确选择

建议 `arguments` 只包含 `selections`，为一个或多个选择项。每项至少包含：

| 字段 | L3 | L4 | 建议语义 |
|---|---|---|---|
| `responsibility_key` | 必填 | 必填 | 精确 `spec_key` 或 `attachment_key`；不接受标题、编号、路径、关键词或模糊回退 |
| `heading_path` | 必填 | 必须为空 | 从 H1 下开始的精确 H2/H3 标题文本数组，用完整层级路径消除同名小节歧义 |

当前不支持任意表格行选择。选中包含表格的 H2/H3 时返回该标题范围内的完整表格；这样比发明缺少通用稳定行键的行定位协议更确定。`heading_path` 成员必须已经去除首尾空白并精确唯一匹配。未来只有真实需求证明整节过大且表格存在可复核稳定行身份时，再扩展行选择。

重复选择项无净价值，建议作为无效输入拒绝。多个选择项分别形成独立子范围，并保持请求顺序；一个成功、一个失败时允许形成部分结果，失败项不得污染独立成功项。

## 6. L3 读取与必要时展开 L4

### 6.1 L3 基本内容

选中 H2 时读取该 H2 到下一个 H2 前的完整范围；选中 H3 时读取其所属 H2 中位于该 H3 前、对全部子节共同适用的正文，以及该 H3 到下一个 H2/H3 前的完整范围。代码围栏内的标题文本不参与结构定位。

每个 L3 结果还必须保留：

1. 来源职责标识符、类型、当前标题和 Git 相对路径；
2. 精确标题路径和实际行范围；
3. 当前 Working Tree 观察时间；
4. 同一来源的适用范围；
5. 与所选规则相关的验证要求、Human Gate 和 Stop Conditions；
6. 附件选择时的当前父规范身份、授权位置和必要父正文；
7. 未能机械确定的必要定义、上位依据或其它上下文缺口。

### 6.2 无法证明最小完整时展开 L4

Code 不能仅靠标题相似或关系可达性解释“必要定义”和具体规则语义。当前采用保守行为：已经精确定位的选择如果无法由当前结构形成 01 要求的最小完整 L3，或者必要定义与上位依据无法确定时，自动把该选择展开为 L4，并明确返回实际披露层级和展开原因。实现没有可复核机械判据时必须展开 L4。附件授权、父正文、来源身份或当前内容本身冲突时，不能用 L4 掩盖冲突；标题路径缺失或歧义属于精确选择不成立，使请求无效，不能回退全文冒充精确选择。

如果 L4 因规则拒绝、技术条件不足或实现错误无法按契约完整读取，则按实际原因报告未完成范围，不返回被截断或自称完整的 L3。读取成功只证明对应内容已经读取，不证明规则适用、Human Gate 或 Stop Conditions 已触发、验证已通过或工作已完成。

## 7. L4 读取边界

普通规范或根规范的 L4 返回该职责当前文件的完整内容。授权附件的 L4 返回附件全文，并同时返回当前父规范全文，因为附件不能脱离父规范授权和正文独立解释。

`basis`、`related_specs` 或图可达性不使所有上位规范自动进入 L4。消费方需要其它完整来源时，应在同一请求中显式增加其 `responsibility_key`；Helper 不根据关系图创造适用性或优先级。

当前不设置可静默截断的正文预算。调用方通过精确选择控制范围；实际环境无法返回完整结果时必须报告未完成或错误，不能返回不完整正文并标记成功。未来只有真实输出限制形成后，才定义可复核的上限和分段协议。

## 8. 建议的结果边界

领域结果至少需要逐项表达：请求选择、实际披露层级、来源身份、当前路径、标题路径或全文范围、内容组成、来源回指、展开原因和该项缺口。来源回指对象必须满足 01 正式契约定义的固定字段要求，使职责标识符、Git 相对路径、标题位置、行范围、实际 worktree 和观察时间都有固定机器位置。共同响应继续使用 04 已有的 `result`、`scope`、`sources`、`disclosure`、`gaps`、`verification` 和 `diagnostics`，不为本操作修改共同顶层字段。

建议结果遵守：

1. 所有选择按契约完成时为 `ok`；
2. 独立选择既有完成，又有因拒绝、不可用或错误未完成时为 `partial`；
3. 零个完成且适用规则、授权或 Stop Conditions 禁止读取时为 `rejected`；
4. 零个完成且实现、能力依据、配置、依赖或环境条件不足时为 `unavailable`；
5. 输入字段、类型、层级、重复项、未知职责标识符或无法唯一匹配标题时为 `invalid_request`；
6. 实现异常或来源身份与范围无法按契约确定时为 `error`；
7. 不使用 `no_change`，因为该操作是纯读取。

这些是对现有 04 结果语义的应用，不建立新的外层状态。

## 9. 需要修改的正式来源

如果 Human 接受本提案，建议只修改：

1. `specs/01-规范模型基础规范.md`：新增公开操作声明、输入、结果、L3/L4 读取和验证规则；
2. 必要时 `specs/attachments/01.Att.01-LDVH双语术语表.md`：只同步已经由正文定义且确有登记必要的现有术语，不为字段说明制造新术语。

当前不建议修改 02、03、04 或 04.Att.01：02/03 的 Working Tree 和来源边界已经充分；04 的共同服务字段和结果语义不变；本操作的领域字段应由 01 定义。如果正式设计最终改变共同字段或管辖消费边界，再重新判断影响范围，不能提前扩写。

## 10. Code 实现边界预案

Specs 激活后再建立实现规划。当前调查建议的内聚模块为：精确选择、Markdown 片段范围、L3 上下文组成、L4 全文读取和领域请求/结果适配；复用现有 repository、markdown、identity、structure、graph、operation runtime 和共同响应。

禁止把实现继续堆入现有 L0–L2 投影、`helper.service` 或 governance resolver。公开操作注册、共同服务边界、共享测试和最终集成由主任务单线完成；新建模块和聚焦 tests 可以按互斥文件所有权并行。

## 11. 术语与概念检查

本提案没有新增正式架构术语。L3/L4 沿用 01 已有的披露层级定义；其它已登记术语继续以当前术语表及其唯一定义来源为准。标题路径、选择回显字段和内容部分字段只是普通描述或局部 Schema 说明，不建立新的正式术语。

候选 `operation_key` 是待确认机器标识，不因出现在本记录中获得公开身份。正式 Specs 起草时仍需检查标题、表头、字段名和重复表达，避免把实现简称或本提案措辞扩散为未定义概念。

## 12. Human 已确认的边界

2026-07-13 Human 已确认以下九项边界：

1. 新建独立操作，不扩展 `read-specification-candidates`；
2. 处理当次调用时，只从用于确认本操作公开身份的当前规则源读取内容，不从工作对象实际 worktree 发现另一套 Specs，也不把尚未机械证明的资格条件改写为已证明；
3. `operation_key` 使用 `read-specification-content`；
4. L3 当前只精确选择 H2/H3，不支持任意表格行；
5. L3 无法机械保证最小完整上下文时自动展开 L4；
6. L4 不自动递归展开全部 `basis`，其它来源由请求显式选择；
7. 当前只读当前 Working Tree，不支持历史 Git 版本；
8. 一次请求支持多个精确选择，并按独立子范围形成 `partial`；
9. 不修改 Helper 共同响应字段，领域契约全部由 01 承担。

Human 确认只授权主任务按照这些边界起草正式 01 变化，不替代术语审核、独立复核、当前规则源机械检查或 Code 实现与验证。本记录本身仍不是规则源。
