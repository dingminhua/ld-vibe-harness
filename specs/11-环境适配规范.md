## 1. 价值判断

本文存在的价值，是把“规则如何进入协作环境”从迁移讨论和临时 README 中收口到正式规范，减少 AI 把文件存在、脚本可运行、manual 命令可调用或历史 Rules/Skill 资产误判为真实环境接管的负担。

环境适配服务 00 的保障与衔接层定位和五类构成要素应用。它只定义入口、触发、状态、payload、receipt、安装、回滚和缺口分流边界，不替代 specs 规则、事实源、行动模板、Code、Web 或 Human Gate。

## 2. 权威依据

本文承接 `specs/01-保障与衔接.md` 的环境入口、Hook、Rules、插件、Runtime Protocol、canonical event、trigger source、receipt 和缺口分流语义，承接 `specs/02-AI行为规范.md` 的保障需求消费时机，承接 `specs/07-Code确定性执行规范.md` 的确定性执行边界，承接 `specs/09-测试与验证规范.md` 的验证声明边界，并与 `specs/10-受管项目接入规范.md` 的 target-first 项目判断配合。

若本文与 00 或 01 的价值和保障消费语义冲突，以 00、01 和 Human Gate 为准。若 Code、Hook、Web、测试、review、README 或迁移材料与本文冲突，以本文和上位规范为准。

## 3. 归口边界

本文归口定义 V3 环境入口如何被分类、声明、验证、安装、回滚和分流。

本文不归口定义 AI 行为保障需求本体、事实对象字段、行动模板步骤、Code 内部实现、Web 页面/API 数据路径、commit message 契约或测试用例细节。这些内容分别由 02、05/20-24、06、07、08、03 和 09 承接。

环境入口不得成为第六类构成要素。环境入口只是保障与衔接层进入具体协作环境的承载方式，不能替代五类构成要素，也不能反向定义规则源或事实源。

## 4. 适用范围

本文适用于：

1. 当前 worktree 的 `git.commit-msg` Hook；
2. `manual.runtime_adapter`、`manual.session_start`、`manual.pre_tool_use` 和 `manual.completion_claim`；
3. 后续外部 runtime adapter、插件、repo instruction、tool hook、completion hook 或等价入口候选；
4. Rules / Skill 历史资产在 V3 中的 legacy/removed 边界；
5. 任何声称环境已经自动接管、阻断、放行、验收或授权的输出。

## 5. 环境入口类型

环境入口必须先归入 `specs/attachments/11.Att.01-环境入口类型表.md` 的类型闭集，再声明接入状态。

`automated_hook` 是当前环境能自动触发、能阻断失败、能被安装状态检查复现的入口。当前只有 `git.commit-msg` 满足该条件。

`manual_entrypoint` 是 Code CLI、README 命令或外部调用方可以手动触发的入口。manual-ready 只能证明入口可用，不证明协作环境会自动触发，也不证明写入、完成声明或 Human Gate 已被拦截。

`external_adapter_candidate` 是后续外部环境、插件或 runtime adapter 可以接入的候选。候选必须等真实触发、稳定 payload、失败处理、安装状态、回滚方式和测试证据齐备后，才能升级为自动入口。

`removed_top_level` 用于 Rules / Skill 这类 V3 已取消的顶层机制。它们不是待启用入口；若后续需要入口可见能力，必须转为 repo instruction、外部包装、manual entrypoint 或正式环境 adapter，而不是恢复顶层目录机制。

## 6. 接入状态声明

环境接入状态必须使用 `specs/attachments/11.Att.02-环境接入状态表.md` 的状态闭集。

状态声明必须区分：

1. `available`：文件、脚本或候选入口存在；
2. `manual_ready`：可手动或外部调用，但没有自动触发；
3. `integrated`：当前环境真实自动触发，失败可阻断，安装状态可复现；
4. `deferred`：后置，不阻断当前主线；
5. `removed_top_level`：V3 顶层机制已取消，不作为后置入口；
6. `absent`：没有可识别入口。

`environment_integrated=partial` 只能在至少一个真实自动入口 integrated，且其它入口边界如实声明时使用。当前 worktree 的预期状态是 `hook_integrated=git.commit-msg`，runtime adapter、session start、pre tool use 和 completion claim 均为 manual-ready 或 deferred。

Code、README、测试、迁移记录和 AI 完成声明不得把 `available`、`manual_ready`、`deferred` 或 `removed_top_level` 写成 `integrated`。

## 7. Runtime payload 与 receipt

runtime payload 字段由 `specs/attachments/11.Att.03-runtime-payload字段表.md` 承接。payload 至少应能表达 event、trigger_source、target_path、operation、task、acknowledged_paths、verification_evidence 和 session_id 等信息。

receipt 是过程输出和证据候选，不是事实源、授权、放行或 Human Gate 完成。receipt 可以帮助 AI 定性入口是否被调用、读取计划是否覆盖、诊断是否产生和缺口如何分流，但必须回到 03 的事实源边界和 09 的验证声明边界。

stdout-only receipt 只能作为当次过程输出。若后续需要稳定 receipt 存储，必须先补事实源回写规则、字段 schema、清理策略和测试，不得把临时 stdout 输出升级为事实源。

## 8. Rules 与 Skill legacy 边界

V3 不保留 `rules/` 或 `skills/` 顶层目录机制。Rules 和 Skill 只作为历史术语、来源材料或外部包装候选存在。

V2 Rules 的入口可见能力可以被转写为 repo instruction、环境薄引用、manual entrypoint 或外部 adapter 候选，但不得恢复 Rules 顶层规则源、Rules registry 或与 specs 并列的权威入口。

V2 Skill 的可复用工作流能力可以被吸收为行动模板步骤、Action Guide 提示、Code CLI 或外部包装候选，但不得恢复 Skill 顶层机制、Skill registry、Skill 执行闭环或用 Skill 输出替代主控 AI 判断。

若环境本身提供名为 Rules 或 Skill 的机制，V3 仍必须按本文重新分类其入口类型和状态；名称相同不等于 V3 顶层机制恢复。

## 9. 安装、回滚与受管项目边界

安装、覆盖或卸载真实环境入口必须有安装目标、回滚方式、状态检查和验证命令。最小检查项由 `specs/attachments/11.Att.04-环境安装回滚检查表.md` 承接。

当前 worktree 的 `git.commit-msg` 通过 `core.hooksPath=hooks` 接入，只声明当前 Git 仓库的 commit message 校验入口已自动触发，不声明外部受管项目、其它 worktree、session start、pre tool use 或 completion claim 已接入。

后续将环境入口接入受管项目时，必须复用 10 的 target-first、Git common-dir 和多目标边界。不得用当前 cwd、路径相似、repo 名称或用户意图替代受管项目解析。

## 10. 保障措施

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口分类要求 | 环境入口必须先分类再声明状态 | 11.Att.01、Code audit、README | 环境治理 | 新增、删除或解释环境入口时 |
| 状态声明要求 | available、manual_ready、integrated、deferred、removed_top_level 和 absent 不得混写 | 11.Att.02、environment_status、environment_entry_audit | 状态治理 | 声称环境已接管、阻断或后置时 |
| payload 边界要求 | runtime payload 和 receipt 不得替代事实源、授权或 Human Gate | 11.Att.03、03、09 | 证据治理 | 新增 runtime adapter 或 receipt 时 |
| legacy 边界要求 | Rules / Skill 不得恢复为 V3 顶层机制 | 本文、04.Att.06、environment_entry_audit | 术语治理 | 出现 Rules/Skill 资产、目录或说明时 |
| 安装回滚要求 | 自动入口安装必须可检查、可回滚、可验证 | 11.Att.04、install_git_hooks、tests | 环境治理 | 安装、覆盖或卸载真实 Hook/adapter 时 |

## 11. 验证方法

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 结构检查 | 11 正文和附件是否有身份块、父规范引用、状态和 Code consumption | 修正文档或 formal gate |
| 状态检查 | `environment_status.py` 是否区分 automated hook 与 manual entrypoints | 回到 Code 和本文状态闭集 |
| 入口审计 | `environment_entry_audit.py` 是否把 Rules / Skill 标为 `removed_top_level`，并把 runtime 自动入口标为 deferred | 修正审计逻辑或本文边界 |
| 安装检查 | 自动入口是否能报告安装状态、路径和回滚方式 | 不得声明 integrated |
| 验证声明检查 | README、迁移记录、完成声明是否没有把 manual-ready 写成自动接入 | 回到 09 和本文修正声明 |

## 12. Human Gate

以下情况必须进入 Human Gate：

1. 新增、删除、改名或重排环境入口类型、接入状态闭集或 removed_top_level 口径；
2. 将 manual-ready、available、deferred 或 absent 入口升级为 integrated；
3. 安装、覆盖、卸载或扩大真实自动 Hook、插件、runtime adapter 或 repo instruction 的影响范围；
4. 恢复 Rules / Skill 顶层机制，或把 legacy 资产重新写成 V3 顶层入口；
5. 接受环境入口无法回滚、无法验证、无法定位 target 或无法说明失败处理的风险；
6. 声称环境入口已经完成授权、放行、验收或 Human Gate。

## 13. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 无法区分入口是 automated、manual-ready、candidate、removed_top_level 还是 absent；
2. 文件存在、脚本存在、README 命令存在或测试通过被写成自动触发证据；
3. runtime receipt、Hook 输出、Code 输出或 Web 展示正在替代事实源、Human Gate 或完成验收；
4. Rules / Skill 目录、注册表或执行闭环被恢复为 V3 顶层机制；
5. 安装或卸载真实入口前没有回滚方式、状态检查和 Human 确认；
6. 受管项目环境入口未通过 target-first 和 Git common-dir 边界确认。

## 14. 待补齐事项

1. 后续如出现真实 session start、pre tool use 或 completion claim 环境 Hook，应先补安装、payload、失败处理、回滚和测试，再升级状态；
2. 后续如需要 repo instruction 或插件入口，应先审计其触发点、作用域和与本文状态闭集的映射；
3. 后续如需要稳定 receipt 存储，应先补事实源回写规则、保留策略和验证测试；
4. 后续外部受管项目接入时，应补跨 repo / worktree 安装和回滚测试；
5. 后续如果 action template 需要调用环境入口，应只消费本文状态，不反向定义环境接入规则。
