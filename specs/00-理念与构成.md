## 1. LDVH 为什么存在

Vibe Coding 让人用自然语言表达目标，由 AI 推理生成实现，门槛低、反馈快、产出多。但 AI 生成代码的本质不是确定性编译，而是基于开发环境上下文、模型训练经验和参数形成的概率性推理，因此天然受上下文依赖、概率性输出和无状态影响。

虽然目前，Vibe Coding 已经能够较好完成单个功能、局部修复，也能在明确测试目标和验收反馈下承担较长时间的连续工作。但是，真实开发往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是如何在项目持续演进中，避免项目从“开始还不错”逐渐变成“难以继续做”的问题。于是：

设计的架构是：

1. 以 AI 执行者为第一服务对象；
2. 以用户事实源为基础；
3. 以五类构成要素为内核；
4. 以保障与衔接层提供运行支撑；
5. 以 V1-V10 价值判断为标准。

采用的方法是：

1. 用规范体系定义产品、边界和保障要求；
2. 用事实模型组织事实、状态、证据和经验；
3. 用行动模板沉淀可复用行动结构；
4. 用 Code 提供确定性执行、校验和反馈；
5. 用 Web 桥接 Human 与 AI，呈现状态、风险和证据。

设计的目标是：

——让 AI、Human、Code 可以各展所长，使 Vibe Coding 推理更稳定、结果更可控、产出更高效；

——进而让环境、模型、使用者可以自由组合，使 Vibe Coding 使用更方便、成本更灵活、协同更顺畅。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于实践沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

LDVH 以 AI 执行者为第一服务对象。要说明这一点，需要先理解 AI 执行者的依赖、能力与本质。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——缺少可用工具或环境能力时，AI 容易停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的工具或环境能力，并把反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

基于这些依赖、能力与本质，LDVH 的设计重点，不是要求 AI 自发变得可靠，而是基于用户事实源底层原则，用五类构成要素组织支撑能力，并通过保障与衔接层进入具体协作环境，最终服务 AI 实现 V1-V10 的价值闭环。

## 3. 以用户事实源为基础

用户事实源是 LDVH 的底层权威原则。它不是普通资料库，也不是某个环境、模型或会话的记忆，而是用户拥有并持续维护的项目事实基础，用来承载稳定事实、判断依据、状态、验证证据、经验沉淀和回写位置。

用户事实源首先属于用户。项目连续性不应绑定在某个 AI 协作环境、某个模型记忆，或某个使用者的临时理解里。AI 可以读取、整理、建议回写，Code 和 Web 可以校验、展示、辅助消费，但最终事实必须回到用户可掌握、可迁移、可追溯的事实源中。

用户事实源必须可追踪。稳定事实的形成、修改、验证和关闭，应能够回到明确承载位置和 Git commit records。聊天过程、工具输出、缓存、Web 页面状态、运行时索引或环境记忆，都不能自动成为最终事实源；只有被吸收并写入对应权威事实源后，才可能成为稳定事实。

用户事实源还必须有组织。它不是把材料集中保存，而是以清楚的承载位置、权威边界、引用关系和回写位置，组织成 AI 能定位、Human 能确认、工具能校验、后续协作者能接续的事实秩序。事实模型可以承接需要对象化、状态化或证据化管理的事实，但不替代用户事实源整体；Code 可以确定性消费事实源，但不替代事实源、Human Gate 或完成验证。

因此，用户事实源不仅服务 AI 少读、少猜、少漂移，也进一步支撑环境、模型和人的解耦。环境代表不同工作入口和操作习惯，模型代表不同能力与使用成本，人代表不同协作角色和确认责任。只要权威事实、行动状态和验证证据能够回到同一用户事实源，项目就可以在不同环境、不同模型、不同参与者之间重新组合推进；变化的是读取、触发、执行、展示、验证和协作方式，不是项目的事实基础。

事实源原则至少包括：

1. 用户事实源属于用户，是用户可维护、可审查、可迁移的权威事实资产；
2. 稳定事实必须回到明确的 Git 可追踪文件承载位置；
3. 同一稳定事实不应长期存在多个互相竞争的权威副本；
4. 聊天、AI 推理、工具输出、Web 状态、缓存、索引和派生视图不能自动成为最终事实源；
5. 派生内容必须能回指来源并声明非权威边界，只有回写到对应权威事实源并满足必要验证后，才可能成为稳定事实；
6. 用户事实源应具备清楚的组织秩序，使 AI、Code 和 Web 在各自边界内能够稳定定位、引用、校验、展示和回写；
7. 事实模型可以组织需要对象化、状态化或证据化管理的事实，但不能吞并用户事实源整体；
8. Code 可以确定性消费、校验、聚合、索引和受控写入事实源，但不能替代事实源、Human Gate 或完成验证；
9. 验证证据、关闭证据、决策依据和经验沉淀必须能回指用户事实源；
10. 事实源修改应具备 Git 可追溯记录。

具体事实源类型、证据规则、回写规则、吸收规则、Code 消费规则和 Git 追溯规则，由后续相关规范承接。保障与衔接层如何让用户事实源进入不同环境、模型和使用者的协作现场，由后文继续定义。本文只定义上位原则。

## 4. 五类构成要素

在用户事实源底层原则之上，LDVH 通过五类构成要素组织服务 AI 的支撑能力。五类构成要素不是第 2 节和第 3 节之外的新体系，而是第 3 节“用五类构成要素组织支撑能力”的归口化表达。

| 构成要素 | 定位 | 回答的问题 |
|---|---|---|
| 规范体系 | 上位原则、边界和价值判断 | 如何定义规则、边界、价值判断和保障要求，支撑 AI 的目标推导、场景识别、行动判断和验收标准生成 |
| 事实模型 | 事实对象化与状态秩序 | 如何在事实源边界内组织需要对象化、状态化或证据化管理的事实，使 AI 能定位、判断、验证和回写 |
| 行动模板 | 可复用行动结构 | 如何为重复场景提供上下文读取、步骤组织、风险暂停、验证关闭和交还方式 |
| Code | 确定性执行、校验和上下文压缩 | 如何通过确定性解析、聚合、校验、诊断、反馈和上下文压缩减少 AI 的读取、判断和验证负担 |
| Web | Human-facing 信息桥接和受控交互 | 如何让 Human 看见状态、风险、证据、待确认事项和 AI 行动方向，并完成验收判断与方向校正 |

五类构成要素不是上下层级，也不是五种同质能力。它们性质不同、归口不同，共同服务第 2 节和第 3 节定义的 LDVH 目标。

五类构成要素不是资产分类。构成要素回答 LDVH 由哪些能力面组成；资产回答这些能力面由哪些可维护承载物实现、登记、验证和适配。一个构成要素可以由多种资产共同承载，一个资产也可能服务多个构成要素。

用户事实源提供权威事实基础；保障与衔接层提供运行支撑，使五类构成要素和用户事实源能够进入具体协作环境。保障与衔接层的具体承载物、命名、登记和适配规则不在 00 定义，由后续对应规范承接。

## 5. V1-V10 价值判断

LDVH 的五类构成要素、保障与衔接层及其下属机制，都必须服务以下价值判断中的一项或多项。V1-V10 不是独立于第 2 节和第 3 节的新目标，而是用于判断某项机制是否真的能缓解 AI 的概率性推理、上下文依赖和无状态风险。

字段、附件、资产承载物、工具、派生关系、Code 输出和 Web 展示等都不是与五类构成要素和保障与衔接层并列的准入主体。它们必须先归属到规范体系、事实模型、行动模板、Code、Web 或保障与衔接层的对应承载位置，再接受 V1-V10 判断。

派生机制只能作为五类构成要素或保障与衔接层的实现方法之一。它服务哪些 V 项取决于自身归属和用途，但不得成为独立价值标准、独立构成要素、事实源或工作对象；具体结构、生成、展示和消费边界由后续对应实践定义。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | AI 能否根据当前目标和场景快速定位应读取的事实源、规范入口、工作状态和工具入口 | AI 盲目全文阅读、找不到入口、遗漏关键事实或规范规则 |
| V2 | 可行动理解 | AI 能否在足够但不过载的上下文中形成可执行的目标、边界、事实、状态和验收标准理解 | AI 反复询问已有事实、误读项目边界、遗漏关键约束，或读了很多仍不能行动 |
| V3 | 正确判断 | AI 能否判断事实源边界、风险、阻塞、工具需求、流程复用需求和专项协作调度需求 | AI 误判工作性质、错过风险或阻塞、错误选择工具、流程或专项协作方式 |
| V4 | 稳定执行 | AI 能否依据规范体系、事实模型和行动编排形成可执行路径、拆解步骤并稳定推进工作，而不是凭聊天记忆自由发挥 | AI 绕过规范规则、跳过工作状态、无法形成稳定路径或直接修改不该修改的事实 |
| V5 | 门禁识别 | AI 能否识别 Human Gate，知道何时必须暂停并等待人确认 | AI 擅自执行高影响变更、跳过确认、误关闭工作对象 |
| V6 | 强制验证 | AI 的关键行动、状态变更、事实回写和交付结论能否通过 Code 校验、检查结果、审查证据、Web 呈现或 Human 确认验证；没有验证证据的完成不视为真正完成 | AI 只凭自述判断完成、用推测性表述替代验证，或验证结果缺失、不可复现 |
| V7 | 证据沉淀 | AI 的验证结果、执行证据、决策依据或 Git 提交记录能否在需要追溯时被稳定找到 | 完成了但无法证明、结果只存在聊天里、后续无法追溯 |
| V8 | 可靠回写 | 稳定事实能否按事实源边界回写到 Git 文件事实源 | 事实漂移在聊天、缓存、Web 页面状态、工具输出或派生数据中 |
| V9 | 人类确认质量 | AI 能否向 Human 提供足够的事实源、证据、项目态势、风险、影响和待确认事项，使 Human 给出可被 AI 消费的高质量确认 | Human 只能凭感觉验收，AI 无法获得明确、可追溯、可执行的确认 |
| V10 | 持续完善 | AI 能否识别可复用经验、反复问题和体系缺口，并推动其回到规范体系、事实模型、行动模板、Code、Web 或保障与衔接层中 | 同类错误反复发生，可复用经验、规范规则缺口和工具能力不足没有沉淀 |

## 6. 构成要素实践准入判断

后续任何规则、对象、字段、附件、工具、资产承载物、Code 输出、Web 展示、保障与衔接承载物或派生机制，作为五类构成要素或保障与衔接层的实践纳入 LDVH 前，必须同时满足：能归属五类构成要素之一或保障与衔接层的对应承载位置；至少服务 V1-V10 中一项；说明预期减少的 AI 负担类型、判断依据、新增维护成本和替代方案；具备事实源边界、验证方式、退出边界、能力缺口处理边界和残留风险说明；不触发本文列出的反向排除项。

在此基础上，还应回答：

1. 它归属五类构成要素中的哪一类，或保障与衔接层的哪类承载位置；如果涉及事实源，它如何遵守事实源底层原则；
2. 它服务 V1-V10 中哪些价值；
3. 它是否仍以 AI 执行者为第一服务对象；
4. 它预期减少 AI 的哪类定位、理解、判断、执行、验证或回写负担，依据是什么；
5. 它相比不新增该实践，是否让 AI 少读、少猜、少重复、减少不必要的 Human 确认或更容易验证；如果不能说明，应说明为什么仍需新增；
6. 它是否会制造第二事实源；
7. 它是否只是新增规则、对象、附件、工具或资产承载物数量，却没有减少任何可说明的 AI 负担；
8. 它是否绕过 Human Gate 或压缩 Human 的关键判断；
9. 它是否能被 Code、Web、测试、审计或临时核对动作稳定消费；若尚不能消费，缺口原因和后续承接位置是什么；
10. 它是否有明确事实源边界、验证方式、退出、废弃、迁移或风险接受边界。

以下情况不应作为构成要素实践纳入 LDVH：

1. 不能归属五类构成要素或保障与衔接层，或不能说明服务 V1-V10 的规则、对象、字段、附件、工具或资产承载物；
2. 只是复制已有规则、制造新入口或增加阅读负担的内容；
3. 把 AI 的语义理解、规范权衡、风险判断或 Human Gate 压缩为不可审查的自动结论；
4. 把工具缓存、Web 页面状态、运行时索引、派生投影或聊天过程当作最终事实源；
5. 创建新的规则、附件、对象、保障与衔接承载物或 Code/Web 能力，却不能说明归属关系、替代方案和预期减少的 AI 负担；
6. 因未来想象能力而阻塞当前可验证实践。

## 7. 规范保障要求

00 是 LDVH 的最高价值锚点。后续规范、附件、构成要素实践和派生机制不得削弱本文定义的存在理由、AI 第一服务对象、五类构成要素、用户事实源底层原则、保障与衔接层和 V1-V10。

00 不重复每篇规范都应具备的入口可见、结构校验、生命周期同步和 Code 消费等基础治理要求；保障与衔接由 01 统一定义，Specs 结构治理由 02 统一定义。本文只声明 00 作为最高价值锚点特有的上位约束承接要求。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续规范、附件、构成要素实践和派生机制必须承接本文定义的存在理由、AI 第一服务对象、五类构成要素、保障与衔接层、事实源底层原则、V1-V10 和构成要素实践准入判断，不得改写、绕开或弱化为普通建议 | 00、01、02、Human Gate、后续规范创建/审核行动编排或一致性核对；具体执行闭环不在 00 定义 | 价值治理 | 新增、修改、合并、拆分、重命名或迁移规范，或后续机制试图重新解释本文最高锚点时 |

## 8. Human Gate
