# PMKit 审计流程

> 创建日期：2026-05-28
> 定位：受管理项目的 PM Kit 合规审计流程
> 适用范围：所有接入 PM Kit 的受管理项目
> 上位依据：specs-v2/00、specs-v2/10、specs-v2/11、specs-v2/14

## 一、流程定义与触发条件

审计是受管理项目运行后的合规检查过程，确保项目现状符合 PM Kit 规范。审计是"从有到对"的检查过程，不是建设过程。初始化归 50-PMKit初始化流程。

| | 50-PMKit初始化流程 | 51-PMKit审计流程 |
|---|---|---|
| 触发时机 | 项目首次接入 | 项目已运行后定期或按需 |
| 行为性质 | 建设：补齐缺失的事实源 | 检查：发现问题和缺口 |
| 结果 | 创建 docs、Rules、Kit Base 等事实源 | 生成审计快照、分流审计发现 |
| AI 角色 | 帮项目搭建基础 | 帮项目检查一致性 |

触发条件：

- 定期合规巡检；
- 版本发布前的质量门禁；
- 代码变更后重新校验技术健康度；
- 项目结构发生变更后重新校验；
- 初始化完成后。

## 二、执行步骤

### 2.1 产品与项目类型判定

#### 2.1.1 产品形态

审计前必须读取 `product.yaml` 并判定产品/项目角色：

| 产品/项目角色 | 判定方式 | 审计策略 |
|---|---|---|
| 单项目产品 | `projects` 只有 1 个项目，且 `path` 为 `.` | 执行单项目审计；跨项目项标记不适用 |
| 多项目产品治理项目 | `projects` 数量 > 1，且存在 `id: product` 或 `path: .` | 执行产品级与跨项目治理审计 |
| 多项目产品子项目 | 多项目产品中非治理项目 | 执行项目内部审计，检查是否正确引用治理规则 |

#### 2.1.2 项目性质

| 项目性质 | 判定方式 | 技术审计重点 |
|---|---|---|
| 业务代码项目 | 有应用代码和运行入口 | lint / typecheck / test / 依赖 / 安全 |
| 工具项目 | 含 `tools/`、API、脚本或 Web 工具 | 启动、API、配置、YAML、错误处理 |
| 规范文档项目 | 主要为 docs / rules | YAML 模板、文档链接、规则引用 |
| 混合项目 | 同时包含工具与规范文档 | 同时执行工具和规范文档适用项 |

### 2.2 审计输入

AI 执行审计前必须读取：

| 输入 | 用途 |
|---|---|
| `README.md` | 项目定位、技术栈、项目关系 |
| `product.yaml` | 产品形态、项目列表、docs/pm-kit-base 路径 |
| 工作区 `.trae/rules/workspace_rules.md` | L0 工作区硬约束 |
| `.trae/rules/project_rules.md` | 项目硬约束和必读索引 |
| `pm-kit-base/changes/` | Change 记录 |
| `pm-kit-base/pitfalls/` | 踩坑记录 |
| `pm-kit-base/memos/` | Memo 索引和待分流信息 |
| 项目 `docs/04-开发实践规范.md` | 开发技术审计依据 |
| 项目 `docs/05-交付实践规范.md` | 发布交付审计依据 |
| specs-v2/11-AI协作规范 | Rule / Skill / Agent / Human Gate 语义 |
| specs-v2/10-事实源规范 | 文档编号、事实源、Change 记录和归档规则 |
| specs-v2/14-管理对象规范 | 管理对象、状态和关闭条件 |
| specs-v2/12-程序辅助规范 | 工具边界和受控编辑范围 |
| specs-v2/13-工具展示规范 | 工具展示边界 |
| `docs/98-技术审计.md` | 历史技术审计快照 |
| `docs/99-规范审计.md` | 历史规范审计快照 |
| `pm-kit-base/` | 任务、任务集和备忘结构 |

### 2.3 规范审计

| 审计对象 | 审计依据 | 结果归属 |
|---|---|---|
| 规范及相关文档的合规性 | specs 正文 | 写入 99-规范审计.md |

### 2.4 技术审计

| 审计对象 | 审计依据 | 结果归属 |
|---|---|---|
| 项目代码、依赖、测试、安全、发布交付实践的合规性 | 项目 04-开发实践规范 + 05-交付实践规范 | 写入 98-技术审计.md |

技术审计读取项目 04/05：04 为空时跳过开发实践审计；05 为空时跳过交付实践审计；无 04/05 时先由 AI 分析项目代码和发布形态生成，经 Human Gate 确认后作为技术审计依据。

### 2.5 全量审计

| 审计对象 | 审计依据 | 结果归属 |
|---|---|---|
| 先规范审计，再技术审计 | specs + 04 + 05 | 写入 99 + 98 |

全量审计执行顺序：先规范审计，再技术审计。

## 三、产出与分流

### 3.1 审计发现分流

#### 3.1.1 分流规则

| 分类 | 条件 | 归宿 |
|---|---|---|
| 任务 | 目标明确、动作明确、归属明确、验证方式明确 | `pm-kit-base/tasks/` |
| 待决策任务 | 可执行但需要人类判断 | `pm-kit-base/tasks/`，状态 Decision Needed |
| 备忘 | 不可任务化或归属不明 | `pm-kit-base/memos/` |

审计发现生成 Task 必须同时满足四个条件；不满足时进入 Memo。

#### 3.1.2 回链要求

审计发现完成分类后，必须记录落盘对象 ID：

| 分类 | 必填回链字段 |
|---|---|
| 任务 | linked_task_id |
| 待决策任务 | linked_task_id |
| 备忘 | linked_memo_id |

审计报告不得只记录分类结果而缺少回链 ID。若发现复用已有对象，记录已有对象 ID；若新建对象，记录新建对象 ID。缺少回链 ID 的发现视为未完成分流。

#### 3.1.3 衍生建议

审计过程中衍生的改进建议（非正式审计发现），按审计发现同等规则处理：可明确任务化的创建 Task，不可任务化的创建 Memo。快照中只记录对应 linked_task_id / linked_memo_id，不记录建议正文。

### 3.2 快照规则

- `docs/98-技术审计.md`：技术审计快照
- `docs/99-规范审计.md`：规范审计快照
- 只追加新轮次，不修改旧轮次
- 记录：审计时间、范围、摘要、发现 ID、分类、linked_task_id / linked_memo_id、Human Gate 项
- 分类为 Task / 待决策 Task / Memo 的发现，缺少对应 linked_task_id / linked_memo_id 时，本轮审计不得视为闭环完成
- 不得记录：当前任务状态、负责人、修复进度、后续计划

### 3.3 报告格式

#### 3.3.1 规范审计报告

```text
规范审计完成：
- 产品：{product-name}（{项目数} 个项目）
- 产品类型：{单项目产品 / 多项目产品}
- 当前项目角色：{单项目产品 / 治理项目 / 子项目}
- 通过：{数}
- 缺失（已自动创建）：{数}
- 不合规：{数}
- 不适用：{数}
- 审计发现：{数}（任务 {数} / 待决策 {数} / 备忘 {数}）
- 发现回链：{全部已记录 / 未完成，列出缺少 linked_task_id 或 linked_memo_id 的发现 ID}
- 已追加 99 快照：是 / 否
- Human Gate：{数和简要说明}
```

#### 3.3.2 技术审计报告

```text
技术审计完成：
- 项目：{project-name}
- 项目类型：{业务代码 / 工具 / 规范文档 / 混合项目}
- 通过：{数}
- 不适用：{数}
- 不合规：{数}
- 审计发现：{数}（任务 {数} / 待决策 {数} / 备忘 {数}）
- 发现回链：{全部已记录 / 未完成，列出缺少 linked_task_id 或 linked_memo_id 的发现 ID}
- 已追加 98 快照：是 / 否
- 04 状态：{存在并完整 / 存在但为空 / 不存在已生成}
```

## 四、Human Gate

以下情况必须暂停并等待用户确认：

1. 修改 L0 / L1 / L2 规则；
2. 创建、修改或删除 Skill；
3. 创建、启用或修改 Agent 调度边界；
4. 新增依赖或工具框架；
5. 修改 `product.yaml` 字段；
6. 覆盖已有事实源；
7. 跨项目影响；
8. 修改审计规范本身；
9. 生成 04-开发实践规范或 05-交付实践规范（首次、技术栈变更或发布流程变更）。

被 git 管理的文件删除不需要 Human Gate 确认，因为 git 可回滚。本条不适用于 Skill、Agent 调度边界、规则文件和 product.yaml 的删除，这些仍需 Human Gate。

## 五、检查要求

1. **快照不可变**：审计报告写入后不再因业务变更而修改，新增审计轮次追加新章节。
2. **发现必须先分类**：审计发现不得直接创建为 TODO，必须先分类为 Task / 待决策 Task / Memo。
3. **禁止推断**：不得仅凭惯例推断技术栈、测试命令、依赖关系、发布流程等，必须从项目 04/05 或项目文件中读取。
4. **审计不自动修复**：只补齐允许自动创建的缺失结构，不自动修复不合规内容。
5. **每次审计后必须产生 Change 记录**（写入 `pm-kit-base/changes/`）。
6. **新建 docs 文件后必须更新**该项目的 `project_rules.md` 必读文档索引。
7. **审计发现不得直接转为 TODO 或批量创建任务**；必须先执行自动分类。
8. **98/99 快照只追加不修改**。
9. **Human Gate 列出的事项必须在执行前确认**；用户已在本轮选择具体规则或 Skill 方案时，视为确认，必须直接创建或修改正式资产。
10. **审计发现必须按 21-Task 和 22-Memo 定义的状态机和对象格式创建** Task 或 Memo。
11. **不得在快照中记录当前任务状态、负责人或修复进度**。
12. **全量审计执行顺序**：先规范审计，再技术审计。
13. **审计衍生建议必须按可任务化→Task、不可任务化→Memo 分流**，不得以纯文本形式留在快照中。
