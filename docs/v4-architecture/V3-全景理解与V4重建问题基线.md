# V3 全景理解与 V4 重建问题基线

> 记录性质：V4 架构重建的调查与决策输入，不是规则源，不授权产品行为。
> 记录状态：当前认知基线；需要通过后续 V3 全量处置矩阵逐项验证和修订。
> 记录日期：2026-07-11

## 1. 记录目的

本记录回答 V4 架构重建开始前必须明确的三个问题：

1. LDVH V4 实际要建设什么；
2. 为什么不能继续在 V3 中原地演进；
3. V4 应重点解决哪些 V3 问题。

本记录用于防止后续工作直接从单份旧规范、编号、YAML 字段或局部实现出发，导致先设计 V4 成员、再倒推系统目的。它不替代 `specs/` 中的正式规则，也不表示其中提出的目标成员、字段或实现方案已经得到接受。

## 2. 当前方法纠正

此前先设计 V4 `01-规范体系基础规范.md`，再补充 V3 全景理解，工作顺序错误。正确顺序应为：

```text
理解 V3 全貌与实际运行状态
→ 建立 V3 问题和资产处置矩阵
→ 推导 V4 独立规范职责、规范依据、结构归属与建设顺序
→ 确定规范成员与编号
→ 设计具体规范、Schema、Code 和 tests
```

因此，当时未提交的 V4 01 只能视为过早的设计试验，以及帮助暴露问题的草案，不能作为已经确定的架构基础。在完成 V3 全量处置矩阵以及 V4 职责和关系分析之前，不继续细化或提交该草案。

## 3. LDVH V4 实际要建设什么

V4 不是 V3 规范的重新编号、重新排版或元数据升级，而是从已接受的根规范 00 重新建立一套真正面向 AI Agent 的 LDVH 架构。

已确认的总体关系为：

```text
规范模型、事实模型、行动模板、Code → Helper → AI
Code → 实现 Helper CLI
Web → Human
```

各部分由 00 确定的职责是：

1. **规范模型**：定义正式 Specs 及其授权附件的身份、结构、关系和规则表达方式。
2. **事实模型**：保存可追踪、可消费的状态、证据和经验。
3. **行动模板**：组织重复性行动的结构、输入、输出与验证，但不擅自创造领域规则。
4. **Code**：实现确定性的解析、目标解析、校验和受控操作。
5. **Helper CLI**：作为面向 AI 的统一跨要素服务入口，组织并消费适用的规范、事实、行动模板和 Code 能力。
6. **Web**：独立读取相应 Source of Truth 并服务 Human，不经过 Helper CLI；本轮保持冻结。

Helper 是基础服务形式和架构入口，不是第六类构成要素，也不能被缩减为 Code 的一个普通能力。Code 负责实现 Helper，但不能因此反向取代 Helper 的架构角色。

V4 还必须保持以下行为边界：

1. 命中来源规范声明的适用范围时，规则要求必须执行。
2. 未命中具体规则时，不限制 AI 的普通求解路径。
3. Human Gate 或 Stop Conditions 命中时，只暂停、分流或交还受影响的最小范围。
4. 未覆盖、未实现、未接入或未验证的范围，不得宣称为已保障、`available`、`integrated` 或 `completed`。
5. V1–V8 是行动价值标尺，不应被机械化为每次行动都必须执行的统一仪式。

## 4. 为什么从 V3 转向 V4

V3 的问题不是若干规范写得不够好，而是规范、Code、tests、环境接入和 V2→V3 迁移历史已经紧密耦合。在 V3 原地改变根本责任，会同时受到旧路径、旧字段、旧 parser、旧 validator、旧 Hook、旧测试和迁移基线的约束。

继续原地修改容易形成以下循环：

```text
架构需要改变
→ 旧实现和测试大面积失败
→ 为维持兼容而保留旧结构或双读
→ 新规范迁就旧实现
→ 架构责任继续重叠
```

V4 的作用是解除这种兼容约束：

1. V3 完整保留为问题样本、历史经验和实现参考。
2. V4 从 00 的上位定义重新推导职责、契约和实现。
3. V4 不继承旧字段、旧附件关系、旧 validator、双读、Git 迁移基线和旧 Hook 契约。
4. 任何 V3 内容只有经过“保留、重写、拆分、合并、迁移、延后或删除”的重新裁决，才能进入 V4。

因此，V4 不是一般意义上的功能升级，而是一次架构解耦和责任重建。

以下数字用于说明 V3 的耦合和重复程度，不直接构成 V4 的设计结论：

1. 归档 V3 有 19 份顶层规范和 18 份附件。
2. 顶层规范约 4,885 行，附件约 916 行。
3. 19 份顶层规范全部包含 `code_consumption`。
4. 18 份包含 `related_specs`，18 份包含 `role_sections`。
5. 17 份重复“保障措施”，17 份重复“验证方法”，18 份包含“待补齐事项”。
6. 根规范已采用 V1–V8，但仍有 12 份成员规范提到 V9，存在下位规范偏离 00 的问题。
7. `archive/v3/code/ldvh_specs.py` 约 7,800 行，将规范解析、事实实例、受治理项目解析、Action Guide、preflight、运行事件、commit gate 和端到端演练等职责集中在一个模块中。

这些事实共同说明：V3 的正式设计范围明显大于实际环境接入范围，同时机器契约与当前文本形状、编号和路径高度耦合。

## 6. V4 需要重点解决的 V3 问题

### 6.1 Helper 尚未成为面向 AI 的统一跨要素服务入口

V3 提供了多个 backend、脚本、Hook 和 Action Guide，但没有形成一个边界清楚、统一稳定的 Helper 服务契约。AI 仍需理解或拼接多个内部入口。

V4 需要建立统一的 Helper 服务模型，使 AI 能通过 Helper 获得适用规则、事实、行动指导、校验和受控操作。Hook、插件和环境适配器只能作为接入 Helper 的适配层，不能反向定义 LDVH 架构。

### 6.2 规范责任混杂且相互重叠

V3 01 同时承载保障、能力匹配、环境入口、运行协议、标准事件、Hook 边界、修复通道、Action Guide、项目路由、回执、证据、诊断、远端 Git 引用、安装和回滚等多类责任，已经成为兜底容器。

V3 07、09、10 也在 Code、环境、校验、目标解析和运行时方面交叉。V4 必须按共同变化、共同消费、共同验证和规则来源重新划分边界清楚且不过度重叠的职责，而不是沿用旧文件边界。

### 6.3 规则适用与效力分散

规则的适用范围、义务、所需能力、验证、Gate/Stop 和能力缺失处理分散在 01、02、04 及多个成员规范中。

V4 需要清楚表达规则适用与履行顺序：

```text
来源规范声明适用范围
→ 当前任务是否命中
→ 命中后产生哪些义务
→ 需要哪些能力与验证
→ 能力不足时暂停哪一部分
```

这一设计必须坚持“命中才约束”，不能扩大成所有 AI 行动都必须通过的全局流程。

### 6.4 来源角色重复且边界模糊

规则源、事实源、聊天与工具输出、证据、回执、诊断、缓存、Web 视图和派生结果的关系在多份规范中反复出现，且存在相互侵入。

V4 需要统一说明不同信息的来源角色与 Git 可追踪边界，同时保持规则源与事实源的明确区分。由 Code 生成的导航、索引或汇总不得因为便于使用而获得新的权威。

### 6.5 共同结构过重，增加 AI 和维护负担

`related_specs`、`role_sections`、“保障措施”、“验证方法”、“待补齐事项”以及多处重复的 Gate/Stop 文字构成了较高的全局维护成本。

V4 应采用最小共同结构：每份来源规范只表达其责任特有的规则和增量；能够从正式来源确定性生成的反向关系、导航和索引，优先由 Code 派生。低频的版本更新、内部维护和一次性迁移不应预先制度化为所有 AI 都需承担的日常规则。

### 6.6 机器契约硬编码于正文、编号和路径

V3 Code 硬编码了编号路径、规范名称、成员集合、字段、章节和来源角色映射；测试还直接依赖具体文字。这使语义无关的重排、改写或拆分也会造成大面积失败。

V4 应采用 Schema 驱动、稳定 ID，并将解析、关系解析和校验职责分配给边界清楚的 Code 模块。Code 应消费明确的机器契约，而不是把自然语言正文、编号或路径本身当作稳定接口。

YAML 仍然可以作为适合 Human、AI 和 Code 共同阅读的机器载体。需要解决的不是“是否使用 YAML”，而是只保留有明确消费方和验证价值的字段，并用代码围栏保证 Human 可读。

### 6.7 迁移和兼容逻辑污染长期架构

V3 04 等正式规范包含 V2→V3 的 legacy/target 结构、迁移基线、旧路径、硬切换和兼容校验。这些是特定阶段的迁移工程，不是 LDVH 长期领域规则。

V4 不继承双读、旧 validator 和迁移基线。确有必要的一次性迁移步骤，应位于工作记录、执行计划或临时行动模板，而不是成为长期核心规范。

### 6.8 设计、实现、接入和验证状态混淆

V3 规范描述了广泛的保障、运行时、Hook 和环境能力，但真实环境接入仍然有限。必须明确区分：

```text
规范已设计
≠ Code 已实现
≠ 环境已接入
≠ 端到端已验证
≠ 当前可用
```

V4 的能力声明和完成声明必须根据当次证据成立，不能由旧文件、旧 Code 或静态存在反向证明。

### 6.9 对 AI 普通求解路径干预过多

V3 曾出现固定读取 00/01/02、全局价值门、过宽 Human Gate 和强 Hook 假设等倾向。这些做法可能把一种环境或协作模式固化为所有任务的前置负担。

V4 应由 Helper 按任务提供相关规则；没有来源规则命中时，AI 保持普通求解自主性。

### 6.10 事实模型可能混入短期编排状态

WorkCase、运行阶段、环境事件、回执和诊断中，部分是需要跨会话保存的稳定事实，部分只是一次执行的过程状态。

V4 应只将确有跨任务、跨会话价值的稳定状态纳入事实源。临时诊断、执行回执和编排状态默认只是各自类型的当次信息，除非能证明其具有持续事实价值。

### 6.11 行动模板的权威边界不一致

V3 一方面声明行动模板不是规则来源，另一方面又将正式规范及授权附件共同定义为规则来源，导致模板的效力边界不够一致。

V4 应明确：行动模板可以承载可复用的行动结构，但不能仅因属于五类构成要素之一而取得规则权威。任何必须执行的要求都必须回溯到当前有效的来源规范；行动模板与来源规范未来如何形成正式承载关系，应由后续规范明确，不能由本记录预设。

### 6.12 根规范与成员规范发生语义漂移

00 已采用 V1–V8，而多份成员规范仍引用 V9，说明根规范没有形成可靠的一致性约束。

V4 00 必须提供 LDVH 的上位定义。下位规范、事实模型、行动模板、Code、Helper 和 Web 都不得反向解释、扩大、弱化或覆盖 00。

### 6.13 Web 的边界需要以后单独校准

V3 对 Web 与 Code 的隔离可能存在过度纠正：独立读取正式来源不必然意味着不能复用保持语义一致的解析能力。但 Web 不在本轮重构范围内，当前只记录问题，不修改、不重构，也不提前决定其 V4 方案。

## 7. V4 明确不追求的方向

V4 不应：

1. 把 V3 04 改名或重编号为 V4 01；
2. 为所有 V3 字段、附件关系、validator 和 Hook 提供兼容；
3. 通过增加更多元治理、生命周期和迁移规则来证明架构成熟；
4. 强制所有 AI 行动经过 Hook 或统一 Gate；
5. 把 Helper 作为第六类构成要素，或把它缩减成 Code 的普通命令；
6. 把旧 Code 存在、旧测试通过或静态文件存在当作 V4 能力证据；
7. 在本轮修改或重构 Web；
8. 为了形式上的行业先进性引入不能降低 AI 负担、没有明确消费方或无法映射到 V1–V8 的新概念。

## 8. 后续裁决原则

新设计只有同时满足以下条件，才应相对 V3 发生变化：

1. 解决了已确认的 V3 问题；
2. 更符合 00、Helper 面向 AI 的统一跨要素服务入口和 AI 第一服务对象；
3. 能说明对 V1–V8 的净价值；
4. 责任、消费方和验证方式清楚；
5. 不增加与使用频率和风险不相称的长期规范负担；
6. 与 V3 存在语义差异时，明确告知 Human，并在需要时取得决定。

如果无法证明新设计更加优秀、先进且契合 LDVH 目标，应保留 V3 的合理语义，而不是擅自改变。

## 9. 下一阶段工作

下一阶段应建立 V3 全量处置矩阵，覆盖：

1. 19 份顶层规范；
2. 18 份附件；
3. 事实成员规范；
4. 行动模板；
5. Code 的主要能力；
6. tests 覆盖与真实环境接入状态。

每个对象至少记录：

| 项目 | 说明 |
| --- | --- |
| V3 原有目的 | 它原本要解决什么问题 |
| 当前实际责任 | 文档、Code 和 tests 实际承担了什么 |
| 已知缺陷 | 重叠、耦合、缺失、过度治理或状态错配 |
| V4 处置 | 保留、重写、拆分、合并、移入 Code、移入事实模型、移入行动模板、降为工作记录、延后或删除 |

| 语义差异 | 相比 V3 是否改变，改变的原因和影响 |
| 验证依据 | 如何证明处置结果满足目标 |

处置矩阵经复核后，再推导 V4 的职责划分与完整性检查结果，并分别明确直接规范依据、结构归属、建设顺序和实现消费关系。规范成员数量和编号是职责分析的结果，不应预先固定。只有到此之后，才重新设计 V4 01。
