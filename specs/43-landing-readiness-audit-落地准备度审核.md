## 1. 行动定位与适用场景

落地准备度审核是 LDVH 对 specs 正式规范中已声明的规范落地要求进行就绪检查的工作流程。它回答：一条规范落地要求是否已经具备足够的保障机制、能力资产、环境入口、确定性检查、Human Gate、生命周期触发或人工降级路径，使 AI 能判断该要求当前是 ready、partial、blocked、needs_human_gate 还是 not_applicable。

本流程不重新审核规范正文写得是否合理，该事项由 42 承接；不审核工作模型设计质量，该事项由 41 承接；不审核工作流程设计质量，该事项由 40 承接；不执行真实部署、安装或环境入口写入，该事项应回到 04.03 和具体执行任务；不把 Code 输出、Web 页面状态、Skill 输出、Agent 输出或当前对话结论当作落地已经完成的事实源证据。

以下场景应进入本流程：

1. 用户要求检查某个规范、某组规范或全部 specs 的落地要求当前是否准备好；
2. 新增、修改或审核 specs 正式规范后，需要判断落地要求是否已有对应保障；
3. 04.01、04.02、04.03、07、08、10、Rules、Skill、Agent、Hook、CI 或环境适配发生变化，需要回溯检查受影响落地要求；
4. Code 派生落地要求表、landing-report、文档结构检查或人工审查发现落地要求缺口；
5. AI 执行时发现规范要求已经写入 specs，但找不到入口、流程、Code、Human Gate、环境适配或降级方式；
6. 准备把某个 candidate 工作流程、Skill、Agent、Hook、Code 或 Web 能力升级为可被落地要求消费的保障机制前；
7. 需要把落地缺口分流为 WorkPlan、Memo、ADR、Pitfall、规范修订、Code/Web 需求或环境适配待补齐事项时。

以下场景不应由本流程直接承接：

1. 只检查规范落地要求表的字段是否齐全；该事项优先由 Code 和 42 承接；
2. 只判断某份规范正文是否符合文档治理、引用纪律或价值标准；该事项由 42 承接；
3. 直接写入、覆盖、删除或部署用户环境入口；该事项由 04.03 和 Human Gate 承接；
4. 直接实现 Code、Web、Skill、Agent 或 Hook；本流程只识别缺口和分流，不替代实现任务；
5. 把一次现场检查结果登记为长期环境状态；该行为违反 09 和 04 系列事实源边界；
6. 关闭长期降级、绕过 Human Gate 或将人工降级写成完整支持。

## 2. 准入条件

进入本流程前，应满足以下条件之一：

1. 已存在至少一条规范落地要求；
2. 已有明确目标规范、目标编号区段、目标落地要求类型或目标能力资产；
3. 已有 Code 诊断、人工审查、入口漂移、能力缺口、环境缺口、验证缺口或生命周期触发缺口线索；
4. 已有 Rules、Skill、Agent、Hook、Code、Web、CI 或环境入口准备作为保障机制被落地要求消费；
5. Human 要求判断 LDVH 当前是否具备进入真实落地、管辖项目接入、环境部署或 dogfood 的准备条件。

不满足以上条件时，不应为了补齐流程编号或制造完整矩阵而触发本流程。若只是抽象讨论某类能力未来可能存在，应记录为候选事项、Memo 或 WorkPlan，而不是声称完成落地准备度审核。

## 3. 事实源边界

本流程的权威规则来自以下事实源：

| 内容 | 权威位置 |
|---|---|
| 规范落地要求类型、声明字段和字段边界 | `specs/04.01-规范落地声明规范.md` |
| LDVH 能力资产、能力保障默认映射和缺口分流 | `specs/04.02-LDVH能力资产与落地保障规范.md` |
| 环境入口、环境适配、部署检查、适配降级和 Human Gate | `specs/04.03-环境入口适配与部署规范.md` |
| 工作流程通用规则、Context、Scenario、Gate、回写和证据 | `specs/06-工作流程基础规范.md` |
| 事实源、过程输出、工具输出和回写边界 | `specs/09-事实源边界与承载规范.md` |
| 测试治理、验证声明、等价验证和残留风险表达 | `specs/10-测试基础规范.md` |
| 被审核落地要求正文 | 对应 specs 正式规范的规范落地要求章节 |

Code 输出、landing-report、命令输出、Web 视图、Skill 输出、Agent 输出、聊天分析、docs/studies 和 docs/sources 只能作为导航、诊断、候选建议或过程输出。审核结论形成稳定事实时，必须按事实类型分流到目标规范、WorkPlan、Memo、ADR、Pitfall、docs 报告、Code/Web 实现文档或其他权威 Git 文件事实源。

本流程不得创建“落地状态”“已准备状态”“环境已支持状态”这类长期状态事实源。准备度结论是一次审核过程输出；若需要长期追溯，应记录为工作对象、决策、风险、任务或规范修订，而不是保存为独立状态清单。

## 4. Context 要求

执行本流程前，AI 应按最小可行动原则准备以下 Context：

1. `../rules/LDVH-MAINTAINER-ENTRY.md` 和 `../rules/LDVH-WORKSPACE-ENTRY.md` 中与规范落地、环境适配、Code 查询入口、STOP 点和事实源边界相关的段落；
2. `specs/04.01-规范落地声明规范.md` 中落地要求类型、声明字段、类型选择规则、后续消费关系和检查要求；
3. `specs/04.02-LDVH能力资产与落地保障规范.md` 中要求到能力资产的默认映射、能力资产边界、能力提供原则和缺口分流；
4. `specs/04.03-环境入口适配与部署规范.md` 中环境入口、适配状态、部署前检查、部署后适配检查、声明完成前检查和 Human Gate；
5. `specs/09-事实源边界与承载规范.md` 中最终事实源、单一事实源、工具输出回写和过程输出回写边界；
6. `specs/10-测试基础规范.md` 中验证方式、验证声明、失败处理和残留风险表达；
7. 目标规范或目标范围内的规范落地要求章节；
8. 必要时运行 `python3 code/specs_validate.py landing specs`、`python3 code/specs_validate.py landing-report`、`python3 code/specs_validate.py index` 或 `python3 code/specs_validate.py all` 获取落地要求清单、结构诊断和成员状态导航；
9. 必要时读取相关 Rules、Skill、Agent、Hook、Code、Web、CI 或环境适配资产的入口摘要，但不得用其输出替代 specs 权威原文。

若无法定位目标落地要求、目标规范、能力资产、环境入口或必要诊断来源，应暂停并说明缺口。若目标保障机制对应 candidate、planned、reserved、removed 或未创建资产，只能按候选或缺口处理，不得判定为 ready。

## 5. Scenario 识别

AI 遇到以下信号时，应识别为落地准备度审核场景：

1. 用户要求检查规范落地要求是否已经准备好、能否执行、是否缺能力或是否可以进入落地；
2. 用户要求按 04.01、04.02 或 04.03 逐条核验落地要求；
3. 用户提到入口可见、流程复用、子 Agent 思考、确定性执行、Human 交互、生命周期触发或上位约束承接是否已经具备保障；
4. Code 报告 landing、landing-report、能力资产、入口适配、引用、字段或结构诊断；
5. 某条落地要求的保障机制写了 Rules、Skill、Agent、Hook、Code、Web、CI 或 Human Gate，但无法定位对应资产、入口、检查方式或降级路径；
6. 某条落地要求需要声明 ready、partial、blocked、needs_human_gate 或 not_applicable；
7. 审核、接入、部署、dogfood 或管辖项目治理前，需要先判断 LDVH 当前能力组合是否足够支撑下一步执行。

多个场景同时命中时，应先判断是否存在更具体的 active 工作流程。若目标是检查“落地要求当前是否具备保障和检查路径”，或没有更具体 active 流程承接该准备度判断，则进入本流程。

## 6. 执行流程

落地准备度审核按以下步骤执行：

1. **确认审核范围**：确认目标是单条落地要求、单个规范、某个编号区段、某类落地要求、某类能力资产，还是全部 specs；若目标范围过大，应先通过 Code 生成清单，再分批审核；
2. **收集落地要求**：读取目标规范的规范落地要求章节，或运行 `python3 code/specs_validate.py landing specs`、`python3 code/specs_validate.py landing-report` 获取落地要求清单；Code 输出只作导航，关键项仍应回读目标规范原文；
3. **确认要求类型**：按 04.01 检查每条落地要求的类型是否属于上位约束承接要求、入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求或生命周期触发要求；类型缺失或混乱时，分流到 42 或目标规范修订；
4. **确认保障机制声明**：检查要求内容、保障机制、同步类型和触发条件是否完整；若只是写“符合规范”“按需处理”或把具体环境实体写成要求本身，应分流到 42 或目标规范修订；
5. **按类型核验准备度**：逐条使用 §6.1 的矩阵判断保障机制是否存在、是否可定位、是否可消费、是否有检查方式、是否有降级分流；
6. **核验能力资产**：若保障机制涉及 Rules、Skill、Agent、Hook、Code、Web、CI、Command 或 Human Gate，应检查其权威定义、入口摘要或实现位置是否存在；candidate、planned、未创建或仅口头存在的能力不得判定为 ready；
7. **核验环境适配**：若要求需要进入具体环境入口，应按 04.03 检查环境入口、接入方式、适配检查、成功条件、失败处理和禁止声明是否明确；未现场检查的环境能力不得写成完整支持；
8. **核验确定性验证**：若要求涉及 Code、测试、CI、命令或可机械检查行为，应确认是否存在可执行命令、测试、等价验证或明确 Code 缺口；未运行或无法运行时按 10 记录等价验证和残留风险；
9. **核验 Human Gate**：若要求涉及授权、确认、验收、高影响写入、长期配置、删除、重命名、完整支持声明或长期降级，应确认 Human Gate 条件、影响范围、确认对象和回写位置；缺失时判定为 needs_human_gate 或 blocked；
10. **判定准备度**：对每条落地要求给出 `ready / partial / blocked / needs_human_gate / not_applicable` 之一，并说明依据、证据、缺口和下一步分流；
11. **识别系统性缺口**：聚合同类缺口，区分能力资产缺口、环境入口接入缺口、个人环境约束、适配检查失败、Code 缺口、Web 缺口、Skill/Agent/Hook 缺口、Human Gate 缺口、规范声明缺口；
12. **形成审核结论**：按 §10 输出过程结论，说明审核对象、读取依据、运行命令、准备度矩阵、触发 Gate、回写建议和残留风险；
13. **分流后续行动**：规范声明错误回写目标规范；能力或实现缺口进入 WorkPlan、Memo、ADR 或 Code/Web 需求；可复用误判进入 Pitfall；研究或报告进入 docs；高影响决策进入 ADR 或 Human Gate；
14. **复跑验证**：若本流程导致规范、Code、入口资产或能力资产变更，应重新运行相关 specs 校验、Code 检查或等价验证；未验证时不得声明完整 ready。

### 6.1 七类落地要求准备度检查矩阵

| 落地要求类型 | ready 的最低条件 | 常见缺口 |
|---|---|---|
| 上位约束承接要求 | 上位依据、相关规范或消费方能定位权威规则；存在引用检查、人工检查或 Code 检查；未形成反向补全或第二事实源 | 只有口头承接；引用方向不清；消费方未声明；Code 只能导航不能检查 |
| 入口可见要求 | AI 或 Human 有稳定入口能定位目标规范或入口摘要；入口只做薄引用或导航；有入口漂移检查或人工降级 | 入口复制正文；入口不存在；入口指向旧路径；恢复上下文后无法重读 |
| 流程复用要求 | 存在 active 工作流程、可复用 SOP、Skill 或人工步骤；输入、输出、失败处理和交还方式明确 | 只有候选流程；Skill 新增稳定规则；步骤依赖聊天记忆 |
| 子 Agent 思考要求 | 存在 Agent 适用边界、输入输出、主控回收和 Human Gate 规则，或有人工多视角降级 | Agent 输出直接生效；没有主控复核；无争议升级路径 |
| 确定性执行要求 | 存在 Code、测试、CI、命令或等价验证；能说明输入、输出、失败条件和残留风险 | 只有“应检查”无实现；命令不可运行；测试失败；输出不能回指事实源 |
| Human 交互要求 | Human Gate 条件、影响范围、确认事项、证据和回写位置明确 | 高影响动作无暂停；确认只存在聊天；授权范围不清 |
| 生命周期触发要求 | 存在 Hook、CI、命令、Skill 提醒、入口 STOP 点或人工降级检查；触发条件和失败处理明确 | 把提醒写成自动触发；无复查入口；Hook 候选被写成已支持 |

---
## 7. Gate 触发条件

出现以下情况时，AI 必须暂停继续宣称 ready，并按影响范围触发 Human Gate、降级检查或后续分流：

1. 准备度结论会影响某项规范、能力资产、环境入口、Code、Web、Rules、Skill、Agent、Hook 或 CI 的长期行为边界；
2. 需要声明某类环境、入口、Hook、Skill、Agent、Code 或 Web 已完整支持某项落地要求；
3. 需要接受长期降级、关闭缺口、跳过验证、跳过 Code 诊断或绕过 Human Gate；
4. 需要写入、覆盖、删除或长期修改用户环境入口、项目入口、配置、自动触发或危险权限；
5. 准备度证据来自 Code 输出、Web 状态、Agent 输出、Skill 输出、聊天判断或环境观察，但尚未回写权威事实源；
6. 发现正式规范、能力资产、环境适配、Code 诊断或目标落地要求之间存在冲突；
7. 准备度审核需要新增、删除、升级、降级或改变落地要求类型、保障机制类型、能力资产边界或环境适配边界；
8. 审核范围过大，无法在当前上下文中可靠回读关键规范原文和证据来源。

Gate 触发时，AI 应说明触发原因、影响范围、可选处理方式、推荐分流和需要 Human 确认的具体事项。Human 确认形成稳定事实时，应按 06 的 Human Gate 最小字段记录时间、决策、范围和约束。

## 8. Skill 和 Agent 调度

本流程默认由主控 AI 执行。只有当准备度审核重复执行、范围较大、争议明显或需要独立上下文时，才考虑 Skill 或 Agent 辅助。

Skill 适合承接：

1. 固定准备度检查清单；
2. 落地要求清单整理；
3. 标准化输出格式；
4. 常见缺口分类；
5. 交还主控的后续分流建议。

Agent 适合承接：

1. 跨规范落地要求之间的语义冲突；
2. 能力资产边界是否足以保障某类要求；
3. 环境适配降级是否会削弱正式规范；
4. 高影响 ready 结论的独立复核；
5. 长期降级、缺口关闭或完整支持声明的争议分析。

Skill 和 Agent 输出均为过程输出，必须交还主控。Skill 不得自行调度 Agent，Agent 输出不得直接生效，不得绕过 Human Gate、Code 诊断、事实源回写或主控判断。

## 9. Code 与命令入口协作适配

本流程优先使用 Code 获取落地要求清单、结构诊断和导航信息。Code 适合承接：

1. specs 规范落地要求表解析；
2. 落地要求类型、字段完整性和来源行号聚合；
3. landing-report 或同类落地要求清单生成；
4. 规范、能力资产、成员自描述、Code、Web、Rules、Skill、Agent、Hook 路径引用检查；
5. 可机械判断的 ready 证据检查；
6. 缺口分类报告和后续分流建议生成。

常用命令包括：

```bash
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py landing-report
python3 code/specs_validate.py index
python3 code/specs_validate.py all
```

Code 输出只作为导航、聚合和诊断结果。Code 不判断规范是否真的已经被环境完整支持，不生成 Human 授权，不替代 AI 对语义、上下文、能力边界和风险的综合判断。Code 不可用、诊断不完整或输出无法回指事实源时，应退回人工检查并记录残留风险。

## 10. 事实源回写与证据留存

本流程执行后的过程输出应至少说明：

1. 审核对象和范围；
2. 读取的权威依据；
3. 运行的 Code 命令或人工降级检查；
4. 落地要求清单和来源位置；
5. 每条落地要求的准备度结论；
6. 发现的缺口类型、证据和影响范围；
7. 是否触发 Human Gate；
8. 是否修改目标规范、能力资产、Code、Web 或环境适配；
9. 后续分流位置和残留风险。

准备度结论分为：

| 结论 | 含义 |
|---|---|
| `ready` | 已有可定位保障机制、检查方式和证据边界，未发现阻塞缺口 |
| `partial` | 可部分使用，但缺少完整检查、实现、入口、触发或降级路径 |
| `blocked` | 缺少关键保障机制或存在冲突，不得宣称已准备好 |
| `needs_human_gate` | 需要 Human 确认后才能继续判定或执行 |
| `not_applicable` | 当前落地要求对本次审核对象不适用，且已说明原因 |

稳定事实回写规则如下：

1. 落地要求声明错误或规范正文缺陷，回写对应 specs 主文件；
2. 能力资产缺口、Code 缺口、Web 缺口、环境适配缺口或后续实现事项，回写 WorkPlan 或 Memo；
3. 长期决策、能力边界选择、接受降级或是否升级 active 的判断，回写 ADR；
4. 可复用误判、反复失败或风险经验，回写 Pitfall；
5. 审核形成报告、研究或迁移说明，回写 docs；
6. 修改事实源时，按 09.01 的 Git、commit message 和 Refs 追溯规则处理。

凡回写为 WorkPlan 的后续行动，必须按 `specs/21-WorkPlan-工作计划.md` 和 `specs/05.01-工作字段内容格式规范.md` 填写 `success_criteria`、`orchestration.execution_items`、`verification_evidence` 与 `closure_evidence` 等字段；流程步骤不得新建 TaskPlan、Task 或 SubTask，执行期拆分只能作为 WorkPlan 内部 `execution_items`。

不得把聊天中的“应该准备好了”“看起来可用”“已有保障机制”当作完成证据。关键结论必须能回指规范、目标文件、Code 命令输出、Human Gate、能力资产路径、环境适配规则或事实源差异。

## 11. 环境适配边界

本流程可以被 Rules 入口提示、Skill SOP、Agent 审查、Code 校验、Web 展示、Hook 提醒、CI 检查或人工降级检查辅助，但这些能力不得替代本流程正文。

环境适配边界如下：

1. Rules 入口只提示何时读取本流程和相关规范，不复制流程全文；
2. Skill 可以封装准备度检查清单，但不新增稳定规则；
3. Agent 可以提供独立语义审查和风险判断，但不直接生效；
4. Code 可以生成清单和诊断，但不替代 AI 语义判断和 Human Gate；
5. Web 可以展示准备度矩阵、缺口和待确认事项，但不维护第二事实源；
6. Hook 或 CI 可以提醒或阻断高风险变更，但触发不等于 ready；
7. 环境能力缺失时，应降级为人工检查并记录残留风险；
8. 任何环境入口现场状态都不得保存为长期“已准备状态”。

## 12. 行动特有可测试性锚点

本流程的关键行为应能通过正例、反例、Gate 场景、回写场景和命令验证进行检查。

正向场景：

1. 目标规范存在规范落地要求表；
2. 每条落地要求能定位来源规范和来源行；
3. 每条落地要求能按 04.01 识别类型；
4. 每条落地要求能按 04.02 识别默认保障机制或缺口；
5. 涉及环境入口时回到 04.03 判断适配检查和禁止声明；
6. 涉及验证时按 10 说明自动化测试、命令校验、等价验证或残留风险；
7. 审核结论能回指事实源、命令输出或 Human Gate。

负向场景：

1. 只因落地要求表字段完整就声明 ready；
2. 把 candidate Skill、Agent、Hook、工作流程或未创建 Code 当成 ready 保障；
3. 把一次现场环境观察写成长期环境支持结论；
4. 把人工降级写成原生完整支持；
5. 用聊天判断、Web 状态或工具输出替代事实源证据；
6. 发现缺口后通过删除落地要求来制造 ready；
7. 未触发 Human Gate 就声明高影响写入、长期配置或完整支持已经准备好。

Gate 场景：

1. 声明某环境完整支持某类落地要求；
2. 接受长期降级或关闭关键缺口；
3. 跳过关键 Code 校验、测试或适配检查；
4. 写入、覆盖或删除用户环境入口；
5. 改变能力资产边界、落地要求类型或事实源归属。

回写场景：

1. 审核发现目标规范落地要求表缺陷，应回写目标规范；
2. 审核发现能力资产缺口，应回写 WorkPlan、Memo 或 ADR；
3. 审核发现长期决策，应回写 ADR；
4. 审核发现可复用误判，应回写 Pitfall；
5. 审核只产生临时建议时，应明确其为过程输出。

修改本流程或目标规范后，至少应运行：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

无法运行自动化校验时，应说明原因、采用的人工检查方式和残留风险，不得声称完整验证。

## 14. 检查要求

落地准备度审核至少包括：

| 检查项 | 标准 |
|---|---|
| 对象归属 | 被审核对象是 specs 正式规范中的规范落地要求、落地要求集合、能力消费请求或准备度争议 |
| 类型识别 | 每条落地要求类型属于 04.01 定义的七类之一 |
| 字段完整 | 要求内容、保障机制、同步类型和触发条件完整 |
| 保障机制 | 保障机制可回指 04.02 的能力资产、能力组合、人工降级或缺口分流 |
| 入口可定位 | 涉及入口可见时，入口摘要或薄引用可定位且不复制正文 |
| 能力存在 | Rules、Skill、Agent、Hook、Code、Web、CI 或 Command 保障存在，或已明确为缺口 |
| 环境适配 | 涉及环境入口时，按 04.03 检查接入方式、适配检查、成功条件、失败处理和禁止声明 |
| 确定性验证 | 涉及 Code、测试、CI 或命令时，有可执行验证、等价验证或明确残留风险 |
| Human Gate | 高影响写入、长期配置、完整支持声明、长期降级或缺口关闭均已触发 Human Gate 或标记 needs_human_gate |
| 事实源边界 | 未把 Code 输出、Web 状态、环境观察、Skill 输出、Agent 输出或聊天结论当作最终事实源 |
| 准备度结论 | 每条要求按 `ready / partial / blocked / needs_human_gate / not_applicable` 分类，且能回指依据 |
| 缺口分流 | 能力资产缺口、环境入口接入缺口、个人环境约束、适配检查失败、Code/Web/Skill/Agent/Hook 缺口已有分流建议 |
| 残留风险 | 未运行命令、未检查环境、未验证能力或只做人工检查时，已说明原因和残留风险 |
