## 1. 行动定位与适用场景

工作流程设计审核是 LDVH 对具体工作流程规范主文件进行质量审查的工作流程。它回答：一个 `specs/40-59` 工作流程主文件是否能被 AI 正确读取、识别、执行、暂停、验证、回写和维护。

本流程只审核工作流程设计质量，不维护工作流程集合清单，不生成派生索引，不替代 Code 派生集合索引，也不替代 `specs/06-工作流程基础规范.md` 和 `specs/03.03-工作流程文档规范.md` 的通用规则。

本流程只审核目标文件作为工作流程主文件的设计质量，不审核目标流程所涉及领域的业务质量、Code 实现质量、Rules 入口质量或 specs 全局价值判断。

以下场景应进入本流程：

1. 新增 `specs/40-59` 具体工作流程主文件前或创建后；
2. 修改已有具体工作流程主文件的 Context、Scenario、Gate、执行流程、回写、证据、能力协作或测试锚点后；
3. 将 planned、candidate、reserved 或 removed 状态的工作流程升级为 active 前；
4. 删除、重命名、移动、重排或降级具体工作流程主文件前；
5. Skill、Agent、Hook、Code、Web、CI 或入口资产准备消费某个具体工作流程前；
6. 执行中反复依赖聊天提醒、临时判断或人工补充来解释某个工作流程时；
7. Code 派生集合索引、骨架检查、引用检查或人工审查发现工作流程相关诊断时。

以下场景不应由本流程直接承接：

1. 只查询当前有哪些工作流程成员；该事项由 Code 派生索引和成员主文件自描述承接；
2. 只机械检查编号、路径、锚点或引用；该事项优先由 Code 承接；
3. 审核 specs 全局逻辑、价值观和 AI 可用性；该事项应由后续 specs 审核流程承接；
4. 审核 Code 实现质量和测试充分性；该事项应由后续 Code 审核流程承接；
5. 审核 Rules 入口资产是否漂移；该事项应由后续 Rules 入口审核流程承接；
6. 管理工作对象实例状态；该事项由 20-39 工作模型规范和后续对象管理流程承接。

## 2. 准入条件

进入本流程前，应满足以下条件之一：

1. 已存在目标工作流程主文件；
2. 已有待创建的工作流程草案、候选标题、编号意向或 Human 明确创建要求；
3. 已有 Code 诊断、入口漂移、引用缺失、骨架缺失、成员自描述缺失或执行失败线索；
4. 已有 Skill、Agent、Hook、Code、Web 或环境入口准备消费该工作流程；
5. 已发现某类行动反复依赖聊天记忆、临时提醒或无事实源判断。

不满足以上条件时，不应为了填补编号或维持顺序而创建或审核工作流程。只存在抽象想法、一次性执行策略或尚未稳定的实践时，应先作为过程输出或候选材料；形成稳定事实后，再按事实类型和对象准入分流到 docs/studies、Memo、Task、TaskPlan、ADR 或其他权威位置。

## 3. 事实源边界

本流程的权威规则来自以下事实源：

| 内容 | 权威位置 |
|---|---|
| LDVH 总体价值标准 | `specs/00-LD-Vibe-Harness理念与纲要.md` |
| 工作流程通用规则 | `specs/06-工作流程基础规范.md` |
| 工作流程文档骨架与成员自描述契约 | `specs/03.03-工作流程文档规范.md` |
| 目录、编号和文件归属 | `specs/01-目录说明.md` |
| 能力资产边界 | `specs/04.02-LDVH能力资产与落地保障规范.md` |
| Code 实现与派生索引边界 | `specs/07-Code确定性执行实现规范.md` |
| 事实源、证据和回写边界 | `specs/09-事实源边界与承载规范.md` |
| 测试治理和验证声明 | `specs/10-测试基础规范.md` |
| 目标工作流程正文 | 对应 `specs/40-59` 成员主文件 |

Code 派生集合索引、命令输出、Skill 输出、Agent 输出、Web 视图、聊天分析和 docs/studies 研究材料只能作为导航、诊断、候选建议或过程输出。审核结论形成稳定事实时，必须按事实类型选择唯一权威位置回写到目标工作流程主文件、相关工作对象、docs 报告、ADR、Memo、Pitfall 或 Git 变更记录，其他位置只保留引用或摘要。

本流程不得恢复手写集合索引，不得把 `docs/studies/` 中的评估记录当作工作流程成员事实源，不得用 Code 派生索引替代成员主文件正文。

## 4. Context 要求

执行本流程前，AI 应按最小可行动原则准备以下 Context：

1. `../rules/LDVH-AI-ENTRY.md` 中与工作流程场景路由、Code 查询入口、STOP 点和维护规则相关的段落；
2. `specs/06-工作流程基础规范.md` 中工作流程定义、标准组成、准入、Context、Scenario、Gate、能力协作、事实源回写、证据留存、40-59 关系和检查要求；
3. `specs/03.03-工作流程文档规范.md` 中适用文件、成员自描述契约、文档骨架、可测试性锚点、环境适配边界和检查要求；
4. `specs/01-目录说明.md` 中 40-59 编号区段、成员自描述与 Code 派生索引边界；
5. `specs/07-Code确定性执行实现规范.md` 中成员集合派生索引边界、Code 输出边界和验证规则；
6. 目标工作流程主文件或候选草案；
7. 必要时读取 `specs/04.02-LDVH能力资产与落地保障规范.md`、`specs/09-事实源边界与承载规范.md` 和 `specs/10-测试基础规范.md`；
8. 必要时运行 `python3 code/specs_validate.py index`、`python3 code/specs_validate.py doc specs`、`python3 code/specs_validate.py refs specs`、`python3 code/specs_validate.py landing specs` 或 `python3 code/specs_validate.py all` 获取导航和诊断。

若目标流程尚未创建，AI 只能审核候选草案和创建方案，不得声称该流程已经是 active 成员。若无法定位目标文件、上位规范或必要诊断来源，应暂停并说明缺口。

## 5. Scenario 识别

AI 遇到以下信号时，应识别为工作流程设计审核场景：

1. 用户要求创建、修改、删除、重排或评价工作流程；
2. 用户提到 40-59、工作流程主文件、Scenario、Context、Gate、回写、证据、测试锚点或流程是否好用；
3. 当前任务涉及 planned、candidate、reserved、removed 与 active 状态切换；
4. Code 派生索引报告工作流程成员自描述、编号、路径、锚点或骨架诊断；
5. 入口资产、Skill、Agent、Hook、Code 或 Web 准备引用某个工作流程；
6. 某个流程看起来像泛化说明、索引、Skill 说明、规范正文拼贴或临时经验汇总；
7. 某个流程执行时无法判断该读什么、何时暂停、如何验证、证据写哪里或失败如何降级。

多个场景同时命中时，应先判断是否存在更具体的 active 工作流程。若没有更具体的 active 工作流程，或目标就是审核工作流程设计质量，则进入本流程。

## 6. 执行流程

工作流程设计审核按以下步骤执行：

1. **确认目标**：确认被审核对象是已存在主文件、候选草案、编号意向、迁移计划还是能力消费请求；
2. **确认权威依据**：读取或定位 06、03.03、01、07 和目标文件，必要时补充 04.02、09、10；
3. **运行确定性诊断**：优先运行或参考 Code 派生索引、文档结构、引用、落地要求和综合校验结果；
4. **审核成员自描述**：检查 `spec_id`、`kind`、`name_en`、`name_zh`、`collection_status`、`canonical_path`、必需锚点和 `code_consumption` 是否完整一致；
5. **审核文件归属**：检查文件名、编号、区段、标题和 canonical path 是否符合 01、03.03 和 06；
6. **审核行动定位**：判断该内容是否确实需要控制 AI 行动，是否不成为工作流程就会导致边界漂移；
7. **审核适用与不适用场景**：检查 Scenario 是否可识别，是否排除了不该进入该流程的场景；
8. **审核 Context**：检查流程是否给出最小可行动上下文，是否能回指 Git 文件事实源，是否避免全文泛读和聊天记忆依赖；
9. **审核 Gate**：检查停止、确认、降级、Human Gate 和条件 Gate 是否明确，是否存在绕过授权或事实源边界的风险；
10. **审核执行步骤**：检查步骤是否可操作、顺序是否合理、是否能被 AI 按步骤执行，而不是只陈述理念；
11. **审核能力协作**：检查 Skill、Agent、Hook、Code、Web、CI 和入口资产的参与是否符合 04.02、07、08 和 06 的主控唯一调度原则；
12. **审核事实源回写与证据**：检查稳定事实、过程输出、验证证据、Human Gate 记录和后续分流是否有明确归属；
13. **审核行动特有可测试性锚点**：检查正向场景、负向场景、Gate 场景、回写场景、失败降级和回归风险是否可验证；
14. **审核落地要求**：检查规范落地要求表是否说明同步、检查或审计触发条件，且没有制造无法保障的落地承诺；
15. **形成审核结论**：按 §10 输出过程结论，必要时触发 Human Gate、创建后续 Task/Memo/ADR/Pitfall 或修订目标文件；
16. **复跑验证**：目标文件被修改后，应重新运行相关校验命令，并记录结果、残留风险和下一步分流。

## 7. Gate 触发条件

出现以下情况时，AI 必须暂停继续宣称审核通过，并按影响范围触发 Human Gate、降级检查或后续分流：

1. 新增 active 工作流程主文件；
2. 删除、重命名、移动或重排 40-59 工作流程编号；
3. 改变成员自描述契约、active 判定条件、集合状态语义或 Code 派生索引消费方式；
4. 让某个流程承担手写集合索引、事实源替代、Code 授权、Human Gate 替代或 Skill/Agent 直接生效职责；
5. 目标流程与 00、01、03.03、06、07、09 或 10 冲突；
6. 目标流程缺少成员自描述、必需锚点、Gate、回写、证据或可测试性锚点，却被要求标记为 active；
7. 审核需要接受长期降级、跳过验证、关闭 open/degraded 缺口或绕过 Code 诊断；
8. Code 诊断、Git 文件事实源、入口资产或目标流程正文之间存在冲突；
9. 审核结论会影响 Skill、Agent、Hook、Code、Web 或环境入口的长期行为边界。

Gate 触发时，AI 应说明触发原因、影响范围、可选处理方式、推荐分流和需要 Human 确认的具体事项。Human 确认形成稳定事实时，应按 06 的 Human Gate 最小字段记录时间、决策、范围和约束。

## 8. Skill 和 Agent 调度

本流程默认由主控 AI 执行。只有当审核任务可复用、复杂、争议大或需要独立上下文时，才考虑 Skill 或 Agent 辅助。

Skill 适合承接：

1. 固定审核清单；
2. 标准化输出格式；
3. 常见失败分类；
4. 交还主控的修订建议；
5. 重复执行的工作流程设计检查 SOP。

Agent 适合承接：

1. 复杂语义自洽审查；
2. 工作流程是否符合 00 价值标准的独立判断；
3. 多个流程之间职责冲突分析；
4. 候选流程是否应独立成流程的争议分析；
5. 高风险流程设计的并行审阅。

Skill 和 Agent 输出均为过程输出，必须交还主控。Skill 不得自行调度 Agent，Agent 输出不得直接生效，不得绕过 Human Gate、Code 诊断、事实源回写或主控判断。

---
## 9. Code 与命令入口协作适配

本流程优先使用 Code 完成可机械化检查。Code 适合承接：

1. 40-59 成员主文件发现；
2. 成员自描述字段解析；
3. 编号、路径、标题和 canonical path 一致性检查；
4. active 流程必需锚点检查；
5. 文档结构和章节骨架检查；
6. specs 引用检查；
7. 规范落地要求表结构检查；
8. 派生集合索引、状态清单和冲突诊断。

常用命令包括：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

Code 输出只作为导航、聚合和诊断结果。Code 不判断流程是否符合价值观、是否语义自洽、是否真的好用，也不生成授权。Code 不可用、诊断不完整或输出无法回指事实源时，应退回人工检查并记录残留风险。

**审查边界声明**：本流程只审查目标工作流程文档中写的规范要求是否合理、完整、一致、可执行；不审查项目中是否已实际满足这些要求。Code 的作用仅限于帮助 AI 检查目标文档的机械属性（成员自描述、编号、路径、骨架、引用、锚点、落地要求表结构），Code 输出不构成"该工作流程在项目中已被满足"的证据。

## 10. 事实源回写与证据留存

本流程执行后的过程输出应至少说明：

1. 审核对象；
2. 读取的权威依据；
3. 运行的 Code 命令或人工降级检查；
4. 发现的问题；
5. 审核结论；
6. 是否触发 Human Gate；
7. 是否修改目标文件或生成后续工作对象；
8. 残留风险和下一步分流。

审核结论分为：

| 结论 | 含义 |
|---|---|
| `pass` | 未发现阻塞问题，且必要验证通过 |
| `pass_with_followups` | 可继续使用，但存在不阻塞的后续改进项 |
| `blocked` | 存在阻塞问题，不得标记为通过或 active |
| `needs_human_gate` | 需要 Human 确认后才能继续 |
| `not_applicable` | 当前对象不属于工作流程设计审核范围 |

稳定事实回写规则如下：

1. 目标工作流程正文需要调整时，回写对应 `specs/40-59` 主文件；
2. 审核形成缺口、任务线索或后续行动时，回写 Memo、Task 或 TaskPlan；
3. 审核形成长期决策时，回写 ADR；
4. 审核形成可复用踩坑经验时，回写 Pitfall；
5. 审核形成研究报告或迁移说明时，回写 docs；
6. 发生事实源修改时，按 27-Change 的 Git、commit message 和 Refs 追溯规则处理。

不得把聊天中的“看起来可以”“应该合格”“已审核”当作完成证据。关键结论必须能回指规范、目标文件、命令输出、Human Gate 或事实源差异。

---
## 11. 环境适配边界

本流程可以被 Rules 入口提示、Skill SOP、Agent 审查、Code 校验、Web 展示、Hook 提醒或 CI 检查辅助，但这些能力不得替代本流程正文。

环境适配边界如下：

1. Rules 入口只提示何时读取本流程和相关规范，不复制流程全文；
2. Skill 可以封装固定审核清单，但不新增稳定规则；
3. Agent 可以提供独立语义审查，但不直接生效；
4. Code 可以提供确定性诊断，但不替代 AI 语义判断和 Human Gate；
5. Web 可以展示审核状态、诊断和 Human Gate 入口，但不维护第二事实源；
6. Hook 或 CI 可以提醒或阻断高风险变更，但触发不等于检查通过；
7. CI 属于保障机制，不是固定文本能力资产类型；
8. 环境能力缺失时，应降级为人工检查并记录残留风险。

## 12. 行动特有可测试性锚点

本流程的关键行为应能通过正例、反例、Gate 场景、回写场景和命令验证进行检查。

正向场景：

1. 目标流程有合法成员自描述；
2. 文件名、编号、标题和 canonical path 一致；
3. active 流程包含 Scenario、Context、Gate、执行流程、回写、证据和可测试性锚点；
4. 能力协作边界清楚；
5. Code 校验无阻塞诊断；
6. 审核结论能回指事实源和验证结果。

负向场景：

1. 缺少成员自描述；
2. `spec_id` 与文件名编号不一致；
3. planned 或 candidate 被当作 active 执行；
4. 恢复手写集合索引，或创建只说明集合发现方式但不定义行动规则的启动/索引型流程；
5. 流程只写理念，没有可执行步骤；
6. 缺少 Gate、事实源回写、证据留存或失败降级；
7. Skill、Agent、Code、Web 或 Hook 被写成事实源或授权者。

Gate 场景：

1. 新增 active 流程；
2. 改变 40-59 编号归属；
3. 删除、重命名或移动工作流程主文件；
4. 接受长期降级或跳过关键验证；
5. 改变能力资产边界或事实源边界。

回写场景：

1. 审核发现正文缺陷，应回写目标工作流程主文件；
2. 审核发现后续改进项，应回写工作对象或 docs；
3. 审核发现长期决策，应回写 ADR；
4. 审核发现可复用误判，应回写 Pitfall；
5. 审核只产生临时建议时，应明确其为过程输出。

修改本流程或目标流程后，至少应运行：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

无法运行自动化校验时，应说明原因、采用的人工检查方式和残留风险，不得声称完整验证。Code 命令输出仅辅助机械属性检查，不替代 AI 对价值与规范的判断。

## 14. 检查要求

工作流程设计审核至少包括：

| 检查项 | 标准 |
|---|---|
| 对象归属 | 被审核对象属于 `specs/40-59` 工作流程主文件、候选草案或能力消费请求 |
| 成员自描述 | `spec_id`、`kind`、`name_en`、`name_zh`、`collection_status`、`canonical_path`、锚点和 `code_consumption` 完整一致 |
| 文件命名 | 文件名符合 `NN-{英文名}-{中文名}` 这类 Markdown 文件命名模式，且不重复“工作流程规范”字样 |
| 状态边界 | 只有 active、主文件存在、骨架检查通过且锚点完整的流程可被执行 |
| 行动定位 | 该流程确实控制 AI 读取、判断、执行、暂停、验证、回写或维护行为 |
| Scenario | 进入条件和不适用场景明确，可被 AI 识别 |
| Context | 最小可行动上下文清晰，可回指事实源 |
| Gate | 停止、确认、降级和 Human Gate 条件明确 |
| 执行流程 | 步骤可操作，顺序合理，不只是理念说明 |
| 能力边界 | Skill、Agent、Hook、Code、Web、CI 和入口资产未互相替代或越权，CI 未被写成固定文本能力资产类型 |
| 事实源边界 | 过程输出、派生索引、工具结果、Agent 输出和 Web 状态未替代 Git 文件事实源 |
| 证据留存 | 审核结论、验证命令、Human Gate、修改结果和残留风险可追溯 |
| 可测试性锚点 | 正例、反例、Gate、回写、失败降级和回归风险明确 |
| 落地要求 | 落地要求表说明同步、检查或审计触发条件，未制造无法保障的承诺 |
| 验证结果 | 相关 Code 校验命令已运行或已说明无法运行的原因、采用的人工检查方式和残留风险；Code 诊断仅辅助机械属性检查，不替代 AI 对价值与规范的判断 |
