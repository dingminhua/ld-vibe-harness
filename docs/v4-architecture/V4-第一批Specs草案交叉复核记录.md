# V4 第一批 Specs 草案交叉复核记录

> 记录性质：本文记录 04–08 第一批草案的起草、独立复核、修正和当前边界。本文不是规则源，不使任何草案、术语、Helper、Code、tests 或 Web 能力生效。

## 1. 本批范围

第一批包含：

| 编号 | 草案 | 职责标识符 | 当前状态 |
|---:|---|---|---|
| 04 | LDVH Helper CLI 服务契约规范 | `helper-cli-service-contract` | `draft` |
| 05 | 事实模型基础规范 | `fact-model-foundation` | `draft` |
| 06 | 行动模板基础规范 | `action-template-foundation` | `draft` |
| 07 | Code 实践与测试规范 | `code-engineering-practices` | `draft` |
| 08 | Web 呈现与交互规范 | `web-presentation-interaction` | `draft` |

本批没有启动环境接入规范，没有新增 Code/tests，没有修改 `web/` 或 `icons/`，也没有恢复任何 V3 具体事实类型、具体行动模板、项目强制规则或环境 adapter。

## 2. 共同起草边界

五份草案共同遵守：

1. 只使用已审定的直接 `basis`，全部以 `ldvh-root` 为结构父规范并使用 `relation: refines`；
2. 保持 `draft`，不进入当前规则源；
3. 使用 01 的固定头部、自由规则主体和固定尾部，H2 连续；
4. 不把 V3 Code、tests、字段、状态、命令、目录或 Web DTO 作为 V4 权威；
5. 具体领域语义必须等待相应正式来源，Code 和 Web 不得反向定义；
6. 术语和机器表示先登记为 `proposed`，定义来源草案进入当前规则源时再同步判断是否可转为 `current`。

## 3. 分项复核与修正

### 3.1 04 Helper

初稿覆盖公开入口、请求、能力发现、机器响应、读取与状态变更、规则判断和环境一致性。独立复核发现并修正：

1. 补回当前任务相关信息和关联视图，要求保留对象身份、关系来源、遗漏分支、派生边界和过期状态；
2. 未跟踪实现细节不进入公开能力身份；
3. `availability` 能力发现结果按未知操作、来源/实现缺失、能力依据不足以及零/部分/全部范围形成互斥决策；
4. `outcome` 服务结果按请求无效、部分完成、拒绝、不可用、错误、全部完成和无需变化形成互斥决策；
5. 规则结果收窄为 `规则适用判断结果 / Rule Applicability Evaluation Result`，使用 `applicability` 与 `insufficient_information`，不复用 01 的 `basis`；
6. Stop Conditions 补齐恢复条件和对应验证行。

最终独立复查：0 blocker、0 major、0 minor。04 仍保持 `draft`，四组公共机器概念登记为 `proposed`。

### 3.2 05 事实模型

初稿覆盖事实类型准入、事实对象身份、来源、证据、关系、状态、变更和类型取消。独立复核发现并修正：

1. 消除“先成为稳定事实才能准入事实模型”的循环：候选内容是否已经是稳定事实继续由 03 判断；类型只决定事实对象身份和类型规则；
2. 建立“候选定义来源拟准入无效力 → 准入条件和独立复核通过 → 唯一定义来源进入当前规则源时同时生效”的两阶段边界；
3. 区分事实对象稳定身份与当前内容有效性；无效内容仍可被定位修复，但不得作为有效稳定事实消费；
4. 统一使用“唯一定义来源”，避免与事实内容的来源回指混淆；
5. 分开关闭、归档、合并、替代、删除和类型取消，不建立统一“退出”状态或机器动作；
6. 区分工作对象与事实对象：前者绑定当前事项，后者是已准入类型下的稳定单位。

独立术语复核建议：`事实类型 / Fact Type` 以“事实对象类型”为别名；`事实对象 / Fact Object` 以“事实实例 / Fact Instance”为别名。最终复查确认 05 可以作为第一批完成的 `draft`，但激活前必须同步 active 03 和术语表。

### 3.3 06 行动模板

初稿覆盖准入、适用、共同结构、验证、回写、交还、参与者、能力、授权和委派。独立复核发现并修正：

1. 具体模板核心行动结构必须由当前规则源正文作为唯一定义来源；现有规范自然承接或经 01 §13 建立普通规范，附件不得承载完整流程；
2. `template_key` 在全部当前具体模板中唯一，改名或移动保持，不得改派；拆分、合并、替代和取消必须保留旧身份的承接位置；
3. 发现入口把 `template_key` 映射到当前定义来源 `spec_key` 与正文位置，不维护第二份手工目录；
4. 01 的规范文件 `draft/active/retired` 不被误作模板生命周期状态；
5. “执行资源”改为含义明确的“参与者、能力与授权”；
6. Human 可以作出来源保留的授权、方向、风险接受和验收决定，但不能补造定义来源、能力、事实或技术验证。

最终独立复查确认无剩余契约问题。`行动模板标识 / Action Template Identifier / template_key` 登记为 `proposed`；第一份具体模板准入前仍须确定机器可解析的正文承载格式。

### 3.4 07 Code 与测试

07 在外部资料核验基础上覆盖 Code 规划、模块与依赖、接口与 Schema 维护、诊断、重构、设计偏移、风险驱动测试和证据边界。独立复核发现并修正：

1. `Code 规划 / Code Planning` 已形成稳定规则对象，完成概念必要性、正反例、替代名称、使用扫描和独立名称复核，并登记为 `proposed`；
2. 区分领域/公开接口语义与纯内部技术接口、内部数据结构的 Code 设计责任；
3. 取消把 `Focused/Component`、`Contract/Boundary`、`System/Public-capability` 当成近义词的错误分组，改用四种 LDVH 本地检查范围；
4. 重构评估增加“结构仍合适，记录依据后保持现状”的合法结果；
5. 共享实现从绝对要求改为优先方向，允许跨语言、跨进程或安全隔离下的独立实现并要求一致性措施；
6. 接口删除证明限定在声明支持范围和已识别消费者集合，保留不可观察风险；
7. ISO 42010 和 ISO 29119 的支持明确为间接参考或有限范围，NIST SSDF 使用已发布 v1.1 而不吸收观察日的 v1.2 draft；
8. 单文件 5000 行只作为重构评估信号，不作为无上下文失败线。

最终定向复查：0 blocker、0 major，最后三处“测试层次”旧表达已经统一为“测试检查范围”。07 保持 `draft`，不表示 Code/tests 已开始。

### 3.5 08 Web

08 覆盖允许范围读取、Working Tree 当前内容、派生信息当前性、来源呈现、受控交互、操作结果和 V3 实践适配。独立复核发现并修正：

1. 未跟踪内容只有完整满足 03 的事实源条件时才可呈现为稳定事实，否则只是当次可观察信息；
2. 补齐 Stop Conditions 恢复条件；
3. 按 Human 最新决定，标题使用 `Web 呈现与交互规范`，独立读取作为正文内部规则，不进入标题；
4. `positioning`、`scope`、职责和正文继续完整保留读取、来源、派生和回读边界。

最终独立复查：0 blocker、0 major、0 minor。08 保持 `draft`，当前 `web/` 和 `icons/` 未被修改，也未声明已符合 V4。

## 4. 外部资料边界

07 调查只使用标准组织、官方知识体系、认证机构、NIST 和实践发布组织的一手页面，并逐项记录来源分类、适用范围和未采用内容。外部资料只帮助判断候选工程要求，不是 LDVH 规范依据或第二规则源。

08 的可访问性方向与 W3C WCAG 2.2 当前正式建议相容，但本批没有把某个 WCAG 等级写成未经产品范围判断的全局符合性声明。具体 Web 支持范围仍须由实际页面、语言、视口、键盘和辅助技术测试证明。

## 5. 机器检查结果

当次检查确认：

1. 五份 YAML 身份块均可解析；
2. `spec_id`、`spec_key`、标题、路径、`status: draft`、`basis`、`parent_spec: ldvh-root`、`relation: refines` 与空附件列表符合已审定关系；
3. H2 分别为 04 的 1–14、05 的 1–14、06 的 1–13、07 的 1–16、08 的 1–12，全部连续；
4. 固定尾部顺序均为验证要求、Human Gate、Stop Conditions；
5. `git diff --check` 通过；
6. 变更文件不包含 `web/`、`icons/`、Code 或 tests。

## 6. 当前结论

第一批工作已经完成到“可供 Human 集中审阅的五份 `draft` 草案”状态。该结论只证明：职责正文已经形成、V3 覆盖入口得到承接、独立复核提出的实质问题已经修正、术语候选已经登记、机器结构检查通过。

该结论不证明：

1. 04–08 已进入当前规则源；
2. 任一 proposed 术语已经 `current`；
3. Helper、事实模型、行动模板、Code/tests 或 Web 能力已经实现、接入或验证；
4. 具体事实类型、具体行动模板、项目规则或环境 adapter 已经完成审核；
5. V3 Web 实践已经符合 V4。

下一步应由 Human 集中审阅五份草案的业务意图和重大取舍。只有 Human 确认相应草案，并完成各自激活前置、术语同步和当前规则源验证后，才分别考虑转为 `active`；不得因为本批一起起草而要求五份同时激活。
