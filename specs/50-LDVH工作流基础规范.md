## 3. 工作流的定义与定位

### 3.1 工作流的定义

LDVH 工作流是 LDVH 对 AI 在项目中如何行动的执行控制建模，通过定义 Context（AI 行动前应获得的最小可行动上下文）、Scenario（AI 如何识别当前任务场景）、Gate（AI 何时必须暂停并请求人确认）、Rules 适用、Skill 进入、Agent 调度、事实源回写和证据留存等内容，约束 AI 的执行行为，确保 AI 稳定、可控地工作。

### 3.2 工作流的核心特征

工作流必须具备以下核心特征：

1. **以 AI 为中心**：工作流以 AI 执行者为第一服务对象，信息组织方式、事实源读取、场景识别、工具选择等首先满足 AI 的需求；
2. **基于事实源**：工作流依赖 Git 文件事实源，不依赖聊天记忆、工具缓存或数据库派生视图；
3. **场景可识别**：行动必须有明确 Scenario 识别条件，使 AI 能判断何时进入该行动；
4. **Context 最小可行动**：行动必须定义执行前需要读取的最小上下文，避免过载或缺失关键依据；
5. **Human Gate 优先**：关键行动必须触发 Human Gate，等待人类确认后方可继续；
6. **证据留存**：AI 执行的关键步骤必须留下可追溯的证据；
7. **事实回写**：AI 完成执行后必须按事实源边界把稳定事实写回项目；
8. **机制可适配**：行动可以说明 Rules、Skill、Agent 和工具如何参与，但不得替代 11、12、13 中对应机制、工具和对象规则。

### 3.3 工作流与自由执行的区别

| 维度 | 自由执行 | 工作流约束下的执行 |
|---|---|---|
| 上下文来源 | 聊天记忆、临时信息 | Git 文件事实源、结构化 Context |
| 场景识别 | 凭感觉、无明确规则 | 按 Scenario 规则明确识别 |
| 约束机制 | 无明确约束 | 规则、Gate、状态机多重约束 |
| Skill / Agent | 随意调用或混用 | 按工作流和 11 系列机制边界选择 |
| 人类确认 | 随意、无明确触发点 | Human Gate 明确触发条件 |
| 证据留存 | 无强制要求、仅聊天记录 | 必须按规范留存可追溯证据 |
| 事实回写 | 随意、可能不回写 | 必须按事实源边界回写 |
| 可追溯性 | 弱、仅聊天历史 | 强、Git 文件事实源 + 结构化证据 |

## 4. 工作流

### 4.1 工作流定义

工作流是 LDVH 对某一类 AI 行动控制事实的标准化建模结构，用于统一描述该行动的行动定位、适用场景、准入条件、事实源边界、Context 要求、Scenario 识别、执行流程、Gate 触发条件、Skill 和 Agent 调度、工具协作、事实源回写、证据留存、Human Gate、落地前决策、价值与要素审查、落地初始化、落地审计、合规检查和待补齐事项。

每个 51-79 具体行动规范，都是一个具体工作流的定义文档。

### 4.2 工作流的标准组成

一个工作流应包含以下内容：

1. 行动定位与适用场景；
2. 准入条件；
3. 事实源边界；
4. Context 要求；
5. Scenario 识别；
6. 执行流程；
7. Gate 触发条件；
8. Skill 和 Agent 调度；
9. 工具协作适配；
10. 事实源回写要求；
11. 证据留存要求；
12. Human Gate；
13. 附件型实践子文档按需拆分规则；
14. 落地前决策；
15. 价值与要素审查；
16. 落地初始化；
17. 落地审计；
18. 合规检查；
19. 待补齐事项。

### 4.3 工作流与行动执行

工作流定义行动类别的规则，行动执行是项目或会话中按模型完成的具体过程。

工作流承载于 `specs/50-79`。行动执行过程中产生的稳定事实不得停留在聊天、Skill 输出、Agent 输出或工具缓存中，必须依据 `specs/10-事实源边界与承载规范.md` 和对应事实模型规范写回 `ldvh-base/`、`docs/`、`specs/` 或其他权威位置。

### 4.4 工作流与事实模型

工作流控制 AI 如何行动，事实模型承载工程生产事实。两者关系如下：

| 维度 | 工作流 | 事实模型 |
|---|---|---|
| 核心问题 | AI 如何读取、判断、执行、停下和回写 | 项目事实如何结构化、流转和沉淀 |
| 规范区段 | `specs/50-79` | `specs/20-49` |
| 实例事实 | 行动执行结果按事实类型回写 | 事实实例承载于 `ldvh-base/` |
| 关键约束 | Context、Scenario、Gate、回写、证据 | 准入、字段、状态机、验收和事实模型关系 |

工作流可以创建、更新、检查或引用事实模型，但不得重新定义事实模型字段、状态机、验收标准或事实实例事实源边界。

### 4.5 工作流与工具实现

工具可以依据工作流开发上下文包生成、Scenario 辅助识别、Gate 提示、证据聚合、回写校验和受控写入能力。工具实现不得替代工作流本身，也不得绕过工作流定义的事实源边界和 Human Gate。

### 4.6 工作流文件命名与附件型实践子文档

51-79 主文件均为具体行动规范，文件名不重复"工作流规范"字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

工作流主文档必须完整定义工作流。工作流附件型实践子文档用于在主模型完整定义后，按需承接某个工作流围绕 Rules、Skill、Agent、Tools 和 Web 的机制实践内容。附件型实践子文档不重新定义工作流，不是模型完整性的默认要求，不得为空占位。

具体行动规范应在主文档中定义 Context、Scenario、Gate、执行流程、回写要求、证据要求、Skill 和 Agent 调度、工具协作、落地初始化、落地审计和合规检查。主文档应保留摘要、适用条件和引用，不得把行动核心规则迁移到子文档中。

工作流附件型子文档的通用规则（分类、命名、状态骨架）由各工作流主文档自行声明，本文不重复维护。

工作流特有内容：

1. 适用区段：50-79；
2. 核心规则留在主文档：行动自身的 Context、Scenario、Gate、执行流程、回写要求和证据要求应留在 `NN` 主文件，不应转移到附件型实践子文档。

### 4.7 落地前决策、价值与要素审查、落地初始化、落地审计与合规检查

工作流规范应按需要定义落地前决策、价值与要素审查、落地初始化、落地审计和合规检查要求。落地前决策用于判断某一工作流在具体项目中需要落地哪些 Rules、Skill、Agent、Tools、Web、契约或附件型实践子文档。落地前决策不是落地初始化，不表示对应实践已经存在。

落地前决策完成后、实际落地初始化开始前，必须依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §4.3 执行价值与要素审查。工作流特定的审查要点：

1. 是否仍以 AI 执行者为第一服务对象，帮助 AI 识别场景、读取事实源、选择工具 / Skill / Agent、触发 Human Gate 和回写事实；

价值与要素审查的结论应成为落地初始化的前置输入。审查不通过时，应回到落地前决策修正方案、标记暂缓或停止落地；不得直接进入初始化。

落地初始化应说明在落地前决策和价值与要素审查完成后，该工作流进入项目实践时需要实际创建、修改或确认的 Rules 摘要、Skill、Agent、Tools 校验能力、Web 信息同步入口、契约子文档、索引引用、初始化产物、暂缓项和 Human Gate。落地初始化完成后，应遍历工作区所有 Git 仓库，对每个因本次落地初始化产生文件修改的仓库执行 commit，确保跨仓库变更完整记录为 Change 事实实例（依据 specs/22-Change-变更记录.md）。

落地审计应说明如何审查该工作流的实践是否真实落地、持续有效、与 Git 文件事实源一致、未绕过 Human Gate，并识别初始化缺口、过期实践和需要整改的附件型实践子文档。落地审计还应检查跨仓库 commit 完整性：任务涉及的所有 Git 仓库是否均已提交，是否存在遗漏提交的仓库。

合规检查应说明行动规范写作、Scenario 识别、Context 读取、Gate 触发、Skill 和 Agent 调度、工具协作、事实源回写、证据留存和 Human Gate 是否符合本工作流和上位规范。

### 4.8 完整方案形成流程

工作流完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义工作流；
2. 定义 Context、Scenario、Gate、执行流程、Skill 和 Agent 调度、工具协作、回写要求和证据要求；
3. 定义落地前决策、价值与要素审查、落地初始化、落地审计要求和合规检查标准；
4. 判断 Rules、Skill、Agent、Tools、Web 或 Contract 实践是否复杂到需要独立维护；
5. 完成落地前决策后，依据 00 总纲执行价值与要素审查；
6. 确保附件型实践子文档状态与实际文件一致；
7. 涉及 Skill、Tools、Web 或 Contract 的，完成联动检查；
8. 修改规范、附件型实践子文档、协作机制或事实源时记录 Change（依据 specs/22-Change-变更记录.md）

## 5. 工作流准入与分类原则

### 5.1 行动分类原则

LDVH 工作流可按治理用途分为以下几类：

1. **初始化行动**：建立项目可被 LDVH 管辖的基础上下文、目录、规则和对象实例承载能力；
2. **需求规划行动**：将人的输入、意图和资料转化为可追踪、可执行、可验证的事实源；
3. **任务执行行动**：推动最小执行对象流转，记录证据、阻塞、风险、变更和关闭条件；
4. **Review 行动**：检查执行结果、证据、关闭条件和 Human Gate；
5. **审计行动**：检查项目状态、事实源、规则、对象、工具和工作流是否持续合规；
6. **协作增强行动**：通过 Skill、Agent、工具或多角色分析增强 AI 的判断质量，但不替代事实源和 Human Gate；
7. **管理行动**：管理事实模型、规则、协作机制和事实源边界的受控变更。

### 5.2 行动清单归属

具体工作流清单、编号归属、维护状态和区段关系见本文 §7.3 工作流区段索引。本文只定义工作流的通用分类和准入原则。

### 5.3 预留编号区段

编号区段 61-79 预留用于未来新增行动，不得未经 Human Gate 确认提前占用。

### 5.4 准入条件原则

一个流程需要满足以下条件之一，才应成为工作流：

1. **需要稳定控制 AI 行动**：该流程需要约束 AI 读取、判断、执行、停止和回写方式；
2. **需要明确 Scenario 识别**：该流程存在可识别的任务场景，且错误进入或漏进入会影响执行质量；
3. **需要明确 Context 要求**：该流程依赖一组稳定的最小可行动上下文；
4. **需要 Gate 控制**：该流程包含必须等待人确认或条件满足后才能继续的节点；
5. **需要跨机制协作**：该流程需要协调 Rules、Skill、Agent、工具和事实模型；
6. **需要事实源回写和证据留存**：该流程产出稳定事实、证据、决策、任务、变更或审计结果；
7. **不成为工作流就会导致 AI 行动边界漂移**：该流程如果不结构化，就会导致 AI 凭聊天记忆执行、绕过 Human Gate 或无法追溯。

不满足以上条件的内容，应按其性质分流：
- 一次性局部执行策略 → 留在当前执行上下文；
- 可复用但可在主上下文完成的轻量流程 → 评估是否作为 Skill；
- 只需独立上下文或专业审查 → 评估是否调用 Agent；
- 长期硬约束 → 写入 specs/ 或 `.trae/rules/`；
- 稳定生产事实 → 按 20-49 事实模型规范写入 `ldvh-base/`；
- 外部参考资料 → 写入 `specs/refs/`。

## 6. 工作流的通用规范

### 6.1 Context（上下文）原则

Context 是由事实源组织出的 AI 执行输入、任务背景和行动依据。

Context 的目标是给 AI 提供足够但不过载的最小可行动上下文，让 AI 能够：

1. 理解当前项目的身份和边界；
2. 理解当前任务的背景和目标；
3. 知道可用的规则、Skill、Agent 和工具；
4. 知道事实源的边界和回写位置；
5. 知道何时触发 Human Gate。

Context 的组织遵循以下原则：

1. **最小化原则**：只包含 AI 执行当前行动所需的最小信息；
2. **结构化原则**：以结构化方式组织，便于 AI 理解和处理；
3. **事实源原则**：所有稳定信息都来自 Git 文件事实源；
4. **动态原则**：根据当前 Scenario 动态调整 Context 内容；
5. **可追溯原则**：Context 应能回溯到原始事实源文件；
6. **读取精准原则**：上下文消耗应与任务复杂度匹配，而非与文档体积成正比。

#### 6.1.1 读取策略

读取精准原则的操作化方法：

1. **定位优先**：AI 读取事实源前，应先使用搜索工具（Grep、SearchCodebase）定位目标段落，再按行范围读取，避免全文读取大文件；
2. **渐进升级**：读取策略按成本从低到高升级——搜索定位 → 按行范围读取 → 按需扩展行范围 → 全文读取；仅在搜索无法定位或需理解完整上下文时才升级到下一级；
3. **行范围约束**：对超过 200 行的规范文档，AI 不应在未定位的情况下直接全文读取；应先搜索关键词，再读取目标段落前后必要上下文；
4. **章节锚点**：LDVH 规范文档使用 `§` 编号体系，AI 可利用章节编号作为精准读取入口，先搜索章节标题再读取对应段落；
5. **上下文预算意识**：AI 应感知当前上下文消耗，优先选择低成本读取策略；当上下文接近上限时，应更严格地使用定位优先策略。

**标准化读取工作流**

AI 读取规范文档时，应按以下工作流执行：

1. **Grep 章节标题**：使用 `Grep` 搜索 `^## |^### ` 获取文档章节标题和行号，同时完成章节发现和行号定位；
2. **机器索引辅助**：如存在符合 `specs/03.01-Specs文档索引规范.md` 的有效 specs 文档索引，可用其辅助定位 `specs/*.md` 根目录文档和章节；索引只作导航辅助，不替代原文读取；
3. **精准读取**：确定目标章节后，使用 `Read` 的 offset/limit 参数精准读取目标段落，避免读取无关章节；
4. **按需扩展**：仅在目标段落引用了上下文内容时，扩展读取范围；
5. **全文升级**：仅在搜索无法定位、需理解完整上下文或文档不足 200 行时，才全文读取。

Grep 是主路径（发现+定位），机器索引是补充路径（定位和诊断）。二者配合使用，不得跳过 Grep 直接 Read 全文。`specs/evals/` 和 `specs/refs/` 不进入 03.01 默认索引范围，只有用户明确指定时才读取。

### 6.2 Scenario（场景）原则

Scenario 是 AI 当前所处的任务类型、协作模式和执行入口。

Scenario 的目标是让 AI 能够：

1. 识别当前任务属于什么行动类型；
2. 选择合适的执行入口；
3. 加载对应的规则和 Context；
4. 判断是否进入 Skill、调用 Agent 或使用工具；
5. 判断是否应触发 Human Gate。

Scenario 的识别遵循以下原则：

1. **基于事实源**：根据 Git 文件事实源和用户当前输入识别当前场景；
2. **明确规则**：每个具体行动规范都应定义识别规则；
3. **优先级**：多个场景同时匹配时，按具体行动规范或 40 索引中的关系说明选择；
4. **Human Gate**：高影响场景切换可能触发 Human Gate；
5. **可降级**：条件不足时应降级为主上下文分析或询问用户，而不是强行进入行动。

### 6.3 Gate（门禁）原则

Gate 是需要人确认或满足条件后才允许继续的控制点。

Gate 分为以下类型：

1. **Human Gate**：必须由人类确认后方可继续；
2. **条件 Gate**：满足特定条件后方可继续；
3. **审批 Gate**：必须由特定角色审批后方可继续。

Gate 的执行遵循以下原则：

1. **先停再问**：识别到 Gate 时，AI 必须先暂停执行，再请求人类确认；
2. **明确说明**：AI 必须明确说明触发 Gate 的原因、影响范围和建议确认事项；
3. **不可绕过**：AI 不得绕过 Gate 继续执行；
4. **证据留存**：Gate 的确认过程必须留下可追溯的证据；
5. **回写联动**：Gate 结果形成稳定事实时，应按事实源边界回写。

在 Trae 平台中，Human Gate 通过 AskUserQuestion 工具实现。触发条件、设计规范和取消降级策略见 `specs/11-LDVH-Trae-Solo-环境规范.md` §9。

### 6.4 Rules 适用原则

规则是 AI、人和工具必须遵守的行为边界。

规则的加载遵循以下原则：

1. **优先级**：项目规则优先于 LDVH 基础规则；
2. **不冲突**：规则之间不得冲突，冲突时按优先级处理，并评估是否需要修正规则；
3. **可追溯**：规则必须有明确的来源和版本；
4. **机制回指**：Rules 机制设计和治理以 `specs/11-LDVH-Trae-Solo-环境规范.md` §6 为准；
5. **Human Gate**：规则变更必须触发 Human Gate。

### 6.5 Skill 进入原则

Skill 是 AI 可使用的可复用流程。工作流可以在具体场景中说明何时建议进入 Skill，但 Skill 的准入、命名、部署、输出和事实源回写边界由 `specs/11-LDVH-Trae-Solo-环境规范.md` §7 定义，本文不重复维护通用规则。

Skill 进入在工作流中的适配说明如下：

1. **场景匹配**：根据当前 Scenario 判断是否需要可复用流程，判断标准以 11 §7 为准；
2. **机制回指**：Skill 准入、边界和证据留存必须回指 11 系列规范及本文 §6.8 事实源回写原则；

### 6.6 Agent 调度原则

Agent 是 AI 代理执行能力。工作流可以在具体场景中说明何时建议调度 Agent，但 Agent 的创建、调用、定义摘要、生命周期、权限边界和事实源回写边界由 `specs/11-LDVH-Trae-Solo-环境规范.md` §8 定义。

Agent 调度在工作流中的通用原则：

1. **场景匹配**：根据当前 Scenario 判断是否需要独立上下文、结论隔离、并行委派或不同权限边界；
2. **机制回指**：Agent 创建或调用治理条件必须回指 11 系列规范；
3. **Rules 约束**：Agent 的执行必须遵守 Rules、事实源边界和工作流；
4. **Human Gate**：关键 Agent 的创建、调度、权限调整或写入动作必须按对应规范评估 Human Gate；
5. **不替代事实源**：Agent 不得成为事实源，只能读取、分析和建议；
6. **能力前提可检查**：具体行动可以声明某类 Agent 能力为增强模式前提；前提不满足时，应降级、暂停或提示用户，而不是假装已具备能力；
7. **主控唯一调度**：需要并行、独立上下文、多角色判断或子 Agent 审计时，由主控调度 Agent；Skill 只能向主控提出调度建议。

### 6.7 工具协作原则

工具可以辅助 AI 读取事实源、获得结构化上下文、执行确定性校验、准备受控写入、展示 Gate 和证据，但工具不得替代 AI 的场景判断，也不得直接调用或模拟 AI 决策。

工具协作遵循以下原则：

1. Tools 辅助和 Web 信息同步的分工以 `specs/12-LDVH工具基础规范.md` 为准；
2. 工具输出不是最终事实源；
3. 工具写入必须受控，且不得绕过事实源边界、事实模型规范、工作流或 Human Gate；
4. 工具能力不足时，工作流不得假定工具已完成校验或回写；
5. 工具运行中产生的稳定事实必须回写 Git 文件事实源后才成立。

### 6.8 事实源回写原则

事实源回写是 AI 完成执行后把稳定事实写回项目的过程。

AI 完成执行后的事实源回写，依据 `specs/10-事实源边界与承载规范.md` §7定义的回写条件执行，本文不重复维护。工作流的适配说明如下：

1. **工作流回写触发**：AI 按 Scenario 执行完毕后，应判断执行结果是否包含稳定事实；若包含，必须按 10 §7回写；
2. **回写与 Gate 联动**：关键事实的回写应评估 Human Gate，依据本文、具体行动规范和相关基础规范判断；
3. **对象回写回指**：任务、证据、变更、风险、决策等对象实例回写必须遵守 20-49 具体事实模型规范；
4. **机制输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实；
5. **报告回写分流**：审计报告、分析报告或管辖项目资料应按 02、03 和具体行动规范判断进入 docs/、ldvh-base/或 specs/。

### 6.9 证据留存原则

工作流的证据留存遵循以下原则：

1. **关键步骤留证**：Context 读取、Scenario 判断、Gate 触发、Skill / Agent 调度、工具校验、事实源回写等关键步骤应留下可追溯证据；
2. **证据归属明确**：证据属于事实实例时，按 Evidence 或相关对象规范写入 `ldvh-base/`；属于报告时，按 docs/ 边界写入；属于规范变更时，记录 Change（依据 specs/22-Change-变更记录.md）
3. **证据可验证**：证据应说明来源、时间、执行者、结果和影响范围；
4. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
5. **关闭前可追溯**：涉及任务、审计或 Review 的行动，在关闭前应能追溯关键证据。

### 6.10 执行中发现问题的分流规则

AI 在执行 Task 过程中发现问题时，必须按以下分流规则判断问题类型并采取对应行动，不得跳过分流、不得把所有问题统一处理为阻塞或忽略。

| 分流类型 | 判断条件 | 处理方式 |
|---|---|---|
| **blocking** | 问题直接阻塞当前 Task 的 acceptance 项完成 | 创建子任务记录 bug，关联到当前 Task，立即修复后重新验证 |
| **follow-up** | 问题不阻塞当前 Task，但需要后续跟进 | 创建新 Task 记录，`source` 引用当前 Task，当前 Task 不等待 |
| **opportunistic fix** | 问题与当前 Task 相关且修复成本极低（<5 分钟），修复不引入新风险 | 在当前 Task 中直接修复，在 closure_evidence 中记录修复内容 |
| **ADR 候选** | 问题涉及架构决策、技术选型或规范变更 | 记录为 Memo 或 ADR proposed 状态，不阻塞当前 Task |
| **Pitfall 候选** | 问题具有通用教训价值，其他项目或场景可能重复遇到 | 创建 Pitfall 记录，关联当前 Task 作为 source_object |
| **Memo 候选** | 问题有保留价值但尚未达到 Pitfall 或 ADR 级别 | 创建 Memo 记录，关联当前 Task |

分流规则遵守以下约束：

1. **blocking 必须处理**：阻塞当前 Task 的问题不得降级为 follow-up 或忽略；
2. **子任务深度限制**：blocking 问题创建子任务时，子任务不得再有子任务（依据 `specs/27.01-Rules.md`）；
3. **opportunistic fix 需谨慎**：修复成本不确定时，应升级为 follow-up 而非冒险在当前 Task 中修复；
4. **ADR/Pitfall/Memo 不阻塞**：候选类问题不阻塞当前 Task 完成和关闭；
5. **分流结果可追溯**：每个分流决定应记录在 Task 的 closure_evidence 或关联事实对象中。

### 6.11 主控唯一调度与流程交还原则

工作流中的主控是唯一的流程编排者。Skill、Agent、Tools、MCP、脚本和 Web 不得替代主控进行跨流程调度。

主控唯一调度遵循以下原则：

1. **Skill 单流程**：Skill 只完成一个明确、受控、可复用的流程；
2. **Skill 不链式调度**：Skill 不得自行调用下一个 Skill，不得自行调用子 Agent；
3. **Skill 交还主控**：Skill 流程结束、暂停、失败或需要升级时，必须输出下一步建议并交还主控；
4. **Agent 由主控调度**：需要并行、独立上下文、多角色判断、隔离审计或不同权限边界时，只能由主控或用户显式调度 Agent；
5. **工具不调度 AI**：Tools、MCP、脚本和 Web 不得调用或模拟 Skill / Agent 调度；
6. **下一步建议可追溯**：Skill 输出的下一步建议应说明建议动作、建议调度对象、原因、所需输入、预期输出和停止条件；
7. **调度结果回到主控**：Agent 或工具输出必须返回主控或用户，由主控判断是否写回事实源、进入下一个 Skill、触发 Human Gate、退回执行或结束流程。

该原则用于降低 AI 遗漏状态流转、Human Gate、独立审计或事实源回写的概率。具体行动规范可在此基础上定义更细的交还格式，但不得允许 Skill 直接调度子 Agent 或跨流程链式执行。

## 9. Human Gate 与检查要求

### 9.1 Human Gate 触发条件

以下情况应评估 Human Gate：

1. 新增行动；
2. 删除行动；
3. 重命名行动；
4. 重排行动编号区段；
5. 改变工作流的通用规则；
6. 改变工作流的标准组成；
7. 改变 Context、Scenario、Gate 的定义；
8. 改变事实源回写的原则；
9. 改变 Human Gate 的触发条件；
10. 新增、删除、重命名或改变工作流附件型实践子文档；
11. 改变 Skill、Agent 或工具在工作流中的调度边界；
12. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 9.2 检查要求

工作流规范写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 行动定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、事实模型、工作流、Context、Scenario 和 Gate 术语一致 |
| 模型组成 | 具体行动规范覆盖工作流的标准组成，缺项已说明原因 |
| 附件型实践子文档 | 已说明是否需要附件型实践子文档；如创建，已确认按需、非空、不替代主模型且经 Human Gate |
| 落地前决策 | 已定义实际初始化前需要完成的落地范围、暂缓项和 Human Gate 决策 |
| 价值与要素审查 | 已说明落地前决策后需依据 00 总纲审查价值实现标准和五类构成要素边界 |
