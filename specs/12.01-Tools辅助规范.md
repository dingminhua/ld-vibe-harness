## 1. 本文定位

本文定义 LD Vibe Harness 如何使用 Tools 辅助层承载确定性解析、校验、聚合、上下文包生成、派生数据生成和受控写入执行。

Tools 辅助层面向机器可执行、可重复、可校验的确定性工作。Tools 输出不是事实源，Tools 实现不替代 specs/、ldvh-base/或 docs/ 的权威事实。

## 2. 父规范关系

`specs/12-LDVH工具基础规范.md` 定义 LDVH 工具体系总边界、事实源回写总原则和 Tools 辅助层 / Web 信息同步层选择边界。本文只展开 Tools 辅助层。

当需要判断某项工具能力应进入 Tools 辅助层还是 Web 信息同步层时，必须以 `specs/12-LDVH工具基础规范.md` 第五节为准；本文只检查已拟使用 Tools 辅助层时是否满足解析、校验、聚合、受控写入和输出治理要求。

Tools 辅助层与其他机制的关系：

| 对象 | 关系 |
|---|---|
| Web 信息同步层 | Tools 辅助层可为 Web 信息同步层提供派生视图数据和受控写入能力 |
| Git 文件事实源 | Tools 辅助层读取、校验、聚合和写入的目标必须回到 Git 文件事实源 |
| Rules / Skill / Agent | Rules 可约束 Tools 使用方式，Skill / Agent 可按授权调用 Tools；Tools 不得调用 AI、Skill 或 Agent |
| 事实模型 | Tools 辅助层可校验和写入事实实例，但字段和状态以 20-49 规范为准 |
| 行动模型 | Tools 辅助层在上下文准备和事实回写中的角色应服从 50-79 行动模型 |

## 3. Tools 辅助层内部设计检查

跨工具层选择依据 `specs/12-LDVH工具基础规范.md` 第五节，本文不另行判断某项能力是否应优先进入 Tools 辅助层或 Web 信息同步层。已拟使用 Tools 辅助层时，应检查该 Tools 能力是否满足以下内部设计条件：

1. 处理逻辑可由确定性处理逻辑描述；
2. 输入来源可追溯到 Git 文件事实源；
3. 输出可以结构化呈现，并标明来源；
4. 写入目标明确且属于对应 Git 文件事实源；
5. 写入前可执行校验；
6. 写入后可通过 Git 追溯；
7. 不依赖聊天记忆、UI 临时状态或缓存作为权威输入；
8. 不调用 AI、Skill 或 Agent；
9. 不绕过 Human Gate；
10. 属于事实模型或行动模型 `NN.04-Tools.md` 实践的 Tools 能力，应依据 `specs/04-LDVH模型子文档规范.md` §8检查消费场景、Contract 依据、需求变更同步和测试同步要求。

## 4. 允许职责

Tools 辅助层可以承担：

| 职责 | 说明 |
|---|---|
| 读取 | 从 Git 文件事实源读取结构化对象和规范信息 |
| 解析 | 解析 Markdown、YAML 或其他约定格式文件 |
| 校验 | 校验字段完整性、状态合法性、引用有效性和格式合规性 |
| 聚合 | 聚合项目上下文、对象状态、缺口和检查结果 |
| 上下文包生成 | 为 AI 或工具生成可追溯的最小上下文包 |
| 派生数据生成 | 为 Web 信息同步层生成可追溯的派生视图数据 |
| 受控写入 | 按授权写入目标事实源，并触发写入前后检查 |
| 缺口报告 | 报告初始化缺口、合规缺口、结构缺口、校验失败和应由 Tools 承担但尚未实现的受控写入能力缺口 |

## 5. 禁止职责

Tools 辅助层不得承担：

1. 保存第二套事实；
2. 将缓存、数据库或运行时索引作为权威状态；
3. 自动修改业务事实、任务状态、specs 规范或 Rules；
4. 绕过对象状态机进行状态流转；
5. 绕过 Human Gate 自动写入；
6. 直接调用 AI、Skill 或 Agent；
7. 将索引类信息持久化为独立事实源；
8. 将 Tools 输出作为任务状态、证据、决策、specs 规范、Rules 或审计的唯一来源；
9. 把上下文包、校验结果或候选参数升级为自动 Agent 调度请求；
10. 启动、编排或作为入口触发子 Agent 流程。

## 6. 解析与校验原则

### 6.1 解析原则

1. Tools 解析的输入必须来自 Git 文件事实源。
2. Tools 不得将缓存、数据库、UI 状态或对话内容作为解析输入的权威来源。
3. 解析逻辑依赖对应事实源格式契约、对象规范和行动模型，Tools 不得自行扩张格式契约。
4. 解析失败时，应报告失败位置、期望格式和实际内容，不得静默跳过。
5. 解析失败不得导致 Tools 修改或覆盖原始事实源文件。

### 6.2 校验原则

1. 校验范围由事实源规范、事实模型规范、行动模型和对应工具场景共同决定。
2. 写入前必须校验目标事实源归属、格式契约、对象字段、状态流转、引用关系和 Human Gate。
3. 当对应主模型流程、Skill 流程或 Web 入口包含可机械化写入步骤时，Tools 校验应报告当前 Tools 是否具备对应受控写入能力；缺失时应输出能力缺口，不得仅因只读校验通过而声称完整支撑落地。
4. 校验结果应结构化输出，包含校验对象、校验依据、校验结果、不合规详情和建议修复方式。
5. 校验失败不得自动修改事实源。
6. 写入前校验失败应阻止写入。

## 7. 聚合与上下文包原则

1. 聚合输入必须来自 Git 文件事实源，不得混入缓存、数据库或 UI 状态中的权威数据。
2. 聚合输出属于派生数据，不是事实源。
3. 聚合输出必须包含来源引用，使每个数据项可以追溯到 Git 文件事实源。
4. 上下文包必须从 Git 文件事实源实时生成或按需生成。
5. 上下文包中出现的新信息，如果需要长期保留，应重新判断对象类型和事实源载体。
6. 索引类信息按需计算并直接返回，不应持久化为独立索引文件。
7. specs 文档索引生成和诊断能力应遵守 `specs/03.01-Specs文档索引规范.md` 的输入范围、输出原则、AI 消费规则和 Tools 辅助程序边界；默认输入范围仅为 `specs/*.md`。

## 8. 受控写入原则

### 8.1 写入目标

1. Tools 的任何写入操作，实际写入目标必须是项目的 Git 文件事实源。
2. 写入不得只停留在 Tools 内部存储、数据库或 UI 状态。
3. Tools 不得维护自己的权威数据存储。

### 8.2 写入前检查

写入前必须检查：

1. 目标事实源归属正确；
2. 写入内容符合对象格式规范；
3. 状态流转合法；
4. 是否触发 Human Gate；
5. 是否已有权威事实，避免覆盖；
6. 写入是否需要追加变更记录（依据 specs/22-Change-变更记录.md）

### 8.3 写入后验证

1. 写入后必须可通过 Git 追溯。
2. 写入后应重新读取或刷新相关派生数据。
3. 写入后如产生稳定变更，应记录变更（依据 specs/22-Change-变更记录.md）

## 9. PyTools 标准化规则

### 9.1 命名规则

PyTools 实现文件统一放置于项目根目录 `tools/` 下，文件名使用以下格式：

```text
ldvh_<domain>_<capability>.py
```

命名含义：

| 部分 | 说明 |
|---|---|
| `ldvh` | 固定前缀，表示 LDVH PyTools 实现 |
| `<domain>` | 能力所属领域，如 `fact`、`specs`、`adr`、`change`、`context` |
| `<capability>` | 具体能力，如 `validate`、`create`、`transition`、`format`、`bundle` |

历史工具暂未迁移前可以保留原文件名，但新增工具应使用统一命名。旧工具迁移时应优先保留兼容 wrapper，避免一次性破坏既有 Skill、Rules 或测试入口。

### 9.2 CLI 参数规则

PyTools CLI 应至少遵守以下规则：

1. 支持 `--help` 展示命令用途、参数和退出码含义；
2. 输入路径参数应明确区分文件、目录和项目根目录；
3. 写入类命令必须显式表达目标对象、目标状态或目标输出路径；
4. 校验类命令应支持机器可读输出或可稳定解析的文本输出；
5. 不得依赖交互式输入完成核心流程；
6. 调用示例应记录在对应 `NN.04-Tools.md` 或工具说明中。

### 9.3 ToolResult 与 ToolIssue 输出规则

PyTools 输出应能被 AI、Rules、Skill、Web 或其他工具稳定消费。结构化输出应区分整体结果和单项问题。

ToolResult 至少包含以下语义字段：

| 字段 | 说明 |
|---|---|
| `ok` | 本次执行是否通过 |
| `command` | 工具命令或能力名称 |
| `target` | 被处理的文件、目录、对象或提交 |
| `summary` | 面向人和 AI 的结果摘要 |
| `issues` | ToolIssue 列表，可为空 |

ToolIssue 至少包含以下语义字段：

| 字段 | 说明 |
|---|---|
| `level` | `error` 或 `warning` |
| `code` | 稳定问题代码 |
| `message` | 问题说明 |
| `path` | 问题来源文件或对象 |
| `field` | 问题字段，可为空 |
| `suggestion` | 建议修复方式，可为空 |

现有工具如仍使用文本输出，应保持问题代码稳定，并在迁移计划中说明向 ToolResult/ToolIssue 对齐的方式。

已实现 `--format json` 的工具：`ldvh_fact_validate.py`。

### 9.4 exit code 规则

PyTools exit code 应遵守以下约定：

| exit code | 含义 |
|---|---|
| `0` | 执行成功，未发现 error |
| `1` | 执行完成但存在 error |
| `2` | 命令参数、输入路径或调用方式错误 |
| `3` | 依赖环境、外部命令或 Git 状态不可用 |

warning 不应单独导致 exit code 非 0，除非该工具场景明确把 warning 设为阻塞条件。

### 9.5 测试规则

PyTools 测试必须遵循本文 §10 的测试与验收原则，并补充以下要求：

1. 新增 PyTools 文件必须新增对应 `tests/tools/test_<tool_name>.py`；
2. 修改 PyTools 输入、输出、错误代码、exit code、写入行为或 Contract 消费方式时，必须同步更新对应测试；
3. 写入类命令必须测试写入前校验失败会阻止写入；
4. 状态流转类命令必须测试合法流转、非法流转和终态不可重开；
5. 校验类命令必须测试有效样例、缺必填字段、非法状态、非法文件名和条件必填；
6. 测试命令和结果应写入 Task closure_evidence 或对应验收材料。

### 9.6 Contract 同步规则

消费 Contract 子文档的 PyTools 必须声明：

| 声明项 | 说明 |
|---|---|
| Contract 来源 | 具体 `NN.06-Contract.md` 文件 |
| 消费字段 | 工具实际读取或校验的字段、状态、枚举、正则或流转矩阵 |
| 消费方式 | 读取、校验、创建、状态流转、删除、聚合或缺口报告 |
| 测试入口 | 对应 pytest 文件和推荐测试命令 |
| 同步触发 | Contract、主模型、Rules、Skill、Web 或工具实现发生何种变化时必须同步检查 |

Contract 变更后，若消费工具和测试尚未同步完成，应在工具输出、任务证据或验收材料中明确同步缺口，不得声称该工具已经完整消费最新 Contract。

## 10. Tools 测试与验收原则

1. 每个 Tools 辅助能力在新增、修改或升级为 active 时，必须同步补充或更新自动化测试。
2. 消费契约子文档的 Tools 在 Contract、需求变更或 Tools 实现变更影响输入、输出、校验范围、错误语义、写入行为或契约消费方式时，必须同步更新 Tools 实现和对应测试（依据 `specs/04-LDVH模型子文档规范.md` §8）。
3. 每次新增、修改或升级 Tools 辅助能力时，必须执行对应自动化测试，并将测试命令、测试结果和无法覆盖项记录到任务证据或人工验收材料中（依据 specs/22-Change-变更记录.md）
4. 测试未通过时，不得声称该 Tools 能力已经完成落地、验收通过，或可作为 Skill / Web 的可靠依赖。
5. `tools/` 下新增或修改 Python 文件时，必须在 `tests/tools/` 下补充或更新对应 pytest 测试文件；测试文件按被测工具命名，例如 `tools/example.py` 对应 `tests/tools/test_example.py`。
6. Python Tools 默认使用 pytest，测试文件统一放在项目根目录 `tests/tools/` 下，并按被测工具命名。
7. 测试输入应使用测试夹具、临时目录或最小样例文件，不得依赖聊天记忆、UI 临时状态、运行时缓存或当前工作区偶然状态作为通过条件。
8. 测试应覆盖读取、解析、校验、聚合、上下文包生成、派生数据生成和受控写入中该 Tools 实际承担的职责。
9. 涉及 Git 文件事实源写入的 Tools，应测试写入前校验失败会阻止写入，并测试写入目标归属、格式契约、引用关系和 Human Gate 判断结果。
10. Tools 测试不得把测试生成物、快照或缓存提升为权威事实源；需要长期保留的稳定结论应按事实源边界写回对应位置。
11. 无法自动化覆盖的 Tools 行为，应在对应变更记录、任务证据或人工验收材料中说明原因、替代检查方式和验收结论。
12. Contract 变更后、Tools 实现和测试尚未同步更新时，Tools 输出应提示契约同步缺口，不得作为最终验收依据。

## 11. Tools 辅助层与 Web 信息同步层关系

1. Tools 辅助层可以为 Web 信息同步层生成派生视图数据。
2. 派生视图数据必须从 Git 文件事实源聚合生成，可追溯到事实源。
3. Web 信息同步层不得将 Tools 辅助层提供的派生视图数据作为权威事实源。
4. Web 信息同步层写入时，可调用 Tools 辅助层的受控写入能力，但不得绕过写入校验和 Human Gate。
5. Tools 辅助层不得承担页面布局、交互体验或人工确认工作台职责。

## 12. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. Tools 写入或覆盖 Git 文件事实源；
2. Tools 改变事实源归属；
3. Tools 将派生数据提升为稳定事实；
4. Tools 绕过 Rules、对象状态机、行动模型或 Human Gate；
5. Tools 引入持久化数据库作为派生层并影响事实源链路；
6. Tools 自动修改任务状态、关闭任务、修改 specs 规范、Rules 或修改其他高影响事实源。

Tools 辅助层检查至少包括：

| 检查项 | 标准 |
|---|---|
| 来源可追溯 | Tools 输入和输出可追溯到 Git 文件事实源 |
| 写入可追溯 | Tools 写入落到 Git 文件并可通过 Git 追溯 |
| 写入能力匹配 | 对应主模型流程、Skill 流程或 Web 入口存在可机械化写入步骤时，Tools 已具备对应受控写入能力，或已显式报告能力缺口和降级边界 |
| 缓存非权威 | 缓存、数据库和索引可重建且非唯一事实源 |
| 项目归属 | Tools 写入目标属于正确项目 |
| Gate 判断 | 高影响写入已评估 Human Gate |
| 校验覆盖 | 写入前校验已执行且通过 |
| AI 边界 | Tools 未直接调用 AI、Skill 或 Agent |
| 联动检查 | 涉及模型实践子文档时，已检查消费场景、Contract 依据、需求变更同步和 Skill / Web 依赖关系 |
| 测试验收 | `tools/` 下新增、修改或升级为 active 的 Tools 已补充或更新对应自动化测试，已执行测试并在任务证据或人工验收材料中记录测试命令和结果，无法自动化覆盖的行为已有替代检查说明和验收结论（依据 specs/22-Change-变更记录.md） |
