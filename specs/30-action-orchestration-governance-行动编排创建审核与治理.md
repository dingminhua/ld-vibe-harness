## 1. 行动定位与适用场景

行动编排创建、审核与治理是 LDVH 对具体行动编排规范主文件进行生命周期治理的行动编排。它回答三类问题：是否应该创建一个新的行动编排；一个 `specs/30-59` 行动编排主文件是否能被 AI 正确读取、识别、执行、暂停、验证、回写和维护；已存在的行动编排在修改、升级、降级、重命名、删除、能力消费和资产漂移时应如何治理。

本流程治理的是行动编排的产生依据、设计质量、消费边界和生命周期状态，不维护行动编排集合清单，不生成派生索引，不替代 Code 派生集合索引，也不替代 `specs/06-行动编排基础规范.md` 和 `specs/03.03-行动编排文档规范.md` 的通用规则。

本流程只处理目标对象作为行动编排的创建、审核与治理质量，不审核目标流程所涉及领域的业务质量、Code 实现质量、Rules 入口质量或 specs 全局价值判断。

本流程包含三条执行路径：

1. **创建路径**：判断是否应新增行动编排，并形成编号、命名、骨架、边界、接管关系和能力资产映射方案；
2. **审核路径**：判断行动编排主文件是否满足 active、消费、执行或修改前后的质量要求；
3. **治理路径**：处理修改、升级、降级、重命名、删除、编号迁移、能力资产漂移、入口引用同步和长期维护边界。

本流程遵守 06 §4.5.1 的主控 AI 判断与能力分工：主控 AI 承担行动编排生命周期治理的语义裁决，Code 只提供机械诊断证据，Skill 只提供可复用检查流程外壳，Agent 只提供独立审查视角，Human Gate 只处理高影响确认。本文只说明该分工在 `specs/30-59` 行动编排创建、审核与治理中的具体应用。

30 不是所有审核的总入口，也不是 Code 检查包装器。它只治理 `specs/30-59` 行动编排资产的生命周期；事实模型设计交给 41，基础规范质量交给 42，保障准备度交给 43，Git 提交执行交给 44。

以下场景应进入本流程：

1. 新增 `specs/30-59` 具体行动编排主文件前或创建后；
2. 修改已有具体行动编排主文件的 Context、Scenario、Gate、执行流程、回写、证据、能力协作或测试锚点后；
3. 将 planned、candidate、reserved 或 removed 状态的行动编排升级为 active 前；
4. 删除、重命名、移动、重排或降级具体行动编排主文件前；
5. Skill、Agent、Hook、Code、Web、CI 或入口资产准备消费某个具体行动编排前；
6. 执行中反复依赖聊天提醒、临时判断或人工补充来解释某个行动编排时；
7. Code 派生集合索引、骨架检查、引用检查或人工审查发现行动编排相关诊断时。

以下场景不应由本流程直接承接：

1. 只查询当前有哪些行动编排成员；该事项由 Code 派生索引和成员主文件自描述承接；
2. 只机械检查编号、路径、锚点或引用；该事项优先由 Code 承接；
3. 审核 specs 全局逻辑、价值观和 AI 可用性；该事项应由后续 specs 审核流程承接；
4. 审核 Code 实现质量和测试充分性；该事项应由后续 Code 审核流程承接；
5. 审核 Rules 入口资产是否漂移；该事项应由后续 Rules 入口审核流程承接；
6. 管理工作对象实例状态；该事项由 20-29 事实模型规范和后续对象管理流程承接。

相邻流程分流如下：

| 目标对象或问题 | 应进入 | 30 的处理边界 |
|---|---|---|
| `specs/30-59` 行动编排主文件、候选草案、状态迁移、编号治理、能力消费前检查 | 30 | 主路径 |
| `specs/20-29` 事实模型字段、状态机、实例事实源、对象关系或验收规则 | 41 | 30 只判断行动编排是否正确引用或分工，不审核事实模型本体 |
| `specs/00-19` 基础规范、文档治理、价值标准、引用纪律或规范保障声明写法 | 42 | 30 只判断行动编排是否承接上位规则，不审核基础规范质量 |
| 保障要求是否 ready、能力保障缺口、完整支持声明、环境适配准备度 | 43 | 30 可登记接管关系和能力映射，但不作 ready 结论 |
| Git commit 创建、拆分、message 预检、提交结果交还 | 44 | 30 不执行提交，只在行动编排治理产生文件修改后交由 44 |

## 2. 准入条件

进入本流程前，应满足以下条件之一：

1. 已存在目标行动编排主文件；
2. 已有待创建的行动编排草案、候选标题、编号意向或 Human 明确创建要求；
3. 已有 Code 诊断、入口漂移、引用缺失、骨架缺失、成员自描述缺失或执行失败线索；
4. 已有 Skill、Agent、Hook、Code、Web 或环境入口准备消费该行动编排；
5. 已发现某类行动反复依赖聊天记忆、临时提醒或无事实源判断。

不满足以上条件时，不应为了填补编号或维持顺序而创建、审核或治理行动编排。只存在抽象想法、一次性执行策略或尚未稳定的实践时，应先作为过程输出或候选材料；形成稳定事实后，再按事实类型和对象准入分流到 docs/studies、Spark、WorkCase、ADR 或其他权威位置。

### 2.1 创建、审核与治理依据检查

进入创建路径时，AI 必须先检查创建依据是否成立。创建依据至少应能回答：

1. 要控制的是哪一类 AI 行动，错误执行或漏执行会造成什么边界漂移；
2. 该候选流程命中 06 §5.4 的哪些准入条件；
3. 为什么现有 active 行动编排、事实模型、规范、Rules、Skill、Agent、Hook、Code 或 Web 不能充分承接；
4. 候选流程预期如何定义 Context、Scenario、Gate、执行、回写、证据、能力协作和可测试性锚点；
5. 编号、命名、状态、归属和 active 升级是否触发 Human Gate；
6. 若当前只存在想法、临时做法或一次性策略，应分流为过程输出、Spark、WorkCase、ADR、Pitfall 或 docs，而不是直接创建 active 行动编排。

进入审核路径时，AI 必须先检查审核对象和审核目的是否成立。审核依据至少应能回答：

1. 被审核对象是 active 主文件、候选草案、编号意向、迁移计划还是能力消费请求；
2. 本次审核用于 active 升级、变更后复核、能力消费前检查、Code 诊断处理还是人工语义审查；
3. 审核是否覆盖 Context、Scenario、Gate、执行流程、事实源回写、证据留存、能力协作、测试锚点和保障要求；
4. 审核是否需要 Code 诊断、Agent 独立审查、Human Gate 或人工降级检查；
5. 审核结论会影响哪些事实源、能力资产、环境入口或后续工作对象。

进入治理路径时，AI 必须先检查治理依据是否成立。治理依据至少应能回答：

1. 修改触发来自哪里，例如上位规范变化、执行失败、Code 诊断、能力资产消费失败、重复误判、Human Gate、事实源边界冲突或测试缺口；
2. 修改影响的是 Context、Scenario、Gate、执行流程、回写、证据、能力协作、环境适配、成员自描述、保障要求还是可测试性锚点；
3. 修改是否改变进入条件、停止条件、事实源边界、主控调度、Human Gate 或相邻行动编排边界；
4. 修改后需要同步哪些事实源和能力资产，例如 03.03、06、09、10、Rules、Skill、Agent、Hook、Code、Web、CI、适配措施或 Git 提交记录；
5. 修改能否通过本文 §14 的检查要求和 §12 的可测试性锚点复核。

没有创建、审核或治理依据时，AI 不得把“更完整”“更像流程”“编号可用”“以后可能会用”作为创建或修改行动编排的充分理由。

本流程的权威规则来自以下事实源：

| 内容 | 权威位置 |
|---|---|

| 目录、编号和文件归属 | `specs/01-目录说明.md` |
| 能力资产边界 | `specs/04.02-LDVH能力资产与保障机制规范.md` |
| Code 实现与派生索引边界 | `specs/07-Code确定性执行实现规范.md` |
| 事实源、证据和回写边界 | `specs/09-事实源边界与承载规范.md` |

本流程不得恢复手写集合索引，不得把 `docs/studies/` 中的评估记录当作行动编排成员事实源，不得用 Code 派生索引替代成员主文件正文。

## 4. Context 要求

执行本流程前，AI 应按最小可行动原则准备以下 Context：

1. `../rules/LDVH-MAINTAINER-ENTRY.md` 中与行动编排场景路由、Code 查询入口、STOP 点和维护规则相关的段落；
2. `specs/06-行动编排基础规范.md` 中行动编排定义、标准组成、准入、Context、Scenario、Gate、能力协作、事实源回写、证据留存、30-59 关系和检查要求；
3. `specs/03.03-行动编排文档规范.md` 中适用文件、成员自描述契约、文档骨架、可测试性锚点、环境适配边界和检查要求；
4. `specs/01-目录说明.md` 中 30-59 编号区段、成员自描述与 Code 派生索引边界；
5. `specs/07-Code确定性执行实现规范.md` 中成员集合派生索引边界、Code 输出边界和验证规则；
6. 目标行动编排主文件或候选草案；
7. 必要时读取 `specs/04.02-LDVH能力资产与保障机制规范.md`、`specs/09-事实源边界与承载规范.md` 和 `specs/11-测试基础规范.md`；
8. 必要时运行 `python3 code/specs_validate.py index`、`python3 code/specs_validate.py doc specs`、`python3 code/specs_validate.py refs specs`、`python3 code/specs_validate.py assurance specs` 或 `python3 code/specs_validate.py all` 获取导航和诊断。

若目标流程尚未创建，AI 只能审核候选草案和创建方案，不得声称该流程已经是 active 成员。若无法定位目标文件、上位规范或必要诊断来源，应暂停并说明缺口。

## 5. Scenario 识别

AI 遇到以下信号时，应识别为行动编排创建、审核与治理场景：

1. 用户要求创建、修改、删除、重排或评价行动编排；
2. 用户提到 30-59、行动编排主文件、Scenario、Context、Gate、回写、证据、测试锚点或流程是否好用；
3. 当前任务涉及 planned、candidate、reserved、removed 与 active 状态切换；
4. Code 派生索引报告行动编排成员自描述、编号、路径、锚点或骨架诊断；
5. 入口资产、Skill、Agent、Hook、Code 或 Web 准备引用某个行动编排；
6. 某个流程看起来像泛化说明、索引、Skill 说明、规范正文拼贴或临时经验汇总；
7. 某个流程执行时无法判断该读什么、何时暂停、如何验证、证据写哪里或失败如何降级。

多个场景同时命中时，应先判断是否存在更具体的 active 行动编排。若没有更具体的 active 行动编排，或目标就是创建、审核或治理行动编排生命周期，则进入本流程。

## 6. 执行流程

行动编排创建、审核与治理先执行通用步骤，再按目标选择创建、审核或治理路径。

通用步骤：

1. **确认目标**：确认对象是待创建流程、已存在主文件、候选草案、编号意向、迁移计划、变更请求还是能力消费请求；
2. **选择路径**：按 §2.1 判断应进入创建路径、审核路径、治理路径，或因不满足准入而分流；
3. **确认权威依据**：读取或定位 06、03.03、01、07 和目标文件，必要时补充 04.02、09、10、11；
4. **运行确定性诊断**：优先运行或参考 Code 派生索引、文档结构、引用、保障要求和综合校验结果；
5. **识别 Gate**：判断是否涉及新增 active、编号迁移、删除重命名、成员契约变化、长期降级、能力资产边界变化或环境入口影响。

创建路径：

1. **检查创建依据**：判断候选行动是否命中 06 的准入条件，是否确实控制 AI 的读取、判断、执行、暂停、验证、回写或维护行为；
2. **排除替代承接**：检查现有 active 行动编排、事实模型、正式规范、Rules、Skill、Agent、Hook、Code、Web 或 CI 是否已能承接；
3. **确定编号与命名**：按 01、03.03 和 06 选择 30-59 编号、英文名、中文名、状态和 canonical path；
4. **形成主文件骨架**：写入 `ldvh_doc`、`ldvh_member`、Context、Scenario、Gate、执行流程、回写证据、环境适配边界、可测试性锚点、保障要求和检查要求；
5. **声明接管与能力映射**：需要接管正式规范保障要求时填写 `assurance_takeover`；需要固定能力保障时填写 `capability_assets`，并推动对应资产创建、修改、验证或降级；
6. **触发必要 Gate**：新增 active、编号占用、命名、状态升级或能力资产落地影响长期行为时，应触发 Human Gate。

创建路径中，主控 AI 必须完成以下实质判断：

1. 候选对象是否真的应成为行动编排，而不是事实模型、基础规范、Skill、Code、入口提示、一次性过程输出或 docs/studies 材料；
2. 候选流程若不结构化，是否会造成 AI 行动边界漂移，例如误读上下文、绕过 Gate、错误回写、能力越权或无法留证；
3. 现有 active 行动编排、事实模型、规范、Rules、Skill、Agent、Hook、Code、Web 或 CI 是否已经足够承接，新增流程是否会制造重复治理；
4. 候选流程的 Context、Scenario、Gate、执行、回写、证据和可测试性锚点是否构成最小且完整的行动控制闭环；
5. 编号、命名、状态、canonical path 和 active 升级是否合理，是否触发 Human Gate；
6. 候选流程是否需要能力资产保障，以及能力需求应落到 Rules、Skill、Agent、Hook、Code、Web、CI、命令入口还是环境适配。

上述判断不得由 Code 或 Skill 代替。Code 可以列出现有成员、检查编号冲突和骨架缺口；Skill 可以提供分流问题和输出模板；最终创建结论必须由主控 AI 基于事实源、风险、替代承接和 Human Gate 作出。

审核路径：

1. **审核成员自描述**：检查 `spec_id`、`kind`、`name_en`、`name_zh`、`collection_status`、`canonical_path`、必需锚点和 `code_consumption` 是否完整一致；
2. **审核文件归属**：检查文件名、编号、区段、标题和 canonical path 是否符合 01、03.03 和 06；
3. **审核行动定位**：判断该内容是否确实需要控制 AI 行动，是否不成为行动编排就会导致边界漂移；
4. **审核适用与不适用场景**：检查 Scenario 是否可识别，是否排除了不该进入该流程的场景；
5. **审核 Context**：检查流程是否给出最小可行动上下文，是否能回指 Git 文件事实源，是否避免全文泛读和聊天记忆依赖；
6. **审核 Gate**：检查停止、确认、降级、Human Gate 和条件 Gate 是否明确，是否存在绕过授权或事实源边界的风险；
7. **审核执行步骤**：检查步骤是否可操作、顺序是否合理、是否能被 AI 按步骤执行，而不是只陈述理念；
8. **审核能力协作**：检查 Skill、Agent、Hook、Code、Web、CI 和入口资产的参与是否符合 04.02、07、08 和 06 的主控唯一调度原则；
9. **审核事实源回写与证据**：检查稳定事实、过程输出、验证证据、Human Gate 记录和后续分流是否有明确归属；
10. **审核行动特有可测试性锚点**：检查正向场景、负向场景、Gate 场景、回写场景、失败降级和回归风险是否可验证；
11. **审核保障要求**：检查规范保障要求表是否说明同步、检查或审计触发条件，且没有制造无法保障的部署适配承诺。

审核路径中，主控 AI 必须完成以下实质判断：

1. 目标文件的行动定位是否成立，是否确实控制 AI 的读取、判断、执行、暂停、验证、回写或维护行为；
2. Scenario 是否足够真实、可识别、可触发，不适用场景是否能防止误进入；
3. Context 是否遵守最小可行动原则，能回指 Git 文件事实源，且没有依赖聊天记忆、派生索引、工具摘要或 Web 视图替代原文；
4. Gate、Human Gate、暂停、降级和失败处理是否覆盖真实高风险点；
5. 执行步骤是否真的可操作、顺序是否合理、是否避免只写理念、口号或泛化原则；
6. Skill、Agent、Code、Web、Hook 或 CI 是否被写成事实源、授权者、主控替代物或环境已支持声明；
7. 事实源回写、证据留存和过程输出分流是否正确，稳定事实应进入哪个权威位置；
8. 审核结论应为 `pass`、`pass_with_followups`、`blocked`、`needs_human_gate` 还是 `not_applicable`。

Code 诊断为零不等于审核通过。只要存在 Scenario 不可识别、Gate 不可执行、回写位置不清、能力越权、事实源分叉、流程只写理念或 Human Gate 缺失，主控 AI 仍必须判为 `blocked` 或 `pass_with_followups`，并说明原因。

治理路径：

1. **确认治理触发**：确认修改、升级、降级、重命名、删除、迁移、能力消费、资产漂移或入口引用变化的触发来源；
2. **评估影响范围**：判断是否影响进入条件、停止条件、事实源边界、主控调度、Human Gate、相邻行动编排、能力资产或环境适配；
3. **同步关联事实源**：按影响范围同步 03.03、06、09、10、Rules、Skill、Agent、Hook、Code、Web、CI、适配措施、测试或 Git 提交记录；
4. **处理状态与迁移**：planned、candidate、reserved、removed 与 active 状态变化必须保持成员自描述、旧编号占位、替代关系和 Code 派生诊断一致；
5. **处理能力资产漂移**：当 `capability_assets` 与实际资产、`ldvh_asset`、验证命令或环境适配边界不一致时，应修订映射、资产或降级说明；
6. **复跑验证并形成结论**：目标文件或相关资产被修改后，应重新运行相关校验命令，并按 §10 记录结果、残留风险和下一步分流。

治理路径中，主控 AI 必须完成以下实质判断：

1. 治理触发是否成立，例如上位规范变化、执行失败、重复误判、Code 诊断、能力资产漂移、入口引用变化或 Human Gate 结论是否足以启动治理；
2. 变更是否影响进入条件、停止条件、事实源边界、主控调度、Human Gate、相邻行动编排职责或能力资产边界；
3. planned、candidate、reserved、removed 与 active 状态变化是否允许，旧编号、替代关系和迁移说明是否需要保留；
4. 删除、重命名、移动、重排编号或长期降级是否触发 Human Gate，可选处理方式和推荐分流是什么；
5. `assurance_takeover`、`capability_assets`、资产元信息、验证命令、部署边界和实际可用性是否仍匹配；
6. 需要同步哪些事实源和能力资产，例如 03.03、06、09、10、Rules、Skill、Agent、Hook、Code、Web、CI、适配措施、测试或 Git commit records；
7. 验证不足时能否降级继续、必须 blocked，还是需要创建 Spark、WorkCase、ADR、Pitfall 或 docs 记录；
8. 治理完成后是否允许能力消费、入口引用或后续执行继续使用该行动编排。

Code 可以辅助发现引用、格式、路径、锚点和资产登记问题，但不得批准生命周期状态流转、能力边界变化、长期降级或删除迁移；Skill 可以给出治理清单和交还格式，但不得成为治理事实源或最终裁判。

## 7. Gate 触发条件

出现以下情况时，AI 必须暂停继续宣称审核通过，并按影响范围触发 Human Gate、降级检查或后续分流：

1. 新增 active 行动编排主文件；
2. 删除、重命名、移动或重排 30-59 行动编排编号；
3. 改变成员自描述契约、active 判定条件、集合状态语义或 Code 派生索引消费方式；
4. 让某个流程承担手写集合索引、事实源替代、Code 授权、Human Gate 替代或 Skill/Agent 直接生效职责；
5. 目标流程与 00、01、03.03、06、07、09 或 10 冲突；
6. 目标流程缺少成员自描述、必需锚点、Gate、回写、证据或可测试性锚点，却被要求标记为 active；
7. 审核需要接受长期降级、跳过验证、关闭 open/degraded 缺口或绕过 Code 诊断；
8. Code 诊断、Git 文件事实源、入口资产或目标流程正文之间存在冲突；
9. 审核结论会影响 Skill、Agent、Hook、Code、Web 或环境入口的长期行为边界。

Gate 触发时，AI 应说明触发原因、影响范围、可选处理方式、推荐分流和需要 Human 确认的具体事项。Human 确认形成稳定事实时，应按 06 的 Human Gate 最小字段记录时间、决策、范围和约束。

## 8. Skill 和 Agent 调度

本流程默认由主控 AI 执行。只有当审核任务可复用、复杂、争议大或需要独立上下文时，才考虑 Skill 或 Agent 辅助。

Skill 适合承接：

1. 固定审核清单；
2. 标准化输出格式；
3. 常见失败分类；
4. 交还主控的修订建议；
5. 重复执行的行动编排创建、审核与治理 SOP。

若后续创建 `ldvh-action-orchestration-governance` Skill，它只封装本文的最小读取顺序、创建/审核/治理检查问题、输出格式、STOP 点和交还方式。该 Skill 的通用边界遵守 06 §4.5.1 和 04.02：它不得替代主控 AI 的治理结论，不得新增稳定规则，不得成为 Code wrapper，不得复制本文正文，不得默认调度 Agent，不得替代 Human Gate。

Agent 适合承接：

1. 复杂语义自洽审查；
2. 行动编排是否符合 00 价值标准的独立判断；
3. 多个流程之间职责冲突分析；
4. 候选流程是否应独立成流程的争议分析；
5. 高风险流程创建、审核或治理方案的并行审阅。

Skill 和 Agent 输出均为过程输出，必须交还主控。Skill 不得自行调度 Agent，Agent 输出不得直接生效，不得绕过 Human Gate、Code 诊断、事实源回写或主控判断。

## 9. Code 与命令入口协作适配

本流程优先使用 Code 完成可机械化检查。Code 适合承接：

1. 30-59 成员主文件发现；
2. 成员自描述字段解析；
3. 编号、路径、标题和 canonical path 一致性检查；
4. active 流程必需锚点检查；
5. 文档结构和章节骨架检查；
6. specs 引用检查；
7. 规范保障要求表结构检查；
8. 派生集合索引、状态清单和冲突诊断。

常用命令包括：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py assurance specs
python3 code/specs_validate.py all
```

Code 输出只作为导航、聚合和诊断结果。Code 不判断流程是否符合价值观、是否语义自洽、是否真的好用，也不生成授权。Code 不可用、诊断不完整或输出无法回指事实源时，应退回人工检查并记录残留风险。

**审查边界声明**：本流程只审查目标行动编排文档中写的规范要求是否合理、完整、一致、可执行；不审查项目中是否已实际满足这些要求。Code 的作用仅限于帮助 AI 检查目标文档的机械属性（成员自描述、编号、路径、骨架、引用、锚点、保障要求表结构），Code 输出不构成"该行动编排在项目中已被满足"的证据。

按 06 §4.5.1，即使 Code 诊断为空，主控 AI 仍必须独立判断行动价值、Scenario 可识别性、Context 可用性、Gate 有效性、执行步骤可操作性、能力协作边界、事实源回写和证据留存是否成立。若这些语义条件不成立，应按 §10 输出 `blocked`、`needs_human_gate` 或 `pass_with_followups`，不得以 Code 通过替代治理结论。

## 10. 事实源回写与证据留存

本流程执行后的过程输出应至少说明：

1. 治理对象；
2. 读取的权威依据；
3. 运行的 Code 命令或人工降级检查；
4. 发现的问题；
5. 行动价值审查小结，说明该流程如何改善 Context、Scenario、Gate、执行、验证、回写或学习闭环，主要服务的 V1-V10 项、未发现的价值偏离和残留风险；
6. 创建、审核或治理结论；
7. 是否触发 Human Gate；
8. 是否修改目标文件或生成后续工作对象；
9. 残留风险和下一步分流。

创建路径输出应额外说明：

1. 是否建议创建行动编排，以及建议状态为 active、candidate、planned、reserved 还是不创建；
2. 推荐编号、英文名、中文名、canonical path 和命名理由；
3. 与现有 active 行动编排、事实模型、规范和能力资产的边界；
4. 初始 Context、Scenario、Gate、执行、回写、证据和测试锚点摘要；
5. 需要接管的保障要求、需要登记的 `capability_assets`、需要创建或修改的能力资产；
6. 需要同步的 specs、Rules、Skill、Agent、Hook、Code、Web、CI、环境适配或测试。

审核路径输出应额外说明：

1. 成员自描述、文件归属、Context、Scenario、Gate、执行、回写、证据、能力协作和测试锚点是否通过；
2. Code 诊断、人工语义审查、Agent 审查或降级检查的结论；
3. 是否允许 active、允许能力消费、允许继续执行或必须 blocked；
4. 必须修复项、不阻塞 followups 和残留风险。

治理路径输出应额外说明：

1. 治理触发来源和影响范围；
2. 状态变化、编号迁移、重命名、删除、降级或替代关系；
3. `assurance_takeover`、`capability_assets`、入口引用、能力资产和验证命令是否漂移；
4. 已同步和未同步的事实源、资产、实现、测试与 Git 提交记录；
5. 需要 Human Gate 的事项和后续分流。

审核结论分为：

| 结论 | 含义 |
|---|---|
| `pass` | 未发现阻塞问题，且必要验证通过 |
| `pass_with_followups` | 可继续使用，但存在不阻塞的后续改进项 |
| `blocked` | 存在阻塞问题，不得标记为通过或 active |
| `needs_human_gate` | 需要 Human 确认后才能继续 |
| `not_applicable` | 当前对象不属于行动编排创建、审核与治理范围 |

稳定事实回写规则如下：

1. 目标行动编排正文需要调整时，回写对应 `specs/30-59` 主文件；
2. 审核形成缺口、后续工作线索或后续行动时，回写 Spark 或 WorkCase；
3. 审核形成长期决策时，回写 ADR；
4. 审核形成可复用踩坑经验时，回写 Pitfall；
5. 审核形成研究报告或迁移说明时，回写 docs；
6. 发生事实源修改时，按 10 的 Git 和 commit message 格式规则处理。

凡回写为 WorkCase 的后续行动，必须按 `specs/21-WorkCase-工作项.md` 和 `specs/05.02-字段内容与格式规范.md` 填写 `success_criteria`、`orchestration.execution_items`、`verification_evidence` 与 `closure_evidence` 等字段；流程步骤不得新建 TaskPlan、Task 或 SubTask，执行期拆分只能作为 WorkCase 内部 `execution_items`。

不得把聊天中的“看起来可以”“应该合格”“已审核”当作完成证据。关键结论必须能回指规范、目标文件、命令输出、Human Gate 或事实源差异。

## 11. 环境适配边界

本流程可以被 Rules 入口提示、Skill SOP、Agent 审查、Code 校验、Web 展示、Hook 提醒或 CI 检查辅助，但这些能力不得替代本流程正文。

环境适配边界如下：

1. Rules 入口只提示何时读取本流程和相关规范，不复制流程全文；
2. Skill 可以封装固定审核清单，但不新增稳定规则；
3. Agent 可以提供独立语义审查，但不直接生效；
4. Code 可以提供确定性诊断，但不替代 AI 语义判断和 Human Gate；
5. Web 可以展示审核状态、诊断和 Human Gate 入口，但不维护第二事实源；
6. Hook 或 CI 可以提醒或阻断高风险变更，但触发不等于检查通过；
7. CI 属于保障机制，不是固定文本能力资产类型；
8. 环境能力缺失时，应降级为人工检查并记录残留风险。

## 12. 行动特有可测试性锚点

本流程的关键行为应能通过正例、反例、Gate 场景、回写场景和命令验证进行检查。

正向场景：

1. 目标流程有合法成员自描述；
2. 文件名、编号、标题和 canonical path 一致；
3. active 流程包含 Scenario、Context、Gate、执行流程、回写、证据和可测试性锚点；
4. 能力协作边界清楚；
5. Code 校验无阻塞诊断；
6. 审核结论能回指事实源和验证结果。

负向场景：

1. 缺少成员自描述；
2. `spec_id` 与文件名编号不一致；
3. planned 或 candidate 被当作 active 执行；
4. 恢复手写集合索引，或创建只说明集合发现方式但不定义行动规则的启动/索引型流程；
5. 流程只写理念，没有可执行步骤；
6. 缺少 Gate、事实源回写、证据留存或失败降级；
7. Skill、Agent、Code、Web 或 Hook 被写成事实源或授权者。

Gate 场景：

1. 新增 active 流程；
2. 改变 30-59 编号归属；
3. 删除、重命名或移动行动编排主文件；
4. 接受长期降级或跳过关键验证；
5. 改变能力资产边界或事实源边界。

回写场景：

1. 审核发现正文缺陷，应回写目标行动编排主文件；
2. 审核发现后续改进项，应回写工作对象或 docs；
3. 审核发现长期决策，应回写 ADR；
4. 审核发现可复用误判，应回写 Pitfall；
5. 审核只产生临时建议时，应明确其为过程输出。

修改本流程或目标流程后，至少应运行：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py assurance specs
python3 code/specs_validate.py all
```

无法运行自动化校验时，应说明原因、采用的人工检查方式和残留风险，不得声称完整验证。Code 命令输出仅辅助机械属性检查，不替代 AI 对价值与规范的判断。

## 13. 规范保障要求

本文通过以下规范保障要求说明相关要求的同步、检查或审计触发条件。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 行动编排创建、审核与治理应承接 06 的行动编排通用规则和 03.03 的行动编排文档骨架、成员自描述契约、可测试性锚点 | 本文、06、03.03、Human Gate | 行动编排治理 | 新增、修改、升级、降级、删除、重命名或审查 30-59 行动编排时 |
| 入口可见要求 | AI 处理行动编排创建、审核、治理、变更或质量审查时应能定位本文 | Rules 入口、06、03.03、Code 派生索引 | AI 执行入口提示 | 行动编排场景路由、成员主文件、入口资产或 Code 查询入口变化时 |
| 流程复用要求 | 高频行动编排创建、审核与治理可以封装为 Skill，但 Skill 不得新增稳定规则或默认调度 Agent | Skill SOP、主控交还、人工降级检查 | 流程复用 | 行动编排创建、审核与治理反复执行且步骤稳定时 |
| 子 Agent 思考要求 | 复杂语义自洽、价值观一致性或流程职责冲突可由 Agent 辅助审查，但 Agent 输出必须回主控 | Agent 审查、主控复核、Human Gate | 子 Agent 思考 | 行动编排创建、审核或治理存在争议、高风险或跨流程冲突时 |
| 确定性执行要求 | Code 应检查成员自描述、编号、路径、锚点、章节、引用和保障要求表，并生成派生集合诊断 | `code/spec_checks/index.py`、`code/specs_validate.py`、测试或等价验证 | 校验实现 | 行动编排成员字段、骨架、锚点、引用或校验规则变化时 |

| 生命周期触发要求 | 本流程或目标行动编排变化后，应检查入口资产、06、03.03、07、09、10、Code、测试、Skill、Agent、Hook、Web 是否需要同步 | Code 校验、人工降级检查、能力资产边界审查 | 触发保障 | Context、Scenario、Gate、执行流程、回写、证据、能力协作、测试锚点或成员自描述变化时 |

## 14. 检查要求

行动编排创建、审核与治理至少包括：

| 检查项 | 标准 |
|---|---|
| 对象归属 | 治理对象属于 `specs/30-59` 行动编排主文件、候选草案、编号意向、迁移计划、变更请求或能力消费请求 |
| 成员自描述 | `spec_id`、`kind`、`name_en`、`name_zh`、`collection_status`、`canonical_path`、锚点和 `code_consumption` 完整一致 |
| 文件命名 | 文件名符合 `NN-{英文名}-{中文名}` 这类 Markdown 文件命名模式，且不重复“行动编排规范”字样 |
| 状态边界 | 只有 active、主文件存在、骨架检查通过且锚点完整的流程可被执行 |
| 新增或修改依据 | 创建或修改行动编排的触发来源、准入条件、替代承接判断、影响范围、同步对象和 Human Gate 已说明；不得只因编号空缺、临时便利或措辞偏好创建或修改 |
| 行动定位 | 该流程确实控制 AI 读取、判断、执行、暂停、验证、回写或维护行为 |
| 行动价值 | 说明该流程如何改善 AI 的 Context、Scenario、Gate、执行、验证、回写或学习闭环，主要服务哪些 V1-V10 项，且未以流程数量、步骤数量或能力实体数量替代价值标准 |
| Scenario | 进入条件和不适用场景明确，可被 AI 识别 |
| Context | 最小可行动上下文清晰，可回指事实源 |
| Gate | 停止、确认、降级和 Human Gate 条件明确 |
| 执行流程 | 步骤可操作，顺序合理，不只是理念说明 |
| 能力边界 | Skill、Agent、Hook、Code、Web、CI 和入口资产未互相替代或越权，CI 未被写成固定文本能力资产类型 |
| 事实源边界 | 过程输出、派生索引、工具结果、Agent 输出和 Web 状态未替代 Git 文件事实源 |
| 证据留存 | 审核结论、验证命令、Human Gate、修改结果和残留风险可追溯 |
| 可测试性锚点 | 正例、反例、Gate、回写、失败降级和回归风险明确 |
| 保障要求 | 保障要求表说明同步、检查或审计触发条件，未制造无法保障的承诺 |
| 验证结果 | 相关 Code 校验命令已运行或已说明无法运行的原因、采用的人工检查方式和残留风险；Code 诊断仅辅助机械属性检查，不替代 AI 对价值与规范的判断 |
