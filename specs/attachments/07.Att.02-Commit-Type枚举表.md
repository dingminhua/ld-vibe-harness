## 1. 定位

本文承载 07 授权的 commit type 严格闭集。

07 正文定义 Git commit records 的事实源追溯性质和 commit message 契约；本文只维护 type 枚举，不得定义 scope 允许枚举、body 必填条件、提交样例、AI 提交流程、Hook 接入或 Code 输出 Schema。

## 2. Type 闭集

| type | 简体中文 | English | 含义 |
|---|---|---|---|
| `feat` | 新增功能 | Feature | 新增功能、能力或用户可见对象 |
| `fix` | 问题修复 | Fix | 修复缺陷、错误或不符合预期的行为 |
| `docs` | 文档修改 | Documentation | 修改文档、规范、规则入口或其他文档性事实源 |
| `style` | 格式调整 | Style / formatting | 代码格式、空白、排版等不影响语义的修改 |
| `refactor` | 代码重构 | Refactor | 重构，不改变外部行为 |
| `perf` | 性能优化 | Performance | 性能优化 |
| `test` | 测试修改 | Tests | 测试相关修改 |
| `build` | 构建系统 | Build | 构建系统、依赖或打包相关修改 |
| `ci` | 持续集成 | Continuous integration | CI 配置或流水线修改 |
| `chore` | 维护杂项 | Chore / maintenance | 辅助维护、杂项或难以归入其他类型的非功能变更 |
| `revert` | 回退变更 | Revert | 回退之前的提交 |

## 3. 使用规则

`type` 必须只有一个，表示本次提交的主变更意图或动作类别。一个提交如果同时包含多个彼此独立的意图，应拆成多个提交；一个原子闭环需要同时修改 specs、Code、Web、docs 或测试时，应选择最能代表闭环目的的主 `type`，其它影响写入 body。

不得使用枚举外内容。不得使用 `improve`、`update`、`完善`、`优化` 这类含义不稳定的 type。所谓“完善”必须按实际变更目的落入明确类型：新增能力用 `feat`，修复问题用 `fix`，规范、规则或 ADR 文本修改用 `docs`，代码结构整理用 `refactor`，维护性调整用 `chore`。

## 4. 辅助核对表

| 核对项 | 标准 |
|---|---|
| 闭集命中 | `type` 属于本文 §2 |
| 单主语义 | 首行只有一个 `type` |
| 不拼接 | 未使用 `feat+docs`、`feat,fix` 或其它拼接规避取舍 |
| 语义稳定 | 未使用“优化”“完善”“更新”作为 type |
