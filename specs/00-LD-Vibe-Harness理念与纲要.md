## 一、LD Vibe Harness 为什么存在

LD Vibe Harness 是面向 Vibe Coding 的工程化驾驭框架，由 LaoDing 基于 Trae Solo 开发实践。

Vibe Coding 让人用自然语言描述需求，AI 快速生成代码，人负责验收和调方向。它快、自由、低门槛，但天生有三大硬伤：非确定性、幻觉和无记忆。没有约束的 Vibe Coding 容易停留在原型阶段，不敢上生产，不敢长期维护。

LD Vibe Harness 要解决的问题，就是把"随性的 AI 编程"变成"可控、可复用、可交付的工程流程"。

它的方法，是以约束体系划定边界，以事实源沉淀记忆，以工具链连接能力，以工作流驱动执行，以任务治理守住交付，以可视化工具桥接信息——让人的自然语言意图通过规则、事实源、工具链和工作流，转化为可规划、可执行、可验证、可沉淀的 AI 工程闭环。

LD Vibe Harness 关注的核心问题是：

```text
AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。
```

## 二、第一服务对象

LD Vibe Harness 以 AI 执行者为第一服务对象，整个体系围绕"帮助 AI 高效、准确、可控地工作"来设计。

这不意味着人和工具处于次要位置，而是说 LD Vibe Harness 的信息组织方式、事实源结构、任务格式、规则入口和工具能力，首先要满足 AI 的读取、理解、场景识别、拆解、执行、检查和事实回写需要。

因此，LD Vibe Harness 不只为 AI 提供上下文，还要为 AI 提供场景识别、工具选择、Skill 进入、子 Agent 调度和人类确认的行动依据。

在这个前提下，LD Vibe Harness 的架构分为三个逻辑层次：底层确保 AI 能基于事实源稳定行动；中间层通过 Human Gate 让人确认关键节点；上层通过工具降低人和 AI 维护事实源的成本。

人在 LD Vibe Harness 中负责：

1. 表达意图；
2. 补充约束；
3. 确认关键节点；
4. 校正 AI 判断；
5. 验收结果。

AI 负责：

1. 读取项目上下文；
2. 识别当前任务场景和事实源边界；
3. 判断需要使用的工具、Skill 或子 Agent；
4. 拆解和执行任务；
5. 识别需要人确认的节点；
6. 记录执行证据；
7. 按事实源边界写回项目。

工具负责：

1. 读取事实源；
2. 聚合事实源；
3. 校验事实源；
4. 提供受控写入入口；
5. 降低人和 AI 维护结构化文件的成本。

## 三、架构：介质层 + 三层能力

LD Vibe Harness 的架构由一个贯穿层和三个能力层构成。介质层是三层共同依赖的行业标准，三层能力各有归属、各有角色、各有规范边界。

### 3.1 介质层

YAML、Markdown、Python、JavaScript 等文件格式和编程语言是行业标准介质，不属于任何一层，但被三层共同使用。

介质层的核心特征：

1. **行业标准**：介质本身的语法和规范由行业标准定义，不属于 Trae、Harness 或项目；
2. **Harness 定义使用规则**：Harness 在 10-事实源规范中定义这些介质的使用规则（什么时候用 YAML、什么时候用 Markdown、字段契约怎么定义），但不重新定义介质本身；
3. **三层共用**：Trae Solo 环境通过 .md 文件落地 Rules、Skill、Agent 定义；Harness 工具通过 .py 程序落地 Web 后端和辅助脚本；Harness 对象通过 .yaml / .md 文件落地 Task、ADR、Pitfall 实例。

### 3.2 三层能力定义

| 层 | 英文 | 归属 | Harness 的角色 | 举例 |
|---|---|---|---|---|
| Trae Solo 环境 | Trae Solo Environment | Trae 提供 | 利用，不重新定义 | Rules、Skill、Agent、MCP、Tool Calling |
| Harness 工具 | Harness Tools | Harness 提供 | 实现和维护 | Web Tools、Python 辅助程序 |
| Harness 对象 | Harness Objects | Harness 定义规范，项目实例化 | 定义规范 | Task、Memo、ADR、Pitfall |

### 3.3 Trae Solo 环境

Trae Solo 提供了 Rules、Skill、Agent、MCP、Tool Calling 等原生机制，它们是 LD Vibe Harness 可以利用的基础能力，但机制本身不会自动形成工程驾驭能力，也不会天然约束 AI 行为。

LD Vibe Harness 对 Trae Solo 环境的态度：

1. **利用不重新定义**：Harness 定义如何使用 Trae 原生机制（规范层），不重新定义机制本身；
2. **规范不替代**：Harness 的 Rules、Skill、Agent 设计规范，是对 Trae 原生机制的使用约束和最佳实践，不是替代 Trae 的机制；
3. **适配不绑定**：Harness 的规范体系适配 Trae Solo 的能力模型，但不假设 Trae 是唯一可用的 AI 编程环境。

### 3.4 Harness 工具

Harness 工具是 LD Vibe Harness 自身提供的能力，用于桥接 AI 优先的结构化信息和人的可读可操作需求。

Harness 工具包括：

1. **Web Tools**：可视化工具，把 AI 优先的结构化信息（YAML、Markdown）转化为人可读、可操作的界面，桥接信息；
2. **Python 辅助程序**：解析、校验、聚合和受控写入事实源，降低人和 AI 维护结构化文件的成本。

Harness 工具的边界：

1. 工具可以降低维护成本，但不能成为最终事实源；
2. 工具可以提供受控写入入口，但不能绕过事实源边界和 Human Gate；
3. 工具可以聚合展示，但不能独立维护与事实源冲突的派生数据。

### 3.5 Harness 对象

Harness 对象是 LD Vibe Harness 定义规范的结构化事实实体。Harness 定义对象的规范（状态机、字段契约、事实源边界、准入条件），项目按规范创建实例。

Harness 对象的核心特征：

1. **规范由 Harness 定义**：对象的状态机、字段契约、事实源边界和准入条件由 Harness 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的对象实例属于项目，存放在项目的 ld-base/ 目录中；
3. **生命周期受治理**：对象的创建、状态变更、验收和关闭受任务治理和 Human Gate 约束。

Harness 对象的权威定义、对象地图、对象关系和对象事实源边界，由 14-Harness 对象规范和 20-49 Harness 对象实践展开。本文只说明 LD Vibe Harness 必须以对象为基础组织事实源、工具辅助和 AI 协作，不在总纲中重复维护对象清单或对象状态。

### 3.6 介质层与三层能力的关系

```text
介质层（YAML / Markdown / Python / JavaScript，行业标准）
  ↕ 三层共用
Trae Solo 环境（提供原生机制，通过 .md 落地）
  ↓ Harness 定义使用规范
Harness 工具（桥接 AI 和人，通过 .py / .js 落地）
  ↓ 工具读写 Harness 对象
Harness 对象（承载项目事实，通过 .yaml / .md 落地）
  ↓ AI 和人通过工具操作对象
```

三层协作的核心闭环：

1. 介质层提供行业标准格式，三层按各自规则使用；
2. Trae Solo 环境提供 Rules、Skill、Agent 等原生机制；
3. Harness 定义这些机制的使用规范，并构建工具链和工作流；
4. Harness 工具桥接 AI 优先的结构化信息和人的可读可操作需求；
5. Harness 对象承载项目事实，AI 和人通过工具操作对象；
6. 人的意图通过规则、事实源、工具链和工作流，转化为可规划、可执行、可验证、可沉淀的 AI 工程闭环。

## 四、事实源原则

LD Vibe Harness 的事实源必须是 Git 可追踪文件。

聊天记录、临时 UI 状态、工具缓存、数据库派生视图都不能成为 LD Vibe Harness 的最终事实源。

基础原则：

1. 事实必须能被 AI 读取；
2. 事实必须能被人审查；
3. 事实必须能被工具解析或聚合；
4. 事实必须能通过 Git 追溯变化；
5. 同一事实只能有一个权威位置，原则上不能出现多个事实源。

YAML 更适合承载任务、状态、结构化关系、审计字段和可解析决策。Markdown 更适合承载背景、原因、解释、需求语境和规范说明。

当一个事实需要高频被 AI 读取、被程序校验或被工具聚合时，应优先考虑结构化承载。

---

## 五、协作闭环

LD Vibe Harness 的协作关系不是"工具替人管理项目"，也不是"AI 凭聊天记忆持续推进"，而是"人、AI、工具围绕 Git 文件事实源形成执行闭环"。

```text
人表达意图、约束或确认
  ↓
AI 识别场景和事实源边界
  ↓
AI 读取事实源，并判断是否需要工具、Skill 或子 Agent
  ↓
AI 拆解、执行、检查任务
  ↓
工具辅助解析、校验、聚合和受控写入
  ↓
执行证据、检查结果或决策回到 Git 文件事实源
  ↓
Web Tools 展示状态、待确认事项和检查结果
  ↓
人基于事实源追踪、确认、验收或调整方向
```

这个闭环必须满足：

1. 起点可以来自人的对话输入，但终点必须回到文件事实源；
2. AI 可以调度工具、Skill 或子 Agent，但不能绕过事实源和人类确认门禁；
3. 工具可以降低维护成本，但不能成为最终事实源；
4. 人可以通过 Web Tools 观察和确认，但关键事实仍以 Git 文件为准；
5. 每次执行都应留下可追溯的任务状态、验证证据、ADR 或检查结果。

---

## 六、价值实现原则

LD Vibe Harness 的建设成效以 AI 是否能稳定理解、受控执行、识别门禁、留下证据并支持人类确认来衡量，而不以文档、任务或工具页面数量衡量。

LD Vibe Harness 应帮助 AI 在每次行动前获得足够但不过载的最小可行动上下文。

LD Vibe Harness 不假设 AI 每次都能一次性正确执行。执行中的失败、不确定性和人类纠偏，应在必要时回到事实源。

LD Vibe Harness 管理项目事实的目的，是持续提高 AI 可用上下文的质量。

LD Vibe Harness 不以消除人类参与为目标，而以提高人类确认质量为目标。

这些原则也是审计 LD Vibe Harness 是否实现核心价值的总纲级判断标准。

## 七、规范体系结构

### 7.1 编号分区

LD Vibe Harness specs 采用分区编号，编号本身必须表达文档在规范体系中的位置，避免将底层规范、Harness 对象实践、场景实践和审计检查类规范混为同一层级。

| 编号段 | 类型 | 说明 |
|---|---|---|
| 00 | 总纲 | 定义 LD Vibe Harness 理念、核心原则、规范体系结构和文档治理规则 |
| 10-19 | 基础规范层 | 定义事实源、AI 协作、程序辅助、工具展示、Harness 对象总规则等底层规范 |
| 20-49 | Harness 对象实践 | 定义各 Harness 对象如何依据基础规范形成对象级实践 |
| 50-69 | 场景实践或操作实践索引 | 承载初始化、迁移、审计准备、日常维护等场景实践或操作实践索引 |
| 70-89 | 审计、检查、发布类规范 | 承载审计、检查、发布前确认等横向治理规范 |
| 90-99 | 保留 | 保留给后续扩展，不得未经确认提前占用 |

新增、调整或占用编号段属于规范体系变更，应评估 Human Gate。

### 7.2 Harness 对象与管辖项目

LD Vibe Harness 规范体系服务两个不同方向：

1. Harness 对象：LD Vibe Harness 定义的语义实体，如 Task、Memo、ADR、Pitfall 等。Harness 对象定义及总表见 14 §三及§八。10-19 基础规范为 Harness 对象提供服务和基础——事实源怎么承载对象、AI 怎么读取和回写对象、程序怎么校验和写入对象、工具怎么展示和确认对象。

2. 管辖项目：接入 LD Vibe Harness 的具体项目。70-89 审计检查类规范为管辖项目制定规范——项目接入时应该检查什么、项目运行后如何审计合规性、项目发布前如何确认质量、审计发现如何分流。

两者的区别：Harness 对象是 LD Vibe Harness 定义的语义实体，管辖项目是 LD Vibe Harness 外部的被管理项目。10-19 回答"对象怎么落地"，70-89 回答"项目怎么治理"。50-69 场景实践介于两者之间：它既涉及对象在特定场景下的适配，也涉及项目在特定场景下的操作实践。

### 7.3 四层载体 + Harness 对象

LD Vibe Harness 基础规范层按落地载体分为四层，加上 Harness 对象规范：

| 编号段 | 层 | 回答什么 |
|---|---|---|
| 10 | 事实源层 | 事实放在哪、边界是什么、如何组织 |
| 11 | AI 协作层 | AI 怎么读、怎么执行、何时停下 |
| 12 | 程序辅助层 | 程序怎么解析、校验、聚合、受控写入 |
| 13 | 工具展示层 | 人怎么看、怎么确认、怎么管理 |
| 14 | Harness 对象规范 | Harness 对象是什么、对象地图、对象关系、对象准入与分流、对象实践如何依据对象规则展开 |

10-13 回答"怎么落地"，14 回答"落地什么"。

10-19 基础规范层的准入条件：

1. 全对象适用：该规则对 14 §八 Harness 对象总表中的所有对象都有约束力；
2. 生命周期依赖：该规则是 Harness 对象生命周期中不可或缺的环节；
3. 跨载体：该规则涉及至少两个载体层；
4. 不可降级：该规则不能被任何一个对象实践文档充分覆盖；
5. 不依赖特定场景：该规则不依赖某个特定场景或工具实现。

不满足全部准入条件的内容，应归入 20-49 Harness 对象实践、50-69 场景实践或 70-89 审计检查类规范。

每个对象在 14 中定义"是什么、准入条件、关系、边界"；具体对象的状态机和字段契约由 20-49 Harness 对象实践展开；格式契约由 10 定义；在 10 中定义"怎么承载"；在 11 中定义"AI 怎么协作"；在 12 中定义"程序怎么处理"；在 13 中定义"工具怎么展示"。对象实践只说明该对象如何适配这些规则，不重新定义底层机制。

初始化/审计/开发/交付不是独立基础规范层，而是四层规范在特定场景下的执行实践。它们的规范性内容归入对应规范或对象体系，操作性内容进入 docs/practices 或 50-69 场景实践索引。

### 7.4 基础规范与实践的边界纪律

基础规范和实践文档必须分工明确：

1. 基础规范只定义跨项目稳定规则、概念边界、行为约束、事实源原则、状态与检查要求，不包含具体对象实践、操作步骤、案例、工具使用手册或项目实例；
2. 实践文档只说明某个 Harness 对象或场景如何依据既有规范落地，不得新增、扩张、重写或替代基础规范；
3. 当实践中发现基础规范缺口时，应回到对应基础规范或总纲补规则，不得在实践文档中自行固化新规范；
4. 当实践内容稳定为跨项目强制规则后，应升级回基础规范，并保留实践文档中的适配说明；
5. 程序、Rules、Skills、Agents 和 Web Tools 应优先读取基础规范判断规则边界，再读取实践文档判断对象或场景适配方式。

### 7.5 Harness 对象实践命名

Harness 对象实践文档必须使用中英文双语命名，文件名应同时表达对象英文名、中文名和文档性质。

命名格式：

```text
{编号}-{EnglishObjectName}-{中文对象名}对象实践.md
```

示例：

```text
20-ADR-决策记录对象实践.md
21-Task-任务对象实践.md
22-Memo-备忘对象实践.md
```

Harness 对象实践不得使用"对象规范"作为文档性质后缀；"对象规范"只用于 Harness 对象规范或确实定义规则的规范文件。对象实践应在正文中声明其上位依据、所属基础规范和事实源边界。

### 7.6 specs 与 docs 的边界

specs 承载跨项目稳定规范和规范性实践。docs 承载 LD Vibe Harness 自身产品需求、实施说明、操作手册、案例、工具使用说明和非规范性实践材料。ld-base 承载具体对象实例。

规范性实践与操作实践的区分：

- 规范性实践：跨项目适用、具有约束力、定义稳定语义或规则、作为 AI/人/工具判断依据。留在 specs。
- 操作实践：解释怎么做、包含步骤和案例、可能随工具演进变化、不直接作为跨项目强制规则。进入 docs。

当操作实践稳定为跨项目强制规则后，应升级回 specs。

### 7.7 规范体系边界

进入 specs 的内容必须满足：具有跨项目复用价值；概念边界稳定；来自当前已验证的先进经验或已经达成共识的基础规则；能约束 AI、人或工具的长期行为；不依赖 Web Tools 某个临时实现细节；不只是一次讨论、一次需求或一次工具改造计划。

LD Vibe Harness 必须从源头控制需求膨胀。需求控制的重点不是阻止记录，而是防止一个尚未稳定的想法被过早升级为规范、任务或工具功能。一个内容只有在目标明确、边界清楚、归属稳定、后续需要被复用或追踪时，才进入对应事实源。

## 八、specs 文档规范

### 8.1 写作标准

specs 文档必须采用以下统一写作标准：

| 标准项 | 要求 |
|---|---|
| 上位依据 | 必须声明以本文为上位依据 |
| 解决问题 | 必须说明本文解决哪个稳定问题 |
| 总纲关系 | 必须说明如何回应本文定义的核心问题 |
| 约束对象 | 必须说明约束 AI、人、工具或事实源中的哪一类对象 |
| 事实源边界 | 核心规则章节开头必须声明本文的权威领域和边界 |
| 不写内容 | 必须列出不进入本文的内容，防止范围膨胀 |
| 待补齐事项 | 必须标记尚未稳定、暂不写死的内容 |

基础规范不声明初始化影响、Harness 对象交叉引用和落地载体映射。Harness 对象实践文档的写作标准、章节骨架和头部字段由 14 §九 定义，不适用本节写作标准和文档骨架。

### 8.2 文档骨架

specs 文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---

## 一、本文解决的问题

## 二、与 00 总纲的关系

## 三～N-3、核心规则
（开头含事实源边界声明；具体章节按主题组织）

## N-2、Human Gate 与检查要求

## N-1、不进入本文的内容

## N、待补齐事项
```

头部字段规则：以上字段为必填字段；本文作为体系顶层文档，可增加"原则"等专属字段；子文档可增加"所属主文档""关系"等归属字段。新增头部字段不得与已有字段语义重叠，不得在头部承载正文才应展开的规范内容。

具体章节可根据主题调整，但不得省略"与 00 总纲的关系""事实源边界声明""不进入本文的内容"。

### 8.3 子文档规则

基础规范文档（10-19）因内容超出单文档承载能力时，可以创建子文档。子文档编号格式为 NN.SS，其中 NN 为父文档编号，SS 为子文档序号。

子文档不是独立规范，而是父文档的扩展。子文档必须遵守以下规则：

1. 子文档不受本节写作标准和文档骨架的约束，由父文档定义其格式；
2. 子文档的权威来源是父文档，子文档不得与父文档矛盾；
3. 子文档只能引用父文档，不得与其他同级文档或跨分支文档建立规范引用关系；
4. 子文档的事实源边界由父文档声明，子文档不单独声明事实源边界；
5. 子文档的 Human Gate 由父文档的 Human Gate 规则覆盖；
6. 新增子文档应评估 Human Gate。

### 8.4 引用纪律

引用纪律的本质是事实源单一性在文档体系中的体现——同一个规则只能在一份文档中定义，其他文档只能指向它，不能复制它。

1. 权威唯一：每个规则只在一个文档中定义，其他文档需要引用该规则时，只能写"依据 XX §Y"，不得重写规则正文；
2. 层级服从：当低层级文档与高层级文档的表述不一致时，以高层级文档为准。层级顺序为 00 > 10-14 > 20-49 > 50-69 > 70-89；
3. 适配不重写：对象实践和场景实践对基础规范的引用只能是适配声明，不能是规则重写。适配声明的格式为"本对象的 XX 行为依据 YY §Z"，不得将 YY 的规则正文复制到本文档。

### 8.5 落地机制递归豁免

10-13 作为四层载体规范，不需要在自身文档中完整展开对其他载体层的适配表，只需说明自身载体边界和被其他规范适配的方式。20-49 中的对象实践只声明适配关系，不重新定义载体机制本身。

## 九、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增 specs 编号段或改变编号体系；
2. 重命名或重排 specs 文档；
3. 改变子文档层级关系；
4. 子文档重新定义父规范已有原则；
5. specs 文档引用 specs 外部文档作为规范依据；
6. 实践文档新增或扩张基础规范。

specs 文档写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明以本文为上位依据 |
| 事实源边界 | 核心规则章节开头已声明本文权威领域和边界 |
| 不写内容 | 已列出不进入本文的内容 |
