## 1. 本文定位

本文定义 Pitfall 工作模型使用的结构化数据契约。本文解决 Pitfall YAML 实例应包含哪些字段、字段类型和约束是什么、文件命名规则是什么、状态流转契约是什么，以及工具实现应如何消费本契约的问题。

本文是 Pitfall 工作模型契约字段的权威位置。本文是 `specs/23-Pitfall-踩坑记录.md` 的附件型契约子文档，不是独立工作模型。本文不得重新定义 Pitfall 的对象定位、准入条件、状态机语义、Human Gate、事实源回写或证据留存要求。发生冲突时，以 32 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款。

## 2. Pitfall YAML Schema

### 2.1 基础字段

Pitfall 基础字段遵循 `specs/07-工作模型基础规范.md` §7.3 的字段契约原则，所有工作模型应包含基础字段。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | Pitfall 对象 ID，格式为 `pitfall-{NNNN}` |
| `type` | string | 是 | 固定为 `pitfall` |
| `title` | string | 是 | 踩坑标题，一句话概括问题 |
| `status` | string | 是 | Pitfall 状态，必须属于标准状态枚举 |
| `created` | date | 是 | 对象创建日期 |
| `updated` | date | 是 | 最近更新日期 |

### 2.2 问题字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `symptoms` | string | 是 | 问题现象，描述发生什么错误、什么表现、什么日志 |
| `trigger_conditions` | string | 是 | 触发条件，什么场景、什么操作、什么环境会触发 |
| `root_cause` | string | 是 | 根因或误判原因 |

### 2.3 经验字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `resolution` | string | 是 | 解决方式，最终如何解决 |
| `verification` | string | 是 | 验证方式与验证结果 |
| `avoidance` | string | 是 | 规避策略，后续如何避免 |
| `applicability` | string | 是 | 适用范围，哪类项目、技术栈、任务或场景可参考 |

### 2.4 关联字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `source_objects` | list of string | 否 | 来源工作模型 ID 列表（Task、Evidence、Memo 等） |
| `related_objects` | list of string | 否 | 关联工作模型 ID 列表 |
| `related_rules` | list of string | 否 | 关联的 specs 或 Rules 文件列表 |
| `superseded_by` | string | 条件必填 | 仅当 `status` 为 `superseded` 时必须填写，指向替代本经验的新 Pitfall ID、Rules 文件或 ADR ID |

### 2.5 分类字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `tags` | list of string | 否 | 标签列表，供筛选和分类 |
| `severity` | string | 否 | 严重程度，可选 `low`、`medium`、`high`、`critical` |
| `repeatability` | string | 否 | 可复现性，可选 `always`、`conditional`、`rare`、`once` |

### 2.6 完整 YAML 示例

```yaml
id: pitfall-0001
type: pitfall
title: AI 未读取 L1 规则就直接修改工作模型字段
status: active
created: '2026-06-03'
updated: '2026-06-03'
symptoms: AI 修改 ldvh-base/ 下 YAML 文件时未先读取 L1 规则和对象规范，导致字段不符合 Contract 定义。
trigger_conditions: 用户在对话中直接要求修改事实实例 YAML，AI 跳过规则读取步骤直接编辑。
root_cause: L0/L1 规则入口提醒不够高频，AI 在短路径对话中容易跳过"先读取规范"步骤。
resolution: 在 L0 工作区规则中增加"编辑 ldvh-base/ YAML 必须进入事实 L0 规则"的强制提醒，并在事实 L0 规则中增加"编辑前必须读取"的硬约束。
verification: 验证方式：模拟 AI 编辑 pitfall-0001 YAML；结果：AI 先读取了事实 L0 规则、32 主文档和 23.06-Contract.md 后才编辑，字段符合 Contract。
avoidance: 修改事实实例前，先读取 L0 工作模型规则，再按对象类型读取对应工作模型规范的准入条件、状态机和 Contract。
applicability: 所有接入 LDVH 的项目，所有工作模型类型
source_objects:
  - task-0001
related_objects:
  - adr-0004
related_rules:
  - specs/07-工作模型基础规范.md
tags:
  - ai-collaboration
  - fact-model
  - rules
severity: high
repeatability: always
```

## 3. 字段约束

1. `status` 必须属于 Pitfall 标准状态枚举：`draft`、`active`、`superseded`、`archived`；
2. `type` 必须固定为 `pitfall`；
3. `superseded_by` 仅在 `status: superseded` 时必填，其他状态下不得填写；
4. `source_objects`、`related_objects` 应引用已存在的工作模型 ID，引用无效时应标记为校验警告；
5. `related_rules` 应引用已存在的 specs 或 Rules 文件路径，引用无效时应标记为校验警告；
6. `id` 格式必须为 `pitfall-{NNNN}`，编号固定 4 位，从 `0001` 起递增；
7. `created` 和 `updated` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
8. `tags`、`source_objects`、`related_objects`、`related_rules` 为列表类型，可为空列表，不得省略字段后以 null 替代空列表；
9. `severity` 如填写，必须属于枚举值：`low`、`medium`、`high`、`critical`；
10. `repeatability` 如填写，必须属于枚举值：`always`、`conditional`、`rare`、`once`。

## 4. 文件命名契约

Pitfall 实例文件命名规则：

```text
pitfall-{NNNN}-short-title.yaml
```

约束：

1. 编号从 `0001` 起递增，固定 4 位；
2. 英文短标题使用小写短横线命名；
3. 每个项目独立编号，不使用跨项目全局编号；
4. 文件存放位置为 `ldvh-base/pitfalls/`；
5. 文件名变化必须同步检查所有引用该 Pitfall 的 `related_objects`、`superseded_by` 和其他关联字段。

## 5. 状态流转契约

Pitfall 状态语义和流转规则由 `specs/23-Pitfall-踩坑记录.md` §5 定义，本文只提供结构化枚举和流转矩阵供 Tools 校验消费。

### 5.1 标准状态枚举

| 标准状态 |
|---|
| `draft` |
| `active` |
| `superseded` |
| `archived` |

状态含义依据 `specs/23-Pitfall-踩坑记录.md` §5.1。

### 5.2 合法状态流转

| 当前状态 | 可流转至 |
|---|---|
| `draft` | `active`, `archived` |
| `active` | `superseded`, `archived` |
| `superseded` | 无 |
| `archived` | 无 |

流转语义和约束依据 `specs/23-Pitfall-踩坑记录.md` §5.2。

## 6. 契约消费声明

1. Tools 辅助程序解析 Pitfall 时应依据本文定义的 YAML schema 和字段约束，不得自行扩张格式契约（依据 `specs/06-Python与Web工具规范.md §4` §6.1）；
2. Tools 辅助程序校验 Pitfall 时应覆盖字段完整性、状态合法性、条件必填和引用有效性；
3. Tools 辅助程序读取 Pitfall 时可依据本文状态枚举和字段契约执行状态筛选、详情解析和关联字段解析，但 Pitfall 读取结果是否可作为执行依据由 32 主文档和 Skill 流程判断；
4. 实践子文档和工具可以消费本文契约，但不得复制维护契约字段第二事实源；
5. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 specs/22-Change-变更记录.md）；
6. 契约子文档应先于工具实现创建，工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束；
7. 本文契约变更时，消费本文的 Tools 实现和对应测试必须同步更新。

## 7. 检查项

检查本文是否被正确使用时，应确认：

1. Pitfall YAML 实例字段是否完整，必填字段是否齐全；
2. `status` 是否属于标准状态枚举；
3. `type` 是否固定为 `pitfall`；
4. `superseded` 状态的 Pitfall 是否已填写 `superseded_by` 字段；
5. `source_objects` 引用的工作模型 ID 是否有效；
6. `related_objects` 引用的工作模型 ID 是否有效；
7. `related_rules` 引用的 specs 或 Rules 文件路径是否有效；
8. 文件命名是否符合 `pitfall-{NNNN}-short-title.yaml` 格式；
9. 状态流转是否合法，是否存在非法流转；
10. 终态 Pitfall 是否存在重开情况；
11. 工具实现是否依据本文 schema 解析和校验，未自行扩张格式契约；
12. 工具只读查询是否只依据本文契约解析状态和字段，未自行判断 Pitfall 读取结果是否可作为执行依据；
13. 修改本文是否记录 Change，并在必要时触发 Human Gate（依据 specs/22-Change-变更记录.md）。
