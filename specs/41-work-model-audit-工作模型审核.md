## 1. 行动定位与适用场景

工作模型审核是 LDVH 对具体工作模型规范主文件进行设计质量审查的工作流程。它回答两个问题：

1. **价值层面**——这个 `specs/20-39` 工作模型主文件是否具备明确的工程生产价值？它定义的对象、字段、状态和关系是否能让 AI 稳定理解、驱动实例创建、状态修改与事实回写，是否与其他工作模型和工作流程保持清晰边界？
2. **规范层面**——它是否符合 05 的工作模型基础规则、03.02 的文档骨架与成员自描述契约、05.01 的字段内容格式、以及 09 的单一事实源原则？是否避免了把规范规则、实例状态和派生视图混在一起？

本流程只从"价值 + 规范"两个层面审查工作模型设计质量，**不把 Code 输出视为"该工作模型在项目中已被满足"的证据**，不审核工作流程设计（由 40 承接），不审核规范文档的通用质量（由 42 承接），也不管理具体实例的运行状态或执行进度。

以下场景应进入本流程：

1. 新增 `specs/20-39` 具体工作模型主文件前或创建后；
2. 修改已有工作模型主文件的成员自描述、字段契约、状态机、事实源边界、对象关系、Human Gate 或适配边界后；
3. 将 planned、candidate、reserved 或 removed 状态的工作模型升级为 active 前；
4. 删除、重命名、移动、重排或降级具体工作模型主文件前；
5. Rules、Skill、Agent、Hook、Code、Web、CI 或工作流程准备消费某个具体工作模型前；
6. AI 执行中反复依赖聊天记忆、临时判断或口头约定才能理解某个工作模型时；
7. 某个工作模型规范看起来像泛化说明、索引、数据字典汇编或工具使用说明；
8. 某个工作模型规范执行时无法判断该读什么、状态如何流转、证据写哪里或失败如何降级。

以下场景不应由本流程直接承接：

1. 只查询当前有哪些工作模型成员；该事项由 Code 派生索引和成员主文件自描述承接；
2. 承担 Code 校验或命令行检查的独立职责（此类事项由 Code 和 CI 自身负责），但可在审查过程中运行 Code 命令获取目标文档的机械属性导航与诊断；
3. 审核工作流程的 Context、Scenario、Gate、执行流程或能力协作；该事项由 40 承接；
4. 审核通用规范文档的价值一致性或引用纪律；该事项由 42 承接；
5. 管理某个 WorkArea、WorkPlan、ADR、Pitfall、Memo、Change 等实例的运行状态。

## 2. 准入条件

进入本流程前，应满足以下条件之一：

1. 已存在目标工作模型主文件；
2. 已有待创建的工作模型候选标题、编号意向或 Human 明确创建要求；
3. 已有成员自描述缺失、字段契约缺失、状态机缺口或执行失败线索；
4. 已有 Rules、Skill、Agent、Hook、Code、Web 或工作流程准备消费该工作模型；
5. 已发现某一类事实需要长期结构化承载，但尚未形成稳定工作模型。

不满足以上条件时，不应为了填补编号或维持顺序而创建或审核工作模型。只有存在明确的工程生产事实需要被定义、承载和验证时，才进入本流程。

## 3. 事实源边界

本流程的权威规则来自以下事实源：

| 内容 | 权威位置 |
|---|---|
| LDVH 工作模型基础规则、标准组成、准入条件、通用规范 | `specs/05-工作模型基础规范.md` |
| 工作模型文档骨架、成员自描述契约、字段契约表达、适配规则表达 | `specs/03.02-工作模型文档规范.md` |
| 公共字段语义、字段内容格式、字段内容写入、Web 语义化渲染规则 | `specs/05.01-工作字段内容格式规范.md` |
| 单一事实源原则、权威位置判断、工具输出边界、Web 状态边界 | `specs/09-事实源边界与承载规范.md` |
| 目录、编号与文件归属 | `specs/01-目录说明.md` |
| 目标工作模型主文件正文 | 对应 `specs/20-39` 成员主文件 |

命令输出、Skill 输出、Agent 输出、Web 视图、`docs/studies/` 研究材料和 `docs/sources/` 外部资料只能作为导航、诊断、候选建议或过程输出。审核结论形成稳定事实时，必须按事实类型选择唯一权威位置回写。

## 4. Context 要求

执行本流程前，AI 应按最小可行动原则准备以下 Context：

1. `../rules/LDVH-MAINTAINER-ENTRY.md` 中与工作模型规范场景路由和维护规则相关的段落；
2. `specs/05-工作模型基础规范.md` 中工作模型定义、标准组成、准入条件、状态机、对象关系、Human Gate、字段契约、事实源回写与适配边界相关章节；
3. `specs/03.02-工作模型文档规范.md` 中成员自描述契约、文档骨架、字段契约表达、适配规则表达、规范落地要求和检查要求；
4. `specs/05.01-工作字段内容格式规范.md` 中公共字段语义、内容格式和消费规则（如适用）；
5. `specs/01-目录说明.md` 中 20-39 编号区段和成员自描述规则；
6. `specs/09-事实源边界与承载规范.md` 中单一事实源原则和权威位置判断规则；
7. 目标工作模型主文件或候选草案。

若目标工作模型尚未创建，AI 只能审核候选草案和创建方案，不得声称该工作模型已经是 active 成员。若无法定位目标文件或上位规范，应暂停并说明缺口。

## 5. Scenario 识别

AI 遇到以下信号时，应识别为工作模型审核场景：

1. 用户要求创建、修改、审查或重写某个 `specs/20-39` 工作模型规范文档；
2. 用户提到字段契约、状态机、实例位置、事实源边界、Human Gate、对象关系或工作对象模型；
3. 当前任务涉及 planned、candidate、reserved、removed 与 active 状态切换；
4. Rules、Skill、Agent、Hook、Code、Web 或工作流程准备引用某个工作模型，但该模型的字段或状态规则不清；
5. 某个工作模型规范看起来像泛化说明、索引、数据字典汇编或工具使用说明；
6. 某个工作模型规范执行时无法判断该读什么、状态如何流转、证据写哪里或失败如何降级。

多个场景同时命中时，应先判断是否存在更具体的 active 工作流程。若没有更具体的 active 工作流程，或目标就是审核工作模型设计质量，则进入本流程。

## 6. 执行流程

工作模型审核按以下步骤执行，核心围绕"价值"与"规范"两个层面审查：

1. **确认目标**：确认被审核对象是已存在的 `specs/20-39` 工作模型主文件、候选草案、编号意向、迁移计划还是能力消费请求；
2. **确认权威依据**：读取或定位 05、03.02、05.01、01、09 和目标文件；
3. **运行确定性诊断**：优先运行或参考 `python3 code/specs_validate.py index`、`python3 code/specs_validate.py doc specs`、`python3 code/specs_validate.py refs specs`、`python3 code/specs_validate.py landing specs`、`python3 code/specs_validate.py all` 获取目标文档的机械属性导航与诊断（成员自描述完整性、编号/路径/标题一致性、骨架章节齐全性、引用有效性、锚点有效性、规范落地要求表结构、派生集合索引与冲突诊断）；
4. **审核成员自描述**：检查 `spec_id`、`kind`（必须是 `work_model`）、`name_en`、`name_zh`、`collection_status`、`canonical_path`、`instance_root`、`schema_anchor`、`state_machine_anchor`、`human_gate_anchor` 是否完整一致；
5. **审核文件归属**：检查文件名、编号、区段、标题和 canonical path 是否符合 01、03.02 和 05；
6. **审核对象定位（价值层面）**：判断该内容是否确实需要被结构化承载为工作模型，是否不成为工作模型就会导致事实不可追溯或边界漂移；是否存在重复覆盖已有的工作模型；
7. **审核准入条件与范围声明**：检查 §1 是否明确说明哪些内容应进入该工作模型，哪些内容不得进入；是否明确"不是什么"；
8. **审核事实源边界（规范层面）**：检查 §2 是否定义实例权威位置、文件命名方式、权威字段所在位置；是否明确区分规范正文、实例文件、派生输出；
9. **审核状态机（规范层面）**：检查 §3 是否定义标准状态、合法状态流转、终态与重开规则、关闭条件或等价约束；是否存在状态描述与字段契约不一致；是否存在自相矛盾的循环或无法关闭的状态；
10. **审核对象关系（规范层面）**：检查 §4 是否定义该工作模型与其他工作模型或工作对象的引用关系；是否明确双向引用规则与一致性要求；
11. **审核 Human Gate（规范层面）**：检查 §5 是否定义需要人类确认的具体场景；确认触发条件是否与状态机中的关键节点、字段变更或范围变更保持一致；
12. **审核字段契约（规范层面）**：检查 §6 是否用稳定表格或结构化代码块表达字段名、含义、类型、必填性、默认值、内容格式和消费方；字段内容格式是否引用 05.01；
13. **审核事实源回写与证据（规范层面）**：检查 §7 对实例创建、修改、关闭、删除和回写的归属规则是否明确；是否声明只有 Git 文件事实源作为权威位置；
14. **审核整体设计（价值+规范交叉层面）**：跳出逐段检查，做一次整体判断：①**边界清晰性**——检查是否与相邻工作模型（WorkArea、WorkPlan、Pitfall、Memo、ADR、Change）职责重叠；是否明确声明"不是什么"；是否存在职责漂移（如本该在工作流程中的执行步骤被写进工作模型）；②**整体流转合理性**——检查从典型事实"进入→状态机推进→字段变更→Human Gate→关闭/回写"的路径是否闭环；状态机的关键状态是否有对应的字段契约支撑；终态是否可到达；③**AI 消费可用性**——检查最小可读上下文（spec_id/kind/collection_status）是否完整；状态机是否驱动了至少 2 个可执行的决策点；字段契约是否提供 AI 可直接消费的结构；④**机制契合度**——检查成员自描述字段是否可被 Code 派生索引；anchor 命名是否与 03.02 的约定一致；collection_status 取值是否在 05 定义的范围内；
15. **审核适配规则**：检查 §8 对 AI、Rules、Skill、Agent、Web、结构化契约的消费方式是否只保留摘要和引用，不复制实现正文；
16. **审核规范落地要求**：检查规范落地要求表是否说明同步、检查或审计触发条件，且没有制造无法保障的落地承诺；
17. **审核检查要求**：检查工作模型是否明确 AI 如何判断实例合法、非法、需要回写或需要 Human Gate；
18. **审核待补齐事项**：检查待补齐事项是否列举了真实缺口而非泛化问题；是否与成员自描述中的 candidate/planned 状态相匹配；
19. **形成审核结论**：按 §10 输出过程结论，必要时触发 Human Gate、创建后续 WorkPlan/Memo/ADR/Pitfall 或修订目标文件；
20. **记录残留风险与下一步分流**：审查完成后，记录变更摘要（如有修改）、残留风险和下一步建议；Code 诊断仅辅助机械属性检查，价值判断与规范一致性由 AI 主导完成。

## 7. Gate 触发条件

出现以下情况时，AI 必须暂停继续宣称审核通过，并按影响范围触发 Human Gate、降级检查或后续分流：

1. 新增 active 工作模型主文件；
2. 删除、重命名、移动或重排 20-39 工作模型编号；
3. 改变成员自描述契约、active 判定条件、集合状态语义或实例权威位置；
4. 让工作模型承担手写集合索引、事实源替代、Human Gate 替代或 Skill/Agent 直接生效职责；
5. 目标工作模型与 00、01、03.02、05、05.01 或 09 冲突；
6. 目标工作模型缺少成员自描述、必需锚点、状态机、字段契约、Human Gate 或事实源回写规则，却被要求标记为 active；
7. 审核需要接受长期降级、跳过验证、关闭 open/degraded 缺口；
8. 审核结论会影响 Rules、Skill、Agent、Hook、Web 或工作流程的长期行为边界；
9. 修改实例文件命名、权威字段定义或 `instance_root` 目录位置，可能影响既有实例可追溯性。

Gate 触发时，AI 应说明触发原因、影响范围、可选处理方式、推荐分流和需要 Human 确认的具体事项。Human 确认形成稳定事实时，应按 `specs/06-工作流程基础规范.md` 的 Human Gate 最小字段和 `specs/25-Change-变更.md` 的变更追溯要求记录时间、决策、范围和约束。

## 8. Skill 和 Agent 调度

本流程默认由主控 AI 执行。只有当审核任务可复用、复杂、争议大或需要独立上下文时，才考虑 Skill 或 Agent 辅助。

Skill 适合承接：

1. 固定审核清单；
2. 标准化输出格式；
3. 常见失败分类（如字段契约缺项、状态机不闭环、实例位置与主规范不一致）；
4. 交还主控的修订建议；
5. 重复执行的工作模型审核 SOP。

Agent 适合承接：

1. 跨工作模型字段与状态一致性审查；
2. 工作模型与工作流程职责边界争议分析；
3. 字段命名或状态语义选择的并行审阅；
4. 长期降级或缺口关闭的争议分析。

Skill 和 Agent 输出均为过程输出，必须交还主控。Skill 不得自行调度 Agent，Agent 输出不得直接生效，不得绕过 Human Gate、事实源回写或主控判断。

---
## 9. Code 与命令入口协作适配

本流程优先使用 Code 完成可机械化检查。Code 适合承接：

1. 工作模型成员自描述字段解析与完整性检查；
2. 编号、路径、标题、canonical_path 一致性检查；
3. active 工作模型必需锚点检查；
4. 文档结构与骨架章节检查；
5. specs 引用检查与锚点有效性；
6. 规范落地要求表结构检查；
7. 派生集合索引与冲突诊断；
8. 与其他工作模型/工作流程成员自描述的一致性提示。

常用命令包括：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

Code 输出只作为导航、聚合和诊断结果。Code 不判断工作模型是否具备工程价值、不判断状态机设计是否合理、不判断对象关系是否清晰、不判断 Human Gate 是否在正确节点触发，也不生成授权。Code 不可用、诊断不完整或输出无法回指事实源时，应退回人工检查并记录残留风险。

**审查边界声明**：本流程只审查目标工作模型文档中写的规范要求是否合理、完整、一致、可执行；不审查项目中是否已实际满足这些要求。Code 的作用仅限于帮助 AI 检查目标文档的机械属性（成员自描述、编号、路径、骨架、引用、锚点、落地要求表结构），Code 输出不构成"该工作模型在项目中已被满足"的证据。

## 10. 事实源回写与证据留存

本流程执行后的过程输出应至少说明：

1. 审核对象；
2. 读取的权威依据；
3. 发现的问题（字段契约、状态机、Human Gate、对象关系或事实源边界层面）；
4. 模型价值审查小结，说明该对象为什么值得成为工作模型、主要服务的 V1-V10 项、是否与已有对象重叠、未发现的价值偏离和残留风险；
5. 审核结论；
6. 是否触发 Human Gate；
7. 是否修改目标文件或生成后续工作对象；
8. 残留风险和下一步分流。

审核结论分为：

| 结论 | 含义 |
|---|---|
| `pass` | 未发现阻塞问题，价值与规范层面均通过，且必要的机械诊断检查通过（成员自描述完整性、编号/路径/锚点一致性、骨架章节齐全、引用有效、规范落地要求表结构完整） |
| `pass_with_followups` | 可继续使用，但存在不阻塞的后续改进项 |
| `blocked` | 存在阻塞问题，不得标记为通过或 active |
| `needs_human_gate` | 需要 Human 确认后才能继续或升级/修改 |
| `not_applicable` | 当前对象不属于工作模型审核范围 |

稳定事实回写规则如下：

1. 目标工作模型正文需要调整时，回写对应 `specs/20-39` 主文件；
2. 审核形成缺口、后续工作线索或后续行动时，回写 Memo 或 WorkPlan；
3. 审核形成长期决策时，回写 ADR；
4. 审核形成可复用踩坑经验时，回写 Pitfall；
5. 审核形成研究报告或迁移说明时，回写 docs；
6. 发生事实源修改时，按 25-Change 的 Git、commit message 和 Refs 追溯规则处理。

凡回写为 WorkPlan 的后续行动，必须按 `specs/21-WorkPlan-工作计划.md` 和 `specs/05.01-工作字段内容格式规范.md` 填写 `success_criteria`、`orchestration.execution_items`、`verification_evidence` 与 `closure_evidence` 等字段；流程步骤不得新建 TaskPlan、Task 或 SubTask，执行期拆分只能作为 WorkPlan 内部 `execution_items`。

不得把聊天中的"看起来可以"、"应该合格"或"已审核"当作完成证据。关键结论必须能回指规范、目标文件、Human Gate 记录或事实源差异。

## 11. 环境适配边界

本流程可以被 Rules 入口提示、Skill SOP、Agent 审查、Web 展示、Hook 提醒或 CI 检查辅助，但这些能力不得替代本流程正文（"价值 + 规范"判断由 AI 完成，不能被工具输出替代）。

环境适配边界如下：

1. Rules 入口只提示何时读取本流程和相关规范，不复制流程全文；
2. Skill 可以封装固定审核清单，但不新增稳定规则；
3. Agent 可以提供独立语义审查和边界判断，但不直接生效；
4. Web 可以展示审核状态、诊断和 Human Gate 入口，但不维护第二事实源；
5. Hook 或 CI 可以提醒或阻断高风险变更，但触发不等于检查通过；
6. CI 属于保障机制，不是固定文本能力资产类型；
7. 环境能力缺失时，应降级为人工检查并记录残留风险。

## 12. 行动特有可测试性锚点

本流程的关键行为应能通过正例、反例、Gate 场景、回写场景和人工交叉验证进行检查。

正向场景：

1. 目标工作模型有合法成员自描述（spec_id、kind=work_model、name_en/name_zh、collection_status、canonical_path、instance_root、schema_anchor、state_machine_anchor、human_gate_anchor）；
2. 文件名、编号、标题和 canonical path 一致；
3. active 工作模型包含状态机、字段契约、Human Gate、对象关系、事实源回写和检查要求；
4. 状态机定义标准状态、合法流转和终态，且没有自相矛盾的回环；
5. 字段契约明确字段名、类型、必填性、内容格式和消费方，引用 05.01 作为内容格式权威；
6. 事实源边界明确实例权威位置与派生输出的区别；
7. 审核结论能回指事实源和验证结果。

负向场景：

1. 缺少成员自描述或 `kind` 不是 `work_model`；
2. `spec_id` 与文件名编号不一致；
3. planned 或 candidate 被当作 active 执行；
4. 工作模型规范同时承担数据字典、工具使用说明或历史记录；
5. 字段契约把 Code 实现或 Web 组件写进字段定义；
6. 缺少状态机、Human Gate、字段契约或事实源回写规则；
7. 实例权威位置分散在多个目录或非 Git 文件位置，无法稳定消费。

Gate 场景：

1. 新增 active 工作模型；
2. 改变 20-39 编号归属；
3. 删除、重命名或移动工作模型主文件；
4. 改变字段契约、状态机或事实源边界；
5. 接受长期降级或跳过关键验证。

回写场景：

1. 审核发现正文缺陷，应回写目标工作模型主文件；
2. 审核发现后续改进项，应回写工作对象或 docs；
3. 审核发现长期决策，应回写 ADR；
4. 审核发现可复用误判，应回写 Pitfall；
5. 审核只产生临时建议时，应明确其为过程输出。

修改本流程或目标工作模型后，至少应运行：

```bash
python3 code/specs_validate.py index
python3 code/specs_validate.py doc specs
python3 code/specs_validate.py refs specs
python3 code/specs_validate.py landing specs
python3 code/specs_validate.py all
```

无法运行自动化校验时，应说明原因、采用的人工检查方式和残留风险，不得声称完整验证。Code 命令输出仅辅助机械属性检查，不替代 AI 对价值与规范的判断。

## 14. 检查要求

工作模型审核至少包括：

| 检查项 | 标准 |
|---|---|
| 对象归属 | 被审核对象属于 `specs/20-39` 工作模型主文件、候选草案或能力消费请求 |
| 权威依据 | 目标工作模型引用的规范锚点齐全（05 工作模型基础规则、03.02 文档骨架与成员自描述契约、05.01 字段内容格式、01 编号与文件归属、09 事实源边界）；未引用 docs/studies、外部 URL 或非 LDVH 资产作为上位依据 |
| 成员自描述 | `spec_id`、`kind=work_model`、`name_en`、`name_zh`、`collection_status`、`canonical_path`、`instance_root`、`schema_anchor`、`state_machine_anchor`、`human_gate_anchor` 完整一致 |
| 文件命名 | 文件名符合 NN 编号规则，且不重复「工作模型规范」字样 |
| 状态边界 | `collection_status` 真实反映该规范当前治理阶段（active/candidate/planned/reserved/removed），未被 AI 误用作 active |
| 对象定位 | 该规范确实定义一类工程生产事实，不是纯数据字典汇编、工具使用说明或泛化需求清单 |
| 模型价值 | 说明该对象为什么需要作为独立工作模型进入事实源，主要服务哪些 V1-V10 项，且未与既有工作模型重复覆盖或以对象数量替代价值标准 |
| 准入条件 | §1 明确说明哪些内容应进入该工作模型，哪些内容不得进入 |
| 范围声明 | 明确"不是什么"的否定边界；避免承担数据字典、工具说明或历史记录等非工作模型职责；与相邻工作模型的职责划分清晰 |
| 事实源边界 | §2 明确实例权威位置、文件命名方式、权威字段定义与派生输出边界 |
| 状态机 | §3 定义标准状态、合法流转、终态与重开规则；不得出现自相矛盾的循环或无法关闭的状态 |
| 对象关系 | §4 定义与其他工作模型或工作对象的引用关系，明确双向引用与一致性检查方式 |
| Human Gate | §5 明确需要人类确认的具体场景；能被状态机或字段变更触发 |
| 字段契约 | §6 使用稳定表格或结构化代码块表达字段名、含义、类型、必填性、默认值、内容格式、消费方；不得把 Code/Web 实现写进字段定义 |
| 事实源回写 | §7 明确实例创建、修改、关闭、删除和回写的权威位置；不得让聊天输出、Web 状态或工具命令直接成为最终事实源 |
| 边界清晰性（整体设计） | 与相邻工作模型（如 WorkArea、WorkPlan、Pitfall、Memo、ADR、Change）职责清晰，无重复覆盖或责任漂移；明确声明哪些内容不属于本工作模型 |
| 整体流转合理性（整体设计） | 从典型事实进入到关闭的流转路径可闭环；状态机与字段契约协同一致；无明显缺口或不可达状态 |
| AI 消费可用性（整体设计） | AI 执行时可快速定位最小可读；状态机能驱动执行；字段能支持最小可行动上下文生成；缺少必要锚点或字段时应识别为缺口 |
| 机制契合度（整体设计） | 能被 Rules、Skill、Agent、Code、Web、CI 等能力资产稳定消费；不制造能力资产无法处理的结构 |
| 适配规则 | §8 只保留摘要和引用，不复制 Skill/Agent/Web 实现正文 |
| 验证结果 | 相关 Code 校验命令已运行或已说明无法运行的原因、采用的人工检查方式和残留风险；Code 诊断仅辅助机械属性检查，不替代 AI 对价值与规范的判断 |
| 落地要求 | 规范落地要求表声明要求内容、保障机制、同步类型和触发条件，不把环境实体写成要求本身 |
| 检查要求 | 明确 AI 如何判断实例合法、非法、需要回写或需要 Human Gate |
| 待补齐事项 | 真实、具体，与 candidate/planned 状态或当前实现缺口一致 |
| 审核结论 | 结论按 `pass / pass_with_followups / blocked / needs_human_gate / not_applicable` 分类，且能回指事实源 |
