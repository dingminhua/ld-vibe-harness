## 3. 移除重复和实现细节后的候选责任

### 3.1 面向 AI 的统一基础服务边界

规则对象是面向 AI，并可由环境入口调用的统一基础服务：调用方如何提供当前任务和工作对象，能够请求哪些已存在的 LDVH 信息或能力，以及服务如何返回来源、范围、歧义、缺口、部分结果和受控状态变更结果。

移除 00 对 Helper 定位、01 对披露层级、02 对工作对象、03 对来源和写入边界的已有规则后，剩余规则为：

1. 任务、工作对象和必要上下文如何进入统一外部请求；
2. 如何发现并区分已定义、已实现、当次可调用、缺失和部分可用的能力；
3. 如何在响应中同时保留结果、对象范围、来源身份、披露层级和缺口；
4. 歧义、无操作、部分成功、能力缺失和错误如何对 AI 保持真实语义；
5. 来源规则、事实、行动模板、Human 当次指令和当次观察如何保留各自来源身份；
6. 读取请求与状态变更请求的边界，以及受控操作的实际结果、拒绝、部分完成、回读失败和未完成范围如何返回；
7. 环境入口调用同一服务时，请求与响应语义不得被环境协议改写；
8. 公开命令族、公开命令与选项名称、输入参数语义、响应封装与字段语义、机器输出边界、错误和退出语义如何形成稳定外部接口；
9. 对具体规则的当次判断如何保留规则身份与来源、工作对象与作用范围，并区分已判断不适用、依据不足无法判断和尚未检查；
10. 缺失输入和相互冲突的来源如何原样报告；Helper 只能报告来源规则定义的效力，不得自行创造通用效力状态或优先级模型。

公开 CLI 接口及其机器可消费输出属于稳定服务契约，不得交给 Code 反向定义。可以留在实现中的内容包括人类可读终端装饰、非公开内部函数布局、parser 与序列化库选择、缓存与索引算法、厂商 Hook、session/receipt/TTL、具体事实字段、行动模板语义，以及尚未形成真实需求的命令或错误码。能力是否可调用和规则是否已经检查，只能依据当次服务结果与来源证据报告，不建立脱离当次证据的永久状态。

### 3.2 需要结构化管理的稳定事实

规则对象是已经满足事实源边界，并因需要稳定身份、字段、状态、关系或证据组织而必须结构化管理的项目事实类型及其实例。

移除 00 的构成要素定义、03 的稳定事实、Working Tree、来源和写入边界后，剩余规则为：

1. 候选事实类型的准入、净价值、更新和退出；
2. 每个事实类型的唯一语义来源，以及 Schema/Code 不得成为第二定义来源；
3. 实例身份、唯一性、允许位置和重复权威实例处理；
4. 字段语义、授权附件和 Schema 的权威方向；
5. 状态闭集、转换条件、转换依据和禁止静默跳转的边界；
6. 实例关系的目标身份、方向、缺失目标和关系冲突处理；
7. 对象如何保存或关联来源与证据，但证据充分性仍由具体来源规则判断；
8. 新建、更新、关闭和删除结构化对象时额外需要成立的身份、字段、状态和关系条件。

基础责任只定义不同事实类型共同需要的身份、Schema 权威方向、状态与关系规则；具体事实类型的核心语义仍必须有自己的正式来源。授权附件只能承载父规范已经定义的字段表、枚举或关系矩阵，不能代替具体事实类型的规则来源。

不应进入该责任的内容包括重新定义 Git、所有类型共用的大型字段注册表、无需求的全局状态枚举、直接恢复 V3 事实类型、Helper 会话或缓存、证据充分性、具体工作流程以及强制所有稳定内容对象化。

### 3.3 重复场景中可复用的行动结构

规则对象是经证明具有重复价值，并用于组织进入场景、必要输入、前置条件、关键步骤、失败分流、验证、回写和交还的可复用行动结构。

移除 00 的行动模板定义、各来源规则的强制要求和 03 的事实回写边界后，剩余规则为：

1. 模板资产的稳定身份、发现入口、准入、更新和退出；
2. 进入场景、输入、前置条件、关键步骤、失败分流、验证入口、回写和交还的最小语义；
3. 模板只能回指来源规则、事实、所需能力和当次能力缺口，不得重定义领域规则、Schema、状态、Human Gate 或保存单次运行状态；
4. 具体模板必须证明重复价值，一次性计划、命令说明和实现步骤不得因格式相似而取得模板身份；
5. 模板存在、结构有效或被选中，不等于行动已经获得授权、实际执行、验证通过或完成；实际执行结果、失败和未完成范围必须来自当次能力调用与回读。

授权附件只能承载父规范已经定义的共同字段表、枚举或结构矩阵，不能承载具体模板的进入场景、步骤、失败分流等完整行动流程。本次责任审计不提前决定具体行动模板的正式载体。

不应进入该责任的内容包括领域规则含义、事实字段与状态、Helper 外部服务契约、具体命令、测试实现、单次计划和全局固定工作流程。

### 3.4 Code 的系统设计与持续工程治理

规则对象是 Code 构成要素在实现前和持续变化中的系统设计、模块边界、接口与 Schema 责任、测试策略、诊断与可观察性、复杂度与重构以及外部工程实践的选择与吸收。

移除 00 的 Code 定位、Helper 外部契约、领域 Schema 语义、真实源码、测试文件、runner、fixture、命令和一次性实施计划后，剩余规则为：

1. 首次启动 Code/tests 实现前，当前系统规划必须先成立；后续改变模块责任、依赖方向、接口、Schema 维护责任或测试策略时，规划至少与该批实现变更同步更新，不得事后补写；
2. 模块责任、允许的依赖与调用方向、公共接口和 Schema 唯一维护责任；
3. 风险驱动的测试策略、正例、反例、边界、失败覆盖和测试同步；
4. 内部错误传播、诊断来源回指和可观察性；
5. 结合责任、耦合、复杂度、变更频率、可测试性和可导航性的重构条件，不使用无上下文的全局行数上限；
6. 外部工程实践必须核验来源和对 LDVH 的适用性，再由当前规则源正式吸收；
7. 系统规划与真实实现发生偏移时的发现、暂停和修正边界。

当前承载建议是一份普通规范正文，并在后续单独证明需要时授权一份结构化附件：正文定义上述核心规则、验证和停止边界；附件只能承载正文已经定义的允许依赖矩阵、公共接口登记、Schema 来源与维护责任表以及有证据支持的度量或阈值。当前目录、具体模块文件、测试文件、实现进度、设计理由和动态实施计划仍属于实现说明或其它适当事实载体，不能仅因可以表格化就进入规则源。系统规划与工程实践不拆成两份普通规范，因为两者约束同一 Code 系统并需持续同步读取。

不应进入该责任的内容包括 Helper 外部字段、领域 Schema 语义、环境协议、真实 Code/tests、具体目录与命令、单一行数失败标准和未经核验的“最佳实践”。

### 3.5 面向 Human 的信息产品边界

规则对象是面向 Human 的产品界面如何读取当前项目信息、形成不具事实权威的派生视图、呈现来源和判断边界，以及在获得适用授权时实施可回读、可失败且不会冒充 Human Gate 的受控交互。

移除 00 的 Web 定位和 03 的当前读取、事实源、来源回指、派生信息和写后回读共同规则后，剩余规则为：

1. Web 派生字段的身份、过期提示、刷新和与当前来源的差异呈现；
2. 页面和 API 不得因展示需要反向创建事实字段、状态机或规则；
3. 事实、风险、证据、未知范围和待确认事项如何在展示、复制和导航中回到来源；
4. 默认只读；获得适用授权时，Web 可以请求已经由来源规则定义、由当次实际可用 Code 能力承接的受控写入。Web 不因表单或 API 存在而自行取得事实写入权威；实际结果必须回读，并呈现失败和未完成范围；
5. 点击、表单提交或页面成功状态不得自动等于 Human Gate、验收、技术通过或工作完成；
6. Web 可以复用共享 Schema 或纯解析能力，但不得把 Code 输出、内部 DTO 或诊断当作事实权威；
7. 文件与事实读取必须限定在允许的项目和来源范围；
8. Human-facing 内容在支持的语言、视口和交互方式下仍能识别身份、来源和主要操作。

V3 已形成的语义阅读、详情与扩展阅读同源、来源感知复制、i18n、响应式布局和轻写入回读是适配输入，但具体 App Shell、五个模块、组件、CSS 类、路由、DTO、当前事实类型和 Spark 写入白名单只是实现实践。现有 `web/` 在责任审核阶段保持不变。

### 3.6 外部运行环境与 Helper 的连接边界

规则对象是外部运行环境中的事件、工具调用和上下文如何被转换为 Helper 请求，Helper 结果如何映射回环境，以及这种连接如何安装、检查、真实触发、诊断、更新、卸载和证明已回滚。

移除 00 的 Helper 和环境上位边界、02 的工作对象、03 的信息来源、Helper 外部服务契约、具体 Code/tests 和重复安装步骤后，剩余规则为：

1. adapter 只转换环境协议、事件和上下文，不复制规则、事实、行动判断或业务状态机；
2. 未知事件、缺失字段和环境能力不足必须显式交还，不得猜测映射或虚构支持；
3. Helper 结果必须按环境真实能力忠实映射，不得把不支持的阻断、警告或反馈写成已强制执行；
4. 环境能力发现、静态安装检测和真实自动触发必须分开；
5. 真实连接结论必须有目标环境、版本、入口、事件、实际触发、Helper 调用、返回映射和失败路径的当次依据，不建立永久的接入状态；
6. 安装、升级、禁用和卸载必须明确目标、净变化、授权、冲突、验证和回滚边界；
7. 回滚验证必须证明目标环境不再自动进入该连接，同时没有破坏无关用户配置；
8. 厂商事件、manifest、安装路径、命令和 payload 字段不得成为所有环境共用的闭集；其中纯实现细节属于 adapter 实现说明和 tests，某一 adapter 的受支持事件、必需输入或安装接口如果形成稳定外部契约，则必须另经 §13 判断其正式来源或授权附件位置，不能只由 Code/tests 定义。

不把 V3 的厂商闭集、固定 lifecycle 事件、插件路径、manifest Schema、缓存目录、固定命令名、runtime receipt、diagnostic code 和环境分类器接口直接恢复为 V4 通用规则；其中真实形成单一 adapter 外部契约的内容仍需按前述边界另行判断。重复安装与回滚步骤可在证明重复价值后进入行动模板。

## 4. 两项应取消的横向总责任

### 4.1 统一管理测试、验证与结论范围

历史候选准备统一管理：验证方式、证据能够支持的对象与范围、设计/实现/接入/验证/可用/完成结论、未验证范围、残留风险和 Human 验收边界。

逐条移除已有承接后：

| 原候选内容 | 已有或正确承接位置 |
|---|---|
| 结论不得超过事实和当次依据 | 00 的 V5、上位验证要求和 Stop Conditions |
| Human 决定不能替代技术状态 | 00 的验证要求和 Human Gate |
| 每份规范的成立条件、依据、入口与可证明范围 | 01 规定的七列验证结构以及每份具体来源规范 |
| 信息、测试输出、验证结果、事实源和 Git 历史的作用边界 | 03 |
| 风险驱动测试策略和测试同步 | Code 系统设计与持续工程治理责任 |
| 具体测试、fixture、runner、命令和执行输出 | Code/tests |
| 服务返回实际结果、能力缺口、部分结果和未完成范围 | 面向 AI 的统一基础服务责任 |
| 真实环境触发、接入、安装和回滚是否成立 | 外部运行环境连接责任 |
| Web 呈现来源、未知范围、风险和 Human 验收信息 | 面向 Human 的信息产品责任 |
| 需要长期存储的验证结果或证据关系 | 在通过事实模型准入后由事实源中的事实对象承载 |

移除上述内容后没有独有稳定规则。该横向责任不满足 §13.2(2)、(3)、(4)、(6) 和 (7)：没有剩余独有规则，不需要唯一定义位置，变化跟随具体来源和实现职责，没有独立失败，新增文档只会增加拼接与同步成本。

建议取消独立普通规范候选，不用改名恢复同一横向容器。

### 4.2 统一管理所有来源规则对当前对象的命中与效力

历史候选准备统一管理：候选规则、命中、不命中、无法判断、多来源冲突、义务、验证、Human Gate、Stop Conditions、缺少所需能力时的处理和最小作用范围。

逐条移除已有承接后：

| 原候选内容 | 已有或正确承接位置 |
|---|---|
| 当次对象与项目管辖范围 | 02 |
| 什么是当前有效规则、规则来源和完整规则上下文 | 01 |
| 每条具体规则的适用对象、场景、命中条件、义务、验证、Human Gate 和 Stop Conditions | 该规则的来源规范 |
| 命中具体规则时必须执行，未命中时保持普通求解自主 | 00 |
| 规则信息不足、来源冲突或可能遗漏 Gate/Stop 时展开全文或报告缺口 | 01 的渐进式披露边界 |
| 规则适用条件、效力或权威关系无法确认时的暂停和最小恢复范围 | 00 的 Stop Conditions 与恢复条件 |
| 多来源规则的规范依据、结构归属和替代关系 | 01；这些关系不自动产生规则优先级或解决内容冲突 |
| 没有明确来源规则时的内容冲突或优先级不确定 | 按 00 暂停，不能从 `basis`、`parent_spec` 或导航关系自行推导优先级 |
| 将 02 对象上下文、01 规则源和来源规则组合后提供给 AI | 面向 AI 的统一基础服务责任；服务保留规则身份、对象、范围、判断状态、缺口和冲突，具体确定性处理由 Code/tests 实现 |

移除上述内容后没有独有稳定规则。“有多来源”本身不能证明需要一份中间总规范；如果未来形成当前 01 关系模型和具体来源无法承接的稳定优先级或冲突规则，必须使用 §13 另行重新证明，不由本次提前预留文件。

该横向责任不满足 §13.2(2)、(3)、(4)、(5)、(6) 和 (7)：没有剩余独有规则或唯一定义需求，变化跟随来源规则或 Helper 服务，若强行建文档则需制造通用命中状态和效力模型，不存在独立失败，且增加跨文档拼接。

建议取消独立普通规范候选，不并入 02，也不用改名保留。02 已经提供该责任需要的工作对象和管辖上下文，具体规则仍回到各自来源；§3.1 已承接 Helper 对规则身份、被判断对象与范围、已判断不适用、依据不足无法判断、尚未检查、缺失输入和来源冲突的服务级报告责任。Helper 只组织并报告来源规则的结果，不创造通用效力模型。

## 6. 正例、反例和责任数量结论

| 候选责任 | 应由该责任处理的正例 | 不应由该责任处理的反例 |
|---|---|---|
| 面向 AI 的统一基础服务 | 定义机器响应如何同时返回结果、来源、对象范围和未完成范围 | 在该责任中定义某事实类型的字段或某厂商事件 payload |
| 需要结构化管理的稳定事实 | 定义事实实例的稳定身份、状态转换依据和关系目标 | 把单次命令输出或 Helper 缓存强制提升为事实对象 |
| 重复场景中的可复用行动结构 | 定义模板进入条件、失败分流和交还所需的共同语义 | 用模板重定义领域规则，或把一次性实施计划登记成模板 |
| Code 的系统设计与持续工程治理 | 在首次实现前确定模块责任和允许依赖方向 | 在规范中固定当前源码文件清单、具体命令或单次重构步骤 |
| 面向 Human 的信息产品 | 定义旧值提示、来源导航和受控写入请求的产品边界 | 让 Web 表单自行取得事实字段定义权或 Human Gate 决策权 |
| 外部运行环境与 Helper 的连接 | 定义未知环境事件如何交还，以及怎样证明真实触发和卸载回滚 | 把某厂商 manifest 字段直接扩成所有环境共用闭集 |

取消横向总责任的代表性反例是：将每份来源规范的验证表、Code 测试策略、Helper 结果、环境验证和 Web 呈现再次汇总为第二套验证来源；或者在 02 已给出工作对象、01 已给出当前规则源、各来源规则已给出自身适用条件后，再创建通用命中状态和效力模型。这两种做法都不能形成新的独有责任。

当前责任数量结论为：

- 已生效 00–03 四项规范责任保持不变；
- 六项历史候选经过 §13 后仍有独有稳定规则，建议各由一份独立普通规范承担；
- 两项横向总责任没有剩余独有规则，取消独立规范候选；
- 三方初次独立复核提出的记录阻断修正并经后续复核确认后，V4 当前规范责任总数候选为十项。

“十项”只是责任审计结果，不等于已确定十份文件的标题、编号、路径或建设顺序，也不是永久闭集；未来出现新的稳定责任时仍须按 01 §13 证明。Code 系统设计责任中的结构化系统规划附件仍是待后续单独证明的承载建议，附件不增加普通规范责任数量。
