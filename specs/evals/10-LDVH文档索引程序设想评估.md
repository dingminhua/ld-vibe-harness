# LDVH 文档索引程序设想评估

> 创建日期：2026-06-01
> 定位：LD Vibe Harness 对 Python 文档索引程序、AI 文档咨询读取路径和章节索引治理影响的内部评估
> 调研边界：不直接构成强制规则
> 执行效力：无，结论需进入 00-79 正式规范区间、Tools 规范或 ADR 后才成为稳定规则
> 编号归属：`specs/evals/` 项目评估与内部辅助文档，编号仅用于排序和引用便利，不属于 specs 正式规范编号体系
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`、`specs/01-LDVH目录说明.md`、`specs/03-Specs文档规范.md`、`specs/10-事实源边界与承载规范.md`
> 相关规范：`specs/11.01-Rules机制规范.md`、`specs/12-LDVH工具基础规范.md`、`specs/12.01-Tools辅助规范.md`、`specs/14-LDVH行动模型基础规范.md`

## 1. 本文解决的问题与结论

本文记录一个后续可推进的设想：使用 Python 程序扫描 LDVH 文档体系，生成机器可读的文档索引，使 AI 在进行文档咨询、规则判断、规范定位和影响分析时，先读取索引，再按需读取正文片段。

本文是内部评估，不直接改变现有 specs 正式规范、Rules、Tools 或文档骨架要求。若后续推进，应先进入正式规范或 ADR，再实施工具、目录、Rules 和文档骨架调整。

### 1.1 核心结论

LDVH 可以考虑建设文档索引程序。该程序的合理定位不是新的事实源，而是 Tools 生成的派生索引和读取导航层。

核心判断如下：

1. Python 生成索引可以显著降低 AI 文档咨询时的搜索成本和上下文消耗；
2. 索引适合承载文件清单、头部元信息、章节树、行号范围、引用关系和机制关系；
3. 索引不能替代 specs 正文、Rules 正文或 `ldvh-base/` 事实实例；
4. 索引与正文冲突时，应以正文为准，并重新生成索引；
5. 文档内手工维护的“章节索引”在机器索引稳定后可以考虑降级为可选，但不建议第一阶段直接删除；
6. 如果索引成为 AI 优先读取入口，`specs/11.01-Rules机制规范.md`、L0、L1、L2 Rules、Tools 规范、目录说明和文档规范都可能需要同步调整。

### 1.2 建议推进方式

建议分阶段推进：

| 阶段 | 目标 | 说明 |
|---|---|---|
| 第一阶段 | 建设只读索引程序 | 不改变现有文档骨架，不删除章节索引，只生成派生索引 |
| 第二阶段 | 将索引作为 AI 优先定位辅助 | 调整读取流程，索引缺失或过期时回退到搜索定位 |
| 第三阶段 | 评估章节索引是否降级 | 在索引程序稳定后，再决定是否修改 03 文档骨架 |
| 第四阶段 | 纳入正式 Tools 治理 | 将索引程序、输出目录、更新时机和检查规则写入正式规范或 ADR |

## 2. 背景与动机

LDVH 文档体系包含 specs 根目录正式规范、模型实践子文档、Contract 子文档、evals 内部评估文档、refs 外部资料引用以及项目 Rules。随着文档数量增长，AI 在回答文档咨询或执行规范判断时，需要先识别项目上下文、读取 L1、定位相关规范、查找章节，再读取正文片段。

当前读取路径主要依赖：

1. L0/L1/L2 Rules 的入口提示；
2. L1 必读入口中的章节级指引；
3. 文档内“章节索引”；
4. 搜索工具定位标题或关键词；
5. 按行范围读取正文。

该路径已经符合读取精准原则，但仍存在以下成本：

1. AI 每次都需要重复搜索相关章节；
2. 搜索结果可能混入无关文档；
3. 文档内章节索引需要人工维护，可能与正文标题不同步；
4. 规则、Contract、Tools、Web、Agent 之间的机制关系需要跨文档查找；
5. 影响分析需要多次读取多个文档。

Python 索引程序可以把这些可机械化提取的信息预先结构化，从而让 AI 先拿到“地图”，再按需读取原文。

## 3. 索引程序的定位

### 3.1 应有定位

索引程序应定位为 Tools 辅助能力，负责从 Git 文件事实源中生成派生索引。

该索引服务于：

1. AI 文档咨询；
2. specs 章节定位；
3. Rules 读取入口辅助；
4. 文档一致性检查；
5. 机制关系和引用关系影响分析；
6. 后续 Web 或 MCP 展示与查询能力。

### 3.2 不应有定位

索引程序不应成为新的规范事实源，不应绕过原文读取，也不应把派生结果作为最终依据。

不应出现以下情况：

1. 用索引内容替代 specs 正文；
2. 用索引内容替代 `ldvh-base/` 事实实例；
3. 在索引中维护一套独立规则解释；
4. 索引过期时仍依据索引作正式判断；
5. AI 只读索引、不读原文就执行高风险规范变更。

### 3.3 事实源关系

建议关系如下：

```text
specs / Rules / ldvh-base 原文 = 最终事实源
Python 索引 = 派生索引和读取导航
AI 文档咨询 = 先读索引，再读原文片段
```

当索引与原文冲突时：

```text
以原文为准 → 重新生成索引 → 再继续判断
```

## 4. 索引内容建议

### 4.1 文档清单索引

文档清单索引记录每份文档的基本信息。

建议字段：

| 字段 | 来源 | 用途 |
|---|---|---|
| path | 文件路径 | 定位文件 |
| title | 一级标题 | 展示与检索 |
| doc_number | 文件名编号 | 判断编号分区 |
| doc_kind | 文件名和头部字段推断 | 判断文档类型 |
| created_at | 头部元信息 | 文档治理 |
| updated_at | 头部元信息或文件状态 | 变更判断 |
| positioning | 头部“定位” | 判断权威领域 |
| scope | 头部“适用范围” | 判断适用边界 |
| basis | 头部“上位依据” | 建立上位关系 |
| related_specs | 头部“相关规范” | 建立关联关系 |
| content_hash | 文件内容 hash | 判断索引是否过期 |

### 4.2 章节索引

章节索引用于按行范围读取正文。

建议字段：

| 字段 | 来源 | 用途 |
|---|---|---|
| path | 文件路径 | 定位文件 |
| heading_level | Markdown 标题层级 | 建立章节树 |
| section_number | 标题编号 | 支持 §N.N 引用 |
| title | 标题文本 | 检索和展示 |
| line_start | 标题所在行 | 精准读取 |
| line_end | 下一个同级或上级标题前一行 | 精准读取 |
| parent_section | 章节层级关系 | 构建树 |

### 4.3 引用关系索引

引用关系索引用于判断文档之间的依赖。

建议提取：

1. 头部上位依据；
2. 头部相关规范；
3. 正文中的 `specs/*.md` 路径；
4. 正文中的 `§N.N` 章节引用；
5. 机制关系声明表格中的关联实体；
6. Contract 与所属主文档关系。

### 4.4 机制关系索引

机制关系索引用于影响分析。

来源包括普通 specs 文档中的“机制关系声明”表格，以及模型实践子文档的主从关系。

建议字段：

| 字段 | 用途 |
|---|---|
| source_doc | 声明关系的文档 |
| mechanism | Rules / Skill / Agent / Tools / Web / Contract |
| entity | 被影响实体 |
| relation_type | 关系类型 |
| sync_trigger | 同步触发 |

## 5. 对文档内章节索引的影响

### 5.1 是否可以删除

从技术上看，文档内手工维护的“章节索引”可以由 Python 程序自动生成。程序可以直接扫描正文标题，得到更准确的章节树和行号范围。

因此，若索引程序稳定，文档内章节索引可以考虑从固定骨架中降级为可选。

### 5.2 为什么不建议第一阶段删除

不建议在第一阶段直接删除文档内章节索引，原因如下：

1. 当前 03 文档规范已将“章节索引”纳入正式规范文档骨架；
2. 人类直接阅读 Markdown 时，文档内章节索引仍有导航价值；
3. 章节索引可以作为索引程序的校验基准；
4. 批量删除章节索引会影响大量文档和检查工具；
5. 删除章节索引属于规范体系级变更，可能需要 Human Gate 和 Change 记录。

### 5.3 推荐处理

建议第一阶段保留文档内章节索引，但明确：

1. AI 优先使用 Python 生成的章节索引定位正文；
2. 文档内章节索引用于人类阅读和一致性校验；
3. 后续如需删除或降级，应先修改 `specs/03-Specs文档规范.md`；
4. 删除或降级前，应确认索引程序可以稳定生成等价章节树。

## 6. 对 Rules 读取机制的影响

### 6.1 对 11.01 的影响

如果索引成为 AI 每次文档咨询的优先入口，`specs/11.01-Rules机制规范.md` 的 L1 读取机制需要调整。

当前读取路径可以概括为：

```text
识别项目 → 读取 L1 → 根据 L1 必读入口搜索章节 → 按行读取正文
```

引入索引后的路径可能变为：

```text
识别项目 → 读取 L1 → 读取项目文档索引 → 根据索引定位文档和章节 → 按行读取正文
```

需要调整的内容包括：

1. L1 读取机制；
2. 必读入口粒度；
3. 读取精准原则的执行顺序；
4. Rules 审计时从 specs 根目录反向发现 Rules 需求的路径；
5. 索引缺失、过期或冲突时的回退机制；
6. Rules 检查项中关于索引入口和更新要求的检查。

### 6.2 对 L0 Rules 的影响

L0 可能需要增加索引读取入口摘要。

建议方向：

```text
读取项目文档或规范前，优先读取项目文档索引；索引缺失、过期或与正文冲突时，回退到搜索定位和行范围读取。索引只用于定位，不替代原文事实源。
```

L0 不应展开索引程序的完整规则，只应保留工作区级入口、回退原则和压缩保护。

### 6.3 对 L1 Rules 的影响

L1 可能需要新增项目索引入口，例如：

```text
项目文档索引路径
索引覆盖范围
索引读取顺序
索引缺失时的回退方式
```

L1 的“必读入口”不一定删除，但其角色可能从“直接读取文档清单”调整为“核心文档兜底入口和索引缺失时的回退指引”。

### 6.4 对 L2 Rules 的影响

L2 specs Rules 可能需要增加以下约束：

1. 修改 specs 文档头部字段、标题、章节、引用或机制关系声明后，应重新生成或校验索引；
2. 索引与正文冲突时，以正文为准；
3. 不得手工维护生成索引作为权威事实源；
4. 删除文档内章节索引前，应先修改 03 文档规范并评估影响。

## 7. 对正式规范和目录的影响

### 7.1 03 Specs 文档规范

03 可能是受影响最大的正式规范。

可能需要新增或调整：

1. 机器可读头部字段要求；
2. 章节标题可解析要求；
3. 文档内章节索引与自动索引的关系；
4. 索引生成和校验要求；
5. 机制关系声明对索引程序的 Tools 消费声明。

### 7.2 01 目录说明

如果新增 `.ldvh-index/`、`tools/index_docs.py` 或类似目录与文件，01 可能需要声明其目录性质。

建议原则：

```text
索引输出目录是 Tools 生成的派生数据目录，不是最终事实源。
```

### 7.3 12 和 12.01 Tools 规范

索引程序若成为长期能力，应纳入 Tools 辅助规范，说明：

1. 输入来源；
2. 输出契约；
3. 更新时机；
4. 过期判断；
5. 校验失败处理；
6. 与 AI、Web、MCP 的消费关系；
7. 派生数据不替代事实源的边界。

### 7.4 14 行动模型基础规范

14 可能需要把读取精准原则升级为更明确的读取顺序：

```text
索引定位 → 搜索定位 → 行范围读取 → 必要时全文读取
```

其中索引定位只是优化路径，不改变最终事实依据。

## 8. 初步实现建议

### 8.1 第一版输入范围

第一版建议只读：

1. `specs/*.md`；
2. `specs/evals/*.md`；
3. `specs/refs/*.md`；
4. `.trae/rules/*.md`；
5. 必要时读取 `ldvh-base/**/*.yaml` 的对象清单，但不做深度语义校验。

### 8.2 第一版输出

建议输出到派生目录，例如：

```text
.ldvh-index/docs-index.yaml
.ldvh-index/sections-index.yaml
.ldvh-index/relations-index.yaml
.ldvh-index/mechanism-index.yaml
.ldvh-index/hashes.json
```

若后续认为 YAML 过大，也可以使用 JSONL 或 SQLite，但第一版建议保持文本化、可 diff、可审查。

### 8.3 第一版功能边界

第一版只做确定性解析：

1. 扫描文件；
2. 解析文件名编号；
3. 解析一级标题；
4. 解析头部 `> 字段：值`；
5. 解析 Markdown 标题树；
6. 计算章节起止行号；
7. 提取路径引用；
8. 提取机制关系声明表格；
9. 输出 hash 用于过期判断。

第一版不做：

1. LLM 摘要；
2. 向量化；
3. 自动改写原文；
4. 自动删除章节索引；
5. 自动执行 Human Gate 判断；
6. 将派生索引作为权威事实源。

## 9. 风险与待确认问题

### 9.1 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 第二事实源 | 索引被误当作规范正文 | 明确索引是派生数据，冲突时以原文为准 |
| 过期索引 | 文档变更后索引未更新 | 使用 hash 或 mtime 判断过期 |
| 规则体系联动过大 | 11.01、L0、L1、L2、03、12、14 都可能受影响 | 分阶段推进，先只读辅助 |
| 章节索引删除过早 | 影响人类阅读和现有骨架 | 等工具稳定后再评估降级 |
| 解析规则脆弱 | 头部字段、表格格式不统一导致漏提取 | 先输出校验报告，不自动修正文档 |

### 9.2 待确认问题

1. 索引输出目录是否使用 `.ldvh-index/`；
2. 索引是否纳入 Git 版本管理；
3. 索引程序是否作为 `tools/` 下正式 Tools；
4. 是否需要为索引输出定义 Contract；
5. 文档内章节索引未来是保留、降级还是删除；
6. L0/L1/L2 Rules 何时切换到索引优先读取；
7. 是否需要 Web 页面展示索引和引用关系；
8. 是否需要 MCP 对外提供索引查询能力。

## 10. 后续推进建议

建议后续如要推进，按以下顺序处理：

1. 先新增 ADR 或 Task，确认索引程序建设是否进入正式计划；
2. 明确索引输出的事实源性质和目录位置；
3. 在 Tools 规范或 ADR 中定义索引程序的输入、输出和边界；
4. 实现只读 Python 原型；
5. 用原型扫描现有文档，输出索引和不一致报告；
6. 根据报告判断是否需要补充头部字段或统一章节标题；
7. 再修改 11.01、L0、L1、L2 的读取入口；
8. 最后再评估是否调整 03 中的“章节索引”骨架要求。

本文只作为后续决策材料，不直接触发以上变更。
