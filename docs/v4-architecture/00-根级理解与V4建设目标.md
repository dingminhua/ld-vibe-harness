# 00 根级理解与 V4 建设目标

> 记录性质：对当前正式 `specs/00-理念与构成.md` 的工作理解和 V4 建设目标说明，不是规则源，不授权产品行为。
> 权威边界：本记录只能帮助后续工作对齐 00，不得反向解释、扩大、弱化或覆盖 00；发生冲突时以 00 为准。
> 记录日期：2026-07-11

## 1. 核心理解

LDVH 的目标不是管理 AI，而是为 AI 建立一套可定位、可理解、可执行、可验证、可接续的长期项目工作环境，使 Vibe Coding 不会随着项目持续演进而逐渐失控。

V4 要建设的不是一批孤立的规范文件，而是一个能够持续帮助 AI 做好项目的 Harness。

## 2. LDVH 要解决的根本问题

AI 擅长语义理解、推理、规划、工具调度和生成，但具有三个天然限制：

1. 输出具有概率性，相同问题可能形成不同判断；
2. 判断高度依赖当前上下文，信息缺失、过载或冲突都会影响结果；
3. 不天然保存跨会话稳定状态，容易遗忘依据、重复犯错或丢失进度。

这些限制在长期项目中容易表现为：

1. 找不到真正适用的规则和事实；
2. 不清楚当前状态、影响范围和验收要求；
3. 每次重新读取大量材料；
4. 决策、实现和验证脱节；
5. 一次会话结束后无法稳定接续；
6. 经验虽然存在，但后续 AI 找不到、无法判断是否适用或无法消费；
7. 项目产出越多，维护负担反而越重。

LDVH 应补足这些限制，使 AI 的推理能力建立在稳定、可验证、可接续的项目基础上。

## 3. AI 是第一服务对象

设计任何规范、字段、模型、命令或流程时，应优先回答：它是否真正帮助 AI 更快、更准确、更稳定地完成长期项目工作。

Human 负责表达目标和方向，并保留必须由 Human 作出的选择、授权、风险接受、验收和方向校正。LDVH 不应要求 Human 充当 AI 的记忆库、人工路由器或每一步行动的审批者。

未命中来源规范声明的具体规则时，AI 的普通求解路径保持自主；LDVH 不以全局流程无差别控制 AI。

## 4. Helper 是面向 AI 的统一服务入口

总体关系为：

```text
规范模型、事实模型、行动模板、Code → Helper → AI
Code → 实现 Helper CLI
Web → Human
```

Helper 应围绕当前任务和工作对象，帮助 AI 获得：

1. 当前项目和工作对象；
2. 真正适用的规则；
3. 相关事实、状态和历史依据；
4. 当前已经实现且可以实际调用的能力；
5. 可执行行动及其边界；
6. 结果的验证、回写和接续要求；
7. Human Gate 或 Stop Conditions 的命中情况及最小受影响范围。

Helper 不是第六类构成要素。Code 负责实现 Helper CLI 的程序、解析、校验和受控操作；Helper 在架构层组织并消费适用的规范模型、事实模型、行动模板和 Code 能力。

## 5. 五类构成要素的目标职责

### 5.1 规范模型

规范模型定义正式 Specs 及其授权附件的身份、结构、关系和规则表达方式，使规则、边界和价值标准能够由 Human、AI 和 Code 稳定消费。取得正式效力的 Specs 正文及其授权附件构成规则源；模型、索引、Helper 输出和 Code 派生结果不得取得独立规则权威。具体规则的适用与效力仍由来源规范决定，不能把没有命中具体规则的普通求解变成全局强制流程。

### 5.2 事实模型

事实模型在事实源边界内组织长期需要保存的状态、决策、证据和经验。稳定事实必须以 Git 可追踪文件为有效承载，并具有明确组织和消费位置。

聊天、AI 推理、缓存、工具输出、Web 状态和派生结果不能自动成为稳定事实；只有按来源规则回写并验证后，才可能取得相应事实身份。

### 5.3 行动模板

行动模板沉淀重复场景中的适用条件、输入、关键步骤、验证入口、回写和交还方式，帮助 AI 稳定执行。它不能重新定义领域规则、事实语义或其他规范的权威关系。

### 5.4 Code

Code 承担不应由 AI 反复依靠概率完成的确定性工作，包括解析、索引、查询、聚合、校验、测试、上下文压缩、受控写入和结构化反馈。Code 负责实现 Helper，但旧 Code 结构不得反向决定 V4 架构。

### 5.5 Web

Web 面向 Human 呈现状态、风险、证据、待确认事项和验收信息。Web 独立读取相应 Source of Truth，不经过 Helper。本轮冻结 Web，待 V4 规则、事实和实现边界稳定后再单独校准。

## 6. V1–V8 的使用方式

V1–V8 从定位、理解、边界、推进、判断、接续、沟通和积累八个方面衡量 LDVH 为 AI 提供的价值。

任何新增规范、字段、模型、命令或机制，都应判断其给 AI 带来的收益是否大于阅读、理解、维护和执行负担：

```text
给 AI 带来的帮助
- 阅读、理解、维护和执行负担
= 是否值得纳入 LDVH
```

“更完整”“更正式”或“行业中存在”本身不是采用理由。低频内部迁移、没有明确消费方、无法验证、增加大量日常字段或强迫 AI 每次执行额外流程的机制，不应轻易进入核心规范。

## 7. 状态与声明必须真实

V4 必须始终区分：

```text
规范已设计
≠ Code 已实现
≠ 环境已接入
≠ 端到端已验证
≠ 当前可用
```

Human 同意不能代替技术验证，文件静态存在不能证明能力可用。未覆盖、未实现、未接入或未验证的内容，不得宣称为已保障、`available`、`integrated` 或 `completed`。

## 8. 目标使用体验

理想情况下，一个 AI 进入长期项目后不需要先理解 LDVH 的全部内部结构，而可以：

1. 通过 Helper 确认项目和当前工作对象；
2. 获得与当前任务相关的规则、事实、状态和可用能力；
3. 区分强制要求与自主判断空间；
4. 调用确定性能力完成解析、校验和受控操作；
5. 在真正重复的场景中使用行动模板；
6. 获得明确的验证结果和残留风险；
7. 将需要长期保存的结果写回事实源；
8. 在另一次会话、模型或环境中稳定接续；
9. 需要 Human 决定时，清楚交还对象、依据、风险和选择；
10. 不把未实现或未验证的事情误报为完成。

Human 则可以通过 Web 和必要的交还信息理解项目，而不必参与每个内部步骤。

## 9. V4 重建目标

V4 的目标不是恢复 V3 的所有能力，而是从 00 出发，重新建立一套责任清楚、负担更低、机器可消费、状态真实，并真正通过 Helper 服务 AI 的 LDVH。

总体建设顺序应为：

```text
理解 V3 解决过的问题和失败原因
→ 确定 V4 各独立规范必须承担的职责
→ 建立最小且完整的规范模型与规则效力
→ 建立事实模型和行动模板
→ 定义 Helper 服务契约
→ 为 Code 构成要素完成系统规划，并核验、选择适用的外部工程实践要求
→ 从 V4 契约按最小端到端可验证实现增量建立模块化 Code 和 tests
→ 接入真实环境并进行端到端验证
→ 最后校准 Web
```

凡是不能推动上述目标、不能证明对 V1–V8 有可辨认净价值的内容，都不应因为 V3 曾经存在而自动进入 V4。

## 11. 后续判断与报告纪律

全面评估 V3 资产、V4 候选独立规范职责和具体实现方案是执行者的责任，不能把庞大矩阵或底层技术选择整体交给 Human 代为发现是否偏离 00。当前 V4 00 是所有后续判断的最高约束，不只是参考材料。

### 11.1 判断顺序

每个架构、规范、字段、Schema、Code 或测试决定都必须依次回答：

1. 00 是否已经直接规定；
2. 它服务 00 中的哪个目标；
3. 它归属于哪类构成要素；
4. 它如何通过 Helper 服务 AI，或者通过 Web 服务 Human；
5. 它为 V1–V8 中哪些价值提供可辨认净收益；
6. 它是否扩大规则作用范围；
7. 它是否限制未命中规则时 AI 的普通求解；
8. 它是否制造第二规则源或第二事实源；
9. 它是否把设计、实现、接入和验证混为一谈；
10. 它是否改变 Human Gate、Stop Conditions 或 Web 边界。

无法清楚回答时，不得直接进入正式设计。

### 11.2 三类处理方式

**00 已经明确规定：**直接遵守，不重新发明。

**00 未直接规定但可以稳定推导：**可以继续推进，但必须说明 00 依据、推导过程、V1–V8 净价值、未改变的根级边界和验证方法。

**存在多种合理解释或可能改变 00：**暂停受影响的决定并报告 Human，不自行选择。

### 11.3 必须报告的情况

对以下事项存在不确定性时，必须先向 Human 报告：

1. 新增、删除、改名或重排构成要素；
2. 改变 Helper 或 Helper CLI 定位；
3. 改变规则源、规范模型或事实源边界；
4. 改变规则适用与 AI 普通求解自主边界；
5. 引入新的顶层模型或架构概念；
6. 改变 V1–V8、Human Gate 或 Stop Conditions；
7. 改变 Web 与 Helper 的关系；
8. 将 V3 内容带入 V4，但无法证明其仍然适用；
9. 行业实践与 00 存在张力；
10. 无法证明新方案优于 V3；
11. 无法区分设计、实现、接入和验证状态。

报告使用以下结构：

```text
待决定问题：
00 的相关依据：
已经确认的事实：
不确定或冲突之处：
可选方案及影响：
执行者的判断与理由：
需要 Human 决定的内容：
```

### 11.4 架构调查与决策输入的参考顺序

```text

→ Human 已明确作出的 00 层面决定
→ 已接受的 V4 下位规范
```

## 12. Specs 结构讨论记录

本节记录 Specs 最终结构与命名讨论中已经识别的稳定问题、暂定理解和待决定分歧。本节不是正式规则源，不代替后续正式 Specs 正文。

### 12.1 工作对象与管辖范围

候选名称为《工作对象与管辖范围规范》（Work Objects and Governance Scope Specification）。当前暂定理解如下：

1. 它的核心责任是根据用户目标、实际工作对象和可复核环境证据，判断当前事项是否进入 LDVH 管辖范围，以及 Helper 后续应为哪些对象提供什么范围的服务。
2. 不应把该责任简化为“是否启动 Helper 服务”；管辖判断本身可以由 Helper 的轻量解析能力提供。
3. AI 根据用户目标和自然语言识别工作对象候选；环境入口提供 `cwd`、target、路径、Git 等结构化信息；Helper 根据规范定义的证据和优先级完成可复核的管辖解析。Code 不应依赖猜测任意自然语言意图决定管辖。
4. 解析结果至少需要区分：命中单一管辖对象、明确非管辖对象、管辖范围无法确认、多对象或混合对象。它们分别导向完整 Helper 服务、`no-op`、能力或信息缺口、拆分/分流/Human Gate。
5. 管辖范围命中只表示当前事项进入 LDVH 服务和规则判断范围，不等于所有 LDVH 规则自动生效。具体规则是否适用，仍由规则适用与效力规范及具体来源规范判断。
6. 该规范不应继承 V3 《安装与配置规范》中的职责混合；安装、Hook、环境接入、配置写入和 Helper CLI 具体命令应由其他规范或实现职责承担。

2026-07-12 复核 V3 真实配置和 Code 后，进一步确认：

1. 保留成熟文件名 `LDVH-GOVERNED-PROJECTS.yaml`，并保留 Human 选择的工作区根目录作为主位置；工作区根可以位于各项目 Git 仓库之外。
2. 该文件是 Helper/Code 的本机工作区配置输入，不属于事实模型，不是项目事实对象，也不得冒充 00 定义的事实源或规则源。
3. 配置语义与字段契约由 02 及其授权附件承担；安装、写入、备份、恢复和回滚由后续行动模板与环境接入职责承担。
4. Human 当次指令可以指定工作对象，但不能在不修改并验证配置的情况下临时创建、排除或改变管辖关系。
5. 配置文件本身可以位于 Git 之外，但配置中登记的管辖项目必须是有效 Git worktree，以满足 00 对项目稳定事实的 Git 可追踪承载要求；`git` 配置字段仍可选，由 Code 在消费时从项目路径复核。

### 12.2 AI 强制要求、可变协作偏好与 ADR 的职责划分

2026-07-12，Human 在继续检查候选内容后确认：V4 不建立独立《AI 行为规范》，也不建立《AI 规则履行规范》。如果广义 AI 行为责任中没有其他来源无法承担的独立稳定规则，为了保留 V3 名称建立空壳会重新形成兜底容器。

相关内容按以下边界分别承担：

1. 规则适用、命中义务和最小作用范围归规则适用与效力责任及具体来源规范；
2. 事实、证据、推测和如实声明的边界归事实源与信息溯源、验证与声明责任；
3. Human Gate、暂停、交还和能力缺口归 00、实际来源规范和 Helper 服务契约；
4. 反复出现的行动结构归行动模板；未命中规则或模板的普通求解路径保持自主。

“矩阵型答复是否使用 SVG”等可随时调整的输出、交互或协作偏好，默认不是永久规则。当次需要由作用范围清楚的 Human 当前指令承载；需要跨会话、按项目或工作对象保留时，可候选建立“AI 协作偏好”事实记录，由未来事实模型判断是否纳入，并用实例表示作用范围和启用/关闭状态。

ADR 只记录为什么选择某项偏好或信息提供、检查机制，不承载当前开关，也不自动产生规则效力。如果某项可变配置需要“必须执行”的效力，必须先由正式来源规范定义参数、适用范围、优先级和效力；事实实例只提供当前值，不成为第二规则源。Human 当前指令和已启用协作偏好也不得覆盖已适用来源规则的强制要求、Human Gate 或 Stop Conditions。

Helper、Code 和环境机制可在已规划、已实现、已接入且可验证的范围内提供、检查或反馈当前规则、Human 指令与协作偏好，但这些机制不形成第六类构成要素或第二规则源。

### 12.3 Code 的系统规划与工程实践要求

2026-07-12，Human 明确要求暂缓 V4 Code 的修改或新建，先完成 Code 的系统规划。当前确认的讨论基线如下：

1. 系统规划与工程实践要求由 00 定义的 Code 构成要素承担，不形成新的“实践层”，也不取代 Helper 的架构层入口。
2. 后续 Code 相关正式规范必须纳入经当前外部资料核验、确认适用的工程实践要求，并在实现前明确系统分解、模块职责、模块引用与调用方向、接口与数据契约、测试策略、可维护性约束，以及文件、类和函数的规模或复杂度控制与重构触发条件。
3. 外部工程实践是设计输入，不因外部资料存在而自动成为 LDVH 规则；只有经过 00 和 V1-V8 判断、被正式来源规范吸收后，才取得相应规则效力。
4. 已核对的 V3 样本显示，`archive/v3/code/ldvh_specs.py` 为 7,817 行，包含 181 个顶层函数或类（计入嵌套定义共 184 个），并混合规范、事实、项目、Action Guide、runtime 和 commit gate 等多类责任；`archive/v3/tests/code/test_ldvh_specs_validate.py` 为 7,310 行。这些是缺少稳定系统分解和持续模块治理的高风险信号。
5. 行数本身不足以证明设计错误，也不在此预设一个适用于所有语言和文件的统一上限。后续规则应结合一个模块承担的职责数量、模块引用与调用关系、复杂度、变更频率、测试性和可导航性定义可执行的阈值与重构条件。
6. Code 的系统规划与工程实践要求由独立规范正文、其授权附件或行动模板如何分别承担，尚待相应规范设计时确定；行动模板不能仅因属于构成要素而取得规则权威，不应在规则来源和承载边界明确前先写实现。
