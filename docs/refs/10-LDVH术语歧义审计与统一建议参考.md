1. 平台 / 环境；
2. 能力 / 承接项；
3. 支持状态 / 承接类型；
4. 检查 / 校验 / 验证 / 审计；
5. 写入 / 回写 / 受控写入 / 受控轻写入；
6. 工作模型 / 工作对象 / 字段内容格式；
7. 状态 / 对象状态 / 集合状态 / 检查过程状态；
8. 规范落地要求 / LDVH落地与检查 / 跨环境融合落地；
9. 工作流程 / 行动 / 步骤 / 阶段标签；
10. Review / 审阅 / 审核。

用户确认：该事项需要记录到新的参考文档中，当前不适合直接推进规范修改；当前优先推进的仍是落地相关工作。

## 2. 审计方式

### 2.1 审计范围

本轮审计范围为：

```text
ld-vibe-harness/docs/specs/
```

重点覆盖：

1. `02-术语规范.md`；
2. `03` / `03.xx` 文档规范；
3. `04` / `04.xx` 规范落地、环境适配、运行投影和平台适配清单；
4. `05` / `05.01` 工作模型基础和字段内容格式；
5. `06` 工作流程基础规范；
6. `20` 工作模型集合索引；
7. `21` 至 `29` 工作模型文档；
8. `40` 工作流程集合索引；
9. `41`、`42`、`44` active 工作流程文档；
10. 典型平台适配清单 `04.07`、`04.08`。

### 2.2 子 Agent 视角

本轮使用多个子 Agent 并行审计，每个子 Agent 聚焦一个语义视角：

| 视角 | 审计重点 |
|---|---|
| 术语规范 / 命名口径 | 术语定义、同义词混用、章节命名、正文推荐写法 |
| 环境 / 平台 / 适配 / 承接 / 运行投影 | 环境、平台、适配、承接、运行投影、运行投影状态、平台清单边界 |
| 规范落地 / landing / 检查 / 验证 / 审计 / 回写 | 落地、landing、检查、校验、验证、审计、写入、回写、过程输出 |
| 工作对象 | ADR、Task、Memo、Pitfall、Change、事实源、证据、状态、字段内容格式 |
| 执行流程 | workflow、Scenario、action、step、Apply、Repair、Verify、Review、Recheck、Human Gate |

### 2.3 检查方法

子 Agent 使用了以下检查方法：

1. 全量检索 `docs/specs` 中高频术语及其变体；
2. 扫描文件名、一级标题、章节标题和表头；
3. 对重点文档做语义阅读，确认术语在上下文中的实际含义；
4. 交叉对比 `02-术语规范.md`、`04` 系列、`06-工作流程基础规范.md`、`41`、`42`、`04.07`、`04.08` 的定义与使用；
5. 区分正式术语、文件路径历史名、字段名、过程输出字段和普通描述词；
6. 标注歧义来源、典型文件、风险等级和建议统一名；
7. 不直接修改 specs，先形成参考记录供后续统一处理。

### 2.4 判断原则

本轮审计采用以下判断原则：

1. 不把文件名中的历史名立即等同为正文推荐术语；
2. 不把过程输出、Web 状态、工具报告或对话结论升格为事实源；
3. 不把固定分类叫成状态，除非它有明确状态机；
4. 不把 LDVH 自身要求误写成环境能力；
5. 不把字段内容格式误写成工作对象；
6. 不把阶段标签误写成工作流程、状态机或事实源状态；
7. 优先收敛到 `02-术语规范.md`，再由对应规范应用；
8. 有 Human Gate、ADR 或文件重命名影响的事项后续单独推进。

### 3.1 平台与环境

已确认：LDVH 正式模型统一使用“环境”。

决策内容：

1. `环境` 作为 LDVH 正式模型词；
2. `平台` 降级为外部产品、历史清单或文件名语境；
3. Trae Work CN、Codex App、Claude Code CLI 在 LDVH 中称为三个 AI 开发环境；
4. 22 号文档已切换为“跨环境承接复用、环境薄入口、三环境承接矩阵、跨环境融合落地”；
5. 04 系列文件改名需要另行讨论，不能只改 04.06 / 04.07 / 04.08。

建议后续术语：

| 建议术语 | 用途 |
|---|---|
| AI 开发环境 | AI 工具及其上下文入口、权限、指令、命令、Hook、MCP、Agent、Human 确认方式等承载条件的组合 |
| 环境薄入口 | 环境侧用于加载或触发 LDVH 的轻量入口 |
| 环境承接 | 环境如何承接 LDVH 共享内核中的承接项 |
| 三环境承接矩阵 | Trae Work CN / Codex App / Claude Code CLI 的横向承接对比矩阵 |
| 跨环境承接复用 | 同一 LDVH 共享内核在不同 AI 开发环境中的承接复用 |
| 跨环境融合落地 | 22 负责的跨环境承接结果如何并入 LDVH 体系 |

### 3.3 04.07 / 04.08 后续处理

### 3.4 当前落地与检查报告

已确认：42 输出统一中文名采用“当前落地与检查报告”。

建议用法：

| 场景 | 推荐写法 |
|---|---|
| 普通语境 | 当前落地与检查报告 |
| 强调 42 | 42 当前落地与检查报告 |
| 不推荐 | 当前过程报告、检查报告、42 过程报告、首次检查报告 |

### 3.5 Apply 中文名

已确认：暂定，不在本轮决定。

候选项：

| 候选 | 含义倾向 | 风险 |
|---|---|---|
| 受控写入执行 | 强调写入动作受控 | 可能偏 Code / 文件写入，覆盖不了非写入执行 |
| 授权落地执行 | 强调 Human Gate 授权后执行 | “落地”仍偏泛，需要和规范落地区分 |

当前处理：后续结合 21 受控执行闭环继续讨论。

### 3.6 Review 中文名

待进一步确认：审阅与审核的区别需要对齐。

初步建议：

| 中文 | 倾向含义 | 适用场景 |
|---|---|---|
| 审阅 | 阅读证据、结果、风险和建议，形成判断或意见 | AI / Human 对结果、报告、候选修复、候选行动的 review |
| 审核 | 带有批准、否决、放行或验收意味 | Human Gate、正式批准、发布前审批、状态关闭前确认 |

因此：

1. `Review` 阶段若主要是看证据和结果，建议中文为“审阅”；
2. 如果该动作产生批准、否决、放行或关闭权限，建议使用“审核”；
3. `Human Gate` 中的确认更接近“审核 / 批准”，而不是普通审阅；
4. 后续需要在 02 或 06 中正式定义边界。

### 3.7 open_items 中文名

已确认：统一使用“待补齐事项”。

说明：

1. 矩阵字段、规范末章和后续中文表头都应使用“待补齐事项”；
2. 字段名如需保留英文，可继续使用 `open_items`；
3. 中文显示不再区分“待补齐项”和“待补齐事项”。

### 3.8 source docs 中文名

已确认：统一使用“来源”。

说明：

1. 中文表头和正文推荐使用“来源”；
2. 不推荐“来源文档”作为固定术语，因为来源可能包括规范、refs、命令输出、现有清单、Human Gate 记录或其他事实源；
3. 字段名如需保留英文，可视具体合同使用 `sources` 或 `source_refs`，后续再定。

## 4. 主要歧义清单

### 4.1 环境 / 平台 / 适配 / 承接

| 问题词 | 风险 | 建议 |
|---|---|---|
| 平台 | 容易以外部产品视角替代 LDVH 环境模型 | 正式模型用环境；平台仅保留在历史清单、文件名或外部产品说明中 |
| 平台适配清单 | 与三环境承接矩阵方向不一致 | 后续整体讨论 04 系列改名 |
| 平台能力 | 容易把环境承接项误当 LDVH 能力 | 用环境能力或承接项，按上下文区分 |
| 能力项 | 容易把 Code / Web / 验证 / 回写塞入环境矩阵 | 环境矩阵中统一用承接项 |
| 能力支持状态 | 容易误解为状态机 | 用承接类型 |
| 承接机制 | 层级过泛 | 规范层用保障机制；环境层用承接方式；实体层用运行投影 |
| 实际承接证据 | 容易被当事实源实体 | 建议改为实际承接检查结论或运行投影现场状态证据 |
| 运行投影状态 | 容易长期状态化 | 建议写运行投影现场状态 / 当前检查结论 |

### 4.2 落地 / 检查 / 验证 / 审计

| 问题词 | 风险 | 建议 |
|---|---|---|
| 规范落地 | 语义过泛 | 具体写规范落地要求、规范落地统筹、LDVH落地与检查或跨环境融合落地 |
| 规范落地章节 | 不够精确 | 写规范落地要求章节 |
| 当前过程报告 | 与 42 输出名不统一 | 改为当前落地与检查报告 |
| 检查报告 | 太泛 | 改为当前落地与检查报告或具体检查结果 |
| 检查 | 可保留，但需和校验、验证、审计区分 | 用于符合性判断或当前状态判断 |
| 校验 | 需专用于 Code / 工具机械检查 | 不替代人工检查或验证 |
| 验证 | 需专用于证明结果成立 | 不替代普通检查清单 |
| 审计 | 不应泛用 | 用于系统性、周期性、跨对象合规审查 |

### 4.3 写入 / 回写 / 证据

| 问题词 | 风险 | 建议 |
|---|---|---|
| 写入 | 泛称，可能误作事实源稳定化 | 保留为文件或字段修改动作 |
| 受控写入 | 需要区分 Code / Human Gate / Web | 定义为由流程、Code 或 Human Gate 约束的写入 |
| 受控轻写入 | 容易误作完整事实源回写 | 限定为 Web 对有限字段、状态或人工标记的轻量写入 |
| 回写 | 容易和写入混用 | 用事实源回写表示稳定结论进入权威 Git 文件事实源 |
| 证据 | 裸用过泛 | 写验证证据、关闭证据、Human Gate 记录、Change commit 证据 |
| Evidence | 容易被当工作对象 | 改为 Evidence 内容格式 / 验证证据格式 |

### 4.4 工作对象 / 状态

| 问题词 | 风险 | 建议 |
|---|---|---|
| 工作模型 | 与工作对象混用 | 仅指对象类别规则 |
| 工作对象 | 与字段格式或事实源混用 | 指按工作模型创建或识别的具体事实实例 |
| 事实对象 | 与事实源混淆 | 建议统一为工作对象或工作对象实例 |
| 字段内容格式 | 当前定义不足 | 需明确 Narrative / Checklist / Evidence / Decision 等不是工作对象 |
| 状态 | 跨层级复用 | 加限定词：对象状态、集合状态、运行投影现场状态、检查过程状态、派生状态 |
| Change | 容易被当 YAML 对象 | 写 Change commit 或 Change / Git commit 记录 |

### 4.5 流程 / 行动 / 阶段

| 问题词 | 风险 | 建议 |
|---|---|---|
| 工作流程 | 被泛化成任意步骤或命令 | 仅用于 40–59 流程规范或工作流程要素 |
| 行动 | 与工作流程并列误解 | 表示工作流程控制的一次执行或行动类别 |
| Scenario | 与适用场景混用 | Scenario 用于进入流程的判定条件；普通范围用适用场景 |
| 步骤 | 与阶段标签混用 | 用于流程内部顺序动作 |
| 阶段标签 | 容易被当状态机 | 用于 Entry / Plan / Apply / Verify 等阶段映射，不是状态 |
| Apply | 中文名待定 | 暂不推进 |
| Repair | 应拆候选修复生成 / 授权修复执行 | 避免未授权修复被执行 |
| Verify | 应是验证证据生成 | 不等于 Human 已审核或事实源已回写 |
| Review | 审阅 / 审核需定边界 | 暂记录，后续决策 |
| Recheck | 应是复检 | 不替代 Review 或 Verify |

## 6. 暂缓原因

本事项当前暂缓推进，原因如下：

1. 当前主线仍是 LDVH 落地相关事项；
2. 术语统一影响范围大，涉及 02、04、05、06、20–29、40–42、工具和引用；
3. 04 系列文件名变更需要单独讨论和迁移计划；
4. 部分术语仍有未决问题，例如 Apply 中文名、Review 中文名边界；
5. 若直接批量修改，容易打断当前落地闭环推进，并引入大规模引用漂移。

因此，本文件只记录审计方法、当前决定和建议路线。后续进入执行阶段前，应先由 Human 明确目标批次和改名范围。

## 7. 当前结论

当前已确认的最小结论：

```text

open_items 中文统一为“待补齐事项”；
source docs / source refs 中文统一为“来源”；
Apply 中文名暂定；
Review 的“审阅 / 审核”边界待后续确认。
```

本事项后续应作为独立术语治理任务推进，不应阻塞当前 LDVH 落地主线。
