## 1. 本文解决的问题

本文是 LDVH 自身文档工作区的应用剖面规范。`docs/` 是 LDVH 文档工作区根目录，`docs/specs/` 是 LDVH 规范正文区，`docs/evals/` 和 `docs/refs/` 是与 `docs/specs/` 并列的输入材料区。本文继承 `docs/specs/03-文档基础规范.md` 的文档工作区三分契约、命名、结构、引用和吸收规则，只规定 `<W>=docs`、`<B>=docs/specs` 时的特有规则。

LDVH 自身规范工作区的三分映射如下：

```text
docs/specs/        LDVH 正式规范正文区
docs/evals/        LDVH 内部评估和设计分析
docs/refs/         LDVH 外部资料引用
```

`docs/evals/`、`docs/refs/` 和用户明确指定的输入材料只提供分析输入；其中稳定结论必须先吸收到 `docs/specs/`、工作对象、ADR、Task 或 Memo 后才生效。

## 2. docs/specs 正文区

### 2.1 正文区定位

`docs/specs/` 根目录正文区承载 LDVH 正式规范。正式规范可以定义稳定规则、对象边界、字段契约、状态机、工作流程、Human Gate、规范落地要求和检查要求。

正式规范正文区不得引用 `docs/evals/`、`docs/refs/` 或输入材料作为规范依据。evals、refs 或输入材料中的稳定规则必须吸收到 `docs/specs/` 正文区后才成为正式规则；长期决策可以进入 ADR；可执行工作或暂存发现可以进入 Task、Memo 等工作对象，但这些对象不因此成为规范规则。

所有 docs/specs 正式规范文档都应设置规范落地要求段落，用于说明该规范要落地需要满足哪些要求。目录说明、编号索引、状态索引、evals、refs 和其他不直接定义稳定规范规则的说明性文档，不默认属于正式规范文档，不要求设置规范落地要求段落；若其中内容被升级为稳定规则，应吸收到对应正式规范后再声明规范落地要求。规范型集合索引按 `docs/specs/03.03-索引文档规范.md` 判断，若维护正式编号区段、集合状态、落地与检查输入或吸收输入，应视为正式规范文档。

### 2.2 编号分区

docs/specs 正文区使用当前编号分区。编号分区、编号占用和新增编号判断由 `docs/specs/01-目录说明.md` 承接。

正式规范文档使用两位编号，文件名格式使用“NN-标题”加 `.md` 后缀。子文档使用“NN.SS-标题”加 `.md` 后缀。固定机制子文档和结构化契约文件沿用既有编号时，必须遵守本文 §6。

### 2.3 正式规范文档骨架

正式规范文档建议采用以下骨架。骨架中标注【必填】的章节为强制要求，未标注的为建议结构；审计时仅检查必填章节，不得将建议章节缺失判定为违规。

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---
## 1. 本文解决的问题【必填】

## 2. 与 00 总纲的关系

## 3～N-2. 核心规则

## N-2. 规范落地要求【必填】

## N-1. Human Gate 与检查要求【必填】

## N. 待补齐事项
```

具体工作模型规范文档骨架由 `docs/specs/03.04-工作模型文档规范.md` 定义；具体工作流程规范文档骨架由 `docs/specs/03.05-工作流程文档规范.md` 定义。其他专项规范如无专用文档规范，应先遵守本文正式规范文档骨架。00 总纲作为顶层文档，可不声明上位依据；00 的 §1 可以使用产品存在理由或总纲叙事标题，不强制命名为“本文解决的问题”，但不得因此改变其他正式规范的标准骨架要求。

00、02 和其他正式规范的引用层级应遵守：

1. 00 是 LDVH 上位概念来源，不应把 02 作为自身上位依据、相关规范或一致性检查标准；
2. 02 应以上位依据承接 00，并负责术语边界、推荐用语、不推荐表达处理和术语变更治理；
3. 其他正式规范涉及产品定位、五类构成要素、事实源原则、运行闭环或 Human Gate 时，应按需要引用 00；
4. 其他正式规范涉及术语定义、不推荐表达处理、术语归口或术语变更治理时，应引用 02，不得并行维护同一术语定义；
5. 同一文档可以同时引用 00 和 02，但应分别说明上位原则承接和术语口径承接，不得混用。

正式规范文档不得设置“本文不做什么”“边界说明”等反向边界章节。职责边界应通过定位、适用范围、上位依据、相关规范和正文正向规则表达。

正式规范文档设置 `相关规范` 时，应遵守 `docs/specs/03-文档基础规范.md` §6.4 的引用方向规则。`相关规范` 是当前文档的读取依赖、字段契约依赖、同步依赖或检查依赖，不是“谁引用了本文”的反向清单；被引用文档不得仅因下游文档引用它而把下游文档登记回来。

## 3. docs/evals

`docs/evals/` 继承 `docs/specs/03-文档基础规范.md` §3.4 和 §3.6 的 evals 与吸收规则。本文只规定 `<W>=docs`、`<B>=docs/specs` 时的特例。

docs/evals 文档特例：

1. `docs/evals/` 承载 LDVH 内部评估、设计探索、方案比较、外部项目借鉴分析和项目内部临时参考；
2. docs/evals 可以引用 docs/specs 正文区作为评估依据和上位规范；
3. 稳定规范规则必须吸收到 docs/specs 正文区后，才能被正式规范文档作为规则消费；
4. 长期决策可以吸收到 ADR，可执行工作或暂存发现可以吸收到 Task、Memo 等工作对象，但不得被正式规范直接当成规则引用；
5. docs/evals 文档头部必须声明 `来源`，来源应指向被评估材料、用户输入、外部资料、调研对象或其他真实输入，不得只指向关联 Task；
6. docs/evals 文档头部可以设置 `关联对象`，用于登记相关 Task、Intent、ADR、Memo 或其他工作对象；该字段可以为空，且不得替代来源；
7. docs/evals 文件名应使用自然序号加 `LDVH` 前缀标识，格式为 NN-LDVH{评估主题}.md 或 NN-LDVH-{评估主题}.md，表示该文档是 LDVH 内部相关评估、分析或参考材料；

docs/evals 文档建议采用以下骨架。骨架中标注【必填】的章节为强制要求，未标注的为建议结构；审计时仅检查必填章节，不得将建议章节缺失判定为违规。

## 6. 固定机制子文档与结构化契约

### 6.1 固定机制子文档取消

LDVH 不再要求每个工作模型或工作流程默认拆分固定 `NN.01` 至 `NN.06` 机制子文档。

Rules、Skill、Agent、Tools、Web、Contract 只在有明确运行实体、实现入口或契约能力需要时维护，不构成当前 docs/specs 的固定组成。

新增或稳定后的机制内容应按机制归属进入对应权威位置。相关权威位置尚未创建或尚未生效时，应进入候选事项、计划或待补齐事项，不得直接引用输入材料作为正式规范：

1. 主规范规范落地要求；
2. 04 系列环境适配相关规范；
3. 工作流程基础规范；
4. `docs/specs/07-Code实现规范.md`；
5. `docs/specs/08-Web信息同步规范.md`；
6. 运行 Rules / Skill 实体、Agent 定义摘要或契约能力。

### 6.2 机制材料边界

机制材料不是独立规范，也不是工作模型或工作流程完整性的默认要求。机制材料只能说明对应模型或流程在某个机制下如何实践，不得重新定义主模型、主流程、字段契约、状态机、Context、Scenario、Gate、事实源边界或 Human Gate。

机制材料中的有效内容应随相关主规范、04 系列、07、08 或运行投影吸收。机制材料不作为当前 docs/specs 的读取入口，也不构成固定子文档机制要求。

### 6.3 结构化契约

结构化契约可以作为字段契约、schema、接口契约或机器消费契约存在，但不构成固定 `NN.06` 子文档要求。新增或稳定后的契约优先回并到主规范契约章节，或由 Code 和 Web 实现消费主规范契约。对应主规范尚未创建或尚未生效时，应记录为候选事项、计划或待补齐事项。

## 7. 规范落地要求与环境适配

LDVH 将规范到运行环境的同步拆成两层：

1. **规范落地要求**：说明某段稳定规范要落地，需要满足哪些要求，例如入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求、生命周期触发要求等；
2. **环境适配映射**：说明某类规范落地要求在 Trae、Codex、Claude Code、Cursor 或其他开发环境中，通过哪些机制、文件、配置、工具、入口或降级策略满足。

规范落地与环境适配的父规范入口是 `docs/specs/04-规范落地与环境适配基础规范.md`。正式规范只声明规范落地要求和保障机制；环境适配映射、运行投影、环境能力承接边界、LDVH 落地特别要求和个人落地特别要求，应分别按 04 系列对应子文档处理。

规范落地要求不是普通引用、文档重要性声明或上位依据声明。规范落地要求的类型、字段、保障机制和“不得直接把具体环境实体写成要求本身”的规则，以 `docs/specs/04.01-规范落地声明规范.md` 为权威；本文只要求 docs/specs 正式规范在创建、修改或审计时回到 04.01 检查该段落。

若某项规则要求在特定时机稳定触发，应声明生命周期触发要求，并由环境适配映射决定该环境使用 Hook、CI、自动运行、规则条件、Skill 组合或降级检查实现。具体环境实体不得直接写入普通规范落地要求表，除非该文档本身就是环境适配映射文档。

遇到“机制落地关系”或“机制承接关系”等不推荐表达时，应按 `docs/specs/02-术语规范.md` 的不推荐表达处理，先拆解为规范落地要求和环境适配映射两层。无法确认环境实体的内容，只能先进入规范落地要求、候选事项或待补齐事项。

## 8. docs/specs 修改执行顺序

AI 新增、修改或审计 docs/specs 正式规范文档时，应按以下顺序执行：

1. 根据任务场景确定基础入口：术语边界、不推荐表达处理或术语变更治理读取 `docs/specs/02-术语规范.md`；文档工作区、命名、引用、evals/refs 或子文档边界读取 `docs/specs/03-文档基础规范.md`；docs/specs 正式规范、规范落地要求或固定机制子文档读取本文；规范型集合索引读取 `docs/specs/03.03-索引文档规范.md`；规范落地、环境适配、环境能力承接、LDVH 落地特别要求或个人落地特别要求读取 `docs/specs/04-规范落地与环境适配基础规范.md`；
2. 判断拟修改内容属于哪个规范权威领域；
3. 读取目标规范及其上位依据、相关规范；目标主题尚未创建或尚未生效时，读取集合索引、候选来源或用户指定材料，但不得把输入材料当作正式规范；
4. 按需读取 00 中与本次变更相关的产品定位、五类构成要素、价值实现标准、运行闭环标准和 Human Gate 要求；
5. 判断变更是否符合 00 上位原则，是否弱化事实源边界、Human Gate、验证纪律或五类构成要素分工；
6. 若变更涉及 00、02、上位依据、相关规范或术语口径，检查 00/02 层级是否仍符合本文 §2.3；
7. 若涉及高影响变更，触发 Human Gate；
8. 修改目标规范；
9. 按 `docs/specs/04.01-规范落地声明规范.md` 检查目标规范的规范落地要求段落，确认每项落地要求均声明要求内容、保障机制、同步类型和触发条件；
10. 判断文档结构、引用、输入材料边界和规范落地要求检查是否已有适配工具；
11. 若检查 Code 实现缺失或现有实现假设与 docs/specs 冲突，按 `docs/specs/03-文档基础规范.md` §9.1 形成文档检查 Code 缺口，并按 `docs/specs/07-Code实现规范.md` 完成 Code 需求准入、最小实现和测试验证；
12. 运行适配后的文档结构校验、引用校验和规范落地要求校验；
13. 检查是否需要更新规范落地要求；
14. 若变更影响运行投影，按 `docs/specs/04.02-环境适配与运行投影规范.md` 检查是否存在对应环境适配映射；不存在时记录为待适配事项；
15. 若变更涉及环境能力承接判断、工具缺口、LDVH 落地特别要求或个人落地特别要求，继续按 `docs/specs/04.03-环境能力承接边界规范.md`、`docs/specs/04.04-LDVH落地特别要求规范.md` 或 `docs/specs/04.05-个人落地特别要求规范.md` 检查；

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 重命名或重排 docs/specs 正式规范文档；
2. 改变 docs/specs 正文区、docs/evals 或 docs/refs 的引用方向规则；
3. 将 docs/evals、docs/refs 或输入材料结论直接作为强制规则使用；
4. 新增、删除或重命名应用剖面或专题子文档；
5. 恢复或新增固定机制子文档结构；
6. 改变规范落地要求或环境适配映射规则，或新增、修改、删除会影响运行投影同步检查、LDVH落地、审计或规则漂移诊断的规范落地要求；
7. 固定机制子文档新增或扩张基础规范；
8. 新增、替换或扩大 docs/specs 文档检查 Code 实现的判定范围。
9. 改变 00 作为上位概念来源、02 作为术语治理入口、其他正式规范按需引用 00 或 02 的层级关系。

规范文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 正式规范文档已声明上位依据，00 除外 |
| 00/02 层级 | 00 未把 02 作为自身上位依据、相关规范或一致性检查标准；02 以上位依据承接 00；其他正式规范按内容性质引用 00 或 02 |
| 编号分区 | 文档编号符合 docs/specs 当前编号分区，或已记录为候选事项、计划或待补齐事项 |
| 文档结构 | 文档骨架符合正式规范、工作模型文档、工作流程文档、evals、refs 或应用剖面要求 |
| 子文档边界 | 子文档只定义应用剖面特例或专题细则，未复制父规范通用规则 |
| 固定机制子文档 | 未恢复固定机制子文档结构 |
| 引用方向 | docs/specs 正文区未引用 evals、refs 或输入材料作为规范依据；`相关规范` 未仅因被下游引用而反向登记引用方 |
| 规范落地要求 | 仅声明规范要落地需要满足的要求 |
| 保障机制 | 每项规范落地要求均声明保障机制 |
| 环境适配映射 | 未把具体环境实体混入普通规范落地要求 |
| Code 适配 | 检查 Code 实现适配 docs/specs；缺失时已按 `docs/specs/03-文档基础规范.md` §9.1 和 `docs/specs/07-Code实现规范.md` 处理 |
| 校验 | docs/specs 修改后已运行适配后的文档结构和引用校验，或记录降级原因与残留风险 |
