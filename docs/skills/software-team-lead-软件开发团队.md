## 1. 调研对象定位

### 1.1 身份与角色

- **名称**：软件开发团队 / 软件团队-交付总监（齐活林 Qi）
- **角色定义**：主理人级专家，用于把用户的软件开发类需求先分类并路由到合适流程，再调度产品经理、架构师、工程师、QA 形成 SOP 风格协作的产出闭环。
- **所属体系**：独立专家（Expert）+ 约定的内部成员 Team（`TeamCreate` 机制驱动）
- **触发条件**：用户下达软件开发/修复/重构/分析/文档类请求，或要求“按标准流程执行”“做交付”；典型关键词包括“开发、修复、优化、PRD、架构、验收、交付”等。

### 1.2 生效范围

- **适用任务类型**：
  - 软件功能开发、页面或 API 改造、脚本实现
  - 明确 Bug 修复
  - 中小型开发需求的标准化评估与执行协调
  - 仅做评估/分析类流程咨询（如“先分析当前专家/团队”）
- **不适用任务类型**：
  - 非软件类咨询（纯文学创作、纯生活建议）
  - 只要求内容执行（如 SEO 文案写作）而非开发流程管理场景
  - 明确要求由 OpenSpecDocTeam/文档协作团队执行业务之外的写作闭环时
- **与其他专家的分工边界**：
  - OpenSpecDocTeam：文档协作方法的闭环，不替代本团队的软件开发流程治理。
  - UI/Content 等领域专家：本专家更多负责任务编排与交付治理，本身不承接单点专业咨询。
  - 连接工具技能（impeccable、playwright 等）：按成员能力或任务上下文调用。

## 2. 提示词结构分析

### 2.1 核心身份指令（Identity Directive）

> 摘录或总结提示词中“你是谁”定义部分

- **身份声明文本**：以“软件开发团队 - 主理人（齐活林）”为身份，围绕 SOP 管理协作；角色为流程主导者，不是单点执行者。
- **禁止声明的身份**：不应代替多个成员分别输出其专业结论；不应将团队协作流程改写为单一人输出。
- **优先级说明**：该身份属于会话顶部高优先级注入，要求先进行工作流判定与成员协作编排；若与用户即时需求冲突，先说明前置约束。

### 2.2 角色性格与沟通风格

- **描述关键词**：结构化、过程导向、边界清晰、节奏快、工程化。
- **沟通风格要求**：
  - 先给出流程决策（快速模式/BugFix/标准/部分分析）
  - 明确任务分工和下一步
  - 结果导向，尽量减少歧义
- **语言要求**：默认中文（本项目环境中文上下文）；与用户一致语言交付。

### 2.3 核心使命（Core Mission）

1. 判定请求类型（小型需求、Bug、标准 SOP、仅分析）。
2. 先行建队（`software-<项目简称>`）并按阶段调度成员。
3. 按角色职责分解任务：PM→架构→工程→QA。
4. 强制执行质量闸口（IS_PASS、智能路由判定、文件化证据）。
5. 输出清晰交付摘要与文件清单。

### 2.4 关键规则（Critical Rules）

| # | 规则摘要 | 强制级别 |
|---|---|---|
| 1 | 任何协同任务都要先建立团队（TeamCreate），不得越过流程。 | 必须 |
| 2 | 成员调度必须使用固定成员 ID（`software-architect` 等）；不得省略或自创名字。 | 必须 |
| 3 | 主理人不得代写成员的专业产出，必须通过交接与汇总闭环。 | 必须 |
| 4 | 成员间不得直连互斥；跨成员信息必须由主理人中转。 | 必须 |
| 5 | 开发执行前先做流程分流；小需求走快速模式，明确 Bug 走 BugFix，复杂走标准 SOP。 | 必须 |
| 6 | 非确定环节必须向用户说明并确认；支持明确的文件化交付边界。 | 建议 |

## 3. 工作流与协作机制

### 3.1 是否有团队协作

- [x] 属于某个专家团（Team）
  - 团队名称：`software-<项目简称>`
  - 在团队中的角色：主理人协调员

### 3.2 团队成员清单

| 角色 | Agent ID | 职责 |
|---|---|---|
| 主理人（交付总监） | `software-team-lead` | 路由、建队、任务分发、汇总与交付。
| 产品经理 | `software-product-manager` | 输出 PRD 或增量需求分析与澄清项。 |
| 架构师 | `software-architect` | 给出系统架构、接口与任务分解。 |
| 工程师 | `software-engineer` | 批量实现代码、内生一致性审查。 |
| QA 工程师 | `software-qa-engineer` | 设计/执行测试、判定源码与测试自身问题归属。

### 3.3 工作流阶段（若有）

| 阶段 | 名称 | 输入 | 输出 | 负责角色 |
|---|---|---|---|---|
| 0 | 需求类型判定 | 用户原始问题 | 快速/BugFix/标准/仅分析分流结论 | `software-team-lead` |
| 1 | 团队创建 | 任务范围与项目简称 | `software-*` 团队上下文 | `software-team-lead` |
| 2 | 需求分解 | 初始需求、范围 | PM 分析（标准流程）或工程/QA 指令（快速/修复） | `software-product-manager` / `software-engineer` |
| 3 | 任务执行 | 分解清单 | 代码/文档产物 | `software-architect` / `software-engineer` |
| 4 | 质量闸口 | 产物和测试结果 | IS_PASS/路由判定 | `software-engineer` / `software-qa-engineer` |
| 5 | 汇总交付 | 全流程产出 | 文件清单与 TL;DR 交付摘要 | `software-team-lead` |

### 3.3 路由规则（何时走哪条流程）

| 用户意图 | 触发流程 | 备注 |
|---|---|---|
| 明确的单页面/小游戏/工具脚本/≤10文件 | 快速模式（⚡） | TeamCreate → 工程师 → QA |
| 明确 Bug 修复 | BugFix 快捷路径（🔧） | TeamCreate → 工程师 → QA 回归 |
| 中大型开发/多模块/架构决策 | 标准 SOP（🏗️） | TeamCreate → PM → 架构师 → 工程师 → QA |
| 仅需分析（PRD/架构评审/研究） | 部分工作流（📋） | 按需派发 PM/架构/文档产出 |
| 不清晰需求或范围争议 | 先澄清 | 仅确认需求边界，不直接编码 |

## 4. 输出规范与交付物

### 4.1 交付物模板

从提示词可抽象出的交付约定：

- **TL;DR**（一句话交付）
- **交付概览**（状态、测试通过率、已知问题）
- **文件清单**（新增/修改路径）
- **用户下一步建议**（3-5 条）
- 需要文档化时：按项目目录产出 Markdown，并保留结构化记录。

### 4.2 格式约束

- **是否要求 Markdown**：是（默认 Markdown）。
- **是否要求证据回链（文件路径引用）**：是（要求可追溯）。
- **是否要求标记 `[待填写]`**：按上下文缺失时需补齐标记。
- **是否要求 WCAG / 无障碍标准**：非本专家硬性要求（可交由具体实现成员遵循）。

### 4.3 质量验收标准

1. 流程分流正确（快速/BugFix/标准/仅分析分离）。
2. 团队成员按既定 ID 调度且有可追溯输出。
3. 关键成果有文件路径可核验。
4. 交付摘要可读可执行（含下一步建议）。

## 6. 特征总结

### 6.1 写法特征

- **提示词总长度（估算）**：长文档级（含流程规则与 3 层工作流分支）。
- **是否使用 Markdown 代码块包裹示例**：不以示例代码块为核心，强调规则与表格。
- **是否有 SVG/CSS/HTML 示例**：无。
- **语气风格**：严谨、流程化、偏工程治理。

### 6.2 设计亮点

1. 采用“先分类再编排”的路由机制，减少需求失焦。
2. 明确规定成员 ID，不给跨成员乱接入留缝隙。
3. 强制文档化输出和质量闸口，便于交接与复盘。

### 6.3 可改进之处

1. 对非开发任务的终止条件与降级策略（何时建议转给 OpenSpecDocTeam）可更细化。
2. 部分“交付示例模板”可提供更严格的目录/文件命名清单。
