## 1. 本文解决的问题

本文定义 LDVH 事实模型的基础规则、事实模型、准入条件、通用规范和与 20-39 具体事实模型规范的关系。

LDVH 事实模型是 LDVH 对工程生产事实的自定义建模，用于承载工作项、决策、火花、研究报告和经验等工作事实，并通过字段契约、字段内容格式和字段注册消费规则承载风险判断、依赖关系、验证证据、产物引用、检查结果等结构化内容。

本文定义事实模型的基础规则和标准组成，但不定义具体事实模型清单、具体字段契约、具体状态机、具体验收标准、字段内容格式或字段注册表。字段层规则由 `specs/05.01-工作模型字段定义与语义规范.md` 定义；字段内容格式由 `specs/05.02-工作模型字段内容与格式规范.md` 定义；字段注册与消费元数据由 `specs/05.03-工作模型字段注册与消费规范.md` 定义；具体事实模型集合事实由 20-39 成员主文件自描述承载，具体规则由 20-39 区段的具体事实模型规范承载。

## 3. 事实模型的定义与定位

### 3.1 事实模型的定义

LDVH 事实模型是 LDVH 对工程生产事实的自定义建模，将项目中的工作项、决策、火花、研究报告和经验等工作事实抽象为具有明确字段契约、状态流转和验收标准的结构化对象，并通过字段内容格式承载风险判断、依赖关系、验证证据、产物引用、检查结果等结构化内容。

### 3.2 事实模型的核心特征

事实模型必须具备以下核心特征：

1. **规范由 LDVH 定义**：对象的准入条件、字段契约、状态流转、事实源边界和验收规则由 LDVH 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的事实实例属于项目，默认存放在该项目自身的 ldvh-base/ 目录中；具体事实模型可以声明承载介质例外，例如 Study 以 Markdown frontmatter 和正文承载报告实例。每个接入 LDVH 的管辖项目应各自拥有 ldvh-base/ 目录，由该项目自身管理（依据 `specs/01-目录说明.md` §4）；
3. **服务工程生产**：对象用于让 AI、人和工具围绕同一组项目事实协作，支持工作项、状态追踪、证据回写、决策追溯和变更审计；
4. **Git 可追溯**：事实实例必须以 Git 可追踪文件的形式承载，优先使用 YAML 格式（适合结构化字段）或 Markdown 格式（适合说明性内容）；
5. **单一事实源**：每个事实实例只能有一个权威承载位置，其他位置只能引用或聚合，不得复制并维护独立事实。

### 3.3 事实模型与临时信息的区别

| 维度 | 临时信息 | 事实模型 |
|---|---|---|
| 性质 | 执行过程中的局部选择、临时判断、聊天内容 | 结构化、可追溯、可验证的工程事实 |
| 持续时间 | 一次性，仅在当前执行上下文中有效 | 长期，可跨会话、跨执行轮次追踪 |
| 复用价值 | 无，仅服务当前执行 | 有，可被其他对象引用、可被 AI 后续执行参考 |
| 追踪需求 | 不需要独立追踪 | 需要独立追踪、状态流转和验收标准 |
| 承载位置 | 聊天记忆、工具缓存、命令输出等临时位置 | Git 文件事实源（specs/、ldvh-base/、docs/ 等） |

## 4. 事实模型

### 4.1 事实模型定义

事实模型是 LDVH 对某一类工程生产事实的标准化建模结构，用于统一描述该对象的对象定位与准入条件（含范围声明）、事实源边界、状态机、对象关系、Human Gate、字段契约、事实源回写与证据留存、适配边界和待补齐事项。

每个 20-39 具体事实模型规范，都是一个具体事实模型的定义文档。

### 4.2 事实模型的标准组成

一个事实模型应包含以下内容：

1. 对象定位与准入条件（含范围声明）；
2. 事实源边界；
3. 状态机；
4. 与其他对象的关系；
5. Human Gate；
6. 字段契约；
7. 事实源回写与证据留存；
8. 适配边界（AI 协作、Code 辅助、Web 信息同步）；
9. 待补齐事项。

事实模型规范的范围声明合并到 §1 对象定位与准入条件的头部；与上位基础规范的关系通过头部元信息的上位依据字段声明，不再独立成章。通用回写与证据规则、AI 协作规则、Code 辅助规则和 Web 同步规则由本文 §7 定义，具体事实模型规范只声明对象特有差异。

### 4.3 事实模型与事实实例

事实模型定义事实类别的规则，事实实例是项目中按事实模型创建的具体事实。

事实模型承载于 `specs/20-39`。除具体事实模型规范明确声明的事实源例外外，事实实例默认承载于 `ldvh-base/`；例如 Study 以 Markdown frontmatter 和正文承载报告实例，由 `specs/24-Study-研究报告.md` 单独定义。Git 提交记录不是事实模型，按 `specs/10-Git提交规范.md` 追溯事实源修改。模型不得承载具体实例状态，实例不得重新定义模型规则。

### 4.4 事实模型与行动编排

事实模型承载工程生产事实，行动编排控制 AI 如何行动。两者关系如下：

| 维度 | 事实模型 | 行动编排 |
|---|---|---|
| 核心问题 | 项目事实如何结构化、流转和沉淀 | AI 如何读取、判断、执行、停下和回写 |
| 规范区段 | `specs/20-39` | `specs/40-59` |
| 实例事实 | 事实实例默认承载于 `ldvh-base/`，具体模型可声明例外 | 行动执行结果按事实类型回写 |
| 关键约束 | 准入、字段、状态机、验收和对象关系 | Context、Scenario、Gate、回写、证据 |

行动编排可以创建、更新、检查或引用事实模型，但不得重新定义事实模型字段、状态机、验收标准或事实实例事实源边界。事实模型可以被行动编排创建、更新、检查或引用，但事实模型规范不得定义行动编排的 Context、Scenario、Gate、执行流程或事实源回写规则。

### 4.5 事实模型与工具实现

工具可以依据事实模型开发解析、校验、聚合、展示和受控写入能力。工具实现不得替代事实模型本身，也不得绕过模型定义的事实源边界和 Human Gate。

### 4.6 事实模型文件命名与适配边界

适用区段：事实模型（specs/20-39）。

20-39 主文件均为事实模型规范，文件名不重复"事实模型规范"字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

事实模型主规范是具体事实模型规则的唯一规范入口。新增事实模型时默认只创建 NN 主规范。环境适配内容应回并到主规范对应章节，或按能力归属进入对应权威位置。

具体事实模型规范应在主规范中定义字段规则、状态规则、验收规则和适配边界，不得把模型核心规则拆到分散文件中。

Rules、Skill、Agent、Code、Web 等能力或实现内容不得作为每个事实模型的重复维护结构。确需承接时，应按能力归属进入 04、06、07、08、运行 Rules、Skill 文件、Agent 定义摘要、Code 实现、Web 实现，或在事实模型主规范适配边界章节中保留摘要和引用。

结构化契约可以作为字段契约、schema 或校验接口继续存在，但其权威性来自事实模型主规范中的字段规则、状态机和事实源边界。

### 4.7 LDVH 级初始化、审计与检查边界

事实模型规范不定义逐对象实施前决策、价值与要素审查、部署适配初始化、部署适配审计或泛化合规检查。事实模型是否新增、升级、降级、停用或重排编号，由本文的准入条件、Human Gate 要求和 `specs/03.02-工作模型文档规范.md` 的成员自描述契约共同约束；Code 派生集合索引校验由 `code/spec_checks/index.py` 承接。

LDVH 初始化是 LDVH 级初始化，不是每个事实模型各自选择初始化内容。LDVH部署适配应依据 20-39 成员主文件自描述确认 active 事实模型清单，统一确认规范、事实源目录、实例命名、Rules、Skill、Agent、Code、Web 和结构化契约是否具备最低可用入口；Code 派生 active 事实模型清单由 `code/spec_checks/index.py` 生成。具体事实模型主规范只声明自身实例目录、文件命名、字段规则、状态规则、关系规则和对象特有实例检查，不重复 LDVH 级初始化流程。

LDVH 审计是 LDVH 级审计，主要检查LDVH部署适配是否完成、active 事实模型是否与 20-39 成员主文件自描述一致、事实源目录和实例是否符合对应主规范、能力材料是否按归属接管、机制引用是否存在断裂；Code 派生集合索引一致性诊断由 `code/spec_checks/consistency.py` 承接。具体事实模型主规范只定义对象特有实例检查，不重复 LDVH 级审计流程。

合规检查不作为事实模型主规范的独立泛化章节。事实模型相关检查拆分为：生产对象规范写作检查、实例数据检查、集合一致性检查和 LDVH 部署适配完整性检查。本文维护生产对象规范写作检查和实例数据检查通用原则；03.02 维护成员自描述契约；集合一致性检查由 `code/spec_checks/consistency.py` 承接；Code 生成部署适配检查输入清单的能力由 `code/spec_checks/index.py` 承接。

### 4.8 完整方案形成流程

事实模型完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义事实模型；
2. 定义实例事实源位置、字段契约、状态机、关系规则、Human Gate、事实源回写与证据留存和适配边界；
3. 定义对象特有实例检查；
4. 判断 Rules、Skill、Agent、Code、Web 或结构化契约实践是否需要进入对应能力资产、运行实体或 Code/Web 实现；
5. 涉及 Skill、Code、Web 或结构化契约的，完成联动检查；
6. 修改规范、协作能力或实例事实源时，应按 `specs/10-Git提交规范.md` 记录可追溯提交。

## 5. 运行入口边界

事实模型对象规则的权威位置是 specs 对应主规范及其已回并结构化契约章节。适配措施只能承接入口摘要、检查提示、能力调用和降级方式，不得替代事实模型主规范。

Rules / Instructions、Skill、Agent、Code、Web 或其他环境实体只保留必要入口摘要、压缩保护、规范引用、消费字段和检查入口，不得复制字段契约、状态机、关闭条件或 Human Gate 细则。具体环境如何承接这些入口，由 04 系列环境适配项和适配措施记录处理。

## 6. 事实模型准入与分类原则

### 6.1 对象分类原则

LDVH 事实模型可按治理用途分为以下几类：

1. **工作项入口**：承载一次目标的工作项、人类确认点和关闭审查；
2. **执行编排承载**：在工作项内部承载可执行、可验证、可恢复的执行项；
3. **决策和风险**：已确认的决策记录、已识别的风险、前置条件或外部约束；
4. **支撑和记录**：执行摘要、验证结果、关闭证据、验收记录、可引用产物、检查项和踩坑经验。

### 6.2 对象清单归属

具体事实模型清单、编号归属、维护状态和区段关系由 20-39 成员主文件自描述承载。当前事实模型集合以 WorkCase、ADR、Pitfall、Spark、Study 等承载长期可追踪事实；WorkCase 内部的 ExecutionItem 只属于执行编排节点，不作为独立事实模型进入 20-39 集合。Git 提交记录用于追溯事实源修改，不进入事实模型集合。Code 派生集合索引、状态清单和冲突诊断由 `code/spec_checks/index.py` 生成。本文只定义事实模型的通用分类和准入原则。

### 6.3 未占用编号区段

编号区段 20-39 用于具体事实模型规范。当前 26-39 暂未占用。未来新增事实模型应依据 `specs/01-目录说明.md` 的编号分区和 `specs/03.02-工作模型文档规范.md` 的成员自描述契约确认编号未占用；Code 派生集合索引诊断由 `code/spec_checks/index.py` 承接。不得未经 Human Gate 确认提前占用。

### 6.4 准入条件原则

一个内容需要满足以下条件之一，才应成为事实模型：

1. **需要独立追踪状态**：该内容有明确的状态流转，需要跨会话或跨执行轮次追踪；
2. **需要可验证的完成标准**：该内容有明确的验收条件，需要验证是否完成；
3. **需要关闭证据**：该内容完成后需要记录证据，供后续追溯或审计；
4. **需要关联其他对象**：该内容需要被其他对象引用，或引用其他对象；
5. **需要被 Web 信息同步，或被 Code 排序、过滤、聚合或审计**：该内容需要被 Web 或 Code 处理，以降低人和 AI 的维护成本；
6. **不成为事实模型就会导致进度、责任、完成标准或验证结果不可追踪**：该内容如果不结构化，就会导致项目事实漂移或不可追溯。

不满足以上条件的内容，应按其性质分流：
- 可以在当前对话中直接回答或处理的信息 → 留在聊天记忆中，不写入事实源；
- 已有明确目标和完成标准，但不需要独立追踪 → 作为 WorkCase 内部执行项或当前执行上下文处理，不单独创建事实模型；
- 属于现有对象的属性、关系、检查项或输出路径 → 写入现有对象字段或模板，不单独创建事实模型；
- 属于长期规则或决策，但不需要独立状态机 → 写入 specs/，必要时由当前项目的适配措施入口保留薄引用摘要；
- 属于项目正文资料 → 写入 docs/ 根目录或项目自有正文区；内部分析 → 写入 docs/studies/；外部参考资料 → 写入 docs/sources/；
- 属于路线规划、阶段说明或产品方向共识 → 优先写入 Markdown 文档、规划入口或 docs/studies 吸收候选；
- 属于临时执行策略 → 留在当前执行上下文中。

## 7. 事实模型的通用规范

### 7.1 事实源边界原则

事实模型的事实源边界依据 `specs/09-事实源边界与承载规范.md` 定义的原则执行，本文不重复维护。事实模型的适配说明如下：

1. **介质选择适配**：依据 `specs/09-事实源边界与承载规范.md` §6，事实实例优先使用 YAML 格式承载（适合工作项、状态、结构化关系和审计字段），说明性内容可使用 Markdown 格式；
2. **目录归属适配**：依据 `specs/09-事实源边界与承载规范.md` §8 和 `specs/01-目录说明.md`，事实模型规范承载于 specs/20-39，事实实例默认承载于 ldvh-base/，具体模型可声明例外；管辖项目资料承载于 docs/，外部资料承载于 docs/sources/。

### 7.2 状态流转原则

事实模型的状态流转遵循以下原则：

1. **状态变更先于执行**：执行者在执行对象相关操作时，必须同步更新事实源中的对象状态；
2. **终态不可重开**：对象进入终态后，不得直接重开；如需重新处理，必须新建对象承接；
3. **状态流转可追溯**：状态变更必须留下可追溯的记录，包括变更时间、变更人和变更原因；
4. **Human Gate 触发原则**：关键状态流转必须触发 Human Gate，等待人类确认后方可继续。

### 7.3 字段契约原则

事实模型的字段契约遵循以下原则：

1. **基础字段对齐**：所有事实模型应包含基础字段（id、type、title、status、created、updated）；基础字段公共语义由 `specs/05.01-工作模型字段定义与语义规范.md` 定义；
2. **扩展字段明确**：具体事实模型的扩展字段由该事实模型的 20-39 主规范明确定义，包括字段名、类型、是否必填、状态条件和对象内约束；
3. **字段语义一致**：相同字段名在不同对象中的语义应保持一致；公共字段语义、字段复用和字段废弃治理归 `specs/05.01-工作模型字段定义与语义规范.md`；
4. **内容格式归口**：字段内容如何使用 Narrative、Checklist、验证证据、Decision、Reference、Log 或 Structured 表达，由 `specs/05.02-工作模型字段内容与格式规范.md` 定义；
5. **注册消费归口**：字段名、重要嵌套字段路径、内容格式映射、Code/Web 消费元数据、废弃字段和替代关系，由 `specs/05.03-工作模型字段注册与消费规范.md` 登记；
6. **具体契约优先**：字段采用、必填性、状态条件必填、状态机、关闭条件和对象内完整 schema 只由 20-39 具体事实模型规范定义。

### 7.4 事实源回写与证据留存通用规则

事实模型的事实源回写与证据留存遵循以下通用规则，具体事实模型规范只声明对象特有差异：

1. **回写时序**：状态变更先于执行（依据本文 §7.2）；
2. **回写不绕过 HG**：涉及 Human Gate 的回写操作必须经确认后执行；
3. **记录提交**：创建、更新或删除对象时应按 `specs/10-Git提交规范.md` 记录可追溯提交；
4. **证据可追溯**：证据应可追溯到 Git 文件事实源，不得仅存在于对话记录、工具缓存或 Web 派生状态中；
5. **证据完整性**：对象状态变更时应留存足以支持后续追溯和审计的证据摘要。

### 7.5 AI 协作通用规则

事实模型的 AI 协作遵循以下通用规则，具体事实模型规范只声明对象特有差异：

1. **事实源优先**：AI 读取对象时应从 Git 文件事实源或本文声明的只读 Code 派生结果获取信息，不得依赖聊天记忆、工具缓存或 Web 派生状态作为最终依据；
2. **状态适用性**：AI 应根据对象状态判断读取结果适用性；
3. **准入判断**：AI 不得因判断重要就自动创建对象，必须先判断是否满足准入条件；
4. **Human Gate 评估**：AI 创建、更新、删除或流转对象前，必须先按本文、具体事实模型规范和相关基础规范评估是否触发 Human Gate；具体模型列明的高影响场景必须暂停并请求 Human 确认。

### 7.6 Code 辅助通用规则

事实模型的 Code 辅助遵循以下通用规则，具体事实模型规范只声明对象特有差异：

1. **解析依据**：Code 实现解析对象时应依据对应事实模型规范定义的字段契约和文件命名规则；
2. **只读不自动成为依据**：Code 只读查询结果不自动成为执行依据；AI 或 Skill 必须按对应事实模型规范的状态语义判断读取结果适用性；
3. **派生不替代事实源**：聚合输出属于派生视图数据，不替代 Git 文件事实源；
4. **不得自行判断准入**：Code 实现不得自行判断对象准入、生成授权、替代流程性判断或自动执行需要 Human Gate 确认的操作；
5. **不得绕过 HG**：Code 实现不得绕过被修改对象的 Human Gate 要求。

### 7.7 Web 信息同步通用规则

事实模型的 Web 信息同步遵循以下通用规则，具体事实模型规范只声明对象特有差异：

1. **可追溯**：Web 信息同步的对象信息必须可追溯到 Git 文件事实源；
2. **不得维护不一致权威状态**：Web 不得维护与 Git 文件事实源不一致的权威状态；
3. **不得绕过格式规范**：Web 不得绕过对应事实模型规范的字段契约直接展示或编辑派生状态。

### 7.8 检查标准原则

事实模型的检查标准遵循以下原则：

1. **可验证**：检查标准必须是可验证的，不能是模糊的主观判断；
2. **明确**：检查标准必须明确，不能有歧义；
3. **可追溯**：检查完成后必须记录检查证据，包括检查时间、检查人和检查结果；
4. **按对象性质选择检查类型**：以完成为目标的对象应定义验收标准；不以完成为目标的对象应定义检查要求；
5. **对象特有检查进入主文件**：具体事实模型主文件只定义本对象特有的实例检查、验收或证据要求。LDVH 级初始化、LDVH 级审计、集合一致性检查和通用规范写作检查不得在每个对象主文件中重复维护。

### 7.9 AI 协作适配原则

AI 协作适配定义 AI 如何读取、创建、更新和检查事实模型。AI 协作适配遵循以下原则：

1. **按事实源读取**：AI 读取事实实例时必须按事实源边界读取，不依赖聊天记忆、工具缓存或数据库派生视图；
2. **按规范创建**：AI 创建事实实例时必须按事实模型规范的字段契约创建，不得自行添加、省略或修改字段；
3. **按状态机更新**：AI 更新事实实例时必须按事实模型规范的状态机流转，状态变更先于执行；
4. **按验收标准检查**：AI 检查事实实例时必须按事实模型规范的验收标准检查，检查结果留存证据；
5. **不得绕过规范**：AI 不得绕过事实模型规范定义的字段契约、状态机、验收标准或事实源边界；
6. **Human Gate 评估**：AI 创建、更新或删除关键事实实例时，应评估是否需要触发 Human Gate；
7. **能力回指**：AI 协作适配中涉及 Rules、Skill、Agent 的使用边界，必须回指 `specs/04.03-环境入口适配与部署规范.md`。

### 7.10 事实源回写适配原则

本节是 AI 适配补充，不重复定义 §7.4 的通用回写规则。

AI 完成执行后的事实源回写，依据 `specs/09-事实源边界与承载规范.md` §7定义的回写条件执行，本文不重复维护。事实模型的适配说明如下：

1. **事实实例回写触发**：AI 按行动编排执行完毕后，应判断执行结果是否需要创建或更新事实实例；若需要，必须按 `specs/09-事实源边界与承载规范.md` §7 回写；
2. **回写与 Gate 联动**：关键事实实例的创建和更新应评估 Human Gate，依据本文、具体事实模型规范和相关基础规范判断；
3. **回写验证**：事实实例回写后应验证字段完整性、状态合法性和引用完整性；
4. **能力输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实实例；
5. **报告回写分流**：检查报告、分析报告或管辖项目资料应按 02、03 和具体事实模型规范判断进入 docs/、ldvh-base/或 specs/。

### 7.11 证据留存适配原则

本节是 AI 适配补充，不重复定义 §7.4 的通用证据要求。

事实模型的证据留存遵循以下原则：

1. **对象创建留证**：对象创建时应记录创建原因、创建者和创建依据；
2. **状态变更留证**：状态变更时应记录变更时间、变更人、变更原因和变更前状态；
3. **验收检查留证**：验收检查时应记录检查时间、检查人、检查结果和检查证据；
4. **Human Gate 确认留证**：Human Gate 确认时应按 `specs/06-工作流程基础规范.md` §6.3.1 记录时间、决策、范围和约束；确认事项、确认人和确认结果可作为扩展字段或别名；
5. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
6. **关闭前可追溯**：涉及工作项、审计或 Review 的对象，在关闭前应能追溯关键证据。

## 8. 与 20-39 具体事实模型规范的关系

### 8.1 成员自描述与 Code 派生集合索引

事实模型集合不再通过独立手写集合索引文档维护成员清单。20-39 成员主文件通过 03.02 定义的成员自描述字段声明自身编号、标题、状态、路径、事实源目录和规则锚点；Code 读取这些字段生成派生集合索引、关系映射、状态清单、升级或降级诊断和维护提示。

### 8.2 20-39 具体事实模型规范

20-39 是具体事实模型规范，每个规范定义一个具体事实模型。具体事实模型规范应依据 §4.2 定义的事实模型标准组成和 03.02 成员自描述契约展开，并在具体事实模型语境下定义更具体的事实模型规则。

具体事实模型规范不得在缺少说明的情况下省略 §4.2 中的标准组成；如某一组成项暂不适用或待补齐，应在对应章节说明原因或进入待补齐事项。具体事实模型规范不重复LDVH 级初始化、LDVH 级审计、集合一致性检查或通用规范写作检查。

### 8.3 关系原则

本文与 20-39 具体事实模型规范的关系遵循以下原则：
1. 本文定义事实模型的通用规则和事实模型的标准组成，20-39 定义具体事实模型；
2. 具体事实模型规范不得与本文的通用规则矛盾；
3. 具体事实模型规范可以在本文的通用规则基础上，定义更具体的规则；
4. 发生冲突时，以本文的通用规则为准，除非具体事实模型规范明确说明例外情况并经 Human Gate 确认。

## 10. Human Gate 与检查要求

### 10.1 Human Gate 触发条件

以下情况应评估 Human Gate：
1. 新增事实模型；
2. 删除事实模型；
3. 重命名事实模型；
4. 重排事实模型编号区段；
5. 改变事实模型的通用规则；
6. 改变事实模型的事实源边界原则；
7. 将原本不属于事实模型的内容升级为事实模型；
8. 将原本属于事实模型的内容降级为非事实模型；
9. 改变事实模型的标准组成；
10. 改变 AI 协作适配边界（AI 如何创建、更新、检查事实模型）；
11. 改变事实模型与行动编排的交互边界；
12. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 10.2 检查要求

事实模型规范写作检查至少包括：
| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 对象定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、事实模型和行动编排术语一致 |
| 模型组成 | 具体事实模型规范覆盖事实模型的标准组成，缺项已说明原因 |
| 适配边界 | 已说明 Rules、Skill、Agent、Code、Web 等能力内容的归属和引用方式 |
| 对象特有实例检查 | 已定义本对象特有的实例字段、状态流转、关系引用、事实源回写、证据留存和事实源边界检查规则 |
| 文件命名 | 主文件命名符合 §4.6，未重复维护区段性质或对象归属 |
| 事实源边界 | 符合 `specs/09-事实源边界与承载规范.md` 的事实源边界原则 |
| 目录归属 | 符合 `specs/01-目录说明.md` 的目录规划 |
| AI 协作适配 | AI 读取、创建、更新和检查事实实例的规则符合 04 环境适配边界和本文 §7.9 |
| 事实源回写 | AI 创建或更新事实实例后的回写符合 09 事实源边界原则和本文 §7.10 |
| 证据留存 | 对象创建、状态变更、验收检查和 Human Gate 确认有可追溯证据要求，符合本文 §7.11 |

## 11. 待补齐事项

4. 事实模型的信息同步方案应在主规范适配边界章节、`specs/08-Web信息同步实现规范.md` 或 Web 实现中定义；
5. 事实模型部署适配检查流程是否存在 active 入口，应查询 40-59 成员主文件自描述和 Code 派生行动编排集合索引；事实模型输入清单和集合一致性依据由 20-39 成员主文件自描述和 Code 派生事实模型集合索引提供。
