## 1. 本文解决的问题

本文定义 LDVH 中测试、验证和回归如何跨规范体系、事实模型、行动编排、Code、Web、运行时扩展和事实源保持一致。

本文解决：

1. 自动化测试、命令校验、等价验证、Human 验收和回归验证如何分层；
2. 测试要求、测试实现细则、测试代码和测试输出分别归属于哪里；
3. AI 何时可以声明“已验证”、何时必须声明“未验证”或“等价验证”；
4. 测试证据、测试输出、覆盖率、截图、trace、缓存和报告为什么不能替代事实源；
5. 规范、Code、Web、行动编排或事实源规则变化后，如何触发测试同步；
6. 测试与 Code 确定性执行、Web Human-facing 展示、行动编排可测试性锚点和 Git 追溯之间如何分工。

本文不定义具体测试框架、测试文件清单、命令实现、Web 页面测试细节或 Code 输出 Schema。具体实现细节由对应实现域和测试文件承接。

## 3. 构成要素归属与价值判断

本文是跨构成要素验证基础规范，不是第七类或第八类构成要素。测试服务六类构成要素的可验证性，但不替代任何构成要素的本体规则。

正向价值判断：

| 价值 | 本文如何服务 |
|---|---|
| V4 稳定执行 | 通过测试入口、验证声明和回归要求让 AI 不只依赖主观判断 |
| V5 门禁识别 | 区分自动化验证、等价验证和 Human 验收，避免机械检查替代高影响确认 |
| V6 强制验证 | 规定“已验证”必须有可复现入口、关键输出或明确等价步骤 |
| V7 证据沉淀 | 规定测试证据如何回指命令、样例、输出和事实源，而不成为第二事实源 |
| V9 人类确认质量 | 让 Web 或过程输出展示验证状态时能区分通过、失败、未运行和残留风险 |

逆向价值判断：

| 反模式 | 本文必须阻止 |
|---|---|
| 用未运行测试冒充已验证 | 未执行、失败或不可复现的验证不得写成完成结论 |
| 用测试输出替代事实源 | 覆盖率、截图、trace、缓存和报告不能替代规范、对象或 Git 记录 |
| 用测试实现反向定义规则 | 测试代码不能反向定义字段契约、状态机、Human Gate 或行动流程 |
| 把测试归入单一 Code 附件 | 测试是跨构成要素验证治理，不是 Code 附件 |
| 忽略 Web 或行动编排测试 | Web 暂不实施不等于 Web 契约和行动可测试性可以丢失 |

## 5. 测试治理分层与实现归属

测试治理按三层分工：

| 层级 | 承载位置 | 职责 |
|---|---|---|
| 上层测试要求 | 本文和对应构成要素规范 | 定义验证纪律、事实源边界、测试归属、同步触发和 Human Gate |
| 实现测试细则 | Code、Web、运行时扩展或对应实现域文档 | 定义当前实现的测试入口、命令、夹具组织、执行方式和失败处理 |
| 测试实现 | `tests/` 或对应实现域测试目录 | 承载可执行测试代码、最小夹具、正反样例和回归样例 |

`tests/` 只能承载测试代码、最小夹具、正反样例和回归样例，不得承载规范规则、事实模型字段契约、状态机、Human Gate、行动编排流程或事实源归口。测试暴露规则缺口时，应回到 specs 或对应构成要素规范修正；测试代码不得反向定义规则。

测试实现归属矩阵由 `attachments/08.Att.01-测试归属矩阵.md` 承载。根目录 `tests/` 不直接放置长期测试文件；Code 测试进入 `tests/code/`，Web 测试进入 `tests/web/`，新增长期测试分区前必须回到 01 和本文评估目录归属与 Human Gate。

`code/docs/` 只能承载 Code 当前参考实现的测试映射、命令入口、模块拆分和执行细则；`web/docs/` 只能承载 Web 当前参考实现的 API contract、页面验证、构建检查和夹具约定。实现域文档不得通过测试细节反向改写 specs、事实模型字段契约、状态机、Human Gate、事实源边界或测试治理规则。

同一规则不得在 specs、实现文档和测试代码中复制维护为多个权威来源。

## 6. 验证声明与失败边界

LDVH 认可以下验证方式：

| 验证方式 | 适用场景 | 声明要求 |
|---|---|---|
| 自动化测试 | 成功条件、失败条件和输入输出可机械复现 | 说明测试入口、关键覆盖点和结果 |
| 命令校验 | 文档结构、引用、构建、格式、类型或 CLI 行为可由命令稳定反馈 | 说明命令、退出状态和关键输出 |
| 等价验证 | 自动化测试暂不可行，但可通过最小样例、人工检查或现有工具复现关键风险 | 说明原因、替代步骤和残留风险 |
| Human 验收 | 涉及授权、确认、体验判断或高影响选择 | 说明确认对象、影响范围、用户选择和证据位置 |
| 回归验证 | 修复问题、迁移结构或改变输入输出后防止复发 | 说明复现样例、失败前表现和通过条件 |

AI 只能在验证方式、关键输出和残留风险可复现时，把变更表述为已验证。无法建立完整测试时，应说明原因、采用的等价验证方式和残留风险。检查命令、测试命令和工具输出只能作为辅助证据，不替代验证结论本身；未实际验证时必须明确写为“未验证”，不得用命令清单、观察印象或局部通过结果暗示完整验证。

验证声明字段由 `attachments/08.Att.02-验证声明字段表.md` 承载。等价验证适用边界由 `attachments/08.Att.08-等价验证适用表.md` 承载。声称“完整验证”时，验证声明必须覆盖目标、入口、输入范围、关键样例或关键输出、结论、残留风险和证据回指；只运行局部测试、只做人工阅读、只跑格式检查或只看工具输出时，不得写成完整验证。

出现以下任一情况时，不得关闭任务、提交验收结论或声称完成：

1. 必须运行的测试失败；
2. 关键检查未运行且没有等价验证；
3. 验证输出无法回指命令、样例、事实源或测试入口；
4. 测试结果与事实源、规范或实现观察冲突且未完成解释；
5. Human 验收尚未发生，却被表述为已确认。

失败阻断核对由 `attachments/08.Att.07-失败阻断核对表.md` 承载。

## 7. 测试证据与缺口分流

测试证据用于支持判断，不成为最终事实源。测试输出、覆盖率、截图、缓存、Mock 数据、浏览器 trace 和临时报告不得替代 Git 文件事实源、规范正文、工作对象或 Human Gate 记录。

原始测试输出不得形成独立事实源。稳定验证结论、残留风险、失败诊断或 Human 验收记录需要长期追溯时，必须按 07 的事实源边界和本文验证声明规则，分流到 WorkCase、Git commit records、Pitfall、ADR、Human Gate 记录或对应事实源字段。

测试证据边界清单由 `attachments/08.Att.03-测试证据边界清单.md` 承载。测试证据应能回指测试入口、输入范围、关键样例、关键输出、命令退出状态、Human 验收记录或对应事实源；无法回指时，只能作为诊断线索，不得作为关闭、验收或事实源回写依据。

测试发现的问题应按性质分流：

1. 规则缺口回到 specs 或对应构成要素规范；
2. 字段、状态、对象关系或写入边界缺口回到 02 或事实模型成员主文件；
3. 行动流程、Gate、Context、回写或可测试性锚点缺口回到 03 或行动编排成员主文件；
4. Code/Web/运行时扩展实现缺口回到对应实现域；
5. 长期经验、反复问题、风险和后续工作回到 Pitfall、ADR、WorkCase、Spark、Study 或 Git commit records。

测试夹具应保持最小、可解释、可回指规则。Mock 数据和快照不得成为事实模型样例的唯一来源。

## 8. Code、Web、行动编排与运行时扩展测试协作

Code 测试必须覆盖关键输入、正反样例、诊断输出、exit code、来源回指和降级路径，不能只保留 smoke test。Code 命令入口、commit 校验、事实模型解析、规范索引、知识地图投影和受控写入前检查变化时，应同步检查测试入口。Code 行为变更前，应先确认规则来源、正反样例、测试或等价验证路径；无法先建立验证路径时，必须说明原因、残留风险和后续补齐位置。知识地图投影测试或等价验证至少覆盖输入范围、排除输入、关系类型闭集、source refs、diagnostics 和 `degraded` 状态。

Code 完整验证入口由 `attachments/08.Att.05-Code完整验证入口表.md` 承载。当前 LDVH Code 参考实现中，`npm run test:code` 是日常完整测试入口，必须同时覆盖 `tests/code` 自动化测试和 `python3 code/specs_validate.py all --fail-on-diagnostics` 综合检查。v2 迁移期的 `python3 code/specs_validate.py v2-check --fail-on-diagnostics --format text` 是 v2 写作区只读迁移诊断入口，不替代 active specs 综合检查。

Web 测试应优先覆盖 Human-facing 读取、错误状态、事实源回指、派生态势原因语义、受控轻写入白名单、Confirm UI 边界、API contract、i18n 文案和缓存不替代事实源。Web 暂不实施时，也必须保留 DTO、Spark 创建白名单、WorkCase orchestration 展示、提交记录展示、Confirm UI 边界、派生态势原因语义、Web 测试/构建/API contract 入口或人工降级检查的回归线。

Web 回归入口由 `attachments/08.Att.06-Web回归入口表.md` 承载。Web API、页面、组件、Confirm UI、受控轻写入、ProjectFiles、Validate、Objects、Changelog 或来源展示变化时，应优先检查 API contract 和高风险 API 回归；E2E、视觉回归和复杂浏览器流程不得作为当前 API contract 的前置条件。

行动编排测试关注成员主文件的 Context、Scenario、Gate、回写触发、能力协作、失败降级和可测试性锚点。测试不得把 inactive、planned 或未迁移流程反向恢复为 active 流程。

行动编排测试机制只能从 30-59 active 成员主文件声明的行动特有可测试性锚点出发。不得为每个流程另设测试子文档体系；具体测试用例、预期矩阵和失败诊断应由对应成员主文件授权后进入测试实现、Code 检查或工作对象。测试实现、测试夹具或历史运行闭环材料不得反向恢复未 active、已清退或尚未迁移的行动编排。

运行时扩展测试关注 Rules、Skills、Agents、Hooks、环境入口、薄引用、Hook 事件、适配检查和权限边界。一次本地环境测试只证明当前现场，不证明环境类型长期完整支持。

## 9. 同步触发规则

以下变化应检查测试要求、实现测试细则和测试实现是否需要同步：

1. 规范身份、编号、引用关系、章节结构、保障要求或 Human Gate 变化；
2. 事实模型字段契约、状态机、对象关系、事实源边界或受控写入规则变化；
3. 行动编排的 Context、Scenario、Gate、执行流程、回写、证据或可测试性锚点变化；
4. Code CLI、输入输出、错误码、诊断格式、写入行为、目录假设或知识地图投影变化；
5. Web API、页面、组件、派生视图、写入白名单、Confirm UI、i18n 或来源呈现变化；
6. 运行时扩展入口、Skill、Agent、Hook、Rules 或环境适配方式变化；
7. 测试目录、测试命令、测试夹具、Mock 数据、构建入口或验证入口变化；
8. 工作项关闭、验收、发布、迁移或删除实现前，需要确认验证证据是否仍可复现。

同步触发矩阵由 `attachments/08.Att.04-同步触发矩阵.md` 承载。触发后应先判断变化属于上层测试要求、实现测试细则还是测试实现：上层规则进入 specs，当前参考实现细节进入 `code/docs/` 或 `web/docs/`，可执行测试进入 `tests/`。

## 12. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 改变 `tests/` 或长期测试分区的目录定位、事实源性质或构成要素归属；
2. 将测试结果、测试缓存、覆盖率、截图、Mock 数据、trace 或测试报告提升为稳定事实；
3. 改变“已验证”“等价验证”“完整验证”“未验证”的声明标准；
4. 删除高价值测试、回归样例或验收证据且缺少替代验证方式；
5. 用测试实现反向定义 specs 规则、对象字段契约、状态机、Human Gate 或行动编排；
6. 接受测试治理、关键验证或回归入口长期降级。
7. 新增长期测试分区、改变构成要素测试归属或扩大测试对任务关闭、发布和验收的判定范围。
8. 改变 `08.Att.01` 至 `08.Att.08` 的信息对象、授权范围或关键闭集。
