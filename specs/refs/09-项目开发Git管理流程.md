# 项目开发 Git 管理流程

> 日期：2026-05-26
> 来源：通用软件工程实践整理
> 定位：外部资料引用，不直接成为 LDVH 强制规则

---

## 一、目标

项目开发中的 Git 管理流程需要解决四类问题：

1. **代码变更可追踪**：每次修改都能明确来源、目的、影响范围和责任人；
2. **协作冲突可控**：多人并行开发时减少覆盖、冲突和重复修改；
3. **交付质量可验证**：合并前完成必要检查，避免把未验证代码带入主干；
4. **问题恢复有路径**：线上或集成环境出现问题时，能够快速定位并回滚。

Git 流程不是为了增加仪式感，而是为了让项目在持续变化中保持可理解、可审计、可恢复。

---

## 二、核心原则

### 2.1 主干始终可用

主干分支应保持可运行、可构建、可部署。任何进入主干的代码都应通过项目规定的检查和必要验证。

### 2.2 小步提交

单次提交应围绕一个明确目的展开，避免把无关修改混在一起。小步提交有利于 Code Review、问题定位和回滚。

### 2.3 先同步，后开发

开始开发前应同步远端最新代码，减少基于过时代码继续开发导致的冲突和返工。

### 2.4 先检查，后合并

合并前必须完成项目要求的检查，例如 lint、typecheck、test、build、接口验证或浏览器验证。不能仅凭“本地看起来没问题”合并。

### 2.5 历史清晰优先

提交历史应能回答“为什么改、改了什么、影响哪里”。不要用大量无意义提交污染历史，例如 `fix`、`update`、`wip`。

## 三、分支模型

### 3.1 推荐分支类型

| 分支类型 | 命名示例 | 用途 |
|---|---|---|
| 主干分支 | `main` / `master` | 稳定代码基线，保持可发布状态 |
| 功能分支 | `feature/user-login` | 新功能开发 |
| 修复分支 | `fix/login-error` | 缺陷修复 |
| 重构分支 | `refactor/auth-service` | 不改变外部行为的结构调整 |
| 文档分支 | `docs/git-workflow` | 文档新增或修改 |
| 实验分支 | `experiment/new-cache-strategy` | 不确定方案验证，不直接合入主干 |
| 热修分支 | `hotfix/payment-timeout` | 生产紧急修复 |

### 3.2 分支命名建议

推荐格式：

```bash
<type>/<short-topic>
```

常用 `type`：

- `feature`：新增功能；
- `fix`：问题修复；
- `docs`：文档修改；
- `refactor`：重构；
- `test`：测试补充或调整；
- `chore`：构建、配置、依赖、脚本等杂项；
- `hotfix`：紧急修复；
- `experiment`：实验性工作。

命名时应避免：

- 使用个人情绪或模糊词，如 `new`、`temp`、`try1`；
- 使用过长描述；
- 在分支名中包含敏感信息、客户名称或内部凭据。

## 四、日常开发流程

### 4.1 开始开发前

1. 确认任务来源和目标；
2. 确认当前工作区没有未处理修改；
3. 切换到主干分支；
4. 拉取远端最新代码；
5. 从最新主干创建工作分支。

示例命令：

```bash
git status
git switch main
git pull --ff-only
git switch -c feature/example
```

如果 `git status` 显示已有未提交修改，应先判断这些修改是否属于当前任务。不要在不清楚来源的情况下继续开发。

### 4.2 开发过程中

开发过程中建议保持以下节奏：

1. 小范围修改；
2. 运行局部检查；
3. 查看差异；
4. 分批提交；
5. 定期同步主干变化。

常用命令：

```bash
git status
git diff
git add <files>
git commit -m "type(scope): summary"
```

对于 AI 协作项目，提交前尤其应检查：

- 是否误改无关文件；
- 是否生成临时文件、缓存文件或日志文件；
- 是否包含密钥、令牌、Cookie、数据库连接串等敏感信息；
- 是否把任务状态、临时讨论或过程记录写入不该写入的文件。

### 4.3 同步主干变化

长时间开发的分支应定期同步主干，降低最终合并冲突。

推荐方式之一：

```bash
git fetch origin
git rebase origin/main
```

如果团队不使用 rebase，也可以使用 merge：

```bash
git fetch origin
git merge origin/main
```

选择 rebase 还是 merge 应遵循项目约定。若项目没有明确约定，团队应先统一，不应在同一仓库中混用多种历史策略。

## 五、提交规范

### 5.1 推荐提交格式

推荐使用接近 Conventional Commits 的格式：

```bash
<type>(<scope>): <summary>
```

示例：

```bash
feat(auth): add login form validation
fix(api): handle empty user profile response
docs(git): add development workflow guide
refactor(task): simplify status transition logic
```

### 5.2 常用 type

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档修改 |
| `style` | 格式调整，不影响逻辑 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 测试相关 |
| `chore` | 构建、脚本、配置、依赖等 |
| `perf` | 性能优化 |
| `revert` | 回滚提交 |

### 5.3 提交粒度

一个提交应尽量满足：

- 能独立说明一个变更目的；
- 不混入无关格式化；
- 不同时修改多个无关模块；
- 回滚该提交时不会影响其他无关工作。

不推荐：

```bash
git commit -m "update"
git commit -m "fix"
git commit -m "change files"
```

推荐：

```bash
git commit -m "fix(task): preserve review status when updating task"
git commit -m "docs(workflow): describe branch naming rules"
```

## 六、合并前检查

### 6.1 自检清单

发起合并前，应至少确认：

- 工作区干净，未遗漏应提交文件；
- 分支已同步目标分支最新代码；
- 已运行项目要求的检查命令；
- 新增或修改功能已完成必要验证；
- 文档、配置、结构化对象等修改符合项目事实源归属；
- 没有提交敏感信息；
- 没有提交临时调试代码或无关日志。

### 6.2 常见检查类型

不同项目检查命令不同，具体以项目开发实践文档或仓库脚本为准。常见检查包括：

```bash
npm run lint
npm run typecheck
npm test
npm run build
pytest
ruff check
cargo test
go test ./...
```

不要凭惯例假设某个命令一定存在。执行前应查看项目文档、`package.json`、`pyproject.toml`、`Cargo.toml`、`Makefile` 或 CI 配置。

### 6.3 Pull Request / Merge Request 要求

合并请求应包含：

1. 变更摘要；
2. 关联任务或需求；
3. 影响范围；
4. 已执行检查；
5. 验证结果；
6. 风险点与回滚方式；
7. 需要 Review 重点关注的问题。

## 七、Code Review 流程

### 7.1 Review 关注点

Code Review 不只看代码能否运行，还应关注：

- 需求是否被正确实现；
- 方案是否过度复杂；
- 是否引入安全风险；
- 是否破坏既有接口、数据结构或兼容性；
- 是否遗漏错误处理、边界条件和测试；
- 是否符合项目文档、规则和事实源分工；
- 是否影响性能、可维护性或可观测性。

### 7.2 Review 修改方式

Review 后的修改应继续提交到同一工作分支。若需要整理历史，可以在合并前按项目约定 squash 或 rebase。

不建议为了逃避 Review 重新开分支或直接推送主干。

### 7.3 AI 协作场景

AI 参与修改时，Review 应额外关注：

- 是否误解需求；
- 是否把示例代码当作真实逻辑；
- 是否引入不存在的依赖或命令；
- 是否遗漏项目专属规则；
- 是否修改了不属于当前任务的文件；
- 是否生成看似合理但缺少事实依据的内容。

## 八、合并策略

### 8.1 Squash Merge

适合希望主干历史简洁的团队。多个开发提交会被压缩成一个提交进入主干。

优点：

- 主干历史清晰；
- 回滚简单；
- 降低临时提交噪音。

注意：

- 合并提交信息必须写清楚；
- 分支内细粒度提交信息不会完整保留在主干。

### 8.2 Rebase and Merge

适合希望保留线性历史且每个提交都有意义的团队。

优点：

- 历史线性；
- 每个提交可追踪；
- 便于 bisect。

注意：

- 提交粒度和提交信息质量要求更高；
- 不应随意 rebase 他人正在基于其开发的共享分支。

### 8.3 Merge Commit

适合需要保留完整分支上下文的团队。

优点：

- 保留分支合并关系；
- 不重写历史；
- 对共享分支友好。

注意：

- 历史可能更复杂；
- 需要清楚的合并提交信息。

## 九、冲突处理

### 9.1 处理步骤

出现冲突时，应按以下顺序处理：

1. 阅读冲突文件上下文；
2. 判断双方修改意图；
3. 保留正确逻辑，而不是机械选择一边；
4. 运行相关检查；
5. 必要时请相关修改者确认。

常用命令：

```bash
git status
git diff
git add <resolved-files>
git rebase --continue
```

如果是 merge 冲突，则解决后提交 merge commit。

### 9.2 冲突处理禁忌

避免以下行为：

- 未理解逻辑就使用 `ours` 或 `theirs`；
- 删除冲突标记后不运行检查；
- 把冲突中的重复逻辑全部保留；
- 解决冲突时顺手改无关代码；
- 将未解决冲突的文件提交。

## 十、回滚与恢复

### 10.1 回滚已合并提交

对于已推送到远端或已合并主干的提交，优先使用 `git revert` 生成反向提交：

```bash
git revert <commit-sha>
```

这种方式不会重写共享历史，适合团队协作和生产修复。

### 10.2 修改本地未推送提交

如果提交只存在于本地，可以使用 amend 或 reset 整理：

```bash
git commit --amend
git reset --soft HEAD~1
```

但如果提交已经推送给他人使用，应避免直接重写历史，除非团队明确允许并已通知相关协作者。

### 10.3 紧急修复

紧急修复建议流程：

1. 从生产对应基线创建 `hotfix/*` 分支；
2. 只修改与紧急问题直接相关的内容；
3. 完成最小必要验证；
4. 合并并发布；
5. 将修复同步回主干和相关长期分支；
6. 补充复盘记录和必要测试。

---

## 十一、标签与版本

### 11.1 标签用途

标签用于标记重要版本、发布点或审计基线。常见格式：

```bash
v1.0.0
v1.2.3
release-2026-05-29
```

### 11.2 标签要求

创建标签前应确认：

- 对应提交已经通过发布要求；
- 版本号符合项目约定；
- 发布说明或变更记录已准备好；
- 标签指向正确提交。

示例命令：

```bash
git tag -a v1.2.0 -m "release: v1.2.0"
git push origin v1.2.0
```

## 十二、安全与敏感信息

Git 历史会长期保存提交内容，因此必须避免提交：

- API Key、Token、Cookie、Session；
- 私钥、证书、数据库密码；
- 生产配置和内部访问地址；
- 用户隐私数据；
- 未脱敏日志；
- 供应商或客户敏感信息。

如果敏感信息已经提交：

1. 立即停止继续传播；
2. 通知项目负责人或安全负责人；
3. 立即轮换泄露凭据；
4. 根据团队规范清理 Git 历史；
5. 检查是否已进入远端、CI 日志、制品或发布包。

仅从最新提交中删除密钥并不等于风险解除，因为密钥仍可能存在于历史记录中。

## 十三、AI 协作下的 Git 注意事项

AI 协作开发时，Git 管理应更强调边界和审计：

1. **不要让 AI 自动提交**：除非用户明确要求，否则 AI 只修改文件、检查结果并汇报，不应自行 commit；
2. **每次修改前后查看差异**：确认修改范围与任务一致；
3. **避免跨任务混改**：一个任务只处理一个明确目标；
4. **保留验证证据**：记录执行过的检查命令、结果和未验证原因；
5. **遵守事实源归属**：不要把临时状态、过程讨论或任务进度写入需求文档；
6. **谨慎处理删除与重命名**：确认文件角色、引用关系和是否属于规则、技能、配置等高风险对象；
7. **不凭惯例运行命令**：先查项目文档或脚本，再执行检查。

## 十四、推荐标准流程

### 14.1 功能开发标准流程

```text
确认任务
  ↓
同步主干
  ↓
创建功能分支
  ↓
小步开发与提交
  ↓
同步目标分支
  ↓
运行检查与验证
  ↓
发起合并请求
  ↓
Code Review
  ↓
修正问题并复验
  ↓
合并主干
  ↓
删除已合并分支
```

### 14.2 缺陷修复标准流程

```text
复现问题
  ↓
定位原因
  ↓
创建 fix 分支
  ↓
最小范围修复
  ↓
补充或更新测试
  ↓
验证原问题已解决
  ↓
检查是否有回归风险
  ↓
发起合并请求
  ↓
Review 后合并
```

### 14.3 紧急修复标准流程

```text
确认事故范围
  ↓
从稳定基线创建 hotfix 分支
  ↓
最小修改修复
  ↓
完成必要验证
  ↓
合并发布
  ↓
同步回主干
  ↓
补充复盘和长期修复任务
```

## 十五、团队约定清单

一个项目至少应明确以下 Git 约定：

- 主干分支名称；
- 分支命名规则；
- 提交信息格式；
- 合并策略；
- 是否允许 force push；
- 是否要求 PR/MR；
- 必跑检查命令；
- Review 通过条件；
- 版本标签规则；
- 回滚责任人与流程；
- 敏感信息处理流程。

如果这些约定没有写入项目文档，团队成员和 AI 都容易凭经验行事，最终导致流程不一致。

## 十六、常用命令速查

| 场景 | 命令 |
|---|---|
| 查看状态 | `git status` |
| 查看未暂存差异 | `git diff` |
| 查看已暂存差异 | `git diff --cached` |
| 拉取远端更新 | `git pull --ff-only` |
| 创建并切换分支 | `git switch -c <branch>` |
| 切换分支 | `git switch <branch>` |
| 暂存文件 | `git add <files>` |
| 提交修改 | `git commit -m "type(scope): summary"` |
| 获取远端更新 | `git fetch origin` |
| 变基到主干 | `git rebase origin/main` |
| 合并主干 | `git merge origin/main` |
| 回滚提交 | `git revert <commit-sha>` |
| 查看提交历史 | `git log --oneline --graph --decorate` |
| 删除本地分支 | `git branch -d <branch>` |
| 删除远端分支 | `git push origin --delete <branch>` |

## 十七、落地建议

对小团队或 AI 高频参与的项目，建议优先采用：

1. `main` 作为稳定主干；
2. 所有开发通过短生命周期分支完成；
3. 提交信息采用 `type(scope): summary`；
4. 合并前必须说明检查和验证结果；
5. 默认使用 Pull Request / Merge Request；
6. 主干禁止直接推送；
7. 已合并分支及时删除；
8. 生产问题优先使用 `revert` 恢复；
9. 文档中明确 AI 不自动提交，除非用户明确要求。

这样可以在流程成本较低的前提下，获得清晰历史、可靠合并和可恢复交付。
