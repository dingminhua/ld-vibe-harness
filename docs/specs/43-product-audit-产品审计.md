## 1. 行动定位与适用场景

产品审计是 LDVH 的后置检查工作流程，用于判断安装与接入初始化依赖的平台适配清单，以及由清单指导形成的环境、配置、目录、入口、事实源、Code、Web 和运行投影是否仍然真实存在、持续有效、未漂移且未绕过 Human Gate。

本文不重新定义安装与接入初始化。42 定义如何建立或补齐接入链路；本文定义如何审查该链路是否仍可被 AI 和 Human 信任。产品审计可以触发 42 补齐初始化缺口，也可以触发 41 规范落地统筹、Task、ADR、Memo、Pitfall、Change、Code 需求或 Web 需求，但不得把审计过程输出直接当成最终稳定事实。

出现以下情况之一时，应考虑进入产品审计：

1. 用户要求检查 LDVH 是否已经初始化完成、是否还能使用、是否漂移或是否缺东西；
2. 42 安装与接入初始化完成后，需要验证初始化结果是否真实可用；
3. 平台适配清单、`LDVH-GOVERNED-PROJECTS.yaml`、LDVH-AI-ENTRY.md、项目 `docs/`、项目 `ldvh-base/` 或工作区级入口发生变化；
4. 管辖项目路径、目录、初始化结果、active 工作模型、active 工作流程或运行投影与索引不一致；
5. 平台适配清单、Code、Web、Rules / Instructions、Skill、Agent、Hook、CI 或环境能力变化可能影响 LDVH 行动闭环；
6. 用户或 AI 发现初始化结果无法支撑当前任务、入口无法定位、事实源缺失或 Human Gate 证据不清；
7. 需要为后续规范落地、任务执行、项目迁移或配置校准提供审计输入。

以下情况通常不应进入完整产品审计：

1. 用户只要求安装、接入或初始化，应优先进入 42；
2. 用户只要求解释规范术语或阅读单个文档；
3. 普通 Task 执行中只需局部检查一个文件或一个命令；
4. 只审计某条 ADR、Task、Memo、Pitfall 或 Change 的对象状态，应进入对应工作模型或候选工作流程；
5. 只做规范落地要求分流且不检查初始化链路持续有效性，应进入 41。

## 2. 准入条件

进入产品审计前，应至少满足以下条件：

1. 能定位 LDVH 自身项目根目录；
2. 能读取 LDVH-AI-ENTRY.md、`LDVH-GOVERNED-PROJECTS.yaml`、当前平台适配清单，或能明确记录其缺失；
3. 能读取 42 安装与接入初始化流程、40 工作流程集合索引和 04.06 平台适配清单规范；
4. 能明确本次审计范围是 LDVH 管理实例、单个管辖项目、多个管辖项目、环境投影、配置文件、目录事实源、入口机制、Code/Web，还是全链路审计；
5. 能区分审计发现、稳定事实、缺口分流和受控写入；
6. 若需要读取目标管辖项目，能确认目标项目 `id`、`path` 和访问权限；
7. 若需要修改配置、目录、入口、项目初始化结果、平台清单、Code 或 Web，已触发 Human Gate。

以下任一条件不满足时，不得宣称产品审计完成：

1. 审计范围不明确；
2. 无法读取或确认管辖项目配置；
3. 目标项目路径无法定位且未记录为审计阻塞；
4. 无法区分初始化缺口、审计发现和普通任务缺口；
5. 需要 Human Gate 的修改尚未确认；
6. 审计结论没有证据、缺口状态或分流去向。

1. 不得把审计状态写入 `LDVH-GOVERNED-PROJECTS.yaml`；

3. 不得把审计发现直接写入正式规范，除非已确认属于规范缺口并通过对应规范修改流程；
4. 不得把工具缓存、命令输出或聊天过程当成最终审计事实；
5. 不得以产品审计名义绕过 42 的初始化 Gate 或 41 的规范落地统筹。

## 5. Scenario 识别

产品审计 Scenario 应按以下条件识别：

| Scenario | 进入条件 | 不进入条件 |
|---|---|---|
| 全链路产品审计 | 用户要求检查 LDVH 是否完整可用、是否已接入成功或是否持续有效 | 用户只要求首次安装或补齐初始化 |
| 环境适配审计 | 需要检查现场环境确认、运行投影、入口或降级方式是否仍有效 | 只是选择当前环境并创建初始化计划 |
| 平台清单审计 | 需要逐项检查当前平台适配清单中的 AI-S1 至 AI-S15 和 LR-1 至 LR-7 要求响应矩阵、状态、证据、降级和 Open Items 是否有效 | 只是询问某个平台概念 |
| 管辖项目配置审计 | 需要检查 `LDVH-GOVERNED-PROJECTS.yaml` 字段、项目清单、路径和实际项目是否一致 | 只是新增项目配置草案 |
| 管辖项目初始化审计 | 需要检查项目 `docs/`、`ldvh-base/`、初始化结果、工作区级入口或 active 模型/流程承载 | 只是普通项目文档阅读 |
| 入口与运行投影审计 | 需要检查 LDVH-AI-ENTRY.md、平台入口、工作区级薄入口或运行投影是否漂移 | 只做会话级临时说明 |
| Code/Web 承接审计 | 需要检查工具、校验命令、Web 展示或 Human-facing 入口是否仍能支撑流程 | 只运行单个已知命令且不判断链路 |
| 缺口分流审计 | 审计发现无法直接修复的缺口，需要分流到 41、42、Task、ADR、Memo、Pitfall、Change、Code 或 Web | 缺口已属于明确 Task 且不影响产品链路 |

多个 Scenario 同时匹配时，应按平台清单、环境、配置、项目路径、目录事实源、初始化结果、入口投影、工作模型、工作流程、Code/Web、缺口分流的顺序审计。若任一步出现阻塞，应记录阻塞并判断是否能继续局部审计，不得把局部通过宣称为全链路通过。

## 6. 执行流程

### 6.1 确认审计范围

AI 应先明确本次审计范围：

1. LDVH 管理实例全链路；
2. 单个管辖项目；
3. 多个管辖项目；
4. 现场环境确认和运行投影；
5. 平台适配清单；
6. 管辖项目配置；
7. 入口机制；
8. Code/Web 承接；
9. 某次初始化结果或缺口补齐结果。

范围不清时，应请求 Human 确认，不得默认审计所有项目或默认修改任何事实源。

### 6.2 审计环境确认和运行投影

AI 应先审计当前平台适配清单中的要求响应矩阵：

1. 当前平台是否有对应清单；
2. 清单是否遵守 `docs/specs/04.06-平台适配清单规范.md`；
3. 当前平台为 Trae Solo 时，是否读取 `docs/specs/04.07-Trae-Solo适配清单.md`；当前平台为 Codex CLI 时，是否读取 `docs/specs/04.08-Codex适配清单.md`；
4. 清单是否逐项覆盖 AI-S1 至 AI-S15 和 LR-1 至 LR-7；
5. 每项要求是否具备承接方法、平台实体、refs 依据、状态、降级方式、43 审计证据和 Open Items；
6. 每项要求的 status 是否与 refs 证据、实测证据和降级说明匹配；
7. 42 初始化结果或 43 上次审计输出是否承接了关键要求的 partial、degraded 和 open_items；
8. 是否只审平台有没有 Rules、Skill、Agent、MCP、Command、Hook 或 Code/Web，而没有回到 LDVH / AI 支持要求本身；
9. 是否把未经审计的平台声明为 supported；
10. 是否把 Trae Solo 平台名硬编码为 42 或 43 的通过依据，而不是围绕清单判断。

清单缺失、要求矩阵缺项、关键要求为 not-started、draft、deprecated 或证据不足时，不得输出全链路 pass。Trae Solo 清单当前为 partial 时，可以审计其 refs 证据和实测证据是否足以升级为 ready-for-audit；从 partial 升级为 ready-for-audit，或从 ready-for-audit 升级为 supported，均必须 Human Gate。

AI 应检查：

1. 当前环境确认方式是否与 42 和 04 系列一致；
2. 运行投影状态、降级方式、Human 确认状态和残留风险是否明确；
3. LDVH-AI-ENTRY.md 是否存在且仍能作为统一入口；
4. 项目内平台投影痕迹是否只作为辅助线索，而非当前环境唯一判据；
5. 平台清单记录能力与当前可用能力是否明显冲突；
6. 42 初始化结果或 43 上次审计输出是否记录本次需要追溯的环境确认证据。

缺失、冲突或漂移应记录为环境审计发现。需要创建或修改持久入口、平台规则、Hook、自动化或平台清单时，必须触发 Human Gate。

### 6.3 审计管辖项目配置

AI 应检查：

1. `LDVH-GOVERNED-PROJECTS.yaml` 是否存在；
2. 是否只包含 03.06 允许字段；
3. `product_name` 和 `product_description` 是否存在且可读；
4. 每个项目是否具备稳定 `id` 和 `path`；
5. 项目 `id` 是否重复；
6. 项目 `path` 是否为可定位路径；
7. 配置是否错误承载初始化状态、审计状态或运行投影正文。

修改配置前必须触发 Human Gate。路径不存在不必立即修改配置，应先记录为审计发现，并判断是配置漂移、项目迁移、权限问题还是暂时不可访问。

### 6.4 审计管辖项目初始化结果

对每个审计范围内的管辖项目，AI 应检查：

1. `{project.path}` 是否存在且与 Human 或配置期望一致；
2. `{project.path}/docs` 是否存在；
3. `{project.path}/docs/evals` 和 `{project.path}/docs/refs` 是否按项目文档规则存在或有合理降级；
4. `{project.path}/ldvh-base` 是否存在；
5. 42 记录的项目初始化结果文档是否存在；
6. 初始化结果是否记录环境、配置、目录、入口、Code/Web、验证、Human Gate 和残留缺口；
7. 初始化结果中的 open / degraded 缺口是否仍未处理；
8. 项目中是否出现不应默认创建的 `docs/specs/`、平台规则文件或 AI 统一入口。

若项目未完成初始化，应分流回 42。若初始化结果存在但已漂移，应记录审计发现，并判断是否需要重新执行 42 的局部补齐步骤。

### 6.5 审计工作模型和工作流程承载

AI 应依据 20 和 40 检查：

1. active 工作模型是否能定位到对应规范；
2. 管辖项目 `ldvh-base/` 是否只为 active 或已授权例外模型创建事实源承载；
3. removed、deferred-field、deferred-doc 或 reserved 工作模型是否被错误创建；
4. active 工作流程是否能定位到 41-59 主文档；
5. planned、candidate 和 reserved 工作流程是否被错误当作已生效流程执行；
6. 初始化结果或入口摘要是否仍引用过期流程状态。

发现规范集合与实际承载不一致时，应记录为审计发现。涉及规范落地、索引或机制承接缺口时，应分流到 41。

### 6.6 审计入口、Code 和 Web 承接

AI 应检查：

1. AI 统一入口是否能指向 LDVH 规范入口和当前执行链路；
2. 工作区级薄入口是否存在、是否复制了权威正文、是否指向错误位置；
3. Code 校验命令是否存在，或缺口是否已记录；
4. Web 是否只作为 Human-facing 展示、确认或受控轻写入入口；
5. Code/Web 状态是否被错误当作最终事实源；
6. 运行投影、Code 和 Web 是否与 42、04、07、08 的边界一致。

工具失败或 Web 不存在不必直接判定产品不可用，应按审计范围判断是否属于必要能力、可降级能力还是后续增强缺口。

### 6.7 汇总审计结论

审计结论应按以下状态表达：

| 状态 | 含义 |
|---|---|
| pass | 审计范围内关键事实源、入口和承载均可定位，未发现阻塞缺口 |
| pass-with-warnings | 关键链路可用，但存在非阻塞 warning、待增强项或可接受降级 |
| degraded | 关键链路可用但依赖降级方式，必须记录残留风险和后续建议 |
| blocked | 缺少关键事实源、权限、路径、入口、配置或 Human Gate，不能宣称审计通过 |
| out-of-scope | 当前请求不覆盖该项，不能据此判断通过或失败 |

审计结论不得只写“正常”“已完成”或“没问题”。必须说明证据、范围、状态、缺口和分流去向。

### 6.8 分流缺口

产品审计发现的缺口应按以下规则分流：

| 缺口类型 | 分流去向 |
|---|---|
| 初始化缺口 | 42 安装与接入初始化 |
| 规范落地要求缺口 | 41 规范落地统筹 |
| 管辖项目配置漂移 | 52 candidate 或 03.06 受控修改，当前按 Human Gate 处理 |
| 可执行修复项 | Task |
| 长期决策或边界变更 | ADR |
| 暂不执行但有保留价值的信息 | Memo |
| 可复用风险或经验 | Pitfall 或最佳实践候选 |
| 已实际修改事实源 | Change / Git commit 记录 |
| Code 或 Web 能力缺口 | Code/Web 需求、Task 或 41 |

无法立即分流的缺口应保留为审计 open item，并说明阻塞原因和需要 Human 决定的事项。

---
## 7. Gate 触发条件

以下情况必须触发 Human Gate：

1. 审计范围不清且继续执行可能误判多个项目；
2. 需要新增、删除或修改 `LDVH-GOVERNED-PROJECTS.yaml`；
3. 需要创建、修改或删除 LDVH-AI-ENTRY.md、工作区级入口或平台适配清单；
4. 需要创建、删除、重命名项目 `docs/`、`ldvh-base/` 或关键子目录；
5. 需要修改项目初始化结果或把审计结论写入非默认位置；
6. 需要接受长期降级、关闭关键审计缺口或宣称 blocked 转为 pass；
7. 需要修改正式规范、Code、Web、Skill、Agent、Hook、CI 或运行投影；
8. 审计结论会影响项目是否被视为可用、可交付、可迁移或可继续执行。

Human Gate 前，AI 应说明影响范围、拟写入位置、可替代方案、残留风险和不执行的后果。

---
## 8. Skill 和 Agent 调度

产品审计默认由主控 AI 执行，不要求创建专用 Skill。

当审计涉及 ADR 决策、长期边界或状态流转时，应按 ADR 工作模型和对应 ADR Skill 规则处理。Skill 输出不得绕过本文的审计范围、事实源边界和 Human Gate。

以下情况可按 44 使用多角色思考或 Agent 辅助：

1. 审计范围跨多个项目、多个入口或多个机制；
2. 环境适配、配置边界、Code/Web、Human Gate 或事实源分流存在争议；
3. 审计结论会影响长期产品体验、规范定位或受控写入策略；
4. 需要并行检查多个项目且结果必须由主控统一汇总。

Agent 输出只是审计输入，不是最终事实源。主控必须汇总、去重、判断冲突，并按本文回写或分流。

---
## 9. 工具协作适配

产品审计可以使用 Code、命令、搜索、文件检查和 Web 协作，但必须遵守以下边界：

1. Code 可以检查配置字段、路径存在性、目录结构、初始化结果、入口引用和索引一致性；
2. Code 输出是证据，不是审计结论本身；
3. 命令执行失败应记录失败原因、影响范围和降级方式；
4. Web 可以展示审计结果、缺口和 Human Gate 选择，但不得替代 Git 文件事实源；
5. 工具不得静默修改配置、入口、目录、平台清单、初始化结果、Code 或 Web；
6. 工具能力缺失时，应记录为审计缺口或分流为 Code 需求，不得降低审计标准。

---
## 10. 事实源回写与证据留存

产品审计应按以下规则回写事实和证据：

1. 审计过程证据可以留在当前对话、Task 证据或后续审计报告中，但稳定事实必须写回对应 Git 文件；
2. 初始化缺口应回到 42 的初始化结果或 Task；
3. 环境适配缺口应回到平台适配清单、42 初始化结果、Task、Memo 或 41；
4. 管辖项目配置变更应写入 `LDVH-GOVERNED-PROJECTS.yaml`，且必须 Human Gate；
5. 项目初始化结果变更应写入 42 记录的初始化结果路径；
6. 规范缺口应进入 41、Task 或正式规范修改；
7. 长期决策应进入 ADR；
8. 实际修改应通过 Git diff 和后续 Change / commit 证据追溯。

审计输出至少应包含：

1. 审计日期；
2. 审计范围；
3. 读取的事实源；
4. 每项检查状态；
5. pass / pass-with-warnings / degraded / blocked / out-of-scope 结论；
6. 证据摘要；
7. 缺口清单；
8. 分流去向；
9. Human Gate 结果；
10. 后续建议。

## 11. 机制适配边界

产品审计的机制适配边界如下：

本节只说明产品审计可借用哪些机制承接审计子步骤及其边界，不构成平台能力盘点；产品审计的主轴仍是当前平台适配清单中的要求响应矩阵、初始化结果和事实源证据。

| 机制 | 可承接内容 | 不可承接内容 |
|---|---|---|
| Rules / Instructions | 提醒 AI 在初始化后、配置变化后或用户询问可用性时考虑产品审计 | 不承载完整审计正文，不替代本文 |
| Skill | 可承接特定审计子步骤、ADR 判断或上下文准备 | 不绕过主控审计结论和 Human Gate |
| Agent | 可并行检查多个项目或专项风险 | 不单独写入最终事实，不替代主控汇总 |
| Code | 可检查路径、字段、目录、索引和入口引用 | 不替代语义审计、Human Gate 或长期决策 |
| Web | 可展示审计结果和收集 Human 选择 | 不作为最终事实源，不静默写入 |
| Hook / CI | 可在配置、入口或目录变化后触发审计提醒或校验 | 不自动接受降级，不自动宣称通过 |
| Human Gate | 决定高影响写入、范围扩展、长期降级和审计结论确认 | 不替代事实源读取和证据检查 |

## 12. 行动特有可测试性锚点

产品审计至少应能派生以下测试锚点：

| 类型 | 锚点 |
|---|---|
| 正向场景 | 用户要求检查 LDVH 是否完成接入、是否持续有效或是否漂移时，应进入产品审计 |
| 负向场景 | 用户要求首次安装或补齐初始化时，应优先进入 42，不应直接宣称审计通过 |
| Gate 场景 | 修改配置、入口、平台清单、项目目录、初始化结果或接受长期降级前必须暂停确认 |
| 回写场景 | 审计发现应分流到 42、41、Task、ADR、Memo、Pitfall、Change、Code/Web 或对应事实源 |
| 失败降级 | 缺少配置、路径、权限、入口或 Human Gate 时，应输出 blocked 或 degraded，不得输出 pass |
| 回归风险 | 修改 42、03.06、04、20、40、Code/Web 或入口投影后，应重新检查产品审计锚点 |

## 14. 检查要求

检查一次产品审计是否符合本流程时，应确认：

1. 已明确审计范围和触发原因；
2. 已读取或记录缺失的平台适配清单、现场环境确认证据、管辖项目配置、入口和目标项目事实源；
3. 已按平台清单、环境、配置、项目、目录、入口、工作模型、工作流程、Code/Web 和缺口分流检查；
4. 已区分 pass、pass-with-warnings、degraded、blocked 和 out-of-scope；
5. 需要 Human Gate 的修改或结论确认没有被跳过；
6. 审计发现已分流到正确事实源或后续流程；
7. 未把审计报告、工具输出、聊天结论或 Web 状态当作最终事实源；
8. 已说明本次审计不能覆盖的范围和残留风险。
