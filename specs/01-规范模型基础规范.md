## 1. 价值判断

规范模型（Specification Model）的价值，是让 AI 能快速找到来源明确的规则，理解每份规范的责任和相互关系，并让 Code 能稳定识别、解析和检查规范文档。

本文主要服务：

1. V1 快速定位：通过职责标识符、编号、路径、YAML 身份和正文结构定位规范及其规则；
2. V2 充分理解：区分规范依据、结构归属、附件授权和其它正文引用的效力边界，并按当前需要从概览逐步展开到充分上下文；
3. V3 边界识别：区分当前规则源、草案、历史材料和 Code 生成结果；
4. V6 工作接续：让不同会话和执行者使用同一套规范身份和定义来源；
5. V8 持续积累：让规范结构、关系和术语中的问题能被发现、修正和复用。

共同结构只有在减少 AI 的搜索、猜测、遗漏和维护负担时才有价值。本文不追求让所有规范拥有相同的主体内容，也不为低频版本升级、批量改号或历史迁移预设繁复流程。

本文不得改变或重新解释 00 对 LDVH 存在理由、AI 执行者、Helper CLI、事实源、五类构成要素、V1–V8、验证要求、Human Gate 和 Stop Conditions 的定义。

## 3. 职责边界

本文负责定义：

1. 根规范、普通规范和授权附件三种规范文件角色；
2. 规范和附件的 YAML 机器身份；
3. 根规范与普通规范的正文结构；
4. 规范依据、结构归属、附件授权和其它正文引用的效力边界；
5. 规则如何在 Markdown 正文和结构化表格中表达，并向 Code 暴露可解析入口；
6. 规范正文及授权附件如何取得当前规则源资格；
7. 双语术语的统一治理规则和定义来源边界；
8. 规范信息的渐进式披露层级、来源回指和安全展开边界；
9. 新建、拆分、合并和取消规范时的判断规则；
10. 可复用的普通规范文档模板。

本文不定义：

1. 具体规则在当前事项中的适用判断与效力；
2. AI 需要遵守的具体行为规则；
3. Helper CLI 的服务、命令、响应或实现；
4. 项目和工作对象的管辖解析；
5. 事实模型、行动模板、Code 和 Web 的领域规则；
6. 解析器算法、错误码、测试实现、环境接入和版本迁移操作步骤。

## 4. 适用范围

本文适用于：

1. `specs/` 根目录中的 LDVH 规范文档；
2. `specs/attachments/` 中由规范正文明确授权的附件；
3. Human、AI 和 Code 对上述文件的发现、识别、定位、解析、引用和一致性检查。

本文不将 `docs/`、`archive/`、Code、tests、聊天、评审结论、缓存、索引或工具输出转化为规则源。其中经过确认的规则陈述，只有被正式规范正文或其授权附件吸收后，才能在来源规范定义的范围内取得规则效力；原始 Code、tests 或工具输出本身不因被吸收而取得规则身份。

## 5. 基础术语

### 5.1 规范文档（Specification）

规范文档是位于 `specs/` 根目录、承担一项明确且稳定规范责任的 Markdown 文档。“Spec”是 Specification 的缩写。

### 5.2 根规范（Root Specification）

根规范是定义 LDVH 存在理由、根级架构、价值标准和上位边界的规范。当前只有 `specs/00-理念与构成.md` 是根规范。

### 5.3 普通规范（Regular Specification）

普通规范是根规范之外，按本文定义的共同正文结构组织具体规则的规范文档。

### 5.4 授权附件（Authorized Attachment）

授权附件是由唯一父规范在 YAML 身份和正文中明确授权，用于承载稳定字段表、枚举、矩阵或术语登记等结构化内容的 Markdown 文件。

### 5.5 YAML 身份块（YAML Identity Block）

YAML 身份块是规范文档或授权附件 H1 标题后固定位置的 `yaml` 代码围栏，用于向 Human、AI 和 Code 提供机器可解析身份。

### 5.6 定义来源（Definition Source）

定义来源是对某个概念的含义、边界和相邻概念差异承担唯一定义责任的正式规范章节。

### 5.7 职责标识符（Responsibility Identifier）

职责标识符是不随标题、编号或路径变化，且不得改派给其它职责的规范职责身份，由规范的 `spec_key` 或附件的 `attachment_key` 承载。`spec_id`、`attachment_id`、标题和路径都不是职责标识符。

### 5.8 渐进式披露（Progressive Disclosure）

渐进式披露是根据当前信息需要，先提供最小且足够的来源可回指信息，并在信息不足、风险提升或消费方要求时展开更完整上下文的信息提供方式。它是规范信息的消费方式，不是第六类构成要素、独立服务或新的规则源。它不表示隐藏已经命中的强制要求，也不强制所有消费都必须从最低层逐级开始。

## 6. 当前规则源

### 6.1 候选文件范围

Code 只从当前工作树中以下位于当前 Git worktree、未被 Git ignore 规则排除的普通 Markdown 文件发现规范候选，不跟随符号链接：

1. `specs/<至少两位数字>-<规范标题>.md`；
2. `specs/attachments/<父规范编号>.Att.<至少两位序号>-<附件标题>.md`。

候选既可以是已经跟踪的文件，也可以是尚未提交的新文件；当前工作树中已经删除的文件不因仍存在于 `HEAD` 而继续成为候选。路径只决定候选范围，不自动产生规则资格。

### 6.2 进入当前规则源的条件

规范正文进入当前规则源，必须同时满足：

1. 位于候选文件范围；
2. YAML 身份块可以按本文解析，职责标识符和当前编号唯一，且身份与实际标题、编号和路径一致；
3. `status` 为 `active`；
4. 正文符合根规范或普通规范的结构；
5. 声明的直接规范依据和结构父规范存在且当前有效；
6. 没有另一份当前有效规范重复承担同一规范责任；
7. 新建规范或实质改变现有规范责任时，已按 §13 完成判断与独立复核，没有经主执行者按证据核对后仍成立的责任重复、承载位置或净价值实质异议。

授权附件还必须同时满足：自身 `status` 为 `active`、唯一父规范当前有效、父规范的 `authorized_attachments` 明确列出它，且父规范正文已定义它承载的对象和边界。

`active` 只是进入当前规则源的必要声明，不是有效性证明。声明为 `active` 但结构、关系或授权错误的文件是规则源不一致，不得通过静默忽略它继续。

### 6.3 草案、退出和当前版本

`status` 只使用 `draft`、`active` 和 `retired`：

| `status` | 含义 | 是否进入当前规则源 |
|---|---|---|
| `draft` | 正在起草或审核 | 否 |
| `active` | 声明当前生效 | 在其余成立条件同时满足时是 |
| `retired` | 已退出当前使用 | 否 |

`draft` 可转为 `active` 或 `retired`，`active` 可转为 `retired`，`retired` 是终态，不得重新启用。需要恢复已退出的职责时，应创建新的职责标识符，并按本文的替代关系规则处理。

当前规则源以当前工作树（Working Tree）中的实际文件内容为默认读取视图。新建、修改、重命名、退出或删除尚未提交，不使当前工作树中的变化失效；其中满足 §6.2 的 `active` 规范及授权附件按当前内容进入当前规则源，`draft` 和 `retired` 仍按状态边界处理。

暂存区（Index）只表示准备进入下一次提交的内容，`HEAD` 只表示当前检出的最近已提交版本。二者用于差异检查、提交前验证和 Git 历史溯源，不得覆盖当前工作树、使 AI 或 Code 回退读取旧内容，或者成为规则生效开关。当前工作树中的 `active` 文件若结构、关系或授权不成立，必须报告规则源不一致并暂停依赖受影响内容的范围，不得静默回退到 Index 或 `HEAD` 中的旧版本。

准备提交时，必须另外验证暂存区实际将提交的完整内容；提交后应确认 `HEAD` 已记录预期版本。提交完成只补充可回查的 Git 历史锚点，不改变此前已经依据当前工作树成立的规则效力，也不证明规则内容正确或验证范围扩大。

本文只定义结果边界：修改、移动、替换或退出当前规范时，不得丢失仍然适用的规则，也不得同时保留两份承担同一责任的当前规范。具体迁移步骤只在实际需要时另行规定。

## 7. YAML 身份块

### 7.1 固定位置与格式

规范文档和授权附件使用 [GitHub Flavored Markdown 0.29-gfm](https://github.github.com/gfm/) 组织标题、列表、表格和代码围栏。文件第一行必须是唯一 H1 标题。H1 后空一行，紧接一个带 `yaml` 语言标识的代码围栏；该围栏是唯一 YAML 身份块。Code 只解析这个固定位置，不搜索正文中的其他 YAML 示例。

YAML 身份块按 [YAML 1.2.2 Core Schema](https://yaml.org/spec/1.2.2/#103-core-schema) 解析。顶层只包含 `ldvh_spec` 或 `ldvh_attachment` 中的一个映射；不允许重复字段、多个 YAML 文档、自定义标签、锚点、别名或合并键。字符串和字符串列表的成员使用双引号，避免 YAML 标量自动类型造成跨解析器差异。

GFM 与 YAML 只是语法格式依赖，不是 LDVH 领域规则源，也不对 00 的上位语义取得解释权。

### 7.2 启动识别与根规范身份

Code 首次启动规范解析时，只需预先知道：候选文件范围、H1 后固定 YAML 身份块、`ldvh_spec` 与 `ldvh_attachment` 两个顶层名称，用于预读的 `spec_key`、`status` 两个字段，以及规范模型定义职责的固定稳定标识 `specification-model-foundation`。这些只是定位启动契约所需的最小 envelope，不在未验证前授予候选文件规则效力。

根规范使用下列一等身份 profile，不是历史兼容 fallback：

| 字段 | 根规范要求 | 用途与边界 |
|---|---|---|
| 逻辑 `spec_key` | 固定为 `ldvh-root`；由本文赋予，不改写 00 YAML | 根规范的职责标识符 |
| `spec_id` | 固定为 `00` | 与文件名前缀一致 |
| `spec_kind` | 固定为 `spec` | 只表示规范文件类型 |
| `title` | 固定为 `理念与构成` | 与 H1 一致 |
| `status` | 当前根规范固定为 `active` | 根规范当前生效声明 |
| `authority` | 固定为 `active` | 表示 00 是 LDVH 根级规则权威；不是普通规范通用字段 |
| `canonical_path` | 固定为 `specs/00-理念与构成.md` | 当前根规范的 Git 路径 |
| `parent_spec` | 固定为空字符串 | 根规范没有结构父规范 |
| `relation` | 固定为空字符串 | 根规范没有结构父关系 |
| `positioning` | 必填非空字符串 | 根规范的简要定位 |
| `scope` | 必填非空字符串 | 根规范的概括范围 |
| `basis` | 固定为空列表 | 根规范没有上位规范依据 |
| `related_specs` | 字符串列表；当前为空 | 只表示 00 显式保留的普通关联，不建立规范依据、结构归属或规则效力 |
| `code_consumption` | 非空字符串列表 | 保留 00 声明的根级 Code 消费入口；不证明已实现 |

Code 按以下顺序完成启动闭环：

1. 使用最小 envelope 扫描候选文件，唯一定位 `spec_key: "specification-model-foundation"` 的候选规范，只预读其内容，不预设其已生效；
2. 从候选规范中加载上述根规范 profile；
3. 按 root profile 唯一验证当前 00，并将其映射为 `ldvh-root`；
4. 以已验证的 `ldvh-root` 及本文完整契约，回头验证候选规范的全部身份、正文结构、`basis`、`parent_spec`、附件授权和 `status`；
5. 只有当根规范与 `specification-model-foundation` 两侧验证同时成立，且承担者为 `active` 时，才使用本契约判定其他普通规范。

候选承担者缺失、重复、非 `active` 或完整验证失败时，暂停依赖相应身份契约的范围，不按编号、标题或路径猜测承担者。

### 7.3 普通规范身份字段

| 字段 | 要求 | 用途与边界 |
|---|---|---|
| `spec_key` | 必填 | 规范的职责标识符；匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，不含编号、路径、状态或版本 |
| `spec_id` | 必填 | 至少两位数字的当前规范编号；与文件名前缀一致，用于 Human 排序和引用 |
| `spec_kind` | 必填 | 固定为 `spec`；只表示文件类型，不表示五类构成要素归属 |
| `title` | 必填 | 当前规范标题；与 H1 一致 |
| `status` | 必填 | `draft`、`active` 或 `retired` |
| `canonical_path` | 必填 | 当前 Git 相对路径；与实际文件一致 |
| `parent_spec` | 条件字段 | 唯一直接结构父规范的 `spec_key`；只在存在真实结构归属时与 `relation` 成对声明 |
| `relation` | 条件字段 | 与 `parent_spec` 的结构关系；不存在 `parent_spec` 时不得声明 |
| `positioning` | 必填 | 一句话说明该规范的唯一定位，用于 AI 和 Helper 快速筛选；不复制章节目录 |
| `scope` | 必填 | 一句话概括适用对象和场景，用于初步定位；不代替正文适用范围 |
| `basis` | 必填 | 直接且必要的上位规范 `spec_key` 列表 |
| `authorized_attachments` | 必填 | 该规范明确授权的 `attachment_key` 列表；无附件时为空列表 |
| `supersedes` | 可选 | 被当前规范实质替代的旧 `spec_key` 列表；同一职责改名或移动时不使用 |

`spec_key` 是规范职责的稳定身份，在标题、编号或路径变化时保持不变，且不得重新分配给其他职责。普通规范使用上表字段闭集；可选字段无值时直接省略，不使用空值占位。

`title` 和 `canonical_path` 分别对 H1 与 Git 实际路径提供可校验的机器镜像；`positioning` 和 `scope` 为 AI 与 Helper 在不全文读取时提供快速筛选摘要。这四个字段的净价值分别是一致性检查和 V1 快速定位；它们不得覆盖 H1、实际路径或正文。

### 7.4 附件身份字段

| 字段 | 要求 | 用途与边界 |
|---|---|---|
| `attachment_key` | 必填 | 附件的职责标识符；匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，不含编号、路径、状态或版本 |
| `attachment_id` | 必填 | `<父规范当前编号>.Att.<至少两位序号>`；与文件名前缀一致 |
| `title` | 必填 | 当前附件标题；与 H1 一致 |
| `status` | 必填 | `draft`、`active` 或 `retired` |
| `canonical_path` | 必填 | 当前 Git 相对路径；与实际文件一致 |
| `positioning` | 必填 | 说明附件只承载什么结构化内容 |
| `supersedes` | 可选 | 被当前附件实质替代的旧 `attachment_key` 列表 |

`attachment_key` 在附件标题、编号或路径变化时保持不变，且不得重新分配。附件不自我声明父规范或授权关系；授权权威只来自父规范的 `authorized_attachments` 及对应正文，Code 从父侧声明生成附件的反向归属。

YAML 身份只承载文件身份、状态、定位、概括范围和主动声明关系。它不代替正文的价值、定义、具体规则、验证、Human Gate 或 Stop Conditions。YAML 与正文冲突时，必须修正不一致，不得选择更方便的一方继续。

## 8. 正文结构

### 8.1 根规范结构

根规范保留 00 已确认的上位叙事结构，不改成本文的普通规范结构。根规范文末保留验证要求、Human Gate 和 Stop Conditions。

### 8.2 普通规范结构

普通规范由固定头部、自由规则主体和固定尾部组成。

固定头部依次为：

1. `价值判断`；
2. `规范依据`；
3. `职责边界`；
4. `适用范围`。

自由规则主体只承载该规范在自身责任内定义的术语、具体规则、边界和结构化契约，章节名称和数量由该规范的责任决定。

固定尾部依次为：

1. `验证要求`；
2. `Human Gate`；
3. `Stop Conditions`。

全部 H2 使用连续阿拉伯数字编号。没有新增 Human Gate 或 Stop Conditions 时仍保留相应章节，并明确“本文不新增相应条件，沿用 00 及实际适用的来源规则”；不得为填充模板制造无实际边界的条件。

“保障措施”、“待补齐事项”、“版本历史”不是所有普通规范的固定章节。只有当某份规范的实际责任需要时，才在自由规则主体中定义对应内容。

### 8.3 验证要求结构

普通规范的验证要求使用 00 已定义的七列：

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|

验证章节定义可复核的成立条件，不声明某次检查已经通过。没有真实成立条件和依据时，不得用空泛的“AI 审核”或“后续测试”填充。

## 9. 规则表达与 Code 读取

### 9.1 规则的语义来源

规范正文是规则含义、边界和适用条件的来源。YAML 身份块只帮助发现和解析，附件只能在父规范已授权的边界内承载结构化细节。

具体规则使用直接、词义一致的陈述，并在来源规范的适用范围或对应规则章节中说明适用对象与场景。例如、说明和建议不因出现在规范中自动取得强制效力；需要 Code 稳定引用的规则，应当放入具有明确标题、表头或结构说明的段落、列表、表格或授权附件。

每条具体规则的适用范围和效力由该规则的来源规范定义；本文只规定规则的承载位置、表达边界和解析入口，不用结构字段替代该判断。

### 9.2 Code 分层读取

规范模型将可披露信息分为以下五层。层级表示消费方获得的信息深度，不限制 Code 内部必须以同样方式读取文件。

| 层级 | 名称 | 承载内容 | 直接用途 | 不能单独证明 |
|---|---|---|---|---|
| L0 | 发现层（Discovery） | 载体类型、稳定 key、当前编号、标题、状态和路径 | 发现、去重、状态过滤和精确定位 | 规范与当前事项相关，或具体规则已生效 |
| L1 | 概览层（Overview） | 规范的 `positioning`、`scope`；附件的 `positioning` | 不全文读取时快速初筛候选规范和附件 | 最终适用范围、规则效力或完整约束 |
| L2 | 关系层（Relationships） | `basis`、`parent_spec`、`relation`、`authorized_attachments`、`supersedes` 及 key/路径映射 | 建立规范依据、结构归属、附件授权和替代关系上下文 | 上位规范的所有规则都对当前事项生效 |
| L3 | 规则层（Rule Context） | 被选中的来源章节、规则陈述、结构化表行或授权附件片段，以及理解它们所必需的范围、定义、验证、Human Gate 和 Stop Conditions 上下文 | 向 AI 提供可判断和履行的候选规则上下文 | 被选中的候选规则已经命中，或已被自动保障 |
| L4 | 全文层（Full Source） | 完整来源规范正文，以及当次判断明确需要的上位规范和授权附件全文 | 完整回读、审核、冲突处理和高影响变更 | Code 已实现规则、环境已接入、验证已通过或行动已完成 |

L0–L2 直接来自 YAML 身份及其可验证关系；L3–L4 来自规范正文和授权附件。这些层级映射现有结构，不要求每份规范再增加一组披露字段。

### 9.3 渐进式披露完整性

渐进式披露必须同时保持精简和语义完整：

1. 每个披露结果都必须明确自身层级，并能回指稳定 key、当前路径和具体位置（字段、标题、表行或附件片段）；同一结果混合多个层级时，必须能区分各部分所属层级。Code 生成的结果还必须保留输入来源回指。
2. L0–L2 只用于发现、初筛和构建关系上下文；不得用它们证明“当前没有适用规则”，也不得以摘要替代具体来源规则。
3. L3 不得把单条规则与其适用范围、必要定义和相关验证、Human Gate 或 Stop Conditions 剥离。无法确定最小完整上下文时，必须展开到 L4 或如实报告不可确定。
4. 当摘要与正文冲突、来源无法回指、信息不足以支持当前判断、可能遗漏强制要求/Gate/Stop，或消费方明确要求全文时，必须展开到足够层级或报告能力缺口，不得静默给出超出已披露依据的结论。
5. 消费方可以直接请求任意足够层级；本文不强制每次请求依次经过 L0–L4，也不将分层读取变成 AI 普通求解前的固定仪式。

本文只定义披露层级、层级内容和最小完整性边界。当前工作对象如何进入选择输入、具体规则如何判定命中与效力、Helper CLI 如何选择层级和组织响应，分别由承担相应职责的规范定义。

Code 可以生成规范目录、关系视图、读取建议和一致性诊断，但这些结果必须能回指当前规则源，不得改变规则身份、含义、适用范围或效力。YAML 字段、固定结构和附件授权只定义 Code 可以消费的输入契约，不表示对应解析器、validator、Helper 命令或测试已实现、已接入或已验证。

## 10. 规范关系

| 关系 | 承载位置 | 含义 | 不用于 |
|---|---|---|---|
| 规范依据（Normative Basis） | `basis` | 通过 `spec_key` 指向理解、判断或维护当前规范所必需的直接上位规范 | 编号相邻、Code 实现、测试覆盖或下游消费者 |
| 结构归属（Structural Parent Relationship） | `parent_spec` + `relation` | 通过 `spec_key` 表示当前规范属于或细化哪个唯一直接父规范 | 自动代替 `basis` 或构造表面层级 |
| 附件授权（Attachment Authorization） | 父规范 `authorized_attachments` 和正文 | 通过 `attachment_key` 确认附件的唯一父规范和承载边界 | 授予附件独立扩张父规范的权力 |
| 替代关系（Supersession） | `supersedes` | 通过职责标识符记录当前规范与被其拆分、合并或替代的旧职责之间的关系；正文必须说明旧职责中仍适用内容是保留、转移还是退出 | 表示同一职责的改名、改号或移动 |
| 其它正文引用（不作为正式关系） | 正文链接或来源回指 | 只表示引用所在语句明示的关系 | 暗示依据、结构归属、授权或规则效力 |

当前普通规范的 `relation` 只使用 `refines`，表示在唯一直接父规范之下细化独立规范责任。未来确有稳定需求时，应先修改本文定义新关系，不得由单篇下位规范自行增加关系枚举。

`basis` 和 `parent_spec` 中的当前规范必须存在且当前有效，不得自指；全部当前有效规范的两类关系分别不得形成循环。`basis` 只保留直接且必要依据，不重复列出可通过上位规范到达的间接依据。

同一职责只改标题、编号或路径时保持原 `spec_key` 或 `attachment_key`，不声明 `supersedes`。发生实质拆分、合并或替代时，新载体的 `supersedes` 必须指向已存在的同类型旧职责，不得自指、重复或形成循环；正文必须说明旧规则的承接或退出结果。新载体转为 `active` 时，被替代的旧载体必须在同一提交中转为 `retired`，不得同时保留两份承担同一当前职责的有效规则。

规范宣称依据某上位规范，不表示上位规范的每条具体规则都对当前事项无条件生效。具体规则的适用范围和效力仍由来源规范定义；未命中具体规则时，不因身份、关系或 Code 生成结果而限制 AI 的普通求解路径。

## 11. 授权附件

授权附件只用于承载父规范已经定义并明确授权的稳定结构化内容。本文通过 `attachment_key: "ldvh-bilingual-terminology"` 授权 `specs/attachments/01.Att.01-LDVH双语术语表.md` 登记双语术语及其唯一定义来源。

附件只能出现在一份当前有效父规范的 `authorized_attachments` 中。附件取得 `active` 且满足授权条件后，在父规范授权的登记字段或结构范围内属于同一 LDVH 规则源；它不因此成为独立概念定义来源。

附件不得承载：

1. 00 的根理念或构成要素定义；
2. 父规范尚未定义的核心规则；
3. 独立适用范围、行动流程、Human Gate 或 Stop Conditions；
4. 可以由 Code 从规范身份和关系直接生成的目录、反向关系或读取建议。

附件与父规范正文冲突时，必须暂停消费受影响内容并同步修正；不得把附件作为规避父规范的便利例外。

## 12. 双语术语治理

### 12.1 责任分工

双语术语的治理方法归本文；每个术语的含义和边界归唯一定义来源。

本文负责规定哪些术语需要双语治理、候选术语如何检查、登记表载什么、术语状态如何成立以及术语冲突如何处理。双语术语表在本文授权下登记中文规范术语（Canonical Chinese Term）、英文规范术语（Canonical English Term）、别名和机器表示；定义某个概念的来源规范负责其含义、边界和与相邻概念的差异。来源规范已经明确中英文名称时，术语表必须与之一致。

定义来源存在只证明“在哪里定义”，不能自行证明概念有必要、定义准确、名称自然或中英文范围一致。初始命名者、定义来源和术语表不得相互循环证明候选术语正确。术语审查和概念必要性判断是 AI 执行者的责任，不能依赖 Human 在后续阅读中逐个发现问题；Human 确认也不能替代语义检查。

00 定义的 Helper、事实源、规范模型等概念仍以 00 为定义来源；本文和术语表都不重新定义它们。

### 12.2 概念先于名称

[ISO 704:2022](https://www.iso.org/standard/79077.html) 区分对象、概念、定义和名称，并分别规定术语形成与定义编写原则；[W3C SKOS](https://www.w3.org/TR/skos-primer/) 也区分概念和用于标记概念的自然语言标签。本文参考这一基本区分，但不要求 LDVH 实现 ISO 术语数据库或 SKOS 数据模型。

提出正式术语前，必须先不用候选名称、只用普通语言说明预期含义，包括它指向什么、解决什么歧义以及与相邻内容有什么不同。只有这个概念本身具有稳定、独立且可重复使用的边界，才继续为它选择名称。

以下情况不建立新的正式术语：

1. 使用普通语言已经能够准确表达，命名不会减少实际理解或消费负担；
2. 现有术语已经覆盖相同概念，只需要澄清用法；
3. 只是为了给一组性质不同的内容提供统一简称；
4. 预期含义主要描述用途、处理阶段或实现便利，尚不能形成稳定概念边界；
5. 只在一次版本更新、内部迁移或低概率操作中使用，不具有跨规范或机器消费价值。

### 12.3 纳入双语治理的条件

符合以下任一条件的术语，应进入双语治理：

1. 在多份规范中稳定使用；
2. 属于 LDVH 核心架构、规则、对象或状态概念；
3. 暴露给 Helper、Code、Schema 或其他机器接口；
4. 存在翻译、缩写、别名或跨语言理解歧义。

只在单篇规范的局部语句中使用、不影响跨规范理解的普通表达，不强制登记，避免把普通写作变成术语管理工作。

### 12.4 候选术语检查

候选术语转为 `current` 前，必须形成可复核的检查记录。记录可以位于定义来源草案或 `docs/` 中的当前架构工作记录；它只提供检查依据，不成为定义来源或第二规则源。记录至少包含：

1. 预期含义：不使用候选名称描述准备表达的概念；
2. 必要性：现有术语或普通语言为什么不足，以及不建立该术语会产生什么具体歧义或消费问题；
3. 来源分类：该名称属于行业标准术语、常见描述性表达还是 LDVH 特定术语；
4. 中英文候选：至少检查规范中文名、规范英文名和确有意义的替代表达，不以逐字翻译代替概念对齐；
5. 定义：用直接语言说明它是什么，以及区别于相邻概念的必要特征；
6. 正例与反例：列出明确属于和看似相近但不属于该概念的代表性对象；
7. 相邻概念：说明上位、下位或容易混淆的概念及其差异；
8. 替换检查：把定义替换进代表性实际语句后，原句含义仍成立，且定义中的每类对象都符合候选名称；
9. 使用扫描：检查 00、当前定义来源、术语表、其它当前规则源、标题、表头和重复用语，确认没有范围漂移、同名异义或同义多名；
10. 影响范围：说明接受、改名或取消该术语会影响哪些规范、附件、字段、Schema、Code 或事实记录；
11. 检查结论：只能是保留、澄清定义、改名或取消正式术语，并列出尚未解决的异议。

来源分类遵守以下边界：

| 来源分类 | 成立要求 | 禁止表述 |
|---|---|---|
| 行业标准术语 | 具有相关标准组织、正式规范或等价一手权威来源，且 LDVH 用法没有扩大或改变来源概念 | 没有直接来源时声称“行业标准”“最佳实践”或“通用模型” |
| 常见描述性表达 | 在相关领域具有自然、可检索且含义相近的真实用法，但不存在或未采用统一标准定义 | 把常见用法包装成统一行业术语 |
| LDVH 特定术语 | 现有行业或普通表达不足，LDVH 确有独立稳定概念需要命名 | 隐去内部定义性质，或者仅为内部简称反向创造概念 |

没有可靠来源时，只能如实标记为常见描述性表达、LDVH 特定术语或来源未确认，不得用执行者记忆补成行业结论。

### 12.5 不通过条件

出现以下任一情况，候选术语不得转为 `current`：

1. 名称覆盖范围比定义更窄或更宽，或者定义列举的对象不能由名称自然包含；
2. 定义主要说明“用于什么”或“何时产生”，却没有说明它是什么和与相邻概念的区别；
3. 正例中包含性质不同、只能靠抽象概括勉强归为一类的对象；
4. 无法提供反例，或反例与正例之间没有可执行的区分标准；
5. 中文与英文指向不同范围，英文只是中文逐字翻译，或者任一语言表达不自然、不可检索或容易产生错误联想；
6. 定义依赖候选名称本身、同义改写或定义来源自我引用形成循环；
7. 现有术语或普通语言已经足够，却仍为形式完整、编号、字段或实现便利创造新名称；
8. 对行业通用性、标准性或最佳实践的描述没有一手可靠来源；
9. 替换检查、使用扫描或独立复核发现未解决的范围冲突、同名异义或词不达意。

检查不通过时，优先取消正式术语并改用准确的普通表达；只有概念必要但名称或定义有问题时，才继续提出替代名称或修正定义。

### 12.6 独立复核与责任

候选术语转为 `current` 前，必须经过至少一次独立于初始命名的复核。独立复核者应是未参与初始命名的另一 AI 执行者或专门审查者；复核必须主动寻找反例、范围错配、相邻概念冲突和更自然的中英文表达，不能只确认登记字段齐全。Human 可以决定业务意图和重大取舍，但不承担替执行者完成语义审计的责任。

独立复核至少覆盖两个视角：

1. 概念视角：不依赖候选名称的原始解释，判断预期含义是否真的形成独立概念；
2. 名称视角：检查中文、英文、定义、正反例和实际用法是否覆盖同一概念。

初始命名者负责提供完整检查记录，独立复核者负责提出异议，主执行者负责核对来源、汇总分歧并作出可解释建议。不得把独立复核或 Human 确认写成责任转移；Human 不负责替执行者完成全量术语发现和语义审计。

Code 只能检查术语登记字段、状态闭集、定义来源存在性、唯一性、引用和机器表示一致性。Code 不能证明名称自然、定义正确、正反例成立或行业来源适用；这些语义结论不得因 validator 通过而自动成立。

### 12.7 表达、登记与状态

受双语治理的术语首次定义时，使用“中文规范术语（Canonical English Term）”。中英文名称必须指向同一概念，英文名称应优先使用当前领域自然、可检索的表达，不得为了逐字对齐制造无法正确表意的名词。

`specs/attachments/01.Att.01-LDVH双语术语表.md` 只登记：中文规范术语、英文规范术语、缩写、机器表示、唯一定义来源、其他有效表达和状态。没有已定义的缩写或机器表示时使用 `—`，不得为填满表格提前发明字段或枚举。状态只使用 `proposed` 或 `current`：

1. `proposed` 表示候选概念或名称尚未完成本文要求的全部检查，不能作为当前规范表达的先例；
2. `current` 表示定义来源当前有效，§§12.2–12.6 的检查已经完成，独立复核没有未解决的语义异议，并且中英文名称、机器表示和定义来源一致；
3. 需要 Human Gate 的术语改变，只有取得作用范围清楚的 Human 决定后才能成为 `current`，但 Human 决定不能豁免 §§12.2–12.6 的语义检查；
4. 历史名称如确有定位价值，记入对应当前术语的“其他有效表达”，不另建无归属的历史行。

术语表不复制定义全文，不改写来源语义，也不自行创造概念。某个名称进入 `current` 只证明它在当前定义和使用范围内通过本节检查，不表示该词在 LDVH 之外是行业标准，也不阻止后续证据暴露问题。

术语表与定义来源不一致时，应回到定义来源确认意图，并同步修正登记。术语表不得成为平行定义点或第二规则源。

本节检查要求同样适用于修订前已经登记为 `current` 的术语。缺少检查记录本身不使其定义来源失效，也不造成全局停止，但在完成全量复核前，不得仅凭既有 `current` 状态声称术语已经按本节重新证明可信，或把旧名称当作新增术语的正确先例。审计发现实际语义问题时，必须停止向新规范、字段和实现继续扩散，并按影响范围提出保留、澄清、改名或取消方案。

## 13. 新建、拆分、合并与取消规范的判断规则

规范文档的数量和边界必须来自实际规则责任，不得由历史文件、预期编号、内部管理方便或实现模块数量反向决定。本节使用普通语言规定判断顺序和成立条件，不为判断过程另行创造架构术语。

本节所说的“实质改变现有规范责任”，是新增、删除或转移规则对象，改变职责边界或适用对象，或者使原应由相邻规范承担的规则进入本规范。在已有责任边界内补充具体规则、澄清等义表达、修正错误或增强验证要求，不因正文变化本身被视为实质改变责任。

### 13.1 固定判断顺序

新建规范、实质改变现有规范责任，或者判断是否拆分、合并或取消规范时，必须依次完成：

1. 先对照 00 确认根级定义、五类构成要素、Helper 和 Web 边界、V1–V8、Human Gate 与 Stop Conditions；
2. 不使用候选标题或 `spec_key`，直接说明准备约束什么对象、关系或行动，以及准备定义哪些具体稳定规则；
3. 逐条检查候选规则是否已由 00、当前有效规范、具体规则的来源规范或已授权附件完整承担；
4. 移除已有规则的重复转述、只属于实现或测试的细节、一次性工作步骤、只服务单次运行或具体实现且没有跨消费方稳定契约价值的内部状态管理，以及未经证明的未来设想；
5. 对剩余规则先按 §13.3 比较实际承载位置，再使用比较结果执行 §13.2 的全部成立条件；
6. 按 §13.4 判断保持、拆分、合并或取消，并完成 §13.5 要求的记录与独立复核；
7. 仅就“规范责任是否应独立存在”这一未决问题，只有在上述判断仍无法收敛，或涉及重大价值取舍时，才由本节新增 Human Gate；同时命中 00、§16 或其它来源规则的 Human Gate 时，仍必须按相应规则进入。

候选规范的名称、编号、`spec_key`、YAML 身份和文件路径，只能在准备承担的规则责任通过上述判断后确定，不得用已经起名或预留编号反向证明它应当独立存在。

### 13.2 建立独立普通规范的成立条件

一项候选责任只有使用 §13.3 的承载位置比较结果，并同时满足以下全部条件，才可建立独立普通规范：

1. 有明确的规则对象，能直接说明准备约束的对象、关系或行动，不只是抽象关注点、处理阶段或管理目的；
2. 在移除现有来源已经完整承担的内容后，仍有独有且需要长期生效的具体规则；
3. 这些规则需要唯一且稳定的定义位置，而现有规范无法在不扩大或混淆自身责任的前提下自然承接；
4. 其适用对象、触发场景或变化原因至少一项能够与相邻规范分开判断，不是始终随另一责任同时适用且同时变化的从属内容；
5. 能自然形成普通规范的价值、依据、责任、范围、具体规则和验证要求，不需为满足模板而制造术语、状态、Human Gate 或 Stop Conditions；
6. 可以说明其独立失败场景和验证边界，不依赖另一规范的失败才能解释它为何错误；
7. 拆出文档后能降低 AI 的定位、理解、冲突或维护负担，且该收益高于新增文档发现、跨文档拼接和同步维护带来的成本。

只能说明“这项内容很重要”、“未来可能被 Code 消费”或“与多份规范有关”，不能证明上述条件成立。

### 13.3 独立规范与其它承载位置的比较

判断候选内容是否通过 §13.2 前，必须先比较以下位置：

| 承载位置 | 适合的内容 | 不应承担 |
|---|---|---|
| 现有规范的正文章节 | 与该规范规则对象和责任一致，只需补充或细化的稳定规则 | 经本表比较后，可能具有独立适用、独立变化和唯一定义需求的另一完整责任 |
| 授权附件 | 父规范已定义并明确授权的稳定字段表、枚举、矩阵或术语登记 | 父规范尚未定义的核心规则、独立范围或行动流程 |
| 独立普通规范 | 经本表比较后仍能满足 §13.2 全部条件的稳定规则责任 | 为分类、编号、实现便利或历史对齐而建立的空壳 |
| 事实源中由适用事实模型组织的事实对象 | 符合事实模型准入要求、需要对象化、状态化或证据化管理的稳定事实 | 规则效力、强制行为或规范文档身份 |
| 行动模板 | 已证明具有重复价值的行动结构 | 定义事实语义、规则权威或一次性工作步骤 |
| Code 和 tests | 具体解析、校验、受控操作、测试文件、夹具、目录布局、运行入口及其实现细节 | 反向定义规则含义、稳定工程与测试要求、事实语义或 Human Gate |
| `web/docs/` 及其它实现说明 | 当前实现结构、页面、API、设计语言、测试映射和实践细节 | 反向改写规范、事实模型或其它来源规则 |
| `docs/` 与归档 | 调查、比较、决策过程、历史材料和候选设计 | 当前规则效力或现行事实身份 |

一项内容很重要或需要长期保留，不表示它必须由独立规范承载。必须先根据内容的性质选择位置，再判断是否需要新规范。

本表按内容性质比较承载位置，不表示 Helper、事实模型、行动模板、Code、Web 或环境不能拥有满足 §13.2 的专属规范。稳定外部契约、构成要素治理和工程要求，必须与单次运行状态、具体实现和测试文件分开判断。

### 13.4 保持、拆分、合并与取消

1. 一组候选规则只有在拆分后的每一组都分别满足 §13.2，并且分开后能减少责任混淆或不必要读取时，才拆分为多份规范；
2. 规则对象相同、适用边界始终需要一起理解，或分开后必须重复定义和同步规则时，应保持在同一规范；
3. 两份现有规范重复承担同一责任，或一份只是另一份的摘要、阶段性转述或实现视图时，应合并到唯一责任来源或取消重复规范；
4. 移除重复内容和错误承载内容后，没有剩余规则能满足 §13.2 时，必须取消候选规范，不通过改名继续保留空壳；
5. 合并、拆分或取消现有规范时，仍适用的规则必须进入唯一明确位置，不得遗失，也不得同时保留两份当前有效来源；
6. 只改标题、编号或路径而责任未变时，按 §10 保持原职责标识符；发生实质拆分、合并或替代时，按替代关系处理。

### 13.5 检查记录与独立复核

新建规范或实质改变现有规范责任前，必须在 `docs/` 中形成可复核记录。该记录只提供判断依据，不因记录存在而成为规则源；责任通过本节判断后形成的候选规范草案可以引用该记录，但不得用草案身份反向证明责任必要性。记录至少包含：

1. 不使用候选名称表达的规则对象和预期作用；
2. 准备由该规范唯一定义的具体规则清单；
3. 每条候选规则与 00、现有规范、来源规则和其它承载位置的对照结果；
4. 移除重复、实现细节和一次性内容后的剩余规则；
5. 独立规范、现有规范章节、授权附件及其它位置的比较；
6. 与相邻责任的正例、反例、独立变化原因和失败场景；
7. 对 V1–V8 带来的价值、新增读取与同步成本及净价值结论；
8. 新建、保持、拆分、合并或取消的建议，以及会受影响的规范、附件、事实、模板、Code、tests 和 Web 实践。

上述记录必须经过至少一次独立于初始判断的复核。复核必须主动尝试由现有位置承接候选规则，查找重复、空壳、职责过细、跨文档拼接成本和未被证明的独立失败场景，不能只确认模板完整。

初始判断者负责列出完整候选规则和承载比较，独立复核者负责提出反例和更小方案，主执行者负责根据 00 和当前规则源汇总裁决。Human 可以决定业务意图和重大取舍，但不承担替执行者发现重复责任和证明独立规范必要性的工作。

本节规则适用于今后的新建和责任调整，也适用于现有规范责任受到实质质疑的情况。过去缺少该记录本身不使当前有效规范自动失效；但已经发现责任重复、错误承载或无独有规则时，必须停止向新规范和实现继续扩散，并按影响范围重新判断。

## 16. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 授予的规范模型定义职责，或要求 00 改用普通规范结构；
2. 改变根规范 profile、`ldvh-root` 或 `specification-model-foundation` 的启动识别语义；
3. 改变根规范与普通规范的基本结构、YAML 身份字段闭集、职责标识符、替代关系语义、三种 `status` 或当前规则源成立条件；
4. 改变附件授权的权威边界，或准备让附件承载独立核心规则；
5. 已按 §13 完成候选规则清单、承载位置比较、净价值判断和独立复核，仍无法确定是否应新建、拆分、合并或取消规范；
6. 改变跨规范核心术语的中英文名称或定义来源，且可能改变现有规则理解；
7. 改变 L0–L4 的基本含义、允许概览或关系层替代具体来源规则，或放弃渐进式披露的来源回指和安全展开边界。
8. 改变术语概念先行、来源分类、正反例、替换检查、独立复核或 `current` 准入要求。

普通草案编辑、错别字修正、等义措辞调整，以及不改变上述语义的术语登记同步，不因本文额外进入 Human Gate。

## 17. Stop Conditions

出现以下任一情况时，必须暂停受影响的规范解析、修改或生效声明：

1. 根规范 profile 或 `specification-model-foundation` 承担者缺失、重复或无法解析；
2. 声明为 `active` 的规范或附件无法按本文识别，或身份、状态、标题、编号和路径冲突；
3. `spec_key`、`attachment_key`、`spec_id`、`attachment_id` 或当前路径重复，稳定 key 被改派，或两份当前规范重复承担同一责任；
4. 准备将新建、拆分或合并形成的候选规范转为 `active`，实质改变现有规范责任，或者取消现有当前有效规范，但未按 §13 完成候选规则对照、承载位置比较、净价值判断或独立复核，取消前未按 §13.4(5) 确认仍适用规则的唯一承接位置，或者删除重复与错误承载内容后已无剩余规则满足 §13.2；
5. `basis`、`parent_spec` 或 `supersedes` 指向缺失、类型错误、非当前可承接目标、自身、重复或循环关系，或替代切换后仍保留重复当前职责；
6. 附件未获唯一当前有效父规范授权，与父规范冲突，或超出授权边界；
7. `retired` 载体被重新启用，或准备提交时尚未根据 Index 的实际内容完成必要验证；
8. 准备将候选术语转为 `current`，但概念必要性、来源分类、定义、正反例、相邻概念、替换检查、使用扫描或独立复核缺失，或者存在词义范围错配、中英文不一致、循环定义、无来源的行业声明或未解决异议；
9. 渐进式披露结果无法回指来源，L0–L2 被用作无适用规则的证明，或 L3 剥离了支持当前判断所必需的范围、定义、验证、Human Gate 或 Stop Conditions；
10. YAML、授权附件、术语表、Code、索引、测试或过程记录正在重新定义正文规则，或把未实现的能力声明为已可用。
11. 已经发现既有 `current` 术语存在实际语义冲突或词不达意，却准备继续把该名称扩散到新的规范、字段、Schema、Code 或事实记录。

暂停只影响能够完整覆盖冲突风险的最小规范、附件、关系、术语或声明范围。明确不受影响的普通求解路径不因本节被禁止。
