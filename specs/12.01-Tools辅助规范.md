## 一、本文定位

本文定义 LD Vibe Harness 如何使用 Tools 辅助层承载确定性解析、校验、聚合、上下文包生成、派生数据生成和受控写入执行。

Tools 辅助层面向机器可执行、可重复、可校验的确定性工作。Tools 输出不是事实源，Tools 实现不替代 specs/、ldvh-base/（工作区级目录）或 docs/ 的权威事实。

## 二、父规范关系

`specs/12-LDVH工具基础规范.md` 定义 LDVH 工具体系总边界、事实源回写总原则和 Tools 辅助层 / Web 展示层选择边界。本文只展开 Tools 辅助层。

当需要判断某项工具能力应进入 Tools 辅助层还是 Web 展示层时，必须以 `specs/12-LDVH工具基础规范.md` 第五节为准；本文只检查已拟使用 Tools 辅助层时是否满足解析、校验、聚合、受控写入和输出治理要求。

Tools 辅助层与其他机制的关系：

| 对象 | 关系 |
|---|---|
| Web 展示层 | Tools 辅助层可为 Web 展示层提供派生视图数据和受控写入能力 |
| Git 文件事实源 | Tools 辅助层读取、校验、聚合和写入的目标必须回到 Git 文件事实源 |
| Rules / Skill / Agent | Rules 可约束 Tools 使用方式，Skill / Agent 可按授权调用 Tools；Tools 不得调用 AI、Skill 或 Agent |
| 生产对象 | Tools 辅助层可校验和写入生产对象实例，但字段和状态以 20-49 规范为准 |
| 行动模型 | Tools 辅助层在上下文准备和事实回写中的角色应服从 50-79 行动模型 |

## 三、Tools 辅助层内部设计检查

跨工具层选择依据 `specs/12-LDVH工具基础规范.md` 第五节，本文不另行判断某项能力是否应优先进入 Tools 辅助层或 Web 展示层。已拟使用 Tools 辅助层时，应检查该 Tools 能力是否满足以下内部设计条件：

1. 处理逻辑可由确定性规则描述；
2. 输入来源可追溯到 Git 文件事实源；
3. 输出可以结构化呈现，并标明来源；
4. 写入目标明确且属于对应 Git 文件事实源；
5. 写入前可执行校验；
6. 写入后可通过 Git 追溯；
7. 不依赖聊天记忆、UI 临时状态或缓存作为权威输入；
8. 不调用 AI、Skill 或 Agent；
9. 不绕过 Human Gate。

## 四、允许职责

Tools 辅助层可以承担：

| 职责 | 说明 |
|---|---|
| 读取 | 从 Git 文件事实源读取结构化对象和规范信息 |
| 解析 | 解析 Markdown、YAML 或其他约定格式文件 |
| 校验 | 校验字段完整性、状态合法性、引用有效性和格式合规性 |
| 聚合 | 聚合项目上下文、对象状态、缺口和检查结果 |
| 上下文包生成 | 为 AI 或工具生成可追溯的最小上下文包 |
| 派生数据生成 | 为 Web 展示层生成可追溯的派生视图数据 |
| 受控写入 | 按授权写入目标事实源，并触发写入前后检查 |
| 缺口报告 | 报告初始化缺口、合规缺口、结构缺口和校验失败 |

## 五、禁止职责

Tools 辅助层不得承担：

1. 保存第二套事实；
2. 将缓存、数据库或运行时索引作为权威状态；
3. 自动修改业务事实、任务状态、规范规则或规范；
4. 绕过对象状态机进行状态流转；
5. 绕过 Human Gate 自动写入；
6. 直接调用 AI、Skill 或 Agent；
7. 将索引类信息持久化为独立事实源；
8. 将 Tools 输出作为任务状态、证据、决策、规范规则或审计的唯一来源。

## 六、解析与校验原则

### 6.1 解析原则

1. Tools 解析的输入必须来自 Git 文件事实源。
2. Tools 不得将缓存、数据库、UI 状态或对话内容作为解析输入的权威来源。
3. 解析逻辑依赖对应事实源格式契约、对象规范和行动模型，Tools 不得自行扩张格式契约。
4. 解析失败时，应报告失败位置、期望格式和实际内容，不得静默跳过。
5. 解析失败不得导致 Tools 修改或覆盖原始事实源文件。

### 6.2 校验原则

1. 校验范围由事实源规范、生产对象规范、行动模型和对应工具场景共同决定。
2. 写入前必须校验目标事实源归属、格式契约、对象字段、状态流转、引用关系和 Human Gate。
3. 校验结果应结构化输出，包含校验对象、校验依据、校验结果、不合规详情和建议修复方式。
4. 校验失败不得自动修改事实源。
5. 写入前校验失败应阻止写入。

## 七、聚合与上下文包原则

1. 聚合输入必须来自 Git 文件事实源，不得混入缓存、数据库或 UI 状态中的权威数据。
2. 聚合输出属于派生数据，不是事实源。
3. 聚合输出必须包含来源引用，使每个数据项可以追溯到 Git 文件事实源。
4. 上下文包必须从 Git 文件事实源实时生成或按需生成。
5. 上下文包中出现的新信息，如果需要长期保留，应重新判断对象类型和事实源载体。
6. 索引类信息按需计算并直接返回，不应持久化为独立索引文件。

## 八、受控写入原则

### 8.1 写入目标

1. Tools 的任何写入操作，实际写入目标必须是项目的 Git 文件事实源。
2. 写入不得只停留在 Tools 内部存储、数据库或 UI 状态。
3. Tools 不得维护自己的权威数据存储。

### 8.2 写入前检查

写入前必须检查：

1. 目标事实源归属正确；
2. 写入内容符合对象格式规范；
3. 状态流转合法；
4. 是否触发 Human Gate；
5. 是否已有权威事实，避免覆盖；
6. 写入是否需要追加 Change 记录。

### 8.3 写入后验证

1. 写入后必须可通过 Git 追溯。
2. 写入后应重新读取或刷新相关派生数据。
3. 写入后如产生稳定变更，应记录到 `ldvh-base/changes/`（工作区级目录）或对应管辖项目变更记录位置。

## 九、Tools 辅助层与 Web 展示层关系

1. Tools 辅助层可以为 Web 展示层生成派生视图数据。
2. 派生视图数据必须从 Git 文件事实源聚合生成，可追溯到事实源。
3. Web 展示层不得将 Tools 辅助层提供的派生视图数据作为权威事实源。
4. Web 展示层写入时，可调用 Tools 辅助层的受控写入能力，但不得绕过写入校验和 Human Gate。
5. Tools 辅助层不得承担页面布局、交互体验或人工确认工作台职责。

## 十、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. Tools 写入或覆盖 Git 文件事实源；
2. Tools 改变事实源归属；
3. Tools 将派生数据提升为稳定事实；
4. Tools 绕过规范规则、对象状态机、行动模型或 Human Gate；
5. Tools 引入持久化数据库作为派生层并影响事实源链路；
6. Tools 自动修改任务状态、关闭任务、修改规范规则或修改规范。

Tools 辅助层检查至少包括：

| 检查项 | 标准 |
|---|---|
| 来源可追溯 | Tools 输入和输出可追溯到 Git 文件事实源 |
| 写入可追溯 | Tools 写入落到 Git 文件并可通过 Git 追溯 |
| 缓存非权威 | 缓存、数据库和索引可重建且非唯一事实源 |
| 项目归属 | Tools 写入目标属于正确项目 |
| Gate 判断 | 高影响写入已评估 Human Gate |
| 校验覆盖 | 写入前校验已执行且通过 |
| AI 边界 | Tools 未直接调用 AI、Skill 或 Agent |
