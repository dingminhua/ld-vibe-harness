# 管辖项目文档规范

> 创建日期：2026-06-08
> 定位：定义安装 LDVH 的管辖项目 `docs/` 文档工作区、项目入口文档、项目正文文档、docs/evals、docs/refs、文档吸收和文档与工作对象关系
> 适用范围：所有接入 LDVH 的管辖项目；LDVH 自身作为管辖项目时的根 README 文档和项目资料文档
> 上位依据：`docs/specs/03-文档基础规范.md`
> 相关规范：`docs/specs/00-LD-Vibe-Harness理念与纲要.md`、`docs/specs/02-术语规范.md`、`docs/specs/04.02-环境适配与运行投影规范.md`、`docs/specs/07-Code实现规范.md`

## 1. 本文定位

本文是管辖项目 `docs/` 文档工作区的应用剖面规范。`docs/` 继承 `docs/specs/03-文档基础规范.md` 的文档工作区三分契约、命名、结构、引用和吸收规则；本文只规定 `<W>=docs` 时的特有规则。

安装 LDVH 的用户项目不默认创建 `specs/` 或 `docs/specs/`。用户项目的生产资料、内部分析和外部引用进入 `docs/` 文档工作区；LDVH 规范由 LDVH 自身 `docs/specs/` 提供，通过规范落地要求和环境适配映射转化为用户项目可消费的运行投影。

---

## 2. docs 文档工作区

### 2.1 三分映射

管辖项目文档工作区的三分映射如下：

```text
docs/        项目正文文档
docs/evals/  项目内部分析、方案评估和复盘
docs/refs/   项目外部调研、第三方资料和引用副本
```

`docs/` 是管辖项目文档事实源，不是 LDVH 规范事实源。项目文档可以承载项目资料、设计说明、需求文档、报告和操作说明，但不得替代工作对象状态、验收、关闭证据或结构化关系。

### 2.2 项目正文区

`docs/` 正文区承载已经被项目采纳、可以作为管辖项目资料事实源的稳定文档。

项目正文区可以包含：

1. 需求文档、PRD、用户故事和产品说明；
2. 技术设计、架构说明、接口说明和实现说明；
3. 操作说明、部署说明、运行手册和维护说明；
4. 审计报告、验收报告、复盘报告和其他项目报告；
5. 被项目采纳的路线、方案、背景说明和资料汇总。

项目正文区文档可以被 Intent、Task、ADR、Memo、Change、Pitfall 等工作对象引用，但不得替代这些对象的权威字段和状态机。

### 2.3 docs/evals

`docs/evals/` 继承 `docs/specs/03-文档基础规范.md` §3.4 和 §3.6 的 evals 与吸收规则。本文只规定 `<W>=docs` 时的特例。

docs/evals 文档特例：

1. `docs/evals/` 承载管辖项目内部分析、方案评估、设计比较、复盘和临时判断；
2. docs/evals 可以引用 docs 正文区作为分析依据；
3. docs/evals 结论必须按本文 §5 吸收后，才可成为项目稳定事实；
4. docs/evals 不得替代 Task 验收、ADR 决策、Intent 目标或 Memo 暂存信息。

### 2.4 docs/refs

`docs/refs/` 继承 `docs/specs/03-文档基础规范.md` §3.5 和 §3.6 的 refs 与吸收规则。本文只规定 `<W>=docs` 时的特例。

docs/refs 文档特例：

1. `docs/refs/` 承载管辖项目外部调研、第三方资料、竞品材料、官方文档摘录或其他外部引用副本；
2. 外部资料中的结论必须按本文 §5.2 吸收后，才可成为项目稳定事实；
3. docs/refs 不得替代 LDVH 自身规范工作区 refs 中的外部资料引用。

## 3. 项目入口文档

项目入口文档是项目根目录下服务人类和 AI 快速理解项目的入口，例如根 README 文档。项目入口文档属于管辖项目文档治理范围，即使它不在 `docs/` 目录内。

项目入口文档可以承载：

1. 项目名称、定位、目标用户和一句话说明；
2. 安装、运行、测试和部署入口；
3. 主要目录说明和贡献方式；
4. 当前项目状态和版本状态；
5. 指向 docs 正文区的导航链接。

项目入口文档不得承载：

1. LDVH 稳定规范规则；
2. 工作对象状态机、字段契约或验收事实；
3. 需要长期治理但未进入 docs 正文区或工作对象的关键结论；
4. 与 docs 正文区、工作对象事实源或 LDVH 规范冲突的事实。

LDVH 自身项目的根 README 文档按本文治理；LDVH v2 正式规范由 `docs/specs/` 承载。

## 4. 项目正文文档类型

### 4.1 需求文档

需求文档承载产品需求、用户问题、目标范围、成功标准和约束。需求文档可以作为 Intent 或 Task 的背景资料，但不替代 Intent 的目标状态或 Task 的验收标准。

当需求文档中的内容需要执行时，应创建或更新 Task；当需求文档中的目标需要跨任务追踪时，应创建或更新 Intent。

### 4.2 技术设计文档

技术设计文档承载架构、接口、模块、数据结构、技术方案和实现说明。技术设计文档可以作为 Task deliverable，也可以作为 ADR 的背景材料。

当技术设计形成长期决策时，应创建 ADR；当技术设计只是某次任务的交付物时，应由 Task 引用该文档路径。

### 4.3 操作和维护文档

操作和维护文档承载安装、运行、部署、维护、故障排查和团队操作约定。若其中内容变成 LDVH 框架级长期规则，应评估是否需要向 LDVH `docs/specs/` 提出规范改进；若只是管辖项目长期约束，应先进入项目正文区、ADR 或对应工作对象。需要长期约束 AI 执行时，再由项目运行投影保留入口摘要和权威来源，不得在用户项目中创建 `specs/` 或 `docs/specs/` 承载。

### 4.4 报告文档

报告文档承载审计、验收、测试、复盘、调研总结和项目状态说明。报告文档可以作为 Task 关闭证据的被引用结果物，但 Task 的关闭状态和 closure_evidence 仍由 Task 对象承载。

## 5. 文档吸收链路

### 5.1 docs/evals 吸收

docs/evals 结论应根据性质吸收到不同出口：

| 结论性质 | 吸收出口 |
|---|---|
| 稳定项目资料 | docs 正文区 |
| 长期技术或产品决策 | ADR |
| 可执行工作 | Task |
| 用户目标或成功标准 | Intent |
| 暂存发现、提醒或观察项 | Memo |
| 踩坑经验 | Pitfall |

吸收后，docs/evals 文档保留分析过程和来源；权威结论以吸收出口为准。

### 5.2 docs/refs 吸收

docs/refs 外部资料需要先经过判断和吸收，不能直接作为项目稳定事实。

常见吸收路径：

1. 外部技术资料被采纳为项目设计依据 → 技术设计文档或 ADR；
2. 外部产品资料被采纳为需求背景 → 需求文档或 Intent；
3. 外部测试、审计或实践方法被采纳为执行动作 → Task 或工作流程；
4. 外部资料仅供背景阅读 → 保留在 docs/refs，不升级。

### 5.3 吸收证据

吸收动作应在吸收出口中保留必要来源说明。需要状态、验收或关闭证据时，应由 Task、ADR、Memo、Intent 或 Change 承载，不得只依赖 docs/evals 或 docs/refs 原文。

## 6. 文档与工作对象关系

### 6.1 文档不是工作对象

依据 `docs/specs/03-文档基础规范.md` §7，项目文档不是独立工作对象。项目文档没有默认状态机、负责人、验收字段或关闭证据。

当文档需要被治理时，应由工作对象承接治理：

| 治理需求 | 对应工作对象 |
|---|---|
| 用户目标、范围和成功标准 | Intent |
| 可执行工作、验收和交付 | Task |
| 长期决策 | ADR |
| 暂存输入、发现和提醒 | Memo |
| 实际变更记录 | Change |
| 复用踩坑经验 | Pitfall |

### 6.2 文档引用方式

工作对象引用项目文档时，应优先使用 Git 文件路径。`related_docs` 等字段应表达文档路径或文档引用结构，不应暗示存在独立 Document 工作模型。

当文档路径变化时，应同步检查引用该路径的 Intent、Task、ADR、Memo、Change、Pitfall 和项目正文文档。

### 6.3 文档产物

Task 可以把项目文档作为 deliverable 或被引用结果物。文档产物完成不等于 Task 自动关闭；Task 仍必须满足 acceptance、verification 和 closure_evidence 要求。

---

## 7. 文档结构特例

项目正文文档继承 `docs/specs/03-文档基础规范.md` 的章节编号、段落、表格、代码块和引用规则。

项目入口文档可根据面向人类阅读和开源展示需要使用更自然的 README 结构，不强制套用完整头部元信息，但不得与项目正文事实源或工作对象事实源冲突。

docs/evals 和 docs/refs 应声明定位、执行效力或来源，避免被误读为项目正文事实源。

---

## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | 管辖项目文档入口摘要 | 管辖项目文档入口摘要、README 边界检查、`docs/specs/04.02-环境适配与运行投影规范.md` | AI 执行入口提示 | 本文的 docs 三分映射、README 边界、文档吸收链路或文档与工作对象关系变化时 |

docs 文档结构和引用校验尚未启用，不在本文规范落地要求中声明。需要检查 docs 文档工作区而现有 Code 实现不能适配时，必须按 `docs/specs/03-文档基础规范.md` §9.1 先形成文档检查 Code 缺口，并按 `docs/specs/07-Code实现规范.md` 完成 Code 需求准入、最小实现和测试验证；启用后再补充对应确定性执行要求。具体环境实体由 `docs/specs/04.02-环境适配与运行投影规范.md` 承接。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变 `docs/`、`docs/evals/` 或 `docs/refs/` 的事实源性质；
2. 将 docs/evals 或 docs/refs 结论直接作为项目正文事实源使用；
3. 让项目文档替代 Intent、Task、ADR、Memo、Change 或 Pitfall 的权威字段；
4. 改变根 README 的项目入口定位；
5. 将用户项目资料写入 `specs/` 或 `docs/specs/`；
6. 将 LDVH 规范正文写入用户项目 `docs/`；
7. 新增、替换或扩大 docs 文档检查 Code 实现的判定范围。

管辖项目文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 工作区归属 | 用户项目文档进入 docs，而不是 specs |
| 三分边界 | 正文、evals、refs 分区清晰 |
| README 边界 | README 是入口文档，不替代正文文档或工作对象 |
| 吸收关系 | docs/evals、docs/refs 结论已吸收到权威位置后才生效 |
| 对象关联 | 文档通过路径或文档引用结构关联工作对象 |
| 状态边界 | 文档未替代 Task 状态、ADR 决策或 Intent 目标 |
| Code 适配 | docs 检查 Code 实现适配 `<W>=docs`；缺失时已按 `docs/specs/03-文档基础规范.md` §9.1 和 `docs/specs/07-Code实现规范.md` 处理 |

## 10. 待补齐事项

1. 管辖项目 `docs/` 初始化模板待后续产品初始化流程稳定后补齐；
2. `related_docs` 字段应统一为路径引用或结构化文档引用，待工作模型字段契约同步调整；
3. docs/evals 和 docs/refs 的机械化校验规则待文档工作区 Code 实现按 `docs/specs/03-文档基础规范.md` §9.1 和 `docs/specs/07-Code实现规范.md` 扩展并验证后补齐，并在启用后补充确定性执行要求；
4. LDVH 当前 `docs/` 中历史设计文档的迁移或吸收路径待后续审计处理。
