## 3. 工作流程的定义与定位

### 3.1 工作流程的定义

LDVH 工作流程是 LDVH 对 AI 在项目中如何行动的执行控制建模，通过定义 Context（AI 行动前应获得的最小可行动上下文）、Scenario（AI 如何识别当前任务场景）、Gate（AI 何时必须暂停并请求人确认）、Rules 适用、Skill 进入、Agent 调度、事实源回写和证据留存等内容，约束 AI 的执行行为，确保 AI 稳定、可控地工作。

### 3.2 工作流程的核心特征

工作流程必须具备以下核心特征：

1. **以 AI 为中心**：工作流程以 AI 执行者为第一服务对象，信息组织方式、事实源读取、场景识别、工具选择等首先满足 AI 的需求；
2. **基于事实源**：工作流程依赖 Git 文件事实源，不依赖聊天记忆、工具缓存或数据库派生视图；
3. **场景可识别**：行动必须有明确 Scenario 识别条件，使 AI 能判断何时进入该行动；
4. **Context 最小可行动**：行动必须定义执行前需要读取的最小上下文，避免过载或缺失关键依据；
5. **Human Gate 优先**：关键行动必须触发 Human Gate，等待人类确认后方可继续；
6. **证据留存**：AI 执行的关键步骤必须留下可追溯的证据；
7. **事实回写**：AI 完成执行后必须按事实源边界把稳定事实写回项目；
8. **机制可适配**：行动可以说明 Rules、Skill、Agent、Code 和 Web 如何参与，但不得替代 04、05、07、08 中对应开发环境、工作模型、Code 和 Web 规则。

### 3.3 工作流程与自由执行的区别

| 维度 | 自由执行 | 工作流程约束下的执行 |
|---|---|---|
| 上下文来源 | 聊天记忆、临时信息 | Git 文件事实源、结构化 Context |
| 场景识别 | 凭感觉、无明确规则 | 按 Scenario 规则明确识别 |
| 约束机制 | 无明确约束 | 规则、Gate、状态机多重约束 |
| Skill / Agent | 随意调用或混用 | 按工作流程和 04 环境能力边界选择 |
| 人类确认 | 随意、无明确触发点 | Human Gate 明确触发条件 |
| 证据留存 | 无强制要求、仅聊天记录 | 必须按规范留存可追溯证据 |
| 事实回写 | 随意、可能不回写 | 必须按事实源边界回写 |
| 可追溯性 | 弱、仅聊天记录 | 强、Git 文件事实源 + 结构化证据 |

## 4. 工作流程

### 4.1 工作流程定义

工作流程是 LDVH 对某一类 AI 行动控制事实的标准化建模结构，用于统一描述该行动的行动定位、适用场景、准入条件、事实源边界、Context 要求、Scenario 识别、执行流程、Gate 触发条件、Skill 和 Agent 调度、工具协作、事实源回写与证据留存、环境适配边界、行动特有可测试性锚点、规范落地要求、检查要求和待补齐事项。

40-59 中成员自描述标记为 active、存在主文档且通过骨架和锚点检查的具体行动规范，才是当前已落地的具体工作流程定义文档；planned、candidate、reserved、removed 或其他非 active 条目只表示规划、候选、保留、取消或历史状态。

### 4.2 工作流程的标准组成

一个工作流程应包含以下内容：

1. 行动定位与适用场景；
2. 准入条件；
3. 事实源边界；
4. Context 要求；
5. Scenario 识别；
6. 执行流程；
7. Gate 触发条件；
8. Skill 和 Agent 调度；
9. Code 与命令入口协作适配；
10. 事实源回写与证据留存；
11. 环境适配边界；
12. 行动特有可测试性锚点；
13. 规范落地要求；
14. 检查要求；
15. 待补齐事项。

### 4.3 工作流程与行动执行

工作流程定义行动类别的规则，行动执行是项目或会话中按模型完成的具体过程。

工作流程承载于 `specs/40-59`。行动执行过程中产生的稳定事实不得停留在聊天、Skill 输出、Agent 输出或工具缓存中，必须依据 `specs/09-事实源边界与承载规范.md` 和对应工作模型规范写回 `ldvh-base/`、`docs/`、`specs/`、Git commit 记录或其他权威位置。

### 4.4 工作流程与工作模型

工作流程控制 AI 如何行动，工作模型承载工程生产事实。两者关系如下：

| 维度 | 工作流程 | 工作模型 |
|---|---|---|
| 核心问题 | AI 如何读取、判断、执行、停下和回写 | 项目事实如何结构化、流转和沉淀 |
| 规范区段 | `specs/40-59` | `specs/20-39` |
| 实例事实 | 行动执行结果按事实类型回写 | 事实实例默认承载于 `ldvh-base/`，具体模型可声明例外 |
| 关键约束 | Context、Scenario、Gate、回写、证据 | 准入、字段、状态机、验收和工作模型关系 |

工作流程可以创建、更新、检查或引用工作模型，但不得重新定义工作模型字段、状态机、验收标准或事实实例事实源边界。

### 4.5 工作流程与工具实现

工具可以依据工作流程开发上下文包生成、Scenario 辅助识别、Gate 提示、证据聚合、回写校验和受控写入能力。工具实现不得替代工作流程本身，也不得绕过工作流程定义的事实源边界和 Human Gate。

### 4.6 工作流程文件命名与环境适配边界

40-59 中成员自描述登记为 active、存在主文档且通过检查的主文件为具体行动规范，文件名不重复"工作流程规范"字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

工作流程主文档必须完整定义工作流程。planned、candidate、reserved、removed 或其他非 active 条目不得被当作已落地主文档执行。具体行动规范应在主文档中定义 Context、Scenario、Gate、执行流程、事实源回写与证据留存、Skill 和 Agent 调度、工具协作、环境适配边界和行动特有可测试性锚点。

工作流程可以声明 Rules、Skill、Agent、Code、Web 或结构化契约的环境适配边界。新增或稳定后的能力实践应按归属进入 04、07、08、运行 Rules、Skill 实体、Agent 定义摘要、Code 实现、Web 实现，或在工作流程主规范中保留摘要和引用。

工作流程核心规则不得拆到分散能力文件中。行动自身的 Context、Scenario、Gate、执行流程、回写要求和证据要求应留在 `NN` 主文件。

### 4.7 LDVH 级初始化、审计与行动特有可测试性锚点

工作流程规范不定义逐流程落地前决策、价值与要素审查、落地初始化、落地审计或泛化合规检查。工作流程是否新增、升级、停用或重排编号，由本文的准入条件、Human Gate 要求、`specs/03.03-工作流程文档规范.md` 的成员自描述契约和 Code 派生集合索引校验共同约束。

LDVH 初始化是 LDVH 级初始化。若后续创建并激活初始化工作流程，该流程应统一建立或确认项目被 LDVH 管辖所需的基础上下文、目录、Rules / Instructions 入口、生产对象实例承载能力、Code 实现入口、命令入口和 Web 信息同步入口。具体工作流程主规范只定义自身行动规则和行动特有可测试性锚点，不重复 LDVH 级初始化流程。

LDVH 审计是 LDVH 级审计。若后续创建并激活审计工作流程，该流程应检查 LDVH 落地检查过程是否满足当前检查标准、事实源、环境入口和适配措施是否持续一致、工作模型和工作流程是否与成员自描述及 Code 派生集合索引诊断一致、能力材料是否按归属接管。具体工作流程主规范只定义行动特有可测试性锚点，不重复 LDVH 级审计流程。

合规检查不作为工作流程主规范的独立泛化章节。工作流程相关检查拆分为：行动规范写作检查、行动执行检查、环境适配检查和 LDVH 落地检查过程。本文维护行动规范写作检查和行动执行检查通用原则；具体工作流程主规范只维护行动特有可测试性锚点。

### 4.8 完整方案形成流程

工作流程完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义工作流程；
2. 定义 Context、Scenario、Gate、执行流程、Skill 和 Agent 调度、工具协作、回写要求和证据要求；
3. 定义环境适配边界和行动特有可测试性锚点；
4. 判断 Rules、Skill、Agent、Code、Web 或结构化契约实践是否需要进入对应能力资产、运行实体或 Code/Web 实现；
5. 确认环境适配边界与实际文件、环境入口或实现目录一致；
6. 涉及 Skill、Code、Web 或结构化契约的，完成联动检查；
7. 修改规范、能力资产、实现入口、协作能力或事实源时，应按 `specs/10-Git提交规范.md` 记录可追溯提交。

### 4.9 落地要求接管责任

工作流程可以接管正式规范中的落地要求，但接管必须显式、可追溯、可验证。某项落地要求被 active 工作流程接管后，该要求的落地责任从来源规范转移到接管它的工作流程；来源规范继续作为规则来源和要求来源存在，但不再维护该要求的执行步骤、检查清单、证据闭环或关闭判断。

接管关系至少应满足以下条件：

1. 来源规范的落地要求表或正文能定位到接管它的 active 工作流程；
2. 接管工作流程在自身主文件中说明接管范围、输入来源、执行边界、验证方式、证据位置、Human Gate 条件和失败降级方式；
3. 接管工作流程可以调度 Skill、Agent、Hook、Code、Web 或 CI 等能力，但不得把这些能力输出直接当作最终事实源；
4. 接管流程降级、移除、重命名、编号变化或失去 active 状态时，必须触发来源规范和相关能力资产的同步检查；
5. 无 active 工作流程可定位时，不得声称该落地要求已由工作流程接管，应记录为待接管缺口、人工降级检查或后续 WorkCase/Spark 线索。

工作流程接管的是落地责任，不是来源规范的规则权威。若接管工作流程与来源规范发生冲突，应按来源规范、本文通用规则、Human Gate 和事实源边界重新校正接管范围。

## 5. 工作流程准入与分类原则

### 5.1 行动分类原则

LDVH 工作流程可按治理用途分为以下几类：

1. **初始化行动**：建立项目可被 LDVH 管辖的基础上下文、目录、规范要求和对象实例承载能力；
2. **需求规划行动**：将人的输入、目标和资料转化为可追踪、可执行、可验证的事实源；
3. **任务执行行动**：推动最小执行对象流转，记录证据、阻塞、风险、变更和关闭条件；
4. **Review 行动**：检查执行结果、证据、关闭条件和 Human Gate；
5. **审计行动**：检查工作对象状态、集合状态、检查过程结论、事实源、规范要求、对象、环境能力和工作流程是否持续合规；
6. **协作增强行动**：通过 Skill、Agent、命令入口、MCP、Code 实现或多角色分析增强 AI 的判断质量，但不替代事实源和 Human Gate；
7. **管理行动**：管理工作模型、规范要求、协作能力和事实源边界的受控变更。

### 5.2 行动清单归属

具体工作流程清单、编号归属、维护状态和区段关系由 40-59 成员主文件自描述承载，并由 Code 生成派生集合索引、状态清单和冲突诊断。本文只定义工作流程的通用分类和准入原则。

### 5.3 预留编号区段

编号区段 40-59 用于具体工作流程规范。具体占用、状态和关系应由成员主文件自描述和 Code 派生集合索引诊断确认，不得未经 Human Gate 确认提前占用或重排。

### 5.4 准入条件原则

一个流程需要满足以下条件之一，才应成为工作流程：

1. **需要稳定控制 AI 行动**：该流程需要约束 AI 读取、判断、执行、停止和回写方式；
2. **需要明确 Scenario 识别**：该流程存在可识别的任务场景，且错误进入或漏进入会影响执行质量；
3. **需要明确 Context 要求**：该流程依赖一组稳定的最小可行动上下文；
4. **需要 Gate 控制**：该流程包含必须等待人确认或条件满足后才能继续的节点；
5. **需要跨能力协作**：该流程需要协调 Rules、Skill、Agent、环境能力、Code 实现和工作模型；
6. **需要事实源回写和证据留存**：该流程产出稳定事实、证据、决策、任务、变更或审计结果；
7. **不成为工作流程就会导致 AI 行动边界漂移**：该流程如果不结构化，就会导致 AI 凭聊天记忆执行、绕过 Human Gate 或无法追溯。

不满足以上条件的内容，应按其性质分流：
- 一次性局部执行策略 → 留在当前执行上下文；
- 可复用但可在主上下文完成的轻量流程 → 评估是否作为 Skill；
- 只需独立上下文或专业审查 → 评估是否调用 Agent；
- 长期硬约束 → 写入 specs/，必要时由当前项目的适配措施入口保留薄引用摘要；
- 稳定生产事实 → 按 20-39 工作模型规范写入对应事实源；默认写入 `ldvh-base/`，Study 等具体模型声明的例外按其权威事实源处理；事实源修改追溯按 Git commit records 处理；
- 外部参考资料 → 按项目归属和授权进入对应 `docs/sources/`，不得直接作为 specs 或项目稳定结论。

## 6. 工作流程的通用规范

### 6.1 Context（上下文）原则

Context 是由事实源组织出的 AI 执行输入、任务背景和行动依据。

Context 的目标是给 AI 提供足够但不过载的最小可行动上下文，让 AI 能够：

1. 理解当前项目的身份和边界；
2. 理解当前任务的背景和目标；
3. 知道可用的 Rules / Instructions 入口、Skill、Agent、Code 工具或命令入口；
4. 知道事实源的边界和回写位置；
5. 知道何时触发 Human Gate。

Context 的组织遵循以下原则：

1. **最小化原则**：只包含 AI 执行当前行动所需的最小信息；
2. **结构化原则**：以结构化方式组织，便于 AI 理解和处理；
3. **事实源原则**：所有稳定信息都来自 Git 文件事实源；
4. **动态原则**：根据当前 Scenario 动态调整 Context 内容；
5. **可追溯原则**：Context 应能回溯到原始事实源文件；
6. **读取精准原则**：上下文消耗应与任务复杂度匹配，而非与文档体积成正比；
7. **派生输入边界**：索引、Context Pack、Code 聚合报告、Web 视图或适配措施可以帮助 AI 定位和压缩上下文，但必须能回指原始 Git 文件事实源，不得替代原文、对象实例或正式规范。

少读不是不读。AI 应优先通过入口、索引、搜索、Code 聚合或报告定位需要读取的事实源，再按任务风险和 Scenario 决定读取深度；不得因为上下文压缩、派生摘要或工具输出看似完整，就跳过必须读取的权威段落。

#### 6.1.1 读取策略

读取精准原则的操作化方法：

1. **定位优先**：AI 读取事实源前，应先使用搜索工具（Grep、SearchCodebase）定位目标段落，再按行范围读取，避免全文读取大文件；
2. **渐进升级**：读取策略按成本从低到高升级——搜索定位 → 按行范围读取 → 按需扩展行范围 → 全文读取；仅在搜索无法定位或需理解完整上下文时才升级到下一级；
3. **行范围约束**：对超过 200 行的规范文档，AI 不应在未定位的情况下直接全文读取；应先搜索关键词，再读取目标段落前后必要上下文；
4. **章节锚点**：LDVH 规范文档使用 `§` 编号体系，AI 可利用章节编号作为精准读取入口，先搜索章节标题再读取对应段落；
5. **上下文预算意识**：AI 应感知当前上下文消耗，优先选择低成本读取策略；当上下文接近上限时，应更严格地使用定位优先策略。

**标准化读取工作流程**

AI 读取规范文档时，应按以下工作流程执行：

1. **Grep 章节标题**：使用 `Grep` 搜索 `^## |^### ` 获取文档章节标题和行号，同时完成章节发现和行号定位；
2. **机器索引辅助**：如存在由 `code/specs_validate.py index` 生成、符合 `specs/03.01-规范文档规范.md` 的有效 specs 文档派生索引，可用其辅助定位 specs 根目录 Markdown 文档和章节；索引只作导航辅助，不替代原文读取；
3. **精准读取**：确定目标章节后，使用 `Read` 的 offset/limit 参数精准读取目标段落，避免读取无关章节；
4. **按需扩展**：仅在目标段落引用了上下文内容时，扩展读取范围；
5. **全文升级**：仅在搜索无法定位、需理解完整上下文或文档不足 200 行时，才全文读取。

Grep 是主路径（发现+定位），机器索引是补充路径（定位和诊断）。二者配合使用，不得跳过 Grep 直接 Read 全文。`docs/studies/` 和 `docs/sources/` 不进入 specs 正式规范派生索引的默认读取范围，只有用户明确指定时才读取。

### 6.2 Scenario（场景）原则

Scenario 是 AI 当前所处的任务类型、协作模式和执行入口。

Scenario 的目标是让 AI 能够：

1. 识别当前任务属于什么行动类型；
2. 选择合适的执行入口；
3. 加载对应的规则和 Context；
4. 判断是否进入 Skill、调用 Agent 或使用工具；
5. 判断是否应触发 Human Gate。

Scenario 的识别遵循以下原则：

1. **基于事实源**：根据 Git 文件事实源和用户当前输入识别当前场景；
2. **明确规则**：每个具体行动规范都应定义识别规则；
3. **优先级**：多个场景同时匹配时，按具体行动规范或 Code 派生集合索引中的关系诊断选择；
4. **Human Gate**：高影响场景切换可能触发 Human Gate；
5. **可降级**：条件不足时应降级为主上下文分析或询问用户，而不是强行进入行动。

### 6.3 Gate（门禁）原则

Gate 是需要人确认或满足条件后才允许继续的控制点。

Gate 分为以下类型：

1. **Human Gate**：必须由人类确认后方可继续；
2. **条件 Gate**：满足特定条件后方可继续；
3. **审批 Gate**：必须由特定角色审批后方可继续。

Gate 的执行遵循以下原则：

1. **先停再问**：识别到 Gate 时，AI 必须先暂停执行，再请求人类确认；
2. **明确说明**：AI 必须明确说明触发 Gate 的原因、影响范围和建议确认事项；
3. **不可绕过**：AI 不得绕过 Gate 继续执行；
4. **证据留存**：Gate 的确认过程必须留下可追溯的证据；
5. **回写联动**：Gate 结果形成稳定事实时，应按事实源边界回写。

#### 6.3.1 Human Gate 轻量人类决策记录

Human Gate 是人类对关键行动作出的轻量决策记录，不是独立工作模型，也不要求默认关联 WorkCase。只有当决策本身需要形成后续执行对象、缺口分流或关闭证据时，才按对应工作模型关联 WorkCase、ADR、Spark 或其他工作对象；事实源修改追溯由 Git 提交记录承接。

Human Gate 记录应服务于可追溯的人类判断：只记录“已确认”“用户同意”或其他结论性表述不足以支撑事实源写入、状态流转、长期降级、验证豁免、关键关闭或后续执行授权。

Human Gate 最小字段为：

1. **时间**：人类作出决策或确认记录形成的时间；环境无法提供稳定身份时，时间可以与“当前 Human 确认”一起记录；
2. **决策**：Human 的选择、授权、取消、暂缓或修改反馈；
3. **范围**：决策影响的事实源、规范、工作对象、Code、Web、运行入口、环境能力或后续流程；
4. **约束**：决策成立所依赖的依据、限制、风险、验证要求、后续分流或回写要求。

Human Gate 可以由 Markdown 文本块、YAML 结构、工作对象字段、报告段落、Web / Human 入口导出的结构化记录或其他 Git 文件事实源承载。单个文件或段落可以承载多条 Human Gate 记录；多条记录应能被逐条识别，不得混成无法区分的汇总结论。

推荐的 Markdown 轻量文本块如下：

```text
Human Gate 记录：
- 时间：
- 决策：
- 范围：
- 约束：
```

推荐的 YAML 轻量结构如下：

```yaml
human_gate:
  - time:
    decision:
    scope:
    constraints:
```

具体工作模型、工作流程、Web 或环境适配项可以在上述结构上增加字段，但不得省略时间、决策、范围、约束四类最小可追溯信息。历史记录中的触发原因、确认事项、影响范围、确认依据、Human 决策、确认人/时间、后续动作、验证方式、回写位置和残留风险可以继续作为扩展字段或别名被消费，但不再作为统一最小必填字段。

Human Gate 的具体承接方式由环境适配项决定，可以通过对话确认、Web / Human 入口、Hook 阻断、提问工具或人工降级检查实现。

### 6.4 Rules 适用原则

Rules / Instructions 资产或入口摘要承载 AI 可见的行为边界提示。

Rules / Instructions 资产或入口摘要的加载遵循以下原则：

1. **优先级**：项目级 Rules 摘要优先于 LDVH 基础入口摘要；
2. **不冲突**：Rules 资产或入口摘要之间不得冲突，冲突时按优先级处理，并评估是否需要修正对应资产或入口摘要；
3. **可追溯**：Rules 资产或入口摘要必须有明确的来源和版本；
4. **能力回指**：Rules 资产设计和治理以 `specs/04.02-LDVH能力资产与落地保障规范.md` 为准；
5. **Human Gate**：Rules 资产或入口摘要变更必须触发 Human Gate。

### 6.5 Skill 进入原则

Skill 是 AI 可使用的可复用流程。工作流程可以在具体场景中说明何时建议进入 Skill，但 Skill 的准入、命名、部署、输出和事实源回写边界由 `specs/04.02-LDVH能力资产与落地保障规范.md` 定义，本文不重复维护通用规则。

Skill 进入在工作流程中的适配说明如下：

1. **场景匹配**：根据当前 Scenario 判断是否需要可复用流程，判断标准以 `specs/04.02-LDVH能力资产与落地保障规范.md` 和本文的 Scenario、准入原则为准；
2. **能力回指**：Skill 准入、边界和证据留存必须回指 `specs/04.02-LDVH能力资产与落地保障规范.md` 及本文 §6.8 事实源回写原则；

### 6.6 Agent 调度原则

按 02 术语，Agent 用于独立上下文、专项视角、并行审查或权限边界差异。本文只规定工作流程中的 Agent 调度原则；Agent 的创建、调用、资产摘要、生命周期、权限边界和事实源回写边界由 `specs/04.02-LDVH能力资产与落地保障规范.md` 定义。

Agent 调度在工作流程中的通用原则：

1. **场景匹配**：根据当前 Scenario 判断是否需要独立上下文、结论隔离、并行委派或不同权限边界；
2. **能力回指**：Agent 创建或调用治理条件必须回指 `specs/04.02-LDVH能力资产与落地保障规范.md`；
3. **入口约束**：Agent 的执行必须遵守 Rules / Instructions 入口摘要、事实源边界和工作流程；
4. **Human Gate**：关键 Agent 的创建、调度、权限调整或写入动作必须按对应规范评估 Human Gate；
5. **不替代事实源**：Agent 不得成为事实源，只能读取、分析和建议；
6. **能力前提可检查**：具体行动可以声明某类 Agent 能力为增强模式前提；前提不满足时，应降级、暂停或提示用户，而不是假装已具备能力；
7. **主控唯一调度**：需要并行、独立上下文、多角色判断或子 Agent 审计时，由主控调度 Agent；Skill 只能向主控提出调度建议。

### 6.7 Code 与命令入口协作原则

Code 实现、脚本、校验器、命令入口或环境工具可以辅助 AI 读取事实源、获得结构化上下文、执行确定性校验、准备受控写入、展示 Gate 和证据，但不得替代 AI 的场景判断，也不得直接调用或模拟 AI 决策。

Code 与命令入口协作遵循以下原则：

1. Code 辅助和 Web 信息同步的分工以 `specs/07-Code确定性执行实现规范.md`、`specs/08-Web信息同步实现规范.md` 为准；
2. Code、脚本、校验器、命令入口或环境工具输出不是最终事实源；
3. Code、脚本、校验器、命令入口或环境工具写入必须受控，且不得绕过事实源边界、工作模型规范、工作流程或 Human Gate；
4. Code、脚本、校验器、命令入口或环境能力不足时，工作流程不得假定其已完成校验或回写；
5. Code、脚本、校验器、命令入口或环境工具运行中产生的稳定事实必须回写 Git 文件事实源后才成立。

### 6.8 事实源回写原则

事实源回写是 AI 完成执行后把稳定事实写回项目的过程。

AI 完成执行后的事实源回写，依据 `specs/09-事实源边界与承载规范.md` §7定义的回写条件执行，本文不重复维护。工作流程的适配说明如下：

1. **工作流程回写触发**：AI 按 Scenario 执行完毕后，应判断执行结果是否包含稳定事实；若包含，必须按 `specs/09-事实源边界与承载规范.md` §7 回写；
2. **回写与 Gate 联动**：关键事实的回写应评估 Human Gate，依据本文、具体行动规范和相关基础规范判断；
3. **对象回写回指**：工作项、决策、火花、经验、研究报告等对象实例，以及验证证据、风险判断、检查结果等字段内容，必须按对应工作模型规范、字段语义、字段内容格式和字段注册规则回写；事实源修改追溯必须按 `specs/10-Git提交规范.md` 回到 Git 提交记录；
4. **对象回写前置校验**：工作流程声明创建、更新或回写工作对象时，必须先校验目标对象对应工作模型规范中的准入条件、对象关系、父级约束、字段契约、状态机和 Human Gate；不得仅因过程输出形成“任务”“缺口”或“后续行动”等语义，就直接创建 WorkCase 或其他工作对象；不满足目标对象准入或父级约束时，应分流到 Spark、既有父级对象，或暂停请求 Human Gate；
5. **能力输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实；
6. **报告回写分流**：检查报告、分析报告或管辖项目资料应按 02、03 和具体行动规范判断进入 docs/、ldvh-base/、specs/、Git commit 记录或其他权威事实源。

#### 6.8.1 过程输出原则

过程输出是工作流程执行中为当前判断、协作、展示、审查或交还主控而产生的中间结果，包括但不限于聊天答复、Skill 输出、Agent 输出、工具报告、Web 视图、检查摘要、候选草案、风险提示、下一步建议和临时分析结论。

过程输出不是默认事实源。工作流程可以要求过程输出具备结构化、可读性和可追溯性，但不得让过程输出与 Git 文件事实源并行维护同一稳定事实，也不得以过程输出替代工作对象、规范正文、管辖项目配置、Code 实现、Web 实现、Human Gate 记录或验证证据。

过程输出遵循以下通用规则：

1. **边界明示**：输出应说明自身是过程输出、候选建议、检查摘要、临时分析还是已回写事实，避免 Human 或后续 AI 误读为稳定事实；
2. **来源可追溯**：引用事实、判断依据、验证结果或工具报告时，应指向原始 Git 文件事实源、命令、测试、Human Gate 记录或可复查输出；
3. **稳定事实分流**：过程输出中形成可执行工作、决策、经验、风险、缺口、验证结论、规范规则、项目配置或事实源修改追溯时，必须按 03、09、10、20-39 工作模型规范和具体工作流程回写到对应权威位置，并遵守目标对象的准入条件、父级关系、状态流转、对象级 Human Gate 和 Git 提交记录要求；
4. **不并行维护**：同一稳定事实一经回写，过程输出只能作为说明、摘要或索引，不得继续承担权威状态、字段、规则或结论维护职责；
5. **Human Gate 联动**：过程输出要求 Human 授权、接受长期降级、确认关键风险、批准写入或关闭工作项时，应触发或引用 Human Gate 记录；
6. **交还主控**：Skill、Agent、工具或 Web 产生的过程输出必须交还主控或用户，由主控判断是否继续执行、回写事实源、触发 Gate、分流问题或结束流程；
7. **降级说明**：过程输出无法完成验证、无法定位事实源、无法回写或只能给出候选结论时，应说明残留风险、下一步建议和需要 Human 或后续工作流程处理的事项。

具体工作流程可以定义本流程的过程输出格式、字段、展示方式和交还内容，但不得降低本文对边界明示、事实源回写、Human Gate、证据留存和主控交还的要求。

### 6.9 证据留存原则

工作流程的证据留存遵循以下原则：

1. **关键步骤留证**：Context 读取、Scenario 判断、Gate 触发、Skill / Agent 调度、工具校验、事实源回写等关键步骤应留下可追溯证据；
2. **证据归属明确**：证据属于事实实例时，按相关工作对象的证据字段或证据归属规则写入对应事实源；默认写入 `ldvh-base/`，Study 等具体模型声明的例外按其权威事实源处理；属于报告时，按 docs/ 边界写入；属于规范修改时，按 Git 提交记录追溯；
3. **证据可验证**：证据应说明来源、时间、执行者、结果和影响范围；
4. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
5. **关闭前可追溯**：涉及工作项、审计或 Review 的行动，在关闭前应能追溯关键证据；
6. **验证结果外部化**：关键完成判断应优先依据 Code 校验、测试、运行结果、审查证据、事实源差异或 Human 确认，不得只依据 AI 自述；
7. **结果可复现**：证据应能让后续 AI 或 Human 复查验证方式、关键输出、结论和残留风险；无法复现时，应记录为 degraded、open、follow-up 或待 Human Gate 判断。

### 6.10 执行中发现问题的分流规则

AI 在执行 WorkCase 过程中发现问题时，必须按以下分流规则判断问题类型并采取对应行动，不得跳过分流、不得把所有问题统一处理为阻塞或忽略。

| 分流类型 | 判断条件 | 处理方式 |
|---|---|---|
| **blocking** | 问题直接阻塞当前 WorkCase 的成功标准完成 | 回到 WorkCase 内部执行编排记录并处理，修复后重新验证 |
| **follow-up** | 问题不阻塞当前 WorkCase，但需要后续跟进 | 记录为 Spark 或新 WorkCase 候选，当前 WorkCase 不等待 |
| **opportunistic fix** | 问题与当前 WorkCase 相关且修复成本极低（<5 分钟），修复不引入新风险 | 在当前 WorkCase 范围内直接修复，并在关闭证据中记录修复内容 |
| **ADR 候选** | 问题涉及架构决策、技术选型或规范变更 | 记录为 Spark 或 ADR proposed 状态，不阻塞当前 WorkCase |
| **Pitfall 候选** | 问题具有通用教训价值，其他项目或场景可能重复遇到 | 创建 Pitfall 记录，关联当前 WorkCase 或相关证据 |
| **Spark 候选** | 问题有保留价值但尚未达到 Pitfall 或 ADR 级别 | 创建 Spark 记录，关联当前 WorkCase 或相关事实源 |

分流规则遵守以下约束：

1. **blocking 必须处理**：阻塞当前 WorkCase 的问题不得降级为 follow-up 或忽略；
2. **执行项深度限制**：blocking 问题应回到 WorkCase 内部执行编排处理，默认不得继续拆出下一层执行项；具体执行项规则由 `specs/21-WorkCase-工作项.md` 承接；
3. **opportunistic fix 需谨慎**：修复成本不确定时，应升级为 follow-up 而非冒险在当前 WorkCase 中修复；
4. **ADR/Pitfall/Spark 不阻塞**：候选类问题不阻塞当前 WorkCase 完成和关闭；
5. **分流结果可追溯**：每个分流决定应记录在 WorkCase 的关闭证据或关联工作对象中。

#### 6.10.1 反合理化与失败暂停

AI 在执行、验证、审查或关闭工作项时，不得用“应该通过”“看起来没问题”“逻辑上可行”“按理说已完成”等推测性表述替代验证证据。

以下情况应暂停继续宣称完成，并按问题性质进入 blocking、follow-up、Human Gate、Spark、Pitfall、ADR、独立审阅或具体工作流程：

1. 验证命令失败、缺少验证命令、验证结果不可复现或验证范围不足；
2. acceptance、Gate 条件、事实源回写、状态流转或证据留存存在未满足项；
3. 同一问题连续修复后仍失败，或失败原因不能明确归属；
4. 工具输出、Web 状态、Agent 输出或聊天结论与 Git 文件事实源不一致；
5. 需要接受长期降级、关闭 open/degraded 缺口或跳过部分验证。

修复后必须重新执行相关验证，或明确记录无法验证的原因、残留风险和后续分流。不得只说明“已修复”或“已调整”后直接关闭。

### 6.11 主控唯一调度与流程交还原则

工作流程中的主控是唯一的流程编排者。Skill、Agent、Code、MCP、脚本和 Web 不得替代主控进行跨流程调度。

主控唯一调度遵循以下原则：

1. **Skill 单流程**：Skill 只完成一个明确、受控、可复用的流程；
2. **Skill 不链式调度**：Skill 不得自行调用下一个 Skill，不得自行调用子 Agent；
3. **Skill 交还主控**：Skill 流程结束、暂停、失败或需要升级时，必须输出下一步建议并交还主控；
4. **Agent 由主控调度**：需要并行、独立上下文、多角色判断、隔离审计或不同权限边界时，只能由主控或用户显式调度 Agent；
5. **工具不调度 AI**：Code、MCP、脚本和 Web 不得调用或模拟 Skill / Agent 调度；
6. **下一步建议可追溯**：Skill 输出的下一步建议应说明建议动作、建议调度对象、原因、所需输入、预期输出和停止条件；
7. **调度结果回到主控**：Agent 或工具输出必须返回主控或用户，由主控判断是否写回事实源、进入下一个 Skill、触发 Human Gate、退回执行或结束流程。

该原则用于降低 AI 遗漏状态流转、Human Gate、独立审计或事实源回写的概率。具体行动规范可在此基础上定义更细的交还格式，但不得允许 Skill 直接调度子 Agent 或跨流程链式执行。

## 7. 与 40-59 具体工作流程规范的关系

### 7.1 成员自描述与 Code 派生集合索引

本文是工作流程基础规范，只定义工作流程通用规则、标准组成、主控调度、过程输出、事实源回写和检查要求。

工作流程集合不再通过独立手写集合索引文档维护成员清单。40-59 成员主文件通过 03.03 定义的成员自描述字段声明自身编号、标题、状态、路径、可执行性和规则锚点；Code 读取这些字段生成派生集合索引、active 流程清单、关系诊断、状态清单和维护提示。本文不维护具体工作流程清单，也不把 Code 派生输出提升为最终事实源。

成员主文件应引用本文作为工作流程通用规则来源；本文变更影响具体工作流程编号、集合状态或可执行性判定时，应检查 03.03 成员自描述契约、40-59 成员主文件和 Code 派生索引能力是否需要同步。

### 7.2 与 40-59 工作流程区段的关系

40-59 是具体工作流程区段，不表示所有编号都已落地。只有成员自描述为 active、存在主文档且通过骨架和锚点检查的条目，才是当前可按主文档执行的具体工作流程规范。具体工作流程规范应依据本文 §4.2 定义的工作流程标准组成展开，并按 `specs/03.03-工作流程文档规范.md` 编写。

planned、candidate、reserved、removed 或其他非 active 条目不得作为具体工作流程规范执行，也不得作为已生效 Markdown 路径引用。具体工作流程规范不得在缺少说明的情况下省略 §4.2 中的标准组成；如某一组成项暂不适用或待补齐，应在对应章节说明原因或进入待补齐事项。

### 7.3 关系原则

本文与 40-59 的关系遵循以下原则：

1. 本文定义工作流程的通用规则，40-59 作为具体工作流程区段，生效主文档定义具体工作流程，成员自描述和 Code 派生索引提供集合读取与诊断；
2. 40-59 不得与本文的通用规则矛盾；
3. 具体工作流程规范可以在本文的通用规则基础上定义更具体的行动规则；
4. 发生冲突时，以本文的通用规则为准，除非具体工作流程规范明确说明例外情况并经 Human Gate 确认；
5. Rules、Skill、Agent 的环境能力选择和治理边界由 `specs/04.03-环境入口适配与部署规范.md` 定义，不由本文或 Code 派生集合索引重复定义。

### 7.4 成员集合 Human Gate

以下情况应评估 Human Gate：

1. 新增、删除、重命名或重排 40-59 区段编号；
2. 改变某个编号对应的工作流程归属；
3. 将保留编号升级为具体工作流程规范；
4. 改变 03.03 成员自描述的编号边界、状态字段、active 判定或维护规则；
5. 让本文重新承担具体工作流程清单维护职责。

### 7.5 同步说明

1. 新增 40-59 具体工作流程规范后，应同步补齐成员自描述并检查 Code 派生集合索引，不在本文维护清单；
2. 工作流程通用规则变更时，应优先修改本文，再检查成员自描述、Code 派生集合索引能力和具体工作流程规范是否需要同步；
3. 具体工作流程的 Context、Scenario、Gate、证据和回写规则稳定后，应在具体工作流程规范中定义，不在本文或 Code 派生集合索引中维护正文规则；
4. 本文变更应按 `specs/10-Git提交规范.md` 记录可追溯提交。

## 8. 能力材料接管边界

本文是工作流程基础规范，不是 40-59 具体工作流程。能力材料中的有效内容应按内容性质回并到主流程规范、04 系列环境适配规范、07 Code、08 Web 或运行实体，不得继续作为每个流程的完整性要求。

具体工作流程如需 Rules、Skill、Agent、Code、Web 或结构化契约，应在对应主规范中声明环境适配边界，并按归属进入 04、07、08、运行 Rules、Skill 实体、Agent 定义摘要、Code 实现或 Web 实现。

### 8.1 内容接管原则

工作模型和工作流程能力材料接管应遵循“先识别、再合并、后校验”的流程：

1. 先识别参考与研究材料中的有效规则、流程、契约和 Code 能力；
2. 按归属合并到主规范、04、07、08、运行 Rules、Skill 实体、Agent 定义摘要、Code 实现或 Web 实现；
3. 合并后检查引用关系，确认主规范、运行实体或适配措施入口已经能反向发现被接管的内容；
4. 删除、归档或重命名仍可能承载权威字段、状态机、Human Gate、Code 或 Web 结构化契约的材料前必须通过 Human Gate；
5. 不得以“后续再补”为理由直接移除仍承载权威内容的材料。

## 10. Human Gate 与检查要求

### 10.1 Human Gate 触发条件

以下情况应评估 Human Gate：

1. 新增行动；
2. 删除行动；
3. 重命名行动；
4. 重排行动编号区段；
5. 改变工作流程的通用规则；
6. 改变工作流程的标准组成；
7. 改变 Context、Scenario、Gate 的定义；
8. 改变事实源回写的原则；
9. 改变 Human Gate 的触发条件；
10. 新增、删除、重命名或改变工作流程机制实体、实现入口或结构化契约；
11. 改变 Skill、Agent 或工具在工作流程中的调度边界；
12. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 10.2 检查要求

工作流程规范写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 行动定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、工作模型、工作流程、Context、Scenario 和 Gate 术语一致 |
| 流程组成 | 具体行动规范覆盖工作流程的标准组成，缺项已说明原因 |
| 环境适配边界 | 已说明是否需要独立运行实体、实现入口或结构化契约；如创建，已确认按需、非空、不替代主流程且经 Human Gate |
| 行动特有可测试性锚点 | 已定义本行动特有的 Scenario、Context、Gate、回写、证据、Human Gate 和失败降级检查规则 |
| Context | Context 来源明确且符合事实源边界 |
| Scenario | Scenario 识别规则明确，避免凭感觉进入行动 |
| Gate | Gate 触发条件明确，确保关键步骤必须等待人类确认 |
| Skill / Agent | 机制使用符合 04 环境适配边界，不由 Skill 调度 Agent |
| 工具协作 | 工具边界符合 `specs/07-Code确定性执行实现规范.md` 和 `specs/08-Web信息同步实现规范.md`，未让工具替代事实源或 AI 判断 |
| 事实源回写 | 符合 `specs/09-事实源边界与承载规范.md` 的事实源边界原则 |
| 证据留存 | 关键步骤有可追溯证据要求 |
| 反合理化与失败暂停 | 完成判断基于可追溯验证证据，连续失败、证据不足或需要长期降级时已暂停并分流 |
| 文件命名 | 主文件命名符合 §4.6，机制实体、实现入口和结构化契约未重复维护区段性质或行动归属 |
