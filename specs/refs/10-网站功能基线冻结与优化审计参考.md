# 网站功能基线冻结与优化审计参考

> 本文整理 PM Kit 工具网站在功能固定、现状梳理、回归保护和优化规划阶段可采用的方法与工具组合。
> 适用对象：类似 `pm-kit-web/` 的小型前后端网站或本地开发工具。

---

## 一、目标

当一个网站已经具备部分可用功能，但准备进入全面梳理与优化阶段时，优先目标不是立即重构，而是先建立当前实现的基线。

基线需要回答：

1. 当前已经实现了哪些功能；
2. 哪些功能可用、部分可用或不可用；
3. 页面入口、前端逻辑、后端接口和数据文件之间如何对应；
4. 后续优化时如何确认没有破坏既有能力。

这类工作可以概括为：

```text
功能基线冻结 + 现状审计 + 回归保护 + 增量优化规划
```

---

## 二、推荐流程

### 2.1 功能基线冻结

功能基线冻结用于固定当前网站的实际行为，不先评价设计优劣。

建议整理：

| 内容 | 说明 |
|---|---|
| 页面清单 | 当前有哪些可访问页面或视图 |
| 功能清单 | 每个页面可执行哪些操作 |
| 入口清单 | 功能从哪个按钮、菜单或 URL 进入 |
| 接口清单 | 前端操作调用了哪些 API |
| 数据清单 | API 读写哪些文件或对象 |
| 状态标记 | 可用、部分可用、不可用、未暴露 |

### 2.2 建立回归样例

基线冻结后，应建立最小回归保护，避免后续优化导致功能漂移。

可分为三层：

1. 手工验收清单：记录关键路径；
2. API 验证样例：记录关键接口请求和返回；
3. 自动化测试：用脚本回放关键页面操作。

### 2.3 现状审计

从以下维度盘点：

| 层级 | 审计重点 |
|---|---|
| 前端 | 页面结构、交互路径、DOM 操作、加载态、错误提示、空状态 |
| 后端 | 接口边界、业务逻辑、数据读写、异常处理、返回结构 |
| 数据 | 字段一致性、状态流转、schema、文件读写安全 |
| 运行 | 启动脚本、依赖、检查命令、本地验证路径 |
| 工程化 | lint、test、coverage、复杂度、安全检查、报告输出 |

### 2.4 分层优化

不建议把所有优化混在一次大重构中。推荐按四类拆分：

| 类型 | 目标 |
|---|---|
| 功能正确性优化 | 修复 bug、补齐异常处理、保证核心流程稳定 |
| 可维护性优化 | 拆分大文件、统一接口调用、分离渲染与业务逻辑 |
| 体验优化 | 改善布局、提示、加载态、筛选、视觉状态 |
| 工程化优化 | 增加检查命令、测试、审计脚本、报告产物 |

## 三、工具组合

### 3.1 功能冻结工具

| 工具 | 用途 | 说明 |
|---|---|---|
| Playwright | 页面 E2E 与截图回归 | 适合录制现有页面行为，后续自动回放 |
| 浏览器截图 | UI 状态留档 | 可作为优化前后的视觉对照 |
| 手工验收清单 | 关键流程确认 | 成本低，适合早期建立 baseline |

Playwright 是功能冻结阶段最推荐的核心工具。它可以打开网站、点击页面、校验页面状态、保存截图，并在后续优化后自动回放。

典型命令：

```bash
npx playwright codegen http://localhost:端口
npx playwright test
```

### 3.2 接口冻结工具

| 工具 | 用途 | 说明 |
|---|---|---|
| curl | 最小接口验证 | 适合固化少量关键请求 |
| HTTPie | 可读性更好的命令行请求 | 适合本地调试 |
| Bruno | 文件化 API 请求集合 | 适合随代码仓库版本管理 |
| Postman | 可视化接口调试 | 适合团队共享和手工调试 |
| OpenAPI / Swagger | 接口契约展示 | FastAPI 项目通常可以直接暴露 `/docs` 和 `/openapi.json` |

若需要把接口行为固定在项目中，优先考虑 Bruno 或 curl 样例；若后端框架已支持 OpenAPI，应同步保留 OpenAPI 输出。

### 3.3 代码审计工具

Python 服务端可考虑：

```bash
python3 -m py_compile pm-kit-web/server/*.py
ruff check .
black --check .
pytest
pytest --cov
pip-audit
radon cc pm-kit-web/server -a
radon mi pm-kit-web/server
```

前端若是原生 HTML/CSS/JavaScript，可考虑：

```bash
node --check pm-kit-web/client/app.js
npx eslint pm-kit-web/client/app.js
npx prettier --check pm-kit-web/client
npx lighthouse http://localhost:端口
```

代码规模和结构盘点可考虑：

```bash
tree pm-kit-web
cloc pm-kit-web
```

### 3.4 体验与性能工具

| 工具 | 用途 |
|---|---|
| Chrome DevTools | 控制台错误、网络请求、性能检查 |
| Lighthouse | 性能、可访问性、最佳实践、SEO 检查 |
| Playwright screenshots | 截图回归 |

## 四、适用于 PM Kit 工具网站的推荐方案

对于 `pm-kit-web/` 这类轻量工具网站，建议采用三档方案。

### 4.1 方案 A：零侵入审计

不新增项目依赖，仅使用外部命令和手工清单。

包含：

1. 启动网站；
2. 浏览器手工走查页面；
3. 记录功能清单；
4. 使用 curl 验证关键接口；
5. 使用 `tree`、`cloc`、`py_compile`、`node --check` 做基础检查。

适合快速了解现状。

### 4.2 方案 B：轻量 baseline

在方案 A 基础上加入 Playwright 或等价 E2E 工具。

包含：

1. 录制关键页面路径；
2. 保存首页、列表页、详情页等关键截图；
3. 固化关键断言；
4. 后续每次优化后回放。

这是最推荐的起步方案。

### 4.3 方案 C：完整审计体系

在方案 B 基础上补齐 API collection、代码复杂度、覆盖率、Lighthouse、审计报告目录。

可形成如下产物：

```text
reports/
├── baseline/
│   ├── api-snapshot.json
│   ├── ui-home.png
│   ├── ui-task-list.png
│   └── smoke-test-result.json
├── audit/
│   ├── cloc.txt
│   ├── radon.txt
│   ├── ruff.txt
│   └── lighthouse.html
```

适合准备长期维护或持续迭代的阶段。

## 五、建议交付物

一次完整的网站功能冻结与优化审计，建议至少产出：

1. 当前功能清单；
2. 页面与接口映射表；
3. 数据模型与状态流转清单；
4. 手工验收清单；
5. API 请求样例或 API collection；
6. UI 截图基线；
7. 代码规模与复杂度报告；
8. 问题清单；
9. 优化路线图。

## 六、PM Kit 当前注意事项

PM Kit 当前技术栈为：

| 层级 | 技术 | 位置 |
|---|---|---|
| 前端 | 原生 HTML / CSS / JavaScript | `pm-kit-web/client/` |
| 服务端 | Python / FastAPI / Uvicorn | `pm-kit-web/server/` |
| 数据 | YAML / Markdown 文件 | `task-base/`、`docs/`、`product.yaml` |
| 启动脚本 | Shell | `pm-kit-web/start.sh` |

当前项目已定义的基础检查命令见 `docs/04-开发生产实践.md`：

```bash
python3 -m py_compile pm-kit-web/server/*.py
node --check pm-kit-web/client/app.js
```

新增依赖前必须先确认；不得为了审计或优化直接引入重型 GUI 框架。

---

## 七、推荐下一步

若要对 PM Kit 工具网站正式执行一次梳理，建议先选择方案 B：

```text
轻量 baseline = 手工验收清单 + 关键 API 样例 + Playwright 页面回归 + 基础代码检查
```

先固定现状，再进入功能正确性、可维护性、体验和工程化的分批优化。
