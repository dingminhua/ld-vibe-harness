## 1. 本文解决的问题

本文定义 LDVH 规范模型的附件型子文档通用规则。LDVH 规范模型包括事实模型（specs/20-49）和行动模型（specs/50-79），两者共享相同的子文档分类、命名、状态骨架和契约子文档规则。本文将这些通用规则提取为独立规范，避免 13 和 14 重复维护同一套子文档约定。

本文是 LDVH 规范模型附件型子文档通用规则的权威位置。13 和 14 的子文档章节应引用本文，不得并行维护同一套子文档命名、骨架或契约规则。

---

## 2. 与 00 总纲的关系

00 定义 LDVH 的五类构成要素，其中事实模型和行动模型是两类核心要素。本文承接 00 中关于规范体系结构的要求，专门定义这两类要素共享的子文档通用规则。

本文不定义事实模型或行动模型本身——事实模型由 13 定义，行动模型由 14 定义。本文只定义两者共享的子文档规则。

---

## 3. LDVH 规范模型

LDVH 规范模型是 specs/ 中按 NN 编号组织的、有主文档和子文档体系的标准建模结构。当前包括：

| 规范模型 | 规范区段 | 基础规范 | 实例层 |
|---|---|---|---|
| 事实模型 | specs/20-49 | `specs/13-LDVH事实模型基础规范.md` | 事实实例（ldvh-base/） |
| 行动模型 | specs/50-79 | `specs/14-LDVH行动模型基础规范.md` | 行动执行（运行时） |

未来新增的规范模型类型（如 specs/80-99 区段）也适用本文定义的子文档通用规则。

## 4. 主文档与子文档的关系

### 4.1 主文档

主文档使用两位编号（NN），完整定义规范模型。主文档必须定义模型的对象定位、准入条件、事实源边界、状态机、Human Gate、字段契约、事实源回写要求、证据留存要求、AI 协作适配、Tools 契约式校验与执行适配、Web 信息同步适配、落地前决策、价值与要素审查、落地初始化、落地审计、合规检查和待补齐事项。

主文档文件名格式为：

```text
NN-{英文名}-{中文名}.md
```

主文档应遵守 `specs/03-Specs文档规范.md` §4.1 的章节编号、标题层级和章节定位要求。

### 4.2 子文档

子文档用于在主模型完整定义后，承接某个规范模型围绕 Rules、Skill、Agent、Tools、Web 的机制实践内容或结构化契约。子文档不重新定义主模型，不得为空占位。

子文档应遵守 `specs/03-Specs文档规范.md` §4.1 的章节编号、标题层级和章节定位要求。

规范模型完成落地初始化时，应为 `NN.01` 至 `NN.06` 六个子文档槽位形成显式结论。六槽位是 LDVH 的设计决定：确保每个规范模型对 Rules、Skill、Agent、Tools、Web 和 Contract 六类机制都有明确结论，避免隐式跳过。已启用或需要独立说明的机制，应创建对应子文档；暂不实现但未来可能需要的机制，应创建 active-prep 子文档说明当前状态、实现前提和边界；明确不需要的机制，应创建不创建说明型子文档说明理由和检查项。

主文档应保留六个子文档槽位的状态清单、摘要、适用条件和引用，不得把模型核心规则迁移到子文档中。不得仅在主文档中标记 planned 而缺少对应子文档或暂缓理由。

## 5. 子文档分类与命名

### 5.1 子文档分类

| 编号 | 文件名 | 类型 | 内容 | 语义定义 |
|---|---|---|---|---|
| `NN.01` | `NN.01-Rules.md` | 机制实践子文档 | Rules 入口约束实践 | Rules 在该模型中的行为约束、入口摘要、放置位置和禁止承载内容 |
| `NN.02` | `NN.02-Skill.md` | 机制实践子文档 | Skill 契约式行动实践 | Skill 在该模型中的契约式行动流程、准入判断、Human Gate 编排和事实源回写边界 |
| `NN.03` | `NN.03-Agent.md` | 机制实践子文档 | Agent 独立上下文并行实践 | Agent 在该模型中的独立上下文、参数注入、上下文分发、并行执行和汇总要求 |
| `NN.04` | `NN.04-Tools.md` | 机制实践子文档 | Tools 契约式校验与执行实践 | Tools 在该模型中的契约校验、聚合、上下文包生成和确定性受控执行能力定义 |
| `NN.05` | `NN.05-Web.md` | 机制实践子文档 | Web 信息同步实践 | Web 在该模型中的信息同步、Human Gate UI、受控编辑入口和协同入口实践 |
| `NN.06` | `NN.06-Contract.md` | 契约子文档 | 结构化契约、字段 schema、接口契约和数据结构 | 该模型的结构化数据契约，是契约字段的权威位置 |

NN.01-NN.05 为机制实践子文档，NN.06 为契约子文档。两者都是附件型子文档，都不重新定义主模型，但性质不同：机制实践子文档回答"这个模型如何实践某个机制"，契约子文档回答"这个模型的结构化接口、schema 和数据契约是什么"。

### 5.2 核心规则留在主文档

模型自身的核心规则应留在 NN 主文件，不应转移到子文档。核心规则的具体内容由各基础规范定义：

- 事实模型的核心规则：字段规则、状态规则、验收规则和实例检查要求（依据 13）
- 行动模型的核心规则：Context、Scenario、Gate、执行流程、回写要求和证据要求（依据 14）

### 5.3 标题格式

附件型子文档标题格式和命名维度规则依据 `specs/02-LDVH术语规范.md` §8.1，本文不重复维护。契约子文档标题格式为：`{主模型名} — 契约`。

## 6. 子文档状态与骨架

### 6.1 not-created

当某类机制经判断不需要为该模型创建实体或展开完整实践时，对应子文档应说明不创建的理由，不需要展开该机制的边界约束、不承载内容、可建议行为或检查项。

not-created 状态不表示子文档文件不存在，而表示该机制实体不创建、不展开完整实践；对应子文档仍应存在，用于说明不创建理由和检查项。不得将“子文档文件已创建”误判为 active。

此类子文档的骨架不适用 `specs/03-Specs文档规范.md` §5.3 的模型实践子文档完整骨架，只需包含：本文定位、不创建理由和检查项。主文档应在子文档清单中标注该子文档为 not-created 状态。

后续如需创建实体或升级为完整实践，应按 Human Gate 流程更新子文档内容，并补齐完整骨架。

### 6.2 active-prep

当某类机制经判断当前不需要实现但未来可能需要时，对应子文档应说明当前状态、未来能力定义、实现前提和边界约束。

此类子文档的骨架不适用 `specs/03-Specs文档规范.md` §5.3 的完整骨架，只需包含：本文定位、当前状态与未来能力定义、实现前提和边界约束、检查项。

主文档应在子文档清单中标注该子文档为 active-prep 状态。后续如需升级为 active，应按 Human Gate 流程更新子文档内容，并补齐完整骨架。

### 6.3 active

当某类机制经判断需要创建时，对应子文档应遵循 `specs/03-Specs文档规范.md` §5.3 的模型实践子文档完整骨架，包含：本文定位、实践目标、适用场景、实践边界、实践内容、Human Gate、检查要求和待补齐事项。若该机制存在 Trae Skill、Agent、Tools 脚本、Web 页面或其他实体实现，active 子文档必须说明实体路径、当前可用能力、调用或使用边界和验证方式。若 active 子文档涉及 Tools 实体实现，还必须说明测试文件路径、测试命令、测试覆盖范围和验收记录要求。

### 6.4 planned

planned 仅表示落地前决策尚未完成或落地初始化尚未执行的临时规划状态。规范模型声称完成落地初始化后，主文档子文档清单不得继续保留 planned 状态；应将每个槽位更新为 active、active-prep 或 not-created，并确保对应子文档存在。

### 6.5 状态与骨架审查顺序

审查模型实践子文档时，应先判断子文档正文意图，再检查主文档子文档清单中的状态是否匹配，不得仅凭主文档状态表机械套用完整骨架。

审查顺序如下：

1. 先读取主文档的附件型实践子文档清单，取得该子文档声明状态；
2. 再读取子文档正文的标题、定位和核心章节，判断正文实际意图；
3. 判断声明状态与正文实际意图是否一致；
4. 若声明状态与正文意图一致，再按对应状态骨架检查章节完整性；
5. 若声明状态与正文意图不一致，应记录为状态标注与正文性质不一致，不得直接按声明状态判定正文缺章节；
6. 若正文明确为不创建说明型，且已包含本文定位、不创建理由和检查项，不应要求补充完整 Human Gate、实践内容或待补齐事项；
7. 只有在正文意图和状态均为 active 时，才按本文 §6.3 要求完整骨架。

## 7. 契约子文档规则

### 7.1 契约子文档定位

契约子文档（NN.06）定义结构化数据契约，是契约字段的权威位置。

契约子文档不承载执行逻辑、流程步骤或 Human Gate 条款。

### 7.2 契约消费

实践子文档和工具可以消费契约子文档，但不得复制维护契约字段第二事实源。

### 7.3 契约变更

修改契约子文档属于规范变更，应评估 Human Gate 并记录 Change。【暂缓：Change 记录机制待替换，见 L1 规则】

### 7.4 契约与工具实现的关系

1. 工具实现应依据契约子文档定义的字段 schema 进行解析和校验，不得自行扩张格式契约（依据 `specs/12.01-Tools辅助规范.md` §6.1）。

2. 契约子文档应先于工具实现创建。工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束。

3. 契约子文档变更时，消费该契约的 Tools 实现和对应测试必须同步更新。契约变更未经 Human Gate 确认前，不得执行 Tools 同步更新。

4. 契约变更后、Tools 和测试同步更新完成前，Tools 校验结果不得视为可靠，应在 Tools 输出中标注契约版本不一致警告。

## 8. Skill、Tools、Contract 与需求变更联动规则

### 8.1 联动定位

Skill、Tools、Contract 和需求变更联动规则用于约束模型落地初始化、模型实践子文档更新、契约变更和实体实现变更之间的同步关系，防止 Skill 流程无 Tools 支撑、Tools 能力无消费场景、Contract 与实现脱节，或需求变更未同步更新契约、Tools 实现和测试。

本文是模型子文档之间联动规则的权威位置。13、14、11.02 和 12.01 应引用本文，不得并行维护另一套联动规则。

### 8.2 Skill 与 Tools 显式消费关系

1. `NN.02-Skill.md` 定义可复用流程时，应说明该流程是否需要 Tools 辅助；需要时应引用 `NN.04-Tools.md` 中的能力定义，并说明 Tools 能力缺失时的暂缓、降级或人工执行方式。
2. `NN.04-Tools.md` 定义 Tools 能力时，应说明该能力服务的主模型流程、`NN.02-Skill.md` 流程或 `NN.05-Web.md` 入口；没有明确消费场景时，不得创建孤立 Tools 实体。
3. `NN.02-Skill.md` 或主模型流程包含创建、更新、状态流转、关联回写、Change 记录生成【暂缓：Change 记录机制待替换，见 L1 规则】等可机械化事实源写入步骤时，必须反向检查 `NN.04-Tools.md` 是否定义对应受控写入执行能力；未定义时，应在落地前决策或暂缓项中显式标记，不得默认视为完整落地。
4. Skill 不得自行定义 Tools 输入输出字段、字段类型或字段约束；涉及结构化数据时，应引用 `NN.06-Contract.md`。
5. Tools 不得承载 Skill 的流程性判断、准入判断、授权生成或 Human Gate 编排。
6. Skill 实体创建或启用前，应检查对应模型的 `NN.04-Tools.md` 和 `NN.06-Contract.md` 是否足以支撑该 Skill 的标准输入输出、校验、受控写入和证据要求。
7. Tools 实体创建或启用前，应检查对应模型是否存在主模型流程、Skill 流程或 Web 入口消费该能力。

### 8.3 Contract、需求变更与实现同步

1. 当模型需求变更影响字段、状态、接口、输入输出、校验规则、文件命名、受控写入或 Web 信息同步数据结构时，应同步评估是否需要更新 `NN.06-Contract.md`。
2. `NN.06-Contract.md` 变更时，应同步检查并更新消费该契约的 `NN.02-Skill.md`、`NN.04-Tools.md`、`NN.05-Web.md`、Tools 实现和 Tools 测试。
3. Tools 实现变更影响输入、输出、校验范围、错误语义、写入行为或契约消费方式时，应同步更新对应 `NN.04-Tools.md` 和测试。
4. Skill 流程变更影响 Tools 调用时机、调用前提、降级路径、写入意图确认或证据要求时，应同步检查 `NN.04-Tools.md` 和 `NN.06-Contract.md`。
5. Web 信息同步入口变更影响数据结构、Human Gate UI、受控编辑入口或派生视图字段时，应同步检查 `NN.05-Web.md`、`NN.06-Contract.md` 和相关 Tools 能力。
6. 同步更新未完成前，不得声称对应 Skill、Tools、Web 或 Contract 已完整落地。

### 8.4 Tools 测试同步要求

1. active 的 `NN.04-Tools.md` 涉及 Tools 实体实现时，必须声明测试文件路径、测试命令、测试覆盖范围和验收记录要求。
2. Contract、需求变更或 Tools 实现变更影响 Tools 行为时，必须同步新增或更新 Tools 测试。
3. 测试应覆盖契约字段解析、必填字段、状态或枚举约束、输入输出格式、错误路径、受控写入边界和 Human Gate 不可绕过要求中的相关项。
4. 测试未执行或未通过时，不得声称 Tools 能力完成落地、验收通过或可作为 Skill / Web 的可靠依赖。
5. 契约变更后，Tools 实现和测试尚未同步更新时，Tools 输出应提示契约同步缺口，不得作为最终验收依据。

### 8.5 落地初始化检查

规范模型完成落地初始化时，应检查：

1. `NN.02-Skill.md`、`NN.04-Tools.md`、`NN.05-Web.md` 和 `NN.06-Contract.md` 的状态是否一致；
2. 已启用的 Skill 流程是否有明确 Tools 依赖、缺失能力处理方式和 Contract 引用；
3. 已启用的 Tools 能力是否有明确消费场景、Contract 依据、测试文件和测试命令；
4. 主模型流程或 Skill 流程中的可机械化写入步骤是否已有对应 Tools 受控写入执行能力，或已明确记录暂缓、降级和人工执行边界；
5. 需求变更、Contract 变更、Tools 实现变更和测试变更是否已同步完成；
6. 同步缺口是否进入暂缓项或待补齐事项。【暂缓：Change 记录机制待替换，见 L1 规则】

若第 4 项未通过，不得声称该规范模型的 Tools 实践已经完整支撑落地初始化；只能声明当前已落地的只读、校验、聚合或其他局部能力。

## 10. Human Gate

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变子文档分类（NN.01-NN.06）；
2. 改变子文档命名规则；
3. 改变子文档状态骨架规则；
4. 改变契约子文档规则；
5. 改变契约与工具实现的关系规则；
6. 改变 Skill、Tools、Contract 与需求变更联动规则；
7. 将六槽位完整实践要求降级为按需创建，或允许落地初始化完成后保留 planned 状态；
8. Contract、需求变更或 Tools 实现变更后，未同步更新消费该契约的 Tools 实现和测试。

## 11. 检查项

检查 LDVH 模型子文档规范是否合规时，应确认：

1. 13 和 14 的子文档章节是否引用本文，未并行维护同一套子文档规则；
2. 子文档命名是否符合本文 §5.1 的分类和命名表；
3. 已完成落地初始化的规范模型是否为 NN.01-NN.06 六个子文档槽位形成显式结论，且对应子文档存在；
4. 子文档状态骨架是否符合本文 §6 的 active、active-prep、not-created 和 planned 规则；
5. 已完成落地初始化的规范模型主文档是否不存在 planned 子文档状态；
6. active 子文档涉及实体实现时是否说明实体路径、当前可用能力、使用边界和验证方式；
7. active 子文档涉及 Tools 实体实现时是否说明测试文件路径、测试命令、测试覆盖范围和验收记录要求；
8. 契约子文档是否遵循本文 §7 的规则；
