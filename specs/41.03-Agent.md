## 一、本文定位

Agent 增强模式是多角色思考的**重型增强手段**，用于需要独立上下文、结论隔离、并行委派、不同权限边界的场景。**默认不要求创建 Agent**，仅在条件满足时才考虑使用。

---

## 二、何时考虑 Agent 增强模式

满足以下**任一**条件时才应考虑：

| 条件 | 说明 |
|---|---|
| 需要多个专业角色并行分析 | 各角色需要独立上下文 |
| 单一主上下文无法承载大量事实源 | 需要结论隔离 |
| 需要不同权限边界或工具能力 | 部分角色需要读写权限 |
| 涉及复杂前端/后端/性能/安全/AI集成/测试维度 | 需要专业 Agent 视角 |
| 用户明确要求使用已安装 Trae 预制 Agent | 显式调用 |

## 三、硬性前提

**Agent 增强模式的默认前提：当前 Trae 环境已安装并可调用相关 Trae 预制 Agent。**

| 前提检查结果 | 处理 |
|---|---|
| 已确认可调用 | 可进入 Agent 增强模式 |
| 未安装 | **降级**为主上下文轻量模式或 Skill 辅助模式 |
| 不可确认 | **不得声称**已执行 Agent 增强分析，应降级或询问用户 |
| 用户要求必须 Agent 增强但前提不满足 | 暂停并提示先安装相关 Agent |

未满足前提时**不影响**轻量模式或 Skill 辅助模式执行。

## 四、预制 Agent 类型参考

在已安装并可调用的前提下，按主题选择：

| 主题 | Agent 类型 | 关注点 |
|---|---|---|
| UI、交互、视觉 | UI 设计 | 用户体验、视觉层次、交互风险 |
| 前端架构 | 前端架构 | 组件结构、状态管理、性能 |
| 后端、API、数据 | 后端架构 | API、数据库、服务边界、业务逻辑 |
| API 可靠性 | API 测试 | 契约、性能、负载 |
| 性能问题 | 性能优化 | 瓶颈、资源消耗、优化建议 |
| 部署、CI/CD、监控 | DevOps 架构 | 部署链路、基础设施、监控和回滚 |
| AI、模型、推荐 | AI 集成 | 模型集成、提示词、自动化边界 |
| 安全相关 | 安全审查 | 权限、密钥、数据保护 |

**注意：** 这是调度建议，不表示 LDVH 已维护对应 Agent 定义。

## 五、调度流程（精简）

1. 主控识别 Scenario → 判断主上下文或 Skill 不足
2. 检查相关 Trae 预制 Agent 是否可用
3. 说明拟调用 Agent、输入 Context、权限边界和预期输出
4. 高影响调度 → 触发 Human Gate
5. 用户显式调用或主控编排 Agent
6. 各 Agent 独立输出 → 主控汇总一致结论、分歧、风险和回写建议

**上下文分发要求：** 只给 Agent 最小必要事实源，明确只读或写入权限，不得分发密钥或敏感信息。

## 六、主控汇总检查

汇总 Agent 输出时，主控必须检查：

1. 每个 Agent 是否在权限边界内行动
2. 是否存在互相冲突的结论
3. 是否存在与 Git 文件事实源冲突的结论
4. 哪些只是过程分析，哪些需要回写
5. 是否有需要 Human Gate 的建议

**Agent 输出不得绕过主控直接写入事实源。**

## 七、门禁

创建、导入、启用、停用、删除 Agent，修改 Agent Prompt 或权限，将 Agent 输出提升为稳定事实，必须暂停确认。
