任何正式事实对象字段都必须在本表恰好登记一次。登记与相应唯一字段定义必须在同一变更中形成；未登记、重复登记、定义悬空或登记与定义不一致的字段不得生效。`field_key` 是字段语义的稳定身份，不随显示名称、承载规范或实现结构调整而改变，也不得改派给其它语义。

登记列遵守以下闭集：

- `field_key`：匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，在全部历史与当前登记中全局唯一且不得改派；
- `container_ref`：必须精确引用结构登记表；字段路径只在该结构的直接成员范围内解释；
- `field_path`：字段在所属结构内的 canonical 直接成员名，不写点号、数组下标或其它结构路径；
- `JSON type`：只使用 `string`、`boolean`、`integer`、`number`、`object` 或 `array`；
- `field_role`：`fact-object` 的直接成员固定为 `object-field`，其它结构的直接成员固定为 `structure-member`；只有 `object-field` 进入类型字段使用绑定；
- `value_structure`：JSON 类型为 `object` 或 `array` 且值由登记结构组成时引用相应 `structure_key`，其余固定为 `none`；不得用未登记 object 作为扩展逃生口；
- `base_presence`：全部直接字段只使用 `required` 或 `conditional`。`required` 表示所在结构出现时该成员必须出现；事实对象直接字段的类型绑定也必须保持 `required`。`conditional` 表示只能依据唯一字段定义收紧为 `required`、`conditional` 或 `forbidden`，不得使用无条件自由省略的 `optional`。结构成员不进入类型绑定表，其值由 Schema 组合按本列与唯一成员定义递归继承；
- `definition_scope`：只使用 `foundation` 或 `type`。前者由本附件唯一定义且提升后不得自动降级，后者由 `applies_to` 中唯一具体类型的来源定义；
- `applies_to`：`*` 表示字段身份对全部当前及后续事实类型保留；其它值使用按 `fact_type_key` ASCII 升序排列、英文逗号连接且不带空格的稳定闭集。`foundation` 可以使用 `*` 或至少两个类型，`type` 必须恰好一个类型；有限闭集即使暂时等于全部当前类型也不得自动改写为 `*`，只有语义本身对任意事实类型成立时才能使用 `*`；
- `definition_ref`：使用 `<responsibility-key>::<exact-H2>::<field-key>`，前两段精确定位唯一字段定义表，第三段必须等于本行 `field_key`；
- `status`：只使用 `current` 或 `retired`。`retired` 字段不得用于新对象，既有对象和引用的迁移或保留规则必须由原定义来源与 05 共同确定。类型或原定义来源退出当前规则源后，`retired` 行仍保留最后有效的 key、位置、shape、适用范围和定义引用作为 tombstone；Code 不再要求该历史类型或定义来源仍为 current，但任何 current 登记和引用都不得消费它。

登记表统一管理字段身份、所属结构、canonical 路径、类型、角色、值结构、定义归口、适用范围和定义位置，不把类型专属字段的完整语义复制到本附件。`retired` 行必须永久保留，`field_key` 和“`container_ref` + `field_path`”均不得被其它语义复用。Code 可以据此生成全局检索视图和五类型适用矩阵；生成结果只用于读取和验证，不得反向修改本表或定义字段。

## 基础结构定义表

| structure_key | meaning | not_meaning | constraints |
|---|---|---|---|
| `fact-object` | 一个具体事实对象的顶层 JSON object 成员闭集 | 不表示具体事实类型、文件格式或存储位置 | 直接成员必须登记为 `object-field` |
| `source-ref` | 重新定位事实内容来源或证据来源所需的引用成员闭集 | 不证明来源正确、证据充分或对象已经验证 | 只承载定位、版本和观察时间，不允许未登记扩展字段 |
| `relation` | 一个事实对象指向另一事实对象的有向关系成员闭集 | 不表示反向关系、派生索引或目标对象内容 | 必须包含关系 key 和稳定目标，关系依据按定义条件出现 |
| `relation-target` | 关系目标的管辖项目、事实类型和对象身份成员闭集 | 不复制目标对象标题、状态或内容 | 必须能够恢复稳定目标；跨配置时保留管辖来源引用 |

本表唯一定义全部 `definition_scope: foundation` 且 `applies_to: *` 的基础结构。结构语义与其直接成员字段共同构成闭集；不得只复制成员 shape 后创建同义结构身份。

公共顶层字段只在本附件定义。每个具体类型通过“类型字段使用绑定表”引用这些字段并说明本类型的出现规则；不得复制本表或改变字段名、JSON 类型和共同语义。

公共字段不得使用显式 `null` 代替缺失或未知。无法取得必填字段时，对象不满足当前类型契约；条件字段不适用时省略。空字符串、空引用列表和仅为满足 Schema 而生成的默认时间、默认状态或默认关系均不成立。

`source_refs[]` 与 `evidence_refs[]` 使用同一成员结构，但两个顶层字段作用不同。成员字段使用闭集；具体类型可以规定哪些字段在特定来源种类下条件必填，不得新增同义定位、版本、观察时间或未登记的通用扩展对象。

## 事实对象关系字段

| field_key | 字段 | JSON 类型 | 出现规则 | 含义与边界 |
|---|---|---|---|---|
| `relation-key` | `relation_key` | string | 必填非空；匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*` | 由来源对象所属具体类型定义的有向关系语义；名称相似不产生关系 |
| `relation-target` | `target` | object | 必填 | 使用“事实对象关系目标字段”唯一定位目标对象 |
| `relation-source-refs` | `source_refs` | array | 关系不是由当前对象其它内容直接、无歧义表达时必填；出现时至少一项 | 说明该关系本身的形成依据；成员使用“来源与证据引用字段”，不替代目标身份 |

`relations[]` 使用本表字段闭集。关系只由来源对象正向声明；反向索引可以由 Code 派生，但不得写回为第二关系权威。

|---|---|---|---|---|

## 类型字段使用绑定表

每个具体事实类型在形成正式字段绑定前，必须先包含一个标题文本为 `字段准入记录` 的 H3，并用下表记录该类型的每项信息需求如何经过全局字段检索：

| information_need | compared_field_keys | decision | resulting_field_key | rationale | review_ref |
|---|---|---|---|---|---|

| 列 | 要求与边界 |
|---|---|
| `information_need` | 先用不预设字段名的语言说明对象必须回答什么问题；不得把预定字段名改写成需求 |
| `compared_field_keys` | 列出统一登记中语义最接近的全部 `field_key`，按 ASCII 排序并以英文逗号连接；确认没有近似项时写 `none`，不得只记录同名字段 |
| `decision` | 只使用 `reuse`、`promote`、`differentiate` 或 `new`，分别对应 05 §7.2 的四种结论 |
| `resulting_field_key` | 最终复用、提升、区分或新增的唯一 `field_key`；必须已在统一登记表中成为 `current` |
| `rationale` | 说明比较过语义、JSON 形态、生命周期、来源与证据、出现条件、未知值和更新规则后的结论；不得只写名称不同、实现方便或没有找到 |
| `review_ref` | 使用 `<spec-key>::<exact-type-H2>::<review-key>` 精确回指同一类型定义章节“字段独立复核”表中的一行；该表只证明复核过程，不取得字段定义权；不得回指聊天、未回写的 agent 输出或用 Code 检查通过代替语义复核 |

全部类型字段使用绑定都必须能回到恰好一行 `resulting_field_key` 相同的准入记录。同一类型内的 `information_need` 和 `resulting_field_key` 分别唯一；多个相近信息需求确实由同一字段承接时必须合并为一个完整但边界清楚的信息需求和一项准入结论，不能保留同一字段的并行准入权威。一项需求确实拆成多个字段时，必须拆写为能够分别判断且互不重复的需求记录，不能用一行含混覆盖。Code 可以验证表格结构、字段引用、唯一性和覆盖关系，不能判定比较是否充分或结论是否正确。

每个具体事实类型的唯一定义章节还必须包含一个标题文本为 `字段独立复核` 的 H3，并紧接一张固定表：

| review_key | reviewer | reviewed_scope | findings | disposition |
|---|---|---|---|---|

`review_key` 在该类型内唯一并匹配 `field-review-[0-9]{4}`；`reviewer` 记录独立于字段与结构初始设计者的 AI 执行者或专门审查者；`reviewed_scope` 必须说明实际复核的全部字段与结构准入行、相应提案和登记对象；`findings` 记录主动寻找的字段或结构同义、冲突、遗漏和反例；`disposition` 记录保留、复用、提升、区分、删除或修正结果。Code 只验证表格 shape、key 和引用存在；是否真正独立、复核是否充分以及结论是否正确仍由 AI/Human 审核。

每个具体事实类型的唯一定义章节必须包含一个标题文本为 `类型字段使用绑定` 的 H3，并紧接一张使用以下真实表头的表格：

| field_key | field_path | presence | type_constraints |
|---|---|---|---|

该表声明完整对象 Schema 实际使用哪些已登记字段以及本类型允许的收紧，不定义字段共同语义：

| 列 | 要求与边界 |
|---|---|
| `field_key` | 必须精确引用统一字段登记表中 `container_ref` 为 `fact-object`、`field_role` 为 `object-field` 的一个 `current` 字段；不得直接绑定结构成员、未知、`retired` 或不适用于本类型的字段 |
| `field_path` | 必须与登记表完全一致；用于防止引用正确 key 却在类型中另起同义路径 |
| `presence` | 只使用 `required`、`conditional` 或 `forbidden`；条件细节写入 `type_constraints`。`base_presence: required` 只能绑定为 `required`；`base_presence: conditional` 可以按唯一字段定义收紧。有限 `applies_to` 已明确字段适用于所列类型，因此不得在其中绑定为 `forbidden`，不再适用时必须先显式移出闭集；只有 `applies_to: *` 为所有类型保留的条件入口可以在某类型绑定为 `forbidden`。全部 `applies_to: *` 的事实对象直接字段都必须在每个类型中出现一行绑定，包括禁止出现的条件基础字段 |
| `type_constraints` | 必填非空。`foundation` 字段只说明本类型出现条件、允许值、充分性或其它由共同定义授权的单调收紧，没有额外收紧时写 `none`。`type` 字段的语义、值形态、内容边界和更新规则已经由同一类型的专属字段定义唯一承担：绑定为 `required` 时本列必须精确写 `none`；绑定为 `conditional` 时必须以 `出现条件：` 开头且只说明何时必填、禁止或省略。不得在绑定中复制 type 字段定义或放宽任何共同边界 |

绑定表必须覆盖本类型使用的全部部分复用和类型归口的事实对象直接字段。登记为适用于本类型的直接字段没有绑定，或者绑定了登记表未授权给本类型的字段时，类型 Schema 不成立。结构成员随绑定字段的 `value_structure` 递归继承，不进入类型绑定表。

## 类型专属字段定义表

每个具体事实类型的唯一定义章节必须先包含一个标题文本为 `结构准入记录` 的 H3。存在本类型新增、区分、复用或提升的非全局基础结构时，使用固定表：

| information_need | compared_structure_keys | decision | resulting_structure_key | rationale | review_ref |
|---|---|---|---|---|---|

其列规则与字段准入记录一一对应，只是比较和产生的对象改为 `structure_key`；`decision` 使用相同四值，查重覆盖全部 `current`、`retired` 结构以及本类型全部结构提案。没有此类结构需求时，在 H3 下直接写明“本类型没有结构准入事项”，不得建立空表。

每个具体事实类型还必须包含一个标题文本为 `类型专属结构定义` 的 H3。存在本类型 `definition_scope: type` 的结构时，使用固定表：

| structure_key | meaning | not_meaning | constraints |
|---|---|---|---|

该表中的每个结构必须完成结构准入并在结构登记表中精确登记；其全部直接成员仍须进入类型专属字段定义表和统一字段登记表。没有类型专属结构时，在 H3 下直接写明“本类型没有类型专属结构”，不得建立空表。

每个具体事实类型的唯一定义章节必须包含一个标题文本为 `类型专属字段定义` 的 H3。存在本类型独有字段时，H3 后紧接一张使用以下真实表头的表格：

| field_key | field_path | JSON type | meaning | not_meaning | constraints |
|---|---|---|---|---|---|

每一行唯一定义一个已经在统一字段登记表中登记为本类型 `definition_scope: type` 的字段：

| 列 | 要求与边界 |
|---|---|
| `field_key` | 必须与统一登记表中的唯一行相同；不得在其它类型或附件字段定义表中再次出现 |
| `field_path` | 必须与登记表完全一致；使用字段名或点号路径，不写数组下标 |
| `JSON type` | 必须与登记表完全一致，只使用登记表允许的 JSON 类型 |
| `meaning` | 必填非空；说明字段回答什么问题，不得复制已有字段语义 |
| `not_meaning` | 必填非空；说明与全局查重中最接近字段的差异以及本字段明确不承载什么；没有近似字段时写明经全局检索未发现近似语义，不得留空 |
| `constraints` | 必填非空；唯一说明字段值形态、嵌套结构、来源、跨字段语义约束、未知内容和更新边界；不得重复该顶层字段何时出现，出现条件只由类型使用绑定承担；无附加约束时写 `none` |

某类型没有专属字段时，在 `类型专属字段定义` H3 下直接写明“本类型没有类型专属字段”，不得创建空表。状态值、关系类型和来源或证据充分性分别在类型定义正文及使用绑定中规定，不作为伪专属字段复制公共入口。

## 跨类型共享字段定义表

| field_key | field_path | JSON type | meaning | not_meaning | constraints |
|---|---|---|---|---|---|
| `current-summary` | `summary` | string | 不读取完整历史即可理解对象当前焦点、边界、进展与剩余不确定性的最新快照 | 不表示标题、期望目标、完整历史、验证结论或终态处置 | 必填非空；对象当前语义发生实质变化时同步更新，不追加过程日志 |
| `priority` | `priority` | string | 同一类型未终态对象之间的相对处理优先级 | 不表示授权、价值、风险、执行顺序或其它类型之间的全局排序 | 闭集 `P0`、`P1`、`P2`、`P3`；P0 表示不及时处理会阻断当前主线或扩大明显错误，P1 表示明确影响近期关键闭环，P2 表示有确定价值但可正常排队，P3 表示可延后处理；只在具体类型定义出现条件后使用，终态对象不保留历史优先级 |

| `closed-at` | `closed_at` | string | 对象当前终态第一次有效成立的时间 | 不表示最近更新时间、提交时间或下游工作完成时间 | 只在终态出现；使用带时区的 RFC 3339 date-time，且 `created_at <= closed_at <= updated_at`；事实更正不改变有依据的原终态时间 |
| `adr-applicability` | `applicability` | string | 对象核心内容成立或适用的对象、环境、条件、范围和明确排除项 | 不表示工作执行范围、对象身份、当前状态、规则适用自动判定或行动授权 | 必填非空；任何泛化必须有来源支持，来源未覆盖的范围必须排除或保持未知；各类型只能收紧自身核心内容的适用边界 |
| `workcase-validation-summary` | `validation_summary` | string | 对对象核心声明的实际验证覆盖、结果、失败与未验证范围的当前说明 | 不表示证据定位、命令日志、终态处置、Human 确认收据或对象已完成 | 非空；结论必须由 evidence_refs 支持；变化时覆盖当前说明，不追加执行日志；类型必须定义验证针对的核心声明和出现条件 |

存在只供部分类型复用的 `definition_scope: foundation` 字段时，只能在本节追加唯一字段定义，使用与“类型专属字段定义表”相同的六列表头。`meaning`、`not_meaning` 和 `constraints` 定义全部使用类型共同成立的基线；各类型差异只能进入相应使用绑定的 `type_constraints`。

原 `definition_scope: type` 字段被第二个类型需要时，必须在同一变更中从原类型定义表删除该定义、在本节建立相同 `field_key` 的唯一共同定义、把定义归口改为 `foundation` 并更新 `applies_to`，再为全部使用类型建立绑定。不得保留原定义副本，也不得新建同义 `field_key`；提升后不得因后续类型不使用而自动降级。

## 跨类型共享结构定义表

存在只供部分类型复用的 `definition_scope: foundation` 结构时，只能在本节追加唯一结构定义，使用与“基础结构定义表”相同的四列表头。原 `definition_scope: type` 结构被第二个类型需要时，必须在同一变更中从原类型结构定义表删除、在本节建立相同 `structure_key` 的唯一共同定义、更新结构登记的定义归口和 `applies_to`，并同步核对全部直接成员字段的定义归口与适用范围。不得保留原定义副本或创建同义结构；提升后不得自动降级。当前没有已准入的部分复用结构，本节不建立空表。

## Schema 组合边界

1. 完整对象 Schema 必须从 `fact-object` 结构中选择适用于该类型且状态为 `current` 的直接字段，组合每个字段的唯一基础或专属定义、`base_presence` 与该类型使用绑定，再按 `value_structure` 递归展开结构成员及其 `base_presence`；不得从实现私有表补字段；
2. 组合后的每个结构使用成员闭集。未知字段、未登记字段、未绑定的对象直接字段、重复定义、悬空结构引用、范围与适用类型不一致或同一结构内路径约束冲突时，组合失败，不能静默选择其中一份；
3. `foundation` 字段的共同 Schema 只有一个 Code 维护位置；`type` 字段也各自只有一个由 `definition_ref` 派生的定义表示。类型完整 Schema 可以生成五份，但不得复制后独立维护；
4. 具体类型可以实现比共同定义更严格且已由使用绑定说明的 `object_id`、状态、来源、证据和关系检查，但不得放宽公共必填、JSON 类型、时间和稳定引用边界；
5. Code 常量、JSON Schema、类型定义、test fixture、全局字段索引、适用矩阵和 Web DTO 都是派生表示，必须能回到登记、唯一字段定义和类型使用绑定；不得反向定义字段。
