## 1. 本文解决的问题

本文解决 LDVH 正式规范如何进入运行环境的问题。

正式规范不能只停留在正文中，也不能直接跳到某个环境的 Rules、Skill、Agent、Hook、命令、CI 或 Web 页面。规范应先说明自己要落地需要满足哪些要求，再说明由什么保障机制执行，之后才进入具体环境适配和运行投影。

本文是 04 系列的父规范，只规定分层链路、子文档边界和适用顺序。各层细则由 04.01 至 04.08 承接。平台差异通过平台适配清单承接；当前已有 Trae Solo 和 Codex 适配清单。当前环境检查、运行投影现场检查和 AI 统一入口细则分别由 04.02、04.04、04.06 和 42 承接，本文不重复展开。

本文使用的规范落地要求、保障机制、环境适配映射、运行投影、环境能力、环境实体、漂移、LDVH落地和环境确认等术语，按 `docs/specs/02-术语规范.md` 定义。本文只规定这些术语在 04 系列中的应用关系和执行边界。

## 2. 与 00 总纲的关系

00 定义开发环境、工作模型、工作流程、Code 和 Web 是 LDVH 的五类构成要素，并要求 LDVH 形成可规划、可执行、可验证、可沉淀、可演进的 AI 工程闭环。

本文承接 00 的上位原则，把正式规范进入运行环境的链路拆成以下层次：

```text
正式规范
→ 规范落地要求
→ 保障机制
→ 落地承接单元
→ 环境适配映射
→ 平台适配规则
→ 候选运行投影
→ 实际承接证据与当前检查结果
→ 稳定结论分流与事实源回写
```

其中，正式规范是权威文本；规范落地要求、保障机制、环境适配映射和运行投影的术语定义按 `docs/specs/02-术语规范.md` 执行。落地承接单元用于说明某项要求由工作流程、Code、Web、Skill、Agent、Hook、平台入口、Human Gate、平台清单 open_items 或其组合承接；平台适配规则用于说明不同平台如何把承接单元映射为平台实体和检查证据。本文在此说明它们在规范进入运行环境时的先后关系。

运行投影不是最终事实源。运行投影、环境工具输出、Skill 输出、Agent 输出、Web 状态、缓存、安装 / 初始化过程状态或环境观察状态与 docs/specs 正式规范冲突时，以 docs/specs 正式规范为准。

04 系列只允许保存具备证据生命周期和权威承载位置的状态，例如 Task、ADR 等工作对象状态、平台适配清单中的 open_items、正式规范待补齐事项或已完成变更证据。安装、初始化和环境观察只能即时读取为当前检查结果，不得另建长期状态登记；需要沉淀时必须按 09 的事实源边界分流到对应对象或规范位置。

## 3. 分层规则

### 3.1 正式规范

正式规范位于 `docs/specs/` 正文区，定义 LDVH 的稳定规则、对象边界、流程要求、Code 要求、Web 要求、环境适配要求或检查要求。

只有 `docs/specs/` 下的正式规范文档默认需要声明“规范落地要求”段落。目录说明、索引说明、research、refs、README、项目资料文档和其他非正式规范文档，不默认需要声明规范落地要求；若其中内容被升级为稳定规则，应先吸收到正式规范，再由正式规范声明规范落地要求。

### 3.2 规范落地要求

规范落地要求用于回答：这条规范要落地，需要被看见、复用、独立思考、确定性执行、Human 交互、生命周期触发或被后续规范承接吗。具体字段、类型和“不得写入具体环境实体”的规则由 `docs/specs/04.01-规范落地声明规范.md` 规定。

### 3.3 保障机制

保障机制用于回答：某项规范落地要求由什么规则、检查、流程、Code、Human Gate、子 Agent 思考、生命周期触发或审计动作保障执行。

规范落地要求必须绑定保障机制。没有保障机制的落地声明，只是愿望，不构成完整落地声明。

### 3.4 落地承接单元

落地承接单元用于回答：某项规范落地要求和保障机制由哪些 LDVH 构成要素或环境能力共同承接。

落地承接单元可以是工作流程、Code、Web、Rules / Instructions、Skill、Agent、Hook、CI、平台入口、Human Gate、平台适配清单 open_items、人工降级检查或它们的组合。承接单元不是平台安装包，也不是长期状态源；它只描述“用什么能力承接这项要求”。具体选择规则由 `docs/specs/04.03-环境能力承接边界规范.md` 定义。

### 3.5 环境适配映射

环境适配映射用于回答：某项规范落地要求和保障机制，在 Codex、Trae、Claude Code、Cursor、CI、Web、命令行或其他环境中如何实现、如何验证、如何降级。

环境适配映射以规范落地要求、保障机制和落地承接单元为输入，不得因为某个环境已有或缺少某项能力而反向改变正式规范本身。

### 3.6 平台适配规则

平台适配规则用于回答：某个平台如何把承接单元映射为平台实体、路径、入口、命令、权限、证据、降级方式和 open_items。

平台适配规则由 `docs/specs/04.06-平台适配清单规范.md` 和具体平台清单承接。它借鉴 target adapter 的分层思想，但不创建安装器、不保存安装状态、不把平台名称硬编码为 42 的通过依据。

### 3.7 候选运行投影与实际承接证据

运行投影是环境适配映射后实际存在或被调用的入口、文件、配置、命令、Skill、Agent、Hook、CI 检查、Web 页面、摘要或降级记录；运行投影的存在、可用或维护情况只能在执行时即时读取为当前检查结果，不替代运行投影本体，也不得保存为长期环境状态。

候选运行投影是 41、42、Code、Web 或 AI 在执行过程中提出的可能承接动作，例如建议新增入口、补 Code 检查、补 Web 展示、补平台清单证据或补 Human Gate。候选运行投影只属于过程输出，必须经 Human Gate、实际写入和验证后，才可能形成实际承接证据。

实际承接证据包括真实文件、入口、配置、命令、测试结果、Web 展示、平台清单证据、Human Gate 记录或 Git diff。实际承接证据仍不等于长期环境状态；它只作为当前检查和后续稳定事实分流的依据。

运行投影必须能追溯到正式规范、规范落地要求和环境适配映射。运行投影不得承载未被正式规范吸收的 research、refs 或临时判断。

## 4. 04 系列子文档边界

04 系列使用子文档，是因为规范落地声明、环境适配、环境能力边界、LDVH 落地特别要求、个人落地特别要求和平台适配清单分别回答不同问题。AI 统一入口、Skill、Agent、Hook、Command 等具体机制属于运行投影或环境能力承接方式，不单独按机制类型拆分专项规范。子文档不得复制父规范通用链路，也不得重新定义 00 的五类构成要素。

| 文档 | 回答的问题 | 边界 |
|---|---|---|
| `docs/specs/04.01-规范落地声明规范.md` | 正式规范如何声明规范落地要求和保障机制 | 不维护具体环境实体 |
| `docs/specs/04.02-环境适配与运行投影规范.md` | 规范落地要求如何映射到具体环境、候选运行投影和实际承接证据 | 不重新定义平台能力，不反向改写正式规范，不保存环境状态 |
| `docs/specs/04.03-环境能力承接边界规范.md` | Rules / Instructions、Skill、Agent、Hook、Code、Web 等能力各自适合承接什么，以及承接单元如何选择 | 不替代各环境官方文档，不维护平台能力清单 |
| `docs/specs/04.04-LDVH落地特别要求规范.md` | LDVH 自行设定的薄入口、Skill 命名和运行投影特别纪律如何登记、启用和检查 | 不维护平台能力清单，不承载个人环境命令约定 |
| `docs/specs/04.05-个人落地特别要求规范.md` | 当前个人或维护者环境中特殊命令、路径或平台约定如何登记和限制 | 不推广为 LDVH 通用跨环境规则，不替代管辖项目自身约定 |
| `docs/specs/04.06-平台适配清单规范.md` | 平台适配清单应如何声明要求响应矩阵、平台实体映射规则、证据、降级、open_items 和 42 依赖方式 | 不替代平台官方文档，不声明未经检查的平台支持 |
| `docs/specs/04.07-Trae-Solo适配清单.md` | Trae Solo 作为当前优先做实的平台清单如何承接 LDVH | 不把 Trae Solo 硬编码为 42 唯一逻辑，不替代 42 现场检查 |
| `docs/specs/04.08-Codex适配清单.md` | Codex CLI 作为当前已有平台清单如何承接 LDVH | 不把 Codex 硬编码为 42 唯一逻辑，不替代 42 现场检查 |

04.03 至 04.06 文件名应尽量表达其规范职责；04.07 和 04.08 是当前平台适配清单，虽然文件名不以“规范”结尾，但只要位于 `docs/specs/` 正文区并定义稳定规则，就仍属于正式规范文档，必须声明规范落地要求。

## 5. 使用顺序

AI 创建、修改或审计 docs/specs 正式规范时，应按以下顺序处理：

1. 先读取 `docs/specs/00-LD-Vibe-Harness理念与纲要.md` 中与本次变更相关的上位原则；
2. 按 `docs/specs/03-文档基础规范.md` 和 `docs/specs/03.01-规范文档规范.md` 判断文档工作区、正式规范身份、引用方向和文档骨架；
3. 按 `docs/specs/04.01-规范落地声明规范.md` 判断目标规范是否需要声明或更新规范落地要求；
4. 若某项落地要求需要进入运行环境，先按 `docs/specs/04.03-环境能力承接边界规范.md` 判断落地承接单元和能力选择边界；
5. 再按 `docs/specs/04.02-环境适配与运行投影规范.md` 判断环境适配映射、候选运行投影、实际承接证据和当前检查结果；
6. 若涉及 LDVH 自行设定的薄入口、Skill 命名或运行投影特别纪律，按 `docs/specs/04.04-LDVH落地特别要求规范.md` 处理；
7. 若涉及当前个人或维护者环境中的命令、路径或平台特别约定，按 `docs/specs/04.05-个人落地特别要求规范.md` 处理；
8. 若涉及 AI 统一入口、工作区级薄入口、项目级入口或平台入口路由，按 `docs/specs/04.02-环境适配与运行投影规范.md` 判断运行投影边界，并按 `docs/specs/04.04-LDVH落地特别要求规范.md` 判断薄入口和入口分层细则；
9. 若涉及平台差异、承接方法、平台实体映射、证据、降级、open_items 或 42 LDVH落地与检查依据，按 `docs/specs/04.06-平台适配清单规范.md` 处理；当前平台为 Trae Solo 时，读取 `docs/specs/04.07-Trae-Solo适配清单.md`；当前平台为 Codex CLI 时，读取 `docs/specs/04.08-Codex适配清单.md`；
10. 若本次任务需要创建、修改或删除持久运行投影，应现场确认当前平台清单、权限边界、Human 授权、验证方式和降级方式；当前判断写入 42 落地与检查报告，稳定结论如需沉淀，应按内容性质另行进入 Task、Memo、ADR、正式规范或对应事实源，不写入当前环境状态登记表；
11. 若发现需要确定性工具、校验、解析、受控写入、测试或上下文压缩，按 `docs/specs/07-Code实现规范.md` 形成 Code 需求、实现最小能力并验证。

## 6. 不得省略的边界

正式规范进入运行时不得省略以下边界：

1. **要求先于环境**：先判断 LDVH 需要什么规范落地要求，再判断某个环境如何适配；
2. **规范不替代平台文档**：平台能力、参数契约和客观限制以官方文档、当前环境配置或 refs 为准；
3. **适配依赖清单**：Codex、Trae、Claude Code、Cursor 或其他环境都通过平台适配清单承接差异；Trae Solo 和 Codex 清单是当前已有清单，不成为 42 的硬编码逻辑；
4. **投影不是事实源**：运行投影只能承载入口、摘要、触发、流程或降级记录，不能替代 docs/specs 正式规范，也不能保存安装、初始化或环境观察的长期状态；
5. **缺口要回到正确层级**：规范缺口回规范，环境缺口回环境适配映射，Code 缺口回 Code 需求，LDVH 落地特别要求回 04.04，个人落地特别要求回 04.05；
6. **稳定事实必须回写**：Agent、Skill、工具、Web、CI 或 Hook 输出中的稳定结论，必须写入 Git 文件事实源后才生效。

## 8. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变规范落地要求、保障机制、环境适配映射和运行投影之间的分层关系；
2. 新增、删除、重命名或改变 04 系列子文档职责；
3. 允许正式规范直接把环境实体写成规范落地要求；
4. 允许运行投影替代 docs/specs 正式规范；
5. 将某个具体环境能力提升为 LDVH 全局唯一底座；
6. 新增或扩大 LDVH 落地特别要求或个人落地特别要求，并可能削弱 Human Gate、事实源边界或 Code 验证纪律；
7. 删除、重命名或改变 AI 统一入口运行投影的职责边界。

04 系列检查至少包括：

| 检查项 | 标准 |
|---|---|
| 分层链路 | 正式规范、规范落地要求、保障机制、落地承接单元、环境适配映射、平台适配规则、候选运行投影、实际承接证据和当前检查结果未混淆 |
| 子文档边界 | 04.01 至 04.06 各自回答不同问题，未互相复制正文 |
