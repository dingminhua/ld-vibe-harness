## 一、本文解决的问题

本文解决 LD Vibe Harness specs 文档如何编号、如何分区、如何区分正式规范文档、子文档、模型实践子文档和内部调研文档，如何界定关键术语边界，以及如何通过引用纪律避免多个事实源的问题。

LD Vibe Harness 的 specs 文档治理目标，不是让所有内容都进入同一种文档格式，而是让 AI、人和工具能稳定判断一份文档在规范体系中的位置、权威范围、上位依据、术语含义、引用方式和 Human Gate 要求。

---

## 二、与 00 总纲的关系

00 定义 LD Vibe Harness 的产品理念、价值实现标准、五类构成要素和基础规范索引。本文承接 00 中关于规范体系结构、术语一致性和事实源单一性的要求，专门定义 specs 文档结构、编号分区、文档类型、术语边界、引用纪律和治理检查。

本文是 specs 文档结构、术语边界和文档治理规则的权威位置。00 只保留基础规范索引和对本文的引用，不重复维护编号分区、子文档、模型实践子文档、术语边界、引用纪律和写作检查细则。

## 三、specs 文档结构与术语职责

本文的权威领域是 LD Vibe Harness specs 文档编号分区、文档类型、正式规范文档格式、子文档规则、模型实践子文档规则、内部调研边界、术语边界、引用纪律和 specs 文档 Human Gate 检查。

术语边界用于约束 specs 写作中的命名一致性。涉及具体机制细节时，仍以对应机制规范为准；本文只定义机制名、中文术语和文档标题中的命名纪律。

## 四、编号分区

LD Vibe Harness specs 采用分区编号，编号本身必须表达文档在规范体系中的位置。编号分区围绕五类构成要素展开，而不是围绕文档形态展开。

| 编号段 | 类型 | 说明 |
|---|---|---|
| 00 | 理念与纲要 | 定义 LD Vibe Harness 的存在理由、第一服务对象、价值实现标准、五类构成要素和顶层治理原则 |
| 01-07 | 基础规范 | 定义 specs 文档结构与术语、目录说明、事实源、LDVH AI 协作规范、LDVH 工具、LDVH 生产对象和 LDVH 行动模型的基础规则 |
| 08-09 | 保留基础规范扩展 | 保留给后续基础规范扩展 |
| 10-39 | LDVH 生产对象规范 | 10 为生产对象集合索引，11 起为具体生产对象规范 |
| 40-69 | LDVH 行动模型规范 | 40 为行动模型集合索引，41 起为具体行动规范 |
| 70-89 | 内部调研（可选编号） | 可选编号段，用于需要纳入 specs 编号体系的内部调研文档；当前项目评估文档统一放在 specs/evals/ 子目录 |
| 90-99 | 保留 | 保留给后续扩展，不得未经确认提前占用 |
| specs/evals/ | 项目评估文档 | 承载 LD Vibe Harness 项目评估、设计探索、方案比较和经验分析，按自然序号组织 |
| specs/refs/ | 外部资料引用文档 | 承载与 LD Vibe Harness 规范体系相关的外部资料引用，按自然序号组织 |

新增、调整或占用编号段属于规范体系变更，应评估 Human Gate。

## 五、文档类型

### 5.1 正式规范文档

正式规范文档使用两位编号，格式为 NN。正式规范文档可以定义稳定规则，适用于 00-69 区间。

示例：

```text
01-specs文档结构与术语规范.md
02-LDVH目录说明.md
03-事实源边界与承载规范.md
04-LDVH-AI协作规范.md
05-LDVH工具基础规范.md
06-LDVH生产对象基础规范.md
07-LDVH行动模型基础规范.md
10-生产对象集合索引.md
40-行动模型集合索引.md
```

正式规范文档必须通过头部元信息声明定位、适用范围、上位依据和相关规范；正文必须包含解决问题、与 00 总纲的关系、核心规则、Human Gate 与检查要求和待补齐事项。00 总纲作为顶层文档，不要求声明上位依据。正式规范文档不得设置“不进入本文”“边界说明”等反向边界章节。

### 5.2 子文档

正式规范文档因内容超出单文档承载能力，或某个编号区间的上位基础规范明确要求通过子文档承接模型实践时，可以创建子文档。子文档编号格式为 NN.SS，其中 NN 为父文档编号，SS 为子文档序号。

子文档不是独立规范，而是父文档的扩展或指定区间内的模型实践承接。子文档的权威来源是父文档，子文档不得与父文档矛盾，不得重新定义父文档、基础规范或机制规范已有规则。

示例：

```text
04.01-Rules机制规范.md
04.02-Skill机制规范.md
04.03-Agent机制规范.md
```

子文档不强制采用正式规范文档的完整骨架，但必须遵守父文档定义的子文档格式，并保留父文档引用、所属范围、章节归属和待补齐标记等最小治理信息。模型实践子文档应说明自身只是生产对象或行动模型在某个机制或主题下的实践承接，不替代主文档。

### 5.3 模型实践子文档

模型实践子文档是指定编号区间内 NN.SS 子文档的一类。当前适用于 `10-39` 生产对象规范区和 `40-69` 行动模型规范区，用于承载某个生产对象或行动模型围绕 Rules、Skill、Agent、Tools、Web 等机制的实践说明。LDVH 当前不设置三段式实践文档层级。

模型实践子文档不是独立规范，不得定义新的基础规则，只能记录对应生产对象或行动模型在某个机制下实际要做什么、怎么做、输入输出、事实源回写、Human Gate、检查要求和待补齐事项。模型实践子文档的具体编号、命名和模板由对应区间的上位基础规范定义：生产对象依据 `specs/06-LDVH生产对象基础规范.md`，行动模型依据 `specs/07-LDVH行动模型基础规范.md`。

示例：

```text
11.01-Rules.md
11.04-Tools.md
41.01-Rules.md
41.02-Skill.md
41.05-Web.md
```

04、05 等基础规范区的子文档不是模型实践子文档。机制规范子文档定义机制本身的治理规则；模型实践子文档只说明某个生产对象或行动模型如何实践这些机制，不替代 Trae 实体定义文件、工具实现、机制规范或主模型。运行结果形成稳定事实时，应按事实源边界写回 specs/、docs/ 或 ldvh-base/。

### 5.4 内部调研文档

70-89 内部调研承载 LD Vibe Harness 自身的研究、设计探索和方案比较。内部调研可以成为规范、ADR 或行动模型调整的依据，但其内容不直接构成强制执行规则。

内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

当前项目评估文档统一放在 specs/evals/ 子目录，按自然序号组织。70-89 编号段为可选编号，用于需要纳入 specs 编号体系的内部调研文档。

### 5.5 索引文档

正式规范区间中，10 或 40 等编号可作为区段入口的索引文档。索引文档编号可以为 `10`、`40` 等，使用两位编号。

索引文档不定义对象字段、状态机或行动流程，只提供该区段内文档的清单、关系映射、状态和维护信息。索引文档服务于 AI 和人在进入一个区段前快速了解该区段的文档组织和现状。

示例：

```text
10-生产对象集合索引.md
40-行动模型集合索引.md
```

索引文档的权威来源是其上位规范（如 10 依据 06、40 依据 07），索引文档不得在清单之外定义新的对象或行动规则。

### 5.6 项目评估文档（evals/）

specs/evals/ 承载因 LD Vibe Harness 项目实际情况而生成的评估文档和内部参考文档，包括对外部工具、方法、框架或概念的项目级评估，以及项目内部临时参考。

项目评估文档按自然序号（01 起）组织，编号只用于排序和引用便利，不属于 specs 规范编号体系。

项目评估文档不直接构成强制执行规则。评估结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

项目评估文档应通过头部元信息声明创建日期、定位、编号归属、调研边界、执行效力、上位依据和相关规范。项目评估文档不需要 Human Gate 与检查要求章节。

### 5.7 外部资料引用文档（refs/）

specs/refs/ 承载与 LD Vibe Harness 规范体系相关的外部资料引用，用于在规范编写和内部调研时快速查阅。

外部资料引用文档按自然序号（01 起）组织，编号只用于排序和引用便利，不属于 specs 规范编号体系。

外部资料引用文档是外部资料的引用副本，不改变其非规范事实源的性质，不直接成为 LD Vibe Harness 强制规则。

外部资料引用文档应通过头部元信息声明创建日期、来源和定位。

## 六、文档骨架

### 6.1 正式规范文档骨架

正式规范文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---

## 一、本文解决的问题

## 二、与 00 总纲的关系

## 二～N-2、核心规则
（具体章节按主题组织）

注：10-39 和 40-69 区段的正式规范，可用"与直接上位基础规范的关系"替代"与 00 总纲的关系"章节标题，直接上位基础规范分别为 `specs/06-LDVH生产对象基础规范.md` 和 `specs/07-LDVH行动模型基础规范.md`。

## N-1、Human Gate 与检查要求

## N、待补齐事项
```

头部字段规则：以上字段为正式规范文档必填字段，00 总纲作为顶层文档可不声明上位依据。新增头部字段不得与已有字段语义重叠，不得在头部承载正文才应展开的规范内容。正文不得通过“不进入本文”“边界说明”等反向清单表达职责边界；职责边界应由头部定位、适用范围、上位依据、相关规范和正文正向规则共同表达。

### 6.2 子文档骨架

子文档建议采用以下骨架：

```markdown
# {子文档标题}

> 创建日期：YYYY-MM-DD
> 所属主文档：`specs/NN-xxx.md`
> 关系：父规范扩展
> 适用范围：...
> 上位依据：`specs/NN-xxx.md`

---

## 一、本文定位

## 二、父规范关系

## 三、核心规则

## 四、Human Gate 与检查要求

## 五、待补齐事项
```

父文档可以为其子文档定义更具体的格式。子文档格式不得弱化本文定义的最小治理信息，也不得设置“不进入本文”“边界说明”等反向边界章节。

### 6.3 模型实践子文档骨架

模型实践子文档建议采用以下骨架，具体生产对象或行动模型可在 06、07 约束下按实践重点调整章节：

```markdown
# {模型实践子文档标题}

> 创建日期：YYYY-MM-DD
> 所属主文档：`specs/NN-xxx.md`
> 关系：生产对象实践子文档 / 行动模型实践子文档
> 适用范围：...
> 上位依据：`specs/NN-xxx.md`
> 相关规范：...（可选）

---

## 一、本文定位

## 二、实践目标

## 三、适用场景

## 四、实践边界

## 五、实践内容

## 六、Human Gate

## 七、检查要求

## 八、待补齐事项
```

模型实践子文档不得复制父规范、主模型或机制规范的规则正文，只能引用其规则并说明该模型实际要做什么、怎么做和如何检查。

### 6.4 索引文档骨架

索引文档建议采用以下骨架：

```markdown
# {区段名称}索引

> 创建日期：YYYY-MM-DD
> 定位：...

---

## 二、索引范围

说明本索引覆盖的编号区间及其边界。

## 三、文档清单

| 编号 | 文档 | 类型 | 定位 | 状态 | 说明 |
|---|---|---|---|---|---|
| 11 | xxx | 正式规范 | ... | stable | ... |
| 12 | yyy | 正式规范 | ... | planned | ... |

## 四、对象/模型关系

说明文档之间的引用关系、依赖关系和事实源边界。

## 五、Human Gate

列出索引范围变更的相关 Human Gate 要求。

```

索引文档不得复制上位基础规范或具体对象/行动规范的规则正文。

## 七、术语边界

术语边界的目标是避免同一词语在 specs 中同时指代 Trae 机制、规范条款、对象规则、行动条件或普通能力，导致事实源和执行边界混淆。

### 7.1 机制英文专名

LDVH specs 中，英文机制名 Rules、Skill、Agent、Tools、Web 专指 Trae 或 LDVH 工具体系中的机制层：

| 术语 | 含义 | 机制规范 |
|---|---|---|
| Rules | Trae Rules 机制 | `specs/04.01-Rules机制规范.md` |
| Skill | Trae Skill 机制 | `specs/04.02-Skill机制规范.md` |
| Agent | Trae Agent 机制 | `specs/04.03-Agent机制规范.md` |
| Tools | LDVH `tools/` Tools 辅助机制 | `specs/05.01-Tools辅助规范.md` |
| Web | LDVH `web/` Web 展示机制 | `specs/05.02-Web展示规范.md` |

提到上述机制时，应使用英文专名 Rules、Skill、Agent、Tools、Web，不使用裸中文“规则”“技能”“代理”“智能体”“程序”“展示”替代。

### 7.2 中文术语必须加定语

中文“规则”“技能”“代理”“智能体”“程序”“展示”等词不得裸用，除非上下文已经通过标题、表格字段或段落首句明确限定其语义。

推荐用法如下：

| 场景 | 推荐术语 | 不推荐裸用 |
|---|---|---|
| specs 中定义的稳定条款 | 规范规则 | 规则 |
| 生产对象字段、状态、验收、检查 | 对象规则、字段规则、状态规则、验收规则、检查规则 | 规则 |
| 行动模型的 Context、Scenario、Gate、流程、回写、证据 | 行动规则、Scenario 识别条件、行动进入条件、Gate 条件、回写要求 | 规则、触发规则 |
| 普通能力说明 | 能力、功能、流程、方法 | 技能 |
| AI 泛称 | AI 执行者、AI 代理能力、子代理能力 | Agent、代理、智能体 |
| 确定性工具辅助 | Tools 辅助、Tools 适配、Tools 能力 | 程序、程序辅助 |
| Web 展示能力 | Web 展示、Web 适配、Web 展示层 | 展示 |
| Trae / LDVH 机制适配 | Rules 适配、Skill 适配、Agent 适配、Tools 适配、Web 适配 | 规则适配、技能适配、代理适配、程序适配、展示适配 |

### 7.3 模型实践子文档命名中的机制名

生产对象和行动模型的 `NN.01` 至 `NN.05` 模型实践子文档必须使用机制英文专名：

| 模型实践子文档 | 机制含义 | 不承载内容 |
|---|---|---|
| `NN.01-Rules.md` | Rules 模型实践子文档 | 不承载对象规则、行动规则、Scenario 完整识别条件或完整 SOP |
| `NN.02-Skill.md` | Skill 模型实践子文档 | 不承载普通能力说明，不替代行动流程或对象规范 |
| `NN.03-Agent.md` | Agent 模型实践子文档 | 不承载泛化 AI 代理说明，不替代 Agent 定义摘要或 Trae 平台实体 |
| `NN.04-Tools.md` | Tools 模型实践子文档 | 不承载业务事实，不替代 Tools 实现或事实源 |
| `NN.05-Web.md` | Web 模型实践子文档 | 不承载 UI 状态作为事实源，不替代 Web 实现 |

对象自身的字段规则、状态规则、验收规则和实例检查要求应留在 `NN` 主文件。行动自身的 Context、Scenario、Gate、执行流程、回写要求和证据要求应留在 `NN` 主文件。Tools 适配和 Web 适配只说明机制接入边界，不承载具体实现代码。

### 7.4 Scenario 与 Rules 的边界

行动模型判断何时进入某行动时，应使用“Scenario 识别条件”或“行动进入条件”。

Rules 可以通过短摘要提醒 AI 评估某个 Scenario，但不应在 Rules 模型实践子文档中维护完整 Scenario 识别条件、角色矩阵、报告模板、执行流程或对象规则。

### 7.5 术语变更治理

以下情况应评估 Human Gate：

1. 改变 Rules、Skill、Agent、Tools、Web 的机制名含义;
2. 将中文“规则”“技能”“代理”“智能体”“程序”“展示”等裸用词提升为正式术语;
3. 改变 `NN.01` 至 `NN.05` 模型实践子文档的机制含义;
4. 将 Scenario 识别条件、行动流程或对象规则转移到 Rules 模型实践子文档;

## 八、引用纪律

引用纪律的本质是事实源单一性在文档体系中的体现——同一个规则只能在一份文档中定义，其他文档只能指向它，不能复制它。

1. 权威唯一：每项稳定规则只能有一个权威定义位置。其他文档需要使用该规则时，只能写“依据 XX §Y”，不得复制、改写或另行定义同义规则；
2. 职责表达：判断规则权威位置时，优先依据文档头部定位、适用范围、上位依据、相关规范和正文正向规则，而不是依据反向边界清单、文档出现顺序、引用次数或描述详细程度；
3. 上位约束：00 定义体系理念、价值标准、构成要素和顶层治理原则；01 定义 specs 文档结构、术语边界和治理规则；02 定义项目目录规划；03 定义事实源边界与承载规则；04 定义 LDVH AI 协作规范基础规则；05 定义 LDVH 工具基础规则；06 定义 LDVH 生产对象基础规则；07 定义 LDVH 行动模型基础规则；10-39 定义具体生产对象规则；40-69 定义具体行动模型规则；70-89 和 specs/evals/ 只提供内部调研，不直接构成强制规则；specs/refs/ 只提供外部资料引用，不直接成为强制规则；
4. 适配不重写：生产对象、行动模型、场景实践或工具说明引用基础规范时，只能说明如何适配，不能重新定义基础规则；
5. 冲突处理：当两个文档对同一规则给出不同表述时，应先判断该规则的权威领域；非权威文档应改为引用权威文档，不能保留并列规则；
6. 调研升级：70-89 或 specs/evals/ 内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

## 九、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增 specs 编号段或改变编号体系；
2. 重命名或重排 specs 文档；
3. 改变子文档或模型实践子文档层级关系；
4. 子文档或模型实践子文档重新定义父规范已有原则；
5. specs 文档引用 specs 外部文档作为规范依据；
6. 模型实践子文档新增或扩张基础规范；
7. 将 70-89 或 specs/evals/ 内部调研结论直接作为强制规则使用；
8. 新增或重排索引文档，改变索引范围或文档归属；
9. 索引文档定义新的对象字段、状态机或行动规则；
10. 改变本文定义的术语边界或机制名含义。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

specs 文档写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 除 00 总纲外，正式规范文档已声明上位依据；子文档、模型实践子文档和索引文档已声明对应上位依据 |
| 职责表达 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 文档类型 | 文档编号和骨架符合正式规范、子文档、模型实践子文档或索引文档类型 |
| 反向边界 | 未设置“不进入本文”“边界说明”等反向边界章节 |
| 术语边界 | Rules、Skill、Agent、Tools、Web 使用英文机制名；中文“规则”“技能”“代理”“智能体”“程序”“展示”等词已加定语或上下文限定 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、生产对象和行动模型术语一致 |
| 目录规划一致性 | 与 `specs/02-LDVH目录说明.md` 的目录规划一致 |
| 事实源边界一致性 | 与 `specs/03-事实源边界与承载规范.md` 的事实源边界一致 |
| 索引一致性 | 索引文档的清单与对应区段实际文档一致，且未在清单之外定义规则 |
