## 1. 本文定位

本文定义 Evidence 事实模型使用的结构化数据契约。本文解决 Evidence YAML 实例应包含哪些字段、字段类型和约束是什么、文件命名规则是什么、状态流转契约是什么，以及工具实现应如何消费本契约的问题。

本文是 Evidence 事实模型契约字段的权威位置。本文是 `specs/29-Evidence-验证证据.md` 的附件型契约子文档，不是独立事实模型。本文不得重新定义 Evidence 的对象定位、准入条件、状态机语义、Human Gate、事实源回写或证据留存要求。发生冲突时，以 29 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款（依据 `specs/04-LDVH模型子文档规范.md` §7.1）。

## 2. Evidence YAML Schema

### 2.1 基础字段

Evidence 基础字段遵循 `specs/13-LDVH事实模型基础规范.md` §7.3 的字段契约原则，所有事实模型应包含基础字段。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | Evidence 对象 ID，格式为 `ev-{NNNN}` |
| `type` | string | 是 | 固定为 `evidence` |
| `title` | string | 是 | 证据标题 |
| `status` | string | 是 | Evidence 状态，必须属于标准状态枚举 |
| `created` | date | 是 | 对象创建日期 |
| `updated` | date | 是 | 最近更新日期 |

### 2.2 扩展字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `evidence_type` | string | 是 | 证据类型：`verification`、`execution`、`closure`、`review` |
| `source_task` | string | 否 | 关联 Task ID |
| `source_adr` | string | 否 | 关联 ADR ID |
| `verification_method` | string | 是 | 验证方法 |
| `verification_result` | string | 是 | 验证结论：`pass`、`fail`、`partial` |
| `content` | string | 是 | 证据内容或摘要 |
| `artifact_path` | string | 否 | 附件路径（截图、日志文件等） |

### 2.3 完整 YAML 示例

```yaml
id: ev-0001
type: evidence
title: Core Loop Skill 验证通过
status: verified
created: 2026-06-03
updated: 2026-06-03
evidence_type: verification
source_task: task-0001
source_adr:
verification_method: npm run lint && npm test
verification_result: pass
content: lint 无错误，12 个测试全部通过
artifact_path:
```

---

## 3. 字段约束

1. `status` 必须属于 Evidence 标准状态枚举：`candidate`、`verified`、`archived`；
2. `type` 必须固定为 `evidence`；
3. `evidence_type` 必须属于证据类型枚举：`verification`、`execution`、`closure`、`review`；
4. `verification_result` 必须属于验证结论枚举：`pass`、`fail`、`partial`；
5. `source_task` 和 `source_adr` 至少填写一个；
6. `source_task` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
7. `source_adr` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
8. `id` 格式必须为 `ev-{NNNN}`，编号固定 4 位，从 `0001` 起递增；
9. `created` 和 `updated` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）。

---

## 4. 文件命名契约

Evidence 实例文件命名规则：

```text
ev-{NNNN}-short-title.yaml
```

约束：

1. 编号从 `0001` 起递增，固定 4 位；
2. 英文短标题使用小写短横线命名；
3. 每个项目独立编号，不使用跨项目全局编号；
4. 文件存放位置为 `ldvh-base/evidence/`；
5. 文件名变化必须同步检查所有引用该 Evidence 的 `related_evidence` 和其他关联字段。

## 5. 状态流转契约

Evidence 状态语义和流转规则由 `specs/29-Evidence-验证证据.md` §5 定义，本文只提供结构化枚举和流转矩阵供 Tools 校验消费。

### 5.1 标准状态枚举

| 标准状态 |
|---|
| `candidate` |
| `verified` |
| `archived` |

状态含义依据 `specs/29-Evidence-验证证据.md` §5.1。

### 5.2 合法状态流转

| 当前状态 | 可流转至 |
|---|---|
| `candidate` | `verified` |
| `verified` | `archived` |
| `archived` | 无 |

流转语义和约束依据 `specs/29-Evidence-验证证据.md` §5.2。

## 6. 契约消费声明

1. Tools 辅助程序解析 Evidence 时应依据本文定义的 YAML schema 和字段约束，不得自行扩张格式契约（依据 `specs/12.01-Tools辅助规范.md` §6.1）；
2. Tools 辅助程序校验 Evidence 时应覆盖字段完整性、状态合法性、条件必填和引用有效性；
3. Tools 辅助程序读取 Evidence 时可依据本文状态枚举和字段契约执行状态筛选、详情解析和关联字段解析，但 Evidence 读取结果是否可作为当前执行依据由 29 主文档和 Skill 流程判断；
4. 实践子文档和工具可以消费本文契约，但不得复制维护契约字段第二事实源（依据 `specs/04-LDVH模型子文档规范.md` §7.2）；
5. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 `specs/04-LDVH模型子文档规范.md` §7.3）（依据 specs/22-Change-变更记录.md）；
6. 契约子文档应先于工具实现创建，工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束（依据 `specs/04-LDVH模型子文档规范.md` §7.4）；
7. 本文契约变更时，消费本文的 Tools 实现和对应测试必须同步更新（依据 `specs/04-LDVH模型子文档规范.md` §7.4、§8）。

## 7. 检查项

检查本文是否被正确使用时，应确认：

1. Evidence YAML 实例字段是否完整，必填字段是否齐全；
2. `status` 是否属于标准状态枚举；
3. `type` 是否固定为 `evidence`；
4. `evidence_type` 是否属于证据类型枚举；
5. `verification_result` 是否属于验证结论枚举；
6. `source_task` 和 `source_adr` 是否至少填写一个；
7. `source_task` 引用的事实模型 ID 是否有效；
8. `source_adr` 引用的事实模型 ID 是否有效；
9. 文件命名是否符合 `ev-{NNNN}-short-title.yaml` 格式；
10. 状态流转是否合法，是否存在非法流转；
11. 终态 Evidence 是否存在重开情况；
12. 工具实现是否依据本文 schema 解析和校验，未自行扩张格式契约；
13. 修改本文是否记录 Change，并在必要时触发 Human Gate（依据 specs/22-Change-变更记录.md）
