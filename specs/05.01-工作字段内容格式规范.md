## 1. 本文解决的问题

本文回答 LDVH 工作模型工作对象中的公共字段语义边界和字段内容格式，尤其是 YAML 工作对象和 Study Markdown frontmatter 中的长文本字段，应采用什么格式书写、被 Web 如何语义化渲染、被 Code 如何校验。本文定义公共字段的语义边界（每个字段回答什么问题、不应该写什么、适合使用哪类内容格式），具体工作模型规范定义对象特有字段契约。本文不定义具体工作模型是否拥有某字段、字段是否必填、状态条件必填、对象状态机或工作模型准入条件，这些仍由 `specs/05-工作模型基础规范.md` 和 20-39 具体工作模型规范负责；Change 的字段契约映射为 commit message，不使用 YAML 字段内容格式。

## 2. 与 00、05 和 09 的关系

00 将工作模型定义为 LDVH 五类构成要素之一。`specs/05-工作模型基础规范.md` 定义工作模型字段契约和事实实例边界，是本文的直接上位依据。`specs/09-事实源边界与承载规范.md` 定义 Markdown 和 YAML 的承载分工原则：

- Markdown 更适合承载背景、原因、解释、设计语境、长文本内容；
- YAML 更适合承载工作计划、状态、结构化关系、审计字段和需要工具解析的事实。

本文在工作模型字段内容格式范围内承接这一分工，进一步规定：除 Change 外，YAML 工作模型工作对象中的长文本字段，其内容可以使用 Markdown 语义书写。Markdown 是字段内容格式，不是新事实源。YAML 或对应具体工作模型声明的事实源仍是权威事实源，Web 和 Code 是派生视图。本文不作为 09 的子文档，也不重新定义 09 的事实源边界。

## 3. 内容格式类型

LDVH 工作模型字段内容分为以下六种格式类型。格式类型不是独立工作模型，不具备独立生命周期、状态机或关闭条件，而是字段内容的书写和消费规则。

### 3.1 Narrative / 叙述说明

适合字段：`description`、`notes`、`context`、`success_criteria`、`constraints`、`rationale`

用途：说明背景、问题、目标、范围、约束。

书写规则：

1. 允许使用 Markdown 标题、段落、列表、引用、代码块、表格、链接；
2. 不强制 checklist；
3. 推荐使用 `## 背景`、`## 目标`、`## 边界` 等标题结构提升可读性；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
description: |
  ## 背景

  当前 Web 呈现中长文本字段缺少统一格式规范。

  ## 目标

  建立工作字段内容格式规范，统一 AI 写入、Web 渲染和 Code 校验。
```

### 3.2 Checklist / 检查清单

适合字段：`acceptance`

用途：完成标准、关闭检查项、质量门禁。

书写规则：

1. 必须使用 `- [ ]`（未完成）或 `- [x]`（已完成）格式；
2. 每项必须是可独立验证的原子条件；
3. 不应包含非 checklist 内容；如需补充说明，放在 checklist 项的文本中；
4. YAML 中应使用块标量 `|` 承载；
5. 具体工作模型若把 Checklist 字段声明为关闭条件，关闭前所有检查项必须标记为 `- [x]`。

示例：

```yaml
acceptance: |
  - [ ] 建立字段内容格式规则
  - [ ] 定义六种内容格式的边界和书写规则
  - [ ] 明确 Code 校验消费规则
  - [ ] 运行事实源校验通过
```

### 3.3 验证证据

适合字段：`verification`、`closure_evidence`

用途：记录验证过程、命令、结果和结论。

书写规则：

1. 应包含验证结果和结论；
2. 可包含验证命令、关键输出、文件路径；
3. 不建议贴超长日志，应摘要关键信息；
4. YAML 中应使用块标量 `|` 承载；
5. 具体工作模型若把验证证据字段声明为关闭条件，进入关闭状态前对应字段不得为空。

#### 3.3.1 Human Gate 记录承载

涉及 Human Gate 的验证证据字段，可以嵌入 `Human Gate 记录：` 文本块。该记录应符合 `specs/06-工作流程基础规范.md` §6.3.1 的最小证据结构，并可被 `code/specs_validate.py human-gate` 检查。

Human Gate 记录进入 `closure_evidence`、ADR `context` / `consequences`、工作流程结果、Memo 或其他事实源字段时，只作为对应字段中的证据片段，不创建独立验证证据对象，也不得替代对象状态机、决策正文、验证结论或 Change / commit 追溯。

示例：

```yaml
closure_evidence: |
  ## 验证结果

  通过。

  ## 验证命令

  ```bash
  python3 code/fact_validate.py ldvh-base/
  ```

  ## 结论

  工作满足验收条件。
```

### 3.4 Decision / 决策记录

适合字段：`decision`、`consequences`

用途：记录决策选择、理由和影响。

书写规则：

1. 应明确"选择了什么"和"为什么"；
2. 应区分已决策和未决策内容；
3. 如决策会改变事实源边界，应进入 ADR；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
decision: |
  采用 YAML 字段内 Markdown 作为内容格式方案。

  ## 理由

  - 不改变事实源边界
  - 兼容现有 Validator
  - Web 改造成本较低
```

### 3.5 Reference / 引用索引

适合字段：`related_docs`、`deliverables`、`affected_docs`

用途：记录引用路径、关联对象和外部资料。

书写规则：

1. 列表元素应为字符串路径或对象 ID；
2. 内部路径应可被 Code 校验存在性；
3. 外部链接使用完整 URL；
4. 这些字段通常是 list 类型，不是 Markdown 文本。

示例：

```yaml
related_docs:
- specs/03-文档基础规范.md
- specs/09-事实源边界与承载规范.md
deliverables:
- specs/05.01-工作字段内容格式规范.md
```

### 3.6 Log / 过程记录

适合字段：`transition_reasons`、执行过程摘要

用途：追踪过程、记录关键节点和后续观察。

书写规则：

1. 适合时间线或过程记录；
2. 不一定是最终结论；
3. 应避免变成无结构流水账；
4. YAML 中应使用块标量 `|` 承载。

## 4. 公共字段语义定义

本节定义跨工作对象共享的公共字段语义边界。每个公共字段明确：回答什么问题、不应该写什么、适用方式和内容格式。各具体工作模型规范定义对象特有字段契约，公共字段引用本节。

### 4.1 全局公共字段

以下字段所有工作对象在采用时 SHALL 遵循统一语义；Change 的公共字段语义由 `specs/27-Change-变更.md` 的 commit message 字段契约承载：

| 字段 | 回答什么问题 | 不应该写什么 | 内容格式 |
|------|------------|------------|---------|
| `id` | 唯一标识 | 描述性内容 | string |
| `type` | 对象类型 | 描述性内容 | enum |
| `title` | 一句话概括 | 详细说明、验证方法、状态变化 | string |
| `status` | 当前状态 | 状态变化历史、变更原因 | enum |
| `created` | 创建时间 | 修改时间 | datetime |
| `updated` | 最后更新时间 | 创建时间 | datetime |
| `description` | 这个对象是什么、为什么存在 | 验证方法、风险说明、约束条件、验收标准、状态变化 | Narrative |

`description`（描述）是所有对象的核心叙述字段，只承载对象的背景、目标和范围说明。以下内容不应写入 `description`，应写入对应字段：

- 验证方法 → `verification`（验证）或 `acceptance`（验收标准）
- 风险说明、约束条件、降级方式 → `constraints`（约束）或 `notes`（备注）
- 验收标准 → `acceptance`（验收标准）
- 状态变化历史、前后状态、修改原因和执行者 → Git commit / Change 派生记录

### 4.2 部分公共字段

以下字段在被具体工作模型采用时 SHALL 遵循统一语义。本文只定义公共语义和内容格式，不规定具体工作模型是否必须采用这些字段。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `source` | 这个对象的输入来源 | 一般关联、验证结论 | 需要记录输入来源的对象 | Reference / Narrative |
| `source_detail` | 输入来源的说明、触发问题或原始输入摘要 | 一般关联清单、状态变化历史 | 需要补充来源上下文的对象 | Narrative / Reference |
| `acceptance` | 完成的判断条件 | 验证方法、风险说明、背景 | 需要验收检查的对象或执行项 | Checklist |
| `verification` | 怎么验证完成 | 风险说明、约束条件、背景说明 | 需要记录验证方式或验证结果的对象 | 验证证据 |
| `closure_evidence` | 关闭时的证据 | 验收标准、风险说明 | 需要关闭证据的对象 | 验证证据 |
| `completion_evidence` | 计划关闭时的证据 | 验收标准、风险说明 | 需要计划级关闭证据的对象 | 验证证据 |
| `closed_at` | 关闭时间 | 创建时间、更新时间 | 需要关闭时间的对象 | datetime |
| `archive_reason` | 为什么归档 | 归档后的内容、验证 | 需要归档原因的对象 | Narrative |
| `discard_reason` | 为什么废弃 | 废弃后的说明、验证 | 需要废弃原因的对象 | Narrative |
| `blocked_by` | 前置依赖 | 后续依赖、一般关联 | 需要记录前置依赖的对象或执行项 | Reference |
| `notes` | 其他字段无法承载的补充说明 | 核心信息、验证方法、决策 | 需要补充说明的对象 | Narrative |

工作对象不得手写维护 `status_history`。状态变化历史、前后状态、修改原因和执行者由 Git commit / Change 派生；需要长期保留的语义转折应写入对象专用字段、证据字段或相关工作对象，不得用手写状态历史形成第二事实源。

`verification`（验证）只承载验证计划、验证命令、验证结果和验证结论。以下内容不应写入 `verification`，应写入对应字段：

- 风险说明、约束条件、降级方式 → `description`（描述）或 `notes`（备注）
- 背景说明 → `description`（描述）
- 验收标准 → `acceptance`（验收标准）

### 4.3 引用字段语义边界

引用字段分为两类：来源引用（`source_*`）和关联引用（`related_*`）。

**来源引用 `source_*`**：本对象的输入来源。如果某个对象是创建本对象的直接原因或输入，应放入 `source_*`。

**关联引用 `related_*`**：与本对象有关联的其他对象。如果某个对象只是与本对象有关联但不是直接输入来源，应放入 `related_*`。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `related_docs` | 引用的文档路径 | 对象 ID 引用 | 需要关联文档的对象 | Reference |
| `related_adrs` | 关联的决策记录 | 来源决策（用 source_*） | 需要关联 ADR 的对象 | Reference |
| `related_memos` | 关联的备忘 | 来源备忘（用 source_memos） | 需要关联 Memo 的对象 | Reference |
| `related_studies` | 关联的研究报告 | 报告正文或研究过程 | 需要关联 Study 的对象 | Reference |
| `related_changes` | 关联的变更 commit | 非变更关联 | 需要关联 Change 的对象 | Reference |
| `related_workareas` | 关联的工作域 | 所属工作域（用归属字段） | 需要关联 WorkArea 的对象 | Reference |
| `related_taskplans` | 关联的任务计划 | 所属任务计划（用归属字段） | 需要关联 TaskPlan 的对象 | Reference |
| `related_pitfalls` | 关联的踩坑经验 | 来源踩坑经验 | 需要关联 Pitfall 的对象 | Reference |
| `related_rules` | 关联的规范路径 | 一般文档引用（用 related_docs） | 需要关联规范或能力路径的对象 | Reference |
| `superseded_by` | 替代本对象的新对象 | 一般关联 | 需要替代关系的对象 | Reference |
| `source_objects` | 本对象的来源对象 | 一般关联（用 related_*） | 需要记录对象来源的对象 | Reference |
| `source_memos` | 本对象的来源备忘 | 一般备忘关联（用 related_memos） | 需要记录备忘来源的对象 | Reference |
| `source_docs` | 本对象的输入资料或来源文档路径 | 后续引用文档（用 related_docs） | 需要记录来源资料路径的对象 | Reference |

判断规则：

1. 如果引用是本对象的直接输入来源，放入 `source_*`；如果只是一般关联，放入 `related_*`。
2. 如果引用是本对象的所属容器，使用具体工作模型规范定义的专属归属字段，不放入 `related_*`。
3. 如果引用是替代本对象的新对象，使用 `superseded_by`，不放入 `related_*`。
4. 如果引用是文档路径，使用 `related_docs`；如果是规范、Rules、Skill、Code 或 Web 路径，使用 `related_rules`。

## 5. 公共字段到内容格式的映射

本节登记需要被 AI、Code 或 Web 按语义消费的公共字段内容格式。`id`、`type`、`title`、`status`、`created`、`updated` 等基础字段的完整字段契约，以 20-39 具体工作模型规范为准；本文不重复维护具体工作模型的完整字段清单。

05.01 中的字段映射只说明“某字段若被具体工作模型采用，应按什么内容格式书写和消费”。字段是否存在、是否必填、是否在某状态下必填，以及是否参与关闭条件，由具体工作模型规范定义。

## 6. Web 语义化渲染消费规则

Web 端应根据字段内容格式选择渲染组件，而不是一律按普通 Markdown 渲染。Web 渲染是派生视图，不得回写事实源。

### 6.1 渲染映射

| 内容格式 | Web 渲染组件 | 说明 |
|---|---|---|
| 叙述说明（Narrative） | SummaryText | Markdown 正文，支持摘要/展开 |
| 检查清单（Checklist） | ChecklistCard | 检查清单，显示完成比例和每项状态 |
| 验证证据 | EvidenceBlock | 验证证据区，突出命令、路径和结果 |
| 决策记录（Decision） | SummaryText / 决策区块 | 决策内容，按 Markdown 渲染 |
| 引用索引（Reference） | ReferenceCard / DocPreviewLink | 引用卡片或文档预览链接 |
| 过程记录（Log） | SummaryText / 时间线 | 过程记录，按 Markdown 或时间线渲染 |

### 6.2 当前 Web 字段分类

当前 Web 字段内容格式分类由 `web/src/utils/fieldFormats.ts` 维护，`ObjectDetail.tsx` 和右侧扩展阅读面板应共同消费同一组规则，避免详情页和扩展区出现不同语义渲染。

```text
SUMMARY_TEXT_FIELDS → 叙述说明 / 决策记录 / 过程记录
  description, source, context, consequences, success_criteria, constraints,
  rationale, observation, analysis, mitigation, resolution, decision,
  symptoms, trigger_conditions, root_cause, avoidance, applicability,
  governance_scope, archive_reason, discard_reason, notes, transition_reasons,
  alternatives, reason,
  scope, impact, summary, details, outcome, next_steps,
  lessons, background, motivation

CHECKLIST_COMPAT_FIELDS → 可兼容检查清单的 Markdown 字段
  success_criteria, constraints, verification,
  trigger_conditions, avoidance, next_steps

EVIDENCE_FIELDS → 验证证据
  verification, closure_evidence, completion_evidence, evidence

REFERENCE_FIELDS → 对象 ID 引用
  workarea, workplan, blocked_by, execution_items,
  related_workareas, related_workplans,
  related_adrs, related_memos, related_pitfalls,
  source_memos, source_objects,
  related_objects, superseded_by, resolved_to

DOC_LINK_FIELDS → 文件路径或 URL 引用
  related_docs, deliverables, affected_docs, related_rules, affects,
  superseded_by
```

Web 渲染顺序应为：明确属于检查清单的字段优先进入 `ChecklistCard`；兼容检查清单的字段只有在内容包含 `- [ ]` / `- [x]` 时进入 `ChecklistCard`；验证证据字段进入 `EvidenceBlock`；叙述说明、决策记录和过程记录字段进入 `SummaryText` 并按 Markdown 渲染；对象 ID 引用进入 `ReferenceCard`；文件路径或 URL 引用进入 `DocPreviewLink`。非对象 ID 的变更引用（如 commit hash）可作为引用标签展示，不应误用对象详情跳转。

当前 Web 可点击对象引用只应覆盖已有对象路由支持的工作对象类型。尚未进入当前对象路由的引用只能作为普通引用文本展示，不得跳转到无效详情页。

### 6.3 Web 边界约束

1. Web 展示的事实以 Git 文件事实源为准；
2. 摘要、折叠、渐进展开只能是展示层派生结果，不得回写到 YAML；
3. YAML 原文折叠区作为事实完整性兜底展示；
4. Web 不得在 UI 中另建权威事实；
5. 如需长期保存 Web 生成的总结，应创建 Memo；除 `specs/08-Web信息同步实现规范.md` §8.2 明确白名单外，Web 不得更新其他对象字段。

## 7. Code 校验消费规则

Code 应根据字段内容格式执行不同级别的校验。本文只定义校验方向，具体校验逻辑由 `code/fact_validate.py` 实现。

### 7.1 必须校验（error）

| 范围 | 字段 | 校验规则 |
|---|---|---|
| 被具体工作模型声明为关闭条件的 Checklist 字段 | `acceptance` 或等价字段 | 非空；如包含文本但不符合 `- [ ]` / `- [x]` 格式，报 error |
| 被具体工作模型声明为关闭条件的验证证据字段 | `closure_evidence`、`completion_evidence` 或等价字段 | 不得为空 |
| 被具体工作模型声明为关闭时间的字段 | `closed_at` 或等价字段 | 不得为空 |
| Memo（resolved） | `resolved_to`、`resolved_at` | 不得为空 |
| Memo（discarded） | `discard_reason` | 不得为空 |

### 7.2 建议校验（warning）

| 范围 | 字段 | 校验规则 |
|---|---|---|
| Checklist 字段 | `acceptance` 或等价字段 | 包含文本但不符合 checklist 格式时提示 |
| 所有 | 长文本字段 | 包含冒号、换行但未使用 YAML 块标量 `|` 时提示 |

### 7.3 暂不校验

| 对象 | 字段 | 说明 |
|---|---|---|
| 所有 | Narrative 字段 | Markdown 语法正确性暂不校验 |
| 所有 | 内部路径 | 路径存在性校验待后续增强 |
| 所有 | 外部链接 | URL 可达性不校验 |
| 所有 | HTML 内容 | 危险 HTML 暂不拦截，待后续增强 |

### 7.4 当前 Validator 现状

`code/fact_validate.py` 当前已实现一部分字段内容格式检查能力：

- Checklist 字段格式校验（warning 级别）；
- 部分关闭证据字段和关闭时间字段必填校验（error 级别）；
- Memo resolved 状态 `resolved_to` 和 `resolved_at` 必填校验（error 级别）；
- Memo discarded 状态 `discard_reason` 必填校验（error 级别）；
- 长文本 YAML 块标量提示（YAML 解析失败时的建议信息）。

暂未实现：

- Narrative 字段 Markdown 语法校验；
- 内部路径存在性校验；
- 危险 HTML 拦截；
- 验证证据字段格式校验；
- Decision 字段结构校验。
- Git / Change 派生状态历史和 `related_changes` 字段的专门校验。
- WorkArea、WorkPlan、ADR、Memo 和 Pitfall 当前新增字段的专门校验。

## 8. AI 写入规则

AI 创建或更新工作对象时，应遵守以下写入规则：

### 8.1 长文本字段优先使用 YAML 块标量

以下字段如包含中文标点、英文冒号、换行、命令、列表式说明或超过一短句，应优先使用 YAML 块标量 `|`：

- 叙述说明字段：`description`、`context`、`summary`、`details`、`background`、`motivation`、`scope`、`constraints`、`notes`
- 检查清单字段：`acceptance`、`success_criteria`、`next_steps`、`avoidance`、`trigger_conditions`
- 验证证据字段：`verification`、`closure_evidence`、`completion_evidence`、`evidence`、`outcome`
- 决策字段：`decision`、`consequences`、`alternatives`、`rationale`
- 过程记录字段：`transition_reasons`、`lessons`、`archive_reason`、`discard_reason`

不得把包含冒号的长文本直接写成未加引号的普通单行字符串。

### 8.2 Checklist 字段必须使用检查列表格式

Checklist 字段必须使用 `- [ ]` 检查列表格式，将验收标准拆解为可独立验证的原子检查项。

### 8.3 验证证据字段应包含验证结果和结论

`verification` 和 `closure_evidence` 应包含验证结果和结论，可包含验证命令和关键输出。

### 8.4 不自行添加未定义字段

AI 不得在工作对象中添加对象规范未定义的字段。如需新增字段，应先更新对应对象规范。

## 9. 事实源边界

1. 工作对象文件仍是权威事实源；多数对象为 YAML，Study 为 Markdown frontmatter，Change 由 Git commit 记录承载。Markdown 可以是字段内容格式，也可以按 Study 规范作为报告正文承载格式；
2. Web 渲染、摘要、折叠、预览都是派生视图，不得替代事实源；
3. 不引入外部 `.md` 正文文件作为工作对象内容引用机制；
4. 如未来需支持外部 Markdown 正文引用，应另建 ADR 决策，不得在本文中预设；
5. 格式类型（Narrative / Checklist / 验证证据 / Decision / Reference / Log）不是独立工作模型，不具备独立生命周期、状态机或关闭条件。

## 12. Human Gate 与检查要求

本文变更属于规范体系变更，应评估 Human Gate。以下变更需要 Human Gate：

1. 新增或删除内容格式类型；
2. 改变字段到内容格式的映射；
3. 改变 Code 校验级别（error / warning / 不校验）；
4. 改变 Web 渲染映射；
5. 改变事实源边界声明。
