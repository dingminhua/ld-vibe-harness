# 管辖项目文档边界规范

> 创建日期：2026-06-08
> 定位：定义 LDVH 读取、引用或受控修改管辖项目自有文档时的边界，以及项目入口文档、项目正文文档、项目内部资料、外部资料、文档吸收和文档与工作对象关系
> 适用范围：所有接入 LDVH 的管辖项目中需要被 LDVH 读取、引用或受控修改的项目文档；LDVH 自身作为 dogfood 管辖项目时的根 README 文档和项目资料文档
> 上位依据：`specs/03-文档基础规范.md`
> 相关规范：`specs/00-LD-Vibe-Harness理念与纲要.md`、`specs/02-术语规范.md`、`specs/04.02-LDVH能力保障规范.md`、`specs/07-Code确定性执行实现规范.md`

---
## 1. 本文解决的问题

本文是管辖项目自有文档被 LDVH 读取、引用或受控修改时的边界规范。项目可以使用 `docs/`、根 README 或其它项目约定位置承载文档；LDVH 不因项目被登记为管辖项目而默认接管、初始化、迁移、重排或强制校验用户 docs。

安装 LDVH 的用户项目不默认创建 `specs/` 或 `specs/`。用户项目的生产资料、内部分析和外部引用由项目自身约定管理；LDVH 规范由 LDVH 自身 `specs/` 提供，通过规范落地要求和环境适配映射转化为用户项目可消费的适配措施。

---

## 2. 项目自有文档边界

### 2.1 默认不接管

设置管辖项目后的默认变化不包括接管用户 docs。LDVH 默认只登记项目、建立或检查 LDVH 工作对象事实源目录，并通过 Web 或等价 Human-facing 入口向用户展示接入结果、缺口和后续动作。

LDVH 只有在以下情况才读取、引用或受控修改项目文档：

1. 用户明确要求处理项目文档；
2. 当前 Task、ADR、Memo、Pitfall、Change 或其它工作对象引用了项目文档；
3. 项目 README、项目约定或 Human 指令要求读取特定文档；
4. 受控写入已通过 Human Gate；
5. Code 或人工检查只读验证项目文档与当前任务的关系。

### 2.2 常见文档位置

项目自有文档常见位置如下，但 LDVH 不要求管辖项目必须采用这些目录：

```text
README.md       项目入口文档
docs/           项目正文文档
docs/studies/   项目内部分析、方案评估和复盘
docs/sources/    项目外部调研、第三方资料和引用副本
```

项目文档不是 LDVH 规范事实源。项目文档可以承载项目资料、设计说明、需求文档、报告和操作说明，但不得替代工作对象状态、验收、关闭证据或结构化关系。

### 2.3 项目正文文档

项目正文文档承载已经被项目采纳、可以作为管辖项目资料事实源的稳定文档。若项目采用 `docs/`，则 `docs/` 根目录可作为项目正文区；若项目采用其它位置，应按项目约定和用户指令定位。

项目正文文档可以包含：

1. 需求文档、PRD、用户故事和产品说明；
2. 技术设计、架构说明、接口说明和实现说明；
3. 操作说明、部署说明、运行手册和维护说明；
4. 检查报告、验收报告、复盘报告和其他项目报告；
5. 被项目采纳的路线、方案、背景说明和资料汇总。

项目正文文档可以被 WorkArea、TaskPlan、Task、SubTask、ADR、Memo、Change、Pitfall 等工作对象引用，但不得替代这些对象的权威字段和状态机。

### 2.4 项目内部资料

当项目采用 `docs/studies/` 或等价内部资料目录时，该目录承载管辖项目内部分析、方案评估、设计比较、复盘和临时判断。

项目内部资料规则：

1. 内部资料可以引用项目正文文档作为分析依据；
2. 内部资料结论必须按本文 §5 吸收后，才可成为项目稳定事实；
3. 内部资料来源应指向被评估材料、用户输入、会议记录、项目资料、外部资料或其他真实输入，不得只指向关联 Task；
4. 内部资料可以登记相关 WorkArea、TaskPlan、Task、ADR、Memo 或其他工作对象；该登记不得替代来源；
5. 内部资料不得替代 TaskPlan 目标、Task 验收、ADR 决策或 Memo 暂存信息。

### 2.5 项目外部资料

当项目采用 `docs/sources/` 或等价外部资料目录时，该目录承载管辖项目外部调研、第三方资料、竞品材料、官方文档摘录或其他外部引用副本。

项目外部资料规则：

1. 外部资料中的结论必须按本文 §5.2 吸收后，才可成为项目稳定事实；
2. 外部资料来源应指向外部资料、引用副本、网页、论文、仓库、产品文档、访谈记录或其他真实来源，不得只指向关联 Task；
3. 外部资料可以登记相关 WorkArea、TaskPlan、Task、ADR、Memo 或其他工作对象；该登记不得替代来源；
4. 项目外部资料不得替代 LDVH 自身规范工作区 sources 中的外部资料引用。

## 3. 项目入口文档

项目入口文档是项目根目录下服务人类和 AI 快速理解项目的入口，例如根 README 文档。项目入口文档属于管辖项目文档治理范围，即使它不在 `docs/` 目录内。

项目入口文档可以承载：

1. 项目名称、定位、目标用户和一句话说明；
2. 安装、运行、测试和部署入口；
3. 主要目录说明和贡献方式；
4. 当前项目状态和版本状态；
5. 指向项目正文文档的导航链接。

项目入口文档不得承载：

1. LDVH 稳定规范规则；
2. 工作对象状态机、字段契约或验收事实；
3. 需要长期治理但未进入项目正文文档或工作对象的关键结论；
4. 与项目正文文档、工作对象事实源或 LDVH 规范冲突的事实。

LDVH 自身项目的根 README 文档按本文治理；LDVH 正式规范由 `specs/` 承载。

---

## 4. 项目正文文档类型

### 4.1 需求文档

需求文档承载产品需求、用户问题、目标范围、成功标准和约束。需求文档可以作为 WorkArea、TaskPlan 或 Task 的背景资料，但不替代 WorkArea 的范围事实、TaskPlan 的目标状态或 Task 的验收标准。

当需求文档中的内容需要执行时，应创建或更新 TaskPlan 和 Task；当需求文档中的目标需要跨任务追踪时，应创建或更新 TaskPlan；当需求文档中的范围需要长期归属时，应创建或更新 WorkArea。

### 4.2 技术设计文档

技术设计文档承载架构、接口、模块、数据结构、技术方案和实现说明。技术设计文档可以作为 Task deliverable，也可以作为 ADR 的背景材料。

当技术设计形成长期决策时，应创建 ADR；当技术设计只是某次任务的交付物时，应由 Task 引用该文档路径。

### 4.3 操作和维护文档

操作和维护文档承载安装、运行、部署、维护、故障排查和团队操作约定。若其中内容变成 LDVH 框架级长期规则，应评估是否需要向 LDVH `specs/` 提出规范改进；若只是管辖项目长期约束，应先进入项目正文区、ADR 或对应工作对象。需要长期约束 AI 执行时，再由项目适配措施保留入口摘要和权威来源，不得在用户项目中创建 `specs/` 或 `specs/` 承载。

### 4.4 报告文档

报告文档承载审计、验收、测试、复盘、调研总结和项目状态说明。报告文档可以作为 Task 关闭证据的被引用结果物，但 Task 的关闭状态和 closure_evidence 仍由 Task 对象承载。

## 5. 文档吸收链路

### 5.1 项目内部资料吸收

项目内部资料结论应根据性质吸收到不同出口：

| 结论性质 | 吸收出口 |
|---|---|
| 稳定项目资料 | 项目正文文档 |
| 长期技术或产品决策 | ADR |
| 可执行工作 | Task |
| 用户目标或成功标准 | TaskPlan |
| 暂存发现、提醒或观察项 | Memo |
| 踩坑经验 | Pitfall |

吸收后，内部资料保留分析过程和来源；权威结论以吸收出口为准。

### 5.2 项目外部资料吸收

项目外部资料需要先经过判断和吸收，不能直接作为项目稳定事实。

常见吸收路径：

1. 外部技术资料被采纳为项目设计依据 → 技术设计文档或 ADR；
2. 外部产品资料被采纳为需求背景 → 需求文档或 TaskPlan；
3. 外部测试、审计或实践方法被采纳为执行动作 → Task 或工作流程；
4. 外部资料仅供背景阅读 → 保留在项目外部资料位置，不升级。

### 5.3 吸收证据

吸收动作应在吸收出口中保留必要来源说明。需要目标状态、验收、关闭证据或长期范围归属时，应由 TaskPlan、Task、WorkArea、ADR、Memo 或 Change 承载，不得只依赖 docs/studies 或 docs/sources 原文。

## 6. 文档与工作对象关系

### 6.1 文档不是工作对象

依据 `specs/03-文档基础规范.md` §7，项目文档不是独立工作对象。项目文档没有默认状态机、负责人、验收字段或关闭证据。

当文档需要被治理时，应由工作对象承接治理：

| 治理需求 | 对应工作对象 |
|---|---|
| 用户目标、范围和成功标准 | TaskPlan；长期范围归属由 WorkArea 承接 |
| 可执行工作、验收和交付 | Task |
| 长期决策 | ADR |
| 暂存输入、发现和提醒 | Memo |
| 实际变更记录 | Change |
| 复用踩坑经验 | Pitfall |

### 6.2 文档引用方式

工作对象引用项目文档时，应优先使用 Git 文件路径。`related_docs` 等字段应表达文档路径或文档引用结构，不应暗示存在独立 Document 工作模型。

当文档路径变化时，应同步检查引用该路径的 WorkArea、TaskPlan、Task、SubTask、ADR、Memo、Change、Pitfall 和项目正文文档。

### 6.3 文档产物

Task 可以把项目文档作为 deliverable 或被引用结果物。文档产物完成不等于 Task 自动关闭；Task 仍必须满足 acceptance、verification 和 closure_evidence 要求。

## 7. 文档结构特例

项目正文文档继承 `specs/03-文档基础规范.md` 的章节编号、段落、表格、代码块和引用规则。

项目入口文档可根据面向人类阅读和开源展示需要使用更自然的 README 结构，不强制套用完整头部元信息，但不得与项目正文事实源或工作对象事实源冲突。

项目内部资料和外部资料应声明定位、执行效力或来源，避免被误读为项目正文事实源。来源必须指向真实输入或外部资料，不得只指向关联 Task；如需记录相关 Task 或其他工作对象，应使用头部 `关联对象` 字段或项目等价记录方式。

## 8. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | AI 在需要读取、引用或修改项目文档时，应知道项目文档由项目自身约定管理，设置管辖项目不等于 LDVH 接管用户 docs | 管辖项目文档边界摘要、README 边界检查、`specs/04.02-LDVH能力保障规范.md` | AI 执行入口提示 | 本文的默认不接管边界、README 边界、文档吸收链路或文档与工作对象关系变化时 |

项目文档结构和引用校验不作为设置管辖项目后的默认动作。需要检查项目文档而现有 Code 实现不能适配时，必须按 `specs/03-文档基础规范.md` §9.1 先形成文档检查 Code 缺口，并按 `specs/07-Code确定性执行实现规范.md` 完成 Code 需求准入、最小实现和测试验证；启用后再补充对应确定性执行要求。具体环境实体由 `specs/04.02-LDVH能力保障规范.md` 承接。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 将设置管辖项目解释为 LDVH 默认接管、初始化、迁移、重排或强制校验用户 docs；
2. 改变项目自有文档、内部资料或外部资料的事实源性质；
3. 将项目内部资料或外部资料结论直接作为项目正文事实源使用；
4. 让项目文档替代 WorkArea、TaskPlan、Task、SubTask、ADR、Memo、Change 或 Pitfall 的权威字段；
5. 改变根 README 的项目入口定位；
6. 将用户项目资料写入 `specs/` 或 `specs/`；
7. 将 LDVH 规范正文写入用户项目文档；
8. 新增、替换或扩大项目文档检查 Code 实现的判定范围。

管辖项目文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 默认不接管 | 设置管辖项目未被解释为 LDVH 默认接管用户 docs |
| 工作区归属 | 用户项目文档按项目自身约定管理，而不是进入 specs |
| 资料边界 | 正文文档、内部资料、外部资料边界清晰 |
| README 边界 | README 是入口文档，不替代正文文档或工作对象 |
| 吸收关系 | 内部资料、外部资料结论已吸收到权威位置后才生效 |
| 对象关联 | 文档通过路径或文档引用结构关联工作对象 |
| 状态边界 | 文档未替代 WorkArea 范围、TaskPlan 目标、Task 状态或 ADR 决策 |
| Code 适配 | 项目文档检查不是接入默认动作；任务需要时，Code 实现按项目文档约定适配，缺失时已按 `specs/03-文档基础规范.md` §9.1 和 `specs/07-Code确定性执行实现规范.md` 处理 |

## 10. 待补齐事项

1. `related_docs` 字段应统一为路径引用或结构化文档引用，待工作模型字段契约同步调整；
2. 项目文档机械化校验规则仅在具体任务需要时评估，待 Code 实现按 `specs/03-文档基础规范.md` §9.1 和 `specs/07-Code确定性执行实现规范.md` 扩展并验证后补齐，并在启用后补充确定性执行要求；
3. LDVH 当前 `docs/` 中设计材料的吸收路径待后续审计处理。
