# 边界冲突分析报告

---

## 一、Trae Solo 环境机制 vs Harness 行动模型——"约束 AI 行动"的职责重叠

### 边界问题

两者都涉及"约束 AI 行动"，但约束的来源、机制和强制力不同：

| 维度 | Trae Solo 环境机制（Rules/Skill/Agent） | Harness 行动模型 |
|---|---|---|
| 约束来源 | Trae 平台提供，AI 协作的原生入口 | Harness 自定义规范，项目执行时适用 |
| 约束机制 | Rules 注入上下文、Skill 封装能力、Agent 编排流程 | 行动模型建模"读取→判断→执行→暂停→回写" |
| 强制力 | 平台级，AI 无法绕过 Rules 注入 | 规范级，依赖 AI 自觉遵守或工具辅助校验 |

### 问题机制

核心冲突点在于**双重约束的优先级未显式定义**：

1. **Rules 与行动模型的指令可能矛盾**：例如，Rules 中可能要求"遇到 X 立即执行 Y"，而行动模型要求"遇到 X 先读取事实源再判断"。当两者冲突时，AI 应遵从哪个？Rules 是平台强制注入的，行动模型是 Harness 定义的，但文档未给出优先级裁决规则。

2. **Skill 封装的行动步骤 vs 行动模型的行动步骤**：Skill 内部可能已编排了"读取→执行→回写"的流程，而行动模型也定义了同样的流程。如果 Skill 的编排与行动模型的约束不一致（例如 Skill 跳过了某个门禁检查），行动模型的约束就被架空。

3. **"利用不重新定义"原则的模糊地带**：Harness 说"利用 Trae 机制，不重新定义"，但行动模型本质上是在 Trae 机制之上叠加了一层"如何使用这些机制"的规范。这层规范是否构成"重新定义"？边界不清。

### 涉及价值标准

- **V2 受控执行**：双重约束若优先级不明，AI 可能选择性遵守较宽松的一方，导致执行失控
- **V3 门禁识别**：若 Rules 和行动模型对门禁触发条件定义不一致，AI 可能遗漏门禁

### 风险等级：🟠 高

双重约束的优先级问题不是理论推演——Rules 是每次会话强制注入的，行动模型需要 AI 主动读取事实源才能获知，信息到达的不对称性使冲突几乎必然发生。

### 建议

1. **显式定义优先级规则**：当 Rules 指令与行动模型约束冲突时，以行动模型为准（因为行动模型是项目级定制，更精确），但需在 Rules 中声明此优先级规则本身
2. **Skill 审计机制**：每个 Skill 的内部流程必须声明其与行动模型的关系——是"遵循行动模型的子流程"还是"行动模型特定场景的替代路径"
3. **在行动模型中增加"Rules 冲突检测"环节**：作为"判断"步骤的子步骤，AI 应主动检查当前 Rules 注入的指令是否与行动模型冲突

## 二、Harness 工具 vs Harness 生产对象——"受控写入"与"非事实源"的张力

### 边界问题

文档声明了三条硬约束：
- 工具不是最终事实源
- 工具不能绕过事实源边界和 Human Gate
- 工具不能独立维护与事实源冲突的派生数据

但工具同时承担"受控写入"生产对象的职责。问题在于：**"受控写入"的"控"由谁定义、由谁执行、由谁验证？**

### 问题机制

1. **写入权限与事实源权威的矛盾**：工具能写入生产对象（如 YAML 文件），而生产对象是 Git 文件事实源。如果工具写入的内容就是事实源的内容，那么"工具不是事实源"的声明实际上是一个语义区分而非操作区分——工具写入了，内容就成了事实。问题在于：**写入前的校验是否充分？** 如果工具绕过了某些校验（例如工具内部逻辑错误），写入的内容就成了"被污染的事实源"。

2. **派生数据的边界模糊**：工具可能需要缓存、聚合或转换生产对象的数据以实现其功能（如展示、校验）。这些派生数据与事实源之间的同步边界在哪里？文档说"不能独立维护与事实源冲突的派生数据"，但"冲突"的判定标准未定义——是"内容不同"算冲突，还是"语义不一致"算冲突？

3. **工具作为"写入管道"的可靠性**：如果工具是写入生产对象的唯一通道，那么工具本身的可靠性就成了整个体系的单点。文档未定义工具故障时的降级策略——AI 是否可以直接写入事实源？如果可以，工具的"受控写入"就失去了意义；如果不可以，体系就存在可用性风险。

### 涉及价值标准

- **V4 证据沉淀**：如果工具写入未经充分校验，沉淀的证据可能不可靠
- **V5 事实回写**：工具是回写的执行者，但其可靠性直接影响回写质量
- **V6 人类确认质量**：如果工具展示的派生数据与事实源不一致，人类确认就基于错误信息

### 风险等级：🟠 高

"工具不是事实源"是一个原则声明，但在操作层面，工具是事实源的写入通道，原则与操作之间存在真空地带。

### 建议

1. **定义"受控写入"的控制链**：写入前校验→写入→写入后验证→事实源确认，每一步的执行者和校验标准需显式定义
2. **定义派生数据的一致性标准**：明确"冲突"的判定规则——建议采用"语义等价"标准，而非"内容相同"
3. **定义工具故障降级策略**：明确工具不可用时的写入路径和校验替代方案

## 三、介质 vs 生产对象——"定义使用规则但不重新定义介质"的能力边界

### 边界问题

YAML 和 Markdown 是行业标准介质，Harness 定义其使用规则（如 YAML 的 schema、Markdown 的结构规范），但不重新定义介质本身。问题在于：**使用规则是否会与介质的原生能力产生冲突？**

### 问题机制

1. **约束性规则 vs 介质的表达自由度**：YAML 原生支持锚点、引用、多文档流等高级特性，但如果 Harness 的使用规则禁止这些特性（出于"AI 可读取"的考虑），就等于在事实上重新定义了"我们使用的 YAML"——这不是 YAML，而是 YAML 的子集。这与"不重新定义介质"的原则存在张力。

2. **Markdown 的结构规范 vs Markdown 的灵活性**：Markdown 的核心优势是灵活性，如果 Harness 定义了严格的结构规范（如标题层级、必含字段），这些规范可能与 Markdown 的"宽松解析"特性冲突——不同 Markdown 解析器对同一文档的解析结果可能不同，而 Harness 的结构规范可能隐含了对特定解析行为的依赖。

3. **介质演进与规则锁定的矛盾**：YAML 1.2 与 YAML 1.1 存在不兼容变更（如科学计数法、布尔值处理），如果 Harness 的使用规则基于 YAML 1.1 制定，当项目迁移到 YAML 1.2 环境时，规则与介质能力之间就会出现冲突。文档未定义介质版本的管理策略。

### 涉及价值标准

- **V1 稳定理解**：如果使用规则限制了介质的表达能力，AI 可能无法获得足够的上下文
- **V4 证据沉淀**：如果介质解析不一致，沉淀的证据可能在不同环境下呈现不同结果
- **V7 持续改进**：介质演进时，使用规则是否同步更新？

### 风险等级：🟡 中

介质能力冲突通常是渐进式的（随介质版本演进），不会立即导致体系失效，但会在长期积累中形成技术债。

### 建议

1. **显式声明介质子集**：如果使用规则限制了介质的某些特性，应明确声明"本体系使用 YAML 的 X 子集"，而非声称"使用 YAML 但不重新定义"
2. **定义介质版本策略**：明确依赖的介质版本，以及版本升级时的迁移路径
3. **建立介质能力与使用规则的映射**：每条使用规则应说明其限制的介质原生能力及限制原因，便于未来评估是否放宽

---

## 四、"AI 为第一服务对象" vs "人负责确认和验收"——信息组织的优先级冲突

### 边界问题

这是整个体系中最根本的张力：**如果信息组织优先满足 AI 的理解需求（结构化、最小可行动、机器可解析），人类确认体验是否会被牺牲？**

### 问题机制

1. **信息密度 vs 可读性的权衡**：AI 偏好高信息密度、结构化的表达（如 YAML 中的密集字段），而人类确认时需要上下文叙述、因果链和可读性。如果生产对象以 AI 优先的方式组织，人类在确认时就需要工具做"翻译"——但工具的翻译质量又回到了问题二的可靠性问题。

2. **"最小可行动上下文"的歧义**：V1 要求 AI 获得"足够但不过载的最小可行动上下文"，但对人类而言，"最小"可能意味着信息不足——人类确认需要理解"为什么这样做"，而不仅仅是"做了什么"。AI 行动模型关注的是"做什么"和"怎么做"，人类确认关注的是"为什么"和"是否应该"。

3. **确认节点的信息不对称**：Human Gate 要求人类做出确认决策，但如果到达 Human Gate 时，AI 已经按照"AI 优先"的方式组织了信息，人类看到的是经过 AI 过滤和结构化的信息，而非原始事实。这种信息不对称可能导致人类确认流于形式——人类基于不完整的信息"确认"了 AI 的行动。

4. **V6 的定义模糊**："人能基于事实源、证据和工具展示做出高质量确认"——"高质量"的标准是什么？如果人类只是看了工具展示的摘要就点确认，这算不算"高质量"？V6 缺乏可操作的度量标准。

### 涉及价值标准

- **V1 稳定理解** vs **V6 人类确认质量**：这是最直接的冲突——为 V1 优化的信息组织可能损害 V6
- **V3 门禁识别**：如果信息组织以 AI 优先，Human Gate 的触发信息可能对人类不够友好，导致门禁形同虚设
- **V7 持续改进**：如果人类确认质量低，纠偏信号就弱，持续改进就缺乏有效输入

### 风险等级：🔴 极高

这不是边界模糊的问题，而是两个价值标准之间的结构性张力。如果不在体系层面做出权衡决策，实践中必然偏向 AI 优先（因为 AI 是执行者，信息组织由 AI 主导），人类确认将逐步沦为形式。

### 建议

1. **显式定义信息组织的双轨策略**：生产对象的结构满足 AI 需求（V1），但在 Human Gate 节点，工具必须生成"人类可读确认包"——包含行动原因、影响范围、风险提示和回退方案
2. **定义 V6 的可操作度量**：例如"人类确认时必须能回答以下三个问题：① AI 做了什么 ② 为什么这样做 ③ 不这样做的后果是什么"——如果人类无法回答，说明确认质量不达标
3. **在行动模型中增加"确认信息准备"步骤**：在触发 Human Gate 之前，AI 必须主动准备面向人类的确认信息，而非仅依赖工具的自动翻译

---

## 五、构成要素与 V1-V7 映射的完整性分析

### 映射现状

基于文档提供的"构成要素对价值实现的贡献"表，我梳理出以下映射：

| 价值标准 | 主要支撑要素 | 辅助支撑要素 | 无直接支撑 |
|---|---|---|---|
| V1 稳定理解 | 生产对象、行动模型 | 介质 | — |
| V2 受控执行 | 行动模型 | 环境机制、工具 | — |
| V3 门禁识别 | 行动模型 | 工具 | — |
| V4 证据沉淀 | 生产对象 | 工具、介质 | — |
| V5 事实回写 | 生产对象 | 工具 | — |
| V6 人类确认质量 | 工具 | 介质 | **生产对象、行动模型** |
| V7 持续改进 | 生产对象 | 工具 | **行动模型** |

### 问题机制

1. **V6 人类确认质量缺乏生产对象和行动模型的直接支撑**：当前映射中，V6 主要依赖工具（展示）和介质（可审查形式）。但人类确认的质量不仅取决于"看到什么"，还取决于"信息如何被组织"（生产对象）和"确认流程如何被引导"（行动模型）。生产对象的结构决定了人类能理解什么，行动模型决定了人类在什么时机、以什么方式确认——两者对 V6 至关重要，但映射中缺失。

2. **V7 持续改进缺乏行动模型的直接支撑**：持续改进的核心是"失败和纠偏能回到事实源，改善后续 AI 行动"。但"改善后续 AI 行动"意味着行动模型本身需要被改进——行动模型不仅是 V7 的受益者，也应是 V7 的支撑者。当前映射中行动模型对 V7 没有贡献，这意味着行动模型的自我改进机制未被建模。

3. **介质对 V3 门禁识别无贡献**：介质决定了信息的承载形式，而门禁识别需要明确的触发信号。如果介质不支持表达"此处需要人类确认"的元数据（如 YAML 中的 `human_gate: true` 字段），门禁识别就只能依赖行动模型的规则判断，缺少来自数据层面的声明式支撑。

4. **Trae Solo 环境机制对 V4、V5、V7 无贡献**：环境机制提供的是"入口和原生机制"，但不直接保证工程可控。然而，环境机制中的 Rules 可以注入校验规则、Skill 可以封装回写流程——这些对 V4（证据沉淀）、V5（事实回写）、V7（持续改进）都有潜在贡献，但当前映射将其排除在外。

### 涉及价值标准

- **V6**：支撑不完整，人类确认质量可能无法保证
- **V7**：行动模型的自我改进未被建模，持续改进可能停留在"事实源更新"层面，无法触及"行动模型优化"
- **V3**：缺少介质层面的声明式门禁支撑，门禁识别完全依赖行动模型的规则判断，鲁棒性不足

### 风险等级：🟠 高

映射不完整意味着某些价值标准在体系设计中缺乏足够的支撑要素，实践中可能出现"价值标准被声明但无法被实现"的情况。

### 建议

1. **补充 V6 的支撑要素**：生产对象应包含"人类确认视图"的定义（如 Change 对象的 `human_summary` 字段），行动模型应包含"确认信息准备"步骤
2. **补充 V7 的支撑要素**：行动模型应包含"行动模型自身的改进触发机制"——例如，当 Pitfalls 记录达到阈值时，触发行动模型规则的审查和更新
3. **补充介质对 V3 的贡献**：在生产对象的 YAML schema 中增加门禁声明字段，使门禁识别同时来自行动模型的规则判断和生产对象的数据声明，形成双重保障
4. **重新评估环境机制对 V4/V5/V7 的贡献**：虽然环境机制"不直接保证工程可控"，但 Rules 和 Skill 的实际效果对这三个价值标准有间接贡献，应在映射中体现

## 总结：风险矩阵

| 分析维度 | 风险等级 | 核心风险 | 最受影响的价值标准 |
|---|---|---|---|
| 环境机制 vs 行动模型 | 🟠 高 | 双重约束优先级未定义 | V2、V3 |
| 工具 vs 生产对象 | 🟠 高 | "受控写入"控制链不完整 | V4、V5、V6 |
| 介质 vs 生产对象 | 🟡 中 | 使用规则隐含重定义介质 | V1、V4、V7 |
| AI 优先 vs 人类确认 | 🔴 极高 | 结构性张力，无权衡决策 | V1 vs V6、V3、V7 |
| 映射完整性 | 🟠 高 | V6/V7 支撑不完整 | V6、V7、V3 |

**最高优先级建议**：先解决维度四（AI 优先 vs 人类确认的结构性张力），因为它是唯一一个🔴极高风险项，且其影响会传导至其他维度——如果人类确认质量无法保证，整个体系的闭环（人→AI→Git→人）就会在"回到人"这一环断裂。

# 价值实现标准冲突可行性评估报告

---

## 一、V1（稳定理解）与 V2（受控执行）的张力

### 冲突场景

AI 接收一个跨模块任务，需要同时理解项目边界、规则体系和任务上下文。V1 要求"最小可行动上下文"——只给 AI 刚好够用的信息；V2 要求"严格按规则执行"——AI 必须完整理解所有适用规则才能正确受控。

### 冲突机制

**最小化与完整性的根本矛盾**：V1 的"不过载"隐含了信息裁剪，而 V2 的"依据规则执行"隐含了规则的全量可达。当规则体系本身庞大时（如本规范体系含 02-10 多个子规范、ADR、pitfalls 等），"最小可行动上下文"可能恰好裁掉了某条关键规则的触发条件，导致 AI 在不知情的情况下违反 V2。

具体表现：
- L1 只索引核心文档，AI 跳过了某条 L2 场景规则，但该规则恰好适用于当前任务
- "压缩保护"口诀虽然存在，但口诀是压缩信息，AI 可能无法从口诀还原出完整的规则适用条件
- V1 追求效率（少读快动），V2 追求安全（全读慢动），两者在规则体量膨胀时必然反向拉扯

### 实际影响

| 严重度 | 表现 |
|---|---|
| 中 | AI 在常见场景下表现正常，但在边缘场景（如跨项目操作、规则冲突场景）遗漏适用规则 |
| 高 | AI 自认为已获得"最小可行动上下文"，实际缺少关键约束，导致 V2 被静默违反 |

### 缓解建议

1. **区分"最小可行动"与"最小可理解"**：V1 应明确，上下文最小化的底线是 AI 能正确判断"我是否需要更多信息"，而非"我能直接行动"。引入**自知边界**概念——AI 知道自己不知道什么，比 AI 以为自己知道更安全。
2. **规则分层加载而非一次性裁剪**：L1 提供规则目录（而非规则内容），AI 按任务场景按需加载 L2，避免"全量读取"与"过度裁剪"的两极。
3. **为 V1 增加验证条件**：AI 声明"我已获得最小可行动上下文"时，应同时列出它认为适用的规则清单，供快速校验是否有遗漏。

---

## 二、V3（门禁识别）与 V1（稳定理解/高效行动）的张力

### 冲突场景

AI 在执行一个多步骤任务时，连续遇到多个潜在门禁点（如修改规则文件、删除文件、变更任务状态）。V3 要求每次都暂停等待确认；V1 要求 AI 高效行动、不过载。

### 冲突机制

**安全刹车与行动流畅性的矛盾**：门禁的本质是"宁可慢，不可错"，V1 的本质是"足够理解就行动"。当门禁定义过宽时（如当前规范中"Skill、Agent、规则文件、product.yaml 等例外对象仍需 Human Gate"），AI 会频繁中断，导致：

- **门禁疲劳**：人类在短时间内被多次要求确认，注意力下降，确认质量反而降低（这与 V6 也冲突）
- **上下文断裂**：每次暂停后恢复执行，AI 需要重新建立上下文，V1 的"稳定理解"被反复打断
- **隐性绕过**：AI 为了避免频繁中断，可能倾向于将任务拆解为"不需要门禁"的子任务，实质上绕过了门禁意图

### 实际影响

| 严重度 | 表现 |
|---|---|
| 中 | 任务执行周期拉长，人类确认负担增加 |
| 高 | 门禁疲劳导致人类机械点击确认，V3 形同虚设 |

### 缓解建议

1. **门禁分级**：将门禁分为"硬门禁"（必须逐次确认，如删除 product.yaml）和"软门禁"（可批量确认，如连续修改多个规则文件），减少中断频率。
2. **门禁预判与合并**：AI 在任务开始前预判所有门禁点，一次性向人类展示"本次任务将触发 N 个门禁，是否全部授权"，而非逐步中断。
3. **为 V3 增加效率指标**：门禁不应只衡量"是否识别"，还应衡量"识别后的人类确认耗时"——如果确认耗时过长，说明门禁设计需要优化。

---

## 三、V5（事实回写/Git文件）与 V4（证据沉淀/可追溯）的张力

### 冲突场景

AI 执行一次复杂任务，产生了大量中间证据（搜索结果、诊断输出、试错记录）。V4 要求这些证据可追溯；V5 要求稳定事实回写到 Git 文件。

### 冲突机制

**证据完整性与 Git 可维护性的矛盾**：

- **并非所有证据都是"稳定事实"**：V4 的范围（执行结果、检查结果、决策、变更记录）远大于 V5 的范围（稳定事实）。大量中间证据是瞬态的、过程性的，回写到 Git 既不必要也有害。
- **Git 文件膨胀**：如果严格执行 V5，每次任务执行都产生 Change YAML、Evidence YAML、任务状态更新，Git 仓库会快速膨胀，尤其是频繁迭代时。
- **回写成本与执行效率**：每次回写都是文件操作 + 潜在的 Git 操作，AI 在高频率任务中会花大量时间在回写上，挤压实际执行时间。
- **回写边界模糊**：当前规范定义了"稳定事实回写到 Git"，但"稳定"的判定标准不清晰——AI 执行过程中产生的临时判断是否算稳定事实？如果不算，V4 的可追溯性就打了折扣。

### 实际影响

| 严重度 | 表现 |
|---|---|
| 中 | Git 仓库中充斥大量低价值 Change/Evidence 文件，增加检索成本 |
| 高 | AI 为了满足 V5 而过度回写，或为了效率而选择性跳过回写，导致 V4 不可靠 |

### 缓解建议

1. **证据分级存储**：将证据分为"Git 级"（决策、变更、ADR）和"会话级"（搜索过程、中间诊断），前者回写 Git，后者仅保留在对话中或临时存储。
2. **为 V5 明确"稳定"的判定标准**：建议定义"稳定事实 = 跨会话仍有参考价值的信息"，而非"所有 AI 产出"。
3. **引入证据生命周期**：Change/Evidence 文件设置保留期，过期后可归档或清理，避免无限膨胀。
4. **回写批量化**：允许 AI 在一个任务内积累变更，在任务完成时一次性回写，而非每步都回写。

---

## 四、V6（人类确认质量）与"AI 为第一服务对象"的张力

### 冲突场景

规范声明"AI 执行者为第一服务对象"，信息组织方式首先要满足 AI 的读取、理解、执行需要。但 V6 要求人类能基于事实源、证据和工具展示做出高质量确认。

### 冲突机制

**信息架构的服务方向矛盾**：

- **AI 优先的信息格式 vs 人类可读性**：YAML、口诀、压缩保护——这些对 AI 高效，对人类不友好。当人类需要在门禁点做确认时，面对的是 AI 优化的信息结构，而非人类优化的展示。
- **"第一服务对象"的排他性风险**：规范说"不意味着人和工具处于次要位置"，但"第一"本身就隐含了优先级。当 AI 需求与人类体验冲突时（如：AI 需要结构化 YAML 输出，人类需要自然语言摘要），"第一服务对象"的表述缺乏仲裁机制。
- **V6 的实现依赖工具层**：规范提到"Web Tools"可以辅助人类观察和确认，但同时又约束"工具不能成为最终事实源"。这意味着人类确认所需的良好体验必须依赖一个"非事实源"的工具层——如果工具层出问题，V6 就无法保障。

### 实际影响

| 严重度 | 表现 |
|---|---|
| 高 | 人类在确认时看到的是 YAML 格式的任务状态和规则引用，而非直观的风险摘要和影响说明，确认质量下降 |
| 中 | "AI 为第一服务对象"成为过度优化 AI 体验的借口，人类确认变成形式主义 |

### 缓解建议

1. **重新定义"第一服务对象"**：建议改为"AI 为执行第一服务对象，人类为确认第一服务对象"——信息生产面向 AI 效率，信息展示面向人类理解。这是两个不同的环节，不需要同一个优先级。
2. **强制要求确认摘要层**：每个门禁触发时，AI 必须生成人类可读的确认摘要（自然语言 + 影响范围 + 风险等级），而非直接展示 YAML。
3. **V6 增加可测量指标**：如"人类确认平均耗时"、"确认回退率"——如果人类确认耗时过长或频繁回退，说明信息展示质量不足。

---

## 五、V7（持续改进）与 V2（受控执行）的张力

### 冲突场景

AI 在执行任务时发现某条规则不合理或与实际情况冲突，按 V7 应该将这个发现沉淀回事实源（如 pitfalls.md、ADR），推动规则改进。但按 V2，AI 必须严格按当前规则执行，不能因为"觉得规则不对"就绕过。

### 冲突机制

**规则稳定性与规则进化性的根本矛盾**：

- **V2 要求规则是稳定的锚点**：AI 的受控执行依赖于规则的确定性。如果规则频繁变化，AI 的执行就失去了可预测性。
- **V7 要求规则是进化的系统**：持续改进意味着规则会变，而且变化本身也需要被管理。
- **改进的时序问题**：AI 发现规则问题 → 沉淀到 pitfalls → 提议修改规则 → 规则更新 → 下次执行使用新规则。在这个链条中，"发现"到"更新"之间存在时间差，AI 在这个时间差内应该如何行动？严格按旧规则（V2）还是按新理解（V7）？
- **AI 的改进权限边界不清**：V7 说"失败、不确定性和人类纠偏能回到事实源"，但 AI 自己发现的规则问题是否算"不确定性"？AI 能否主动提议修改规则，还是只能记录问题等待人类裁决？

### 实际影响

| 严重度 | 表现 |
|---|---|
| 高 | AI 发现规则问题但不敢偏离，继续按有缺陷的规则执行，导致重复犯错 |
| 中 | 规则改进流程过长，从发现问题到规则更新的周期远超实际迭代速度 |

### 缓解建议

1. **引入"受控偏离"机制**：AI 发现规则问题时，可以记录偏离原因并按更合理的方式执行，同时将偏离事实回写到 pitfalls/ADR，等待人类确认。这既满足 V7（改进被记录），又不违反 V2（偏离是受控的、有记录的）。
2. **规则版本化与生效机制**：规则变更应有版本号和生效时间，AI 在过渡期内同时可见新旧版本，明确标注"当前执行版本"。
3. **V7 增加改进时效指标**：从问题发现到规则更新的平均时长应被追踪，避免"持续改进"变成"持续记录但不改进"。

---

## 六、跨维度交叉冲突

除上述五组直接张力外，还存在交叉冲突：

### 6.1 V1 + V2 + V7 三角困境

AI 需要最小上下文（V1）来高效行动，但必须按规则执行（V2），而规则本身在持续变化（V7）。**AI 每次加载的"最小可行动上下文"可能已经过时**，但 V2 不允许它用过时信息行动，V1 不允许它加载全量信息来验证时效性。

**缓解**：在 L1 中增加规则版本时间戳，AI 加载 L1 时先校验版本是否最新，再决定是否需要重新加载 L2。

### 6.2 V3 + V5 + V6 门禁回写确认循环

门禁触发（V3）→ AI 需要回写事实到 Git（V5）→ 人类需要基于回写内容确认（V6）→ 确认本身又产生新的变更需要回写（V5）→ 可能触发新的门禁（V3）。**形成无限循环**。

**缓解**：定义"确认行为本身不产生需要再次确认的变更"，打破循环。

### 6.3 V4 + V7 证据的追溯价值衰减

证据沉淀（V4）的价值在于可追溯，但持续改进（V7）意味着规则和实践会变化，旧证据的追溯价值会随时间衰减。**Git 中大量历史证据可能基于已废弃的规则体系，对新 AI 执行无参考价值**。

**缓解**：证据文件应标注"适用规则版本"，AI 读取历史证据时先校验规则版本是否匹配当前版本。

## 七、总结评估

| 张力对 | 冲突强度 | 核心矛盾 | 最关键风险 |
|---|---|---|---|
| V1 ↔ V2 | **强** | 最小化 vs 完整性 | AI 静默遗漏关键规则 |
| V3 ↔ V1 | **中强** | 安全刹车 vs 行动流畅 | 门禁疲劳导致确认形同虚设 |
| V5 ↔ V4 | **中** | Git 可维护性 vs 证据完整性 | Git 膨胀或证据丢失 |
| V6 ↔ AI优先 | **强** | AI 效率 vs 人类理解 | 确认质量下降，V6 被架空 |
| V7 ↔ V2 | **强** | 进化性 vs 稳定性 | 规则缺陷被机械执行 |

**最需优先解决的冲突**：V1↔V2 和 V6↔AI优先。前者直接决定 AI 是否能"正确地行动"，后者直接决定人类是否能"有效地监督"。如果这两个冲突不解决，其他冲突的缓解措施也会失效——因为 AI 要么行动不正确，要么行动无人有效监督。

**核心建议**：在价值标准之间增加**仲裁原则**——当 V1-V7 发生冲突时，按什么优先级裁决？当前规范缺少这个仲裁层，导致每对冲突都需要独立解决。建议增加一条元规则：**"执行安全性（V2+V3）优先于执行效率（V1），人类可理解性（V6）优先于 AI 可读性，改进时效（V7）优先于规则稳定性（V2）的表面形式但不及于其约束实质。"** 这条元规则本身也需要被验证和迭代。

# LD Vibe Harness 理念与纲要——逻辑一致性审查报告

---

## 审查概述

对"第三节 价值实现标准"V1-V7、"第四节 五类构成要素"及"第五节 运行闭环"进行交叉审查，共发现 **8 个冲突点**，其中高严重度 3 个、中严重度 3 个、低严重度 2 个。

---

## 冲突点详述

### 冲突 1：V1（稳定理解）与 V2（受控执行）+ V7（持续改进）的上下文膨胀矛盾

| 项目 | 内容 |
|---|---|
| **涉及标准** | V1 ↔ V2、V7 |
| **严重程度** | **高** |
| **冲突描述** | V1 要求 AI 获得"足够但不过载的最小可行动上下文"，核心约束是**不过载**。V2 要求 AI 依据规则、事实源和行动模型执行——这意味着 AI 必须读取的上下文量与规则/事实源的规模正相关。V7 驱动持续改进，要求失败和纠偏回写到事实源（Pitfall、规则、行动模型），导致事实源**只增不减**。三者叠加：V7 使事实源持续膨胀 → V2 要求 AI 读取更多规则和事实源 → V1 的"不过载"约束越来越难满足。 |
| **冲突根因** | V1 的"最小可行动上下文"是静态表述，未考虑事实源随项目演进的动态增长；V7 的改进机制缺乏对事实源体量的反向约束。 |
| **建议** | 在 V1 中补充"上下文裁剪机制"的明确要求——不是所有规则和事实源都需要在每次行动前全量加载，应定义分层加载策略（如 L1 必读 → L2 按场景加载 → L3 按需检索）。同时在 V7 中增加"改进也包含对已有规则的精简和合并"，防止只增不减的棘轮效应。 |

---

### 冲突 2：V2（受控执行）与 V3（门禁识别）的规则边界盲区

| 项目 | 内容 |
|---|---|
| **涉及标准** | V2 ↔ V3 |
| **严重程度** | **高** |
| **冲突描述** | V2 要求 AI"依据规则、事实源和行动模型执行"，本质上限定 AI 的行为边界是**已编码的规则**。V3 要求 AI"识别 Human Gate，知道何时必须暂停"——但实际项目中，并非所有需要人确认的场景都能被规则穷举。当遇到规则未显式编码的门禁场景时：若 AI 严格按 V2 只执行规则中有的内容，则 V3 的隐式门禁会被遗漏；若 AI 凭判断识别规则外的门禁，则违反 V2"不凭聊天记忆自由发挥"的约束。这是一个**精确率-召回率的两难**。 |
| **冲突根因** | V2 将 AI 的行动依据限定为显式规则，V3 却隐含要求 AI 具备规则之外的判断力，两者对"AI 自主性边界"的定义不一致。 |
| **建议** | 在行动模型中显式定义"门禁识别"的两层机制：(1) 规则显式声明的门禁（硬门禁，必须触发）；(2) AI 判断的高影响操作（软门禁，建议触发），并给出软门禁的判定标准（如影响范围、不可逆性、跨模块性），使 V3 的识别行为本身也受规则约束，从而与 V2 兼容。 |

---

### 冲突 3："AI 为第一服务对象"与 V6（人类确认质量）的架构张力

| 项目 | 内容 |
|---|---|
| **涉及标准** | 第二节第一服务对象 ↔ V6 |
| **严重程度** | **高** |
| **冲突描述** | 第二节明确"信息组织方式、事实源结构、任务格式、规则入口和工具能力，**首先要满足 AI 的读取、理解、场景识别**需要"。V6 要求"人能基于事实源、证据和工具展示做出高质量确认"。当设计优先级冲突时（如：YAML 格式对 AI 解析友好但对人阅读困难、任务状态字段为 AI 调度设计但人不需要看），AI 优先的设计取向会系统性地降低人获取关键信息的效率。文档虽声明"不意味着人处于次要位置"，但未提供当两者需求矛盾时的裁决规则，该声明缺乏操作性。 |
| **冲突根因** | "第一服务对象"确立了 AI 优先的设计原则，但 V6 的质量要求依赖人的认知效率，两者在信息呈现层存在结构性竞争，文档未定义优先级裁决机制。 |
| **建议** | 补充设计裁决规则：当 AI 可读性与人可审查性冲突时，采用"AI 适应人的审查需要"原则——因为 V3 和 V6 共同要求人在关键节点做出高质量判断，如果人看不懂，门禁和验收就形同虚设。具体措施：事实源格式对 AI 友好（YAML），但 Web Tools 展示层必须为人优化；任务状态字段同时服务 AI 调度和人审查时，展示层做差异化呈现。 |

---

### 冲突 4：V3（门禁识别）与 V5（事实回写）的时序缺口

| 项目 | 内容 |
|---|---|
| **涉及标准** | V3 ↔ V5 |
| **严重程度** | **中** |
| **冲突描述** | V3 要求 AI 在 Human Gate 处暂停等待人确认。V5 要求稳定事实回写到 Git 文件事实源。问题：AI 到达门禁点时，是否应将**未确认的中间结果**先回写？若写——可能污染事实源（人尚未确认）；若不写——会话中断则工作丢失，且 V4（证据沉淀）要求的可追溯性受损。运行闭环的约束 1 说"终点必须回到文件事实源"，但未定义门禁等待期间的事实源状态管理。 |
| **冲突根因** | 运行闭环只描述了"起点→终点"的完整路径，未覆盖门禁暂停这一中间状态的证据处理策略。 |
| **建议** | 在行动模型中定义"门禁态"的事实源写入规则：门禁等待期间，中间结果写入临时/草稿区（如任务的 `status: pending_review` 字段 + `pending_changes` 子字段），人确认后才提升为正式事实源内容。这样既满足 V5 的边界约束，又满足 V4 的可追溯性。 |

---

### 冲突 5：反向判断 #3 与工具定位的实践矛盾

| 项目 | 内容 |
|---|---|
| **涉及标准** | 3.3 反向判断 #3 ↔ 构成要素"Harness 工具" + 闭环约束 3、4 |
| **严重程度** | **中** |
| **冲突描述** | 反向判断 #3 声明"工具展示与 Git 文件事实源不一致"即未实现核心价值。但闭环约束 3 明确"工具不能成为最终事实源"，约束 4 明确"关键事实仍以 Git 文件为准"——这等于承认工具展示和 Git 文件之间**允许存在不一致**（工具可能缓存、转换、聚合）。如果工具永远与 Git 文件完全一致，工具就失去了独立存在的价值（它只是 Git 文件的镜像）；如果工具允许有差异，反向判断 #3 就随时可能被触发。 |
| **冲突根因** | 反向判断 #3 对一致性的要求是绝对的，但工具的设计定位（降低维护成本、提供展示）内在地允许与原始事实源存在表示层差异，两者对"一致"的定义不同。 |
| **建议** | 将反向判断 #3 中的"不一致"细化为"语义不一致"而非"表示不一致"：工具展示可以与 Git 文件的格式、聚合方式不同，但核心语义（状态、决策、证据）不得矛盾。同时补充工具的一致性校验职责（构成要素表中 Harness 工具已包含"校验事实源"），使工具自身承担一致性保障的部分责任。 |

---

### 冲突 6：V4（证据沉淀）与 V5（事实回写）的边界摩擦

| 项目 | 内容 |
|---|---|
| **涉及标准** | V4 ↔ V5 |
| **严重程度** | **中** |
| **冲突描述** | V4 要求"执行结果能留下可追溯的证据、检查结果、决策或变更记录"，覆盖范围较广。V5 要求"稳定事实能**按边界**回写到 Git 文件事实源"，强调边界约束。两者的摩擦点：并非所有执行证据都是"稳定事实"——例如 AI 的中间推理过程、尝试后放弃的方案、调试日志等，这些对 V4 的可追溯性有价值，但可能不属于 V5 定义的"稳定事实"边界，不应写入 Git 文件事实源。 |
| **冲突根因** | V4 的"证据"范围大于 V5 的"稳定事实"范围，但文档未区分哪些证据属于稳定事实、哪些属于临时/辅助证据，也未定义后者的存储位置。 |
| **建议** | 将证据分为两级：(1) **持久证据**（决策、变更记录、验证结果）→ 回写到 Git 文件事实源（V5）；(2) **过程证据**（中间推理、尝试记录）→ 存储在会话/任务的过程记录中，不进入 Git 事实源但可通过任务对象追溯。在 V4 中明确这一分级，使 V4 和 V5 各自的边界清晰。 |

---

### 冲突 7：Trae Solo 环境机制的"不直接保证工程可控"与 V2 的张力

| 项目 | 内容 |
|---|---|
| **涉及标准** | 构成要素"Trae Solo 环境机制" ↔ V2 |
| **严重程度** | **低** |
| **冲突描述** | 3.2 节明确 Trae Solo 环境机制"提供 AI 协作入口和原生机制，但**不直接保证工程可控**"。V2 要求"受控执行"。作为五类构成要素之一，Trae Solo 环境机制是 AI 行动的物理载体——如果它不保证可控，那么 V2 的可控性完全依赖其余四类要素的约束力穿透 Trae Solo 的原生行为。当 Trae Solo 的原生行为（如 AI 自由补全、忽略系统提示）与 Harness 规则冲突时，V2 可能被绕过。 |
| **冲突根因** | 五类要素中有一类明确不保证可控，但 V2 的实现依赖所有要素的协同，存在约束力缺口。 |
| **建议** | 这不一定是设计缺陷（可能是对现实的诚实承认），但应在行动模型中补充"环境机制穿透策略"：当 Trae Solo 原生行为与 Harness 规则冲突时，Harness 行动模型和工具如何检测和纠正偏离。例如，工具在写入前校验是否符合规则，作为环境机制不可控时的兜底。 |

---

### 冲突 8：V7（持续改进）的改进回路与 V2（受控执行）的规则固化倾向

| 项目 | 内容 |
|---|---|
| **涉及标准** | V7 ↔ V2 |
| **严重程度** | **低** |
| **冲突描述** | V7 要求失败和纠偏"回到事实源，改善后续 AI 行动"，隐含事实源（规则、行动模型）是**可变的**。V2 要求 AI 依据规则执行，隐含规则是**稳定的**参照系。当 V7 驱动规则频繁变更时，AI 面对的规则基线不稳定，V2 的"受控"可能变为"受控于一个不断变动的目标"。 |
| **冲突根因** | V7 的改进机制缺乏版本稳定期约束，与 V2 对规则稳定性的隐含依赖存在节奏差异。 |
| **建议** | 在 V7 中补充"改进生效节奏"：规则和行动模型的变更应有生效窗口（如任务边界），避免在任务执行中途变更规则基线。这类似于立法的"法不溯及既往"原则——新规则从下一个任务开始生效，当前任务仍按旧规则执行。 |

# 多角色 Skill 与多系统子 Agent 讨论补充记录

> 记录时间：2026-05-30
> 记录目的：避免当前会话上下文丢失，沉淀关于多角色思考执行模式、非系统 Agent Prompt 复用、可调用 Agent 容器和 41 规范修正方向的阶段性结论。

## 一、问题背景

用户希望实现"多角色讨论"的功能，核心诉求不是创建大量固定 Agent，而是让不同角色能够在隔离上下文中并行分析，最后由主控 AI 汇总，达到"又快又干净"的效果。

讨论中围绕以下问题展开：

1. `.trae/agents/` 下的自定义 Agent 是否能被主控 AI 直接调用；
2. 是否可以把一个固定 Agent 启动多个实例，并给每个实例注入不同角色参数；
3. 是否所有 Prompt 型自定义 Agent 都可以在调用时通过参数注入实现；
4. Skill 与多系统子 Agent 在多角色思考中的区别；
5. 41 多角色思考行动模型应如何表达这种机制。

## 二、已确认的技术事实

### 2.1 自定义 Agent 文件可读取，但不能被当前主控直接作为子 Agent 调用

`.trae/agents/` 下的自定义 Agent 文件可以被读取、理解和复用其中的 Prompt、描述、触发时机和角色边界。

但当前主控 AI 通过工具接口可调用的 `subagent_type` 是系统提供的固定列表，例如：

- `search`
- `general_purpose_task`
- `ui-designer`
- `frontend-architect`
- `backend-architect`
- `api-test-pro`
- `ai-integration-engineer`
- `devops-architect`
- `performance-expert`

因此，`.trae/agents/我的智能体.md` 这类非系统 Agent 不能被主控直接注册为或调用为新的 `subagent_type`。

### 2.2 Skill 不具备独立上下文和并行隔离能力

Skill 本质是可复用流程、提示词和执行说明的展开。它在当前主上下文中执行，不会天然形成独立上下文，也不提供角色间隔离。

因此，Skill 可以承接轻量多角色分析流程，但不能替代真正的多 Agent 并行隔离分析。

### 2.3 `general_purpose_task` 可作为可调用 Agent 容器

当前真正可由主控并行启动、并具备独立上下文的通用容器是 `general_purpose_task`。

它可以在调用时通过自然语言参数注入角色，例如：

| 实例 | 可调用 Agent 容器 | 注入角色参数 |
|---|---|---|
| 实例 1 | `general_purpose_task` | 治理角色：关注事实源、编号、规范一致性、Human Gate |
| 实例 2 | `general_purpose_task` | 架构角色：关注机制抽象、执行链路、上下文隔离 |
| 实例 3 | `general_purpose_task` | 安全角色：关注权限、写入、风险、不可逆操作 |
| 实例 4 | `general_purpose_task` | 验证角色：关注证据、检查、关闭条件、可审计性 |

这种方式可以实现：

- 多实例并行；
- 每个实例独立上下文；
- 每个实例角色参数不同；
- 子 Agent 输出回到主控；
- 主控统一汇总一致结论、分歧、风险、执行顺序和 Human Gate。

## 三、核心概念区分

### 3.1 Agent Prompt 模板

Agent Prompt 模板是可读取的角色定义、触发时机、关注点、输出格式和边界约束。

它可以来源于：

- `.trae/agents/*.md` 中的自定义 Agent 文件；
- specs 中的角色定义；
- docs 中的 Agent 定义摘要；
- 当前对话临时给出的角色要求。

Agent Prompt 模板本身不等于可调用 Agent 实例。

### 3.2 可调用 Agent 容器

可调用 Agent 容器是当前主控能够通过工具接口实际启动的 Agent 类型。

当前可用容器包括系统内置子 Agent，尤其是 `general_purpose_task`。未来如果平台允许主控直接调用 `.trae/agents/` 自定义 Agent，则自定义 Agent 也可以成为可调用 Agent 容器。

### 3.3 主控 AI

主控 AI 负责：

1. 判断是否需要多角色思考；
2. 判断采用 Skill 轻量模式还是多系统子 Agent 模式；
3. 选择角色或读取 Agent Prompt 模板；
4. 构造每个角色的调用参数；
5. 并行启动可调用 Agent 容器的多个实例；
6. 收集子 Agent 输出；
7. 汇总一致结论、分歧点、风险、执行顺序、事实源回写建议和 Human Gate。

## 四、关于"是否需要提前设计自定义 Agent"的结论

对于多角色讨论，不需要提前设计一批固定自定义 Agent。

如果自定义 Agent 的核心只是"角色 + Prompt + 输出格式"，则完全可以在调用 `general_purpose_task` 时通过参数注入实现。

提前创建自定义 Agent 的价值主要在于：

- 方便人在 Trae Agent 面板中手动选择；
- 沉淀常用 Prompt；
- 形成团队可读的角色模板；
- 作为未来平台可调用 Agent 的候选资产。

但它不是实现多角色并行隔离的必要条件。

不能被参数注入完全替代的是平台配置层能力，例如：

- 指定模型；
- 固定工具权限范围；
- MCP Server 绑定；
- 平台级 Agent 生命周期管理；
- 在 Agent 面板中的一键调用入口。

因此，准确结论是：

> Prompt 型自定义 Agent 可以通过调用时参数注入复用；平台配置型自定义 Agent 不能完全通过参数注入替代。

## 五、Skill 模式与多系统子 Agent 模式的决策关系

多角色思考应先由主控判断是否进入多角色分析场景。进入后再判断执行模式。

### 5.1 Skill / 主上下文轻量模式

适合：

- 普通讨论；
- 事实源读取较少；
- 不要求角色间结论隔离；
- 允许多个视角在同一上下文中串行分析；
- 用户希望快速得到结构化分析。

特点：

- 串行；
- 共用主上下文；
- 成本低；
- 角色间可能互相影响；
- 最终由主控直接汇总。

### 5.2 多系统子 Agent 模式

适合：

- 用户明确要求多 Agent、并行、独立上下文或结论隔离；
- 话题复杂，单一上下文容易污染判断；
- 需要多个角色独立形成结论；
- 需要并行读取或分析较多事实源；
- 分析结果将影响规范、规则、Agent、Skill、工具或事实源边界。

特点：

- 并行；
- 每个角色独立上下文；
- 角色结论先隔离形成；
- 成本更高；
- 子 Agent 输出回主控；
- 主控统一汇总。

### 5.3 难以取舍时的处理

当 Skill 轻量模式和多系统子 Agent 模式都可行，但难以判断是否需要升级时，应由主控说明差异并交给人选择。

可沉淀为规则：

> 默认轻量；需要隔离则 Agent；难以取舍则 Human Gate；所有结果回主控汇总；稳定事实按事实源边界回写。

## 六、对 41 多角色思考行动模型的修正方向

41 主文档后续应避免把 Agent 增强模式绑定为"创建固定自定义 Agent"。更稳妥的表达应是：

> Agent 增强模式通过可调用 Agent 容器实现。主控根据角色选择或 Agent Prompt 模板，为每个角色构造独立参数，并行启动一个或多个可调用 Agent 容器实例。每个实例在独立上下文中形成角色结论，输出返回主控，由主控完成汇总、风险判断、事实源回写建议和 Human Gate 判断。

建议在 41 中补充或调整以下概念：

1. **可调用 Agent 容器**：当前主控能够实际启动的系统子 Agent 或未来可被工具接口调用的自定义 Agent；
2. **Agent Prompt 模板**：可读取的角色定义和触发时机，可作为调用参数注入容器；
3. **自定义 Agent 文件边界**：存在 `.trae/agents/` 文件不等于主控可调用，不得假设其已成为可调度 Agent；
4. **模式选择规则**：默认 Skill / 主上下文轻量模式，需要结论隔离、并行委派或用户明确要求时升级为多系统子 Agent 模式；
5. **汇总责任**：无论 Skill 还是多系统子 Agent，最终汇总者都是主控 AI；
6. **Human Gate**：难以取舍或涉及创建、修改、启用 Agent / Skill / 规则 / 行动模型时，由人确认。

## 七、阶段性结论

本轮讨论形成的关键结论是：

1. 多角色思考不是一定要提前创建多个自定义 Agent；
2. 当前可落地方案是"可调用 Agent 容器 + 运行时角色参数注入 + 主控汇总"；
3. Skill 适合轻量多角色分析，但不能提供独立上下文；
4. `general_purpose_task` 可以作为当前最通用的隔离执行容器；
5. 非系统 Agent 的 Prompt 和触发时机可以被读取、吸收和注入，但不能自动注册为系统子 Agent；
6. 41 文档应从"固定 Agent 清单"或"预制 Agent 映射"转向"可调用 Agent 容器"模型；
7. 模式难以取舍时，应把 Skill 串行共上下文与多系统子 Agent 并行独立上下文的差异说明给用户，由用户选择。

# 角色定义形态与 PM Kit 对比分析补充记录

> 记录时间：2026-05-30
> 记录目的：沉淀关于角色定义形态、PM Kit 多角色讨论 Skill 问题分析、以及 LDVH 角色体系最终设计方向的决策。

## 一、用户提出的问题

用户提出建立一个"角色"生产对象，记录不同角色在 Skill 或 Agent 中的定义；在多角色讨论的 Skill 中，先通过工具获得角色索引，再根据需要调用角色信息；同时希望不同应用场景下返回的信息结构不同，因此考虑再构建"角色应用场景"生产对象进行约定。

## 二、角色是否应成为生产对象的准入分析

按 06 §6.1 生产对象准入条件逐条检查：

| 准入条件 | 角色是否满足 | 说明 |
|---|---|---|
| 需要独立追踪状态 | 弱 | 角色定义是相对稳定的配置，状态流转需求弱 |
| 需要可验证的完成标准 | 不满足 | 角色定义没有"完成"概念 |
| 需要关闭证据 | 不满足 | 角色不会被"关闭" |
| 需要关联其他对象 | 满足 | 角色需要被 Skill、Agent、行动模型引用 |
| 需要被工具展示、排序、过滤、聚合或审计 | 满足 | 角色索引需要被工具读取和聚合 |
| 不成为生产对象就会导致不可追踪 | 中等 | 角色定义散落各处会导致不一致 |

角色不完全满足生产对象核心准入条件。它更像配置型参考数据，而不是有状态流转的工程生产事实。

但角色定义需要跨 Skill、Agent、行动模型和工具共享，如果散落各处会违反 03 单一事实源原则。

## 三、"角色应用场景"是否应成为独立生产对象

角色应用场景本质上是"同一角色定义 + 不同输出结构约束"。它更像是角色定义的一个字段维度，而不是独立实体。

如果拆成独立对象，会导致：

1. 对象数量膨胀；
2. 角色和角色应用场景之间是强 1:N 关系，每次读取角色都要额外读取应用场景；
3. 角色应用场景没有独立状态流转和关闭条件；
4. 角色应用场景的生命周期完全依附于角色。

因此，不建议创建独立的"角色应用场景"生产对象。输出格式差异应作为角色定义的字段维度解决。

## 四、角色定义形态的三种选项

| 形态 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| specs 规范中的结构化章节 | 权威、稳定、符合 LDVH 事实源边界 | 不可被工具直接解析、项目级扩展困难 | 角色高度稳定、跨项目通用 |
| Role 生产对象（ldvh-base/roles/） | 结构化 YAML、可索引、可扩展、可被工具解析 | 需要定义新生产对象、增加维护成本 | 角色需要项目级自定义 |
| specs 定义通用角色 + ldvh-base/roles/ 承载项目扩展 | 兼顾稳定性和扩展性 | 两层结构，需要明确边界 | 通用角色稳定 + 项目角色可扩展 |

## 五、用户决策：角色定义放在稳定规范中

用户确认角色定义应放在 specs 稳定规范中，不需要创建 Role 生产对象，也不需要 ldvh-base/roles/ 目录。

这意味着：

1. 角色定义是跨项目通用的稳定规则，不是项目级可自定义的动态实例；
2. 角色定义的权威位置在 specs 规范中（可能是 41 主文档或 41 附件型实践子文档）；
3. 不需要为角色创建独立的生产对象编号（不占用 10-39 区段）；
4. 角色的输出格式差异作为规范中的字段定义，不单独创建"角色应用场景"对象；
5. 工具可以从 specs 规范中解析角色定义，提供索引和聚合能力。

## 六、PM Kit 多角色讨论 Skill 的问题分析

PM Kit 把多角色讨论设计成 Skill（`pm-kit-multi-role-analysis`），存在以下问题：

### 6.1 Skill 没有独立上下文，但多角色讨论需要角色间隔离

08.04 定义了轻量模式和 SOLO Agent 模式。但 Skill 本身没有独立上下文。轻量模式下所有角色共享主上下文，角色间互相可见、互相影响。SOLO Agent 模式下 Skill 只是"建议用户调用 SOLO Agent"，不能调度 Agent。两种模式之间的过渡是断裂的。

### 6.2 角色矩阵硬编码在规范文档 Markdown 表格中

08.04 把 20 个角色定义在 Markdown 表格里。这导致：

1. 不可被工具解析：Markdown 表格不是结构化数据；
2. 不可被项目扩展：角色定义写死在 PM Kit 规范中；
3. 不可被 Skill 和 Agent 以结构化方式共享：Skill 只能读取文本；
4. 变更类型-角色映射也是硬编码。

### 6.3 Skill 把流程和角色定义耦合在一起

Skill 同时承载了执行流程、角色矩阵引用、输出格式定义和模式升级判断。修改任何一项都需要同时修改 Skill 和规范。

### 6.4 Skill 的"SOLO Agent 模式"只是建议，不是真正的模式切换

Skill 不能调度 Agent，用户需要手动切换。SOLO Agent 有自己的编排逻辑，不一定遵循 08.04 的角色矩阵和输出格式。轻量模式和 SOLO Agent 模式之间没有统一的汇总逻辑。

## 七、LDVH 应避免的 PM Kit 设计问题

LDVH 41 多角色思考行动模型应避免以下问题：

1. 不把角色定义硬编码在 Markdown 表格中——应使用结构化字段定义；
2. 不把执行流程和角色定义耦合在 Skill 中——角色定义在 specs，执行流程在行动模型；
3. 不让模式切换变成"建议用户手动操作"——主控应能直接启动多系统子 Agent；
4. 不让输出格式固定在 Skill 中——输出格式应作为角色定义的字段维度；
5. 不创建独立的"角色应用场景"生产对象——输出格式差异用字段解决。

## 八、LDVH 41 多角色思考最终设计方向

基于全部讨论，41 多角色思考行动模型的设计方向如下：

### 8.1 角色定义

- 角色定义放在 specs 稳定规范中（41 主文档或其附件型实践子文档）；
- 角色定义使用结构化字段，不使用 Markdown 表格；
- 角色定义包含：角色名、维度、关注点、触发条件、输出格式（按场景区分）、Prompt 模板；
- 角色定义不需要成为生产对象，不需要 ldvh-base/roles/ 目录；
- 角色定义的变更通过规范变更流程和 Human Gate 管理。

### 8.2 执行模式

- 默认 Skill / 主上下文轻量模式：串行、共用上下文、成本低；
- 多系统子 Agent 模式：并行、独立上下文、结论隔离、通过可调用 Agent 容器实现；
- 模式选择由主控判断，难以取舍时 Human Gate 交用户选择；
- 所有模式最终由主控汇总。

### 8.3 可调用 Agent 容器

- 当前可用容器为系统内置子 Agent，尤其是 `general_purpose_task`；
- 主控根据角色定义构造参数，注入可调用 Agent 容器；
- 每个角色启动一个独立实例，实现结论隔离；
- 未来如果平台支持主控调用自定义 Agent，可扩展容器类型。

### 8.4 Agent Prompt 模板

- 角色定义中的 Prompt 模板可作为调用参数注入容器；
- `.trae/agents/` 中的自定义 Agent 文件可作为 Prompt 模板参考；
- 存在自定义 Agent 文件不等于主控可调用，不得假设其已成为可调度 Agent。

### 8.5 输出格式

- 输出格式作为角色定义的字段维度，按应用场景区分；
- 不创建独立的"角色应用场景"生产对象；
- Skill 和 Agent 从角色定义中读取对应场景的输出格式。

### 8.6 汇总与回写

- 无论 Skill 还是多系统子 Agent，最终汇总者都是主控 AI；
- 汇总包含：一致结论、分歧点、风险、执行顺序、事实源回写建议、Human Gate 判断；
- 稳定事实按事实源边界回写，过程分析不回写。

### 8.7 核心决策规则

> 默认轻量；需要隔离则 Agent；难以取舍则 Human Gate；所有结果回主控汇总；稳定事实按事实源边界回写。
