## 1. LDVH 为什么存在

Vibe Coding 让人用自然语言表达目标，由 AI 推理生成实现，门槛低、反馈快、产出多。但 AI 生成代码的本质不是确定性编译，而是基于开发环境上下文、模型训练经验和参数形成的概率性推理，因此天然存在上下文依赖、概率性输出和无状态等问题。

虽然目前 Vibe Coding 已经能够较好地完成单个功能、局部修复，也能在明确的测试目标和验收反馈下承担较长时间的连续工作。但真实开发不是单点工作的叠加，它往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是项目在持续演进中，如何避免从“开始还不错”逐渐变成“难以继续做”的问题。概括如下：

设计理念：

1. 以 AI 执行者为第一服务对象；
2. 以事实源为判断依据；
3. 以保障与衔接层为落地通道；
4. 以五类构成要素为组织骨架；
5. 以 V1-V10 价值标准为行动标尺。

构成要素：

1. 用规范体系定义产品、边界和保障要求；
2. 用事实模型组织事实、状态、证据和经验；
3. 用行动模板沉淀可复用行动结构；
4. 用 Code 提供确定性执行、校验和反馈；
5. 用 Web 桥接 Human 与 AI，呈现状态、风险和证据。

最终目标：

1. 让 AI、Human、Code 可以各展所长，使 Vibe Coding 推理更稳定、结果更可控、产出更高效；
2. 进而让环境、模型、使用者可以自由组合，使 Vibe Coding 使用更方便、选择更丰富、协同更顺畅。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于实践沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

LDVH 以 AI 执行者为第一服务对象。要说明这一点，需要先理解 AI 执行者的依赖、能力与本质。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——缺少可用工具或环境能力时，AI 容易停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的工具或环境能力，并把反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

基于这些依赖、能力与本质，LDVH 的设计重点，不是要求 AI 自发变得可靠，而是以事实源为判断依据，以五类构成要素为组织骨架，通过保障与衔接层落地到具体协作环境，最终服务于 AI 实现 V1-V10 的价值闭环。

## 3. 以事实源为判断依据

LDVH 以事实源为判断依据，并提出两项要求：

1. 有 Git，可溯源。事实源以 Git 可追踪文件为唯一有效承载形态，稳定事实的形成、修改、验证和关闭都能回到明确的 Git 文件位置和 Git 溯源记录；聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图等只有回写到 Git 文件事实源并完成验证后，才可能成为稳定事实。

2. 有组织，可消费。事实源不是材料堆积，而是要形成清晰的事实组织：事实放在哪里，边界是什么，引用关系如何建立，状态如何变化，结果回写到哪里。组织清晰的事实源才能被 Code 消费，进而放大事实源的价值——让 AI 少读、少猜、少漂移，让验证、回写和接续有稳定入口，而不只是人能看懂的材料。

上述两项要求共同构成本文所称的事实源边界：符合两项要求，才是 LDVH 认可的事实源；不符合的，不得作为稳定事实的承载位置。后续 §5、§7、§8 中“事实源边界”均指这两项要求。

事实模型、Code 和 Web 可以承接、消费、展示或辅助回写事实，但不得替代事实源整体。具体事实源类型、证据规则、回写规则、吸收规则、Code 消费规则和 Git 溯源等规则，由后续相关规范承接；本文只定义上位原则。

## 4. 以保障与衔接层为落地通道

LDVH 以保障与衔接层为落地通道。没有保障与衔接层，规则只能停留在"应该如此"，无法被稳定读取、执行、验证和回写。

保障与衔接层不新增构成要素，也不替代事实源。它围绕五类构成要素的应用，形成三层职责：

1. 内部保障：回答 LDVH 凭什么让规则不落空，如何形成能力、承接机制、证据和缺口分流；
2. 外部衔接：回答 LDVH 如何进入具体协作环境，使保障能力能够在环境中执行；
3. 行动指南：回答 AI 每次行动前可以提前获得的帮助与约束，读取什么、先做什么、何时停止、如何验证、如何分流。

三层职责的具体展开由后续规范承接；本文只定义上位定位。

## 5. 以五类构成要素为组织骨架

LDVH 以五类构成要素为组织骨架，把规则、事实、行动、确定性反馈和 Human-facing 呈现分开归口，形成 AI 可定位、可行动、可验证、可交还的结构。

LDVH 的五类构成要素包括：

1. 规范体系。承接上位规则、边界、价值标准和保障要求，使 AI 能据此推导目标、识别场景、判断行动并生成验收标准；
2. 事实模型。在事实源边界内组织需要对象化、状态化或证据化管理的事实，使结论、状态、证据和经验有稳定承载；
3. 行动模板。沉淀重复场景中的可复用行动结构，使 AI 在相似任务中有稳定步骤、验证入口和交还方式；
4. Code。提供解析、索引、聚合、校验、测试、上下文压缩和受控写入等确定性反馈，降低 AI 的读取、判断和验证成本；
5. Web。呈现状态、风险、证据、待确认事项和验收信息，帮助 Human 进行方向校正与决策，并让确认结果可被 AI 消费。

五类构成要素不是上下层级，也不是资产分类或自动准入清单。规则、对象、字段、附件、工具、Code 输出、Web 展示或派生机制等作为构成要素实践纳入 LDVH 前，必须先归属到五类构成要素或保障与衔接层的对应承载位置，并接受事实源边界和 V1-V10 价值判断。

AI 可以准备归口建议、依据和风险说明。不能说明归属、价值、预期减少的 AI 负担、事实源边界和验证方式的内容，不得纳入；可能制造第二事实源、绕过 Human Gate、压缩 Human 关键确认，或只增加维护对象而不能减少 AI 负担的内容，必须按第 8 节评估 Human Gate。

## 6. 以 V1-V10 价值标准为行动标尺

LDVH 以 V1-V10 价值标准为行动标尺。五类构成要素、保障与衔接层及其下属机制，都必须服务以下价值判断中的一项或多项。V1-V10 不是独立于第 1 节和第 2 节的新目标，而是用于判断某项机制是否真的能缓解 AI 的概率性推理、上下文依赖和无状态风险。

本文中，“V1-V10 价值判断”是正式对象名称；“价值标准”“行动标尺”和表格中的“标准”均指 V1-V10 的价值维度。“准入作用”指构成要素实践或派生机制纳入前必须接受 V1-V10 判断；“反向判断”指表格中“不满足时的表现”所对应的风险识别方式。它们均不构成独立机制或独立对象。

字段、附件、资产承载物、工具、派生关系、Code 输出和 Web 展示等都不是与五类构成要素和保障与衔接层并列的准入主体。它们必须先归属到规范体系、事实模型、行动模板、Code、Web 或保障与衔接层的对应承载位置，再接受 V1-V10 判断。

派生机制只能作为五类构成要素或保障与衔接层的实现方法之一。它服务哪些 V 项取决于自身归属和用途，但不得成为独立价值标准、独立构成要素、事实源，或脱离其归属承载位置的独立工作对象；具体结构、生成、展示和消费边界由后续对应实践定义。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | AI 能否根据当前目标和场景快速定位应读取的事实源、规范入口、工作状态和工具入口 | AI 盲目全文阅读、找不到入口、遗漏关键事实或规范规则 |
| V2 | 可行动理解 | AI 能否在足够但不过载的上下文中形成可执行的目标、边界、事实、状态和验收标准理解 | AI 反复询问已有事实、误读项目边界、遗漏关键约束，或读了很多仍不能行动 |
| V3 | 正确判断 | AI 能否判断事实源边界、风险、阻塞、工具需求、行动模板复用需求和专项协作调度需求 | AI 误判工作性质、错过风险或阻塞、错误选择工具、行动模板或专项协作方式 |
| V4 | 稳定执行 | AI 能否依据规范体系、事实模型、行动模板和保障与衔接层形成可执行路径、拆解步骤并稳定推进工作，而不是凭聊天记忆自由发挥 | AI 绕过规范规则、跳过工作状态、无法形成稳定路径或直接修改不该修改的事实 |
| V5 | 门禁识别 | AI 能否识别 Human Gate，知道何时必须暂停并等待人确认 | AI 擅自执行高影响变更、跳过确认、误关闭工作对象 |
| V6 | 强制验证 | AI 的关键行动、状态变更、事实回写和交付结论能否通过 Code 校验、检查结果、审查证据、Web 呈现或 Human 确认验证；没有验证证据的完成不视为真正完成 | AI 只凭自述判断完成、用推测性表述替代验证，或验证结果缺失、不可复现 |
| V7 | 证据沉淀 | AI 的验证结果、执行证据、决策依据或 Git 提交记录能否在需要追溯时被稳定找到 | 完成了但无法证明、结果只存在聊天里、后续无法追溯 |
| V8 | 可靠回写 | 稳定事实能否按事实源边界回写到 Git 文件事实源 | 事实漂移在聊天、缓存、Web 页面状态、工具输出或派生数据中 |
| V9 | 人类确认质量 | AI 能否向 Human 提供足够的事实源、证据、项目态势、风险、影响和待确认事项，使 Human 给出可被 AI 消费的高质量确认 | Human 只能凭感觉验收，AI 无法获得明确、可追溯、可执行的确认 |
| V10 | 持续完善 | AI 能否识别可复用经验、反复问题和体系缺口，并推动其回到规范体系、事实模型、行动模板、Code、Web 或保障与衔接层中 | 同类错误反复发生，可复用经验、规范规则缺口和工具能力不足没有沉淀 |

## 7. 规范保障要求

00 是 LDVH 的最高价值锚点。后续规范、附件、构成要素实践和派生机制不得削弱本文定义的存在理由、AI 第一服务对象、事实源边界、保障与衔接层、五类构成要素和 V1-V10。

00 不重复每篇规范都应具备的入口可见、结构校验、生命周期同步和 Code 消费等基础治理要求；保障与衔接由 01 统一定义，Specs 结构治理由 04 统一定义。本文只声明 00 作为最高价值锚点特有的上位约束承接要求。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续规范、附件、构成要素实践和派生机制必须承接本文定义的存在理由、AI 第一服务对象、事实源边界、保障与衔接层、五类构成要素、V1-V10 和 Human Gate 边界，不得改写、绕开或弱化为普通建议 | 00、01、02、Human Gate、后续规范创建/审核行动模板或一致性核对；具体执行闭环不在 00 定义 | 价值治理 | 新增、修改、合并、拆分、重命名或迁移规范，或后续机制试图重新解释本文最高锚点时 |

## 8. Human Gate

以下情况必须暂停并等待 Human 确认：

1. 改变第 1 节“LDVH 为什么存在”的表述、定位或方法；
2. 改变第 2 节“以 AI 执行者为第一服务对象”的依赖、能力、本质或支撑方向；
3. 新增、删除、改名或重排五类构成要素；
4. 将事实源改为构成要素，或将派生机制、附件、工具输出、Web 页面状态、运行时索引升级为事实源；
5. 改变 V1-V10 的编号、含义、准入作用或反向判断；
6. 将运行闭环、事实对象生命周期、具体流程步骤或具体环境适配细则写入 00，导致 00 替代后续构成要素实践；
7. 将保障与衔接层改为构成要素，或绕过 01 直接在下位规范各自发明互相竞争的保障衔接基础规则；
8. 用对象数量、页面数量、工具数量、附件数量或资产数量替代 V1-V10 价值判断。

以下情况必须评估 Human Gate；确认影响 00 最高锚点、事实源边界、保障与衔接层、五类构成要素或 V1-V10 时，必须暂停确认：

1. 调整本文待补齐事项的归口、范围或关闭条件；
2. 新增可能影响后续构成要素实践纳入边界的价值判断、风险边界或检查标准；
3. 后续规范、附件、Code、Web 或保障与衔接承载物试图把本文原则解释为自身执行豁免；
4. 规范核对发现本文与 01、02 或后续单篇规范存在上位冲突。

Human Gate 只能由 Human 完成确认、授权、方向校正或验收。AI 可以准备事实源、影响范围、风险、待确认事项和建议选项，但不得把 AI 结论、Code 校验、工具成功输出或 Web 展示结果替代 Human Gate。

1. 保障与衔接层的具体承载物、资产登记和环境适配规则，应由后续对应规范承接；
2. V1-V10 的后续消费、检查、映射和展示方式，应在 01、Code、Web 和保障与衔接相关规范单篇确认后继续补齐，并回指本文价值锚点。
