## 1. 00 的当前定位

00 只定义 LDVH 的根语义：存在理由、第一服务对象、基础服务形式、事实源信息锚点、五类构成要素、V1-V8 价值标准，以及上位验证边界、Human Gate 和 Stop Conditions。

当前五点设计理念为：

1. 以 AI 执行者为第一服务对象；
2. 以 LDVH Helper CLI 为基础服务形式；
3. 以事实源为信息锚点；
4. 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素；
5. 以 V1-V8 价值标准为行动标尺。

00 的判断边界为：

- 具体事项命中来源规范的适用范围时，AI 必须执行该规则规定的要求；
- 未命中具体规则时，LDVH 不限制 AI 的普通求解路径；
- 触发 Human Gate 或 Stop Conditions 时，受影响的行动、对象或声明按来源规则暂停、分流或交还；
- 未接入或未验证的范围必须如实说明，不得声明为已保障、已 integrated 或已完成。

## 2. 00 的定义颗粒度

00 保留在“后续规范改名、重编号、合并、拆分或更换实现后仍然成立”的层级。

00 不定义：

- 后续 Specs 的具体编号和文件路径；
- Helper CLI 的命令、响应字段和实现方式；
- 管辖与 target 解析算法；
- 环境 integrated 的具体判定流程；
- 验证工具和验证命令；
- 事实对象字段、状态机和回写格式；
- Code、Hook、插件、adapter 或 Web 的实现细节。

这些内容由承担对应职责的下游规范定义。

## 3. 引用方向

权威引用遵守“谁需要谁，谁引用谁”：

1. 下位规范通过 `basis` 指向上位依据；
2. 规则或能力的消费者指向提供者；
3. 附件通过 `parent_spec` 指向授权正文。

上位规范不反向登记下位规范、实现者或消费者。`related_specs`、下位规范列表、消费者列表和反向引用由 Code 根据正向关系派生，只用于导航，不形成第二规则源。

00 只授权下游职责，不绑定当前编号或文件。权威依赖图必须无环；职责标识、唯一性、冲突处理和解析方式由承担 Specs 共同结构治理职责的规范定义。

1. 收口 00：去除下游具体编号和反向引用，补足 Helper 服务范围与规则适用范围的层次区分，校准事实承载、验证审核和 integrated 的上位表达；
