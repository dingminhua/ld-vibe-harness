## 一、评估结论摘要

MCP Shrimp Task Manager 是面向 AI 编程助手的任务管理型 MCP Server。它把自然语言目标转化为结构化任务，提供任务规划、任务分解、依赖管理、执行追踪、完成验证、跨会话记忆、研究模式、项目规则初始化和 Web 任务查看器等能力。其核心价值不是“替人管理项目”，而是为 AI Agent 提供一组可调用的任务治理工具，让 AI 在长上下文、多步骤开发中减少遗忘、重复劳动和执行混乱。

对 LD Vibe Harness 而言，Shrimp Task Manager 最值得借鉴的不是具体 MCP 实现，而是它把 AI 编程过程拆成“计划—分解—执行—验证—反思—记忆”的工具化工作流，并通过持久化任务数据维持跨会话连续性。这与 LDVH 的核心问题高度同构：AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。

但 Shrimp Task Manager 与 LDVH 的定位不同。Shrimp 更像一个任务编排与执行辅助工具；LDVH 是围绕 Git 文件事实源、生产对象、行动模型、Human Gate 和工具辅助能力形成的工程化驾驭框架。因此，LDVH 可以借鉴 Shrimp 的交互工具、任务流程和 Agent 友好设计，但不能把 Shrimp 的运行时数据、MCP Server 状态或 Web GUI 状态直接提升为 LDVH 最终事实源。

本文建议：LDVH 不应照搬 Shrimp Task Manager，而应吸收其“任务工具化”“步骤显式化”“跨会话连续性”“研究模式”“执行验证”“项目规则初始化”“Web 可视化”的思想，并将这些思想重新落到 LDVH 的五类构成要素中：以 Git 文件作为最终事实源，以 Harness 生产对象承载稳定事实，以 Harness 行动模型约束 AI 行动，以 Harness 工具降低读写和展示成本。

## 二、MCP Shrimp Task Manager 的关键特征

### 2.1 面向 AI Agent 的任务管理 MCP Server

Shrimp Task Manager 通过 MCP 向 AI 编程客户端暴露任务管理工具。AI 可以调用这些工具完成任务规划、任务分析、任务拆分、任务查询、任务更新、任务执行、任务验证、研究和反思等动作。

其设计重点包括：

1. 把自然语言目标转化为结构化任务；
2. 把复杂任务拆成可执行、可验证的子任务；
3. 维护任务之间的依赖关系；
4. 在执行过程中持续追踪状态；
5. 在任务完成后进行验证；
6. 将任务历史和项目知识持久化，供后续会话读取；
7. 通过 Web 任务查看器提高人的可观察性。

这说明 Shrimp 的第一服务对象也是 AI 执行者，而不是传统项目经理。它不是先为人设计一个项目管理系统，再让 AI 填写；而是直接面向 AI 的执行流程设计工具接口和提示模板。

### 2.2 任务流程显式化

Shrimp 将 AI 编程中的隐性过程显式拆解为多个动作：规划、分析、分解、执行、验证、反思、研究和查询。相比让 AI 在一次对话中自由发挥，这种拆解能降低长任务中的上下文漂移。

对 LDVH 有启发的是：AI 行动不应只靠通用提示词约束，而应有明确的行动阶段和阶段产物。任务治理的关键不是“告诉 AI 要认真”，而是把 AI 的行动拆成可调用、可检查、可回写的步骤。

### 2.3 跨会话记忆与任务持久化

Shrimp 强调任务和执行历史的持久化，避免 AI 因上下文窗口、会话切换或重复询问而丢失进展。其数据目录可以存储任务数据、历史备份和项目知识。

这与 LDVH 的“AI 不依赖聊天记忆”目标一致。但二者在事实源边界上存在差异：Shrimp 的持久化目录偏向工具运行数据；LDVH 要求稳定事实必须回到 Git 可追踪文件，并且同一事实只能有一个权威位置。

因此，LDVH 可借鉴“跨会话连续性”的目标，但应坚持由 `ldvh-base/` 和 `specs/` 等 Git 文件事实源承载稳定事实。工具数据可以作为派生数据或受控写入入口，不能独立成为最终事实源。

### 2.4 项目规则初始化

Shrimp 提供项目规则初始化能力，用于让 AI 在项目内形成编码规范、开发约定和执行标准。这对新会话或新 Agent 进入项目特别重要。

LDVH 已有 Rules、Skill、Agent、specs 和项目规则的分层设计。可借鉴点不在于让工具自动生成规则，而在于：项目入口规则应服务 AI 的行动启动，让 AI 能快速识别项目定位、必读文档、事实源边界、Human Gate 和检查命令。

### 2.5 研究模式与反思机制

Shrimp 提供研究模式和反思工具，用于支持 AI 在执行前系统性调查技术方案，或在执行后复盘任务结果。

这对 LDVH 的启发是：调研、决策、执行和复盘应区分承载。研究过程可以由工具辅助，但稳定的结论应回写到评估文档、ADR、Memo、Pitfall 或其他合适对象中。反思不是聊天中的一句总结，而应在必要时转化为可追踪事实。

### 2.6 Web 任务查看器

Shrimp 的 Web 任务查看器提供任务列表、搜索过滤、标签组织、Agent 管理、自动刷新和项目历史查看等能力。其价值在于提升人的可观察性和操作效率。

这与 LDVH 的 Web Tools 方向一致。Web 界面应桥接 AI 优先的结构化信息和人的可读可操作需求，但 Web 页面状态不应替代 Git 文件事实源。LDVH 可借鉴其可视化思路，但必须将工具展示定位为读取、聚合和受控写入事实源的界面。

## 三、与 LDVH 五类构成要素的映射

| Shrimp 特征 | LDVH 可映射位置 | 借鉴方式 | 边界要求 |
|---|---|---|---|
| MCP Server 工具接口 | Harness 工具 | 可借鉴“AI 可调用工具集”的设计，把任务操作、查询、验证和研究能力工具化 | 工具不能成为最终事实源 |
| 任务规划与分解 | Harness 生产对象 + 行动模型 | 可映射到 Task、TaskSet、Checklist、Scenario 等对象和行动阶段 | 任务稳定状态应回写 `ldvh-base/` |
| 依赖管理 | Harness 生产对象 | 可借鉴任务依赖字段、阻塞关系和执行顺序检查 | 依赖关系应有结构化权威字段 |
| 执行追踪 | Harness 生产对象 + Evidence | 可借鉴执行状态、进度记录和验证结果 | 执行证据应进入 Evidence、Change 或 Task 检查字段 |
| 任务验证 | Harness 行动模型 | 可借鉴 verify 阶段，要求 AI 在完成前执行检查 | 验证通过不等于 Human Gate 通过 |
| 跨会话记忆 | Git 文件事实源 | 可借鉴跨会话连续性目标 | 不能把工具内存、缓存或备份文件作为唯一事实源 |
| 项目规则初始化 | Trae Solo 环境机制 + specs | 可借鉴“进入项目先建立规则入口”的思路 | 规则新增或改变触发 Human Gate |
| 研究模式 | specs/evals、ADR、Memo | 可借鉴调研工具化和结论沉淀 | 调研结论进入正式规范或 ADR 后才有执行效力 |
| 反思机制 | Pitfall、Change、ADR | 可借鉴执行后复盘 | 稳定经验应写入对应对象，不停留在聊天中 |
| Web 任务查看器 | Web Tools | 可借鉴任务可视化、筛选、历史查看和人机确认界面 | Web 展示不得与 Git 文件事实源冲突 |

## 四、LDVH 应重点吸收的设计原则

### 4.1 以 AI 行动阶段设计工具，而不是以人类表单设计工具

Shrimp 的工具划分围绕 AI 的行动过程展开：规划、分析、拆分、执行、验证、反思、研究。这个方向符合 LDVH “以 AI 执行者为第一服务对象”的定位。

LDVH 后续设计工具时，应优先问：AI 在当前场景下需要什么最小可行动上下文？需要调用什么能力？需要写回什么事实？需要何时暂停？而不是先问页面上应该有几个表单字段。

### 4.2 把任务从“待办清单”升级为“可执行对象”

Shrimp 的任务不是简单 todo，而是带有描述、状态、依赖、执行指引、验证方式和历史记忆的工作单元。LDVH 的 Task 对象也应坚持这个方向：Task 不是聊天中的计划摘要，而是可被 AI 读取、可被工具检查、可被人验收、可被 Git 追踪的生产对象。

这意味着 LDVH 的 Task 规范应特别关注：

1. 任务目标是否清晰；
2. 任务边界是否可判断；
3. 依赖和阻塞是否可解析；
4. 执行证据是否可追溯；
5. 验收标准是否可检查；
6. Review 和 Human Gate 是否可区分。

### 4.3 将“验证”设为任务完成的前置动作

Shrimp 将 verify_task 作为任务流程的一部分，提醒 AI 不应只完成实现，还要检查结果。LDVH 应吸收这一点，把验证前置为关闭任务、回写证据或请求验收前的必要阶段。

但 LDVH 需要进一步区分：

1. 工具验证：命令、测试、lint、类型检查或结构校验通过；
2. AI 自检：AI 基于规则和任务目标检查是否满足要求；
3. 人类验收：人基于事实源、证据和展示结果确认是否接受；
4. Human Gate：高影响变更在执行前或关键节点必须暂停确认。

验证可以支持验收，但不能替代验收；AI 自检可以降低风险，但不能绕过 Human Gate。

### 4.4 将记忆沉淀为可追踪事实，而不是工具私有缓存

Shrimp 的跨会话记忆解决了 AI 编程中的真实痛点。LDVH 必须吸收这一目标，但实现方式应更强调事实源纪律。

在 LDVH 中，长期有价值的记忆应按性质进入不同承载：

| 记忆类型 | 建议承载 |
|---|---|
| 稳定规范 | `specs/01-69` |
| 外部资料摘录 | `specs/refs/` |
| 项目级评估 | `specs/evals/` |
| 任务状态与执行字段 | `ldvh-base/tasks/` |
| 决策结论 | `ldvh-base/adrs/` 或对应 ADR 目录 |
| 执行证据 | `ldvh-base/evidence/` |
| 变更记录 | `ldvh-base/changes/` |
| 经验教训 | `ldvh-base/pitfalls.md` 或 Pitfall 对象 |

工具可以帮助收集、展示和写入这些记忆，但不能把自己的数据库或缓存变成权威事实源。

### 4.5 把研究模式纳入规范化调研链路

Shrimp 的 research_mode 对 LDVH 有直接借鉴价值。LDVH 的 specs/evals 正是项目评估、设计探索和方案比较的承载区。后续可以考虑形成“研究模式行动模型”：

1. 识别调研问题；
2. 确认调研边界和执行效力；
3. 收集资料并标注来源；
4. 按 LDVH 架构映射可借鉴点；
5. 区分可直接采用、需改造采用和不适合采用；
6. 将稳定结论进入 evals、ADR 或正式规范；
7. 对正式规范升级触发 Human Gate。

这会让调研从“聊天里问一问”变成可审查、可追踪、可复用的工程活动。

### 4.6 Web Tools 应服务确认质量

Shrimp 通过任务查看器提升任务可见性。LDVH 的 Web Tools 也应服务 V6“人类确认质量”：让人能看到状态、风险、证据、缺口和待确认事项。

但 LDVH Web Tools 的目标不应是复制一个通用任务管理软件，而是围绕 Harness 生产对象和行动模型提供视图，例如：

1. 当前任务、阻塞和依赖；
2. 待 Human Gate 确认事项；
3. 任务证据与验证结果；
4. 规范和规则命中情况；
5. 变更记录和影响文件；
6. Pitfall 与重复风险提示。

## 五、不应照搬的部分

### 5.1 不应把 MCP Server 状态视为最终事实源

Shrimp 的 MCP Server 可以保存任务数据和历史，但 LDVH 的最终事实源必须是 Git 可追踪文件。若未来 LDVH 接入类似 MCP 工具，该工具也只能读取、聚合和受控写入事实源，不能在工具私有目录中维护另一套权威状态。

### 5.2 不应让自动分解绕过人的边界确认

自动任务分解可以提升效率，但分解结果可能改变范围、优先级、风险或事实源位置。LDVH 中涉及高影响变更、规范升级、目录事实源边界改变、远程 Git 操作、规则/Skill/Agent 改动等事项，仍必须触发 Human Gate。

### 5.3 不应把验证工具等同于交付质量

Shrimp 的验证流程有价值，但验证命令通过只代表部分质量标准满足。LDVH 的交付质量还包括事实源回写、证据沉淀、Human Gate 识别、规范一致性和人类确认质量。

### 5.4 不应复制思维链内容作为事实

Shrimp 强调思维链、反思和推理过程。LDVH 可以借鉴“反思”动作，但不应把完整推理过程作为事实源保存。应保存的是可审查的结论、依据、风险、决策和后续行动，而不是不可验证的内部推理文本。

### 5.5 不应把项目规则初始化变成规则泛滥

规则入口有助于 AI 稳定进入项目，但规则过多会造成上下文噪音和维护成本。LDVH 应强调规则分层、最小入口、场景加载和权威引用，避免每次调研或每个工具都生成一套重复规则。

## 六、对 LDVH 后续建设的建议

### 6.1 在行动模型中补齐任务生命周期

建议在 `40-69` 行动模型区间中，后续补齐任务生命周期相关规范，明确 AI 从接收意图到任务关闭的标准动作：

1. 读取上下文；
2. 识别场景；
3. 判断事实源边界；
4. 判断 Human Gate；
5. 拆解任务；
6. 执行任务；
7. 记录证据；
8. 执行验证；
9. 请求验收或关闭；
10. 回写 Change、Pitfall 或 ADR。

### 6.2 在 Task 对象规范中强化依赖和验证字段

Shrimp 对依赖管理和验证流程的强调，提示 LDVH 的 Task 对象不应只记录状态，还应能表达依赖、阻塞、完成标准和验证证据。后续 Task 规范可评估是否明确以下字段或关系：

1. depends_on；
2. blocks；
3. acceptance_criteria；
4. verification；
5. evidence_refs；
6. review；
7. human_gate；
8. change_refs。

具体字段是否进入正式规范，应在 Task 对象规范阶段评估，不由本文直接决定。

### 6.3 建立“研究模式”实践路径

建议将 specs/evals 作为研究模式的主要落点，形成面向 AI 的调研写作骨架：

1. 调研对象；
2. 调研边界；
3. 外部资料来源；
4. 与 LDVH 架构映射；
5. 可借鉴点；
6. 不适用点；
7. 进入正式规范或 ADR 的候选事项；
8. 后续行动。

这样可以把类似本文的外部工具评估变成可复用流程。

### 6.4 将 Web Tools 设计为事实源观察与受控写入界面

Shrimp 的任务查看器说明 Web 可视化对 AI 任务治理很重要。LDVH 后续 Web Tools 应围绕 Git 文件事实源设计，而不是围绕独立数据库设计。核心方向包括：

1. 从 `ldvh-base/` 聚合任务、证据、变更和风险；
2. 从 `specs/` 展示规则命中和规范引用；
3. 标出 Human Gate 待确认项；
4. 展示验证结果和缺失证据；
5. 提供受控写入入口并生成 Change 记录。

### 6.5 评估 MCP 作为 Harness 工具接入形式

Shrimp 的 MCP Server 形态说明：MCP 适合将任务治理能力暴露给 AI 客户端。LDVH 后续可以评估是否提供 MCP Server，但应遵守以下原则：

1. MCP Server 是 Harness 工具的一种实现形式；
2. MCP Server 读取 Git 文件事实源；
3. MCP Server 的写入必须受事实源边界和 Human Gate 约束；
4. MCP Server 的缓存和索引可从事实源再生成；
5. MCP Server 不定义新的规范权威位置。

## 七、可转化为正式规范或 ADR 的候选事项

本文不直接建立正式规则，但以下事项值得后续进入正式规范或 ADR 讨论：

| 候选事项 | 建议落点 | 原因 |
|---|---|---|
| 任务生命周期行动模型 | `specs/40-69` | 约束 AI 如何从意图进入执行、验证和回写 |
| Task 对象依赖与验证字段 | `specs/10-39` | 让任务成为可执行、可检查、可追溯对象 |
| 研究模式行动模型 | `specs/40-69` 或 evals 模板 | 把外部调研转化为可复用工程流程 |
| Web Tools 事实源边界 | `specs/05` 或其子文档 | 防止 Web 状态替代 Git 文件事实源 |
| MCP 工具接入 ADR | `ldvh-base/adrs/` | 判断 LDVH 是否采用 MCP Server 作为工具入口 |
| Human Gate 与自动任务分解关系 | `specs/40-69` | 防止自动分解扩大执行范围或绕过确认 |

## 八、最终判断

MCP Shrimp Task Manager 对 LDVH 的最大价值，是提供了一个“面向 AI Agent 的任务治理工具”样板。它证明任务管理不必只服务人类看板，也可以直接服务 AI 的规划、执行、验证和记忆过程。

LDVH 应吸收这种 AI 优先的工具设计思想，但要保持自己的核心边界：

1. LDVH 不是单一任务工具，而是工程化驾驭框架；
2. LDVH 的最终事实源必须是 Git 可追踪文件；
3. Harness 生产对象承载稳定工程事实；
4. Harness 行动模型约束 AI 如何行动；
5. Harness 工具只辅助读取、校验、聚合、展示和受控写入；
6. Human Gate 不能被自动规划、自动分解或自动验证绕过。

因此，Shrimp Task Manager 应作为 LDVH 工具化和任务行动模型设计的重要参考，而不是作为 LDVH 规范体系的替代品。最合理的借鉴路径，是将其任务规划、分解、依赖、验证、研究、记忆和可视化能力拆解为 LDVH 内部的对象规范、行动模型和工具能力，并始终回到 Git 文件事实源和 Human Gate 的治理边界内。
