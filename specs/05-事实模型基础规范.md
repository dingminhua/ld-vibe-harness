## 1. 价值判断

本文的价值，是在具体事实类型形成前先确定共同准入、公共字段和消费边界，使 AI 能区分“需要长期保留的稳定事实”与“确实需要事实模型管理的结构化事实”，并通过一套统一的对象身份、类型、标题、时间、来源、证据和关系入口可靠地定位、关联、更新和处置事实对象，而不让各具体类型、Code 或 Web 分别创造同义字段。

本文主要服务：

1. V1 快速定位：让 AI 能从具体事实类型的定义来源定位允许的对象、位置和当前权威实例；
2. V2 充分理解：把事实对象、来源回指、证据、状态和关系放回同一类型语义中理解；
3. V3 边界识别：区分稳定事实、事实模型管理对象、具体类型规则和实现派生结构；
4. V5 据实判断：使状态、结论和更新声明不超出来源与证据实际支持的范围；
5. V6 工作接续：使需要结构化管理的事实可以跨行动、会话、执行者和阶段恢复与继续更新；
6. V8 持续积累：只把具有持续净价值的事实类型纳入模型，并在类型停止使用或对象被关闭、归档、合并、替代或删除时保留仍适用的事实。

独立建立本文，是因为事实类型是否准入、准入后共同遵守什么，以及具体事实类型的定义来源和消费实现分别负责什么，具有独立于任何单一事实类型的规则对象和失败边界。没有这层共同规则时，各类型容易重复或冲突地定义事实身份、权威位置、状态与更新边界；把这些规则交给某一具体类型、Code 或 Web，又会使局部实现反向定义整个事实模型。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：定义事实模型作为三类语义构成要素之一，在事实源边界内组织需要对象化、状态化或证据化管理的事实，并要求具体实践按照实际服务对象接受 V1-V8、HV1-HV5 或两组分别成立的价值判断；
2. `work-object-governance-scope`：定义事实所属管辖项目、工作对象和管辖范围的判断边界；
3. `source-of-truth-traceability`：定义稳定事实、来源回指、事实源写入与更新、当前 Working Tree 读取和 Git 溯源边界。

本文不得重新定义上述规范的事实源、管辖范围、稳定事实、来源回指或 Git 语义。本文作为普通规范，仍按 `specification-model-foundation` 的普遍结构和治理规则形成；该普遍约束不是本文的事实模型语义依据，因此不写入 `basis`。

历史规范、附件、实例、Code、tests 和 Web 只可作为问题与设计输入。历史名称、字段、状态、目录与对象实例不因曾经存在，就取得当前事实类型身份或规则效力。

## 3. 职责边界

本文负责定义：

1. 稳定事实进入事实模型管理的共同准入条件，以及不应对象化时的分流边界；
2. 管辖项目拥有自身 `ldvh-base/` 的唯一事实载体拓扑，以及具体事实类型及其事实对象共同遵守的身份、权威位置、来源、证据、状态、关系、发现、召回、消费、变更与处置边界；
3. 全部事实对象字段的统一登记、字段新增准入、唯一身份和适用范围，以及跨类型字段与类型专属字段的定义、引用、提升和组合规则；
4. 具体事实类型的唯一定义来源必须承担的规则范围；
5. 事实模型领域的 Helper 公开操作及其领域 `arguments`、`result`、机械校验边界和部分失败语义；
6. 规范正文、授权附件、Helper、Code、tests 和 Web 在事实模型中的权威边界；
7. 事实类型和事实对象在不成立、冲突、停止使用、关闭、归档、合并、替代或删除时的验证、Human Gate 与 Stop Conditions。

本文不负责定义：

1. 任何具体事实类型是否成立，或具体类型的目的、对象范围、增量字段、合法初态、状态值、阶段、转换边、关系类型、Schema 和文件格式；本文定义的 `ldvh-base/` 共同拓扑不构成类型准入或类型语义；
2. 某项证据是否足以证明具体领域结论、完成、通过、关闭或验收；
3. 04 统一定义的 Helper 共同请求与响应字段、Code 模块与算法、诊断码、缓存、测试文件或 Web DTO、路由和页面交互；本文只可在自身领域责任内定义事实服务公开操作的 `arguments` 与 `result`；
4. 事实源之外的信息分类、Working Tree 与 Git history 的一般边界；
5. 创建、修改、删除、提交、push 或其它外部行动的通用授权；
6. 可复用行动步骤、环境接入或项目特定强制规则。

具体事实类型的定义来源负责类型语义；相应领域来源负责成立条件与证据充分性；03 负责事实源与信息溯源；04 负责 Helper 共同请求与响应语义，本文负责事实模型领域操作语义；Code 和 tests 负责实现与确定性验证；Web 负责读取、呈现和受控交互。任何消费方都不得因实现方便而取得事实类型定义权。本文后续定义的 Helper 操作只能规定跨类型调用协议、作用范围、原子性和结果语义；当操作需要检查合法初态、状态、阶段、转换、关系或字段条件时，必须读取或忠实派生相应具体类型来源，不得在本文再建立一份类型规则枚举。

## 4. 适用范围

本文适用于管辖项目中以下场景：

1. 判断一类稳定事实是否需要由事实模型对象化、状态化或证据化管理；
2. 新建或实质修改具体事实类型的定义来源；
3. 创建、读取、关联、更新、更正、推进、关闭、归档、移动或删除事实对象；
4. Helper、Code、tests 或 Web 发现、召回、读取、解析、校验、索引、聚合、展示、消费或请求受控修改事实对象；
5. 具体事实类型准备停止新增、合并、替代或取消当前使用；
6. 当前事实对象、具体事实类型的定义来源、Schema 或派生结果之间出现冲突。

本文不要求所有稳定事实都成为事实对象。普通 Markdown 或其它符合来源规则、位于管辖项目实际 Git Working Tree 的当前文件已经能自然、清楚地保存和消费内容，且不需要对象化、状态化或证据化管理时，该内容继续按 03 作为稳定事实处理，不因缺少具体事实类型而失效。

## 5. 草案概念边界

本节定义三个双语术语；其名称和登记必须符合 `specification-model-foundation` 和当前双语术语表。

### 5.1 事实类型（Fact Type）

事实类型是对一类准备在项目中稳定保留、具有相同事实语义和实例边界，并需要按共同规则接受对象化、状态化或证据化管理的事实内容所作的语义分类。每个事实类型由当前有效的唯一定义来源定义；类型本身不是承担规范责任的文件或实现模块。类型及其定义来源成立前，候选内容是否已经是稳定事实仍按 03 判断；仅凭候选类型名称不得取得事实对象身份或类型规则效力。

事实类型不是文件扩展名、目录名、Schema 名称、前端筛选项或 Code 类名。两个对象使用相似字段不证明它们属于同一事实类型；一个既有名称或现存目录也不证明该类型已经获当前准入。

`事实对象类型` 与本概念指向同一语义，只作为术语表登记的中文别名；当前规则源使用首选名称“事实类型”，不得让两个名称看似承担不同概念。

### 5.2 事实对象（Fact Object）

事实对象是在已准入事实类型之下，由该类型的定义来源赋予稳定身份和当前权威位置、用于独立定位、验证、关联和更新事实内容的单位。对象身份可以在当前内容无效时继续用于定位冲突和修复目标；不满足定义来源或事实源条件的当前内容不得作为有效稳定事实消费。

事实对象必须位于 00 和 03 定义的事实源边界内。文件、YAML 映射、Markdown 区块或其它结构只有在具体事实类型的定义来源允许并满足共同规则时，才可能承载事实对象；结构化文件、对象 ID、Code 输出或 Web 记录本身不自动成为事实对象。

“事实类型”约束一类对象的共同语义，“事实对象”是该类型下的具体稳定事实单位，“稳定事实”则还包括不需要事实模型管理的内容。三者不得互相替代。

“工作对象”绑定当前事项，范围包括文件、目录、仓库、Git ref 和其它被当前行动指向的资源；“事实对象”是已经准入事实类型下可以跨行动和会话稳定定位的事实单位。当前事项指向某个事实对象时，同一资源可以同时作为工作对象和事实对象，但两种身份的成立条件与作用不同。

`事实实例 / Fact Instance` 与本概念指向同一语义，只作为术语表登记的中英文别名；当前规则源使用首选名称“事实对象 / Fact Object”。

### 5.3 事实类型标识（Fact Type Identifier）

事实类型标识是具体事实类型的唯一定义来源赋予、用于跨规范、Helper、Code、tests 和 Web 稳定引用同一事实类型的机器可读标识，机器字段为 `fact_type_key`。它只识别事实类型，不识别承担定义责任的规范、具体事实对象、目录、Schema 或实现模块，也不证明该类型已经实现或某个事实对象有效。

`fact_type_key` 使用小写 ASCII kebab-case，必须匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`。它在全部当前事实类型中唯一；类型名称、标题、路径或承载规范发生不改变类型语义的调整时保持不变，类型取消后的 key 不得改派给其它事实类型。

事实类型标识不是所有事实内容共用的全局对象 ID。每个事实对象必须按本文授权的统一字段登记保存 `fact_type_key`，其值必须与对象所属具体事实类型的当前声明完全一致；具体类型不得改用 `type`、文件目录、Schema 名称或 Code 类名表达同一公共语义。跨类型或跨消费方形成稳定引用时同样必须保留该标识。

## 6. 事实类型准入与承载位置

### 6.1 准入条件

一项候选事实类型只有同时满足以下条件，才可以完成准入。起草中的候选定义来源可以声明“拟准入”，但该声明没有当前规则效力；只有全部准入条件和独立复核通过，并且唯一定义来源进入当前规则源时，类型准入与其类型规则才同时生效：

1. 候选内容准备在管辖项目中跨行动、会话、执行者或阶段继续保留，而不是只服务当次推理、展示、缓存或执行过程；候选内容是否已经是稳定事实按 03 判断，仅凭拟准入声明不得取得事实对象身份或类型规则效力；
2. 该类内容确实需要对象化、状态化或证据化管理中的至少一种，并能说明缺少相应管理会造成的定位、理解、判断、接续或积累失败；
3. 该类内容具有可重复使用的稳定语义和对象边界；即使只有一个高价值对象，也必须存在独立身份、关系、更新或生命周期需要，而不能只因内容重要就建立类型；
4. 由普通 Markdown 或其它符合来源规则的文件承载的稳定内容、现有事实类型或其它正确承载位置不能在不混淆责任的情况下自然承担；
5. 在准入生效时具有唯一且当前有效的定义来源，能够完整定义 §10 要求的类型责任；起草阶段的候选来源只用于证明这一条件可以成立；
6. 纳入后能够为其实际服务对象带来对应净价值：服务 AI 时按 V1-V8 判断，服务 Human 时按 HV1-HV5 判断，同时服务两者时分别判断；新增类型发现、跨来源读取、Schema 维护、迁移和实现成本不得抵消该价值；
7. 类型名称、跨规范术语和机器表示在需要时满足 01 的术语与规范责任治理要求。

文件已经结构化、历史中存在同名规范或实例、Web 已有页面、Code 已有解析器或可能实现自动化，均不能单独证明类型应当准入。

### 6.2 唯一定义来源与结构承载

具体事实类型的核心语义必须由符合 01 的当前规则源正文作为唯一定义来源承担。已有规范能够在自身责任内自然定义该类型时，可以在该规范正文中承担；确有独立规范责任时，才按 01 §13 建立新的普通规范。

授权附件只可承载父规范正文已经定义并授权的字段表、枚举或关系矩阵，不能独自定义类型目的、准入、对象边界、状态含义、证据要求、Human Gate 或 Stop Conditions。Schema、Code 常量、tests、Helper 响应和 Web DTO 必须从唯一定义来源推导，不能成为第二定义来源。

定义一个或多个具体事实类型的当前来源，必须在正文中使用唯一一个标题文本完全为 `事实类型声明` 的 H3，并使用以下真实表头逐行声明：

| fact_type_key | summary | definition_ref |
|---|---|---|

三个字段分别表示：`fact_type_key` 是符合 §5.3 的稳定事实类型标识；`summary` 是不替代正式定义的一句话类型摘要；`definition_ref` 使用 `<spec_key>::<exact-heading-text>` 指向同一当前来源正文中承担该类型完整语义的唯一 H2。类型定义统一使用 H2，使其内部可以按统一字段登记设置“准入审计引用”“类型字段使用绑定”和“类型专属字段定义”等 H3，不允许用 H3 定义类型后再制造同级伪嵌套。

Code 按以下闭集规则解析声明：

1. 每份当前规则源至多出现一个标题文本为 `事实类型声明` 的 H3；该 H3 所属章节除空白行外必须直接以声明表开始，并在下一个 H2 或 H3 前只包含这一张表；
2. 声明表必须恰有 `fact_type_key`、`summary`、`definition_ref` 三列，顺序与上述真实表头一致，不接受附加列、缺列、重复列或替代表头；
3. 每个数据行必须按 GFM 表格规则解析为恰好三个非空单元格；表格至少包含一个数据行，同一来源内不得重复 `fact_type_key`；
4. `definition_ref` 在第一个 `::` 处分为两段；前段必须与声明所在规范的 `spec_key` 完全相同，后段必须非空且不得再包含 `::`；
5. 后段按去除 Markdown 标题标记和首尾空白后的完整标题文本，在声明所在规范全文中唯一匹配一个 H2；不得指向 H3 或 `事实类型声明` 自身；
6. 被引用定义章节的范围从匹配 H2 开始，到下一个 H2 前结束。

声明表只是各类型唯一定义来源中的机器读取入口，不是平行登记表。只有声明所在规范进入当前规则源、`definition_ref` 目标存在且 §6.1 全部准入条件成立时，相应事实类型才进入当前事实类型集合。草案中的声明没有规则效力。声明 H3 后缺表、重复声明 H3、多表、空表、表头或数据行畸形时，该来源中的全部声明都不得进入派生视图；某一行的 key 格式错误、`definition_ref` 格式错误、越源、目标缺失、目标歧义或指向声明表自身时，只暂停该行对应类型；当前来源之间或同一来源内出现重复 `fact_type_key` 时，所有重复项都暂停发现和消费。Code 可以扫描全部当前规则源中的声明表形成派生视图，但不得让实现注册表、缓存或生成文件反向成为类型来源。

本文通过 `fact-object-field-registry` 附件建立全部正式事实对象字段的统一登记表。登记表是结构与字段稳定身份、当前定义位置和适用类型范围的唯一索引权威，不复制类型归口字段的完整语义；定义归口为 `foundation` 的字段由附件唯一定义，定义归口为 `type` 的字段仍由相应具体类型的唯一定义来源承担，并由登记表中的 `definition_ref` 精确回指。`fact-object-mechanical-validation-catalog` 则逐项登记当前来源明确交给 Code 的机械规则族、适用类型、来源定位、唯一 owner、必须覆盖的事实入口、未完成检查的结果边界与范围测试要求；它不复制字段或类型语义，也不由实现反向更新。Code 可以从登记表和各定义来源派生 Schema、适用矩阵和检索视图，但派生结果不得成为第二字段权威。本文不建立中央事实类型清单；04 的 `capabilities` 也只发现已有当前来源的 Helper 公开操作。除非未来当前来源另行定义事实类型或字段发现操作及其契约，事实类型声明和字段登记不得被冒充为已经可通过 Helper 调用的能力。

## 7. 事实对象共同边界

### 7.1 统一字段登记与类型字段组合

本文授权 `specs/attachments/05.Att.01-事实对象统一字段登记.md` 承载结构与字段统一登记表、`foundation` 字段、来源与证据引用、关系目标、类型字段引用表和类型归口字段定义表的结构化契约。附件只展开本节已经定义的以下边界，不取得具体事实类型定义权：

1. 每个正式字段必须先取得全局唯一且不得改派的 `field_key`，并在附件统一字段登记表中登记所属结构、canonical `field_path`、JSON 类型、字段角色、值结构、定义归口、适用事实类型、唯一定义来源和状态；未登记字段不得进入类型定义、Schema、对象、Code、tests 或 Web DTO；
2. `object_id`、`fact_type_key`、`title`、`created_at` 和 `updated_at` 是所有事实对象必需的公共字段；`status`、`urls` 和 `relations` 按附件及具体类型规则条件出现；
3. 字段的定义归口与适用类型是两个独立维度。`foundation` 表示字段由附件唯一定义，可以通过 `applies_to` 对全部类型保留或只供多个明确类型复用；`type` 表示字段只由一个具体类型来源唯一定义，并且 `applies_to` 恰为该类型。字段不会因为当前已完成类型数量变化而自动改变定义归口；
4. `foundation` 字段的路径、共同语义、JSON 类型和基础约束只由附件定义；具体类型只通过“类型字段使用绑定表”声明适用于本类型的 `field_key` 与 `presence`，没有差异时直接继承，确有单调收紧时用 `constraint_ref` 回指本类型唯一正文归口；绑定表不得复制路径或自然语言规则，也不得改名、放宽或改变共同语义；
5. `type` 字段的完整语义只在相应具体类型的“类型专属字段定义表”中定义，同时必须在统一登记表中保留相同 `field_key`、所属结构、字段路径、JSON 类型、唯一 `definition_ref` 和唯一适用类型。类型来源不得定义未完成统一登记的字段；
6. 类型来源可以收紧 `object_id` 格式，定义 `status` 的值与状态机，规定自然语言验证说明和 `urls` 的使用条件，定义 `relations[].relation_key` 的语义、目标类型、基数和完整性，但不得改变公共入口的名称、JSON 类型或共同边界；“收紧”只允许增加本类型成立条件，不得否定共同语义或使同一字段在不同类型回答不同问题；
7. 派生 Schema 必须从附件登记的结构身份开始，由结构成员、适用于该类型的事实对象直接字段、每个字段的唯一语义定义和类型使用绑定单向组合；结构成员随容器引用继承，不得在各类型重复绑定；不得把各类型复制后的完整 Schema 当作互相独立的字段权威；
8. 修改 `applies_to: *` 的基础字段必须评估全部当前事实类型；修改只供部分类型复用的 `foundation` 字段必须评估全部适用类型；修改 `type` 字段必须评估其唯一类型及消费者。任何变更都必须先更新统一登记及唯一来源，再评估对象、Helper、Code、tests 和 Web 的同步或迁移范围，不得用局部兼容字段规避共同变更；

### 7.2 字段新增准入与提升

任何具体类型提出正式字段或 JSON object 结构前，必须检索附件登记的全部 `current` 与 `retired` 字段和结构，并比较字段或结构回答的问题、不承载的语义、JSON 值形态、成员闭集、生命周期、来源与证据、出现条件、未知值和更新规则；只比较名称、路径或实现 shape 不成立。聊天、记忆或尚未回写的 agent 输出不能作为查重全集。

字段提案只能得到以下四种结论之一：

1. 现有字段能够无损承接时，复用现有 `field_key`；不得因命名偏好、类型归属或实现方便创建别名；
2. 现有 `definition_scope: type` 字段被第二个类型需要时，先在同一变更中将其定义归口提升为 `foundation`、把唯一共同定义迁入附件并更新 `applies_to` 与全部使用绑定，再由新类型引用；不得先复制后整理；
3. 相似字段实际语义不同且不能形成共同基线时，保留或建立不同字段，但必须记录差异边界，避免同名异义；
4. 全部现有字段都不能无损承接时，才可以创建新的类型归口字段，并在同一变更中完成唯一 `field_key`、类型来源定义、统一登记和使用绑定。

字段提升到 `foundation` 后不得因为后续新增类型不使用而降回类型来源；`applies_to` 只按实际复用范围扩展或经显式退出决定收缩。字段从适用范围退出、拆分、合并、改名或改变身份语义时，必须显式处理已有对象和引用。`retired` 登记行用于仍须承接既有对象或当前消费者的历史字段；确认没有实际对象、消费者或迁移需要时，应连同其结构、定义和实现依赖一并删除，而不是保留无消费价值的 tombstone。仍保留的 `retired` 行不得被改派；重新需要其语义时必须形成显式恢复或替代决定。异名同义字段不得并存；同名异义字段不得在同一所属结构中共用 canonical 路径。

结构使用同一四结论准入和提升规则：首次只服务一个类型时由该类型唯一定义；第二个类型需要复用时先提升到附件 `foundation` 定义，再更新适用范围和全部成员字段。结构只表示 JSON object 成员闭集，array 字段通过 `value_structure` 引用 item object 结构。结构提升、拆分、合并、改名、retired 保留或在确认无实际对象、消费者和迁移需要时完整删除，均适用与字段相同的身份、查重和依赖清理要求；不得创建同义 `structure_key` 绕过字段查重。

Code 负责枚举完整登记、检查 `field_key`、`structure_key` 和定义唯一性、精确名称或路径冲突、引用、类型、适用范围、成员出现规则与 Schema 组合；AI 负责比较字段与结构的自然语言语义，并形成复用、提升、区分或新增判断。Code 不得根据关键词、相似度、embedding 或其它启发式自动裁决语义等价。语义仍有歧义、涉及破坏性迁移或改变全部类型共同边界时进入 Human Gate。

具体类型的当前推进顺序属于架构推进计划，不属于本文的长期事实模型语义。无论采用何种推进顺序，一个类型只有在自身语义、对象边界、全部字段与结构准入、状态、来源、证据、关系、验证和独立复核完整形成后，才能作为后续类型查重的已完成输入。

### 7.2.1 对象记录价值、消费与最小充分性

字段或结构已经登记、并被某类型绑定，只说明它可以在该类型中承担已经定义的语义；不表示每个对象、每次更新或每一条引用都应写入该位置。每个实际记录的直接字段、结构成员和引用条目都必须在当前对象中具有独立、持续的消费价值：它必须回答后续 Human 或 AI 在理解、召回、核对、更新、状态判断、关系导航或来源复核时确实需要的一个问题，并且该问题不能由同一对象中已经保留的其它内容无损回答。

这里的“消费价值”不要求每个字段在每个页面拥有独立视觉区块，也不要求所有消费者在同一时刻读取全部字段，更不以篇幅短小、实现细节少或未形成最终方案作为条件。一个正文、摘要或演变条目可以完整保留相互依赖的当前问题、已观察事实、设计约束、可选方向、待决事项和验收边界；只要后续 Human 或 AI 需要依此继续判断、实施、复核或交还，它们就是同一对象不可替代的消费内容，不能因其中包含详细方案或过程背景而删除。具体类型可以规定正文、概览、召回卡、关系、来源核对或历史追溯中的不同阅读顺序；但已记录内容必须能够在相应消费场景中按其原有字段身份被定位和使用。仅为展示方便、满足模板、猜测未来可能有用、无损重复其它字段、复制目标对象内容，或只逐次罗列工具调用、文件改写、迁移动作而没有保留任何独立的观察、判断变化、约束、影响、证据范围或验收边界的流水，才不具有记录价值，不得写入事实对象。

事实对象不是用来证明自身“正确”的材料包。对执行、观察、判断、验证和未知范围的据实说明，是为了让后续消费者理解记录的实际边界并在该边界内继续行动，不要求对每个自然语言字段建立证明链、复现实验、审核流水或可展开证据包。某项审核、测试、Human 决定或工具动作已经发生，只有在其当前结果仍直接约束对象的授权、状态、接续或终态判断时才具有记录价值；过程曾经发生本身不是长期保留理由。

`urls` 与 `relations` 适用同一记录价值原则，但职责不同：

1. `urls` 只保留外部、可长期复核且确有当前消费价值的 HTTP(S) 资料；每项以标题和摘要说明支持范围或限制，不能用本机路径、代码、日志、会话或 Git revision 代替；
3. `relations` 只保留当前对象与目标对象之间已由来源类型定义的业务语义；它只包含 `relation_key` 与稳定 `target`，不得承载来源、证据、治理资料、责任 ID、反向导航或目标标题；
4. 外部资料重复时按 URL 去重；同一资料只在确有不同且被摘要明确说明的支持范围或限制时才分别保留。

对象创建、实质更新、更正、替代、退出或迁移前，AI 必须逐项复核目标快照中的记录价值：保留仍承担当前问题的内容，合并无损重复，删除已经不再承担任何当前消费的字段值或引用条目；但不得以清理为由删除仍用于理解终态、替代链、来源边界、证据范围或类型来源明确要求保留的历史事实。条件字段在该对象中不适用时必须省略，不能用空值、空列表、占位时间或泛化说明维持位置。

记录价值、是否无损重复、当前理解是否仍需要某项来源以及证据是否足够，属于 AI/Human 的语义判断。Code 只可执行当前来源已经明确为机械规则的字段闭集、出现条件、载体定位、重复身份、关系 key、目标和状态边界；它不得以字数、关键词、kind 白名单、页面样式或启发式相关性自行裁决一条记录是否有价值。

### 7.3 对象成立与稳定引用

每个事实对象必须同时满足：

1. 所属具体事实类型已经准入，能够通过 `fact_type_key` 唯一回到其当前有效的定义来源；
2. 对象位于对应管辖项目的 Git worktree 和该类型允许的事实源位置；
3. 对象通过公共字段 `object_id` 具有在同一管辖项目和同一事实类型范围内唯一且稳定的身份；具体类型可以收紧格式，但不得改用标题、路径、`fact_type_key` 或其它字段替代对象身份；
4. 对象的当前权威位置唯一；副本、索引、缓存、摘要、聚合和 Web 视图不得与当前对象形成并行权威；
5. 当前 Working Tree 内容可以按该类型的定义来源解析，并满足适用字段、状态、关系和验证要求；
6. 对象能够按具体类型的要求回指理解其当前内容所需的来源和形成依据；未定义外部资料或结构化来源成员的类型，可以由对象自有语义字段据实说明形成范围、实际观察、已采取处理、验证覆盖和未知范围满足这一要求。发生更新后必须回读实际 Working Tree 内容，是否长期保存更新历史由该类型的定义来源决定；
7. 对象的结论、状态与声明没有超出当前来源和证据实际支持的范围。
8. 对象中实际出现的字段值、结构成员和引用条目符合 §7.2.1 的记录价值与最小充分性要求；没有为页面、模板、无独立作用的过程流水或未来猜测保留无当前消费者的内容。

### 7.4 管辖项目的 canonical 事实载体拓扑



此共同拓扑只规定存储归属和路径根，不额外定义字段、状态、文件命名、目录附加层级或实现。具体类型仍由其唯一定义来源决定对象语义、字段、状态、文件后缀及其目录中的合法对象。仓库根级 `facts/` 不是当前事实对象的 canonical 路径，不得被读取器、写入器、校验器、Web、测试或迁移兼容逻辑作为第二来源。

具体事实类型的定义来源必须确定对象粒度、身份稳定边界、允许位置以及一文件一对象、多对象同文件或其它承载方式。本文不预设文件与对象的数量关系，也不规定 YAML、Markdown 或其它格式。

事实对象的稳定引用至少必须能还原为“当前选定管辖项目配置中的项目 `id` + `fact_type_key` + `object_id`”。项目 `id` 只在其所属配置内唯一；引用需要跨工作区配置解释时，还必须按附件保留配置来源以及 02 要求的项目身份依据，不能假定不同配置中的同名项目 `id` 指向同一项目。该引用规则用于消除跨项目和跨类型歧义，不要求把三部分写进同一个字符串。

重命名、移动或结构迁移不得无意改变对象身份。多个当前位置声称承载同一对象、多个对象重复使用同一身份，或者对象身份只能靠标题、路径相似与 Code 猜测时，不能选择较新、较近或较方便的一份静默继续。

## 8. 来源、证据与关系

1. 事实对象必须遵守 03 的来源回指和信息溯源规则；具体事实类型的定义来源负责定义对象需要保留哪些来源、在什么条件下必须包含版本、观察时间、输入范围或其它上下文；
2. 来源回指只证明能够回到形成依据，不单独证明内容正确或证据充分；具体领域成立条件和该类型的定义来源共同决定可接受依据与可证明范围；
3. 当次观察、Human 指令、聊天、AI 推理、命令或测试输出可以成为事实对象写入或更新的输入，但必须按 03 和具体事实类型的定义来源完成写入、校验与回读后，才能在实际成立范围内作为稳定事实消费；
4. 对象形成原因由各类型的自有语义字段表达；结论、验证、状态与处置的事实依据由相应自然语言字段表达。只有外部、可长期复核资料通过 `urls` 记录，其成员不得伪装成本机或会话定位；
5. 事实对象之间的关系统一通过公共字段 `relations` 表达，每项保留关系方向、类型和可稳定定位的目标；关系类型、基数、跨项目边界、目标缺失与循环是否合法，由定义该关系语义的具体事实类型定义来源负责，并且不得与目标类型的定义来源冲突；面向 Human 呈现关系目标时，目标名称只能由该稳定目标当前对象的 `title` 派生读取，不得复制、人工维护或把名称写入关系；具体类型可以进一步规定何时必须机械确认该标题可读。不得重新建立 `related_sparks`、`related_workcases` 或其它按目标类型分裂的同义公共字段；
6. 索引、反向关系和聚合可以由 Code 派生，但必须回指当前对象和来源规则，不得反向增加事实关系或改变事实语义。

上述自然语言说明不当然要求 `source_ref`、`evidence_ref`、关系边、URL 或可展开资料包；只有具体类型明确要求外部资料、版本、观察时点或结构化来源成员时，才按该类型定义保留并展开。缺少某类未被该类型定义的引用，不得单独推定对象无效、证据不足或不可消费。

来源存在、证据数量、Human 验收、测试通过或 Git commit 均不能脱离具体成立条件单独证明对象结论或状态成立。

### 8.1 事实对象发现、召回、展开与语义消费

事实对象被创建后，只有在后续行动中能够于正确时机被重新发现、读取和语义消费，才实际形成跨行动价值。该链路必须区分四个不可互相替代的结论：

1. **发现**：在已确定的管辖项目和实际 Working Tree 中，枚举符合当次结构化条件的对象引用和最小候选信息；
2. **召回**：在当前行动、对象、主题或 lifecycle 时机下，把少量可能相关的候选提供给 AI，并保留候选命中依据与未检查范围；
3. **展开**：对 AI 选中或当前输入精确引用的对象，从唯一当前权威位置读取完整内容并完成已实现的机械检查；
4. **语义消费**：AI 依据具体类型来源、当前目标、对象内容、状态、来源、证据、适用边界和现时环境，判断该事实能否以多大范围影响当前行动。

精确事实引用、当前工作对象、来源 locator、对象关系、类型、状态、标题与当前来源已明确交给 Code 的可检索文本，可以作为确定性发现或候选缩小依据。Code 必须返回实际命中依据，不得根据关键词权重、相似度、embedding、LLM 输出或其它启发式自动裁决两段自然语言是否语义相关、对象是否适用或结论是否仍当前。AI 也不得因为候选被返回、文件机械有效、文本相似或对象状态非终态，就把它宣称为当次适用事实。

事实信息的渐进式披露使用以下五层。层级只表示 AI 当次获得的信息深度，不新增事实对象字段，也不预先定义 Helper API：

| 层级 | 内容 | 直接用途 | 不能单独证明 |
|---|---|---|---|
| F0 恢复清单 | 当次管辖项目、实际 worktree/common-dir、各类型/状态数量、Schema 与对象集指纹、当前工作对象引用、已选对象、coverage 和未完成 cursor | 确认恢复边界、过期与未检查范围 | 任何具体对象相关、适用或内容未变 |
| F1 基础卡片 | 具体类型来源要求在会话建立或恢复时完整审阅的全部最小权威字段投影 | 建立当前决策约束和未关闭责任全貌 | 对象全文已读、已适用或已授权行动 |
| F2 候选卡片 | 按类型、状态、引用、关系、locator 或允许字段精确文本命中的少量对象、最小权威字段、命中依据，以及具体类型确有需要时从完整文本形成的有界确定性摘录 | 让 AI 在不读取全部正文时筛选可能相关对象并决定是否进入 F3 | 语义相关、现时适用、结论当前、被摘录字段已经完整读取或事实源内容应保持短小 |
| F3 完整对象 | 对象当前权威文件的全部内容与已实现机械检查 | 完成对象语义、状态、适用与限制判断 | 来源真实、证据充分、外部事实当前或行动获授权 |
| F4 来源证据 | 只对影响当次适用、决定、验证或当前性的必要、且由该类型实际保留的 source/evidence locator 进行展开 | 核对具体声明及其来源、版本、观察时点和范围 | 未展开引用也已核对，或对象全部声明都当前；未定义此类 locator 的类型不因此缺证 |

召回是候选与基础上下文的提供机会，不是把当前项目全部事实对象正文永久注入 AI 上下文。进入事实消费分支的消费方应先取得 F0，再按类型来源完成当次必需的 F1，其它对象先进入 F2，只对 AI 选中对象按需展开 F3 和 F4。F1 可以要求“全部对象的最小卡片”，与不全量注入正文不冲突。任何分层结果的数量、排序、分页、截断、指纹、无效/不可读对象和未检查范围都必须可观察；超过资源或上下文边界时应分页、继续缩小或报告 partial，不得静默截断后声称已全量召回。F2 的确定性摘录只属于 Helper 派生输出，必须保留原字段路径、固定预算、是否完整和 F3 稳定引用；它不得写回事实对象、由 AI 重写、替代 F3，或反向要求事实源把完整内容压缩到卡片预算内。

00 §8.1 所述规则引导先于本节的事实恢复。AI 在已经理解 Human 当前目标后，只有明确判断项目事实为完成当次理解、判断或行动所必需，或者需要复核当前输入、父上下文或来源所给出的精确稳定事实引用时，才进入事实消费分支。新会话开始、会话恢复、上下文压缩后继续、任务委派或环境生命周期事件本身，都不自动构成进入该分支的理由；尚未进入时，事实恢复状态为 `not_requested`，不表示事实不存在、无效、完整或与任务无关。

进入事实消费分支后，AI 必须先按 02 确定管辖项目和实际 Working Tree，再重建 F0，并按具体类型来源完成当次必需的 F1。21 §9.1 与 22 §7 当前分别要求的 WorkCase / ADR F1 对象集必须沿 `next_cursor` 持续分页，直至读完全部页，才可声称相应 F1 完整；每页之间必须保持同一查询、Schema 指纹和对象集指纹。任一 `partial`、cursor 失效、无效或不可读对象、资源/时间预算中断都使相应 coverage 保持未完成。若当前工作对象已由独立依据精确绑定一个 WorkCase，AI 按 21 §9.1 的语义情形决定该对象及其直接 `open`/`blocked` 依赖需展开到何层；精确引用只提供定向读取入口，不把项目全量恢复、事实适用、行动允许或完成判断机械化。压缩恢复中需要重新回读的已判断适用 ADR、仍影响行动的 Pitfall、已引用 Study 结论的版本/观察/限制边界、相关 `open` Spark，以及未完成分页与未检查范围，仍由 AI 依据当次目标和已知精确引用决定。旧摘要、缓存或压缩前文本只能用于恢复精确引用，不替代当前 Working Tree 回读。

完整 Helper coverage 不等于必需 F1 已全部交付给 AI。受环境上下文或交付投影预算限制时，无法容纳的必需 F1 卡片必须使 `delivery_coverage` 保持 `incomplete`，并显式返回总数、已交付数、省略数、来源和继续展开入口。不得静默截断后声称已完整审阅 F1，也不得用 byte 预算改写 Helper 实际 coverage。Helper 仍按 §11.5–11.6 接收并回显精确恢复引用；WorkCase 当前绑定、F1/F2 投影和按语义展开 F3 的唯一类型合同按 21 §9.1 解释，环境交付投影唯一按 09 §5.4 解释，Code 不成为第二份合同权威。

新的独立 AI 执行上下文先取得与职责相称的规则引导；只有存在它或其父执行者明确交付的精确引用，或者已明确的目标或继续工作确实需要当前项目事实时，才按本节进入事实消费分支。父执行者摘要、任务描述、环境继承标记或精确引用都不能单独证明 F0/F1 已完成、事实当前适用或行动获授权。

目标环境明确提供 startup、resume、compact 或等价 lifecycle 事件时，薄 Skill 默认只交付 01 §9.10 的规则引导；只有 AI 已明确进入事实消费分支时，才可调用本节的 Helper 恢复链路。环境没有相应事件时，AI 也可以在发现事实缺口并作出该判断后调用。任何一种环境的 lifecycle 事件名都不得反向定义规则引导或事实恢复语义，环境缺少 compact 事件时也不得声称已普遍自动恢复。

具体类型的唯一定义来源必须定义：哪些当前目标、语义情形、显式引用、关系或 lifecycle 时机应产生本类型的召回机会；各状态对象何时进入默认候选、仅作历史或仅在精确引用下展开；展开后必须核对哪些适用、时效、证据或安全边界。本文不建立所有类型共用的触发词、时间间隔、相关性分数、默认数量或状态排序闭集。终态对象不得一律丢弃，非终态对象也不得无差别注入；其实际作用由对象类型、状态语义、当前场景和精确来源共同决定。

被当前对象的 `relations` 精确指向的其它事实对象，无论是否终态，都进入按需引用闭包；外部 `urls` 不扩展事实对象闭包。这只使目标可按支持当次理解所需层级展开，不使终态内容恢复当前效力。`find-fact-object-candidates` 在 §11.5–§11.6 明确定义并当次可用时，可以把 AI 已知稳定事实源的一跳正向声明关系组织为 F2 目标卡片、边级来源和继续读取入口；它仍只在 AI 已明确进入本节事实消费分支后由 AI 显式请求，不因环境 lifecycle、当前工作对象、关系存在或本段语义自动触发。

反向引用同样可用同一能力提示：AI 对当前对象展开或判断适用性时，可以经 `find-fact-object-candidates` 的 `relation_targets` 反向过滤，识别 `relations[].target` 指向当前对象的其它事实对象，作为入向责任、查重或承接范围的辅助核对。该提示只告知可用能力，不构成必须步骤，也不使反向引用自动进入闭包或替代对目标对象的精确读取与适用判断。

当前 `read-fact-objects` 只对已知稳定引用执行展开和机械检查，不实现发现或召回。本节不因定义语义模型而使新的 Helper 公开操作、候选索引、环境触发或上下文注入能力自动成立；这些能力必须在后续增量中另行定义预算、请求结果契约、失败语义、实现与范围匹配测试。

## 9. 状态与事实对象变更

### 9.1 状态边界

事实类型只有在其对象确实存在需要跨行动接续、影响消费或约束更新的语义阶段时，才定义状态。并非每个事实类型都必须有状态字段或状态机。

需要状态时，具体事实类型的定义来源必须定义：

1. 状态集合及每个状态的语义；
2. 初始状态如何成立；
3. 允许和禁止的转换；
4. 每次转换所需的来源、证据、验证和必要授权；
5. 转换失败、部分写入和当前状态无法判断时的处理；
6. 终止、关闭、归档或其它处理方式是否存在及其语义。

本文不规定任何通用状态名称、机器值、顺序或终态。文件存在、Git tracked/untracked/dirty、commit 创建、命令成功、测试通过、Human 回应或 Web 展示状态，不自动等于事实对象的领域状态或状态转换。

### 9.2 更新规则

新建、修改、更正、关系变更或状态转换必须依次确认：

1. 目标事实类型已准入，唯一定义来源和对象当前权威位置明确；
2. Human 当前指令已经授权，且适用于该行动的全部来源规则许可条件已经成立；
3. 输入信息的作用、来源回指和证据范围清楚，没有把推测改写成已证实事实；
4. 更新后的身份、字段、状态和关系满足该类型的定义来源；
5. 写入使用实际可用的入口完成，没有用计划、请求或工具成功替代实际结果；
6. 写入后回读当前 Working Tree 中的目标内容，并按该类型的定义来源完成验证；
7. 失败、部分成立、未验证范围和残留风险按实际结果保留，没有扩大成功声明。

更正事实内容与推进对象状态可能具有不同成立条件；具体类型需要区分时必须分别定义，不能把任意内容修改自动解释为状态推进。本文也不因定义更新规则而授予任何消费方通用写入或删除权限。

### 9.3 关闭、归档、合并、替代与删除

具体事实类型的定义来源必须分别定义是否允许关闭、归档、合并、替代或删除，以及每种实际存在的行为如何成立、处理后是否仍可作为历史或参考信息消费、仍适用事实的承接位置和恢复边界。本文不把这些性质不同的行为合并为统一状态或统一机器动作。

关闭或归档不等于文件必须删除，也不等于其历史内容失效。删除、合并或替代不得丢失仍需接续的事实、来源、证据和关系；没有来源规则明确允许时，不得用“已完成”“已过时”或实现清理需要推定对象可以删除。

### 9.4 跨 clone 与多机合并中的事实对象身份冲突处置

本节适用于不同 clone 或不同机器各自创建或修改事实对象后，经 Git 合并或拉取汇聚到同一实际 worktree 的场景。共享同一 Git common-dir 的主 worktree 与 linked worktree 之间的并发由 §11.8 的协调根在写入时防止，不属于本节范围；跨 clone 写入时的冲突预防（如提交前远端新鲜度验证与全局身份比对）当前没有来源已声明且范围匹配的 Helper 公开操作，本节不声明跨 clone 唯一分配或前置拦截已经解决（§11.4）。跨 clone 协作的冲突预防依赖同步纪律：写入事实前同步远端、写入后尽快推送，并使长期并存的编辑分支尽量短命；该纪律不形成新的机械入口。

合并或拉取使 `ldvh-base/` 发生变化后，在对该 worktree 继续事实写入或形成提交前，必须执行 `check-fact-integrity` 全库机械检查；Git 合并冲突涉及事实载体时同样适用。该检查是合并/拉取事件触发的独立入口，不改变 03 §9.9 的提交候选校验边界。检查发现 §7.4 所述重复身份或重复承载情形时，按 §7.4 不得静默选择其中一份继续；受影响对象在处置完成前不得进入后续事实写入、提交或消费结论。

冲突分类是语义判断，由 AI 对照双方标题、目标与形成上下文提出，Human 决定方向，Code 不裁决：

1. 同一对象的分叉编辑——同一项工作在不同 clone 各自更新同一对象：走合并路径。以当前内容更完整的一方为基线，把另一方独有且仍需接续的事实、来源、证据与关系并入（§9.3），并在对象中据实记录合并来源与当次处置；按 32 §5.3 B 由 AI 对单对象变化分类（通常为 `content_update`、`fact_correction` 或 `single_object_lifecycle`），写后按同一机械边界回读；
2. 不同对象碰巧分得同一 `object_id`——各方独立创建了不同工作：走改号路径。选择迁移的一方以受控创建取得新 `object_id` 重建对象，counter 不回退、已消耗编号不复用（§11.4）；旧对象按具体类型定义来源允许的合并、替代或删除规则处置（§9.3），并据实记录改号原因与新身份；全部指向旧身份的入向引用（`relations` 中“项目 + 类型 + `object_id`”稳定三元组）必须枚举并逐个更新到新身份。写集合整体属于 32 的 `multi_object_disposition`；其中受控创建新身份、旧对象处置与入向引用更新各自独立形成完整有效对象、中间状态可保存恢复，没有来源已声明且范围匹配的多对象原子能力时按 32 的合法多步序列逐对象 CAS 执行，每个对象独立回读与审计，不用多个单对象写入拼接整体成功声明。

处置完成后，必须经 `read-fact-objects` 精确回读全部受影响对象，并以 `check-fact-integrity` 确认同一实际 worktree `result.status=complete`；任一不成立时不得提交或声明处置完成。处置的来源、分类判断与 Human 方向决定按适用来源规则保留在受影响对象或相应 WorkCase 中。

## 10. 具体事实类型的责任边界

每个具体事实类型的唯一定义来源至少必须定义：

1. 类型目的、准入理由、实际服务对象及其对应 V1-V8 或 HV1-HV5 净价值，以及与由普通文件承载的稳定内容、相邻类型的边界；同时服务 AI 与 Human 时分别判断；
2. `fact_type_key`、适用的管辖项目或工作对象范围，以及来源如何被定位；
3. 事实对象表达什么、对象粒度、稳定身份、允许位置和当前权威位置；
4. 回指本文统一字段登记，先通过准入审计记录确认每项信息需求已经全局查重，再通过类型字段使用绑定引用现有字段，并只在确实新增 `definition_scope: type` 字段时建立类型专属字段定义；必须说明未知内容处理、Schema 组合位置、生成方式和一致性验证，不得复制 `foundation` 字段定义；
5. 是否需要状态；需要时的状态集合、语义、转换、验证以及关闭或归档方式；
6. 来源回指、证据、关系、可接受依据和可证明范围；
7. 发现、召回、展开与语义消费时机，各状态的候选边界，以及创建、读取、更新、更正、关联、合并、移动、归档和删除中实际适用的行动边界；
8. 验证要求、Human Gate、Stop Conditions，以及失败和部分成立时的最小影响范围；
9. 类型停止新增、合并、替代或取消时，现有对象与仍适用事实的处置方式。

上述清单规定必须回答的语义问题。字段身份和跨类型结构只由本文及其附件统一规定；具体事实类型的定义来源只有在本类型语义确实需要、完成全局字段检索且不能复用时才建立类型专属字段、状态值、关系类型或行动边界，不得为了填满模板制造结构，也不得重新定义公共入口。

具体类型来源是其合法初态、状态与阶段闭集、转换边、转换成立条件、字段失效、关系语义和召回投影的唯一语义权威。本文、附件、行动模板、Helper、Code、tests 和 Web 可以回指、投影或机械执行这些规则，但不得复制后形成可独立修改的第二权威；跨类型 Helper 契约需要描述能力边界时，应引用对应类型章节，并只补充该操作特有的单对象、多对象、CAS、原子性、失败和结果语义。实现确需使用派生常量时，必须明确其来源归属并以范围匹配测试防止与具体类型来源漂移。

| `update-fact-object` | 对一个已精确读取的当前事实对象执行内容指纹绑定的完整目标替换、转换检查、写后回读并附加独立事实完整性审计 | `may_change_state` | `fact-model-foundation::11.7 事实对象单对象 CAS 更新输入与结果` | `fact-model-foundation::11.7 事实对象单对象 CAS 更新输入与结果` |
| `migrate-legacy-routed-spark` | 对固定 allow-list 中一条已获逐条 Human 授权的历史 routed Spark，迁移为 implemented 并移除该 Spark 自身旧 routed-to 关系；不支持批量或任意对象迁移 | `may_change_state` | `fact-model-foundation::11.7.3 历史 routed Spark 受控迁移输入与结果` | `fact-model-foundation::11.7.3 历史 routed Spark 受控迁移输入与结果` |

除非具体类型来源另行定义并实现可验证的时间尺度承接，本文、授权附件以及 20–25 中以“带时区 RFC 3339 时间”或“RFC 3339 date-time”表述的全部字段，均指当前 Code 可机械比较的严格常规形态：扩展日历日期 `YYYY-MM-DD`、大写 `T`、小时/分钟/秒、省略或以 `.` 后至少一位十进制数字表示的小数秒，以及 `Z` 或已知 `±HH:MM` UTC 偏移；秒只能为 `00`–`59`。本节的非空 `event_at`、创建时点，以及受控写操作在事实对象和相应 Working Tree observation 中生成的任何时点，也一律使用此形态。`-00:00` 表示未知本地偏移，不是已知 UTC 偏移，因而禁止；已知 UTC 只能使用 `Z` 或 `+00:00`。不接受 ISO 8601 的其它日期或 offset 写法、首尾空白或 `:60` 闰秒；后者需要来源定义的闰秒表与时间尺度，Code 不得自行推断。任意小数秒必须精确比较，末尾零表示同一时点；输入和回显不得为此规范化或改写原始 string。


`read-fact-objects` 只读取当前 Working Tree 中由 20–25 定义位置承载的现有对象，不创建、更新、修复、迁移、删除或规范化重写文件，不做模糊检索、自然语言查重、全库语义召回或跨 Working Tree 聚合。它按 §11.2 返回完整对象内容，并报告实际完成的载体、Schema、身份、引用和关系机械检查；`mechanically_valid` 不证明对象准入、来源真实性、证据充分性、自然语言结论、状态决定或关系领域语义成立。草案准备和受控创建的额外边界只由 §11.3–11.4 授予，不扩大读取操作。

`find-fact-object-candidates` 与精确读取使用同一管辖、Working Tree、当前类型来源、派生 Schema 和机械读取边界。它直接扫描当前权威对象，不建立持久索引、embedding、相关性分数、AI 摘要、标签或第二事实权威；返回候选只证明对象满足当次确定性过滤并被投影为卡片，不证明语义相关、现时适用、来源真实、证据充分或行动获授权。

### 11.0 写入责任署名三字段语义

`change_log.signature` 与 Git footer 共用同一组三字段。三者是按**可观察的承载关系**定义的不同角色，不是同一发行物的不同叫法；判定以本次实际运行的进程拓扑为准，不以品牌、厂商或模型先验为准。

- **外层产品（Outer Product，`product_name`）**：用户直接启动、并在其中发起本次会话的可分发应用。当一个 Agent 运行时被另一个应用托管、嵌入或启动时，该托管应用是外层产品。判定问题是「用户在与哪个应用的界面/入口交互以发起这次会话」。外层产品保留产品自身提供的显示名称（如 `Cindy`），不由 LDVH 改名、翻译或推断。
- **Agent 运行时（Agent Runtime，`agent_runtime_name`）**：实际承载 Agent 会话、prompt 与工具调用执行的进程或运行器。判定问题是「谁在执行本次工具调用」，如 `claude-code`、`codex-cli`。它是机器可归一的运行时标识，不是品牌或产品显示名。
- **模型（Model，`model_name`）**：本次会话可观察到的模型或配置模型名称，保留其可观察拼写（含供应商前缀，如 `chatgpt/gpt-5.6-sol`）；机械层只做去首尾空白、移除末尾方括号注记与空白归一，不剥除前缀、不改名。

三者关系与边界：

1. 当 CLI/SDK 运行时被桌面端或平台产品托管启动时，外层产品是托管产品，运行时是被托管的 runner，二者不同（如 `Cindy` + `claude-code`）。
2. 当运行时被用户**直接启动、不存在托管它的外层应用**时，没有外层产品，`product_name` 必须为 `null`，并在写入前按行动模板向 Human 披露该项缺失及原因；**不得**把运行时自身的产品名或品牌填入 `product_name`。运行时不能是它自己的「外层」产品。
3. `product_name` 与 `agent_runtime_name` 是独立的可观察字段；即使产品显示名与运行时标识归一后相同，也不能仅凭字符串相等推断发生语义混淆。外层产品是否存在、以及产品提供的显示名称，只能依据当次实际承载关系观察；不可观察时按本节披露并填 `null`，不得跨字段推导。
4. 三字段都允许 `null` 表示该项在本次环境中不可观察；`null` 是「未声明/未知」，不是「确认不存在」，也不得跨字段推导或由其它字段补造。
5. 本字段的 `product_name` 与管辖配置 `LDVH-GOVERNED-PROJECTS.yaml` 的根字段 `product_name`（LDVH 管理实例名）是两个独立字段，含义不同，不要求相等，不得互相替代。

示例（仅示意承载关系，具体显示名以当次产品实际提供为准）：

| 场景 | product_name | model_name | agent_runtime_name |
|---|---|---|---|
| 桌面端托管 Claude Code 运行时 | `Cindy` | `glm-5.2` | `claude-code` |
| 桌面端托管 Codex 运行时 | `Cindy` | `chatgpt/gpt-5.6-sol` | `codex-cli` |
| 终端直接启动运行时，无托管应用 | `null`（写前披露） | 当次可观察模型 | `claude-code` |
| 本次只能观察到模型，产品与运行时均不可得 | `null`（写前披露） | 当次可观察模型 | `null`（写前披露） |

### 11.1 事实对象读取输入字段

本操作使用 04 定义的共同请求对象，并复用 02 `resolve-governance-scope` 对 `work_object_locators`、`arguments.workspace_root`、配置、路径和 Git 身份的解释。`work_object_locators` 默认或为空时使用 Helper 进程实际 `cwd`；非空时每项必须是非空路径 string。每个定位输入都必须完成并形成 `governed` 结果，且全部结果必须属于同一 `governed_project_id` 和同一实际 `git_worktree_root`；任一定位输入未完成、不是 `governed`、形成混合或多项目范围，或者同一项目落在不同 worktree 时，都不读取任何事实文件。同一项目的不同 worktree 不得合并或由登记项目路径替代。不能形成唯一读取边界时，按 04 报告全部事实引用未完成范围和实际管辖结果。

领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全使用 02 §10.1 的配置选择语义，不表示该目录本身是事实对象位置 |
| `fact_refs` | array | 必填且 1–128 项；成员使用下表闭集 | 按稳定三元组精确选择对象；保持输入顺序，重复项不合并，不接受路径、标题、关键词或相似性回退 |

`fact_refs[]` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `governed_project_id` | string | 必填非空 | 目标在本次所选配置中的项目 `id`；必须与实际管辖解析结果核对 |
| `fact_type_key` | string | 必填；必须精确匹配当次当前来源中已准入的一类 | 决定 20–25 中的载体、目录、扩展名或目录成员、对象 ID 和机械约束，不做别名或大小写修正 |
| `object_id` | string | 必填非空 | 目标类型范围内的稳定对象身份；必须满足该类型来源定义的格式 |

每个输入成员按原始顺序取得从零开始的 `fact_ref_index`，并以该序号区分重复三元组。未知共同或领域字段、空 `fact_refs`、成员字段闭集或 JSON 类型错误、未知 `fact_type_key`、不符合相应类型格式的 `object_id`、非绝对 `workspace_root`、非空 `observed_context`、非空 `authorization_reference`，或者非 `null` 的 `requested_disclosure`，均使用 `invalid_request`；不得通过尝试路径或猜测类型修正请求。`task` 可以出现但不参与项目、Working Tree、类型或对象选择。

共同 `scope.requested`、`scope.completed` 和 `scope.not_completed` 对每个事实引用使用相同 object 成员闭集：`fact_ref_index` 为原始非负 integer 序号，`requested_ref` 为字段闭集与 `fact_refs[]` 相同的 object。每个输入成员先进入 `requested`，再按其逐项结果进入 `completed` 或 `not_completed`；不得只写 integer、合并重复引用或用路径替代原始稳定三元组。

### 11.2 事实对象读取结果字段

领域 `result` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `items` | array | 已形成唯一读取边界时必填且与 `fact_refs` 等长；按 `fact_ref_index` 排序 | 每个请求引用恰有一项；局部坏文件、缺失对象或技术未完成不得吞掉其它项 |

`items[]` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `fact_ref_index` | integer | 必填且不小于零 | 对应原始 `fact_refs[]` 序号 |
| `requested_ref` | object | 必填；字段闭集与 `fact_refs[]` 相同 | 原样回显精确三元组，不提升未知身份 |
| `canonical_path` | string 或 null | 必填；能够从当前类型与合法身份确定时为 Git 相对 POSIX 路径 | 只表示类型来源定义的唯一预期位置，不证明文件存在、可追踪或有效 |
| `check_status` | string | 必填；只允许 `mechanically_valid`、`invalid`、`not_found` 或 `unavailable` | 分别表示已通过全部当次已实现且适用的机械检查、已完成检查但对象不成立、预期位置不存在，或技术条件使检查未完成 |
| `content_fingerprint` | string 或 null | 必填；`mechanically_valid` 时为 64 位小写十六进制 string；`invalid` 时，只有载体已安全完整读取且可解析稳定 `object_id`、`fact_type_key`、`created_at`、`updated_at` 时才允许同样返回 | 对当次安全读取的完整 UTF-8 载体 bytes 计算 SHA-256；invalid 时首先只绑定当次诊断快照，只有具体类型来源明确允许 invalid 记录修复时才可作为 §11.7 的 CAS 过期检测条件。它不证明对象有效、身份语义成立、Git 版本或内容语义等价；WorkCase 不得用该指纹进入专属写操作 |
| `current_snapshot_projection` | object 或 null | 必填；仅 mechanically-valid WorkCase 且已有当次 `content_fingerprint` 时为 object，其它类型及其它读取状态为 `null` | WorkCase object 的字段闭集、成立条件、枚举与映射只由 21 §9.3 定义；Helper 原样使用本项 `content_fingerprint` 作为其中的 `source_content_fingerprint`。它是绑定刚回读快照的类型专属派生视图，不是 `fact_object` 字段、第二 Schema、校验结论、授权判断或持久事实；不能形成 resolved 投影时不得猜测 |
| `issues` | array | 必填；无问题时为空 | 成员使用下述机械问题字段；只陈述已观察的失败或未完成，不作自然语言领域裁决 |
| `source_refs` | array | 必填且至少一项；成员直接复用 04 授权附件的“来源回指字段”闭集 | 回指类型来源、实际 Working Tree 文件或支持本项结果的路径/Git 观察；不得用 `HEAD` 或其它 worktree 替代当前内容 |
| `carrier` | string | 必填；只允许 `yaml` 或 `markdown` | 决定 `fact_object` 的形状：yaml 为对象映射，markdown 为 `frontmatter` 与 `body` 的闭集；读取中按类型来源当前载体恒非空，不因读取状态为空 |
| `fact_object` | object 或 null | 必填；仅 `fields` 已安全完整解析且（`mechanically_valid` 或有当次 `content_fingerprint`）时为 object，否则 null | 当次权威文件的完整解析内容，供 §8.1 F3 语义消费；invalid 但可解析稳定身份且有修复指纹的对象同样返回，以支持 §11.7 CAS 修复快照；字段语义与 §11.4/§11.7 中同名字段一致，`current_snapshot_projection` 不是其替代 |

`fact_object` 与 `carrier` 是 read-fact-objects 按 §8.1 F3 返回当次回读完整对象内容的显式职责：调用方据此完成对象语义、状态、适用与限制判断，无需再按路径自行解析载体。两者只承载当次回读的解析结果，不构成第二 Schema、持久投影或事实权威。

对象文件必须位于目标实际 worktree 中；从 worktree 根到 canonical path 的任何现有路径组件及叶节点都不得是符号链接。单个文件的 Git 状态不决定其进入当次机械检查或成为稳定事实的资格。读取不得回退 `HEAD`、Index、登记项目路径、同仓库其它 worktree 或缓存。


`mechanically_valid` 要求：预期位置与文件身份成立，载体可解析，字段和递归结构闭集、JSON 类型、必填/禁止/非空、明确枚举、时间不等式、引用 shape 以及当前来源明确交给 Code 的类型条件全部通过；需要对象全集才能判断的目标存在、重复身份、基数和 DAG 只在实际完成对应全集检查时进入该结论。尚未实现或本次不能完成的适用机械检查必须使受影响项成为 `unavailable`，不得降级为通过。单个对象的失败不使其它已完成项失效。

读取边界未形成时 `result` 固定为 `null`，全部事实引用 scope member 进入 `not_completed`。读取边界已经形成后，`invalid` 和 `not_found` 是检查已经完成的领域结果，相应 scope member 进入共同 `scope.completed`；只要全部项均形成 `mechanically_valid`、`invalid` 或 `not_found`，外层使用 `outcome: ok`。`unavailable` 进入 `scope.not_completed`；同时存在已完成项时使用 `partial`，没有任何项完成时再按 04 区分 `unavailable` 或 `error`。共同 `scope.governance_resolution` 必须承载当次完整管辖解析结果；`changes` 固定为空。共同 `verification` 只列实际执行并有依据的机械检查，`gaps` 和 `diagnostics` 保留技术未完成与未验证范围，不得用 `outcome: ok` 或本操作结果冒充事实语义已经由 Code 确认。

### 11.3 事实对象草案准备输入与结果

`prepare-fact-object-draft` 是无事实源副作用的读取操作。它只在一个已解析的管辖项目和一个实际 Git Working Tree 中，为 AI 已经选择的事实类型返回当前派生字段契约、载体、候选身份和草案依据；不创建 canonical 文件、不预留身份、不写 counter 或其它分配持久状态、Git ref、配置、缓存。AI 仍负责依据具体类型来源判断是否值得对象化、类型是否正确、自然语言字段如何填写、来源和证据是否充分。


候选身份只表示准备时观察到的下一顺序编号，不形成预留、稳定引用或成功承诺。多个调用可以得到同一候选身份；正式创建必须重新分配并返回实际身份。草案依据必须同时绑定当次 `governed_project_id`、实际 `git_worktree_root`、`git_common_dir`、事实类型和派生 Schema；创建时任一绑定变化都必须拒绝旧草案，不得静默移植到另一 worktree 或旧 Schema。

结果中的每个 `field_contracts[]` 恰含 `field_path`、`json_type`、`presence`、`definition_ref` 与 `constraint_ref`。`definition_ref` 恒为非空的 canonical 字段定义入口，格式遵从统一字段登记的 `<responsibility-key>::<exact-H2>::<field-key>`，使调用者能够定位字段的唯一权威定义；它不携带该定义的正文。`constraint_ref` 只表示当前类型对该字段施加的收紧位置，或以 `inherit` 表示没有额外类型收紧，不能替代 `definition_ref`。`allowed_values`、约束正文、模板、完整 `fact_object` 或其它第二 schema 内容不得进入该结果。派生 Schema 的 `schema_fingerprint` 覆盖这五项字段契约身份；其中 `definition_ref` 身份变化必须使既有草案依据失效。

### 11.4 事实对象受控创建输入与结果

`create-fact-object` 是一次只创建一个对象的状态变更操作。领域 `arguments` 只允许：可选绝对路径 `workspace_root`；必填 `draft_basis` object；必填 `fact_object` object。`draft_basis` 必须精确包含 `governed_project_id`、`fact_type_key`、`candidate_object_id`、`schema_fingerprint` 和 `worktree_fingerprint`，并来自 §11.3 的实际结果。YAML 类型的 `fact_object` 是待创建字段 object；Study 的 `fact_object` 精确包含 `frontmatter` object 与非空 `body` string。AI 提供的字段中禁止 `object_id`、`fact_type_key`、`created_at` 和 `updated_at`；Code 在最终分配身份时写入这四项，其中两个时间使用同一个带时区 RFC 3339 创建时点。AI 必须提供其余当前必填字段与自然语言内容，不得提交空值或占位内容；外部资料仅在类型要求或实际需要时使用 `urls`。

`observed_context` 必须包含 `signature`，且该 object 恰含 `product_name`、`model_name`、`agent_runtime_name` 三个键。每项为非空 string 或 null；三项均为 null、缺键或混入其它键时返回 `invalid_request`。Code 只把这一份观察到的快照完整覆盖到最新 `change_log` 条目的 `signature`，并删除该新条目的 `session_id`；不得合并草案自填值、默认值或旧署名。


full-v4 Working Tree 测试证据 DTO 的唯一字段与比较契约属于 07 及其授权附件，不是事实对象共同字段、类型专属字段或本登记的结构。05 只约束承载该 DTO 的事实读写边界，不复制或另行授权其字段。

最终身份由 Code 在创建临界区分配。顺序编号在同一管辖项目的同一 `git_common_dir` 内使用“项目 + 类型”共享排他锁和单调 counter；counter 是协调根中的唯一持久单调记录，永不因目标冲突、回读失败、回滚、调用失败或崩溃回退。本文所称“身份分配”只是基于可见身份和 counter 选择下一尝试编号的过程，不拥有另一份持久状态；后续所称的提交、回读或未改变均专指 counter，不得表述为另有独立分配器已经提交。进入共同锁后，Code 必须先重新扫描全部可见 linked worktree 的既有身份和 counter，形成本次唯一的 `attempted_object_id`；再原子推进 counter 并立即按预期 bytes 回读。只有原子推进与该回读都成功，`counter_state` 才是 `committed`，该 ID 才是实际 `allocated_object_id`。随后才可重新执行最终前置检查，并对该唯一 ID 尝试一次目标文件原子 no-overwrite 创建，最后按 `read-fact-objects` 的同一机械边界回读实际 Working Tree。一个公开 `create-fact-object` 调用至多发起一次 counter 原子推进和一次目标 no-overwrite 创建；目标已存在、符号链接、手工并发写入、候选身份过期或其它已知 no-overwrite 冲突都必须立即如实交还，不得在同一次调用中静默分配下一编号重试。下一次创建必须是新的公开调用并重新形成当次观察。不同 clone 或不同机器不共享本地锁，首版只在后续合并前通过全局身份扫描拒绝冲突，不声明跨 clone 唯一分配已经解决。

写后回读未能 `passed` 时，只可在确认目标仍精确等于本次原子创建 bytes 时尝试条件删除回滚。`rollback_state=not_needed` 只表示目标已确认创建且写后回读已通过；它不能表示“没有发生任何创建”。`not_applicable` 只表示尚未确认初次目标创建，因而不能安全定义删除动作；`not_removed` 表示虽已确认初次创建，但删除条件不能证明成立，或条件删除已经明确未能移除目标；`uncertain` 表示条件删除进入了不能确认是否移除的状态。删除成功只表示 `rollback_state=removed`：目标文件已移除、本次对象未创建；它不回退 counter，也不得据此声称编号未消耗。`not_removed` 或 `uncertain` 时，必须按同一项目级机械边界重新读取目标，并在 `final_observation` 中据实区分当前载体与本次创建 bytes 一致、为另一机械有效版本、机械无效、预期位置不存在或无法完成读取；该次重新读取只证明当前观察，不得把相同 bytes、目标不存在或其它结果归因于条件删除。counter 的编号状态与目标文件的命名空间状态是两个独立的操作结果：目标不存在不证明编号未消耗，目标存在或残留也不单独证明 counter 已提交。

在对具体 `attempted_object_id` 发起 counter 原子推进前失败时，领域 `result` 为 `null`。一旦已对该具体 ID 发起 counter 原子推进，无论外层 `outcome` 为何，领域 `result` 必须使用以下字段闭集；这些是本次受控创建的操作结果，不是 `fact_object` 字段，也不得改塞入 `diagnostics.details`：

| 字段 | JSON 类型与出现规则 | 含义与机械边界 |
|---|---|---|
| `requested_candidate_id` | string，必填 | 原始 `draft_basis` 中的候选身份；不因最终尝试身份不同而改写 |
| `allocation` | object，必填 | 使用下表“分配结果”字段闭集 |
| `target_namespace` | object，必填 | 使用下表“目标命名空间结果”字段闭集 |
| `actual_ref` | object，仅且必须在创建与写后回读均成功时出现 | 使用 §11.1 的稳定三元组；失败、回滚或残留不确定时不得把尝试 ID 冒充为有效事实引用 |
| `carrier` | string，仅且必须与 `actual_ref` 同时出现 | 只允许 `yaml` 或 `markdown` |
| `fact_object` | object，仅且必须与 `actual_ref` 同时出现 | 成功写后回读的实际对象；YAML 直接为对象映射，Study 为 `frontmatter` 与 `body` 的闭集 |

`allocation` 字段闭集为：`attempted_object_id`（非空 string）、`allocated_object_id`（string 或 `null`）、`counter_state`（`committed`、`not_committed` 或 `uncertain`）和 `allocation_consumed`（boolean 或 `null`）。`committed` 时 `allocated_object_id` 必须精确等于 `attempted_object_id`，且 `allocation_consumed=true`；`not_committed` 时前者必须为 `null` 且后者为 `false`；`uncertain` 时前者必须为 `null` 且后者为 `null`。`uncertain` 表示 counter 原子推进或其强制回读不能确认，不能被写成 `false`，也不能用目标当前是否存在代替。`target_namespace` 字段闭集为：`canonical_path`（基于 `attempted_object_id` 的 Git 相对 POSIX 路径）、`create_namespace_state`（`not_attempted`、`created`、`not_created` 或 `uncertain`）、`post_create_readback`（`not_run`、`passed`、`failed` 或 `unavailable`）、`rollback_state`（`not_applicable`、`not_needed`、`removed`、`not_removed` 或 `uncertain`）和 `final_observation`（`not_required`、`same_created_bytes`、`other_mechanically_valid`、`mechanically_invalid`、`not_found` 或 `unavailable`）。除下表列出的组合外一律非法；表中“新鲜观察”只允许后五个 `final_observation` 值，且必须是该次重新读取的实际结果。

| `counter_state` / `allocation_consumed` | `create_namespace_state` | `post_create_readback` | `rollback_state` | `final_observation` | `actual_ref`、`carrier`、`fact_object` |
|---|---|---|---|---|---|
| `not_committed` / `false` | `not_attempted` | `not_run` | `not_applicable` | `not_required` | 均不得出现 |
| `uncertain` / `null` | `not_attempted` | `not_run` | `not_applicable` | 新鲜观察 | 均不得出现 |
| `committed` / `true`；最终前置检查拒绝，尚未发起目标创建 | `not_attempted` | `not_run` | `not_applicable` | `not_required` | 均不得出现 |
| `committed` / `true` | `not_created` | `not_run` | `not_applicable` | 新鲜观察 | 均不得出现 |
| `committed` / `true` | `uncertain` | `not_run` | `not_applicable` | 新鲜观察 | 均不得出现 |
| `committed` / `true` | `created` | `passed` | `not_needed` | `not_required` | 三者均必须出现 |
| `committed` / `true` | `created` | `failed` 或 `unavailable` | `removed` | `not_required` | 均不得出现 |
| `committed` / `true` | `created` | `failed` 或 `unavailable` | `not_removed` 或 `uncertain` | 新鲜观察 | 均不得出现 |

只有 `counter_state=committed` 后才允许目标创建；`create_namespace_state=created` 时，`post_create_readback` 必须记录该次 bytes、载体、Schema、身份、引用和关系机械检查是否实际通过、失败或不可用。`not_applicable` 不得用于已确认初次创建，`not_needed` 不得用于未通过写后回读，`removed`、`not_removed` 与 `uncertain` 只允许用于已确认初次创建且写后回读为 `failed` 或 `unavailable` 的两行。目标冲突、目标创建不确定、counter 不确定，以及未确认移除的写后回读失败，都必须按表重新读取目标并填写新鲜观察，同时在共同 `verification`、`gaps` 和 `sources` 中保留实际检查、未完成范围及其依据；`same_created_bytes` 只说明当前 bytes 一致，不说明条件删除导致该结果。

在对具体 `attempted_object_id` 发起 counter 原子推进前失败时，`changes` 必须为空。此后共同 `changes` 必须与上述领域 `result` 一致，并按发生顺序精确包含两项或三项，不能用泛化的 `created` 压缩：第一项的 `target` 为 `allocation.attempted_object_id`，其 `status` 随 `counter_state` 分别为 `counter-consumed`、`counter-not-advanced` 或 `counter-advance-uncertain`；第二项的 `target` 为 `target_namespace.canonical_path`，其 `status` 随 `create_namespace_state` 分别为 `target-not-attempted`、`target-created`、`target-not-created` 或 `target-create-uncertain`。仅当 `rollback_state=removed` 时追加第三项 `target-removed`；仅当其为 `not_removed` 或 `uncertain` 时追加第三项 `target-remove-unconfirmed`；其余 `rollback_state` 不得追加第三项。每项的 `source_refs` 至少回指本节及当前类型的承载定义。`target-created` 只陈述一次目标创建已发生，并不等同于对象创建成功；只有表中的成功行才成立有效事实引用。`verification` 仍须如实说明实际检查、回滚和未完成范围，不得代替或压缩其中的 machine-readable allocation、命名空间和观察结果。

创建调用的 `scope.requested`、`scope.completed` 与 `scope.not_completed` 均以原始 `draft_basis` 作为同一范围成员；成功时该成员进入 `completed`，最终身份只进入 `result.actual_ref` 与 `verification.scope`，不得用新身份替换请求范围。只有目标创建和写后回读均成功时才可返回 `outcome: ok`；草案过期、Schema 或 worktree 变化、初始状态或语义字段机械不成立、出现未定义关系、授权或来源规则不允许时不得写入，并按 04 区分 `invalid_request`、`rejected` 或 `unavailable`。请求成功只证明一个新文件已经原子创建并通过当次机械回读，不证明自然语言事实真实、证据充分、Human Gate 已完成、Git 已提交或上层工作完成。

### 11.5 事实对象候选发现输入字段

本操作复用 §11.1 的 `work_object_locators`、`arguments.workspace_root`、管辖解析和唯一实际 worktree/common-dir 边界。领域 `arguments` 使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全复用 02 的配置选择语义 |
| `governed_project_id` | string | 必填非空 | 必须与实际管辖项目精确一致 |
| `card_layer` | string | 必填；只允许 `F1` 或 `F2` | `F1` 固定形成恢复基线；`F2` 按确定性条件缩小候选 |
| `fact_type_keys` | array | `F2` 必填且 1–6 个互异当前类型；`F1` 禁止 | F2 扫描类型范围，不改变类型语义 |
| `relation_targets` | array | F2 可选；最多 128 个互异稳定三元组 | 只保留 `relations[].target` 与任一目标精确相等的对象 |
| `relation_source_refs` | array | F2 可选；出现时 1–128 个互异稳定三元组 | 从每个已知来源对象的 `relations[]` 取得其**直接**正向声明边；来源类型不必位于 `fact_type_keys`，但每项必须属于 `governed_project_id`。它只提供一跳边与其目标的候选入口，不递归读取目标的 `relations`、不返回源或目标 F3 全文，也不以关系存在宣称语义相关、现时适用、行动允许或完成 |
| `relation_keys` | array | F2 可选；出现时 1–32 个互异非空 string，且 `relation_source_refs` 必须出现 | 只使来源类型当前定义的这些 `relation_key` 进入候选卡；每个值必须同时属于每个 `relation_source_refs` 来源类型在 20–25 定义的 relation-key 闭集。未选中的已声明边仍按 §11.6 的 `relation_navigation.edges` 保留为 `filtered`，不得静默消失；若所选来源类型的 relation-key 闭集没有共同成员，则不能同次使用本字段 |
| `current_workcase_ref` | object | 可选；使用 §11.1 稳定三元组且类型必须为 `workcase` | 回显 AI 或上层入口已知的当前工作责任，供 F0 恢复和后续 F3 精确展开；不由 Code 猜测绑定 |
| `selected_fact_refs` | array | 可选；1–128 个互异稳定三元组 | 回显压缩前或上层入口已明确选择的事实引用，供恢复后重新读取；不证明仍相关或适用 |
| `locator_text` | string | F2 可选；出现时必须非空且不超过 512 Unicode code points | 在 `urls[].ref` 中作区分大小写的精确字面 substring 匹配 |
| `text_match` | object | F2 可选；字段闭集为 `text`、`field_paths` | `text` 为 1–512 code points；`field_paths` 为 1–16 个互异、由所选类型 F2 卡片当前定义的直接字段或确定性摘录来源字段；只在对象完整当前字段的 string 或 string-array 成员中作区分大小写的精确字面 substring 匹配，返回卡片仍只携带允许的直接投影与有界摘录 |
| `page_size` | integer | 可选；1–200，默认 100 | 未请求 `relation_source_refs` 时限制本页卡片数量；请求时限制本页直接关系边数量，`cards` 只投影该边页中可返回目标的去重 F2 卡片，不另设第二个分页集合 |
| `cursor` | string | 可选；出现时必须非空 | 只能继续同一项目、worktree、查询和对象集指纹的下一页；不得移植、猜测或修复 |

在通用 `capabilities` 发现中，本操作可通过 `operations[].input_examples` 提供 `text_match` 的可组合输入片段。该片段只能列出本节已定义、无需猜测实例范围的 `card_layer`、`fact_type_keys` 与 `text_match`；它不是完整请求，调用者必须自行加入当前实际 `governed_project_id`，并按所选类型当前 F2 字段闭集替换文本与 `field_paths`。片段的来源回指至少包括本节，且其解释和组合边界以 04 的 `input_examples[]` 共同契约为准。


`relation_source_refs` 是正向边过滤，不是把来源对象本身作为候选卡。Helper 先对每个精确来源引用安全读取其关系声明，再仅沿来源对象实际 `relations[]` 的单条直接边定位目标；不根据标题、任务文字、关键词、相似度、历史会话或关系键名称猜测其它边。来源对象因路径、解析、Schema、身份、关系形状、项目级关系检查或资源边界而不能形成可用关系声明时，不生成伪边或候选卡，必须在 §11.6 `relation_navigation.source_results`、共同 `gaps` 和相应 partial 范围中保留实际状态。来源具有可用声明但目标不存在、invalid 或 unavailable 时，仍必须保留该边及其稳定 source/key/target，不把它降格为“无关系”。

当 `relation_source_refs` 出现时，候选对象必须是其中某一条直接边的目标，且仍满足 `fact_type_keys`、显式 `statuses`、`exact_refs`、`relation_targets`、`locator_text` 与 `text_match` 的全部其它条件。省略 `statuses` 时，直接边的 mechanically valid 目标不受默认候选状态过滤；因此终态直接目标仍进入按需引用闭包。显式 `statuses` 仍精确过滤终态。每条可安全取得的直接声明按固定顺序处理：先以 `relation_keys` 判定 relation key 是否入选；未入选时边固定为 `filtered/relation-key-filter`，不再宣称已检查目标。relation key 入选后，先处理 source/target 的 `not_found`、`invalid`、`unavailable`，这些失败优先于其余 F2 过滤；来源自身关系形状可安全取得、但其 `invalid` 仅由当前边目标的缺失、invalid 或 unavailable 引起时，边必须以相应 target 状态报告，`source-invalid` 只用于来源声明或其它来源条件本身阻止安全形成该边的情形。只有 source 与 target 均 mechanically valid 时，才依次计算类型、显式状态、exact ref、relation target、locator 和字段文本过滤。`relation_targets` 与 `relation_source_refs` 同时出现时分别按对象自身的反向条件和来源到该对象的正向边计算，二者必须同时成立；不得改为任一方向的并集、邻域搜索或关系传递闭包。

未知字段、非法类型或状态、重复成员、F1 携带过滤器、F2 缺少类型、`relation_keys` 缺少 `relation_source_refs`、relation key 不在全部来源类型当前闭集、字段路径不属于所选类型 F2 直接投影或确定性摘录来源字段、非空 `observed_context`、非空 `authorization_reference` 或非 `null` 的 `requested_disclosure` 均为 `invalid_request`。cursor 解码失败、查询不一致、worktree/common-dir 不一致、对象集指纹变化或 offset 越界使用 `rejected`，并要求从第一页重启，不得把旧页与新对象集合并；查询指纹必须包含 `relation_source_refs` 与 `relation_keys` 的稳定排序值，因而不得把不同种子、关系键或 F2 过滤条件的页面拼接。

### 11.6 事实对象候选发现结果字段

领域 `result` 使用字段闭集：`recovery_manifest`、`cards`、`coverage`，以及仅在请求 `relation_source_refs` 时出现的 `relation_navigation`。`recovery_manifest` 是 F0，字段闭集为：

| 字段 | JSON 类型 | 含义 |
|---|---|---|
| `governed_project_id` | string | 当次实际管辖项目 |
| `git_worktree_root`、`git_common_dir` | string | 当次实际 Git 身份的绝对路径 |
| `schema_fingerprint`、`object_set_fingerprint` | string | 当前五类型派生 Schema 与被扫描对象集合的 SHA-256 指纹；只用于过期检测，不成为事实身份 |
| `counts` | array | 按类型和状态升序列出机械有效对象数量；每项字段闭集为 `fact_type_key`、`status`、`count` |
| `current_workcase_ref`、`selected_fact_refs` | object 或 null；array | 原样回显请求中的恢复指针；前者未提供时为 `null`，后者未提供时为空数组；不提升为候选命中或事实适用结论 |
| `invalid_objects`、`unavailable_objects` | array | 列出未进入卡片集合的 canonical path、`check_status` 和机械问题；对象身份可安全确定时包含稳定 `fact_ref`，目录或预算范围失败时改含 `fact_type_key`；不可静默忽略 |



| 类型 | F2 `fields` 投影 |
|---|---|
| Spark | `fields` 只含 `object_id`、`title`、`status`、`priority`、`updated_at`；`intent` 存在时，`excerpts` 按 `intent`、`summary` 的固定顺序各包含一项对应 `field_path` 的有界摘录，旧对象缺失 `intent` 时只包含 `summary`；两个字段都是 F2 `text_match.field_paths` 允许的完整检索来源，但都不直接进入 `fields`，也不得在旧对象上生成伪 `intent` 摘录 |
| WorkCase | 字段闭集、active/closed 差异、`work_item_counts` 与无摘录边界唯一按 21 §9.1 |
| ADR | `object_id`、`title`、`status`、`decision_question`、`decision`、`applicability`、`updated_at` |
| Pitfall | `object_id`、`title`、`status`、`symptoms`、`trigger_conditions`、`applicability`、`validation_summary`、`updated_at` |
| Study | `object_id`、`title`、`status`、`research_intent`、`research_question`、`abstract`、`recommendation_summary`、`relations`、`updated_at` |

`match_reasons[]` 只允许字段闭集 `kind`、`field_path`、`matched_text`；`kind` 为 `recovery-baseline`、`default-status`、`status`、`exact-ref`、`relation-target`、`relation-source`、`locator` 或 `field-text`。`relation-source` 的 `field_path` 精确为形成该卡的 `relations[<non-negative index>].target`，不出现 `matched_text`；对应 source、relation key、目标和来源定义位置只能回到同页 `relation_navigation.edges`，不得由卡片标题、排序或 AI 摘要补造。`matched_text` 只在 locator 或字段文本命中时出现，并且必须是对象完整当前字段中实际命中的原文字面内容；命中位置可以位于返回摘录之外，这不允许扩大摘录预算或暗示摘录已覆盖命中上下文。不得返回相关性说明或语义分数。Study 卡片不解释当前性；版本与观察边界只能通过精确读取和必要 F4 来源核对。

当 `relation_source_refs` 出现时，`relation_navigation` 使用字段闭集 `source_results`、`edges`。这是当前 Working Tree 中来源对象正向关系声明的当次派生组织，不是新的事实关系、反向写回、持久索引、语义相关性判断或自动读取记录；来源变化后必须重新调用，不得跨对象集指纹、worktree、cursor 或会话直接复用。`source_results[]` 按稳定三元组升序，字段闭集为 `source_ref`、`check_status`、`canonical_path`、`issues`、`source_refs`：`source_ref` 使用 §11.1 三元组；`check_status` 只允许 `mechanically_valid`、`invalid`、`not_found` 或 `unavailable`；`canonical_path` 在类型和身份可确定时为该来源当前预期 Git 相对 POSIX 路径，否则为 `null`；`issues` 使用 §11.2 的机械问题字段闭集，无问题时为空，必须保留导致 source/边无效、不可用、冲突或循环的实际检查依据；`source_refs` 回指类型来源、实际 Working Tree 读取或实际失败依据。来源因目标缺失等项目级关系条件成为 `invalid` 时，只要其自身已安全读取并具有当前 Schema 允许的 `relations[]` 形状，仍必须从该声明形成下表边；不能安全取得该形状时才没有边，且不得把缺边解释为来源没有关系。

`edges[]` 只含当页的直接声明边，并按 `(source_ref.governed_project_id, source_ref.fact_type_key, source_ref.object_id, relation_key, target_ref.governed_project_id, target_ref.fact_type_key, target_ref.object_id, relation_index)` 升序。每项字段闭集为 `source_ref`、`relation_index`、`relation_key`、`target_ref`、`relation_definition_refs`、`source_refs`、`edge_status`、`reasons`。前三个引用/键字段分别精确回显实际声明的来源、其 `relations[]` 从零开始下标、relation key 和目标稳定三元组；`relation_definition_refs` 至少一项，回指该来源类型在 20–25 中定义此关系方向、含义和边界的位置；`source_refs` 至少一项，回指当前源对象读取或其实际可读的关系声明。`edge_status` 只允许：`returned`（该边的目标 F2 卡已在本页返回）、`filtered`（relation key 未入选，或目标有效但未满足当前其余 F2 过滤）、`not_found`、`invalid` 或 `unavailable`（来源或目标不能形成可用边，`reasons` 使用下表实际失败值）。`reasons` 是非空、去重、按固定枚举顺序排列的 string array，不表示语义原因、优先级或行动建议：

| `edge_status` | `reasons` 允许值 | 含义与边界 |
|---|---|---|
| `filtered` | `relation-key-filter`、`fact-type-filter`、`explicit-status-filter`、`exact-ref-filter`、`relation-target-filter`、`locator-filter`、`field-text-filter` | 只说明哪一项当次结构化 F2 条件未命中；省略 `statuses` 时不得使用默认状态过滤，也不得用 `default-status` 排除直接目标 |
| `not_found` | `target-not-found` | 目标的预期 canonical 位置不存在；目标缺失时仍保留整条声明边。source 不存在时没有可读取的声明边，必须在 `source_results` 与共同 gaps 中报告 |
| `invalid` | `source-invalid`、`target-invalid` | 对应对象或边的已完成机械检查不成立；不把它作为有效事实关系或可消费 F2 卡 |
| `unavailable` | `source-unavailable`、`target-unavailable`、`scan-budget` | 所需安全读取、项目级关系检查或当前 10,000 canonical 身份扫描预算未完成；只能报告实际观察到的范围，不能把未读部分写成无边 |
| `returned` | `relation-source` | 边的目标已作为本页 F2 卡返回；该值只记录直接声明命中，不证明对象相关、适用、应读取或应采取行动 |

同一目标可由多条不同边指向；`cards` 仍按稳定身份去重，而每条本页边都必须保留。页面外的边不在本页伪造 `not_expanded` 记录；它们只能由同一 `coverage.next_cursor` 的后续边页继续取得，因而一条 cursor 始终只对应一个稳定边序列，不存在与卡片竞争的第二分页集合。来源无法安全读到关系形状、目录/对象扫描预算使来源范围未完成，或来源类型不定义任何关系时，分别通过 `source_results`、共同 `gaps` 或空 `edges` 如实表达；空边只证明已完成来源范围内没有可报告的直接声明，不证明对象在事实语义上“无关联”。

`coverage` 字段闭集为：`status`（`complete` 或 `partial`）、`total_matching`、`returned`、`offset`、`next_cursor`、`object_set_fingerprint`。未请求 `relation_source_refs` 时，`total_matching` 是同一对象集合与查询下完整 mechanically valid F2 卡匹配数，`returned` 是本页实际 F2 卡数，`offset` 和 `next_cursor` 作用于卡片序列。请求 `relation_source_refs` 时，四个分页数值改为同一当次已实际观察到、可稳定排序的直接声明**边**序列：`total_matching` 为该序列总边数（包括 `filtered`、`not_found`、`invalid` 和 `unavailable` 边），`returned` 为本页 `edges` 数，`offset` 为本页首边位置，`next_cursor` 只在尚有下一边页时为非空 string；不能安全读取关系形状的 source 不贡献未知边数，必须使 coverage 为 `partial`，并在 `source_results`、共同 `scope.not_completed` 与 `gaps` 保留该未观察来源范围，`total_matching` 不证明该 partial 范围内不存在其它边；`cards` 仅是本页 `returned` 边可形成目标卡的去重投影，既不另计数也不另分页。存在 invalid 或 unavailable 对象、`relation_navigation.source_results` 未完成项，或已观察边序列含 `not_found`、`invalid`、`unavailable` 时 coverage 为 `partial`，并必须进入共同 `scope.not_completed` 与 `gaps`：来源读取范围逐项保留；边的 source/key/target 与原因只对**当前已交付边页**逐项保留，尚未交付页只由 partial coverage 和同一 `next_cursor` 表达，必须在其实际取得时再展开；F1 此时不得宣称恢复基线完整。没有这些对象且本页形成时为 `complete`，即使仍有下一页也只表示已观察边集合完整，AI 仍须继续分页才能声称全部直接边已读。

首版单次最多扫描五类合计 10,000 个 canonical 身份；目录、Git 身份、Schema 或必需机械检查不能完成时相应范围为 unavailable。操作不返回 F3 正文；AI 选中对象后必须使用 `read-fact-objects` 精确展开。共同 `changes` 固定为空；共同 `verification` 只证明当次直接扫描、机械检查、确定性过滤、投影、排序和分页实际完成的范围。

### 11.7 事实对象单对象 CAS 更新输入与结果


领域 `arguments` 只允许：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全复用 02 §10.1 的配置选择语义 |
| `fact_ref` | object | 必填；精确使用 §11.1 `fact_refs[]` 的稳定三元组字段闭集 | 选择唯一目标；不接受路径、标题、别名或搜索回退 |
| `expected_content_fingerprint` | string | 必填 64 位小写十六进制 string | 必须精确匹配同一 worktree 当前载体再次安全读取的 SHA-256；不匹配时使用 `rejected` 且不写入 |
| `fact_object` | object | 必填 | YAML 类型提交排除 Code 托管字段后的完整目标字段映射；Study 精确包含 `frontmatter` object 与非空 `body` string；未提交字段表示目标状态中不存在，不实施部分 merge |

`work_object_locators` 与唯一实际 worktree/common-dir 边界复用 §11.1；`observed_context.signature` 必须恰含 `product_name`、`model_name`、`agent_runtime_name`。每项为非空 string 或 null，三项全空、缺键或混入其它键时返回 `unavailable`，不得保留草案手填、默认署名或 `session_id`。每次写入前必须重新取得并判断三字段快照，不得复用先前写入或其他动作的快照。Code 用该完整快照覆盖最新流水的 `signature`。`requested_disclosure` 必须为 `null`。`authorization_reference` 可以回指当次已经存在的 Human 决定或授权来源，但 Code 不根据自然语言自动判断授权语义或作用范围。Code 托管 `object_id`、`fact_type_key`、`created_at` 和 `updated_at`：前三项从当前对象原样保留，最后一项在实际变更时写为当次带时区 RFC 3339 时点且必须晚于当前 `updated_at`；本地时钟无法形成后继时点时拒绝写入，AI 不得提交这四项。

当 mechanically valid 的当前 Working Tree before 完全没有顶层 `change_log` 时，本操作只可在**同一次真实更新**中建立第一条流水，不提供独立迁移、空更新或历史回填。Code 必须在类型锁内读取 HEAD 中同一 canonical path 的普通文件，并确认其可按当前对象身份与类型 Schema 机械读取、同样完全没有 `change_log`；HEAD 路径不存在、不是普通文件、读取或机械校验不可用，或者 HEAD 已有流水但 Working Tree 删除了它时，必须零写入拒绝。该资格只由当前 before、同路径 HEAD before、完整内容指纹和类型规则决定，不得使用对象编号、创建日期或固定实例 allow-list。调用方提交的完整 after 必须包含恰好一条流水；Code 用本次 `observed_context.signature` 覆盖其署名、移除 `session_id`，并将该条 `at` 与本次 `updated_at` 绑定为同一 `event_at`。第一条摘要必须据实说明本次真实变化和此前历史未恢复；它不表示对象创建、原始形成者、此前修改次数或完整历史。已有流水仍必须保留完整前缀并恰追加一条。

Code 必须在同一类型受控写入锁内重新确认管辖、Git 身份、目标普通文件、当前对象机械有效性和完整内容指纹。来源明确允许的历史记录更正是唯一例外：当前载体虽因既有机械错误无效，但 `read-fact-objects` 已按 §11.2 返回修复指纹，且仍可解析稳定身份、托管时间和完整内容 bytes 时，Code 可以只为形成完全机械有效的同一对象 after 执行 CAS；它不解释错误语义、不选择状态结论、不接受无法解析身份、托管时间或指纹的对象，也不放宽普通更新的 current-valid 前置。输入内容与当前对象除 `updated_at` 外完全相同时返回 `no_change`，不重写文件或制造新时间。确有变化时，必须对完整目标快照执行载体、Schema、身份、引用、关系和具体类型条件检查，并对变更前后执行以下机械转换边界：

1. status 不变时只可作具体类型来源允许的原地更正或内容更新；status 或 phase 变化只允许该类型来源明示可以由单对象快照完成的转换，终态能否重开、何时退回及字段如何失效均以该来源为准；
2. 本操作不接受 `fact_type_key=workcase`；WorkCase 的普通活动期写入、Human 主动终止开始、主动终止完成、正常 Gate2 关闭与 closed 更正必须分别使用 21 §7 定义的 `update-workcase`、`begin-workcase-termination`、`complete-workcase-termination`、`close-workcase` 与 `correct-closed-workcase`。请求 WorkCase 时使用 `invalid_request` 且零写入，不得因 status/phase 不变或自称笔误而退回通用入口。上述五个 WorkCase 专属操作都只接受 mechanically valid 的当前 before，不继承本节为其它来源明确允许的 invalid 记录修复例外；只有 21 §7 明确固定历史来源、对象 allowlist、`status=closed`/`check_status=invalid` 前置条件、恢复标记和 0092 完整性审计证明的 `recover-invalid-workcase` 可以恢复其列出的 invalid closed WorkCase。除此例外，invalid WorkCase 只能继续只读诊断与交还，不得借专属操作删除旧字段、改换形状或推进 lifecycle。

具体类型仍可把责任边界、来源意义、审核独立性、验证充分性或更正是否仍为同一事实交给 AI/Human 判断。Code 只机械比较来源已定义的结构投影；对 21 已明示定义的 plan/result projection，结构差异、版本递增与失效集合是确定性机械规则，不再由 AI 判断是否“实质改变”，也不得把自然语言改写解释为“只是文案”以绕过重审。

受支持的 Helper 写入在类型锁内串行，并在原子替换前再次比较旧载体完整 bytes。这一保证覆盖共享同一 `git_common_dir` 且通过当前受控入口的并发进程；不使用该锁的外部手工进程或工具只能在替换前后尽可能检出，不声称对这些外部写入或跨 clone 写入提供线性化 CAS。原子替换后必须使用 `read-fact-objects` 的同一机械边界回读。写后回读不成立时，只可在目标仍精确等于本次新载体时 CAS 回滚原文；条件回滚没有形成 `namespace_state=committed` 时，必须再按同一项目级机械边界重新读取目标，并据实区分当前载体与本次新载体一致、与更新前载体一致、为另一机械有效版本、机械无效、预期位置不存在或无法完成读取；该次重新读取只证明其当前观察，不得把相同 bytes 归因于条件回滚。`namespace_state=not_committed` 与 `namespace_state=uncertain` 必须分开表达。冲突或回滚失败必须报告上述实际残留和未完成验证，不得返回 `ok`。

成功与 `no_change` 的领域 `result` 字段闭集为：`actual_ref`、`canonical_path`、`carrier`、`previous_content_fingerprint`、`content_fingerprint` 和 `fact_object`。`actual_ref` 使用 §11.1 稳定三元组；两个指纹都是 64 位小写十六进制 SHA-256，`no_change` 时两者相同。`fact_object` 返回回读后实际对象。共同 scope 的三个数组都使用原始 `fact_ref` 作为同一范围成员；成功更新时 `changes.status` 为 `updated`，并回指实际对象和 Working Tree 路径。请求成功只证明该单文件已在当次 CAS 边界内替换并通过机械回读，不证明自然语言事实、证据、Human Gate、Git 提交或上层工作已完成。

领域 `arguments` 只允许：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 完全复用 02 §10.1 的配置选择语义 |

`authorization_reference` 必须至少包含一个已经存在且作用范围明确的 Human 决定或授权来源；它证明当次迁移被授权，不替代 `migration_signature` 的实际执行责任。`work_object_locators` 与唯一实际 worktree/common-dir 边界复用 §11.1；`observed_context` 必须为空，`requested_disclosure` 必须为 `null` 或省略。

Code 必须在同一项目、同一事实类型的共享受控写锁内重新读取目标，并依次确认：目标仍为 mechanically valid；当前完整指纹与 `expected_content_fingerprint` 精确相等；目标确实缺少 `change_log`；`event_at` 是严格晚于当前 `updated_at` 的真实带时区 RFC 3339 时点；目标类型来源仍可形成完整 Schema；迁移后的完整对象、身份、引用、关系与类型条件均通过机械检查。迁移 after 保留既有身份、`fact_type_key`、`created_at`、所有对象自有语义字段、关系、状态和其它条件字段，只新增一条 `change_log` 起点，并由 Code 将 `updated_at` 与该条 `at` 绑定为同一实际迁移事件时间。新条目的 `signature` 只含统一登记允许的 `agent_id` 与 `host_environment`，`session_id` 单独记录；不得写入 `signer_type`，不得追加多条未知历史。

替换前任何校验、锁、CAS、Schema、来源或授权失败都必须零写入。原子替换后必须按同一对象边界精确回读并执行独立全库完整性审计；若回读失败，只有在当前载体仍逐字节等于本次新载体时才可条件回滚。并发改变、回滚失败、回滚状态或当前载体无法确认时，禁止覆盖或补偿写入，必须交还实际 `rollback_state`、`final_observation`、残留和未完成范围，并停止后续事实写入。操作一次只修改一个对象；外层可以逐对象编排，但不得把多个单对象结果声明为一个原子批处理成功。

成功结果至少返回实际稳定引用、canonical path、carrier、变更前后 fingerprint、迁移后的完整对象、迁移事件时间与 `history_recovered=false`；写入口自身的 `verification` 必须区分目标精确回读和独立完整性审计。`outcome=ok` 只表示该单对象替换和当次结果已经形成，不表示其它遗留对象已迁移、事实语义真实、下游行动完成或 Git 已提交。

### 11.7.2 已退休：未提交流水旧签名归一

> 本节以下原始契约仅作历史记录，已不授予任何写入能力；当前实现没有对应的 Helper 公开操作。

`normalize-uncommitted-change-log-signatures` 是严格单对象的提交前元数据归一入口。它只处理当前 `HEAD:<canonical path>` 已存在、且 Working Tree 在该 HEAD `change_log` 精确前缀之后追加了至少一条 `signature` 恰为非空 `model_id` / `host_name` 中间形状的流水；只把这些后缀条目的 `host_name` 键改为 `agent_workbench`，值与其它全部内容不变。HEAD 前缀中的同形状记录作为只读历史原样保留。该操作不追加流水、不更新时间、不改变业务字段、不推进状态或 phase，也不是 closed WorkCase 更正入口。

领域 `arguments` 只允许 `workspace_root`、使用 §11.1 稳定三元组的 `fact_ref`、绑定当前 Working Tree 完整内容的 `expected_content_fingerprint`，以及绑定当前 HEAD 同一路径普通文件内容的 `expected_head_content_fingerprint`；两个指纹均为 64 位小写十六进制 string。`authorization_reference` 必须至少包含一个范围明确的 Human 授权来源；`observed_context` 必须为空，`requested_disclosure` 必须为 `null` 或省略。

Code 必须在目标类型共享锁内重新读取 Working Tree 与 HEAD，并确认两项指纹、Git 普通文件身份、当前 Schema、稳定对象身份和 HEAD 日志精确前缀。后缀中任一条不是精确的 `model_id` / `host_name` 两字段形状、出现空值、混合字段、旧 `agent_id` / `host_environment`，或 HEAD 前缀和 Working Tree 不一致时，必须零写入拒绝。候选只能发生上述键名替换；`model_id`、宿主值、`session_id`、`at`、`summary`、对象语义、托管时间和 HEAD 前缀逐项不变。替换使用完整 Working Tree bytes 的 CAS，写后精确回读，并附加 §11.9–11.10 同核全库完整性审计；审计未达 complete 时如实保留局部写入与回读事实，但不得据此继续事实写入、提交或声明整体完成。

成功结果返回实际引用、canonical path、carrier、HEAD/Working Tree 前指纹、写后指纹、归一条目数和回读对象。该结果只证明未提交后缀的字段名已受控归一，不把归一行为表述为新业务事件、历史重新签名或身份真实性验证。

### 11.7.3 历史 routed Spark 受控迁移输入与结果

`migrate-legacy-routed-spark` 只处理 20 固定 allow-list 中仍为 `status: routed` 的单一 Spark。领域 `arguments` 只允许 `workspace_root`（可选）、`fact_ref` 和 `expected_content_fingerprint`；`fact_ref` 必须是当前管辖项目中的 Spark 稳定三元组，指纹必须绑定当次完整 before。共同 `authorization_reference` 必须至少含一条逐条 Human 授权来源，`observed_context` 必须提供当前环境署名，`requested_disclosure` 必须为 null 或省略。Code 不接受目标状态、关系、处置说明或完整 after：它只按 20 构造 `routed → implemented` 的唯一 after，将该 Spark 自身的每条旧 `routed-to` 转为同目标 `related-to` 并去重，保留其它历史内容，并追加本次 change_log 流水。

操作必须在同一实际 worktree 的受控锁内再次读取、核对 allow-list、状态、指纹和完整处置说明，完成原子替换、精确回读及 11.9 独立完整性审计。每次调用只写一个对象；失败、拒绝、冲突、回读失败或审计未完成时不得继续其它对象。成功结果复用 11.7 的 `actual_ref`、路径、前后指纹和回读事实对象；共同 `changes` 只在实际更新时标记 `updated`。

### 11.8 共享单对象受控写事务

`create-fact-object`、`update-fact-object` 和具体类型来源声明的受控写操作共同使用同一 `git_common_dir/ldvh` 持久协调根。创建使用“项目 + 类型”单调 counter 与 §11.4 所述无状态身份分配过程；对既有对象的更新使用同一“项目 + 类型”排他域串行当前受控入口。linked worktree 不得各自建立 counter 或锁，不得在权限不足时回退 worktree-local、进程临时目录、仅内存锁或无锁扫描；这些替代会分裂可见对象集合、复用已消耗编号或削弱已声明的并发边界。

单对象更新事务按以下顺序执行：

1. 在进入锁前完成有效请求、唯一项目/worktree/common-dir 与派生 Schema 的只读确认；
2. 进入共同类型锁后重新安全读取目标载体、机械校验当前对象，并精确比较 expected content fingerprint；普通更新要求当前机械有效；只有具体类型来源明确允许 invalid 记录修复时，才可进入 §11.7 的例外，并继续满足稳定身份、托管时间和修复指纹条件；
3. 请求表达的完整 after 与当前对象相同时先返回 `no_change`，不得为了更新时间而重写；
4. 确有变化时使用 Helper 服务边界提供的唯一带时区 RFC 3339 `event_at` 写 `updated_at`；该值不能严格晚于当前值时拒绝且零写入；类型专属托管记录只能按其来源把同一值用于本事件的其它时间字段；
5. 对完整候选执行载体 parse、派生 Schema、身份、引用、关系、项目级约束和变更前后 transition 检查；
6. 在替换前再次比较当前完整 bytes，原子写入后按 `read-fact-objects` 的同一边界回读；回读失败时只可在目标仍精确等于本次新 bytes 时条件回滚；已确认完成原子写入与精确回读的写入口必须在返回中附加与 `check-fact-integrity` 同核的独立全库机械审计，其结果单列于共同 `verification`，不得由目标回读替代。回读失败、残留或不可观察分支仍按各操作和行动模板要求调用公开审计入口。


共享事务接收调用方或类型适配层已经确定的完整语义 after，不解释事实正文、审核结论、授权含义、实质变化或流程推进，也不反向调用 Helper。类型适配层可以确定性填入来源明示的托管字段和固定失效集合，但不得复制状态机或从普通字段差异选择 phase、版本、复审或 Human Gate。完成类型专属回读的成功写入口复用 §11.9–11.10 的同核审计实现，并把 `complete`、`partial` 或不可用的实际结果作为独立 `verification` 交还；写入口自身的 `ok` 只陈述原子写入与精确回读，不能把 audit 未完成写成可继续、可提交或整体成功。残留、回滚或不可观察分支保持由行动模板调用公开审计入口。通用 `update-fact-object` 的请求与完整结果形状唯一按本节执行，具体类型不得复制或改写。

Helper 在有效服务请求边界只观察一次 `event_at`；实际受控记录时间和该受控写操作生成的 Working Tree observation 应复用该值，不得在 operation、候选和该对象写入来源回指中各自重新读取时钟。管辖、配置或其它只读观察仍按其自身实际观察边界记录。`no_change` 的领域结果不得把该边界观察冒充对象事件；具体操作需要返回事件字段时使用 `null`。

进入共同锁前，锁目录或锁文件因权限、只读文件系统或等价的预期访问限制无法创建或取得时，必须在 target 与 counter 均未改变的情况下返回 `unavailable`，使用稳定 code `controlled_write_lock_unavailable`，并在 compact 中保留摘要与恢复条件、在 diagnostic 中安全增加 `stage`、协调根角色、所需访问和系统错误类别。不得返回原始异常正文或把目标读写阶段的其它异常误分类为锁问题。`capabilities` 是读取入口，不得以创建目录或锁文件作为写探针；没有观察到确定性缺口只表示可以尝试调用，不保证未来动态锁获取成功。

既有对象的目标载体已经原子替换并按同一机械边界成功回读后，若共同锁的解锁（unlock）或文件描述符关闭（descriptor close）发生异常，事实目标仍属于已完成范围：Helper 保持 `ok`、原 `fact_ref` 进入 `scope.completed`、`scope.not_completed` 为空，并完整保留领域 `result`、`changes.status=updated` 与成功回读验证；不得倒退为锁进入阶段的 `unavailable` 或通用实现 `error`，也不得把事实写入表述为未知。

创建操作在 counter 已提交并按其定义边界回读，且新目标已创建、按同一机械边界成功回读并完成当次应有的关系检查后，若共同锁发生同类释放异常，也属于已完成范围：Helper 保持 `ok`、原 `draft_basis` 仍为 `scope.completed`、`scope.not_completed` 为空，并完整保留创建领域的 `result`、`counter-consumed` 与 `target-created` 两项变化记录及成功验证；不得因为无法确认后续串行协调而撤销已确认的编号消耗、新对象或创建结论。

前两种已完成边界使用稳定 gap code `controlled_write_lock_release_uncertain`，只表示后续受控写的串行协调状态无法确认；compact 必须说明该影响及恢复条件，diagnostic 可以安全增加锁释放阶段（release stage）和状态类别，但不得回显原始异常正文。若在共同锁释放前已经形成其它领域结果（包括拒绝、不可用、回滚后的残留或编号消耗状态），同类释放异常不得将该结果覆盖为通用实现 `error`，也不得套用上述成功 code 或声称目标已完成；必须保留原结果、实际 `changes`、残留和未完成验证，并以无稳定 code 的协调 gap 说明后续串行状态及恢复条件。再次执行受控写入前，必须人工核对共同锁状态，并确认受控写入口能够重新取得和释放共同锁。

`no_change` 没有发生原子替换，因此不得使用 `controlled_write_lock_release_uncertain`；若其读取完成后仍发生同类锁释放异常，领域结果保持 `no_change`、`changes` 为空，并以同一个 `event_at` 记录当次 Working Tree observation，只把后续受控写的串行协调状态作为无稳定 code 的 gap 与恢复条件交还，不得把该观察冒充对象事件。

所有 YAML 事实载体序列化后必须满足：重新解析所得结构与目标字段语义等价；任何物理行不得以 ASCII space 或 tab 结束；最终文本使用 UTF-8 和单个结尾换行。实现必须通过 emitter 配置避免自动折行制造尾随空白，不得对已生成文本逐行 `rstrip`，因为字符串值中的空白可能具有领域语义。Study 的 frontmatter 服从同一规则，正文继续按其类型来源和 carrier 契约处理。

受控写把目标载体与协调根落到同一实际 Git Working Tree，并要求平台提供与具体事实类型耐久声明一致、且已声明/实现的持久化等级。`file_only` 表示仅文件内容已原子写入，未做 directory 元数据 fsync；`file_and_directory` 表示文件内容与目录元数据均已持久化。缺省 fail-closed：未获准平台对受控写保持关闭，`native_atomic_fact_writes_supported()` 返回 False，不得落到 `ldvh-base/`。Windows（`os.name == "nt"`）仅在以下条件全部成立时获准以 `file_only` 耐久受控写入：(a) 本文（05）处于当前规则源且本条款生效——此为必要前置，不代表行动允许已成立；(b) 目标文件系统为 NTFS，且本文/09 所列 file-only 原子写、排他锁与路径安全探针已验证通过；(c) Human 已在本条款经 Human Gate 批准时接受 `file_only` 相对 `file_and_directory` 的残留风险。获准平台范围不得由 Code、tests 或环境侧扩写或改判；获准不改变 00 §4 的 action-permission 独立成立语义。

**条件 (c) 状态：2026-08-07 经 Human Gate 满足。** Human 接受以下残留风险：断电或系统崩溃发生在 `os.replace()` 成功之后、目录项变更持久化之前时，目标目录可能回退到替换前的旧目录项（旧文件完整且已知），但不会产生部分写入、混合状态或损坏文件——临时文件在 `os.replace()` 前已 `fsync`，且 `os.replace()` 在 NTFS 上是原子操作。获准范围限于 NTFS fixed drive；UNC 路径、非 NTFS 文件系统、可移动驱动器和网络映射驱动器不适用。若 file-only 原子写、排他锁或路径安全探针的实现发生变更，或出现未预见的跨平台一致性缺口，本条件自动失效，须重新进入 Human Gate。

### 11.9 事实完整性机械检查输入字段

`check-fact-integrity` 是对一个受管辖 Git worktree 当前全部事实对象的只读全量机械检查，供行动模板与 Skill 在需要整库机械结论时引用。本操作使用 04 定义的共同请求对象。`work_object_locators` 必填且必须恰有一个非空路径 string，定位一个实际 Git worktree 或其中对象；相对路径以 Helper 进程实际 `cwd` 为基准。领域 `arguments` 只使用以下字段闭集：

| 字段 | JSON 类型 | 必填性与空值 | 含义与边界 |
|---|---|---|---|
| `workspace_root` | string | 可选；出现时必须为非空绝对路径 | 明确选择本次管辖配置的工作区根；不表示目标已经受管辖 |

本操作不接受候选路径清单、对象引用、快照身份、来源指纹、Index 身份或内容正文；检查范围由当次管辖解析唯一确定的受管辖 worktree 内本文与 20–25 定义的全部事实对象布局形成。`observed_context` 与 `authorization_reference` 必须为空，`requested_disclosure` 必须省略或为 `null`。本操作是只读检查，不创建、更新、修复、迁移或删除任何事实对象，不形成 Git 写入，也不对暴露的既有合规问题作静默修复。

检查必须使用与 `read-fact-objects` 相同的管辖、当前规则源、派生 Schema、载体解析与机械校验实现（同核），不得复制第二份解析或校验逻辑。全量扫描只允许存在于本操作等独立一等化入口；提交链路按 03 §9.9 只校验当次 Index 候选，不得引入全库扫描。

### 11.10 事实完整性机械检查结果字段

全量检查完成时，Helper 外层使用 `outcome: ok`，领域 `result` 使用以下字段闭集：

| 字段 | JSON 类型 | 空值规则 | 含义与边界 |
|---|---|---|---|
| `status` | string | 只允许 `complete` 或 `partial` | `complete` 表示发现过程完整且全部当前事实对象机械有效；`partial` 表示发现与读取已完成但存在机械无效对象或结构问题 |
| `object_count` | integer | 必填；不小于 0 | 当次扫描边界内发现的事实对象数量 |
| `problems` | array | 没有问题时为空 | 每项描述一处结构问题或一个机械无效对象 |

`problems[]` 成员字段闭集为 `fact_type_key`、`canonical_path`、`check_status` 与 `issues`；`check_status` 只允许 `invalid` 或 `unavailable`；`issues[]` 成员字段闭集为 `category`、`field_path`、`summary`，与读取操作的机械问题形状一致。结果不携带对象正文、自然语言语义判断、准入结论或行动授权。

管辖、规则源、派生 Schema 或发现过程无法形成可信全量检查输入时，外层使用 `unavailable` 并保留未完成范围、来源与诊断，不得以 `partial` 或空库表述。`status=complete` 只证明当次扫描边界内全部对象通过当次机械检查，不证明语义真实、来源充分、关系领域语义或 Human 授权；对象集合、规则源或 Working Tree 任一变化，先前结果立即失效。

## 12. 事实类型停止新增、合并、替代或取消

事实类型准备停止新增、合并、替代或取消当前使用时，必须先：

1. 确认其唯一定义来源的责任将保留、转移还是退出，并按 01 处理相应规范或附件关系；
2. 停止创建无法由当前有效来源验证的新对象；
3. 逐类确定现有对象继续保持、迁移、合并、归档或删除的条件；
4. 为仍适用的事实、来源、证据和关系确定唯一当前承接位置；
5. 处理引用该类型的其它事实对象、Helper、Code、tests 和 Web 契约，避免悬空引用或并行权威；
6. 验证迁移、替代或取消后的当前 Working Tree，并如实标记未处理对象、未验证范围和残留风险。

上述处理不建立本文统一的类型状态字段，也不能只通过删除 Schema、隐藏页面或停止 Code 支持完成。唯一定义来源仍为 `active` 时，实现不得自行宣布该类型已经取消；定义来源退出或被替代时，也不得遗失仍然适用的事实或让两个来源同时承担当前语义。

## 13. 时间字段的 Canonical 与兼容边界

事实对象中的时刻字段统一按 RFC 3339 instant 解释。Code 新生成或新写出的时刻必须使用 UTC `Z` 形式；`created_at`、`updated_at`、`change_log.at`、演变时间、审核/批准时间、观察时间和事件时间均适用此规则。

既有对象中的 `+08:00` 或其它明确 UTC 偏移属于可读取的历史表示，不迁移、不批量重写，也不因表示不同而创建“更正”流水。读取、比较和排序必须按瞬时值处理，不能按原始字符串的字典序处理；无法解析的值只能保留为未解析诊断。

纯日期字段不携带时区，不得套用 instant 的转换规则。未来时间是时间关系诊断，不等同于对象无效或事实错误；相对时间展示不得把未来值写成“前/ago”。

## 15. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 对事实模型的定义，或准备让不满足事实源边界的内容取得事实对象身份；
2. 已完成 §6.1、承载位置比较和独立复核，仍无法判断候选事实类型的净价值，或者需要接受明显的长期迁移与维护负担；
3. 同一事实对象或同一类事实存在多个相互冲突的权威位置，来源规则无法确定保留、合并或放弃哪一处；
4. 事实类型或大批事实对象的合并、迁移、归档或删除可能造成仍适用事实、来源、证据或关系的实质损失；
5. 需要处理具体事实类型定义来源规定必须由 Human 决定的证据例外、状态转换、风险、关闭、归档、合并、替代或删除方向。
6. 新增、删除、改名、拆分、合并或改变字段的 JSON 类型、稳定身份或共同语义，并且语义复核仍有歧义，或会对多个当前类型产生破坏性迁移负担。

Human 决定的复用按 00 §10 执行；Human 只能决定是否停止、改向、取舍承接位置或接受清楚标明的未验证风险，不能替代类型准入、定义来源、事实源写入与回读、对象校验、证据充分性或技术验证，也不能使无效对象、状态或关系自动成立。

## 16. Stop Conditions

出现以下任一情况时，必须暂停依赖受影响事实类型、事实对象或声明的最小范围：

1. 候选类型尚未满足准入条件或没有当前有效的唯一定义来源，却准备创建、更新或消费正式事实对象；
2. 正在仅凭历史名称、规范、字段、状态、目录、现存实例、Code 或 Web 实现恢复具体事实类型；
3. 事实类型标识重复、格式错误、被改派或无法回到同一当前定义来源，或者对象不在允许的事实源位置、稳定引用有歧义、身份或当前权威位置不唯一，或者当前 Working Tree 内容无法按具体事实类型的定义来源解析；
4. 状态、字段、证据或关系违反具体事实类型的定义来源，却准备静默修复、回退旧提交或继续作出成立声明；
5. 正在创建或使用未登记字段或结构，字段或结构没有覆盖全部 `current`、`retired` 登记及本类型完整提案的全局查重与独立语义复核，多个类型或草案出现未消歧的同名异义或异名同义身份，第二个类型准备复制现有专属字段或结构而未先提升，或者登记、唯一定义、适用范围、成员出现规则和类型绑定不一致；
6. 来源无法按所需精度回指，证据范围不能支持当前结论或转换，或者关系目标无法通过稳定身份定位；
7. Helper、Code、tests、Schema、缓存、索引、聚合或 Web 正在新增、改变或覆盖事实类型语义，或把确定性命中、候选返回、机械有效或非终态自动解释为语义相关、当次适用或应全量注入；
8. 写入、更新、转换、关闭、归档、合并、替代、删除或类型变更没有实际完成并回读，却准备声明对象或类型已改变；
9. 类型或对象的变更会遗失仍适用事实、来源、证据或关系，留下悬空引用，或形成多个当前承接位置；
10. 无法确认停止影响哪些对象、类型、消费方或声明，继续推进可能扩大不一致。

类型未准入、对象无效、状态无法判断或关系缺失本身不造成全局停止。暂停范围与允许继续的行动按 00 §11 执行；可以继续只读核对当前来源和对象、比较承载位置、补充来源与证据、修正草案或对象结构、拆分冲突、准备 Human Gate，并继续明确不依赖受影响事实的普通工作。

恢复按 00 §11 执行；与触发原因对应的条件必须满足：类型准入和唯一定义来源成立；字段与结构已经完成全局查重、唯一登记、定义、适用绑定和独立复核；对象身份、位置、结构、状态、来源、证据或关系已经修正并回读；冲突权威位置已经处理；声明已经缩小到现有依据实际支持的范围；类型或对象变更已经保留仍适用事实；或者 Human 已对其保留事项作出作用范围清楚的决定。
