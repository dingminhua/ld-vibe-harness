# V4 Web 实现规划

> 当前规划入口：本文是当前唯一的 V4 Web 实现规划入口。本文不是规则源，不定义事实类型、字段、状态或产品语义；稳定要求以当前有效 Specs 为准。`web/docs/` 保留既有产品实践与实现说明，若其内容与当前 Specs 或本文记录的 V4 适配状态冲突，不得据此扩大 V4 符合性声明。

> 当前实际浏览器观察见 [`V4-Web-浏览器表现基线.md`](V4-Web-浏览器表现基线.md)。该记录只承载当次实现依据与未验证范围，不是规则源。

## 1. 目标与边界

Web 可以整治内部结构、依赖、重复实现和测试，但本轮属于行为保持型工作。未经明确来源或 Human 决定，不得改变当前用户可以观察到的产品表现，包括：

1. 视觉、布局、颜色、字体、图标和信息层级；
2. 路由、导航、交互流程、文案和多语言表现；
3. API 的可观察请求与响应、页面数据展示及错误、空态和加载状态；
4. 当前响应式、键盘和已有可访问性行为。

允许改变的范围是 Web 内部实现，例如模块责任、重复代码、类型、数据读取层、组件边界和测试组织。重构若同时需要改变产品行为，必须把行为变化与结构变化分开规划、验证和决定，不能以“整治”为由一并实施。

本规划不授权恢复 V3 事实类型、字段、状态或写入契约。现有 Web 中相应实现只属于待审核的历史产品实践。

## 2. 当前实现与运行方式

当前 Web 是一个由 `web/package.json` 管理的 Node/TypeScript 工程：

```text
web/
  api/        Express API
  src/        React 页面与组件
  tests/      Web 自有测试
  docs/       既有产品实践与实现说明
  package.json
```

主要运行入口：

```bash
cd web
npm ci
npm run dev
```

开发服务器默认由 Vite 在 `127.0.0.1:5173` 提供前端，由 Express 在 `3001` 提供 API。构建、类型检查、lint 和当前测试分别使用：

```bash
npm run build
npm run check
npm run lint
npm test
```

`web/tests/` 只验证 Web；`code/tests/` 只验证 Code。仓库根目录不设置 `tests/`。未来统一执行入口可以依次调用两套测试，但不能改变资产归属或扩大任何一套测试的结论。

## 3. 当前可观察基线

### 3.1 页面与路由

当前前端公开路由为：

| 路由 | 页面 |
|---|---|
| `/` | Dashboard |
| `/project-files` | ProjectFiles |
| `/objects/:type` | ObjectList |
| `/objects/:type/:id` | ObjectDetail |
| `/changelog` | Changelog |
| `/changelog/:hash` | ChangelogDetail |
| 其它路径 | 重定向到 `/` |

现有 App Shell、对象卡片和详情、ReadingPanel、提交记录、ProjectFiles、复制语义、中英文界面及响应式实现的产品说明主要位于 `web/docs/01-全局设计约束.md` 至 `web/docs/10-Web开发现状与设计语言基线.md`。它们用于识别需要保持的现状，不因此成为 V4 事实或规则来源。

### 3.2 API

当前 Express 应用挂载：

- `/api/auth`
- `/api/dashboard`
- `/api/objects`
- `/api/changelog`
- `/api/docs`
- `/api/sparks`
- `/api/project-files`
- `/api/health`

所有 `/api` 响应设置 `Cache-Control: no-store`。认证入口仍返回未实现；Spark 写入仍在当前应用中挂载，但没有 V4 来源授权，不能据此声明 V4 写入能力可用。

## 4. 当前结构与依赖问题

以下问题来自当前源码和已有审核记录，作为实施输入，不是新的架构概念：

1. `ObjectDetail.tsx`、`ProjectFiles.tsx` 和 `ReadingPanel.tsx` 体量较大，多个页面同时承担数据转换、领域判断和呈现；拆分前必须先用特征测试固定可观察行为；
2. Web API 和前端直接硬编码 V3 事实类型、字段、状态和目录，必须等待相应 V4 来源成立后逐项适配，不能由重构自行定义；
3. `facts.ts` 和 Dashboard 会在部分读取或解析失败时返回空集合或零计数，可能掩盖遗漏范围；
4. Docs 和 ProjectFiles 的路径检查存在真实路径、符号链接和允许目录边界风险；在修复前不得扩大部署范围或声称读取边界已经安全；
5. Spark 写入由 Web 自行定义字段、初始状态和路径，并且写后验证失败可能留下文件；在 V4 来源和 Code 受控能力成立前不能作为 V4 写入能力；
6. 当前小屏隐藏 Sidebar，但没有经过真实测试确认的等价主导航；既有设计资料对此也不完全一致；
7. 当前 lint 有既存错误，生产 bundle 有体积警告；两者需要在不改变产品行为的独立增量中处理。

## 5. 测试策略

测试按风险和可观察边界逐步补齐：

| 范围 | 首要目的 | 当前安排 |
|---|---|---|
| API 特征与契约 | 固定现有公开状态码、响应结构、只读文件浏览和 Git DTO | 首批放入 `web/tests/api/`，使用临时目录和真实本地 HTTP 监听与请求 |
| 组件行为 | 固定复制、i18n、状态、空态和 ReadingPanel 交互 | 在组件拆分前补齐；当前未实现 |
| 页面与路由 | 固定路由、加载、错误、空态、页面身份和来源呈现 | 在页面重构前补齐；当前未实现 |
| 浏览器流程 | 固定代表性桌面/窄屏、键盘和跨页面流程 | 确认可重复运行环境后建立；当前未实现 |
| 视觉比较 | 辅助发现布局、样式和图标意外变化 | 只作为人工/自动比较证据之一，不把截图工具或单张图片当产品契约 |

测试夹具必须是满足当前测试所需的最小临时数据，不复制完整项目，不成为事实或 Schema 来源。只用 mock 的测试不能证明真实文件系统、Git、独立进程或浏览器组合；当前首批 API 测试使用临时 Git 仓库、真实 Express 监听端口和实际 HTTP 请求，但没有验证独立 server process。

从 V3 归档恢复测试时必须逐项审核。依赖当前仓库已不存在的 `ldvh-base/` 数据、反向固定 V3 领域契约，或者会把当前未获授权写入固化为 V4 正常行为的测试，不直接恢复。

## 6. 分批实施顺序

1. **恢复可执行测试入口**：将仍有效的 API 特征测试放入 `web/tests/`，修正 npm 和内部实现文档中的旧根级测试路径；不修改产品源码。
2. **建立页面表现基线**：选择代表性桌面与窄屏视口，记录路由、页面身份、关键交互、错误/空态、复制、i18n 和键盘行为；只记录可重复观察范围。
3. **修复高风险读取边界**：先为路径穿越、符号链接、部分读取和遗漏报告建立失败测试，再修改 Docs、ProjectFiles 和事实读取；保持已确认页面表现不变。
4. **隔离未获 V4 授权的写入**：在具体来源与 Code 能力成立前，规划 Spark 写入的隔离方式及其对当前产品表现的影响；涉及可见入口变化时进入 Human 决定，不能在普通重构中隐式处理。
5. **按模块逐批重构**：从纯转换和重复呈现开始，再处理数据读取层、API 路由、页面和大组件。每批只处理清楚的责任范围，并运行对应特征与回归测试。
6. **补齐支持范围证据**：对实际声明支持的语言、视口、键盘和辅助技术范围完成测试，未覆盖部分继续明确为未验证。

每个增量开始前必须更新本规划中的目标、影响范围、模块责任、依赖、风险和测试映射；完成后记录实际结果与未验证范围。不得在实现完成后才反向补写计划。

## 7. 首批测试增量的完成边界

首批只解决测试位置和最小可执行基础，完成条件为：

1. `web/tests/api/` 中的测试可以从 `web/package.json` 稳定执行；
2. 不再引用根级 `tests/web/`；
3. 类型检查、构建和首批 API tests 的结果可回指；
4. 没有修改 `web/src/`、`web/api/`、视觉资产、路由或产品行为；
5. lint 的既存失败、页面/组件/视觉/响应式/可访问性缺口继续明确记录，不冒充已解决；
6. V3 领域读取和 Spark 写入测试没有因“恢复测试”被错误授予 V4 契约身份。

完成这一增量只表示 Web 测试基础开始恢复，不表示当前 Web 已完成 V4 适配、产品表现已被完整锁定或 Web 可以部署。
