## 1. 本文解决的问题

本文解决 LDVH 中 Code 如何被提出、实现、验证、修改和维护的问题。

00 定义 Code 是五类构成要素之一，用于承担确定性执行、校验、上下文压缩、受控写入和稳定反馈。本文只围绕这个定义展开。Code 工具、脚本、校验器、测试程序、格式化命令、构建命令和受控写入入口，都是 Code 的具体实现形态，不与 Code 并列成为新的构成要素。

本文使用的 Code、Code 工具、脚本、校验器和命令入口等术语，按 `specs/02-术语规范.md` 定义。本文只规定 Code 实现的准入、验证和维护规则。

当 AI 在规范创建、文档检查、事实源维护或执行验证中发现“有一个确定性实现会更可靠、更省上下文或更容易验证”时，应先按 `specs/04.03-环境入口适配与部署规范.md` 判断 Code 工具缺口，再按本文判断是否形成 Code 需求，并完成最小实现、测试验证和后续维护。

## 2. 与 00 总纲的关系

00 定义 Code 的上位职责：

1. 查询、读取、索引和聚合事实源；
2. 生成 AI 可行动的最小上下文；
3. 校验事实源、规范、引用、状态和执行结果；
4. 提供受控写入入口；
5. 通过测试、校验、格式化、构建等确定性操作给出稳定反馈。

本文承接这些职责，定义 Code 实现从需求到验证的治理规则。

事实源查询是 Code 的稳定职责之一。Code 应逐步承接规范索引、20-39 工作模型派生集合索引、40-59 工作流程派生集合索引、工作对象列表与详情、关键词搜索、状态统计、对象关系、规范落地要求聚合、环境能力清单检查、后续重新设计的落地检查过程输出检查和管辖项目配置查询等只读能力，帮助 AI 先定位事实源，再读取最小必要原文。Code 承担这些能力的目的，是减少 AI 在重复读取、机械校验和上下文整理上的负担，不是替代 AI 对语义、上下文、规范权衡、风险和执行路径的综合判断。Code 承担这些能力不意味着 Web 必须复用 Code 实现；Web 可以基于同一 Git 文件事实源和同一 specs 契约，为 Human-facing 场景独立实现读取、解析、聚合、缓存、API 和展示逻辑。

本文不替代工作模型、工作流程、Web 或环境适配项。Code 可以满足这些规范提出的确定性执行要求，但 Code 本身不成为最终事实源，也不替代 AI 的综合判断、规范判断或 Human Gate。Code 与 Web 之间不是强制上下游关系；二者的共同约束是同源事实、同源规范、同源对象契约和可追溯验证。

## 3. Code 实现边界

Code 实现可以：

1. 查询、读取、解析、索引和聚合 Git 文件事实源；
2. 生成 AI 可行动的最小上下文或诊断结果；
3. 校验文档结构、引用、字段、状态、契约、测试结果或执行结果；
4. 执行测试、格式化、构建或其他确定性反馈操作；
5. 在规范授权和 Human Gate 满足后执行受控写入；
6. 为入口可见要求、流程复用要求、子 Agent 思考要求、Human 交互要求或其他规范落地要求提供确定性数据或校验结果。

事实源查询类 Code 默认只读。其输出属于派生视图、导航结果、聚合摘要或诊断信息，不得替代 Git 文件事实源。涉及创建、修改、关闭、删除、状态流转或高影响写入时，必须进入受控写入规则、对应工作模型或工作流程，并按需触发 Human Gate。

Code 实现不得：

1. 替代规范正文、工作对象、docs 正文或 Git 文件事实源；
2. 将输出、缓存、派生索引、测试结果或运行时状态提升为最终事实源；
3. 替代 AI 对语义理解、上下文综合、规范权衡、风险识别或执行路径选择的核心判断；
4. 直接调用 AI、Skill 或 Agent 来生成确定性结论；
5. 绕过 Human Gate 自动写入、授权、验收或关闭任务；
6. 用语义推断、LLM 摘要、向量相似度或聊天记忆替代确定性校验；
7. 通过实现细节反向改写规范规则。

### 3.1 过程输出实现边界

Code 可以实现工作流程过程输出的结构化生成、格式校验、来源聚合、诊断分类、证据索引、导出和受控写入前检查，但过程输出实现只承担确定性辅助职责，不得成为工作流程结论、对象状态、验证结果或 Human Gate 记录的权威来源。

过程输出相关 Code 应满足：

1. 输入必须来自 Git 文件事实源、明确的命令输出、测试结果、Human 输入或工作流程当前上下文，不得依赖聊天记忆作为唯一输入；
2. 输出应标明过程输出性质、来源路径、命令或验证依据，以及是否已回写事实源；
3. 输出格式可以服务 AI 阅读、Web 展示或后续工具消费，但不得要求下游把该输出解释为稳定事实；
4. 检查摘要、候选草案、风险提示、下一步建议和临时诊断只能作为过程输出，形成稳定事实后必须交由对应工作模型、工作流程或受控写入链路回写；
5. 受控写入类实现必须区分“生成候选过程输出”和“写入权威事实源”，并在写入前检查授权、Human Gate、目标位置和写入后验证；
6. 无法定位来源、无法验证、无法回写或只能给出候选结论时，输出必须显式返回降级状态、残留风险和建议分流位置。

Code 不得通过过程输出实现绕过 06 §6.8.1 的主控交还、09 的事实源边界或 08 的 Web 展示边界；工作流程测试机制是否存在 active 入口，应查询 40-59 成员主文件自描述和 Code 派生工作流程集合索引，不作为 Code 的隐含前置约束。

### 3.2 成员集合派生索引边界

Code 可以依据 `specs/01-目录说明.md` 的编号分区、`specs/03.03-工作模型文档规范.md` 的工作模型成员自描述契约、`specs/03.04-工作流程文档规范.md` 的工作流程成员自描述契约、05 / 06 基础规则和 09 事实源边界，生成工作模型和工作流程派生集合索引。

成员集合派生索引应满足：

1. 输入来自 20-39 / 40-59 成员主文件、明确命令输出和测试结果，不从聊天记忆推断成员状态；
2. 输出必须回指成员主文件路径、成员自描述字段、章节锚点和诊断依据；
3. 输出可以列出成员清单、collection_status 分布、active 清单、编号冲突、缺失锚点、非法状态、重复路径和建议读取位置；
4. 输出只作为派生视图、导航结果和诊断结果，不替代成员主文件或正式规范；
5. 发现编号冲突、状态非法、active 成员缺失必需锚点或成员自描述与文件名不一致时，应返回明确失败或 degraded 诊断，不得静默生成可执行清单；
6. 删除、重命名、重排编号或改变成员状态仍属于规范结构变更，必须按对应规范和 Human Gate 执行，Code 不生成授权。

## 4. Code 需求准入

AI 认为需要新增或扩展 Code 实现时，应先判断 Code 需求是否成立。

Code 需求成立前，应先满足文档先行纪律：需求来源、规则、输入输出、失败条件、验证要求或执行计划必须已经由正式规范、工作对象或其它对应 Git 文件事实源承载。未进入文档或事实源的聊天判断、实现想法或临时页面状态不能直接触发 Code 实现。

Code 需求成立条件至少包括一项：

1. 规范已经要求某项确定性检查、验证、聚合、上下文生成或受控写入；
2. 同类人工检查会重复出现，且存在明确可机械化规则；
3. 现有实现不适配当前文档工作区、事实源结构或规则版本；
4. 关键结论需要可复现验证，不能只依赖 AI 自述；
5. Code 能明显降低上下文消耗、误读风险或维护成本；
6. 入口可见要求、流程复用要求、子 Agent 思考要求、Human 交互要求或工作流程需要稳定消费同一确定性结果。

Code 需求不成立的情况：

1. 只是一次性阅读、解释或判断，无法形成稳定输入输出；
2. 规则本身尚未稳定，实现会先于规范制造事实源；
3. 需要 AI 语义判断才能得出核心结论；
4. 没有明确失败条件，无法验证实现是否正确；
5. 只服务未来假想场景，不服务当前可运行闭环。

Code 需求记录至少包含：

| 项目 | 要求 |
|---|---|
| 需求来源 | 来源规范、章节、任务或当前检查缺口 |
| Code 能力 | 事实源查询、读取、索引、聚合、上下文生成、校验、受控写入或稳定反馈 |
| 输入范围 | 文件、目录、事实源类型、参数和默认值 |
| 规则来源 | 需要机械化的规则、成功条件和失败条件 |
| 输出形式 | 文本、结构化诊断、exit code、产物或写入结果 |
| 写入行为 | 是否写入；若写入，说明目标、授权、Human Gate 和验证 |
| 验证方式 | 正例、反例、边界样例、测试命令或等价验证方式 |
| 降级方式 | 实现不可用时暂停、人工检查或残留风险记录 |

若 Code 需求用于生成或检查过程输出，需求记录还应说明过程输出类型、消费方、来源追溯方式、事实源回写触发条件、Web 展示需求和验证证据归属。

## 5. Code 实现规则

新增或扩展 Code 实现时，应优先实现覆盖当前需求的最小确定性能力，不得因为发现更大体系缺口而扩张为通用环境。

Code 实现应满足：

1. 实现入口、调用方式和依赖清晰；
2. 输入路径、参数边界和默认行为明确；
3. 输出可被 AI、人或后续实现稳定读取；
4. 成功条件和失败条件可被测试复现；
5. 写入类实现默认禁止隐式写入，必须显式声明写入目标、授权条件和写入后验证；
6. 实现内部不得硬编码未生效候选事项或参考与研究材料作为权威来源；
7. 输入缺失、环境不可用或校验规则不稳定时，应返回清晰错误，不得静默通过。

Code 可以通过 Code 工具、脚本、校验器、测试程序、格式化命令、构建命令、后端服务或其他确定性程序实现。具体形态应由当前需求、项目技术栈和维护成本决定，不因当前 LDVH 有 Python 辅助程序而把 Python 工具写成唯一实现方式。

Code 实现和测试内容的目录边界如下：

1. `code/` 承载 LDVH 提供的 Code 参考实现，例如校验器、脚本、上下文生成、受控写入和其他确定性实现；用户可根据本文约束自行实现 Code，不强制使用 `code/` 下的实现；
2. `code/docs/` 承载 LDVH 当前 Code 参考实现的结构、命令、模块拆分、测试映射和执行细则；该目录不承载 LDVH 稳定规范规则，不替代本文或 `specs/10-测试基础规范.md`；
3. 根目录 `tests/` 是测试集合目录，只承载按构成要素分区的测试子目录，不直接放置测试文件；测试治理、验证声明和事实源边界由 `specs/10-测试基础规范.md` 承载；
4. Code 工具、脚本、校验器、受控写入和其它确定性实现的测试应放在 `tests/code/` 下；
5. Web 信息同步、Web API、Web 组件、Web 页面和 Human-facing 交互的测试应放在 `tests/web/` 下，由 `specs/08-Web信息同步实现规范.md` 和 `specs/10-测试基础规范.md` 承载上层要求；
6. 不在 `code/` 中放测试内容，也不在 `web/` 中放 LDVH 规范要求的长期测试入口；实现框架生成的临时缓存、覆盖率、截图和构建产物不得进入测试事实源；
7. 测试文件命名应表达被验证的构成要素、入口或规则，例如 `tests/code/test_specs_validate.py`。

若既有实现只需小范围扩展，应优先扩展并测试既有实现；若既有实现的目录假设、规则假设或事实源边界与当前需求冲突，应视为 Code 缺口，不能直接沿用其通过结果。

LDVH 自身 `code/` 参考实现可通过 `code/docs/` 维护更具体的结构约束和迁移计划。此类文档只约束当前参考实现的执行细节；若某项内容具有跨实现、跨项目或长期规范效力，应回写本文或对应 specs 正文。

## 6. Code 验证规则

新增 Code 实现必须同步提供测试或等价验证。修改输入、输出、错误码、写入行为、字段消费、目录假设、章节规则、引用规则、状态规则或校验规则时，必须同步更新验证方式。Code 验证声明、测试实现归属、测试证据事实源边界和无法自动化时的等价验证应同时遵守 `specs/10-测试基础规范.md`。

LDVH 不强制所有 Code 工作采用经典 TDD 流程，即不要求所有场景都必须先写自动化测试代码再写实现；但 LDVH 强制文档约束先行、测试先行和实现后行。AI 在新增、扩展或修改 Code 前，应先确认正式文档或事实源已经承载规则来源、成功条件、失败条件和执行计划，再根据文档补齐正例、反例、边界样例、测试命令或等价验证方式，最后进行最小实现。

测试先行的要求如下：

1. 能用自动化测试表达的 Code 行为，应先补测试，再修改实现；
2. 修复已知 bug 时，应先补能复现失败的测试，再修改实现；
3. 目录迁移、路径规则、输入输出、错误码、受控写入和状态流转变化，应先补正反样例、测试或等价验证，再修改实现；
4. 规则尚未稳定、失败条件不明确或只能依赖 AI 语义判断时，不得为了满足测试形式而先制造测试事实源；
5. 无法先写自动化测试时，应先说明原因、采用的等价验证方式和残留风险，再修改实现；
6. 只有验证方式、关键输出和残留风险可复现时，才能把 Code 变更表述为已验证。

验证至少覆盖：

1. 基础调用或帮助信息；
2. 参数错误、路径不存在或输入缺失；
3. 应通过样例；
4. 应失败样例；
5. 输出结构、诊断信息和 exit code；
6. 边界样例；
7. 写入类实现的写入前阻断和写入后验证。

测试夹具应最小化，只服务 Code 行为验证，不得演化为第二事实源。测试缓存和测试结果不得替代 Git 文件事实源。

当前任务无法建立完整测试时，AI 必须说明原因、采用的等价验证方式和残留风险。该情况不得被表述为 Code 已完整验证。

## 7. Code 修改、维护和删除

以下变化会触发 Code 同步检查：

1. 文档工作区、目录结构、文件命名或引用规则变化；
2. 字段契约、状态机、对象关系或事实源边界变化；
3. Human Gate、受控写入或验证要求变化；
4. 规范落地要求、环境适配项或运行入口变化；
5. 入口可见要求、流程复用要求、子 Agent 思考要求、Human 交互要求或其他 Code 实现开始消费输出；
6. 输出格式、错误码、诊断格式或写入产物变化。

修改 Code 实现时，应同步检查：

1. 实现是否仍匹配规范来源；
2. 测试或等价验证是否覆盖变更前后的关键行为；
3. 下游调用方是否需要同步；
4. Code 文档或使用说明是否需要同步；
5. 规范落地要求和环境适配项是否需要更新。

删除 Code 实现前，应确认：

1. 没有规范、工作流程、入口可见要求、流程复用要求、子 Agent 思考要求、Human 交互要求或其他 Code 实现继续调用；
2. 没有测试或文档继续引用；
3. 替代实现或降级方式已明确；
4. 删除不会让规范要求的检查、验证、上下文生成或受控写入失去可执行入口；
5. 影响高价值检查、受控写入或 Human Gate 时已触发 Human Gate。

## 8. Code 文档边界

Code 可以拥有代码文档或使用说明，用于说明命令、参数、示例、维护方式、故障排查、测试夹具、依赖、已知限制、参考实现结构和模块拆分计划。

LDVH 当前 `code/` 参考实现的结构、命令入口、模块拆分、测试映射和 AI 修改顺序由 `code/docs/` 承载；其中 `code/docs/01-Code参考实现结构规范.md` 是当前 Code 参考实现结构治理入口。AI 修改 `code/` 前，应先读取本文，再读取 `code/docs/` 中与当前实现相关的细则。

Code 文档不得承载：

1. LDVH 稳定规范规则；
2. 工作对象字段契约；
3. 状态机权威定义；
4. Human Gate 权威条件；
5. 事实源最终结论；
6. 与 specs 正文冲突的行为定义。

当 Code 文档中的内容具有长期规范效力时，应回写 specs 正文；当它形成任务、决策、变更或经验时，应回写对应工作对象。

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变本文定义的 Code 职责分工；
2. 改变 Code 实现、测试或 Code 文档的事实源性质；
3. Code 写入或覆盖 Git 文件事实源；
4. Code 改变事实源归属；
5. Code 将派生数据、缓存、运行时索引或测试结果提升为稳定事实；
6. Code 绕过工作流程、对象状态机、受控写入规则或 Human Gate；
7. 删除被规范、入口可见要求、流程复用要求、子 Agent 思考要求、Human 交互要求或其他 Code 实现消费的实现；
8. 扩大 Code 判定范围并影响规范结论、吸收结论、任务关闭或验收判断。

Code 检查至少包括：

| 检查项 | 标准 |
|---|---|
| 需求准入 | Code 需求有明确能力归属、规则来源、输入输出、失败条件和降级方式 |
| 可验证先行 | Code 变更前已明确成功条件、失败条件、正反样例、边界样例、测试命令或等价验证方式 |
| 最小实现 | Code 只覆盖当前稳定需求，未扩张为未来假想环境 |
| 事实源边界 | Code 输出、缓存、索引和测试结果未替代 Git 文件事实源 |
| 验证证据 | 新增或修改 Code 已提供正反样例测试或等价验证 |
| 写入边界 | 写入类 Code 有明确授权、Human Gate 和写入后验证 |
| 维护联动 | 规格变更已同步检查实现、验证方式、文档和下游调用方 |
| AI 协作边界 | Code 未直接调用 AI、Skill 或 Agent 生成确定性结论 |
| 过程输出边界 | 过程输出实现已标明临时性质、来源、回写状态、降级风险和下游消费边界 |
