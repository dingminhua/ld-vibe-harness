> 创建日期：2026-05-28
> 对象名：Change / 变更记录
> 适用范围：所有接入 PM Kit 且需要记录变更的项目
> 上位依据：`specs-v2/00-PMKit理念与纲要.md`、`specs-v2/14-管理对象规范.md`、`specs-v2/10-事实源规范.md`、`specs-v2/11-AI协作规范.md`、`specs-v2/12-程序辅助规范.md`、`specs-v2/13-工具展示规范.md`

## 一、对象定位与准入

### 1.1 对象定义

Change 是对 Artifact、Rules、Task、Requirement、ADR、配置或事实源边界产生影响的实际修改的结构化记录。

Change 的关键特征：

1. **无状态机**——记录即终态，写入后不再变更；
2. **无准入条件**——每次修改都应记录，不需要判断是否"重要"或"值得"；
3. **写多读少**——AI 每次变更后写入，但正常工作流中极少读取；
4. **主要消费者是追溯和审计**——不是 AI 执行前匹配的对象。

### 1.2 与临时判断的区别

| 维度 | 临时判断 | Change |
|---|---|---|
| 性质 | 执行过程中的局部选择 | 实际发生的结构化修改记录 |
| 持续时间 | 一次性 | 长期可追溯 |
| 复用价值 | 无 | 追溯和审计价值 |
| 追踪需求 | 不需要独立追踪 | 需要独立记录、不可修改、不可删除 |

### 1.3 准入条件

Change 无准入条件。每次对项目事实源的修改都应创建 Change 记录，不需要判断修改是否"重要"或"值得"。

### 1.4 Change 不应被误用为

1. 任务追踪——应使用 Task；
2. 决策记录——应使用 ADR；
3. 问题管理——应使用 Task、Risk 或 Memo；
4. 踩坑经验——应使用 Pitfall；
5. 未任务化输入——应使用 Memo。

## 三、生命周期

Change 无状态机。Change 的生命周期为记录即终态：写入后不再变更。

### 3.1 生命周期特征

1. **记录即终态**——Change 写入后不再变更，不存在状态流转；
2. **不可修改**——Change 是记录类事实源，写入后不得更新、补充或删除。如果变更记录有误，应新建 Change 说明更正，不得修改原 Change；
3. **不可删除**——Change 是历史记录，删除 Change 等同于消除历史。

### 3.2 写入规则

1. **每次修改都应创建 Change 记录**。AI 完成对项目事实源的修改后，必须创建 Change YAML 文件到 `pm-kit-base/changes/`；
2. **写入时机**：变更完成后立即写入，不得积压。一次逻辑变更记一条 Change；
3. **记录粒度**：
   - 同一原因、同一目标的多文件修改记一条 Change；
   - 不同原因的修改分开记录；
   - 跨项目影响写入 `impact` 字段，不拆成多条；
4. **不维护索引文件**：`pm-kit-base/changes/` 目录本身提供时间排序索引，不需要额外的 `changelog.md` 或索引文件；
5. **不依赖 git**：所有项目均可产生 Change 记录，无论是否配置 git。已配置 git 的项目，commit message 与 Change 互补但不替代。

## 四、字段契约

### 4.1 基础字段

Change 的基础字段对齐 10 §12.2，包括：`id`、`type`、`title`、`status`、`created`、`updated`。

其中 `status` 对 Change 而言为固定值（记录即终态），`type` 为 `change`。

### 4.2 Change 扩展字段

Change 扩展字段对齐 10 §12.3，字段名称与简要说明如下：

| 字段 | 必须 | 简要说明 |
|---|---|---|
| `date` | 是 | 变更日期，格式 YYYY-MM-DD |
| `changes` | 是 | 变更内容 |
| `reason` | 是 | 变更原因 |
| `impact` | 是 | 影响范围 |
| `validation` | 是 | 验证方式，不可省略，无具体验证内容时标记为 `—` |
| `project` | 否 | 项目标识 |
| `tags` | 否 | 标签列表 |

字段约束详见 10 §12.3，本文档不重复定义。

### 4.3 文件命名

文件命名对齐 10 §12.3：`pm-kit-base/changes/{YYYYMMDDHHmmss}.yaml`。

- 时间戳精确到秒级，固定 14 位；
- `id` 与文件名中的时间戳一致，格式 `CHG-{YYYYMMDDHHmmss}`；
- 每个项目独立时间戳，不使用跨项目全局编号。

## 五、与其他对象的关系

### 5.1 Change 与 Task

- 一个 Task 的执行可以产生多个 Change；
- Change 的 `reason` 字段可引用 Task ID，说明变更来源；
- Change 不替代 Task 的关闭证据或验收记录；
- Task 回答需要做什么，Change 回答实际改了什么。

### 5.2 Change 与 ADR

- Change 的 `reason` 字段可引用 ADR ID，说明变更的决策依据；
- ADR 不替代 Change 的变更内容记录；
- 当 ADR 的决策需要具体执行时，执行过程产生的修改应记录为 Change；
- ADR 回答为什么这样决定，Change 回答实际改了什么。

### 5.3 Change 与 Pitfall

- Change 记录实际修改，Pitfall 记录可复用的踩坑经验；
- 如果一次变更过程中发现了可复用的踩坑经验，应同时创建 Change 和 Pitfall，两者通过 ID 互相引用；
- Change 不替代 Pitfall 的规避方式记录。

### 5.4 Change 与 Memo

- Change 记录实际修改，Memo 记录未任务化但有保留价值的输入；
- Change 不替代 Memo 的输入保留功能；
- 如果变更过程中产生了需要保留但暂不任务化的发现，应同时创建 Change 和 Memo。

### 5.5 Change 与 Evidence

- Change 回答实际改了什么，Evidence 回答如何证明某项工作满足要求；
- Change 的 `validation` 字段记录变更的验证方式，不等同于 Task 关闭证据；
- Task 关闭证据由 Evidence 或 Task 的关闭字段承载。

### 5.6 Change 与 commit message

- 已配置 git 的项目，commit message 仍然记录代码级变更；
- Change 记录的是面向项目事实源的变更摘要，与 commit message 互补但不替代；
- Change 不依赖 git。未配置 git 的项目同样产生 Change 记录。

1. 识别项目中是否已有 Change 事实源（`pm-kit-base/changes/`）；
2. 识别现有 Change 记录是否具备变更内容、原因、影响范围和验证方式；

4. 判断是否需要生成 Change 规范缺口、迁移建议或 Human Gate 提示。

## 八、AI 协作适配

本节声明 Change 对象如何适配 AI 协作层（11），不重新定义 11 的规则。

### 8.1 AI 读取 Change

1. AI 通常不在每次执行前默认读取 Change 事实源；
2. AI 在追溯、审计、发布记录和工具聚合场景下读取 Change；
3. AI 读取 Change 时应从 `pm-kit-base/changes/` 目录读取，不得从缓存或派生视图读取。

### 8.2 AI 写入 Change

1. AI 完成对项目事实源的修改后，必须创建 Change YAML 文件到 `pm-kit-base/changes/`；
2. AI 不得修改已写入的 Change 记录；
3. AI 不得删除 Change 记录；
4. AI 写入 Change 时必须包含所有必填字段。

### 8.3 AI 与 Change 的协作边界

1. Change 不是 AI 执行前匹配的对象，AI 不应在每次执行前遍历 Change 目录；
2. Skill 可在完成变更后自动创建 Change 记录，但必须包含所有必填字段；
3. Agent 可围绕 Change 进行追溯或审计分析，但不得修改已写入的 Change；
4. AI 不得将 Change 误用为任务追踪、决策记录或问题管理。

## 九、Human Gate

以下 Change 相关操作应触发或评估 Human Gate：

1. 执行难以回滚的 Change；
2. 执行跨项目的 Change；
3. 执行影响事实源边界的 Change；
4. 删除 Change 记录。

Human Gate 的完整定义和执行规则见 11 §十二。

## 十、程序辅助适配

本节声明 Change 对象如何适配程序辅助层（12），不重新定义 12 的规则。

### 10.1 程序解析 Change

1. 程序可解析 `pm-kit-base/changes/` 目录下的 YAML 文件；
2. 程序解析依赖 10 §12.3 定义的格式契约，不得自行定义或扩张格式契约。

### 10.2 程序校验 Change

1. 程序可校验 Change 的必填字段完整性、id 格式合规性和文件命名合规性；
2. 程序可校验 Change 写入后未被修改或删除；
3. 校验失败不得导致程序自动修改事实源，应报告给 AI 或人。

### 10.3 程序聚合 Change

1. 程序可聚合 Change 记录生成时间线、影响范围和聚合视图；
2. 聚合输出属于派生视图数据，不是事实源；
3. 聚合输出必须能追溯到 Git 文件事实源。

### 10.4 程序受控写入 Change

1. 程序可提供受控写入入口，按授权写入 Change YAML 文件；
2. 写入前必须校验必填字段完整性和格式合规性，拒绝缺失必填字段的写入；
3. 写入后必须记录变更，写入不得只停留在程序内部存储。

## 十一、工具展示适配

本节声明 Change 对象如何适配工具展示层（13），不重新定义 13 的规则。

### 11.1 工具展示 Change

1. PM Web Tools 可展示 Change 时间线、影响范围和聚合视图；
2. 工具展示必须从 Git 文件事实源读取，不得维护第二套 Change 事实源；
3. 工具展示与事实源不一致时，以 Git 文件事实源为准。

### 11.2 工具与 Change 的边界

1. 工具不得维护与 Git 文件不一致的 Change 权威状态；
2. 工具不得允许通过 UI 修改或删除已写入的 Change 记录；
3. 工具写入 Change 时必须通过受控写入入口，遵守 12 的受控写入原则。
