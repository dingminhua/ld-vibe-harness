## 一、本文解决的问题

本文解决的问题是：AI 协作中什么必须做、禁止做、允许做；Rule、Skill、Agent、多角色讨论的行为边界和概念边界是什么；L0/L1/L2 规则如何分层和读取；Rule/Skill/Agent/多角色讨论的设计模板、检查项和变更流程是什么；标准技能目录和推荐 Agent 清单包含什么；什么场景必须触发 Human Gate；任务状态变更与证据回写的约束是什么；规则冲突时以哪个文档为准。

本文约束对象为 AI 执行者、人类确认者和工具受控写入行为。AI 是第一约束对象，人是第二约束对象，工具是第三约束对象。

## 二、与 00 总纲的关系

00 定义 PM Kit 的核心理念和事实源原则，本文将核心理念转化为 AI 协作的具体行为规则。

00 声明以下原则，本文负责实践：

1. 人主 AI 辅：人类决策，AI 执行；
2. 事实源优先：AI 的所有判断和操作必须基于项目事实源，不得凭惯例推断；
3. 单一事实源：同一规则或约束只在一个权威位置维护。

00 提出的核心问题：

```text
AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。
```

本文直接回答"不能做什么"和"何时停下等待人确认"，并通过 Rule 分层和 L0/L1/L2 读取机制回答"该读什么"，通过证据回写规则回答"完成后如何把事实写回项目"。

## 四、AI 协作总原则

1. **人主 AI 辅**：人类决策，AI 执行。AI 不得绕过人类确认修改规则、Skill、Agent、product.yaml、跨项目契约或长期治理方式。
2. **事实源优先**：AI 的所有判断和操作必须基于项目事实源（docs/、pm-kit-base/、Rules），不得凭惯例推断。
3. **Human Gate 不可绕过**：Human Gate 是 AI 行为约束，不是平台自动保证。AI 检测到 Human Gate 场景时必须暂停并等待用户确认。
4. **单一事实源**：同一规则或约束只在一个权威位置维护。其他文档只能引用、摘要或聚合，不得复制正文形成第二套事实源。
5. **规范与实践分离**：规则集中在基础规范层；模板、示例、流程和检查项放入实践文档。
6. **路径归属明确**：L0 规则和 Skill 描述中引用文档路径时，必须区分 PM Kit 项目路径与受管理项目路径。PM Kit 项目路径下是基础规范等只读引用源；受管理项目路径下是 pm-kit-base、.trae/rules 等读写目标。不得用"当前项目"等模糊表述掩盖路径归属差异。
7. **项目上下文优先**：会话开始时，AI 必须先识别用户工作目录所属项目，再读取对应 L1 规则。不得跳过项目上下文识别直接使用默认配置。
8. **工具不成为事实源**：Rule、Skill、Agent、MCP、Trae `.trae/specs/`、AGENTS.md 和 CLAUDE.md 都是执行机制、过程资产或兼容入口，只有经确认写入 PM Kit 正式事实源后，相关内容才成为项目事实。
9. **最小可行动上下文**：AI 每次行动前应获得足够但不过载的最小可行动上下文，不假设每次都能一次性正确执行。

## 五、Rule 规则

### 5.1 Rule 定义

Rule 是 AI 和人执行项目工作时必须遵守的稳定约束。Rule 可以存在于 PM Kit specs 规范、工作区规则、项目规则和场景规则中。

### 5.2 规则分层架构

PM Kit specs 是工作区内所有项目的规范体系，定义通用 AI 协作规则、管理对象规则、文档治理规则、实践规范和工具规范。

在此基础上，通过三层通道规则逐级落地：

```text
规范层：PM Kit specs-v2（所有项目继承）
  ├─ 00 PMKit 理念与纲要
  ├─ 10-14 基础规范层
  ├─ 20-49 管理对象实践
  └─ 50-89 场景实践与审计检查

通道层：L0 → L1 → L2
  L0：工作区桥接 —— 声明规范来源、管理项目叠加、L1 引导 L2
  L1：项目专属 —— 不重复规范层，只写本项目特有约束，引导 L2
  L2：场景规则 —— 特定文件类型、特定目录或特定场景约束

叠加层：管理项目规范（可选）
  └─ 多项目产品有独立治理项目时，产品级特色规范叠加在规范层之上
```

### 5.3 各层职责边界

| 层级 | 位置 | 职责 | 禁止 |
|---|---|---|---|
| 规范层 | PM Kit `specs-v2/` | 定义所有项目继承的通用规则 | 绑定具体业务产品 |
| L0 | 工作区根 `.trae/rules/workspace_rules.md` | 桥接规范来源、管理项目叠加、L1 引导 L2 | 展开规则正文或承载单项目约束 |
| L1 | 各项目 `.trae/rules/project_rules.md` | 项目定位、必读索引、项目专属硬约束、L2 引导 | 重复规范层或 L0 已定义内容 |
| L2 | `.trae/rules/*-rules.md` | 特定文件类型、目录或场景约束 | 替代或覆盖规范层 |
| 管理项目规范 | `{product}-product/docs/` | 产品级特色规范 | 与 PM Kit 规范层冲突 |

### 5.4 规则唯一事实源

| 规则性质 | 事实源 |
|---|---|
| 通用约束 | PM Kit specs-v2 |
| 工作区桥接 | L0 |
| 项目专属 | L1 |
| 场景约束 | L2 |

L1 不得重复 L0 或规范层已有内容。若发现重复，审计必须识别并修正。

### 5.5 L0/L1/L2 读取机制

读取某个项目目录下的文档或代码文件时，必须先识别项目上下文并读取对应规则：

1. **识别项目上下文**：从文件路径判断所属项目；检查是否已读取过该项目 L1，会话期间已读取过则跳过。
2. **读取规则**：先读取 L0 工作区规则，再读取 L1 项目规则。
3. **检查必读文档索引**：确认已阅读当前项目的核心文档。

L1 不存在时：若项目有 `docs/` 目录但无 L1 规则，提示用户"该项目尚未建立 L1 规则，建议补充"；继续读取项目核心文档；仅依赖工作区规则和规范层执行。

每个项目的 L1 在会话期间只需读取一次。L0 工作区规则在会话期间只需读取一次。

### 5.6 A/B 双轨归属

PM Kit 协作资产必须区分 A 轨和 B 轨：

| 轨道 | 定义 | 事实源 | 约束 |
|---|---|---|---|
| A 轨 | PM Kit 提供和维护的协作基础设施，包括规范层、L0/L1/L2 模板、PM Kit 标准 Skill 行为边界、Agent/MCP/Human Gate 语义 | `trae-pm-kit/specs-v2/` | 规定性，受管理项目不得复制或覆盖 |
| B 轨 | 受管理项目依据 PM Kit 建立的项目规则、项目 Skill、项目 Agent、项目 MCP 配置和过程资产 | 受管理项目 `docs/`、`pm-kit-base/`、`.trae/rules/` | 指导性，不得与 A 轨冲突 |

PM Kit Skill 属于 A 轨，统一部署在工作区顶层 `.trae/skills/pm-kit-*`。受管理项目业务 Skill 属于 B 轨，不得使用 `pm-kit-` 前缀，也不得复制 PM Kit Skill 的规范逻辑。

### 5.7 Rule 设计原则

1. 规则文件应短小、可检查、可引用。
2. L0 只做工作区桥接，不展开规范层正文。
3. L1 只写项目专属约束，不复制规范层或 L0。
4. L2 只补充特定场景约束，不替代规范层或 L1。
5. 新增 docs/ 文件时，相关项目 L1 的必读文档索引需要同步检查。
6. 规则变更执行前应先判断 Human Gate。
7. L0 中引用规范层文档时，路径必须包含 PM Kit 项目目录前缀，不得使用裸相对路径，避免多项目环境下路径歧义。
8. 编写代码前，应先查看当前项目的 `pm-kit-base/pitfalls/`，了解已记录的反直觉问题和规避策略。
9. Rules 只放必须遵守、绝对禁止、事实源边界、质量门禁和 Skill / Agent 调用入口，不放大段教程、完整架构说明、完整 SOP 或可按需加载的低频知识。

### 5.8 兼容入口边界

AGENTS.md / CLAUDE.md 可作为跨工具规则入口或迁移辅助入口，但必须遵守：

1. 只能引用 PM Kit specs、`.trae/rules/` 和受管理项目 L1，不得复制规则正文形成第二事实源。
2. 不得定义与 PM Kit 冲突的 Human Gate、Skill、Agent 或 MCP 调度规则。
3. 从兼容入口导入 Trae Rules 后，必须检查重复规则、过期引用和路径归属混淆。

## 六、Skill 规则

### 6.1 Skill 定义

Skill 是由 AI 在对话层调用的可复用流程入口，用于执行稳定的分析、整理、评估或轻量写入流程。Skill 不是事实源。

### 6.2 Skill 类型

| 类型 | 定义 | 触发方式 |
|---|---|---|
| 自动触发型 | AI 根据规则判断需要执行的可复用流程 | 规则条件满足时自动调用 |
| 人主动触发型 | 需要人类明确要求才执行的稳定流程 | 用户显式要求 |

### 6.3 Skill 行为边界

1. Skill 不得成为事实源，只能读取、整理、展示或按授权轻量写入目标项目事实源。
2. Skill 不得修改规则、Agent、product.yaml、跨项目契约或其他管理资产。
3. Skill 发现 Human Gate 场景时必须暂停并提示用户确认。
4. Skill 不得调度 Agent。复杂场景只能建议用户调用 SOLO Agent 进行多 Agent 分析。
5. Skill 创建、修改或删除必须触发 Human Gate。
6. PM Kit 提供或初始化生成的标准 Skill 必须使用 `pm-kit-` 前缀，并统一部署在工作区顶层 `.trae/skills/`，不得在受管理项目中生成副本。
7. Skill 只能读取 PM Kit specs 作为规范事实源，并按授权读取或写入受管理项目事实源；Skill 自身不得成为事实源。

### 6.4 Skill 与 Rule / Agent 的边界

| 场景 | 归属 |
|---|---|
| AI 可根据条件自动判断并执行 | Rule |
| 需要稳定流程且可在主上下文执行 | Skill |
| 需要独立上下文、结论隔离、并行委派或不同工具权限 | Agent |

### 6.5 Skill 适用判断原则

适合设计为 Skill 的流程：需要复用的多步骤分析流程；需要标准化输入和输出的整理流程；需要由用户显式触发的稳定写入流程；需要在主上下文内执行的轻量评估流程。

不适合设计为 Skill 的流程：单步骤、无分支的简单操作；Human Gate 判断本身；需要独立上下文、隔离执行、并行委派或不同工具权限的流程。

### 6.6 Skill 输出原则

Skill 输出应满足：明确输入来源；明确分析结论；明确建议动作；明确是否触发 Human Gate；明确哪些内容是事实、哪些内容是建议。

涉及写入的 Skill 应在输出中列出待写入文件、写入原因和影响范围。

### 6.7 需求增加识别与询问规则

AI 在对话中识别到需求增加时，必须主动询问用户是否需要整理为任务或备忘。

识别标准（满足任一即触发询问）：

- 对话中明确提出了新的功能需求、改进需求或修复需求
- 对话中确定了需要执行的新工作项
- 对话中产生了需要记录的新约束或新发现

不触发询问的场景：

- 试探性讨论、假设性分析、头脑风暴（未确定执行）
- 对已有需求的澄清、解释、确认（未增加新内容）
- 纯信息查询或知识问答

## 七、Agent 规则

### 7.1 Agent 定义

Agent 是具备独立上下文的执行实体，用于专业角色隔离分析、并行委派或需要不同工具权限的高级可选能力。Agent 不是轻量分析框架，也不是 PM Kit 默认协作机制。PM Kit 不默认内置项目业务 Agent，也不要求受管理项目创建 Agent。

### 7.2 Agent 创建或调用门槛

满足以下条件之一时，才可创建或调用 Agent：

1. 需要独立上下文读取大量事实源。
2. 需要结论隔离。
3. 需要并行委派多个专业角色。
4. 需要不同工具权限。

主上下文多角色讨论优先。只有当主上下文无法满足独立上下文、结论隔离、并行委派或工具权限差异时，才升级为 Agent。

### 7.3 Agent 调度规则

Agent 不得自行触发或由普通 AI 自动触发。Agent 只能通过以下方式调度：

1. **用户显式要求**：用户直接 @ 某个 Agent 或要求调用某 Agent。
2. **SOLO Agent 主控编排**：SOLO Agent 作为主控智能体，根据任务复杂度调用已配置的子 Agent。子 Agent 被动响应，不自主判断是否参与。

Skill 不得调度 Agent。Skill 认为需要独立上下文、隔离执行或并行委派时，只能提示用户建议调用 SOLO Agent。

### 7.4 Agent 创建与修改规则

1. 创建、修改或删除 Agent 必须触发 Human Gate。
2. 未经用户确认，不得创建、修改或删除 Agent。
3. 修改 Agent 职责边界、调度方式、工具权限或触发条件，必须触发 Human Gate。
4. Agent 定义文件和平台 Agent Prompt 必须保持一致。
5. Agent Prompt 不得复制 PM Kit specs、受管理项目事实源或 Agent 定义全文，只能作为角色入口、执行约束、事实源引用和输出格式说明。

### 7.5 Agent 与事实源的关系

1. Agent 输出不是事实源，稳定事实必须回写 Git 文件事实源。
2. Agent 默认只读分析，除非主控明确授权写入。
3. Agent 发现 Human Gate 场景时必须标注并停止修改。
4. Agent 不得自行修改规则、Skill、Agent、product.yaml 或跨项目契约。

## 八、多角色讨论规则

### 8.1 多角色讨论定义

多角色讨论是在主上下文内进行的分析框架，通过切换角色视角完成结构化评估。它不是 Agent，也不具备独立上下文。

### 8.2 多角色讨论与 Agent 的边界

| 维度 | 多角色讨论 | Agent |
|---|---|---|
| 本质 | 分析框架 / 方法论 | 执行实体 / 技术组件 |
| 上下文 | 共享主上下文 | 独立上下文 |
| 执行 | 顺序分析，角色视角切换 | 并行 / 隔离执行 |
| 成本 | 低 | 高 |
| 触发 | Skill 或主上下文轻量模式 | 用户显式要求或 SOLO Agent 主控编排 |
| 产出 | 结构化对比报告 | 独立结论 + 汇总报告 |

### 8.3 升级规则

先尝试多角色讨论。只有当独立上下文、结论隔离、并行委派、大量事实源读取或工具权限差异成为必要条件时，才建议升级为 Agent。

升级 Agent 必须经用户确认，由 SOLO Agent 主控编排。Skill 不得直接调度 Agent。

### 8.4 多角色讨论适用判断原则

适用场景：需要从不同角色视角分析；架构变更需要评估多个模块影响；技术选型需要多维度对比；需求变更需要评估产品、技术、质量、治理影响。

不适用场景：简单问题，单角色分析即可解决；用户已明确要求调用 SOLO Agent；内容已满足 Task 创建条件，应直接创建 Task。

## 九、任务执行与证据回写规则

### 9.1 状态变更先于执行

任务状态变更必须先于执行动作同步到 pm-kit-base。状态变更是执行动作的前置步骤，不是事后补录。

### 9.2 Review Gate

Task 进入 `Review Needed` 后，必须通过检查或确认形成 review 结果，且 `review.status` 进入 `passed` 且 `human_ready == true`，或 `skipped` 且有原因，才能进入 Human Gate。

Task 检查不是 Human Gate 的替代，而是 Human Gate 的前置条件：

```text
开发完成 → Review Needed → 检查/确认 → human_ready = true 或 skipped → Human Gate → 人类验收
```

`review.status` 为 `pending`、`failed` 或 `needs_human` 时，Task 不得关闭。

PM Kit 不要求配置任务检查 Agent。Task 检查可通过工具内置检查、SOLO 主流程检查或人类确认完成。

### 9.3 证据回写原则

1. 每次执行都应留下可追溯的任务状态、验证证据、ADR 或检查结果。
2. 执行证据不得只停留在聊天记录中，必须写入项目事实源。
3. 证据写入的目标位置由对应管理对象实践定义。
4. 违反 Human Gate 的操作必须回滚，并记录到 Change 记录。

## 十、外部工具与过程资产规则

### 10.1 MCP 定位

MCP 在 PM Kit 中只作为外部工具能力：AI 需要知道 MCP 是外部工具能力而非事实源，避免将 MCP 输出等同于项目事实。PM Kit 不涉及 MCP 的具体实践、配置或可用性保障。

### 10.2 MCP 认知边界

1. MCP 是外部工具能力，不是 PM Kit 事实源，也不是独立协作主轴。
2. 不因 MCP 可用而跳过 docs、pm-kit-base、Rules 等项目事实源。
3. 外部资料只能作为参考，不能覆盖项目事实源。
4. 高风险 MCP 必须最小授权，并在执行前触发 Human Gate。
5. MCP 不承载稳定规范、长期决策、项目事实或完整流程说明。

### 10.3 高风险 MCP 场景

以下 MCP 或外部工具操作必须触发 Human Gate：

- 生产或云资源写操作
- 权限或凭据相关操作
- 付费或不可低成本回滚操作
- 跨项目或跨系统契约变更

### 10.4 Trae Plan / Spec 过程资产规则

Trae `.trae/specs/` 是 Plan / Spec 模式生成的执行计划资产或过程知识资产，不自动等同 PM Kit 正式需求、任务或规范事实源。

1. 若 `.trae/specs/` 内容被采纳为正式需求，必须同步到 `docs/20-59`。
2. 若 `.trae/specs/` 内容被采纳为正式任务，必须创建或更新 `pm-kit-base/tasks/`。
3. 若 `.trae/specs/` 内容被采纳为正式规范，必须写入 PM Kit `specs-v2/` 并经过对应 Human Gate。
4. `.trae/specs/` 可作为过程证据或执行草案，但不得替代 PM Kit facts。
5. 从 `.trae/specs/` 晋升为正式事实源属于事实源归属变化，应触发 Human Gate。

## 十一、AI 协作边界与冲突处理

### 11.1 AI 可以自主执行

- 读取项目事实源（docs/、pm-kit-base/、Rules）。
- 根据规则判断是否需要 Human Gate。
- 执行不涉及 Human Gate 的代码修改和文档更新。
- 自动分类审计发现为 Task / 待决策 Task / Memo。
- 追加 Change 记录和踩坑记录。

### 11.2 AI 必须确认后执行

- 修改规则、Skill、Agent、product.yaml。
- 跨项目变更。
- 决策和新增依赖。
- 覆盖已有事实源或改变事实源归属。
- 需求 L2/L3 变更。

### 11.3 AI 禁止执行

- 绕过 Human Gate 修改规则、Skill、Agent 或 product.yaml。
- 仅凭惯例推断技术栈、测试命令或依赖关系。
- 在审计快照中记录可变状态字段。
- 自动修复审计发现的不合规内容（只补齐允许自动创建的缺失结构）。
- 让 PM 工具直接调用 AI、Skill 或 Agent。

### 11.4 PM 工具不直接调用 AI

PM 工具不直接调用 AI。PM 工具只提供结构化上下文、受控编辑入口、Human Gate 提示和可复制或可投递的执行请求。AI 能力由 Trae 对话层提供，工具不替代对话层的分析、决策和调度能力。

### 11.5 规则冲突处理优先级

当多个规则看似冲突时，AI 按以下优先级执行：

1. **规范层（specs）> 工作区规则（L0）> 项目规则（L1）> 场景规则（L2）**
2. **Human Gate 触发规则 > 一切其他规则**
3. **事实源仲裁表中的权威位置 > 其他文档的相同内容**
4. **明确规则 > 隐含规则**：显式写出的规则优先级高于推断出的规则
5. **新规则 > 旧规则**：同层级冲突时，以后更新日期为准

## 十二、Human Gate 与检查要求

### 12.1 定义

Human Gate 是项目门禁要求，要求 AI 在特定场景下暂停执行并等待人类确认后才能继续。Human Gate 不是平台自动保证，而是 AI 行为约束。

### 12.2 触发条件

以下情况必须触发 Human Gate：

| 类别 | 触发场景 |
|---|---|
| 规则变更 | 修改 PM Kit specs、L0、L1、L2 或其他规则文件 |
| 管理资产 | 创建、修改或删除 Skill；创建、启用、删除或修改 Agent 调度边界 |
| 决策 | 决策、新增依赖、难以低成本回滚的技术路线变化 |
| 跨项目影响 | 跨项目影响、修改跨项目接口契约、改变项目集治理方式；修改兼容入口边界 |
| 产品配置 | 修改 product.yaml 字段 |
| 事实源 | 覆盖已有事实源、改变事实源归属；将过程资产晋升为正式事实源 |
| 审计 | 修改审计规范本身；生成开发或交付实践（首次、技术栈变更或发布流程变更） |
| Task 流转 | 审计发现的待决策 Task；Task 状态从 Decision Needed 流出 |
| 需求变更 | L2/L3 需求变更（改变交付范围、验收标准、事实源归属、工具边界或跨项目约定） |
| 高风险工具 | 高风险 MCP 或外部工具写操作 |

### 12.3 执行规则

1. AI 检测到 Human Gate 场景时必须暂停，向用户说明触发原因和待确认内容。
2. 用户确认后 AI 才能继续执行。
3. 明确确认表达包括"确认""按方案 A 执行""继续执行该方案"等；"你觉得呢""再看看""有没有别的办法"等不构成确认。
4. 用户确认某个裁决或设计方向，不必然等于授权立即修改全部正式文件；正式执行前应确认待修改文件、影响范围和是否写入事实源。
5. 用户在本轮选择具体规则、Skill 或 Agent 方案时，视为确认该具体方案，AI 必须直接创建或修改正式资产，不停留在建议状态。
6. 违反 Human Gate 的操作必须回滚，并记录到 Change 记录。
7. 删除 / 重命名 / 替换文件前，按以下顺序判断是否需要 Human Gate：
   1. 若对象是 Skill、Agent、规则文件或 `product.yaml`，必须 Human Gate。
   2. 否则判断是否已被 git 跟踪；若是 git 已跟踪的普通代码、文档或配置文件，可直接删除、重命名或替换，不得因该文件操作请求确认。
   3. 若文件未被 git 跟踪，但可由当前操作安全重建，或明确是新建临时文件，可直接删除。
   4. 若文件未被 git 跟踪且不可安全重建，必须请求确认。
   5. 若当前文件操作属于已确认方案的一部分，普通 git 文件不再二次确认，只在完成摘要中说明已删除、重命名或替换。
8. Human Gate 的确认对象必须精确到决策、方案或例外资产，不得泛化到执行该方案所需的普通 git 文件操作。

### 12.4 检查要求

| 检查项 | 标准 |
|---|---|
| Human Gate 触发 | 检测到触发场景时已暂停并等待确认 |
| 确认表达 | 确认表达明确，不含糊 |
| 回滚 | 违反 Human Gate 的操作已回滚并记录 |
| 文件操作 | 删除/重命名/替换文件前已按判断顺序处理 |
| 事实源边界 | 未复制规则正文形成第二事实源 |
| 规则分层 | L1 不重复规范层或 L0 内容 |
| Skill 边界 | Skill 未调度 Agent，未成为事实源 |
| Agent 边界 | Agent 未自行触发，未调度其他 Agent |
| 证据回写 | 执行证据已写入项目事实源 |
