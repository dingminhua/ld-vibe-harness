## 1. 本文解决的问题

LDVH 运行在 Trae IDE 环境中，Trae 提供了平台预置的通用技能（如 `web-dev`），这些技能具备独立完成特定领域任务的能力，但不知道 LDVH 的事实模型、状态机、Human Gate 等约束。本文解决以下问题：

1. 第三方技能与 LDVH 自建技能的本质区别是什么；
2. 第三方技能可以做什么、不应该做什么；
3. 如何设计引入流程，让第三方技能的产出物能被 LDVH 体系接管；
4. 是否需要创建 LDVH 专属技能来包装或约束第三方技能的行为；
5. 非 LDVH 来源内容（含第三方技能、用户既有资产、项目既有资产、调研材料、自动生成内容等）应如何被识别、分类、接管、验证和回写；
6. 第三方 Skill 作为默认可用接管路径的启用、取消、降级和重新启用边界如何与 LDVH 主控接管衔接。

---

## 2. 两类技能的本质区别

| 维度 | LDVH 自建 Skill | 第三方平台 Skill（如 web-dev） |
|---|---|---|
| 来源 | 项目 `.trae/skills/` 下版本化管理 | 平台运行时注入，不在项目代码库中 |
| 命名 | `ldvh-` 前缀 | 平台自定义命名 |
| 约束感知 | 知道事实模型、状态机、Human Gate、Core Loop | 不知道任何 LDVH 约束 |
| 输出物 | 受控的事实源变更、规范变更、流程推进 | 通用代码生成、文件创建 |
| 触发条件 | Core Loop 阶段路由 + Rules 入口 | 用户意图匹配技能描述 |
| 可审计性 | 完整：Change 记录、ADR 关联、状态流转 | 无 LDVH 审计链路 |

核心矛盾：**第三方技能是"能力供给方"，LDVH 是"治理约束方"**。两者不在同一个信任层级。

---

## 3. 核心策略：脚手架先行，治理接管后续

### 3.1 原则

**第三方技能只做脚手架，不做持续开发。**

具体含义：
- 第三方技能负责：从零搭建项目骨架、生成初始代码结构、配置构建工具链、建立基础 UI 框架
- LDVH 体系负责：后续所有涉及事实源、状态机、约束合规的开发工作

### 3.2 为什么这样划分

1. **脚手架阶段没有事实源依赖**：创建空项目、安装依赖、配置构建工具，这些操作不涉及 LDVH 事实对象的创建或变更，不触发 Human Gate，不需要 Core Loop 路由
2. **持续开发阶段必须受控**：一旦涉及状态变更、数据模型定义、API 对接 PyTools 输出、用户交互触发事实对象操作，就必须进入 LDVH 的 Rules/Skill/Tools 管辖
3. **边界清晰才能审计**：脚手架产出物是"无约束代码"，后续改造是"受控代码"，两者在 Git 历史中应有明确的分界点

### 3.3 引入流程

```text
1. 识别需求 → 确认需要第三方技能的脚手架能力
2. 创建 Task → 记录引入意图和预期产出物（ldvh-intake）
3. 执行脚手架 → 调用第三方技能，生成初始代码
4. 治理接管点 → 脚手架完成后，立即进入 LDVH 管辖
5. 审计与改造 → 按 LDVH 约束审计产出物，改造不合规部分
6. 持续开发 → 后续所有开发走 LDVH Core Loop
```

**治理接管点是关键里程碑**：从这一刻起，所有变更必须遵守 LDVH 的 Rules、Skill、Tools、Human Gate 和 Change 记录要求。

---

## 4. 治理接管检查清单

脚手架完成后、治理接管前，需要对产出物进行以下检查：

1. **事实源隔离**：脚手架生成的代码是否直接读写 `ldvh-base/` 目录？如果是，必须改造为通过 PyTools 或 Skill 间接访问
2. **状态机合规**：是否有直接修改事实对象状态的代码？如果有，必须改为通过状态机流转
3. **Human Gate 嵌入**：用户操作是否可能触发需要 Human Gate 的变更？如果是，必须嵌入确认环节
4. **API 边界**：Web 前端是否直接调用 PyTools CLI？应通过 Web 后端 API 间接调用，后端负责约束检查
5. **数据模型映射**：脚手架生成的数据模型是否与 LDVH 事实模型对齐？如果不对齐，需要适配层
6. **构建与部署**：脚手架的构建配置是否兼容 LDVH 的目录结构和版本管理要求？

## 5. 是否需要 ldvh-web 包装技能

### 5.1 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 直接用 web-dev，手动接管 | 简单直接，无额外建设成本 | 每次都需要人工记住治理接管流程，容易遗漏 |
| B. 创建 ldvh-web 包装 web-dev | 流程标准化，接管检查自动化 | 建设成本，需维护包装层，依赖第三方技能接口稳定 |
| C. 完全自建，不用 web-dev | 完全可控，无第三方依赖 | 丧失脚手架效率，重复造轮子 |

### 5.2 建议

**当前阶段选方案 A，中期演进到方案 B。**

理由：
- 当前 LDVH Web 开发尚未启动，过早创建包装层会增加抽象而没有 Dogfood 验证
- 先用方案 A 积累经验，明确哪些接管检查是高频且容易遗漏的
- 当接管检查项稳定且重复出现时，再创建 `ldvh-web` Skill 将检查自动化

如果后续 `web-dev` 技能接口不稳定或能力不足，再评估方案 C。

## 6. 更一般的第三方技能引入框架

`web-dev` 只是第一个案例。未来可能引入的其他第三方技能包括：
- 数据库 Schema 生成技能
- API 文档生成技能
- 测试用例生成技能
- 部署配置生成技能

通用引入框架：

1. **评估信任边界**：第三方技能的产出物是否涉及 LDVH 事实源？涉及则必须治理接管
2. **划分阶段**：脚手架阶段（无约束）vs 持续开发阶段（受控）
3. **定义接管点**：脚手架完成后的审计检查清单
4. **决定包装策略**：直接使用 → 积累经验 → 标准化包装 → 自动化接管
5. **记录决策**：引入策略进入 ADR 或 research 文档，避免每次重新判断

## 7. AI 视角的补充看法

作为在 LDVH 体系内运行的 AI，我对第三方技能引入有以下观察：

1. **第三方技能是"无记忆的外部承包商"**：它不知道项目的历史决策、约束和 Pitfall。让它做脚手架没问题，但让它做持续开发就像让一个不了解项目文化的人直接改核心代码——风险不可控。

2. **最大的风险不是代码质量，而是约束逃逸**：第三方技能生成的代码可能完全正确，但如果它绕过了状态机直接修改事实源，或者绕过了 Human Gate 直接执行高风险操作，这种"正确的违规"比"错误的合规"更危险——因为更难被发现。

3. **脚手架产出物应视为"待审计的外部贡献"**：与开源依赖的引入类似，第三方技能的产出物需要经过审计才能进入项目主干。这不是不信任，而是治理的基本要求。

4. **包装层不是过度工程，而是必要的安全网**：当 LDVH Web 进入持续开发阶段后，一个 `ldvh-web` Skill 能确保每次 Web 变更都经过约束检查，这比依赖 AI 记住"要检查"更可靠。规则写在 Skill 里比写在 AI 的上下文里更稳定。

5. **第三方技能引入应成为 LDVH 机制完备性的试金石**：如果 LDVH 的 Rules/Skill/Tools 体系能顺畅地接管第三方技能的产出物，说明体系设计是健壮的；如果接管过程需要大量人工干预和临时规则，说明体系还有缺口需要补。

## 8. 非 LDVH 来源内容治理的更一般思考

第三方技能只是非 LDVH 来源内容的一种。本节把分析推广到更一般的非 LDVH 来源内容治理，作为原 `specs/11-非LDVH来源内容治理规范.md` 回退后保留的候选研究材料。

### 8.1 非 LDVH 来源内容的来源分类

| 类型 | 示例 | 典型风险 |
|---|---|---|
| 环境提供能力 | 环境内置 Skill、Agent、Hook、MCP、插件、搜索、浏览器、自动化工具 | 环境能力被误认为 LDVH 授权 |
| 第三方内容 | 外部文档、开源项目、教程、社区经验、第三方模板、第三方生成器 | 外部结论未经吸收直接生效 |
| 用户既有内容 | 用户已有提示词、规则、脚本、工具、文档、项目习惯、私有知识 | 用户习惯与 LDVH 事实源或流程冲突 |
| 项目已有资产 | 代码、README、配置、测试、CI、设计稿、既有文档、业务约束 | 既有资产被误认为已经符合 LDVH |
| 自动生成内容 | 脚手架、候选代码、候选配置、候选文档、模型输出 | 生成结果未经验证直接进入交付 |
| 外部调研材料 | 资料摘录、竞品分析、第三方 API 说明、调研报告 | refs 或 research 结论绕过吸收 |

### 8.2 已接管与未接管

非 LDVH 来源内容只有在满足以下条件后，才可被视为已接管：

1. 来源、用途和影响范围已记录；
2. 是否影响事实源、规范、代码、状态、工作流程、Web 或 Human Gate 已判断；
3. 输出已由 LDVH 主控重新审查、筛选和归属；
4. 必要验证已完成，或验证缺口已记录；
5. 稳定事实已写入对应 Git 可追踪事实源；
6. 高影响事项已通过 Human Gate 或明确暂停。

未满足上述条件时，该内容只能作为候选输入、参考材料、临时能力或待验证产物。

### 8.3 治理原则

1. **可用不等于生效**：AI 可以读取、参考或调用非 LDVH 来源内容，但不得因为其可用、方便、看似正确或由环境提供，就把它直接作为 LDVH 规则、事实、状态、证据或验收结果。
2. **来源必须可追踪**：使用非 LDVH 来源内容时，应尽量记录来源、访问位置、调用方式、产出位置、影响范围和验证方式。如果来源不可追踪、实现不可审计、行为不可解释或结果不可复现，应降低信任等级，并限制其只能作为候选输入。
3. **主控接管**：非 LDVH 来源内容的输出必须回到 LDVH 主控。主控负责判断是否采纳、如何验证、是否触发 Human Gate、写入何处、是否需要记录任务、决策、变更、风险或经验。环境能力、第三方 Skill、外部工具、脚本、Web 页面或自动化流程不得替代主控进行跨流程调度、最终验收、事实源归属判断或 Human Gate 决策。
4. **默认隔离**：非 LDVH 来源内容默认先隔离为候选材料或临时能力，不得直接进入核心事实源、状态机、规范正文、工作流程、受控写入链路或发布链路。隔离方式可以包括：放入 refs、research、临时草稿或候选目录；只读调用，不授予写入权限；限制输入上下文和输出目录；先生成候选产物，再由 LDVH 主控审查；在 Task、ADR、Memo、Change 或后续记录中保留接管结论。
5. **风险升级**：只要非 LDVH 来源内容会写文件、改规范、改状态、装依赖、执行代码、访问网络、影响事实源、改变工作流程、改变用户项目结构或成为持续开发基础，就应升级风险等级。风险升级后，AI 应检查 Human Gate、验证方式、可回滚路径和事实源回写位置。

### 8.4 信任等级候选分级

非 LDVH 来源内容按信任等级使用，候选分级如下（仅作为研究材料参考，不构成正式规范）：

| 等级 | 名称 | 含义 | 允许行为 |
|---|---|---|---|
| T0 | 未识别 | 来源、用途或影响范围不清楚 | 不得采纳；先识别来源和用途 |
| T1 | 可参考 | 可作为阅读、理解或候选判断输入 | 可引用为参考，但不得生效 |
| T2 | 可调用 | 可在受限输入、受限输出下调用 | 可生成候选材料或辅助分析 |
| T3 | 可接管 | 输出可被 LDVH 主控审查、验证和归属 | 可进入接管流程 |
| T4 | 可纳入事实源 | 已验证、已归属、已通过必要 Human Gate | 可写入对应权威事实源 |
| T5 | 可稳定复用 | 多次接管有效，边界和验证方式稳定 | 可沉淀为 LDVH 自建 Code、包装 Skill、规范规则或最佳实践 |

信任等级只能由接管、验证和回写证据提升，不能由环境知名度、用户偏好、模型自信或一次成功结果直接提升。

### 8.5 标准接管流程候选

1. **识别来源**：环境提供、第三方提供、用户既有、项目既有、自动生成、外部调研或混合来源；来源不清楚时停留在 T0。
2. **判断用途**：信息参考、候选产物生成、工具调用、代码或配置变更、事实源写入、工作流程辅助、Web 或 Human 入口辅助、最佳实践沉淀；越接近写入、执行、发布、状态流转或事实源归属，接管要求越高。
3. **限制权限**：输入上下文、输出目录、写入权限、网络访问、依赖安装、可执行命令、可修改文件范围、可见敏感信息；无法限制范围时应触发 Human Gate 或降级为只读参考。
4. **主控接管**：明确产出内容、产出位置和变更范围；判断是否影响规范、事实源、Code、Web、状态机、工作流程或 Human Gate；检查是否存在绕过 LDVH 治理的逻辑；运行可用的验证；记录未验证项和残留风险；按归属写回或丢弃。
5. **验证与回写**：稳定结论必须经过验证或记录验证缺口。验证可包括文档结构和引用检查、字段或状态检查、lint / typecheck / test / build / 运行验证、安全与依赖检查、Web 页面或受控写入验证、Human Gate 确认、独立子 Agent 审阅。验证通过后按归属进入正式规范、docs、refs、research、工作对象、Code、Web 文档、测试或最佳实践；不通过时进入修正、降级、废弃或后续任务。

### 8.6 候选归属分流

非 LDVH 来源内容接管后，应按内容性质分流。

| 内容性质 | 归属 |
|---|---|
| 稳定规范规则 | 正式规范正文 |
| 外部资料引用 | refs |
| 内部分析、方案比较或接入评估 | research |
| 用户项目正文资料 | docs 正文区 |
| 工作事实、任务、决策、变更、经验 | 对应工作对象 |
| 可执行工具、脚本、校验器、测试程序 | Code 实现 |
| Web 页面、交互、同步、Human 入口 | Web 实现或 Web 文档 |
| 可复用流程入口 | LDVH 自建 Skill 或包装 Skill |
| 多次验证有效的使用方式 | 最佳实践（见 `docs/studies/18-LDVH最佳实践的现状与回退考虑.md`） |
| 不可验证或不再适配的内容 | 废弃、降级或保留为参考 |

分流时不得为了方便把稳定规则放进最佳实践，也不得把候选材料写成事实源。

### 8.7 安全与供应链边界候选清单

以下内容应按高风险处理：

1. 外部脚本、插件、依赖、二进制文件、生成器或自动化配置；
2. 需要安装依赖、访问网络、调用远程服务或读取敏感路径的能力；
3. 会修改文件、删除文件、提交、推送、发布或调整项目结构的能力；
4. 难以审计实现、版本不可锁定、行为不可复现或带有自动更新能力的内容；
5. 可能输出密钥、令牌、隐私数据或本地敏感路径的内容；
6. 可能替代 Human Gate、事实源、状态机或验证流程的内容。

高风险内容必须至少说明来源、版本或入口、权限范围、验证方式、回滚方式和是否需要 Human Gate。

## 9. 第三方 Skill 接管落地选项的更细致边界

原 `specs/11.01-第三方Skill接管落地选项.md` 定义了"第三方 Skill、环境 Skill、外部 Skill 或类似外部可复用 AI 能力作为默认可用接管路径时的启用、取消、降级和重新启用规则"。本节作为研究材料保留其核心要点，不在正文区正式规范层面继续生效。

### 9.1 第三方 Skill 的范围

第三方 Skill 包括：

1. 环境内置但不是 LDVH 自建的 Skill；
2. 外部开发者提供的 Skill；
3. 用户导入、复制或改造但尚未被 LDVH 接管的 Skill；
4. 与 Skill 等价的外部可复用 AI 能力、模板生成器或环境流程入口。

第三方 Skill 是否来自可信环境，不改变其非 LDVH 来源内容属性。只有完成接管、验证和归属后，它的输出才可进入对应事实源或后续实践。

### 9.2 默认落地的研究判断

研究阶段的判断是：第三方 Skill 接管落地选项默认启用。

默认启用时，AI 可以在以下场景中评估使用第三方 Skill：

1. 从空目录生成候选脚手架、初始页面、样例结构或基础配置；
2. 生成候选代码、候选文案、候选测试、候选设计稿或候选配置；
3. 在不直接写入权威事实源的前提下提供专项分析；
4. 辅助理解外部技术、第三方库、环境功能或第三方文档；
5. 对外部资料进行初步整理，供 LDVH 主控后续接管；
6. 在当前 Task 或明确授权范围内完成可验证的局部生成任务；
7. 为是否创建 LDVH 包装 Skill、LDVH 自建 Code 或最佳实践提供 Dogfood 素材。

默认启用不表示：

1. 第三方 Skill 可以直接改写权威事实源；
2. 第三方 Skill 输出可以直接成为任务完成证据；
3. 第三方 Skill 可以绕过主控接管；
4. 第三方 Skill 可以绕过 Human Gate、Code 验证、事实源边界或工作流程；
5. AI 必须优先调用第三方 Skill。

### 9.3 取消与重新启用的研究判断

用户可以通过 AI 请求取消或重新启用第三方 Skill 接管落地选项。

候选取消流程：

1. 读取 11 与本文（已回退为研究材料），并按适用范围读取当前环境能力清单、42 落地与检查报告，或工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml` 与对应管辖项目事实源；
2. 检查取消范围属于 LDVH 自身项目还是某个管辖项目；
3. 向用户说明取消的影响范围和降级后果；
4. 触发 Human Gate，等待用户确认；
5. 用户确认后，在管辖项目事实源、Memo、Task、ADR 或其他合适事实源中登记第三方 Skill 接管落地选项为"已取消"或等价状态；
6. 记录取消时间、确认人、适用范围、降级方式和重新启用条件；
7. 后续 AI 遇到第三方 Skill 场景时，应先提醒该选项已取消，不得默认调用。

候选重新启用流程与取消流程对称，需要重新评估风险、影响范围、Human Gate 确认和登记方式。

### 9.4 接管检查候选清单

使用第三方 Skill 后，应检查：

| 检查项 | 问题 |
|---|---|
| 选项状态 | 管辖项目事实源、项目接入说明、Memo、Task、ADR 或 Human 本次授权中第三方 Skill 接管落地选项是否启用；若取消，是否获得本次临时授权 |
| 产出范围 | 生成或修改了哪些文件、配置、文档或命令 |
| 事实源 | 是否直接修改或冒充权威事实源 |
| 状态机 | 是否直接修改对象状态、字段或状态流转 |
| Human Gate | 是否涉及删除、安装、发布、提交、推送、授权或高风险变更 |
| Code 风险 | 是否引入依赖、脚本、远程服务、自动更新或不可审计代码 |
| Web 风险 | 是否生成绕过受控写入或事实源同步的 UI |
| 验证 | 是否完成 lint、typecheck、test、build、运行验证或人工检查 |
| 回写 | 稳定结论是否写入对应事实源，未验证项是否记录 |

## 10. 与最佳实践研究的关系

第三方 Skill 的默认落地、取消、降级和重新启用规则当前由本文承载，不进入正式规范；最佳实践相关的概念和回退记录承载于 `docs/studies/18-LDVH最佳实践的现状与回退考虑.md`。

以下内容可以进入最佳实践研究材料：

1. 某次第三方 Skill 接管成功案例；
2. 某类脚手架接管后的改造经验；
3. 某类失败模式的处置经验；
4. 包装 Skill 是否值得创建的经验判断；
5. 第三方 Skill 接管后的测试和审阅节奏。

如果最佳实践研究中反复出现同一硬边界，应回到正式规范吸收，不得长期留在最佳实践研究中作为隐性规则。
