## 一、LD Vibe Harness 为什么存在

LD Vibe Harness 是面向 Vibe Coding 的工程化驾驭框架，由 LaoDing 基于 Trae Solo 开发实践。

Vibe Coding 让人用自然语言描述需求，AI 快速生成代码，人负责验收和调方向。它快、自由、低门槛，但天生有三大硬伤：非确定性、幻觉和无记忆。没有约束的 Vibe Coding 容易停留在原型阶段，不敢上生产，不敢长期维护。

LD Vibe Harness 要解决的问题，就是把"随性的 AI 编程"变成"可控、可复用、可交付的工程流程"。

它的方法，是以约束体系划定边界，以事实源沉淀记忆，以工具链连接能力，以工作流驱动执行，以任务治理守住交付，以可视化工具桥接信息——让人的自然语言意图通过规则、事实源、工具链和工作流，转化为可规划、可执行、可验证、可沉淀的 AI 工程闭环。

LD Vibe Harness 关注的核心问题是：

```text
AI 进入项目后，如何知道该读什么、做什么、不能做什么、何时停下等待人确认，以及完成后如何把事实写回项目。
```

---

## 二、第一服务对象

LD Vibe Harness 以 AI 执行者为第一服务对象，整个体系围绕"帮助 AI 高效、准确、可控地工作"来设计。

这不意味着人和工具处于次要位置，而是说 LD Vibe Harness 的信息组织方式、事实源结构、任务格式、规则入口和工具能力，首先要满足 AI 的读取、理解、场景识别、拆解、执行、检查和事实回写需要。

因此，LD Vibe Harness 不只为 AI 提供上下文，还要为 AI 提供场景识别、工具选择、Skill 进入、子 Agent 调度和人类确认的行动依据。

在这个前提下，LD Vibe Harness 的架构由介质、Trae Solo 环境机制、Harness 工具、Harness 生产对象和 Harness 行动模型五类构成要素共同组成。

人在 LD Vibe Harness 中负责：

1. 表达意图；
2. 补充约束；
3. 确认关键节点；
4. 校正 AI 判断；
5. 验收结果。

AI 负责：

1. 读取项目上下文；
2. 识别当前任务场景和事实源边界；
3. 判断需要使用的工具、Skill 或子 Agent；
4. 拆解和执行任务；
5. 识别需要人确认的节点；
6. 记录执行证据；
7. 按事实源边界写回项目。

工具负责：

1. 读取事实源；
2. 聚合事实源；
3. 校验事实源；
4. 提供受控写入入口；
5. 降低人和 AI 维护结构化文件的成本。

## 三、价值实现标准

LD Vibe Harness 的建设成效不以文档、任务、工具页面或对象数量衡量，而以 AI 是否能在项目中稳定理解、受控执行、识别门禁、留下证据并支持人类确认来衡量。

### 3.1 总体评价标准

| 编号 | 标准 | 含义 | 不满足时的表现 |
|---|---|---|---|
| V1 | 稳定理解 | AI 能在行动前获得足够但不过载的最小可行动上下文 | AI 反复询问已有事实、误读项目边界、遗漏关键约束 |
| V2 | 受控执行 | AI 能依据规则、事实源和行动模型执行任务，而不是凭聊天记忆自由发挥 | AI 绕过规则、跳过任务状态、直接修改不该修改的事实 |
| V3 | 门禁识别 | AI 能识别 Human Gate，知道何时必须暂停并等待人确认 | AI 擅自执行高影响变更、跳过确认、误关闭任务 |
| V4 | 证据沉淀 | AI 的执行结果能留下可追溯的证据、检查结果、决策或变更记录 | 完成了但无法证明、结果只存在聊天里、后续无法追溯 |
| V5 | 事实回写 | 稳定事实能按边界回写到 Git 文件事实源 | 事实漂移在聊天、缓存、UI 或派生数据中 |
| V6 | 人类确认质量 | 人能基于事实源、证据和工具展示做出高质量确认 | 人只能凭感觉验收，无法看到状态、风险、证据和影响 |
| V7 | 持续改进 | 失败、不确定性和人类纠偏能回到事实源，改善后续 AI 行动 | 同类错误反复发生，踩坑经验没有沉淀 |

### 3.2 五类构成要素与价值标准的关系

| 构成要素 | 对价值实现的贡献 |
|---|---|
| 介质 | 提供 Git 可追踪、AI 可读取、人可审查、工具可解析的承载形式 |
| Trae Solo 环境机制 | 提供 AI 协作入口和原生机制，但不直接保证工程可控 |
| Harness 工具 | 降低读取、校验、聚合、展示和受控写入事实源的成本 |
| Harness 生产对象 | 把项目生产事实建模为可追踪、可验证、可流转的对象 |
| Harness 行动模型 | 约束 AI 如何读取上下文、识别场景、执行任务、触发门禁和回写事实 |

### 3.3 反向判断

出现以下情况时，应认为 LD Vibe Harness 未实现核心价值：

1. AI 需要依赖聊天记忆才能继续项目；
2. 任务状态、证据、决策或变更无法在 Git 文件事实源中追溯；
3. 工具展示与 Git 文件事实源不一致；
4. AI 无法识别应触发 Human Gate 的关键节点；
5. 人无法基于事实源和证据完成验收；
6. 同类失败反复发生且没有进入 Pitfall、规则或行动模型。

## 四、架构：五类构成要素

LD Vibe Harness 不是由单一工具、单一规范或单一对象体系构成，而是由五类构成要素共同形成 AI 工程驾驭体系：介质、Trae Solo 环境机制、Harness 工具、Harness 生产对象和 Harness 行动模型。

这五类不是上下层级，也不是五种能力，而是性质不同、分工不同、共同服务于同一工程闭环的构成要素。

### 4.1 五类构成要素总览

| 类别 | 英文 | 归属 | Harness 的角色 | 回答的问题 | 举例 |
|---|---|---|---|---|---|
| 介质 | Medium | 行业标准 | 定义使用规则，不重新定义介质本身 | 用什么承载 | YAML、Markdown、Python、JavaScript |
| Trae Solo 环境机制 | Trae Solo Environment Mechanisms | Trae 提供 | 利用，不重新定义 | AI 协作运行在哪些原生机制之上 | Rules、Skill、Agent、MCP、Tool Calling |
| Harness 工具 | Harness Tools | Harness 提供 | 实现和维护 | 用什么辅助读取、校验、展示和写入 | Web Tools、Python 辅助程序 |
| Harness 生产对象 | Harness Production Objects | Harness 定义规范，项目实例化 | 建模工程生产事实 | 项目事实如何被组织、流转和沉淀 | Intent、Task、Memo、ADR、Evidence、Change、Pitfall |
| Harness 行动模型 | Harness Action Model | Harness 定义规范，项目执行时适用 | 建模 AI 行动控制 | AI 如何读取、判断、执行、停下和回写 | Context、Scenario、Gate、规则适用、Skill 进入、Agent 调度、事实源回写 |

### 4.2 介质

YAML、Markdown、Python、JavaScript 等文件格式和编程语言是 LD Vibe Harness 使用的行业标准承载形式。介质本身不属于 Trae、Harness 或项目，也不是 Harness 自定义对象。

介质的核心特征：

1. **行业标准**：介质本身的语法和规范由行业标准定义；
2. **Harness 定义使用规则**：Harness 在基础设施规范中定义这些介质的使用规则，但不重新定义介质本身；
3. **五类共用**：Trae Solo 环境机制通过 .md 文件落地 Rules、Skill、Agent 定义；Harness 工具通过 .py / .js 程序落地 Web 后端、前端和辅助脚本；Harness 生产对象通过 .yaml / .md 文件落地 Task、ADR、Pitfall 等实例；Harness 行动模型通过规范、规则入口和结构化上下文约束 AI 行动。

### 4.3 Trae Solo 环境机制

Trae Solo 提供了 Rules、Skill、Agent、MCP、Tool Calling 等原生机制，它们是 LD Vibe Harness 可以利用的 AI 协作底座，但机制本身不会自动形成工程驾驭能力，也不会天然约束 AI 行为。

LD Vibe Harness 对 Trae Solo 环境机制的态度：

1. **利用不重新定义**：Harness 定义如何使用 Trae 原生机制，不重新定义机制本身；
2. **规范不替代**：Harness 的 Rules、Skill、Agent 设计规范，是对 Trae 原生机制的使用约束和最佳实践，不是替代 Trae 的机制；
3. **适配不绑定**：Harness 的规范体系适配 Trae Solo 的能力模型，但不假设 Trae 是唯一可用的 AI 编程环境。

### 4.4 Harness 工具

Harness 工具是 LD Vibe Harness 自身提供的辅助执行手段，用于桥接 AI 优先的结构化信息和人的可读可操作需求。

Harness 工具包括可视化工具和程序辅助工具。当前主要包括：

1. **Web Tools**：可视化工具，把 AI 优先的结构化信息转化为人可读、可操作的界面，桥接信息；
2. **Python 辅助程序**：解析、校验、聚合和受控写入事实源，降低人和 AI 维护结构化文件的成本。

Harness 工具的边界：

1. 工具可以降低维护成本，但不能成为最终事实源；
2. 工具可以提供受控写入入口，但不能绕过事实源边界和 Human Gate；
3. 工具可以聚合展示，但不能独立维护与事实源冲突的派生数据。

### 4.5 Harness 生产对象

Harness 生产对象是 LD Vibe Harness 对工程生产事实的自定义建模，用于承载意图、任务、决策、风险、依赖、证据、变更、产物、检查项和经验沉淀。

典型 Harness 生产对象包括 Intent、TaskSet、Task、Memo、ADR、Risk、Dependency、Evidence、Artifact、Checklist、Change、Pitfall。

Harness 生产对象的核心特征：

1. **规范由 Harness 定义**：对象的准入条件、字段契约、状态流转、事实源边界和验收规则由 Harness 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的对象实例属于项目，存放在项目的结构化事实源目录中；
3. **服务工程生产**：对象用于让 AI、人和工具围绕同一组项目事实协作，支持任务拆解、状态追踪、证据回写、决策追溯和变更审计。

### 4.6 Harness 行动模型

Harness 行动模型是 LD Vibe Harness 对 AI 在项目中如何行动的执行控制建模，用于回答 AI 进入项目后该读什么、如何判断、如何执行、何时停下等待人确认，以及完成后如何把事实写回项目。

Harness 行动模型包括：

1. **Context**：AI 行动前应获得的最小可行动上下文；
2. **Scenario**：AI 如何识别当前任务场景；
3. **Gate / Human Gate**：AI 何时必须暂停并请求人确认；
4. **规则适用**：AI 如何加载、理解和遵守 Rules；
5. **Skill 进入**：AI 何时进入可复用流程；
6. **Agent 调度**：AI 何时调用子 Agent 或专业角色；
7. **事实源回写**：AI 完成执行后如何按事实源边界写回项目。

其中 Rules、Skill、Agent 与 Trae Solo 原生机制有关。Trae Solo 提供底层机制，LD Vibe Harness 不重新定义机制本身，只定义这些机制在 Harness 中如何被设计、组织、触发、治理和回写事实源。

## 五、五类构成要素的运行闭环

### 5.1 事实源闭环

LD Vibe Harness 的事实源必须是 Git 可追踪文件。聊天记录、临时 UI 状态、工具缓存、数据库派生视图都不能成为 LD Vibe Harness 的最终事实源。

基础原则：

1. 事实必须能被 AI 读取；
2. 事实必须能被人审查；
3. 事实必须能被工具解析或聚合；
4. 事实必须能通过 Git 追溯变化；
5. 同一事实只能有一个权威位置，原则上不能出现多个事实源。

五类构成要素与事实源的关系：

| 构成要素 | 与事实源的关系 |
|---|---|
| 介质 | 提供事实源承载形式 |
| Trae Solo 环境机制 | 提供协作入口，但不成为最终事实源 |
| Harness 工具 | 读取、校验、聚合、展示和受控写入事实源，但不成为最终事实源 |
| Harness 生产对象 | 是项目生产事实的主要结构化承载 |
| Harness 行动模型 | 规定 AI 如何读取、判断和回写事实源 |

YAML 更适合承载任务、状态、结构化关系、审计字段和可解析决策。Markdown 更适合承载背景、原因、解释、需求语境和规范说明。

当一个事实需要高频被 AI 读取、被程序校验或被工具聚合时，应优先考虑结构化承载。

### 5.2 AI 行动闭环

LD Vibe Harness 的协作关系不是“工具替人管理项目”，也不是“AI 凭聊天记忆持续推进”，而是“人、AI、工具围绕 Git 文件事实源形成执行闭环”。

```text
人表达意图、约束或确认
  ↓
AI 依据 Harness 行动模型识别场景、事实源边界和 Human Gate
  ↓
AI 读取事实源，并判断是否需要工具、Skill 或子 Agent
  ↓
AI 按生产对象和行动模型拆解、执行、检查任务
  ↓
工具辅助解析、校验、聚合和受控写入
  ↓
执行证据、检查结果或决策回到 Git 文件事实源
  ↓
Web Tools 展示状态、待确认事项和检查结果
  ↓
人基于事实源追踪、确认、验收或调整方向
```

这个闭环必须满足：

1. 起点可以来自人的对话输入，但终点必须回到文件事实源；
2. AI 可以依据 Harness 行动模型调度工具、Skill 或子 Agent，但不能绕过事实源边界和 Human Gate；
3. 工具可以降低维护成本，但不能成为最终事实源；
4. 人可以通过 Web Tools 观察和确认，但关键事实仍以 Git 文件为准；
5. 每次执行都应留下可追溯的任务状态、验证证据、ADR 或检查结果。

### 5.3 人类确认闭环

| 环节 | 人的作用 | AI 的作用 | 工具的作用 |
|---|---|---|---|
| 意图输入 | 表达目标、约束、优先级 | 识别任务场景 | 提供输入入口 |
| 执行前 | 确认高影响变更 | 识别 Human Gate | 展示待确认事项 |
| 执行中 | 校正方向 | 记录证据和风险 | 展示状态和缺口 |
| 执行后 | 验收结果 | 回写事实源 | 聚合证据和检查结果 |

### 5.4 工具辅助闭环

工具不是最终事实源。工具的价值是降低人和 AI 操作事实源的成本，而不是替代事实源。

工具可以读取、解析、校验、聚合、展示和受控写入 Git 文件事实源；工具缓存、数据库派生视图、运行时索引和页面状态不得成为任务状态、证据、决策、规则或审计结果的唯一来源。

## 六、规范体系结构

### 6.1 specs 编号分区

LD Vibe Harness specs 采用分区编号，编号本身必须表达文档在规范体系中的位置。编号分区围绕五类构成要素展开，而不是围绕文档形态展开。

| 编号段 | 类型 | 说明 |
|---|---|---|
| 00 | 理念与纲要 | 定义 LD Vibe Harness 的存在理由、第一服务对象、价值实现标准、五类构成要素和文档治理规则 |
| 01-09 | 基础设施规范 | 定义介质、事实源、Trae Solo 环境机制、Harness 工具、引用纪律、命名规则等稳定基础设施 |
| 10-39 | Harness 生产对象 | 定义工程生产事实的对象模型，如 Intent、Task、Memo、ADR、Evidence、Change、Pitfall 等 |
| 40-69 | Harness 行动模型 | 定义 AI 在项目中如何行动，如 Context、Scenario、Gate、规则适用、Skill 进入、Agent 调度、审计流程、迁移流程、交付流程等 |
| 70-89 | 内部调研 | 承载 LD Vibe Harness 内部调研、设计探索、方案比较和经验分析 |
| 90-99 | 保留 | 保留给后续扩展，不得未经确认提前占用 |

新增、调整或占用编号段属于规范体系变更，应评估 Human Gate。

### 6.2 五类构成要素与编号分区

| 构成要素 | 主要编号段 | 说明 |
|---|---|---|
| 介质 | 01-09 | 作为基础设施规范的一部分展开 |
| Trae Solo 环境机制 | 01-09 | 作为基础设施规范的一部分展开 |
| Harness 工具 | 01-09 | 作为基础设施规范的一部分展开 |
| Harness 生产对象 | 10-39 | 独立编号段展开 |
| Harness 行动模型 | 40-69 | 独立编号段展开 |

### 6.3 内部调研区边界

70-89 内部调研承载 LD Vibe Harness 自身的研究、设计探索和方案比较。内部调研可以成为规范、ADR 或行动模型调整的依据，但其内容不直接构成强制执行规则。只有被升级进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

## 七、目录与事实源边界

本文中的“管辖项目”，指接入并使用 LD Vibe Harness 进行需求、任务、证据、变更、审计或交付治理的实际项目。

| 目录 | 定位 | 是否最终事实源 |
|---|---|---|
| specs/ | LD Vibe Harness 规范事实源，承载理念总纲、基础设施规范、生产对象定义、行动模型规范和内部调研；不承载具体生产对象实例 | 是，其中 70-89 内部调研不直接构成强制规则 |
| docs/ | 管辖项目资料、管辖项目审计结果、报告、操作说明、产品资料和非规范性实践 | 是管辖项目文档事实源，但不是 LD Vibe Harness 基础规范 |
| references/ | 外部资料、第三方文档、外部案例和参考材料 | 否，不作为 LD Vibe Harness 规范事实源 |
| ld-base/ | 结构化生产对象实例，如 Task、ADR、Evidence、Change、Pitfall | 是结构化生产对象事实源 |
| ld-web/ | LD Vibe Harness 的 Web Tools 实现 | 否，工具实现不是最终事实源 |
| ld-tools/ | 程序辅助工具、脚本、校验器、聚合器和受控写入工具 | 否，工具实现不是最终事实源 |

编号分区只约束 specs/ 下的规范与调研文档。外部资料、管辖项目资料、结构化对象实例和工具实现不进入 specs 编号体系，也不得以 specs 文档替代对象实例事实源。

references/ 下的文档可使用两位数字前缀按新增顺序自然增长；该编号只用于排序和引用便利，不属于 specs 规范编号体系。

审计流程属于 Harness 行动模型，应进入 40-69；审计结果属于具体管辖项目事实，应进入 docs/；审计发现转化出的任务、风险、证据或检查项，应进入 ld-base/；外部审计方法资料应进入 references/。

## 八、specs 文档治理规则

### 8.1 写作标准

specs 文档必须采用以下统一写作标准：

| 标准项 | 要求 |
|---|---|
| 上位依据 | 必须声明以本文为上位依据 |
| 解决问题 | 必须说明本文解决哪个稳定问题 |
| 总纲关系 | 必须说明如何回应本文定义的核心问题 |
| 约束对象 | 必须说明约束 AI、人、工具、事实源、生产对象或行动模型中的哪一类对象或行为 |
| 事实源边界 | 核心规则章节开头必须声明本文的权威领域和边界 |
| 不写内容 | 必须列出不进入本文的内容，防止范围膨胀 |
| 待补齐事项 | 必须标记尚未稳定、暂不写死的内容 |

### 8.2 文档骨架

specs 文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---

## 一、本文解决的问题

## 二、与 00 总纲的关系

## 三～N-3、核心规则
（开头含事实源边界声明；具体章节按主题组织）

## N-2、Human Gate 与检查要求

## N-1、不进入本文的内容

## N、待补齐事项
```

头部字段规则：以上字段为必填字段；本文作为体系顶层文档，可增加“原则”等专属字段；子文档可增加“所属主文档”“关系”等归属字段。新增头部字段不得与已有字段语义重叠，不得在头部承载正文才应展开的规范内容。

具体章节可根据主题调整，但不得省略“与 00 总纲的关系”“事实源边界声明”“不进入本文的内容”。

### 8.3 子文档规则

正式规范文档（01-69）因内容超出单文档承载能力时，可以创建子文档。子文档编号格式为 NN.SS，其中 NN 为父文档编号，SS 为子文档序号。

子文档不是独立规范，而是父文档的扩展。子文档必须遵守以下规则：

1. 子文档不强制采用正式规范文档的完整骨架，但必须遵守父文档定义的子文档格式，并保留父文档引用、所属范围、章节归属和待补齐标记等最小治理信息；
2. 子文档的权威来源是父文档，子文档不得与父文档矛盾；
3. 子文档只能引用父文档，不得与其他同级文档或跨分支文档建立规范引用关系；
4. 子文档的事实源边界由父文档声明，子文档不单独声明事实源边界；
5. 子文档的 Human Gate 由父文档的 Human Gate 规则覆盖；
6. 新增子文档应评估 Human Gate。

### 8.4 引用纪律

引用纪律的本质是事实源单一性在文档体系中的体现——同一个规则只能在一份文档中定义，其他文档只能指向它，不能复制它。

1. 权威唯一：每项稳定规则只能有一个权威定义位置。其他文档需要使用该规则时，只能写“依据 XX §Y”，不得复制、改写或另行定义同义规则；
2. 边界优先：判断规则权威位置时，优先依据事实源边界，而不是依据文档出现顺序、引用次数或描述详细程度；
3. 上位约束：00 定义体系理念、价值标准、构成要素和文档治理规则；01-09 定义基础设施规则；10-39 定义生产对象规则；40-69 定义行动模型规则；70-89 只提供内部调研，不直接构成强制规则；
4. 适配不重写：生产对象、行动模型、场景实践或工具说明引用基础设施规则时，只能说明如何适配，不能重新定义基础设施规则；
5. 冲突处理：当两个文档对同一规则给出不同表述时，应先判断该规则的权威领域；非权威文档应改为引用权威文档，不能保留并列规则；
6. 调研升级：70-89 内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

### 8.5 规范区与调研区边界

01-69 是正式规范区间，能约束 AI、人或工具的长期行为。70-89 是内部调研区间，不能直接作为强制执行规则。内部调研中的结论需要进入 01-69 正式规范区间或 ADR 后，才成为稳定规则。

## 九、Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增 specs 编号段或改变编号体系；
2. 重命名或重排 specs 文档；
3. 改变子文档层级关系；
4. 子文档重新定义父规范已有原则；
5. specs 文档引用 specs 外部文档作为规范依据；
6. 实践文档新增或扩张基础规范。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

本文只定义 specs 治理层面的 Human Gate 触发场景和最低动作要求；具体确认、记录、恢复执行和事实回写流程由 40-69 Harness 行动模型定义。

specs 文档写作检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明以本文为上位依据 |
| 事实源边界 | 核心规则章节开头已声明本文权威领域和边界 |
| 不写内容 | 已列出不进入本文的内容 |
| 架构术语一致性 | 与五类构成要素、生产对象和行动模型术语一致 |
| 目录边界一致性 | 与 specs、docs、references、ld-base、ld-web、ld-tools 的目录边界一致 |
