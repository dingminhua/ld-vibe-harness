## 1. 本文解决的问题

本文解决 LD Vibe Harness 如何使用 Rules、Skill、Agent、AskUserQuestion 及其他 Trae Solo 环境机制，以及 AI 在具体场景中应如何在 Rules、Skill、Agent 之间选择合适承载方式的问题。

本文同时定义 AskUserQuestion 工具在 LDVH 中的使用方式，包括何时触发、如何设计问询、取消后如何降级、以及如何让不了解该工具的 AI 知道如何使用。

11 系列只治理 LDVH 当前可定义、可创建、可检查、可治理的核心协作资产。

## 2. 与 00 总纲的关系

00 定义 Trae Solo 环境机制是 LD Vibe Harness 的五类构成要素之一，并明确 LDVH 对 Trae Solo 环境机制的态度是利用、不重新定义、规范不替代和适配不绑定。

本文承接 00 的该判断，选择 Rules、Skill 和 Agent 作为 11 系列正式治理对象，同时纳入 AskUserQuestion 使用规范和其他 Trae Solo 工具规范。三者共同回答：AI 如何被 Rules 约束、何时进入可复用契约式行动流程、何时进入独立上下文或专业 Agent 能力。AskUserQuestion 回答：Human Gate 如何通过 Trae 平台工具实现。

## 3. 权威领域

本文是 Rules、Skill、Agent 选择边界、AskUserQuestion 使用方式、事实源回写原则和 Human Gate 检查要求的唯一事实源。各机制内部设计细则在本文对应章节展开，不重复维护跨机制选择规则。

## 4. LDVH 与 Trae Solo 环境机制的关系

Trae Rules、Skill 和 Agent 是 LDVH 可利用的协作底座。LDVH 不重新定义 Trae 官方能力，不替代 Trae 的产品说明，也不保证 Trae 机制的运行行为始终稳定不变。

LDVH 对三类机制的治理原则如下：

1. **利用不重新定义**：LDVH 定义如何使用 Rules、Skill 和 Agent，不重新定义 Trae 官方机制本身。
2. **规范不替代**：LDVH 的机制规范是 Trae 使用约束和最佳实践，不替代 Trae 官方文档。
3. **适配不绑定**：LDVH 适配 Trae Solo 的能力模型，但不假设 Trae 是唯一可用 AI 编程环境。
4. **机制不等于事实源**：Rules、Skill 和 Agent 是执行机制或协作入口，不直接成为最终事实源。
5. **稳定事实必须回写**：三类机制产生的稳定结论、规则、任务、证据、决策或变更，必须写入 specs/、ldvh-base/、docs/ 或其他对应 Git 文件事实源后才成为 LDVH 稳定事实。

## 5. Rules / Skill / Agent 选择边界

本节是 AI 判断"这件事应该放入 Rules、Skill 还是 Agent"的唯一对比事实源，也是跨机制选择的最后决策点。本文后续各机制章节可引用本节，但不得复制维护另一套选择规则。

分工原则是：本节负责"选谁"，各机制章节负责"选定之后如何设计、治理和检查"。当机制内部检查项与本节发生冲突时，以本节为准，并应修正对应章节。

| 机制 | 适合承载 | 不适合承载 | 进入条件 |
|---|---|---|---|
| Rules | 必须遵守、绝对禁止、事实源边界、Human Gate 入口、L0/L1/L2 高频硬约束 | 大段教程、完整 SOP、低频流程、角色隔离分析 | 需要稳定约束 AI 或人，且规则应长期生效 |
| Skill | 可复用多步骤流程、标准化输入输出、轻量评估、受控写入流程 | Human Gate 判断本身、稳定规则正文、需要独立上下文或并行委派的任务 | 流程可复用、可在主上下文执行、边界和输出稳定 |
| Agent | 独立上下文、结论隔离、并行委派、不同权限边界、长期专业入口 | 简单问答、单文件小改、可由 Skill 完成的流程、仅包装角色名称 | 主上下文或 Skill 不足，且存在隔离、并行或权限差异需求 |

选择顺序：

1. 能通过稳定约束解决的问题，优先进入 Rules；
2. 需要可复用流程但可在主上下文完成的问题，进入 Skill；
3. 需要独立上下文、结论隔离、并行委派或不同权限边界的问题，才考虑 Agent；
4. 不能因为某个流程"看起来专业"就升级为 Agent；
5. 不能因为某个步骤"经常出现"就写入 Rules，若它是流程，应优先判断 Skill；
6. 不能在正式规范中提前创建具体 Skill 清单或 Agent 清单，除非对应对象规范、行动模型或模型实践子文档已稳定支撑。

### 5.1 选择判断流程

判断某项内容应由哪类机制承载时，应按以下流程处理：

1. 先判断它是否是长期稳定硬约束；若是，优先进入 Rules 或 specs 正式规范；若不是，不得仅因高频出现就写入 Rules。
2. 再判断它是否是可复用流程；若流程多步骤、输入输出稳定且可在主上下文执行，优先进入 Skill；若只是一次性操作，不应创建 Skill。
3. 再判断它是否需要独立上下文、结论隔离、并行委派或不同权限边界；只有主上下文或 Skill 不足时，才考虑 Agent。
4. 最后判断是否需要创建新的机制资产；若现有 Rules、Skill、Agent 已能覆盖，应优先引用或复用。

### 5.2 常见误判纠偏

以下判断不得作为进入某类机制的充分理由：

1. 高频出现不等于应写入 Rules；若本质是流程，应优先判断是否进入 Skill。
2. 多步骤不等于必须创建 Skill；若流程不可复用、输入输出不稳定或只服务单次任务，不应创建 Skill。
3. 专业名称不等于应创建 Agent；只有存在独立上下文、结论隔离、并行委派或权限差异时，才考虑 Agent。
4. 重要信息不等于可以停留在 Skill 或 Agent 输出；稳定事实必须回写 Git 文件事实源。
5. 机制入口不等于最终事实源；Rules、Skill、Agent 是执行机制或协作入口，不替代 specs/、ldvh-base/、docs/ 等事实源。

### 5.3 机制章节引用纪律

本文各机制章节可以描述各自机制内部的设计条件、文件结构、命名规则、生命周期、权限边界和检查项，但不得维护另一套跨机制选择规则。

涉及机制边界时，应遵守：

1. 可以写"已拟使用本机制后如何设计、治理和检查"；
2. 必须引用本文 §5 作为跨机制选择依据；
3. 不得复制本文 §5 的三机制对比表；
4. 不得新增与本文 §5 不同的选择顺序；
5. 不得用章节局部检查项覆盖本文 §5 的跨机制判断；
6. 如发现章节边界描述与本文 §5 不一致，应修改对应章节，使其回到引用关系。

## 6. Rules 机制规范

本节定义 LD Vibe Harness 如何使用 Trae Rules 机制承载 L0/L1/L2 规则通道、项目上下文读取入口、规则唯一事实源和规则变更检查。

Trae Rules 是 AI 行为约束入口。LDVH 不重新定义 Trae Rules 的官方机制，只定义 Rules 在 LDVH 中的分层、职责、触发方式映射、设计约束和 Human Gate。

Rules 与其他机制的关系：

| 对象 | 关系 |
|---|---|
| Skill | Rules 可定义 Skill 触发入口，但不承载完整 Skill SOP |
| Agent | Rules 可定义 Agent Human Gate 和调用边界，但不承载 Agent Prompt |

### 6.1 规则分层

LDVH 的规则体系由规范层和通道层共同构成：

```text
规范层：LDVH specs
  ├─ 00 理念与纲要
  ├─ 01-03、10-14 基础规范
  ├─ 20-49 事实模型规范
  └─ 50-79 行动模型规范

通道层：L0 → L1 → L2
  L0：工作区桥接 —— 声明基础规范来源、项目识别机制、L1 读取机制、管辖项目配置和事实模型编辑规则
  L1：项目规则 —— 声明项目定位、必读入口、目录事实源边界和项目专属硬约束
  L2：场景规则 —— 声明特定文件类型、目录或场景的局部约束
```

各层职责如下：

| 层级 | 典型位置 | 职责 | 禁止 |
|---|---|---|---|
| 规范层 | `specs/` | 定义 LDVH 通用规范、对象规则和行动模型 | 绑定单一管辖项目的临时事实 |
| L0 | 工作区根 `.trae/rules/ldvh-l0-rules.md`、`ldvh-l0-fact-model-rules.md` | 工作区桥接、项目上下文识别、L1 读取机制、管辖项目配置、事实模型编辑规则 | 展开完整规范正文或承载单项目约束 |
| L1 | 项目 `.trae/rules/ldvh-l1-rules.md` | 项目定位、必读入口、项目专属硬约束、L2 引导 | 重复规范层或 L0 已定义内容 |
| L2 | 项目 `.trae/rules/ldvh-l2-*-rules.md` | 特定文件类型、目录或执行场景约束 | 替代规范层、L0 或 L1 |

### 6.2 Trae Rules 生效方式映射

LDVH 保留 L0/L1/L2 分层，同时必须映射 Trae Rules 的真实生效方式：

| LDVH 层级 | 推荐 Trae 生效方式 | 说明 |
|---|---|---|
| L0 | 始终生效 | 工作区桥接、项目识别和基础规范入口 |
| L0 事实模型规则 | `globs` 指定文件生效 | 编辑管辖项目 ldvh-base/ 下 YAML 文件时生效 |
| L1 | 始终生效 | 项目定位、项目专属硬约束和必读入口 |
| L2 文件类型规则 | `globs` 指定文件生效 | 适用于文档、测试、前端、后端等文件类型 |
| L2 场景规则 | `description` 智能生效或手动 `#Rule` | 适用于发布、审计、迁移、规范重构等场景 |
| Git 提交规则 | `scene: git_message` | 仅用于提交消息生成 |

`#Rule` 手动触发优先于自动匹配。`scene: git_message` 是特殊场景规则，不应由普通 `alwaysApply`、`globs` 或 `description` 替代。

### 6.3 L1 读取机制

AI 读取某个项目目录下的文档或代码文件时，应先识别项目上下文并读取该项目 L1 规则。会话期间同一项目 L1 已读取过的，可以不重复读取。

执行顺序：

1. 从文件路径判断所属项目；
2. 检查会话中是否已读取该项目 L1；
3. 未读取时，先依据 L0 工作区规则识别规则入口，再读取项目 `.trae/rules/ldvh-l1-rules.md`；
4. 根据 L1 必读入口读取必要核心文档；
5. 若 L1 引导到相关 L2 场景规则，再按任务场景读取 L2。

L1 不存在时，应提示用户该项目尚未建立 L1 规则；若项目仍有 docs/、specs/ 或结构化事实源目录，应继续读取项目核心文档，并仅依据 L0 与规范层执行。

#### 6.3.1 L1 必读入口粒度

L1 必读入口应区分读取方式，避免 AI 对所有入口一律全文读取：

| 入口类型 | 读取方式 | 说明 |
|---|---|---|
| 项目身份与定位 | 全文读取 | 通常较短，AI 需要完整理解项目定位 |
| 必读规范文档 | 按需定位读取 | 先搜索章节标题定位，再按行范围读取目标段落 |
| 事实模型规范 | 按需定位读取 | 先识别对象类型，再搜索对应章节 |
| 场景规则 | 全文读取 | 场景规则通常较短且需要完整理解 |

L1 必读入口应提供章节级指引，说明各文档的核心章节编号和主题，便于 AI 精准定位。未提供章节级指引时，AI 应先搜索文档章节标题再读取目标段落，不得直接全文读取超过 200 行的文档。

#### 6.3.2 L1 读取策略

AI 读取 L1 引导的核心文档时，应遵循读取精准原则（依据 `specs/50-LDVH工作流基础规范.md` §6.1.1）：

1. 先用搜索工具定位目标章节，再按行范围读取；
2. 仅在需要完整上下文构建时才全文读取；
3. 不得因"必读"而默认全文读取所有必读文档。

### 6.4 规则唯一事实源

同一规则只能有一个权威位置。其他规则文件或文档需要使用该规则时，只能引用权威位置或保留压缩摘要，不得复制维护完整规则正文。

Rules 是 specs 正式规范的运行时投影，可以承载入口摘要、压缩保护、场景触发和项目专属硬约束。Rules 不得长期承载具有跨环境复用价值的框架级原则正文；当 L0/L1/L2 Rules 中出现新的长期原则、框架级约束、机制边界判断或跨环境复用规则时，应先回流到对应 specs 正式规范，再由 Rules 保留摘要和规范引用。

典型归属：

| 规则类型 | 权威位置 |
|---|---|
| LDVH 理念、构成要素和基础规范索引 | `specs/00` |
| specs 编号、文档类型和引用纪律 | `specs/03` |
| 目录事实源性质声明 | `specs/01` |
| 事实源边界和回写原则 | `specs/10` |
| Trae 机制总体边界 | `specs/11` |
| Rules 机制规则 | `specs/11` §6 |
| 管辖项目定义和术语边界 | `specs/02` |
| 工作区桥接规则 | L0 |
| 管辖项目配置 | L0 |
| 事实模型编辑规则 | L0 |
| 项目专属硬约束 | L1 |
| 文件类型或执行场景约束 | L2 |

### 6.5 Rules 与机制落地关系

普通 specs 文档与 Rules 实体的关联关系，应由对应 specs 文档依据 `specs/03-Specs文档规范.md` §6 的机制落地关系维护。本文不集中登记所有 Rules 实体清单，只定义 Rules 分层、边界和变更流程。

Rules 文件头部应声明规范来源和维护边界。规范来源用于说明该 Rules 文件摘要、触发或约束的权威 specs；维护边界用于说明该 Rules 文件只作为运行时入口、压缩摘要或场景约束，不替代 specs 正式规范。

当普通 specs 文档的机制落地关系指出某个 Rules 文件需要同步检查时，应检查该 Rules 文件：

1. 是否仍引用正确的权威 specs；
2. 是否只保留必要入口摘要，未复制维护完整规则正文；
3. 生效方式是否仍与 alwaysApply、globs、description 或 scene 匹配；
4. 压缩保护、必读入口或 L2 引导是否需要同步更新；
5. 变更是否需要记录 Change（依据 specs/22-Change-变更记录.md）

20-49 事实模型和 50-79 行动模型与 Rules 的关系，通过 NN.01-Rules.md 模型实践子文档承接，不使用普通机制落地关系替代。

审计现有 L0/L1/L2 Rules 时，不得只检查已有 Rules 文件本身，还必须从 specs 根目录正式文档反向发现 Rules 需求。审计顺序如下：

1. 读取 `specs/*.md` 根目录正式文档，并区分普通基础规范、机制基础规范、模型基础规范、区段索引文档、具体事实模型和具体行动模型；
2. 对普通 specs 文档，依据 `specs/03-Specs文档规范.md` §6 判断其稳定规则是否被 L0/L1/L2 Rules 摘要、触发或作为运行时约束消费；
3. 对 20-49 事实模型和 50-79 行动模型，检查是否由对应 NN.01-Rules.md 模型实践子文档承接 Rules 关系，不得改用普通机制落地关系替代；
4. 对模型基础规范和区段索引文档，检查其是否定义会影响事实实例编辑入口、模型实践子文档入口或 L2 场景入口的稳定规则；如存在，应通过对应基础规范、模型实践子文档或索引维护规则声明关系；
5. 将反向发现的 Rules 需求与当前 L0/L1/L2 Rules 文件对照，判断是否缺少入口、头部规范来源、维护边界、生效方式、压缩保护或 L2 引导；
6. 如发现 Rules 中存在 specs 未承接的长期原则、框架级约束、机制边界判断或跨环境复用规则，应创建或修改对应 specs 正式规范，不得继续只扩写 Rules；
7. 需要修改 Rules 文件时，只能加入必要入口摘要和权威 specs 引用，不得复制 specs 正文或把 Rules 文件变成第二事实源；
8. 需要新增、删除、重命名 Rules 文件，或改变 Rules 需求发现方式时，应评估 Human Gate 并记录 Change（依据 specs/22-Change-变更记录.md）

Rules 审计要求的落地必须遵循文档先行传导顺序：

1. 先在 specs 权威文档中定义判断标准、触发条件和检查要求；
2. 新的长期原则、框架级约束、机制边界判断或跨环境复用规则先回流到对应 specs 正式规范；
3. 再依据 specs 文档的机制落地关系或模型实践子文档，判断哪些 L0/L1/L2 Rules 入口需要同步；
4. 最后只在 Rules 文件中写入运行时入口摘要、必读提醒、压缩保护、场景触发提示或项目专属硬约束；
5. Rules 文件与 specs 文档冲突时，以 specs 权威文档为准，Rules 文件应回退为引用或摘要；
6. 后续 AI 维护 Rules 时，应先检查对应 specs 文档是否已有权威规则，未有权威规则时不得直接在 Rules 文件中创造新规则。

本文通过以下机制关系说明 Rules 相关机制实体的落地、同步、检查或审计触发条件。

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| Rules | `../.trae/rules/ldvh-l0-rules.md` | L0 工作区入口和项目识别规则 | 本文的 Rules 分层、L1 读取机制、Rules 变更流程或 Rules 文件头部要求变化时 |
| Rules | `../.trae/rules/ldvh-l0-fact-model-rules.md` | L0 事实实例编辑入口 | 本文的 L0 事实模型 Rules 定位、Rules 生效方式或 Rules 文件头部要求变化时 |
| Rules | `.trae/rules/ldvh-l1-rules.md` | LDVH 项目 L1 入口和 L2 引导 | 本文的 L1 职责、L1 读取机制、L2 引导或 Rules 变更流程变化时 |

### 6.6 规则设计约束

已拟使用 Rules 时，规则正文应短小、稳定、可检查、可引用。单个 Rules 文档正文有效内容不得超过 1000 字符；正文有效内容只统计承载行为约束、入口摘要、触发条件、压缩保护和权威引用的有意义文本，不统计标题、头部元数据、空行、表格分隔符、列表编号、Markdown 标记和纯格式字符。超过时应回到 specs 权威文档、Skill、Agent 或 Tools 承载细节，Rules 只保留入口摘要、触发条件、压缩保护和权威引用。跨机制选择依据本文 §5，本节不另行判断某项内容是否应优先进入 Rules、Skill 或 Agent。

规则正文不应包含：

1. 大段教程；
2. 完整 SOP；
3. 低频知识；
4. 长篇背景材料；
5. 工具使用手册全文；
6. 可由 Skill 按需加载的流程细节；
7. 可由 specs 正式规范承载的稳定规则正文；
8. 可由 references 承载的外部资料。

新增或修改 docs/、specs/、ldvh-base/ 关键入口时，应同步检查 L1 必读入口是否需要更新。

### 6.7 规则变更流程

规则变更执行时应按以下流程处理：

1. 判断变更对象属于规范层、L0、L1 还是 L2；
2. 判断是否触发 Human Gate；
3. 说明变更原因、影响范围和待修改文件；
4. 用户已批准的情况下修改对应规则文件；
5. 同步检查引用、必读入口、L2 引导和压缩保护；
6. 追加 Change 记录（依据 specs/22-Change-变更记录.md）；
7. 执行一致性检查。

## 7. Skill 机制规范

本节定义 LD Vibe Harness 如何使用 Trae Skill 机制承载可复用流程、标准化输入输出、轻量评估、契约式行动和受控写入入口。

Skill 是可复用专业能力说明书，不是事实源。LDVH 不在本节中定义具体 LDVH 标准 Skill 清单，也不把其他项目的标准 Skill 目录迁移为 LDVH 正式规则。

Skill 与其他机制的关系：

| 对象 | 关系 |
|---|---|
| Rules | Rules 可定义 Skill 触发入口；Skill 不替代 Rules |
| Agent | Skill 不调度 Agent；需要独立上下文时只能建议用户或主控使用 Agent，调度权必须交还主控 |
| Tools | Skill 可在授权流程中调用 Tools 执行确定性解析、校验、聚合、上下文准备或受控写入；Tools 不承载 Skill 的流程性判断 |
| 事实模型 | Skill 可按授权整理事实实例草案或编排受控写入流程，但对象字段和状态以 20-49 规范为准 |
| 行动模型 | Skill 的触发、执行和回写流程应服从 50-79 行动模型 |

### 7.1 Skill 内部设计检查

跨机制选择依据本文 §5，本节不另行判断某项内容是否应优先进入 Rules、Skill 或 Agent。已拟使用 Skill 时，应检查该 Skill 是否满足以下内部设计条件：

1. 可复用，不是一次性临时操作；
2. 存在多步骤流程或稳定分支判断；
3. 需要标准化输入、输出或写入格式；
4. 可在主上下文中执行；
5. 有明确事实源读取和回写边界；
6. 不承载 Human Gate 判断本身；
7. 不承载稳定规则正文；
8. 不承载完整教程或外部工具手册；
9. 具体对象流程已有事实模型规范、行动模型或模型实践子文档支撑；
10. 涉及 Rules、specs、事实模型、行动模型或 Human Gate 中已有约束时，应在 Skill 流程中列出适用入口、关键检查项或 STOP 点，作为执行提醒；Skill 不重新定义或复制稳定规则正文。

### 7.2 命名与部署边界

LDVH 提供的通用 Skill 应使用 `ldvh-` 前缀，避免与管辖项目业务 Skill 或外部 Skill 混淆。

命名规则：

| 项目 | 规则 |
|---|---|
| 目录名 | `.trae/skills/ldvh-{skill-name}/` |
| YAML `name` | 使用与目录一致的 `ldvh-{skill-name}` |
| 命名风格 | 小写字母、数字和连字符 |
| 禁止 | 不得使用其他项目前缀，不得绑定具体业务项目名 |

部署边界：

1. LDVH 通用 Skill 应部署在管辖项目 `.trae/skills/` 目录下，使用 `ldvh-` 前缀声明为全局可用，随项目一起版本管理；
2. 管辖项目业务 Skill 应部署在对应项目 `.trae/skills/` 位置，并不得使用 `ldvh-` 前缀；
3. Skill 实体文件是 Trae 执行入口，不替代 specs/、ldvh-base/ 或 docs/ 的事实源；
4. Skill 创建、修改、删除或迁移部署位置应评估 Human Gate；
5. 规范或模型实践子文档引用 Skill 实体路径时，应明确该路径归属哪个管辖项目，不得只写相对路径导致层级歧义。

使用边界：

1. Skill 是可被用户或 AI 主控应用的运行时流程入口；Skill 实体本身不自动授权事实源写入；
2. 应用 Skill 前，AI 应确认当前任务命中该 Skill 的触发条件，并读取 Skill 声明的必读事实源；
3. Skill 遇到 Human Gate 时必须暂停并按本文 §9 AskUserQuestion 规范确认，用户确认后才继续执行；
4. 用户选择暂停、暂缓或取消后，Skill 流程停止并等待后续指示；
5. Skill 输出的稳定结论、决策或写入结果必须回写 Git 文件事实源后才成为稳定事实。

#### 7.2.1 LDVH 通用 Skill 部署判断检查流程

判断某个 `ldvh-*` Skill 是否已部署或可调用时，AI 必须同时检查：

1. 本节部署边界原文；
2. 管辖项目 `.trae/skills/ldvh-{skill-name}/` 目录下存在 `SKILL.md`；
3. `SKILL.md` YAML `name` 与目录名一致；
4. 文件结构满足 §7.3 最小段落要求；
5. Skill 创建、迁移或部署在需 Human Gate 时已通过确认。

不得仅因其他项目级 `.trae/skills/ldvh-*` 目录存在，或聊天记忆称其存在，就判断 LDVH 通用 Skill 已部署或可调用。

### 7.3 Skill 文件结构要求

每个 Skill 至少应包含以下信息：

| 段落 | 要求 |
|---|---|
| YAML 头部 | 包含 `name` 和 `description`，description 应从 AI 视角描述触发时机 |
| 定位 | 说明 Skill 解决的问题和机制边界 |
| 触发条件 | 明确自动触发或人主动触发条件 |
| 不适用场景 | 明确不应调用该 Skill 的场景 |
| 必读文件 | 列出执行前必须读取的权威事实源 |
| 执行流程 | 步骤化流程，包含必要分支 |
| 规则强调 | 涉及既有 Rules 或 specs 约束时，列出适用入口、关键检查项或 STOP 点，不复制稳定规则正文 |
| 输出格式 | 明确结构化输出、写入结果和交还主控的下一步建议 |
| 交还主控 | 明确本流程结束后的建议动作、建议调度对象、所需输入和停止条件 |
| Human Gate | 明确遇到门禁时暂停并请求确认 |
| 事实源回写 | 明确哪些结果需要回写到 Git 文件事实源 |
| Agent 边界 | 明确 Skill 不调度 Agent |

Skill 必读文件中的路径必须区分 LDVH 项目规范、工作区规则和管辖项目事实源，不得用"当前项目"等模糊表述掩盖路径归属。

Skill 中的规则强调用于降低 AI 在流程执行中的遗漏风险。若某项约束已经存在于 Rules、specs、事实模型、行动模型或 Human Gate 规范中，且该 Skill 的触发、执行、写入、验证或停止条件会受到该约束影响，Skill 应在对应流程段落中以入口、检查项或 STOP 点形式显式提示。该提示不改变权威来源，不得与原规则冲突，也不得复制完整规范正文。

#### 7.3.1 Skill 内容引用原则

Skill 主体内容必须引用 specs 对应章节，不得在 Skill 文档中自成一派。具体要求：

1. **流程细节引用**：Skill 执行流程中涉及的规则、字段契约、状态机、Human Gate 条件和事实源回写要求，必须引用对应 specs 章节的标题和行号范围，不得在 Skill 中重新定义或复制；
2. **入口与检查项**：Skill 只写触发条件、必读文件、关键检查项和 STOP 点，不写完整规范正文；
3. **单一事实源**：当 Skill 文档与 specs 规范对同一事项有不同表述时，以 specs 规范为准；
4. **变更同步**：specs 规范变更后，引用该规范的 Skill 应同步更新引用位置，但不需要同步复制变更内容；
5. **禁止自定规则**：Skill 不得在引用之外新增规则、字段、状态或约束；如需新增，应先在 specs 中定义，再在 Skill 中引用。

属于事实模型或行动模型 `NN.02-Skill.md` 实践的 Skill，还应检查对应 `NN.04-Tools.md`、`NN.06-Contract.md`、Tools 能力缺失处理方式、需求变更同步关系和测试同步要求。

### 7.4 输出与事实源回写

Skill 输出应满足：

1. 明确输入来源；
2. 明确读取了哪些事实源；
3. 明确分析结论；
4. 明确建议动作；
5. 明确是否触发 Human Gate；
6. 明确哪些内容是事实、哪些内容是建议；
7. 涉及写入时列出待写入文件、写入原因和影响范围；
8. 写入后说明变更记录是否已追加（依据 specs/22-Change-变更记录.md）。

Skill 输出不是最终事实源。Skill 产生的稳定结论、任务、备忘、证据、决策或变更，必须写入对应 Git 文件事实源后才成为稳定事实。

#### 7.4.1 Skill 交还主控输出要求

Skill 只完成一个受控流程，不负责全局调度。每个 Skill 在流程结束、暂停、失败、需要 Human Gate、需要 Agent 或建议进入下一个 Skill 时，必须显式交还主控。

交还主控输出至少应说明：

1. **本流程结果**：completed / blocked / failed / needs_human / needs_agent / needs_next_skill；
2. **状态变化**：涉及事实对象时说明对象、原状态、新状态和是否已写回事实源；
3. **证据与产物**：列出文件、命令、验证结果、草案或其他可追溯输出；
4. **下一步建议**：说明建议主控执行什么动作、是否建议调用某个 Skill 或 Agent、建议理由、所需输入和预期输出；
5. **停止条件**：说明用户不同意、验证失败、事实源不满足、能力前提不存在或风险过高时应如何停止、退回或等待。

Skill 不得自行链式调用下一个 Skill，不得自行调用子 Agent，不得把"建议下一步"表述为已完成的调度。主控根据 Skill 输出决定继续、暂停、回退、触发 Human Gate、调度 Agent 或进入下一个 Skill。

### 7.5 Skill 与 Agent 边界

Skill 不得调度 Agent。Skill 发现以下情况时，应停止升级动作并提示用户或主控判断是否使用 Agent：

1. 主上下文难以承载所需事实源；
2. 需要不同角色独立形成结论；
3. 需要并行委派多个专业角色；
4. 需要与主上下文不同的权限边界；
5. 需要长期维护 Agent Prompt 或权限配置。

Skill 可在输出中说明"建议主控或用户评估是否使用 Agent 或进入对应行动模型"的理由，但不得自行创建、调用、编排、修改或删除 Agent。涉及子 Agent 流程的，应回到对应 Rules 入口和行动模型主文档，由主控依据该行动模型编排。

### 7.6 具体 Skill 清单原则

本文不维护 LDVH 标准 Skill 清单。具体 Skill 只有在满足以下条件后，才可进入模型实践子文档或实体定义：

1. 对应事实模型规范、行动模型或工具实践已稳定；
2. Skill 的输入、输出和事实源回写边界明确；
3. Skill 不复制 specs 正文或外部资料；
4. Skill 创建已通过 Human Gate；
5. 已记录变更（依据 specs/22-Change-变更记录.md）；
6. 已验证不会与管辖项目 Skill 或外部 Skill 命名冲突；
7. 涉及模型实践子文档时，已完成 Skill、Tools、Contract 和需求变更联动检查。

## 8. Agent 机制规范

本节定义 LD Vibe Harness 如何使用 Trae Agent 机制处理独立上下文、结论隔离、并行委派和不同权限边界场景。

Agent 是高级可选能力。LDVH 不默认要求创建 Agent，不在本节中维护推荐自建 Agent 清单，也不把其他项目的推荐自建 Agent 清单迁移为 LDVH 正式规则。

Agent 与其他机制的关系：

| 对象 | 关系 |
|---|---|
| Rules | Rules 可定义 Agent 创建、调用和 Human Gate 边界 |
| Skill | Skill 不调度 Agent，只能建议用户或主控判断是否使用 Agent |
| 行动模型 | Agent 调度、输入输出和事实回写应服从 50-79 行动模型 |

### 8.1 Agent 创建或调用治理检查

跨机制选择依据本文 §5，本节不另行判断某项内容是否应优先进入 Rules、Skill 或 Agent。已拟使用 Agent 时，应检查是否满足以下治理条件：

1. **独立上下文**：需要读取大量事实源，主上下文难以承载或容易污染当前任务；
2. **结论隔离**：需要不同角色独立形成判断，避免主上下文过早合并观点；
3. **并行委派**：需要多个专业角色并行分析或执行；
4. **不同权限边界**：需要与主上下文不同的权限范围；
5. **长期专业入口**：某类复杂审查、分析或执行场景高频出现，且已有稳定定义和边界。

Agent 治理检查还应确认：

1. 不是仅为单次简单问答或单文件小改创建 Agent；
2. 不用 Agent 承载稳定规范正文、项目事实源正文或完整教程；
3. 不是仅为了包装角色名称；
4. Agent 创建、修改、删除或权限调整已按 Human Gate 处理。

### 8.2 调度规则

Agent 应被动响应用户显式调用或主控编排，不得自行触发。

调度规则：

1. 用户可通过 Trae `@Agent` 显式调用已存在的 Agent；
2. SOLO Agent 或主控流程可在复杂任务中编排子 Agent；
3. 子 Agent 调度权只属于用户显式调用或主控编排，Skill、Tools、MCP、脚本或工具缓存不得直接发起子 Agent 调度；
4. 若某一行动模型已经定义子 Agent 流程入口，主控编排子 Agent 必须从该行动模型的 Rules 入口和主文档进入，不得由 Skill、Tools、MCP、脚本或工具缓存绕过入口直接发起；
5. Skill 不得调度 Agent；
6. Agent 默认不调度其他 Agent，除非其定义和主控授权明确允许；
7. Agent 默认只读分析，除非输入上下文明确授权写入；
8. Agent 发现 Human Gate 场景时必须标注并停止相关修改；
9. Agent 输出应返回主控或用户，由主控决定是否写回事实源、是否进入下一个 Skill、是否触发 Human Gate 或是否结束流程。

### 8.3 Agent 定义摘要单一事实源

Trae 平台中的 Agent Prompt 是运行入口。LDVH 中已确认创建或导入的 Agent，应在项目 Git 文件事实源中维护定义摘要，避免关键行为只存在于平台配置中。

Agent 定义摘要应至少包含：

| 字段 | 内容 |
|---|---|
| Agent 名称 | Trae 平台显示名称 |
| 英文标识 | 稳定英文标识 |
| 角色定位 | 覆盖项目、核心职责、调度方 |
| 触发场景 | 触发条件、触发频率、停止条件 |
| 分析关注点 | 必须分析的维度和输出判断项 |
| 职责边界 | 只读/写入权限、Human Gate、上下游影响 |
| 必读文档 | 执行前必须读取的权威事实源 |
| 输入输出 | 输入上下文要求和输出结构 |
| 权限范围 | 权限范围和高风险权限说明 |
| Prompt 来源 | Trae Prompt 与定义摘要的同步关系 |
| 维护状态 | active / deprecated / planned |

Agent 定义摘要和 Trae 平台 Prompt 不得形成两个互相冲突的事实源。Prompt 应尽量引用定义摘要作为权威来源，只保留角色入口、执行约束和输出格式等必要内容。

### 8.4 生命周期

#### 8.4.1 创建

1. 检查是否满足 Agent 创建或调用治理条件；
2. 说明为什么 Rules、Skill 或主上下文不足；
3. 说明拟创建 Agent 的角色、权限边界、触发方式和影响范围；
4. 触发 Human Gate 并等待用户确认；
5. 用户确认后在 Trae 中创建或导入 Agent；
6. 在 Git 文件事实源中维护 Agent 定义摘要；
7. 追加变更记录（依据 specs/22-Change-变更记录.md）。

#### 8.4.2 修改

1. 判断修改是否影响职责边界、触发条件、权限边界或 Prompt；
2. 涉及高影响变更时触发 Human Gate；
3. 同步修改 Trae 平台配置和 Git 文件定义摘要；
4. 检查引用和索引；
5. 追加变更记录（依据 specs/22-Change-变更记录.md）。

#### 8.4.3 删除或停用

1. 确认该 Agent 不再被流程、规则、Skill 或文档引用；
2. 触发 Human Gate；
3. 从 Trae 平台删除、禁用或停用 Agent；
4. 归档或更新 Git 文件定义摘要；
5. 更新引用和索引；
6. 追加变更记录（依据 specs/22-Change-变更记录.md）。

### 8.5 Agent 输出与事实源回写

Agent 输出不是最终事实源。Agent 输出中的分析、建议、证据、风险、任务拆分、决策建议或变更说明，只有写入对应 Git 文件事实源后才成为稳定事实。

回写规则：

1. specs 规范或 Rules 写入 specs/ 或 `.trae/rules/` 对应位置；
2. 任务、证据、变更、风险等结构化对象写入 `ldvh-base/`；
3. 管辖项目报告或审计结果写入 docs/；
4. 外部资料或 Agent 模板参考写入 specs/refs/；
5. Agent 输出与事实源冲突时，以 Git 文件事实源为准；
6. Agent 不得自行宣称任务完成，必须由主控或用户依据事实源和证据判断。

### 8.6 推荐清单处理原则

其他项目的推荐自建 Agent 清单、Trae 官方一键导入 Agent 示例和社区 Agent 模板，只能作为参考输入。LDVH 正式规范不得直接维护推荐自建 Agent 清单。

如未来确需建立 LDVH Agent 参考清单，应满足：

1. 放入 70-89 内部调研区或经确认进入正式规范；
2. 明确调研边界和执行效力；
3. 不表示已创建任何 Trae Agent；
4. 不替代 Agent 创建门槛和 Human Gate；
5. 不绑定具体业务项目或技术栈，除非进入管辖项目文档。

## 9. AskUserQuestion 使用规范

本节定义 Trae Solo 环境机制中 AskUserQuestion 工具在 LDVH 中的使用方式。

本文只定义 AskUserQuestion 工具在 LDVH 中的：

1. **何时触发**：什么场景应调用 AskUserQuestion；
2. **如何设计**：问题格式、选项设计、取消友好要求；
3. **取消后如何处理**：降级策略和禁止重复追问规则；
4. **如何传递给 AI**：通过 Rules、Skill 和规范文档让 AI 了解用法。

本文不重新定义 AskUserQuestion 的参数契约（见 `specs/refs/trae/08-内置AI工具.md`）、Trae IDE 的弹窗渲染逻辑、用户选择后 IDE 如何封装返回消息。

### 9.1 AskUserQuestion 工具定位

AskUserQuestion 是 Trae IDE 提供给 AI 的交互式问询工具，用于在关键决策点暂停 AI 执行，通过 UI 弹窗向用户展示选择题，用户点击选项后，选择结果返回给 AI，直接影响后续执行路径。

在 LDVH 中，AskUserQuestion 是实现 Human Gate 的首选技术方式。

### 9.2 参数契约摘要

AskUserQuestion 接收 `questions` 数组，每个问题包含以下字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `question` | string | 是 | 问题描述，以问号结尾 |
| `header` | string | 是 | 问题标签，chip/tag 显示，最多 12 字符 |
| `multiSelect` | boolean | 否 | 是否允许多选，默认 false |
| `options` | array | 是 | 选项列表，2-4 个选项 |

每个选项包含：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `label` | string | 是 | 选项显示文本，1-5 词 |
| `description` | string | 是 | 选项说明，解释选择后果 |

完整参数契约见 `specs/refs/trae/08-内置AI工具.md`。

约束条件：

| 约束 | 值 |
|---|---|
| 问题数量 | 1-4 个 |
| 选项数量 | 每个问题 2-4 个 |
| header 长度 | 最多 12 字符 |
| label 长度 | 1-5 词 |
| 选项互斥 | multiSelect: false 时只能选一个 |

### 9.3 触发场景

#### 9.3.1 Human Gate 实现

当行动模型规范、事实模型规范、项目 Rules 或当前任务语境定义 Human Gate 触发条件时，应通过 AskUserQuestion 实现用户确认。

当用户请求创建或修改事实源、执行 ADR 写入、事实对象状态流转、规范升级、高风险变更，或需要在 2-4 个互斥或可多选方案中选择时，AI 必须暂停拟执行动作并调用 AskUserQuestion；用户选择确认后才可继续执行，用户选择暂停、暂缓或取消后必须停止执行并等待后续指示。

触发场景示例：

| 场景 | 问询示例 |
|---|---|
| 创建新事实对象 | "即将创建 ADR-001，是否确认创建，或暂缓？" |
| 关键状态流转 | "将 Task-001 从 proposed 转为 accepted，是否确认，或暂缓？" |
| 删除事实对象 | "即将删除 Memo-003，是否确认删除，或暂停？" |
| 高风险操作 | "此变更影响 5 个文件，是否继续，或暂停？" |

#### 9.3.2 模式选择

当 AI 判断存在多种可行执行模式但难以取舍时，应通过 AskUserQuestion 交由用户选择。

示例（依据 51 §7.3）：

```text
header: "模式选择"
question: "难以判断是否需要升级，请选择执行模式："
options:
  - 轻量模式: 串行分析，共用上下文，快速得到结果
  - Agent 模式: 并行分析，独立上下文，结论隔离
  - 暂停讨论: 先详细说明差异，由用户决定
```

#### 9.3.3 技术选型

当存在多个可行技术方案且无明确最优解时，应通过 AskUserQuestion 交由用户选择。

示例：

```text
header: "技术选型"
question: "[技术点] 有多种方案，请选择："
options:
  - [方案 A]: [后果说明]
  - [方案 B]: [后果说明]
  - 暂缓讨论: 暂不决策，先详细说明差异
```

#### 9.3.4 高风险操作

当操作可能影响多个文件、模块或事实源时，应在执行前通过 AskUserQuestion 确认。

示例：

```text
header: "高风险"
question: "[操作描述]，影响 [N] 个文件，是否继续？"
options:
  - 继续: 执行操作
  - 暂停: 暂停执行
  - 查看影响详情: 先展示影响范围再决定
```

### 9.4 问询设计规范

#### 9.4.1 问题格式

| 规则 | 说明 |
|---|---|
| 以问号结尾 | question 字段必须以 `?` 或 `？` 结尾 |
| 场景前置 | 先描述场景，再提出问题 |
| 不含糊 | 问题应明确指向需要用户做的决策 |
| header 简洁 | 用 2-4 词概括问题类型，如"技术选型"、"方案确认"、"高风险" |

#### 9.4.2 选项设计

| 规则 | 说明 |
|---|---|
| 选项互斥 | 各选项之间不重叠，用户能明确区分 |
| 后果说明 | 每个选项的 description 必须说明选择后果 |
| 覆盖完整 | 确保选项覆盖所有合理选择，不要遗漏"取消"或"暂缓"选项 |
| 推荐标注 | 如需推荐某选项，应将推荐选项放在第一项，并在 label 末尾添加 "(推荐)" |
| 结构化决策 | 当问题可表达为 2-4 个互斥或可多选选项时，应使用 AskUserQuestion，不得以自由文本问句替代 |
| 数量适中 | 2-4 个选项，不超过 4 个 |

#### 9.4.3 取消友好

| 规则 | 说明 |
|---|---|
| 必含暂缓选项 | 每个问询必须包含"取消"、"暂缓"或"暂停"等效选项 |
| 避免二选一强迫 | 只有两个选项时，应增加第三选项（如"详细说明"或"暂缓"） |
| 取消即暂缓 | 将取消行为理解为"暂缓执行，等待用户主动指示" |

#### 9.4.4 输出与问询边界

以下内容应使用自由 Markdown 输出：

1. 分析报告、审计报告和整改建议表；
2. RoleSelectionOutput、MultiRoleReport、风险汇总和事实源回写建议；
3. 已完成执行结果、证据说明和检查结果。

以下内容必须使用 AskUserQuestion 承载，不得用自由文本问题替代：

1. Human Gate 暂停确认；
2. 模式选择；
3. 范围确认或范围修正；
4. 整改优先级或执行批次确认；
5. 其他 2-4 个互斥或可多选选项中的用户决策。

AI 不得在同一条自由 Markdown 报告中夹带本应由 AskUserQuestion 承载的选项询问。需要用户先选择模式、范围或优先级时，应先暂停执行并调用 AskUserQuestion；获得用户选择后，再输出报告或继续执行。

### 9.5 取消与降级处理

#### 9.5.1 取消信号识别

用户点击取消时，系统返回的 answer 为取消标识（实际验证中返回 `暂停`）。AI 应识别以下信号为取消：

| 返回值 | 含义 |
|---|---|
| `暂停` | 用户点击取消 |
| 其他取消标识 | 取决于平台实现 |

#### 9.5.2 降级策略

用户取消问询后，AI 必须遵循以下降级规则：

1. **不重复追问**：不得再次弹出相同或类似的问询；
2. **暂停执行**：输出"已暂停，等你进一步指示"或类似表述；
3. **等待用户指示**：由用户决定下一步，AI 不得自行继续；
4. **记录取消事件**：在证据或 Change 中记录用户取消行为（如适用）。

#### 9.5.3 禁止重复追问

AI 在以下情况下不得重复弹出 AskUserQuestion：

| 场景 | 禁止行为 |
|---|---|
| 用户已点击取消 | 不得再次弹出相同问询 |
| 用户已选择某选项 | 不得因"不满意"而重新弹出 |
| 用户已明确下一步指示 | 不得回到旧问询 |

### 9.6 跨 AI 知识传递

#### 9.6.1 问题描述

AskUserQuestion 是 Trae 平台特有工具，其他 AI 模型不具备此能力。即使在 Trae 平台内，不同 AI 模型也可能不了解此工具的存在和用法。因此，需要通过 LDVH 的知识传递机制让 AI 了解如何使用。

#### 9.6.2 知识传递路径

| 路径 | 机制 | AI 如何获知 |
|---|---|---|
| L0 Rules | 会话初始化时自动注入 | 平台自动注入 |
| Skill 模板 | 按需展开问询模板 | 语义匹配触发 |
| 规范文档引用 | AI 读取本文 §9 | 文件读取 |

#### 9.6.3 Rules 注入

L0 Rules 应承载 AskUserQuestion 使用要求。Rules 只写运行时入口摘要，不复制本文完整规则；入口摘要必须让 AI 知道需要执行 Human Gate 时应暂停动作并调用 AskUserQuestion 完成人类确认，而不是只提示"入口见 specs/11 §9"。L1/L2 Rules 不应重复维护与 L0 相同的 AskUserQuestion 通用规则，只在存在项目或场景专属约束时补充差异化要求。

```markdown
## Human Gate 实现

本工作区使用 Trae AskUserQuestion 工具承载 Human Gate 确认机制。需要 Human Gate 时，先暂停拟执行动作，用 AskUserQuestion 向用户确认；问题和选项按 `specs/11-LDVH-Trae-Solo-环境规范.md` §9.4 设计，必须包含暂停/暂缓选项；用户取消或选择暂停后，按 `specs/11-LDVH-Trae-Solo-环境规范.md` §9.5 停止执行并等待指示。触发场景见 `specs/11-LDVH-Trae-Solo-环境规范.md` §9.3。
```

L0 Rules 因字符上限需要压缩时，至少保留以下信息：

```text
Human Gate：用 AskUserQuestion 承载确认机制；当用户请求创建/修改事实源、执行 ADR 写入、事实对象状态流转、规范升级、高风险变更，或需要在 2-4 个互斥或可多选方案中选择时，先暂停拟执行动作并问询；确认后继续，暂停/暂缓/取消后停止等待；问询按 specs/11 §9.4，含暂停/暂缓；取消按 specs/11 §9.5 停止等待。
```

#### 9.6.4 Skill 模板

Skill 可提供结构化问询模板，降低 AI 构造参数的认知负担。Skill 模板应引用本文 §9.4（设计规范）和 §9.5（取消处理）。

#### 9.6.5 规范文档引用

当 AI 需要详细了解 AskUserQuestion 工具参数时，引导读取 `specs/refs/trae/08-内置AI工具.md`。

## 10. 其他 Trae Solo 工具规范

本节覆盖 LDVH 对 Trae Solo 其他工具的使用约束，工具本身的行为定义以 Trae 官方文档和 `specs/refs/trae/` 对应文件为准。

### 10.1 RunCommand

1. RunCommand 用于终端操作（git、npm、docker、build 脚本等），不用于文件读写操作；
2. 文件读写应使用专用工具（Read、Write、Edit 等），不得通过 RunCommand 调用 cat、sed、awk 等；
3. 长时间运行的服务器进程应使用非阻塞模式启动；
4. 破坏性命令（如 git push --force、rm -rf）不得执行，除非用户明确要求；
5. RunCommand 输出不是事实源；稳定结论必须回写 Git 文件事实源。

### 10.2 Schedule

1. Schedule 仅支持 cron 周期任务，不支持一次性定时或子分钟粒度；
2. 周期任务间隔不得少于 10 分钟；
3. Schedule 的 message 应从用户视角清晰描述任务目标和上下文；
4. Schedule 触发的执行结果不是事实源；稳定结论必须回写 Git 文件事实源。

### 10.3 MCP

1. MCP 工具的使用边界由对应管辖项目 L1 规则定义；
2. MCP 工具输出不是事实源；稳定结论必须回写 Git 文件事实源；
3. 涉及认证或私有服务的 MCP 调用，应检查是否有专用 Skill 或 MCP 工具提供认证访问，不得通过 RunCommand 或其他方式绕过认证。

## 11. 事实源回写原则

Rules、Skill、Agent 和 AskUserQuestion 运行过程中产生的信息按以下规则处理：

### 11.1 通用回写规则

1. Skill 输出、Agent 分析和临时计划默认都是过程信息；
2. 过程信息只有满足 `specs/10-事实源边界与承载规范.md` 的回写要求，并写入对应 Git 文件事实源后，才成为稳定事实；
3. 规则类事实应写入 specs/ 或 `.trae/rules/` 对应规则文件；
4. 结构化事实模型事实应写入 `ldvh-base/` 对应对象目录；
5. 管辖项目资料、报告或审计结果应写入 docs/；
6. 外部资料和第三方参考应写入 specs/refs/，不得直接作为 LDVH 强制规则；
7. Skill 或 Agent 的输出不得与 Git 文件事实源并行维护同一稳定事实。

### 11.2 规范判断必须回原文

AI 涉及机制、事实模型、状态机、部署边界、目录边界或规则归属判断时，必须先定位并读取对应正式规范原文，再结合当前实例状态判断。

1. 不得只凭聊天记忆、目录现状、工具输出或经验作出规范判断；
2. Rules、Skill、Agent 是运行时机制入口，不是稳定事实源；稳定事实必须回写 specs/、ldvh-base/、docs/ 等 Git 文件事实源；
3. 当发现依赖错误记忆、跳过规范原文、混淆层级或误判部署边界时，应将错误模式转化为可执行检查项；
4. 错误模式检查项必须包含触发场景、必读原文、检查顺序和停止条件；
5. 检查项未满足、必读原文未定位或当前实例状态无法确认时，必须停止规范判断，并转入补读、核查或 Human Gate。

### 11.3 Rules 特有回写

Rules 是 specs 正式规范的运行时投影。当 L0/L1/L2 Rules 中出现新的长期原则、框架级约束、机制边界判断或跨环境复用规则时，应先回流到对应 specs 正式规范，再由 Rules 保留摘要和规范引用。Rules 不得长期承载具有跨环境复用价值的框架级原则正文。

### 11.4 Skill 特有回写

Skill 输出不是最终事实源。Skill 产生的稳定结论、任务、备忘、证据、决策或变更，必须写入对应 Git 文件事实源后才成为稳定事实。涉及写入时应列出待写入文件、写入原因和影响范围，写入后说明变更记录是否已追加。

### 11.5 Agent 特有回写

Agent 输出不是最终事实源。Agent 输出中的分析、建议、证据、风险、任务拆分、决策建议或变更说明，只有写入对应 Git 文件事实源后才成为稳定事实。Agent 输出与事实源冲突时，以 Git 文件事实源为准。Agent 不得自行宣称任务完成，必须由主控或用户依据事实源和证据判断。

## 13. Human Gate 与检查要求

### 13.1 通用 Human Gate 触发场景

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变 11 系列规范编号和职责分工；
2. 创建、修改、删除或启用/禁用规则、Skill 或 Agent；
3. 调整 Agent 权限、可写文件范围、网络访问范围或可调用范围；
4. 将外部参考、Agent 输出、Skill 输出或工具缓存提升为稳定事实；
5. 在正式规范中新增具体 LDVH 标准 Skill 清单、自建 Agent 推荐清单或多角色矩阵；
6. 改变 Rules、Skill、Agent 与 LDVH 事实源边界、事实模型或行动模型之间的职责关系。

### 13.2 Rules 特有 Human Gate

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变 L0/L1/L2 规则文件；
2. 改变项目上下文识别、L1 读取机制或 L1 引导 L2 机制；
3. 改变规则唯一事实源归属；
4. 将教程、SOP、外部参考或工具输出提升为规则正文；
5. 改变 Git 提交规则、规则生效方式或高风险操作门禁；
6. 改变 Rules 与普通 specs 文档机制落地关系的维护方式。

### 13.3 Skill 特有 Human Gate

以下情况应评估 Human Gate：

1. 创建、修改、删除、重命名或启用/禁用 Skill；
2. 改变 Skill 部署位置、命名前缀或触发条件；
3. 将 Skill 输出提升为稳定事实但未回写 Git 文件事实源；
4. 允许 Skill 修改 Rules、specs 规范、Agent、跨项目契约或其他高影响资产；
5. 允许 Skill 调度 Agent；
6. 在正式规范中新增具体 LDVH 标准 Skill 清单。

### 13.4 Agent 特有 Human Gate

以下情况应评估 Human Gate：

1. 创建、导入、启用、停用、删除或重命名 Agent；
2. 修改 Agent Prompt、职责边界、触发方式或定义摘要；
3. 调整 Agent 权限边界、写入权限、网络权限或可调用范围；
4. 允许 Agent 调度其他 Agent；
5. 将 Agent 输出提升为稳定事实但未回写 Git 文件事实源；
6. 将推荐 Agent 清单正式化；
7. 删除或改变 Agent 定义摘要的权威位置。

### 13.5 AskUserQuestion 特有 Human Gate

新增或修改以下事项时，应评估 Human Gate：

1. 新增 AskUserQuestion 触发场景；
2. 修改降级策略或取消处理规则；
3. 在 L0 Rules 中新增、修改或移除 AskUserQuestion 通用运行时入口摘要。
