## 3. 事实模型的定义与定位

### 3.1 事实模型的定义

LDVH 事实模型是 LDVH 对工程生产事实的自定义建模，将项目中的意图、任务、决策、风险、依赖、证据、变更、产物、检查项和经验沉淀等内容，抽象为具有明确字段契约、状态流转和验收标准的结构化对象。

### 3.2 事实模型的核心特征

事实模型必须具备以下核心特征：

1. **规范由 LDVH 定义**：对象的准入条件、字段契约、状态流转、事实源边界和验收规则由 LDVH 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的事实实例属于项目，存放在该项目自身的 ldvh-base/ 目录中；每个接入 LDVH 的管辖项目应各自拥有 ldvh-base/ 目录，由该项目自身管理（依据 `specs/01-LDVH目录说明.md` §3.5）；
3. **服务工程生产**：对象用于让 AI、人和工具围绕同一组项目事实协作，支持任务拆解、状态追踪、证据回写、决策追溯和变更审计；
4. **Git 可追溯**：事实实例必须以 Git 可追踪文件的形式承载，优先使用 YAML 格式（适合结构化字段）或 Markdown 格式（适合说明性内容）；
5. **单一事实源**：每个事实实例只能有一个权威承载位置，其他位置只能引用或聚合，不得复制并维护独立事实。

### 3.3 事实模型与临时信息的区别

| 维度 | 临时信息 | 事实模型 |
|---|---|---|
| 性质 | 执行过程中的局部选择、临时判断、聊天内容 | 结构化、可追溯、可验证的工程事实 |
| 持续时间 | 一次性，仅在当前执行上下文中有效 | 长期，可跨会话、跨执行轮次追踪 |
| 复用价值 | 无，仅服务当前执行 | 有，可被其他对象引用、可被 AI 后续执行参考 |
| 追踪需求 | 不需要独立追踪 | 需要独立追踪、状态流转和验收标准 |
| 承载位置 | 聊天记忆、工具缓存、命令输出等临时位置 | Git 文件事实源（specs/、ldvh-base/、docs/ 等） |

## 4. 事实模型

### 4.1 事实模型定义

事实模型是 LDVH 对某一类工程生产事实的标准化建模结构，用于统一描述该对象的对象定位、准入条件、事实源边界、状态机、对象关系、Human Gate、字段契约、事实源回写要求、证据留存要求、AI 协作、Tools 契约式校验与执行、Web 信息同步、落地前决策、价值与要素审查、落地初始化、落地审计、合规检查和待补齐事项。

每个 21-49 具体事实模型规范，都是一个具体事实模型的定义文档。

### 4.2 事实模型的标准组成

一个事实模型应包含以下内容：

1. 对象定位与准入条件；
2. 事实源边界；
3. 状态机；
4. 与其他对象的关系；
5. Human Gate；
6. 字段契约；
7. 事实源回写要求；
8. 证据留存要求；
9. AI 协作适配；
10. Tools 契约式校验与执行适配；
11. Web 信息同步适配；
12. 附件型实践子文档按需拆分规则；
13. 落地前决策；
14. 价值与要素审查；
15. 落地初始化；
16. 落地审计；
17. 合规检查；
18. 待补齐事项。

### 4.3 事实模型与事实实例

事实模型定义事实类别的规则，事实实例是项目中按事实模型创建的具体事实。

事实模型承载于 `specs/20-49`，事实实例承载于 `ldvh-base/`。模型不得承载具体实例状态，实例不得重新定义模型规则。

### 4.4 事实模型与行动模型

事实模型承载工程生产事实，行动模型控制 AI 如何行动。两者关系如下：

| 维度 | 事实模型 | 行动模型 |
|---|---|---|
| 核心问题 | 项目事实如何结构化、流转和沉淀 | AI 如何读取、判断、执行、停下和回写 |
| 规范区段 | `specs/20-49` | `specs/50-79` |
| 实例事实 | 事实实例承载于 `ldvh-base/` | 行动执行结果按事实类型回写 |
| 关键约束 | 准入、字段、状态机、验收和对象关系 | Context、Scenario、Gate、回写、证据 |

行动模型可以创建、更新、检查或引用事实模型，但不得重新定义事实模型字段、状态机、验收标准或事实实例事实源边界。事实模型可以被行动模型创建、更新、检查或引用，但事实模型规范不得定义行动模型的 Context、Scenario、Gate、执行流程或事实源回写规则。

### 4.5 事实模型与工具实现

工具可以依据事实模型开发解析、校验、聚合、展示和受控写入能力。工具实现不得替代事实模型本身，也不得绕过模型定义的事实源边界和 Human Gate。

### 4.6 事实模型文件命名与附件型实践子文档

适用区段：事实模型（specs/20-49）。

21-49 主文件均为事实模型规范，文件名不重复"事实模型规范"字样，格式为：

```text
NN-{英文名}-{中文名}.md
```

事实模型主文档必须完整定义事实模型。事实模型附件型实践子文档用于在主模型完整定义后，按需承接某个事实模型围绕 Rules、Skill、Agent、Tools 和 Web 的机制实践内容。附件型实践子文档不重新定义事实模型，不是模型完整性的默认要求，不得为空占位。

具体事实模型规范应在主文档中定义字段规则、状态规则、验收规则和实例检查要求。依据 `specs/04-LDVH模型子文档规范.md` §4.2，规范模型完成落地初始化时，必须为 NN.01 至 NN.06 六个子文档槽位形成显式结论，对应子文档文件必须存在，状态为 active、active-prep 或 not-created 之一。not-created 状态不表示不创建子文档文件，该子文档文件仍需存在以说明不创建理由和检查项。主文档应保留摘要、适用条件和引用，不得把模型核心规则迁移到子文档中。

附件型实践子文档的分类、命名、状态骨架和契约子文档规则依据 `specs/04-LDVH模型子文档规范.md`，本文不重复维护。

### 4.7 落地前决策、价值与要素审查、落地初始化、落地审计与合规检查

事实模型规范应按需要定义落地前决策、价值与要素审查、落地初始化、落地审计和合规检查要求。落地前决策用于判断某一事实模型在具体项目中需要落地哪些 Rules、Skill、Agent、Tools、Web、契约或附件型实践子文档，并同时判断该事实模型进入项目实践时的读取策略和写入策略。落地前决策不是落地初始化，不表示对应实践已经存在。

落地前决策中的读取策略至少应说明 AI、人、Tools 和 Web 在什么场景需要读取该事实模型、读取哪些事实源、如何筛选有效状态、读取结果如何作为执行依据或历史参考，以及读取后发现缺口、冲突或需变更时如何分流到创建、更新、升级、废弃、推翻或其他后续流程。

落地前决策中的写入策略至少应说明该事实模型在什么场景允许创建、更新、状态流转、关联回写、废弃、推翻、升级或记录 Change（依据 specs/22-Change-变更记录.md），哪些写入必须触发 Human Gate，哪些写入可由 Tools 承接受控执行，哪些写入需由 AI 或人按规范人工完成，以及 Tools 能力缺失时的降级方式和记录要求。

落地前决策完成后、实际落地初始化开始前，必须依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §4.3 执行价值与要素审查。事实模型特定的审查要点：

1. 是否仍以 AI 执行者为第一服务对象，帮助 AI 读取事实源、创建和更新事实实例、触发 Human Gate 和回写事实；

价值与要素审查的结论应成为落地初始化的前置输入。审查不通过时，应回到落地前决策修正方案、标记暂缓或停止落地；不得直接进入初始化。

落地初始化应说明在落地前决策和价值与要素审查完成后，该事实模型进入项目实践时需要实际创建或确认的目录、实例命名规则、索引引用、读取入口、写入入口、状态适用规则、Rules 摘要、Skill、Agent、Tools、Web、契约、初始化产物、暂缓项和 Human Gate。涉及 Skill、Tools、Web 或 Contract 的，应依据 `specs/04-LDVH模型子文档规范.md` §8检查显式消费关系、需求变更同步、Tools 测试同步和未完成同步缺口。若事实模型主流程或 Skill 流程包含读取、筛选、查询、统计、校验、创建、更新、状态流转、关联回写或 Change 记录生成（依据 specs/22-Change-变更记录.md）等可机械化步骤，还应检查 `NN.04-Tools.md` 和 Tools 实现是否具备对应只读查询、契约校验或受控写入能力；缺失时必须进入暂缓项或待补齐事项，不得声称 Tools 实践完整支撑落地初始化。落地初始化完成后，应遍历工作区所有 Git 仓库，对每个因本次落地初始化产生文件修改的仓库执行 commit，确保跨仓库变更完整记录为 Change 事实实例（依据 specs/22-Change-变更记录.md）。

落地审计应说明如何审查该事实模型的实践是否真实落地、持续有效、与 Git 文件事实源一致、未绕过 Human Gate，并识别初始化缺口、过期实践和需要整改的附件型实践子文档。落地审计还应检查跨仓库 commit 完整性：任务涉及的所有 Git 仓库是否均已提交，是否存在遗漏提交的仓库。

合规检查应说明事实模型规范写作、事实实例字段、状态流转、关系引用、事实源边界、事实源回写、证据留存、Human Gate、AI 协作适配、Tools 契约式校验与执行和 Web 信息同步是否符合本事实模型和上位规范。

### 4.8 完整方案形成流程

事实模型完整方案按以下顺序形成：

1. 创建或更新 `NN` 主文件，完整定义事实模型；
2. 定义实例事实源位置、字段契约、状态机、关系规则、Human Gate、事实源回写要求、证据留存要求、AI 协作适配、Tools 契约式校验与执行适配和 Web 信息同步适配；
3. 定义落地前决策、价值与要素审查、落地初始化计划、落地审计要求和合规检查标准；
4. 在落地前决策中同时定义读取策略和写入策略，说明读取入口、有效状态筛选、读取后分流、写入入口、Human Gate、Tools 能力和降级边界；
5. 判断 Rules、Skill、Agent、Tools、Web 或 Contract 实践是否复杂到需要独立维护；
6. 完成落地前决策后，依据 00 总纲执行价值与要素审查；
7. 确保六个子文档槽位均已形成显式结论，对应子文档文件存在且状态为 active、active-prep 或 not-created 之一（依据 `specs/04-LDVH模型子文档规范.md` §4.2、§6）；
8. 涉及 Skill、Tools、Web 或 Contract 的，依据 `specs/04-LDVH模型子文档规范.md` §8完成联动检查；
9. 修改规范、附件型实践子文档、协作机制或实例事实源时记录 Change（依据 specs/22-Change-变更记录.md）

## 6. 事实模型准入与分类原则

### 6.1 对象分类原则

LDVH 事实模型可按治理用途分为以下几类：

1. **核心执行实体**：最小可执行、可追踪、可验证、可关闭的对象；
2. **意图和入口**：承载人的目标、范围、成功标准和约束，以及未任务化但有保留价值的输入；
3. **决策和风险**：已确认的决策记录、已识别的风险、前置条件或外部约束；
4. **支撑和记录**：执行摘要、验证结果、关闭证据、验收记录、可引用产物、检查项、变更记录和踩坑经验。

### 6.2 对象清单归属

具体事实模型清单、编号归属、维护状态和区段关系由 `specs/20-事实模型集合索引.md` 维护。本文只定义事实模型的通用分类和准入原则。

### 6.3 预留编号区段

编号区段 33-49 预留用于未来新增事实模型，不得未经 Human Gate 确认提前占用。

### 6.4 准入条件原则

一个内容需要满足以下条件之一，才应成为事实模型：

1. **需要独立追踪状态**：该内容有明确的状态流转，需要跨会话或跨执行轮次追踪；
2. **需要可验证的完成标准**：该内容有明确的验收条件，需要验证是否完成；
3. **需要关闭证据**：该内容完成后需要记录证据，供后续追溯或审计；
4. **需要关联其他对象**：该内容需要被其他对象引用，或引用其他对象；
5. **需要被 Web 信息同步，或被 Tools 排序、过滤、聚合或审计**：该内容需要被 Web 或 Tools 处理，以降低人和 AI 的维护成本；
6. **不成为事实模型就会导致进度、责任、完成标准或验证结果不可追踪**：该内容如果不结构化，就会导致项目事实漂移或不可追溯。

不满足以上条件的内容，应按其性质分流：
- 可以在当前对话中直接回答或处理的信息 → 留在聊天记忆中，不写入事实源；
- 已有明确目标和完成标准，但不需要独立追踪 → 作为现有 Task 的子步骤，不单独创建对象；
- 属于现有对象的属性、关系、检查项或输出路径 → 写入现有对象字段或模板，不单独创建事实模型；
- 属于长期规则或决策，但不需要独立状态机 → 写入 specs/ 或 .trae/rules/；
- 属于项目背景或参考资料 → 写入 docs/ 或 specs/refs/；
- 属于路线规划、阶段说明或产品方向共识 → 优先写入 Markdown 文档或 evals 入口；
- 属于临时执行策略 → 留在当前执行上下文中。

## 7. 事实模型的通用规范

### 7.1 事实源边界原则

事实模型的事实源边界依据 `specs/10-事实源边界与承载规范.md` 定义的原则执行，本文不重复维护。事实模型的适配说明如下：

1. **介质选择适配**：依据 10 §6，事实实例优先使用 YAML 格式承载（适合任务、状态、结构化关系和审计字段），说明性内容可使用 Markdown 格式；
2. **目录归属适配**：依据 10 §8 和 `specs/01-LDVH目录说明.md` §3.2，事实模型规范承载于 specs/20-49，事实实例承载于 ldvh-base/，管辖项目资料承载于 docs/，外部资料承载于 specs/refs/。

### 7.2 状态流转原则

事实模型的状态流转遵循以下原则：

1. **状态变更先于执行**：执行者在执行对象相关操作时，必须同步更新事实源中的对象状态；
2. **终态不可重开**：对象进入终态后，不得直接重开；如需重新处理，必须新建对象承接；
3. **状态流转可追溯**：状态变更必须留下可追溯的记录，包括变更时间、变更人和变更原因；
4. **Human Gate 触发原则**：关键状态流转必须触发 Human Gate，等待人类确认后方可继续。

### 7.3 字段契约原则

事实模型的字段契约遵循以下原则：

1. **基础字段对齐**：所有事实模型应包含基础字段（id、type、title、status、created、updated）；
2. **扩展字段明确**：具体事实模型的扩展字段由该事实模型的规范明确定义，包括字段名、类型、是否必填、约束条件；
3. **字段语义一致**：相同字段名在不同对象中的语义应保持一致；
4. **引用完整性**：引用其他对象的字段应确保引用的对象存在且有效。

### 7.4 检查标准原则

事实模型的检查标准遵循以下原则：

1. **可验证**：检查标准必须是可验证的，不能是模糊的主观判断；
2. **明确**：检查标准必须明确，不能有歧义；
3. **可追溯**：检查完成后必须记录检查证据，包括检查时间、检查人和检查结果；
4. **按对象性质选择检查类型**：以完成为目标的对象应定义验收标准；不以完成为目标的对象应定义检查要求；
5. **检查要求进入主文件**：合规检查标准、落地初始化计划和落地审计要求应在具体事实模型主文件中定义；附件型实践子文档只承接复杂机制实践的展开内容，不承载事实模型核心检查标准。

### 7.5 AI 协作适配原则

AI 协作适配定义 AI 如何读取、创建、更新和检查事实模型。AI 协作适配遵循以下原则：

1. **按事实源读取**：AI 读取事实实例时必须按事实源边界读取，不依赖聊天记忆、工具缓存或数据库派生视图；
2. **按规范创建**：AI 创建事实实例时必须按事实模型规范的字段契约创建，不得自行添加、省略或修改字段；
3. **按状态机更新**：AI 更新事实实例时必须按事实模型规范的状态机流转，状态变更先于执行；
4. **按验收标准检查**：AI 检查事实实例时必须按事实模型规范的验收标准检查，检查结果留存证据；
5. **不得绕过规范**：AI 不得绕过事实模型规范定义的字段契约、状态机、验收标准或事实源边界；
6. **Human Gate 评估**：AI 创建、更新或删除关键事实实例时，应评估是否需要触发 Human Gate；
7. **机制回指**：AI 协作适配中涉及 Rules、Skill、Agent 的使用边界，必须回指 `specs/11-LDVH-AI协作规范.md` 及其子文档。

### 7.6 事实源回写适配原则

AI 完成执行后的事实源回写，依据 `specs/10-事实源边界与承载规范.md` §7定义的回写条件执行，本文不重复维护。事实模型的适配说明如下：

1. **事实实例回写触发**：AI 按行动模型执行完毕后，应判断执行结果是否需要创建或更新事实实例；若需要，必须按 10 §7回写；
2. **回写与 Gate 联动**：关键事实实例的创建和更新应评估 Human Gate，依据本文、具体事实模型规范和相关基础规范判断；
3. **回写验证**：事实实例回写后应验证字段完整性、状态合法性和引用完整性；
4. **机制输出回写**：Skill 或 Agent 输出只有写入对应 Git 文件事实源后才成为稳定事实实例；
5. **报告回写分流**：审计报告、分析报告或管辖项目资料应按 02、03 和具体事实模型规范判断进入 docs/、ldvh-base/或 specs/。

### 7.7 证据留存适配原则

事实模型的证据留存遵循以下原则：

1. **对象创建留证**：对象创建时应记录创建原因、创建者和创建依据；
2. **状态变更留证**：状态变更时应记录变更时间、变更人、变更原因和变更前状态；
3. **验收检查留证**：验收检查时应记录检查时间、检查人、检查结果和检查证据；
4. **Human Gate 确认留证**：Human Gate 确认时应记录确认事项、确认人和确认结果；
5. **过程信息不冒充事实**：聊天、临时分析、命令输出和 Agent 输出不得直接冒充稳定证据；
6. **关闭前可追溯**：涉及任务、审计或 Review 的对象，在关闭前应能追溯关键证据。

## 8. 与 20-49 具体事实模型规范的关系

### 8.1 20 事实模型集合索引

20 是事实模型集合索引，不定义事实模型字段、状态机、模型实践子文档或行动流程，只提供该区段内文档的清单、关系映射、状态、升级结论、降级结论和维护信息。

### 8.2 21-49 具体事实模型规范

21-49 是具体事实模型规范，每个规范定义一个具体事实模型。具体事实模型规范应依据 §4.2 定义的事实模型标准组成展开，并在具体事实模型语境下定义更具体的事实模型规则。

具体事实模型规范不得在缺少说明的情况下省略 §4.2 中的标准组成；如某一组成项暂不适用或待补齐，应在对应章节说明原因或进入待补齐事项。

### 8.3 关系原则

本文与 20-49 具体事实模型规范的关系遵循以下原则：
1. 本文定义事实模型的通用规则和事实模型的标准组成，20-49 定义具体事实模型；
2. 具体事实模型规范不得与本文的通用规则矛盾；
3. 具体事实模型规范可以在本文的通用规则基础上，定义更具体的规则；
4. 发生冲突时，以本文的通用规则为准，除非具体事实模型规范明确说明例外情况并经 Human Gate 确认。

## 9. Human Gate 与检查要求

### 9.1 Human Gate 触发条件

以下情况应评估 Human Gate：
1. 新增事实模型；
2. 删除事实模型；
3. 重命名事实模型；
4. 重排事实模型编号区段；
5. 改变事实模型的通用规则；
6. 改变事实模型的事实源边界原则；
7. 将原本不属于事实模型的内容升级为事实模型；
8. 将原本属于事实模型的内容降级为非事实模型；
9. 改变事实模型的标准组成；
10. 新增、删除、重命名或改变事实模型附件型实践子文档；
11. 改变 AI 协作适配边界（AI 如何创建、更新、检查事实模型）；
12. 改变事实模型与行动模型的交互边界；
13. 改变检查要求的执行边界。

当 AI 识别到上述情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。

### 9.2 检查要求

事实模型规范写作检查至少包括：
| 检查项 | 标准 |
|---|---|
| 上位依据 | 已声明上位依据 |
| 对象定位 | 头部定位、适用范围、上位依据和相关规范清晰 |
| 引用纪律 | 未复制其他权威文档的规则正文 |
| 架构术语一致性 | 与五类构成要素、事实模型和行动模型术语一致 |
| 模型组成 | 具体事实模型规范覆盖事实模型的标准组成，缺项已说明原因 |
| 附件型实践子文档 | 已说明是否需要附件型实践子文档；如创建，已确认按需、非空、不替代主模型且经 Human Gate |
| 落地前决策 | 已定义实际初始化前需要完成的落地范围、暂缓项和 Human Gate 决策 |
| 价值与要素审查 | 已说明落地前决策后需依据 00 总纲审查价值实现标准和五类构成要素边界 |
| 落地初始化 | 已按需要定义设计进入实践的初始化计划、初始化产物和暂缓项 |
| 落地审计 | 已按需要定义实践是否真实落地并持续有效的审计要求 |
| 合规检查 | 已定义事实模型规范写作、实例字段、状态流转、事实源回写、证据留存和事实源边界的符合性检查标准 |
| 文件命名 | 主文件和附件型实践子文档命名符合 §4.6，未重复维护区段性质或对象归属 |
| 事实源边界 | 符合 `specs/10-事实源边界与承载规范.md` 的事实源边界原则 |
| 目录归属 | 符合 `specs/01-LDVH目录说明.md` 的目录规划 |
| AI 协作适配 | AI 读取、创建、更新和检查事实实例的规则符合 11 系列规范和本文 §7.5 |
| 事实源回写 | AI 创建或更新事实实例后的回写符合 10 事实源边界原则和本文 §7.6 |
| 证据留存 | 对象创建、状态变更、验收检查和 Human Gate 确认有可追溯证据要求，符合本文 §7.7 |
