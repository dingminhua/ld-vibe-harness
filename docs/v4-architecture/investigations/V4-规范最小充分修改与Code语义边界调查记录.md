# V4 规范最小充分修改与 Code 语义边界调查记录

> 记录性质：本文是本次规范治理调整的调查与复核依据，不是规则源，不建立审计规范、状态机或中央登记。
> 核验日期：2026-07-16。

## 1. 本次问题

本次调查回答三个问题：

1. 修改现有规范时，谁负责判断规范增量是否最小、充分并归入正确责任；
2. Code 可以检查哪些越界风险，哪些语义判断仍必须由 AI 完成；
3. tests 可以固定哪些边界，如何避免 tests 反向成为规则来源。

## 2. 当前规则源的覆盖情况

### 2.1 00 无需修改

00 已经确定 Human、AI、Code 的根级分工：Human 决定只能由 Human 决定的意图和重大取舍；AI 负责理解来源、判断适用性、规划、实施与复核；Code 只执行来源已经定义且可以确定性处理的能力，不重新解释规则语义。它同时要求能力和完成声明不得超出实际证据。

这些上位原则足以支持本次调整。继续向 00 加入规范最小增量、Code review 或测试设计细节，会把普通规范责任重新上提并增加根规范负担，因此 00 保持不变。

### 2.2 01 已定义新建与责任调整，但存量修改入口不够明确

01 §13 已经要求候选规则逐条对照现有来源、移除重复内容、比较承载位置并独立复核，也已说明在既有责任内补充具体规则不等于实质改变责任。

当前缺口不是缺少新的治理体系，而是缺少两个明确入口：

1. AI 修改现有规范前，应先判断能否由现有责任以最小充分增量承接；
2. 出现重复、冲突、错误承载等信号时，AI 应对明确范围复核，并保留未检查范围，不能把局部检查扩大为全量结论。

这两项属于 01 的规范模型治理责任，应在 §13、§13.5 和对应验证要求中收敛，不新增独立审计规范。

### 2.3 07 已禁止 Code 和 tests 成为语义来源，但审核动作不够明确

07 已经规定来源规范或外部契约定义领域与外部语义，Code 类型、validator 和 tests 都不能取得语义权威；测试结论也只能覆盖实际检查范围。

当前缺口是：当 Code 把机械结果提升为来源未定义的语义结论时，尚未明确要求 AI 在设计和复核中主动识别这种越权；tests 也需要更直接地限定为只固定正式来源已经定义的可观察边界。

这些要求属于 07 的 Code 实践和测试责任，不应进入 04 的 Helper 字段定义，也不需要修改生产 Code。

## 3. 职责划分

| 对象 | 应承担的责任 | 不应承担的责任 |
|---|---|---|
| Human | 决定业务意图、不可逆承诺和来源保留给 Human 的重大取舍 | 替 AI 完成规范去重、责任归口和最小方案证明 |
| AI | 判断候选规则是否重复、是否由现有责任承接、规范增量是否最小充分；审核 Code 是否越过来源语义边界；独立复核并保留未检查范围 | 把局部复核声称为全量保障，或用评审意见代替正式规则源 |
| Code | 检查来源已定义的精确身份、结构、关系、引用、确定性条件和可观察结果；报告未实现或无法判断的范围 | 判断自然语言语义等价、规范责任重复、最小承载位置或规则适用性；把候选结果升级为来源未定义的结论 |
| tests | 验证来源已经定义的可观察行为、边界、失败路径和证据范围 | 通过断言、fixture、快照或关键词规则创造新的业务语义、授权语义或规范责任 |

Code 应接受越权审核，但审核责任属于 AI。Code 本身无需判断本地规范修改是否为最小增量，也不得为此引入关键词、相似度、段落摘要或其它语义近似规则。

| 07 的职责、语义边界、测试边界与验证要求 | 最小修改 | 负责 Code 设计、审核和 tests 的共同工程边界 |

| 新审计规范、状态机或中央登记 | 不建立 | 会扩大治理面，并把本可由既有责任承接的要求独立化 |

## 5. Code 现状复核

对当前规范仓库、结构检查、规范内容读取和规则快照路径的静态复核表明：

1. 规范仓库把尚未实现的语义条件保留为未检查范围；
2. 结构检查只验证文档结构，不解释正文语义；
3. L3/L4 内容读取执行精确选择和机械标题边界，不判断规则适用性；
4. 规则快照只证明来源集合与内容完整性，不执行语义审计。

因此本次不修改生产 Code。新增 tests 只防止以后把语义重复、责任归口或来源未定义的判断下沉到 Code。

## 6. 修改与验证方案

1. 保持 00、04、普通规范模板、Helper 字段和生产 Code 不变；
2. 在 01 中明确 AI 对现有规范最小充分增量、责任归口和有范围独立复核的责任；
3. 在 07 中明确 AI 对 Code 语义越权的审核责任，以及 tests 只能固定正式来源已定义的可观察边界；
4. 增加具有独立失败价值的最小负向 tests，证明机械检查不会因语义相似或冲突措辞生成语义结论，并在既有快照测试中保留未检查条件；
5. 修改完成后进行独立 POST 审核，并运行聚焦测试、全量测试、格式检查和变更范围检查。

## 7. 结论边界

本次结论只覆盖 01、07 及当前检查到的规范仓库、结构检查、内容读取和规则快照路径，不证明所有未来 Code 都不会越权。以后出现规则选择、授权、状态推断、语义汇总、完成声明、回退或跨来源聚合增量时，仍须依据正式来源重新审核。

调查记录和复核意见不取得规则效力。只有进入正式规范正文的要求才约束后续实现与测试。

## 8. POST 审核与验证结果

修改完成后，三名独立审核者分别复核了 01 的责任归口与中文表达、07 的 Code/tests 语义边界和新增测试。首轮审核发现 01 的非语义编辑豁免与证据分层不够清楚，以及 tests 使用中文关键词排除语义诊断、可能被换词绕过；相应内容收窄后，三名审核者均确认通过。全量测试额外发现一处既有测试夹具使用固定日期，已经改为相对实际 `created_at` 生成合法 `updated_at`，补充审核确认没有放宽生产校验。

按后续确认重新限定 POST 范围后，独立审核发现“文本候选”和“机械候选”仍可能诱导语义审计 Code，因此进一步禁止 Code 生成、筛选、评分、诊断或建议语义候选，并明确 AI 判断发生在 Code 之外。四组新增测试经独立失败价值比较后，收敛为三个独立测试和一个加入既有快照集成测试的断言；重复的常量、关键词和无专属触发条件断言已经删除。

最终验证结果：

1. 聚焦测试：42 项通过；
2. 全量测试：802 项通过，10 项原生 Windows 测试按既有平台标记跳过；
3. Ruff：147 个 Python 文件 lint 与格式检查通过；
4. `git diff --check` 通过；
5. 变更范围只包括本文、01、07 和 tests；00、04、普通规范模板、Helper 字段及生产 Code 未修改。

## 9. 下位 Specs、生产 Code 与 tests 一致性收口

2026-07-16 在前述规则激活和 V3 历史边界收敛后，又对三层实际状态进行逐层回读。本节只记录当次检查范围和收口结论，不把调查记录提升为规则源。

### 9.1 下位 Specs

检查范围覆盖当前 active 的 02–09、20–24、30–33 及四份授权附件。下位来源继续遵守同一分工：02 只解析管辖事实；03 保留来源和 Git 可追踪性；04 只组织公开服务与机械结果；05 和 20–24 明确把对象化、语义相关、证据充分和生命周期成立性留给 AI/Human；06 只提供模板机械候选和内容；08、09 约束 Web 与环境薄适配，不把实现或 tests 变成领域权威。

未发现下位来源要求 Code 判断规范语义重复、责任归口、最小充分性或自然语言适用性，也未发现下位来源授权 tests 通过关键词、快照或自建算法补造语义。Web direct capture 的 `exact_duplicate` 是 08/20 明确定义的字节级身份结果，不是 Code 自行扩张的语义查重。

### 9.2 生产 Code

静态复核覆盖规范发现与结构检查、规范候选与内容读取、管辖解析、事实候选/读取/创建/更新、行动模板读取、Web direct capture、提交契约和 V3 历史调查模块。当前实现只处理来源已定义的身份、结构、闭集、引用、关系、固定转换和精确内容结果；未使用关键词相似度、语义评分、模型调用或其它启发式机制判断规范重复、责任归口和最小增量。

实现中出现的 duplicate 检查均有确定性对象：JSON/YAML key、机器身份、路径、声明 key、精确 capture identity 或来源定义的结构关系。无法机械证明的自然语言条件继续进入 unchecked、gap、unavailable 或显式 AI 复核边界。生产 Code 因此无需修改。

### 9.3 tests

审核发现的直接偏差已收敛：删除了 tests 内第二套 Web canonicalization 和规范中文文案清单；规范候选与管辖请求测试不再切割原文证明语义；规范内容的披露说明只检查来源定义的层级、来源对应和非空边界，不再固定当前中文措辞。生产实现的固定向量、非法输入、精确来源、事务失败和越权最小反例仍由各自唯一测试保留。

其余跨层重复、全局组合快照、V3 历史测试耗时、字段登记样板和 Specs fixture 成本没有发现会改变当前规则语义或掩盖生产越权，已经单独记录在 `V4-Code与tests存量膨胀后续问题.md`。这些项目只按后续实际维护或反馈成本触发，不阻塞当前主路线。

### 9.4 结论边界

在上述实际检查范围内，下位 Specs、生产 Code 与 tests 已对齐：规则语义仍由正式来源定义，AI 承担最小充分修改、责任归口和语义越权审核，Code 只执行确定性契约，tests 只固定来源已定义的可观察行为与最小反例。本结论不证明所有未来增量天然合规；以后改变规则选择、授权、状态推断、语义汇总、完成声明或跨来源聚合时仍须重新审核受影响范围。

收口后的聚焦回归为 113 passed；全量回归为 787 passed、10 个原生 Windows 用例按既有条件 skipped；Ruff check、format check 和 `git diff --check` 均通过。变更范围没有生产 Code 或正式 Specs。
