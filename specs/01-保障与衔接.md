## 1. 价值判断

本文存在的价值，是把 00 的理念、构成要素和 V1-V9 从“应该如此”推进到“可以被保障并接入协作环境”。没有保障与衔接，规则只能停留在规范正文、聊天提醒或 AI 自觉，无法稳定形成入口提示、执行拦截、验证证据、事实源回写、范式交互和缺口分流。

本文整体服务 V1-V9：通过入口、消费时机和行动指南支撑快速定位与充分理解；通过保障需求、承接机制和能力缺口支撑正确判断与稳定执行；通过 Human Gate、验证证据、事实源回写和缺口分流支撑门禁确认、强制验证、格式回写、范式交互和主动迭代。本文不新增构成要素，而是定义五类构成要素、事实源和协作环境之间的保障与衔接层。

## 5. 内部保障

内部保障回答：LDVH 凭什么让规则不落空。它关注规则要求如何形成保障需求，保障需求需要哪些能力或能力组合，由哪个承接机制接住，输出什么证据，并在缺口出现时如何分流。

### 5.1 保障、能力、承接与衔接定义

规则说明“应该怎样”。保障说明“如何防止规则落空”。能力说明“LDVH 凭什么提供保障”。承接是保障链路内部的动作，说明“由哪个构成要素、保障衔接位置、环境入口机制或 Human Gate 接住保障”。衔接说明 LDVH 如何进入具体协作环境，使保障能够被读取、触发、执行、验证、产生当次可观察依据、回写和分流。

保障链路如下：

```text
规则要求
  -> 保障需求
  -> LDVH 能力 / 能力组合
  -> 承接机制
  -> 执行 / 提示 / 拦截
  -> receipt / evidence
  -> 验证 / diagnostic
  -> 事实源回写 / 缺口分流
```

保障需求不是规则本体之外的新价值来源，也不是事实源。它是规则进入技术环节的可消费表达。承接机制不是事实源；承接机制输出只有按事实源边界受控回写到 Git 可追踪文件事实源后，才可能成为稳定事实；Git 提交记录只作为溯源证据，不成为独立事实源。

### 5.2 LDVH 能力与能力缺口

LDVH 能力不是单个工具、Hook、Skill、页面或脚本，而是 LDVH 为减少 AI 负担、保障构成要素应用而形成的能力面。能力可以由规范体系、事实模型、行动模板、Code、Web、环境入口、测试、Git 和 Human Gate 共同形成。

能力资产或承载物只是能力的具体承载，例如 Hook、插件、扩展包、Skill、Agent、Code、Web、命令、测试或页面。本文只定义能力、能力组合和能力缺口的共同口径；具体资产登记、安装、schema、页面和环境适配由后续归口规范承接。

环境能力是 Codex、Claude Code、IDE、Shell 或其它 AI 协作环境提供的入口和机制。环境能力可以被 LDVH 使用，但不自动成为 LDVH 能力本体；只有具备可安装、可验证、可阻断 AI lifecycle Hook 的协作环境，回到本文定义的保障需求、承接机制、证据边界和缺口分流后，才能声称被 LDVH 保障链路消费。

能力缺口必须显式暴露。若某项保障需求缺少所需能力、能力组合、环境支持或承接机制，AI、Code、Web、行动模板或环境入口不得静默跳过，也不得把必要保障缺失降级为普通待补齐事项。

### 5.2.1 能力匹配模型

能力匹配模型用于把 `00` 的目标和保障需求转成可执行的能力判断。AI 判断“能不能做”时，不得只看某个工具、环境、文件或命令是否存在；必须先说明目标需要什么能力，再判断哪些 provider 可以提供、提供到什么强度、依据是什么、做不到时如何交还。

能力匹配至少包含以下维度：

| 维度 | 含义 | 边界 |
|---|---|---|
| `provider_dimension` | 能力来源的大类，例如 AI 协作环境、LDVH Code、Git / 文件系统、Tests / Web / 构建、Human Gate、外部资料或服务 | 维度不是规则源；只能帮助 AI 分辨能力来源和限制 |
| `provider` | 具体能力提供者，例如当前 Codex 会话、当前 WorkBuddy 会话、`git.commit-msg`、`code/test_runner.py`、目标环境插件或 Human 当场确认 | provider 必须绑定当前上下文；不能用一个环境的 provider 替代另一个环境 |
| `capability_axis` | 需要判断的能力轴，例如 lifecycle 触发、payload 提供、读写副作用分类、target 归口、阻断、receipt / evidence、验证、回滚、长期保存 | 不同能力轴必须分开判断；局部支持不能写成完整支持 |
| `control_strength` | provider 对当前能力轴的控制强度，例如只读观察、提示、确定性检查、软阻断、硬阻断、Human 决策 | 控制强度不足时只能声明 partial、degraded、unverifiable 或 capability_gap |
| `acceptance_basis` | 当前判断依据，例如 specs 契约、当次真实 lifecycle 输出、repo-local 静态检查、fixture / dry-run、测试结果、Git 提交记录、Human 当场反馈 | 依据只代表其覆盖范围；repo-local 样例、手动命令或测试通过不得冒充真实 integrated |
| `fallback_disposition` | 能力不足或不可验证时的处理，例如 no-op、degraded、capability_gap、unverifiable、blocking / stop、Human Gate、交还 30 / 33 / 09 或对应事实源缺口 | 不得自动恢复、自动接受风险或扩大作用域 |

Codex、WorkBuddy、Claude Code、IDE Agent 等都属于“AI 协作环境”这一 provider dimension 下的具体 provider。它们可以能力不同、事件名不同、payload 不同、安装方式不同，但 LDVH 只能验收映射后的 LDVH canonical event 和当次可观察依据；不得把某个环境的原生事件名、样例插件、配置缓存或用户口头描述直接写成另一个环境的 integrated。

能力匹配的判断流程为：

1. 从 `00` 目标、当前任务和保障需求出发，列出必须能力轴；
2. 为每个能力轴标明 provider dimension、provider、control strength 和 acceptance basis；
3. 将可满足、部分满足、不可验证、缺失和需要 Human Gate 的部分分开输出；
4. 对不可验证或缺失的能力，按 `fallback_disposition` 交还到行动指南、diagnostic、验证声明、30 安装验收、33 插件要求、事实源缺口或 Human Gate；
5. 完成声明只可声称 acceptance basis 覆盖的范围，未覆盖能力必须进入未验证范围和 residual risk。

能力匹配输出不是事实源、授权、安装状态、环境 integrated 声明或完成证明。它只能帮助 AI 准确行动、暴露缺口和选择下一步；若需要把能力判断长期沉淀，必须回到 03、05、09、10、30、33 或对应事实对象归口。

### 5.3 保障需求最小字段

正式 spec 提出保障需求时，至少应说明：

| 字段 | 要求 |
|---|---|
| 需求ID | 稳定标识，用于 Code、行动模板、环境入口、Web、测试和过程输出回指。 |
| 保障需求 | 要防止哪条规则落空，减少哪类 AI 负担。 |
| 来源依据 | 保障需求来自哪篇 spec、章节、附件、事实对象或证据。 |
| 所需能力 | 需要哪些 LDVH 能力、能力组合或环境能力；当前缺失时必须说明能力缺口。 |
| 消费时机 | 在什么行动时机必须被读取、检查、提示、拦截、验证或交还。 |
| 承接归口 | 由规范体系、事实模型、行动模板、Code、Web、保障与衔接层、环境入口、Git 溯源、测试或 Human Gate 中哪个主位置接住。 |
| 承接机制 | 具体通过规则入口、行动模板、Code、Web、Hook、Rules、Skill、Agent、测试、Git 或 Human Gate 中的哪些机制承接。 |
| 完成证据 | 什么 receipt、evidence、命令结果、Web 呈现、测试结果、Human 决策或 Git 记录可证明本次保障发生过。 |
| 阻断条件 | 哪些缺失、失败、冲突、不可验证或 Human Gate 未决会阻断当前行动或完成声明。 |
| 缺口分流 | 不能承接时回到哪个构成要素缺口、事实对象、行动模板候选、Human Gate 或待补齐事项。 |

字段可以由正文表格、授权附件、Code 派生结构或后续成员规范承载，但不得只存在聊天过程或一次性工具输出中。

### 5.4 消费时机

消费时机用于回答保障需求何时被 AI、Code、Web、环境入口、行动模板或 Human Gate 使用。

当前消费时机闭集由 `specs/attachments/01.Att.01-保障消费时机表.md` 承载。正式 spec 不得私自新增同义时机；需要新增、删除、重命名或改变消费时机含义时，必须修改本文或授权附件，并评估 Human Gate。

### 5.5 承接机制边界

承接机制可以包括：

| 承接机制 | 作用 | 边界 |
|---|---|---|
| Specs 正文 | 定义规则、保障需求和权威边界。 | 不替代执行、验证或事实源回写。 |
| 行动模板 | 将保障需求组织为 Context、Scenario、Gate、执行、验证、回写和分流。 | 不重写来源规则，不维护第二事实源。 |
| Code | 解析、校验、诊断、生成 read_plan、聚合和受控写入前检查。 | 不替代 AI 判断或 Human Gate。 |
| Web | 展示状态、风险、证据、验证结果和待确认事项。 | 不维护事实源，不替代行动判断。 |
| 环境入口 | 提供 Hook、插件、入口可见和环境适配能力。 | 不证明当前环境已经完整支持 LDVH。 |
| 测试 | 提供可复现验证、回归检查和失败阻断依据。 | 不把测试通过升级为 Human 授权。 |
| Git | 记录 Git 文件事实源变更的溯源证据和提交说明。 | 不替代 Git 文件事实源、规则正文或对象状态。 |
| Human Gate | 完成授权、方向校正、风险接受或验收确认。 | 只能由 Human 完成，AI 和 Code 不得代替。 |

承接机制可以组合使用，但必须说明主承接位置和输出回指关系。多个机制共同承接同一保障需求时，不得形成互相竞争的权威副本。

### 5.6 Receipt、Evidence 与 Diagnostic

`receipt` 是某个保障消费、执行、确认或写入动作已经发生的回执。`evidence` 是用于支持判断、验证、关闭或溯源的证据。`diagnostic` 是对缺失、失败、风险、不可验证或不一致的结构化判断。

receipt、evidence 和 diagnostic 默认是过程输出，不自动成为事实源。需要长期溯源时，必须按事实源边界受控回写到 Git 可追踪文件事实源；Git 提交记录只用于证明文件变更和提交语义，不承载独立事实源。

当规则讨论当次审计、当次验收、环境接入判定、Hook 触发或安装检测时，`证据` 默认指当次可观察依据，包括命令输出、Hook 输出、插件事件、payload 回显、阻断结果、文件状态或 Human 当场反馈；它不默认要求长期留存，不默认形成状态标记，也不默认写入事实源。只有事实模型、行动模板、验证声明或 Human Gate 明确要求回写时，才需要把相关内容按事实源边界受控回写为长期证据。AI 面向 Human 解释验收时，必须优先使用“当次可观察依据 / 当次验收依据”，不得把验收误表述为“留存证据后才完成”。

运行态 receipt cache 是 receipt 的短期桥接形态，只用于同一环境会话内让不同 lifecycle 事件共享已发生的过程回执。它不得写入项目 repo、`specs/`、`ldvh-base/`、Spark、受管项目或工作树隐藏目录；不得存储聊天全文、文件正文、完整 transcript 或完整 tool payload；不得替代事实源、Human Gate、验证结论或长期状态。运行态 receipt cache 必须放在操作系统 runtime、temporary 或 cache 目录，绑定 session、workspace 和过期时间，具备最小权限、可清理和可重建边界；目录解析、字段和清理要求由 `01.Att.05` 承接，安装告知和回滚清理由 `01.Att.06` 承接。

AI 不得把 receipt 等同于规则满足，不得把 evidence 等同于 Human 授权，不得把 diagnostic 等同于最终结论。它们都必须回到主控 AI、事实源规则和必要的 Human Gate。

### 5.7 缺口分流

保障需求无法被承接时，必须区分：

| 类型 | 判断 | 处理 |
|---|---|---|
| `blocking` | 阻断当前行动、规则成立、完成声明、事实源回写或 Human Gate。 | 停止当前完成声明，修复、分流或交还 Human。 |
| `warning` | 不阻断当前行动，但影响风险、证据完整性或判断可信度。 | 明示风险和承接位置，不得静默。 |
| `follow_up` | 不阻断当前行动，但需要后续补齐。 | 写入对应事实源、待补齐事项或工作对象。 |
| `unverifiable` | 当前无法验证、验证范围不足或证据不可复现。 | 说明原因、影响范围和后续承接，不得声明已验证。 |

必要保障缺失不得降级为普通待补齐事项。若缺失支撑当前规则成立、关键行动、Human Gate、Stop Conditions 或完成声明，必须作为 blocker、Human Gate 或 Stop Condition 处理。

### 5.8 Repair Lane

Repair lane 是 `ldvh.pre_tool_use` / preflight 下的受控修复模式，用于修复当前 primary target 的结构性事实对象诊断。它使用 `operation=repair` 或等价 payload 表达，不新增消费时机，不新增 runtime event，不替代 `completion_claim`，也不是 bypass、授权、放行或 Human Gate。

Repair lane 只允许处理事实对象实例的结构性诊断。目标必须能归口为单一事实对象实例，诊断必须属于 07 定义的可修复诊断闭集，且诊断 scope 必须是当前 target 的 `target_primary`；必要的直接 dependent 可随 primary 在同一 repair receipt 中被重新验证。状态推进、关闭、风险接受、Human Gate、跨对象迁移、任意文本改写或非结构性业务判断不得借 repair lane 自动放行。

Repair lane 的最终验证只判断 primary target 及必要直接 dependent 的结构性诊断是否被清除。`unrelated_global` 不得让 repair 永远失败，但必须保留为 diagnostic 或 residual risk。若 repair 写入后最终验证仍失败，AI 和 Code 必须把结果表述为“已写未通过”或等价失败状态，不得声明完成、关闭或验收通过。

### 5.8.1 自锁事故处置路径

自锁事故指 LDVH 因自身事实源、target 归口、read_plan receipt、runtime cache、validator 或 diagnostic 分流异常，导致 AI 无法继续维护 LDVH 或受管项目事实源的情况。处置目标是恢复“AI 能准确行动”的保障链路，而不是自动恢复、自动放行或把异常写成长期健康状态。

遇到自锁事故或疑似自锁事故时，AI、Code 和 Hook 必须按以下顺序处置：

1. 先消费 10 的 target-first 管辖解析，明确当前行动的 `scope_status`、target、operation 和影响范围；`non_governed` 必须 no-op，`scope_unknown` 必须 degraded / `capability_gap` / `unverifiable`，不得被扩大成管辖阻断；
2. 再按当前 target 对 diagnostic 分流，区分 `target_primary`、必要 direct dependent / cascade、`unrelated_global` 和 `runtime_blocker`；无关坏对象只作为 residual risk，不得阻断当前无关普通写入；
3. 若当前 target 自身存在结构性事实对象诊断，普通写入必须停止，并在 repair、拆分、补 target、补 read_plan 或 Human Gate 之间分流；
4. 只有满足 §5.8 和 07 闭集条件时，才可用 `ldvh.pre_tool_use` repair mode 修复当前 primary target；repair 不是 bypass，不得推进状态、关闭对象、接受风险、跨对象迁移或替代 Human Gate；
5. repair 写入后必须执行 final validation：只判断 primary target 和必要 direct dependent 是否清除结构性诊断；仍失败时必须记录“已写未通过”或等价失败结果，不得声明完成、关闭或验收通过；
6. 若失败来自 Hook、runtime cache、target resolver、validator、read_plan receipt 或 diagnostic 分流机制本身，必须暴露机制失败、影响范围和需要 Human 介入的位置；Human 可以授权一次受控处理或要求先完善机制，但 LDVH 不提供默认自动恢复路径；
7. 任何 receipt、diagnostic、测试输出、子 agent 结论或过程报告都只能作为当次依据候选；需要长期沉淀时，必须回到 03、05、09、10、30、33 或对应事实对象归口。

该处置路径不新增 runtime event、不新增 bypass、不改变 Human Gate 条件，也不要求每次维护都运行全量测试。它只把 01 的 Hook 行动边界、07 的 Code repair 契约、09 的自锁事故验收矩阵和 10 的管辖解析串成同一判断顺序。

### 5.9 不得声称生效边界

出现以下情况时，不得声称保障已完整生效：

1. 只有规范正文要求，没有消费时机、承接机制或完成证据；
2. 只有 Code、Hook、Web、Skill、Agent 或测试输出，没有回指来源保障需求；
3. 只有环境入口资产文件存在，没有证明当前环境已接入；
4. 只有 receipt 或工具成功输出，但缺少主控 AI 判断、验证证据或 Human Gate；
5. 缺口、warning、blocker、unverifiable 没有分流位置；
6. 稳定事实停留在聊天、缓存、环境索引、Web 状态或工具输出中。

## 6. 外部衔接

外部衔接回答：LDVH 如何进入具体协作环境，使内部保障能力能够被读取、触发、执行、验证、产生当次可观察依据、回写和分流。

### 6.1 环境入口边界

环境入口是 LDVH 面向外部协作环境暴露的入口层，只能由可安装、可验证、可阻断的 AI lifecycle Hook、插件、扩展包或 package 承载。环境入口的职责是让协作环境通过真实生命周期事件进入同一套保障消费语义，不是复制 specs 规则，也不是证明当前环境已经完整支持 LDVH。

LDVH 仅支持具备 AI lifecycle Hook 的协作环境。缺少 AI lifecycle Hook 的环境不属于 LDVH 正式支持范围；非 Hook 机制、聊天提醒或 AI 自觉消费不得作为 LDVH 环境入口、安装策略、接入判定或验证路径。

### 6.2 Runtime Protocol 最小语义

Runtime Protocol 是 LDVH 暴露给协作环境的统一生命周期协议。不同环境可以有不同触发方式，但必须归一到同一套保障消费语义。

本文只定义 Runtime Protocol 的最小语义：

1. 识别当前事件属于哪个消费时机；
2. 标明触发来源，例如 Hook、插件、扩展包、package 或其它已验证生命周期入口；
3. 携带足够上下文以判断目标、管辖范围、读写性质和已有 receipt；
4. 消费对应保障需求，输出 read_plan、检查结果、阻断、receipt、evidence、diagnostic 或行动指南输入；
5. 暴露能力缺口、环境缺口、不可验证范围和 Human Gate 未决事项。

本文不定义完整 payload schema、dispatcher 文件路径、命令参数、receipt 存储路径或环境安装方式。这些内容由 Code、本文授权附件、测试、事实源与 Git 溯源等承接。

V3 不保留独立的 Runtime Protocol 可见入口文件。Runtime Protocol 语义由本文、`01.Att.05`、Code runtime adapter、环境插件或扩展包承接；任何环境入口只能指向 LDVH Code，不得通过仓库内的独立协议文件证明安装、接入或自动触发生效。接入判定分类由 `01.Att.04` 和 Code 环境审计承接。

### 6.3 Canonical Event 与 Trigger Source

`canonical event` 是 LDVH 内部消费保障需求的统一事件语义。`trigger source` 是同一事件来自哪个外部入口的来源说明。

必须区分三层事件名称：

1. 环境原生事件：由 Codex、WorkBuddy、IDE、Agent 平台或其它目标环境定义，例如 Codex 的 `SessionStart`、`PreToolUse`、`Stop`。环境原生事件只作为触发来源，不是 LDVH 规则、验收或完成声明的事件本体。
2. LDVH canonical event：LDVH 自己定义并验收的生命周期事件。跨环境、跨插件、runtime payload、receipt、诊断和验收表达中，LDVH canonical event 必须带 `ldvh.` 前缀，例如 `ldvh.session_start`、`ldvh.pre_tool_use`、`ldvh.completion_claim`、`ldvh.acknowledge_read_plan`，以避免与环境原生事件混淆。
3. 保障消费时机：`01.Att.01` 表中的 `session_start`、`pre_tool_use`、`completion_claim` 等是 LDVH 内部消费保障需求的稳定键。它们可以作为 Code 内部枚举和表格键存在；当这些键通过环境入口、runtime adapter、receipt、验收卡或 Human-facing 输出表达为 lifecycle event 时，必须映射为带 `ldvh.` 前缀的 LDVH canonical event。

环境插件、扩展包或 adapter 必须把一个或多个环境原生事件映射为 LDVH canonical event。不同环境的事件名可以不同，也可以通过组合或拆分后承接同一个 LDVH canonical event；验收时判断的是 LDVH canonical event 是否在目标环境中正常触发、阻断、输出和分流，而不是环境原生事件名本身是否与某个环境样例一致。

环境插件必须是薄引用入口。它只能把目标环境原生事件、payload 和输出协议投影到 LDVH runtime / adapter，不得在不同环境插件中分别实现规则判断、复杂命令分类、target 归口、diagnostic 分流、read_plan 消费、repair / bypass / completion 判断或状态推进。凡是会影响阻断、no-op、diagnostic、验证声明或事实源回写的逻辑，都必须回到共享 LDVH Code、specs 和事实源承接。

当前可用的消费时机闭集仍以 `01.Att.01` 为准。若后续需要把用户输入、外部页面操作、自动任务或其它入口提升为新的消费时机，必须修改本文或授权附件，并评估 Human Gate。

canonical event 不得反向定义消费时机闭集。trigger source 不得改变规则权威，也不得让不同 Hook、插件、扩展包或 package 路径各自形成不同规则。

### 6.4 外部衔接不得固化的内容

本文不应固化具体 Hook 安装方式、插件目录结构、adapter 文件名、dispatcher CLI、payload 完整字段、receipt 文件路径、环境专属配置、Web 页面、测试用例或 Git commit-msg 细节。

这些内容应由 Code、本文授权附件、行动模板、测试、Web、Git 和事实源规范承接。本文只定义它们必须回到同一套保障消费语义，并说明不得声称生效的边界。

### 6.5 环境入口类型

环境入口必须先归入 `specs/attachments/01.Att.03-环境入口类型表.md` 的类型闭集，再输出接入判定分类。

`automated_hook` 是当前环境能自动触发、能阻断失败、且安装与接入的当次可观察依据可复核的入口。入口是否满足该条件必须由当次依据检查、安装依据和失败处理共同判断。

V3 当前 Hook 分为两类：

1. Git Hook：由 Git 仓库事件触发，例如 `commit-msg`。Git Hook 受 Git 机制限制，通常必须在各自 Git repo 中安装 shim；该 shim 只能定位并调用 LDVH，不得复制 specs、事实源、校验逻辑、Human Gate 判断或管辖项目规则。包括 LDVH 自身在内，Git Hook 的核心逻辑都必须留在 LDVH Code 中。
2. 环境 Hook：由 AI 环境、编辑器、Agent 平台或插件生命周期触发，例如 session start、pre tool use、completion claim 或 tool-call before write。环境 Hook 是薄引用入口，应指向 LDVH runtime / adapter，由 LDVH 根据 cwd、target、payload 和管辖项目配置判断是否受管，并把环境原生事件映射为带 `ldvh.` 前缀的 LDVH canonical event。环境入口必须消费 10 的管辖解析结果：`non_governed` 必须静默 no-op，并以 exit 0 结束，不得输出 stdout、systemMessage、additionalContext、deny 决策、read_plan 或完成声明 warning；`scope_unknown` 不得被当作管辖对象阻断或注入上下文，应交还 degraded / capability gap 或要求补充可复核依据；`governed_target_unknown` 只在已有管辖范围证据但 target 不明时成立，高影响动作必须要求明确 target、拆分或进入 Human Gate；`declared_multi_governed` 必须保留每个对象独立归口；`mixed_scope` 必须阻断、拆分或进入 Human Gate。

Git Hook 和环境 Hook 都只是入口与触发机制，不是规则源。二者必须回到同一套 V3 specs、管辖项目配置、Action Guide、preflight、commit gate、验证和 Human Gate 边界。不得让每个项目、每个编辑器或每个环境各自维护一份规则逻辑。

所有受支持协作环境，其环境 Hook 的正式安装形态都必须是该环境的 LDVH 插件、扩展包或 package；Codex plugin 只是当前可审计实现样例。插件只能承载入口声明、Hook 配置、薄引用 shim / adapter 和必要资产引用；不得复制 specs 规则、事实源、行动模板、校验逻辑、命令分类逻辑或 Human Gate 判断。直接写入用户级 `hooks.json`、项目级 `.codex/config.toml`、IDE Hook 配置、环境系统 Hook 文件或临时 Hook 文件，只能作为调试、探针或迁移验证手段，不能替代正式插件安装口径。

`external_adapter_candidate` 是后续外部环境、插件或 runtime adapter 可以接入的候选。候选必须等真实触发、稳定 payload、失败处理、安装与接入依据、回滚方式和测试依据齐备后，才能升级为自动入口。

`removed_top_level` 用于 Rules / Skill 这类 V3 已取消的顶层机制。它们不是待启用入口；若后续需要入口可见能力，必须进入正式环境 Hook、插件、扩展包或 package，而不是恢复顶层目录机制。

### 6.6 接入判定分类

环境接入判定输出必须使用 `specs/attachments/01.Att.04-环境接入判定分类表.md` 的分类表。该分类表不是 04 所定义的可记录状态闭集，也不是安装状态记录；它只用于 Code、README、测试、迁移记录和 AI 完成声明表达当前审计或当次验收输出。

环境接入判定是对“当次验收时、目标环境、目标 LDVH root、目标插件或配置版本、当前触发依据”的过程判断，不是对环境写入长期状态。`integrated` 只表示本次审计或验收中对应入口真实自动触发、失败可阻断、payload 可消费且安装与接入依据可复核；插件升级、路径迁移、App 重启后失效、配置变化或换到另一个环境后，原判定只能作为历史依据候选，不自动继续成立。

环境接入判定必须绑定验收边界，至少说明目标环境、LDVH root、触发入口、验收时间或命令输出、关键当次可观察依据和不可验证范围。当前环境不能真实触发另一个环境的 lifecycle Hook 时，只能输出不可在当前环境验收的 diagnostic 或 `absent` / `available` / `deferred` 等候选分类，不得把其它环境的样例包、配置缓存或用户口头确认写成该目标环境 integrated。例如，在 Codex 会话中不能直接验收 WorkBuddy 的真实 lifecycle 触发；只能审计 WorkBuddy 样例包或接收 WorkBuddy 环境回传的当次触发依据后再判断。

环境 Hook 当次判定为 `integrated` 时，最小当次验收依据必须同时覆盖：

1. 安装与启用依据：目标环境插件、扩展包、package 或 adapter 已安装、已启用、已授权或无待授权，Hook 配置指向当前 V3 LDVH root、V3 shim 或 `runtime_adapter.py`，且没有 stale V1/V2 path；
2. `ldvh.session_start` 真实触发依据：新开、恢复或等价环境事件由目标环境自动触发，并被 adapter 映射为 `ldvh.session_start`，产生可回指的 read_plan、receipt、event、session_id、cwd 或 target 输出；
3. `ldvh.pre_tool_use` 阻断依据：写入类或等价高影响工具调用前由目标环境自动触发，并被 adapter 映射为 `ldvh.pre_tool_use`，负例能阻断或返回目标环境认可的 deny，正例或只读动作不被误阻断；
4. `ldvh.completion_claim` 或 completion-adjacent 依据：完成、停止或等价环境事件由目标环境自动触发，并被 adapter 映射为 `ldvh.completion_claim` 或明确的 completion-adjacent LDVH canonical event，能输出完成声明检查、验证缺口或残留风险提示，且不得误阻断环境正常停止；
5. payload 与 target 依据：payload 足以判断 event、trigger_source、session_id、cwd、target_path / target_paths、operation、acknowledged_paths、verification_evidence 或 10 定义的管辖解析结果；缺字段时必须能区分 `non_governed`、`scope_unknown` 和 `governed_target_unknown`，不得把 scope unknown 直接写成管辖阻断；
6. 回滚依据：禁用、卸载或移除入口后，同一目标环境不再自动触发 LDVH，短期 runtime cache 被清理或说明 TTL 到期后不再采信。

上述当次依据缺任一项时，不得把环境 Hook 写成完整 integrated；应按 `01.Att.04` 输出 `available`、`deferred` 或 `absent` 等接入判定分类，并附带 `unverifiable`、blocking 或其它 diagnostic / 缺口分流。安装检测、repo-local shim 直测、手动 runtime 命令、插件页面可见或用户口头确认只能作为依据候选，不能单独替代真实 lifecycle 触发和失败处理依据。

接入判定分类必须区分：

1. `available`：Hook、插件、扩展包、package、配置或候选资产存在，但未证明真实自动触发；
2. `integrated`：当次验收中当前环境真实自动触发，失败可阻断，payload 可消费，安装与接入依据可复核；
3. `deferred`：后置，不阻断当前主线；
4. `removed_top_level`：V3 顶层机制已取消，不作为后置入口；
5. `absent`：没有可识别入口。

`environment_integrated=partial` 只能在当次审计或验收中至少一个真实自动入口 integrated，且其它入口边界如实声明时使用。具体当前环境接入判定应由环境审计、验证命令、README 或实现域文档报告，不得手写成不可复核的长期规则、安装状态或事实对象状态。

Code、README、测试、迁移记录和 AI 完成声明不得把 `available`、`deferred` 或 `removed_top_level` 写成 `integrated`。

### 6.7 Runtime payload 与 receipt

runtime payload 字段由 `specs/attachments/01.Att.05-runtime-payload字段表.md` 承接。payload 至少应能表达 event、trigger_source、target_path、operation、task、acknowledged_paths、verification_evidence 和 session_id 等信息，并为 Code 按 10 解析管辖范围提供足够上下文。跨环境 payload 的 `event` 应表达带 `ldvh.` 前缀的 LDVH canonical event；Code 内部可以继续使用 `01.Att.01` 的消费时机键作为兼容枚举，但输出给环境、receipt、验收卡和 Human-facing 结论时必须能回指对应的 `ldvh.*` canonical event。

receipt 是过程输出和证据候选，不是事实源、授权、放行或 Human Gate 完成。receipt 可以帮助 AI 定性入口是否被调用、读取计划是否覆盖、诊断是否产生和缺口如何分流，但必须回到 03 的事实源边界和 09 的验证声明边界。

`acknowledge_read_plan` / `ldvh.acknowledge_read_plan` 在 V3 中保留为 LDVH 内部保障消费时机和 runtime receipt bridge，不恢复 V2 persistent session receipt 存储，也不得被要求为任何目标环境的原生 Hook 时机。环境 Hook integrated 验收不得要求 Codex、WorkBuddy、IDE 或其它目标环境自动触发 `acknowledge_read_plan`；应验收的是 LDVH 自己的 `ldvh.pre_tool_use` 能否获得“AI 已消费 read_plan”的当次依据。当前承接方式是：`ldvh.session_start` 生成 read_plan；LDVH 通过显式 `acknowledged_paths`、validator runtime、CLI、环境 shim 辅助或 transcript 推断等 LDVH bridge 机制生成 read_plan 消费依据；`ldvh.pre_tool_use` 和 `git_commit_msg` 优先通过显式 `acknowledged_paths` 检查 read_plan 消费证据，`ldvh.pre_tool_use` 在真实 lifecycle payload 缺少显式字段时可以读取同 session、同 workspace、未过期的 runtime cache；`ldvh.completion_claim` 和 09 验证声明检查验证证据、未验证范围和残留风险。缺少 read_plan 消费证据时，写入前检查和需要显式 read_plan 的 commit gate 必须阻断或返回 diagnostic，不得从 commit body、聊天声明或环境可见文件推断已消费。

`ldvh.pre_tool_use` 的 read plan 检查必须覆盖两层：第一层是 00、01、02 的入口必读集合；第二层是 preflight 按 target 类型生成的 `required_read_plan`，例如事实对象实例必须覆盖 03、05、09、对应成员规范和当前事实对象文件。目标专属 read plan 不是提示文本；对受管写入而言，`acknowledged_paths` 或同 session runtime cache 未覆盖完整 `required_read_plan` 时，`ldvh.pre_tool_use` 必须阻断并输出 read plan incomplete diagnostic，而不是继续放行或只给 warning。

runtime cache 只能作为过程输出。runtime cache 只允许短 TTL、最小字段、session / workspace 绑定和过期清理；过期、缺失、session 不匹配、workspace 不匹配或字段不完整时不得采信。若后续需要长期 receipt 存储，必须先补事实源回写规则、字段 schema、清理策略和测试，不得把临时 runtime cache 输出升级为事实源。

### 6.8 Hook 行动边界表

Hook 行动边界表用于约束 LDVH canonical event 在自锁、repair、unknown/gated、completion 和 read_plan receipt 场景下的共同处理口径。表中事件名使用 LDVH canonical event 或内部消费时机；目标环境原生事件只作为 trigger source，不得直接成为 LDVH 事件本体。

| 事件 / 时机 | 必要输入 | 输出 | 阻断规则 | no-op / degraded | Human Gate / 禁止声明 |
|---|---|---|---|---|---|
| `ldvh.session_start` / `session_start` | `session_id`、`cwd`、`task`、可用时的 `target_path` / `config_root` | 入口 `task_read_plan`、source_refs、scope diagnostic、capability gap | 只在消费时机未知、payload 无法形成最低限度输出或目标明确触发 Stop Conditions 时阻断；不得因无关事实对象结构诊断阻断会话入口 | `non_governed` 静默 no-op；`scope_unknown` 只能 degraded / capability_gap，不得注入项目事实源 read_plan | 不声明环境 integrated、read_plan 已消费、Human Gate 已完成或事实源健康 |
| `ldvh.acknowledge_read_plan` / `acknowledge_read_plan` | `session_id`、`acknowledged_paths`、workspace / root 匹配信息 | stdout-only receipt 或短期 runtime receipt cache | 必读入口路径缺失、不匹配、过期或 cache 校验失败时阻断 receipt 采信 | 不要求目标环境原生 Hook；只作为 LDVH 内部 bridge；找不到 cache 时回到显式 `acknowledged_paths` 或阻断诊断 | 不得变成任意命令 bypass；不声明写入授权、read_plan 内容正确或 Human Gate 完成 |
| `ldvh.pre_tool_use` / `pre_tool_use` | `cwd`、`target_path` / `target_paths`、`operation`、tool payload、`acknowledged_paths` 或同 session runtime cache | preflight、required_read_plan、diagnostic、deny / no-op / degraded 输出 | 目标专属 read_plan 未消费、`target_primary` 普通写入 blocker、`runtime_blocker`、`governed_target_unknown` 高影响写入、`mixed_scope` 写入均阻断 | `non_governed` 静默 no-op；`scope_unknown` degraded / capability_gap；`unrelated_global` 只作 residual risk，不阻断当前普通写入 | 不回答“是否应该写入”；不替代 Human Gate；不得把 unknown 当作管辖对象扩大阻断 |
| `ldvh.pre_tool_use` repair mode | 单一事实对象 target、`operation=repair` 或 `mode=repair`、可修复 diagnostic code、read_plan 消费依据 | repair preflight、target_primary / target_cascade / unrelated_global 诊断、final validation 要求 | 非事实对象 target、非闭集 diagnostic、状态推进、关闭、风险接受、跨对象迁移或业务语义判断必须阻断或 Human Gate | repair final validation 只看 primary target 和必要 direct dependent；`unrelated_global` 保留为 residual risk | repair 不是 bypass；不得声明对象关闭、状态已推进或验收通过；repair 后仍失败必须写“已写未通过” |
| `git_commit_msg` | repo root / common-dir、staged paths、commit message、必要 read_plan 证据 | commit message 检查、全局健康诊断、Git record 过程证据 | commit gate 在其它明确替代的全局健康保障机制落地前保持全局健康要求；commit message 契约、必读、Human Gate 或验证缺口不满足时阻断 | message file 不作为项目 target；非提交动作不得借 git gate 判断放行 | Git commit record 不替代事实源、验证声明、Human Gate 或完成声明 |
| `ldvh.completion_claim` / `completion_claim` | `target_path` / `target_paths`、verification_evidence、当前 diagnostic、scope_status | 完成声明检查、未验证范围、residual risk、completion diagnostic | 缺少验证证据、`target_primary` blocker、`runtime_blocker` 或 target / scope 未决时阻断完成声明 | `unrelated_global` 不阻断当前完成，但必须作为 residual risk；Stop 类环境事件不得被误阻断环境正常关闭 | 不替代 Human 验收；不得把工具成功、receipt 或测试通过单独写成完成 |
| `human_facing_output` | 当前结论、依据、风险、诊断、未验证范围、需要 Human 决策的对象 | Human-facing 摘要、选项、风险、待确认事项 | 准备表达授权、验收、风险接受、关闭或完成但缺少 Human Gate / 验证依据时阻断输出结论 | 无法归口时交还待确认对象和影响范围，不得自行扩大 scope | Human Gate 只能由 Human 完成；AI 不得把 Code / Hook 输出改写成人已确认 |
| `external_output_intake` | Code、测试、Hook、Web、子 agent、外部工具或环境输出及 source_refs | 过程输出分类、证据采纳边界、diagnostic disposition 输入 | 外部输出无法回指来源、与事实源冲突、试图替代 Human Gate 或事实源时阻断采纳 | 不足以采信时降级为过程输出、warning、follow_up 或 unverifiable | 不得把外部输出直接写成事实源、授权、验收或完成 |
| `diagnostic_disposition` | diagnostic code、level、scope、target、source_refs、影响范围 | blocking / warning / follow_up / unverifiable 分流 | 必要保障缺失、`target_primary` 当前动作 blocker、`runtime_blocker` 或 Human Gate 未决时阻断对应动作 | `unrelated_global` 对当前无关动作只作 residual risk；`scope_unknown` 不得扩大成全局阻断 | 不得把待补齐事项当作已落地；不得自动恢复事实源或自动接受风险 |

自锁场景必须按本表处理：坏事实对象可以阻断自身普通写入和完成声明，但不得把无关动作全局锁死；repair 只允许在本表和 07 的闭集内处理结构性事实对象诊断；保障机制失败时只能交还 Human 完善机制或授权一次受控处理，不提供默认自动恢复路径。

### 6.9 Rules 与 Skill legacy 边界

V3 不保留 `rules/` 或 `skills/` 顶层目录机制。Rules 和 Skill 只作为历史术语、来源材料或外部包装候选存在。

V2 Rules 的入口可见能力不得转写为 V3 正式环境入口；后续若需要入口能力，必须通过正式环境 Hook、插件、扩展包或 package 承接，不得恢复 Rules 顶层规则源、Rules registry 或与 specs 并列的权威入口。

V2 Skill 的可复用工作流能力可以被吸收为行动模板步骤、Action Guide 提示、Code CLI 或外部包装候选，但不得恢复 Skill 顶层机制、Skill registry、Skill 执行闭环或用 Skill 输出替代主控 AI 判断。

若环境本身提供名为 Rules 或 Skill 的机制，V3 仍必须按本文重新分类其入口类型和状态；名称相同不等于 V3 顶层机制恢复。

### 6.10 安装、回滚与管辖项目边界

安装、覆盖或卸载真实环境入口必须有安装目标、回滚方式、安装与接入依据检查和验证命令。最小检查项由 `specs/attachments/01.Att.06-环境安装回滚检查表.md` 承接。

worktree-local Git Hook 只声明对应 Git 仓库的 commit message 校验入口已自动触发，不声明外部管辖项目、其它 worktree、session start、pre tool use 或 completion claim 已接入。具体 Hook path、安装命令和回滚命令由实现域文档承接。

受管项目 Git Hook 安装只能安装薄 shim。安装前必须确认目标 repo 已由 10 的 target-first 与 Git common-dir 解析为单一管辖项目，并确认 Human Gate。安装后依据检查必须能证明该 repo 的 Git 事件会调用 LDVH。卸载时必须移除或禁用该 repo 的 shim、恢复或清除由 LDVH 设置的 Hook 配置、保留或恢复原有用户 Hook 资产，并用 status 命令证明该 repo 不再由 LDVH Git Hook 接管。

环境 Hook 安装只能让外部环境以薄引用方式指向 LDVH runtime / adapter。安装前必须确认环境入口、触发事件、payload、失败处理、目标解析和回滚方式。卸载时必须移除或禁用环境入口中的 LDVH 指向，并验证环境不再自动触发 LDVH；不得删除 specs、事实源、管辖项目配置或 LDVH 本体。

环境 Hook 安装必须优先通过目标环境支持的 LDVH 插件、扩展包或 package 完成。插件安装、升级、禁用、卸载或从 V2 插件迁移到 V3 插件，都必须能检查插件 manifest、Hook 配置、信任状态、指向的 LDVH 根目录、触发事件和回滚方式。旧插件、旧仓库路径、直接写入的环境 Hook 系统文件或只存在历史 trust 记录，均不得声明为 V3 环境入口 integrated。

后续将环境入口接入管辖项目时，必须复用 10 的 target-first、Git common-dir 和多目标边界。不得用当前 cwd、路径相似、repo 名称或用户意图替代管辖项目解析。

## 7. 行动指南

行动指南回答：AI 每次行动前最终拿到什么。它是保障与衔接层面向 AI 当前行动的承接包，不是第三套规则体系。

### 7.1 行动指南定位

行动指南可以由 Code、环境入口、行动模板、AI 主控或后续专门机制共同生成或组织。它的职责是帮助 AI 快速判断当前行动应该读取什么、先做什么、何时停止、如何验证、如何分流。

行动指南继承 V2 知识地图的实时任务导航投影职责。知识地图的核心价值不是保存一张地图，而是从大量 specs、附件、事实源、WorkCase、历史线索、diagnostic、测试和当前任务输入中，组织出 AI 当前能理解、能继续行动的脉络。V3 行动指南是在该能力上叠加管辖项目、验证、保障和环境入口承接，不得把知识地图能力缩减成 read_plan 清单、preflight 阻断输出或普通检查清单。

行动指南依赖规范化、格式化文本形成可编译输入。Specs、附件、事实对象、WorkCase、Spark、Study、ADR 或其它正式信息对象，应通过身份、状态、authority、role_sections、source_refs、对象关系、Stop Conditions、Human Gate 和验证要求等结构，让 Code 可以确定性读取、聚合和投影。Code 不能从非结构化长文中猜测规则；无法确定性提取脉络时，行动指南必须输出 `missing_fields`、`capability_gap`、`unverifiable` 或 fallback，而不是生成看似完整的任务导航。

行动指南必须保留知识地图阶段形成的渐进式披露要求。默认输出应优先给当前任务所需的派生结果、短契约、source_refs、Stop Conditions 和 next_queries，而不是把所有相关规范正文、事实对象全文或跨项目上下文一次性注入给 AI。只有在修改对应 spec / attachment / fact object、需要解释规则限制、发现规则冲突、Code 派生结果不足、source_refs 不可信、Human Gate 或 Stop Conditions 被触发、或高影响变更需要回读权威原文时，才升级到章节读取或全文读取。

渐进式披露应能表达至少四类读取层级：`result` 表示只消费 Code / Action Guide 派生出的当前任务结论；`contract` 表示消费可审计短契约和关键边界；`section` 表示读取指定章节、字段或对象片段；`full` 表示读取完整文件。P0 / P1 读取项必须有数量和语义上限；P2 / P3、跨项目召回和远关系展开默认只能进入 `next_queries`、影响面判断或 fallback，不得默认全文注入。重复的同 session、同 cwd、同 target、同 action hint 或等价输入，若已确认消费，可只返回 `guide_receipt` / brief 确认，不重复刷完整行动指南。

行动指南不是规则源、授权器、事实源、测试结论或 Human Gate。行动指南输出必须回指来源依据和保障需求；无法回指时，只能作为过程建议或 diagnostic，不得作为完成证明。

### 7.2 行动指南输入

行动指南输入可以包括：

1. active specs 和授权附件；
2. 当前用户目标、raw input、cwd、target、session_id 和 trigger source；
3. 已有 read_plan、read_plan_consumed receipt、运行时 receipt 或 diagnostic；
4. 当前保障需求、消费时机、承接机制和阻断条件；
5. Code 关系定位输出、事实对象状态、Git 溯源信息或测试结果；
6. 格式化文本中的身份、状态、authority、role_sections、source_refs、对象关系、Stop Conditions、Human Gate 和验证要求；
7. 能力缺口、环境缺口、Human Gate 状态和不可验证范围。

输入不足时，行动指南必须暴露 `missing_fields`、`capability_gap`、`unverifiable` 或 Stop Conditions，不得生成看似完整但不可验证的行动约束。

### 7.3 行动指南输出

行动指南至少应能表达：

| 输出 | 用途 |
|---|---|
| `task_context` | 当前任务、目标对象、已知事实、关键约束和当前所处阶段形成的任务脉络。 |
| `relationship_projection` | 与当前任务相关的 specs、附件、事实对象、WorkCase、证据、测试和环境入口关系。 |
| `task_read_plan` | 当前行动需要优先读取的事实源、规范、对象或证据。 |
| `read_order` | 建议读取顺序、P0 / P1 层级、authority / context / verification / fallback 等角色。 |
| `read_mode` | 每个读取项或读取组的披露层级，例如 `result`、`contract`、`section` 或 `full`。 |
| `guide_receipt` | 对已消费且输入未变化的行动指南返回 brief / receipt 确认，避免重复注入完整上下文。 |
| `suggested_sections` | 需要优先定位的章节、字段、对象、关系或证据片段。 |
| `next_queries` | 需要继续定位或展开时的后续查询。 |
| `stop_conditions` | AI 必须暂停、分流或进入 Human Gate 的条件。 |
| `validation_guard` | 完成声明、写入、提交或交还前需要验证的内容。 |
| `next_action` | 当前建议的下一步行动、暂停、追问或分流。 |
| `missing_fields` | 当前缺失但影响行动判断的信息。 |
| `capability_gap` | 当前保障能力、环境能力或承接机制缺口。 |
| `impact_summary` | 受影响的规范、事实对象、行动模板、Code、Web、测试或环境入口。 |
| `source_refs` | 输出依据回指到的 specs、附件、事实源、对象或证据。 |

这些字段是行动指南的语义契约，不要求当前阶段已经存在完整 Code schema。具体字段 schema、生成方式和测试由后续 Code、行动模板或本文外部衔接规则承接。

当行动指南由 `ldvh.pre_tool_use` / preflight 生成时，`task_read_plan` 或 `required_read_plan` 是写入前必须消费的目标专属读取计划。环境 shim 可以将其展示给 AI，但展示本身不等于消费；只有 `acknowledged_paths`、runtime receipt bridge 或等价可检查依据覆盖完整计划，才可通过写入前检查。

### 7.4 管辖项目行动指南

当 Action Guide 服务管辖项目时，必须先消费 10 的管辖解析结果，并把 `scope_status` 当作分流输入，而不是从 cwd、对话上下文或路径相似性反推项目归口。
非管辖项目必须静默 no-op；该规则同时适用于环境入口和 Action Guide。

| `scope_status` | Action Guide 分流 |
|---|---|
| `governed_single` | 可以为该单一管辖对象生成项目事实源 `task_read_plan`、`source_refs`、`stop_conditions` 和 `validation_guard`。 |
| `non_governed` | 必须静默 no-op，不生成 LDVH guidance、项目事实源 read_plan、完成声明 warning 或 deny 决策。 |
| `scope_unknown` | 只能输出 degraded、`capability_gap`、`missing_fields` 或 `unverifiable`，不得把 unknown 当作管辖对象注入行动指南。 |
| `governed_target_unknown` | 必须要求补充 target、拆分范围或进入 Human Gate；target 清楚前不得生成项目事实源 read_plan。 |
| `declared_multi_governed` | 只能用于 Human 明确发起的跨管辖对象读取、审计或对比；必须按每个管辖对象拆分项目事实源、source_refs、验证和风险。 |
| `mixed_scope` | 不得生成合并行动指南；必须阻断、拆分或进入 Human Gate。 |

管辖项目行动指南必须区分四类来源：LDVH specs、LDVH 本体事实源、管辖项目事实源和过程输出。管辖项目事实源只能来自对应 `governed_project_path` 下的 `ldvh-base/` 入口；目录存在只说明入口可检查，不说明事实实例存在、Hook integrated 或 Human Gate 已完成。无法确认项目事实源入口、事实实例或读取能力时，必须输出 `capability_gap`、`missing_fields` 或 `unverifiable`，不得生成看似完整的项目事实源 read_plan。

### 7.5 Fallback 与不可验证

若关系定位能力、Code 输出、环境入口或其它行动指南输入不可用，行动指南必须使用 fallback read_plan 或显式 diagnostic，并说明 fallback 的来源、覆盖范围和不足。

AI 不得确认空 read_plan 后进入写入、提交或完成声明。若当前无法形成足够行动指南，必须按 blocking、warning、follow_up、unverifiable 或 Human Gate 分流。

### 7.6 行动指南边界

行动指南不得替代 AI 主控判断、Human Gate、事实源、Hook 实际拦截、测试验证、Code 校验或具体行动模板。AI 按行动指南行动时，仍必须保留价值判断、归口判断、风险判断、验证声明和 Human Gate 交还责任。

行动指南也不得遗忘知识地图的任务导航能力。若输出只剩文件清单、阻断结果或验证清单，不能组织当前任务脉络、关系投影、渐进读取、停止条件、章节 / 对象定位和影响面判断，应视为行动指南能力缺口，而不是完整 Action Guide。

行动指南不得把渐进式披露退化成“少给信息”或“永远不读原文”。结果优先、短契约优先和 brief / receipt 只是默认负担控制；当 source_refs 不足、规则冲突、目标是修改权威文件、涉及 Human Gate / Stop Conditions 或需要作出高影响判断时，必须升级到章节或全文读取，并把未展开范围写入 `next_queries`、`unverifiable` 或 residual risk。

后续 specs 可以配置行动指南应引用哪些规则、行动模板、事实源和验证方式，但不得另建与本文并列的行动入口机制。

### 7.7 行动指南验收清单

判断某次 Action Guide 输出是否满足本文要求时，应至少检查：

| 验收项 | 通过口径 |
|---|---|
| 任务脉络 | 输出包含当前任务、消费时机、target、cwd、`scope_status`、管辖项目和当前阶段；缺失时写入 `missing_fields` 或 `capability_gap`。 |
| 关系投影 | 输出不止是文件清单，能表达当前任务相关 specs、附件、事实对象、WorkCase、证据、测试或环境入口之间的关系。 |
| 渐进读取 | `task_read_plan` 具有 P0/P1 上限、读取顺序、source type、role、reason 和 `read_mode`；P2/P3、远关系或跨项目展开默认进入 `next_queries`、影响面判断或 fallback。 |
| 来源回指 | read_plan、stop conditions、validation guard、capability gap、unverifiable 和人类可见摘要必须能回到 specs、附件、事实源、对象或过程输出边界。 |
| 停止与验证 | 输出包含当前行动相关的 Stop Conditions、Human Gate 候选或 validation guard；没有相关项时应能说明未触发或不可验证范围。 |
| 缺口暴露 | target 不明、scope unknown、项目事实源缺失、source_refs 不足或能力不可验证时，必须输出 `missing_fields`、`capability_gap`、`unverifiable` 或 degraded，而不是生成完整指南假象。 |
| 授权边界 | 输出不得包含 `allowed`、`approved`、`unblocked`、Human Gate 已完成、风险已接受、对象已关闭或任务已完成等授权语义。 |
| 管辖分流 | `non_governed` 必须 no-op；`scope_unknown` 必须 degraded；`declared_multi_governed` 必须拆分；`mixed_scope` 必须阻断、拆分或 Human Gate，不得合并项目事实源。 |
| 人类可见输出 | 当 Action Guide 以 text、receipt、Hook 消息或其它 Human-facing 形式呈现时，应展示任务脉络、读取计划、停止条件、验证要求、缺口、source boundary 和下一步，而不只展示 read_plan。 |
| 回归验证 | Code builder、runtime facade、session_start / CLI 文本输出和管辖项目分流均应有自动化测试或等价验证；测试通过只证明覆盖范围，不替代 Human Gate 或真实环境 integrated。 |

| 检查类别 | 检查内容 | 不满足时 |

## 10. Human Gate

以下情况必须进入 Human Gate：

1. 改变内部保障、外部衔接和行动指南三层职责的关系；
2. 新增、删除、重命名或改变消费时机闭集含义；
3. 改变 Runtime Protocol、canonical event 或 trigger source 的基础语义，导致环境入口和运行时判断边界变化；
4. 改变 receipt、evidence、diagnostic 的基础语义，导致后续机制判断边界变化；
5. 允许行动指南、Code、Hook、Web、Skill、Agent、测试或环境入口跳过 Human Gate、事实源边界或验证证据；
6. 接受关键保障不可验证、不可回写、无法分流或无行动指南缺口暴露的风险。
7. 新增、删除、改名或重排环境入口类型、接入判定分类或 removed_top_level 口径；
8. 将 available、deferred 或 absent 入口升级为 integrated；
9. 安装、覆盖、卸载或扩大真实自动 Hook、插件、扩展包、package 或 runtime adapter 的影响范围；
10. 恢复 Rules / Skill 顶层机制，或把 legacy 资产重新写成 V3 顶层入口；
11. 接受环境入口无法回滚、无法验证、无法定位 target 或无法说明失败处理的风险；
12. 声称环境入口已经完成授权、放行、验收或 Human Gate。

## 11. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 下位规范绕过本文各自定义互相竞争的保障与衔接基础规则；
2. 新增规则提出强制要求，但没有保障需求、承接机制、验证方法或缺口分流；
3. 保障需求缺少所需能力或能力缺口说明，却被声称已经完整生效；
4. 行动指南正在替代 AI 主控判断、测试验证或完成证明；
5. 行动指南丢失知识地图演化来的任务导航、关系投影、渐进读取、章节 / 对象定位或影响面判断能力，却被声明为完整 Action Guide；
6. 行动指南为降低上下文负担而隐藏 source_refs、规则冲突、Human Gate、Stop Conditions 或必须回读的权威原文；
7. 无法判断某个承接缺口是否阻断当前行动或完成声明。
8. 无法区分入口是 automated、candidate、removed_top_level 还是 absent；
9. 文件存在、脚本存在、README 命令存在或测试通过被写成自动触发依据；
10. Rules / Skill 目录、注册表或执行闭环被恢复为 V3 顶层机制；
11. 安装或卸载真实入口前没有回滚方式、依据检查和 Human 确认；
12. 管辖项目环境入口未通过 target-first 和 Git common-dir 边界确认。

暂停后，AI 只能交还触发条件、涉及事实源、影响范围、建议归口和是否需要 Human Gate，不得继续声明保障生效。
