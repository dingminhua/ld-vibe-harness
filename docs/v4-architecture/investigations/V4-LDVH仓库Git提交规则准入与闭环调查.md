# V4 LDVH 管辖项目统一 Git 提交契约承载与闭环调查

> 记录性质：本文是 `specification-model-foundation` §13.5 要求的规范责任调整判断记录，不是规则源，不使任何 commit 合规，也不授权 amend、push 或其它 Git 写入。初始判断者为 GPT SOL；初稿形成时间为 2026-07-15 04:13:22 +08:00，最终承载再审时间为 2026-07-15（Asia/Shanghai）。Human 已明确：LDVH 统一提交契约适用于全部受 LDVH 管辖的项目，不只用于 LDVH V4 仓库。复核否决由可选 30 定义共同强制规则；进一步对现有承载位置再审后，最终采用 03 §9 定义提交作为历史与溯源证据的共同契约，30 只组织实际创建行动，不建立 09 或 10。

## 1. 不使用候选名称表达规则对象

需要补齐的规则对象是：**在任何受 LDVH 管辖的实际 Git worktree 中准备创建新本地 commit 时，候选变化、提交拆分、完整 message、验证声明以及创建前后回读结果之间必须满足的统一关系**。

具体需要回答：

1. 一个 commit 应覆盖什么样的主要目的，何时必须拆分；
2. header 使用什么结构，允许哪些 type/scope；
3. 什么情况下 body 必填，至少保留什么内容；
4. 格式机械校验、AI 语义审核和 Git 写后回读分别负责什么；
5. 已创建的不合规 commit 如何停止扩散，何时必须交还 Human。

这些要求不能藏在 Code、Hook、提示词或归档中，但“必须有正式来源”不等于“必须建立独立普通规范”。承载位置还要继续比较它们能否脱离 Git 提交行动独立消费、独立变化，以及拆分后的读取成本。

## 2. 实际暴露的问题

2026-07-15 创建的 `a82b00feeabf94851ea2e10671a433d8a01d106d` 使用 `feat: add Git commit action template mechanism`。该 message 能描述大意，但没有遵循 V3 历史提交契约体现的 LDVH 习惯：description 不是简体中文，八个文件和高影响范围也没有 body。

直接根因是：

1. 03 §9 有意不定义提交拆分、message 格式、Hook 和 push；
2. 30 初版有意只组织项目规则发现、候选、验证、创建和回读，并明确不定义项目政策；
3. 当前 V4 没有正式来源定义全部受管辖项目共同遵守的 LDVH 提交契约；
4. 因而 30 的“读取项目提交政策”把 LDVH 应当提供的共同基线错误地下放给各项目，执行者只能临场选择格式；
5. V3 validator 可以证明历史机制存在，但 `archive/`、Code 和 tests 不能自行恢复规则效力。

因此，先 amend 只能修复一个历史锚点，不能消除下一次重复失败。

## 3. 移除重复和实现细节后的规则

03 已经定义 Working Tree、Index、`HEAD`、history 和 message 的一般证明边界；06 已经定义行动模板共同准入与消费规则；30 已经定义本地 commit 的目标隔离、候选、验证、创建和回读关系。去掉这些重复内容，以及 `git add`、CLI、锁、Hook 安装和测试实现后，仍需补充：

1. 对全部受 LDVH 管辖项目统一适用的 header、type/scope、简体中文 description 和 body 契约；
2. 一个 commit 的主要目的与拆分条件；
3. 使用实际候选路径和完整 message 的提交前机械校验；
4. AI 对目的、真实性、验证覆盖和风险的语义审核；
5. 已创建不合规 commit 的报告、停止和历史改写 Human Gate。

这些是稳定规则，不应留在当次对话或实现中；但它们只在 Git 提交行动进入候选形成、message 生成、创建前校验和写后处置时被消费。

## 4. 结构性重审：稳定契约是否必须成为独立文件

### 4.1 已确认存在独立消费者

第一轮独立复核正确指出，统一契约不仅在创建 commit 时消费，还可被以下只读场景独立消费：

1. 只解释、审查或建议 message，不创建 commit；
2. 对已有 commit 做带契约版本的历史合规审计；
3. validator 和 `commit-msg` Hook 检查 message；
4. Web 解析并呈现历史 commit 的 type、scope、description 和 body。

因此此前“没有脱离提交行动的独立消费者”的判断撤回。契约具有稳定子责任、独立读取和独立失败边界。

### 4.2 独立消费者不自动决定文件边界

01 §13.2 仍要求比较现有规范能否自然承接以及拆分后的净价值。一个规范的明确章节可以有多个消费者；“可以只读消费”不能单独证明必须新增普通规范。若 30 明确把“统一提交契约”和“创建 commit 的行动结构”分成可精确读取的章节，则：

1. 只读审查、validator、Hook 和 Web 可以只读取契约章节，不进入模板执行；
2. 创建 commit 时只需读取一个具体 Git 行动来源，不再拼接独立契约文件；
3. 契约变化可以只修改 30 的契约章节和对应消费者，不必改变 Index 隔离等步骤；
4. 30 仍只承担同一 Git 提交对象的有效形态与形成行动，不吸收其它领域语义。

因此，独立消费者使“契约章节必须清楚独立”成立，但独立文件的净价值仍需与“30 内精确分层”继续比较。

### 4.3 当前 06 构成真实阻塞

当前 06 要求模板移除领域规则和项目强制要求后仍只保留行动结构，并要求引用已有正式来源。按现有文字，30 不能直接新增统一 type/scope/body 契约。此前用“具体模板当然可以定义项目限定输出”重新解释 06 的做法不成立，第一轮复核意见接受。

Human 随后明确的架构意图是：统一提交格式不是各项目自己的领域政策，而是 LDVH 为全部受管辖项目提供的 Git 提交能力契约。若保持 30 同源方案，必须先实质澄清 06：

1. **行动内生契约**：只定义该具体行动自身稳定的输入、输出、统一语法、最低验证和交还条件，可以由具体模板定义并供只读消费者精确读取；
2. **外部领域规则**：事实语义、项目业务状态、领域测试条件、分支保护和其它不由该行动本身产生的要求，必须由对应正式来源定义，模板只能引用和组织；
3. 行动内生契约不得借模板身份扩张到未命中该行动或未受管辖的对象，也不得覆盖上位规范。

这一调整改变 06 的职责边界，必须按 01 §13 记录并独立复核；通过前不能修改 active 06 或 30。

### 4.4 当前候选比较结论

独立契约规范的优点是完全符合当前 06、便于只读消费者定位，并允许契约独立变化。代价是：

1. 30 必须永久引用一个与自身共同形成 Git 提交闭环的并列规范；
2. message、验证、Stop Conditions 和 Human Gate 在 09 与 30 之间容易重复；
3. 后续执行者必须先判断“行动规则”和“项目规则”两份文件的组合关系；
4. Code validator 的来源回指和测试同步也被人为拆成两层。

30 同源方案的优点是一个 Git 行动具有单一来源、L3 可以按契约或步骤精确读取，且符合 03 §9 已保留的“由行动模板或项目策略承接”。代价是必须澄清 06，并确保契约章节不会和行动步骤互相混写。

当前主执行者仍倾向 30 同源，但撤回“独立规范已被证明不成立”的过早结论。最终只能在 06 边界复核后裁决；若行动内生契约概念不能形成清晰且可复用边界，则恢复独立契约规范方案。

## 5. 承载位置比较

### 5.1 03 正文或 03 附件

不采用。03 管辖 Git 与信息溯源的一般语义，而 LDVH header/type/scope 是 LDVH 执行 Git 提交这一具体行动的统一契约。加入 03 会把行动约束伪装成 Git 通用语义；附件也不得承担父规范没有先定义的核心规则和 Human Gate。

### 5.2 独立提交契约规范

保留为真实备选。它具有只读审查、历史审计、validator/Hook 和 Web 消费者，也可独立变化和失败；但会增加 30 执行时的永久拼接和同步成本。是否采用取决于 06 是否允许行动内生契约由具体模板同源承载，以及第二轮独立复核的净价值判断。

### 5.3 30 正文

建议采用。30 已经是 LDVH Git 提交这一具体、重复行动的正式来源，message 形成、拆分、校验和不合规处置都是该行动的输入、步骤分支、验证或交还条件。将统一契约放入 30，不会让 06 或 03 取得具体行动政策，也不会把实现提升为权威。

30 应明确分成两层：

1. **LDVH 统一提交契约**：对全部受管辖项目定义 header、type/scope、body、主要目的、校验和不合规历史处置；
2. **通用行动结构**：目标 worktree、授权、用户既有 Index 保护、领域/项目附加规则发现、候选、验证、创建、回读和交还。

项目自己的正式来源可以追加领域验证、分支保护或其它不冲突的更严格要求，但不得替换、削弱或静默扩展 30 的统一 header/type/scope/body 和拆分契约。确需改变共同契约时，应修改 30，而不是在单个项目形成方言。

### 5.4 `30.Att.01` 授权附件

当前不建立。type/scope 和 body 条件虽适合结构化表格，但数量和复用范围尚不足以证明新增附件的净价值。先在 30 正文中由同一来源定义核心规则与表格；只有表格规模、独立机器消费或维护负担实际增加，并且 30 已先定义相应核心语义和授权边界时，才重新判断附件。

### 5.5 Code、Hook、tests 或配置

只实现，不定义。validator 可以解析 30 中的结构化表格或由 Code 规划定义内部表示；Hook 和环境接入可以调用 validator；tests 证明机械范围。任一实现都不得维护第二份 type/scope 或 body 规则。

## 6. 与 06 的拟议边界调整

当前 06 不支持直接把统一提交契约放进 30。拟议调整不是把项目领域规则改名后塞入模板，而是新增“行动内生契约”与“外部领域规则”的区分。

本次调整需要同步澄清 30 初版中过度绝对的边界：

1. 具体模板只有在规则对象就是该行动自身的输入、输出或形成条件，且存在重复的跨项目一致性价值时，才可定义行动内生契约；
2. 30 据此定义全部受管辖项目的 LDVH 提交共同基线，不再把格式责任下放给各项目；
3. 项目和领域来源仍定义其特有测试、分支保护和其它附加条件，30 组织实际发现和执行；
4. 附加条件不得削弱共同 message 与拆分最低基线；是否允许更严格拆分和更多 body 条件由 30 明确，不使用“不得扩展”一概禁止；
5. Code、Hook、Skill、Web 和环境接入只消费相应精确章节，不复制契约正文。

具体模板不能仅因某规则在行动中使用就取得定义权。行动内生契约必须能说明：没有该行动就不存在相应输入/输出对象、其统一性由 LDVH 行动能力提供、外部领域来源不适合定义，并且同源承载的净价值高于独立规范。上述条件若无法通过独立复核，统一提交契约必须回到独立正式来源。

## 7. 正例、反例和失败边界

正例：在任一受 LDVH 管辖项目中提交同一主要目的的规范、实现和测试变化。30 统一要求简体中文 header、必要 body 和实际候选校验；项目来源另行补充对应领域测试要求。

反例：某个受管辖业务仓库通过自己的说明文件改用另一套 type 或允许多文件高影响提交省略 body。该说明不能削弱 30 的共同契约；若业务需要确实证明共同契约不足，应回到 30 统一修改。

失败边界：目标、授权、候选和 Git 能力都成立，但任一受管辖项目的 message 使用未知 type、全英文 description 或多文件无 body。30 在创建前停止；该失败属于具体 Git 提交行动，不需要另建规范才能解释。

## 8. 对 V1–V8 的净价值

将统一契约合入 30：

1. V1：一次定位即可找到 Git 提交完整行动规则；
2. V2/V3：03、06、30 分别保持“溯源语义、模板共同规则、具体行动”的三层边界；
3. V4/V5：提交前校验和写后回读进入同一因果链，且机械与语义结论分开；
4. V6/V7：后续执行者和 Human 从同一来源恢复 message、验证和风险要求；
5. V8：规则、validator 和环境接入都回指 30，避免第二权威。

代价是 30 正文变长，并同时包含共同契约和执行步骤；通过明确小节和机器可解析表格可以控制。相比新增 09、各项目重复规则和永久跨文档拼接，该成本更低。

## 9. 建议与 Gate

建议按以下顺序推进：

1. 保留“30 同源”和“独立提交契约规范”两个候选，不预占 09 或附件；
2. 对 06 的行动内生契约边界和两种承载位置做第二轮独立复核；
3. 只有 06 调整和 30 同源方案均通过时，才先修改 06，再在 30 内增加统一契约并同步 positioning、scope、职责边界、行动步骤、验证、Human Gate 和 Stop Conditions；否则建立独立契约来源并让 30 只消费；
4. 形成 07 要求的 Code 实现规划，实现只读、无 Git 写副作用的 message + candidate paths validator 和风险 tests；
5. validator 成立后，再由 Human 决定是否 amend `a82b00fe`，并用同一 30 流程完成重校验和写后回读。

独立复核必须主动挑战：

1. 行动内生契约是否是必要且稳定的共同概念，还是在为 30 同源反向造概念；
2. 独立消费者、独立变化与执行时单一来源成本如何比较；
3. type/scope/body 表是否需要附件，还是正文最小充分；
4. 是否存在把领域测试要求、项目特有约束或实现细节误吸入 30 的内容；
5. 扩充 30 后的读取成本是否仍低于新增规范。

复核与主执行者处置完成前，不修改 active 06 或 30 的责任边界，不实现 validator，也不改写现有 commit。

## 11. 迁移后的最小闭环与阶段边界

第一阶段必须同时完成：

1. 30 成为统一提交契约与 Git 提交行动的唯一正式来源；
2. validator 从 30 取得 type/scope/body 的可机械部分，接收完整 message 和实际候选路径；
3. AI 继续承担主要目的、高影响语义、验证覆盖、风险遗漏和 Human 授权判断；
4. tests 回放 V3 正例、未知 scope、全英文 description、高影响或多路径缺 body、缺 `关键变更:`、注释行和 Windows 换行，并增加 V4 当前错误 message 的回归；

## 18. 只读 Git 输入 Adapter 实现结果

`ldvh.commits.git_adapter` 已按实现规划落地。它只消费已经形成的单一 `governed_single` 管辖结果，再以隔离 Git 环境核对实际 worktree，读取 `HEAD` tree、完整 Index stage 和 staged name-status；候选路径读取前后快照漂移、目标与管辖身份不一致、Git 读取失败或输出不可判定时，不形成可验证输入。

Adapter 不生成 message，不进行 AI 语义判断，不调用 Git 写命令，也不承担 30 的 Human Gate。真实临时仓库风险 tests 8 项、commits 模块合计 31 项及相关规范组合 109 项通过，覆盖无 `HEAD`、空候选、add/delete/rename、linked worktree、环境重定向、身份不一致、观察期 Index 漂移与进程失败；普通观察前后 status 和 Index 原始字节保持一致。增量后的全量 Code tests 为 368 passed、46 failed、102 errors，失败与错误仍由已登记的五类型准入记录旧路径漂移触发，数量没有增加。

该结果关闭了“真实 Index/worktree 候选无法绑定到纯 Validator”的内部 Code 缺口，但不等于行动模板已经可由 Helper 执行。Helper 公开操作、创建前 AI 语义审核编排、Git 写入封装、创建后回读、Hook/环境接入及历史改写仍未实现。下一步是先用当前只读闭环审查真实候选和拟用 message，再单独判断最薄写入边界；不得从 Adapter tests 外推真实 commit 已获授权或已创建。

当前 V4 worktree 的真实预检确认管辖为 `governed_single`，Adapter 观察成功，但实际 Index 没有 staged paths，Validator 因 `candidate_paths_empty` 返回 `unverifiable`。因此后续实现必须把“依据已授权目标形成候选”明确承认为写入阶段，不能扩大只读 Adapter 去读取 Working Tree 后假称候选已经成立。

写入边界复核采用受控临时 Index 方向：先保留真实 Index 身份和既有 staged 条目，以当前 `HEAD` 或 unborn 空树装配只含显式目标路径的临时候选；Validator 与 AI 审核该实际候选，创建前重检全部身份，再通过正常 Git commit lifecycle 保留既有 Hook。提交后只在真实 Index 未漂移且目标路径不存在既有 staged 重叠时，对齐目标路径到新 `HEAD`；其它既有 staged 条目必须保持。任何创建后 tree/message/parent 不匹配或 Index 无法安全对齐均作为部分结果交还，不自动 reset、amend 或回滚历史。详细接口、结果分层与风险 tests 见 Code 实现规划 §13。

## 20. 受控候选与 commit 执行实现结果

`ldvh.commits.candidate_index` 与 `ldvh.commits.execution` 已形成内部写入闭环。前者用带所有权标记的临时 Index 装配显式路径候选，拒绝既有 staged 重叠、目录扩张、身份漂移和不安全清理；`git add`/`write-tree` 会写入未被 ref 引用的 Git 对象，因此该阶段明确属于写入能力，不混入只读 Adapter 的完成声明。后者在调用方明确确认授权、语义审核和验证覆盖后，重新执行机械 Validator 与全部身份核对，通过正常 Git commit lifecycle 保留现有 Hook 和项目配置，随后回读实际 commit 并安全对齐目标 Index entries。

执行结果区分 `blocked`、`not_created`、`created` 和 `partial`。Hook 拒绝不创建 commit；Hook 或并发变化造成 tree/message/paths/parent 不一致、真实 Index 无法安全对齐、回读或清理失败时保留实际结果并返回 `partial`，不自动 reset、amend 或回滚历史。调用方 approval guard 只阻止缺少显式确认的调用，不被报告为 Human 授权事实本身。

候选形成与执行新增 27 项真实仓库风险 tests，commits 模块合计 58 项、全量 Code 543 项通过，Ruff check/format check 通过。内部能力仍未成为 Helper 公开操作，也没有安装 Hook、改变环境配置、执行 push/PR 或提供跨进程持久候选；真实 commit 必须继续按 30 使用同一候选完成 AI 语义审核和 Human 授权判断。
