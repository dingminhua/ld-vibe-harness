## 1. 本文解决的问题

本文解决 LDVH 中术语应如何命名、解释、引用和变更的问题。

术语规范的目标不是复制各专项规范的规则正文，而是让 AI 和 Human 在阅读、编写和执行 LDVH 文档时，能够稳定区分项目、工作区、规范、成员自描述、规范保障、能力保障、环境适配、适配措施、构成要素、环境能力、工作对象、字段内容格式、状态、检查、校验、验证、审计、写入、回写、审阅和审核等概念。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 的产品定位、五类构成要素、事实源原则、运行闭环标准和 Human Gate 原则，是本文的上位概念来源。本文承接 00，将后续正式规范、事实模型、行动编排、Code、Web 和环境适配需要复用的概念整理为统一术语边界。

本文不得反向改写 00 的产品定位和上位概念。若术语治理发现需要调整 00 中的上位概念，应单独触发 Human Gate，而不是在本文或其他规范中隐式覆盖。

除 00 的上位概念表达外，本文是 LDVH 术语定义和术语变更治理的权威位置。01、03、04、05、06、07、08、09 以及后续事实模型和行动编排规范可以说明术语在本规范中的应用规则，但不得并行维护同一术语的权威定义。术语建议被吸收后，应以本文为准；未吸收内容不得作为 LDVH 语义依据。

## 3. 术语归口规则

术语定义原则上归口到本文。00 负责提供上位概念来源，不被本文反向管辖；其他规范可以使用术语、引用术语，或说明某个术语在本规范场景中的应用规则，但不得重复定义同一术语。

术语本体定义与对象规则定义应区分处理。术语本体定义回答“这个名称在 LDVH 中是什么意思、边界是什么、推荐怎么称呼”，归口本文；对象规则定义回答“某个事实模型、行动编排、字段、状态或环境适配项在其权威规范中如何构成、如何约束、如何执行”，归口对应专项规范。专项规范可以在自身权威领域定义对象规则、字段契约、状态机或执行规则，但不得借对象规则定义改写本文已归口术语的名称、同义词、边界、包含关系或替代表达。

分工如下：

| 文档 | 负责内容 | 不负责内容 |
|---|---|---|
| `specs/00-LD-Vibe-Harness理念与纲要.md` | 产品定位、五类构成要素、事实源原则、运行闭环和 Human Gate 的上位概念来源 | 后续专项术语细化、不推荐表达处理、术语变更治理清单 |

| `specs/03-文档基础规范.md` | 文档结构、引用、studies/sources、吸收和文档治理规则 | 术语权威定义 |
| `specs/04-规范保障与环境适配基础规范.md` | 规范保障、能力保障、环境适配、适配措施和环境能力的应用规则 | 术语权威定义 |

若某个专项规范需要说明概念，应使用“术语应用关系”或等价章节，引用本文术语，并保留该术语在本规范内的应用关系。术语应用关系只说明本文已定义术语在当前规范、当前编号区段或当前专项场景中的职责分工、消费方式、边界限制和相邻术语关系；不得改写术语本体定义，不得给术语新增与本文不一致的必要条件、状态、字段、同义词、包含关系、排除关系或反向边界。

术语应用关系推荐使用“术语 / 本规范应用关系”表格，表格行应直接引用本文中的术语名称，说明列应使用“在本规范中用于……”“由……消费”“与……区分”“不得用于……”等应用句式。说明列不得写成“X 是……”“X 指……”“X 定义为……”“X 包括且仅包括……”等定义句式；如需描述字段、状态、流程、检查或环境实体，应写成该术语在当前规范中的承载、消费、约束或检查关系，而不是重述术语定义。

非术语归口文档不得通过章节标题、表格列名、段落首句、脚注、示例、头部元信息或规范保障要求重复定义本文已归口术语。专项规范不得设置“术语定义”“概念定义”“名词解释”等章节重新定义 02 已归口术语；不得把字段契约、状态机、流程步骤或环境实体写成 02 术语定义；不得用“本规范另行定义”“本规范语境下定义为”“为便于本文使用重新定义”等写法形成第二事实源。若发现术语缺失、语义不足或需要改名、拆分、废止，应先补充本文，再在专项规范中说明应用关系。

## 4. 项目、工作区与文档分区术语

| 术语 | 定义 | 边界 |
|---|---|---|
| LDVH 自身项目 | 承载和维护 LDVH 规范体系、文本能力资产、Code、Web 和 dogfood 事实实例的项目 | 目标结构使用 `specs/` 作为规范资产和规范事实源 |
| 管辖项目 | 安装并使用 LDVH 进行需求、工作项、证据、变更、审计或交付治理的用户项目 | 管辖项目不默认创建 `specs/`，项目文档由项目自身约定管理，常见为 `docs/` 或 README |
| 管辖项目配置 | 工作区根目录 `LDVH-GOVERNED-PROJECTS.yaml`，用于说明当前工作区 LDVH 管理实例并登记管辖项目最小清单 | 根字段只包含 `product_name`、`product_description`、`projects`；每个项目只强制 `id` 和 `path`，可选 `name` 和 `description`；不承载初始化状态、部署适配结果、检查状态、项目状态、项目类型、环境适配、适配措施或工作对象关系 |
| LDVH 文档工作区 | 承载 LDVH 用户资产、内部研究和外部信源资料的文档工作区 | 在 LDVH 自身项目中为 `docs/`，其下根目录 Markdown 文档是用户资产或项目文档资产，子目录 `docs/studies/` 和 `docs/sources/` 是可变资料区 |
| 规范正文区 | 承载 LDVH 正式规范正文的文档分区 | 在 LDVH 自身项目中为 `specs/`；管辖项目不默认创建 |
| 管辖项目文档工作区 | 承载管辖项目正文、内部分析和外部引用的文档工作区 | 在管辖项目中为 `docs/` |
| 正文区 | 文档工作区中承载稳定正文的根层级 | 在 LDVH 自身项目中，`specs/` 是规范正文区，`docs/` 根目录 Markdown 文档是用户资产或项目文档资产；`studies/` 和 `sources/` 不属于正文区 |
| studies | 内部评估、方案分析、吸收候选或内部调研区 | 不直接构成正式规范，结论需要吸收到 specs、正文区或工作对象后生效 |
| sources | 外部引用、第三方资料、官方文档摘录或引用副本区 | 不直接构成正式规范，不反向维护 specs 或正文区规则 |
| 来源 | 说明某项结论、适配、字段、证据或判断所依据的规范、sources、studies、命令输出、现有清单、Human Gate 记录或其他事实源 | 不固定写作“来源文档”；来源不自动等于权威事实源，应按来源类型判断是否需要吸收、验证或回写；specs 不得把 docs 或外部资料作为依据 |
| 吸收 | 将 studies、sources 或临时分析中的结论转入 specs、正文区、工作对象、ADR、Spark 或其他权威位置的治理动作 | 只引用 studies、sources 或临时材料路径，不构成吸收 |
| 参考与研究材料 | `docs/sources/`、`docs/studies/` 或临时分析中用于调研、参考、对照、候选方案或阶段性推进计划的材料 | 不是 LDVH 资产，不是权威事实源，也不是环境适配层；稳定结论必须吸收到正式规范、工作对象、ADR、Code、Web 或其他对应权威位置后才生效 |
| 待补齐事项 | 已识别但尚未完成调研、验证、实现、回写、清理或决策的后续事项 | 不是失败状态，不等于已批准工作；字段名可保留 `open_items`，中文显示统一使用“待补齐事项” |

## 5. 规范体系术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 正式规范 | `specs/` 正文区中定义稳定规则、对象边界、流程要求、Code 要求、Web 要求、环境适配要求或检查要求的规范文档 | 正式规范应遵守 03 的文档骨架，并按 04.01 判断规范保障要求 |
| 资产 | LDVH 可被复用、承接、加载、触发、执行或展示的能力本体、规则本体、实现本体或界面本体 | 资产不等同于目录容器、适配措施、过程输出或工作对象实例；是否为事实源取决于具体资产类型 |
| 规范资产 | `specs/` 中承载稳定规则、模型、流程、合同和检查要求的规范正文资产 | 同时是规范事实源；不得由 docs、环境入口、薄引用、Rules、Skill、Agent、Hook、Code 输出或 Web 状态替代 |
| 文本能力资产 | `rules/`、`skills/`、`hooks/`、`agents/` 中面向 AI 的规则、能力、触发策略、角色或多角色模板等 Markdown 文本资产 | 只承载可复用文本能力，不替代正式规范、行动编排、Code、Web 或工作对象事实源 |
| Code 能力资产 | `code/` 中 LDVH 提供的可执行检查、校验、解析、生成、迁移、受控写入、上下文压缩或报告输出的确定性参考实现资产 | Code 输出不是最终事实源；稳定结论必须回写到对应 Git 文件事实源 |
| Web 能力资产 | `web/` 中面向 Human 的展示、审阅、确认、检查、矩阵展示或受控轻写入界面资产 | Web 页面状态不是最终事实源；写入和回写必须受正式规范、Code 合同和 Human Gate 约束 |
| 工作对象事实源 | `ldvh-base/` 或管辖项目对应命名空间中承载 WorkCase、ADR、Spark、Pitfall、Study 等工作对象实例的事实源 | 不是能力资产；多数工作对象使用 YAML 实例，Study 使用 Markdown frontmatter 实例；可以记录资产相关决策、工作项、证据或踩坑，但不承载可复用能力资产本体；Git 提交记录不是工作对象事实源字段 |
| 用户资产 | `docs/` 根目录 Markdown 文档中由用户或项目维护的长期项目文档资产 | 不是 LDVH 规范资产；若其中内容需要成为 LDVH 规则，必须吸收到 specs |
| 可变资料区 | `docs/studies/` 和 `docs/sources/` 等 docs 子目录中承载内部研究、吸收候选、外部信源或参考资料的区域 | 可整理、归档或删除；不承载稳定依赖；不得作为 specs 依据 |
| 候选事项 | 尚未创建、尚未生效或需要后续讨论、吸收、废止、保留的事项 | 候选事项不得被当作已经生效的规则执行 |

LDVH 资产目录包括 `specs/`、`rules/`、`skills/`、`hooks/`、`agents/`、`code/` 和 `web/`。`docs/` 根目录 Markdown 文档是用户资产或项目文档资产；`docs/studies/` 和 `docs/sources/` 是可变资料区，不是 LDVH 资产目录。

规范资产只能引用 LDVH 内部资产作为实现、验证或承接对象；非 specs 资产不得成为规范上位依据。docs、外部资料和非 LDVH 资产不得作为 specs 依据。

## 6. 索引文档术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 索引文档 | 用于定位编号区段、文档集合、状态清单或输入清单的文档 | 不替代对应基础规范或具体规范 |
| 说明性索引 | 只帮助查找文档、章节或资料，不定义稳定治理规则的索引文档 | 不默认属于正式规范 |
| 成员自描述 | 具体事实模型或具体行动编排主文件中声明自身编号、类型、标题、集合状态、路径和规则锚点的机器可读信息 | 是成员主文件的一部分；用于 Code 派生集合索引，不是独立第二事实源 |
| Code 派生集合索引 | Code 依据成员主文件自描述生成的成员清单、状态清单、active 清单和冲突诊断 | 只作导航、诊断和上下文压缩；不替代成员主文件或正式规范 |
| 规范型集合索引 | 已废弃的手写集合事实源类型；不得用于维护正式编号区段或规范集合的清单、状态、编号占用、关系、部署适配检查输入或 Human Gate 规则 | 不得新增此类手写集合事实源；成员集合以成员主文件自描述和 Code 派生集合索引消费 |

## 7. 规范保障与环境适配术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 规范保障要求 | 正式规范声明自己需要被看见、复用、检查、触发、确认或实现的要求 | 不是落地结果，不等于 Rules、Skill、Agent、Hook、CI、命令、工具文件或 Web 页面 |
| 能力保障 | LDVH 为满足规范保障要求而提供的能力组合，包括入口提示、流程复用、确定性检查、Human Gate、Code、Web、Agent、生命周期触发或人工检查 | 能力保障由 LDVH 提供，不由环境替 LDVH 选择；具体环境只影响执行方式和降级方式 |
| LDVH 能力资产 | LDVH 自己定义和维护、用于保障规范要求的能力内容，包括 Rules、Skill、Agent、Hook、Code 和 Web 等能力资产 | 不是环境入口，不表示用户本地已经部署、启用或验证；由 `specs/04.02-LDVH能力资产与保障机制规范.md` 规定 |
| 保障机制 | 能力保障中用于让某项规范保障要求被执行、检查、复用、触发或确认的具体机制 | 必须与规范保障要求绑定；无法保障时应记录能力缺口或适配降级 |
| 环境入口 | AI 开发环境提供的读取、加载、调用、触发、配置、展示或执行某类环境能力的位置或机制 | 环境入口不只限于 Rules；Rules、Skill、Agent、Hook、Command、MCP、instructions、配置文件、用户级目录、项目级目录、页面或自动触发机制都可能有各自环境入口；环境入口不是 LDVH 能力资产本体，由 `specs/04.03-环境入口适配与部署规范.md` 规定 |
| 环境适配 | 将 LDVH 能力资产通过薄引用、配置、安装、软链、受控复制、人工降级或其他适配措施接入具体环境入口的过程 | 不得反向改写正式规范；环境只提供客观入口和能力，不是 LDVH 决策源；不同能力资产类型可以接入不同环境入口 |
| 环境能力清单 | 某个环境可用于入口、流程、工具、触发、确认、校验或回写的客观能力、来源证据、限制和证据状态的登记载体 | 环境能力清单是集合和证据结构，不是单项环境能力；由 `specs/04.03-环境入口适配与部署规范.md` 规定；不得写成 LDVH 全局要求 |
| 适配措施 | 能力保障在具体环境中形成的薄引用、文件、命令、配置、工具、页面、Skill、Agent、Hook、CI 检查、摘要或降级记录 | 不是最终事实源；不得替代正式规范、工作对象事实源或 Code 验证；适配措施不是环境入口本体，而是 LDVH 使用或维护环境入口的方式 |
| 适配措施状态 | 某个适配措施在当前环境中的存在、可用或维护状态，例如已存在、计划创建、缺失、部分可用、已废止或不适用 | 不是适配措施本体，只用于即时标注、检查和漂移判断，不持久化保存 |
| 环境 | AI 和 Human 实际执行工作的具体工具、产品、产品版本、入口组合或运行面实例 | 环境是具体执行对象；开发环境是 LDVH 五类构成要素之一；同一软件的不同版本可以作为同一环境族下的入口变体处理，只有入口、权限、加载行为或适配检查存在稳定差异时才单列；当前 04.03 只覆盖 Trae Work 环境族与 Codex App；其他环境需先调研再追加环境适配 |
| AI 开发环境 | AI 工具及其上下文入口、权限、指令、命令、Hook、MCP、Agent、Human 确认方式等承载条件的具体组合 | 是环境的一类具体语境，不替代 00 中“开发环境”构成要素；不得写作平台或平台能力 |
| 环境实体 | 具体环境中可被定位、配置、调用或维护的文件、规则、Skill、Agent、Hook、命令、页面、CI 配置或环境入口 | 只能作为环境适配或适配措施的一部分 |
| 环境能力 | 具体环境中可被 LDVH 用来落实能力保障的单项入口、机制、工具或运行面 | 环境能力是单项能力，不是环境能力清单；能力边界由 `specs/04.03-环境入口适配与部署规范.md` 规定；环境能力不得反向成为 LDVH 全局要求 |
| 适配边界 | 某类环境能力适合承载什么适配措施、不适合承载什么适配措施，以及何时需要组合其他能力或降级处理的边界 | 具体规则由 `specs/04.03-环境入口适配与部署规范.md` 规定 |
| 适配检查 | 用于检查环境适配声明是否真实、可定位、可验证、未越界且能追溯到权威事实源的检查方式 | 没有适配检查或等价检查的适配声明，只能作为待确认、适配降级或参考处理 |
| 适配降级 | 环境能力不足、适配措施缺失、适配检查不可用或稳定触发无法保证时，记录的替代检查、人工确认、后续工作或残留风险处理方式 | 不得用于降低正式规范要求；应说明降级原因、残留风险和后续补齐位置 |
| 工作区级入口 | 用户当前开发环境或工作区配置中用于引导 AI 进入 LDVH 工作区入口、管辖项目配置、管辖项目事实源和工作对象事实源的环境入口 | 属于用户工作区，不随 LDVH 项目提交；初始化时只应写入醒目的薄引用或等价最小入口内容；推荐指向 `../rules/LDVH-WORKSPACE-ENTRY.md` |
| 项目级入口 | LDVH 自身项目仓库内用于引导 AI 维护 LDVH 产品资产的环境入口、环境规则文件、项目指令或等价入口 | 默认只用于 LDVH 自身项目；管辖项目一般不创建项目级入口；推荐指向 `../rules/LDVH-MAINTAINER-ENTRY.md`；不得直接处理管辖项目 `ldvh-base/` 工作对象 |
| AI 入口分层 | LDVH 将 AI 入口分为工作区级入口和 LDVH 项目级维护入口的入口组织方式 | 工作区级入口处理管辖治理和 `ldvh-base/` 工作对象；LDVH 项目级维护入口处理产品资产 |
| LDVH 项目事实源 | 管辖项目中由 LDVH 创建、维护或消费的命名空间事实源、工作对象实例或受控记录 | 可以在管辖项目内创建；不得伪装成用户项目原有入口或替代用户项目业务文件 |
| 项目接入说明 | 解释某个管辖项目如何通过工作区级入口、管辖项目配置、`ldvh-base/` 或 `docs/` 进入 LDVH 治理的叙述性说明 | 不是工作区根目录管辖项目清单；不得承载初始化状态、部署适配结果、检查状态、环境能力核验、适配措施正文或环境入口正文 |
| 能力缺口 | LDVH 尚未提供能力完整保障某项规范保障要求，或能力存在但缺少必要配置、入口、Code、测试、权限或 Human Gate | 不得通过改低正式规范要求解决，应记录能力建设需求、适配降级或待补齐事项 |
| 环境缺口 | 当前环境不能完整承载某项能力保障，或缺少必要环境能力、配置、入口、权限、检查方式或证据 | 不得写成 LDVH 能力缺口；应在环境适配中记录适配降级或待补齐事项 |
| 漂移 | 适配措施、环境适配或自动触发方式与 specs 正式规范不一致，或规范已变更但适配措施未同步 | 漂移检查结果不是最终事实源，稳定结论需要回写 |
| LDVH 运行纪律 | LDVH 自行设定、跨环境适配措施时需要遵守的运行纪律，例如薄引用、LDVH 自建 Skill 命名和 Skill 触发边界 | 由 `specs/04.02-LDVH能力资产与保障机制规范.md` 规定 |
| 启用 | 将已登记的部署适配特别要求应用到特定环境、项目、适配措施、Code 配置或 Human 选择中的动作 | 未启用事项不得被 AI 当成当前项目规则执行 |
| 薄引用 | LDVH 接入环境入口时采用的最小引用措施，只承担发现、触发、导航、提醒和交还职责，不复制完整规范正文，不维护第二事实源 | 薄引用不是环境入口本体；环境入口是环境提供的位置或机制，薄引用是 LDVH 写入、配置或安装到该入口中的接入措施；不等于信息不足，细则应回到正式规范、环境能力清单、管辖项目配置、行动编排、Code 实现或其他权威位置读取 |

规范保障要求定义要被保障什么，能力保障定义 LDVH 提供什么组合保障，保障机制定义组合中的具体机制，环境入口定义环境提供什么承载位置或机制，环境适配定义能力资产如何接入当前环境，部署执行定义当前环境中的实际写入、安装、配置或启用动作，适配检查定义如何确认当前环境适配真实有效。只有部署执行完成且适配检查通过的当前现场有效结果，才可称为落地。

规范保障要求类型以 `specs/04.01-规范保障声明规范.md` 为准。术语规范不手写维护完整类型枚举，避免 04.01 新增、删除或调整类型语义后形成第二事实源。

## 8. 构成要素与环境能力术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 开发环境 | LDVH 五类构成要素之一，提供 AI 与 Human 实际执行工作的环境能力 | 开发环境是构成要素类型，不等于某个具体环境实例；不是最终事实源 |
| 事实模型 | LDVH 五类构成要素之一，用于承载项目工作事实、对象字段、状态和验收规则 | 通用规则由 `specs/05-工作模型基础规范.md` 承载 |
| 工作对象 | 依据事实模型创建、维护和检查的具体事实实例，例如 WorkCase、ADR、Spark、Pitfall 或 Study | 不等同于普通 Markdown 文档；具体对象字段、状态或特殊承载方式由对应事实模型规范定义；管辖项目配置和 Git 提交记录不是工作对象 |
| WorkCase / 工作项 | LDVH 用于承载一次可验收工作的目标理解、范围边界、验收标准、执行编排摘要、验证证据、关闭判断和经验分流的工作项对象 | 是 Human 与 AI 对齐工作的核心工作对象；不等同于环境中的 Plan Mode、聊天计划、执行草稿或普通计划文本 |
| WorkCase Draft / 工作项草案 | WorkCase 正式创建或进入可执行状态前，用于对齐目标、范围、验收标准、执行编排和 Human Gate 的计划草案 | 不作为独立工作对象；经确认后应吸收到 WorkCase、Spark、ADR 或其他权威位置 |
| 执行编排 | WorkCase 内部用于组织 AI 执行顺序、依赖关系、角色分配、复查安排和证据回收的结构化安排 | 服务 AI 调度和上下文恢复；不替代 WorkCase 的目标、验收标准、验证证据或关闭判断 |
| ExecutionItem / 执行项 | WorkCase 内部执行编排中的最小可恢复节点，用于表达某项执行活动的标题、角色、状态、依赖、最近结果、下一步和证据引用 | 不是独立事实模型，不单独进入 `ldvh-base/`，不作为 Human 直接管理入口 |
| Role Contract / 角色契约 | 用于规范专业 Agent 或专业审查视角的目的、输入、必读材料、允许动作、禁止动作、输出格式、交还对象和停止条件的能力契约 | 不是工作对象，不等同于某个 Agent 实体；可调用性、部署适配方式和环境适配由开发环境、能力资产和行动编排规范承接 |
| 事实模型字段 | 事实模型或工作对象中用于承载特定事实、关系、状态、证据或引用的字段 | 字段命名和公共语义由 `specs/05.01-工作模型字段定义与语义规范.md` 定义，内容格式由 `specs/05.02-工作模型字段内容与格式规范.md` 定义，注册与消费元数据由 `specs/05.03-工作模型字段注册与消费规范.md` 定义 |
| 字段内容格式 | 事实模型字段中用于组织叙述、清单、证据、决策、引用或结构化值的内容表达格式 | Narrative、Checklist、验证证据、Decision 等是内容格式，不是工作对象；不得把验证证据或 Decision 直接当作对象实例 |
| 对象状态 | 单个工作对象实例在其状态机中的状态 | 只适用于具备对象状态机的工作对象；不得泛化为集合状态、检查过程状态或派生状态 |
| 集合状态 | 集合、索引或清单对一组对象、文档或条目的汇总状态 | 不等同于单个对象状态；不得直接驱动对象状态流转 |
| 检查过程状态 | 一次检查、校验、验证或审计过程中的临时执行状态 | 不是长期事实源状态，稳定结论需要回写到对应权威位置 |
| 派生状态 | 由工具、Web、报告或查询结果根据事实源计算出的展示状态 | 不是事实源本体；不得替代对象状态、集合状态或正式规范判断 |
| Git 提交记录 | 由 Git commit records 承载的事实源修改追溯证据 | 不是工作对象，不进入 20-39 事实模型集合；不得把 Git 提交记录误写成独立 YAML 对象 |
| 行动编排 | LDVH 五类构成要素之一，用于约束 AI 如何识别场景、读取事实、执行、验证、回写和暂停 | 通用规则由 `specs/06-工作流程基础规范.md` 承载 |
| Code | LDVH 五类构成要素之一，用于确定性执行、解析、校验、聚合、测试、上下文压缩和受控写入 | 工具、脚本、校验器和命令入口都是 Code 的实现形态 |
| Web | LDVH 五类构成要素之一，用于 Human-facing 展示、确认、授权、验收和受控轻写入 | Web 页面状态不是最终事实源 |
| 受控写入 | 由正式规范、行动编排、Code 校验、权限边界或 Human Gate 约束的写入动作 | 不等于任意文件修改；高影响写入、状态流转、长期配置和权限扩大必须遵守对应 Human Gate |
| 受控轻写入 | Web 在规范授权范围内，对已定义字段、状态或人工标记执行的有限写入 | 不是开放式事实源编辑；写入入口、校验规则和事实源回写仍必须由对应 Code 能力或正式规范约束 |
| Rules / Instructions | 环境中用于入口可见、硬约束摘要、事实源边界提示或项目入口提示的能力或实体 | 只是适配措施，不是最终规范事实源 |
| Skill | 环境中用于复用多步骤流程、标准化输入输出或受控检查步骤的能力或实体 | 不负责调度子 Agent；需要稳定触发时应组合 Hook、CI、自动运行或降级检查 |
| LDVH 自建 Skill | 由 LDVH 为承接自身行动编排、治理动作、检查步骤或适配措施而创建或要求维护的 Skill | 不等于管辖项目业务 Skill、第三方环境 Skill 或一次性实验 Skill |
| LDVH 包装 Skill | LDVH 为封装、调用或约束第三方能力、项目能力或既有流程而维护的 Skill | 不改变被包装能力的事实源边界，也不得绕过 LDVH 自建 Skill 的正文边界要求 |
| Agent | 环境中用于独立上下文、专项视角、并行审查或权限边界差异的能力或实体 | Agent 输出必须回到主控或 Human，稳定结论回写后才生效 |
| Hook / 自动触发 | 环境中用于生命周期事件触发、提醒、阻断、记录或自动检查的能力或实体 | 不定义规范正文或行动编排本身 |
| MCP / 模型上下文协议 | 环境中用于向 AI 提供外部工具、数据源或上下文扩展的协议和连接能力 | MCP 是环境能力类型之一，不是 LDVH 构成要素；MCP Server 输出不是最终事实源；LDVH 不自建 MCP Server 作为核心能力 |

Tools 和 PyTools 不作为核心构成要素或独立机制术语。需要指向具体实现时，优先使用 Code、工具、脚本、校验器、命令入口或 `code/` 目录实现。

“事实模型 / 行动编排”是当前正式表达；“工作模型 / 工作流程”仅作为旧文件路径、机器字段、历史事实文本和兼容枚举中的保留表达。AI 在撰写新规范正文、总结规则或解释职责边界时应优先使用“事实模型 / 行动编排”；在引用现有文件路径、`doc_kind`、`ldvh_member.kind`、Code 内部键名、保障要求类型或 Git 历史事实时，应保留原始机器标识或路径文本，不得为了术语统一改写到不存在的路径或字段名。

## 9. 行动编排、运行闭环、初始化、审计与检查术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 运行闭环 | LDVH 从 Input、Plan、Execute、Verify、Record 到 Learn 的端到端质量闭环 | 不等同于单个工作对象、单个行动编排或单次检查 |
| 具体行动编排 | 40-59 区段中单一行动或行动族的执行规范，约束 Context、Scenario、Gate、执行、验证、回写和暂停 | 具体行动编排是行动编排构成要素在运行闭环中的组成单元 |
| 行动 | 由行动编排控制的一次执行或行动类别 | 不等同于行动编排全文、普通命令或任意步骤 |
| Scenario 识别条件 | 行动编排用于判断某个行动是否进入的场景条件 | 不应由 Rules / Instructions 维护完整正文 |
| 适用场景 | 文档、能力、入口或规则适合使用的普通范围说明 | 不等同于行动编排中的 Scenario 识别条件 |
| 步骤 | 具体行动编排内部的顺序动作 | 不等同于阶段标签、状态机或事实源状态 |
| 阶段标签 | 用于标识 Entry、Plan、Apply、Verify、Review、Recheck 等流程阶段的标签 | 不是状态机，不得作为对象状态或事实源状态使用 |
| Apply | 行动编排中执行已授权行动、写入、修复、生成或部署动作的阶段标签 | 中文名暂不固定；不得将未授权修复、危险写入或高影响变更直接并入 Apply |
| Verify | 行动编排中生成验证证据、证明结果成立或确认执行结果的阶段标签 | 不等同于 Human 已审核，也不等同于事实源已回写 |
| Review | 行动编排中审阅结果、证据、风险和建议的阶段标签 | 不等同于 Verify 或 Recheck；若产生批准、否决、放行或关闭权限，应进入审核或 Human Gate 语境 |
| Recheck | 修复、回写、复验或复审后再次检查的阶段标签 | 不替代 Verify、Review 或 Human Gate |
| Gate | 行动编排中的暂停、进入、退出、确认或授权条件 | Human Gate 是高影响场景中的人类确认机制 |
| Human Gate 记录 | Human Gate 触发时保留的轻量人类决策记录，最小应包含时间、决策、范围和约束 | 不是普通聊天摘要；不能被工具输出或 Web 页面状态替代；确认人、触发原因、风险说明、影响范围和执行前暂停证据可作为扩展字段或别名 |
| 落地 | 部署执行完成且适配检查通过后形成的当前现场有效结果 | 不作为长期状态登记；部署执行前、适配检查前或检查未通过时，应分别称为规范保障要求、能力保障、环境适配、部署执行或适配检查 |
| 环境确认 | 现场确认当前环境、权限、工具、入口、适配措施和适配降级的动作 | 不是长期状态登记；不得绑定到未在 40-59 成员自描述中标记为 active 的行动编排步骤 |
| LDVH部署与适配检查 | 面向 LDVH 部署适配结果、环境能力和缺口分流的行动编排候选主题 | 是否具备 active 统一行动编排、默认保障机制或可执行入口，应查询 40-59 成员主文件自描述和 Code 派生行动编排集合索引 |
| 部署适配检查报告 | 部署适配检查流程或人工检查形成的过程输出 | 不是长期状态文档，不替代工作对象事实源；其输出契约应由 active 行动编排或 Code 契约定义 |
| 检查 | 依据规范、工作对象、行动编排或 Code 契约，对文档、实例、行动、输出或适配措施进行符合性判断 | 检查结果不是最终事实源，稳定结论需要回写 |
| 校验 | 由 Code、工具、测试或 CI 执行的机械性规则判断 | 不替代人工检查、Human Gate 或语义验证 |
| 验证 | 通过测试结果、命令输出、证据链、人工确认或复现步骤证明某个结果成立 | 不等同于普通检查清单，也不等同于 Human 已审核或事实源已回写 |
| 审计 | 对规范、事实源、工作对象、流程、适配措施或运行闭环进行系统性、周期性或跨对象的合规审查 | 不应泛用为普通检查、校验或验证 |
| 审阅 | 阅读结果、证据、风险和建议并形成判断或意见的动作 | 不自带批准、否决、放行或验收含义 |
| 审核 | 带有批准、否决、放行、验收、关闭或授权含义的审查动作 | 高影响审核应进入 Human Gate 或对应授权流程 |
| 写入 | 对文件、字段、状态、配置或记录执行修改的动作 | 不自动表示稳定事实已进入权威事实源；应按写入对象判断是否需要受控写入或 Human Gate |
| 回写 | 将经过吸收、验证或确认的稳定结论写回对应权威事实源的动作 | 不等同于普通写入；推荐在需要强调事实源归属时写作事实源回写 |
| 事实源回写 | 将稳定事实写入正式规范、工作对象、Git 提交记录、Code / Web 实现文件或其他指定权威位置的回写动作 | 不得由缓存、页面状态、聊天摘要或工具临时输出替代 |

“工作闭环”不作为推荐术语；优先使用“运行闭环”。

## 12. 不推荐表达与替代写法

本节用于帮助 AI 识别不推荐表达，并改写为当前正式术语。正式产品资产不得保留不推荐表达作为兼容信息；历史事实记录、外部资料原文、docs/studies 或 temp 草稿中的原文引用只作为证据阅读，不得回流为当前术语口径。

## 13. 术语变更治理

术语变更治理用于防止局部文档隐式改写术语含义。

新增、改名、废止或改变本文定义的术语时，应先判断：

1. 是否影响 00 的五类构成要素、事实源原则或运行闭环标准；
2. 是否影响 01 的目录分区或编号分区；
3. 是否影响 03 的文档结构、引用或索引文档规则；
4. 是否影响 04 的规范保障要求、能力保障、保障机制、环境适配、适配措施或 AI 入口分层；
5. 是否影响 07 的 Code 实现边界；
6. 是否需要同步事实模型、行动编排、Web、事实源、运行闭环测试、非 LDVH 来源内容治理、第三方 Skill 接管选项或最佳实践规范；
7. 是否需要 Human Gate。

术语检查需求按三层处理：

| 检查层级 | 检查需求 | 处理方式 |
|---|---|---|
| 当前机械校验 | 不推荐裸词、不推荐表达、过往术语残留、removed 集合项被当作当前概念使用、非归口文档含子文档疑似二次定义已归口术语、非 02 文档设置二次术语定义章节、表格单元格、头部元信息和脚注中的二次定义句式 | 由 `code/specs_validate.py consistency` 和 `code/specs_validate.py index --fail-on-diagnostics` 承接；修改本文后应运行 `python3 code/specs_validate.py all --fail-on-diagnostics` |
| 后续 Code 候选 | 从本文术语表自动解析术语清单、不推荐表达、替代写法、允许定义归口和术语表必填列；检查 Code 常量是否与本文术语表同步 | 只有在本文表格结构稳定并形成正反样例后，才按 `specs/03-文档基础规范.md` §9.1 扩展 `code/specs_validate.py` |
| Human Gate | 改变核心术语定义、拆分或合并术语、删除替代表达、允许非 02 文档维护权威术语定义、改变 00 与 02 的层级关系 | 先说明影响范围、替代写法、受影响规范和残留 Code 缺口，再由 Human 判断是否生效 |

当前机械校验输出只是诊断入口，不替代本文的权威定义。若 Code 未覆盖某项术语检查需求，应把该需求记录为 Code 候选或待补齐事项，不得把人工阅读表述为完整机械校验通过。

## 15. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变五类构成要素的术语边界；
2. 将环境能力、环境实体或适配措施提升为最终事实源；
3. 将环境确认、部署执行或适配检查任一单项等同于落地；
4. 改变规范保障要求、能力保障、保障机制、环境适配、适配措施或 AI 入口分层之间的术语关系；
5. 改变 Code、工具、脚本、校验器或 `code/` 目录实现之间的术语边界；
6. 长期保留不推荐表达对照而不安排收敛；
7. 允许其他规范并行维护本文已定义术语的权威定义。

术语检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位来源 | 00 是本文的上位概念来源，本文未反向改写 00，00 未以本文作为自身规范依据 |
| 术语归口 | 术语定义归口本文，其他规范只说明应用规则，不通过章节、表格、示例或规范保障要求重复定义 |
| 落地 | 落地未被环境确认、部署执行或适配检查任一单项替代 |
| 环境适配 | 环境能力、环境实体和适配措施未混同 |
| AI 入口分层 | AI 入口分层被视为适配措施组织方式，不是正式规范或最终事实源 |
