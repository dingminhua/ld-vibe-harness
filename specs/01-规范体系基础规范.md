## 1. 本文解决的问题

本文定义一篇规范最低应具备什么结构，才能让 Human 判断、AI 行动、Code 解析同一份 Markdown 事实源。

本文解决：

1. 规范如何声明身份、状态、路径、父子关系和来源；
2. 规范正文应有哪些稳定章节角色；
3. 规范如何表达上位依据、价值判断、事实源边界和权威归口；
4. 引用关系如何显式写入正文，供 Code 生成行动指南；
5. 附件何时可以存在，以及为什么附件不得承载正文级规则；
6. AI 修改、迁移或新增规范时应按什么顺序行动；
7. Code 能检查什么，不能检查时如何记录缺口。

本文不定义事实模型字段、行动流程、Code 实现、Web 展示、Runtime 入口或 Git 提交规则。这些内容由对应下位规范承接。

## 2. 上位依据

本文承接 `specs/00-LDVH-v3理念与价值标准.md`。

本文不得重定义 00 的存在理由、AI 第一服务对象、六类构成要素、事实源原则或价值判断。本文只定义这些上位原则如何在规范正文中被声明、承接、引用、检查和停止。

若本文与 00 冲突，以 00 为准。若本文与 v2 01 冲突，本文只作为当前体系候选方向，不反向改写 v2 active 规范。

## 3. 构成要素归属与价值判断

本文属于六类构成要素中的规范体系。

| 价值 | 本文如何服务 | 减少的 AI 负担 |
|---|---|---|
| V1 快速定位 | 身份块、路径、父子关系和显式引用让 AI 快速找到入口 | 定位负担 |
| V2 可行动理解 | 稳定章节角色让 AI 快速判断目标、边界和本地规则 | 理解负担 |
| V3 正确判断 | 权威归口、附件边界和事实源边界降低误归口风险 | 判断负担 |
| V4 稳定执行 | 写作与修改顺序约束 AI 如何创建、迁移和修改规范 | 执行负担 |
| V5 门禁识别 | Human Gate / Stop Conditions 明确必须暂停的情况 | 停止负担 |
| V6 强制验证 | Code 消费边界和缺口处理让完成声明可验证 | 验证负担 |
| V10 持续完善 | 待补齐事项和 Code 缺口为后续改进保留入口 | 回写负担 |

本文不要求每篇规范服务全部价值。每篇规范必须说明自己真实服务哪些价值，不得为了填表虚构价值。

## 4. 适用范围与事实源边界

本文适用于：

1. `specs/` 中的规范正文；
2. 被规范正文显式引用的附件；
3. 规范迁移、修改、审核和 Code 解析过程。

规范规则的事实源是 Markdown 正文。identity block、表格、引用路径和 Stop Conditions 都是正文的一部分。

以下内容不是规范事实源：

1. Code 输出、行动指南、生成索引或诊断；
2. `_migration/` 中的扫描、样板和过程证据；
3. 测试 fixture、缓存、对话和一次性分析；
4. 未被正文引用的附件或表格。

这些内容可以作为证据、诊断或迁移辅助，但不能替代规范正文。

## 5. 规范身份、命名和路径

规范文件放在 `specs/` 下，文件名应包含稳定编号和标题。编号用于排序和引用，标题用于 Human 和 AI 识别。

规范必须包含 `v3_spec` identity block。字段闭集见 `specs/attachments/01.Att.01-规范身份字段表.md`。

附件必须包含 `v3_attachment` identity block。字段闭集见 `specs/attachments/01.Att.05-附件身份字段表.md`。

identity block 是正文的一部分。Code 可以解析它，但不得用它替代正文规则。

路径规则：

| 对象 | 位置 |
|---|---|
| 根规范 | `specs/{NN}-标题.md` |
| 成员规范 | `specs/{NN}-short-title-中文标题.md` |
| 附件 | `specs/attachments/{父编号}.Att.{NN}-标题.md` |
| 迁移证据 | `_migration/` |

不得手写全量目录作为规范事实源。目录、清单和索引应由 Code 从 Markdown 文件和 identity block 生成。

## 6. 正式规范必要信息角色

规范正文应具备稳定信息角色。角色表见 `specs/attachments/01.Att.02-规范信息角色表.md`。

信息角色不是固定章节模板。后续规范不得为了满足形式而机械铺开 01 的全部章节；同一章节可以承载多个角色，短规范可以用更少标题表达，只要 Human、AI 和 Code 能稳定识别。

所有正式规范必须提供以下角色：

1. identity block：让 Code 定位、回指和判断状态；
2. 本文解决的问题：让 Human 和 AI 判断是否该读；
3. 上位依据：让 AI 判断权威来源和冲突处理；
4. 构成要素归属与价值判断：让 Human 和 AI 判断存在理由；
5. 适用范围与事实源边界：让 AI 知道适用、不适用和事实源；
6. 本地规则：只写本规范相对上位规范新增、细化或例外的内容；
7. 验证与证据：让 AI 知道如何确认规则已满足、证据回指哪里；
8. Human Gate / Stop Conditions：让 AI 知道何时停止；
9. 待补齐事项：让未闭合问题进入 next queries；没有缺口时应显式写无。

以下角色按触发条件出现：

| 角色 | 触发条件 |
|---|---|
| 引用关系 | 本规范依赖、影响或消费其它规范、附件或事实对象 |
| 附件边界 | 本规范授权附件 |
| 保障要求 | 本规范提出需要执行、验证或分流的复杂规则 |
| Code 覆盖与缺口 | 本规范声明 Code 可检查内容，或存在应由 Code 检查但尚未覆盖的规则 |
| 写作与修改顺序 | 本规范治理某类文件、对象或行动的创建与修改 |
| 专题成员与专属骨架 | 本规范作为父规范管理成员规范 |

缺少必需角色时，Code 应输出诊断，AI 不得声称规范结构完整。缺少条件角色时，Code 应先判断触发条件是否存在；未触发时不得要求空章节。

验证与证据角色只要求最小确认口径，不要求展开测试计划。若验证必须依赖复杂机制，再触发保障要求或 Code 覆盖与缺口角色。

## 7. 权威域、定义归口与吸收规则

规则应写入最小权威归口。

| 内容 | 归口 |
|---|---|
| 最高价值和准入判断 | 00 |
| 规范写法、引用、附件和治理规则 | 01 |
| 事实模型字段、状态和实例边界 | 02 及事实模型成员 |
| 行动流程、Context、Scenario、Gate | 03 及行动成员 |
| Code 输入、输出、诊断和实现边界 | 04 |
| Web、Runtime、Git、测试等规则 | 对应下位规范 |

附件、Code、行动指南、测试和迁移证据不得反向定义正文规则。若发现下游需要新增规则，应回到对应正文规范吸收。

## 8. 术语与表达最小纪律

术语治理只服务行动和解析，不建立独立大词典。

术语进入正文的条件：

1. 影响 AI 行动判断；
2. 影响 Code 解析；
3. 影响 Human Gate、事实源边界或权威归口；
4. 多篇规范反复使用且容易误解。

表达要求：

| 要求 | 说明 |
|---|---|
| 明确定语 | 避免“这个”“那个”“相关内容”等漂移表达 |
| 明确主体 | 说明 Human、AI、Code、规范、附件或事实源谁承担责任 |
| 明确边界 | 说明适用、不适用、停止和回写位置 |
| 避免空泛 | 不写不能指导行动或解析的原则性套话 |

## 9. 引用关系与行动指南输入

引用关系必须显式写在正文或 identity block 中。关系类型见 `specs/attachments/01.Att.03-引用关系类型表.md`。

引用关系至少服务：

| 行动指南要素 | Markdown 来源 |
|---|---|
| relationships | `parent_spec`、`basis`、`related_specs`、路径引用 |
| read_plan | 上位依据、本地规则、显式引用 |
| impact_judgment | scope、positioning、code_consumption、相关规范 |
| stop_conditions | Human Gate、Stop Conditions、禁止项、状态 |
| next_queries | 待补齐事项、缺失引用、未确认迁移项 |
| verification | Code 消费类别、测试或等价验证说明 |
| source_refs | canonical path、basis、附件引用和事实对象引用 |

行动指南由 Code 从 Markdown 生成，不手写成规范正文或附件。

## 10. 附件规则

附件只是正文的附属内容。正文必须先成立，附件只能被正文引用。

允许进入附件：

1. 正文引用的表；
2. 正文引用的图；
3. 字段闭集；
4. 枚举；
5. 纯数据矩阵；
6. 多篇规范复用且不包含规则解释的机器契约。

不得进入附件：

1. 上位原则；
2. 核心规则；
3. 行动流程；
4. Human Gate；
5. 事实源边界；
6. 大段解释；
7. 迁移过程；
8. 可由 Code 生成的目录、关系图、检查清单或读取路线。

本规范当前只建立五个附件：

| 附件 | 类型 | 为什么需要 |
|---|---|---|
| `01.Att.01-规范身份字段表.md` | 字段闭集 | identity block 字段需要 Code 稳定解析 |
| `01.Att.02-规范信息角色表.md` | 角色表 | 信息角色需要跨规范复用 |
| `01.Att.03-引用关系类型表.md` | 枚举 | 关系类型需要 Code 稳定投影 |
| `01.Att.04-保障要求字段表.md` | 字段表 | 保障要求字段需要规范间一致 |
| `01.Att.05-附件身份字段表.md` | 字段闭集 | 附件身份需要 Code 稳定盘点和回指 |

附件不得增加本文没有授权的规则。

## 11. 专题成员与专属骨架规则

成员规范可以有专属骨架，但专属骨架由成员所属父规范定义。

| 成员类型 | 归口 |
|---|---|
| 事实模型成员 | 02 |
| 行动编排成员 | 03 |
| Code 需求、命令、诊断 | 04 |
| Web、Runtime、Git、测试成员 | 对应下位规范 |

本文只要求成员规范声明父规范、关系、身份、事实源边界和本地 delta，不定义成员专属流程。

## 12. 规范保障要求

规范保障要求用于说明某条规范规则如何被执行、验证或分流。字段表见 `specs/attachments/01.Att.04-保障要求字段表.md`。

保障要求不得写成重复长清单。能由 Code 检查的，交给 Code 诊断；需要行动闭环的，交给行动编排；需要 Human 判断的，进入 Human Gate。

最小表达：

| 字段 | 作用 |
|---|---|
| 要求 | 需要保障什么 |
| 机制 | 通过正文规则、Code、测试、行动编排或 Human Gate 如何保障 |
| 触发 | 什么变化会触发检查 |
| 证据 | 完成或阻塞时回指哪里 |
| 缺口处理 | 不能验证时如何记录和分流 |

## 13. Human Gate / Stop Conditions

以下情况必须暂停并等待 Human 确认：

1. 改变 00 的价值锚点、AI 第一服务对象、六类构成要素或事实源原则；
2. 改变本文定义的必要章节、身份字段、附件边界、权威归口或 Human Gate；
3. 新增、删除、合并、拆分或重命名规范；
4. 将附件、Code 输出、行动指南、迁移证据或对话升级为规则事实源；
5. 删除本地 Human Gate、事实源边界、验证要求或回写要求；
6. 让 Code 或行动指南输出授权语义；
7. 顺手修改 Runtime、hook、dispatcher、rules、skills 或 Web 策略。

AI 可以准备事实源、影响范围、风险和选项，但不得把 AI 结论、Code 校验或行动指南替代 Human Gate。

## 14. 规范写作与修改执行顺序

AI 新增、迁移、修改或审计规范时，按以下顺序执行：

1. 读取 00、本文、目标规范和上位依据；
2. 判断目标内容减少哪类 AI 负担；
3. 判断最小权威归口；
4. 判断是否触发 Human Gate；
5. 写入或修改 Markdown 正文；
6. 只在正文需要附属表、图、字段闭集或枚举时新增附件；
7. 检查 identity block、章节角色、引用关系、附件引用和 Stop Conditions；
8. 运行 Code 校验；没有 Code 覆盖时记录缺口；
9. 评估行动指南能否从正文结构生成；
10. 将迁移过程和未定事项留在 `_migration/`、Spark 或 WorkCase，不写入正式规范。

不得先复制 v2 长正文再事后删减。应先映射职责，再写正文。

## 15. Code 覆盖与缺口处理

Code 应优先检查：

1. identity block 字段；
2. canonical path 与文件路径一致性；
3. parent、basis、related refs 是否存在；
4. 必要章节角色是否可识别；
5. 附件是否被正文引用；
6. 附件是否只承载附属表或闭集；
7. Stop Conditions 是否存在；
8. 行动指南是否能生成 source refs、read_plan 和 next_queries。

没有 Code 覆盖时，AI 必须记录：

| 项目 | 说明 |
|---|---|
| 缺口 | 哪项规则无法确定性检查 |
| 临时核对 | 当前如何人工检查 |
| 风险 | 不检查会造成什么误判 |
| 后续 | 应由哪个规范、Code 或 WorkCase 承接 |

Code 缺口未处理前，不得声称该规则已被完整确定性验证。
