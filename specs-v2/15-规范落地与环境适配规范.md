# 规范落地与环境适配规范

> 创建日期：2026-06-08
> 定位：定义 LDVH v2 正式规范如何声明规范落地要求、绑定保障机制、通过环境适配映射转化为运行投影，并处理规范变更后的同步与漂移检查
> 适用范围：LDVH `specs-v2/` 正式规范、后续环境适配映射、运行投影同步、规范变更审计和漂移检查
> 上位依据：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs-v2/03-文档基础规范.md`、`specs-v2/03.01-规范文档规范.md`、`specs-v2/14-Code实现规范.md`

---
## 1. 本文解决的问题

本文解决 LDVH v2 正式规范如何从文本规则进入运行的问题。

正式规范不能只停留在正文中。凡是需要被 AI、Human、Code、Web、子 Agent、Skill、Hook、Rules、CI 或其他环境能力持续消费的稳定规则，都应说明该规范要落地需要满足哪些要求、这些要求由什么保障机制执行、具体环境如何适配，以及适配后形成哪些运行投影。

本文不替代 03 的文档工作区规则，不替代 14 的 Code 实现规则，也不直接维护 Codex、Trae、Claude Code、Cursor 等环境的具体文件路径。具体环境实体由后续环境适配映射文档或运行投影同步记录定义。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 由开发环境、工作模型、工作流程、Code 和 Web 五类构成要素共同形成 AI 工程驾驭体系，并要求规范驱动的 AI 工作 Harness 能够可规划、可执行、可验证、可沉淀、可演进。

本文承接 00 的要求，定义规范从权威文本进入运行环境的中间层：

```text
正式规范
→ 规范落地要求
→ 保障机制
→ 环境适配映射
→ 运行投影
```

00 自身的原则不直接写成具体 Rules、Skill、Hook、Code 或 Web 页面。00 的原则如需运行，应先被对应专项规范吸收为可执行规则，再由专项规范按本文声明规范落地要求和保障机制。

---
## 3. 基本概念

### 3.1 规范落地要求

规范落地要求用于说明一条稳定规范要落地，需要满足哪些要求。

规范落地要求回答：

1. 这条规范要被 AI 看见吗；
2. 这条规范需要被流程复用吗；
3. 这条规范需要子 Agent 独立、专项或并行思考吗；
4. 这条规范需要确定性执行或校验吗；
5. 这条规范需要 Human 交互、确认或展示吗；
6. 这条规范需要在某个生命周期事件上稳定触发吗；
7. 这条规范是否是上位约束，需要后续规范承接。

规范落地要求不是环境实体，不应直接写成 Rules、Skill、Agent、Hook、CI、命令、Web 页面或工具文件。

### 3.2 保障机制

保障机制用于说明规范落地要求由什么规则、检查、流程、Code、Human Gate、子 Agent 思考、环境触发或审计动作保障执行。

规范落地要求必须绑定保障机制。只写“需要上位约束承接”“需要生命周期触发”“需要确定性执行”，但没有说明由什么保障执行，不构成完整落地声明。

保障机制可以是单一机制，也可以是组合机制。例如“规范变更后必须校验”通常需要入口提示、Code 校验、生命周期触发和降级记录共同保障。

### 3.3 环境适配映射

环境适配映射用于说明某项规范落地要求和保障机制，在特定开发环境中通过哪些机制、文件、配置、命令、工具、页面或降级策略实现。

环境适配映射回答：

1. 当前环境是否支持该落地要求；
2. 支持时映射到哪个环境机制或实体；
3. 调用入口、文件路径、配置位置或命令是什么；
4. 验证方式是什么；
5. 不支持时如何降级，是否需要 Human Gate 或后续任务。

环境适配映射不得反向改写规范本身。

### 3.4 运行投影

运行投影是环境适配映射后实际生成、维护或调用的入口、文件、命令、配置、工具、页面、Skill、Agent、Hook、CI 检查或摘要。

运行投影用于帮助 AI 和 Human 在具体环境中执行、看见、检查或同步规范，但运行投影不是最终事实源。运行投影与 specs-v2 正式规范冲突时，以 specs-v2 正式规范为准。

## 4. 规范落地要求类型

正式规范可以声明以下规范落地要求：

| 落地要求 | 含义 | 常见保障机制 |
|---|---|---|
| 上位约束承接要求 | 该规范作为上位依据，需要后续正式规范、检查流程或 Human Gate 持续承接 | 上位依据字段、总纲一致性检查、专项规范转化、Human Gate |
| 入口可见要求 | AI 进入项目、文档工作区或任务场景时需要看见该规范摘要、边界或入口 | 入口摘要、项目说明、Rules / Instructions 映射、目录入口 |
| 流程复用要求 | 该规范中的重复步骤需要被封装成可复用流程 | Skill、命令、工作流程、操作清单 |
| 子 Agent 思考要求 | 需要脱离主上下文、使用特定专业视角、或并行展开多个视角 | 子 Agent、独立审阅、并行审查、专项检查 |
| 确定性执行要求 | 该规范需要稳定的解析、校验、聚合、测试、上下文压缩或受控写入 | Code、测试、校验命令、CI、脚本 |
| Human 交互要求 | 该规范需要 Human 看见、确认、授权、验收或轻写入 | Human Gate、Web、对话确认、审批提示 |
| 生命周期触发要求 | 该规范需要在提交、写入、修改、停止、子 Agent 完成等事件上稳定触发 | Hook、CI、自动运行、定时任务、降级检查 |

子 Agent 思考要求中的独立、专项、并行是可组合维度。一个场景可以要求多个独立 Agent 分别从文档一致性、Code 可验证性和环境适配风险等视角并行审查后汇总。

## 5. 规范落地要求声明规则

正式规范文档应在“规范落地要求”段落中声明自身稳定规则的落地要求。

规范落地要求至少包含：

| 字段 | 含义 |
|---|---|
| 落地要求 | 采用 §4 中的类型 |
| 要求内容 | 该要求具体要保障什么 |
| 保障机制 | 由什么规则、检查、流程、Code、Human Gate、子 Agent 思考或生命周期触发保障执行 |
| 同步类型 | 初始化、入口摘要、校验实现、流程复用、展示同步、审计输入等 |
| 触发条件 | 规范变更、字段契约变化、Human Gate 变化、运行投影漂移、环境迁移等 |

必要时可以补充来源章节、验证方式、降级处理和是否需要环境适配映射。

不直接定义稳定规范规则的说明性文档不默认需要声明规范落地要求。目录说明、编号索引、迁移状态索引、evals、refs、README 和项目资料文档，应先把稳定结论吸收到正式规范后，再由正式规范声明规范落地要求。

---
## 6. 保障机制规则

规范落地要求必须说明保障机制。保障机制可以来自以下来源：

1. **规范结构保障**：上位依据、相关规范、正式规范骨架、章节要求、检查清单；
2. **Code 保障**：确定性校验、测试、解析、聚合、上下文压缩、受控写入；
3. **流程保障**：可复用步骤、Skill、工作流程、命令入口；
4. **子 Agent 保障**：独立审阅、专项视角、并行检查、汇总报告；
5. **Human Gate 保障**：人工确认、授权、验收、暂停和风险判断；
6. **生命周期触发保障**：Hook、CI、自动运行、定时检查、会话停止检查；
7. **环境映射保障**：具体环境中可用的规则入口、配置、工具、页面或降级策略。

保障机制不得绕过事实源边界、Human Gate 或 Code 验证纪律。保障机制无法完整实现时，应记录降级方式和残留风险，不得表述为完整落地。

---
## 7. 环境适配映射规则

环境适配映射应以规范落地要求为输入，不得以某个环境已有能力反向决定规范需要什么要求。

环境适配映射至少说明：

| 字段 | 含义 |
|---|---|
| 环境 | Codex、Trae、Claude Code、Cursor、CI、Web 或其他环境 |
| 落地要求 | 被适配的规范落地要求 |
| 保障机制 | 在该环境中使用的机制组合 |
| 运行投影 | 具体文件、配置、命令、Skill、Agent、Hook、页面或降级记录 |
| 验证方式 | 如何确认运行投影存在、可用、未漂移 |
| 降级方式 | 环境不支持时如何处理 |

不同环境可以用不同方式满足同一要求。例如生命周期触发要求在 Codex 中可以映射为 Hook，在 CI 中可以映射为工作流检查，在 Trae 中可能映射为 Rules、自动运行、SOLO Agent 编排或人工降级检查。

---
## 8. 运行投影同步与漂移

运行投影同步包括初始化同步和规范变更后的增量同步。

初始化同步用于第一次把规范落地要求映射到当前环境。规范变更同步用于在正式规范发生变化后检查对应运行投影是否需要更新。

运行投影出现以下情况时，应视为漂移风险：

1. 正式规范已变化，但入口摘要、Skill、Hook、Code、Web 或 CI 未同步；
2. 运行投影复制旧正文，和 specs-v2 正式规范冲突；
3. Code 校验逻辑与正式规范的检查要求不一致；
4. Web、Skill、Agent 或 Hook 依赖的路径、字段或规则已过期；
5. 环境不支持某落地要求，但没有降级记录；
6. 运行投影被当成事实源反向修改规范。

漂移检查可以由 Code、子 Agent 思考、Human Gate 或环境触发机制共同完成。检查结果不是最终事实源；需要保留的结论应回写到正式规范、Task、Memo、ADR、审计报告或其他权威位置。

---
## 9. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续正式规范声明规范落地要求时，应遵守本文定义的字段、类型和边界 | `specs-v2/03.01-规范文档规范.md` 正式规范骨架、规范文档检查 | 文档治理 | 本文 §4-§7 变化时 |
| 入口可见要求 | AI 修改 specs-v2 正式规范时应能定位本文作为规范落地与环境适配权威入口 | 规范文档入口摘要、相关规范引用 | AI 执行入口提示 | 本文定位、适用范围或关键术语变化时 |
| 确定性执行要求 | 文档检查 Code 应能识别“规范落地要求”章节并避免旧机制字段误判 | `tools/specs_validate.py` 或后续文档校验 Code | 校验实现 | 规范落地要求章节名、表格字段或正式规范骨架变化时 |
| 生命周期触发要求 | 正式规范变更后应检查是否影响运行投影和环境适配映射 | 环境 Hook、CI、Skill 流程或人工降级检查 | 触发保障 | 正式规范新增、重命名、删除、规范落地要求变化或环境迁移时 |

具体环境实体不在本文中声明，应由后续环境适配映射解释。

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变规范落地要求类型；
2. 改变保障机制字段或声明规则；
3. 允许正式规范直接把环境实体写成落地要求；
4. 允许运行投影成为最终事实源；
5. 改变环境适配映射与正式规范之间的权威边界；
6. 删除某项已被正式规范消费的保障机制或运行投影；
7. 扩大自动同步、自动写入或自动覆盖运行投影的范围；
8. 将不能机械验证的语义判断表述为完整 Code 校验通过。

规范落地与环境适配检查至少包括：

| 检查项 | 标准 |
|---|---|
| 落地要求 | 正式规范声明的是要求，不是环境实体 |
| 保障机制 | 每项落地要求都有保障机制 |
| 环境映射 | 具体环境实体只出现在环境适配映射或运行投影中 |
| 事实源边界 | 运行投影未替代 specs-v2 正式规范 |
| 触发边界 | 必须稳定触发的要求未只依赖 Skill 自动调用 |
| Code 适配 | 可机械化检查已按 `specs-v2/14-Code实现规范.md` 判断和验证 |
| 降级处理 | 环境不支持时已记录降级方式和残留风险 |
