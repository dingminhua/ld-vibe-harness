> 适用范围：LD Vibe Harness 自身 `specs/` 规范正文区、`docs/` 根目录用户资产、`docs/studies/` 内部研究区和 `docs/sources/` 外部信源区

## 1. 本文解决的问题

本文是 LDVH 自身文档工作区的应用剖面规范。`specs/` 是 LDVH 规范资产和规范事实源，`docs/` 根目录 Markdown 文档是用户资产或项目文档资产，`docs/studies/` 和 `docs/sources/` 是可变资料区。本文继承文档基础规范的文档工作区契约、命名、结构、引用和吸收规则，只规定 LDVH 自身项目的特有规则。

LDVH 自身规范工作区的三分映射如下：

```text
specs/             LDVH 正式规范资产和规范事实源
docs/studies/      LDVH 内部研究、评估和吸收候选
docs/sources/      LDVH 外部资料和客观信源
```

`docs/studies/`、`docs/sources/` 和用户明确指定的参考与研究材料只提供分析输入；其中稳定结论必须先吸收到 `specs/`、工作对象、ADR、Task、Memo 或 Pitfall 后才生效。`specs/` 正式规范不得出现指向 `docs/`、外部 URL、外部项目资料或非 LDVH 资产的依据性引用。

## 2. specs 正文区

### 2.1 正文区定位

`specs/` 根目录正文区承载 LDVH 正式规范资产和规范事实源。正式规范可以定义稳定规则、对象边界、字段契约、状态机、工作流程、Human Gate、规范落地要求和检查要求。

正式规范正文区不得出现指向 `docs/`、外部 URL、外部项目资料或非 LDVH 资产的依据性引用，也不得把 `docs/studies/`、`docs/sources/` 或参考与研究材料作为规范依据。外部或研究内容只有被改写并吸收到 `specs/` 正文区后才成为正式规则；长期决策可以进入 ADR；可执行工作或暂存发现可以进入 Task、Memo 等工作对象；已解决且可复用的踩坑经验可以进入 Pitfall，但这些对象不因此成为规范规则。

正式 specs 采用规则态写法。specs 正文只定义当前有效规则、契约、流程、边界和状态判定方法，不记录历史迁移、旧编号、旧文件名、退回过程、来源演化、废弃说明、执行结果或状态实例。状态实例必须由目录、索引、事实源、Code 输出、环境适配记录或 Human Gate 记录查询得到；历史信息如需保留，应进入 ADR、Task、docs/studies 或 Git history。

所有 specs 正式规范文档都应设置规范落地要求段落，用于说明该规范要落地需要满足哪些要求。目录说明、studies、sources、Code 派生索引输出和其他不直接定义稳定规范规则的说明性材料，不默认属于正式规范文档，不要求设置规范落地要求段落；若其中内容被升级为稳定规则，应吸收到对应正式规范后再声明规范落地要求。工作模型和工作流程集合状态不再由手写集合索引文档承载，而由成员主文件自描述和 Code 派生视图共同服务读取与检查。

### 2.2 编号分区

specs 正文区使用当前编号分区。编号分区、编号占用和新增编号判断由目录说明承接。

正式规范文档使用两位编号，文件名格式使用“NN-标题”加 `.md` 后缀。子文档使用“NN.SS-标题”加 `.md` 后缀。`NN.SS` specs 子文档必须声明 `所属主文档`、`关系`、`适用范围` 和 `上位依据`；`所属主文档` 与 `上位依据` 通常都指向父规范，`关系` 用于说明应用剖面或专题子文档性质。结构化契约文件沿用既有编号时，必须遵守本文 §6。

### 2.3 正式规范文档骨架

正式规范文档建议采用以下骨架。骨架中标注【必填】的章节为强制要求，未标注的为建议结构；审计时仅检查必填章节，不得将建议章节缺失判定为违规。

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`

---
## 1. 本文解决的问题【必填】

## 2. 与 00 总纲的关系

## 3～N-2. 核心规则

## N-2. 规范落地要求【必填】

## N-1. Human Gate 与检查要求【必填】

## N. 待补齐事项
```

具体工作模型规范文档骨架由 `specs/03.02-工作模型文档规范.md` 定义；具体工作流程规范文档骨架由 `specs/03.03-工作流程文档规范.md` 定义。其他专项规范如无专用文档规范，应先遵守本文正式规范文档骨架。00 总纲作为顶层文档，可不声明上位依据；00 的 §1 可以使用产品存在理由或总纲叙事标题，不强制命名为“本文解决的问题”，但不得因此改变其他正式规范的标准骨架要求。

00、02 和其他正式规范的引用层级应遵守：

1. 00 是 LDVH 上位概念来源，不应把 02 作为自身上位依据、相关规范或一致性检查标准；
2. 02 应以上位依据承接 00，并负责术语边界、推荐用语、不推荐表达处理和术语变更治理；
3. 其他正式规范涉及产品定位、五类构成要素、事实源原则、运行闭环或 Human Gate 时，应按需要引用 00；
4. 其他正式规范涉及术语定义、不推荐表达处理、术语归口或术语变更治理时，应引用 02，不得并行维护同一术语定义；
5. 同一文档可以同时引用 00 和 02，但应分别说明上位原则承接和术语口径承接，不得混用。

正式规范文档不得设置“本文不做什么”“边界说明”等反向边界章节。职责边界应通过定位、适用范围、上位依据、相关规范和正文正向规则表达。

正式规范文档设置 `相关规范` 时，应遵守 `specs/03-文档基础规范.md` §6.4 的引用方向规则。`相关规范` 是当前文档的读取依赖、字段契约依赖、同步依赖或检查依赖，不是“谁引用了本文”的反向清单；被引用文档不得仅因下游文档引用它而把下游文档登记回来。

## 3. docs/studies

`docs/studies/` 继承文档基础规范 §3.4 和 §3.6 的 studies 与吸收规则。本文只规定 LDVH 自身项目中的特例。

docs/studies 文档特例：

1. `docs/studies/` 承载 LDVH 内部评估、设计探索、方案比较、外部项目借鉴分析和项目内部临时参考；
2. docs/studies 可以引用 specs 正文区作为评估依据和上位规范；
3. 稳定规范规则必须吸收到 specs 正文区后，才能被正式规范文档作为规则消费；
4. 长期决策可以吸收到 ADR，可执行工作或暂存发现可以吸收到 Task、Memo 等工作对象，已解决且可复用的踩坑经验可以吸收到 Pitfall，但不得被正式规范直接当成规则引用；
5. docs/studies 文档头部必须声明 `来源`，来源应指向被评估材料、用户输入、外部资料、调研对象或其他真实输入，不得只指向关联 Task；
6. docs/studies 文档头部可以设置 `关联对象`，用于登记相关 WorkArea、TaskPlan、Task、SubTask、ADR、Memo、Pitfall 或其他工作对象；该字段可以为空，且不得替代来源；
7. docs/studies 文件名应使用自然序号加 `LDVH` 前缀标识，格式为 NN-LDVH{评估主题}.md 或 NN-LDVH-{评估主题}.md，表示该文档是 LDVH 内部相关评估、分析或参考材料；
8. docs/studies 不需要 Human Gate 与检查要求章节。

docs/studies 文档建议采用以下骨架。骨架中标注【必填】的章节为强制要求，未标注的为建议结构；审计时仅检查必填章节，不得将建议章节缺失判定为违规。

> 调研边界：不直接构成强制规则
> 执行效力：无；规范规则需进入 specs 正文区，决策或工作事实需进入对应工作对象后才生效
> 来源：{被评估材料、用户输入、外部资料或其他真实输入}
> 关联对象：{WorkArea / TaskPlan / Task / SubTask / ADR / Memo / Pitfall / 其他工作对象，可为空}
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`

## 6. 能力材料归属与结构化契约

### 6.1 能力材料归属

能力相关内容应按能力归属进入对应权威位置，不作为工作模型或工作流程的默认完整性要求。

新增或稳定后的能力内容应按能力归属进入对应权威位置。相关权威位置尚未创建或尚未生效时，应进入候选事项、计划或待补齐事项，不得引用 `docs/`、外部 URL、外部项目资料或非 LDVH 资产作为正式规范依据：

1. 主规范规范落地要求；
2. 04 系列环境适配相关规范；
3. 工作流程基础规范；
4. Code 确定性执行实现规范；
5. Web 信息同步实现规范；
6. 运行 Rules / Skill 实体、Agent 定义摘要或结构化契约。

### 6.2 能力材料边界

能力材料不是独立规范，也不是工作模型或工作流程完整性的默认要求。能力材料只能说明对应模型或流程在某个机制下如何实践，不得重新定义主模型、主流程、字段契约、状态机、Context、Scenario、Gate、事实源边界或 Human Gate。

能力材料中的有效内容应随相关主规范、04 系列、07、08 或适配措施吸收。能力材料不作为当前 specs 的读取入口。

### 6.3 结构化契约

结构化契约可以作为字段契约、schema 或接口契约存在。新增或稳定后的契约优先回并到主规范契约章节，或由 Code 和 Web 实现消费主规范契约。对应主规范尚未创建或尚未生效时，应记录为候选事项、计划或待补齐事项。

## 7. 规范落地要求与环境适配

LDVH 将规范到运行环境的同步拆成三层：

1. **规范落地要求**：说明某段稳定规范要落地，需要满足哪些要求，例如入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求、生命周期触发要求等；
2. **LDVH 能力保障**：说明 LDVH 用哪些能力组合保障规范落地要求；
3. **环境适配**：说明 LDVH 如何基于环境客观能力清单，将能力保障主动适配为环境入口、适配措施、检查、降级和缺口记录。

规范落地与环境适配的父规范入口是规范落地与环境适配基础规范。正式规范只声明规范落地要求和保障机制；LDVH 能力保障、适配措施、环境能力清单、环境适配、LDVH 落地特别要求和个人落地特别要求，应分别按 04 系列对应子文档处理。

规范落地要求不是普通引用、文档重要性声明或上位依据声明。规范落地要求的类型、字段、保障机制和“不得直接把具体环境实体写成要求本身”的规则，以规范落地声明规范为权威；本文只要求 specs 正式规范在创建、修改或审计时回到 04.01 检查该段落。

若某项规则要求在特定时机稳定触发，应声明生命周期触发要求，并由 LDVH 能力保障和环境适配决定该环境使用 Hook、CI、自动运行、规则条件、Skill 组合或降级检查实现。具体环境实体不得直接写入普通规范落地要求表，除非该文档本身就是环境适配文档。

遇到“机制落地关系”或“机制承接关系”等不推荐表达时，应按术语规范的不推荐表达处理，先拆解为规范落地要求、LDVH 能力保障和环境适配。无法确认环境实体的内容，只能先进入规范落地要求、候选事项或待补齐事项。

## 8. specs 修改执行顺序

AI 新增、修改或审计 specs 正式规范文档时，应按以下顺序执行：

1. 根据任务场景确定基础入口：术语边界、不推荐表达处理或术语变更治理读取术语规范；文档工作区、命名、引用、studies/sources、子文档边界、定义归口、引用类型、反向补全或事实源归属读取文档基础规范；specs 正式规范、规范落地要求或能力材料归属读取本文；工作模型或工作流程集合读取成员主文件自描述和 Code 派生集合索引；规范落地、环境适配、环境能力清单、LDVH 落地特别要求或个人落地特别要求读取规范落地与环境适配基础规范；
2. 判断拟修改内容属于哪个规范权威领域，并按文档基础规范 §6.5 检查定义归口；
3. 读取目标规范及其上位依据、相关规范；目标主题尚未创建或尚未生效时，读取成员自描述、Code 派生集合索引、候选来源或用户指定材料，但不得把参考与研究材料当作正式规范；
4. 按需读取 00 中与本次变更相关的产品定位、五类构成要素、价值实现标准、运行闭环标准和 Human Gate 要求；
5. 判断变更是否符合 00 上位原则，是否弱化事实源边界、Human Gate、验证纪律或五类构成要素分工；
6. 若变更涉及 00、02、上位依据、相关规范或术语口径，检查 00/02 层级是否仍符合本文 §2.3；
7. 若变更新增、删除、升级或降级引用关系，按文档基础规范 §6.4 和 §6.6 检查引用方向与引用类型，确认未把导航、追溯、主题相关或被下游引用提升为上位依据或相关规范；
8. 若变更触及被引用文档、成员自描述、Code 派生集合索引、工作对象、Code、Web、Rules、Skill、Agent、Hook 或环境入口，按文档基础规范 §6.7 和事实源边界与承载规范检查是否存在反向补全或反向引用误写；
9. 检查稳定事实是否写入其权威归口，确认参考材料、审计追溯、工具输出、环境观察和过程状态未被当作最终事实源；
10. 若涉及高影响变更，触发 Human Gate；
11. 修改目标规范；
12. 按规范落地声明规范检查目标规范的规范落地要求段落，确认每项落地要求均声明要求内容、保障机制、同步类型和触发条件；
13. 判断文档结构、引用、参考与研究材料边界、定义归口、引用类型、反向补全、事实源归属和规范落地要求检查是否已有适配工具；
14. 若检查 Code 实现缺失或现有实现假设与 specs 冲突，按文档基础规范 §9.1 形成文档检查 Code 缺口，并按 Code 确定性执行实现规范完成 Code 需求准入、最小实现和测试验证；
15. 运行适配后的文档结构校验、引用校验和规范落地要求校验；
16. 检查是否需要更新规范落地要求；
17. 若变更影响适配措施，按 LDVH 能力资产与落地保障规范和环境入口适配与部署规范检查是否存在对应环境适配；不存在时记录为待适配事项；
18. 若变更涉及环境能力判断、工具缺口或 LDVH 落地要求，继续按环境入口适配与部署规范、LDVH 能力资产与落地保障规范检查；
19. 若变更涉及 AI 统一入口、工作区级环境入口、项目级入口、薄引用或环境入口路由，继续按 LDVH 能力资产与落地保障规范检查；
20. 若变更涉及 LDVH 自身项目的当前环境适配措施，应现场确认当前环境能力清单、权限边界、Human 授权、真实入口、验证方式和降级方式；当前具体检查结果只说明当前检查结论，需长期保留的稳定结论应写入 Task、Memo、ADR、Pitfall、正式规范或对应事实源。

## 9. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | specs 编辑入口摘要 | 规范文档入口摘要、正式规范骨架、相关规范引用 | AI 执行入口提示 | 本文的正式规范文档骨架、docs/studies、docs/sources、子文档或规范落地要求变化时 |
| 确定性执行要求 | specs 文档结构和引用校验 | `code/specs_validate.py` 或后续文档校验 Code、正反样例验证 | 校验实现 | 本文的章节编号、章节引用、路径引用、docs/studies、docs/sources、定义归口、引用类型、反向补全、事实源归属或文档治理检查变化时 |
| 生命周期触发要求 | specs 变更后的文档检查触发 | LDVH 能力资产与落地保障规范、环境入口适配与部署规范、环境适配、CI、Skill 流程或人工降级检查 | 触发保障 | 正式规范发生新增、重命名、结构变化、引用变化、定义归口变化、事实源归属变化或规范落地要求变化时 |

上述规范落地要求的具体环境实体由 LDVH 能力资产与落地保障规范和环境入口适配与部署规范处理。环境规则目录、项目配置、`code/` 或其他环境实体不自动成为权威适配。

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 重命名或重排 specs 正式规范文档；
2. 改变 specs 正文区、docs/studies 或 docs/sources 的引用方向规则；
3. 将 docs/studies、docs/sources 或参考与研究材料结论直接作为强制规则使用；
4. 新增、删除或重命名应用剖面或专题子文档；
5. 改变规范落地要求或环境适配规则，或新增、修改、删除会影响适配措施同步检查、LDVH落地、审计或规则漂移诊断的规范落地要求；
6. 新增、替换或扩大 specs 文档检查 Code 实现的判定范围；
7. 改变 00 作为上位概念来源、02 作为术语治理入口、其他正式规范按需引用 00 或 02 的层级关系；
8. 改变定义归口、事实源归属、引用类型分级、反向补全禁止规则或单一事实源边界；
9. 新增、删除、升级或降级会影响多个正式规范、工作对象、Code、Web、Rules、Skill、Agent、Hook、环境入口或适配措施的高影响引用关系；
10. 将参考材料、审计追溯、工具输出、环境观察、过程状态或被下游引用关系升级为正式规范依据、事实源归属或同步义务。

规范文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 正式规范文档已声明上位依据，00 除外 |
| 00/02 层级 | 00 未把 02 作为自身上位依据、相关规范或一致性检查标准；02 以上位依据承接 00；其他正式规范按内容性质引用 00 或 02 |
| 定义归口 | 拟新增或修改的规则、字段、状态、术语、流程、目录事实和规范落地要求已写入最小权威归口 |
| 编号分区 | 文档编号符合 specs 当前编号分区，或已记录为候选事项、计划或待补齐事项 |
| 文档结构 | 文档骨架符合正式规范、工作模型文档、工作流程文档、studies、sources 或应用剖面要求 |
| 子文档边界 | 子文档只定义应用剖面特例或专题细则，未复制父规范通用规则 |
| 引用方向 | specs 正文区未出现指向 docs、外部 URL、外部项目资料或非 LDVH 资产的依据性引用，未把 studies、sources 或参考与研究材料作为规范依据 |
| 引用类型 | 上位依据、相关规范、正文依据引用、消费引用、关联引用、来源引用、导航引用和审计追溯按最低充分级别使用 |
| 反向补全 | `相关规范`、上位依据、关联对象、来源、同步义务或正文规则未仅因被下游引用、消费、登记或提到而反向补写 |
| 事实源归属 | 稳定事实写入对应 Git 文件事实源，未把参考材料、审计追溯、工具输出、环境观察或过程状态当作最终事实源 |
| 规范落地要求 | 仅声明规范要落地需要满足的要求 |
| 保障机制 | 每项规范落地要求均声明保障机制 |
| 环境适配 | 未把具体环境实体混入普通规范落地要求 |
| Code 适配 | 检查 Code 实现适配 specs；缺失时已按文档基础规范 §9.1 和 Code 确定性执行实现规范处理 |
| 校验 | specs 修改后已运行适配后的文档结构和引用校验，或记录降级原因与残留风险 |
