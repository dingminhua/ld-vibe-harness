## 1. 价值判断

本文存在的价值，是把安装、配置、接入方式选择和验证这类高影响行动沉淀成可复用模板，让 AI 在执行前能稳定说明写入位置、影响范围、验证方式和回滚路径，减少遗漏告知、误装入口、误判 integrated 或绕过 Human Gate 的风险。

该模板主要服务 V1、V2、V3、V4、V5、V6、V7 和 V8：它让 AI 快速定位安装、配置与验证入口，理解写入对象和环境边界，正确判断受管项目、环境入口和 integrated 状态，按固定 Gate 稳定执行，在高影响写入、配置位置确认或风险接受前等待 Human 确认，执行指定验证，按格式回写配置和残留风险，并用范式交互向 Human 呈现待确认事项。安装、配置或接入方式变化会改变环境入口、配置位置或受管项目边界；如果没有模板，AI 容易把“方案存在”“样例包存在”“旧插件存在”误写成“已部署”或“已接管”，也容易把系统检查结果当成用户决策、把后置缺口放进主选项，或在最终确认前边问边写。

## 2. 权威依据

本文承接 `specs/06-行动模板基础规范.md` 的 Context、Scenario、Gate、执行、验证、回写和交还结构。行动模板不是规则源，也不是授权器；本文的职责是把来源规则、Code 输出、Human Gate、验证证据和交还内容组织为可复用行动路径。

本文承接 `specs/01-保障与衔接.md` 的环境入口、Hook 分类、插件 / 扩展包安装口径和 integrated 声明边界；承接 `specs/10-安装与配置规范.md` 的配置事实源和 target-first 解析边界；承接 `specs/07-Code确定性执行规范.md` 和 `specs/09-测试与验证规范.md` 的实现域与验证边界。

安装向导 CLI 或等价 Code facade 已出现时，本文仍保持正式行动模板角色：10 归口安装与配置的机器契约，Code facade 归口确定性 `check -> plan -> apply -> verify` 执行壳，本文归口 Human-facing 五阶段编排、告知清单、最终确认、断点恢复、失败信息包、验证交还和缺口分流。CLI 不替代本文；本文也不得复制 CLI、10、01 或 07 的机器规则形成第二规则源。

本文受 V3 01 的环境入口边界约束，也受 V3 01、06、10 的共同约束：01 管环境入口、06 管行动模板结构、10 管管辖项目配置契约。本文不声明 integrated；只有真实自动触发、失败可阻断、安装与接入依据可复核、回滚方式明确且验证依据齐备时，才可由对应环境入口规则判断是否 integrated。

若本文与 01、06、10 或 Human Gate 冲突，应回到上位规范和 Human Gate，不得由本模板自行覆盖。

## 3. 归口边界

本文归口定义安装、配置与验证行动的步骤组织、用户告知清单、Gate、验证、断点恢复和交还。断点后验证的统一标准，是 runtime 循环在真实工作流里产出可复核 receipt；目标环境缺少可安装、可验证、可阻断 lifecycle Hook 时，正式安装与 LDVH 影响验证必须阻断。

本文不归口定义环境入口判定分类、Hook 安装实现、插件 manifest schema、管辖项目配置字段、Code 命令细节、Web 页面、测试框架或真实用户环境配置。环境入口边界归 01，状态归口原则归 04，Code 实现实践归 07 和 `code/docs/`，管辖项目配置契约归 10，验证声明归 09。

本文可以组织“先告知、再确认、再执行、再验证、再断点恢复、再交还”的行动顺序，也可以把安装向导 Code facade 的输出翻译为 Human 可理解的安装阶段、净变化、风险和下一步；但不得把行动步骤写成环境入口安装授权、配置事实源契约、Code 实现细节、机器规则源或 integrated 状态证明。

本文不得登记 Git 提交、WorkCase 推进或其它后续行动模板候选的迁入判断；跨模板候选筛选统一回到 `specs/06-行动模板基础规范.md`。

**概念区分：环境 Hook 与 Git Hook 是两类独立机制。** 环境 Hook（plugin lifecycle event、PreToolUse、SessionStart 等）由 IDE / AI Agent / Runner 平台触发，依赖当前运行环境的能力；Git Hook（commit-msg、pre-commit 等）由 Git 自身在执行 `git commit` 等命令时触发，不依赖 AI 运行环境。两者独立安装、独立验证、独立生效，不能因为目标环境不支持 Hook 就推断 Git Hook 不需要安装，也不能因为 Git Hook 已安装就推断环境 Hook 已 integrated。安装前检查、安装方案预览和验证交还中，必须分别检查并分别呈现两者的状态。

## 4. 适用范围

本文适用于：

1. 用户要求安装 LDVH、接入 LDVH 或初始化 LDVH；
2. 用户要求配置、生成或迁移 `LDVH-GOVERNED-PROJECTS.yaml`；
3. 用户要求把项目登记为管辖项目，或检查某项目是否已被 LDVH 管辖；
4. 用户要求检查安装是否生效、修复旧插件、旧路径或 stale V2 path；
5. 后续真实安装、升级、禁用、卸载环境插件或 Git hook shim 前的 Human Gate 准备。

用户只是询问概念、职责或边界时，只回答 01、06、10 和本文边界，不写入配置、不安装插件、不修改 Hook。

## 5. 模板定位与来源

本文是 06 之后的第一个独立正式行动模板，编号为 `30`。它不是 06 父规范的正文示范，也不是 Code 实现域文档；它是可被 AI 直接引用的行动模板成员。

因此，30 的成败不取决于是否亲自执行底层安装逻辑，而取决于是否能按 06 的行动模板结构稳定组织安装行动：进入场景识别、Context 收集、Gate 与 Human Gate、五阶段交互、验证入口、回写边界、交还和断点恢复。底层确定性执行由安装向导 Code facade 承接；30 必须消费其输出并交还主控 AI 与 Human 判断。

本文承接安装、初始化、首次管辖项目配置和验收交还能力。历史行动模板、环境适配材料或外部包装只能作为来源线索，不能让本文复制其全文、恢复 Rules / Skill 顶层机制或越过 Human Gate。

当前最小闭环包括：安装入口发现、目标工作区确认、管辖项目登记、用户告知清单、安装方案预览、最终确认、写入后验证、断点引导、失败信息包和交还。真实环境插件写入、管辖项目 Git Hook 写入、完整部署自动化、用户级配置解析、项目内配置迁移和批量项目接入仍需按来源规则进入 Human Gate 与最终确认。

## 6. 用户告知清单

安装、部署、初始化、配置或卸载前，本模板必须先形成用户告知清单，并把清单交给 Human 确认。

告知清单至少包括：

1. 要安装、生成、修改、覆盖、禁用、卸载或删除的对象；
2. 写入位置及其级别：用户级、工作区级、项目级、Git 本地目录、插件 cache、仓库内样例或只读检查；
3. 受影响项目、不受影响项目、跨项目范围和混合非管辖 target 风险；
4. 会接入哪些 Git hook shim、环境 Hook、plugin lifecycle event、插件、扩展包、package 或 runtime adapter；
5. 是否需要创建或检查管辖项目根下的 `ldvh-base/` 事实源目录，以及每个子目录的用途；
6. 哪些事件可能阻断，哪些只是 diagnostic，哪些仍是 `available`、`deferred` 或 `absent`；
7. 旧插件、旧路径、旧配置、stale V2 path、历史 trust 或旧 Hook 的处理方式；
8. 验证入口、预期结论、不可验证范围和失败处理；
9. 回滚或卸载入口，以及卸载后如何确认环境不再自动触发 LDVH；
10. 环境入口是否会使用 session-scoped runtime receipt cache；若会使用，必须说明 OS runtime / temporary / cache 目录、TTL、权限、可关闭方式、清理方式和非事实源边界；
11. 写入完成后需要在重启 App、新窗口或新会话中继续确认的 lifecycle 验证内容；
12. 残留风险、source_refs 和下一步 Human Gate。

管辖项目事实源目录告知只说明是否需要按 10 §8 检查或创建 `ldvh-base/` 及其事实源子目录、创建是否进入 Human Gate、目录存在不代表事实实例或环境入口 integrated。目录用途、不得替代边界和研究材料边界回指 `specs/10-安装与配置规范.md` §8 及 20-24 成员规范，本文不复制目录用途表。

不适用于当前场景的告知项（如无旧插件时第 7 项"旧插件处理方式"、无 cache 时第 10 项"runtime receipt cache"）可以标记为"不适用"后省略详情，无需逐项填充零信息。但不得跳过对当前场景有意义的告知项；判断"是否适用"的依据是 2/5 安装前检查的检查事实，不得凭空判定。

缺少用户告知清单时，不得安装、部署、初始化、写入配置、声明接入或要求 Human 验收。告知清单不是授权本身；授权只能来自 Human Gate。

## 7. 安装行动阶段与 Human Gate

### 7.1 行动阶段与交互边界

安装、接入、初始化或配置管辖项目时，AI 必须使用安装行动阶段组织 Human-facing 交互。安装行动不是测试模式；它是正常安装流程。是否执行只由最终确认决定。

安装行动固定为五个阶段：

| 阶段 | 名称 | 说明 | 写入边界 |
|---|---|---|---|
| 1/5 | 路径确认 | 展示完整流程，确认 LDVH 本体路径和目标工作区路径；从当前 AI 运行上下文识别目标环境并锁定，后续不再询问 | 不写入 |
| 2/5 | 安装前检查 | 只读检查当前项目、目标工作区配置、事实源目录、环境入口、旧插件和旧路径证据 | 不写入 |
| 3/5 | 安装选项 | 只收集真正需要 Human 决定的安装选项；配置位置不作为选项；目标环境已锁定时不再次询问 | 不写入 |
| 4/5 | 安装方案预览 | 汇总用户告知清单、检查结果、Human 选择、将执行动作、后置项、验证方式和回滚方式 | 不写入 |
| 5/5 | 最终确认 | Human 选择执行或不执行；只有选择执行后才可写入；写入完成后交还断点恢复入口和 lifecycle 验证清单 | 确认执行后才可写入 |

当 2/5 安装前检查确认管辖项目配置已存在且可解析、所有管辖项目 Git commit-msg Hook 均已安装且可执行、事实源目录均已存在、且环境入口承接内容已就绪时，安装行动无需新写入。此时 AI 应在 2/5 检查结果中明确声明"无需新写入"，跳过 3/5 安装选项和 4/5 安装方案预览中与写入相关的部分，直接进入验证与交还。5/5 最终确认的选项含义变为：`1 执行方案` = 确认当前状态并进入验证交还，`2 不执行，停止安装` = 停止流程。跳过阶段时不得跳过用户告知清单中与当前状态相关的告知项（如管辖项目范围、接入方式、验证入口、回滚入口和残留风险）。

每次向 Human 展示安装行动时，交互输出应表达当前阶段、已确认决策 / 结果和未发生事项。本文不得新增安装运行时状态闭集，不得把交互展示项写成环境入口判定事实、事实对象状态或安装事实记录。具体图标、表格列、控件、展示样式和交还摘要模板归实现域文档或运行时输出。

安装行动应按场景复杂度精简呈现，不得对所有操作堆砌完整表格集。回答组织分为两层：用户主界面只展示 Human 需要知道的结果、风险、下一步操作和需要 Human 决定的选项；具体命令、字段名、source_refs、raw diagnostic、环境审计字段和 Hook status 字段归技术明细附录或命令输出，默认不在用户主界面逐字展示。需要 Human 作出选择时，每次只问一个问题，不把检查事实、后置项或返回修改混入主选项；最终确认只允许“执行方案”和“不执行，停止安装”两个主选项。

安装行动必须区分方案确认和执行确认。4/5 安装方案预览只能询问“是否进入最终确认”，该选择不是执行授权，不得用“执行方案”或其它会让 Human 误以为已经授权写入的措辞。5/5 最终确认必须直接询问“执行方案”或“不执行，停止安装”，不得再次要求 Human 确认只读检查、重复展示安装前检查事实，或把断点后验证包装成新的安装授权选项。Human 在 5/5 选择 `1 执行方案` 后，AI 必须立即执行已确认写入并进入执行后验证；写入完成后必须交还恢复入口语、lifecycle 验证清单和失败信息包，不得继续解释流程或再次索要同一授权。

安装前检查必须区分检查结论和是否阻断；注意、需安装、需升级或阻断类结论的来源和具体展示形态回指 01、10、09、Code facade 和实现域文档。图标、表格列和示例形态不得替代结论文字、Human Gate 或验证结论。

### 7.2 用户告知、用户选择与检查事实

用户告知清单必须作为 4/5 安装方案预览的必含内容交给 Human 确认；若 2/5 安装前检查发现 blocking，AI 也必须在暂停交还时同步列出已能确认的告知清单项、缺失项和解除条件。告知清单不得替代 5/5 最终确认。

安装前检查只能输出系统已检查事实，不得把事实伪装成 Human 选项。目录、配置、环境入口、旧插件旧路径、外部 Hook、Git worktree 和 Git Hook 检查结果应按 01、10、09 和 Code facade 输出归类为检查事实、需授权动作、后置项或阻断项；需要安装、升级或阻断时进入方案预览或暂停交还，不在本文重写具体判定规则。

### 7.3 路径发现、配置位置与管辖项目清单

目标工作区配置已存在且方案倾向保留时，安装前检查必须展示当前配置摘要和项目候选，供 Human 决定是否保留或按编号调整。配置字段、配置正确性、路径解析、target-first 结论和层级冲突判定回指 10、10 附件和 Code facade；本文只规定需要让 Human 能比较当前配置与拟写入配置，不维护配置校验规则摘要。

安装入口发现必须先从 LDVH 本体读取本文。目标工作区没有 LDVH 文件时，AI 可以执行有限、只读、有证据的 bootstrap discovery：依次检查当前对话或进程已知 LDVH root、`LDVH_ROOT` / `LDVH_HOME` 环境变量、已安装插件 / Hook / wrapper 中记录的 LDVH root、当前 cwd 向上的 LDVH 本体证据、常见工作区父目录的有限深度搜索；找到候选后必须展示候选路径和证据，多个候选必须让 Human 选择，找不到时必须要求 Human 提供 LDVH 本体路径，不得要求目标工作区已经存在 `specs/30`。

安装选项只包含当前可执行且需要 Human 取舍的决策。管辖项目配置位置、目标工作区默认值、项目内 / 用户级 / LDVH 本体目录边界和配置层级冲突回指 10；本文只规定路径确认必须让 Human 看清 LDVH 本体路径、目标工作区根目录和配置文件完整路径的含义、建议、证据和可复制路径，具体表格列和展示形态归实现域。未显式指定目标工作区根目录时，默认值是 LDVH 本体路径的父目录；AI 应直接展示该默认绝对路径和“由 LDVH 本体父目录推导”的证据，不得把目标工作区根目录写成“待确认”。只有出现多个合理工作区候选、用户显式要求改用其它工作区，或默认父目录与配置层级检查冲突且需要 Human 取舍时，才进入目标工作区选择。

### 7.4 安装方案预览与最终确认

安装方案预览必须合并所有 Human Gate。主界面只展示普通用户作出下一步判断所需的信息：会改变什么、不会改变什么、执行后还需要验证什么、是否存在阻断；技术明细可以附后或折叠展示，但不得丢失。写入对象、写入位置、将执行动作、不会执行的事项、后置项、验证入口、失败处理和回滚方式都必须在此步可见或可展开，具体检查项和命令由 01、10、09、Code facade 和实现域文档承接。

完整安装方案必须覆盖目标环境 AI lifecycle Hook 承接和每个已选择管辖项目的 Git Hook 承接。非 Git worktree、配置层级冲突、目标不明确、非管辖或混合 target、目标 AI 环境无可安装可验证可阻断 lifecycle Hook、Human 未确认等阻断按来源规则暂停，不得继续进入最终执行或声明完成。真实 lifecycle、外部环境触发或卸载后自动触发状态无法在当前回合验证时，必须写入不可验证范围，不得混入“验证通过”；只读安装检测是否足以支持写入完成结论回指 01、09 和 Code facade。最终确认前，AI 只能只读检查、展示结果和收集选择，不得写入配置、创建目录、安装插件、修改 Hook、修改用户环境或声明 integrated。

### 7.5 环境入口承接与统一验证边界

目标环境入口承接只能通过可安装、可验证、可阻断的 AI lifecycle Hook 完成。用户界面的“运行时入口”应解释为目标环境插件、扩展包、package 或 runtime adapter 调用 LDVH `runtime_adapter.py` 的入口链，而不是用户手动命令、提示文本或规则文件。

30 只支持目标 AI 环境通过可安装、可验证、可阻断的 lifecycle Hook 接入 LDVH。支持 Hook 的目标环境可以安排目标环境插件 / 工具入口插件、扩展包或 package；暂不支持 Hook 的目标环境不得安排替代安装路径，只能停止正式安装并交还“目标环境暂不属于 LDVH 支持范围”或“需先实现目标环境插件 / 扩展包 / package”的诊断。

AI 必须读取 01、`01.Att.03`、`01.Att.04` 和环境审计结果，并把 raw diagnostic 翻译为可行动语言。环境审计字段、配置检查字段、Hook status 字段和 source_refs 只允许放在技术明细、命令输出或诊断附录中；主界面应表达为用户可理解的触发方式、待验证范围、阻断原因和下一步。

当 30 发现目标环境尚未提供 LDVH 插件、扩展包、package 或 runtime adapter，或 Code facade 输出 `unsupported` / `external_adapter_candidate` 时，用户主界面必须出现“目标环境插件缺口提示”。该提示至少包含：目标环境名称、当前不能继续正式安装的原因、不会执行任何替代环境写入、下一步是按 spec 33 编写目标环境 LDVH 插件 / adapter、实现后重新运行本文安装前检查。不得只输出 raw diagnostic，也不得让用户误以为只需重启、粘贴提示词或手动运行 runtime 命令即可完成环境接入。

AI 消费 Code facade 的 `environment_strategy` 输出时，必须交叉验证该策略与当前运行环境是否一致。当环境审计或当前运行上下文检测到 TRAE、Cline、Cursor 等目标环境没有可安装、可验证、可阻断的 LDVH lifecycle Hook 时，AI 不得盲目接受 `plugin_hook` 策略；应将策略修正为 `unsupported` 或 `external_adapter_candidate`，并在技术明细中标注 Code facade 输出与修正原因。Code facade 自身也应从当前运行环境自动检测 environment_name，而非默认假定 Codex；当 Code facade 的自动检测和人工指定策略存在且冲突时，以人工指定为准。

目标环境确认暂不支持 AI lifecycle Hook 时，30 必须停止正式安装，交还不支持原因、影响范围和后续可行路径。后续可按 spec 33 为目标环境编写 LDVH 插件、扩展包、package 或 runtime adapter，在具备真实触发、payload、失败处理、安装接入依据和回滚方式后重新进入本文安装流程。

统一验证标准不是“插件页面可见”或“Hook 配置文件存在”，而是 runtime 循环在真实 AI lifecycle 里产出可复核的当次可观察依据。验证必须回指 Runtime Protocol、01 和 09 的依据要求，并能结合 Git `commit-msg` 正反例、写入前检查或完成声明检查说明 LDVH 已在当前工作流中被消费。文件存在、插件缓存、历史 trust 或聊天印象都不得单独写成 integrated 或完整生效证明。

环境 Hook 当次 integrated 验收必须按 01 的最小当次验收依据逐项交还，不得只给“插件已安装”或“命令可运行”。30 组织验收时至少覆盖：目标环境和 LDVH root、插件 / 扩展包 / package 或 adapter 的安装启用依据、`ldvh.session_start` 真实触发依据、`ldvh.pre_tool_use` 负例阻断依据、`ldvh.pre_tool_use` 正例或只读放行依据、`ldvh.completion_claim` 或 Stop 类完成检查依据、payload / target 依据、回滚后不再触发依据、不可验证范围。任一项缺失时，主结论只能写“本次未验证”或“本次验证失败”，不得写 integrated。

环境 Hook 或插件提示必须按当前目标环境命名。AI 能从当前运行上下文识别当前 AI 运行环境名称时，必须优先使用该环境名称，不得沿用示例环境名称；只有当前运行环境、环境审计或 Human 明确目标环境为 Codex 时，才可在用户主界面写 `Codex/工具入口插件`。目标环境不是当前运行环境，或换成 Trae、IDE、Agent runner、CI、未知环境时，必须改写为对应的目标环境名称，或使用环境无关的 `目标环境插件 / 工具入口插件`。

AI 提示用户安装、升级、授权或验收环境插件时，必须说明目标环境、用户需要执行的动作、断点后验证入口、失败后应返回给 AI 的信息，以及后续诊断来源。具体插件页面、命令、输出字段和提示模板归 01、Code 实现域文档或运行时输出承接。未真实写入插件包、未进入插件页面或未获得授权依据前，不得写成“插件已安装”，只能写当前依据和待验证范围。

### 7.6 写入完成后的断点引导与 lifecycle 验证（LDVH 影响验证）

安装验证是 30 的固有组成，不是可选升级，也不交给独立验收模板。30 的验证分为两类：当前回合可完成的安装检测，以及写入完成后因重启 App、新窗口或新会话产生的断点后 LDVH 影响验证。断点是物理事实，不是流程缺陷；AI 必须把断点设计成可识别、可恢复、可复跑。

当前回合可完成的安装检测是机械验证：只确认文件是否写入正确、路径是否存在、配置是否可解析、Git Hook managed marker 是否存在、环境入口指向是否正确。具体检查项、命令和输出字段由来源规则、Runtime Protocol 和实现域文档承接。安装检测通过后仍不得把文件存在、插件可见或直测通过写成 integrated。

LDVH 影响验证是行为验证：回答"LDVH 会在什么时候影响当前工作流、会得到什么结果、不会产生什么副作用"。它必须通过重启 App、新窗口或新会话触发真实 AI lifecycle runtime 循环来验证，不得用当前回合的机械检测替代。它应按 `plugin_hook` 或具备真实 lifecycle Hook 的正式 adapter 组织，而不是只问 Hook 文件是否存在。缺少可阻断 AI lifecycle Hook 时，本次正式 LDVH 影响验证不能通过。

断点后 lifecycle 验收必须先明确 AI 与 Human 的职责分工。AI 负责安装检测、repo-local shim / `runtime_adapter.py` 直测、最小验收卡生成、失败信息包整理和最终判读；Human 只负责目标环境里 AI 无法替代的动作，包括打开插件页或扩展页、确认启用 / 授权 / 无错误、重启或新开目标环境会话、执行 AI 给出的自然语言任务、复制目标环境实际输出或说明未看到输出。Human 不负责理解 integrated 分类，不负责判断通过 / 失败，也不负责手动运行 `runtime_adapter.py`、repo-local shim 或其它命令来证明 integrated。

手动 `runtime_adapter.py`、repo-local shim 直测、payload fixture 或 dry-run 只能作为安装检测、技术对照或失败定位依据；不得作为环境 Hook integrated 的替代验收。真实 integrated 验收必须由目标环境自动 lifecycle 触发产生当次可观察依据。AI 设计验收时，必须把“命令直测已通过”和“目标环境真实自动触发已通过”分开交还；前者最多支持 `install_verified` 或 `available`，不能单独支持 `integrated`。

AI 交给 Human 的断点后验收卡必须最小化，不得要求 Human 执行或理解技术判定。验收卡至少包含：目标环境名称、插件页面要看的状态、需要重启或新开会话的动作、自然语言触发任务、每项正常可观察表现、失败时应贴回的原始输出。自然语言触发任务必须覆盖新会话 / 恢复时的 `ldvh.session_start` 可见性、写入前负例、写入前正例或只读放行、完成或 Stop 检查；不得用“请运行 runtime adapter 命令”替代真实 lifecycle。Human 回传后，AI 必须逐项判读 `integrated`、`available`、`failed` 或 `unverifiable`，并说明缺失项和下一步。

断点后 lifecycle 验证必须把 `ldvh.session_start`、`ldvh.pre_tool_use` 和 `ldvh.completion_claim` / Stop 分开验收：`ldvh.session_start` 证明入口自动给出读取计划；`ldvh.pre_tool_use` 证明写入前能阻断负例且不误伤正例；`ldvh.completion_claim` / Stop 证明完成声明检查可见且不误阻断环境关闭。当前环境无法触发目标环境真实 lifecycle 时，30 只能记录不可在当前环境验收，并要求目标环境回传当次可观察依据或先补目标环境插件 / adapter。

LDVH 影响验证默认只读，不得写 `spark-0046`、`ldvh-base/`、specs 或其它正式事实源。真实工作流需要覆盖写入前检查时，优先使用 payload fixture、dry-run 或只读探针；确需 harmless scratch target 时，必须显式说明 scratch 路径、写入目的、清理方式和删除确认，且删除失败时本次影响验证不得通过。

环境 Hook 使用 session-scoped runtime receipt cache 时，该 cache 只能作为同一会话内 `acknowledge_read_plan` 到 `pre_tool_use` 的短期过程回执桥接，不属于正式事实源写入。验证必须说明本次是否写入 cache、cache 所在 OS 目录、TTL、是否命中、是否过期或清理，以及 cache 缺失时会回到显式 `acknowledged_paths`、transcript 推断或阻断诊断；不得把 cache 命中写成任务完成、Human 授权或 integrated。

写入完成交还时，AI 必须输出断点恢复协议：

1. 恢复入口语：用户在任何新窗口或新会话粘贴后，AI 必须识别为继续 30 验证；
2. 可复制的只读可见性探针与最小 Human 验收卡：可复制探针用于安装检测和失败定位；验收卡用自然语言说明目标环境内要执行和观察的动作，不要求 Human 手动运行 adapter 命令，不要求 Human 判断通过 / 失败；
3. 授权 / trust 检查：目标环境需要插件、扩展包或 package 时，必须先提示用户确认插件已授权、已信任或无待处理授权，再进入重启、新窗口、新会话或真实触发检查；
4. runtime cache 检查：目标环境使用短期 receipt cache 时，必须提示 cache 目录、TTL、是否需要授权、是否已写入或命中、如何关闭和如何清理；cache 不能作为事实源或完成证据；
5. Hook 触发依据检查：支持 Hook 的目标环境必须提示用户查看插件 Hook / lifecycle 触发记录、Hook 输出、插件事件日志或等价当次可观察依据；若目标环境没有可见记录，必须把“未取得 Hook 触发依据”列入未完成触发项，不得用手动探针替代真实 Hook 触发依据；若出现 PreToolUse 阻断，尤其是 `RUNTIME_READ_PLAN_CONSUMED_EMPTY`、`PREFLIGHT_TARGET_UNKNOWN` 或等价前置检查错误，必须分类为“Hook 已触发，但 read_plan 消费依据链路未通过”，不得继续写成 lifecycle 未触发；
6. LDVH 影响验证清单：至少覆盖一次真实管辖项目 Git `commit-msg` 正反例、一次 `ldvh.session_start` 真实触发、一次 `ldvh.pre_tool_use` 负例阻断、一次 `ldvh.pre_tool_use` 正例或只读放行、一次 `ldvh.completion_claim` / Stop 完成检查，并说明接入方式、触发时机、预期结果和是否写入；需要 scratch target 时必须显式说明路径、清理和删除确认；
7. 失败反馈包：目标环境名称和版本、入口结果、统一安装验证输出、环境审计输出、失败步骤编号、是否发生实际写入、scratch target 路径和文件状态、runtime cache 状态、相关错误文本；
8. 当前不可验证范围和复跑方式：用户回来后 AI 先复跑只读统一安装验证入口重建上下文，不依赖聊天记忆、不写长期过程状态文件；短期 runtime cache 过期时必须重新 acknowledge，不得要求用户保留 cache。

断点后用户回来时，AI 不得重新启动安装向导或要求用户重新确认已完成写入；必须先复跑只读统一安装验证入口重建当前依据，再按恢复入口语和验证清单逐项引导。需要 Human 观察的内容必须写成“你是否看到了上述正常表现”或“请贴出完整输出”，由 AI 根据本文判断通过、失败或暂停诊断；不得要求 Human 自行理解专业“通过 / 失败”。

LDVH 影响验证的主结论只能表达“本次验证通过”“本次验证失败”或“本次未验证”。该结论是当前验证输出，不写成长效事实状态；但只要后续复跑只读验证显示 LDVH root、管辖项目配置、Git Hook managed marker、环境入口指向和 runtime adapter 输出未变化，AI 可以消费当前证据继续行动。环境变化、插件升级、Hook 改动、配置变化、stale path 或验证冲突出现时，必须重新验证或写为未验证。

### 7.7 写入完成交还、断点恢复与失败信息包

执行完成后必须先交还“写入完成”结论，再交还断点恢复协议和技术明细。支持 Hook 的正式插件、扩展包、package 或外部 adapter 候选都不得产生不同的完成分支；差异只体现在触发来源、写入对象和不可验证范围。用户主结论必须明确写入是否完成、下一步恢复入口语和真实工作流验证要求，不得把“断点后验证待完成”写成停止后续验证的理由。

交还摘要至少覆盖：实际写入对象、明确未写入对象、01.Att.04 环境接入判定分类及证据、环境入口触发来源、每个管辖项目 Git `commit-msg` Hook 验证摘要、断点恢复入口语、LDVH 影响验证清单、下一步 Human Gate、不可验证范围、回滚或卸载入口和 source_refs。交还摘要不得形成新的安装状态闭集，也不得把 01.Att.04 分类写成长效事实状态。

交还必须拆成两个块：`Runtime 入口与 lifecycle 验证`（对用户解释为 `Runtime 入口与 LDVH 影响验证`）和 `提交消息检查`。前者说明环境插件、runtime adapter、写入前检查、完成声明检查和副作用边界；后者说明每个管辖项目 Git Hook、正例放行和反例阻断。不得用一个“Hook 已通过”覆盖两类入口。

用户下一步待办按以下顺序组织，不另开独立验收模板：

1. 打开插件页面 / 扩展页面 / 插件管理器并确认已授权 / trust 或无待处理授权（目标环境需要时）；
2. 重启 App 或新开目标环境会话，查看插件 Hook / lifecycle 触发记录；若没有可见记录则返回"未取得 Hook 触发依据"；
3. 新开或恢复目标环境会话，按 AI 给出的自然语言验收卡观察是否自动出现 LDVH read plan、`ldvh.session_start`、receipt 或等价输出；若未出现则返回“未看到 LDVH 输出”；
4. 按引导触发真实工作流验证：逐项覆盖 Git `commit-msg` 正反例、`ldvh.session_start` 真实触发、`ldvh.pre_tool_use` 负例阻断、`ldvh.pre_tool_use` 正例或只读放行、`ldvh.completion_claim` / Stop 完成检查；需要 harmless scratch target 时明确路径、清理方式和删除确认；
5. 若任一验证失败，复制失败信息包。

授权 / trust 确认必须排在重启或新开会话之前；支持 Hook 的目标环境必须把 Hook 触发依据检查排在手动 runtime 探针之前。手动 runtime 探针只能由 AI 作为技术对照或失败定位使用，不能写成 Human 验收动作，也不能作为 integrated 依据。

失败或暂停时必须提供可复制失败信息包，不得只要求“截图给我”。失败信息包至少列出：目标环境名称和版本、入口结果、统一安装验证输出、环境审计输出、失败步骤编号、是否发生实际写入、scratch target 路径和文件状态、相关错误文本。若某项拿不到，写“未取得”并说明原因。

最终确认只展示两个主选项：`1 执行方案` 和 `2 不执行，停止安装`。最终确认前必须明确提示选择执行后才会开始写入；最终确认摘要只列出将写入对象和不写入对象，不得重复安装前检查表或把已完成的只读检查再次作为待确认事项。Human 选择不执行时，AI 必须停止在方案预览或最终确认状态，不得写入；Human 要求调整方案时，AI 必须回到对应前一步，但不得把返回修改作为第三个主选项；只有 Human 选择执行后，AI 才能按方案执行已确认的仓库内动作，并在写入后执行验证、回滚说明和残留风险交还。

安装执行完成后必须输出写入完成交还总结，不得只给零散验证结果。交还总结必须单列实际写入、未写入对象、当前回合安装检测摘要、断点后 lifecycle 验证入口、不可验证范围和撤销 / 恢复入口。缺少断点恢复入口语、可复制探针或失败信息包时，不得声明安装交还完整。

## 10. 验证方法

验证本文规则时应检查：

| 检查类别 | 检查内容 | 不满足时 |
|---|---|---|
| 行动阶段检查 | 是否使用五阶段安装行动、表达当前阶段与已确认决策 / 结果、覆盖安装方案预览和最终确认；是否把检查事实、用户决策和后置项分开；是否避免把交互展示项写成新的状态闭集 | 不得执行写入或要求 Human 验收 |
| 清单检查 | 是否在安装、部署、初始化、配置或卸载前列出用户告知清单 | 不得执行写入或要求 Human 验收 |
| Gate 检查 | 是否识别配置位置、环境入口、插件安装、integrated 声明和多项目 target 的 Human Gate | 暂停并交还 Human |
| 环境检查 | 是否按 01、09、Runtime Protocol 和 Code facade 区分安装检测、接入判定、用户侧冒烟检查和不可验证范围；是否避免把用户侧观察、文件存在或插件可见写成 integrated | 不得声明环境 integrated；安装检测未通过时不得声明写入完成 |
| Git Hook 检查 | 是否把每个已选择管辖项目 Git Hook 纳入安装 / 升级方案，并通过统一安装验证入口或等价入口验证当前管辖项目 Hook 结果 | 不得声明完整写入完成 |
| Git 项目检查 | 是否检查每个已选择管辖项目是有效 Git worktree；非 Git 目录是否阻断并说明管辖项目必须是 Git 仓库 | 不得继续执行安装 |
| 配置检查 | 是否按 10 解析和验证管辖项目配置，并确认配置固定在目标工作区根目录，且展示 LDVH 本体路径、目标工作区根目录和配置文件完整路径 | 不得声明管辖项目配置已生效 |
| 配置层级检查 | 是否检查目标工作区根目录到目标项目路径链上已有项目内配置 | 不得继续执行工作区安装 |
| 事实源目录检查 | 是否回读管辖项目 `ldvh-base/` 及五个子目录状态，并说明每个目录用途 | 不得声明管辖项目事实源初始化完成 |
| 回滚检查 | 是否说明回滚或卸载入口，并验证卸载后不再自动触发 LDVH | 不得声明部署闭环完整 |
| 交还总结检查 | 是否在写入完成后单列实际写入、未写入对象、统一安装验证入口或等价验证结果、Hook 接入后测试、不可验证范围和撤销 / 恢复入口 | 不得声明写入完成 |

## 11. Human Gate

以下情况必须进入 Human Gate：

1. 安装、升级、禁用、卸载或迁移 LDVH 插件 / 扩展包 / package；
2. 写入、覆盖、删除或迁移环境入口、Hook、plugin lifecycle event、扩展包、package 或 runtime adapter；
3. 创建、修改、迁移目标工作区根目录下的 `LDVH-GOVERNED-PROJECTS.yaml`，或确认 LDVH 本体路径 / 目标工作区根目录；
4. 创建、删除、迁移或重命名管辖项目 `ldvh-base/` 及事实源子目录；
5. 删除、迁移、合并、覆盖或保留同一路径链上的多个 `LDVH-GOVERNED-PROJECTS.yaml`；
6. 接受用户级配置目录后置缺口或其它当前 Code 不支持的配置候选；
7. 声称环境入口 integrated、接受阻断行为、接受残留风险、确认安装方案预览、选择执行或不执行、要求调整方案或要求 Human 验收；
8. 多项目、跨项目或混合非管辖 target 的安装、配置或验证范围不清。

## 12. Stop Conditions

出现以下情况时，AI 必须暂停：

1. 目标环境、写入对象、写入位置级别或影响范围不清；
2. 缺少安装行动阶段展示、用户告知清单、安装方案预览或最终确认，或这些内容未交给 Human 确认；
3. 插件、Hook、旧路径或历史 trust 被写成 integrated 证明；
4. LDVH 本体路径、目标工作区根目录或目标工作区配置文件完整路径不清；
5. 目标项目内已有 `LDVH-GOVERNED-PROJECTS.yaml` 尚未删除、迁移或明确保留；
6. 管辖项目 `ldvh-base/` 目录用途、写入影响或 Human Gate 状态未说明，或系统已检查事实被重新包装成 Human 选项；
7. Code、环境审计或工具输出正在替代 Human Gate、事实源或完成判断；
8. 验证、回滚或卸载路径不可复现，却要求声明安装部署完成。

## 13. 待补齐事项

1. 本模板用于真实安装、升级、禁用、卸载或迁移 LDVH 插件 / 扩展包 / package 前，必须重新生成用户告知清单并进入 Human Gate；
2. 用户级配置目录和项目内配置不是本模板支持的主位置；如已存在，只能作为 legacy / conflict 或后置缺口处理；
3. 本模板当前只承接最小安装、初始化、管辖项目配置和事实源目录初始化闭环；若要扩展到批量管辖项目配置、跨项目安装或完整卸载记录，必须先修订本文并重新进入 Human Gate；
4. 本模板声明安装、升级或卸载完成前，需要 Code 实现域提供可复现的验证和回滚证据；
