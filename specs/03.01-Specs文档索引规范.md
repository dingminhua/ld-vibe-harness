## 1. 本文定位

本文定义 LD Vibe Harness `specs/` 文档索引的定位、输入范围、索引类型、生成原则、输出原则、消费规则、失效回退、Tools 辅助程序边界和文档治理检查要求。

本文服务于 AI 对 specs 文档的精准读取、人对文档体系的审查、Tools 对 Markdown 文档的确定性解析和文档一致性诊断。

本文只治理 specs 文档索引。项目生产内容、`ldvh-base/` 事实实例、业务对象、业务数据、业务 Web / MCP 查询索引和管辖项目自有索引由对应项目、事实模型、行动模型或业务 Tools 承接。

## 2. 父规范关系

`specs/03-Specs文档规范.md` 定义 specs 文档类型、文档骨架、引用纪律、机制关系声明和文档治理检查。本文是 03 的父规范扩展，只定义 specs 文档如何被机器索引、定位、校验和消费。

03 中关于正式规范文档、子文档、模型实践子文档、索引文档、evals 文档和 refs 文档的类型定义、骨架要求、引用纪律和机制关系声明仍为权威依据。本文不得重新定义这些文档类型，也不得改变 03 对文档骨架和引用纪律的规定。

当本文与 03 发生冲突时，以 03 为准，并应修正本文或对应 Tools 实现。

## 3. specs 文档索引的定位

specs 文档索引是从 specs Markdown 原文中确定性提取的派生导航信息，用于帮助 AI、人和 Tools 定位文档、章节、头部元信息、引用关系、机制关系声明和文档治理缺口。

specs 文档索引应服务于以下目标：

1. 降低 AI 读取 specs 文档时的搜索成本和上下文消耗；
2. 支持 AI 按行范围读取原文片段；
3. 支持文档清单、章节树、引用关系和机制关系声明的可追溯检查；
4. 支持 Markdown 标题树、章节编号和真实标题的一致性诊断；
5. 支持 Tools 输出可审查的文档治理诊断结果。

specs 文档索引不得替代 specs 原文，不得维护独立规则解释，不得作为事实模型、行动模型、Rules、Tools 或 Web 的权威规则来源。

## 4. 事实源边界

specs 文档索引属于 Tools 从 Git 文件事实源生成的派生数据。索引内容必须能回溯到 specs 原文路径、行号和文件内容状态。

事实源边界如下：

1. specs 原文是规范事实源；
2. specs 文档索引是读取导航和校验辅助；
3. 索引与原文冲突时，以原文为准；
4. 索引缺失、过期或解析失败时，不得作为规范判断依据；
5. 稳定规则、字段契约、状态机、Human Gate、引用纪律和机制关系声明只能以对应 specs 原文为准。

Tools 输出的 specs 文档索引不得成为 specs 规范、Rules、审计结论、决策或任务状态的唯一来源。需要形成稳定事实的诊断结论，应按 `specs/10-事实源边界与承载规范.md` 和对应事实模型要求回写到权威位置。

## 5. 输入范围

第一阶段 specs 文档索引默认只覆盖以下输入：

1. `specs/*.md`。

其中 `specs/*.md` 包含正式规范文档、子文档、模型实践子文档、Contract 子文档和区段集合索引。

第一阶段默认不覆盖以下输入：

1. `specs/evals/*.md`；
2. `specs/refs/*.md`；
3. `ldvh-base/` 事实实例；
4. `docs/` 管辖项目资料和审计结果；
5. `web/` Web Tools 实现；
6. `tools/` Tools 辅助程序实现；
7. `tests/` 测试代码和测试夹具；
8. 管辖项目业务数据和生产内容索引。

`specs/evals/` 和 `specs/refs/` 文档只有在用户明确指定具体文件、具体目录，或明确要求读取内部评估、外部资料引用时，才可按原文读取。读取这些子目录文档时仍应遵守读取精准原则和事实源边界；evals 文档不得直接替代正式规范，refs 文档不得直接作为 LDVH 强制规则依据。

后续如需扩展默认输入范围，应先判断扩展对象是否仍属于 specs 文档索引。超出 specs 根目录文档范围的索引能力不得直接纳入本文，应由对应事实模型、行动模型、Tools 规范、Web 规范或项目级业务规范承接。

## 6. 索引类型

specs 文档索引包括以下类型。

### 6.1 文档清单索引

文档清单索引记录每份 specs 文档的基本信息，包括路径、标题、编号、文档类型、头部元信息、内容 hash、解析状态和来源范围。

文档清单索引用于帮助 AI 和 Tools 判断某份文档在 specs 体系中的位置，不替代 `specs/01-LDVH目录说明.md` 的目录规划和编号分区，也不替代 03 的文档类型定义。

### 6.2 章节索引

章节索引记录 Markdown 标题树、标题层级、章节编号、标题文本、起止行号和父子关系。

章节索引用于支持 AI 按行范围读取原文片段。章节索引不得替代原文标题，也不得用索引标题修正文档标题。

### 6.3 头部元信息索引

头部元信息索引记录文档头部 `>` 字段，包括创建日期、更新日期、定位、适用范围、所属主文档、关系、上位依据、相关规范、索引范围、调研边界、执行效力、编号归属等。

头部元信息索引用于文档治理检查和文档类型判断。字段缺失、重复或语义冲突时，应输出诊断，不得自动补写。

### 6.4 引用关系索引

引用关系索引记录 specs 文档中的路径引用、章节引用和头部依据引用。

引用关系索引用于检查默认输入范围内的路径存在性、章节引用、上位依据和相关规范是否可追溯。引用关系索引不得推断未在原文出现的规范依赖。`specs/refs/` 反向引用纪律由 03 或对应专项检查承接，不进入第一阶段默认索引检查范围。

### 6.5 机制关系声明索引

机制关系声明索引记录普通 specs 文档中的机制关系声明表格，包括关联机制、关联实体、关系类型和同步触发。

机制关系声明索引用于辅助 Rules、Tools、Web 或其他机制同步检查。索引只反映原文表格，不得创造新的机制关系。

### 6.6 文档治理诊断索引

文档治理诊断索引记录解析失败、头部字段缺失、标题层级异常、章节编号重复、章节定位异常、引用路径不存在、机制关系声明表格异常等可机械化发现的问题。

诊断索引是检查结果，不是最终审计结论。需要形成稳定审计结论时，应回写到对应事实源。

## 7. 生成原则

specs 文档索引生成应遵循以下原则：

1. 输入必须来自 Git 文件事实源中的 specs Markdown 原文；
2. 解析逻辑必须确定性、可重复、可审查；
3. 每条索引记录应保留来源路径，涉及正文内容时应保留来源行号；
4. 解析失败时应输出诊断，不得静默跳过；
5. 解析失败不得导致 Tools 修改或覆盖原始 specs 文档；
6. 索引生成不得调用 AI、Skill 或 Agent；
7. 索引生成不得自动执行 Human Gate 判断；
8. 索引生成不得自动修改文档头部、章节标题、章节索引、引用关系或机制关系声明。

第一阶段生成原则应保持只读，不对 specs 原文执行受控写入。后续如需支持受控写入，应回到 `specs/12.01-Tools辅助规范.md` 的写入前检查、Human Gate 和写入后验证要求。

## 8. 输出原则

specs 文档索引输出属于派生数据。输出格式可以是 JSON、YAML、JSONL 或其他可审查文本格式。

输出应满足以下要求：

1. 明确标记输出是派生数据；
2. 明确标记生成时间、生成工具和输入范围；
3. 每条记录可追溯到来源文件；
4. 涉及章节或引用时应记录来源行号；
5. 包含用于判断过期的内容 hash 或等价机制；
6. 支持删除后从 specs 原文重新生成；
7. 不以输出文件作为唯一事实源；
8. 不在输出中维护独立规则解释或摘要替代原文。

第一阶段建议输出以下派生结果：

| 输出 | 用途 |
|---|---|
| specs-docs-index | 文档清单和头部元信息 |
| specs-sections-index | Markdown 标题树和章节行号 |
| specs-relations-index | 路径引用、章节引用和依据引用 |
| specs-mechanism-index | 机制关系声明表格提取结果 |
| specs-diagnostics | 文档治理诊断结果 |

输出目录和文件名由 Tools 实现或后续 ADR 确认。输出目录如需成为长期约定，应同步检查 `specs/01-LDVH目录说明.md` 和 `specs/12.01-Tools辅助规范.md`。

## 9. Markdown 章节定位关系

specs 文档的章节定位以 Markdown 标题树、章节编号、标题文本和来源行号为基础。机器生成的章节索引用于 AI 精准定位和文档治理诊断，不产生独立规范事实。

章节定位关系如下：

1. Markdown 原文标题是章节事实源；
2. 机器生成章节索引用于 AI 按行范围读取和 Tools 校验；
3. 机器生成章节索引可以检查章节编号、标题层级和真实 Markdown 标题的一致性；
4. specs 文档不得依赖文档内章节索引作为固定骨架；
5. 章节定位冲突时，应读取 Markdown 原文标题和 03 的文档骨架要求判断。

机器生成章节索引能替代行号定位能力，但不得替代 specs 原文。

## 10. AI 消费规则

AI 可以使用 specs 文档索引辅助定位规范文档和章节，但必须遵循读取精准原则和事实源边界。

AI 消费 specs 文档索引时应遵循以下顺序：

1. 根据任务识别需要查询的 specs 根目录规范文档或主题；
2. 使用文档清单索引或章节索引定位候选文档和章节；
3. 按索引中的路径和行号读取 specs 原文片段；
4. 以读取到的原文作为规范判断依据；
5. 索引缺失、过期、冲突或无法定位时，回退到搜索定位和行范围读取。

`specs/evals/` 和 `specs/refs/` 不属于默认索引消费范围。AI 只有在用户明确指定具体文件、具体目录，或明确要求读取内部评估、外部资料引用时，才可读取这些子目录文档；读取后仍不得将 evals 或 refs 文档直接作为 LDVH 稳定规范判断依据。

AI 不得只读索引而不读原文就执行高影响规范变更、Rules 修改、Tools 写入、Human Gate 判断或事实源回写。

Rules 文件可以引用本文作为 specs 文档定位和章节索引机制依据，但 Rules 不应复制维护完整索引说明。Rules 与本文或 03 冲突时，应回到 03 和本文修正 Rules 摘要。

## 11. Tools 辅助程序边界

specs 文档索引程序属于 Tools 辅助层能力，适合承担读取、解析、校验、聚合、上下文包生成、派生数据生成和缺口报告职责。

Tools 辅助程序可以：

1. 扫描 specs Markdown 文件；
2. 解析文件名编号、一级标题和头部字段；
3. 解析 Markdown 标题树并计算章节行号；
4. 提取路径引用、章节引用和机制关系声明表格；
5. 输出派生索引和诊断结果；
6. 为 AI 提供可追溯的最小上下文定位信息。

Tools 辅助程序不得：

1. 将索引类信息持久化为独立事实源；
2. 将 Tools 输出作为 specs 规范、Rules、审计或决策的唯一来源；
3. 自动修改 specs 原文、Rules 或事实实例；
4. 绕过 Human Gate 自动写入；
5. 直接调用 AI、Skill 或 Agent；
6. 用 LLM 摘要、向量化结果或语义推断替代确定性解析结果。

## 12. 失效、冲突与回退

出现以下情况时，应视为索引不可直接作为定位依据：

1. 索引缺失；
2. 索引生成时间早于输入文件变更；
3. 索引记录的内容 hash 与当前文件不一致；
4. 索引路径不存在；
5. 索引行号无法对应当前原文；
6. 索引内容与原文标题、头部字段或机制关系声明冲突；
7. Tools 报告解析失败或诊断结果阻断使用。

失效或冲突处理顺序如下：

1. 停止依据该索引作规范判断；
2. 回退到搜索定位和行范围读取；
3. 以 specs 原文为准完成当前判断；
4. 将索引问题记录为文档治理诊断或 Tools 缺口；
5. 必要时重新生成索引或修正文档原文。

当机器索引与 Markdown 原文标题冲突时，应读取 Markdown 原文标题和 03 的文档骨架要求判断，不得直接用机器索引覆盖原文标题。

## 14. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 将 specs 文档索引提升为规范事实源；
2. 改变 03 定义的 specs 文档骨架、头部字段或引用纪律；
3. 新增长期索引输出目录并改变目录事实源性质；
4. 让 Tools 自动修改 specs 原文、Rules 或事实实例；
5. 将索引输出作为 Rules、审计、决策或规范判断的唯一依据；
6. 将本文适用范围扩展到 `ldvh-base/` 事实实例或项目生产内容索引。

specs 文档索引检查至少包括：

| 检查项 | 标准 |
|---|---|
| 事实源边界 | 索引输出未被声明为最终事实源 |
| 输入范围 | 第一阶段默认只覆盖 specs 根目录 Markdown 文档，evals 和 refs 仅在用户明确指定时按原文读取 |
| 可追溯性 | 索引记录包含来源路径，章节和引用记录包含来源行号 |
| 章节定位 | Markdown 标题树和行号可用于按行范围读取原文 |
| 头部字段 | 必要头部字段可被解析，缺失或异常有诊断 |
| 引用关系 | 路径引用和章节引用可追溯，无法解析时有诊断 |
| 机制关系 | 机制关系声明表格只从原文提取，不创造新关系 |
| 失效回退 | 索引缺失、过期或冲突时回退到搜索定位和原文读取 |
| Tools 边界 | Tools 不自动修改原文，不绕过 Human Gate，不调用 AI、Skill 或 Agent |
