## 1. 本文定位

本文定义 Profile 事实模型使用的结构化数据契约。本文解决 Profile YAML 实例应包含哪些字段、字段类型和约束是什么、文件命名规则是什么、状态流转契约是什么，以及工具实现应如何消费本契约的问题。

本文是 Profile 事实模型契约字段的权威位置。本文是 `specs/26-Profile-项目画像.md` 的附件型契约子文档，不是独立事实模型。本文不得重新定义 Profile 的对象定位、准入条件、状态机语义、Human Gate、事实源回写或证据留存要求。发生冲突时，以 26 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款。

## 2. Profile YAML Schema

### 2.1 基础字段

Profile 基础字段遵循 `specs/07-LDVH事实模型基础规范.md` §7.3 的字段契约原则，所有事实模型应包含基础字段。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | Profile 对象 ID，格式为 `profile-{NNNN}` |
| `type` | string | 是 | 固定为 `profile` |
| `title` | string | 是 | 项目画像标题 |
| `status` | string | 是 | Profile 状态，必须属于标准状态枚举 |
| `created` | date | 是 | 对象创建日期 |
| `updated` | date | 是 | 最近更新日期 |

### 2.2 扩展字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `description` | string | 是 | 项目画像详细描述 |
| `project_name` | string | 是 | 项目名称 |
| `project_path` | string | 是 | 项目根路径 |
| `ldvh_base_path` | string | 是 | ldvh-base 目录路径 |
| `language` | string | 否 | 主要编程语言 |
| `framework` | string | 否 | 主要框架 |
| `rules_path` | string | 否 | .trae/rules/ 路径 |
| `skills_path` | string | 否 | .trae/skills/ 路径 |
| `related_tasks` | list of string | 否 | 关联 Task ID 列表 |
| `related_adrs` | list of string | 否 | 关联 ADR ID 列表 |
| `notes` | string | 否 | 补充说明 |

### 2.3 完整 YAML 示例

```yaml
id: profile-0001
type: profile
title: ld-vibe-harness 项目画像
status: active
created: 2026-06-04
updated: 2026-06-04
description: LDVH 核心框架项目，承载规范体系、事实模型和工具链
project_name: ld-vibe-harness
project_path: /Users/dmh2002/trae_projects/ld-vibe-harness
ldvh_base_path: /Users/dmh2002/trae_projects/ld-vibe-harness/ldvh-base
language: Python
framework: ""
rules_path: /Users/dmh2002/trae_projects/ld-vibe-harness/.trae/rules
skills_path: /Users/dmh2002/trae_projects/ld-vibe-harness/.trae/skills
related_tasks:
  - task-0001
related_adrs:
  - adr-0001
notes: LDVH 核心项目，所有规范和事实模型的管辖项目
```

## 3. 字段约束

1. `status` 必须属于 Profile 标准状态枚举：`draft`、`active`、`suspended`、`archived`；
2. `type` 必须固定为 `profile`；
3. `project_name` 不得为空字符串，应使用项目唯一标识名称；
4. `project_path` 必须为有效绝对路径；
5. `ldvh_base_path` 必须为有效绝对路径，且应为 `project_path` 的子路径；
6. `rules_path` 如填写，必须为有效绝对路径；
7. `skills_path` 如填写，必须为有效绝对路径；
8. `related_tasks` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
9. `related_adrs` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
11. `id` 格式必须为 `profile-{NNNN}`，编号固定 4 位，从 `0001` 起递增；
12. `created` 和 `updated` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
13. `related_tasks`、`related_adrs` 为列表类型，可为空列表，不得省略字段后以 null 替代空列表。

---

## 4. 文件命名契约

Profile 实例文件命名规则：

```text
profile-{NNNN}-project-name.yaml
```

约束：

1. 编号从 `0001` 起递增，固定 4 位；
2. 英文短标题使用小写短横线命名；
3. 每个项目独立编号，不使用跨项目全局编号；
4. 文件存放位置为 `ldvh-base/profiles/`；
5. 文件名变化必须同步检查所有引用该 Profile 的 `related_profiles` 和其他关联字段。

## 5. 状态流转契约

Profile 状态语义和流转规则由 `specs/26-Profile-项目画像.md` §5 定义，本文只提供结构化枚举和流转矩阵供 Tools 校验消费。

### 5.1 标准状态枚举

| 标准状态 |
|---|
| `draft` |
| `active` |
| `suspended` |
| `archived` |

状态含义依据 `specs/26-Profile-项目画像.md` §5.1。

### 5.2 合法状态流转

| 当前状态 | 可流转至 |
|---|---|
| `draft` | `active` |
| `active` | `suspended`, `archived` |
| `suspended` | `active`, `archived` |
| `archived` | 无 |

`active` → `suspended` 为暂停流转，应记录暂停原因。

`suspended` → `active` 为恢复流转，应记录恢复原因。

流转语义和约束依据 `specs/26-Profile-项目画像.md` §5.2。

## 6. 契约消费声明

1. Tools 辅助程序解析 Profile 时应依据本文定义的 YAML schema 和字段约束，不得自行扩张格式契约（依据 `specs/06-PyTools与WebTools规范.md §4` §6.1）；
2. Tools 辅助程序校验 Profile 时应覆盖字段完整性、状态合法性、条件必填和引用有效性；
3. Tools 辅助程序读取 Profile 时可依据本文状态枚举和字段契约执行状态筛选、详情解析和关联字段解析，但 Profile 读取结果是否可作为当前执行依据由 26 主文档和 Skill 流程判断；
4. 实践子文档和工具可以消费本文契约，但不得复制维护契约字段第二事实源；
5. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 specs/22-Change-变更记录.md）；
6. 契约子文档应先于工具实现创建，工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束；
7. 本文契约变更时，消费本文的 Tools 实现和对应测试必须同步更新。

## 7. 检查项

检查本文是否被正确使用时，应确认：

1. Profile YAML 实例字段是否完整，必填字段是否齐全；
2. `status` 是否属于标准状态枚举；
3. `type` 是否固定为 `profile`；
4. `project_path` 是否为有效绝对路径；
5. `ldvh_base_path` 是否为有效绝对路径且为 `project_path` 的子路径；
6. `related_tasks` 引用的事实模型 ID 是否有效；
7. `related_adrs` 引用的事实模型 ID 是否有效；
9. 文件命名是否符合 `profile-{NNNN}-project-name.yaml` 格式；
10. 状态流转是否合法，是否存在非法流转；
11. 终态 Profile 是否存在重开情况；
12. 暂停流转是否记录了暂停原因；
13. 恢复流转是否记录了恢复原因；
14. 工具实现是否依据本文 schema 解析和校验，未自行扩张格式契约；
15. 修改本文是否记录 Change，并在必要时触发 Human Gate（依据 specs/22-Change-变更记录.md）
