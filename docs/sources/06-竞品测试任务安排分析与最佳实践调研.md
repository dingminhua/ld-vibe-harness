## 1. 竞品测试任务安排对比

### 1.1 Gstack — 真实验证优先的多层测试体系

**测试架构：三层测试金字塔**

| 层级 | 名称 | 目标 | 执行方式 |
|------|------|------|---------|
| Tier 1 | 单元测试 | 验证单个函数/模块 | 自动化，CI 触发 |
| Tier 2 | 集成测试 | 验证 Skill 间协作 | Session Runner 编排 |
| Tier 3 | 端到端测试 | 验证完整用户流程 | Eval Store 评估 |

**核心机制：**
- **Session Runner**：测试编排引擎，按 Skill 流程顺序执行测试
- **Eval Store**：评估结果存储，支持历史对比和回归检测
- **`/qa` Skill**：质量检查入口，自动运行分层测试
- **`/review` Skill**：代码审查入口，人工确认 + 自动检查结合

**人工确认设计：**
- 确认点分为四类：偏好选择、安全护栏、流程门禁、首次配置
- 各 Skill 中确认点分布不均匀，`/review` 和 `/deploy` 确认最密集
- 确认粒度可配置，支持 Headless 模式跳过低风险确认

### 1.2 Superpowers — TDD 强制的工程纪律框架

**核心铁律体系：**

| 铁律 | 内容 | 强制方式 |
|------|------|---------|
| TDD 铁律 | 先写失败测试 → 写功能代码 → 重构 | Skill 强制拉起，不可跳过 |
| 验证铁律 | 每个 Task 必须有可验证的完成标准 | Task 模板强制包含验证字段 |
| 调试铁律 | 先写复现测试再调试 | 调试 Skill 检查测试存在性 |
| Skill 铁律 | 最佳实践编码为 Skill，版本化可 Review | Skill 注册机制 |

**子代理驱动开发：**
- 控制器-工作者模式：主 AI 分配任务，子代理执行
- 两阶段审查：规格审查员（功能是否符合计划）+ 质量审查员（代码质量）
- 模型选择策略：简单任务用小模型，复杂任务用大模型

**五种测试反模式识别：**
1. 测试通过但功能未实现（Happy Path Only）
2. 测试覆盖了实现细节而非行为
3. 测试间存在隐式依赖
4. Mock 过度导致测试失去意义
5. 测试不验证边界条件

### 1.3 BMAD-METHOD — 企业级质量门禁体系

**微文件架构：**
- 每个步骤为自包含文件，顺序强制执行
- Frontmatter 状态追踪，与 LDVH 状态机模型对应
- 文件即规格，规格即执行依据

**质量门禁体系：**

| 门禁 | 触发时机 | 检查内容 |
|------|---------|---------|
| PRD 七维度评审 | 需求阶段 | 完整性、一致性、可测试性、可行性、优先级、依赖、风险 |
| Story 完成门禁 | 开发阶段 | 验收标准全部通过、代码审查完成、文档更新 |
| 实现就绪门禁 | 编码前 | 设计方案已评审、测试用例已定义、依赖已就绪 |
| Sprint 状态机 | 迭代管理 | 规划→执行→审查→完成的强制流转 |
| 代码审查门禁 | 提交前 | 自审 + 正式 CR，Critical/Major/Minor/Suggestion 分级 |

**人工确认环节：**
- Gate 点：阶段转换时强制人工确认
- 菜单确认：多选项时人工选择方向
- Headless 模式豁免：低风险操作可配置自动通过

## 2. 竞品异同与优劣分析

### 2.1 测试任务安排方式对比

| 维度 | Gstack | Superpowers | BMAD |
|------|--------|-------------|------|
| **测试位置** | 开发后置，分层验证 | 开发前置，TDD 强制 | 全流程嵌入，门禁驱动 |
| **测试粒度** | 三层金字塔 | 铁律 + 反模式识别 | 七维度评审 + 多级门禁 |
| **人工确认** | 可配置粒度，支持 Headless | 服务于工程纪律，不可跳过 | Gate 点强制，低风险可豁免 |
| **自动化程度** | 高（Session Runner + Eval Store） | 中（TDD 循环自动，审查需人工） | 中（门禁自动检查，评审需人工） |
| **适用规模** | 中小团队快速迭代 | 小团队纪律强化 | 大型企业级项目 |

### 2.2 各竞品优劣

**Gstack 优势：**
- 真实验证优先，不依赖 Mock
- 自动化程度高，Session Runner 编排完整测试流程
- Eval Store 支持历史对比和回归

**Gstack 劣势：**
- 测试后置，可能积累技术债
- 人工确认粒度配置复杂，容易过度或不足

**Superpowers 优势：**
- TDD 强制，从源头保障质量
- 反模式识别，防止"测试通过但功能不对"
- 子代理交叉验证，减少单一 AI 盲区

**Superpowers 劣势：**
- 纪律过强可能降低开发速度
- 小团队可能觉得流程过重

**BMAD 优势：**
- 全流程门禁，质量保障最全面
- 微文件架构，规格与执行一体化
- 企业级适用，支持大规模团队

**BMAD 劣势：**
- 流程最重，小项目可能过重
- 门禁数量多，需要精细配置才能平衡效率

## 3. 行业最佳实践

### 3.1 STDD（规格-测试驱动开发）模式

SDD（规格驱动）和 TDD（测试驱动）的融合正在成为 AI 编程主流：

- **SDD** 通过 Markdown/YAML 文档强调需求（规格先行）
- **TDD** 通过 TestCase 强调质量（测试驱动）
- **STDD** = 规格定义验收标准 + 测试用例从规格派生 + TDD 循环执行

### 3.2 从 Vibe Coding 到 Agentic Engineering

Google 的 Addy Osmani 提出的 Agentic Engineering 四步工作流：

1. **从计划开始** → 规格中包含验收标准
2. **指导，然后审查** → 用审查人类 PR 的严谨度审查 AI 代码
3. **无情地测试** → 测试是 Vibe Coding 和 Agentic Engineering 最大的区分器
4. **拥有代码库** → 维护文档、版本控制、CI、监控生产

> "测试是你将不可靠的代理转变为可靠系统的方式。没有测试，AI 会愉快地在有问题的代码上宣布'完成'。"

### 3.3 Harness Engineering 的 Checkpoint 机制

- 安全 Checkpoint：每步执行后保存状态，失败可回滚
- Progress File：记录当前进度和已验证步骤
- 最小脚手架 + 最大操作 Harness

### 3.4 人工确认/审核机制汇总

| 机制 | 描述 |
|------|------|
| SDD 决策检查点 | 规格→计划→任务→实现→测试回归，每步人类审阅 |
| 计划审批 | 每个 Task 含精确验证标准，人工审核通过后才执行 |
| PR 级代码审查 | 用审查人类 PR 的严谨度审查 AI 代码 |
| 子代理交叉验证 | 规格审查员 + 质量审查员双重复核 |
| Commit 交互确认 | AI 分析 diff 生成 commit message，交互确认后提交 |

## 4. LDVH 改进建议

### 4.1 LDVH 现有机制与业界对照

| 业界实践 | LDVH 对应机制 | 匹配度 |
|---------|-------------|--------|
| SDD 规格先行 | Intent → Task 拆解 | 高 |
| 决策检查点 | Human Gate | 高 |
| 子代理审查 | Task 关闭条件（acceptance + closure_evidence） | 中 |
| OpenSpec 四段式 | Core Loop（Intent → Plan → Execute → Record） | 高 |
| Harness Checkpoint | Task 状态机 + blocked_by | 高 |
| Knowledge as Code | Skill + ADR | 高 |
| TDD 铁律 | **缺失** | 低 |

### 4.2 具体改进建议

**建议 1：明确测试 Task 在 Task 拆解中的位置**

当前 LDVH 的 Task 拆解没有强制要求包含测试 Task。建议：
- Task 拆解时，验收标准（acceptance）必须包含可测试的原子条件
- 复杂 Task（涉及代码变更）应拆出独立的验证子任务
- 验证子任务的 `blocked_by` 指向开发子任务，确保开发完成后才验证

**建议 2：引入验证铁律**

借鉴 Superpowers 的验证铁律，在 Task 规范中增加：
- 每个 Task 必须有 `verification` 字段（当前为可选）
- `verification` 应描述具体的验证方式（手动测试、自动测试、代码审查等）
- Task 关闭时 `closure_evidence` 必须引用验证结果

**建议 3：分层验证策略**

借鉴 Gstack 的三层测试和 BMAD 的多级门禁：
- 简单 Task（文档修改、配置调整）：验收标准 + 人工确认即可
- 中等 Task（功能开发、Bug 修复）：验收标准 + 自动测试 + 代码审查
- 复杂 Task（架构变更、跨模块影响）：验收标准 + 自动测试 + 代码审查 + 集成验证

**建议 4：Human Gate 粒度配置**

借鉴 Gstack 的可配置确认粒度和 BMAD 的 Headless 豁免：
- 当前 LDVH 的 Human Gate 是全有或全无
- 建议按风险级别配置：高风险操作强制确认，低风险操作可自动通过
- 风险级别可由 Task 类型、影响范围、变更文件数等维度判断

**建议 5：错误到规则的反馈闭环**

借鉴 Error-Driven Context Refinement：
- 当前 LDVH 的 Pitfall（陷阱/BUG）记录了问题，但缺乏从问题到规则的自动转化
- 建议增加 Pitfall → ADR 的推荐流程：当 Pitfall 关闭时，提示是否需要创建 ADR 固化经验
- Change 记录中标注是否源自 Pitfall 修复

## 5. 总结

LDVH 的治理框架（Core Loop、Human Gate、状态机、事实源）与业界 Agentic Engineering 最佳实践高度一致，核心架构无需大改。主要改进方向是**在 Task 层面补充测试纪律的明确规范**，包括：

1. 测试 Task 的位置和时机
2. 验证字段的强制化
3. 分层验证策略
4. Human Gate 的粒度配置
5. 错误到规则的闭环

这些改进可以在现有框架内通过规范升级实现，不需要架构层面的变更。
