## 1. 本文解决的问题

本文回答 LD Vibe Harness 项目目录层级、主要目录用途、目录事实源性质、目录间关系、文档工作区映射和 specs 编号分区，并为后续事实源边界、文档治理、Code 实现、Web 信息同步、工作模型规范和工作流程规范提供目录语境。

目录说明提供项目结构地图和目录事实源性质声明。本文回答"内容应放在哪个目录"和"该目录在事实源体系中的性质"；事实源权威性的判断原则、单一事实源规则和工具输出回写规则，由 `specs/04-事实源边界与承载规范.md` 定义。

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 的产品理念、价值实现标准、五类构成要素和基础规范索引。本文承接 00 中"开发环境、工作模型、工作流程、Code 和 Web 共同组成工程驾驭体系"的架构判断，专门定义这些内容在项目目录中的承载位置和 specs 编号分区。

本文是 LD Vibe Harness 项目目录规划、文档工作区映射、specs 编号分区和目录事实源性质声明的权威位置。00 只保留基础规范索引，不重复维护项目目录说明；04 定义事实源权威性判断原则，本文依据 04 的原则声明各目录在事实源体系中的性质，但不定义原则本身。

## 3. 目录规划

本文的权威领域是 LD Vibe Harness 项目目录规划、一级目录用途、目录之间的内容归属关系、目录事实源性质声明、管辖项目定义、文档工作区映射和 specs 编号分区。

### 3.1 管辖项目定义

本文中的"管辖项目"，指接入并使用 LD Vibe Harness 进行需求、任务、证据、变更、审计或交付治理的实际项目。管辖项目的完整定义和术语边界依据 `specs/02-术语规范.md` §7。管辖项目目录列表由工作区规则中的管辖项目配置维护。

### 3.2 一级目录说明

| 目录 | 定位 | 主要内容 | 事实源性质 |
|---|---|---|---|
| specs/ | LD Vibe Harness 规范文档工作区 | specs 正文、specs/evals、specs/refs | LDVH 规范事实源；evals/refs 不直接构成强制规则 |
| docs/ | 管辖项目文档工作区 | docs 正文、docs/evals、docs/refs、管辖项目资料、报告和操作说明 | 管辖项目文档事实源；不是 LDVH 规范事实源 |
| ldvh-base/ | 结构化对象实例目录 | Task、ADR、Change、Pitfall 等 LDVH 事实实例 | 结构化事实实例事实源 |
| web/ | Web 信息同步实现目录 | LD Vibe Harness Web 信息同步层的前端、后端、页面和相关实现 | 非最终事实源；Web 实现和运行状态不能替代事实源 |
| tools/ | Tools / PyTools 辅助工具目录 | 脚本、校验器、聚合器、受控写入工具和其他 Tools / PyTools 辅助工具 | 非最终事实源；工具实现和运行结果不能替代事实源 |
| tests/ | 自动化测试目录 | Tools、Web 和其他项目实现的自动化测试、测试夹具和测试辅助代码 | 非最终事实源；测试代码和测试结果不能替代事实源 |

各目录的事实源性质依据 `specs/04-事实源边界与承载规范.md` 定义的原则判断。目录名称和内容归属本身不自动决定事实权威性；事实是否为最终事实源、同一事实由哪里权威承载，必须依据 04、对应工作模型规范和工作流程判断。

### 3.3 specs 目录

specs/ 承载 LD Vibe Harness 的规范体系、外部资料引用和项目评估文档。

specs/ 继承 `specs/03-文档基础规范.md` 的文档工作区三分契约，特有规则由 `specs/03.01-规范文档规范.md` 定义。specs/ 中使用的术语边界和机制英文专名由 `specs/02-术语规范.md` 定义。

#### 3.3.1 refs 目录

refs/ 位于 specs/ 下，承载与 LD Vibe Harness 规范体系相关的外部资料引用。

refs/ 的内容来源是外部资料中与当前规范体系直接相关的材料，按自然序号（01 起）组织。refs/ 下的文档是外部资料的引用副本，用于在规范编写和内部调研时快速查阅，不改变其非规范事实源的性质。

refs/ 与 specs/ 规范体系之间的引用方向如下：

1. specs/ 根目录正式规范文档（00-79 编号区间）不得引用 specs/refs/ 中的任何文件，包括路径引用、关联规范声明和依据引用；
2. refs/ 不得反向引用 specs/ 目录内的任何文件，包括路径引用、关联规范声明和依据引用；
3. refs/ 下的文档不得包含对 specs/ 目录内文件的路径引用、关联规范声明或依据引用。

refs/ 下的编号只用于排序和引用便利，不属于 specs 规范编号体系。

#### 3.3.2 evals 目录

evals/ 位于 specs/ 下，承载因 LD Vibe Harness 项目实际情况而生成的评估文档。

evals/ 的内容包括对外部工具、方法、框架或概念的项目级评估，按自然序号（01 起）组织。evals/ 下的文档是内部调研结论的项目级表达，不直接构成强制规则；结论进入 00-79 正式规范区间或 ADR 后才成为稳定规则。

evals/ 与 specs/ 规范体系之间的引用方向如下：

1. specs/evals/ 可以引用 specs/ 根目录正式规范文档（00-79 编号区间）作为评估依据和上位规范；
2. specs/ 根目录正式规范文档（00-79 编号区间）不得引用 specs/evals/ 中的任何文件，包括路径引用、关联规范声明和依据引用；
3. specs/evals/ 的评估结论必须进入 00-79 正式规范区间或 ADR 后，才能被正式规范文档消费。

evals/ 下的编号只用于排序和引用便利，不属于 specs 规范编号体系。

#### 3.3.3 refs/trae 目录

refs/trae/ 位于 specs/refs/ 下，承载与 Trae 平台相关的外部资料引用。

refs/trae/ 的内容来源是 Trae 平台官方文档中与 LDVH 规范体系直接相关的材料，按自然序号（01 起）组织。refs/trae/ 下的文档是外部资料的引用副本，用于在规范编写和内部调研时快速查阅，不改变其非规范事实源的性质。

refs/trae/ 遵守 refs/ 的引用方向规则（§3.3.1）。

refs/trae/ 下的编号只用于排序和引用便利，不属于 specs 规范编号体系。

### 3.4 docs 目录

docs/ 承载管辖项目文档工作区，包括项目正文文档、docs/evals 内部分析、docs/refs 外部引用、管辖项目资料、管辖项目审计结果、报告、操作说明和产品资料。

docs/ 面向人的阅读、确认、审查和操作需要，不用于承载 LD Vibe Harness 规范正文。安装 LDVH 的管辖项目不默认创建 specs/；管辖项目文档工作区的特有规则由 `specs/03.02-管辖项目文档规范.md` 定义。

### 3.5 ldvh-base 目录

ldvh-base/ 承载结构化 LDVH 事实实例，例如 Task、ADR、Change、Pitfall 等。

ldvh-base/ 属于 ld-vibe-harness/ 项目内部目录，承载结构化 LDVH 事实实例。每个接入 LDVH 的管辖项目应各自拥有 ldvh-base/ 目录，由该项目自身管理。ldvh-base/ 下各对象实例的目录结构、字段、状态和验收规则由 20-39 LDVH 工作模型规范定义。

### 3.6 web 与 tools 目录

web/ 承载 LD Vibe Harness Web 信息同步、人类确认工作台、派生视图和受控编辑入口的实现。

tools/ 承载 Code / PyTools 辅助工具、脚本、校验器、聚合器和受控写入工具。

Code / PyTools 辅助层边界由 `specs/14-Code实现与工具规范.md` 定义；Web 信息同步层边界由 `specs/15-Web信息同步规范.md` 定义。

### 3.7 tests 目录

tests/ 承载 LD Vibe Harness 项目实现的自动化测试、测试夹具和测试辅助代码。

PyTools 辅助层测试要求依据 `specs/14-Code实现与工具规范.md` §8；测试代码、测试夹具、测试缓存和测试结果不得替代 Git 文件事实源。

## 4. specs 编号分区

specs/ 采用分区编号，编号本身必须表达文档在规范体系中的位置。编号分区围绕五类构成要素展开，而不是围绕文档形态展开。

新增或调整 specs/ 根目录正式规范文档编号时，应先判断内容权威领域，再选择编号：

1. 优先归并到已有权威文档；只有现有文档无法承载新的稳定权威领域时，才新增编号。
2. 新文档应进入与其主要构成要素或治理职责匹配的编号段；跨多个构成要素但主要定义目录、术语、文档或事实源边界时，进入基础规范区。
3. Code 与 PyTools 规则优先进入 14，Web 信息同步规则优先进入 15；06 是已拆分保留位，不得重新作为现行工具规范编号使用。
4. 工作模型主规范进入 20-39，工作流程主规范进入 40-59；历史 NN.SS 机制文件不决定 specs 根目录编号。
5. specs/evals/ 和 specs/refs/ 使用自然序号，编号只用于排序和引用便利，不占用 specs 根目录正式规范编号。

| 编号段 | 类型 | 说明 |
|---|---|---|
| 00 | 理念与纲要 | 定义 LD Vibe Harness 的存在理由、第一服务对象、价值实现标准、五类构成要素和顶层治理原则 |
| 01-03 | 基础规范 | 定义 LDVH 目录说明、术语规范和文档工作区基础规则 |
| 04 | 事实源边界规范 | 定义 Git 文件事实源边界、事实源承载和权威性原则 |
| 05 | Trae Solo 环境规范 | 定义 Rules、Skill、Agent 与 AskUserQuestion 等开发环境机制边界 |
| 06 | 已拆分 | 原 Python 与 Web 工具规范已拆分为 14 Code 实现与工具规范、15 Web 信息同步规范 |
| 07 | 工作模型基础规范 | 定义生产对象 / 工作模型通用规则 |
| 08 | 工作流程基础规范 | 定义工作流程通用规则与区段索引 |
| 09 | 保留基础规范扩展 | 保留给后续基础规范扩展 |

| 40-59 | LDVH 工作流程规范 | 40 为工作流程基础规范与区段索引，41 起为具体行动规范 |
| 80-99 | 保留 | 保留给后续扩展，不得未经确认提前占用 |
| specs/evals/ | 项目评估文档 | 承载 LD Vibe Harness 项目评估、设计探索、方案比较和经验分析，按自然序号组织 |

## 7. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 新增、删除、重命名或改变本文定义的一级目录；
2. 改变一级目录的定位；
3. 改变一级目录的事实源性质声明；
4. 将某类内容迁移到与本文目录规划不一致的位置；
5. 将目录用途说明扩展为事实源判断原则、对象规则或行动流程规则；
6. 新增 specs 编号段或改变编号体系。

当 AI 识别到上述情况时，依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §5.3 Human Gate 闭环执行。

目录规划检查至少包括：

| 检查项 | 标准 |
|---|---|
| 目录存在性 | 一级目录规划清晰 |
| 内容归属 | 文件放置符合本文目录用途说明 |
| 编号分区 | specs 文档编号符合本文编号分区 |
| 边界不扩张 | 本文未替代事实源规则、对象规则或工作流程规则 |
| 引用一致性 | specs 文档结构和事实源规则指向对应权威规范 |
| refs 反向引用 | refs/ 下文档未引用 specs/ 目录内文件 |
