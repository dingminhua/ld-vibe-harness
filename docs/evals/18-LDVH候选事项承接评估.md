## 1. 本文解决的问题

本文整理 LDVH 中跨多个规范、工作模型、工作流程或实现层的候选事项如何被识别、分流、承接、暂缓或废弃的内部评估结论。

候选事项通常来自内部评估、外部调研、Dogfood 经验、工具实践、Web 设计、第三方 Skill 接管、平台能力适配或运行闭环测试。它们可能有长期价值，但如果直接写入 00 总纲、工作对象规范、工作流程规范或实现层，容易造成规范膨胀、重复定义、第二事实源或过早机制化。

本文不替代具体正式规范。候选事项只有被吸收到对应正式规范、工作对象、Code、Web、测试、最佳实践或工作流程后，才具备对应效力。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 的存在理由、五类构成要素、事实源原则、运行闭环、Human Gate 和顶层价值标准。本文以 00 的治理边界为评估依据，只整理“哪些候选事项值得保留，以及应该由哪里承接”。

本文中的候选事项不得直接提升为 00 级原则。若候选事项涉及产品定义、五类构成要素、事实源权威性、运行闭环或 Human Gate 顶层边界，应先判断 00 是否已经覆盖；只有 00 无法承接且确属顶层原则变化时，才评估修改 00 并触发 Human Gate。

---
## 3. 候选事项定义

候选事项是已经显示出复用价值、治理价值或风险提示价值，但尚未完全确定正式归属、字段契约、流程边界、Code 实现、Web 呈现、测试方式或环境适配映射的内容。

候选事项可以包括：

1. 需要下游规范继续承接的总纲原则；
2. 尚未成为独立工作流程的行动模式；
3. 尚未成为工作模型字段或状态的事实表达需求；
4. 尚未成为 Code 或 Web 实现的校验、聚合、展示或受控写入需求；
5. 尚未稳定为最佳实践的执行经验；
6. 尚未完成接管的第三方、平台、用户既有或自动生成内容治理经验；
7. 明确不应吸收或需要暂缓的机制方向。

候选事项不是事实源状态、工作对象实例、Task 验收项或实现需求本身。需要执行时，应创建或更新对应工作对象；需要长期规则时，应吸收到对应正式规范。

## 4. 分流规则

候选事项建议按内容性质分流，不应在多个正式规范中复制维护同一规则。

| 候选事项性质 | 优先承接位置 |
|---|---|
| 产品定义、五类构成要素、事实源原则、运行闭环顶层纪律、Human Gate 顶层定义 | `docs/specs/00-LD-Vibe-Harness理念与纲要.md` |
| 目录、编号、文档工作区、evals/refs、引用和吸收规则 | 01、03 系列 |
| 术语、推荐用语、不推荐表达和术语变更治理 | `docs/specs/02-术语规范.md` |
| 规范落地要求、环境适配映射、运行投影、环境能力边界 | 04 系列 |
| 工作模型准入、字段契约、状态机、对象关系、验收和关闭条件 | 05、20、21-39 |
| 工作流程 Context、Scenario、Gate、执行流程、回写、证据和 Skill / Agent 调度 | 06、40、41-59 |
| Code 校验、解析、聚合、受控写入、测试入口或确定性执行 | `docs/specs/07-Code实现规范.md`、`tools/`、`tests/` |
| Web 态势入口、Human Gate UI、受控编辑、派生视图和 Web 文档边界 | `docs/specs/08-Web信息同步规范.md`、`web/` |
| 事实源权威性、单一事实源、承载介质和回写规则 | `docs/specs/09-事实源边界与承载规范.md` |
| 运行闭环测试、流程测试用例、失败诊断和自修正顺序 | `docs/specs/10-运行闭环测试规范.md`、`tests/` |
| 平台、第三方、用户既有、项目既有或自动生成内容接管 | 11、11.01、40 中接管类候选流程 |
| 非强制经验、执行习惯、失败红旗和案例 | `docs/specs/12-最佳实践.md` |

如果候选事项同时影响多个位置，应先选择权威归属位置，再让其他文档只保留入口摘要或引用关系。

## 5. 当前候选事项清单

本节整理仍有承接价值、但不宜直接写入上位规范的候选事项。状态含义如下：

| 状态 | 含义 |

| covered | 已由当前正式规范主体覆盖，本文仅保留一致性提醒 |
| candidate | 有价值，但需在承接位置继续讨论或细化 |
| deferred | 暂缓，不进入当前最小运作主线 |
| rejected | 不吸收，后续不得以同一理由恢复 |

### 5.3 暂缓事项

| 候选事项 | 状态 | 暂缓原因 |
|---|---|---|
| 自建 MCP 作为核心能力入口 | deferred | 当前 Code、Web、Validator、Context Pack 和受控写入边界尚未稳定；优先本地 Code 和 Web |
| ProjectGroup 工作模型 | deferred | 当前管辖项目配置已能承接最小项目名册；跨项目聚合需求未稳定 |
| Automation / Cron 工作模型 | deferred | Task、Change、Verify、Web 和 Validator 闭环尚未稳定 |
| 大规模生成 Rules、Skill、Validators 或 Web schema | deferred | 规范结构化程度、字段契约、状态机、Human Gate 条件和测试覆盖仍需逐步整理 |
| Web 开放式写入后台 | deferred | 受控轻写入可以讨论，开放式 YAML 编辑或任意字段写入不得先行 |

### 5.4 不吸收事项

| 候选事项 | 状态 | 理由 |
|---|---|---|
| 隐藏本地状态目录、memory store、local database 或 Web 数据库作为核心事实源 | rejected | 会制造第二事实源 |
| AI 自动 push、release、merge | rejected | 属于 Human 权限边界 |
| 分数式完成标准 | rejected | LDVH 完成标准应基于 acceptance、验证、evidence、Human Gate、Change 和状态机 |
| 人格化 Agent 系统 | rejected | LDVH 中的 Agent 是独立上下文、专业审计或隔离评估能力，不是人格角色系统 |
| AI 主控仅凭自身总结完成审查和关闭 | rejected | Verify 必须具备外部性和可追溯证据 |
| 平台能力替代 LDVH 内核 | rejected | Codex、Trae、MCP、第三方 Skill 或 Web 能增强底座，但不能替代事实模型、Task 治理、Human Gate 和运行闭环 |

## 6. 后续承接建议

后续 AI 或 Human 处理候选事项时，建议按以下顺序判断：

1. 判断该事项是否已由正式规范覆盖；
2. 若已覆盖，只引用权威规范，不复制候选表述；
3. 若未覆盖，按 §4 选择唯一优先承接位置；
4. 判断是否需要 Human Gate；
5. 若需要执行，创建或更新对应工作对象；
6. 若需要长期规则，修改对应正式规范并声明规范落地要求；
7. 若只是经验，进入最佳实践；
8. 若只是输入材料，保留在 evals 或 refs，并按 03 的来源与关联对象规则登记；
9. 若属于 deferred 或 rejected，不得绕过本文直接创建模型、流程、Code、Web 或运行投影。

候选事项不应直接作为 Task 关闭依据、ADR 决策依据、Code 实现依据或 Web 写入依据。执行层只能消费已经归属到正式规范或工作对象中的内容。

## 7. 后续吸收建议

本文不是正式规范，不声明规范落地要求。若本文中的候选事项后续被吸收到正式规范，应由对应正式规范按 `docs/specs/04.01-规范落地要求规范.md` 声明规范落地要求。

| 吸收场景 | 建议处理 |
|---|---|
| 吸收到正式规范 | 对应规范应声明规范落地要求、Human Gate 与检查要求 |
| 吸收到工作对象 | 对应对象应记录来源、影响范围、验证方式和关闭证据 |
| 吸收到 Code、Web 或测试 | 应先确认正式规范依据，再实现、验证和回写结果 |
| 保留为最佳实践 | 应说明适用场景、不适用场景、检查点和升级出口 |
| 继续保留为 evals | 应保留来源、关联对象和调研边界，不得被当作正式规则 |

## 8. 升级前确认点

以下情况在升级本文候选事项前，建议评估 Human Gate：

1. 将 candidate 升级为正式规范规则、工作模型、工作流程、Code、Web 或运行投影；
2. 将 deferred 升级为 candidate 或正式规则；
3. 恢复 rejected 事项；
4. 改变候选事项优先承接位置；
5. 删除仍被其他正式规范引用的候选事项；
6. 将候选事项直接写成 00 级原则；
7. 创建新的工作模型、工作流程或实现层能力来承接候选事项。

候选事项升级前至少检查：

| 检查项 | 标准 |
|---|---|
| 归属唯一 | 已选择唯一优先承接位置 |
| 状态清晰 | covered、candidate、deferred、rejected 未混用 |
| 不越权 | candidate 未被当作 active 规则执行 |
| 不重复 | 未在多个正式规范复制维护同一规则正文 |
| 不恢复取消项 | Profile、Evidence、ProjectGroup、Automation 等已取消或暂缓项未绕过本文恢复 |
| 事实源边界 | 未把 evals、refs、聊天、Web、Skill 或 Agent 输出当作最终事实源 |
