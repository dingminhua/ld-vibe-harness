## 1. 总判断

v1 的子文档和成员文件不是为了把文档拆短，而是承担机制性归口。v2 可以减少文件数，但不能删除机制。

迁移口径是：

1. 子文档减少必须是机制迁移，不是机制消失；
2. 附件只能承载长表、矩阵、模板、示例或边类型清单，不得承载主规范机制；
3. Code 当前消费的元信息、章节锚点、成员自描述、保障要求表和字段注册列必须有 v2 兼容或迁移层；
4. Web 虽暂不实施 v2，但 Web 读取事实对象、状态、字段和 Spark 创建白名单的现有契约不能被 v2 静默破坏。

## 3. 当前 v2 高风险点

### 3.1 02 不得成为单一 schema 权威

v2 02 可以成为事实模型与字段治理的统一入口，但不得变成所有字段 schema 的唯一权威。

必须保持以下 owner 分层：

| 问题 | 归口 |
|---|---|
| 公共字段语义 | 02 |
| 内容格式类型 | 02 |
| 字段注册表和机器消费元数据 | 02 授权附件 |
| 字段是否被某模型采用 | 20-29 具体模型 |
| 字段是否必填、状态条件、关闭条件 | 20-29 具体模型 |
| 对象内完整 schema | 20-29 具体模型 |
| Code/Web 消费字段 | Code/Web 依据 02、附件和具体模型共同派生，不反向定义规范 |

### 3.2 子文档取消不等于机制取消

若 v2 不保留 v1 形式上的 `03.01`、`03.02`、`03.03`、`03.04`，对应机制必须迁入主规范或成员主文件。

不得把 `ldvh_doc`、`ldvh_member`、保障要求类型、成员锚点、资产登记机制或环境适配状态交给普通附件独立维护。

### 3.3 02 事实源重排是高影响重构

v2 `02-事实模型基础规范.md` 对 v1 `09` 的承接属于高影响重构，不是对 v1 `04` 的简单前移。

在 Human 单篇核对前，不得把 v1 `09` 视为已并入 v2 02，也不得让 03、04、05、06 的差异规则替代全局事实源原则。

### 3.4 知识地图只读派生

知识地图必须是 Code 基于 active specs、管辖项目配置、工作对象字段和 Git history 实时解析出的只读关系投影。

知识地图不得：

1. 落盘为 `entities.json`、`edges.json` 或图数据库缓存；
2. 成为事实源；
3. 反向维护项目清单；
4. 默认接管、迁移、重排或强制校验用户 docs；
5. 以裸对象 ID 作为跨项目全局节点 ID。

## 4. Code v2 兼容底线

Code v2 原型前，至少应确认以下兼容或迁移层：

1. v1 `ldvh_doc` 到 v2 metadata 的映射；
2. v1 `ldvh_member` 到 v2 成员自描述的映射；
3. v1 章节标题锚点到 v2 章节锚点的双解析或迁移提示；
4. v1 字段注册表列名和枚举到 v2 字段注册表的映射；
5. v1 事实对象目录、状态、字段和 DTO 到 v2 的兼容策略；
6. v1 Web Spark 创建白名单和 WorkCase orchestration 展示字段不被静默破坏；
7. `python3 code/specs_validate.py all --fail-on-diagnostics` 继续作为 active specs 的回归底线。

## 5. Gate 完成标准

进入任一 v2 正式规范迁入前，应先完成：

1. 每个 v1 机制性契约都有 v2 目标、保留方式和消费方；
2. 每个 v2 主规范都说明自己承接哪些 v1 机制、不承接哪些 v1 机制；
3. 每个附件都有主规范授权，且不定义主规范原则；
4. 每个 Code v2 解析能力都有输入范围、输出边界、事实源回指和测试策略；
5. 每个高影响重构项单独经过 Human 核对。
