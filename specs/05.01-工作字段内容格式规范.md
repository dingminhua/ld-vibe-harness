## 1. 本文解决的问题

本文回答 LDVH 工作模型工作对象中的公共字段语义边界、字段内容格式和消费注册问题，尤其是 YAML 工作对象和 Study Markdown frontmatter 中的字段，应采用什么格式书写、被 Web 如何语义化渲染、被 Code 如何校验。本文定义公共字段的语义边界（每个字段回答什么问题、不应该写什么、适合使用哪类内容格式），并维护所有工作对象字段名和重要嵌套字段路径的内容/消费注册表。

具体工作模型规范定义对象特有字段契约。本文不定义具体工作模型是否采用某字段、字段是否必填、状态条件必填、对象状态机、关闭条件或对象内结构约束，这些仍由 `specs/05-工作模型基础规范.md` 和 20-39 具体工作模型规范负责；Git 提交记录的 message 契约由 `specs/09.01-Git提交记录与变更追溯规范.md` 承接，不属于工作对象 YAML 字段内容格式。

字段进入 20-39 具体对象规范前，应先在本文注册字段名或重要嵌套字段路径；字段注册只登记字段语义、内容格式、Code/Web 消费元数据、废弃字段和别名关系，不替代对象完整 schema。

引入全字段注册表的核心原因，是避免“非公共字段”在不同工作对象中各自定义出语义相同、格式相近但名称、消费方式或迁移关系不同的重复字段。字段一旦会被 AI 写入、Code 校验、Web 渲染、跨对象引用或迁移逻辑消费，就不只是某个对象内部的局部文本；如果这些字段分散在各对象规范中独立定义，容易导致同类内容重复建模、同名字段语义漂移、旧字段迁移不可见、Code 无法确定性校验、Web 无法稳定表达。

因此，具体对象规范需要新增对象特有字段时，应先判断该字段是否与已有注册字段承载同一类内容。若语义相同，应复用已注册字段名或在本文登记别名/废弃映射；若确需使用不同字段名，应在本文登记其对象特有语义、消费方式和不复用既有字段的原因。本文通过注册表统一“字段名如何被理解和消费”，20-39 具体对象规范再决定“哪些字段被该对象采用以及何时必填”。

## 2. 与 00、05 和 09 的关系

00 将工作模型定义为 LDVH 五类构成要素之一。`specs/05-工作模型基础规范.md` 定义工作模型字段契约和事实实例边界，是本文的直接上位依据。`specs/09-事实源边界与承载规范.md` 定义 Markdown 和 YAML 的承载分工原则：

- Markdown 更适合承载背景、原因、解释、设计语境、长文本内容；
- YAML 更适合承载工作计划、状态、结构化关系、审计字段和需要工具解析的事实。

本文在工作模型字段内容格式范围内承接这一分工，进一步规定：YAML 工作模型工作对象中的长文本字段，其内容可以使用 Markdown 语义书写。Markdown 是字段内容格式，不是新事实源。YAML 或对应具体工作模型声明的事实源仍是权威事实源，Web 和 Code 是派生视图。本文不作为 09 的子文档，也不重新定义 09 的事实源边界。

## 3. 内容格式类型

LDVH 工作模型字段内容分为以下七种格式类型。格式类型不是独立工作模型，不具备独立生命周期、状态机或关闭条件，而是字段内容的书写和消费规则。

### 3.1 Narrative / 叙述说明

适合字段：`description`、`notes`、`context`、`success_criteria`、`constraints`、`rationale`

用途：说明背景、问题、目标、范围、约束。

书写规则：

1. 允许使用 Markdown 标题、段落、列表、引用、代码块、表格、链接；
2. 不强制 checklist；
3. 推荐使用 `## 背景`、`## 目标`、`## 边界` 等标题结构提升可读性；
4. YAML 中应使用块标量 `|` 承载。

示例：

```yaml
description: |
  ## 背景

  当前 Web 呈现中长文本字段缺少统一格式规范。

  ## 目标

  建立工作字段内容格式规范，统一 AI 写入、Web 渲染和 Code 校验。
```

### 3.2 Checklist / 检查清单

适合字段：`acceptance`

用途：完成标准、关闭检查项、质量门禁。

书写规则：

1. 必须使用 `- [ ]`（未完成）或 `- [x]`（已完成）格式；
2. 每项必须是可独立验证的原子条件；
3. 不应包含非 checklist 内容；如需补充说明，放在 checklist 项的文本中；
4. YAML 中应使用块标量 `|` 承载；
5. 具体工作模型若把 Checklist 字段声明为关闭条件，关闭前所有检查项必须标记为 `- [x]`。

示例：

```yaml
acceptance: |
  - [ ] 建立字段内容格式规则
  - [ ] 定义七种内容格式的边界和书写规则
  - [ ] 明确 Code 校验消费规则
  - [ ] 运行事实源校验通过
```

### 3.3 验证证据

适合字段：`verification`、`verification_evidence`、`closure_evidence`

用途：记录验证过程、命令、结果、结论，以及关闭判断所需的证据摘要。

书写规则：

1. 应使用稳定 Markdown 骨架表达验证，不得写成无结构长段落；
2. 新写入或重写 `verification`、`verification_evidence`、`closure_evidence` 时，应按顺序包含以下二级标题：`## 验证计划`、`## 验证命令`、`## 验证结果`、`## 结论`；
3. `## 验证计划` 回答“要验证什么、依据什么判断通过”，应列出验证对象、判断条件、人工检查或自动检查范围；
4. `## 验证命令` 记录实际运行的命令、脚本、检查入口、人工检查动作或“不适用”的理由；命令应使用 fenced code block 或行内代码；
5. `## 验证结果` 记录每项检查的结果摘要、关键输出、路径或观察结论；不得粘贴超长日志，必要时引用日志、截图、报告或 commit；
6. `## 结论` 给出明确验证结论，例如“通过”“未通过”“部分通过/降级接受”“未运行”，并说明残留风险、关闭判断或后续分流；
7. YAML 中应使用块标量 `|` 承载；
8. 具体工作模型若把验证证据字段声明为关闭条件，进入关闭状态前对应字段不得为空，且不得只写“已验证”“见上文”“通过”等无法复查的短句。

存量对象可兼容读取旧格式；新增、重写或进入关闭审查的对象应使用上述四段式结构。Web 可以据此把验证证据渲染为分段阅读区，Code 可以据此检查关键二级标题是否存在。

#### 3.3.1 Human Gate 记录承载

涉及 Human Gate 的验证证据字段，可以嵌入 `Human Gate 记录：` 文本块。该记录应符合 `specs/06-工作流程基础规范.md` §6.3.1 的最小证据结构，并可被 `code/specs_validate.py human-gate` 检查。

Human Gate 记录进入 `closure_evidence`、ADR `context` / `consequences`、工作流程结果、Memo 或其他事实源字段时，只作为对应字段中的证据片段，不创建独立验证证据对象，也不得替代对象状态机、决策正文、验证结论或 Git 提交记录追溯。

示例：

````yaml
closure_evidence: |
  ## 验证计划

  检查字段内容格式规范、Web 字段渲染和对应测试是否一致。

  ## 验证命令

  ```bash
  python3 code/specs_validate.py doc specs
  npm run check --workspace web
  ```

  ## 验证结果

  两项检查均通过，未发现结构错误或类型错误。

  ## 结论

  工作满足验收条件。
````

### 3.4 Decision / 决策记录

适合字段：`decision`、`consequences`

用途：记录决策选择、理由和影响。

书写规则：

1. 应明确"选择了什么"和"为什么"；
2. 应区分已决策和未决策内容；
3. 如决策会改变事实源边界，应进入 ADR；
4. YAML 中应使用块标量 `|` 承载。

ADR `consequences` 字段是决策影响闭环，不写成泛泛的“积极后果/消极后果”。`active` ADR 必须按顺序固定使用以下五个二级标题：

1. `## 正向价值`：依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §4 的 V1-V10 价值标准说明该决策服务什么价值；
2. `## 逆向价值`：依据 `specs/00-LD-Vibe-Harness理念与纲要.md` §4 的 V1-V10 价值标准，说明决策成功生效后仍确定接受或长期承受的价值削弱、牺牲或折中；若不存在逆向价值，必须填写 `当前决策无逆向价值`；
3. `## 实施成本`：说明迁移、实现、维护、学习、Web 呈现、校验或协作成本；
4. `## 风险评估`：说明事实源漂移、上下文过载、判断误导、Human Gate 缺失、实现不一致等概率性风险；
5. `## 注意事项`：说明通过规范约束、Code 校验、Web 呈现、Human Gate、后续 WorkPlan、降级策略或关联对象需要注意和托底的事项。

`## 逆向价值` 只记录相对 `specs/00-LD-Vibe-Harness理念与纲要.md` §4 的 V1-V10 价值判断中被削弱、牺牲或折中的部分，存在逆向价值时必须点名 `V1`-`V10` 中至少一项；不记录实施投入、迁移摩擦或概率性风险，这些内容分别写入 `## 实施成本` 与 `## 风险评估`。

示例：

```yaml
decision: |
  采用 YAML 字段内 Markdown 作为内容格式方案。

  ## 理由

  - 不改变事实源边界
  - 兼容现有 Validator
  - Web 改造成本较低
consequences: |
  ## 正向价值

  - 服务 V8 可靠回写：字段内容仍在 YAML 事实源中，Markdown 只是内容格式。

  ## 逆向价值

  当前决策无逆向价值

  ## 实施成本

  - Web 和 Code 需要统一消费 Markdown 字段。

  ## 风险评估

  - 如果缺少字段注册，Markdown 内容可能被不同入口解释为不同语义。

  ## 注意事项

  - 通过本文字段注册表、Code 校验和 Web 统一渲染规则约束消费方式。
```

### 3.5 Reference / 引用索引

适合字段：`related_docs`、`related_rules`、`urls`、`source_docs`

用途：记录引用路径、关联对象和外部资料。

书写规则：

1. 列表元素应为字符串路径或对象 ID；
2. 内部路径应可被 Code 校验存在性；
3. 外部链接使用完整 URL；
4. 这些字段通常是 list 类型，不是 Markdown 文本；
5. `urls` 只保存外部 `http(s)` 网址。每个条目必须使用结构化网址对象，至少包含 `ref` 和 `summary`：`ref` 必填并保存完整 `http(s)` URL，`summary` 必填并用中文说明该网址在当前报告中支撑什么判断，`title` 是可选展示标题。不得写裸 URL 字符串，也不得用英文或空泛文本替代中文简介。

示例：

```yaml
related_docs:
- specs/03-文档基础规范.md
- specs/09-事实源边界与承载规范.md
related_rules:
- specs/05.01-工作字段内容格式规范.md
urls:
- ref: https://example.com/reference
  title: 外部参考资料标题
  summary: 说明该网址支撑报告中的哪个判断，而不是复制外部资料正文。
```

### 3.6 Log / 过程记录

适合字段：`transition_reasons`、执行过程摘要

用途：追踪过程、记录关键节点和后续观察。

书写规则：

1. 适合时间线或过程记录；
2. 不一定是最终结论；
3. 应避免变成无结构流水账；
4. YAML 中应使用块标量 `|` 承载。

### 3.7 Structured / 结构化对象

适合字段：`orchestration`、`orchestration.execution_items`、`orchestration.review`

用途：承载对象内部的结构化子对象或列表，使 Code 能按路径校验、Web 能按结构化语义呈现。

书写规则：

1. 使用 YAML object 或 list[object]，不得写成 Markdown 字符串；
2. 重要嵌套字段路径应在本文 §5 注册；
3. 完整对象内 schema、字段是否必填、状态条件和关闭条件由具体工作模型规范定义；
4. Web 应按结构化区域语义消费，不得只作为普通 JSON/YAML 文本展示；
5. Code 可依据注册路径做基础类型、枚举、引用和废弃字段检查，但不得用本文替代具体工作模型规范中的对象内约束。

## 4. 公共字段语义定义

本节定义跨工作对象共享的公共字段语义边界。每个公共字段明确：回答什么问题、不应该写什么、适用方式和内容格式。各具体工作模型规范定义对象特有字段契约，公共字段引用本节。

### 4.1 全局公共字段

以下字段所有工作对象在采用时 SHALL 遵循统一语义：

| 字段 | 回答什么问题 | 不应该写什么 | 内容格式 |
|------|------------|------------|---------|
| `id` | 唯一标识 | 描述性内容 | string |
| `type` | 对象类型 | 描述性内容 | enum |
| `title` | 一句话概括 | 详细说明、验证方法、状态变化 | string |
| `status` | 当前状态 | 状态变化历史、变更原因 | enum |
| `created` | 创建时间 | 修改时间 | datetime |
| `updated` | 最后更新时间 | 创建时间 | datetime |
| `description` | 这个对象是什么、为什么存在 | 验证方法、风险说明、约束条件、验收标准、状态变化 | Narrative |

`datetime` 字段必须写为 ISO 8601 时间戳，至少包含日期、小时和分钟，例如 `2026-06-18T17:10:00+08:00` 或 `2026-06-18T17:10:00`。仅包含日期的 `YYYY-MM-DD` 属于 `date`，不得写入 `created`、`updated`、`closed_at`、`review_requested_at`、`evolution.at` 等 `datetime` 字段。只有字段契约明确为 `date` 时，才允许使用纯日期，例如 ADR 的 `date` 或 Memo 的 `resolved_at`。

`description`（描述）是所有对象的核心叙述字段，只承载对象的背景、目标和范围说明。以下内容不应写入 `description`，应写入对应字段：

- 验证方法 → `verification`（验证）或 `acceptance`（验收标准）
- 风险说明、约束条件、降级方式 → `constraints`（约束）或 `notes`（备注）
- 验收标准 → `acceptance`（验收标准）
- 状态变化历史、前后状态、修改原因和执行者 → Git 提交记录派生信息

### 4.2 部分公共字段

以下字段在被具体工作模型采用时 SHALL 遵循统一语义。本文只定义公共语义和内容格式，不规定具体工作模型是否必须采用这些字段。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `source` | 这个对象的输入来源 | 一般关联、验证结论 | 需要记录输入来源的对象 | Reference / Narrative |
| `source_detail` | 输入来源的说明、触发问题或原始输入摘要 | 一般关联清单、状态变化历史 | 需要补充来源上下文的对象 | Narrative / Reference |
| `acceptance` | 完成的判断条件 | 验证方法、风险说明、背景 | 需要验收检查的对象或执行项 | Checklist |
| `verification` | 怎么验证完成 | 风险说明、约束条件、背景说明 | 需要记录验证方式或验证结果的对象 | 验证证据 |
| `verification_evidence` | 成功标准如何被检查 | 验收标准、背景说明 | 需要记录验证证据的对象 | 验证证据 |
| `closure_evidence` | 为什么可以关闭、关闭结果、残留风险和 Human Gate 结果 | 验收标准、背景说明 | 需要关闭证据的对象 | 验证证据 |
| `closed_at` | 关闭时间 | 创建时间、更新时间 | 需要关闭时间的对象 | datetime |
| `archive_reason` | 为什么归档 | 归档后的内容、验证 | 需要归档原因的对象 | Narrative |
| `deprecated_reason` | 为什么废弃 | 归档原因、状态流水、替代关系 | 需要表达废弃原因的对象 | Narrative |
| `discard_reason` | 为什么废弃 | 废弃后的说明、验证 | 需要废弃原因的对象 | Narrative |
| `notes` | 其他字段无法承载的补充说明 | 核心信息、验证方法、决策 | 需要补充说明的对象 | Narrative |

具体工作模型只要定义 `archived`、`deprecated`、`discarded` 等非活跃终态，就必须为该终态定义并填写对应原因字段：`archived` 使用 `archive_reason`，`deprecated` 使用 `deprecated_reason`，`discarded` 使用 `discard_reason`。原因字段必须说明为什么对象不再处于活跃入口，以及后续 AI / Human 应如何理解该对象；不得只写“已归档”“已废弃”等重复状态本身的空泛文本。

工作对象不得手写维护 `status_history`。状态变化历史、前后状态、修改原因和执行者由 Git 提交记录派生；需要长期保留的语义转折应写入对象专用字段、证据字段或相关工作对象，不得用手写状态历史形成第二事实源。

`verification`（验证）只承载验证计划、验证命令、验证结果和验证结论。以下内容不应写入 `verification`，应写入对应字段：

- 风险说明、约束条件、降级方式 → `description`（描述）或 `notes`（备注）
- 背景说明 → `description`（描述）
- 验收标准 → `acceptance`（验收标准）

### 4.3 引用字段语义边界

引用字段分为两类：来源引用（`source_*`）和关联引用（`related_*`）。

**来源引用 `source_*`**：本对象的输入来源。如果某个对象是创建本对象的直接原因或输入，应放入 `source_*`。

**关联引用 `related_*`**：与本对象有关联的其他对象。如果某个对象只是与本对象有关联但不是直接输入来源，应放入 `related_*`。

| 字段 | 回答什么问题 | 不应该写什么 | 适用方式 | 内容格式 |
|------|------------|------------|---------|---------|
| `related_docs` | 引用的文档路径 | 对象 ID 引用 | 需要关联文档的对象 | Reference |
| `urls` | 报告正文提炼出的外部网址及用途摘要 | 项目内文档、规范路径、代码位置或纯说明文本 | Study 等需要提炼外部网址依据的对象 | Reference |
| `related_adrs` | 关联的决策记录 | 来源决策（用 source_*） | 需要关联 ADR 的对象 | Reference |
| `related_memos` | 关联的备忘 | 来源备忘（用 source_memos） | 需要关联 Memo 的对象 | Reference |
| `related_studies` | 关联的研究报告 | 报告正文或研究过程 | 需要关联 Study 的对象 | Reference |
| `related_workareas` | 关联的工作域 | 所属工作域（用归属字段） | 需要关联 WorkArea 的对象 | Reference |
| `related_workplans` | 关联的工作计划 | 所属工作计划（用归属字段） | 需要关联 WorkPlan 的对象 | Reference |
| `related_pitfalls` | 关联的踩坑经验 | 来源踩坑经验 | 需要关联 Pitfall 的对象 | Reference |
| `related_rules` | 关联的规范路径 | 一般文档引用（用 related_docs） | 需要关联规范或能力路径的对象 | Reference |
| `superseded_by` | 替代本对象的新对象 | 一般关联 | 需要替代关系的对象 | Reference |
| `source_objects` | 本对象的来源对象 | 一般关联（用 related_*） | 需要记录对象来源的对象 | Reference |
| `source_memos` | 本对象的来源备忘 | 一般备忘关联（用 related_memos） | 需要记录备忘来源的对象 | Reference |

判断规则：

1. 如果引用是本对象的直接输入来源，放入 `source_*`；如果只是一般关联，放入 `related_*`。
2. 如果引用是本对象的所属容器，使用具体工作模型规范定义的专属归属字段，不放入 `related_*`。
3. 如果具体工作模型仍保留替代关系字段，使用 `superseded_by`，不放入 `related_*`；未保留该字段的对象不得自行引入替代状态或替代字段。
4. 如果引用是文档路径，使用 `related_docs`；如果是规范、Rules、Skill、Code 或 Web 路径，使用 `related_rules`。
5. 如果引用是 Study 报告正文中的外部网页资料，使用 `urls`；`urls` 只承载 `http(s)` URL 及用途摘要，不表达项目文档关系、规范路径、代码位置或纯说明文本。

## 5. 字段内容/消费注册表

本节是 AI、Code 和 Web 共同消费字段语义的权威注册入口。注册表服务 `specs/00-LD-Vibe-Harness理念与纲要.md` 的 AI 第一原则：让 AI 快速定位字段语义、减少猜测、避免跨对象同义字段漂移，并让 Code/Web 从同一字段契约派生校验和呈现。

`id`、`type`、`title`、`status`、`created`、`updated` 等基础字段也应进入注册表，登记其通用语义和消费元数据；这些基础字段在具体工作模型中的取值规则、枚举值、必填性和状态条件，以 20-39 具体工作模型规范为准。05.01 只说明“字段若被具体工作模型采用，应按什么语义、内容格式和消费元数据理解”。

### 5.1 注册边界

字段注册表负责：

1. 登记字段名或重要嵌套字段路径；
2. 登记字段回答的问题和不得承载的内容；
3. 登记字段内容格式和稳定消费枚举；
4. 登记 Code 可机械消费的值形态、引用种类、枚举归属、schema 归属和可校验维度；
5. 登记 Web 可消费的派生视图语义，不规定组件名、页面布局或交互方案；
6. 登记废弃字段、别名字段、替代字段和迁移指向；
7. 暴露跨对象重复字段风险：同义字段应复用已有注册项，或在本文登记别名、废弃、替代或差异关系。

字段注册表不负责：

1. 具体工作模型是否采用该字段；
2. 具体工作模型字段是否必填；
3. 状态条件必填；
4. 状态机和合法状态流转；
5. 关闭条件；
6. 对象内完整 schema 和跨字段约束。

以上内容必须回到 20-39 具体工作模型规范。若字段注册与具体工作模型规范冲突，以具体工作模型规范的字段采用、必填性、状态条件和关闭条件为准；以本文的字段语义、内容格式和消费元数据为准。

Code / Web 消费元数据只表达字段契约如何被机器检查和人机界面理解，不规定具体实现文件、函数名、组件名、页面布局或交互方案。具体实现结构由 `specs/07-Code确定性执行实现规范.md`、`specs/08-Web信息同步实现规范.md` 和对应实现负责。

### 5.2 字段路径写法

字段路径使用点号表示重要嵌套字段：

```text
orchestration.execution_items.status
orchestration.review.specialist_review.required
```

数组元素不写 `[]`；注册项默认适用于该数组内每个对象。字段路径只用于登记内容/消费规则，不代表该路径在所有对象中存在。

### 5.3 注册枚举

注册表字段应使用稳定枚举，避免把自然语言描述当成机器契约。

| 注册列 | 允许值或写法 | 含义 |
|---|---|---|
| `field_path` | 字段名或点号路径 | 字段或重要嵌套字段路径 |
| `scope` | `common` / `workplan` / 具体工作模型名 | 注册项适用范围 |
| `format_kind` | `narrative` / `checklist` / `evidence` / `decision` / `reference` / `log` / `structured` | 本文 §3 定义的内容格式类型 |
| `value_shape` | `string` / `markdown` / `checklist_markdown` / `evidence_markdown` / `boolean` / `datetime` / `object` / `list_object` / `list_string` / `list_mixed` | Code 可判断的值形态 |
| `ref_kind` | `none` / `object_ref` / `workarea_ref` / `workplan_ref` / `commit_ref` / `doc_path` / `mixed_ref` / `local_id` / `enum` | 引用或标识类型 |

### 5.6 已清退工作对象边界

旧 `TaskPlan`、`Task` 和 `SubTask` 不再是当前 active 工作模型，也不再作为 Code 或 Web 的兼容读取、校验、迁移、直达展示或测试夹具维护对象。历史事实由 Git 历史、相关 Memo 或已迁移后的 WorkPlan 承载；当前事实源、Code 入口、Web 入口和注册表只面向 active 工作模型。

清退后的边界要求：

1. `ldvh-base/taskplans/`、`ldvh-base/tasks/` 和 `ldvh-base/subtasks/` 不得作为当前事实源目录存在；
2. `taskplan`、`task`、`subtask` 不得作为 CLI、Validator、Web API 或 Web 路由的对象类型；
3. `taskplans`、`related_taskplans`、`related_tasks`、`source_tasks`、`tasks`、`completion_evidence`、`deliverables`、`affected_docs` 等旧字段不得作为 active 对象字段扩展；
4. 需要表达执行拆分时使用 `WorkPlan.orchestration.execution_items`；需要表达关联关系时使用当前对象字段或文档/Git 引用；
5. 如果在历史文档、commit message 或研究材料中出现旧名称，Web 和 Code 不得把它们自动提升为当前对象入口。

## 6. Web 语义化渲染消费规则

Web 应消费 §5 注册表中的 `format_kind`、`ref_kind`、`web_render_kind`、`status` 和 `replacement`，从同一字段契约派生 Human-facing 视图。本文只定义字段到派生视图语义的契约，不规定具体组件名称、文件结构、页面布局或交互实现。Web 渲染是派生视图，不得回写事实源。

### 6.1 `web_render_kind` 枚举

| `web_render_kind` | 派生视图语义 | 必须保持的契约 |
|---|---|---|
| `summary` | 摘要或正文区域 | 按 Markdown 字段内容展示；不得把摘要派生结果回写为事实 |
| `checklist` | 检查清单区域 | 保留每项检查状态和完成比例语义 |
| `evidence` | 证据区域 | 突出验证命令、路径、结果、结论、关闭判断和 Human Gate 结果 |
| `object_ref` | 对象引用 | 仅对可识别对象 ID 执行对象跳转；不可识别引用按普通引用显示 |
| `doc_link` | 文档或路径引用 | 按文件路径、规范路径或 URL 引用显示 |
| `commit_ref` | Git 提交引用 | 作为 Git commit 引用显示，不得误当工作对象 ID |
| `mixed_ref` | 混合引用列表或混合引用值 | 分类型识别对象 ID、路径、URL、命令和说明性文本；不可识别项按普通引用显示，不得强行跳转 |
| `structured_area` | 结构化区域 | 结构化对象或列表不得裸渲染为普通 Markdown 文本 |
| `status_signal` | 状态信号 | 用于对象状态、优先级和内部执行状态等带进展或风险含义的稳定枚举展示 |
| `enum_signal` | 普通枚举信号 | 用于编排模式、类型等不直接表示进展或风险的稳定枚举展示 |
| `metadata` | 元信息 | 用于时间、布尔、局部 ID 等不构成正文的字段 |
| `deprecated` | 废弃字段提示 | 读取历史字段时应提示替代关系，不应鼓励新写入 |

`mixed_ref` 字段可以同时包含路径、对象 ID、URL、命令、Git 变更引用或说明性文本。Code 只应对可判定为项目内文件或目录路径的项做存在性检查；不可判定为路径的项应保留为普通混合引用，由 Web 按类型识别或降级展示。

### 6.2 Web 消费顺序

Web 视图应优先消费 `structured_area`、`checklist`、`evidence`、`object_ref`、`commit_ref`、`doc_link` 和 `mixed_ref` 等强语义字段，再消费 `summary`、`status_signal`、`enum_signal` 和 `metadata`。当同一字段同时具备引用和叙述含义时，以 `ref_kind` 决定是否可跳转，以 `web_render_kind` 决定展示语义。

`related_workplans` 必须作为 WorkPlan 对象引用消费；对象相关提交必须由 Git 历史和 `Refs:` 派生，不得依赖对象字段手写维护；`orchestration` 和 `orchestration.execution_items` 必须作为结构化区域消费；`success_criteria`、`verification_evidence` 和 `closure_evidence` 必须作为关闭审查核心信号消费。

### 6.3 Web 边界约束

1. Web 展示的事实以 Git 文件事实源为准；
2. 摘要、折叠、渐进展开只能是展示层派生结果，不得回写到 YAML；
3. YAML 原文折叠区作为事实完整性兜底展示；
4. Web 不得在 UI 中另建权威事实；
5. Web 对 `status=deprecated`、`status=removed` 或 `status=alias` 的旧对象和旧字段只能作为历史兼容视图消费；除受控迁移或历史详情直达外，不得进入主导航、Dashboard、默认关注队列或新建入口；
6. 如需长期保存 Web 生成的总结，应创建 Memo；除 `specs/08-Web信息同步实现规范.md` §8.2 明确白名单外，Web 不得更新其他对象字段。

## 7. Code 校验消费规则

Code 应消费 §5 注册表中的 `field_path`、`format_kind`、`value_shape`、`ref_kind`、`enum_owner`、`schema_owner`、`code_check_kind`、`status` 和 `replacement`。本文只定义可机械消费维度和字段契约，具体校验逻辑、文件位置、命令名称、测试组织和错误输出格式由 Code 实现规范与对应实现负责。

### 7.1 `code_check_kind` 枚举

| `code_check_kind` | 可机械消费维度 | 边界 |
|---|---|---|
| `none` | 不从本文派生校验 | 仍可由具体对象规范或实现自行校验 |
| `format` | 字段内容格式、YAML 块标量、Markdown/checklist/evidence 基础形态 | 不决定字段是否必填 |
| `ref` | 引用类型、引用前缀、路径或 commit 形态 | 引用存在性是否强制由具体对象规范或 Code 实现决定 |
| `enum` | 枚举值集合 | 枚举值以 `enum_owner` 指向的规范为准 |
| `structured` | object / list[object] 形态和已注册嵌套路径 | 不替代 `schema_owner` 定义的完整对象内 schema |
| `deprecated` | 废弃字段、别名、替代字段、迁移提示 | 不自动执行迁移，迁移策略由工作对象或流程承接 |
| `owner_state` | 状态条件必填、关闭条件、对象内跨字段约束 | 05.01 只登记字段可被消费；具体诊断级别归属对象规范和 Code 实现 |

### 7.2 Code 消费边界

1. Code 不应从 05.01 推导具体工作模型采用字段、必填性、状态机、关闭条件或对象内完整 schema；
2. Code 应使用 `schema_owner` 和 `enum_owner` 回到对应 20-39 具体工作模型规范读取完整约束；
3. Code 应将 `status=deprecated`、`status=removed` 和 `replacement` 作为兼容读取、迁移提示和新写入拦截的输入；
4. Code 对 `removed work model` 和 `deprecated alias` 的新建写入必须拦截；历史对象只保留读取、校验、迁移提示、受控清理和兼容展示能力；
5. Code 应优先让 Web 复用同一字段注册结果，避免 Code/Web 分别维护字段分类；
6. 当前 Markdown 注册表是权威规范表达；后续可派生或迁移为机器可读 YAML/JSON registry，但不得产生第二事实源。

## 8. AI 写入规则

AI 创建或更新工作对象时，应遵守以下写入规则：

### 8.1 长文本字段优先使用 YAML 块标量

注册表中 `value_shape=markdown`、`value_shape=checklist_markdown` 或 `value_shape=evidence_markdown` 的字段，如包含中文标点、英文冒号、换行、命令、列表式说明或超过一短句，应优先使用 YAML 块标量 `|`。

不得把包含冒号的长文本直接写成未加引号的普通单行字符串。

### 8.2 Checklist 字段必须使用检查列表格式

注册表中 `format_kind=checklist` 的字段必须使用 `- [ ]` 检查列表格式，将验收标准拆解为可独立验证的原子检查项。

### 8.3 验证证据字段应使用四段式结构

注册表中 `format_kind=evidence` 的字段应使用 `## 验证计划`、`## 验证命令`、`## 验证结果`、`## 结论` 四段式结构；可在对应段落中包含关键输出、关闭判断、残留风险或 Human Gate 结果。存量旧格式可兼容读取，但新增、重写和进入关闭审查的事实源不得继续写成无结构段落。

### 8.4 不自行添加未注册或未定义字段

AI 不得在工作对象中添加本文未注册、且对象规范未定义的字段。如需新增字段，应先在本文登记字段名或重要嵌套字段路径，再更新对应对象规范；字段是否被具体对象采用仍由 20-39 具体工作模型规范决定。

## 9. 事实源边界

1. 工作对象文件仍是权威事实源；多数对象为 YAML，Study 为 Markdown frontmatter。Git 提交记录不是工作对象字段，由 `specs/09.01-Git提交记录与变更追溯规范.md` 承接。Markdown 可以是字段内容格式，也可以按 Study 规范作为报告正文承载格式；
2. Web 渲染、摘要、折叠、预览都是派生视图，不得替代事实源；
3. 不引入外部 `.md` 正文文件作为工作对象内容引用机制；
4. 如未来需支持外部 Markdown 正文引用，应另建 ADR 决策，不得在本文中预设；
5. 格式类型（Narrative / Checklist / 验证证据 / Decision / Reference / Log / Structured）不是独立工作模型，不具备独立生命周期、状态机或关闭条件。

## 12. Human Gate 与检查要求

本文变更属于规范体系变更，应评估 Human Gate。以下变更需要 Human Gate：

1. 新增或删除内容格式类型；
2. 改变字段到内容格式的映射或字段注册元数据；
3. 改变 `code_check_kind`、`value_shape`、`ref_kind`、`enum_owner` 或 `schema_owner`；
4. 改变 `web_render_kind` 或 Web 派生视图语义；

6. 改变事实源边界声明。
