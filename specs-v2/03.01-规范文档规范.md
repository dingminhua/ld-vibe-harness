## 1. 本文定位

本文是 `specs-v2/` 规范文档工作区的应用剖面规范。`specs-v2/` 继承 `specs-v2/03-文档基础规范.md` 的文档工作区三分契约、命名、结构、引用和吸收规则；本文只规定 `<W>=specs-v2` 时的特有规则。

LDVH 自身规范工作区的三分映射如下：

```text
specs-v2/        LDVH v2 正式规范正文区
specs-v2/evals/  LDVH v2 内部评估和设计分析
specs-v2/refs/   LDVH v2 外部资料引用
```

旧 `specs/` 在 v2 重建期间作为迁移素材库。旧 `specs/` 中尚未迁入 `specs-v2/` 的内容，不自动构成 v2 权威规范。

---

## 2. specs-v2 正文区

### 2.1 正文区定位

`specs-v2/` 根目录正文区承载 LDVH v2 正式规范。正式规范可以定义稳定规则、对象边界、字段契约、状态机、工作流程、Human Gate、规范落地要求和检查要求。

正式规范正文区不得引用 `specs-v2/evals/`、`specs-v2/refs/`、旧 `specs/evals/` 或旧 `specs/refs/` 作为规范依据。evals、refs 或旧规范素材中的稳定规则必须吸收到 `specs-v2/` 正文区后才成为 v2 权威规则；长期决策可以进入 ADR；可执行工作或暂存发现可以进入 Task、Memo 等工作对象，但这些对象不因此成为规范规则。

所有 specs-v2 正式规范文档都应设置规范落地要求段落，用于说明该规范要落地需要满足哪些要求。目录说明、编号索引、迁移状态索引、evals、refs 和其他不直接定义稳定规范规则的说明性文档，不默认属于正式规范文档，不要求设置规范落地要求段落；若其中内容被升级为稳定规则，应吸收到对应正式规范后再声明规范落地要求。规范型集合索引按 `specs-v2/03.03-索引文档规范.md` 判断，若维护正式编号区段、集合状态、初始化输入或审计输入，应视为正式规范文档。

### 2.2 编号分区

specs-v2 正文区使用重建后的编号分区。编号分区、编号占用和新增编号判断由 `specs-v2/01-目录说明.md` 承接；旧 `specs/01-目录说明.md` 只作为迁移素材，不在 v2 中直接生效。

正式规范文档使用两位编号，文件名格式使用“NN-标题”加 `.md` 后缀。子文档使用“NN.SS-标题”加 `.md` 后缀。旧机制文件和结构化契约文件沿用既有编号时，必须遵守本文 §6。

### 2.3 正式规范文档骨架

正式规范文档建议采用以下骨架：

```markdown
# {规范标题}

> 创建日期：YYYY-MM-DD
> 定位：...
> 适用范围：...
> 上位依据：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---
## 1. 本文解决的问题

## 2. 与 00 总纲的关系

## 3～N-2. 核心规则

## N-2. 规范落地要求

## N-1. Human Gate 与检查要求

## N. 待补齐事项
```

工作模型、工作流程和其他专项规范的专用骨架待迁入 v2 后定义。迁入前，旧 `specs/07-工作模型基础规范.md`、`specs/08-工作流程基础规范.md` 等只作为迁移素材，不直接约束 v2 正式规范。00 总纲作为顶层文档，可不声明上位依据。

正式规范文档不得设置“本文不做什么”“边界说明”等反向边界章节。职责边界应通过定位、适用范围、上位依据、相关规范和正文正向规则表达。

## 3. specs-v2/evals

`specs-v2/evals/` 继承 `specs-v2/03-文档基础规范.md` §3.4 和 §3.6 的 evals 与吸收规则。本文只规定 `<W>=specs-v2` 时的特例。

specs-v2/evals 文档特例：

1. `specs-v2/evals/` 承载 LDVH v2 内部评估、设计探索、方案比较、外部项目借鉴分析和项目内部临时参考；
2. specs-v2/evals 可以引用 specs-v2 正文区作为评估依据和上位规范；
3. 稳定规范规则必须吸收到 specs-v2 正文区后，才能被正式规范文档作为规则消费；
4. 长期决策可以吸收到 ADR，可执行工作或暂存发现可以吸收到 Task、Memo 等工作对象，但不得被正式规范直接当成规则引用；
5. specs-v2/evals 不需要 Human Gate 与检查要求章节。

> 执行效力：无；规范规则需进入 specs-v2 正文区，决策或工作事实需进入对应工作对象后才生效
> 上位依据：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：...（可选）

---

## 6. 旧机制文件与结构化契约

### 6.1 固定机制子文档取消

LDVH 不再要求每个工作模型或工作流程默认拆分固定 `NN.01` 至 `NN.06` 机制子文档。历史上存在的 Rules、Skill、Agent、Tools、Web、Contract 文件只作为迁移前过渡资料或遗留契约保留。

新增或稳定后的机制内容应按机制归属进入 v2 对应权威位置。相关权威位置尚未迁入 v2 时，应进入待迁移事项，不得直接引用旧 `specs/` 作为 v2 权威：

1. 主规范规范落地要求；
2. 04 系列环境适配相关规范；
3. 工作流程基础规范；
4. `specs-v2/14-Code实现规范.md`；
5. Web 信息同步规范；
6. 运行 Rules / Skill 实体、Agent 定义摘要或契约能力。

### 6.2 旧机制文件

旧机制文件不是独立规范，也不是工作模型或工作流程完整性的默认要求。旧机制文件只能说明对应模型或流程在某个机制下曾如何实践，不得重新定义主模型、主流程、字段契约、状态机、Context、Scenario、Gate、事实源边界或 Human Gate。

旧机制文件的迁移、保留和删除规则待 v2 工作模型、工作流程和 04 系列环境适配相关规范继续稳定后定义。迁入前，旧机制文件只作为迁移素材，不构成 v2 子文档机制要求。

### 6.3 结构化契约

结构化契约可以作为字段契约、schema、接口契约或机器消费契约存在，但不构成固定 `NN.06` 子文档要求。新增或稳定后的契约优先回并到 v2 主规范契约章节，或由 Code 和 Web 实现消费主规范契约。对应主规范尚未迁入 v2 时，应记录为待迁移事项。

## 7. 规范落地要求与环境适配

v2 将规范到运行环境的同步拆成两层：

1. **规范落地要求**：说明某段稳定规范要落地，需要满足哪些要求，例如入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求、生命周期触发要求等；
2. **环境适配映射**：说明某类规范落地要求在 Trae、Codex、Claude Code、Cursor 或其他开发环境中，通过哪些机制、文件、配置、工具、入口或降级策略满足。

规范落地与环境适配的父规范入口是 `specs-v2/04-规范落地与环境适配基础规范.md`。正式规范只声明规范落地要求和保障机制；环境适配映射、运行投影、环境能力承接边界、LDVH 环境适配特别要求和个人环境适配特别要求，应分别按 04 系列对应子文档处理。

规范落地要求不是普通引用、文档重要性声明或上位依据声明。规范落地要求的类型、字段、保障机制和“不得直接把具体环境实体写成要求本身”的规则，以 `specs-v2/04.01-规范落地要求规范.md` 为权威；本文只要求 specs-v2 正式规范在创建、修改或审计时回到 04.01 检查该段落。

若某项规则要求在特定时机稳定触发，应声明生命周期触发要求，并由环境适配映射决定该环境使用 Hook、CI、自动运行、规则条件、Skill 组合或降级检查实现。具体环境实体不得直接写入普通规范落地要求表，除非该文档本身就是环境适配映射文档。

旧文档中的“机制落地关系”或“机制承接关系”进入 v2 时，应按 `specs-v2/02-术语规范.md` 的旧称处理，先拆解为规范落地要求和环境适配映射两层。无法确认环境实体的内容，只能先迁入规范落地要求或待迁移事项。

## 8. Specs-v2 修改执行顺序

AI 新增、修改或审计 specs-v2 正式规范文档时，应按以下顺序执行：

1. 根据任务场景确定基础入口：术语边界、旧称处理或术语变更治理读取 `specs-v2/02-术语规范.md`；文档工作区、命名、引用、evals/refs 或子文档边界读取 `specs-v2/03-文档基础规范.md`；specs-v2 正式规范、规范落地要求或旧机制文件读取本文；规范型集合索引读取 `specs-v2/03.03-索引文档规范.md`；规范落地、环境适配、环境能力承接、LDVH 特别要求或个人环境特别要求读取 `specs-v2/04-规范落地与环境适配基础规范.md`；
2. 判断拟修改内容属于哪个规范权威领域；
3. 读取目标规范及其 v2 上位依据、相关规范；目标主题尚未迁入 v2 时，读取旧 `specs/` 作为迁移素材；
4. 按需读取 00 中与本次变更相关的产品定位、五类构成要素、价值实现标准、运行闭环标准和 Human Gate 要求；
5. 判断变更是否符合 00 上位原则，是否弱化事实源边界、Human Gate、验证纪律或五类构成要素分工；
6. 若涉及高影响变更，触发 Human Gate；
7. 修改目标规范；
8. 按 `specs-v2/04.01-规范落地要求规范.md` 检查目标规范的规范落地要求段落，确认每项落地要求均声明要求内容、保障机制、同步类型和触发条件；
9. 判断文档结构、引用、迁移边界和规范落地要求检查是否已有适配工具；
10. 若检查 Code 实现缺失或旧实现假设与 specs-v2 冲突，按 `specs-v2/03-文档基础规范.md` §9.1 形成文档检查 Code 缺口，并按 `specs-v2/14-Code实现规范.md` 完成 Code 需求准入、最小实现和测试验证；
11. 运行适配后的文档结构校验、引用校验和规范落地要求校验；
12. 检查是否需要更新规范落地要求；
13. 若变更影响运行投影，按 `specs-v2/04.02-环境适配与运行投影规范.md` 检查是否存在对应环境适配映射；不存在时记录为待迁移事项；
14. 若变更需要登记环境适配映射或运行投影，继续按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 检查；
15. 若变更涉及环境能力承接判断、工具缺口、LDVH 环境适配特别要求或个人环境适配特别要求，继续按 `specs-v2/04.04-环境能力承接边界.md`、`specs-v2/04.05-LDVH环境适配特别要求.md` 或 `specs-v2/04.06-个人环境适配特别要求.md` 检查；
16. 若变更涉及当前环境运行投影，继续按 `specs-v2/04.03-环境适配映射与运行投影记录模板.md` 检查项目根目录的 `LDVH-ENVIRONMENT-INITIALIZATION.md` 是否存在、是否中文可读、是否已适配当前项目、当前开发平台、权限边界和 Human 授权状态；文件不存在或未适配时应持续提醒用户先创建、确认或改写，不得继续创建持久运行投影。

## 9. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | specs-v2 编辑入口摘要 | 规范文档入口摘要、正式规范骨架、相关规范引用 | AI 执行入口提示 | 本文的正式规范文档骨架、specs-v2/evals、specs-v2/refs、子文档、旧机制文件或规范落地要求变化时 |

| 生命周期触发要求 | specs-v2 变更后的文档检查触发 | `specs-v2/04.02-环境适配与运行投影规范.md`、环境触发映射、CI、Skill 流程或人工降级检查 | 触发保障 | 正式规范发生新增、重命名、结构变化、引用变化或规范落地要求变化时 |

## 10. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 重命名或重排 specs-v2 正式规范文档；
2. 改变 specs-v2 正文区、specs-v2/evals 或 specs-v2/refs 的引用方向规则；
3. 将 specs-v2/evals、specs-v2/refs 或旧 `specs/` 迁移素材结论直接作为强制规则使用；
4. 新增、删除或重命名应用剖面或专题子文档；
5. 恢复或新增固定机制子文档结构；
6. 改变规范落地要求或环境适配映射规则，或新增、修改、删除会影响运行投影同步检查、产品初始化、审计或规则漂移诊断的规范落地要求；
7. 旧机制文件新增或扩张基础规范；
8. 新增、替换或扩大 specs-v2 文档检查 Code 实现的判定范围。

规范文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 上位依据 | 正式规范文档已声明上位依据，00 除外 |
| 编号分区 | 文档编号符合 specs-v2 当前编号分区，或已记录为待迁移事项 |
| 文档结构 | 文档骨架符合正式规范、工作模型、工作流程、evals、refs 或应用剖面要求 |
| 子文档边界 | 子文档只定义应用剖面特例或专题细则，未复制父规范通用规则 |
| 旧机制文件 | 未恢复固定机制子文档结构 |
| 引用方向 | specs-v2 正文区未引用 evals、refs 或旧 specs 作为规范依据 |
