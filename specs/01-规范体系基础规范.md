## 1. 读者和使用方式

本文首先写给正在编写或迁移 spec 的 AI，其次写给解析 spec 的 Code，最后写给审核规范质量的 Human。

AI 读本文后，应能完成三件事：

1. 判断一篇 v3 spec 应该写什么、不写什么；
2. 把父层通用规则和子规范本地 delta 分开；
3. 让 Code 能从 Markdown 中生成 Action Guide。

Code 读本文后，应能定位身份块、章节角色、附件关系、去冗余分类和 source refs。

Human 读本文后，应能判断 AI 是否把 spec 写厚了、写散了，或写成第二事实源。

## 2. 写作顺序

AI 新建或迁移 v3 spec 时，按以下顺序执行：

| 顺序 | 动作 | 产物 |
|---|---|---|
| 1 | 读 00，确认工作通过价值门 | 可说明减少哪类 AI 负担 |
| 2 | 确认父规范 | `parent_spec` 和上位依据 |
| 3 | 写 identity block | `v3_spec` 可被 Code 解析 |
| 4 | 写本地问题 | 说明本 spec 独有问题 |
| 5 | 写本地 delta | 只写父层没有覆盖的规则 |
| 6 | 写 Code / Action Guide 消费边界 | 说明可生成哪些导航要素 |
| 7 | 写 Human Gate 和待补齐事项 | 形成 stop_conditions 和 next_queries |
| 8 | 跑 Code 校验或记录缺口 | 形成可复查证据 |

不得先复制 v2 长正文，再事后尝试删减。

## 3. Markdown 是规范事实源

v3 spec 正文必须是 Markdown。Markdown 同时服务 Human 可读、AI 可行动和 Code 可解析。

允许的机器层：

| 层级 | 位置 | 作用 |
|---|---|---|
| identity block | Markdown fenced YAML | 让 Code 识别身份、状态、父子关系和消费类别 |
| 附件表 | `specs/attachments/*.md` | 定义字段、闭集、章节角色和判定表 |
| schema | `specs/schemas/*.yaml` | 校验 Code 输入输出结构 |
| generated output | stdout、临时文件或测试输出 | 诊断和 Action Guide，不是事实源 |

不允许为普通 spec 建立长期人工 YAML 孪生文件。

## 4. 正文写什么

每篇 spec 正文只写四类内容：

| 内容 | 说明 |
|---|---|
| 本地问题 | 这篇 spec 独自解决什么 AI 行动问题 |
| 本地规则 | 父规范没有覆盖的 delta、例外或更严格要求 |
| 本地停止条件 | 本 spec 特有 Human Gate、阻塞和分流条件 |
| 本地消费边界 | Code、Action Guide 或下游规范如何消费它 |

正文不得重复大段父层 doctrine。需要继承父层时，写来源和差异，不复制全文。

## 5. 正文不写什么

以下内容不进入普通 spec 正文：

1. 全量目录登记；
2. 全量关系图；
3. 可由 Code 生成的检查清单；
4. 可由 Action Guide 当次生成的读取路线；
5. 与本 spec 无关的通用 Human Gate doctrine；
6. 与本 spec 无关的通用事实源 doctrine；
7. 过程讨论、扫描日志、迁移草稿和一次性对照。

这些内容需要时进入 Code 输出、`_migration/`、WorkCase、Spark 或对应事实源。

## 6. 附件怎么写

附件只写 Code 和 AI 行动需要反复使用的稳定契约。

01 只保留四类附件：

| 附件 | 给谁用 | 为什么存在 |
|---|---|---|
| `01.Att.01-规范身份字段表.md` | Code | 解析 `v3_spec` |
| `01.Att.02-规范章节角色表.md` | AI + Code | 把不同标题映射到行动角色 |
| `01.Att.03-行动指南关系类型表.md` | Code | 输出稳定 relationships |
| `01.Att.04-去冗余判定表.md` | AI + Human | 判断重复内容如何处理 |

不能说明 Code 消费、AI 行动价值或 Human 审核价值的附件，不进入 01。

## 7. 父子规则

父规范写通用规则，子规范写本地 delta。

AI 判断一段重复文本时，按以下顺序分类：

| 判断 | 处理 |
|---|---|
| 多个子规范都重复，且不依赖本地场景 | 上收到父规范 |
| 是本地 Human Gate、事实源边界或执行差异 | 留在子规范 |
| 是 Code 可机械检查的要求 | 转为 schema、validator 或 diagnostics |
| 是读取路线、停止提醒或下一步查询 | 由 Action Guide 生成 |
| 是迁移过程证据 | 留在 `_migration/` |

分类闭集见 `specs/attachments/01.Att.04-去冗余判定表.md`。

## 8. Action Guide 输入责任

一篇 spec 至少应让 Code 生成以下导航要素：

| Action Guide 要素 | Markdown 来源 |
|---|---|
| relationships | `parent_spec`、`basis`、`related_specs`、附件引用 |
| read_plan | 上位依据、章节角色、附件角色、本地规则 |
| impact_judgment | 构成要素归属、消费类别、相关规范 |
| stop_conditions | Human Gate、禁止项、状态、待澄清项 |
| next_queries | 待补齐事项、缺失引用、未确认迁移项 |
| verification | Code 消费类别、schema、测试或等价验证 |
| source_refs | canonical path、父规范、附件和来源文件 |

如果 Code 无法生成这些要素，应输出诊断，不得猜测补全。

## 9. Stop Conditions

AI 必须暂停：

1. 准备手写全量目录、全量图谱或全量检查清单；
2. 准备删除本地 Human Gate、事实源边界或行动特有 delta；
3. 准备用 YAML 孪生文件替代 Markdown 正文；
4. 准备让附件定义父规范没有授权的新规则；
5. 准备让 Code 或 Action Guide 输出授权语义；
6. 准备顺手修改 Runtime、hook、dispatcher、rules、skills 或 Web。

## 10. 下一步读取

AI 读完本文后：

1. 要写 identity block，读 `01.Att.01`；
2. 要判断章节是否足够，读 `01.Att.02`；
3. 要生成或审查 Action Guide 关系，读 `01.Att.03`；
4. 要去冗余，读 `01.Att.04`；
5. 要实现 Code，等待 04 或 Code 契约成立。
