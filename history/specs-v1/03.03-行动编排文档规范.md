## 1. 本文解决的问题

本文解决具体行动编排规范文档应如何书写的问题，包括文档骨架、成员自描述契约、Context、Scenario、Gate、执行流程、回写证据、环境适配边界、行动特有可测试性锚点和检查要求。

本文只规定行动编排规范文档的写作方式。行动编排的定义、准入、通用规则、主控调度和回写原则由 `specs/06-行动编排基础规范.md` 定义。

---
## 2. 与 00 和 06 的关系

00 定义行动编排是 LDVH 五类构成要素之一，并要求形成可读取、可执行、可验证、可回写的运行闭环。06 定义行动编排基础规则。行动编排测试机制是否存在 active 入口，应查询 30-59 成员主文件自描述和 Code 派生行动编排集合索引。

本文承接 03 的文档治理规则和 06 的流程组成要求，规定已生效的具体行动编排规范如何把行动规则和行动特有可测试性锚点写入同一主文档。具体测试用例、预期行为矩阵、失败诊断和回归用例不由本文定义统一事实源；每个流程不另设测试子文档。跨构成要素的测试治理、验证声明和测试证据边界由 `specs/11-测试基础规范.md` 承载。

---
## 3. 适用文件

30-59 是具体行动编排规范区段，均按本文编写。行动编排集合不再通过独立手写集合索引文档维护成员清单；每个具体行动编排主文件通过 `ldvh_doc` 声明文档级身份、定位、适用范围和上位引用，通过文件名编号和 `ldvh_member` 成员自描述字段声明自身集合事实，Code 依据这些字段生成派生集合索引。

只有 `collection_status: active`、主文件存在、骨架检查通过且必需锚点完整的行动编排，才能被 AI 当作已生效流程执行。planned、candidate、reserved、removed 或其他非 active 状态只能作为讨论输入、计划、保留或历史信息，不得作为具体行动编排规范执行。

具体行动编排规范文件名采用：

```text
NN-{英文名}-{中文名}.md
```

文件名不得重复“行动编排规范”字样。

具体行动编排主文件的编号、文件名编号、标题编号和成员自描述 `spec_id` 必须一致。编号冲突、编号越界、文件缺失、状态非法、必需锚点缺失或自描述字段缺失时，Code 必须报告诊断；AI 不得把存在诊断错误的派生集合索引作为执行依据。

## 4. 成员自描述契约

具体行动编排主文件必须在 `ldvh_doc` 之后、正文第一章之前提供机器可读成员自描述块。成员自描述块用于 Code 生成派生行动编排集合索引、active 流程清单、冲突诊断和 AI Context Pack；它是成员主文件的一部分，不是派生索引。

`ldvh_doc` 与 `ldvh_member` 成员自描述契约分工如下：

1. `ldvh_doc` 承载文档级事实，包括 `doc_id`、`doc_kind=work_process_spec`、标题、文档治理状态、规范路径、定位、适用范围、上位依据、相关规范和文档级 Code 消费入口；
2. 文件名承载编号事实，`ldvh_doc.doc_id`、`ldvh_member.spec_id` 必须与文件名编号一致；
3. `ldvh_member.kind` 承载 `work_process` 成员类型；
4. `ldvh_member.collection_status` 承载集合治理状态和 active 判定输入，不与 `ldvh_doc.status` 混用；
5. `ldvh_member.canonical_path` 必须与 `ldvh_doc.canonical_path` 一致；
6. `ldvh_member` 各类 Context、Scenario、Gate、执行、回写、证据、可测试性 anchor 承载行动编排集合成员的 Code 消费锚点；
7. specs 根目录普通头部不得重复登记 `ldvh_doc` 或 `ldvh_member` 已承载的任何文档元信息、集合成员事实或等价字段。

成员自描述块必须使用 YAML 代码块，字段至少包括：

| 字段 | 含义 | 要求 |
|---|---|---|
| `spec_id` | specs 编号 | 必填，必须为 30-59 内两位编号，并与文件名一致 |
| `kind` | 成员类型 | 必填，固定为 `work_process` |
| `name_en` | 英文名 | 必填，与文件名英文段保持一致 |
| `name_zh` | 中文名 | 必填，与文件名中文段保持一致 |
| `collection_status` | 集合状态 | 必填；取值为 `active`、`planned`、`candidate`、`reserved`、`removed`；状态语义由 06 和本文约束 |
| `canonical_path` | 主文件路径 | 必填，指向当前文件 |
| `scenario_anchor` | Scenario 章节锚点 | active 流程必填 |
| `context_anchor` | Context 章节锚点 | active 流程必填 |
| `gate_anchor` | Gate 章节锚点 | active 流程必填 |
| `execution_anchor` | 执行流程章节锚点 | active 流程必填 |
| `writeback_anchor` | 回写章节锚点 | active 流程必填 |
| `evidence_anchor` | 证据章节锚点 | active 流程必填 |
| `testability_anchor` | 行动特有可测试性锚点 | active 流程必填 |
| `code_consumption` | Code 消费说明 | 必填，列出 Code 应读取的字段、章节或校验入口 |
| `assurance_takeover` | 接管的保障要求来源 | 可选；当行动编排接管正式规范保障要求时填写，使用列表，每项必须包含 `source_spec=`、`requirement=` 和 `scope=` |
| `capability_assets` | 能力资产映射索引 | 可选；当行动编排声明需要固定 Rules、Skill、Agent、Hook 或其他能力资产保障时填写，使用列表，每项应包含 `type=`、`path=`、`purpose=` 和 `status=` |
| `supersedes` / `superseded_by` | 替代关系 | 可选，用于重命名、迁移或废弃后的追溯 |

示例：

```yaml
ldvh_member:
  spec_id: "40"
  kind: work_process
  name_en: example-workflow
  name_zh: 示例行动编排
  collection_status: candidate
  canonical_path: specs/40-example-workflow-示例行动编排.md
  scenario_anchor: "{Scenario 章节锚点}"
  context_anchor: "{Context 章节锚点}"
  gate_anchor: "{Gate 章节锚点}"
  execution_anchor: "{执行流程章节锚点}"
  writeback_anchor: "{回写章节锚点}"
  evidence_anchor: "{证据章节锚点}"
  testability_anchor: "{行动特有可测试性章节锚点}"
  code_consumption:
    - scenario
    - gates
    - writeback
```

成员自描述中的集合状态只描述该规范成员在 30-59 区段中的治理状态，不承载项目运行状态、检查过程状态或流程执行实例。Code 派生输出必须回指成员主文件，不得把派生索引作为最终事实源。

`assurance_takeover` 只登记行动编排接管关系的最小机器可读索引，不替代正文接管说明。每一项应采用紧凑字符串格式：

```text
source_spec=specs/NN-xxx.md; requirement=保障要求名称或锚点; scope=接管范围摘要
```

正文仍必须按本文 §7 说明执行责任、验证责任、证据位置、Human Gate 条件和失败降级方式。Code 派生集合索引可以暴露 `assurance_takeover` 供导航、报告和后续重复接管诊断使用，但派生输出不得替代来源规范或行动编排正文。

`capability_assets` 只登记行动编排与能力资产的最小机器可读映射，不替代能力资产自身的 `ldvh_asset` 元信息，也不声明环境已经部署或启用该资产。每一项应采用紧凑字符串格式：

```text
type=skill|agent|hook|rule|code|web|ci|command|environment; path=相对路径或能力标识; purpose=保障目的摘要; status=required|optional|degraded|planned
```

正文仍必须按本文 §7 说明能力参与的输入、输出、停止点、交还方式、验证命令、降级方式和同步触发。固定 Rules、Skill、Agent 或 Hook 资产的权威登记仍由对应资产文件的 `ldvh_asset` 元信息承载；Code、Web、CI、命令入口和环境适配的权威位置分别回到 07、08、04.03、实现目录或适配措施。行动编排登记的是“本流程需要哪些能力保障及其当前映射”，不是能力资产正文、部署状态或第二事实源。

## 6. 行动特有可测试性锚点

具体行动编排规范必须包含行动特有可测试性锚点，用于说明该流程哪些关键行为需要能被验证。行动特有可测试性锚点至少覆盖：

1. 正向场景：满足 Scenario 时应进入流程；
2. 负向场景：不满足 Scenario 时不得进入流程；
3. Gate 场景：应暂停、确认或降级的条件；
4. 回写场景：稳定事实应写入哪里；涉及工作对象创建、更新或状态流转时，应说明目标对象的准入条件、父级关系、字段契约、状态机和对象级 Human Gate 如何被校验；
5. 失败降级：缺少上下文、工具失败、权限不足或 Human Gate 未确认时如何停止；
6. 回归风险：修改该流程后应重新检查哪些已有行为。

这些锚点是行动编排设计的一部分，不承载具体测试用例、预期行为矩阵、失败诊断或回归用例，也不替代成员自描述和 Code 派生集合索引中的 active 流程判定。

## 7. 能力保障与环境适配边界表达

具体行动编排规范可以说明 Rules / Instructions、Skill、Agent、Code、Web、Hook 或 CI 如何参与，但不得把适配措施正文、Skill 全文、Agent 完整提示词、Code 实现说明或 Web 设计稿搬入流程规范。

环境适配边界应回答：

1. 是否需要某类能力参与；
2. 能力参与的输入、输出、停止点和交还方式；
3. 不能由该能力承接的内容；
4. 当前能力缺口和降级方式；
5. 需要同步检查的 Code、Web、适配措施或环境适配项。

具体行动编排是能力保障需求和能力资产映射的登记位置。任何正式规范提出的保障要求，如果需要 Rules、Skill、Agent、Hook、Code、Web、CI、命令入口或环境适配来稳定执行，应由接管该要求的行动编排说明需要哪些能力、为什么需要、当前是否已有资产、资产权威路径、验证方式、缺口和降级方式。正式规范可以声明保障要求和能力类型边界，但不应维护具体能力资产清单、部署状态、执行步骤或资产正文。

当能力资产已存在时，行动编排应在正文或 `capability_assets` 中登记映射，并检查资产自身 `ldvh_asset` 元信息是否回指来源规范或行动编排。当能力资产尚不存在时，行动编排应推动创建、修改、登记、验证或明确降级，并按 06 的能力保障闭环责任记录残留风险。行动编排不得以“后续需要 Skill / Hook / Code / Web”等悬空描述替代能力闭环。

同一行动编排可以登记多个能力资产，同一能力资产也可以映射多个行动编排。映射关系只说明能力如何保障流程，不改变行动编排作为流程事实源、能力资产作为执行保障外壳、环境部署作为适配层的分层关系。

当具体行动编排接管正式规范中的保障要求时，主文件必须写清接管关系。接管说明至少包含：来源规范、被接管的保障要求名称或锚点、接管范围、执行责任、验证责任、证据位置、Human Gate 条件、失败降级方式，以及接管关系变化时需要同步检查的规范、能力资产或 Code/Web 实现。

行动编排接管保障要求后，来源规范只保留来源声明和接管引用；具体执行步骤、检查清单、证据闭环、缺口分流和关闭判断由接管行动编排维护。具体行动编排不得同时要求来源规范继续维护同一保障要求的执行细节，也不得把 Skill、Agent、Hook、Code、Web 或 CI 的输出直接写成该要求的最终完成事实。

## 8. 规范保障要求

本文通过以下规范保障要求说明相关要求的同步、检查或审计触发条件。

| 保障要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 具体行动编排规范文档应按 06 的标准组成、03.01 的 `ldvh_doc`、本文骨架和成员自描述契约编写 | 03.01、本文、06、Human Gate | 文档治理 | 新增、修改、重命名或审计 30-59 行动编排规范时 |
| 工作流程接管要求 | 具体行动编排接管正式规范保障要求时，应在主文件和必要的成员自描述中声明来源、范围、执行责任、验证责任、证据位置、Human Gate 和失败降级；来源规范不得并行维护同一要求的执行细节 | 04.01、06、具体行动编排主文件、成员自描述、Code 派生集合索引 | 行动编排治理 | 行动编排接管、取消接管或改变正式规范保障要求时 |
| 工作流程接管要求 | 具体行动编排需要能力保障时，应在主文件登记能力需求、资产映射、验证方式、缺口和降级方式；正式规范不维护具体能力资产清单、部署状态、执行步骤或资产正文 | 06、04.02、04.03、具体行动编排主文件、能力资产元信息、Code/Web/Hook/Skill 校验 | 行动编排治理 | 行动编排声明能力需求、资产映射变化、能力资产新增/降级/删除或环境适配边界变化时 |
| 确定性执行要求 | Code 应能检查具体行动编排规范是否覆盖 `ldvh_doc`、成员自描述、必要章节和行动特有可测试性锚点，并生成派生行动编排集合索引 | `code/spec_checks/index.py`、正反样例 | 校验实现 | 行动编排文档骨架、文档元信息、成员自描述字段、可测试性锚点或检查项变化时 |
| 生命周期触发要求 | 具体行动编排规范变化后，应检查文档元信息、成员自描述、Code 和 Web 是否需要同步；行动编排测试机制是否存在 active 入口应查询 Code 派生集合索引和 30-59 成员主文件自描述 | `ldvh_doc` 校验、成员自描述校验、Code 派生索引、联动检查、人工降级检查 | 触发保障 | Context、Scenario、Gate、执行流程、回写要求、文档元信息、成员自描述或环境适配边界变化时 |

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变具体行动编排规范的标准骨架；
2. 允许具体行动编排规范省略标准组成且无说明；
3. 将行动编排测试用例分散到每个流程的测试子文档；
4. 改变 Context、Scenario、Gate、回写要求或行动特有可测试性锚点的表达方式；
5. 改变成员自描述字段、集合状态语义、active 判定条件或 Code 派生集合索引消费方式。

行动编排文档检查至少包括：

| 检查项 | 标准 |
|---|---|
| 骨架 | 覆盖本文 §5 标准章节，缺项已说明 |
| 上位依据 | 上位依据指向 06，相关规范按内容引用 02、03、09、07、08；若后续存在 active 的行动编排测试规范或 30-59 成员自描述声明的 active 流程测试入口，再按需引用 |
| 成员自描述 | 自描述字段完整，编号、文件名、路径、集合状态、active 判定和锚点可被 Code 校验 |
