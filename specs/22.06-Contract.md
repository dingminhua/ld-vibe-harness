## 1. 本文定位

本文定义 Change 工作模型使用的 commit message 格式契约。本文解决 commit message 应包含哪些部分、各部分格式约束是什么、type 和 scope 枚举有哪些，以及工具实现应如何消费本契约的问题。

本文是 Change 工作模型契约字段的权威位置。本文是 `specs/22-Change-变更记录.md` 的附件型契约子文档，不是独立工作模型。本文不得重新定义 Change 的对象定位、准入条件、状态机、Human Gate、事实源回写或证据留存要求。发生冲突时，以 22 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款。

## 2. Commit Message 格式 Schema

### 2.1 格式结构

```text
<type>(<scope>): <subject>

<body>

Refs: <object-refs>
```

### 2.2 各部分说明

| 部分 | 必填 | 说明 |
|---|---|---|
| `type` | 是 | 变更类型，必须属于 type 枚举 |
| `scope` | 否 | 影响范围，推荐值见 scope 枚举 |
| `subject` | 是 | 简短描述，不超过 72 字符 |
| `body` | 否 | 详细说明变更原因和内容 |
| `Refs` | 否 | 关联对象，格式为 `Refs: <object-refs>`，多个对象用逗号分隔 |

### 2.3 格式正则

第一行格式正则：

```regex
^([a-z]+)(?:\(([^)]+)\))?:\s+(.+)$
```

Refs 行格式正则：

```regex
^Refs:\s*(.+)$
```

## 3. 字段约束

### 3.1 type 枚举

| type | 含义 |
|---|---|
| `feat` | 新增功能或对象 |
| `fix` | 修复缺陷 |
| `docs` | 文档修改 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 测试相关 |
| `chore` | 构建、配置或辅助工具修改 |
| `spec` | specs 规范文档修改 |
| `rule` | Rules 文件修改 |
| `adr` | ADR 实例创建或状态变更 |
| `revert` | 回退之前的变更 |

### 3.2 scope 枚举（推荐值，非强制）

| scope | 含义 |
|---|---|
| `specs` | specs 规范文档 |
| `rules` | Rules 文件 |
| `adr` | ADR 实例 |
| `tools` | Tools 辅助程序 |
| `web` | Web Tools |
| `evals` | evals 评估与调研文档 |
| `refs` | refs 参考文档 |

### 3.3 subject 约束

| 约束 | 值 |
|---|---|
| 最大长度 | 72 字符 |
| 不可为空 | 是 |

### 3.4 Refs 约束

| 约束 | 值 |
|---|---|
| 格式 | `Refs: <object-refs>` |
| 分隔符 | 逗号 |
| 不可为空 | Refs 行存在时，object-refs 不可为空 |

## 4. 契约消费声明

### 4.1 对象接口摘要

| 项 | 契约 |
|---|---|
| 对象类型 | `change` |
| 最终事实源 | Git commit 历史 |
| YAML 实例状态 | 当前项目已取消 `ldvh-base/changes/` YAML 作为生产事实源，仅保留历史迁移说明 |
| 文件命名 | 不适用 |
| 默认状态 | 不适用 |
| 终态 | Git commit 一经形成即作为不可变历史事实处理 |
| 主要读取场景 | commit 前格式预检、历史 commit 审计、准入变更追溯、Task closure_evidence 引用 |
| 主要写入场景 | 通过 Git commit 写入最终事实源，不由 Change Tools 执行写入 |

### 4.2 Raw Object 接口

Change 当前 Raw Object 接口以 commit message 为结构化载体，由本文 §2 和 §3 定义，包含：

1. 第一行结构：`<type>(<scope>): <subject>`；
2. 可选 body：说明变更原因和内容；
3. 可选 Refs 行：`Refs: <object-refs>`；
4. type 枚举：本文 §3.1；
5. scope 推荐枚举：本文 §3.2；
6. subject 长度、Refs 格式和中文字符检测规则。

如后续重新引入 Change YAML 实例，必须先更新本文补充 YAML schema，再同步更新消费工具和测试。

### 4.3 引用关系接口

| 引用位置 | 目标对象 | 必填 | 校验要求 |
|---|---|---|---|
| `Refs` 行 | Intent、Task、ADR、Pitfall、Memo、Profile 或 specs 文档引用 | 否 | Refs 行存在时内容不可为空，多个引用用逗号分隔 |
| Task `related_changes` | Change / commit 引用 | 否 | 引用无效时标记为校验警告 |
| closure_evidence | commit 或命令输出引用 | 否 | 应能追溯到 Git 历史或命令输出 |

Change 与其他对象的关系以 Git commit 历史和对象字段引用共同承载；Tools 输出不作为独立 Change 事实源。

### 4.4 消费者接口

| 消费者 | 消费方式 | 消费内容 | 测试或验证入口 | 同步触发 |
|---|---|---|---|---|
| `tools/check_22_commit_format.py` | 校验 | type 枚举、scope 推荐值、subject 长度、Refs 格式、中文字符检测 | `python3 -m pytest tests/tools/test_check_22_commit_format.py` | 本文格式结构、枚举、Refs 规则或中文字符检测变化时 |
| `ldvh-commit` Skill | 提交编排 | commit message 结构、预检命令、Refs 引用、准入变更提交纪律 | Skill 流程审查与实际 commit 演练 | commit 格式、准入变更或预检制度变化时 |
| L0/L1 Rules | 运行时提醒 | 准入变更后立即调用提交流程、commit message 格式和预检要求 | Rules 读取与提交纪律检查 | 提交纪律或 Change 契约变化时 |
| AI | 遵守 | 生成中文 commit message，提交前执行预检，不自动 push/tag/release | `tools/check_22_commit_format.py --check-message` | 任一 Change 格式契约或提交流程变化时 |

### 4.5 通用消费声明

1. 实践子文档和工具可以消费本文契约，但不得复制维护 commit message 格式第二事实源；
2. `tools/check_22_commit_format.py` 必须依据本文校验 type 枚举、scope 推荐值、subject 长度、Refs 格式和中文字符检测；
3. Change Tools 当前只读校验，不执行 Git commit 写入；
4. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 specs/22-Change-变更记录.md）；
5. 本文契约变更时，消费本文的 Tools 实现、测试、Rules 和 Skill 必须同步检查。

### 4.6 中文字符检测规则

subject 和 body 中必须包含至少一个中文字符（Unicode 范围 `\u4e00-\u9fff`）。type 和 scope 不要求中文。

正则实现参考：

```python
HAS_CHINESE_RE = re.compile(r'[\u4e00-\u9fff]')
```

检查范围：subject 中 type 和 scope 之后的内容部分，以及 body 全文。缺少中文字符视为 error。

## 5. 检查项

检查 Change 契约是否合规时，应确认：

1. type 枚举是否与 `specs/22-Change-变更记录.md` §8.2 一致；
2. scope 枚举是否与 `specs/22-Change-变更记录.md` §8.3 一致；
3. subject 约束是否与 `specs/22-Change-变更记录.md` §8.1 一致；
4. `tools/check_22_commit_format.py` 是否依据本契约进行校验，未自行扩张契约；
5. 契约变更后，Tools 实现和测试是否已同步更新。
