## 1. 目标

v2 的目标不是复制一套新规范，而是把现有 specs 的权威归口、读取路径和知识地图结构构件重整为更服务 AI 的体系。

目标判断以 00 的 AI 第一服务对象和 V1-V10 为准：

1. 服务 V1：AI 能快速定位该读什么；
2. 服务 V2：AI 获得足够但不过载的可行动理解；
3. 服务 V3：AI 能判断定义归口、消费关系、事实源边界和风险；
4. 服务 V4：AI 能稳定执行，而不是依赖聊天记忆；
5. 服务 V5：AI 能识别 Human Gate；
6. 服务 V6：关键结论能验证；
7. 服务 V7：证据能沉淀；
8. 服务 V8：稳定事实可靠回写；
9. 服务 V9：Human 能看见态势、风险和证据；
10. 服务 V10：可复用经验、反复问题和体系缺口能回流。

## 2. 基本原则

1. `specs/` 在切换前仍是唯一 active 正式规范事实源。
2. `specs-v2/` 只承载 candidate 计划、结构和占位。
3. 不批量迁入正式规范正文；每篇文档必须单独和 Human 核对后再迁入。
4. 知识地图是实现 V1/V2/V3/V9/V10 的方法之一，不是 00 中的独立价值判断。
5. 知识地图不是新事实源、不是工作对象、不是第七类构成要素，也不是资产分类。
6. 知识地图由 specs 结构契约、工作对象字段、管辖项目配置和 Git 提交记录经 Code 实时解析生成。
7. Web 暂不实施；v2 先完成规范结构和 Code v2 只读解析能力。
8. v1 子文档和成员文件中的机制性契约不得因 v2 减少文件数量而消失。
9. 逐篇迁入前必须先通过 `V1-UNDERSTANDING-GATE.md` 中的机制理解门禁。

编号调整理由：

1. 01 是所有规范的结构元规范；每篇规范如何声明身份、权威域、引用关系、附件授权和知识地图结构构件，应先由 01 定义。
2. 02 是 AI 和 Code 的系统地图入口，在文档结构规则之后定义目录、入口、编号、管辖项目配置和知识地图定位边界。
3. 03 术语在文档结构和系统地图之后统一表达，避免术语规范承载结构规则。
4. 04 事实源规则在结构、地图和术语之后收口，承接过程输出、证据、回写和吸收边界。

依赖顺序约束：

1. v2 01 是文档治理，不是 v1 04 保障机制的前移。
2. v2 04 是 v1 09 全局事实源规则的候选承接，属于高影响重构，未核对前不得视为完成迁移。
3. v2 05 若合并 v1 04 系列，必须显式保留 v1 04、04.01、04.02、04.03 的声明、资产登记机制、环境适配和检查链路，并保留 v1 对 Code/Web、运行时扩展和其它可维护承载物的消费边界映射。
4. v2 06/07 若吸收 v1 03.02/03.03，必须保留成员自描述、active 判定、强制骨架和 Code 派生索引输入。

## 4. 附件与成员区

附件不是常规子文档体系。附件只承载主规范授权的注册表、矩阵、模板、示例或长清单。

附件不得承载 `ldvh_doc`、`ldvh_member`、保障要求类型、成员锚点、资产登记机制、环境适配状态或其他机制性事实；这些必须由主规范、成员主文件或正式资产自描述承载。

| 区域 | 用途 | 边界 |
|---|---|---|
| 根目录 `{父编号}.Att.{两位序号}-{名称}.md` | 字段注册表、知识地图关系类型、环境矩阵、模板、示例 | 不定义主规范原则 |
| `20-29-事实模型/` | 具体事实模型候选迁移区 | 每篇单独核对 |
| `30-59-行动编排/` | 具体行动编排候选迁移区 | 每篇单独核对 |

## 5. 知识地图结构构件

v2 主规范应天然支持 Code 抽取知识地图，但不得要求 AI 读取全量文件。知识地图依赖文档结构、字段契约、管辖项目配置和 Git 记录等结构构件，由 Code 实时解析生成，只读派生，不落盘为新的事实源。

候选结构构件包括：

1. 文档身份；
2. 权威域；
3. 定义项；
4. 消费项；
5. 被检查项；
6. 回写目标；
7. Human Gate 关系；
8. 附件授权；
9. 成员集合；
10. 管辖项目命名空间。

候选边类型先放入 `02.Att.01-知识地图关系类型表.md`，待 02 单篇核对时确认。

## 6. 已记录判断

以下判断只作为 v2 候选计划记录，不构成正式迁入：

1. 00 从“理念与纲要”收敛为“理念与价值标准”，作为所有 v2 内容的最高判断基准。
2. V1-V10 不只是评价标准，而是六类构成要素及其下属机制成为构成要素实践的准入门槛。
3. 字段、附件、资产承载物、工具、知识地图关系、Code 输出和 Web 展示都必须先归属六类构成要素之一，不得在 00 中被写成并列准入主体。
4. 知识地图是服务 V1/V2/V3/V9/V10 的方法之一，不在 00 中作为独立章节维护。
5. 运行闭环不在 00 中作为独立章节维护；00 只保留闭环相关价值判断，具体事实对象生命周期、AI 行动生命周期、证据回写、Git 追溯和持续回流分别由 04、06、07、10 及相关事实模型或行动编排规范承接。
6. 01 定义通用文档结构；06 定义事实模型文档的专属结构和字段契约。
7. 02 是 AI 和 Code 的系统地图，并承接知识地图定位边界，不展开字段、回写或行动编排细节。
8. 字段契约属于事实模型，但 06 只能成为统一治理入口，不得成为所有具体模型 schema 的单一权威。
9. 公共字段稳定性由 06 中央定义、20-29 具体模型声明采用、Code 生成字段矩阵校验共同保障；注册表不得反向定义字段存在性、必填性或状态条件。
10. 30-59 行动编排不能简单合并；07 承接通用规则和成员结构，30/41/42/43/44 等具体流程仍需保留各自职责。
11. Web 暂不实施不等于 Web 契约可忽略；事实对象 DTO、状态字段和 Spark 创建白名单仍是迁移回归线。

2. 禁止将 v1 正文批量复制到 v2。
3. 禁止创建落盘知识地图缓存。
4. 禁止修改 Web 以消费 v2。
5. 禁止把附件写成新的独立权威域。
