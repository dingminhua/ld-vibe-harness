## 1. LDVH 为什么存在

Vibe Coding 使 Human 能够用自然语言表达目标，由 AI 理解上下文、推理方案并生成实现，门槛低、反馈快、产出多。但 AI 生成代码的本质不是确定性编译，而是基于开发环境上下文、模型训练经验和参数形成的概率性推理，因此天然存在上下文依赖、概率性输出和无状态等问题。

虽然目前 Vibe Coding 已经能够较好地完成单个功能、局部修复，也能在明确的测试目标和验收反馈下承担较长时间的连续工作。但真实开发不是单点工作的叠加，它往往是从一个概念出发，通过一个个功能、一次次修改、一步步迭代、一点点完善打磨出来的。在这个过程中，如果缺乏对需求、状态、验证、决策、经验和上下文的稳定衔接，就会导致产出越多、负担越重，最终陷入问题回归、判断失据、质量漂移和闭环断裂。

LD Vibe Harness 要解决的，就是项目在持续演进中，如何避免从“开始还不错”逐渐变成“难以继续做”的问题。概括如下：

设计理念：

1. 以 AI 执行者为第一服务对象；
2. 以 LDVH Helper CLI 为基础服务形式；
3. 以事实源为信息锚点；
4. 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素；
5. 以 V1-V8 价值标准为行动标尺。

构成要素：

1. 用规范体系定义规则、边界和保障要求；
2. 用事实模型组织事实、状态、证据和经验；
3. 用行动模板沉淀可复用行动结构；
4. 用 Code 提供确定性解析、校验、受控操作和反馈；
5. 用 Web 桥接 Human 与 AI，呈现状态、风险和证据。

最终目标：

1. 让 AI、Human、Code 可以各展所长，使 Vibe Coding 推理更稳定、结果更可控、产出更高效；
2. 进而让环境、模型、使用者可以自由组合，使 Vibe Coding 使用更方便、选择更丰富、协同更顺畅。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于经验沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

LDVH 以 AI 执行者为第一服务对象。要说明这一点，需要先理解 AI 执行者的依赖、能力与本质。

AI 依赖：

1. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解工作范围；
2. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
3. 关联信息——缺少相关背景、依赖、约束和上下游关系时，AI 容易孤立理解工作，误判影响范围；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 可用工具——缺少可用工具或环境能力时，AI 容易停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 规划构造——能把复杂目标拆解为路径、步骤和待处理对象，并基于上下文、规则和经验组织解决方案；
3. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
4. 工具调度——能根据工作场景识别需要使用的工具或环境能力，并把反馈纳入后续判断；
5. 泛化应用——能在相似问题之间复用经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失过往依据。

这些依赖、能力与本质共同决定了 LDVH 的支撑方向：为 AI 提供可消费、可验证、可接续的稳定依据与协作条件，使其能够充分发挥自身能力，让长期项目中的判断有据、行动可续、结果可验。

## 3. 以 LDVH Helper CLI 为基础服务形式

LDVH 以 Helper CLI 为基础服务形式。AI 可以直接调用，环境 Hook、插件和 adapter 也可以在相应生命周期中调用同一服务能力，并将结果交给 AI。

Helper CLI 围绕当前任务和工作对象提供服务，帮助 AI 定位事实与规则、了解当前状态、调用 LDVH 已有能力、识别当前行动适用的要求，并明确结果如何验证、回写和接续。

Helper CLI 只在当前事项落入来源规范的适用范围时产生强制作用。命中具体规则时，AI 必须执行该规则规定的要求；未命中具体规则时，LDVH 不对 AI 的普通求解路径产生影响。

Helper CLI 的具体命令、响应格式、环境衔接和实现方式由后续相关规范承接；本文只定义其基础服务形式、作用和边界。

## 4. 以事实源为信息锚点

LDVH 以事实源为信息锚点，并提出两项要求：

1. 有 Git，可溯源。事实源以 Git 可追踪文件为唯一有效承载形态，稳定事实的形成、修改、验证和关闭都能回到明确的 Git 文件位置和 Git 溯源记录；聊天、AI 推理、工具输出、缓存、索引、Web 状态和派生视图等只有回写到 Git 文件事实源并完成验证后，才可能成为稳定事实。

2. 有组织，可消费。事实源不是材料堆积，而是要形成清晰的事实组织：事实放在哪里，边界是什么，引用关系如何建立，状态如何变化，结果回写到哪里。组织清晰的事实源才能被 Code 消费，进而放大事实源的价值——让 AI 少读、少猜、少漂移，让验证、回写和接续有稳定入口，而不只是人能看懂的材料。

上述两项要求共同构成本文所称的事实源边界：符合两项要求，才是 LDVH 认可的事实源；不符合的，不得作为稳定事实的承载位置。后续本文中“事实源边界”均指这两项要求。

事实源承载管辖项目中需要稳定保留的事实、状态、证据、决策和经验，为 AI 理解项目现状、追溯既有依据、回写验证结果和接续后续工作提供稳定位置。

事实模型、Code 和 Web 可以承接、消费、展示或辅助回写事实，但不得替代事实源整体。具体事实源类型、证据规则、回写规则、吸收规则、Code 消费规则和 Git 溯源等规则，由后续相关规范承接；本文只定义上位原则。

## 5. 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素

LDVH 以规范体系、事实模型、行动模板、Code 和 Web 为构成要素。这五类构成要素把规则、事实、行动、确定性反馈和 Human-facing 呈现分开归口，形成 AI 可定位、可行动、可验证、可交还的结构。

LDVH 的五类构成要素包括：

1. 规范体系。以 Code 可消费的 Markdown 组织 LDVH 的规则、边界、价值标准和保障要求，由正式 specs 正文及其授权附件共同构成 LDVH 规则源，为 AI 以及包括 Helper CLI 在内的 Code 能力提供可定位、可解析、可引用的规则依据，使 AI 能据此理解目标边界、识别适用场景并判断行动约束；
2. 事实模型。在事实源边界内组织需要对象化、状态化或证据化管理的事实，使结论、状态、证据和经验能够在事实源中稳定记录、关联、更新和消费；
3. 行动模板。沉淀重复场景中的可复用行动结构，明确适用条件、关键步骤、验证入口和交还方式，使 AI 在命中相应场景时能够稳定行动；
4. Code。提供解析、索引、聚合、校验、测试、上下文压缩和受控写入等确定性能力与反馈，并以 Helper CLI 作为面向 AI 执行者的基础服务形式，降低 AI 的读取、判断和验证成本；
5. Web。从事实源独立读取并呈现状态、风险、证据、待确认事项和验收信息，帮助 Human 理解项目情况、进行方向校正与决策。

五类构成要素用于确定 LDVH 内容的职责归口，不形成上下层级，也不直接决定具体实践是否准入。规则、对象、字段、附件、工具、Code 输出、Web 展示和派生机制等构成要素实践纳入 LDVH 前，必须归属于规范体系、事实模型、行动模板、Code 或 Web，并接受 V1-V8 价值判断；涉及稳定事实承载时，还必须符合事实源边界。

LDVH Specs 的共同结构由 04《Specs 基础规范》在本文授权范围内统一治理。04 分别定义本文采用的根规范结构和下位正式规范采用的标准规范结构，统一信息角色、结构要求、解析入口和承接规则，但不得改变或重新解释本文的上位定义。

## 6. 以 V1-V8 价值标准为行动标尺

LDVH 以 V1-V8 价值标准为行动标尺。五类构成要素及其具体实践，都必须帮助 AI 获得以下一种或多种价值。

V1-V8 分别从定位、理解、边界、推进、判断、接续、沟通和积累八个方面进行判断。每项实践按照自身职责服务其中一项或多项价值；新增机制只有在为 AI 带来可辨认的净收益时，才具有纳入 LDVH 的价值。

本文所称“V1-V8 价值标准”，是表格列出的八项价值维度；“V1-V8 价值判断”是依据这些标准判断构成要素及其具体实践能否为 AI 带来相应价值；“行动标尺”表示这些标准对 LDVH 设计、纳入和使用的指导作用。表格中的“不满足时的表现”用于识别相应负担和风险。

| 编号 | 标准 | 判断问题 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | 能否帮助 AI 根据当前目标和工作对象，快速定位相关且来源明确的规则、事实和状态，以及可用能力的入口 | 信息存在但 AI 找不到；盲目搜索或全文读取；误用来源；遗漏关键规则、事实、状态或能力入口 |
| V2 | 充分理解 | 能否帮助 AI 将当前相关的目标、工作对象、规则、事实、状态、依赖关系和验收要求联系起来，形成充分、连贯且不过载的整体理解 | AI 找到了相关信息，但仍无法形成整体理解；关系、冲突或关键上下文被遗漏；上下文不足或过载造成误解 |
| V3 | 边界识别 | 能否帮助 AI 依据来源明确且可回指的规则、事实和当前状态，识别当前事项适用哪些要求、什么必须遵守、什么可以自主决定、什么情况必须暂停、暂停影响什么，以及哪些决定应交由 Human | AI 已理解当前事项，但仍发生规则适用误判、要求遗漏、作用外溢、越权推进、应停未停或错误恢复 |
| V4 | 稳定推进 | 能否帮助 AI 在 LDVH 已明确承接的事项中，复用适用的行动结构和可用能力，并及时获得能够支持后续调整或分流的确定性反馈 | AI 已明确目标和边界，但仍反复重建已有处理方式、遗漏关键要求、无效试错，或在缺少反馈时发生执行漂移 |
| V5 | 据实判断 | 能否帮助 AI 使受 LDVH 规则或项目事实约束的重要判断，以及关于状态变化、能力状态、环境接入和完成情况的结论与声明，保持在验证结果或当次可观察依据实际支持的范围内，并清楚区分已经证实、尚未证实和残留风险 | AI 将事实与推测混淆；以自述、工具成功、局部结果或静态存在代替范围匹配的依据；判断或声明超出实际证据范围 |
| V6 | 工作接续 | 能否帮助 AI 把当前项目后续工作需要的事实、状态、证据和决策稳定保留下来，使不同会话、执行者和阶段都能恢复这些信息、追溯其来源和变化并接续工作 | 当次工作已有可信结果，但后续执行者无法恢复依据、状态和决定，只能重复调查、重建状态或中断接续 |
| V7 | 清晰沟通 | 能否帮助 AI 在需要 Human 判断、授权、确认或验收时，清楚交还当前状态、依据、影响、风险和待决定事项，使 Human 能够作出对象与作用范围明确的回应，并使 AI 能够据此继续、调整或保持暂停 | AI 已识别需要 Human 参与，但交还内容仍然含混；Human 无法明确回应，或 AI 无法确定回应约束的对象、范围和后续行动 |
| V8 | 持续积累 | 能否帮助 AI 使当前工作中形成的可复用经验、反复问题以及规则或能力缺口，在后续事项中能够被复用或继续处理 | 当前项目可以接续，但相似事项仍然重复分析和试错；同类问题反复发生；已经发现的经验和体系缺口长期悬置 |

## 7. 验证要求

验证要求用于判断本文定义的上位原则是否在具体变更、机制和声明中成立。验证结论只覆盖当次检查的对象、环境和范围；未检查、不可观察或缺少依据的部分仍属于未验证范围。

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 存在理由与第一服务对象 | 修改本文存在理由、第一服务对象、设计理念或最终目标时 | 修改后的定义仍然服务 AI 在长期项目中获得稳定依据、边界、状态、验证和接续能力，并保持 AI 执行者为第一服务对象 | 本文正文、变更影响说明、相关场景分析和 Human 明确决定 | AI 语义审核、Human Gate | 当次修改及其直接影响的上位定义 | 暂停修改，说明冲突和影响范围，进入 Human Gate |
| Helper CLI 基础服务与规则作用边界 | 修改 Helper CLI、服务契约、Hook、插件、adapter 或相关环境入口，或者声称 LDVH 规则已经产生强制作用时 | AI 可以直接调用相应服务；环境入口调用同一服务能力；命中具体规则时落实规则要求；未命中具体规则时保持普通求解路径自主 | 来源规范、Helper 响应、Code 或测试输出、当次环境触发结果和失败诊断 | Helper CLI、Code、tests、环境探针和 AI 审核 | 当次检查的服务能力、规则场景和环境入口 | 暴露能力或接入缺口，不声明规则已被自动保障；按来源规则暂停、降级、分流或交还 |
| 事实源信息锚点 | 新增或修改事实源类型、事实模型、事实回写、状态或证据规则时 | 稳定事实由 Git 可追踪文件承载，具有明确组织和消费位置；过程输出、缓存、Web 状态和派生结果没有替代事实源 | Git 文件路径、对象结构、字段与状态规则、引用关系、回读结果和 Git 溯源 | Helper CLI、AI 审核、Code validator 和回读检查 | 当次检查的事实类型、对象、字段、状态和路径 | 不将相关内容作为稳定事实消费；回到事实源或事实模型规则，必要时进入 Human Gate |

| Specs 结构治理授权 | 修改 04 定义的根规范结构、标准规范结构、信息角色、结构要求、解析入口或承接规则时 | 修改仍在本文授权范围内，能够区分根规范结构与标准规范结构，并且没有改变或重新解释本文的上位定义 | 本文授权、04 正文、结构变更说明、受影响规范样例和 Code 解析结果 | AI 架构审核、Specs validator、Code tests 和 Human Gate | 当次修改的结构规则、受影响规范类型和解析入口 | 暂停受影响的结构变更，回到本文授权和 04 修正；需要改变授权范围时进入 Human Gate |
| V1-V8 价值判断 | 新增或修改构成要素实践、规则、对象、能力或派生机制时 | 能够说明主要帮助 AI 获得哪些 V1-V8 价值、减少什么负担或风险，并且新增负担没有抵消其价值 | 对应价值判断问题、独立失败场景、目标作用说明、当次验证结果或 Human 审核 | Helper CLI、AI 价值审核和 Human Gate | 当次评估的具体实践，不自动扩张到相邻机制 | 保持为候选或不予纳入；无法判断价值或需要接受重大取舍时进入 Human Gate |
| 能力、环境与完成声明 | 声称能力 available、环境 integrated、状态成立或工作 completed 时 | 声明范围与实际可用能力、验证结果或当次可观察依据一致，并明确已经证实、尚未证实和残留风险 | 实际调用结果、测试结果、环境触发结果、回读结果、Human 验收和来源回指 | Helper CLI、Code、tests、环境验收和 Human | 当次检查的对象、环境、入口、版本和时间范围 | 缩小声明范围，标记为未验证、部分成立或不可观察；需要接受残留风险时进入 Human Gate |
| Human Gate 与 Stop Conditions | 触发 Human Gate 或 Stop Conditions，或者准备恢复受影响行动时 | 受影响的行动、对象或声明已经优先暂停；Human 回应的对象和作用范围清楚；恢复条件具有来源规则和当次依据 | 触发规则、暂停状态、交还内容、Human 明确回应和恢复依据 | Helper CLI、AI 审核、环境入口和 Human | 受 Gate 或 Stop 影响的具体行动、对象或声明 | 保持暂停，不根据推测恢复；按来源规则确认、分流或交还 |

具体命令、响应格式、测试实现、环境探针和验证工具由后续相关规范与实现承接；本文只定义上位验证对象、成立条件、可接受依据、证明范围和未满足时的处理。

## 8. Human Gate

Human Gate 用于保留只能由 Human 作出的上位判断、授权、方向选择、风险接受和验收决定。Human Gate 触发后，受其影响的行动、对象或声明必须优先暂停；未受影响的工作可以在来源规则和作用范围清楚时继续。

以下事项只能由 Human 决定：

1. 改变 LDVH 的存在理由、核心问题或最终目标；
2. 改变 AI 执行者作为第一服务对象的定位，或者改变 Human、AI 和 Code 的基本职责关系；
3. 改变 Helper CLI 的基础服务形式，或者改变“命中具体规则时落实规则要求、未命中具体规则时保持普通求解路径自主”的作用边界；
4. 改变事实源作为信息锚点的定位、事实源边界，或者将事实源改为构成要素；
5. 新增、删除、改名或重排规范体系、事实模型、行动模板、Code 和 Web 五类构成要素；
6. 改变 V1-V8 的数量、名称、判断问题、价值边界或净价值成立原则；
7. 改变本文对 04《Specs 基础规范》的结构治理授权范围，或者改变根规范结构与标准规范结构的基本关系；
8. 改变本文验证要求、Human Gate 或 Stop Conditions 的上位语义；
9. 改变下位规范、附件、事实对象、Code、Web、工具输出和环境入口不得重新解释、覆盖或弱化本文上位定义的关系；
10. 接受来源规则要求交由 Human 决定的重大取舍、未验证范围或残留风险。

不改变规则含义的错别字修正、格式调整、措辞澄清和等义表达优化，不单独触发 Human Gate。无法确认修改是否改变上位语义时，应当先暂停受影响的修改并交由 Human 判断。

进入 Human Gate 时，AI 应当向 Human 清楚交还：

1. 待决定的对象和问题；
2. 触发 Human Gate 的来源规则；
3. 当前事实、验证依据和未验证范围；
4. 受影响的行动、对象和声明；
5. 可选处理方式及各自影响；
6. 已知风险和残留风险；
7. Human 回应后可以继续、调整、分流或保持暂停的范围。

Human 回应应当能够明确决定对象、作用范围和后续方向。无法判断 Human 回应约束哪些对象或行动时，受影响范围继续保持暂停，并请求补充确认。

Human Gate 只能完成 Human 判断、授权、方向校正、风险接受或验收决定，不能把未验证内容转化为已验证，也不能替代事实源、测试结果、环境触发依据或完成声明所需的验证。

AI 可以准备事实、影响范围、风险、选项和建议，但不得替代 Human 作出决定；Code、tests、Hook、Helper 响应、工具成功输出和 Web 展示结果也不得替代 Human Gate。

## 9. Stop Conditions

Stop Conditions 用于在继续推进会越过已经生效的规则、事实、验证或 Human 决定边界时，优先暂停受影响范围。停止效力只作用于命中来源规则的行动、对象或声明；未命中具体停止条件的普通求解路径保持自主。

出现以下任一情况时，AI 必须暂停受影响的行动、对象或声明：

1. 已经触发 Human Gate，但尚未取得对象、作用范围和后续方向清楚的 Human 回应；
2. 已经发现与当前行动、对象或声明相关的具体来源规则，但无法确认其适用条件、效力，或者无法判断多条规则之间的权威关系，继续推进可能违反其中的强制要求；
3. 具体规则已经适用，但其要求的行动、受控入口、验证或回写无法满足，并且来源规则没有提供可以继续的分流方式；
4. 准备创建、修改或回写正式事实对象或事实源，但无法满足适用的事实模型、字段、状态、验证或 Git 溯源要求；
5. 准备将新的规则、对象、能力或机制纳入 LDVH，但无法归入五类构成要素，或者无法确认其能够为 AI 带来 V1-V8 中可辨认的净价值；
6. 准备声明状态成立、能力 available、环境 integrated 或工作 completed，但现有验证结果或当次可观察依据不能支持声明范围；
7. 下位规范、附件、事实对象、Code、Web、工具输出或环境入口试图重新解释、覆盖或弱化本文的上位定义，或者 04 的结构治理超出本文授权范围；
8. 无法确认停止影响哪些行动、对象或声明，或者无法确认恢复条件及 Human 回应的作用范围。

Stop Conditions 与 Human Gate 承担不同职责：Stop Conditions 决定何时暂停，Human Gate 决定哪些事项必须由 Human 作出判断。未触发 Human Gate 的停止，可以在来源规则定义的核对、修复、验证或分流条件满足后恢复；已经触发 Human Gate 的，必须取得作用范围清楚的 Human 回应。

暂停期间，AI 可以开展不越过停止边界的规则定位、事实核对、验证、证据收集、修复准备、分流准备和 Human Gate 交还，也可以继续未受影响的工作。

受影响范围只能在以下依据成立后恢复：

1. 规则适用条件、效力或权威关系已经确认；
2. 强制要求已经满足，或者已经进入来源规则明确允许的分流方式；
3. 缺少的事实、验证或环境依据已经取得，相关声明已经缩小到依据实际支持的范围；
4. Human Gate 已经取得对象、作用范围和后续方向清楚的 Human 回应；
5. 越过本文上位定义或结构治理授权的冲突已经修正并完成相应验证。

恢复只覆盖现有依据能够支持的范围，不自动恢复其它受影响事项。

Helper CLI、Code、Hook、validator 和环境入口可以识别、报告或执行来源规则已经定义的停止条件。其停止效力必须回指具体来源规则、触发条件和受影响范围；未命中时，AI 的普通求解路径保持自主。
