## 一、Trae Rules 生效方式映射

PM Kit 保留 L0/L1/L2 分层，同时必须映射 Trae Rules 的真实生效方式：

| PM Kit 层级 | 推荐 Trae 生效方式 | 说明 |
|---|---|---|
| L0 | 始终生效 | 工作区桥接、规范来源、项目识别入口 |
| L1 | 始终生效 | 项目定位、项目专属硬约束、核心入口 |
| L2 文件类型规则 | `globs` 指定文件生效 | 例如 docs、tests、frontend、backend |
| L2 场景规则 | `description` 智能生效或手动 `#Rule` | 例如 release、audit、migration |
| Git 提交规则 | `scene: git_message` | 仅用于提交消息生成 |

`#Rule` 手动触发优先于自动匹配。`scene: git_message` 属于特殊场景规则，不由普通 `alwaysApply`、`globs`、`description` 替代。多条规则同时命中时，按 11-AI协作规范 §十一 的规则冲突优先级和 Human Gate 优先原则处理。

## 二、L0/L1/L2 设计模板

### 2.1 L0 设计模板

适用场景：工作区承载多个项目，且需要声明规范来源、管理项目叠加关系和各项目 L1 入口时。

推荐结构：

```markdown
# 工作区规则

> 最后更新：YYYY-MM-DD

## 工作区定位

本工作区用于承载...项目。

## 项目集成员

- 项目A：...
- 项目B：...

## 基础规范来源

本工作区的基础规范以 trae-pm-kit `specs-v2/` 为权威定义，所有项目均继承此规范。

## 项目上下文识别与 L1 读取机制

会话开始时，AI 必须先识别用户工作目录所属项目，再读取对应 L1 规则。详见 11-AI协作规范 §5.5。

## L1 引导 L2

各项目 L1（`.trae/rules/project_rules.md`）负责定义项目专属硬约束，并引导本项目 L2 场景规则。

## Vibe Coding 最小底线

- 修改前先理解目标项目已有结构、同类文件、已有工具和事实源，优先复用现有模式，不得凭惯例另起一套实现。
- 执行用户任务时只做与目标直接相关的最小必要修改，不得顺手重构、扩展范围、替换架构或引入新依赖。
- 不得编造项目事实、文件内容、依赖、命令输出、测试结果或用户确认；不确定时必须读取事实源、运行检查或询问用户。
- 涉及规则、Skill、Agent、product.yaml、跨项目契约、事实源归属或难以低成本回滚的修改时，必须先说明方案、影响范围和待修改文件，并等待 Human Gate 确认。
- 完成修改后必须执行与变更类型匹配的最小验证；无法验证时必须说明原因、风险和建议补验方式。
- 新增需求、约束或发现不得只停留在对话里，必须询问是否整理为 Task / Memo。
- L0 只放跨项目底线、事实源入口、Human Gate 和 L1 引导；流程、模板、教程进入 Skill 或 specs。

## 压缩保护

先读 L1 | 会话开始识别项目上下文 | 规范见PMKit-specs | L1引导L2 | 管理项目叠加 | Vibe Coding最小底线
```

L0 检查项：

| 检查项 | 标准 |
|---|---|
| 工作区定位 | 能一句话说明工作区用途 |
| 项目成员 | 列出当前工作区项目及职责 |
| 规范来源 | 指向 PM Kit specs-v2 |
| 文档路径 | 引用规范层时使用 PM Kit 项目目录前缀，不使用裸 docs/ 相对路径 |
| 路径归属 | 引用 PM Kit 规范时标注 PM Kit 项目路径；引用受管理项目数据时标注受管理项目路径；不得用"当前项目"等模糊表述（见 11-AI协作规范 §四.6） |
| L1 引导 | 明确各项目 L1 负责项目专属约束 |
| 压缩保护 | 能在上下文压缩后保留关键规则入口 |

### 2.2 L1 设计模板

适用场景：每个有 docs/ 或独立规则约束的项目应维护 L1。

推荐结构：

```markdown
# {项目名} 项目规则

> 最后更新：YYYY-MM-DD

## 项目定位

{一句话说明项目职责。}

## 必读文档索引

- pm-kit-base/（changes、pitfalls、memos）：...
- specs-v2/10~14：...
- docs/20~59：...

## 硬约束

以下为项目专属约束。通用约束见规范层 `specs-v2/`。

1. ...
2. ...

## L2 场景规则

- `.trae/rules/{scene}-rules.md`：...

## 压缩保护

关键词1 | 关键词2 | 关键词3
```

L1 设计检查项：

| 检查项 | 标准 |
|---|---|
| 项目定位 | 不超过一段，明确项目职责 |
| 必读索引 | 覆盖核心 docs/、ADR、必要规则入口 |
| 硬约束 | 只写项目专属约束 |
| L2 引导 | 列出本项目已有场景规则 |
| 压缩保护 | 只摘要项目专属高频约束 |

### 2.3 L2 设计模板

适用场景：L2 适合承载特定文件类型的约束、特定目录的约束、特定执行场景的约束。

命名格式：`.trae/rules/{scene}-rules.md`，`{scene}` 使用小写连字符格式，如 `test-rules`、`docs-rules`、`release-rules`。

推荐结构：

```markdown
# {场景} 规则

> 最后更新：YYYY-MM-DD
> 适用范围：...

## 触发场景

- ...

## 执行约束

1. ...
2. ...

## 检查项

| 检查项 | 标准 |
|---|---|
| ... | ... |

## 压缩保护

关键词1 | 关键词2 | 关键词3
```

## 三、规则变更执行流程

规则变更执行时按以下步骤处理：

1. 判断变更对象属于规范层、L0、L1 还是 L2。
2. 按 11-AI协作规范 §十二 判断并触发 Human Gate。
3. 说明变更原因、影响范围和待修改文件。
4. 用户确认后修改对应文件。
5. 同步检查引用、必读索引和相关 L2 入口。
6. 追加 Change 记录。
7. 执行一致性检查。

---

## 四、规则审计检查项

| 检查项 | 标准 |
|---|---|
| 单一事实源 | 同一规则未在多个文件重复维护 |
| 规范与实践分离 | 规则在规范层，模板和检查项在本文 |
| L0 短小 | L0 只做桥接和入口声明 |
| L1 不重复 | L1 不复制规范层或 L0 正文 |
| L2 不覆盖 | L2 不替代规范层或 L1 |
| 必读索引同步 | 新增 docs/ 文件后 L1 已检查 |
| Human Gate 引用 | 变更流程引用 11-AI协作规范 §十二，不维护第二套清单 |
| Change 记录 | 规则变更已写入 pm-kit-base/changes/ |
