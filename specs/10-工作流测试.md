## 1. 本文解决的问题

本文解决 LDVH 如何把工作流程、Skill 生产方法和 AI 行动控制转化为可验证测试的问题，包括：

1. 工作流测试的定义、目标和事实源边界；
2. 如何把工作流程场景、Skill 使用场景和 Human Gate 场景建模为测试用例；
3. 自动化测试如何辅助 AI 发现规范、生产方法和机制实体中的问题；
4. AI 发现问题后应按什么顺序自修正规范、测试用例、生产方法或机制实体；
5. 工作流测试与 05、08、14、15 及 40-59 工作流程规范的关系。

本文不直接定义具体 Skill，不直接修改既有 Skill 实体，不替代具体工作流程规范，也不替代工具实现规范。

## 2. 与 00 总纲的关系

00 定义 LDVH 通过理念、规范、事实源和工作流约束 AI 稳定工作。工作流测试承接这一目标，把“AI 应如何行动”进一步转化为可复现、可检查、可迭代的测试用例，使 AI 不只依赖会话经验发现问题，而能依据规范化测试发现问题、定位原因并提出修正。

本文是 LDVH 工作流测试的权威位置。工作流程基础规则由 `specs/08-工作流程基础规范.md` 定义；Trae Skill、Agent、Rules 等开发环境机制由 `specs/05-Trae-Solo环境规范.md` 定义；Python 与 Web 工具边界由 `specs/14-Code实现与工具规范.md`、`specs/15-Web信息同步规范.md` 定义。本文只定义这些机制如何进入测试建模和测试反馈闭环。

## 3. 权威领域

本文的权威领域包括：

1. 工作流测试的定义和目标；
2. 工作流测试用例的最小组成；
3. 测试对象、测试类型和测试覆盖要求；
4. 自动化测试的输入、输出和事实源边界；
5. AI 自发现、自诊断和自修正顺序；
6. 工作流测试对 Skill 生产方法的准入要求；
7. 工作流测试的 Human Gate 与检查要求。

本文不定义工作模型字段契约、对象状态机、具体工作流程执行步骤、具体 Skill 文档正文或具体工具实现代码。

## 4. 工作流测试定义

### 4.1 工作流测试

工作流测试是 LDVH 对 AI 行动控制规则的测试建模方法，用于将规范中的工作流程、Skill 生产方法、Human Gate、事实源读取、事实源回写、失败降级和机制边界转化为可复现测试用例。

工作流测试的目标不是证明 AI 永远正确，而是让 AI 在执行前、执行中或机制升级前，能够依据测试用例发现以下问题：

1. 规范缺失、冲突或表述不可执行；
2. 工作流程的 Context、Scenario、Gate 或回写边界不完整；
3. Skill 触发条件、不适用场景、输入输出或失败处理不稳定；
4. Rules、Skill、Agent、Tools、Web 或 Contract 的机制边界不一致；
5. 自动化工具无法检查关键约束或检查结果无法回写为事实。

### 4.2 工作流测试与普通软件测试

工作流测试可以使用软件测试工具实现，但测试对象不是普通函数行为，而是 AI 行动控制行为。它测试的是 AI 是否按规范读取、判断、暂停、执行、回写和修正。

工作流测试不得把一次会话的临时成功视为稳定通过。只有测试用例、输入条件、预期行为、检查方式和失败处理均可复现时，才可作为稳定测试依据。

### 4.3 工作流测试与评估文档

项目评估文档可以提出测试建议，但测试建议只有进入正式规范、测试用例事实源或工具实现后，才成为稳定测试依据。工作流测试应优先从正式规范和事实源生成，不得直接以聊天结论或临时评估结论作为长期测试规则。

## 5. 测试对象

工作流测试至少覆盖以下对象：

1. **工作流程规范**：测试 Context、Scenario、Gate、执行流程、回写要求和证据留存是否可执行；
2. **Skill 生产方法**：测试某类流程是否具备创建或修改 Skill 的规范依据、测试用例和失败处理；
3. **Skill 实体**：测试 Skill 是否遵守上位规范、触发边界、输入输出和回写规则；
4. **Rules 投影**：测试 Rules 是否只承载入口摘要、压缩保护和运行时硬约束，不替代 specs；
5. **工具实现**：测试工具是否按规范读取、校验、生成、回写和报错；
6. **Human Gate**：测试需要人确认的场景是否暂停，且用户取消、暂缓或调整时不会继续执行；
7. **事实源回写**：测试稳定事实是否写入对应 Git 文件事实源，而不是停留在聊天、Skill 输出、Agent 输出或工具缓存。

## 6. 测试用例建模

### 6.1 测试用例最小组成

一个工作流测试用例至少应包含：

1. `id`：稳定测试用例标识；
2. `title`：测试用例标题；
3. `target`：被测试的规范、流程、Skill、Rules、工具或事实源；
4. `scenario`：触发场景；
5. `given`：执行前事实源、上下文和前置条件；
6. `input`：用户输入、工具输入或模拟事件；
7. `expected_behavior`：AI 或工具应表现出的行为；
8. `expected_stop`：是否必须停止、暂停或触发 Human Gate；
9. `expected_evidence`：应产生或检查的证据；
10. `expected_writeback`：是否应写回事实源以及写回位置；
11. `failure_diagnosis`：失败后应优先判断的问题归属；
12. `repair_policy`：失败后允许的修正方向和禁止动作。

### 6.2 测试用例来源

工作流测试用例应从以下来源生成：

1. 正式规范中的 Context、Scenario、Gate、执行流程和检查要求；
2. 工作模型中的准入条件、状态机、字段契约、验收和 closure 条件；
3. Trae 机制在 LDVH 中的使用边界；
4. Human Gate、高风险变更和事实源回写要求；
5. 已发生的失败案例、误触发案例、漏触发案例和规范冲突案例。

### 6.3 测试用例类型

工作流测试应覆盖以下类型：

1. **正向路径**：输入满足触发条件，AI 应进入对应流程或 Skill；
2. **负向路径**：输入不满足触发条件，AI 不应进入对应流程或 Skill；
3. **边界路径**：输入同时接近多个机制边界，AI 应按规范选择 Rules、Skill、Agent 或主控执行；
4. **缺失上下文路径**：事实源、规范或实例缺失时，AI 应停止并说明缺口；
5. **Human Gate 路径**：涉及写入、删除、状态流转、规范升级或高风险变更时，AI 应暂停确认；
6. **失败降级路径**：工具失败、权限不足、验证失败或规范冲突时，AI 应交还主控，不得强行继续；
7. **回写路径**：稳定事实产生后，AI 应写回正确事实源或说明尚未获得写入授权；
8. **回归路径**：修正一个问题后，不得破坏既有正向、负向和 Human Gate 用例。

## 7. 自动化测试

### 7.1 自动化测试定位

自动化测试用于提高工作流测试的可复现性和检查效率。自动化测试可以检查文件结构、字段、路径、章节、引用、测试用例格式、工具输出和部分行为约束，但不得替代 Human Gate，也不得替代人对规范方向、风险级别和产品取舍的判断。

### 7.2 自动化测试输入

自动化测试的输入应来自 Git 文件事实源，包括：

1. specs 正式规范；
2. 工作模型实例；
3. 工作流测试用例；
4. Rules、Skill、Agent 定义摘要或实体文件；
5. 工具实现与测试夹具；
6. 受控样例输入和预期输出。

自动化测试不得依赖不可复现的聊天记忆作为唯一输入。

### 7.3 自动化测试输出

自动化测试输出至少应包含：

1. 通过或失败结果；
2. 失败用例标识；
3. 失败位置；
4. 失败原因分类；
5. 建议修正方向；
6. 是否需要 Human Gate；
7. 是否可由 AI 继续提出补丁。

测试输出本身不是稳定事实。需要长期保留的测试结论、变更记录、风险、任务或决策必须写回对应事实源。

### 7.4 自动化测试分层

工作流测试自动化应分层实现：

1. **结构检查**：检查文件存在、命名、章节、字段和引用；
2. **规则检查**：检查禁止事项、必填项、状态流转和引用完整性；
3. **场景检查**：以测试用例模拟输入，检查应触发的流程、Skill、Gate 或停止条件；
4. **回写检查**：检查稳定事实是否写入允许位置，是否越权修改；
5. **回归检查**：检查新增或修改规则是否破坏既有用例。

## 8. AI 自发现与自修正

### 8.1 自发现

AI 可以依据工作流测试结果发现问题。发现问题时，AI 应先输出问题归属判断，而不是直接修改文件。

问题归属分为：

1. 规范缺失；
2. 规范冲突；
3. 测试用例缺失或错误；
4. Skill 生产方法缺口；
5. Skill 实体实现偏差；
6. Rules 投影偏差；
7. 工具实现缺陷；
8. 事实源实例错误；
9. Human Gate 未确认或权限不足。

### 8.2 自修正顺序

AI 自修正应按以下顺序执行：

1. 若正式规范缺失或冲突，先提出规范修正；
2. 若测试用例不能覆盖问题，先提出测试用例修正；
3. 若生产方法不能指导机制实体生成，先修正生产方法；
4. 若机制实体未遵守已稳定规范，才修改机制实体；
5. 若工具实现不符合规范，才修改工具实现；
6. 若事实源实例不符合契约，按对象规范和 Human Gate 修正实例；
7. 每次修正后运行相关回归测试。

### 8.3 禁止直接修 Skill

Skill 失败不得直接推导为“修改 Skill”。在 LDVH 中，Skill 是规范和生产方法的运行入口，不是规则本身。任何 Skill 修改前，都应先检查对应规范、测试用例和生产方法是否已经稳定。

只有满足以下条件时，才允许修改 Skill 实体：

1. 上位正式规范已定义该行为；
2. 工作流测试用例已定义预期行为；
3. 失败原因已定位为 Skill 实体未遵守规范或测试用例；
4. 修改范围不新增规范未定义的规则、字段、状态或 Human Gate 条件；
5. 修改后能回跑相关测试。

## 9. 与 Skill 生产方法的关系

工作流测试是 Skill 生产方法的前置约束。创建或修改 Skill 前，应先完成以下检查：

1. 该能力是否应由 Skill 承载；
2. 上位规范是否已经定义流程边界；
3. 是否已有测试用例覆盖正常触发、负向触发、Human Gate、失败降级和事实源回写；
4. 测试失败时是否能判断修正规范、测试用例、生产方法还是 Skill 实体；
5. 是否存在足够证据证明 Skill 实体修改不是临时修补。

Skill 生产方法的质量，不以 Skill 文档长度衡量，而以触发稳定性、边界清晰度、输入输出可执行性、失败处理完整性、事实源回写正确性和测试可复现性衡量。

## 10. 与工作流程规范的关系

工作流程规范定义 AI 应如何行动，工作流测试定义这些行动如何被验证。具体关系如下：

| 维度 | 工作流程规范 | 工作流测试 |
|---|---|---|
| 关注点 | 行动规则 | 行动规则是否可复现验证 |
| 核心内容 | Context、Scenario、Gate、执行流程、回写、证据 | 用例、输入、预期行为、检查、失败诊断、修正策略 |
| 事实源 | specs/40-59 具体流程规范 | specs、测试用例事实源和工具测试夹具 |
| 失败处理 | 规定 AI 应如何停下或回写 | 判断失败属于规范、用例、生产方法、实体还是工具 |

具体工作流程规范应能派生出测试用例。若某个工作流程无法生成可复现测试用例，应优先检查该工作流程的 Context、Scenario、Gate 或回写要求是否过于模糊。

## 11. 测试用例事实源边界

工作流测试用例应作为稳定事实源维护。具体承载位置由后续工具规范、目录规范或工作流程测试实现方案确定。

在承载位置稳定前，测试用例不得散落在聊天记录、临时脚本输出或 Skill 文档正文中。若必须临时记录，应回写到受控文档或任务证据中，并标注待迁移位置。

测试用例事实源不得重新定义规范正文。测试用例只能表达“在某输入和前置条件下，应如何验证规范行为”。若测试用例发现规范未定义预期行为，应回到正式规范修正。

## 12. Human Gate 与检查要求

以下工作流测试相关行为必须触发 Human Gate：

1. 新增、修改或删除正式规范中的测试规则；
2. 创建、修改或删除稳定测试用例事实源；
3. 将测试失败结论用于修改 Skill、Rules、Agent、Tools、Web 或 Contract 实体；
4. 自动化测试建议执行高风险变更、删除事实源或修改对象状态；
5. 测试结果显示规范冲突，需要选择修正规范方向；
6. AI 自修正将影响多个工作流程、多个工作模型或跨项目规则入口。

检查工作流测试时，应确认：

1. 测试用例是否有明确目标、输入、预期行为和失败诊断；
2. 测试是否能区分规范缺失、测试缺失、生产方法缺口和实体实现偏差；
3. 自动化测试是否只辅助检查，不绕过 Human Gate；
4. AI 是否先修正规范和生产方法，再修改 Skill 实体；
5. 测试输出中的稳定结论是否已按事实源边界回写；
6. 回归测试是否覆盖既有正向、负向、Human Gate 和失败降级路径。
