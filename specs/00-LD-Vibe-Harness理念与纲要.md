## 1. LD Vibe Harness 为什么存在

Vibe Coding 让人用自然语言表达意图，AI 推理生成实现——门槛低，反馈快，产出多，但 AI 生成代码的本质不是确定性编译，而是基于开发环境组织的上下文、结合模型训练经验和参数进行的概率性推理——因此天生带有非确定性、幻觉和无状态三大硬伤。

没有约束的 Vibe Coding 随着项目深入往往就会困在原型阶段：问题回归，判断失据，质量参差，结果漂移，代码堆叠却无法稳定推进。

LD Vibe Harness 是面向 Vibe Coding，由规范驱动的 AI 工作 Harness，用于把“随性的 AI 编程”纳入可规划、可执行、可验证、可沉淀、可演进的 AI 工程闭环。

它的方法，是以规范文档定义产品、明确要求，以 AI 推理生成实现、落地回流，以工作模型记录过程、沉淀记忆，以工作流程驱动执行、监督闭环，以 Code 工具提供确定性执行、稳定结果，以 Web 视图桥接 Human 与 AI、协调认知——进而让 Vibe Coding 更高效、更稳定、更可控。

LD Vibe Harness 是 Harness 思想的实践，由 LaoDing 基于实践沉淀而来，简称为 LDVH。

## 2. 以 AI 执行者为第一服务对象

LD Vibe Harness 以 AI 执行者为第一服务对象，通过深入理解 AI 执行者的依赖、能力与本质，依托开发环境构建可实现的方法与机制，为 AI 提供有力支撑，推动 AI 更稳定地输出，最终形成可持续的产品闭环。

AI 依赖：

1. 清晰目标——没有明确目标，AI 容易自行补全意图，导致方向偏移；
2. 明确边界——边界模糊时，AI 容易扩大、遗漏或误解任务范围；
3. 稳定事实——事实源混乱时，AI 判断失去依据，行动随上下文漂移；
4. 可见状态——状态不可见时，AI 无法判断当前进展、阻塞和下一步；
5. 具体验收标准——缺少验收标准时，AI 不知道何时停下，也难以判断是否完成；
6. 可用工具入口——没有工具入口时，AI 只能停留在推理和生成，难以形成确定执行。

AI 能力：

1. 语义理解——能从自然语言和复杂信息中提取目标、约束、关系和关键问题；
2. 任务拆解——能把复杂目标拆解为路径、步骤和待处理对象；
3. 方案构造——能基于上下文、规则和经验组织解决方案、表达实现思路；
4. 约束判断——能识别规则边界、风险、阻塞、冲突和需要 Human 确认的节点；
5. 工具调度——能根据任务场景识别需要使用的环境工具、Code、Skill 或 Agent，并把工具反馈纳入后续判断；
6. 泛化迁移——能在相似问题之间迁移经验，举一反三，提出新的处理方式。

AI 本质：

1. 概率性推理——AI 输出不是确定性编译结果，而是基于上下文、训练经验和模型参数生成的概率性结果；
2. 上下文依赖——AI 判断质量高度依赖当前可见上下文，上下文缺失、过载或冲突都会影响判断；
3. 无状态——AI 不天然保留跨会话稳定状态，容易前说后忘、重复犯错或丢失历史依据。

基于这些依赖、能力与本质，LD Vibe Harness 的设计重点，不是要求 AI 自发变得可靠，而是用清晰事实提供判断依据，用工作模型约束对象边界，用工作流程约束行动路径，用 Code 提供确定性执行和校验，用 Web 桥接 Human 的判断输入，使 AI 的能力被充分发挥，使 AI 的不稳定风险被结构化约束。

在这个框架中，Human、AI、Code、Web 四个角色各展所长、分工协作。

Human 负责判断、授权与责任边界：

1. 表达意图；
2. 补充约束；
3. 排定优先级；
4. 确认关键节点；
5. 做出关键决策和执行授权；
6. 校正 AI 判断；
7. 验收结果。

AI 负责推理与泛化：

1. 读取项目上下文；
2. 识别当前任务场景和事实源边界；
3. 拆解任务并提出执行计划；
4. 判断需要使用的 Code、Web、Skill 或 Agent；
5. 识别风险、阻塞和需要 Human 确认的节点；
6. 执行任务并记录执行证据；
7. 按事实源边界写回项目。

Code 负责确定性执行：

1. 读取、索引和聚合事实源；
2. 生成 AI 可行动的最小上下文；
3. 校验事实源、规范、引用、状态和执行结果；
4. 提供受控写入入口；
5. 通过测试、校验、格式化、构建等确定性操作给出稳定反馈。

Web 负责桥接 Human 与 AI：

1. 呈现项目态势、对象状态、执行证据、风险和待确认事项；
2. 支持 Human 补充判断、给出建议，并在规范授权范围内执行受控轻写入；
3. 将 Human 的干预转化为 AI 可读取的事实源变化或人工修改标记；
4. 降低 Human 理解、判断和介入项目事实源的成本。

这四个角色共同围绕 Git 文件事实源协作：Human 提供判断和授权，AI 形成推理，Code 提供确定反馈，Web 完成桥接与受控干预，使 Vibe Coding 不再依赖一次性对话生成，而是进入可读取、可判断、可执行、可验证、可回写、可演进的产品闭环。

## 3. 四类构成要素与事实源原则

LD Vibe Harness 不是由单一工具、单一规范或单一对象体系构成，而是由四类构成要素共同形成 AI 工程驾驭体系：开发环境、辅助工具、工作模型和工作流程。

事实源不是并列的构成要素，而是贯穿四类构成要素的底层权威原则。LDVH 中稳定事实必须回到 Git 可追踪文件；Markdown 和 YAML 的边界、权威性判断、单一事实源原则和工具输出回写规则，由 `specs/04-事实源边界与承载规范.md` 定义。

四类构成要素不是上下层级，也不是四种能力，而是性质不同、分工不同、共同服务于同一工程闭环的构成要素。

### 3.1 四类构成要素总览

| 类别 | 英文 | 归属 | 角色 | 回答的问题 | 举例 |
|---|---|---|---|---|---|
| 开发环境 | Development Environment | 开发环境提供 | 利用，不重新定义 | AI 协作运行在哪些原生机制之上 | Rules、Skill、Agent |
| 辅助工具 | Supporting Tools | LDVH 提供 | 实现和维护 | 用什么辅助读取、校验、展示、确认和回写 | Code 工具、Web 工具 |
| 工作模型 | Work Model | LDVH 定义规范，项目实例化 | 建模工程工作对象 | 项目工作如何被组织、流转和沉淀 | Intent、Task、Memo、ADR、Change、Pitfall |
| 工作流程 | Work Process | LDVH 定义规范，项目执行时适用 | 建模 AI 执行控制 | AI 如何读取、判断、执行、停下和回写 | Context、Scenario、Gate、Rules 适用、Skill 进入、Agent 调度、事实源回写 |

### 3.2 开发环境

在 LDVH 当前正式治理范围内，开发环境先纳入 Rules、Skill、Agent 三类可落地协作机制。它们是 LD Vibe Harness 可以利用的 AI 协作底座，但机制本身不会自动形成工程驾驭能力，也不会天然约束 AI 行为。

LD Vibe Harness 对开发环境的态度：

1. **利用不重新定义**：LDVH 定义如何使用具体开发环境提供的原生机制，不重新定义机制本身；
2. **规范不替代**：LDVH 的 Rules、Skill、Agent 设计规范，是对开发环境机制的使用约束和最佳实践，不是替代开发环境本身；
3. **适配不绑定**：LDVH 的规范体系可以适配不同 AI 编程环境的能力模型，但不假设某个开发环境是唯一可用底座。

具体开发环境的特有工具能力（如 Trae Solo 的 AskUserQuestion）由对应专项规范定义。00 不重复维护具体工具的触发场景、设计规范或降级策略。

### 3.3 辅助工具

辅助工具是 LD Vibe Harness 自身提供的工具化能力，用于降低 AI 和 Human 读取、理解、验证、维护和回写 Git 文件事实源的成本。辅助工具不成为最终事实源，也不替代规范、Human Gate 或 AI 判断。

辅助工具在总纲层分为 Code 工具和 Web 工具两类：

1. **Code 工具**：提供确定性执行结果和稳定反馈，用于解析、索引、校验、聚合、测试、构建、格式化和受控写入事实源。Python 辅助程序只是当前 LDVH 使用 Code 工具能力的一种实现方式，其他语言或运行时也可以实现同等能力；
2. **Web 工具**：提供 Human 交互入口，用于呈现项目态势、对象状态、执行证据、风险和待确认事项，辅助 Human Gate，并在规范授权范围内触发受控轻写入。Web 工具应复用或对齐 Code 工具的事实源访问、解析、校验和状态判断能力，但其总纲角色是 Human-facing 的态势入口和受控交互层。

辅助工具的边界：

1. 辅助工具可以降低读取、验证、展示和维护事实源的成本，但不能成为最终事实源；
2. Code 工具可以提供确定性执行结果、稳定反馈和受控写入入口，但不能替代规范判断或 Human Gate；
3. Web 工具可以提供态势呈现、Human Gate 辅助和受控轻写入入口，但不能成为开放式事实源编辑后台；
4. 辅助工具应以 Git 文件事实源为读取和展示依据，可以提供索引、聚合和展示能力，但不得把缓存、派生状态或运行时数据作为事实源，也不得独立维护与 Git 文件事实源冲突的数据；
5. Web 工具获取对象状态、字段和验证结果时，应复用 Code 工具的事实源访问、解析、校验和状态判断能力，或至少共享同一契约、测试和校验入口；不得分别维护两套对象读取、状态计算、字段解析或受控写入逻辑。

### 3.4 工作模型

工作模型是 LD Vibe Harness 对工程工作的自定义对象建模，用于承载意图、任务、决策、风险、依赖、证据、变更、产物、检查项和经验沉淀。

典型工作模型对象包括 Intent、Task、Memo、ADR、Change、Pitfall。

其中 Task 是 LDVH 的执行治理锚点，用于承接目标、验收标准、优先级、依赖、执行过程、验证证据、Agent 审查、Skill 产物吸收和关闭判断；具体字段契约和状态流转由 `specs/27-Task-任务.md` 定义。

工作模型的核心特征：

1. **规范由 LDVH 定义**：对象的准入条件、字段契约、状态流转、事实源边界和验收规则由 LDVH 规范体系定义；
2. **实例由项目拥有**：每个项目按规范创建的对象实例属于项目，存放在项目的结构化事实源目录中；
3. **服务工程生产**：对象用于让 AI、人和工具围绕同一组项目事实协作，支持任务拆解、状态追踪、证据回写、决策追溯和变更审计。

### 3.5 工作流程

工作流程是 LD Vibe Harness 对 AI 在项目中如何行动的执行控制建模，用于回答 AI 进入项目后该读什么、如何判断、如何执行、何时停下等待人确认，以及完成后如何把事实写回项目。

工作流程包括：

1. **Context**：AI 行动前应获得的最小可行动上下文；
2. **Scenario**：AI 如何识别当前任务场景；
3. **Gate / Human Gate**：AI 何时必须暂停并请求人确认；
4. **Rules 适用**：AI 如何加载、理解和遵守 Rules；
5. **Skill 进入**：AI 何时进入可复用流程；
6. **Agent 调度**：AI 何时调用子 Agent 或专业角色；
7. **事实源回写**：AI 完成执行后如何按事实源边界写回项目。

## 4. 价值实现标准

LD Vibe Harness 的价值实现由开发环境、辅助工具、工作模型和工作流程共同支撑。任何新增规则、对象、工具、网页视图或开发环境适配，都必须能服务 4.1 总体评价标准中的一项或多项，否则不应进入 LDVH 核心体系。

### 4.1 总体评价标准

| 编号 | 标准 | 含义 | 不满足时的表现 |
|---|---|---|---|
| V1 | 快速定位 | AI 能根据当前意图和场景快速定位应读取的事实源、规范入口、任务状态和工具入口 | AI 盲目全文阅读、找不到入口、遗漏关键事实或规则 |
| V2 | 完整理解 | AI 能在足够但不过载的上下文中理解目标、边界、事实、状态和验收标准 | AI 反复询问已有事实、误读项目边界、遗漏关键约束 |
| V3 | 正确判断 | AI 能判断事实源边界、风险、阻塞、工具需求、Skill 进入和子 Agent 调度 | AI 误判任务性质、错过风险或阻塞、错误选择工具、Skill 或子 Agent |
| V4 | 稳定执行 | AI 能依据规范体系、工作模型和工作流程执行任务，而不是凭聊天记忆自由发挥 | AI 绕过规则、跳过任务状态、直接修改不该修改的事实 |
| V5 | 门禁识别 | AI 能识别 Human Gate，知道何时必须暂停并等待人确认 | AI 擅自执行高影响变更、跳过确认、误关闭任务 |
| V6 | 强制验证 | AI 的关键行动、状态变更、事实回写和交付结论能通过辅助工具、检查结果、审查证据或 Human 确认验证；没有验证证据的完成不视为真正完成 | AI 只凭自述判断完成、用“应该通过”“看起来没问题”“逻辑上可行”等表述替代验证，或验证结果缺失、不可复现 |
| V7 | 证据沉淀 | AI 的执行结果能留下可追溯的证据、检查结果、决策或变更记录 | 完成了但无法证明、结果只存在聊天里、后续无法追溯 |
| V8 | 可靠回写 | 稳定事实能按事实源边界回写到 Git 文件事实源 | 事实漂移在聊天、缓存、网页视图、工具输出或派生数据中 |
| V9 | 人类确认质量 | 人能基于事实源、证据和网页视图呈现的项目态势、风险、影响和待确认事项做出高质量确认 | 人只能凭感觉验收，无法看到状态、风险、证据和影响 |
| V10 | 持续完善 | AI 能主动发现问题和改进机会，推动经验回到规范体系、工作模型、工作流程或辅助工具中 | 同类错误反复发生，规则缺口、工具不足和踩坑经验没有沉淀 |

### 4.2 反向判断

出现以下情况时，应认为 LD Vibe Harness 未实现核心价值：

1. AI 无法快速定位应读取的事实源、规范入口、任务状态或工具入口；
2. AI 需要依赖聊天记忆才能继续项目；
3. AI 获得的上下文长期缺失或过载，导致误读边界、遗漏事实或反复询问已有信息；
4. AI 绕过规范、状态、事实源边界或 Human Gate 直接行动；
5. 关键行动、状态变更、事实回写或交付结论缺少可复现验证，或用 AI 自述、推测性表述替代验证；
6. 任务状态、证据、决策或变更无法在 Git 文件事实源中追溯；
7. 网页视图呈现结果与 Git 文件事实源不一致；
8. 人无法基于事实源、证据和网页视图完成排序、决策、确认或验收；
9. 同类失败反复发生且没有进入 Pitfall、specs 规范、工作模型、工作流程或辅助工具。

### 4.3 价值一致性判断标准

新增、升级、停用或重排工作模型、工作流程、机制入口和辅助工具时，应进行价值一致性判断。该判断用于确认拟变更内容是否服务 LDVH 价值实现标准，是否仍符合四类构成要素的分工，是否存在为机制而机制、制造第二事实源、绕过 Human Gate 或偏离 AI 第一服务对象的问题。

价值一致性判断至少应覆盖：

1. 是否有助于 V1 快速定位、V2 完整理解、V3 正确判断、V4 稳定执行、V5 门禁识别、V6 强制验证、V7 证据沉淀、V8 可靠回写、V9 人类确认质量或 V10 持续完善中的一项或多项；
2. 是否明确归属于开发环境、LDVH 辅助工具、LDVH 工作模型或 LDVH 工作流程之一，且未混淆四类构成要素边界；
3. 是否仍以 AI 执行者为第一服务对象；
4. 是否能帮助 AI 快速定位事实源、规范入口、任务状态或工具入口，并获得足够但不过载的最小可行动上下文；
5. 是否包含可复现的强制验证方式，避免只凭 AI 自述、推测性表述或不可复现结果判断完成；
6. 是否避免把工具缓存、网页视图、Agent 输出、Skill 输出或聊天过程当作最终事实源；
7. 是否避免创建无必要的规则、Skill、Agent、工具或对象，导致体系膨胀但不提升可控性；
8. 是否明确需要 Human Gate 的事项，并在确认后再执行关键变更；
9. 是否能沉淀问题、纠偏和改进机会，推动规范体系、工作模型、工作流程或辅助工具持续完善。

价值一致性判断不是独立的落地前决策流程，也不是每个工作模型或工作流程必须重复设置的章节。具体新增、升级、停用或重排规则由对应基础规范、集合索引和 Human Gate 要求约束。

## 5. 运行闭环标准

LDVH 的运行闭环标准由标准运行流程和闭环质量要求共同构成。标准运行流程描述 AI 从意图识别到经验回流的生命周期；闭环质量要求用于判断该生命周期是否真正回到事实源、通过验证、保留证据并接受 Human 判断。

LDVH 的标准运行流程为：

```text
Intent → Plan → Execute → Verify → Record → Learn
```

1. **Intent**：识别 Human 意图、判断事实对象准入、确认是否需要创建或关联 Intent、Task、Memo 或 Profile；
2. **Plan**：拆解执行路径、明确验收标准、识别风险、工具需求、依赖关系和 Human Gate；
3. **Execute**：在规范、事实源边界和受控工具约束下执行变更或推进任务；
4. **Verify**：通过测试、校验、运行结果、审查证据或 Human 确认验证关键行动和交付结论；
5. **Record**：将执行结果、验证证据、决策、变更和状态流转回写到 Git 文件事实源；
6. **Learn**：将反复出现的问题、踩坑经验、规范缺口和工具改进机会回流为 Pitfall、Memo、ADR、规范、Rules、Skill、工具或 Web 改进。

LDVH 不要求所有临时对话都进入完整治理闭环；暂不适合创建 Task 但具有后续价值的讨论、判断或线索，可以先记录为 Memo，待条件成熟后再关联 Intent 或 Task 推进。

下列 5.1-5.5 是对标准运行流程的闭环质量要求，不替代各阶段在 `specs/08-工作流程基础规范.md`、`specs/27-Task-任务.md`、对象规范、Skill 或工具规范中的具体执行规则。

### 5.1 事实源闭环

LD Vibe Harness 的事实源必须回到 Git 可追踪文件。事实源权威性判断、单一事实源原则、承载格式选择和工具输出回写规则，由 `specs/04-事实源边界与承载规范.md` 定义；本文只保留事实源闭环的顶层价值要求。

四类构成要素与事实源的关系：

| 构成要素 | 与事实源的关系 |
|---|---|
| 开发环境 | 提供协作入口，但不成为最终事实源 |
| 辅助工具 | 通过 Code 工具和 Web 工具辅助读取、索引、校验、聚合、展示和受控回写事实源，但不成为最终事实源 |
| 工作模型 | 是项目工作事实的主要结构化承载 |
| 工作流程 | 规定 AI 如何读取、判断和回写事实源 |

YAML 更适合承载任务、状态、结构化关系、审计字段和可解析决策。Markdown 更适合承载背景、原因、解释、需求语境和规范说明。

当一个事实需要高频被 AI 读取、被程序校验或被工具聚合时，应优先考虑结构化承载。

### 5.2 AI 行动闭环

LD Vibe Harness 的协作关系不是“工具替人管理项目”，也不是“AI 凭聊天记忆持续推进”，而是“人、AI、工具围绕 Git 文件事实源形成执行闭环”。

```text
人表达意图、约束或确认
  ↓
AI 依据工作流程识别场景、事实源边界和 Human Gate
  ↓
AI 读取事实源，并判断是否需要工具、Skill 或子 Agent
  ↓
AI 按工作模型和工作流程拆解、执行、检查任务
  ↓
Code 工具辅助解析、校验、聚合和受控写入
  ↓
执行证据、检查结果或决策回到 Git 文件事实源
  ↓
Web 工具展示状态、待确认事项和检查结果，并辅助 Human Gate 与受控轻写入
  ↓
人基于事实源追踪、确认、验收或调整方向
```

这个闭环必须满足：

1. 起点可以来自人的对话输入，但终点必须回到文件事实源；
2. AI 可以依据工作流程调度工具、Skill 或子 Agent，但不能绕过事实源边界和 Human Gate；
3. 工具可以降低维护成本，但不能成为最终事实源；
4. 人可以通过 Web Tools 观察和确认，但关键事实仍以 Git 文件为准；
5. 每次执行都应留下可追溯的任务状态、验证证据、ADR 或检查结果。

### 5.3 人类确认闭环

| 环节 | 人的作用 | AI 的作用 | 工具的作用 |
|---|---|---|---|
| 意图输入 | 表达目标、约束、优先级 | 识别任务场景 | 提供输入入口 |
| 执行前 | 确认高影响变更 | 识别 Human Gate | 展示待确认事项 |
| 执行中 | 校正方向 | 记录证据和风险 | 展示状态和缺口 |
| 执行后 | 验收结果 | 回写事实源 | 聚合证据和检查结果 |

### 5.4 工具辅助闭环

辅助工具不是最终事实源。工具的价值是降低 Human 和 AI 读取、验证、展示和维护事实源的成本，而不是替代事实源。

Code 工具负责提供确定性执行结果和稳定反馈，辅助读取、解析、索引、校验、聚合、测试、构建、格式化和受控写入 Git 文件事实源；Web 工具负责呈现项目态势、对象状态、执行证据、风险和待确认事项，辅助 Human Gate，并在规范授权范围内触发受控轻写入。

Web 工具获取对象状态、字段和验证结果时，应复用 Code 工具的事实源访问、解析、校验和状态判断能力，或至少共享同一契约、测试和校验入口。工具输出、派生视图、运行时索引、页面状态或人工修改标记不得成为任务状态、证据、决策、specs 规范、Rules 或审计结果的最终来源。

### 5.5 防递归建设原则

LD Vibe Harness 处于"用框架完善框架"阶段，必须防止递归死循环：为了完善框架不断要求先补更多框架能力，导致永远无法进入真实使用和产品验证。

1. **框架建设必须服务最近一次可运行闭环**：每次新增规范、Skill、Tools 或对象，都必须说明它服务哪个已定义闭环，不能只服务未来假想能力；
2. **只补当前闭环的最小缺口**：不得因为发现更大体系缺口而扩张当前任务边界；
3. **Dogfood 优先于继续抽象**：当某个闭环具备最小可运行条件时，优先用 LDVH 自身跑一次，而不是继续补规范；
4. **一层抽象后必须落地一次**：每新增一层抽象（规范、对象、Skill、Tools 分类），必须安排一个实例化验证；
5. **连续新增抽象而未 Dogfood 时，应暂停扩张并转入实例验证**。

## 6. 机制落地关系

本文是 LDVH 的理念与纲要文档，主要定义产品定位、价值实现标准、四类构成要素、事实源原则、运行闭环标准和顶层治理边界。本文不直接作为 Rules、Skill、Agent、Tools、Web 或 Contract 的运行时消费对象。

本文对后续正式规范、工作模型、工作流程和机制实体的约束，通过上位依据、引用纪律、价值一致性判断、Human Gate 与文档治理检查实现。后续正式规范的制定、修改和审计，不得违背本文定义的产品定位、价值实现标准、四类构成要素、事实源原则和运行闭环标准。

当本文中的理念、价值标准或构成要素需要转化为 AI 可执行约束、工具校验规则、Web 展示逻辑或对象契约时，应先在对应正式规范中形成可执行规则，再由该规范按 `specs/03-文档规范.md` §6 声明机制落地关系。

具体 specs 修改执行顺序、引用纪律、机制落地关系和文档治理检查，由 `specs/03-文档规范.md` 定义。

## 7. Human Gate 与检查要求

Human Gate 是 Human 对高影响变更的判断权、授权权和责任边界，不是普通偏好选择，也不是 AI 自行推断可以替代的形式步骤。

涉及 LD Vibe Harness 产品定位、价值实现标准、四类构成要素、事实源原则、运行闭环标准、基础规范权威领域、工作模型或工作流程的高影响变更，应评估 Human Gate。

具体文档结构类 Human Gate 由 `specs/03-文档规范.md` 定义；目录规划类 Human Gate 由 `specs/01-目录说明.md` 定义；术语变更类 Human Gate 由 `specs/02-术语规范.md` 定义；事实源边界类 Human Gate 由 `specs/04-事实源边界与承载规范.md` 定义；工作模型和工作流程相关 Human Gate 由对应正式规范定义。

当 AI 识别到可能触发 Human Gate 的情况时，至少必须暂停当前变更动作，向人提醒该操作可能触发 Human Gate，并说明涉及的事实源、影响范围和建议确认事项。在 Human Gate 获得确认前，AI 不得继续执行对应高影响变更，不得以“看起来合理”“符合上下文”“用户大概率会同意”等推测替代确认。

总纲检查至少包括：

| 检查项 | 标准 |
|---|---|
| 产品定位一致性 | 未改变 LD Vibe Harness 面向 Vibe Coding、由规范驱动的 AI 工作 Harness 定位 |
| 理念一致性 | 未改变 LD Vibe Harness 的存在理由、AI 第一服务对象和工程闭环定位 |
| 价值标准一致性 | V1-V10 价值实现标准未被弱化或改写为对象数量、页面数量等替代指标 |
| 构成要素一致性 | 开发环境、辅助工具、工作模型、工作流程四类构成要素及其分工未被混淆 |
| 事实源一致性 | 未将聊天、缓存、工具输出、Web 页面状态、Skill 输出或 Agent 输出作为最终事实源 |
| 运行闭环一致性 | 未弱化 Intent → Plan → Execute → Verify → Record → Learn 的标准运行流程和验证、记录、学习要求 |
| 术语一致性 | 术语使用符合 `specs/02-术语规范.md` |
| 文档治理一致性 | 文档结构、引用纪律、机制落地关系和检查要求符合 `specs/03-文档规范.md` |
| Human Gate | 高影响变更已识别对应 Human Gate，并获得人类确认 |
| 待补齐事项 | 待补齐事项与当前 specs 编号分区和规划状态一致 |
