# 第三方 Skill 使用规范

> 创建日期：2026-06-07
> 定位：定义 LDVH 使用第三方平台 Skill 的准入、边界、治理接管、Human Gate、事实源回写和机制适配要求
> 适用范围：LD Vibe Harness 项目及所有接入 LD Vibe Harness 的管辖项目中，由平台、市场、全局目录、外部生态或非本项目版本化来源提供的第三方 Skill
> 上位依据：`specs/00-LD-Vibe-Harness理念与纲要.md`

## 1. 本文解决的问题

本文定义 LDVH 如何使用第三方平台 Skill。第三方平台 Skill 是开发环境提供或外部生态引入的可复用 AI 能力入口，其能力可能高效，但默认不知道 LDVH 的事实源、工作模型、工作流程、状态机、Human Gate、ADR、Change 和验证纪律。

本文解决以下问题：

1. 第三方平台 Skill 与 LDVH 自建 Skill 的信任边界；
2. 何时允许调用第三方平台 Skill；
3. 第三方平台 Skill 产出物如何被 LDVH 接管；
4. 第三方平台 Skill 不得绕过哪些 LDVH 治理机制；
5. 何时需要将第三方平台 Skill 的使用经验沉淀为 LDVH 自建 Skill、Rules 摘要、Tools 辅助或正式规范。

本文不重新定义 Trae Skill 的平台行为、文件格式、安装方式或官方最佳实践。Trae Skill 的平台客观能力以 `specs/05-Trae-Solo环境规范.md` 声明的平台事实为准。本文只定义 LDVH 如何治理第三方平台 Skill 的使用。

## 2. 与 00 总纲的关系

00 总纲定义 LDVH 以 AI 执行者为第一服务对象，依托开发环境、辅助工具、工作模型和工作流程，为 AI 提供清晰目标、明确边界、稳定事实、可见状态、具体验收标准和可用工具入口。

第三方平台 Skill 属于开发环境中的能力供给入口，不是 LDVH 权威事实源。LDVH 可以利用第三方平台 Skill 提升脚手架、生成、审查、调研或专项操作效率，但必须把第三方平台 Skill 的过程输出纳入 Git 文件事实源、工作模型、工作流程、Human Gate 和验证纪律。

因此，第三方平台 Skill 在 LDVH 中的基本定位是：

```text
第三方平台 Skill 提供能力；LDVH 提供治理。
```

第三方平台 Skill 的输出只有在按事实源边界写入对应权威位置、通过必要 Human Gate、完成必要验证并可被 Git 追溯后，才成为 LDVH 稳定事实。

## 3. 术语与分类

### 3.1 第三方平台 Skill

第三方平台 Skill 指不由当前 LDVH 项目或管辖项目在项目 Git 仓库内版本化维护，且由平台、市场、全局目录、外部生态、用户导入包或运行时注入提供的 Skill 能力。

典型来源包括：

1. Trae 平台预置 Skill；
2. Trae Skill 市场或全局 Skill；
3. 外部 Agent Skills 生态导入的 Skill；
4. 用户从其他项目复制但尚未纳入当前项目治理的 Skill；
5. 平台运行时提供、当前仓库不可审计其完整实现的 Skill。

### 3.2 LDVH 自建 Skill

LDVH 自建 Skill 指由 LDVH 项目或管辖项目在 Git 文件事实源中版本化维护，用于承接 Core Loop、工作模型、工作流程或受控写入流程的 Skill。

LDVH 自建 Skill 的行为边界必须能从 specs、ADR、工作区规则、项目规则和对应 Skill 文件推理出来。LDVH 自建 Skill 不是事实源本身，只是稳定流程入口。

### 3.3 包装 Skill

包装 Skill 指 LDVH 为某类第三方平台 Skill 建立的自建 Skill 入口。包装 Skill 不复制第三方平台 Skill 的能力说明，而是负责：

1. 判断是否允许调用第三方平台 Skill；
2. 装配 LDVH 必要上下文；
3. 声明 Human Gate 停止点；
4. 定义第三方平台 Skill 产出后的治理接管检查；
5. 规定事实源回写、验证和 Change 记录要求。

包装 Skill 只有在某类第三方平台 Skill 使用频率高、输入输出稳定、接管检查重复出现且已有 Dogfood 证据时，才应创建。

## 4. 信任边界

### 4.1 基本信任分层

第三方平台 Skill 与 LDVH 自建 Skill 的信任分层如下：

| 维度 | LDVH 自建 Skill | 第三方平台 Skill |
|---|---|---|
| 来源 | 当前项目或 LDVH 工作区版本化维护 | 平台、市场、全局目录、外部生态或运行时注入 |
| 约束感知 | 应感知 LDVH 事实源、状态机、Human Gate 和回写要求 | 默认不感知 LDVH 约束 |
| 审计能力 | 可通过 Git、specs、Rules、ADR 和 Skill 文件追溯 | 只能审计调用结果，通常无法审计完整内部行为 |
| 适用角色 | 稳定流程入口、受控写入编排、Core Loop 阶段承接 | 能力供给、脚手架生成、专项辅助、候选产物生成 |
| 事实源地位 | 不是事实源，但可由 specs 推导其流程 | 不是事实源，输出必须被接管后才可稳定化 |

第三方平台 Skill 不得被视为 LDVH 规则、决策或事实源的权威来源。第三方平台 Skill 的输出是待审计输入，不是可直接采信的稳定事实。

### 4.2 能力供给方与治理约束方

第三方平台 Skill 是能力供给方，LDVH 是治理约束方。AI 调用第三方平台 Skill 时，必须保持以下判断：

1. 能力强不等于可信度高；
2. 生成结果正确不等于治理合规；
3. 平台自动调用不等于 LDVH 授权；
4. Skill 输出不等于事实源写入；
5. 外部 Skill 的最佳实践不替代 LDVH 的 Human Gate、状态机、验证和 Change 纪律。

### 4.3 约束逃逸风险

第三方平台 Skill 使用中的主要风险不是单纯代码质量，而是约束逃逸。以下情况必须视为高风险：

1. 第三方平台 Skill 直接读写 `ldvh-base/`；
2. 第三方平台 Skill 修改 specs、Rules、Tools、工作模型、工作流程或状态机边界；
3. 第三方平台 Skill 生成绕过 Human Gate 的 UI、脚本或自动化流程；
4. 第三方平台 Skill 生成直接修改事实状态、ADR 状态或 Task 状态的逻辑；
5. 第三方平台 Skill 引入不可追溯的缓存、数据库或外部服务作为权威事实源；
6. 第三方平台 Skill 自动执行安装、发布、提交、推送、删除或远程控制等高风险操作。

出现上述情况时，AI 必须暂停并回到 LDVH 工作流程、Human Gate 和事实源边界处理。

## 5. 准入与禁止场景

### 5.1 允许使用场景

第三方平台 Skill 可用于以下场景：

1. 从空目录生成脚手架、初始页面、基础 UI 或样例结构；
2. 生成候选代码、候选文案、候选测试、候选配置或候选设计稿；
3. 在不写入权威事实源的前提下提供专项分析、格式转换或结构化建议；
4. 辅助理解外部技术、第三方库或平台功能；
5. 对非权威资料进行初步整理，供 AI 后续按 LDVH 事实源纪律审查；
6. 在包装 Skill 或当前 Task 明确授权下，执行边界清晰、可验证、可回滚的局部生成任务。

### 5.2 禁止使用场景

第三方平台 Skill 不得直接用于以下场景：

1. 创建、修改、删除或迁移 `ldvh-base/` 事实实例；
2. 执行 ADR 创建、接受、拒绝、废弃、替代或升级；
3. 直接修改 Task 状态、Intent 状态、对象字段契约或状态机；
4. 直接修改工作区规则、项目规则或 specs 正式规范中的稳定规则正文；
5. 代替 Human Gate 作出确认、授权、验收或关键决策；
6. 自动提交、自动推送、自动发布或自动删除项目事实源；
7. 绕过 PyTools、Web 信息同步层或受控写入入口操作权威事实源；
8. 生成或持久化不可追溯的权威状态。

如确需在上述领域借助第三方平台 Skill 的能力，只能让其生成候选材料，并由 LDVH 主控 AI 按对应规范、Human Gate、Tools 校验和事实源回写流程接管。

### 5.3 脚手架优先原则

第三方平台 Skill 的默认安全用法是脚手架先行：

```text
脚手架生成 → 治理接管 → 审计改造 → 持续开发
```

第三方平台 Skill 可负责从零搭建项目骨架、生成初始代码结构、配置构建工具链或建立基础 UI 框架。脚手架完成后，后续持续开发必须回到 LDVH Core Loop、Task 状态机、Human Gate、验证和 Change 纪律。

脚手架产出物应被视为待审计的外部贡献，而不是已完成的受控实现。

### 5.4 持续开发限制

同一第三方平台 Skill 不得在没有治理接管的情况下持续参与同一项目的多轮核心开发。若某类第三方平台 Skill 已经成为持续开发依赖，AI 必须评估是否满足以下任一处理条件：

1. 将重复接管流程写入当前工作流程或 Task 验收标准；
2. 创建包装 Skill 承接接管检查；
3. 将稳定硬约束回写到 specs 或 Rules 摘要；
4. 将确定性检查沉淀为 PyTools 或测试；
5. 通过 ADR 记录长期采用、限制或废弃的决策。

## 6. 标准使用流程

### 6.1 调用前判断

AI 准备使用第三方平台 Skill 前，应完成以下判断：

1. 当前任务是否已有 Task、Plan 或明确验收标准；
2. 第三方平台 Skill 是否只是提供候选产物，而不是替代 LDVH 决策；
3. 产出物是否可能影响 specs、Rules、Tools、Web、`ldvh-base/` 或其他 Git 文件事实源；
4. 是否存在 Human Gate、高风险操作或授权需求；
5. 是否有可运行的验证方式；
6. 是否需要先读取对应项目规则、规范原文或 ADR。

若判断结果不清晰，AI 不得让第三方平台 Skill 直接执行写入或破坏性操作，应先向人类确认或退回 LDVH Plan 阶段。

### 6.2 调用中约束

调用第三方平台 Skill 时，AI 应限制其输入范围：

1. 只提供完成候选产物所需的最小上下文；
2. 不提供密钥、令牌、隐私数据或无关项目资料；
3. 明确禁止其直接操作权威事实源；
4. 明确产出物必须等待 LDVH 主控 AI 审查后才能接管；
5. 对可能产生文件变更的第三方平台 Skill，先确认其输出目录和影响范围。

若第三方平台 Skill 在执行中尝试扩大范围、请求危险权限或产生不符合 LDVH 事实源边界的操作，AI 必须停止使用并回到 Human Gate。

### 6.3 治理接管点

第三方平台 Skill 完成产出后，立即进入治理接管点。治理接管点是 LDVH 对第三方平台 Skill 输出重新取得控制权的固定里程碑。

治理接管点必须完成：

1. 明确产出文件、变更范围和未完成事项；
2. 判断是否涉及权威事实源；
3. 检查是否引入直接读写事实源、绕过 Human Gate 或绕过状态机的逻辑；
4. 运行可用的 lint、typecheck、test、build、Fact Validator 或项目特定校验；
5. 将稳定结论、任务证据、规范变更或决策回写到对应事实源；
6. 按 Change 纪律准备提交信息或变更证据。

### 6.4 持续开发接管

治理接管点之后，第三方平台 Skill 不再主导持续开发。后续工作必须按 LDVH 正常流程执行：

1. 新目标进入 Intent 或 Task；
2. 执行前进入 Plan 或等价计划；
3. 规范、事实源、Tools、Web 或状态机变更按对应规范执行；
4. 高风险节点触发 Human Gate；
5. 完成后进入 Verify、Record 和 Learn。

## 7. 治理接管检查清单

第三方平台 Skill 产出物进入项目后，AI 应按以下检查清单审计。

### 7.1 事实源检查

1. 是否直接读写 `ldvh-base/`；
2. 是否把缓存、数据库、浏览器状态、运行时索引或外部服务当作权威事实源；
3. 是否修改 specs、Rules、ADR、Task、Intent、Change 或 Pitfall；
4. 是否存在未记录来源的稳定结论；
5. 是否需要通过 PyTools、Web 信息同步层或受控写入入口改造。

### 7.2 状态机与对象规则检查

1. 是否直接修改对象状态字段；
2. 是否绕过合法状态流转；
3. 是否新增对象字段、目录或状态而未同步对象规范；
4. 是否把派生视图当作对象实例；
5. 是否需要更新 Task、ADR 或其他工作模型的关联字段。

### 7.3 Human Gate 检查

1. 是否包含删除、迁移、重命名、发布、提交、推送、安装或远程控制等高风险操作；
2. 是否触发事实源创建、关键状态流转、ADR 写入、规范升级或高风险变更；
3. 是否需要人类确认需求范围、授权范围、验收标准或接管结果；
4. 是否在 UI 或脚本中提供绕过确认的路径。

### 7.4 安全与供应链检查

1. 是否引入新的依赖、脚本、远程服务或外部执行入口；
2. 是否记录或输出密钥、令牌、隐私数据或本地敏感路径；
3. 是否包含自动更新、遥测、远程控制、自动发布或后台任务；
4. 是否存在不可解释的混淆代码、下载执行或权限扩大；
5. 是否需要锁定依赖版本、补充安全说明或移除不必要能力。

### 7.5 验证检查

1. 是否存在项目既有 lint、typecheck、test、build 或格式检查命令；
2. 是否需要运行 Fact Validator 或对象级校验；
3. 是否需要真实页面、CLI、安装或端到端验证；
4. 验证失败是否已回到 Task、Pitfall、ADR 或后续子任务处理；
5. 验证结果是否可追溯到命令输出、文件变更或 Git 事实源。

## 8. 包装 Skill 策略

### 8.1 直接使用

在以下情况下，可以直接使用第三方平台 Skill，并由当前 Task 承担接管检查：

1. 首次试用或低频使用；
2. 产出物主要是脚手架或候选材料；
3. 不涉及权威事实源直接写入；
4. 接管检查可以在当前 Task 内完成；
5. 尚无足够 Dogfood 证据证明需要标准化包装。

直接使用时，Task 的验收标准应包含治理接管、验证和事实源回写检查项。

### 8.2 包装 Skill 准入

当满足以下条件时，应考虑创建 LDVH 包装 Skill：

1. 同类第三方平台 Skill 被反复用于相似场景；
2. 调用前上下文装配、调用中限制和调用后接管检查稳定；
3. 多次出现遗漏 Human Gate、事实源边界或验证步骤的风险；
4. 使用经验已通过 Task、Pitfall、ADR 或规范变更沉淀；
5. 包装后能显著降低 AI 执行摩擦，而不是增加抽象负担。

包装 Skill 的创建必须按 Skill 创建流程、项目规则和 Human Gate 执行。包装 Skill 仍不得替代 specs 正式规范、Rules 入口或 Tools 确定性校验。

### 8.3 包装 Skill 职责边界

包装 Skill 应负责流程编排，不应负责以下内容：

1. 复制第三方平台 Skill 的完整教程或实现细节；
2. 重新定义 Trae Skill 平台行为；
3. 维护稳定规则正文；
4. 直接作出 Human Gate 决策；
5. 绕过 PyTools 或对象规范执行事实源写入；
6. 在没有 Task、Plan 或明确验收标准时扩大任务范围。

### 8.4 废弃与降级

如果第三方平台 Skill 接口不稳定、输出不可控、频繁触发治理接管失败或引入高风险依赖，AI 应评估以下处理：

1. 降级为仅生成候选材料；
2. 暂停使用并创建 Pitfall 或 Task；
3. 改为 LDVH 自建 Skill 或 PyTools；
4. 创建 ADR 记录长期废弃、替代或限制使用决策。

## 9. 机制落地关系

| 关联机制 | 关联实体 | 关系类型 | 触发条件 |
|---|---|---|---|
| specs | `specs/13-第三方Skill使用规范.md` | 权威规范 | 第三方平台 Skill 使用边界、接管流程或包装策略发生稳定变化 |
| Rules | 工作区规则或项目规则 | 入口摘要 | AI 高频遗漏第三方平台 Skill 治理接管或 Human Gate 时 |
| Skill | LDVH 自建 Skill | 流程入口 | Dogfood 证据显示直接使用反复遗漏接管检查 |
| Agent | 独立上下文 Agent | 隔离审计 | 第三方平台 Skill 产出物规模大、风险高或需要独立审查 |
| Tools | PyTools | 确定性校验 | 检查项稳定且适合确定性处理 |
| Web | Web 工作台 | Human 协同 | 需要人类确认、验收或可视化接管工作台 |
| ADR | ADR 对象 | 长期决策 | 判断影响长期执行方式、协作边界或多个机制 |
| Change | Change 记录或 Git commit | 变更记录 | 修改满足 Change 准入条件时 |

## 10. Human Gate 与检查要求

### 10.1 必须触发 Human Gate 的场景

第三方平台 Skill 使用中出现以下情况，必须暂停并请求人类确认：

1. 创建、修改、删除、迁移或重命名 facts、specs、Rules、Skill、Tools、Web 或其他权威事实源；
2. 触发 ADR 写入、ADR 状态流转或规范升级；
3. 执行删除、安装、发布、提交、推送、远程控制、权限授权或不可逆操作；
4. 第三方平台 Skill 的产出物将成为持续开发基础；
5. 第三方平台 Skill 需要访问敏感信息、外部账号、网络服务或本地私有路径；
6. 第三方平台 Skill 的行为边界、输出范围或验证方式无法判断。

### 10.2 调用前检查

AI 调用第三方平台 Skill 前应检查：

1. 是否已读取当前项目规则；
2. 是否已有 Task 或明确验收标准；
3. 是否明确第三方平台 Skill 的使用目的和输出范围；
4. 是否知道接管点和验证方式；
5. 是否存在必须先 Human Gate 的风险。

### 10.3 接管后检查

AI 接管第三方平台 Skill 产出后应检查：

1. 产出物是否与 Task acceptance 对齐；
2. 是否违反事实源边界、对象状态机、Human Gate 或工具协作边界；
3. 是否需要同步 specs、Rules、Skill、Tools、Web 或测试；
4. 是否完成必要 lint、typecheck、test、build、Fact Validator 或真实交互验证；
5. 是否记录 Change、Task closure evidence、Pitfall 或 ADR。
