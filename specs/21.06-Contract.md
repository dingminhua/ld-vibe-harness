## 一、本文定位

本文定义 ADR 事实模型使用的结构化数据契约。本文解决 ADR YAML 实例应包含哪些字段、字段类型和约束是什么、文件命名规则是什么、状态流转契约是什么，以及工具实现应如何消费本契约的问题。

本文是 ADR 事实模型契约字段的权威位置。本文是 `specs/21-ADR-决策记录.md` 的附件型契约子文档，不是独立事实模型。本文不得重新定义 ADR 的对象定位、准入条件、状态机语义、Human Gate、事实源回写或证据留存要求。发生冲突时，以 21 主文档和上位基础规范为准。

本文不承载执行逻辑、流程步骤或 Human Gate 条款（依据 `specs/04-LDVH模型子文档规范.md` §7.1）。

## 二、ADR YAML Schema

### 2.1 基础字段

ADR 基础字段遵循 `specs/13-LDVH事实模型基础规范.md` §7.3 的字段契约原则，所有事实模型应包含基础字段。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | ADR 对象 ID，格式为 `adr-{NNNN}` |
| `type` | string | 是 | 固定为 `adr` |
| `title` | string | 是 | 决策标题 |
| `status` | string | 是 | ADR 状态，必须属于标准状态枚举 |
| `created` | date | 是 | 对象创建日期 |
| `updated` | date | 是 | 最近更新日期 |

### 2.2 扩展字段

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `date` | date | 是 | 决策日期 |
| `context` | string | 是 | 决策背景 |
| `decision` | string | 是 | 决策内容 |
| `consequences` | string | 是 | 决策后果 |
| `alternatives` | string | 否 | 考虑过但未采纳的替代方案 |
| `affects` | list of string | 否 | 影响范围列表 |
| `related_objects` | list of string | 否 | 关联事实模型 ID 列表 |
| `related_rules` | list of string | 否 | 关联的 specs 或 Rules 文件列表 |
| `superseded_by` | string | 条件必填 | 仅当 `status` 为 `superseded` 时必须填写，指向替代本决策的新 ADR ID |

### 2.3 完整 YAML 示例

```yaml
id: adr-0001
type: adr
title: 使用 YAML 作为 ADR 承载格式
status: accepted
created: 2026-06-01
updated: 2026-06-01
date: 2026-06-01
context: ADR 需要结构化承载决策背景、内容和后果，同时保持 Git 可追溯和工具可解析。
decision: 采用 YAML 格式承载 ADR 实例，存放在 ldvh-base/adrs/ 目录下。
consequences: 所有 ADR 实例统一使用 YAML 格式，工具可按 schema 解析和校验。
alternatives: Markdown 格式更易阅读但不易结构化解析；JSON 格式不支持注释。
affects:
  - ldvh-base/adrs/
  - specs/21-ADR-决策记录.md
related_objects:
  - memo-0001
related_rules:
  - specs/13-LDVH事实模型基础规范.md
```

## 三、字段约束

1. `status` 必须属于 ADR 标准状态枚举：`proposed`、`accepted`、`deprecated`、`superseded`、`rejected`；
2. `type` 必须固定为 `adr`；
3. `superseded_by` 仅在 `status: superseded` 时必填，其他状态下不得填写；
4. `related_objects` 应引用已存在的事实模型 ID，引用无效时应标记为校验警告；
5. `related_rules` 应引用已存在的 specs 或 Rules 文件路径，引用无效时应标记为校验警告；
6. `id` 格式必须为 `adr-{NNNN}`，编号固定 4 位，从 `0001` 起递增；
7. `created` 和 `updated` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
8. `date` 使用 ISO 8601 日期格式（`YYYY-MM-DD`）；
9. `affects`、`related_objects`、`related_rules` 为列表类型，可为空列表，不得省略字段后以 null 替代空列表。

---

## 四、文件命名契约

ADR 实例文件命名规则：

```text
adr-{NNNN}-short-title.yaml
```

约束：

1. 编号从 `0001` 起递增，固定 4 位；
2. 英文短标题使用小写短横线命名；
3. 每个项目独立编号，不使用跨项目全局编号；
4. 文件存放位置为 `ldvh-base/adrs/`；
5. 文件名变化必须同步检查所有引用该 ADR 的 `related_objects`、`superseded_by` 和其他关联字段。

## 五、状态流转契约

### 5.1 标准状态枚举

| 标准状态 | 含义 |
|---|---|
| `proposed` | 已提出，尚未确认 |
| `accepted` | 已确认，后续应遵守 |
| `deprecated` | 已废弃，不再建议遵守，但保留历史 |
| `superseded` | 已被新 ADR 替代 |
| `rejected` | 已否决，不采纳 |

### 5.2 合法状态流转

```text
proposed → accepted, rejected
accepted → deprecated, superseded
deprecated → 无
superseded → 无
rejected → 无
```

约束：

1. 未在上述规则中列出的流转为非法流转，工具应拒绝执行；
2. `deprecated`、`superseded` 和 `rejected` 是稳定终态，终态 ADR 不得重开；
3. 如需对已终态的决策重新判断，必须新建 ADR，并在新 ADR 中引用原 ADR；
4. `proposed` 状态的 ADR 不应作为执行依据；
5. `accepted → superseded` 时，必须同时填写 `superseded_by` 字段指向新 ADR ID。

## 六、契约消费声明

1. Tools 辅助程序解析 ADR 时应依据本文定义的 YAML schema 和字段约束，不得自行扩张格式契约（依据 `specs/12.01-Tools辅助规范.md` §6.1.3）；
2. Tools 辅助程序校验 ADR 时应覆盖字段完整性、状态合法性、条件必填和引用有效性；
3. Tools 辅助程序读取 ADR 时可依据本文状态枚举和字段契约执行状态筛选、详情解析和关联字段解析，但 ADR 读取结果是否可作为当前执行依据由 21 主文档和 Skill 流程判断；
4. 实践子文档和工具可以消费本文契约，但不得复制维护契约字段第二事实源（依据 `specs/04-LDVH模型子文档规范.md` §7.2）；
5. 修改本文契约属于规范变更，应评估 Human Gate 并记录 Change（依据 `specs/04-LDVH模型子文档规范.md` §7.3）；
6. 契约子文档应先于工具实现创建，工具实现不得在没有契约子文档的情况下自行定义字段名、字段类型或字段约束（依据 `specs/04-LDVH模型子文档规范.md` §7.4）；
7. 本文契约变更时，消费本文的 Tools 实现和对应测试必须同步更新（依据 `specs/04-LDVH模型子文档规范.md` §7.4、§八）。

## 七、检查项

检查本文是否被正确使用时，应确认：

1. ADR YAML 实例字段是否完整，必填字段是否齐全；
2. `status` 是否属于标准状态枚举；
3. `type` 是否固定为 `adr`；
4. `superseded` 状态的 ADR 是否已填写 `superseded_by` 字段；
5. `related_objects` 引用的事实模型 ID 是否有效；
6. `related_rules` 引用的 specs 或 Rules 文件路径是否有效；
7. 文件命名是否符合 `adr-{NNNN}-short-title.yaml` 格式；
8. 状态流转是否合法，是否存在非法流转；
9. 终态 ADR 是否存在重开情况；
10. 工具实现是否依据本文 schema 解析和校验，未自行扩张格式契约；
11. 工具只读查询是否只依据本文契约解析状态和字段，未自行判断 ADR 读取结果是否可作为执行依据；
12. 修改本文是否记录 Change，并在必要时触发 Human Gate。
