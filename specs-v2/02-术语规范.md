> 创建日期：2026-06-08

> 适用范围：LDVH `specs-v2/` 正式规范、evals、refs、管辖项目文档、工作对象、Code、Web、环境适配映射和运行投影中的术语使用

## 1. 本文解决的问题

本文解决 LDVH v2 中术语应如何命名、解释、引用和变更的问题。

术语规范的目标不是复制各专项规范的规则正文，而是让 AI 和 Human 在阅读、编写、迁移和执行 LDVH 文档时，能够稳定区分项目、工作区、规范、旧规范迁移、索引文档、规范落地、环境适配、运行投影、构成要素、环境能力、初始化、审计和检查等概念。

---
## 2. 与 00 总纲的关系

00 定义 LDVH 的产品定位、五类构成要素、事实源原则、运行闭环标准和 Human Gate 原则。本文承接 00 的术语一致性要求，为后续正式规范、工作模型、工作流程、Code、Web 和环境适配提供统一术语边界。

本文是 LDVH v2 术语定义和术语变更治理的权威位置。00 只保留术语一致性的上位要求；01、03、04、14 以及后续工作模型和工作流程规范可以说明术语在本规范中的应用规则，但不得并行维护同一术语的权威定义。

---
## 3. 术语归口规则

术语定义应归口到本文。其他规范可以使用术语、引用术语，或说明某个术语在本规范场景中的应用规则，但不得重复定义同一术语。

分工如下：

| 文档 | 负责内容 | 不负责内容 |
|---|---|---|
| 本文 | 术语名称、术语边界、推荐用法、旧称处理、术语变更治理 | 具体执行流程、字段契约、环境映射细则 |
| `specs-v2/01-目录说明.md` | 目录和编号分区规则 | 术语权威定义 |
| `specs-v2/03-文档基础规范.md` | 文档结构、引用、evals/refs、吸收和文档治理规则 | 术语权威定义 |
| `specs-v2/04-规范落地与环境适配基础规范.md` | 规范落地、环境适配、运行投影和环境能力的应用规则 | 术语权威定义 |
| `specs-v2/14-Code实现规范.md` | Code 需求、实现、验证和维护规则 | Code、工具、脚本等术语权威定义 |

若某个专项规范已经存在基本概念章节，应在本文迁入后改为引用本文术语，并保留该术语在本规范内的应用关系。

## 4. 项目、工作区与文档分区术语

| 术语 | 定义 | 边界 |
|---|---|---|
| LDVH 自身项目 | 承载和维护 LDVH 规范体系、Code、Web 和 dogfood 事实实例的项目 | 当前项目使用 `specs-v2/` 作为 v2 规范事实源 |
| 管辖项目 | 安装并使用 LDVH 进行需求、任务、证据、变更、审计或交付治理的用户项目 | 管辖项目不默认创建 `specs-v2/` 或 `specs/`，使用 `docs/` 承载项目文档 |
| 规范文档工作区 | 承载 LDVH v2 规范、内部评估和外部引用的文档工作区 | 在 LDVH 自身项目中为 `specs-v2/` |
| 管辖项目文档工作区 | 承载管辖项目正文、内部分析和外部引用的文档工作区 | 在管辖项目中为 `docs/` |
| 正文区 | 文档工作区中承载稳定正文的根层级 | `evals/` 和 `refs/` 不属于正文区 |
| evals | 内部评估、方案分析、迁移评估或内部调研区 | 不直接构成正式规范，结论需要吸收到正文区或工作对象后生效 |
| refs | 外部引用、第三方资料、官方文档摘录或引用副本区 | 不直接构成正式规范，不反向维护正文区规则 |

## 5. 规范体系与旧规范迁移术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 正式规范 | `specs-v2/` 正文区中定义稳定规则、对象边界、流程要求、Code 要求、Web 要求、环境适配要求或检查要求的规范文档 | 正式规范应遵守 03 的文档骨架，并按 04.01 判断规范落地要求 |
| 旧规范 | v2 重建前位于旧 `specs/` 中的规范、机制文件、evals、refs 或特别说明 | 旧规范不自动构成 v2 权威规范 |
| 旧规范迁移 | 将旧 `specs/` 内容吸收、重写、废止、保留为迁移素材或登记为待迁移事项的过程 | 不建议使用“历史迁移”指代该过程 |
| 迁移素材库 | v2 重建期间供 AI 查阅、比较和吸收的旧资料集合 | 旧 `specs/` 是迁移素材库，不是 v2 权威事实源 |
| 待迁移事项 | 尚未迁入 v2，但需要后续讨论、吸收、废止或保留的事项 | 待迁移事项不得被当作已经生效的规则执行 |
| 迁移期临时内容 | 为了帮助旧规范吸收、术语替换或旧称识别而临时保留的说明、对照表或历史引用记录 | 迁移完成后应删除、收敛或转入对应正式规范 |

## 6. 索引文档术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 索引文档 | 用于定位编号区段、文档集合、迁移范围、状态清单或输入清单的文档 | 不替代对应基础规范或具体规范 |
| 说明性索引 | 只帮助查找文档、迁移状态、章节或资料，不定义稳定治理规则的索引文档 | 不默认属于正式规范 |
| 规范型集合索引 | 维护正式编号区段或规范集合的清单、状态、编号占用、关系、初始化输入、审计输入或 Human Gate 规则的索引文档 | 属于正式规范，规则由 `specs-v2/03.03-索引文档规范.md` 定义 |

## 7. 规范落地与环境适配术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 规范落地要求 | 一条稳定规范要落地需要满足的要求 | 不等于 Rules、Skill、Agent、Hook、CI、命令、工具文件或 Web 页面 |
| 保障机制 | 保障某项规范落地要求被执行、检查、复用、触发或确认的规则、流程、Code、Human Gate、子 Agent 思考、生命周期触发或审计动作 | 必须与规范落地要求绑定；无法保障时应记录降级方式 |
| 环境适配映射 | 某项规范落地要求和保障机制在特定开发环境中如何实现、验证和降级的映射关系 | 不得反向改写正式规范 |
| 运行投影 | 环境适配映射后实际存在、维护或调用的入口、文件、命令、配置、工具、页面、Skill、Agent、Hook、CI 检查、摘要或降级记录 | 不是最终事实源 |
| 环境 | AI 和 Human 实际执行工作的工具、平台或运行面 | 可以包括 Codex、Trae、Claude Code、Cursor、CI、Web 工作台、命令行等 |
| 环境实体 | 具体环境中可被定位、配置、调用或维护的文件、规则、Skill、Agent、Hook、命令、页面、CI 配置或平台入口 | 只能作为环境适配映射或运行投影的一部分 |
| 环境能力 | 具体环境中可被 LDVH 用来承接规范落地要求的入口、机制、工具或运行面 | 能力边界由 `specs-v2/04.04-环境能力承接边界.md` 规定 |
| 漂移 | 运行投影、环境映射或自动触发方式与 specs-v2 正式规范不一致，或规范已变更但运行投影未同步 | 漂移检查结果不是最终事实源，稳定结论需要回写 |
| 降级方式 | 环境能力不足、运行投影缺失或稳定触发无法保证时，记录的替代检查、人工确认、后续任务或残留风险处理方式 | 不得用于降低正式规范要求 |

规范落地要求类型包括上位约束承接要求、入口可见要求、流程复用要求、子 Agent 思考要求、确定性执行要求、Human 交互要求和生命周期触发要求。各类型的规则以 `specs-v2/04.01-规范落地要求规范.md` 为准。

## 8. 构成要素与环境能力术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 开发环境 | LDVH 五类构成要素之一，提供 AI 与 Human 实际执行工作的环境能力 | 不是最终事实源 |
| 工作模型 | LDVH 五类构成要素之一，用于承载项目工作事实、对象字段、状态和验收规则 | 通用规则待 07 工作模型基础规范迁入 |
| 工作流程 | LDVH 五类构成要素之一，用于约束 AI 如何识别场景、读取事实、执行、验证、回写和暂停 | 通用规则待 08 工作流程基础规范迁入 |
| Code | LDVH 五类构成要素之一，用于确定性执行、解析、校验、聚合、测试、上下文压缩和受控写入 | 工具、脚本、校验器和命令入口都是 Code 的实现形态 |
| Web | LDVH 五类构成要素之一，用于 Human-facing 展示、确认、授权、验收和受控轻写入 | Web 页面状态不是最终事实源 |
| Rules / Instructions | 环境中用于入口可见、硬约束摘要、事实源边界提示或项目入口提示的能力或实体 | 只是运行投影，不是最终规范事实源 |
| Skill | 环境中用于复用多步骤流程、标准化输入输出或受控检查步骤的能力或实体 | 不负责调度子 Agent；需要稳定触发时应组合 Hook、CI、自动运行或降级检查 |
| Agent | 环境中用于独立上下文、专项视角、并行审查或权限边界差异的能力或实体 | Agent 输出必须回到主控或 Human，稳定结论回写后才生效 |
| Hook / 自动触发 | 环境中用于生命周期事件触发、提醒、阻断、记录或自动检查的能力或实体 | 不定义规范正文或工作流程本身 |

Tools 和 PyTools 不作为 v2 核心构成要素或独立机制术语。需要指向具体实现时，优先使用 Code、工具、脚本、校验器、命令入口或 `tools/` 目录实现。

## 9. 工作流程、运行闭环、初始化、审计与检查术语

| 术语 | 定义 | 边界 |
|---|---|---|
| 运行闭环 | LDVH 从 Intent、Plan、Execute、Verify、Record 到 Learn 的端到端质量闭环 | 不等同于单个工作流程 |
| 工作流程 | 单一行动或行动族的执行规范，约束 Context、Scenario、Gate、执行、验证、回写和暂停 | 工作流程是运行闭环的组成单元 |
| Scenario 识别条件 | 工作流程用于判断某个行动是否进入的场景条件 | 不应由 Rules / Instructions 维护完整正文 |
| Gate | 工作流程中的暂停、进入、退出、确认或授权条件 | Human Gate 是高影响场景中的人类确认机制 |
| 产品初始化 | 将 LDVH 规范体系真正转化为项目可用实践的落地环节 | 详细流程待后续工作流程迁入；不得被环境初始化替代 |
| 环境初始化 | 为某个项目和开发平台完成环境能力核验、环境适配映射、运行投影准备和降级记录的初始化准备 | 只是产品初始化的前置准备或组成部分，不等同于产品初始化 |
| 当前环境初始化记录 | 项目根目录 LDVH-ENVIRONMENT-INITIALIZATION.md，记录当前项目环境适配、运行投影、能力核验和降级方式 | 不是 specs-v2 正式规范，不替代产品初始化 |
| 产品审计 | 对已经完成或声称完成的产品初始化结果进行审查，确认实践是否真实存在、持续有效、未漂移且未绕过 Human Gate | 可以使用检查作为手段，但不等同于检查 |
| 检查 | 依据规范、工作对象、工作流程或 Code 契约，对文档、实例、行动、输出或运行投影进行符合性判断 | 检查结果不是最终事实源，稳定结论需要回写 |

旧称“工作闭环”不作为 v2 推荐术语；除引用旧规范外，优先使用“运行闭环”。

## 10. 中文术语定语规则

中文“规则”“技能”“代理”“智能体”“工具”“程序”“展示”“机制”等词不得裸用，除非上下文已经通过标题、表格字段或段落首句明确限定其语义。

推荐用法如下：

| 场景 | 推荐用语 | 避免裸用 |
|---|---|---|
| specs-v2 中的稳定条款 | 正式规范、规范规则、规范要求 | 规则 |
| 工作模型字段、状态、验收、检查 | 字段规则、状态规则、验收规则、对象检查 | 规则 |
| 工作流程 Context、Scenario、Gate、执行、回写、证据 | 行动规则、Scenario 识别条件、Gate 条件、回写要求 | 规则、触发规则 |
| 环境入口约束 | Rules / Instructions 入口、入口摘要、硬约束摘要 | 规则 |
| 普通能力说明 | 能力、功能、流程、方法 | 技能 |
| AI 泛称 | AI 执行者、AI 代理能力、子 Agent | 代理、智能体 |
| 确定性实现 | Code 实现、工具、脚本、校验器、命令入口 | 程序 |
| Web 能力 | Web、Human-facing 页面、信息同步、受控交互 | 展示 |
| 环境适配 | 环境能力、环境实体、运行投影 | 机制 |

## 11. 旧称与迁移期临时对照

本节是迁移期临时内容，用于帮助 AI 识别旧规范、旧称和历史引用记录。旧规范迁移完成后，本节应删除、收敛或转入对应正式规范，不应长期作为正文术语表保留。

| 旧称或旧写法 | v2 推荐处理 | 说明 |
|---|---|---|
| 历史迁移 | 旧规范迁移 | 对象是旧 `specs/` 规范体系 |
| 工作闭环 | 运行闭环 | 除引用旧规范外，v2 优先使用运行闭环 |
| 机制落地关系 | 规范落地要求 + 环境适配映射 | 旧关系字段应拆成两层 |
| 机制承接关系 | 规范落地要求 + 环境适配映射 | 无法确认环境实体时先进入待迁移事项 |
| Tools / PyTools 机制 | Code 实现、工具、脚本、校验器或 `tools/` 目录实现 | 不再作为独立构成要素 |
| NN.01-Rules 至 NN.06-Contract | 旧机制文件、迁移前过渡资料或遗留契约 | 不构成 v2 固定子文档要求 |
| 产品初始化等同环境初始化 | 不推荐 | 环境初始化只是产品初始化的前置准备或组成部分 |

## 12. 旧机制文件术语边界

旧机制文件指旧 `specs/` 中围绕工作模型或工作流程形成的 `NN.01` 至 `NN.06` 文件，例如 Rules、Skill、Agent、Tools、Web 和 Contract 文件。

旧机制文件在 v2 中只作为迁移素材或遗留契约识别，不构成新增工作模型或工作流程的固定完整性要求。旧机制文件中的稳定内容应按内容性质回并到主规范、规范落地要求、环境适配映射、Code 规范、Web 规范、工作流程规范、结构化契约或待迁移事项。

## 13. 术语变更治理

术语变更治理用于防止局部文档隐式改写术语含义。

新增、改名、废止或改变本文定义的术语时，应先判断：

1. 是否影响 00 的五类构成要素、事实源原则或运行闭环标准；
2. 是否影响 01 的目录分区或编号分区；
3. 是否影响 03 的文档结构、引用、索引文档或旧规范迁移规则；
4. 是否影响 04 的规范落地要求、保障机制、环境适配映射或运行投影；
5. 是否影响 14 的 Code 实现边界；
6. 是否需要同步后续工作模型、工作流程、Web 或事实源规范；
7. 是否需要 Human Gate。

## 14. 规范落地要求

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 上位约束承接要求 | 后续正式规范涉及本文定义的术语时，应引用本文，不得并行维护同一术语定义 | 相关规范引用、术语归口规则、规范文档检查 | 文档治理 | 新增、修改或审计 specs-v2 正式规范时 |
| 入口可见要求 | AI 编写、迁移或审计 v2 文档时应能定位本文作为术语入口 | 规范文档入口摘要、相关规范引用、01 编号分区 | AI 执行入口提示 | 本文定位、术语表或旧称对照变化时 |
| 确定性执行要求 | 后续 Code 应能检查关键术语旧称、重复定义和不推荐裸词的高风险用法 | `tools/specs_validate.py` 扩展、正反样例、人工降级检查 | 校验实现 | 术语表、旧称对照、文档检查范围或术语治理规则变化时 |
| 生命周期触发要求 | 正式规范新增、重命名、迁移或术语变化后，应检查本文和相关规范引用是否需要同步 | `specs-v2/03.01-规范文档规范.md` 修改执行顺序、术语一致性检查、人工降级检查 | 触发保障 | 术语定义、术语旧称、文档标题、编号分区或规范归口变化时 |
| Human 交互要求 | 改变核心术语边界或删除迁移期临时内容时，应让 Human 看见影响范围和替代写法 | Human Gate、变更前说明、术语影响清单 | 术语治理 | 改变五类构成要素、产品初始化、运行闭环、规范落地、环境适配或旧规范迁移相关术语时 |

## 15. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变五类构成要素的术语边界；
2. 将环境能力、环境实体或运行投影提升为最终事实源；
3. 将环境初始化等同于产品初始化；
4. 改变规范落地要求、保障机制、环境适配映射或运行投影之间的术语关系；
5. 改变 Code、工具、脚本、校验器或 `tools/` 目录实现之间的术语边界；
6. 将旧机制文件恢复为 v2 固定子文档要求；
7. 长期保留迁移期临时对照表而不安排收敛；
8. 允许其他规范并行维护本文已定义术语的权威定义。

术语检查至少包括：

| 检查项 | 标准 |
|---|---|
| 术语归口 | 术语定义归口本文，其他规范只说明应用规则 |
| 旧规范迁移 | 旧 `specs/` 只作为迁移素材，未被直接当成 v2 权威 |
| 产品初始化 | 产品初始化未被环境初始化替代 |
| 环境适配 | 环境能力、环境实体和运行投影未混同 |
| 构成要素 | 开发环境、工作模型、工作流程、Code、Web 未互相替代 |
| 中文定语 | 高风险中文裸词已有上下文限定或改为推荐用语 |
| 迁移期内容 | 旧称对照和历史引用记录已标明临时性质和后续移除要求 |
