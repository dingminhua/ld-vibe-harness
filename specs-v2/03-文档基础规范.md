# 文档基础规范

> 更新日期：2026-06-08
> 定位：LD Vibe Harness 文档工作区、文档分区、命名、结构、引用、吸收和文档治理检查的基础规范
> 适用范围：LDVH 自身 `specs-v2/` 文档工作区、安装 LDVH 的管辖项目 `docs/` 文档工作区，以及由正式规范明确纳入治理的项目入口文档
> 上位依据：`specs-v2/00-LD-Vibe-Harness理念与纲要.md`
> 相关规范：`specs-v2/02-术语规范.md`、`specs-v2/03.01-规范文档规范.md`、`specs-v2/03.02-管辖项目文档规范.md`、`specs-v2/03.03-索引文档规范.md`、`specs-v2/04-规范落地与环境适配基础规范.md`

## 1. 本文解决的问题

本文定义 LD Vibe Harness 中不同文档工作区共享的基础规则：文档工作区如何划分正文、evals 和 refs，文件如何命名，章节和段落如何组织，文档之间如何引用，调研或分析结论如何吸收，以及 AI 修改文档时应如何检查。

本文不直接定义 LDVH v2 正式规范编号、规范落地要求字段、README 写作规则、需求文档模板或技术文档模板。这些特例由应用剖面文档定义：规范文档剖面依据 `specs-v2/03.01-规范文档规范.md`，管辖项目文档剖面依据 `specs-v2/03.02-管辖项目文档规范.md`。

---

## 2. 与 00 总纲的关系

00 定义 LD Vibe Harness 依赖 Git 可追踪文件作为稳定事实源，并要求 AI、人、Code 和 Web 围绕同一组事实协作。本文承接该要求，为 Markdown 文档类事实源提供统一的文档工作区、文档结构、引用和吸收规则。

本文是文档基础规则的权威位置。应用剖面文档只能声明某个文档工作区的特有规则，不得复制或改写本文的通用规则。

## 3. 文档工作区三分契约

### 3.1 文档工作区

文档工作区是一个 Git 可追踪目录，用于承载一组具有共同事实源边界的 Markdown 文档。LDVH 当前正式识别两类文档工作区：

| 文档工作区 | 根目录 | 应用剖面 | 说明 |
|---|---|---|---|
| LDVH v2 规范文档工作区 | `specs-v2/` | `specs-v2/03.01-规范文档规范.md` | LDVH v2 基线规范、评估和外部引用 |
| 管辖项目文档工作区 | `docs/` | `specs-v2/03.02-管辖项目文档规范.md` | 安装 LDVH 的用户项目资料、分析和外部引用 |

管辖项目不默认创建 `specs/` 或 `specs-v2/`。LDVH 自身作为被 LDVH 管辖的项目时，v2 基线以 `specs-v2/` 承载 LDVH 规范，以根 `README.md` 和必要的 `docs/` 承载项目入口文档或项目资料。

### 3.2 三分契约

每个文档工作区使用同一套三分契约：

```text
<W>/        正文区
<W>/evals/  内部评估、内部分析和方案比较
<W>/refs/   外部引用、外部调研和第三方资料
```

其中 `<W>` 是文档工作区根目录。LDVH v2 规范文档工作区中 `<W>=specs-v2`；管辖项目文档工作区中 `<W>=docs`。

### 3.3 正文区

正文区承载已经被采纳、可以作为该文档工作区稳定事实源的文档。

正文区规则：

1. 正文区是该文档工作区的权威文档区域；
2. 正文区不得把 `evals/` 或 `refs/` 作为权威依据；
3. 正文区可以记录已经吸收的结论，但结论正文必须写入正文区自身或对应工作对象；
4. 正文区文档如需稳定关联工作对象，应使用对象 ID、文件路径或应用剖面定义的字段承载。

### 3.4 evals 区

`evals/` 承载内部评估、内部分析、方案比较、实践复盘和设计探索。

evals 区规则：

1. evals 文档不直接构成正文区稳定事实；
2. evals 文档可以引用正文区作为评估依据；
3. evals 结论必须吸收到正文区、ADR、Task、Memo、Intent 或其他权威位置后才生效；
4. evals 编号只用于排序和引用便利，不占用正文区编号体系。

### 3.5 refs 区

`refs/` 承载外部引用、外部调研和第三方资料。

refs 区规则：

1. refs 文档不直接构成正文区稳定事实；
2. refs 文档不得反向维护正文区规则、正文区结论或工作对象状态；
3. refs 文档不得包含对正文区文件的路径引用、关联规范声明或依据引用；
4. 外部资料中的结论必须先被分析、判断并吸收到正文区或工作对象后，才可成为稳定事实；
5. refs 编号只用于排序和引用便利，不占用正文区编号体系。

### 3.6 吸收规则

吸收是指将 evals 或 refs 中的结论转入某个权威位置。吸收后，权威位置承载结论本身，原 evals 或 refs 只保留背景、来源或分析过程。

常见吸收出口如下：

| 输入位置 | 结论性质 | 吸收出口 |
|---|---|---|
| `evals/` | 稳定文档规则 | 正文区 |
| `evals/` | 长期决策 | ADR |
| `evals/` | 可执行工作 | Task |
| `evals/` | 暂存发现或待观察信息 | Memo |
| `refs/` | 被采纳的外部事实或方法 | 正文区、ADR 或 Task |
| `refs/` | 仅供背景阅读 | 保留在 refs，不升级 |

吸收不得只通过“引用 evals/refs 路径”完成。权威结论必须在吸收出口中明确写出，并保留必要来源说明。

## 4. 命名与路径规则

### 4.1 文件命名

文档文件名应表达文档身份和主题。文档工作区应用剖面可以为正文区、evals 区和 refs 区定义更具体的编号或命名规则。

通用命名规则：

1. 正文区文件名应稳定、可读、避免临时词；
2. evals 和 refs 文件可使用自然序号作为排序前缀；
3. 文件名变更必须同步检查所有路径引用；
4. 文件名不得只依赖日期、聊天轮次或临时任务名表达长期身份；
5. 同一文档工作区内不得出现两个表达同一权威领域的正文文件。

### 4.2 章节编号

Markdown 正文章节标题统一使用阿拉伯数字层级编号。一级章节使用 `## N. 标题`，二级章节使用 `### N.N 标题`，三级章节按需使用 `#### N.N.N 标题`。

同一文档内不得混用中文大写章节编号、罗马数字编号和阿拉伯数字章节编号。正文有序列表可以在章节内从 `1.` 重新开始，不属于章节编号。

### 4.3 应用剖面与专题子文档

子文档用于承接同一父规范下的应用剖面或专题分工。子文档不是固定机制子文档，不得成为每个工作模型或工作流程的默认拆分结构。

允许创建子文档的条件：

1. 父规范已经存在可复用通用规则；
2. 至少存在两个需要共享通用规则但边界不同的应用剖面或专题问题；
3. 子文档只定义应用剖面特例或专题细则，不复制父规范通用规则；
4. 父规范维护子文档清单和适用边界；
5. 新增、删除或重命名子文档应评估 Human Gate。

当前正式子文档入口如下：

| 子文档 | 类型 | 说明 |
|---|---|---|
| `specs-v2/03.01-规范文档规范.md` | 应用剖面 | `<W>=specs-v2`，LDVH v2 规范文档工作区 |
| `specs-v2/03.02-管辖项目文档规范.md` | 应用剖面 | `<W>=docs`，管辖项目文档工作区 |
| `specs-v2/03.03-索引文档规范.md` | 应用剖面 | 规范型集合索引和说明性索引的文档结构、承载边界和维护规则 |
| `specs-v2/04-规范落地与环境适配基础规范.md` | 专题父规范 | 04 系列专题子文档入口；具体清单由 04 §4 维护 |

固定机制子文档（如为每个工作模型默认创建 Rules、Skill、Agent、Tools、Web、Contract 子文档）不属于本节允许的子文档，除旧规范迁移保留外不得新增。

## 5. 文档结构与段落规则

### 5.1 头部元信息

正式纳入文档工作区治理的 Markdown 文档应通过头部元信息说明定位和边界。不同应用剖面可以定义必填字段。

通用头部字段包括：

| 字段 | 含义 |
|---|---|
| 创建日期 / 更新日期 | 文档创建或最近更新日期 |
| 定位 | 文档回答什么问题，属于什么事实源边界 |
| 适用范围 | 文档适用的项目、场景或文档工作区 |
| 上位依据 | 本文依赖的上位规范或权威文档 |
| 相关规范 / 关联对象 | 与本文相关但不替代本文权威领域的文档或对象 |

头部不得承载正文才应展开的规则，不得用“本文不做什么”的反向清单替代正向职责表达。

### 5.2 段落与列表

段落应围绕一个明确判断或规则展开，避免把多个事实、判断和行动塞入同一长段。

列表用于表达并列规则、步骤、检查项或选项。列表项应互相独立，避免一个列表同时混合定义、例外、检查和执行步骤。

### 5.3 表格

表格用于表达稳定对照关系。表格列名应清楚，行内容应能被 AI 和工具稳定解析。

表格不得用于隐藏长篇说明。需要解释的内容应放在表格前后正文中。

### 5.4 代码块

代码块用于承载示例、模板、命令、结构化片段或流程图。代码块中的示例不得被误读为真实事实源，必要时应在代码块前说明其示例性质。

## 6. 引用与关联规则

### 6.1 路径引用

引用 Git 文件事实源时，应使用明确路径。Markdown 正文中的路径引用应可被 AI 搜索和工具检查。

当引用目标文件发生重命名、迁移或删除时，必须同步检查所有路径引用。

### 6.2 章节引用

引用章节时统一使用 `§N`、`§N.N` 或 `§N.N.N`。章节引用必须指向真实存在的标题编号。

应用剖面可以定义编号速记规则，但速记规则不得替代真实路径和章节存在性检查。

### 6.3 对象引用

引用工作对象时，应使用对应工作模型定义的对象 ID 或文件路径。文档引用对象不改变对象状态；对象状态、负责人、验收和关闭证据仍由工作对象事实源承载。

### 6.4 引用方向

文档引用必须遵循事实源边界。正文区不得通过引用 evals 或 refs 来绕过吸收；evals 和 refs 也不得反向定义正文区规则。

---

## 7. 文档与工作对象关系

文档和工作对象是不同事实源形态。

文档适合承载：

1. 背景、解释、设计语境和报告；
2. 需求、技术说明、操作说明和外部资料；
3. 不需要状态机和高频结构化解析的长文本事实。

工作对象适合承载：

1. 状态、负责人、验收、关闭证据和关系字段；
2. 需要 Code 实现校验、聚合或受控写入的事实；
3. 需要跨会话追踪的 Intent、Task、ADR、Memo、Change、Pitfall 等实例。

当一个文档需要生命周期治理时，不应直接把文档升级成工作对象；应创建或更新相应 Intent、Task、ADR 或 Memo，并在对象中引用文档路径。

## 8. 规范落地要求

规范落地要求用于说明一条稳定规范要落地，需要满足哪些要求。规范落地要求只回答“这条规范要落地，需要哪些入口、流程、检查、触发、交互或思考要求”，不直接回答“某个开发环境里具体写入哪个文件或配置”。

规范落地要求是 specs-v2 正式规范文档的特有段落要求，不是所有 Markdown 文档的通用要求。目录说明、索引说明、evals、refs、README、项目文档和其他非正式规范文档，不默认要求设置规范落地要求段落；只有被应用剖面明确纳入正式规范治理的文档，才适用该段落要求。

规范落地要求到具体开发环境实体的转换，称为环境适配映射。规范落地与环境适配的父规范入口由 `specs-v2/04-规范落地与环境适配基础规范.md` 定义；环境适配映射应说明同一落地要求在 Trae、Codex、Claude Code、Cursor 或其他开发环境中通过哪些机制、文件、配置、命令、入口、降级方式和验证方式满足，通用规则由 `specs-v2/04.02-环境适配与运行投影规范.md` 定义。

本文通过以下规范落地要求说明相关要求的同步、检查或审计触发条件。

| 落地要求 | 要求内容 | 保障机制 | 同步类型 | 触发条件 |
|---|---|---|---|---|
| 入口可见要求 | 文档工作区入口摘要 | 文档工作区入口摘要、应用剖面引用、专题子文档引用、`specs-v2/04.02-环境适配与运行投影规范.md` | AI 执行入口提示 | 本文的文档工作区三分契约、命名规则、引用规则、子文档规则或文档与工作对象关系变化时 |
| 确定性执行要求 | 文档章节和引用校验 | `tools/specs_validate.py` 或后续文档校验 Code、正反样例验证、降级风险记录 | 校验实现 | 本文的章节编号、章节引用、路径引用、evals/refs 边界或文档治理检查变化时 |

具体环境实体不在本文表格中声明，应由后续环境适配映射解释。读取旧规范中的“机制落地关系”或“机制承接关系”时，应按 `specs-v2/02-术语规范.md` 的旧称处理，将其拆分为“规范落地要求”和“环境适配映射”两层后再迁入 v2。

## 9. Human Gate 与检查要求

以下情况应评估 Human Gate：

1. 改变文档工作区三分契约；
2. 改变正文区、evals 区或 refs 区的事实源性质；
3. 新增、删除或重命名应用剖面或专题子文档；
4. 恢复或新增固定机制子文档结构；
5. 允许正文区直接以 evals 或 refs 作为权威依据；
6. 改变文档与工作对象之间的权威边界；
7. 新增、替换或扩大文档检查 Code 实现的判定范围，并可能影响规范结论、迁移结论或文档治理通过条件。

文档基础检查至少包括：

| 检查项 | 标准 |
|---|---|
| 文档工作区 | 文档位于正确工作区和正确分区 |
| 命名 | 文件名表达稳定主题，重命名后引用已同步 |
| 章节编号 | 正文章节使用阿拉伯数字层级编号 |
| 章节引用 | `§` 引用目标真实存在 |
| 引用边界 | 正文区未以 evals/refs 作为权威依据 |
| 吸收关系 | evals/refs 结论已写入权威吸收出口后才生效 |
| 对象边界 | 文档未替代工作对象状态、验收或关闭证据 |

### 9.1 文档检查 Code 缺口处理

当某项文档检查已经被规范要求，但现有 Code 实现无法覆盖该检查时，AI 不得直接沿用不适配的旧实现得出通过结论，也不得仅以人工阅读替代确定性检查结论。

AI 应按以下顺序处理文档检查 Code 缺口：

1. 明确检查需求：说明要检查的对象、规则来源、输入范围、预期失败条件和输出格式；
2. 判断是否已有适配 Code 实现：若已有实现只需小范围扩展，应先扩展既有实现；若旧实现假设与当前文档工作区冲突，应视为 Code 缺口；
3. 按 `specs-v2/14-Code实现规范.md` 判断 Code 需求准入，需求成立时实现覆盖当前检查需求的最小确定性校验；
4. 按 `specs-v2/14-Code实现规范.md` 验证 Code 实现本身，至少使用一个应通过样例和一个应失败样例，或使用等价的正反验证方式，证明实现能识别目标规则；
5. 运行 Code 实现检查目标文档；
6. 将 Code 需求、实现位置、验证方式和检查结果写入本次任务记录或相关工作对象；
7. 若当前任务不能实现对应 Code，应记录缺口、降级检查方式和残留风险；该降级不得被表述为完整通过。

文档检查实现满足确定性执行要求，也属于 Code 构成要素。新增、扩展、测试、修改、维护或删除文档检查 Code 实现时，应同时遵守 `specs-v2/14-Code实现规范.md`；若该 Code 实现需要在不同开发环境中暴露为命令、脚本入口或自动化检查，还应由 `specs-v2/04.02-环境适配与运行投影规范.md` 解释具体实体。
