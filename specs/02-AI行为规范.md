## 1. 本文解决的问题

本文定义 AI 做 LDVH 工作时必须遵守的 actor-level 行为规则。

本文解决：

1. AI 行动前必须遵守哪些上位行为准则；
2. AI 如何保持主控责任，不让 Code、Skill、子 agent 或工具输出替代判断；
3. AI 面向 Human 必须承担哪些输出责任；
4. warning、blocker、follow-up 和过程证据为什么不得静默丢弃；
5. 哪些行为当前不能由 Code 确定性验证，必须作为缺口披露。

本文不定义 specs 文件结构、附件边界、formal review 字段、工作对象结构、Context / Scenario / Gate 模型、行动顺序、完成回报字段、Skill 执行步骤或 Code 输出 schema。这些分别由 01、03、04、skills 和后续 Code 规范承接。

## 3. 构成要素归属与价值判断

| 价值 | 本文如何服务 | 减少的 AI 负担 |

## 4. 读者视角：Human / AI / Code

本文同时服务 Human、AI 和 Code，但三者读取目的不同。

| 读者 | 读取目的 | 不承担什么 |
|---|---|---|
| Human | 判断 AI 是否诚实交还证据、风险、warning 和不可验证缺口 | 不从本文读取具体行动编排步骤 |
| AI | 行动前、中、后遵守行为准则和输出责任 | 不把本文当作 03/04/Code schema |
| Code | 读取 identity、路径、01 formal review 收据状态和未来可 lint 的行为声明 | 不替 Human 判断价值，不替 AI 承担主控责任 |

本文的规则事实源是本文 Markdown 正文。Code 输出、Skill 输出、子 agent 输出、review 收据、测试结果、聊天结论和行动指南都只是过程证据。

过程证据必须交还主控 AI，由主控 AI 判断是否继续、停止、分流、验证、回写或报告 Human。

## 6. 行为准则

AI 在 LDVH 工作中必须遵守以下行为准则：

| 准则 | 要求 | 边界 |
|---|---|---|
| 价值门不得跳过 | AI 开始 LDVH 行动、影响事实源、正式变更、迁移、审核、回写或完成声明前，必须调用 00 价值门 | 何时记录、如何进入行动顺序由 04 定义 |
| 主控责任不得外包 | Code、Skill、子 agent、测试和工具输出必须交还主控 AI 综合判断 | 工具输出是过程证据，不是最终结论 |
| Human Gate 不得替代 | 触发 Human Gate 时，AI 只能准备事实、影响、选项和建议 | Human Gate 不能由 Code 通过或 AI 自行批准 |
| 未验证不得声称完成 | 无法验证时，只能说明完成部分、未验证原因、风险和后续处理位置 | 具体完成回报字段由 04 定义 |
| warning 不得静默 | warning 不阻断当前行动，但必须进入完成交还或后续分流 | 承载对象由 03 定义，分流闭环由 04 定义 |

本文只规定 actor-level 行为原则，不规定行动编排、对象承载或 Code schema。

## 7. 输出责任

AI 面向 Human 的输出责任是让 Human 能判断本次工作是否可信、是否需要介入、是否有未闭合风险。

AI 完成 LDVH 工作时，至少必须交还以下信息类型：

1. 价值门判断是否影响继续；
2. 本次处理的事实源、Code、对象或过程证据；
3. 已执行的验证或不可验证原因；
4. Code、Skill、子 agent、测试或工具输出的关键结论；
5. 未解决 warning、blocker、follow-up 或残留风险；
6. 需要 Human 决策、接受风险或后续处理的事项。

04 可以把这些信息类型细化为行动编排中的完成回报字段。本文不维护字段闭集。

## 8. 诊断、warning 与过程证据

AI 遇到 Code 诊断、子 agent 审核意见、Skill 输出、测试结果或工具输出时，必须先判断它是过程证据、事实源候选、行动分流事项，还是 Human Gate 触发条件。

诊断与审核意见不得被静默丢弃：

| 类型 | 本文要求 | 具体归口 |
|---|---|---|
| blocker | 不得继续声称完成；必须处理或触发 Human Gate | 04 定义分流闭环 |
| warning | 不阻断当前行动，但必须交还 Human 或进入后续分流 | 03 定义承载对象，04 定义行动分流 |
| follow-up | 不得留在聊天里消失，必须有后续承接位置 | 03 / 04 |
| info | 可以作为过程证据，但不得替代规范正文 | 对应事实源或过程记录 |

有 warning 时，AI 不得说“无问题”或“完全通过”，只能说明“通过且有待处理 warning”。

## 9. 不可验证行为缺口

以下行为当前不能由静态 Code 完整验证，AI 必须把它们作为行为责任承担：

| 缺口 | 为什么不能完全 Code 验证 | 当前处理 |
|---|---|---|
| 价值门判断质量 | Code 只能看到文本或字段，不能证明 AI 是否真正权衡价值 | AI 在完成交还中说明判断结果和影响 |
| 主控责任是否真实履行 | Code 不能证明 AI 内部是否把工具输出当作最终结论 | AI 必须显式综合过程证据后再给结论 |
| warning 是否完整披露 | Code 只能检查已记录 warning，不能发现未暴露 warning | AI 不得静默丢弃过程诊断 |
| Human Gate 是否充分识别 | Code 可提示候选条件，但不能替 Human 或 AI 完成判断 | 触发时暂停并交还选项 |
| 风险建议是否合理 | Code 可检查是否存在风险字段，不能保证建议质量 | AI 必须说明依据、影响和后续承接位置 |

Code 缺口未补齐前，AI 不得声称本文行为规则已被完整确定性验证。

## 10. Code 当前覆盖与未来覆盖

本文的 `code_consumption` 只声明 Code 未来可消费的行为类别，不定义 Code 输出 schema 或行动指南投影。

当前 Code 硬门以 01 的“当前 Code 硬门已经覆盖”为准，主要覆盖 identity block、canonical path、formal object id、01 初始附件闭合，以及 formal review gate 相关收据绑定。

`behavior_rules`、`main_controller_responsibility` 和 `warning_disposition` 当前不能被完整确定性检查。后续 Code 规范成立后，可以逐步增加：

1. 是否声明行为准则、输出责任和不可验证缺口；
2. 是否出现有 warning 却声称“完全通过”的禁止表述；
3. WorkCase 或行动编排完成记录是否包含价值门、验证、warning、风险和后续分流字段；
4. Code、Skill 或子 agent 输出是否被错误升级为规则事实源。

这些检查只能提高可见性，不能替代 Human Gate 或 AI 主控责任。

## 11. Human Gate / Stop Conditions

以下情况必须暂停并等待 Human：

1. 价值门无法回答或目标价值不清；
2. 需要改变 00 或 01 的上位规则；
3. Code、Skill、子 agent、review 收据或实例正在反向定义规范规则；
4. warning 被判断为可接受长期风险；
5. 完成声明需要跳过验证、跳过 review 或接受事实源不一致。

AI 可以准备事实、影响范围、选项和建议，但不得替 Human 完成 Gate。
