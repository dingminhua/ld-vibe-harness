# LDVH V4 架构重建基线

> 记录性质：V4 架构重建的工作基线，不是规则源，不授权产品行为。
> 起点分支：`dev-v4`
> 起点提交：`9d89d57f`
> 建立日期：2026-07-11

## 1. 记录目的

本记录用于约束 V4 架构重建阶段的起点、资产身份、声明边界和完成条件，防止 V3 的规则、实现和验证结论在未经重新裁决时被默认带入 V4。

本记录位于 `docs/` 而非 `specs/`，不定义 LDVH 的持久产品规则、Schema、接口契约或验收契约。需要长期生效的规则，必须经过 V4 裁决并写入当前 V4 规则源。

## 2. V4 的非继承起点

V4 是全新的架构与规范起点，不是 V3 的兼容迁移、原地修补或继续演进。因此：

1. V3 的规则、字段、附件关系、状态、路径和解析约定不自动在 V4 中生效。
2. V4 不承担旧字段、旧附件授权、旧 validator、双读、Git 迁移基线或其他 V3 过渡机制的兼容义务。
3. V3 资产可以作为问题样本、历史经验和实现参考，但必须逐项得到“采纳、改写、拆分或淘汰”的 V4 处置结论。
4. 任何被采纳的内容都必须在 V4 当前规则源、模型或实现中重新明确表达；不得仅以 V3 中已存在为由主张其对 V4 有效。

## 3. 当前资产身份与权威边界

| `archive/v3/specs/` | V3 Specs 及附件的历史归档 | 仅供调查、溯源和选择性设计参考；其 `active` 标记、规则效力和结构契约均不适用于 V4。 |
| `docs/positioning-calibration/` | 定位校准和规划种子资产 | 用于理解已确认的元架构和历史讨论，不代替正式 V4 规则。 |
| `code/` | V3 留存实现参考 | 尚未被裁决为 V4 Code，不证明 V4 Helper、parser、validator 或受控操作已实现。 |
| `tests/` | V3 留存测试参考 | 尚未被裁决为 V4 验证契约，其通过或失败不证明 V4 能力成立与否。 |
| `hooks/` | V3 环境接入实现参考 | 已与当前 worktree 的 Hook 入口隔离；不得将其内容或历史执行结果解读为 V4 规则履行或 integrated 证据。 |

正式规则权威只能来自 `specs/` 中被明确接受的 V4 内容。当前 `specs/00-理念与构成.md` 已按 §4.1 恢复并接受为 V4 根规范；后续规则必须在其边界内建立。任何历史资产、路径位置、旧状态标记、实现存在或旧测试结果，都不得自动扩大这一范围。

当前已经落实两项外围隔离：顶层 `README.md` 已切换为 V4 仓库入口；当前 worktree 的 `core.hooksPath` 已指向无可执行 Hook 的 `.githooks-v4`，因而旧 `hooks/` 不再被当前 worktree 执行。这两项是身份校准和执行隔离，不是 V4 功能完成证据。

## 4. V3 Specs 归档结论

原顶层 `specs/` 中的 V3 规范与附件已整体移至 `archive/v3/specs/`，Git 历史仍可追溯。该移动的目的是隔离权威身份，不是删除历史信息，也不是把 V3 契约转换成 V4 契约。

新的顶层 `specs/` 专用于 V4。V3 文件中对原 `specs/` 路径的引用、扫描、校验或 Hook 依赖可以因此失效；这些失效不构成 V4 的兼容缺陷。

### 4.1 V4 00 的语义一致性要求

V4 的非继承原则不改变根规范的最终一致性要求：正式接受的 V4 `00-理念与构成.md` 必须与本次归档的 V3 `00-理念与构成.md` 保持根级语义一致。

这里的“一致”是语义一致，不要求文字、章节数量或载体结构相同。V4 00 可以：

1. 删除 V3 YAML 身份块、旧路径、`code_consumption`、旧附件关系、validator、双读和迁移契约；
2. 将具体命令、工具名称和实现入口下沉到对应 V4 规范；
3. 改写或压缩论证材料；
4. 增加不改变 V3 根级定义的澄清，例如区分当次观察证据与可接续稳定事实，或显式说明 Helper 的架构角色与 Code 实现归属。

V4 00 不得在未告知 Human 并取得明确决定的情况下，删除、弱化、扩大或改变 V3 00 已定义的根级语义。当前 V4 00 已以归档 V3 00 正文为母版完成恢复；除已确认且不冲突的 Helper 架构澄清外，逐段对照未发现根级正文语义差异。后续出现的任何差异均视为待处理缺口，不因文件修改或下游规范已经使用而自动获得接受。

正式接受前至少必须逐项对齐并复核：

1. 存在理由、最终目标以及 AI、Human、Code 的基本职责关系；
2. AI 第一服务对象和 Helper CLI 基础服务形式；
3. 事实源以 Git 可追踪文件为唯一有效承载的边界，以及有组织、可消费要求；
4. 五类构成要素、明确主要归口和 Web 的上位职责；
5. V1–V8 的名称、完整判断问题、价值边界和净价值原则；
6. 根级验证边界，包括 Human 决定不能替代技术验证、静态存在不能证明可用、`integrated` 只按当次依据成立；
7. Human Gate 的触发、交还、回应和效力边界；
8. Stop Conditions 的来源规则驱动、最小暂停范围、暂停期间允许行动和按触发原因恢复；
9. 下位规范、事实模型、行动模板、Code、Helper、Web 和工具输出不得反向解释、覆盖或弱化根规范。

如果 V4 设计确需改变其中任何一项，应先向 Human 明确说明与 V3 的差异、原因、影响和替代方案；在 Human 明确改变本一致性基线前，该差异阻断 V4 00 的正式接受。

## 5. Web 冻结边界

本轮重建不修改 Git 跟踪的 `web/` 内容，不对其进行架构调整、接口迁移、数据适配或风格修改。

Web 仍作为既有产品资产保留。未来只有在 V4 规则、信息源和实现边界已稳定，且另行明确纳入范围后，才能开始其 V4 校准。

## 6. 旧测试结果的处置

V3 定向测试曾得到 `245 passed, 37 failed`。这一结果描述的是 V3 旧 validator 与当时规范变动之间的冲突，不是 V4 的失败清单、验收基线或修复 backlog。

V4 测试必须从已接受的 V4 规则、Schema、服务契约和实现边界重新推导。旧测试只能用来发现候选场景、边界条件和历史风险；采纳某个场景时，仍需要为它建立 V4 的独立验证依据。

## 7. 重建阶段的声明约束

在 V4 对应资产完成设计、实现、接入和验证之前：

- 不得因为旧 Code、tests、hooks、`ldvh-base/` 或 Web 仍存在，就声明对应 V4 能力已实现、available、integrated、已保障或 completed。
- 不得用 V3 测试通过数量或 Hook 执行成功来证明 V4 合规。
- 不得将未经接受的草案、讨论记录或历史文件表述为已生效的 V4 规则。
- 未被 V4 覆盖、未实现、未接入或未验证的范围，必须在当次工作中如实降级声明。

## 8. V4 干净基线阶段的完成条件

只有以下条件全部满足，才能将“V4 干净基线”标记为完成：

1. 顶层 `specs/` 已被明确校准为 V4 唯一当前规则源根，V3 Specs 已完整归档且不会被当前规则扫描器误读。
2. V4 根规范已按 §4.1 完成与归档 V3 00 的逐项语义一致性复核并被正式接受，且重建时间性内容已留在本工作记录中；任何未获 Human 明确决定的根级语义差异均已消除。
3. V4 规范体系的最小治理契约已确定，能区分草案与生效规则，并能说明权威引用、适用、效力和验证边界。
4. 顶层入口说明已完成 V4 身份校准，当前 worktree 的 Hook 入口已完成隔离；V3 Hook 不再对 V4 产生伪权威约束，且隔离状态没有被表述为 V4 Hook 能力。
5. `code/`、`tests/`、`hooks/` 和 `ldvh-base/` 在被重新裁决前均有不会被误读的非权威身份，且不被用于支撑 V4 能力或完成声明。
6. V4 的实现与测试准入方式已从 V4 规则重新推导，旧测试结果已与 V4 backlog 和验收状态明确隔离。
7. Git 跟踪的 `web/` 与起点相比保持不变，且没有用 Web 的旧实现反向定义 V4 架构。
8. 对上述边界已进行当次可复核检查，没有把“文件存在”、“历史可运行”或“局部测试通过”写成 V4 已完成的证据。

## 9. 后续裁决方式

对 V3 资产的后续处理应以职责和 V4 实际需求为单位，而不是按旧编号或旧文件整体搬运。每项采纳应至少能说明：

1. 它解决的 V4 问题和对 AI 的净价值；
2. 它在 V4 中的职责归属和权威来源；
3. 它的适用、效力、验证和声明边界；
4. 它是采纳、改写、拆分还是淘汰，以及为何。

当此类结论需要形成持久规则时，应进入 V4 `specs/`；只描述重建过程、阶段状态或资产处置的内容，应继续保留在工作记录中。
