## 研究问题

本报告回答一个 LDVH 的并行协作问题：一项工作何时真的可以拆开，拆开后谁对共享改动、交接信息和最终判断负责。

具体问题包括：

1. Codex 的子代理、worktree 和运行时配置各自适合承担哪些职责；
2. 一项工作何时可以拆给多个执行者，何时必须保留单一汇总人；
3. 运行时权限和项目责任的区别是什么，为什么不能互相替代；
4. 这些原则应如何影响 LDVH 后续的协作判断，而不变成固定流程。

## 输入与边界

本报告输入来自三类资料。

第一类是 Codex 官方文档：Subagents（说明子代理适合读密集、可独立汇总的任务）、Local environments（说明 worktree 用于隔离并发改动）、Configuration Reference（说明子代理继承权限和配置）。

第二类是当前的 LDVH 实践经验：V3 曾有多份研究（study-0002、study-0011）涉及子 Agent 和 worktree 协作，本报告吸收了其问题意识和边界判断，但不把 V3 结论当作当前来源。

第三类是项目内部的实际协作观察：多线程、多 worktree 并行时，容易出现产出可汇总性下降、写入责任不清的问题。

边界如下：

- 不比较其它 agent 产品（Trae、Claude 等已在其他研究中覆盖）；
- 不测量并行的实际收益或成本；
- 不声称任何做法已被当前项目采用、验证或授权；
- worktree 的环境准备、文件并发修改范围和汇总方式取决于未来具体任务，不能从产品文档自动得出。

## 关键发现

### 可并行的是有独立交付面的阅读与核验，不是角色数量

Subagents 文档把代码库探索、测试、分诊和资料汇总列为适合并行的场景。它们的共同点不是任务名称，而是可以先说明输入问题、预期输出和不碰触的范围。一份资料比较、一个只读代码定位或一项测试观察，都能由主线程在随后统一吸收。

对 LDVH 的启发是：先问"结果交回后能否由一个人清楚比较和采用"，再决定是否拆分。一个可用的最小交接包含：要回答的问题、输出形式、允许读取的范围、不得修改的范围，以及谁负责汇总。这样并行服务于推进判断，而不是制造更多过程记录。

反之，多个任务若争夺同一份事实对象、同一个 Schema 或同一处代码设计，表面上可以分派，实质上仍要共享判断；这类工作过早并行，往往只是把冲突从开始时移到汇总时。

### Worktree 解决的是检出隔离，不是交接和可交付性

Local environments 文档说明 worktree 可把并发改动放在独立目录中。这使两个确实需要不同改动面的任务可以减少直接覆盖，也让主工作目录不必承担所有实验性改动。

对 LDVH 而言，真正需要保留的是"实际在哪个工作树写入"和"谁负责把结果带回主线"两件事。独立目录仍可能缺依赖、生成文件、环境变量或本地准备；即使测试在一个目录通过，也不自动说明结果适合另一个目录，更不说明可以合并。

因此，worktree 是在具体 WorkCase 中可验证的手段，不是 Study 可以提前宣布的默认流程。若任务没有真实的并行写入需求，额外建 worktree 反而增加准备与交接成本。

### 运行时权限和项目责任是两层不同的东西

Configuration Reference 说明子代理会继承父任务的沙箱与权限上下文，并允许以配置控制并发或专用角色。这解释了运行时能做什么、会受到什么限制。

但项目责任仍需在任务语境里明确：谁能修改共享文件、谁吸收多路发现、何时需要 Human 判断方向或接受风险。运行时允许一次写入，不表示这次写入已经有项目层面的理由；运行时能同时启动多个角色，也不表示结果之间已经一致。

这一区分让 LDVH 不必把产品配置抄成规范。配置是当次执行条件，项目责任则由目标、规则与 Human 决定共同限定；两者都应在需要时被看见，但不应互相替代。

## 建议

### 先定义交接，再决定是否并行

对未来的研究、代码定位或测试核验，先写出每个子任务的输入问题、预期交付、汇总人和不修改范围。只有这些信息能够让汇总人比较结果、并且任务之间不需要频繁互相改写时，才值得并行。

这是一项工作方式建议，不是新建模板或强制门禁。一次短小的单线程工作不需要为了满足格式而拆出角色；当交接信息写不清时，也应把它当作暂不并行的信号。

### 共享写入保留单一所有者

涉及同一 Study、同一规则、同一 Schema 或同一代码切面的变更，应明确一个写入所有者。其他并行工作可以提供资料、定位、测试观察或建议，但由所有者结合当前工作树和约束决定如何落地与验证。

这样并不排斥协作：它把协作的重点从"同时改同一处"移到"提供可吸收的输入"。若未来确有独立改动面，worktree 可以作为隔离手段，但仍需明确合并、测试和回收责任。

### 只在真实需求出现时试行 Worktree 协作

当 Human 要求试行并行实现，并且任务已有清楚目标、独立改动面和可接受的交接成本时，可建立有界 WorkCase，记录实际的 worktree 准备、交接和汇总结果。该试行的目的不是证明并行天然正确，而是判断它是否在当前项目中带来净收益。

是否把角色划分、worktree 使用或并行阈值固化为长期默认，仍应由 Human 在看到真实成本和适用范围后决定；本 Study 不替代那项取舍。
