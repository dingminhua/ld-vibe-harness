# 规范体系基础规范

```yaml
ldvh:
  schema: "ldvh-spec/v1"
  kind: "spec"
  key: "normative-system-foundation"
  spec_id: "01"
  status: "draft"
  structure: "standard"
  basis:
    - "ldvh-root"
```

> 本文当前为 draft，不构成 V4 当前规则。

## 1. 价值判断

规范体系需要让 AI 快速找到当前规则、理解规则之间的关系，并能由 Code 稳定解析。共同结构和机器身份只有在减少读取、猜测、遗漏和维护成本时才有价值。

本文主要服务：

- V1：快速定位当前规则及其来源；
- V2：理解规范依据、结构归属、附件授权和普通引用；
- V3：避免草案、说明文件、归档和派生结果被误当成规则；
- V6：在标题、编号或路径调整后仍能识别同一规范职责；
- V8：让结构问题可以被发现和修正。

本文只规定长期稳定、日常识别和消费规则所必需的共同约束。低频的版本升级、批量重编号、历史迁移和内部维护步骤，不因可能发生就进入基础规范；需要时应由维护指南、行动模板、Code 或测试承接。

## 2. 规范依据

本文直接依据 `specs/00-理念与构成.md`。00 是根规范，本文只承接其对 Specs 共同结构、职责标识、正向依赖、派生导航、解析入口和承接规则的授权。

本文不得改变或重新解释 00 对 LDVH 存在理由、AI 第一服务对象、Helper CLI、事实源边界、五类构成要素、V1–V8、验证要求、Human Gate 和 Stop Conditions 的定义。

`docs/v4-architecture/` 中的评估和设计记录可以解释本文形成过程，但不是规则源。

## 3. 职责边界

本文负责定义：

1. 当前规则源的发现与成立条件；
2. 规范和附件共同使用的 YAML 身份块；
3. 根规范与标准规范的正文结构；
4. 上位语义依赖、结构归属、附件授权和替代关系；
5. 最小生命周期和 Git 生效边界；
6. 双语术语的构造与未来术语表边界；
7. Code 可以派生的导航及其非权威边界。

本文不定义具体领域规则，不定义 Helper CLI 命令、解析器实现、测试实现或 Web 交互，也不规定低频版本维护的详细操作步骤。

## 4. 适用范围

本文适用于：

- `specs/*.md` 中的 V4 规范；
- `specs/attachments/*.md` 中由规范明确授权的附件；
- 上述文件的识别、结构、身份、关系、状态和 Code 解析。

本文不适用于 `archive/`、`docs/`、旧 Code/tests、聊天、过程输出、缓存或生成索引。这些内容不会因为包含 YAML、规则措辞或历史状态而成为 V4 当前规则。

## 5. 当前规则源

### 5.1 核心名词

本文使用以下双语规范术语：

| 中文规范术语 | English Canonical Term | 本文含义 | 机器表示 |
| --- | --- | --- | --- |
| 规范 | Specification（Spec） | 承担一项稳定规范职责的 Markdown 文件 | `kind: "spec"` |
| 授权附件 | Authorized Attachment | 由规范正文明确授权、承载稳定结构化内容的附件 | `kind: "attachment"` 与父规范授权 |
| 规范载体 | Specification Artifact | 规范与附件的统称，不表示该文件当前有效 | `kind` |
| 身份块 | Identity Block | H1 后固定位置、供 Human、AI 和 Code 识别身份的 YAML 代码块 | `yaml` 围栏中的 `ldvh` 映射 |
| 稳定职责标识 | Stable Responsibility Identifier | 不随标题、编号或路径变化的职责身份 | `key` |
| `active` 状态声明 | Active Status Declaration | 载体声明希望进入当前规则源；该声明本身不证明结构和关系有效 | `status: "active"` |
| 规则源一致性 | Rule-Source Consistency | 候选文件的身份、结构、关系和授权共同成立 | — |
| 当前规则源 | Current Rule Source | 当前已提交版本中通过一致性检查、可以作为规则依据的规范正文及其授权附件 | — |

中文规范术语负责日常阅读，English Canonical Term 用于跨语言检索和未来术语表，机器表示只负责 Code 解析。三者必须指向同一概念，不得互相代替定义。

### 5.2 候选文件与当前规则

Code 只检查当前已提交 Git 版本中以下受跟踪的普通 Markdown 文件，不跟随符号链接：

1. `specs/*.md`；
2. `specs/attachments/*.md`。

这两个目录只存放规范载体，不放置 README 或普通说明文件。路径只确定检查范围，不自动产生规则资格。

规范进入当前规则源至少必须满足：身份块有效、`status: "active"`、正文结构有效、稳定职责标识和规范编号唯一、没有另一当前规范承担同一职责，并且所声明的上位依据与结构父规范存在且当前有效。

附件进入当前规则源还必须取得唯一当前有效父规范的明确授权。身份可以确定解析且状态为 `draft` 或 `retired` 的文件，以及身份有效但未获授权的附件，不属于当前规则源。

声明 `status: "active"` 只是进入当前规则源的必要条件，不是充分条件。候选文件的身份无法解析到足以确定状态，或者一个声明为 `active` 的文件校验失败时，必须报告规则源不一致；不得通过忽略该文件把它静默当成不存在。依赖该文件的范围暂停，其他明确不受影响的工作可以继续。

## 6. YAML 身份块

### 6.1 固定位置与格式

规范载体第一行必须是唯一一级标题（H1）。H1 后空一行，紧接一个带 `yaml` 语言标识的代码围栏；该围栏就是身份块（Identity Block）。解析器只读取这个固定位置的身份块，不搜索正文中的其他 YAML 示例。

身份块使用 YAML 1.2 Core Schema，顶层只包含一个 `ldvh` 映射。所有标量字段和列表成员均使用双引号字符串；不得使用显式 `null`、重复字段、未知字段、多个 YAML 文档、自定义标签、锚点、别名或合并键。加载器选择、错误码和具体解析算法由 Schema、Code 和测试承接。

### 6.2 最小字段

| 字段 | 适用对象 | 类型 | 含义与要求 |
| --- | --- | --- | --- |
| `schema` | 全部 | 字符串 | 身份结构版本；当前为 `ldvh-spec/v1` |
| `kind` | 全部 | 字符串 | 载体类型；`spec` 或 `attachment` |
| `key` | 全部 | 字符串 | 稳定职责标识；在候选文件中全局唯一 |
| `spec_id` | 规范 | 字符串 | 当前规范编号，必须与文件名前缀一致 |
| `attachment_id` | 附件 | 字符串 | 当前附件编号，必须与文件名前缀一致 |
| `status` | 全部 | 字符串 | 生命周期状态；`draft`、`active` 或 `retired` |
| `structure` | 规范 | 字符串 | 正文结构；`root` 或 `standard` |
| `basis` | 规范 | 字符串列表 | 直接且必要的上位语义依赖 `key`；根规范使用空列表 |
| `parent_spec` | 规范 | 字符串 | 可选；直接结构父规范的 `key` |
| `authorized_attachments` | 规范 | 字符串列表 | 可选；本文明确授权的附件 `key` |
| `supersedes` | 全部 | 字符串列表 | 可选；被本载体实质替代的同类旧职责 `key` |

`kind: "spec"` 必须具有 `spec_id`、`structure` 和 `basis`，不得具有 `attachment_id`；`kind: "attachment"` 必须具有 `attachment_id`，不得具有 `spec_id`、`structure`、`basis`、`parent_spec` 或 `authorized_attachments`。列表成员必须是非空且不重复的字符串；除根规范的 `basis` 外，可选空列表应直接省略。

`key` 使用小写 ASCII kebab-case，匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`。规范文件名使用 `<至少两位数字>-<标题>.md`，例如 `01-规范体系基础规范.md`。附件编号使用 `<父规范编号>.Att.<至少两位序号>`，例如 `01.Att.01`。

规范编号和附件编号用于阅读、排序和导航；稳定关系只使用 `key`。同一职责改标题、改编号或移动时保持 `key` 不变。一个曾由 `active` 规范载体使用的 `key` 不得再分配给其他职责；该检查只在分配新 `key` 时针对仓库仍保留的 V4 Git 历史执行。

标题从 H1 取得，当前路径从 Git 取得，职责和适用范围从正文取得，不在身份块中重复维护。

### 6.3 最小启动识别

Code 启动规范解析时，必须能从候选文件中唯一找到 `key: "ldvh-root"`、`structure: "root"` 的当前根规范，以及 `key: "normative-system-foundation"` 的当前规范体系基础规范。缺失、重复或身份无法解析时，暂停依赖规范目录的解析，不按编号、标题或路径猜测承担者。

启动实现只需要预先知道候选路径、身份块固定位置、`ldvh` 顶层映射、`schema`、`kind`、`key`、`status` 四个启动字段和上述两个稳定 `key`。找到本文后，再按本文读取其余字段、结构和关系；启动过程不依赖附件、V3 身份格式或双读。

### 6.4 身份块与规则正文

身份块负责机器身份、状态和主动声明关系；规则正文负责价值、依据、职责、适用范围、具体规则、验证、Human Gate 和 Stop Conditions。

身份块不能代替正文规则，正文也不能用普通叙述暗中改变身份字段。两者冲突时，暂停依赖冲突内容的范围并修正，不得选择方便的一方继续。

## 7. 正文结构

### 7.1 根规范

根规范（Root Specification）只用于 `key: "ldvh-root"` 与 `structure: "root"`。根规范保留 00 的上位叙事结构，并在文末保留验证要求、Human Gate 和 Stop Conditions。本文不得要求 00 改成标准规范结构。

### 7.2 标准规范

标准规范（Standard Specification）依次包含：

1. 唯一 H1；
2. H1 后固定位置的 YAML 身份块；
3. `1. 价值判断`；
4. `2. 规范依据`；
5. `3. 职责边界`；
6. `4. 适用范围`；
7. 一个或多个由本规范职责决定的规则主体 H2；
8. `验证要求`；
9. `Human Gate`；
10. `Stop Conditions`。

全部 H2 使用连续阿拉伯数字编号。Code 根据固定标题识别信息角色，不要求正文重复维护章节索引。

验证要求沿用 00 的七列：验证对象、验证时机、成立条件、可接受依据、验证入口、可证明范围、未满足时的处理。

标准规范没有新增 Human Gate 或 Stop Conditions 时仍保留相应章节，并明确沿用 00 及实际适用的来源规则；不得为了填充结构制造没有来源的条件。

## 8. 主动声明关系

### 8.1 上位语义依赖

上位语义依赖（Upstream Semantic Dependency）由 `basis` 表达，只列出理解、判断或维护当前规范所必需的直接上位规范。

`basis` 使用稳定职责标识，不使用路径或编号；当前有效规范只依赖其他当前有效规范，依赖关系不得形成环。

声明 `basis` 不表示上位规范的全部规则无条件适用于当前事项。具体规则是否命中仍由来源规范的适用范围决定。

上位规则命中当前职责和事项时，下位规范必须遵守，不得重新解释、覆盖或弱化其定义。下位规范只补充自身职责范围内的增量；需要改变上位定义时，必须回到定义来源修改。

### 8.2 结构归属

结构归属（Structural Parent Relationship）由 `parent_spec` 表达，只在规范确实存在直接结构父规范时使用。结构归属不自动构成上位语义依赖；两种关系都成立时分别声明。

### 8.3 替代关系与普通引用

替代关系（Supersession Relationship）由 `supersedes` 表达，只用于职责被实质拆分、合并或替代。单纯改标题、改编号或移动文件继续使用原 `key`，不建立替代关系。

正文链接只表达所在语句明确说明的普通引用，不自动产生依赖、结构归属、附件授权或替代关系。低频替代操作的详细步骤不在本文规定。

## 9. 附件授权

附件授权（Attachment Authorization）由父规范的 `authorized_attachments` 表达。附件只有在自身为 `active`、唯一父规范为当前有效并且父规范正文明确说明授权对象和边界时，才进入当前规则源。

附件不通过自己的字段自我授权，父规范关系由 Code 根据授权列表派生。

附件只能承载父规范正文已经定义并授权的稳定结构化内容，例如较大的字段表、枚举和矩阵。附件不得承载根理念、父规范尚未定义的核心规则、独立适用范围、行动流程、Human Gate、Stop Conditions，或可由 Code 派生的目录和反向关系。

附件与父规范正文冲突时，以父规范定义的授权边界为判断来源，暂停消费冲突附件并同步修正；不得把附件当作便利例外继续使用。

本文当前不授权附件。未来术语表如采用附件形式，必须在本文正式生效后另行建立和授权，不能参与本文自身的首次识别。

## 10. 生命周期与 Git 生效边界

规范载体只使用三个生命周期状态：

| 状态 | 中文名称 | 是否属于当前规则源 |
| --- | --- | --- |
| `draft` | 草案（Draft） | 否 |
| `active` | 当前声明（Active Status Declaration） | 通过其余校验后属于 |
| `retired` | 退出（Retired） | 否 |

尚未进入 `active` 的草案可以继续修改或删除。当前规范不再适用时转为 `retired`；由新职责承接时，新载体可以用 `supersedes` 保留替代关系。本文不规定物理归档流程。

修改当前规范时，应同步核对受影响的价值、依据、职责、范围、规则、验证、Human Gate、Stop Conditions、身份字段、关系和附件；只更新正文或只更新身份块都不能证明变更完整。

当前规则源默认来自当前检出的 `HEAD` 提交。工作树（Working Tree）中的修改只用于编辑和预览；面向提交的校验必须针对暂存区（Index）实际将提交的完整内容。未提交修改不会静默改变当前规则源，只有提交后的有效 `active` 载体才进入新的当前规则源。

版本升级、批量重编号、批量移动、拆分合并和历史清理属于低频内部维护。它们只需遵守稳定 `key`、不丢失当前有效规则、关系同步和验证成立等结果约束；详细步骤在实际需要时由维护指南或行动模板承接。

## 11. 双语术语与未来术语表

准备进入全局术语表、暴露给机器接口，或者存在跨语言歧义风险的核心名词，必须同时确定中文规范术语（Canonical Chinese Term）和英文规范术语（English Canonical Term）。两种名称必须表达同一概念，而不是对现有词语作机械翻译；普通中文表达不因此全部进入双语治理。

机器字段、枚举和对象名称属于机器表示（Machine Representation），必须与双语术语建立明确映射，但不能代替术语定义。例如：稳定职责标识（Stable Responsibility Identifier）对应机器字段 `key`。

纳入双语治理的术语首次定义时使用“中文规范术语（English Canonical Term）”；后续中文正文优先使用中文规范术语，机器字段和值使用反引号。只在单篇规范中使用、不会影响跨规范理解的局部表达，不进入全局术语表。

未来术语表只登记名称和来源，不复制概念定义。最小结构为：

| 中文规范术语 | English Canonical Term | 机器表示 | 唯一定义来源 | 其他有效表达 | 历史名称 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |

“机器表示”只填写精确字段、枚举或对象名称；没有直接机器表示时填写 `—`，不得填写解释性定义。“状态”只使用 `current` 或 `historical`，分别表示当前推荐表达或仅供历史检索。

术语含义由“唯一定义来源”指向的规范正文承担。术语表与来源冲突时回到来源规范修正，术语表不得自行裁决或形成第二定义点。

## 12. 派生导航与 Code 消费

派生导航（Derived Navigation）是 Code 根据当前规则源生成的目录、关系和读取建议。Code 可以从身份块、H1、固定 H2、主动声明关系和附件授权派生：

- 当前规范及附件清单；
- `key`、编号、标题和路径映射；
- 上位语义依赖、结构归属、附件授权和替代关系；
- 反向关系和面向 AI 的建议读取范围；
- 身份、结构和关系诊断。

派生结果用于定位、压缩上下文和诊断，不是第二规则源，不得改变规则身份、适用范围或效力。

YAML 身份块是 Code 进行身份发现、规则定位和关系解析的稳定入口；Code 仍需按正文结构读取相应规则。V4 解析器、校验器或 Helper 尚未实现、接入或验证时，必须如实说明能力缺口，不能把规范设计声明成已可用能力。

## 13. 验证要求

## 14. Human Gate

以下事项必须进入 Human Gate：

1. 改变 00 授权的 Specs 共同结构治理范围；
2. 改变候选路径、当前规则源成立条件或派生结果的非权威边界；
3. 改变最小身份字段、根/标准结构、生命周期闭集或主动声明关系的含义；
4. 无法判断两份规范是不同职责，还是形成重复当前职责；
5. 准备退出、拆分、合并或替代当前有效规范，但无法确认其规则是否已被完整承接；
6. 改变受双语治理的核心术语，可能造成既有规则含义变化；
7. 本文设计与 00 发生冲突，需要修改上位定义。

普通草案编辑、格式修正、等义措辞优化以及不改变上述语义的内部维护，不因本文额外进入 Human Gate。

## 15. Stop Conditions

出现以下任一情况时，必须暂停受影响的规范解析、修改或声明：

1. 当前规则源中的规范载体无法识别，或声明 `active` 的文件身份、结构或状态无法确认；
2. 稳定 `key`、规范编号或附件编号重复，编号与文件名不一致，或者不同 `key` 的当前规范承担同一职责；
3. 当前有效的 `basis` 或 `parent_spec` 指向缺失、非当前有效目标或形成环；
4. 附件未获唯一当前有效父规范授权，或内容超出授权边界；
5. 身份块与规则正文冲突，或者准备删除仍然适用且尚未承接的规则；
6. 受双语治理的核心术语中，中英文名称或机器表示指向不同概念，已经影响规则理解或 Code 解析；
7. Code、索引、测试或过程记录正在反向定义规则，或把未实现能力声明为已可用。

暂停只影响与冲突载体、关系、附件或术语直接相关的最小范围。恢复时必须修正触发原因并完成相应验证；不得通过忽略错误文件或扩大未验证声明来恢复。
